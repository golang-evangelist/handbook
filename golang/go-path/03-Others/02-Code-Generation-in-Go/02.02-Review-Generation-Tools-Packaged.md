# 02.02 Packaged tools for code generation

> **Go Path - Zero to Gopher** / **03 Others → Code Generation in Go** / Lesson 02.02

## Lesson goals

After this lesson you will be able to:

- use `stringer` as a typical small external generator with `//go:generate`;
- understand the role of `protoc-gen-go` in the `.proto` → `*.pb.go` chain;
- pin tool versions (`go run tool@version` or `tools.go`);
- decide when to use an off-the-shelf tool vs write your own (02.03);
- predict PATH / `go_package` / drift errors and verify with a trace.

## Prerequisite

- 02.01 (`go generate`, directives, `DO NOT EDIT`).
- Go 1.22+.
- Preferably: basic protobuf concept (details in the gRPC/proto block).
- Terminal and `go.mod` in a working module.

## Problem this lesson solves

Teams either hand-write `String()` for every enum, or invoke the wrong tool version “from a blog post”. External generators are powerful only when **pinned**, documented, and tied to a directive. This lesson shows two representative tools:

1. **stringer** — source is a Go type with constants;
2. **protoc-gen-go** — source is `.proto` outside Go files, a plugin for `protoc`.

Both fit the same `go generate` flow you already know.

## Mental model

```text
  [Go tip + const] --stringer-->           [*_string.go]
  [.proto]         --protoc + protoc-gen-go--> [*.pb.go]
         \                ^
          \               |
           +-- //go:generate (in a .go file) --+
```

In common: source of truth ≠ generated Go. Difference: stringer reads Go package/constants; `protoc` reads IDL and sends a request to the plugin over the stdin/stdout protocol.

### Glossary

| Term (English) | Role | Typical output |
|----------------|------|----------------|
| `stringer` | CLI from `golang.org/x/tools/cmd/stringer` | `String() string` |
| `protoc` | protobuf compiler | invokes plugins |
| `protoc-gen-go` | plugin (name on PATH) | `*.pb.go` |
| `go_package` | option in `.proto` | import path / package name |
| pin | fixed tool version | deterministic diff |
| `tools.go` | blank import of tools into module | versions in `go.mod` |

## Mechanism

### 1. stringer — input and output

`stringer` generates a `String() string` method for types with constants (most often the `iota` enum pattern).

Minimal invocation:

```text
go run golang.org/x/tools/cmd/stringer@v0.22.0 -type=Status
```

Default output: `status_string.go` (name from the type). You can change `-output`.

### 2. Official stringer flags (do not invent others)

| Flag | Meaning |
|------|---------|
| `-type` | required; comma-separated list of types |
| `-output` | output file name |
| `-trimprefix` | strip prefix from constant name in the string |
| `-linecomment` | use line comment text instead of the name |
| `-tags` | build tags (when input is a directory) |

Example with multiple types:

```text
go run golang.org/x/tools/cmd/stringer@v0.22.0 -type=Status,Phase
```

### 3. Trace: stringer from constant to `String()`

Input:

```go
package job

//go:generate go run golang.org/x/tools/cmd/stringer@v0.22.0 -type=Phase

type Phase int

const (
	PhasePending Phase = iota
	PhaseRunning
	PhaseDone
)
```

**Trace**

```text
1. go generate .
2. cwd = package job dir
3. runs stringer -type=Phase
4. stringer loads package, finds constants of type Phase
5. emits phase_string.go with DO NOT EDIT
6. PhasePending.String() → "PhasePending" (without -trimprefix)
```

### 4. Predict, then check: `-trimprefix`

Same constants, directive:

```go
//go:generate go run golang.org/x/tools/cmd/stringer@v0.22.0 -type=Phase -trimprefix=Phase
```

**Predict:** `PhaseRunning.String()`?

**Check:** `"Running"` — prefix `Phase` stripped from the identifier when emitting the string.

### 5. Predict, then check: `-linecomment`

```go
const (
	PhasePending Phase = iota // pending
	PhaseRunning              // running
	PhaseDone                 // done
)
```

```go
//go:generate go run golang.org/x/tools/cmd/stringer@v0.22.0 -type=Phase -linecomment
```

**Predict:** `PhasePending.String()`?

**Check:** `"pending"` (text after `//` on that line), not `"PhasePending"`.

Useful when logs/API require a stable string different from the Go identifier.

### 6. protoc-gen-go — call chain

```text
protoc --go_out=DIR --go_opt=OPT file.proto
        |
        +--> looks for protoc-gen-go executable on PATH
        +--> sends CodeGeneratorRequest (protobuf) to plugin stdin
        +--> reads CodeGeneratorResponse from stdout
        +--> writes *.pb.go
```

Naming convention: plugin for `--X_out` is called `protoc-gen-X`. So `--go_out` looks for `protoc-gen-go`.

### 7. Minimal `.proto` and Go option

```proto
syntax = "proto3";

package demo.v1;

option go_package = "example.com/demo/gen/demopb";

message Hello {
  string name = 1;
}
```

`go_package` sets the Go import path (and package name — often the last segment, or `path;name` form).

### 8. Typical call with `paths=source_relative`

```text
protoc --go_out=. --go_opt=paths=source_relative hello.proto
```

| `paths` | Where `*.pb.go` goes |
|---------|------------------------|
| `import` (default) | under tree per import path from `go_package` |
| `source_relative` | next to input `.proto` (relative to out dir) |

**Predict:** Without `source_relative`, with `go_package = "example.com/demo/gen/demopb"` and `--go_out=.`, where do you expect the file?

**Check:** often `./example.com/demo/gen/demopb/hello.pb.go` (import layout). That is why teams in small packages prefer `paths=source_relative`.

### 9. Wiring to `go generate`

Stringer in a Go file next to the type:

```go
//go:generate go run golang.org/x/tools/cmd/stringer@v0.22.0 -type=Status -linecomment
```

Proto — `go generate` lives in a `.go` file even when the source is `.proto`:

```go
package demopb

// Source of truth: hello.proto in the same directory.
//
//go:generate protoc --go_out=. --go_opt=paths=source_relative hello.proto
```

### 10. Trace: “plugin not found”

```text
protoc-gen-go: program not found or is not executable
Please specify a program using absolute path or make sure the program is available in your PATH system variable
```

**Diagnostic trace**

```text
1. protoc run with --go_out
2. looks for protoc-gen-go on PATH
3. not found → error above
4. fix A: go install google.golang.org/protobuf/cmd/protoc-gen-go@v1.34.2
           add $(go env GOPATH)/bin to PATH in the same session
5. fix B: wrapper that explicitly exports PATH before protoc
```

Do not mix the old module `github.com/golang/protobuf` with new `google.golang.org/protobuf` without a conscious migration plan.

### 11. Predict, then check: two plugin versions

```text
Dev A: protoc-gen-go v1.28
Dev B: protoc-gen-go v1.34
both run go generate
```

**Predict:** Is `*.pb.go` identical?

**Check:** Often not — small differences in generated code / comments. Code review becomes noise. Pin in script or `go run` / `go install` same version for everyone.

### 12. `tools.go` pattern

```go
//go:build tools

package tools

import (
	_ "golang.org/x/tools/cmd/stringer"
	_ "google.golang.org/protobuf/cmd/protoc-gen-go"
)
```

Then:

```text
go mod tidy
go install golang.org/x/tools/cmd/stringer
go install google.golang.org/protobuf/cmd/protoc-gen-go
```

Versions live in `go.mod`. Tools are not runtime imports — blank import + build tag `tools` keeps them out of normal build.

### 13. Trace: `go run` in directive vs `PATH` binary

```text
A) //go:generate stringer -type=Status
   → depends on PATH; CI agent may have another version

B) //go:generate go run golang.org/x/tools/cmd/stringer@v0.22.0 -type=Status
   → version in the line; slower first time (download), but reproducible
```

For small projects B often wins. For large monorepos: `tools.go` + `go install` in bootstrap script, then short directive.

### 14. Predict, then check: wrong `go_package`

Module: `example.com/shop`

```proto
option go_package = "github.com/other/oldpath/pb";
```

**Predict:** What breaks?

**Check:** import paths in other packages do not match your module; `go build` / `go mod` chaos. `go_package` should start with your module path, e.g. `example.com/shop/gen/orderpb`.

### 15. Script wrapper + short directive

```powershell
# scripts/gen-stringer.ps1
$ErrorActionPreference = "Stop"
Set-Location $PSScriptRoot/..
go run golang.org/x/tools/cmd/stringer@v0.22.0 -type=Phase ./internal/job
```

```go
//go:generate pwsh -File ../../scripts/gen-stringer.ps1
```

**Trace:** `go generate` only runs pwsh; flags live in the script; Linux CI needs a `.sh` equivalent or plain `go run` without a shell.

### 16. Predict, then check: `-linecomment` without comments

```go
const (
	A Status = iota
	B // only-b
)
```

**Predict:** `A.String()` and `B.String()` with `-linecomment`?

**Check:** `A` → `"A"` (no line comment, name stays); `B` → `"only-b"`. The flag does not force a comment on every line.

### 17. When stringer is *not* enough

- `String()` must be localized (multiple languages).
- String depends on runtime state, not only the constant.
- You need a `code → description` map from richer annotations (then 02.03 or another tool).

### 18. When to write your own tool instead of an off-the-shelf one

- Domain comments must become a separate help map.
- You need a separate file per constant / special layout.
- Off-the-shelf tool forces wrong naming style and has no flag for it.

Otherwise — prefer a maintained external generator.

### 19. Trace: CI and stringer drift

```text
1. PR changes iota order
2. developer does not run generate
3. CI: go generate ./... && git diff --exit-code
4. *_string.go differs → FAIL
5. developer regenerate, amend/new commit
```

Diff in a generated file is not “noise” — it proves the source of truth changed.

### 20. Predict, then check: `paths=import` in a narrow package

Layout:

```text
/api
  hello.proto
  doc.go      //go:generate protoc ...
```

`go_package = "example.com/app/api"`
`--go_out=.` bez `source_relative`

**Predict:** Does `hello.pb.go` appear in `/api`?

**Check:** Often not — it goes under `example.com/app/api/` below `--go_out`. That is why local packages almost always set `--go_opt=paths=source_relative`.

### 21. Ecosystem map (pattern, not a catalog to learn at once)

| Tool | Source | Typical output |
|------|--------|----------------|
| `stringer` | Go constants | `String()` |
| `protoc-gen-go` | `.proto` messages | struct + API |
| `protoc-gen-go-grpc` | service in proto | gRPC stubs |
| mockgen / mockery | `interface` | mock types |

Pattern is always the same: **source → tool → directive → pin → CI**.

### 22. Predict, then check: bare `stringer` on a clean machine

Fresh CI image, no `GOPATH/bin` on PATH, directive:

```go
//go:generate stringer -type=Status
```

**Predict:** Success?

**Check:** Fail — `stringer: executable file not found`. Switch to `go run ...@version` or bootstrap `go install` in the workflow.

### 23. Determinism and order

External tools should emit the **same** byte-for-byte output for the same input (with the same version). If your wrapper sorts paths or uses `map` range without sorting, CI diff jumps. Stringer and protoc-gen-go are disciplined there; custom wrappers often are not.

### 24. License and maintenance

Before you bring a tool into a critical path:

1. Is it maintained?
2. Can the version live in `go.mod`?
3. Does output pass `gofmt` / compile?
4. Is the license OK for your context?
5. Can the team debug when generate fails?

### 25. Trace: from `.proto` field to Go field

```proto
message Hello {
  string name = 1;
}
```

**Trace (simplified)**

```text
protoc parses message Hello
protoc-gen-go emits type Hello
field name → Name  (exported, CamelCase)
getter / proto reflection metadata with struct
```

You do not write that boilerplate. Change `.proto`, regenerate, compile clients.

### 26. Predict, then check: `-type` with two types, one output

```go
//go:generate go run golang.org/x/tools/cmd/stringer@v0.22.0 -type=Status,Phase
```

**Predict:** How many output files by default?

**Check:** One — default name from the *first* type (`status_string.go`), and methods for both types go in that file (unless `-output` says otherwise). Check docs for the version you pin if you split outputs.

### 27. Workshop flow for an external tool

1. Change source (constant or `.proto` field).
2. Run `go generate` (or script).
3. Run `go test ./...`.
4. Commit source + output together.
5. If you skip step 2, CI must catch you.

### 28. What a reviewer looks for in a PR with generate

- Directive next to source?
- Output has `DO NOT EDIT`?
- Style like after `gofmt`?
- No non-deterministic ordering?
- README mentions command and pin?

### 29. Predict, then check: `option go_package` with `;name`

```proto
option go_package = "example.com/app/gen/foopb;foopb";
```

**Predict:** What is the import path, and what is the package name in the Go file?

**Check:** Import path is the part before `;` (`example.com/app/gen/foopb`); package name is `foopb`. Form without `;` derives package name from the last path segment.

### 30. FAQ (short)

**Does generate run in `go test`?** Not automatically.

**May I hand-edit a gen file “just this once”?** No. Change the generator or source.

**What about conflict in a gen file?** Regenerate after merging source.

**Do generics (Go 1.22+) kill stringer?** No. Generics reduce *some* container generators, not IDL and `String()` for enums.

### 31. Trace: stringer array check after inserting a constant

```text
const (
  A T = iota  // 0
  B           // 1
)
// generated: _ = x[B-1]

insert Mid between A and B:
  A=0, Mid=1, B=2
old generated still: _ = x[B-1]  → B-1=1, OK index?
actually stringer regenerates indices and switch too;
without regenerate: String() for B may lie + array trick breaks depending on change
```

So: after every const block change — generate.

### 32. Mini tool selection checklist

1. Is there a maintained generator?
2. Can version live in `go.mod` / `go run @ver`?
3. Does output pass the compiler?
4. License OK?
5. Can the team debug failures?

If five times “no” — another tool, or 02.03.

## Rules and syntax

| Tool | Source | Output | Typical directive |
|------|--------|--------|-------------------|
| stringer | Go constants | `*_string.go` | `go run .../stringer@ver -type=T` |
| protoc-gen-go | `.proto` | `*.pb.go` | `protoc --go_out=... --go_opt=...` |

Pinning:

```text
go run golang.org/x/tools/cmd/stringer@v0.22.0 -type=Status
```

Avoid “whatever is latest on the CI agent” without locking.

For proto plugin version align with `google.golang.org/protobuf` runtime in `go.mod` (generator and runtime must not drift too far apart).

## Examples

### Example 1: stringer with `-linecomment`

```go
package job

//go:generate go run golang.org/x/tools/cmd/stringer@v0.22.0 -type=Phase -linecomment

type Phase int

const (
	PhasePending Phase = iota // pending
	PhaseRunning              // running
	PhaseDone                 // done
)
```

**Predict, then check**

| Expression | Predict | Check |
|------------|---------|-------|
| `PhasePending.String()` | `"pending"` | yes |
| `Phase(99).String()` | `Phase(99)` style | yes (default branch) |

### Example 2: `-trimprefix` + `-linecomment` together

When a line comment exists, `-linecomment` takes priority for that string. Without a comment, trim applies.

```go
const (
	StatusOK Status = iota // ok
	StatusFail
)
//go:generate go run golang.org/x/tools/cmd/stringer@v0.22.0 -type=Status -trimprefix=Status -linecomment
```

**Predict:** `StatusOK` → ? `StatusFail` → ?

**Check:** `"ok"` and `"Fail"`.

### Example 3: protoc-gen-go minimal input

```proto
syntax = "proto3";

package demo.v1;

option go_package = "example.com/demo/gen/demopb";

message Hello {
  string name = 1;
}
```

```text
protoc --go_out=. --go_opt=paths=source_relative hello.proto
```

**Trace:** `hello.pb.go` appears with type `Hello` and field `Name`.

### Example 4: Directive next to proto

```go
package demopb

// Package demopb holds generated types.
// Source: hello.proto in the same directory.
//
//go:generate protoc --go_out=. --go_opt=paths=source_relative hello.proto
```

**What happens here:** the `go generate` hook is in the `.go` file; source of truth is `.proto`. An empty/documentation package file is common.

### Example 5: tools.go + install

```go
//go:build tools

package tools

import (
	_ "golang.org/x/tools/cmd/stringer"
	_ "google.golang.org/protobuf/cmd/protoc-gen-go"
)
```

**Predict:** Does `go build ./...` compile this package into the service binary?

**Check:** Not in normal build because of `//go:build tools` — file is excluded unless you explicitly request that tag.

### Example 6: Wrapper that pins plugin on PATH

```powershell
$env:PATH = "$(go env GOPATH)\bin;" + $env:PATH
go install google.golang.org/protobuf/cmd/protoc-gen-go@v1.34.2
protoc --go_out=. --go_opt=paths=source_relative .\api\hello.proto
```

**Trace:** same session sees same binary; another machine without `go install` step → plugin not found.

### Example 7: Predict, then check — commit only `.proto`

Team commits `*.pb.go`. Developer changes a field in `.proto`, regenerates locally, `git add` only `.proto`.

**Predict:** CI outcome with generate+diff?

**Check:** FAIL on `*.pb.go` diff. Fix: commit source + output together.

### Example 8: Tool comparison in one table

| Question | stringer | protoc-gen-go |
|----------|----------|---------------|
| Input | Go type | `.proto` |
| Need `protoc`? | no | yes |
| Typical output | `String()` | struct + proto API |
| Pin | `go run @ver` | install / PATH + version |
| Directive lives in | `.go` next to type | `.go` next to `.proto` |

### Example 9: Predict, then check — stringer without `-type`

```text
go run golang.org/x/tools/cmd/stringer@v0.22.0
```

**Predict:** What happens?

**Check:** Error — `-type` must be set. Stringer does not guess the type from the package.

### Example 10: Trace — from PATH error to green CI

```text
CI log: protoc-gen-go: program not found
  → workflow adds:
       go install google.golang.org/protobuf/cmd/protoc-gen-go@v1.34.2
       echo "$(go env GOPATH)/bin" >> $GITHUB_PATH
  → same job: protoc --go_out=...
  → *.pb.go is created
  → diff check passes
```

Without `GITHUB_PATH` (or equivalent) the next step still does not see the plugin.

### Example 11: Documentation package file for generate only

```go
// Package apiwire holds protobuf types.
// Regeneration: go generate .
package apiwire
```

With directive in the same or adjacent file. No runtime logic — only hook and documentation. That is a valid idiomatic pattern.

### Example 12: Predict, then check — old vs new protobuf module

```go
import "github.com/golang/protobuf/proto" // old path
```

versus

```go
import "google.golang.org/protobuf/proto"
```

**Predict:** May you mix generated code from new-world `protoc-gen-go` with old runtime without a plan?

**Check:** Not without migration. Pin generator and runtime from the same ecosystem (`google.golang.org/protobuf`) and document in README.

### Example 13: Short onboarding text (template)

```text
1. Install protoc (version X) — link in README
2. go install google.golang.org/protobuf/cmd/protoc-gen-go@v...
3. Add GOPATH/bin to PATH
4. go generate ./...
5. go test ./...
```

Five lines prevent an hour of onboarding chaos.

## Decision analysis

**Off-the-shelf tool** — when the problem is standard (enum strings, proto messages, OpenAPI with a known generator).

**Custom generator** — when you have a domain DSL or mapping no tool covers cleanly (02.03).

**Do not use stringer** — if `String()` must be localized or depends on runtime state.

**Script vs bare directive** — script when you have `protoc` + multiple plugins + PATH setup; bare `go run` for stringer on a small package.

## Trade-offs

| Choice | You gain | You pay |
|--------|----------|---------|
| stringer | fast, idiomatic | only for constants |
| protoc-gen-go | gRPC/proto ecosystem | `protoc` + plugin setup |
| hand-written `String()` | full control | maintenance, silent drift |
| `latest` without pin | “always new” | non-determinism |
| `tools.go` | versions in module | bootstrap step |
| `go run @ver` in directive | zero PATH | slower first download |

## Common mistakes

1. `stringer` not on PATH, but directive calls bare `stringer`.
2. Wrong `go_package` — generated import is invalid.
3. Commit only `.proto` without regenerating `*.pb.go` (if team commits generated).
4. Mixing old `github.com/golang/protobuf` path with `google.golang.org/protobuf`.
5. Generating into wrong directory because of `paths=import` vs `source_relative`.
6. Different `protoc-gen-go` versions per developer.
7. Hand-editing `*.pb.go` / `*_string.go`.
8. Forgotten `protoc` on CI (you have plugin, not compiler).

## Idiomatic Go

- Pin tool versions.
- `Code generated; DO NOT EDIT`.
- One source of truth.
- CI diff check.
- Prefer `go run tool@version` in directives for small projects.
- For proto: document `protoc` and plugin version in README.
- Do not resolve merge conflicts by hand in generated code — regenerate after merging source.

## Practical scenario

Team adopts gRPC. Each developer installs “some” `protoc` and “some” `protoc-gen-go` from the web. `*.pb.go` diffs jump in every PR. Review takes longer from noise than from logic.

They introduce `./scripts/gen-proto.ps1` (and `.sh` for Linux CI) that:

1. pins plugin via `go install ...@v...`;
2. sets PATH;
3. calls `protoc` with `--go_opt=paths=source_relative`;
4. documents exact `protoc` version in README.

`//go:generate` directive calls the script. Onboarding: one command, zero surprises. Stringer stays `go run @ver` in packages with enums.

## Summary

External generators such as stringer and `protoc-gen-go` cover standard source→Go bridges. Tie them to `go generate`, pin versions, choose correct output layout (`source_relative` when needed), and do not mix hand code with output. The pattern is always the same — only source and tool change.
