# 02.03 In-source generators: go/ast, go/parser, go/format

> **Go Path - Zero to Gopher** / **03 Others → Code Generation in Go** / Lesson 02.03

## Lesson goals

After this lesson you will be able to:

- parse a Go file into an AST using `go/parser` and `go/token`;
- walk the AST (`ast.Inspect` or `f.Decls`) and extract types/constants;
- emit code and format it with `go/format`;
- wire a small local generator into `//go:generate` with `//go:build ignore`;
- predict errors (wrong cwd, emit without format, generator in the build) and verify with a trace.

## Prerequisite

- 02.01–02.02.
- Basic understanding of Go syntax (types, constants, `package`).
- Go 1.22+.
- Willingness to read the `go/ast` package documentation (you do not have to memorize every node).

## Problem this lesson solves

When an off-the-shelf tool does not cover your pattern — e.g. a help table from line comments, a name list for an admin UI, a separate file per constant — you need a generator that *reads Go* and *writes Go*. Without AST people run regex over the source: it breaks on comments, strings, and formatting. This lesson builds a minimal, correct path: parser → model → emit → `format.Source` → write.

## Mental model

```text
source.go
   │
   ▼
token.FileSet + parser.ParseFile
   │
   ▼
*ast.File  (declaration tree)
   │
   ▼
your extract logic  →  model (slice of names, maps, struct)
   │
   ▼
emit ([]byte / strings.Builder)  →  format.Source  →  out.gen.go
```

AST is a tree of nodes (`*ast.File`, `*ast.GenDecl`, `*ast.TypeSpec`, `*ast.ValueSpec`, …). `token.FileSet` remembers positions for compiler-style error messages.

### Concept table

| Concept (English) | Package | Role |
|-------------------|---------|------|
| `FileSet` | `go/token` | position map → file:line:column |
| `ParseFile` | `go/parser` | text/file → `*ast.File` |
| `ast.Inspect` | `go/ast` | DFS walk of the tree |
| `GenDecl` | `go/ast` | `import` / `const` / `type` / `var` block |
| `ValueSpec` | `go/ast` | names in `const`/`var` |
| `format.Source` | `go/format` | `gofmt` over `[]byte` |
| `//go:build ignore` | constraint | exclude `main` generator from the package |

## Mechanism

### 1. Five mandatory steps

1. `fset := token.NewFileSet()`
2. `f, err := parser.ParseFile(fset, path, nil, parser.ParseComments)` (or `0` if comments are not needed)
3. Walk `f.Decls` / `ast.Inspect`, filter types and constants
4. Assemble Go source into a buffer
5. `format.Source(raw)` then `os.WriteFile`

If you skip step 5, the output often “works” but does not pass team style and easily hides syntax errors.

### 2. Parsing a file — skeleton

```go
package main

import (
	"fmt"
	"go/parser"
	"go/token"
	"os"
)

func main() {
	fset := token.NewFileSet()
	f, err := parser.ParseFile(fset, "status.go", nil, parser.ParseComments)
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	fmt.Println("package:", f.Name.Name)
}
```

**Trace**

```text
NewFileSet()           → empty set of files
ParseFile(..., path)   → reads disk, fills fset, builds *ast.File
f.Name.Name            → "status" (package identifier)
```

### 3. Predict, then check: parsing from a string

```go
src := `package p
const X = 1
`
f, err := parser.ParseFile(fset, "p.go", src, 0)
```

**Predict:** Does the file `p.go` need to exist on disk?

**Check:** No. The third argument (`src`), if not `nil`, is used as the source; the name `"p.go"` is for positions in errors. Ideal for unit tests.

### 4. Walking: `Inspect` vs `f.Decls`

For top-level constants a direct pass is often clearer:

```go
for _, d := range f.Decls {
	gd, ok := d.(*ast.GenDecl)
	if !ok || gd.Tok != token.CONST {
		continue
	}
	for _, spec := range gd.Specs {
		vs := spec.(*ast.ValueSpec)
		for _, name := range vs.Names {
			_ = name.Name
		}
	}
}
```

`ast.Inspect` is handy when you search deep in the tree (nested nodes, types inside functions). For a package-level enum generator — `Decls` is more readable.

### 5. Trace: filtering constants by type

Input:

```go
type Status int

const (
	Idle Status = iota
	Busy
)

const Other = 3
```

**Trace of extract logic (goal: only Status)**

```text
find TypeSpec named Status
walk const GenDecl
for each ValueSpec:
  if explicit type == Status → take the name
  if type omitted (iota group) → inherit the group type
skip Other (not Status)
result: Idle, Busy
```

A simplified skeleton often takes all `ast.Con` names — that is OK for learning, but production must filter by type like stringer.

### 6. Emit + format

```go
func writeList(pkg string, names []string) error {
	var b bytes.Buffer
	fmt.Fprintf(&b, "// Code generated by genlist; DO NOT EDIT.\n\n")
	fmt.Fprintf(&b, "package %s\n\n", pkg)
	fmt.Fprintf(&b, "var AllNames = []string{\n")
	for _, n := range names {
		fmt.Fprintf(&b, "\t%q,\n", n)
	}
	fmt.Fprintf(&b, "}\n")
	formatted, err := format.Source(b.Bytes())
	if err != nil {
		return err
	}
	return os.WriteFile("names_gen.go", formatted, 0o644)
}
```

**Predict:** What if you put `var AllNames = []string{` without the closing `}` in the emit?

**Check:** `format.Source` returns an error — an early signal. Better than writing invalid Go.

### 7. `//go:build ignore` + directive

```go
// gen_names.go
//go:build ignore

package main
// ... generator ...
```

```go
// status.go
package status

//go:generate go run ./gen_names.go

type Status int

const (
	Idle Status = iota
	Busy
)
```

**Trace**

```text
go build .
  → gen_names.go excluded (ignore)
go generate .
  → go run ./gen_names.go  (explicit)
  → writes names_gen.go in the package cwd
go test .
  → sees names_gen.go as part of package status
```

### 8. Predict, then check: generator without ignore

Same `package status` in `gen_names.go` with `func main()` and no build tag.

**Predict:** `go build .`?

**Check:** Fail — `main` redeclared / wrong package for a library, or a conflict. That is why ignore (or a separate module/cmd directory).

### 9. Errors with position

```go
if err != nil {
	fmt.Fprintln(os.Stderr, fset.Position(f.Pos()), err)
}
```

The message looks like the compiler: `status.go:1:1: ...`. Without `FileSet` you lose context.

### 10. Predict, then check: `ParseComments`

You have line comments `// pending` that you want in a help map.

```go
parser.ParseFile(fset, path, nil, 0) // without ParseComments
```

**Predict:** Are the comments in the AST?

**Check:** Not reliably for your use — pass `parser.ParseComments` and read `ast.CommentGroup` from declarations / fields.

### 11. Deterministic output

If you collect names from `map[string]T`, **sort** before emitting. Otherwise CI sees a random key order.

```go
sort.Strings(names)
```

Stringer and similar tools are deterministic — your generator must be the same.

### 12. Trace: from fixture test to extract

```go
func TestExtract(t *testing.T) {
	src := `package p
type T int
const (
	A T = iota
	B
)`
	fset := token.NewFileSet()
	f, err := parser.ParseFile(fset, "p.go", src, 0)
	if err != nil {
		t.Fatal(err)
	}
	names := extractConsts(f, "T")
	if len(names) != 2 || names[0] != "A" {
		t.Fatalf("%v", names)
	}
}
```

**Trace**

```text
no disk
ParseFile from a string
extractConsts reads AST
assert on the model — emit is tested separately
```

### 13. Separate extract and render

```text
extractNames(f, typeName) []string
render(pkg string, names []string) ([]byte, error)
```

You test extract without writing to disk. You test render with a fixed model. That is the difference between a script and a tool.

### 14. Predict, then check: relative path

Directive:

```go
//go:generate go run ./gen_names.go
```

The generator does:

```go
f, err := parser.ParseFile(fset, "status.go", nil, 0)
```

You run `go generate` from the **repo root** as `go generate ./internal/status`.

**Predict:** Does `status.go` exist relatively?

**Check:** Yes — cwd is the `status` package directory, not root. If you hardcode `internal/status/status.go`, it breaks. Later (02.04) you read `GOFILE`.

### 15. `go/types` — when you need more than AST

| You need | Enough |
|----------|--------|
| constant names, line comments | AST |
| correct type after type-check (aliases, generics) | `go/types` + `packages` |
| only `String()` | ready-made stringer |

For this lesson we stay at the AST level — enough for a small list/map generator.

### 16. Predict, then check: regex vs AST

Input with a comment:

```go
const (
	// Idle means waiting
	Idle Status = iota
)
```

A “find identifiers after const” regex can pick wrong tokens or miss the format.

**Predict:** Does AST `ValueSpec.Names` still see `Idle`?

**Check:** Yes. A comment is a separate node; the name is stable.

### 17. Emit via `go/printer` (alternative)

Instead of a hand-built string you can build an AST and print:

```go
cfg := printer.Config{Mode: printer.UseSpaces | printer.TabIndent, Tabwidth: 8}
cfg.Fprint(&buf, fset, astNode)
```

For starters `strings.Builder` + `format.Source` is clearer. Use `printer` when you are already manipulating the AST tree.

### 18. Trace: the whole mini pipeline in your head

```text
status.go (Idle, Busy)
  → ParseFile
  → extract [Idle Busy]
  → render:
       // Code generated ...
       package status
       func Names() []string { return []string{"Idle", "Busy"} }
  → format.Source
  → names_gen.go
  → go test  (Names() len==2)
```

### 19. Predict, then check: empty const block

The type exists, no constants (yet).

**Predict:** What should `render` emit?

**Check:** Valid Go, e.g. `var AllNames = []string{}` or a function that returns an empty slice — no panic, no invalid syntax. Zero-value input = valid output.

### 20. Emit safety: `%q` for string literals

```go
fmt.Fprintf(&b, "\t%q,\n", n)
```

If the name is ever not a pure identifier (rare for const), `%q` produces a valid Go string. For identifiers in code (type names), validation is stricter — do not insert arbitrary text in place of identifiers.

### 21. Mini generator checklist

1. `//go:build ignore` (or a `cmd/` package)
2. `DO NOT EDIT` header
3. `format.Source`
4. Deterministic order
5. `//go:generate` directive
6. At least one test (string fixture)
7. Fail-fast messages on stderr

### 22. Predict, then check: write over an existing hand-edited file

`names_gen.go` already exists with old content.

**Predict:** Does `WriteFile` ask for confirmation?

**Check:** No — it overwrites. That is why DO NOT EDIT and CI: a generated file is not the place for manual patches.

### 23. When *not* to write your own AST generator

- You only need `String()` → stringer.
- You need proto → protoc-gen-go.
- The problem is a one-off 5-line copy-paste.

Write your own tool when the pattern is not covered and when it will repeat.

### 24. Trace: extract error in the CI log

```text
go generate ./internal/status
gen_names: status.go:14:2: expected ..., found ...
exit status 1
```

Without `fset.Position` you often see only `expected ...` without a file — harder for on-call.

### 25. Generator code organization

```text
/internal/status/
  status.go
  status_string.go      // from stringer (optional)
  names_gen.go          // from your tool
  gen_names.go          // ignore main
```

Or:

```text
/internal/cmd/gennames/
  main.go
  extract.go
  render.go
  extract_test.go
```

The second form scales better; the first is OK up to ~150–200 lines.

### 26. Predict, then check: `parser.AllErrors`

```go
parser.ParseFile(fset, path, nil, parser.AllErrors)
```

**Predict:** Difference from the default?

**Check:** More errors in one pass instead of stopping early. Useful in tooling; for a strict generator the first error + exit 1 often suffices.

### 27. Link to templates (02.05)

AST = reading. Template (`text/template`) = drawing output from the model. Idiom:

```text
extract (AST) → model struct → template.Execute → format.Source
```

This lesson stops at `fmt`/`Builder` emit; later ones replace emit with a template.

### 28. Predict, then check: `ast.File.Comments`

After `ParseComments`, `f.Comments` holds all comment groups.

**Predict:** Is it easier to map a line comment onto a `ValueSpec` via `f.Comments` or via a field on the spec?

**Check:** For line comments next to a constant you often look at `vs.Comment` / doc on the spec — closer to the node. `f.Comments` is useful for free-floating comments; do not mix them unnecessarily.

### 29. Mini map of nodes you actually use

| Node | When |
|------|------|
| `*ast.File` | root |
| `*ast.GenDecl` | const/type block |
| `*ast.TypeSpec` | type name |
| `*ast.ValueSpec` | constant names |
| `*ast.Ident` | identifier |
| `*ast.CommentGroup` | doc / line comments |

Do not learn the entire `go/ast` catalog at once — learn these six for an enum generator.

### 30. Trace: extract refactor → fewer bugs

```text
v1: 200-line main with Parse + Write mixed
  → bug: wrong type filter, hard to test
v2: extract_test.go with 5 fixture strings
  → bug caught in 2 minutes
v3: render_test.go checks empty slice
  → CI green after format change
```

The investment in separation pays back as soon as another developer touches the generator.

## Examples

### Example 1: Package name only

See mechanism §2. Goal: confirm the input exists and is valid Go before extract.

### Example 2: Finding const names (skeleton)

```go
func findConstNames(f *ast.File) []string {
	var names []string
	for _, d := range f.Decls {
		gd, ok := d.(*ast.GenDecl)
		if !ok || gd.Tok != token.CONST {
			continue
		}
		for _, spec := range gd.Specs {
			vs := spec.(*ast.ValueSpec)
			for _, name := range vs.Names {
				names = append(names, name.Name)
			}
		}
	}
	return names
}
```

#### What happens here

`findConstNames` walks the top-level declarations of a parsed `*ast.File`. It keeps `GenDecl` nodes whose token is `CONST`, then appends every name on each `ValueSpec`. The slice it returns is every constant name in the file. Nothing in the loop compares a name or a type with `Status`, so a production extractor still adds that filter.

**Predict, then check:** Does this filter by type `Status`?

**Check:** No — it takes all constants. Expand for production.

### Example 3: Emitting a list

See mechanism §6. After generate, `AllNames` must compile in the same package.

### Example 4: Complete mini loop

```go
//go:build ignore

package main

import (
	"fmt"
	"go/ast"
	"go/format"
	"go/parser"
	"go/token"
	"os"
	"strings"
)

func main() {
	const src = "status.go"
	fset := token.NewFileSet()
	f, err := parser.ParseFile(fset, src, nil, 0)
	if err != nil {
		fatal(err)
	}
	var names []string
	ast.Inspect(f, func(n ast.Node) bool {
		id, ok := n.(*ast.Ident)
		if ok && id.Obj != nil && id.Obj.Kind == ast.Con {
			names = append(names, id.Name)
		}
		return true
	})
	var b strings.Builder
	b.WriteString("// Code generated; DO NOT EDIT.\n\npackage status\n\n")
	b.WriteString("func Names() []string { return []string{\n")
	for _, n := range names {
		b.WriteString("\t\"" + n + "\",\n")
	}
	b.WriteString("}}\n")
	out, err := format.Source([]byte(b.String()))
	if err != nil {
		fatal(err)
	}
	if err := os.WriteFile("names_gen.go", out, 0o644); err != nil {
		fatal(err)
	}
}

func fatal(err error) {
	fmt.Fprintln(os.Stderr, err)
	os.Exit(1)
}
```

#### What happens here

The build tag `ignore` makes this `main` a generator program, separate from package `status`. It parses `status.go`, and `ast.Inspect` keeps identifiers whose object kind is `ast.Con`. Those names are written into `names_gen.go` as the body of `Names`, and `format.Source` has to succeed before `WriteFile` runs. `fatal` prints the error on stderr and exits with status 1.

**Note:** `id.Obj` depends on parser object resolution; for a robust tool prefer walking `GenDecl`/`ValueSpec` as in example 2.

### Example 5: Directive

```go
package status

//go:generate go run ./gen_names.go

type Status int

const (
	Idle Status = iota
	Busy
)
```

#### What happens here

Package `status` declares the int type `Status` with the constants `Idle` and `Busy`. The line `//go:generate go run ./gen_names.go` is the directive `go generate` executes. This file is the input the generator parses. The generated name list is written by that other program.

### Example 6: Predict, then check — deliberately broken emit

Put into the buffer: `package status\nfunc (` without the rest.

**Predict:** Does the file get created?

**Check:** Not if you check `format.Source` before `WriteFile`. If you write first and then format — garbage can appear; that is why format *before* write.

### Example 7: Fixture test extract + render

```go
func TestRenderEmpty(t *testing.T) {
	out, err := render("p", nil)
	if err != nil {
		t.Fatal(err)
	}
	if !bytes.Contains(out, []byte("[]string{")) {
		t.Fatalf("%s", out)
	}
}
```

#### What happens here

`TestRenderEmpty` calls `render` with the package name `p` and a nil name list. An error from `render` fails the test through `t.Fatal`. The output has to contain the bytes `[]string{`. An empty model is expected to stay valid Go, with an empty slice literal inside the package.

**Trace:** an empty model still passes `format.Source` and yields a valid package.

### Example 8: Two generators in the same package

```go
//go:generate go run golang.org/x/tools/cmd/stringer@v0.22.0 -type=Status
//go:generate go run ./gen_names.go
```

#### What happens here

The first directive runs `stringer` at `v0.22.0` with `-type=Status`. The second runs the local program `./gen_names.go`. `go generate` executes the two lines in that order. Each line names its own tool, and the output path is chosen inside the tool.

**Predict:** Do they fight over the same output file?

**Check:** Not if stringer writes `status_string.go` and your tool writes `names_gen.go`. Agree on output names in advance.

### Example 9: Predict, then check — `Obj` nil

In the `Inspect` skeleton from example 4, `id.Obj` can be `nil` depending on how you parse.

**Predict:** Does `id.Obj.Kind == ast.Con` without a nil check panic?

**Check:** Yes if `Obj` is nil. That is why production code prefers `GenDecl` + `ValueSpec` instead of relying on `Obj`.

### Example 10: Snapshot test of render

```go
func TestRenderSnapshot(t *testing.T) {
	got, err := render("status", []string{"Idle", "Busy"})
	if err != nil {
		t.Fatal(err)
	}
	want, err := os.ReadFile("testdata/names_gen.golden")
	if err != nil {
		t.Fatal(err)
	}
	if !bytes.Equal(got, want) {
		t.Fatalf("drift:\n%s", got)
	}
}
```

#### What happens here

`TestRenderSnapshot` renders package `status` for the names `Idle` and `Busy`. It reads `testdata/names_gen.golden` and compares the two byte slices with `bytes.Equal`. A difference fails the test and prints the new output under the label drift. Changing the golden file is a separate edit, done when the generated shape is supposed to change.

**Trace:** regenerate golden deliberately (`-update` flag in the test) when you change the shape; otherwise CI catches random drift.

## Decision analysis

**AST vs text** — AST for reading Go. Text/template for emit is OK with `go/format`.

**go/types** — when you need a full type model; for enum lists AST often suffices.

**Ready-made stringer** — if you only need `String()`, do not write your own.

**`cmd/` package vs ignore main** — `cmd/` is cleaner for a team; ignore is faster for 80 lines.

## Trade-offs

| Approach | Advantage | Cost |
|----------|-----------|------|
| Regex | quickly cobbled together | breaks on comments/format |
| AST | correct | steep learning curve |
| go/types | exact types | harder setup |
| Template only | nice emit | you still need an input model |
| Fprintf emit | simple | unreadable when it grows |

## Common mistakes

1. Emit without `format.Source`.
2. Generator without `ignore` (or outside `cmd/`) — breaks the package.
3. Relative path wrong when called from the wrong cwd (rare with `go generate`, often with manual `go run`).
4. Parsing without `ParseComments` when annotations are needed.
5. Oversized generator in the same PR without a test fixture.
6. Non-deterministic order from `map`.
7. Mixing extract and I/O in one function — untestable.
8. Inserting an unchecked string as a Go identifier.

## Idiomatic Go

- `//go:build ignore` for one-shot `main`, or `internal/cmd/...`.
- Read `GOFILE` (02.04) instead of hardcoding names when you can.
- Deterministic output (`sort`).
- Test: input `.go` string fixture → expected model / snapshot.
- Keep the generator short until you need more; split files as it grows.
- stderr + non-zero exit on error.

## Practical scenario

The product has `Permission` constants and needs a `code → description` map for the admin UI. Stringer only gives names. The team writes an ~80-line generator that reads line comments (`ParseComments`) and emits:

```go
var permissionHelp = map[Permission]string{ ... }
```

Directive next to the type; CI checks the diff. The earlier regex version crashed when someone inserted a comment inside a const block. The AST version survived a formatting refactor.

## Summary

A small in-source generator: parse AST, extract model, emit Go, format, write. That is the foundation when off-the-shelf tools fall short, and the bridge to `text/template` in later lessons. Discipline (ignore, DO NOT EDIT, tests, determinism) is worth as much as the parser itself.
