# 02.01 Introduction to Code Generation in Go

> **Go Path - Zero to Gopher** / **03 Others → Code Generation in Go** / Lesson 02.01

## Lesson goals

After this lesson you will be able to:

- explain why the Go ecosystem often generates code instead of relying on reflection at runtime;
- recognize the `//go:generate` directive and run `go generate` on a package;
- distinguish `go generate` from `go build` / `go test` / `go run`;
- set up a small, repeatable generate step with `DO NOT EDIT` output;
- predict what happens when a directive has a prefix mistake and verify with a trace.

## Prerequisite

- Comfortable work with modules (`go.mod`) and packages.
- Go 1.22+.
- Basic terminal (PowerShell or bash).
- Familiarity with `go build` and `go test` at the level of “run a package”.

## Problem this lesson solves

Repeated boilerplate — `String()` for enum constants, mock implementations for an `interface`, protobuf stubs, maps from a schema — buries hand-written code in mistakes. Runtime reflection costs performance and loses the type checking the compiler otherwise provides. Generation yields **type-strict** Go that compiles, with a single source of truth (IDL, comment, YAML, Go type).

Without agreement around `go generate`, teams forget to regenerate files. CI then fails mysteriously: tests expect `"Idle"`, but logs show `Status(0)`. This lesson builds a mental model: what generate is, what it is not, and how to fit it into daily workflow.

## Mental model

```text
  source of truth           generator                 output
  (proto / .go / yml)  ->  (tool or script)     ->  *.gen.go / *_string.go
                              ^
                              |
                    //go:generate line in a .go file
                    go generate ./...   (explicit command)
```

Key fact: `go generate` does **not** run by itself during `go build`. That is intentional. Generation is a separate step for the package author, not a hidden part of compilation.

### Glossary

| Term (English) | What it means here | What it is not |
|----------------|--------------------|----------------|
| `//go:generate` | special comment-directive | an ordinary comment for humans |
| `go generate` | command that scans and runs directives | part of `go build` |
| generator | process that writes Go (or other) output | runtime reflection |
| source of truth | type, `.proto`, schema you edit by hand | generated file |
| `DO NOT EDIT` | signal to people and tools | magic that blocks the editor |
| `go/build` tag `ignore` | exclude generator from normal build | a replacement for `.gitignore` |

## Mechanism

This section is the core of the lesson. Follow the flow from directive to execution, step by step.

### 1. Directive in source

In a `.go` file, at the start of the line (no space between `//` and `go`):

```go
package animals

//go:generate stringer -type=Animal

type Animal int

const (
	Dog Animal = iota
	Cat
)
```

`go generate` does **not** parse the Go AST to find the directive. The scanner looks at lines of text. So a line that *looks* like `//go:generate` inside a string literal or block comment can also be treated as a directive — watch what you write.

### 2. Running it

```text
go generate ./...
go generate ./internal/animals
go generate animals.go
```

The command:

1. determines packages (or listed `.go` files);
2. in a package, processes files by name;
3. in a file, runs directives top to bottom;
4. for each directive, sets env (`GOFILE`, `GOPACKAGE`, … — details in 02.04) and runs the command in the **package directory**.

If one generator returns an error (non-zero exit), `go generate` **skips** further processing of that package.

### 3. Trace: what happens line by line

Imagine a package:

```go
// file: status.go
package status

//go:generate echo step-A
//go:generate echo step-B

type Status int
```

**Execution trace** (`go generate .` in that dir):

```text
1. Open status.go, scan lines
2. Find //go:generate echo step-A  → cwd=package dir → run "echo step-A"
3. Find //go:generate echo step-B  → same cwd → run "echo step-B"
4. End of file / package
```

`go build` in the same directory does **not** print `step-A` or `step-B`. Directives are invisible to the compiler.

### 4. Predict, then check: space in the prefix

Given a file:

```go
package demo

// go:generate echo SHOULD-NOT-RUN

func main() {}
```

**Predict:** what will `go generate .` do?

**Check:** nothing (or silence only). A space after `//` means the line is **not** a directive. The prefix must be exactly `//go:generate`.

Fix:

```go
//go:generate echo SHOULD-RUN
```

### 5. Why generate, not just a script?

You can have a `Makefile` or `scripts/gen.ps1` without `go generate`. Advantages of the standard hook:

- the directive lives **next to** the type / source you change;
- `go generate ./...` is the agreed name in the Go ecosystem;
- tools and CI know where to look;
- env context (`GOFILE`, …) comes for free.

Scripts still have a place — often the directive is short and calls a script.

### 6. Typical reasons for codegen

| Need | Example generator | Why not by hand |
|------|-------------------|-----------------|
| `String()` for constants | `stringer` | easy to forget after changing iota |
| protobuf → Go types | `protoc` + `protoc-gen-go` | huge boilerplate |
| mock for `interface` | mockery / mockgen | long and tedious |
| maps / tables from DSL | custom tool (02.03) | domain rules |
| parser from grammar | `goyacc` and similar | errors in hand-written parser |

### 7. Generation vs build vs test

```text
go generate  →  writes/refreshes source files
go build     →  compiles what already exists
go test      →  builds and runs tests (no automatic generate)
go run       →  compiles and runs the program (no generate)
```

So a valid flow is:

```text
1. change the source of truth
2. go generate ./...
3. go test ./...
4. commit source + generated (if the team agrees)
```

### 8. `//go:build ignore` for a local generator

Often the generator lives as `main` in the same directory. So `go build` does not treat it as part of the package:

```go
//go:build ignore

package main

import (
	"os"
	"time"
)

func main() {
	content := "// Code generated by gen_version.go; DO NOT EDIT.\n\n" +
		"package version\n\nvar Version = \"" +
		time.Now().UTC().Format(time.RFC3339) + "\"\n"
	_ = os.WriteFile("version_gen.go", []byte(content), 0o644)
}
```

Directive in the package:

```go
package version

//go:generate go run ./gen_version.go

var Version = "dev"
```

**Trace:**

```text
go generate .
  → cwd = package version dir
  → go run ./gen_version.go
  → writes version_gen.go
go build .
  → compiles package version (without gen_version.go because of ignore)
  → Version comes from version_gen.go if it exists
```

Note: `Version = "dev"` in the hand-written file and generated `Version` can collide — in practice use only generated, or split names. The example illustrates the ignore + generate mechanism, not a perfect production layout.

### 9. Generated file header

Official convention (regexp that tools recognize):

```text
^// Code generated .* DO NOT EDIT\.$
```

Example:

```go
// Code generated by stringer -type=Status; DO NOT EDIT.

package status
```

The line must appear before the first non-comment, non-blank text. That lets linters and reviewers know: **do not edit by hand**.

### 10. Predict, then check: does build run generate?

**Predict:** You run only `go build ./...`. Does `//go:generate echo hi` run?

**Check:** No. No `hi` in the output. Only `go generate` runs the directive.

### 11. Order and dependencies

Within a file: top to bottom. Within a package: files by name. Packages: order from the command line.

If directive B needs the output of directive A:

- put A above B in the same file, or
- merge into one script / one directive, or
- document explicit order in CI.

Do not rely on “magic” across packages.

### 12. Build tag `generate`

`go generate` sets the build tag `generate`, so a file can be visible to generate and ignored in a normal build (alongside the `ignore` pattern). Keep tag details with `go help buildconstraint` — here remember: there is an intentional split between generate and build.

### 13. Trace: CI discipline

```text
developer changes Status constants
  → forgets go generate
  → push
CI:
  go generate ./...
  git diff --exit-code
  → diff in *_string.go → job FAIL
```

That is not punishment — it signals that source and output are out of sync.

### 14. When *not* to generate

- One-off ten-line script with no schema.
- Code that changes every hour by hand with no stable source of truth.
- Places where generics (Go 1.22+) already remove container boilerplate.

Generate is a tool, not the identity of the project.

### 15. Predict, then check: multiple directives, one failure

```go
//go:generate echo first
//go:generate false
//go:generate echo third
```

On Unix-like systems `false` returns non-zero.

**Predict:** Will `third` run?

**Check:** Not in the same package after the failure — `go generate` stops further processing of that package. Keep directives independent or catch errors in a wrapper.

(On Windows the equivalent “fail” command depends on the shell; the point is exit status ≠ 0.)

### 16. What `go generate` is not

| It is not | Why people confuse it | Use instead |
|-----------|----------------------|-------------|
| template engine | generate “makes code” | `text/template` in the generator (02.05+) |
| dependency manager | tools are pinned | `go.mod` / `go run @ver` |
| file watcher | “when I save, regenerate” | editor task / CI / manual |
| replacement for `go mod` | modules ≠ generate | modules for dependencies |
| part of `go test` | tests “should know” | explicit generate step |

Remember: `go generate` is a **command orchestrator**, not a generator by itself.

### 17. Trace: from constant change to log line

```text
1. Developer changes:
     const (
       Idle Status = iota
       Busy
       Done   // NEW
     )
2. Forgets go generate
3. Old status_string.go still:
     case Busy: return "Busy"
     default: return "Status(" + strconv.Itoa(int(i)) + ")"
4. Code sends Done (value 2)
5. Log: Status(2)   ← symptom
6. go generate
7. New String() knows Done
8. Log: Done        ← fix
```

The whole incident is missing discipline, not language magic.

### 18. Predict, then check: directive in a string

```go
package trap

var hint = `
//go:generate echo FROM-STRING
`

//go:generate echo FROM-REAL
```

**Predict:** How many times will echo run?

**Check:** `go generate` does not parse Go. A line that *starts* with `//go:generate` after possible leading whitespace depends on scanner behavior — in practice **avoid** having the exact prefix at the start of a line inside raw strings and comments. If the `FROM-STRING` line in the file starts with that directive exactly, the scanner may pick it up. Keep generate lines out of literals.

Safe pattern: never put a literal `//go:generate` at the start of a line inside a string; break the line or space differently if you must document the syntax.

### 19. Team workflow — one entry point

Agree on one command:

```text
go generate ./...
```

If that is too slow on a monorepo:

```text
go generate -run stringer ./...
go generate -run proto ./services/...
```

(`-run` in detail in 02.04.) Every target must be in the root or package README.

### 20. What to put in the PR description after a source change

1. What is the source of truth (type / proto / YAML).
2. Which `//go:generate` line touches the file.
3. Whether you ran generate locally.
4. Whether CI runs a diff check.

Then the reviewer does not guess why `*_string.go` is in the diff.

### 21. Anti-pattern: pre-commit without a pin

A pre-commit hook that calls “whatever `stringer` is on PATH” creates non-deterministic diffs between developers. Pin:

```text
go run golang.org/x/tools/cmd/stringer@v0.22.0 ...
```

or `go install` from `tools.go` whose versions live in `go.mod`.

### 22. Predict, then check: `go generate` on the wrong package

Layout:

```text
/repo
  /internal/a/a.go    //go:generate echo A
  /internal/b/b.go    //go:generate echo B
```

You run from `/repo`:

```text
go generate ./internal/a
```

**Predict:** Do you see `B`?

**Check:** No. Only package `a`. `./...` would take both (and deeper).

### 23. Responsibility table

| Role | Responsibility |
|------|----------------|
| Author of change | run generate, commit source + output (if agreed) |
| Reviewer | verify source and output match; look for DO NOT EDIT |
| CI | regenerate + diff exit code |
| Tech lead | pin tool versions, document targets |

### 24. Trace: `-command` alias in one file

```go
package job

//go:generate -command str go run golang.org/x/tools/cmd/stringer@v0.22.0
//go:generate str -type=Phase
//go:generate str -type=Result
```

**Trace**

```text
1. See -command str ...  → remember alias "str" for the rest of THIS file
2. str -type=Phase        → expands to go run ...stringer@v0.22.0 -type=Phase
3. str -type=Result       → same with -type=Result
4. Another file in the package does NOT inherit alias "str"
```

The alias is local to the file — not a global Makefile.

### 25. zero value and generate — mental link

Generated code often must behave correctly when input is empty (no constants, empty name slice). When designing a generator ask: what do I emit if the list is empty? Valid Go or panic?

Answer always: valid Go (e.g. empty `[]string{}`), because CI and tests run generate on stub data too. In Go that matches **zero value** behavior — the generator must not assume “there is always at least one element”.

### 26. Predict, then check: commit source only

The team commits generated files. Developer changes the type, runs generate locally, but `git add` only `status.go`.

**Predict:** What does CI see?

**Check:** After `go generate` + diff, CI sees a change in `status_string.go` that is not in the commit → fail. That is desired behavior.

### 27. Minimal checklist before merge

1. Source of truth clear?
2. Command pinned / reproducible?
3. Output has `DO NOT EDIT`?
4. README or comment documents the step?
5. `go test ./...` passes after generate?
6. No hand patches in the generated file?

## Rules and syntax

| Rule | Detail |
|------|--------|
| Prefix | exactly `//go:generate` at line start (no space in `//go`) |
| Command | rest of line — tokens or Go double-quoted strings |
| Working dir | package directory (file with the directive) |
| Multiple lines | multiple `//go:generate` in the same file, in order |
| Alias | `//go:generate -command name args...` (for the rest of that file) |
| Commit | generated often in git; team agreement + CI |
| Header | `// Code generated ... DO NOT EDIT.` |

Pinned command example:

```go
//go:generate go run golang.org/x/tools/cmd/stringer@v0.22.0 -type=Status -output=status_string.go
```

Alias example:

```go
//go:generate -command stringer go run golang.org/x/tools/cmd/stringer@v0.22.0
//go:generate stringer -type=Status
//go:generate stringer -type=Phase
```

## Examples

### Example 1: Minimal proof the directive works

```go
package main

import "fmt"

//go:generate echo generate-ok

func main() {
	fmt.Println("hello")
}
```

#### What happens here

`main` prints `hello` when this program runs. The `//go:generate echo generate-ok` line is a directive that `go generate` executes, and that command prints `generate-ok`. `go run` and `go build` compile this file and leave the directive unexecuted.

**Predict, then check**

| Step | Predict | Check |
|------|---------|-------|
| `go run .` | prints `hello`, not `generate-ok` | correct |
| `go generate .` | prints `generate-ok` | correct |
| `go build` | no echo | correct |

### Example 2: Local generator with ignore

```go
// gen_answer.go
//go:build ignore

package main

import (
	"os"
)

func main() {
	out := "// Code generated by gen_answer.go; DO NOT EDIT.\n\n" +
		"package puzzle\n\nconst Answer = 42\n"
	if err := os.WriteFile("answer_gen.go", []byte(out), 0o644); err != nil {
		panic(err)
	}
}
```

#### What happens here

This file is a small generator in package `main`. The build constraint `//go:build ignore` keeps it out of a normal build of package `puzzle`. `main` writes `answer_gen.go` with a generated-file header, `package puzzle`, and `const Answer = 42`. A write error ends in `panic`.

```go
// puzzle.go
package puzzle

//go:generate go run ./gen_answer.go
```

#### What happens here

`puzzle.go` is package `puzzle` and holds the generate directive. `go generate` reads `//go:generate go run ./gen_answer.go` and runs that ignored generator. This file does not declare `Answer`. The constant shows up in the file the generator writes.

**Trace**

```text
go generate .
  cwd = .../puzzle
  go run ./gen_answer.go
  WriteFile answer_gen.go
go test .
  compiles package puzzle including Answer
```

#### What happens here

The trace is the command order for the two files above. `go generate .` uses the puzzle directory as its working directory and runs `go run ./gen_answer.go`. That program writes `answer_gen.go`. `go test .` then compiles package `puzzle` with the generated `Answer` included.

### Example 3: Documentation next to the type

```go
package colors

// Color represents a named color in the UI system.
//
// After changing constants run:
//
//	go generate ./...
//
//go:generate go run golang.org/x/tools/cmd/stringer@v0.22.0 -type=Color
type Color int

const (
	Red Color = iota
	Green
	Blue
)
```

#### What happens here

The comment tells a reader to run `go generate ./...` after the constants change. The directive under the comment is the instruction the tool runs: `stringer` at `v0.22.0` for type `Color`. `Red`, `Green`, and `Blue` are the iota values that tool reads. The comment and the directive stay next to the type they describe.

You tell people *when*. You tell the generator *how*. README + directive = less “code is out of date”.

### Example 4: Multiple independent generators

```go
package api

//go:generate go run ./internal/cmd/genroutes
//go:generate go run golang.org/x/tools/cmd/stringer@v0.22.0 -type=Code
```

#### What happens here

Two `//go:generate` lines name two tools in package `api`. `go generate` runs them in the order written: `./internal/cmd/genroutes`, then `stringer` at `v0.22.0` for type `Code`. That sequence is the line order in this file. The tool names are left unsorted.

**Predict:** Does order depend on tool names alphabetically?

**Check:** No — it depends on line order in the file (and file order in the package). If `genroutes` does not depend on stringer, order does not matter. If it does, arrange explicitly or merge.

### Example 5: Array check in stringer style (reading output)

Typical fragment of generated code (illustrative):

```go
// Code generated by stringer -type=Status; DO NOT EDIT.

package status

import "strconv"

func _() {
	var x [1]struct{}
	_ = x[Idle-0]
	_ = x[Running-1]
}

func (i Status) String() string {
	switch i {
	case Idle:
		return "Idle"
	case Running:
		return "Running"
	default:
		return "Status(" + strconv.Itoa(int(i)) + ")"
	}
}
```

#### What happens here

This is a sample of `stringer` output for type `Status`, opened by the standard generated-file header. The function `_` indexes a one-element array with `Idle-0` and `Running-1`, so those constants have to stay 0 and 1 for the file to compile. `String` returns the names `Idle` and `Running`, and any other value is formatted as `Status` plus the integer. The header marks the file as generated output.

**Trace when you change iota without regenerate**

```text
Idle = 0, Running = 1   → OK
change: Idle = 0, Running = 2 (insert new constant in the middle)
old generated still has _ = x[Running-1]
compiler: invalid array index  → FAIL
```

#### What happens here

The trace starts from `Idle = 0` and `Running = 1`, which match the generated indexes. Inserting a constant so that `Running` becomes 2 leaves the old check `_ = x[Running-1]` in place. That index is then outside the one-element array, and the compiler rejects the package. The failure is the signal to run generate again.

That is an intentional signal: regenerate.

### Example 6: Directory layout

```text
/internal/status/
  status.go           // type + //go:generate
  status_string.go    // generated
  gen_names.go        // optional: //go:build ignore local tool
```

#### What happens here

The tree is one directory with three roles. `status.go` holds the type and the `//go:generate` directive. `status_string.go` is the generated file. `gen_names.go` is an optional local tool kept out of the normal build. Generated text stays beside its source, in its own file.

Keep generated next to the source of truth. Do not mix hand-written and generated code in the *same* file.

### Example 7: Predict, then check — build tag ignore

Files:

```go
// gen.go
//go:build ignore

package main

func main() {}
```

#### What happens here

`gen.go` is package `main` with an empty `main`. `//go:build ignore` removes it from the file list used by `go list` and `go build`. `go run ./gen.go` still executes it, because the command names the file. A generate directive uses that same explicit `go run`.

```go
// lib.go
package lib

func Hello() string { return "hi" }
```

#### What happens here

`lib.go` is an ordinary file in package `lib`. `Hello` returns `hi`. The file has no ignore constraint and no generate directive. A normal package list includes it.

**Predict:** `go list -f '{{.GoFiles}}' .` — does it include `gen.go`?

**Check:** No (for normal list/build). `go run ./gen.go` still works because you explicitly run that file. That is why `//go:generate go run ./gen.go` makes sense.

### Example 8: Trace — pinning version changes the diff

```text
Day 1:  //go:generate go run .../stringer@v0.21.0 -type=S
Day 2:  someone bumps to @v0.22.0 without agreement
go generate ./...
git diff
  → maybe small changes in format / comment in generated file
  → PR noise “infra” instead of feature
```

#### What happens here

The trace pins `stringer` at `v0.21.0` on day 1 and shows a bump to `v0.22.0` on day 2. `go generate ./...` then rewrites the generated file with the new tool version. `git diff` can contain only a comment or a formatting change. That diff is noise on a feature pull request, which is why the version pin is a team contract.

**Conclusion:** pinning is part of the team contract, not personal taste.

### Example 9: Predict, then check — `go generate` on one file

```text
go generate status.go
```

#### What happens here

`go generate status.go` names one file. A list of `.go` files from one directory is treated as one package, and that package is built from the files named on the command line, so this run reads directives in `status.go`. Each of those directives runs, in order. Narrowing them to a single directive is what `-run` does, in lesson 02.04.

**Predict:** Does it process only directives in `status.go` or the whole package?

**Check:** Listing `.go` files from the same path is treated as one package; `go help generate` says a list of `.go` files from one directory goes as a package. For precise focus on *one directive* use `-run` (02.04), not just the file name, if you have multiple directives in multiple files.

### Example 10: Hand-written String() vs generate — comparison

By hand:

```go
func (s Status) String() string {
	switch s {
	case Idle:
		return "Idle"
	case Busy:
		return "Busy"
	default:
		return "unknown"
	}
}
```

#### What happens here

This hand-written `String` returns `Idle` or `Busy` for those two cases. The default branch returns `unknown` for every other value. A new constant with no added case still compiles, and callers receive `unknown`.

Generate (`stringer`) additionally often inserts a compile-time check of constant offsets. Hand-written default `"unknown"` hides drift; stringer default `Status(N)` exposes it in logs.

**Predict:** You add `Offline` to the const block, forget the switch. What does hand-written `String()` return?

**Check:** `"unknown"` (or whatever the default says) — silently. With stale stringer output: either it does not compile (array trick) or `Status(N)` in the log. Both beat silent `"unknown"` in production if you need accuracy.

## Decision analysis

**Commit generated code?**
Most Go projects: yes. Simpler CI, fewer tools on the reviewer machine, `go test` works right after clone. Some monorepos: no — then CI *must* generate + diff check, and developer machines need pinned tools.

**Generate in `go build`?**
Not built in. If you want one command, wrap a `Makefile` / task that calls generate then build. Do not expect magic from the toolchain alone.

**Reflection instead of generate?**
OK for rare plugins and dynamic boundaries. For hot paths, public APIs, and log messages — generate or generics give better types and a clearer stack.

**Script vs bare directive?**
Short, pinned `go run tool@version ...` can go in the directive. Long flag chains — script; directive stays one line.

## Trade-offs

| Approach | Advantage | Cost |
|----------|-----------|------|
| `go generate` | standard, next to source | easy to forget to run |
| Makefile only | full control | people look for a directive, do not find one |
| Reflection | no extra step | slower, weaker types |
| Generics | no generator for containers | does not cover IDL / stringer |
| Hand boilerplate | zero tools | errors, tedium, drift |

## Common mistakes

1. Space: `// go:generate` — **does not work**; silent like an ordinary comment.
2. Expecting `go test` or `go build` to generate automatically.
3. Generator without `DO NOT EDIT` header — reviewer cannot tell what is hand-written.
4. Relative path assumes wrong cwd — generate runs from the package dir, not repo root.
5. Generated file in `.gitignore` without CI check — silent drift.
6. Hand-editing a generated file “just this once”.
7. Unpinned `latest` tool version — different diffs per machine.
8. Dependent directives without clear order or one script.

## Idiomatic Go

- Header: `// Code generated ...; DO NOT EDIT.`
- Directive next to the type / source being generated.
- Prefer `go run tool@version` for reproducibility.
- Keep the generator simple; put complex orchestration in a script.
- In CI: `go generate ./...` + `git diff --exit-code` (or equivalent).
- Do not commit “temporary” hand patches to generated files.
- One source of truth; generated is derived.

## Practical scenario

A microservice has 12 enum types for order, payment, and delivery status. A developer adds `StatusRefunded`, forgets stringer. In production logs show `Status(3)` instead of a name. On-call spends an hour on “where is magic number 3?”.

The team introduces:

1. `//go:generate go run .../stringer@v... -type=...` on each type;
2. README: “after changing constants → `go generate ./...`”;
3. CI step regenerate + diff.

Incidents disappear. Onboarding gets one command. Reviewer in PR looks at source + generated together.

## Exercises

1. Add `//go:generate echo ok` and run `go generate`. Then break it to `// go:generate` and observe silence.
2. Build a `//go:build ignore` generator that writes `answer_gen.go` with `const Answer = 42`. Verify `go build` of the package does not compile the generator as part of the package.
3. Document in README when generate must run (3–5 sentences).
4. Deliberately break a generated file and write a CI check (`go generate` + diff) that catches it.
5. Sketch a table for your mini-project: source of truth → command → output file.

## Check questions

1. Does `go build` run `go generate`?
2. What exact directive prefix must you use?
3. Why `//go:build ignore` on a generator file?
4. When do you choose generate over reflection?
5. Why does CI often diff after generate?
6. What happens to remaining directives in a package if one returns an error?
7. What is the working directory when a directive command runs?

## Summary

`go generate` is the standard hook for running generators described by `//go:generate` directives. It is separate from build and test, suited for stringer / proto / mock / custom flows, and requires team discipline: pin tools, `DO NOT EDIT`, commit or CI check. The directive lives next to the source of truth; do not hand-edit the generated file.
