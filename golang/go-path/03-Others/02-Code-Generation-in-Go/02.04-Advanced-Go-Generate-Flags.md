# 02.04 Advanced go generate flags

> **Go Path - Zero to Gopher** / **03 Others → Code Generation in Go** / Lesson 02.04

## Lesson goals

After this lesson you can:

- use `go generate -x`, `-n`, `-v`, `-run`, `-skip` for debug and filtering;
- read env variables `GOFILE`, `GOLINE`, `GOPACKAGE` (and related) in a generator;
- write directives that are reproducible and easier to maintain;
- diagnose why a directive does not run — predict, then check with a trace.

## Prerequisite

- 02.01–02.03.
- Go 1.22+.
- Experience with at least one `//go:generate` directive locally.

## Problem this lesson solves

`go generate ./...` “does something” then fails — with no trace of which command. Or you run 30 directives when you need one. Or the generator hardcodes `status.go` and breaks when you rename the file. Flags and env vars solve **visibility**, **selection**, and **context transfer**. This lesson uses only real flags from `go help generate`.

## Mental model

```text
go generate [flags] [packages | files]
    for each package:
      for each .go file (by name):
        for each //go:generate directive (top to bottom):
          if -run / -skip filter says no → skip
          set env (GOFILE, GOLINE, GOPACKAGE, ...)
          expand $NAME on the command line
          if -n → print only
          else run (and print if -x)
```

You write the generator as a CLI that *can* read those env vars — and fail-fast if they are missing.

### Glossary table

| Term | Meaning |
|------|---------|
| `-n` | dry-run: prints commands, does not execute |
| `-x` | prints commands while executing them |
| `-v` | package/file names as they are processed |
| `-run regexp` | only directives whose full text matches |
| `-skip regexp` | omit directives that match |
| `GOFILE` | base name of the file with the directive |
| `GOLINE` | directive line number |
| `GOPACKAGE` | package name |
| `DOLLAR` | literal `$` |
| `-command` | command alias within the file |

## Mechanism

### 1. Flags — only the real ones

From `go help generate` / `cmd/go` source:

| Flag | Meaning |
|------|---------|
| `-run=""` | regexp — select directives whose **full original text** (without trailing spaces/newline) matches |
| `-skip=""` | regexp — suppress directives that match; if both `-run` and `-skip` hit, the directive is **skipped** |
| `-n` | prints commands that would be executed |
| `-x` | prints commands as they are executed |
| `-v` | prints package and file names as they are processed |

It also accepts standard build flags (see `go help build`) — but for the generate flow you most often use the ones above.

### 2. Env that `go generate` sets

| Variable | Content |
|----------|---------|
| `GOFILE` | file base name (not an absolute path) |
| `GOLINE` | directive line |
| `GOPACKAGE` | package name |
| `GOARCH` | architecture |
| `GOOS` | OS |
| `GOROOT` | root of the Go toolchain that ran generate |
| `DOLLAR` | `$` |
| `PATH` | parent PATH with `$GOROOT/bin` at the front |

The generator reads them via `os.Getenv`. On the directive line itself `$GOFILE` is expanded before launch.

### 3. Trace: `-n` vs `-x`

Package with:

```go
//go:generate echo hello-generate
```

```text
go generate -n .
```

**Trace**

```text
prints the command (echo ...)
does NOT run echo
no side-effect files
```

```text
go generate -x .
```

**Trace**

```text
prints the command
AND runs it
you see hello-generate
```

### 4. Predict, then check: does `-n` “make generate work”

Someone says: “I ran `go generate -n ./...` and I still do not have a new `*_string.go`.”

**Predict:** Why?

**Check:** `-n` **never** executes. That is a feature. For real generate drop `-n` (keep `-x` if you want a log).

### 5. `-run` filters by directive text

```go
package job

//go:generate go run golang.org/x/tools/cmd/stringer@v0.22.0 -type=Phase
//go:generate go run ./gen_docs.go
```

```text
go generate -run stringer ./internal/job
```

**Trace**

```text
directive 1 text contains "stringer" → match → execute
directive 2 has no "stringer" → skip
```

The regexp is over the **full** directive line text (including `//go:generate ...`), not only the program name.

### 6. Predict, then check: `-run` too narrow

```text
go generate -run Stringer ./...
```

The directive has `stringer` in lowercase.

**Predict:** Does it match?

**Check:** Depends on the regexp — the default Go regexp is case-sensitive. `Stringer` ≠ `stringer`. Use `-run stringer` or `(?i)stringer` if you deliberately want case-insensitive.

### 7. `-skip`

```text
go generate -skip gen_docs ./...
```

Skips directives whose text matches `gen_docs`, even if `-run` would otherwise hit. If both hit — skip wins.

### 8. Trace: env in the generator

```go
//go:build ignore

package main

import (
	"fmt"
	"os"
)

func main() {
	fmt.Println("file:", os.Getenv("GOFILE"))
	fmt.Println("line:", os.Getenv("GOLINE"))
	fmt.Println("package:", os.Getenv("GOPACKAGE"))
}
```

```go
package demo

//go:generate go run ./printenv.go
```

You run `go generate -x .`:

```text
file: demo.go          // example name
line: 3              // where the directive sits
package: demo
```

### 9. Predict, then check: is `GOFILE` absolute?

**Predict:** Is `GOFILE` `/home/me/proj/demo.go`?

**Check:** No — **base name** (`demo.go`). The working directory is the package dir; that is why `parser.ParseFile(fset, os.Getenv("GOFILE"), nil, 0)` works.

### 10. GOFILE in an AST generator

```go
src := os.Getenv("GOFILE")
if src == "" {
	fmt.Fprintln(os.Stderr, "GOFILE is not set; run via go generate")
	os.Exit(1)
}
f, err := parser.ParseFile(fset, src, nil, parser.ParseComments)
```

**Trace**

```text
same gen.go script
directive in a.go → GOFILE=a.go
directive in b.go → GOFILE=b.go
one tool, multiple inputs
```

### 11. Predict, then check: manual `go run ./gen.go`

Without `go generate`:

```text
go run ./gen.go
```

**Predict:** What is `GOFILE`?

**Check:** Empty (unless you exported it yourself). That is why fail-fast:

```go
func mustEnv(key string) string {
	v := os.Getenv(key)
	if v == "" {
		fmt.Fprintf(os.Stderr, "%s is not set (run via go generate)\n", key)
		os.Exit(2)
	}
	return v
}
```

### 12. Expansion of `$NAME` in the directive

```go
//go:generate echo package=$GOPACKAGE file=$GOFILE
```

Before launch, `go generate` replaces `$GOPACKAGE` and `$GOFILE` with values. The syntax is `$NAME` on **all** OSes (not `%NAME%` on Windows for this expansion).

If `NAME` is not set, `$NAME` becomes an empty string.

### 13. `DOLLAR` on Windows

```go
//go:generate echo $DOLLAR GOPACKAGE is $GOPACKAGE
```

**Trace:** you should see `$ GOPACKAGE is demo` (with the matching package) — a literal dollar via `DOLLAR`, then the expanded package.

When you need the `$` character in arguments, do not rely on shell quoting; use `$DOLLAR`.

### 14. Predict, then check: quoting

```go
//go:generate go run ./gen.go -title "My Title"
```

**Predict:** Is `"My Title"` one argument?

**Check:** Yes — double-quoted strings in the directive use Go syntax and become one argument to the generator. Still: complex shell escape on Windows vs Unix remains a trap; prefer `go run` without a shell-script middle layer when you can.

### 15. Processing order

```text
packages (order from CLI)
  → files in the package (by name)
    → directives in the file (top to bottom)
```

If B depends on A: put A above, or one script. Do not depend on the alphabetical order of *tool names*.

### 16. Trace: an error stops the package

```go
//go:generate echo one
//go:generate go run ./fail.go
//go:generate echo three
```

`fail.go` does `os.Exit(1)`.

**Trace**

```text
one executes
fail → non-zero
three does NOT execute in that package
go generate moves on to the next package (if any)
```

### 17. `-v` for orientation in a monorepo

```text
go generate -v ./...
```

Prints which package/file is being processed. Useful when “nothing is happening” — you see that it never even enters the expected dir.

### 18. Predict, then check: wrong `-run` + silence

```text
go generate -run protoc ./internal/job
```

In the `job` package there are only stringer directives.

**Predict:** Output?

**Check:** Silence / no commands. Not a bug — the filter. Drop `-run` or fix the regexp. `-v` shows that the files were seen.

### 19. Makefile / task targets

```make
gen:
	go generate ./...

gen-proto:
	go generate -run proto ./...

gen-dry:
	go generate -n ./...

gen-x:
	go generate -x ./...
```

People remember `make gen-proto`; underneath it is still standard `go generate`.

### 20. Trace: diagnosing “nothing is happening”

```text
1. go generate -v ./path   → does it see the package?
2. go generate -x ./path   → are there any commands?
3. Check the //go:generate prefix (no space)
4. Is -run / -skip filtering too much?
5. Are you in the right directory / package path?
6. go generate -n  → what does the expanded command look like?
```

### 21. Predict, then check: what `GOLINE` is for

The generator can report:

```text
gen: status.go:12: unknown type Foo
```

using `GOFILE` + `GOLINE` as context for “which directive called me”, even if it parses other content.

**Predict:** Does `GOLINE` change if you move the directive lower?

**Check:** Yes — it is the directive’s line number in the source, not the type’s line.

### 22. GOOS/GOARCH caution

Env includes `GOOS`/`GOARCH` of the machine running generate.

**Predict:** May generated code depend on the developer’s `GOOS`?

**Check:** Rarely. Prefer the same output on all machines. If you emit conditional code, let it depend on the *model*, not on the accidental OS of a CI agent vs a laptop.

### 23. `PATH` and the same `go`

`go generate` puts `$GOROOT/bin` at the front of `PATH` for the child process. Generators that call `go` get the same toolchain as the parent — fewer “wrong go on PATH” issues.

### 24. Predict, then check: `-command` and `-run`

```go
//go:generate -command str go run golang.org/x/tools/cmd/stringer@v0.22.0
//go:generate str -type=Phase
```

```text
go generate -run stringer .
```

**Predict:** Does the second directive match `stringer`?

**Check:** The text of the second line is `//go:generate str -type=Phase` — **no** substring `stringer`. `-run stringer` will **not** run it. Use `-run str` or `-run Phase` or do not use an alias with such a filter.

### 25. Selective CI job

```text
go generate -run 'protoc|proto' ./...
go generate -run stringer ./...
```

Split time and cache. Document the regexps — part of the team contract.

### 26. Trace: Windows vs Unix in a script

```go
//go:generate ./scripts/gen.sh
```

On Windows without bash → fail.

**Better:**

```go
//go:generate go run ./internal/cmd/gen
```

or separate directives / tasks per OS. Test on the OS that CI uses.

### 27. Predict, then check: build flags with generate

```text
go generate -tags=tools ./...
```

Generate accepts build flags. Tags affect which files the package sees when loading — useful when generate needs to see files with a special tag. Do not confuse with `//go:build ignore` generators you call via `go run` explicitly.

### 28. Mini debug table

| Symptom | Check |
|---------|-------|
| Silent | prefix, path, `-run`/`-skip` |
| Wrong file | `GOFILE`, cwd |
| Too slow | `-run`, split CI |
| Works locally, not in CI | PATH, pin, OS shell |
| Partial generate | error mid-package (exit ≠ 0) |

### 29. Predict, then check: expansion inside a quoted string

Docs say: because of evaluation order, variables expand **even inside** quoted strings.

```go
//go:generate go run ./gen.go -in "$GOFILE"
```

**Predict:** Does the generator see the literal `$GOFILE` or the file name?

**Check:** The file name — expansion already happened. (Tangibility: test on your Go version if you build critical logic around this.)

- Without 02.01 you do not understand why the flags exist.
- Without 02.03 `GOFILE` has no AST context.
- After this lesson: 02.05 templates for nicer emit with the same env context.

### 31. Predict, then check: multiple packages, error in the middle

```text
go generate ./a ./b ./c
```

Package `b` has a directive that fails.

**Predict:** Is `c` processed at all?

**Check:** Yes — the error stops *that* package, not necessarily the whole command for other packages. Still check the exit code of the whole `go generate` in CI (aggregate failure).

### 32. Trace: from file rename to GOFILE

```text
status.go → phase.go  (rename)
directive stays in phase.go
old generator: ParseFile("status.go") → fail
new generator: ParseFile(mustEnv("GOFILE")) → phase.go OK
```

That is why env is not a “nice to have” — it reduces brittleness.

### 33. Documenting the `-run` contract

In the README:

```text
go generate -run stringer ./...   # enum String()
go generate -run proto ./...      # protobuf (directives contain protoc)
go generate -n ./...              # dry-run review
```

If the regexp is not documented, teams invent different `-run` values and CI diverges.

### 34. Predict, then check: `$HOME` in a directive

```go
//go:generate echo $HOME
```

**Predict:** Does it expand?

**Check:** Yes — expansion applies to alphanumeric env names, not only `GO*`. Empty if unset. Do not rely on codegen using `$HOME` for artifact paths — prefer relative paths in the package.

### 35. When *not* to use `-x` always in CI

`-x` increases the log. In a happy-path job a quiet generate + diff is enough. In a failure retry / debug job turn on `-x` (or reproduce locally with `-x`).

### 36. Mental exercise: join 02.03 + 02.04

```text
//go:generate go run ./gen_names.go
gen_names:
  file := mustEnv("GOFILE")
  pkg  := mustEnv("GOPACKAGE")
  parse file, extract, render into pkg
```

That is the production shape of a small in-source generator.

## Rules and syntax

```text
go generate -x ./internal/...
go generate -n ./...
go generate -v -x ./...
go generate -run stringer ./...
go generate -run 'protoc|stringer' ./...
go generate -skip gen_docs ./...
```

In the generator:

```go
file := mustEnv("GOFILE")
pkg := mustEnv("GOPACKAGE")
line := os.Getenv("GOLINE")
```

The directive must still be `//go:generate ...`.

## Examples

### Example 1: `-n` and `-x`

```text
go generate -n ./internal/job
go generate -x ./internal/job
```

#### What happens here

Both commands target the package `./internal/job`. `-n` prints the commands `go generate` would run and stops before executing them, so it leaves files unchanged. `-x` prints each command and then runs it. The dry run is how you read the expanded line before a real generate.

**Predict, then check:** Does `-n` change files? No.

### Example 2: `-run` filters

See mechanism §5. Locally iterate only stringer until you finish the enum.

### Example 3: printenv generator

See mechanism §8. Save the output; compare with the expected file name.

### Example 4: AST + GOFILE

```go
src := mustEnv("GOFILE")
f, err := parser.ParseFile(fset, src, nil, parser.ParseComments)
```

#### What happens here

`mustEnv("GOFILE")` reads the file name `go generate` put in the environment. `parser.ParseFile` parses that file and keeps comments because the mode is `parser.ParseComments`. The same generator can parse a different input whenever the directive sits in a different file. An empty `GOFILE` stops in `mustEnv`, before `ParseFile` is called.

One `gen.go` serves all files with a directive.

### Example 5: `DOLLAR`

```go
//go:generate echo $DOLLAR GOPACKAGE is $GOPACKAGE
```

#### What happens here

The directive runs `echo` with `$DOLLAR` and `$GOPACKAGE`. `go generate` expands `$DOLLAR` to one dollar sign and `$GOPACKAGE` to the package name before it starts `echo`. The printed text therefore contains a literal `$` and the package name. `$DOLLAR` is the expansion that supplies a dollar sign on Windows and on Unix.

### Example 6: fail-fast wrapper

```go
func mustEnv(key string) string {
	v := os.Getenv(key)
	if v == "" {
		fmt.Fprintf(os.Stderr, "%s is not set (run via go generate)\n", key)
		os.Exit(2)
	}
	return v
}
```

#### What happens here

`mustEnv` reads one environment variable by name. An empty value writes a stderr line that names the key and says to run via `go generate`, then exits with status 2. A non-empty value is returned to the caller. Callers use it so a manual `go run` stops at once when the generate variables are absent.

### Example 7: Predict, then check — `-skip` wins

```text
go generate -run go -skip gen_docs .
```

#### What happens here

The command is `go generate -run go -skip gen_docs .` in the current directory. `-run go` keeps directives whose full source text matches the regular expression `go`. `-skip gen_docs` drops directives whose text matches `gen_docs`. A directive that matches both expressions is skipped.

Directive: `//go:generate go run ./gen_docs.go`

**Predict:** Does it execute?

**Check:** No — matches `-run go` and `-skip gen_docs` → skip.

### Example 8: Makefile targets

See mechanism §19.

### Example 9: Mapping env → constant count

The generator opens `GOFILE`, counts `const` declarations, writes `const GenCount = N` to `counts_gen.go`. Run via `go generate -x` and save the log.

### Example 10: Trace CI log with `-x`

```text
##[cmd] go generate -x ./services/order
//go:generate protoc --go_out=...
protoc --go_out=...
protoc-gen-go: program not found
```

#### What happens here

The log is `go generate -x` for `./services/order`. `-x` prints the `//go:generate` line and then the `protoc` command it expanded into. The following line is `protoc-gen-go: program not found`, so the missing plugin is named in the same trace. You can see which command failed.

You immediately see **which** command fails — not “generate failed” without context.

### Example 11: Predict, then check — `-v` without directives

A package with no `//go:generate` lines.

```text
go generate -v ./internal/empty
```

#### What happens here

`go generate -v ./internal/empty` asks for verbose names of packages and files. `-v` prints each package and file as generate walks it. A package whose files contain no `//go:generate` lines has no commands to run, and the command still succeeds. The package was visited, and there was nothing to execute.

**Predict:** Error?

**Check:** No — you see that the package/file is processed, but there are no commands. Silent commands ≠ path error.

### Example 12: GOLINE in an error message

```go
fmt.Fprintf(os.Stderr, "%s:%s: type %q not found\n",
	mustEnv("GOFILE"), mustEnv("GOLINE"), typeName)
os.Exit(1)
```

#### What happens here

The format writes `file:line: type "name" not found` to stderr. `mustEnv("GOFILE")` and `mustEnv("GOLINE")` supply the file name and the directive line that `go generate` recorded. `%q` quotes `typeName`. `os.Exit(1)` ends the generator, and `go generate` then stops further directives in that package.

**Trace:** the developer jumps exactly to the directive that launched the generator, then to the type in the same file.

### Example 13: Selective local flow

```text
# only while iterating on the enum
go generate -run stringer ./internal/job

# dry-run before a large regenerate
go generate -n ./services/...
```

#### What happens here

The first command runs directives whose text matches `stringer`, and only under `./internal/job`. That is the narrow loop while an enum is still changing. The second command is `go generate -n ./services/...`, which prints the expanded commands for that tree and does not execute them. The comment above it calls that second step the dry run.

### Example 14: Predict, then check — expansion of a missing var

```go
//go:generate echo START$NOTSETEND
```

#### What happens here

The directive is `echo START$NOTSETEND`. `go generate` expands `$NOTSET` before `echo` starts. A name that is unset expands to the empty string, so the argument `echo` receives is `STARTEND`. The characters `$NOTSET` are gone from the command that actually runs.

**Predict:** Output?

**Check:** `STARTEND` — `$NOTSET` becomes an empty string. Useful to know when debugging “vanished” parts of a command.

### Example 15: Combined debug steps (checklist)

1. `-v` — am I in the right package?
2. `-n` — what does the expanded command look like?
3. `-x` — what actually runs and where does it fail?
4. `-run` / `-skip` — is the filter cutting too much?
5. Manual `go run ./gen.go` — does `mustEnv` catch the missing context?

## Decision analysis

**-n in PR descriptions** — show what generate does without changing files.

**-run in CI** — separate proto from stringer jobs.

**Required GOFILE** — yes: fail-fast outside generate context.

**Alias `-command`** — shortens repetition; watch the interaction with `-run`.

## Trade-offs

| Technique | Advantage | Cost |
|-----------|-----------|------|
| `-x` always locally | visibility | noise |
| `-n` | safe review | confuses beginners |
| `-run` | speed | needs name/regexp agreement |
| Env context | flexible generator | you must document |
| Script instead of bare command | power | another layer, OS differences |

## Common mistakes

1. Regex `-run` misses because of a wrong substring or case.
2. Generator assumes a Linux shell on Windows CI.
3. Reading `GOFILE` as an absolute path — it is a base name; cwd is the package dir.
4. Expecting `-n` to write files.
5. Directive with a space `// go:generate` — silent.
6. Alias + `-run` that looks for the full tool name.
7. Ignoring exit status mid a long generate.
8. Generated output depends on the developer’s `GOOS`.

## Idiomatic Go

- Document `go generate -run ...` targets in the README.
- Fail if `GOFILE` / `GOPACKAGE` are missing.
- Use `-x` when debugging CI.
- Pin tools; generate flags are not a substitute for a pin.
- Keep commands in directives short; put long ones in a `go run` program.
- Prefer `go run ./internal/cmd/...` over `bash` scripts when you need portable.

## Practical scenario

A monorepo has 200 `//go:generate` lines. Full `go generate ./...` takes 8 minutes. The team introduces:

```text
go generate -run proto ./services/...
go generate -run stringer ./...
```

in separate CI jobs. Locally a developer uses `-run` for the package they work on. `-x` in the logs reveals a wrong `protoc` path in 10 minutes instead of an hour. Generators move to `mustEnv("GOFILE")` — hardcoded file names disappear after a rename refactor.

## Check questions

1. Difference between `-n` and `-x`?
2. What is in `GOFILE` — base name or absolute path?
3. What is `-run` for? What does `-skip` do when it overlaps with `-run`?
4. Why does `GOLINE` exist?
5. When to use `DOLLAR`?
6. Why can `-run stringer` miss a `-command` alias `str`?
7. What happens to remaining directives in the package after a non-zero exit?
8. Why is `GOFILE` not an absolute path — and how does that affect `ParseFile`?
9. When in CI do you use `-n`, and when `-x`?

## Summary

`go generate` flags give visibility (`-n`, `-x`, `-v`) and selection (`-run`, `-skip`); env vars give context to the generator (`GOFILE`, `GOPACKAGE`, `GOLINE`, …). Together they make the generate flow debuggable and suitable for large repos — without invented flags, only what the toolchain actually offers.

Remember three reflexes: (1) dry-run with `-n` before a mass regenerate, (2) `-x` when debugging a failure, (3) `mustEnv("GOFILE")` in every local generator.
