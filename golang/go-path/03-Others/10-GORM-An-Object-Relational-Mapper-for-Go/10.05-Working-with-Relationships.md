# 10.05 Relationships: has many, belongs to, and Preload

> **Go Path - Zero to Gopher** / **03 Others → GORM: An Object Relational Mapper for Go** / Lesson 10.05

## Lesson goals

After this lesson you should be able to:

- model `belongs to` and `has many` (and briefly `many2many`) via real GORM tags
- explain the **N+1 problem** with concrete query counts
- use `Preload` to load associations without N+1
- understand the difference `Preload` vs `Joins` (when to use which)
- set foreign key fields consciously, not by “magic”
- limit loading depth (do not pull the whole graph “just in case”)

## Prerequisite

- Lessons 10.01–10.04 (`Open`, models, CRUD, `Where`/`Find`/`First`)
- Basic FK concepts in SQL
- Go 1.22+, `gorm.io/gorm`

## Problem this lesson solves

Classic N+1:

```go
var orders []Order
db.Find(&orders) // 1 query
for _, o := range orders {
	var items []Item
	db.Where("order_id = ?", o.ID).Find(&items) // N queries
}
```

For 50 orders = 1 + 50 queries. Under load the database and latency suffer. The ORM does not solve this automatically — you **must** say `Preload`.

Second problem: wrongly modeled relations (wrong FK, wrong tag) give empty slices or silent errors.

## Mental model

```text
User 1──* Order 1──* Item
  │
  └── belongs to / has many are directions in the Go struct
      FK lives in the “child” table (order.user_id)
```

- **Belongs to:** `Order` belongs to `User` — `Order` has `UserID`.
- **Has many:** `User` has many `Order` — slice `Orders`.
- **Preload:** an additional SELECT (or selective) to fill associations after (or with) the main query — without a loop in your code.

```text
db.Preload("Items").Find(&orders)
→ SELECT * FROM orders;
→ SELECT * FROM items WHERE order_id IN (...);
```

Two queries instead of 1+N.

## Mechanism

### Struct definitions (real patterns)

```go
type User struct {
	ID     uint
	Name   string
	Orders []Order `gorm:"foreignKey:UserID"`
}

type Order struct {
	ID     uint
	UserID uint
	User   User   `gorm:"constraint:OnUpdate:CASCADE,OnDelete:SET NULL;"`
	Items  []Item `gorm:"foreignKey:OrderID"`
}

type Item struct {
	ID      uint
	OrderID uint
	SKU     string
	Cents   int
}
```

By convention GORM looks for `UserID` for `User`. The `foreignKey` tag confirms explicitly. Do not invent method chains — use documented tags and `Preload` string field names.

### N+1 — trace with concrete values

Table `orders`: IDs 1,2,3. Each has 2 items.

**Without Preload:**

| Step | SQL (essence) |
|------|----------------|
| Find orders | `SELECT * FROM orders` |
| loop ID=1 | `SELECT * FROM items WHERE order_id = 1` |
| loop ID=2 | `SELECT * FROM items WHERE order_id = 2` |
| loop ID=3 | `SELECT * FROM items WHERE order_id = 3` |

Total 4 queries for 3 orders. For 100 orders ≈ 101 queries.

**With Preload:**

| Step | SQL (essence) |
|------|----------------|
| Find | `SELECT * FROM orders` |
| Preload Items | `SELECT * FROM items WHERE order_id IN (1,2,3)` |

Total 2 queries.

### `Preload` API

```go
err := db.Preload("Items").Find(&orders).Error
err = db.Preload("User").Preload("Items").Find(&orders).Error
err = db.Preload("Items", "cents > ?", 0).Find(&orders).Error
```

The name in `Preload("Items")` = the **field** name in the struct, not the table name.

Nested:

```go
db.Preload("Orders.Items").Find(&users)
```

### Predict-then-answer

**Code:**

```go
var orders []Order
db.Find(&orders)
fmt.Println(len(orders[0].Items))
```

Assume in the database order 0 has 3 items. What does it print?

**Answer:** `0` — `Items` is not loaded; the zero value for a slice is `nil`/empty. Without Preload (or a manual Find) the association stays empty.

### `Joins` versus `Preload`

```go
db.Joins("User").Find(&orders)
```

`Joins` does a SQL JOIN (often one query, different mapping). `Preload` does separate SELECTs. For has many lists, Preload is common and clear. For filter “only orders whose user.Name = X”, you often need `Joins` + `Where`.

Do not confuse: `Preload` does not filter parent rows by a child condition the way beginners expect — for that you combine `Joins` / subquery patterns from the documentation, not invented methods.

### many2many (briefly, real tag)

```go
type Student struct {
	ID    uint
	Courses []Course `gorm:"many2many:student_courses;"`
}
type Course struct {
	ID uint
}
```

GORM expects join table `student_courses`. AutoMigrate can create it in **dev**; in prod still migrations (10.06).

### Deletion and FK

`constraint` tags affect how the database (and AutoMigrate) set FKs. Soft delete on a parent does not magically delete child rows — plan explicitly.

### Select and Preload

```go
db.Select("id", "user_id").Preload("Items").Find(&orders)
```

Parent columns limited; child Preload still goes by its own logic. Make sure FK fields needed for linking stay in Select (`user_id` / `id`).

### Session and loops — anti-pattern

```go
for _, id := range ids {
	var o Order
	db.Preload("Items").First(&o, id) // N times Preload pattern
}
```

Better: one `Where("id IN ?", ids).Preload("Items").Find(&orders)`.

### Logger — see SQL

```go
db = db.Session(&gorm.Session{Logger: logger.Default.LogMode(logger.Info)})
```

In dev enable the log and **count** SELECTs. If you see repetition by ID in a loop — N+1.

### Trace: Preload with a condition

```go
db.Preload("Items", "cents >= ?", 100).Find(&orders)
```

Loads only items ≥ 100 cents. The order still exists even if it has no expensive items — the child list can be empty.

### Association Mode (mention, without inventing)

GORM has `Model(&user).Association("Orders").Append(...)` — an existing API for adding relations. Use gorm.io documentation; we do not introduce fake chains. For most CRUD lessons: set the FK and `Create` child / `Preload` for reading.

## Rules and syntax

- `Preload("FieldName")` uses the field name in the struct.
- You solve N+1 with Preload (or a JOIN strategy), not a Find loop.
- Belongs to: FK on the child struct (`UserID`).
- Has many: slice on the parent + foreignKey tag as needed.
- Enable SQL log in dev to count queries.
- Do not Preload the whole world “just in case” — depth costs memory.
- many2many: tag `many2many:join_table;`.

## Examples

### Example 1 — Create a graph

```go
u := User{Name: "Ana", Orders: []Order{
	{Items: []Item{{SKU: "A", Cents: 100}, {SKU: "B", Cents: 200}}},
}}
db.Create(&u)
```

#### What happens here

GORM can save associations on Create (depending on FullSaveAssociations configuration etc.). Check the SQL log. Often clearer: create User, then Order with UserID, then Items with OrderID.

### Example 2 — Preload chain

```go
var users []User
err := db.Preload("Orders.Items").Find(&users).Error
```

#### What happens here

Users → orders → items. Query count: typically 3 SELECTs (users, orders IN, items IN), not a loop explosion.

### Example 3 — N+1 demonstration in a test

```go
func countQueries(t *testing.T, fn func()) int {
	// use a logger counter or pg wrapper — idea: measure
	fn()
	return 0 // replace with a real counter in the exercise
}
```

Exercise: compare Find+loop vs Preload.

### Example 4 — Joins for filter

```go
var orders []Order
db.Joins("JOIN users ON users.id = orders.user_id").
	Where("users.name = ?", "Ana").
	Find(&orders)
```

#### What happens here

You filter the parent via a child/parent table. Then if needed `Preload("Items")`.

### Example 5 — Wrong Preload string

```go
db.Preload("Item").Find(&orders) // the field is called Items
```

#### What happens here

Error or no-op depending on version/config — the SQL log shows Items were not loaded. The name must match exactly.

## Decision analysis

| Approach | When |
|----------|------|
| Preload | lists + associations, readable Go |
| Joins | filter/sort by another table |
| Hand-written SQL | complex reports |
| No associations in struct | microservices that do not join the graph |

## Trade-offs

- Preload readability vs round-trip count (still >1).
- Deep `Orders.Items.Product.Vendor` vs memory and time.
- DTO denormalization vs ORM graph.

## Common mistakes

1. **Wrong:** loop `Find` by child.  
   **Effect:** N+1.  
   **Why:** no batch IN query.  
   **Fix:** `Preload`.

2. **Wrong:** `Preload("items")` with field `Items`.  
   **Effect:** does not load.  
   **Why:** field name must match.  
   **Fix:** `Preload("Items")`.

3. **Wrong:** expecting an empty slice means “not in the database” after Find without Preload.  
   **Effect:** wrong business conclusion.  
   **Why:** association not loaded.  
   **Fix:** Preload or explicit query.

4. **Wrong:** Preload everything in a list of 10k parent rows.  
   **Effect:** memory spike.  
   **Why:** too wide a graph.  
   **Fix:** pagination + narrower Preload.

5. **Wrong:** FK field not selected.  
   **Effect:** Preload does not link.  
   **Why:** no key.  
   **Fix:** include FK in Select.

6. **Wrong:** mixing Joins and expecting has many as one row.  
   **Effect:** duplicate parent rows.  
   **Why:** JOIN mathematics.  
   **Fix:** understand SQL or use Preload.

7. **Wrong:** AutoMigrate many2many in prod as the only migration.  
   **Effect:** uncontrolled schema changes.  
   **Why:** 10.01/10.06 warning.  
   **Fix:** versioned migrations.

8. **Wrong:** ignoring the SQL log.  
   **Effect:** N+1 invisible until production.  
   **Why:** no evidence.  
   **Fix:** logger Info in dev.

## Idiomatic Go

- Small DTO for the API instead of exposing the whole ORM graph.
- Preload names as constants if they repeat.
- A test that fails if query count > threshold (anti N+1 guard).
- Explicit FK in the struct, not only a “hidden” convention.

## Practical scenario

Endpoint `GET /orders` in a load test held p95 at 2 s. SQL log: 1 + 200 queries. Fix: `Preload("Items")` + pagination 20. p95 fell to 80 ms. Second bug: frontend thought an order without Items in JSON meant an empty cart — actually the programmer forgot Preload on one code path. They added an integration test counting queries and asserting `len(items)==2`.

## Check questions

1. **What is N+1?**  
   1 query for N parent rows + N queries for children.

2. **How does GORM mitigate N+1?**  
   `Preload` with an IN query (typically).

3. **What does `Preload("Items")` use as the name?**  
   The field name in the struct.

4. **Where does the FK for belongs to User live?**  
   On Order: `UserID`.

5. **Why empty Items after Find?**  
   Association not loaded.

6. **Preload vs Joins?**  
   Preload separate SELECT; Joins SQL JOIN — different purposes.

7. **Does Preload happen automatically always?**  
   No.

8. **What does `Preload("Orders.Items")` do?**  
   Nested loading.

When latency jumps on lists, turn on the SQL log before you “optimize” Go. When JSON has no child, ask: was Preload called on that path?

Relations in an ORM are a convenience; N+1 is the cost of carelessness. Preload is a conscious decision, not default behavior.

### Additional mechanism: DTO vs ORM graph in JSON

If `encoding/json` serializes `Order` with `User` and `Items`, you easily:

- leak fields you do not want (`password_hash` on User);
- get cyclic references if both directions have pointers without `json:"-"`;
- the response becomes huge.

Idiom: `type OrderResponse struct { ... }` manually mapped, Preload only what the response needs.

### Trace: Preload with pagination

```go
var orders []Order
db.Offset(0).Limit(20).Preload("Items").Find(&orders)
```

Preload IN list = those 20 IDs, not the whole table. Without Limit, Preload on 100k parents hurts.

### Predict-then-answer: Count and Preload

```go
var n int64
db.Model(&Order{}).Preload("Items").Count(&n)
```

**What does Count do with Preload?** Count typically counts parent rows; Preload is not needed for Count and can confuse. For counting use a clean `Model.Count` without Preload.

### Foreign key types

`UserID uint` vs `UserID *uint` (nullable FK). Zero value `0` for uint can wrongly mean “belongs to user 0”. For optional belongs to often a pointer or `sql.NullInt64`. That is a Go zero value trap with the ORM.

### Query-counting exercise (concrete)

Enable the logger. Do:

1. `Find` 5 orders without Preload + Items loop → write SELECT count.
2. Same with Preload → write count.
3. Expect ~6 vs ~2.

If you do not see a difference, Preload is not activated (wrong name).

### many2many replace caution

When updating associations, Association mode `Replace` / `Clear` exist in GORM — read docs before production. A wrong Clear deletes links.

### Relationships checklist

1. FK field exists and correct type
2. Preload name = struct field
3. SQL log checked on the list endpoint
4. JSON DTO does not leak sensitive fields
5. Pagination before a large Preload
6. Anti-N+1 test on the critical path


## Mechanism — N+1 vs Preload: deep trace (50×3)

### Path A — loop (anti-pattern)

```go
var orders []Order
db.WithContext(ctx).Find(&orders) // 1
for i := range orders {
	db.WithContext(ctx).Where("order_id = ?", orders[i].ID).Find(&orders[i].Items)
}
```

For **50** orders: **51** SQL. For **200**: **201** SQL. Latency grows almost linearly with N.

### Path B — Preload (gorm.io)

```go
err := db.WithContext(ctx).Preload("Items").Find(&orders).Error
```

Typically:

```sql
SELECT * FROM "orders";
SELECT * FROM "items" WHERE "order_id" IN (?,?,…);
```

Total **2** queries. Name `"Items"` = **field** name, not table.

**Predict:** `Preload("items")` with field `Items` — what do you get?

**Answer:** Often an empty slice without an obvious error. Assert `len(Items)` in a test + SQL Logger.

### Index on FK

```sql
CREATE INDEX idx_items_order_id ON items(order_id);
```

Preload solves the **count** of queries; the index solves the **cost** of the `IN (...)` query as the table grows.

### Preload vs Joins

| Need | Tool |
|------|------|
| Fill `order.Items` | `Preload("Items")` |
| Filter parent by child column | `Joins` + `Where` |
| Both | Joins for filter, then Preload for the graph |

```go
db.Joins("JOIN items ON items.order_id = orders.id").
	Where("items.sku = ?", sku).
	Preload("Items").
	Distinct().
	Find(&orders)
```

Watch for duplicate parent rows after JOIN — `Distinct` / subquery as needed.

### Cond Preload

```go
db.Preload("Items", "cents > ?", 0).Find(&orders)
db.Preload("Items", func(tx *gorm.DB) *gorm.DB {
	return tx.Order("cents desc").Limit(20)
}).Find(&orders)
```

The condition goes on the association SELECT.

### Chained Preload — explosion

```go
db.Preload("Orders.Items").Find(&users)
```

On a list endpoint with thousands of users this blows memory. Better: pagination + shallow Preload; depth on the detail endpoint.

### Belongs to Preload

```go
db.Preload("User").First(&order, id)
```

```sql
SELECT * FROM orders WHERE id = $1;
SELECT * FROM users WHERE id = $2; -- order.user_id
```

### Has one

```go
type User struct {
	ID      uint
	Profile Profile `gorm:"foreignKey:UserID"`
}
type Profile struct {
	ID     uint
	UserID uint
	Bio    string
}
db.Preload("Profile").First(&user, id)
```

### many2many — join table

```go
type Student struct {
	ID      uint
	Courses []Course `gorm:"many2many:student_courses;"`
}
```

In DEV AutoMigrate can create `student_courses`. In prod: explicit migration (10.06).

```go
db.Preload("Courses").First(&student, id)
db.Model(&student).Association("Courses").Append(&course)
```

`Replace` / `Clear` can delete links — read gorm.io before use.

### JSON cycle

```go
type Order struct {
	Items []Item `json:"items"`
}
type Item struct {
	Order Order `json:"order"` // cycle on marshal
}
```

Solution: DTO without the back-link, or `json:"-"`.

### Repository opts

```go
type GetOrderOpts struct{ WithItems bool }

func (r *Repo) GetOrder(ctx context.Context, id uint, opt GetOrderOpts) (Order, error) {
	q := r.db.WithContext(ctx)
	if opt.WithItems {
		q = q.Preload("Items")
	}
	var o Order
	return o, q.First(&o, id).Error
}
```

### FK constraint in the database

```sql
ALTER TABLE items
  ADD CONSTRAINT fk_items_order
  FOREIGN KEY (order_id) REFERENCES orders(id);
```

An ORM tag is not a substitute for REFERENCES.

### Soft delete on the child

Preload respects soft delete scope. For admin:

```go
db.Preload("Items", func(tx *gorm.DB) *gorm.DB {
	return tx.Unscoped()
}).First(&order, id)
```

### Anti-pattern: Preload in a loop

```go
for _, id := range ids {
	db.Preload("Items").First(&o, id) // still an N pattern
}
```

Fix:

```go
db.Where("id IN ?", ids).Preload("Items").Find(&orders)
```

### Measuring in CI

Team rule: list endpoint with items ≤ 2 SQL (or agreed threshold). Custom logger / counter catches regression.

## Decision analysis — extended

| Decision | Motive |
|----------|--------|
| Preload per use-case | no universal eager load |
| Index on FK | cheap IN |
| DTO | JSON control |
| SQL count test | catches N+1 |

## Trade-offs — extended

| Strategy | Gain | Cost |
|----------|------|------|
| Preload | Anti-N+1 | Extra query, larger payload |
| Deep Preload | Less code | Data explosion |
| Joins filter | Filter in SQL | Duplicate parent |
| Association API | Short | Side-effect (Replace) |

## Idiomatic Go — extended

```go
func (r *OrderRepo) ListByEmail(ctx context.Context, email string, withItems bool) ([]Order, error) {
	q := r.db.WithContext(ctx).Where("email = ?", email).Limit(50)
	if withItems {
		q = q.Preload("Items")
	}
	var out []Order
	return out, q.Find(&out).Error
}
```

## Summary

Belongs to and has many you model with struct fields and FKs. N+1 arises from a query loop; `Preload` compresses it into a small number of SELECTs. Preload name = field name. Use Joins for filters. Always measure SQL in dev. Do not load an infinite graph.
