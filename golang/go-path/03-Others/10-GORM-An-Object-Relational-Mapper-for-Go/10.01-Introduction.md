# 10.01 Introduction to GORM: ORM versus database/sql

> **Go Path - Zero to Gopher** / **03 Others → GORM: An Object Relational Mapper for Go** / Lesson 10.01

## Lesson goals

After this lesson you should be able to:

- explain what an Object-Relational Mapper (ORM) does and what it deliberately does not do for you
- compare explicit `database/sql` with GORM from `gorm.io/gorm`
- open a connection via `gorm.Open` and an official driver (e.g. `gorm.io/driver/postgres`)
- read the SQL that GORM generates (Logger) and predict it before you see it
- understand the cost of abstraction: hidden SQL, N+1 risk, AutoMigrate misuse
- decide when GORM makes sense in a Go service, and when a thin SQL layer is the better choice

## Prerequisite

- Go 1.22+ (or newer on the team)
- Basic SQL: `SELECT`, `INSERT`, `UPDATE`, `DELETE`, indexes, transactions at the conceptual level
- Preferred: Postgres in Docker Compose from previous lessons on relational databases
- Modules:

```bash
go get gorm.io/gorm
go get gorm.io/driver/postgres
```

For local experiments you can use the SQLite driver, but in the production mental model keep **one** dialect.

## Problem this lesson solves

`database/sql` is explicit: you write SQL, scan rows, close `Rows`, map errors, pass `context.Context`. That is predictable and powerful. For a rich CRUD domain the code grows quickly: fifteen columns, `sql.Null*` types, soft delete conventions, associations, batch insert.

GORM offers conventions: models as structs, `Where` / `Find` chains, associations, hooks, `AutoMigrate` for a local start. The cost is a layer of abstraction. If you do not know which SQL is produced, you get slow queries, N+1 loops, and production surprises.

This lesson sets a **mental framework for choosing**, not the slogan “GORM always”. The goal is that afterward you can open a connection, see the SQL, and consciously say yes or no to an ORM for a given bounded context.

## Mental model

```text
Your code
   ↓
GORM API (Create, Find, Where, Preload, …)
   ↓
Generated SQL (string + arguments)
   ↓
Dialect / driver (postgres, mysql, sqlite, …)
   ↓
database/sql (*sql.DB pool)
   ↓
Database
```

GORM **is not** the database. GORM **is not** a substitute for understanding indexes, transactions, isolation, and schema. It is a mapper and SQL generator with conventions.

Three questions before introducing it:

1. Does the team know SQL well enough to read generated queries in code review?
2. Does the domain have rich relations where the ORM saves time without hiding performance?
3. Are you ready to treat migrations seriously — **not** only `AutoMigrate` in production?

If the answer to 1 or 3 is “no”, the ORM will cost more than it gives.

### Predict, then verify

While learning GORM, always use this rhythm:

1. Write the call (`Create`, `First`, …).
2. **Predict** the SQL (what you expect the database to see).
3. Enable the Logger and **compare**.
4. If it differs — that is your lesson, not “magic”.

## Mechanism

This section is the core of the lesson. Here you follow the path from `gorm.Open` to the SQL that actually goes to the database.

### 1. What an ORM maps

A relational database works with tables, columns, rows, constraints. Go works with structs, slices, types, errors.

The ORM connects:

| Go | SQL world |
|----|-----------|
| type `Product` | table (e.g. `products`) |
| field `Name string` | column `name` |
| value in memory | value in a row |
| `Create(&p)` | `INSERT …` |
| `Find(&list)` | `SELECT …` |
| relation `Items []Item` | FK / join / another SELECT (Preload) |

Mapping is not free. GORM must:

- reflect the struct (fields, tags)
- build the statement
- bind arguments
- execute via `database/sql`
- scan the result back into the struct

That is why there is overhead compared to hand-written narrow SQL — and why the Logger exists: so you see the cost.

### 2. `gorm.Open` — entry point

Official entry:

```go
import (
	"gorm.io/driver/postgres"
	"gorm.io/gorm"
)

dsn := "host=localhost user=app password=secret dbname=app port=5432 sslmode=disable"
db, err := gorm.Open(postgres.Open(dsn), &gorm.Config{})
if err != nil {
	return err
}
```

What happens:

1. The driver (`postgres.Open`) prepares the dialect and connection string.
2. `gorm.Open` creates a `*gorm.DB` session/façade over the pool.
3. Underneath, `*sql.DB` still lives.

Accessing the pool:

```go
sqlDB, err := db.DB()
if err != nil {
	return err
}
sqlDB.SetMaxOpenConns(25)
sqlDB.SetMaxIdleConns(5)
sqlDB.SetConnMaxLifetime(time.Hour)
if err := sqlDB.Ping(); err != nil {
	return err
}
```

**Rule:** the ORM does not remove the duty to configure the pool. In a container (GOMEMLIMIT, Postgres `max_connections`) a wrong pool = an incident.

### 3. Predict SQL: Create

Code:

```go
type Product struct {
	ID    uint `gorm:"primaryKey"`
	Name  string
	Cents int
}

p := Product{Name: "kafa", Cents: 350}
err := db.Create(&p).Error
```

**Predict** (before the Logger):

- Is it `INSERT` or `UPSERT`?
- Which columns go in?
- Does `ID` return into the struct?

**Answer (typical Postgres trace):**

```sql
INSERT INTO "products" ("name","cents") VALUES ('kafa',350) RETURNING "id"
```

(Exact form depends on dialect and configuration; the Logger is the truth.)

After success, `p.ID` is filled. That is mapper work — not magic.

### 4. Predict SQL: First

```go
var out Product
err := db.First(&out, 42).Error
```

**Predict:**

- `SELECT *` or a column list?
- Is there `LIMIT 1`?
- Where is `WHERE`?

**Answer (typical trace):**

```sql
SELECT * FROM "products" WHERE "products"."id" = 42 ORDER BY "products"."id" LIMIT 1
```

`First` expects exactly one row. If there is no row, the error is `gorm.ErrRecordNotFound` — that is not “other network errors”.

### 5. The chain is a builder; execution is late

```go
q := db.Where("cents >= ?", 1000).Order("id desc").Limit(20)
// still no SQL execution against the database in the sense of fetching results
err := q.Find(&list).Error
```

`Where` / `Order` / `Limit` build the statement. `Find` / `First` / `Create` / `Updates` / `Delete` execute it (with internal steps).

That is why you can compose:

```go
func applyActive(db *gorm.DB) *gorm.DB {
	return db.Where("active = ?", true)
}

err := applyActive(db).Find(&list).Error
```

(Scopes in more detail in 10.07 — here you only see that `*gorm.DB` is a chain.)

### 6. Logger — a required learning habit

```go
import "gorm.io/gorm/logger"

db, err := gorm.Open(postgres.Open(dsn), &gorm.Config{
	Logger: logger.Default.LogMode(logger.Info),
})
```

In development: `Info` so you see SQL and duration. In production: care — volume, PII, secrets in literals if someone wrongly logs the DSN.

**Mental model exercise:** for every new chain you write in the first weeks, look in the log for:

1. number of queries per HTTP request
2. whether there is a loop of `SELECT … WHERE id = ?` (N+1 smell)
3. whether `SELECT *` pulls too many columns

### 7. GORM still sits on `database/sql`

Everything you learned about:

- the connection pool
- timeouts
- database-level transactions
- indexes
- `EXPLAIN`

still applies. GORM does not “optimize” queries by itself. It generates; you choose the API and the schema.

When you need full control:

```go
var name string
err := db.Raw("SELECT name FROM products WHERE id = ?", id).Scan(&name).Error
```

or `db.Exec` for DDL/DML outside the model. A hybrid is legitimate — if it is **conscious**, not accidental.

### 8. AutoMigrate — a DEV helper, not a production strategy

```go
err := db.AutoMigrate(&Product{})
```

What AutoMigrate **does** (per official documentation):

- creates missing tables
- adds missing columns, indexes, constraints it can derive
- can change column type in some cases (size/precision/nullable directions)

What AutoMigrate **deliberately does not** do:

- **does not delete** unused columns (protects data)
- is not a versioned migration history in git as a SQL review package
- is not a reliable rename (you often get a new column + the old one)
- is not a backfill plan, expand/contract, or lock strategy for multi-pod deploy

**Clear message of this course:**

> `AutoMigrate` is for local development and empty prototype databases.  
> Production schema evolution = versioned migrations (10.06).  
> Do not put `AutoMigrate` in production `main` as the only story.

### 9. N+1 — a preview you must feel early

```go
var orders []Order
db.Find(&orders)
for i := range orders {
	db.Where("order_id = ?", orders[i].ID).Find(&orders[i].Items)
}
```

For 50 orders: 1 + 50 queries. Under load the database and latency suffer.

The solution in GORM (detail in 10.05): `Preload("Items")` — typically 1 query for parents + 1 query with `WHERE order_id IN (...)`.

Already in 10.01: if in the Logger you see the same `SELECT` in a loop — stop and rewrite.

### 10. One `*gorm.DB` per process (per database)

Anti-pattern:

```go
func handler(w http.ResponseWriter, r *http.Request) {
	db, _ := gorm.Open(...) // BAD: Open per request
}
```

Correct: `Open` in `main` / wiring, inject `*gorm.DB` (or a repository) into handlers. The pool lives long; the request uses `db.WithContext(r.Context())`.

### 11. Errors on the chain

Methods often return `*gorm.DB`. The error is in `.Error`:

```go
tx := db.Create(&p)
if tx.Error != nil {
	return tx.Error
}
```

or shorter:

```go
if err := db.Create(&p).Error; err != nil {
	return err
}
```

Ignoring `.Error` is a classic mistake: the test “passes”, the database is empty.

For “no row”:

```go
import "errors"

err := db.First(&p, id).Error
if errors.Is(err, gorm.ErrRecordNotFound) {
	// 404 path
}
```

### 12. Context from day one

```go
err := db.WithContext(ctx).First(&p, id).Error
```

Without context: the request is canceled, the query still holds a connection. Details in 10.07; the habit starts here.

### 13. DTO versus model

A GORM model often has fields you do not want in JSON (`DeletedAt`, internal flags). Idiom: API DTO separated from the persistence model. Do not blindly export a GORM struct as the response.

### 14. Flow comparison: the same insert

**GORM path:**

```go
item := Item{Name: "kafa", Cents: 350}
err := db.WithContext(ctx).Create(&item).Error
```

**database/sql path:**

```go
err := db.QueryRowContext(ctx,
	`INSERT INTO items(name, cents) VALUES($1,$2) RETURNING id`,
	"kafa", 350,
).Scan(&id)
```

Both are legitimate. GORM saves boilerplate on CRUD + relations. `database/sql` saves surprises on the hot path and analytics.

### 15. When you choose what

Choose GORM when:

- you have many similar CRUD endpoints
- relations are often loaded together (with Preload discipline)
- the team reviews SQL log / DryRun in the PR

Choose `database/sql` / sqlc / explicit SQL when:

- the hot path must be exactly one known query
- complex CTE / window / reports
- a strict requirement that every SQL lives in a file as SQL

A hybrid per **bounded context** is OK. A hybrid “by developer mood in the same package” is not.

## Rules and syntax

1. Import path for new projects: `gorm.io/gorm` (not the old `github.com/jinzhu/gorm` v1 as the default choice).
2. Entry: `gorm.Open(dialector, &gorm.Config{})`.
3. Check errors via `.Error` or the returned `error` value of the API you use.
4. Configure the pool via `db.DB()`.
5. In development enable the Logger; in production reduce noise and PII risk.
6. DSN from the environment (`os.Getenv`), not hardcoded in the repo.
7. One long-lived `*gorm.DB` per database; per request `WithContext`.
8. `AutoMigrate` = local helper; production = versioned migrations (10.06).
9. Never assume the ORM “knows indexes” or “prevents N+1”.
10. Use placeholders (`?`) in `Where` — never concatenate user input into a SQL string (10.04).

### Minimal import set

```go
import (
	"gorm.io/driver/postgres"
	"gorm.io/gorm"
	"gorm.io/gorm/logger"
)
```

### Minimal Config pattern

```go
cfg := &gorm.Config{
	Logger: logger.Default.LogMode(logger.Warn),
}
db, err := gorm.Open(postgres.Open(dsn), cfg)
```

For learning temporarily use `logger.Info`.

## Examples

### Example 1 — Minimal program with Postgres

```go
package main

import (
	"fmt"
	"log"
	"os"

	"gorm.io/driver/postgres"
	"gorm.io/gorm"
	"gorm.io/gorm/logger"
)

type Item struct {
	ID    uint `gorm:"primaryKey"`
	Name  string
	Cents int
}

func main() {
	dsn := os.Getenv("DATABASE_URL")
	if dsn == "" {
		log.Fatal("DATABASE_URL required")
	}
	db, err := gorm.Open(postgres.Open(dsn), &gorm.Config{
		Logger: logger.Default.LogMode(logger.Info),
	})
	if err != nil {
		log.Fatal(err)
	}
	// DEMO ONLY — not a production migrate story
	if err := db.AutoMigrate(&Item{}); err != nil {
		log.Fatal(err)
	}
	item := Item{Name: "kafa", Cents: 350}
	if err := db.Create(&item).Error; err != nil {
		log.Fatal(err)
	}
	fmt.Println("id", item.ID)
}
```

#### Predict the result

Before running, write on paper the expected `INSERT`. Then compare with the Logger output.

#### What happens here

A connection opens, AutoMigrate for the demo aligns the table, `Create` inserts a row and fills `ID`. The Logger trains the eye.

### Example 2 — The same task with database/sql

```go
package main

import (
	"context"
	"database/sql"
	"log"
	"os"
	"time"

	_ "github.com/jackc/pgx/v5/stdlib"
)

func main() {
	db, err := sql.Open("pgx", os.Getenv("DATABASE_URL"))
	if err != nil {
		log.Fatal(err)
	}
	defer db.Close()
	ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()
	var id int
	err = db.QueryRowContext(ctx,
		`INSERT INTO items(name, cents) VALUES($1,$2) RETURNING id`,
		"kafa", 350,
	).Scan(&id)
	if err != nil {
		log.Fatal(err)
	}
	log.Println("id", id)
}
```

#### What happens here

Explicit SQL, explicit context. No AutoMigrate — the schema must already exist. More code for CRUD, less magic. This is the reference point while you learn GORM.

### Example 3 — Pool and ping after Open

```go
sqlDB, err := db.DB()
if err != nil {
	log.Fatal(err)
}
sqlDB.SetMaxOpenConns(25)
sqlDB.SetMaxIdleConns(5)
sqlDB.SetConnMaxLifetime(time.Hour)
if err := sqlDB.Ping(); err != nil {
	log.Fatal(err)
}
```

#### Predict the result

Does `Ping` send SQL? (Yes — a simple round-trip, dialect-dependent.)

#### What happens here

You confirm the pool is alive and credentials work before you start CRUD.

### Example 4 — DryRun: see SQL without execution

```go
stmt := db.Session(&gorm.Session{DryRun: true}).
	Create(&Item{Name: "caj", Cents: 200})
fmt.Println(stmt.Statement.SQL.String())
fmt.Println(stmt.Statement.Vars)
```

#### What happens here

You learn the generator without a side effect on the database. Useful in unit-ish statement tests (integration still needs a real database).

### Example 5 — Compose for learning

```yaml
services:
  db:
    image: postgres:16.3-alpine
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: app
      POSTGRES_DB: app
    ports: ["5432:5432"]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d app"]
      interval: 5s
      retries: 10
```

```text
DATABASE_URL=host=localhost user=app password=app dbname=app port=5432 sslmode=disable
```

#### What happens here

Local Postgres ready for GORM exercises. Healthcheck reduces the race with the first `gorm.Open`.

### Example 6 — Trade-offs table (worksheet)

| Dimension | database/sql | GORM |
|-----------|--------------|------|
| SQL control | full | good with Logger + Raw |
| CRUD writing speed | slower | faster |
| Relations / preload | manual | built-in |
| Migrations | yours | AutoMigrate + external tools |
| Learning curve | SQL | SQL + ORM conventions |
| Surprise N+1 | rarer (explicit) | often without Preload discipline |

#### What happens here

There is no universal winner. You choose by context.

### Example 7 — Shared DB in an HTTP server

```go
type Server struct {
	db *gorm.DB
}

func (s *Server) getItem(w http.ResponseWriter, r *http.Request) {
	id := /* parse */ uint(1)
	var item Item
	err := s.db.WithContext(r.Context()).First(&item, id).Error
	if errors.Is(err, gorm.ErrRecordNotFound) {
		http.NotFound(w, r)
		return
	}
	if err != nil {
		http.Error(w, "db error", 500)
		return
	}
	_ = item
}
```

#### Predict the result

`SELECT … WHERE id = 1 … LIMIT 1`. Check the Logger.

#### What happens here

One `*gorm.DB`, context from the request, clear mapping `ErrRecordNotFound` → 404.

### Example 8 — Anti-example: Open in a loop

```go
for _, id := range ids {
	db, _ := gorm.Open(postgres.Open(dsn), &gorm.Config{})
	var p Product
	_ = db.First(&p, id)
}
```

#### What happens here

Connection explosion, slow requests, easy to hit `max_connections`. Fix: one Open, one `Where("id IN ?", ids).Find`.

## Decision analysis

### GORM for the whole project vs only admin CRUD

Sometimes a team wants thin SQL for the public API, GORM for the internal backoffice. Two styles in the same service cost cognitive load. Better: one strategy per bounded context, a clear package boundary.

### sqlc / Jet / hand-written SQL

sqlc generates typed code from SQL — the compromise “SQL is the source of truth”. GORM likes conventions and models. Do not mix all three in the same package without a boundary.

### AutoMigrate in CI for ephemeral databases

For throwaway test containers AutoMigrate can be acceptable. That is **not** an argument for AutoMigrate in production startup. Test and prod have different risks.

### Logger level

| Environment | Suggestion |
|-------------|------------|
| local learning | Info |
| CI integration | Silent or Warn + selective Debug |
| production | Warn/Error; sampling as needed |

### When the ORM “wins” on a Go team

- Many CRUD endpoints with similar patterns
- Relations often loaded together (with Preload)
- The team already knows SQL well enough to review generated queries

### When the ORM “loses”

- Heavy reports and analytics
- An extremely simple service with three queries
- A strict requirement that every SQL is in a file reviewed as SQL

## Trade-offs

| Choice | Gain | Cost |
|--------|------|------|
| GORM | Fast CRUD, relations, conventions | Abstraction, N+1 risk, convention learning curve |
| Only database/sql | Predictability, thin stack | More boilerplate |
| GORM + Raw everywhere | “Flexibility” | You lose the point of the ORM; two styles |
| AutoMigrate in prod | “easy” in a demo | Dangerous schema drift, weak review |
| One style per context | Clear mental model | Requires team discipline |
| Open per request | — | Only harm |

Trade-off is not theory: measure SQL count per request and p95 latency before you “optimize by feel”.

## Common mistakes

1. Ignoring `.Error` on the method chain — silent fail.
2. Thinking the ORM “optimizes” queries by itself.
3. `AutoMigrate` as the only migration strategy in production.
4. Opening a new `gorm.Open` per request instead of a shared `*gorm.DB`.
5. Logging SQL with secrets / PII in production without control.
6. Mixing v1 `jinzhu/gorm` API with v2 `gorm.io/gorm` documentation.
7. Losing context (`Background` deep in the repo without reason).
8. An N+1 loop then “the database is slow” instead of Preload.
9. Treating a GORM model as a public JSON DTO without a filter.
10. Concluding “works locally with AutoMigrate” = “ready for prod schema”.

## Idiomatic Go

- Wiring in `main`: Open → pool → (dev AutoMigrate?) → inject.
- A repository or store layer hides GORM from HTTP handlers where the team wants that.
- `WithContext(ctx)` on the request path.
- Errors: `errors.Is(err, gorm.ErrRecordNotFound)`.
- Modules: `gorm.io/gorm` + one driver; pin versions in `go.mod`.
- Tests: a real database (testcontainers / Compose), not only a mock if you are learning SQL traces.
- Do not export `*gorm.DB` into every package — keep a boundary.

Pattern:

```go
type ProductRepo struct {
	db *gorm.DB
}

func (r *ProductRepo) ByID(ctx context.Context, id uint) (Product, error) {
	var p Product
	err := r.db.WithContext(ctx).First(&p, id).Error
	return p, err
}
```

## Practical scenario

A team rewrites PHP CRUD into Go. They choose GORM to speed delivery. After three months the dashboard is slow. The tracer shows 80–200 SQL per page. Cause: order list, then items in a loop. They enable the Logger on staging, add `Preload`, introduce a rule:

> Every `Find` with a relation must explicitly `Preload` or `Joins`, otherwise no merge.

At the same time the hot-path report stays in `Raw` SQL. The hybrid works because it is **conscious**, not accidental. AutoMigrate stays banned in the production entrypoint; migrations go via a job (10.06).

Second episode: a junior opens `gorm.Open` in middleware “so it is fresh”. Postgres `max_connections` collapses. Fix: one DB in `main`, pool metrics on `/debug`.

3. Configure the pool; intentionally set a small `max_connections` on Postgres and observe errors under parallel requests.
4. DryRun for `Create` and `First` — print the SQL string and Vars.
5. Intentionally ignore `.Error` on `Create` — see why the test lies; then fix.
6. Intentionally make an N+1 loop (10 rows + 10 child queries); count SQL in the log; remember the pain for 10.05.
7. Write a short team decision (10 lines): where AutoMigrate is allowed, where not.

## Summary

GORM (`gorm.io/gorm`) speeds up CRUD and relations on top of `database/sql`, but does not abolish SQL, the pool, migrations, or responsibility for performance. The entry is `gorm.Open`; the truth is SQL in the Logger. `AutoMigrate` is a DEV helper — not a production migration story. Learn the predict-then-verify rhythm, share `*gorm.DB`, and consciously choose where the ORM stops and where Raw/SQL takes over.
