# 10.02 Defining schemas: models, tags, and AutoMigrate

> **Go Path - Zero to Gopher** / **03 Others → GORM: An Object Relational Mapper for Go** / Lesson 10.02

## Lesson goals

After this lesson you should be able to:

- model tables via Go structs and GORM tags `gorm:"..."`
- use embedding `gorm.Model` consciously (ID, timestamps, soft delete field)
- set `primaryKey`, `uniqueIndex`, `index`, `size`, `not null`, `column`, `type`
- override the table name via `TableName()`
- run `AutoMigrate` in development and explain why it **does not delete columns** and why it is not a production migration
- distinguish a rename in the struct from a rename in the database (often a new column + the old one)

## Prerequisite

- Lesson 10.01 (`gorm.Open`, Logger, predict-then-verify)
- Postgres (or SQLite for short experiments) — keep one dialect in the project
- Basic Go struct tags

## Problem this lesson solves

Without agreement on the schema, every developer has a different struct and a different table. AutoMigrate “fixes” things locally while staging breaks on `NOT NULL` without a default. Tags are a contract between the Go type and the SQL schema. AutoMigrate is convenient for a prototype — **not** a substitute for versioned migrations when data exists.

The key misunderstanding this lesson breaks:

> “I changed the struct → AutoMigrate synchronized the database 1:1.”

No. AutoMigrate **adds** and **adjusts** within documented rules, but **does not drop** unused columns. A rename often leaves debris.

## Mental model

```text
Go struct field  ↔  SQL column
Go type (Product) ↔  SQL table (products or TableName())
gorm tag         ↔  constraint / index / type / name
AutoMigrate      ↔  “add what is missing”, not “do a full sync drop”
```

`AutoMigrate`:

- adds missing tables / columns / indexes / FKs it can derive
- can change type in some cases (size, precision, non-null → null directions per docs)
- **does not delete** unused columns (officially: protects data)
- does not replace careful data rewrite (rename with transformation, table split)

Therefore: AutoMigrate for greenfield locally; production → lesson 10.06.

## Mechanism

### 1. From struct to table

```go
type Product struct {
	ID    uint
	Name  string
	Cents int
}
```

Convention (default): table `products`, columns `id`, `name`, `cents`. Plural and snake_case convention can surprise — that is why often explicit `TableName` and `column:`.

**Predict DDL** after `AutoMigrate(&Product{})` on an empty database (simplified):

```sql
CREATE TABLE "products" (
  "id" bigserial PRIMARY KEY,
  "name" text,
  "cents" bigint
);
```

(Exact types depend on dialect — Logger / `\d products` in psql are the truth.)

When you run `Create` after that, **predict**:

```sql
INSERT INTO "products" ("name","cents") VALUES ('kafa',350) RETURNING "id"
```

The link is clear: the schema the model describes becomes metadata GORM uses for both the DDL helper and DML.

### 2. Exported fields vs unexported

```go
type Row struct {
	ID   uint
	Name string
	secret string // GORM ignores for schema/column mapping
}
```

Only exported fields (capital first letter) participate in mapping. If a “column disappears”, first check whether the field is exported.

Exclude a field intentionally:

```go
type Row struct {
	ID       uint
	Password string `gorm:"-"` // does not go into SQL mapping
	Name     string
}
```

**Predict AutoMigrate DDL:** no `password` or `secret` column. If Password must go into the database, remove `gorm:"-"` and think about hashing before Create (do not store plaintext).

### 3. `gorm.Model` embedding

```go
import "gorm.io/gorm"

type User struct {
	gorm.Model
	Email string `gorm:"uniqueIndex;size:255"`
}
```

`gorm.Model` brings:

| Field | Role |
|-------|------|
| `ID` | `uint` primary key |
| `CreatedAt` | creation time |
| `UpdatedAt` | update time |
| `DeletedAt` | `gorm.DeletedAt` — soft delete |

**Consequence:** `Delete` becomes soft delete (10.03), and default queries add a condition on `deleted_at`.

**Predict DDL fragments** you often see:

```sql
"id" bigserial PRIMARY KEY,
"created_at" timestamptz,
"updated_at" timestamptz,
"deleted_at" timestamptz
```

plus an index on `deleted_at` (the tag on `DeletedAt` often carries `index`).

If you do not want soft delete or a `uint` ID (e.g. UUID), **do not** embed `gorm.Model` — define fields manually.

### 4. Tags you actually use

A tag is a string with directives separated by `;`:

```go
Email string `gorm:"column:email_address;size:255;uniqueIndex;not null"`
```

Common, documented directives:

| Tag | Meaning |
|-----|---------|
| `primaryKey` | primary key |
| `column:name` | column name |
| `type:text` / `type:jsonb` | SQL type (dialect!) |
| `size:255` | length |
| `uniqueIndex` | unique index |
| `index` | ordinary index |
| `not null` | NOT NULL |
| `default:0` | default |
| `-` | ignore field |
| `embedded` / `embeddedPrefix:` | nested struct |

Do not invent arbitrary chain methods in tags. If you are unsure — gorm.io docs for your version.

**Predict** for the Email tag above (simplified):

```sql
"email_address" varchar(255) NOT NULL
-- plus unique index on email_address
```

### 5. `primaryKey` and ID types

```go
type Product struct {
	ID uint `gorm:"primaryKey"`
}
```

UUID example (requires database/default support):

```go
type Product struct {
	ID uuid.UUID `gorm:"type:uuid;primaryKey;default:gen_random_uuid()"`
}
```

**Predict:** does `default:gen_random_uuid()` work on an SQLite test? Often not. That is why one dialect.

If the default lives only in the database, Create without ID still works — the database fills it. If there is no default, a `BeforeCreate` hook (10.07) or an explicit UUID in the service.

### 6. `uniqueIndex` and composite

```go
type Enrollment struct {
	ID       uint
	UserID   uint `gorm:"not null;uniqueIndex:ux_user_course"`
	CourseID uint `gorm:"not null;uniqueIndex:ux_user_course"`
}
```

The same `uniqueIndex` name on multiple fields → composite unique. Useful for “user once per course”.

**Predict SQL (simplified):**

```sql
CREATE UNIQUE INDEX "ux_user_course" ON "enrollments" ("user_id","course_id");
```

**Predict DML error:** a second insert of the same pair → unique violation. Map to 409 in the HTTP layer.

### 7. `TableName()` override

```go
func (Order) TableName() string {
	return "shop_orders"
}
```

Without this, convention may give `orders`. An explicit name reduces surprises in joins and raw SQL.

**Predict** after Create:

```sql
INSERT INTO "shop_orders" (...) VALUES (...)
```

If in the Logger you still see `orders`, check whether you are calling the wrong type or whether another `TableName` / naming strategy exists.

### 8. AutoMigrate — exact mechanism and boundaries

```go
err := db.AutoMigrate(&model.Product{}, &model.Order{})
```

What to expect:

1. If the table does not exist → CREATE.
2. If a column from the model is missing → ADD COLUMN.
3. If an index the tag asks for is missing → CREATE INDEX (when the migrator can).
4. If you remove a field from the struct → **the column stays in the database**.

Official documentation note: AutoMigrate **WON'T delete unused columns**.

That is why after a model “cleanup” the local database and production can diverge silently — old columns live forever until you drop them with a migration.

**Predict a second AutoMigrate** on the same schema with no model changes: almost a no-op (no new ALTERs). That is not proof the schema is “clean” — garbage columns may still exist.

### 9. Rename trap (critical)

You want `Name` → `Title`:

```go
// was: Name string
// now: Title string
_ = db.AutoMigrate(&Product{})
```

**Predict what happens:**

- A new column `title` is added.
- The old column `name` **remains** (no drop).
- Data in `name` does not migrate automatically into `title`.

**Correct path:** SQL migration `ALTER TABLE ... RENAME COLUMN` + aligning the model (10.06).

Worksheet (do this once):

| Step | Action | Expectation |
|------|--------|-------------|
| 1 | Model with Name, AutoMigrate, insert | column name filled |
| 2 | Field Title, AutoMigrate | name + title |
| 3 | First in Go | Title zero/empty |
| 4 | SQL RENAME | one column title with old data |

### 10. NOT NULL without a default on a full table

```go
Phone string `gorm:"not null"`
```

On a table with existing rows, adding a NOT NULL column without a default/backfill can break the migration. AutoMigrate locally on an empty database “works”; staging with data breaks. Expand/contract: nullable → backfill → NOT NULL.

**Predict** on staging with 10k rows: ALTER/ADD NOT NULL → error. Local “green” AutoMigrate lies to you.

### 11. Soft delete field without the whole Model

```go
type Product struct {
	ID        uint
	SKU       string
	DeletedAt gorm.DeletedAt `gorm:"index"`
}
```

Same soft delete behavior as with `gorm.Model`, but you control the other fields.

**Predict SELECT** after Delete:

```sql
SELECT * FROM "products" WHERE ... AND "deleted_at" IS NULL
```

### 12. Indexes for the hot path, not “index everything”

```go
Email string `gorm:"size:255;index"`
```

An index speeds WHERE/JOIN; slows writes and uses space. A tag in the model is not a substitute for `EXPLAIN ANALYZE` on real volume.

**Predict:**

```sql
CREATE INDEX IF NOT EXISTS "idx_users_email" ON "users" ("email");
```

(Index name depends on GORM naming strategy — Logger/Migrator is the truth.)

### 13. Dialect and `type:`

```go
Payload string `gorm:"column:event_payload;type:jsonb"`
```

`jsonb` is Postgres-specific. On an SQLite test it can fail. Document the dialect in the README; do not lie to yourself that it “works everywhere”.

**Predict** on Postgres: column `event_payload` of type jsonb.  
**Predict** on SQLite: possible fail or a different type — that is why integration tests on the same dialect as prod.

### 14. Model vs DTO

Persistence model:

```go
type Product struct {
	ID        uint
	SKU       string `gorm:"uniqueIndex;size:64;not null"`
	Cents     int
	DeletedAt gorm.DeletedAt `gorm:"index"`
}
```

API DTO:

```go
type ProductResponse struct {
	ID    uint   `json:"id"`
	SKU   string `json:"sku"`
	Cents int    `json:"cents"`
}
```

Do not mix `json` and `gorm` roles: `json` is transport; `gorm` is schema/ORM.

### 15. Predict-then-verify for AutoMigrate

Steps:

1. Write the model.
2. Predict DDL (CREATE/ALTER).
3. Run AutoMigrate on an empty local database.
4. Compare with `\d table` / information_schema.
5. Change a field (rename) — predict that the old column remains — confirm.

If you do not do step 5 at least once, you have not understood AutoMigrate.

### 16. Naming strategy — why the name is not always what you think

GORM has a naming strategy (snake_case, plural). That is why `UserAgent` can become `user_agents` / `user_agent` depending on context (table vs column).

**Team rule:** whenever a name enters raw SQL, a join, or documentation — explicit `TableName()` and `column:`.

### 17. Embedded struct

```go
type Audit struct {
	CreatedBy string
	UpdatedBy string
}

type Document struct {
	ID    uint
	Title string
	Audit Audit `gorm:"embedded;embeddedPrefix:audit_"`
}
```

**Predict columns:** `audit_created_by`, `audit_updated_by` (with prefix). Without a prefix names can collide.

### 18. Multiple models in one AutoMigrate

```go
err := db.AutoMigrate(
	&model.User{},
	&model.Product{},
	&model.Order{},
	&model.Item{},
)
```

Order can matter if you expect FK constraints. In production still prefer versioned migrations with explicit FKs (10.06). AutoMigrate FK support exists, but reviewing DDL remains your responsibility.

### 19. Schema check after AutoMigrate (psql)

```sql
\d products
SELECT column_name, data_type, is_nullable
FROM information_schema.columns
WHERE table_name = 'products'
ORDER BY ordinal_position;
```

Compare with the struct. If you see extra columns — that is a trace of an old model or manual changes.

### 20. Checklist before merging a model (extended)

- [ ] Primary key clear
- [ ] Unique where the domain requires it
- [ ] Indexes for WHERE/JOIN hot path (not “index everything”)
- [ ] Soft delete intentional or not
- [ ] Migration plan if the database is not empty
- [ ] No secrets in default tags
- [ ] Dialect documented
- [ ] TableName explicit if the name is not obvious
- [ ] DTO separated from the model
- [ ] Rename planned as SQL, not AutoMigrate

### 21. Link to Docker lessons

The schema lives in the database from Compose. The application image does not contain Postgres. Migrations (later) can be:

- an init container,
- a job in CI,
- or a start hook only in DEV.

Do not mix “I brought up Compose” with “the schema is versioned”.

### 22. Minimal “team contract” (copy into README)

```text
1. AutoMigrate is allowed only locally (APP_ENV=dev) and in throwaway test databases.
2. Every schema change in a shared environment goes as a migration file (10.06).
3. Rename = SQL RENAME/expand-contract, not a struct rename alone.
4. Deleting a column = explicit DROP with review; AutoMigrate will not do that.
5. One dialect: Postgres in dev/stage/prod/testcontainers.
```

## Rules and syntax

1. Exported fields are mapped; unexported are not.
2. `gorm:"-"` excludes a field from ORM mapping.
3. Be explicit with `not null` and unique where the domain requires an invariant.
4. Do not expect rename via AutoMigrate.
5. AutoMigrate **does not drop** columns — an explicit warning.
6. Keep models in `internal/model` or `internal/domain`.
7. One dialect per project while learning.
8. `TableName()` when the name is not an obvious convention.
9. Composite unique = the same `uniqueIndex:name` on multiple fields.
10. Production: versioned migrations; AutoMigrate only DEV/prototype.

### Syntax patterns

```go
type Product struct {
	ID        uint           `gorm:"primaryKey"`
	SKU       string         `gorm:"uniqueIndex;size:64;not null"`
	Name      string         `gorm:"size:200;not null"`
	Active    bool           `gorm:"not null;default:true"`
	DeletedAt gorm.DeletedAt `gorm:"index"`
}

func (Product) TableName() string { return "products" }
```

```go
if err := db.AutoMigrate(&Product{}); err != nil {
	return err
}
```

## Examples

### Example 1 — Model with tags

```go
package model

import (
	"time"

	"gorm.io/gorm"
)

type Product struct {
	ID        uint           `gorm:"primaryKey"`
	SKU       string         `gorm:"uniqueIndex;size:64;not null"`
	Name      string         `gorm:"size:200;not null"`
	Cents     int            `gorm:"not null"`
	Active    bool           `gorm:"not null;default:true"`
	CreatedAt time.Time
	UpdatedAt time.Time
	DeletedAt gorm.DeletedAt `gorm:"index"`
}

func (Product) TableName() string { return "products" }
```

#### Predict the result

Unique on `sku`, index on `deleted_at`, table `products`.

#### What happens here

A readable contract for review. Soft delete intentional. Table name explicit.

### Example 2 — AutoMigrate locally

```go
if err := db.AutoMigrate(&model.Product{}, &model.Order{}); err != nil {
	log.Fatal(err)
}
```

#### What happens here

GORM aligns missing structures. Good for an empty local database. In production with data: risk of NOT NULL, lock, drift.

### Example 3 — Rename proof

1. Create a model with `Name`.
2. AutoMigrate, insert a row.
3. Rename the field to `Title`, AutoMigrate.
4. Check columns: expect both `name` and `title`.

#### What happens here

You see why rename requires a SQL migration.

### Example 4 — Composite unique

```go
type Enrollment struct {
	ID       uint
	UserID   uint `gorm:"not null;uniqueIndex:ux_user_course"`
	CourseID uint `gorm:"not null;uniqueIndex:ux_user_course"`
}
```

#### Predict the result

Unique index over `(user_id, course_id)`.

### Example 5 — BAD: production main with only AutoMigrate

```go
func main() {
	db := mustOpen()
	_ = db.AutoMigrate(&User{}, &Order{}, &Payment{}, &Audit{})
	runServer(db)
}
```

#### What happens here

Every deploy can change the schema without SQL review. Moves to 10.06.

### Example 6 — gorm.Model vs manual fields

```go
type UserA struct {
	gorm.Model
	Email string
}

type UserB struct {
	ID        uuid.UUID `gorm:"type:uuid;primaryKey"`
	Email     string    `gorm:"uniqueIndex;size:255"`
	CreatedAt time.Time
	UpdatedAt time.Time
}
```

### Example 7 — column + type

```go
type Audit struct {
	ID      uint
	Payload string `gorm:"column:event_payload;type:jsonb"`
}
```

### Example 8 — information_schema check

After AutoMigrate compare the Go model with `information_schema.columns`. Extra columns = signal for a manual DROP later.

## Decision analysis

### Should you embed `gorm.Model`?

Yes: speed, convention, soft delete OK for the resource.  
No: UUID PK, no soft delete, different timestamp source (database only).

### Tags for indexes vs SQL migrations

Tags keep the truth close to code. Complex indexes (partial unique `WHERE deleted_at IS NULL`) often **do not** fit nicely in a tag — a SQL migration wins (10.06).

### One big `models.go`

Split by aggregate. A 2000-line file slows review and increases merge conflicts.

### AutoMigrate in tests

Acceptable for an ephemeral schema. Do not mix with the production entrypoint.

## Trade-offs

| Approach | Gain | Cost |
|----------|------|------|
| AutoMigrate | Fast start | Weak oversight; does not drop columns |
| Tags for indexes | Close to code | Part of the truth outside SQL files |
| Only SQL migrations | Full control | More ceremony |
| `gorm.Model` | Convention | Soft delete and uint ID everywhere |
| Manual fields | Control | More boilerplate |
| One dialect | Fewer surprises | Less “portability” in tests |
| Embedded struct | DRY fields | Prefix/name traps |

## Common mistakes

1. AutoMigrate in prod without backup/review.
2. Expecting rename via AutoMigrate.
3. Unexported fields then “missing” columns.
4. Wrong table name (plural convention surprises).
5. `NOT NULL` on a full table without backfill.
6. JSON tags mixed with gorm tags without understanding roles.
7. Believing that deleting a field from the struct deletes the column — **it does not**.
8. `type:jsonb` on an SQLite test then “GORM is broken”.
9. Soft delete “accidentally” via `gorm.Model` without team agreement.
10. Unique on a column + soft delete without a partial index (later pain in 10.03/10.06).

## Idiomatic Go

- Models without HTTP obligations where you can; mapper to DTO.
- Domain validation in Go **and** constraint in the database (defense in depth).
- `not null` in the database for invariants that truly hold.
- Package `internal/model` does not import `net/http`.
- Only unusual tags are commented (`type:`, special default), not every field.

```go
// Product is a persistence model; do not use directly as a JSON response.
type Product struct {
	ID  uint   `gorm:"primaryKey"`
	SKU string `gorm:"uniqueIndex;size:64;not null"`
}
```

## Practical scenario

Staging AutoMigrate adds `users.phone NOT NULL` without a default. The table has old rows → migration fails, deploy goes red. Hotfix: remove not null from the tag, manual SQL backfill, then the constraint. The same day they ban AutoMigrate in the prod deploy hook.

Second story: a developer “cleans” the model (deletes the `legacy_code` field). Thinks the column is gone. A month later a GDPR export still pulls `legacy_code` from the database. Cause: AutoMigrate does not drop. Fix: explicit migration `DROP COLUMN` with review.

Third: the team mixes SQLite in unit tests and Postgres in prod. Tag `type:jsonb` fails locally. They move to testcontainers Postgres — the same dialect everywhere.

## Summary

GORM schemas are Go structs plus tags plus naming conventions. `primaryKey`, `uniqueIndex`, embedding `gorm.Model`, and `TableName()` form the contract with the database. `AutoMigrate` speeds local development: it adds and adjusts, but **does not drop columns** and does not safely manage data evolution in production. Be explicit about unique/not null/indexes and plan rename through real migrations.
