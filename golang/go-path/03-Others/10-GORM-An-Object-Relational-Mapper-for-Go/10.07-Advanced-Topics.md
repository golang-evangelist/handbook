# 10.07 Advanced GORM topics: hooks, Transaction, scopes, context

> **Go Path - Zero to Gopher** / **03 Others → GORM: An Object Relational Mapper for Go** / Lesson 10.07

## Lesson goals

After this lesson you should be able to:

- use real GORM hooks (`BeforeCreate`, `AfterCreate`, `BeforeUpdate`, `BeforeDelete`, …)
- pack multiple writes into `db.Transaction(func(tx *gorm.DB) error { ... })`
- write scopes as `func(db *gorm.DB) *gorm.DB` and chain them with `db.Scopes(...)`
- pass `context.Context` via `WithContext`
- know the boundaries: hooks are not a free event bus; transactions have an isolation story

## Prerequisite

- 10.01–10.06
- Understanding `context` in Go 1.22+
- Basic SQL transactional concepts (BEGIN/COMMIT/ROLLBACK)

## Problem this lesson solves

Without a transaction:

```go
db.Create(&order)
db.Create(&payment) // fail — order remains “paid” in your head, not in the database
```

Without hooks: timestamp / UUID logic copied in 12 places.  
Without context: queries ignore HTTP timeout / cancel.  
Without scopes: the same `Where("deleted_at IS NULL")` copy-paste (when you do not use built-in soft delete).

This lesson connects those four tools with the **real** GORM API.

## Mental model

```text
Request ctx ──WithContext──► *gorm.DB
                              │
                              ├─ Scopes (reuse filters)
                              ├─ Transaction (atomicity)
                              └─ Hooks (model lifecycle)
```

`*gorm.DB` is a chain of options; `Transaction` gives a `tx` that you **must** use inside the callback, not the outer `db`.

## Mechanism

### Transaction — real signature

```go
err := db.Transaction(func(tx *gorm.DB) error {
	if err := tx.Create(&order).Error; err != nil {
		return err // rollback
	}
	if err := tx.Create(&payment).Error; err != nil {
		return err
	}
	return nil // commit
})
```

You return `error` → rollback. You return `nil` → commit. Do not mix `db.Create` inside a transaction if you want it to be part of the same TX — use `tx`.

**Trace:** Create order OK on `tx`, Create payment error → order is not visible afterward (rollback). Predict: `db.First(&order, id)` after the error → `ErrRecordNotFound`.

### Predict-then-answer: wrong handle

```go
db.Transaction(func(tx *gorm.DB) error {
	return db.Create(&order).Error // uses db, not tx!
})
```

**What happens?** Create often goes outside the transaction (auto-commit path). Rollback of the callback does not undo that Create.  
**Fix:** always `tx.Create`.

### Hooks — real names

GORM calls methods on the model, e.g.:

```go
func (p *Product) BeforeCreate(tx *gorm.DB) error {
	if p.ID == 0 {
		// assign UUID or leave serial
	}
	if p.Slug == "" {
		p.Slug = slugify(p.Name)
	}
	return nil
}

func (p *Product) AfterCreate(tx *gorm.DB) error {
	// e.g. outbox row — careful with side effects
	return nil
}
```

There are also `BeforeUpdate`, `AfterUpdate`, `BeforeDelete`, `AfterDelete`, `BeforeSave`, `AfterSave`, `AfterFind` — use the documented ones. Do not invent `BeforeFetch`.

Hooks receive `tx *gorm.DB` — use it for additional queries in the same transaction.

### Danger of hooks

- Side effect (HTTP call) in `AfterCreate` + later rollback = a false world.
- Heavy logic in hooks hides the flow from the reader.
- Prefer explicit service methods for business; hooks for cross-cutting small things (timestamp, slug).

`CreatedAt` / `UpdatedAt` with `gorm.Model` already covered by GORM — do not duplicate.

### Scopes

```go
func Paid(db *gorm.DB) *gorm.DB {
	return db.Where("status = ?", "paid")
}

func LastN(n int) func(db *gorm.DB) *gorm.DB {
	return func(db *gorm.DB) *gorm.DB {
		return db.Order("id DESC").Limit(n)
	}
}

db.Scopes(Paid, LastN(10)).Find(&orders)
```

Scope = a function that returns `*gorm.DB`. Stacking filters without copy-paste Where.

### WithContext

```go
ctx, cancel := context.WithTimeout(r.Context(), 3*time.Second)
defer cancel()

err := db.WithContext(ctx).First(&product, id).Error
```

Cancel / timeout propagates to the driver (depending on driver support). In an HTTP handler always bind to `r.Context()`.

### Combination

```go
err := db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
	if err := tx.Scopes(Paid).First(&order, id).Error; err != nil {
		return err
	}
	order.Status = "refunded"
	return tx.Save(&order).Error
})
```

### Soft delete + hooks

With `gorm.Model` / `DeletedAt`, `Delete` does soft delete. `BeforeDelete` is still called. `Unscoped().Delete` does hard delete — consciously.

### Session options (mention)

```go
tx := db.Session(&gorm.Session{SkipHooks: true})
```

Exists for special cases (data import). Do not use it as an excuse to turn off all hooks forever.

### Logger and Transaction

In dev, the log shows `BEGIN`, queries, `COMMIT`/`ROLLBACK`. Learn to read that trace.

### Nested transactions

GORM uses savepoint patterns in some cases — do not rely on “nested” without reading docs for your version. Prefer one clear Transaction boundary per use-case.

## Rules and syntax

- In the `Transaction` callback use `tx`, not the outer `db`.
- `return err` → rollback; `return nil` → commit.
- Hooks: documented method names on the model.
- Side effects in hooks = caution with rollback.
- Scopes: `func(*gorm.DB) *gorm.DB`.
- `WithContext(ctx)` on every request path.
- Soft delete: know the difference `Delete` vs `Unscoped`.

## Examples

### Example 1 — Order + Payment atomically

```go
err := db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
	if err := tx.Create(&order).Error; err != nil {
		return err
	}
	payment.OrderID = order.ID
	return tx.Create(&payment).Error
})
```

#### What happens here

`WithContext` attaches `ctx` to the session, and `Transaction` runs the callback on `tx`. Both `Create` calls use `tx`, so the order row and the payment row are in one transaction. Returning an error rolls that transaction back; returning nil commits it. The payment insert runs only after the order insert returns nil, and it stores `order.ID` in `payment.OrderID`.

### Example 2 — BeforeCreate slug

```go
func (p *Product) BeforeCreate(tx *gorm.DB) error {
	if p.Slug == "" {
		p.Slug = strings.ToLower(strings.ReplaceAll(p.Name, " ", "-"))
	}
	return nil
}
```

#### What happens here

GORM calls `BeforeCreate` on the product before the INSERT and passes the open transaction as `tx`. If `Slug` is empty, the method sets it from `Name` by lowercasing and replacing each space with a hyphen. Returning nil tells GORM to continue the create with that field already set. This body does not run a query; `tx` is there for hook work that must share the same transaction.

### Example 3 — Active scope

```go
func Active(db *gorm.DB) *gorm.DB {
	return db.Where("active = ?", true)
}
```

#### What happens here

`Active` matches the scope type `func(*gorm.DB) *gorm.DB`. It adds `Where("active = ?", true)` and returns the chain, with `true` bound as a placeholder rather than pasted into the SQL text. Invoking the function does not execute a query by itself. A later `Find`, `First`, or similar call is what sends the statement.

### Example 4 — Timeout

```go
ctx, cancel := context.WithTimeout(context.Background(), time.Second)
defer cancel()
err := db.WithContext(ctx).Where("name = ?", name).First(&p).Error
```

#### What happens here

`WithTimeout` cancels this context after one second, and `defer cancel()` stops the timer when the surrounding function returns. `WithContext` passes that context into `First`, so the query has a deadline. A driver that honors context can then return a context error instead of waiting with no limit. The parent is `context.Background()`, and `name` is supplied through a placeholder.

### Example 5 — AfterCreate trap

```go
func (o *Order) AfterCreate(tx *gorm.DB) error {
	return httpPostWebhook(o.ID) // BAD if TX later fails
}
```

#### What happens here

`AfterCreate` runs after the INSERT. The method calls `httpPostWebhook` and returns that error, so a webhook failure fails the create. The comment points at the other half of the hazard: if the webhook returns nil and a later step in the same transaction fails, the HTTP call has already been made and rollback does not undo it. A network side effect in this hook is tied to a database result that may still be rolled back.

Better: outbox table in the same TX, worker sends the webhook.

### Example 6 — SkipHooks import

```go
return db.Session(&gorm.Session{SkipHooks: true}).Create(&legacyRows).Error
```

#### What happens here

`Session` with `SkipHooks: true` returns a session that does not run model hooks. `Create` on that session inserts `legacyRows` without `BeforeCreate`, `AfterCreate`, or the other hook methods. The error from `Create` is returned, so a failed insert is visible to the caller. This option applies to the session used here, not as a permanent switch on every future use of the original `db`.

## Decision analysis

| Tool | When |
|------|------|
| Transaction | more than one write that must go together |
| Hook | small, local on the model |
| Service method | rich domain / side effects |
| Scope | repeated filters |
| WithContext | every request/job with cancel |

## Trade-offs

- Hidden hooks vs explicit service.
- Long transactions vs locks.
- Scope abstraction vs readable Where in place.

## Common mistakes

1. **Wrong:** `db.Create` inside a Transaction callback.  
   **Effect:** outside TX.  
   **Why:** wrong handle.  
   **Fix:** `tx.Create`.

2. **Wrong:** ignoring error from Transaction.  
   **Effect:** you think it committed.  
   **Why:** error discarded.  
   **Fix:** check `err`.

3. **Wrong:** HTTP in AfterCreate.  
   **Effect:** side effect with rollback.  
   **Why:** hook ordering.  
   **Fix:** outbox.

4. **Wrong:** invented hook `BeforeFetch`.  
   **Effect:** does not work.  
   **Why:** not API.  
   **Fix:** `AfterFind` or service.

5. **Wrong:** without WithContext.  
   **Effect:** query lives after cancel.  
   **Why:** no ctx.  
   **Fix:** `WithContext`.

6. **Wrong:** huge TX over an HTTP call.  
   **Effect:** locks.  
   **Why:** long critical section.  
   **Fix:** narrow TX.

7. **Wrong:** Scope with side-effect mutation of global db.  
   **Effect:** filter leakage.  
   **Why:** bad pattern.  
   **Fix:** clean scope return.

8. **Wrong:** Unscoped Delete “for cleanup” in prod without audit.  
   **Effect:** data loss.  
   **Why:** hard delete.  
   **Fix:** procedure + backup.

## Idiomatic Go

- Use-case function opens Transaction.
- Model hooks thin.
- ctx first argument of the service method: `func (s *Store) PlaceOrder(ctx context.Context, ...)`.
- Scopes in `store/scopes.go`.

## Practical scenario

PlaceOrder wrote order then charge. Charge failed — “ghost” orders remained. Fix: one Transaction. Webhook in AfterCreate sent email then TX failed on another step — email went, order vanished. Fix: outbox row in TX, mailer reads outbox.

Timeout: a slow report query without ctx held connections. Fix: `WithContext` + statement timeout.

## Check questions

1. **How do you do rollback in a GORM Transaction?**  
   Return a non-nil error from the callback.

2. **Which handle do you use in the callback?**  
   `tx *gorm.DB`.

3. **Name two real hooks.**  
   E.g. `BeforeCreate`, `AfterDelete`.

4. **What is a scope?**  
   `func(*gorm.DB) *gorm.DB` for reusing filters.

5. **What is WithContext for?**  
   Passes cancel/timeout into queries.

6. **Why does HTTP in AfterCreate hurt?**  
   Side effect can remain after rollback.

7. **What does SkipHooks do?**  
   Skips hooks in that session.

8. **Soft delete vs Unscoped Delete?**  
   Soft marks DeletedAt; Unscoped deletes the row.

When a “transaction does not work”, look for `db` instead of `tx`. When a hook “does not fire”, check the method name and that SkipHooks is not set. When a query ignores cancel, look for WithContext.

### Additional mechanism: isolation and expectations

GORM Transaction uses the driver’s/database’s default isolation level (e.g. Postgres Read Committed). Do not assume Serializable. If you need a stricter level, that is SQL/`SET TRANSACTION` territory — read driver docs, do not invent a GORM method.

### Trace: panic in Transaction

If the callback panics, GORM tries to rollback (usual behavior). Still, do not rely on panic as control flow — return `error`.

### Predict-then-answer: Scopes order

```go
db.Scopes(Paid).Where("cents > ?", 100).Scopes(LastN(5))
```

Where and Scope stack into a chain. Exact SQL depends on call order. Check the logger. Predict that both filters exist in the same SELECT.

### Context cancel mid-Transaction

If ctx expires during TX, the driver may break the connection / rollback. Design TX short. Do not hold TX while waiting for external HTTP.

### Hook error

```go
func (p *Product) BeforeCreate(tx *gorm.DB) error {
	return errors.New("slug empty")
}
```

Create will not succeed; the error propagates. That is a valid validation style, but complex validation often stays in the service layer for clear API errors.

### Testing Transaction

In a test:

1. Open TX (or use db + truncate).
2. Call a use-case that fails on the second step.
3. Assert the first entity does not exist.

Without this test, the `db` vs `tx` regression returns.

### Advanced PR checklist

1. Transaction uses `tx`
2. Hooks thin / no HTTP
3. WithContext on request path
4. Scopes clean
5. Soft delete intent documented
6. SQL log review in dev

### Link to the Mongo lesson

SQL TX ≠ Mongo single-document atomicity ≠ multi-doc transactions (Mongo supports multi-doc TX under conditions). Do not transfer GORM habits blindly — the next course builds a different mental model.


## Mechanism — Transaction trace with values

### Success

```go
err := db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
	if err := tx.Create(&order).Error; err != nil {
		return err
	}
	return tx.Create(&Item{OrderID: order.ID, SKU: "A", Cents: 100}).Error
})
```

```text
BEGIN → INSERT orders id=42 → INSERT items → COMMIT → err=nil
```

### Failure of the second Create

```text
BEGIN → INSERT orders → INSERT items ERROR → ROLLBACK
SELECT orders WHERE id=42 → no row
```

**Predict:** Inside `db.Create` for items, `tx.Create` for order — after “rollback”?

**Answer:** Items via `db` may remain committed; order vanishes → orphan / FK error. Always `tx`.

### Locking (qty=1, two checkouts)

```go
import "gorm.io/gorm/clause"

err := db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
	var p Product
	if err := tx.Clauses(clause.Locking{Strength: "UPDATE"}).First(&p, id).Error; err != nil {
		return err
	}
	if p.Qty < n {
		return fmt.Errorf("insufficient stock")
	}
	return tx.Model(&p).Update("qty", p.Qty-n).Error
})
```

```text
T1: FOR UPDATE qty=1; UPDATE 0; COMMIT
T2: waits for lock; sees qty=0; insufficient; ROLLBACK
```

Without a lock both pass the check → overselling.

### Hook Create order (simplified)

```text
BeforeSave → BeforeCreate → INSERT → AfterCreate → AfterSave
```

**Predict:** BeforeCreate returns error — was INSERT done?

**Answer:** No.

### Hook + TX

The hook receives `tx *gorm.DB`. Extra DB work in the hook goes through that `tx`, not the outer `db`.

### Anti-hook: network in AfterCreate

```go
func (o *Order) AfterCreate(tx *gorm.DB) error {
	return sendEmail(o.Email) // BAD
}
```

Problems: flaky, slow, side-effect with later rollback. Better outbox in the same TX.

### Scopes — continued

```go
func Active(db *gorm.DB) *gorm.DB {
	return db.Where("active = ?", true)
}
func BySKU(sku string) func(*gorm.DB) *gorm.DB {
	return func(db *gorm.DB) *gorm.DB {
		return db.Where("sku = ?", sku)
	}
}
db.Scopes(Active, BySKU("ABC")).Find(&products)
```

**Predict WHERE:** `active = true AND sku = $1`. Scope without I/O.

### Context cancel

```go
ctx, cancel := context.WithTimeout(r.Context(), 50*time.Millisecond)
defer cancel()
err := db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
	return tx.Exec(`SELECT pg_sleep(1)`).Error
})
```

Expect a context error; that is why WithContext is not decoration.

### gorm.Expr

```go
tx.Model(&stock).Update("qty", gorm.Expr("qty - ?", n))
```

`SET qty = qty - $1` — with lock/condition more atomic than read-modify in Go.

### Outbox

```go
err := db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
	if err := tx.Create(&order).Error; err != nil {
		return err
	}
	return tx.Create(&Outbox{Topic: "order.created", Payload: order.ID}).Error
})
// worker sends email off the request path
```

### Idempotency in TX

```go
err := db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
	var existing Idempotency
	err := tx.Where("key = ?", in.Key).First(&existing).Error
	if err == nil {
		return nil
	}
	if !errors.Is(err, gorm.ErrRecordNotFound) {
		return err
	}
	if err := tx.Create(&order).Error; err != nil {
		return err
	}
	return tx.Create(&Idempotency{Key: in.Key, OrderID: order.ID}).Error
})
```

TX = atomicity of one attempt; idempotency = protection from duplicate HTTP retry.

### DryRun + Scope

```go
stmt := db.Session(&gorm.Session{DryRun: true}).Scopes(Active).Find(&Product{})
fmt.Println(stmt.Statement.SQL.String(), stmt.Statement.Vars)
```

### Soft delete + Delete

`Delete` often `UPDATE deleted_at`. `Unscoped().Delete` = hard delete. `BeforeDelete` is still called — test it.

### Nested TX

GORM can savepoint — do not rely on intuition. One clear TX per use-case.

### SkipHooks

```go
db.Session(&gorm.Session{SkipHooks: true}).Create(&legacyRows)
```

Only for import/special case.

## Decision analysis — extended

| Decision | Motive |
|----------|--------|
| One TX per use-case | clear rollback |
| FOR UPDATE + index | prevents race on stock |
| Outbox | reliable side-effect |
| Small hook | local invariant |
| WithContext | cancel/timeout |
| Scope vs repo | horizontal filter vs use-case |

## Trade-offs — continued

| Tool | Gain | Cost |
|------|------|------|
| Transaction | Atomicity | Lock |
| Hooks | Central rules | Hidden flow |
| Scopes | DRY | Indirection |
| FOR UPDATE | Anti-race | Waiting / deadlock risk |
| Outbox | Reliable event | Table + worker |
