# 10.06 Modifying schemas: AutoMigrate is not a production migration

> **Go Path - Zero to Gopher** / **03 Others → GORM: An Object Relational Mapper for Go** / Lesson 10.06

## Lesson goals

After this lesson you should be able to:

- explain what `AutoMigrate` does and what it **does not** do (does not drop columns)
- separate the dev convenience from the production migration process
- choose a versioned tool (`golang-migrate`, `gormigrate`, or hand-written SQL) without invented APIs
- plan additive changes (new column) vs breaking changes (rename/drop)
- connect the AutoMigrate warning from 10.01/10.02 with practice

## Prerequisite

- 10.01–10.05
- Basic SQL DDL (`ALTER TABLE`)
- Docker Compose Postgres from course 08 (preferred)

## Problem this lesson solves

Beginner flow:

```go
db.AutoMigrate(&User{}, &Order{})
```

in `main` and in production. Consequences:

- competition of multiple replicas changing the schema at the same time;
- silent addition of columns without code review of DDL;
- **deleting a field from the struct does not delete the column in the database** — waste / confusion remains;
- renaming a field = new column + old empty one, data “disappears” from the ORM view;
- no rollback strategy.

AutoMigrate is a **dev/prototype** helper, not a migration framework.

## Mental model

```text
Dev laptop          Staging/Prod
─────────────       ─────────────────────────────
AutoMigrate OK      Versioned SQL / migration tool
                    (golang-migrate, gormigrate, ...)
                    One-way (or planned) deploy
                    Review DDL in the PR
```

Three truths:

1. AutoMigrate **adds** missing tables/columns/indexes (within its capabilities).
2. AutoMigrate **does not drop** columns / tables to “follow” the struct.
3. Production requires **named, versioned** migrations with an audit trail.

## Mechanism

### What AutoMigrate really does

```go
err := db.AutoMigrate(&Product{})
```

GORM compares the model with the schema and tries to align: creates the table if missing, adds missing columns, indexes from tags as needed.

**Does not do (important):**

- does not delete column `old_name` when you remove the field from the struct;
- is not a reliable tool for rename;
- is not a substitute for data migrations (mass `UPDATE ...`).

### Trace: removing a field

1. Struct has `Nickname string`.
2. AutoMigrate → column `nickname`.
3. You remove the field from the struct, AutoMigrate again.
4. Column `nickname` **remains** in Postgres.
5. `SELECT *` in the DB console still shows the column; GORM no longer maps it.

**Predict-then-answer:** Does AutoMigrate delete `nickname`?  
**Answer:** No.

### Trace: “rename” via AutoMigrate

1. Field `Name` → column `name` with data.
2. You rename to `FullName` in the struct.
3. AutoMigrate adds `full_name` (empty); `name` remains with old data.
4. The application reads empty `FullName` — looks like data loss.

Fix: a real migration `ALTER TABLE ... RENAME COLUMN` or `ADD` + `UPDATE` + later `DROP` in separate releases.

### Versioned tools (real projects, no fake API)

**golang-migrate** (`github.com/golang-migrate/migrate`): files `0001_init.up.sql`, `0001_init.down.sql`; CLI `migrate -path ... -database ... up`.

**gormigrate** (`github.com/go-gormigrate/gormigrate/v2`): migrations as Go functions with GORM `*gorm.DB`.

**Hand-written SQL** in CI: you apply DDL scripts with review.

The course does not teach invented methods — you pick one tool and read its documentation. The point of the lesson: **process**, not memorizing the whole CLI.

### Expand / contract pattern

Breaking changes with zero downtime:

1. **Expand:** add a new column (nullable or with default).
2. Deploy code that writes to both / reads from the new one.
3. Backfill data.
4. **Contract:** remove the old code path; later drop the old column with a migration.

AutoMigrate can partially “expand” (ADD); “contract” drop does not do by itself.

### Multiple replicas and AutoMigrate

Three pods start at once, all call AutoMigrate. Risk: races on DDL. A migration job as **one** init/Job in Kubernetes, or a CI migrate step before rollout, is more reliable.

### Dev UX: AutoMigrate locally

```go
if os.Getenv("APP_ENV") == "dev" {
	if err := db.AutoMigrate(&User{}, &Order{}); err != nil {
		log.Fatal(err)
	}
}
```

Production: migration step, not this block.

### Indexes and tags

```go
Email string `gorm:"uniqueIndex"`
```

AutoMigrate can add an index in dev. In prod: explicit migration `CREATE UNIQUE INDEX` so you know the name and concurrency options (`CONCURRENTLY` on Postgres — carefully, outside a transaction).

### Predict-then-answer: dropping a table

**Question:** You delete `type Order struct` from the code and call AutoMigrate only for `User`. Does table `orders` disappear?

**Answer:** No. AutoMigrate does not drop tables that are not in the call.

### Recording the schema

Keep a `schema.sql` dump or a migrations folder as the source of truth. Struct tags describe the ORM’s **wish**; migrations describe the database’s **reality**.

## Rules and syntax

- AutoMigrate = dev / local bootstrap.
- Production = versioned migrations (SQL or gormigrate).
- AutoMigrate does not drop columns — say that out loud in PR review.
- Rename = planned migration + backfill, not only changing the struct name.
- One migration runner in deploy, not every replica AutoMigrate.
- Review DDL as code.

## Examples

### Example 1 — Dev only AutoMigrate

```go
func migrateIfDev(db *gorm.DB) error {
	if os.Getenv("APP_ENV") != "dev" {
		return nil
	}
	return db.AutoMigrate(&User{}, &Product{})
}
```

### Example 2 — golang-migrate up SQL sketch

```sql
-- 0002_add_products_cents.up.sql
ALTER TABLE products ADD COLUMN cents bigint NOT NULL DEFAULT 0;
```

```sql
-- 0002_add_products_cents.down.sql
ALTER TABLE products DROP COLUMN cents;
```

#### What happens here

Explicit DDL, reversible down, auditable in git.

### Example 3 — Dangerous main

```go
func main() {
	db, _ := gorm.Open(...)
	_ = db.AutoMigrate(&User{}) // BAD in prod binary without protection
}
```

### Example 4 — Detecting a zombie column

```sql
SELECT column_name FROM information_schema.columns
WHERE table_name = 'products';
```

Compare with struct fields. Excess = candidate for a contract migration.

### Example 5 — Zero downtime rename (phases)

1. Migration: `ADD COLUMN full_name`.
2. Code writes `name` and `full_name`.
3. Backfill: `UPDATE ... SET full_name = name`.
4. Code reads `full_name`.
5. Later: `DROP COLUMN name`.

## Decision analysis

| Approach | When |
|----------|------|
| AutoMigrate | local sandbox, spike |
| SQL migrate files | clear DDL, DBA review |
| gormigrate | you like Go and GORM in migrations |
| Managed schema (Ent, etc.) | out of scope — do not mix |

## Trade-offs

- Dev speed vs prod discipline.
- Down migrations often hard (data loss) — teams sometimes do not use them in prod.
- `CONCURRENTLY` indexes vs transaction simplicity.

## Common mistakes

1. **Wrong:** AutoMigrate in prod `main`.  
   **Effect:** uncontrolled DDL.  
   **Why:** no version/review.  
   **Fix:** migration step.

2. **Wrong:** believing removing a field drops the column.  
   **Effect:** zombie columns.  
   **Why:** AutoMigrate does not drop.  
   **Fix:** explicit DROP migration.

3. **Wrong:** rename only in the struct.  
   **Effect:** “lost” data.  
   **Why:** new column empty.  
   **Fix:** RENAME/backfill plan.

4. **Wrong:** all replicas migrate.  
   **Effect:** races / locks.  
   **Why:** parallel DDL.  
   **Fix:** one job.

5. **Wrong:** mixing manual ALTER and AutoMigrate.  
   **Effect:** drift.  
   **Why:** two sources of truth.  
   **Fix:** one process.

6. **Wrong:** no down/rollback story.  
   **Effect:** panic in an incident.  
   **Why:** not planned.  
   **Fix:** expand/contract or restore.

7. **Wrong:** NOT NULL column without default on a large table.  
   **Effect:** long lock / fail.  
   **Why:** DDL + data.  
   **Fix:** phased migrate.

8. **Wrong:** ignoring uniqueIndex conflict on backfill.  
   **Effect:** migration fails.  
   **Why:** duplicates.  
   **Fix:** clean data before the constraint.

## Idiomatic Go

- `APP_ENV` / config flag around AutoMigrate.
- Migrations in `migrations/` in git.
- CI: `migrate up` before deploy.
- Struct tags and migrations must agree — review both.

## Practical scenario

A service in prod called AutoMigrate. A release removed the `LegacyCode` field. The column stayed. A month later the DBA saw PII in a “dead” column — GDPR incident. Fix: explicit DROP in a migration + ban AutoMigrate in prod + policy check in CI (`grep AutoMigrate` in main package fails if not behind a `dev` guard).

## Check questions

1. **Does AutoMigrate drop columns?**  
   No.

2. **What is AutoMigrate for in dev?**  
   Fast schema bootstrap.

3. **What to use in prod?**  
   Versioned migrations (SQL/gormigrate/…).

4. **What happens on “rename” only in the struct?**  
   New column empty; old remains.

5. **Why one migration runner?**  
   Avoids DDL races.

6. **What is expand/contract?**  
   Phased schema change without downtime.

7. **Does AutoMigrate replace data migrations?**  
   No.

8. **Where to review DDL?**  
   In the PR with the code.

When data “disappears” after a model change, first look at the schema in the database, not only the struct. When prod “changes tables by itself”, look for AutoMigrate in the startup path.

Schema is a contract. The ORM model is a view. A migration is a change to the contract.

### Additional mechanism: migration order and GORM models

Deploy order that works:

1. Migration ADD nullable column
2. Rollout code that reads/writes the new column
3. Backfill job
4. Migration SET NOT NULL / index
5. Remove old code path

Wrong order: code expects a column before the migration runs → panic in prod.

### Trace: two application versions during rollout

While a rolling update runs, old and new pods run at the same time. The schema must support **both** codes (expand phase). That is why you do not drop a column in the same release you stop writing to it — wait for the next one.

### Predict-then-answer: AutoMigrate and uniqueIndex on dirty data

**Question:** You add `gorm:"uniqueIndex"` on `Email`, AutoMigrate on staging. The table already has duplicate emails. What happens?

**Answer:** Creating the unique index fails. AutoMigrate returns an error. You must first clean data with SQL, then the constraint.

### Shadow database in CI

Design: bring up Postgres in Compose, `migrate up`, `go test` — proof that migrations + models work. That connects 08.03, 09.03, and this lesson.

### Documenting a breaking schema

In CHANGELOG:

```text
## DB
- ADD products.cents
- BACKFILL from price_float (script)
- DROP products.price_float (from v1.5)
```

Without this an ORM PR looks like “a little struct” and is actually data ops.

### Migration checklist in a PR

1. Up SQL
2. Down SQL or explicit “down unsupported”
3. Backfill plan
4. Expand/contract note
5. AutoMigrate not in prod path
6. Model tags aligned

### More on “does not drop columns”

Repeat until automatic: **AutoMigrate does not drop columns.** That is the most common myth. Write it in code review comments until it becomes culture.


## Mechanism — AutoMigrate is not a production migration (deepened)

### Official rule (gorm.io)

AutoMigrate:

- creates missing tables;
- adds missing columns / indexes / constraints where it can;
- **does not delete** unused columns (*will NOT delete unused columns*).

That protects data — and that is why it is **not** a lifecycle tool for production.

### What production needs that AutoMigrate does not give

| Need | AutoMigrate | Versioned migration |
|------|-------------|---------------------|
| SQL review in PR | no | yes |
| Rename preserving data | no | yes (`RENAME COLUMN`) |
| Controlled DROP | no | yes |
| Rollback / forward-fix | no | yes |
| One runner in cluster | often abused | Job / CI |
| Schema history | no | yes |
| Backfill + NOT NULL in steps | no | yes |

### Predict: dropping a field

```go
// v1
type Product struct{ ID uint; SKU string; LegacyCode string }
db.AutoMigrate(&Product{})
// v2 — LegacyCode removed
type Product struct{ ID uint; SKU string }
db.AutoMigrate(&Product{})
```

**Answer:** column `legacy_code` **remains**. Only:

```sql
ALTER TABLE products DROP COLUMN IF EXISTS legacy_code;
```

### Predict: rename

```text
Model Name → Title
AutoMigrate: ADD title; name remains; data does not move
```

Correct:

```sql
ALTER TABLE products RENAME COLUMN name TO title;
```

or expand/contract without downtime.

### Cluster trap

```text
3 replicas → each AutoMigrate in main → DDL race → lock/timeout
```

Correct: **one** Job / init container / CI `migrate up`, not a side-effect of every API pod.

### Correct order

```text
1. SQL/gormigrate migration
2. Update GORM model = new state
3. Same PR: DDL + model
4. CI: migrate → test → deploy
```

## Mechanism — expand/contract with numbers

Scenario: `name` → `title`, 2_000_000 rows, zero-downtime.

1. **Expand:** `ADD COLUMN title TEXT NULL`
2. Deploy: read title??name; write to both
3. **Backfill:** `UPDATE … SET title = name WHERE title IS NULL` (batch by id)
4. `ALTER … SET NOT NULL`
5. Deploy: title only
6. **Contract:** `DROP COLUMN name`

**Predict:** DROP while old code still SELECTs `name`?

**Answer:** Old pods fail on a SQL error. Contract waits until all instances are on the new code.

## Example — golang-migrate style

```text
migrations/
  0001_init.up.sql
  0001_init.down.sql
  0002_add_weight.up.sql
  0002_add_weight.down.sql
```

```sql
-- 0002_add_weight.up.sql
ALTER TABLE products ADD COLUMN weight_grams INT NULL;
```

```sql
-- 0002_add_weight.down.sql
ALTER TABLE products DROP COLUMN IF EXISTS weight_grams;
```

```bash
migrate -path ./migrations -database "$DATABASE_URL" up
```

### gormigrate — explicit SQL

```go
{
	ID: "20260926_add_weight_grams",
	Migrate: func(tx *gorm.DB) error {
		if tx.Migrator().HasColumn(&Product{}, "WeightGrams") {
			return nil
		}
		return tx.Exec(`ALTER TABLE products ADD COLUMN weight_grams INT NULL`).Error
	},
	Rollback: func(tx *gorm.DB) error {
		return tx.Exec(`ALTER TABLE products DROP COLUMN IF EXISTS weight_grams`).Error
	},
},
```

### Migrator API (only in a migration script)

```go
db.Migrator().HasTable(&Product{})
db.Migrator().AddColumn(&Product{}, "WeightGrams")
db.Migrator().DropColumn(&Product{}, "LegacyCode")
db.Migrator().CreateIndex(&Product{}, "idx_name")
```

Not in an HTTP handler.

### CONCURRENTLY

```sql
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_items_order_id ON items(order_id);
```

On Postgres **not** in a transaction. Check your migration tool docs.

### Partial unique (soft delete)

```sql
CREATE UNIQUE INDEX ux_products_sku_active
ON products(sku) WHERE deleted_at IS NULL;
```

GORM `uniqueIndex` tag does not express this well — SQL wins.

### NOT NULL without backfill

```sql
ALTER TABLE products ADD COLUMN phone TEXT NOT NULL; -- fail on a full table
```

First NULL → backfill → NOT NULL.

### Immutable migrations

An applied migration is not edited. Add a new version (forward-fix).

### Dev guard

```go
func migrateIfDev(db *gorm.DB) error {
	if os.Getenv("APP_ENV") != "dev" {
		return nil
	}
	return db.AutoMigrate(&Product{}, &Order{})
}
```

### CI order

```yaml
- name: Migrate
  run: migrate -path ./migrations -database "$DATABASE_URL" up
- name: Deploy
  run: ./deploy.sh
```

### Docker: initdb vs migrate

`docker-entrypoint-initdb.d` only works on an empty volume. A living database → migrate job.

### Observability

```go
var v string
db.Raw(`SELECT version FROM schema_migrations ORDER BY version DESC LIMIT 1`).Scan(&v)
log.Printf("schema version=%s", v)
```

### Quick FAQ

**Q: Can AutoMigrate in CI for an ephemeral test database?**  
A: Yes, often — the database is thrown away after the job. That is not the same as AutoMigrate on shared staging/prod.

**Q: May gormigrate “call” AutoMigrate inside?**  
A: Technically yes, but for rename/drop/backfill still write explicit SQL. AutoMigrate inside gormigrate does not solve the no-drop rule.

**Q: What if down was never tested?**  
A: Do not rely on it in prod. Test down in DEV; in prod prefer forward-fix.

**Q: How to review large DDL?**  
A: Same PR as the model; checklist: nullable first, index CONCURRENTLY where needed, no DROP until code stops reading.
## Summary

AutoMigrate is convenient in development and **does not drop** columns. Production needs versioned migrations, DDL review, and careful rename/drop plans. One runner, expand/contract for zero downtime, never blind AutoMigrate in prod `main`.
