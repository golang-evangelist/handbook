# 10.03 Creating, updating, and deleting records

> **Go Path - Zero to Gopher** / **03 Others → GORM: An Object Relational Mapper for Go** / Lesson 10.03

## Lesson goals

After this lesson you should be able to:

- use `Create`, `Save`, `Updates`, `Update`, `Delete` correctly
- distinguish zero-value traps when using `Updates` with a struct versus a map and `Select`
- understand soft delete when the model has `DeletedAt` / `gorm.Model`
- use `Unscoped` when you truly need physical deletion or reading deleted rows
- write CRUD with `WithContext`, `.Error` checks, and `RowsAffected`
- predict the SQL trace for each of these operations before you open the Logger

## Prerequisite

- Lessons 10.01–10.02
- A model with or without a soft delete field
- Logger enabled while you practice (`logger.Info` locally)

## Problem this lesson solves

Beginners call `Save` for everything, or `Updates` with a struct and wonder why `false` / `0` / `""` were not written. GORM when updating with a struct by default **skips zero value** fields. That is not a “random bug” — it is documented behavior that prevents accidental overwrites, but breaks patch APIs that send `active=false`.

Soft delete confuses the second wave: `Delete` does not remove the row physically, and `Find` / `First` do not return it. Teams think the row “vanished”, while a unique constraint still sees the soft-deleted SKU. Without a clear model you lose data or get “ghost” rows.

## Mental model

| Method | Intent | Zero values |
|--------|--------|-------------|
| `Create` | INSERT a new row | are written (including zero where it makes sense) |
| `Save` | saves the whole record by primary key | writes zero too |
| `Updates` + struct | partial update | **skips** zero fields |
| `Updates` + map | partial update | **includes** zero if they are in the map |
| `Update` | one column | explicit value |
| `Delete` | soft or hard | depends on `DeletedAt` |

Soft delete: `Delete` sets `deleted_at`. The default scope adds `WHERE deleted_at IS NULL` on reads.

Remember one sentence:

> Struct Updates = “write only non-zero”. Map Updates = “write exactly these fields”.

## Mechanism

### 1. `Create` — INSERT and returning the ID

`Create` takes a pointer to a struct, builds an INSERT from non-zero (and configured) fields, executes it, and fills the primary key back into the same object.

```go
p := model.Product{SKU: "ABC", Name: "Filter", Cents: 1200}
err := db.WithContext(ctx).Create(&p).Error
// after success: p.ID is filled
```

**Predict SQL (Postgres, simplified):**

```sql
INSERT INTO "products" ("sku","name","cents","created_at","updated_at")
VALUES ('ABC','Filter',1200,'...','...')
RETURNING "id"
```

If you forget `&`, the ID will not return into your variable the way you expect. Always `Create(&p)`.

**Predict error** on a second Create with the same unique SKU: driver error (unique violation). Map to 409 above the GORM layer; do not return raw SQL to the client.

### 2. `CreateInBatches` — fewer round-trips

```go
items := []model.Product{
	{SKU: "A", Name: "a", Cents: 1},
	{SKU: "B", Name: "b", Cents: 2},
	// ...
}
err := db.WithContext(ctx).CreateInBatches(items, 100).Error
```

**Predict:** instead of N separate INSERT round-trips, GORM sends batches of 100. Exact SQL form depends on dialect. Unique still applies — one bad row can fail the batch; plan a transaction (10.07) if you need atomicity of the whole set.

### 3. `Save` — full save including zero

`Save` saves the whole record. If the primary key exists, it does an UPDATE that **includes** zero values. If ID is missing / zero in some cases, it may go toward an insert flow — check docs for your version and always watch the Logger.

```go
p.Name = ""
p.Cents = 0
err := db.WithContext(ctx).Save(&p).Error
```

**Predict SQL:**

```sql
UPDATE "products"
SET "name"='',"cents"=0,"updated_at"=...
WHERE "id" = 1
```

**Danger:** if the struct is partially loaded (you did not `First` all columns Save touches), you will overwrite columns with old zeros. Rule: Save only over a complete aggregate in memory.

### 4. `Updates` with a struct — zero value trap (critical)

This is the most common production GORM bug.

```go
db.Model(&p).Updates(model.Product{
	Name:   "Novo",
	Active: false, // ZERO VALUE
	Cents:  0,     // ZERO VALUE
})
```

**Predict SQL:**

```sql
UPDATE "products"
SET "name"='Novo', "updated_at"=...
WHERE "id" = 1
```

Notice: no `active`, no `cents`. Features “deactivate” and “reset price to 0” silently do not work.

Why does GORM do this? So a random zero in a Go struct does not wipe columns you did not mean to touch. The intent is protection; the cost is a trap for patch APIs.

### 5. `Updates` with a map — explicit truth

```go
db.Model(&p).Updates(map[string]interface{}{
	"name":   "Novo",
	"active": false,
	"cents":  0,
})
```

**Predict SQL:**

```sql
UPDATE "products"
SET "name"='Novo', "active"=false, "cents"=0, "updated_at"=...
WHERE "id" = 1
```

A map is the idiomatic choice for partial updates with zero values. Less typed than a struct, but predictable.

### 6. `Select` forces columns (also with a struct)

```go
db.Model(&p).Select("Name", "Active").Updates(model.Product{
	Name:   "x",
	Active: false,
	Cents:  999, // outside Select — does not enter
})
```

`Select` narrows which columns go into the UPDATE. With a struct it can also force zero fields that are in the Select list — but map + clear column names often stays more readable in review. **Always** check the Logger; do not memorize edge cases of every version.

`Omit` on Save:

```go
db.Omit("CreatedAt").Save(&p)
```

**Predict:** `created_at` is not in the SET list.

### 7. `Update` — one column

```go
db.Model(&p).Update("name", "solo")
```

**Predict:**

```sql
UPDATE "products"
SET "name"='solo', "updated_at"=...
WHERE "id" = 1
```

Useful when you truly touch one field. For multiple fields with zero — map.

### 8. Soft delete — what really happens

Model with `DeletedAt`:

```go
type Product struct {
	ID        uint
	SKU       string
	DeletedAt gorm.DeletedAt `gorm:"index"`
}
```

```go
err := db.WithContext(ctx).Delete(&p).Error
```

**Predict SQL — not DELETE FROM:**

```sql
UPDATE "products"
SET "deleted_at"='2026-09-26 ...'
WHERE "id" = 1
```

Then reading:

```go
err := db.First(&found, p.ID).Error // ErrRecordNotFound
```

**Predict SELECT:**

```sql
SELECT * FROM "products"
WHERE "id" = 1
AND "deleted_at" IS NULL
LIMIT 1
```

The row exists in the table. The scope hides it. That is soft delete.

### 9. `Unscoped` — hard delete and visibility of deleted rows

```go
db.Unscoped().Delete(&p)
```

**Predict:**

```sql
DELETE FROM "products" WHERE "id" = 1
```

Reading including soft-deleted:

```go
db.Unscoped().Where("id = ?", id).First(&p)
```

**Predict SELECT** without `deleted_at IS NULL`.

Use for GDPR / admin purge. Plan related rows (order items) — otherwise debris or FK breakage remains.

### 10. Batch delete with Where

```go
res := db.WithContext(ctx).
	Where("active = ?", false).
	Delete(&model.Product{})
```

**Predict:** soft UPDATE `deleted_at` for all matching rows if the model has DeletedAt; otherwise a real DELETE. Be explicit with Where. Delete without a condition is dangerous.

Check `res.Error` and when needed `res.RowsAffected`.

### 11. `RowsAffected` — 404 semantics

```go
res := db.WithContext(ctx).Model(&model.Product{}).
	Where("id = ?", id).
	Updates(map[string]interface{}{"active": false})
if res.Error != nil {
	return res.Error
}
if res.RowsAffected == 0 {
	return gorm.ErrRecordNotFound
}
return nil
```

Useful when UX requires distinguishing “no row” vs “already false” (in the other case RowsAffected can be 0 even if the value is the same — depends on database/ORM; test it).

### 12. Unique + soft delete — hidden conflict

Scenario:

1. Create SKU=`ABC`.
2. Soft delete.
3. Create again SKU=`ABC`.

**Predict** with an ordinary unique index: the second Create fails — the soft-deleted row still holds the unique.

The solution often is not a GORM tag, but a SQL migration (10.06):

```sql
CREATE UNIQUE INDEX ux_products_sku_active
ON products(sku)
WHERE deleted_at IS NULL;
```

### 13. Pointer fields as an alternative to the zero trap

```go
type ProductPatch struct {
	Active *bool
	Cents  *int
}
```

`nil` = “do not touch”; `&false` / `&0` = “write zero”. GORM with pointer fields treats nil differently from zero. That can solve struct update, but complicates the model. Map update is often simpler for the team.

### 14. Unique error on Create — mapping

```go
err := db.WithContext(ctx).Create(&p).Error
if err != nil {
	// errors.As on pgconn.PgError / mysql — adapter layer
	return err
}
```

Do not swallow. Do not return `err.Error()` with SQL text to the client.

### 15. Context on all writes

```go
db.WithContext(ctx).Create(&p)
db.WithContext(ctx).Save(&p)
db.WithContext(ctx).Model(&p).Updates(m)
db.WithContext(ctx).Delete(&p)
```

Without context: the request is canceled, the query still holds a connection. Habit from 10.01; here it is mandatory on the write path.

### 16. Step-by-step: feature “deactivate product”

1. Handler receives JSON `{"active": false}`.
2. Wrong: `Updates(Product{Active: false})`.
3. **Predict:** SET without `active`.
4. Logger confirms.
5. Fix: map `{"active": false}`.
6. **Predict:** SET with `active=false`.
7. An integration test with `false` and `0` must exist — otherwise the regression returns.

### 17. Step-by-step: soft delete audit path

1. Create a product; remember the ID.
2. `Delete(&p)`.
3. **Predict:** UPDATE deleted_at, not DELETE FROM.
4. `First` → `ErrRecordNotFound`.
5. `Unscoped().First` → the row is there, DeletedAt set.
6. Admin API uses Unscoped; public API does not.
7. `Unscoped().Delete` → physically gone; **predict** DELETE FROM.

### 18. Save vs Updates — decision table

| Situation | Choice | Why |
|-----------|--------|-----|
| Aggregate complete in memory | `Save` | writes zero too |
| Patch a few fields including zero | `Updates` map | explicit |
| Struct patch without zero | `Updates` struct | OK |
| One column | `Update` | narrowest SET |
| You do not know if the struct is complete | **do not** Save | overwrite risk |

### 19. Create with associations (preview 10.05)

```go
order := model.Order{
	Email: "a@b.com",
	Items: []model.Item{{SKU: "A", Cents: 100}},
}
err := db.Create(&order).Error
```

**Predict:** INSERT order, then INSERT items with OrderID. If the second fails outside a transaction, a partial record remains. Production → `db.Transaction` (10.07).

### 20. HTTP errors (adapter sketch)

```go
switch {
case errors.Is(err, gorm.ErrRecordNotFound):
	http.Error(w, "not found", 404)
default:
	if isUniqueViolation(err) {
		http.Error(w, "conflict", 409)
		return
	}
	http.Error(w, "db error", 500)
}
```

`isUniqueViolation` lives with driver codes — do not guess by string-matching messages.

### 21. Repository pattern SetActive

```go
func (r *ProductRepo) SetActive(ctx context.Context, id uint, active bool) error {
	res := r.db.WithContext(ctx).Model(&model.Product{}).
		Where("id = ?", id).
		Updates(map[string]interface{}{"active": active})
	if res.Error != nil {
		return res.Error
	}
	if res.RowsAffected == 0 {
		return gorm.ErrRecordNotFound
	}
	return nil
}
```

The handler does not choose between Save/Updates — it chooses a use-case method.

### 22. What the Logger must show in the exercise

For each operation write the predicted SQL **before** running:

1. Create
2. Save with Name=""
3. Updates struct with Active=false
4. Updates map with active=false
5. Delete soft
6. Unscoped Delete

If 3 and 4 give the same SQL — check model/version; they usually differ. If 5 looks like `DELETE FROM` — the model has no `DeletedAt`.

### 23. Link to AutoMigrate and late addition of DeletedAt

If you add `DeletedAt` later: AutoMigrate (DEV) adds the column; existing rows have NULL = “alive”. From then Delete does soft. Unique policy may need a migration (partial index) — that is not AutoMigrate magic.

### 25. Anti-pattern: “universal Save”

```go
// BAD as the only update path
func (r *Repo) Upsert(ctx context.Context, p *model.Product) error {
	return r.db.WithContext(ctx).Save(p).Error
}
```

If the handler fills only `ID` and `Active`, Save can wipe other fields with zeros. Better explicit methods: `Create`, `Patch`, `SetActive`.

## Rules and syntax

1. Always a pointer where the method fills fields (`Create(&p)`).
2. For partial update with zero values — **map**, not struct.
3. Soft delete: “not in Find” ≠ “not in the table”.
4. Hard delete / reading deleted → `Unscoped`.
5. Check `RowsAffected` when UX requires it.
6. Batch: `CreateInBatches`; delete with explicit `Where`.
7. Do not swallow unique errors — map them.
8. `WithContext` on the request path.
9. Do not mix Save on a partially filled struct.
10. Document the team soft delete policy.

### Syntax patterns

```go
db.WithContext(ctx).Create(&p)
db.WithContext(ctx).Save(&p)
db.WithContext(ctx).Model(&p).Updates(map[string]interface{}{"active": false})
db.WithContext(ctx).Model(&p).Update("name", "x")
db.WithContext(ctx).Delete(&p)
db.WithContext(ctx).Unscoped().Delete(&p)
```

## Decision analysis

### Soft delete everywhere?

Convenient for audit and undo. Complicates unique, reports, storage. Do not enable blindly via `gorm.Model`.

### Hard delete for GDPR

`Unscoped().Delete` + related data. Plan cascades in migrations.

### Save vs Updates map vs Update

Save = complete aggregate. Map patch = zero OK. Update = one column.

### Hooks BeforeDelete

Useful for local rules; do not put heavy network work (10.07).

## Trade-offs

| API | Gain | Cost |
|-----|------|------|
| Save | Simple, writes zero | Easy to overwrite fields |
| Updates map | Zero values OK | Less typed |
| Updates struct | Typed | Zero trap |
| Soft delete | Recovery from mistakes | Unique and “holes” |
| Hard delete | Clean | Irreversible |
| CreateInBatches | Throughput | Larger fail surface |

## Common mistakes

1. Struct `Updates` and `false` / `0` / `""`.
2. `Save` on a partially filled struct.
3. Expecting soft-deleted to vanish from the table.
4. Unique conflict with a soft-deleted row.
5. Ignoring `ErrRecordNotFound` vs other errors.
6. Delete without Where in a chain that accidentally widens scope.
7. Mixing soft and hard delete without `Unscoped` discipline.
8. Ignoring `RowsAffected` where UX requires 404.
9. Returning a raw SQL error string to the client.
10. Create without context on the HTTP path.

## Idiomatic Go

```go
type ProductRepo struct{ db *gorm.DB }

func (r *ProductRepo) Create(ctx context.Context, p *model.Product) error {
	return r.db.WithContext(ctx).Create(p).Error
}

func (r *ProductRepo) Patch(ctx context.Context, id uint, fields map[string]interface{}) error {
	res := r.db.WithContext(ctx).Model(&model.Product{}).Where("id = ?", id).Updates(fields)
	if res.Error != nil {
		return res.Error
	}
	if res.RowsAffected == 0 {
		return gorm.ErrRecordNotFound
	}
	return nil
}
```

The handler does not choose the GORM API — it chooses the repo use-case.

## Practical scenario

Feature “deactivate product” sends `active=false`. Developer uses `Updates(product)`. The field does not change; QA reports a bug. Fix: map update. At the same time a soft-deleted SKU prevents re-creation — they add a partial unique migration.

Admin “deletes” a product (`Delete`), support asks for data. The team learns `Unscoped` and builds an internal admin path with an audit log, not a public API.

Third episode: “universal Save” in the repo wipes columns with zeros. They move to `Patch(map)` and ban Save outside a complete aggregate.

### One more predict-then-answer (CRUD)

```go
p := Product{ID: 1, Name: "x", Active: true}
db.Model(&p).Updates(Product{Active: false})
```

**Predict SQL:** does `active` enter the SET?

**Answer:** Typically **no** — `false` is the zero value for bool in struct Updates. Use map `{"active": false}` or `Select("Active").Updates(...)`.

### Mini CRUD checklist

1. Create checks Error
2. Patch with zero → map/Select
3. Save only when you have a full model
4. Soft delete intent clear
5. RowsAffected when API wants 404
6. WithContext on writes

### Closing sentence

Zero value is not an “empty update” — for GORM `Updates` with a struct it is a trap. Remember map/Select before a production patch endpoint.

### One line to memorize

`Updates(struct)` ≠ `Updates(map)` when you send `false` or `0`.

## Summary

CRUD in GORM requires a conscious choice of `Create` / `Save` / `Updates` / `Delete`. The zero value trap on struct `Updates` is critical — for a patch with `false`/`0` use a map or `Select`. Soft delete changes the meaning of Delete/Find and affects unique. Use `Unscoped` for real deletion, `WithContext` on writes, and a repository to isolate details.
