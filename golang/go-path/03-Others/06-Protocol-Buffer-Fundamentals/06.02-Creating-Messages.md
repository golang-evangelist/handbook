# 06.02 Creating protobuf messages

> **Go Path - Zero to Gopher** / **03 Others → Protocol Buffer Fundamentals** / Lesson 06.02

## Lesson goals

After this lesson you will be able to:

- write `syntax = "proto3"` messages with fields and numbers;
- use scalars, `enum`, `repeated`, `map`, and `oneof`;
- choose types consciously for Go (e.g. `int64` for money in minor units);
- understand why **field numbers**, not names, are wire identity;
- use `reserved` consciously already while modeling (evolution details in 06.04);
- avoid common syntax and design mistakes in messages.

## Prerequisite

- 06.01 (why schema, wire numbers, compatibility as a goal).
- A text editor; `protoc` if possible (generate in 06.03).
- Go 1.22+.
- A basic feel for DTOs / domain models in Go.

## Problem this lesson solves

Badly modeled messages (string for everything, wrong numbers, abusing `oneof`, float for money) lead to painful migrations. This lesson gives a working vocabulary of proto3 constructs before code generation.

Typical symptoms of a bad model:

1. One giant `message` with 40 fields and no structure.
2. An enum where `0 = PAID` — a zero-value trap.
3. A `map` instead of a table / entity.
4. Field numbers assigned “as they come”, then reused later.
5. Names treated as if they were the wire contract — they are not.

## Mental model

```text
message = a set of fields
field   = type + name + number [= rules / comment]
number  = stable ID on the wire
name    = label for people + generated identifier
```

```text
syntax proto3
   └── package
         └── message / enum
               ├── scalar fields
               ├── nested message
               ├── repeated
               ├── map<K,V>
               ├── oneof { ... }
               └── reserved ...
```

The field number is the stable ID on the wire. The name is for people and generated identifiers. Renaming ≠ changing wire identity (but it breaks the local Go API until you regenerate / adapt the code).

### Terminology table

| Term | Meaning |
|--------|----------|
| `syntax = "proto3"` | the schema dialect this course uses |
| `package` | protobuf namespace (e.g. `shop.v1`) |
| field number | wire identity of the field |
| scalar | `string`, `bool`, `bytes`, integers, float types |
| `enum` | a closed set of named integer values |
| `repeated` | a list / sequence of values |
| `map<K,V>` | a map; K is limited to certain types |
| `oneof` | at most one of the listed fields is set |
| `reserved` | forbidden numbers and/or names |
| `optional` | presence tracking for scalars in proto3 |
| nested message | a `message` inside or as a field type |
| default (proto3) | zero value when the field is not on the wire |

## Mechanism

The mechanism of creating messages: from `syntax` to choosing a construct, through types, numbers, traces of wire behavior, and predictions before generate.

### 1. File skeleton — the order you memorize

```proto
syntax = "proto3";

package shop.v1;

option go_package = "example.com/shop/gen/shoppb;shoppb"; // details 06.03

// contract comments
message Product {
  string sku = 1;
  string title = 2;
  int64 price_minor = 3;
  bool active = 4;
}
```

Order in your head:

1. `syntax` — always proto3 in the course.
2. `package` — a version in the name (`v1`) helps evolution.
3. `option go_package` — for the Go import (06.03); put it early so you do not forget.
4. `message` / `enum` — the domain model.
5. Numbers — consciously, not “auto”.

### 2. Field number is wire identity — mechanism, not decoration

On the wire the decoder asks: “what is the number?” not “what is it called?”.

Consequences:

- You can rename carefully; you do not reuse the number.
- Two fields with the same number in the same message = a schema error.
- Numbers 1–15 use a smaller tag on the wire (cheaper); 16+ a more expensive tag — use 1–15 for frequent fields, not for temporary debug.

```text
frequent field  -> small number (1..15) when you can
rare field      -> larger number OK
deleted         -> reserved (06.04), never “free it for something new”
```

### 3. Scalars and Go mapping (working subset)

| Proto | Typical Go (protoc-gen-go) | Note |
|-------|----------------------------|----------|
| `string` | `string` | UTF-8 |
| `bool` | `bool` | |
| `bytes` | `[]byte` | |
| `int32` | `int32` | |
| `int64` | `int64` | money minor, IDs as numbers |
| `uint64` | `uint64` | caution with JSON interop later |
| `float` / `double` | `float32` / `float64` | not for money |
| `fixed64` / `sfixed64` | fixed width | special cases |

The exact shape depends on the plugin version — always look at `*.pb.go` after generate.

**Money:** `int64 price_minor` + `string currency_code`, not `double price`.

### 4. Enum — a closed set with a zero value

```proto
enum OrderStatus {
  ORDER_STATUS_UNSPECIFIED = 0;
  ORDER_STATUS_PENDING = 1;
  ORDER_STATUS_PAID = 2;
  ORDER_STATUS_CANCELED = 3;
}

message Order {
  string id = 1;
  OrderStatus status = 2;
}
```

Zero mechanism:

- In proto3, 0 is the default when the field is not set.
- If `0 = PAID`, “I did not send status” looks like paid.
- Idiom: `*_UNSPECIFIED = 0`.

Prefixing values with the enum name reduces collisions in some languages and makes logs more readable.

### 5. repeated — a list

```proto
message Cart {
  string id = 1;
  repeated LineItem items = 2;
}

message LineItem {
  string sku = 1;
  int32 qty = 2;
}
```

- `repeated` preserves order (for messages/scalars in common use).
- In Go: a slice (`[]*LineItem` or similar — see generated).
- Empty list vs absence: in practice you often treat them as “no items”; do not build business logic on thin differences without presence discipline.

### 6. map — key to value

```proto
message Cart {
  string id = 1;
  map<string, string> coupons = 3;
}
```

- `K` is not arbitrary: typically string or integers (see proto3 rules for map keys).
- Order is not guaranteed as a stable contract for clients.
- A large `map` as a database substitute = anti-pattern.
- In Go: `map[string]string` (or corresponding types).

### 7. oneof — mutually exclusive

```proto
message PaymentMethod {
  oneof kind {
    Card card = 1;
    BankAccount bank = 2;
  }
}

message Card { string last4 = 1; }
message BankAccount { string iban = 1; }
```

Mechanism:

- At most one of the fields in the `oneof` is set.
- In Go the generated API uses a wrapper / `interface` for which variant is current.
- Dozens of variants in one `oneof` = a sign you need a separate RPC or messages.

### 8. Nested message — composition instead of flattened chaos

```proto
message Customer {
  string id = 1;
  Address shipping = 2;
  Address billing = 3;
}

message Address {
  string line1 = 1;
  string city = 2;
  string country_code = 3;
}
```

Better than `shipping_line1`, `billing_line1`, …. On evolution, `Address` expands once.

### 9. reserved — already when deleting / planning

```proto
message Account {
  reserved 3, 5 to 7;
  reserved "legacy_name", "old_flag";
  string user_id = 1;
  int64 balance_cents = 2;
  string currency = 8;
}
```

Mechanism: numbers and names on the “graveyard” must not return to the active schema. Detailed evolution rules are in 06.04 — here remember that `reserved` exists *as part of modeling*, not as an afterthought.

### 10. optional and presence (proto3)

Proto3 enables the “not set” vs default distinction for scalars via `optional`:

```proto
message PatchUser {
  optional string email = 1;
  optional bool active = 2;
}
```

- Use it when you need presence (PATCH semantics).
- Do not put `optional` on every field “just in case” — it noises the API.
- Check team style and the generated API (`HasEmail` / pointers — depends on version).

### 11. Trace A — from schema to wire tags (conceptually)

Message:

```proto
message Ping {
  string msg = 1;
  int32 code = 2;
}
```

Values: `msg = "ok"`, `code = 7`.

**Trace:**

1. Marshal looks at the descriptor: field 1 string, field 2 int32.
2. Writes the tag for field 1 + length-delimited `"ok"`.
3. Writes the tag for field 2 + varint `7`.
4. Unmarshal on the other side reads tags; maps 1→Msg, 2→Code.
5. If unknown field 9 arrives — ignores it.

**Predict then verify:**

- Predict: does renaming `msg` → `message` (same number 1) change the bytes for the same value?
- Verify: no at the wire level (same number and type); yes at the Go API level after regenerate.

### 12. Trace B — enum zero

Schema with a mistake:

```proto
enum State {
  STATE_OPEN = 0; // WRONG
  STATE_CLOSED = 1;
}
```

**Trace:**

1. Client sends `Order{}` without status.
2. The wire has no status field (default).
3. Server sees `STATE_OPEN`.
4. Business thinks the order is open.

**Fix:**

```proto
enum State {
  STATE_UNSPECIFIED = 0;
  STATE_OPEN = 1;
  STATE_CLOSED = 2;
}
```

**Predict then verify:** predict what `GetState()` returns on an empty message before and after the fix; check the generated zero value.

### 13. Trace C — repeated vs map choice

Domain: a cart with lines and coupons.

**Predict:**

- Cart items (sku, qty, order) → `repeated LineItem` or `map`?
- Coupons code→description →?

**Verification:**

- Items: `repeated` (order, duplicate skus possible until you introduce a rule).
- Coupons: `map<string,string>` OK for a small attribute set; or `repeated Coupon` if you need more fields per coupon.

### 14. Trace D — oneof payment

**Predict:** what if you set both `card` and `bank` in the same `oneof` in Go?

**Verification:** the generated API typically keeps only the last set variant; do not treat it as “both apply”. Model exclusivity on purpose.

### 15. Trace E — float money (anti-trace)

```proto
double price = 1; // WRONG for money
```

**Trace:**

1. 0.1 + 0.2 typical binary float noise.
2. Comparisons and bookkeeping become unstable.
3. The wire “works”; money does not.

**Fix:** `int64 price_minor` + currency.

### 16. Number assignment mechanism — team practice

Suggested discipline:

```text
1-15   : entity core (id, status, frequent fields)
16-50  : extensions
51-100 : rare / debug / deprecated before reserved
```

Not a protobuf standard — a team agreement. Important: **record** what is taken; do not free a number without `reserved`.

### 17. Naming — proto style that maps to Go

| Element | Convention |
|---------|------------|
| message | `UpperCamel` (`LineItem`) |
| field | `lower_snake` (`price_minor`) |
| enum type | `UpperCamel` (`OrderStatus`) |
| enum value | `ENUM_NAME_VALUE` (`ORDER_STATUS_PAID`) |
| package | `org.service.v1` style |

The Go generator produces `PriceMinor`, `OrderStatus_ORDER_STATUS_PAID` (shape depends on version — read `*.pb.go`).

### 18. Predict then verify — mini modeling lab

**Lab 1:** Sketch an `Invoice` with repeated lines and an enum status. Predict field numbers 1–5. Verify that no number is “temporary”.

**Lab 2:** Rewrite `double total` into minor + currency. Predict where JSON interop breaks if someone still sends a float.

**Lab 3:** Model login as `oneof { password_hash, oauth_token }`. Predict a Go switch on the variant; check the generated type.

**Lab 4:** Add `reserved 9; reserved "legacy_tax";` “ahead of time” for a field you plan to remove. Predict whether someone can add `string foo = 9` — protoc should reject it.

### 19. Empty message

```proto
message Ping {}
```

Valid for an RPC with no data. On domain events rare — you usually want at least an ID and time (or carry them in a metadata layer).

### 20. Large vs small message — branching mechanism

```text
one giant message
  + fast at the start
  - hard evolution, review, validation

more small messages + composition
  + clarity, reuse
  - more names, imports
```

Practically: extract `Address`, `Money`, `PageRequest` when they repeat.

### 21. Mechanism checklist before generate

- [ ] `syntax = "proto3"`
- [ ] `package` with `v1` (or agreed template)
- [ ] numbers assigned consciously; 1–15 for frequent fields
- [ ] enum 0 = UNSPECIFIED
- [ ] money without float
- [ ] unit comments on numeric fields
- [ ] `oneof` only where exclusivity is real
- [ ] `map` is not a database substitute
- [ ] `reserved` for everything you delete
- [ ] `go_package` ready (06.03)

### 22. Trace F — wrong type on the same number (preview 06.04)

Suppose the field was `int32 count = 5`, then you “switch” to `string count = 5`.

**Predict:** does an old payload with varint 42 correctly become the string `"42"`?

**Verification:** no — wire type and semantics break. Correct: a new field with a new number, old one `reserved`. This lesson teaches you to choose a type wide enough *at creation* (`int64` for money) so you do not have to break later.

### 23. Comment mechanism as part of the contract

```proto
message Quota {
  // limit: maximum number of requests in the window
  int32 limit = 1;
  // window_seconds: window length in seconds (not ms)
  int64 window_seconds = 2;
}
```

Without the comment, someone sends milliseconds in `window_seconds`. An `int64` type schema does not prevent that — review + comment + test do.

### 24. From JSON DTO to proto — mechanism steps

1. List the JSON object fields.
2. Assign types consciously (money → minor).
3. Assign numbers (frequent = low).
4. Extract nested types.
5. Enum for closed states.
6. `oneof` where exclusivity is real.
7. Unit comments.
8. Only then `go_package` + generate (06.03).

**Predict then verify:** predict which JSON fields are “string because it was easy” but should be enum/int64; check with a domain expert before you lock numbers.

### 25. Mechanism summary

You build a message as a contract: type + name + **number**. Enum, repeated, map, oneof are tools with clear rules. The wire does not know your pretty names — it knows numbers. That is why modeling *is* versioning ahead of time. Choose types and numbers as if they will live for years — because they will.

### 26. Trace G — package v1 in the name as an evolution signal

```proto
package shop.v1;
```

**Mechanism:** `v1` in the package name is not decoration. It signals: “this contract evolves compatibly; a break goes into `shop.v2`.”

**Predict then verify:** predict whether changing `package shop.v1` → `shop.v2` with the same field numbers breaks clients. Verify: that is a *new* protobuf package / often a new Go import — a conscious break, not a silent one. Use it when you truly need v2 (06.04), not for taste.

### 27. Choice mechanism: string status vs enum

| Question | Enum | string |
|---------|------|--------|
| Closed and small set? | yes | rarely |
| Often add values from config? | caution | string more often |
| Need a codegen switch? | yes | hand-rolled parse |
| Zero-value trap? | 0=UNSPECIFIED | empty string |

**Predict:** order status in a shop — enum or string?  
**Verification:** enum (`PENDING/PAID/...`) with an unknown branch; string if partners send arbitrary labels outside your control.

### 28. bytes field mechanism

```proto
message BlobRef {
  string id = 1;
  bytes content_sha256 = 2; // exactly 32 bytes — document it
}
```

- `bytes` in Go → `[]byte`.
- Do not use `bytes` for text (that is `string`).
- Document length/format (hash; protobuf-in-protobuf rarely — prefer a nested message).

### 29. From JSON fields to proto — working mechanism example

JSON:

```json
{
  "userId": "u1",
  "roles": ["admin", "editor"],
  "profile": {"city": "BG", "country": "RS"},
  "login": {"oauth": "tok"}
}
```

Proto sketch:

```proto
message User {
  string user_id = 1;
  repeated string roles = 2;
  Address profile = 3;
  oneof login {
    string password_hash = 10;
    string oauth_token = 11;
  }
}
message Address {
  string city = 1;
  string country_code = 2;
}
```

**Decision trace:** `userId` → `user_id` + number 1; nested profile; oneof for login shape; roles as repeated. Numbers 10/11 leave room for core 1–9.

## Rules and syntax

| Construct | Rule |
|--------------|---------|
| `syntax = "proto3"` | at the top of the file |
| Field number | 1–15 cheaper tag; never reuse |
| Enum zero | `_UNSPECIFIED = 0` idiom |
| `repeated` | list / order |
| `map<K,V>` | K limited; order is not a contract |
| `oneof` | at most one set |
| `reserved` | after deletion / for forbidding |
| Money | `int64` minor + currency string |
| Names | message CamelCase; fields snake_case |

Scalars you will touch most often: `string`, `bool`, `bytes`, `int32`, `int64`, `uint64`, `float`, `double`, fixed*.

## Examples

### Example 1: Basic message

```proto
syntax = "proto3";

package shop.v1;

message Product {
  string sku = 1;
  string title = 2;
  int64 price_minor = 3;
  bool active = 4;
}
```

### What happens here

Clear package, four fields, money as `int64` minor — without float mistakes.

### Example 2: Enum

```proto
enum OrderStatus {
  ORDER_STATUS_UNSPECIFIED = 0;
  ORDER_STATUS_PENDING = 1;
  ORDER_STATUS_PAID = 2;
  ORDER_STATUS_CANCELED = 3;
}

message Order {
  string id = 1;
  OrderStatus status = 2;
}
```

### What happens here

The zero value is “not set”. Do not use 0 for `PAID`.

### Example 3: repeated and map

```proto
message Cart {
  string id = 1;
  repeated LineItem items = 2;
  map<string, string> coupons = 3;
}

message LineItem {
  string sku = 1;
  int32 qty = 2;
}
```

### What happens here

`repeated` for an ordered list of items. `map` for key→value attributes. In Go: slice and `map[string]string`.

### Example 4: oneof

```proto
message PaymentMethod {
  oneof kind {
    Card card = 1;
    BankAccount bank = 2;
  }
}

message Card { string last4 = 1; }
message BankAccount { string iban = 1; }
```

### What happens here

The message models “exactly one shape”. In Go the generated code uses a wrapper for oneof.

### Example 5: Bad vs good type for money

```proto
// bad for money
double price = 1;

// better
int64 price_minor = 1;
string currency_code = 2; // ISO code
```

### What happens here

Binary floating point is not for money. Minor units + currency are predictable.

### Example 6: Money as a reuse type

```proto
message Money {
  int64 amount_minor = 1;
  string currency_code = 2;
}

message Invoice {
  string id = 1;
  Money total = 2;
  Money tax = 3;
}
```

### What happens here

The same money contract in multiple places; `Money` evolution is centralized.

### Example 7: optional for PATCH

```proto
message UpdateProduct {
  string id = 1;
  optional string title = 2;
  optional int64 price_minor = 3;
  optional bool active = 4;
}
```

### What happens here

Presence enables “change only title”. Without `optional`, empty string and 0 do not distinguish “not sent” from “set to default”.

## Decision analysis

**Message vs enum** — closed set of states: enum; open/extensible set of labels: string with documentation (rarer) or a separate table.

**repeated message vs map** — list of entities: repeated; index by ID in the payload: map or a separate lookup outside the message.

**oneof vs optional fields** — mutually exclusive: oneof; independent optionality: `optional` / separate fields.

**Nested vs flattened** — nested when the concept repeats (`Address`); flattened only for 1–2 fields that will never grow (rarely true).

**Larger int immediately** — `int64` for money and for IDs that may grow; migrating `int32`→wider on the same number is not safe (06.04).

## Trade-offs

| Choice | Advantage | Cost |
|-------|----------|------|
| Many small messages | clarity, reuse | more names |
| One giant message | fast at the start | hard evolution |
| map | convenient lookup | non-deterministic order |
| oneof | strict exclusivity | slightly harder Go API |
| optional everywhere | presence | noise, complexity |
| string for “everything” | flexibility | loss of types |

## Common mistakes

1. Enum without 0 `UNSPECIFIED`.
2. `float` / `double` for money.
3. Reusing a field number.
4. Oversized `map` instead of a table in the database.
5. `oneof` with dozens of variants — a sign you need a separate RPC/messages.
6. Treating field names as the wire contract.
7. Flattened addresses that later must be “unpacked”.
8. Assigning numbers 1–15 to temporary debug fields.
9. `optional` on every scalar field “just in case”.
10. Missing unit comments on numeric fields.

## Idiomatic Go / proto style

- `package foo.v1;`
- `UpperCamel` names for messages, `lower_snake` for fields.
- Prefix enum values with the enum name.
- Comment units and invariants.
- Keep messages focused; extract `Money`, `Address`.
- After generate: read `*.pb.go` instead of guessing types.
- In Go code: `GetX()`; for oneof — switch on the generated wrapper type.
- Do not mix domain validation (“qty > 0”) into the schema — the schema carries shape, the app carries rules.

Idiomatic oneof reading example (illustration):

```go
switch m := method.GetKind().(type) {
case *pb.PaymentMethod_Card:
	_ = m.Card.GetLast4()
case *pb.PaymentMethod_Bank:
	_ = m.Bank.GetIban()
default:
	// unspecified / nil
}
```

(Exact type names depend on generate output — check your `*.pb.go`.)

## Practical scenario

An `Order` message has 40 fields, including shipping and billing addresses flattened. A reviewer forces an `Address` message + `oneof payment`. Generated Go becomes more readable; validation splits.

Later adding `pickup_point` does not touch payment: a new field / new oneof variant with a **new** number. The team introduces a checklist: enum 0, money minor, reserved on deletion. `.proto` PRs take longer — incidents take less.

## Summary

Proto3 messages are built from typed fields with stable numbers, plus enum/repeated/map/oneof as needed. Design for Go types and future evolution, not only for today’s JSON shape. The wire remembers numbers — that is why modeling is already half of versioning.
