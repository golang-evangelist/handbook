# 06.01 Why Protocol Buffers

> **Go Path - Zero to Gopher** / **03 Others → Protocol Buffer Fundamentals** / Lesson 06.01

## Lesson goals

After this lesson you will be able to:

- explain what a schema is and why a contract matters more than ad-hoc JSON;
- compare binary protobuf with JSON on size, speed, and readability;
- understand that the wire uses **field numbers**, not names, as field identity;
- treat compatibility as a design goal, not luck after a deploy;
- decide when protobuf makes sense in Go services (Go 1.22+);
- explain the difference between schema, generated code, and wire bytes.

## Prerequisite

- Basic Go and working with `encoding/json` (struct + tags or `map[string]any`).
- Preferred: gRPC context from blocks 03/05 — not required; protobuf works without gRPC.
- Go 1.22+.
- A text editor; `protoc` is not needed for this lesson (it comes in 06.03).
- Familiarity with the idea of an API contract (OpenAPI, DTO, “whatever we agree in the PR”).

## Problem this lesson solves

JSON APIs often “document” fields in a Wiki that nobody updates. Clients guess types (`amount` sometimes a string, sometimes a number). Breaking changes slip through silently because there is no compiler bridge between the contract and the code.

Protobuf forces a schema into a `.proto` file, generates types, and provides evolution rules. This lesson answers *why* before *how* (messages in 06.02, generate in 06.03, versioning in 06.04).

Concrete pain in practice:

1. Two services “agree” verbally on a JSON shape.
2. One adds a field; the other ignores it — or parses it wrong.
3. After six months nobody knows what the canonical contract is.
4. Incident: wrong type in the payload, silent data corruption.
5. The post-mortem ends with “let’s update the Wiki” — and the cycle repeats.

A schema as a contract shrinks that class of errors. It does not eliminate everything (you can still design fields badly), but it moves the error from runtime to review and codegen.

## Mental model

```text
  [.proto schema = contract]
           |
           +--protoc / protoc-gen-go--> [Go types + Marshal/Unmarshal]
           |
           +-- wire: binary protobuf
           |         tag = (field number << 3) | wire type
           |         value; field names are NOT on the wire
           |
           +-- evolution rules: new numbers, reserved, compatibility
```

Three layers to keep separate in your head:

| Layer | What it is | Who reads it | What breaks it |
|------|--------|------------|----------|
| Schema (`.proto`) | team contract | people + `protoc` | silent semantic change |
| Generated Go | types and API | your code, the compiler | hand-editing `*.pb.go` |
| Wire bytes | runtime contract | another process / language | reusing a field number |

JSON: text + agreement. Protobuf: contract + compiler bridge + dense wire format.

### Terminology table

| Term | Meaning in this lesson |
|--------|-------------------------|
| schema | message definition in `.proto` |
| message | message type (`message Account { ... }`) |
| field number | field number; **identity on the wire** |
| field name | name for people and generated identifiers |
| wire format | binary encoding of a protobuf message |
| tag | on the wire: field number + wire type |
| wire type | how the value is encoded (varint, length-delimited, …) |
| codegen | generating `*.pb.go` from `.proto` |
| compatibility | old and new readers/writers still work |
| forward compatible | a newer reader understands older messages |
| backward compatible | an older reader tolerates newer messages (ignore unknown) |
| proto3 | modern syntax (the course uses proto3) |
| `proto.Marshal` / `Unmarshal` | Go API from `google.golang.org/protobuf/proto` |
| IDL | interface definition language — here `.proto` |

## Mechanism

The mechanism is the core of the lesson: how a schema becomes a contract, how the wire picks numbers instead of names, why compatibility is design, and how to *predict then verify* behavior before you wire up tooling.

### 1. Schema first — IDL before code

You define a `message` with fields and **numbers** before you write handlers:

```proto
syntax = "proto3";

package billing.v1;

message Account {
  string user_id = 1;
  int64 balance_cents = 2;
  bool active = 3;
}
```

The schema answers:

- which values exist;
- what type they are;
- what the stable field ID is (field number);
- (through comments) what the units and invariants are.

Without a schema, a JSON DTO lives in three places at once: a Go struct, a Wiki, and “an example in Slack”. With a schema, one place is the source of truth — `.proto` in the repo.

**Discipline:** product + engineering agree on meaning *in the schema*, not in a side channel.

```proto
// balance_cents is an amount in the smallest currency units (e.g. cents).
// Never send major units in this field.
int64 balance_cents = 2;
```

A schema without semantics leaves a hole: `amount` becomes ambiguous again.

### 2. The generator builds types — the bridge to Go

`protoc` + `protoc-gen-go` (details in 06.03) produce structs and serialization methods. You do not write a hand-rolled parser. A wrong type does not pass the compiler.

Illustration (Go field names are exported, CamelCase):

```go
acc := &pb.Account{
	UserId:       "u1",
	BalanceCents: 1500,
	Active:       true,
}
b, err := proto.Marshal(acc)
if err != nil {
	return err
}
out := &pb.Account{}
if err := proto.Unmarshal(b, out); err != nil {
	return err
}
```

No `map[string]any` guessing. `BalanceCents` is `int64` — not a string by accident.

The schema → Go bridge is *compiler-backed*: if someone changes a type in `.proto` and regenerates, your hand-written code often stops compiling. That is desired.

### 3. Wire: tag + value, without field names

On the network (or in a file/queue) you get:

1. **tag** — a combination of field number and wire type;
2. **value** — varint, length-delimited string, nested message, and so on.

Names like `balance_cents` **do not travel** on the wire. That is why the field number is the identity. If you rename a field in `.proto` but keep the number, old bytes still map to the same field (with care for generated names and review — see 06.04).

Conceptual contrast:

```text
JSON:  {"balance_cents":1500}              // the key is repeated in every document
PB:    tag(field=2, wire_type=varint) + 1500  // number 2 is the identity
```

Why is this design, not an implementation detail?

- Renaming for people does not automatically break the wire (the number stays).
- Size does not grow with name length.
- Evolution is tied to **numbers**, not string keys.

The cost: the wire is not as readable as JSON in a `curl` output.

### 4. Compatibility as default behavior (proto3 practice)

A reader with an older schema **ignores unknown fields** (unknown field numbers). A writer with an older schema simply does not send new fields; the reader sees default / absence.

That enables a matrix:

| | old client | new client |
|--|---------------|--------------|
| old server | baseline | new sends extra fields → old ignores |
| new server | old does not send new fields → default | baseline |

Compatibility is not magic: you must **design** changes (new number, no reuse, `reserved` — 06.04). But the wire model is built to support that *if* you follow the rules.

**Key course sentence:** compatibility is a design goal, not luck after a deploy.

### 5. Trace A — JSON path for the “same” data

**Input (intent):** account `u1`, balance 1500 cents, active.

**JSON document:**

```json
{"user_id":"u1","balance_cents":1500,"active":true}
```

**Trace steps:**

1. The encoder writes textual keys and values.
2. Every document repeats `"user_id"`, `"balance_cents"`, `"active"`.
3. The decoder must know (or guess) the type: is `balance_cents` a number or a string?
4. If someone sends `"balance_cents":"1500"`, Go `json.Unmarshal` into `int64` may fail or require a custom type.
5. The Wiki says “always a number” — until someone sends a string from another language.
6. If the key is renamed to `balanceCents` without agreement, old clients “lose” the field silently (`omitempty` / zero-value traps).

**Trace conclusion:** JSON carries names; the contract is social; types are soft without extra discipline.

### 6. Trace B — protobuf path for the same data

**Same intent**, schema with numbers 1, 2, 3.

**Trace steps:**

1. `proto.Marshal` looks at the type and field numbers from the generated descriptor.
2. For field 1 (`string`): length-delimited tag + bytes `"u1"`.
3. For field 2 (`int64`): varint tag + 1500.
4. For field 3 (`bool`): varint tag + 1 or 0.
5. On the other side `Unmarshal` maps tags to fields **by number**, not by name.
6. If field 4 arrives that this reader does not know — it ignores it (or keeps it in unknown fields, depending on the API), without panicking.
7. If field 2 arrives with the wrong wire type relative to the schema — error/invalid parse, not a “silent string”.

**Trace conclusion:** wire identity = field number; names are a local label of the schema and the code.

### 7. Trace C — adding a field (compatibility in action)

**v1 schema:** fields 1–3.  
**v2 schema:** + `string currency = 4`.

**Predict then verify — prediction step:**

What do you expect in these cells *before* you look at the table below?

| | old client | new client |
|--|---------------|--------------|
| old server | ? | ? |
| new server | ? | ? |

**Verification (expected behavior with correct evolution):**

| | old client | new client |
|--|---------------|--------------|
| old server | works (baseline) | works: old ignores field 4 |
| new server | works: currency default/empty | works (baseline) |

If any “must work” cell fails, you are not compatible — the problem is in the schema change or in an application assumption (“currency is always set!”), not in “protobuf magic”.

### 8. Trace D — why names are not identity (thought experiment)

Suppose the wire carried names like JSON. What would happen?

1. Renaming `user_id` → `account_id` would break all old clients immediately.
2. Localization / abbreviations / typos become wire-breaking.
3. Message size grows with name length.
4. The “same” contract in two languages with different naming conventions (`userId` vs `user_id`) becomes chaos.

Protobuf chooses numbers precisely so that **evolution** and **density** are possible. The cost: debugging needs tools (`protoc --decode`, specialized viewers), not `cat`.

### 9. Trace E — silent meaning change (anti-trace)

**Bad scenario:** field 2 was `balance_cents`. The team “switches” to major units but keeps number 2 and renames to `balance`.

**Trace:**

1. Old client sends 1500 (cents).
2. New server interprets 1500 as majors.
3. Bookkeeping ×100 — silent catastrophe.
4. The wire “works”; the semantics do not.

**Conclusion:** format compatibility ≠ meaning compatibility. That is why changing meaning on the same number is a forbidden practice (06.04).

### 10. Predict then verify — lab

**Task 1 — predict size (conceptually):**

A message with one field `int64 balance_cents = 2`, value 1500.

- Predict: is JSON `{"balance_cents":1500}` longer than PB tag+varint?
- Verify: after 06.03 measure `len(jsonBytes)` vs `len(pbBytes)`. Do not trust marketing numbers blindly.

**Task 2 — predict a type error:**

A JSON client sends `"balance_cents": "1500"`. The Go struct has `BalanceCents int64`.

- Predict: does `json.Unmarshal` succeed?
- Verify: a small test. Compare with protobuf: the type is in the schema; a string is not a silent int64.

**Task 3 — predict default:**

You add `string currency = 4`. An old client does not send field 4.

- Predict: what does `GetCurrency()` return on the new server?
- Verify: empty string for `string` in proto3 (except presence/`optional` — 06.02). Application often: `if cur == "" { cur = "RSD" }`.

**Task 4 — predict rename:**

You rename `user_id` → `account_id`, **same number 1**, regenerate, deploy only the server.

- Predict: does the old client still send correct bytes for field 1?
- Verify: yes at the wire level (number 1); not at the Go-name level in old code if the old code was not regenerated. Separate wire compatibility from local API breakage.

**Task 5 — predict a “Wiki contract”:**

Two teams write JSON without a schema. One sends `amount`, the other expects `amount_minor`.

- Predict: when does it break — compile or runtime?
- Verify: runtime, often silently (zero value). Protobuf + codegen moves part of the pain to compile time.

### 11. Schema as a team contract — process, not just a file

`.proto` is where product + engineering agree on field meaning. Process around the schema:

1. Propose the change in a PR (not in chat as the only record).
2. Questions: compatibility? reserved? units? `go_package`?
3. Generate + test.
4. CHANGELOG / note for schema consumers.

Without process, `.proto` becomes just another file that drifts — only binary.

### 12. Relationship to gRPC — and life without it

gRPC uses protobuf as the serializer by default. But protobuf is not tied only to RPC:

- files on disk;
- messages in a queue;
- cache values;
- inter-process in the same monorepo.

gRPC adds an RPC layer (methods, streaming, status codes). Protobuf remains the language of messages. This lesson chooses protobuf for the contract and wire model — gRPC is an option, not a requirement.

```text
protobuf  = message language + wire
gRPC      = RPC framework that often uses that language
```

### 13. When JSON still wins — decision mechanism

The decision mechanism is not “protobuf always”:

```text
do you need a strict schema + codegen?     → PB candidate
is wire readability critical?              → JSON candidate
browser / curl without codegen?            → JSON often
internal service ↔ service?                → PB / gRPC often
public HTTP for third parties?             → JSON + OpenAPI often
partners without protoc discipline?        → JSON often
queue + many languages + schema?           → PB candidate
```

Mixed is legitimate: protobuf inside, JSON at the edge (gateway). That is not “impurity” — it is a conscious boundary. The canonical model lives inside; outside is an adapter.

### 14. “Readability” table by layers

| Layer | JSON | Protobuf |
|------|------|----------|
| Wire | readable text | binary |
| Code | hand-written struct / tags | generated |
| Contract | OpenAPI / Wiki / “agreement” | `.proto` |
| Evolution | social agreement | rules + reserved |
| Debug in the terminal | easy | needs a tool |
| Multi-language codegen | less standard | first class |

### 15. Performance — mental model, not marketing

Protobuf *often* gives a smaller payload and faster encode/decode than JSON, especially when:

- you have many numeric fields;
- you send high QPS of small messages;
- JSON field names are long and frequent.

But:

- do not treat an “internet benchmark” as the truth of your domain;
- CPU vs network — the bottleneck may be the database, not the serializer;
- readability and tooling can cost more than a 20% payload saving.

**Rule:** choose protobuf first for contract and evolution; confirm speed with measurement if it is critical.

### 16. Mechanism anti-patterns (what not to do)

1. “We have a `.proto`, but the Wiki is still the source of truth.”
2. “The generated file is wrong, I’ll fix it by hand.”
3. “It is faster to change the meaning of field 3 than to add 4.”
4. “Protobuf everywhere, including a public browser API without codegen.”
5. “We’ll fix compatibility when it breaks.”
6. “JSON and protobuf on the same boundary without a clear canon.”

### 20. Trace F — gateway mix (PB inside, JSON outside)

**Setup:** a mobile client speaks JSON HTTP. Internal services speak protobuf.

**Trace:**

1. The request arrives as JSON at the BFF/gateway.
2. The gateway validates / maps into a protobuf `message`.
3. The internal call goes over the binary wire (often gRPC).
4. The response is mapped back to JSON for the mobile client.
5. The canonical model lives in `.proto`; JSON is an adapter at the edge.

**Predict then verify:**

- Predict: where does drift appear if the gateway maps “by eye” without a schema?
- Verify: if the gateway generates the mapping from the same `.proto` (or shares types), drift drops. If it hand-maintains a JSON DTO *and* proto, you have two contracts again.

### 21. What protobuf does *not* solve by itself

The contract mechanism does not replace:

- authorization and authentication;
- business-rule validation (e.g. “amount must be > 0”);
- event idempotency and deduplication;
- observability (you still need a trace-id);
- agreement on field *meaning* — it only forces that meaning to live next to the type.

That is why unit comments and API review remain part of the mechanism, not optional decoration.

### 22. Mechanism summary in five sentences

1. The schema in `.proto` is the team contract.  
2. Codegen bridges the contract to Go types.  
3. The wire uses field numbers, not names, as identity.  
4. Compatibility is designing changes under that wire model.  
5. JSON remains legitimate where readability and universality win.

## Rules and syntax

We are not learning every message syntax yet — remember the principles:

| Principle | Meaning |
|---------|----------|
| Schema first | IDL (`.proto`) before an ad-hoc DTO |
| Field number = identity | the name is a label; the number is not reused |
| Binary wire | not for hand-reading in logs |
| Generation | do not write hand-rolled protobuf parsers |
| Compatibility | design of changes, not luck |
| Go 1.22+ | the course assumes a modern toolchain |
| One contract | do not duplicate the schema in a Wiki as the source of truth |
| Semantics in a comment | units and invariants next to the field |

Practical team rules:

1. Every `.proto` change goes through review as an API.
2. Generated files are not “fixed” by hand.
3. Pin `protoc` / `protoc-gen-go` versions (06.03).
4. Document units in the field comment.
5. An old×new matrix at least on paper for every non-trivial change.

## Examples

### Example 1: Same intent — JSON vs proto

```json
{"user_id": "u1", "balance_cents": 1500, "active": true}
```

```proto
syntax = "proto3";

message Account {
  string user_id = 1;
  int64 balance_cents = 2;
  bool active = 3;
}
```

### What happens here

JSON repeats keys in every document. Proto on the wire uses numbers 1, 2, 3. Go gets typed fields (`UserId`, `BalanceCents`, `Active`) after generate.

### Example 2: Go working with a generated type (illustration)

```go
package main

import (
	"fmt"

	"google.golang.org/protobuf/proto"
	pb "example.com/shop/gen/accountpb"
)

func demo() error {
	acc := &pb.Account{
		UserId:       "u1",
		BalanceCents: 1500,
		Active:       true,
	}
	bytes, err := proto.Marshal(acc)
	if err != nil {
		return err
	}
	out := &pb.Account{}
	if err := proto.Unmarshal(bytes, out); err != nil {
		return err
	}
	fmt.Println(out.GetUserId(), out.GetBalanceCents(), out.GetActive())
	return nil
}
```

### What happens here

The roundtrip confirms: types are strict; `GetX()` getters are idiomatic when the message may be nil. The import path comes from `go_package` (06.03).

### Example 3: Compatibility — adding a field

```proto
message Account {
  string user_id = 1;
  int64 balance_cents = 2;
  bool active = 3;
  string currency = 4; // new — new number
}
```

### What happens here

An old client sends without `currency`; the new server sees the default. A new client sends `currency`; the old server ignores the unknown field. This is *adding* — safer than changing the meaning of field 2.

### Example 4: Where JSON still wins

```text
- public browser API without codegen
- quick script / debug curl
- logs that people read every day
- partners who expect OpenAPI + JSON
```

### What happens here

Protobuf is not a religion. Choose JSON where readability and universality matter more than density and a strict schema.

### Example 5: Size (conceptually, then measurement)

```text
JSON:  {"balance_cents":1500}  -> many text bytes + quotes
PB:    tag for field 2 + varint 1500 -> short
```

### What happens here

Savings grow with the number of fields and message frequency. Measure in your domain.

### Example 6: Format choice checklist

```text
[ ] Do I need a strict schema?
[ ] Do I need codegen for multiple languages?
[ ] Is wire readability critical?
[ ] Can the team handle protoc tooling?
[ ] Do I have a versioning plan (06.04)?
```

### What happens here

The decision is engineering, not aesthetic. If you have no versioning plan, protobuf gives you a sharper knife — you can still cut yourself by reusing numbers.

### Example 7: Schema + unit comment

```proto
message Transfer {
  string from_account = 1;
  string to_account = 2;
  // amount_minor: smallest units (cents, para...)
  int64 amount_minor = 3;
  // ISO 4217, e.g. "RSD", "EUR"
  string currency_code = 4;
}
```

### What happens here

Without the comment, someone will put majors into `amount_minor` again. The contract includes semantics.

### Example 8: Evolution table (preview 06.04)

| Change | Compatible? | Action |
|--------|---------------|--------|
| New field, new number | yes | just add |
| Deleting a field | conditional | `reserved` |
| Changing type of the same number | no | new field or v2 |
| New name, same number | caution | wire OK, local API break |

### What happens here

Already in 06.01 you see that “why protobuf” includes *why discipline*. A tool without rules is not enough.

## Decision analysis

**Internal service ↔ service** — protobuf (often with gRPC) is a strong candidate: schema, speed, multi-language codegen.

**Public HTTP for third parties** — JSON + OpenAPI is often more pragmatic: curl, browser, partners without `protoc`.

**Mixed** — protobuf inside, JSON at the edge (API gateway / BFF). The boundary must be explicit: where transcoding happens, where the canonical model lives.

**Event bus / queue** — protobuf fits well if all consumers share the schema; JSON if consumers must read the payload in logs without tools.

**“We’re still small, just JSON”** — valid until type drift hurts. Switching later costs more because implicit contracts already exist.

Questions for a PR review of the choice:

1. Who is the contract consumer (internal vs external)?
2. How many languages must generate code?
3. How large is the traffic / message size?
4. Can the team keep `protoc` discipline?
5. Do we have a plan for reserved and v2 (06.04)?
6. Where is the source of truth if we have both OpenAPI and `.proto`?

## Trade-offs

| Format | Advantage | Cost |
|--------|----------|------|
| Protobuf | schema, dense wire, codegen, evolution rules | tooling, lower wire readability |
| JSON | universality, curl, human readability | larger payload, easier type drift |
| Hand-rolled binary | maximum control | expensive development and maintenance |
| JSON + JSON Schema | schema without a binary format | different toolchain; not the same wire model |

The trade-off is not only technical: it is **operational**. Protobuf without pinned generators and CI diffs often hurts more than JSON with a good OpenAPI.

One more trade-off: **speed of introduction**. A JSON DTO “works immediately”. Protobuf needs a generate step. If the team is not ready, delayed introduction can be better than a half measure.

## Common mistakes

1. Changing the meaning of an existing field number (“same field, different semantics”).
2. Reusing a number after deletion (use `reserved` — 06.04).
3. Expecting protobuf to be readable in Wireshark / logs like JSON.
4. Duplicating the schema in a Wiki instead of `.proto` as the source of truth.
5. Generating then hand-editing `*.pb.go`.
6. Introducing protobuf “for speed” without a compatibility plan — speed is a bonus; the contract is the reason.
7. Mixing old and new Go protobuf APIs without a migration plan.
8. Assuming every service will regenerate on the same day after a schema change.
9. Protobuf on a public browser edge without a clear reason and without a codegen path for clients.
10. Treating compatibility as documentation instead of as a design rule.

## Idiomatic Go

- Use the modern module: `google.golang.org/protobuf` (do not mix legacy without need).
- `proto.Marshal` / `proto.Unmarshal` for a binary roundtrip.
- `GetX()` getters when working with potentially nil messages.
- Keep `.proto` in the repo as the source of truth; review it as an API.
- Do not commit “hand-fixed” generated code — regenerate.
- In tests: a small roundtrip after a schema change (sanity).
- Go 1.22+: keep the toolchain aligned with the rest of the course / project.

Sanity test example (conceptual):

```go
func TestAccountRoundTrip(t *testing.T) {
	in := &pb.Account{UserId: "u1", BalanceCents: 10, Active: true}
	b, err := proto.Marshal(in)
	if err != nil {
		t.Fatal(err)
	}
	out := &pb.Account{}
	if err := proto.Unmarshal(b, out); err != nil {
		t.Fatal(err)
	}
	if out.GetBalanceCents() != 10 {
		t.Fatalf("got %d", out.GetBalanceCents())
	}
}
```

## Practical scenario

A fintech team sends JSON events between 8 services. The `amount` field is sometimes a string, sometimes a number, sometimes major units. Incident: wrong bookkeeping.

They move to a `payment.v1.Event` proto:

```proto
syntax = "proto3";
package payment.v1;

message Event {
  string event_id = 1;
  string account_id = 2;
  int64 amount_minor = 3;
  string currency_code = 4;
}
```

Codegen in Go and one other language. Type drift disappears at the contract boundary. CI breaks the PR if someone forgets to regenerate or if the `protoc-gen-go` version produces an unexpected diff (pin + diff policy).

Team lesson: protobuf is not “faster JSON” — it is **forced contract discipline**. Speed and size come as a consequence. JSON stays on partner portals; the canonical event inside is PB.

10. Which three layers (schema / generated / wire) do you separate in review?

## Summary

Protocol Buffers give you a schema as a contract, a binary wire where the **field number** is field identity, and a foundation for compatible API evolution. In Go (1.22+) that means type-strict generated code and less guessing than JSON — with tooling discipline.

JSON still has a place. Choose consciously: an internal contract is often PB; public readability is often JSON; a mix at the edge is legitimate. Compatibility is a design goal — not documentation written after an incident.
