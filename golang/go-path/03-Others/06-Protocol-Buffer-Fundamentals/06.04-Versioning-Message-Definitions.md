# 06.04 Versioning message definitions

> **Go Path - Zero to Gopher** / **03 Others → Protocol Buffer Fundamentals** / Lesson 06.04

## Lesson goals

After this lesson you will be able to:

- add fields without breaking old clients;
- never reuse a field number;
- use `reserved` for numbers and names;
- evolve enums carefully (unknown values);
- choose between compatible evolution and a new `v2` package;
- test an old×new matrix at least on paper before merge.

## Prerequisite

- 06.01–06.03 (why numbers, how to model, how to generate).
- Go 1.22+.
- Understanding that in production old and new binaries often live *at the same time*.

## Problem this lesson solves

The most expensive protobuf bug: delete field 3, later add a new field with number 3 of a different meaning. An old binary payload “revives” wrong data. Versioning and `reserved` prevent that class of incident.

Another expensive bug: change the type on the same number (`int32` → `string`). The wire “works” enough to pass silently — then corrupts semantics.

This lesson turns compatibility from a wish into rules.

## Mental model

```text
Field number = eternal ID
Name         = label for people / generated code
reserved     = graveyard of IDs that nobody may use again
v1 / v2      = when compatibility is impossible — a clear boundary
```

```text
                  add field (new number)
                        │
   old wire ────────────┼─────────► new reader (default / presence)
                        │
   new wire  ───────────┼─────────► old reader (ignore unknown)
                        │
              reuse number / type change ──► INCIDENT
```

Compatible change: old and new speak enough of the same language.  
Breaking: new package / new RPC / conscious break with migration.

### Terminology table

| Term | Meaning |
|--------|----------|
| field number reuse | same number, new meaning — **forbidden** |
| `reserved` | forbidding numbers and/or names in the schema |
| additive change | new field, new number |
| breaking change | type/semantics/break reading old bytes |
| unknown fields | unknown tags the reader ignores / keeps |
| enum evolution | adding values; handling unknowns |
| `package .v2` | new contract when v1 cannot be preserved |
| rollout window | period when old and new binaries live |
| dual-write | temporarily writing old and new fields |

## Mechanism

The versioning mechanism is the longest part of block 06: rules, incident traces, predictions, matrices, enum, v2.

### 1. Golden rule

**A field number is not reused.** Never. Not “only internally”. Not “we’re not in production yet” if there is a single old byte in a log, queue, or mobile client.

The number is an eternal ID. The name is a label. Semantics are not “overwritten” on top of an old ID.

### 2. What is usually compatible

- Add a new field with a **new** number.
- Add a new enum value (with application handling of unknowns).
- Relax validation at the application level (stricter → looser carefully).
- Rename a field carefully with the same number (wire OK; local Go API breaks until regenerate — that is *local*, not wire-breaking, but still requires coordination).

### 3. What is forbidden / very dangerous

- Reusing a field number.
- Changing a field type on the same number (`int32` → `string`; `int32` → `int64` is not safe as “the same”).
- Quietly changing field meaning (cents → majors, same number).
- “Temporarily” taking a deleted number because “there are no more clients” without proof.

### 4. `reserved` — the graveyard mechanism

```proto
message Account {
  reserved 3, 5 to 7;
  reserved "legacy_name", "old_flag";
  string user_id = 1;
  int64 balance_cents = 2;
  string currency = 8;
}
```

- `reserved 3, 5 to 7` — numbers forbidden.
- `reserved "legacy_name"` — name forbidden (prevents confusion; less dangerous than number reuse, still useful).
- `protoc` reports if someone tries to put a field back on a reserved number/name.

A graveyard comment helps people:

```proto
message Session {
  // reserved history:
  // 2 = old_token (bytes) removed 2026-01
  reserved 2;
  string id = 1;
  string token = 3;
}
```

### 5. Trace A — classic reuse incident

**History:**

1. Field `bool promo = 7`.
2. Team deletes `promo` without `reserved`.
3. A month later: `int64 promo_id = 7`.

**Runtime trace:**

1. Old mobile client sends `promo=true` → wire: field 7, varint 1.
2. New server reads field 7 as `promo_id` → value 1.
3. Promotion ID=1 activates — wrong.
4. Wire and schema “compile”; business lies.

**Fix:**

```proto
reserved 7;
reserved "promo";
int64 promo_id = 8;
```

**Predict then verify:** predict the `promo_id` value when an old client sends bool true on number 7; verify that is exactly the incident from the scenario section.

### 6. Trace B — adding a field (happy path)

```proto
message Invoice {
  string id = 1;
  int64 total_minor = 2;
  string currency = 3; // added later
}
```

**Matrix — predict then verify:**

| | old client | new client |
|--|---------------|--------------|
| old server | baseline | ? |
| new server | ? | baseline |

**Verification:**

| | old client | new client |
|--|---------------|--------------|
| old server | OK | OK (ignore 3) |
| new server | OK (currency default) | OK |

Application on the new server:

```go
cur := inv.GetCurrency()
if cur == "" {
	cur = "RSD"
}
```

Schema default ≠ domain default — join them consciously.

### 7. Trace C — type change on the same number

```proto
// was:
// int32 count = 5;
// WRONG:
string count = 5;
```

**Trace:**

1. Old payload: varint encoding for int32.
2. New reader expects length-delimited string.
3. Parse error or garbage in the field.
4. Intermittent fail depends on the value.

**Correct:**

```proto
reserved 5;
reserved "count";
string count_text = 9;
```

Migration: dual-write / feature flag / backfill as needed.

### 8. Trace D — semantic change without type change

Field 2: `balance_cents` → team decides to send majors, renames to `balance`, same number 2.

**Predict:** does the wire “work”?  
**Verify:** yes. Is it compatible? **No** — that is a semantic break. Same shape of incident as reuse, just without deletion.

Rule: new meaning = new number (or v2), old reserved or clearly deprecated with a parallel period.

### 9. Trace E — enum evolution

```proto
enum State {
  STATE_UNSPECIFIED = 0;
  STATE_OPEN = 1;
  STATE_CLOSED = 2;
  // new:
  STATE_ARCHIVED = 3;
}
```

**Trace new server → old client:**

1. Server sends `ARCHIVED = 3`.
2. Old client has no name for 3.
3. Generated code often keeps the numeric value / “unrecognized”.
4. UI if it does `switch` without `default` — panic or blank.

**Predict then verify:** predict what your `switch` does for an unknown enum; verify you have a `default` branch “unknown / upgrade client”.

**Dangerous:** change the meaning of an existing enum value (`1` was OPEN, now means CLOSED).

**Dangerous:** put a useful value on 0.

### 10. Trace F — deletion with and without reserved

**Without reserved:** protoc does not prevent reuse → a time bomb.  
**With reserved:** protoc/CI breaks a PR that tries reuse → a cheap fuse.

Team mechanism: *every* deletion in the same PR adds `reserved` number + name + date comment.

### 11. `v2` package mechanism

When compatibility is impossible:

```proto
package billing.v2;

message Invoice {
  string id = 1;
  Money total = 2;
}

message Money {
  int64 minor = 1;
  string currency = 2;
}
```

Use `v2` when:

- you cannot correctly read old messages;
- semantics break broadly;
- a series of “small” breaking changes in `v1` would be worse than a clean cut.

Do not force `v2` for cosmetics (renaming for looks).

Migration flow:

1. Publish `v2` alongside `v1`.
2. Dual support in the server.
3. Migrate clients.
4. Turn off `v1` when metrics say it is dead — not by feeling.

### 12. Test matrix — verification mechanism

```text
              | old client | new client
--------------+---------------+-------------
old server  | baseline      | must work (ignore new)
new server   | must work   | baseline
```

If any “must work” cell fails — you are not compatible.

Extended matrix for a queue:

| Payload in queue | Consumer vN | Consumer vN+1 |
|----------------|-------------|---------------|
| old | OK | OK (defaults) |
| new | OK (ignore) | OK |

A queue keeps bytes for a long time — number reuse in an event schema is especially dangerous.

### 13. Predict then verify — lab

**Lab 1:** Take a message, “delete” a field correctly with `reserved`. Predict whether `protoc` accepts `string novo = <same number>`. Verify — it should reject.

**Lab 2:** Plan a migration `int32` → wider values. Predict why the same number does not pass. Verify the plan: new field + dual-read.

**Lab 3:** Draw an old/new matrix for adding `currency`. Fill the cells before you look at the lesson above.

**Lab 4:** Enum + unknown value. Predict UI without `default`. Verify in code that `default` exists.

**Lab 5:** Decide on paper: does this change go into `v1` compatibly or require `v2`. Write *one* criterion.

### 14. Deprecate mechanism (without fake reuse)

Markers / comments:

```proto
message User {
  string id = 1;
  // Deprecated: use email_primary = 4. Kept for reading old payloads.
  string email = 2 [deprecated = true];
  string email_primary = 4;
}
```

- Do not delete immediately if old payload still lives.
- Do not change the meaning of `email`.
- When everyone has moved: `reserved 2` + remove the field.

### 15. Dual-write / dual-read mechanism (Go side)

Flow:

1. New field `amount_minor = 8` next to old `amount = 2` (while migration lasts — old later reserved).
2. Writer writes both during the window.
3. Reader prefers new; falls back to old.
4. When metrics say old is dead — stop writing old, reserved.

```go
func Amount(e *pb.Event) int64 {
	if e.GetAmountMinor() != 0 {
		return e.GetAmountMinor()
	}
	// legacy path — document and remove after migration
	return e.GetAmount()
}
```

(Adapt presence if 0 is not a valid sentinel — that is why `optional` exists.)

### 16. Rollout window — operational mechanism

Compatibility is not only schema. It is also deploy order:

1. First deploy code that *reads* new (and ignores/does not require).
2. Then deploy code that *writes* new.
3. The reverse often breaks older readers that are not ready yet (depends on the change).

For a pure additive field: new writers + old readers usually OK (ignore). For removal: first stop reading the dependency, then reserved.

### 17. Anti-patterns

1. “There are no more old clients” without metrics.
2. Reuse because the number is “nice”.
3. Breaking in `v1` because “we’re not in production yet” — but there is staging with durable data.
4. Enum without an unknown branch.
5. Type change “temporarily”.
6. Deletion without `reserved`.
7. `v2` because of a rename for taste.
8. Believing that regenerating all services on the same day solves wire history (queue/log still exist).

### 18. Mechanism checklist before merging a proto PR

- [ ] New fields = new numbers
- [ ] Deleted = `reserved` (number + name) + comment
- [ ] No type change on the same number
- [ ] No silent semantic change
- [ ] Enum: 0 UNSPECIFIED; new values OK; unknown handling
- [ ] Unit / semantics comments
- [ ] Generate + test
- [ ] Old×new matrix filled
- [ ] Do we need `v2`?
- [ ] Rollout order written in the PR description

### 19. Link to generate (06.03)

Versioning a schema without pinned generate and CI diff = people think “everyone is on the same schema” while laptops lie. The evolution mechanism includes tooling discipline: same script, same pin, diff.

### 20. Mechanism summary

The wire remembers numbers forever. `reserved` is a fuse. Adding with a new number is the default happy path. Changing type/semantics on the same number is an incident in preparation. Enum requires an unknown branch. `v2` is a clean break when it must. The old×new matrix is not bureaucracy — it is a cheaper post-mortem.

### 21. Trace G — “we only renamed” (semantics)

The team says: we renamed `tax_code` to `fiscal_code`, same number 4, same `string` type — “not breaking”.

**Wire:** often OK.  
**People / integrations / documentation:** often a break.  
**Generated Go:** break until everyone regenerates and adapts identifiers.

**Predict then verify:** predict whether a mobile client that logs the JSON field name (if it uses proto JSON mapping) sees the old or new name — depends on options; do not treat rename as free. For public contracts prefer a new field + deprecate the old.

### 22. Trace H — narrowing validation vs schema

The schema allows `qty = -1` (`int32`). Application v1 rejects negative. Application v2 “relaxes” and accepts.

**Is that protobuf breaking?** Not at the wire level.  
**Can it break business assumptions?** Yes.

Mechanism: separate *wire compatibility* from *application contract*. Both need review — but tools (`reserved`, field numbers) cover the wire layer.

### 23. Documenting the change in a PR

Required template (adapt to the team):

```text
## Proto change
- Type: additive | reserved | v2 | other
- Field numbers added: ...
- Field numbers reserved: ...
- Enum values added: ...
- Old×new matrix: (link or table)
- Rollout: readers first / writers first
- Do consumers need regenerate: yes/no
```

**Predict:** a PR without this section — how many reviewers catch reuse?  
**Verify:** almost none reliably. The template is part of the mechanism.

### 24. Parallel consumers mechanism (fan-out)

One producer, five consumer services.

```text
producer vN+1 writes new field 12
consumer A already on N+1 → reads 12
consumer B still on N → ignores 12
consumer C still on N, but the app *requires* field 12 in logic after hand parsing → BREAK
```

**Conclusion:** ignore unknown helps the generated protobuf path. If someone hand-parses or hard-requires a field before all consumers know about it — the matrix breaks. Rollout: first everyone *can* ignore/read, only then *require*.

### 25. “Dry-run” compatibility mechanism in a test

Illustration (conceptual):

```go
// old shape without currency
old := &pb.Invoice{Id: "1", TotalMinor: 100}
b, _ := proto.Marshal(old)

// new type with currency field in the schema
newMsg := &pb.Invoice{}
_ = proto.Unmarshal(b, newMsg)
if newMsg.GetCurrency() != "" {
	t.Fatal("expected default empty currency")
}
```

**Predict then verify:** predict that `TotalMinor` survives; verify with a test after generate. Reverse test: marshal new with currency, unmarshal into “old” generated code (or an older type copy) — field 3 is ignored.

### 26. When adding a field alone is *not* enough

- You change the identification model (ID scheme).
- You merge two fields into one with different semantics.
- You remove a required business assumption that old clients still send as a different meaning.
- Event sourcing / audit requires the old shape to stay readable forever → often `v2` alongside `v1`, not overwrite.

Then the mechanism leads to `package .v2` + a migration plan, not to “one more field”.

### 27. Mechanism summary (checklist in your head)

1. New number or reserved — there is no third.  
2. Type and semantics on a number are forever.  
3. Enum grows; unknown is handled.  
4. Old×new matrix before merge.  
5. Rollout order is part of the change.  
6. `v2` when it must, not when it itches.

### 28. Trace I — deleted field still lives in the DLQ

**Scenario:** field 4 reserved in the schema. The dead-letter queue still has messages with field 4 from last quarter.

**Trace:**

1. New consumer ignores field 4 (reserved / no field) — OK for reading.
2. Someone “brings back” field 4 with new meaning because “reserved is annoying”.
3. DLQ replay fills new meaning with old bytes — incident.

**Predict then verify:** predict whether retention policy enters the decision about `reserved` duration. Verify: yes — while an old byte exists, the number stays dead.

### 29. Communicating to schema consumers

An internal Slack “hey regenerate” is not enough. Minimum:

1. CHANGELOG / release note for the proto module.
2. Which numbers were added / reserved.
3. Whether code deploy is needed before the producer starts writing new.
4. Deadline for removing the dual-read path.

Without that, the old×new matrix exists only in the PR author’s head.

### 31. Predict then verify — final scenarios

**Scenario A:** you add `bool newsletter = 15`. Predict all four old×new cells. Verify with the table from Trace B.

**Scenario B:** you change `string sku = 1` into `int64 sku_num = 1`. Predict whether that is additive. Verify: it is not — reserved + new field or v2.

## Rules and syntax

| Rule | Why |
|---------|-------|
| Never reuse a number | old bytes lie |
| `reserved` after deletion | forces discipline |
| New number for new meaning | even if “same name” |
| Do not change type on the same number | wire type / semantics |
| `package .v2` for a break | clear boundary |
| Enum 0 = UNSPECIFIED | zero value |
| Document | comment + proto CHANGELOG |
| Test old×new | queues and mobiles live long |

`reserved` syntax (reminder):

```proto
reserved 2, 15, 9 to 11;
reserved "foo", "bar";
```

## Examples

### Example 1: Adding a field

```proto
message Invoice {
  string id = 1;
  int64 total_minor = 2;
  // added later
  string currency = 3;
}
```

### What happens here

Old senders without `currency` still work. New readers use the default empty string or an application default (`RSD`).

### Example 2: Deletion with reserved

```proto
message Invoice {
  reserved 4;
  reserved "tax_code";
  string id = 1;
  int64 total_minor = 2;
  string currency = 3;
}
```

### What happens here

Field 4 was once `tax_code`. Now it is forbidden. The compiler/protoc reports if someone tries reuse.

### Example 3: Dangerous type change

```proto
// was:
// int32 count = 5;
// WRONG:
string count = 5;
```

### What happens here

Wire interpretation breaks. Correct: new field `string count_text = 9` + migration; old reserved.

### Example 4: v2 package

```proto
package billing.v2;

message Invoice {
  string id = 1;
  Money total = 2;
}

message Money {
  int64 minor = 1;
  string currency = 2;
}
```

### What happens here

When the model changes substantially, `v2` is clearer than a series of breaking changes in `v1`.

### Example 5: Go — default strategy

```go
cur := inv.GetCurrency()
if cur == "" {
	cur = "RSD"
}
```

### What happens here

Presence/default strategy lives in Go code too. The schema gives the frame; the domain confirms the default.

### Example 6: Enum with an unknown branch

```go
switch o.GetStatus() {
case pb.OrderStatus_ORDER_STATUS_PENDING:
	// ...
case pb.OrderStatus_ORDER_STATUS_PAID:
	// ...
case pb.OrderStatus_ORDER_STATUS_UNSPECIFIED:
	// treat as input error
default:
	// unknown future value — do not panic
	log.Printf("unknown status: %v", o.GetStatus())
}
```

### What happens here

Additive enum evolution does not break runtime if the application has `default`.

### Example 7: Graveyard comment

```proto
message Session {
  // reserved history:
  // 2 = old_token (bytes) removed 2026-01
  reserved 2;
  string id = 1;
  string token = 3;
}
```

### What happens here

People see *why* 2 is dead — not only that it is.

## Decision analysis

**reserved always on deletion?** Yes — a cheap fuse.

**When v2?** When you cannot read old messages correctly or semantics break broadly.

**Enum extension** — OK, but old code must handle unknown values.

**Rename of the same number** — wire often OK; local API and clarity suffer. Do it rarely and with communication.

**Dual-write how long?** Until metrics show the legacy path is cold — not until “next sprint” by default.

## Trade-offs

| Strategy | Advantage | Cost |
|------------|----------|------|
| Only add fields | simple | messages grow |
| reserved discipline | safety | team discipline |
| v2 package | clean break | two contracts in parallel |
| Quiet meaning change | “fast” | production incidents |
| Dual-write | smooth migration | temporary complexity |
| Forced big-bang regenerate | “clean” | unrealistic with mobile/queue |

## Common mistakes

1. Reusing a number after delete.
2. Changing type on the same number.
3. Assuming all clients will regenerate on the same day.
4. No `reserved` names — someone brings back the same name with another number and confuses people (less dangerous than number reuse, still bad).
5. Breaking in `v1` because “we’re not in production yet” — but you are.
6. Enum without unknown / default branch.
7. Changing semantics (units) on the same number.
8. Deleting a field that the queue still reads, without a migration window.
9. `v2` for cosmetics.
10. Old×new matrix “in your head” instead of in the PR.

## Idiomatic Go / proto

- Review proto as a public API.
- A “deleted fields” table in a file comment if needed.
- Feature flags + dual write during migration.
- Test old binary × new code and new binary × old code.
- Do not force v2 for cosmetics.
- In Go `switch` on enum: always `default`.
- Getters + explicit domain defaults.
- Pin generate (06.03) so everyone talks about the same schema.

## Practical scenario

The team deletes `bool promo` (field 7), a month later adds `int64 promo_id = 7`. Old mobile clients send `promo=true` as varint 1; the server interprets `promo_id=1` and activates wrong promotions. Incident. Fix: `reserved 7` + new field `8`.

The post-mortem becomes a required lesson:

1. Every deletion → `reserved` in the same PR.
2. Old×new checklist in the PR template.
3. Queue retention enters the “may we delete” decision.
4. Onboarding for new engineers includes this scenario — not only proto3 syntax.

## Summary

Versioning protobuf messages rests on eternal field numbers, a `reserved` graveyard, and an honest `v2` when compatibility is impossible. Adding fields with a new number is the happy path; reuse and type/semantics change are incidents. Discipline here saves production.
