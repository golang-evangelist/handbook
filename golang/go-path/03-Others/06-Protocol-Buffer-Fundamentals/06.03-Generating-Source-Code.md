# 06.03 Generating source code from protobuf

> **Go Path - Zero to Gopher** / **03 Others → Protocol Buffer Fundamentals** / Lesson 06.03

## Lesson goals

After this lesson you will be able to:

- run `protoc` with the `protoc-gen-go` plugin;
- set `option go_package` correctly (import path + optional package name);
- fit generate into `go generate` / a script with pinned versions;
- distinguish `paths=source_relative` and `paths=import`;
- verify that the generated package matches the `go.mod` path;
- avoid invented flags and “copy-paste from a forum” that do not exist.

## Prerequisite

- 06.01–06.02 (schema, messages, field numbers).
- Installed `protoc` (Protobuf compiler).
- Ability to `go install` / `go run` for `google.golang.org/protobuf/cmd/protoc-gen-go`.
- Go 1.22+.
- A basic feel for the `go.mod` module path.

## Problem this lesson solves

The most common failure: `protoc-gen-go: program not found`, a wrong import path, mixing old and new protobuf modules, or generated files in the wrong directory. This lesson focuses on *reproducible* generation for Go — carefully, with real options.

The goal is not “memorize 20 flags”. The goal is: one predictable flow that works the same on a laptop and in CI.

## Mental model

```text
protoc
  reads .proto (+ -I / --proto_path for imports)
  calls plugin protoc-gen-go (PATH or --plugin)
  writes *.pb.go according to go_package + --go_out / --go_opt
```

```text
.go.mod module path
        ↑ must match
option go_package = "module/path/to/pkg;pkgname"
        ↑ leads to
physical directory in the repo (with the chosen paths mode)
```

`go_package` says *which Go import path* (and optionally the package name). Without alignment: `go build` fails or you import the wrong package.

### Terminology table

| Term | Meaning |
|--------|----------|
| `protoc` | Protobuf compiler (reads `.proto`, calls plugins) |
| `protoc-gen-go` | plugin that generates Go for messages/enums |
| `go_package` | `option` in `.proto` for the Go import path |
| `--go_out` | output directory for the Go plugin |
| `--go_opt` | options for the Go plugin (e.g. `paths=...`) |
| `paths=source_relative` | `*.pb.go` next to `.proto` (relative) |
| `paths=import` | output by import path from `go_package` |
| `--proto_path` / `-I` | where `protoc` looks for imported `.proto` files |
| pin | fixed tool version in script/CI |
| `//go:generate` | Go directive for the generate step |

## Mechanism

The generation mechanism: from `go_package` to bytes on disk, through PATH, pin, `paths`, imports, and a `go build` check.

### 1. What the chain actually does

1. You write / change a `.proto`.
2. `protoc` parses the schema (syntax, imports).
3. `protoc` runs `protoc-gen-go` as a plugin (plugin stdin/stdout protocol — you do not need to know it by heart).
4. The plugin emits `*.pb.go` with types, descriptors, `ProtoReflect`, etc.
5. Your hand-written code imports that package and calls `proto.Marshal` / domain logic.

Without steps 2–4 there are no types. Hand-writing an equivalent of `*.pb.go` is not the course style.

### 2. `go_package` — the contract with the Go module

Minimum:

```proto
option go_package = "example.com/shop/gen/shoppb";
```

With an explicit package name:

```proto
option go_package = "example.com/shop/gen/shoppb;shoppb";
```

Mechanism:

- Left of `;` (or the whole string value): **import path**.
- Right of `;`: **package name** in the Go file (if you want it to differ from the last path segment).

If the module is `example.com/shop`, import `example.com/shop/gen/shoppb` expects a package under that path in that module (with `source_relative` caveats — see below: you still must align how you package the code).

### 3. Basic command (real flags)

```text
protoc --go_out=. --go_opt=paths=source_relative api.proto
```

What is real here:

| Part | Role |
|-----|--------|
| `protoc` | compiler |
| `--go_out=.` | output root for the Go plugin |
| `--go_opt=paths=source_relative` | path mode |
| `api.proto` | input |

Often you also need an include path:

```text
protoc -I . --go_out=. --go_opt=paths=source_relative .\shop\v1\ping.proto
```

`-I` / `--proto_path` — where `import "..."` is resolved.

**Do not invent flags.** If you are unsure, `protoc --help` and `protoc-gen-go` documentation, not a random blog post.

### 4. `paths=source_relative` vs `paths=import`

**`paths=source_relative`**

- Output goes relative to the input `.proto` (next to the file, under the `--go_out` root).
- Simpler for small repos: `shop/v1/ping.proto` → `shop/v1/ping.pb.go`.
- The Go import path still comes from `go_package` — the physical path must align with the module layout.

**`paths=import`**

- Output follows the import path from `go_package`.
- Useful when you want a strict layout under the `--go_out` root.

**Predict then verify:**

- Predict where `ping.pb.go` will appear for both modes.
- Verify with one generate; do not guess in a PR.

### 5. Plugin on PATH — the most common mechanism on Windows

```text
go install google.golang.org/protobuf/cmd/protoc-gen-go@v1.34.2
```

Then ensure `$(go env GOPATH)\bin` is on `PATH`:

```powershell
$env:PATH = "$(go env GOPATH)\bin;" + $env:PATH
protoc-gen-go --version
```

`protoc` looks for the executable `protoc-gen-go` by plugin naming convention. If it is missing: `protoc-gen-go: program not found`.

Alternative: `--plugin=protoc-gen-go=path\to\protoc-gen-go.exe` (a real `protoc` option) when you do not want to touch PATH.

### 6. Pin versions — the reproduction mechanism

Without a pin:

- five developers, five plugin versions;
- every PR changes the whole `*.pb.go` style/details;
- review becomes noise.

With a pin:

```powershell
$ver = "v1.34.2"
go install google.golang.org/protobuf/cmd/protoc-gen-go@$ver
```

Also pin the `protoc` version in a README table. CI uses the same numbers.

Note: versions in this lesson are an **example of pinning**, not “the only correct forever”. Choose the version the team holds; the course requires pin discipline, not a cult of one number.

### 7. Trace A — happy path generate

**Input:** `ping.proto` with `go_package = "example.com/shop/gen/shoppb;shoppb"`.

**Trace:**

1. `protoc` successfully parses `syntax` / `package` / `message`.
2. Finds `protoc-gen-go` on PATH.
3. Plugin generates `PingRequest`, `PingReply`, methods, file descriptor.
4. File lands where `paths` says.
5. `go build ./...` passes because the import path exists.

**Predict then verify:** predict the Go field name for `string msg = 1` → `Msg`; verify in `*.pb.go`.

### 8. Trace B — plugin not found

**Trace:**

1. `protoc --go_out=...` starts.
2. Looks for `protoc-gen-go` — it is not there.
3. Error: program not found.
4. No `*.pb.go` or the old one remains.

**Check / fix:** `go install` + PATH, or `--plugin=...`. Again `protoc-gen-go --version`.

### 9. Trace C — wrong `go_package`

```proto
option go_package = "example.com/wrong/shoppb";
```

**Trace:**

1. Generate “succeeds”.
2. Hand-written code imports `example.com/shop/gen/shoppb`.
3. `go build` does not find the package / finds an empty path.
4. An hour lost on “why doesn’t it see the type”.

**Predict then verify:** deliberately break `go_package`, generate, read the `go build` error. Restore correctly. Remember the error — you debug faster next time.

### 10. Trace D — `paths` confusion

Same proto, once `source_relative`, once `import`, same `--go_out=gen`.

**Predict:** two different places for `*.pb.go`.  
**Verify:** run both (in a scratch branch), compare the tree. Choose one mode per repo — do not mix without documentation.

### 11. Trace E — forgotten `-I`

Proto A imports `"shop/v1/types.proto"`, but `protoc` is run without `-I` to the root where that file lives.

**Trace:** `File not found` / import error.  
**Check:** add `-I` to the API tree root. Do not “copy everything into one folder” as a permanent fix.

### 12. `go generate` mechanism

```go
package shoppb

//go:generate protoc --go_out=. --go_opt=paths=source_relative ./ping.proto
```

Flow:

1. `go generate ./...` or `go generate -x` (see the command).
2. The shell executes the directive from the package.
3. Requires that `protoc` and the plugin are available in that environment.

Document in the README: “how to generate”, “which versions”, “what CI checks”.

### 13. PowerShell script — one entry for people and CI

```powershell
$ErrorActionPreference = "Stop"
$ver = "v1.34.2"
go install google.golang.org/protobuf/cmd/protoc-gen-go@$ver
$env:PATH = "$(go env GOPATH)\bin;$env:PATH"
protoc -I . --go_out=. --go_opt=paths=source_relative .\api\shop\v1\*.proto
```

Discipline mechanism:

- same script locally and in CI;
- pin at the top;
- fail-fast (`Stop`).

### 14. Messages only vs + gRPC

```text
--go_out        => messages, enums (this lesson)
--go-grpc_out   => gRPC service stubs (another plugin; gRPC block)
```

Do not mix them in your head: `protoc-gen-go` ≠ `protoc-gen-go-grpc`. For pure messages `--go_out` is enough.

### 15. Old vs new Go protobuf modules

Modern course flow: `google.golang.org/protobuf`.

Legacy: `github.com/golang/protobuf` (older API). Mixing without a migration plan = pain. If you inherit old code, migrate consciously; do not add new generate next to old on the same types without a strategy.

### 16. CI diff mechanism

1. CI installs pinned `protoc` + `protoc-gen-go`.
2. Runs the same generate script.
3. `git diff --exit-code` on `*.pb.go` (or equivalent).
4. If there is a diff → someone committed stale generate or a different tool version.

That closes the reproduction loop.

### 17. Predict then verify — lab

**Lab 1:** Add `go_package`, generate `PingReply`, import in `main`, `go build`.

**Lab 2:** Deliberately remove the plugin from PATH. Predict the error. Verify. Restore PATH.

**Lab 3:** Change only a field name in proto, regenerate. Predict whether the wire number changes (no). Check the diff in `*.pb.go` (field name / JSON name options — read the diff).

**Lab 4:** Add `//go:generate`, run `go generate -x`. Predict the exact command line. Check `-x` output.

**Lab 5:** Record in a table: `protoc` version, `protoc-gen-go` version, `paths` mode, script path.

### 18. Buf — orientation, not a course requirement

Large teams use Buf (lint, generate, breaking detection). Same idea: pin, reproduction, contract in `.proto`. For this course `protoc` + `protoc-gen-go` is enough. Know that an alternative exists; do not learn Buf flags here as if they were part of the required flow.

### 19. Generate mechanism anti-patterns

1. Generate “however it works on my laptop” without a pin.
2. Commit `*.pb.go` from one version, CI from another.
3. Hand-edit a generated file “just this getter”.
4. `go_package` copy-paste from another repo.
5. Mixing `source_relative` and `import` in the same repo without documentation.
6. Generating into `vendor/` by accident.
7. Invented flags from a Stack Overflow snippet without checking `--help`.

### 20. Mechanism checklist

- [ ] `protoc --version` works
- [ ] `protoc-gen-go --version` works (pin)
- [ ] `go_package` matches the module path
- [ ] Chosen and documented `paths=...`
- [ ] `-I` covers imports
- [ ] `go test ./...` / `go build ./...` passes

- [ ] CI diff policy agreed

### 21. Minimal proto for a generate exercise

```proto
syntax = "proto3";

package shop.v1;

option go_package = "example.com/shop/gen/shoppb;shoppb";

message PingRequest {}
message PingReply { string msg = 1; }
```

Command (example, `source_relative`):

```text
protoc -I . --go_out=. --go_opt=paths=source_relative .\shop\v1\ping.proto
```

Hand-written code:

```go
import shoppb "example.com/shop/gen/shoppb"

func NewPing() *shoppb.PingReply {
	return &shoppb.PingReply{Msg: "pong"}
}
```

### 22. What to look at in `*.pb.go` after the first generate

Do not memorize the whole file. Look for:

- `type PingReply struct`
- field `Msg string`
- `func (x *PingReply) GetMsg() string`
- header `Code generated ... DO NOT EDIT`
- `const` / enum numbers if there is an enum

That is the bridge from the 06.01–06.02 mental model to the real Go API.

### 23. Mechanism summary

Generation is a reproduced chain: schema → `protoc` → pinned `protoc-gen-go` → `*.pb.go` on a predictable path → an import that `go build` accepts. `go_package` and `paths` are not decoration — that is half a debug session when something “cannot find the package”.

### 24. Trace F — stale generated in a PR

**Scenario:** a developer changes `.proto`, forgets generate, sends a PR.

**Trace:**

1. Reviewer sees the schema change.
2. `*.pb.go` is still old.
3. CI (if there is no diff check) merges a false truth.
4. Local `go generate` for another developer produces a huge diff tomorrow.

**Predict then verify:** predict whether `go test` always catches stale generate. Verify: not necessarily — that is why CI `git diff --exit-code` after generate exists.

### 25. Trace G — two `go_package` in the same file? No.

One `.proto` file — one `option go_package`. If you share types between services, you share **files/packages**, not “two go_package in one file”.

**Predict:** what if copy-paste adds a second `go_package`?  
**Verify:** `protoc` reports a conflict / the last one wins depending on the tool — do not rely on it; keep one.

### 26. Imported proto file mechanism

```proto
// types.proto
syntax = "proto3";
package shop.v1;
option go_package = "example.com/shop/gen/shoppb;shoppb";
message Money { int64 amount_minor = 1; string currency_code = 2; }

// order.proto
syntax = "proto3";
package shop.v1;
option go_package = "example.com/shop/gen/shoppb;shoppb";
import "shop/v1/types.proto";
message Order { string id = 1; Money total = 2; }
```

**Trace:**

1. `protoc -I . ... shop/v1/order.proto`
2. Resolver finds `shop/v1/types.proto` via `-I`.
3. Both files share the same `go_package` → types in the same Go package (a common simple layout).
4. Without `-I`: import fail.

**Rule:** align the `go_package` strategy for all files that should live in the same Go package.

### 27. Mechanism of what is *not* in this lesson (so you do not invent)

This lesson does **not** cover as required:

- invented `--go_opt` keys beyond documented ones (`paths=...`);
- hand-tuning JSON names except when the team explicitly uses known options;
- Buf CLI flags as part of the course;
- gRPC plugin details (`protoc-gen-go-grpc`) — only a note that it exists separately.

If you need an option: check the official `protoc-gen-go` documentation for *your* pinned version.

### 28. Step-by-step first time (Windows / PowerShell)

1. Install `protoc` (distribution / package manager) — check `protoc --version`.
2. `go install google.golang.org/protobuf/cmd/protoc-gen-go@v1.34.2`
3. Add `$(go env GOPATH)\bin` to PATH in the session.
4. `protoc-gen-go --version` — must print a version.
5. Write `ping.proto` with `go_package`.
6. Run `protoc -I . --go_out=. --go_opt=paths=source_relative ...`
7. Open `*.pb.go` — confirm `DO NOT EDIT`.
8. Write a small Go file that imports the package.
9. `go build` / `go test`.
10. Record versions in the README.

**Predict then verify at step 3:** predict the error if you skip PATH; verify `program not found`.

### 29. Alignment mechanism with `go.mod`

```text
module example.com/shop

go_package = "example.com/shop/gen/shoppb;shoppb"
physical:     gen/shoppb/*.pb.go   (or shop/v1/*.pb.go with source_relative + correct import path layout)
```

If `go_package` says `example.com/other/...` and the module is `example.com/shop`, `go build` of your services will not “magically” find types in this repo.

**Alignment checklist:**

- [ ] module path
- [ ] go_package import path
- [ ] folder on disk
- [ ] import in hand-written code
- [ ] same `paths` mode as in the documentation

### 30. Mechanism summary (again, operationally)

Pin → PATH → `go_package` → `paths` → `-I` → generate → `go build` → CI diff. Skip any step and debugging becomes folklore instead of engineering.

### 31. Trace H — generate in the wrong working directory

**Scenario:** the script runs `protoc ... .\api\shop\v1\*.proto` but is started from `scripts/` without `-I` toward the root.

**Trace:**

1. Relative paths break.
2. Import `"shop/v1/types.proto"` does not find the file.
3. Or `*.pb.go` output ends up in an unexpected folder.

**Predict then verify:** predict the difference when you run the script from root vs `scripts/`. Verify: in the script `Set-Location` to the repo root or use absolute `-I` paths.

### 32. One source of truth for the command

Keep **one** canonical command:

```text
scripts/gen-proto.ps1
```

Everything else (README snippet, `go:generate`, CI step) calls the same script or identical arguments. Duplicating flags in three places = three ways to diverge.

**Predict:** what happens when the README says `paths=import` and the script `source_relative`?  
**Verify:** developer A follows the README, B the script — two layouts, one chaos. One source.

### 33. Post-generate check mechanism (minimal Go)

```go
package shop_test

import (
	"testing"

	"google.golang.org/protobuf/proto"
	shoppb "example.com/shop/gen/shoppb"
)

func TestPingSmoke(t *testing.T) {
	in := &shoppb.PingReply{Msg: "ok"}
	b, err := proto.Marshal(in)
	if err != nil {
		t.Fatal(err)
	}
	out := &shoppb.PingReply{}
	if err := proto.Unmarshal(b, out); err != nil {
		t.Fatal(err)
	}
	if out.GetMsg() != "ok" {
		t.Fatalf("got %q", out.GetMsg())
	}
}
```

Include the smoke test in the same PR as generate. Catches obvious import/type breaks.

### 34. What to do when the `*.pb.go` diff looks “huge” and the proto change is small

1. Compare the `protoc-gen-go` version locally vs CI.
2. Check that you did not change `paths` or `go_package`.
3. Check that you did not turn on another plugin by accident.
4. If style/field order in the generated file changed due to a plugin bump — either pin back, or accept a one-time bump in a separate PR (tooling only, no schema).

**Predict then verify:** bump the plugin in an isolated PR; predict a large diff; verify that the schema was not touched.

### 35. Output file naming mechanism

`protoc-gen-go` typically produces `name.pb.go` from `name.proto`. Do not rename by hand to `types_gen.go` — the next generate restores the old name or creates a duplicate.

**Predict:** what if you commit `ping_gen.go` that is a copy of `ping.pb.go`?  
**Verify:** two sources of truth; `go build` may see type redefinitions. Keep only the generated name.

### 36. Final check before you say “generate works”

```text
[ ] protoc --version
[ ] protoc-gen-go --version (pin)
[ ] go_package aligned
[ ] paths documented
[ ] -I covers imports
[ ] *.pb.go appeared where you expect
[ ] go build ./... OK
[ ] smoke Marshal/Unmarshal test OK
[ ] CI uses the same script
```

If all hold — tooling is no longer a mystery; you can return to message design and versioning.

## Rules and syntax

| Element | Recommendation |
|---------|-----------|
| `go_package` | always set |
| Plugin | pin the version (`go install ...@vX.Y.Z`) |
| Out | clear `gen/` or `api/...` structure |
| `paths` | one mode per repo + document it |
| `-I` | explicit for imports |
| Commit | team agreement + CI diff |
| Do not mix | old `github.com/golang/protobuf` with new without a plan |
| Do not invent | flags outside `--help` / official docs |

For gRPC you add `--go-grpc_out` (separate plugin) — this lesson is on messages.

## Decision analysis

**source_relative vs import** — source_relative simpler for small repos; import for a strict layout under one out root.

**gen/ in the same module** — yes for most Go services.

**Separate API module** — when multiple services share proto and you want independent Go module versioning.

**go generate vs make/ps1** — `go generate` close to the code; a script better when you have multiple languages / multiple plugins.

**Commit generated code** — common Go style (reproduction + CI diff). If the team does not commit, CI must generate + cache strategy — agree explicitly.

## Trade-offs

| Approach | Advantage | Cost |
|---------|----------|------|
| go install plugin | simple `protoc` | local PATH |
| Docker generate | identical CI/local | slower, image maintenance |
| Buf | lint + ecosystem | new tool |
| No pin | fast at the start | diff chaos |
| source_relative | simple layout | import alignment discipline |
| Separate API module | clean boundary | more repos / tags |

## Common mistakes

1. `protoc-gen-go: program not found`.
2. Wrong `go_package` — import does not exist.
3. Mixing `paths` options and wondering where the file is.
4. Generating into `vendor` by accident.
5. Two different plugin versions on laptop and CI.
6. Hand-editing `*.pb.go`.
7. Copy-paste of invented / outdated flags.
8. Mixing old and new protobuf Go APIs without a plan.
9. Forgotten `-I` when there is `import` between proto files.
10. Generate without a `go build` check in the same PR.

## Idiomatic Go

- `gen/...pb` or `api/.../v1` layout.
- Pin in a script or README version table.
- Respect `// Code generated ... DO NOT EDIT.`
- `go generate` or `make proto` / `scripts/gen-proto.ps1`.
- CI diff on generated files.
- `google.golang.org/protobuf` as the modern import.
- After generate: a small compile test / roundtrip test.

## Practical scenario

Five developers, five `protoc-gen-go` versions, every PR changes the whole `*.pb.go` style. The reviewer cannot see the real schema change in the noise.

They introduce `scripts/gen-proto.ps1` with a pin and CI that fails on diff. After a week diffs are only real schema changes. Onboarding: “run the script, do not invent flags”.

Second incident: wrong `go_package` in a new service — hours of “why doesn’t it see Account”. A checklist with `go_package` + `go build` in the same PR closes the hole.

## Summary

Generating Go code from protobuf requires an aligned `go_package`, a pinned `protoc-gen-go`, and a predictable out path (`paths` + `--go_out`). Without that, tooling eats more time than the API design itself. Use real flags; check `go build`; do not edit generated code.

Note: the pinned plugin version in the examples is an illustration of discipline, not an eternal obligation to one number — choose the team version and keep it the same everywhere.
