# 03.01 Introduction to gRPC in Go

> **Go Path - Zero to Gopher** / **03 Others → gRPC Fundamentals in Go** / Lesson 03.01

## Lesson goals

After this lesson you can:

- explain what RPC is and how it differs from a typical REST JSON HTTP API;
- connect gRPC with HTTP/2, Protocol Buffers, and IDL (`.proto`);
- sketch the flow: `.proto` → generated stub → server/client;
- follow what happens on the wire for a unary call (bytes, frames, status);
- know what comes in the next lessons (server, client, stream).

## Prerequisite

- Basic Go: `package`, `interface`, `error`, `context`.
- Basic networking concepts: TCP, HTTP request/response at least at client level.
- Preferred: 02.02 (protoc-gen-go) and awareness of `go generate`.
- Go 1.22+.

## Problem this lesson solves

Teams often “try gRPC” without a model: they mix in REST habits, expect human-readable JSON on the wire, or do not understand why they need `protoc`. Without the foundations (RPC + HTTP/2 + protobuf + IDL), configuration looks like magic, and errors (`Unavailable`, `DeadlineExceeded`) stay opaque. This lesson builds vocabulary and a call trace before server code.

## Mental model

```text
  Client --(HTTP/2 stream + protobuf bytes)--> Server
              ^
              |
         contract in .proto (IDL)
         generated stubs in Go
```

Four concepts you must keep separate:

| Concept | What it is | What it is not |
|-------|--------|----------|
| **RPC** | a remote procedure call over the network, with errors and deadline | “the same stack” as a local call |
| **IDL** | an API description language (`.proto`) | a Go implementation |
| **Protobuf** | a binary message format | JSON, XML |
| **HTTP/2** | transport (multiplex, streams, headers) | REST resource style |

gRPC = conventions + generation + libraries around that combination. One `.proto` is the contract; Go, Java, C#, and Node can have different stubs, but the same wire contract.

## Mechanism

### RPC versus a local call

Locally:

```go
reply := SayHello(req) // an error is rarely “network”
```

RPC:

```go
reply, err := client.SayHello(ctx, req)
```

`err` can be a business error *or* transport/timeout/cancel. That is why gRPC status codes (`codes.InvalidArgument`, `codes.Unavailable`, …) exist separately from HTTP 404/500 habits. The deadline comes through `context` — not through a hidden global timeout.

### IDL: one contract, multiple languages

You write the service and messages in `.proto`. That is not “documentation”; it is input to a generator. Without IDL every language invents its own DTO and the contract falls apart.

Throughout this block we use a small **Catalog** service (consistent across 03.01–03.04):

```proto
syntax = "proto3";

package demo.v1;

option go_package = "example.com/demo/gen/demopb;demopb";

// Catalog is a small sample contract for the lessons.
service Catalog {
  // Unary: one request, one response.
  rpc SayHello(HelloRequest) returns (HelloReply);

  // Server stream: one request, a sequence of Item messages.
  rpc List(ListRequest) returns (stream Item);

  // Client stream: a sequence of Chunk messages, one UploadSummary.
  rpc Upload(stream Chunk) returns (UploadSummary);
}

message HelloRequest {
  string name = 1;
}

message HelloReply {
  string message = 1;
}

message ListRequest {
  string prefix = 1;
  int32 limit = 2;
}

message Item {
  string id = 1;
  string title = 2;
}

message Chunk {
  bytes data = 1;
}

message UploadSummary {
  int64 bytes_received = 1;
}
```

Field numbers (`= 1`, `= 2`) are part of the wire contract. You can rename a field in newer clients while keeping compatibility; **do not change a field number** without `reserved` rules (more detail in module 06).

### Protobuf on the wire (byte trace)

Protobuf is not JSON. A message `HelloRequest{name: "Ana"}` on the wire looks roughly like this (simplified):

```text
tag for field 1 (string) | length | UTF-8 bytes "Ana"
```

Key properties:

1. **The schema is known to both sides** (from `.proto` / generated code). Without the schema the bytes are unreadable to humans — and that is intentional.
2. **Fields are tagged by number**, not by name. That is why the wire is shorter than JSON with `"name":"Ana"`.
3. **Unknown fields** (newer client → older server) are usually ignored or forwarded per versioning rules — that is why API evolution is possible without a “big bang” change.

You do not have to write encode/decode by hand: `protoc-gen-go` generates types with `ProtoReflect` / marshal paths.

### HTTP/2 as transport

gRPC (in the Go implementation) runs RPC over HTTP/2:

- One TCP connection can carry **multiple streams** (multiplex). You do not open a new TCP for every RPC.
- Each RPC is typically one HTTP/2 stream.
- Headers carry gRPC metadata (e.g. `content-type: application/grpc`, a path like `/demo.v1.Catalog/SayHello`).
- Data frames carry protobuf messages (plus a 5-byte gRPC message header: compression + length).
- Trailers carry the final `grpc-status` and optionally `grpc-message`.

Unary call trace (simplified):

```text
1. Client: HEADERS  :method=POST  :path=/demo.v1.Catalog/SayHello
            content-type=application/grpc
2. Client: DATA     [5-byte prefix][protobuf HelloRequest]
3. Server:  HEADERS  :status=200  content-type=application/grpc
4. Server:  DATA     [5-byte prefix][protobuf HelloReply]
5. Server:  TRAILERS grpc-status=0
```

If the server returns an error, you often still see HTTP 200 at the transport level, and the **real outcome** is in `grpc-status` (e.g. `3` = `InvalidArgument`). That confuses people used to REST: “HTTP is 200, but the client sees an error”. In gRPC you look at the status package, not only the HTTP code.

### Generating stubs

Flow:

```text
Catalog.proto
    |
    v
protoc
  + protoc-gen-go       -> demopb/*.pb.go       (messages)
  + protoc-gen-go-grpc  -> demopb/*_grpc.pb.go  (Client/Server interface, Register)
    |
    v
Your code: implements CatalogServer
Client:   calls CatalogClient.SayHello(ctx, req)
```

Example command (local development; adjust paths for your project):

```bash
protoc \
  --go_out=. --go_opt=paths=source_relative \
  --go-grpc_out=. --go-grpc_opt=paths=source_relative \
  demo/v1/catalog.proto
```

Generated `CatalogServer` is an `interface`. Generated `RegisterCatalogServer` binds your implementation to `*grpc.Server`. Generated `CatalogClient` is a type that sends RPCs over `*grpc.ClientConn`.

### Unary, then streaming (overview)

| Kind | Request | Response | In our Catalog |
|-------|---------|----------|-----------------|
| Unary | 1 | 1 | `SayHello` |
| Server stream | 1 | N | `List` |
| Client stream | N | 1 | `Upload` |
| Bidi | N | N | (we will introduce it in 03.04 as an extension) |

Most production APIs are unary. Streaming is not “more advanced REST”; it is another shape of message flow on the same HTTP/2 stream. Details of `Recv` / `CloseSend` / `io.EOF` are in 03.04.

### Server and client — where what lives

On the server (lesson 03.02):

1. `lis, err := net.Listen("tcp", ":50051")`
2. `s := grpc.NewServer()`
3. `demopb.RegisterCatalogServer(s, &catalogServer{})`
4. `s.Serve(lis)` — blocks; usually in `main` or with graceful `GracefulStop`

On the client (lesson 03.03), modern API:

```go
conn, err := grpc.NewClient(
	"localhost:50051",
	grpc.WithTransportCredentials(insecure.NewCredentials()),
)
```

`insecure.NewCredentials()` is **only for local development**. In production: TLS credentials. Older code often uses `grpc.Dial` / `grpc.DialContext` — it still works in many versions, but new code prefers `grpc.NewClient`. Deadline: `context.WithTimeout`.

### Status codes

Package `google.golang.org/grpc/status` and `codes`:

- Server: `return nil, status.Errorf(codes.InvalidArgument, "name is empty")`
- Client: `st, ok := status.FromError(err)` then `st.Code()`

Mapping “everything to HTTP 500” loses meaning. gRPC codes are part of the contract between services.

### Metadata and deadline (brief)

- **Deadline** travels in `context` — the server sees the same deadline (within clock skew limits).
- **Metadata** are key/value pairs in headers/trailers (e.g. request ID). Do not put business data in metadata if it belongs in the message.

See deeper metadata and interceptor details in module 05; here it is enough to know they exist alongside the protobuf body.

### What gRPC is not

- Not a replacement for every public browser API (browsers and CORS/gRPC-Web are a separate story).
- Not “faster because Google” — speed comes from the binary format, HTTP/2 multiplex, and less boilerplate, but a bad message design still hurts.
- Not free of operations: metrics, message size limits, TLS, and auth are still required.

## Rules and syntax

Minimal Go concepts alongside generated code:

| Concept | Role |
|-------|-------|
| `demopb.HelloRequest` | message (struct) |
| `demopb.CatalogServer` | `interface` you implement |
| `demopb.RegisterCatalogServer` | registration on `*grpc.Server` |
| `demopb.CatalogClient` | client stub |
| `demopb.NewCatalogClient(conn)` | stub constructor |
| `context.Context` | cancellation and deadline |
| `status` / `codes` | structured errors |

IDL rules to adopt immediately:

1. `syntax = "proto3";` at the top.
2. `package` + `option go_package` — without them the Go import path suffers.
3. RPC signatures only through `message` types (not “bare” `string` in the modern style we generate here).
4. Streaming is marked with the keyword `stream` on the request or response side.

## Examples

### Example 1: Prediction — what the client “sees”

Read this server return:

```go
if req.GetName() == "" {
	return nil, status.Errorf(codes.InvalidArgument, "name is required")
}
return &demopb.HelloReply{Message: "hello, " + req.GetName()}, nil
```

#### What happens here

An empty name returns a nil reply and `status.Errorf` with `codes.InvalidArgument` and the text `name is required`. Any other name returns a `HelloReply` whose message is `hello, ` plus that name, together with a nil error. On the client, the empty-name path arrives as a non-nil `err` whose `status.Code` is `InvalidArgument`. The success path is the one that yields a reply to read.

**Predict:** what does `err` on the client contain if you send an empty `name`? Is the HTTP status necessarily 400?

**Answer:** `err != nil`, `status.Code(err) == codes.InvalidArgument`. The HTTP/2 layer often still shows 200; the gRPC status is in the trailers. Do not conclude the outcome from the HTTP code alone.

### Example 2: Call trace for `SayHello`

```text
Client goroutine:
  ctx, cancel := context.WithTimeout(..., 2*time.Second)
  client.SayHello(ctx, &HelloRequest{Name: "Ana"})
    -> stub serializes protobuf
    -> opens/uses an HTTP/2 stream
    -> sends headers + data
    -> waits for headers + data + trailers
    -> if grpc-status=0, unmarshals HelloReply
    -> if != 0, returns a status error

Server:
  Serve picks handlers by :path
  calls CatalogServer.SayHello(ctx, req)
  your code returns (*HelloReply, error)
  runtime packs the response or status into frames
```

#### What happens here

The trace follows one unary `SayHello` for the name `Ana`, with a two-second timeout on the client context. The stub serializes the protobuf, uses an HTTP/2 stream, and waits for headers, data, and trailers. A grpc-status of 0 becomes a `HelloReply`, and any other status becomes an error. On the server, `Serve` selects the handler by `:path`, calls `SayHello`, and the runtime packs the reply or the status into frames.

### Example 3: Why `context` must travel

```go
ctx, cancel := context.WithTimeout(context.Background(), time.Second)
defer cancel()
_, err := client.SayHello(ctx, req)
```

#### What happens here

The caller builds a child context with a one-second timeout and passes that `ctx` into `SayHello`. `defer cancel()` releases the timer when the caller returns. If the handler runs longer than that second, the call ends with `DeadlineExceeded`. Calling `cancel()` earlier ends it with `Canceled`.

If the server sleeps 5s, the client gets `DeadlineExceeded` (or `Canceled` if `cancel()` runs earlier). Without a timeout, the goroutine and resources can “hang” for as long as the network stays quiet.

### Example 4: Same contract, different stub (idea)

The same `Catalog.proto` in Java yields `CatalogGrpc.CatalogImplBase` / a blocking stub; in Go `CatalogServer` / `CatalogClient`. The wire path `/demo.v1.Catalog/SayHello` stays the same. That is why polyglot works — not because you share a Go package.

## Decision analysis

**Why not “just JSON over HTTP/1.1” for internal services?**

JSON + OpenAPI is excellent for public APIs and the browser. For an internal mesh gRPC gives a stricter contract, less ad-hoc DTO drift, a better streaming model, and standard codes. The cost: tooling (`protoc`), learning curve, harder debug “with the naked eye”.

**Why IDL instead of “the Go struct is the contract”?**

A Go struct is not a contract for Java. IDL is language-agnostic. If you will never use another language, you still get generation, field versions, and a clear boundary — but you can consciously stay on JSON.

**Unary first?**

Yes. Streaming without unary discipline often hides bad API design (oversized messages, undefined stream end).

## Trade-offs

| Choice | You get | You pay |
|-------|---------|--------|
| gRPC + protobuf | strict contract, efficient wire | `protoc`, less “curl-friendly” |
| REST + JSON | simple debug, browser | weaker contract, more boilerplate |
| gRPC-Web / gateway | browser access | an extra layer |
| Insecure localhost | fast start | forbidden in production |
| Huge messages | fewer RPCs | memory, timeout, poor UX |

## Common mistakes

1. Treating gRPC as “REST with another name” and expecting JSON on the wire.
2. Ignoring `grpc-status` because HTTP is 200.
3. Running production with `insecure.NewCredentials()`.
4. Having no deadline on the client `context` — leaking goroutines and threads on the server.
5. Changing a field number in `.proto` instead of adding a new field / `reserved`.
6. Mixing a business error (`InvalidArgument`) with a transport error (`Unavailable`) without `status.FromError`.
7. Expecting `go build` to run `protoc` by itself.
8. Keeping `.proto` out of version control or having four “truths” about the same field.

## Idiomatic Go

- Keep generated code in its own package (`demopb`), do not mix it with hand-written logic.
- Put business logic behind a small `interface` (e.g. `Greeter` / store), and let the gRPC layer only map messages ↔ domain.
- Always pass `ctx` downward into calls (DB, other RPC).
- Return errors via `status.Errorf`; do not panic on bad input.
- Limit message size on the server (`MaxRecvMsgSize` / similar options) — defensively.
- Log `codes` and duration; do not log whole messages if they carry PII.

## Practical scenario

A team has an Order service (Go) and an Inventory service (Go). At first they talked JSON over HTTP. After three months, the field `qty` in one service means “ordered”, in the other “reserved”. They introduce an `inventory.v1` proto with clear names and a `SayHello`-style health/echo for smoke test, then build a `Reserve` unary RPC. The client always sends `context.WithTimeout`. On review they reject a PR that uses insecure credentials outside local `docker compose`. The “hanging” call incident goes away when every RPC gets a deadline. Later they add a `List` server stream for export — only once unary is stable.

## Summary

gRPC joins RPC semantics, protobuf messages, and HTTP/2 transport around a contract in `.proto`. The generator builds stubs; your code implements the server `interface` and calls the client stub with `context`. Unary `SayHello` is the first shape; `List` and `Upload` introduce stream. On the wire you look at frames and `grpc-status`, not JSON. The next lesson builds a real server: `NewServer`, Register, Serve.

## Deeper: anatomy of the gRPC message prefix

Every protobuf message in a gRPC data frame starts with 5 bytes:

```text
| 1 byte: compressed flag (0 or 1) | 4 bytes: message length (big-endian) | N bytes: protobuf |
```

If you enable compression (e.g. gzip) on the call, the flag is 1 and the payload is compressed. Beginners often think “the whole stream is one protobuf” — it is not; framing is a required part of the protocol.

## Deeper: method path

`:path` for our example:

```text
/demo.v1.Catalog/SayHello
```

Shape: `/` + package + `.` + Service + `/` + Method. Changing `package` or the service name **breaks** clients even if the Go type looks similar. That is why packages are named with a version (`demo.v1`).

## Deeper: what the server does before your code

1. Accept TCP (or an already open HTTP/2).
2. Parse HPACK headers.
3. Find the service/method in the internal registry (filled via `RegisterCatalogServer`).
4. Read data frames until the full request message is assembled (unary).
5. Unmarshal into `*HelloRequest`.
6. Call your method.
7. Marshal the response or pack `status`.
8. Send response headers/data/trailers.

If registration fails (you forget `Register`), the client gets `Unimplemented`. That is a common first-day mistake.

## Deeper: error as a value

In Go, `error` is a value. The gRPC runtime checks whether the `error` is a gRPC status:

```go
import (
	"google.golang.org/grpc/codes"
	"google.golang.org/grpc/status"
)

func (s *catalogServer) SayHello(ctx context.Context, req *demopb.HelloRequest) (*demopb.HelloReply, error) {
	if err := ctx.Err(); err != nil {
		return nil, err // runtime maps cancel/deadline
	}
	if req.GetName() == "" {
		return nil, status.Error(codes.InvalidArgument, "name is required")
	}
	return &demopb.HelloReply{Message: "hello, " + req.GetName()}, nil
}
```

If you return a plain `fmt.Errorf("boom")`, the client often sees `codes.Unknown`. So an explicit `status` is not ceremony — it is the contract.

## Deeper: when to choose gRPC

Choose gRPC when:

- you have internal services with clear RPC operations;
- you need a strict contract and/or polyglot;
- streaming (server/client/bidi) is a real requirement;
- the team accepts `protoc` in CI.

Stay on JSON/HTTP when:

- a public API for browser/partners without gRPC-Web;
- the team lacks tooling discipline;
- the payload must be human-readable in logs without a decoder.

## Mechanism (continued): from byte to Go value

### Step by step on the client

Assume `conn` is already created via `grpc.NewClient` and you have a stub:

```go
client := demopb.NewCatalogClient(conn)
ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
defer cancel()
reply, err := client.SayHello(ctx, &demopb.HelloRequest{Name: "Ana"})
```

What happens inside (logical trace):

1. The stub checks whether `conn` is closed.
2. It creates a call object bound to method descriptor `/demo.v1.Catalog/SayHello`.
3. It serializes `HelloRequest` into protobuf bytes.
4. It adds the 5-byte gRPC prefix.
5. It picks an HTTP/2 stream (new or existing connection per load balancing / resolver rules).
6. It sends headers (including remaining timeout if the runtime maps that from `context`).
7. It sends data.
8. It blocks (in this goroutine) until response frames arrive or `ctx` cancels.
9. It reads trailers: `grpc-status`.
10. If status is not OK, it builds an `error` via the `status` package; otherwise it unmarshals into `*HelloReply`.

If in step 8 `cancel()` runs, the client sends cancellation on the stream; the server’s `ctx.Done()` closes — *if* the server respects `ctx`.

### Step by step on the server

1. `Serve` reads frames.
2. For a new stream, it parses `:path`.
3. It finds the handler in the map of registered methods.
4. It reads the request message (unary: exactly one).
5. It creates a `context` bound to the stream (cancel when the client cancels or the deadline arrives).
6. It calls your `SayHello`.
7. If you return `(reply, nil)`, marshal + prefix + data + `grpc-status=0`.
8. If you return a `status` error, it sends trailers with the code; body often empty.

### Why “trace” exists in the lesson

Without a trace, gRPC looks like magical `client.Foo()`. With a trace you can predict:

- where time disappears (marshal, network, your code);
- why you see `Canceled` instead of a business error;
- why `Unimplemented` means “you did not register”, not “a bug in protobuf”.

## Mechanism (continued): four RPC kinds on the same transport

All four kinds use an HTTP/2 stream. The difference is **how many messages** go in which direction.

```text
Unary:         Client --req--> Server --resp--> Client
Server stream: Client --req--> Server --resp*--> Client
Client stream: Client --req*--> Server --resp--> Client
Bidi:          Client --req*--> Server --resp*--> Client  (overlap possible)
```

For `List` (server stream): the client sends one `ListRequest`, then loops `Recv()` until it gets `io.EOF` — that is the **normal end** of the stream, not necessarily an error. For `Upload` (client stream): the client sends multiple `Chunk`, calls `CloseSend()`, then waits for one `UploadSummary`. Details and who calls `CloseSend` are in 03.04 — here remember only the mapping onto Catalog.

## Mechanism (continued): resolver and target string

`grpc.NewClient("localhost:50051", ...)` uses a target string. In the simple case that is host:port. In production you see schemes like DNS (`dns:///service.namespace`) and load balancing. For this course:

- localhost + port is enough;
- do not learn “service mesh” until unary works stably;
- an `Unavailable` error often means: wrong port, server not up, or TLS mismatch.

## Table: REST habit → gRPC translation

| REST habit | gRPC translation |
|-------------|-------------|
| `GET /items/1` | `rpc GetItem(GetItemRequest) returns (Item)` |
| `404` | `codes.NotFound` |
| `400` | `codes.InvalidArgument` |
| `401/403` | `Unauthenticated` / `PermissionDenied` |
| `429` | `ResourceExhausted` |
| `503` | `Unavailable` |
| JSON body | protobuf message |
| Query string filter | fields in the request message |
| SSE / chunked | server streaming RPC |

Translations are not 1:1 religion; they are landmarks so you do not invent your own status system.

## Lesson glossary (keep at hand)

- **stub** — generated client (or server) code that packs the RPC.
- **channel / ClientConn** — connection to the server (in Go `*grpc.ClientConn`).
- **deadline** — absolute time until which the RPC may run.
- **metadata** — headers outside the protobuf body.
- **status** — code + message of the RPC outcome.
- **IDL** — `.proto` contract.
- **wire contract** — bytes and path that all implementations must respect.

You must be able to explain to a colleague in five minutes: what the contract is, what the transport is, what a generated stub is, and why `error` on the client is not the same as an HTTP status from the REST world. That is the ticket to 03.02.

## Mechanism (deepening): Catalog as the thread through block 03

The whole fundamentals block sticks to one contract — Catalog — so you do not jump between demo domains.

```protobuf
syntax = "proto3";
package demo.v1;
option go_package = "example.com/demo/gen/demo/v1;demopb";

service Catalog {
  rpc SayHello(HelloRequest) returns (HelloReply);
  rpc List(ListRequest) returns (stream Item);
  rpc Upload(stream UploadChunk) returns (UploadSummary);
}
message HelloRequest { string name = 1; }
message HelloReply { string message = 1; }
message ListRequest { int32 page_size = 1; }
message Item { string id = 1; string title = 2; }
message UploadChunk { bytes data = 1; }
message UploadSummary { int64 bytes = 1; }
```

| RPC | Type | What you learn |
|-----|-----|----------|
| SayHello | unary | request/response, status, deadline |
| List | server-stream | Recv loop, EOF |
| Upload | client-stream | Send + CloseSend |

The same contract returns in 05.x with Java/C#/Node stubs — the wire stays.

## Mechanism (deepening): from byte to Go value (unary)

```text
1. Client serializes HelloRequest (protobuf)
2. gRPC framing: compressed-flag + length + message
3. HTTP/2 HEADERS (:method POST, :path /demo.v1.Catalog/SayHello, content-type application/grpc)
4. HTTP/2 DATA
5. Server: path → registered method → deserialization into *HelloRequest
6. Your handler (ctx, req) (resp, err)
7. If err = status → trailers grpc-status / grpc-message
8. If OK → DATA with HelloReply + trailers status 0
9. Client deserializes or status.FromError
```

**Predict:** you think gRPC is “TCP + struct”.  
**Answer:** in between are the HTTP/2 stream, method path, protobuf, and status in trailers.

## Mechanism (deepening): method path

`:path` is `/{package}.{Service}/{Method}` e.g. `/demo.v1.Catalog/SayHello`.  
grpcurl, Java, C#, Node — all hit the same path. Wrong package in proto = “works in a Go test, fails polyglot”.

## Mechanism (deepening): error as a value

In a Go handler:

```go
return nil, status.Error(codes.InvalidArgument, "name required")
```

That is **not** a panic and not HTTP 400 directly. It is a gRPC status that the runtime puts in trailers. The client reads `codes.InvalidArgument`. The REST habit “everything via status int” must be translated.

| REST habit | gRPC translation |
|-------------|-------------|
| 400 | InvalidArgument (often) |
| 404 | NotFound |
| 401 | Unauthenticated |
| 403 | PermissionDenied |
| 504 | DeadlineExceeded |
| 503 | Unavailable |

Not a 1:1 table for every case — document the mapping in the BFF.

## Mechanism (deepening): four RPC shapes on the same transport

All use HTTP/2 streams; the difference is who sends how many messages.

```text
unary:        1 req  → 1 resp
server stream: 1 req → N resp
client stream: N req → 1 resp
bidi:          N req ↔ N resp
```

Unary is the default choice. Stream when the domain truly produces/sends a sequence.

## Predict-then-check (mini set)

**A.** JSON over HTTP “because it is easier to debug”.  
**Answer:** often OK for a public API; for a strict polyglot contract gRPC wins — choose consciously.

**B.** You ignore the deadline because the lab is on localhost.  
**Answer:** a bad reflex; in 03.03/05.05 it becomes an incident.

**C.** You mix the package name between server and client.  
**Answer:** Unimplemented / path miss.

**D.** You think `error` on the client = HTTP status.  
**Answer:** read `status.Code`.

## Mechanism (deepening): observability from day one

Minimum:

- log `FullMethod` + code + duration  
- request id in metadata  
- metric by code (not only “error count”)

Without that, the 03.02 server “works” until it goes to prod.

## Mechanism (deepening): security orientation

- lab: insecure plaintext  
- prod direction: TLS (+ auth)  
- message size limit  
- do not log Authorization

Details in 05.x; here only so you do not normalize plaintext.
