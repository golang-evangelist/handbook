# 03.04 Streaming responses in gRPC (Go)

> **Go Path - Zero to Gopher** / **03 Others → gRPC Fundamentals in Go** / Lesson 03.04

## Lesson goals

After this lesson you can:

- distinguish server stream, client stream, and bidirectional stream;
- implement `List` (server stream) and `Upload` (client stream) on the Catalog service;
- on the client, read a server stream until `io.EOF`;
- know who calls `CloseSend` and why;
- follow the message trace on the HTTP/2 stream for each shape;
- avoid typical mistakes (treating `EOF` as failure, forgetting CloseSend).

## Prerequisite

- 03.01–03.03 (contract, server, unary client).
- Catalog `.proto` with `List` and `Upload`.
- Go 1.22+.

## Problem this lesson solves

Streaming tutorials often show a loop without end rules. People treat `io.EOF` as an error, forget `CloseSend`, or mix server and client stream. This lesson fixes **who sends how many messages** and **how the stream closes**.

## Mental model

```text
Server stream (List):
  Client ---- ListRequest ----> Server
  Client <--- Item, Item, ... -- Server
  Client Recv() gets io.EOF = normal end

Client stream (Upload):
  Client ---- Chunk, Chunk, ... -> Server
  Client CloseSend()
  Client <--- UploadSummary ----- Server

Bidi:
  Both directions N messages; often two goroutines (send/recv)
```

One HTTP/2 stream carries the whole RPC. The difference is the number of messages and who closes which half.

## Mechanism

### Server stream: `List`

Proto:

```proto
rpc List(ListRequest) returns (stream Item);
```

#### Server implementation

```go
func (s *catalogServer) List(req *demopb.ListRequest, stream demopb.Catalog_ListServer) error {
	if err := stream.Context().Err(); err != nil {
		return err
	}
	limit := int(req.GetLimit())
	if limit <= 0 || limit > 100 {
		return status.Error(codes.InvalidArgument, "limit must be 1..100")
	}
	// demo data
	items := []demopb.Item{
		{Id: "1", Title: req.GetPrefix() + "alpha"},
		{Id: "2", Title: req.GetPrefix() + "beta"},
		{Id: "3", Title: req.GetPrefix() + "gamma"},
	}
	for i := 0; i < len(items) && i < limit; i++ {
		if err := stream.Context().Err(); err != nil {
			return err
		}
		if err := stream.Send(&items[i]); err != nil {
			return err
		}
	}
	return nil // runtime sends successful status; client sees EOF on Recv
}
```

Trace:

```text
1. Client sends one ListRequest
2. Server in a loop Send(Item)
3. Server return nil
4. Runtime closes the stream with grpc-status=0
5. Client Recv: Item... then io.EOF
```

#### Client

```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()

stream, err := client.List(ctx, &demopb.ListRequest{Prefix: "go-", Limit: 10})
if err != nil {
	return err
}
for {
	item, err := stream.Recv()
	if err == io.EOF {
		break // normal end of server stream
	}
	if err != nil {
		return err // real error
	}
	fmt.Println(item.GetId(), item.GetTitle())
}
```

**Rule:** `Recv` returns `io.EOF` at the end of a successful server stream. That is not a `status` error.

### Client stream: `Upload`

Proto:

```proto
rpc Upload(stream Chunk) returns (UploadSummary);
```

#### Server

```go
func (s *catalogServer) Upload(stream demopb.Catalog_UploadServer) error {
	var n int64
	for {
		chunk, err := stream.Recv()
		if err == io.EOF {
			// client closed the send side
			return stream.SendAndClose(&demopb.UploadSummary{BytesReceived: n})
		}
		if err != nil {
			return err
		}
		n += int64(len(chunk.GetData()))
		if n > 1<<20 { // 1 MiB demo limit
			return status.Error(codes.InvalidArgument, "upload too large")
		}
	}
}
```

Trace:

```text
1. Client opens the stream
2. Client Send(Chunk)* 
3. Client CloseSend()  // announces end of request messages
4. Server Recv gets EOF
5. Server SendAndClose(UploadSummary)
6. Client reads summary (CloseAndRecv pattern)
```

#### Client

```go
ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
defer cancel()

stream, err := client.Upload(ctx)
if err != nil {
	return err
}
for _, part := range [][]byte{[]byte("he"), []byte("llo")} {
	if err := stream.Send(&demopb.Chunk{Data: part}); err != nil {
		return err
	}
}
summary, err := stream.CloseAndRecv()
if err != nil {
	return err
}
fmt.Println(summary.GetBytesReceived())
```

`CloseAndRecv` = `CloseSend` + waiting for one response. You can also split: `CloseSend()` then manual recv — but `CloseAndRecv` is idiomatic for client stream unary-response.

**Who calls `CloseSend`?** The client, when it finishes sending request messages. Without that the server often stays forever in the `Recv` loop (until ctx expires).

### Bidirectional stream (shape)

Not in our minimal Catalog proto, but you must know the mechanism:

```proto
rpc Chat(stream ChatMessage) returns (stream ChatMessage);
```

Typical client:

- a goroutine for the `Send` loop + `CloseSend` at the end;
- main or another goroutine for `Recv` until `EOF`;
- synchronization via `errgroup` or a channel for the first error.

Server similarly: reads and writes on the same stream object. Watch for deadlocks (both waiting on Recv).

### EOF map

| Situation | `Recv` err | Meaning |
|-----------|------------|----------|
| Server stream finished successfully | `io.EOF` | normal |
| Client stream: client CloseSend | server `Recv` → `io.EOF` | normal, time for response |
| Status error | other err; `status.Code` | not EOF |
| Ctx canceled | `Canceled` / ctx err | cancel |

### Context and streams

A long stream must periodically check `stream.Context().Done()`. Otherwise a canceled client still spends server resources.

### Backpressure (intuition)

`Send` can block if the client does not read fast enough (HTTP/2 window / flow control). Do not assume `Send` is always instantaneous. For huge exports: unary pagination or a controlled server stream with limits.

### Errors mid-stream

If the server does `return status.Error(...)` after several `Send`, the client may receive some Items then an error on the next `Recv`. API design: does a partial result make sense? Document it.

## Rules and syntax

1. Server stream handler: `(req *Req, stream X_YServer) error`.
2. Client stream handler: `(stream X_YServer) error` — the request comes through `Recv`.
3. Client server-stream: `Recv` loop until `io.EOF`.
4. Client client-stream: `Send`* then `CloseAndRecv` (or `CloseSend` + recv).
5. `CloseSend` is called by the **client** when it finishes sending.
6. Do not treat `io.EOF` as failure at the end of a server stream.

## Examples

### Example 1: List end-to-end

Server `Send` in a loop; client `Recv` until EOF — code above.

### Example 2: Predict — forgotten CloseSend

Client does `Send` but never `CloseAndRecv`/`CloseSend`, just waits.  
**Predict:** server blocks on `Recv`; both wait until the deadline.  
**Check:** remove Close; observe timeout.

### Example 3: Predict — treat EOF as error

```go
item, err := stream.Recv()
if err != nil {
	return err // BUG if it is EOF
}
```

#### What happens here

`Recv` returns the next stream item or an error. The `if` returns every non-nil error to the caller, and that includes `io.EOF`. On a server stream, `io.EOF` means the server has finished sending and the list is complete. Returning that value unchanged makes a finished `List` look like a failure, which is the bug the comment marks.

**Outcome:** a successful List looks like a fail. Always special-case `io.EOF`.

### Example 4: Upload with three chunks

Send 3x `Chunk{Data: []byte("x")}`; expect `BytesReceived: 3`.

### Example 5: Cancel mid-List

Client `cancel()` after the first Item. Server’s next `Send` or `ctx.Err` should stop. Confirm it does not continue heavy work.

## Decision analysis

**Why not return `repeated Item` in unary?** Fine for small lists. Server stream when: unsuitable memory, progressive display, long export.  
**Client stream vs HTTP multipart?** gRPC client stream gives status codes and the same stack; HTTP upload can be simpler at the edge. Choose by ecosystem.  
**Bidi always?** Rarely. Chat, interactive ACL, signal multiplexing — yes. CRUD — no.

## Trade-offs

| Shape | Plus | Minus |
|-------|------|-------|
| Unary + repeated | simple | everything in memory |
| Server stream | progressive flow | more complex client |
| Client stream | upload without one huge message | CloseSend discipline |
| Bidi | interactivity | concurrency, deadlock risk |

## Common mistakes

1. Treating `EOF` as failure at the end of a server stream.
2. Forgetting `CloseSend` / `CloseAndRecv`.
3. Ignoring `stream.Context()` on a long List.
4. Endless Send without a limit / without cancel.
5. Mixing `SendAndClose` (server client-stream) with ordinary `Send`.
6. Assuming bidi message order without an application protocol.
7. Holding huge chunks — limits and MaxRecvMsgSize still apply **per message**.

## Idiomatic Go

- `errors.Is(err, io.EOF)` or `err == io.EOF` (EOF is a sentinel).
- `errgroup` for bidi send/recv.
- Limit `limit` in the List request on the server (defense).
- Metrics: number of sent items, upload bytes, code at the end.

## Practical scenario

A reporting service first returns 50MB JSON unary — OOM. They move to a `List` server stream of 500 Items. The client writes to a file per `Recv`. Second use-case: upload configuration through `Upload` chunks of 64KiB; without `CloseAndRecv` a hang in staging for a whole day until they added a timeout. Bidi stays out of scope until on-call asks for an interactive protocol.

## Check questions

1. **What does `Recv` return at the end of a successful server stream?** `io.EOF`.
2. **Who calls `CloseSend`?** The client when it finishes sending request messages.
3. **Which Catalog method is client stream?** `Upload`.
4. **What does the server do on EOF in Upload `Recv`?** `SendAndClose(summary)` (or equivalent).
5. **Why check `stream.Context()`?** So you respect cancel/deadline.
6. **Is EOF always an error?** No — often an end signal.

## Summary

Streaming = more messages on the same RPC/HTTP2 stream. `List`: server `Send`, client `Recv` until EOF. `Upload`: client `Send` + Close, server `Recv` until EOF then summary. Bidi needs careful concurrency. Unary remains the default choice until stream proves its value.

## Deeper: generated stream interfaces

For `List`, the client gets something like `Catalog_ListClient` with `Recv()`, `Header()`, `Trailer()`, `Context()`, `CloseSend()` (CloseSend on a server-stream client is rarely needed for pure reading).

For `Upload`, `Catalog_UploadClient` has `Send`, `CloseAndRecv`.

Server side: `Catalog_ListServer` has `Send`; `Catalog_UploadServer` has `Recv` and `SendAndClose`.

Do not invent signatures — open `*_grpc.pb.go`.

## Deeper: headers and trailers mid-stream

The server can send headers before the first message. Trailers carry the final status. If an error arrives after partial data, the client must decide what to do with already received Items (idempotent reconnect? discard?).

## Deeper: comparative traces

```text
UNARY SayHello
  C: headers+req
  S: headers+resp+trailers

SERVER List
  C: headers+req
  S: headers+item*+trailers

CLIENT Upload
  C: headers+chunk*+close-send
  S: headers+summary+trailers

BIDI
  C/S: headers, then messages both ways, then Close side
```

## Extension: when stream is not needed

If you always return ≤20 small records, `repeated Item` in unary is simpler for cache, retry, and authz. Add stream when volume or time requires it.

## Glossary

- **server stream** — N responses.
- **client stream** — N requests, 1 response.
- **bidi** — N+N.
- **CloseSend** — end of sending from the client.
- **SendAndClose** — server’s only response on a client stream.
- **io.EOF** — end of messages on that side.

## Mechanism (continued): full List server with a store

```go
type catalogServer struct {
	demopb.UnimplementedCatalogServer
	items []demopb.Item
}

func (s *catalogServer) List(req *demopb.ListRequest, stream demopb.Catalog_ListServer) error {
	limit := int(req.GetLimit())
	if limit <= 0 || limit > 100 {
		return status.Error(codes.InvalidArgument, "limit must be 1..100")
	}
	sent := 0
	for i := range s.items {
		if sent >= limit {
			break
		}
		if req.GetPrefix() != "" && !strings.HasPrefix(s.items[i].GetTitle(), req.GetPrefix()) {
			continue
		}
		select {
		case <-stream.Context().Done():
			return stream.Context().Err()
		default:
		}
		if err := stream.Send(&s.items[i]); err != nil {
			return err
		}
		sent++
	}
	return nil
}
```

Filtering on the server reduces the network. Limit is defense against “give me everything”.

## Mechanism (continued): Upload with a temporary buffer

```go
func (s *catalogServer) Upload(stream demopb.Catalog_UploadServer) error {
	var buf bytes.Buffer
	for {
		chunk, err := stream.Recv()
		if err == io.EOF {
			// here you would parse buf.Bytes() — demo only counts
			return stream.SendAndClose(&demopb.UploadSummary{
				BytesReceived: int64(buf.Len()),
			})
		}
		if err != nil {
			return err
		}
		if buf.Len()+len(chunk.GetData()) > 1<<20 {
			return status.Error(codes.InvalidArgument, "upload too large")
		}
		_, _ = buf.Write(chunk.GetData())
	}
}
```

Notice: you check the limit **before** writing. Defensive programming.

## Mechanism (continued): bidi skeleton without an invented domain

```go
// Assume rpc Chat(stream ChatMessage) returns (stream ChatMessage);
func (s *catalogServer) Chat(stream demopb.Catalog_ChatServer) error {
	for {
		msg, err := stream.Recv()
		if err == io.EOF {
			return nil
		}
		if err != nil {
			return err
		}
		// echo
		if err := stream.Send(msg); err != nil {
			return err
		}
	}
}
```

This is only the shape. In a real Chat you often have a separate send loop. Deadlock happens when both sides block on Recv without a Send protocol — so the application protocol must be clear (e.g. “client always sends first”).

## Mechanism (continued): client List with counting

```go
func listAll(ctx context.Context, client demopb.CatalogClient, prefix string) ([]*demopb.Item, error) {
	stream, err := client.List(ctx, &demopb.ListRequest{Prefix: prefix, Limit: 100})
	if err != nil {
		return nil, err
	}
	var out []*demopb.Item
	for {
		item, err := stream.Recv()
		if err == io.EOF {
			return out, nil
		}
		if err != nil {
			return out, err // partial result + error — API consumer decision
		}
		out = append(out, item)
	}
}
```

Document whether a partial `out` may be used when `err != nil`.

## Comparative Close table

| RPC | Client closes send | Server signal of request end | Client end of recv |
|-----|----------------------|------------------------------|-------------------|
| Unary | automatically after 1 req | N/A | 1 response |
| List | after 1 req | N/A | `Recv` EOF |
| Upload | `CloseSend` / `CloseAndRecv` | `Recv` EOF | 1 summary |
| Bidi | `CloseSend` when done | by protocol | `Recv` EOF |

## Mechanism (deepening): three stream shapes — Close and EOF

Streaming in gRPC is not “a socket then read bytes”. It is typed protobuf messages on an HTTP/2 stream with clear rules on who closes what.

### Server-stream List — trace

```text
client List(req)
  → server loop Send(Item)
  → server return nil
  → client Recv ... Recv → io.EOF (successful end)
```

EOF on a server-stream client after successful messages is a **normal end**, not an error. Do not log EOF as error.

```go
for {
	item, err := stream.Recv()
	if errors.Is(err, io.EOF) {
		break
	}
	if err != nil {
		return err
	}
	process(item)
}
```

### Client-stream Upload — trace

```text
client Upload()
  → Send(chunk)...
  → CloseAndRecv()  // closes send, waits for summary
  → server Recv until EOF
  → server SendAndClose(summary)
```

Without Close of the send side the server often stays in `Recv` forever (until deadline).

### Bidi — intuition

Both directions send until they close. Typical mistakes: deadlock (both wait on Recv), or ignoring `ctx.Done()` in the loop.

## Mechanism (deepening): context breaks long loops

```go
for {
	if err := stream.Context().Err(); err != nil {
		return err
	}
	// Send / Recv
}
```

A client deadline cancels stream.ctx. If the loop only sends without checking and without an error from Send, you spend CPU/network after cancel.

**Predict:** List sends 1e6 items without checking ctx.  
**Answer:** the client has gone; the server still works.

## Mechanism (deepening): headers/trailers mid-stream

- initial response headers can go before the first message  
- **status lives in trailers** at the end  
- an error after N successful Items means: the client already processed N, then sees fail — design idempotency/UI for that

```text
Item1 OK, Item2 OK, then ResourceExhausted
  → UI must know that partial is possible
```

## Mechanism (deepening): when stream is NOT needed

| Situation | Better choice |
|-----------|-------------|
| 1 object < limit | unary |
| pagination of small pages | unary Page + token |
| huge dump / events | server-stream |
| file upload | client-stream |
| chat / sync both ways | bidi |

Do not choose stream because it “looks modern”.

	ps := req.GetPageSize()

		return status.Error(codes.InvalidArgument, "page_size")

## Mechanism (deepening): Upload with a buffer

```go
func (s *server) Upload(stream demopb.Catalog_UploadServer) error {
	var n int64
	for {
		c, err := stream.Recv()
		if errors.Is(err, io.EOF) {
			return stream.SendAndClose(&demopb.UploadSummary{Bytes: n})
		}
		if err != nil {
			return err
		}
		n += int64(len(c.GetData()))
		if n > maxUpload {
			return status.Error(codes.ResourceExhausted, "too large")
		}
	}
}
```

## Mechanism (deepening): partial failure and UI contract

A server-stream can send 10 Items and only then a status error. Client/UI must know:

- whether to show a partial list  
- whether to retry the whole List or only continuation (if there is a cursor)  
- whether metrics count partial as fail  

Unary does not have this problem — that is why unary remains the default.

### Bidi skeleton without a fake domain

```go
func (s *server) Chat(stream demopb.Catalog_ChatServer) error {
	for {
		in, err := stream.Recv()
		if errors.Is(err, io.EOF) {
			return nil
		}
		if err != nil {
			return err
		}
		if err := stream.Send(outFrom(in)); err != nil {
			return err
		}
	}
}
```
