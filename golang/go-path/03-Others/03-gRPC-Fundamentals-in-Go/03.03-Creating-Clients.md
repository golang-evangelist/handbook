# 03.03 Creating gRPC clients in Go

> **Go Path - Zero to Gopher** / **03 Others → gRPC Fundamentals in Go** / Lesson 03.03

## Lesson goals

After this lesson you can:

- open a connection with modern `grpc.NewClient` (and know what older `Dial`/`DialContext` is);
- create a stub via `NewCatalogClient`;
- call unary `SayHello` with `context.WithTimeout`;
- read `codes` via `status.FromError`;
- close `ClientConn` with `Close`;
- distinguish insecure credentials (lab only) from TLS.

## Prerequisite

- 03.01–03.02 (contract, server, Register, Serve).
- Catalog server running on `127.0.0.1:50051`.
- Go 1.22+.

## Problem this lesson solves

Client code often “works while the server is alive”, then in production hangs without a deadline, leaks connections, or uses a deprecated API without understanding. This lesson sets up a **reliable unary client**: conn → stub → ctx → call → status → close.

## Mental model

```text
grpc.NewClient(target, opts...) -> *ClientConn
        |
        v
NewCatalogClient(conn) -> CatalogClient (stub)
        |
        v
ctx + SayHello(ctx, req) -> (reply, err)
        |
        v
status.FromError(err) / codes
```

`ClientConn` is a long-lived connection (channel). The stub is thin. `context` carries deadline/cancel **per RPC**.

## Mechanism

### Modern API: `grpc.NewClient`

```go
import (
	"google.golang.org/grpc"
	"google.golang.org/grpc/credentials/insecure"
)

conn, err := grpc.NewClient(
	"127.0.0.1:50051",
	grpc.WithTransportCredentials(insecure.NewCredentials()),
)
if err != nil {
	log.Fatalf("new client: %v", err)
}
defer conn.Close()
```

What it means:

1. **Target** `127.0.0.1:50051` — where traffic should go.
2. **Transport credentials** — required; without them `NewClient`/`Dial` rejects in modern versions.
3. **Insecure** — plaintext; **local development only**.
4. **Lazy connect** — `NewClient` usually does not block on the TCP handshake; the first RPC or `conn.Connect()` starts the dial.

Eager connect (optional):

```go
conn.Connect()
```

Useful when you want to fail-fast before the first business call, or wait for a `Ready` state in a health loop.

### Older API: `Dial` / `DialContext`

In older tutorials and code:

```go
conn, err := grpc.Dial(
	"127.0.0.1:50051",
	grpc.WithTransportCredentials(insecure.NewCredentials()),
)
```

or

```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()
conn, err := grpc.DialContext(ctx, "127.0.0.1:50051",
	grpc.WithTransportCredentials(insecure.NewCredentials()),
	grpc.WithBlock(), // often with DialContext
)
```

For **new code** prefer `grpc.NewClient`. If you maintain old code, `Dial`/`DialContext` are the older pattern — understand it, do not spread it into new services without reason. In local lab lessons, insecure + localhost is OK with an explicit note.

### Stub

```go
client := demopb.NewCatalogClient(conn)
```

Stub methods look local, and they do RPC. Do not cache “one stub per call” — cache `conn` (and typically one stub) in the process.

### Unary call with deadline

```go
ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
defer cancel()

reply, err := client.SayHello(ctx, &demopb.HelloRequest{Name: "Ana"})
if err != nil {
	st, _ := status.FromError(err)
	log.Printf("rpc failed: code=%v msg=%s", st.Code(), st.Message())
	return
}
fmt.Println(reply.GetMessage())
```

Trace:

```text
1. WithTimeout records the deadline in ctx
2. Stub sends the RPC; runtime maps remaining time into the protocol
3. Server sees a ctx that cancels when it expires
4. If the response arrives: unmarshal HelloReply
5. If not: err with DeadlineExceeded / Canceled / Unavailable / ...
```

**Always** put a timeout on the client RPC in network code. Without it, a network error keeps the goroutine busy.

### Reading status

```go
if err != nil {
	switch status.Code(err) {
	case codes.InvalidArgument:
		// user error — do not retry aggressively
	case codes.Unavailable:
		// temporary — maybe retry with backoff (carefully)
	case codes.DeadlineExceeded:
		// increase timeout or fix server latency
	default:
		// log + metric
	}
	return err
}
```

`status.Code(err)` on a non-status error often yields `Unknown`. That is why the server should return `status` errors.

### Close

```go
defer conn.Close()
```

`Close` closes the transport and cancels RPCs. Do not close `conn` after every RPC in a loop — that is an anti-pattern (expensive handshake). One conn per process/worker, many RPCs over it.

### TLS client (defensive form)

```go
creds, err := credentials.NewClientTLSFromFile("ca.crt", "localhost")
conn, err := grpc.NewClient("localhost:50051", grpc.WithTransportCredentials(creds))
```

Production: real CA, correct server name (SNI), certificate rotation. Lab: insecure.

### What the client does not do

- It does not parse JSON unless you explicitly mix protocols.
- It does not open a new TCP for every RPC (HTTP/2 multiplex on the same conn).
- It does not “guess” a REST path — the path is `/demo.v1.Catalog/SayHello`.

### Wait for ready (brief)

Under load, a short `Unavailable` during reconnect is possible. The `WaitForReady` option changes connection-wait behavior — advanced topic; for fundamentals first a stable server + timeout.

### Metadata from the client (overview)

```go
md := metadata.Pairs("x-request-id", "abc-123")
ctx = metadata.NewOutgoingContext(ctx, md)
```

The server reads incoming metadata. Details in 05.02; here know that a request ID does not go in protobuf if it is a transport concern.

## Rules and syntax

1. Credentials are required in the options.
2. Insecure only localhost/lab.
3. Timeout per RPC via `context`.
4. One `ClientConn`, defer `Close` in `main`/lifecycle.
5. Interpret errors via `status`/`codes`.
6. Prefer `NewClient` in new code; document `Dial` as older.

## Examples

### Example 1: Complete small client

```go
package main

import (
	"context"
	"fmt"
	"log"
	"time"

	"example.com/demo/gen/demopb"
	"google.golang.org/grpc"
	"google.golang.org/grpc/credentials/insecure"
	"google.golang.org/grpc/status"
)

func main() {
	conn, err := grpc.NewClient(
		"127.0.0.1:50051",
		grpc.WithTransportCredentials(insecure.NewCredentials()),
	)
	if err != nil {
		log.Fatal(err)
	}
	defer conn.Close()

	client := demopb.NewCatalogClient(conn)
	ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
	defer cancel()

	reply, err := client.SayHello(ctx, &demopb.HelloRequest{Name: "Ana"})
	if err != nil {
		log.Fatalf("SayHello: %v (%v)", err, status.Code(err))
	}
	fmt.Println(reply.GetMessage())
}
```

#### What happens here

`main` calls `grpc.NewClient` for `127.0.0.1:50051` with insecure transport credentials. That is the modern client constructor used in this lesson. `defer conn.Close()` closes the connection when `main` returns, and `NewCatalogClient` builds the stub on it. `SayHello` sends the name `Ana` under a two-second timeout, logging `status.Code` on error and printing `GetMessage()` on success.

### Example 2: Predict — server shut down

**Predict:** `Unavailable` and/or `DeadlineExceeded` depending on timing.  
**Check:** shut down the server, run the client.

### Example 3: Predict — timeout 1ms

```go
ctx, cancel := context.WithTimeout(context.Background(), time.Millisecond)
```

#### What happens here

`context.WithTimeout` sets a deadline one millisecond from now on a background context. The snippet creates that context and its `cancel` function. An RPC that receives this context has that one-millisecond budget. A round trip that takes longer ends with `DeadlineExceeded`.

Even locally you can get `DeadlineExceeded` if end-to-end is slower than 1ms.  
**Lesson:** the timeout must be realistic for p95 latency + margin.

### Example 4: Two RPCs, one conn

```go
_, _ = client.SayHello(ctx1, req1)
_, _ = client.SayHello(ctx2, req2)
```

#### What happens here

Both lines call `SayHello` on the same `client` value. `ctx1` and `ctx2` are separate contexts, so each call carries its own deadline and cancel. The connection already lives inside that client, and both calls share it. The two lines open no extra connection.

Two different `ctx` — different deadlines. Same `conn`.

### Example 5: Older Dial only as reference

```go
// Older pattern — prefer NewClient in new code.
conn, err := grpc.Dial(
	"127.0.0.1:50051",
	grpc.WithTransportCredentials(insecure.NewCredentials()),
)
```

#### What happens here

This block calls `grpc.Dial` for `127.0.0.1:50051` with insecure transport credentials. The comment labels `Dial` as the older pattern and points new code at `NewClient`. The call still returns a connection and an error. It sits here so an older snippet can be read beside the modern constructor.

If you read an old blog, map mentally: Dial ≈ older NewClient path.

## Decision analysis

**Conn per request in an HTTP handler?** No — create the conn at service start, share it (thread-safe).  
**Global timeout on conn?** Deadline is per RPC via ctx; service config can add defaults (advanced).  
**Automatic retry?** Dangerous on non-idempotent methods. Unary echo can; `CreateOrder` — not without an idempotency key.

## Trade-offs

| Choice | Plus | Minus |
|-------|------|-------|
| NewClient lazy | faster start | first RPC pays dial |
| Connect() eager | fail-fast | slower boot |
| Short timeout | fast error | false fail on slow network |
| Long timeout | fewer false fails | slower recovery |
| Insecure | simple | forbidden outside the lab |

## Common mistakes

1. No timeout on ctx.
2. `Dial`/`NewClient` in a loop with Close every time.
3. Insecure in production.
4. Interpreting every `error` as `Internal` without `status.Code`.
5. Forgotten `defer cancel()` — timer leak.
6. Wrong target (`localhost` vs IPv6 confusion) — use `127.0.0.1` in the lab for clarity.
7. Mixing an HTTP client with a gRPC stub on the same “URL” mental model.

## Idiomatic Go

- Factory: `NewCatalogAPI(conn demopb.CatalogClient)` in your package — easy to mock.
- Pass `ctx` from the HTTP handler into the gRPC call (one request ID chain).
- Log code + method + duration.
- Do not log whole request messages with secrets.

## Practical scenario

An API gateway (Go) calls Catalog. The first version opens a new Dial per HTTP request — latency and TIME_WAIT explode. Refactor: conn in `main`, stub in a struct, every handler does `WithTimeout(parentCtx, 800ms)`. Invalid name no longer retries; `Unavailable` gets a limited retry. On-call sees codes in metrics instead of a pile of strings.

## Summary

Client: `NewClient` + credentials → stub → `WithTimeout` → RPC → `status` → `Close` the conn at the end of the process lifetime. `Dial` is older. Insecure only lab. Next: streaming (`List`, `Upload`, bidi).

## Deeper: connectivity states

`ClientConn` goes through states (Idle, Connecting, Ready, TransientFailure, Shutdown). For the lab: if the server is up before the client, the first RPC usually succeeds after connect. If you are debugging “I hang”, log the state or temporarily enable gRPC log env vars.

## Deeper: parent context from HTTP

```go
func (h *Handler) ServeHTTP(w http.ResponseWriter, r *http.Request) {
	ctx, cancel := context.WithTimeout(r.Context(), 800*time.Millisecond)
	defer cancel()
	reply, err := h.catalog.SayHello(ctx, &demopb.HelloRequest{Name: r.URL.Query().Get("n")})
	// ...
}
```

When the HTTP client disconnects, `r.Context()` cancels and the gRPC RPC should move toward cancellation.

## Deeper: errors that are not status

If you yourself create `err := errors.New("x")` on the client side before the call, that is not a gRPC code. Distinguish: transport/RPC err vs local validation.

## Deeper: message size on the client

`grpc.WithDefaultCallOptions(grpc.MaxCallRecvMsgSize(...))` protects the client from a huge response. Symmetry with server `MaxRecvMsgSize`.

## Predict-then-check

**A.** `defer cancel()` before the call, but you call `cancel()` manually right after `WithTimeout`.  
Outcome: RPC immediately canceled.

**B.** Two clients, two `NewClient` to the same server.  
Outcome: works, but usually unnecessary; one conn is enough.

**C.** Target `localhost:50051` on a system where `localhost` goes to `::1`, and the server listens only on IPv4.

## Extension: what you carry into 03.04

A streaming client uses the **same** `conn` and stub. The call shape changes:

## Mechanism (continued): what `NewClient` does not guarantee

`NewClient` success ≠ server available. It only means the `ClientConn` object was created and options were accepted. The real dial can fail later. So:

- the first RPC can return `Unavailable`;
- or you call `Connect()` and watch the state;
- you always have a timeout on the RPC so you do not hang forever.

### Failed dial trace

```text
NewClient OK
SayHello(ctx)
  -> runtime tries connect
  -> connection refused
  -> err with codes.Unavailable (typically)
  -> ctx timeout if dial takes too long
```

### Successful unary trace

```text
NewClient OK
SayHello(ctx, {name:Ana})
  -> connect (if needed)
  -> HTTP/2 stream
  -> response HelloReply
  -> err == nil
```

## Mechanism (continued): how the timeout “travels”

`context.WithTimeout` sets a deadline. gRPC-Go computes remaining time and sends it to the server (timeout protocol). The server’s `ctx` cancels near the same moment. Clock skew exists, but the model is: **one deadline for the whole RPC chain** if you pass the same ctx further.

If the server calls another RPC with a **new** long timeout and ignores the parent — you break the chain. Idiom: `ctx` downward, shorten only consciously.

## Mechanism (continued): CallOptions

```go
reply, err := client.SayHello(
	ctx,
	req,
	grpc.WaitForReady(true),
)
```

`CallOptions` change one call. Defaults on the conn you set with `grpc.WithDefaultCallOptions`. For the course: the most important “option” is actually a good `ctx` timeout; the rest as needed.

## Table: code → client action

| Code | Typical action |
|------|----------------|
| OK | process reply |
| InvalidArgument | no retry; fix request |
| NotFound | no retry; UI message |
| Unauthenticated | refresh token / sign in |
| PermissionDenied | no retry; audit |
| Unavailable | limited retry + backoff |
| DeadlineExceeded | metrics; maybe larger timeout or faster server |
| Canceled | you canceled; do not treat as server fail |
| Unimplemented | deploy/version bug |

## Extension: what is different in a stream client

Unary returns `(*Reply, error)`. Stream returns `(StreamClient, error)` then a loop. The deadline still lives in the `ctx` passed when opening the stream. If ctx expires mid-`Recv`, you get cancel — expected.

## Mechanism (deepening): List / Upload client

```go
stream, err := client.List(ctx, &demopb.ListRequest{PageSize: 10})

	item, err := stream.Recv()

		break
	}

		return err
	}
	_ = item
}

up, err := client.Upload(ctx)

	if err := up.Send(&demopb.UploadChunk{Data: c}); err != nil {
		return err
	}
```
