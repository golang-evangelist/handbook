# 03.02 Creating gRPC servers in Go

> **Go Path - Zero to Gopher** / **03 Others → gRPC Fundamentals in Go** / Lesson 03.02

## Lesson goals

After this lesson you can:

- define a Catalog service in `.proto` and generate Go code;
- implement the `CatalogServer` `interface` (unary `SayHello`);
- bring up a server with `grpc.NewServer`, `RegisterCatalogServer`, and `Serve`;
- return errors via `status` / `codes`;
- follow the trace from `Listen` to the response to the client;
- stop the server in a controlled way (`GracefulStop` / `Stop`).

## Prerequisite

- 03.01 (RPC, HTTP/2, protobuf, IDL, Catalog contract).
- `protoc`, `protoc-gen-go`, `protoc-gen-go-grpc` available on PATH.
- Go 1.22+ and a module (`go.mod`).

## Problem this lesson solves

Many tutorials show a “hello server” without an ordered set of steps: where `.proto` lives, what exactly `Register` does, why `Serve` blocks, and how an error reaches the client. Without that, debugging looks like guessing. This lesson builds the **server path** to the first successful unary RPC.

## Mental model

```text
catalog.proto
    -> protoc (+ plugins)
        -> demopb (messages + CatalogServer + Register)
            -> your struct implements SayHello
                -> grpc.NewServer()
                -> RegisterCatalogServer(s, impl)
                -> net.Listen + s.Serve(lis)
```

Four mandatory points: **contract → generate → implementation → registration + Serve**. Skip one and you get `Unimplemented`, an empty listen, or code that does not compile.

## Mechanism

### 1) Module and dependencies

```bash
mkdir -p catalog-server && cd catalog-server
go mod init example.com/demo
go get google.golang.org/grpc@latest
go get google.golang.org/protobuf@latest
```

Plugins (once on the machine / in the CI image):

```bash
go install google.golang.org/protobuf/cmd/protoc-gen-go@latest
go install google.golang.org/grpc/cmd/protoc-gen-go-grpc@latest
```

Check: `protoc --version`, `protoc-gen-go --version`, `protoc-gen-go-grpc --version`.

### 2) Proto file (same Catalog)

Save as `api/proto/demo/v1/catalog.proto` (the path is a project agreement):

```proto
syntax = "proto3";

package demo.v1;

option go_package = "example.com/demo/gen/demopb;demopb";

service Catalog {
  rpc SayHello(HelloRequest) returns (HelloReply);
  rpc List(ListRequest) returns (stream Item);
  rpc Upload(stream Chunk) returns (UploadSummary);
}

message HelloRequest { string name = 1; }
message HelloReply { string message = 1; }
message ListRequest { string prefix = 1; int32 limit = 2; }
message Item { string id = 1; string title = 2; }
message Chunk { bytes data = 1; }
message UploadSummary { int64 bytes_received = 1; }
```

In this lesson you implement **only** `SayHello`. `List` and `Upload` remain for 03.04; the generated `interface` still requires all methods — so you embed `UnimplementedCatalogServer` (the modern generator expects that).

### 3) Generation

From the module root (adjust include paths):

```bash
protoc \
  -I api/proto \
  --go_out=. --go_opt=module=example.com/demo \
  --go-grpc_out=. --go-grpc_opt=module=example.com/demo \
  api/proto/demo/v1/catalog.proto
```

An alternative with `paths=source_relative` if you keep gen next to the proto file. Important: a `demopb` package appears with:

- message types;
- `CatalogServer` `interface`;
- `UnimplementedCatalogServer` struct (embedding);
- `RegisterCatalogServer`;
- `CatalogClient` (for later).

### 4) Service implementation

```go
package main

import (
	"context"

	"example.com/demo/gen/demopb"
	"google.golang.org/grpc/codes"
	"google.golang.org/grpc/status"
)

type catalogServer struct {
	demopb.UnimplementedCatalogServer
}

func (s *catalogServer) SayHello(ctx context.Context, req *demopb.HelloRequest) (*demopb.HelloReply, error) {
	if err := ctx.Err(); err != nil {
		return nil, err
	}
	name := req.GetName()
	if name == "" {
		return nil, status.Error(codes.InvalidArgument, "name is required")
	}
	return &demopb.HelloReply{Message: "hello, " + name}, nil
}
```

**Why embed `UnimplementedCatalogServer`?** When you add a new RPC to the proto and regenerate, the old server still compiles; unimplemented methods return `Unimplemented` instead of breaking your build (depending on generated options — follow the generated comments). That is a safer default for API evolution.

### 5) NewServer, Register, Serve

```go
package main

import (
	"log"
	"net"

	"example.com/demo/gen/demopb"
	"google.golang.org/grpc"
)

func main() {
	lis, err := net.Listen("tcp", "127.0.0.1:50051")
	if err != nil {
		log.Fatalf("listen: %v", err)
	}

	s := grpc.NewServer(
		grpc.MaxRecvMsgSize(4<<20), // 4 MiB — defensive
	)
	demopb.RegisterCatalogServer(s, &catalogServer{})

	log.Printf("catalog gRPC on %s", lis.Addr())
	if err := s.Serve(lis); err != nil {
		log.Fatalf("serve: %v", err)
	}
}
```

Startup trace:

```text
1. Listen opens a TCP socket (no gRPC semantics yet)
2. NewServer builds the runtime: codec, interceptor chain (empty), service map
3. RegisterCatalogServer writes methods into the map (/demo.v1.Catalog/SayHello, ...)
4. Serve enters the loop: Accept -> HTTP/2 -> dispatch -> your SayHello
```

Without step 3, the client gets `Unimplemented`. Without step 1, there is no port. Without step 4, the process exits immediately if `Serve` is not called.

### 6) What `Serve` does with one unary call

```text
Accept connection
  -> HTTP/2 preface / settings
  -> HEADERS :path=/demo.v1.Catalog/SayHello
  -> DATA (HelloRequest)
  -> lookup handler
  -> catalogServer.SayHello(ctx, req)
  -> HEADERS + DATA (HelloReply) + TRAILERS grpc-status=0
```

Each RPC typically lives in its own goroutine inside the server. So your handler must be safe for concurrent access if it shares state (mutex / no shared mutable state).

### 7) Errors and status

```go
return nil, status.Errorf(codes.NotFound, "item %q not found", id)
```

Mapping you should remember:

| Situation | Typical code |
|-----------|--------------|
| Bad input | `InvalidArgument` |
| No entity | `NotFound` |
| No auth | `Unauthenticated` |
| No permission | `PermissionDenied` |
| Overload | `ResourceExhausted` |
| Temporarily unavailable | `Unavailable` |
| Internal bug | `Internal` |
| Method not there | `Unimplemented` |

Do not return `Internal` for a user error — clients will retry the wrong things.

### 8) Context on the server

`ctx` in `SayHello` is cancellable:

```go
select {
case <-ctx.Done():
	return nil, ctx.Err()
case res := <-work:
	return res, nil
}
```

If you do slow I/O without respecting `ctx`, the client cancels and you still spend CPU/DB. That is a common production mistake.

### 9) Graceful stop

`Serve` blocks. For a clean shutdown:

```go
go func() {
	// wait for signal (SIGINT) — omitted for brevity
	s.GracefulStop() // waits for active RPCs (with timeout policy)
}()
```

`Stop` is harder: it cancels immediately. In microservices (04.02) you see the same pattern around `http.Server.Shutdown` — same idea, different API.

### 10) TLS note (defensive)

The local example listens on plaintext. In production:

```go
creds, err := credentials.NewServerTLSFromFile("server.crt", "server.key")
s := grpc.NewServer(grpc.Creds(creds))
```

Do not learn attack; remember: plaintext only in the lab.

### 11) Message limit and resource exhaustion

Without a limit, a client can send a huge message. `MaxRecvMsgSize` is basic defense. Also think about authentication and rate limiting (interceptor) — outside the minimal hello server, but not “never later”.

### 12) Why not `http.Handle` for gRPC

A gRPC server is not an ordinary `net/http` handler in this basic flow (there is `grpc.Server` as an HTTP/2 handler in more advanced setups). For fundamentals use `net.Listen` + `Serve`. Mixing with REST on the same port is possible, but complicates the lesson — keep them separate until you master Register/Serve.

## Rules and syntax

1. Unary method signature: `(context.Context, *Req) (*Resp, error)`.
2. Embedding `UnimplementedCatalogServer` in modern generated code.
3. `Register*Server` before `Serve`.
4. `Serve` blocks — do not put it in a goroutine without a lifecycle plan.
5. Errors: `status` package, not a bare `errors.New` if you want a meaningful code.
6. `GetName()` instead of the field directly — idiomatic with generated getters (nil-safe on messages).

## Examples

### Example 1: Minimal `main` + server in one file

See sections 4–5 above. Run: `go run .` and leave the process alive.

### Example 2: Predict — forgotten Register

```go
s := grpc.NewServer()
// no RegisterCatalogServer
_ = s.Serve(lis)
```

#### What happens here

`grpc.NewServer` builds a server that has no services registered yet. The comment records the missing `RegisterCatalogServer` call. `Serve` still blocks on `lis`, and this sketch discards the error from `Serve`. A client `SayHello` finds no handler, so the runtime returns `codes.Unimplemented`.

**Predict:** client calls `SayHello` → `codes.Unimplemented`.  
**Check:** add Register; same binary, different outcome.

### Example 3: Predict — empty name

Client sends `Name: ""`.  
**Predict:** `InvalidArgument`, message `name is required`.  
**Check:** `status.Convert(err).Message()`.

### Example 4: Concurrent handlers

```go
type catalogServer struct {
	demopb.UnimplementedCatalogServer
	hits atomic.Int64
}

func (s *catalogServer) SayHello(ctx context.Context, req *demopb.HelloRequest) (*demopb.HelloReply, error) {
	s.hits.Add(1)
	return &demopb.HelloReply{Message: "ok"}, nil
}
```

#### What happens here

`catalogServer` embeds `UnimplementedCatalogServer` and keeps `hits` in an `atomic.Int64`. `SayHello` adds one to that counter and returns a reply whose message is `ok`. `Add` is safe when many RPC goroutines run the method at the same time. `ctx` and `req` stay unused here because the snippet is about the shared counter.

Use `atomic` or `Mutex` for a shared counter. Explanation: more RPCs = more goroutines.

### Example 5: List/Upload stub so the build passes

If the generator does *not* embed Unimplemented, you must write:

```go
func (s *catalogServer) List(req *demopb.ListRequest, stream demopb.Catalog_ListServer) error {
	return status.Error(codes.Unimplemented, "List not implemented yet")
}

func (s *catalogServer) Upload(stream demopb.Catalog_UploadServer) error {
	return status.Error(codes.Unimplemented, "Upload not implemented yet")
}
```

#### What happens here

`List` accepts the request and a server stream, and `Upload` accepts only the client-stream argument. Both methods return `status.Error` with `codes.Unimplemented` and a short message. These bodies let `catalogServer` satisfy the generated interface when `UnimplementedCatalogServer` is absent. The parameter lists have to match that interface exactly.

Signatures must match the generated `interface` exactly — do not invent them. In 03.04 you fill them with real flows.

## Decision analysis

**One `grpc.Server` per process?** Usually yes for one listen socket. Multiple services (Catalog + Health) you register on the same `Server`.

**Health check?** Production often adds `grpc.health.v1`. For the lab it is not required; for Kubernetes readiness — yes.

**Interceptors now?** You can add a logging interceptor, but first verify unary works without it. Middleware/interceptor is a higher-order function around the handler — the same idea as HTTP middleware in 04.06.

## Trade-offs

| Choice | Plus | Minus |
|-------|------|-------|
| Everything in `main` | fast learning | bad for testing |
| `internal/server` package | cleaner tests | more files |
| Plaintext | simple | lab only |
| Huge MaxRecvMsgSize | fewer errors for large files | memory risk |
| GracefulStop | cleaner deploy | needs signal handling |

## Common mistakes

1. Forgotten `Register*Server`.
2. Listen on the wrong interface (`:50051` vs `127.0.0.1`) then firewall/confusion.
3. `Serve` in main without a log — it looks like “nothing works” while it is actually waiting.
4. Returning `fmt.Errorf` → client sees `Unknown`.
5. Ignoring `ctx` in a slow handler.
6. Holding a mutable map without synchronization.
7. Generating into the wrong module path (`go_package` does not match).
8. Mixing versions of `protoc-gen-go` and the `protobuf` runtime.

## Idiomatic Go

- Thin gRPC shell; domain in `internal/catalog`.
- Input validation at the boundary (handler or a small use-case layer).
- `log/slog` with method name and code.
- Test the handler without the network: call `SayHello` directly in a unit test.
- Integration test: bring up `bufconn` or a real port.

## Practical scenario

The team adds Catalog echo before the real inventory RPC. The first PR forgets Register — QA sees `Unimplemented` and thinks the proto is wrong. The second PR returns `errors.New("bad name")` — the mobile client does not know how to map that to the UI. The third PR adds `status.Error` + Unimplemented embedding + MaxRecvMsgSize. The CI smoke test starts the server, calls `SayHello`, checks the message. Only then do they open stream methods.

## Check questions

1. **Which three calls make the server skeleton?** `NewServer`, `Register*Server`, `Serve`.
2. **What does the client see without Register?** `Unimplemented`.
3. **Why embed `UnimplementedCatalogServer`?** Default unimplemented methods + easier evolution.
4. **Where does the deadline live on the server?** In `ctx`; check `ctx.Err()` / `ctx.Done()`.
5. **Why `status.Error` instead of a bare `error`?** So the client gets a stable `codes` contract.
6. **Does `Serve` return immediately?** No; it blocks until the server is stopped.

## Summary

Server path: proto → generate → implement `CatalogServer` → `NewServer` → `Register` → `Listen`/`Serve`. Unary `SayHello` returns a message or a `status` error. Respect `context`, limit message size, plaintext only locally. Next lesson: client with `grpc.NewClient` and deadline.

## Deeper: what Register writes

Generated code typically registers a `grpc.ServiceDesc` with:

- `ServiceName: "demo.v1.Catalog"`;
- a list of methods (`MethodName`, handler function);
- stream descriptors for `List` / `Upload`.

`RegisterCatalogServer` is a thin wrapper that dribbles that into `*grpc.Server`. That is why the package+service name must match what the client sends in `:path`.

## Deeper: nil receiver and empty server

```go
var s *catalogServer // nil
demopb.RegisterCatalogServer(gs, s) // dangerous
```

If the method has a pointer receiver and `s` is nil, the call can panic. Always register `&catalogServer{}` (or a valid value).

## Deeper: test without a port

```go
func TestSayHello(t *testing.T) {
	s := &catalogServer{}
	resp, err := s.SayHello(context.Background(), &demopb.HelloRequest{Name: "Ana"})
	if err != nil {
		t.Fatal(err)
	}
	if resp.GetMessage() != "hello, Ana" {
		t.Fatalf("got %q", resp.GetMessage())
	}
}
```

This tests logic without the network. Add a network test separately.

## Deeper: bufconn trace (integration)

```go
lis := bufconn.Listen(1024 * 1024)
```


Same TCP port, different `:path` prefixes. Do not mix this with the “one process = one bounded context” decision from 04.01 — that is architecture, not a Listen limit.

## Predict-then-answers: Serve and lifecycle

**Q:** What happens if you call `Serve` twice on the same server?  
**A:** Do not do that; one `Serve` per server instance. A second call is not a supported pattern.

**Q:** Can `Listen` be a unix socket?  
**A:** Yes (`net.Listen("unix", ...)`), the client target must match. For the course we stay on TCP localhost.

**Q:** Does `MaxRecvMsgSize` limit the stream total or per message?  
**A:** Per message (recv message). A stream of a million small chunks can still spend time/CPU — other limits (timeout, app logic) are still needed.

## Mechanism (continued): from Accept to handler

When `Serve` receives a new TCP connection:

1. The gRPC transport negotiates HTTP/2 (for a plaintext lab connection — h2c style within the gRPC stack).
2. For each new stream it reads headers.
3. From `:path` it extracts service and method.
4. It looks up the `ServiceDesc` written by Register.
5. It allocates/decodes the request according to the method type (unary vs stream).
6. It calls the generated wrapper that calls your method.
7. It encodes the response or status trailers.

If step 4 has no hit → `Unimplemented`. If in step 5 the message exceeds `MaxRecvMsgSize` → error before your code. That is why limits protect even before business logic.

## Mechanism (continued): interceptor as a higher-order function

A server unary interceptor has roughly this shape:

```go
func loggingInterceptor(
	ctx context.Context,
	req any,
	info *grpc.UnaryServerInfo,
	handler grpc.UnaryHandler,
) (any, error) {
	start := time.Now()
	resp, err := handler(ctx, req)
	slog.Info("rpc", "full_method", info.FullMethod, "code", status.Code(err), "dur", time.Since(start))
	return resp, err
}

s := grpc.NewServer(grpc.UnaryInterceptor(loggingInterceptor))
```

That is a **higher-order function**: it takes `handler`, returns behavior around it. Same idea as HTTP middleware in 04.06. For fundamentals it is enough to know it exists; you do not have to assemble it immediately.

## Mechanism (continued): panics

If a handler does `panic`, the default server may crash the process or stream depending on version/options. Do not rely on luck: validate input, do not panic on a bad request. `Internal` status + log stack for real bugs.

## Diagnostics: five questions when “it does not work”

1. Is the process listening at all? (`netstat` / address log)
2. Was Register called?
3. Does `:path` match package+service+method?
4. Does the client use the same credentials (plaintext vs TLS)?
5. Does the error have `codes` or is it a local dial fail?

Answer in order — do not scale the log level to 99 immediately.

## Mechanism (deepening): from Accept to handler

```text
net.Listen → grpc.NewServer → RegisterCatalogServer → Serve
  → Accept TCP
  → HTTP/2 preface / settings
  → HEADERS :path=/demo.v1.Catalog/SayHello
  → lookup service/method in registry
  → deserialize req
  → unary interceptor chain (if any)
  → your SayHello(ctx, req)
  → serialize resp OR status trailers
```

`Register*` writes descriptors. If you forget Register, the client gets Unimplemented — not “connection refused”.

**Predict:** `Serve` without Register.  
**Answer:** the server lives, methods do not.

**Predict:** nil implementation passed to Register.  
**Answer:** panic or broken runtime — always pass a concrete struct.

## Mechanism (deepening): Unimplemented built in

```go
type server struct {
	demopb.UnimplementedCatalogServer
}
```

When the proto gets a new RPC method, the old binary does not have to implement it immediately — it returns Unimplemented until you fill it in. That is a backward-compatibility mechanism for the implementation, not a substitute for proto message compatibility.

## Mechanism (deepening): status in the handler

```go
func (s *server) SayHello(ctx context.Context, req *demopb.HelloRequest) (*demopb.HelloReply, error) {
	if req.GetName() == "" {
		return nil, status.Error(codes.InvalidArgument, "name required")
	}
	return &demopb.HelloReply{Message: "Hello " + req.GetName()}, nil
}
```

Rules:

- validation → InvalidArgument  
- no resource → NotFound  
- do not panic for expected errors  
- message short, no secrets  

## Mechanism (deepening): interceptor as higher-order

```go
func logging(ctx context.Context, req any, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (any, error) {
	start := time.Now()
	resp, err := handler(ctx, req)
	code := status.Code(err)
	log.Printf("method=%s code=%v dur=%s", info.FullMethod, code, time.Since(start))
	return resp, err
}
srv := grpc.NewServer(grpc.UnaryInterceptor(logging))
```

Chain order matters: auth before business logging details. The same FullMethod string you see in metrics.

## Mechanism (deepening): context and cancel

```go
select {
case <-ctx.Done():
	return nil, status.FromContextError(ctx.Err()).Err()
case result := <-work:
	return result, nil
}
```

Long work without checking ctx = work after the client timeout.

## Mechanism (deepening): List / Upload on the server (skeleton)

```go
func (s *server) List(req *demopb.ListRequest, stream demopb.Catalog_ListServer) error {
	for _, it := range s.store.Page(req.GetPageSize()) {
		if err := stream.Context().Err(); err != nil {
			return err
		}
		if err := stream.Send(it); err != nil {
			return err
		}
	}
	return nil
}

func (s *server) Upload(stream demopb.Catalog_UploadServer) error {
	var n int64
	for {
		chunk, err := stream.Recv()
		if errors.Is(err, io.EOF) {
			return stream.SendAndClose(&demopb.UploadSummary{Bytes: n})
		}
		if err != nil {
			return err
		}
		n += int64(len(chunk.GetData()))
	}
}
```

## Mechanism (deepening): test without a port (bufconn intuition)

An in-memory listener enables an integration test without a TCP port. Idea: same Register/Serve path, different Listener. Use in CI so you do not chase flaky ports.

## Mechanism (deepening): graceful stop

```go
go srv.Serve(lis)

srv.GracefulStop() // or Stop() when you must immediately
```

GracefulStop waits for active RPCs. Align with the container grace period — the same operational story as HTTP Shutdown.
