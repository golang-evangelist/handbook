# 11.01 Getting started with Go and non-relational databases

> **Go Path - Zero to Gopher** / **03 Others → Accessing No-Relational Database in Go** / Lesson 11.01

## Lesson goals

After this lesson you should be able to:

- distinguish the **document** model (MongoDB) from the **key-value** model (Redis) and from the **relational** model (Postgres)
- decide when Mongo makes sense versus Postgres, and when Redis is only a helper layer
- connect to MongoDB with the official driver `go.mongodb.org/mongo-driver` via `mongo.Connect`
- configure `options.Client`, run `Ping`, get `Database` and `Collection`
- understand BSON as data (`bson.D` / `bson.M` / struct tags), not as a string you glue together
- always bind network operations to a `context` with a timeout
- briefly know where `go-redis` stands as contrast (cache, TTL, session) — without replacing the Mongo focus

## Prerequisite

- Go 1.22+ installed; `go mod` habits
- Docker or Compose for local MongoDB (port 27017)
- understanding of `context.Context`, `WithTimeout`, `defer cancel`
- experience with HTTP or CLI in Go (enough to see where the store sits)
- GORM / SQL module is not required, but helps compare mental models
- env discipline: secrets do not go into git (URI with password from `MONGODB_URI`)

## Problem this lesson solves

Not every piece of data sits nicely in tables with a fixed schema. A catalog with 30 optional attributes, an event as a document, a session as a blob with TTL — those are different needs. Teams often:

1. push everything into Postgres and suffer from wide NULL columns or JSONB without discipline
2. or the reverse — put a strictly relational financial ledger into Mongo “because it is modern”

The wrong model costs more than the wrong handler. This lesson sets a **map of the territory** and a practical start: client, ping, database/collection, BSON, timeout. CRUD details come in 11.02; here you must know *what* you are connecting and *why*.

Second problem: people treat filters as SQL strings. In the Mongo Go driver a filter is **structured data** (`bson.D`, `bson.M`, struct). There is no “glue user input into the query”. That is not style — that is a security and type contract.

## Mental model

Three families of storage you will meet in Go services:

| Type | Example | Unit | Typical strength | Typical weakness |
|------|---------|------|------------------|------------------|
| Relational | Postgres | row / table | JOIN, transactions, schema, constraint | awkward variable shape |
| Document | MongoDB | BSON document / collection | flexible shape, embed, horizontal patterns | ad-hoc JOIN costlier; index discipline |
| Key-value | Redis | key → value | latency, TTL, in-memory structures | not the primary source of truth for lasting money without a plan |

### Document (MongoDB)

- document ≈ JSON object, in practice **BSON** (binary)
- collection ≈ a group of documents (rough table analog, without fixed schema at server level)
- database (`Database`) groups collections
- default identifier: `_id` (often `primitive.ObjectID`)
- query = filter document; update = document with operators (`$set` in the next lesson)

### Key-value (Redis, contrast)

- key is a string; value is string / hash / list / set / sorted set
- TTL is a first-class idea
- often sits **in front of** the primary database (cache), not instead of it
- in this lesson: only `Ping` / `Set` / `Get` as orientation via `github.com/redis/go-redis/v9`

### Relational (Postgres, reference)

- schema up front; NULL and types are part of the contract
- JOIN and transactions are cheap mentally and in tooling
- when the domain is row + relation + constraint — Postgres remains the default choice

### When Mongo vs when Postgres

Choose Mongo when:

- document shape varies by entity type (attribute catalog)
- you read an aggregate as a whole (order + items embed)
- the team already lives in document tooling and knows indexes / aggregations

Stay on Postgres when:

- strict constraints and reporting via JOIN are the core
- you already have mature SQL ops and little document need (JSONB can fit)
- a financial ledger where the schema is law

Polyglot persistence per bounded context is normal: Mongo for catalog, Postgres for payment, Redis for session.

### Layer in the application

```text
HTTP / CLI
    ↓ context
service
    ↓
store (*mongo.Collection or repo)
    ↓
*mongo.Client  →  Database("shop")  →  Collection("products")
```

One `*mongo.Client` per process (like `*sql.DB`). `Database` and `Collection` are cheap handles — they do not open a new TCP per call.

## Mechanism

This section is the core of the lesson: exactly what the driver does from URI to collection, how BSON enters the wire, and where timeout cuts waiting.

### 1. Official driver and modules

Module:

```text
go.mongodb.org/mongo-driver
```

Packages you use immediately:

| Package | Role |
|---------|------|
| `mongo` | `Connect`, `Client`, `Database`, `Collection`, errors |
| `mongo/options` | `Client().ApplyURI`, timeout options, later Find/Index |
| `bson` | `bson.M`, `bson.D`, marshal/unmarshal |
| `bson/primitive` | `ObjectID`, `NewObjectID`, `ObjectIDFromHex` |

Installation:

```bash
go get go.mongodb.org/mongo-driver/mongo@latest
```

Pin the version in `go.mod`. Follow release notes around the `bson` API.

### 2. URI and client options

URI carries host, auth, optionally query-string options:

```text
mongodb://USER:PASS@localhost:27017
```

In code:

```go
uri := os.Getenv("MONGODB_URI")
opts := options.Client().ApplyURI(uri)
```

`ApplyURI` parses the string and fills `ClientOptions`. You can extend:

```go
opts.SetServerSelectionTimeout(5 * time.Second)
opts.SetConnectTimeout(5 * time.Second)
```

**Prediction:** if the URI has a wrong host, `Connect` can “succeed” locally (the client is created), and the first `Ping` or operation fails on selection/timeout.

**Answer:** always `Ping` after `Connect` in bootstrap. `Connect` in the modern driver initializes the client; network proof is `Ping`.

### 3. `mongo.Connect` and lifetime

```go
ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
defer cancel()

client, err := mongo.Connect(ctx, options.Client().ApplyURI(uri))
if err != nil {
	return fmt.Errorf("connect: %w", err)
}
```

What happens:

1. the driver reads options
2. prepares a connection pool to the cluster / standalone
3. returns `*mongo.Client` or a parse/init error

**Do not** call `mongo.Connect` per HTTP request. Do it once in `main` / `wire` / `fx` lifecycle, share the client.

Shutdown:

```go
shutdownCtx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()
if err := client.Disconnect(shutdownCtx); err != nil {
	log.Printf("disconnect: %v", err)
}
```

Without `Disconnect` in long CLI jobs the pool leaks; in short scripts the OS cleans up, but idiomatically always close.

### 4. `Ping` — proof the path works

```go
if err := client.Ping(ctx, nil); err != nil {
	return fmt.Errorf("ping: %w", err)
}
```

The second argument is `*readpref.ReadPref` (e.g. primary). `nil` = default.

**Trace of a successful start:**

```text
main
  → WithTimeout(10s)
  → mongo.Connect(ctx, opts)
  → client.Ping(ctx, nil)
       → server selection
       → hello / ping command
  → OK
  → Database("shop").Collection("products")
```

**Trace of failure (wrong port):**

```text
Ping
  → waits for server selection
  → context deadline exceeded  OR  connection refused
  → err ≠ nil → Fatal / return 503 in health
```

**Prediction:** a health endpoint without a timeout can hang forever if the network is dead.

**Answer:** `context.WithTimeout(r.Context(), 2*time.Second)` around `Ping` in `/healthz`.

### 5. `Database` and `Collection`

```go
db := client.Database("shop")
coll := db.Collection("products")
```

- database name: string (`"shop"`)
- collection name: string (`"products"`)
- Mongo often **lazily** creates the database/collection on first write — that is why an empty collection list after Ping is not an error

`ListCollectionNames`:

```go
names, err := db.ListCollectionNames(ctx, bson.M{})
```

The list filter is again a BSON document (`bson.M{}` = no extra filter), not SQL.

### 6. BSON as data

BSON ≈ JSON + types (ObjectID, Date, Binary, …). In Go three common forms:

**A) Struct + tag**

```go
type Product struct {
	ID    primitive.ObjectID `bson:"_id,omitempty"`
	SKU   string             `bson:"sku"`
	Name  string             `bson:"name"`
	Cents int                `bson:"cents"`
}
```

- `omitempty` on `_id` lets the server assign ID on insert
- tag `bson` is not `json` — if you only have `json`, fields can stay empty in the database

**B) `bson.M` — map**

```go
doc := bson.M{"sku": "ABC", "name": "Filter", "cents": 1200}
```

Fast for scripts and ad-hoc filters. Key order is not guaranteed (map).

**C) `bson.D` — ordered pair slice**

```go
filter := bson.D{{Key: "sku", Value: "ABC"}}
```

Use when element order matters (e.g. index keys, some operators). For simple equality both `M` and `D` work.

**Filter safety rule:** you build the filter as values in `bson.M` / `bson.D` / struct fields. The user string goes **as a field value**, not as the source of query structure.

```go
// correct: sku is data in the filter document
sku := r.PathValue("sku")
filter := bson.M{"sku": sku}
```

Do not learn “string injection” patterns. There is no gluing of query parts. If you need a dynamic condition, you add elements to `bson.D` / a map in code — the structure stays yours, values come from outside.

### 7. ObjectID

```go
id := primitive.NewObjectID()
hex := id.Hex()

parsed, err := primitive.ObjectIDFromHex(hex)
if err != nil {
	// bad input → 400, not 500
}
```

**Prediction:** you pass string `"abc"` into `ObjectIDFromHex` → error.

**Answer:** map to a validation error before you go to `FindOne`.

Do not force autoincrement int as in SQL without reason — ObjectID is the default document style.

### 8. Context timeout — where exactly it sits

Three layers:

| Layer | Example | Purpose |
|-------|---------|---------|
| Bootstrap | 10–15s on Connect/Ping | application start |
| Request path | 1–5s on store methods | do not block a worker forever |
| Shutdown | 5s on Disconnect | graceful |

```go
ctx, cancel := context.WithTimeout(parent, 3*time.Second)
defer cancel()
err := coll.FindOne(ctx, filter).Decode(&out)
```

If the parent (`r.Context()`) expires earlier, the inner timeout respects the earlier deadline.

**Timeout trace:**

```text
FindOne(ctx)
  → sends OP_MSG
  → waits for response
  → ctx Done()
  → driver interrupts / returns context.DeadlineExceeded (or wrapped)
```

### 9. Redis as contrast (briefly, without depth)

```go
import "github.com/redis/go-redis/v9"

rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
if err := rdb.Ping(ctx).Err(); err != nil {
	return err
}
err := rdb.Set(ctx, "session:"+id, payload, time.Hour).Err()
val, err := rdb.Get(ctx, "session:"+id).Result()
```

Role next to Mongo:

```text
request → Redis GET product:SKU
            ├─ hit  → return cache
            └─ miss → Mongo FindOne → SET cache TTL → return
```

Redis does not replace a document store. Invalidation after changing a document is a separate problem (TTL or delete the key) — CRUD details are 11.02.

Env:

```text

```

**Race trace without healthcheck:**

```text
compose up
  → app starts immediately
  → Connect/Ping
  → mongo not ready yet
  → error → crash loop
```

With `depends_on: condition: service_healthy` (Compose v2) the app waits for the container ping.

### 11. Read preference and write concern (orientation)

On a local standalone Docker default is enough. In a production replica set:

- **write concern** — how many nodes confirm the write
- **read preference** — primary vs secondary

Do not “optimize” a stale read before you understand that a secondary can lag. For this module: know the knobs exist; leave default until you build a cluster.

### 12. Operation comparison (mental table)

| SQL concept | Mongo |
|-------------|-------|
| database | database |
| table | collection |
| row | document |
| primary key | `_id` |
| NULL | field absent or `null` |
| JOIN | embed or later `$lookup` |
| prepared statement parameters | values in `bson.M` / `bson.D` |

Embed (`items` inside an order document) often replaces JOIN on read. Cost: updating a shared entity in multiple places. Choose embed vs reference consciously.

### 13. Full bootstrap mechanism (one pass)

```go
func openMongo(ctx context.Context, uri string) (*mongo.Client, error) {
	ctx, cancel := context.WithTimeout(ctx, 15*time.Second)
	defer cancel()

	client, err := mongo.Connect(ctx, options.Client().ApplyURI(uri))
	if err != nil {
		return nil, err
	}
	if err := client.Ping(ctx, nil); err != nil {
		_ = client.Disconnect(context.Background())
		return nil, err
	}
	return client, nil
}
```

**Prediction:** Ping fails → you leave the client without Disconnect → leak in tests that repeat open.

**Answer:** on error after successful Connect, Disconnect before return.

### 14. Store wrapper — why now, before CRUD

```go
type Store struct {
	products *mongo.Collection
}

func NewStore(client *mongo.Client) *Store {
	return &Store{
		products: client.Database("shop").Collection("products"),
	}
}
```

Isolation mechanism: the handler does not see the URI or database name. 11.02 only adds methods to this shape.

### 15. What the driver *does not* do for you

- does not validate business rules (empty SKU)
- does not impose a schema like SQL (unless you add server validation — out of scope)
- does not choose indexes automatically for your access pattern
- does not replace redis cache policy

Your job in this lesson: correct client, correct BSON, correct timeout, clear mental model.

## Rules and syntax

1. **Always** `context.WithTimeout` (or parent deadline) around Connect, Ping, and later operations.
2. URI and credentials from env (`MONGODB_URI`), never committed to the repo.
3. One `*mongo.Client` per process; share it.
4. `Disconnect` on graceful shutdown.
5. Tag `bson:"field"` — do not rely only on the `json` tag for persistence.
6. Filters and documents: `bson.D` / `bson.M` / struct — values as data, not query concatenation.
7. `Database("name")` and `Collection("name")` — explicit names; do not hardcode in 10 places (constant or config).
8. ObjectID: `NewObjectID` / `ObjectIDFromHex`; bad hex = validation error.
9. Ping in bootstrap and in readiness (`/healthz`).
10. Redis (if present) is a helper layer; Mongo remains the document source for this module.
11. Do not mix database names between test and prod URI without intent.
12. Pin `mongo-driver` in `go.mod`.

### Syntax patterns (quick list)

```go
// Connect
client, err := mongo.Connect(ctx, options.Client().ApplyURI(uri))

// Ping
err = client.Ping(ctx, nil)

// Database / Collection
coll := client.Database("shop").Collection("products")

// Filter as data
filter := bson.M{"sku": sku}
// or
filter = bson.D{{Key: "sku", Value: sku}}

// Struct document
p := Product{SKU: "ABC", Name: "Filter", Cents: 1200}
```

### Example 2 — Connect, Ping, list collections

```go
package main

import (
	"context"
	"log"
	"os"
	"time"

	"go.mongodb.org/mongo-driver/bson"
	"go.mongodb.org/mongo-driver/mongo"
	"go.mongodb.org/mongo-driver/mongo/options"
)

func main() {
	uri := os.Getenv("MONGODB_URI")
	if uri == "" {
		log.Fatal("MONGODB_URI empty")
	}

	ctx, cancel := context.WithTimeout(context.Background(), 15*time.Second)
	defer cancel()

	client, err := mongo.Connect(ctx, options.Client().ApplyURI(uri))
	if err != nil {
		log.Fatal(err)
	}
	defer func() {
		_ = client.Disconnect(context.Background())
	}()

	if err := client.Ping(ctx, nil); err != nil {
		log.Fatal("ping:", err)
	}

	names, err := client.Database("shop").ListCollectionNames(ctx, bson.M{})
	if err != nil {
		log.Fatal(err)
	}
	log.Printf("collections: %v", names)
}
```

#### Trace

```text
env MONGODB_URI
 → Connect
 → Ping OK
 → ListCollectionNames(shop, {})
 → [] or ["products", ...]
 → Disconnect
```

#### Prediction

Fresh database → empty slice. That is success, not an error.

### Example 3 — BSON struct vs `bson.M` (same document)

```go
coll := client.Database("shop").Collection("products")

doc := bson.M{"sku": "ABC", "name": "Filter", "cents": 1200}
res1, err := coll.InsertOne(ctx, doc)
// res1.InsertedID — typically ObjectID

type Product struct {
	ID    primitive.ObjectID `bson:"_id,omitempty"`
	SKU   string             `bson:"sku"`
	Name  string             `bson:"name"`
	Cents int                `bson:"cents"`
}

p := Product{SKU: "ABD", Name: "Hose", Cents: 900}
res2, err := coll.InsertOne(ctx, p)
```

#### What happens here

Both times the driver marshals to BSON and sends insert. `bson.M` is faster for a script; struct is better for application code, validation, and tests. Detailed CRUD and errors — 11.02.

#### Prediction

You forget the `bson` tag, leave only `json:"sku"` → in the document the key may be `SKU` or empty behavior depending on settings — often “fields disappear”.

#### Answer

Put explicit `bson` tags on the persistent model.

### Example 4 — Health endpoint with timeout

```go
mux.HandleFunc("GET /healthz", func(w http.ResponseWriter, r *http.Request) {

	defer cancel()
```

```text
GET /healthz

```

```go
rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
```

### Example 8 — Document vs Postgres JSONB (team decision in code)

Same catalog:

- Postgres: table `products` + `attributes JSONB`
- Mongo: collection `products` with nested fields

```go
// Mongo document — attributes are part of the same document
type Product struct {
	SKU        string         `bson:"sku"`
	Name       string         `bson:"name"`
	Attributes map[string]any `bson:"attributes,omitempty"`
}
```

#### When you choose what

If the rest of the system already lives in SQL transactions and JOIN reports — JSONB can be a smaller jump. If the aggregate is document-first and the team knows Mongo indexes — a collection is a cleaner model.

## Decision analysis

### Mongo vs Postgres JSONB

- **JSONB in existing Postgres:** fewer new ops; still SQL; GIN indexes can help.
- **Mongo document-first:** more natural embed; different ops and tooling; horizontal looks different.

Not religion — look at bounded context and team skills.

### One global client

Yes. Same as `*sql.DB` / `*gorm.DB`. The pool lives in the client. New Connect per request kills performance and file descriptors.

### Redis as primary store

Possible for ephemeral data (session, rate limit). For lasting business records you need a persistence strategy and awareness of memory loss / restart. In this course Redis = contrast and cache, not a replacement for 11.02 CRUD.

### `bson.M` vs struct everywhere

- Prototype / one-off job: `bson.M` OK
- A living service: struct + `bson` tags + error mapping

### Embed vs reference

- Embed: one read, consistent aggregate snapshot
- Reference (`otherID`): normalization, more round-trips, easier entity sharing

### Timeout policy

Inner `WithTimeout(ctx, 3*time.Second)` protects from `context.Background()` in a wrong call. Downside: can shorten a longer parent. Document the policy in the store package.

## Trade-offs

| Choice | Gain | Cost |
|--------|------|------|
| Document model | Flexible shape, embed | Weaker ad-hoc JOIN; index discipline |
| Relational model | Constraint, JOIN, mature SQL ops | Wide NULL / JSONB discipline |
| Key-value cache | Low latency, TTL | Invalidation, eventual inconsistency |
| Everything in one Postgres DB | Simpler ops | Awkward documents and mixed approaches |
| Mongo + Redis | Fast read path | Two systems, two errors, two healths |
| No timeout | Fewer lines | Hanging requests and goroutines |
| Connect per request | “looks isolated” | Latency, leaks, chaos |
| Only `json` tags | Fewer tags | Wrong BSON shape |
| Default write/read concern | Simple locally | You must learn the knobs before a production cluster |

## Common mistakes

1. **`mongo.Connect` per HTTP request** — instead of one client in the process.
2. **Without `Ping` / health** — the application “works” until the first real query in production.
3. **URI with password in git** — credential leak.
4. **Mixing `json` and `bson` tags** — empty or wrongly named fields in the collection.
5. **Redis as the only source of truth** for lasting business data without a plan.
6. **Forgotten `Disconnect`** in CLI/batch loops that open the client multiple times.
7. **Without `context` timeout** — Ping/Find hang.
8. **Treating a filter as a SQL string** — trying concatenation instead of `bson.M{"field": value}`.
9. **Wrong database in URI/config** — test writes to the prod database name.
10. **Expecting the collection list is not empty** after a fresh Ping — false alarm.
11. **ObjectID hex without check** — 500 instead of 400.
12. **Ignoring server selection timeout** on a bad network — slow failure.

## Idiomatic Go

```go
package store

import (
	"context"
	"fmt"
	"time"

	"go.mongodb.org/mongo-driver/mongo"
	"go.mongodb.org/mongo-driver/mongo/options"
)

type Store struct {
	client   *mongo.Client
	products *mongo.Collection
}

func Open(ctx context.Context, uri, dbName string) (*Store, error) {
	ctx, cancel := context.WithTimeout(ctx, 15*time.Second)
	defer cancel()

	client, err := mongo.Connect(ctx, options.Client().ApplyURI(uri))
	if err != nil {
		return nil, fmt.Errorf("mongo connect: %w", err)
	}
	if err := client.Ping(ctx, nil); err != nil {
		_ = client.Disconnect(context.Background())
		return nil, fmt.Errorf("mongo ping: %w", err)
	}

	return &Store{
		client:   client,
		products: client.Database(dbName).Collection("products"),
	}, nil
}

func (s *Store) Close(ctx context.Context) error {
	return s.client.Disconnect(ctx)
}
```

Patterns:

- `context` first argument on store methods (from 11.02)
- wrap errors with `%w`
- do not export `*mongo.Collection` if the repo can hide the driver
- tests: separate database name; Compose or Testcontainers

## Practical scenario

A team has a product catalog: 30 optional attributes shoved in as 30 Postgres columns (mostly NULL). Migrations hurt; ORM models are unreadable. They propose a Mongo document per SKU:

```text
{ _id, sku, name, cents, attributes: { color, size, material, ... } }
```

Plan:

1. Compose Mongo + `MONGODB_URI`
2. One `*mongo.Client`, Ping in readiness
3. Store with `Database("catalog").Collection("products")`
4. Redis in front for hot SKU read (TTL 2–5 min)
5. Postgres remains for order and payment — they **do not** kill relational truth because of the catalog

Reporting that did wide SQL JOIN moves to aggregations or export to a warehouse. First week: only Connect/Ping/BSON models. Only then CRUD (11.02) and a unique index on `sku`.

Error they caught early: staging URI pointed at the same database as a local volume share — they separated `catalog_staging` vs `catalog_dev` database names.

## Summary

Non-relational databases are not “anti-SQL” — they are different data models. Document (MongoDB) stores BSON documents in collections; key-value (Redis) holds fast keys with TTL; relational (Postgres) remains king of schema and JOIN. This module chooses **MongoDB** and the official driver `go.mongodb.org/mongo-driver`: `mongo.Connect`, `options.Client`, `Ping`, `Database`, `Collection`, BSON as structured data (`bson.D` / `bson.M` / struct), `context` timeout. Redis is mentioned as contrast and a cache layer, not as a replacement. The next lesson does CRUD: `InsertOne`, `FindOne`, `UpdateOne`, `DeleteOne`, cursors, indexes.
