# 05.01 Introduction — polyglot RPC goal

> **Go Path - Zero to Gopher** / **03 Others → Enhancing Application Communication with gRPC in Go** / Lesson 05.01

## Lesson goals

After this lesson you should be able to:

- explain why gRPC exists in a polyglot environment
- connect a .proto contract to generated clients in multiple languages
- distinguish a public JSON API from internal RPC
- sketch a map of this module (concepts → tooling → Go → Java/C#/Node)
- recognize operational requirements that gRPC does not remove

## Prerequisite

- Go 1.22+
- module 04 completed, especially 04.07
- a basic idea of RPC and HTTP/2 as transport
- a team or personal goal to share a contract across at least two languages

You do not need to have protoc installed yet — that is 05.03. Here we set the goal and the language of explanation for the whole module.

## Problem this lesson solves

Organizations rarely live in a single language. Billing may be Go, legacy CRM Java, internal admin C#, and an event worker Node.js. If each team invents its own JSON contract, you get four “truths” about the same quantity field.

The polyglot RPC goal is: **one .proto contract, generated stubs, the same semantics for status and deadline**, without hand-copying DTOs. This lesson sets up why that works and how the module is layered — not as a copy-paste Pluralsight transcript, but as an engineering compass.

## Mental model

Imagine three circles:

1. **Contract** — .proto messages and services (language-agnostic).
2. **Generation** — a plugin per language builds types and stub/server interfaces.
3. **Adapter** — your implementation in Go/Java/C#/Node that calls the domain.

Browsers and partners can still see JSON at the edge. gRPC is often the *internal* language of the platform. Polyglot does not mean every language does everything; it means the **contract is not owned by one runtime**.

### Why not “just OpenAPI”

OpenAPI is strong for HTTP JSON. gRPC+Protobuf is stronger when you want a binary payload, streaming, and strict generation in languages where JSON schema discipline is weak. They are not enemies: they often coexist (a gateway does transcoding).

### What gRPC does not solve

Deploy, secrets, on-call, idempotency, observability. Module 04.01 still applies. Polyglot only multiplies the number of runtimes you must observe.

## Rules and syntax

1. One source of truth for the contract: .proto in the repo (or a buf schema registry).
2. Generated code is not edited by hand.
3. Package version (package shop.v1) is part of the discipline.
4. Explanations in this course were originally in Serbian (ekavian); code keeps English identifiers.
5. When we show Java/C#/Node, we always give the Go counterpart as well.
6. Do not claim plugin version compatibility from memory — pin in CI (05.03).
7. Deadline and auth metadata are part of the behavioral contract, not “later”.

## Examples

### Example 1 — same method, four stubs

Proto: rpc GetStock(GetStockRequest) returns (GetStockResponse);

- Go: client.GetStock(ctx, req)
- Java: stub.getStock(req)
- C#: client.GetStockAsync(req)
- Node: client.getStock(req, callback) or Promise API

### What happens here

The RPC name and fields stay the same. Teams do not negotiate JSON keys on Slack.

### Example 2 — edge vs core

Browser → JSON /v1/orders → Order Go service → gRPC Inventory (Java)

### What happens here

The public shape stays curl-friendly. The core uses strict RPC. The polyglot goal is on the internal boundary.

### Example 3 — breakage without proto discipline

A Java team adds a field to JSON ad hoc. A Go client ignores it. A month later a Node worker sends a string instead of an int. Production stays quiet until billing falls over.

### What happens here

Without a contract, polyglot is chaos. With proto, CI breaks the build.

### Example 4 — course success map

After 05.11 you should stand up a small GetStock server in Go and call it from at least one other language using the same .proto.

### What happens here

That is proof of the polyglot goal — not a PowerPoint.

## Decision analysis

| Decision | For | Against |
|----------|-----|---------|
| gRPC inside + JSON outside | clear split | two stacks |
| Only gRPC everywhere | one stack | pain for browser/partners |
| Shared proto repo | one truth | needs CI discipline |
| Copying DTOs per language | fast start | divergence |

## Trade-offs

- Polyglot increases contract productivity, but demands tooling literacy.
- Generation reduces boilerplate, but hides wire details until you learn the concepts (hence 05.02).
- More languages = more runtime patches and Docker base images.

## Common mistakes

1. Starting from a framework before the contract.
2. Manually syncing “the same” fields in four languages.
3. Mixing v1 and v2 messages without a package strategy.
4. Ignoring deadline because “our network is fast”.
5. Thinking gRPC removes the need to log a request ID.
6. Pushing gRPC into a public mobile client without a grpc-web/proxy plan.
7. Learning only the Go dialect and wondering why the Java team generates “something different”.

## Idiomatic Go

In the Go part of the course you stay idiomatic: context as the first argument, status.Error for codes, Unimplemented embed, gen code in a separate package. In the Java/C#/Node lessons we do not impose Go style — we respect the idioms of those ecosystems, but RPC semantics stay the same.

## Practical scenario

A platform team in fintech has a Go core, Java fraud, C# backoffice, Node notifications. After two quarters of JSON haggling they introduce a shared protos/ repo, buf breaking checks, and mandatory generation in CI.

First RPC: EvaluatePayment. Go calls Java. Request ID goes through metadata. Deadline 150 ms. The fraud team no longer sends “by the way” new JSON fields — they change the proto, everyone regenerates.

Six months later onboarding a new language takes days, not weeks. That is the polyglot RPC goal in practice.

## Mechanism (deep dive): Catalog as the reference contract

```protobuf
syntax = "proto3";
package demo.v1;
option go_package = "example.com/shop/gen/demo/v1;demopb";

  rpc SayHello(HelloRequest) returns (HelloReply);
  rpc List(ListRequest) returns (stream Item);

```

In 05.x we often also practice the shorter `Inventory.GetStock` for a unary focus, but the **same** polyglot mechanism applies: one proto → Go / Java / C# / Node stubs.

### Polyglot call trace

```text
.proto (Catalog or Inventory)
  → protoc + plugin (Go / Java / C# / Node)
  → generated types + stub / server base
  → your implementation or client call
  → HTTP/2 + Protobuf on the wire
  → status code + (optionally) metadata
```

**Predict:** The Java team “quickly” adds a field only in their JSON because “proto CI is not ready yet”.  
**Answer:** A fourth truth about quantity. The polyglot goal dies without generation discipline.

## Mechanism (deep dive): JSON at the edge, gRPC in the core

```text
[Browser / mobile]
        | JSON HTTP
        v
[API Gateway / BFF] ---- gRPC ----> [Order Go]
                                      |
                                      +-- gRPC --> [Inventory Java]
                                      +-- gRPC --> [Fraud Java]
                                      +-- gRPC --> [Notify Node]
```

**Predict:** You expose a gRPC port directly to a mobile client without a bridge.  
**Answer:** TLS, auth, versions, DevTools debounce — pain. Plan a gateway or gRPC-Web deliberately.

## Mechanism (deep dive): Definition of Done for a contract change

1. PR in `protos/` (or buf registry) with a compatibility description.
2. Breaking check green (buf or equivalent).
3. Regeneration in Go **and** in languages that consume the contract.
4. Status code mapping updated if needed.
5. Changelog / ADR one sentence: why.
6. Smoke: Go server + at least one other-language client in CI.

Without 3 and 6, “shared proto” is a wiki lie.

## Mechanism (deep dive): operational cost × N runtimes

| Item | One language | Polyglot |
|------|--------------|----------|

| Debug tool | curl | + grpcurl/grpcui |
| On-call runbook | 1 | N sections or a generic RPC part |
| Deadline budgets | local | chain across languages |

## Mechanism (deep dive): four stub calls — same semantics

The same unary contract, four languages (Inventory or Catalog SayHello — pick one for the lab):

```go
// Go — prefer NewClient
conn, _ := grpc.NewClient("127.0.0.1:50051", grpc.WithTransportCredentials(insecure.NewCredentials()))
client := pb.NewInventoryClient(conn)
ctx, cancel := context.WithTimeout(context.Background(), 200*time.Millisecond)
defer cancel()
resp, err := client.GetStock(ctx, &pb.GetStockRequest{Sku: "ABC"})
```

```java
ManagedChannel ch = ManagedChannelBuilder.forAddress("127.0.0.1", 50051).usePlaintext().build();
InventoryGrpc.InventoryBlockingStub stub = InventoryGrpc.newBlockingStub(ch)
    .withDeadlineAfter(200, TimeUnit.MILLISECONDS);
GetStockResponse resp = stub.getStock(GetStockRequest.newBuilder().setSku("ABC").build());
```

```csharp
using var channel = GrpcChannel.ForAddress("http://127.0.0.1:50051");
var client = new Inventory.InventoryClient(channel);
var resp = await client.GetStockAsync(new GetStockRequest { Sku = "ABC" },
    deadline: DateTime.UtcNow.AddMilliseconds(200));
```

```javascript
const client = new pkg.Inventory('127.0.0.1:50051', grpc.credentials.createInsecure());
client.GetStock({ sku: 'ABC' }, { deadline: Date.now() + 200 }, (err, resp) => { /* ... */ });
```

**Predict:** in all four languages `sku` empty — which code?  
**Answer:** InvalidArgument (if the server maps it that way). Status semantics are part of the behavioral contract across languages.

## Mechanism (deep dive): ownership of the proto repo

Who may merge a breaking change?

1. Platform / API steward reviews.
2. CI breaking check.
3. Consumer notification (Go, Java, C#, Node packages).
4. Synchronous release or a compatibility window.

Without ownership, “shared proto” becomes shared blame.

## Mechanism (deep dive): observability from day one

```text
metric: rpc_server_handled_total{method, code, service}
metric: rpc_client_handled_total{method, code, target}
log: rid=... method=... code=... dur=...
trace: span per RPC, parent from metadata if present
```

**Predict:** You measure only “error rate” without a code label.  
**Answer:** You do not see a spike of InvalidArgument vs Unavailable. Code is a dimension.

## Mechanism (deep dive): security minimum

1. TLS between services outside the lab.  
2. Auth metadata (bearer) validated on the server interceptor/Middleware.  
3. No PII in the status message.  
4. Max message size.  
5. Reflection off or network-restricted in prod.  
6. Insecure credentials only locally.

This is not a “later chapter” — it is part of the DoD for polyglot RPC.

## Mechanism (deep dive): what is the contract and what is the stub

- **Contract**: `.proto` (service + messages + code semantics)  
- **Stub**: generated client/server API in the language  
- **Wire**: HTTP/2 + protobuf framing  

You change the stub surface per language; you do not change the wire at will. If a Node loader renames fields differently from Go generated — that is a tooling bug/mismatch, not “another protocol”.

## Mechanism (deep dive): insecure lab vs TLS direction

All 05 lessons use plaintext in the lab so polyglot can be fast. Production direction:

- TLS  
- auth (metadata token / mTLS)  
- message limit  
- mandatory deadline  

Do not copy lab credentials into a Helm chart.

## Mechanism (deep dive): status as a shared language

| Semantics | Go | Java | C# | Node |
|-----------|----|------|----|------|
| bad input | InvalidArgument | INVALID_ARGUMENT | InvalidArgument | INVALID_ARGUMENT |
| missing | NotFound | NOT_FOUND | NotFound | NOT_FOUND |
| timeout | DeadlineExceeded | DEADLINE_EXCEEDED | DeadlineExceeded | DEADLINE_EXCEEDED |
| down | Unavailable | UNAVAILABLE | Unavailable | UNAVAILABLE |

Wire status numbers are aligned — that is why metrics can be shared.
