## Problem this lesson solves

Without a shared glossary, teams mix up “connection” and “request”, treat every error as Internal, and forget deadline. Polyglot hurts extra: Java says `Status`, Go `codes`, Node `grpc.status` — same semantics, different syntax. This lesson builds a shared model before code.

## Mental model

```text
[Client process]
  channel (long-lived HTTP/2 connection)
    → stub (generated client)
         → RPC call + context (deadline) + metadata
              → [network]
                   → server dispatch
                        → your implementation
                             → response OR status
```

Interceptors are middleware for RPC (counterpart of 04.06). Catalog examples: `SayHello` (unary), `List` (server stream), `Upload` (client stream) — the concepts apply to all three shapes.

## Mechanism

### Channel (connection / ClientConn)

A long-lived HTTP/2 connection. Multiple RPCs share the same channel (multiplex).

| Language | Typical API |
|----------|-------------|
| Go | `grpc.NewClient` → `ClientConn` |
| Java | `ManagedChannelBuilder` → `ManagedChannel` |
| C# | `GrpcChannel.ForAddress` |
| Node | address + credentials when creating the client |

**Predict:** You open a new channel per RPC.  
**Answer:** Expensive, you lose multiplex. Reuse channel / conn per process (or per pool policy).

### Stub

A generated client that packages calls: `NewCatalogClient(conn)`, `InventoryGrpc.newBlockingStub(ch)`, `new Inventory.InventoryClient(channel)`.

Stub ≠ channel. The stub is a thin wrapper over the channel for a concrete service.

### Server implementation

Generated interface / base:

- Go: `CatalogServer` + embed `UnimplementedCatalogServer`
- Java: `CatalogImplBase` / `InventoryImplBase`
- C#: `CatalogBase` / `InventoryBase`
- Node: method object for `addService`

### Status

Stable behavioral codes:

| Code | Typical situation | Retry? |
|------|-------------------|--------|
| OK | success | — |
| InvalidArgument | bad input | no |
| NotFound | no resource | no |
| AlreadyExists | create conflict | no |
| PermissionDenied | authz | no |
| Unauthenticated | missing/bad auth | no (refresh token) |
| DeadlineExceeded | budget expired | maybe (idempotent) |
| Unavailable | temporarily unavailable | yes, backoff |
| Canceled | client canceled | not as a server fail |
| Internal | bug / unexpected | caution |
| Unimplemented | wrong deploy/version | no |

**Predict:** Validation `sku == ""` returns Internal.  
**Answer:** Wrong — InvalidArgument. Internal is for “this should not have happened”.

### Deadline and cancellation

The client sets the budget. The server sees the same pressure through `ctx.Done()` / `Context.CancellationToken` / deadline options.

```go
ctx, cancel := context.WithTimeout(parent, 200*time.Millisecond)
defer cancel()
resp, err := client.SayHello(ctx, &demopb.HelloRequest{Name: "Ana"})
```

```text
Deadline trace:
client WithTimeout(200ms)
  → RPC starts
  → server SayHello reads ctx
  → slow DB without ctx → client sees DeadlineExceeded
  → server may still work until it checks ctx (work leak)
```

Therefore: **pass ctx** into DB/HTTP calls.

### Metadata

Key/value pairs alongside the RPC (not the body).

Typically:

- `x-request-id` — correlation (same name across languages)
- `authorization` — bearer token

```go
md := metadata.Pairs("x-request-id", rid, "authorization", "Bearer "+tok)
ctx = metadata.NewOutgoingContext(ctx, md)
```

Header metadata goes at the start; trailer at the end. You do not put 2 MB of JSON in metadata.

### Interceptors ≈ middleware

```go
func unaryLog(
	ctx context.Context,
	req any,
	info *grpc.UnaryServerInfo,
	handler grpc.UnaryHandler,
) (any, error) {
	start := time.Now()
	resp, err := handler(ctx, req)
	log.Printf("method=%s code=%v dur=%s rid=%s",
		info.FullMethod, status.Code(err), time.Since(start), ridFrom(ctx))
	return resp, err
}
```

Same mental model as `withLogging` from 04.06: measure after the inner work.

## Rules and syntax

1. Do not swallow an error without a status code at the RPC boundary.
2. The client sets the deadline; the server respects cancellation.
3. Metadata keys — lowercase convention.
4. Do not use metadata as transport for business payload.
5. `Unavailable ≠ InvalidArgument`.
6. Idempotent retry only for safe codes/methods.
7. Document mapping to HTTP if you have a gateway.
8. One name for request id across Go/Java/C#/Node.
9. PII does not go into the `status` message string.
10. Stream RPCs share the same status/deadline/metadata concepts.

## Examples

### Example 1 — NotFound on Catalog/Inventory

```go
return nil, status.Error(codes.NotFound, "sku not found")
```

### What happens here

The client branches the UI; metrics count `code=NotFound`. Do not treat it as a 500.

### Example 2 — deadline prevents cascade

Order has 800 ms. Fraud is called with a 150 ms child budget (or the inherited remainder). A spike in fraud does not hold Order forever.

### What happens here

The budget is part of the behavioral contract, not a magic number in one file.

### Example 3 — metadata auth

An interceptor reads `authorization`, validates, puts the principal in context. The handler does not parse the header by hand.

### What happens here

Same as HTTP authz middleware — different API.

### Example 4 — Unavailable and retry

Connection refused / transient LB → `Unavailable`. Retry with jitter backoff on **idempotent** GetStock/SayHello. Not on Create without an idempotency key.

### What happens here

Retry policy lives on the client or the mesh; it must be code-aware.

### Example 5 — SayHello trace (unary)

```text
stub.SayHello(ctx, {name:Ana})
  → HTTP/2 HEADERS :path=/demo.v1.Catalog/SayHello
  → DATA protobuf HelloRequest
  → server SayHello
  → DATA HelloReply
  → trailers status=OK
```

**Predict:** empty name, server returns InvalidArgument.  
**Answer:** client `status.Code(err) == InvalidArgument`; no retry.

## Decision analysis

| Concept | Typical mistake | Better practice |
|---------|-----------------|-----------------|
| Internal for everything | no signal | exact code |
| No deadline | hang / cascade | WithTimeout / Deadline |
| PII in message | leak | generic message + log |
| Meta for body | limit/MD break | fields in the proto message |
| New channel per RPC | latency | reuse |
| Retry everything | duplicate write | retry matrix |

## Trade-offs

- Rich status codes help automation, but require team discipline.
- Metadata is convenient for correlation/auth, but is not a universal bag.
- A short deadline protects the system; it can increase `DeadlineExceeded` until you optimize the slow path.
- Interceptors centralize log/auth — an overly fat interceptor becomes a god-object.

## Common mistakes

1. `codes.Internal` for validation errors.
2. `context.Background()` on the client in a production path without a timeout.
3. Case-sensitive metadata chaos (`X-Request-Id` vs `x-request-id`).
4. Ignoring the Header vs Trailer MD difference.
5. Retry on non-idempotent Create.
6. Mixing `time.After` with context cancellation.
7. Logging the entire MD with secrets.
8. Mixing channel and stub terms in review.
9. Assuming Java `Status` and Go `codes` “are not the same”.
10. Deadline on the client, but the server ignores `ctx` in the DB call.

## Idiomatic Go

- `status.Error` / `status.Errorf` at the boundary.
- `metadata` package for MD.
- Unary/stream interceptors for cross-cutting concerns.
- `context` always the first parameter of the RPC method.
- Prefer `grpc.NewClient` for the channel (details in 05.05).

In Java/C#/Node respect local idioms; code/deadline/MD semantics stay the same.

## Practical scenario

Incident: payment hangs because the fraud RPC has no deadline. The team introduces a 150 ms timeout, a `code=DeadlineExceeded|Unavailable` metric, and degradation (skip fraud score under a flag). The next spike does not take down checkout.

Second incident: request ID disappears at the Java boundary because Go sends `X-Request-ID` and the Java interceptor reads `x-request-id` case-sensitively in custom code. They agree on **lowercase** `x-request-id` in all languages.

## Mechanism (deep dive): channel states (Go)

`ClientConn` goes Idle → Connecting → Ready → TransientFailure → Shutdown.

```text
NewClient OK
SayHello
  → connect if needed
  → Ready → RPC
  or TransientFailure → Unavailable
```

**Predict:** `NewClient` success = server up.  
**Answer:** No. Only an RPC (or `Connect`) proves availability.

## Mechanism (deep dive): status in four languages

```go
return nil, status.Error(codes.InvalidArgument, "name required")
```

```java
responseObserver.onError(
  Status.INVALID_ARGUMENT.withDescription("name required").asRuntimeException());
```

```csharp
throw new RpcException(new Status(StatusCode.InvalidArgument, "name required"));
```

```javascript
callback({ code: grpc.status.INVALID_ARGUMENT, message: 'name required' });
```

The wire code is the same. A client in another language must understand it.

## Mechanism (deep dive): deadline chain

```text
HTTP request ctx (800ms)
  → gRPC Order→Inventory (same ctx or shortened)
    → gRPC Inventory→Warehouse (same ctx)
```

If Warehouse does `Background()` + 5s — it breaks the chain. Idiom: ctx downward.

**Predict:** child timeout longer than the parent remainder.  
**Answer:** The parent will cancel earlier; the child’s “longer” timeout does not help. Account for the remainder.

## Mechanism (deep dive): metadata header vs trailer

| Type | When it arrives | Typical use |
|------|-----------------|-------------|
| Header MD | before body | auth, request id, routing |
| Trailer MD | after body | server stats, debug token |

A client that reads the trailer before the end of the RPC is wrong. Unary: usually header out + optional trailer in.

## Mechanism (deep dive): retry matrix

| Code | GetStock / SayHello | CreateOrder |
|------|---------------------|-------------|
| Unavailable | retry + backoff | only with idempotency key |
| DeadlineExceeded | measure; maybe larger budget | not blindly |
| InvalidArgument | no | no |
| NotFound | no | no |
| Internal | limited / alert | caution |

Without a matrix, “retry middleware” creates duplicate charges.

## Mechanism (deep dive): HTTP map (gateway)

| gRPC | HTTP (approximate) |
|------|--------------------|
| InvalidArgument | 400 |
| Unauthenticated | 401 |
| PermissionDenied | 403 |
| NotFound | 404 |
| AlreadyExists | 409 |
| DeadlineExceeded | 504 |
| Unavailable | 503 |
| Internal | 500 |

Document deviations. Do not expect a perfect 1:1 automatic mapping.

## Mechanism (deep dive): stream and the same glossary

```text
List (server stream):
  client sends ListRequest once
  server sends N × Item
  status at the end (trailer)

Upload (client stream):
  client sends N × Chunk
  server returns UploadSummary + status
```

Deadline applies to the **whole** stream. Metadata is still at the start. Status is still at the end. Catalog 03.04 deepens the API; here remember that the concepts are not only unary.

## Predict-then-check

**A.** Server ignores ctx, does Sleep(5s), client timeout 100ms.  
**Answer:** Client DeadlineExceeded; server still burns CPU until it checks ctx.

**B.** Retry on AlreadyExists.  
**Answer:** Usually pointless; the resource is already there.

**C.** Auth token in a proto field instead of metadata.  
**Answer:** Possible, but mixes a transport concern with the domain message; metadata + interceptor is the more common pattern.

**D.** Log the `authorization` MD value.  
**Answer:** Secret leak. Log only presence / subject.

**E.** Two teams: one Internal for “no sku”, the other NotFound.  
**Answer:** Clients and dashboards lie. The code contract must be agreed.

**F.** Node callback without `code`, only a string.  
**Answer:** You lose branching. Use `grpc.status.*`.

## Scenario (extended): fraud 150 ms

## Summary

- Channel, stub, status, deadline, metadata = the basic glossary of polyglot RPC.

## Mechanism (deep dive): interceptor order

Like an HTTP chain:

```text
recover → logging/metrics → auth → handler
```

Auth inside sees rid if logging/auth setup set it earlier. Document the order. In Java `ServerInterceptors.intercept`, in C# middleware pipeline, in Node less standardized — but semantics are the same.

## Mechanism (deep dive): an error that is not status

If the client locally does `errors.New("bad")` before the call, that is not a gRPC code. Distinguish:

1. local validation before RPC,
2. transport/RPC error with a code,
3. success with a business “soft fail” in the message (avoid — prefer status).

## Mechanism (deep dive): message size

`MaxRecvMsgSize` / `MaxSendMsgSize` on the server and symmetric options on the client protect against huge messages. An Upload stream of chunks is often better than one giant unary.

## Glossary

| Term | Meaning |
|------|---------|
| channel | long-lived connection |
| stub | generated client API |
| status/code | typed RPC outcome |
| deadline | until when the RPC may run |
| metadata | MD pairs alongside the call |

| unary | one req / one resp |

## Mechanism (deep dive): status as contract — ADR template

```text
# ADR: gRPC status mapping for Inventory
## Codes we emit
- InvalidArgument: empty/malformed sku
- NotFound: sku missing in store
- Unavailable: dependency down (rare; prefer degrade)
- Internal: unexpected
## Codes we never emit for validation
- Internal for empty sku (forbidden)
## Client retry
- Unavailable: max 2 with jitter on GetStock
- others: no
```

## Mechanism (deep dive): the glossary that carries the whole polyglot story

Without a shared glossary, Java “Status” and Go “codes” look like different worlds. They are not — they map the same wire.

### Channel / connection

A long-lived object to a destination (Go `ClientConn`, Java `ManagedChannel`, C# `GrpcChannel`, Node client). Stubs are built cheaply on top of it.

### Stub — continued

Generated proxy: looks like a local call, does RPC. Does not hold business logic.

### Deadline / timeout

Time budget of the RPC. Go: `context`. Java: `withDeadlineAfter`. C#: `Deadline`/`CancellationToken`. Node: `deadline` Date.

### Metadata — continued

Key-value beside the protobuf body (request id, auth). Not for large payload.

### Status code

Machine outcome of the RPC. More stable than the message string.

### Streaming

Multiple messages on one HTTP/2 stream (List/Upload/bidi).

## Mechanism (deep dive): method path

```text
/demo.v1.Catalog/SayHello
/demo.v1.Catalog/List
/demo.v1.Catalog/Upload
```

grpcurl and all languages hit the same path. Package + service + method must be identical in the proto.

## Mechanism (deep dive): unary vs stream decision

```text
1 object, small → SayHello-style unary
sequence of results → List server-stream
upload of parts → Upload client-stream
both directions live → bidi (later as needed)
```

## Mechanism (deep dive): errors and retry policy (concept)

| Code | Retry? |
|------|--------|
| InvalidArgument | no |
| NotFound | no |
| PermissionDenied | no |
| Unavailable | yes, bounded |
| DeadlineExceeded | rarely; more often fix the budget |
| ResourceExhausted | backoff |

Service config retry exists in Go — for the course first an explicit matrix in code/BFF.

## Mechanism (deep dive): interceptors / middleware

A shared place for log, auth, metrics. Not for business rules sku/price. Order: auth → logging → handler.

## Mechanism (deep dive): from concept to ADR — status catalog

Write one page:

```text
Codes we emit:
  InvalidArgument, NotFound, Unauthenticated, PermissionDenied,
  FailedPrecondition, Unavailable, DeadlineExceeded, ResourceExhausted

Codes we never emit for validation:
  Internal (that is not validation)
  Unknown (that is not “I do not know what”)

Client retry:
  Unavailable: yes, bounded
  DeadlineExceeded: usually no automatic flood
  InvalidArgument/NotFound: never
```

This is a Mechanism of agreement, not documentation for documentation’s sake.
