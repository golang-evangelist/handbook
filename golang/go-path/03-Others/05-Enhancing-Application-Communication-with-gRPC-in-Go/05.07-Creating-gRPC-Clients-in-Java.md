# 05.07 Creating gRPC Clients in Java

> **Go Path - Zero to Gopher** / **03 Others → Enhancing Application Communication with gRPC in Go** / Lesson 05.07

## Lesson goals

After this lesson you should be able to:

- open a `ManagedChannel`
- create a **blocking stub** (and know that an async stub exists)
- set a deadline
- read `StatusRuntimeException`
- compare with Go `NewClient` + stub

## Prerequisite

- 05.06 Java server or Go server on the same proto
- Java 17+

## Problem this lesson solves

Java clients often mix blocking and async stubs, forget to `shutdown` the channel, and swallow `StatusRuntimeException` as an ordinary error without a code.

## Mental model

```text
ManagedChannelBuilder.forAddress(host, port).usePlaintext().build()
  → InventoryGrpc.newBlockingStub(channel)
       → withDeadlineAfter(...)
            → getStock(request)
                 → response OR StatusRuntimeException
  → channel.shutdown()
```

Go counterpart: `grpc.NewClient` → `NewInventoryClient` → `WithTimeout` → RPC.

## Mechanism

### Blocking stub (course focus)

```java
ManagedChannel channel = ManagedChannelBuilder
    .forAddress("127.0.0.1", 50051)
    .usePlaintext() // lab only
    .build();

InventoryGrpc.InventoryBlockingStub stub = InventoryGrpc.newBlockingStub(channel)
    .withDeadlineAfter(200, TimeUnit.MILLISECONDS)
    .withInterceptors(MetadataUtils.newAttachHeadersInterceptor(md));

try {
  GetStockResponse resp = stub.getStock(
      GetStockRequest.newBuilder().setSku("A").build());
  System.out.println(resp.getQuantity());
} catch (StatusRuntimeException e) {
  System.out.println(e.getStatus().getCode());
} finally {
  channel.shutdownNow();
}
```

### Catalog SayHello

```java
CatalogGrpc.CatalogBlockingStub stub = CatalogGrpc.newBlockingStub(channel)
    .withDeadlineAfter(800, TimeUnit.MILLISECONDS);
HelloReply reply = stub.sayHello(HelloRequest.newBuilder().setName("Ana").build());
```

### Trace

```text
ManagedChannel
blockingStub.getStock
  → HTTP/2
  → response
  or StatusRuntimeException(code)
```

**Predict:** `usePlaintext` in production.  
**Answer:** no — TLS. Lab only.

**Predict:** a new channel per HTTP request in a gateway.  
**Answer:** anti-pattern like Go Dial per request. Reuse the channel.

### Metadata

```java
Metadata md = new Metadata();
md.put(Metadata.Key.of("x-request-id", Metadata.ASCII_STRING_MARSHALLER), rid);
stub = stub.withInterceptors(MetadataUtils.newAttachHeadersInterceptor(md));
```

## Rules and syntax

1. Blocking stub for a simple synchronous lab and many service-to-service calls.  
2. Deadline via `withDeadlineAfter` or Context.  
3. Catch `StatusRuntimeException`, read `getStatus().getCode()`.  
4. `usePlaintext` lab only.  
5. Reuse `ManagedChannel`.  
6. `shutdown` / `shutdownNow` on shutdown.  
7. Same proto as the server.  
8. Do not mix the async stub API “along the way” without understanding.  
9. Agreed request id name (`x-request-id`).  
10. Map code to a domain error.

## Examples

### Example 1 — NOT_FOUND

```java
catch (StatusRuntimeException e) {
  if (e.getStatus().getCode() == Status.Code.NOT_FOUND) {
    // UX
  }
}
```

#### What happens here

A blocking stub reports a failed RPC by throwing `StatusRuntimeException`. The `catch` reads `getStatus().getCode()` and compares it with `Status.Code.NOT_FOUND`, the missing-sku code. That branch is where the client applies not-found UX. The same code is what a Go server sends as `codes.NotFound`.

## Decision analysis

| Stub | When |
|------|------|
| blocking | simple sync call |
| async | non-blocking client, stream |
| future stub | ListenableFuture style |

## Trade-offs

A blocking stub blocks a thread — with virtual threads / a separate pool OK for many services; in a tight event loop choose async. Channel reuse requires lifecycle management.

## Mechanism (deep dive): ManagedChannel lifecycle — trace from creation to shutdown

A Java client lives or dies with `ManagedChannel`. If you treat it like `HttpURLConnection` (open–call–discard), you pay handshake, DNS, and thread pool setup on every RPC. The correct model is the same as Go `ClientConn`: one long-lived channel per process (or per logical destination), stubs are cheap.

### Trace: successful blocking SayHello to a Go server

```text
1. ManagedChannelBuilder.forAddress("127.0.0.1", 50051).usePlaintext().build()
2. CatalogGrpc.newBlockingStub(channel)
3. stub.withDeadlineAfter(800, MILLISECONDS).sayHello(HelloRequest{name=Ana})
4. HTTP/2 HEADERS :path=/demo.v1.Catalog/SayHello
5. DATA frame = protobuf HelloRequest
6. server Go handler → HelloReply
7. DATA + trailers grpc-status:0
8. blocking stub returns HelloReply (no throw)
9. process shutdown → channel.shutdown() → awaitTermination
```

### Trace: INVALID_ARGUMENT

```text
sayHello(name="")
  → Go server status.Error(codes.InvalidArgument, "name required")
  → trailers grpc-status:3
  → StatusRuntimeException
  → e.getStatus().getCode() == INVALID_ARGUMENT
  → do NOT retry; fix the request or UI validation
```

### Trace: DEADLINE_EXCEEDED

```text
withDeadlineAfter(50, MILLISECONDS)
  → server Sleep(200ms) in SayHello
  → client cancels
  → StatusRuntimeException DEADLINE_EXCEEDED
  → server ctx.Done() (if it checks ctx)
```

**Predict:** you forget `withDeadlineAfter` on the blocking stub.  
**Answer:** the call can hang as long as the channel lives; a parent timeout from an HTTP BFF does not automatically reach gRPC if you did not connect them.

**Predict:** you catch only `Exception` and log `e.getMessage()`.  
**Answer:** you lose a stable `Status.Code` for metrics and retry policy.

## Mechanism (deep dive): same .proto — different stub, same wire

Catalog contract (illustration — do not pretend the whole build works without a generate step):

```protobuf
syntax = "proto3";
package demo.v1;
option java_package = "com.example.demo.v1";
option java_multiple_files = true;

service Catalog {
  rpc SayHello(HelloRequest) returns (HelloReply);
  rpc List(ListRequest) returns (stream Item);
  rpc Upload(stream UploadChunk) returns (UploadSummary);
}
message HelloRequest { string name = 1; }
message HelloReply { string message = 1; }
message ListRequest { int32 page_size = 1; }
message Item { string id = 1; string title = 2; }
message UploadChunk { bytes data = 1; }
message UploadSummary { int64 bytes = 1; }
```

After `protoc` + Java plugin you get `CatalogGrpc` with:

- `newBlockingStub` — synchronous unary / client-stream helpers
- `newStub` — async `StreamObserver`
- `newFutureStub` — `ListenableFuture` (rarer in new code)

The wire on the network is the same as a Go stub: HTTP/2 + protobuf. The Go server does not know the client is Java.

### Blocking vs async — when which

| Style | When | Risk |
|-------|------|------|
| blocking stub | simple BFF, virtual threads, script | blocks an OS thread without virtual threads |
| async stub | high concurrency on platform threads | callback hell / forgotten `onError` |
| future stub | Guava/CompletableFuture integration | mixing error models |

The course keeps the **blocking stub** because you are reading Go unary style `(resp, error)` in parallel.

## Mechanism (deep dive): List server-stream on the Java client

```java
Iterator<Item> it = stub
    .withDeadlineAfter(5, TimeUnit.SECONDS)
    .list(ListRequest.newBuilder().setPageSize(10).build());
while (it.hasNext()) {
  Item item = it.next();
  // process item
}
```

Trace:

```text
list()
  → HTTP/2 stream opened
  → server sends N DATA (Item)
  → iterator.hasNext() reads
  → trailers OK or status error at the end
```

**Predict:** you treat the stream as unary and expect one object.  
**Answer:** you get an iterator; an error can arrive after several successful `Item`s.

**Predict:** no deadline on a long List.  
**Answer:** a slow server or network keeps the thread busy.

## Mechanism (deep dive): Upload client-stream (sketch)

```java
StreamObserver<UploadChunk> reqObs = asyncStub.upload(new StreamObserver<UploadSummary>() {
  public void onNext(UploadSummary v) { /* summary */ }
  public void onError(Throwable t) { /* status */ }
  public void onCompleted() { }
});
reqObs.onNext(UploadChunk.newBuilder().setData(chunk).build());
reqObs.onCompleted(); // mandatory CloseSend counterpart
```

Without `onCompleted` on the request observer the server often waits forever — same as a Go client that forgets `CloseSend`.

## Mechanism (deep dive): code → action (Java)

| Status.Code | Client action |
|-------------|----------------|
| OK | map into domain |
| INVALID_ARGUMENT | do not retry; validation |
| NOT_FOUND | do not retry; domain exception |
| UNAUTHENTICATED | refresh token |
| PERMISSION_DENIED | do not retry; audit |
| UNAVAILABLE | limited retry + backoff |
| DEADLINE_EXCEEDED | metric; no blind retry loops |
| CANCELLED | parent canceled |
| RESOURCE_EXHAUSTED | backoff / reduce rate |
| UNIMPLEMENTED | deploy bug / wrong server |

```java
try {
  return stub.getStock(req);
} catch (StatusRuntimeException e) {
  switch (e.getStatus().getCode()) {
    case NOT_FOUND -> throw new SkuNotFoundException();
    case INVALID_ARGUMENT -> throw new BadRequestException(e.getStatus().getDescription());
    case UNAVAILABLE -> throw new UpstreamUnavailableException(e);
    default -> throw e;
  }
}
```

```java
ManagedChannel ch = ManagedChannelBuilder.forAddress(host, port)
```

**Answer:** handshake fail / UNAVAILABLE — not a “silent” JSON 404.

**Answer:** same class of error; align the lab profile.

## Mechanism (deep dive): comparison with Go NewClient

| Concept | Go | Java |
|---------|----|------|
| Channel | `grpc.NewClient` → `ClientConn` | `ManagedChannelBuilder` → `ManagedChannel` |
| Stub | `NewCatalogClient(conn)` | `CatalogGrpc.newBlockingStub(ch)` |
| Timeout | `context.WithTimeout` | `stub.withDeadlineAfter` |
| Error | `status.FromError` | `StatusRuntimeException` |
| Close | `conn.Close()` | `channel.shutdown()` |
| Lab plaintext | `insecure.NewCredentials()` | `usePlaintext()` |

Same `.proto` → different generated types → **same** HTTP/2 + protobuf wire. That is why polyglot works.

## Mechanism (deep dive): BFF pattern — HTTP in, gRPC out

```text
Browser → Spring MVC / HttpServer
  → request id + auth
  → blocking stub SayHello / GetStock
  → map Status.Code → HTTP status
  → JSON response
```

Mapping (rough, document in an ADR):

| gRPC code | HTTP |
|-----------|------|
| OK | 200 |
| INVALID_ARGUMENT | 400 |
| NOT_FOUND | 404 |
| UNAUTHENTICATED | 401 |
| PERMISSION_DENIED | 403 |
| DEADLINE_EXCEEDED | 504 |
| UNAVAILABLE | 503 |

Do not turn everything into 500. Do not return a raw `grpc-status` string to the user without a filter.

## Mechanism (deep dive): keep-alive and idle LB (operations)

A load balancer often cuts idle HTTP/2. Symptom: first RPC after a pause → `UNAVAILABLE`, then success on retry. Options:

- configure keepalive on the channel (measure first; aggressive ping costs)
- align idle timeout on the LB with the client
- application health RPC instead of blind keep-alive if the platform requires it

**Predict:** “I will fix UNAVAILABLE with infinite retry without jitter”.  
**Answer:** thundering herd on server restart.

## Mechanism (deep dive): message size

The default message limit (often 4 MiB) also applies on the client. Large `Upload` chunks or fat `Item`s break with `RESOURCE_EXHAUSTED` / related. Solution: stream chunks, not one giant unary.

```text
Upload 20MB as one unary UploadRequest
  → likely fail on the limit
Upload as stream UploadChunk 64KB
  → OK with the same proto contract
```

## Mechanism (deep dive): Java client in a BFF — mapping and shutdown

```java
ManagedChannel channel = ManagedChannelBuilder.forAddress(host, port)
    .usePlaintext() // LAB
    .build();
CatalogGrpc.CatalogBlockingStub stub = CatalogGrpc.newBlockingStub(channel);

  channel.shutdown();
```
