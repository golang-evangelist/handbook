# 05.03 Preparing for gRPC

> **Go Path - Zero to Gopher** / **03 Others → Enhancing Application Communication with gRPC in Go** / Lesson 05.03

## Lesson goals

After this lesson you should be able to:

- install `protoc`
- add the Go plugins `protoc-gen-go` and `protoc-gen-go-grpc`
- pin versions in CI
- generate code from `.proto`
- organize `go_package` and module path
- prepare the same proto for Java/C#/Node generate in later lessons

## Prerequisite

- 05.02
- Go modules
- permission to install CLI tools
- Catalog or Inventory `.proto` sketch

## Problem this lesson solves

The most common fail: mixed `protoc` and plugin versions, wrong `go_package`, gen files committed sometimes yes / sometimes no, Windows PATH without `GOPATH/bin`. Without reproducible tooling, polyglot CI lies.

## Mental model

```text
.proto
  → protoc
      → protoc-gen-go        → *.pb.go (messages)
      → protoc-gen-go-grpc   → *_grpc.pb.go (service/stub)
  → your module imports the gen package
```

The same `.proto` later feeds Java (`protobuf-gradle-plugin`), C# (Grpc.Tools), Node (loader or `grpc_tools_node_protoc`). One source of truth.

## Mechanism

### Installing Go plugins

```bash
go install google.golang.org/protobuf/cmd/protoc-gen-go@v1.34.2
go install google.golang.org/grpc/cmd/protoc-gen-go-grpc@v1.5.1
```

Pin versions — `@latest` only for a personal experiment. `protoc` must be on `PATH` (system package, GitHub release, or asdf/devcontainer).

Check:

```bash
protoc --version
which protoc-gen-go
which protoc-gen-go-grpc
```

### Generation (Go)

```bash
protoc -I api \
  --go_out=. --go_opt=module=example.com/shop \
  --go-grpc_out=. --go-grpc_opt=module=example.com/shop \
  api/demo/v1/catalog.proto
```

### go_package

```protobuf
option go_package = "example.com/shop/gen/demo/v1;demopb";
```

Left: import path. Right: package clause name. Must align with the `go.mod` module and `go_opt=module=...`.

### Catalog proto for the generate lab

```protobuf
syntax = "proto3";
package demo.v1;
option go_package = "example.com/shop/gen/demo/v1;demopb";

service Catalog {
  rpc SayHello(HelloRequest) returns (HelloReply);
  rpc List(ListRequest) returns (stream Item);
  rpc Upload(stream Chunk) returns (UploadSummary);
}

message HelloRequest { string name = 1; }
message HelloReply { string message = 1; }
message ListRequest { string prefix = 1; }
message Item { string id = 1; string name = 2; }
message Chunk { bytes data = 1; }
message UploadSummary { int32 chunks = 1; int64 bytes = 2; }
```

For a shorter unary lab you can also keep `inventory.v1.Inventory/GetStock` in parallel — the generate flow is identical.

### Makefile / script — the only official way

```make
.PHONY: generate
generate:
	protoc -I api \
	  --go_out=. --go_opt=module=example.com/shop \
	  --go-grpc_out=. --go-grpc_opt=module=example.com/shop \
	  api/demo/v1/catalog.proto
```

**Predict:** Everyone types a different `protoc` line in the docs.  
**Answer:** Path divergence. One target in CI and locally.

## Rules and syntax

1. Pin plugin and `protoc` versions in CI.  
2. Do not edit gen files by hand.  
3. One consistent module path.  
4. `-I` include path explicitly.  
5. Script/`Makefile` is the only official generate.  
6. Check breaking changes with a tool (`buf breaking` or equivalent).  
7. Document versions in the README Development section.  
8. Do not mix the old `github.com/golang/protobuf` API with the new `google.golang.org/protobuf` without migration.  
9. The same proto file for all languages — no “Java fork”.  
10. Windows: add `$(go env GOPATH)\bin` to PATH.

## Examples

### Example 1 — plugin not found

```text
protoc-gen-go: program not found or is not executable
```

### What happens here

`PATH` does not see `GOPATH/bin`. Fix PATH; do not “install again blindly”.

### Example 2 — wrong module opt

Files land in a weird folder like `example.com/shop/example.com/shop/...`.

### What happens here

`go_opt=module` must match `go.mod` exactly.

### Example 3 — messages only, no service

You run only `--go_out` without `--go-grpc_out`.

### What happens here

You have types, you do not have `RegisterCatalogServer` / `NewCatalogClient`. Add the go-grpc plugin.

### Example 4 — CI cache

Cache `protoc` and plugin binaries with a hash of the pinned versions.

### What happens here

Faster pipeline, reproducible build.

### Example 5 — buf generate (optional)

Larger monorepos often use `buf.gen.yaml`. Same idea: declarative generate, pin, breaking check. The course does not force buf, but recommends it when the script outgrows itself.

## Decision analysis

| Approach | When |
|----------|------|
| Commit gen code | simple clone, small team |
| Gen only in CI | smaller diff, stricter CI |
| buf generate | larger mono-repo, more languages |
| Devcontainer with pinned tools | onboarding / Windows pain |

## Trade-offs

- Committed gen code eases the start, but creates noisy diffs.  
- CI-only requires every developer to be able to generate locally for debug.  
- `@latest` is comfortable and dangerous.  
- One huge proto vs several small ones — generate time and review pain.

## Common mistakes

1. `latest` without a pin in production CI.  
2. Mixing old `golang/protobuf` and the new runtime.  
3. Generating from the wrong working directory.  
4. Forgotten go-grpc plugin.  
5. Forgotten Windows PATH.  
6. Different `protoc` on the laptop and in CI.  
7. Hand edit of `.pb.go` “just a little”.  
8. Wrong `go_package` leading slash / trailing inconsistency.  
9. Generate into `vendor/` by accident.  
10. Two generate scripts (Java and Go) with different proto paths.

## Idiomatic Go

- `go.mod` requirements for `google.golang.org/grpc` and `google.golang.org/protobuf` aligned with the plugin.  
- Gen code in `gen/` or `api/` separated from `internal/` domain.  
- README: exact versions + `make generate`.  
- CI job: `make generate && git diff --exit-code` if you commit gen.

## Practical scenario

A new member cannot build because they lack `protoc`. The team adds a devcontainer with exact versions. Onboarding drops from half a day to 20 minutes. Second incident: laptop `protoc` 3.x, CI 24.x — tiny differences in generated comments create false diffs. Pinning equalizes them.

## Mechanism (deep dive): successful generate trace

```text
catalog.proto
  → protoc parses
  → calls protoc-gen-go (plugin protocol)
  → writes gen/demo/v1/catalog.pb.go
  → calls protoc-gen-go-grpc
  → writes gen/demo/v1/catalog_grpc.pb.go
  → go build ./...
```

**Predict:** You change a field in the proto, do not regenerate, build still passes.  
**Answer:** Yes, until you reference the new field — then runtime/CI lag. Always regenerate after a proto change.

## Mechanism (deep dive): repo layout

```text

cmd/catalog-grpc/main.go
Makefile
```

Proto lives outside `internal` so other languages / modules can copy or submodule it.

## Mechanism (deep dive): pin in CI (sketch)

```yaml
env:
  PROTOC_VERSION: "27.1"
  GEN_GO: "v1.34.2"
  GEN_GO_GRPC: "v1.5.1"
steps:
  - name: install tools
    run: |
      # install protoc $PROTOC_VERSION
      go install google.golang.org/protobuf/cmd/protoc-gen-go@${GEN_GO}
      go install google.golang.org/grpc/cmd/protoc-gen-go-grpc@${GEN_GO_GRPC}
  - run: make generate
  - run: git diff --exit-code
```

Versions in the example are **illustrative** — check current compatible pins for your stack (uncertainty: exact semver combinations change; pin what the team agrees).

## Mechanism (deep dive): breaking check

```text
buf breaking --against '.git#branch=main'
```

Or manual discipline: do not change field numbers; do not reuse a number; package.v2 for a break. Tool > wiki.

**Predict:** renumber `name = 1` to `name = 3`.  
**Answer:** Wire break with old clients. Breaking check should go red.

## Predict-then-check

**A.** `go_package` without module alignment.  
**Answer:** Weird output tree / import fail.

**B.** Commit gen + local regenerate with another plugin version.  
**Answer:** Noisy diff in CI. Pin.

**C.** Proto in `internal/proto` and the Java team has no access.  
**Answer:** Bad ownership. Keep the contract shareable (`api/` or a separate repo).

**D.** Generate only on the PR author’s laptop.  
**Answer:** CI must verify.

**E.** Two `catalog.proto` files — one “for Go” one “for Node”.  
**Answer:** Polyglot dies. One file.

## Mechanism (deep dive): tooling lab — step by step with traces

### Step A — pin file

Create `TOOL_VERSIONS.md`:

```text
protoc: 27.x (pin exact)
protoc-gen-go: v1.34.x
protoc-gen-go-grpc: v1.5.x
go: 1.22+
```

**Predict:** Without this file, a new member installs latest.  
**Answer:** Diff chaos the next day.

### Step B — first generate

```bash
make generate
ls gen/demo/v1/
# catalog.pb.go catalog_grpc.pb.go
```

Success trace: both files exist, `go build ./...` is clean.

### Step C — deliberate go_package break

Change the module path on purpose, regenerate, read where files land. Revert. This exercise saves hours later.

### Step D — CI diff gate

```text
make generate
git diff --exit-code
```

If someone forgets to regenerate after a proto change — CI goes red.

### Step E — Java/C#/Node path preparation

```text
api/demo/v1/catalog.proto  ← only source
java/ ... generate in 05.06
csharp/ ... 05.08
node/ ... 05.10
```

Do not copy the proto into three folders without a sync strategy. Better: one path, include from other builds.

### Step F — breaking check story

Scenarios the tool should catch:

1. renumber field  
2. delete field without reserve  
3. change field type  
4. rename package without v2

### Step G — Windows PATH checklist

```text
[ ] protoc on PATH
[ ] go env GOPATH
[ ] %GOPATH%\bin on PATH
[ ] protoc-gen-go -h works
[ ] protoc-gen-go-grpc -h works
```

### Step H — commit gen vs not

| Team | Choice | Gate |
|------|--------|------|
| small | commit gen | CI diff = regenerate == committed |
| large | CI-only artifact | cache pinned tools |

Document the choice in README — do not mix.

### Step I — inventory vs catalog generate

Both protos can live in `api/`. One `make generate` walks all `api/**/*.proto` or an explicit list. An explicit list is clearer at the start.

### Step J — verifying grpc.pb.go contents

Open and find:

- `RegisterCatalogServer`  
- `NewCatalogClient`  
- `Catalog_SayHello_FullMethodName` or equivalent

If there is no Register — you did not run the go-grpc plugin.

## Mechanism (deep dive): generate errors and fixes

| Symptom | Cause | Fix |
|---------|-------|-----|
| plugin not found | PATH | add GOPATH/bin |
| undefined Register | no grpc out | add --go-grpc_out |
| import cycle | gen in wrong package | fix go_package |
| huge nested dirs | module opt | align with go.mod |
| noisy diffs | different versions | pin |

## Mechanism (deep dive): tooling lab — from proto to gen/ with a trace

The goal of 05.03 is reproducible generate: same machine, same plugin pin, same hash in `gen/`.

### Successful generate trace (Go)

```text

2. pin protoc + protoc-gen-go + protoc-gen-go-grpc versions
3. protoc --go_out --go-grpc_out
4. gen/demo/v1/*.pb.go + *_grpc.pb.go
```

**Predict:** Everyone locally has a different plugin minor version.  
**Answer:** Noise in the diff; pin in CI and in README.

**Predict:** You commit gen/ once, then regenerate locally “when you get around to it”.  
**Answer:** Drift; either always CI generate, or always committed gen with proto — pick a policy and keep it.

## Mechanism (deep dive): go_package and java_package

```protobuf
option go_package = "example.com/shop/gen/demo/v1;demopb";
option java_package = "com.example.demo.v1";
option java_multiple_files = true;
option csharp_namespace = "Demo.V1";
```

Without these options generate “works”, but import paths and namespaces become chaos in polyglot CI.

## Mechanism (deep dive): breaking check intuition

Breaking = removing a field, changing a type, renumbering a tag, deleting an RPC.  
Non-breaking = new optional field, new RPC method (with Unimplemented discipline).

In CI: `buf breaking` or equivalent — at least a manual checklist until you introduce a tool.

## Mechanism (deep dive): tooling — final pin and breaking ritual

### Pin ritual (team)

```text
1. write down protoc version
2. write down protoc-gen-go / go-grpc
3. write down Java/C#/Node plugin versions
4. CI uses the same numbers
5. CHANGELOG when you bump a plugin
```

### Breaking ritual

```text
proposed proto change
  → checklist: tag, type, deleted field, deleted RPC?
  → if breaking: major / new package v2
  → generate + cross-language clients
  → only then merge
```

### Predict final

**E.** Bump the plugin “because newest”.  
**Answer:** Noise in gen diff without benefit.

**F.** Hand edit of a generated file.  
**Answer:** Next gen overwrites; forbid it.
