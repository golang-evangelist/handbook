# 09.02 Configuring Ports and Environment Variables

> **Go Path - Zero to Gopher** / **03 Others → Docker for Software Development: Go Apps** / Lesson 09.02

## Lesson goals

After this lesson you should be able to:

- distinguish three concepts: **listen** in the process, **EXPOSE** in the Dockerfile, and **publish** (`-p` / Compose `ports:`)
- prove why `EXPOSE` does **not** open a port on the host
- configure a Go application via env variables in 12-factor style (`os.Getenv`, one `Load()` function, fail fast)
- separate what belongs in the image (binary, non-secret default) from runtime config (env, secrets)
- connect Compose `environment` / `env_file` with the same key contract that Go reads
- avoid hardcoded secrets in Dockerfile `ENV` and build `ARG`
- understand why listening on `127.0.0.1` inside the container breaks publish from the host

## Prerequisite

- Lesson 09.01 (multi-stage Dockerfile, runtime stage, `EXPOSE` as documentation in the image)
- Basic HTTP server in Go (`net/http`, `ListenAndServe`)
- Compose basics (services, network, `ports`)
- Understanding that a container is an isolated network namespace relative to the host

## Problem this lesson solves

Three mistakes repeat in the same PR:

1. A developer adds `EXPOSE 8080` and expects `curl localhost:8080` from the laptop to work without `-p` — it does not.
2. The application does `ListenAndServe("127.0.0.1:8080", ...)` “works locally”; in the container `docker exec` curl to localhost works, and from the host through `-p` you get connection refused — confusing until you check the listen address.
3. Staging DSN and API key baked into the image via `ENV` or a config file in `COPY` — every environment needs a new build; the secret ends up in registry history.

12-factor principle: **configuration in the environment**, code in the image. The port the process listens on, the port the Dockerfile documents (`EXPOSE`), and the port the host maps (publish) are not the same thing. This lesson connects the Docker network chain with idiomatic Go env reading.

## Mental model

Chain from laptop to handler:

```text
Host :18080
   │
   │  publish: docker run -p 18080:8080
   │           Compose ports: "18080:8080"
   ▼
Container namespace :8080
   │
   │  EXPOSE 8080  ← metadata / documentation only
   │
   ▼
Process Listen(":8080") or ("0.0.0.0:8080")
   │
   ▼
http.Handler
```

Three questions you always separate:

| Question | The answer lives in |
|---------|----------------|
| Where does the process bind? | Go code + env (`ADDR` / `PORT`) |
| Which port does the image “announce”? | `EXPOSE` |
| Which port does the host see? | `-p` / `ports:` |

Env chain:

```text
Compose environment / env_file / kubectl env / docker -e
   → process environment
   → os.Getenv("DATABASE_URL")
   → config.Load() validation
   → server start or fatal
```

Secrets do not go into an image layer. Defaults for non-secrets (`ADDR=:8080`, `LOG_LEVEL=info`) may go in `ENV` as default values that runtime overrides.

### Predict then answer (chain)

**Question.** The Dockerfile has `EXPOSE 8080`. You run `docker run --rm app:dev` **without** `-p`. Does `curl localhost:8080/healthz` from the host work?

**Predict**, then read.

**Answer.** No (unless something else is already listening on 8080 on the host — that is not your container). `EXPOSE` does not publish. Without `-p` / `-P` the host has no mapping to the container.

## Mechanism

### 1. EXPOSE — what it is and what it is not

```dockerfile
EXPOSE 8080
```

or

```dockerfile
EXPOSE 8080/tcp
```

Mechanism:

```text
docker build
  → EXPOSE writes metadata into the image config
docker run without -p
  → the port is NOT mapped to the host
docker run -P
  → the daemon can map exposed ports to random host ports
docker run -p 18080:8080
  → explicit mapping; EXPOSE is not a requirement for -p, but documents intent
```

`EXPOSE` does **not**:

- open a firewall
- bind the process
- replace `Listen` in Go
- make the port available to other containers by itself (that needs a shared network + listen)

`EXPOSE` **does**:

- document the contract for people and tools
- enable a meaningful `-P`
- appear in `docker inspect` under `Config.ExposedPorts`

#### Trace inspect

```bash
docker image inspect app:dev --format '{{json .Config.ExposedPorts}}'
```

Expected (conceptual):

```text
{"8080/tcp":{}}
```

That is not proof the port is published on the host — only that the image announces 8080/tcp.

#### Predict then answer — EXPOSE vs -p

**Scenario.** `EXPOSE 3000`, and the process listens on `:8080`. `docker run -p 18080:8080 app`.

**Question.** Does healthz work from `localhost:18080`?

**Answer.** Yes, if the process actually listens on 8080. `EXPOSE 3000` is only wrong documentation; `-p` maps host 18080 → container 8080. Tools that trust only `EXPOSE` will be confused — so keep `EXPOSE` aligned with the real listen port.

### 2. Publish: -p and Compose ports

```bash
docker run --rm -p 18080:8080 -e ADDR=:8080 app:dev
curl -s localhost:18080/healthz
```

`-p` syntax:

```text
-p <hostPort>:<containerPort>
-p 8080:8080
-p 127.0.0.1:8080:8080   # loopback only on the host
```

Compose:

```yaml
services:
  api:
    image: inventory:dev
    ports:
      - "18080:8080"
```

Traffic trace:

```text
curl host:18080
  → iptables/userland proxy (depends on Docker setup)
  → container eth0:8080
  → if the process listens on 0.0.0.0:8080 → handler
  → if the process listens on 127.0.0.1:8080 → refused from the publish path
```

Inside the Compose network another service does not use the host publish port — it uses the **service name** and **container port**:

```text
http://api:8080/healthz
```

not `http://api:18080`.

### 3. Listen address in the Go process

```go
http.ListenAndServe(":8080", mux)           // OK in a container
http.ListenAndServe("0.0.0.0:8080", mux)  // OK, explicit
http.ListenAndServe("127.0.0.1:8080", mux) // BAD for publish
```

Why `127.0.0.1` breaks publish:

```text
127.0.0.1 in the container = loopback of THAT container
Publish sends packets to the container IP (eth0), not to your laptop loopback
Bind only on lo rejects external (including -p) traffic
```

Symptom trace:

```text
Host: curl localhost:18080 → connection refused
docker exec app curl -s localhost:8080/healthz → 200 OK
```

Conclusion: the application works; listen is wrong for publish. It is not “Docker does not work.”

#### Predict then answer — localhost listen

**Question.** Why does `docker exec` curl work while host curl through `-p` does not when listen is `127.0.0.1:8080`?

**Answer.** `docker exec` shares the container's network namespace and hits the container's loopback where the process is bound. Host publish enters through a different network interface.

### 4. 12-factor config via env

Principle: the image is the **same** for staging and prod; env values differ.

```text
Image: /app (binary)
Runtime:
  ADDR=:8080
  DATABASE_URL=postgres://...
  LOG_LEVEL=info
```

Go reading — minimal:

```go
addr := os.Getenv("ADDR")
if addr == "" {
	addr = ":8080"
}
```

Better — one struct, validation, fail fast:

```go
type Config struct {
	Addr        string
	DatabaseURL string
	LogLevel    string
	MaxWorkers  int
}
```

Start trace:

```text
container start
  → config.Load()
  → DATABASE_URL empty
  → return error
  → main log.Fatal / os.Exit(1)
  → orchestrator sees a crash loop with a clear log
instead of:
  → server up
  → first request 500 "driver: bad connection"
```

Fail fast is cheaper than a “green” healthz that lies while the DB URL is unset (unless healthz deliberately checks the DB — then document that).

### 5. Docker -e, ENV, ARG — three different lifetimes

| Mechanism | When it is set | Enters the image? | For what |
|-----------|----------------|----------------|--------|
| `ARG` | build | can remain in build-stage history | version, TARGETARCH |
| `ENV` in Dockerfile | build → stays in image | yes | non-secret default |
| `-e` / Compose `environment` | run | no (only that container) | real config, secrets |

```dockerfile
ENV ADDR=:8080
ENV LOG_LEVEL=info
# NOT: ENV DATABASE_URL=postgres://user:pass@...
```

```bash
docker run -e DATABASE_URL="$DSN" -e LOG_LEVEL=debug app:dev
```

#### Predict then answer — secret in ENV

**Question.** You put `ENV API_KEY=secret` in the Dockerfile, build, push. Who can see the secret?

**Answer.** Anyone who can `docker pull` + `inspect` / history / run the image and read env. The secret is in the artifact. Do not bake secrets into the image.

### 6. Compose environment and env_file

```yaml
services:
  api:
    image: inventory:dev
    ports:
      - "18080:8080"
    environment:
      ADDR: ":8080"
      LOG_LEVEL: debug
      DATABASE_URL: postgres://app:${POSTGRES_PASSWORD}@db:5432/app?sslmode=disable
    env_file:
      - .env
```

Priority mechanism (typical Compose feel — check your project's Compose version):

```text
env_file loads keys
environment: block overwrites / supplements
docker run -e on the CLI overwrites for ad-hoc
```

`.env` next to the Compose file often serves **interpolation** (`${POSTGRES_PASSWORD}`) — that is not automatically the same as `env_file` inside the container. Separate:

- `.env` for Compose interpolation (do not commit secrets)
- `.env.example` in git with empty/placeholder values
- real secrets in a secret store / CI secrets

Hostname `db` works only on the Compose network — that is the service DNS name, not `localhost`.

#### Trace DSN

```text
DATABASE_URL=postgres://app:***@db:5432/app
  → Go sql.Open
  → DNS lookup "db" in the container network
  → Postgres container IP
  → TCP 5432
```

If you put `localhost` in the DSN inside the api container, `localhost` is the api container — not Postgres. Classic mistake.

### 7. PORT vs ADDR (PaaS convention)

Many platforms inject `PORT` (a string number, e.g. `8080`), not a full listen addr.

```go
func listenAddr() string {
	if p := os.Getenv("PORT"); p != "" {
		return ":" + p
	}
	if a := os.Getenv("ADDR"); a != "" {
		return a
	}
	return ":8080"
}
```

Priority trace:

```text
PORT set → ":"+PORT
else ADDR set → ADDR
else default :8080
```

Document the priority in a README table — that is part of your image's API.

### 8. Validation and types from string env

Env is always a string. Numbers, bool, duration require parse:

```go
if v := os.Getenv("MAX_WORKERS"); v != "" {
	n, err := strconv.Atoi(v)
	if err != nil || n < 1 {
		return c, fmt.Errorf("invalid MAX_WORKERS: %q", v)
	}
	c.MaxWorkers = n
}
```

Bad parse trace:

```text
MAX_WORKERS=abc
  → Atoi error
  → Load() error
  → process does not start
MAX_WORKERS=0
  → your validation: invalid
```

Do not swallow the error with `n, _ := strconv.Atoi(v)`.

### 9. Kubernetes orientation (same contract)

```yaml
containers:
  - name: api
    image: ghcr.io/acme/inventory:1.2.3
    ports:
      - containerPort: 8080
    env:
      - name: ADDR
        value: ":8080"
      - name: DATABASE_URL
        valueFrom:
          secretKeyRef:
            name: inventory-db
            key: url
```

`containerPort` is documentation analogous to `EXPOSE`. Service/Ingress does the publish equivalent. Same binary, same env keys.

### 10. What not to do with ports in code

```go
// BAD: hardcode different per build tag
//go:build staging
const addr = ":3000"
```

Instead one binary, env chooses the port. The image is not rebuilt because “staging listens on 3000.”

### 11. GOMEMLIMIT and similar runtime hints

The Go runtime respects some env hints (e.g. `GOMEMLIMIT`) — that is still 12-factor: the operator sets them without a rebuild. Document optional keys alongside application ones.

### 12. End-to-end trace: from Compose to handler

```text
1. ports: "18080:8080"          → host mapping
2. environment ADDR=:8080       → process sees ADDR
3. config.Load()                → Addr = ":8080"
4. ListenAndServe(cfg.Addr)     → bind 0.0.0.0:8080 in the namespace
5. EXPOSE 8080                  → metadata aligned
6. curl localhost:18080/healthz → 200
```

If step 4 uses `127.0.0.1`, step 6 fails. If step 1 is missing, step 6 fails. If step 2 sets `ADDR=127.0.0.1:8080`, step 6 fails — env can **break** listen just like a hardcode.

## Rules and syntax

1. `EXPOSE` documents; it does **not** publish.
2. Publish: `docker run -p host:container` or Compose `ports:`.
3. In the container listen on `:8080` or `0.0.0.0:8080`, not `127.0.0.1`.
4. Configuration via env; `os.Getenv` + one `Load()`.
5. Fail fast on required keys (`DATABASE_URL`).
6. Do not bake secrets into `Dockerfile ENV` or build `ARG`.
7. `ENV` is fine for non-secret defaults (`ADDR`, `LOG_LEVEL`).
8. Document keys in `.env.example` and a README table.
9. `PORT` (PaaS) and `ADDR` can coexist — define priority.
10. Inside the Compose network use service name + container port, not the host publish port.
11. Do not log secret values; you may log that a key is set.
12. Test `Load()` with `t.Setenv`.

## Examples

### Example 1 — Dockerfile: EXPOSE + non-secret default

```dockerfile
# syntax=docker/dockerfile:1
FROM gcr.io/distroless/static-debian12:nonroot
COPY app /app
ENV ADDR=:8080
ENV LOG_LEVEL=info
EXPOSE 8080
USER nonroot:nonroot
ENTRYPOINT ["/app"]
```

#### What happens here

The runtime stage copies the `app` binary to `/app` on distroless and records `ENV` defaults `ADDR=:8080` and `LOG_LEVEL=info`. Those defaults ship in the image and can be overridden at run time with `-e` or Compose `environment`, without rebuilding. `EXPOSE 8080` only adds 8080/tcp to image metadata. It does not publish a host port, open a firewall, or bind the process; publish is `-p`, `-P`, or Compose `ports:`.

#### Predict then answer

**Question.** Staging runs the same image with `-e ADDR=:3000 -p 3000:3000`. Is a rebuild needed?

**Answer.** No. Env overrides the default. The image stays the same.

### Example 2 — config.Load with validation

```go
package config

import (
	"fmt"
	"os"
	"strconv"
)

type Config struct {
	Addr        string
	DatabaseURL string
	LogLevel    string
	MaxWorkers  int
}

func Load() (Config, error) {
	c := Config{
		Addr:        listenAddr(),
		DatabaseURL: os.Getenv("DATABASE_URL"),
		LogLevel:    envOr("LOG_LEVEL", "info"),
		MaxWorkers:  4,
	}
	if c.DatabaseURL == "" {
		return c, fmt.Errorf("DATABASE_URL is required")
	}
	if v := os.Getenv("MAX_WORKERS"); v != "" {
		n, err := strconv.Atoi(v)
		if err != nil || n < 1 {
			return c, fmt.Errorf("invalid MAX_WORKERS: %q", v)
		}
		c.MaxWorkers = n
	}
	return c, nil
}

func listenAddr() string {
	if p := os.Getenv("PORT"); p != "" {
		return ":" + p
	}
	return envOr("ADDR", ":8080")
}

func envOr(k, d string) string {
	if v := os.Getenv(k); v != "" {
		return v
	}
	return d
}
```

#### What happens here

`Load` reads the process environment once and returns a `Config` or an error. An empty `DATABASE_URL` fails the call, so the process can exit before it serves traffic. If `PORT` is set, the listen address is `:` plus that value and `ADDR` is ignored; otherwise `ADDR` is used, or `:8080` when `ADDR` is empty. `LOG_LEVEL` defaults to `info`. `MAX_WORKERS` stays 4 unless it is set, and a set value must parse as an integer of at least 1.

#### Trace

```text
DATABASE_URL unset → error
PORT=9090 → Addr=":9090"
ADDR=:8080, PORT unset → Addr=":8080"
MAX_WORKERS=-1 → error
```

#### What happens here

Each line is one result from `Load`. An unset `DATABASE_URL` is an error. `PORT=9090` sets `Addr` to `":9090"`. With `PORT` unset, `ADDR=:8080` is kept as `":8080"`, and `MAX_WORKERS=-1` is an error because it is less than 1.

### Example 3 — main uses Load

```go
package main

import (
	"log"
	"net/http"
	"os"

	"example.com/inventory/internal/config"
)

func main() {
	cfg, err := config.Load()
	if err != nil {
		log.Fatal(err)
	}
	mux := http.NewServeMux()
	mux.HandleFunc("GET /healthz", func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
	})
	log.Printf("listening on %s log=%s", cfg.Addr, cfg.LogLevel)
	if err := http.ListenAndServe(cfg.Addr, mux); err != nil {
		log.Fatal(err)
	}
	_ = os.Stderr
}
```

#### What happens here

`main` calls `config.Load` and uses `log.Fatal` if that returns an error, so an invalid environment never reaches the listener. The mux handles `GET /healthz` by writing status 200 and no body. `ListenAndServe` then blocks on `cfg.Addr`, which came from `PORT` or `ADDR`. The log line prints only that address and the log level.

Do not log `cfg.DatabaseURL`.

### Example 4 — Compose publish + env

```yaml
services:
  api:
    image: inventory:dev
    ports:
      - "18080:8080"
    environment:
      ADDR: ":8080"
      DATABASE_URL: postgres://app:${POSTGRES_PASSWORD}@db:5432/app?sslmode=disable
      LOG_LEVEL: debug
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: app
```

#### What happens here

The `api` service publishes host port 18080 to container port 8080 and injects `ADDR`, `DATABASE_URL`, and `LOG_LEVEL` into the process environment. The DSN host is the Compose service name `db` on port 5432, the port Postgres listens on inside the Compose network. `${POSTGRES_PASSWORD}` is filled by Compose interpolation before the container starts, so the password is not an `ENV` layer in the image. The `db` service gets `POSTGRES_PASSWORD` and `POSTGRES_DB` as its own runtime environment.

#### Predict then answer

**Question.** From the api container, which URL do you use for Postgres: `localhost:5432` or `db:5432`?

**Answer.** `db:5432`. `localhost` in the api container is not Postgres.

### Example 5 — Anti-example listen localhost

```go
// BAD in a container
_ = http.ListenAndServe("127.0.0.1:8080", mux)

// GOOD
_ = http.ListenAndServe(":8080", mux)
```

#### What happens here

`ListenAndServe("127.0.0.1:8080", mux)` accepts connections only on the container loopback. A published port delivers packets to another interface in that namespace, so a host client is refused while `docker exec` curl to localhost still works. `ListenAndServe(":8080", mux)` listens on all interfaces, which is the bind that publish can reach. The handler is the same; the listen address is what changes the result.

### Example 6 — Test Load with t.Setenv

```go
func TestLoadRequiresDatabaseURL(t *testing.T) {
	t.Setenv("DATABASE_URL", "")
	_, err := config.Load()
	if err == nil {
		t.Fatal("expected error")
	}
}

func TestLoadPORTWins(t *testing.T) {
	t.Setenv("DATABASE_URL", "postgres://x")
	t.Setenv("PORT", "9090")
	t.Setenv("ADDR", ":8080")
	c, err := config.Load()
	if err != nil {
		t.Fatal(err)
	}
	if c.Addr != ":9090" {
		t.Fatalf("got %q", c.Addr)
	}
}
```

#### What happens here

`TestLoadRequiresDatabaseURL` sets `DATABASE_URL` to an empty string and fails the test if `Load` returns no error. `TestLoadPORTWins` sets a dummy DSN, `PORT=9090`, and `ADDR=:8080`, then requires `Addr` to be `:9090`. That checks the priority in `listenAddr`: a non-empty `PORT` wins over `ADDR`. `t.Setenv` applies those values for the test and restores the previous environment afterward, and neither test talks to Docker.

### Example 7 — slog level from env

```go
func parseLevel(s string) slog.Level {
	switch s {
	case "debug":
		return slog.LevelDebug
	case "warn":
		return slog.LevelWarn
	case "error":
		return slog.LevelError
	default:
		return slog.LevelInfo
	}
}
```

#### What happens here

`parseLevel` maps a log-level string onto an `slog.Level`. `debug`, `warn`, and `error` select those levels. Any other string, including the empty string, returns `slog.LevelInfo`. The function does not read the environment; the caller passes the string `Load` already resolved.

### Example 8 — Contract table with operators

| Key | Required | Example | Description |
|-------|----------|--------|------|
| `ADDR` | no | `:8080` | Listen address |
| `PORT` | no | `8080` | PaaS style; if set, priority |
| `DATABASE_URL` | yes | `postgres://...` | DSN |
| `LOG_LEVEL` | no | `info` | slog level |
| `GOMEMLIMIT` | no | `256MiB` | GC soft limit |

This table is part of the image “API” as much as HTTP routes.

### Example 9 — Demonstrating EXPOSE without publish

```bash
docker run -d --name demo app:dev
curl -s localhost:8080/healthz || echo "FAIL expected"
docker port demo
docker rm -f demo

docker run -d --name demo -p 18080:8080 app:dev
curl -s localhost:18080/healthz
docker rm -f demo
```

#### What happens here

The first `docker run` starts the container without `-p` or `-P`. `EXPOSE` does not publish a port, so curl to `localhost:8080` fails, the `|| echo` prints `FAIL expected`, and `docker port` shows no mapping. The second run adds `-p 18080:8080`, which is what lets a host curl target container port 8080. Each demo container is removed with `docker rm -f`.

Expectation trace:

```text
First curl: FAIL expected
docker port demo (without -p): empty
Second curl: 200
```

#### What happens here

The first curl is expected to fail: that container was started with no published port. `docker port` is empty for the same run, because `EXPOSE` does not publish a port. The second curl is expected to return 200 from `localhost:18080`, the host port mapped by `-p 18080:8080`. These three lines are the expected outcomes of the commands above.

## Decision analysis

**ENV default in the image vs runtime only.** Defaults for non-secrets reduce local smoke friction. Secrets only at runtime.

**One DSN vs host/port/user/password separately.** DSN is simpler for Go `database/sql`. Separate keys make rotating one field in a secret store easier. The team picks one and documents it.

**Feature flags in env.** Fine for coarse switches (`FEATURE_X=true`). Complex flag platforms are out of scope for this lesson.

**Healthz without a DB check.** Faster start and a clear “process alive”; a separate `/readyz` can ping the DB. Do not mix without documentation.

**Compose env_file vs CI secrets.** Locally `env_file`; CI injects from a secret store. Do not commit real `.env` files.

## Trade-offs

| Approach | Gain | Cost |
|---------|-------|------|
| Everything via env | 12-factor, same image | Many keys, string parsing |
| Config file in a volume | Readable for large config | Mount, permissions, drift |
| Hardcode in binary | “Works immediately” | Rebuild per environment |
| EXPOSE + documentation | Clear contract | Easy to forget updating when you change the port |
| Only `-p` without EXPOSE | Works | Tools/people do not see intent in image metadata |
| PORT + ADDR | PaaS portability | You must document priority |

## Common mistakes

1. **`EXPOSE` treated as publish.** Host curl without `-p` “Docker does not work.”
2. **Listen on `127.0.0.1`.** Exec works, publish does not.
3. **Secret in `Dockerfile ENV` or build-arg.** Leak into the registry.
4. **`localhost` in the DSN between Compose services.** Wrong network namespace.
5. **Different key names** (`DB_URL` vs `DATABASE_URL`) across environments without a table.
6. **Assuming the container port is always 8080** while the Service expects 80 — mapping must match.
7. **Escape / password interpolation** with special characters in Compose.
8. **Logging `DATABASE_URL`.** Secret in the log aggregator.
9. **Healthz 200 while `Load` has not validated required keys** — or the opposite: crash without a clear error string.
10. **Mixing host port and container port** in documentation (`18080` inside the service network).

## Idiomatic Go

- One `Load()` in `package config`; `main` only calls it and exits on error.
- `t.Setenv` in config tests (Go 1.17+).
- You do not change env via hot-reload unless you deliberately build that mechanism — container restart is the normal model.
- `context` for graceful shutdown; env is read at start.
- Official terms: `error` from `Load`, not “mistake”; `package config`.

```go
cfg, err := config.Load()
if err != nil {
	log.Fatal(err)
}
```

## Practical scenario

Staging deploy “does not respond.” The Service maps 80→8080. The application reads `ADDR` from an old config file baked into the image that says `127.0.0.1:8080`. On-call sees:

```text
kubectl port-forward ... → refused
exec curl localhost:8080 → 200
```

Diagnosis: listen, not Service. The team deletes the config file from the image, moves to env + `Listen(":8080")`, adds a README key table and a CI smoke that fails if `/healthz` is not reachable from the published port. The next incident lasts minutes instead of hours.

## Summary

Ports in Docker are a chain: process listen → `EXPOSE` (documentation) → publish (`-p` / `ports:`). `EXPOSE` does not open a host port. A Go application in a container listens on `:8080` / `0.0.0.0`, not on `127.0.0.1`, and pulls configuration from the environment per the 12-factor principle. Secrets do not go into the image; `Load()` fail fast protects both developers and operators. The same key contract applies in Compose and in the cluster.
