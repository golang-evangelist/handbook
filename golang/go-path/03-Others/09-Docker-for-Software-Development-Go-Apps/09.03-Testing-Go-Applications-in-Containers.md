# 09.03 Testing Go Applications in Containers

> **Go Path - Zero to Gopher** / **03 Others → Docker for Software Development: Go Apps** / Lesson 09.03

## Lesson goals

After this lesson you should be able to:

- run `go test` reliably on a CI runner and inside a Docker build target / test container
- separate unit, integration, and smoke/e2e tests by cost and place of execution
- use Compose to bring up dependencies (Postgres, Redis) for integration and smoke without a manual local stack
- understand the Testcontainers concept at a high level and, when you use the library, the real API (`testcontainers.GenericContainer` / modules) — without invented methods
- connect test exit codes to the CI gate before image publish
- know briefly what image tag and digest are when CI stores test artifacts / references the image under test

## Prerequisite

- Lessons 09.01–09.02 (multi-stage, `--target test`, env, ports)
- `go test`, table-driven tests, `testing.T`
- Docker available locally; in CI: Docker on the runner or a build without DinD for a pure `go test` job
- Basic Compose (`services`, `depends_on`, network)

## Problem this lesson solves

In-memory unit tests do not catch SQL dialect, migrations, service DNS names (`db` vs `localhost`), TLS edges, or a wrong listen. On the other hand, a full Compose e2e for every tiny PR is slow and brittle. You need a **pyramid**:

```text
many fast unit (ms–s)
  fewer integrations with a real dependency in a container (s–min)
    little smoke over the final image (s–min)
      rarely broad e2e (min)
```

Without discipline you get an inverted pyramid: five unit tests and two hundred e2e — CI hurts, a colleague's laptop goes red because “there is no Postgres on 5432.”

Testcontainers automates the lifecycle of a dependent container from a Go test. Compose automates the same stack declaratively. Both are legitimate; this lesson teaches `go test` in CI/container + Compose dependencies as the foundation, and Testcontainers only with the real API of the `testcontainers-go` library.

## Mental model

| Layer | Where it runs | Speed | What it catches |
|------|-----------------|--------|-----------|
| Unit | `go test` on the runner | ms–s | pure logic |
| Integration | `go test` + dependency containers | s–min | SQL, network, migrations |
| Image smoke | running app container | s–min | listen, env, `/healthz` |
| E2E | Compose stack | min | flow across multiple services |

What each layer does **not** test:

```text
Docker --target test (go test in the build)
  → tests code in the build context + toolchain
  → does NOT necessarily test the final distroless runtime image

Compose smoke
  → tests the final image + publish + env
  → does NOT replace unit coverage of logic
```

Tag vs digest (briefly, for test artifacts):

```text
image:ghcr.io/acme/app:sha-abc     → movable reference (tag may move later)
image:ghcr.io/acme/app@sha256:... → immutable bytes (useful for “we tested exactly this”)
```

### Predict then answer (pyramid)

**Question.** CI has only Compose e2e (15 min) and zero unit tests. A PR changes a pure function `DiscountCents`. What is the problem?

**Answer.** Feedback is slow and expensive; e2e may pass or fail for infra reasons without a clear diagnosis of the logic. A unit test would fail in seconds on the exact function.

## Mechanism

### 1. `go test` on the CI runner (first gate)

```yaml
- uses: actions/setup-go@v5
  with:
    go-version: "1.22.x"
    cache: true
- run: go test ./...
```

Trace:

```text
checkout
  → setup-go + module cache
  → go test ./...
  → exit 0 → next job
  → exit ≠0 → stop, no build/push
```

This is the fastest feedback. No Docker overhead. Unit tests here **must not** require the daemon.

Exit code is the contract with CI: any failing test → non-zero → gate closed. Not “a warning in the log then push.”

#### Predict then answer

**Question.** A test in `package store` does `sql.Open` to `localhost:5432` without a tag. A colleague without Postgres runs `go test ./...`. What happens?

**Answer.** The test fails or hangs. Default `go test ./...` must be green without Docker. Mark integration with a build tag or a separate package/job.

### 2. Build tag for integration

```go
//go:build integration

package store_test
```

```bash
go test ./...                      # without integration
go test -tags=integration -timeout 15m ./...
```

CI trace:

```text
job unit:        go test ./...
job integration: needs unit → go test -tags=integration -timeout 15m ./...
```

A suite-level timeout prevents an infinite hang when a container does not start.

### 3. `go test` inside Docker `--target test`

From 09.01:

```dockerfile
FROM base AS test
COPY . .
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    go test ./...
```

```bash
docker build --target test .
```

Mechanism:

```text
build context (after .dockerignore)
  → COPY into the stage
  → go test in an isolated toolchain same as the builder
  → FAIL → whole build fails → CI red
```

What you get: a reproducible toolchain (same Go version as the image build).  
What you do not get: proof that the **runtime** image (distroless) starts and serves HTTP.

`.dockerignore` must not exclude `*_test.go` — otherwise “no tests” and falsely green.

#### Predict then answer — target test

**Question.** `--target test` passes, but `docker run` of the runtime image does not respond on the publish port. How?

**Answer.** The test stage did not run the final binary as a server; it tested packages. Listen/`EXPOSE`/env are caught by smoke (next section).

### 4. `go test` inside a running container (ad-hoc)

Sometimes CI does:

```bash
docker run --rm \
  -v "$PWD":/src -w /src \
  -e CGO_ENABLED=0 \
  golang:1.22.5-bookworm \
  go test ./...
```

Trace:

```text
ephemeral container
  → mount of sources
  → same go test command as on the host
  → exit, container removed
```

Useful when the runner has no Go but has Docker. Module cache on a volume or BuildKit cache mount in the image build usually scales better than a pure bind mount without cache.

Variant with network to Compose dependencies:

```bash
docker compose up -d db
docker run --rm --network <compose_network> \
  -v "$PWD":/src -w /src \
  -e DATABASE_URL=postgres://postgres:test@db:5432/app?sslmode=disable \
  golang:1.22.5-bookworm \
  go test -tags=integration -timeout 10m ./internal/store/...
```

Trace: the Go test process sees hostname `db` because it shares the Compose network — the same DNS model as the runtime api service.

### 5. Compose as a dependency for test / smoke

```yaml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: test
      POSTGRES_DB: app
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 2s
      timeout: 5s
      retries: 10
  api:
    image: inventory:dev
    ports:
      - "8080:8080"
    environment:
      ADDR: ":8080"
      DATABASE_URL: postgres://postgres:test@db:5432/app?sslmode=disable
    depends_on:
      db:
        condition: service_healthy
```

Smoke in CI:

```bash
docker compose up --build -d
for i in $(seq 1 30); do
  curl -fsS http://127.0.0.1:8080/healthz && exit 0
  sleep 2
done
docker compose logs
exit 1
```

Trace:

```text
db healthy
  → api start, Load(), Listen
  → publish 8080
  → curl healthz 200
  → compose down -v
```

This catches: wrong DSN host (`localhost` instead of `db`), listen on `127.0.0.1`, missing CA, wrong ENTRYPOINT.

### 6. Integration test with Compose network (Go on the host)

Pattern:

```text
1. docker compose up -d db
2. export DATABASE_URL to localhost:<published_port>
3. go test -tags=integration ./internal/store/...
4. docker compose down -v
```

Dynamic port (avoid fixed 5432 conflict):

```yaml
ports:
  - "5432"   # maps to a random host port
```

```bash
PORT=$(docker compose port db 5432 | cut -d: -f2)
export DATABASE_URL="postgres://postgres:test@127.0.0.1:${PORT}/app?sslmode=disable"
```

Fixed-port conflict trace:

```text
two parallel jobs
  → both -p 5432:5432
  → second bind fails
  → flaky CI
```

### 7. Testcontainers — concept and real API

Lifecycle concept:

```text
Test start
  → API to Docker daemon: start an image (e.g. postgres)
  → wait ready
  → map port, assemble DSN
  → run assertions
  → terminate container (Cleanup)
```

Requirement: the CI agent talks to Docker (socket or DinD — operational platform detail).

Library: `github.com/testcontainers/testcontainers-go`.

**Real entry** — generic container:

```go
//go:build integration

package store_test

import (
	"context"
	"testing"
	"time"

	"github.com/testcontainers/testcontainers-go"
	"github.com/testcontainers/testcontainers-go/wait"
)

func TestWithGenericPostgres(t *testing.T) {
	ctx, cancel := context.WithTimeout(context.Background(), 2*time.Minute)
	defer cancel()

	req := testcontainers.ContainerRequest{
		Image:        "postgres:16",
		ExposedPorts: []string{"5432/tcp"},
		Env: map[string]string{
			"POSTGRES_PASSWORD": "test",
			"POSTGRES_DB":       "app",
		},
		WaitingFor: wait.ForListeningPort("5432/tcp"),
	}
	c, err := testcontainers.GenericContainer(ctx, testcontainers.GenericContainerRequest{
		ContainerRequest: req,
		Started:          true,
	})
	if err != nil {
		t.Fatal(err)
	}
	t.Cleanup(func() {
		_ = c.Terminate(context.Background())
	})

	host, err := c.Host(ctx)
	if err != nil {
		t.Fatal(err)
	}
	port, err := c.MappedPort(ctx, "5432/tcp")
	if err != nil {
		t.Fatal(err)
	}
	dsn := "postgres://postgres:test@" + host + ":" + port.Port() + "/app?sslmode=disable"
	_ = dsn
	// repo := newRepo(t, dsn); ... assertions ...
}
```

**Modules** (e.g. the Postgres module from the same ecosystem) — when you use them, stick to the documented module API (`modules/postgres`), do not invent helper names. If you do not pull a module, `GenericContainer` + `wait` is a sufficient teaching pattern.

Do not teach invented calls like `testcontainers.StartPostgres(...)` in this lesson if they are not part of the real API you use in the project.

#### Predict then answer — Testcontainers

**Question.** Why `t.Cleanup(Terminate)` instead of relying on the OS to “somehow” clean up?

**Answer.** A test can fail mid-suite; Cleanup still runs. Without it you leave zombie containers and occupied ports — flaky next run.

### 8. Readiness without blind Sleep-only

```go
func waitPing(t *testing.T, db *sql.DB, timeout time.Duration) {
	t.Helper()
	deadline := time.Now().Add(timeout)
	for time.Now().Before(deadline) {
		if err := db.Ping(); err == nil {
			return
		}
		time.Sleep(200 * time.Millisecond)
	}
	t.Fatal("db not ready")
}
```

Trace:

```text
Postgres still init
  → Ping fail
  → short backoff
  → Ping OK → continue
timeout
  → Fatal, does not hang forever
```

A single `time.Sleep(10*time.Second)` at the start is not synchronization — it only slows green runs and does not help slower agents.

### 9. Separating jobs

```yaml
jobs:
  unit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version: "1.22.x"
          cache: true
      - run: go test ./...

  integration:
    runs-on: ubuntu-latest
    needs: unit
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version: "1.22.x"
          cache: true
      - run: go test -tags=integration -timeout 15m ./...

  image-test:
    needs: unit
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker build --target test .

  smoke:
    needs: [integration, image-test]
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker compose up --build -d
      - run: |
          for i in $(seq 1 30); do
            curl -fsS http://127.0.0.1:8080/healthz && exit 0
            sleep 2
          done
          docker compose logs
          exit 1
      - run: docker compose down -v
```

Cost trace:

```text
unit fail → cheap stop
integration only if unit green
smoke only when image and integration make sense
```

### 10. Tag and digest in the context of the tested image

```bash
docker build -t ghcr.io/acme/app:${GIT_SHA} .
docker push ghcr.io/acme/app:${GIT_SHA}
DIGEST=$(docker buildx imagetools inspect ghcr.io/acme/app:${GIT_SHA} --format '{{.Manifest.Digest}}')
# smoke / deploy records image@DIGEST
```

Why it matters in the test report:

```text
"tested tag :main" tomorrow may be a different digest
"tested @sha256:…" remains the same artifact
```

Detailed tag/push/digest discipline is 09.05; here only the link: CI needs to know **which bytes** smoke saw.

### 11. What not to test in a container

- String formatting, arithmetic, DTO validation — unit
- `gofmt` / linter — CI tool job
- Whether a public registry “works” — infra probe, not an app test

You pay for a container with time; spend it where it catches real integration bugs.

### 12. Flaky: causes and response mechanism

| Symptom | Common cause | Response |
|---------|------------|---------|
| Occasional connection refused | no wait/ready | healthcheck / wait.ForListeningPort / waitPing |
| Port already allocated | fixed host port | random publish |
| Test passes alone, fails in the package | shared DB state | clean container or transactional rollback |
| Timeout only in CI | slow image pull | cache base image; raise timeout deliberately |

Do not “skip if flaky.” Isolate or fix sync.

### 13. Migrations in an integration test — same SQL as prod

```text
Test brings up Postgres
  → Apply(migrations) same code path as boot in main
  → Insert / Find assertions
  → Terminate
```

If the test uses AutoMigrate “for ease” and prod uses versioned SQL files, you catch false safety. Truth mechanism: **the same migration runner** in the test and in boot.

#### Predict then answer — migrations

**Question.** A unit mock repo passes; integration with real SQL fails on `NOT NULL`. Where is the gap?

**Answer.** The mock did not enforce the constraint. The integration layer with a real DB and the same migrations catches a schema the mock does not simulate.

### 14. t.Parallel and containers

```text
t.Parallel() + one shared Postgres
  → row races, flaky
t.Parallel() + GenericContainer per test
  → isolation, more expensive (pull/start)
suite-level one container + serial tests in the package
  → speed trade-off
```

Rule: do not mix `t.Parallel` with shared mutable DB state without a transactional rollback pattern.

### 15. go test flags useful with containers

```bash
go test -tags=integration -timeout 15m -count=1 ./...
go test -tags=integration -timeout 15m -v ./internal/store/...
go test -tags=integration -run TestOrderRepository ./internal/store/
```

`-count=1` disables the test result cache — useful when you suspect the cache masks flaky.  
`-run` narrows the set while you debug one container test.

### 16. Artifacts: logs and coverage (without magic)

```bash
go test -tags=integration -coverprofile=cover.out ./...
go tool cover -func=cover.out
docker compose logs > compose-smoke.log
```

Coverage from integration measures whether the path through SQL ran — it does not replace unit coverage. Compose logs in a CI artifact speed up diagnosing a smoke failure.

### 17. Redis / another dependency with the same pattern

```go
req := testcontainers.ContainerRequest{
	Image:        "redis:7",
	ExposedPorts: []string{"6379/tcp"},
	WaitingFor:   wait.ForListeningPort("6379/tcp"),
}
```

Same lifecycle as Postgres: GenericContainer → MappedPort → client → Cleanup. Do not teach a special invented `StartRedis` helper as if it were part of the library — write a local helper around the real API if needed.

### 18. Gate order to publish (link to 09.05)

```text
unit go test
  → integration (Compose or GenericContainer)
  → docker build --target test
  → build runtime image
  → smoke (compose up + curl)
  → record digest
  → only then push/promote (09.05)
```

Skipping smoke because “unit is green” lets listen/`EXPOSE`/env class bugs through.

### 19. Predict then answer — smoke loop exit code

**Scenario.** Loop `curl` 30 times, each time fail; at the end `exit 1`. CI job?

**Answer.** Red. If someone puts `curl ... || true`, the gate lies. Smoke must return non-zero when healthz did not reach 200.

### 20. Diagnostic trace when smoke fails

```text
1. docker compose ps          → are api/db Up?
2. docker compose logs api    → Load() fatal? listen error?
3. docker compose exec api    → if there is a shell; distroless has none
4. curl from host vs exec     → publish vs listen (09.02)
5. DATABASE_URL host          → localhost vs db
```

Distroless makes exec harder — so logs on stdout are a mandatory contract.

## Rules and syntax

1. Unit tests: no network, no Docker, in default `go test ./...`.
2. Integration: `//go:build integration` or a separate job/package.
3. `go test -timeout ...` on a suite that brings up containers.
4. `--target test` must not ignore `*_test.go` via `.dockerignore`.
5. Compose smoke tests the final image + env + publish.
6. Random host port instead of fixed 5432 in parallel CI.
7. `t.Cleanup` to close the DB and Terminate the container.
8. Testcontainers: `GenericContainer` / modules — without invented APIs.
9. Do not replace the unit pyramid with e2e.
10. Record the digest when you claim “this image passed smoke.”
11. Same migration path in the test and in boot.
12. The smoke loop must return non-zero on fail.

## Examples

### Example 1 — Fast unit

```go
package pricing

import "testing"

func TestDiscountVIP(t *testing.T) {
	got := DiscountCents(10_000, true)
	if got != 9_000 {
		t.Fatalf("got %d", got)
	}
}
```

#### What happens here

`TestDiscountVIP` calls `DiscountCents(10_000, true)` and fails if the result is not `9_000`. It imports only `testing` and uses no network, database, or Docker. This is a unit test: it belongs in the default `go test ./...` job and fails in the function under test, not in a compose stack. Nothing here starts a container or waits on a port.

CI: `go test ./...`

### Example 2 — Test stage

```dockerfile
FROM base AS test
COPY . .
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    go test ./...
```

#### What happens here

The `test` stage starts from `base`, copies the build context, and runs `go test ./...` during the image build. The cache mounts reuse modules and build outputs without writing those caches into image layers. A failing test fails the `RUN` instruction, so `docker build --target test` fails. This stage does not boot the final runtime image, so listen, env, and `/healthz` stay unproved here.

### Example 3 — Compose smoke loop

See Mechanism §5. Expected success trace: `curl` 200, `down -v`.

### Example 4 — GenericContainer (real API)

See Mechanism §7. After the DSN, ordinary `database/sql` + migrations + assertions.

### Example 5 — Anti-example fixed port

```yaml
# BAD in parallel CI
ports:
  - "5432:5432"
```

#### What happens here

`"5432:5432"` binds host port 5432 to container port 5432. A second job on the same machine that publishes the same host port cannot bind it, and the suite fails for an infrastructure clash rather than a bad assertion. Postgres inside the container can still listen on 5432. The fixed host port is the part that does not belong in parallel CI.

```yaml
# BETTER
ports:
  - "5432"
```

#### What happens here

`"5432"` publishes container port 5432 on an ephemeral host port chosen by Docker. Parallel jobs can run together because they no longer all demand host port 5432. A client on the host has to read the mapped port; it cannot assume 5432. The container port in this mapping is still 5432.

### Example 6 — t.Cleanup pattern

```go
t.Cleanup(func() {
	_ = db.Close()
	_ = c.Terminate(context.Background())
})
```

#### What happens here

`t.Cleanup` runs the registered function when the test ends, including after a failure. The function closes `db` and then calls `Terminate` on the container. `Terminate` is given `context.Background()` so cancellation of the test context does not skip shutdown. The blank identifier drops errors from those two calls, which keeps cleanup from replacing the original test failure, while both steps still run.

### Example 7 — Orientational pyramid numbers

For a medium Go API:

- 100–500 unit (seconds)
- 10–50 integration (minutes)
- 3–10 smoke/e2e (minutes)

If you have 5 unit and 200 e2e — the pyramid is inverted.

### Example 8 — Narrowing one integration test

```bash
go test -tags=integration -timeout 10m -v -run TestWithGenericPostgres ./internal/store/
```

#### What happens here

This command runs only `TestWithGenericPostgres` in `./internal/store/`. `-tags=integration` compiles the integration files that a plain `go test ./...` excludes. `-timeout 10m` stops the process if a container never becomes ready, instead of leaving the job hung. `-v` shows the test output, and `-run` avoids starting the other integration tests in that package.

Trace: only what that test needs comes up; faster feedback while you fix the DSN.

## Decision analysis

**Host `go test` vs Docker test target.** Host: faster PR feedback. Docker target: same toolchain as the release build. Both can; do not duplicate without reason (e.g. host on PR, Docker target on release).

**Testcontainers vs Compose.** Testcontainers: granular per test, Go-centric. Compose: closer to the production stack, good smoke. Often: GenericContainer for the store layer, Compose for release smoke.

**Shared DB for all tests.** Faster, flaky. Prefer a clean container or rollback.

**DinD vs mounted docker.sock.** Operational choice of the CI platform; application tests should not depend on *how* the daemon arrives, only that it is available when the job needs containers.

## Trade-offs

| Strategy | Gain | Cost |
|------------|-------|------|
| Unit only | Speed | Gaps in SQL/network |
| go test in Docker target | Reproducible toolchain | Slower; does not test runtime image |
| Compose smoke | Realism of the final image | Coarser, slower |
| Testcontainers GenericContainer | Isolation per test | Docker in CI, pull time |
| Everything in E2E | “We cover everything” | Slow, brittle, expensive |
| Digest in the report | Exact bytes | Recording automation |

## Common mistakes

1. Integration in default `go test ./...` without Docker — red laptops.
2. No `-timeout` — hanging job.
3. Fixed 5432 in parallel jobs.
4. `.dockerignore` swallows `*_test.go` — falsely green test target.
5. `localhost` between containers instead of the service name.
6. Blind `Sleep(10s)` instead of readiness.
7. Ignoring flaky tests instead of isolation.
8. Assuming the Docker test target replaces smoke of the runtime image.
9. Invented Testcontainers API instead of `GenericContainer` / modules.
10. “We tested `:latest`” without a digest — tomorrow different bytes.
11. AutoMigrate in the test, SQL files in prod — false schema.
12. Smoke with `|| true` — falsely green gate.

## Idiomatic Go

- Table-driven unit tests.
- `t.Helper()`, `t.Cleanup`.
- `context.WithTimeout` around bringing up a container.
- An integration helper like `newTestDB(t) *sql.DB` that registers cleanup — without magical global singletons.
- Official terms: `error`, `testing`, `context`, `package`.

## Practical scenario

The team has 90% unit test coverage; production fails on a `NOT NULL` constraint that local AutoMigrate “smooths over.” They introduce an `integration` tag: `GenericContainer` with `postgres:16`, the same migrations as prod. The bug is caught in CI in 4 minutes. Compose smoke remains for the release gate. PR job: unit + selective integration packages. Once flaky because of a fixed port — they move to a mapped port. They record the digest of the image that passed smoke in the release notes.

## Summary

Testing Go applications with containers requires a pyramid: fast `go test` on CI, optional `--target test` for a toolchain gate, Compose dependencies and smoke over the final image, and when needed Testcontainers via the real `GenericContainer` / modules API. Timeout, dynamic ports, and `t.Cleanup` keep CI stable. The tag names; the digest names the exact bytes smoke saw. Docker is a tool for dependencies and a realistic start — not the only way to “have tests.”
