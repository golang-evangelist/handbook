# 09.01 Building Multi-stage Dockerfiles for Go Applications

> **Go Path - Zero to Gopher** / **03 Others → Docker for Software Development: Go Apps** / Lesson 09.01

## Lesson goals

After this lesson you should be able to:

- write a multi-stage Dockerfile with named stages `base`, `test`, `build`, and `runtime` as the team's default contract
- separate module download (`COPY go.mod go.sum` + `go mod download`) from copying source code for layer cache
- use BuildKit cache mount (`RUN --mount=type=cache`) for `/go/pkg/mod` and `/root/.cache/go-build` with the real syntax only
- build a static Linux binary with `CGO_ENABLED=0 GOOS=linux` and understand why that fits a distroless/scratch runtime
- choose a runtime base: distroless, scratch, or Alpine with `ca-certificates` when you need HTTPS
- use `COPY --from=` so only the artifact enters the final image, not the toolchain
- run a real multi-platform build via `docker buildx --platform linux/amd64,linux/arm64`
- distinguish Docker layer cache from BuildKit cache mount and know what enters the pushed image

## Prerequisite

- Completed module 08 (Compose, Dockerfile optimization, CI sketch) or equivalent experience
- Go 1.22+ locally; understanding of `go.mod`, `go.sum`, and the module cache
- Docker with BuildKit enabled (`DOCKER_BUILDKIT=1` or Docker Desktop by default)
- A basic HTTP Go service under `cmd/...` that you can package
- Knowing the difference between image and container (image is the artifact; container is a running instance)

## Problem this lesson solves

A simple Dockerfile “FROM golang → COPY everything → go build → same image as runtime” works on a laptop and fails in production on three fronts:

1. **Size and attack surface.** The runtime image carries the compiler, git, a shell, and hundreds of packages the application does not use.
2. **Slow CI.** Every change to a `.go` file invalidates a layer and re-downloads modules from the network, because `COPY . .` sits before `go mod download`.
3. **Non-reproducibility.** `FROM golang:latest` today and tomorrow are not the same bytes; an ARM node pulls an amd64-only image and fails without a clear cause.

Multi-stage fixes the contract: the **builder stage** may be rich with tools; the **runtime stage** is a declaration — only what the process needs to run. Cache mount speeds rebuilds on the same builder node, but it **does not enter** the image you send to the registry. Layer cache and cache mount are not the same memory — mixing those terms leads to a false sense that “the image is cached so the content is the same.”

This lesson goes deeper than an intro to multi-stage: the same Dockerfile as a development contract, pinned bases, explicit `CGO_ENABLED`, `COPY --from`, buildx platforms, and real BuildKit mount syntax.

## Mental model

Three separate memories:

```text
1) Build context     → what the daemon gets from you (.dockerignore cuts it)
2) Image layers      → what remains in the artifact and goes to the registry
3) Cache mount       → the builder's local disk between builds; NOT in the image
```

Decision trace when reading a Dockerfile:

```text
FROM golang:... AS build
  → “go, gcc, cache are allowed here”
COPY go.mod go.sum
  → “a code change does NOT invalidate download”
RUN go mod download
  → “module graph in the layer or in the mount”
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -o /out/app
  → “binary at a known path”
FROM gcr.io/distroless/... AS runtime
COPY --from=build /out/app /app
  → “toolchain stays in the build stage; runtime does not know about go”
```

The builder is a factory. The runtime is a delivery box. If you put the factory in the box, you have not finished multi-stage — you have only renamed the problem.

### Predict then answer (mental model)

**Question.** After `docker build -t app:dev .` with a multi-stage file, does `/go/pkg/mod` exist in the `app:dev` image if you used a cache mount on `/go/pkg/mod` in the build stage?

**Predict** before you read the answer.

**Answer.** No. Cache mount lives on the builder. Only what `COPY`/`RUN` in the **runtime** stage explicitly places enters `app:dev`. The module cache is not part of the pushed image.

## Mechanism

This section is the core of the lesson. Follow the flow from the syntax directive to multi-platform push, with traces and predictions.

### 1. Syntax line and named stages

```dockerfile
# syntax=docker/dockerfile:1

FROM golang:1.22.5-bookworm AS base
```

`# syntax=docker/dockerfile:1` enables the modern Dockerfile frontend (mounts, secrets as mounts, etc.). Without it, an older parser may reject `RUN --mount=...`.

`AS base` names the stage. Later `FROM base AS build` inherits layers up to that point. CI calls a target by name:

```bash
docker build --target test .
docker build --target runtime -t inventory:dev .
```

CI gate trace:

```text
PR opened
  → docker build --target test .
      FAIL → job red, no publish
      PASS → docker build --target runtime -t ... --push
```

### 2. Module cache: COPY go.mod go.sum before code

```dockerfile
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
```

Why this order:

| Step | Effect on layer cache |
|-------|------------------------|
| `COPY go.mod go.sum` | Changes only when the module graph changes |
| `RUN go mod download` | Is cached until `go.mod`/`go.sum` change hash |
| `COPY . .` | Changes on almost every commit |
| `RUN go build` | Must repeat for a code change — OK |

If you do `COPY . .` then `go mod download`, every comment change in `main.go` invalidates the download layer. That is the most common cause of “CI always downloads modules from scratch.”

#### Predict then answer — COPY order

**Scenario.** `go.sum` unchanged; you change only `internal/billing/calc.go`.

**Question.** Which RUN runs again if the order is: mod files → download → COPY code → build?

**Answer.** `go mod download` stays from the layer cache. `go build` repeats. The download layer is not invalidated.

### 3. BuildKit cache mount (real syntax)

Layer cache stores the result of `RUN` as an image layer (until you invalidate it). Cache mount is a **temporary volume on the builder** during `RUN`:

```dockerfile
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    go build -o /out/app ./cmd/app
```

And for download:

```dockerfile
RUN --mount=type=cache,target=/go/pkg/mod \
    go mod download
```

What the mount does:

```text
First build on a clean builder
  → /go/pkg/mod empty
  → go downloads modules into the mount
  → the layer may not contain modules (depends on whether you COPY-ed them)
  → the mount remains on the builder disk

Second build, same go.sum, .go change
  → mount already has modules
  → go build uses /root/.cache/go-build
  → faster, no network for modules
```

Explicit `id` when the same builder builds multiple projects:

```dockerfile
RUN --mount=type=cache,id=inventory-gomod,target=/go/pkg/mod \
    --mount=type=cache,id=inventory-gobuild,target=/root/.cache/go-build \
    go build -o /out/app ./cmd/app
```

**Rule.** Learn only the real syntax `RUN --mount=type=cache,...`. Do not invent `CACHE FROM` inside the Dockerfile as a substitute for this.

#### Trace: what enters the image after a mount

```text
RUN --mount=type=cache,target=/go/pkg/mod go mod download
  → during RUN: modules visible in /go/pkg/mod
  → after RUN: mount detaches
  → the layer records filesystem CHANGES outside the mount
  → /go/pkg/mod from the mount is NOT automatically in the layer
```

That is why runtime does not “inherit” the module cache by mistake — unless you explicitly `COPY` `/go/pkg/mod`, which you **do not**.

### 4. Static build: CGO_ENABLED=0 GOOS=linux

```dockerfile
ARG TARGETOS=linux
ARG TARGETARCH=amd64
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH \
    go build -trimpath -ldflags="-s -w -X main.version=${VERSION}" \
    -o /out/app ./cmd/app
```

Why `CGO_ENABLED=0`:

- the binary does not depend on glibc/musl in the runtime image
- works with `distroless/static` and with `scratch`
- if you enable CGO, the runtime must have compatible shared libraries — a different contract

`GOOS=linux` even when you build on a Windows laptop: the target is a Linux container, not the Windows host.

`-trimpath` removes local paths from the binary (more reproducible build, less path leakage in stack traces).
`-ldflags="-s -w"` shrinks symbol tables (release); keep symbols for debug.
`-X main.version=...` injects the version without reading `.git` in the runtime image.

#### Predict then answer — CGO + distroless

**Question.** Build with `CGO_ENABLED=1` and `FROM gcr.io/distroless/static-debian12`. What do you expect on container start?

**Answer.** Often `error while loading shared libraries` or a similar crash, because static distroless does not have the libs a dynamically linked binary needs. Or the build fails entirely without gcc in the builder. Contract: CGO off + static runtime, or CGO on + a runtime with the required libs (e.g. `distroless/base` or Debian slim) — consciously.

### 5. COPY --from: bridge between stages

```dockerfile
FROM gcr.io/distroless/static-debian12:nonroot AS runtime
COPY --from=build /out/app /app
USER nonroot:nonroot
EXPOSE 8080
ENTRYPOINT ["/app"]
```

`COPY --from=build` copies **only the named path** from another stage. It does not copy the entire build filesystem.

Size trace:

```text
build stage image (if you tag it): 800MB+ (golang base + src + cache traces)
runtime stage:                       ~5–30MB (binary + minimal base)
```

If `docker images` shows a huge “app”, check that you did not tag `build` instead of `runtime`, or that you did not forget `--target runtime` when you have multiple stages and the last one is not runtime.

### 6. Runtime bases: distroless, scratch, Alpine

| Base | When | HTTPS / CA | Shell | Note |
|------|------|------------|-------|------|
| `gcr.io/distroless/static-debian12:nonroot` | static Go, nonroot | CAs included in the static variant for TLS clients | none | good default |
| `scratch` | extremely thin | **no** CA — add them manually or outbound HTTPS fails | none | static binary only |
| `alpine:3.20` | you need a shell/tools in the container | `apk add --no-cache ca-certificates` | yes | larger attack surface than distroless |

For HTTPS to external APIs from a Go client you need root CAs. Distroless static typically already carries a CA bundle. Scratch does not — you must:

```dockerfile
FROM alpine:3.20 AS certs
RUN apk add --no-cache ca-certificates

FROM scratch AS runtime
COPY --from=certs /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
COPY --from=build /out/app /app
ENTRYPOINT ["/app"]
```

Or stay on distroless and do not complicate things.

#### Trace HTTPS without CA

```text
Go http.Get("https://api.example.com")
  → crypto/x509 looks for system CAs
  → scratch without certs
  → x509: certificate signed by unknown authority
```

The symptom is not “the network does not work” — TLS verification fails. The fix is CAs in the image or (rarely, and dangerously) disabling verification — you do not do that in production.

### 7. Multi-platform: only real buildx

```bash
docker buildx build \
  --platform linux/amd64,linux/arm64 \
  -t ghcr.io/acme/inventory:1.2.0 \
  --push \
  .
```

What happens:

```text
buildx for amd64
  → GOARCH=amd64 (BuildKit TARGETARCH)
  → layers for that platform
buildx for arm64
  → GOARCH=arm64
  → separate layers
push
  → manifest list in the registry
  → the node pulls the architecture that matches it
```

In the Dockerfile use the automatic ARGs that BuildKit sets:

```dockerfile
ARG TARGETOS
ARG TARGETARCH
RUN CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH go build -o /out/app ./cmd/app
```

Do not learn invented flags. For a local smoke on one architecture:

```bash
docker buildx build --platform linux/amd64 -t inventory:dev --load .
```

`--load` loads into the local daemon (usually one platform). Multi-platform + `--push` goes to the registry.

### 8. ARG scope — common cause of “version always dev”

```dockerfile
ARG VERSION=dev
FROM golang:1.22.5-bookworm AS build
ARG VERSION
RUN echo "building $VERSION"
```

Trace:

```text
ARG VERSION before FROM
  → applies to FROM lines (e.g. FROM golang:${GO_VERSION})
  → does NOT automatically enter the stage
ARG VERSION after FROM
  → now visible in RUN in that stage
docker build --build-arg VERSION=1.4.2
  → ldflags gets 1.4.2 only if ARG is re-declared in the stage
```

#### Predict then answer — ARG

**Question.** You have `ARG VERSION=dev` only before `FROM`, then in the stage `go build -ldflags="-X main.version=${VERSION}"` without a second `ARG VERSION`. What is `main.version`?

**Answer.** Empty string or an unexpected value — the shell sees empty `VERSION` because the ARG from global scope is not automatically in the stage. Fix: `ARG VERSION` immediately after `FROM ... AS build`.

### 9. `.dockerignore` and the test target

The context you send the daemon must match the targets:

```text
.git
bin
*.md
.github
```

If you add `**/*_test.go`, then `RUN go test ./...` in `--target test` may report “no tests” and **pass green** without tests. That is a false gate.

For assets that `go:embed` reads (lesson 09.04): do not ignore `static/` in the build-stage context.

### 10. Reference flow — the whole Dockerfile as mechanism

```dockerfile
# syntax=docker/dockerfile:1

FROM golang:1.22.5-bookworm AS base
WORKDIR /src
COPY go.mod go.sum ./
RUN --mount=type=cache,target=/go/pkg/mod \
    go mod download

FROM base AS test
COPY . .
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    go test ./...

FROM base AS build
COPY . .
ARG TARGETOS=linux
ARG TARGETARCH=amd64
ARG VERSION=dev
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH \
    go build -trimpath -ldflags="-s -w -X main.version=${VERSION}" \
    -o /out/app ./cmd/app

FROM gcr.io/distroless/static-debian12:nonroot AS runtime
COPY --from=build /out/app /app
USER nonroot:nonroot
EXPOSE 8080
ENTRYPOINT ["/app"]
```

Trace of one PR:

```text
1. docker build --target test .
   → base: go.mod/sum cache
   → test: go test ./...
2. docker buildx build --platform linux/amd64,linux/arm64 \
     --build-arg VERSION=$GIT_SHA \
     -t ghcr.io/acme/app:$GIT_SHA --push .
   → runtime image in the registry
3. deploy pulls the image, does not rebuild on the node
```

### 11. Pinning the base image

```dockerfile
FROM golang:1.22.5-bookworm AS base
# better long-term:
# FROM golang:1.22.5-bookworm@sha256:<digest>
```

Tag `1.22.5-bookworm` is better than `latest`, but a tag can still move (rarely for patch tags, more often for floating ones). Digest-pinning the base image is the same discipline as in 09.05 for your images.

### 12. Nonroot and the filesystem

The Distroless `nonroot` user has no write on arbitrary paths. If the application writes to `/var/app` without a volume and without a writable path — crash. Trace:

```text
os.WriteFile("/etc/app.conf", ...)
  → permission denied as nonroot
```

Write to `/tmp` or a mounted volume; pull config from env (09.02), not by writing into an image layer.

### 13. Monorepo ARG SERVICE

```dockerfile
ARG SERVICE=api
RUN CGO_ENABLED=0 go build -o /out/app ./cmd/${SERVICE}
```

CI matrix:

```yaml
strategy:
  matrix:
    service: [api, worker]
```

BuildKit treats different ARG values as different builds; a cache mount with a shared `id` still shares the module cache across services.

### 14. What multi-stage explicitly does not solve

- Secrets in `ARG` can still remain in the build-stage layer history — do not put tokens in ARG
- Cache mount on a shared self-hosted runner needs isolation (`id`, separate builders)
- `go test` in a Docker target tests code in the context, not necessarily the final runtime image (smoke is 09.03)

## Rules and syntax

1. First useful line: `# syntax=docker/dockerfile:1` when you use mounts.
2. Name stages: `AS base`, `AS test`, `AS build`, `AS runtime`.
3. `COPY go.mod go.sum` → download → `COPY . .` → build.
4. Cache mount only as `RUN --mount=type=cache,target=...`.
5. `CGO_ENABLED=0` until you explicitly need CGO.
6. `GOOS=linux` (and `GOARCH` via `TARGETARCH` in buildx).
7. Runtime: distroless/scratch/Alpine — consciously for CA and shell.
8. `COPY --from=build` only the binary (and certs if scratch).
9. `USER nonroot` where the base supports it.
10. Do not copy `/go/pkg/mod` into runtime.
11. Pin base image versions; avoid `latest` as the only reference.
12. `.dockerignore` must not lie to the test target.
13. Multi-platform: `docker buildx --platform linux/amd64,linux/arm64`.
14. `ARG` after `FROM` for values you use in that stage.

## Examples

### Example 1 — Minimal Go service you package

```go
package main

import (
	"encoding/json"
	"net/http"
	"os"
)

var version = "dev"

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /healthz", func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
	})
	mux.HandleFunc("GET /version", func(w http.ResponseWriter, r *http.Request) {
		_ = json.NewEncoder(w).Encode(map[string]string{"version": version})
	})
	addr := ":8080"
	if v := os.Getenv("ADDR"); v != "" {
		addr = v
	}
	_ = http.ListenAndServe(addr, mux)
}
```

#### Predict then answer

**Question.** After a build with `-X main.version=1.2.0`, what does `GET /version` return?

**Answer.** JSON `{"version":"1.2.0"}`. The `version` variable is set by ldflags at compile time; runtime does not read git.

### Example 2 — Reference multi-stage (repeated with flow comments)

```bash
export DOCKER_BUILDKIT=1
docker build --target test -f Dockerfile .
docker build --target runtime -t inventory:dev --build-arg VERSION=dev .
docker run --rm -p 8080:8080 inventory:dev
curl -s localhost:8080/version
```

Expected output trace (conceptual):

```text
{"version":"dev"}
```

### Example 3 — Alpine runtime with ca-certificates

```dockerfile
# syntax=docker/dockerfile:1
FROM golang:1.22.5-bookworm AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN --mount=type=cache,target=/go/pkg/mod go mod download
COPY . .
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    CGO_ENABLED=0 GOOS=linux go build -o /out/app ./cmd/app

FROM alpine:3.20 AS runtime
RUN apk add --no-cache ca-certificates \
 && adduser -D -H -u 65532 nonroot
WORKDIR /home/nonroot
COPY --from=build /out/app /app
USER nonroot
EXPOSE 8080
ENTRYPOINT ["/app"]
```

#### What happens here

Alpine gives a shell (useful for debug `docker exec`), CAs for HTTPS, and a nonroot user. The image is larger than distroless static, smaller than a full golang image.

### Example 4 — Scratch + CA from an intermediate stage

```dockerfile
FROM alpine:3.20 AS certs
RUN apk add --no-cache ca-certificates

FROM golang:1.22.5-bookworm AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN --mount=type=cache,target=/go/pkg/mod go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -o /out/app ./cmd/app

FROM scratch
COPY --from=certs /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
COPY --from=build /out/app /app
EXPOSE 8080
ENTRYPOINT ["/app"]
```

#### Predict then answer

**Question.** Can you `docker exec -it <id> sh` in a scratch runtime?

**Answer.** No — there is no shell. Debug works via logs, an ephemeral debug image, or a temporary Alpine target. That is the scratch trade-off.

### Example 5 — Make targets aligned with stages

```makefile
.PHONY: docker-test docker-run docker-push
docker-test:
	docker build --target test .

docker-run:
	docker build --target runtime -t inventory:dev .
	docker run --rm -p 8080:8080 inventory:dev

docker-push:
	docker buildx build \
	  --platform linux/amd64,linux/arm64 \
	  --build-arg VERSION=$(VERSION) \
	  -t ghcr.io/acme/inventory:$(VERSION) \
	  --push .
```

#### What happens here

The developer does not memorize long commands. Same Dockerfile; different targets. No parallel `Dockerfile.ci` that diverges.

### Example 6 — Cache mount vs layer only (measurement)

```dockerfile
# A: layer only
RUN go mod download
RUN go build -o /out/app ./cmd/app

# B: cache mount
RUN --mount=type=cache,target=/go/pkg/mod go mod download
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    go build -o /out/app ./cmd/app
```

Trace on a laptop (typical feel, not absolute numbers):

```text
First build A and B: similar (cold download)
Second build after a .go change, same go.sum:
  A: download layer cached; build often from scratch for packages
  B: download from mount; go-build cache speeds compilation
On ephemeral CI without cache export: B helps within the job less than locally
```

### Example 8 — Verify that runtime has no `go`

```bash
docker build --target runtime -t inventory:dev .
```

**Question.** Why does `docker run inventory:dev go version` not work on distroless?

**Answer.** There is no `go` binary and no shell that would run it. ENTRYPOINT is `/app`. That is the desired runtime state.

## Decision analysis

**One Dockerfile with targets vs multiple files.** One file scales: CI, local run, test gate. The exception is a deliberate `Dockerfile.debug` for Delve — not five “almost the same” production files.

**Bookworm vs Alpine as builder.** For `CGO_ENABLED=0` both work. Bookworm is closer to the glibc ecosystem; Alpine is a smaller download. The team picks one and does not mix without reason.

**Distroless vs Alpine vs scratch.** Distroless static + nonroot is a good default for a Go API. Alpine when you need `exec`/tools. Scratch when you control CAs and accept a zero debug UX.

**Vendoring (`vendor/`) + cache mount.** Vendor removes the network from the build; the mount still helps the `go-build` cache. Offline policy ≠ a substitute for multi-stage.

**Test in the same Dockerfile.** Yes, as `--target test`, but that is not a substitute for host `go test` in fast PR feedback (09.03).

**Pin the base image digest immediately.** Worth it as soon as you have supply-chain requirements; otherwise at least pin a minor/patch tag (`1.22.5-bookworm`), never only `latest`.

## Trade-offs

| Technique | Gain | Cost |
|---------|-------|------|
| Multi-stage | Small runtime, smaller attack surface | Longer Dockerfile, more stage mental model |
| Cache mount | Fast repeated builds | Depends on builder state; not in the image |
| Layer cache only | Simpler | Slower without mount; COPY order easily broken |
| Distroless | Thin, nonroot | Harder ad-hoc debug |
| Scratch | Minimal | Manual CA; no shell |
| Alpine | Shell, apk | Larger image than distroless static |
| buildx multi-platform | One manifest for amd64+arm64 | Slower CI; needs registry push |
| Multiple targets | One source of truth | CI must know which target is the gate |

## Common mistakes

1. **Cache mount treated as a layer in the registry.** The mount does not travel with `docker push`.
2. **`COPY . .` before `go mod download`.** Every commit breaks the module layer.
3. **`**/*_test.go` in `.dockerignore`.** Test target falsely green.
4. **Copying `/go/pkg/mod` into runtime “just in case”.** Inflates the image, does not help.
5. **`FROM golang:latest` alongside a story about reproducibility.** The tag floats.
6. **CGO build + distroless static.** Shared libs are missing.
7. **Forgotten `ARG VERSION` after `FROM`.** ldflags always sees empty/dev.
8. **Tagged the build stage instead of runtime.** A “small Go image” of 1GB.
9. **HTTPS from scratch without CA.** `x509: unknown authority`.
10. **Listen on `127.0.0.1` in the application.** Publish does not help (detailed in 09.02) — but the symptom is often blamed on the Dockerfile.
11. **Invented BuildKit flags.** Stick to `RUN --mount=type=cache`.
12. **Expecting `docker build` without buildx to produce multi-arch.** It will not — you need `buildx --platform ...`.

## Idiomatic Go

- One `main` per `cmd/<name>`; the Dockerfile points at the exact package (`./cmd/app`).
- `-trimpath` in the release build.
- Version via ldflags (`main.version`), not reading `.git` in the container.
- No network calls in `init()` — container start must be predictable.
- Configuration from env (09.02), not from a file baked differently per environment.
- Static build (`CGO_ENABLED=0`) until a library explicitly requires CGO.
- Fast tests in `--target test`; heavy integration outside the default path or with a build tag (09.03).

```go
// cmd/app/main.go — version that ldflags sets
package main

var version = "dev"
```

## Practical scenario

The team has a 12-minute CI: 8 minutes fall on `go mod download` + cold compilation. The Dockerfile was a single stage `FROM golang`, `COPY . .`, build, then the same image to production (900MB). An ARM node in staging occasionally cannot run an image built on a developer's amd64 laptop.

Intervention:

1. Multi-stage: `base` → `test` → `build` → distroless `runtime` (~18MB).
2. `COPY go.mod go.sum` + cache mount on `/go/pkg/mod` and `go-build`.
3. `CGO_ENABLED=0`, pin `golang:1.22.5-bookworm`.
4. CI: `--target test` as gate; publish via `buildx --platform linux/amd64,linux/arm64 --push`.

After two weeks the PR job is typically ~3 minutes when only `internal/` changes. Once the cache on a self-hosted runner “holds” an old error after a Go patch bump — fix: change the cache `id` prefix. They document: **cache is acceleration, `go.sum` is truth**. The incident with the 900MB image and mixed arch disappears.

## Summary

A multi-stage Dockerfile for Go separates a rich builder from a thin runtime: you cache module download with the `go.mod`/`go.sum` order and optionally a BuildKit cache mount; you build the binary with `CGO_ENABLED=0 GOOS=linux`; into the image goes `COPY --from` of the artifact onto distroless, scratch (with CA as needed), or Alpine. Layer cache and cache mount are not the same thing — only runtime content travels to the registry. buildx with `--platform linux/amd64,linux/arm64` closes the arch gap. One Dockerfile with named targets is the team contract; `go.sum` remains the source of truth.
