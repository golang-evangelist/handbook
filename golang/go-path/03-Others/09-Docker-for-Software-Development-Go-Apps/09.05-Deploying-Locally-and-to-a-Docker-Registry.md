# 09.05 Deploying Locally and to a Docker Registry

> **Go Path - Zero to Gopher** / **03 Others → Docker for Software Development: Go Apps** / Lesson 09.05

## Lesson goals

After this lesson you should be able to:

- run an image locally with correct `-p` and env (without baking secrets)
- tag an image for a registry (`docker tag` / build `-t`)
- push to GHCR or Docker Hub with real commands
- distinguish **tag** and **digest** (`image@sha256:...`) and pin the digest in deploy
- connect the local flow with CI lesson 08.05

## Prerequisite

- 09.01–09.04 (multi-stage, ports/env, tests, embed)
- An account on GHCR (GitHub) or Docker Hub
- `docker login` works

## Problem this lesson solves

The image “works on my machine” but:

- it is not in a registry — another developer / CI / cluster cannot pull it;
- the `:latest` tag is overwritten without a trail;
- deploy pulls the wrong tag;
- a local run uses the wrong publish port or baked-in secrets.

This lesson closes the Docker part of course 09: **from binary in an image to a reliable artifact in the registry**.

## Mental model

```text
docker build → local image (ID)
     ↓
docker tag / -t  → name:tag  (pointer)
     ↓
docker push      → registry stores layers + manifest
     ↓
digest sha256:…  → immutable reference
     ↓
deploy pins digest (not only latest)
```

A registry is not “a folder of files” — it is a content-addressable store of layers with manifests.

## Mechanism

### Local run — reminder

```text
docker run --rm -p 8080:8080 \
  -e ADDR=:8080 \
  -e DATABASE_URL=postgres://... \
  ordersvc:dev
```

- `-p` publish (EXPOSE is not enough)
- `-e` runtime config (not Dockerfile `ENV` secrets)
- `--rm` removes the container on exit

### Tagging

```text
docker build -t ordersvc:1.0.0 .
docker tag ordersvc:1.0.0 ghcr.io/acme/ordersvc:1.0.0
docker tag ordersvc:1.0.0 ghcr.io/acme/ordersvc:latest
```

Or immediately:

```text
docker build -t ghcr.io/acme/ordersvc:1.0.0 .
```

A tag is an alias to an image ID. Multiple tags can point at the same ID.

### Login and push

GHCR:

```text
echo $GITHUB_TOKEN | docker login ghcr.io -u USERNAME --password-stdin
docker push ghcr.io/acme/ordersvc:1.0.0
```

Docker Hub:

```text
docker login
docker push acme/ordersvc:1.0.0
```

Do not commit the token. Do not paste the token into a Dockerfile.

### Digest

After push:

```text
docker buildx imagetools inspect ghcr.io/acme/ordersvc:1.0.0
```

You see `Digest: sha256:...`. Deploy:

```text
ghcr.io/acme/ordersvc@sha256:0123456789abcdef...
```

**Predict then answer:** You pin digest `aaa`. Someone pushes the same tag `1.0.0` with new content (digest `bbb`). Does a pod with `@sha256:aaa` change code?

**Answer:** No. The digest reference stays on the old content. Tag `1.0.0` now points at `bbb`, but your pin is `aaa`.

### Trace: local ID vs registry digest

1. `docker build -t ordersvc:1.0.0 .` → local ID `sha256:loc1`.
2. Push → registry computes manifest digest `sha256:reg1` (may match inspect).
3. On another machine `docker pull ...:1.0.0` → gets the layers for that manifest.

### Multi-platform push (reminder 08.01)

```text
docker buildx build \
  --platform linux/amd64,linux/arm64 \
  -t ghcr.io/acme/ordersvc:1.0.0 \
  --push .
```

Without `--push`, a multi-platform manifest list usually does not end up in the local daemon as a single load.

### Retag without rebuild

```text
docker pull ghcr.io/acme/ordersvc:1.0.0
docker tag ghcr.io/acme/ordersvc:1.0.0 ghcr.io/acme/ordersvc:stable
docker push ghcr.io/acme/ordersvc:stable
```

Same content digest, new tag pointer. Useful for `stable` promotion after QA.

### Deletion and GC (conceptual)

The registry keeps unused layers until a GC policy cleans them. Deleting a tag does not always delete the digest immediately. Pinning a digest means GC must respect references — depends on the registry product (GHCR, ECR, Hub).

### Local registry for learning (optional)

```text
docker run -d -p 5000:5000 --name registry registry:2
docker tag ordersvc:1.0.0 localhost:5000/ordersvc:1.0.0
docker push localhost:5000/ordersvc:1.0.0
```

Official `registry:2` image. For learning push/pull without the cloud.

### Predict then answer: why pull “does not see” the new latest

**Question:** You pushed `:latest`. On the server `docker pull ...:latest` says “up to date,” but the code is old.

**Answer:** Often a local tag already exists that the daemon considers current; or CDN/cache; or you did not really push the same repo. Check the digest locally and in registry inspect. Pinning digest removes this class of confusion.

### Link with Compose

```yaml
services:
  api:
    image: ghcr.io/acme/ordersvc@sha256:abc...
    ports:
      - "8080:8080"
    environment:
      ADDR: ":8080"
```

Compose pulls the pinned artifact. For dev: `build: .` instead of a remote image.

### Registry security

- Private package / repo visibility.
- Token with the smallest scope (`write:packages` / read-only for a deploy bot).
- Do not use a personal password in CI — a token.
- Scan the image before you declare it `stable` (08.05).

### Semver policy (proposal)

| Tag | Meaning |
|-----|----------|
| `1.4.2` | immutable release (by agreement) |
| `1.4` | floating minor (caution) |
| `latest` | only for people / demo |
| `sha-deadbeef` | CI commit |

Production: digest or a strictly immutable tag + verify.

## Rules and syntax

- Local run: `-p` + `-e`, no secrets in the image.
- Tag format: `registry/org/name:version`.
- Push requires `docker login`.
- Production pins `@sha256:...`.
- Multi-platform requires buildx + usually `--push`.
- Do not share the token in git.
- Document the registry image name in README.

## Examples

### Example 1 — From build to GHCR

```text
docker buildx build --target runtime \
  -t ghcr.io/acme/ordersvc:1.0.0 \
  --load .

docker run --rm -p 8080:8080 -e ADDR=:8080 ghcr.io/acme/ordersvc:1.0.0
# smoke curl

docker push ghcr.io/acme/ordersvc:1.0.0
docker buildx imagetools inspect ghcr.io/acme/ordersvc:1.0.0
```

#### What happens here

Build → local smoke → push → reading the digest.

### Example 2 — Digest in a Kubernetes fragment

```yaml
image: ghcr.io/acme/ordersvc@sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef
```

### Example 3 — Hub

```text
docker tag ordersvc:1.0.0 myuser/ordersvc:1.0.0
docker push myuser/ordersvc:1.0.0
```

### Example 4 — Promoting stable

```text
docker buildx imagetools create \
  -t ghcr.io/acme/ordersvc:stable \
  ghcr.io/acme/ordersvc:1.0.0
```

(`imagetools create` is a real buildx command for retagging in the registry.)

### Example 5 — Wrong login

```text
docker push ghcr.io/acme/ordersvc:1.0.0
# denied: denied
```

#### What happens here

No auth or no permission on the package. Fix: login + package permissions (GitHub Packages settings).

### Example 6 — Compose pull pin

See Mechanism — `image: ...@sha256:...`.

## Decision analysis

| Decision | For | Against |
|--------|----|--------|
| Hub only | simple | org policy |
| GHCR | close to GitHub Actions | permissions model |
| digest pin | reproducibility | longer manifests |
| latest in a demo | fast | dangerous in prod |

## Trade-offs

- **Immutable tag discipline vs convenience of latest**
- **Public image vs private** (supply chain, secrets in an embed mistake)
- **Manual push vs CI-only push** — manual push easily bypasses scan

## Common mistakes

1. **Wrong:** deploy on `:latest` without a digest.  
   **Effect:** silent version swap.  
   **Why:** a tag is movable.  
   **Fix:** pin digest.

2. **Wrong:** push without login.  
   **Effect:** denied.  
   **Why:** registry auth.  
   **Fix:** `docker login`.

3. **Wrong:** token in git.  
   **Effect:** compromise.  
   **Why:** secret in the repo.  
   **Fix:** rotation + secret store.

4. **Wrong:** local smoke without `-p`.  
   **Effect:** “registry image does not work.”  
   **Why:** publish.  
   **Fix:** `-p host:container`.

5. **Wrong:** push a debug image as a prod tag.  
   **Effect:** Delve in prod.  
   **Why:** wrong target/tag.  
   **Fix:** separate tags.

6. **Wrong:** mixing Hub and GHCR names.  
   **Effect:** push to the wrong host.  
   **Why:** tag string.  
   **Fix:** full registry host in the tag.

7. **Wrong:** believing `docker tag` copies bytes.  
   **Effect:** confusion about “two images.”  
   **Why:** a tag is a pointer.  
   **Fix:** look at image ID / digest.

8. **Wrong:** multi-platform without push.  
   **Effect:** no expected manifest locally.  
   **Why:** load limitation.  
   **Fix:** `--push` or one platform `--load`.

## Idiomatic Go / Docker

- README: `docker pull` example with a version.
- CI the only writer of prod tags.
- Semver + digest in release notes.
- The same image locally smoked before push.

## Practical scenario

The team pushed `:latest` from a laptop outside CI. The cluster refreshed pods — pulled an unscanned image with local debug flags. Incident.

Fix: banned manual push credentials for people on the prod package; only GitHub Actions SA; deploy only the digest from a CI artifact; `latest` remained for a demo namespace.

## Check questions

1. **What does `docker tag` do?**  
   Adds an alias to an existing image ID.

2. **What is a digest?**  
   A `sha256` identifier of the manifest/content.

3. **Why pin a digest?**  
   An immutable reference despite the tag moving.

4. **Does EXPOSE publish?**  
   No; you need `-p` or Compose ports.

5. **Where do secrets go?**  
   Runtime env / secret store, not the image.

6. **Why login?**  
   The registry requires authentication for push (and private pull).

7. **What does `--push` do with buildx multi-platform?**  
   Sends manifests and layers to the registry.

8. **Who may push prod?**  
   Preferably only CI.

When pull “does not update,” compare digests. When push is denied, check login and permissions. When the cluster has the “wrong version,” ask whether the manifest uses a tag instead of a digest.

### Additional mechanism: what the registry stores

When you push:

1. Layer blobs (content addressable)
2. Config blob
3. Manifest (points at layer digests)
4. Tag → pointer to the manifest digest

That is why two tags can share layers: space savings. That is why deleting a tag does not immediately delete a blob if another tag references it.

### Trace: inspect after push

```text
docker buildx imagetools inspect ghcr.io/acme/ordersvc:1.0.0 --raw
```

You see the JSON manifest. For multi-platform, the manifest list shows child digests by `platform`.

### Predict then answer: pull by digest from another machine

**Question:** Machine A pushes `@sha256:abc`. Machine B does not have that image locally. `docker pull ghcr.io/acme/ordersvc@sha256:abc` — does it work without a tag?

**Answer:** Yes, pull by digest is valid. A tag is not required for a content-addressable fetch.

### Robot accounts

For CI:

- GitHub Actions: `GITHUB_TOKEN` with `packages: write`
- or Fine-grained PAT / classic with `write:packages`
- Deploy bot: **read-only** pull token

Separate write and read credentials.

### Promoting artifacts without a rebuild

Same digest:

```text
dev → staging → prod
```

only new tags on the same manifest. A rebuild per environment introduces the risk “not the same binary.” Prefer promote tag/digest.

### Local fail: insecure registry

`localhost:5000` sometimes needs daemon config for an insecure registry. That is a local learning setup — do not do insecure against a real cloud registry.

### Checklist before “it is done in the registry”

1. Local smoke with `-p` and env
2. Push succeeded (not denied)
3. `imagetools inspect` shows expected platforms
4. Digest written in release / ticket
5. Deploy manifest uses digest
6. Debug tag is not mixed with the prod tag
7. Token is not in shell history pasted into a wiki

### Scenario: mirror and air-gap

Some environments mirror the image into an internal registry. Then the digest must be preserved through the mirror copy. If the mirror only retags `:latest`, you lose the pin. Seek a tool / process that copies the **digest**.

### Another predict-then-answer

**Question:** `docker tag a:1 b:1` then `docker push b:1` without a build — does the registry get the same content as `a:1`?

**Answer:** Yes, if `a:1` and `b:1` point at the same local image ID. A tag does not change bytes.

### Workbook: first push to GHCR (step by step)

1. Create a GitHub repo `acme/ordersvc` (or use an existing one).
2. In GitHub → Settings → Developer settings create a token with `write:packages` (or use `gh auth`).
3. `echo TOKEN | docker login ghcr.io -u USER --password-stdin`
4. `docker build -t ghcr.io/USER/ordersvc:0.1.0 .`
5. `docker run --rm -p 8080:8080 -e ADDR=:8080 ghcr.io/USER/ordersvc:0.1.0`
6. `curl http://127.0.0.1:8080/healthz` — must be OK.
7. `docker push ghcr.io/USER/ordersvc:0.1.0`
8. `docker buildx imagetools inspect ghcr.io/USER/ordersvc:0.1.0`
9. Write the digest into `RELEASE.md`.
10. In Compose replace `build:` with `image: ...@sha256:...` and `docker compose pull && up`.

If any step fails, do not go further — each is a gate.

### Trace: what `docker push` sends

Assume an image of 3 layers: base 7 MB, ca-certs 1 MB, binary 15 MB.

- First push: sends (almost) everything.
- Second push of the same base + new binary: mostly sends the new layer; the base is deduplicated in the registry.

That is why a stable base tag speeds up push.

### Predict then answer: tag overwrite

**Question:** Push `1.0.0` on Monday (digest A). Push the same tag on Friday (digest B). What does `pull :1.0.0` return on Saturday on a clean machine?

**Answer:** Digest B (the current tag pointer). That is why prod pins A or B explicitly, and does not trust the name.

### Cosign / signing (mention at a high level)

Some teams sign the image (cosign). That is a supply-chain layer above the digest. The course does not teach a fake API — if you introduce signing, read Sigstore/cosign docs. The digest remains the basis of the pin.

### Helm / Kustomize fragment

```yaml
image: ghcr.io/acme/ordersvc
digest: sha256:9f2c1111...
```

or combined `image: ghcr.io/acme/ordersvc@sha256:9f2c...`

Do not mix `tag: latest` with a digest without discipline — one source of truth.

### Rollback exercise

1. Deploy digest A.
2. Deploy digest B (bad).
3. Return values to A.
4. Confirm `/healthz` and the version in the log (print SHA env `VERSION=f00dcafe` in the app).

Without a digest, rollback is “guess which latest.”

### Mini FAQ

**Q: Do I need Docker Hub if I have GHCR?**  
A: No. One registry per org policy.

**Q: Can there be a digest without a registry?**  
A: A local image ID exists, but the cluster pulls from a registry — you need push.

**Q: Why `imagetools` and not just `docker images`?**  
A: Multi-platform manifests and the remote digest are better seen via imagetools.

### Additional mechanism: image naming

Proposed convention:

```text
ghcr.io/<org>/<service>:<semver>
ghcr.io/<org>/<service>:sha-<gitsha>
ghcr.io/<org>/<service>:debug-<gitsha>   # never in prod deploy
```

Semver for people, sha for CI traceability, debug separated.

### Trace: digest in CI summary

```yaml
- name: Summary
  run: |
    echo "image=ghcr.io/acme/ordersvc:${{ github.sha }}" >> $GITHUB_STEP_SUMMARY
    echo "digest=${{ steps.build.outputs.digest }}" >> $GITHUB_STEP_SUMMARY
```

People see the digest in the Actions UI without digging through logs.

### Predict then answer: two registries

**Question:** Push to Hub and GHCR of the same binary — are the digests the same?

**Answer:** Layer content can have the same digest (content addressable), but the manifest digest in different registries should be checked per registry. Do not assume; inspect both.

### Rate limit and anonymous pull

Public Hub pull has a rate limit. GHCR/org package permissions differ. For CI use auth even for public pull when possible.

### Additional lab: retag stable

```text
DIGEST=$(docker buildx imagetools inspect ghcr.io/acme/ordersvc:1.0.0 --format '{{.Manifest.Digest}}')
docker buildx imagetools create -t ghcr.io/acme/ordersvc:stable ghcr.io/acme/ordersvc@$DIGEST
```

Stable now points at the same content as 1.0.0.

### Note on package deletion

GHCR package delete permissions and GC policies vary. Do not rely on “I deleted the tag = gone forever” without checking. A digest pin in an old cluster can still pull while the blob exists.

### Extended mechanism: reading the digest in a script

```text
docker buildx imagetools inspect ghcr.io/acme/ordersvc:1.0.0 \
  --format '{{json .Manifest}}'
```

You parse the digest in CI and write it to an artifact file `digest.txt`. The deploy job reads that file. One source of truth.

### Last predict-then-answer

**Question:** `docker pull img@sha256:aaa` then `docker tag img@sha256:aaa img:prod` then push `img:prod` — does `prod` point at `aaa`?

**Answer:** Yes, if the push succeeds and nobody else moves the tag. Still, deploy most safely pins `@sha256:aaa` directly.

A local run confirms the image before publish. The tag names; push sends to the registry; the digest locks the content. Production pins the digest. Secrets and publish ports remain a runtime concern. CI is the preferred path to prod tags.
