# 01.04 Interface types for polymorphism

> **Go Path - Zero to Gopher** / **03 Others → Object-Oriented Programming with Go** / Lesson 01.04

## Lesson goals

After this lesson you will be able to:

- explain implicit satisfaction of an `interface` contract without an `implements` keyword;
- connect the `method set` to whether type `T` or `*T` satisfies a given `interface`;
- design small `interface` types near consumers (often one `method`);
- apply the proverb *accept interfaces, return structs* with conscious exceptions;
- read an `interface` value (type + data) and avoid `nil` traps;
- use `type assertion` and `type switch` only where they are needed;
- build polymorphism without class inheritance — Go **does not** have class inheritance.

## Prerequisite

- Lessons 01.01–01.03: types, `struct`, `method`, `receiver`, encapsulation via `package`, `method set` for `T` and `*T`.
- Go 1.22+ (`go version`).
- Basic `error` contract and reading `io.Reader` / `io.Writer` signatures from the standard library.

If you still mix up value `receiver` and pointer `receiver`, go back to 01.02–01.03 before diving into the `nil` traps here.

## Problem this lesson solves

Without `interface` types, functions depend on concrete `struct` types. Tests spin up a database or network. Adding a new implementation touches every call site.

With *oversized* `interface` types you get a different pain: the mock must “know everything,” while the consumer uses two methods. Implementations lie about the contract.

Classic OOP offers a class hierarchy. Go **does not** have class inheritance. Instead it offers:

1. small contracts (`interface`);
2. implicit satisfaction;
3. type composition (`embedding` — see 01.03);
4. runtime dispatch via `interface` values.

This lesson teaches that tool from scratch: from declaration, through `method set` rules, to design and traps.

## Mental model

Polymorphism here means: **the same call, different behavior at runtime**, without changing the caller.

```text
concrete value (e.g. Email{})  +  its dynamic type
                    |
                    v
         interface variable
         (type | data)
                    |
                    v
         method call — dispatch by dynamic type
```

The compiler checks: does the type’s `method set` cover every signature in the `interface`? If yes — the type satisfies the contract. There is no `implements` list. Types you did not write (e.g. `*os.File`) can satisfy your local contract.

### Terminology

| Term (English) | What it means here | Typical mental mistake |
|----------------|--------------------|-------------------------|
| `interface` | Named set of `method` signatures — a contract | “A class without a body” |
| `method` | Function with a `receiver` | “Virtual function from C++” |
| `receiver` | Type before the `method` name | Mixing value / pointer |
| `method set` | Set of methods the type offers | Forgetting that `T` and `*T` are not the same |
| `pointer` | Address of a value | “Pointer receiver is always better” |
| `struct` | Concrete type with fields | Returning an `interface` “just in case” |
| `embedding` | Including a type in a `struct` or `interface` | Confusing it with a class tree |
| `promotion` | Methods from `embedding` “surface” outward | Expecting override semantics |
| `type assertion` | Extracting a concrete type from an `interface` | Using it instead of a better API |
| `type switch` | Branching on dynamic type | Replacing a strategy with a small contract |
| `zero value` | Default value of a type | Confusing it with an “empty” `interface` |
| `package` | Unit of encapsulation | Hiding via private fields in another package |

Remember the dual nature:

- **Static**: the compiler checks satisfaction.
- **Dynamic**: an `interface` variable carries type + value; the call picks the implementation at runtime.

## Mechanism

This section is the heart of the lesson. Go in order: declaration → satisfaction → `method set` → `interface` value → `nil` → design → `type assertion` / `type switch`.

### 1. Declaring an `interface`

```go
package notify

type Notifier interface {
	Notify(msg string) error
}
```

That is not a class. It is a **list of signatures**. A type that has a `method` with the same name, parameters, and results satisfies `Notifier`.

Empty contract:

```go
var anything any // alias for interface{}
```

`any` accepts every value. You lose static guarantees. Use it rarely (boundaries, reflection), not as the default “polymorphism.”

### 2. Implicit satisfaction

```go
package notify

import "fmt"

type Email struct{ Addr string }

func (e Email) Notify(msg string) error {
	fmt.Printf("email %s: %s\n", e.Addr, msg)
	return nil
}

type Slack struct{ Channel string }

func (s Slack) Notify(msg string) error {
	fmt.Printf("slack #%s: %s\n", s.Channel, msg)
	return nil
}

func Broadcast(n Notifier, msg string) error {
	return n.Notify(msg)
}
```

`Email` and `Slack` **nowhere** write that they implement `Notifier`. The compiler sees it from the `method set`.

#### Trace — assignment and call

```text
Broadcast(Email{Addr: "a@b.c"}, "hi")
  1. Compiler: Email.method set contains Notify(string) error? YES.
  2. An interface value is built:
       type     = Email
       data     = Email{Addr: "a@b.c"}
  3. Inside Broadcast: n.Notify("hi")
  4. Runtime picks Email.Notify
  5. Prints "email a@b.c: hi"
```

The same `Broadcast` with `Slack{Channel: "ops"}` picks `Slack.Notify`. The caller does not change. That is polymorphism without a class tree — Go **does not** have class inheritance.

### 3. The `method set` decides who passes

From 01.02–01.03:

- The `method set` of type `T` contains methods with value `receiver` `(T)`.
- The `method set` of type `*T` contains methods with value `receiver` `(T)` **and** pointer `receiver` `(*T)`.

Consequence for `interface`:

> If the contract requires a `method` that exists only with a pointer `receiver`, a value of type `T` **does not** satisfy that contract. The address `*T` does.

#### Concrete example — `T` fails, `*T` passes

```go
package store

type Counter interface {
	Inc()
	Value() int
}

type tally struct{ n int }

func (t *tally) Inc()     { t.n++ }
func (t *tally) Value() int { return t.n }

func bump(c Counter) {
	c.Inc()
}
```

Try this:

```go
var t tally
// bump(t)   // DOES NOT COMPILE: tally has no Inc in method set
bump(&t)     // OK: *tally satisfies Counter
```

#### Predict, then check — satisfaction

**Code:**

```go
package main

import "fmt"

type Speaker interface {
	Speak() string
}

type Dog struct{ Name string }

func (d *Dog) Speak() string {
	return d.Name + " woof"
}

func say(s Speaker) {
	fmt.Println(s.Speak())
}

func main() {
	d := Dog{Name: "Rex"}
	// A) say(d)
	// B) say(&d)
	_ = d
}
```

**Predict:**

1. Does line A compile?
2. Does line B compile?
3. Why?

**Check** (enable B, run):

```text
go run .
# with B: Rex woof
# with A: compile error — Dog does not implement Speaker
#         (Speak method has pointer receiver)
```

**Why:** `Speak` is on `*Dog`. The `method set` of type `Dog` is empty for that signature. The `method set` of type `*Dog` contains `Speak`. Only `&d` (or another `*Dog` value) fits into `Speaker`.

#### Trace — what the compiler “sees”

```text
interface Speaker { Speak() string }

method set(Dog):
  (no Speak)

method set(*Dog):
  Speak() string   ← from func (d *Dog) Speak()

Conclusion:
  Dog  ⊭ Speaker
  *Dog ⊨ Speaker
```

Remember the reverse direction: if the `method` is on a value `receiver`, both `T` and `*T` satisfy the contract (because `*T` includes value methods).

```go
func (d Dog) Speak() string { return d.Name + " woof" }

var d Dog
say(d)  // OK
say(&d) // OK — *Dog also has Speak
```

### 4. What is an `interface` value

An `interface` variable is not “just a pointer to an object.” Conceptually it carries:

```text
interface value = (dynamic type, dynamic data)
```

- Dynamic type: which concrete type is inside (`Email`, `*tally`, …).
- Dynamic data: a copy of the value or a `pointer`, depending on what you assigned.

Two “empty” states people confuse:

1. **`interface` is `nil`**: no type, no data.
2. **`interface` holds a type, but the data is a `nil` `pointer`**: the `interface` **is not** `nil`.

#### Predict, then check — `nil` trap

**Code:**

```go
package main

import (
	"bytes"
	"fmt"
	"io"
)

func main() {
	var r io.Reader
	fmt.Println("1:", r == nil)

	var b *bytes.Buffer // zero value pointer: nil
	r = b
	fmt.Println("2:", r == nil)
	fmt.Printf("3: type=%T data=%v\n", r, r)
}
```

**Predict** what 1, 2, 3 print.

**Check:**

```text
1: true
2: false
3: type=*bytes.Buffer data=<nil>
```

**Why:** after `r = b`, `r` has type `*bytes.Buffer` and data `nil`. Comparing `r == nil` asks whether the **entire** `interface` is empty. It is not — the type is present. Hence `false`.

#### Trace — assigning a `nil` pointer into an `interface`

```text
var r io.Reader          // (type=nil, data=nil)  → r == nil
var b *bytes.Buffer      // b == nil
r = b                    // (type=*bytes.Buffer, data=nil)
r == nil?                // false — type is not nil
r.Read(...)              // panic: nil pointer dereference
                         //   (call goes to *bytes.Buffer.Read with nil receiver)
```

Classic production bug: a function returns `(io.Reader, error)`, in the `error` branch it does `return broken, err` where `broken` is type `*MyReader` and `nil`. The caller sees `err != nil` or, worse, `r != nil` and calls `Read` and gets a panic.

Fix: return an **unnamed** `nil` for the `interface` result:

```go
func open() (io.Reader, error) {
	var b *bytes.Buffer
	if b == nil {
		return nil, fmt.Errorf("no buffer") // nil interface
	}
	return b, nil
}
```

Not:

```go
return b, fmt.Errorf("no buffer") // b is typed nil → interface is not nil
```

### 5. Small `interface` types

The standard library shows the style:

| Contract | Methods | Why it works |
|----------|---------|--------------|
| `io.Reader` | `Read([]byte) (int, error)` | Huge ecosystem; one capability |
| `io.Writer` | `Write([]byte) (int, error)` | Same |
| `fmt.Stringer` | `String() string` | Print, logs |
| `error` | `Error() string` | All of error handling |

One `method` is often enough. Small contract = easy mocks, clear responsibility, composition instead of a fat “god.”

#### Trace — consumer chooses the contract

```text
Handler needs only Find(id) ([]byte, error)
  → local interface Store { Find(...) }
  → production: *Postgres with 20 methods — OK, has Find
  → test: fake with one method — OK
  → you do not pull UserRepository with Migrate/WithTx into the handler
```

### 6. Accept interfaces, return structs

Proverb:

- **Accept** an `interface` → flexible input, easy testing.
- **Return** a concrete type (`struct` or `*Struct`) → caller sees the full API.

```go
package archive

import "io"

type TarWriter struct {
	w io.Writer
	n int64
}

func NewTarWriter(w io.Writer) *TarWriter {
	return &TarWriter{w: w}
}

func (t *TarWriter) Write(p []byte) (int, error) {
	n, err := t.w.Write(p)
	t.n += int64(n)
	return n, err
}

func (t *TarWriter) Written() int64 { return t.n }
```

#### Trace — why not return `io.Writer` here

```text
NewTarWriter returns io.Writer
  → caller sees only Write
  → Written() disappears from the type
  → or you type-assert back to *TarWriter (bad smell)

NewTarWriter returns *TarWriter
  → Write + Written available
  → inside still depends on io.Writer (good input)
```

Exception: deliberately hiding the implementation (`NewSigner() Signer`) when you truly swap the type behind the contract or export only a capability. That is a decision, not a default reflex.

### 7. Where to declare the contract

Idiom: **the `interface` lives with the consumer**, not with the implementation.

```go
package report

type Store interface {
	Find(id string) ([]byte, error)
}

func Build(s Store, id string) (string, error) {
	raw, err := s.Find(id)
	if err != nil {
		return "", err
	}
	return string(raw), nil
}
```

`Store` is in `report`. The database package does not need to know about `report`. The database exports `*DB` with the full API; `report` asks only for `Find`.

#### Predict, then check — fat contract

**Code (anti-example):**

```go
package users

type Repository interface {
	Create(u User) error
	Update(u User) error
	Delete(id string) error
	Find(id string) (User, error)
	FindAll() ([]User, error)
	Search(q string) ([]User, error)
	Count() (int, error)
	WithTx(fn func(Repository) error) error
	Migrate() error
}
```

**Predict:** how many methods must a mock implement for a handler that only calls `Find`?

**Check:** everything except `Find` is noise. Split:

```go
type Finder interface {
	Find(id string) (User, error)
}

type Writer interface {
	Create(u User) error
	Update(u User) error
	Delete(id string) error
}
```

The read handler accepts `Finder`. The test mock has one `method`.

### 8. Composing `interface` types

`embedding` at the contract level merges signatures:

```go
package pipe

import "io"

type ReadWriter interface {
	io.Reader
	io.Writer
}
```

That is not a class tree. It is a union of methods. The type must satisfy **both**.

```go
func CopyClose(dst io.Writer, src io.ReadCloser) error {
	defer src.Close()
	_, err := io.Copy(dst, src)
	return err
}
```

You ask for exactly `ReadCloser` — read + `Close`. You do not ask for a larger file API.

### 9. Compile-time check (optional)

In the implementation package:

```go
var _ io.Reader = (*MyType)(nil)
```

If `*MyType` loses `Read`, the compiler fails immediately. Useful for types you pass into standard functions when you want an early signal.

### 10. `type assertion` — briefly

When you already have an `interface` and *must* have the concrete type:

```go
func sizeHint(r io.Reader) int {
	if s, ok := r.(io.Seeker); ok {
		cur, _ := s.Seek(0, io.SeekCurrent)
		end, _ := s.Seek(0, io.SeekEnd)
		_, _ = s.Seek(cur, io.SeekStart)
		return int(end)
	}
	return -1
}
```

The form `x.(T)` panics if the type does not match. The form `v, ok := x.(T)` is safe.

#### Trace — assertion

```text
r dynamic type = *os.File
r.(io.Seeker)
  → *os.File satisfies Seeker? YES
  → ok=true, s is *os.File as Seeker

r dynamic type = bytes.Buffer (value) via wrapper without Seek
  → ok=false
```

Do not use assertion as a substitute for a small contract. If the consumer always asserts to the same type, return that type directly.

### 11. `type switch` — briefly

```go
func describe(v any) string {
	switch x := v.(type) {
	case nil:
		return "nil"
	case string:
		return "string:" + x
	case int:
		return fmt.Sprintf("int:%d", x)
	default:
		return fmt.Sprintf("other:%T", x)
	}
}
```

Useful at boundaries (`JSON`, plugin registry). In the domain core, prefer a small `interface` with one `method` over a `switch` on types.

### 12. Polymorphism without a class tree

Go **does not** have class inheritance. You build behavior chains through composition:

```go
package logio

import (
	"io"
	"log"
)

type counted struct {
	w io.Writer
	n *int64
}

func (c counted) Write(p []byte) (int, error) {
	n, err := c.w.Write(p)
	*c.n += int64(n)
	log.Printf("wrote %d", n)
	return n, err
}

func Meter(w io.Writer, n *int64) io.Writer {
	return counted{w: w, n: n}
}
```

#### Trace — decorator chain

```text
file := os.Create("out.gz")
gz := gzip.NewWriter(file)      // io.Writer
m := Meter(gz, &n)              // io.Writer
m.Write([]byte("hi"))
  → counted.Write
    → gzip.Writer.Write
      → *os.File.Write
```

All speak `io.Writer`. No `extends`. No virtual tables you declare through a hierarchy. There is contract + satisfaction + composition.

### 13. `interface` and `embedding` / `promotion` (short tie-in)

When a `struct` uses `embedding` of another type, `promotion` can “deliver” methods into the `method set`:

```go
type LoggedBuffer struct {
	bytes.Buffer // embedding
}

// LoggedBuffer gets Write, Read, ... through promotion
var _ io.Writer = (*LoggedBuffer)(nil)
```

That is not override like in classes. If you add your own `Write`, you hide the promoted one — document carefully. Details of `embedding` stay in 01.03; here what matters: promotion changes the `method set`, and the `method set` changes satisfaction.

### 14. Mechanism as a whole — one decision map

```text
Need runtime choice of behavior?
  NO → concrete type, plain function
  YES → is the contract small and clear?
         NO → narrow the contract (split)
         YES → declare interface at the consumer
              accept interface, return struct
              check method set (T vs *T)
              beware typed nil
```

## Rules and syntax

### Declaration

```go
type I interface {
	M()
	N() error
}
```

### Embedding contracts

```go
type ReadWriter interface {
	io.Reader
	io.Writer
}
```

### Empty contract

```go
type empty interface{} // same as any
```

### Satisfaction

There is no `implements`. A type passes if its `method set` covers all signatures (names + parameter/result types; parameter names are not part of the signature).

### Compiler check

```go
var _ I = (*MyType)(nil)
var _ I = MyType{} // only if value receivers cover I
```

### `type assertion`

```go
t := x.(T)       // panic if it fails
t, ok := x.(T)   // ok=false if it fails
```

### `type switch`

```go
switch v := x.(type) {
case T:
	// v is T
case S:
	// v is S
default:
	// ...
}
```

### Comparison with `nil`

```go
var i I
i == nil          // true — empty interface

var p *T
i = p
i == nil          // false if type is stored
```

### Naming

| Pattern | Example | Note |
|---------|---------|------|
| capability `-er` | `Reader`, `Notifier` | Prefer |
| verb as method | `ServeHTTP` | HTTP contract |
| local short name | `store`, `sink` | OK in one file |
| avoid | `IUser`, `UserInterface` | Noise from other languages |

## Examples

### Example 1: Implicit satisfaction

```go
package notify

import "fmt"

type Notifier interface {
	Notify(msg string) error
}

type Email struct{ Addr string }

func (e Email) Notify(msg string) error {
	fmt.Printf("email %s: %s\n", e.Addr, msg)
	return nil
}

type SMS struct{ To string }

func (s SMS) Notify(msg string) error {
	fmt.Printf("sms %s: %s\n", s.To, msg)
	return nil
}

func Broadcast(n Notifier, msg string) error {
	return n.Notify(msg)
}
```

#### What happens here

`Broadcast` does not know about `Email` or `SMS`. Adding `Push` does not touch the `Broadcast` signature. Polymorphism is on the contract, not on a hierarchy — Go **does not** have class inheritance.

#### Predict, then check

What happens if you change `SMS.Notify` to a pointer `receiver` `func (s *SMS) Notify...` and call `Broadcast(SMS{To: "1"}, "x")`?

**Predict:** compiler error — `SMS` no longer satisfies `Notifier`.

**Check:** yes; pass `&SMS{To: "1"}` or restore a value `receiver`.

### Example 2: `method set` wall

```go
package main

import "fmt"

type Incrementer interface {
	Inc()
}

type C struct{ n int }

func (c *C) Inc() { c.n++ }

func run(i Incrementer) { i.Inc() }

func main() {
	var c C
	// run(c)  // error
	run(&c)
	fmt.Println(c.n) // 1
}
```

#### Trace

```text
run(c):
  requires method set(C) ⊇ {Inc()}
  Inc is on *C → NO

run(&c):
  method set(*C) ⊇ {Inc()} → YES
  interface = (*C, &c)
  Inc mutates c.n via pointer receiver
```

### Example 3: Accept interfaces, return structs

See `TarWriter` in Mechanism. Extension — test input:

```go
package archive_test

import (
	"bytes"
	"testing"

	"example.com/archive"
)

func TestWritten(t *testing.T) {
	buf := &bytes.Buffer{}
	tw := archive.NewTarWriter(buf)
	_, _ = tw.Write([]byte("abc"))
	if tw.Written() != 3 {
		t.Fatalf("got %d", tw.Written())
	}

```

Input is `*bytes.Buffer` as `io.Writer`. Output is `*TarWriter` — `Written()` remains.

### Example 4: Local contract at the consumer

```go
package billing

type ChargeStore interface {
	Charge(userID string, cents int) error
```

Production sends `*StripeClient`. Test sends:

### Example 5: `nil` trap in an API

```go
package fetch

import (
	"fmt"
	"io"
)

type boom struct{}

func (b *boom) Read(p []byte) (int, error) {
	return 0, io.EOF
}

func Open(ok bool) (io.Reader, error) {
	var b *boom
	if !ok {
		// BAD: return b, fmt.Errorf("nope")
		return nil, fmt.Errorf("nope")
	}
	b = &boom{}
	return b, nil
}
```

#### Predict, then check

If in the `!ok` branch you return `b, err` (where `b` is still `nil` `*boom`), what is `r == nil` at the caller after `r, err := Open(false)`?

**Predict:** `false`.

**Check:** yes — typed `nil` inside. Hence always `return nil, err` for an `interface` result.

### Example 6: Decorator via a small contract

```go
package limit

import "io"

type limited struct {
	r io.Reader
	n int64
}

func (l *limited) Read(p []byte) (int, error) {
	if l.n <= 0 {
		return 0, io.EOF
	}
	if int64(len(p)) > l.n {
		p = p[:l.n]
	}
	n, err := l.r.Read(p)
	l.n -= int64(n)
	return n, err
}

func Limit(r io.Reader, n int64) io.Reader {
	return &limited{r: r, n: n}
}
```

Same pattern as `io.LimitReader`. Polymorphism + composition.

## Decision analysis

**When to introduce an `interface`?**

- You have (or clearly expect) multiple implementations.
- Tests need a substitute without heavy infrastructure.
- You write a library that accepts I/O or plugin points.

**When not to introduce one?**

- One concrete type, one package, no test that suffers.
- Speculative abstraction “might need it later.”

**Where to declare?**

- Near the consumer. Duplicating small contracts is cheaper than one fat contract in `shared`.

**Return an `interface` from a constructor?**

- Only when you intentionally hide the type or return one of several types under the same contract.
- Otherwise return `struct` / `*Struct`.

**Value or pointer `receiver` for the implementation?**

- If the `method` mutates state → pointer.
- If the contract must accept both value and pointer → value `receiver` (both pass).
- If you mutate, document that the consumer must pass `*T`.

**`type assertion` or a new contract?**

- If several types share a capability → new small `interface`.
- If it is a one-off boundary → assertion / `type switch` OK.

## Trade-offs

| Choice | Advantage | Cost |
|--------|-----------|------|
| Small `interface` | testability, clarity | more names |
| Large `interface` | “everything in one place” | heavy mocks, breaking change when extended |
| Return `struct` | full API | tighter coupling to concrete type |
| Return `interface` | hidden implementation | narrower API, frequent asserts |
| Contract at consumer | independence from implementation | possible minor duplication |
| Contract at implementation | “single source of truth” | fat API, false dependency |
| Value `receiver` | both `T` and `*T` pass | no mutation on a copy |
| Pointer `receiver` | mutation, large `struct` | only `*T` satisfies contract |

Extending an **exported** `interface` type with a new method is a **breaking change** for every implementation outside your module. That is why the standard library prefers new contracts (`io.ReadCloser`) over extending old ones.

## Common mistakes

1. Introducing an `interface` before the first real need (speculative abstraction).
2. Keeping a fat contract in the implementation package (15 methods “for everything”).
3. Returning an `interface` then `type assert`ing back to the same `struct`.
4. Comparing `interface == nil` without understanding typed `nil` inside.
5. Ignoring the `method set`: expecting `T` to satisfy a contract that requires a pointer `receiver`.
6. Naming `IService` / `ServiceInterface` instead of a capability (`Finder`).
7. Using `any` + assert where a small contract or generics (01.05) works better.
8. Extending a public `interface` with a new method without thinking about breaking change.
9. Returning a typed `nil` pointer as an `interface` error.
10. Writing a `type switch` in the domain core instead of a strategy with one method.

## Idiomatic Go

- `io.Reader` style: one `method` where you can.
- Proverb: *accept interfaces, return structs*.
- `var _ Interface = (*Type)(nil)` when you want an early compile signal.
- Do not invent a contract for every `struct` up front.
- Prefer standard contracts (`error`, `fmt.Stringer`, `io.*`) over private clones.
- Declare the contract where it is consumed.
- Document whether the implementation requires a pointer (mutation).
- On `error` paths return plain `nil` for `interface` results.

## Practical scenario

A payment service depends on `*sql.DB` directly. Unit tests spin up Docker with Postgres for every trivial case. CI takes minutes per package.

Refactor:

```go
package pay

import (
	"context"
	"database/sql"
)

type Executer interface {
	ExecContext(ctx context.Context, query string, args ...any) (sql.Result, error)
}

func MarkPaid(ctx context.Context, db Executer, id string) error {
	_, err := db.ExecContext(ctx, `UPDATE payments SET paid=true WHERE id=$1`, id)
	return err
}
```

#### Trace — before / after

```text
BEFORE:
  Handler → *sql.DB
  Test → Docker Postgres
  CI → slow, fragile

AFTER:
  Handler → Executer
  Production → *sql.DB or *sql.Tx (both have ExecContext)
  Test → fake Executer that records query
  CI → seconds
```

The team did not introduce a “UserRepository” with twenty methods. They introduced **one** capability the handler actually calls. That is Go polymorphism in practice.

## Check questions

1. How does a type satisfy an `interface` in Go without `implements`?
2. Why does a value of type `T` not have to satisfy a contract that requires a pointer `receiver` method?
3. What does *accept interfaces, return structs* mean?
4. Why does `var r io.Reader = (*bytes.Buffer)(nil)` give `r == nil` as `false`?
5. Where should you declare a small contract — at the consumer or at the implementation — and why?
6. How does Go achieve polymorphism if it **does not** have class inheritance?

## Summary

Go polymorphism rests on implicit, small `interface` contracts and a precise understanding of `method set` rules. Declare contracts where they are consumed, accept `interface`, return `struct`, beware typed `nil`, and introduce abstraction only when pain outweighs speculation. There is no class inheritance — there is contract, composition, and discipline.
