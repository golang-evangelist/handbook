# 01.02 Using Methods to Define Behavior

> **Go Path - Zero to Gopher** / **03 Others → Object-Oriented Programming with Go** / Lesson 01.02

## Lesson goals

After this lesson you will be able to:

- define a `method` with value and `pointer` `receiver`;
- explain the *method set* for `T` and `*T` and how that affects `interface`;
- choose a `receiver` deliberately (mutation, copy, consistency, type size);
- predict automatic adjustment at *call* time (`T` ↔ `*T`) and why that *does not* apply to satisfying an `interface`;
- understand method `promotion` through `embedding` and where the method set becomes intricate;
- avoid classic mistakes around copying structs and `nil` `pointer` `receiver`.

## Prerequisite

- Lesson 01.01 (Go is not class OOP; types + `method` + `interface`; Go has no class inheritance).
- Solid use of `pointer` (`&x`, `*p`) and addressability.
- Go 1.22+.

## Problem this lesson solves

Without a clear `receiver` model, methods “sometimes work”: state does not change because you copied a value; a type does not satisfy an `interface` because the method set does not match; or you mix value and `pointer` methods without rules. This lesson sets the mechanics of type behavior — the core of Go’s tool for “object-like” behavior without classes.

The goal is not to memorize magical exceptions. The goal is that at any moment you can answer: *which type is the receiver, what is in the method set, am I mutating a copy or shared state*.

## Mental model

A `method` is a function whose first argument is a *receiver*, embedded in the signature:

```text
func (receiver Type) Name(args) results
```

Two layers of rules people mix up:

1. **Method call** — the compiler often auto-inserts `&x` or `*p` so the call succeeds.
2. **Method set / interface** — strict type rules; no “automatic” satisfaction.

```text
  method set(T)  = { methods with receiver T }
  method set(*T) = { methods with receiver T } ∪ { methods with receiver *T }
```

So `*T` “can do more” than `T` when we look at `interface`. Remember briefly:

> A value `receiver` is in **both** method sets.  
> A `pointer` `receiver` is **only** in the method set of `*T`.

```text
  value T   --method set-->  { methods on T }
  pointer *T   --method set-->  { methods on T } ∪ { methods on *T }
```

### Table of official terminology (this lesson)

| English term | Role in this lesson |
|--------------|---------------------|
| `method` | function with `receiver` bound to a type |
| `receiver` | declared type of the method’s first argument (`T` or `*T`) |
| `method set` | set of methods a type offers for `interface` |
| `pointer` | address; often `receiver` for mutation |
| `struct` | type whose methods you write most often |
| `interface` | contract; checked via method set |
| `embedding` | unnamed field; pulls in `promotion` |
| `promotion` | methods / fields of inner type available on the outer type |
| `zero value` | e.g. `nil` for `*T`, `0` for numbers |
| `exported` / `unexported` | whether method / field leaves the `package` |
| `error` | common return type from methods that change state |

## Mechanism

### 1. Method declaration

```go
type Counter struct{ n int }

func (c Counter) Value() int { return c.n } // value receiver
func (c *Counter) Inc()      { c.n++ }      // pointer receiver
```

Name the `receiver` short and consistently (`c`, not `this`). The `receiver` type determines which method set the method enters.

#### Trace: two methods, two worlds

| Method | Receiver type | In method set of `Counter`? | In method set of `*Counter`? |
|--------|---------------|----------------------------|------------------------------|
| `Value` | `Counter` | yes | yes |
| `Inc` | `*Counter` | **no** | yes |

### Predict, then check — where Inc lives

**Question:** Does type `Counter` “have” method `Inc` in the method set sense?

**Answer:** No. `Inc` exists as a declaration, and you can call it as `c.Inc()` because `c` is addressable, but the method set of `Counter` **does not** contain `Inc`.

### 2. Call and automatic adjustment

```go
var c Counter
c.Inc()   // equivalent to (&c).Inc()
p := &c
p.Value() // equivalent to (*p).Value()
```

| Call you write | What the compiler does | Condition |
|----------------|------------------------|-----------|
| `c.Inc()` where `Inc` is on `*T` | `(&c).Inc()` | `c` addressable |
| `p.Value()` where `Value` is on `T` | `(*p).Value()` | `p` has type `*T` |
| `x.Inc()` where `x` is not addressable | error | e.g. map element temp value / non-addressable expression |

This *does not* mean `Counter` satisfies an `interface` that requires `Inc()` — for that, look at the method set.

### Predict, then check — map element

```go
m := map[string]Counter{"a": {}}
// m["a"].Inc()  // ?
```

**Question:** Why does `m["a"].Inc()` not compile (with `Inc` on `*Counter`)?

**Answer:** A map element is not addressable. You cannot take `&m["a"]` implicitly. Typical pattern: temporary variable, call, write back — or store `*Counter` in the map.

### 3. Method set and interface — central proof

```go
type Incrementer interface {
	Inc()
}

func bump(i Incrementer) { i.Inc() }

var c Counter
// bump(c)  // does not compile: Counter has no Inc in method set
bump(&c)    // OK: *Counter has Inc
```

#### Compiler trace (conceptual)

| Step | Check | Outcome for `bump(c)` | Outcome for `bump(&c)` |
|-----:|-------|----------------------|------------------------|
| 1 | Which type am I passing? | `Counter` | `*Counter` |
| 2 | Which method set? | only `Value` | `Value` + `Inc` |
| 3 | Look for `Inc()` | missing | present |
| 4 | Satisfies `Incrementer`? | no → error | yes → OK |

Remember the course formulation:

- value `receiver` is in **both** method sets;
- `pointer` `receiver` is **only** in the method set of `*T`;
- so a value **does not** satisfy an `interface` that requires a `pointer` `receiver`.

### Predict, then check — mixed interface

```go
type CounterView interface {
	Value() int
	Inc()
}
```

**Question:** Which of `Counter` and `*Counter` satisfies `CounterView`?

**Answer:** Only `*Counter`. `Value` is in both sets, but `Inc` only in the set of `*Counter`.

### 4. Mutation: why pointer receiver

```go
func (c Counter) IncBroken() { c.n++ }

func (c *Counter) Inc() { c.n++ }
```

#### Trace: IncBroken

| Step | Caller’s `c.n` | Copy inside method |
|-----:|----------------|---------------------|
| before call | 0 | — |
| enter `IncBroken` | 0 | 0 (copy) |
| `c.n++` in method | 0 | 1 |
| return | **0** | discarded |

#### Trace: Inc

| Step | State via `pointer` |
|-----:|---------------------|
| before | 0 |
| `c.n++` | 1 |
| after | **1** |

### Predict, then check — large struct

**Question:** If a `struct` has a large array field and a method only *reads* one field, must you use a value `receiver`?

**Answer:** No. A value `receiver` copies the whole `struct`. For large types you often choose `pointer` even for reads — because of copy cost, with documented semantics.

### 5. When to choose pointer receiver

Choose `*T` when:

- the method changes state;
- the struct is large (avoid copies);
- you want consistency: most methods of the type on `*T`;
- you work with `nil`-able semantics (optional state);
- the type must satisfy an `interface` that includes mutating methods.

### 6. When to choose value receiver

Choose `T` when:

- the method is pure / only reads and the type is small;
- you want immutable semantics at the API boundary;
- the type is naturally by value (small ID, coordinates, `time.Time`-style API);
- you do not want a `nil` `pointer` in play.

### 7. Consistency of method set on one type

Bad: half the methods on `T`, half on `*T` without reason. Good: if there is at least one mutating method, consider putting all methods on `*T` for consistent `interface` satisfaction.

| Style | Example | Effect on interface |
|-------|---------|---------------------|
| Mixed | `Value()` on `T`, `Inc()` on `*T` | only `*T` satisfies contract needing both |
| Consistent `*T` | both on `*T` | clear: works with `*T` |
| Consistent `T` | all on `T`, no mutation | both `T` and `*T` satisfy |

### Predict, then check — consistency

```go
type S struct{ x int }
func (s S) X() int    { return s.x }
func (s *S) Set(v int) { s.x = v }

type SX interface {
	X() int
	Set(int)
}
```

**Question:** Does `var s S; var i SX = s` compile?

**Answer:** No. `Set` is not in the method set of `S`. You need `var i SX = &s`.

### 8. Nil pointer receiver

```go
type Node struct {
	next *Node
	val  int
}

func (n *Node) Len() int {
	if n == nil {
		return 0
	}
	return 1 + n.next.Len()
}
```

Call `(*Node)(nil).Len()` is legal if the method handles `nil`. That is not a “class null object” — it is an agreement that `nil` `receiver` makes sense.

#### Trace: Len on a chain

Let `a -> b -> nil` (two nodes):

| Call | `n` | Returns |
|------|-----|---------|
| `a.Len()` | `&a` | `1 + b.Len()` |
| `b.Len()` | `&b` | `1 + (*Node)(nil).Len()` |
| `nil.Len()` | `nil` | `0` |
| total | | `2` |

### Predict, then check — panic

```go
func (c *Counter) Inc() { c.n++ }
var p *Counter
p.Inc()
```

**Question:** What happens?

**Answer:** Panic on `c.n++` because `c == nil`. The method did not check `nil`. Either disallow `nil`, or handle it explicitly.

### 9. Embedding and method promotion

```go
type Inner struct{}
func (Inner) A()  {}
func (*Inner) B() {}

type Outer struct{ Inner }
```

`promotion` lifts methods:

| Type | Method set (simplified) |
|------|-------------------------|
| `Outer` | `A` (promoted from `Inner`) |
| `*Outer` | `A`, `B` ( `B` via `*Inner` promotion) |

#### Trace: why B is not on Outer

| Question | Answer |
|----------|--------|
| Does `Outer` have field `Inner`? | yes (embedding) |
| Does `Inner` have `B` in its method set? | no — `B` is on `*Inner` |
| Can `Outer` promote `B`? | not directly into method set of `Outer` |
| Can `*Outer`? | yes — takes address of field from `embedding` |

If you design deep `embedding` to mimic class inheritance (which Go does not have), the method set becomes intricate — another reason for explicit composition and small `interface`.

### Predict, then check — promotion and interface

```go
type Flyer interface{ Fly() }
type Bird struct{}
func (b *Bird) Fly() {}

type Robot struct{ Bird }

func takeoff(f Flyer) {}
```

**Question:** Does `takeoff(Robot{})` compile? Does `takeoff(&Robot{})` compile?

**Answer:** `Robot{}` — no (`Fly` not in method set of `Robot`). `&Robot{}` — yes (`*Robot` gets `Fly` by promotion).

### 10. Value in list / slice and mutation

```go
type Item struct{ n int }
func (i *Item) Inc() { i.n++ }

items := []Item{{}, {}}
for i := range items {
	items[i].Inc() // OK: items[i] is addressable
}
```

#### Trace

| Index | Before | After `Inc` |
|------:|--------|-------------|
| 0 | 0 | 1 |
| 1 | 0 | 1 |

Anti-pattern:

```go
for _, it := range items {
	it.Inc() // changes copy it, not slice element
}
```

### Predict, then check — range copy

**Question:** After `for _, it := range items { it.Inc() }`, what are `items[0].n` and `items[1].n` if they were 0 before?

**Answer:** Still 0. `it` is a copy of the element; `Inc` mutates that copy (via `pointer` to that copy).

### 11. Method value and method expression

```go
c := Counter{n: 1}
mv := c.Value      // method value: bound to c (closure over receiver)
fmt.Println(mv())  // 1

me := (*Counter).Inc // method expression: ordinary function
me(&c)
```

| Form | Type | Use |
|------|------|-----|
| `c.Value` | `func() int` | callback bound to concrete value |
| `(*Counter).Inc` | `func(*Counter)` | explicit `receiver` argument |

This helps you see: a `method` *is* a function with a hidden first argument.

### 12. Exported methods and API surface

Only methods with an uppercase initial letter leave the `package`. Keep internal helpers `unexported`:

```go
func (a *Account) Withdraw(amount int64) error {
	if err := a.ensurePositive(amount); err != nil {
		return err
	}
	a.balance -= amount
	return nil
}

func (a *Account) ensurePositive(amount int64) error { /* ... */ }
```

`ensurePositive` is not part of the public contract. It is part of behavior encapsulation (with fields from 01.03).

### 13. Complete trace: from declaration to interface call

```go
type Account struct{ balance int64 }

func (a Account) Balance() int64         { return a.balance }
func (a *Account) Withdraw(x int64) error {
	if x > a.balance {
		return fmt.Errorf("insufficient funds")
	}
	a.balance -= x
	return nil
}

type Purse interface {
	Balance() int64
	Withdraw(int64) error
}

func Spend(p Purse, x int64) error { return p.Withdraw(x) }
```

| Step | Action | Outcome |
|-----:|--------|---------|
| 1 | `a := Account{balance: 100}` | value |
| 2 | `Spend(a, 10)` | **compiler error** — no `Withdraw` in method set of `Account` |
| 3 | `Spend(&a, 10)` | OK |
| 4 | inside `Withdraw` | `balance` becomes 90 |
| 5 | `a.Balance()` | 90 |

### Predict, then check — Balance on pointer works

**Question:** After `p := &a`, does `p.Balance()` work even though `Balance` is declared on `Account`?

**Answer:** Yes. At call time it does `(*p).Balance()`. Also, `Balance` is in the method set of `*Account`.

### 14. Decision: mini flow diagram

```text
Does the method change fields?
  yes -> pointer receiver
  no  -> is the type small and do you want a copy?
           yes -> value receiver
           no -> pointer receiver (copy cost / consistency)

Does the type go into an interface with mutation?
  yes -> expect *T as dynamic type
  no -> T may be enough

Do you use embedding?
  yes -> check method set Outer vs *Outer explicitly
```

### 15. Generic methods? (Go 1.22+)

Rules for `receiver` and method set are stable. Generic methods *on a type* in the form `func (t T) M[U any]()` **do not** exist. Generics go on functions and types (`type parameter`). Do not mix those two mechanisms with OOP behavior of a type.

```go
// OK: generic function
func MapSlice[T any, U any](in []T, f func(T) U) []U { /* ... */ }

// Not supported as a method with its own type parameter on the receiver type
```

### 16. Trace of a bug: “works in test, fails in API”

Common scenario: in a test you call `a.Withdraw(...)` directly (address autocompletion). In production you pass `a` into `Purse` and the compiler stops.

| Context | Works? | Why |
|----------|--------|-----|
| Direct call `a.Withdraw` | yes (addressable) | autocompletion `&` |
| `Purse(a)` | no | method set |
| `Purse(&a)` | yes | `*Account` |

Learn to test the *same* shape that goes into the `interface`, not only direct calls.

### 17. Table: value vs pointer — quick consequences

| Choice | Mutation visible to caller? | In method set of `T`? | In method set of `*T`? | `nil` risk |
|--------|------------------------------|------------------------|-------------------------|------------|
| `func (t T) M()` | no (copy), unless sharing references internally | yes | yes | not via `receiver` |
| `func (t *T) M()` | yes | no | yes | yes |

### Predict, then check — shared slice in value receiver

```go
type Bag struct{ items []string }

func (b Bag) AppendBroken(s string) {
	b.items = append(b.items, s)
}

func (b *Bag) Append(s string) {
	b.items = append(b.items, s)
}
```

**Question:** Why can `AppendBroken` *sometimes* look like it “works,” yet the caller’s slice header stays old?

**Answer:** `append` may reallocate. The new header is written into the **copy** of `Bag`. If the buffer was not reallocated, elements in the shared array may still be visible — which is more dangerous because behavior depends on capacity. So collection mutation goes through `pointer` `receiver`.

### 18. Concrete fail: interface with pointer receiver (repeat with code)

This must “click” before you move on:

```go
package fail

type Touchable interface {
	Touch()
}

type Box struct {
	n int
}

func (b *Box) Touch() { b.n++ }

func use(t Touchable) { t.Touch() }

func Show() {
	var b Box
	b.Touch() // OK: addressable, compiler does (&b).Touch()

	// use(b)  // compile error:
	// Box does not implement Touchable (Touch method has pointer receiver)

	use(&b) // OK
}
```

#### Compiler decision trace for `use(b)`

| Step | Check | Result |
|-----:|-------|--------|
| 1 | Argument type `Box` | — |
| 2 | Method set(`Box`) | empty for `Touch` |
| 3 | Does `Box` implement `Touchable`? | no |
| 4 | Error | yes |

Remember the sentence:

> A value `receiver` is in **both** method sets; a `pointer` `receiver` is **only** in the method set of type `*T`. A value therefore **does not** satisfy an `interface` that requires a `pointer` method.

## Rules and syntax

| Rule | Explanation |
|------|-------------|
| One `receiver` per method | `func (t T) M()` — no language “static method” |
| Short `receiver` name | `c Counter`, not `this` / `self` |
| Method set(`T`) | only value `receiver` |
| Method set(`*T`) | value **and** `pointer` |
| Call ≠ interface | autocompletion on call does not widen method set |
| `nil` `receiver` | allowed; you must handle it explicitly |
| Consistency | if you mutate, prefer `*T` everywhere on the type |

Syntax:

```go
func (t T) M()      {}
func (t *T) N()     {}
func (t *T) E() error { return nil }
```

Calls:

```go
var t T
t.M()
t.N()    // (&t).N()
p := &t
p.M()    // (*p).M()
p.N()
```

### Table: value does not satisfy interface with pointer method

```go
type Touchable interface{ Touch() }
type Box struct{}
func (b *Box) Touch() {}
```

| Expression | Compiles? |
|------------|-----------|
| `var b Box; b.Touch()` | yes (addressable) |
| `var t Touchable = b` | **no** |
| `var t Touchable = &b` | yes |

## Examples

### Example 1: Counter with mixed receivers

```go
package count

type Counter struct{ n int }

func (c Counter) Value() int { return c.n }

func (c *Counter) Inc() {
	if c == nil {
		return
	}
	c.n++
}

func (c *Counter) Add(delta int) {
	if c == nil {
		return
	}
	c.n += delta
}
```

#### What happens here

Read on value; mutation on `pointer`. `nil` is safe for mutators. For an `interface` that requires `Inc`, use `*Counter`.

#### Predict, then check

| Call | `n` after |
|------|-----------|
| `c := Counter{}; c.Inc();` | 1 |
| `var p *Counter; p.Inc();` | (no panic; `n` does not exist on `nil`) |

**Question:** Does `Value` on `nil` `*Counter` panic if you do `(*Counter)(nil).Value()`?

**Answer:** No — `Value` has value `receiver`, so `(*p).Value()` tries to copy `*p`… actually: call `p.Value()` on `nil` `p` does `(*p).Value()` and **panics** on dereference. Careful: autocompletion for value method on `nil` `pointer` can panic.

### Example 2: Interface requires pointer method set

```go
package bump

type Incrementer interface{ Inc() }

type Counter struct{ n int }

func (c *Counter) Inc() { c.n++ }

func Bump(i Incrementer) { i.Inc() }

func Demo() {
	var c Counter
	// Bump(c) // error
	Bump(&c)
}
```

#### What happens here

This is the canonical lesson example: a value **does not** satisfy an `interface` that requires a `pointer` `receiver`.

#### Predict, then check

**Question:** If you change `Inc` to value `receiver` (meaningless for mutation), does `Bump(c)` compile?

**Answer:** Yes, it compiles — but mutation will not stick on the caller. So “compiles” ≠ “works as you want.”

### Example 3: Embedding promotion

```go
package embeddemo

type Inner struct{ n int }

func (i Inner) N() int    { return i.n }
func (i *Inner) Inc()     { i.n++ }

type Outer struct{ Inner }

func Demo() {
	var o Outer
	_ = o.N()
	o.Inc() // works via address Outer -> Inner
	// var inc interface{ Inc() } = o // no
	var inc interface{ Inc() } = &o   // yes
	_ = inc
}
```

#### What happens here

`promotion` allows short call `o.Inc()`, but the method set of `Outer` still does not contain `Inc` for `interface` purposes.

#### Predict, then check

**Question:** Does `o.N()` change anything about copying `Inner`?

**Answer:** `N` only reads; value `receiver` copy is safe. State lives in `o.Inner.n`.

### Example 4: Correct mutation of slice elements

```go
package items

type Item struct{ n int }

func (i *Item) Inc() { i.n++ }

func IncAll(items []Item) {
	for i := range items {
		items[i].Inc()
	}
}
```

#### What happens here

Indexing yields an addressable element. `IncAll` mutates the original `slice` contents.

#### Predict, then check

Trace for `items := []Item{{n:0},{n:0}}` after `IncAll(items)`:

| i | `items[i].n` |
|--:|--------------|
| 0 | 1 |
| 1 | 1 |

**Question:** Must `IncAll` return a new `slice`?

**Answer:** No. Elements are mutated in place. (The `slice` header is copied into the function, but it points at the same array.)

### Example 5: Method expression as ordinary function

```go
package meth

type Point struct{ X, Y int }

func (p *Point) Move(dx, dy int) {
	p.X += dx
	p.Y += dy
}

func Demo() {
	move := (*Point).Move
	pt := &Point{}
	move(pt, 2, 3) // pt = {2,3}
}
```

#### What happens here

`(*Point).Move` is a function of type `func(*Point, int, int)`. You see `receiver` explicitly as the first parameter.

#### Predict, then check

**Question:** What is the type of expression `pt.Move`?

**Answer:** `func(int, int)` — `receiver` is already bound to `pt` (method value).

### Example 6: Defensive nil receiver in a tree

```go
package tree

type Node struct {
	Left, Right *Node
	Val         int
}

func (n *Node) Sum() int {
	if n == nil {
		return 0
	}
	return n.Val + n.Left.Sum() + n.Right.Sum()
}
```

#### What happens here

Recursion stops naturally on `nil`. Without the check you would panic on `n.Val`.

#### Predict, then check

Tree: root 5, left 3, right nil.

| Call | Returns |
|------|---------|
| `root.Sum()` | `5 + 3 + 0 = 8` |

**Question:** May `(*Node)(nil).Sum()` be called?

**Answer:** Yes; returns `0`.

## Decision analysis

**Value or pointer?** First ask: do I mutate? Second: how big is the copy? Third: which `interface` must I satisfy?

**Mix receiver types?** Only when there is a strong reason (e.g. small immutable type with rare mutator on `*T`). Otherwise consistency wins.

**Embedding for brevity?** OK for small, clear compositions. Bad as replacement for class inheritance — Go has no class inheritance; do not build pyramids for `promotion`.

**Nil receiver?** Use when `nil` has domain meaning (empty tree, optional resource). Otherwise document that `receiver` must not be `nil`.

## Trade-offs

| Choice | You gain | You pay |
|--------|----------|---------|
| `pointer` receiver | mutation, cheaper for large types | `nil`, method set stricter for values |
| value receiver | simple copy, no `nil` | expensive copy; mutation “silently” fails |
| mixed receivers | micro-optimization / nuance | confusing `interface` |
| `embedding` + `promotion` | shorter calls | intricate method set |
| `nil`-tolerant methods | elegant recursion | hidden control flow |

## Common mistakes

1. **Mutation on value `receiver`** — looks like it works, state stays old.
2. **Expecting `bump(c)` to work because `c.Inc()` works** — call ≠ method set.
3. **`for _, v := range` + mutating `v`** — you change a copy.
4. **`Inc` on map element without temporary variable** — not addressable.
5. **Mixing `T` / `*T` without strategy** — half the types do not enter `interface`.
6. **Panic on `nil` `pointer` `receiver`** — no check.
7. **Deep `embedding` for “hierarchy”** — Go has no class inheritance; method set becomes unreadable.
8. **Ignoring copy cost of large `struct`** — value `receiver` everywhere “because it is cleaner.”

## Idiomatic Go

- Short `receiver` name, same across all methods of the type.
- If the type has mutators, prefer `*T` for readers too.
- Check `interface` satisfaction with `var _ I = (*T)(nil)` in the package.
- Document whether `nil` `receiver` is allowed.
- For tests, bind `interface` to the same shape (`*T`) used in production.
- Do not look for generic methods on a type — use generic functions.

Verification patterns in code:

```go
var _ Incrementer = (*Counter)(nil)
// var _ Incrementer = Counter{} // intentionally does not compile — documents decision
```

## Practical scenario

A cart service has `Cart` with `Add` / `Total`. First version: all methods on value `receiver`. QA reports `Add` “does not remember” items. Cause: copy.

Second version: `Add` on `*Cart`, but handler passes `Cart` into `interface{ Add(...); Total() ... }`. Compiler rejects. Team changes handler signature to work with `*Cart` and adds `var _ Basket = (*Cart)(nil)`.

Third trap: `embedding` `Storage` inside `Cart` with `pointer` methods. Value `Cart` in tests “worked” via direct calls, not in HTTP layer. After the method set lesson, tests use `&Cart{}` everywhere.

## Summary

`method` defines type behavior via `receiver`. The method set of `T` contains value methods; the method set of `*T` contains both value and `pointer` methods. So a value does not satisfy an `interface` that requires a `pointer` `receiver` — even when a direct call works thanks to autocompletion. Choose `receiver` by mutation, size, and consistency. `embedding` brings `promotion`, but not class inheritance (which Go does not have). Check contracts with `var _ I = (*T)(nil)` and test the same shape used in production.
