# 01.03 Exploring Data Encapsulation Strategies

> **Go Path - Zero to Gopher** / **03 Others → Object-Oriented Programming with Go** / Lesson 01.03

## Lesson goals

After this lesson you will be able to:

- use `unexported` fields and `package`-level visibility as primary encapsulation;
- write idiomatic `NewT` / constructor functions with invariant validation;
- design a safe `zero value` or deliberately forbid it;
- choose getters only when they preserve invariants or prevent leaking internal state;
- place `interface` as a boundary between packages, not as decoration;
- choose what to export (type, fields, methods) without leaking implementation.

## Prerequisite

- 01.01 and 01.02 (types, `method`, method set; Go has no classes or class inheritance).
- Understanding `exported` / `unexported` rules: `Name` versus `name`.
- Go 1.22+.

## Problem this lesson solves

In class-based languages encapsulation is often `private` field + getter/setter. In Go people often either export all fields (“JSON-friendly struct”) or add meaningless getters for every field. Real encapsulation in Go lives at the **package boundary**: `unexported` state, controlled constructor, small `interface` toward the consumer.

Without that, invariants break (`balance < 0`, empty ID, shared internal `slice`), and refactors become expensive because the whole program depended on field layout. This lesson teaches strategies: what to hide, what to export, how to construct, how not to leak references.

## Mental model

```text
  [package domain]
    type with unexported fields
    NewT / ParseT
    methods that preserve invariants
           |
           | export only what is needed
           v
  [package app / api]
    depends on interface or narrow API
```

Encapsulation is not “hide everything.” Encapsulation is: *hide what may change without your control*. An `interface` at the boundary says what the consumer may do, not how you did it.

Three levers:

1. **Name visibility** — uppercase / lowercase (`exported` / `unexported`).
2. **Construction** — `NewT` / `ParseT` as the only door to a valid object.
3. **Behavior boundary** — `interface` at the consumer or narrow exported methods.

### Table of official terminology (this lesson)

| English term | Role |
|--------------|------|
| `package` | unit of visibility; encapsulation boundary |
| `exported` / `unexported` | uppercase / lowercase initial letter |
| `struct` | state holder |
| `zero value` | default value; may be safe or forbidden |
| `pointer` | common return from `NewT` when sharing mutable state |
| `method` / `receiver` | only way to change `unexported` state from outside package |
| `interface` | contract at boundary; hides concrete type |
| `composite literal` | `{...}`; outside package sees only `exported` fields |
| `slice` / `map` | often leak if you return internal buffer |
| `error` | signal failed construction / mutation |
| `module` | dependency version; does not change visibility rules inside `package` |

## Mechanism

### 1. Visibility at package level

- `Account` — type visible to whole program (if `exported`).
- `balance` — field visible only to files in the same `package`.
- `NewAccount` — factory other packages call.

There is no `protected`. Subpackages (`domain/user`) are **different** packages — they do not see parent `unexported` names.

```go
package bank

type Account struct {
	ID      string // exported — consumer can change directly
	balance int64  // unexported — only this package
}
```

#### Trace: who sees what

| Code location | `Account` type | `a.ID` | `a.balance` | `NewAccount` |
|---------------|----------------|--------|-------------|--------------|
| `package bank` | yes | yes | yes | yes |
| other `package` | yes | yes | **no** | yes |
| other `package` if type is `account` (lowercase) | **no** | — | — | only if factory returns `interface` |

### Predict, then check — subdirectory

**Question:** File `bank/savings/savings.go` has `package savings`. Does it see `balance` from `package bank`?

**Answer:** No. Different `package`, even if in a subfolder. Import path ≠ shared visibility.

### 2. Composite literal and exported fields

```go
// in another package:
a := bank.Account{ID: "A1"} // OK
// a := bank.Account{ID: "A1", balance: 10} // error: balance unexported
```

| Expression outside package | Allowed? |
|----------------------------|----------|
| `Account{ID: "x"}` | yes |
| `Account{balance: 1}` | no |
| `a.balance = 1` | no |
| `a.ID = "y"` | yes (because `exported`) |

So: if a field is `exported`, **it is not encapsulated**. There is no “almost private.”

### Predict, then check — JSON tag temptation

**Question:** The team exports all fields for `encoding/json`. What is the cost for invariants?

**Answer:** Every consumer can build an invalid struct literal or unmarshal one. Better: DTO for JSON + domain type with `unexported` fields, or custom `MarshalJSON` / `UnmarshalJSON`.

### 3. Constructor NewT

```go
func NewAccount(id string, opening int64) (*Account, error) {
	if id == "" {
		return nil, fmt.Errorf("empty id")
	}
	if opening < 0 {
		return nil, fmt.Errorf("negative balance")
	}
	return &Account{id: id, balance: opening}, nil
}
```

Conventions:

- `NewT` for type `T`;
- `ParseT` / `Parse` when input is raw string / bytes;
- returns `(*T, error)` or `(T, error)` when validation can fail;
- panic only in rare “must” cases (`template.Must`) — not in ordinary domain code.

#### Trace: success and failure

| Input | Return | State |
|-------|--------|-------|
| `("A1", 100)` | `(*Account, nil)` | `id="A1"`, `balance=100` |
| `("", 100)` | `(nil, error)` | no object |
| `("A1", -1)` | `(nil, error)` | no object |

### Predict, then check — why pointer

**Question:** Why often `*Account` and not `Account` from `NewAccount`?

**Answer:** Shared mutation, clear `nil` with `error`, and method set that includes `pointer` methods. For small immutable types `(T, error)` is often better.

### 4. Zero value design

Every type has a `zero value`. The question is not “does it exist,” but “is it safe to use.”

| Strategy | When | How you enforce |
|----------|------|-----------------|
| Safe `zero value` | `0`, empty string, empty `slice` make sense | you may allow `var t T` |
| Unsafe `zero value` | invariants need valid ID / range | `unexported` fields + `NewT` only |
| `nil` `pointer` as absence | optional state | document; check |

```go
type SKU struct{ code string } // zero value: code ""

func Parse(code string) (SKU, error) {
	if code == "" {
		return SKU{}, fmt.Errorf("empty")
	}
	return SKU{code: code}, nil
}
```

`SKU{}` exists, but the API does not treat it as a valid product code — you enforce `Parse`.

### Predict, then check — zero value Counter

```go
type Counter struct{ n int }
func (c *Counter) Inc() { c.n++ }
```

**Question:** Is `var c Counter; c.Inc()` safe zero value design?

**Answer:** Yes for this type — `n=0` is meaningful. `NewCounter` is not required unless you want a starting value ≠ 0 with validation.

### 5. Getters — when yes, when no

Avoid getters that only return an `exported` field. Use a method when:

- the field is `unexported`;
- you need a computed value;
- you need a **copy** (`slice` / `map`) so the internal buffer does not leak;
- you need synchronization / metrics on read;

```go
func (a Account) Balance() int64 { return a.balance } // makes sense: unexported

func (a Account) GetID() string { return a.ID } // pointless if ID is already exported
```

### 6. Leaking internal slice / map

```go
type Team struct {
	name    string
	members []string
}

func (t Team) Members() []string {
	return t.members // DANGEROUS: caller can change same array
}

func (t Team) MembersCopy() []string {
	out := make([]string, len(t.members))
	copy(out, t.members)
	return out
}
```

#### Leak trace

| Step | Code | Effect on Team |
|-----:|------|----------------|
| 1 | `m := t.Members()` | `m` shares array with `t` |
| 2 | `m[0] = "HACKER"` | `t.members[0]` changed too |
| 3 | with `MembersCopy` | step 2 does not touch internal array |

### Predict, then check — map leak

**Question:** Does `return t.scores` where `scores map[string]int` leak mutability?

**Answer:** Yes. Caller can do `m["x"]=1` and change internal state. Return a copy or expose read-only access via methods.

### 7. Interface as API boundary

The consumer package defines what it needs:

```go
package checkout

type Balancer interface {
	Balance() int64
}

func CanAfford(b Balancer, price int64) bool {
	return b.Balance() >= price
}
```

Implementation stays in `domain`. Consumer does not import internal fields and does not depend on the whole `Account` API.

#### Dependency trace

| Approach | `checkout` depends on | Consequence |
|----------|----------------------|-------------|
| Concrete `*bank.Account` | whole type | tight coupling |
| `Balancer` in `checkout` | one / two methods | loose coupling, easier test |
| Huge `AccountService` interface in `bank` | everything | mock nightmare |

Idiom (proverb): *accept interfaces, return structs* — accept `interface` in parameters, return concrete types from constructors. Polymorphism details in 01.04.

### Predict, then check — where interface lives

**Question:** Must `Balancer` live in `package bank`?

**Answer:** Not necessarily. Often better at consumer (`checkout`), so `bank` does not need to know every contract someone invents.

### 8. Unexported type + exported interface

Strong encapsulation: hide even the type name.

```go
package token

type Signer interface {
	Sign(msg []byte) ([]byte, error)
}

type hmacSigner struct{ key []byte }

func NewHMAC(key []byte) (Signer, error) {
	if len(key) < 32 {
		return nil, fmt.Errorf("key too short")
	}
	k := make([]byte, len(key))
	copy(k, key)
	return &hmacSigner{key: k}, nil
}

func (h *hmacSigner) Sign(msg []byte) ([]byte, error) { /* ... */ }
```

#### Trace

| Outside package | Can? |
|-----------------|------|
| `NewHMAC` | yes |
| `Signer` methods | yes |
| `hmacSigner{...}` | no (type `unexported`) |
| type assertion to concrete type | cannot name type |

### Predict, then check — type assertion

**Question:** Can a consumer do `s.(*hmacSigner)` if `s` comes from `NewHMAC`?

**Answer:** They cannot name `hmacSigner` outside the package. That is intentional.

### 9. Mutators that preserve invariants

```go
func (a *Account) Withdraw(amount int64) error {
	if amount <= 0 {
		return fmt.Errorf("amount must be positive")
	}
	if amount > a.balance {
		return fmt.Errorf("insufficient funds")
	}
	a.balance -= amount
	return nil
}
```

#### Trace: rejected mutation

| Before `balance` | `amount` | After | `error` |
|------------------|----------|-------|---------|
| 100 | 40 | 60 | `nil` |
| 100 | 0 | 100 | non-nil |
| 100 | 150 | 100 | non-nil |

Invariant `balance >= 0` holds. If `balance` were `exported`, consumer could do `a.Balance = -5` (or `a.balance` if visible) and bypass rules.

### 10. Setters — rare, deliberate

A setter makes sense when:

- you change one field with validation;
- you trigger side effects (cache invalidation);
- you keep symmetry with a getter for an `unexported` field.

```go
func (u *User) SetEmail(email string) error {
	if !validEmail(email) {
		return fmt.Errorf("email")
	}
	u.email = email
	return nil
}
```

Do not add `SetX` for every field out of habit. If five fields must change together, prefer one method `UpdateProfile(...)` that preserves a shared invariant.

### Predict, then check — atomicity

**Question:** Why can three setters `SetStreet`, `SetCity`, `SetZIP` break an address?

**Answer:** Caller can leave object half-updated (new city, old ZIP). One method `SetAddress(Address)` validates the whole.

### 11. Package-internal helpers

Inside a package you may read `unexported` fields directly — that is OK. Encapsulation is not for its own sake inside a package, but from *outside*.

```go
func (a *Account) transferTo(other *Account, amount int64) error {
	if err := a.Withdraw(amount); err != nil {
		return err
	}
	return other.Deposit(amount)
}
```

Keep `transferTo` `unexported` if it is not part of public API. Public API may be `Transfer(from, to *Account, amount int64) error` in the same package.

### 12. Complete trace: from NewT to consumer

```go
package bank

type Account struct {
	id      string
	balance int64
}

func NewAccount(id string, opening int64) (*Account, error) { /* validation */ }

func (a Account) ID() string     { return a.id }
func (a Account) Balance() int64 { return a.balance }
func (a *Account) Deposit(int64) error  { /* ... */ }
func (a *Account) Withdraw(int64) error { /* ... */ }
```

```go
package atm

type Purse interface {
	Balance() int64
	Withdraw(int64) error
}

func Dispense(p Purse, amount int64) error {
	return p.Withdraw(amount)
}
```

| Step | Action | Encapsulation |
|-----:|--------|---------------|
| 1 | `acc, err := bank.NewAccount("A1", 200)` | valid object |
| 2 | `atm.Dispense(acc, 50)` | `*Account` satisfies `Purse` |
| 3 | `acc.balance` from `atm` | **unavailable** |
| 4 | after success | `Balance()==150` |
| 5 | try `Account{id:"x"}` from `atm` | does not compile |

### Predict, then check — method set (reminder)

**Question:** Why must `Dispense` receive `*Account`, not `Account`, if `Withdraw` is on `*Account`?

**Answer:** Method set — see 01.02. Encapsulation and method set work together: hide fields, expose mutation via `pointer` methods that enter `interface`.

### 13. Validation in one place

```go
package sku

import (
	"fmt"
	"unicode"
)

type SKU struct{ code string }

func Parse(code string) (SKU, error) {
	if len(code) < 3 || len(code) > 32 {
		return SKU{}, fmt.Errorf("length")
	}
	for _, r := range code {
		if !unicode.IsLetter(r) && !unicode.IsDigit(r) && r != '-' {
			return SKU{}, fmt.Errorf("character")
		}
	}
	return SKU{code: code}, nil
}

func (s SKU) String() string { return s.code }
```

All inputs to the system go through `Parse`. Inside there is no “raw” string pretending to be SKU. That is encapsulation of *meaning*, not only fields.

### 14. DTO versus domain

| Layer | Type | Fields | Why |
|-------|------|--------|-----|
| HTTP JSON | `AccountDTO` | `exported` | serialization |
| Domain | `Account` | `unexported` | invariants |
| Translation | `ToDTO` / `FromDTO` | — | controlled bridge |

Mixing DTO and domain = leaking layout through the whole application.

### Predict, then check — one struct for everything

**Question:** What happens when the same `struct` is used for DB, JSON, and domain?

**Answer:** Tags and `exported` fields dictate the domain. A DB column change breaks API. Encapsulation disappears.

### 15. Encapsulation mechanism checklist

1. Which invariant must not break?
2. Is `zero value` safe?
3. Which fields must be `unexported`?
4. What is the only construction path (`NewT` / `Parse`)?
5. Do methods return shared mutable references?
6. Which `interface` does the consumer see?
7. Does a subpackage wrongly expect “protected” access? (there is none)

## Rules and syntax

| Symbol | Visibility |
|--------|------------|
| `Foo` | `exported` from `package` |
| `foo` | same `package` only |
| field in another package’s `composite literal` | must be `exported` |

```go
type T struct {
	Public  int
	private int
}

func NewT(v int) T {
	return T{Public: v, private: v}
}

func (t T) Private() int { return t.private }
```

### Rules for NewT

| Situation | Signature |
|-----------|-----------|
| Validation can fail | `(T, error)` or `(*T, error)` |
| Never fails (rare) | `T` / `*T` |
| Optional absence | `(*T, error)` with `nil, nil` only if intentional — usually avoid |
| Must panic | only tool `MustParse` with documentation |

### Rules for getters / setters

| You do | When |
|--------|------|
| Getter | `unexported` field or computed value or copy |
| Setter | validation + one field or clear side effect |
| Nothing | field is `exported` and has no invariant — direct access |

## Examples

### Example 1: Account with strict construction

```go
package bank

import "fmt"

type Account struct {
	id      string
	balance int64
}

func NewAccount(id string, opening int64) (*Account, error) {
	if id == "" {
		return nil, fmt.Errorf("empty id")
	}
	if opening < 0 {
		return nil, fmt.Errorf("negative balance")
	}
	return &Account{id: id, balance: opening}, nil
}

func (a Account) ID() string     { return a.id }
func (a Account) Balance() int64 { return a.balance }

func (a *Account) Deposit(amount int64) error {
	if amount <= 0 {
		return fmt.Errorf("amount must be positive")
	}
	a.balance += amount
	return nil
}
```

#### What happens here

Outside the package there is no way to make an `Account` with negative balance without bypassing (unsafe / reflection — out of scope). API enforces `NewAccount` and mutators with `error`.

#### Predict, then check

**Question:** Does `var a bank.Account` in another package compile?

**Answer:** Yes — type is `exported`, `zero value` exists (`id=""`, `balance=0`). If that is a problem, consider `unexported` type + `interface`, or document that only `NewAccount` is supported.

### Example 2: Slice copy on read

```go
package team

type Team struct {
	name    string
	members []string
}

func New(name string, members []string) Team {
	cp := make([]string, len(members))
	copy(cp, members)
	return Team{name: name, members: cp}
}

func (t Team) Members() []string {
	out := make([]string, len(t.members))
	copy(out, t.members)
	return out
}
```

#### What happens here

Both input and output copy the `slice`. Consumer does not share internal array on construction or read.

#### Predict, then check

Trace:

| Step | Action | Internal `members[0]` |
|-----:|--------|----------------------|
| 1 | `in := []string{"Ana"}; t := New("X", in)` | `"Ana"` |
| 2 | `in[0] = "Tina"` | stays `"Ana"` |
| 3 | `m := t.Members(); m[0]="Hack"` | stays `"Ana"` |

**Question:** Why does `New` copy input?

**Answer:** Otherwise caller would hold an alias to the same array and could change “encapsulated” state after construction.

### Example 3: Interface boundary at consumer

```go
package notify

type Addressable interface {
	Email() string
}

func SendWelcome(a Addressable) error {
	_ = a.Email()
	return nil
}
```

```go
package user

type User struct {
	email string
	name  string
}

func New(email, name string) (User, error) { /* validation */ }
func (u User) Email() string               { return u.email }
func (u User) Name() string                { return u.name }
```

#### What happens here

`notify` does not know `User.name`. It depends only on `Email()`. Tests can send a fake type with one method.

#### Predict, then check

**Question:** Must `SendWelcome` take `user.User`?

**Answer:** No — and it should not if you want loose coupling. `Addressable` is enough.

### Example 4: Unexported type behind Signer

```go
package sign

import "fmt"

type Signer interface {
	Sign([]byte) ([]byte, error)
}

type hmacSigner struct{ key []byte }

func NewHMAC(key []byte) (Signer, error) {
	if len(key) == 0 {
		return nil, fmt.Errorf("empty key")
	}
	k := append([]byte(nil), key...)
	return &hmacSigner{key: k}, nil
}

func (h *hmacSigner) Sign(msg []byte) ([]byte, error) {
	// ... HMAC ...
	return append([]byte(nil), msg...), nil // stub
}
```

#### What happens here

Consumer gets `Signer`. Cannot build `hmacSigner` literal. Key is copied at construction.

#### Predict, then check

**Question:** Why `append([]byte(nil), key...)` instead of `k := key`?

**Answer:** `k := key` shares array with caller; caller could wipe key memory after `NewHMAC` and break signing.

### Example 5: Setter with validation

```go
package profile

import "fmt"

type Profile struct {
	displayName string
}

func New(name string) (Profile, error) {
	p := Profile{}
	if err := p.SetDisplayName(name); err != nil {
		return Profile{}, err
	}
	return p, nil
}

func (p Profile) DisplayName() string { return p.displayName }

func (p *Profile) SetDisplayName(name string) error {
	if len(name) < 2 || len(name) > 40 {
		return fmt.Errorf("name length")
	}
	p.displayName = name
	return nil
}
```

#### What happens here

Both construction and later change go through the same length rule. No duplicated condition in two unrelated places — `New` delegates to `SetDisplayName`.

#### Predict, then check

**Question:** Why does `SetDisplayName` have `pointer` `receiver`?

**Answer:** It changes a field; value `receiver` would discard the change.

### Example 6: Safe zero value Buffer-style

```go
package accum

type Sum struct{ total int64 }

func (s *Sum) Add(v int64) { s.total += v }
func (s Sum) Total() int64 { return s.total }
```

#### What happens here

`var s Sum` is valid. No `NewSum`. Encapsulation is not critical for invariants here (any `int64` total is OK), but you can keep `total` `unexported` to force `Add` instead of direct assignment.

#### Predict, then check

**Question:** If you export `Total int64` as a field, what do you lose?

**Answer:** Ability to add metrics / mutex / checks in `Add` later without breaking all `s.Total = ...` assignments in consumer code.

## Decision analysis

**Hide field or not?** If there is an invariant or you want refactor freedom — `unexported`. If it is a pure DTO with no rules — `exported` may be OK.

**NewT always?** No. Safe `zero value` types (`bytes.Buffer` style, small accumulators) may use `var t T`. Domain entities with rules — `NewT`.

**Interface at boundary?** Yes when you have multiple implementations or test doubles. No when you have one implementation and abstraction does not help — then “return structs.”

**Getter for every field?** No. That is Java habit. In Go a getter earns its place.

**Unexported type?** When you want one implementation behind a stable `interface` and do not want anyone depending on the type name.

## Trade-offs

| Choice | You gain | You pay |
|--------|----------|---------|
| `unexported` fields | invariants, refactor | more methods / constructors |
| All `exported` | fast JSON / short code | leak, brittle dependencies |
| Strict `NewT` | valid objects | more ceremony |
| Copying `slice`/`map` | safety | allocations |
| `interface` boundary | testability | indirection, sometimes premature |
| `unexported` type | fortress | harder to extend type from outside |

## Common mistakes

1. **Export all fields for JSON** — mix DTO and domain.
2. **Meaningless getters for `exported` fields** — noise without encapsulation.
3. **Return internal `slice` / `map`** — consumer mutates your state.
4. **Construction without validation** — `composite literal` bypasses rules.
5. **Expecting `protected` in subpackage** — there is none; other `package` is foreign.
6. **Huge `interface` in producer package** — everyone must implement everything.
7. **Per-field setters without atomicity** — object half-updated.
8. **Sharing `[]byte` key / buffer in `NewT`** — alias leak.
9. **Forgetting method set** — `interface` boundary rejects value because mutators are on `*T`.

## Idiomatic Go

- Visibility is at `package` level, not type level.
- `NewT` / `Parse` for invariants; safe `zero value` when it makes sense.
- Accept small `interface`, return concrete struct values / `pointer`.
- Copy mutable collections at boundaries.
- Document whether `zero value` is supported.
- Contract check: `var _ Purse = (*Account)(nil)`.
- Do not simulate class inheritance for “protected” fields — Go has no class inheritance; use `package` boundaries.

## Practical scenario

An e-commerce team has `Order` with `exported` fields. Front end sends JSON straight into domain. Orders appear with negative price and empty ID. Hotfix: validation in HTTP handler — but another entry (gRPC, worker) bypasses handler.

Refactor: `Order` fields `unexported`, `ParseOrder` / `NewOrder`, DTO only in `api` package. `checkout` depends on `interface { Total() int64; ID() string }`. Leak of `[]OrderLine` fixed with copy in getter. Invalid state incidents disappear; tests use fake `Purse` without whole `Order` type.

Second incident: `NewHMAC(key)` kept `key` without copy. Test suite zeroed `buf` after construction and signing “sometimes” failed. Copy in constructor closes the hole.

## Summary

Encapsulation in Go is not `private` inside a class — Go has no classes or class inheritance. Encapsulation is the `package` boundary: `unexported` fields, `NewT`/`Parse` for invariants, methods that do not leak internal `slice`/`map` references, and small `interface` toward the consumer. Design whether `zero value` is safe. Introduce getters and setters only when they preserve rules. Accept `interface`, return struct.
