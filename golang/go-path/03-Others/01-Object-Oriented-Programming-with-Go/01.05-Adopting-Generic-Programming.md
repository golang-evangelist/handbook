# 01.05 Generic programming in Go

> **Go Path - Zero to Gopher** / **03 Others → Object-Oriented Programming with Go** / Lesson 01.05

## Lesson goals

After this lesson you will be able to:

- declare functions and types with a **type parameter** list (Go 1.18+, course targets Go 1.22+);
- write a **type constraint** (including union and `~` approximation);
- use language constraints `any` and `comparable`;
- distinguish when a small `interface` (01.04) is enough, when a type parameter is, and when `any` is the last resort;
- read type inference and know when you must specify type arguments explicitly;
- connect generics with Go’s OOP tools: types, `method`, `interface` — without class inheritance (Go **does not** have class inheritance).

## Prerequisite

- 01.01–01.04: types, `method` / `receiver` / `method set`, `package` encapsulation, small `interface` contracts, *accept interfaces, return structs*.
- Go 1.22+ (`go version`). Generics exist since 1.18; here we assume a modern compiler and standard packages `slices` / `maps` / `cmp` where it makes sense.

If you still mix runtime polymorphism (`interface`) with “same code for several types,” read Mental model twice before Mechanism.

## Problem this lesson solves

Before Go 1.18 libraries chose among:

1. `interface{}` / `any` + `type assertion` (errors at runtime);
2. copy-paste per type (`MinInt`, `MinFloat64`, …);
3. code generation (`go generate`) for type-specialized files.

That yields noise, assertion panics, or heavy tooling. Generics give **compiler** checking for algorithms over a family of types.

But generics are **not** a replacement for OOP polymorphism from 01.04. An `interface` picks behavior at runtime. A type parameter parameterizes an algorithm at compile time. Wrong tool → noisy API or false abstraction.

This lesson teaches the mechanism from scratch and selection criteria: constraint vs `interface` vs `any`, tied back to OOP tools without a class tree.

## Mental model

```text
interface:      "value can do X"           → runtime dispatch
type parameter: "algorithm works for T"    → compile-time specialization
any:            "anything"                 → you lose static checks
```

A type parameter is a **variable for a type**. A type constraint says which types may fill that variable.

```go
func Keys[M ~map[K]V, K comparable, V any](m M) []K
```

Read as: for map `M` (or a type whose underlying type is `map[K]V`), key `K` must be `comparable`, value `V` may be anything; return a `slice` of keys.

### Terminology

| Term (English) | What it means here | Typical mental mistake |
|----------------|--------------------|-------------------------|
| type parameter | Type name in `[T …]` | “Like class T in Java” (not the same) |
| type constraint | What `T` may be | Oversized constraint = fat contract |
| `any` | Constraint “everything” (`interface{}`) | Default style instead of a real contract |
| `comparable` | Types that support `==` / map keys | Forgetting it and wondering why map fails |
| type inference | Compiler deduces type arguments | Forcing `[T]` everywhere |
| generic function | Function with type parameter list | Mixing with an `interface` parameter |
| generic type | `struct` / alias with type parameter | Generic “for every domain struct” |
| `interface` | Runtime method contract (01.04) | Substitute for type parameter |
| `method` / `receiver` | Behavior on a type | Generic method with a *new* parameter (forbidden) |
| `zero value` | `var z T` for unknown `T` | Returning `nil` where `T` is not a pointer |
| `slice` / `map` | Main containers for generic algorithms | `[]any` as “generics” |
| `package` / `module` | Where the API lives | Export before two consumers |

Remember: Go **does not** have class inheritance. Generics do not introduce a type hierarchy. They parameterize code.

## Mechanism

The longest section. Order: function → type → constraint → `~` → `comparable` → inference → generic methods (limits) → tool choice → tie to OOP.

### 1. Generic function

```go
package seq

func First[T any](items []T) (T, bool) {
	var zero T
	if len(items) == 0 {
		return zero, false
	}
	return items[0], true
}
```

- `[T any]` — type parameter list.
- `T any` — `T` may be any type.
- `var zero T` — `zero value` for unknown `T` (for `int` it is `0`, for `string` `""`, for pointer `nil`).

#### Trace — calling `First`

```text
xs := []string{"a", "b"}
v, ok := First(xs)

1. Inference: T = string (from []string)
2. Instance: First[string]
3. zero = ""
4. len>0 → return "a", true
```

Empty input:

```text
var xs []int
v, ok := First(xs)
→ zero=0, ok=false
```

### 2. Generic type

```go
package stack

type Stack[T any] struct {
	items []T
}

func (s *Stack[T]) Push(v T) {
	s.items = append(s.items, v)
}

func (s *Stack[T]) Pop() (T, bool) {
	var zero T
	if len(s.items) == 0 {
		return zero, false
	}
	i := len(s.items) - 1
	v := s.items[i]
	s.items = s.items[:i]
	return v, true
}
```

`Stack[int]` and `Stack[string]` are different types. Methods on the type use the **same** type parameter `T` as the type — they do not introduce a new one.

#### Composite literal

```go
s := Stack[int]{items: []int{1, 2}}
s.Push(3)
```

### 3. Type constraint — more than `any`

When an algorithm uses operators or methods, `any` is not enough.

```go
package ord

type Ordered interface {
	~int | ~int64 | ~float64 | ~string
}

func Max[T Ordered](a, b T) T {
	if a > b {
		return a
	}
	return b
}
```

Here the constraint is itself an `interface` with a **union** of types. That is not a runtime contract from 01.04 in the classic consumer sense — it is the set of types allowed for the compiler. The name `Ordered` documents intent.

#### Predict, then check — operator in constraint

**Code:**

```go
func BadMax[T any](a, b T) T {
	if a > b { // ?
		return a
	}
	return b
}
```

**Predict:** does it compile?

**Check:** no. With `any` the compiler does not know that `>` exists. You need a constraint that guarantees ordered types (or `cmp.Ordered` in newer standard library).

### 4. Approximation `~`

`~int` means: a type whose **underlying** type is `int` (including `int` and `type Cents int`).

```go
type Cents int

func Sum[T ~int](xs []T) T {
	var total T
	for _, x := range xs {
		total += x
	}
	return total
}

_ = Sum([]Cents{10, 20}) // OK because of ~
```

Without `~`, only exact `int` passes — not `Cents`.

#### Trace — `~` decision

```text
constraint: ~int64
type Money int64  → underlying int64 → passes
type int64        → passes
type int          → does not pass
type string       → does not pass
```

### 5. Constraint with methods

A constraint may require methods — then it resembles 01.04, but it still applies at **compile-time** for `T`:

```go
package hashable

type Key interface {
	comparable
	Hash() uint64
}

func Lookup[K Key, V any](m map[K]V, k K) (V, bool) {
	v, ok := m[k]
	return v, ok
}
```

`K` must be `comparable` (because of `map`) **and** have `Hash()`. A type without `Hash` does not qualify — compiler error, not runtime assert.

#### Predict, then check — constraint vs small `interface`

**Scenario A:** you draw on screen; different brushes at runtime.

```go
type Brush interface {
	Paint(x, y int)
}

func Stroke(b Brush, points [][2]int) {
	for _, p := range points {
		b.Paint(p[0], p[1])
	}
}
```

**Scenario B:** you compute `Max` over a `slice` of numbers of different types.

**Predict:** which scenario wants a type parameter?

**Check:** B. A is classic small `interface` (01.04). Generics in A add no benefit — you need runtime choice of implementation.

### 6. `comparable`

Types that support `==` and `!=`, and may be map keys.

```go
package set

type Set[T comparable] map[T]struct{}

func New[T comparable](vals ...T) Set[T] {
	s := make(Set[T], len(vals))
	for _, v := range vals {
		s[v] = struct{}{}
	}
	return s
}

func (s Set[T]) Has(v T) bool {
	_, ok := s[v]
	return ok
}
```

`slice`, `map`, `func` are not `comparable`. A `struct` is if all fields are `comparable`.

#### Trace — why not `any` for Set

```text
Set[T any] + map[T]struct{}
  → error: T is not comparable

Set[T comparable]
  → Set[string], Set[int] OK
  → Set[[]byte] NO
```

### 7. Type inference

The compiler often deduces arguments from parameters:

```go
package infer

func Map[T, U any](in []T, f func(T) U) []U {
	out := make([]U, len(in))
	for i, v := range in {
		out[i] = f(v)
	}
	return out
}

func Demo() []int {
	return Map([]string{"a", "bb"}, func(s string) int { return len(s) })
}
```

#### Trace — inference

```text
Map([]string{...}, func(string) int)
  T ← string
  U ← int
  result []int
```

Explicit when context is insufficient:

```go
var empty []int
// First(empty) — OK, T=int from type of empty
x := First[int](nil) // need [int] because nil has no element type
```

#### Predict, then check — nil slice

**Code:**

```go
package main

import "fmt"

func First[T any](items []T) (T, bool) {
	var zero T
	if len(items) == 0 {
		return zero, false
	}
	return items[0], true
}

func main() {
	// A) v, ok := First(nil)
	// B) v, ok := First[string](nil)
	_ = fmt.Stringer(nil)
}
```

**Predict:** does A compile? B?

**Check:** A no (cannot infer `T`). B yes — returns `""`, `false`.

### 8. Generic methods — language limit

Methods **cannot** have their *own* new type parameters:

```go
// forbidden:
// func (s *Stack[T]) Convert[U any]() Stack[U]
```

`T` from the type is available. New `U` on a method — no. Instead, a generic **function** in the package:

```go
func Convert[T, U any](s Stack[T], f func(T) U) Stack[U] {
	out := Stack[U]{}
	for _, v := range s.items {
		out.Push(f(v))
	}
	return out
}
```

#### Trace — why the limit exists

```text
Receiver type already fixes T (e.g. Stack[int]).
New list [U] on method complicates method set and types.
Language chooses: generic package functions instead of generic methods.
```

### 9. Generic types vs generic functions

| Need | Tool | Example |
|------|------|---------|
| Algorithm over data | generic function | `First`, `Map`, `Unique` |
| Container / state | generic type | `Stack[T]`, `Set[T]`, `Result[T]` |
| Behavior only | `interface` (01.04) | `io.Reader`, `Brush` |
| Unknown type at boundary | `any` + care | JSON decode, reflection |

Do not make `UserService[T]` because it “looks modern.” Generics need a **repeated algorithm or container**, not every domain `struct`.

### 10. When constraint is enough, and when `interface`

**Constraint / type parameter** when:

- you write the same code over `slice` / `map` for several types;
- you need operators (`+`, `<`) or `comparable`;
- you want the compiler to keep the concrete type (`[]int` stays `[]int`).

**Small `interface`** when:

- you need runtime plugin / I/O / strategy;
- implementations change without recompiling the caller in the same dispatch sense;
- proverb *accept interfaces, return structs* solves testability.

**Both together** sometimes:

```go
func WriteAll[T io.Writer](w T, p []byte) (T, error) {
	_, err := w.Write(p)
	return w, err
}
```

Here the constraint requires `Write`, and `T` stays concrete (e.g. `*bytes.Buffer`) so you do not lose other methods — akin to the spirit of “return structs.”

### 11. Why generics beat `any`

```go
package legacy

func UniqueAny(items []any) []any {
	seen := map[any]struct{}{}
	var out []any
	for _, it := range items {
		if _, ok := seen[it]; ok {
			continue
		}
		seen[it] = struct{}{}
		out = append(out, it)
	}
	return out
}

func Unique[T comparable](items []T) []T {
	seen := make(map[T]struct{}, len(items))
	out := make([]T, 0, len(items))
	for _, it := range items {
		if _, ok := seen[it]; ok {
			continue
		}
		seen[it] = struct{}{}
		out = append(out, it)
	}
	return out
}
```

#### Trace — loss of type

```text
UniqueAny([]any{1, "x"})  // mixes types; []any outside
Unique([]int{1, 1, 2})    // []int outside; compiler keeps type
```

`UniqueAny` allows apples and oranges. `Unique[T]` does not.

### 12. Tie to the OOP block

Tools you saw in 01.01–01.04:

1. types and values;
2. `method` + `receiver` + `method set`;
3. `package` encapsulation (exported / unexported);
4. small `interface` + polymorphism — Go **does not** have class inheritance;
5. **now** type parameter + constraint.

Generics **complement** that toolbox. They do not introduce classes. They do not replace `interface` for I/O. They do not solve encapsulation — `package` still hides fields.

```text
OOP question: "who can do X?"        → interface
Generics:     "same code for family T" → type parameter
Boundary:     "unknown type"           → any (rare)
Specialized source per type:           → maybe go generate (next block)
```

### 13. Standard packages since Go 1.21: `slices`, `maps`, `cmp`

These three packages are the everyday form of the generics in this lesson. The course baseline is Go 1.22+, so they are available. There is no separate lesson for them. This section is the bridge.

`slices` and `cmp` have kept the same calls since Go 1.21:

```go
nums := []int{3, 1, 2}
slices.Sort(nums)
fmt.Println(slices.Contains(nums, 2)) // true
fmt.Println(cmp.Compare(2, 5))        // -1
```

`maps.Keys` changed shape:

- Go 1.22: `maps.Keys(m)` returns a `[]K` slice.
- Go 1.23+: `maps.Keys(m)` returns an iterator. Materialize it with `slices.Collect(maps.Keys(m))`, or range over it directly.

```go
ages := map[string]int{"Ana": 30, "Bo": 20}
keys := slices.Collect(maps.Keys(ages)) // Go 1.23+
slices.Sort(keys)
```

On Go 1.22, drop `slices.Collect` and sort the slice that `maps.Keys` already returned.

#### What happens here

1. `slices.Sort` and `slices.Contains` are generic. The compiler infers `int` from the slice. You do not write `slices.Sort[int]`.
2. `cmp.Compare` returns `-1`, `0`, or `1`. `cmp.Ordered` is the constraint for types that support `<`.
3. Prefer these functions over a hand-written `Min` or `Contains`. Write your own generic only when the standard library does not already express the operation.
4. Do not copy a Go 1.23 `maps.Keys` snippet into a Go 1.22 module. The return type is not the same.

### 13b. Type set — what a constraint “means” to the compiler

A constraint defines a **type set**: the set of types that may instantiate the parameter.

```text
interface { ~int | ~string }
  type set ≈ { types whose underlying is int or string }

interface { Read([]byte) (int, error) }
  type set ≈ { all types whose method set contains Read... }

comparable
  type set ≈ { types with == }
```

Hence `Max[T Ordered]` may use `>`: every type in the type set supports `<`/`>`. Hence `BadMax[T any]` may not: the type set is “everything,” and not all types have `>`.

#### Predict, then check — method constraint

**Code:**

```go
type Stringer interface {
	String() string
}

func Label[T Stringer](v T) string {
	return v.String()
}

type User struct{ Name string }

func (u User) String() string { return u.Name }

func demo() {
	_ = Label(User{Name: "Ana"})
	// _ = Label(42) // ?
}
```

**Predict:** does `Label(42)` compile?

**Check:** no — `int` has no `String` in its `method set`, not in the constraint’s type set.

**Comparison with 01.04:** same *spirit* as a small `interface`, but here there is no `interface` value at runtime for `T` — the compiler specializes `Label[User]`. If you need a list of different types in one `slice` and a common call, that is `[]fmt.Stringer` (runtime), not necessarily generics.

### 14. Decision map (whole)

```text
Need runtime behavior / plugin / I/O?
  YES → small interface (01.04)
  NO → need same algorithm for several types?
         YES → type parameter (+ constraint as narrow as possible)
         NO → plain function / concrete type

Do you lose type with []any / map[string]any in the core?
  YES → candidate for generics or a better model

Writing generic type "for every struct"?
  STOP — no algorithm, no generics
```

## Rules and syntax

| Element | Example |
|---------|---------|
| Parameter list | `[T any]` |
| Multiple parameters | `[K comparable, V any]` |
| Constraint `interface` | `interface{ ~string }` |
| Union | `int \| string` |
| Approximation | `~int` |
| Call with inference | `First(xs)` |
| Explicit | `First[int](xs)` |
| Generic type | `type Stack[T any] struct{…}` |
| Method on type | `func (s *Stack[T]) Push(v T)` |
| Forbidden | `func (s *Stack[T]) M[U any]()` |

### Language constraints

```go
any         // everything
comparable  // == and map key
```

### Named constraint

```go
type Number interface {
	~int | ~int64 | ~float64
}
```

### Instantiation

```go
Stack[int]{}
New[string]("a", "b")
```

### Zero value pattern

```go
func Head[T any](s []T) (T, bool) {
	var z T
	if len(s) == 0 {
		return z, false
	}
	return s[0], true
}
```

Do not return `nil` as “empty” unless the constraint guarantees a type where `nil` makes sense.

## Examples

### Example 1: Safer than `any`

```go
package boxes

func Ptr[T any](v T) *T { return &v }

func Must[T any](v T, err error) T {
	if err != nil {
		panic(err)
	}
	return v
}
```

#### What happens here

`Ptr(42)` yields `*int`, not `*any`. The compiler keeps the type. With old `interface{}` you would lose that information immediately.

#### Predict, then check

What is the type of `Ptr("hi")`?

**Predict:** `*string`.

**Check:** yes — `var p *string = Ptr("hi")` compiles.

### Example 2: `Ordered` constraint

```go
package ord

type Ordered interface {
	~int | ~int64 | ~float64 | ~string
}

func Max[T Ordered](a, b T) T {
	if a > b {
		return a
	}
	return b
}
```

#### Trace

```text
Max(3, 5)           → T=int, result 5
Max("b", "a")       → T=string, result "b"
Max([]int{1}, …)    → does not compile — []int is not Ordered
```

```go

type Brush interface {

		b.Paint(p[0], p[1])

```

### Example 6: `Result[T]` in a pipeline

```go
package result

type Result[T any] struct {
	Val T
	Err error
}

func OK[T any](v T) Result[T] { return Result[T]{Val: v} }

func Fail[T any](err error) Result[T] {
	var z T
	return Result[T]{Val: z, Err: err}
}

func Map[T, U any](r Result[T], f func(T) U) Result[U] {
	if r.Err != nil {
		return Fail[U](r.Err)
	}
	return OK(f(r.Val))
}
```

#### Trace

```text
OK(2) → Map(x, func(n int) string { return fmt.Sprint(n*n) })
  Err==nil → OK("4") type Result[string]
Fail[int](err) → Map(...) → Fail[string](err), Val zero string
```

Useful inside the core. At the JSON boundary you may still use `any` — consciously.

### Example 7: Constraint + keeping concrete type

```go
package bufioextra

import "io"

func Tee[T io.Reader](r T, w io.Writer) T {
	// illustration of the idea: return the same T
	return r
}
```

In real code you often use `io.TeeReader` which returns `io.Reader`. The generic pattern shows *why* you sometimes want `T`: so you do not lose methods of the concrete type.

### Example 8: Head / Tail

```go
package seq

func Head[T any](s []T) (T, bool) {
	var z T
	if len(s) == 0 {
		return z, false
	}
	return s[0], true
}

func Tail[T any](s []T) []T {
	if len(s) == 0 {
		return nil
	}
	return s[1:]
}
```

Simple, type-safe — generics without ceremony.

## Decision analysis

**Generics** — algorithms over containers, numerics, `Result`/`Option` helpers, data structures in libraries.

**`interface`** — I/O, services, plugin points, decorators, everything where runtime polymorphism is the point (01.04).

**`any`** — rarely: reflection, debug print, truly unknown type at a boundary. Not as the default “generic” style.

**`go generate`** — when you need specialized source per type (stringer, mock, protobuf). Generics reduce the need for containers, but do not kill generation. The next course block covers that.

**How narrow a constraint?** As narrow as possible — but do not copy a fat service into a constraint. If you need one method, name it. If you need `+`, name a numeric union.

**Export a generic API?** Only when you have at least two real consumers. Otherwise keep an unexported helper.

## Trade-offs

| Tool | Check | Dispatch | Readability |
|------|-------|----------|-------------|
| Generics | compiler | specialization | can be noisy with constraints |
| `interface` | compiler (contract) | runtime | excellent for behavior |
| `any` + assert | runtime | n/a | short, fragile |
| copy-paste | compiler | n/a | fast short-term, rots long-term |
| `go generate` | compiler | n/a | tooling, more files |

| Choice | Advantage | Cost |
|--------|-----------|------|
| Wide `any` | fast to write | loss of type |
| Narrow constraint | clear guarantees | more names, longer signatures |
| Generic type | state + API | complexity for reader |
| Function only | simpler | no encapsulated state |

## Common mistakes

1. Generic type “for every `struct`” without an algorithm that needs it.
2. Oversized constraint copying fat services instead of small sets of types/methods.
3. Mixing type parameter with class inheritance in your head (Go **does not** have class inheritance).
4. Attempting a generic method with a *new* type parameter on `receiver`.
5. Forgetting `comparable` and wondering why `map[T]` fails.
6. `[]any` as “generics” — you lose type and get asserts.
7. Forcing explicit `[T]` where inference works.
8. Exporting generic API before two consumers exist.
9. Method constraint where runtime `interface` at consumer (01.04) is needed.
10. Returning `nil` instead of `zero value` for arbitrary `T`.

## Idiomatic Go

- Prefer inference: `maps.Keys(m)` style.
- Use `slices`, `maps`, `cmp` before reinventing.
- Keep constraints small and named when reused.
- Do not export generic API until you have real consumers.
- Document type parameter in one sentence (`T is set element`).
- For runtime behavior stay on small `interface` (01.04).
- `var _ Constraint = Type{}` is not the same shape as for ordinary contracts — rely on calls that instantiate.
- Keep OOP discipline: `package` encapsulation still applies inside generic types.

## Practical scenario

Logging middleware holds fields in `map[string]any`. Types are lost; errors surface in production through wrong asserts. The team introduces:

- generic `Result[T]` for internal pipelines;
- small `interface` `LogSink` for output (runtime);
- `any` remains only at the JSON boundary.

#### Trace — before / after

```text
BEFORE:
  core → map[string]any
  assert everywhere
  bugs at runtime

AFTER:
  core → Result[User], Result[Order]
  sink → LogSink interface
  JSON boundary → any
  fewer asserts, clearer review
```

Generics did not “eat” `interface`. They split responsibilities: type safety inside, polymorphism at the edge.

## Summary

Generics in Go 1.18+ (course: 1.22+) provide type parameters and constraints for algorithms with compiler checking. They complement, not replace, `interface` polymorphism from 01.04. Choose generics for type-identical operations, `interface` for behavior, `any` only when you must. There is no class inheritance — there is discipline in the toolbox: types, methods, packages, contracts, then type parameters.

The next course block goes to code generation — another way to get type-specialized source when generics are not the right answer.
