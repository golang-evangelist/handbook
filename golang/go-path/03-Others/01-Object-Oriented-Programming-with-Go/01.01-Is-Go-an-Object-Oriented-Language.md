# 01.01 Is Go an Object-Oriented Language?

> **Go Path - Zero to Gopher** / **03 Others → Object-Oriented Programming with Go** / Lesson 01.01

## Lesson goals

After this lesson you will be able to:

- distinguish Alan Kay’s idea of OOP from “Java-style” classes and the class model;
- explain what Go *does not* have (classes, class inheritance) and what it *does* have (`struct`, `method`, `interface`, `embedding`, `promotion`);
- map familiar OOP ideas to Go mechanisms without forcing foreign idioms;
- predict how type, `method`, and `interface` together shape behavior;
- recognize when the question “is Go OOP?” is useful and when it gets in the way of design.

## Prerequisite

- Basic Go: `package`, types, functions, `pointer`.
- Understanding that `type` defines a name for a set of values.
- Go 1.22+ installed locally (the course targets Go 1.22+; generic types exist since Go 1.18).
- Desirable: experience with one class-based language (Java, C#, C++) — not required, but helps with comparison.

## Problem this lesson solves

Teams coming from class-based languages often look for a “class,” an “abstract class,” and a type hierarchy in Go. When they do not find them, they either give up on good design or force structures that look like Java trees. The question is not academic: a bad mental model leads to oversized `interface` contracts, false “is-a” relationships through `embedding`, and unreadable code.

This lesson gives an accurate frame: Go is not a class-based OOP language. Go has no classes and no class inheritance. Still, Go supports object-oriented *thinking* through types, `method` behavior, encapsulation at the `package` boundary, and polymorphism via implicit satisfaction of `interface` contracts.

## Mental model

Imagine three layers that together form an “object” in the Go sense:

1. **Data** — most often a `struct` (but other types too) holds state.
2. **Behavior** — `method` bound to a type: `func (t T) M()`.
3. **Contract** — `interface` describes what a type must be able to do, not how it is implemented.

Alan Kay often tied OOP to *messages* between objects and late binding, not to class hierarchies. Java/C# OOP in practice often means: class + class inheritance + explicit `implements`. Go takes a different path: composition, small `method` sets, implicit satisfaction of `interface`.

```text
  [state: type / struct]
           |
           | method (receiver)
           v
  [behavior: method set]
           |
           | satisfies contract?
           v
  [interface — contract toward consumer]
```

`embedding` is not “A *is* B” in the Java sense. It is composition with `promotion` of methods on the outer type — a useful tool, not a replacement for class inheritance (which Go does not have).

Generic programming (since Go 1.18; here Go 1.22+) is not an OOP mechanism. It is type parameterization (`type parameter`, `type constraint`). Do not mix it with the class model; details are in a later course lesson.

### Table of official terminology (this lesson)

| English term | How we read it here | What it is not |
|--------------|---------------------|----------------|
| `struct` | type that groups fields | class |
| `method` | function with a `receiver` | class “member” |
| `receiver` | first argument embedded in the method signature | `this` / `self` as keywords |
| `method set` | set of methods of type `T` or `*T` | `implements` list |
| `interface` | contract about methods | Java `interface` + explicit `implements` |
| `embedding` | unnamed field of a type inside another type | class inheritance |
| `promotion` | methods of embedded type become available on the outer type | `override` |
| `package` | unit of visibility and compilation | namespace with `protected` |
| `pointer` | address of a value | stand-in for a class object reference |
| `zero value` | default value of a type | “null object” |
| `exported` / `unexported` | uppercase / lowercase initial letter | `public` / `private` at field level on a type |
| `error` | value describing failure | thrown exception |
| `composite literal` | `{...}` for `struct` / slice / map | class constructor |

## Mechanism

This section is the core of the lesson. Go through it slowly: each subsection builds one layer of the mental model, and the execution trace tables show what actually happens in memory and in the type system.

### 1. Type instead of class

In Go you define a type. Most often it is a `struct`:

```go
type Account struct {
	ID      string
	Balance int64 // in smallest currency units
}
```

There is no `class Account`. There is no constructor as a language concept — there is the convention `NewAccount(...)`. There is no `protected` / `private` at the field level *within a type* for other types in the same `package`: visibility is at the *package* level (`exported` / `unexported`).

The `zero value` for `Account` is `Account{ID: "", Balance: 0}`. That is not an “uninitialized object” — it is a valid value of the type, unless your domain says otherwise (then you enforce `NewT` and `unexported` fields; see 01.03).

#### Trace: creating a value

| Step | Expression | Result / state | Note |
|-----:|------------|----------------|------|
| 1 | `var a Account` | `ID=""`, `Balance=0` | `zero value` |
| 2 | `a = Account{ID: "A1", Balance: 100}` | `ID="A1"`, `Balance=100` | `composite literal` |
| 3 | `p := &a` | `p` points at the same `Account` value | `pointer` to `a` |
| 4 | `p.Balance = 120` | `a.Balance == 120` | change via `pointer` |

### Predict, then check — zero value

**Question:** What does `fmt.Println((Account{}).Balance)` print?

Stop and predict before you look at the answer.

**Answer:** `0`. `Account{}` is the `zero value`; field `Balance` of type `int64` has `zero value` `0`.

### 2. Method instead of a “class member function”

A `method` has a `receiver`:

```go
func (a Account) CanWithdraw(amount int64) bool {
	return amount > 0 && a.Balance >= amount
}
```

The `receiver` is part of the signature. The set of methods of a type forms its *method set* — that later determines which `interface` the type satisfies.

A method is not “in a class.” A method is a declaration in the same `package` as the type (for concrete types). You can have multiple files in a package; all methods of type `Account` live in that package.

#### Trace: call with value receiver

```go
a := Account{ID: "A1", Balance: 50}
ok := a.CanWithdraw(40)
```

| Step | What the compiler / runtime does | State |
|-----:|----------------------------------|-------|
| 1 | Copies `a` into the method’s `receiver` `a` | local `a.Balance=50` |
| 2 | Evaluates `40 > 0 && 50 >= 40` | `true` |
| 3 | Returns `true` into `ok` | original `a` unchanged |

A value `receiver` gets a **copy**. If the method mutates fields on a value `receiver`, it mutates the copy — the caller does not see it. That is why mutation almost always uses a `pointer` `receiver` (in detail in 01.02).

### Predict, then check — receiver copy

```go
func (a Account) DepositBroken(amount int64) {
	a.Balance += amount
}

a := Account{Balance: 10}
a.DepositBroken(5)
```

**Question:** What is `a.Balance` after the call?

**Answer:** `10`. The method changed a copy. The fix is `func (a *Account) Deposit(...)`.

### 3. Interface instead of explicit `implements`

```go
type Withdrawer interface {
	CanWithdraw(amount int64) bool
	Withdraw(amount int64) error
}
```

Any type with those methods *automatically* satisfies the `interface`. There is no “implements Withdrawer” list. That is the core of Go polymorphism.

The consumer depends on the contract, not the concrete type:

```go
func Pay(w Withdrawer, amount int64) error {
	if !w.CanWithdraw(amount) {
		return fmt.Errorf("insufficient funds")
	}
	return w.Withdraw(amount)
}
```

#### Trace: does the type satisfy the interface?

Assume:

```go
func (a Account) CanWithdraw(amount int64) bool { /* ... */ }
func (a *Account) Withdraw(amount int64) error  { /* ... */ }
```

| Type we look at | Has `CanWithdraw`? | Has `Withdraw`? | Satisfies `Withdrawer`? |
|-----------------|--------------------|-----------------|-------------------------|
| `Account` | yes (value `receiver`) | no (`Withdraw` is on `*Account`) | **no** |
| `*Account` | yes (value methods enter the method set of `*T`) | yes | **yes** |

This is one of the most important rules of the course: **the method set of `T` contains methods with value `receiver`; the method set of `*T` contains both value and `pointer` methods.** So a value often *does not* satisfy an `interface` that requires a `pointer` `receiver`.

### Predict, then check — interface and pointer receiver

```go
type Incrementer interface {
	Inc()
}

type Counter struct{ n int }

func (c *Counter) Inc() { c.n++ }

func bump(i Incrementer) { i.Inc() }

var c Counter
```

**Question:** Does `bump(c)` compile? Does `bump(&c)` compile?

**Answer:** `bump(c)` does **not** compile — `Counter` does not have `Inc` in its method set. `bump(&c)` **yes** — `*Counter` has `Inc`.

### 4. Embedding and promotion instead of a class tree

```go
type LoggedAccount struct {
	Account
	Logger interface{ Println(v ...any) }
}
```

`LoggedAccount` gets methods of type `Account` in its method set through `promotion` (with nuances around `pointer`). That is not “LoggedAccount inherits Account” — Go has no class inheritance. It is an unnamed field + `promotion`.

```go
la := LoggedAccount{
	Account: Account{ID: "A1", Balance: 20},
	Logger:  log.Default(),
}
_ = la.CanWithdraw(10) // promotion: calls Account.CanWithdraw
```

#### Trace: where state lives

| Expression | Meaning |
|------------|---------|
| `la.Balance` | shorthand for `la.Account.Balance` (field `promotion`) |
| `la.Account.Balance` | explicit access to field from `embedding` |
| `la.CanWithdraw(5)` | `promotion` of method from `Account` |
| `la.Logger.Println("x")` | call via named field `Logger` |

`embedding` is useful when you want to “borrow” another type’s API. It is dangerous when you build a deep pyramid to simulate a class tree — Go deliberately does not support that as a language model.

### Predict, then check — embedding is not is-a

```go
type Animal struct{ Name string }
func (a Animal) Speak() string { return a.Name }

type Dog struct{ Animal }

func describe(a Animal) string { return a.Speak() }

d := Dog{Animal: Animal{Name: "Rex"}}
```

**Question:** Does `describe(d)` compile?

**Answer:** **No.** `Dog` is not `Animal`. `embedding` does not create a subtype. You must be explicit: `describe(d.Animal)`, or change the signature to take an `interface` with `Speak()`.

### 5. Three OOP pillars mapped to Go

Classic textbooks list: encapsulation, polymorphism, “reuse” / hierarchy. In Go:

| Pillar | Go mechanism | Where in the course |
|--------|--------------|---------------------|
| Encapsulation | `unexported` fields + `NewT` + `package` boundary | 01.03 |
| Polymorphism | implicit satisfaction of `interface` | 01.04 |
| Behavior with type | `method` + `receiver` + method set | 01.02 |
| Reuse without class model | composition, `embedding`, functions | this + 01.02 |

Go **does not have** class inheritance. So you do not look for “reuse” in `extends`, but in composition and small contracts.

### 6. Alan Kay versus class OOP — mechanics of the difference

Alan Kay often described OOP through cell biology and messages: objects keep internal state and react to messages. Class inheritance was not the core of that story. In industry, OOP became tied to UML class diagrams and deep hierarchies.

| Question | Kay’s emphasis | Class OOP in practice | Go |
|----------|----------------|-------------------------|-----|
| What is an object? | state + reaction to message | class instance | value of a type + methods |
| How do you share behavior? | protocol / messages | base class | `interface` |
| How do you hide details? | cell interior | `private` fields | `package` + `unexported` |
| How do you extend the system? | new objects that understand messages | `extends` / `override` | new types that satisfy `interface` |

When you read Go code with OOP glasses, look for:

1. who owns state (which type, which `package`);
2. who changes state (which methods, whether on `pointer`);
3. who defines the contract (where the `interface` lives — at consumer or implementation);
4. how behavior is reused (functions, `embedding`, decorators).

### 7. Complete mini-trace: from struct to interface

Code:

```go
package bank

import "fmt"

type Account struct {
	id      string
	balance int64
}

func NewAccount(id string, opening int64) (*Account, error) {
	if id == "" {
		return nil, fmt.Errorf("empty id")
	}
	if opening < 0 {
		return nil, fmt.Errorf("negative balance")
	}
	return &Account{id: id, balance: opening}, nil
}

func (a *Account) Deposit(amount int64) error {
	if amount <= 0 {
		return fmt.Errorf("amount must be positive")
	}
	a.balance += amount
	return nil
}

func (a Account) Balance() int64 { return a.balance }
func (a Account) ID() string     { return a.id }

type Creditable interface {
	Deposit(amount int64) error
	Balance() int64
}

func Credit(c Creditable, amount int64) error {
	return c.Deposit(amount)
}
```

#### Execution trace for `Credit`

| Step | Code | State / types | Why it works |
|-----:|------|---------------|--------------|
| 1 | `acc, err := NewAccount("A1", 100)` | `*Account`, `balance=100` | constructor preserves invariants |
| 2 | `err == nil` | we continue | validation passed |
| 3 | `Credit(acc, 25)` | argument is `*Account` | `*Account` satisfies `Creditable` |
| 4 | inside `Credit`: `c.Deposit(25)` | dynamic call | `interface` holds `(type, value)` |
| 5 | `a.balance` becomes `125` | mutation via `pointer` | `Deposit` has `*Account` receiver |
| 6 | `acc.Balance()` → `125` | read | value `Balance` works on `*Account` too |

### Predict, then check — can a value go into Credit?

**Question:** If you do `var a Account` (not a `pointer`) and call `Credit(a, 10)`, what happens?

**Answer:** It does not compile. `Deposit` is on `*Account`, so `Account` does not satisfy `Creditable`. You need `Credit(&a, 10)` — and only if `a` is addressable.

### 8. Where Go is *not* OOP in the Java sense

- No class inheritance (`extends`).
- No virtual tables you control explicitly like in C++.
- No guarantee “every object is a class instance.”
- No `protected` between “subtypes” — because there are no class subtypes.
- `embedding` does not create a subtype: `Dog` is not `Animal`.
- Generic types (Go 1.18+) are not a replacement for class hierarchy.

### 9. Mental map Java → Go (without forcing)

Use this table as a *translation*, not an obligation to port every Java pattern 1:1.

| Java / C# idea | Go approximate mechanism | Danger if you force it |
|----------------|--------------------------|------------------------|
| `class` | `type` + `struct` + methods | looking for a constructor in the language |
| `private` field | `unexported` name | expecting privacy per type within a package |
| `interface` + `implements` | `interface` without `implements` | huge contracts “like an abstract class” |
| `extends` | composition / `embedding` | deep embedding pyramid |
| abstract class | small `interface` + concrete types | “base” struct with 20 methods |
| dependency injection via `interface` | `interface` at consumer | `interface` in same package without need |
| getter/setter for everything | methods only when preserving invariant | bucket of meaningless getters |

### 10. Trace of a mistake: forcing hierarchy

Bad attempt (mental model from Java):

```go
type Vehicle struct{ Speed int }
type Car struct{ Vehicle }
type ElectricCar struct{ Car }
```

| Problem | Why it hurts |
|---------|--------------|
| Deep `embedding` | unclear who owns state |
| “Base” methods on `Vehicle` | every “subtype” pulls a bloated API |
| Tests | mock must look like whole tree |
| New type `Scooter` | forced into tree though it only shares part of behavior |

Better Go model: separate small contracts (`Powertrain`, `Registrable`, `Billable`) and concrete types that satisfy them where it makes sense.

### Predict, then check — what is the OOP question here?

**Question:** The team asks: “What is the base class for all entities in the domain?” What is a better question in Go?

**Answer:** “Which contracts (`interface`) do we need at package boundaries?” and “Which invariants must stay hidden (`unexported`)?”

### 11. Zero value, pointer, and “object”

In class-based languages you often have `new Foo()` or `null`. In Go:

| Situation | Typical choice | Why |
|-----------|----------------|-----|
| Small, safe `zero value` | value `T` | simple, no `nil` |
| Invariants / optional absence | `*T` + `NewT` | `nil` means “no instance” |
| Mutating shared state | `*T` | one object, many aliases |
| Copy without sharing | `T` | each caller has its own value |

“Object” in Go conversation often means: *value of a type with methods*, sometimes behind a `pointer`. It is not the same as a JVM heap object with a class header.

### 12. Package as encapsulation factory (preview 01.03)

```go
package catalog

type Product struct {
	sku   string
	price int64
}

func NewProduct(sku string, price int64) (Product, error) { /* validation */ }

func (p Product) SKU() string  { return p.sku }
func (p Product) Price() int64 { return p.price }
```

#### Visibility trace

| Code location | `p.sku` directly? | `p.SKU()`? |
|---------------|-------------------|------------|
| Same `package catalog` | yes | yes |
| Other `package` | no | yes |

That is Go’s replacement for private class fields, with different granularity: **`package`, not type**.

### 13. Generic types are not a class tree

Since Go 1.18 (course: Go 1.22+):

```go
func Sum[T ~int | ~int64](xs []T) T {
	var s T
	for _, x := range xs {
		s += x
	}
	return s
}
```

| | Generics | OOP via interface |
|--|----------|-------------------|
| When | same algorithm, different data types | different behavior, same contract |
| Binding | compile-time (`type parameter`) | runtime via `interface` |
| Typical example | `slice` util, containers | `io.Reader`, services |

Do not ask “what base class for numbers?” — ask whether you need a `type constraint` or an `interface` with methods.

### 14. Synthetic trace: message = method call via interface

```go
type Speaker interface {
	Speak() string
}

type Dog struct{ Name string }
func (d Dog) Speak() string { return "woof-woof: " + d.Name }

type Robot struct{ Model string }
func (r Robot) Speak() string { return "beep: " + r.Model }

func Announce(s Speaker) string { return s.Speak() }
```

| Call | Dynamic type in `s` | Result |
|------|---------------------|--------|
| `Announce(Dog{Name: "Maza"})` | `Dog` | `"woof-woof: Maza"` |
| `Announce(Robot{Model: "R2"})` | `Robot` | `"beep: R2"` |

No common ancestor. There is a common contract. That is Go’s answer to “object orientation” in Kay’s spirit.

### Predict, then check — do we need a common struct?

**Question:** Must `Dog` and `Robot` `embedding` a common `BaseSpeaker struct` for `Announce` to work?

**Answer:** No. It is enough that both have `Speak() string`. A common `struct` would be artificial if there is no shared state.

### 15. Mechanism checklist before the next section

Read the list aloud:

1. Type ≠ class.
2. `method` = behavior tied to type via `receiver`.
3. `interface` = contract; satisfaction is implicit.
4. Method set of `T` ≠ method set of `*T` when there are `pointer` methods.
5. `embedding` + `promotion` ≠ class inheritance (which Go does not have).
6. Encapsulation lives at the `package` boundary.
7. Generics (1.18+) are a separate tool, not an OOP pillar.

If you can explain each point with an example, you are ready for rules and syntax.

## Rules and syntax

| Concept | Go | Typical class language |
|---------|----|------------------------|
| State | `type T struct { ... }` | `class T { fields }` |
| Behavior | `func (t T) M()` | methods in class |
| Abstraction | `interface` | `interface` / abstract class |
| Reuse | composition, `embedding` | class inheritance |
| Visibility | `package` (`Foo` / `foo`) | `public` / `private` / `protected` |
| Polymorphism | implicit `interface` | explicit `implements` |

Syntax stubs you should recognize:

```go
type T struct{ /* fields */ }

func (t T) M()  {}   // value receiver
func (t *T) N() {}   // pointer receiver

type I interface {
	M()
}

type Outer struct {
	T // embedding — unnamed field
}
```

### Method set rules (brief; detail in 01.02)

| Type | Method set contains |
|------|---------------------|
| `T` | methods with `receiver` of type `T` |
| `*T` | methods with `receiver` of type `T` **and** `*T` |

Consequence: if an `interface` requires a method with `pointer` `receiver`, value type `T` **does not** satisfy that `interface`.

### Naming rules

| What | Idiom |
|------|-------|
| Type | `Account`, `HTTPClient` (acronyms capitalized per Go style) |
| `unexported` field | `balance`, `id` |
| Constructor | `NewAccount`, `ParseSKU` |
| `receiver` name | short: `a Account`, not `this` / `self` |

### What the language deliberately omits

- `class`
- class inheritance
- `extends` / `override` as a language model
- `protected`
- constructors as a separate syntactic form

## Examples

### Example 1: State + behavior without a class

```go
package bank

import "fmt"

type Account struct {
	id      string
	balance int64
}

func NewAccount(id string, opening int64) (*Account, error) {
	if id == "" {
		return nil, fmt.Errorf("empty id")
	}
	if opening < 0 {
		return nil, fmt.Errorf("negative balance")
	}
	return &Account{id: id, balance: opening}, nil
}

func (a *Account) Deposit(amount int64) error {
	if amount <= 0 {
		return fmt.Errorf("amount must be positive")
	}
	a.balance += amount
	return nil
}

func (a Account) Balance() int64 { return a.balance }
func (a Account) ID() string     { return a.id }
```

#### What happens here

`Account` encapsulates state through *unexported* fields and *exported* methods. There is no class, yet you get controlled access. `NewAccount` is a factory — Go idiom, not a language constructor. Mutation goes through `pointer` `receiver`; reads can stay on value.

#### Predict, then check

**Question:** Why does `NewAccount` return `*Account`, not `Account`?

**Answer:** Because you want one shared object with mutation (`Deposit`), clear `nil` with `error`, and consumers naturally working with a type that satisfies `interface` with `pointer` methods. (Value return is OK when the type is small and immutable.)

### Example 2: Interface as contract between packages

```go
package payment

type Chargeable interface {
	ID() string
	Balance() int64
	Deposit(amount int64) error
}

func Credit(c Chargeable, amount int64) error {
	return c.Deposit(amount)
}
```

#### What happens here

Package `payment` does not know about `bank.Account`. It only knows the contract. That is OOP in Kay’s spirit: objects communicate via messages/contracts, not via a shared base class.

#### Predict, then check

**Question:** Must `Chargeable` live in package `bank`?

**Answer:** No. Idiomatically it often lives at the *consumer* (`payment`), so you do not pull unnecessary methods. More in 01.04.

### Example 3: Embedding is not an “is-a” hierarchy

```go
package audit

import "log"

type AccountView interface {
	ID() string
	Balance() int64
}

type Audited struct {
	AccountView
	log *log.Logger
}

func (a Audited) Snapshot() {
	a.log.Printf("account=%s balance=%d", a.ID(), a.Balance())
}
```

#### What happens here

`Audited` composes any `AccountView`. There is no `class Audited extends Account`. If you need “base behavior + extension,” first think about `interface` and composition, then about `embedding` a concrete type.

#### Predict, then check

**Question:** Can `Audited` be passed where `AccountView` is expected?

**Answer:** Yes, because `embedding` an `interface` value + method `promotion` means `Audited` has `ID` and `Balance` — so it satisfies `AccountView` (as long as the embedded field is not `nil`).

### Example 4: Comparing mental models (Alan Kay vs Java OOP)

```go
package compare

// Java mental model (pseudo):
// class Animal { abstract void Speak(); }
// class Dog extends Animal { void Speak() { ... } }

// Go model: small interface + concrete types
type Speaker interface {
	Speak() string
}

type Dog struct{ Name string }

func (d Dog) Speak() string { return "woof-woof: " + d.Name }

type Robot struct{ Model string }

func (r Robot) Speak() string { return "beep: " + r.Model }

func Announce(s Speaker) string { return s.Speak() }
```

#### What happens here

Polymorphism comes from `interface`, not a common ancestor. `Dog` and `Robot` do not share a hierarchy — they share a contract. That is Go’s answer to “object orientation.”

#### Predict, then check

**Question:** If you add `type Cat struct{}` without a `Speak` method, does `Announce(Cat{})` compile?

**Answer:** No. `Cat` does not satisfy `Speaker`. There is no runtime “abstract method” surprise — the error is at compile time.

### Example 5: Explicit proof that value does not satisfy interface

```go
package demo

type Mutator interface {
	Touch()
}

type Box struct{ n int }

func (b *Box) Touch() { b.n++ }

func apply(m Mutator) { m.Touch() }

func Demo() {
	var b Box
	// apply(b)  // compile error: Box does not implement Mutator
	apply(&b)    // OK
}
```

#### What happens here

This is a concrete example to remember: **a value does not satisfy an `interface` that requires a `pointer` `receiver`.** The compiler at a method call often does `(&b).Touch()`, but *satisfying* an `interface` looks at the method set, not call-site autocompletion.

#### Predict, then check

**Question:** Why does `b.Touch()` work directly, but `apply(b)` does not?

**Answer:** A direct call allows automatic address-taking of addressable `b`. Passing `b` into an `interface` requires the *value type* to already have that method in its method set — and `Box` does not.

### Example 6: Rewriting one Java-style shape model

```go
package geom

import "math"

type Shaper interface {
	Area() float64
}

type Circle struct{ R float64 }

func (c Circle) Area() float64 { return math.Pi * c.R * c.R }

type Rect struct{ W, H float64 }

func (r Rect) Area() float64 { return r.W * r.H }

func TotalArea(shapes ...Shaper) float64 {
	var sum float64
	for _, s := range shapes {
		sum += s.Area()
	}
	return sum
}
```

#### What happens here

There is no abstract class. `Shaper` is a contract. A new shape enters without touching existing types, as long as it implements `Area()`. That is openness for extension without a class tree.

#### Predict, then check

Trace for `TotalArea(Circle{R: 1}, Rect{W: 2, H: 3})`:

| Step | Element | `Area()` | Running sum |
|-----:|---------|----------|-------------|
| 1 | `Circle{R:1}` | ≈ 3.14159 | ≈ 3.14159 |
| 2 | `Rect{2,3}` | 6 | ≈ 9.14159 |

**Question:** Must `Circle` and `Rect` live in the same `package` as `Shaper`?

**Answer:** No. They can be in other packages; only the method set matters.

## Decision analysis

**Do you call Go OOP?** If OOP means “classes + class inheritance,” the answer is no — Go has no classes and no class inheritance. If it means “objects with state, behavior, and abstraction,” the answer is partly yes — through types, `method`, and `interface`.

**When do you force the class model in Go?** When you build long `embedding` chains to simulate `extends`, when you want an “abstract class” instead of a small `interface`, when you push all types into one hierarchy for a “pretty” UML diagram.

**When does the Go model shine?** Libraries with clear `package` boundaries, testing via small `interface`, composing behavior without brittle hierarchy, microservices with narrow contracts.

**When is the question “is Go OOP?” harmful?** When it stops design: instead of defining types and contracts, debate wastes time. A more useful question: “How will we model state, behavior, and boundaries?”

**Where do generics stop?** When the algorithm does not depend on behavior but on data shape — `type parameter`. When it depends on behavior — `interface`. Mix consciously, not from habit “everything is a class.”

## Trade-offs

| Choice | You gain | You pay |
|--------|----------|---------|
| `interface` instead of classes | flexibility, testability | you must design contracts explicitly |
| No class inheritance | fewer rigid hierarchies | no cheap “reuse” via base class |
| Visibility at `package` level | simple rules | harder to mimic `protected` between “subtypes” |
| `embedding` | short code, `promotion` | can hide the real dependency |
| Value vs `pointer` | clear copy / sharing semantics | method set surprises around `interface` |
| Generics with OOP tools | less repetition for data | another layer of decisions (1.18+) |

## Common mistakes

1. **Looking for `class` in the docs** — instead look for `type`, `method`, and `interface`.
2. **Deep `embedding` as replacement for class inheritance** — code becomes unclear about who actually owns state. Go has no class inheritance; do not simulate it by force.
3. **Huge `interface` “like an abstract class”** — makes mocks hard and blurs contract focus.
4. **Exporting all struct fields** — you lose encapsulation; more in 01.03.
5. **Mixing OOP questions with generic types** — generics are not a replacement for behavior contracts; they are a separate tool.
6. **Assuming `b.Touch()` ⇒ `Mutator(b)` works** — method call and `interface` satisfaction are not the same rules (method set).
7. **“Dog is Animal because of embedding”** — it is not; there is no value subtyping.
8. **One “base” struct for the whole domain** — pulls a bloated API and slows change.

## Idiomatic Go

- Prefer **composition** over simulating the class model.
- Keep `interface` **small** and close to the consumer.
- Use **unexported** fields + `NewT` when you need invariants.
- Do not ask “what is the base class?” — ask “what contract do I need?”
- In package docs describe type behavior, not UML hierarchy.
- When mutating, be aware of `pointer` `receiver` and method set.
- Keep generic functions for data; `interface` for behavior.

## Practical scenario

A team ports a Java domain “Vehicle → Car → ElectricCar” to Go. First attempt: three levels of `embedding` structs and a shared “base” type with twenty methods. Tests break because the mock must implement everything.

Refactor: `Powertrain`, `Registrable`, `Billable` as separate small `interface`; concrete types satisfy them where it makes sense. Test line count drops, and new type `Scooter` enters without touching the old hierarchy — because there was none.

Second lesson from the same refactor: several functions expected a `Vehicle` value, but methods were on `*Car`. The compiler rejected conversion to `interface`. The team learned to look at method set *before* drawing a diagram.

## Summary

Go is not a class-based OOP language: it has no classes and no class inheritance. It offers types, `method`, `interface`, and `embedding`/`promotion` as tools for state, behavior, and polymorphism. Alan Kay’s emphasis on messages and late binding is closer to Go `interface` contracts than to Java hierarchies. Method set determines what a type “can do” for an `interface` — a value is often not enough when methods mutate via `pointer`. Design contracts and composition, not class family trees. Generics since Go 1.18 complement the toolkit but are not an OOP pillar.
