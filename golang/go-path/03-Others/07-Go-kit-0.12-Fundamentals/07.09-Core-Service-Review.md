# 07.09 Core Service Review

> **Go Path - Zero to Gopher** / **03 Others → Go kit 0.12 Fundamentals** / Lesson 07.09

## Lesson goals

After this lesson you should be able to:

- run a **review gate** of the core (service → endpoint → transport) *before* observability (log/metrics)
- confirm that the `service` package has **no** `net/http` (nor JSON encode as a wire concern)
- verify that decode stays **thin** (wire → DTO), without business rules
- require core unit tests (happy + error path) instead of “logs as tests”
- make a checklist of gaps that observability would only *hide*, not *fix*
- decide: continue to 07.10 or go back to boundary refactor

## Prerequisite

- 07.05 — Service interface + implementation, sentinel errors, table tests
- 07.06 — request/response DTO, error style A/B
- 07.07 — endpoint factory (`Make…Endpoint`)
- 07.08 — HTTP transport (`decode`/`encode`, `httptransport.NewServer`, mux)
- 07.03–07.04 — folders, dependency arrow, pin `kit@v0.12.0`

## Problem this lesson solves

Observability on a broken core gives **prettier logs of chaos**. If `service` imports `net/http`, if decode does business, if there are no tests for `ErrEmpty`, then transport logging (07.10) and application logging (07.11) only accelerate bad diagnoses: more lines, same mess.

This lesson is a **gate**: you do not learn a new API — you *check* that the layers you already wrote hold their boundaries. The gate is not ceremony; the gate is cheaper than a week of reading PII body dumps in production.

## Mental model

```
                    ┌─────────────────────────┐
                    │   OBSERVABILITY (later) │
                    │  07.10 / 07.11 / 07.12   │
                    └───────────▲──────────────┘
                                │ only if the
                                │ core is green
┌───────────────┐   ┌───────────┴───────────┐   ┌──────────────┐
│   transport   │──►│       endpoint        │──►│   service    │
│ decode/encode │   │ Make…Endpoint         │   │ Uppercase…   │
└───────────────┘   └───────────────────────┘   └──────────────┘
         ▲                     ▲                         ▲
         │                     │                         │
    thin wire            type assert +              no http/json
    errors mapped        one err style              unit tests
```

Review asks five questions in five minutes:

1. **Dependencies** — arrow one-way?
2. **Tests** — `go test` green without a server?
3. **Decode** — shape only, not domain?
4. **Errors** — sentinel + mapping agreed?
5. **main** — wiring, not business?

If any is “no” — stop. Do not go to log.

## Mechanism

### Step 0 — why the gate *now*, not after logs

Teams often say: “first let’s see the logs, then we’ll fix”. That reverses the order. A log without a stable method name, without a clear error, without a tested happy path, becomes a **narrative without evidence**.

Gate before observability means:

- you know *what* you measure (use-case name, not a random URL string)
- you know *what* an error is (sentinel vs panic vs wire fail)
- you know *where* the concern sits (service vs transport)

**Predict-then-answer A**

Question: can a Finalizer that logs HTTP status replace a unit test for `ErrEmpty`?

- Predict: “partially, you see 400 in the log”.
- Answer: no. Status proves the edge; a unit test proves the *domain*. A log is not an assertion. Do not use logs as tests.

### Step 1 — checklist: `service` package

Open `internal/service` (or whatever you named it) and walk through:

| Check | OK looks like | Smell |
|-------|---------------|-------|
| Imports | `context`, `errors`, `strings`, domain | `net/http`, `encoding/json` for wire, gRPC status as the only error |
| API | typed methods + `ctx` first | “handler” methods, `http.ResponseWriter` |
| Errors | `var ErrEmpty = errors.New(...)` | string compare `err.Error() == "empty"` everywhere |
| Test | table test happy + empty + (optional) cancel | only `fmt.Println` in `main` “works” |
| Globals | no mutable global state | `var svc = ...` that changes in a test |

A command that helps:

```powershell
rg "net/http|encoding/json" .\internal\service
```

Expect empty (or a clearly justified exception that is *not* an HTTP handler). `encoding/json` in service is not always wrong (e.g. storing an opaque blob), but for StringService pedagogy — **not needed**.

**Predict-then-answer B**

Question: may service log?

- Predict: “no, never”.
- Answer: on this path — *not yet*, and not directly from a domain method as the primary style. 07.11 introduces **LoggingMiddleware** around the Service interface. If you already stuck `log.Println` into `Uppercase`, that is a review smell: mixes job and platform, hardens testing.

### Step 2 — checklist: endpoint layer

Check the factory:

```go
func MakeUppercaseEndpoint(svc service.Service) endpoint.Endpoint {
    return func(ctx context.Context, request interface{}) (interface{}, error) {
        req, ok := request.(uppercaseRequest)
        if !ok {
            return nil, errors.New("invalid request type") // or typed error
        }
        v, err := svc.Uppercase(ctx, req.S)
        // style A or B — consistently
        ...
    }
}
```

Checklist:

1. Type assert with `ok` branch (no panic on bad type).
2. One error style (A: Err in response body; B: `return nil, err`) documented.
3. No `http.Request` in the endpoint.
4. At least one test that calls the endpoint with a fake request (without mux).

**Predict-then-answer C**

Question: does an endpoint test “replace” a service test?

- Predict: “yes, integration is enough”.
- Answer: no. Endpoint test checks the glue and error style; service test checks the domain. Both. Logs replace neither.

### Step 3 — checklist: transport / thin decode

Decode may:

- read body / path / query
- unmarshal into DTO
- reject a *wire* error (bad JSON, oversized body)

Decode must not:

- “if string shorter than 3, ErrEmpty” (that is domain — service)
- call `svc.Uppercase`
- choose HTTP status (unless ErrorEncoder policy explicitly lives here — and then *not* business)

A thin function looks roughly:

```go
func decodeUppercaseRequest(_ context.Context, r *http.Request) (interface{}, error) {
    var req uppercaseRequest
    if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
        return nil, err
    }
    return req, nil
}
```

If you see `strings.TrimSpace` + business rules in decode — **return to service** before 07.10.

### Step 4 — walkthrough: one happy-path request through layers

Imagine `POST /uppercase` with `{"s":"go"}`.

1. **Mux** picks the handler (`httptransport.Server`).
2. **ServerBefore** (not required yet — comes in 07.10) would put request id into `context`.
3. **decode** → `uppercaseRequest{S:"go"}`.
4. **endpoint** type assert → `svc.Uppercase(ctx, "go")`.
5. **service** → `"GO", nil`.
6. **endpoint** packs response DTO.
7. **encode** writes JSON + content-type.
8. Client sees `{"v":"GO"}`.

In review *out loud* retell these 8 steps. If you stall on “where does ErrEmpty mapping live” — that is a gap: write it down before logs.

### Step 5 — walkthrough: error path (`ErrEmpty`)

1. Body `{"s":""}`.
2. Decode succeeds (JSON is valid!).
3. Service returns `("", ErrEmpty)`.
4. Endpoint style A: response with `err` field, `error == nil` *or* style B: `nil, ErrEmpty`.
5. Transport maps to 400 (ErrorEncoder or reading Err field).

If decode rejects empty string *before* service, you broke the boundary: wire is OK, domain is not. Review fail.

**Predict-then-answer D**

Question: is 400 from decode for empty string “the same as ErrEmpty”?

- Predict: “same for the client”.
- Answer: for the client maybe; for architecture no. Another transport (gRPC) will not share the decode rule. Domain must live in service.

### Step 6 — walkthrough: wire fail (bad JSON)

1. Body `{not-json`.
2. Decode returns error.
3. Endpoint is *not* called.
4. ErrorEncoder / ServerErrorEncoder → 400.
5. Service tests are not relevant here — this is a transport concern.

Review asks: is there a test of decode for bad JSON *or* at least a conscious manual curl? Ideally: a small test of the decode function.

### Step 7 — tests: what must exist before 07.10

Minimum set:

| Layer | Test | Why |
|-------|------|-----|
| service | table: `"go"` → `"GO"`; `""` → `ErrEmpty` | domain proof |
| service | (optional) ctx cancel propagation if you have I/O | context discipline |
| endpoint | MakeUppercaseEndpoint + fake svc | error style |
| transport | decode bad JSON / (optional) httptest happy | edge |

Commands:

```powershell
go test ./internal/service -count=1
go test ./internal/endpoint -count=1
go test ./... -count=1
go test ./internal/service -race -count=1
```

`-race` is not “nice to have” if you share state; for StringService often clean, but the discipline remains.

### Step 8 — anti-pattern: logs as tests

Symptoms:

- CI has no `go test`, but “we look at logs in staging”
- assertion is grepping a string in a log file
- bug fix = “add another log” without a failing test

Why it hurts:

- log format changes (key rename) → false fail
- flaky environment
- does not catch regression locally in 200ms

**Gate rule:** if there is no failing unit test that would catch the bug, do not close review with “we’ll see in the logs”.

### Step 9 — checklist: `main` and wiring

`main` may:

- construct logger (later), svc, endpoints, servers
- read env (port, timeouts)
- register routes, `ListenAndServe` / graceful shutdown

`main` must not:

- Uppercase business rules
- copy-paste validate
- silent `log.Fatal` without context for every small thing without a recovery strategy

Also check:

- `go.mod` pin `github.com/go-kit/kit v0.12.0` (or the exact agreed patch in that minor)
- README: how to run, curl example
- server timeouts (link 04.02) — at least ReadHeaderTimeout

### Step 10 — checklist: errors and mapping

Make a small table in the PR description or ADR:

| Error | Where it arises | HTTP | Note |
|-------|-----------------|------|------|
| bad JSON | decode | 400 | wire |
| `ErrEmpty` | service | 400 | domain |
| panic / unknown | ? | 500 | do not swallow silently |
| ctx cancel | anywhere | 499/client closed | depends on policy |

If the table does not exist in the team’s head — observability will mix “client error” and “server error”.

### Step 11 — package boundaries: `go list` / import graph

Quick check:

```powershell
go list -f "{{.ImportPath}} {{.Imports}}" ./internal/...
```

Look for:

- `service` does not import `transport`
- `endpoint` does not import `net/http` (unless you consciously joined — avoid)
- no cycle

If you see a cycle — **gate red**, not 07.10.

### Step 12 — walkthrough: second transport thought experiment

Ask yourself: “could I tomorrow add gRPC Uppercase *without* touching service?”

- Yes → boundaries OK.
- No, because validate lives in HTTP decode → refactor now.
- No, because response DTO has `http` tags deep in service → refactor now.

This question is cheaper than real gRPC; use it as a litmus.

### Step 13 — mini lab: fill the gate checklist (what you write down)

Copy into notes and check honestly:

```
[ ] service: no net/http
[ ] service: table test happy + ErrEmpty
[ ] endpoint: ok-assert; style A/B documented
[ ] decode: thin; no domain validate
[ ] ErrorEncoder / Err mapping exists for ErrEmpty
[ ] main: only wiring + timeouts
[ ] go test ./... green
[ ] go.mod pin kit aligned
[ ] README curl example
[ ] no critical TODO in the core
[ ] layer diagram in PR (ascii OK)
[ ] explicit: we do not use log as test
```

All green → 07.10. Anything red → ticket before observability.

### Step 14 — predict-then-answer: “just one smell”

**Predict-then-answer E**

Question: service imports `encoding/json` only to log a struct — allow?

- Predict: “OK because it is not http”.
- Answer: still a smell for StringService. Logging structures is better done by middleware (07.11) with truncate. Do not widen the import surface “for debug”.

**Predict-then-answer F**

Question: no endpoint test, but there is httptest — gate?

- Predict: “OK, integration covers”.
- Answer: conditionally yellow. httptest is slower and mixes layers. For the course: add at least one endpoint unit test before you stack log middleware.

### Step 15 — walkthrough: what happens if you skip the gate

Scenario: skip → 07.10 Finalizer logs `code=500` for empty string because you panicked on type assert in the endpoint.

- SRE sees a 500 spike.
- Thinks infra.
- Real bug: `request.(T)` without `ok`.
- Logs were loud; diagnosis slow because there is no unit test that fails in 10ms.

The gate would have caught assert discipline *before* log noise.

### Step 16 — linking to 07.10–07.12 (without stealing their topics)

This lesson does *not* implement logging. It only prepares the ground:

| After the gate | Lesson | You get |
|----------------|--------|---------|
| transport access log | 07.10 | status, path, request id |
| application log | 07.11 | method, took, err around Service |
| metrics | 07.12 | RED, histogram |

If the gate is red — those lessons measure the wrong thing.

### Step 17 — walkthrough: cancel / timeout through layers

Client closes the connection or server `context` expires:

1. `ctx` in the transport handler becomes canceled.
2. Endpoint passes the same `ctx` into `svc.Uppercase`.
3. If service (later with I/O) respects `ctx.Done()`, it returns `ctx.Err()`.
4. Status mapping: often 499/client closed or 504 — **team agreement**, not guessing in the log.

Gate question: does *anywhere* swallow `ctx.Err()` and return `nil`? That is a hole a Finalizer will not explain well.

**Predict-then-answer G**

Question: must StringService *read* `ctx` today?

- Predict: “yes, otherwise gate fail”.
- Answer: for pure CPU Uppercase often `_ = ctx` or just the signature. The gate asks for *signature discipline* (`ctx` first) and that you do not swallow cancel when I/O arrives. It does not force fake I/O for a checkbox.

### Step 18 — review comments that are worth it (template)

When reviewing someone else’s PR before 07.10, use concrete comments:

- “This validate belongs in service — decode stays wire.”
- “Add a table case for `ErrEmpty` before we merge logging.”
- “`request.(T)` → `ok` branch + test.”
- “Error style here is B, in Count A — align or ADR.”
- “I will not approve observability until `go test ./internal/service` is green.”

Avoid: “lgtm”, “we’ll see in the logs”, “temporarily OK”.

### Step 19 — what is *not* part of this gate

Consciously you do *not* block for:

- lack of Prometheus metrics (07.12)
- lack of request id (07.10)
- lack of LoggingMiddleware (07.11)
- perfect OpenAPI
- 100% coverage

The gate blocks for **boundaries, core tests, error mapping**. The rest is the next floor.

### Step 20 — mechanism wrap-up: Continue / Refactor decision

| Decision | When |
|----------|------|
| **Continue** | checklist green; tests; thin decode; arrow OK |
| **Refactor** | http in service; business in decode; no tests; cycle |
| **Narrow yellow** | only README/curl/timeouts then immediately 07.10 |

Do not “partially green then log”. Observability is not a bandage for architecture.

Write in notes (one sentence):

> Gate 07.09: **Continue** / **Refactor** because _________.

Without that sentence, the next lesson starts in fog.

### Step 21 — request walkthrough poster (forbid yourself to skip)

Before you mark the gate green, out loud (or in the PR) fill:

```
Happy:
mux → [Before?] → decode → endpoint assert → service Uppercase → encode → client

ErrEmpty:
decode OK → service ErrEmpty → style A/B → status ? → client

Wire fail:
decode err → (no service) → ErrorEncoder → status 400
```

If you cannot fill status `?` for ErrEmpty — the error map is not done.

### Step 22 — what you do when a colleague says “lgtm, add log”

Answer template:

> Gate 07.09 is not green yet: missing ____. Logging PR only after ____ tests / decode refactor. Otherwise Finalizer measures the wrong thing.

That is not blocking for ego — that is protecting the observability signal.

## Rules and syntax

1. **Gate before log/metrics** — observability does not fix boundaries.
2. **`service` without `net/http`** — hard rule of this path.
3. **Thin decode** — wire shape; domain in service.
4. **Tests > logs** — assertion in `*_test.go`, not in Loki.
5. **One error style A/B** — document before status mapping.
6. **Type assert with `ok`** — panic is not 400.
7. **`go test ./...` green** before merging an observability PR.
8. **`-race` on critical packages** when there is shared state.
9. **Thin main** — wiring, env, server lifecycle.
10. **Pin kit** aligned with 07.03.
11. **README curl** — manual confirmation is not a substitute for a test, but helps onboarding.
12. **No critical TODO** in the core “for after logs”.
13. **Diagram in PR** — ascii layers enough.
14. **Second transport litmus** — mental gRPC boundary test.

## Examples

### Example 1 — checklist fully green

The team has:

- `service` table test
- endpoint test with fake svc
- decode without domain
- ErrorEncoder for `ErrEmpty` → 400
- README curl

### What happens here

Gate passed. The next PR may add `ServerErrorLogger` / Finalizer without fear of measuring chaos.

### Example 2 — service imports `net/http` “only for status”

```go
// anti-pattern
func (s stringService) Uppercase(ctx context.Context, str string) (string, error) {
    if str == "" {
        return "", &httpError{code: 400, msg: "empty"}
    }
    ...
}
```

### What happens here

HTTP leaking into the domain. Another transport cannot use the same error cleanly. Review: remove; return sentinel; map in transport.

### Example 3 — “tests” = watching logs on staging

No `TestUppercase`. Deploy. `kubectl logs`. “Looks OK”.

### What happens here

Gate fail. Log is not a test. Add a table test *before* 07.10.

### Example 4 — decode rejects empty string

```go
if req.S == "" {
    return nil, errEmptyFromDecode
}
```

### What happens here

Domain in the wire layer. Curl works; gRPC tomorrow duplicates the rule. Move to service.

### Example 5 — endpoint panic on cast

`req := request.(uppercaseRequest)` without `ok`. A bad test sends `nil`.

### What happens here

500 instead of a controlled error. Fix: `ok` branch + test. Not “log the panic”.

### Example 6 — green unit, red curl

Tests OK, but mux route wrong (`/upper` vs `/uppercase`).

### What happens here

Gate yellow: add README curl or a thin httptest. Observability later helps, but first fix the route.

### Example 7 — style A and style B mixed per method

Uppercase style A; Count style B. ErrorEncoder half-done.

### What happens here

Review requires alignment *before* metrics label strategy (07.12). Otherwise “error rate” lies.

## Decision analysis

| Option | When you choose | Risk |
|--------|-----------------|------|
| Continue to 07.10 | checklist green | low |
| Refactor boundaries | http in service / business in decode | delays log, saves later |
| Only httptest, no unit | demo urgency | medium — return unit quickly |
| Skip gate | “we’ll see in production” | high — expensive debug |
| Coverage idol | chase % | false safety; critical branches matter more |
| Document A/B style | always before status map | low cost, high clarity |

## Trade-offs

- **Review costs an hour** — saves days of log archaeology.
- **More tests** — CI a bit slower; feedback much faster.
- **Strict no-http in service** — sometimes awkward for a “quick hack”; long-term cheaper.
- **Thin decode** — more lines in service validation; one truth for all transports.
- **Not logging yet** — less visibility briefly; cleaner signal-to-noise after.

## Common mistakes

1. Skip review because “works on my laptop”.
2. Only happy path test.
3. Log as a substitute for `testing.T`.
4. Metrics/log before fixing boundaries.
5. Silent swallow (`_ = err`).
6. Dead code / critical TODO in the core.
7. Wrong module path / unpin kit.
8. Business in decode.
9. `net/http` in service “temporarily”.
10. Panic type assert.
11. Mixing error style A/B.
12. main with business logic.
13. No ErrorEncoder / mapping for sentinel.
14. No README how to run.

## Idiomatic Go

- Small, focused PR for the gate (checklist + test fix), separate from the logging PR.
- Table-driven tests in the service package.
- `errors.Is` / sentinel, not string compare.
- `go test -race` when it makes sense; always `go test ./...`.
- Clear package imports; `internal/` boundaries.
- Comments for *why* (error style), not *how* line by line.

## Practical scenario

A team wants an “observability sprint”. Tech lead imposes a **core review gate**: without a green checklist there is no log ticket.

Finds: `ErrEmpty` mapped to 500 because the endpoint returns style B, and ErrorEncoder treats everything as internal. Fix: 20 lines + test. Only then 07.10 Finalizer shows a meaningful `code=400`.

Without the gate SRE would spend a week looking at a 500 spike and restarting pods.

## Summary

- Core Service Review is a **gate** before 07.10–07.12.
- Check dependencies, thin decode, tests, error mapping, thin main.

## Going deeper: core review gate

### 1. insight

**Coverage is not an idol; critical branches are.** 100% lines with one happy path still miss `ErrEmpty`. The gate asks for *branches*, not %.

Practical check: does your service test cover empty string and at least one success?

### 2. insight

**A PR diagram reduces review time.** An ascii arrow transport → endpoint → service prevents “put it in utils” comments.

Practical check: put a diagram in the next PR description (5 lines enough).

### 3. insight

**README curl is not vanity.** Onboarding and incident response use the same one-liner. Not a substitute for a test — a complement.

Practical check: can someone new hit the endpoint in 60s without asking?

### 4. insight

**Timeouts in main are part of “operability core”.** The gate will not dig deep into 04.02, but missing ReadHeaderTimeout is a hole before log noise.

Practical check: does `http.Server` have at least ReadHeaderTimeout?

### 5. insight

**Sentinel stability.** If `ErrEmpty` disappears or becomes wrapped without `errors.Is` discipline, ErrorEncoder breaks — metrics later lie.

Practical check: does mapping use `errors.Is(err, service.ErrEmpty)`?

### 6. insight

**Endpoint names consistent.** `MakeUppercaseEndpoint` / metric `uppercase` — stable vocabulary for 07.12. URL is not the name.

Practical check: does the use-case name live outside the path string?

### 7. insight

**Mux method patterns (Go 1.22+).** Wrong method → 405; do not mix with a domain error. Gate: document method in README.

Practical check: curl with GET on a POST route — expected status?

### 8. insight

**Graceful shutdown present?** Observability incidents often mix deploy kill and app bug. Shutdown discipline reduces false alarms.

Practical check: do you catch signal and `Shutdown` ctx?

### 9. insight

**Config struct instead of scattered `os.Getenv`.** Gate smell: 15 Getenv in main without default/validate.

Practical check: one `Config` structure + defaults?

### 10. insight

**No global var mutation.** Tests that change package-level svc = flake factory. Prefer DI through `New` / constructor.

Practical check: do parallel tests (`t.Parallel`) touch a global?

### 11. insight

**`go vet` / `go test` as entry to an observability PR.** If vet is not clean, a log PR must not hide it.

Practical check: `go vet ./...` quiet?

### 12. insight

**Prepare fields you want later in the log** (`method`, `err`, `took`) — but *do not implement* them here. Only an awareness checklist.

Practical check: list of 5 keys you expect in 07.10/07.11.

### 13. insight

**Do not mix `fmt.Println` debug.** Gate: remove Println from service before merge. Otherwise 07.10 gets two formats.

Practical check: `rg "Println|Printf" ./internal/service` empty?

### 14. insight

**Review is discipline, not heroism.** Same checklist every time. Team gate > ad-hoc “lgtm”.

Practical check: save the checklist in team wiki / handbook snippet.

### Quick recap

- Gate = dependencies + tests + thin decode + errors + thin main.
- Log ≠ test.
- Happy + `ErrEmpty` walkthrough mandatory.
- Litmus: second transport without touching service?
- Continue / Refactor explicit.
- 07.10 only after green.
