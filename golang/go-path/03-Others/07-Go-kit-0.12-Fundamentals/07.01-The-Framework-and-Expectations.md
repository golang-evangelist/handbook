## Problem this lesson solves

When you hear “microservices framework,” the brain often expects magic: auto-DI, auto-routing, auto-config. go-kit is not that. It is a **toolkit**: a set of packages and layer agreements. If you expect magic, you will be disappointed and write business logic in a decode function. If you expect layering, you get a testable service that exposes the same use-case over HTTP and gRPC.

This lesson calibrates expectations before you write code in 07.05+.

## Mental model

Three layers (inside out):

1. **Service** — plain Go `interface` + implementation. Business rules. Does not know JSON, HTTP status, protobuf.
2. **Endpoint** — `endpoint.Endpoint`: adapter that takes `context.Context` and `request interface{}`, returns `(response interface{}, error)`. Closes over (closure) a reference to the service. `endpoint.Chain` middleware lives here.
3. **Transport** — encode/decode at the wire edge. `httptransport.NewServer(endpoint, decode, encode)` or gRPC equivalent. HTTP headers, status codes, body limits live here.

```text
HTTP/gRPC request
        │
        ▼
┌───────────────────┐
│ Transport         │  decode → typed request struct
│ (http / grpc)     │  encode ← typed response struct
└─────────┬─────────┘
          │ interface{}
          ▼
┌───────────────────┐
│ Endpoint (+ MW)   │  type assert, call service method
└─────────┬─────────┘
          │ typed arguments
          ▼
┌───────────────────┐
│ Service           │  business logic
└───────────────────┘
```

Analogy: service is the kitchen (recipes). Endpoint is the waiter who orders from the kitchen without knowing whether the order came from the counter or an app. Transport is counter / delivery.

## Mechanism

This section is the core of the lesson. Read it slower than the examples. At “Predict” stops, pause and answer before reading the solution.

### What go-kit is

go-kit is a programming toolkit for microservices (and tidy monoliths) in Go. Goal: solve recurring architecture problems — layering, middleware, pluggable transport — so focus stays on business value.

From the project README: *“a programming toolkit for building microservices”*. Key word is **toolkit**, not framework.

What that means in practice:

- you write `main` and explicitly wire pieces;
- you choose which packages to import (`endpoint`, `transport/http`, `log`, `metrics`…);
- you decide whether you need gRPC, HTTP, or both;
- kit does not impose deployment, configuration, or orchestration (those are non-goals in documentation).

### What go-kit is not

| Expectation | Reality |
|------------|-----------|
| DI container like Spring | None; wiring manually in `main` or factory functions |
| “Controller” base class | None; service is your `interface` |
| ORM / migrations | None; you use `database/sql` or your own layer |
| Auto-routing by annotations | None; you register handlers explicitly |
| Mandatory Consul/etcd | None; discovery is optional / often platform (k8s DNS) |

If you need an opinionated full-stack framework, kit is not that tool. If you need layer discipline + same middleware on multiple transports — it is.

### Signature you must remember: Endpoint

In go-kit **0.12** the type is (non-generic):

```go
package endpoint

import "context"

// Endpoint is the fundamental building block of servers and clients.
type Endpoint func(ctx context.Context, request interface{}) (response interface{}, err error)
```

Remember three things:

1. `request` and `response` are `interface{}` — typing is done with assert in the endpoint factory function.
2. There is no `endpoint.Endpoint[TReq, TRes]` in 0.12. If in modern code you make a small generic helper, that is **your local code**, not go-kit API.
3. `error` from endpoint and “business error in response struct” are two different patterns; the course separates them in 07.06–07.08.

### Middleware as higher-order function

```go
type Middleware func(Endpoint) Endpoint
```

Middleware takes Endpoint and returns a new Endpoint (often a function literal / closure that logs, measures, traces, then calls `next`).

`endpoint.Chain(outer, inners...)` composes order: first argument is outermost.

```go
e = endpoint.Chain(loggingMW, metricsMW, tracingMW)(e)
```

Predict: if `loggingMW` logs before and after `next(ctx, req)`, and `metricsMW` measures duration inside itself — which middleware “sees” the other’s time included?

Answer: depends on order in `Chain`. If logging is outside, its `took` includes metrics overhead. That is why you document MW order in the team README.

### Transport: NewServer

For HTTP (package `github.com/go-kit/kit/transport/http`, in code often alias `httptransport`):

```go
handler := httptransport.NewServer(
    uppercaseEndpoint,
    decodeUppercaseRequest,
    encodeResponse,
)
```

`NewServer` returns something that implements `http.Handler`. Decode reads `*http.Request` → `interface{}`. Encode writes `interface{}` → `http.ResponseWriter`. **Service is not called from decode.**

### One HTTP request walkthrough (concrete)

Scenario: client sends `POST /uppercase` with body `{"s":"go"}`. Goal: response `{"v":"GO"}`.

Step by step:

1. **net/http** (Go 1.22+ mux) receives request on `/uppercase` and passes to `httptransport.Server`.
2. **Transport Before** (optional): e.g. put request id in `context`.
3. **decodeUppercaseRequest**: `json.NewDecoder(r.Body).Decode(&req)` into `uppercaseRequest{S string}`. Returns `req` as `interface{}`. Does not call service. Does not do business validation like “is string empty” if that is domain rule — that is service (`ErrEmpty`).
4. **Endpoint** (maybe through Chain MW): type assert `req.(uppercaseRequest)`, calls `svc.Uppercase(ctx, req.S)`, packs `uppercaseResponse{V: v}`.
5. **Service**: `strings.ToUpper(s)` or your rules; returns `(string, error)`.
6. **encodeResponse**: `json.NewEncoder(w).Encode(response)`.
7. Client sees JSON.

Predict: where would you put check “Content-Type must be application/json”?

Answer: transport (decode or ServerBefore). That is wire contract, not business rule about strings.

Predict: where would you put “empty string is invalid input for Uppercase”?

Answer: service (domain). Same rule must hold if you add gRPC transport tomorrow.

### Why three files / three packages instead of one handler

One `http.HandlerFunc` doing JSON + ToUpper + log + metrics works for demo. It breaks when:

- you add second transport;
- you want to test ToUpper without `httptest`;
- middleware must be shared between methods;
- team grows and review wants boundaries.

Kit does not make Hello World shorter. It makes **boundaries explicit** when the service outgrows one file.

### Link to modules 04 and 05

- **04**: plain `net/http`, middleware, timeout, graceful shutdown — still valid. Kit HTTP server is `http.Handler`; you host it on the same server.
- **05**: gRPC / multiple protocols — kit endpoint layer is where you share use-case between HTTP and gRPC without copying rules.

If you do not master `context` cancellation and HTTP basics, return to 04 before deep kit.

### Explicit wiring (mental code in main)

```go
func main() {
    logger := log.NewLogfmtLogger(os.Stderr)

    var svc StringService
    svc = stringService{}              // pure implementation
    // svc = loggingMiddleware{logger, svc}  // later 07.11
    // svc = instrumentingMiddleware{...}    // later 07.12

    uppercase := makeUppercaseEndpoint(svc)
    // uppercase = endpoint.Chain(...) (uppercase) // later

    r := http.NewServeMux()
    r.Handle("/uppercase", httptransport.NewServer(
        uppercase,
        decodeUppercaseRequest,
        encodeResponse,
    ))

    // http.Server{Addr, Handler: r, ReadHeaderTimeout: ...}.ListenAndServe()
}
```

No reflection. No “component scan.” That is intentional.

### Going deeper: what happens in memory (conceptual)

When `httptransport.NewServer` handles a request, conceptual order is:

1. `context` for request is allocated / used (cancel when client closes — details depend on server settings);
2. decode function reads body into stack/heap struct (e.g. `uppercaseRequest`);
3. returned as `interface{}` — concrete type still lives “under” interface value;
4. endpoint function literal closes over (closure) variable `svc` from outer scope of factory function;
5. type assert extracts concrete struct;
6. service method does work; return values packed into response struct;
7. encode writes bytes to network.

Why this matters: bug “decode returns pointer, endpoint expects value” is common. Discipline: agree in team decode **always** returns same shape (value or pointer) endpoint asserts.

Predict: decode does `return &req, nil`, endpoint does `request.(uppercaseRequest)` without star. What do you get?

Answer: assert fails (or `ok == false` branch). Types must match: both pointer or both value.

### Going deeper: dependency direction (why review breaks)

Write direction as team rule, not decoration:

```text
transport  →  endpoint  →  service  →  (domain types, repo interface)
     │              │
     └──── net/http, json, proto (only here) ────┘
```

What **may** import what:

| Package | May | Must not |
|-------|-----|--------|
| `internal/service` | `context`, `errors`, own domain, repo `interface` | `net/http`, `encoding/json`, `httptransport`, protobuf generated in domain file “for convenience” |
| `internal/endpoint` | `endpoint`, service `interface`, DTO from agreed place | SQL driver, direct read of `*http.Request` |
| `internal/transport/http` | `httptransport`, `net/http`, `encoding/json`, endpoint factory | business rules (`strings.ToUpper` “because short”) |
| `cmd/.../main` | wires everything | business logic longer than few setup lines |

Predict: `internal/service` file does `import "net/http"` only to return `http.StatusBadRequest` as `int` in error. What is the problem?

Answer: HTTP status is transport concern. Domain needs `var ErrEmpty = errors.New(...)` (or typed error); mapping to 400 is ErrorEncoder / encode branch in 07.08. Otherwise gRPC transport has nowhere to put that `int`.

### Going deeper: Chain order with measurement

Suppose three middlewares:

```go
loggingMW   // logs method, took = time.Since(begin) after next
metricsMW   // Histogram.Observe(seconds) after next
authMW      // rejects before next if no token
```

Team wants: “do not measure unauthenticated requests” and “log always sees auth outcome.”

One valid arrangement:

```go
e = endpoint.Chain(loggingMW, authMW, metricsMW)(e)
```

Conceptual call stack (outside → inside):

1. logging enters, starts clock;
2. auth enters — if fail, returns error **without** metrics Observe (metrics never entered);
3. metrics enters only for allowed;
4. core endpoint + service;
5. return through metrics → auth → logging.

Predict: if you put `metricsMW` **outside** `authMW`, what happens to histogram on 401?

Answer: metrics count rejections too — sometimes desired (attack / scan), sometimes not (SLO only for authed traffic). So order is not decoration: product decision. Document it in README next to `Chain(...)` call.

### Going deeper: two schools of errors (calibration, not implementation)

Kit stringsvc examples historically mix two styles. Course separates later; here so you do not “guess” wrong mental model:

**Style A — error in response struct**

```go
type uppercaseResponse struct {
    V   string `json:"v,omitempty"`
    Err string `json:"err,omitempty"`
}
// endpoint returns (uppercaseResponse{Err: "..."}, nil)
```

HTTP often stays 200; client reads `err` field. Simple for demo JSON; worse for generic HTTP clients that only look at status.

**Style B — real `error` from endpoint**

```go
// endpoint returns (nil, ErrEmpty) or (resp, err)
// transport ErrorEncoder maps to 400/500
```

Better for idiomatic HTTP; needs error → status mapping agreement.

Predict: may you use style A for Uppercase and style B for Count in **same** service?

Answer: technically yes, product-wise chaos. Pick one contract per API surface and stick to it. 07.06–07.08 build discipline.

### Going deeper: service decorator vs endpoint middleware

Two levels of “wrappers” are not the same type:

```go
// A) endpoint.Middleware — sees interface{} request/response
type Middleware func(Endpoint) Endpoint

// B) service decorator — sees typed methods of your interface
type loggingMiddleware struct {
    logger log.Logger
    next   StringService
}
func (mw loggingMiddleware) Uppercase(ctx context.Context, s string) (string, error) {
    // ...
    return mw.next.Uppercase(ctx, s)
}
```

When to choose what:

| Need | Prefer |
|---------|------------|
| Same behavior for HTTP and gRPC over **same** endpoint | `endpoint.Middleware` / `Chain` |
| Logging typed arguments without assert | service decorator |
| Metric by method name with label from DTO | often endpoint MW (have request after decode) or service MW (have `s string`) |
| Auth reading HTTP header | transport `ServerBefore` / HTTP middleware — header not yet “lost” in DTO |

Predict: you put JWT check in service decorator. What do you lose?

Answer: service now depends on auth vocabulary; domain unit tests pull tokens. Auth at transport/endpoint edge keeps `StringService` clean for `Uppercase` rules.

### Going deeper: one service, many methods (map without code)

Strings example is not one route forever. Mental map for N use-cases:

```text
StringService
  ├─ Uppercase  → makeUppercaseEndpoint  → POST /uppercase
  ├─ Count      → makeCountEndpoint      → POST /count
  └─ ...        → make...Endpoint        → ...

shared encodeResponse (often)
per-route decode*Request (almost always)
optional: endpoint.Chain per route or shared chain
```

Why decode rarely shares 1:1 with encode: request shapes differ; response shape (JSON object + possible ErrorEncoder) often stays same.

Predict: can one `endpoint.Endpoint` serve both Uppercase and Count?

Answer: bad idea. One Endpoint = one use-case adapter. Otherwise you return to god-handler with `switch` on path inside endpoint — layer purpose lost.

### Going deeper: context through three layers

`context.Context` travels:

```text
http.Request.Context()
        → NewServer passes to decode(ctx, r)
        → same ctx in Endpoint(ctx, request)
        → svc.Uppercase(ctx, s)
        → repo/DB calls with ctx
```

What context **carries** (typical): deadline, cancel, request id, span, auth claims (if MW inserted).

What context **must not carry** (anti-pattern): huge structs “so I would not change signature,” mutable request cache without discipline.

Predict: service ignores `ctx` and calls DB without it. What breaks in production?

Answer: client cancels request, handler returns, query still runs — consumes pool, sometimes writes result nobody waits for. Module 04 already taught this; kit does not magically fix ignored `ctx`.

## Rules and syntax

1. Domain (service) does not import transport packages (`net/http`, `httptransport`, protobuf runtime in domain file).
2. Endpoint is adapter: type assert + call typed service method.
3. Middleware is `func(Endpoint) Endpoint` or service decorator of same `interface` — do not mix levels without need.
4. Wiring is explicit in `main` (or `cmd/.../main.go`).
5. One service, N transports — shared endpoints.
6. Pin `github.com/go-kit/kit v0.12.0` in `go.mod`; logger via `github.com/go-kit/log`.
7. Do not invent API outside documentation of version you pin.
8. Test service without HTTP server.
9. Decode does not call service.
10. `interface{}` request/response requires DTO struct naming discipline.

## Examples

### Example 1 — wrong DI expectation

“go-kit will inject dependencies like Spring.”

### What happens here

It will not. You construct `stringService{}`, pass it to `makeUppercaseEndpoint(svc)`, mount handler. If you want DI library, that is separate choice — not part of kit.

### Example 2 — three layers in names

```go
type StringService interface {
    Uppercase(ctx context.Context, s string) (string, error)
}

func makeUppercaseEndpoint(svc StringService) endpoint.Endpoint {
    return func(ctx context.Context, request interface{}) (interface{}, error) {
        req := request.(uppercaseRequest) // in production: ok form
        v, err := svc.Uppercase(ctx, req.S)
        return uppercaseResponse{V: v}, err
    }
}

func decodeUppercaseRequest(_ context.Context, r *http.Request) (interface{}, error) {
    var req uppercaseRequest
    err := json.NewDecoder(r.Body).Decode(&req)
    return req, err
}
```

### What happens here

Service sees `string`. Endpoint sees `interface{}` and DTO. Transport sees `*http.Request`. Boundaries are in types.

### Example 3 — same endpoint, second transport (idea)

HTTP decode reads JSON. gRPC decode reads proto message into same `uppercaseRequest` (or parallel DTO). Both call same `makeUppercaseEndpoint(svc)`. Uppercase business rule exists once.

### What happens here

Why kit “pays off” only when you have more than one transport or heavy middleware chain — otherwise plain net/http may be simpler.

### Example 4 — pin version

```bash
go get github.com/go-kit/kit@v0.12.0
go get github.com/go-kit/log@v0.2.0
```

### What happens here

Reproducible build. Mixing tutorials with different log import path without reading `go.mod` creates “ghost” errors.

### Example 5 — generic helper (local, not kit)

```go
// THIS IS NOT go-kit API. Local helper in your package.
func TypedEndpoint[In, Out any](
    f func(ctx context.Context, in In) (Out, error),
) endpoint.Endpoint {
    return func(ctx context.Context, request interface{}) (interface{}, error) {
        in, ok := request.(In)
        if !ok {
            return nil, fmt.Errorf("invalid request type")
        }
        return f(ctx, in)
    }
}
```

### What happens here

In modern Go 1.22+ code generics help. Mark clearly helper is local. In 0.12 `endpoint.Endpoint` remains non-generic `func`.

### Example 6 — wrong layer: SQL in decode

```go
func decodeCreateOrder(_ context.Context, r *http.Request) (interface{}, error) {
    var req createOrderRequest
    if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
        return nil, err
    }
    // ANTI-PATTERN: decode must not write to database
    if err := db.ExecContext(r.Context(), `INSERT INTO orders...`); err != nil {
        return nil, err
    }
    return req, nil
}
```

### What happens here

Decode became use-case. You lose: transactional boundaries in service, test without DB for JSON validation, ability for same create over gRPC. Fix: decode only fills struct; service does persistence.

### Example 7 — predict status code

Endpoint returns `(uppercaseResponse{Err: "empty string"}, nil)` — Go `error` is `nil`, message in field. Predict: which HTTP status does client see if encode only does `json.Encode` without ErrorEncoder branch?

### What happens here

Usually **200 OK** with JSON body containing error. That is pedagogical stringsvc pattern (style A). Alternative (style B): return real `error` from endpoint and map in ErrorEncoder to 400/500. Course separates styles in 07.06–07.08 — here only calibrate that “no error” ≠ “no business error.”

### Example 8 — Closure in factory function

```go
func makeUppercaseEndpoint(svc StringService) endpoint.Endpoint {
    return func(ctx context.Context, request interface{}) (interface{}, error) {
        // this function literal closes over svc — that IS closure
        req := request.(uppercaseRequest)
        v, err := svc.Uppercase(ctx, req.S)
        return uppercaseResponse{V: v}, err
    }
}
```

### What happens here

Without closure you would need global service or struct method carrying dependency differently. Kit examples almost always use factory + closure. Term **closure** stays in English.

## Decision analysis

| Choice | When it makes sense |
|-------|-----------------|
| Plain `net/http` without kit | Small service, one transport, thin middleware |
| go-kit layers | Multiple transports, shared endpoint middleware, team discipline |
| Other framework (Echo/Fiber + own layer) | Team already has standard; kit is not dogma |
| Generic local helper around Endpoint | Reduces assert boilerplate; document it is not kit type |
| Copy old strings example 1:1 | Good for learning shape; bad if blindly copying stale imports |

## Trade-offs

- **More files / packages** vs **clear boundaries and tests**.
- **`interface{}` on endpoint** vs **flexible transport**; cost is asserts and DTO discipline.
- **Explicit wiring** vs **shorter main in magical frameworks**; you gain readability and control.
- **Learning kit vocabulary** vs **faster start with one handler**; course chooses long-term clarity.
- **Pin 0.12** vs **newest main branch**; course sacrifices bleeding-edge for reproducibility.

## Common mistakes

1. Expecting magic DI / auto-config.
2. Business logic in `decode` or HTTP handler beside kit server.
3. Import `net/http` in service package “only for StatusBadRequest.”
4. Mixing `kit/log` and `go-kit/log` paths without `go.mod` check.
5. Learning from stale blog as if it were 0.12 API.
6. Premature kit on literal Hello World without need for layers.
7. Invented API (`Endpoint[T]`, nonexistent metrics/tracing methods).
8. Testing only through live port — service stays untested in isolation.
9. Swallowing errors in encode instead of clear ErrorEncoder pattern (more in 07.08).
10. Treating kit as replacement for understanding `context` and HTTP timeout from 04.

## Idiomatic Go

Idiomatic kit project in Go 1.22+:

- `cmd/stringsvc/main.go` — wiring, `http.Server` with `ReadHeaderTimeout`, signal for shutdown;
- `internal/service` — `interface` + unexported impl + tests;
- `internal/endpoint` — `make*Endpoint` factory functions;
- `internal/transport/http` — decode/encode + `NewServer`;
- errors as values (`var ErrEmpty = errors.New("empty string")`);
- `context.Context` as first argument of service methods;
- no global mutable state for logger — pass through middleware / constructor.

## Practical scenario

Team has pricing use-case that must work over REST (partners) and gRPC (internal mesh). Without endpoint layer, rules for “rounding” and “currency not supported” end copied in two handlers and diverge for six months. With kit shape: one `PricingService` interface, endpoint factory per method, two transport packages. Code review asks: “is this domain or wire?” — and has where to comment.

## Summary

- go-kit 0.12 is layer toolkit, not magic framework.
- Service (interface) → Endpoint (`func` with `interface{}`) → Transport (`NewServer` + decode/encode).

## Going deeper: expectations and layering

### 1. insight

Kit README explicitly says toolkit. In review, if PR adds “framework core” package hiding wiring behind reflection, ask why — that is not kit style.

### 2. insight

Hexagonal / ports-and-adapters spirit: service is inside, transport is adapter. Kit only gives agreed types for ports.

### 3. insight

`interface{}` on endpoint is historical design (before generics in Go). Live with it disciplined or add local generic helper — but do not claim that is kit 0.12 type.

### 4. insight

One monolithic `handlers.go` of 2000 lines signals you need layering, not necessarily kit. Kit is one way; clean internal package split is another.

### 5. insight

Endpoint middleware sees request/response as `interface{}` and `error`. Service middleware sees typed methods. Choose level by what types you need.

### 6. insight

Observability (log, metrics, trace) is not “fourth layer of business logic.” Those are cross-cutting concerns around endpoint/service. Course separates them in 07.10+.

### 7. insight

Service discovery in production 2020s is usually platform (Kubernetes Service DNS, mesh). `kit/sd` exists but is not mandatory design center — 07.14.

### 8. insight

Tracing: modern default is OpenTelemetry around endpoint, not necessarily old Zipkin-only tutorial. 07.15.

### 9. insight

Kit does not replace protobuf contracts. gRPC transport adapts messages; schema still lives in `.proto`.

### 10. insight

If you do not see API on `pkg.go.dev` for `@v0.12.0`, do not learn it from Stack Overflow snippet.

### 11. insight

`go-kit/log` structured keyvals (`key, value, key, value`) are part of example culture. Log level semantics are not same as `slog` — comparison in 07.10.

### 12. insight

Plain net/http service from 04 can “grow” into kit shape gradually: first extract service interface, then endpoint, then replace handler with `NewServer`.

### 13. insight

Code review question that saves weeks: “Does this import violate dependency direction?”

### 14. insight

Document in team handbook: “we use kit 0.12; logger = go-kit/log; no generic Endpoint type from kit.”

### Quick recap

- Toolkit ≠ framework.
- Three layers; domain inside.
- Endpoint signature is non-generic in 0.12.
- Wiring explicit; pin versions.
- Observability and SD come later, in right place.
