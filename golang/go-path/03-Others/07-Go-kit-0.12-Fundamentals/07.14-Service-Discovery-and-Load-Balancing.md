# 07.14 Service Discovery and Load Balancing

> **Go Path - Zero to Gopher** / **03 Others → Go kit 0.12 Fundamentals** / Lesson 07.14

## Lesson goals

After this lesson you should be able to:

- explain the **problem** of service discovery (SD) and load balancing (LB) without dogma
- distinguish the **production default** (Kubernetes DNS, cloud LB, mesh) from the **historical** kit/sd + Consul tutorial
- describe `kit/sd` **only at a high level** (Instancer → Endpointer → LB) if you mention it — without inventing API
- list what still remains **yours**: health, timeout, retry policy, connection reuse
- prefer **less in-app SD code** when the platform already does discovery
- write a short **ADR** of the SD choice for your context

## Prerequisite

- 07.13 — visibility checklist green (gate)
- basics: DNS service name, or at least the concepts Kubernetes Service / cloud load balancer
- 07.08 — HTTP transport; awareness of gRPC as another transport (05.x arc)

## Problem this lesson solves

Old tutorials push Consul + `github.com/go-kit/kit/sd` as a mandatory ritual. In many 2020s productions discovery is done by the **platform**: kube-dns / CoreDNS, cloud service discovery, service mesh. If you blindly copy-paste a 2017 blog, you get a second control plane without need — and lose time that should be spent on timeout/retry/health.

## Mental model

```
SD  = how the client (or proxy) learns WHICH instances exist
LB  = how it chooses WHICH instance gets the request

Server-side LB:  client → VIP/Service → backend pods
Client-side LB:  client knows the list → chooses (RR/least-conn…)

Modern default in k8s:
  stringsvc.default.svc.cluster.local  →  ClusterIP / endpoints
```

- **Kit/sd** exists in the go-kit 0.12 line for registrar/subscriber patterns — **check** maintenance and whether you need it.
- Course preference: **platform SD first**; in-app SD only when the platform does not cover the case.
- This is **not** a full Consul tutorial.

## Mechanism

### Step 0 — what SD solves (and what it does not)

Solves: IP changes, replica scaling, removing dead instances from the set.

Does not solve by itself: bad timeout, retry storm, missing health check, PII in log, red 07.13 checklist.

**Predict-then-answer A**

Question: does SD replace `/healthz`?

- Predict: “the registry knows everything”.
- Answer: no. Health (liveness/readiness) feeds LB decisions. Without health, SD can send traffic to a dead process.

### Step 1 — production default: platform

Typical paths:

| Environment | SD | LB |
|-------------|----|----|
| Kubernetes | Service DNS + Endpoints/EndpointSlice | kube-proxy / IPVS / eBPF; or mesh |
| Cloud VM | Cloud LB + target group / service discovery | cloud LB |
| Mesh (Istio/Linkerd/…) | sidecars + control plane | mesh policy |
| Local lab | docker compose DNS / localhost | often no real LB |

For StringService in k8s: the client calls the DNS name; it does **not** hardcode the pod IP.

### Step 2 — what you implement in the Go process

Often **little** SD code:

1. Listen on `:8080` (or env port).
2. Expose `/healthz` (and readiness if needed).
3. Use `http.Client` with timeouts and connection reuse (`Transport` pool).
4. Retry policy **conscious** (idempotency!).
5. Metrics/logs from 07.10–07.13.

You do not have to write a Consul registrar to be a “real microservice”.

### Step 3 — kit/sd at a high level (without fantasy)

In the go-kit ecosystem there is a chain idea (terms from docs/examples — **check your pin**):

```
Instancer  →  provides the instance set (updates)
Endpointer →  makes endpoint.Endpoint per instance
Balancer   →  chooses which endpoint to call (e.g. round-robin idea)
```

That is a **pattern** for client-side SD when you maintain the list yourself. Do not stamp from memory exact constructor names, `Register`/`Deregister` methods for Consul, or whether the package is deprecated in your pin.

Course rule: if you mention kit/sd — say “the pattern exists; I read the README for v0.12 before copy-paste”. **Do not invent** API.

**Predict-then-answer B**

Question: must you use Consul because `kit/sd/consul` exists in the tree?

- Predict: “yes, that is why it is there”.
- Answer: no. Package ≠ obligation. Platform DNS is often enough.

### Step 4 — health: liveness vs readiness

| Probe | Question | Typical effect |
|-------|----------|----------------|
| Liveness | is the process alive? | restart pod |
| Readiness | may it take traffic? | remove from LB |

Readiness fail during migration / warming = good. Liveness fail because of a temporary downstream timeout = often **bad** (restart loop).

Align the cloud/k8s probe with the real `/healthz` handler — not with `/metrics`.

### Step 5 — timeout

Without a timeout, goroutine and connection hang. In Go:

- `http.Server` ReadHeaderTimeout / ReadTimeout / WriteTimeout / IdleTimeout
- client: `http.Client.Timeout` or context deadline per request
- outbound: context propagation (07.15 will add span; timeout remains yours)

Document the budget: e.g. client 2s, server handler 1s, downstream 800ms.

### Step 6 — retry (caution)

Retry helps on a network blip. Retry on a **non-idempotent** POST can duplicate a side-effect.

Thumb rules:

- Retry only where it is safe (pure read, or idempotency key).
- Exponential backoff + jitter.
- Budget: max N attempts; not infinite.
- Do not retry 400 Bad Request / domain `ErrEmpty` — that is not transient.

**Predict-then-answer C**

Question: 3 services in a chain, each retry ×3 — how many calls at the bottom?

- Predict: “3”.
- Answer: up to 27 in the worst case (retry storm). Hence budget and one layer of retry policy.

### Step 7 — connection reuse

`http.Transport` keep-alive / HTTP/2 multiplexing (gRPC) reduces handshake cost.

Anti: new `http.Client{}` per request without a shared Transport → TIME_WAIT and latency.

For gRPC: long stream / managed channel — do not dial per RPC naively.

### Step 8 — HTTP LB vs gRPC LB

| | HTTP/1.1 through L4/L7 LB | gRPC (HTTP/2) |
|--|---------------------------|---------------|
| Connection | often short or keep-alive | long, multiplex |
| LB at L4 | can stickily hold on one instance | imbalance risk |
| Better | L7 or client-side / mesh understands h2 | headless + client LB or mesh |

Do not assume “same as REST behind nginx” automatically applies to gRPC. Document.

### Step 9 — walkthrough: request through a k8s Service

1. Client resolves `stringsvc.default.svc.cluster.local`.
2. ClusterIP → pod selection (iptables/IPVS/…).
3. Pod receives HTTP; your MW (log/metrics) work as usual.
4. If pod NotReady — it should not get traffic.
5. If pod dies mid-request — client sees error; retry policy decides.

Your Go code **does not have to** know about iptables.

### Step 10 — walkthrough: instance down

1. One of 3 pods crashes.
2. Endpoints update (short delay possible).
3. Stale connections may still error a bit.
4. Metrics: short error spike; rid shows connection errors.
5. Without health/readiness — longer black period.

### Step 11 — walkthrough: stale DNS TTL

1. Client caches DNS aggressively outside the cluster.
2. Scaling / deploy changes the set.
3. Traffic goes to an old IP.
4. Symptom: intermittent errors after deploy.

Mitigations: respect TTL, use platform in-cluster DNS, or mesh; do not hardcode IP.

### Step 12 — when (rarely) in-app kit/sd makes sense

- Multiple backends outside the k8s DNS model.
- Legacy Consul already in the org and must integrate.
- Special client-side LB algorithm the platform does not give.

Even then: thin layer, pin versions, test failure modes, ADR.

### Step 13 — anti-pattern: mandatory Consul dogma

“Microservice = Consul.” No. Microservice = clear boundaries + operability. Discovery is a platform detail.

### Step 14 — anti-pattern: copy 2017 API

Blogs go stale. `go doc` + kit v0.12 source > memory from Stack Overflow.

If handbook and docs diverge — **docs win for your pin**.

### Step 15 — security note

Do not expose instance IPs directly to the public internet “for SD”. Private network, NetworkPolicy, mTLS (often mesh).

SD is not authn. mTLS/mesh is a separate story — mention, do not implement the whole thing here.

### Step 16 — link with visibility (07.13)

When LB shifts traffic, your signals must work **per instance** (pod label in Prometheus). Rid still follows one request across one pod. SD does not replace rid.

### Step 17 — prefer less in-app SD code

Fewer moving parts:

- Fewer registrars that can “forget” to deregister.
- Less split-brain between Consul and k8s.
- Faster onboarding.

Move complexity to the platform team **deliberately** (with their SLA), not accidentally into every service.

**Predict-then-answer D**

Question: does “less code” mean “you have no LB”?

- Predict: “yes, single instance”.
- Answer: no. LB still exists — in Service/mesh/cloud. It is just not in your `main`.

### Step 18 — gRPC headless (orientation)

Pattern: headless Service → DNS returns pod A records → gRPC client-side LB. Details depend on the stack. For the course: know that a **difference** exists; read the implementation in gRPC docs when you get there.

### Step 19 — dependency map

Draw:

```
frontend → stringsvc (DNS)
stringsvc → (no downstream in lab) 
```

When you add Inventory: arrow + timeout budget + “who does SD for Inventory”.

### Step 20 — chaos mini thought

Kill one pod (`kubectl delete pod …`). Observe:

- whether error ratio stays in budget
- whether rid shows transient
- whether readiness removes traffic quickly

That is a better exercise than reading a Consul UI tutorial.

### Step 21 — ADR sketch (mandatory exercise)

```

Status: proposed
Context: k8s cluster …

Consequences: we depend on cluster DNS; no Consul operations
Alternatives: Consul + kit/sd; mesh
```

### Step 22 — what the lesson deliberately does not do

- Step-by-step Consul ACL/agent setup
- Invented `sd.MustRegisterEverything(...)` API
- Full mesh install guide
- Replacing 07.13 signals “because we have LB”

### Step 23 — request walkthrough (client in the same cluster)

```
1. app-A: http.Client GET/POST http://stringsvc/…
2. DNS resolve ClusterIP
3. packet → node → pod-B
4. ServerBefore rid
5. decode → endpoint → MW → service
6. response back on the same connection (reuse if keep-alive)
7. app-A: client metrics (if any) / error handling / retry?
```

### Step 24 — connect reuse vs load balance tension

A long keep-alive connection to **one** pod can reduce traffic spread after scale-up. Mesh/L7 or occasional refresh helps. Be aware; do not panic in a lab with 2 QPS.

### Step 25 — pin and reading

```
go doc github.com/go-kit/kit/sd
# read README in module cache for v0.12
# do not memorize every backend (consul, etcd, …)
```

Goal: know it exists, know when you **do not** need it.

### Step 27 — predict pack

**E.** Hardcode `10.0.0.15` in the client?  
Anti — the SD problem returns on every restart.

**F.** Retry on `ErrEmpty`?  
Usually no — domain, not network.

**G.** Does a kit Endpoint on the server require kit/sd?  
No. Endpoint is a use-case adapter; sd is a client/discovery story.

You understand SD vs LB, platform default, caution around kit/sd API fantasy, health/timeout/retry/reuse, gRPC note, preference for less in-app code. Next: distributed tracing (map of hops that SD/LB hide).

## Rules and syntax

1. Do not claim you must use Consul because kit has a package.
2. Prefer platform SD (k8s DNS, cloud LB, mesh).
3. Health (readiness/liveness) must exist and be aligned.
4. Timeout everywhere; document the budget.
5. Retry carefully — storm and idempotency.
6. Connection reuse; not a new client per request.
7. gRPC LB ≠ naive HTTP LB.
8. kit/sd only high-level; read docs before code.
9. Do not invent kit method / registrar API.
10. Less in-app SD code when you can.
11. Not a full Consul tutorial — do not turn the lesson into one.
12. Visibility (07.13) remains a prerequisite.
13. ADR for the SD choice.
14. Pin versions; blog ≠ truth.

## Examples

### Example 1 — k8s DNS

Client calls `http://stringsvc.default.svc.cluster.local:8080/uppercase`.

### What happens here

Platform SD + ClusterIP LB. Your `main` does not register Consul.

### Example 2 — kit/sd chain (idea)

Instancer → Endpointer → balancer → call `endpoint(ctx, req)`.

### What happens here

Client-side pattern **if** you do discovery yourself. Check API in the pin; do not copy blindly.

### Example 3 — headless + gRPC

Headless Service gives the pod IP list; gRPC client balances.

### What happens here

Client-side LB typical for h2; requires understanding, not copying REST habit.

### Example 4 — historical Consul registrar

Old example: process registers in Consul; clients subscribe.

### What happens here

May exist in legacy; not automatically the 2026 default for a k8s-native team.

### Example 5 — retry storm

Gateway retry ×3, service A retry ×3, B ×3.

### What happens here

Load amplification on the database. One retry layer + budget.

### Example 6 — no readiness

Deploy pulls a new pod that is not listening yet; LB sends 502.

### What happens here

Readiness probe on `/healthz` removes traffic until ready.

### Example 7 — new Client per request

```go
// anti-pattern (idea)
resp, err := (&http.Client{}).Do(req)
```

### What happens here

No reuse pool; cost and ephemeral port pressure.

## Decision analysis

| Option | When | Risk |
|--------|------|------|
| k8s Service DNS | most in-cluster | DNS dependency |
| Cloud LB | VM / hybrid | vendor |
| Mesh | mTLS + advanced policies | operational cost |
| kit/sd + Consul | legacy / special | second control plane |
| Localhost only | lab | does not teach SD |

## Trade-offs

- Client-side LB flexible, more complex in app code.
- Server-side (Service/proxy) simpler for the app, less algorithm control.
- Retry increases resilience and storm risk.
- Keep-alive faster and can reduce distribution after scale-up.
- Less in-app SD = less control outside the platform — usually a good trade.

## Idiomatic Go

- Client: DNS name, `context` timeout, shared `http.Client` / Transport.
- Server: timeouts on `http.Server`, graceful shutdown (07.16).
- Health handler thin — without a heavy dependency if you can.
- kit/sd only when you truly need it; otherwise stdlib + platform.
- Endpoint (`endpoint.Endpoint`) on the server does not depend on the SD package.

## Practical scenario

Team removes Consul for internal services because k8s DNS + readiness cover 95% of cases. They delete thousands of lines of registrar/subscriber code. MTTR drops because there are fewer components in the postmortem diagram. kit/sd remains in repo history as git archaeology — not as an obligation for new services.

## Deepening: service discovery

### 1. insight

**Registrar vs Subscriber** (kit/sd terminology). Registrar publishes “I am here”; subscriber tracks the list. In k8s often none of that in the app.

Practical check: does your `main` call anything like Register?

### 2. insight

**Endpointer factory** in legacy examples — makes a kit Endpoint toward each instance. Read as pattern history, not mandatory homework.

Practical check: do you need a client-side instance list?

### 3. insight

**Round-robin idea** in balancers — simple; not always optimal. Platform may do something else (least conn, EWMA…).

Practical check: who chooses the algorithm for you — app or mesh?

### 4. insight

**Pin-check package exports.** Do not cite a package your major no longer ships the same way.

Practical check: `go list` / module cache look at sd?

### 5. insight

**Cloud LB health = your /healthz.** If the probe hits the wrong path, a “healthy” service loses traffic.

Practical check: probe path == handler path?

### 6. insight

**Stale DNS TTL** — common “deploy then 5 minutes of errors”.

Practical check: where does the client cache DNS?

### 7. insight

**Zone-aware routing** — platform feature (cost vs latency). App rarely needs to do it manually.

Practical check: does the org force same-zone?

### 8. insight

**Do not expose instances to the public internet.** SD inside; edge separate.

Practical check: NetworkPolicy / private subnet?

### 9. insight

**mTLS with mesh** — authn/authz beside LB. Do not mix with “DNS works”.

Practical check: do you need mesh for mTLS or only for LB?

### 10. insight

**Dependency map** in README — who calls whom, which DNS, which timeout.

Practical check: does the map exist?

### 11. insight

**Chaos: kill a pod.** Better teacher than a slide.

Practical check: done at least once?

### 12. insight

**Kit does not replace kube-proxy magic.** Endpoint in the process ≠ Kubernetes Endpoint object.

Practical check: do you distinguish those two meanings of the word endpoint?

### 13. insight

**Without k8s:** Cloud Map, Nomad, freelance DNS — same idea: name → instance set outside the app when you can.

Practical check: which platform is your reality?

### 14. insight

**07.15 tracing** shows the hops that SD/LB hide (which pod, which downstream). That is why tracing comes after the basic SD mental model.

Practical check: ready to see more spans in a trace after mesh?
