# 07.03 Setting up Your Environment

> **Go Path - Zero to Gopher** / **03 Others → Go kit 0.12 Fundamentals** / Lesson 07.03

## Lesson goals

After this lesson you should be able to:

- initialize a Go module for a practice service (e.g. `stringsvc`)
- pin `github.com/go-kit/kit@v0.12.0` exactly and verify the version with `go list -m`
- organize folders: `cmd/`, `internal/service`, `internal/endpoint`, `internal/transport`
- understand the log package note: older tutorials vs `github.com/go-kit/log` (`NewLogfmtLogger`, `With`)
- prepare a minimal `main`, README “how to run”, and `go test ./...` as a CI entry point
- avoid classic traps: GOPATH mode, wrong module path, mixing forks, forgotten `replace`

## Prerequisite

- 07.02 — you know *why* you need layers (challenges without kit)
- Go **1.22+** installed (`go version`)
- Network to `proxy.golang.org` (or corporate `GOPROXY`)
- Editor with `gopls` (optional, but helps jump-to-def on `endpoint.Endpoint`)
- Windows: PowerShell consistently; do not randomly mix cmd/Git Bash path styles in the same README without a note

## Problem this lesson solves

Wrong import path, mixing old tutorials and “latest kit from GitHub main” break the build mid-course. Without a pin:

- one laptop pulls v0.12, another v0.13+ with different re-exports
- copy-paste from a blog uses `github.com/go-kit/kit/log` while newer texts use `github.com/go-kit/log`
- folder chaos (`handlers` + `api` + `utils`) blocks the dependency rule from 07.04

This lesson sets a *reproducible* environment so 07.04–07.xx can talk about components, not “it does not compile on my machine”.

## Mental model

```
go.mod (pin kit@v0.12.0)
    ↓
folders that mirror the layers
    cmd/stringsvc/main.go          ← wiring
    internal/service/              ← job
    internal/endpoint/             ← endpoint.Endpoint factory
    internal/transport/http/       ← decode/encode + NewServer
    ↓
go test ./...  +  README
```

The pin keeps the API stable. Folders keep dependency arrows. `internal/` prevents other modules from importing your guts. Log: decide *one* import path and document it.

## Mechanism

### Step 0 — tool check

```powershell
go version
go env GOPATH GOMODCACHE GOPROXY GO111MODULE
```

Expect:

- Go ≥ 1.22
- `GO111MODULE` typically `on` or empty (modules default)
- `GOPROXY` is not empty in a corporate lockdown without an alternative

**Predict-then-answer A**

Question: what if `GO111MODULE=off`?

- Predict: “it still works like 2017 GOPATH”.
- Answer: you are in trouble — the course assumes modules. Turn modules on and work from a directory with `go.mod`.

### Step 1 — create project and module

```powershell
mkdir stringsvc
cd stringsvc
go mod init example.com/stringsvc
```

`example.com/stringsvc` is a *practice* module path. At work you use a real one (e.g. `github.com/org/stringsvc`). Important: the path must be stable because it enters every `import` line.

Check:

```powershell
Get-Content go.mod
```

You should see:

```
module example.com/stringsvc

go 1.22
```

(go directive may be 1.22 or newer — align with the local toolchain.)

### Step 2 — pin kit@v0.12.0

```powershell
go get github.com/go-kit/kit@v0.12.0
```

Check:

```powershell
go list -m github.com/go-kit/kit
```

Expected output similar to:

```
github.com/go-kit/kit v0.12.0
```

**Predict-then-answer B**

Question: may you `go get github.com/go-kit/kit@latest`?

- Predict: “yes, always newest”.
- Answer: for this course — no. Pinning v0.12.0 keeps the API aligned with the lessons (`endpoint.Endpoint`, `httptransport.NewServer`, `endpoint.Chain`). A newer patch *may* be OK if the API is the same, but a major/minor jump needs a diff and a note.

### Step 3 — log package note (important)

History that confuses:

| Source | Import you see | What to do in the course |
|--------|----------------|--------------------------|
| Older kit tutorials | `github.com/go-kit/kit/log` | Works with kit v0.12; check whether it is a re-export |
| Newer texts / split | `github.com/go-kit/log` | Often an explicit dependency: `NewLogfmtLogger`, `log.With` |
| Random blog 2018 | mix | Do not copy blindly |

Recommendation for the module:

1. Decide one style in the README.
2. If you use `github.com/go-kit/log`, add it explicitly:

```powershell
go get github.com/go-kit/log@latest
```

(or pin a concrete version the team approves — record it in the README next to the kit pin.)

Minimal smoke:

```go
package main

import (
    "os"

    "github.com/go-kit/log"
)

func main() {
    var logger log.Logger
    logger = log.NewLogfmtLogger(os.Stderr)
    logger = log.With(logger, "svc", "stringsvc")
    _ = logger.Log("msg", "boot")
}
```

**Predict-then-answer C**

Question: does `NewLogfmtLogger` come from `kit/endpoint`?

- Predict: “yes, everything is in kit”.
- Answer: no. The logger API is in the log package (`go-kit/log` or historically `kit/log`). Endpoint is separate.

### Step 4 — folder layout (proposal we follow)

```text
stringsvc/
  go.mod
  go.sum
  README.md
  cmd/
    stringsvc/
      main.go
  internal/
    service/
      service.go
      service_test.go
    endpoint/
      endpoints.go
    transport/
      http/
        server.go
        decode.go
        encode.go
```

Why this way:

- `cmd/stringsvc` — one process, one `main`; wiring lives here
- `internal/service` — business `interface` + implementation; no HTTP
- `internal/endpoint` — `makeUppercaseEndpoint(svc)` → `endpoint.Endpoint`
- `internal/transport/http` — `httptransport.NewServer`, decode/encode
- `internal/` — other modules *cannot* import your guts

**Predict-then-answer D**

Question: may `internal/service` import `internal/transport/http`?

- Predict: “yes, so it knows status codes”.
- Answer: no. The arrow goes transport → endpoint → service. Reverse = circular risk and broken principle (07.04).

### Step 5 — file skeleton (compiles, not real work yet)

`internal/service/service.go`:

```go
package service

import "context"

type Service interface {
    Uppercase(ctx context.Context, s string) (string, error)
}

type stringService struct{}

func New() Service { return stringService{} }

func (stringService) Uppercase(ctx context.Context, s string) (string, error) {
    _ = ctx
    return s, nil // 07.05 replaces with real logic
}
```

`internal/endpoint/endpoints.go` (type preview — detail 07.04+):

```go
package endpoint

import (
    "context"

    "github.com/go-kit/kit/endpoint"
    "example.com/stringsvc/internal/service"
)

func MakeUppercaseEndpoint(svc service.Service) endpoint.Endpoint {
    return func(ctx context.Context, request interface{}) (interface{}, error) {
        // cast + call svc in later lessons
        _ = ctx
        _ = request
        _ = svc
        return nil, nil
    }
}
```

`cmd/stringsvc/main.go`:

```go
package main

import (
    "fmt"

    "example.com/stringsvc/internal/service"
)

func main() {
    svc := service.New()
    fmt.Println("stringsvc boot", svc != nil)
}
```

### Step 6 — build and test loop

```powershell
go test ./...
go build -o bin/stringsvc.exe ./cmd/stringsvc
```

On Linux/macOS: `-o bin/stringsvc`. On Windows: `.exe` or without extension as you prefer — document in README.

If `go test ./...` fails because of empty packages, add at least:

```go
// internal/service/service_test.go
package service_test

import (
    "context"
    "testing"

    "example.com/stringsvc/internal/service"
)

func TestNew(t *testing.T) {
    svc := service.New()
    if svc == nil {
        t.Fatal("nil service")
    }
    _, _ = svc.Uppercase(context.Background(), "x")
}
```

**Predict-then-answer E**

Question: why `go test ./...` immediately in CI, while there is still no HTTP server?

- Predict: “pointless until there are handlers”.
- Answer: it catches import/compile breaks early; teaches the team that green is an *entry*, not an afterthought. Service tests grow in 07.05.

### Step 7 — README minimal contract

```markdown
# stringsvc

## Versions

- Go: 1.22+
- github.com/go-kit/kit: v0.12.0
- log: github.com/go-kit/log (NewLogfmtLogger / With)

## Run

go test ./...
go run ./cmd/stringsvc

## Layout

cmd/ → wiring
internal/service → business
internal/endpoint → endpoint.Endpoint
internal/transport/http → HTTP encode/decode
```

Without a README, onboarding guesses the pin and log import — you return to the problem from the intro.

### Step 8 — editor / gopls check

In the editor open `MakeUppercaseEndpoint` and jump-to-definition on `endpoint.Endpoint`. You should see the type from kit sources:

```go
type Endpoint func(ctx context.Context, request interface{}) (response interface{}, err error)
```

If gopls does not see the module:

```powershell
go mod download
# restart gopls / window
```

### Step 9 — common Windows traps

1. Mixing `\` and `/` in documentation — Go imports always `/`.
2. Running from the wrong cwd (no `go.mod` in parent) → module mode confusion.
3. Antivirus lock on `go.exe` / module cache — rare, but first check `GOMODCACHE`.
4. Copy-paste bash heredoc into PowerShell — does not work the same; use files.

**Predict-then-answer F**

Question: does a `replace` directive in `go.mod` belong in the course skeleton?

- Predict: “yes, for a local fork”.
- Answer: not by default. Use `replace` only for local fork debug and it *must* be documented — a forgotten `replace` breaks CI on another machine.

### Step 10 — optional: Makefile / scripts

```makefile
.PHONY: test build
test:
	go test ./...
build:
	go build -o bin/stringsvc ./cmd/stringsvc
```

On Windows without `make`: `scripts/test.ps1` with the same commands. The goal is not tool religion — the goal is *one* command for green state.

### Step 11 — CI skeleton (conceptual)

```yaml
# idea, not a mandatory vendor file
steps:
  - run: go version
  - run: go test ./...
  - run: go list -m github.com/go-kit/kit
```

Asserting that the version is `v0.12.0` (or an allowed patch) prevents a silent upgrade in a lockfile PR.

### Step 12 — walkthrough: what *not* to do in this lesson

- Do not write a production HTTP server yet (that comes after components / business logic).
- Do not add ten middlewares “for a complete feeling”.
- Do not vendor unless the company requires it (`go mod vendor`) — if you vendor, document it.
- Do not mix the `stringsvc` example path with a production module path in the same `go.mod` without reason.

### Step 13 — predict the whole “first day” loop

Imagine a new teammate:

1. Clones a template repo with pin and folders.
2. `go test ./...` — green in 15 min.
3. Reads README layout.
4. Opens 07.04 with the question “where does the Endpoint type live”.

Without this lesson, step 2 takes half a day (proxy, GOPATH, wrong import).

**Predict-then-answer G**

Question: where does the `httptransport.NewServer` import path live?

- Predict: “`github.com/go-kit/kit/transport/http`”.
- Answer: yes — that is the standard kit HTTP transport package. You will use it when you wire the server; for now it is enough to know where it will sit in the `internal/transport/http` folder.

### Step 14 — environment completion checklist

Before 07.04 this must be true:

| Check | Command / artifact | OK? |
|-------|--------------------|-----|
| Module exists | `go.mod` | |
| Kit pin | `go list -m github.com/go-kit/kit` → v0.12.0 | |
| Layout | cmd + internal/{service,endpoint,transport} | |
| Test | `go test ./...` | |
| README | versions + run + layout | |
| Log decision | one import path documented | |
| No blind replace | `go.mod` review | |

If anything is missing, do not go further — debug here is cheaper than mid-07.07.

Extra smoke (optional but useful):

```powershell
go vet ./...
go build -o bin/stringsvc.exe ./cmd/stringsvc
Remove-Item bin/stringsvc.exe
```

`go vet` catches suspicious constructs; build confirms the `cmd` package actually links `internal` packages. Delete the local binary so it does not end up in git status by mistake.

### Step 16 — what to do when `go get` fails

1. Read the exact error (sum / 404 / timeout).
2. `go env GOPROXY GOPRIVATE GONOSUMDB`.
3. Check whether the company requires VPN.
4. Try `go clean -modcache` *only* if you understand the next download will be slower.
5. Do not “fix” by switching to a random kit fork.

**Predict-then-answer H**

Question: should `go clean -modcache` be the first step?

- Predict: “yes, it always helps”.
- Answer: no. First diagnose proxy/path. Clearing the cache is expensive and rarely needed for a pin to a known version.

### Step 17 — link back to 07.02 and forward to 07.04

- 07.02: challenges → layer map.
- **07.03: folders and pin make the map physical.**
- 07.04: component names and dependency rule.
- 07.05: real business logic in `internal/service`.

Environment is not “admin work” — it is a prerequisite so principles do not stay slides. Environment is a team contract: a PR that stuffs everything back into `main.go` breaks layout the same as a linter.

## Rules and syntax

1. **Pin the kit version** to `v0.12.0` for the course; record deviations.
2. **`internal/` for private** — do not expose service/endpoint as another module’s public API.
3. **One `cmd` per process** — `cmd/stringsvc`, not five `main`s in the root.
4. **`go test ./...` in CI** from day 1.
5. **Do not mix random forks** of kit / log without an ADR.
6. **README how to run** + versions + layout.
7. **Same Go version** as the course / team toolchain file.
8. **One log import style** — document `go-kit/log` vs `kit/log`.
9. **`go.mod` + `go.sum` commit** (when commit time comes) — reproducibility.
10. **No `replace` by default.**
11. **Stable module path** — `example.com/...` only for practice.
12. **Do not keep all code in one file forever** — the folder skeleton exists so you use it.

## Decision analysis

| Decision | Course choice | Alternative | Alternative risk |
|----------|---------------|-------------|------------------|
| Kit version | v0.12.0 pin | @latest | Lesson break / API drift |
| Module path | example.com/stringsvc | github.com/you/... | OK if consistent |
| Log package | documented go-kit/log | mixing kit/log | Import chaos |
| Layout | cmd + internal/* | everything in root | No dependency rule |
| Vendoring | no (default) | go mod vendor | Longer PR, firm policy OK |
| CGO | off if not needed | CGO_ENABLED=1 | Larger binary, slower CI |
| Make vs ps1 | what the team knows | nothing | Slower onboarding |
| go 1.22+ | yes | older Go | Modules/tooling drift |

## Trade-offs

- **Pinning older kit** vs **new log split and patches** — document what you use; do not upgrade mid-course without a note.
- **`internal/` strictness** vs **sharing code between binaries** — for multiple binaries in the *same* module `internal` still works; for *another* module you need a public package or a separate module.
- **Early CI** vs **“nothing to test yet”** — early CI catches env breaks; raise at least a smoke test.
- **Devcontainer** vs **local Go** — container equalizes versions, costs setup.
- **Vendoring** vs **proxy** — vendor helps offline/airgap; slows review diff.
- **One stringsvc through the whole module** vs **new repo per lesson** — one project = import consistency.

## Common mistakes

1. **No `go.mod`** — working in GOPATH style.
2. **`GO111MODULE=off`** forgotten.
3. **Copy-paste old import** `kit/log` vs `go-kit/log` confusion without README.
4. **Everything in one file forever** — skeleton exists in vain.
5. **No CI / no `go test ./...`**.
6. **Windows path chaos** in scripts.
7. **Forgotten `replace`** in `go.mod` — CI red.
8. **`go get` without version** mid-course.
9. **Wrong module path** after renaming a folder.
10. **Committing binary** `stringsvc.exe` to git.
11. **Mixing examples path** with production path.
12. **Stale gopls cache** then “kit has no Endpoint” — false alarm.

## Idiomatic Go

- `internal` + `cmd` layout is idiomatic for applications.
- `gofmt` / `go fmt ./...` before push.
- `go test ./...` as the default loop.
- Explicit module path in every import.
- Small packages per layer, not a “package util” jungle.
- Zero value and a simple `New()` constructor at the start.
- Do not export what `internal` already hides — do not make a fake public API.

## Practical scenario

A team builds a template repo:

- `go.mod` with kit@v0.12.0
- folder skeleton
- README + `go test` in CI

Onboarding a new member: **15 minutes** to green `go test` and an open `main`. Another team without a template: half a day on proxy, versions, and “which log import is correct”. The difference is not talent — the difference is 07.03 done once for everyone.

## Going deeper: go-kit v0.12 environment

### 1. insight

**Check `go env GOPROXY`.** At work Athens/Artifactory often sits there. If the proxy is silent, `go get` “hangs” and looks like a kit problem. Network first, then versions.

Practical check: `go env GOPROXY GOPRIVATE` — write it in onboarding.

### 2. insight

**Vendoring is firm policy, not kit dogma.** `go mod vendor` helps airgap; increases diff. If you vendor, CI must `go test -mod=vendor`.

Practical check: does the repo already have `vendor/`? Align commands.

### 3. insight

**Devcontainer with a Go 1.22 image** equalizes Windows/Mac/Linux. Costs image pull; saves “works on my machine”.

Practical check: if the team loses >1h/month on toolchain, consider a container.

### 4. insight

**`make test` / `scripts/test.ps1` immediately.** One command = fewer Slack questions “how do you run tests”.

Practical check: can a new member without README run only via script?

### 5. insight

**Do not mix examples module path with production path.** Copy-paste from `github.com/go-kit/kit/examples` breaks imports until you replace the prefix.

Practical check: `rg "github.com/go-kit/kit/examples"` in your code — should be empty.

### 6. insight

**golangci-lint later, but not never.** First green `go test`; lint in a second PR so you do not mix setup noise with style noise.

Practical check: separate “env green” from “lint green” in the checklist.

### 7. insight

**Disable CGO if not needed** — smaller binary, faster CI. `CGO_ENABLED=0 go build`.

Practical check: do you need a DNS/resolver or lib that requires CGO?

### 8. insight

**Document minimum OS.** Windows developer + Linux CI = path and shell differences. README must have both examples or one canonical (container).

Practical check: does README copy-paste work on your OS without edits?

### 9. insight

**For gRPC transport you also need proto tooling** (05.03). Not required in 07.03, but record the future dependency (`protoc`, plugins) so it does not surprise a sprint.

Practical check: if gRPC is on the roadmap, add “tooling TBD” to the README.

### 10. insight

**Cache modules in CI.** Without cache, every job pulls kit again — slow and flaky on the network.

Practical check: does CI cache `GOMODCACHE` or a `go.sum`-based cache?

### 11. insight

**Verify gopls sees kit sources.** If not, Jump-to-Endpoint does not work and you learn the wrong signature from memory.

Practical check: open the definition of `endpoint.Chain` once today.

### 12. insight

**One stringsvc example through the whole module.** Changing the project name per lesson multiplies cognitive load. Consistency > creativity in naming.

Practical check: do all imports share the same module prefix?

### 13. insight

**Record breaking changes if you upgrade kit.** Even a patch: read the CHANGELOG. The course pin exists so you *do not* do that mid-learning.

Practical check: before upgrade — `go list -m -u github.com/go-kit/kit` and a diff.

### 14. insight

**Windows: PowerShell consistently; do not commit a binary file; 07.04 introduces principles formally.** Without environment there are no exercises — that is why this lesson exists *before* components. Editor build tags only when needed. The skeleton succeeds if `go test ./...` and the pin hold.

Practical check: checklist from Step 14 — all 7 items green before you open 07.04.
