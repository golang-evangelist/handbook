# 07.13 Visibility and Diagnostics Review

> **Go Path - Zero to Gopher** / **03 Others → Go kit 0.12 Fundamentals** / Lesson 07.13

## Lesson goals

After this lesson you should be able to:

- define **visibility** as a triad: **signals + ownership + runbook**
- walk through a **checklist** (transport log, app log, metrics, rid, dashboard, alerts, no PII)
- **correlate** request id (`rid`) through access and app logs
- set a **gate** before Service Discovery and distributed tracing (07.14 / 07.15)
- write an **SLO** sketch and at least one **alert** with a link to a runbook
- refuse to continue until the checklist is green (culture, not ceremony)

## Prerequisite

- 07.10 — transport logging (`ServerBefore`, `ServerFinalizer`, request id)
- 07.11 — application logging (`github.com/go-kit/log`, LoggingMiddleware)
- 07.12 — instrumenting (kit/metrics, RED, `/metrics`, low cardinality)
- 07.09 — core green (service without HTTP leakage)

## Problem this lesson solves

Metrics without an alert and logs without `rid` do not help at 3 a.m. Dashboard wallpaper is not observability. Visibility review is a **stop-gate**: before you add SD complexity or OTel span noise, you must know *what* you look at, *who* owns it, and *what you do* when red lights up.

## Mental model

```
Visibility = Signals + Ownership + Runbook

Signals:   access log | app log | RED metrics | (later trace)
Ownership: which team, which rota, which channel
Runbook:   step 1…n when an alert fires
```

- **Signal** without ownership = orphan dashboard.
- **Alert** without a runbook = wakeup without context.
- **Log** without `rid` = MTTR explosion (grep by luck).

Gate before 07.14/07.15: if the checklist is not green, SD and tracing only complicate diagnosis.

## Mechanism

### Step 0 — why a review, not a new library

This lesson does **not introduce** a new go-kit package. It summarizes 07.10–07.12 into an operational DoD. If something is missing, **go back** — do not “patch” the gap with Consul or a span.

**Predict-then-answer A**

Question: does OTel (07.15) replace the visibility review?

- Predict: “trace shows everything, checklist is redundant”.
- Answer: no. A trace without rid policy, without an alert, and without ownership still leaves on-call without a map. Review first.

### Step 1 — checklist (mandatory table)

Go item by item. Green = evidence (URL, screenshot, error in log, PromQL, PR link).

| # | Item | Evidence | Status |
|---|------|----------|--------|
| 1 | Transport log (path/code/`rid`) | access line for happy + 4xx/5xx | ☐ |
| 2 | App log (method/err/took) | LoggingMiddleware line | ☐ |
| 3 | Metrics RED (count/latency/error) | `/metrics` + Grafana panel | ☐ |
| 4 | Request id through layers | same `rid` in access + app | ☐ |
| 5 | `/metrics` live and scraped | curl + Prometheus target UP | ☐ |
| 6 | Dashboard (at least RED) | board link in README/ops | ☐ |
| 7 | Alert on error ratio (or equivalent) | alert rule + channel | ☐ |
| 8 | No PII in log/metric labels | audit list | ☐ |
| 9 | Low cardinality | no user_id/rid label | ☐ |
| 10 | Runbook link in the alert | markdown runbook URL | ☐ |
| 11 | Ownership (team/rota) | CODEOWNERS / on-call | ☐ |
| 12 | MW tests stay green | `go test ./...` | ☐ |

Do not go to 07.14 until at least 1–10 are green. 11–12 are hard for production.

### Step 2 — signals: three pillars (reminder)

| Pillar | Lesson | Question |
|--------|--------|----------|
| Access | 07.10 | Which path/code/`rid`? |
| App event | 07.11 | Which method/err/took? |
| Aggregate | 07.12 | What rate/error/p99? |

Trace (07.15) is the **fourth** pillar — it does not enter this gate as mandatory. If you already have it, it must not replace rid or RED.

### Step 3 — ownership

Ask explicitly:

1. Who receives the alert at 03:00?
2. Who may change the dashboard / PromQL?
3. Where is escalation (L1 → L2)?

Without answers, the signal is decoration. Write one sentence in README ops or wiki: *“StringService on-call: …”*.

**Predict-then-answer B**

Question: does “everyone in the Slack channel” = ownership?

- Predict: “yes, transparent”.
- Answer: no. Shared channel without a rota = bystander effect. You need a named rota or pager.

### Step 4 — runbook shape (minimal)

A runbook is not a novel. Five to ten steps:

```
1. Open Grafana RED board (link)
2. Check error ratio 5m / 1h
3. If style A: check domain success=false, not only HTTP 5xx
4. Take one rid from the access log (peak window)
5. Grep app log by that rid
6. If ErrEmpty spike — check client input / synthetic
7. If latency — sat / downstream / CPU
8. Escalate if … (condition)
9. Link to postmortem template
```

The alert **must** contain a URL to this. Otherwise the alert is only a siren.

### Step 5 — `rid` correlation

Flow you defend:

1. `ServerBefore` puts `rid` in context (+ header out if needed).
2. Access Finalizer logs `rid` + code + path.
3. LoggingMiddleware logs `rid` (from context) + method/err/took.
4. Metric does **not** have `rid` as a label (07.12).
5. On-call: metric → time → access `rid` → app log.

**Predict-then-answer C**

Question: do two different UUIDs in access and app log “pass” the checklist?

- Predict: “both exist, OK”.
- Answer: no. Correlation is the point. Same key, same value.

### Step 6 — PII and signal security

Forbidden in log body / attributes / labels (reminder):

- email, phone, full name, address
- tokens, password, Authorization header raw
- pan numbers, national ID, similar
- unbounded body dump “just in case”

Allowed with policy:

- truncated input (e.g. first N characters) if product agrees
- enum errors (`ErrEmpty`) instead of raw user string in alerts

`/metrics` and debug endpoints: network policy / separate port (from 07.12).

### Step 7 — dashboard minimalism

One board “StringService RED”:

- Rate (QPS) by `method`
- Error ratio
- Latency p50/p99
- (optional) HTTP code rate from the edge

Not five boards before the first alert. Orphan dashboard = checklist antipattern.

### Step 8 — alert: error ratio example

Idea (replace metric names with yours):

- Window: 5m
- Condition: `errors / all > 2%` (or absolute threshold for low QPS)
- Severity: warning / critical by agreement
- Annotation: runbook URL + “check style A domain errors”

**Predict-then-answer D**

Question: alert on every `ErrEmpty`?

- Predict: “yes, that is an error”.
- Answer: often no. Expected client fail can be noise. Alert on *unexpected* growth or 5xx/unknown; document expected.

### Step 9 — walkthrough: happy path through signals

1. Client `POST /uppercase` with body `{"s":"hi"}`.
2. Before: `rid=abc`.
3. decode OK → endpoint → InstrMW → LogMW → core.
4. Core OK.
5. InstrMW: Counter + Histogram success=true.
6. LogMW: method=uppercase err=null took=…
7. Finalizer: code=200 rid=abc.
8. Grafana: rate↑, error calm, p99 OK.
9. On-call does not wake — no alert. That is success.

### Step 10 — walkthrough: style A domain error

1. `{"s":""}` → `ErrEmpty`.
2. HTTP maybe 200 (style A) or 4xx (style B) — documented.
3. Domain metric: success=false.
4. App log: err present, same `rid`.
5. Access: code per policy.
6. If the board looks only at HTTP 5xx — **false calm**. Review catches this.

### Step 11 — walkthrough: decode fail

1. Bad JSON.
2. No domain RED bump (07.12).
3. Access + ErrorLogger see the problem.
4. Checklist: does transport error have a signal? Yes — access. Do you expect Uppercase counter? No.

### Step 12 — walkthrough: cardinality incident (regression)

1. Someone adds label `user_id` “temporarily”.
2. Prometheus memory grows; scrape lags; board disappears.
3. Review item 9: failed. Rollback label; `rid` stays in the log.

### Step 13 — walkthrough: alert without runbook

1. Error ratio > 2%.
2. Pager: “StringService errors”.
3. On-call opens an empty description.
4. 20 minutes wandering through folders.
5. Process fix: annotation + runbook before merging the alert.

### Step 14 — gate before SD (07.14)

Service discovery adds hops, DNS TTL, retry. If you cannot diagnose **one** pod with rid+RED, SD will only multiply uncertainty.

Gate question: *“Can I find the root cause of one failed request on staging in 10 minutes?”* If not — not 07.14.

### Step 15 — gate before tracing (07.15)

Tracing is a chain map. Without local signals, the map is empty or expensive noise. The rid↔trace id link comes in 07.15 — here only reserve the policy: rid stays in the log.

### Step 16 — SLO sketch (not a formal SRE course)

Minimum:

| SLI | Target (example) | Window |
|-----|------------------|--------|
| Availability (success ratio) | 99.5% | 30d |
| Latency p99 Uppercase | < 50ms | 30d |

Error budget story: if you burn the budget, freeze features, fix reliability. Enough for a handbook note.

### Step 17 — noisy debug vs prod signal

- Debug log on every loop step = disk burn.
- Sampling debug / level by env.
- Prod default: info access + app method line; debug off.

Review: do staging and prod share the same flood? If yes — reduce.

### Step 18 — synthetic check

Simple cron/k8s probe: `POST /uppercase` with a known body. Does not replace RED, but catches “all metrics dead because scrape fails” or “DNS broken”.

Healthz ≠ synthetic business call. Both have a place; do not mix them.

### Step 19 — anti-pattern catalog

| Anti | Why it hurts |
|------|--------------|
| Alert on everything | pager fatigue |
| No runbook | MTTR↑ |
| PII in log | compliance + incident² |
| High cardinality | you lose metrics when you need them most |
| Logs only | no Rate/SLO |
| Metric only | no zoom on one request |
| Orphan dashboard | nobody looks |
| Rid only in one layer | no correlation |
| Continue to SD while red | long debt |

### Step 20 — linking with 04.x operational cost

Every signal has a cost (storage, scrape, attention). Visibility review chooses **enough** signal, not the maximum. Same spirit as 04.01: you pay for what you diagnose.

### Step 21 — tests as part of visibility

- Unit: service + MW (log/metrics stub).
- Do not delete tests “because we have Grafana”.
- Contract: style A/B error map documented by a test where it makes sense.

Checklist item 12 is not decoration.

### Step 22 — version / build in signals

- Log on start: build id / git sha (once).
- Metric label `version` — only if **low** cardinality (few active versions).
- Do not put full sha as a high-churn label without agreement.

### Step 23 — postmortem uses these signals

Template sections:

1. Detection (which alert / who reported)
2. Timeline (rid examples)
3. Impact (RED chart)
4. Root cause
5. Action items (including checklist gaps)

If the postmortem cannot cite rid — the checklist was red and nobody stopped.

### Step 24 — quiet hours / severity

Not every alert pages at 03:00. Warning → ticket; critical → page. Document. Review asks: is severity ridiculous?

### Step 25 — mini lab (mandatory before “done”)

1. Fill the checklist table with evidence.
2. Deliberately send `ErrEmpty`; find the same `rid` in access and app.
3. Sketch alert + 7-step runbook.
4. PII audit: 10 sample log lines — scrub if leaking.
5. Peer: a colleague tries diagnosis with only your README — measure time.

### Step 26 — predict pack (quick check)

**E.** Does a dashboard without an alert pass the gate?  
Not for production DoD — a board without action is wallpaper.

**F.** Does `rid` in a Prometheus label help correlation?  
No — cardinality bomb; correlation goes the log path.

**G.** May you go to 07.14 with green 1–7 but without a runbook?  
Not recommended. Item 10 exists because an alert without guidance burns the night.

### Step 27 — request walkthrough poster (handbook)

```
client
  → Before(rid)
  → decode
  → endpoint
  → InstrMW (Add/Observe)
  → LogMW (method/err/took + rid)
  → service
  → encode
  → Finalizer(code, rid)
in parallel: Prometheus scrape /metrics
on-call: alert → board → rid → app log → fix / escalate
```

If you cannot draw this, the review is not done.

### Step 28 — what to tell a PM rushing to a “Consul demo”

> We do not have a green visibility checklist. SD before that increases MTTR. We close signals/ownership/runbook this sprint; SD follows.

That is professional pushback, not blocking out of spite.

### Step 29 — mechanism wrap-up

You understand the signals/ownership/runbook triad, checklist, rid correlation, PII/cardinality discipline, alert+runbook, gate before 07.14/07.15. Later lessons assume you stopped here if needed.

## Rules and syntax

1. Visibility = signals + ownership + runbook.
2. Do not go to 07.14/07.15 until the checklist is green.
3. Same `rid` in transport and app log.
4. `rid` is not a metric label.
5. Alert must have a runbook link.
6. No PII; low cardinality.
7. RED + access + app — all three.
8. Style A requires domain error visibility.
9. Wire fail ≠ domain counter (expected).
10. Ownership named, not “everyone”.
11. Tests stay green.
12. Document an SLO sketch (even roughly).
13. Orphan dashboard = fail.
14. Choose signal cost consciously (04.x spirit).

## Examples

### Example 1 — alert on error ratio

Threshold: error ratio 5m > 2%. Annotation: link to runbook section “StringService errors”.

### What happens here

Wakeup with context: where to look, which rid step, when to escalate.

### Example 2 — rid search

Access: `rid=7f3a… code=200`. App: `rid=7f3a… method=uppercase err=null took=1.2ms`.

### What happens here

MTTR drops because you do not grep by body content.

### Example 3 — cardinality incident

Label `email=…` on counter. Series explode.

### What happens here

Review item 9 red; rollback before SD work.

### Example 4 — review gate stop

Team wants kit/sd + Consul “because the course mentions it”. Checklist 4 and 7 red.

### What happens here

Culture: stop, close gaps, only then 07.14.

### Example 5 — orphan Grafana

Board “tmp_marko” without alert, without owners.

### What happens here

Either bind it to on-call + alert, or delete it.

### Example 6 — PII in app log

`logger.Log("input", fullEmail)`.

### What happens here

Audit fail. Truncate / hash / do not log.

### Example 7 — metrics only

On-call sees error spike, no rid in log (Finalizer turned off “for performance”).

### What happens here

Aggregate without zoom. Bring transport log back.

## Decision analysis

| Option | When | Risk |
|--------|------|------|
| Strict gate (checklist) | prod / team | slower “demo” |
| Lab gate (relaxed) | personal laptop | does not transfer the habit |
| Alert on ratio | stable QPS | OK |
| Alert on absolute | low QPS | fewer false |
| One RED board | always first | low |
| Many boards | later | orphan risk |
| Synthetic + RED | prod | operational cost |

## Trade-offs

- More signals = better diagnosis and higher storage/attention cost.
- Stricter gate = slower feature train, faster MTTR.
- Expected `ErrEmpty` in alert = noise vs blindness — choose thresholds consciously.
- Log retention: longer = more expensive; shorter = harder forensics.

## Common mistakes

1. Alert on everything (pager fatigue).
2. No runbook in the alert.
3. PII in logs or attributes.
4. High label cardinality.
5. Logs only without metrics.
6. Metrics only without log / without rid.
7. Orphan dashboard.
8. Different rid keys per layer.
9. Continuing to SD/tracing while checklist red.
10. Ownership = “Slack #general”.
11. Style A invisible on HTTP-only board.
12. `/metrics` public without protection.
13. Deleting tests because “we have Grafana”.
14. SLO never written, then “everything is urgent”.

## Idiomatic Go

- DoD includes observability the same as `go test`.
- Middleware composition stays clean; review does not mix layers.
- `github.com/go-kit/log` keys consistent (`request_id` / `rid` — **one** agreement).
- Context carries rid; not global request→id maps.
- main wiring readable: logger, metrics, MW order documented in README.

## Practical scenario

Team goes to prod with a nice RED board. First incident: error ratio alert without a runbook. On-call three hours. Retrospective introduces the 07.13 checklist as a merge gate for platform PRs. Next incident: 25 minutes to rid + root cause (bad client retry). Visibility review did not slow delivery — it shortened night hours.

## Deepening: visibility review

### 1. insight

**Operational cost (04.01).** Every panel and alert you pay for with attention. Choose signals that change action.

Practical check: which signal would you delete tomorrow without losing DoD?

### 2. insight

**On-call rota before SD.** Discovery complications without a rota = collective blindness.

Practical check: person/rota name on the wiki?

### 3. insight

**Trace is not yet mandatory.** 07.15 comes later; rid+RED are enough for one service.

Practical check: is someone blocking merge because “no Jaeger”? Pushback.

### 4. insight

**Log retention.** 3 days vs 30 — write the policy; incident forensics depends on it.

Practical check: how many days does Loki/ELK keep stringsvc?

### 5. insight

**Cost budget for metrics.** Cardinality = money and stability. Review item 9 is financial.

Practical check: number of active time series for the service?

### 6. insight

**Synthetic /uppercase.** Catches “silent death” of scrape and DNS that RED alone does not interpret.

Practical check: is there a probe beyond /healthz?

### 7. insight

**Error budget (sketch).** Without a number, everything is Sev-1 politically.

Practical check: one SLI sentence in README?

### 8. insight

**Postmortem eats your signals.** If they are missing, you write fiction.

Practical check: does the last postmortem cite rid?

### 9. insight

**Do not hide unknown errors.** Mapped `ErrEmpty` OK; `err` without type in the “success” bucket — a lie.

Practical check: where do unexpected errors land in the metric label?

### 10. insight

**Version label carefully.** Low cardinality only.

Practical check: how many versions simultaneously in prod?

### 11. insight

**Build id in log on start.** One line at boot — gold for “which bin”.

Practical check: does `logger.Log("msg","start","build",…)` exist?

### 12. insight

**Healthz separate from /metrics.** Different audiences and threats.

Practical check: do probe and scrape share the same public listener without policy?

### 13. insight

**Race detector > fake ASAN ritual for this course.** `go test -race` where concurrency hurts.

Practical check: does CI run race on critical packages?

### 14. insight

**Platform standards.** If the org imposes a label schema / alert routing — align; do not invent a parallel universe.

Practical check: is there an org observability guide?

### Appendix: rid policy (one page)

```
Field name: request_id (or rid) — ONE across the whole service
Source: ServerBefore (generate or accept inbound)
Propagation: context.Value / typed context key

App LogMW: always log
Metrics: NEVER as a label
Trace (07.15): log trace_id beside rid — do not replace rid
```
