# 07.02 What Are the Challenges with Writing Services

> **Go Path - Zero to Gopher** / **03 Others → Go kit 0.12 Fundamentals** / Lesson 07.02

## Lesson goals

After this lesson you should be able to:

- name concrete challenges of writing services *without* go-kit: wiring, transport duplication, observability, resilience, errors, testing
- map each challenge to a future kit layer (service, endpoint, transport, middleware)
- distinguish business concerns (domain, use-case) from platform concerns (HTTP, log, metrics, timeout)
- explain why “just a `net/http` handler” quickly becomes expensive to maintain when a second transport arrives
- prepare motivation for the rest of the module: without a clear problem, kit looks like ceremony

## Prerequisite

- 07.01 Course Overview — you know what go-kit is and what the module *is not* (not a platform, not a service mesh)
- basic Go: `interface`, `error`, `context.Context`, `struct`, package layout
- experience with at least one HTTP service in Go (`net/http` or similar)
- useful: memory of microservices costs from 04.xx and DTO versions from 04.05

## Problem this lesson solves

A service is not just a series of `if` branches in a handler. In production the same use-case must:

- work over HTTP *and* (often later) gRPC or a message queue
- log latency, errors, and correlation identifiers consistently
- respect timeout and cancel via `context`
- return errors the client can distinguish from “server crashed”
- be tested without starting a full HTTP server for every business branch

Without a framework, teams usually solve this by *copying*: the same validate in two handlers, log only in HTTP, metrics with different names, business rules in JSON decode. The lesson names those challenges *before* you introduce kit, so later layers make sense.

## Mental model

Imagine four boxes and one dependency arrow:

```
[Transport]  →  [Endpoint]  →  [Service / domain]
      ↑              ↑
  encode/decode   middleware (log, metrics, authz at use-case level)
```

- **Service** — business logic; does not know about HTTP status or JSON.
- **Endpoint** — use-case adapter: `endpoint.Endpoint = func(ctx context.Context, request interface{}) (response interface{}, err error)`.
- **Transport** — wire: `httptransport.NewServer`, decode/encode, gRPC wrapper.
- **Middleware** — decorator around the endpoint (`endpoint.Chain`) or around the service interface.

Every *challenge* in this lesson maps to one box. If you cannot map it, you are probably mixing two concerns in one file.

## Mechanism

This section is a walkthrough: start from a “naive” service, predict the pain, then see how kit answers *later*. You are not writing production code yet — you are learning the mapping.

### Step 0 — starting point without kit

Typical `main` + handler:

```go
func uppercaseHandler(w http.ResponseWriter, r *http.Request) {
    var body struct{ S string `json:"s"` }
    if err := json.NewDecoder(r.Body).Decode(&body); err != nil {
        http.Error(w, "bad json", http.StatusBadRequest)
        return
    }
    if body.S == "" {
        http.Error(w, "empty", http.StatusBadRequest)
        return
    }
    out := strings.ToUpper(body.S)
    _ = json.NewEncoder(w).Encode(map[string]string{"v": out})
}
```

Here three concerns are *mixed*: JSON decode, validation, the job (`ToUpper`), response encode. For one endpoint it looks clean. The problem appears when you add a second transport or another cross-cutting concern.

**Predict-then-answer A**

Question: where would you put latency measurement from request entry to encode, if tomorrow you add a gRPC handler with the same `ToUpper`?

- Predict: “in both handlers, copy-paste `time.Since`”.
- Answer: yes — without a shared place (endpoint / middleware) you duplicate measurement. Kit answers: `endpoint.Middleware` around one `endpoint.Endpoint`, then HTTP and gRPC share the same timing.

### Step 1 — challenge: duplicating handler logic

You add gRPC:

```go
func (s *Server) Uppercase(ctx context.Context, req *pb.UpperReq) (*pb.UpperResp, error) {
    if req.GetS() == "" {
        return nil, status.Error(codes.InvalidArgument, "empty")
    }
    return &pb.UpperResp{V: strings.ToUpper(req.GetS())}, nil
}
```

Now you have *two* places for “empty string” and *two* places for `ToUpper`. When product changes the rule (“whitespace-only is an error”), you change two files and forget one.

Mapping to kit:

| Without kit | With kit |
|-------------|----------|
| validate in HTTP + gRPC | validate once in service or endpoint factory |
| `ToUpper` in both | `Service.Uppercase` once |
| different error types | domain error → mapping in transport |

**Predict-then-answer B**

Question: must the `endpoint` layer *always* contain validation?

- Predict: “yes, always”.
- Answer: not always. Common split: transport checks wire shape (JSON parsed), service checks business rules. Endpoint casts `request interface{}` to a typed `struct` and calls service. What matters is *one* place for the business rule, not whether it is called “endpoint” or “service”.

### Step 2 — challenge: mixing JSON decode and business rules

In a naive handler, a `Decode` error and “SKU does not exist” often become the same `400` or the same `500`. Client and SRE cannot tell “bad wire” from “business rejected”.

Error walkthrough:

1. JSON is not valid → transport / decode error → typically 400.
2. Field exists but violates domain → service returns typed `error` → transport maps to 400/409/422 per team agreement.
3. DB timeout → service / infra error → 503 or 500 + alert, not “bad request”.

Without layers, all paths end in `http.Error(w, err.Error(), 500)`.

Mapping: **transport** = encode/decode + status map; **service** = semantics; **endpoint** = glue `interface{}` ↔ types.

### Step 3 — challenge: no single place for logging latency

HTTP middleware (`alice`, custom `http.Handler` wrapper) logs only HTTP. gRPC interceptor logs only gRPC. Message consumer has none. SRE sees three different field formats (`method`, `rpc`, `queue`).

Kit pattern: log the *use-case name* at endpoint level, e.g. `uppercase`, independent of transport. `github.com/go-kit/log` (`NewLogfmtLogger`, `log.With`) often goes with that — details in 07.03 and later lessons.

**Predict-then-answer C**

Question: is it enough to put the log only in `Service.Uppercase`?

- Predict: “yes, one method — one log”.
- Answer: partially. Service log often sees domain parameters, but not always wire status or whether decode failed *before* calling the service. Endpoint middleware sees success/failure of the whole use-case call including cast errors. Many teams log briefly at the endpoint (latency, error) and details in the service as needed.

### Step 4 — challenge: hard to test without a server

If all logic is in `http.HandlerFunc`, tests use `httptest.NewRecorder` + `http.NewRequest` for every branch. That is not wrong, but:

- slower than a pure unit test of a service method
- mixes JSON asserts with job asserts
- makes table-driven domain tests harder

Goal: test `Service` directly; test endpoint with a typed request `struct` without network; test transport encode/decode separately.

Mapping: **service** = fast unit tests; **endpoint** = adapter tests; **transport** = a small number of integration tests.

### Step 5 — challenge: late gRPC addition hurts

Sixth month: “we need gRPC for internal”. Without an endpoint layer:

1. You copy validate and the job.
2. You rework error mapping.
3. You duplicate metrics labels.
4. Two weeks of “refactor on the fly” instead of one day of wiring.

With an endpoint layer, a new transport = new decode/encode + `httptransport.NewServer` analog (gRPC server in kit) around the *same* `endpoint.Endpoint`.

**Predict-then-answer D**

Question: does kit *erase* the need for service discovery, deploy, TLS?

- Predict: “kit solves microservices”.
- Answer: no. Kit is a toolkit for code *structure*. Ops (04.01) remains: deploy, mesh, certs, SLO. Toolkit ≠ platform.

### Step 6 — challenge: wiring and “everything in main”

Naive growth:

```go
func main() {
    db := openDB()
    mux := http.NewServeMux()
    mux.HandleFunc("/upper", func(w http.ResponseWriter, r *http.Request) {
        // 80 lines: db, cache, auth, json, metrics...
    })
}
```

`main` becomes a god object. A new teammate does not know where to add retry. Circular imports start when `handlers` import `metrics` which import `handlers`.

Kit discipline: explicit wiring in `cmd/.../main.go` — construct service, wrap service middleware, make endpoints, wrap `endpoint.Chain`, then `httptransport.NewServer`. Dependencies flow *inward*.

### Step 7 — challenge: resilience (timeout, cancel, partial failure)

Without discipline around `context`:

- handler ignores `r.Context()`
- DB call has no deadline
- client cancels, server still does expensive work

Mapping: `context` flows through the endpoint signature (`ctx` first argument). Middleware can add a deadline. Service *must* pass `ctx` downward. This is not a “kit feature” — kit only makes `ctx` part of the endpoint contract.

**Predict-then-answer E**

Question: where do you put retry — service, endpoint middleware, or transport client?

- Predict: “always in service”.
- Answer: it depends. Retry toward an *external* HTTP API often lives in the client transport/middleware layer. An idempotent read can tolerate retry; a non-idempotent write often cannot. The domain rule “may it be repeated” belongs to service/product agreement, not blind copy-paste middleware.

### Step 8 — challenge: consistent errors and observability names

SRE wants a histogram by *use-case name* (`uppercase`, `count`), not by URL (`/v1/string/upper`) that changes with versions. Endpoint name is a more stable label.

Without that: Prometheus labels diverge between HTTP and gRPC, the dashboard lies.

Mapping: **endpoint** = stable name; **middleware** = metrics; **transport** = path/rpc name as an *extra* dimension when needed.

### Step 9 — synthesis: challenge → future layer table

| Challenge | Symptom without discipline | Future kit / layer |
|-----------|----------------------------|--------------------|
| Double validate / job | Bug in one transport | Service (+ endpoint factory) |
| JSON in business | 500 for bad JSON | Transport decode |
| Log only on HTTP | Silence on gRPC | Endpoint middleware |
| Slow tests | Everything through `httptest` | Test service directly |
| Second transport late | Weeks of copying | Shared endpoint |
| Everything in `main` | God object | Explicit wiring |
| No timeout | Zombie work | `context` through endpoint |
| Divergent metrics | Different names | Endpoint name + middleware |
| Domain error = 500 | Bad UX / alert noise | Mapping in transport |
| Authz in front of work | Copy auth into handlers | Endpoint or service middleware |

### Step 10 — what this map does *not* solve

- Wrong number of microservices (organizational challenge)
- Chatty monolith over the network (04.01)
- Idempotency and product semantics
- Versioning DTO contracts (04.05)
- Data race in shared service `struct` state

Kit reduces *structural* chaos. It does not replace engineering judgment.

### Step 11 — mini review simulation

Imagine a PR that adds `POST /count` next to `/upper`. Reviewer asks:

1. Is count logic only in the handler?
2. Will gRPC tomorrow copy again?
3. What is the stable name for the metric?
4. Where is the timeout?

If the PR has no answers, the challenges from this lesson are already there — they just do not hurt enough yet for the team to see them.

**Predict-then-answer F**

Question: should you introduce kit *before* the second transport?

- Predict: “only when gRPC arrives”.
- Answer: pragmatically — if you expect a second transport, multiple teams, or heavy observability, an endpoint boundary *earlier* reduces debt. If it is one internal HTTP tool with a short life, stdlib may be enough. The lesson asks you to *name* the challenge, not always add a dependency.

### Step 12 — walkthrough: one request through the naive stack

Mentally follow one `POST /uppercase` with body `{"s":"go"}`:

1. `net/http` server receives the request in a new goroutine (server runtime).
2. Router picks `uppercaseHandler`.
3. Handler reads body, `json.Decode` into an anonymous `struct`.
4. Validate: empty string?
5. `strings.ToUpper`.
6. `json.Encode` response.
7. (Optional) somewhere a log — or nowhere.

Now the same use-case over gRPC `Uppercase` RPC: steps 3–6 *repeat* in another file, with different error types (`status.Error`). Observability (step 7) often is missing.

With the kit map, the same request looks like this:

1. Transport (`httptransport.NewServer`) decode → typed request `struct`.
2. (Optional) endpoint middleware: start timer, log fields.
3. Endpoint: type assert `request interface{}` → `uppercaseRequest`, call `Service.Uppercase(ctx, ...)`.
4. Service: job + domain errors.
5. Back through middleware (latency, error).
6. Transport encode + HTTP status map.

**Predict-then-answer G**

Question: in which step may `json.Decoder` live?

- Predict: “in service, so it is in one place”.
- Answer: no — `json.Decoder` is a wire concern. It lives in transport decode. Service receives an already typed string/DTO. Otherwise service depends on HTTP JSON and gRPC cannot call it cleanly.

### Step 13 — walkthrough: “SKU not found” error

Without layers, three handlers do three different things:

| Handler | Behavior |
|---------|----------|
| HTTP v1 | `404` + plain text |
| HTTP v2 | `200` + `{"error":"..."}` (anti-pattern) |
| gRPC | `codes.Internal` (wrong) |

Clients retry Internal, cache wrongly treats 200, monitoring does not group the same thing.

Target discipline:

1. Service returns `ErrNotFound` (sentinel or typed).
2. Endpoint passes `error` upward (or packs it into a response `struct` — the team picks one style and sticks to it).
3. Each transport maps the *same* domain error to *its* wire code: HTTP 404, gRPC `NotFound`.

**Predict-then-answer H**

Question: should the endpoint know about `http.StatusNotFound`?

- Predict: “yes, to be complete”.
- Answer: no. HTTP status is a transport concern. Endpoint/service stay transport-agnostic. If endpoint imports `net/http` for status, the dependency arrow is already broken.

### Step 14 — walkthrough: adding logging fields

You want fields: `transport=http|grpc`, `endpoint=uppercase`, `took_ms`, `error_kind`.

Naive approach: manually in every handler. Forget one field — logs useless for query.

Better approach (later in the module):

```go
logger := log.With(base, "endpoint", "uppercase")
// in middleware around endpoint.Endpoint
```

`github.com/go-kit/log` (`NewLogfmtLogger`, `With`) gives structured fields; endpoint middleware fills `took_ms` once. Transport can add `transport=http` at the edge.

### Step 15 — walkthrough: test pyramid in numbers

Imagine 40 tests:

| Layer | Count | What you assert |
|-------|-------|-----------------|
| Service | 28 | empty input, unicode, error paths |
| Endpoint | 8 | cast fail, request/response mapping |
| Transport | 4 | JSON shape, status codes |

Without the pyramid, all 40 go through `httptest` — every JSON field change breaks 40 tests. With the pyramid, a JSON change breaks 4.

**Predict-then-answer I**

Question: must an endpoint test *start* a TCP port?

- Predict: “yes, otherwise it is not a real test”.
- Answer: no. Endpoint is an ordinary function: you call it with `context.Background()` and a request value. TCP is transport integration.

### Step 16 — walkthrough: wiring explosion

After 10 use-cases, naive `main` has 400 lines of `HandleFunc`. Nobody dares touch middleware order.

Kit style (preview, detail in later lessons):

```go
var svc service.Service
svc = service.New(...)
svc = service.LoggingMiddleware(logger)(svc)

upper := endpoint.Chain(
    middleware.Logging(logger),
    middleware.Instrument(hist),
)(makeUpperEndpoint(svc))

http.Handle("/uppercase", httptransport.NewServer(
    upper,
    decodeUpperRequest,
    encodeResponse,
))
```

Here you see *where* each concern lives. The challenge “everything in main as spaghetti” is solved by organization, not magic.

### Step 17 — challenge: partial failure and downstream

Service calls billing API and inventory API. Billing succeeds, inventory fails. Without a clear policy:

- some handlers roll back
- some return 500 leaving the charge in place
- some “best effort” stay silent

Kit does not choose SAGA vs compensation. But the challenge *shows* why business rules must be in the service, not scattered across transport handlers — otherwise each wire does a different partial-failure.

**Predict-then-answer J**

Question: may an HTTP handler call billing directly “because it is faster for now”?

- Predict: “yes in MVP”.
- Answer: MVP may, but record the debt. A second transport *must* copy or refactor into service. Better immediately `Service.Checkout` even if it is a thin wrapper method.

### Step 18 — mechanism wrap-up: checklist before 07.03

Before you pin kit in `go.mod`, confirm:

1. You know at least 5 challenges in *your own* words.
2. You can show the arrow transport → endpoint → service on paper.
3. You distinguish “we need kit” from “we need a platform”.
4. You accept that `endpoint.Endpoint` uses `interface{}` in the v0.12 API.
5. You do not expect a generic `Endpoint[T]` as the official kit contract.

If these five hold, 07.03 makes sense. If not, go back to Examples and do exercises 1–2.

## Rules and syntax

1. **Name the problem before the solution.** If you cannot say which challenge kit solves in your PR, you are probably adding ceremony.
2. **Do not introduce middleware until you have a use-case.** First service method, then endpoint, then the chain.
3. **Observability is a requirement, not an afterthought.** Plan latency and error rate by use-case name.
4. **Transport is replaceable.** HTTP today, gRPC tomorrow — same endpoint.
5. **Domain errors ≠ wire errors.** Do not mix decode fail with “entity not found”.
6. **`context` carries deadline and cancel.** Pass it; do not swallow it.
7. **Document team challenges** (ADR / README): why kit, which transports, where authz.
8. **One place for the business rule.** Copy-paste validate is a smell.
9. **Test pyramid:** service > endpoint > transport integration.
10. **Toolkit ≠ platform.** Deploy, mesh, certs stay outside kit.
11. **`endpoint.Endpoint` signature is fixed in the kit API** (`request/response interface{}`); do not invent `Endpoint[T]` as if it were kit API.
12. **Wiring explicit in `cmd`.** Avoid hidden globals.

## Examples

### Example 1 — double validate across HTTP and gRPC

```go
// HTTP
if sku == "" { http.Error(w, "sku", 400); return }

// gRPC (another file, a month later)
if sku == "" { return nil, status.Error(codes.InvalidArgument, "sku") }
```

Product adds a rule: SKU must be uppercase. One handler updated, the other not — prod incident.

### What happens here

Duplication challenge. Target state: `Service.GetProduct(ctx, sku)` rejects a bad SKU once. HTTP and gRPC only map the error. Endpoint layer holds the request cast.

### Example 2 — log only in HTTP middleware

```go
mux.Handle("/upper", loggingMiddleware(http.HandlerFunc(upperHandler)))
// gRPC server without interceptor — silent
```

Incident on the gRPC path: no latency logs, debug takes hours.

### What happens here

A platform concern hooked to the wrong layer (only one transport). Endpoint middleware logs the use-case regardless of wire.

### Example 3 — tests only through `httptest`

```go
func TestUpper(t *testing.T) {
    rr := httptest.NewRecorder()
    req := httptest.NewRequest("POST", "/upper", strings.NewReader(`{"s":"a"}`))
    uppercaseHandler(rr, req)
    // assert JSON body...
}
```

Twenty tests, all break when you change JSON field `s` → `input`, even though `ToUpper` is the same.

### What happens here

Mixing transport contract and the job. Test `Service.Uppercase` directly for business branches; cover the JSON contract with fewer transport tests.

### Example 4 — ops cost remains (link to 04.01)

The team expects kit to “solve microservices”. You still need: deploy pipeline, dashboards, on-call, backoff policy, request size limits.

### What happens here

Kit reduces structural debt in code. It does not erase the operational cost of a distributed system. Motivation for kit must be accurate, or disappointment and a wrong ADR follow.

### Example 5 — authz copy-paste

```go
func upperHandler(...) {
    if !authorized(r) { http.Error(w, "no", 401); return }
    // job
}
func countHandler(...) {
    if !authorized(r) { http.Error(w, "no", 401); return }
}
```

### What happens here

Cross-cutting concern without middleware composition. Later: `endpoint.Chain(authMiddleware, loggingMiddleware)(upperEndpoint)`. One auth rule change — one file.

### Example 6 — correlation id only in HTTP header

Gateway sends `X-Request-Id`. HTTP handler logs it. gRPC path uses metadata key `request-id`, but nobody reads it. Trace in Jaeger breaks at the boundary.

### What happens here

Request identity is a platform concern that must enter `context` early (transport) and be available to endpoint middleware / service logs. Without a shared contract, each wire invents its own key.

### Example 7 — “temporary” shared helper that pulls `net/http`

```go
// package service
func WriteErr(w http.ResponseWriter, err error) { /* ... */ }
```

Service package now imports `net/http`. gRPC module cannot use `WriteErr`. Domain tests pull HTTP.

### What happens here

Wrong dependency direction. HTTP status helper belongs in the transport package. Service returns `error`; transport writes the wire.

### Example 8 — metrics with different buckets

HTTP middleware uses Prometheus buckets `[0.01, 0.05, 0.1, 0.5]`. gRPC interceptor uses default buckets. Same use-case, incomparable histograms, fake SLO conversations.

### What happens here

Observability must be agreed at use-case level (endpoint middleware with one histogram vec), not “each on its own transport”.

## Decision analysis

| Decision | When it makes sense | Risk if wrong |
|----------|---------------------|---------------|
| Stay on plain `net/http` | One transport, small team, short life | Pain on second transport |
| Introduce endpoint boundary early | Expect gRPC / queue / multiple teams | More files at the start |
| Log on HTTP middleware | Only HTTP forever | Silence on other wires |
| Log on endpoint middleware | Multiple transports, same metrics | Needs name discipline |
| Validation in transport | Wire shape only | Business rules leak into JSON |
| Validation in service | Domain invariant | Transport must map error |
| Everything in `main` | Spike / POC | God object in production |
| Explicit wiring | Prod / multiple devs | A bit more boilerplate |
| Kit for the CV | Never as the only reason | Ceremony without benefit |
| Kit for mapped challenges | This table “hurts” | — |

Team ADR question: *which three challenges from the table do we already have?* If none, delay kit. If three+, build layers deliberately.

## Trade-offs

- **More files / types at the start** vs **less pain on the second transport**. Initial cost is real; it pays when the system grows.
- **Endpoint `interface{}` abstraction** vs **simple typed handler**. You lose a bit of type safety at the boundary; you get one signature for Chain and transport adapters. (Kit v0.12 uses `interface{}`, not generic `Endpoint[T]`.)
- **Early observability** vs **prototype speed**. A prototype can skip histograms; production rarely can.
- **One fat service** vs **many microservices**. Kit does not choose service boundaries — you do. Wrong boundaries + kit = prettier chaos.
- **Shared validate library** without endpoint vs **real endpoint layer**. Shared lib helps, but does not solve metrics/logging once for all transports.
- **Learning curve for a new member** vs **repeatable pattern**. You need onboarding docs; otherwise folders confuse.
- **Strangler migration** vs **big-bang rewrite**. Strangler takes longer on the calendar, but less production risk; big-bang looks faster until a release breaks.
- **Central error types in service** vs **ad-hoc string errors**. Central types need discipline; strings are faster and more expensive in support.
- **One logger contract** (`go-kit/log` or other) vs **fmt.Println in handlers**. The second “works” until you need field queries in Loki/ELK.

## Common mistakes

1. **Introduce kit for the CV** — no challenges, only folders.
2. **Ignore challenges** until they explode in an incident.
3. **Leave everything in `main`** and call it “temporary” for a year.
4. **God object service** that knows HTTP, SQL, and Kafka.
5. **Premature abstraction** — ten middlewares before the first use-case.
6. **Mixing domain error with 500** — alert noise and bad client retry.
7. **Forgotten timeout / `context`** — zombie work.
8. **Metrics by URL instead of use-case name** — breaks when path versions.
9. **Tests only through HTTP** — brittle suite.
10. **Expecting kit to solve ops / discovery / TLS**.
11. **Double validate “temporarily”** in two transports.
12. **Authz only in one handler** — another endpoint stays open.

## Idiomatic Go

- Small, focused `interface` types for service (e.g. one group of use-case methods).
- `context.Context` as the first argument of methods that do I/O or can be canceled.
- `error` as the last return value; do not panic for expected business errors.
- Composition over inheritance: middleware is `func(Endpoint) Endpoint`, not a base class.
- Explicit dependencies via `struct` fields / constructor, not hidden globals.
- Package boundaries: `internal/service`, `internal/endpoint`, `internal/transport` — detail in 07.03.
- Zero value and clear request `struct` types instead of “map[string]interface{} everywhere” in the domain.
- Names in log/metrics: stable, short, without PII.

## Practical scenario

A team has an HTTP string service for six months. Product asks for gRPC for an internal BFF. Without an endpoint layer:

- Two weeks: copying validate, error map, metrics.
- Three incidents: gRPC accepts empty string that HTTP rejects.
- SRE: two dashboards, different names.

Another team, same product ask, but with kit endpoints from the start:

- One day: gRPC transport + encode/decode.
- Same service tests still green.
- Same latency histogram label `uppercase`.

The difference is not “talent” — the difference is that the first team paid this lesson’s challenges with interest. The second named them and mapped them to layers while the pain was still cheap.

Shared scenario conclusion: **time to second transport** and **number of diverged validate rules** are better KPIs than “number of kit imports”. If after introducing kit the KPI does not drop, you did not extract an endpoint — you only renamed folders (see insight 12).

## Summary

- Services hurt through duplication, mixed concerns, observability, testing, wiring, and resilience — not through a lack of `if`s.
- Each challenge maps to a future layer: service, endpoint, transport, middleware.
- Kit answers by *composition* and clear boundaries, not inheritance magic and not a platform.
- Toolkit ≠ platform; ops and product semantics remain yours.
- Canonical endpoint signature (kit v0.12): `func(ctx context.Context, request interface{}) (response interface{}, err error)`.

This section expands the challenge → layer mapping with insights for code review and runbook. Goal: 14 *real* insights, without generic filler.

### 1. insight

**A chatty monolith over the network is not a kit problem.** If you sliced a monolith into N services that still exchange chatty calls, kit will only package the pain more neatly. First fix boundaries and data (04.01), then code structure. A kit endpoint does not reduce the number of network hops; it only makes each hop more consistent.

Practical check: count remote calls per one user action. If >5 without batching, kit is not the first priority.

Review question: “Does this PR reduce chatiness or only repackage handlers?”

### 2. insight

**Idempotency is not a kit feature.** `endpoint.Chain` does not make `CreateOrder` safe for retry. That is product + store semantics (idempotency key, upsert). Middleware retry without that semantics *creates* duplicates.

Practical check: for every write endpoint write “may it be repeated?” in an ADR.

### 3. insight

**DTO versioning remains your problem (04.05).** Endpoint stabilizes the use-case, but you still version JSON/proto fields. Do not expect the `transport/http` folder to magically solve a breaking change.

Practical check: do you have a compatibility policy (`additive only`, deprecation window)?

### 4. insight

**Kit helps structure, not the product roadmap.** Nicely stacked layers do not say *which* use-case to build. Do not use layer refactor as a substitute for unclear requirements.

Practical check: is the current PR “folder cleanup” or “behavior delivery”? Name it honestly.

### 5. insight

**SRE wants the same metrics by use-case name.** URL changes (`/v1` → `/v2`); endpoint name `uppercase` stays. Agree on label convention *before* dashboard explosion.

Practical check: compare Prometheus labels HTTP vs gRPC on the same job — do they match?

### 6. insight

**Security: authz often on endpoint middleware.** Authentication can extract identity from the wire (transport), but the decision “may this principal do this use-case” often belongs to endpoint or service middleware so it applies to all transports.

Practical check: find an endpoint without authz that “wasn’t reached yet” — that is a hole, not backlog romanticism.

### 7. insight

**Data race in service state is still your bug.** Kit does not protect a `map` without a mutex in a service `struct`. More requests = more goroutines. Race detector (`go test -race`) remains mandatory.

Practical check: run `-race` on the service package before blaming transport.

### 8. insight

**Document failure modes before code.** “What if DB timeout?” “What if partial write?” If you have no list, retry and error middleware will be guessing.

Practical check: for one use-case write 5 failure modes and expected status/log.

### 9. insight

**The “too many microservices” challenge kit does not solve.** If you have 30 services with one developer, the problem is org / boundary, not lack of `endpoint.Endpoint`.

Practical check: how many services does one feature PR change on average? If >3, think about joining, not more middleware.

### 10. insight

**A polyglot environment (05.xx) needs a shared contract.** Kit in a Go service does not align a Java client. You need proto/OpenAPI + error agreement. Endpoint in Go only eases *your* side.

Practical check: where does the contract source of truth live — repo? portal? nowhere?

### 11. insight

**Legacy handler → strangler toward endpoint.** No need for big-bang. Extract a service method, add endpoint, leave the old handler as a thin delegate, then replace transport.

Practical check: pick *one* handler this week for strangler, not the whole monolith.

### 12. insight

**Measure time to second transport as a refactor KPI.** If after a “kit migration” adding gRPC still takes two weeks, you did not extract an endpoint — you only renamed folders.

Practical check: stopwatch on a spike: new transport for an existing use-case. Goal: hours/days, not sprints.

### 13. insight

**Training cost: a new member learns layers.** Without a dependency diagram, `internal/endpoint` looks like magic. Onboarding checklist must include this lesson + 07.04.

Practical check: new member in 30 min draws the arrow transport → endpoint → service. If they cannot, docs are weak.

### 14. insight

**Without challenges, stdlib is enough; with challenges, kit reduces chaos.** Final message: choose deliberately. Write “why kit” in an ADR. Do not jump to metrics middleware before a service interface. 07.03 sets module and pin so the next steps are reproducible.

Practical check: write one ADR sentence: “We introduce kit because ___ ; we do not introduce it because ___.”

Review note: if a PR adds `github.com/go-kit/kit` without an ADR link or without at least one challenge from this lesson listed, ask for justification before merge — not as ceremony, but as protection from toolkit-for-CV.

### Quick recap

- Challenges: duplication, mixed concerns, log/metrics, tests, late transport, wiring, `context`, errors.
- Map: service = job; endpoint = use-case adapter; transport = wire; middleware = platform around the use-case.
- Predict loops in Mechanism practice “where it hurts” before copy-paste solutions.
- Kit ≠ ops platform; ≠ idempotency; ≠ DTO versioning; ≠ the right number of services.
- ADR and SRE labels by use-case name protect the future more than a “pretty” folder.
- Strangler > big-bang; measure time to second transport.
- `-race`, failure modes, authz holes — remain your discipline.
- Next step is not business logic yet — but the environment (07.03).
- `endpoint.Endpoint` in kit v0.12: `func(ctx context.Context, request interface{}) (response interface{}, err error)`.
- Transport replaceability is the test: “how many files do I touch for gRPC?” — goal is a small number.

### Mini checklist after reading

1. You have a list of ≥5 challenges mapped to layers.
2. You distinguish domain error from wire/decode error on one example.
3. You know why endpoint name helps metrics more than URL.
4. You can explain “toolkit ≠ platform” to a colleague in 30 seconds.
5. You have not announced kit without at least one real pain in an ADR.
6. You predict where authz and latency log go when a second transport arrives.
7. Go back to Lesson goals and check each item honestly.
8. Open 07.03 with the question: “how can folders support this map?”
9. Do Predict-then-answer A–J without looking at answers; mark where you were wrong.
10. Write in the handbook one sentence: “Our most expensive challenge is ___ because ___.”
11. Mark three challenges kit *does not* solve (ops, idempotency, number of services) so you do not expect magic.
