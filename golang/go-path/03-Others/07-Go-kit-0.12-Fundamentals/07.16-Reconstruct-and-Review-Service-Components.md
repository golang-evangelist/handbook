# 07.16 Reconstruct and Review Service Components

> **Go Path - Zero to Gopher** / **03 Others → Go kit 0.12 Fundamentals** / Lesson 07.16

## Lesson goals

After this lesson you should be able to:

- assemble the **whole** StringService in your head and in code (one runnable `main`)
- respect the **wire order**: logger → metrics → svc → logMW → instrMW → endpoints(+trace) → HTTP → server
- draw a **diagram** of layers and middleware order
- run **tests**, **curl** (happy + error), check **`/metrics`**
- do **graceful shutdown** (signal + server Shutdown + tracer flush idea)
- understand that **optional gRPC reuses** the same endpoints
- do a final **review** against layer leakage (07.09 gate spirit)

## Prerequisite

- 07.05–07.15 (business, req/resp, endpoint, transport, review, log, metrics, visibility, SD awareness, tracing awareness)
- local Go module with pinned go-kit 0.12 and `github.com/go-kit/log`

## Problem this lesson solves

Lesson pieces must join into **one** working service. Otherwise you are left with a folder of half-wired files and a false sense of progress. Reconstruction is the exam: whether you understand the order, not only the definitions.

## Mental model

```
main wiring (outside → inside for the request):

  signal.Notify → http.Server
       │
       ▼
  HTTP transport (Before rid, decode, encode, Finalizer)
       │
       ▼
  endpoint (+ TraceMiddleware)
       │
       ▼
  Service : InstrMW → LogMW → core stringService
       │
  metrics ← InstrMW     logger ← LogMW / transport
  /metrics scrape (separate)

Wire construction (often reverse of request flow):
  logger → metrics → svc → logMW → instrMW
        → make endpoints → wrap trace
        → NewHTTPHandler → ListenAndServe
```

Remember: **construction** stacks decorators; the **request** passes through them in the reverse / defined order — document which you chose.

## Mechanism

### Step 0 — Definition of Done (reconstruction)

Green means:

1. `go test ./...` passes
2. process listens; curl happy 200 + expected body
3. curl / empty → documented error style (A or B)
4. `/metrics` shows RED series
5. log has rid (and trace_id if OTel)
6. Ctrl+C → graceful shutdown without panic
7. diagram in README
8. no `net/http` in the service package

### Step 1 — packages (suggested layout)

```
/cmd/stringsvc/main.go
/internal/service/service.go          // interface + core
/internal/service/middleware.go       // log + instr MW
/internal/endpoint/endpoint.go        // makeUppercase, makeCount
/internal/transport/http.go           // decode/encode/handlers
/internal/transport/grpc.go           // optional later
```

Adapt names; the **boundary** matters.

### Step 2 — wire order in main (canonical for the course)

```go
// shape — do not stamp every metrics/otel constructor
logger := log.With(baseLogger, "service", "stringsvc")

// metrics: Counter + Histogram (07.12) — exact adapter from docs
requestCount := /* … */
requestLatency := /* … */

var svc service.Service
svc = service.New()
svc = service.LoggingMiddleware(logger)(svc)
svc = service.InstrumentingMiddleware(requestCount, requestLatency)(svc)

var uppercase endpoint.Endpoint
uppercase = makeUppercaseEndpoint(svc)
uppercase = TraceMiddleware("uppercase")(uppercase) // 07.15 if you introduce it

// same for count if it exists

handler := NewHTTPHandler(uppercase, /* count */, logger)
// otelhttp wrap optional
// /metrics on the same or a separate mux

srv := &http.Server{Addr: addr, Handler: handler, ReadHeaderTimeout: …}
// listen + signal shutdown
```

**Predict-then-answer A**

Question: does `InstrumentingMiddleware` before `LoggingMiddleware` change request semantics?

- Predict: “whatever”.
- Answer: it changes *who wraps whom*. The request sees the outer MW first. Document: e.g. Instr outside → Log inside → core (or reverse) and **stick to it**.

### Step 4 — MW order discipline

Service MW:

- Both implement the same `Service` interface.
- Order in `main` must be in README in one sentence.
- MW tests can stub `next`.

Endpoint MW (trace):

- After `makeXxxEndpoint(svc)`, before bind to transport.
- You do not put Trace MW inside the service package.

### Step 8 — curl scenarios

Happy:

```bash
curl -sS -X POST localhost:8080/uppercase \
  -H "Content-Type: application/json" \
  -d "{\"s\":\"hello\"}"
```

Error (`ErrEmpty`):

```bash
curl -sS -X POST localhost:8080/uppercase \
  -H "Content-Type: application/json" \
  -d "{\"s\":\"\"}"
```

Metrics:

```bash
curl -sS localhost:8080/metrics | head
```

Check rid in the process log output.

### Step 9 — graceful shutdown

```go
// shape
idleConnsClosed := make(chan struct{})
go func() {
    sig := make(chan os.Signal, 1)
    signal.Notify(sig, os.Interrupt) // + SIGTERM on Unix
    <-sig
    ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
    defer cancel()
    _ = srv.Shutdown(ctx)
    // tracerProvider.Shutdown(ctx) if OTel exists
    close(idleConnsClosed)
}()

if err := srv.ListenAndServe(); err != http.ErrServerClosed {
    // log fatal
}
<-idleConnsClosed
```

Without Shutdown: clients see reset; in-flight requests die ugly; spans disappear.

### Step 10 — walkthrough: happy request through all layers

1. Signal path idle; server Accept.
2. otel extract (if any) + Before rid.
3. decode OK.
4. Trace MW Start `uppercase`.
5. Endpoint → Instr defer arm → Log defer arm → core.
6. core returns `"HELLO"`, nil.
7. Instr: Add/Observe success.
8. Log: method/took/err/rid/trace_id.
9. Trace End.
10. encode JSON.
11. Finalizer code=200.
12. scrape later sees +1 rate.

### Step 11 — walkthrough: `ErrEmpty`

Same path; err != nil; success=false; style A/B on HTTP; same rid in both logs.

### Step 12 — walkthrough: bad JSON

Decode fail → no endpoint/service MW → ErrorLogger + Finalizer; domain counter idle.

### Step 13 — walkthrough: Ctrl+C during a request

Shutdown: server stops Accept; waits for in-flight until timeout; MW defers should still finish on active requests; flush trace.

### Step 14 — optional gRPC: reuse endpoints

```
same svc (with MW)
same endpoint.Endpoint values
transport/grpc bind → gRPC server
HTTP and gRPC in parallel in main (two listeners) or separate binaries
```

Point of go-kit: **do not duplicate** business. New decode/encode + bind.

**Predict-then-answer C**

Question: does gRPC require a new InstrumentingMiddleware?

- Predict: “yes, per transport”.
- Answer: no — Service MW already measures the use case for both transports.

### Step 15 — fail review: layer leakage

Red if:

- `service` imports `net/http` / mux
- core logs directly bypassing MW (except a conscious boot log)
- endpoint does SQL
- transport contains business rules (uppercase logic)

Return to the 07.09 mental model.

### Step 16 — fail review: wrong MW order “just because”

If Instr and Log both read begin time OK, but documentation lies — onboarding suffers. Fix docs or code.

### Step 17 — fail review: double listen

Two `ListenAndServe` on the same port without intentional architecture = fail. `/metrics` on the same mux OK; separate port document.

### Step 18 — short load test

```bash
# idea — tool of choice
# N parallel curl / hey / vegeta briefly
```

Watch RED live; do not DDoS prod. Goal: metrics are not dead.

### Step 19 — README completeness

Must have:

- how to build/run
- curl examples
- env variables (ADDR)
- wiring diagram
- MW order
- style A/B
- link to runbook (07.13)
- pinned go-kit version

### Step 20 — anti-pattern catalog

| Anti | Fix |
|------|-----|
| Skipping tests | `go test ./...` |
| Wrong MW order without docs | write it down |
| No shutdown | add signal |
| Double listen | one server/mux plan |
| Orphan endpoint (made, not bound) | remove or bind |
| Docs lie | update in the same PR |
| Copy without understanding | walkthrough from memory |
| gRPC copy-paste of whole service | reuse endpoint |

5. `/metrics` sees series.
6. Log has rid (and trace_id if OTel).
7. No layer leakage.

## Decision analysis

| Option | When | Risk |
|--------|------|------|
| HTTP only | course default | OK |
| HTTP + gRPC | bonus / 05 arc | two listeners |
| Trace MW immediately | if 07.15 done | SDK wiring |
| Trace later | MVP | fewer chain signals |
| metrics on same port | lab | watch auth |
| separate metrics port | prod hardening | ops |

## Trade-offs

- Complete example longer — pedagogically worth it.
- More MW = clearer concerns and a little overhead.
- e2e httptest slower than unit — choose a thin set.
- gRPC bonus increases surface; does not block HTTP DoD.

## Idiomatic Go

- Readable `main`, explicit wiring.
- Clean packages; small `Service` interface.
- Middleware as higher-order function / function literal (Go closure in the language sense).
- `context` through all calls.
- Signal.Notify + Shutdown idiom.
- Fast tests; race where there is shared state.
