# 07.10 Implement Transport Logging

> **Go Path - Zero to Gopher** / **03 Others → Go kit 0.12 Fundamentals** / Lesson 07.10

## Lesson goals

After this lesson you should be able to:

- construct a structured logger via `github.com/go-kit/log` (`NewLogfmtLogger`, `With`)
- add **transport / access logging** at the HTTP edge (path, method, status code, latency as needed)
- use `httptransport.ServerErrorLogger`, `ServerFinalizer`, `ServerBefore` (request id in `context`)
- distinguish transport log from application log (07.11)
- avoid PII and body dumps in log lines
- briefly contrast kit/log with `log/slog` (the course stays on the kit pattern)

## Prerequisite

- 07.09 — core review gate green (tests, thin decode, no http in service)
- 07.08 — `httptransport.NewServer`, encode/decode
- 07.03 — note on `github.com/go-kit/log` (not older paths from outdated tutorials)
- 04.06 (HTTP path) — access log / request id idea; here the kit API

## Problem this lesson solves

Without a transport log you do not see the **edge**: which path, which status, whether decode fails, whether the client gets 499. The application log (07.11) talks about the use case; the transport log talks about the **wire event**. Mixing those two levels gives either duplicates or gaps (e.g. you see an app error, you do not see that it was 200 because style A hides err in the body).

## Mental model

```
client ──HTTP──► [ServerBefore: request id]
                      │
                      ▼
                 decode / encode
                      │
         ServerErrorLogger (wire/encode fail)
                      │
                      ▼
                 endpoint → service
                      │
                      ▼
              ServerFinalizer(code) ──► access log line
```

- **Transport log** = access log (status, path, request_id, component=transport).
- **App log** = method, took, business err (07.11) — *not* here.
- **kit/log** = key-value `Log("k", v, ...)`; `With` for default fields.

## Mechanism

### Step 0 — logger: `NewLogfmtLogger` + `With`

```go
package main

import (
    "os"

    "github.com/go-kit/log"
)

func newLogger() log.Logger {
    var logger log.Logger
    logger = log.NewLogfmtLogger(log.NewSyncWriter(os.Stderr))
    logger = log.With(logger,
        "ts", log.DefaultTimestampUTC,
        "caller", log.DefaultCaller,
    )
    return logger
}
```

Notes:

- `NewSyncWriter` reduces interleaved lines from goroutines.
- `With` adds **base** fields to every `Log` call.
- logfmt is the default spirit of kit tutorials; JSON is OK if the team agrees (`NewJSONLogger`).

**Predict-then-answer A**

Question: can a “temporary” `fmt.Println` in decode stay alongside kit/log?

- Predict: “OK until we hit prod”.
- Answer: no. Two formats = two parsers. Remove Println in the same PR when you introduce kit/log.

### Step 1 — where the transport logger lives

Wiring in `main` / transport factory:

1. Create the root logger.
2. `transportLogger := log.With(logger, "component", "transport")` (or `"http"`).
3. Pass it into `NewServer` options — **not** into the service package.

Service still does not import log *in this lesson* (07.11 does app MW).

### Step 2 — `ServerErrorLogger`

```go
import (
    httptransport "github.com/go-kit/kit/transport/http"
)

handler := httptransport.NewServer(
    endpoints.Uppercase,
    decodeUppercaseRequest,
    encodeResponse,
    httptransport.ServerErrorLogger(transportLogger),
)
```

What it typically catches: errors from the decode/encode path that the server treats as an error path (depends on styles). Used so you **do not stay silent** on wire fail.

Do not expect ErrorLogger to replace Finalizer: one talks about the error object, the other about the **HTTP status code** at the end.

### Step 3 — `ServerFinalizer` for status

```go
httptransport.ServerFinalizer(func(ctx context.Context, code int, r *http.Request) {
    _ = transportLogger.Log(
        "transport", "http",
        "method", r.Method,
        "path", r.URL.Path,
        "code", code,
    )
})
```

Finalizer is called at the end of request handling with the status code. That is the core of the **access log** line.

Extensions (as needed):

- duration: measure in Before (put `time.Time` in ctx) + subtract in Finalizer
- `request_id` from ctx (Step 4)
- `bytes` / user-agent — caution, keep low cardinality / no PII

**Predict-then-answer B**

Question: should Finalizer always log the full `r.URL.RawQuery`?

- Predict: “yes, useful for debug”.
- Answer: caution. Query often carries tokens / email. Prefer path + agreed safe params. PII policy > curiosity.

### Step 4 — `ServerBefore` and request id

```go
type ctxKey int

const requestIDKey ctxKey = 0

func withRequestID(ctx context.Context, id string) context.Context {
    return context.WithValue(ctx, requestIDKey, id)
}

func requestIDFrom(ctx context.Context) string {
    if v, ok := ctx.Value(requestIDKey).(string); ok {
        return v
    }
    return ""
}

httptransport.ServerBefore(func(ctx context.Context, r *http.Request) context.Context {
    id := r.Header.Get("X-Request-Id")
    if id == "" {
        id = newID() // UUID / ulid — your choice
    }
    return withRequestID(ctx, id)
})
```

In Finalizer:

```go
_ = transportLogger.Log(
    "request_id", requestIDFrom(ctx),
    "path", r.URL.Path,
    "code", code,
)
```

Link to 04.06: same correlation idea; here it enters through a kit Option, not an ad-hoc global.

**Predict-then-answer C**

Question: must request id be a UUID?

- Predict: “yes, standard”.
- Answer: it must be **unique enough** and free of PII. UUID/ULID are common; short random is also OK. More important: the same id in transport and (later) app log.

### Step 5 — assembling `NewServer` options

```go
handler := httptransport.NewServer(
    endpoints.Uppercase,
    decodeUppercaseRequest,
    encodeResponse,
    httptransport.ServerErrorLogger(transportLogger),
    httptransport.ServerBefore(injectRequestID),
    httptransport.ServerFinalizer(accessLogFinalizer(transportLogger)),
)
```

The order of Before/Finalizer/ErrorLogger is not a “business order” like Chain middleware — these are server hooks. Read kit docs when something does not fire as you expect; do not memorize every Option.

### Step 6 — walkthrough: happy path through transport log

1. Client `POST /uppercase` with `X-Request-Id: abc` (or generated).
2. `ServerBefore` puts `abc` in ctx.
3. Decode OK → endpoint → service → `"GO"`.
4. Encode 200.
5. Finalizer: `path=/uppercase code=200 request_id=abc`.
6. **No** body `"s":"..."` in the log.

App log does not exist yet (07.11) — and that is OK: you see that the edge succeeded.

### Step 7 — walkthrough: bad JSON

1. Body is not JSON.
2. Decode error.
3. ErrorLogger records the error (message without body dump!).
4. Client 400.
5. Finalizer: `code=400`.

If ErrorLogger prints the raw body — that is a **policy bug**, not a feature.

### Step 8 — walkthrough: `ErrEmpty` (depends on style)

Style B (`return nil, err`): ErrorEncoder → 400; Finalizer `code=400`; ErrorLogger may see err.

Style A (err in body, `error == nil`): Finalizer can show **200** while the body has `"err":"empty string"`. That is why transport log ≠ the whole truth — hence 07.11 / a clear ErrorEncoder policy.

Gate 07.09 required a documented style exactly because of this.

### Step 9 — what **not** to log (PII / body)

Forbidden / strictly limited:

- raw request/response body
- Authorization header, cookie
- email, phone, card, exact token
- unbounded query string with secrets

Typically allowed:

- path template or path without secret segments
- method, status code
- request_id
- latency ms
- error *type* / sentinel name, not personal content

Truncate if you must have a debug string (e.g. first 16 runes) — and prefer that in app log 07.11 with a policy.

### Step 10 — kit/log vs `log/slog` (brief)

| | kit/log | slog |
|--|---------|------|
| Style | `Log("k", v, ...)` | `Info("msg", "k", v)` / attrs |
| In kit ecosystem | natural fit with tutorials / MW examples | needs adapter or parallel logger |
| Stdlib | no | yes (Go 1.21+) |
| Course | **use kit/log here** | know it exists; migration later OK |

Do not dual-write “both kit and slog” in the same PR without need. One format, one sink.

**Predict-then-answer D**

Question: does slog make Finalizer unnecessary?

- Predict: “slog middleware replaces everything”.
- Answer: no. Finalizer is a kit hook for the **HTTP code** at the end of the `NewServer` lifecycle. slog does not magically know about kit Finalizer.

### Step 11 — latency in Finalizer (pattern)

```go
type startKey struct{}

func withStart(ctx context.Context) context.Context {
    return context.WithValue(ctx, startKey{}, time.Now())
}

// in ServerBefore: ctx = withStart(ctx)
// in Finalizer:
start, _ := ctx.Value(startKey{}).(time.Time)
_ = logger.Log("took_ms", time.Since(start).Milliseconds(), "code", code)
```

Keep `took` at the transport level as *request* duration. App `took` in 07.11 measures the service method — they can differ (decode overhead). That is a feature, not a bug — do not swap them.

### Step 12 — ErrorEncoder + log (do not duplicate the message badly)

If ErrorEncoder already writes a JSON problem detail to the client, the log should carry:

- brief `err`
- `code`
- `request_id`

Do not log the same long stack three times (ErrorLogger + Finalizer + manual in encode). Agree: ErrorLogger for unexpected; Finalizer always the access line.

### Step 13 — walkthrough: request id correlation toward 07.11

Even though app MW is not written yet, prepare the contract:

1. Before puts id in ctx.
2. Later LoggingMiddleware reads the same key.
3. One `request_id` in a Grafana/Loki query joins transport + app lines.

If 07.11 introduces a *different* key name — correlation breaks. Document the key in a handbook note.

### Step 14 — testing transport log (pragmatic)

Options:

1. Do **not** assert the log string as the primary test (07.09: log ≠ test).
2. Test behavior: decode error → status 400 (httptest).
3. Optional: `log.NewLogfmtLogger` into `bytes.Buffer` + verify that a Finalizer call exists in a unit test of a *helper* — thin, not a CI idol.

Focus: status and wiring; not grepping “code=200”.

### Step 15 — mux: more routes, same pattern

```go
opts := []httptransport.ServerOption{
    httptransport.ServerErrorLogger(transportLogger),
    httptransport.ServerBefore(injectRequestID),
    httptransport.ServerFinalizer(accessLogFinalizer(transportLogger)),
}
r.Handle("/uppercase", httptransport.NewServer(epUpper, decU, enc, opts...))
r.Handle("/count", httptransport.NewServer(epCount, decC, enc, opts...))
```

Shared options = same access format. Per-route logger: `log.With(transportLogger, "handler", "uppercase")` if needed.

### Step 16 — anti-pattern catalog

| Anti | Why |
|------|-----|
| Body dump | PII, disk, leak |
| `Println` + kit/log | two formats |
| Only ErrorLogger, no Finalizer | no status on success path |
| Only Finalizer, ignores decode err text | harder to debug wire |
| Log in decode business | mixes layers |
| Request id only in response header, not in ctx | app MW cannot see it |
| Logging Authorization | incident waiting |

### Step 17 — linking with 07.09 and 07.11

- 07.09: without a green core, Finalizer only nicely formats a lie.
- 07.11: do **not** repeat path/code in the app log; app log = method/took/err.
- 07.12: metrics for RED; log remains the event, metric the aggregate.

### Step 19 — mechanism wrap-up

You have:

- root logger (`NewLogfmtLogger` + `With`)
- `ServerErrorLogger`
- `ServerFinalizer` access line
- `ServerBefore` request id
- PII policy
- a clear boundary toward app log

### Step 20 — sink and operational details (brief, so you do not break prod)

- Log to stderr (or an agreed file); leave stdout for rare CLI tools.
- In a container, stdout/stderr is collected by the runtime — do not invent local rotate without an ops agreement.
- Do not block the request on a network HTTP log sink “directly from Finalizer” in the first PR; write locally, an agent ships further.
- Line size: access log should fit in one glance; if it has 40 fields, you are cutting the signal.

### Step 21 — correlation with the load balancer

If the LB generates a request id:

1. Before **prefers** the inbound header.
2. Echo the id in a response header (optional, useful for clients).
3. Finalizer logs the same id.

If LB and service use different header names — map both or agree on one. Document in README.

### Step 22 — what is *not* transport logging

- Business “user upgraded plan” events → app / domain event (not Finalizer).
- Rate/p99 metrics → 07.12.
- Distributed trace span → 07.15.
- Debug `Printf` in encode → remove.

Keep this lesson narrow: access + error logger + request id.

### Step 23 — walkthrough: 5xx encode/panic edge

If encode panics or the server returns 500:

1. Finalizer should still record `code=500` when kit reaches the finalizer.
2. ErrorLogger may have the error text.
3. Do not expect an app log if the panic is not in service (or if recover is not set up).

For the course: do not build a full recover stack here; know that access log remains the primary signal for “edge 5xx”.

### Step 24 — checklist “before merging transport logging”

Say out loud:

- Would I know path, code, request_id from one log line at 3:00 a.m.?
- Does the line contain a secret? If yes — stop.
- Is app logging leaking into this PR? If yes — split it out.

Three yes/no answers save review time.

## Rules and syntax

1. Structured key-value (`Log("k", v, ...)`), not Println.
2. `log.With` for component / ts / caller.
3. Finalizer logs **code** (access log).
4. ErrorLogger for wire/encode error visibility.
5. ServerBefore for request id in **context**.
6. **No PII / body dump**.
7. One format (logfmt or JSON) per service.
8. Transport logger does not enter the `service` package here.
9. Do not duplicate app concerns (method took) — that is 07.11.
10. Know slog exists; the course uses kit/log.
11. Test status behavior; do not idolize log string asserts.
12. Shared `ServerOption` for multiple routes.
13. Document the ctx key name for correlation.
14. SyncWriter when writing to shared stderr from more goroutines.

## Examples

### Example 1 — logfmt access line

```
ts=2026-09-25T22:01:02Z caller=main.go:80 component=transport transport=http method=POST path=/uppercase code=200 request_id=abc took_ms=3
```

### What happens here

Loki/grep by `request_id` or `code=5xx`. No body. No Authorization.

### Example 2 — request id Before

Client sends `X-Request-Id`. Before puts it in ctx. Finalizer and (later) app MW read the same.

### What happens here

Cross-service correlation if upstream already has an id; otherwise you generate locally.

### Example 3 — no body dump (incident)

Junior adds `logger.Log("body", string(b))` in decode. Prod leaks email.

### What happens here

Revert + policy in checklist. Debug on staging with a redact tool, not in permanent log.

### Example 4 — comparison with 04.06

In 04.xx: custom middleware around `http.Handler`. Here: kit `ServerOption` hooks. Same goal — access log + id.

### What happens here

Do not learn two worlds; map the concepts.

### Example 5 — style A confuses Finalizer

`code=200` + body err. On-call thinks success.

### What happens here

Either move to ErrorEncoder style B for domain errors, or app log / metric `error=true`. Document it.

### Example 6 — JSON logger instead of logfmt

`log.NewJSONLogger(os.Stderr)` + same `With` fields.

### What happens here

Aggregators that like JSON are happier; kit API is the same.

### Example 7 — per-handler With

`log.With(transportLogger, "endpoint", "uppercase")` in the Finalizer closure.

### What happens here

Easier filter without parsing path; path can still remain.

## Decision analysis

| Option | When | Risk |
|--------|------|------|
| logfmt | kit default spirit, simple | OK |
| JSON | ELK/loki json parser | OK |
| Finalizer only | minimal access | weaker wire err text |
| Finalizer + ErrorLogger | course recommendation | a few more lines |
| slog adapter immediately | team standard slog | extra glue; postpone if learning kit |
| Body log “temporarily” | never in prod | PII |

## Trade-offs

- More logs = disk/cost; filter noise (do not log health check as error).
- SyncWriter vs async buffer: simplicity vs throughput.
- Request id generation: UUID dependency vs short random.
- took on transport vs app: two numbers — document meaning.
- Style A + Finalizer 200: you need another signal for business err.

## Common mistakes

1. `fmt.Println` next to kit/log.
2. PII / body dump.
3. No `code` in the access line.
4. Mixing app and transport fields in the same slog without discipline.
5. Synchronous slow network sink on the request path without a buffer strategy.
6. Different formats per package.
7. Business log in decode.
8. Request id only in response header, not in ctx.
9. Logging Authorization.
10. Asserting log string as the only CI test.
11. Forgotten Finalizer (only ErrorLogger).
12. Duplicate ErrorEncoder + triple log of the same error.

## Idiomatic Go

- `log.With` for default fields; short `Log` calls.
- Typed ctx key (`type ctxKey int`) — not raw string key everywhere (possible, but typed is cleaner).
- `_ = logger.Log(...)` or explicitly handle Log error (rare; stderr fail).
- Alias `httptransport` as in 07.08.
- Options slice shared across routes.

## Practical scenario

Incident: spike of 499/timeout. Finalizer shows `code=499` on `/uppercase` with rising `took_ms`. SRE knows it is the **edge / client / LB**, not a random 500 in app. Without Finalizer, app log (when 07.11 arrives) only shows slow `took` without status — longer diagnosis.

## Deepening: transport logging

### 1. insight

**Exclude health/ready endpoints from noise** or log them at lower interest. Otherwise Loki drowns in `code=200 path=/healthz`.

Practical check: does Finalizer filter `/healthz` / `/ready`?

### 2. insight

**Path cardinality.** `/users/123` as raw path explodes. Prefer the route pattern if you have it; otherwise normalize.

Practical check: can the path label have an unbounded ID?

### 3. insight

**Keep ErrorLogger messages short.** `json: cannot unmarshal` is enough; not raw body.

Practical check: deliberately send bad JSON; check the log line.

### 4. insight

**Same X-Request-Id header name** as the gateway. If Envoy sends another header, Before must read both or the agreed one.

Practical check: which header name is in the platform docs?

### 5. insight

**Do not log business outcome in encode** — encode is wire only. Outcome → Finalizer code + later app log.

Practical check: does encode call logger?

### 6. insight

**Stdout vs stderr.** Often log → stderr, metrics elsewhere. Ops agreement.

Practical check: where does your container runtime collect logs?

### 7. insight

**Clock in tests.** If you test took, inject a clock; otherwise flake.

Practical check: does a unit test of time exist or did you consciously skip?

### 8. insight

**ServerAfter exists in the API** — do not mix it with Finalizer without reading docs. Finalizer is the right place for status code access log in the typical pattern.

Practical check: open the kit transport/http Option list once.

### 9. insight

**Graceful shutdown and mid-request log.** Finalizer should still be called for in-flight where possible; do not expect miracles after a hard kill.

Practical check: link to 07.09 shutdown checklist.

### 10. insight

**One transportLogger, multiple With.** Do not make a global mutable logger without `With` copies.

Practical check: does anyone do `logger =` reassign in a handler?

### 11. insight

**gRPC transport logging** has its own interceptors — same idea (access + code), different API. Do not force the HTTP Finalizer metaphor 1:1 without reading.

Practical check: do you plan gRPC soon? If yes, note a “parity logging” ticket.

### 12. insight

**Sampling.** At extreme QPS, sample 1% of success 200; always log 5xx. Policy > naive “log everything forever”.

Practical check: what QPS do you expect on the exercise? Probably log everything OK.

### 13. insight

**Security: log injection.** If you log a user-controlled string (rarely needed), escape/limit length so it does not break logfmt.

Practical check: does any field come directly from the client without truncate?

### 14. insight

**Preparation for 07.11:** same request_id key; do not log `code` in app MW. Separation of concerns remains.

Practical check: write one sentence of the transport vs app fields contract.

### Appendix: Finalizer function template (extended)

```go
func accessLogFinalizer(logger log.Logger) httptransport.ServerFinalizerFunc {
    return func(ctx context.Context, code int, r *http.Request) {
        fields := []interface{}{
            "transport", "http",
            "method", r.Method,
            "path", r.URL.Path,
            "code", code,
            "request_id", requestIDFrom(ctx),
        }
        if start, ok := ctx.Value(startKey{}).(time.Time); ok {
            fields = append(fields, "took_ms", time.Since(start).Milliseconds())
        }
        _ = logger.Log(fields...)
    }
}
```

Do not add `Authorization`. Do not read the body for logging.

### Appendix: Before template (request id + start)

```go
func injectRequestIDAndStart(ctx context.Context, r *http.Request) context.Context {
    id := r.Header.Get("X-Request-Id")
    if id == "" {
        id = newID()
    }
    ctx = withRequestID(ctx, id)
    ctx = withStart(ctx)
    return ctx
}
```

One Before, two ctx values — less Option noise.

### Appendix: predict-then-answer quick pack (reinforcement)

**H.** Does ErrorEncoder replace Finalizer?  
Answer: no. Encoder maps error→response; Finalizer sees the final code for access log.

**I.** Does `log.With` always mutate the existing logger in-place?  
Answer: `With` returns a **new** logger with added fields (treat as an immutable chain); do not share mutable “current request state” via reassign on the hot path without need.

**J.** Should transport log use `component=service`?  
Answer: no — leave `transport`/`http` so Loki filters work.

### Appendix: encode path errors

Encode can fail (broken pipe). ErrorLogger + Finalizer still give a trail. Do not silently swallow encode error. Do not log the response body at that moment.

### Appendix: link with MaxBytesReader (07.08)

Oversized body → decode/limit error → 4xx. Access log `code=4xx` without body dump. That is a policy success, not a “lack of detail”.
