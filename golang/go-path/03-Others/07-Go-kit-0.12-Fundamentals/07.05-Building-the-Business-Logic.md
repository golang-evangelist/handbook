# 07.05 Building the Business Logic

> **Go Path - Zero to Gopher** / **03 Others → Go kit 0.12 Fundamentals** / Lesson 07.05

## Lesson goals

After this lesson you should be able to:

- write a small **Service** `interface` for StringService pedagogy (`Uppercase`, `Count`)
- implement an **unexported** type (`stringService`) and an exported constructor (`New`)
- keep `context.Context` as the **first** parameter of every method
- return **sentinel** errors (`var ErrEmpty = errors.New(...)`) that the caller checks with `errors.Is`
- write **table-driven** unit tests without `net/http`, JSON, or kit types
- know where the service layer sits in the chain: Transport → Endpoint → **Service** (here you only work on the last)

## Prerequisite

- 07.04 — component names, dependency rule, `endpoint.Endpoint` signature (you do not write it here yet)
- 07.03 — layout `internal/service`, pin `kit@v0.12.0`
- Go: `interface`, method sets, `context.Context`, `errors`, `testing` table tests, `strings`

## Problem this lesson solves

If you put business logic in an HTTP handler (or in decode/encode), you get:

- tests that require `httptest` and JSON just to check `strings.ToUpper`
- inability to expose the same `Uppercase` over gRPC without copy-paste
- review where “business” knows about status code and Content-Type
- panic or `log.Fatal` instead of a typed error that transport can map

This lesson builds a **clean service layer**: only Go types, only domain. No JSON tags, no `endpoint.Endpoint`, no `httptransport`. That comes in 07.06–07.08.

## Mental model

```
┌──────────────────────────────────────────┐
│  Service interface (use-case contract)   │
│  Uppercase(ctx, s) (string, error)       │
│  Count(ctx, s) int                       │
└──────────────────────────────────────────┘
                    ▲
                    │ implements
┌──────────────────────────────────────────┐
│  stringService (unexported struct)       │
│  + New() Service                         │
│  + sentinel ErrEmpty                     │
└──────────────────────────────────────────┘
```

Call flow in a complete service (later):

```
HTTP/gRPC wire → decode → Endpoint → Service.Uppercase → response → encode
                                      ▲
                                      └── you are here in 07.05
```

StringService is a **pedagogical** example from the go-kit `stringsvc` tradition: small enough to see the shape, real enough to practice errors and tests. Your production domain will be richer — the shape stays the same.

## Mechanism

### Step 0 — where the code lives

Typical layout (aligned with 07.03/07.04):

```
internal/service/
  service.go       // interface + ErrEmpty + New
  uppercase.go     // optional: methods if the file grows
  service_test.go  // table tests
```

Package: `package service`. Do not import `net/http`, `encoding/json`, `github.com/go-kit/kit/...`. If `go list` shows those imports in the service package — you broke the layer boundary.

**Predict-then-answer A**

Question: may a service file have `json:"s"` on a struct field?

- Predict: “yes, and the endpoint will use the same.”
- Answer: not in the service layer. JSON tags belong to the transport DTO (07.06). Service takes `string`, not a “wire shape”.

### Step 1 — exported interface, unexported implementation

```go
package service

import (
	"context"
	"errors"
	"strings"
)

// ErrEmpty is a sentinel: empty input is not valid for Uppercase.
var ErrEmpty = errors.New("empty string")

// Service is the contract that endpoint and middleware see.
type Service interface {
	Uppercase(ctx context.Context, s string) (string, error)
	Count(ctx context.Context, s string) int
}

// stringService is the concrete implementation — unexported.
type stringService struct{}

// New returns Service. Caller does not see stringService.
func New() Service {
	return stringService{}
}
```

Why this shape?

| Decision | Reason |
|----------|--------|
| `Service` exported | Endpoint/MW must depend on the contract, not the struct |
| `stringService` unexported | Prevents `svc := service.stringService{}` outside the package; forces `New` |
| `New() Service` | One construction point; later easy to inject dependencies (repo, clock) |
| Zero-value struct | No fields → no shared mutable state → concurrently safe for this example |

**Predict-then-answer B**

Question: may you export `type StringService struct{}` instead of an interface?

- Predict: “yes, simpler.”
- Answer: possible for one file without MW, but the kit pattern and 07.10+ middleware expect `func(Service) Service`. Without an interface, decorators become awkward. Keep the interface from the start.

### Step 2 — context.Context first

```go
func (stringService) Uppercase(ctx context.Context, s string) (string, error) {
	if err := ctx.Err(); err != nil {
		return "", err
	}
	if s == "" {
		return "", ErrEmpty
	}
	return strings.ToUpper(s), nil
}

func (stringService) Count(ctx context.Context, s string) int {
	_ = ctx // reserved for cancel/deadline in slower methods
	return len(s)
}
```

Rules for `ctx`:

1. **First** parameter — Go convention; kit and stdlib expect that order.
2. Do not store `ctx` in a service struct field — it lives only in the call.
3. In slow methods (DB, HTTP client) check `ctx.Err()` / `ctx.Done()` before expensive work.
4. In this pedagogical `Uppercase`, checking `ctx.Err()` is an optional disciplinary gesture; CPU work is cheap, but the pattern remains.

`Count` in the classic stringsvc example often **does not** return `error` — an empty string has length 0. That is a domain decision, not a framework error.

**Predict-then-answer C**

Question: why does `Count` have no `error` while `Uppercase` does?

- Predict: “Count cannot fail.”
- Answer: in this domain every `string` has a length; “empty” is not invalid for counting. `Uppercase` has the business rule “reject empty input”. The error follows the *rule*, not “every method must have error”.

### Step 3 — sentinel errors

```go
var ErrEmpty = errors.New("empty string")
```

How the caller (later endpoint/transport) reacts:

```go
v, err := svc.Uppercase(ctx, "")
if errors.Is(err, service.ErrEmpty) {
	// map to 400 / InvalidArgument — outside the service layer
}
```

Alternative for a larger domain: typed error.

```go
type ValidationError struct {
	Field string
	Msg   string
}

func (e ValidationError) Error() string {
	return e.Field + ": " + e.Msg
}
```

For StringService pedagogy a sentinel is enough and readable in tests.

Do not:

- `panic("empty")` — panic is not an API contract
- `return "", fmt.Errorf("empty")` without wrap/sentinel — caller cannot reliably `errors.Is`
- returning an HTTP status code from a service method

### Step 4 — complete implementation (one file)

```go
package service

import (
	"context"
	"errors"
	"strings"
)

var ErrEmpty = errors.New("empty string")

type Service interface {
	Uppercase(ctx context.Context, s string) (string, error)
	Count(ctx context.Context, s string) int
}

type stringService struct{}

func New() Service {
	return stringService{}
}

func (stringService) Uppercase(ctx context.Context, s string) (string, error) {
	if err := ctx.Err(); err != nil {
		return "", err
	}
	if s == "" {
		return "", ErrEmpty
	}
	return strings.ToUpper(s), nil
}

func (stringService) Count(_ context.Context, s string) int {
	return len(s)
}
```

Note on `_ context.Context` vs named `ctx`: in `Count` you can use `_` if you truly do not read it; in production slow methods keep the name and use it. Team consistency > pedantry.

### Step 5 — table-driven tests (without HTTP)

```go
package service_test

import (
	"context"
	"errors"
	"testing"

	"example.com/stringsvc/internal/service"
)

func TestUppercase(t *testing.T) {
	svc := service.New()
	ctx := context.Background()

	tests := []struct {
		name    string
		in      string
		want    string
		wantErr error
	}{
		{name: "ascii", in: "go", want: "GO"},
		{name: "mixed", in: "GoKit", want: "GOKIT"},
		{name: "empty", in: "", wantErr: service.ErrEmpty},
		{name: "already upper", in: "OK", want: "OK"},
	}

	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			got, err := svc.Uppercase(ctx, tt.in)
			if tt.wantErr != nil {
				if !errors.Is(err, tt.wantErr) {
					t.Fatalf("err = %v, want %v", err, tt.wantErr)
				}
				return
			}
			if err != nil {
				t.Fatalf("unexpected err: %v", err)
			}
			if got != tt.want {
				t.Fatalf("got %q, want %q", got, tt.want)
			}
		})
	}
}

func TestCount(t *testing.T) {
	svc := service.New()
	ctx := context.Background()

	tests := []struct {
		name string
		in   string
		want int
	}{
		{name: "empty", in: "", want: 0},
		{name: "ascii", in: "go", want: 2},
		{name: "unicode bytes", in: "ć", want: len("ć")}, // len = bytes, not runes
	}

	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			if got := svc.Count(ctx, tt.in); got != tt.want {
				t.Fatalf("got %d, want %d", got, tt.want)
			}
		})
	}
}

func TestUppercaseCanceledContext(t *testing.T) {
	svc := service.New()
	ctx, cancel := context.WithCancel(context.Background())
	cancel()

	_, err := svc.Uppercase(ctx, "go")
	if !errors.Is(err, context.Canceled) {
		t.Fatalf("err = %v, want context.Canceled", err)
	}
}
```

Running:

```bash
go test ./internal/service/ -count=1
```

**Predict-then-answer D**

Question: does `Count("č")` return 1?

- Predict: “yes, one letter.”
- Answer: `len(s)` counts UTF-8 **bytes**. `"č"` is often 2 bytes. If the domain wants runes, use `utf8.RuneCountInString`. Document the invariant in a comment or method name (`CountBytes` vs `CountRunes`).

| Thing | Where it goes |
|-------|---------------|
| `uppercaseRequest` / JSON tags | 07.06 |

| `decode` / `httptransport.NewServer` | 07.08 |

### Step 7 — dependencies (when the example grows)

When the service needs a DB:

```go
type Repository interface {
	SaveNormalized(ctx context.Context, s string) error
}

type stringService struct {
	repo Repository
}

func New(repo Repository) Service {
	return stringService{repo: repo}
}
```

Still: interface on top, unexported struct, `ctx` first, sentinel/typed errors. Test injects a fake `Repository`. Kit still does not know about your repo.

### Step 8 — concurrency and state

`stringService` without fields is safe for parallel calls. Anti-pattern:

```go
// BAD — shared buffer
type stringService struct {
	buf []byte
}

func (s *stringService) Uppercase(ctx context.Context, str string) (string, error) {
	s.buf = append(s.buf[:0], str...) // race if multiple goroutines
	// ...
}
```

If you need a cache, use synchronization or per-request local values — not a silent global.

```

```

Until you finish 07.05, do not “skip ahead” into NewServer. A clean service is cheaper to refactor than a transport that knows about `strings.ToUpper`.

### Step 11 — comparing bad and good API

Bad (everything in one “handler” style):

```go
func UpperHandler(w http.ResponseWriter, r *http.Request) {
	var body struct {
		S string `json:"s"`
	}
	_ = json.NewDecoder(r.Body).Decode(&body)
	if body.S == "" {
		http.Error(w, "empty", 400)
		return
	}
	fmt.Fprint(w, strings.ToUpper(body.S))
}
```

Problems: you cannot call the same from gRPC; test needs `httptest`; error is string + status, not an `error` value.

Good (service only — the rest in later lessons):

```go
func (stringService) Uppercase(ctx context.Context, s string) (string, error) {
	if s == "" {
		return "", ErrEmpty
	}
	return strings.ToUpper(s), nil
}
```

Wire shape (`{"s":"..."}`) is not part of this contract. The endpoint will extract `req.S` and call this method.

### Step 12 — what the endpoint expects from you (preview without writing the endpoint)

In 07.07 the factory roughly does:

```text
request (interface{}) → assert → svc.Uppercase(ctx, req.S) → response (interface{})
```

That is why the service signature must be **stable** and **without wire details**. If tomorrow you change JSON field `s` to `text`, the service stays the same — only DTO/decode change.

**Predict-then-answer E**

Question: if you change the JSON key, must you change the `Service` interface?

- Predict: “yes, everything is connected.”
- Answer: no, if you separated layers well. You change DTO + decode; `Uppercase(ctx, s string)` stays.

### Step 13 — export policy checklist before merge

Before you mark a PR ready:

- [ ] `ErrEmpty` (or typed errors) exported if transport must `errors.Is`
- [ ] `Service` exported
- [ ] concrete struct **un**exported (unless the team explicitly wants otherwise)
- [ ] `New` the only constructor on the package public API
- [ ] tests in `service_test` or `service` package — both OK; `service_test` forces the public API
- [ ] README/comment does not promise an HTTP status from a service method

### Step 14 — link to 07.04 dependency rule

From 07.04: transport → endpoint → service (one-way).

This lesson **fills** the bottom of the arrow. If you pull transport types here, the arrow flips and you get a circular import as soon as the endpoint package tries to import a service that imports transport.

Remember: kit v0.12 does **not** export a generic `Endpoint[T]`. You still write an ordinary `Service` interface — you may use generics in your own code for repo helpers, but do not invent that as kit API.

## Rules and syntax

1. **Small interface** — methods = use-case names (`Uppercase`, not `DoStuff`).
2. **`ctx` first** — always; not as a second field in a struct.
3. **Sentinel or typed errors** — caller uses `errors.Is` / `errors.As`.
4. **No JSON tags** in the service layer.
5. **No `net/http`** import in `internal/service`.
6. **Table-driven tests** — happy path + empty + (optional) canceled ctx.
7. **Unexported implementation** + `New() Service`.
8. **No mandatory logging in the method** — middleware later (07.10+).
9. **No reading env/config in the method** — inject in `New`.
10. **No proto / gRPC types** as service API return values.
11. **Document invariants** (`len` = bytes) in a comment or name.
12. **One-way dependency** — service does not know endpoint/transport.

## Examples

### Example 1 — Uppercase happy path

```go
svc := service.New()
out, err := svc.Uppercase(context.Background(), "go")
// out == "GO", err == nil
```

### What happens here

A clean unit call. No mux, no JSON decode. If this fails, transport will not help — fix the service first.

### Example 2 — ErrEmpty

```go
_, err := svc.Uppercase(context.Background(), "")
fmt.Println(errors.Is(err, service.ErrEmpty)) // true
```

### What happens here

The sentinel stays a stable error string/identity. Transport (07.08) maps `ErrEmpty` to 400; the service does not know about 400.

### Example 3 — Count and empty string

```go
n := svc.Count(context.Background(), "")
// n == 0 — not an error
```

### What happens here

Another method, same `Service` value. The domain rule for Count is not the same as for Uppercase — that is why the signatures diverge (`error` vs without).

### Example 4 — test double via interface

```go
type stubService struct{}

func (stubService) Uppercase(context.Context, string) (string, error) {
	return "STUB", nil
}
func (stubService) Count(context.Context, string) int { return 42 }

var _ service.Service = stubService{}
```

### What happens here

An endpoint test (07.07) can inject a stub instead of the real `stringService`. The interface is the double point — that is why it is exported.

### Example 5 — wrap sentinel (when you add a layer)

```go
if s == "" {
	return "", fmt.Errorf("uppercase: %w", ErrEmpty)
}
```

### What happens here

`errors.Is(err, ErrEmpty)` still works because of `%w`. The message becomes richer for logs; the error identity remains.

## Decision analysis

| Option | When you choose | Cost |
|--------|-----------------|------|
| Sentinel `var ErrEmpty` | Small example, 1–3 known errors | Growing number of `var Err*` |
| Typed `ValidationError` | More fields, i18n messages, details | More types, `errors.As` |
| `error` on every method | Uniformity | Fake errors where there are none (e.g. Count) |
| Exported struct without interface | One binary, no MW | Harder decorators, harder test double |
| Interface + unexported impl | Kit style, MW, tests | Small `New` boilerplate |
| Validation in service | Domain rules | Transport must still reject bad JSON |
| Validation only at the edge | Faster service | Duplicate rules if you have multiple transports |

For this course: **sentinel + interface + unexported impl + table tests**.

## Trade-offs

- **Interface from day 1** eases middleware (07.10+) and tests; for one struct in a CLI tool it can feel like over-abstraction — here it is not, because the goal is the kit stack.
- **`strings.ToUpper`** ignores locale; for Turkish `i`/`I` you need another library/rule. Pedagogy ≠ production i18n.
- **`len` vs rune count** — example simplicity vs Unicode domain accuracy; document what you measure.
- **Checking `ctx.Err()` in a cheap method** — discipline vs micro-overhead; the team chooses consistently.
- **Service without logs** — cleaner tests; operators see less until you add MW.

## Common mistakes

1. **HTTP in service** — `http.Error`, status code, reading headers.
2. **Panic on empty** instead of `ErrEmpty`.
3. **Global mutable** (`var cache = map...` without sync).
4. **Log spam in the method** (`log.Printf` on every call) instead of structured MW.
5. **Reading env in the method** (`os.Getenv` mid-`Uppercase`).
6. **Returning proto types** from the service API.
7. **No tests** — “we’ll see on curl”.
8. **JSON tags on a domain struct** that “happens” to be the service model.
9. **`context` in a service struct field**.
10. **Exporting `stringService`** and forcing the caller onto a concrete type.
11. **Mixing a `Count` error** because “all methods must have error”.
12. **Importing kit endpoint in service** “just in case”.

## Idiomatic Go

- `errors.Is` / `errors.As` in the caller, not string compare `err.Error()`.
- Small interface (consumer-side: define what you use).
- Table tests with `t.Run`.
- `New` constructor returns an interface.
- Unexported types for impl details.
- `ctx` first; cancel is respected downward.
- Comments on exported `Err*` and `Service` methods if behavior is unusual.

## Practical scenario

A team builds `PricingService.Calculate(ctx, PricingInput) (Money, error)`. HTTP handler and gRPC server are only adapters. QA writes table tests on `Calculate` with a stub exchange rate client — without starting port 8080. When a new transport arrives (queue consumer), the same service is called from another endpoint factory. Review checklist: “Does `internal/service` import `net/http`?” — fail the PR if yes.

StringService is training for that reflex: first a clean contract, then wire.

## Going deeper: business logic

This section expands the topic with concrete insights for code review and runbook. Fourteen real insights — without filler loops.

### 1. insight — metrics do not belong in the method

Do not stick a Prometheus counter into `Uppercase`. Instrumentation goes as middleware around Service or Endpoint (07.12). Reason: tests otherwise depend on a global registry; dual transport duplicates metrics.

**Check:** would the service method pass a test without a `promauto` import?

### 2. insight — where to validate input

Domain validation (“empty string forbidden”) lives in service. Wire syntax validation (“not JSON”) lives in decode (07.08). If you validate only at the HTTP edge, the gRPC path bypasses the rule.

**Check:** would the same rule hold if tomorrow you add gRPC?

### 3. insight — write idempotency

StringService is pure. When you add `Save`, document whether the call is idempotent (same key → same result). Endpoint/transport do not “guess” — the service contract speaks.

**Check:** is there a comment or test that fixes a repeated call?

### 4. insight — transactions in service/repo

If `Uppercase` becomes “normalize then write”, the transaction belongs to service orchestration or the repo layer — not the decode handler. Kit does not offer an ORM; you choose `database/sql` / pgx.

**Check:** does the HTTP layer open `Begin`? If yes — wrong layer.

### 5. insight — do not return `map[string]any`

A service API with `map[string]any` kills types and forces the endpoint into magic. Return a concrete type or a small struct (domain, not JSON DTO).

**Check:** does IDE autocomplete know the return value fields?

### 6. insight — method names = use case

`Uppercase` reads as a command. `Process` / `Handle` / `Do` smell that the layer has no boundaries. A reviewer should guess input/output from the name.

**Check:** can you write a one-liner what the method does without looking at the body?

### 7. insight — document invariants

`Count` uses `len` (bytes). That is an invariant. Without documentation the next developer “fixes” to runes and breaks clients.

**Check:** is there a test named `unicode_bytes` or a comment on the method?

### 8. insight — race: no shared buffer

A service instance is often a singleton in `main`. Shared `[]byte` without sync = data race under load. `-race` in CI is a cheap signal.

**Check:** `go test -race ./internal/service` green?

### 9. insight — context cancel in slow methods

Pedagogical `ToUpper` is fast. A real service calls DB: respect `ctx`. Ignoring cancel keeps a goroutine after client disconnect — resource leak.

**Check:** does the repo call receive the same `ctx`?

### 10. insight — stringsvc is pedagogy

Official go-kit examples/root stringsvc are a shape, not your domain model. Do not force “everything must be string upper” in production — force **layers**.

**Check:** did you copy folder structure or only method names?

### 11. insight — hexagonal: repo interface below

Service depends on a `Repository` interface that the service package *defines* (or `internal/port`). Implementation is in `internal/postgres`. Arrow: impl → interface, not reverse.

**Check:** does `postgres` import `service` only to implement the port, or does `service` import `postgres`?

### 12. insight — kit does not mandate an ORM

There is no “kit.Model”. Choose the stack independently. The mistake is importing a GORM model as a service return type — persistence leaking into the contract.

**Check:** do JSON/DB tags sit on a type that `Service` returns?

### 13. insight — code review: no net/http import

Simple litmus: `internal/service` must not list `net/http`. If it may — the dependency rule is dead before 07.06.

**Check:** add a CI grep/AST check on forbidden imports.

### 14. insight — fuzz for Uppercase edges

```go
func FuzzUppercase(f *testing.F) {
	f.Add("go")
	f.Add("")
	f.Fuzz(func(t *testing.T, s string) {
		svc := service.New()
		_, _ = svc.Uppercase(context.Background(), s) // must not panic
	})
}
```

Goal: no panic on weird UTF-8 inputs. Empty string → `ErrEmpty`, not crash.

**Check:** `go test -fuzz=FuzzUppercase -fuzztime=5s ./internal/service`

### Quick recap

- Service = contract + clean impl; wire stays outside.
- `ctx` first; sentinel errors; table tests.
- No JSON/HTTP/kit in this package.
- StringService teaches the shape — your domain replaces method bodies.
- Review litmus: forbidden imports + `-race` + clear invariants.
- Next step maps DTO at the edge, does not change this contract.
