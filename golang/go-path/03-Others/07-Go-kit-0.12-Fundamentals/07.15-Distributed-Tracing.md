# 07.15 Distributed Tracing

> **Go Path - Zero to Gopher** / **03 Others → Go kit 0.12 Fundamentals** / Lesson 07.15

## Lesson goals

After this lesson you should be able to:

- explain why **OpenTelemetry (OTel)** is the modern default for tracing
- describe the **middleware shape** around `endpoint.Endpoint` (span start/end)
- understand the fields **trace id** and **span** (parent/child)
- propagate context (**W3C** `traceparent`) through HTTP/gRPC
- connect **rid ↔ trace id** in the log (you do not replace rid)
- apply **sampling** awareness (not 100% in hard prod without a budget)
- **not invent** a kit-only tracing API or unstable span calls

## Problem this lesson solves

Metrics say *that* it hurts; logs say *what* on one node; tracing says *where in the chain*. Kit historically has tracing integrations; industry moved toward OpenTelemetry. The course chooses OTel as the standard and shows how it **wraps** the endpoint — it does not teach outdated Zipkin-only as the only path and does not invent a kit-only API.

## Mental model

```
Trace  = tree (or DAG) of spans for one logical request through the system
Span   = one step (e.g. uppercase endpoint, SQL, outbound HTTP)
Context carries the current span; child span inherits the trace id

HTTP headers (W3C):
  traceparent: version-traceid-spanid-flags

rid (07.10)  ≠  trace id
rid: local correlation in your logs
trace id: correlation across services in the tracer backend
Ideal: log BOTH
```

Endpoint middleware: `Start` span → `next(ctx, req)` → `End` span.

## Mechanism

### Step 0 — why OTel, not a vendor SDK in code

OTel gives **API/SDK** + exporter (OTLP) to Jaeger/Tempo/Honeycomb/…. Code depends on the OTel API; you change the backend by configuration.

Historical Zipkin/OpenTracing paths may exist in old kit packages — read the pin; **new code**: OTel.

**Predict-then-answer A**

Question: must you use Jaeger because “all tutorials”?

- Predict: “yes, Jaeger = tracing”.
- Answer: no. Jaeger is one backend. OTLP → whatever the org uses.

### Step 1 — where the span lives in go-kit layers

| Layer | Tracing role |
|-------|--------------|
| Transport HTTP | extract/inject W3C; server span (often otelhttp) |
| Endpoint MW | use-case span (`uppercase`) |
| Service MW | rarely an extra span; log/metrics already here |
| Core service | without OTel import if you can |

Course preference: **EndpointMiddleware** for the use-case name + HTTP instrumentation for entry.

### Step 2 — EndpointMiddleware shape (defensible)

Non-generic `endpoint.Endpoint` (kit 0.12):

```go
import (
    "context"

    "github.com/go-kit/kit/endpoint"
    "go.opentelemetry.io/otel"
    "go.opentelemetry.io/otel/trace"
)

func TraceMiddleware(spanName string) endpoint.Middleware {
    return func(next endpoint.Endpoint) endpoint.Endpoint {
        return func(ctx context.Context, request interface{}) (interface{}, error) {
            tracer := otel.Tracer("stringsvc")
            ctx, span := tracer.Start(ctx, spanName)
            defer span.End()

            // optional: span.SetAttributes(...) — low cardinality
            resp, err := next(ctx, request)
            if err != nil {
                // status/error recording: read current OTel API
                // typical idea: mark span as error; do not invent a method
            }
            return resp, err
        }
    }
}
```

Discipline notes:

- `tracer.Start` / `span.End` / `trace.SpanFromContext` are **real** OTel patterns — use them when the pin confirms.
- Do not invent `kit.StartSpanMagic(...)`.
- If you are not sure about the `RecordError` / `SetStatus` signature — **describe the intent** and check `go.opentelemetry.io/otel/trace` docs when coding.

**Predict-then-answer B**

Question: is a span in core `stringService.Uppercase` better?

- Predict: “closer to the business”.
- Answer: it dirties the domain with an OTel import. MW on the endpoint keeps service clean.

### Step 3 — `SpanFromContext` (when needed)

```go
span := trace.SpanFromContext(ctx)
// read span.SpanContext().TraceID() for a log field — check API string format
_ = span
```

Use for: adding an event, reading trace id in the logger. Do not call `Start` if you are only reading.

### Step 4 — W3C propagation

Inbound HTTP: middleware/extractor reads `traceparent` → puts parent in context.

Outbound HTTP: injector writes the header from context.

Without propagation: each service starts a **new** trace — you lose the chain. That is a common “tracing does not work” mistake.

gRPC: metadata propagation via OTel interceptor (idea); read otelgrpc docs when implementing.

### Step 5 — sampling

100% sample in prod at huge QPS = cost and I/O. Policies:

- head-based ratio (e.g. 1%–10%)
- always-on for error / latency (tail sampling in the collector — more advanced)
- lab: 100% OK

Document in ops README. Alerting on “no trace” at 1% sample is naive.

**Predict-then-answer C**

Question: why is rid still needed with 5% sample?

- Predict: “trace covers everything”.
- Answer: many requests have no saved trace; rid in the log still captures 100% of app events (with your log policy).

### Step 6 — rid ↔ trace id

In app or access log (key agreement):

```
request_id=… trace_id=…
```

On-call workflow:

1. Alert / RED (07.12–07.13)
2. rid from access
3. app log → read trace_id
4. open tracer UI for that trace
5. see the slow span (e.g. downstream)

Do not put trace_id as a **Prometheus label** (cardinality / 07.12).

### Step 7 — attributes: low cardinality, no PII

Allowed (examples): `rpc.method=uppercase`, `http.status_code` (bucket), `service.name`.

Forbidden: email, full URL with id, raw body, token.

Same discipline as metric labels + log PII.

### Step 8 — wiring order (sketch)

```go
// pseudo-order — adapt factory names to your main
var uppercase endpoint.Endpoint = makeUppercaseEndpoint(svc)
uppercase = TraceMiddleware("uppercase")(uppercase)
// then HTTP transport bind to uppercase
// HTTP server handler wrapped with otelhttp (extract parent)
```

Service MW (log/metrics) still around `svc` before makeEndpoint — as in 07.11/07.12.

### Step 9 — walkthrough: happy path one service

1. Client without traceparent → server creates root span (transport).
2. Endpoint MW: child span `uppercase`.
3. Service log/metrics MW run inside; log can read trace id.
4. Span End; batch export to collector.
5. UI: one trace, 2 spans (HTTP + uppercase) — count depends on instrumentation.

### Step 10 — walkthrough: two services

1. A outbound injects traceparent.
2. B extract → continues the **same** trace id.
3. UI: A HTTP client span → B server span → B uppercase.
4. You see where the 180ms is (as in the practical scenario).

### Step 11 — walkthrough: without propagation

1. A and B have separate trace ids.
2. On-call cannot see the chain.
3. Fix: injector/extractor, not “more Jaeger”.

### Step 12 — walkthrough: style A domain error

1. `ErrEmpty` — HTTP 200 (style A).
2. Span status: think — is domain error = span error? Team agreement.
3. Event/attribute `error.type=ErrEmpty` (enum) can be more useful than status=Error on every expected fail.
4. Do not log PII input.

### Step 13 — HTTP status vs span status

Mapping is not 1:1 magic. 404 can be expected. 5xx often Error. Read OTel semantic conventions; do not invent a proprietary kit map.

### Step 14 — resource attributes

`service.name=stringsvc`, `service.version=…` — on TracerProvider resource, not on every span manually if the SDK does it.

Stable service name = filter in UI.

### Step 15 — export path

```
app SDK → (batch) → OTLP exporter → collector → Tempo/Jaeger/…
```

Lab: all-in-one Jaeger or local collector. Prod: collector gateway, not every pod directly to SaaS without policy.

### Step 16 — kit tracing packages (history)

In the kit tree there may be zipkin/opentacing helpers. Before use:

1. Read whether they are maintained in your v0.12 pin.
2. Prefer OTel for new code.
3. Do not mix OpenTracing API and OTel in the same PR without a migration plan.

**Do not invent** “the official only kit tracing” as a replacement for OTel.

### Step 17 — span per for loop

A thousand spans per request (per item in a slice) = expensive and unreadable. Aggregate; one span + attribute count.

### Step 18 — baggage caution

Baggage propagates key-value through the chain. Do not put huge data or PII. Rarely needed in the StringService lab.

### Step 19 — exemplars (orientation)

Advanced: metric ↔ sample trace. Do not mix with “put trace id in a label”. If the org does not have it — skip.

### Step 20 — testing

- In-memory exporter / sdk trace test helpers (check current packages).
- Unit test MW: whether End is called (defer) even when next returns error.
- Do not require real Jaeger in a `go test` unit.

### Step 21 — anti-pattern catalog

| Anti | Why |
|------|-----|
| 100% sample hard prod without budget | cost |
| PII attributes | compliance |
| High cardinality attributes | backend hurts |
| No propagation | fake “distributed” |
| Span in a tight loop | noise |
| Invented kit-only API | does not compile / lie |
| Trace without rid policy | gap on sample miss |
| OpenTracing + OTel chaos | migration without plan |
| Trace id as Prom label | cardinality |

### Step 22 — linking pillars

| Pillar | Tool | Question |
|--------|------|----------|
| Aggregate | metrics | How much / how bad? |
| Event | log + rid | What exactly? |
| Chain | trace | Where in the graph? |

Three together; none replaces the others.

## Rules and syntax

1. OTel as the default story for new tracing.
2. W3C `traceparent` propagation.
3. Span name = use case (e.g. `uppercase`).
4. EndpointMiddleware shape; non-generic Endpoint.
5. `tracer.Start` + `defer span.End` — verified OTel pattern.
6. `SpanFromContext` for reading / log fields.
7. Do not invent a kit-only tracing API.
8. Attributes: low cardinality, no PII.
9. Sampling policy documented.
10. Log rid **and** trace_id; do not replace.
11. Do not put trace_id in a Prom label.
12. Do not mix OpenTracing legacy into new code without a plan.
13. Span not in a thousand loops.
14. Flush/Shutdown on shutdown (with 07.16).

## Decision analysis

| Option | When | Risk |
|--------|------|------|
| OTel + OTLP | default now | learning curve |
| Vendor agent with OTel API | org standard | OK |
| Logs only | early lab | no chain |
| Endpoint span | course prefer | low |
| Span in service core | anti | dirty domain |
| 100% sample | lab | expensive in prod |
| Tail sampling | mature collector | complexity |

## Trade-offs

- Tracing costs CPU/network; sampling necessary at large QPS.
- More spans = better detail and more noise.
- Domain error as span Error can pollute error rate in tracer UI — agree semantics.
- Propagation + mesh automatic instrumentation sometimes duplicates spans — clean up names.

## Common mistakes

1. 100% sample in hard prod without budget.
2. PII in attributes.
3. High cardinality attributes.
4. No W3C propagation.
5. Span per for loop a thousand times.
6. Mixing outdated OpenTracing API.
7. Trace without rid policy.
8. Invented kit-only tracing API.
9. Trace id as Prometheus label.
10. Span in core service instead of MW.
11. Expecting a trace for every request with low sample.
12. Forgotten Shutdown/flush.
13. Zipkin-only dogma.
14. Mixing rid and trace id as the same thing.

## Idiomatic Go

- Context propagation through all `next(ctx, …)`.
- Thin EndpointMiddleware closure (function literal) around `endpoint.Endpoint`.
- OTel API in MW / main wiring; not in domain core.
- `defer span.End()` always.
- Read `go.opentelemetry.io/otel` docs for the pin; not a blog for another major.

## Practical scenario

Order → Inventory → Fraud. p99 Order rises. RED says Inventory is slow. Trace shows 180ms in the Java fraud span, not in Go Inventory SQL. Targeted optimization; without the trace the team would have “optimized” the wrong repo for weeks.
