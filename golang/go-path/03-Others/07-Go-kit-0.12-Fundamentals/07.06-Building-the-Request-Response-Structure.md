# 07.06 Building the Request Response Structure

> **Go Path - Zero to Gopher** / **03 Others → Go kit 0.12 Fundamentals** / Lesson 07.06

## Lesson goals

After this lesson you should be able to:

- define **request/response** structs per use-case (`uppercaseRequest` / `uppercaseResponse`, `countRequest` / `countResponse`)
- separate those DTOs from `Service` parameters (`string` / `int`) from 07.05
- put **JSON tags** only at the transport edge (DTO), never in the service layer
- understand the **Err-in-response** pattern (string field in response) versus the **ErrorEncoder** path
- know why `endpoint.Endpoint` sees `interface{}` and how type assert returns the type
- locate the DTO relative to layers: Transport decode ↔ **DTO** ↔ Endpoint ↔ Service

## Prerequisite

- 07.05 — `Service`, `ErrEmpty`, table tests, no JSON
- 07.04 — `endpoint.Endpoint` signature with `interface{}`
- Go: struct tags, `encoding/json`, type assert, `omitempty`

## Problem this lesson solves

`endpoint.Endpoint` has the signature:

```go
type Endpoint func(ctx context.Context, request interface{}) (response interface{}, err error)
```

Without a concrete request struct:

- you lose the type (everything is “something”)
- there is nowhere to attach `json:"s"` for HTTP decode
- the endpoint factory sinks into ad-hoc map[string]any
- gRPC and HTTP do not share a clear field map

A DTO at the **edge** solves the wire shape. Service still receives a clean `string`.

## Mental model

```
JSON body {"s":"go"}
        │
        ▼
uppercaseRequest{S: "go"}     ← DTO (this lesson)
        │
        ▼
svc.Uppercase(ctx, req.S)     ← Service (07.05)
        │
        ▼
uppercaseResponse{V:"GO"}     ← DTO
        │
        ▼
JSON {"v":"GO"}
```

Err-in-response variant (classic kit HTTP example):

```
svc returns ErrEmpty
    → endpoint returns uppercaseResponse{Err: "empty string"}, nil
    → encode writes JSON with "err" field (often HTTP 200 + err in body)
```

ErrorEncoder variant (alternative):

```
endpoint returns nil, err
    → httptransport ErrorEncoder maps to HTTP status
```

Both are legitimate; **the team must choose one style** and document it. This lesson teaches both so 07.07/07.08 have the language.

## Mechanism

### Step 0 — where types live

Common organizations:

| Layout | When |
|--------|------|
| `internal/endpoint/reqresp.go` | DTO + factory together |
| `internal/endpoint/uppercase.go` | per method |
| `internal/transport/http/request.go` | if you want DTO strictly with HTTP |

For the course: keep DTO next to the endpoint factory (`internal/endpoint`). The service package **does not** see these types.

Do not export DTO if it is not needed outside the package — lowercase `uppercaseRequest` is fine inside the `endpoint` package.

**Predict-then-answer A**

Question: should `Service.Uppercase` take `uppercaseRequest`?

- Predict: “yes, less mapping.”
- Answer: no. Service stays `Uppercase(ctx, s string)`. Mapping `req.S → s` is done by the endpoint. Otherwise service depends on a wire DTO.

### Step 1 — uppercase pair

```go
package endpoint

// uppercaseRequest is the input for the Uppercase use-case at the transport edge.
type uppercaseRequest struct {
	S string `json:"s"`
}

// uppercaseResponse is the output. Err is a string because of the JSON encode pattern.
type uppercaseResponse struct {
	V   string `json:"v"`
	Err string `json:"err,omitempty"`
}
```

Why short `S` / `V` fields? Pedagogical stringsvc style: JSON keys `s` / `v` are short. In production choose readable names (`Text`, `Result`) with stable JSON keys.

`Err string` — not `error` interface: `error` does not marshal usefully to JSON without a custom type. Kit examples often put `err.Error()` into a string field.

### Step 2 — count pair

```go
type countRequest struct {
	S string `json:"s"`
}

type countResponse struct {
	V int `json:"v"`
}
```

Count in the classic example **has no** `Err` field — the service does not return an error. Do not add an empty `Err` “for symmetry”; symmetry lies about the domain.

**Predict-then-answer B**

Question: should `countResponse` have `Err string` like uppercase?

- Predict: “yes, same shape everywhere.”
- Answer: not necessarily. Fields follow real outcomes. A uniform envelope (`{data, error}`) is another API decision — document it if you introduce it.

### Step 3 — JSON tags: rules

1. Tags live **only** on DTO, not on service/domain types.
2. `omitempty` on `Err`: success does not send `"err":""`.
3. Rarely put `omitempty` on `V` for uppercase — empty result and success are different signals; here `V` after success is not empty because of the `ErrEmpty` rule, but the habit of `omitempty` on business fields hides `0` / `""` bugs.
4. Explicit names (`json:"s"`) stabilize the API; do not rely on default lowercase fields without agreement.

Marshal round-trip test (golden shape):

```go
func TestUppercaseRequestJSON(t *testing.T) {
	in := uppercaseRequest{S: "go"}
	b, err := json.Marshal(in)
	if err != nil {
		t.Fatal(err)
	}
	if string(b) != `{"s":"go"}` {
		t.Fatalf("got %s", b)
	}
	var out uppercaseRequest
	if err := json.Unmarshal([]byte(`{"s":"hi"}`), &out); err != nil {
		t.Fatal(err)
	}
	if out.S != "hi" {
		t.Fatalf("got %#v", out)
	}
}
```

### Step 4 — Err-in-response vs ErrorEncoder

**Style A — Err in response (kit stringsvc HTTP demo often):**

```go
// in endpoint factory (07.07) — preview
v, err := svc.Uppercase(ctx, req.S)
if err != nil {
	return uppercaseResponse{Err: err.Error()}, nil // <-- error return is nil
}
return uppercaseResponse{V: v}, nil
```

Consequences:

- `encodeResponse` always sees a response object
- HTTP status often 200; client reads the `err` field
- simple encode; weaker REST semantics

**Style B — error return + ErrorEncoder:**

```go
v, err := svc.Uppercase(ctx, req.S)
if err != nil {
	return nil, err // transport ErrorEncoder → 400/500
}
return uppercaseResponse{V: v}, nil
```

Consequences:

- cleaner HTTP status
- response DTO can omit the `Err` field
- needs `httptransport.ServerErrorEncoder` (07.08)

**Predict-then-answer C**

Question: if the endpoint returns `uppercaseResponse{Err: "..."}, nil`, does ErrorEncoder run?

- Predict: “yes, it sees the Err field.”
- Answer: not automatically. ErrorEncoder reacts to the **error return** from Endpoint, not to a field in the struct. Mixing styles without agreement = monitoring bugs (everything looks 200).

### Step 5 — interface{} and type assert

Endpoint receives `request interface{}`. After decode that is (usually) a value of type `uppercaseRequest` (or a pointer — be consistent).

```go
req, ok := request.(uppercaseRequest)
if !ok {
	return nil, fmt.Errorf("invalid request type %T", request)
}
```

Panic form `request.(uppercaseRequest)` is shorter in examples, dangerous in production. 07.07 forces the `ok` form.

Pointer vs value:

| Decode returns | Assert |
|----------------|--------|
| `uppercaseRequest{}` (value) | `request.(uppercaseRequest)` |
| `&uppercaseRequest{}` | `request.(*uppercaseRequest)` |

Mixing → assert fail. One style per service.

### Step 6 — mapping to service (mental code)

```go
// not the factory yet — only field map
func mapUppercase(req uppercaseRequest) (in string) {
	return req.S
}

func mapUppercaseResult(v string, err error) uppercaseResponse {
	if err != nil {
		return uppercaseResponse{Err: err.Error()}
	}
	return uppercaseResponse{V: v}
}
```

These helper functions are optional; they often live inline in the factory. Point: the **map is explicit**.

### Step 7 — gRPC link (without a fake API)

gRPC uses proto messages, not JSON tags. Typical bridge:

```go
// sketch — names depend on your .proto
func uppercaseRequestFromProto(pb *pb.UppercaseRequest) uppercaseRequest {
	return uppercaseRequest{S: pb.GetS()}
}

func uppercaseResponseToProto(res uppercaseResponse) *pb.UppercaseReply {
	return &pb.UppercaseReply{V: res.V, Err: res.Err}
}
```

Or: gRPC transport maps **directly** to service parameters and bypasses the HTTP DTO — also valid. What matters is that service does not import `pb` types if you want a clean core (many teams still keep the mapper in the transport/grpc package).

Kit package: `github.com/go-kit/kit/transport/grpc` — decode/encode analog to HTTP. Details in 07.08.

### Step 8 — validation on DTO vs service

| Layer | What it checks |
|-------|----------------|
| Decode | JSON syntax, MaxBytes, maybe required field present |
| DTO helper | optional `validate` tag libraries (outside kit core) |
| Service | domain rules (`ErrEmpty`) |

`go-playground/validator` is not part of go-kit. If you add it, keep it at the edge or a thin adapter — do not pull it into `stringService` without need.

### Step 9 — versions and field evolution

As in the 04.05 DTO spirit:

- adding an optional field with `omitempty` is usually compatible
- renaming a JSON key breaks clients — prefer a new field + deprecate
- do not reuse the same mega `Request` struct for five use-cases

```go
// BAD
type megaRequest struct {
	S     string `json:"s"`
	Limit int    `json:"limit"`
	Flag  bool   `json:"flag"`
	// ... all methods share this
}
```

### Step 10 — security: what does not go in the response struct

- tokens, password hash, internal DB id map without need
- raw `error` with stack/SQL details in public JSON
- `Err: err.Error()` can leak internal messages — for a public API map to a stable code/message

Pedagogical `ErrEmpty` message is safe. Production: `Err: "invalid_input"` + log the internal detail in MW.

### Step 11 — complete mini file for the course

```go
package endpoint

type uppercaseRequest struct {
	S string `json:"s"`
}

type uppercaseResponse struct {
	V   string `json:"v"`
	Err string `json:"err,omitempty"`
}

type countRequest struct {
	S string `json:"s"`
}

type countResponse struct {
	V int `json:"v"`
}
```

That is enough for 07.07. Do not add fake kit generic types like `Endpoint[uppercaseRequest, uppercaseResponse]` — they **do not exist** in kit v0.12 as official API.

### Step 12 — position in the chain (repetition)

```
Transport (07.08)  decode → uppercaseRequest
Endpoint  (07.07)  assert + svc call → uppercaseResponse
Service   (07.05)  Uppercase(ctx, string)
Transport (07.08)  encode ← uppercaseResponse
```

This lesson defines the **shape of the boxes** that encode/decode and endpoint exchange.

### Step 14 — test strategy for DTO only

Without an HTTP server:

1. `json.Marshal` / `Unmarshal` golden
2. Check `omitempty` (success without `err` key)
3. Negative JSON (`{"s":1}`) — Unmarshal error (prep for decode test in 07.08)

```go
func TestUppercaseResponseOmitErr(t *testing.T) {
	b, _ := json.Marshal(uppercaseResponse{V: "GO"})
	if strings.Contains(string(b), "err") {
		t.Fatalf("unexpected err key: %s", b)
	}
}
```

### Step 15 — pointer DTO (when the team insists)

Some teams decode into a pointer:

```go
func decodeUppercaseRequest(_ context.Context, r *http.Request) (interface{}, error) {
	var req uppercaseRequest
	if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
		return nil, err
	}
	return &req, nil // pointer
}
```

Then the endpoint **must**:

```go
req, ok := request.(*uppercaseRequest)
```

Mixing value decode + pointer assert = fail. If you choose pointer for a `nil` signal “no body”, document that; for StringService value is simpler.

**Predict-then-answer D**

Question: does `json.Decoder.Decode` require a pointer argument?

- Predict: “no, value works.”
- Answer: `Decode` requires a pointer (`&req`) to fill fields. That is **not** the same as “I return a pointer as `interface{}`”.

### Step 16 — envelope pattern (alternative to stringsvc)

Some public APIs use:

```go
type apiResponse struct {
	Data  json.RawMessage `json:"data,omitempty"`
	Error *apiError       `json:"error,omitempty"`
}
```

That is **not** required for kit. Stringsvc pedagogy uses flat `v` / `err` fields. If you introduce an envelope, the endpoint can still return a domain DTO and encode packs the envelope — or the endpoint returns the envelope. Do not mix both in the same service.

### Step 17 — what DTO is not

| Is not | Why |
|--------|-----|
| GORM model | persistence ≠ wire |
| `pb.UppercaseRequest` without a map | HTTP client does not speak protobuf bytes on a REST route (unless a special agreement) |
| `map[string]any` | loses the contract |
| Service parameter list “as a struct with json tags” in the service package | breaks the 07.05 boundary |

### Step 18 — walkthrough before 07.07

1. Open `internal/endpoint` (or agreed package).
2. Write four types: uppercase/count request/response.
3. Golden JSON tests.
4. Write in a package comment: Err-in-response **or** ErrorEncoder.
5. **Do not** write `makeUppercaseEndpoint` yet until DTOs are green in tests — a factory without a stable DTO only moves the bug.

### Step 19 — predict exercise: empty Err vs omitempty

JSON success with `Err: ""` and tag `omitempty`:

```json
{"v":"GO"}
```

JSON error:

```json
{"err":"empty string"}
```

If you remove `omitempty` and send success:

```json
{"v":"GO","err":""}
```

Clients that check `if (body.err)` in JS may treat `""` as falsy — but clients that check `hasOwnProperty('err')` behave differently. So `omitempty` is not cosmetics.

### Step 20 — link back to 07.05 and forward to 07.07

```
07.05  Service.Uppercase(ctx, s string) (string, error)
         ▲
         │ maps req.S / res.V|Err
07.06  uppercaseRequest / uppercaseResponse   ← you are here
         │
         ▼
07.07  makeUppercaseEndpoint closes over svc and asserts request
```

Without 07.06, 07.07 asserts fog. Without 07.05, DTO has nowhere to send the work.

## Rules and syntax

1. **One pair of structs per** use-case method.
2. **JSON tags here**, not in `internal/service`.
3. **Err as a string field** if you follow the kit HTTP Err-in-response pattern; otherwise document ErrorEncoder style.
4. **Do not leak** DB model / proto message as HTTP DTO without a map.
5. **Names** clear: `uppercaseRequest`, not `Req1`.
6. **Wire validation** may precede service; **domain** stays in service.
7. **gRPC** has proto — mapper to DTO or directly to service.
8. **Consistent** value vs pointer through decode → assert.
9. **No** generic kit `Endpoint[T]` — use `interface{}` + assert.
10. **omitempty** on error yes; on business `V` carefully.
11. **Do not put** secret fields in the response.
12. **Stable JSON keys** = API contract.

## Examples

### Example 1 — countRequest / countResponse

```go
type countRequest struct {
	S string `json:"s"`
}
type countResponse struct {
	V int `json:"v"`
}
```

### What happens here

Same pattern as uppercase, different return value (`int`). No `Err` field because service `Count` does not return `error`.

### Example 2 — Err field after service error

```go
res := uppercaseResponse{Err: service.ErrEmpty.Error()}
b, _ := json.Marshal(res)
// {"err":"empty string"}
```

### What happens here

Encode (07.08) can just `Encode(res)`. Status mapping — if you want it — is not automatic from this field; either custom encode reads the field, or you switch to ErrorEncoder style.

### Example 3 — separate from domain

```go
// service
Uppercase(ctx context.Context, s string) (string, error)

// endpoint DTO
type uppercaseRequest struct{ S string `json:"s"` }
```

### What happens here

04.05 DTO spirit: wire shape ≠ domain shape. Even when they are almost the same (`S` ≈ `s`), the boundary prevents later leakage.

### Example 4 — type assert in endpoint (preview)

```go
req := request.(uppercaseRequest) // literature example; production: ok form
```

### What happens here

The factory (07.07) localizes the assert. Transport must pass the exact dynamic type.

### Example 5 — bad mega-request

```go
type allRequest struct {
	S string `json:"s"`
	N int    `json:"n"`
}
// used for both Uppercase and some other use-case
```

### What happens here

Client sends irrelevant fields; validation blurs; OpenAPI suffers. One pair per use-case.

## Decision analysis

| Option | Advantage | Drawback |
|--------|-----------|----------|
| Err string in response | Simple encode; kit demo | Weaker HTTP status; easy to ignore `err` on client |
| only `return nil, err` + ErrorEncoder | REST status; cleaner DTO | More transport code |
| DTO in endpoint package | Close to factory | HTTP-only teams want DTO in transport |
| DTO in transport/http | Clear wire zone | Duplicate if gRPC shares the same shape |
| exported DTO | Sharing test helpers | Larger public API |
| unexported DTO | Encapsulation | Harder tests in another package |
| uniform envelope | Consistent API | Loses stringsvc simplicity |

Course default: **unexported DTO in endpoint package + Err-in-response for uppercase** (like the classic example), with awareness of the ErrorEncoder alternative.

## Trade-offs

- **err string in JSON** is not ideal for every public API; pedagogically it is clear.
- **Short fields `S`/`V`** save the example, cost readability in a large API.
- **Double mapping** (proto ↔ DTO ↔ service) is boilerplate; the price for polyglot.
- **omitempty** hides zeros — suitable for errors, risky for counters if added wrongly.

## Common mistakes

1. Service parameters as JSON-tagged structs in `internal/service`.
2. Shared mega request for all methods.
3. Wrong type assert (value vs pointer) → panic.
4. Mixing Err-in-response and ErrorEncoder without documentation.
5. Proto message as HTTP DTO without a map.
6. `omitempty` on `V` so the client does not see empty string when needed.
7. Exporting DTO without need.
8. Secret / internal detail in response struct.
9. `error` type as a JSON field without custom marshal.
10. Generic “kit Endpoint[T]” in handbook code as if official.
11. Validation only in HTTP decode — gRPC bypasses.
12. Changing a JSON key without version / changelog.

## Idiomatic Go

- Small struct per use-case.
- Explicit `json` tags.
- Local (unexported) types in the endpoint package.
- `ok` form of type assert.
- Golden test for JSON shape.
- Document error style in one package comment.

## Practical scenario

A team keeps `internal/endpoint` with DTO + factory; `internal/transport/http` only decode/encode and `NewServer`. Domain/service does not see `json` tags. When marketing asks to rename JSON field `s` → `text`, the PR touches DTO + OpenAPI + golden test — **not** the `Service` interface. Reviewer rejects a PR that “works faster” by having service take `uppercaseRequest`.

## Going deeper: request response structures

Fourteen real insights — without filler loops.

### 1. insight — read official examples

Kit stringsvc / examples are the reference shape for field names and the Err pattern. This handbook translates the pedagogy; on disagreement check the upstream example with pin `v0.12.0`.

**Check:** does your DTO look like the example or a random REST tutorial?

### 2. insight — do not copy err string blindly into a public API

An internal tool can use `{"err":"empty string"}`. A public banking API often wants `{ "error": { "code": "EMPTY_INPUT" } }` + HTTP 400. Choose deliberately.

**Check:** who consumes the JSON — internal FE or a third party?

### 3. insight — field versioning

Add `text` beside `s`, document deprecate, remove `s` only in a major version. Same rule as 04.05.

**Check:** is there a changelog / OpenAPI diff in the PR?

### 4. insight — validation tags optional

`validate:"required"` is not kit. If the team already uses playground validator, keep it with the DTO. Do not push it into the service signature.

**Check:** must a service test register a validator?

### 5. insight — document the field map

One table in README: JSON `s` → Go `S` → service arg `s`. Saves onboarding.

**Check:** can a new teammate fill the table without reading all the code?

### 6. insight — golden marshal/unmarshal

A fixed expected JSON string in the test catches accidental tag renames.

**Check:** does CI fail when you change `json:"s"` to `json:"S"`?

### 7. insight — avoid `any` in the exported API

`map[string]any` response kills the contract. DTO struct exists to prevent that.

**Check:** do public package types use `any` without docs?

### 8. insight — Count response only int

Do not force an `Err` field onto Count. Empty DTO noise = false error signal.

**Check:** do all response types look copy-paste identical?

### 9. insight — Unicode / locale note

JSON string is UTF-8. Uppercase domain still in service. DTO does not “fix” locale — it only carries text.

**Check:** do you test non-ASCII in a JSON golden test?

### 10. insight — security response

Never `Password`, `Secret`, raw SQL err in response struct tags. Review grep on `json:"`.

**Check:** does a secret type have a json tag “temporarily for debug”?

### 11. insight — gRPC mapper names

`RequestFromProto` / `ToProto` convention makes transport/grpc readable. Keep them next to decode.

**Check:** does the mapper live in the service package? (it should not)

### 12. insight — file names

`reqresp.go` or `uppercase.go` + `count.go`. Consistency > perfection. Do not use `utils.go` for DTO.

**Check:** does `git grep uppercaseRequest` find the expected file?

### 13. insight — code review: does a DB model leak?

If the response has `gorm` tags — leakage. DTO must be clean wire.

**Check:** `json` + `db` + `gorm` on the same struct?

### 14. insight — Err field vs status in 07.08

This lesson defines fields; 07.08 chooses how status is produced. Write the decision before NewServer.

**Check:** is there a one-sentence decision in ADR / package comment?

Extra reminder before merging a DTO PR:

- [ ] Golden test for success and error
- [ ] No `json` tags in `internal/service`
- [ ] Count without a fake `Err` field (unless domain says otherwise)
- [ ] Value/pointer style written in a package comment
- [ ] Error style (Err-in-response vs ErrorEncoder) written next to `MakeEndpoints` or in transport README

### Quick recap

- DTO = wire shape; Service = domain shape.
- JSON tags only at the edge.
- Err-in-response ≠ ErrorEncoder.
- One pair of structs per use-case.
- Assert discipline (value/pointer).
- `omitempty` on `Err` changes the client contract — test golden JSON.
- Pointer vs value must be the same from decode to assert.
- Next: factory closes over service and glues DTO.
