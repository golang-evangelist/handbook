# 07.04 Services Components and Principles

> **Go Path - Zero to Gopher** / **03 Others → Go kit 0.12 Fundamentals** / Lesson 07.04

## Lesson goals

After this lesson you should:

- name the four components: **Service**, **Endpoint**, **Transport**, **Middleware**
- explain the difference **ServiceMiddleware** vs **EndpointMiddleware**
- apply the dependency rule: transport → endpoint → service (one-way)
- memorize the canonical kit v0.12 signatures (`endpoint.Endpoint`, `endpoint.Middleware`, `endpoint.Chain`, `httptransport.NewServer`)
- connect the layout from 07.03 with the hexagonal / ports-and-adapters idea
- recognize circular import and “invented Endpoint signature” as anti-patterns

## Prerequisite

- 07.03 — module, pin `kit@v0.12.0`, folders `internal/service|endpoint|transport`, log note
- 07.02 — challenges that motivate layers
- Go: `interface`, function types, `context.Context`, type assert on `interface{}`

## Problem this lesson solves

Without *names* for components, teams mix files: business in decode, HTTP status in service, middleware “somehow in main”. Consequences:

- circular imports (`service` ↔ `transport`)
- inability to share the same use case over HTTP and gRPC
- reviews without vocabulary (“put it somewhere in utils”)
- fake generic `Endpoint[T]` as if it were kit API

This lesson gives a shared vocabulary and dependency arrows before 07.05 writes the real `Uppercase`.

## Mental model

```
        ┌─────────────────────────────────────┐
        │         Middleware (decorators)     │
        │  ServiceMW: Service → Service       │
        │  EndpointMW: Endpoint → Endpoint    │
        └─────────────────────────────────────┘
                         │
Transport ──► Endpoint ──► Service
 (wire)      (use-case)    (work)
```

- **Service** — business `interface` + implementation; knows nothing about HTTP/JSON.
- **Endpoint** — `endpoint.Endpoint`: invocation of one use case via `interface{}` request/response.
- **Transport** — encode/decode + `httptransport.NewServer` (or gRPC analog).
- **Middleware** — composition of cross-cutting concerns *without* changing the core method.

Hexagonal parallel: Service ≈ application core; Transport ≈ adapter; Endpoint ≈ port/use-case adapter between them.

## Mechanism

### Step 0 — canonical signatures (learn by heart)

```go
import (
    "context"

    "github.com/go-kit/kit/endpoint"
)

// Kit v0.12 — not Endpoint[T]
type Endpoint func(ctx context.Context, request interface{}) (response interface{}, err error)

type Middleware func(Endpoint) Endpoint
```

Service (your type, not a kit type):

```go
type Service interface {
    Uppercase(ctx context.Context, s string) (string, error)
    // Count(ctx context.Context, s string) (int, error) // later
}

type ServiceMiddleware func(Service) Service
```

**Predict-then-answer A**

Question: does kit export `type Service interface`?

- Predict: “yes, in kit/service”.
- Answer: no. You write the Service interface *yourself* for your domain. Kit standardizes Endpoint/Middleware/Transport, not your business `interface`.

### Step 1 — Service: what is allowed and what is not

Allowed:

- business rules, domain validation, orchestration of repo/client calls
- returning typed `error` values
- passing `context` downward

Not allowed:

- `net/http`, JSON encode, gRPC `status.Error` as the *only* error shape
- reading HTTP headers directly (identity comes via `context` if needed)
- import `internal/transport/...`

Example skeleton:

```go
package service

import (
    "context"
    "errors"
    "strings"
)

var ErrEmpty = errors.New("empty string")

type Service interface {
    Uppercase(ctx context.Context, s string) (string, error)
}

type stringService struct{}

func New() Service { return stringService{} }

func (stringService) Uppercase(ctx context.Context, s string) (string, error) {
    if s == "" {
        return "", ErrEmpty
    }
    _ = ctx
    return strings.ToUpper(s), nil
}
```

(Real logic is deepened in 07.05; here the *shape* matters.)

### Step 2 — Endpoint: glue between service ↔ transport

```go
package endpoint

import (
    "context"

    "github.com/go-kit/kit/endpoint"
    "example.com/stringsvc/internal/service"
)

type uppercaseRequest struct {
    S string
}

type uppercaseResponse struct {
    V   string `json:"v,omitempty"`
    Err string `json:"err,omitempty"`
}

func MakeUppercaseEndpoint(svc service.Service) endpoint.Endpoint {
    return func(ctx context.Context, request interface{}) (interface{}, error) {
        req := request.(uppercaseRequest) // in production: safe assert + error
        v, err := svc.Uppercase(ctx, req.S)
        if err != nil {
            return uppercaseResponse{Err: err.Error()}, nil // style A: error in body
            // or: return nil, err // style B: error upward
        }
        return uppercaseResponse{V: v}, nil
    }
}
```

Two error styles (pick *one* on the team):

| Style | Endpoint returns | Transport |
|------|----------------|-----------|
| A | response with Err field, `error == nil` | reads Err, picks status |
| B | `nil, err` | maps err to status |

**Predict-then-answer B**

Question: why `request interface{}` instead of `uppercaseRequest` in the Endpoint signature?

- Predict: “bad kit design”.
- Answer: one function type enables `Middleware` and `Chain` without generics (v0.12 era). Type assert is the cost at the boundary. Do not invent `Endpoint[T]` as official kit API — you can wrap locally, but kit transport expects `endpoint.Endpoint`.

### Step 3 — EndpointMiddleware and `endpoint.Chain`

```go
func LoggingMiddleware(logger log.Logger) endpoint.Middleware {
    return func(next endpoint.Endpoint) endpoint.Endpoint {
        return func(ctx context.Context, request interface{}) (interface{}, error) {
            // before
            resp, err := next(ctx, request)
            // after: log latency / error
            return resp, err
        }
    }
}

ep := endpoint.Chain(
    LoggingMiddleware(logger),
    InstrumentingMiddleware(hist),
)(MakeUppercaseEndpoint(svc))
```

Order: `Chain(A, B)(ep)` means A outside, B inside — like an onion. Check docs/kit behavior and *test* order (auth before business logic, etc.).

**Predict-then-answer C**

Question: where to measure latency for a use case that goes over both HTTP and gRPC?

- Predict: “in both transport middlewares”.
- Answer: in EndpointMiddleware (once), so the label `endpoint=uppercase` is the same.

### Step 4 — ServiceMiddleware

```go
func LoggingServiceMiddleware(logger log.Logger) ServiceMiddleware {
    return func(next Service) Service {
        return &loggingService{logger, next}
    }
}

type loggingService struct {
    logger log.Logger
    next   Service
}

func (s *loggingService) Uppercase(ctx context.Context, str string) (string, error) {
    // log domain parameters as needed (watch PII)
    return s.next.Uppercase(ctx, str)
}
```

Wiring:

```go
var svc service.Service = service.New()
svc = service.LoggingServiceMiddleware(logger)(svc)
```

When ServiceMW, when EndpointMW?

| Concern | Typical layer |
|-------|----------------|
| Use-case latency, transport-agnostic | EndpointMW |
| Authz “may this principal run this use case” | often EndpointMW (or ServiceMW) |
| Cache by domain key / idempotency in domain | ServiceMW |
| Instrumentation near business methods | ServiceMW |
| JSON decode fail | Transport (not MW on endpoint) |

### Step 5 — Transport: encode/decode + NewServer

```go
import httptransport "github.com/go-kit/kit/transport/http"

func NewHTTPHandler(ep endpoint.Endpoint) http.Handler {
    return httptransport.NewServer(
        ep,
        decodeUppercaseRequest,
        encodeResponse,
    )
}

func decodeUppercaseRequest(_ context.Context, r *http.Request) (interface{}, error) {
    var body struct {
        S string `json:"s"`
    }
    if err := json.NewDecoder(r.Body).Decode(&body); err != nil {
        return nil, err
    }
    return uppercaseRequest{S: body.S}, nil
}

func encodeResponse(_ context.Context, w http.ResponseWriter, response interface{}) error {
    w.Header().Set("Content-Type", "application/json")
    return json.NewEncoder(w).Encode(response)
}
```

Transport *only*:

1. decode wire → request value (`interface{}` the endpoint expects)
2. call endpoint (NewServer does this)
3. encode response → wire
4. map errors to status (NewServer options / ErrorEncoder)

**Predict-then-answer D**

Question: may `decodeUppercaseRequest` call `strings.ToUpper`?

- Predict: “yes, fewer files”.
- Answer: no — that is business work. Decode may parse and optionally check *wire shape* (JSON exists). Business “empty string” stays in service.

### Step 6 — dependency rule (arrow)

Allowed:

```
cmd/stringsvc          → service, endpoint, transport, log, kit
transport/http         → endpoint types (request struct), kit/transport/http
endpoint               → service, kit/endpoint
service                → (std, domain deps)  ✗ not transport
```

Forbidden:

```
service → transport/http
service → net/http (for status)
endpoint → net/http (for StatusOK)
```

If `go list` / the compiler reports import cycle, the arrow is almost always broken.

**Predict-then-answer E**

Question: where may a shared request `struct` live?

- Predict: “in transport, because JSON”.
- Answer: often in the `endpoint` package (transport decode returns that type). Transport must not depend on service internals; service must not depend on JSON tags if you want a clean domain — pragmatically teams keep DTO in endpoint/transport and map into service string/value.

### Step 7 — wiring in `main` (explicit)

```go
func main() {
    logger := log.NewLogfmtLogger(os.Stderr)
    logger = log.With(logger, "svc", "stringsvc")

    var svc service.Service
    svc = service.New()
    svc = service.LoggingServiceMiddleware(logger)(svc)

    upper := endpoint.Chain(
        LoggingMiddleware(logger),
    )(ep.MakeUppercaseEndpoint(svc))

    http.Handle("/uppercase", httptransport.NewServer(
        upper,
        decodeUppercaseRequest,
        encodeResponse,
    ))

    logger.Log("msg", "listening", "addr", ":8080")
    log.Fatal(http.ListenAndServe(":8080", nil))
}
```

Explicitness > magic DI container at this course level. You see MW order and where NewServer sits.

### Step 8 — walkthrough of one request through components

1. Client sends `POST /uppercase` `{"s":"go"}`.
2. `httptransport.NewServer` calls `decodeUppercaseRequest` → `uppercaseRequest{S:"go"}`.
3. Logging EndpointMW enters (start timer).
4. `MakeUppercaseEndpoint` cast + `svc.Uppercase`.
5. Logging ServiceMW (optional) + `stringService.Uppercase` → `"GO"`.
6. Endpoint returns `uppercaseResponse{V:"GO"}`.
7. EndpointMW logs `took`.
8. `encodeResponse` writes JSON.

**Predict-then-answer F**

Question: if decode fails, is Service called?

- Predict: “yes, with zero value”.
- Answer: no. NewServer returns decode error before the endpoint. That is why transport tests cover bad JSON separately from service tests.

### Step 9 — two transports, same endpoint

```go
upper := MakeUppercaseEndpoint(svc)
upper = endpoint.Chain(LoggingMiddleware(logger))(upper)

httpHandler := httptransport.NewServer(upper, decodeHTTP, encodeHTTP)
grpcHandler := /* kit grpc server around same upper */
```

The challenge from 07.02 (“gRPC comes later”) gets a mechanism here: new decode/encode, same `upper`.

### Step 10 — anti-pattern catalog (recognize quickly)

1. **Service imports http** — breaks the arrow.
2. **Business in decode** — duplication with gRPC.
3. **Mixing ServiceMW and EndpointMW** without agreement — double logs, double latency.
4. **Global service singleton** without `interface` — cannot inject fake in tests.
5. **Transport in domain test** — slow, brittle tests.
6. **Implicit wire** (init() side effects) — MW order unreadable.
7. **Invented signature** `type Endpoint[T any] func...` as “kit standard” — not v0.12 API.
8. **Renaming Endpoint to Handler** — confusion with `http.Handler`.

### Step 11 — connecting to hexagonal

| Hexagonal | Kit component |
|-----------|----------------|
| Application core | Service |
| Inbound port / use-case | Endpoint (+ your factory) |
| Adapter | Transport (HTTP/gRPC) |
| Decorating use-case | Middleware |

Principle > framework dogma: you can keep the same arrow without kit import; kit gives ready types and `NewServer`/`Chain`.

### Step 12 — more methods = more endpoint factories

```go
type Endpoints struct {
    Uppercase endpoint.Endpoint
    Count     endpoint.Endpoint
}

func MakeEndpoints(svc service.Service) Endpoints {
    return Endpoints{
        Uppercase: MakeUppercaseEndpoint(svc),
        Count:     MakeCountEndpoint(svc),
    }
}
```

One service, N endpoints. Each use case gets a name for metrics.

**Predict-then-answer G**

Question: may one `endpoint.Endpoint` do both Uppercase and Count via an “op” field in the request?

- Predict: “yes, fewer types”.
- Answer: avoid it. You lose a clear name, complicate MW and tests. Kit style: one use case — one endpoint.

### Step 13 — context through all layers

```go
func (s stringService) Uppercase(ctx context.Context, str string) (string, error) {
    select {
    case <-ctx.Done():
        return "", ctx.Err()
    default:
    }
    // ...
}
```

Endpoint signature *forces* `ctx` first. Transport should pass `r.Context()`. MW must not swallow cancel without reason.

### Step 14 — predict-then-answer: review checklist

When reviewing a PR “adding /count”:

1. New service method? Test?
2. New `MakeCountEndpoint`?
3. Same Chain MW as upper?
4. New decode/encode?
5. Service still without `net/http`?
6. Metric label = `count`?

If the PR only adds `HandleFunc` in `main` bypassing endpoint, send it back to this lesson.

## Rules and syntax

1. **Service does not know HTTP.**
2. **Endpoint type is from `kit/endpoint`** — `interface{}` request/response.
3. **Transport only encode/decode + kit server.**
4. **ServiceMW** for concerns near domain methods (cache, domain authz, fine log).
5. **EndpointMW** for transport-agnostic (latency, use-case authz, request/response log).
6. **Wiring explicit** in `cmd`.
7. **No circular imports.**
8. **One use case — one endpoint** (as a rule).
9. **`context` first, `error` last** on service methods.
10. **Do not rename Endpoint to Handler.**
11. **Do not claim `Endpoint[T]` is kit API** on v0.12.
12. **Agree error style** (in response vs `error` upward) and stick to it.

## Examples

### Example 1 — dependencies one-way

```
transport/http → endpoint → service
cmd → all
```

### What happens here

One-way arrow preserves testability and swappable transport. Reverse arrow = cycle or god object.

### Example 2 — two MW on different layers

```go
svc = InstrumentService(svc)           // ServiceMW
ep  = endpoint.Chain(LogEP)(Make(...)) // EndpointMW
```

### What happens here

ServiceMW sees typed method arguments; EndpointMW sees `interface{}` request and works for every transport. They are not interchangeable.

### Example 3 — gRPC + HTTP same endpoint

```go
shared := MakeUppercaseEndpoint(svc)
http.Handle(..., NewServer(shared, ...))
// grpc.Register(..., shared)
```

### What happens here

Principle from 07.02 in code: use case once, wire many times.

### Example 4 — anti: service imports http

```go
func (s stringService) Uppercase(...) (string, error) {
    // http.Error(...) — no ResponseWriter here, so "invent" panic helper
}
```

### What happens here

Broken. Service returns `error`; transport maps.

### Example 5 — Chain order

```go
endpoint.Chain(auth, logging)(ep)
```

### What happens here

Auth as outer layer rejects before logging body details (or the opposite — *test* what you want). Order is part of the contract, not a detail.

### Example 6 — request/response types per method

`uppercaseRequest` / `countRequest` separate.

### What happens here

Clearer cast, clearer JSON, clearer metrics. “One mega request struct” becomes a god DTO.

### Example 7 — NewServer ErrorEncoder

Custom `ErrorEncoder` maps `service.ErrEmpty` → 400.

### What happens here

Mapping lives at the edge (transport), not in service. Endpoint style B (`return nil, err`) cooperates nicely.

## Decision analysis

| Decision | When | Risk |
|--------|-----|-------|
| ServiceMW for cache | Domain key clear | Cache in EndpointMW with `interface{}` hurts |
| EndpointMW for latency | Multiple transports | HTTP-only MW → silence on gRPC |
| Error in response body | Simple JSON API | Easy to forget status |
| Error upward | Clean mapping | Needs ErrorEncoder discipline |
| DTO in endpoint package | Fast stringsvc | Weaker domain purity |
| Strict domain types | Larger system | More mapping |
| Kit Chain | Standard | Learn order |
| Manual wrap without Chain | Full control | Verbose, order mistakes |
| Code gen endpoint | Large API surface | Tooling cost; not required |
| Manual factory | Course / small service | Repeated boilerplate |

## Trade-offs

- **More types / files** vs **clearer boundaries** — upfront cost, long-term readability.
- **`interface{}` at boundary** vs **generics locally** — kit v0.12 stays `interface{}`; generics are your wrapper, not a replacement for NewServer contract.
- **Two MW layers** vs **everything in EndpointMW** — two layers need agreement; one layer gets crowded.
- **Principles without kit** vs **kit types** — principles always apply; kit speeds wiring.
- **Hexagonal purity** vs **pragmatic DTO** — team picks a point on the spectrum and documents it.
- **Explicit main** vs **DI framework** — course chooses explicit; DI is fine when the team already has a standard.

## Common mistakes

1. Circular import service ↔ transport.
2. Business logic in decode/encode.
3. Mixing ServiceMW and EndpointMW without policy (double log).
4. Global service without interface.
5. Domain tests start HTTP server.
6. Implicit wire in `init`.
7. Invented `Endpoint[T]` as kit API.
8. Endpoint imports `net/http` for status.
9. One endpoint for N operations via “op” string.
10. Renaming to Handler → confusion.
11. Authz only on one transport.
12. Swallowing `ctx.Err()` in service without returning error.

## Idiomatic Go

- Small `interface` (segregation by use-case group).
- `ctx` first parameter; `error` last.
- Function composition (`Middleware`) instead of inheritance.
- Explicit dependencies in `struct` / constructor.
- Type assert with check (`ok`) in production, not just `.(T)`.
- Package names: `service`, `endpoint`, `transport` — boring and clear.
- Treat zero value request struct consciously (validate in service).

## Practical scenario

Review checklist on PR: “Draw the dependency arrow”. If the author cannot, PR does not pass. After introducing rules:

- Onboarding: “Endpoint is here, Service there” — 10 min.
- Second transport: a day instead of two weeks.
- Incident: latency by `endpoint` label, not URL regex.

A team that ignored principles ended with `internal/misc` and three logging styles — kit folders exist, but without 07.04 discipline.

## Going deeper: go-kit components and principles

### 1. insight

**`endpoint.Chain` for a stack of MW.** Order is part of semantics (auth, log, metrics). Test it; do not guess. Document in README “outside → inside”.

Practical check: write one unit test proving auth MW rejects before calling a fake service.

### 2. insight

**`transport/http.Server` Options.** ErrorEncoder, Finalizer, exchange context — read API when you need status mapping. Do not memorize all Options day one; know they exist.

Practical check: open docs/source for `NewServer` and list 3 Option names.

### 3. insight

**Do not rename Endpoint to Handler.** `http.Handler` is a different contract (`ServeHTTP`). Confusion in review costs hours.

Practical check: `rg "type Handler"` in endpoint package — expect empty or clearly unrelated name.

### 4. insight

**Request/response types per method.** `uppercaseRequest` ≠ `countRequest`. Shared “god struct” collects unwanted fields and fake validation.

Practical check: number of request types = number of use-case endpoints?

### 5. insight

**Principles > framework dogma.** If kit disappears, the dependency arrow still holds. Kit is an accelerator, not a religion.

Practical check: can you explain the same design to a colleague who dislikes kit?

### 6. insight

**Hexagonal: service = app core.** Transport adapters are swappable. Endpoint is the bridge. When someone says “hexagonal”, show this diagram — not a buzzword.

Practical check: on a drawing mark core red, adapters blue.

### 7. insight

**DTO ≠ domain in stricter teams.** JSON tags on domain entity leak wire details into the core. Map consciously.

Practical check: does `service` package import encoding/json without need?

### 8. insight

**Document endpoint names for metrics.** `uppercase`, `count` — stable names. URL is not a name.

Practical check: does a Prometheus label exist in the runbook?

### 9. insight

**Same idea as 04.06: MW composition.** Same onion idea; kit gives types. Do not learn two worlds — connect them.

Practical check: compare one HTTP middleware and one endpoint middleware — same story?

### 10. insight

**gRPC transport exists in kit — use when needed.** Do not force gRPC “because microservices”. When the requirement arrives, same endpoint saves weeks (07.02).

Practical check: is gRPC on the roadmap? If yes, endpoint discipline *now*.

### 11. insight

**Do not force `interface{}` request without type assert discipline.** Panic on cast = 500 instead of 400. Use the `ok` branch.

Practical check: in `Make...Endpoint` replace `.(T)` with check; return meaningful error.

### 12. insight

**Go generics optionally *outside* kit core types.** You can build your own typed wrapper, but NewServer still requires `endpoint.Endpoint`. Do not mix wrapper with “kit now has Endpoint[T]”.

Practical check: if you have a generic helper, do you still pass `endpoint.Endpoint` at the end?

### 13. insight

**Code gen is not required.** Manual factory is OK for a small service. Gen makes sense when endpoint count explodes and boilerplate becomes risky.

Practical check: how many endpoints do you have? <10 → manual often enough.

### 14. insight

**One service, many methods = many endpoint factories; principles hold without kit import; 07.05 writes real Uppercase; keep this lesson as a poster; without principles kit becomes folder chaos.**

Practical check: print/mental poster: Service / Endpoint / Transport / MW + arrow. If the poster is unclear, return to Steps 0–6 before code in 07.05.

Note: the next lesson assumes `Service` interface and folders exist — do not start 07.05 until you know where the Endpoint type lives.

Extra review before code: (1) does `cmd` only wire, (2) does decode contain business, (3) do metrics use use-case name, (4) is Chain order documented, (5) is error style A/B in ADR. Five “no” answers = return to Mechanism before writing Uppercase.
