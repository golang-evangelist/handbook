# 07.12 Instrumenting the Service

> **Go Path - Zero to Gopher** / **03 Others → Go kit 0.12 Fundamentals** / Lesson 07.12

## Lesson goals

After this lesson you should be able to:

- explain **metrics** conceptually via `github.com/go-kit/kit/metrics` (`Counter`, `Histogram`)
- describe the **instrumenting middleware** shape around `Service` (same decorator spirit as 07.11)

- understand the idea of a **Prometheus adapter** (kit metrics → Prometheus exposition) without pretending you memorized every constructor
- use patterns you can defend: **`Add`** on counter, **`Observe`** on histogram (typical in kit/metrics) — **without inventing** insecure method names

## Prerequisite

- 07.09 — core green (otherwise you measure chaos)

- 07.11 — LoggingMiddleware shape; same wiring style
- 07.04 — ServiceMiddleware vs EndpointMiddleware

## Problem this lesson solves

Logs are events. Metrics are **aggregates**: how many calls, what share of errors, what latency. Without metrics, scaling and SLO (p99) remain guesses from Loki greps. Instrumentation at the **Service** level measures the use case the same for HTTP and future gRPC.

## Mental model

```
                 ┌─ Counter.Add(1)           // rate / error count
request ──► MW ──┼─ Histogram.Observe(sec)  // duration
                 └─ next.Uppercase(...)

RED:
  Rate     ≈ call count / s (counter)
  Errors   ≈ failure count / s (counter or label)
  Duration ≈ latency histogram
```

- **Log** (07.11): one line per call.
- **Metric**: a point in a time series / bucket.
- Labels: **low cardinality** or Prometheus hurts.

## Mechanism

### Step 0 — what kit/metrics gives you (concept)

`kit/metrics` defines **measurement abstractions**, not necessarily one vendor:

- **Counter** — monotonically increases (event count). Typical pattern: `Add(delta float64)`.
- **Histogram** / (sometimes Timer around a histogram) — value distribution (latency). Typical pattern: `Observe(value float64)`.
- Often there is also a **Gauge** (current value) — less central for the RED request path.

Adapters (e.g. Prometheus) implement those interfaces and expose `/metrics`.

**Important for this lesson:** do not stamp from memory the exact names of every constructor (`NewCounterFrom`, factory helpers) if you are not sure — **describe the shape** you defend: you get a `Counter`/`Histogram` (often with `With(labelValues...)` for dimensions), then in MW you call `Add` / `Observe`. When coding, **open** `kit/metrics` and the Prometheus adapter docs/source for exact constructors in v0.12.

**Predict-then-answer A**

Question: does `logger.Log` replace Counter?

- Predict: “almost, we count with grep”.
- Answer: no. Grep is not Rate/SLO. A metric is cheaper for dashboards and alerting.

### Step 1 — RED on the use-case name

| RED | What you measure | Typical metric |
|-----|------------------|----------------|
| Rate | how many Uppercase calls | counter `Add(1)` per call |
| Errors | how many times `err != nil` | error counter or label `success=false` |
| Duration | how long the next call takes | histogram `Observe(seconds)` |

Method name (`uppercase`, `count`) = stable dimension. Do **not** use raw `/users/12345` as a label.

### Step 2 — low-cardinality labels

Allowed (examples):

- `method=uppercase|count`
- `success=true|false` or `result=ok|error`
- `service=stringsvc` (constant)

Forbidden / dangerous:

- user id, email, request_id as label
- full URL with unbounded path segments
- raw error string with infinite variations

request_id belongs in the **log**, not a Prometheus label.

**Predict-then-answer B**

Question: why does request_id not go into a metric label?

- Predict: “useful for join”.
- Answer: it explodes time series (one series per request). Join works via log + time + method, not via a label cardinality bomb.

### Step 3 — InstrumentingMiddleware shape (defensible skeleton)

Same spirit as LoggingMiddleware:

```go
func InstrumentingMiddleware(
    requestCount metrics.Counter,
    requestLatency metrics.Histogram,
) Middleware {
    return func(next Service) Service {
        return &instrumentingMiddleware{
            next:           next,
            requestCount:   requestCount,
            requestLatency: requestLatency,
        }
    }
}

type instrumentingMiddleware struct {
    next           Service
    requestCount   metrics.Counter
    requestLatency metrics.Histogram
}
```

`metrics.Counter` / `metrics.Histogram` here are **types from kit/metrics** (interfaces). When you write code, import the right package and check exact interface names in the version you use.

### Step 4 — method with defer: Add + Observe

Pattern you defend (analogy with 07.11 named returns):

```go
func (mw instrumentingMiddleware) Uppercase(ctx context.Context, s string) (v string, err error) {
    defer func(begin time.Time) {
        // label values: align with how you created the metric (With)
        lvs := []string{"method", "uppercase", "success", fmt.Sprint(err == nil)}
        mw.requestCount.With(lvs...).Add(1)
        mw.requestLatency.With(lvs...).Observe(time.Since(begin).Seconds())
    }(time.Now())
    return mw.next.Uppercase(ctx, s)
}
```

Discipline notes:

- `Observe` in **seconds** often (Prometheus convention); do not mix ms without agreement.
- `With(lvs...)` — exact API (key/value pairs vs values only) **check in docs**; the idea is: low-cardinality dimensions.
- If `With` does not exist on your adapter the same way, stick to the documented shape — **do not invent**.

**Predict-then-answer C**

Question: `Observe(took.Milliseconds())` with buckets tuned for seconds?

- Predict: “whatever, a number is a number”.
- Answer: no. Buckets and the Grafana board assume a unit. Wrong unit = fake p99.

### Step 5 — wiring next to logging MW

```go
svc = service.New()
svc = service.LoggingMiddleware(appLogger)(svc)
svc = service.InstrumentingMiddleware(requestCount, requestLatency)(svc)
```

Document the order. Both MW are Service decorators; the endpoint still just calls `svc`.

### Step 6 — Prometheus adapter (idea, not rote memorization)

Flow:

1. You define metrics via the kit Prometheus adapter package (check the exact import path for v0.12).
2. The adapter implements `Counter`/`Histogram`.
3. You mount `promhttp.Handler()` (or equivalent) on `/metrics` in main — **separate** from business routes.
4. Prometheus scrapes; Grafana draws RED.

Do not mix `/metrics` auth policy with the public API without thinking (internal listener / network policy).

If you are not sure about the name `NewCounterFrom` / `prometheus.NewCounter` wrapper — **open an example in the kit repo / docs** at implementation time. The lesson asks you to understand the adapter's *role*, not recite the signature.

### Step 7 — walkthrough: happy path through layers

1. Transport Before: request_id (log only).
2. decode OK → endpoint → instrumenting MW → logging MW → core.
3. Core OK.
4. Instrumenting defer: Counter.Add(1), Histogram.Observe(dt).
5. Logging defer: method/took/err line.
6. Finalizer: code=200.

Three signals: metric rate↑, log line, access code. Different purposes.

### Step 8 — walkthrough: `ErrEmpty`

1. err != nil.
2. Counter with `success=false` (or error counter +1).
3. Histogram still Observe (errors *have* latency — important for “slow reject”).
4. App log has err.
5. Transport code depends on style A/B.

**Predict-then-answer D**

Question: should errors be excluded from the histogram?

- Predict: “yes, they spoil p99”.
- Answer: usually do **not** exclude — use a `success` label to split the dashboard. Slow failures are a signal.

### Step 9 — walkthrough: bad JSON (no service metric)

Decode fail → service MW does not run → **no** Uppercase counter bump.

Transport metrics (if you add them on Finalizer / HTTP MW) are another story. Do not expect a domain counter for wire fail.

### Step 10 — HTTP status metrics vs domain RED

| Signal | Where | Cardinality |
|--------|-------|-------------|
| domain method success | Service MW | low |
| HTTP code | Finalizer / HTTP MW | code bucket 2xx/4xx/5xx better than 20+ codes if you can |

Do not replace one with the other. Style A: HTTP 200 + domain error → HTTP success metrics lie without domain RED.

### Step 11 — Endpoint instrumenting? (contrast)

You can use `endpoint.Middleware` with metrics. Service level remains preferred here (types, same svc for more transports). If you instrument both — agree not to **double-count** the same use case.

### Step 12 — Gauge (brief)

Gauge for in-flight requests or queue length — useful, not the core of RED. If you introduce: Inc on entry, Dec in defer. Low cardinality.

### Step 13 — creating metrics in main (shape)

Pseudocode deliberately without stamping an unstable API:

```go
// 1) Create Prometheus registry / use default (check docs)
// 2) requestCount := <adapter Counter with name + help + label names>
// 3) requestLatency := <adapter Histogram with buckets>
// 4) Pass into InstrumentingMiddleware
// 5) http.Handle("/metrics", promhttp.Handler())
```

When implementing: open the real kit v0.12 Prometheus example. Handbook note: “adapter = kit interface ←→ Prometheus types”.

### Step 14 — bucket choice (histogram)

Bad buckets (everything in the first) → useless histogram. For StringService CPU:

- small range (micro/milli)
- do not blindly copy buckets for 30s downstream I/O

Document buckets in README ops.

### Step 15 — alerting idea (not implementing the whole stack)

- Error rate: `rate(errors)/rate(all)` > threshold
- Latency: histogram quantile > SLO
- Do not alert on request_id

07.13 (review) will summarize visibility — here only connect that metrics exist for **action**, not for dashboard wallpaper.

### Step 16 — anti-pattern catalog

| Anti | Why |
|------|-----|
| Label = user id | cardinality |
| Observe in ms, board in s | fake SLO |
| Logs only, “metrics later never” | no Rate |
| Counting in decode and in service | double rate |
| Metrics in core `stringService` | mixes concerns; use MW |
| Invented `counter.Increment()` if API wants `Add` | does not compile / fake docs memory |
| /metrics public without protection | info leak |

### Step 23 — saturation (optional addition to RED)

In-flight gauge:

- Inc on MW entry
- Dec in defer (also on error)

Low cardinality. Useful when “rate OK, but everything is stuck” (queue). Not required for the first PR.

### Step 24 — poster: Add vs Observe vs Log

| Tool | Semantics | Cardinality concern |
|------|-----------|---------------------|
| Log | event | disk/volume |
| Counter.Add | how many | label sets |
| Histogram.Observe | distribution | label sets + buckets |

Three tools, three costs. Do not replace one with another.

### Step 25 — walkthrough: deploy + scrape gap

New pod comes up; Grafana gap 30s until scrape starts. That is not “metrics broken” — that is scrape interval. Do not panic; compare with logs.

### Step 26 — metric name and breaking change

Changing a metric name breaks board and alert. Treat as API. Prefer add new + deprecate old with a period.

### Step 27 — histogram vs summary (orientation)

Prometheus Histogram (bucket) vs Summary (client quantile) — different trade-offs. The kit adapter path often leads to histogram. Do not mix on the same board without knowledge. For the course: histogram + `Observe` is enough of a mental model.

## Rules and syntax

1. Measure the use case (Service MW), not only the URL.
2. RED: rate, errors, duration.
3. Counter ≈ `Add`; Histogram ≈ `Observe` (kit/metrics spirit).
4. Low-cardinality labels; request_id only in the log.
5. Latency units agreed (seconds often).
6. Do not instrument the core method directly — MW.
7. Document MW order with logging.
8. `/metrics` separate; think about exposure.
9. Do not invent API — read adapter docs when coding.
10. Wire fail ≠ domain counter.
11. Error latency still Observe with a label.
12. Buckets meaningful for the workload.
13. Style A requires a domain error metric.
14. Preparation for 07.13 visibility review.

## Decision analysis

| Option | When | Risk |
|--------|------|------|
| Service instrumenting | course default | low |
| Endpoint instrumenting | when no service MW | watch double count |
| Logs only | early demo | no SLO |
| success label vs error counter | team taste | consistency |
| Prometheus | de facto | ops overhead |
| Other backend via kit interface | adapter already exists | learn one first |

## Trade-offs

- Histogram memory vs bucket resolution.
- More labels = better slice, higher cardinality risk.
- MW defer overhead small vs I/O; still real at extreme QPS.
- Adapter API accuracy requires reading docs — the handbook does not fake signatures.

## Common mistakes

1. High-cardinality labels (id, email).
2. Wrong Observe unit.
3. Metrics in core instead of MW.
4. Double counting HTTP + service.
5. Invented API method names.
6. /metrics public.
7. Ignoring style A (HTTP 200 + err).
8. Expecting domain metric on decode fail.
9. request_id as label.
10. Buckets copy-paste from another service.
11. Alert on raw counter without rate.
12. Mixing transport code and domain success without documentation.

## Idiomatic Go

- Same Middleware type as logging.
- Named returns + defer for Observe/Add.
- Dependency injection of metrics through the MW constructor.
- `fmt.Sprint(err == nil)` or map `ok`/`err` — consistent.
- Read `go doc` for the adapter before copy-paste from a blog for another major.

## Practical scenario

SLO: p99 Uppercase < 50ms. Without a histogram, the team “feels” it from logs. After InstrumentingMiddleware + Grafana, p99 180ms at peak — turns out staging shares CPU with a batch job. The fix is not “more logs”, but capacity. RED shortened debates.

## Deepening: instrumenting the service

### 1. insight

**Four Golden Signals** (Latency, Traffic, Errors, Saturation) ≈ RED + saturation (gauge/queue). Saturation is not required in the first PR.

### 2. insight

**Exemplars / trace id in metrics** — advanced; do not mix with request_id label. 07.15 tracing is another story.

### 3. insight

**Name spelling.** `stringsvc_uppercase_request_duration_seconds` — stable; do not change weekly.

Practical check: metric name in README?

### 4. insight

**Help string.** Prometheus help is not decoration; on-call reads it.

Practical check: does help state the unit?

### 5. insight

**Testing metrics.** You can stub Counter/Histogram interface in a MW unit test — proof that Add is called. Does not replace the service domain test.

Practical check: is there a fake counter?

### 6. insight

**Reset counters?** Not in a 24/7 process. Rate() in PromQL works over growth.

Practical check: does anyone “zero” a counter in a request? Anti.

### 7. insight

**Multi-instance.** Each pod exposes its own; Prometheus aggregates. Do not expect a global in-process total without the scrape model.

Practical check: how many replicas in your head?

### 8. insight

**Recording rules** — later. First raw RED.

Practical check: does the board use raw histogram_quantile?

### 9. insight

**Cost.** Every timeseries costs. Drop “debug label” before prod.

Practical check: number of unique label combinations?

### 10. insight

### 11. insight

**Instrumenting + logging begin time.** You can share begin; usually separate defers — simpler.

### 12. insight

**Partial failure downstream.** When service calls DB, the histogram includes DB. That is OK — it measures the method user experience.

Practical check: do you need a separate DB histogram? Later.

### Appendix: sample PromQL *idea* (not as the only true query)

- counter rate: `rate(stringsvc_requests_total[5m])`
- error ratio: errors / all (when you have dimensions)
- latency: `histogram_quantile(0.99, …)`

### Appendix: instrumenting + logging — what on-call opens first

1. Grafana RED (is the spike global).
2. Access log `code` (edge).
3. App log `err` + `request_id` (one case).

Reverse order (first one log) is slower for outage. Metrics are the entry; logs are the zoom.

### Appendix: common confusion Timer vs Histogram

Some APIs offer a Timer helper around a histogram. Semantically you still measure duration. If you use Timer, read docs — do not mix with `time.Timer` from stdlib.

### Appendix: predict-then-answer pack

**E.** Does Gauge replace Counter for rate?  
No — rate is computed from counter growth; gauge is current.

**F.** May you have `success=true` and `error_type=ErrEmpty` as labels?  
`error_type` with a *small* enum (sentinel names) can; unbounded `err.Error()` must not.

**G.** May InstrumentingMiddleware import `net/http`?  
Not on this path — same reason as logging MW.
