# 04.01 Introduction — microservice boundaries

> **Go Path - Zero to Gopher** / **03 Others → Building Microservices in Go** / Lesson 04.01

## Lesson goals

After this lesson you should:

- define what a microservice *boundary* is and why a boundary is not “one folder = one service”
- distinguish synchronous and asynchronous ways services communicate
- estimate operational cost (deploy, observation, errors, versions) before you cut a monolith
- recognize when it is better to stay in one process, and when it makes sense to introduce the network
- connect this module with the HTTP, JSON, middleware, and gRPC lessons that follow

## Prerequisite

- Go 1.22+ installed (`go version`)
- basic knowledge of HTTP (request, response, status code)
- experience packaging code into packages and modules
- preferred: at least one small HTTP handler in Go

If you have not yet worked with `net/http`, the next lesson (04.02) builds the skeleton. This lesson is deliberately about *decisions*, not syntax.

## Problem this lesson solves

Teams often hear “microservices” and immediately cut the application along technology lines: auth service, user service, order service, notification service. After a month they have more deploys, more logs, and more places where an error can disappear into the network — while business logic still joins the same tables in the same database.

The problem is not “how to write an HTTP handler”. The problem is: **where to put the boundary**, **how services talk**, and **what you pay** when you cross the boundary with the network instead of a function call.

Without a clear mental model, a Go microservice becomes only a monolith distributed across more binaries.

## Mental model

Imagine the system as a set of *units of responsibility*, not a set of technologies.

1. **Boundary** = the place where you change data ownership, deploy tempo, or language/team.
2. **Synchronous call** = “I wait for the answer now” (HTTP/gRPC request-response).
3. **Asynchronous event** = “I announce what happened” (queue, event bus, outbox).
4. **Operational cost** = everything that is not business logic: health, metrics, logs, timeout, retry, deploy, configuration, secrets.

In Go it is cheap to make a small HTTP server. So the temptation is to make *too many* services. Go does not punish the number of binaries; it punishes bad boundaries through latency, shared state, and messy errors.

## Mechanism

### What a boundary really means

A microservice boundary is not a folder in the repo. A boundary exists when:

- **one team** can deploy without coordinating with another team in the same release
- **data** has a clear owner (another service does not write directly into that table)
- an **API contract** (HTTP/JSON, gRPC, event schema) is the only way to “get inside”
- **failure** of one service does not automatically take down the whole system (at least not the same way as a panic in the same process)

If two “services” share the same database schema and `SELECT` each other’s tables, the boundary is fake. You have a distributed monolith.

### Synchronous communication

The client sends a request and waits for a response. In the Go ecosystem that is most often:

- HTTP + JSON (`net/http`, later in 04.02–04.06)
- gRPC + Protobuf (04.07 and module 05)

Advantages:

- simple mental model (like a function call over the network)
- easy to debug one request
- suitable for queries and commands that must return a result immediately

Disadvantages:

- couples availability (if B is down, A waits or fails)
- timeout and retry must be explicit
- latency adds up through call chains (A→B→C)

### Asynchronous communication

The producer publishes an event; the consumer reacts later. Typical patterns:

- a message on a queue (NATS, RabbitMQ, Kafka, SQS…)
- outbox in the database + publisher
- webhook / callback

Advantages:

- looser coupling (producer does not need to know who listens)
- better handles spikes if the queue buffers
- enables eventual consistency

Disadvantages:

- harder to follow the flow (“what happened to this order?”)
- you need idempotency (the same message can arrive twice)
- errors are deferred; the user may already see “success” while background work is still running

### Operational cost — what you pay per service

Every new process usually requires:

| Item | Why it costs |
|--------|-------------|
| Deploy pipeline | build, image, rollout, rollback |
| Health / readiness | the orchestrator must know when it is ready |
| Logs + request ID | correlation across multiple services |
| Metrics | latency, error rate, saturation |
| Configuration and secrets | more places for a wrong env |
| Timeout / circuit / retry | the network is not a local call |
| API versions | clients do not upgrade on the same day |

One formula you use in practice: **if you cannot name who watches the dashboard and who responds at night, do not cut another service.**

### When to stay in one process

Stay in a monolith (or “modular monolith”) when:

- one team owns the whole domain
- transactions often join multiple aggregates
- you are still learning domain boundaries
- operational capacity is small (few people, few tools)

Go supports a modular monolith well: packages by domain, clear interfaces, one `main`, one deploy.

### When to introduce a network boundary

Introduce a separate service when:

- different *scale* (one part needs 10× more instances)
- different *lifecycle* (release every day vs. quarterly)
- different *language or runtime* (e.g. ML service in Python, core in Go)
- a clear security boundary (PCI, PII, admin surface)
- team autonomy is real, not declarative

## Rules and syntax

This lesson has no new Go syntax, but it sets decision rules you use in code later:

1. **Boundary = contract.** If you do not have a documented API (OpenAPI, proto, event schema), you do not have a service — you have hope.
2. **Synchronous by default only within one UX flow.** If the user is not waiting for that result on screen, consider an event.
3. **Timeout is part of the contract.** Without a timeout, a synchronous call is an infinite hang.
4. **Idempotency for writes over the network.** Retry without idempotency creates duplicates.
5. **One data owner.** Other services read via API or projection, not via someone else’s table.
6. **Measurability before cutting.** If the monolith has no metrics, the microservice will not “magically” be observed.

Pseudo-rule for PR review:

```text
If a PR introduces a new HTTP service, it must answer:
- which data does it own?
- who are the clients?
- synchronous or asynchronous?
- which timeout and which error is returned to the client?
- how is it visible in logs (request ID)?
```

## Examples

### Example 1 — fake vs. real boundary

**Wrong (fake boundary):** `order-service` and `inventory-service` share the same Postgres schema; order does `UPDATE inventory SET qty = qty - 1`.

**Better (real boundary):** inventory owns stock; order sends a `ReserveStock` command (HTTP/gRPC) or an `OrderPlaced` event, and inventory decides on reservation.

### What happens here

In the bad model the network only slows down SQL. In the better model inventory can change its internal storage without breaking the order service — as long as the contract stays stable.

### Example 2 — a synchronous chain that hurts

The user clicks “Pay”. The API gateway calls `Order`, Order calls `Payment`, Payment calls `Fraud`, Fraud calls `Risk`. Each hop +20–50 ms + timeout risk.

A better shape: Order creates an order in `pending` state, sends `PaymentRequested`, and the client polls or gets websocket/push when done — *if* UX allows it.

### What happens here

A synchronous chain adds up latency and errors. An asynchronous flow moves complexity into state and observation, but protects UX from long waits when work lasts longer than an HTTP request.

### Example 3 — Go monolith with clear packages

```go
package main

import (
	"log"
	"net/http"

	"example.com/shop/internal/order"
	"example.com/shop/internal/payment"
)

func main() {
	mux := http.NewServeMux()
	order.Register(mux)
	payment.Register(mux)

	log.Fatal(http.ListenAndServe(":8080", mux))
}
```

Packages `order` and `payment` can become services tomorrow — *if* the boundary proves its value. Today they share a process, tomorrow they share a contract.

### What happens here

First you learn the domain through packages. You introduce the network only when measurement and team need require it. That is a cheaper path than “everything as a microservice immediately”.

### Example 4 — operational checklist before a new service

```text
[ ] Health endpoint
[ ] Structured log + request ID
[ ] Timeout on your server and on clients
[ ] Metric: RPS, p95, error %
[ ] API version (/v1/...)
[ ] Plan for image rollback
[ ] Who is on-call?
```

### What happens here

The checklist forces you to see the cost. If you cannot check half the items, a new service will increase chaos faster than team speed.

## Decision analysis

| Decision | Choose when… | Avoid when… |
|--------|-------------|-----------------|
| One process, multiple packages | small team, unclear boundaries | strict compliance split |
| Synchronous HTTP/gRPC | UX waits for the result | long batch / email / report |
| Asynchronous event | side-effect, fan-out | strict immediate consistency |
| New service | different scale/lifecycle | “sounds modern” |

Key decision in this course: **first learn to build a good HTTP service in Go**, then cut. Module 04 builds that foundation; gRPC and go-kit come as the next layers of communication and structure.

## Trade-offs

- **More services ⇒ more autonomy, fewer local transactions.** You must accept saga/outbox patterns.
- **Synchronous ⇒ simpler code, more brittle availability.** Asynchronous ⇒ more resilient, harder to debug.
- **Go small binaries ⇒ cheap deploy per command.** That is not a license for infinite fragmentation.
- **Shared database ⇒ faster start, more expensive divorce.** Clean database per service ⇒ cleaner ownership, more operations.

There is no universally correct number of services. There is only the number your team can *operationally* carry.

## Common mistakes

1. **Cutting by layers instead of by domain** (`user-db-service`, `user-api-service`) — you get a chatty network.
2. **Forgotten timeout** — one slow dependency freezes the worker pool.
3. **Retry without backoff and without idempotency** — thundering herd + double charge.
4. **Shared database “temporarily”** — temporarily lasts for years.
5. **No request ID** — an incident lasts hours because you cannot correlate logs.
6. **Microservice for the CV** — technical debt dressed as architecture.
7. **Mixing sync and async without clear state** — the client thinks it succeeded, but the event is not processed yet.

## Idiomatic Go

In the Go community a microservice often looks modest:

- one `main` per service
- `internal/` for private code
- standard `net/http` until you prove need for a framework
- explicit `context.Context` through calls (deadline travels with the request)
- errors as values, with mapping to HTTP/gRPC status at the edge

The idiom is not “use library X”. The idiom is: **small surface, clear contracts, observation from day one.**

```go
// Idiom: context goes through boundaries
func (s *OrderService) Create(ctx context.Context, in CreateInput) (Order, error) {
	if err := s.stock.Reserve(ctx, in.SKU, in.Qty); err != nil {
		return Order{}, err
	}
	return s.repo.Insert(ctx, in)
}
```

## Practical scenario

A team of six engineers has a Go monolith for a web shop. Checkout joins catalog, cart, payment, and email. Latency grows on Black Friday because email SMTP blocks workers.

**Wrong reflex:** cut five microservices over the weekend.

**Better plan:**

1. Extract email sending into an asynchronous worker (same repo, another `main` or goroutine + queue).
2. Add metrics and request ID to the monolith.
3. If payment must scale separately and has another owner, *then* extract it as a service with a clear API.
4. Catalog stays in-process as long as it has no separate lifecycle.

After a quarter they have two deployables (API + mailer) instead of seven — and fewer night alarms.

### Mini case: sync timeout budget

Assume a UX budget of 400 ms for “Add to cart”.

- gateway → cart: 40 ms
- cart → catalog (price check): 80 ms
- cart → inventory (soft reservation): 120 ms
- serialization + client network: 60 ms

About ~100 ms reserve remains. If inventory p95 jumps to 250 ms, the whole flow breaks. Options: cache price locally, async soft-reserve with later confirmation, or raise the budget and communicate to the user. The decision is a product one, not only technical.

### Mini case: an event that “fixes” UX

After payment the user does not have to wait for a PDF invoice. The API returns `202 Accepted` + `orderId`, and an `InvoiceGenerated` event fills storage. The UI polls status or uses SSE. The synchronous part stays short; the slow part goes to a queue.

## Summary

- A microservice starts from **ownership boundary**, not from the number of repos.
- **Sync** is simple but couples availability; **async** loosens coupling at the cost of state and observation.
- Every new process has an **operational cost** — measure it before cutting.
- Go makes small servers easy; decision discipline stays with you.
- The following lessons build a concrete HTTP service, then JSON, middleware, and gRPC.

## Extra insight: the cost of coupling

When two teams share a database “temporarily”, the cost is not only technical. Release calendars couple, migrations require coordination, and an incident in one table hits both dashboards. A real microservice boundary therefore starts from the question: *who may change the schema without a meeting?*

If the answer is not clear, you still have a monolith — only with network hops.

A synchronous call is like a local method: simple to read in code, dangerous when the chain grows. An asynchronous event is like a bulletin: looser, but you must keep history and tolerate duplicates.

In the rest of module 04 you practice building *one* good HTTP process. Only then does cutting make sense. Remember the operational cost from this lesson while you add health, JSON, middleware, and gRPC.

### Checklist before cutting the monolith

1. Do we have metrics by domain inside the process?
2. Do we have a clear data owner on paper?
3. Do we have on-call capacity for another deploy?
4. Do we have a plan for timeout and idempotency?
5. Do we have a way to follow request ID through future hops?

If three answers are “no”, first fix the monolith. Go makes that easier with packages and clear `main` entry points.

## Mechanism (continued): synchronous chain trace

Assume three services in the same request path:

```text
Browser -> API Gateway -> Order (Go) -> Inventory (Go) -> Reply
```

What happens in time:

1. Gateway receives HTTP, sets `X-Request-ID`, timeout e.g. 2s on the whole request.
2. Order gets JSON, opens ctx with remaining budget (e.g. 1.5s).
3. Order calls Inventory (HTTP or gRPC) with the **same** ctx (or a shorter child timeout).
4. Inventory answers slowly in 1.2s.
5. Order assembles the response; gateway returns 200.
6. If Inventory needs 3s, Order sees timeout, returns 503/504 or a mapped code — the user sees an error even though “only one hop” is slow.

Lesson: **every sync hop eats budget**. Before cutting, draw the p95 chain.

### Asynchronous message trace

```text
Order -> INSERT order + outbox row (same transaction)
      -> commit
Publisher -> reads outbox -> sends to bus
Inventory consumer -> processes -> ack
```

The user already got “order created”. Inventory may lag. So UI and support must know eventual consistency. Idempotency: the same `event_id` must not reduce stock twice.

## Mechanism (continued): fake vs real boundary

**Fake boundary (distributed monolith):**

- Order and Inventory in separate processes
- Both write into the same `public` schema, Order does `UPDATE inventory SET ...`
- Deploying Order requires a migration Inventory does not expect
- No API contract; there is a SQL contract

**Real boundary:**

- Inventory alone writes into its tables
- Order calls `Reserve(sku, qty)` (HTTP/gRPC) or emits `OrderCreated`
- Inventory’s schema is not visible to Order
- API versions are explicit (`/v1`, proto package `inventory.v1`)

## Mechanism (continued): checklist before cutting

Answer in writing before you open a new `cmd/`:

1. Who is on-call for the new process?
2. Which metric says it is healthy (liveness/readiness)?
3. Which timeout and retry are allowed?
4. Where does request ID live across hops?
5. Who is the data owner (table/stream)?
6. What does the user see when this service fails?
7. Does a modular monolith (package boundaries in the same process) solve 80% of the problem?

If you do not have answers, do not cut.

## Mechanism (continued): Go-specific traps

- **Cheap HTTP server** → too many binaries without need.
- **One `database/sql` pool “for everything”** across the network → fake boundary.
- **Shared library with business rules** between services → hidden coupling (lib change = coordinated deploy).
- **Ctx without timeout** between services → leak under load.

Go makes the right thing easy (small services) and the wrong thing easy (too many services). Discipline is in boundaries, not in the language.

## Predict-then-answers

**Q1.** Two teams, one database, two HTTP services. Is that a microservice?  
**A.** Operationally yes, architecturally often no — the data boundary is missing.

**Q2.** Order emits an event, Inventory listens, the user immediately sees “purchased” and stock lags 30s. Is it a bug?  
**A.** It can be intentional eventual consistency — it must be documented and visible in UX.

**Q3.** p95 chain A→B→C is 1.8s, gateway timeout 1s. What do you do first?  
**A.** Shorten the chain, speed up a hop, or raise the budget consciously — not “just retry”.

## Mechanism (deepening): what you really cut when you “cut a service”

A microservice is not a folder in a monorepo. The boundary mechanism is: **separate deploy artifact + separate failure domain + clear contract**. If two “services” must always deploy together and share a database without discipline, cutting is cosmetic.

### Trace: synchronous chain that eats budget

```text
Client 200ms budget
  → API Gateway 10ms
  → OrderSvc 40ms
       → InventorySvc 50ms
            → PricingSvc 60ms
  → remaining < 40ms for network/GC/retry
  → p95 breaks when any hop slows
```

Lesson: before cutting **draw the p95 chain**. Every sync hop eats budget. If you cannot draw it, do not cut.

### Trace: fake boundary

```text
OrderSvc and BillingSvc
  → same Postgres schema
  → FK across services
  → deploy Order without Billing migration = fail
```

That is not independence. A real boundary: own data or an explicit sync/async contract with a version.

## Mechanism (deepening): checklist before cutting

1. Schema owner clear (who may change the table).  
2. Timeout budget drawn (p50/p95).  
3. On-call exists for the new service (not “everyone for everything”).  
4. Failure mode documented (what the UI does when Inventory fails).  
5. Modular monolith considered (packages/`internal` boundaries in one process).  
6. Contract: OpenAPI or proto — not “look at the code”.  
7. Observability: request id across hops.  
8. Idempotency for write paths if there is retry.

**Predict:** you cut because the team heard microservices are “best practice”.  
**Answer:** coupling and ops cost often outweigh the benefit until the domain is clear.

## Mechanism (deepening): sync vs async boundary

| Style | Mechanism | When |
|------|-----------|-----|
| Sync HTTP/gRPC | request/response, deadline | need the answer now |
| Async messaging | publish/consume, at-least-once | can be eventual |

```text
PlaceOrder sync
  → reserve stock sync
  → charge card sync
  → if charge fails after reserve = compensation
```

Vs:

```text
PlaceOrder
  → write outbox
  → event OrderPlaced
  → Inventory and Billing react asynchronously
  → UI poll/status
```

Do not choose async to “avoid timeout” — choose because the domain is eventually consistent.

## Mechanism (deepening): Go-specific traps when cutting

- **shared `internal` package** copied into two modules → type divergence  
- **one `utils` module** as a hidden monolith  
- **`replace` in go.mod** forgotten in CI → “works on my machine”  
- **graceful shutdown** forgotten → 502 on rollout (04.02)  
- **context** does not cross hops → cancel does not work

## Mechanism (deepening): team organization around the boundary

Cutting without an org map produces “everyone touches everything”. Minimum:

| Service | Team | On-call | Repo | Contract |
|--------|-----|---------|------|--------|
| Order | A | A | order | proto/OpenAPI |
| Inventory | B | B | inventory | proto |

If on-call is the same for everything — you did not reduce load, you only added a network.

### Go monorepo vs polyrepo

Monorepo: easier atomic proto change, stricter CI.  
Polyrepo: clearer ownership, harder simultaneous breaking.  
The decision is operational, not “purity”.
