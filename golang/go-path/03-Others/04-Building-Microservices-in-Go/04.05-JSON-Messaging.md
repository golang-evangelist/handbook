# 04.05 JSON Messaging

> **Go Path - Zero to Gopher** / **03 Others → Building Microservices in Go** / Lesson 04.05

## Lesson goals

After this lesson you should:

- define request/response DTOs separately from the domain model
- use `encoding/json` correctly with body size limits
- version a JSON API without breaking clients
- map errors to predictable JSON envelopes
- understand trade-offs of `omitempty`, unknown fields, and strict decode

## Prerequisite

- Go 1.22+
- lesson 04.04 (routes and PathValue)
- basic knowledge of JSON types (object, array, string, number, bool, null)

## Problem this lesson solves

Microservices talk in messages. If a handler does `json.NewDecoder(r.Body).Decode(&User{})` directly into an ORM struct with DB tags, you get:

- leakage of internal fields in the response
- breaking clients when a column is renamed
- DoS via a huge body
- silently ignoring unknown fields or, conversely, brittle fail without a strategy

This lesson sets up a **message contract**: DTO in, DTO out, version, error.

## Mental model

Three type layers:

1. **Wire DTO** — what goes over the network (`CreateOrderRequest`).
2. **Domain** — what the service understands (`Order`).
3. **Storage** — what the database stores (row, document).

Conversion is explicit. JSON tags live on DTOs, not on everything.

An API version is a promise: `/v1/orders` does not change field meaning; new behaviors go to `/v2` or into backward-compatible fields.

## Mechanism

### Decode with a limit

```go
func decodeJSON[T any](r *http.Request, maxBytes int64) (T, error) {
	var zero T
	r.Body = http.MaxBytesReader(nil, r.Body, maxBytes)
	dec := json.NewDecoder(r.Body)
	dec.DisallowUnknownFields()
	var v T
	if err := dec.Decode(&v); err != nil {
		return zero, err
	}
	// reject trailing junk
	if err := dec.Decode(&struct{}{}); err != io.EOF {
		return zero, errors.New("trailing data")
	}
	return v, nil
}
```

`MaxBytesReader` protects memory. `DisallowUnknownFields` protects against the class of bugs where the client thinks it is sending a field the server ignores.

### Encode

```go
func writeJSON(w http.ResponseWriter, status int, v any) {
	w.Header().Set("Content-Type", "application/json; charset=utf-8")
	w.WriteHeader(status)
	enc := json.NewEncoder(w)
	enc.SetEscapeHTML(true)
	_ = enc.Encode(v)
}
```

### DTO example

```go
type CreateOrderRequest struct {
	CustomerID string `json:"customerId"`
	SKU        string `json:"sku"`
	Qty        int    `json:"qty"`
}

type OrderResponse struct {
	ID     string `json:"id"`
	Status string `json:"status"`
	Qty    int    `json:"qty"`
}

type ErrorBody struct {
	Code    string `json:"code"`
	Message string `json:"message"`
}
```

### Versioning

Strategies:

| Strategy | Example | Note |
|------------|--------|----------|
| URL prefix | `/v1/orders` | clearest for HTTP |
| Header | `Accept: application/vnd.shop.v2+json` | rarer, harder to debug |
| Tolerant fields | new field optional | backward compatible |

Rule: **do not remove a field from v1**; mark deprecated, remove in v2.

### Numbers and time

JSON numbers are float in many languages. For money use a decimal string or integer minor units. For time: RFC3339 string in UTC.

```go
type Money struct {
	Amount   string `json:"amount"`   // "19.99"
	Currency string `json:"currency"` // "EUR"
}
```

## Rules and syntax

1. `json` tags on exported fields; unexported ones are not serialized.
2. `omitempty` skips zero value — beware of `false` and `0` if they are meaningful.
3. Pointer fields distinguish “not sent” from zero value in PATCH semantics.
4. Always set `Content-Type` on the response.
5. Do not return raw `err.Error()` from internal errors to the client.
6. Limit body per route (e.g. 64 KiB for JSON commands, more for upload).
7. `time.Time` encodes as RFC3339 — document the timezone expectation (UTC).

```go
type PatchUserRequest struct {
	DisplayName *string `json:"displayName"`
	Active      *bool   `json:"active"`
}
```

## Examples

### Example 1 — handler with DTO

```go
func (h *Handlers) createOrder(w http.ResponseWriter, r *http.Request) {
	req, err := decodeJSON[CreateOrderRequest](r, 1<<16)
	if err != nil {
		writeJSON(w, http.StatusBadRequest, ErrorBody{Code: "bad_json", Message: "invalid body"})
		return
	}
	if req.Qty < 1 {
		writeJSON(w, http.StatusBadRequest, ErrorBody{Code: "bad_qty", Message: "qty must be >= 1"})
		return
	}
	out, err := h.svc.Create(r.Context(), req)
	if err != nil {
		writeJSON(w, http.StatusConflict, ErrorBody{Code: "create_failed", Message: "could not create"})
		return
	}
	writeJSON(w, http.StatusCreated, OrderResponse{ID: out.ID, Status: out.Status, Qty: out.Qty})
}
```

### What happens here

Input is validated at the edge. A domain error maps to a stable `code`. The client can branch logic without parsing free text.

### Example 2 — backward-compatible field

v1 response:

```json
{"id":"o1","status":"paid"}
```

v1.1 adds:

```json
{"id":"o1","status":"paid","paidAt":"2026-09-25T10:00:00Z"}
```

Old clients ignore `paidAt`. New ones use it. No `/v2` until you change the meaning of `status`.

### What happens here

Adding an optional field is the cheapest evolution. Breaking is rename, type change, or new meaning of an old enum.

### Example 3 — strict vs tolerant decode

```go
// strict for commands
dec.DisallowUnknownFields()

// tolerant for ingest from another system
// (without DisallowUnknownFields) + metrics for unknown keys if you parse a map
```

### What happens here

For a team public API: strict. For integration with a legacy partner: often tolerant with a log. Document the choice.

### Example 4 — list envelope

```go
type ListOrdersResponse struct {
	Items      []OrderResponse `json:"items"`
	NextCursor string          `json:"nextCursor,omitempty"`
}
```

### What happens here

Cursor pagination in JSON is predictable. Avoid bare arrays as top-level if you need metadata tomorrow.

### Example 5 — validation error with fields

```go
type FieldError struct {
	Field   string `json:"field"`
	Message string `json:"message"`
}
type ErrorBody struct {
	Code   string       `json:"code"`
	Errors []FieldError `json:"errors,omitempty"`
}
```

### What happens here

The UI can mark the exact field. A stable `code` remains for telemetry.

## Decision analysis

| Decision | Choose when |
|--------|------------|
| Separate DTO | always for a public API |
| `/v1` in path | multiple clients, long life |
| `DisallowUnknownFields` | commands you must understand 100% |
| String money | finance, forex |
| Int minor units | internal billing where currency is fixed |

You do not version because it “looks professional”. You version because you have clients you do not control on the same day.

## Trade-offs

- **Strict JSON** — catches client bugs, more 400s at first.
- **omitempty** — smaller payload, ambiguous zeros.
- **Same struct for DB and JSON** — write speed, pain in maintenance.
- **Large max body** — flexibility, larger memory risk.

## Common mistakes

1. Returning a domain entity with sensitive fields.
2. No `MaxBytesReader` — easy memory pressure.
3. Breaking v1 by renaming a field without a new path.
4. Float for money.
5. Mixing local time and UTC in timestamps.
6. `json.Unmarshal` of the whole body into `map[string]any` everywhere — you lose types.
7. Different ErrorBody per handler without agreement.

## Idiomatic Go

- Generics for `decodeJSON[T]` are OK in Go 1.22+.
- Validation near decode; business rules in the service.
- Tests: table-driven JSON golden files.
- `json.Encoder` for the response; do not build the string by hand.

```go
// prefer
type ID string // if you want a stronger type, the DTO still uses string on the wire
```

## Practical scenario

A mobile client and the web use `/v1/orders`. Backend wants to rename `customerId` to `buyerId`. If they rename in v1, the mobile app in the store breaks for weeks.

The team adds `buyerId` as an alias while keeping `customerId` (populate both), announces deprecation in the changelog, after two quarters introduces `/v2` without `customerId`. JSON messaging discipline saves the release.

### Operational detail

Log error `code` as a metric (`api_errors{code=bad_qty}`). Do not log the whole PII body. Request ID (04.06) ties the JSON error to the trace.

## Summary

- JSON messages are a contract: DTO, limit, clear errors, versions.
- Strict decode and MaxBytesReader are part of defense.
- Evolve fields backward-compatibly; breaking goes to v2.
- Next: middleware for log, authz hook, and request ID.

## Extra insight: client compatibility

The mobile store and partner integrators do not upgrade on the same day you merge a PR. So treat the JSON contract like a database: migrations are backward compatible until you cut a major version.

Checklist before a breaking change:

- is there at least one client outside your monorepo?
- can you temporarily send both fields?
- is there a feature flag or header for early v2 access?

If the answers hurt, do not rename on Friday evening. The DTO layer exists exactly so the domain can be refactored without breaking the wire format.

### Contract testing

Keep at least one golden JSON file per major version. CI fails if the response changes outside agreement. That is a cheaper contract test than full Pact for small teams.

### Envelope discipline

Agree on one error shape and one list shape. A mix of `{error: "..."}` here and `{message: "..."}` there costs hours in client code. A stable `code` + human `message` + optional `errors[]` cover 90% of UI needs.

## Working note: PATCH semantics

PUT usually replaces the representation; PATCH changes parts. In a Go DTO, pointer fields help: `nil` means “not sent”, not zero value. Without that you do not know whether the client wants `active=false` or simply did not send `active`.

Document the semantics in OpenAPI and in README. Otherwise clients guess. With PATCH you often also want `If-Match` / row version to avoid lost update. JSON messaging is not only Encode/Decode — it is an agreement about the meaning of a missing field.


## Mechanism (deepening): decode trace step by step

```text
HTTP body bytes
  → MaxBytesReader (hard ceiling)
  → json.Decoder.Decode(&DTO)
  → (optional) DisallowUnknownFields
  → trailing junk check
  → field validation (qty >= 1, sku != "")
  → DTO → domain CreateCommand mapping
  → service.Create(ctx, cmd)
  → domain → response DTO mapping
  → Encoder.Encode + Content-Type
```

**Predict:** what if you skip MaxBytesReader and the client sends 500 MB?  
**Answer:** memory pressure / OOM risk. The limit is not a “micro-optimization” — it is part of defense.

**Predict:** `Decode` succeeds, but after the JSON object in the body there is still `{"x":1}`.  
**Answer:** without a trailing-junk check, you silently accept. A second `Decode` into an empty struct should see `io.EOF`; otherwise 400.

### Complete helper (production shape)

```go
func decodeJSON[T any](w http.ResponseWriter, r *http.Request, maxBytes int64) (T, error) {
	var zero T
	r.Body = http.MaxBytesReader(w, r.Body, maxBytes)
	dec := json.NewDecoder(r.Body)
	dec.DisallowUnknownFields()
	var v T
	if err := dec.Decode(&v); err != nil {
		return zero, err
	}
	if err := dec.Decode(&struct{}{}); err != io.EOF {
		return zero, errors.New("trailing data")
	}
	return v, nil
}

func writeJSON(w http.ResponseWriter, status int, v any) {
	w.Header().Set("Content-Type", "application/json; charset=utf-8")
	w.WriteHeader(status)
	enc := json.NewEncoder(w)
	enc.SetEscapeHTML(true)
	if err := enc.Encode(v); err != nil {
		log.Printf("writeJSON: %v", err)
	}
}
```

## Mechanism (deepening): DTO vs domain vs storage

```go
type CreateOrderRequest struct {
	CustomerID string `json:"customerId"`
	SKU        string `json:"sku"`
	Qty        int    `json:"qty"`
}

type CreateOrderCmd struct {
	CustomerID CustomerID
	SKU        SKU
	Qty        Quantity
}

type OrderRow struct {
	ID           string
	CustomerID   string
	SKU          string
	Qty          int32
	InternalNote string // never in JSON response
}
```

**Predict:** handler returns `OrderRow` as JSON.  
**Answer:** leakage of `InternalNote` and coupling to the DB schema. Breaking when you rename a column.

```go
func (r CreateOrderRequest) toCmd() (CreateOrderCmd, error) {
	if r.Qty < 1 {
		return CreateOrderCmd{}, errBadQty
	}
	return CreateOrderCmd{
		CustomerID: CustomerID(r.CustomerID),
		SKU:        SKU(r.SKU),
		Qty:        Quantity(r.Qty),
	}, nil
}
```

## Mechanism (deepening): omitempty, pointers, PATCH

```go
type PatchUserRequest struct {
	DisplayName *string `json:"displayName"`
	Active      *bool   `json:"active"`
}
```

| JSON | DisplayName | meaning |
|------|-------------|----------|
| `{}` | nil | do not touch |
| `{"displayName":""}` | pointer to "" | set empty string |
| `{"active":false}` | Active → false | explicitly turn off |

**Predict:** `Active bool` without a pointer + `omitempty` on response.  
**Answer:** `false` disappears from JSON — the client does not know whether the field is supported.

### Lost update

```http
PATCH /v1/users/u1
If-Match: "3"
{"displayName":"Mila"}
```

If the row version is not 3 → 412 Precondition Failed. JSON messaging includes concurrency.

## Mechanism (deepening): errors as a stable contract

```go
type FieldError struct {
	Field   string `json:"field"`
	Message string `json:"message"`
}

type ErrorBody struct {
	Code      string       `json:"code"`
	Message   string       `json:"message"`
	Errors    []FieldError `json:"errors,omitempty"`
	RequestID string       `json:"requestId,omitempty"`
}
```

**Predict:** you return `err.Error()` from `sql: no rows` to the client.  
**Answer:** internal leakage + unstable string. Map to `code=not_found`, generic message, detail in the log with request ID.

| Situation | HTTP | code |
|-----------|------|------|
| Bad JSON | 400 | `bad_json` |
| Field validation | 400 | `validation_failed` |
| No resource | 404 | `not_found` |
| Unique conflict | 409 | `conflict` |
| Body too large | 413 / 400 | `body_too_large` |
| Internal | 500 | `internal` |

## Mechanism (deepening): versioning in practice

Backward compatible: add `paidAt` — old clients ignore. Breaking rename: `/v1` keeps the old field (deprecated), `/v2` the new. **Predict:** rename in `/v1` because “everyone uses the web”. **Answer:** mobile store and partners break for weeks.

Content-Type version (`Accept: application/vnd.shop.v2+json`) is harder to debug than `/v2` in the path — pick one strategy per product.

## Mechanism (deepening): handler from start to end

```go
func (h *Handlers) createOrder(w http.ResponseWriter, r *http.Request) {
	req, err := decodeJSON[CreateOrderRequest](w, r, 1<<16)
	if err != nil {
		writeJSON(w, http.StatusBadRequest, ErrorBody{
			Code: "bad_json", Message: "invalid body", RequestID: RequestIDFrom(r.Context()),
		})
		return
	}
	cmd, err := req.toCmd()
	if err != nil {
		writeJSON(w, http.StatusBadRequest, ErrorBody{
			Code: "validation_failed", Message: "invalid fields", RequestID: RequestIDFrom(r.Context()),
			Errors: []FieldError{{Field: "qty", Message: "must be >= 1"}},
		})
		return
	}
	out, err := h.svc.Create(r.Context(), cmd)
	if err != nil {
		writeJSON(w, http.StatusConflict, ErrorBody{
			Code: "create_failed", Message: "could not create", RequestID: RequestIDFrom(r.Context()),
		})
		return
	}
	writeJSON(w, http.StatusCreated, OrderResponse{ID: out.ID, Status: out.Status, Qty: out.Qty})
}
```

### Trace

```text
POST /v1/orders
  → MaxBytesReader
  → Decode CreateOrderRequest
  → toCmd validation
  → svc.Create
  → 201 OrderResponse
```

**Predict:** `svc.Create` returns context deadline.  
**Answer:** do not map blindly to 409; use 504/503 per policy. The error-mapping table lives next to ErrorBody.

## Mechanism (deepening): unknown fields in the log (tolerant mode)

When you cannot `DisallowUnknownFields` (legacy partner), still measure:

```go
var raw map[string]json.RawMessage
if err := json.Unmarshal(body, &raw); err == nil {
	for k := range raw {
		if !known[k] {
			unknownFieldCount.Add(1, k) // caution: key cardinality!
		}
	}
}
```

Better: total unknown count, not a label per typo key (high cardinality).

## Mechanism (deepening): Content-Type discipline

```go
ct := r.Header.Get("Content-Type")
if !strings.HasPrefix(ct, "application/json") {
	writeJSON(w, http.StatusUnsupportedMediaType, ErrorBody{Code: "bad_content_type", Message: "expected application/json"})
	return
}
```

**Predict:** you accept a `text/plain` body that “looks like JSON”.  
**Answer:** contract break; clients send anything. Be explicit on commands.

## Mechanism (deepening): pagination traps

Offset pagination (`?page=50`) breaks under inserts in the middle. A cursor (`nextCursor`) is more stable for a feed. A cursor must not leak internal DB offsets without a signature — sign or encrypt if sensitive.

```json
{"items":[...],"nextCursor":"eyJpZCI6Im85In0"}
```

## Mechanism (deepening): JSON evolution timeline

```text
t0: /v1/orders {id,status}
t1: add paidAt optional — old clients OK
```

**Answer:** you do not know whether /v1 still lives. Measure an `api_version` label.

### Content negotiation traps

If you support JSON and protobuf on the same HTTP path, `Accept` must be strictly tested. For this course: JSON on the HTTP edge, gRPC inside — less magic.

### Large payload policies

| Route | max body | why |
|------|----------|-------|
| POST /v1/orders | 64 KiB | command |
| POST /v1/imports | 8 MiB | batch with authz |
| multipart upload | separate path | not JSON decode |

One global 100 MiB limit “just in case” is bad defense.

### Encoder errors after WriteHeader

When `Encode` fails after 200, the client sees truncated JSON. Log it; consider buffer-then-write for critical responses (memory trade-off).

### Soft delete in JSON

```json
{"id":"u1","deletedAt":null}
```

vs omitting the resource (404). Agree: list does not show soft-deleted; GET by id may be 404 or an object with `deletedAt` — document it.
