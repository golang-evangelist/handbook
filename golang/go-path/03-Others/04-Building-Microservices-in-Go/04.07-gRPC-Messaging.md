# 04.07 gRPC Messaging

## Prerequisite

- Go 1.22+
- completed 04.01–04.06 (boundaries, HTTP, JSON, middleware)
- basic idea of RPC (you call a method, you get a response)
- you do not have to already have `protoc` — module 05 covers tooling in detail; here the focus is on the *decision* and a small code shape

## Problem this lesson solves

JSON HTTP is excellent for public APIs and the browser. Between internal services it often hurts:

- verbose payload
- manually keeping OpenAPI and code aligned
- streaming that does not sit well on request/response JSON
- strict contracts across languages (Go ↔ Java ↔ C# ↔ Node)

gRPC + Protocol Buffers offers a **strictly typed contract**, an efficient binary format, and generated clients. This lesson sets up *when* and shows a small Go server; detailed polyglot practice is module 05.

## Mental model

```text
.proto  →  protoc + plugin  →  generated Go types + service interface
                                      ↓
                              your implementation
                                      ↓
                              grpc.Server + listen
```

The client gets a **stub**: a local object that looks like a method call, and underneath is HTTP/2 + Protobuf.

gRPC status codes (`codes.NotFound`, `codes.InvalidArgument`) are related to HTTP statuses, but not a 1:1 map — do not mix them blindly.

## Mechanism

### When gRPC instead of JSON

Choose gRPC when:

- communication is **service ↔ service** (not the browser directly without grpc-web/proxy)
- you want **one contract** for multiple languages
- you need **streaming** (server/client/bidi)
- lower latency/payload with many small calls matters

Stay on JSON HTTP when:

- a public API for third parties that expect REST
- debugging with curl is the first line of support
- the team does not yet have proto discipline and CI generation

### Small proto (illustration)

```protobuf
syntax = "proto3";
package inventory.v1;
option go_package = "example.com/shop/gen/inventory/v1;inventoryv1";

service Inventory {
  rpc GetStock(GetStockRequest) returns (GetStockResponse);
}

message GetStockRequest { string sku = 1; }
message GetStockResponse {
  string sku = 1;
  int32 quantity = 2;
}
```

### Go server skeleton (after generation)

```go
type inventoryServer struct {
	inventoryv1.UnimplementedInventoryServer
	stock map[string]int32
}

func (s *inventoryServer) GetStock(ctx context.Context, req *inventoryv1.GetStockRequest) (*inventoryv1.GetStockResponse, error) {
	if req.GetSku() == "" {
		return nil, status.Error(codes.InvalidArgument, "sku required")
	}
	q, ok := s.stock[req.GetSku()]
	if !ok {
		return nil, status.Error(codes.NotFound, "sku not found")
	}
	return &inventoryv1.GetStockResponse{Sku: req.GetSku(), Quantity: q}, nil
}

func main() {
	lis, err := net.Listen("tcp", ":50051")
	if err != nil {
		log.Fatal(err)
	}
	srv := grpc.NewServer()
	inventoryv1.RegisterInventoryServer(srv, &inventoryServer{
		stock: map[string]int32{"ABC": 9},
	})
	log.Fatal(srv.Serve(lis))
}
```

`UnimplementedInventoryServer` embeds backward compatibility: new RPC methods do not break old code immediately.

### Deadline

```go
ctx, cancel := context.WithTimeout(ctx, 200*time.Millisecond)
defer cancel()
resp, err := client.GetStock(ctx, &inventoryv1.GetStockRequest{Sku: "ABC"})
```

Same as HTTP context: the budget travels with the call. Without a deadline, a synchronous RPC hangs.

### Interceptors ≈ middleware

gRPC has unary/stream interceptors for logging, auth, metrics — the same mental model as 04.06, a different API. Module 05 and the go-kit transport lessons continue that thread.

## Rules and syntax

1. The contract lives in `.proto`, not in ad-hoc JSON structs for internal RPC.
2. Always embed `Unimplemented...Server` in the Go implementation.
3. Return `status.Error` with `codes.*`, not bare `errors.New` across the boundary if you expect a code.
4. Fields in proto have numbers — **do not renumber** existing fields.
5. Package + version in the name (`inventory.v1`) is part of the discipline.
6. Do not expose gRPC directly to the browser without a conscious bridge.
7. Graceful stop: `srv.GracefulStop()` similar to HTTP `Shutdown`.

```go
go func() {
	<-ctx.Done()
	srv.GracefulStop()
}()
```

## Examples

### Example 1 — HTTP ↔ gRPC error map (approximate)

| Situation | HTTP | gRPC code |
|-----------|------|-----------|
| Bad input | 400 | InvalidArgument |
| No auth | 401 | Unauthenticated |
| No permission | 403 | PermissionDenied |
| No resource | 404 | NotFound |
| Conflict | 409 | AlreadyExists / Aborted |
| Server error | 500 | Internal |

### What happens here

A gateway that does transcoding must map consciously. Do not expect perfect automation.

### Example 2 — JSON REST stays for the public, gRPC inside

```text
Browser → API Gateway (JSON) → Order (gRPC) → Inventory (gRPC)
```

### What happens here

The public contract stays curl-friendly. Internal calls get strict types and generate clients.

### Example 3 — small client

```go
conn, err := grpc.Dial("localhost:50051", grpc.WithTransportCredentials(insecure.NewCredentials()))
if err != nil {
	log.Fatal(err)
}
defer conn.Close()
client := inventoryv1.NewInventoryClient(conn)
resp, err := client.GetStock(context.Background(), &inventoryv1.GetStockRequest{Sku: "ABC"})
```

Note: the newer API prefers `grpc.NewClient` in newer library versions — follow the release notes of the `google.golang.org/grpc` you use. The idea remains: connection + stub + context. `Dial` is the older API.

### What happens here

The client does not write JSON by hand. Generated types force fields. The error carries a gRPC code.

### Example 4 — when JSON hurts at volume

A service does 20k small lookups/s between pods. JSON allocations and verbose keys spend CPU. Protobuf shrinks the payload and codegen removes manual boilerplate. Before you “optimize”, measure — gRPC is not free (HTTP/2, streaming complexity).

### What happens here

The decision is measurement-driven, not fashion-driven.

### Example 5 — health

gRPC has a standard health protocol (`grpc.health.v1`). Orchestrators and load balancers often know how to check it. Enable it in a real service; here remember it exists as a counterpart to `/healthz`.

### What happens here

The operational cost from 04.01 applies to gRPC processes too: health, metrics, logs, deploy.

## Decision analysis

| Question | JSON HTTP | gRPC |
|---------|-----------|------|
| Public API | often better | rarer (with a bridge) |
| Polyglot internal | possible + OpenAPI | proto stronger default |
| Streaming | SSE/WS by hand | first-class |
| Debug with curl | excellent | needs grpcurl/grpcui |
| Browser | native | needs a proxy |

## Trade-offs

- **Stronger contract** — fewer runtime surprises, more CI/codegen discipline.
- **Binary format** — efficiency, harder ad-hoc debug.
- **HTTP/2 requirements** — proxy and load balancer must understand it.
- **Two stacks** (REST + gRPC) — flexibility, larger operational surface.

## Common mistakes

1. gRPC for the CV while the team has no proto CI.
2. Missing `Unimplemented*Server`.
3. Changing tag numbers in proto messages.
4. No deadline on the client.
5. Returning internal errors as `codes.Internal` with PII in the message.
6. Mixing protobuf runtime and plugin versions (details in 05.03).
7. Assuming gRPC is “always faster” without measuring.

## Idiomatic Go

- Generated package separated (`gen/` or `api/`).
- Hand-written business logic does not live in generated code.
- `status` package for errors at the edge.
- The same domain service can have HTTP and gRPC adapters — go-kit formalizes that in module 07.

```go
if err != nil {
	return nil, status.Errorf(codes.Internal, "query failed")
}
```

## Practical scenario

Order and Inventory first talked JSON HTTP. A frequent bug: Inventory adds a field, Order ignores it, then only in production they realize the client sends the wrong type for `quantity` (string vs number).

They moved to proto: CI generates Go code, a PR breaks the build if the contract does not match. The public checkout API stays JSON. Internal RPC is gRPC. Module 05 then teaches Java/C#/Node teams to share the same `.proto`.

### Link to operational cost

A new gRPC service still needs: deploy, dashboards, alerts, idempotency for writes, request ID in metadata. gRPC does not cancel 04.01 — it only changes the transport.

## Extra insight: transition period

It is rarely realistic to turn off JSON on Friday and turn on gRPC on Monday. Often you run a strangler pattern: new internal calls go gRPC, old JSON stays until clients move. The same domain service can expose both adapters.

In that period keep *one* business logic. Duplicating rules in the HTTP handler and the gRPC method is a path to divergence. Module 07 (go-kit) shows a more formal endpoint layer exactly for that; even without go-kit, extract a `Service` interface that both transports call.

### grpcurl as the curl counterpart

For debug install `grpcurl` or `grpcui`. Without that the team quickly forgets how to check an RPC by hand. Operational discipline from 04.01 applies: if you cannot try health and one read RPC, the service is not done.

## Mechanism (deepening): gRPC vs JSON decision by trace

```text
Is the caller a browser / partner with curl?
  yes → JSON HTTP at the edge (gateway stays)
  no → continue
Do you share a contract with another language (Java/C#/Node)?
  yes → proto + gRPC a strong candidate
  no → JSON can stay if the team wants that
Do you need server/client/bidi stream?
  yes → gRPC first-class; JSON needs SSE/WS by hand
Do you have CI for generate + breaking check?
  no → tooling first (05.03), not “gRPC for the CV”
```

**Predict:** the browser calls native gRPC to your Go server.  
**Answer:** you need gRPC-Web or a JSON gateway — plan the edge. Do not promise “the same as REST in DevTools”.

## Mechanism (deepening): small server with status trace

```go
func (s *inventoryServer) GetStock(ctx context.Context, req *inventoryv1.GetStockRequest) (*inventoryv1.GetStockResponse, error) {
	if err := ctx.Err(); err != nil {
		return nil, status.FromContextError(err).Err()
	}
	if req.GetSku() == "" {
		return nil, status.Error(codes.InvalidArgument, "sku required")
	}
	q, ok := s.stock[req.GetSku()]
	if !ok {
		return nil, status.Error(codes.NotFound, "sku not found")
	}
	return &inventoryv1.GetStockResponse{Sku: req.GetSku(), Quantity: q}, nil
}
```

### Success trace

```text
Serve(lis)
  → HTTP/2 stream
  → :path=/inventory.v1.Inventory/GetStock
  → GetStock(ctx, {sku:ABC})
  → response {quantity:9}
  → codes.OK
```

### Error trace

```text
GetStock({sku:""})
  → status.Error(InvalidArgument)
  → client: status.Code(err) == InvalidArgument
  → no retry
```

**Predict:** you return `errors.New("sku required")` without the status package.  
**Answer:** the client often sees `Unknown` / a useless code. At the RPC boundary use `status.Error`.

**Predict:** you forget to embed `UnimplementedInventoryServer`.  
**Answer:** new RPC methods in the proto break compilation or return Unimplemented unexpectedly — the modern generator expects the embed.

## Mechanism (deepening): client prefers NewClient

```go
conn, err := grpc.NewClient("127.0.0.1:50051",
	grpc.WithTransportCredentials(insecure.NewCredentials()))
if err != nil {
	log.Fatal(err)
}
defer conn.Close()

client := inventoryv1.NewInventoryClient(conn)
ctx, cancel := context.WithTimeout(context.Background(), 200*time.Millisecond)
defer cancel()

resp, err := client.GetStock(ctx, &inventoryv1.GetStockRequest{Sku: "ABC"})
```

`grpc.Dial` is the older API — follow the docs for your `google.golang.org/grpc` version. The course prefers `grpc.NewClient`. Insecure **lab only**.

**Predict:** `NewClient` success means the server is up.  
**Answer:** no. The connection object was created; the first RPC can get `Unavailable`. That is why a timeout on ctx.

## Mechanism (deepening): deadline chain

```text
Order handler ctx (800ms)
  → Inventory.GetStock(ctx, ...)  // same ctx
  → Inventory calls Warehouse.Get(ctx, ...) // still the same
```

If Warehouse opens `context.WithTimeout(context.Background(), 5*time.Second)` — it **breaks** the chain. Idiom: ctx downward, shorten only consciously.

**Predict:** no deadline, Inventory hangs on a DB lock.  
**Answer:** Order workers fill up, cascade. Deadline is a budget, not decoration.

## Predict-then-check

**A.** You change field number `sku = 1` to `sku = 3` in an existing proto.  
**Answer:** wire break — old clients read wrong fields. Never renumber.

**B.** Same process `:8080` JSON + `:50051` gRPC.  
**Answer:** OK if contracts are clear; do not mix DTO and proto automatically.

**C.** Retry on `CreateOrder` on `Unavailable`.  
**Answer:** caution — non-idempotent. Idempotency key or only read retry.

**D.** PII in `status.Errorf(codes.Internal, "user %s email %s", ...)`.  
**Answer:** leakage into client logs. Generic message; detail locally.

## Mechanism (deepening): GracefulStop and signal

```go
srv := grpc.NewServer()
inventoryv1.RegisterInventoryServer(srv, &inventoryServer{stock: stock})

lis, err := net.Listen("tcp", ":50051")
if err != nil {
	log.Fatal(err)
}

go func() {
	log.Fatal(srv.Serve(lis))
}()

stop := make(chan os.Signal, 1)
signal.Notify(stop, os.Interrupt, syscall.SIGTERM)
<-stop
srv.GracefulStop()
```

**Predict:** `Stop()` instead of `GracefulStop()` under load.  
**Answer:** in-flight RPCs are cut. Graceful waits for completion (with an upper timeout policy in a real system).
