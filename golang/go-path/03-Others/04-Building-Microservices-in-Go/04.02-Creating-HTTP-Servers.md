# 04.02 Creating HTTP Servers

## Lesson goals

After this lesson you should:

- configure `ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout`, and `IdleTimeout`
- implement graceful shutdown via `signal.NotifyContext` and `Server.Shutdown`
- understand why `ListenAndServe` alone is not enough for production
- connect `context.Context` with the process lifecycle

## Prerequisite

- Go 1.22+
- completed lesson 04.01 (boundaries, sync/async, operational cost)
- basic knowledge of HTTP methods and status codes
- a terminal and the ability to run a local process on a port

## Problem this lesson solves

Many Go tutorials end with:

```go
http.ListenAndServe(":8080", mux)
```

That works on a laptop. In a container, behind a load balancer, under SIGTERM, and with slow clients, the same code leaks:

- endless header reading (Slowloris style)
- violent killing of in-flight requests on deploy
- hang on `Write` when the client disappears
- unclear who closes the listener and when

This lesson builds a **service skeleton** you can carry through the rest of the module: routing, JSON, middleware, then gRPC alongside HTTP.

## Mental model

An HTTP server in Go has three layers:

1. **Listener** — accepts TCP connections (`Listen`).
2. **Server** — reads the request, calls the handler, writes the response; holds the timeout policy.
3. **Handler / mux** — your business edge (`ServeHTTP`).

Graceful shutdown means: **stop accepting new connections, wait for active requests (with a deadline), then exit.** That is not the same as `os.Exit(0)` mid-`json.Encode`.

Timeouts are **budgets**. Without a budget, goroutines and memory leak into slow clients.

## Mechanism

### Minimal skeleton

```go
package main

import (
	"context"
	"errors"
	"log"
	"net/http"
	"os"
	"os/signal"
	"syscall"
	"time"
)

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /healthz", func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte("ok"))
	})

	srv := &http.Server{
		Addr:              ":8080",
		Handler:           mux,
		ReadHeaderTimeout: 5 * time.Second,
		ReadTimeout:       15 * time.Second,
		WriteTimeout:      30 * time.Second,
		IdleTimeout:       60 * time.Second,
	}

	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
	defer stop()

	errCh := make(chan error, 1)
	go func() {
		log.Printf("listening on %s", srv.Addr)
		errCh <- srv.ListenAndServe()
	}()

	select {
	case err := <-errCh:
		if err != nil && !errors.Is(err, http.ErrServerClosed) {
			log.Fatal(err)
		}
	case <-ctx.Done():
		shutdownCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
		defer cancel()
		if err := srv.Shutdown(shutdownCtx); err != nil {
			log.Printf("shutdown: %v", err)
		}
	}
}
```

### Why fields on `http.Server`

| Field | Role |
|-------|--------|
| `ReadHeaderTimeout` | protects against slow header sending |
| `ReadTimeout` | whole request (header + body) budget |
| `WriteTimeout` | budget for writing the response |
| `IdleTimeout` | keep-alive connections that sit idle |

`ReadHeaderTimeout` is often the most important for public APIs. Without it, an attacker can hold many half-open connections.

### Graceful shutdown flow

1. The orchestrator sends SIGTERM.
2. `signal.NotifyContext` cancels ctx.
3. `Shutdown` closes the listener (no new accepts).
4. Active handlers get time until the `shutdownCtx` deadline.
5. If they do not finish, a force close remains (and you log that).

Kubernetes: set `terminationGracePeriodSeconds` longer than your shutdown timeout. Otherwise kube kills the process before Go finishes.

### Health and readiness

- **liveness** (`/healthz`): the process is alive; light response.
- **readiness** (`/readyz`): ready to receive traffic (database ping, dependencies).

Do not mix them. If readiness fails on a slow database, traffic is removed; liveness must not restart the pod because of a temporary DB hiccup without reason.

### Context in the handler

`r.Context()` carries cancellation when the client disconnects or when the server is shutting down. Pass it into DB/HTTP clients:

```go
func handleGet(w http.ResponseWriter, r *http.Request) {
	ctx := r.Context()
	item, err := store.Find(ctx, r.PathValue("id"))
	if err != nil {
		http.Error(w, "not found", http.StatusNotFound)
		return
	}
	_, _ = w.Write(item)
}
```

## Rules and syntax

1. Use `&http.Server{...}` instead of bare `ListenAndServe` in services.
2. Always set at least `ReadHeaderTimeout`.
3. Call `Shutdown` from the main flow with your own timeout context.
4. `ListenAndServe` in a goroutine; main waits for a signal or an error.
5. Do not only `Fatal` in a handler — return a status; the process stays alive.
6. Go 1.22+ mux: methods in the pattern `"GET /path"` (details in 04.04).
7. Read port and timeouts from env in a real service; in the lesson they are hardcoded for clarity.

```go
// Good: explicit Close error
if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
	return err
}
```

## Examples

### Example 1 — server with env port

```go
func addr() string {
	if p := os.Getenv("PORT"); p != "" {
		return ":" + p
	}
	return ":8080"
}
```

### What happens here

Platforms (Cloud Run, Heroku-style, Kubernetes) often inject `PORT`. The skeleton respects the environment without code changes for every deploy.

### Example 2 — readiness with a dependency

```go
mux.HandleFunc("GET /readyz", func(w http.ResponseWriter, r *http.Request) {
	ctx, cancel := context.WithTimeout(r.Context(), 2*time.Second)
	defer cancel()
	if err := db.PingContext(ctx); err != nil {
		http.Error(w, "not ready", http.StatusServiceUnavailable)
		return
	}
	w.WriteHeader(http.StatusOK)
})
```

### What happens here

Readiness uses a short timeout so it does not block the probe forever. 503 removes the pod from the load balancer until the database answers.

### Example 3 — error on port bind

```go
ln, err := net.Listen("tcp", srv.Addr)
if err != nil {
	log.Fatalf("listen: %v", err)
}
go srv.Serve(ln)
```

### What happens here

`Listen` immediately discovers “address already in use”. Useful in tests and when you want a custom listener (TLS, systemd socket).

### Example 4 — TLS termination in-process

```go
go func() {
	errCh <- srv.ListenAndServeTLS("cert.pem", "key.pem")
}()
```

### What happens here

In a cluster TLS often runs in a sidecar/ingress. For internal tools or edge services, `ListenAndServeTLS` is valid. Timeout fields still apply.

### Example 5 — forbidden hang on Shutdown

```go
shutdownCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
defer cancel()
if err := srv.Shutdown(shutdownCtx); err != nil {
	_ = srv.Close() // last line of defense
}
```

### What happens here

If a handler ignores cancellation, `Shutdown` can expire. `Close` forces it; it is better to fix handlers to respect `ctx.Done()`.

## Decision analysis

| Decision | For | Against |
|--------|----|--------|
| Only `ListenAndServe` | 30-second demo | no timeout/shutdown |
| `&http.Server` + signals | production minimum | a bit more code |
| Short WriteTimeout | protects resources | SSE/streaming needs special treatment |
| Long shutdown (60s) | finishes slow requests | slow deploy rotation |

For a JSON API typical values (starting point, not dogma): ReadHeader 5s, Read 10–30s, Write 30s, Idle 60–120s, Shutdown 10–30s.

## Trade-offs

- **Aggressive timeout** reduces risk, but breaks legitimately slow uploads — then use a separate endpoint with a larger budget.
- **Graceful shutdown** improves UX on deploy, but requires handlers to respect context.
- **Health on the same mux** is simple; some teams extract an admin port — more isolation, more configuration.
- **One process = one port** is clear; multiple listeners (metrics :9090) add operational complexity.

## Common mistakes

1. No `ReadHeaderTimeout` on a public API.
2. `log.Fatal` inside a handler kills the whole process because of one bad request.
3. Shutdown timeout longer than the Kubernetes grace period.
4. Readiness pings an external SaaS without a timeout → fake 503 waves.
5. Forgotten `errors.Is(..., http.ErrServerClosed)` so CI sees “fatal” on an orderly Shutdown.
6. WriteTimeout kills long-poll / websocket — you need another server or hijack without that budget.
7. Starting `Shutdown` before `Serve` has even started (race in tests).

## Idiomatic Go

- `main` is thin: wire config → server → run loop.
- Libraries do not call `ListenAndServe` by themselves; they return `http.Handler`.
- Test handlers via `httptest.NewRecorder` or `httptest.NewServer`.
- Use `errgroup` when you start HTTP + a background worker in parallel and want shared cancellation.

```go
mux.Handle("GET /healthz", http.HandlerFunc(...)) // or HandleFunc with a pattern
```

The standard library is enough until you prove need for a framework. That is the idiomatic stance of a Go service.

## Practical scenario

A team deploys a Go API on Kubernetes. On rollout users get intermittent 502s. Cause: the pod gets SIGTERM, the process dies immediately, ingress still sends requests.

**Fix:**

1. Introduce `Shutdown` with 15s.
2. Readiness fails as soon as shutdown starts (or via `preStop` sleep 2–3s so ingress removes the endpoint).
3. Handlers pass `r.Context()` into SQL.
4. In the `preStop` hook they add a short pause aligned with the readiness period.

502s drop almost to zero. The same skeleton is later used for all microservices in 04.x.

### Extra operational detail

On start, print the binary version and `GOMAXPROCS` in the logs. During an incident you know exactly what is running in production. On shutdown log `shutdown started` and `shutdown done` — the timeline in Loki/ELK immediately shows whether the grace period is enough.

## Extra insight: timeout budget in practice

Think of a request as a wallet of milliseconds. If the client gives 3 seconds, your server must not spend it all on reading the body. Leave reserve for business logic and the outbound call.

Typical mistake: `WriteTimeout` shorter than the slowest legitimate handler for report export. The solution is not to remove the timeout, but to extract long jobs into an async flow or a separate endpoint with an explicitly larger budget.

When testing graceful shutdown, run parallel load, send SIGTERM, and count 5xx. The goal is that deploy rotation does not look like an incident. Pair that with Kubernetes `preStop` and readiness — Go `Shutdown` alone does not solve the race on ingress.

### Signal map

- **SIGTERM** — normal shutdown request in a container
- **SIGINT** — Ctrl+C in development
- **SIGKILL** — not caught; that is why the grace period must finish before kill

On start, print version and `Addr` in the logs. On shutdown, print duration. That shortens MTTR when someone asks whether the new pod even brought up the listener.

## Mechanism (deepening): trace, ready flag, predict-then-check

Request trace: Accept → read header/body with timeout → `ServeHTTP` → write response. `Shutdown` stops Accept and waits for active ones with a deadline; `r.Context()` is canceled.

**Predict:** `ListenAndServe` in main without a goroutine + signal wait in the same flow. **Answer:** blocks — Serve in a goroutine, main waits for signal, then `Shutdown`.

**Predict:** `/healthz` == `/readyz`. **Answer:** bad — liveness must not fail because of a temporary DB outage.

Ready flag: `ready.Store(false)` before `Shutdown`, short sleep so the LB removes traffic, then `Shutdown`.

| Timeout | Role |
|---------|--------|
| ReadHeaderTimeout | slow headers |
| ReadTimeout | slow input |
| WriteTimeout | slow client on the response |
| IdleTimeout | keep-alive zombies |

Additional exercises: atomic ready; log Shutdown duration; env for Addr and timeouts. `ErrServerClosed` is not fatal on orderly shutdown.

## Mechanism (deepening): complete HTTP server lifecycle in Go

This section joins the lesson skeleton into one operational trace you must be able to draw on a whiteboard before you move to 04.03.

### Trace: start

```text
1. read env: ADDR, timeouts, SHUTDOWN_TIMEOUT
2. mux + route registration (health/ready/API)
3. http.Server{ Addr, Handler, ReadHeaderTimeout, ReadTimeout, WriteTimeout, IdleTimeout }
4. go srv.ListenAndServe()
5. main waits for signal (SIGINT/SIGTERM)
```

### Trace: request under load

```text
Accept
  → ReadHeaderTimeout budget for headers
  → ReadTimeout budget for body
  → ServeHTTP / mux
  → handler uses r.Context()
  → WriteTimeout budget for response
  → keep-alive or Close (IdleTimeout)
```

### Trace: graceful shutdown

```text
SIGTERM
  → ready.Store(false)          // LB stops sending new
  → short pause (aligned preStop)
  → Shutdown(ctx with timeout)
       → stops Accept
       → waits for active requests until deadline
       → cancels r.Context() when it must
  → log shutdown done
  → exit 0
```

**Predict:** `ListenAndServe` in the main goroutine, and signal handling never arrives.  
**Answer:** Serve blocks — must be in `go`, main waits for signal.

**Predict:** `log.Fatal` inside a handler on a database error.  
**Answer:** you kill the whole process because of one request; return 5xx and metricize.

## Mechanism (deepening): why each timeout exists

| Field | Attack / symptom it prevents | Typical misconfiguration |
|-------|-------------------------------|--------------------------------|
| ReadHeaderTimeout | slowloris on headers | left at 0 in production |
| ReadTimeout | endless upload | shorter than legitimate max body |
| WriteTimeout | slow client on download | breaks SSE/stream if you forget |
| IdleTimeout | keep-alive zombies | too short behind an LB that reuses |

Do not “raise everything to 5 minutes” as a fix. Split: short API vs long export endpoint with an explicitly larger budget.

## Mechanism (deepening): health vs ready

```go
mux.HandleFunc("GET /healthz", func(w http.ResponseWriter, r *http.Request) {
	w.WriteHeader(http.StatusOK)
})
mux.HandleFunc("GET /readyz", func(w http.ResponseWriter, r *http.Request) {
	if !ready.Load() || !dbOK() {
		http.Error(w, "not ready", http.StatusServiceUnavailable)
		return
	}
	w.WriteHeader(http.StatusOK)
})
```

- **liveness** (`/healthz`): the process is alive; do not check the database (otherwise crash loop on temporary DB outage).  
- **readiness** (`/readyz`): may receive traffic.

**Predict:** same handler for both.  
**Answer:** kube kills the pod while the database flickers — worsens the incident.

## Mechanism (deepening): context through the stack

```go
func (a *API) getItem(w http.ResponseWriter, r *http.Request) {
	ctx := r.Context()
	item, err := a.repo.Find(ctx, id)
	// ...
}
```

On Shutdown, net/http cancels the request context. If the repo uses `context.Background()`, SQL continues after the client disappears — you spend the pool.

```text
Shutdown
  → r.Context canceled
  → QueryContext sees cancel
  → row in the pool free
```

## Mechanism (deepening): ErrServerClosed

```go
go func() {
	err := srv.ListenAndServe()
	if err != nil && !errors.Is(err, http.ErrServerClosed) {
		log.Fatal(err)
	}
}()
```

`ErrServerClosed` after a successful `Shutdown` is **not** fatal. Treating it as fatal = false alarm in the deploy log.

## Mechanism (deepening): signal map in a container

| Signal | Who sends | Your reaction |
|--------|----------|----------------|
| SIGTERM | kube/docker stop | graceful Shutdown |
| SIGINT | Ctrl+C locally | same |
| SIGKILL | grace timeout | not caught — that is why grace must fit |

Align:

- `terminationGracePeriodSeconds` > Shutdown timeout + preStop  
- readiness fail before Shutdown  
- `preStop` sleep so iptables/LB removes the endpoint

## Mechanism (deepening): production skeleton (concise, accurate)

```go
srv := &http.Server{
	Addr:              addr,
	Handler:           mux,
	ReadHeaderTimeout: 5 * time.Second,
	ReadTimeout:       15 * time.Second,
	WriteTimeout:      30 * time.Second,
	IdleTimeout:       60 * time.Second,
}
errCh := make(chan error, 1)
go func() { errCh <- srv.ListenAndServe() }()

sigCh := make(chan os.Signal, 1)
signal.Notify(sigCh, os.Interrupt, syscall.SIGTERM)
select {
case <-sigCh:
	ready.Store(false)
	ctx, cancel := context.WithTimeout(context.Background(), 15*time.Second)
	defer cancel()
	_ = srv.Shutdown(ctx)
case err := <-errCh:
	if err != nil && !errors.Is(err, http.ErrServerClosed) {
		log.Fatal(err)
	}
}
```

This is not a “framework” — this is stdlib discipline.

## Mechanism summary

An HTTP server in a Go microservice is not a one-line `ListenAndServe` demo. It is a **time budget + signal + Shutdown + ready + context**. When you hold this, static/routing/JSON/middleware become add-ons on a stable base.

## Mechanism (deepening): timeout budget as a wallet

A request from a client with a 3s budget is not permission for the server to spend 2.9s reading the body. Leave reserve for the handler and outbound calls.

```text
client budget 3000ms
  → ReadHeader+Read  ≤ 500ms
  → business + DB     ≤ 2000ms
  → write response    ≤ 400ms
  → reserve           100ms
```

### SSE / long flows

A short WriteTimeout breaks SSE. Extract the long flow to a separate endpoint with an explicit budget or use a different model (chunked with a conscious timeout).

### Kubernetes alignment (extended)

| Knob | Role |
|------|-------|
| readinessProbe | removes from endpoints |
| preStop sleep | gives LB time |
| terminationGracePeriodSeconds | upper bound |
| Shutdown timeout | Go waits for active |

If grace < Shutdown, you get SIGKILL mid-work.

## Mechanism (deepening): multiple listeners

Often: `:8080` API, `:9090` metrics. Each has its own shutdown order. Do not mix API readiness with the metrics port without documentation.

## Mechanism (deepening): handler discipline

- no `log.Fatal` in the handler  
- errors → status code + log with request id  
- body limit (`http.MaxBytesReader`) with ReadTimeout  
- do not ignore `r.Context().Err()` after slow work

## Mechanism (deepening): request id and access log

```go
func withRequestID(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		rid := r.Header.Get("X-Request-Id")
		if rid == "" {
			rid = newID()
		}
		ctx := context.WithValue(r.Context(), ctxKeyRID, rid)
		w.Header().Set("X-Request-Id", rid)
		start := time.Now()
		next.ServeHTTP(w, r.WithContext(ctx))
		log.Printf("rid=%s method=%s path=%s dur=%s", rid, r.Method, r.URL.Path, time.Since(start))
	})
}
```

Without rid, Shutdown and timeout incidents are hard to correlate.
