# 08.03 Managing the application with Docker Compose

> **Go Path - Zero to Gopher** / **03 Others → Developing Go Apps with Docker** / Lesson 08.03

## Lesson goals

After this lesson you should be able to:

- describe a Compose file for a Go API + a dependent service (e.g. Postgres or Redis)
- use `depends_on` together with `healthcheck` instead of “sleeping” in a script
- separate the env file from git (`.env.example` commit, `.env` ignore)
- configure the application in 12-factor style via env variables
- understand networks and volumes enough for a local stack
- start, stop, and review stack logs with one command
- understand what Compose is (local/dev orchestrator) and what it is not (a Kubernetes replacement)

## Prerequisite

- Lessons 08.01–08.02 (Dockerfile multi-stage, nonroot, no secrets in the image)
- Docker Compose v2 (`docker compose version`)
- basic idea of TCP ports and env variables

## Problem this lesson solves

A Go service rarely lives alone while you develop it: you need a database, message queue, mailhog, mock OAuth. Manually starting five containers with long `docker run` lines does not scale for a team. Compose gives a **declarative stack**: one YAML, the same networks, the same volumes, the same health-check order.

Without a healthcheck, `depends_on` only waits for the container to *start*, not for the database to *accept connections*. Result: the Go application fails on the first `Ping`, restart loop, false feeling that “Compose is broken”.

Second problem: a `.env` with passwords in git. A secret pushed once lives forever in history.

## Mental model

A Compose project = a name + a set of services + networks + volumes.

```text
compose.yaml
├── services
│   ├── api      (your Go container)
│   └── db       (Postgres)
├── networks     (default project bridge network)
└── volumes      (persistent disk for db data)
```

- **Service** — a long-lived process (your API, Postgres).
- **depends_on** — start order / condition, not a distributed lock.
- **healthcheck** — a command inside the container that says “I am ready”.
- **env_file / environment** — 12-factor style configuration.
- **volume** — data durability (database) between `down` and `up`.
- **network** — DNS name of the service (`db`, `api`) inside the project.

Compose does not replace a Kubernetes service mesh. For Go Path - Zero to Gopher, the goal is a **fast, repeatable local and CI smoke stack**.

## Mechanism

### Lifecycle commands

```bash
docker compose up --build -d
docker compose ps
docker compose logs -f api
docker compose down
docker compose down -v
```

| Command | Effect |
|---------|--------|
| `up --build -d` | build as needed, start the stack in the background |
| `ps` | service status |
| `logs -f api` | follow stdout/stderr of service `api` |
| `down` | stop and remove containers/networks |
| `down -v` | like `down` + deletes named volumes |

`--build` rebuilds the image when the Dockerfile or context changes.

### Service — what YAML actually asks for

Minimal service with a build:

```yaml
services:
  api:
    build: .
    ports:
      - "8080:8080"
```

Minimal service with a ready-made image:

```yaml
services:
  db:
    image: postgres:16.3
    environment:
      POSTGRES_PASSWORD: example
```

**Predict then answer:** If you specify both `build:` and `image:`, what is `image:` for?

**Answer:** The name/tag that Compose assigns to the locally built image (and uses for references). It is not always “either-or” — they often stand together.

### `depends_on` without health — the trap

```yaml
depends_on:
  - db
```

This waits for the `db` container to **exist and start**, not for Postgres to accept TCP connections. Go `sql.Open` + `Ping` can fail in the first seconds.

### `depends_on` + `healthcheck` — the correct pattern

```yaml
services:
  db:
    image: postgres:16.3
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 5s
      retries: 10
  api:
    build: .
    depends_on:
      db:
        condition: service_healthy
```

**Trace on `up`:**

```text
1. Compose creates the project network
2. Starts db
3. Runs healthcheck in a loop
4. When healthy → starts api
5. api resolves hostname "db" via DNS
```

### Healthcheck for the Go API

In the application:

```go
mux.HandleFunc("/healthz", func(w http.ResponseWriter, r *http.Request) {
	w.WriteHeader(http.StatusOK)
	_, _ = w.Write([]byte("ok"))
})
```

In Compose (if you have `curl`/`wget` in the image — on Alpine yes, on distroless often no):

```yaml
healthcheck:
  test: ["CMD", "/ordersvc", "health"] # only if you have such a subcommand
```

For distroless more often: health is checked by the **orchestrator from outside** (Compose healthcheck requires a command *inside* the container). Practical compromise for a local stack: Alpine runtime in a dev Compose profile, distroless in the prod Dockerfile target.

Alpine alternative:

```yaml
healthcheck:
  test: ["CMD", "wget", "-qO-", "http://127.0.0.1:8080/healthz"]
  interval: 10s
  timeout: 3s
  retries: 5
```

### Env files that do not go into git

| File | In git? | Content |
|------|---------|---------|
| `.env` | **no** | real values, secrets |
| `.env.example` | **yes** | keys + fake/placeholder values |
| `.gitignore` | yes | must contain `.env` |

Example `.env.example`:

```text
POSTGRES_PASSWORD=changeme
DATABASE_URL=postgres://postgres:changeme@db:5432/app?sslmode=disable
ADDR=:8080
```

Example `.gitignore` snippet:

```text
.env
*.pem
```

Compose automatically reads `.env` from the project directory for **interpolation** of `${VAR}` in the YAML.

### 12-factor config via env

The application does not read `config.prod.json` from the image. It reads env:

```go
func envOr(key, fallback string) string {
	if v := os.Getenv(key); v != "" {
		return v
	}
	return fallback
}

func main() {
	addr := envOr("ADDR", ":8080")
	dsn := os.Getenv("DATABASE_URL")
	if dsn == "" {
		log.Fatal("DATABASE_URL is required")
	}
	// ...
}
```

In Compose:

```yaml
services:
  api:
    environment:
      ADDR: ":8080"
      DATABASE_URL: ${DATABASE_URL}
    env_file:
      - .env
```

**Predict then answer:** Why `DATABASE_URL` with host `db`, not `localhost`?

**Answer:** Inside the Compose network, `localhost` is the `api` container itself. The database service is reached by the service DNS name — `db`.

### Networks — briefly

Compose creates a default network for the project. All services on it see each other by service name.

Explicitly:

```yaml
networks:
  backend:

services:
  api:
    networks: [backend]
  db:
    networks: [backend]
```

For this course: the default network is enough until you deliberately split front/back.

### Volumes — briefly

A named volume keeps Postgres data:

```yaml
services:
  db:
    image: postgres:16.3
    volumes:
      - pgdata:/var/lib/postgresql/data

volumes:
  pgdata:
```

`docker compose down` — data remains.  
`docker compose down -v` — the volume is deleted (be careful with local data).

Bind mount for development (optional):

```yaml
volumes:
  - ./config:/app/config:ro
```

Do not mount secrets from random paths into git.

### Port mapping

```yaml
ports:
  - "8080:8080"
```

Left: host. Right: container.  
For a database locally often:

```yaml
ports:
  - "5432:5432"
```

In production the database is often **not** published on the host; locally it is, for a `psql` client.

### Line-by-line: complete `compose.yaml`

```yaml
name: orders
# 1) Project name (instead of the folder name)

services:
  db:
    # 2) Dependent service
    image: postgres:16.3
    # 3) Pinned tag — not latest
    environment:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: orders
    # 4) Password from .env interpolation
    volumes:
      - pgdata:/var/lib/postgresql/data
    # 5) Data durability
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres -d orders"]
      interval: 5s
      timeout: 5s
      retries: 10
    # 6) Ready when it accepts connections
    ports:
      - "5432:5432"
    # 7) Local access from the host

  api:
    build:
      context: .
      dockerfile: Dockerfile
    # 8) Multi-stage Dockerfile from 08.02
    image: ordersvc:dev
    # 9) Local image name
    environment:
      ADDR: ":8080"
      DATABASE_URL: ${DATABASE_URL}
    env_file:
      - .env
    # 10) 12-factor config
    ports:
      - "8080:8080"
    # 11) Publish API
    depends_on:
      db:
        condition: service_healthy
    # 12) Wait for healthy, not just start

volumes:
  pgdata:
  # 13) Named volume declaration
```

### Trace: first `up` on an empty machine

```text
1. Reads compose.yaml + .env
2. Interpolates ${POSTGRES_PASSWORD}, ${DATABASE_URL}
3. Pull postgres:16.3 (if not local)
4. Build api image from Dockerfile
5. Creates volume pgdata
6. Creates network orders_default (or similar)
7. Start db → healthcheck loop
8. db healthy → start api
9. api reads DATABASE_URL → connects to host db:5432
10. Log: listening on :8080
```

### What if `.env` is missing

Compose warns about unset variables; values become empty. Postgres may refuse to start without a password. The Go api fails on `DATABASE_URL is required`.

So: document `.env.example` and a README step “copy to `.env`”.

### Restart and the development loop

```bash
# Go code change
docker compose up --build -d api
docker compose logs -f api
```

Only `api` rebuilds; the `db` volume remains. That is the point of Compose in development.

### Compose is not Kubernetes

| Compose | Kubernetes |
|---------|------------|
| local YAML stack | cluster orchestration |
| `depends_on` | probes + init/ordering patterns |
| named volume on one host | PVC, distributed storage |
| good for dev/CI smoke | production scaling, self-healing |

Do not learn Compose as “small K8s”. Learn it as a **reproducible local stack**.

### Predict then answer round

1. **Q:** `depends_on: [db]` — does api wait for `pg_isready`?  
   **A:** No, unless you have `condition: service_healthy` and a healthcheck.

2. **Q:** Can api use `localhost:5432` for Postgres in Compose?  
   **A:** Not for connecting to another service; use `db`.

3. **Q:** Does `env_file: .env` commit secrets?  
   **A:** Not by itself — but if `.env` is not in `.gitignore` and someone adds it, yes.

4. **Q:** Does `down -v` delete code in git?  
   **A:** No. It deletes Docker volumes (e.g. database data).

### Multiple environments: override file (introduction)

```bash
docker compose -f compose.yaml -f compose.override.yaml up
```

Override is often not in git or is personalized. The base `compose.yaml` stays shared. Do not complicate at the start — one file + `.env` is enough.

### Logs as the first diagnostic step

```bash
docker compose ps
docker compose logs --tail=100 db
docker compose logs --tail=100 api
```

If `api` restarts in a loop, almost always: DSN, health timing, or migrations. More detail in 08.04.

### Migrations and order (practice)

Compose does not run migrations magically. Patterns:

1. api runs migrate on start (simple, watch for locks);
2. a separate one-shot `migrate` service with `depends_on` healthy db;
3. manually `docker compose run --rm api /migrate`.

For the lesson: document the choice; do not hide the problem.

## Rules and syntax

- Prefer `compose.yaml` (or consistently `docker-compose.yml` across the whole repo).
- Pin image tags of dependent services (`postgres:16.3`), not `latest`.
- `depends_on` + `condition: service_healthy` with a real healthcheck.
- `.env` in `.gitignore`; `.env.example` in git.
- Config via env (12-factor), not via files baked into the image.
- Dependency hostname = service name.
- Map only the ports you need locally.
- `down -v` deliberately — it deletes data.
- Compose = local/dev/CI smoke, not a production orchestrator replacement.

## Examples

### Example 1 — Go API + Postgres

`compose.yaml` as in the line-by-line section. `.env`:

```text
POSTGRES_PASSWORD=localdevpass
DATABASE_URL=postgres://postgres:localdevpass@db:5432/orders?sslmode=disable
```

```bash
cp .env.example .env
# change the password locally
docker compose up --build -d
curl -s http://127.0.0.1:8080/healthz
```

#### What happens here

Compose builds api, starts Postgres, waits for health, then api. `curl` from the host goes to published `8080`. Secrets are in `.env`, not in git.

### Example 2 — Redis as a second dependency

```yaml
services:
  redis:
    image: redis:7.2.5
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 10
  api:
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_healthy
    environment:
      REDIS_ADDR: redis:6379
```

#### What happens here

Api waits for both healthy conditions. Hostname `redis` resolves inside the project network.

### Example 3 — Anti-example: sleep in an entrypoint script

```bash
#!/bin/sh
sleep 10
exec /ordersvc
```

#### What happens here

Sometimes “works” on a fast laptop, fails on slow CI. Healthcheck is more deterministic than a magic `sleep`.

### Example 4 — Interpolation and leaking in `ps`

```yaml
environment:
  DATABASE_URL: ${DATABASE_URL}
```

```bash
docker compose config
```

#### What happens here

`config` shows the rendered YAML. Be careful what you share — it can expand secrets into the terminal/log. Do not paste `compose config` with production secrets into a public ticket.

### Example 5 — You delete a volume by mistake

```bash
docker compose down -v
docker compose up -d
```

#### What happens here

The database is empty. If you had local test data only in the volume, it is gone. For “reset the database” that is intentional; for “restart api” use `down` without `-v`.

### Example 6 — Predict: api log says connection refused on localhost:5432

**Cause:** DSN uses `localhost` instead of `db`.

**Fix:** `DATABASE_URL=...@db:5432/...`

### Example 7 — Dev publish of the database + GUI client

```yaml
ports:
  - "5432:5432"
```

From the host: `psql postgres://postgres:...@127.0.0.1:5432/orders`.

#### What happens here

Publish enables local tools. Inside the Compose network api still uses `db:5432`, not the host port mapping.

### Example 8 — Line-by-line Go reading env

```go
package main

import (
	"database/sql"
	"log"
	"net/http"
	"os"

	_ "github.com/jackc/pgx/v5/stdlib"
)

func main() {
	addr := os.Getenv("ADDR")
	if addr == "" {
		addr = ":8080"
	}
	dsn := os.Getenv("DATABASE_URL")
	if dsn == "" {
		log.Fatal("DATABASE_URL is required")
	}
	db, err := sql.Open("pgx", dsn)
	if err != nil {
		log.Fatal(err)
	}
	defer db.Close()
	if err := db.Ping(); err != nil {
		log.Fatal(err)
	}
	mux := http.NewServeMux()
	mux.HandleFunc("/healthz", func(w http.ResponseWriter, r *http.Request) {
		if err := db.Ping(); err != nil {
			http.Error(w, "db down", http.StatusServiceUnavailable)
			return
		}
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte("ok"))
	})
	log.Fatal(http.ListenAndServe(addr, mux))
}
```

#### What happens here

Without `DATABASE_URL` the process does not start — fail fast. `/healthz` also checks the DB. Compose health on api can use the same endpoint if the image has an HTTP client tool; otherwise `curl` from the host outside.

## Decision analysis

| Decision | Options | Recommendation for the course |
|----------|---------|-------------------------------|
| One vs multiple compose files | 1 / override | start with 1 |
| Distroless api in Compose | yes / Alpine dev | Alpine easier for local healthcheck |
| Publish DB port | yes / no | yes locally, no on a shared server |
| Migrations | in api / one-shot | document the choice |
| Secret delivery | `.env` / vault | `.env` locally; vault in real prod |

## Trade-offs

- **Healthcheck + depends_on** slows the first start by a few seconds; saves hours of flaky restarts.
- **`.env` locally** is convenient and risky if it leaks into git — ignore discipline is mandatory.
- **Compose volume** is not a backup strategy.
- **Same compose in CI** simplifies smoke, but CI needs ephemeral secrets and cleanup.
- **Too many services in one file** (whole microservice flat) becomes slow for daily work — split by “dev slice”.

## Common mistakes

1. **`depends_on` without `service_healthy`** — api starts too early.
2. **`localhost` instead of the service name** — connection refused.
3. **`.env` in git** — secret leak.
4. **`latest` for Postgres** — nondeterministic stack.
5. **`down -v` out of habit** — loss of local data.
6. **Secrets hardcoded in `compose.yaml`** — same as baking into the image.
7. **Mixing host port and service DNS** in the DSN.
8. **Expecting that Compose = production orchestrator**.
9. **Healthcheck that needs `curl` in a distroless image** — always fails.
10. **Forgotten `ports` then “api does not work”** — it works inside the network, not from the host.

## Idiomatic Docker/Go

- One `compose.yaml` for the local API + dependencies stack.
- Pinned tags for all images.
- Config exclusively via env.
- Healthy dependencies before api starts.
- `.env.example` as the team contract.
- Logs on stdout; diagnostics via `compose logs`.
- Multi-stage image from 08.02 as the `build:` context.

## Practical scenario

Five developers, five different `docker run` notes in Notion. A new member loses a day bringing up Postgres + Redis + API. The team introduces `compose.yaml` + `.env.example`. Onboarding rule: `cp .env.example .env && docker compose up --build`. Flaky “api can't connect” disappears after `service_healthy`. One incident: a colleague commits `.env` — secret in Git history; password rotation + `git filter` procedure + pre-commit check for `.env`. After that Compose becomes the default way of local work; CI uses the same file for smoke on a PR (08.05).

### Checklist before sharing the stack with the team

1. `compose.yaml` without hardcoded secrets.
2. `.env.example` up to date.
3. `.env` in `.gitignore`.
4. Healthcheck on dependencies.
5. `depends_on` with `service_healthy`.
6. Pinned image tags.
7. README: three commands to `/healthz`.

### Extended mechanism: DNS inside the Compose network

When api does:

```go
dsn := "postgres://postgres:pass@db:5432/orders?sslmode=disable"
```

resolving `db`:

```text
1. Go/net resolver asks DNS in the container
2. Docker's embedded DNS (typically 127.0.0.11) answers
3. IP of the db service container
4. TCP connection to 5432 on that IP
```

`db` is not a magic word — it is the **service name** in the YAML. Rename the service to `postgres` → the hostname becomes `postgres`.

### Trace: `compose up` when healthcheck fails

```text
1. db starts
2. healthcheck: pg_isready → fail (not ready yet)
3. retries are consumed
4. if db never becomes healthy → api does not start (with condition)
5. compose ps shows unhealthy
6. logs db → real cause (e.g. wrong POSTGRES_PASSWORD interpolation)
```

Without condition: api would start and fall into a restart loop — harder to diagnose.

### Predict: two projects, same port

```text
Folder A: ports 8080:8080
Folder B: ports 8080:8080
```

**A:** The second `up` fails because the host port is taken. Solution: another host port (`8081:8080`) or stop the first project.

### Mini exercise in text: map symptom → cause

| Symptom | Cause |
|---------|-------|
| connection refused `localhost:5432` from api | wrong host in DSN |
| password authentication failed | `.env` / interpolation |
| unhealthy db | healthcheck command / Postgres does not start |
| port is already allocated | host port conflict |
| `.env` not found warnings | missing `.env` next to `compose.yaml` |

### Project name and isolation

```yaml
name: orders-dev
```

or:

```bash
docker compose -p orders-dev up -d
```

Two projects = two networks, two isolations. Useful when you work on feature branches in parallel.

### Compose and multi-stage: which target you build locally

```yaml
services:
  api:
    build:
      context: .
      dockerfile: Dockerfile
      target: runtime
```

If the Dockerfile has `AS build` and `AS runtime`, `target: runtime` prevents accidentally tagging the build stage. Align with 08.02.

### Predict: env in YAML vs env_file priority

Compose merges sources; explicit `environment:` usually wins over values from `env_file` for the same key (check your Compose version if you need a strict edge case). Keep one source of truth so you do not debug “which password is being read”.

## Summary

Compose declares a local stack: services, networks, volumes. `depends_on` must go with `healthcheck` and `condition: service_healthy` if you want the Go api to start only when the database accepts connections. Configuration is 12-factor via env; `.env` is not for git. Dependency hostname = service name. A volume keeps DB data; `down -v` deletes it. Compose is a tool for repeatable development and smoke — not a production orchestrator.
