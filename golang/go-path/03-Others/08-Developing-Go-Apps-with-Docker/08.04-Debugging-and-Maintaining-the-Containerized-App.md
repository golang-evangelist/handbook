# 08.04 Debugging and maintaining a containerized Go application

> **Go Path - Zero to Gopher** / **03 Others → Developing Go Apps with Docker** / Lesson 08.04

## Lesson goals

After this lesson you should be able to:

- read and filter container logs as the first diagnostic step (`docker logs`, Compose logs)
- build a separate debug image with Delve
- connect a debugger to the process in the container with the port bound to localhost
- never ship Delve in a production image/tag
- understand maintenance: health, restart policy, resource limits, log rotation
- set a diagnostics hierarchy: logs → health → reproduction → Delve (debug only)

## Prerequisite

- Lessons 08.01–08.03
- Basic local debugging of Go code (IDE or Delve locally)
- Compose or bare `docker run`
- Understanding of the prod vs debug artifact difference from 08.02

## Problem this lesson solves

A container changes debugging habits. You do not have the same filesystem, often you have no shell (distroless), the PID namespace is isolated, and “just put Delve in the same image” ends with the production registry getting a debugger and a `-gcflags=all=-N -l` build without optimizations.

The other end of the spectrum: the team only looks at orchestrator Events and never at application logs — they miss an error that was already printed on stdout.

This lesson sets a **diagnostics hierarchy**: logs → health/restart → reproduce locally → Delve in a *debug* image.

## Mental model

Three image lines:

```text
1) prod   — stripped, nonroot, NO Delve, NO -N -l
2) debug  — same source, NO -s -w, WITH Delve, often with a shell
3) dev    — optional bind-mount; not the same as prod
```

Maintenance ≠ debugging.

- **Debugging** — find the cause in code/state.
- **Maintenance** — how the process survives restart, how logs do not fill the disk, how limits stop one service from eating the host.

```text
Incident
   │
   ▼
docker logs / compose logs  ──► clear error? ──yes──► fix + deploy
   │
   no
   ▼
health / restart / resources ──► infra cause? ──yes──► fix limits/probes
   │
   no
   ▼
reproduce locally (Compose)
   │
   ▼
Delve in debug image (localhost:2345) ──► never in the prod tag
```

## Mechanism

### Logs — Docker captures stdout/stderr

The Docker logging driver (often `json-file`) captures the process standard output.

```bash
docker logs -f --since 10m api
docker logs --tail=200 api
docker compose logs -f --tail=200 api
docker compose logs --since 30m db api
```

In Go: structured log (`log/slog` in 1.21+) or at least consistent text. One request — one `request_id` if you can.

**Rule:** log to stdout/stderr. Not to a local file inside the container without a volume and rotation.

### Trace: path of one log line

```text
1. log.Printf("order %s created", id)
2. writes to stdout of process PID 1
3. container runtime captures the stream
4. logging driver records (json-file on host disk / plugin)
5. docker logs reads that store
6. central agent (optional) sends to Loki/ELK — out of scope for this lesson
```

### Structured log in Go (minimal)

```go
package main

import (
	"log/slog"
	"net/http"
	"os"
)

func main() {
	logger := slog.New(slog.NewJSONHandler(os.Stdout, nil))
	mux := http.NewServeMux()
	mux.HandleFunc("/healthz", func(w http.ResponseWriter, r *http.Request) {
		logger.Info("healthz", "path", r.URL.Path)
		w.WriteHeader(http.StatusOK)
	})
	logger.Info("listening", "addr", ":8080")
	_ = http.ListenAndServe(":8080", mux)
}
```

**Predict then answer:** If you log to `/var/log/app.log` in a distroless nonroot container without a volume, what happens?

**Answer:** Often permission denied or logs disappear with the container’s lifetime. stdout is the correct channel.

### Health and restart — maintenance

Compose example:

```yaml
services:
  api:
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://127.0.0.1:8080/healthz"]
      interval: 10s
      timeout: 3s
      retries: 3
      start_period: 10s
```

| Field | Role |
|-------|------|
| `restart` | container restart policy |
| `healthcheck` | whether the application is “alive” by your definition |
| `start_period` | grace period while the app starts |

`restart: unless-stopped` is a common local choice. In Kubernetes restart policy and probes are a different model — do not mix the concepts 1:1.

### Resource limits and Go

Compose (e.g.):

```yaml
mem_limit: 512m
cpus: 1.0
```

Go in a container: set `GOMEMLIMIT` so GC respects limits better (e.g. a bit below the hard limit).

Without a limit, one memory leak in a Go service can threaten the whole dev laptop or node.

### Delve — ONLY in the debug image

Delve (`dlv`) is a debugger. In a container the typical pattern is:

1. build **without** `-ldflags="-s -w"`
2. build with `-gcflags="all=-N -l"` (disables some optimizations for better debug)
3. install `dlv` in the debug stage
4. listen on `2345`
5. publish the port **only on localhost** of the host
6. IDE attaches to `127.0.0.1:2345`

**Never** mix this into the production tag.

### Line-by-line: Dockerfile.debug

```dockerfile
# syntax=docker/dockerfile:1
# 1) Separate file OR separate stage target — important: separate tag

FROM golang:1.22.5-alpine AS debug
# 2) Deliberately golang base — need go and room for dlv

WORKDIR /src
RUN apk add --no-cache git ca-certificates
# 3) Tools to fetch Delve / modules

COPY go.mod go.sum ./
RUN go mod download

RUN go install github.com/go-delve/delve/cmd/dlv@v1.22.1
# 4) Pinned Delve version — not @latest without awareness

COPY . .
ARG TARGETOS=linux
ARG TARGETARCH=amd64
RUN CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH \
    go build -gcflags="all=-N -l" -o /out/ordersvc ./cmd/ordersvc
# 5) WITHOUT -s -w; WITH -N -l for debug

WORKDIR /app
COPY --from=debug /out/ordersvc /app/ordersvc
# note: in a single-stage debug image it can stay in /out
# simplified here — final is the same base with dlv on PATH

EXPOSE 2345 8080
# 6) 2345 = Delve; 8080 = app (documentation)

ENTRYPOINT ["/go/bin/dlv", "exec", "/out/ordersvc", "--listen=:2345", "--headless=true", "--api-version=2", "--accept-multiclient", "--continue", "--"]
# 7) dlv starts the app; --continue so it does not stop immediately at start
```

A more practical, clearer single-stage debug pattern:

```dockerfile
# syntax=docker/dockerfile:1
FROM golang:1.22.5-alpine
WORKDIR /src
RUN apk add --no-cache git ca-certificates \
 && go install github.com/go-delve/delve/cmd/dlv@v1.22.1
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -gcflags="all=-N -l" -o /app/ordersvc ./cmd/ordersvc
EXPOSE 8080 2345
ENTRYPOINT ["dlv", "exec", "/app/ordersvc", "--listen=:2345", "--headless=true", "--api-version=2", "--accept-multiclient", "--continue", "--"]
```

This image is **large** and has a toolchain — that is why it is `ordersvc:debug`, not `ordersvc:1.2.3`.

### Delve port bound to localhost

```bash
docker run --rm -p 8080:8080 -p 127.0.0.1:2345:2345 ordersvc:debug
```

or Compose:

```yaml
services:
  api-debug:
    build:
      context: .
      dockerfile: Dockerfile.debug
    ports:
      - "8080:8080"
      - "127.0.0.1:2345:2345"
```

**Why `127.0.0.1:2345`?**  
So the Delve API is **not** reachable from other machines on the network. A debugger open on `0.0.0.0` is a remote code execution surface.

**Predict then answer:** Is `-p 2345:2345` without a bind address safe enough on shared Wi‑Fi?

**Answer:** No. On many setups publish goes to all network addresses (network interfaces). Use `127.0.0.1:2345:2345`.

### Why never Delve in production

1. **Attack surface** — headless Delve accepts clients; that is control over the process.
2. **Larger image** — toolchain + dlv + unoptimized binary.
3. **Heisenbug** — `-N -l` changes performance and sometimes timing behavior.
4. **Policy** — the prod tag must be the same class of artifacts that pass scan (08.05).

Same **source**, different **artifact tag**.

### Compose profiles: `api` vs `api-debug`

```yaml
services:
  api:
    build:
      context: .
      dockerfile: Dockerfile
    ports:
      - "8080:8080"
  api-debug:
    profiles: ["debug"]
    build:
      context: .
      dockerfile: Dockerfile.debug
    ports:
      - "8080:8080"
      - "127.0.0.1:2345:2345"
```

```bash
docker compose --profile debug up --build api-debug
```

### IDE attach (general flow)

1. Start `api-debug` with localhost publish on 2345.
2. In the IDE: “Attach to remote Delve” / host `127.0.0.1` port `2345`.
3. Set a breakpoint in source that matches the build (same commit).
4. Send an HTTP request → breakpoint.

Without source mapping (same files), breakpoint lines can miss — build from the same worktree.

### Maintaining logs — rotation

Default `json-file` can grow. In daemon or Compose logging options (where supported):

```yaml
logging:
  driver: json-file
  options:
    max-size: "10m"
    max-file: "3"
```

Without rotation, the host disk fills “mysteriously”.

### `docker inspect` and container state

```bash
docker inspect -f '{{.State.Status}} {{.State.ExitCode}} {{.State.Error}}' api
docker compose ps
```

Exit code ≠ 0 + restart loop → first logs, then health.

### Trace: restart loop

```text
1. api start
2. Ping DB fail (not healthy yet / wrong DSN)
3. log.Fatal → exit 1
4. restart policy brings the container up again
5. loop
6. docker compose logs --tail=50 api  → you see the same error N times
```

The symptom “Compose does not work” is often application fail-fast + restart.

### Predictive moments

1. **Q:** Prod image has `dlv` “just disabled” by an ENV flag. Safe?  
   **A:** No. The binary still exists; a config mistake or ENV compromise turns it on. Separate the image.

2. **Q:** Distroless prod — how do you `docker exec`?  
   **A:** Often you cannot. Rely on logs; for shell debug use a debug/Alpine variant locally.

3. **Q:** Does `-gcflags=all=-N -l` go into prod for “easier support”?  
   **A:** No. Use the debug tag when needed; prod stays optimized.

### Signals and graceful shutdown (maintenance)

Docker sends `SIGTERM` then after the grace period `SIGKILL`.

```go
ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
defer stop()
// server.Shutdown(ctx) pattern
```

Without graceful shutdown, deploy/restart cuts in-flight requests. That is not a Delve topic — but it is maintenance of a containerized Go service.

### `GOMEMLIMIT` example

```yaml
environment:
  GOMEMLIMIT: 450MiB
mem_limit: 512m
```

**What happens here:** the container hard limit is 512 MiB; Go GC aims below that to reduce OOM kill.

## Rules and syntax

- Logs first, then debugger.
- Delve only in `Dockerfile.debug` / `--target debug` / tag `:debug`.
- Never Delve, `-N -l`, or toolchain in the prod tag.
- Publish the Delve port as `127.0.0.1:2345:2345`.
- Log to stdout; rotate the logging driver.
- Set `restart` + healthcheck deliberately.
- `GOMEMLIMIT` with a memory limit.
- Do not use `DEBUG=true` to inject Delve into the same final stage for release.
- Name the Compose debug service explicitly (`api-debug`).

## Examples

### Example 1 — Incident: reading logs

```bash
docker compose ps
docker compose logs --tail=200 api
docker compose logs --since 20m db
curl -s -o /NUL -w "%{http_code}" http://127.0.0.1:8080/healthz
```

#### What happens here

You see whether the container is Up/Restarting, read the last messages, check health from outside. Often the problem is already in the log (`DATABASE_URL`, migrate, bind address).

### Example 2 — Debug image + localhost Delve

```bash
docker build -f Dockerfile.debug -t ordersvc:debug .
docker run --rm -p 8080:8080 -p 127.0.0.1:2345:2345 ordersvc:debug
```

#### What happens here

App listens on 8080, Delve on 2345 only on the host loopback. IDE attach → breakpoint.

### Example 3 — Anti-example: Delve in the prod Dockerfile

```dockerfile
# BAD
FROM golang:1.22.5-alpine AS build
# ... build with -N -l ...
FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /go/bin/dlv /dlv
COPY --from=build /out/app /app
ENTRYPOINT ["/dlv", "exec", "/app", "--listen=:2345", ...]
```

#### What happens here

Production gets a debugger. Even behind a firewall, this breaks the threat model. Fix: separate tag; prod ENTRYPOINT is only `/app`.

### Example 4 — Compose restart loop

```bash
docker compose ps
# api Restarting
docker compose logs --tail=30 api
# fatal: DATABASE_URL is required
```

#### What happens here

Restart is not a “Docker bug” — the application exits. Fix env, do not increase `retries` forever.

### Example 5 — Predict: breakpoint is not hit

Cause candidates:

- IDE looks at a different commit/path;
- image built with old code without `--build`;
- strip/`-s -w` in the “debug” image by mistake.

#### What happens here

Debugger and source must match. Rebuild the debug image from the current worktree.

### Example 6 — Logging rotation

```yaml
services:
  api:
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "5"
```

#### What happens here

The host does not keep an infinite json log. For log centralization use an external system — but rotation is the local minimum.

### Example 7 — Line-by-line: handling SIGTERM

```go
package main

import (
	"context"
	"log"
	"net/http"
	"os"
	"os/signal"
	"syscall"
	"time"
)

func main() {
	srv := &http.Server{Addr: ":8080", Handler: http.DefaultServeMux}
	http.HandleFunc("/healthz", func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
	})
	go func() {
		log.Println("listening")
		if err := srv.ListenAndServe(); err != nil && err != http.ErrServerClosed {
			log.Fatal(err)
		}
	}()
	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
	defer stop()
	<-ctx.Done()
	shutdownCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()
	_ = srv.Shutdown(shutdownCtx)
	log.Println("bye")
}
```

#### What happens here

On `docker stop` / Compose stop, the process gets SIGTERM, closes the listener, and finishes more cleanly. Maintenance of deploy without cutting every request.

### Example 8 — Comparing tags

```bash
docker images ordersvc:1.2.3 ordersvc:debug
docker run --rm ordersvc:1.2.3 true  # distroless: no true
```

#### What happens here

Size and content differ dramatically. That is desired. Registry policy: ban `:debug` in the prod namespace if you can.

## Decision analysis

| Decision | Choice | Why |
|----------|--------|-----|
| Where Delve lives | only `:debug` | security + heisenbug |
| Port publish | `127.0.0.1:2345` | not open on LAN |
| First incident step | logs | cheap, often enough |
| Restart policy | `unless-stopped` locally | less manual up/down |
| Strip in debug | no | Delve needs symbols |

## Trade-offs

- **Debug image is large and unsafe for prod** — that is why it is separate.
- **`-N -l` slows down** — OK for a debug session, not for a load test “on the debug tag”.
- **Distroless prod makes exec harder** — you gain security; you debug elsewhere.
- **More Dockerfiles** — a bit more maintenance, much clearer tags.
- **localhost bind** — debugger does not work from another machine without an SSH tunnel (that is intentional).

## Common mistakes

1. **Delve in the production image.**
2. **Publishing `2345` on `0.0.0.0`.**
3. **`-s -w` in the debug build.**
4. **Ignoring `docker logs` while jumping into the debugger.**
5. **Restart loop without reading the exit reason.**
6. **Logging to a file without volume/rotation.**
7. **Mixing prod and debug in the same tag via ENV magic.**
8. **Breakpoint on the wrong commit/source.**
9. **No healthcheck then “random” failures on deploy.**
10. **Memory limit without `GOMEMLIMIT` then frequent OOM.**

## Idiomatic Docker/Go

- stdout JSON/slog logs.
- Prod IMAGE = thin, stripped, nonroot, no Delve.
- Debug IMAGE = explicit, localhost Delve, `-N -l`.
- Graceful shutdown on SIGTERM.
- Health endpoint for probes.
- Compose profiles for the debug service.

## Practical scenario

Production: elevated latency. The team immediately asks “to put Delve into prod”. Instead: logs show a slow `Ping` to the database; health flapping; connection pool exhausted. The fix is pool + timeout, not a debugger in prod. Later, for a race in a development feature, a developer brings up `api-debug` with `127.0.0.1:2345`, finds a deadlock in 20 minutes. Registry-scanned images remain without `dlv`. Policy: CI fails if the prod Dockerfile contains the string `delve`.

### Debug session checklist

1. Same commit in IDE and image build.
2. Tag `:debug` (not prod).
3. Delve port on localhost.
4. App port publish if you test HTTP.
5. After the session: `compose down`, do not leave debug on a shared host.

### Extended mechanism: what Delve does in headless mode

```text
dlv exec /app/ordersvc --listen=:2345 --headless=true --api-version=2 --accept-multiclient --continue --
```

| Flag | Role |
|------|------|
| `exec` | run an existing binary under the debugger |
| `--listen=:2345` | API port inside the container |
| `--headless=true` | no interactive TUI; for IDE |
| `--api-version=2` | protocol the IDE expects |
| `--accept-multiclient` | multiple clients (optional) |
| `--continue` | do not stop immediately at start |
| `--` | separator; arguments after go to the application |

**Predict then answer:** If you forget `--continue`, what do you see?

**Answer:** The process stands until the debugger client sends continue — HTTP “does not work” until you attach.

### Line-by-line: Compose debug service (complete)

```yaml
services:
  api-debug:
    profiles: ["debug"]
    build:
      context: .
      dockerfile: Dockerfile.debug
    environment:
      ADDR: ":8080"
      DATABASE_URL: ${DATABASE_URL}
    ports:
      - "8080:8080"
      - "127.0.0.1:2345:2345"
    depends_on:
      db:
        condition: service_healthy
```

```bash
docker compose --profile debug up --build api-debug db
```

### Trace: from HTTP request to breakpoint

```text
1. IDE attach to 127.0.0.1:2345
2. Breakpoint on the handler line
3. curl localhost:8080/orders
4. Request enters the container
5. Delve stops the goroutine at the breakpoint
6. IDE shows variables
7. Continue → response reaches the client
```

### Maintenance: what to do when host disk disappears

```bash
docker system df
docker compose logs --tail=1 api   # is the log growing?
```

Often: json-file logs without `max-size`. Add logging options (Example 6). Do not delete volumes blindly (`down -v`) until you know what you lose.

### Predict: prod container “healthy”, but users see 500

**A:** Health only checks process/up — not a business dependency. Extend `/healthz` to ping the DB (caution: deep health vs liveness). In K8s often split liveness and readiness; locally Compose keeps it simpler.

### Table: tool by diagnostics layer

| Layer | Tool | When |
|-------|------|------|
| stdout | `docker logs` | always first |
| status | `compose ps` / `inspect` | restart loop |
| HTTP | `curl /healthz` | from outside |
| resources | `docker stats` | CPU/mem |
| code | Delve `:debug` | last, locally |

### Anti-pattern: `docker exec` in production as the standard

If you need a shell in prod to “fix it”, the process is wrong: you lack logs, lack metrics, or the image is not reproducible. Go back to logs and a debug image locally.

### Mini lab: compare two sessions

1. Session A: only logs + fix DSN — 5 minutes.
2. Session B: Delve immediately without logs — an hour.

Write in the team notes: the diagnostics hierarchy saves time.

### Trace: `docker stats` during a memory problem

```bash
docker stats --no-stream
```

If `MEM USAGE` goes to the limit and the container disappears, look for OOM. Set `mem_limit` + `GOMEMLIMIT`. Delve does not help first here — logs + stats help.

### Predict: does `profiles: ["debug"]` prevent accidental `up` of the debug service?

**A:** Yes, default `docker compose up` does not start profile services until you specify `--profile debug`. That is intentional protection.

### Line-by-line: slog with request_id (diagnostics)

```go
func withRequestID(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		id := r.Header.Get("X-Request-ID")
		if id == "" {
			id = "local-" + strconv.FormatInt(time.Now().UnixNano(), 36)
		}
		slog.Info("request", "id", id, "path", r.URL.Path, "method", r.Method)
		next.ServeHTTP(w, r)
	})
}
```

In container logs you filter by `id` — faster than Delve for many incidents.

### Maintenance: `start_period` vs false unhealthy

If the app takes 15s to start (migrations), a healthcheck without `start_period` marks unhealthy too early and confuses `depends_on`. Set `start_period` realistically.

### Checklist after a debug session

1. Stop `api-debug`.
2. Do not push `:debug` to the prod registry.
3. Return to the prod Dockerfile for CI.
4. If you found a bug — unit test + fix, not “just a breakpoint”.

### Final predict: may staging use the `:debug` image “because it is easier”?

**A:** Not as the default. Staging should resemble prod (same Dockerfile target). Debug remains a local profile. Otherwise heisenbugs “works in staging debug, crashes in prod”.

### One sentence of discipline

“Logs first; Delve locally on localhost; never in the prod tag.”

### Last reminder before CI

Locally you know: logs → health → debug image. CI (08.05) will not run Delve — CI wants test + scan. The debugger remains a human, local tool.

## Summary

Containerized Go is first diagnosed with logs (`docker logs` / Compose), then health/restart/resource signals. Delve lives exclusively in a debug image, with the port bound to localhost, without `-s -w`, with `-N -l`. The production tag stays thin and without a debugger. Maintenance covers restart policy, healthcheck, log rotation, `GOMEMLIMIT`, and graceful SIGTERM.
