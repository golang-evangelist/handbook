# 08.05 Integrating a Go application with CI/CD pipelines

> **Go Path - Zero to Gopher** / **03 Others → Developing Go Apps with Docker** / Lesson 08.05

## Lesson goals

After this lesson you should be able to:

- sketch a GitHub Actions flow: `go test` → build image → scan → (conditional) push
- understand the difference between a **tag** (`ordersvc:1.2.0`) and a **digest** (`ordersvc@sha256:...`)
- connect Go module cache and Docker/Buildx cache for faster pipelines
- insert image scanning (e.g. Trivy) as a gate before publish
- separate PR checks from release publish
- avoid classic CI traps: secrets in the log, only `latest`, build without tests, baking secrets into the image

## Prerequisite

- Lessons 08.01–08.04 (Dockerfile, multi-stage, Compose, debug separate from prod)
- A GitHub repo or understanding of analogous CI systems (job, step, secret, artifact)
- Go 1.22+, Docker Buildx

## Problem this lesson solves

Locally “works on my laptop” is not delivery. Without CI:

- tests are skipped before merge;
- the image is built manually with different Docker versions;
- the registry gets tags without an audit trail;
- CVEs are discovered only in production;
- nobody knows which **digest** exactly runs in the cluster.

CI/CD for Go + Docker is not special magic — it is **automated discipline**: the same command every time, with proof (test exit code, scan report, digest).

## Mental model

Pipeline as filters in a sequence:

```text
Checkout (exact commit SHA)
    → go test ./...          (proof that the code passes)
    → docker buildx build    (reproducible image)
    → scan                   (CVE / misconfig gate)
    → push (main/tag only)   (registry artifact)
    → deploy pins digest     (not floating latest)
```

PR branch: steps through scan, **without** push to the prod registry (or push to a `pr-123` tag).  
Release / main: goes through to push.  
Deploy manifest in production: `image@sha256:...`, not only `:latest`.

## Mechanism

### Why `go test` before the image build

Image build is more expensive and slower than unit tests. If tests fail, there is no point spending minutes on Buildx and the registry.

```yaml
- name: Test
  run: go test ./...
```

Extensions (by team agreement; all are real `go` commands):

```text
go test ./... -count=1
go test ./... -race
go vet ./...
```

`-race` is slower; often on main, not on every PR commit. Do not invent flags — use documented ones.

**Trace:** A PR changes only the README. CI still runs `go test` — cheap and keeps discipline. A PR changes SQL in a store package and breaks a test — the image build does not happen because the job stops. That is desired.

### Tag versus digest

| Concept | Example | Stability |
|---------|---------|-----------|
| Tag | `ghcr.io/acme/ordersvc:1.2.0` | **movable** — someone can push over the same tag |
| Digest | `ghcr.io/acme/ordersvc@sha256:abc...` | **immutable** content of that byte sequence |

A tag is human. A digest is the contract for production. CI can push tag `1.2.0` **and** record the digest in an artifact / release notes. Deploy uses the digest.

**Predict then answer:** You push `ordersvc:1.2.0` on Monday (digest `aaa`). On Wednesday someone force-pushes the same tag with different code (digest `bbb`). A cluster that pulls `:1.2.0` without a digest — what does it get after a new pull?

**Answer:** the new content (`bbb`). That is why production pins the digest or uses an immutable tag policy + digest verify.

### GitHub Actions — minimal skeleton (real actions)

We do not invent APIs. We use common actions:

```yaml
name: ci

on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read
  packages: write

jobs:
  test-and-build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-go@v5
        with:
          go-version: "1.22.x"
          cache: true

      - name: Test
        run: go test ./...

      - uses: docker/setup-buildx-action@v3

      - uses: docker/login-action@v3
        if: github.event_name == 'push' && github.ref == 'refs/heads/main'
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Build (PR — no push)
        if: github.event_name == 'pull_request'
        uses: docker/build-push-action@v6
        with:
          context: .
          push: false
          load: true
          tags: ordersvc:ci
          cache-from: type=gha
          cache-to: type=gha,mode=max

      - name: Build and push (main)
        if: github.event_name == 'push' && github.ref == 'refs/heads/main'
        uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: |
            ghcr.io/${{ github.repository }}/ordersvc:latest
            ghcr.io/${{ github.repository }}/ordersvc:${{ github.sha }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
```

#### What happens here

- `setup-go` with `cache: true` caches module download between runs.
- `go test ./...` gate before Docker.
- PR: `push: false` — only proof that the image builds.
- main: push with tag `latest` **and** `github.sha` (immutable-ish reference to the commit).
- Buildx GHA cache speeds up layers.

Better production practice: semver tag on `git tag`, do not rely only on `latest`.

### Scan as a gate

Example with Trivy (common tool; CLI is real):

```yaml
- name: Scan image
  run: |
    docker run --rm -v /var/run/docker.sock:/var/run/docker.sock \
      aquasec/trivy:latest image --exit-code 1 --severity HIGH,CRITICAL ordersvc:ci
```

`--exit-code 1` fails the job if it finds HIGH/CRITICAL. The team can choose the severity threshold. Important: scan **before** push to the prod registry, or right after the local build in CI.

### Caching — two levels

1. **Go modules:** `setup-go` cache or `actions/cache` on `~/go/pkg/mod`.
2. **Docker layers / Buildx:** `cache-from` / `cache-to` of type `gha` or registry cache.

Without cache: every PR downloads modules and the golang base from scratch — slow and expensive.

**Trace with numbers:** first run 8 min, second run with cache 2.5 min. If the second run is still 8 min, the cache was not hit (wrong key, `Dockerfile` COPY order breaks layer cache — go back to 08.01).

### Secrets in CI

- `GITHUB_TOKEN` / registry password: only in `secrets`, never in YAML plain text.
- Do not `echo` a secret into the log.
- Do not pass a secret as a `build-arg` that remains in the image (08.02).
- For private Go modules: `GOPRIVATE` + token via env in the `go test` / build step, not `ENV` in the Dockerfile final stage.

### Multi-platform in CI

Real flags:

```yaml
with:
  platforms: linux/amd64,linux/arm64
  push: true
```

On a PR with `load: true` usually **one** platform (e.g. `linux/amd64`), because `--load` does not carry a multi-manifest as a local daemon image. Multi-platform + push on the release job.

### Predict then answer: step order

Pipeline proposed like this:

1. build image  
2. push  
3. go test  
4. scan  

**What is wrong?** Test and scan after push mean a broken / vulnerable image already exists in the registry. Correct order: test → build → scan → push.

### Artifact: digest output

`docker/build-push-action` can export a digest (documented output). Save it:

```yaml
- id: build
  uses: docker/build-push-action@v6
  with:
    push: true
    tags: ghcr.io/acme/ordersvc:${{ github.sha }}

- name: Print digest
  run: echo "digest=${{ steps.build.outputs.digest }}"
```

The deploy job / release note uses that digest.

### Connection to Delve / debug image

CI does **not** push a debug image with Delve to the prod registry as the default tag. If a debug artifact is needed, a separate `*-debug` tag and a strict policy on who may pull it. The production job uses `--target runtime`.

### Lint and format (optional, real tools)

```text
gofmt -l .
go vet ./...
```

Or `golangci-lint` if the team adopts it — do not invent a linter API. Important: a lint error = failed job, not a warning everyone ignores.

### Matrix Go version (when it makes sense)

```yaml
strategy:
  matrix:
    go: ["1.22.x", "1.23.x"]
```

For libraries. For one service often one version pinned in `go.mod` and Dockerfile — less noise.

### Fail-fast discipline

| Event | CI reaction |
|-------|-------------|
| test fail | stop, no image |
| build fail | stop, no push |
| scan HIGH | stop (if it is a gate) |
| push fail | stop, alarm |
| docs-only change | still test (cheap) or path filter by agreement |

Path filters are OK for a monorepo, but dangerous if they skip tests for a shared `internal/` package.

### Detailed trace of one PR (concrete values)

Assume:

- commit `c0ffee` on branch `feature/pay`
- changes `internal/pay/provider.go` and `provider_test.go`
- Dockerfile unchanged

Flow:

1. `actions/checkout` clones SHA `c0ffee`.
2. `setup-go` — cache hit on modules (go.sum unchanged) → ~5 s instead of 40 s.
3. `go test ./...` — package `internal/pay` fails: expected status 402, got 500.
4. Job stops. Buildx does **not** start.
5. Developer sees a red X, reads test output, fixes, push `c0ffee2`.
6. Test passes. Buildx builds; layer `go mod download` CACHED; `go build` new.
7. Scan passes. Because it is a PR, `push: false` — registry untouched.

**Predict:** does GHCR have an image for this PR?  
**Answer:** no (under this policy). Only merge to main pushes.

### Second trace: main push after merge

1. Merge commit `deadbeef` on `main`.
2. Test OK, build OK, scan OK.
3. Push tags: `:latest` and `:deadbeef`.
4. Output digest `sha256:1111...`.
5. CD system (outside this lesson) updates the manifest to `@sha256:1111...`.
6. Tomorrow someone manually pushes `:latest` from a laptop — the cluster **does not** change behavior because it pins the digest.

That is the point of the digest.

### What CI must know about multi-stage

CI does not “guess” the stage. Explicitly:

```yaml
with:
  target: runtime
```

or a Dockerfile where runtime is the last stage and debug is not accidentally below it. Review checklist: “can the debug stage become the default?”

### go test in a container vs on the runner

Two schools:

| Approach | Advantage | Drawback |
|----------|-----------|----------|
| `go test` on the runner (setup-go) | fast, simple | OS difference vs image |
| `go test` in a `golang` container | closer to build environment | slower, more complex |

For most services: test on the runner + build the same code in the Dockerfile is enough. Integration tests with a database: Compose in CI or testcontainers (09.03) — do not invent an API.

### Permission model on GitHub

```yaml
permissions:
  contents: read
  packages: write
```

Smallest set. `packages: write` is needed for GHCR push. Do not grant `write-all` “just in case”.

### Predict then answer: cache poison?

**Question:** Can Buildx GHA cache “hide” a broken Dockerfile step?

**Answer:** Cache returns the previous result for the same input hash. If you change a Dockerfile instruction, the hash changes and you get a cache miss. A more dangerous scenario is a wrong `COPY` order that caches stale modules while you think they are fresh — that is why 08.01 insists on `go.mod`/`go.sum` first. Periodic `cache: false` or a weekly clean helps confidence.

### CI checklist before you declare “done”

1. `go test ./...` exists and fails the job
2. Build uses the same Dockerfile as local
3. `--target runtime` or a safe last stage
4. PR does not push the prod tag
5. main/release pushes a tag + records the digest
6. Scan gate agreed (severity)
7. Secrets only from GitHub Secrets
8. README: local equivalent of the commands

## Rules and syntax

- Always `go test ./...` (or a narrower package scope with a reason) before publish.
- Tag + digest: humans read the tag, machines pin the digest.
- PR does not push to the prod tag without a review policy.
- Do not bake secrets into the image; CI secrets ≠ Dockerfile `ENV`.
- Cache Go modules and Buildx layers.
- Scan before or right with the build, before the artifact becomes “truth”.
- Pin action versions (`@v4`, `@v5`) — not `@main` for supply-chain peace.
- Dockerfile in CI same as local (or same `--target runtime`).

## Examples

### Example 1 — Test-only job (first team step)

```yaml
name: test
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version-file: go.mod
          cache: true
      - run: go test ./...
```

#### What happens here

The smallest useful CI. No Docker yet, but it already kills regressions. Add build when tests exist and pass.

### Example 2 — Build without push on PR

See the skeleton in the Mechanism section (`push: false`, `load: true`). Goal: proof that the Dockerfile is not broken.

### Example 3 — Push with a commit SHA tag

```text
ghcr.io/acme/ordersvc:a1b2c3d4e5f6...
```

#### What happens here

Every main commit = a new tag. Rollback = previous SHA. Easier than “who moved `latest`”.

### Example 4 — Local CI simulation

```text
go test ./...
docker buildx build --target runtime -t ordersvc:ci --load .
docker run --rm ordersvc:ci # or curl health if it is a server
```

#### What happens here

The same commands as CI. If it passes locally and CI fails, look at Go/Docker versions and secrets, not “CI is broken”.

### Example 5 — Semver release (sketch)

```yaml
on:
  push:
    tags: ["v*"]
```

Tag `v1.4.2` → image `ordersvc:1.4.2` + digest in the GitHub Release body.

### Example 6 — Why `latest` is not enough

```text
# BAD as the only identifier in prod
image: ghcr.io/acme/ordersvc:latest

# BETTER
image: ghcr.io/acme/ordersvc@sha256:0123abcd...
```

#### What happens here

Digest locks the bytes. `latest` is a pointer that moves.

## Decision analysis

| Decision | Choose when | Cost |
|----------|-------------|------|
| SHA tag | continuous deploy | many tags in the registry |
| Semver tag | controlled release | tagging discipline |
| Scan soft-fail | ramp-up | risk of being ignored |
| Scan hard-fail | mature | false positives slow you down |
| Multi-platform on every PR | heterogeneous fleet | slower PRs |
| Multi-platform only on release | CI savings | platform bug later |

## Trade-offs

- **Speed vs coverage:** `-race` on every PR vs a nightly job.
- **`latest` convenience vs audit:** handy locally; dangerous in prod.
- **Cache vs determinism:** cache speeds up; rarely masks “works only with cache” — a periodic build without cache helps.
- **Monorepo path filters vs forgotten tests:** filters save minutes; easy to skip a critical package.

## Common mistakes

1. **Wrong:** push image then only then `go test`.  
   **Effect:** broken artifact in the registry.  
   **Why:** wrong gate order.  
   **Fix:** test → build → scan → push.

2. **Wrong:** only tag `latest` in the Kubernetes manifest.  
   **Effect:** unclear rollback, silent code swap.  
   **Why:** tag is movable.  
   **Fix:** pin digest or immutable semver + digest.

3. **Wrong:** `echo ${{ secrets.REG_TOKEN }}` in the log.  
   **Effect:** secret leak.  
   **Why:** logs are often more widely readable.  
   **Fix:** never print secrets.

4. **Wrong:** CI builds without `--target runtime` while the last stage is debug.  
   **Effect:** Delve in the “prod” image.  
   **Why:** wrong stage.  
   **Fix:** explicit target.

5. **Wrong:** no cache; every PR 10+ min.  
   **Effect:** the team bypasses CI.  
   **Why:** friction.  
   **Fix:** setup-go cache + buildx gha cache.

6. **Wrong:** scan only once a year manually.  
   **Effect:** CVE in production for weeks.  
   **Why:** not a gate.  
   **Fix:** scan in the pipeline.

7. **Wrong:** different Dockerfile locally and in CI.  
   **Effect:** “works on my machine”.  
   **Why:** divergence.  
   **Fix:** one Dockerfile, same flags.

8. **Wrong:** build-arg with a production password.  
   **Effect:** secret in a layer.  
   **Why:** same mistake as 08.02.  
   **Fix:** runtime secrets.

## Idiomatic Go / CI

- `go test ./...` as the default package scope.
- Go version in CI = `go.mod` / Dockerfile.
- Commit SHA in the image tag for traceability.
- Structured log in the application eases CI smoke (`curl /healthz`).
- Do not commit `.env`; CI uses GitHub Secrets.
- README: “how to reproduce CI locally”.

## Practical scenario

The team merged to main on Friday. Image `:latest` went to EKS. Saturday: incident. Nobody knows which commit is in `latest` because the tag was overwritten two more times.

Fix:

1. Tag `:${{ github.sha }}` on every main build.
2. Deploy pin to the digest from the Actions output.
3. `go test` + Trivy hard-fail for CRITICAL.
4. PR no longer pushes to the same registry namespace as prod.

After a month: MTTD for a bad deploy dropped; rollback = previous digest in Helm values. Second win: cache cut PRs from 9 min to 3 — less “skip CI” pressure.

Incident #2: a junior inserted a `printf` debug with an API key in a test helper. CI logs public to the org. Key rotation. Rule: secret scanning (GitHub) + code review checklist.

## Check questions

1. **Why test before build?**  
   Cheaper fail; you do not spend Buildx/registry on broken code.

2. **What is a digest?**  
   An immutable `sha256` reference to the image content.

3. **Why is `latest` not enough in prod?**  
   The tag is movable; there is no audit of what exactly runs.

4. **What does `push: false` on a PR do?**  
   Builds the image for verification, does not publish it to the registry (in that configuration).

5. **Which two caches speed up CI?**  
   Go module cache and Docker/Buildx layer cache.

6. **Why not print secrets?**  
   Logs leak; rotation is expensive.

7. **Where may a Delve image be?**  
   A separate debug tag, not prod publish.

8. **What is a healthy order?**  
   test → build → scan → push.

When CI is “flaky”, first turn off the cache and check whether flakiness remains. When deploy “mysteriously” changes behavior, check whether the manifest pulls a tag instead of a digest.

The pipeline is the document of truth: if it is not in CI, it is not part of the definition of done. A local hero build is not a substitute.

### Extra mechanism: from commit to digest (end-to-end trace)

Concrete values:

1. Developer merges a PR; main SHA = `f00dcafe`.
2. CI: `go test ./...` — 142 tests, 0 fail, 18.2 s.
3. `docker buildx build --target runtime -t ghcr.io/acme/ordersvc:f00dcafe --push`.
4. Scan: 0 CRITICAL, 1 HIGH in the base image — team agreed a waive with ticket #441.
5. Action output digest = `sha256:9f2c…`.
6. CD updates Helm values: `image.digest: sha256:9f2c…`.
7. Three pods restarted; `kubectl describe` shows the same digest.
8. Five days later someone pushes `:latest` manually — the cluster **does not** change because it does not pull `latest`.

Remember this trace: CI is not a “build script”, but a chain of proof.

### What to put in Release notes

- Git tag / SHA
- Image tag
- Image digest
- Go version (`go version` in the CI log)
- Scan result (brief)

Without a digest in the notes, rollback becomes archaeology.

### Local preflight before the push button

```text
go test ./...
docker build --target runtime -t ordersvc:local .
docker run --rm -p 8080:8080 -e ADDR=:8080 ordersvc:local
curl -sf http://127.0.0.1:8080/healthz
```

If this does not pass, CI will not “fix” it by magic.

### Predict then answer: matrix and Dockerfile

**Question:** The matrix tests Go 1.22 and 1.23, but the Dockerfile has `FROM golang:1.22.5-alpine`. Is that a problem?

**Answer:** Test on the runner ≠ compiler in the image. The application in prod is compiled with the Go version from the Dockerfile. A matrix on a library makes sense; for one service align `go.mod` and Dockerfile, and use a matrix optionally only for library compatibility.

### Tag policy — mini RFC for the team

Proposed text for CONTRIBUTING:

1. CI on `main` pushes `:sha-<short>` and a digest artifact.
2. Git tag `vX.Y.Z` pushes `:X.Y.Z`.
3. People do not push to the `prod/` namespace.
4. Deploy pins the digest from CI.
5. `:latest` only in the `demo/` namespace.

### More on scan false positives

Scan finds a CVE in a package that your scratch image **does not have**. Cause: you scan the builder stage or the wrong tag. Always scan the **runtime** tag you deploy. If the tool scans multi-stage wrongly, explicitly specify the runtime image ID.

### Link 08.04 and 08.05

A debug image with Delve does **not** pass the same release gate as prod. A separate workflow or an `if` that never tags debug as `v*`. Otherwise someone “temporarily” debugs prod.

### Workbook: first green pipeline

1. Add `.github/workflows/ci.yml` with checkout + setup-go + `go test ./...`.
2. Confirm a green run on a PR.
3. Add buildx + build-push `push: false` on PR.
4. Confirm that a Dockerfile error fails the job.
5. On main add login + push SHA tag.
6. Insert Trivy with exit-code 1; temporarily lower severity if you need to learn the log, then restore HIGH.
7. Save the digest in the Step Summary.
8. Document the local equivalent in README.

### Trace: failed test output

```text
--- FAIL: TestPrice (0.00s)
    price_test.go:12: got 110 want 100
```

CI must show this log in the UI. If `go test` goes into Docker without `-v` and without a saved log, debug takes longer. Prefer visible test output.

### Predict then answer: concurrency of jobs

**Question:** Two jobs in parallel: `test` and `build`. Build succeeds, test fails. May it push?

**Answer:** Not if they are independent without `needs:`. Use `needs: [test]` on the build/push job so push waits for test.

```yaml
jobs:
  test:
    ...
  build:
    needs: [test]
    ...
```

### OIDC and cloud (mention)

Some registries/clouds use OIDC instead of long-lived secrets. If you introduce that, read the cloud docs — do not bake static keys. Same principle: short-lived credentials.

### Flaky test policy

A flaky test that “sometimes fails” destroys trust in CI. Treat as P0: isolate, fix, or remove with a ticket. Do not spread `continue-on-error` as culture.

## Summary

CI for Go + Docker joins `go test`, a reproducible `buildx` build, scanning, and conditional push. A tag is for people; a digest is for production. Cache speeds up; secrets go neither into the log nor into the image. PR proves; main/release publishes. Gate order is part of security.
