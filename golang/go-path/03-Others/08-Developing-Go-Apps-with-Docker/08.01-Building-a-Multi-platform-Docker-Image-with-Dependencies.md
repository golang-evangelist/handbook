# 08.01 Building a multi-platform Docker image with Go dependencies

> **Go Path - Zero to Gopher** / **03 Others → Developing Go Apps with Docker** / Lesson 08.01

## Lesson goals

After this lesson you should be able to:

- explain why a Go binary with `CGO_ENABLED=0` and `GOOS=linux` can run in a distroless or scratch-ish runtime image
- write a Dockerfile that first copies `go.mod` and `go.sum`, runs `go mod download`, and only then copies the source code
- run `docker buildx build` with the real flag `--platform linux/amd64,linux/arm64`
- understand that `EXPOSE` does not publish a port on the host — that is done by `-p` / Compose `ports`
- choose a base image deliberately: Alpine, distroless, or scratch — and explain the cost of each choice
- pin base image versions and module dependencies so the build is predictable

## Prerequisite

- Go 1.22+ locally (`go version`)
- Docker Desktop or Docker Engine with Buildx (`docker buildx version`)
- basic `go mod init`, `go build`, understanding of `GOOS` / `GOARCH`
- preferably: a small HTTP service in `./cmd/app` that listens on port 8080

If `buildx` is not active, create a builder:

```text
docker buildx create --use --name multiarch
```

On Windows, work through Docker Desktop. Emulation for `linux/arm64` on an `amd64` host (and vice versa) can be slower, but is enough for learning.

## Problem this lesson solves

Go produces a statically linked binary — often enough for deployment. Still, teams package applications in containers because orchestration, networking, secrets, health probes, and CI expect an **image**, not a “raw” file on disk.

The problem appears when:

- the image only works on `amd64`, while the laptop or cloud node is `arm64` (Apple Silicon, Graviton);
- `go build` in Docker re-downloads all modules on every code change;
- the base image pulls in a shell, package manager, and thousands of files that production does not need;
- dependencies are not pinned, so the build pulls an unexpected version;
- someone thinks `EXPOSE 8080` “opens” the port on the laptop — and the container is not reachable from the host.

This lesson solves the first step: **the same Dockerfile, multiple platforms, predictable dependencies, a clear reason why scratch/distroless works for Go**.

## Mental model

Imagine three layers:

```text
1. Source code + go.mod / go.sum     → version contract
2. Build environment (golang image)  → compiler + toolchain
3. Runtime environment (Alpine /     → filesystem + your binary
   distroless / scratch)               (+ CA certificates if HTTPS is needed)
```

**Multi-platform build** means: for each target architecture Buildx runs a build (natively or through emulation) and merges the results into a **manifest list** (index). A client that pulls the image picks the platform that matches the host.

**Dependency caching** works like this:

```text
COPY go.mod go.sum ./     → layer A
RUN go mod download       → layer B (cached until go.mod/go.sum change)
COPY . .                  → layer C (changes often)
RUN go build ...          → layer D
```

Changing a `.go` file invalidates C and D, but **not** A and B. That is why modules first, then code.

**Why Go fits scratch/distroless:** with `CGO_ENABLED=0` the compiler does not link C libraries. The binary is (almost) fully static. It does not need Debian’s `libc`, nor `apk`. It only needs kernel syscalls — and optionally a CA bundle if the application calls HTTPS APIs.

## Mechanism

This section is the heart of the lesson. Read slowly: every subsection has concrete values you can predict before running anything.

### Why `CGO_ENABLED=0` and `GOOS=linux`

By default, on a Linux host `go build` may enable CGO if it finds a C compiler. CGO means dynamic linking against `libc` — so a scratch image **crashes** with an error like “not found” / “no such file” because there are no shared libraries.

Explicitly:

```text
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -o app ./cmd/app
```

means:

| Variable | Value | Effect |
|----------|-------|--------|
| `CGO_ENABLED` | `0` | pure Go, static link |
| `GOOS` | `linux` | Linux binary (even if you build on Windows/macOS) |
| `GOARCH` | `amd64` or `arm64` | CPU architecture |

**Trace with concrete values:** on a Windows laptop you run `GOOS=linux GOARCH=arm64 CGO_ENABLED=0 go build -o app`. You get an ELF binary for Linux ARM64. That file **cannot** run on Windows (`app.exe` it is not), but **can** run in a `linux/arm64` container.

### Why Alpine, distroless, or scratch

- **`golang:1.22.5-alpine`**: small build image, has `apk`, suitable for compilation. Musl instead of glibc — for pure Go without CGO that is usually not a problem.
- **`alpine:3.20`**: small runtime with a shell — convenient for `docker exec` and debugging.
- **`gcr.io/distroless/static-debian12`**: runtime without a shell. Smaller attack surface.
- **`scratch`**: empty filesystem. Only what you `COPY`. Thinnest, strictest.

If the application makes HTTPS client calls, it needs a CA certificate bundle. On Alpine: `apk add ca-certificates`. On distroless static it often already exists; on scratch you must copy it explicitly from the build stage.

### Module download as a cache layer

`go mod download` reads `go.mod` / `go.sum` and fills the module cache. It **does not compile** your code. That is why it is an ideal candidate for an earlier Docker layer.

Proxy: default is `proxy.golang.org`. In an air-gapped environment set `GOPROXY` and `GOSUMDB` explicitly in a Dockerfile `ENV` or build arg.

**Predict then verify:** you have a `go.mod` with 12 dependencies. You change only `main.go` (one `fmt.Println`). Which Docker layers rebuild?

**Answer:** the `COPY . .` layer and the `go build` layer. The `go mod download` layer stays from cache — because `go.mod` and `go.sum` were not touched.

### Buildx and `TARGETOS` / `TARGETARCH`

BuildKit automatically passes ARGs for the target platform. In the Dockerfile:

```dockerfile
ARG TARGETOS
ARG TARGETARCH
RUN CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH \
    go build -o /out/app ./cmd/app
```

Without that, `go build` in the container may compile for the **build node** architecture, not for the `--platform` target. Classic: build on Apple Silicon, image labeled as `amd64`, container on EC2 throws `exec format error`.

### The real multi-platform invocation

Only real flags — do not invent any:

```text
docker buildx build \
  --platform linux/amd64,linux/arm64 \
  -t registry.example/ordersvc:1.0.0 \
  --push .
```

What each part does:

| Part | Meaning |
|------|---------|
| `buildx build` | BuildKit builder, not the old legacy builder |
| `--platform linux/amd64,linux/arm64` | two architectures in one manifest list |
| `-t ...` | image tag |
| `--push` | sends to the registry (needed for multi-platform in most setups) |
| `.` | build context (current directory) |

`--load` loads the image into the local Docker daemon — but **only for one** platform at a time. For two platforms you usually `--push`, or `--output type=oci`.

### `EXPOSE` is not publish

```dockerfile
EXPOSE 8080
```

That is **documentation** for the Dockerfile reader and for some tools. It does not open a port on the host. To hit the container from your laptop:

```text
docker run -p 8080:8080 ordersvc:1.0.0
```

`-p host:container` maps. Without `-p`, the process in the container listens on 8080 **inside** the container network, but the host does not see that port.

### Trace: what happens during the build (concrete values)

Assume:

- module: `example.com/ordersvc`
- `go.mod` requires `github.com/gin-gonic/gin v1.10.0`
- files: `cmd/app/main.go`, `internal/...`
- platforms: `linux/amd64` and `linux/arm64`

Step by step for amd64:

1. BuildKit creates stage `build` from `golang:1.22.5-alpine`.
2. `WORKDIR /src` — working directory in the container.
3. `COPY go.mod go.sum ./` — only two files; layer ~kilobytes.
4. `RUN go mod download` — downloads gin and transitive modules into `/go/pkg/mod`.
5. `COPY . .` — whole context (respect `.dockerignore`!).
6. `ARG TARGETOS` = `linux`, `TARGETARCH` = `amd64`.
7. `go build` produces `/out/ordersvc` (ELF amd64, static).
8. Runtime stage: `COPY --from=build /out/ordersvc /app/ordersvc`.
9. The same repeats for `arm64`.
10. The registry gets a manifest list that points to both digests.

### `.dockerignore` — why it is part of the mechanism

Without `.dockerignore`, `COPY . .` sends `.git`, local binaries, `tmp/`, maybe even a `.env` with secrets into the build context. That:

- slows context upload;
- breaks the cache (every commit changes `.git`);
- risks leaking secrets into image history.

Minimal `.dockerignore`:

```text
.git
bin
tmp
*.exe
.env
.env.*
coverage.out
```

### Pinning versions

Bad:

```dockerfile
FROM golang:latest
```

Better:

```dockerfile
FROM golang:1.22.5-alpine
```

Even better in CI: a digest (`golang:1.22.5-alpine@sha256:...`) when you want byte-for-byte reproducibility. For learning, a patch tag is a sufficient step up from `latest`.

### Predict then answer: exec format error

**Scenario:** Dockerfile without `GOOS`/`GOARCH`. Buildx `--platform linux/amd64` on an M2 Mac. The image “successfully” builds. On EC2 `amd64` the container dies immediately.

**What do you predict?** The binary was compiled for `arm64` (the host architecture inside the emulation/build node was not aligned with the target because you did not pass TARGETARCH).

**Fix:** always:

```dockerfile
ARG TARGETOS
ARG TARGETARCH
RUN CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH go build -o /out/app ./cmd/app
```

### HTTPS and CA certificates in a thinner image

If `ordersvc` calls Stripe or another HTTPS API:

```dockerfile
FROM alpine:3.20
RUN apk add --no-cache ca-certificates tzdata
COPY --from=build /out/ordersvc /app/ordersvc
```

Without `ca-certificates`, the Go TLS client does not trust public CAs — you get a certificate verification error. That is not a “bug in Go”; the filesystem has no bundle.

### Non-root user (introduction)

Already in this lesson you can:

```dockerfile
RUN adduser -D -H -u 10001 appuser
USER appuser
```

Optimization details and `-ldflags` go in 08.02; here remember: a production container should not run as UID 0 without a reason.

### Build context vs image layer — two different costs

People mix up two concepts:

1. **Build context** — the archive/files the Docker client sends to the daemon/BuildKit. Context size affects time *before* the first `RUN`.
2. **Image layer** — the result of instructions in the Dockerfile. Layer size affects pull, scanning, and storage in the registry.

Example with numbers:

| Item | Size | Where it hurts |
|------|------|----------------|
| `.git` in the context | 180 MB | slow context upload every time |
| `golang` toolchain in the final image | 300+ MB | slow pull on nodes |
| your static binary | 12 MB | acceptable |
| CA bundle | ~200 KB | negligible |

So `.dockerignore` solves the context, and multi-stage solves the final image. Both are needed.

### What `go.sum` guarantees (and what it does not)

`go.sum` stores cryptographic checksums of module contents. When you run `go mod download` in Docker with the same `go.mod` + `go.sum`, you get the **same** dependency sources (with a correct `GOPROXY`/`GOSUMDB`).

`go.sum` does **not** guarantee:

- the same base OS packages in an Alpine image (that is why you pin the base image tag/digest);
- the same BuildKit version;
- the same QEMU result under emulation (rarely matters, but it exists).

For Go code and the module graph — `go.sum` is the contract. Always commit it.

### Line-by-line: why `WORKDIR` before `COPY`

```dockerfile
WORKDIR /src
COPY go.mod go.sum ./
```

`COPY ... ./` uses the current `WORKDIR`. Without `WORKDIR`, you copy into `/` and easily make a mess (`/go.mod` at the filesystem root). Idiom: set the working directory, then relative `COPY`.

### Predict then answer: do you need `git` in the build image?

**Question:** The Dockerfile has `RUN apk add --no-cache git` before `go mod download`. Is `git` always necessary?

**Answer:** Not always. For modules from the proxy (`proxy.golang.org`) `git` is often not needed. It is needed when a dependency comes directly from a VCS path that the toolchain clones, or when you use certain `replace` / private module flows. If the build works without `git`, remove it — smaller build layer and fewer packages to scan in the build stage (the build stage is not shipped, but it still affects time and the build machine supply chain).

### Private modules (briefly, without invented flags)

If `go.mod` pulls a private GitHub module, the Docker build must authenticate. Typical real approaches:

- BuildKit secret mount for `netrc` or SSH (syntax `RUN --mount=type=secret,...`);
- `GOPRIVATE` env to skip the public checksum DB where needed;
- pre-vendoring (`vendor/`) in CI when policy allows.

Do not bake a Personal Access Token into `ENV` in the Dockerfile. A token in layer history is an incident.

### How to read `docker build` output as a trace

When BuildKit prints:

```text
=> CACHED [build 3/6] COPY go.mod go.sum ./
=> CACHED [build 4/6] RUN go mod download
=> [build 5/6] COPY . .
=> [build 6/6] RUN CGO_ENABLED=0 ...
```

Reading: modules are cached; code and link are new. That is the **desired** pattern after changing only `.go` files.

When you see that even `go mod download` is not CACHED after changing a comment in `main.go`, the order in the Dockerfile is wrong or the context sends something that changes earlier layers (e.g. `COPY . .` too early).

## Rules and syntax

- Pin major.minor.patch base image tags (`golang:1.22.5-alpine`), not just `latest`.
- Always copy `go.sum` along with `go.mod` before `go mod download`.
- For a pure Go server: `CGO_ENABLED=0` — static binary, easier move to scratch/distroless.
- Multi-platform: explicit `GOOS`/`GOARCH` via `$TARGETOS`/`$TARGETARCH`.
- `EXPOSE` is documentation; publish is `-p` or Compose `ports`.
- Do not mix `ADD` with URLs and unchecked archives; `COPY` is more predictable.
- Do not bake secrets (`ENV DB_PASSWORD=...`) into the image — configuration goes through env at runtime (12-factor).
- Use `.dockerignore` so the context does not pull `.git` and local artifacts.
- `--load` = one platform locally; multi-platform usually `--push`.

Minimal naming patterns:

| Layer | Typical image | Role |
|-------|---------------|------|
| build | `golang:1.22.5-alpine` | compiler + modules |
| runtime Alpine | `alpine:3.20` | small Linux + shell |
| runtime distroless | `gcr.io/distroless/static-debian12` | no shell |
| runtime scratch | `scratch` | only your files |

## Examples

### Example 1 — Multi-platform Dockerfile (Alpine build + Alpine runtime)

```dockerfile
# syntax=docker/dockerfile:1

FROM golang:1.22.5-alpine AS build
WORKDIR /src

RUN apk add --no-cache git ca-certificates

COPY go.mod go.sum ./
RUN go mod download

COPY . .
ARG TARGETOS
ARG TARGETARCH
RUN CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH \
    go build -o /out/ordersvc ./cmd/ordersvc

FROM alpine:3.20
RUN apk add --no-cache ca-certificates tzdata \
    && adduser -D -H -u 10001 appuser
WORKDIR /app
COPY --from=build /out/ordersvc /app/ordersvc
USER appuser
EXPOSE 8080
ENTRYPOINT ["/app/ordersvc"]
```

#### What happens here

The build stage uses the Go toolchain on Alpine. First modules (cache layer), then compilation for the target OS/architecture that Buildx passes. The runtime stage is a thinner Alpine with CA certificates and a non-root user. The same file builds amd64 and arm64.

### Example 2 — Distroless runtime

```dockerfile
# syntax=docker/dockerfile:1

FROM golang:1.22.5-alpine AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
ARG TARGETOS
ARG TARGETARCH
RUN CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH \
    go build -ldflags="-s -w" -o /out/ordersvc ./cmd/ordersvc

FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /out/ordersvc /ordersvc
EXPOSE 8080
USER nonroot:nonroot
ENTRYPOINT ["/ordersvc"]
```

#### What happens here

No shell in the runtime. You cannot `docker exec ... sh`. Smaller attack surface. `-ldflags="-s -w"` strips the symbol table and DWARF — smaller binary (more detail in 08.02).

### Example 3 — Scratch + CA bundle

```dockerfile
# syntax=docker/dockerfile:1

FROM golang:1.22.5-alpine AS build
WORKDIR /src
RUN apk add --no-cache ca-certificates
COPY go.mod go.sum ./
RUN go mod download
COPY . .
ARG TARGETOS
ARG TARGETARCH
RUN CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH \
    go build -o /out/ordersvc ./cmd/ordersvc

FROM scratch
COPY --from=build /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
COPY --from=build /out/ordersvc /ordersvc
EXPOSE 8080
ENTRYPOINT ["/ordersvc"]
```

#### What happens here

Scratch has nothing. You copy the CA bundle from the Alpine build image and the binary. If you forget CA, the HTTPS client fails. If you forget `CGO_ENABLED=0`, the binary looks for `libc` that is not there.

### Example 4 — Local single-platform load for a smoke test

```text
docker buildx build \
  --platform linux/amd64 \
  -t ordersvc:dev \
  --load .
docker run --rm -p 8080:8080 ordersvc:dev
curl http://127.0.0.1:8080/healthz
```

#### What happens here

One platform + `--load` gives a local tag. `-p 8080:8080` publishes the port (not `EXPOSE`). `curl` on loopback checks that the process is alive.

### Example 5 — Small Go service that goes into the image

```go
package main

import (
	"encoding/json"
	"log"
	"net/http"
	"os"
)

func main() {
	addr := os.Getenv("ADDR")
	if addr == "" {
		addr = ":8080"
	}
	mux := http.NewServeMux()
	mux.HandleFunc("/healthz", func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Type", "application/json")
		_ = json.NewEncoder(w).Encode(map[string]string{"status": "ok"})
	})
	log.Println("listening on", addr)
	log.Fatal(http.ListenAndServe(addr, mux))
}
```

#### What happens here

Port configuration via env (`ADDR`) — a 12-factor habit. The zero value for env is an empty string; default `:8080`. The image does not bake the port into the code as a constant without an escape hatch.

### Example 6 — Inspecting a multi-platform manifest

```text
docker buildx build \
  --platform linux/amd64,linux/arm64 \
  -t ghcr.io/example/ordersvc:1.0.0 \
  --push .

docker buildx imagetools inspect ghcr.io/example/ordersvc:1.0.0
```

#### What happens here

`imagetools inspect` shows that the tag points to a **list** of manifests with `linux/amd64` and `linux/arm64`. If you see only one platform, the build is not multi-platform the way you think.

## Decision analysis

| Decision | Choose when... | Avoid when... |
|----------|----------------|---------------|
| Alpine runtime | you need a shell for debug, `apk`, fast onboarding | strict security requires zero shell |
| distroless | production, smaller attack surface | the team is still learning Docker and needs `exec sh` |
| scratch | maximally thin image, fully static binary | you need timezone/CA and forget to copy them |
| one platform locally | smoke test, fast loop | release to a heterogeneous fleet |
| multi-platform + push | ARM laptop + AMD server | you have no registry credentials |

Question to ask before merge: **“Does this Dockerfile build the same artifact on CI and on my laptop?”** If the answer depends on luck (`latest`, missing `go.sum`, no TARGETARCH), it is not ready.

## Trade-offs

- **Emulation vs native:** building arm64 on an amd64 host is slower. CI with native runners per architecture is faster, but more complex.
- **Module cache vs context size:** `COPY . .` after download is correct, but a bad `.dockerignore` still breaks the cache.
- **Thinness vs debuggability:** scratch gives no shell; Alpine does. Teams often keep Alpine in staging, distroless in prod — or the reverse with a strong observability stack.
- **Pin digest vs pin tag:** digest is more reproducible; tag is more readable. CI often uses digest, README uses tag.
- **CGO_ENABLED=0 vs native libs:** SQLite with CGO, some crypto/HSM wrappers — then scratch is not free; you need a matching runtime with `.so` files.

## Common mistakes

1. **Wrong:** `FROM golang:latest` + `go build` without `CGO_ENABLED=0`, then `FROM scratch`.  
   **Effect:** container does not start (missing shared libraries).  
   **Why:** CGO pulls in `libc`.  
   **Fix:** `CGO_ENABLED=0` or a runtime with the needed libs.

2. **Wrong:** `COPY . .` and only then `go mod download`.  
   **Effect:** every code change invalidates the download layer; CI takes minutes longer.  
   **Why:** Docker cache looks at the layer checksum.  
   **Fix:** first `go.mod`/`go.sum`, download, then code.

3. **Wrong:** multi-platform without `GOOS`/`GOARCH` / TARGETARG.  
   **Effect:** `exec format error` on another architecture.  
   **Why:** the binary does not match kernel/CPU.  
   **Fix:** `ARG TARGETOS TARGETARCH` + pass them into `go build`.

4. **Wrong:** believing that `EXPOSE 8080` opens the port on the host.  
   **Effect:** `curl localhost:8080` does not work; “the container is broken”.  
   **Why:** EXPOSE is metadata.  
   **Fix:** `docker run -p 8080:8080 ...`.

5. **Wrong:** `ENV DATABASE_PASSWORD=supersecret` in the Dockerfile.  
   **Effect:** secret in image history and the registry.  
   **Why:** layers are durable artifacts.  
   **Fix:** runtime env / secret store; never bake into the image.

6. **Wrong:** commit without `go.sum`, CI runs `go mod download` and gets a different graph.  
   **Effect:** “works on my machine”.  
   **Why:** checksum verification and version pinning.  
   **Fix:** always commit `go.sum`.

7. **Wrong:** `--load` with `--platform linux/amd64,linux/arm64`.  
   **Effect:** Buildx rejects or loads unexpectedly.  
   **Why:** the daemon accepts one image per load.  
   **Fix:** one platform + `--load`, or `--push` for more.

8. **Wrong:** no `.dockerignore`, context 2 GB.  
   **Effect:** slow build, cache miss.  
   **Why:** `.git` and artifacts enter the context.  
   **Fix:** add `.dockerignore`.

## Idiomatic Go / Docker

- One binary per image (`./cmd/ordersvc`), not a “monolith folder” as an ENTRYPOINT script.
- Configuration via env (`os.Getenv`), not via files baked into the image.
- Health endpoint (`/healthz`) for smoke and later Compose healthcheck.
- Structured log on stdout/stderr — Docker captures logs from there.
- Pin the Go version in the Dockerfile to the same as in `go.mod` (`go 1.22`).
- Prefer `COPY` over `ADD`.
- Image tag: `name:semver` + later digest pin in deploy manifests (09.05).

## Practical scenario

A team has a Go checkout API. Half of the developers work on Apple Silicon, production is `linux/amd64` on EKS. The Dockerfile was:

```dockerfile
FROM golang:1.22
WORKDIR /app
COPY . .
RUN go build -o api .
FROM alpine
COPY --from=0 /app/api /api
CMD ["/api"]
```

Symptoms:

1. On an M-series laptop `docker build` + `run` works.
2. On CI (amd64) the image “works”.
3. After introducing an arm64 node group in EKS, pods on arm64 crash with `exec format error`.

Root analysis:

- There was no `CGO_ENABLED=0` nor `GOOS`/`GOARCH`.
- `COPY . .` before mod download — CI cache barely exists.
- `FROM alpine` without a tag — floating.
- Nobody ran `buildx` with `--platform linux/amd64,linux/arm64`.

Fix in one PR: multi-stage with download cache, TARGETOS/ARCH, pin Alpine 3.20, `ca-certificates`, nonroot, and a CI step:

```text
docker buildx build --platform linux/amd64,linux/arm64 -t ghcr.io/acme/checkout:1.4.2 --push .
```

After that `imagetools inspect` shows both platforms. Arm64 nodes pass readiness. Build time on CI drops from 6 min to ~2 min thanks to the module cache.

Second incident the same week: a junior adds `ENV STRIPE_KEY=sk_live_...` “temporarily”. The key ends up in the registry. Key rotation + forbidden pattern in CI (`hadolint` / grep for `ENV .*KEY=`). Lesson: an image is a public or semi-public artifact as long as there is registry access.

## Check questions

1. **Why does `CGO_ENABLED=0` enable scratch?**  
   Because the binary is not dynamically linked against `libc`; scratch has no shared libraries.

2. **What does `go mod download` do in a Dockerfile?**  
   Downloads modules per `go.mod`/`go.sum` into the cache; does not compile your package.

3. **Why first `COPY go.mod go.sum`?**  
   So the dependency layer stays valid when you change only source code.

4. **Does `EXPOSE 8080` publish a port on the host?**  
   No. Publish is done by `-p` or Compose `ports`.

5. **What is the real flag for two platforms?**  
   `--platform linux/amd64,linux/arm64` with `docker buildx build`.

6. **What are `TARGETOS` and `TARGETARCH`?**  
   BuildKit ARGs for the target OS and architecture during a buildx build.

7. **Why CA certificates in the runtime image?**  
   So the TLS client can verify public HTTPS certificates.

8. **Why not bake secrets into `ENV` in the Dockerfile?**  
   They remain in image layer history and can leak through the registry.

When you get stuck around “why this image does not work on the server”, ask three questions: (1) what is the binary’s `GOARCH`, (2) does the runtime have the needed files (CA, timezone), (3) did you publish the port or only `EXPOSE` it.

Layer cache is not magic — it is a hash of inputs. Change the input, you invalidate everything after. That is why modules go before code.

One more check before the next lesson: open the Dockerfile and aloud read the order of `COPY` / `RUN`. If `go mod download` is not above `COPY` of the full source, fix it before you go to optimization.

### Mini checklist before merging a Dockerfile

Print or keep in the PR description:

1. `CGO_ENABLED=0` (or a documented CGO reason)
2. `COPY go.mod go.sum` before source
3. `ARG TARGETOS` / `ARG TARGETARCH` when you use buildx multi-platform
4. pinned base tag (not `latest`)
5. `.dockerignore` exists
6. no secrets in `ENV` / `ARG` that remain in the final image
7. `EXPOSE` is not substituted for `-p` in the README instructions for local run
8. runtime has CA if it makes HTTPS client calls

If the checklist passes, only then optimize size (08.02).

### Extra predict-then-answer: context size

**Question:** The `.git` folder is 200 MB. It is not in the image (no `COPY .git`). Why does the build still take longer while sending the context?

**Answer:** Docker sends the **entire** context (minus dockerignore) to the daemon before the Dockerfile decides what to copy. A `.dockerignore` that excludes `.git` shortens the upload, even if `.git` would never end up in a layer.

### Extra line-by-line: why the order `apk` / `COPY` / `download` is not random

```dockerfile
RUN apk add --no-cache ca-certificates
COPY go.mod go.sum ./
RUN go mod download
COPY . .
```

1. `apk` — rarely changes → good early cache.
2. `COPY go.mod go.sum` — changes when you add modules.
3. `go mod download` — expensive; cache as long as the sum does not change.
4. `COPY . .` — most frequent changes.

If you put `apk` after `COPY . .`, every code change reinstalls packages — slow with no benefit.

### Trace: `exec format error` from first symptom to fix

```text
1. docker run ... → exec format error
2. Assumption: wrong GOARCH
3. Extract the binary (docker create/cp) or build with --progress=plain
4. Check that the Dockerfile has GOARCH=$TARGETARCH
5. Rebuild: buildx --platform linux/amd64 --load
6. Repeat run on the matching host / emulation
```

### Predict: does `GOOS=linux` need to be set on a Linux host in a Docker build?

**A:** Setting it explicitly via TARGETOS is still idiomatic — the Buildx target can be clear, and you document intent. On Windows Docker Desktop without GOOS=linux a local `go build` outside the container produces the wrong artifact; inside a `golang` Linux image the default GOOS is linux, but TARGET* is still needed for ARCH.

## Summary

A multi-platform Go image requires alignment of three things: pinned module dependencies, explicit `GOOS`/`GOARCH` via Buildx target ARGs, and a deliberate runtime image base. `CGO_ENABLED=0` explains why a distroless/scratch-ish runtime makes sense. `go mod download` as an early layer saves time. `EXPOSE` does not publish. Secrets do not go into the image. Buildx with `--platform linux/amd64,linux/arm64` merges architectures into one tag — with `--push` and manifest verification.
