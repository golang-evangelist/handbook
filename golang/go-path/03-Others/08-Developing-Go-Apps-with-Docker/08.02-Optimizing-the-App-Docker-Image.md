# 08.02 Optimizing the Docker image of a Go application

> **Go Path - Zero to Gopher** / **03 Others → Developing Go Apps with Docker** / Lesson 08.02

## Lesson goals

After this lesson you should be able to:

- assemble a proper multi-stage Dockerfile: a builder with a `golang` image and a thin runtime
- explain why `CGO_ENABLED=0` simplifies the runtime layer and enables distroless/scratch-ish
- use `COPY --from=build` so only the binary enters the final image (plus CA if needed)
- apply `-ldflags="-s -w"` deliberately and know what you lose in debugging
- run the process as a nonroot user (`USER`)
- measure image size before and after and interpret the result
- never bake secrets into image layers

## Prerequisite

- Lesson 08.01 (Dockerfile, Buildx, `go mod download`, `EXPOSE` vs `-p`)
- Go 1.22+, Docker with BuildKit
- basic idea: debug symbols exist in the binary and can be stripped with linker flags

## Problem this lesson solves

The first Dockerfile often “works”: the image builds, the container listens on 8080. Then an 800 MB layer enters the registry because the final stage remained `golang:...`, or the binary carries full debug symbols, or the process runs as root. Consequences:

- slower pull on nodes and laptops;
- larger attack surface (compiler, shell, package manager in production);
- harder security scan (more packages = more CVE findings);
- incident: a compromised container with root can do more;
- a secret written as `ENV` stays forever in layer history.

Optimization here is not micro-tuning — it is **deliberate separation of build and runtime concerns**.

## Mental model

Two questions for every layer:

```text
1. Does this file need to be there while the application serves traffic?
   NO → it does not go into the final image
2. Does the process have to be root?
   NO → USER nonroot
```

Go helps because you often ship **one static binary**. The cost of CGO: you pull shared libraries. That is why `CGO_ENABLED=0` is the default stance for network services until you prove you need CGO.

Multi-stage in one picture:

```text
[stage build: golang]          [stage final: alpine/distroless/scratch]
  go.mod, go.sum, source   →     only /app/ordersvc
  go mod download                (+ ca-certificates)
  go build -o /out/app           USER nonroot
       │
       └── COPY --from=build /out/app /app/app
```

The builder dies after the build. The final tag does not contain the compiler.

## Mechanism

### Why multi-stage is not “optional aesthetics”

Single-stage Dockerfile:

```dockerfile
FROM golang:1.22.5-alpine
WORKDIR /src
COPY . .
RUN go build -o /app ./cmd/app
CMD ["/app"]
```

It works. But the final image contains:

- the entire Go toolchain;
- the module cache;
- source code (if you did not delete it);
- the `apk` world.

An attacker who enters the container gets a compiler. Pull takes longer. Scan reports CVEs from packages that production does not use.

Multi-stage: the builder stage produces an artifact; the runtime stage only copies it.

### `COPY --from` — the transfer mechanism

```dockerfile
COPY --from=build /out/ordersvc /app/ordersvc
```

Meaning: take the file from the stage named `build` (or index `0`, `1`, …) and put it into the current stage. Without `--from`, `COPY` takes from the build context on the host — that is a different thing.

**Trace:** if you mistakenly write `COPY /out/ordersvc /app/ordersvc` in the runtime stage, Docker looks for that path in the context on the laptop, not in the builder. The build fails or copies the wrong file.

### `CGO_ENABLED=0` again — now with measurement

With CGO enabled, even an “ordinary” net/http service sometimes pulls dynamic dependencies depending on the environment. Explicit `0` removes that uncertainty.

**Predict then verify:**

1. Build with `CGO_ENABLED=0`, runtime `scratch`, only the binary → starts.
2. Same application, remove `CGO_ENABLED=0`, on an Alpine build host with gcc, runtime `scratch` → often does **not** start.

The answer is not magic: ldd (or `file`) on the binary shows whether it is statically linked.

### `-ldflags="-s -w"` — what exactly it strips

| Flag | Effect |
|------|--------|
| `-s` | strips the symbol table |
| `-w` | strips DWARF debug info |

Smaller binary. A panic stack trace still often has file:line in many cases, but debugging with full symbols / some tools suffers.

**When to use:** production tag.  
**When not:** local debug image where you want Delve and rich symbols (08.04).

Example:

```dockerfile
RUN CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH \
    go build -ldflags="-s -w" -o /out/ordersvc ./cmd/ordersvc
```

### Runtime with `ca-certificates` if there is HTTPS

An application that calls external APIs:

```dockerfile
FROM alpine:3.20
RUN apk add --no-cache ca-certificates tzdata
COPY --from=build /out/ordersvc /app/ordersvc
```

Or distroless static that already carries CA. Or scratch with an explicit `COPY` of the CA bundle from the build stage (08.01 example).

Without CA: `x509: certificate signed by unknown authority`. That looks like a network bug; the cause is the filesystem.

### Nonroot — UID, permissions, `COPY --chown`

```dockerfile
RUN adduser -D -H -u 10001 appuser
COPY --from=build --chown=appuser:appuser /out/ordersvc /app/ordersvc
USER appuser
```

If you copy as root then switch to `USER appuser` without readable/executable permissions, the process cannot execute the binary.

Distroless often offers a ready `nonroot` user:

```dockerfile
FROM gcr.io/distroless/static-debian12:nonroot
USER nonroot:nonroot
```

### Secrets do not go into the image

**Wrong:**

```dockerfile
ENV DB_PASSWORD=hunter2
ARG API_KEY=sk_live_xxx
```

Even if `ARG` “disappears” after the stage, there are ways it can leak through intermediate layers and build logs. Course rule: **do not bake secrets into the Dockerfile**. Runtime gets secrets via:

- `-e` / Compose `environment` / `env_file` (which is not in git);
- orchestrator secrets;
- vault agent — out of scope for this lesson, but the idea is the same.

Build-time secrets for private modules: BuildKit secret mounts, not `ENV`.

### Measuring size — concrete numbers

```text
docker image ls ordersvc
docker history ordersvc:fat
docker history ordersvc:slim
```

Example typical outcome (rows are illustrative; your numbers will differ):

| Tag | Size |
|-----|------|
| `ordersvc:fat` (golang as final) | ~800 MB |
| `ordersvc:alpine` multi-stage | ~20–40 MB |
| `ordersvc:distroless` + `-s -w` | ~15–25 MB |
| `ordersvc:scratch` + CA | ~12–20 MB |

Look at `docker history` to see **which layer** is fat — do not guess.

### Trace: optimization step by step

Initial state: single-stage `golang` image, 820 MB.

1. Add multi-stage, Alpine runtime → 35 MB.  
2. Add `-ldflags="-s -w"` → 28 MB.  
3. Move to distroless → 22 MB.  
4. Remove unnecessary `tzdata` if you do not format local time → a bit more.

Measure every step. If after step 1 you still see 800 MB, you are mistakenly tagging the builder stage (`docker build -t` without `--target` when you have multiple stages and the wrong default — check that the last stage is really the runtime).

### Predict then answer: which stage is final?

Dockerfile:

```dockerfile
FROM golang:1.22.5-alpine AS build
...
FROM alpine:3.20 AS runtime
...
FROM golang:1.22.5-alpine AS debug
...
```

**Question:** `docker build -t ordersvc:x .` without `--target` — which stage enters the tag?

**Answer:** the last stage in the file (`debug`). That is why a production Dockerfile keeps runtime as the **last** stage, or always pass `--target runtime` in CI.

### `.dockerignore` as part of optimization

Optimization is not only the final layer. A large context slows every build. Exclude:

```text
.git
bin
dist
**/*_test.go
coverage.out
.env
.env.*
*.md
```

Caution: excluding `*_test.go` makes sense for a **production** image build. For a test image in CI (09.03) you need a different Dockerfile or target that includes tests.

### Alpine `apk` — one layer, without package cache in the image

```dockerfile
RUN apk add --no-cache ca-certificates tzdata
```

`--no-cache` prevents the `apk` index from remaining in the layer. A small detail, but a clean habit.

### `ENTRYPOINT` vs `CMD`

```dockerfile
ENTRYPOINT ["/app/ordersvc"]
CMD ["--help"]  # optional
```

Exec form as a JSON array — without a shell. On scratch/distroless a shell does not exist anyway, so `CMD ./app` (shell form) does not work.

### Read-only root filesystem (preview for production)

Many orchestrators enable `readOnlyRootFilesystem: true`. That means: the application must not write to `/`. Logs go to stdout. Temporary files — `emptyDir` or a `/tmp` mount. Design the Go service so it does not have to write next to itself in the image.

### Detailed trace: what remains in each layer

Assume a multi-stage build. After success:

**Build stage layers (do not enter the final tag if you do not copy them):**

| Layer | Content | ~Size |
|-------|---------|-------|
| base golang alpine | toolchain | ~300 MB |
| apk git/ca | packages | +10 MB |
| go.mod/go.sum | text | ~KB |
| go mod download | modules | +50–200 MB |
| source COPY | code | +MB |
| go build output | `/out/ordersvc` | ~15 MB |

**Runtime stage layers (that is your tag):**

| Layer | Content | ~Size |
|-------|---------|-------|
| alpine:3.20 | base | ~7 MB |
| ca-certificates | CA | +1 MB |
| COPY binary | app | +12–20 MB |

The runtime sum is what `docker image ls` shows as the tag size (with layer sharing between images — so the number is not always a simple sum).

### Predict then answer: does `docker system df` lie?

**Question:** You delete the tag `ordersvc:fat`, but `docker system df` still shows large usage.

**Answer:** Layers can remain as dangling / shared. `docker image prune` and `builder prune` clean up. “Image” size and disk usage are not 1:1 while BuildKit caches exist.

### Go build flags besides `-s -w`

You often see:

```text
go build -trimpath -ldflags="-s -w" -o /out/app ./cmd/app
```

`-trimpath` removes local file paths from the binary (more reproducible build, less path leakage from CI agents like `/home/runner/work/...`). That is not an invented flag — official `go build` supports `-trimpath`.

Combination for prod:

```dockerfile
RUN CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH \
    go build -trimpath -ldflags="-s -w" \
    -o /out/ordersvc ./cmd/ordersvc
```

### Why not copy all of `/src` into runtime “just in case”

Some Dockerfiles do:

```dockerfile
COPY --from=build /src /src
```

into runtime. That puts source code back into the production image — worsens size and attack surface. Copy **only** the artifact that must run (`/out/ordersvc`) and needed data files (CA, maybe `migrations/` if the application reads them — better `go:embed` in 09.04).

### Timezone data

`tzdata` on Alpine is needed if you use `time.LoadLocation("Europe/Belgrade")`. If you work only in UTC (`time.Now().UTC()`), you can often skip `tzdata` and save a layer. Predict: code that calls `LoadLocation` without `tzdata` in scratch/Alpine minimal → zone loading error.

### Verifying nonroot in runtime

```text
docker run --rm ordersvc:slim id
```

Expect `uid=10001` (or distroless nonroot UID, often 65532). If you see `uid=0`, `USER` is not active or an ENTRYPOINT script switches back to root (avoid wrapper scripts).

### Compose preview: same slim image, different env

An optimized image is the **same** artifact for staging and prod if it is 12-factor. The difference is in env and secrets that Compose/Kubernetes inject — not in baked `ENV` in the Dockerfile. Lesson 08.03 develops that; here remember: thin image + rich runtime config.

### Optimization checklist before merge

1. The last stage is runtime (or CI uses `--target runtime`)
2. No `golang` toolchain in the final image (`docker history` confirmation)
3. `CGO_ENABLED=0` or documented CGO
4. `-ldflags="-s -w"` only on the prod tag
5. `USER` nonroot
6. CA present if HTTPS is needed
7. No secrets in the Dockerfile
8. Measured sizes before/after in the PR description

## Rules and syntax

- Last stage = production runtime, or explicit `--target`.
- Builder: `golang:1.22.x-alpine` (pin version).
- Runtime: Alpine / distroless / scratch — deliberately.
- `CGO_ENABLED=0` until CGO is a proven requirement.
- `COPY --from=build` for the binary; `COPY --chown` when nonroot is needed.
- `-ldflags="-s -w"` on the prod tag; not on the debug tag.
- `USER` nonroot in the final stage.
- Never secrets in `ENV`/`ARG` that remain in the image.
- `apk add --no-cache` on Alpine.
- ENTRYPOINT in exec form.
- Measure with `docker image ls` and `docker history` before/after.

## Examples

### Example 1 — Reference multi-stage (Alpine)

```dockerfile
# syntax=docker/dockerfile:1

FROM golang:1.22.5-alpine AS build
WORKDIR /src
RUN apk add --no-cache git ca-certificates
COPY go.mod go.sum ./
RUN go mod download
COPY . .
ARG TARGETOS
ARG TARGETARCH
RUN CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH \
    go build -ldflags="-s -w" -o /out/ordersvc ./cmd/ordersvc

FROM alpine:3.20 AS runtime
RUN apk add --no-cache ca-certificates tzdata \
    && adduser -D -H -u 10001 appuser
WORKDIR /app
COPY --from=build --chown=appuser:appuser /out/ordersvc /app/ordersvc
USER appuser
EXPOSE 8080
ENTRYPOINT ["/app/ordersvc"]
```

#### What happens here

The builder downloads modules, compiles a static binary without symbols. Runtime is a small Alpine with CA and nonroot. `EXPOSE` documents; publish still goes through `-p`.

### Example 2 — Distroless nonroot

```dockerfile
# syntax=docker/dockerfile:1

FROM golang:1.22.5-alpine AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
ARG TARGETOS
ARG TARGETARCH
RUN CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH \
    go build -ldflags="-s -w" -o /out/ordersvc ./cmd/ordersvc

FROM gcr.io/distroless/static-debian12:nonroot AS runtime
COPY --from=build /out/ordersvc /ordersvc
EXPOSE 8080
USER nonroot:nonroot
ENTRYPOINT ["/ordersvc"]
```

#### What happens here

No shell. No `apk`. Smaller attack surface. Debugging goes through logs and a separate debug image, not through `docker exec sh`.

### Example 3 — Comparative build fat vs slim

```text
docker build -t ordersvc:fat -f Dockerfile.fat .
docker build -t ordersvc:slim -f Dockerfile .
docker image ls ordersvc
docker history ordersvc:fat
docker history ordersvc:slim
```

#### What happens here

You see the numbers. If `slim` is not significantly smaller, check whether you mistakenly left the toolchain in the final stage.

### Example 4 — Wrong ARG that leaks

```dockerfile
# BAD — do not do this in production
FROM alpine:3.20
ARG DB_PASSWORD
ENV DB_PASSWORD=$DB_PASSWORD
COPY ordersvc /ordersvc
```

```text
docker build --build-arg DB_PASSWORD=secret -t leak:1 .
```

#### What happens here

Bad habit: the secret enters the image. Fix: remove `ARG`/`ENV` for secrets; pass them in `docker run -e DB_PASSWORD=...` from a secret store / local env that is not committed.

### Example 5 — `--target` for debug vs runtime

```dockerfile
FROM golang:1.22.5-alpine AS build
...
FROM alpine:3.20 AS runtime
...
FROM golang:1.22.5-alpine AS debug
COPY --from=build /out/ordersvc /ordersvc
# Delve later here — 08.04
```

```text
docker build --target runtime -t ordersvc:1.2.0 .
docker build --target debug -t ordersvc:1.2.0-debug .
```

#### What happens here

Two tags from the same Dockerfile. Prod never gets the debug stage by mistake if CI explicitly uses `--target runtime`.

### Example 6 — Checking that the binary is not root-only

```text
docker run --rm --entrypoint /bin/sh ordersvc:slim -c "ls -l /app/ordersvc"
```

(On distroless this does not work — no shell. On Alpine it does.)

#### What happens here

You see the owner and execute bits. If `USER appuser` and the file is not executable for that user, the container exits immediately.

## Decision analysis

| Decision | Choose when | Cost |
|----------|-------------|------|
| Alpine runtime | you need a shell, faster onboarding | larger than distroless, more packages |
| distroless | prod hardening | harder live debug |
| scratch | maximum thinness | you add CA/timezone yourself |
| `-s -w` | prod tag | less debug info |
| without `-s -w` | debug tag | larger binary |
| one Dockerfile + `--target` | fewer files | discipline in CI |
| separate Dockerfile.debug | clear boundary | duplication |

## Trade-offs

- **Size vs debuggability:** smaller image = fewer tools in the container.
- **`-s -w` vs incident response:** faster pull; poorer native debug. Compensate with structured logging and crash reporting.
- **Nonroot vs writing to a file:** an application that writes to `/app/data` must have a volume and correct permissions.
- **One multi-stage file vs multiple files:** one file is DRY; more files reduce the risk of a wrong `--target`.
- **Optimization before measurement:** without `docker history` you “optimize a feeling”.

## Common mistakes

1. **Wrong:** final stage remains `FROM golang`.  
   **Effect:** image hundreds of MB, compiler in prod.  
   **Why:** no multi-stage or wrong last stage.  
   **Fix:** runtime stage at the end + `COPY --from`.

2. **Wrong:** forgotten `COPY --from=build`, `COPY ordersvc` from context.  
   **Effect:** old binary from the laptop or build fail.  
   **Why:** wrong COPY source.  
   **Fix:** explicit `--from=build`.

3. **Wrong:** `-ldflags="-s -w"` on an image that Delve debugs.  
   **Effect:** odd debugger behavior / missing info.  
   **Why:** stripped symbols.  
   **Fix:** separate debug build without those flags.

4. **Wrong:** `USER appuser` without `--chown` / permissions.  
   **Effect:** permission denied, exit != 0.  
   **Why:** file belongs to root and is not executable by others.  
   **Fix:** `COPY --chown=...` or `chmod` in the build.

5. **Wrong:** `ENV PAYMENT_KEY=...` in the Dockerfile.  
   **Effect:** secret leak.  
   **Why:** layer history.  
   **Fix:** runtime secret injection.

6. **Wrong:** `docker build -t prod .` when the last stage is `debug`.  
   **Effect:** Delve/tooling in the “prod” tag.  
   **Why:** default is the last stage.  
   **Fix:** `--target runtime` or stage order.

7. **Wrong:** measuring only `ls -lh` of the binary on the host.  
   **Effect:** false sense of savings.  
   **Why:** image = base + layers, not just the binary.  
   **Fix:** `docker image ls` + `history`.

8. **Wrong:** shell form `CMD ./ordersvc`.  
   **Effect:** does not work on scratch/distroless.  
   **Why:** no `/bin/sh`.  
   **Fix:** exec form JSON array.

## Idiomatic Go / Docker

- One `cmd/ordersvc` = one image.
- Prod and debug = different tags / targets.
- Configuration and secrets only via runtime env.
- Log to stdout; not to a file in the image.
- Pin base image versions.
- Health endpoint stays light (no heavy dependencies in `/healthz` if you can).
- Document in README: how to build slim vs debug.

## Practical scenario

The checkout service in production had a 1.1 GB image because the Dockerfile was single-stage `golang:1.21`. Pull on the autoscaling group took too long — cold start timeout.

PR #1: multi-stage Alpine → 42 MB.  
PR #2: `-ldflags="-s -w"` + distroless → 19 MB.  
PR #3: nonroot.  
PR #4 (incident): someone added `ARG STRIPE_SECRET` “just for a build test” — secret in Harbor registry. Rotation + policy gate.

After PR #1–#3: pull time on a new node from 90 s to ~8 s. Scan reported 90% fewer CVEs on the runtime image (no toolchain packages).

Extra twist: the application wrote cache to `/app/cache`. With nonroot + read-only root FS in Kubernetes, the pod CrashLoop. Fix: `emptyDir` mount on `/cache` and env `CACHE_DIR=/cache`. Image optimization exposed a bad disk-write design.

## Check questions

1. **What does `COPY --from=build` do?**  
   Copies files from the named stage into the current stage.

2. **Why does `CGO_ENABLED=0` help a thinner runtime?**  
   A static binary does not require `libc` in the image.

3. **What do `-s` and `-w` strip?**  
   The symbol table and DWARF debug info.

4. **Why nonroot?**  
   Reduces damage if the process is compromised.

5. **May a secret go into `ENV` in the Dockerfile?**  
   No — it remains in image history.

6. **Which stage does `docker build` choose without `--target`?**  
   The last stage in the Dockerfile.

7. **Why `apk add --no-cache`?**  
   So the package index/cache does not remain in the layer.

8. **Why exec form ENTRYPOINT?**  
   Does not require a shell; works on distroless/scratch.

When the image is “somehow large”, do not guess — `docker history`. When the container “will not start” after nonroot, check the binary owner. When TLS “does not work” only in the container, check CA.

Optimization without measurement is cosmetics. Optimization that bakes secrets is a regression. Optimization that mixes debug and prod tags is a bomb with a delayed fuse.

Before Compose (08.03) you must have **one** clean runtime image configured via env — not an image that “knows” the production password.

### One more trace: BuildKit cache mount (optional, real API)

When you want a faster local rebuild without copying the module cache into a layer:

```dockerfile
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH \
    go build -trimpath -ldflags="-s -w" -o /out/ordersvc ./cmd/ordersvc
```

This is real BuildKit syntax (`--mount=type=cache`). The cache mount is **not** part of the final image — it speeds up the build. Do not confuse it with `COPY` caching of the `go.mod` layer; both complement each other. See more patterns also in 09.01.

### Detailed trace: what `docker history` must show

After a successful slim build:

```bash
docker history ordersvc:slim
```

Expected pattern (simplified):

```text
ENTRYPOINT ["/ordersvc"]
USER nonroot
COPY /out/ordersvc /ordersvc     ← small layer (binary size)
FROM gcr.io/distroless/...       ← base
```

What must not appear in the final history chain as huge steps:

```text
RUN go mod download              ← that is the build stage, not final
RUN go build ...                 ← same
COPY . .                         ← source does not belong in runtime
```

If you see `go build` in the history of the final tag, you are tagging the wrong stage or you do not have multi-stage.

### Predict-then-answer: `--target build`

```bash
docker build --target build -t ordersvc:buildstage .
```

**Q:** What is this tag for?  
**A:** A debug/CI artifact of the build stage (e.g. to extract the binary). It is **not** a production image. Production = the last runtime stage without `--target` or with `--target runtime`.

### Nonroot + read-only rootfs (preparation)

In an orchestrator often:

```text
readOnlyRootFilesystem: true
```

The Dockerfile must not expect writes to `/`. Temporary writes: an explicit volume on `/tmp` with the correct UID. If the application “must” write next to the binary, refactor paths before you weaken nonroot.

### Compare three ldflags profiles

| Profile | ldflags | gcflags | Tag |
|---------|---------|---------|-----|
| prod | `-s -w` | (default) | `:1.2.3` |
| staging | optionally without strip | default | `:sha-...` |
| debug | without `-s -w` | `all=-N -l` | `:debug` |

Do not mix the columns. Staging can be closer to prod; debug is deliberately different.

### Anti-pattern walkthrough: “optimizing” by deleting in the same stage

```dockerfile
FROM golang:1.22.5-alpine
COPY . .
RUN go build -o /app ./cmd/app \
 && rm -rf /go /usr/local/go /src
```

**Why this is not multi-stage:** the layer with `go build` still contains the toolchain in history; `rm` in a new layer does not erase the previous layer from the image. Scan and pull still suffer. The only real separation is a new `FROM` + `COPY --from`.

### Measurement checklist before merge (extended)

1. `docker images` before/after.
2. `docker history` of the final tag.
3. Confirm `USER` (inspect or distroless nonroot).
4. Confirm there are no `ENV` secrets.
5. HTTPS smoke if CA is needed.
6. Documented MB number in the PR description.

### More decision examples: when Alpine runtime remains the better choice

Distroless is not always the winner:

- local healthcheck with `wget`/`curl` in Compose;
- ops team insists on `docker exec` in staging;
- you need `tzdata` and a simple `apk` upgrade flow.

Then: multi-stage still, Alpine runtime + nonroot + CA + strip. You get 80% of the size benefit without losing the shell. Distroless remains the goal for strict prod.

### Predict: `COPY --from=build /etc/ssl/certs/ca-certificates.crt` from Alpine build onto scratch

Often works as a pattern. Check that the path exists in the build stage after `apk add ca-certificates`. Without that, scratch + HTTPS client crashes.

### Layer counter — mental exercise

Write on paper every instruction of the runtime stage and estimate MB. Sum. Compare with `docker images`. If estimate and reality diverge by >2×, you do not understand what enters — go back to `history`.

### Final predict: do nonroot + distroless + `-s -w` guarantee “no CVE”?

**A:** No. They reduce surface and size; the base can still have findings. That is why 08.05 introduces a scan gate. Optimization and scanning are complementary, not substitutes.

### One sentence for the PR

“Multi-stage, CGO off, strip, nonroot, no secrets in layers; size X→Y MB.”

### Last number before Compose

Measure the final image one more time. If it is still hundreds of MB, you have not finished multi-stage. Only a thin image makes sense in `compose build`.

MB number in the PR description > gut feeling.

## Summary

Optimizing a Go Docker image starts by separating build and runtime stages (`COPY --from`), continues with `CGO_ENABLED=0`, deliberate `-ldflags -s -w`, a nonroot user, CA certificates as needed, and a strict ban on secrets in the image. Measure the whole image. Debug symbols and the debugger do not belong in the same tag as production.
