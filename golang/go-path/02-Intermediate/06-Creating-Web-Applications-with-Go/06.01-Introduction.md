# 06.01 Introduction to web applications in Go

> **Go Path - Zero to Gopher** / **02 Intermediate → Creating Web Applications with Go** / Lesson 06.01

## Lesson goals

After this lesson you should be able to:

- distinguish a **web application** (HTML, sessions, templates) from an **HTTP API** (JSON/XML, mostly without a UI)
- describe the **request lifecycle** from accepting a TCP connection to sending the response
- understand the role of `http.Handler` and why it is the central interface
- visualize a **middleware chain** as a higher-order function of the form `func(http.Handler) http.Handler`
- configure `http.Server` with `ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout`, and `IdleTimeout`
- know that **graceful** `Shutdown` exists instead of abruptly killing the process
- use Go 1.22+ `ServeMux` patterns at an introductory level (details in 06.02)

## Prerequisite

- Go 1.22+ (`go version`)
- basic HTTP concepts: HTTP method, path, header, status code
- module **05 Creating Web Services with Go** (or equivalent): `ListenAndServe`, `HandleFunc`, basic JSON response
- familiarity with `context.Context` at the level of “passes through the call”
- basic notion of a **goroutine** (the server starts one per connection/request)

## Problem this lesson solves

Many Go programmers first “start a server” like this:

```go
http.HandleFunc("/", home)
log.Fatal(http.ListenAndServe(":8080", nil))
```

That works on a laptop. In production the same pattern leaves doors open:

- a slow client holds the connection while sending headers byte by byte
- no `ReadHeaderTimeout` — the goroutine stays busy
- no clear boundary between “page” and “API”
- middleware is stuffed in later as an afterthought (copy-paste `log` into every handler)
- the process is killed in `kill -9` style instead of `Shutdown`

The lesson sets a **mental model of the web layer** before you enter forms, templates, and the database: what an application is, how a request flows, where the handler sits, why middleware is a higher-order function, and why a timeout is not optional decoration.

## Mental model

Imagine an HTTP server as a **post office with counters**:

1. The **Listener** accepts a connection (letters arrive at an address).
2. The **Server** reads the request (envelope + content) with time limits.
3. The **Mux (router)** chooses a counter by path and HTTP method.
4. **Middleware** are entrance checks: log, authentication, size limit — each can reject or forward via `next`.
5. The **Handler** is the counter that does the work: reads the body, looks at cookies, writes HTML or JSON.
6. The **response** goes back on the same connection; then the connection goes into keep-alive or is closed.

**Web application** here means: a server that often returns HTML (or generates it with a template), uses cookie/session, serves static files, and sometimes also has JSON endpoints. An **API** is narrowly focused on machine clients. The same `net/http` machinery runs both; the difference is the *contract* with the client, not a magic second runtime.

`http.Handler` is a contract with one method:

```go
type Handler interface {
	ServeHTTP(ResponseWriter, *Request)
}
```

Everything that “handles a request” — router, middleware, your `home` — is essentially a Handler. That is why the chain is built by composition: a function takes a Handler, returns a new Handler. That is a higher-order function in Go style.

```text
                    ┌─────────────────────────────────────┐
  TCP Accept ──►    │  http.Server (timeouts)             │
                    │    ▼                                │
                    │  middleware₁ (e.g. log)             │
                    │    ▼                                │
                    │  middleware₂ (e.g. recover)         │
                    │    ▼                                │
                    │  ServeMux ──► concrete Handler      │
                    │    ▼                                │
                    │  ResponseWriter → client            │
                    └─────────────────────────────────────┘
```

## Mechanism

### Web app versus API

| Dimension | Web application | API |
|-----------|-----------------|-----|
| Typical response `Content-Type` | `text/html` | `application/json` |
| Client state | cookie, CSRF, form | token, API key |
| Errors for humans | HTML 404/500 page | JSON `{ "error": "..." }` |
| Static files | CSS, JS, images | rarely in the same process |
| Templates | `html/template` | rarely |
| Typical client | browser | another service, mobile app, curl |

In practice one binary often does **both**: `/` renders HTML, `/api/v1/...` returns JSON. What matters is that you **clearly separate** routes and middleware (e.g. CSRF on forms, not on a pure JSON API with an `Authorization` header).

#### Trace — same process, two contracts

```text
GET /{$}          → pageHome  → Content-Type: text/html  → "<h1>..."
GET /api/health   → apiHealth → Content-Type: application/json → {"status":"ok"}

Same mux, same Server, same port.
Difference: what the handler WRITES and what the client EXPECTS.
```

**Predict, then answer:** If a browser opens `/api/health`, what does the user see?

Answer: raw JSON text in the window — it works, but UX is not a “page”. So API routes are not a substitute for an HTML home; they are for machines (LB health check, frontend fetch).

**Predict, then answer:** Do you need a different Go runtime for HTML versus JSON?

Answer: No. Same `net/http`. You separate routes, `Content-Type`, and sometimes middleware groups — not the runtime.

### Request lifecycle

In `net/http` simplified, for one HTTP/1.1 request:

1. `Server` accepts a connection (`Accept`).
2. A goroutine starts that serves that connection (simplified: one per active connection).
3. Reads the request line and headers — this is where **`ReadHeaderTimeout`** hits.
4. As needed reads the body (`Content-Length` / chunked) — here **`ReadTimeout`** and body limits (`MaxBytesReader`, later) enter.
5. Calls `Handler.ServeHTTP(w, r)`.
6. The handler writes status, headers, body via `ResponseWriter`.
7. The server finishes the response; **`IdleTimeout`** measures keep-alive idle before the next request on the same connection.
8. If the client disappears mid-work, `r.Context()` is canceled (under typical conditions).

#### Trace — successful GET

```text
t0  Accept(":8080") → conn
t1  read "GET /{$} HTTP/1.1\r\nHost: localhost\r\n\r\n"
    ReadHeaderTimeout clock: STILL RUNNING (5s budget)
t2  mux match → home
t3  home: WriteHeader(200) implicitly, Fprintln "hello"
t4  response sent; IdleTimeout waits for the next request or end of connection
```

#### Trace — slow client without ReadHeaderTimeout

```text
t0  Accept → conn
t1  client sends "G" ... pause 30s ... "ET / ..."
    WITHOUT ReadHeaderTimeout: goroutine WAITS
    WITH ReadHeaderTimeout=5s: after ~5s the server STOPS reading headers
t2  handler is NOT called (request incomplete)
```

**Predict, then answer:** Does `ReadHeaderTimeout` protect against a huge 2 GB JSON body?

Answer: Not directly. It measures time for headers. A large body needs `ReadTimeout` + `MaxBytesReader` / proxy limit. Those are different defense axes.

The handler **must not** assume it owns the goroutine forever: the client can cancel; `Request.Context()` is canceled when the connection disappears. So long operations should honor context.

### Handler as a unit of work

```go
func home(w http.ResponseWriter, r *http.Request) {
	fmt.Fprintln(w, "hello")
}
```

`http.HandlerFunc` adapts such a function into a `Handler`:

```go
type HandlerFunc func(ResponseWriter, *Request)

func (f HandlerFunc) ServeHTTP(w ResponseWriter, r *Request) {
	f(w, r)
}
```

The router (`ServeMux`) and middleware work with the `Handler` interface — so the same pattern holds from the first “hello” to a complex application.

#### Trace — HandlerFunc adapter

```text
home: func(w, r)          // ordinary function
↓
http.HandlerFunc(home)    // type with ServeHTTP method
↓
mux.Handle("GET /{$}", http.HandlerFunc(home))
// or shorter:
mux.HandleFunc("GET /{$}", home)  // internally does the same
```

**Predict, then answer:** Can you register a struct with a `ServeHTTP` method instead of a function?

Answer: Yes. `mux.Handle("GET /{$}", &HomePage{...})` where `HomePage` implements `Handler`. Useful when the handler carries dependencies (DB, config) as struct fields.

### Middleware chain as a higher-order function

Middleware in `net/http` idiomatically looks like this:

```go
func withLog(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		log.Printf("%s %s", r.Method, r.URL.Path)
		next.ServeHTTP(w, r) // next is OPTIONAL: you can return before the call
	})
}
```

That is a **higher-order function**: takes a Handler, returns a Handler. Inside is a **function literal** (closure) that captures `next`.

`next` is optional in the sense of flow control: middleware can:

- call `next.ServeHTTP(w, r)` — forward
- **not** call `next` — reject (401, 429, 400) and end the chain
- call `next` with a modified `r` (`r.WithContext(...)`)

Wrapping order matters:

```go
handler := withLog(withAuth(mux))
// equivalent to reading outside → inside:
// request:  log → auth → mux
// response: mux → auth → log  (if you measure after next)
```

```text
logging(auth(mux))

The outer layer sees the request FIRST.
The inner (mux) sees the request LAST before the work.
After next, the outer sees the “return” — so duration logging goes AFTER next.ServeHTTP.
```

#### Trace — wrapping

```text
Construction (inside → outside):
  mux
  auth(mux)     → H1
  log(H1)       → H2 = final Handler

Request GET /secret:
  H2.log:  log "GET /secret"; next=H1
  H1.auth: no cookie → 401; does NOT call next
  mux:     NEVER called

Request GET /secret with a valid session:
  H2.log → H1.auth → mux.home → response
  H2.log measures duration after return
```

**Predict, then answer:** If you write `auth(log(mux))` instead of `log(auth(mux))`, what changes?

Answer: Auth sees the request first. Failed auth can still be logged only if auth itself logs — the outer log sees only what reaches it. Order changes what you measure and what you reject before logging.

**Predict, then answer:** Must middleware always call `next`?

Answer: No. If you reject the request (e.g. 401), you deliberately do not call `next`. That is part of the chain contract.

### Timeouts on `http.Server`

`http.ListenAndServe(addr, handler)` internally builds a `Server` **without** `ReadHeaderTimeout`. Recommendation for publicly exposed servers: an explicit `http.Server`.

#### How to choose starting values (lab → staging)

```text
Lab / demo:
  ReadHeaderTimeout: 5s
  the rest often default or mild

Staging (publicly exposed behind a proxy):
  ReadHeaderTimeout: 5s
  ReadTimeout:       15–30s  (forms; upload routes separately)
  WriteTimeout:      15–30s  (except stream routes)
  IdleTimeout:       60–120s

Production:
  align with reverse proxy timeouts
  measure p95 latency before cutting WriteTimeout
```

**Predict, then answer:** If the proxy has a 60s timeout and Go `WriteTimeout` is 10s, who “wins”?

Answer: The client sees a break as soon as the first component in the chain gives up. Align them consciously; otherwise you debug “random” disconnects.

Key fields:

| Field | What it measures | Typical purpose |
|-------|------------------|-----------------|
| `ReadHeaderTimeout` | time to read headers | Slowloris-style defense |
| `ReadTimeout` | budget for reading the request (headers + body, in practice) | slow upload / slow client |
| `WriteTimeout` | budget for writing the response | client stuck on download |
| `IdleTimeout` | keep-alive idle | close sleeping connections |

`ReadHeaderTimeout` is often the **first** thing you add if you have not touched timeouts yet.

#### Trace — four clocks

```text
Connection opened
│
├─[ReadHeaderTimeout]── read headers ──► OK or cut
│
├─[ReadTimeout]──────── read body (if any) ──► OK or cut
│
├─ Handler.ServeHTTP ...
│
├─[WriteTimeout]─────── write response ──► OK or cut
│
└─[IdleTimeout]──────── wait for next request on keep-alive
```

Note: exact behavior and field interaction depend on the version and `net/http` documentation — always check the current Go doc. The mental model remains: **separate budgets for different phases**.

**Predict, then answer:** Why can `WriteTimeout` hurt SSE / a long stream?

Answer: Because it measures the whole response write. A long stream can exceed the budget. Then you tune the timeout differently, or put those routes behind another server/proxy rule.

### Graceful Shutdown

When the process must stop (deploy, signal `SIGINT`/`SIGTERM`), an abrupt exit cuts active requests. Idiomatic pattern:

```go
go func() {
	log.Println(srv.ListenAndServe())
}()

// ... wait for signal ...
ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
defer cancel()
_ = srv.Shutdown(ctx) // stops Accept; waits for existing requests until timeout
```

`Shutdown` does not kill immediately: it stops accepting new connections and waits for active handlers to finish (with a deadline). Handlers should still honor `r.Context()` where it makes sense.

#### Trace — Shutdown

```text
t0  SIGTERM
t1  Shutdown(ctx10s): Listener.Close() — new Accept rejected
t2  active GET /report still running (up to 8s)
t3  GET /report done → connection closed cleanly
t4  no more active → Shutdown returns nil
```

If a handler ignores the signal and runs 60s, and the Shutdown budget is 10s, `Shutdown` returns an error / context deadline — remaining connections are closed more forcibly.

**Predict, then answer:** Does `Shutdown` replace `ReadHeaderTimeout`?

Answer: No. Shutdown is the *process* lifecycle. Timeouts are the lifecycle of an *individual request/connection*. You need both.

### Go 1.22+ ServeMux — introduction

From Go 1.22, `ServeMux` supports patterns with an HTTP method and wildcards:

```go
mux := http.NewServeMux()
mux.HandleFunc("GET /{$}", home)       // only exact "/"
mux.HandleFunc("GET /item/{id}", item) // PathValue("id")
mux.HandleFunc("POST /login", login)
```

Details (`{$}`, prefixes, trailing slash) are topic **06.02**. Here remember: **HTTP method + path in the pattern** reduces manual `if r.Method != http.MethodGet` checks and “POST entered a GET handler” bugs.

#### Trace — old vs new pattern

```text
Old:  mux.HandleFunc("/", home)
      GET /about → often ENTERS home, then if Path != "/" → 404 manually

New:  mux.HandleFunc("GET /{$}", home)
      GET /about → does NOT match /{$} → other pattern or 404 from mux
```

**Predict, then answer:** Does `GET /{$}` match `GET /index`?

Answer: No. `{$}` means end of path after `/` — only root `/`.

## Rules and syntax

### Minimal server with timeouts

```go
srv := &http.Server{
	Addr:              ":8080",
	Handler:           mux, // or middleware(mux)
	ReadHeaderTimeout: 5 * time.Second,
	ReadTimeout:       15 * time.Second,
	WriteTimeout:      15 * time.Second,
	IdleTimeout:       60 * time.Second,
}
log.Fatal(srv.ListenAndServe())
```

### Handler registration (Go 1.22+)

```go
mux := http.NewServeMux()
mux.HandleFunc("GET /{$}", home)
mux.Handle("GET /static/", http.StripPrefix("/static/", fs))
```

### Middleware signature

```go
type Middleware func(http.Handler) http.Handler

func chain(h http.Handler, mws ...Middleware) http.Handler {
	for i := len(mws) - 1; i >= 0; i-- {
		h = mws[i](h)
	}
	return h
}
```

You wrap from last to first so that order in the slice is “first in the list = outermost”.

### Handler interface — status and body

- Implement `ServeHTTP` or use `HandlerFunc`.
- The first `WriteHeader` / implicit 200 “locks” the status.
- After writing the body, a late `WriteHeader` has no effect of the kind you expect.
- `http.Error` writes status + message — do not mix with a later `fmt.Fprint` as if it were 200.

### Context in the handler

```go
ctx := r.Context()
select {
case <-ctx.Done():
	return
case res := <-dbCh:
	_ = res
}
```

### What NOT to do in production (brief)

```go
// avoid as the only pattern for the public internet:
log.Fatal(http.ListenAndServe(":8080", nil)) // DefaultServeMux + no ReadHeaderTimeout
```

## Examples

### Example 1: Web app versus JSON endpoint on the same mux

```go
package main

import (
	"encoding/json"
	"fmt"
	"log"
	"net/http"
	"time"
)

func pageHome(w http.ResponseWriter, r *http.Request) {
	w.Header().Set("Content-Type", "text/html; charset=utf-8")
	fmt.Fprint(w, `<!doctype html><html><body><h1>Shop</h1></body></html>`)
}

func apiHealth(w http.ResponseWriter, r *http.Request) {
	w.Header().Set("Content-Type", "application/json")
	_ = json.NewEncoder(w).Encode(map[string]string{"status": "ok"})
}

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /{$}", pageHome)
	mux.HandleFunc("GET /api/health", apiHealth)

	srv := &http.Server{
		Addr:              ":8080",
		Handler:           mux,
		ReadHeaderTimeout: 5 * time.Second,
		ReadTimeout:       15 * time.Second,
		WriteTimeout:      15 * time.Second,
		IdleTimeout:       60 * time.Second,
	}
	log.Fatal(srv.ListenAndServe())
}
```

#### What happens here

- HTML and JSON share the same process and mux, but different paths and `Content-Type`.
- `GET /{$}` is the exact root in Go 1.22+ mux syntax.
- The server has explicit timeouts; it is not the “default” `ListenAndServe` without control.

#### Trace

```text
curl -i localhost:8080/
→ 200 text/html ... <h1>Shop</h1>

curl -i localhost:8080/api/health
→ 200 application/json ... {"status":"ok"}

curl -i -X POST localhost:8080/api/health
→ does not match GET pattern → 404 (or another handler if one exists)
```

**Predict, then answer:** What does `GET /api/health/` (with trailing slash) return if you only registered `GET /api/health`?

Answer: In the Go 1.22+ mux that is **not** automatically the same — typically 404, unless you add a redirect or another pattern. (Details in 06.02.)

### Example 2: Logging middleware in the chain

```go
func withRequestLog(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		start := time.Now()
		next.ServeHTTP(w, r)
		log.Printf("%s %s %s", r.Method, r.URL.Path, time.Since(start))
	})
}

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /{$}", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, "ok")
	})

	srv := &http.Server{
		Addr:              ":8080",
		Handler:           withRequestLog(mux),
		ReadHeaderTimeout: 5 * time.Second,
	}
	log.Fatal(srv.ListenAndServe())
}
```

#### What happens here

- `mux` is the inner Handler; `withRequestLog` wraps it.
- Duration measurement goes **after** `next.ServeHTTP`.
- `srv.Handler` is the chain, not a “raw” mux.

#### Trace

```text
GET /
  withRequestLog: start=T0
  next = mux → home writes "ok\n"
  log: "GET / 1.2ms"
```

**Predict, then answer:** If home panics before return, does the log line still print duration?

Answer: No — panic aborts the function literal before `log.Printf`, unless you have `recover` middleware *inside* or *around* log. That is why `recover` is often placed outside or immediately inside with a clear order.

### Example 3: Auth middleware that sometimes does not call next

```go
func withToken(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		if r.Header.Get("X-Token") != "secret" {
			http.Error(w, "forbidden", http.StatusUnauthorized)
			return // next is NOT called
		}
		next.ServeHTTP(w, r)
	})
}

func mount(mux *http.ServeMux) http.Handler {
	mux.HandleFunc("GET /private", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, "secret")
	})
	return withRequestLog(withToken(mux))
}
```

#### Trace

```text
GET /private  (no X-Token)
  log → token → 401 "forbidden"
  mux.private: not executed
  log measures short duration (auth rejection only)

GET /private  X-Token: secret
  log → token → mux.private → "secret"
```

**Predict, then answer:** Where in `withToken` is the “optional next”?

Answer: In the `if` branch that `return`s before `next.ServeHTTP`. The higher-order function always *receives* next, but does not have to *call* it.

### Example 4: Why ReadHeaderTimeout matters

```go
// Bad pattern for the public internet:
log.Fatal(http.ListenAndServe(":8080", mux))

// Better pattern:
srv := &http.Server{
	Addr:              ":8080",
	Handler:           mux,
	ReadHeaderTimeout: 5 * time.Second,
	IdleTimeout:       60 * time.Second,
}
log.Fatal(srv.ListenAndServe())
```

#### What happens here

- Same `mux`, different entrance time policy.
- Timeout does not replace a body size limit — that is another axis.
- In production you combine timeouts, body limits, and a reverse proxy in front of the process.

**Predict, then answer:** Does a proxy (nginx) in front of the Go process mean you may leave `ListenAndServe` without timeouts?

Answer: Better not. Defense in depth: the proxy protects the edge; the Go process still needs its own bounds if someone bypasses the proxy or misconfigures it.

### Example 5: Handler that honors cancellation

```go
func slowReport(w http.ResponseWriter, r *http.Request) {
	ctx := r.Context()
	select {
	case <-time.After(30 * time.Second):
		fmt.Fprintln(w, "report done")
	case <-ctx.Done():
		log.Printf("canceled: %v", ctx.Err())
		return
	}
}
```

#### Trace

```text
Client starts GET /report, then closes the connection at t=2s
  ctx.Done() fires
  select takes the canceled branch
  "report done" is NOT written
  the goroutine is released instead of waiting another 28s
```

**Predict, then answer:** What if instead of `select` you only do `time.Sleep(30 * time.Second)`?

Answer: Sleep ignores context — you spend resources even after the client left. Fine for short demos; for DB/IO work it is a bad habit.

### Example 6: Graceful Shutdown sketch

```go
func run(ctx context.Context, srv *http.Server) error {
	errCh := make(chan error, 1)
	go func() {
		errCh <- srv.ListenAndServe()
	}()

	select {
	case err := <-errCh:
		return err
	case <-ctx.Done():
		shCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
		defer cancel()
		_ = srv.Shutdown(shCtx)
		return ctx.Err()
	}
}
```

#### What happens here

- `ListenAndServe` runs in a background goroutine.
- Canceling the outer context (signal) starts `Shutdown` with its own deadline.
- New requests are not accepted; old ones get a chance to finish.

### Example 7: ResponseWriter “locking” the status

```go
func oops(w http.ResponseWriter, r *http.Request) {
	fmt.Fprintln(w, "body first")          // implicit 200 + start of body
	w.WriteHeader(http.StatusNotFound)    // TOO LATE — no effect of the kind you expect
}
```

#### Trace

```text
1) Fprintln → WriteHeader(200) implicitly, writes bytes
2) WriteHeader(404) → ignored / warning in debug mode
3) client sees 200 with text, not a 404 page
```

**Predict, then answer:** Where must `WriteHeader(404)` stand?

Answer: Before the first body write. Or use `http.Error` / `http.NotFound` which do the order correctly.

### Example 8: DefaultServeMux trap in a test

```go
// package A (library) — BAD:
func init() {
	http.HandleFunc("/hidden", hidden) // registers on DefaultServeMux
}

// your test in package B:
func TestServer(t *testing.T) {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /{$}", home)
	// DefaultServeMux still exists globally — collisions between tests/packages
}
```

#### Trace

```text
Library package calls http.HandleFunc → DefaultServeMux
Your srv.Handler = local mux → OK for your routes
But other code that does ListenAndServe(":x", nil) also gets /hidden
Tests that share a process see global state
```

**Predict, then answer:** What is the idiomatic alternative?

Answer: The library exports `func Mount(mux *http.ServeMux)` or returns `http.Handler` — never touches `DefaultServeMux` in `init`.

### Another trace — IdleTimeout keep-alive

```text
GET /  (keep-alive)
  response sent
  IdleTimeout=60s starts
  ... 10s silence ...
  GET /api/health on the same connection → OK, clock resets
  ... 61s silence ...
  server closes the sleeping connection
```

**Predict, then answer:** Does a short `IdleTimeout` (e.g. 2s) “kill” a slow user reading HTML?

Answer: Idle measures idle *between* requests on a keep-alive connection, not the time reading an already received response in the browser. Still, too short an idle can open new TCP connections more often — a trade-off with resources.

## Decision analysis

| Decision | Choice | Why |
|----------|--------|-----|
| One binary for HTML + API | Often yes | Simple deploy; separate routes and middleware |
| `ListenAndServe` without Server struct | Local demo only | No `ReadHeaderTimeout` |
| Global `http.DefaultServeMux` | Avoid in libraries | Tests and multiple servers collide |
| Middleware early in design | Yes | Otherwise copy-paste log/auth per handler |
| Higher-order `func(Handler) Handler` | Yes | Composition, testability, optional `next` |
| Templates from day one | Not required | First understand handler and lifecycle |
| Graceful Shutdown | Yes in services | Clean deploy without cutting requests |
| Strict mux patterns (1.22+) | Yes | Fewer HTTP method/path mistakes |

## Trade-offs

- **More timeout fields** — better resilience, but wrong values cut legitimate slow uploads or long SSE streams; tune per route/proxy.
- **One process for everything** — cheap start; harder horizontal scale by load type (CPU templates vs I/O API).
- **Pure `net/http` versus Gin** — the standard library is enough and instructive; a framework speeds routing/bind, but adds abstraction (later module).
- **Strict mux patterns (1.22+)** — fewer mistakes, a little more path syntax learning.
- **Thick middleware chain** — clear policy at the edge; an overly deep chain makes debug harder (log a request ID).
- **Shutdown timeout too short** — fast deploy, more cut requests; too long — slow rolling update.

## Common mistakes

1. **`http.ListenAndServe` in production without `ReadHeaderTimeout`.**
2. Mixing HTML and JSON errors on the same route without a clear `Accept` / path.
3. Assuming `DefaultServeMux` is “yours” — in tests and libraries make a local mux.
4. Middleware as copy-paste instead of `func(http.Handler) http.Handler`.
5. Ignoring `r.Context()` in long handlers.
6. Writing the body then trying to change the status code.
7. Forgetting that the reverse proxy also has timeouts — align them.
8. Wrapping middleware in the wrong order (`auth` inside/outside without intent).
9. Killing the process without `Shutdown` during deploy.
10. Mixing `WriteTimeout` with long stream responses without a separate policy.

## Idiomatic Go

- Explicit `&http.Server{...}` for anything that listens on the network outside an exercise.
- Small handlers; shared logic in middleware or a service layer.
- `ServeMux` per process/application, not a hidden global registry in packages.
- Middleware as a higher-order function; call `next` only when forwarding.
- Dependencies in a struct handler (`type API struct { DB *sql.DB }`), not in globals.
- Log HTTP method, path, duration; request ID comes soon (06.03).
- Separate packages: `cmd/web`, `internal/handler`, `internal/middleware` as the project grows.
- In tests: local mux + `httptest.NewRecorder` / `httptest.NewRequest`.

## Practical scenario

The “Internal portal” team has an HTML UI for employees and `/api/health` for the load balancer. On staging everything works. In production, under DDoS tooling, metrics show a rising number of goroutines and connections stuck reading requests.

**Cause:** `ListenAndServe` without `ReadHeaderTimeout`, plus handlers that read the body without a limit, plus a deploy that kills the PID mid POST form.

**Fix:**

1. Introduce `http.Server` with `ReadHeaderTimeout: 5s`, `ReadTimeout`, `WriteTimeout`, `IdleTimeout`.
2. Logging middleware as `func(http.Handler) http.Handler` around the whole mux.
3. Body limit on POST forms (details in 06.03).
4. `Shutdown` on `SIGTERM` with a 15s budget — rolling update no longer cuts half of checkout.
5. Health stays light JSON; HTML routes later get a session middleware group.

Same binary, clearer lifecycle. Stuck connection count drops; deploy becomes boring — which is the goal.

Second incident: a junior registers `HandleFunc("/", home)` and wonders why `/api/health` sometimes shows HTML. After moving to `GET /{$}` + explicit API patterns, collisions disappear.

## Summary

- Web app and API share the same HTTP machinery; they differ by contract (HTML/cookie versus JSON/token).
- A request passes through the server (timeouts), an optional middleware chain, mux, then handler.
- `http.Handler` is the shared language of composition; middleware is `func(http.Handler) http.Handler` with optional `next`.
- An explicit `http.Server` with `ReadHeaderTimeout` (and other timeouts) is basic hygiene.
- Graceful `Shutdown` protects active requests during wrap-up.
- Go 1.22+ mux patterns (HTTP method + path) are the foundation for 06.02.
