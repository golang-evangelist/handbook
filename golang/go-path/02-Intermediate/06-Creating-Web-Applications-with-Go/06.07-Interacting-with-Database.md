# 06.07 Interacting with the database from a web handler

> **Go Path - Zero to Gopher** / **02 Intermediate → Creating Web Applications with Go** / Lesson 06.07

## Lesson goals

After this lesson you should be able to:

- keep `*sql.DB` as a **long-lived pool** in `main` / wiring, and not call `sql.Open` per HTTP request
- run queries via `QueryContext`, `ExecContext`, and `QueryRowContext` with `r.Context()` (or a derived timeout)
- choose **transactions per use-case** (`BeginTx` → work → `Commit`, with `defer Rollback`), not “one Tx per request always”
- map `sql.ErrNoRows` to **404**; treat an empty list as **200** with an empty result
- inject the store (dependency injection) into a server struct; do not hold a Tx open during template render
- respect `rows.Close` and `rows.Err` after iteration

## Prerequisite

- relational databases module / `database/sql` basics (`QueryContext`, `ExecContext`, `Tx`, placeholders)
- 06.01–06.06 (handler, middleware, context, timeout)
- a local DB is not required for reading; examples use the real `database/sql` API (Go 1.22+)
- you know the difference between `context.Context` cancellation and HTTP status codes

## Problem this lesson solves

Four common mistakes in the web layer around the database:

1. **`sql.Open` per request** — expensive, uncontrolled connection count, unstable pool.
2. **Ignoring context** — the client left, the query still holds a connection from the pool.
3. **A transaction around the whole request** “just in case” — long Tx, locks, bad throughput; worse if you render HTML while the Tx is open.
4. **`ErrNoRows` as 500** — the user sees “internal error” instead of “no such item”; an empty list wrongly becomes 404.

The lesson connects the HTTP lifecycle with SQL calls: short use-cases, request-scoped context, correct status codes, a clear handler ↔ store boundary.

## Mental model

```text
main / wiring
  └─ *sql.DB  (one pool for the process)
       └─ Store{db}  (SQL boundary)
            └─ Server{store}  (HTTP boundary)
                 └─ Request
                      → Handler (path, auth, validation)
                        → use-case (rules)
                          → Store: QueryContext / ExecContext / BeginTx
                      ← DTO / domain → HTML or JSON
```

Key claims:

- `*sql.DB` is **not** one connection; it is a pool. `Open` does not guarantee the database is available — check with `PingContext`.
- One HTTP request can have zero, one, or more queries. A transaction only when **multiple steps must be atomic**.
- “No row” (`sql.ErrNoRows`) is often an **expected** outcome of a lookup by ID → 404, not panic and not 500.
- An empty list (`[]Item{}` / nil slice) is a successful list response → 200, not 404.
- Database access on the request path **always** uses `r.Context()` (or a timeout derived from it).

## Mechanism

This section is the core of the lesson: from pool to status code, with traces and short checks.

### 1. The pool lives in the process, not in the handler

```go
db, err := sql.Open("pgx", dsn) // or "sqlite", "postgres", ...
if err != nil {
	log.Fatal(err)
}
db.SetMaxOpenConns(20)
db.SetConnMaxLifetime(time.Hour)

ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
defer cancel()
if err := db.PingContext(ctx); err != nil {
	log.Fatal(err)
}
```

What `*sql.DB` does:

1. Holds driver and DSN configuration.
2. Borrows connections from the pool for each query / Tx.
3. Returns the connection to the pool when `Rows` is closed or the Tx finishes.

**Forbidden pattern:**

```go
func handler(w http.ResponseWriter, r *http.Request) {
	db, _ := sql.Open("pgx", dsn) // NO — per request
	defer db.Close()
	// ...
}
```

#### Execution trace — pool vs Open per request

```text
Good (one pool):
  main: Open → PingContext → Store{db}
  req1: QueryRowContext → borrow conn → Scan → return conn
  req2: QueryContext   → borrow conn → Close rows → return conn

Bad (Open per request):
  req1: Open → new pool/conn → ... → Close
  req2: Open → again → ...
  → MaxOpen on the DB side, latency, leak if you forget Close
```

#### Predict, then answer

A handler in a loop of 100 parallel requests calls `sql.Open` then `QueryRow` without a shared `*sql.DB`. What do you expect under load?

<details>
<summary>Answer</summary>

Unstable connection count, slower start per request, risk of hitting the database limit. Correct: one `*sql.DB` in `main`, injected into the store.
</details>

### 2. Request-scoped queries: always the `*Context` variants

Three APIs you use on the HTTP path:

| Method | When | Typical outcome |
|--------|------|-----------------|
| `QueryRowContext` | one row (get-by-id) | `Scan` or `sql.ErrNoRows` |
| `QueryContext` | 0..N rows (list) | `*sql.Rows` + iteration |
| `ExecContext` | INSERT/UPDATE/DELETE | `sql.Result` (`RowsAffected`) |

```go
func (s *Store) FindItem(ctx context.Context, id string) (Item, error) {
	var it Item
	err := s.db.QueryRowContext(ctx,
		`SELECT id, name FROM items WHERE id = $1`, id,
	).Scan(&it.ID, &it.Name)
	return it, err
}
```

From the handler:

```go
func (s *Server) getItem(w http.ResponseWriter, r *http.Request) {
	ctx, cancel := context.WithTimeout(r.Context(), 2*time.Second)
	defer cancel()

	id := r.PathValue("id")
	it, err := s.store.FindItem(ctx, id)
	// ... error mapping ...
	_ = it
}
```

Why `r.Context()`, not `context.Background()`:

- client disconnects → request context is canceled → driver can abort the query (depends on driver/DB)
- middleware timeout / deadline is inherited
- you do not hold a pool connection after an abandoned request

#### Execution trace — QueryRowContext + timeout

```text
t0  client GET /item/42
t1  handler: WithTimeout(r.Context(), 2s)
t2  store: QueryRowContext(ctx, ...)
t3a fast DB → Scan OK → 200
t3b slow DB → after 2s ctx.Done → error (context deadline) → 500 + log
t3c client Abort → r.Context canceled → query should stop → connection back to pool
```

#### Predict, then answer

What happens if in a store method you use `QueryRow` (without Context) while the handler already received a canceled `r.Context()`?

<details>
<summary>Answer</summary>

The query **does not see** cancellation. It runs to completion (or until a DB timeout), holds a connection, wastes resources. On the HTTP path always `QueryRowContext` / `QueryContext` / `ExecContext` with `ctx` from the request.
</details>

### 3. List: QueryContext, Close, Err

```go
func (s *Store) ListItems(ctx context.Context, limit int) ([]Item, error) {
	rows, err := s.db.QueryContext(ctx,
		`SELECT id, name FROM items ORDER BY name LIMIT $1`, limit)
	if err != nil {
		return nil, err
	}
	defer rows.Close()

	var out []Item
	for rows.Next() {
		var it Item
		if err := rows.Scan(&it.ID, &it.Name); err != nil {
			return nil, err
		}
		out = append(out, it)
	}
	return out, rows.Err()
}
```

Required steps after `QueryContext`:

1. Check `err` from `QueryContext`.
2. `defer rows.Close()` — returns the connection to the pool.
3. Loop `rows.Next` + `Scan`.
4. Return `rows.Err()` — errors during iteration (network, cancellation).

Empty table → `out` is an empty slice, `err == nil` → handler sends **200** and empty JSON/HTML. That is **not** 404.

#### Execution trace — empty list vs missing ID

```text
GET /items          → ListItems → 0 rows → 200 + []
GET /item/missing   → FindItem  → ErrNoRows → 404
GET /item/1         → FindItem  → row       → 200 + body
```

#### Predict, then answer

`ListItems` returns `nil, nil` (nil slice, no error). Which HTTP status do you pick for a JSON list API?

<details>
<summary>Answer</summary>

**200** with `[]` (after `json.Marshal` a nil slice often becomes `null` — better explicitly `out := []Item{}` if you always want `[]`). Reserve 404 for “this concrete resource does not exist”, not for “there are no items in the collection”.
</details>

### 4. Transactions: BeginTx, Commit, defer Rollback

Transaction per **use-case**, not per HTTP method.

```go
func (s *Store) PlaceOrder(ctx context.Context, userID, itemID string, qty int) error {
	tx, err := s.db.BeginTx(ctx, nil)
	if err != nil {
		return err
	}
	defer func() { _ = tx.Rollback() }() // no-op after successful Commit

	res, err := tx.ExecContext(ctx,
		`UPDATE items SET stock = stock - $1 WHERE id = $2 AND stock >= $1`, qty, itemID)
	if err != nil {
		return err
	}
	n, err := res.RowsAffected()
	if err != nil {
		return err
	}
	if n == 0 {
		return errInsufficientStock
	}
	_, err = tx.ExecContext(ctx,
		`INSERT INTO orders(user_id, item_id, qty) VALUES ($1,$2,$3)`, userID, itemID, qty)
	if err != nil {
		return err
	}
	return tx.Commit()
}
```

When you **need** a Tx:

- decrease stock + write an order
- move money between two rows
- multiple INSERTs that must all succeed or all fail

When you **do not need** a Tx:

- one `SELECT` to display a page
- independent read-only queries for a dashboard (unless you need snapshot isolation — rare in this course)

#### Execution trace — success and failure

```text
Success:
  BeginTx → Exec UPDATE (1 row) → Exec INSERT → Commit
  defer Rollback sees an already-committed Tx → Rollback is a no-op

Failure (stock):
  BeginTx → Exec UPDATE (0 rows) → return errInsufficientStock
  defer Rollback → undo (no INSERT)

Failure (network on INSERT):
  BeginTx → UPDATE OK → INSERT err → return err
  defer Rollback → undo UPDATE
```

#### Predict, then answer

Handler calls `PlaceOrder`, gets `errInsufficientStock`. Which status code?

<details>
<summary>Answer</summary>

Typically **409 Conflict** (or 422, by API contract) — domain error, not 500. Leave 500 for unexpected DB/driver errors that you log internally.
</details>

### 5. ErrNoRows → 404; everything else → 500 without leaking

```go
item, err := store.FindItem(ctx, id)
if errors.Is(err, sql.ErrNoRows) {
	http.NotFound(w, r)
	return
}
if err != nil {
	log.Printf("FindItem id=%s: %v", id, err)
	http.Error(w, "internal error", http.StatusInternalServerError)
	return
}
```

Mapping rules:

| Store outcome | HTTP |
|---------------|------|
| `sql.ErrNoRows` on get-by-id | 404 |
| domain sentinel (`errInsufficientStock`) | 409 / 422 |
| context canceled / deadline | 499/504 by policy, or 500 + log |
| other DB errors | 500, generic message to the client |
| empty list | 200 |

Never send raw `err.Error()` to the client — it leaks schema, table names, driver messages.

### 6. Dependency injection: Server + Store

```go
type Store struct {
	db *sql.DB
}

type Server struct {
	store *Store // or ItemStore interface in production
}
```

Wiring in `main`:

```go
store := &Store{db: db}
srv := &Server{store: store}
mux.HandleFunc("GET /item/{id}", srv.getItem)
```

Why not `context.Value` for DB:

- implicit, hard to test
- fake “service locator”
- an explicit field on a struct is idiomatic Go at this level

### 7. Do not hold a Tx during template render

```go
// Bad pattern
tx, _ := db.BeginTx(ctx, nil)
item, _ := load(tx, id)
_ = tmpl.Execute(w, item) // slow I/O, client may wait
_ = tx.Commit()
```

```go
// Good pattern
item, err := store.FindItem(ctx, id) // Tx if needed — finished inside
if err != nil { /* map */ return }
_ = tmpl.Execute(w, item) // outside Tx
```

Why:

- lock / snapshot lasts while HTML is written
- an external HTTP call inside an open Tx is even worse (payment API + stock lock)
- the pool connection is occupied longer than SQL requires

#### Execution trace — bad vs good

```text
Bad:
  BeginTx → SELECT → [render 800ms] → Commit
  conn+lock live 800ms+

Good:
  QueryRowContext → Scan → (Tx already done)
  → render 800ms without DB resources
```

#### Predict, then answer

Checkout: in a Tx decrease stock, then call a payment HTTP API, then `Commit`. What is the risk?

<details>
<summary>Answer</summary>

While waiting for payment, you hold a Tx and often a lock on the stock row. Better: reserve in a short Tx + `Commit`, then payment; on failure a separate use-case for release / compensation.
</details>

### 8. Context through the whole request chain

```text
r.Context()
  → WithTimeout (optional)
    → service.PlaceOrder(ctx, ...)
      → BeginTx(ctx)
        → ExecContext(ctx, ...)
```

Rule: **database access inside a request uses `r.Context()`**. Background work after the response uses `context.Background()` + its own timeout — deliberately, outside the request guarantee.

```go
go func() {
	ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()
	_ = s.store.Audit(ctx, payload)
}()
```

For critical audit when the process shuts down — queue / outbox, not a “fire and forget” goroutine.

### Mechanism — compact decision diagram

```text
HTTP handler
  ├─ need atomicity of multiple SQL steps?
  │    yes → BeginTx + defer Rollback + Commit
  │    no → Query*/Exec* on *sql.DB
  ├─ get-by-id and ErrNoRows? → 404
  ├─ list empty? → 200
  └─ render / external I/O? → only after finished Tx / query
```

## Rules and syntax

- On the HTTP path always `QueryContext`, `ExecContext`, `QueryRowContext` — not `Query` / `Exec` / `QueryRow` without context.
- One `*sql.DB` per process (or per bounded scope); `Open` in `main`, not in the handler.
- `defer rows.Close()`; check `rows.Err()`.
- `BeginTx(ctx, opts)` → work → `Commit`; `defer Rollback` as a safety net.
- `errors.Is(err, sql.ErrNoRows)` for lookup.
- Placeholders (`$1` / `?`) — never string concatenation of user input into SQL.
- Do not log SQL with secrets; log request ID + error type.
- HTML and JSON handlers share the store; they differ only in render.
- Go 1.22+: `r.PathValue("id")` with `ServeMux` pattern `GET /item/{id}`.

## Examples

### Example 1: Store + handler lookup (404 / 500)

```go
package main

import (
	"context"
	"database/sql"
	"errors"
	"fmt"
	"log"
	"net/http"
	"time"
)

type Item struct {
	ID   string
	Name string
}

type Store struct {
	db *sql.DB
}

func (s *Store) FindItem(ctx context.Context, id string) (Item, error) {
	var it Item
	err := s.db.QueryRowContext(ctx,
		`SELECT id, name FROM items WHERE id = $1`, id,
	).Scan(&it.ID, &it.Name)
	return it, err
}

type Server struct {
	store *Store
}

func (s *Server) getItem(w http.ResponseWriter, r *http.Request) {
	ctx, cancel := context.WithTimeout(r.Context(), 2*time.Second)
	defer cancel()

	id := r.PathValue("id")
	it, err := s.store.FindItem(ctx, id)
	if errors.Is(err, sql.ErrNoRows) {
		http.NotFound(w, r)
		return
	}
	if err != nil {
		log.Printf("FindItem: %v", err)
		http.Error(w, "internal error", http.StatusInternalServerError)
		return
	}
	fmt.Fprintf(w, "id=%s name=%s\n", it.ID, it.Name)
}
```

#### What happens here

- 2s timeout derived from the request context.
- `ErrNoRows` → 404; other errors → 500 + log.
- Store does not know about HTTP; Server does not write SQL strings outside the store in this example.

### Example 2: List with iteration

```go
func (s *Store) ListItems(ctx context.Context, limit int) ([]Item, error) {
	rows, err := s.db.QueryContext(ctx,
		`SELECT id, name FROM items ORDER BY name LIMIT $1`, limit)
	if err != nil {
		return nil, err
	}
	defer rows.Close()

	out := make([]Item, 0)
	for rows.Next() {
		var it Item
		if err := rows.Scan(&it.ID, &it.Name); err != nil {
			return nil, err
		}
		out = append(out, it)
	}
	return out, rows.Err()
}

func (s *Server) listItems(w http.ResponseWriter, r *http.Request) {
	ctx, cancel := context.WithTimeout(r.Context(), 3*time.Second)
	defer cancel()

	items, err := s.store.ListItems(ctx, 50)
	if err != nil {
		log.Printf("ListItems: %v", err)
		http.Error(w, "internal error", http.StatusInternalServerError)
		return
	}
	w.Header().Set("Content-Type", "application/json")
	_ = json.NewEncoder(w).Encode(items) // [] if empty
}
```

#### What happens here

- `QueryContext` respects cancellation.
- `rows.Err()` catches errors during iteration.
- Empty list → 200 + `[]`, not 404.

### Example 3: Transaction for an order

```go
var errInsufficientStock = errors.New("insufficient stock")

func (s *Store) PlaceOrder(ctx context.Context, userID, itemID string, qty int) error {
	tx, err := s.db.BeginTx(ctx, nil)
	if err != nil {
		return err
	}
	defer func() { _ = tx.Rollback() }()

	res, err := tx.ExecContext(ctx,
		`UPDATE items SET stock = stock - $1 WHERE id = $2 AND stock >= $1`, qty, itemID)
	if err != nil {
		return err
	}
	n, err := res.RowsAffected()
	if err != nil {
		return err
	}
	if n == 0 {
		return errInsufficientStock
	}
	_, err = tx.ExecContext(ctx,
		`INSERT INTO orders(user_id, item_id, qty) VALUES ($1,$2,$3)`, userID, itemID, qty)
	if err != nil {
		return err
	}
	return tx.Commit()
}

func (s *Server) postOrder(w http.ResponseWriter, r *http.Request) {
	ctx, cancel := context.WithTimeout(r.Context(), 3*time.Second)
	defer cancel()

	err := s.store.PlaceOrder(ctx, "u1", r.PathValue("id"), 1)
	if errors.Is(err, errInsufficientStock) {
		http.Error(w, "out of stock", http.StatusConflict)
		return
	}
	if err != nil {
		log.Printf("PlaceOrder: %v", err)
		http.Error(w, "internal error", http.StatusInternalServerError)
		return
	}
	w.WriteHeader(http.StatusCreated)
}
```

#### What happens here

- Two atomic steps → Tx.
- `defer Rollback` is safe; after `Commit` Rollback does no harm.
- Handler maps the domain error to 409.

### Example 4: Why not hold a Tx during render

```go
func (s *Server) badGetItem(w http.ResponseWriter, r *http.Request) {
	ctx := r.Context()
	tx, err := s.store.db.BeginTx(ctx, nil)
	if err != nil {
		http.Error(w, "internal error", 500)
		return
	}
	defer tx.Rollback()

	var it Item
	err = tx.QueryRowContext(ctx,
		`SELECT id, name FROM items WHERE id = $1`, r.PathValue("id"),
	).Scan(&it.ID, &it.Name)
	if errors.Is(err, sql.ErrNoRows) {
		http.NotFound(w, r)
		return
	}
	if err != nil {
		http.Error(w, "internal error", 500)
		return
	}
	// BAD: slow render while Tx lives
	time.Sleep(200 * time.Millisecond) // template simulation
	fmt.Fprintf(w, "%s\n", it.Name)
	_ = tx.Commit()
}
```

#### What happens here

- Tx lock/resource lives during slow I/O.
- Better: `FindItem` without a long Tx, then render.
- Same applies to external HTTP calls inside an open Tx.

### Example 5: Wiring in main + HTTP timeouts

```go
func main() {
	db, err := sql.Open("sqlite", "file:app.db?_pragma=foreign_keys(1)")
	if err != nil {
		log.Fatal(err)
	}
	defer db.Close()

	pingCtx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
	defer cancel()
	if err := db.PingContext(pingCtx); err != nil {
		log.Fatal(err)
	}

	store := &Store{db: db}
	srv := &Server{store: store}

	mux := http.NewServeMux()
	mux.HandleFunc("GET /item/{id}", srv.getItem)
	mux.HandleFunc("GET /items", srv.listItems)

	httpSrv := &http.Server{
		Addr:              ":8080",
		Handler:           mux,
		ReadHeaderTimeout: 5 * time.Second,
	}
	log.Fatal(httpSrv.ListenAndServe())
}
```

#### What happens here

- One pool for the process; `PingContext` at startup.
- Server struct carries dependencies — easy for a fake store in a test.
- HTTP timeouts remain; DB has its own context timeout per request.

### Example 6: Store interface (prep for tests)

```go
type ItemStore interface {
	FindItem(ctx context.Context, id string) (Item, error)
	ListItems(ctx context.Context, limit int) ([]Item, error)
}

type Server struct {
	store ItemStore
}
```

#### What happens here

- Handler depends on an interface, not a concrete `*sql.DB`.
- In 06.09: fake store with `sql.ErrNoRows` without a real database.
- Production `*Store` still uses the pool.

## Decision analysis

| Decision | Choice | Why |
|----------|--------|-----|
| DB in `context.Value` | No | Implicit, hard to test |
| `sql.Open` per request | No | Pool must be shared |
| Tx per request always | No | Overlong Tx, locks |
| Tx per use-case | Yes | Atomicity where needed |
| `ErrNoRows` → 404 | Yes for get-by-id | Resource semantics |
| Empty list → 404 | No | 200 + empty result |
| Tx during `ExecuteTemplate` | No | Holds resource needlessly |
| `r.Context()` in store | Yes | Cancellation and deadline |

## Trade-offs

- **Short timeout (2–3s)** — fast cancellation; complex reports need a separate endpoint/job.
- **Many small queries** — simple; solve N+1 with join/batch in the store.
- **SQLite in the demo** — easy start; production often Postgres + `pgx`.
- **Store interface** — testability; a bit more boilerplate.
- **Wide `MaxOpenConns`** — throughput; risk of killing the DB under a spike.

## Common mistakes

1. `Query` / `Exec` / `QueryRow` without Context in an HTTP handler.
2. `sql.Open` per request instead of a shared `*sql.DB` pool.
3. `ErrNoRows` → 500 instead of 404.
4. Empty list mapped to 404.
5. Tx open during slow I/O (template, payment HTTP).
6. Ignoring `rows.Close` / `rows.Err`.
7. String concatenation in SQL instead of placeholders.
8. Returning raw `err.Error()` to the client (schema leak).
9. `context.Background()` on the request path “so the query surely finishes”.
10. Holding `*sql.Tx` in a Server field across multiple requests.

## Idiomatic Go

- `errors.Is(err, sql.ErrNoRows)`.
- Sentinel / wrapped errors for the domain (`errInsufficientStock`).
- `Server` / `Store` structs with explicit fields (DI).
- Test store via an interface (next topic in 06.09).
- Migrations outside the request path (tool at startup/deploy).
- `PingContext` at startup; do not rely on `Open` alone.

## More detail: reading and cancellation

When the client aborts an HTML download, `r.Context()` is canceled. If `QueryContext` is still in progress, the driver should abort (depends on driver/DB). Therefore **do not** use `context.Background()` in the handler except for deliberately separate background jobs you do not tie to the response.

### Trace: client Abort during SELECT

```text
1. Handler entered QueryContext(ctx)
2. Driver sent the query, waiting for rows
3. Client closed TCP / browser Abort
4. net/http cancels r.Context()
5. ctx.Done closed → QueryContext returns an error
6. rows.Close (if Rows are open) → conn back to pool
7. Handler maps to 500 or stops writing the response
```

Background work after the response:

```go
go func() {
	ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()
	_ = s.store.Audit(ctx, payload)
}()
```

Deliberately: no completion guarantee on process shutdown — for critical work use a queue / outbox.

#### Predict, then answer

Does `WithTimeout(r.Context(), 2*time.Second)` cancel the query even when the client stays connected but the DB is 10s slow?

<details>
<summary>Answer</summary>

Yes — the child deadline expires after 2s, even if the parent request context still lives. That protects the pool from slow queries. Parent cancellation (Abort) still works earlier than 2s.
</details>

## Practical scenario

An e-commerce admin “order view” returned 500 when the ID did not exist — support thought the database was “crashing”. After mapping `ErrNoRows` → 404, 500 metrics drop and 404s rise as expected.

Second incident: checkout held a Tx while calling the payment API — lock on the stock row. Refactor: reserve stock in a short Tx, `Commit`, then payment; compensation (release) as a separate use-case on failure.

Third: handler used `context.Background()` for the list; on deploy old connections lingered. They switched to `r.Context()` + 3s timeout.

Fourth: a new endpoint called `sql.Open` in middleware “temporarily”. Under load test — connection explosion. They put the pool back in `main` in 20 minutes.

4. How do you map `sql.ErrNoRows` to HTTP? What about an empty list?
5. Why not hold a Tx during template render?
6. What do you pass into `QueryContext` from the handler?
7. Why store DI (a field on Server) instead of a global `db`?

## Summary

- `*sql.DB` is a long-lived pool; `Open` once, not per request.
- Queries on the request path go through `QueryContext` / `ExecContext` / `QueryRowContext` with `r.Context()`.
- Tie transactions (`BeginTx` / `Commit` / `defer Rollback`) to atomic use-cases.
- `ErrNoRows` → 404 for get-by-id; empty list → 200; do not hold a Tx during render.
- Separate HTTP and SQL boundaries (DI) for tests and clarity.
