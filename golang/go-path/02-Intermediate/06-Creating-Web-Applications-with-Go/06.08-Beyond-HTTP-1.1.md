# 06.08 Beyond HTTP/1.1: HTTP/2, h2c, push, graceful shutdown

> **Go Path - Zero to Gopher** / **02 Intermediate → Creating Web Applications with Go** / Lesson 06.08

## Lesson goals

After this lesson you should be able to:

- understand that **`net/http` automatically offers HTTP/2 over TLS** with `ListenAndServeTLS` (ALPN `h2`) on common platforms
- know what **h2c** (HTTP/2 cleartext) is and why it is not the first choice on a public edge
- treat **`http.Pusher` / Server Push** as a **deprecated / historical** feature — do not build new features on it
- implement **graceful shutdown** via `signal.NotifyContext` + `http.Server.Shutdown` (not `Close` for deploy)
- recognize `http.ErrServerClosed` as the expected end of `ListenAndServe`
- connect timeouts, readiness, and the Kubernetes grace period with process shutdown

## Prerequisite

- 06.01 (`http.Server`, `ReadHeaderTimeout` and other timeouts)
- basic TLS concepts (certificate, HTTPS, ALPN)
- `os/signal` / `signal.NotifyContext` (Go 1.16+)
- 06.06–06.07 (middleware, context) — useful for in-flight requests during shutdown

## Problem this lesson solves

Four misconceptions:

1. “I must specially enable HTTP/2” — for HTTPS with standard `ListenAndServeTLS` it often already works.
2. “Server Push speeds up the site” — Push is abandoned in practice; browsers and the platform went another way. `http.Pusher` is not a strategy for new code.
3. “`os.Exit` / kill the pod” — cuts active requests mid-write; you need `Shutdown`.
4. “HTTP/2 removes timeouts” — no; `ReadHeaderTimeout` and the rest still apply.

The lesson separates **what the standard library does for you** from **what to avoid**, and how to shut down the server cleanly in an orchestrated environment.

## Mental model

- **HTTP/1.1** — textual; keep-alive helps; pipelining / head-of-line limits on the HTTP layer.
- **HTTP/2** — binary framing, multiplexing streams over one TCP (+TLS) connection; less HOL blocking on the HTTP layer (TCP still exists).
- In Go, for a **TLS server**, HTTP/2 support is in `net/http` with a usual linux/windows amd64 build.
- **h2c** — HTTP/2 without TLS; useful behind a TLS-terminating proxy or in a lab; on the public web you expect HTTPS.
- **Shutdown** — stop accepting new; wait (with a context deadline) for old handlers to finish; then exit.
- **Close** — more aggressive; for urgent shutdown / some tests, not for rolling deploy.

```text
SIGTERM / Ctrl+C
  → signal.NotifyContext Done
    → ready = false (optional, LB removes from rotation)
      → Server.Shutdown(ctx)
        → does not accept new connections
        → waits for in-flight ServeHTTP (until timeout)
          → ListenAndServe returns ErrServerClosed
```

## Mechanism

The longest section: from TLS/HTTP/2 to graceful shutdown, with traces and checks.

### 1. HTTP/2 over TLS — automatic

```go
srv := &http.Server{
	Addr:              ":8443",
	Handler:           mux,
	ReadHeaderTimeout: 5 * time.Second,
}
log.Fatal(srv.ListenAndServeTLS("cert.pem", "key.pem"))
```

What happens when a modern client connects:

1. TCP connect to `:8443`.
2. TLS handshake; server offers ALPN protocols including `h2`.
3. Client chooses `h2` → HTTP/2 session.
4. Requests go as streams over the same connection.
5. If the client does not negotiate `h2`, it stays HTTP/1.1 over TLS — still OK.

For the usual case in modern Go you **do not need** to manually call `http2.ConfigureServer`. Focus: valid TLS + `&http.Server{}` with timeouts.

Lab check:

```text
curl -k -v --http2 https://localhost:8443/
# in the traces look for ALPN / HTTP/2
```

#### Execution trace — ListenAndServeTLS

```text
main: ListenAndServeTLS(cert, key)
  → TLS listener
  → accept
  → handshake + ALPN
       ├─ h2  → HTTP/2 framer → ServeHTTP per stream
       └─ http/1.1 → classic request loop
```

#### Predict, then answer

You start `ListenAndServe()` on `:8080` without TLS. Do clients automatically get HTTP/2?

<details>
<summary>Answer</summary>

Not in the standard public pattern. HTTP/2 in `net/http` for the server typically goes with TLS. Cleartext HTTP/2 is **h2c** and needs a special setup — see the next subsection.
</details>

### 2. h2c — a note, not the default production path

**h2c** = HTTP/2 cleartext (without TLS).

Where it makes sense:

- an internal service mesh / proxy that already terminates TLS on the edge
- lab and experiments

Where it does not:

- public browser traffic without HTTPS
- “faster without a certificate” on the internet — bad tradeoff (security, middleboxes)

Setup often goes through `golang.org/x/net/http2` + `h2c.NewHandler`. This lesson does **not** set h2c as the default production pattern — only so you know it exists and do not confuse it with automatic HTTP/2 over TLS.

#### Predict, then answer

Behind nginx that terminates TLS and speaks plain HTTP to the Go process: must Go serve h2c for the browser to see HTTP/2?

<details>
<summary>Answer</summary>

Not necessarily. Browser ↔ nginx can be HTTP/2; nginx ↔ Go often HTTP/1.1. h2c on the Go side is an option for internal optimization, not a condition for “the internet seeing h2”.
</details>

### 3. http.Pusher — deprecated strategy

Earlier, Server Push allowed the server to “push” CSS/JS before HTML asked for the resource:

```go
// HISTORICAL — do not use as the basis of a new architecture
if p, ok := w.(http.Pusher); ok {
	_ = p.Push("/static/app.css", nil)
}
```

Why not build on this:

- browser support is removed or irrelevant
- hard to guess what is already in cache — a wrong push **slows things down**
- the ecosystem pushes toward other techniques (CDN, cache, bundling, eventually Early Hints at the proxy layer)

`http.Pusher` still exists in the API for compatibility — that is **not** a signal that it is a good strategy for a 2026 web app.

#### Trace — why Push “looks like it works” in old code

```text
1. Type assert w.(http.Pusher) → ok on an HTTP/2 connection
2. Push sends PUSH_PROMISE
3. Modern browser ignores / does not use it
4. HTML still works via ordinary <link> — Push brought no gain
```

#### Predict, then answer

Code review finds `p.Push` in a handler from 2019. What do you propose?

<details>
<summary>Answer</summary>

Remove reliance on Push; leave ordinary links / static cache / CDN. Document in an ADR: “do not use http.Pusher for new features”.
</details>

### 4. Graceful shutdown: signal.NotifyContext + Shutdown

```go
ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt)
defer stop()

go func() {
	err := srv.ListenAndServe()
	if err != nil && !errors.Is(err, http.ErrServerClosed) {
		log.Fatal(err)
	}
}()

<-ctx.Done()
shutdownCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
defer cancel()
if err := srv.Shutdown(shutdownCtx); err != nil {
	log.Printf("shutdown: %v", err)
}
```

Steps:

1. `ListenAndServe` (or `ListenAndServeTLS`) in a goroutine — the main thread can wait for a signal.
2. Signal (Ctrl+C / SIGTERM) → `ctx.Done()`.
3. `Shutdown(shutdownCtx)` — stops accept; waits for active handlers until `shutdownCtx` expires.
4. `ListenAndServe` returns `http.ErrServerClosed` — **expected**, do not treat it as a fatal application error.

#### Execution trace — Ctrl+C during /slow

```text
t0  ListenAndServe in goroutine; GET /slow sleeps 5s
t1  Ctrl+C → NotifyContext Done
t2  Shutdown(10s) starts — new GET / rejected/not accepted
t3  /slow finishes ServeHTTP (~5s from start)
t4  Shutdown returns nil; process exits cleanly
t5  ListenAndServe → ErrServerClosed
```

If the shutdown timeout is **1s**, and `/slow` needs **5s**:

```text
t2  Shutdown(1s)
t3  timeout — Shutdown returns an error; connections are cut more aggressively
t4  /slow client sees a broken response
```

#### Predict, then answer

`ListenAndServe` in `main` without a goroutine, and you call `Shutdown` from a signal handler. Why is the goroutine pattern more common?

<details>
<summary>Answer</summary>

`ListenAndServe` blocks. If you keep it in `main` without parallel logic for the signal, it is harder to cleanly connect “wait for signal → Shutdown”. Typical pattern: listen in a goroutine, `main` waits `<-ctx.Done()`, then `Shutdown`.
</details>

### 5. Shutdown vs Close

```go
_ = srv.Close()           // immediately: listener + more aggressive cutoff
_ = srv.Shutdown(ctx)     // waits for handlers until ctx.Done()
```

| | `Shutdown` | `Close` |
|---|------------|---------|
| New accept | no | no |
| In-flight | waits (until ctx) | cuts faster |
| Deploy / SIGTERM | yes | no (except urgent) |
| Test teardown | sometimes | often OK |

#### Predict, then answer

In Kubernetes SIGTERM arrives. You call `Close()` instead of `Shutdown`. What do you see in metrics?

<details>
<summary>Answer</summary>

A spike of 5xx / interrupted checkouts during a rolling update — active requests do not get time to finish. Correct: `Shutdown` + grace aligned with `terminationGracePeriodSeconds`.
</details>

### 6. ErrServerClosed

```go
err := srv.ListenAndServe()
if err != nil && !errors.Is(err, http.ErrServerClosed) {
	log.Fatal(err)
}
```

Without this check: every successful graceful shutdown looks like “Fatal” in the log — a false alarm in CI/CD and paging.

### 7. Timeouts still apply with HTTP/2

```go
srv := &http.Server{
	Addr:              ":8443",
	Handler:           mux,
	ReadHeaderTimeout: 5 * time.Second,
	ReadTimeout:       15 * time.Second,
	WriteTimeout:      30 * time.Second,
	IdleTimeout:       60 * time.Second,
}
```

HTTP/2 multiplexing does **not** replace protection against slow/stuck clients. Especially watch long streams (SSE): `WriteTimeout` can cut legitimate streams — then the route needs special treatment.

### 8. Readiness on shutdown + K8s grace

Advanced pattern: before `Shutdown` mark the pod as not-ready so the LB stops sending new requests.

```text
SIGTERM
  → ready.Store(false)
  → short sleep (aligned with LB probe interval)
  → Shutdown(shutdownCtx)
```

Kubernetes:

```text
terminationGracePeriodSeconds: 20
Shutdown timeout:               15s
sleep before Shutdown:          ~2s (example)
sum < grace  → you avoid SIGKILL mid-work
```

If the Shutdown timeout is **longer** than the grace period, kube still sends SIGKILL — the graceful plan fails.

#### Trace — aligned deploy

```text
t0  kube SIGTERM
t1  app: ready=false
t2  sleep 2s — probe sees 503, LB removes pod
t3  Shutdown(15s) — finishes in-flight
t4  exit 0
t5  grace 20s has not expired — no SIGKILL
```

#### Predict, then answer

`terminationGracePeriodSeconds: 10`, and `Shutdown` waits 30s. Outcome?

<details>
<summary>Answer</summary>

After ~10s kube sends SIGKILL. `Shutdown` does not finish — same symptom as without graceful. Shorten the Shutdown timeout below grace (leave a buffer).
</details>

### Mechanism — decision map

```text
Need HTTP/2 for the public web?
  → ListenAndServeTLS + timeouts (automatic h2 via ALPN)

Internal cleartext h2?
  → h2c only deliberately; not as default edge

Static performance?
  → cache, CDN, bundling — NOT http.Pusher

Shutdown in K8s?
  → NotifyContext → (ready=false) → Shutdown
  → ignore ErrServerClosed as fatal
  → align timeout with grace period
```

## Rules and syntax

- Production: HTTPS (Let’s Encrypt / platform / mesh).
- Always set at least `ReadHeaderTimeout` on `Server`.
- `Shutdown` + check `errors.Is(err, http.ErrServerClosed)`.
- Do not call `Close()` when you want a graceful deploy.
- Do not build features on `http.Pusher`.
- Long-lived streams (SSE) can hold shutdown — know your routes.
- Align shutdown timeout with the orchestrator (K8s grace).

### Example 1: HTTPS server with timeouts

```go
srv := &http.Server{
	Addr:              ":8443",

	ReadHeaderTimeout: 5 * time.Second,
	ReadTimeout:       15 * time.Second,

log.Println("https on :8443")
log.Fatal(srv.ListenAndServeTLS("cert.pem", "key.pem"))
```

#### What happens here

- Timeouts still apply.
- Local self-signed cert for the lab; in production a real certificate chain.

### Example 2: Graceful shutdown with a signal

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"log"
	"net/http"
	"os"
	"os/signal"
	"time"
)

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /{$}", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, "ok")
	})
	mux.HandleFunc("GET /slow", func(w http.ResponseWriter, r *http.Request) {
		time.Sleep(5 * time.Second)
		fmt.Fprintln(w, "done")
	})

	srv := &http.Server{
		Addr:              ":8080",
		Handler:           mux,
		ReadHeaderTimeout: 5 * time.Second,
	}

	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt)
	defer stop()

	go func() {
		log.Println("listen :8080")
		err := srv.ListenAndServe()
		if err != nil && !errors.Is(err, http.ErrServerClosed) {
			log.Fatal(err)
		}
	}()

	<-ctx.Done()
	log.Println("shutting down...")
	shCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()
	if err := srv.Shutdown(shCtx); err != nil {
		log.Printf("shutdown error: %v", err)
	}
	log.Println("done")
}
```

#### What happens here

- Ctrl+C → `Shutdown`.
- If `/slow` is still running, waits up to 10s.
- New requests are not accepted after shutdown starts.
- `ErrServerClosed` is not a fatal program error.

### Example 3: Misguided reliance on Push (don’t)

```go
func legacy(w http.ResponseWriter, r *http.Request) {
	if p, ok := w.(http.Pusher); ok {
		_ = p.Push("/static/app.css", &http.PushOptions{Method: http.MethodGet})
	}
	fmt.Fprint(w, `<link rel="stylesheet" href="/static/app.css">`)
}
```

#### What happens here

- The code compiles; on some stacks it does something.
- As a performance strategy it is obsolete.
- Prefer an ordinary link / preload at HTML or proxy level without `Pusher` as a foundation.

### Example 4: Shutdown + middleware recover

```go
h := withLog(withRecover(mux))
srv.Handler = h
```

#### What happens here

- Graceful does not replace recover; recover does not replace graceful.
- Signal → Shutdown waits for `ServeHTTP` to finish (including recover branches).
- Align K8s `terminationGracePeriodSeconds` with the shutdown timeout.

### Example 5: Close vs Shutdown in test thinking

```go
func demo() {
	srv := &http.Server{Addr: ":0", Handler: mux, ReadHeaderTimeout: time.Second}
	// urgent / test:
	_ = srv.Close()
	// deploy:
	_ = srv.Shutdown(context.Background())
}
```

#### What happens here

- `Close` for abrupt shutdown.
- `Shutdown` for SIGTERM and rolling update.
- In K8s: SIGTERM → your `Shutdown` → if too long, SIGKILL.

### Example 6: Readiness probe sketch

```go
var ready atomic.Bool

func main() {
	ready.Store(true)
	mux := http.NewServeMux()
	mux.HandleFunc("GET /health/live", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, "ok")
	})
	mux.HandleFunc("GET /health/ready", func(w http.ResponseWriter, r *http.Request) {
		if !ready.Load() {
			http.Error(w, "not ready", http.StatusServiceUnavailable)
			return
		}
		fmt.Fprintln(w, "ok")
	})
	// ... Listen + signal ...
	ready.Store(false)
	time.Sleep(2 * time.Second)
	_ = srv.Shutdown(shCtx)
}
```

#### What happens here

- Live stays “process is alive”; ready goes to false before Shutdown.
- LB removes the pod from rotation before you cut in-flight.

### Example 7: Full lifecycle with TLS and signal

```go
func run(ctx context.Context, srv *http.Server) error {
	errCh := make(chan error, 1)
	go func() {
		err := srv.ListenAndServeTLS("cert.pem", "key.pem")
		if err != nil && !errors.Is(err, http.ErrServerClosed) {
			errCh <- err
			return
		}
		errCh <- nil
	}()

	select {
	case <-ctx.Done():
		shCtx, cancel := context.WithTimeout(context.Background(), 15*time.Second)
		defer cancel()
		_ = srv.Shutdown(shCtx)
		return <-errCh
	case err := <-errCh:
		return err
	}
}
```

#### What happens here

- The same pattern works for TLS: HTTP/2 stays automatic; lifecycle is orthogonal.
- `select` separates “shutdown signal” from “listen error at start” (e.g. port in use).
- `ErrServerClosed` is still not fatal after `Shutdown`.

### Example 8: In-flight counter during a shutdown exercise

```go
var inFlight atomic.Int64

func withInFlight(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		inFlight.Add(1)
		defer inFlight.Add(-1)
		next.ServeHTTP(w, r)
	})
}

// in the log before/after Shutdown:
log.Printf("in-flight before shutdown: %d", inFlight.Load())
```

#### What happens here

- You see how many `ServeHTTP` are still running when shutdown starts.
- After a successful `Shutdown` you expect 0 (unless the timeout cut them).
- Useful in the lab and in metrics (Gauge) — does not replace readiness.

### More detailed trace: from SIGTERM to ErrServerClosed

```text
1. kube sends SIGTERM to the process
2. signal.NotifyContext closes ctx
3. (optional) ready=false; sleep so the probe sees 503
4. Shutdown:
   a. stops Accept on the listener
   b. idle connections are closed
   c. active handlers get time until shutdownCtx.Done()
5. when all finish (or ctx expires): Shutdown return
6. ListenAndServeTLS/ListenAndServe return ErrServerClosed
7. main exits; kube sees exit != SIGKILL
```

If step 4c lasts longer than `terminationGracePeriodSeconds`, kube injects SIGKILL between 5 and 7 — logs disappear, 5xx metrics spike.

#### Predict, then answer

You have an SSE endpoint that holds a connection for hours. Shutdown timeout is 15s. What happens on deploy?

<details>
<summary>Answer</summary>

`Shutdown` waits up to 15s, then cuts remaining connections (including SSE). Clients must reconnect. Alternative: shorter stream timeout, or an LB that stops sending new SSE before shutdown + client reconnect policy.
</details>

### Checklist: timeouts beside the protocol

| Timeout | Protects against | Note with HTTP/2 |
|---------|------------------|------------------|
| `ReadHeaderTimeout` | Slowloris / slow headers | Remains mandatory |
| `ReadTimeout` | slow body read | Per connection / request policy |
| `WriteTimeout` | stuck write | Watch with SSE |
| `IdleTimeout` | dead keep-alive / idle stream | Useful on the edge |
| Shutdown ctx | overlong deploy | Align with K8s |

HTTP/2 does **not** erase this table. It only changes how frames share one TCP connection.

During `Shutdown` a handler that holds `QueryContext(r.Context())` is still running. Does the DB query get cancel immediately?

<details>
<summary>Answer</summary>

</details>

## Decision analysis

| Decision | Choice | Why |
|----------|--------|-----|
| HTTP/2 | Via TLS + `ListenAndServeTLS` | Standard Go path |
| h2c public on the edge | No | Without TLS |
| Server Push / `http.Pusher` | No for new | Deprecated in practice |
| `Shutdown` on SIGTERM | Yes | Finishes requests |
| `Close` on deploy | No | Cuts in-flight |
| Shutdown timeout 10–30s | Typical | Align with orchestrator |
| Ignore `ErrServerClosed` as fatal | Yes | Expected end |
| WriteTimeout vs SSE | Watch | Stream needs special treatment |

## Trade-offs

- **Short shutdown timeout** — fast deploy; cuts slow requests.
- **Long timeout** — finishes work; slower rolling update.
- **HTTP/1.1 only behind an old proxy** — rare; most modern LBs speak h2 or terminate TLS.
- **Self-signed in the lab** — fast; do not mix with the production trust store.
- **Readiness sleep** — fewer 5xx; slightly longer shutdown.

## Common mistakes

1. Treating `ErrServerClosed` as fatal (`log.Fatal` after every graceful).
2. No SIGTERM handler in the container — killed requests.
3. Shutdown timeout longer than K8s grace period — SIGKILL anyway.
4. Building features on `http.Pusher`.
5. Thinking HTTP/2 removes the need for `ReadHeaderTimeout`.
6. `Shutdown` before the server has actually started (race in a test) — synchronize.
7. `ListenAndServe` in `main` without a goroutine / without a clear point for the signal.
8. Mixing h2c and “automatic HTTP/2 over TLS” in team docs.
9. `WriteTimeout` on an SSE route without a deliberate decision.
10. Shutting down with `os.Exit(0)` from a signal handler without `Shutdown`.

## Idiomatic Go

- `signal.NotifyContext` + `Server.Shutdown`.
- Explicit `&http.Server{...}` instead of bare `http.ListenAndServe` in production.
- Log start/end of shutdown; optionally an in-flight counter (`atomic` + middleware).
- Health: `/health/live` vs `/health/ready` — on shutdown ready → false.
- `errors.Is(err, http.ErrServerClosed)`.

## More on HTTP/2 in practice for a web app

Multiplexing helps when a page pulls many small resources from the **same host**. Still true:

- compression (proxy or `Content-Encoding`)
- cache headers for static
- do not send huge HTML without need
- HTTP/2 is not an excuse for N+1 JSON calls from the browser — API design still matters

For local development you often stay on HTTP/1.1 cleartext (`:8080`); that is fine. Test HTTP/2 on staging with real TLS.

### Trace — 20 small static files

```text
HTTP/1.1 (without enough parallel connections):
  browser opens a limited number of TCP → waiting in queue

HTTP/2:
  one TLS session → more streams → less waiting on the HTTP layer
  (TCP HOL still exists on the lower layer)
```

#### Predict, then answer

The team says: “we moved to HTTP/2, N+1 API calls from the SPA are no longer a problem”. Correct?

<details>
<summary>Answer</summary>

No. Multiplexing reduces transport cost, but N+1 still means N round-trip logic, N serialization, N auth checks. API design (batch/join) is still needed.
</details>

## Practical scenario

A team kills pods in Kubernetes and sees a 5xx spike during rolling update. Cause: the process dies on SIGTERM without `Shutdown`; active checkouts break. They introduce `NotifyContext` + 15s `Shutdown`, and `terminationGracePeriodSeconds: 20`. 5xx during deploy drops.

Another team “optimizes” LCP via Server Push in Go in 2018. 2024–2026 Push does not work in target browsers — they remove the code, rely on HTTP/2 + CDN cache. ADR: “do not use http.Pusher”.

Third: shutdown timeout 60s, grace 30s — still SIGKILL. They shortened Shutdown to 20s; the problem disappeared.

## Summary

- HTTP/2 comes with TLS + `ListenAndServeTLS` on common platforms.

- `signal.NotifyContext` + `Shutdown`, respect `ErrServerClosed`, align timeouts and readiness with the K8s grace period.

## Local certificate for the lab (sketch)

For an HTTP/2 exercise locally generate a self-signed pair (openssl or a small `go run` tool). The browser will warn — for curl use `-k`. Do not commit private keys to git. In production use the platform’s automatic certificate issuer.

### Readiness on shutdown (advanced sketch)

```go
var ready atomic.Bool
ready.Store(true)

mux.HandleFunc("GET /health/ready", func(w http.ResponseWriter, r *http.Request) {
	if !ready.Load() {
		http.Error(w, "not ready", http.StatusServiceUnavailable)
		return
	}
	fmt.Fprintln(w, "ok")
})

// before Shutdown:
ready.Store(false)
time.Sleep(2 * time.Second) // LB removes pod from rotation
_ = srv.Shutdown(shCtx)
```

This reduces requests that fail mid-deploy. Align the sleep with the LB check interval.

### What to remember in one sentence

TLS + a standard `Server` covers HTTP/2 for a typical Go web service; h2c is a specialization; Push is not the future; `Shutdown` is a mandatory part of the lifecycle in orchestrated environments.
