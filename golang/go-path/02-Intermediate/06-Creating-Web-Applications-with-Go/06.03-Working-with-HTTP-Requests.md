# 06.03 Working with HTTP requests: forms, cookies, context, body limit

> **Go Path - Zero to Gopher** / **02 Intermediate → Creating Web Applications with Go** / Lesson 06.03

## Lesson goals

After this lesson you should be able to:

- parse HTML forms via `ParseForm` / `ParseMultipartForm` and read `r.Form` / `r.PostForm`
- understand why `PostForm` protects against query “injection” of values
- set and read a **cookie** (`http.SetCookie`, `r.Cookie`) with `HttpOnly`, `Secure`, `SameSite`
- understand why `context.WithValue` is not a generic “request bag” for everything
- limit request body size (`http.MaxBytesReader` or `io.LimitReader`) **before** parsing
- connect these mechanisms to CSRF/session at an awareness level (without a full security course and without attack procedures)

## Prerequisite

- 06.01 and 06.02 (server, mux, redirect, PRG, PathValue)
- basic HTML `<form method="POST">`
- `io.Reader` / `context` basics
- awareness that the request body is a stream read once

## Problem this lesson solves

Handlers that “just read” the body often:

- call `ParseForm` after the body is already consumed
- mix query (`?x=`) and POST fields without `PostForm`
- suffer a 2 GB upload because there is no limit
- push user ID, DB pool, logger, everything into `context.Value` until the code becomes unreadable
- set a session cookie without `HttpOnly` / `Secure` / `SameSite`
- believe that “cookie exists ⇒ POST is the user’s intent” (CSRF awareness)

The lesson teaches the **request input layer**: how to extract data the client sent safely and predictably, with defensive limits and clear boundaries for context.

## Mental model

A request is a **message with several drawers**:

1. **URL** — path, query string
2. **Headers** — cookie, content-type, auth
3. **Body** — form-urlencoded, multipart, JSON (JSON more in API lessons; here forms)
4. **Context** — cancellation + *rare* request-scoped values (request ID), not a substitute for function parameters

```text
  ┌─────────────────────────────────────────────┐
  │ *http.Request                               │
  │  URL.Path / RawQuery  → query fields        │
  │  Header (Cookie, CT)  → cookie, body type   │
  │  Body (io.ReadCloser) → form / multipart    │
  │  Context              → Done + rare values  │
  └─────────────────────────────────────────────┘
           │
           ▼ after ParseForm
  Form     = query ∪ post   (merged)
  PostForm = body only
```

`ParseForm` fills maps from query + body (for POST/PUT/PATCH with the matching content-type). `PostForm` looks at the body only. A cookie is a small piece of state the browser sends back — the server signs/validates it in a real app (here we learn the API, not production crypto).

A body limit is a **valve**: without it one client can fill memory.

## Mechanism

### Forms — ParseForm and ParseMultipartForm

```go
if err := r.ParseForm(); err != nil {
	http.Error(w, "invalid form", http.StatusBadRequest)
	return
}
email := r.PostForm.Get("email")
```

| API | When | What it fills |
|-----|------|---------------|
| `ParseForm` | `application/x-www-form-urlencoded` (+ query) | `Form`, `PostForm` |
| `ParseMultipartForm(maxMemory)` | `multipart/form-data` | same + files |
| `FormValue` / `PostFormValue` | convenient | internally calls Parse*; **swallows error** |

Rules:

- `r.Form` includes query + post
- `r.PostForm` only post (body)
- For authentication / state changes prefer **`PostForm`**
- limit the body **before** `ParseForm`

#### Trace — successful urlencoded POST

```text
POST /login
Content-Type: application/x-www-form-urlencoded
Body: user=marko&pass=secret

1) r.Body = MaxBytesReader(w, r.Body, 4096)
2) ParseForm()
   reads body → PostForm["user"]=["marko"], PostForm["pass"]=["secret"]
   query empty → Form ≈ PostForm
3) PostForm.Get("user") → "marko"
```

#### Trace — query tries to “inject” user

```text
POST /login?user=admin
Body: user=marko&pass=secret

After ParseForm:
  PostForm.Get("user") → "marko"   // body only
  Form.Get("user")     → depends on merge order / first value
                         // easy to confuse — do NOT use for login

Conclusion: for POST fields → PostForm
```

**Predict, then answer:** What does `r.FormValue("user")` do in the example above?

Answer: Internally calls `ParseForm` (if not already) and reads from `Form` — may return a value from the query. Parsing error is swallowed. Handy in a demo; dangerous for authentication.

**Predict, then answer:** If before `ParseForm` you do `io.ReadAll(r.Body)`, what happens?

Answer: The body is consumed. `ParseForm` has nothing left to read (or sees EOF) — fields stay empty / error. One stream, one read.

### Multipart — text + file

```go
r.Body = http.MaxBytesReader(w, r.Body, 8<<20)
if err := r.ParseMultipartForm(4 << 20); err != nil {
	http.Error(w, "multipart error", http.StatusBadRequest)
	return
}
title := r.FormValue("title")
file, hdr, err := r.FormFile("photo")
```

`ParseMultipartForm(maxMemory)` keeps part in memory; the rest may go to disk (by implementation). `MaxBytesReader` still holds the **upper** bound of the whole HTTP body.

#### Trace — small upload

```text
POST /upload  multipart
  field title="cv"
  field photo= file 200KiB

MaxBytesReader limit = 8MiB  → OK
ParseMultipartForm(4MiB)     → metadata + part in memory
FormFile("photo")            → ReadCloser + Header{Filename, Size, ...}
handler reads file / rejects
```

**Predict, then answer:** May you blindly use `hdr.Filename` as a path on disk?

Answer: No. That is a client string (may contain `../` ideas). Use your own name ID; Filename is metadata for display/log with sanitization.

### Cookie — SetCookie, reading, flags

```go
http.SetCookie(w, &http.Cookie{
	Name:     "sid",
	Value:    sessionID,
	Path:     "/",
	HttpOnly: true,
	Secure:   true, // HTTPS
	SameSite: http.SameSiteLaxMode,
	MaxAge:   3600,
})

c, err := r.Cookie("sid")
```

| Flag | Idea (concept) |
|------|----------------|
| `HttpOnly` | JS in the page does not read the cookie (reduces theft via XSS) |
| `Secure` | sent only over HTTPS |
| `SameSite` | Lax/Strict/None — affects when the browser sends the cookie on cross-site requests |
| `Path` / `Domain` | scope; Path must match on delete too |
| `MaxAge` | lifetime; `-1` deletes |

These are **flag concepts**, not an attack recipe. In production the session value is an opaque ID, not a plain-text role.

#### Trace — set then read

```text
Handler loginPost:
  SetCookie Name=sid Value=abc Path=/ HttpOnly SameSite=Lax
  → response: Set-Cookie: sid=abc; Path=/; HttpOnly; SameSite=Lax
  Redirect 303 → /me

Browser next GET /me:
  Cookie: sid=abc
  r.Cookie("sid") → Value "abc", err=nil
```

#### Trace — delete

```text
SetCookie Name=sid Value="" MaxAge=-1 Path=/ HttpOnly
→ browser removes cookie for that Name+Path
If Path does not match original → cookie “survives” (classic logout bug)
```

**Predict, then answer:** Why is a demo cookie with `Value: user` not a production pattern?

Answer: A username in plain text can be changed by the client. You need an opaque session ID + server-side store / signed token — a sessions topic, not this intro.

**Predict, then answer:** What does `SameSite=Lax` do at the idea level?

Answer: The browser is more restrictive about sending the cookie on cross-site requests (e.g. many cross-site POSTs without the cookie). That **reduces** classic CSRF vectors, but is not the only complete protection — that is why CSRF token awareness exists too.

### MaxBytesReader — body limit

```go
r.Body = http.MaxBytesReader(w, r.Body, 1<<20) // 1 MiB
if err := r.ParseForm(); err != nil {
	// may be *http.MaxBytesError or a related error
	http.Error(w, "too large or invalid", http.StatusRequestEntityTooLarge)
	return
}
```

Set the limit **before** any body read. `MaxBytesReader` on overrun can affect the response — check your version’s docs and treat the error as 413/400.

#### Typical limits per route (orientation, not dogma)

```text
POST /login          → 4 KiB – 16 KiB   (username/password)
POST /settings       → 64 KiB – 256 KiB (ordinary form)
POST /upload         → 2 MiB – 32 MiB   (file; better a separate service)
JSON API (later)     → often 1 MiB default + per endpoint
```

**Predict, then answer:** Why does login have a stricter limit than upload?

Answer: A login body is small by nature; a large “login” is a sign of abuse or a bug. Upload legitimately carries a file — but still has a ceiling.

#### Trace — oversized body

```text
Limit = 4096 bytes
Client sends body 10000 bytes

ParseForm / Read:
  reads to the limit → MaxBytes* error
  handler returns 413/400
  memory does not grow with an “infinite” body
```

**Predict, then answer:** Does `ReadHeaderTimeout` replace `MaxBytesReader`?

Answer: No. Timeout measures time; MaxBytes measures bytes. Slow small request vs huge fast request — different attacks, different axes.

**Predict, then answer:** Where to put the limit — in every handler or in middleware?

Answer: Both work. Middleware with a default limit + a stricter limit on login/upload routes is a common pattern.

### context.WithValue — caution

```go
type ctxKey int
const reqIDKey ctxKey = 1

ctx := context.WithValue(r.Context(), reqIDKey, id)
r = r.WithContext(ctx)
```

**Use for:** request ID, span ID, authenticated user *if* the team has a clear convention.

**Do not use for:** required dependencies (DB, config, logger) — pass explicitly in a struct/handler dependency. Context values are silent, invisible in the function signature, hard to test.

A private key type (`type ctxKey int`) prevents collision with other packages that use the same string `"reqID"`.

#### Trace — request ID through the chain

```text
withRequestID middleware:
  id = Header X-Request-ID or new nano id
  ctx = WithValue(r.Context(), reqIDKey, id)
  next(w, r.WithContext(ctx))

handler:
  requestIDFrom(r.Context()) → id
  log.Printf("req=%s failed: %v", id, err)
```

#### Trace — bad pattern (anti-example)

```text
ctx.Value("db")     → *sql.DB
ctx.Value("cfg")    → Config
ctx.Value("user")   → User
ctx.Value("logger") → Logger

Function signature: func Do(ctx context.Context) error
→ you do not see dependencies; tests lie; type assertions everywhere
```

**Predict, then answer:** Why can string key `"db"` from two packages collide?

Answer: Same string literal = same key. Package A and package B both put `"db"` — one overwrites the other or reads the wrong type. A private key type per package cuts that.

**Predict, then answer:** How do you idiomatically pass `*sql.DB` into a handler?

Answer: A field on a struct: `type Handlers struct { DB *sql.DB }`, method receiver `func (h *Handlers) Login(...)`. Explicit, visible in the test.

## Rules and syntax

- Always check the `ParseForm` / `ParseMultipartForm` error.
- For form fields use `PostForm.Get` when you do not want the query to “inject” a value.
- For multi-select: `r.PostForm["tag"]` returns `[]string`, not only `Get`.
- Cookie `Name`/`Value` — do not freely put sensitive data in plain text in production.
- Context key type: **private type** (`type key int`) so string keys do not collide.
- Set the limit **before** reading the body.
- `r.FormValue("x")` calls ParseForm internally and swallows the error — handy in a demo, careful in production.
- When deleting a cookie match `Name` and `Path` (and Domain if you used it).

## Examples

### Example 1: Login form (ParseForm + PostForm + cookie + PRG)

```go
package main

import (
	"fmt"
	"log"
	"net/http"
	"time"
)

func loginForm(w http.ResponseWriter, r *http.Request) {
	w.Header().Set("Content-Type", "text/html; charset=utf-8")
	fmt.Fprint(w, `
<form method="POST" action="/login">
  <input name="user" />
  <input name="pass" type="password" />
  <button>Sign in</button>
</form>`)
}

func loginPost(w http.ResponseWriter, r *http.Request) {
	r.Body = http.MaxBytesReader(w, r.Body, 4096)
	if err := r.ParseForm(); err != nil {
		http.Error(w, "form too large or invalid", http.StatusBadRequest)
		return
	}
	user := r.PostForm.Get("user")
	pass := r.PostForm.Get("pass")
	if user == "" || pass == "" {
		http.Error(w, "missing fields", http.StatusBadRequest)
		return
	}
	// demo: no real password check
	http.SetCookie(w, &http.Cookie{
		Name:     "demo_user",
		Value:    user,
		Path:     "/",
		HttpOnly: true,
		SameSite: http.SameSiteLaxMode,
		MaxAge:   3600,
	})
	http.Redirect(w, r, "/me", http.StatusSeeOther)
}

func me(w http.ResponseWriter, r *http.Request) {
	c, err := r.Cookie("demo_user")
	if err != nil {
		http.Error(w, "not signed in", http.StatusUnauthorized)
		return
	}
	fmt.Fprintf(w, "hello, %s\n", c.Value)
}

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /login", loginForm)
	mux.HandleFunc("POST /login", loginPost)
	mux.HandleFunc("GET /me", me)

	srv := &http.Server{Addr: ":8080", Handler: mux, ReadHeaderTimeout: 5 * time.Second}
	log.Fatal(srv.ListenAndServe())
}
```

#### What happens here

- Limit 4 KiB before `ParseForm`.
- `PostForm` reads fields from the body, not from a `?user=` query trick.
- Cookie carries a demo identity; PRG leads to `/me`.

#### Trace

```text
GET /login → HTML
POST /login body user=marko&pass=x
  MaxBytes OK → ParseForm → PostForm user=marko
  Set-Cookie demo_user=marko
  303 → /me
GET /me Cookie: demo_user=marko → "hello, marko"
```

**Predict, then answer:** What if someone does `POST /login?user=admin` with body `user=marko` and you read `Form.Get`?

Answer: You may get the wrong “user” depending on the merge. That is why `PostForm`.

### Example 2: Multipart (text + small file)

```go
func upload(w http.ResponseWriter, r *http.Request) {
	r.Body = http.MaxBytesReader(w, r.Body, 8<<20)
	if err := r.ParseMultipartForm(4 << 20); err != nil {
		http.Error(w, "multipart error", http.StatusBadRequest)
		return
	}
	title := r.FormValue("title")
	file, hdr, err := r.FormFile("photo")
	if err != nil {
		http.Error(w, "no file", http.StatusBadRequest)
		return
	}
	defer file.Close()
	fmt.Fprintf(w, "title=%s name=%s size=%d\n", title, hdr.Filename, hdr.Size)
}
```

#### Trace

```text
max body 8MiB, maxMemory 4MiB
file 1MiB → OK, prints name
file 20MiB → MaxBytes error → 400
```

**Predict, then answer:** Why do you have both MaxBytesReader and the maxMemory argument?

Answer: MaxBytes = hard ceiling of the HTTP body. maxMemory = how much multipart keeps in RAM before spilling to disk. Different controls.

### Example 3: Request ID in context (narrow use)

```go
type ctxKey int

const reqIDKey ctxKey = 1

func withRequestID(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		id := r.Header.Get("X-Request-ID")
		if id == "" {
			id = fmt.Sprintf("%d", time.Now().UnixNano())
		}
		ctx := context.WithValue(r.Context(), reqIDKey, id)
		w.Header().Set("X-Request-ID", id)
		next.ServeHTTP(w, r.WithContext(ctx))
	})
}

func requestIDFrom(ctx context.Context) string {
	v, _ := ctx.Value(reqIDKey).(string)
	return v
}
```

#### Trace

```text
Request without X-Request-ID
  middleware generates id="1712..."
  WithValue → next handler
  log uses requestIDFrom
  response has X-Request-ID header (correlation)
```

**Predict, then answer:** Should this middleware put `*sql.DB` in context?

Answer: No. Pass DB into a handler struct.

### Example 4: Form vs PostForm confusion

```go
func ambiguous(w http.ResponseWriter, r *http.Request) {
	_ = r.ParseForm()
	fmt.Fprintln(w, "Form:", r.Form.Get("user"))
	fmt.Fprintln(w, "PostForm:", r.PostForm.Get("user"))
}
```

Call: `POST /login?user=admin` with body `user=marko`.

#### Trace

```text
PostForm.Get("user") → "marko"
Form.Get("user")     → may be "admin" or "marko"
                       (depends on order in url.Values)
```

**Predict, then answer:** Which map do you use for the password?

Answer: Exclusively `PostForm` (or the equivalent from the body only). A password in the query must not be the source of truth — and it leaks into URL logs.

### Example 5: Multiple values of the same field

```go
_ = r.ParseForm()
tags := r.PostForm["tag"] // []string
for _, t := range tags {
	fmt.Fprintln(w, t)
}
```

#### Trace

```text
Body: tag=go&tag=http&tag=web
PostForm["tag"] = ["go", "http", "web"]
Get("tag") = "go"   // only the first
```

**Predict, then answer:** Why is `Get` not enough for multi-select?

Answer: It returns only the first value; the rest are lost if you do not read the slice from the map.

### Example 6: Logout — deleting the cookie

```go
func logout(w http.ResponseWriter, r *http.Request) {
	http.SetCookie(w, &http.Cookie{
		Name:     "demo_user",
		Value:    "",
		Path:     "/",
		MaxAge:   -1,
		HttpOnly: true,
		SameSite: http.SameSiteLaxMode,
	})
	http.Redirect(w, r, "/login", http.StatusSeeOther)
}
```

#### Trace

```text
Path must be "/" as when SetCookie in login
MaxAge=-1 → browser deletes
next GET /me → Cookie not found → 401
```

### Example 7: LimitReader vs MaxBytesReader

```go
// LimitReader — pure read limit (not tied to ResponseWriter):
r.Body = io.NopCloser(io.LimitReader(r.Body, 4096))

// MaxBytesReader — net/http helper tied to ResponseWriter:
r.Body = http.MaxBytesReader(w, r.Body, 4096)
```

#### Trace

```text
LimitReader: after N bytes → EOF; you decide the status code
MaxBytesReader: on overrun may signal a MaxBytesError-type error
               and help the connection behave correctly with w
```

**Predict, then answer:** Which do you choose in new `net/http` web code?

Answer: Typically `MaxBytesReader` at the handler/middleware entrance. `LimitReader` is a general `io` tool — useful, but less “HTTP aware”.

### Example 8: httptest form in a test

```go
func TestLoginPostForm(t *testing.T) {
	form := url.Values{}
	form.Set("user", "marko")
	form.Set("pass", "x")
	body := strings.NewReader(form.Encode())

	req := httptest.NewRequest(http.MethodPost, "/login?user=admin", body)
	req.Header.Set("Content-Type", "application/x-www-form-urlencoded")
	rr := httptest.NewRecorder()

	loginPost(rr, req)

	if rr.Code != http.StatusSeeOther {
		t.Fatalf("code=%d", rr.Code)
	}
	// cookie should carry "marko", not "admin" from the query
}
```

#### Trace

```text
Query user=admin, body user=marko
PostForm → marko
Set-Cookie demo_user=marko
303 Location /me
```

**Predict, then answer:** What is missing if you forget the `Content-Type` header in the test?

Answer: `ParseForm` may not treat the body as urlencoded — fields empty, handler returns 400. The test must imitate the browser.

### Example 9: Struct handler instead of context DB

```go
type Handlers struct {
	// in a real app: DB *sql.DB
	Sessions map[string]string // demo store
}

func (h *Handlers) me(w http.ResponseWriter, r *http.Request) {
	c, err := r.Cookie("sid")
	if err != nil {
		http.Error(w, "not signed in", http.StatusUnauthorized)
		return
	}
	user, ok := h.Sessions[c.Value]
	if !ok {
		http.Error(w, "invalid session", http.StatusUnauthorized)
		return
	}
	fmt.Fprintf(w, "hello, %s\n", user)
}
```

#### Trace

```text
h.Sessions explicit in the receiver
no ctx.Value("sessions")
test: Handlers{Sessions: map...} → call me → assert
```

**Predict, then answer:** Where does the request ID go then if DB is not in context?

Answer: Request ID may still go in context (narrow, request-scoped). DB/config/session store — struct fields or parameters. Mix on purpose: values for correlation, struct for dependencies.

### Example 10: SameSite and Secure together (local lab)

```go
http.SetCookie(w, &http.Cookie{
	Name:     "sid",
	Value:    id,
	Path:     "/",
	HttpOnly: true,
	Secure:   false, // local http://localhost lab; in production true + HTTPS
	SameSite: http.SameSiteLaxMode,
	MaxAge:   3600,
})
```

#### Trace

```text
Lab HTTP: Secure=false otherwise the browser does not send the cookie on http://
Production HTTPS: Secure=true mandatory for session
Do not copy lab values into prod config
```

**Predict, then answer:** Can `SameSite=None` work without `Secure`?

Answer: Modern browsers require Secure with SameSite=None. For an ordinary same-site app prefer Lax/Strict instead of None.

## Decision analysis

| Decision | Choice | Why |
|----------|--------|-----|
| `PostForm` vs `Form` | PostForm for POST fields | Resistance to query smuggling |
| Session in cookie plain text | Not in production | Use opaque ID |
| Everything in context.Value | No | Implicit dependencies |
| MaxBytesReader | Always at body entrance | DoS hygiene |
| `FormValue` | Demo OK | Production: Parse + error |
| SameSite=Lax | Good default for many apps | CSRF profile ↑ |
| Private ctx key type | Yes | No package collision |

## Trade-offs

- **Small MaxAge cookie** — better security, more frequent sign-ins.
- **Strict SameSite** — better CSRF profile, may break some cross-site flows (e.g. return from external IdP — separate topic).
- **Context values** — fewer parameters in the signature, weaker readability.
- **Large multipart maxMemory** — faster, more RAM; small — more disk.
- **Global body limit in middleware** — simple; upload routes need a larger exception.
- **HttpOnly** — protects from JS reading; does not protect from CSRF by itself.

## Common mistakes

1. Reading the body manually then `ParseForm` (body consumed).
2. No limit — memory pressure.
3. Trusting `Form.Get` for authentication.
4. Cookie without `HttpOnly` (XSS can read it from the document).
5. String keys in context from different packages.
6. Ignoring the parse error.
7. Mixing a JSON body handler with `ParseForm` on the same body.
8. Logout without a matching `Path` — cookie remains.
9. `FormValue` in production without checking error / limit.
10. DB/`Config` pushed into `context.Value` instead of struct dependency.

## Idiomatic Go

- Dependency injection: `type Handler struct { DB *sql.DB; ... }` instead of context for DB.
- Request ID middleware + log field.
- A single helper function `parseFormLimited(r, max)`.
- In tests: `httptest.NewRequest` + `strings.NewReader` for the form body (`url.Values{}.Encode()`).
- Set cookie flags explicitly; do not rely on “default is OK”.
- PRG after a successful state change (link to 06.02).

## CSRF awareness (without a full security course)

The browser sends the cookie automatically to the same site. A malicious page can force the browser to POST to your endpoint while you are logged in (classic CSRF concept), unless you have protection. Here we do **not** give attack procedures — only defensive awareness:

- **SameSite=Lax/Strict** on the session cookie — reduces many CSRF vectors
- **CSRF token** in the form (hidden field) + server check — additional proof of intent
- For an API with an `Authorization` header (not cookie) CSRF is a different story: the browser does not send that header automatically from another page the same way

In this lesson we do not implement a full token protocol; what matters is that you **do not trust** that “cookie exists ⇒ POST is the user’s intent” without an additional signal.

#### Trace — why a cookie is not enough proof of intent

```text
Session: sid cookie valid
GET  /transfer  → shows form (OK, read)
POST /transfer  → changes state

If the server looks ONLY at "does sid cookie exist"
  then every POST with that cookie passes
  — including ones the user did not consciously start from your form

So: SameSite + (in a real app) CSRF token aligned with the session
```

**Predict, then answer:** Does `HttpOnly` solve CSRF?

Answer: No. HttpOnly prevents JS from *reading* the cookie; CSRF uses the fact that the browser *sends* the cookie automatically. Different threat, different control.

### Deleting a cookie

```go
http.SetCookie(w, &http.Cookie{
	Name:     "demo_user",
	Value:    "",
	Path:     "/",
	MaxAge:   -1,
	HttpOnly: true,
})
```

`MaxAge: -1` (or `Expires` in the past) asks the browser to delete the cookie. Path/Name must match what was set.

### Query vs body — mini checklist

| Source | Typical purpose | Risk |
|--------|-----------------|------|
| Query | filters, pagination, `next` (with allow-list) | URL logging leaks data; state change via GET |
| PostForm | passwords, state changes | without limit → DoS |
| Cookie | session ID | XSS without HttpOnly; CSRF without SameSite/token |
| Header | request ID, auth bearer | client must send consciously |

### Another mini-example: parseFormLimited helper

```go
func parseFormLimited(w http.ResponseWriter, r *http.Request, max int64) error {
	r.Body = http.MaxBytesReader(w, r.Body, max)
	return r.ParseForm()
}
```

Use it in all POST form handlers so you do not forget the limit.

## Practical scenario

An event registration portal accepts `multipart` with a biography and a PDF. The first release has no `MaxBytesReader`. One user sends a 1.5 GB “PDF” and workers go into swap.

**After the incident:** global limit 8 MiB on the upload route, stricter limit on the login form (4 KiB), and separating the upload service.

**Second bug:** support sees that `?role=admin` in the query sometimes “appears” in the admin UI because of `Form.Get`. Fix: only `PostForm` + server-side session roles, never a role from the form.

**Third bug:** logout “does not work” on mobile — they deleted the cookie without the same `Path`. After aligning Path, the session disappears as it should.

**Fourth bug:** the team pushes `*sql.DB` into context “so the signature stays clean”. A new member does not see dependencies; tests break on type assertion. Refactor to `Handlers{DB: db}` struct — readability returns.

**Fifth bug:** a form changes email without a CSRF token; SameSite=None because of a wrong CDN setup. They restore Lax + a plan for a token in the next sprint. Lesson: cookie flags are not decoration.

## Summary

- Forms: parse consciously, prefer `PostForm` for the body, always limit size before reading.
- Cookie: small state transport; `HttpOnly` / `Secure` / `SameSite` are part of the design; Path must be consistent.
- Context values: narrow (ID, span), not as a service locator — DB goes in a struct.
- Body limit is mandatory entrance hygiene.
- CSRF awareness: cookie ≠ proof of intent; SameSite helps, a token protocol is the next level.
