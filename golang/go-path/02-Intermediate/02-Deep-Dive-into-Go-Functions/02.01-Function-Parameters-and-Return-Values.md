# 02.01 Function parameters and return values: value semantics and errors

> **Go Path - Zero to Gopher** / **02 Intermediate → Deep dive into Go Functions** / Lesson 02.01

## Lesson goals

After this lesson you can:

- explain that Go **always** passes arguments **by value** — even when that value is a `pointer`
- explain `slice`, `map`, and `channel` as header values that hide a `pointer` to shared data
- use multiple return values, including the `(T, error)` contract with `error` last
- recognize when a `named result` helps, and when it obscures the flow (the naked `return` trap)
- choose between `pointer` and value for a `struct` parameter based on size, mutation, and API consistency
- use a `variadic` parameter and know that inside the function it becomes an ordinary `slice`

## Prerequisite

- Basic Go functions: `func`, parameters, `return` (01-Basics)
- `struct`, `slice`, `map` at introductory level
- `error` as an `interface` (introductory concept from 01-Basics)

## Problem this lesson solves

A programmer coming from languages where “everything is a reference” (JavaScript, Python, Java for objects) expects that `func f(s []int)` changes the original as soon as it changes `s` inside the function, or that `func f(u User)` automatically mutates the caller. Both expectations are true in one narrow sense, and wrong in the general case — and that difference is the source of subtle bugs. Go has **one** argument-passing rule: copy the value. The problem is that three different value shapes (scalar, `struct`, header type like `slice`) produce three visibly different behaviors from that same rule. Without a precise model, the programmer randomly adds `*` in front of the parameter type, until the bug appears only when `append` quietly reallocates the underlying array or when writing to a `nil` `map` crashes the program. The other half of the problem is the error contract: code that ignores `error` for another result, or — worse — mistakenly returns old values through a `named result` after an early `return`, spreads uncertainty further down the call stack instead of stopping it at the place it arose.

## Mental model

Go has exactly one argument-passing mechanism: **copying the value into the parameter**, same as ordinary assignment (`param := arg`). There is no special “pass by reference” function mode, as in C++ (`&`) or C# (`ref`). Every difference in behavior the programmer notices comes from *what* that copied value is — not from *how* it is copied.

1. **Scalar** (`int`, `bool`, `string`, `float64`, ...) — the value itself is copied. Changing the parameter inside the function does not touch the caller's original.
2. **`struct` value** — every field is copied, recursively, including nested `struct` values. A large `struct` means a large copy on every call.
3. **`pointer`** (`*T`) — the **address** it points to is copied, not the value behind the address. The address copy in the parameter and the original address in the caller point to the *same place* in memory, so `*p = x` inside the function changes that shared place.
4. **`slice`** is not an “array” — it is a small `struct` with three fields the Go runtime holds internally: a `pointer` to the underlying array, `len` (length), and `cap` (capacity). That small `struct` is copied — in this lesson we call it the *header*. The header copy and the original header point to the *same* underlying array, but each has its own independent copy of the `len`/`cap` fields.
5. **`map`** is a header that carries a `pointer` to a runtime hash table. The header copy shares that *same* runtime structure — there are not two separate stores.
6. **`channel`** is a header that carries a `pointer` to a runtime message queue. The header copy shares the *same* queue — all receivers see the same messages, in the same order.
7. A function may return multiple values. Ecosystem convention: when one of the results is `error`, it is **last** in the list, and the caller checks it **before** using the other results.
8. A `named result` gives a name to a result directly in the function signature (`func f() (n int, err error)`). It is useful when `defer` must read or change that result on exit from the function. It is dangerous when a naked `return` (with no arguments) lets an unset or stale value through to the caller.
9. A `variadic` parameter (`...T`) is syntactic sugar: **inside** the function it is an ordinary `[]T`. The caller may pass zero arguments, several individual values separated by commas, or an existing `slice` with the spread operator `s...`.

## Mechanism

### Copying a scalar — the starting point

Before you introduce `struct` or `slice`, establish the basic rule on the simplest example:

```go
func bump(x int) {
	x++
}

func main() {
	n := 5
	bump(n)
	fmt.Println(n) // 5
}
```

The call `bump(n)` copies the value `5` from `n` into a new, local parameter `x`. `x++` increments that copy to `6`. When `bump` finishes, that copy disappears — there was never a link back to `n`. `main` still has its `n`, unchanged at `5`. This is the entire Go argument mechanism, applied to the simplest possible type. Everything that follows is the same story applied to more complex values.

### `struct` value — every field is copied

A `struct` is not a special case of the rule — it just has more fields to copy. We follow the trace step by step:

```go
type Account struct {
	ID      string
	Balance int64
}

func creditValue(a Account, amount int64) Account {
	a.Balance += amount
	return a
}
```

The call `creditValue(acc, 50)` copies the **whole** `struct` `acc` — field `ID` and field `Balance` — into the local parameter `a`. That copy is completely independent of `acc` in the caller.

| Step | `acc` (caller) | `a` (parameter, copy) |
|------|----------------|------------------------|
| before the call | `{ID: "A1", Balance: 100}` | does not exist |
| entering the function | `{ID: "A1", Balance: 100}` | `{ID: "A1", Balance: 100}` |
| `a.Balance += 50` | `{ID: "A1", Balance: 100}` | `{ID: "A1", Balance: 150}` |
| `return a` | `{ID: "A1", Balance: 100}` | value `{ID: "A1", Balance: 150}` goes to the caller as the result |

`acc.Balance` stays `100` through the whole call. The function returned a **new** value — the caller must explicitly take it (`b := creditValue(acc, 50)`) to use it. This is a clean, predictable form: the function mutates nothing that does not belong to it; the cost is copying the whole `struct` on every call.

Now the same task via a `pointer`:

```go
func creditPtr(a *Account, amount int64) {
	a.Balance += amount
}
```

The call `creditPtr(&acc, 25)` copies the **address** of `acc` (the result of `&acc`) into parameter `a`. `a` is of type `*Account` — the copy is small, only an address, regardless of how many fields `Account` has. But `a.Balance += 25` does not write into a copy of `Account` — it writes to the address `a` points to, and that is the *same* place where `acc` lives in the caller. The notation `a.Balance` is shorthand for `(*a).Balance`; Go automatically dereferences the `pointer` when accessing a field, so the syntax does not immediately reveal that the same memory is involved.

| Step | Address `a` points to | Value at that address |
|------|------------------------|------------------------|
| before the call | — | `acc = {ID: "A1", Balance: 100}` |
| `a := &acc` (implicitly through the argument) | address of `acc` | `{ID: "A1", Balance: 100}` |
| `a.Balance += 25` | address of `acc` | `{ID: "A1", Balance: 125}` |
| leaving the function | address of `acc` | `acc` in the caller is now `{ID: "A1", Balance: 125}` |

Here there is no copying of `Balance` back and forth — there is one `Account` value, and `creditPtr` only received an address to it. That is why the caller sees the change without explicitly taking a result.

**Predict the result:** if in `main` you do `a := Account{ID: "A1", Balance: 100}`, then `b := creditValue(a, 50)`, then `creditPtr(&a, 25)`, what does `fmt.Println(a.Balance, b.Balance)` print?

**Answer:** `125 150`. `creditValue` worked on a copy and returned a new value into `b` (`100+50=150`), not touching `a`. `creditPtr` worked through a `pointer` directly on `a`, so `a.Balance` became `100+25=125`. `b` knows nothing about the later change to `a`, because it was created as an independent copy before that change.

The choice between value and `pointer` receiver for a `struct` **parameter** (not `method` — that is 02.03) reduces to three questions: whether the function should mutate the original, how large the `struct` is (copying 10 `int64` fields on every call in a hot path is a measurable cost), and whether the API should be consistent with the rest of the package that already uses one style.

### `slice` as a header — three fields, not an array

This is the most common source of confusion in this lesson, so we take it apart slowly. A `slice` variable **is not** an array of data. It is a small, fixed-size `struct` that the Go runtime defines internally roughly as:

```go
type sliceHeader struct {
	ptr *elementType // address of the first element in the underlying array
	len int           // current number of elements available through this slice
	cap int           // how many elements fit in the underlying array from ptr onward
}
```

When you write `func f(s []int)`, `s` is a variable of type “header with three fields”. When you call `f(buf)`, those three fields — `ptr`, `len`, `cap` — are copied into a new header `s` inside `f`. The header copy and the original header in the caller point to the *same* underlying array (same `ptr`), but they are two **independent** header-type variables. Changing `s.len` inside the function (e.g. through `append` that does not reallocate) does not change `len` in the caller's header — that is a separate field in a separate copy.

First case — changing an **element** through the shared `ptr`:

```go
func fill(s []int, v int) {
	for i := range s {
		s[i] = v
	}
}
```

`s[i] = v` writes to address `ptr + i`, i.e. directly into the underlying array. That array is the same for `s` in `fill` and for `buf` in the caller — `fill` does not copy the array, only the header that points to it. That is why `fill(buf, 1)` changes `buf` “in place”, visible to the caller.

Second case — changing the **header**, not an element:

```go
func grow(s []int) {
	s = append(s, 7)
}
```

`append(s, 7)` can work in two ways, depending on whether there is room in the underlying array (`cap > len`):

- **There is room:** writes `7` at position `len` in the *same* underlying array and returns a header with `len+1`. The element is written into the shared array — but `s = ...` in `grow` overwrites the **local header copy**, not the header in the caller. The caller still has the old `len`, so through its (shorter) header it does not “see” the new element, even though it physically exists in the array.
- **There is no room:** `append` allocates a **new**, larger underlying array, copies the old elements, writes the new element, and returns a header that points to that new array. Now `s` in `grow` points to completely different memory from `buf` in the caller.

In both cases, `s = append(s, 7)` changes only the local header `s`. When `grow` finishes, that header disappears. The caller gets nothing, because `grow` does not return the header to the caller — there is no `return`, no writing through a `pointer` to the header.

| Step | `buf` header (caller) | `s` header (in `grow`) | underlying array |
|------|------------------------|-------------------------|------------------|
| `buf := make([]int, 3)` then `fill(buf, 1)` | `{ptr: A, len: 3, cap: 3}` | — | `[1 1 1]` at address A |
| call `grow(buf)` — copies header | `{ptr: A, len: 3, cap: 3}` | `{ptr: A, len: 3, cap: 3}` | `[1 1 1]` |
| `append(s, 7)` with no room (`cap==len`) → reallocate | `{ptr: A, len: 3, cap: 3}` (unchanged) | `{ptr: B, len: 4, cap: 6}` (new memory) | A: `[1 1 1]`, B: `[1 1 1 7]` |
| `grow` finishes, `s` disappears | `{ptr: A, len: 3, cap: 3}` | — | A: `[1 1 1]` (B is “lost”) |
| `fmt.Println(buf)` | — | — | prints: `[1 1 1]` |

That is why an idiomatic Go API that adds elements **returns** a new `slice`, and the caller explicitly takes the result:

```go
func growReturn(s []int) []int {
	return append(s, 7)
}

buf = growReturn(buf) // buf is now = [1 1 1 7]
```

Here nothing changes “magically” — `growReturn` returns a new header as a result, and `buf = ...` in the caller **overwrites** the caller's header with that new value. The same mechanism as any assignment.

**Predict the result:** `s := make([]int, 2, 5)` (thus `len=2, cap=5`), then you call `func addOne(s []int) { s = append(s, 9) }` with `addOne(s)`. Does `s[2]` in the caller exist after the call?

**Answer:** No — `s` in the caller still has `len=2`. `append` inside `addOne` had room (`cap=5 > len=2`), so `9` was physically written into the underlying array at position 2 — but only the local header in `addOne` got `len=3`. The caller's header, with `len=2`, does not “see” that position through normal indexing or `range`, because its `len` says it has only two elements. The value `9` physically exists in memory, but is unreachable until the caller gets a new header with `len=3` (e.g. through `return`).

### `map` and `channel` — headers with shared runtime state

`map` and `channel` follow the same header logic as `slice`, only the runtime structure behind them is different (hash table for `map`, message queue with synchronization for `channel`), and — the key difference from `slice` — there is **no** concept of “double capacity that requires a reallocation visible to the caller”. Writing to a `map` or sending on a `channel` changes the shared runtime structure directly, without a local data copy that could “fall away” as with a `slice`.

```go
func mark(m map[string]bool, k string) {
	m[k] = true
}

seen := make(map[string]bool)
mark(seen, "milk")
fmt.Println(seen["milk"]) // true
```

`mark` gets a copy of header `m` — but that header is only a `pointer` to the runtime hash table that `make` allocated. The write `m[k] = true` writes directly into that table, through the `pointer` that `seen` and `m` share. There is no “local version of the map” that could disappear when `mark` finishes — the map as a runtime structure exists independently of any variable that points to it, as long as at least one reference remains.

Trap: a `nil` `map` is a valid value for **reading** (reading from a `nil` map gives the `zero value` and `false` for `ok`), but writing to a `nil` `map` is a `panic`:

```go
var m map[string]bool // zero value: nil, not an empty map
m["x"] = true          // panic: assignment to entry in nil map
```

A function that takes `map[string]bool` as a parameter must document whether it assumes the caller already called `make`, or itself creates the map if it is `nil`.

A `channel` has the same header-with-shared-state shape:

```go
func send(ch chan<- int, v int) {
	ch <- v
}
```

Copying `ch` into the parameter copies the header (`pointer` to the runtime message queue with a mutex and buffer). Sending `v` on `ch` inside `send` puts the message into the *same* queue that every other code holding that `channel` sees. Detailed `channel` and `goroutine` semantics are a topic of later lessons (03.x); here what matters is only: a `channel` passed as an argument is not a copy of the message queue, but a shared handle to one queue.

### Multiple return values and `(T, error)`

Go allows a function to return a list of values separated by commas in parentheses in the signature:

```go
func Parse(s string) (int, error) {
	n, err := strconv.Atoi(s)
	if err != nil {
		return 0, fmt.Errorf("Parse: %w", err)
	}
	return n, nil
}
```

The compiler applies a strict rule: every `return` must list **exactly** as many values as the signature promises, of the **correct** types (or values that convert implicitly, like `0` into an `int` position). There is no “return only the first result if the second is unimportant” — you must explicitly write `0, nil` or similar on every `return` branch.

Ecosystem convention — not a compiler rule, but a firm habit that tools (linters, code review) enforce — is that `error` is always the **last** result: `(T, error)`, `(T1, T2, error)`, never `(error, T)`. The caller knows, without looking at documentation, where to look for the failure signal:

```go
n, err := Parse(s)
if err != nil {
	return err // or handle the error here
}
// from this line, n is safe to use
```

Important discipline: when `err != nil`, the other results (`n` in the example) **do not guarantee** a useful value. The convention is that the caller ignores `n` when `err != nil`, unless the function documentation explicitly says otherwise (rare, documented exceptions — e..g. `Read` from `io.Reader` may return `n > 0` **and** `err == io.EOF` in the same call). On failure `n` usually carries the type's `zero value` (`0` for `int`), but that is not a “sentinel value” to check — the sentinel is exclusively `err != nil`.

Ignoring `error` via the `blank identifier` is syntactically allowed, but it is a discipline lapse, not a language feature:

```go
n, _ := strconv.Atoi(s) // compiles; loses failure information
```

If `s` is not a number, `n` is `0` — and `0` is also a legitimate value for valid input `"0"`. Without `err`, the caller cannot tell “the user entered zero” from “the input was not a number”.

### `named result` — use it, but consciously

A `named result` gives a name to a result directly in the signature parentheses:

```go
func divmod(a, b int) (q, r int) {
	q = a / b
	r = a % b
	return // "naked" return — returns current q and r
}
```

The names `q` and `r` are **already declared, initialized to `zero value`** local variables from the moment of entering the function — before the first line of the body. A naked `return` (with no arguments) returns their *current* values at that moment. This is useful in two cases: when `defer` needs to read or change the result (next section), and when documentation gains clarity (`(min, max int)` says more than `(int, int)`).

The trap arises when an early-`return` branch and a naked `return` branch are mixed in the same function:

```go
func parseAge(s string) (age int, err error) {
	age, err = strconv.Atoi(s)
	if err != nil {
		return 0, fmt.Errorf("parseAge: %w", err)
	}
	if age < 0 {
		err = fmt.Errorf("parseAge: negative")
		return // returns both age (already parsed) AND err — the caller gets BOTH
	}
	return age, nil
}
```

When `age < 0`, the code sets `err`, then does a naked `return`. That returns the **current** `age` (say `-5`, because `Atoi` successfully parsed a negative number) together with `err != nil`. A caller that — by mistake — does not check `err` before using `age` gets a concrete negative number that looks like “data”, not like an empty value. The explicit version is clearer and harder to misuse:

```go
func parseAgeClean(s string) (int, error) {
	age, err := strconv.Atoi(s)
	if err != nil {
		return 0, fmt.Errorf("parseAge: %w", err)
	}
	if age < 0 {
		return 0, fmt.Errorf("parseAge: negative")
	}
	return age, nil
}
```

Every `return` branch here explicitly chooses what goes into the first result — there is no implicit “whatever currently sits in the variable”. Rule for choosing: use a `named result` when you **need** something to read the result name before the end of the function (classically: `defer`); in all other cases, explicit `return T{}, err` is more readable.

**Strong reason for `named result`** — `defer` that appends a Close `error`:

```go
func readConfig(path string) (data string, err error) {
	f, err := os.Open(path)
	if err != nil {
		return "", err
	}
	defer func() {
		if cerr := f.Close(); err == nil && cerr != nil {
			err = cerr
		}
	}()

	buf := make([]byte, 64)
	n, err := f.Read(buf)
	if err != nil {
		return "", err
	}
	return string(buf[:n]), nil
}
```

The `defer` function literal here **captures** the variable `err` from the outer scope (the same mechanism as a closure — in detail in lesson 02.02 and in 01-Basics/02.08). When `readConfig` exits — whether through `return string(...), nil`, or through an earlier `return "", err` — before the real return to the caller the `defer` body runs. It calls `f.Close()`; if the read was successful (`err == nil` at that moment) but Close was not (`cerr != nil`), `defer` **overwrites** `err` with the Close error. Without a `named result`, there would be no variable `err` in the outer scope that `defer` can change after `return` has already “packed” the values — the `named result` *is* that variable sent to the caller, and `defer` sees it like any other captured variable.

### `variadic` parameter — `...T` becomes `[]T`

The last parameter in the signature may be `variadic`:

```go
func Sum(xs ...int) int {
	total := 0
	for _, x := range xs {
		total += x
	}
	return total
}
```

Inside `Sum`, `xs` is an ordinary variable of type `[]int` — the same header with `ptr`/`len`/`cap` as any other `slice`. The difference is only on the **caller side**: the syntax allows three call forms.

```go
Sum()                  // xs = []int{} (len 0)
Sum(1, 2, 3)           // Go creates a new slice {1, 2, 3} and passes it as xs
nums := []int{4, 5, 6}
Sum(nums...)           // the ... operator spreads an EXISTING slice; the nums HEADER is copied into xs, same underlying array
```

The first two forms: the compiler allocates a **new**, temporary underlying array and packs the individual arguments into it — `xs` inside the function points to that new memory, which does not exist anywhere in the caller's code.

The third form (`nums...`): there is no new allocation for the call itself — `xs` gets a header that points to the **same** underlying array as `nums`. That means mutating an **element** through `xs` inside the function (`xs[0] = 99`) changes `nums[0]` in the caller — identical to an ordinary `slice` parameter. `append` inside the function on `xs` follows exactly the same header logic as any other `append`: if there is room in `cap`, it can quietly overwrite data past `len` in the caller's array (dangerous if the caller still uses that memory); if there is no room, it reallocates and the local header change is lost without a `return`.

## Rules and syntax

- Signature: `func Name(a Type, b Type) (Type, error)`; parameters of the same type may share the type: `func f(a, b int)`.
- `error` is, by convention, always the **last** result when it exists.
- `named result`: `func f() (n int, err error)` — each name is an already declared variable with `zero value` on entry into the function.
- Naked `return` returns the **current** values of the `named result`s; use it consciously, not as a habit.
- `variadic` must be the **last** parameter in the signature: `func f(prefix string, xs ...int)` is legal, `func f(xs ...int, prefix string)` is not.
- The spread operator `s...` works only with a value of type `[]T` (or compatible) at the call site of a `variadic` function; it does not combine with individual arguments in the same call (`f(1, xs...)` is not legal when `f` is `variadic` on one parameter).
- For a large `struct` consider a `*T` receiver/parameter to avoid copying; for a small, immutable `struct` a value is often more readable.
- Document explicitly (comment above the function) whether the function mutates a `slice`/`map` argument passed to it — the compiler does not force that.
- Do not use `panic` for expected parsing/validation errors of user input — that is topic 02.02.

## Examples

### Example 1 — Value versus `pointer` on a `struct`

```go
package main

import "fmt"

type Account struct {
	ID      string
	Balance int64
}

func creditValue(a Account, amount int64) Account {
	a.Balance += amount
	return a
}

func creditPtr(a *Account, amount int64) {
	a.Balance += amount
}

func main() {
	a := Account{ID: "A1", Balance: 100}
	b := creditValue(a, 50)
	fmt.Println(a.Balance, b.Balance) // 100 150

	creditPtr(&a, 25)
	fmt.Println(a.Balance) // 125
}
```

#### What happens here

`creditValue` receives a copy of the whole `struct`; changes a field on that copy and returns a **new** value — the original `a` in `main` is never touched. `b` is that new value, which the caller must explicitly take by assignment. `creditPtr` receives the address of the original `a`; `a.Balance += amount` inside the function writes directly to that address, so the change is visible in `main` without any `return`. The choice between these two styles is an API choice: `creditValue` is safer for sharing (the caller knows the original can never be changed “suddenly”), `creditPtr` is cheaper and more natural when mutation is the real intent (e.g. a method that changes account state).

### Example 2 — `slice` header and three common traps

```go
package main

import "fmt"

func fill(s []int, v int) {
	for i := range s {
		s[i] = v
	}
}

func grow(s []int) {
	s = append(s, 7) // changes local header, not the caller's
}

func growReturn(s []int) []int {
	return append(s, 7)
}

func main() {
	buf := make([]int, 3)
	fill(buf, 1)
	fmt.Println(buf) // [1 1 1]

	grow(buf)
	fmt.Println(buf) // still [1 1 1]

	buf = growReturn(buf)
	fmt.Println(buf) // [1 1 1 7]
}
```

#### What happens here

`fill` changes **elements** through the shared underlying array — visible to the caller without `return`. `grow` changes only the **local header copy** (`len`/`cap`/possibly a new `ptr` after reallocation) — the caller sees nothing, because `grow` does not return that new header back. `growReturn` does the identical `append`, but **returns** the new header, which `main` explicitly takes by assignment `buf = growReturn(buf)`. This is why every `append`-based API in the standard library (and idiomatic Go code in general) returns a `slice` instead of expecting mutation to “magically” leave the function.

### Example 3 — `map` as a shared handle

```go
package main

import "fmt"

func mark(m map[string]bool, k string) {
	m[k] = true
}

func main() {
	seen := make(map[string]bool)
	mark(seen, "milk")
	fmt.Println(seen["milk"]) // true

	var nilMap map[string]bool
	fmt.Println(nilMap["x"]) // false — reading from a nil map is safe
	// nilMap["x"] = true    // panic: assignment to entry in nil map
}
```

#### What happens here

The header that carries a `pointer` to the runtime hash table is copied; `mark` writes directly into that shared table, so `seen["milk"]` becomes `true` without any `return`. The `zero value` for a `map` type is `nil` — not an empty, allocated map. Reading from a `nil` map is legal and returns the element's `zero value` (`false` for `bool`); writing to a `nil` map is a `panic`. A function that takes a `map` parameter must either document that the caller guarantees the map is not `nil`, or itself check and allocate before writing.

### Example 4 — `(T, error)` and the `named result` trap

```go
package main

import (
	"fmt"
	"strconv"
)

func parseAge(s string) (age int, err error) {
	age, err = strconv.Atoi(s)
	if err != nil {
		return 0, fmt.Errorf("parseAge: %w", err)
	}
	if age < 0 {
		err = fmt.Errorf("parseAge: negative")
		return // returns (age, err) — age is already parsed, e.g. -5
	}
	return age, nil
}

func parseAgeClean(s string) (int, error) {
	age, err := strconv.Atoi(s)
	if err != nil {
		return 0, fmt.Errorf("parseAge: %w", err)
	}
	if age < 0 {
		return 0, fmt.Errorf("parseAge: negative")
	}
	return age, nil
}

func main() {
	age, err := parseAge("-5")
	fmt.Println(age, err) // -5 parseAge: negative

	age2, err2 := parseAgeClean("-5")
	fmt.Println(age2, err2) // 0 parseAge: negative
}
```

#### What happens here

`parseAge` uses a naked `return` on the negative branch, so it returns the **current** value of `age` (`-5`, because `strconv.Atoi` successfully parsed the number) together with `err`. A caller that does not check `err` before using `age` gets a concrete, “credible” negative number. `parseAgeClean` explicitly returns `0, err` on every failure branch — there is no chance that an old or “half-correct” value escapes with the error. `age2` is `0`, a clear signal that the result is not for use.

### Example 5 — `variadic` and a shared underlying array

```go
package main

import "fmt"

func Sum(xs ...int) int {
	total := 0
	for _, x := range xs {
		total += x
	}
	return total
}

func zeroFirst(xs ...int) {
	if len(xs) > 0 {
		xs[0] = 0
	}
}

func main() {
	fmt.Println(Sum(1, 2, 3)) // 6

	nums := []int{4, 5, 6}
	fmt.Println(Sum(nums...)) // 15

	zeroFirst(nums...)
	fmt.Println(nums) // [0 5 6] — element changed through the shared array
}
```

#### What happens here

`Sum(1, 2, 3)` creates a new, temporary underlying array that does not exist anywhere in the caller's code — safe, no sharing. `Sum(nums...)` spreads an existing `slice`: `xs` inside `Sum` gets a header that points to the *same* underlying array as `nums`, even though `Sum` behaves identically (only reads). `zeroFirst(nums...)` shows the consequence: since `xs` shares the array with `nums`, `xs[0] = 0` changes `nums[0]` in the caller — `variadic` with spreading an existing `slice` carries the same mutation risk as an ordinary `slice` parameter.

## Decision analysis

| Decision | Motive | Alternative |
|----------|--------|-------------|
| `(T, error)` with `error` last | Explicit, predictable failure signal | `panic` — only for programmer bugs (02.02) |
| Return `slice` after `append` | The header must be explicitly saved at the caller | In-place mutation via `*[]T` — rare, less clear |
| `pointer` for mutation or a large `struct` | Clear intent, less copying per call | Value — safer for sharing, costlier for a large `struct` |
| Value for a small, immutable `struct` | Simpler reasoning, no shared state | `pointer` “just in case” — loses the immutability guarantee |
| `named result` only when `defer` must read/write the result | Less hidden state in other cases | Local variable + explicit `return` |
| `variadic` for a variable number of same-type arguments | Natural API (`fmt.Println`, `append`) | Explicit `[]T` parameter when the caller already has a `slice` and mutation is a risk |

## Trade-offs

- Copying a small `struct` is cheap and safe; copying a large `struct` in a hot path is a measurable cost — measure, do not assume.
- `named result` + `defer` is a powerful combination, but every additional `named result` variable without that reason makes the signature less readable.
- Mutating a `slice`/`map` argument is cheap (no data copying), but hides the effect from the caller if undocumented — the cleaner alternative (returning a new value) costs an allocation.
- A rich `error` type (your own error type) carries more information than an `errors.New(...)` string, but requires `%w` wrapping and `errors.Is`/`errors.As` discipline (in detail in 02.10).
- A `variadic` API is convenient for the caller, but hides allocation of a temporary `slice` when called with individual arguments — for a hot path sometimes an explicit `[]T` is better.

## Common mistakes

### Expecting that `append` inside a function changes the caller's `slice`

**Wrong:**

```go
func addSuffix(s []int) {
	s = append(s, 0)
}
// ...
addSuffix(data) // caller expects data with an added element
```

**Effect:** `data` in the caller stays unchanged — the function only changed its local header, which disappears on exit from the function. If `append` reallocated (no room in `cap`), the new element does not even exist physically near the original array.

**Fix:** Return a new `slice` and force the caller to take the result: `func addSuffix(s []int) []int { return append(s, 0) }`, and the call becomes `data = addSuffix(data)`.

### Using the result when `err != nil`

**Wrong:**

```go
n, err := strconv.Atoi(s)
fmt.Println("parsed:", n)
if err != nil {
	return err
}
```

**Effect:** `n` is used (printed, or worse — passed further into logic) before checking `err`, so the “value” `0` from a failed parse looks like legitimate data.

**Fix:** Check `err` **immediately** after the call, before any use of the other results: `if err != nil { return err }` and only then `fmt.Println("parsed:", n)`.

### Naked `return` with a `named result` that was not explicitly set on a failure branch

**Wrong:**

```go
func parseAge(s string) (age int, err error) {
	age, err = strconv.Atoi(s)
	if age < 0 {
		err = fmt.Errorf("negative")
		return // returns a "half-correct" age too
	}
	return age, nil
}
```

**Effect:** A caller that does not check `err` before using `age` gets a concrete, credible value (`age`) with an error — easy to confuse “has data” with “data is valid”.

**Fix:** Explicitly list both values on every `return` branch: `return 0, fmt.Errorf("negative")`. Reserve naked `return` exclusively for cases where it is *intentional* that the caller gets the current values (e.g. the happy path at the end of the function).

### Passing a large `struct` value where a `pointer` would be cheaper

**Wrong:**

```go
type Report struct {
	Rows [10000]float64
	Meta [50]string
}

func Summarize(r Report) float64 { /* only reads */ }
```

**Effect:** Every call to `Summarize` copies the whole `Report` (tens of thousands of bytes) onto the stack, even though the function only reads data — a measurable cost in a loop or hot path, with no functional benefit.

**Fix:** Pass `*Report` when the `struct` is large, even if the function mutates nothing: `func Summarize(r *Report) float64`. Document that the function does not change the contents if that matters to the caller.

### Mutating a `map` argument without documenting that the function does that

**Wrong:**

```go
// NormalizeKeys deletes empty keys.
func NormalizeKeys(m map[string]string) {
	for k := range m {
		if k == "" {
			delete(m, k)
		}
	}
}
```

**Effect:** The name and comment do not say that the function mutates the **passed** map (does not return a new one) — a caller who expected a pure function loses the original data without warning.

**Fix:** Either document explicitly in the comment (“mutates `m` in place”), or change the signature to return a new map: `func NormalizedKeys(m map[string]string) map[string]string`, leaving the original untouched.

### Writing to a `nil` `map` received as a parameter

**Wrong:**

```go
func setDefault(cfg map[string]string) {
	cfg["timeout"] = "30s" // panic if cfg is nil
}
```

**Effect:** If the caller passes `var cfg map[string]string` (declared, but never `make`-d), the `zero value` is `nil`, and the write panics in production on a rare branch where configuration was not initialized.

**Fix:** Check and, if needed, signal an error instead of a quiet `panic`: `if cfg == nil { return errors.New("setDefault: cfg is nil") }`, or document that the caller guarantees a `make`-d map.

### Mixing individual arguments and `slice` spreading in a `variadic` call

**Wrong:**

```go
extra := []int{4, 5}
Sum(1, 2, extra...) // does not compile
```

**Effect:** The compiler rejects the call — a `variadic` call takes **either** a list of individual values **or** one `slice` with `...`, not a combination.

**Fix:** Build one `slice` before the call: `all := append([]int{1, 2}, extra...)` then `Sum(all...)`.

## Idiomatic Go

- The standard library holds the `(T, error)` pattern almost universally: `strconv.Atoi`, `os.Open`, `json.Marshal`.
- Document explicitly (comment above the function, not only the name) every side-effect on a `slice`/`map` argument.
- `var zero T; return zero, err` or `return T{}, err` — never “whatever currently sits in the variable” on an error that is not an intentional `named result`.
- Do not use `panic` for user-input parsing errors — `error` is the contract for expected failures (02.02 goes deeper).
- `pointer` receiver/parameter when mutation is the intent or the `struct` is large; value when the `struct` is small and immutable — and be consistent within the same package.
- Reserve `variadic` APIs (`fmt.Println`, `append`) for cases when “a variable number of same-type arguments” truly describes the domain; do not force `variadic` when a fixed parameter list is clearer.

## Practical scenario

A checkout service has a function `func ApplyDiscount(cart []Line, pct int)` that should add a discount line to the cart. A developer writes `cart = append(cart, feeLine)` inside the function, without `return` in the signature — it compiles without warning, tests on small carts (where `append` happens to reallocate and “works” in the test because of a specific `cap`) pass. In production, on carts with enough room in `cap`, `append` writes the line into the same underlying array but the **local** header with the new `len` disappears on exit from the function — the fee line quietly does not exist for billing. Fix: the signature becomes `func ApplyDiscount(cart []Line, pct int) ([]Line, error)`, every caller in the code takes the result (`cart, err = ApplyDiscount(cart, pct)`), and code review adds a rule: “every function that does `append` on a parameter must return a `slice`, no exception.” The same team, two weeks later, catches a similar bug: `func Reprice(cart []Line) []Line` correctly returned a new `slice`, but the caller forgot `cart = Reprice(cart)` and used the old variable — the rule expands to the code review checklist: “every `append`-based result must be assigned, not discarded.”

## Check questions

1. **Does Go pass arguments by value or by reference?**  
   **Answer:** Exclusively by value — there is no special “by reference” mode. When the value is a `pointer`, the address is copied, which creates the *impression* of shared state, but the mechanism is still copying.

2. **What exactly does a `slice` header contain, and what is copied when we pass it to a function?**  
   **Answer:** A `pointer` to the underlying array, `len`, and `cap`. All three fields are copied — the copy and the original point to the same underlying array, but have independent `len`/`cap`.

3. **Why must `append` inside a function often return a `slice` for the change to be visible to the caller?**  
   **Answer:** `append` changes the local header (and possibly allocates a new underlying array); that local change disappears on exit from the function unless it is explicitly returned and the caller takes it by assignment.

4. **Why is `err != nil` the failure sentinel, and not the `zero value` of the other results?**  
   **Answer:** The `zero value` (e.g. `0`) can also be a legitimate successful result (valid input `"0"`); the only reliable failure signal is checking the `error` result.

5. **When is a `named result` a justified choice?**  
   **Answer:** When `defer` must read or change the result on exit from the function (e.g. appending a resource Close `error`); in other cases an explicit `return` is more readable.

6. **Does a `map` parameter share state with the caller?**  
   **Answer:** Yes — the header that carries a `pointer` to the same runtime structure is copied; a write through the parameter is visible to the caller.

7. **What does a `variadic` parameter become inside the function body, and what risk does a call with `existing...` carry?**  
   **Answer:** It becomes an ordinary variable of type `[]T`. A call with `existing...` shares the underlying array with the caller's `slice`, so mutating an element inside the function also changes the original.

## Summary

Go has one rule — arguments are copied — but three value shapes (scalar, `struct`, header type like `slice`/`map`/`channel`) produce three different visible behaviors. `slice`, `map`, and `channel` are small headers that share underlying data, but do not share their **own** state (`len`/`cap` for a `slice`) — that is why `append` without `return` quietly loses the change. Multiple return values with `error` last is the basic contract of reliable Go code; use a `named result` intentionally, most often with `defer`, not out of habit. Choose a `pointer` when mutation is the intent or the `struct` is large; a value when the API should be safe for sharing. `variadic` is syntactic sugar over `[]T` with the same copying rules as any other `slice` parameter.
