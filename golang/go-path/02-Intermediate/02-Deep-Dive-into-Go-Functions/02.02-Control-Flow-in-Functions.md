# 02.02 Control flow in functions: early return, `defer`, `panic`/`recover`

> **Go Path - Zero to Gopher** / **02 Intermediate → Deep dive into Go Functions** / Lesson 02.02

## Lesson goals

After this lesson you can:

- write an early `return` (guard clause) instead of deeply nested `if`
- explain the exact execution order of multiple `defer` calls (LIFO) and **when** their arguments are evaluated
- recognize the `defer`-in-a-loop trap and know when to extract the body into a helper function
- explain the difference between `error` (expected failure) and `panic`/`recover` (unstable state)
- place `recover` at a clear system boundary, instead of scattered through every function

## Prerequisite

- 02.01 (value semantics, `(T, error)`, `named result`)
- Basic `if`, `for`, `os.File` from 01-Basics

## Problem this lesson solves

A function with a pyramid of `if err == nil { if x > 0 { if ok { ... } } }` is hard to read, because the “happy path” is buried in the middle of nested blocks, and every new check adds one indentation level. A forgotten `f.Close()` on one `return` branch slowly leaks file descriptors until the process dies on “too many open files”. A programmer who hits `panic(err)` for “file not found” — a situation that is **expected** occasionally in normal program operation — crashes the whole process because of one unavailable path. On the other side, `recover` scattered in every function swallows real bugs and turns them into silent no-ops, instead of reporting them. This lesson sets a clear boundary: `error` for everything that is **expected** to go wrong, `defer` for cleanup that must happen regardless of which `return` branch runs, and `panic`/`recover` reserved for rare, clearly bounded cases.

## Mental model

1. The **happy path** goes vertically downward, without indentation; every error jumps out **early** and leaves the function.
2. `defer` is a promise to the runtime: “run this call when the **current function** exits” — whether it exits through a normal `return` or through a `panic` that propagates further.
3. Arguments of a `defer` expression are evaluated **immediately**, at the moment the `defer` line runs — not at the moment the deferred call actually happens. Only the **call** is deferred.
4. Multiple `defer` calls in the same function form a **stack**: last registered, first executed (LIFO — last in, first out).
5. `panic` is a signal for unstable state: a programmer bug, an impossible invariant, a situation where continuing makes no sense. `error` is the contract for expected failure: bad user input, unavailable network, a file that does not exist.
6. `recover` works exclusively inside a `defer` function, in the same `goroutine` that panicked. It is typically placed at a system **boundary** (HTTP middleware, a worker that processes messages from a queue) — not in every internal function.

## Mechanism

### Early `return` — guard clause instead of a pyramid

When a function checks several prerequisites before doing the real work, the natural (but wrong) instinct is to nest every successful case inside the previous one:

```go
func normalizeEmailNested(s string) (string, error) {
	trimmed := strings.TrimSpace(s)
	if trimmed != "" {
		if strings.Contains(trimmed, "@") {
			return strings.ToLower(trimmed), nil
		} else {
			return "", fmt.Errorf("email: no @")
		}
	} else {
		return "", fmt.Errorf("email: empty")
	}
}
```

Every check adds an indentation level, and the real logic (`strings.ToLower(trimmed)`) is buried three levels deep. A guard clause reverses the order: **first** check what is wrong, **immediately** exit, and the happy path stays at the base indentation level:

```go
func normalizeEmail(s string) (string, error) {
	s = strings.TrimSpace(s)
	if s == "" {
		return "", fmt.Errorf("email: empty")
	}
	if !strings.Contains(s, "@") {
		return "", fmt.Errorf("email: no @")
	}
	return strings.ToLower(s), nil
}
```

The mechanics are simple: `if s == "" { return ... }` leaves the function **immediately** when the failure condition is true; the compiler neither knows nor cares that it is a “guard” — it is an ordinary `if` with `return` in the body. The difference is stylistic, not syntactic, but the consequence is large: when you reach the last line of the function, you know all prerequisites are satisfied, without needing to hold a stack of three nested `if`s in your head. Every next check is added at the **same** indentation level, not inside the previous one.

### `defer` — a promise that something will happen on exit

`defer` registers a call that will run when the current function finishes executing — either by a normal `return`, or when a `panic` flies through that stack frame on the way up (that function's defers run **before** the panic continues to propagate further).

Follow line by line:

```go
func demo() {
	fmt.Println("A")
	defer fmt.Println("B")
	fmt.Println("C")
}
// prints: A, C, B
```

When execution reaches `defer fmt.Println("B")`, “B” is **not** printed immediately. That line does two things: (1) evaluates the argument `"B"` (trivial, because it is already a constant), (2) puts the **call** `Println("B")` onto the deferred-call stack that belongs to this `demo()` invocation. Execution continues to the next line, `fmt.Println("C")`, which runs normally and prints “C” immediately. Only when `demo` reaches the end of the body (implicit `return`) does the runtime pop the defer stack and run all deferred calls — in this case only one, `Println("B")`.

| Moment | What runs | Print | Defer call stack |
|--------|-----------|-------|------------------|
| line 1 | `fmt.Println("A")` | `A` | `[]` |
| line 2 | `defer fmt.Println("B")` — registers, does not run | (nothing) | `[Println("B")]` |
| line 3 | `fmt.Println("C")` | `C` | `[Println("B")]` |
| end of function | runtime pops the stack | `B` | `[]` |

### Multiple `defer` calls — LIFO stack

When a function registers multiple `defer` calls, they run in **reverse** registration order — last registered, first executed:

```go
func order() {
	defer fmt.Println(1)
	defer fmt.Println(2)
	defer fmt.Println(3)
}
// prints: 3, 2, 1
```

Think of the stack as a physical pile of plates: each `defer` puts a new plate **on top**. When the function finishes, the runtime takes plates **from the top**, so the last one put on (`Println(3)`) runs first, then the middle one (`Println(2)`), and finally the first one put on (`Println(1)`). LIFO order is not arbitrary — it exists exactly so resources opened **later** are closed **before** resources opened **earlier**, which is the natural order for nested dependencies (e.g. a transaction opened after a connection must be closed before the connection).

### `defer` evaluates arguments **immediately** — not at execution time

This is the most common trap in this lesson, so it is worth separating the two steps a `defer` line does: (1) evaluate arguments **now**, (2) execute the call **later**. Only the call is deferred; the arguments are already “packed” at registration time.

```go
func mystery() {
	n := 1
	defer fmt.Println(n) // n is HERE 1 — argument evaluated NOW
	n = 2
	fmt.Println(n)
}
```

Execution trace, step by step:

| Step | Statement | `n` at that moment | What happened |
|------|-----------|---------------------|---------------|
| 1 | `n := 1` | `1` | local variable set |
| 2 | `defer fmt.Println(n)` | `1` | argument `n` **evaluated IMMEDIATELY** → `1`; the call `Println(1)` is put on the stack (not `Println(n)` — the value is already taken) |
| 3 | `n = 2` | `2` | variable `n` overwritten; the already registered call on the stack still carries `1`, does not “see” this change |
| 4 | `fmt.Println(n)` | `2` | prints `2` — ordinary, current statement |
| 5 | end of function, runtime pops the stack | — | runs `Println(1)`, which long ago “packed” the value `1` |

So the output is `2`, then `1` — not `2`, then `2`, as someone might intuitively assume. `defer fmt.Println(n)` is equivalent to writing `arg := n; defer func() { fmt.Println(arg) }()` — the argument is taken at registration time, not at execution time.

**Predict the result:** if you want the deferred call to see the **later** value of `n` (thus `2`, not `1`), how must you write the `defer` line?

**Answer:** You must defer a **call to a function literal with no arguments**, which only reads the variable when it runs:

```go
func mystery2() {
	n := 1
	defer func() { fmt.Println(n) }() // defers the CALL to the closure, with no arguments
	n = 2
	fmt.Println(n)
}
// prints: 2, then 2
```

Here `defer` registers a call to the function literal `func() { fmt.Println(n) }` — the literal itself has no arguments, so there is nothing to evaluate ahead of time (except the function value itself, which is trivial). The literal's body captures the variable `n` from the outer scope (the same mechanism as a closure — in detail in 02.04 and in 01-Basics/02.08). When the runtime finally runs this deferred call, the body reads `n` **at that moment**, when `n` is already `2`. The difference between `mystery` and `mystery2` is the difference between “argument evaluated at registration” and “variable read at execution” — the same difference that makes a closure “see” later changes, while a direct argument does not.

### Classic resource pattern — `defer` immediately after successful acquisition

```go
f, err := os.Open(path)
if err != nil {
	return err
}
defer f.Close()
```

The order here is not accidental: `defer f.Close()` comes **after** the `err != nil` check, not before. Why that matters: `Close` is a method on `f`; if `Open` failed, `f` is `nil` (`zero value` for `*os.File`), and `defer f.Close()` would register a method call on a `nil` value. For `*os.File` specifically, `Close` on a `nil` receiver returns an error without a `panic` (the standard library implementation checks that explicitly), but that is a property of **that specific** implementation, not a general rule for every type — the pattern “register `defer` **only after** successful resource acquisition” remains correct and safe for every resource (mutex, DB connection, HTTP response body), with no exception you must remember per type.

Once `defer f.Close()` has registered the call, **every** subsequent `return` from that function — any branch, however many there are further down in the body — first runs `Close`, then returns the result to the caller. The programmer does not have to remember to add `f.Close()` on every `return` line; `defer` guarantees that once, at the acquisition site.

### `defer` in a loop — a trap that does not leak immediately

```go
func readAllBad(paths []string) error {
	for _, path := range paths {
		f, err := os.Open(path)
		if err != nil {
			return err
		}
		defer f.Close() // registers, but does NOT run until the END of the WHOLE function
		// read f ...
	}
	return nil
}
```

Here the trap is subtle, because the code **works** — it does not panic, does not return wrong data. The problem is *when* `Close` actually happens. `defer` is tied to the current function (`readAllBad`), not to the current loop iteration. Every `defer f.Close()` inside the `for` loop registers a **new** call on the same stack, but the runtime pops that stack only when the **whole** `readAllBad` finishes — after the loop has processed **all** paths. Result: if `paths` contains a thousand files, all thousand stay open **at the same time** while the loop runs, and they all close together at the end, in reverse open order (LIFO). For small lists this does not create a visible problem; for large lists, the process exhausts available file descriptors and the next `os.Open` fails with “too many open files” — a bug that shows up only under production load, not in a small test.

Solution: extract the body of one iteration into a helper function. Each call to that function has **its own** deferred-call stack, which is popped at the end of **that** call, not at the end of the whole loop:

```go
func readAll(paths []string) error {
	for _, path := range paths {
		if err := readOne(path); err != nil {
			return err
		}
	}
	return nil
}

func readOne(path string) error {
	f, err := os.Open(path)
	if err != nil {
		return err
	}
	defer f.Close() // pops at the end of THIS readOne call, not the whole loop
	// read f ...
	return nil
}
```

Now each file is opened and closed within one iteration, before the loop moves to the next path. At any moment, at most one file is open.

### `panic` and `error` — two different contracts

`error` is **part of the function signature** — the caller explicitly receives it as a value and explicitly checks it. `panic` **interrupts** normal flow: it unwinds the stack, running `defer` calls along the way, until it reaches a `recover` or the top of the `goroutine` (where the whole process dies, printing a stack trace).

```go
func readOrPanic(path string) string {
	b, err := os.ReadFile(path)
	if err != nil {
		panic(err) // BAD: "file does not exist" is an EXPECTED failure, not a bug
	}
	return string(b)
}

func readFile(path string) (string, error) {
	b, err := os.ReadFile(path)
	if err != nil {
		return "", fmt.Errorf("readFile: %w", err)
	}
	return string(b), nil
}
```

`readOrPanic` turns a predictable situation (a file that occasionally does not exist — the user deletes configuration, the network is slow, a deploy is in progress) into a `panic`, which — if nobody places `recover` above — crashes the whole process. `readFile` returns the same situation as an `error`, which the caller handles as they see fit: try a default, report to the user, retry with backoff. Criterion for choosing: if the situation enters the normal, documented flow of the program (unavailable file, bad input, HTTP 404), use `error`. If the situation means something is **impossible** by the program's contract (an index out of bounds that should never happen if the logic is correct, a `nil` `pointer` where an invariant guarantees it cannot be `nil`), `panic` is more legitimate — but even then, libraries often offer a `Must` variant (`template.Must`) exactly to isolate `panic` to a place where the programmer *chooses* to take the risk, typically at program `init`.

### `recover` — only in `defer`, only at the boundary

`recover` stops `panic` propagation **exclusively** when called inside a `defer` function, in the same `goroutine` that is panicking:

```go
defer func() {
	if r := recover(); r != nil {
		log.Printf("panic caught: %v", r)
		// state BELOW this point may be inconsistent — limit what you do next
	}
}()
```

A call to `recover()` outside a `defer` function does nothing (returns `nil`, catches nothing) — it must be **directly** inside the body of the function that `defer` registered (or inside a function that `defer` function calls, as long as it is in the same deferred-call stack frame). The typical place for `recover` is a system **boundary**: HTTP middleware that wraps every handler, a worker that processes queue messages one by one, a `goroutine` started from `main` whose crash should not take down the whole process. `recover` in every internal function turns every `panic` — including real bugs like a `nil` dereference that **should** be visible and fixed — into a silent no-op, which hides the bug instead of reporting it.

### `panic` through multiple call levels — what actually propagates

It is worth slowly separating what the runtime **actually** does when a `panic` travels through several nested function calls, because the intuition “panic immediately stops the process” is wrong — the panic **first** goes through all `defer` calls along the path, and only if nobody does `recover` does the process die.

```go
func level3() {
	defer fmt.Println("level3 defer")
	panic("boom")
}

func level2() {
	defer fmt.Println("level2 defer")
	level3()
	fmt.Println("level2: this is NEVER printed")
}

func level1() {
	defer func() {
		if r := recover(); r != nil {
			fmt.Println("level1 recover:", r)
		}
	}()
	level2()
	fmt.Println("level1: this is also not printed")
}
```

Execution trace, step by step:

| Step | What happened | Print |
|------|---------------|-------|
| 1 | `level1` registers `defer` with `recover()` | (nothing) |
| 2 | `level1` calls `level2` | — |
| 3 | `level2` registers its `defer` | (nothing) |
| 4 | `level2` calls `level3` | — |
| 5 | `level3` registers its `defer` | (nothing) |
| 6 | `level3` runs `panic("boom")` — normal flow in `level3` is IMMEDIATELY interrupted; the rest of the body (if there was any) does not run | (nothing) |
| 7 | Runtime runs the `defer` row of `level3` **before** leaving that stack frame | `level3 defer` |
| 8 | Panic continues to propagate into `level2` (which called `level3`) — the line `fmt.Println("level2: ...")` does **not** run, because the `level3()` call was the last thing that flowed normally | (nothing new) |
| 9 | Runtime runs the `defer` row of `level2` | `level2 defer` |
| 10 | Panic continues into `level1` — `fmt.Println("level1: ...")` does not run | (nothing new) |
| 11 | Runtime runs the `defer` row of `level1`; inside, `recover()` **catches** the panic — from this moment, the panic does not propagate further | `level1 recover: boom` |
| 12 | `level1` finishes normally (as if the panic never existed, from the perspective of *its* caller) | — |

Total output: `level3 defer`, `level2 defer`, `level1 recover: boom`. Key lesson: **every** level on the propagation path runs its `defer` row (including LIFO order within that level, if there are multiple `defer` calls), and `recover()` stops propagation exactly where it is called — no level **above** that point (in this case, the caller of `level1`) learns that a panic ever existed.

### `panic` inside a `defer` function — a panic that replaces a panic

A rare but important subtlety: if a `defer` function **itself** panics while handling a previous panic (e.g. while logging or cleaning up), the new panic **replaces** the old one in further upward propagation. The original value of the first panic is not completely lost — the Go runtime still records it and shows both in the output when the process dies — but for a `recover()` that continues the path to the next level, only the second panic is the one actually caught.

```go
func risky() {
	defer func() {
		panic("second panic, from defer") // replaces the first in further propagation
	}()
	panic("first panic")
}
```

A call to `risky()` with no `recover` on the path would crash the process with a message that mentions **both** panics (the Go runtime chains them in the stack trace), but logically, a `recover()` placed above `risky()` would catch the value `"second panic, from defer"`, not `"first panic"`. Practical consequence: a `defer` function that does `recover()` should be **simple** and carefully written — an extra `panic` inside it (e.g. from poorly implemented logging code) erases the original error context that was valuable for diagnosis.

## Rules and syntax

- `defer expression(arguments)` evaluates `arguments` **immediately**; the call itself is deferred until exit from the current function.
- Multiple `defer` calls in the same function: LIFO — last registered, first executed.
- `defer` is tied to the **function** in which it is called, not to a block or loop inside it; there is no package-level `defer`.
- `recover()` works only when called directly inside a `defer` function, in the same `goroutine`.
- `panic`/`recover` are not a substitute for `error` — use `error` for everything expected to occasionally go wrong.
- `Must*` helpers (e.g. `template.Must`, `regexp.MustCompile`) legitimately panic — usually at `init` or configuration, where continuing without a correct value makes no sense.
- After `recover`, program state may be partially changed (panic interrupted flow at an arbitrary point) — limit what you do next in the same `goroutine`, typically only log and a clean exit from processing that one request.
- A guard clause (early `return`) needs no special syntax — it is a stylistic pattern of using ordinary `if` + `return`.

## Examples

### Example 1 — Guard clause instead of a pyramid

```go
package main

import (
	"fmt"
	"strings"
)

func normalizeEmail(s string) (string, error) {
	s = strings.TrimSpace(s)
	if s == "" {
		return "", fmt.Errorf("email: empty")
	}
	if !strings.Contains(s, "@") {
		return "", fmt.Errorf("email: no @")
	}
	return strings.ToLower(s), nil
}

func main() {
	fmt.Println(normalizeEmail("  User@Example.com "))
	fmt.Println(normalizeEmail(""))
	fmt.Println(normalizeEmail("noat"))
}
```

#### What happens here

Every failure condition jumps out immediately, at the base indentation level — there are no nested `else` branches. The first call passes both guards and reaches `return strings.ToLower(s), nil`. The second call (`""`) jumps out on the first guard. The third (`"noat"`) passes the first guard (not empty), but fails the second (no `@`). Reading is linear: every line says what **must** be true for the function to continue, instead of describing a nested branching structure.

### Example 2 — `defer f.Close()` and LIFO order

```go
package main

import (
	"fmt"
	"os"
)

func copyShort(dst, src string) error {
	in, err := os.Open(src)
	if err != nil {
		return err
	}
	defer in.Close()

	out, err := os.Create(dst)
	if err != nil {
		return err
	}
	defer out.Close()

	buf := make([]byte, 32)
	n, err := in.Read(buf)
	if err != nil {
		return err
	}
	_, err = out.Write(buf[:n])
	return err
}

func orderDemo() {
	defer fmt.Println("first defer (runs last)")
	defer fmt.Println("second defer (runs first)")
}

func main() {
	orderDemo()
	_ = copyShort
}
```

#### What happens here

`orderDemo` prints “second defer...” before “first defer...” — LIFO. In `copyShort`, both `defer`s (`in.Close()` and `out.Close()`) are registered in open order, but run in **reverse** order on every `return` branch: first `out.Close()` (registered second, but runs first), then `in.Close()`. Regardless of which `return` line is hit — successful at the end or an error in the middle — both files are closed, because `defer` calls are tied to the function, not to the point where `return` is written.

### Example 3 — `defer` for `Unlock`

```go
package counter

import "sync"

type Counter struct {
	mu sync.Mutex
	n  int
}

func (c *Counter) Inc() {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.n++
}

func (c *Counter) Value() int {
	c.mu.Lock()
	defer c.mu.Unlock()
	return c.n
}
```

#### What happens here

`defer c.mu.Unlock()` is registered immediately after `Lock()`, before any logic that might have multiple `return` branches. If someone later adds an early `return` inside `Inc` (e.g. a guard for an invariant), `Unlock` still runs on exit, with no need to add it manually on every new branch. A forgotten `Unlock` without `defer` means every new `return` branch the programmer adds must also manually add `Unlock` — one forgotten branch is a deadlock that only appears when that branch is finally hit in production.

### Example 4 — `panic` is not a substitute for `error`

```go
package main

import (
	"fmt"
	"os"
)

func readOrPanic(path string) string {
	b, err := os.ReadFile(path)
	if err != nil {
		panic(err) // BAD for expected "file does not exist"
	}
	return string(b)
}

func readFile(path string) (string, error) {
	b, err := os.ReadFile(path)
	if err != nil {
		return "", fmt.Errorf("readFile: %w", err)
	}
	return string(b), nil
}

func main() {
	s, err := readFile("config.json")
	if err != nil {
		fmt.Println("expected failure:", err)
		return
	}
	fmt.Println(s)
	_ = readOrPanic
}
```

#### What happens here

`readFile` returns an `error` that `main` handles explicitly — the program continues to run, only reports the failure and returns from `main`. `readOrPanic` would, on the same failure, start a `panic` that propagates through the caller's stack; without `recover` anywhere on the path, the whole process stops with a stack trace on standard error. For “configuration file does not exist” — a situation expected on first program start or a bad path — `panic` is an excessive reaction; `error` gives the caller a choice how to react.

### Example 5 — `recover` at the HTTP handler boundary

```go
package main

import (
	"fmt"
	"log"
	"net/http"
)

func withRecover(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		defer func() {
			if rec := recover(); rec != nil {
				log.Printf("panic: %v", rec)
				http.Error(w, "internal error", http.StatusInternalServerError)
			}
		}()
		next.ServeHTTP(w, r)
	})
}

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /boom", func(w http.ResponseWriter, r *http.Request) {
		panic("bug simulation")
	})
	mux.HandleFunc("GET /ok", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, "ok")
	})
	log.Println("demo server :8080")
	log.Fatal(http.ListenAndServe(":8080", withRecover(mux)))
}
```

#### What happens here

`withRecover` is middleware that wraps **every** handler with one `defer` + `recover`, placed **once**, at the boundary (before calling `next.ServeHTTP`). When `/boom` panics, `recover()` inside the `defer` function catches that value before it reaches the top of the `goroutine` processing that HTTP request — the server keeps running, that one request gets HTTP 500, and `/ok` still works normally for the next request. Without this middleware, a `panic` in a handler would in the standard `net/http` implementation also be caught at the server level (which internally has its own `recover` per connection) — but your own middleware gives control over the **format** of the response and logging, instead of relying on the library's default behavior.

### Example 6 — `named result` + `defer` + `errors.Join` for multiple resources

```go
package main

import (
	"errors"
	"fmt"
	"os"
)

func mergeFiles(dst, srcA, srcB string) (err error) {
	out, err := os.Create(dst)
	if err != nil {
		return err
	}
	defer func() {
		err = errors.Join(err, out.Close())
	}()

	a, err := os.Open(srcA)
	if err != nil {
		return err
	}
	defer func() {
		err = errors.Join(err, a.Close())
	}()

	b, err := os.Open(srcB)
	if err != nil {
		return err
	}
	defer func() {
		err = errors.Join(err, b.Close())
	}()

	if _, err := fmt.Fprintln(out, "merged"); err != nil {
		return err
	}
	return nil
}

func main() {
	err := mergeFiles(os.TempDir()+"/out.txt", os.TempDir()+"/a.txt", os.TempDir()+"/b.txt")
	fmt.Println(err)
}
```

#### What happens here

Each resource (`out`, `a`, `b`) gets its own `defer` immediately after successful acquisition, by the same pattern as earlier examples. The difference is that each `defer` uses `errors.Join(err, ...)` to **append** the Close error onto the existing `named result` `err`, instead of simply overwriting it. `errors.Join` (Go 1.20+) makes one `error` value that wraps multiple errors — if `err` on entry into `defer` is `nil` and Close succeeds, `errors.Join(nil, nil)` returns `nil`; if either side is not `nil`, the result carries both pieces of information. LIFO order means `b.Close()` is appended first (registered last), then `a.Close()`, then `out.Close()` — all onto the same `err` variable, so no Close error is silently lost, no matter how many resources are involved.

## Decision analysis

| Decision | Motive | Alternative |
|----------|--------|-------------|
| Early `return` (guard clause) | Less nesting, happy path stays readable | Deeply nested `if`/`else` — harder to read and change |
| `defer` immediately after successful acquisition | Cleanup guaranteed on every `return` branch, without manual addition | Manual `Close`/`Unlock` on every branch — easy to forget on a new branch |
| `error` for expected failures | Caller chooses how to react | `panic` — crashes the process or always requires `recover` |
| `recover` at the boundary (middleware, worker) | Bug isolation, one request does not take down the whole process | `recover` in every function — hides bugs, hard to debug |
| Extracting the loop body into a helper for `defer` | Cleanup per iteration, not per whole loop | `defer` directly in `for` — resources pile up until end of function |

## Trade-offs

- Many early `return` branches sometimes duplicate `fmt.Errorf` wrapping on every branch — help with a helper function if the pattern repeats three or more times.
- `defer` in a hot loop (millions of iterations) carries a small but measurable registration cost — measure if performance is critical, do not assume ahead of time.
- `recover` swallows the stack trace unless you explicitly log `debug.Stack()` — without that, the cause of the bug is harder to reconstruct after the fact.
- The `Close() error` result is often ignored (`defer f.Close()` without checking the value) — the `named result` + `defer` pattern from 02.01 is better when the Close error must be seen.
- Guard clause versus one large `if` with all conditions joined by `&&`: the guard is more readable for debug (each line has its own error message), the large `if` is more compact for trivial checks.

## Common mistakes

### Pyramid of `if err == nil { ... }` instead of early `return`

**Wrong:**

```go
func process(s string) error {
	if s != "" {
		if len(s) < 100 {
			// real logic deep inside
			return nil
		} else {
			return fmt.Errorf("too long")
		}
	} else {
		return fmt.Errorf("empty")
	}
}
```

**Effect:** The happy path is buried three indentation levels inside; adding a new check requires another level, and reading the logic requires tracking all open `if`/`else` branches at once.

**Fix:** Guard clause for every failure condition, happy path at the end: `if s == "" { return fmt.Errorf("empty") }`, `if len(s) >= 100 { return fmt.Errorf("too long") }`, then `return nil`.

### `defer f.Close()` before checking `err` on `Open`

**Wrong:**

```go
f, err := os.Open(path)
defer f.Close() // f may be nil if Open failed
if err != nil {
	return err
}
```

**Effect:** If `Open` fails, `f` is `nil`; `defer f.Close()` registers a method call on a `nil` value. For `*os.File` that is safe in the standard library, but for your own types or other resources without that same protection, a method call on a `nil` receiver that dereferences a field is a `panic`.

**Fix:** Register `defer` **after** the error check: check `err != nil` and return early, then only then `defer f.Close()`.

### `panic` for validating user input

**Wrong:**

```go
func parsePort(s string) int {
	p, err := strconv.Atoi(s)
	if err != nil {
		panic("invalid port: " + s)
	}
	return p
}
```

**Effect:** User input is **expected** to be occasionally invalid (typo, empty field) — `panic` on every such input crashes the process or requires every caller to place `recover`, instead of simply checking `error`.

**Fix:** Return `(int, error)` and let the caller decide: show a message to the user, use a default value, or abort only that operation — `func parsePort(s string) (int, error)`.

### `recover` in every function, not only at the boundary

**Wrong:**

```go
func computeDiscount(price float64) float64 {
	defer func() {
		recover() // swallows EVERY panic, including real bugs
	}()
	return price * discountTable[price] // panic if price is not a key
}
```

**Effect:** `recover()` with no check or logging turns a `panic` (which here is a signal of a **bug** — a missing key in the map) into a silent no-op that returns the `zero value` (`0.0`) with no trace that something went wrong. The bug stays undiscovered until the user notices that all discounts are `0`.

**Fix:** Remove `recover` from internal logic; either check key existence explicitly (`if d, ok := discountTable[price]; ok { return price * d }`) and return `error` for an unknown price, or let the `panic` travel to the single, documented boundary (e.g. HTTP middleware) where it is caught **and logged**.

### `defer` directly in a `for` loop for resources opened per iteration

**Wrong:**

```go
func processAll(paths []string) error {
	for _, p := range paths {
		f, err := os.Open(p)
		if err != nil {
			return err
		}
		defer f.Close() // closes only at the end of the WHOLE processAll
		// process f ...
	}
	return nil
}
```

**Effect:** All files stay open at the same time until the end of the **whole** function, not until the end of their iteration. For a long list of paths, the process exhausts available file descriptors before the loop finishes.

**Fix:** Extract the iteration body into a helper function (`processOne(path string) error`) that has its own `defer` stack, popped at the end of **that** call, not at the end of the loop.

### Relying on `defer` order without LIFO awareness

**Wrong:**

```go
defer releaseLock()      // registered first
defer closeConnection()  // registered second — but connection may need the lock to close
```

**Effect:** LIFO order runs `closeConnection()` **first** (because it was registered last), and `releaseLock()` **after** — if `closeConnection` internally depends on locked state, Close happens when the resource is already unlocked, opening a window for a race with another `goroutine`.

**Fix:** Register `defer` calls in the order that matches the **desired** reverse execution order — if `closeConnection` must go before `releaseLock`, register `closeConnection` first, `releaseLock` second, so LIFO runs `releaseLock` first, `closeConnection` second... or, more clearly, rethink whether the lock should wrap that operation at all.

## Idiomatic Go

- The standard library and Effective Go favor guard clauses over nested `if`/`else`.
- `defer resp.Body.Close()` immediately after a successful `http.Get` — a common pattern in code that makes HTTP calls.
- `Must*` functions (`regexp.MustCompile`, `template.Must`) legitimately panic, but only for configuration known at compile/`init` time, not for runtime input.
- `recover` middleware is standard in HTTP servers and worker pools — one place, not scattered.
- Register `defer` for `Unlock`/`Close`/`Cancel`/rollback **immediately** after successful acquisition, not at the end of the function.

## Practical scenario

A file upload service opens a temporary file on disk, then initializes an S3 client, then opens a database transaction — all in a sequence, without `defer` on any step. When the third step (transaction) fails, the function returns `error`, but the temporary file and S3 session stay open, because the programmer planned “manual” cleanup at the end that was never written for an error on the third step. After a few weeks in production, the disk fills with temporary files. Refactor: every resource gets `defer` **immediately** after its successful acquisition — `defer os.Remove(tmpPath)` after successfully creating the temporary file, `defer s3Client.Close()` after a successful connection, `defer tx.Rollback()` after `BeginTx` (with a `named result` `err` that, if the operation succeeds, explicitly calls `tx.Commit()` before `return` — pattern in detail in lesson 03.02 on transactions). In parallel, the team notices that the handler processing uploads occasionally panics on a `nil` `pointer` when a client sends a malformed multipart body — they add `recover` middleware at the HTTP router level, so that specific bug returns HTTP 500 instead of taking down the whole process, until the bug is fixed in the next release.

## Check questions

1. **When are arguments of a `defer` expression evaluated?**  
   **Answer:** Immediately, at the moment the `defer` line runs — not at the moment the deferred call actually happens. Only the call is deferred.

2. **What is the execution order of multiple `defer` calls in the same function?**  
   **Answer:** LIFO — the last registered runs first.

3. **Why should `defer f.Close()` go after checking `err` on `Open`, not before?**  
   **Answer:** If `Open` fails, `f` is `nil`; registering a `defer` method call on a potentially `nil` value is risky outside specific, documented standard library exceptions.

4. **What is the trap of `defer` in a `for` loop?**  
   **Answer:** `defer` is tied to the whole function, not the iteration — all resources opened in the loop stay open until the end of the whole function, not until the end of their iteration, unless the iteration body is extracted into a helper function.

5. **What is the difference between `error` and `panic` as a failure signal?**  
   **Answer:** `error` is part of the function signature for **expected** failures that the caller explicitly checks; `panic` interrupts normal flow for **unstable** state (bug, impossible invariant) and propagates until `recover` catches it or the process dies.

6. **Where may `recover()` be called to have an effect?**  
   **Answer:** Exclusively directly inside a `defer` function, in the same `goroutine` that is panicking — a call outside a `defer` context catches nothing.

7. **Why is `recover` in every internal function not good practice?**  
   **Answer:** It also swallows real bugs (e.g. a `nil` dereference that should be visible and fixed), turning them into silent no-ops; `recover` should be placed at a clear, documented system boundary.

8. **What happens if a `defer` function that handles a `panic` itself panics?**  
   **Answer:** The new panic replaces the old one in further upward propagation — `recover()` at the next level catches the **new** value, not the original; the runtime still records both in the output on an uncaught crash.

## Summary

Control flow in a reliable Go function has three tools with clearly separated roles: early `return` (guard clause) for readable branching without nesting, `defer` for cleanup that must happen on every exit from the function (with LIFO order and arguments evaluated immediately at registration), and `panic`/`recover` reserved for unstable state at a clearly bounded system boundary, not for expected failures that go through `error`. `defer` in a loop needs care — it is tied to the function, not the iteration, so a body that opens resources per iteration usually needs to be extracted into a helper function.
