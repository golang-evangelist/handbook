# 02.03 Method Receivers: Value Receiver, Pointer Receiver, and Method Set

> **Go Path - Zero to Gopher** / **02 Intermediate → Deep dive into Go Functions** / Lesson 02.03

## Terminology (gloss once)

The terms below are **not translated** further through the lesson — they are used in the original. Here is the explanation once, in one place.

| Term | Meaning |
|---|---|
| **receiver** | The implicit first parameter of a method — the type the function is “bound” to (in `func (b *Bag) Add(...)`, `b` is the receiver). |
| **pointer** | A value that holds a memory address where some data lives; `*T` is the type of a pointer to `T`. |
| **interface** | A contract defined by a set of methods; a type satisfies (implements) an interface if its method set contains all of its methods. |
| **method set** | The set of methods available for a given type (`T` or `*T`); determines which interfaces that type satisfies and which methods can be called. |
| **value receiver** | A receiver declared as `(t T)` — the method gets a copy of the value `t`. |
| **pointer receiver** | A receiver declared as `(t *T)` — the method gets a copy of the pointer (the same address), so it shares state with the caller. |
| **zero value** | The value with which a variable is automatically initialized when not set explicitly (`nil` for a pointer, `0` for numbers, `""` for string, a struct with all fields at their zero values). |

## Lesson goals

- Choose **value receiver** vs **pointer receiver** by the rules of mutation, consistency, and type size.
- Understand the **method set** of types `T` and `*T` and why that is decisive for satisfying an **interface**.
- Recognize when Go automatically takes an address (auto-referencing) and when that is not possible (addressability).
- Write methods on **named types** over scalars (`type Celsius float64`) and understand why they do not inherit methods of the underlying type.
- Safely write and call methods on a **nil receiver** when that is intentionally allowed.
- Design a consistent type API — without randomly mixing receiver styles.
- Connect receiver mechanics with the copy semantics from lessons 02.01–02.02.

## Prerequisite

- Lessons 02.01–02.02 (functions, parameters, copy vs shared memory).
- Structs and basic familiarity with interfaces.
- Slice header (pointer, len, cap) — mentioned in the traces of this lesson.

## Problem this lesson solves

A random choice between `func (t T) M()` and `func (t *T) M()` leads to three classes of bugs and frustrations:

- a method that “does not keep” changes, because it worked on a copy of the receiver, not the original;
- types that seemingly should implement some interface, but the compiler refuses because the method set of `T` does not contain methods defined on `*T`;
- an inconsistent API where half the methods require a pointer, half do not, so the same type works in one context (a local variable) and does not work in another (a map element, a function result).

This lesson solves the problem by first explaining the **mechanism** — what exactly is copied and when — and then deriving design rules from the mechanism.

## Mental model

A method is a function with an **implicit first argument** — the receiver. That means:

```go
func (b *Bag) Add(s string) { b.items = append(b.items, s) }
```

is conceptually equivalent (not literally, but the mechanics are the same) to the function:

```go
func Add(b *Bag, s string) { b.items = append(b.items, s) }
```

From that follow four pillars of the model that we will unpack in detail in Mechanism:

- `(t T)` — the receiver gets a **copy** of the value `t`, like any other parameter passed by value.
- `(t *T)` — the receiver gets a **copy of the pointer** (the same address); through that copy you can reach the original.
- The method set of `*T` includes methods defined with both a `T` and a `*T` receiver.
- The method set of `T` includes **only** methods defined with a `T` receiver — not those with `*T`.
- That is why `var x T` may **not** implement an interface that requires at least one pointer method, while `&x` (of type `*T`) always implements all of them.

Details, traces, and “what if” scenarios come in the next section — intentionally the longest in the lesson, because this is the point where the most mistakes are made in practice.

## Mechanism

This is the longest section of the lesson. Every subsection has a concrete execution trace and a micro-exercise of the form **Predict** (try to answer before you read) / **Answer** (explanation). The goal is for the mechanics to become a reflex, not a memorized rule.

### 1. Receiver as an implicit parameter

```go
type Bag struct{ items []string }

func (b *Bag) Add(s string) { b.items = append(b.items, s) }

var b Bag
b.Add("milk")
```

**Predict:** `b` is of type `Bag`, not `*Bag`. Why does `b.Add("milk")` even compile when `Add` is defined on `*Bag`?

**Answer:** The compiler automatically takes the address of the variable when that is needed and possible — the call `b.Add("milk")` is treated as `(&b).Add("milk")`. This works **only** when `b` is *addressable* (an ordinary variable, a field of a struct that is a variable, a slice element) — it does not work for every value, as we will see in section 4.

This small but key fact — auto-referencing on a method call, but not on assignment to an interface — explains almost all confusion around receivers in Go. Remember it; we return to it several times.

### 2. Value receiver — copy mechanics

```go
type Bag struct{ items []string }

func (b Bag) AddValue(s string) { b.items = append(b.items, s) }

func main() {
	var b Bag
	b.AddValue("milk")
	fmt.Println(len(b.items)) // ?
}
```

**Predict:** What does `len(b.items)` print?

**Answer:** `0`. Execution trace:

| Step | Instruction | `b.items` at the caller | `b.items` inside the method (copy) |
|---|---|---|---|
| 0 | `var b Bag` | `nil` (slice zero value) | — |
| 1 | `b.AddValue("milk")` — receiver is copied | `nil` | header copy: `nil` |
| 2 | `append` in the method body allocates a new array and returns a new header `{ptr: X, len: 1, cap: ≥1}` | `nil` (unchanged) | `{ptr: X, len: 1, cap: ≥1}` |
| 3 | method returns, local receiver copy is discarded | `nil` | (discarded) |
| 4 | `len(b.items)` at the caller | `0` | — |

A slice is underneath a three-word structure (pointer to the underlying array, len, cap) — that “header” is copied like every other struct field when the receiver is a value. `append` in the method body changes the **copy** of the header, not the original.

**Predict (bonus, subtler):** Would the result be different if `b.items` already had free capacity, e.g. `b.items = make([]string, 0, 5)` before the call?

**Answer:** `len(b.items)` at the caller is **still 0**, because `len` is part of the header that was copied — but! If there is free capacity, `append` inside the method writes “milk” **into the same underlying array** the caller shares (no reallocation because there is room). The data physically exists in memory that the caller's slice also looks at, but the caller's header still says `len=0`, so `fmt.Println` does not see it. Danger: if the caller later does its own `append` within that capacity, it can **overwrite** “milk” with no connection to `AddValue`. This is why slice mutations are almost always done through a pointer receiver — you avoid this kind of quiet, hard-to-debug chaos.

**Predict (third level):** Does ANY mutation through a value receiver fail to reach the caller?

**Answer:** No — it depends on whether the mutation changes the slice **header** (length, capacity, pointer to a new array — that is not visible through the copy) or changes an **element** through the existing underlying array (`a[i] = x` — that is visible, because the underlying array is not copied, only the header that points to it). The standard library uses this (`sort.Interface.Swap`) and we return to it in the “Idiomatic Go” section.

### 3. Pointer receiver — shared-address mechanics

```go
func (b *Bag) Add(s string) { b.items = append(b.items, s) }

func main() {
	var b Bag
	b.Add("milk")
	fmt.Println(b.items) // ?
}
```

**Predict:** What exactly is copied when the receiver is `*Bag`?

**Answer:** The **pointer itself** is copied — the address value — not the structure it points to. Execution trace (addresses are illustrative):

| Step | Instruction | Address of `b` at the caller | Value at that address (`items`) |
|---|---|---|---|
| 0 | `var b Bag` at `0xA000` | `0xA000` | `nil` |
| 1 | `b.Add("milk")` → `(&b).Add("milk")` — receiver copy is a pointer with value `0xA000` | `0xA000` | `nil` |
| 2 | in the body: `b.items = append(b.items, "milk")` — this is actually `(*receiver).items = ...`, a write to address `0xA000` | `0xA000` | `["milk"]` |
| 3 | method returns; the pointer copy is discarded, but the write is already done on the shared address | `0xA000` | `["milk"]` |
| 4 | `fmt.Println(b.items)` at the caller | `0xA000` | `["milk"]` — visible! |

The **address** is copied, not the **contents at the address**. That is why dereferencing (`b.items = ...` inside the method, where `b` is of type `*Bag`) writes to the same memory the caller also sees.

### 4. Method set and addressability — the T vs *T rule

Formal rule:

| Type definition `T` | Method set of `T` | Method set of `*T` |
|---|---|---|
| Methods | only those with a `(t T)` receiver | those with a `(t T)` **and** those with a `(t *T)` receiver |

Consequence: `*T` always “sees” everything; `T` sees only its subset. But whether you can **call** a pointer method through a value variable depends on the **addressability** of that variable — not only on the type.

```go
type Counter struct{ n int }

func (c *Counter) Inc() { c.n++ }

func main() {
	// Case A — ordinary variable: addressable
	var a Counter
	a.Inc() // OK, compiler does (&a).Inc()

	// Case B — slice element: addressable
	s := []Counter{{}}
	s[0].Inc() // OK, compiler does (&s[0]).Inc()

	// Case C — map element: NOT addressable
	m := map[string]Counter{"a": {}}
	m["a"].Inc() // ???
}
```

**Predict:** Does Case C compile?

**Answer:** No. Map elements are not addressable, because a Go map may internally reallocate storage (for example on rehash), so the address of an element would not be stable. The compiler rejects the call with an error in the spirit of: `cannot call pointer method Inc on m["a"]` (or `cannot take address of m["a"]`). This is not a stylistic recommendation — the code **does not compile**.

Contrast with a slice (Case B): slice elements **are** addressable, because the underlying array is stable, contiguous memory — `&s[0]` is legal and stable as long as the slice itself is not reallocated through `append`.

**Predict (deeper):** Does `s[0].Inc()` from Case B affect `s`?

**Answer:** Yes — `s[0]` is an addressable element of a shared underlying array; `(&s[0]).Inc()` changes the `n` field directly on that memory, so `s[0].n` at the caller sees the change. This is the same mechanism as the pointer receiver in section 3, only the address is “inside” the slice instead of a standalone variable.

### 5. Interface satisfaction and method set

```go
type Greeter interface {
	Greet() string
}

type Person struct{ Name string }

func (p *Person) Greet() string { return "Hello, " + p.Name }

func main() {
	p := Person{Name: "Marko"}

	fmt.Println(p.Greet()) // (A) — works?

	var g Greeter
	g = p // (B) — compiles?
	_ = g
}
```

**Predict:** Does line (A) work? Does line (B) compile?

**Answer:** (A) works — `p.Greet()` is a **direct method call** on the addressable variable `p`, so the compiler does auto-referencing: `(&p).Greet()`. (B) **does not compile** — assignment to an interface variable is a static check of the **method set of type** `Person` (without auto-referencing): `Person` does not have `Greet` in its method set, because `Greet` is defined on `*Person`. The error is in the spirit of: `cannot use p (variable of type Person) as Greeter value: Person does not implement Greeter (method Greet has pointer receiver)`.

Fix for (B): `g = &p`. Then `*Person` — whose method set contains `Greet` — satisfies `Greeter`.

**Predict (key difference):** Why do (A) and (B) have different outcomes when both “use” `p`?

**Answer:** A method call (A) is a syntactic convenience that does auto-referencing if the operand is addressable and if that is needed to find the method. Assignment to an interface (B) does not go through that convenience — the compiler must know ahead of time, statically, that the concrete type satisfies the interface, and that depends exclusively on the **declared** method set of the type on the left side of the assignment (`Person`, not `*Person`). This is the most common cause of “works when I call the method directly, but not when I pass it to a function that takes an interface” bugs.

### 6. Named scalars — type mechanics

```go
type Celsius float64
type Fahrenheit float64

func (c Celsius) ToF() Fahrenheit { return Fahrenheit(c*9/5 + 32) }

func main() {
	var c Celsius = 100
	var f Fahrenheit = c // ???
}
```

**Predict:** Does the assignment `var f Fahrenheit = c` compile?

**Answer:** No. `Celsius` and `Fahrenheit` are two **different** named types, even though both have `float64` as the underlying type. Go does not allow implicit assignment between different named types even when their underlying type is identical. Error: `cannot use c (variable of type Celsius) as type Fahrenheit in variable declaration`. An explicit conversion is needed: `Fahrenheit(c)`, or — idiomatically — a method: `c.ToF()`.

**Predict (method inheritance):** If `float64` somehow had a method `M()` (it does not, but hypothetically), would `Celsius` “inherit” it?

**Answer:** No. Defining `type Celsius float64` creates a **new, independent** type with the same storage (underlying representation) as `float64`, but methods are not transferred from the base type to the new one. The reverse also holds: a method defined on `Celsius` does not exist on `float64`, and does not exist on `Fahrenheit` even though the underlying type is the same. This differs from some other languages where a “type alias” implies shared behavior — in Go a named type (`type X Y`) is a new identity, and `type X = Y` (alias, with `=`) would be the same identity, but an alias does not allow adding your own methods if `Y` is from another package, nor does it change anything in this story about method sets.

### 7. Nil receiver — when it is allowed and how to use it safely

```go
type List struct {
	val  int
	next *List
}

func (l *List) Len() int {
	if l == nil {
		return 0
	}
	return 1 + l.next.Len()
}

func main() {
	var l *List // pointer zero value: nil
	fmt.Println(l.Len()) // ?
}
```

**Predict:** Does `l.Len()` panic when `l` is nil?

**Answer:** No. Calling a pointer-receiver method on a `nil` value of type `*T` is **legal in Go** — the receiver is simply passed as a `nil` pointer, like any other argument. A panic would arise **only** if the method body tried to dereference `nil` (e.g. `l.val` without a check). Here the first line is `if l == nil { return 0 }` — the check runs **before** any dereferencing, so it is safe. Result: `0`.

**Predict:** What would happen without that check, with `l.next.Len()` directly on a nil `l`?

**Answer:** `l.next` would try to read the `next` field from address `nil` — runtime panic: `runtime error: invalid memory address or nil pointer dereference`. A nil receiver is safe only while you treat it as **valid input data that you check first**, not as guaranteed non-nil.

This pattern (“nil as the empty case”) is common in recursive structures (lists, trees) and avoids the need for a special “empty” type or wrapper.

**Zero value note:** `nil` is the **zero value** for every pointer type in Go. When you declare `var l *List` without initialization, `l` automatically gets the zero value `nil` — this is not a special case, but the general rule for the zero value of pointer types (same as `0` for `int`, `""` for `string`).

**The nuance that confuses the most people — a nil pointer inside a non-nil interface:**

```go
type MyError struct{ msg string }

func (e *MyError) Error() string { return e.msg }

func doWork() error {
	var err *MyError // nil, zero value
	return err        // we return a nil *MyError PACKED into an error interface
}

func main() {
	if doWork() != nil {
		fmt.Println("an error occurred?!") // THIS IS PRINTED
	}
}
```

**Predict:** Does `doWork() != nil` give `true` or `false`?

**Answer:** `true` — even though the concrete pointer is `nil`! An interface value in Go internally carries a **pair** `(type, value)`. When `err` (of type `*MyError`, value `nil`) is returned as `error`, that interface carries the pair `(*MyError, nil)`. That is **not** the same as an “empty” interface — the pair `(nil, nil)`, which arises only if the interface variable never received either a type or a value. The check `!= nil` compares the whole pair, not only the value, so `(*MyError, nil) != (nil, nil)` is `true`. This is one of the best-known Go traps, and it is a direct consequence of the rule from section 5 (an interface carries a concrete type, not only a value).

We return to this as a concrete mistake in the “Common mistakes” section (item 7).

### 8. Consistent API — method set rules applied to constructor design

```go
type Counter struct{ n int }

func (c *Counter) Inc() { c.n++ }

func NewCounter() Counter { return Counter{} } // returns a VALUE

func main() {
	NewCounter().Inc() // ???
}
```

**Predict:** Does `NewCounter().Inc()` compile?

**Answer:** No. A function call result is a **temporary value** — it is not addressable (there is no variable whose `&` the compiler could take). The error is in the spirit of: `cannot call pointer method Inc on Counter` / `cannot take address of NewCounter()`. This is a direct consequence of the addressability rule from section 4, applied to a function return value instead of a map element.

**Predict:** How is this solved at the design level, not only locally at the call site?

**Answer:** If a type has **any** pointer-receiver method, the constructor should return `*T`, not `T` — then the result is already a pointer and there is no need for addressability tricks:

```go
func NewCounter() *Counter { return &Counter{} }

func main() {
	NewCounter().Inc() // OK — NewCounter() is already *Counter
}
```

This is why the rule “be consistent per type” is not only aesthetics — inconsistency directly breaks compilability of code in legitimate, common cases (function result, map element, value obtained from an interface).

## Rules and syntax

```go
func (r ReceiverType) Name(params) results
```

- Receiver name: short, usually one or two letters derived from the type (`c *Counter`, `s *Server`) — not `this` or `self` (those are conventions from other languages, not from Go).
- The receiver must be defined in the **same package** as the type.
- You cannot add a method directly on a type from another package (e.g. on `string` or `time.Duration` without your own named type) — you must define your own named type and put the method on it.
- The receiver name must be **the same in all methods of the same type** (a style convention that `go vet`/linters check) — see Common mistakes, item 8.
- `T` cannot have a pointer-receiver method in its method set; `*T` has both value and pointer receiver methods in its.

## Examples

### Example 1 — Mutation requires a pointer receiver

```go
package main

import "fmt"

type Bag struct {
	items []string
}

func (b Bag) AddValue(s string) {
	b.items = append(b.items, s) // changes only the local header copy
}

func (b *Bag) Add(s string) {
	b.items = append(b.items, s)
}

func main() {
	var b Bag
	b.AddValue("milk")
	fmt.Println(len(b.items)) // 0

	b.Add("milk")
	fmt.Println(b.items) // [milk]
}
```

#### What happens here

A value receiver changes a copy of the slice header — the caller does not see the change. A pointer receiver keeps the change, because it writes through a shared address. For collections that grow (append), a pointer receiver is the natural and usual choice. Full mechanics are explained in detail in Mechanism sections 2 and 3.

### Example 2 — Method set and interface

```go
package main

import "fmt"

type Greeter interface {
	Greet() string
}

type Person struct {
	Name string
}

func (p *Person) Greet() string {
	return "Hello, " + p.Name
}

func main() {
	var g Greeter
	p := Person{Name: "Marko"}
	// g = p  // does not compile: Person has no Greet in its method set
	g = &p
	fmt.Println(g.Greet())
}
```

#### What happens here

`Greet` has a pointer receiver. `Person` (value) does not implement `Greeter`; `*Person` implements it, because its method set contains both value and pointer receiver methods. The detailed trace of why that is so is in Mechanism section 5 — this is the most common trap when assigning a concrete type to an interface variable.

### Example 3 — Consistent pointer receivers

```go
package account

type Account struct {
	ID      string
	Balance int64
}

func (a *Account) Credit(amount int64) {
	a.Balance += amount
}

func (a *Account) Debit(amount int64) error {
	if amount > a.Balance {
		return errInsufficient
	}
	a.Balance -= amount
	return nil
}

func (a *Account) Snapshot() Account {
	return *a // state copy for reading, intentionally a value
}
```

```go
package account

import "errors"

var errInsufficient = errors.New("account: insufficient funds")
```

#### What happens here

All mutating methods use `*Account` — consistent, without surprises. `Snapshot` returns a value for immutable reading without sharing mutable state with the caller (the caller gets its own copy, which it may freely read without fear of concurrent change). This is a legitimate exception: value receiver/result for reading, pointer receiver for mutation — in the same type, without confusion, because the intent is clear from context.

### Example 4 — Named scalar Celsius

```go
package temp

import "fmt"

type Celsius float64
type Fahrenheit float64

func (c Celsius) String() string {
	return fmt.Sprintf("%.1f°C", float64(c))
}

func (c Celsius) ToF() Fahrenheit {
	return Fahrenheit(c*9/5 + 32)
}

func FromF(f Fahrenheit) Celsius {
	return Celsius((f - 32) * 5 / 9)
}
```

```go
package main

import (
	"fmt"

	"example.com/shop/temp"
)

func main() {
	c := temp.Celsius(22)
	fmt.Println(c.String(), c.ToF())
}
```

#### What happens here

`Celsius` is a separate type from `float64` and from `Fahrenheit` — you do not accidentally mix temperatures of different scales or a temperature with a bare number. Methods give behavior (`String`, `ToF`); `String` also helps with automatic formatting through the `fmt` package (if the type implements `fmt.Stringer`). The mechanics of why `Celsius` and `Fahrenheit` are not mutually assignable are in Mechanism section 6.

### Example 5 — Value receiver for a small immutable type

```go
package money

type Cent int64

func (c Cent) Add(o Cent) Cent { return c + o }

func (c Cent) String() string {
	neg := c < 0
	if neg {
		c = -c
	}
	s := formatTwoDecimals(int64(c))
	if neg {
		return "-" + s
	}
	return s
}

func formatTwoDecimals(v int64) string {
	whole := v / 100
	frac := v % 100
	return itoa(whole) + "," + twoDigits(frac)
}

func itoa(n int64) string {
	if n == 0 {
		return "0"
	}
	var b [32]byte
	i := len(b)
	for n > 0 {
		i--
		b[i] = byte('0' + n%10)
		n /= 10
	}
	return string(b[i:])
}

func twoDigits(n int64) string {
	return string([]byte{'0' + byte(n/10), '0' + byte(n%10)})
}
```

#### What happens here

`Cent` is a small scalar type; methods return **new** values instead of mutating the original (`Add` returns `Cent`, does not change the receiver). A value receiver is readable and safe for concurrent sharing of copies — there is no shared mutable state, so there is no need for synchronization when such a type passes through multiple goroutines. (Production code would use `strconv` for conversions — here the manual `itoa` is intentional, to focus on receiver mechanics without extra imports.)

### Example 6 — Nil-safe pointer receiver on a recursive structure

```go
package list

type Node struct {
	Value int
	Next  *Node
}

func (n *Node) Len() int {
	if n == nil {
		return 0
	}
	return 1 + n.Next.Len()
}

func (n *Node) Sum() int {
	if n == nil {
		return 0
	}
	return n.Value + n.Next.Sum()
}
```

```go
package main

import (
	"fmt"

	"example.com/shop/list"
)

func main() {
	var empty *list.Node
	fmt.Println(empty.Len(), empty.Sum()) // 0 0 — call on a nil receiver is safe

	l := &list.Node{Value: 1, Next: &list.Node{Value: 2, Next: &list.Node{Value: 3}}}
	fmt.Println(l.Len(), l.Sum()) // 3 6
}
```

#### What happens here

`empty` is `nil` — the zero value for `*list.Node`. Calling `Len()`/`Sum()` on it is legal because both methods first check `n == nil` before any dereferencing. This is the idiomatic way for a recursive structure (list, tree) to have an “empty” case without a special wrapper type or `if list == nil { ... } else { list.Len() }` at every call site. Detailed mechanics are in Mechanism section 7.

### Example 7 — Refactoring toward a consistent API

Before — mixed receivers, constructor returns a value:

```go
package cache

type Cache struct {
	data map[string]string
}

func New() Cache { return Cache{data: map[string]string{}} }

func (c Cache) Get(k string) string { return c.data[k] } // value receiver
func (c *Cache) Set(k, v string)    { c.data[k] = v }     // pointer receiver
func (c *Cache) Delete(k string)    { delete(c.data, k) } // pointer receiver
```

Problem: `cache.New().Set(...)` does not compile (function result is not addressable — see Mechanism section 8), while `cache.New().Get(...)` works. The same type behaves differently depending on which method you call — confusing for anyone using the package for the first time.

After — consistent, constructor returns a pointer:

```go
package cache

type Cache struct {
	data map[string]string
}

func New() *Cache { return &Cache{data: map[string]string{}} }

func (c *Cache) Get(k string) string { return c.data[k] }
func (c *Cache) Set(k, v string)     { c.data[k] = v }
func (c *Cache) Delete(k string)     { delete(c.data, k) }
```

```go
c := cache.New()
c.Set("name", "Marko")
fmt.Println(c.Get("name")) // Marko
```

#### What happens here

All methods are on `*Cache`, and `New` returns `*Cache`. There is no situation where `Get` works and `Set` does not depending on the addressability context. A consistent method set also means that `*Cache` cleanly implements any interface that requires all three methods — no mixing of value/pointer stories at the level of the type the package uses.

## Decision analysis

| Decision | Motive |
|----------|--------|
| `*T` on mutation | Changes stay visible to the caller (sections 2–3) |
| Consistent receiver style per type | Fewer surprises; constructor and methods agree (section 8) |
| Named scalar instead of bare `float64`/`int` | Type safety — prevents mixing different units/values (section 6) |
| Knowing method set rules | Interfaces work as you expect; no “works when I call directly, does not when I pass” bugs (section 5) |
| `nil` check at the start of a pointer method | Recursive structures and optional receivers without panic (section 7) |
| Constructor returns `*T` when the type has pointer methods | Constructor result is immediately addressable, without tricks at the call site (section 8) |

## Trade-offs

- Everything on a pointer receiver: simple and consistent, but a nil receiver becomes possible on every call — document whether that is intentionally allowed.
- Value receiver methods on a large struct: hidden copies in loops and when passing through multiple function layers — measurable, but rarely decisive for correctness, more for performance.
- Mixing styles: sometimes justified (`String()`/`Snapshot()` return/use a value for reading immutability), but mutating methods should always be pointer, and clearly documented why the exception is an exception.
- A named scalar adds conversions at boundaries (to/from `float64`, `int64`...) — a small syntactic cost for a large type-safety gain.

## Common mistakes

### **Wrong:**

```go
type Wallet struct{ cents int64 }

func (w Wallet) Deposit(amount int64) {
	w.cents += amount
}

var w Wallet
w.Deposit(500)
fmt.Println(w.cents) // ?
```

**Effect:** `Deposit` changes a local copy of `w`; the balance at the caller stays `0`. The code compiles and “works” with no error or panic — a bug that is hard to notice until you write a test that checks state after the call.

**Fix:**

```go
func (w *Wallet) Deposit(amount int64) {
	w.cents += amount
}

var w Wallet
w.Deposit(500)
fmt.Println(w.cents) // 500
```

### **Wrong:**

```go
type Validator interface{ Validate() error }

type Form struct{ Name string }

func (f *Form) Validate() error {
	if f.Name == "" {
		return errors.New("name is required")
	}
	return nil
}

func check(v Validator) error { return v.Validate() }

f := Form{Name: "Marko"}
check(f) // ???
```

**Effect:** `Form` (value) does not have `Validate` in its method set — only `*Form` has it. The compiler reports an error in the spirit of: `cannot use f (variable of type Form) as Validator value: Form does not implement Validator (method Validate has pointer receiver)`.

**Fix:**

```go
check(&f) // OK — *Form implements Validator
```

### **Wrong:**

```go
type Counter struct{ n int }
func (c *Counter) Inc() { c.n++ }

counters := map[string]Counter{"a": {}}
counters["a"].Inc() // ???
```

**Effect:** A map element is not addressable (the map may internally reallocate storage), so the compiler cannot implicitly do `&counters["a"]`. Error in the spirit of: `cannot call pointer method Inc on counters["a"]`.

**Fix:**

```go
// Option A — store pointers in the map:
counters := map[string]*Counter{"a": {}}
counters["a"].Inc() // OK — the pointer is already an address

// Option B — read, change, write back as a value:
c := counters2["a"]
c.Inc()
counters2["a"] = c
```

### **Wrong:**

```go
type Celsius float64
type Fahrenheit float64

var c Celsius = 100
var f Fahrenheit = c // ???
```

**Effect:** `Celsius` and `Fahrenheit` are different named types even though both have `float64` as the underlying type. Error in the spirit of: `cannot use c (variable of type Celsius) as type Fahrenheit in variable declaration`.

**Fix:**

```go
var f Fahrenheit = Fahrenheit(c) // explicit conversion
// idiomatically, via a method:
var f2 Fahrenheit = c.ToF()
```

### **Wrong:**

```go
func New() Cache { return Cache{data: map[string]string{}} }
func (c *Cache) Set(k, v string) { c.data[k] = v }

New().Set("name", "Marko") // ???
```

**Effect:** `New()` returns a value; a function call result is not addressable, so the compiler cannot take `&` to call a pointer-receiver method. Error in the spirit of: `cannot call pointer method Set on Cache`.

**Fix:**

```go
func New() *Cache { return &Cache{data: map[string]string{}} }

New().Set("name", "Marko") // OK — New() is already *Cache
```

### **Wrong:**

```go
type Tree struct {
	Value       int
	Left, Right *Tree
}

func (t *Tree) Sum() int {
	return t.Value + t.Left.Sum() + t.Right.Sum() // no check for nil
}

var empty *Tree
empty.Sum() // ???
```

**Effect:** Recursion on a `nil` receiver tries to read `t.Value` without a check — runtime panic: `runtime error: invalid memory address or nil pointer dereference`.

**Fix:**

```go
func (t *Tree) Sum() int {
	if t == nil {
		return 0
	}
	return t.Value + t.Left.Sum() + t.Right.Sum()
}
```

### **Wrong:**

```go
type MyError struct{ msg string }
func (e *MyError) Error() string { return e.msg }

func doWork() error {
	var err *MyError // nil
	return err        // we return a nil *MyError packed into an error interface
}

if doWork() != nil {
	fmt.Println("an error occurred?!") // this is printed, even though err was nil
}
```

**Effect:** An `error` interface value carries a pair `(type, value)`. Here the pair is `(*MyError, nil)` — that is **not** the same as an “empty” interface `(nil, nil)`. So `doWork() != nil` gives `true` even though the concrete pointer was `nil`. A classic Go trap, a direct consequence of interface mechanics from sections 5 and 7.

**Fix:**

```go
func doWork() error {
	var err *MyError
	if err == nil {
		return nil // explicitly return an "empty" error interface
	}
	return err
}
```

### **Wrong:**

```go
func (this *Server) Start() error      { return nil }
func (s *Server) Stop() error          { return nil }
func (server *Server) Restart() error  { return nil }
```

**Effect:** No compile error, but `go vet`/linters (e.g. receiver-naming check) report a warning; readability suffers — every method calls the receiver by a different name (`this`, `s`, `server`) for the same type, so the reader must remapping the name on every method.

**Fix:**

```go
func (s *Server) Start() error   { return nil }
func (s *Server) Stop() error    { return nil }
func (s *Server) Restart() error { return nil }
```

## Idiomatic Go

- `encoding/json` uses a pointer receiver for `UnmarshalJSON` on user types — mutation is the essential reason, same as in sections 1–3.
- `time.Time` methods are on a value receiver because `time.Time` is designed as an immutable value — every operation (`Add`, `AddDate`) returns a **new** `time.Time`, does not mutate the original. This is the same pattern as Example 5 (`money.Cent`).
- `sort.Interface` is an instructive exception: implementations like `type ByAge []Person` usually have a **value receiver** even for `Swap`, which still mutates:

```go
type ByAge []Person

func (a ByAge) Len() int           { return len(a) }
func (a ByAge) Less(i, j int) bool { return a[i].Age < a[j].Age }
func (a ByAge) Swap(i, j int)      { a[i], a[j] = a[j], a[i] } // value receiver, but mutation WORKS
```

  Why it works: `a` is a copy of the slice header, but `a[i]`/`a[j]` index the same underlying array as the original — a swap through indexing is visible to the caller because the array itself is not copied, only the header. This is exactly the nuance from Mechanism section 2 (“header mutation” vs “element mutation through the existing array”) — do not be surprised when you see a value receiver “mutate” something in the standard library.
- Short receiver names are the norm in the stdlib (`r *Reader`, `w *Writer`, `s *Scanner`) — aligned with the rule from the “Rules and syntax” section.
- Constructors in the stdlib (`bytes.NewBuffer`, `bufio.NewReader`) return a pointer precisely when the type's methods are on a pointer receiver — the same pattern as Example 7.

## Practical scenario

**Scenario A.** Package `cart` has `func (c Cart) Add(item Item)` with a value receiver. QA reports that the cart stays empty after an `Add` call in an HTTP handler. Root cause: copy (Mechanism section 2). Switching to `*Cart` and changing the `Indexer` interface to take `*Cart` fixes the bug. The team adds a rule to the code review checklist: “every mutating method must have a pointer receiver”, plus a test that directly checks that `var c Cart; var i Indexer = c` does **not** compile (a negative test at build level, not runtime).

**Scenario B.** The team introduces `type UserID int64` to prevent mixing `userID` and `orderID` (both were bare `int64`). The first version also adds `type OrderID int64`, and in one function signature writes `func Charge(id UserID, amount int64)`, but the caller mistakenly passes an `OrderID` value. The compiler refuses (Mechanism section 6 — different named types, even with the same underlying type) — a bug that would have passed unnoticed in production with bare `int64`s is caught **at compile time**. This is cited as the main argument for named scalars in the team's internal Go style guide.

8. Write a map element with a pointer-receiver method; show the compiler error, then fix by changing the map to `map[K]*V`.

## Check questions

1. **When do you choose a pointer receiver?**
   When the method mutates the receiver, when the struct is large (you avoid copying), or when consistency with other methods of the same type that already require a pointer is needed.

2. **What is the method set of `T`?**
   Methods defined with a `T` receiver — it does not include methods defined with a `*T` receiver.

3. **What is the method set of `*T`?**
   Methods defined with both a `T` and a `*T` receiver — always a superset of the method set of `T`.

4. **Why might `var x T` not implement an interface that `&x` implements?**
   If the interface requires at least one method defined on `*T`, that method is not in the method set of `T` — only `*T` satisfies it.

5. **Why does `p.Method()` work when `p` is a value and `Method` is on a pointer receiver, but `var i Interface = p` does not?**
   A direct method call allows auto-referencing (`&p`) when `p` is addressable; assignment to an interface is a static check of the method set of type `p` without that convenience.

6. **Does `m["k"].Method()` work when `Method` is on a pointer receiver?**
   No — a map element is not addressable, so the compiler cannot automatically take its address.

7. **Can you add a method directly on `float64` or `string`?**
   No; you must define your own named type (`type Celsius float64`) and put the method on it.

8. **Does a value receiver copy the struct?**
   Yes — identical to when the struct were passed as an ordinary function parameter.

9. **Can `Celsius` and `Fahrenheit` be directly assigned to each other if both have `float64` as the underlying type?**
   No — they are different named types; an explicit conversion is needed.

10. **Is a call to a pointer-receiver method on a `nil` value of type `*T` always a panic?**
    No — it is legal as long as the method body does not dereference `nil` without a prior check.

11. **Why is an interface that contains a `nil` pointer of a concrete type not equal to `nil`?**
    Because an interface value carries a pair `(type, value)`; the pair `(*T, nil)` is different from the “empty” pair `(nil, nil)`.

12. **Why does `NewCounter().Inc()` not compile when `NewCounter` returns `Counter` (value) and `Inc` is on a pointer receiver?**
    A function call result is not addressable — the compiler cannot take its address to call a pointer method.

## Table: T vs *T in interfaces and addressability

| You have a value | Methods available on it | Assignable to an interface that requires pointer methods? | Note on addressability |
|---|---|---|---|
| `T` (ordinary variable) | only `(T)` directly; `(*T)` methods can be **called** (auto-referencing) but do not count in the method set for assignment | no | addressable — method call works, interface assignment does not |
| `T` (map element) | only `(T)` — `(*T)` methods cannot even be called | no | not addressable — even a pointer method call does not work |
| `T` (function call result) | only `(T)` — `(*T)` methods cannot even be called | no | not addressable |
| `T` (slice element) | `(T)` and `(*T)` — both can be called | no (the `T` element itself, if assigned as a value, does not implement) | addressable via `&s[i]` |
| `*T` (of any origin) | `(T)` and `(*T)` — both available through dereferencing | yes | a pointer is always “its own” address |

Remember this table — it saves hours of debugging around “why does this not compile, it works somewhere else”.

## Summary

You choose a receiver consciously: mutation and method set drive the game, and addressability determines whether auto-referencing can happen at all. Named scalars give methods and type safety without inheriting the underlying type's behavior. A nil receiver is a legal and useful tool when you treat it as input that is checked, not as a guaranteed non-nil value — and an interface that carries a nil pointer of a concrete type is not a nil interface. API consistency (receiver style, constructor return type) is not a stylistic detail — it directly affects whether code even compiles in all contexts in which it is used.
