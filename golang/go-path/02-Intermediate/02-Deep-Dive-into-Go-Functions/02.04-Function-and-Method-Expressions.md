# 02.04 Function and method expressions: function values, `method value`, `method expression`, callbacks

> **Go Path - Zero to Gopher** / **02 Intermediate → Deep dive into Go Functions** / Lesson 02.04

## Lesson goals

After this lesson you can:

- use functions as first-class values (function values) in variables, parameters, and `map`s
- distinguish a **`method value`** (`p.Greet`, receiver already bound) from a **`method expression`** (`Person.Greet`/`(*Person).Greet`, receiver is an explicit first parameter)
- recognize the **concrete, additional first parameter** that a `method expression` introduces relative to a `method value`
- pass functions as a **callback** and write middleware in the `http.HandlerFunc` style
- explain a `closure` in a loop under Go 1.22+ semantics (a new variable per iteration)

## Prerequisite

- 02.01–02.03 (value semantics, `error`, receivers and `method set`)
- Basic `http.HandlerFunc` useful, but not required
- Go 1.22+ (important for loop variable semantics)

## Problem this lesson solves

Without function values as first-class values, every behavior branch goes through a `switch` on type or a string key, and Go has no inheritance as a mechanism to “swap behavior” — so code multiplies through copied loops with small differences. When a programmer first hits `T.Method` (without an instance before the dot), intuition from other languages does not help: that is not a call, that is a **function** whose receiver is an **explicit, additional first parameter** that must be listed on the call — the difference from `p.Method` (where the receiver is **already bound**, “locked” inside the function value) is not obvious until you see a concrete example with different parameter counts. The third part of the problem is older: a `closure` made inside a `for` loop historically captured the wrong (shared) variable — Go 1.22 changes that, but the programmer must know **exactly** what changed to write and read such code reliably.

## Mental model

1. A function has a type (`func(int) int`, `func(T) error`, ...) — the same value can sit in a variable, go as an argument, be returned as a result, or be a value in a `map`.
2. **`method value`** — `p.Greet` (without parentheses) is a function of type `func() string` with receiver `p` **already bound** inside that value. The call `f := p.Greet; f()` does not pass `p` anywhere explicitly — `p` is “sealed” at the moment `f` was created.
3. **`method expression`** — `Person.Greet` or `(*Person).Greet` (the **type** name, not an instance, before the dot) is a function of type `func(Person) string` or `func(*Person) string`, where the receiver is an **explicit first parameter** that the caller must list on **every** call.
4. Key, concrete difference: a `method value` has the **same number of parameters** as the original method (the receiver is already “inside”); a `method expression` has **one more parameter** — the receiver, in first place — relative to the original method.
5. A callback is a function that one function/API takes as an argument so it can call it at an agreed moment: “call me for every element”, “call me when you finish”.
6. A `closure` (a function that captures surrounding variables) inside a `for` loop: from Go 1.22, the loop variable gets a **new instance per iteration** — the closure captures *that* instance, not a shared variable from the whole loop.

### Official terminology table (this lesson)

| Official Go term | Short English gloss (first time only) | Do not use as the concept name |
|------------------|----------------------------------------|--------------------------------|
| function value | a value of function type | — |
| function literal | a function without a name written in place | “anonymous function” as a term |
| method value | a method with an already bound receiver | — |
| method expression | a method with an explicit receiver as the first parameter | — |
| closure | a function that captures surrounding variables | do not mix with resource `Close` |
| higher-order function | a function that takes/returns a function | — |

| method set | the set of methods available on a type | — |
| blank identifier | `_` | empty identifier |

Prose stays in English. Names of Go concepts stay English, with an English gloss only on first appearance.

## Mechanism

### Function value — starting point, without methods

Before you introduce `method value` and `method expression`, establish the base on an ordinary function (without a receiver):

```go
var op func(int, int) int
op = func(a, b int) int { return a + b }
fmt.Println(op(2, 3)) // 5
```

`op` is a variable of type `func(int, int) int`. The assignment `op = func(...) {...}` does not run the body — it only puts a function value into the variable. `op(2, 3)` is a call that runs the body with `a=2, b=3`. This is the same mechanism covered in detail in 01-Basics/02.08 — here it is only a reminder, because `method value` and `method expression` build directly on this concept, only with an added receiver.

### `method value` — the receiver is already bound inside the function value

```go
type Speaker struct {
	Name string
}

func (s Speaker) Hello() string {
	return "Hello, " + s.Name
}
```

```go
sp := Speaker{Name: "Mila"}
mv := sp.Hello // METHOD VALUE — without parentheses, not a call
fmt.Println(mv())        // "Hello, Mila"
```

The line `mv := sp.Hello` does **not** call `Hello`. It creates a new function value of type `func() string` — note, **zero** parameters, the same as the original method `Hello()` (which also has no parameters besides the receiver). The receiver `sp` is at that moment **copied** (because `Hello` has a value receiver) and “sealed” inside `mv` — `mv` carries its private copy of `sp`, independent of the variable `sp` in the surrounding code.

```go
sp.Name = "Ana"
fmt.Println(mv()) // STILL "Hello, Mila" — mv sealed a COPY from before the change
```

If `Hello` instead had a `pointer` receiver, `mv` would seal the **address** of `sp`, not a copy of the value — in that case a later change to `sp.Name` would be visible through `mv()`, because `mv` would read through that same address at call time, not at binding time. This is exactly the same rule as value versus pointer receiver from 02.03 — a `method value` only “freezes” the binding moment; the copy/share mechanism stays identical.

### `method expression` — the receiver becomes an explicit, additional first parameter

Now the same type, but with the **type** name before the dot, not an instance:

```go
me := Speaker.Hello // METHOD EXPRESSION
fmt.Println(me(sp)) // "Hello, Mila" — sp is passed EXPLICITLY
```

`me` is a function value of type `func(Speaker) string` — **one parameter**, of type `Speaker`, representing the receiver. The call `me(sp)` must explicitly pass `sp` — there is no “sealed” receiver, because `me` is not bound to any concrete instance. This is a concrete parameter-count difference worth pairing visually side by side:

| Expression | Value type | Parameter count on call | Receiver |
|------------|------------|-------------------------|----------|
| `sp.Hello` (`method value`) | `func() string` | **0** | already bound (copy or address of `sp`, sealed at binding time) |
| `Speaker.Hello` (`method expression`) | `func(Speaker) string` | **1** — receiver is the first parameter | not bound; the caller passes it on every call |

For a `pointer` receiver method, a `method expression` requires an address as the parameter:

```go
type Counter struct{ N int }

func (c *Counter) Inc() { c.N++ }
```

```go
var c Counter
inc := (*Counter).Inc // method expression for pointer receiver: func(*Counter)
inc(&c)                // you explicitly pass &c as the first (and only) argument
inc(&c)
fmt.Println(c.N) // 2
```

`inc` is of type `func(*Counter)` — **one** parameter, the receiver, which the caller explicitly passes as `&c`. `Inc()` itself has no parameters besides the receiver, so the `method expression` here has **exactly one** more parameter than the `method value` of that same method (which would have **zero** parameters: `mv := c.Inc` then `mv()`, with no argument).

**Predict the result:** if `Speaker` has a method `func (s Speaker) Greet(prefix string) string { return prefix + s.Name }` (thus a method **with one** parameter besides the receiver), how many parameters does the `method expression` `Speaker.Greet` have, and how many the `method value` `sp.Greet`?

**Answer:** The `method value` `sp.Greet` is of type `func(string) string` — **one** parameter (`prefix`), receiver `sp` is already bound. The `method expression` `Speaker.Greet` is of type `func(Speaker, string) string` — **two** parameters: receiver **first**, then `prefix`. The rule is general: a `method expression` always has **exactly one more parameter** than the corresponding `method value` of the same method — that additional parameter is the receiver, always in first place.

### `higher-order function` — a function that takes or returns a function

A function value, `method value`, and `method expression` are all **values** of the same general shape (`func(...) ...`), so all can be an argument or result of another function:

```go
func fold(nums []int, init int, op func(int, int) int) int {
	acc := init
	for _, n := range nums {
		acc = op(acc, n)
	}
	return acc
}
```

```go
sum := fold([]int{1, 2, 3}, 0, func(a, b int) int { return a + b })
max := fold([]int{1, 8, 3}, 0, func(a, b int) int {
	if b > a {
		return b
	}
	return a
})
```

`fold` knows nothing about sum or maximum — it gets a **strategy** as a function, and applies it the same number of times regardless of which behavior was chosen. This is a **higher-order function**: the `op` parameter is itself a function. The same pattern works identically with a `method value` instead of a function literal — if some type has a method with signature `func(int, int) int` (without the receiver in the count, the receiver is already bound), the `method value` of that method can be passed in the `op` place without changing `fold`.

### `closure` in a loop — Go 1.22+ new variable per iteration

```go
var handlers []func() string
labels := []string{"alpha", "beta", "gamma"}

for i, label := range labels {
	handlers = append(handlers, func() string {
		return fmt.Sprintf("%d:%s", i, label)
	})
}

for _, h := range handlers {
	fmt.Println(h())
}
// 0:alpha
// 1:beta
// 2:gamma
```

Every call `h()` sees **its own** value of `i` and `label` — not the last value from the whole loop. Reason: from Go 1.22, `for i, label := range labels` creates a **new** variable `i` and a **new** variable `label` **for each iteration** — a `closure` made in that iteration captures exactly those per-iteration-new variables, not one shared variable that would at the end of the loop hold the last value.

**Historical trap (before Go 1.22):** all three functions would capture **one and the same** variable `i` (and `label`), which at the end of the loop stays at its last value (`2`, `"gamma"`) — all `h()` calls would return `"2:gamma"`, regardless of which iteration the `closure` was made in. For code that must run on versions older than 1.22, the manual protection is a local copy inside the loop: `label := label` (a new, shadowed name) creates a **new** variable per iteration manually — exactly what 1.22 does automatically for the loop variable itself. This lesson and the course as a whole assume Go 1.22+, so `label := label` is not needed here, but it is still often seen in older code and tutorials — worth knowing why it is there, even when you do not write it.

### Callback API — the library controls the loop, the caller controls the body

```go
package walk

type Item struct {
	SKU string
	Qty int
}

func Each(items []Item, fn func(Item) error) error {
	for _, it := range items {
		if err := fn(it); err != nil {
			return err
		}
	}
	return nil
}
```

`Each` is a `higher-order function` that implements the callback pattern: the loop and order are inside `Each`, per-element behavior is `fn`, which the caller passes. If `fn` returns an `error`, `Each` **immediately** stops the loop and returns that error to the caller — the caller does not have to manually write `break` logic, because that decision is already built into `Each`.

```go
err := walk.Each([]walk.Item{{"MILK", 2}, {"BREAD", 1}}, func(it walk.Item) error {
	fmt.Println(it.SKU, it.Qty)
	return nil
})
```

### `http.HandlerFunc` — a named type over a function that satisfies an `interface`

```go
type HandlerFunc func(ResponseWriter, *Request)

func (f HandlerFunc) ServeHTTP(w ResponseWriter, r *Request) {
	f(w, r)
}
```

(A shortened definition from the standard library, for illustrating the mechanism.) `HandlerFunc` is a **named type** over the function type `func(ResponseWriter, *Request)` — the same pattern as `type Celsius float64` from 02.03, only the underlying type is a function instead of a scalar. `HandlerFunc` has **one** method, `ServeHTTP`, with a value receiver, which simply **calls** the function the receiver carries (`f(w, r)`). This method is why `HandlerFunc` satisfies the `interface Handler` (which requires `ServeHTTP`) — converting an ordinary function `func(w, r) {...}` into `HandlerFunc(func(w, r) {...})` “wraps” that function in a type that already has the needed method, bridging a function value and an `interface` without writing a special `struct`.

```go
func requireMethod(method string, next http.HandlerFunc) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		if r.Method != method {
			http.Error(w, "method", http.StatusMethodNotAllowed)
			return
		}
		next(w, r)
	}
}
```

`requireMethod` is middleware: it takes a `HandlerFunc`, returns a **new** `HandlerFunc` that wraps the original with an extra check. This is a `closure` (the returned function captures `method` and `next` from the outer scope of `requireMethod`) and a `higher-order function` (takes and returns a function) in the same pattern — a combination that is the basis of almost every HTTP middleware in the Go ecosystem.

### Operation registries — a `method expression` in a table that works over an arbitrary instance

The previous section showed a `method expression` on one instance (`inc(&c)`). The real benefit shows when a table needs to work over **multiple** instances of the same type, without manually binding each one separately:

```go
type Account struct {
	ID      string
	Balance int64
}

func (a *Account) Credit(amount int64) { a.Balance += amount }
func (a *Account) Debit(amount int64) error {
	if amount > a.Balance {
		return fmt.Errorf("insufficient funds")
	}
	a.Balance -= amount
	return nil
}
```

```go
type op func(*Account, int64) error

ops := map[string]op{
	"credit": func(a *Account, amt int64) error { a.Credit(amt); return nil },
	"debit":  (*Account).Debit, // method expression — directly, without a wrapper
}

acc := &Account{ID: "A1", Balance: 100}
if err := ops["debit"](acc, 30); err != nil {
	fmt.Println(err)
}
fmt.Println(acc.Balance) // 70
```

`ops["debit"]` is literally `(*Account).Debit`, whose type is `func(*Account, int64) error` — it fully matches the declared type `op`. No wrapper function literal is needed, because `Debit` already has a signature that, when the receiver is “revealed” as the first parameter, exactly matches the required shape. `ops["credit"]` **did** need a wrapper, because `Credit` does not return `error` — a `method expression` by itself does not change the signature, it only reveals the receiver; if the signatures do not match exactly, a function literal is still needed to align them. This table works for **any** `*Account` instance you pass it, because the receiver is never “sealed” inside `ops` — that is the key difference from a table of `method value`s, which would need one entry **for each concrete instance**.

### Side-by-side overview of the three forms

| Form | Example | Value type (for `func (a *Account) Debit(amt int64) error`) | Receiver on call |
|------|---------|--------------------------------------------------------------|------------------|
| Plain function value | `f := someFunc` | as `someFunc` is declared | n/a — no receiver |
| `method value` | `f := acc.Debit` | `func(int64) error` | already bound to `acc` at the moment `f` is made |
| `method expression` | `f := (*Account).Debit` | `func(*Account, int64) error` | explicit, first parameter, different for every call |

This table is worth keeping next to the code until the pattern becomes a reflex — the most common confusion is forgetting that a `method expression` has **one more parameter** than the `method value` of the same method, exactly as much as the receiver “occupies” when it stops being implicit.

## Rules and syntax

- Function types are compatible if the signatures (parameters and results, by type and order) match completely.
- `method value`: `instance.Method` — a function with the same number of parameters as the original method; the receiver is bound at the moment that value is created.
- `method expression` for a value receiver method: `Type.Method` — a function with **one more parameter** (receiver first).
- `method expression` for a pointer receiver method: `(*Type).Method` — a function whose first parameter is `*Type`.
- `http.HandlerFunc(fn)` converts `func(ResponseWriter, *Request)` into a type that implements `Handler`.
- From Go 1.22, `for i, v := range` creates a new variable `i` and `v` per iteration; older code (or code targeting pre-1.22) uses `v := v` to achieve the same manually.
- Calling a `nil` function value (including a `method value`/`method expression` variable that was never assigned) is a `panic`.

## Examples

### Example 1 — Function value as a strategy

```go
package main

import "fmt"

func fold(nums []int, init int, op func(int, int) int) int {
	acc := init
	for _, n := range nums {
		acc = op(acc, n)
	}
	return acc
}

func main() {
	sum := fold([]int{1, 2, 3}, 0, func(a, b int) int { return a + b })
	max := fold([]int{1, 8, 3}, 0, func(a, b int) int {
		if b > a {
			return b
		}
		return a
	})
	fmt.Println(sum, max) // 6 8
}
```

#### What happens here

`fold` knows nothing about addition or maximum — it gets a strategy as an `op` parameter of type `func(int, int) int`. The same loop inside `fold` is reused for both calls, only with different behavior passed as a function literal. Adding a third operation (e.g. product) does not require changing `fold`, only a new call with a new `op`.

### Example 2 — `method value`

```go
package main

import "fmt"

type Speaker struct {
	Name string
}

func (s Speaker) Hello() string {
	return "Hello, " + s.Name
}

func run(fn func() string) {
	fmt.Println(fn())
}

func main() {
	s := Speaker{Name: "Mila"}
	mv := s.Hello // method value: receiver s is already bound
	run(mv)       // "Hello, Mila"
	run(s.Hello)  // same, directly without an intermediate variable
}
```

#### What happens here

`s.Hello` is `func() string` with `s` already bound inside that value — `run` knows nothing about the `Speaker` type, it only calls the function it gets as a parameter. `mv` and the direct `s.Hello` in the second call are equivalent — both create a `method value` at the moment that expression is evaluated. Useful for callback registries where you need to pass “the behavior of this concrete instance” without manually writing a wrapper closure.

### Example 3 — `method expression` with an explicit, additional receiver parameter

```go
package main

import "fmt"

type Counter struct{ N int }

func (c *Counter) Inc() { c.N++ }

func main() {
	var c Counter
	inc := (*Counter).Inc // method expression: func(*Counter)
	inc(&c)
	inc(&c)
	fmt.Println(c.N) // 2

	// method value for comparison — zero parameters on call:
	mv := c.Inc // receiver &c already bound (Inc has a pointer receiver)
	mv()
	fmt.Println(c.N) // 3
}
```

#### What happens here

`inc := (*Counter).Inc` creates a `method expression` of type `func(*Counter)` — every call (`inc(&c)`) explicitly passes the receiver as an argument, because the receiver is not bound to any concrete instance at the moment `inc` is created. For comparison, `mv := c.Inc` creates a `method value` of type `func()` — receiver `&c` is already bound (Go automatically takes the address of `c` because `Inc` has a pointer receiver), so `mv()` takes no argument. Both end up incrementing `c.N`, but the `method expression` makes the receiver visible and explicit at the call site — useful when you build a generic table that needs to work with an **arbitrary** `*Counter` instance, not only one concrete one.

### Example 4 — Callback API with `error`

```go
package walk

type Item struct {
	SKU string
	Qty int
}

func Each(items []Item, fn func(Item) error) error {
	for _, it := range items {
		if err := fn(it); err != nil {
			return err
		}
	}
	return nil
}
```

```go
package main

import (
	"fmt"

	"example.com/shop/walk"
)

func main() {
	err := walk.Each([]walk.Item{{"MILK", 2}, {"BREAD", 1}}, func(it walk.Item) error {
		fmt.Println(it.SKU, it.Qty)
		return nil
	})
	fmt.Println(err)
}
```

#### What happens here

`Each` stops the loop on the first error `fn` returns — the caller gets that error directly as the result of `Each`, without needing to manually track “should I break the loop” state. The pattern is close to the philosophy of `filepath.WalkDir` from the standard library: the library controls order and stopping, the caller controls the body of each iteration through a function literal.

### Example 5 — `http.HandlerFunc` as a function value and middleware

```go
package main

import (
	"fmt"
	"log"
	"net/http"
)

func requireMethod(method string, next http.HandlerFunc) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		if r.Method != method {
			http.Error(w, "method", http.StatusMethodNotAllowed)
			return
		}
		next(w, r)
	}
}

func main() {
	hello := func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, "hello")
	}
	mux := http.NewServeMux()
	mux.HandleFunc("GET /hello", requireMethod(http.MethodGet, hello))
	log.Fatal(http.ListenAndServe(":8080", mux))
}
```

#### What happens here

`requireMethod` is middleware — a `higher-order function` that takes a `HandlerFunc` (`next`) and returns a **new** `HandlerFunc` that captures `method` and `next` through a `closure`. The returned function checks the HTTP request method **before** delegating to `next(w, r)` — if the check fails, `next` is never called. Go 1.22 `ServeMux` already has built-in method checking through the `"GET /hello"` syntax, so `requireMethod` here is intentionally a redundant example that illustrates composing function values, not a recommended production pattern for exactly that check.

### Example 6 — `closure` and a loop under Go 1.22+

```go
package main

import "fmt"

func main() {
	var fns []func()
	for _, s := range []string{"a", "b", "c"} {
		fns = append(fns, func() { fmt.Println(s) })
	}
	for _, fn := range fns {
		fn()
	}
	// a
	// b
	// c
}
```

#### What happens here

Each closed function prints **its own** string, because Go 1.22+ creates a new variable `s` for each loop iteration — a `closure` made in the iteration with `s == "b"` captures exactly that variable, not a shared variable from the whole loop. Before 1.22, all three functions would capture one and the same `s`, which at the end of the loop would be `"c"` — all three calls would print `"c"`. The code here does not need `s := s` (redundant protection from the older style) because the course assumes 1.22+, but recognizing that pattern in older code is still useful.

### Example 7 — Operation registry with a `method expression`, over an arbitrary instance

```go
package main

import (
	"errors"
	"fmt"
)

type Account struct {
	ID      string
	Balance int64
}

func (a *Account) Credit(amount int64) { a.Balance += amount }

func (a *Account) Debit(amount int64) error {
	if amount > a.Balance {
		return errors.New("insufficient funds")
	}
	a.Balance -= amount
	return nil
}

type op func(*Account, int64) error

func main() {
	ops := map[string]op{
		"credit": func(a *Account, amt int64) error { a.Credit(amt); return nil },
		"debit":  (*Account).Debit,
	}

	accounts := []*Account{
		{ID: "A1", Balance: 100},
		{ID: "A2", Balance: 50},
	}

	for _, acc := range accounts {
		if err := ops["debit"](acc, 30); err != nil {
			fmt.Println(acc.ID, "error:", err)
			continue
		}
		fmt.Println(acc.ID, "new balance:", acc.Balance)
	}
}
```

#### What happens here

One `ops["debit"]` entry — `(*Account).Debit`, a `method expression` — works identically for **every** instance in `accounts`, because the receiver is never bound inside the map; the loop explicitly passes it on every call (`ops["debit"](acc, 30)`). If `ops["debit"]` were a `method value` (e.g. `accounts[0].Debit`), it would work **only** for that one, first instance, regardless of which `acc` variable the loop currently carries — the `method expression` is what enables the same table entry to generically serve an arbitrary number of instances of the same type.

## Decision analysis

| Decision | Motive |
|----------|--------|
| Strategy as a function value (`fold`) | Without the weight of an `interface` for one operation |
| `method value` for a callback bound to an instance | Receiver sealed once, call without repeating the instance |
| `method expression` for generic tables/wrappers | Works with an arbitrary instance through an explicit parameter |
| `http.HandlerFunc` as an adapter | Idiomatic bridge function value → `interface` |
| Go 1.22+ per-iteration loop variables | A `closure` in a loop works intuitively, without manual protection |

## Trade-offs

- `interface` versus a `func` parameter: an `interface` is a better choice when there are multiple related methods or when a test needs a mock with its own state; `func` is better for one, isolated “hole” of behavior.
- A `method value` keeps the receiver “alive” (the garbage collector does not free the memory the receiver points to) as long as that function value is reachable — long-term storage of a `method value` over a large receiver carries an implicit cost.
- A deep chain of callbacks (a callback that calls a callback that calls a callback) becomes hard to follow — an explicit loop or a `channel`-based pattern is often more readable than nested function literals.
- A `method expression` is powerful for generic wrappers, but reads harder at first glance than a `method value` — a comment explaining “the receiver is an explicit first parameter” helps a reader who sees that pattern for the first time.

## Common mistakes

### Mixing `method value` and `method expression` signatures

**Wrong:**

```go
type Speaker struct{ Name string }
func (s Speaker) Hello() string { return "Hello, " + s.Name }

var fn func(Speaker) string = Speaker.Hello // OK
// var fn2 func(Speaker) string = sp.Hello  // does NOT compile — sp.Hello is func() string, not func(Speaker) string
```

**Effect:** Trying to assign a `method value` (which has no parameter for the receiver) to a variable of a type that **expects** the receiver as a parameter does not compile — the compiler reports a function type mismatch.

**Fix:** Use a `method expression` (`Speaker.Hello`) when you need the receiver as an explicit parameter; use a `method value` (`sp.Hello`) when the receiver is already known and you only need the remaining parameters.

### `closure` in a loop written by a pre-1.22 reflex, with unnecessary shadowing that confuses reading

**Wrong (not a bug on Go 1.22+, but confusing if you do not understand why it exists):**

```go
for _, s := range items {
	s := s // "why does this even exist" — the reader does not know this is pre-1.22 protection
	fns = append(fns, func() { use(s) })
}
```

**Effect:** Redundant shadowing on Go 1.22+ does not create a bug, but confuses a reader who does not know the history — it looks like something was intentionally “fixed” without explaining what.

**Fix:** On a codebase that targets exclusively Go 1.22+, remove `s := s` — the loop variable is already new per iteration. If the project must support an older version, add a comment `// pre-1.22 protection: new variable per iteration` so it is clear why the line exists.

### Calling a `nil` function value obtained as a `method value`/`method expression` from a `nil` `map`

**Wrong:**

```go
handlers := map[string]func(){}
h := handlers["nonexistent"] // zero value: nil
h()                          // panic: call of nil function value
```

**Effect:** Reading a nonexistent key from a `map` returns the type's `zero value` (for a function type, that is `nil`), and calling a `nil` function value is a `panic`, regardless of whether that value was a plain function value, a `method value`, or a `method expression`.

**Fix:** Check key existence before the call: `if h, ok := handlers[name]; ok { h() } else { /* handle unknown case */ }`.

### An oversized, nested anonymous callback instead of a named function

**Wrong:**

```go
walk.Each(items, func(it walk.Item) error {
	// 40 lines of logic, with its own nested if/for
	// ...
	return nil
})
```

**Effect:** A callback that grows past a dozen lines loses the readability advantage it was supposed to bring — the reader must enter an anonymous function in the middle of an `Each` call to understand what is happening, instead of seeing a name that describes intent.

**Fix:** Extract the body into a named function with a descriptive name, and pass that function as a `method value` or plain function value: `func processItem(it walk.Item) error { ... }` then `walk.Each(items, processItem)`.

### Forgetting that a `method value` with a pointer receiver sees later changes, while a value receiver does not

**Wrong (assuming they are the same):**

```go
type Config struct{ Timeout int }
func (c Config) Get() int { return c.Timeout }   // value receiver
func (c *Config) GetP() int { return c.Timeout } // pointer receiver

cfg := Config{Timeout: 5}
get := cfg.Get
getP := cfg.GetP
cfg.Timeout = 10
fmt.Println(get(), getP()) // 5 10 — NOT 5 5, and NOT 10 10
```

**Effect:** A programmer who does not distinguish value/pointer receiver in a `method value` context expects both `get()` and `getP()` to return the same value — in reality, `get` sealed a copy of `cfg` from the binding moment (`5`), while `getP` reads through the address and sees the later change (`10`).

**Fix:** When making a `method value`, explicitly think about the receiver style of the original method (02.03) — if it needs to see later changes, the receiver must be a `pointer`.

### An operation registry with a mismatched signature, without a wrapper

**Wrong:**

```go
type op func(*Account, int64) error

ops := map[string]op{
	"credit": (*Account).Credit, // does NOT compile: Credit is func(*Account, int64), without error
}
```

**Effect:** `Credit` has no `error` in the result, so `(*Account).Credit` has type `func(*Account, int64)`, not `func(*Account, int64) error` — the compiler refuses assignment into the `ops` map of type `op`, because the signatures do not match exactly.

**Fix:** Wrap in a function literal that aligns the signature: `"credit": func(a *Account, amt int64) error { a.Credit(amt); return nil }`.

## Idiomatic Go

- `http.HandlerFunc`, `fs.WalkDirFunc`, `sort.Slice`'s `less` function — all are examples of function value parameters in the standard library.
- Small `interface`s (one or two methods) are a common choice when a callback also carries its own state that needs to be tested separately; a plain `func` parameter is a common choice for a one-shot, isolated strategy.
- Test stub pattern: a `struct` with a field of type `func(...)` that the test fills with a fake implementation, plus a thin `method` that calls that field — satisfies an `interface` without a heavy mock generator.
- A `method expression` is useful when you build an operation table (`map[string]func(*T)`) that needs to work generically over a receiver, not over one fixed instance.
- Document a Go 1.22+ dependency if a `closure` in a loop **must** work by per-iteration semantics (rarely needed to write explicitly, but useful in a comment on code that targets mixed versions).

## Practical scenario

A notification service has `switch channel { case "email": sendEmail(msg); case "sms": sendSMS(msg); ... }` that grows with every new channel, and every new option requires changing the **central** `switch` function. The team switches to a registry: `map[string]func(Msg) error`, where each channel registers at program `init` via `registry["email"] = sendEmail`. When `sendEmail` becomes a method on a `*Mailer` type (because it needs access to connection configuration), registration becomes `registry["email"] = mailer.Send` — a `method value` with `mailer` already bound, with no change to the registry or the call. For testing, the team inserts `registry["test"] = func(m Msg) error { return nil }` — a plain function literal, without needing an `interface` of five methods that would otherwise have to be mocked. When a need appears for a generic “retry wrapper” that works over an **arbitrary** channel, the team uses the `method expression` `(*Mailer).Send` to make a table that takes the instance as a parameter, instead of making one `method value` for each known instance ahead of time.

## Check questions

1. **What is a `method value`?**  
   **Answer:** A function value with an already bound receiver, e.g. `sp.Hello` — the call has no parameter for the receiver, only the remaining parameters of the original method.

2. **What is a `method expression`, and how many parameters does it have relative to the corresponding `method value`?**  
   **Answer:** A function value of type `func(Receiver, ...) ...` obtained as `Type.Method` or `(*Type).Method` — it has **exactly one more parameter** than the `method value` of the same method: the receiver, in first place, which the caller explicitly passes.

3. **Why do function values help with testing?**  
   **Answer:** A dependency is easily replaced with a fake function (a function literal or a field of type `func` on a stub `struct`) without needing a large mock framework or an `interface` of many methods.

4. **How does `http.HandlerFunc` satisfy the `interface Handler` even though it is defined as a function, not a `struct`?**  
   **Answer:** `HandlerFunc` is a named type over a function type, with one method `ServeHTTP` that simply calls the function the receiver carries — converting an ordinary function into `HandlerFunc` “wraps” it in a type that already has the needed method.

5. **What does a `closure` made inside a `for` loop under Go 1.22+ capture?**  
   **Answer:** The loop variable **specific to that iteration** — Go 1.22+ creates a new variable per iteration, so each `closure` sees the value from its iteration, not the last value from the whole loop (as was the case before 1.22).

6. **Does a `method value` made over a value receiver method see a later change to the instance?**  
   **Answer:** No — a value receiver method makes a `method value` that seals a **copy** of the instance at binding time; later changes to the original variable are not visible through that `method value`. For a pointer receiver method, the `method value` reads through the address and sees later changes.

7. **What happens when calling a `nil` function value, regardless of origin (plain function, `method value`, `method expression`)?**  
   **Answer:** `panic` — calling a `nil` function value is always a `panic`, because there is no body to execute.

8. **Why can `(*Account).Credit` not go directly into `map[string]func(*Account, int64) error`, while `(*Account).Debit` can?**  
   **Answer:** A `method expression` does not change the method signature, it only reveals the receiver — `Credit` has no `error` in the result, so its `method expression` has type `func(*Account, int64)`, not `func(*Account, int64) error`; `Debit` already has a matching signature, so it goes in directly without a wrapper.

## Summary

Functions, including methods, are values that are stored, passed, and kept like any other value. A `method value` (`p.M`) seals the receiver at binding time and is called without an extra parameter; a `method expression` (`T.M`/`(*T).M`) leaves the receiver explicit, as an additional first parameter that the caller passes on every call — a difference that becomes obvious as soon as you compare the parameter counts of both forms for the same method. A `method expression` is especially useful for registries and generic wrappers that need to work over an arbitrary instance, not one fixed one, while the signature must match exactly or a wrapper is needed. Callbacks and middleware compose behavior through a `higher-order function` pattern without inheritance, and `http.HandlerFunc` is the idiomatic bridge between a plain function value and an `interface`. Go 1.22+ changes a `closure` in a loop so each iteration gets its own variable, making the intuitively expected behavior also the default.
