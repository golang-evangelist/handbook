# 02.05 Closures

> **Go Path - Zero to Gopher** / **02 Intermediate → Deep dive into Go Functions** / Lesson 02.05

## Lesson goals

After this lesson you should:

- understand what a **closure** is in Go: a function literal that captures variables from the surrounding scope
- remember that a closure captures the **variable**, not a snapshot of the value at creation time
- use Go 1.22+ loop semantics (per-iteration loop variables) correctly
- understand how `defer` in a loop works with a closure over a loop variable
- write a middleware factory as a closure and avoid classic traps with `go func()` and `err`

## Prerequisite

- lessons 02.01–02.04 (function parameters, control flow in functions, method receivers, function expressions)
- `defer` semantics (02.02)
- basic goroutine awareness (`go f()` syntax) — details in 08-Concurrent-Programming-with-Go
- Go 1.22+ (`go` directive in `go.mod`)

## Problem this lesson solves

A closure shares variables with its surroundings. Historically a `for` loop had one variable for all iterations — all `go func()` saw the last value. Go 1.22 improves the loop (a new variable per iteration), but a **closure still captures the variable**, not a copy. `defer` in a loop accumulates closures until the end of the function. Mixing these rules creates silent bugs in logging, retry loops, and middleware factories.

This lesson belongs here — in the Deep Dive into Functions module — because a closure is a fundamental property of function literals, not an error-handling topic.

## Mental model

1. **Closure** = function literal + bound (captured) variables.
2. What is captured is the **variable** (address / binding), not a frozen snapshot — unless you yourself make a new local.
3. **Go 1.22+**: `for` creates per-iteration variables; each iteration has its own binding.
4. **defer in a loop**: all defers wait for the function return (LIFO); in 1.22 each defer's closure sees **its own** iteration variable.
5. **Middleware factory** is a closure that captures config (logger, limit) and returns `http.Handler`.
6. **err in a loop**: reusing the same `err` variable + a closure can confuse — read the binding carefully.

```text
outer scope
  n := 1          ← variable lives here
  f := func() {
    return n      ← f closes over n (not the value 1, but the variable n)
  }
  n = 5
  f()             → prints 5, not 1
```

## Mechanism

### What a closure is

```go
package basic

func MakeAdder(base int) func(int) int {
	return func(x int) int {
		return base + x // closure captures base
	}
}
```

`MakeAdder(10)` returns a function literal that still "sees" `base`. That is a closure: the function literal + the binding of `base`.

### Captures the variable, not a snapshot

```go
package capture

func Demo() {
	n := 1
	f := func() int { return n }
	n = 2
	// f() == 2 — not a snapshot of 1
	_ = f
}
```

The closure did not freeze the value `1`. It bound the variable `n`. When `n` changes to `2`, calling `f()` returns `2`.

### Trace — explicit snapshot

To freeze a value, create a new local variable:

```go
package snap

func Demo() {
	n := 1
	nCopy := n
	f := func() int { return nCopy }
	n = 2
	// f() == 1 — nCopy is a separate variable
	_ = f
}
```

Or briefly in a loop (pre-1.22 style, still readable):

```go
v := v // new local per iteration
go func() { use(v) }()
```

### Go 1.22 per-iteration loop variables

Before 1.22:

```go
for _, v := range items {
	go func() { fmt.Println(v) }() // often all print the last v
}
```

From Go 1.22: each iteration has a **new** `v`. A closure created in the iteration captures that iteration's `v`.

```go
package loop22

func PrintAll(items []string) {
	for _, v := range items {
		go func() {
			println(v) // Go 1.22+: v of this iteration
		}()
	}
}
```

**Required**: `go.mod` with `go 1.22` or newer. If CI builds with an older toolchain without this semantics, behavior changes.

### Trace — go func with a parameter (always a clear contract)

```go
for _, v := range items {
	go func(v string) {
		println(v)
	}(v)
}
```

The parameter creates a new binding per call — works before and after 1.22. Good for teams with mixed versions or explicit clarity.

### defer in a loop and closure

```go
package defloop

import (
	"fmt"
	"os"
)

func Process(paths []string) error {
	for _, path := range paths {
		f, err := os.Open(path)
		if err != nil {
			return err
		}
		defer f.Close() // does NOT close per iteration — Close at end of function
		_, _ = fmt.Fscanf(f, "%s", new(string))
	}
	return nil
}
```

All `defer f.Close()` wait for the end of `Process`. In Go 1.22, `f` is per-iteration — each defer closes **its own** file (not the last). It still keeps all files open until return — for large N use an inner function:

```go
func Process2(paths []string) error {
	for _, path := range paths {
		if err := processOne(path); err != nil {
			return err
		}
	}
	return nil
}

func processOne(path string) error {
	f, err := os.Open(path)
	if err != nil {
		return err
	}
	defer f.Close() // at the end of processOne — correct per-item
	// ...
	return nil
}
```

### defer captures loop variable (1.22)

```go
package defvar

import "fmt"

func Show() {
	for i := 0; i < 3; i++ {
		defer func() { fmt.Println(i) }()
	}
}
```

In Go 1.22+ each iteration has its own `i`, so defers in LIFO order print `2`, `1`, `0` — each with **its own** value. Before 1.22 they would often all see `3` (after the loop). Document the version when you explain this example.

### Trace — err and closure

```go
package errclose

import "fmt"

func Bad() {
	var err error
	ops := []func(){func() {}, func() {}}
	for _, op := range ops {
		err = do(op)
		defer func() {
			if err != nil {
				fmt.Println("defer sees", err)
			}
		}()
	}
}

func do(func()) error { return nil }
```

Here `err` is **one** variable outside the per-iteration loop rule (`err` is not a loop var). All defers see the **same** `err` — the last state at the end of the function. Snapshot:

```go
err := err
defer func(err error) {
	if err != nil {
		fmt.Println(err)
	}
}(err)
```

### Middleware factory as a closure

```go
package mw

import (
	"log/slog"
	"net/http"
	"time"
)

func RequestLog(log *slog.Logger) func(http.Handler) http.Handler {
	return func(next http.Handler) http.Handler {
		return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			start := time.Now()
			next.ServeHTTP(w, r)
			log.Info("request",
				"method", r.Method,
				"path", r.URL.Path,
				"dur", time.Since(start),
			)
		})
	}
}
```

**What happens here:**

1. `RequestLog(log)` is a higher-order function.
2. It returns middleware that is a closure over `log`.
3. The inner handler is again a function literal — a closure over `next` and `log`.
4. No global logger; the factory closes over the dependency — easy to test and inject.

### Auth middleware factory

```go
package mw

import (
	"net/http"
)

func RequireToken(valid func(string) bool) func(http.Handler) http.Handler {
	return func(next http.Handler) http.Handler {
		return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			tok := r.Header.Get("Authorization")
			if !valid(tok) {
				http.Error(w, `{"code":"unauthorized","message":"unauthorized"}`, http.StatusUnauthorized)
				return
			}
			next.ServeHTTP(w, r)
		})
	}
}
```

`valid` is captured in the closure — it can be a function that checks a set, verifies a JWT, etc.

### Trace — goroutine + closure (errgroup pattern)

```go
package egc

import (
	"context"

	"golang.org/x/sync/errgroup"
)

func Run(ctx context.Context, ids []int, work func(context.Context, int) error) error {
	g, ctx := errgroup.WithContext(ctx)
	for _, id := range ids {
		id := id // explicit snapshot; in 1.22 redundant but clear for reviewers
		g.Go(func() error {
			return work(ctx, id) // closure captures id and ctx
		})
	}
	return g.Wait()
}
```

`ctx` is the same binding for all — intentional (cancellation propagates). `id` must be per-iteration / copied.

### Trace — once pattern as a closure

```go
package oncepat

import "sync"

func Memo[T any](fn func() (T, error)) func() (T, error) {
	var (
		once sync.Once
		v    T
		err  error
	)
	return func() (T, error) {
		once.Do(func() { v, err = fn() })
		return v, err
	}
}
```

The closure holds `once`, `v`, `err` — a classic idiomatic pattern for lazy initialization.

### Trace — memory leak via a closure

A large slice / buffer captured in a long-lived closure (e.g. a registered handler) holds memory until the closure is garbage collected:

```go
// bad long-term:
big := make([]byte, 1<<20)
h := func() { _ = big[0] } // holds 1 MiB alive as long as h lives

// better: extract what you need
first := big[0]
h2 := func() { _ = first } // holds only one byte
```

## Rules and syntax

1. Function literal:

```go
f := func(x int) int { return x + 1 }
```

2. A closure captures names from the outer block — read what is a loop var and what is not.

3. Go 1.22+: range/for vars are per-iteration; **still** copy if you want a clear snapshot or support for older tools.

4. `defer` in a loop: prefer an inner function for a resource per item.

5. For `err` outside a loop var: snapshot before defer if defer must see that iteration's error.

6. Middleware factory pattern: `func(deps) func(http.Handler) http.Handler`.

7. Do not use global mutable vars instead of a closure factory without reason.

8. Term in documentation and code comments: **closure**, not another name.

## Examples

### Example A — Predict the result

```go
package main

import "fmt"

func main() {
	n := 1
	f := func() { fmt.Println(n) }
	n = 5
	f()
}
```

**Answer:**

```
5
```

#### What happens here

The closure reads the current `n` at call time, not the value at creation time.

### Example B — Predict the result (snapshot)

```go
package main

import "fmt"

func main() {
	n := 1
	c := n
	f := func() { fmt.Println(c) }
	n = 5
	f()
}
```

**Answer:**

```
1
```

#### What happens here

`c` is a new variable; the closure captures `c`, not `n`. `n` changing to `5` does not affect `c`.

### Example C — Predict the result (parameter)

```go
package main

import "fmt"

func main() {
	n := 1
	f := func(n int) { fmt.Println(n) }
	n = 5
	f(n)
}
```

**Answer:**

```
5
```

#### What happens here

The call `f(n)` passes `5` as an argument. The inner parameter `n` shadows the outer one — the value is passed by value at call time.

### Example D — Predict the result (Go 1.22 defer loop)

```go
package main

import "fmt"

func main() {
	for i := 0; i < 3; i++ {
		defer func() { fmt.Print(i) }()
	}
}
```

**Answer (Go 1.22+):**

```
210
```

#### What happens here

LIFO defer: the closure from the last iteration (i=2) fires first, then i=1, then i=0. Each closure has its own per-iteration `i` in Go 1.22+.

### Example E — Predict the result (shared err)

```go
package main

import "fmt"

func main() {
	var err error
	for i := 0; i < 2; i++ {
		err = fmt.Errorf("%d", i)
		defer func() { fmt.Print(err, " ") }()
	}
}
```

**Answer:**

```
1 1 
```

#### What happens here

`err` is not a loop variable — both defers see the same `err` after the loop (value `"1"`). Snapshot it if you need to preserve each iteration's error.

### Example F — middleware order

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
)

func wrap(name string) func(http.Handler) http.Handler {
	return func(next http.Handler) http.Handler {
		return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			fmt.Print(name, ">")
			next.ServeHTTP(w, r)
			fmt.Print("<", name)
		})
	}
}

func main() {
	h := wrap("A")(wrap("B")(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		fmt.Print("H")
	})))
	h.ServeHTTP(httptest.NewRecorder(), httptest.NewRequest("GET", "/", nil))
}
```

**Answer:**

```
A>B>H<B<A
```

#### What happens here

Each `wrap` is a closure over `next`. Entry goes A→B→H, exit reverses: <B then <A.

### Example G — Predict the result (range 1.22)

```go
package main

import "fmt"

func main() {
	var fs []func()
	for _, v := range []int{1, 2, 3} {
		fs = append(fs, func() { fmt.Print(v) })
	}
	for _, f := range fs {
		f()
	}
}
```

**Answer (Go 1.22+):**

```
123
```

#### What happens here

Each function literal is a closure over the iteration `v`. All calls print `1`, `2`, `3` — not three times `3`.

### Example H — Predict the result (shadowing)

```go
package main

import "fmt"

func main() {
	err := fmt.Errorf("outer")
	func() {
		err := fmt.Errorf("inner")
		_ = err
	}()
	fmt.Println(err)
}
```

**Answer:**

```
outer
```

#### What happens here

`:=` inside the function literal makes a **new** `err`; the outer one stays unchanged. This is a common source of "I thought I was handling the error but the outer err never changed".

## Decision analysis

| Situation | Technique | Why |
|-----------|-----------|-----|
| `go` in a loop | parameter `(v)` or 1.22 var | clarity / version portability |
| defer + resource in a loop | inner function | Close lifespan per item |
| defer + err | snapshot / parameter | `err` is not a loop var |
| config in HTTP middleware | factory closure | dependency injection without globals |
| long-lived handler | do not capture a huge slice | prevents memory leak |
| shared computation | `Memo` with `sync.Once` | single initialization, goroutine-safe |

## Trade-offs

- Explicit `v := v` / parameters: more code, less confusion across versions.
- Inner function for defer: one more stack frame, but correct `Close` timing.
- Closure vs struct with a method: struct is often more readable for large dependencies; closure is shorter for small factories.
- Memo closure with `sync.Once`: elegant, but harder to reset in tests.
- Per-iteration vars (1.22): idiomatic but requires documenting the minimum `go` version for the team.

## Common mistakes

1. Assuming a closure makes a snapshot — it does not.
2. Building with `go 1.21` while reading a 1.22 tutorial — different loop semantics.
3. `defer Close` in a loop without an inner function — too many open files until function return.
4. Defer over a shared `err` — all defers see the last value.
5. `go func() { use(i) }` in old Go without a copy.
6. Capturing a mutable `http.Request` field after the handler returns.
7. A huge buffer in a long-lived closure — memory leak.
8. Global mutable config instead of a factory closure — data races.
9. Name shadowing (`err :=` vs `err =`) while defer reads the wrong binding.
10. Mixing method value and pointer/nil receiver without a test.

## Idiomatic Go

- Middleware: `func(cfg) func(http.Handler) http.Handler`.
- For a goroutine in a loop: `go func(id int) { ... }(id)` stays crystal clear regardless of version.
- Resource per item: extract `func() error { defer close; ... }()` as a helper.
- Name factories by role (`RequestLog`, `RequireToken`), not `MakeHandler2`.
- In comments and titles use the word **closure**.
- Test the factory with `httptest`; inject a fake `valid` function or logger.
- Prefer closures over global `var` for dependencies in handlers.

## Practical scenario

A team migrates to Go 1.22. Old code has `v := v` everywhere — it stays (explicit is fine). New code relies on per-iteration semantics. One bug remains: `var err error` + `defer log(err)` in a retry loop — all defers log the last err. Fix: `defer func(err error){...}(err)`. Second bug: middleware captures a `*slog.Logger` that changes in tests without a mutex — the factory should take the logger at server construction, not use a global. After the change, the error handler is injected as an `ErrorWriter` closure into a `WithErrors` wrapper.

### Checklist

- [ ] `go` version in `go.mod` ≥ 1.22 (to rely on per-iteration semantics)
- [ ] Loops with goroutine: review bindings explicitly
- [ ] defer in a loop: inner function or proven small N
- [ ] Middleware factories without global mutable state
- [ ] Tests for unauthorized / log path via injected dependencies

## Check questions

1. **What does a closure capture — the value or the variable?**
   The variable (binding), not a snapshot of the value at creation time.

2. **What does Go 1.22 change in a `for` loop?**
   Each iteration gets its own loop variable; closures created in that iteration see their own binding.

3. **Why does `defer f.Close()` in a loop keep files open longer than expected?**
   All defers run at the end of the enclosing function, not at the end of each iteration. Use an inner function to limit scope.

4. **Why does `var err error` + defer in a loop see the last err?**
   `err` is not a loop variable — it is a single variable declared outside the loop; all defers capture the same binding.

5. **What does a middleware factory look like as a closure?**
   `func(deps) func(http.Handler) http.Handler` — the outer function captures dependencies, the inner function captures `next`.

6. **How does the parameter `go func(v int){ ... }(v)` help?**
   It passes the current value of `v` by value as an argument, creating an independent binding in the goroutine's stack.

7. **What is a higher-order function in this context?**
   A function that takes or returns other functions — `MakeAdder`, `RequestLog`, `RequireToken` are examples.

8. **How do you isolate `Close` lifespan with an inner function?**
   Extract a helper function; `defer f.Close()` inside it runs when the helper returns, not when the outer loop function returns.

## Summary

A **closure** in Go is a function literal that captures surrounding variables by binding, not by snapshot. Go 1.22 gives per-iteration loop variables, making many `v := v` copies redundant. `defer` in a loop still waits for the end of the enclosing function; a shared `err` is not a loop var — snapshot it. A middleware factory is the idiomatic closure for HTTP: capture configuration at construction time, inject `next` at wrapping time. Understanding binding rules is the key to writing correct concurrent, error-handling, and middleware code in Go.
