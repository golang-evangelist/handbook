# 15.07 Managing projects: tidy, vendor, and verify

> **Go Path - Zero to Gopher** / **02 Intermediate → The Go CLI Playbook** / Lesson 15.07

## Lesson goals

After this lesson you should be able to:

- Run `go mod tidy` and explain what it changes in `go.mod` and `go.sum`.
- Create `vendor/` via `go mod vendor` and know when the build uses vendored copies.
- Run `go mod verify` and put it in CI as a cache integrity check.
- Distinguish the roles of `go.mod`, `go.sum`, the module cache, and the `vendor/` folder.
- Decide consciously: vendor in the repo or cache + proxy — with trade-offs.
- Connect these commands to reproducible builds, onboarding, and supply-chain expectations.
- Not mix `tidy` / `vendor` / `verify` with workspace `sync` from 15.06.

## Prerequisite

- Modules: `go.mod`, `go.sum`, basic `go get` (15.01+).
- 15.06: you know what a workspace is and why `sync` is not a substitute for `tidy`.
- Go 1.22+ recommended; you understand that lazy-loading behavior ties to the `go` directive in `go.mod`.
- A useful feel for CI (caching `GOMODCACHE`, checkout policy).

## Problem this lesson solves

`go.mod` swells with dependencies nobody imports anymore. `go.sum` is missing from the repo — CI pulls different contents or wastes time on untrusted downloads. Someone deletes `go.sum` “because it causes merge conflicts”. Another commits half a `vendor/` facade after manual deletion. A third never verifies checksums and wonders about the supply-chain story. A fourth mixes `go work sync` and `go mod tidy` until they get a random diff.

Project management in the Go world is not a Maven XML ritual. It is a **small set of commands** that keep the dependency graph honest:

- `tidy` — align requirements with the actual code.
- `vendor` — optionally materialize dependencies in the repo.
- `verify` — check that cached modules were not tampered with after download.

Along with that, `go mod download` (related hygiene) fills the cache ahead of time — useful in CI, but not a focus substitute for the three named commands.

## Mental model

| Artifact / command | Role |
|--------------------|-------|
| `go.mod` | what we require (module path, `go` version, `require`, sometimes `exclude`/`replace`) |
| `go.sum` | cryptographic fingerprints of contents we have seen |
| module cache (`GOMODCACHE`) | local copies of downloaded modules |
| `go mod tidy` | align `go.mod`/`go.sum` with imports in code |
| `go mod vendor` | copy needed packages into `vendor/` |
| `go mod verify` | check that the cached zip/content was not changed since download |

Picture: `go.mod` is the guest list. `go.sum` is the seal on the envelopes. `tidy` tidies the list according to who actually showed up. `download` brings envelopes into the cache drawer ahead of time. `verify` checks the seals on what is in the cache. `vendor` keeps photocopies in the project’s own drawer.

Important: `verify` checks the **local download cache** against expected content — it is not a substitute for dependency code review, SCA scanners, or “whether upstream is safe”.

## Mechanism

### `go mod tidy`

```powershell
go mod tidy
go mod tidy -v
go mod tidy -diff
```

What it changes (official behavior):

- Adds modules needed to build packages of the current module and their dependencies.
- Removes unused modules that do not provide relevant packages.
- Adds missing entries to `go.sum` and removes unnecessary ones.

Useful real flags:

| Flag | Effect |
|------|--------|
| `-v` | prints information about removed modules to stderr |
| `-e` | tries to continue despite errors loading packages |
| `-x` | prints commands that download executes |
| `-diff` | does not change files; prints a unified diff of needed changes; exit ≠ 0 if the diff is not empty |
| `-go=version` | updates the `go` directive; can change which dependencies stay explicit |
| `-compat=version` | preserves checksums needed by an older `go` tool; error if that version would load differently |

When to run:

- After adding or removing imports.
- After a `go get` experiment that left noise.
- In a PR: if you change dependency code, expect a tidy diff.
- In CI: `go mod tidy -diff` as a check that the repo is “tidy”.

Trace:

```text
added import example.com/lib
  → go mod tidy
  → require in go.mod + sum lines in go.sum

removed last import example.com/old
  → go mod tidy
  → old disappears from require (if not needed indirectly in a way tidy keeps)
```

Note on Go 1.17+ lazy loading: newer `go` directives retain more requirements for loading the graph. So “why is this still in go.mod” is not always “tidy did not work” — read the documentation for your `go` line.

### `go mod vendor`

```powershell
go mod vendor
go mod vendor -v
```

What it changes:

- Resets the main module’s `vendor/` directory to include all packages needed to build and test **packages of the main module**.
- Does not include test code of vendored packages.
- `-v` prints names of vendored modules/packages.
- `-e` tries to continue despite load errors.
- `-o outdir` creates vendor at another path — useful for other tools; `go` itself uses only `vendor` in the module root.

How build chooses vendor:

```powershell
go build -mod=vendor .
go test -mod=vendor ./...
```

From Go 1.14+, when `vendor/` exists and the module is the main module, `go` often automatically uses vendor mode — but in CI be explicit if that is your policy (`-mod=vendor`), so there are no surprises.

What vendor **is not**:

- Not a substitute for `go.sum`.
- Not a workspace (15.06).
- Not a guarantee that nobody will manually touch files in `vendor/` — so regenerate it with the command, not a “manual patch” without process.

Offline build trace:

```text
go mod tidy
go mod vendor
# CI / air gap:
go build -mod=vendor .
```

### `go mod verify`

```powershell
go mod verify
```

What it does:

- Checks that dependencies of the current module, stored in the local download cache, **have not been changed** since download.
- If everything is fine: prints `all modules verified.`
- If something is wrong: reports which modules and exits with non-zero status.

When to use:

- In CI after download / before build.
- After suspicion that the cache is corrupted.
- As a cheap integrity check alongside `go.sum` policy.

What verify **does not** do:

- Does not necessarily re-download everything from the network (works over the cache).
- Does not score CVEs.
- Does not fix `go.mod` — only checks.

### Related: `go mod download` (context)

```powershell
go mod download
go mod download example.com/lib@v1.2.3
```

Fills `GOMODCACHE`. Useful in CI before a step that is more restrictive with the network, or to warm the cache. Not a substitute for `tidy` / `vendor` / `verify`, but often sits in the same pipeline:

```text
go mod download
go mod verify
go test ./...
```

### Relationship to workspace `sync`

| Command | Scope |
|---------|--------|
| `go mod tidy` | one module ↔ its code |
| `go work sync` | workspace build list → modules on the desk |
| `go mod vendor` | one module → `vendor/` |
| `go mod verify` | dependency cache of the current module |

Do not substitute them for each other.

### Trace 1 — PR hygiene with `-diff`

```text
CI step:
  go mod tidy -diff
  → empty diff: OK
  → non-empty diff: FAIL + patch in the log
Developer locally:
  go mod tidy
  git add go.mod go.sum
```

### Trace 2 — Vendor regeneration after a bump

```text
go get example.com/lib@v1.4.0
go mod tidy
go mod vendor
go test -mod=vendor ./...
git add go.mod go.sum vendor
```

### Trace 3 — Verify fail

```text
go mod verify
  → module X: ...
Causes often:
  - manually touched cache
  - broken disk/cache layer
  - rarely: real content mismatch
Reaction:
  - clean/re-download the problematic module per team procedure
  - do not ignore FAIL in CI “because it works locally”
```

### Trace 4 — Cross-compile and vendor

```text
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -mod=vendor -o app .
```

Vendor does not turn off cgo rules. If a dependency pulls cgo, `CGO_ENABLED=0` can still fail. A pure Go graph + vendor + `CGO_ENABLED=0` is a common recipe for a reproducible cross-compile.

## Rules and syntax

### Minimal ritual after changing an import

```powershell
go mod tidy
go test ./...
```

### Ritual with vendor policy

```powershell
go mod tidy
go mod vendor
go test -mod=vendor ./...
```

### CI integrity ritual

```powershell
go mod download
go mod verify
go build ./...
```

### Team rules

1. Commit `go.sum`. Deleting “because of conflict” without understanding is an antipattern.
2. After resolving a conflict in `go.mod`/`go.sum`, run `tidy` (and `vendor` if you are in vendor mode).
3. Do not edit `vendor/` manually except for an urgent, documented exception — regenerate.
4. `go mod tidy -diff` in CI protects against a “forgotten tidy”.
5. `verify` is cheap; put it where you already download modules.
6. Do not mix private laptop-path `replace` into `go.mod` (see 15.06).
7. Document whether the repo uses vendor or not — half the team must not guess.
8. For pure Go cross-compile: `CGO_ENABLED=0` + known `GOOS`/`GOARCH`; vendor as needed.

### What not to invent

Use flags from `go help mod tidy`, `go help mod vendor`, `go help mod verify`. If you are unsure, `go help mod <cmd>` — not a blog post from 2018.

## Examples

### Example 1 — Tidy adds a dependency

**Predict the result:** After a new import and `tidy`, does a `require` appear in `go.mod`?

```powershell
go mod init example.com/demo
@'
package main

import (
	"fmt"

	"rsc.io/quote"
)

func main() {
	fmt.Println(quote.Hello())
}
'@ | Set-Content main.go
go mod tidy
Get-Content go.mod
```

#### What happens here

`go mod init` creates module `example.com/demo`, and the here-string writes a `main` that imports `rsc.io/quote`. `go mod tidy` adds that module to `go.mod` and writes its checksums into `go.sum`. `Get-Content go.mod` prints the file, including the new `require` line.

**Answer:** Yes. `tidy` adds the needed module and updates `go.sum`. Without `tidy`/`go get`, the build often pulls itself in newer Go, but explicit `tidy` is the hygiene you want in a PR.

### Example 2 — Tidy removes a dead dependency

**Predict the result:** If you delete the import and run `tidy`, must the old `require` disappear?

```powershell
# remove rsc.io/quote from main.go, leave only fmt
go mod tidy -v
Get-Content go.mod
```

#### What happens here

The comment removes the `rsc.io/quote` import and leaves `fmt`. `go mod tidy -v` rebuilds the requirement graph from the imports that remain and drops `rsc.io/quote` when nothing still needs it. The `-v` output lists what changed, and `Get-Content` prints the updated `go.mod`.

**Answer:** If it is no longer needed, it disappears from relevant require lines (with nuances of lazy loading / indirect requirements). `-v` helps you see what was removed. Check `go.sum` too — unnecessary entries should thin out.

### Example 3 — `tidy -diff` in CI style

**Predict the result:** If the repo is already tidy, does `-diff` change files?

```powershell
go mod tidy -diff
echo ExitCode:$LASTEXITCODE
```

#### What happens here

`go mod tidy -diff` prints the edits tidy would make and does not write `go.mod` or `go.sum`. `echo ExitCode:$LASTEXITCODE` shows 0 when that diff is empty. A non-empty diff ends with a non-zero exit code.

**Answer:** It does not change `go.mod`/`go.sum`. If there is no difference, the diff is empty and the exit code is 0. If there is a difference, you see a unified diff and a non-zero exit — ideal for a CI gate.

### Example 4 — Vendor and explicit `-mod=vendor`

**Predict the result:** Does `go mod vendor` itself change `go.mod` require lines like `tidy`?

```powershell
go mod tidy
go mod vendor
go test -mod=vendor ./...
```

#### What happens here

`go mod tidy` aligns `go.mod` and `go.sum` with the imports. `go mod vendor` copies the selected module source into `vendor/`. `go test -mod=vendor ./...` runs the tests using that directory as the module source.

**Answer:** No — `vendor` materializes packages in `vendor/` according to the current graph. Hygiene of require lines is done by `tidy`. That is why the order `tidy` then `vendor` is common and healthy.

### Example 5 — Verify happy path

**Predict the result:** What is a typical successful output?

```powershell
go mod download
go mod verify
```

#### What happens here

`go mod download` places the required modules in the local cache. `go mod verify` compares those cached files with the checksums already recorded. A clean cache prints `all modules verified.` and exits 0.

**Answer:** The message `all modules verified.` and exit 0. That means cached content matches expectation from the download / sum mechanism — not that business logic is correct.

### Example 6 — Why not to delete `go.sum`

**Predict the result:** What do you risk if you “resolve a conflict” by deleting the entire `go.sum`?

```powershell
# antipattern: Remove-Item go.sum; go mod tidy
```

#### What happens here

The comment deletes `go.sum` and then runs `go mod tidy`. Deleting the file throws away every checksum the module had recorded. The tidy that follows writes new sums for the bytes downloaded at that moment.

**Answer:** You lose the history of fingerprints the team has already seen; you open a window for different content on re-download if something odd happens in the chain. More correct: resolve the conflict carefully, then `tidy`, then review the diff. In vendor mode regenerate `vendor/` too.

### Example 7 — Cross-compile with vendor

**Predict the result:** Does `-mod=vendor` remove the need for a C compiler if a dependency uses cgo?

```powershell
$env:CGO_ENABLED = "0"
$env:GOOS = "linux"
$env:GOARCH = "amd64"
go build -mod=vendor -o demo .
Remove-Item Env:CGO_ENABLED
Remove-Item Env:GOOS
Remove-Item Env:GOARCH
```

#### What happens here

The assignments select `CGO_ENABLED=0`, `GOOS=linux`, and `GOARCH=amd64`, and `go build -mod=vendor` compiles the current package into `demo` from `vendor/`. Those `Remove-Item` lines clear the three variables in this PowerShell session. The vendor directory supplies source; with cgo disabled, a dependency that needs a C compiler still fails the build.

**Answer:** No. Vendor only chooses the source of dependency code. `CGO_ENABLED=0` refuses cgo. If the graph requires cgo, the build fails even with vendor. For a pure Go cross-compile choose dependencies and tags consciously.

### Example 8 — `-ldflags -X` with a clean module

**Predict the result:** Does `tidy` write the version from `-X` into `go.mod`?

```powershell
go build -ldflags "-X example.com/demo/internal/version.Version=1.2.3" -o demo .
```

#### What happens here

The command builds `demo` and passes `-X example.com/demo/internal/version.Version=1.2.3`, which sets that string variable inside the binary when the variable exists. The output of the command is the binary. `go.mod` is left unchanged.

**Answer:** No. `-ldflags -X` embeds the value into the binary at link time. `tidy` does not know about it and should not. Module version and the version embedded in the binary often go together in a release script, but they are different mechanisms.

## Decision analysis

**Whether to vendor?**  
Yes: air gap, strict reproducibility, slow/unreliable proxy, compliance requirement “dependency code in the repo”.  
No: small team, good proxy, you want a smaller git and faster clone; you rely on `go.sum` + cache.

**Tidy in CI as `-diff` or as “run tidy and commit”?**  
`-diff` as a gate is predictable. Auto-commit from CI is rarely a good default policy.

**Verify always?**  
In CI after download — yes, cheap. Locally after every save — pretentious; locally after cache suspicion — yes.

**`go get` vs `tidy`?**  
`go get` changes versions deliberately. `tidy` aligns with code. After manually editing imports, `tidy`. After a deliberate bump, `go get` then often `tidy`.

**Workspace sync instead of tidy?**  
No. Different scopes (15.06).

## Trade-offs

| Approach | Gain | Cost |
|---------|-------|------|
| Only `go.sum` + proxy/cache | smaller repo, simple flow | you depend on network/cache in the build |
| `vendor/` in git | offline/reproducibility | larger repo, noisier diffs |
| `tidy -diff` in CI | discipline | sometimes a “surprising” fail when someone forgets local tidy |
| Aggressive deletion of `go.sum` | temporarily fewer conflicts | loss of fingerprints, worse integrity story |
| Manual edit of `vendor/` | quick hotfix feeling | later `go mod vendor` overwrites the change |

## Common mistakes

1. Committing code without `tidy` — CI fails on `-diff`.
2. Deleting `go.sum` as a merge strategy.
3. Committing half a `vendor/` facade after manually deleting files.
4. Expecting `verify` to “scan CVEs”.
5. Mixing `go work sync` and `go mod tidy`.
6. Laptop-path `replace` in `go.mod` alongside an otherwise clean tidy ritual.
7. Cross-compile fail blamed on vendor, while the cause is cgo.
8. Believing vendor includes dependency tests (it does not).
9. `go mod vendor -o` then wondering why `go build` does not see that path.
10. Ignoring `-v` when tidy “mysteriously” removes a module you wanted to keep without an import.

## Idiomatic Go

- `go.sum` in git always for application modules.
- README: whether you use vendor or not; exact CI commands.
- After a dependency bump: `tidy` (+ `vendor` if needed) + test.
- CI: `download` → `verify` → test/build; optionally `tidy -diff`.
- Do not commit local experiments with `replace` paths.
- For release binary: separately document `-ldflags -X` and module versions.
- For a pure Go artifact: `CGO_ENABLED=0` when that is policy.
- Runtime settings (`GOGC`, `GOMEMLIMIT`, `GOMAXPROCS`) do not mix into the `go.mod` hygiene story — a different axis.

## Practical scenario

A team has a microservice with ~40 direct dependencies. Merge conflicts in `go.sum` become a panic ritual: people delete the file, run `tidy`, get a different graph than a colleague. Once `vendor/` stays partial after “manual cleanup so the PR is smaller”.

New policy:

1. Forbidden to delete the entire `go.sum` without a pair in the #platform channel.
2. CI step `go mod tidy -diff`.
3. CI step `go mod verify` after `go mod download`.
4. Vendor is not used — except one air-gapped tool in another repo, where `vendor/` is required and regenerated only by command.
5. Onboarding README shows the exact sequence for a dependency bump.

After a quarter: fewer “works on my machine” around the graph; PRs with dependencies have a predictable tidy diff; verify once catches a corrupted cache agent on a self-hosted runner.

## Summary

- `go mod tidy` aligns `go.mod`/`go.sum` with code; `-diff` is a CI friend.
- `go mod vendor` materializes dependencies in `vendor/`; explicit `-mod=vendor` reduces surprises.
- `go mod verify` checks integrity of cached modules — a cheap CI step.
- `go.sum` is committed; it is not deleted “for an easier merge”.
- Vendor, workspace, and proxy/cache are different levers.
- Cross-compile, `-ldflags`, build tags, and runtime env remain orthogonal — but often sit in the same release pipeline.

A developer wants a smaller PR. Deletes “unimportant” folders from `vendor/`. Locally `go test` passes because it sometimes pulls from cache or is not explicit `-mod=vendor`. CI with `-mod=vendor` fails. Lesson: `vendor/` is regenerated by command; it is not edited like an ordinary source tree without process.

## More detailed flow: dependency bump

```text
1. go get example.com/lib@v1.4.0
2. go mod tidy
3. (if vendor policy) go mod vendor
4. go test ./...
5. review diff of go.mod go.sum [vendor]
6. PR with a note why the bump
```

If you use a workspace (15.06), after local multi-module work consider `go work sync`, but **not instead of** step 2.

## `go` directive traps

- Raising the `go` line via `go mod tidy -go=1.22` can change which dependencies stay explicit.
- The team should raise the `go` version consciously, not “along the way in a tidy PR” that changes half the graph.
- `-compat` exists to preserve compatibility with older tools — read `go help mod tidy` before putting it in a script.

## Extended example: private module and tidy

When you pull a private module, `tidy` still does the same hygiene, but the network layer depends on `GOPRIVATE` / `GOPROXY` settings. Diagnostics:

```powershell
go env GOPRIVATE GOPROXY GOSUMDB GOMODCACHE
go mod tidy -x
```

`-x` shows what download does — useful when “tidy hangs” on an auth problem, not on Go logic.

## Extended example: why CI sees a diff and the laptop does not

```text
Laptop has an older cache + GOFLAGS
CI clean agent + different go version
go mod tidy -diff fails only on CI
```

Reaction: align the Go tool version, check the `go` directive, locally run the same tidy with a cleaner environment. Do not “fix” by turning off the CI step.

An honest graph > a smart feeling. `tidy` keeps the guest list. `sum` keeps the seals. `verify` checks the cache. `vendor` is a photocopy when you need it in the project drawer.

## Note on `go mod graph`, `why`, `edit`

`go mod` also offers `graph`, `why`, `edit`, `download`... In this lesson the focus is `tidy`, `vendor`, `verify` because those are the pillars of project hygiene. `why` is excellent when you ask “why does this dependency exist” — use it with `tidy`, not instead of it. A more detailed project inspection goes to 15.08 (`go list`, `go doc`, `go version -m`).

## Closing scenario: Friday afternoon bump

A developer raises a major HTTP library five minutes before the end. `go get` succeeds. Tests “roughly” pass locally. Forgets `tidy` (indirect lines dirty). CI `-diff` fails. A vendor-repo colleague regenerates vendor in the same PR and gets an 8k-file diff — review dies.

Better story: bump in a separate PR, `tidy` (+ `vendor`), `verify` locally, tests, short description of the breaking change, merge when there is time for rollback.

- Fewer PRs with accidental `go.mod` noise.
- Zero habit of “delete go.sum”.
- CI clearly reports an untidy state.
- Verify catches a corrupted cache at least once before it becomes a myth.
- The team knows to say “regenerate vendor” instead of “fix it manually”.

```text
Monday:    go get example.com/metrics@v0.12.0
Tuesday:   go mod tidy && go test ./...
Wednesday: CI tidy -diff green; verify green
Thursday:  security bulletin — bump to v0.12.1
Friday:    go get ...@v0.12.1; tidy; test; PR only for the bump
```

Bad flow the same week: Friday bump + feature + manual vendor edit + deleting `go.sum` because of conflict. Review lasts longer than the code itself. Module hygiene likes small PRs.

## Symptom matrix and first commands

| Symptom | First command | Common truth |
|---------|--------------|--------------|
| CI says untidy | `go mod tidy -diff` locally | forgotten tidy |
| “all modules verified” disappears | `go mod verify` | corrupted cache agent |
| Offline build asks for network | does `vendor/` + `-mod=vendor` exist? | unclear policy |
| Huge vendor diff | was `go mod vendor` after tidy? | manual cuts |
| Private module 404 | `go env GOPRIVATE GOPROXY` | auth/proxy, not tidy logic |

## Anti-pattern catalog with fix

1. **Always delete `go.sum`.** → Resolve the conflict, then `tidy`.
2. **Vendor as a manual source tree.** → Only regeneration by command.
3. **Verify turned off because “sometimes flaky”.** → Fix the agent cache; do not silence the signal.
4. **Tidy in the same PR as a large feature without need.** → Separate bump/hygiene when it is noisy.
5. **Believing vendor solves CVEs.** → Vendor is a copy; you still bump versions.

## What `go mod tidy -diff` means for culture

`-diff` turns hygiene into a measurable gate. It is not a moral lesson — it is the same principle as a format check. Teams that introduce it have fewer “incidental” `go.mod` surprises in feature PRs. Teams that lack it spend review on noise.

Suggestion: introduce `-diff` before you introduce strict SCA gates. First an honest graph, then scanning.

## Vendor and git performance

A large `vendor/` slows clone and IDE indexing. Therefore:

- vendor only where policy requires it;
- do not vendor “preventively all services”;
- consider shallow clone and sparse checkout only if you must — better to reduce the need for vendor.

If compliance requires vendor, pay the cost consciously and automate regeneration.

## Downgrade and tidy

```powershell
go get example.com/lib@v1.2.0
go mod tidy
go test ./...
```

Downgrade is not shameful — sometimes it is incident response. But tidy after a downgrade is not optional. Indirect lines and sum fingerprints must follow reality.

## How to explain `go.sum` to management (2 sentences)

“`go.mod` says which modules we want. `go.sum` records the fingerprint of the content we actually downloaded, so tomorrow we do not silently get something else.”

If they ask you to delete `go.sum` “for simplicity” — that is not simplicity, that is blindness.

## Checklist before merging a bump PR

- [ ] `go mod tidy` (locally) done
- [ ] `go test ./...` (or agreed subset) green
- [ ] `go mod verify` green
- [ ] vendor regenerated if that is policy
- [ ] no laptop `replace`
- [ ] note why the bump (CVE, feature, incident)
- [ ] CI `-diff` understood if it fails

## Closing thought before inspecting projects

The next lesson teaches how to **see** what the tool and binary actually contain (`go list`, `go doc`, `go version -m`). Hygiene without inspection is faith. Inspection without hygiene is chaos forensics. You need both.

## Additional exercise: why a module exists

```powershell
go mod why -m example.com/lib
go mod graph | Select-Object -First 40
```

`why` and `graph` are not the focus of the lesson, but they help when tidy “holds” a dependency and you do not see an import. Use them as a magnifying glass, not as a substitute for `tidy`/`verify`.

## Additional exercise: clean agent

On a clean CI machine (or a local container) run:

```text
go mod download
go mod verify
go mod tidy -diff
go test ./...
```

If only your laptop passes, the laptop is lying — cache, GOFLAGS, or manual vendor. Hygiene is measured on a clean agent.

## Five questions for dependency review

1. Is the bump intentional?
2. Is the tidy diff the only noise?
3. Does verify pass on the CI agent?
4. Is vendor (if present) regenerated as a whole?
5. Does the breaking change have a test and a rollback note?
