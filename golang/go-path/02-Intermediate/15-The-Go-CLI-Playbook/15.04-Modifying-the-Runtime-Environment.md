# 15.04 Modifying the runtime environment: GOGC, GOMEMLIMIT, GOMAXPROCS

> **Go Path - Zero to Gopher** / **02 Intermediate → The Go CLI Playbook** / Lesson 15.04

## Lesson goals

After this lesson you should:

- distinguish **runtime** variables from **build** variables (15.02)
- understand at a high level what `GOGC`, `GOMEMLIMIT`, and `GOMAXPROCS` do
- know **when** to touch these values, and when to measure and fix code first
- set runtime env in a local shell, Docker, and a systemd/Kubernetes description
- avoid “magic” tunings copied from forums without a hypothesis
- explain that runtime env changes a **running process**, not an already-linked binary on disk

## Prerequisite

- 15.01–15.03: toolchain, build env, `go build`/`run`/`install`
- basic concepts: goroutine, heap, that GC exists
- preferred: a feel for metrics (CPU, RSS) at least at Task Manager / `docker stats` level
- you know the binary is already built before runtime env “breathes”

## Problem this lesson solves

A service in a container gets a memory limit. Without tuning, the Go process can use more than the orchestrator allows — followed by an OOM kill. Someone “fixes” it by raising the limit in Kubernetes forever. Another copies `GOGC=20` from a blog and slows latency. A third turns on diagnostics in production and floods the logs.

Runtime environment is a **lever for the behavior of a process that is already running**. The wrong lever does not replace a bad algorithm, a memory leak, or a wrong pool. The lesson gives a map of levers and a discipline of measurement.

Symptoms this lesson addresses:

- OOM in small containers
- “CPU goes through the roof” after lowering GOGC
- not understanding why parallelism does not grow “by itself”
- fear of GC instead of profiling
- setting `GOOS` instead of `GOMEMLIMIT` in a Deployment (wrong layer)

## Mental model

Imagine a car that is already driving:

- **GOGC** — how aggressively you clean the trunk (GC target); lower number = more frequent cleaning, more CPU.
- **GOMEMLIMIT** — a soft boundary “do not expand recklessly above this” (soft memory limit); helps in containers.
- **GOMAXPROCS** — how many OS threads may run Go code “in parallel” in the sense of scheduler Ps.

Build env changes **what is in the engine**. Runtime env changes **how the engine breathes while driving**. Setting `GOOS` in Kubernetes env does **not** change an already-built binary. Setting `GOMEMLIMIT` does **not** change which files entered the build.

Another picture: thermostat and a contract with the building.

| Lever | Analogy | Touch when… |
|--------|-----------|------------|
| GOGC | GC thermostat | you have a measurement of GC CPU vs heap |
| GOMEMLIMIT | consumption contract | the container has a hard limit |
| GOMAXPROCS | number of workers on a shift | you share CPU with many processes / you measure |

Runtime env is read at process start (and some of it can be changed programmatically via the `runtime` package — but this lesson focuses on the **env levers** ops sets).

## Mechanism

### Boundary: build vs runtime vs app config

```text
GOOS / GOARCH / CGO / -X / tags     → build time → bytes on disk
GOGC / GOMEMLIMIT / GOMAXPROCS      → process start → runtime behavior
DATABASE_URL / APP_ENV              → your code (os.Getenv) → business config
```

Three maps. Three lessons (15.02, 15.04, 15.05). Mixing = chaos in an incident.

### GOGC — the “garbage” target

- Historically default around `100` (a ratio tied to how much garbage is tolerated before GC — see official `runtime` documentation for the exact semantics of your version).
- `GOGC=off` disables GC — dangerous except for micro experiments.
- Lower `GOGC` → more frequent GC, typically smaller heap, more CPU on GC.
- Higher `GOGC` → less frequent GC, larger heap, less CPU on GC (up to a point).

Trace of a lower GOGC:

```text
1. Start with GOGC=50
2. Allocations flow
3. GC wakes more often
4. Heap grows less aggressively (often)
5. CPU % on GC rises
6. Latency can suffer if GC is too frequent
```

Trace of a higher GOGC:

```text
1. GOGC=200
2. GC less frequent
3. Heap larger
4. Less GC CPU (often)
5. Higher risk of hitting the container memory wall without GOMEMLIMIT
```

Do not treat `GOGC` as the only memory tool. Since Go 1.19+ **`GOMEMLIMIT`** is often a better first ally in containers.

### GOMEMLIMIT — soft memory limit

- Soft limit for runtime memory.
- Values like `512MiB`, `1GiB` (syntax the runtime accepts — check version docs / `go doc runtime`).
- Goal: GC becomes more aggressive as you approach the limit, to reduce the chance of an OOM from the OS.
- Not a magic wall: allocations can still break through in pathological cases; the limit should be **below** the hard cgroup limit with headroom.

Trace in a container:

```text
1. Kubernetes memory limit = 512Mi
2. GOMEMLIMIT=450MiB (headroom below the hard limit)
3. Service allocates
4. Runtime sees approach to the soft limit
5. GC more aggressive
6. Lower chance the kernel OOMs before Go tries to restrain itself
7. If there is still a leak — still OOM; now at least you have a better signal to profile
```

Discipline recommendation: **hard limit (orchestrator) > GOMEMLIMIT > expected working memory**.

### GOMAXPROCS — scheduler Ps

- Default often the number of CPUs the runtime sees.
- In containers with CPU limits, newer Go takes cgroups into account better than long ago — so pin the version and measure.
- Manual reduction can make sense on dense multi-process nodes; increasing above logical CPUs rarely helps pure Go code.

Trace:

```text
1. GOMAXPROCS=2
2. Runtime uses up to 2 Ps for Go code
3. More goroutines still exist — but Go code execution is limited by that parallelism
4. Container CPU throttling and GOMAXPROCS must be understood together
```

`GOMAXPROCS` is not “the number of goroutines.” There can be thousands of goroutines; Ps are execution resources.

### Where it is set

PowerShell:

```powershell
$env:GOMEMLIMIT = "512MiB"
$env:GOGC = "100"
$env:GOMAXPROCS = "4"
go run .
# or .\bin\api.exe
```

Bash:

```bash
GOMEMLIMIT=512MiB GOGC=100 GOMAXPROCS=4 ./api
```

Docker:

```text
ENV GOMEMLIMIT=512MiB
# or docker run -e GOMEMLIMIT=512MiB ...
```

Kubernetes:

```text
env:
  - name: GOMEMLIMIT
    value: "512MiB"
  - name: GOMAXPROCS
    value: "2"
```

Important: env must be visible to the **binary process**, not only to the build job.

### Programmatically? (awareness only)

The `runtime` package offers things like `runtime.GOMAXPROCS`, and newer APIs cover the memory limit / GC percent — read `go doc runtime` for the version. Ops often prefers env because it does not require a rebuild. Code can log effective values at start for diagnostics.

### Measure before you touch

Without a hypothesis:

```text
1. Symptom: OOM
2. Hypothesis: heap grows to the hard limit without a soft limit
3. Action: GOMEMLIMIT below hard
4. Measurement: restart count, RSS, GC metrics
5. If it does not help: profile allocations, not an even lower GOGC blindly
```

Without measurement, `GOGC=20` is a horoscope.

### What runtime env does **not** do

- It does not fix `N+1` queries.
- It does not shrink a goroutine leak (e.g. forgotten cancel) — it only changes GC/CPU pressure.
- It does not change the artifact’s `GOOS`.
- It does not replace horizontal scaling when the work is CPU-bound beyond one process.

### Typical anti-patterns

1. `GOGC=off` in production “because faster” — until OOM.
2. `GOMEMLIMIT` **above** the hard cgroup limit — loses the point of headroom.
3. Copying `GOMAXPROCS=16` onto a 2-CPU pod.
4. Changing five env vars at once without control.
5. Mixing with app env (`DB_HOST`) in the same debate without labeling the layer.

### Relationship to `go env`

`go env` shows **toolchain** effective values (including sometimes things relevant to the build). `GOGC` / `GOMEMLIMIT` / `GOMAXPROCS` are **runtime** variables for your program. Do not expect `go env GOGC` to be your main instrument for a production service — look at the process env (Kubernetes describe, `docker inspect`, systemd, or a start log).

For toolchain diagnostics still `go env`. For runtime breathing — the env of the running `api` process.

### Start log (team idiom)

At `main` start log:

```text
GOMAXPROCS=...
GOMEMLIMIT=...
GOGC=...
go version (build-time if you have -X)
```

That shortens night incidents.

### Deeper trace: allocation → GC → soft limit

```text
1. Handler allocates []byte / structs on the heap
2. Heap grows
3. Without GOMEMLIMIT: GOGC decides when GC is “worth it”
4. With GOMEMLIMIT: as you approach the limit, GC pressure rises
5. If allocation still runs wild (cache without a bound), RSS goes toward the hard limit
6. Orchestrator sends OOMKill
7. Without a heap profile, the next step is often wrong (just raise the limit)
```

That is why the order is: metric → soft limit → profile → code fix → only then chronically raise hard.

### Deeper trace: goroutine vs P

```text
1. 10_000 goroutines in a server — normally possible
2. GOMAXPROCS=4 → up to 4 Ps execute Go code at once
3. Other goroutines wait / block on I/O
4. Lowering GOMAXPROCS does not “delete” goroutines
5. A goroutine leak still eats memory independent of GOMAXPROCS
```

If you see goroutine count growth in `/debug/pprof/goroutine`, that is not a problem `GOMAXPROCS=2` solves.

### How to read a “high CPU” symptom

Checklist:

```text
[ ] Is GC CPU high? (metrics / gctrace locally)
[ ] Is GOGC very low?
[ ] Is GOMEMLIMIT too tight so GC thrash?
[ ] Is the work really CPU-bound (JSON, crypto, compression)?
[ ] Does GOMAXPROCS not match the CPU limit?
```

Each branch leads to a different action. One blog number does not cover everything.

### How to read an “OOM” symptom

```text
[ ] How large is the hard limit?
[ ] Is GOMEMLIMIT set and below hard?
[ ] Heap profile: who allocates?
[ ] Off-heap? (cgo, native) — soft limit does not cover everything the same way
[ ] Memory leak vs large legitimate cache
```

### Local lab (without production)

```powershell
$env:GODEBUG = ""  # do not invent keys; read docs if you use it
$env:GOMEMLIMIT = "100MiB"
$env:GOGC = "100"
go run ./cmd/api
```

If you use `GODEBUG`, those are diagnostic switches — read version documentation; do not treat them as stable app config. This lesson focuses on the three main levers: GOGC, GOMEMLIMIT, GOMAXPROCS.

### Systemd example (idea)

```text
[Service]
Environment=GOMEMLIMIT=512MiB
Environment=GOMAXPROCS=2
ExecStart=/usr/local/bin/api
```

Same principle: env with the **runtime** process, not with the build.

### What to document in the runbook

```text
1. Default GOMEMLIMIT per environment (dev/stage/prod)
2. Relationship to the Kubernetes memory limit
3. When ops may touch GOGC
4. Which metric confirms a change succeeded
5. Rollback: remove env / restore the old value
```

Without a runbook, every on-call repeats the same mistakes.

### Link back to 15.02/15.03

```text
15.02 makes the correct linux artifact
15.03 puts it in an image / bin/
15.04 tunes how it breathes in the container
```

If 15.02 gets the OS wrong, 15.04 will not help. If 15.03 runs `go run` in prod, 15.04 tuning is cosmetics on a bad contract.

## Rules and syntax

1. **Layer:** runtime env ≠ build env ≠ app config.
2. **Containers:** first `GOMEMLIMIT` below the hard limit, not a blind `GOGC=off`.
3. **One change per experiment** + a metric.
4. **`GOGC=off`** lab only.
5. **`GOMAXPROCS`** do not mix with goroutine count.
6. **Go version** affects cgroup awareness — pin and measure.
7. **Document** env in Helm/compose next to the memory limit.
8. **Do not cure** a leak with tuning forever.
9. **Read** `go doc runtime` for the exact semantics of the version.
10. **Log** effective values at boot.

## Examples

### Example 1 — Local start with GOMEMLIMIT

```powershell
$env:GOMEMLIMIT = "256MiB"
.\bin\api.exe
```

### What happens here

The process starts with a soft limit. GC will be more aggressive near 256MiB. The OS hard limit still exists separately (e.g. if there is no container, machine RAM).

### Predict the result

Does this change the existing `api.exe` on disk?

**Answer:** no. It changes the behavior of **this** process instance.

---

### Example 2 — GOGC experiment (carefully)

```powershell
$env:GOGC = "50"
.\bin\api.exe
# measure CPU and latency
$env:GOGC = "200"
.\bin\api.exe
```

### Predict the result

What do you expect from `GOGC=50` versus `200` on an allocation-heavy service?

**Answer:** more frequent GC and potentially more GC CPU at 50; larger heap and less frequent GC at 200 — with measurement, not dogmatically.

---

### Example 3 — Container with hard 512Mi

```text
resources:
  limits:
    memory: "512Mi"
env:
  - name: GOMEMLIMIT
    value: "450MiB"
```

### What happens here

The soft limit leaves headroom to hard OOM. The runtime tries to restrain itself earlier.

### Predict the result

What if you set `GOMEMLIMIT=600MiB` with hard `512Mi`?

**Answer:** a soft limit above hard does not help — the kernel can kill before soft logic makes sense. Keep soft **below** hard.

---

### Example 4 — GOMAXPROCS on a shared node

```powershell
$env:GOMAXPROCS = "2"
.\bin\worker.exe
```

### Predict the result

Does the goroutine count drop to 2?

**Answer:** no. Execution parallelism (Ps) is limited, not the number of goroutines.

---

### Example 5 — Wrong layer

```text
env:
  - name: GOOS
    value: linux
  - name: GOMEMLIMIT
    value: "512MiB"
```

### Predict the result

Which line affects an already-built image?

**Answer:** `GOMEMLIMIT` (runtime). `GOOS` here does not rewrite the binary.

---

### Example 6 — GOGC=off lab

```powershell
$env:GOGC = "off"
# briefly, with a machine / container memory limit
```

### Predict the result

What is the risk?

**Answer:** memory grows without GC; OOM or swap pain. Not for production.

---

### Example 7 — One change

Incident: latency spike. Someone proposes at once `GOGC=20`, `GOMAXPROCS=16`, `GOMEMLIMIT=1GiB`.

### Predict the result

Why is that a bad experiment?

**Answer:** you do not know which lever helped (or hurt). Change one, measure, then the next.

---

### Example 8 — Bash one-liner

```bash
GOMEMLIMIT=512MiB GOMAXPROCS=4 ./api
```

### What happens here

Env applies to that process (and children it is passed to). It does not have to pollute the whole shell.

### Predict the result

Does the next `./api` without the prefix inherit those values?

**Answer:** no, if they were not exported in the shell. A one-line prefix applies to that command.

---

### Example 9 — OOM hypothesis

```text
Symptom: OOMKill
Metric: RSS grows to the limit
Action: GOMEMLIMIT=80% hard
Result A: more stable → keep + profile allocations
Result B: still OOM → leak / oversized cache; tuning is not enough
```

### Predict the result

Does success A mean you may ignore a leak forever?

**Answer:** no. Soft limit buys time; the root cause still deserves a profile.

---

### Example 10 — GOMAXPROCS and throttling

A pod has CPU limit 1.0. Someone sets `GOMAXPROCS=8`.

### Predict the result

What is the more likely outcome?

**Answer:** excessive parallelism on a tight CPU budget → more contention/throttling symptoms. Align with real CPU.

---

### Example 11 — Build-time vs run-time in the same README

```markdown
Build: CGO_ENABLED=0 GOOS=linux go build -o api
Run:   GOMEMLIMIT=512MiB ./api
```

### Predict the result

Why are they in separate lines?

**Answer:** different moments in the artifact’s life. Mixing into one “env block” confuses ops.

---

### Example 12 — Log at start (sketch)

```go
package main

import (
	"log"
	"os"
	"runtime"
)

func main() {
	log.Printf("GOMAXPROCS=%d", runtime.GOMAXPROCS(0))
	log.Printf("GOMEMLIMIT=%s GOGC=%s", os.Getenv("GOMEMLIMIT"), os.Getenv("GOGC"))
	// ...
}
```

### Predict the result

Why log `Getenv` for GOGC even when the runtime has a default?

**Answer:** so you see whether env is **set**; empty string ≠ “runtime uses 0.” (LookupEnv details in 15.05.)

---

### Example 13 — Memory decision matrix

| You observe | First action |
|-----------|-------------|
| OOM + no GOMEMLIMIT | add soft below hard |
| OOM + has GOMEMLIMIT | heap profile |
| High GC CPU + low GOGC | return GOGC toward 100, measure |
| High RSS + legitimate cache | limit the cache in code |

### Predict the result

Where in the table does “just raise hard to 8Gi forever” go?

**Answer:** nowhere as a first action. That is the last ops trade-off after understanding, not a reflex.

---

### Example 14 — Same bin, two env

```powershell
$env:GOMEMLIMIT = "128MiB"
.\api.exe
# stop
$env:GOMEMLIMIT = "512MiB"
.\api.exe
```

### Predict the result

Must you `go build` again between them?

**Answer:** no. Runtime env changes per process; the binary is the same.

---

### Example 15 — GOMAXPROCS=1 to reproduce a race?

```powershell
$env:GOMAXPROCS = "1"
go test ./...
```

### Predict the result

Does `GOMAXPROCS=1` **guarantee** absence of races?

**Answer:** no. It can change timing; for detection use `go test -race` (another topic). Do not replace the race detector with tuning.

---

### Example 16 — Compose fragment

```yaml
services:
  api:
    image: shop-api:1.4.2
    environment:
      GOMEMLIMIT: "400MiB"
      GOMAXPROCS: "2"
    mem_limit: 512m
```

### Predict the result

Why both `mem_limit` and `GOMEMLIMIT`?

**Answer:** hard (Docker) + soft (Go runtime). Soft must be below hard.

---

### Example 17 — Rollback list

After a bad tuning in prod:

```text
1. Return GOGC to previous / remove override
2. Check GOMEMLIMIT is still below hard
3. Watch p95 latency and OOM events 15–30 min
4. Only then a new hypothesis
```

### Predict the result

Why not “even lower GOGC” immediately after a bad attempt?

**Answer:** compounding without control. First rollback to known, then a new experiment.

---

### Example 18 — Two processes on the same node

```text
api:    GOMAXPROCS=2
worker: GOMAXPROCS=2
node:   4 CPU
```

### Predict the result

What do you risk if both set `GOMAXPROCS=4`?

**Answer:** too much fighting for CPU; throttling and latency. Share the budget deliberately.

---

### Example 19 — What to log, what not

Log: effective GOMAXPROCS, whether GOMEMLIMIT is set, binary version.

Do not log: guesses, the whole Environ, secrets.

### Predict the result

Is it enough to log only `os.Getenv("GOMAXPROCS")`?

**Answer:** better also `runtime.GOMAXPROCS(0)` — it shows the effective value the runtime uses, even when env is not set.

---

### Example 20 — Link to measurement

```text
Before change:  p95=40ms, RSS=300Mi, OOM=2/day
After GOMEMLIMIT: p95=55ms, RSS=280Mi, OOM=0
```

### Predict the result

Is this a success?

**Answer:** probably yes for stability (OOM→0), with awareness that latency rose a bit. The trade-off is explicit — that is the point of measurement.

## Decision analysis

| Symptom | First lever | Not first |
|---------|-------------|---------|
| OOM in a container | GOMEMLIMIT below hard | GOGC=off |
| High GC CPU | measure, maybe higher GOGC / fewer allocations | blind GOMAXPROCS |
| CPU throttling | align GOMAXPROCS / replicas | just raise GOGC |
| Goroutine leak | profile / cancel | memory tuning forever |

## Trade-offs

- **Lower GOGC** — smaller heap vs more CPU.
- **GOMEMLIMIT** — fewer OOMs vs more GC near the limit; can raise latency under pressure.
- **Lower GOMAXPROCS** — better coexistence vs lower throughput of one process.
- **Ops env tuning** — fast without rebuild vs hiding a root bug.
- **Logging runtime env** — great diagnostics vs noise if you log too much.

## Common mistakes

1. Mixing build and runtime env in Kubernetes.
2. `GOGC=off` in prod.
3. Soft limit above the hard limit.
4. Five env vars at once.
5. `GOMAXPROCS` = “number of goroutines.”
6. Tuning instead of an allocation profile.
7. Copying blog numbers without the Go version.
8. Forgetting that env must be on the **runtime** container.
9. Expecting `go env` to show the production service’s GOGC.
10. Raising the memory limit forever instead of understanding growth.

## Idiomatic Go

- Containers: hard limit + `GOMEMLIMIT` with headroom.
- Boot log: GOMAXPROCS + relevant env.
- One experiment = one lever.
- Pin Go version because of runtime/cgroup behavior.
- Profile (`pprof`) before religion about GC.

## Practical scenario

A service on a 256Mi hard limit dies at night (OOMKill). Someone raises it to 2Gi “temporarily” and forgets. A month later the node suffers.

Better flow:

1. Set `GOMEMLIMIT=200MiB` with hard 256Mi.
2. Enable memory metrics / `pprof` heap.
3. Find a cache without a bound in the process.
4. Add a cache limit in code.
5. Keep a reasonable hard + soft; not 2Gi forever.

Second case: after `GOGC=20` p95 latency rises. Returning to 100 + `GOMEMLIMIT` restores calm. Lesson: lower GOGC is not a universal win.

## Summary

`GOGC`, `GOMEMLIMIT`, and `GOMAXPROCS` are levers of a **running** Go process. In containers often first `GOMEMLIMIT` below the hard limit. `GOGC` trades CPU and heap. `GOMAXPROCS` chooses execution parallelism, not goroutine count. Measure, change one thing, do not mix with build env. Next: how **your code** reads the environment (`os.Getenv`) and how that relates to `go env`.
