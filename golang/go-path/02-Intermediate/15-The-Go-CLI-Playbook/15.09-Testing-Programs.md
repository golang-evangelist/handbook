# 15.09 Testing programs: go test, race, cover, shuffle

> **Go Path - Zero to Gopher** / **02 Intermediate → The Go CLI Playbook** / Lesson 15.09

## Lesson goals

After this lesson you should be able to:

- Run `go test` over packages (`.` / `./...`) and understand local directory mode vs package list mode.
- Use real flags: `-race`, `-cover`, `-shuffle`, `-timeout`, `-count` (and related ones like `-coverprofile`, `-covermode` where they naturally go with cover).
- Explain what the race detector requires from the environment and why it is not “free”.
- Read coverage output and not idolize the percentage.
- Use `-shuffle` and `-count` to hunt order-dependent tests and flaky behavior.
- Set `-timeout` consciously instead of waiting for the default 10m in a loop.
- Connect the test flow with `go env`, build tags, `CGO_ENABLED`, and (where needed) runtime `GOMAXPROCS`.

## Prerequisite

- 15.01–15.08: modules, build, env, workspace, module hygiene, inspection (`go list` helps when a test “does not see” a file).
- You know what `*_test.go` is and basic `TestXxx(t *testing.T)`.
- Go 1.22+ recommended; the race detector requires a supported platform/architecture.
- A useful feel for CI (test cache, OS matrix).

## Problem this lesson solves

The team “has tests”, but:

- a flaky test passes locally, fails on CI because of order;
- a data race lives for months because nobody turns on `-race`;
- coverage is 92% and production burns on an uncovered error path;
- someone runs `go test` without packages in a weird directory and thinks “everything is green” because of cache;
- a 10-minute timeout hides a deadlock until the end of the shift;
- nobody knows `-count=1`, so they “fix” the cache by deleting half the disk.

`go test` is the central tool. Flags are not decorations — they change what is compiled, how it executes, what is measured, and whether the result may be cached.

## Mental model

`go test` = **compilation of a test binary + (optionally) vet + execution + report**.

Two modes (from official help):

1. **Local directory mode** — `go test` without package arguments: builds and tests the package in the current directory; caching of successful results is disabled.
2. **Package list mode** — `go test ./...` or explicit paths: tests the listed packages; successful results may be `(cached)` when flags allow cache.

Flags this lesson must teach:

| Flag | Mental role |
|------|----------------|
| `-race` | looks for data race conditions during execution |
| `-cover` | enable coverage analysis |
| `-shuffle` | randomize order of tests/benchmarks |
| `-timeout` | kill the test binary after a duration |
| `-count` | repeat each test/benchmark N times (also affects cache) |

Picture: ordinary `go test` is a check drive. `-race` puts sensors on every lane change. `-cover` paints which streets you passed. `-shuffle` changes the order of intersections. `-timeout` is a clock that does not allow you to stand forever. `-count` says “drive the route N times before you say it is stable”.

## Mechanism

### Basic invocations

```powershell
go test
go test .
go test ./...
go test ./internal/auth
go test -v ./...
```

What happens:

- `*_test.go` files are collected with the package.
- Files that start with `_` or `.` are ignored.
- `testdata/` is not treated as a Go package for build.
- A package with suffix `_test` (external test package) is compiled separately and linked with the test binary.
- By default a limited set of `go vet` checks also runs; problems can prevent the test from starting.

### `-race`

```powershell
go test -race ./...
```

What it changes:

- Builds with race detector instrumentation.
- During execution reports data races (concurrent access without synchronization).
- Slower build and runtime; higher memory use.
- Requires a supported platform (e.g. typically amd64/arm64 on major OSes — check your Go version/docs if you doubt).

Not a substitute for good abstractions (`mutex`, channel, `atomic`). It finds **data races**, not all logical concurrency bugs.

With cover, the default `-covermode` becomes `atomic` when race is on.

### `-cover` and profiles

```powershell
go test -cover ./...
go test -coverprofile=cover.out ./...
go tool cover -func=cover.out
go tool cover -html=cover.out
```

What it changes:

- `-cover` enables coverage analysis.
- Source annotation changes compilation; line numbers in some fail messages can look “shifted”.
- `-coverprofile` writes a profile and enables cover.
- `-covermode set|count|atomic`:
  - `set` — whether a statement was executed;
  - `count` — how many times;
  - `atomic` — count safe for multithreaded tests (more expensive); default with `-race`.
- `-coverpkg` expands which packages you measure during the test.

Policy: coverage is a signal, not a goal by itself. 100% with meaningless tests < 70% with good tables on error boundaries.

### `-shuffle`

```powershell
go test -shuffle=on ./...
go test -shuffle=12345 ./...
go test -shuffle=off ./...
```

What it changes:

- Randomizes the execution order of tests and benchmarks.
- `on` — seed from the system clock; the seed is reported for reproduction.
- Integer N — uses N as seed.
- `off` — default behavior (disabled).

When a test “sometimes fails”, first suspect order dependence or shared state — `-shuffle` and `-count` are friends.

### `-timeout`

```powershell
go test -timeout 30s ./...
go test -timeout 0 ./...
```

What it changes:

- If the test binary runs longer than `d`, a panic (timeout) occurs.
- `0` disables the timeout.
- Default is **10m**.

Use a shorter timeout in CI for unit packages so a deadlock does not consume the agent. For slow integration tests — a separate job with a larger timeout, not a universal 10m for everything.

### `-count`

```powershell
go test -count=1 ./...
go test -count=10 ./...
go test -race -count=5 ./...
```

What it changes:

- Runs each test/benchmark/fuzz seed N times (default 1).
- If `-cpu` is set, N times for each GOMAXPROCS value.
- Examples always run once; `-count` does not apply to fuzz tests matched with `-fuzz`.
- **`-count=1` is the classic way to avoid a cached “ok (cached)”** when you want a real re-run in package list mode.

### Result caching

In package list mode, a successful result may be cached. Cacheable flags are a limited set (including e.g. `-timeout`, `-coverprofile`; `-count` is not a path to “always cache” — actually `-count=1` forces re-execution). When you see `(cached)` and expect a new run: `go test -count=1 ./...`.

### Build tags and tests

```powershell
go test -tags=integration ./...
```

Integration files with `//go:build integration` do not enter until you give the tag. `go list` (15.08) confirms which files are selected.

### CGO and test

```powershell
$env:CGO_ENABLED = "0"
go test ./...
Remove-Item Env:CGO_ENABLED
```

If a package requires cgo, the test fails the same as the build. Race on some setups has its own requirements — do not mix “race does not work” with “cgo disabled” without diagnostics.

### Runtime with tests

```powershell
$env:GOMAXPROCS = "1"
go test -count=10 ./...
Remove-Item Env:GOMAXPROCS
```

Lowered `GOMAXPROCS` sometimes more easily surfaces lock/order bugs; raised sometimes surfaces race. That is not a substitute for `-race`, but it is a useful experiment axis. `GOGC` and `GOMEMLIMIT` rarely go into unit tests; they make sense in stress/integration scenes.

### Trace 1 — Flaky order

```text
go test ./...           # green
go test -shuffle=on ./... # red
# read the seed from the output
go test -shuffle=<seed> ./... # reproduction
# remove shared global state / Reset in TestMain
```

### Trace 2 — Race in CI

```text
go test -race -count=1 ./...
# FAIL: DATA RACE
# stack A and stack B
# synchronize or redesign data ownership
```

### Trace 3 — Coverage as a hole map

```text
go test -coverprofile=cover.out ./...
go tool cover -func=cover.out | Sort-Object
# find 0% functions on the error path
# add a table-driven test
```

### Trace 4 — Timeout catches a deadlock

```text
go test -timeout 5s ./internal/worker
# panic: test timed out
# often: wait on a channel without close/send
```

### Trace 5 — Cache confuses

```text
go test ./...
ok  example.com/x  (cached)
# change to a test fixture that the cache rule does not see as you expect
go test -count=1 ./...
```

## Rules and syntax

### Minimal good local ritual

```powershell
go test ./...
go test -race -count=1 ./...
```

### CI ritual (illustration)

```powershell
go test -count=1 -shuffle=on -timeout 2m ./...
go test -race -count=1 -timeout 5m ./...
go test -coverprofile=cover.out -count=1 ./...
```

Not everything must be in one job. Race often goes separately because it is slower.

### Team rules

1. Default tests (`go test ./...`) must be fast; integration behind a tag.
2. Race in CI at least on a linux amd64/arm64 agent.
3. Coverage tracks trend and critical packages; do not punish people for 0.5%.
4. Flaky = bug; `-shuffle` + `-count` required in diagnostics.
5. `-timeout` explicit per job type.
6. Do not turn off vet forever because it “gets in the way” — fix the code or narrow consciously (`-vet=off` only with a reason).
7. Document the `CGO_ENABLED` expectation for the test matrix.
8. Workspace (15.06): test with the same `GOWORK` expectation as developers, or explicitly `GOWORK=off` in CI.

### Flags we do NOT invent

Use `go help test` and `go help testflag`. This lesson focuses on `-race -cover -shuffle -timeout -count`. There are also `-v`, `-run`, `-bench`, `-failfast`, `-parallel`, profiles... — use them when needed, but do not invent names.

## Examples

### Example 1 — Basic test

**Predict the result:** Does `go test` without arguments cache success as `(cached)`?

```powershell
go mod init example.com/tlab
@'
package tlab

func Add(a, b int) int { return a + b }
'@ | Set-Content tlab.go
@'
package tlab

import "testing"

func TestAdd(t *testing.T) {
	if Add(2, 3) != 5 {
		t.Fatalf("got %d", Add(2, 3))
	}
}
'@ | Set-Content tlab_test.go
go test
go test
```

#### What happens here

The script creates module `example.com/tlab`, function `Add`, and `TestAdd`, which fails if `Add(2, 3)` is not 5. Both `go test` commands omit package arguments, so they run in local directory mode. In that mode a success is not saved as `(cached)`, and the second command runs the test again.

**Answer:** In local directory mode (without package arguments) caching is disabled — do not expect `(cached)` as in `go test ./...` package list mode. Both times it really executes.

### Example 2 — Package list and `-count=1`

**Predict the result:** What does `-count=1` do when you see `(cached)`?

```powershell
go test ./...
go test ./...
go test -count=1 ./...
```

#### What happens here

`go test ./...` selects packages by pattern, so a repeated success can be printed as `(cached)` and the test binary skipped. `go test -count=1 ./...` runs each test once and disables that cache. The third command is the one that forces a fresh execution.

**Answer:** The first/second call in package list mode may show `(cached)` for success. `-count=1` forces re-execution instead of relying on cache.

### Example 3 — `-cover`

**Predict the result:** Does the output show a percentage?

```powershell
go test -cover ./...
go test -coverprofile=cover.out ./...
go tool cover -func=cover.out
```

#### What happens here

`go test -cover ./...` runs the tests and prints a coverage percentage on the `ok` line. The next command writes a coverage profile to `cover.out`. `go tool cover -func=cover.out` reads that file and prints a percentage for each function.

**Answer:** Yes — `ok` lines with a coverage percentage (when cover works), plus a profile for finer analysis. The percentage alone does not prove assertion quality.

### Example 4 — `-race` on a deliberate race

**Predict the result:** Will the race detector report a problem?

```powershell
@'
package tlab

import "testing"

func TestRace(t *testing.T) {
	var x int
	done := make(chan struct{}, 2)
	go func() { x = 1; done <- struct{}{} }()
	go func() { x = 2; done <- struct{}{} }()
	<-done
	<-done
	_ = x
}
'@ | Set-Content race_test.go
go test -race -count=1 .
```

#### What happens here

`TestRace` lets two goroutines write `x` and then reads `x` in the test goroutine, with no mutex around `x`. The channel orders each write before the final read, but it does not order the two writes against each other. `go test -race -count=1 .` rebuilds with the race detector, runs once, and reports a data race on `x`.

**Answer:** Expect a data race report (sometimes needing a “lucky” schedule; `-count` helps it surface). This is an educational antipattern — do not leave it in code.

### Example 5 — `-shuffle` reproduction

**Predict the result:** Does the seed enable the same order?

```powershell
go test -shuffle=on -count=1 ./...
# assume seed 1699999999 from the output
go test -shuffle=1699999999 -count=1 ./...
```

#### What happens here

`-shuffle=on` randomizes test order from a clock seed and prints that seed. The following command uses `-shuffle=1699999999`, so the same integer drives the order. `-count=1` on both lines runs the tests instead of accepting a cached pass.

**Answer:** Yes — the same seed reproduces the randomization. That is why the CI log must keep the seed when shuffle runs.

### Example 6 — `-timeout` on a deliberate hang

**Predict the result:** What happens after 1s?

```powershell
@'
package tlab

import "testing"

func TestHang(t *testing.T) {
	select {}
}
'@ | Set-Content hang_test.go
go test -timeout 1s -count=1 .
```

#### What happens here

`TestHang` stops forever in `select {}`. `go test -timeout 1s -count=1 .` runs it once and panics when the test binary is still alive after one second. Without `-timeout`, that limit would be the default of 10 minutes.

**Answer:** The test binary exceeds the timeout and panics due to time expiry. Without a short `-timeout`, it would wait until the default 10m.

### Example 7 — Integration tag

**Predict the result:** Does `go test ./...` run the integration test without the tag?

```powershell
@'
//go:build integration

package tlab

import "testing"

func TestIntegration(t *testing.T) { t.Log("integration") }
'@ | Set-Content integ_test.go
go test -count=1 .
go test -tags=integration -count=1 -v .
```

#### What happens here

`integ_test.go` begins with `//go:build integration`, so the first `go test` does not compile the file and does not run `TestIntegration`. The second command passes `-tags=integration`, which adds the file to the build, and `-v`, which shows the `t.Log` output. `-count=1` keeps the run off the test cache.

**Answer:** Without the tag, the file is not in the build — the test is not seen. With `-tags=integration`, it enters. Keep slow tests behind a tag.

### Example 8 — Cover + race

**Predict the result:** Which covermode do you expect with `-race`?

```powershell
go test -race -cover -count=1 .
```

#### What happens here

The command enables the race detector and coverage together and runs the tests once. With `-race`, the coverage mode is `atomic`. The binary is instrumented for both, so the run costs more than coverage alone.

**Answer:** With `-race`, the default covermode is `atomic` (per testflag documentation). Slower, but more correct counting in multithreaded tests.

## Decision analysis

**Race on every local save?**  
No — too slow. Locally when you suspect concurrency; CI regularly.

**One job for all flags?**  
Often no. Fast unit job separate from race/cover/integration.

**Shuffle always in CI?**  
Good for hunting flake; keep the seed. If the suite is not ready, first clean global state.

**Timeout globally 10m?**  
Bad for unit. Explicitly shorter; integration separate.

**Coverage gate 80%?**  
Can be a signal for critical packages; dangerous as the only KPI.

**`-count=100` on everything?**  
Diagnostics of a flaky test — yes. Default CI for all packages — expensive and rarely needed.

## Trade-offs

| Approach | Gain | Cost |
|---------|-------|------|
| Only `go test ./...` | fast | misses race/flake |
| `-race` in CI | catches data race | slower, more memory |
| `-cover` gate | pressure for tests | gaming the percentage |
| `-shuffle=on` | hunts order bugs | reproduction needs seed |
| short `-timeout` | faster fail on deadlock | false fail on a slow agent |
| `-count=1` | no false cache | slightly slower CI |

## Common mistakes

1. Trusting green `(cached)` after changing a fixture outside cache rules.
2. Never `-race` in CI.
3. Coverage idolatry.
4. Shared global state + parallel tests without `t.Parallel` discipline — or the reverse.
5. Integration tests in default `./...` without a tag — CI lasts forever.
6. Timeout 10m masks a deadlock.
7. Ignoring the seed from `-shuffle`.
8. Mixing “test does not compile because of GOOS” with “logic failed” — use `go list` (15.08).
9. Cgo off in CI and on locally — divergent suite.
10. `t.Fatal` in a goroutine without `t.Cleanup` / synch — unwanted panics and flaky.

## Idiomatic Go

- Table-driven tests for boundaries and errors.
- `t.Helper()` in assert helpers.
- `t.Parallel()` only when there is no shared mutable state.
- External `_test` package when you test the public API as a client.
- Race + short unit timeout in CI.
- Document tags for integration.
- For pure Go: `CGO_ENABLED=0` in the matrix job that expects it.
- Do not fix flake with `time.Sleep` without understanding; use synch and `-shuffle`.

## Practical scenario

A reservation service has flaky CI on `TestAllocator`. Locally always green. They add `-shuffle=on` and the fail appears in 1/5 runs. The seed reproduces: test A leaves a global clock mock, test B reads that clock. Fix: `t.Cleanup` restores the clock; they remove package-level mutable. Then they turn on `-race` and find a real bug in a map without a mutex. Coverage stays ~75%, but incident rate drops.

Policy after that:

1. PR CI: `go test -count=1 -shuffle=on -timeout 90s ./...`
2. Nightly: `go test -race -count=1 -timeout 10m ./...`
3. Weekly: cover profile artifact, without a strict global gate; gate only on `internal/billing`.

## Summary

- `go test` builds and runs tests; the mode depends on package arguments.
- `-race`, `-cover`, `-shuffle`, `-timeout`, `-count` are real flags with clear effects.
- Cache in package list mode requires conscious `-count=1` when you need a fresh run.
- Shuffle + count hunt flake; race hunts data race; timeout hunts hang; cover maps holes.
- Tags, cgo, workspace, and `GOMAXPROCS` affect what and how you test.
- Do not invent flags — `go help testflag`.

## Additional scenario: cache and generated code

A generator writes a file that a test reads. The developer sees `(cached)` green even though the generator changed the output. Ritual: in that package always `-count=1` after generate, or CI generate in the same job before the test without cache in between.

## More detailed flow: from flaky to fix

```text
1. go test -shuffle=on -count=10 ./package
2. note seed and test name
3. go test -shuffle=SEED -run TestName -count=20
4. remove global state / add synch
5. go test -race -run TestName -count=20
6. return to CI suite
```

## Parallelism traps

- `t.Parallel` + package-level map without protection.
- Shared `httptest.Server` without isolation.
- Time (`time.Now`) without injection.
- Working directory (`os.Chdir`) in parallel tests.

## Note on benchmark and fuzz

`go test` also runs benchmarks (`-bench`) and fuzz (`-fuzz`). This lesson focuses on correctness and stability with the requested flags. Benchmark deserves its own discipline (`-benchtime`, iteration count via `b.N`; `b.Loop` is Go 1.24+ when mentioned); fuzz deserves a corpus and time. Do not mix them into the same CI job without intent.

## More on vet in test

`go test` runs a subset of vet checks. If vet fails, the test binary does not start. When “the test won’t start”, read whether it is vet or compilation. `-vet=off` disables; use rarely and consciously.

## Anti-pattern catalog with fix

1. **`time.Sleep` to “stabilize”.** → Synchronization or deterministic clock.
2. **Skip a flaky test forever.** → Quarantine with a ticket or fix.
3. **Race off because slow.** → Separate job, not silence.
4. **One timeout for everything.** → Unit short, integration longer.
5. **Cover gate on generated code.** → Exclude or test the generator separately.

## How to write a table-driven test that cover likes for the right reasons

```go
func TestSplit(t *testing.T) {
	cases := []struct {
		name string
		in   string
		want int
	}{
		{name: "empty", in: "", want: 0},
		{name: "one", in: "a", want: 1},
		{name: "many", in: "a,b,c", want: 3},
	}
	for _, tc := range cases {
		t.Run(tc.name, func(t *testing.T) {
			// ...
		})
	}
}
```

Cover grows because you pass through branches. But the value is in named cases, not in the percentage.

## Parallel rules in one list

- You may `t.Parallel` when state is local.
- You may not when you touch `os.Chdir`, a global logger without isolation, a shared server without port 0.
- If you don’t know — don’t. A slower suite is cheaper than flaky.

## Cache: what a developer must remember

1. Without package arguments — no package-list cache.
2. With `./...` — cache possible.
3. `(cached)` is not an error — but not proof of a fresh run either.
4. `-count=1` is a friend.
5. Changing a fixture outside Go files? Check whether the cache rule sees it.

## Checklist before “tests are flaky, go sleep”

- [ ] Reproduction with `-count` and `-shuffle`
- [ ] Seed in the ticket
- [ ] `-race` on the same package
- [ ] Check global state / Cleanup
- [ ] Check parallelism
- [ ] Check time and network (fake clock / httptest)
- [ ] Only then consider raising the timeout — rarely the real fix

## Closing thought before shared libraries

Tests protect Go code in the Go world. The next lesson crosses the language boundary (`c-shared` / `c-archive`). There `go test` remains necessary — and becomes insufficient. Bring the habit of measurement and reproduction; FFI will charge for it if you lack it.
