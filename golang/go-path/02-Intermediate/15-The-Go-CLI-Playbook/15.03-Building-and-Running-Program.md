# 15.03 Building and running a program: build, run, install, and output paths

> **Go Path - Zero to Gopher** / **02 Intermediate → The Go CLI Playbook** / Lesson 15.03

## Lesson goals

After this lesson you should:

- distinguish **`go run`**, **`go build`**, and **`go install`** by artifact lifecycle
- control the binary **name and path** (`-o`, `GOBIN`, working directory)
- build `main` packages in a `cmd/...` structure typical for Go services
- use `go clean` deliberately; know what it deletes and what it does not
- connect the local flow to CI: reproducible commands, without hidden IDE magic
- explain what each command **changes on disk** and what it leaves untouched

## Prerequisite

- lessons 15.01–15.02: toolchain map, GOOS/GOARCH, ldflags, tags
- Go 1.22+; a module with at least one `package main`
- a basic feel for `cmd`, `internal`, `pkg` folders (even if you do not yet use them strictly)
- PowerShell or bash; you know what PATH is

## Problem this lesson solves

On a team you hear three different “truths”:

- “Run with `go run`.”
- “Build then start the exe.”
- “Do `go install` then call the command from PATH.”

All three can be correct — for **different intents**. Without a clear model people:

- do not know where the binary is after a build
- commit `main.exe` to git because they do not know how CI builds
- use `go install` and wonder why the old version still runs (PATH points at another file)
- in Docker run `go run` as “production”
- delete the wrong folder with `go clean` expecting `GOMODCACHE` to vanish

The lesson resolves confusion about **where the result lives** and **for how long**.

## Mental model

Three commands, three fates of the same source:

| Command | What it does | Where the result ends up | Typical intent |
|---------|----------|---------------------|----------------|
| `go run` | compiles + executes immediately | temporary | fast loop |
| `go build` | compiles (+ links) | working dir or `-o` | artifact for deploy/test |
| `go install` | compiles and installs | `GOBIN` or `GOPATH/bin` | tool on PATH |

Imagine a restaurant:

- `go run` — the cook cooks and serves immediately; you do not leave a plate for tomorrow.
- `go build` — cooks and packs for takeaway to an agreed place.
- `go install` — puts the dish on a permanent shelf where everyone in the house knows to look.

Another axis: **what you are building**. `go build .` in a `main` package produces a program. `go build ./...` builds every package that can be built (libraries are compiled for checking, without a mandatory “exe”). For libraries often `go test` or `go build` of a package without `main` only validates that it compiles.

Third axis: **what remains on disk after the command**.

| Command | Lasting artifact in the project? | Cache may fill? | Install into bin? |
|---------|-----------------------------|-------------------------|---------------------|
| `go run` | no (temporary) | yes | no |
| `go build` | yes (cwd or `-o`) | yes | no |
| `go install` | not necessarily in the project | yes | yes (`GOBIN`/`GOPATH/bin`) |

## Mechanism

### `go run` — compile and execute immediately

```text
go run .
go run ./cmd/api
go run . -config=dev.yaml
go run ./cmd/api -- -config=dev.yaml
```

What happens on disk:

```text
1. Toolchain compiles the main package (and dependencies)
2. Writes a temporary binary (outside your repo folder, in temp space Go chooses)
3. Runs that binary
4. Forwards arguments to the program
5. When finished, does not leave “app.exe” in your project as a product (usual behavior)
6. GOCACHE/GOMODCACHE may still gain cache entries
```

Good for:

- local tryout
- small scripts during development
- a fast “change → run” loop

Not a replacement for:

- production start in a container (slower, less control over the artifact)
- a release artifact you upload
- a long-lived daemon where you want an exact file and checksum

Trace with arguments:

```text
go run . -- -port=8080
```

Understand that arguments after the package go to your program (conventions vary by call form — check `go help run` when quoting gets stuck).

### `go build` — leave the artifact where you say

```text
go build
go build .
go build -o bin/api ./cmd/api
go build ./...
```

What it changes on disk:

```text
1. Compiles needed packages
2. For package main → links an executable file
3. Without -o: name/output by convention (often the directory name) in the current dir
4. With -o path: you choose exactly where and what it is called
5. Does not “install” into GOBIN
6. Cache fills
```

For libraries (no `main`): `go build` checks that it compiles; it does not have to leave a `.a` file you “hold in your hand” as a product — the focus is validation. For `main`, the focus is the executable artifact.

CI pattern:

```powershell
go build -o bin/api ./cmd/api
```

Always an explicit `-o` in automation — fewer surprises about the name (`api` vs `api.exe` vs module name).

Windows trace:

```text
go build -o bin/api.exe ./cmd/api
dir bin\api.exe   # exists
```

Linux target from a Windows host (from 15.02):

```text
$env:GOOS="linux"; $env:GOARCH="amd64"; $env:CGO_ENABLED="0"
go build -o bin/api ./cmd/api
# file exists, but is not for native Windows start
```

### `go install` — put it on the PATH shelf

```text
go install .
go install ./cmd/api
go install example.com/mod/cmd/api@latest
```

What it changes on disk:

```text
1. Compiles the main package
2. Copies/writes the binary into GOBIN if set
3. Otherwise into $(go env GOPATH)/bin
4. Binary name usually follows the package directory name (api, not the whole module path)
5. The project folder does not have to get a local ./api.exe
```

Check where it goes:

```powershell
go env GOBIN
go env GOPATH
# effective destination: GOBIN or GOPATH\bin
```

Trace of “old version” confusion:

```text
1. go install ./cmd/api   → writes into GOPATH/bin/api.exe
2. PATH also has another api.exe earlier
3. where.exe api          → first hit is not the one you think
4. You run “api” → old binary
```

That is why after `go install` you check `where` / `Get-Command` and the file’s modification time.

`go install pkg@version` (outside the local module) is a common way to pull a tool. For **your** module in development, more often `go install ./cmd/...` from the checkout.

### Comparative trace: same change in main.go

Suppose you change the message in `fmt.Println`.

| Step | `go run` | `go build -o app.exe` | `go install` |
|-------|----------|------------------------|--------------|
| Compilation | yes | yes | yes |
| New message immediately | yes, on run | only when you run `.\app.exe` | only when you run the installed command |
| File in the project | no | yes, `app.exe` | not necessarily |
| File in GOBIN | no | no | yes |

If after `go build` you still see the old message, you may be running a **different** binary (installed), not the one you just built.

### The `cmd/...` convention

Typical layout:

```text
module example.com/shop

cmd/
  api/
    main.go
  worker/
    main.go
internal/
  ...
```

Build:

```powershell
go build -o bin/api.exe ./cmd/api
go build -o bin/worker.exe ./cmd/worker
```

Why: multiple `main` packages in one module without collision; a clear entry boundary. `go run ./cmd/api` during development; `go build -o` in CI.

### `go clean` — what it deletes (carefully)

```text
go clean
go clean -cache
go clean -modcache
go clean -i
```

Read `go help clean` for the exact list. High level:

- default `go clean` removes files that build leaves in the package (e.g. local binaries from `go build` in some contexts)
- `-cache` clears the build cache (`GOCACHE`)
- `-modcache` clears the module cache (`GOMODCACHE`) — expensive for re-download
- `-i` removes installed archives/binaries related to the package (see help)

Trace of a bad habit:

```text
1. Build is weird
2. go clean -modcache -cache immediately
3. An hour of download
4. Same bug because the problem was GOOS / wrong dir
```

Diagnose first (15.01), then clear the cache if you have a reason.

### What **none** of the three commands change

- They do not change `go.mod` by themselves (unless you use other subcommands like `go get` / `tidy`)
- They do not change production runtime env
- They do not commit to git — you choose what goes into VCS (binaries usually **do not**)

### Docker / production

Bad pattern:

```dockerfile
CMD ["go", "run", "./cmd/api"]
```

Better pattern (idea):

```text
1. build stage: go build -o /out/api ./cmd/api
2. runtime stage: copy /out/api
3. CMD ["./api"]
```

Why: smaller image, more deterministic start, no toolchain in the final container if not needed.

### IDE Run vs CLI

The IDE often does the equivalent of `go run` or a debug build in temp. For a team contract:

```text
Document:
  go run ./cmd/api
  go build -o bin/api.exe ./cmd/api
  go test ./...
```

If only the “green button” works, onboarding suffers.

### Multiple packages: `./...`

```powershell
go build ./...
go test ./...
```

Builds/tests the tree. For a release artifact still be explicit:

```powershell
go build -o bin/api.exe ./cmd/api
```

`./...` is not a replacement for “make the production api.exe.”

### Exit codes

- success → 0
- compile / test error → != 0

CI depends on the exit code. `go run` returns the exit code of **your** program if compilation succeeds (plus toolchain errors if the build part fails).

## Rules and syntax

1. **Intent first:** loop → `run`; artifact → `build -o`; tool on PATH → `install`.
2. **CI always `-o`:** explicit output path.
3. **Do not commit binaries** without a strong reason; ignore `*.exe`, `bin/`.
4. **After install:** check `where` / the path and file time.
5. **`GOBIN`:** set if you want a clean shelf outside `GOPATH/bin`.
6. **`go clean -modcache`:** last line of defense, not a reflex.
7. **Production:** run a built binary, not `go run`.
8. **`cmd/...`:** one main per entry.
9. **Same line in README and CI.**
10. **`go help run` / `build` / `install` / `clean`** before assuming flags.

## Examples

### Example 1 — Three commands, three fates

```go
package main

import "fmt"

func main() {
	fmt.Println("v2")
}
```

```powershell
go run .
go build -o hello.exe .
.\hello.exe
go install .
# then: hello  (if GOPATH\bin is on PATH)
```

### What happens here

`run` prints immediately. `build` leaves `hello.exe` next to you. `install` puts a copy on the shelf. Three ways to see “v2.”

### Predict the result

You delete `hello.exe` from the project. Can `hello` from PATH still work?

**Answer:** yes, if `go install` earlier wrote into `GOBIN`/`GOPATH/bin` and that dir is on PATH.

---

### Example 2 — Wrong binary on PATH

```powershell
go build -o bin\api.exe .\cmd\api
# you change code
go build -o bin\api.exe .\cmd\api
api
# still the old message?
where.exe api
```

### What happens here

You ran `api` from PATH, not `bin\api.exe`. The build succeeded, but you are executing a different file.

### Predict the result

What does `.\bin\api.exe` do after a rebuild?

**Answer:** the new version — that path points at the artifact you just built.

---

### Example 3 — `go run` and disk

```powershell
go run .
Get-ChildItem *.exe
```

### Predict the result

Do you expect a new `*.exe` in the project after `go run`?

**Answer:** typically no. The temporary artifact is not a project product. (Cache elsewhere may grow.)

---

### Example 4 — Explicit `GOBIN`

```powershell
$env:GOBIN = "D:\tools\gobin"
go env GOBIN
go install ./cmd/api
Get-ChildItem $env:GOBIN
```

### What happens here

Install goes exactly to the shelf you choose. Useful when you do not want mixing with other GOPATH bin tools.

### Predict the result

If `GOBIN` is not on PATH, does `api` “just work” from another folder?

**Answer:** no, until you add that dir to PATH or call it with a full path.

---

### Example 5 — `go build ./...` vs one main

```powershell
go build ./...
go build -o bin/api.exe ./cmd/api
```

### What happens here

The first validates compilation of the tree. The second makes a concrete release artifact.

### Predict the result

Does `go build ./...` guarantee that `bin/api.exe` exists?

**Answer:** no. Without `-o` and without an agreement on the name, do not rely on it for deploy.

---

### Example 6 — Clean caution

```powershell
go env GOCACHE GOMODCACHE
# do not immediately:
# go clean -modcache
go build -o bin/api.exe ./cmd/api
go clean
```

Read `go help clean` for what was removed in your case.

### Predict the result

Must `go clean` (without flags) delete the entire `GOMODCACHE`?

**Answer:** no. There is a separate flag for that (`-modcache`). Do not mix cleaning levels.

---

### Example 7 — Docker mental model (without a full Dockerfile course)

```text
STAGE build:  go build -o /out/api ./cmd/api
STAGE final:  COPY /out/api /api
CMD ["/api"]
```

### Predict the result

Why does the final stage not run `go run`?

**Answer:** you do not need the toolchain or source in the runtime image; start is faster and more deterministic with a finished binary.

---

### Example 8 — Two main packages

```powershell
go build -o bin/api.exe ./cmd/api
go build -o bin/worker.exe ./cmd/worker
```

### Predict the result

Can `go build .` in a root with no `main` make both?

**Answer:** not as “both exes.” A root without `main` is not those two entries. Build `./cmd/...` explicitly.

---

### Example 9 — `go install` of tool versions

```powershell
go install golang.org/x/tools/cmd/goimports@latest
```

### What happens here

Pulls the module (into cache), builds, puts `goimports` on the shelf. That is not the same as `go get` in your service `go.mod` without intent — choose the command by intent (tool vs application dependency).

### Predict the result

Does this necessarily change `go.mod` of your application module?

**Answer:** for this form of `go install ...@version` the focus is installing a tool; do not treat it as a replacement for managing application dependencies (`go get` / `tidy` in the module).

---

### Example 10 — Decision table in one sentence

Situations:

1. You change a handler and watch the log — ?
2. You make a zip for a GitHub Release — ?
3. You want `staticcheck` as a command — ?

### Predict the result

Map 1/2/3 to run/build/install.

**Answer:** 1 → `go run` (or local build+start); 2 → `go build -o`; 3 → `go install` (tool).

---

### Example 11 — Cache after run/build/install

```powershell
go run .
go build -o app.exe .
go install .
```

### Predict the result

Can all three write into `GOCACHE`?

**Answer:** yes. The cache is a shared toolchain accelerator. The difference between commands is the lifecycle of the **executable** artifact, not “whether cache is allowed.”

---

### Example 12 — Ignore bin in git

```gitignore
/bin/
*.exe
```

### Predict the result

Why does CI then run `go build` at all?

**Answer:** because the artifact is created in the pipeline as a job product, not as a file from VCS.

---

### Example 13 — Order in the local loop

```powershell
go test ./...
go run ./cmd/api
# when you need an artifact for a manual deploy test:
go build -o bin/api.exe ./cmd/api
```

### What happens here

Test first (signal). Run for interaction. Build when you need a file. Do not invert the order “build then forget test.”

### Predict the result

Does `go run` run unit tests?

**Answer:** no. That is what `go test` is for. `run` runs `main`.

---

### Example 14 — What remains after a failed build

```powershell
go build -o bin/api.exe ./cmd/api
# deliberately introduce an error in the code
go build -o bin/api.exe ./cmd/api
```

### Predict the result

Must the old `bin/api.exe` vanish when the new build fails?

**Answer:** not necessarily. A failed build often does **not** replace the old file. You can run a stale binary thinking it is new. Delete or check the modification time.

---

### Example 15 — `go build` without main

```powershell
# in a library package without main
go build ./internal/store
```

### Predict the result

What is success here?

**Answer:** the package compiles without error. Do not expect a new “store.exe.” That is validation, not a release artifact.

---

### Example 16 — Compare size and time (rough feel)

```powershell
Measure-Command { go build -o bin/api.exe ./cmd/api }
Measure-Command { go run ./cmd/api }
```

### What happens here

`run` includes starting the program (which may exit immediately). Measure deliberately. Point of the exercise: feel that `run` is not “free” in a CI loop a thousand times — that is why CI prefers a `test`/`build` strategy.

### Predict the result

Why does production still not choose `go run` even if it is “fast enough” locally?

**Answer:** artifact control, image size, determinism, no need for a toolchain at runtime.

### Example 17 — Disk table (fill in yourself)

After each command write YES/NO:

| After command | `.\app.exe` in project | file in GOBIN | temporary start |
|---------------|------------------------|--------------|------------------|
| `go run .` | ? | ? | ? |
| `go build -o app.exe .` | ? | ? | ? |
| `go install .` | ? | ? | ? |

### Predict the result

Fill the row `go build -o app.exe .`.

**Answer:** YES in the project (app.exe), NOT necessarily GOBIN, NOT “only temporary” — a lasting artifact on the `-o` path.

### Example 18 — `go install` from a module vs `@version`

```powershell
# local checkout
go install ./cmd/api

# tool from the network
go install golang.org/x/tools/cmd/stringer@latest
```

### What happens here

The first builds your code from disk. The second pulls a module by version and installs the tool. Do not mix intents in the README.

### Predict the result

Does the second form require that you are in your `go.mod` directory?

**Answer:** not necessarily — that is installing the named package by version, independent of the current app module (within the usual toolchain rules).

---

### Example 19 — What cache means for “clean” CI

```powershell
go build -o bin/api.exe ./cmd/api
# second time:
go build -o bin/api.exe ./cmd/api
```

### Predict the result

Why is the second time often faster?

**Answer:** `GOCACHE` hits. That does not change that `-o` still (over)writes the target artifact when needed.

---

### Example 20 — Explicit working directory

```powershell
Set-Location D:\proj\shop
go build -o bin/api.exe ./cmd/api
```

### Predict the result

What if you run the same command from `D:\proj` without `shop`?

**Answer:** no expected `go.mod` / path — error. Working directory is part of the CLI contract.

## Decision analysis

| Intent | Choose | Do not choose |
|--------|-------|----------|
| Fast loop | `go run` | `go install` every time |
| Release / Docker | `go build -o` | `go run` in CMD |
| Personal/tooling CLI | `go install` | commit exe |
| Check the whole tree | `go build ./...` / `go test` | guessing |
| Weird old version | `where` + rebuild | blind `clean -modcache` |

## Trade-offs

- **`go run`** — loop speed vs less artifact control.
- **`go build` in cwd without `-o`** — short vs unclear name in CI.
- **`go install` everywhere** — convenient PATH vs confusion which binary lives.
- **Keeping bin in the repo** — offline convenient vs merge hell and platform mismatch.
- **Aggressive `go clean`** — “fresh” vs hours of download.

## Common mistakes

1. `go run` in a production container.
2. Committing `*.exe` because “that’s how it works for me.”
3. `go install` then running another binary from PATH.
4. Expecting `go build ./...` to make a release name.
5. Mixing `GOBIN` and the working directory.
6. `go clean -modcache` as the first debug step.
7. Build without `-o` in CI then a script looks for the wrong name.
8. One `main` in the root then later pain with a second entry.
9. Docs only “press Run.”
10. Ignoring the exit code in scripts.

## Idiomatic Go

- `cmd/service/main.go` + `go build -o bin/service`.
- `.gitignore` for `bin/` and exe.
- README: copy-paste commands that CI uses.
- Tools: `go install pkg@ver` with a pinned version in docs.
- Locally: `go run ./cmd/...`; release: `go build -o`.

## Practical scenario

Onboarding: a new member does `go install ./cmd/api`, changes code, calls `api`, does not see changes. Cause: did not reinstall, or PATH points at an older `api` from another project.

Team fix procedure:

1. `where api` / `Get-Command api`
2. `go install ./cmd/api` again **or** use `go build -o bin/api.exe` + explicit path
3. Document: “for development use `go run ./cmd/api` or `.\bin\api.exe`”

Second incident: CI uploads the wrong file name because a developer locally gets `main.exe` and the script looks for `api`. Introducing a mandatory `-o bin/api` fixes it.

## Summary

`go run` compiles and executes immediately without a lasting project artifact. `go build` leaves a binary in cwd or on the `-o` path. `go install` puts the binary on `GOBIN`/`GOPATH/bin`. Choose the command by intent; in CI be explicit with `-o`; do not mix PATH with local `bin/`. Next: the runtime environment that changes a **running** process, not a file on disk.
