# 15.06 Managing workspaces: go.work, use, and sync

> **Go Path - Zero to Gopher** / **02 Intermediate → The Go CLI Playbook** / Lesson 15.06

## Lesson goals

After this lesson you should be able to:

- Explain what a **Go workspace** is and what the `go.work` file changes in the behavior of the `go` command.
- Initialize a workspace with `go work init` and add modules with `go work use`.
- Run `go work sync` and understand what gets written back into the modules in the workspace.
- Check the active workspace via `go env GOWORK` and temporarily turn it off with `GOWORK=off`.
- Decide when a workspace replaces a local `replace` in `go.mod`, and when it does not.
- Connect the workspace to everyday commands (`go build`, `go test`, `go list -m`) without inventing flags.
- Understand the boundary: a workspace is a local DX layer; CI and release still live on `go.mod` / `go.sum`.

## Prerequisite

- Lessons 15.01–15.05: modules, `go.mod`, environment (`go env`), build and runtime variables.
- At least one local module that successfully runs `go build` / `go test`.
- Preferably: two related projects (library + service) or a monorepo with multiple `go.mod` files.
- Go 1.18+ for workspace support; in practice aim for Go 1.22+ so the example stays aligned with the rest of the path.
- A basic feel for the `replace` directive in `go.mod` (even if you have not used it often).

## Problem this lesson solves

You work on the library `example.com/auth` and the service `example.com/shop` that imports it. You change `Token()` in auth. Shop locally still sees the old version from the proxy or cache, because its `go.mod` pins the published version. Without a workspace you have bad options:

1. Publish a new auth tag for every tiny change — slow and noisy.
2. Insert `replace example.com/auth => ../auth` into `shop/go.mod` — fast locally, dangerous in git: CI often lacks that relative path.
3. Manually copy code — you lose module boundaries.

Second pain: a monorepo with multiple `go.mod` files. People jump `cd` across folders, lose track of which is the “main module”, and do not know why `go list -m` shows different versions from different directories.

A workspace solves the **local view** over multiple modules: `go.work` tells the toolchain which local paths to treat as root modules for build and related operations. It does not replace versions in production. It does not “publish” a library. It does not magically make CI aware of your laptop — unless the team consciously commits `go.work` as monorepo policy.

## Mental model

Imagine two layers of contract:

1. **`go.mod`** — the module’s master ledger. What the module requires from the world, which `go` version it declares, which `require` lines apply to everyone who uses that module as-is.
2. **`go.work`** — a local desk map. “While I work here, these modules sit together on the desk.” The toolchain in that directory tree (by search rules) sees the workspace.

Key operations:

| Command / concept | Mental role |
|-----------------|-------------|
| `go work init` | Set up the desk and place the first folders |
| `go work use` | Add or remove a folder from the desk |
| `go work sync` | Align dependency requirements across modules on the desk |
| `go env GOWORK` | “Which desk is active?” |
| `GOWORK=off` | Temporarily remove the sticky note and work as a single module |

Picture: `go.mod` is the master ledger. `go.work` is a sticky note on the monitor: “today I look at these folders together”. You do not send the sticky note into a CAT-1 release, unless the team agrees otherwise.

Important constraint: a workspace with no `use` directives (no local modules on the desk) cannot build from local modules in the expected way. The desk must have content.

## Mechanism

### How `go` finds a workspace

The `go` command looks for `go.work` in the current and parent directories (per tool rules). When it finds one, it runs in workspace mode. Check:

```powershell
go env GOWORK
```

The output is the path to the active `go.work`, or empty / `off` if a workspace is not in play. This is the first diagnostic when “the local library is not visible”.

Temporary disable:

```powershell
$env:GOWORK = "off"
go list -m
Remove-Item Env:GOWORK
```

On a Unix shell the equivalent is `GOWORK=off go list -m`. Essence: same code, different source of versions for local modules.

### Initialization: `go work init`

```powershell
go work init ./auth ./shop
```

What it changes:

- Creates `go.work` in the current directory (if one does not already exist in that initialization context).
- Writes a `go` directive (file format version).
- Writes `use` directives for the listed module paths.

Example contents:

```go
go 1.22

use (
	./auth
	./shop
)
```

Each listed directory must be a module (have a `go.mod`). The `use` argument is the directory that contains `go.mod`, not a package path inside it.

### Adding and removing: `go work use`

```powershell
go work use ./payments
go work use -r ./libs
```

What it changes:

- For each argument-directory that **exists** as a module: adds `use` to `go.work` (if it is not already there).
- For an argument that **does not exist**: removes the corresponding `use` directive from `go.work`.
- If after that some remaining `use` path points at a non-existent module, the command fails — the workspace must not “lie” about paths.
- Updates the `go` line in `go.work` to be at least as new as the `go` lines in the used modules.
- With no arguments: only performs that `go` line update.

The `-r` flag recursively finds modules under the listed directories and behaves as if you listed them all. Symlinks to directories within that tree are ignored during `-r` search. Important: `go` does not resolve symbolic links when matching `use` paths to modules — a symlink and its target are not interchangeable in `use` directives.

### Aligning: `go work sync`

```powershell
go work sync
```

What it changes (essence of official behavior):

1. Computes the workspace **build list**: the set of versions of all (transitive) dependency modules used for builds in the workspace, via Minimal Version Selection (MVS).
2. **Syncs that list back** into the modules listed by `use` directives.
3. Sync proceeds by sequential dependency upgrades in each workspace module to the version from the build list, if it is not already the same.
4. MVS guarantees that the version in the build list is always the same as or higher than the one in individual workspace modules.

What `sync` **is not**:

- Not a substitute for `go mod tidy` within a single module (that is 15.07).
- Not “publish the local module”.
- Not magic that fixes a wrong import path.

### Relationship to `replace`

- `replace` in `go.mod` — part of the module; everyone who uses that `go.mod` as-is sees it (including CI if it is committed).
- `replace` in `go.work` — same syntax as in `go.mod`, takes precedence over `replace` in the `go.mod` files of workspace modules; primarily for resolving conflicts between different workspace modules.
- Workspace `use` — a local path overlay: modules on the desk become root modules for operations.

For private local work on your own library: prefer a workspace over committing a relative `replace` in `go.mod`.

### How a workspace affects everyday commands

When a workspace is active, commands like `go build`, `go test`, `go list` use the workspace context. A local module listed in `use` can satisfy another local module’s import without a public tag.

Version diagnostics:

```powershell
go list -m
go list -m all
go list -m example.com/auth
```

If you suspect the build environment, also check:

```powershell
go env GOWORK
go env GOOS GOARCH
go env CGO_ENABLED
```

A workspace does not change `GOOS`/`GOARCH`. Cross-compilation still follows the rules from 15.02: pure Go often goes with `CGO_ENABLED=0`; cgo requires an appropriate toolchain.

### Trace 1 — From clone to a visible local change

```text
repo/
  auth/go.mod
  shop/go.mod
```

1. `go work init ./auth ./shop` → `go.work` appears with `use`.
2. In `shop` you import `example.com/auth`.
3. `go env GOWORK` shows the path to `go.work`.
4. You change a function in `auth`.
5. `go test` / `go run` from `shop` sees the local code — because auth is on the desk.
6. `GOWORK=off` → shop looks up auth as an external module (proxy/cache/version from `go.mod`); the local change disappears from view.

### Trace 2 — A relative replace that breaks CI

```text
Developer commits in shop/go.mod:
  replace example.com/auth => ../auth

CI checks out only shop (or a different path structure)
  → ../auth does not exist as the local laptop expects
  → build FAIL
```

Workspace + `.gitignore` for `go.work` keeps locality out of the shared `go.mod`.

### Trace 3 — sync after dependency divergence

```text
shop requires lib@v1.2.0
auth requires lib@v1.4.0
workspace build list (MVS) chooses >= needed level
go work sync
  → raises requirements in modules toward build list versions where needed
```

After sync you still run `go mod tidy` where you touched imports — sync and tidy do different jobs.

### Trace 4 — Wrong working directory

```text
cd shop/internal/api
go env GOWORK   # if no go.work above by the rules — empty/off
go test ./...     # behaves like an ordinary single module
```

Path diagnostics first, not “Go is broken”.

## Rules and syntax

### Shape of `go.work`

The file is line-oriented: keyword + arguments. Blocks like import code:

```go
go 1.22

use (
	./auth
	./shop
	./payments
)

replace example.com/foo v1.2.3 => example.com/bar v1.4.5
```

### Team and tooling rules

1. Do not commit `go.work` / `go.work.sum` until the team has an explicit policy. Many put both in `.gitignore`.
2. Document in the README the exact sequence: `go work init ...` or a `scripts/work.ps1` script.
3. CI: build modules separately (or with an explicitly committed workspace in a monorepo) — be consistent.
4. Do not mix workspace with “I no longer need to version libraries”.
5. After `use`, check `go list -m` and `go env GOWORK`.
6. Keep `use` paths relative and stable; avoid absolute Windows paths in a shared file.
7. A symlink in `use` is not the same as the target path — do not “fix” at random.
8. `go work use` with no arguments only aligns the `go` line — not an error, but not `sync` either.

### Typical `.gitignore`

```text
go.work
go.work.sum
```

Monorepo exception: some teams commit `go.work` as the canonical view. That must be a conscious decision, not one developer’s accident.

### Typical layout

```text
repo/
  go.work              # often ignored
  go.work.sum          # often ignored
  auth/go.mod
  shop/go.mod
  payments/go.mod
  scripts/work.ps1
```

## Examples

### Example 1 — Two modules and `go work init`

**Predict the result:** After `init`, can `shop` see local `auth` without a published tag, if the workspace is active and the import path is correct?

```powershell
mkdir auth, shop
cd auth
go mod init example.com/auth
@'
package auth

func Token() string { return "t-local" }
'@ | Set-Content auth.go

cd ..\shop
go mod init example.com/shop
@'
package main

import (
	"fmt"

	"example.com/auth"
)

func main() {
	fmt.Println(auth.Token())
}
'@ | Set-Content main.go

cd ..
go work init ./auth ./shop
go env GOWORK
cd shop
go run .
```

#### What happens here

The script creates `example.com/auth`, whose `Token` returns `t-local`, and `example.com/shop`, whose `main` imports that module and prints the token. `go work init ./auth ./shop` writes a parent `go.work` that uses both directories, and `go env GOWORK` prints the path to that file when the workspace is active. `go run .` in `shop` then builds against the local `auth` module and prints `t-local`.

**Answer:** Yes — with an active workspace, the local module from `use` satisfies the import. Output should be `t-local` (local code), not some old published version. If `go run` hits the network/proxy and does not see local, first `go env GOWORK`, then whether the `use` path is correct. The exact sequence around `go get` / `tidy` can vary with `go.mod` state; the lesson’s essence is workspace visibility, not one magic one-liner.

### Example 2 — `go work use` adds a third module

**Predict the result:** What will stand in `go.work` after `use ./payments`?

```powershell
mkdir payments
cd payments
go mod init example.com/payments
cd ..
go work use ./payments
Get-Content go.work
```

#### What happens here

The commands create module `example.com/payments` and then `go work use ./payments` adds `./payments` to the `use` block of `go.work`. `Get-Content go.work` prints the file, including that new directory beside the ones already listed. The new module keeps its own `go.mod`.

**Answer:** In the `use` block (or as a line) `./payments` will appear alongside the existing paths. Each module still has its own `go.mod`. The workspace only expands the desk.

### Example 3 — `GOWORK=off` comparison

**Predict the result:** With `GOWORK=off`, does `go list -m example.com/auth` still show the local path of the workspace module?

```powershell
cd shop
go env GOWORK
go list -m example.com/auth
$env:GOWORK = "off"
go list -m example.com/auth
Remove-Item Env:GOWORK
```

#### What happens here

The first `go list -m example.com/auth` still runs with the workspace active, so the listed module can be the local `use` directory. Setting `GOWORK` to `off` makes the next `go list -m` resolve `auth` from `shop`'s `go.mod` and the module cache or proxy. `Remove-Item Env:GOWORK` clears that override for later commands in the same window.

**Answer:** Do not expect the same local workspace view. With `off`, shop looks up auth as an external module per `go.mod` / proxy / cache rules. That is an intentional difference between DX and the “clean” module world.

### Example 4 — `go work sync` after an external dependency

**Predict the result:** Does `sync` itself add an import in Go code?

```powershell
cd shop
go get rsc.io/quote@v1.5.2
cd ..
go work sync
```

#### What happens here

`go get rsc.io/quote@v1.5.2` in `shop` records that version in the module requirements and downloads it as needed. `go work sync` rebuilds the workspace build list and moves the `use` modules up to those versions where they are behind. The import list in each `.go` file stays as it was; these commands change module metadata and the download cache.

**Answer:** No. `go get` changes module requirements (and often the cache). `go work sync` aligns the workspace build list back into the modules. You still add the import in the `.go` file; single-module hygiene is completed by `go mod tidy` (15.07).

### Example 5 — Why a relative `replace` in git hurts

**Predict the result:** Does CI that lacks `../auth` succeed with this in `shop/go.mod`?

```go
replace example.com/auth => ../auth
```

#### What happens here

The `replace` directive loads `example.com/auth` from the relative directory `../auth`. A build of this `go.mod` looks for that sibling folder on disk. If the checkout has no `../auth`, the build fails on the missing path.

**Answer:** Often no. The relative path is valid for the author’s laptop layout. A workspace keeps that locality out of the shared `go.mod`. If you must have `replace` in `go.mod`, keep it temporary, documented, and removed before merge to main — or replace it with a fork/version.

### Example 6 — Recursive `use -r`

**Predict the result:** Does `-r ./libs` add only direct subfolders or deeper modules as well?

```powershell
go work use -r ./libs
Get-Content go.work
```

#### What happens here

`go work use -r ./libs` walks `libs` recursively and adds each module it finds, as if every directory had been named on the command line. Symlinks to directories inside that tree are ignored. `Get-Content go.work` prints the `use` block that results.

**Answer:** It recursively finds modules under `libs` and adds them as if listed individually. Symlinks to directories within that tree are ignored during that search. Verify the result with your eyes in `go.work` — do not trust memory.

### Example 7 — Diagnostics with `go env` and platform

**Predict the result:** Does a workspace change `GOOS`?

```powershell
go env GOWORK GOOS GOARCH CGO_ENABLED
```

#### What happens here

This `go env` prints `GOWORK`, `GOOS`, `GOARCH`, and `CGO_ENABLED` on separate lines. `GOWORK` is the active workspace file, or `off` when workspace mode is disabled. `GOOS`, `GOARCH`, and `CGO_ENABLED` stay the target system and the cgo switch; the workspace file does not rewrite them.

**Answer:** No. `GOWORK` is a path (or off). `GOOS`/`GOARCH` remain the target platform. `CGO_ENABLED` remains the cgo switch. Workspace and cross-compile are orthogonal concepts; they mix only indirectly when you build modules with cgo dependencies.

### Example 8 — `use` removes a vanishing path

**Predict the result:** What happens if you run `go work use ./old-module` and the folder does not exist?

```powershell
go work use ./old-module
```

#### What happens here

`go work use ./old-module` adds that directory to `go.work` when the directory exists, and removes the matching `use` line when it does not. A missing `./old-module` is therefore dropped rather than recorded. If any `use` line that remains still names a missing directory, the command fails.

**Answer:** If that is the way to remove a `use` for a path that no longer exists, the command removes the directive. If after the operation `use` lines toward non-existent modules remain, `use` fails. The workspace must stay consistent.

## Decision analysis

**Workspace or `replace` in `go.mod`?**  
Local development of multiple own modules → workspace. An urgent third-party fork with a long life → sometimes `replace` + fork, but plan an exit (own module path or upstream merge).

**Commit `go.work`?**  
Default: no. Yes only if monorepo policy says it is the canonical file for all developers and CI.

**One `go.mod` instead of many?**  
If packages are always versioned together and boundaries are weak — one module is simpler. Workspace shines when modules have a separate release rhythm or clear boundaries.

**When not to use a workspace?**  
One module, no local libraries in development — do not complicate.

**Script or README ritual?**  
If paths are not obvious, a `scripts/work.ps1` script reduces new-member mistakes. The README must still state commit/gitignore policy.

**`go.work` `replace` vs `go.mod` `replace`?**  
Conflict between workspace modules → consider `replace` in `go.work`. A lasting contract of one module toward the world → carefully in `go.mod`, rarely relative laptop paths.

## Trade-offs

| Approach | Gain | Cost |
|---------|-------|------|
| Local workspace (gitignore) | fast feedback without dirtying `go.mod` | people forget CI does not have the same desk |
| Committed `go.work` | unified view in the monorepo | less laptop path flexibility; everyone needs the same structure |
| Relative `replace` in `go.mod` | explicit in the module | easily breaks CI and colleagues |
| One large module | less tooling | weaker version and release boundaries |
| Only published tags | clean CI model | slow feedback while you work on the library |

## Common mistakes

1. Committing a relative `replace ../` “temporarily” — it stays forever.
2. Expecting the workspace itself to publish modules or change the proxy.
3. Wrong working directory — empty `GOWORK`, blaming Go.
4. Absolute Windows paths in a shared `go.work`.
5. `go work sync` as a substitute for `go mod tidy` where tidy is needed.
6. Two different `go.work` files in odd subfolders — confusing overlap.
7. Ignoring policy for `go.work.sum`.
8. Mixing GOPATH habits with the workspace mental model.
9. Symlink “tricks” in `use` paths.
10. Cross-compile fail blamed on the workspace, while the cause is `CGO_ENABLED` / toolchain.

## Idiomatic Go

- README section: “Multi-module local development” with exact commands.
- `.gitignore` for `go.work` and `go.work.sum` unless the monorepo says otherwise.
- Onboarding checklist: `go env GOWORK` after cloning.
- Prefer a workspace for local changes to a library the service uses.
- Keep module boundaries clean; a workspace is not an excuse for spaghetti imports between services.
- In CI do not depend on laptop `go.work` except for an explicit monorepo decision.
- For pure Go cross-compile still think about `CGO_ENABLED=0`; the workspace does not solve that for you.
- Still inject version into the binary via `-ldflags -X` when needed — orthogonal to the workspace.

## Practical scenario

A platform team maintains an `sdk` module and three services. Developers insert `replace => ../../sdk` into every service. One forgets to remove it — green locally, red CI. Tickets repeat.

Policy after the incident:

1. `go.work` and `go.work.sum` in `.gitignore`.
2. Script `scripts/work.ps1` runs `go work init` / `go work use` with relative paths everyone shares in the checkout structure.
3. CI builds each module in isolation with versions from `go.mod` / `go.sum`.
4. PR checklist: “no relative `replace` paths”.
5. SDK release still goes by tags; services pin versions consciously.

After a month: zero tickets “CI cannot find sdk”. Local feedback stays fast. A new member runs the script, checks `go env GOWORK`, works.

Supplement: one developer tried to “speed up CI” by committing their `go.work` with `C:\Users\...` paths. Reviewer rejects. Policy says: either relative paths for everyone, or nothing in git.

## Summary

- `go.work` is a local desk for multiple modules; `go.mod` remains the module’s contract with the world.
- `go work init` sets up the desk; `go work use` adds/removes paths; `go work sync` syncs the workspace build list back into modules.
- `go env GOWORK` is the first diagnostic; `GOWORK=off` compares the world without the desk.
- Prefer a workspace over committing relative `replace` paths.
- A workspace does not replace versions, proxy, `tidy`, or cross-compile rules (`CGO_ENABLED`, `GOOS`/`GOARCH`).
- Commit vs gitignore policy must be team policy, not personal.

```text

```

If `go test` hits the network and asks for `auth` from the proxy while you expect local, the workspace is not active or `use` is wrong — first `go env GOWORK`.

## Path traps

- Absolute Windows paths in committed `go.work` — pain for Linux CI.
- Symlinks and different drive letters — check before blaming Go.
- Working from a subpackage without awareness of where `go.work` is — empty `GOWORK`.
- Mixing forward/back slash in docs without testing on both platforms.
- “Works on my machine” because `GOWORK` is always set in the laptop shell profile — the colleague does not have it.

## Short glossary

| Term | Meaning |
|-------|----------|
| `go.work` | local module desk |
| `use` | add/remove a module on the desk |
| `sync` | sync the workspace build list back into modules |
| `replace` | version/path overlay (caution in `go.mod`) |
| `GOWORK=off` | ignore the workspace |
| MVS | Minimal Version Selection — chooses versions in the build list |
| root module | the module from which (or from whose desk) `go` drives the operation |

## Mapping to other CLI topics

| Topic | Link to workspace |
|------|----------------------|
| `go env` | `GOWORK`, but also `GOOS`/`GOARCH`, `CGO_ENABLED` for build diagnostics |
| `go mod tidy` | hygiene of one module; sync is not a substitute |
| `go list -m` | see which versions/paths the workspace chooses |
| `-ldflags -X` | writing version into the binary — orthogonal |
| build tags | still select files; workspace selects modules |
| `CGO_ENABLED=0` | pure Go cross-compile; workspace does not turn off cgo for you |
| `GOMAXPROCS` / `GOGC` / `GOMEMLIMIT` | process runtime behavior — do not mix with module resolution |

## More traces for PR review

Before you declare the workspace a “team standard”, answer in the PR description:

1. What do we change in CI tomorrow?
2. What do we document in the README?
3. What do we measure to know it is better (e.g. number of CI failures due to `replace`)?
4. What is explicitly out of scope (e.g. we do not touch release rhythm)?

Without these four answers, the lesson stays theory. With them it becomes practice.

## Extended example: library + two consumers

```text
repo/
  go.work
  sdk/go.mod          # example.com/sdk
  billing/go.mod      # example.com/billing
  gateway/go.mod      # example.com/gateway
```

Flow:

```powershell
go work init ./sdk ./billing ./gateway
cd sdk
# API change
cd ..\billing
go test ./...
cd ..\gateway
go test ./...
cd ..
go work sync
```

Expectation: both consumers see the local sdk while the workspace is active. CI still pins versions when sdk is not in the same checkout as in your experiment — that is why policy must be clear.

## What to do when sync makes a large diff

1. Read the diff in each `go.mod` — which dependency was raised?
2. Check whether that is MVS intent or the result of a temporary `go get` experiment.
3. Run `go test ./...` in the affected modules.
4. Do not mix an API refactor and a mass dependency bump in the same PR without need.
5. If the diff is “weird”, compare with `GOWORK=off` to see what the clean module world is.

## Contrast: workspace vs vendor vs proxy

- **Workspace** — local modules on the desk.
- **Vendor** (`go mod vendor`, 15.07) — a copy of dependencies in the repo.
- **Proxy/cache** — network/cache source of published modules.

These are three different levers. They do not replace one another. Workspace does not vendor. Vendor does not make a local sibling module magically visible like `use`.

## Exercise with build tags (orthogonal)

Create in `auth` a file with a build tag and verify that the workspace still works, while file selection goes through tags:

```powershell
go test -tags=integration ./...
```

Goal: understand that the workspace chooses **modules**, and build tags choose **files within packages**.

## Exercise with `-ldflags -X` (orthogonal)

```powershell
go run -ldflags "-X example.com/shop/internal/version.Version=dev-workspace" .
```

Goal: embedding version does not depend on `go.work`. Document both rituals separately in the README.

## Final reminder

A workspace is DX. Versions and CI stay on `go.mod`/`go.sum`. If the local desk and the CI story diverge, first check `GOWORK`, not “module magic”.

Keep the init script in `scripts/` so a new member does not guess paths. After a week of use, the ritual becomes automatic.

When something “does not see the local change”:

1. `go env GOWORK`
2. Contents of `use` in `go.work`
3. Import path vs `module` line in `go.mod`
4. Comparison with `GOWORK=off`
5. Only then `tidy` / `sync` / network

1. What is the difference between “module is not on the desk” and “module is on the desk but the import path is wrong”?
2. Why can `go work sync` touch multiple `go.mod` files at once?
3. How would you explain a workspace to a junior in three sentences without the “MVS” jargon?
4. When would you propose merging two modules instead of introducing `go.work`?
5. Where in the pipeline do you check that there is no relative `replace`?

## Note on `go work edit` and `go work vendor`

Official `go work` also has `edit` (for tools/scripts) and `vendor` (vendoring at workspace level). In this lesson the focus stays on `go.work` + `use` + `sync` because that covers the everyday flow. If you need automatic `go.work` edits from a script, read `go help work edit`. Vendoring in more detail is covered in 15.07 at module level (`go mod vendor`); workspace vendor is a more advanced layer when a monorepo consciously chooses that model.

New member:

## Symptom matrix and first commands

| Symptom | First command | Second hypothesis |
|---------|--------------|--------------------|
| I don’t see the local library change | `go env GOWORK` | wrong import path |
| CI cannot find the local module | is `replace` in git? | CI lacks your `go.work` |
| `use` fails | does `go.mod` exist on the path? | symlink confusion |
| Huge diff after sync | intentional bump? | mixing with tidy |
| Works only on my machine | absolute paths in `go.work`? | `GOWORK` in shell profile |

## How to explain workspace to a junior (script)

1. “Each project still has its own `go.mod`.”
2. “`go.work` tells the tool: these local projects work together today.”
3. “That does not go to production by itself — CI still looks at versions.”
4. “That is why we do not commit laptop `replace` paths.”
5. “Check: `go env GOWORK`.”

If after this the junior still commits `replace`, the problem is review, not a lack of blog posts.

## Anti-pattern catalog with fix

1. **Anti-pattern:** five `go.work` files in subfolders.  
   **Fix:** one root workspace or explicit documentation of which is canonical.

2. **Anti-pattern:** `go work sync` in a post-commit hook without control.  
   **Fix:** sync consciously, with diff review.

3. **Anti-pattern:** mixing GOPATH-mode nostalgia with modules.  
   **Fix:** modules + workspace; no return to 2017.

4. **Anti-pattern:** “workspace replaces semantic versioning”.  
   **Fix:** local desk ≠ release policy.

5. **Anti-pattern:** documentation only for Linux paths in a Windows team.  
   **Fix:** relative paths + test on both platforms.

## Link to runtime env (what a workspace is not)

A workspace does not configure:

- `GOMAXPROCS` — how many OS threads the scheduler uses;
- `GOGC` — GC aggressiveness;
- `GOMEMLIMIT` — soft memory limit;
- `-ldflags -X` — embedding version into the binary;
- build tags — file selection.

It chooses the **module root set** for operations. When a latency incident starts, do not look for `go.work` — look for metrics and runtime env. When “wrong library version” starts — then `GOWORK` and `go list -m`.

## Checklist before merging a multi-module PR

- [ ] Diff does not contain `go.work` (except monorepo policy)
- [ ] Diff does not contain a relative `replace` to a laptop path
- [ ] Every touched module has a sensible `go.mod` diff
- [ ] Tests pass with an active workspace locally
- [ ] You understand how CI builds without your desk
- [ ] README/ritual updated if paths are new
- [ ] Release plan for the library if the API surface changes the contract
