# 15.02 Modifying the build environment: GOOS, GOARCH, CGO, ldflags, and tags

> **Go Path - Zero to Gopher** / **02 Intermediate → The Go CLI Playbook** / Lesson 15.02

## Lesson goals

After this lesson you should:

- control the **target OS and architecture** via `GOOS` and `GOARCH`
- understand what `CGO_ENABLED` does and when to turn it off deliberately
- inject build-time metadata via `-ldflags -X`
- use **build tags** for conditional compilation without copying the whole project
- know the boundary: what is build environment vs runtime environment (following lessons)
- build a “static-ish” pure Go artifact with `CGO_ENABLED=0` and understand the limits
- verify effective values via `go env GOOS GOARCH CGO_ENABLED` before the build

## Prerequisite

- lesson 15.01: `go` as a toolchain, `go env`, modules
- Go 1.22+; you can `go build` and `go run` in a module
- basic concepts: package, `main`, exported identifiers
- PowerShell or bash for temporarily setting env variables

## Problem this lesson solves

A team builds a CLI tool. It works on Windows. On a Linux server “something is wrong” — the binary is not for that OS at all, or it is linked against a C library that does not exist on an alpine image. Another time: the version in `--version` says `dev` even though it is a release, because nobody injected the git SHA into the build. A third time: a Windows file and a Unix file both enter the build and symbols collide.

Without a deliberate **build environment** people:

- build “whatever the laptop gives them” and call that an artifact
- enable CGO without knowing they lost simple cross-compile
- copy `#ifdef` habits from C instead of Go tags
- hard-code versions in source and forget to update them
- set `GOOS` in Kubernetes env thinking it will change an already-built binary

The lesson teaches that a build is a **contract**: for which OS, with which C bridge, with which metadata, with which conditional files.

## Mental model

The build environment is a **mold** into which the same source goes, and a different artifact comes out.

1. **GOOS / GOARCH** — the shape of the mold (linux/amd64, windows/arm64…).
2. **CGO_ENABLED** — whether it may call a C compiler and linker (bridge to the C world).
3. **`-ldflags -X`** — stamping strings into already-declared variables at link time.
4. **Build tags** — which files enter compilation at all.

Runtime env (`GOGC`, `GOMEMLIMIT`…) changes the behavior of a **running** process. Build env changes **what you get on disk**. Mixing these two layers creates chaos in docs (“set GOOS in Kubernetes” — that does not change an already-built binary).

Picture: same recipe, different oven. Tags choose which ingredients you put in the bowl. `-X` stamps the bake date on the packaging. CGO decides whether you may call an outside craftsman with a different tool.

Another axis: **host vs target**.

| Concept | Question |
|-------|---------|
| Host | On which OS/arch is `go` **running** now? |
| Target | For which OS/arch are you **building** the binary? |

`go version` shows the host. `GOOS`/`GOARCH` set the target. When they match — ordinary local build. When they differ — cross-compilation.

## Mechanism

### Cross-compilation with GOOS and GOARCH

The Go toolchain can build for another OS/arch from the same machine (with limits around CGO). You set:

```text
GOOS=linux GOARCH=amd64
```

then `go build`.

On bash/zsh:

```bash
GOOS=linux GOARCH=amd64 go build -o app .
```

On PowerShell:

```powershell
$env:GOOS = "linux"
$env:GOARCH = "amd64"
go build -o app .
# afterward: remove or restore if you do not want it to remain for the rest of the session
Remove-Item Env:GOOS -ErrorAction SilentlyContinue
Remove-Item Env:GOARCH -ErrorAction SilentlyContinue
```

Check before the build:

```powershell
go env GOOS GOARCH
```

Trace of one cross build:

```text
1. Shell sets GOOS=linux, GOARCH=amd64
2. go build reads the effective env
3. Files with matching GOOS/GOARCH constraints and tags are selected
4. Compiler generates an object for linux/amd64
5. Linker produces an ELF (Linux) binary — not PE (.exe)
6. -o app writes the file to disk
7. That binary does NOT run on Windows (except via VM/WSL/emulation)
```

Without CGO, this is often enough for pure Go programs. With CGO, you need a C cross-toolchain — that is why many CI jobs build with `CGO_ENABLED=0` for simple services.

### Common GOOS / GOARCH values

Not an inventory of “everything that exists” — typical pairs you see in practice:

| GOOS | GOARCH | Note |
|------|--------|----------|
| `linux` | `amd64` | common servers |
| `linux` | `arm64` | ARM cloud / Raspberry-style devices |
| `windows` | `amd64` | desktop / Windows servers |
| `darwin` | `arm64` | Apple Silicon |
| `darwin` | `amd64` | older Intel Mac |

The list of supported pairs depends on the toolchain version. Do not memorize rare ones; check the docs / experiment in CI.

### CGO as a bridge switch

- `CGO_ENABLED=1` — allow cgo (default on many desktop installs).
- `CGO_ENABLED=0` — pure Go build; no use of the `import "C"` path; easier cross-compile for pure Go.

CGO is not “bad.” CGO is a **more expensive contract**: slower builds, harder deploy, more platform traps. Turn it off when you do not need it, turn it on when you must (e.g. certain drivers, special crypto, legacy).

Trace with `CGO_ENABLED=0`:

```text
1. CGO_ENABLED=0 go build
2. Toolchain does not call an external C compiler for cgo
3. Packages that require cgo will not build
4. Pure Go code passes
5. Cross GOOS/GOARCH more often succeeds without an extra C toolchain
```

Note on “static-ish”: `CGO_ENABLED=0` for **pure Go** often gives a binary that does not pull C libraries via cgo. That is **not** a magic guarantee of “fully static everything in the universe” — but it is a common and correct pattern for simple Go services in minimal containers. Do not invent extra flags you have not read in `go help build` / linker docs.

PowerShell:

```powershell
$env:CGO_ENABLED = "0"
$env:GOOS = "linux"
$env:GOARCH = "amd64"
go build -o app .
```

### `-ldflags -X` — stamping strings at link time

The linker can set the value of a **string** variable:

```text
-ldflags="-X 'main.version=1.4.2' -X 'main.commit=abc123'"
```

Form:

```text
-X importpath.name=value
```

The variable must already exist in the package (e.g. `var version = "dev"`). This is not a magic config file — it is stamping into the binary at link time.

Example in code:

```go
package main

import "fmt"

var version = "dev"

func main() {
	fmt.Println(version)
}
```

Build:

```powershell
go build -ldflags="-X 'main.version=1.4.2'" -o app.exe .
```

Trace:

```text
1. Compiler sees var version = "dev"
2. Linker applies -X main.version=1.4.2
3. In the binary the string becomes 1.4.2
4. Running prints 1.4.2
5. Source can still have "dev" as the default for local go run without ldflags
```

Multiple `-X` in the same `-ldflags` is common (version, commit, build time — if you deliberately inject it).

Note: values with spaces and quoting depend on the shell. On PowerShell quoting can hurt — test locally the same command you put in CI.

### Build tags (constraints)

Build tags choose **which files** enter compilation.

Modern form at the top of the file:

```go
//go:build windows

package platform
```

The older form (`// +build windows`) still exists in older code; new code prefers `//go:build`.

Example file pair:

```go
// file: path_windows.go
//go:build windows

package app

func pathSep() string { return `\` }
```

```go
// file: path_unix.go
//go:build unix

package app

func pathSep() string { return "/" }
```

(The exact set of tags like `unix` / `windows` follows Go platform rules — do not inventory from memory; read `go help buildconstraint`.)

Trace:

```text
1. GOOS=windows → windows file enters, unix does not
2. GOOS=linux → unix file enters, windows does not
3. Both files in the same package → one pathSep definition for the target
4. Without tags, two functions of the same name → symbol conflict
```

Manual tags (e.g. `integration`):

```go
//go:build integration

package svc_test
```

Running with tags goes via `-tags` on `go build` / `go test` (see `go help build`):

```powershell
go test -tags=integration ./...
```

### How a file enters the build — the decision

For every `.go` file the toolchain asks:

```text
1. Does the file name or //go:build constraint match GOOS/GOARCH/tags?
2. Is it _test.go (only for test)?
3. Is it in the right package directory?
```

If all package files are excluded by tags, you get an empty package / error. That is a common cause of “no Go files” when you forget a tag on CI.

### Checking what would enter — list and intent

```powershell
go list -f "{{.GoFiles}}" .
go env GOOS GOARCH CGO_ENABLED
```

`GoFiles` (and related fields) help you see which files the package sees for the current context. When debugging tags, this is an X-ray.

### What build env does **not** change

- It does not change an already-running process in production.
- It does not change `GOGC` behavior (that is runtime, 15.04).
- It does not replace `os.Getenv` in your code (15.05) — that is another map.
- Setting `GOOS` in a Kubernetes Deployment does **not** rewrite an image already built for the wrong OS.

### CI pattern (typical)

```yaml
# idea, not a mandatory YAML dialect:
# env:
#   CGO_ENABLED: "0"
#   GOOS: linux
#   GOARCH: amd64
# script:
#   go build -ldflags="-X main.version=$CI_COMMIT_SHA" -o bin/app .
```

Document the same variables in the README. A local developer on Windows can reproduce a Linux artifact without a Linux laptop (for pure Go + CGO off).

### Metadata reproducibility

If `-X` injects build time down to the second, two builds of the same commit produce different bytes. For reproducible builds teams often:

- pin version / commit
- avoid “now” in ldflags or use a source timestamp from VCS
- fix the toolchain version

That is not the whole lesson’s topic, but you know why “same code” is not always “same bytes.”

### Windows exe vs Linux without extension

```powershell
# target windows
$env:GOOS="windows"; $env:GOARCH="amd64"
go build -o app.exe .

# target linux
$env:GOOS="linux"; $env:GOARCH="amd64"
go build -o app .
```

You choose the file name via `-o`. The `.exe` extension is a Windows convention, not GOOS magic — but users expect `.exe` on Windows.

### Debug: “build works, binary won’t start on the server”

Checklist:

```text
1. file app / Get-Item — is it a Linux ELF at all?
2. go env GOOS GOARCH at build time (log it in CI!)
3. CGO_ENABLED — does it pull glibc that alpine does not have?
4. GOARCH arm vs amd64 on the server
```

Often the answer: built for windows/amd64, uploaded to linux/arm64.

### Release matrix (mental table)

For a CLI that supports multiple platforms, CI often runs a matrix:

```text
linux/amd64
linux/arm64
windows/amd64
darwin/arm64
```

Each cell = same source + different `GOOS`/`GOARCH` (+ usually `CGO_ENABLED=0`) + different `-o` artifact name (e.g. `app-linux-amd64`).

You do not have to support everything from day one. You must **know** that each artifact is a separate mold contract.

### File name vs binary contents

Renaming `app.exe` to `app` does not turn a Windows PE into a Linux ELF. It only changes the label. Truth is in the bytes the linker produced under the given `GOOS`/`GOARCH`.

That is why “upload under a linux name” without cross-compile is not a fix.

### `runtime.GOOS` in code vs build tags

```go
import "runtime"

func pathSep() string {
	if runtime.GOOS == "windows" {
		return `\`
	}
	return "/"
}
```

This chooses a branch **at runtime** in one binary. Build tags choose code **at compile time** — different bytes per target. Both are legitimate:

- small difference → `runtime.GOOS` often enough
- large OS-specific APIs / files → tags are cleaner

### When you need a real Linux agent instead of cross

- you need CGO with Linux libraries
- you test system calls that cross does not cover enough
- you want `go test` on real target kernel behavior

Otherwise, for a pure Go service, cross with `CGO_ENABLED=0` is often enough.

### Documenting in the README (pattern)

```markdown
## Release build (Linux amd64)

PowerShell:
$env:CGO_ENABLED="0"
$env:GOOS="linux"
$env:GOARCH="amd64"
go build -ldflags="-X main.version=VERSION" -o bin/app ./cmd/app
```

If the README lies relative to CI, the team will upload the wrong artifact again.

### Quick artifact check after cross-compile

On Windows you do not always have `file(1)`. Minimal discipline:

```powershell
go env GOOS GOARCH CGO_ENABLED
go build -o bin/app .
# record in CI log: expected target = linux/amd64
```

On a Linux agent after downloading the artifact:

```bash
file bin/app
# ELF ... → good for Linux
```

If CI builds and immediately tests in the same job on the same OS, host==target and this check is trivial. The problem appears when the artifact crosses an OS boundary.

### ldflags security

Anything you inject via `-X` can be found in the binary (`strings` tools). Do not stamp:

- tokens
- passwords
- private URLs with secret query parameters

Version and commit SHA are OK. Secrets go into runtime env / a secret store (15.05 is about reading, not linking into bytes).

## Rules and syntax

1. **Target:** `GOOS` and `GOARCH` set the goal; check `go env` before the build.
2. **Temporary > permanent:** for cross-compile prefer env in one command / job over a forgotten `go env -w`.
3. **CGO:** `CGO_ENABLED=0` for pure Go cross and simpler containers; enable CGO only when you must.
4. **`-X`:** only existing string variables; importpath must be exact (`main.version` or `example.com/app/cmd/api.version`).
5. **Tags:** `//go:build` at the top; one clear intent per file; read `go help buildconstraint`.
6. **`-tags`:** pass explicitly in CI when testing/building conditional packages.
7. **Do not mix layers:** build env ≠ runtime env ≠ app config env.
8. **Log in CI:** `GOOS`, `GOARCH`, `CGO_ENABLED`, `go version`, and the full `go build` line.
9. **`-o`:** always an explicit output name in the release job.
10. **Check help:** `go help build`, `go help buildconstraint` — do not invent flags.

Minimal cross pattern (PowerShell):

```powershell
$env:CGO_ENABLED = "0"
$env:GOOS = "linux"
$env:GOARCH = "amd64"
go build -ldflags="-X 'main.version=1.0.0'" -o bin/app ./cmd/app
```

## Examples

### Example 1 — Cross-compile from a Windows host

```powershell
$env:CGO_ENABLED = "0"
$env:GOOS = "linux"
$env:GOARCH = "amd64"
go env GOOS GOARCH CGO_ENABLED
go build -o bin/api ./cmd/api
```

### What happens here

You temporarily change the target and turn CGO off. `go env` confirms before the build. Output `bin/api` is a Linux amd64 artifact (for pure Go). The host stays Windows — only the mold is different.

### Predict the result

Can you reliably run that `bin/api` by double-clicking on Windows?

**Answer:** not as a native Windows program. It is a Linux binary. It runs on Linux (or WSL/VM/an appropriate environment).

---

### Example 2 — `-ldflags -X` for version

```go
package main

import "fmt"

var (
	version = "dev"
	commit  = "none"
)

func main() {
	fmt.Printf("%s (%s)\n", version, commit)
}
```

```powershell
go build -ldflags="-X 'main.version=1.4.2' -X 'main.commit=abc123'" -o app.exe .
.\app.exe
```

### What happens here

Without ldflags, `go run .` prints `dev (none)`. With ldflags, the linker stamps release metadata. Source keeps a safe default for local work.

### Predict the result

What if you type `-X 'main.verzion=1.4.2'` (typo in the name)?

**Answer:** the linker typically does not “hit” the right variable; version stays `dev` (or you get a warning depending on tools/version). Check the name exactly.

---

### Example 3 — Build tag for platform

```go
// file_windows.go
//go:build windows

package main

func openConfigPath() string {
	return `C:\app\config.json`
}
```

```go
// file_other.go
//go:build !windows

package main

func openConfigPath() string {
	return "/etc/app/config.json"
}
```

### What happens here

For a Windows target the first file enters; for non-Windows the second. Same function, different implementation, without a runtime `if runtime.GOOS` (you can do that too — tags are for compilation).

### Predict the result

If both files **have no** tag and both define `openConfigPath`, what happens on `go build`?

**Answer:** conflict — redeclaration of a symbol in the same package.

---

### Example 4 — Integration tag

```go
//go:build integration

package db_test
```

```powershell
go test ./...                 # without integration tests in that file
go test -tags=integration ./...
```

### What happens here

Default tests stay fast. Heavy tests enter only when you explicitly request the tag. CI can have a separate job.

### Predict the result

Does `-tags=integration` change `GOOS`?

**Answer:** no. Tags and GOOS are different axes of file filtering.

---

### Example 5 — CGO trap on cross-compile

An imagined package that uses cgo. You do:

```powershell
$env:GOOS = "linux"
$env:GOARCH = "amd64"
# CGO stays 1
go build -o app .
```

### What happens here

The toolchain tries to cross **with** cgo — often fails because you do not have a Linux C cross-compiler on a Windows host. With `CGO_ENABLED=0` the same pure Go project passes; a project that **must** use cgo needs a real cross C toolchain or a build on a Linux agent.

### Predict the result

What is the pragmatic CI strategy for a pure Go microservice without cgo?

**Answer:** `CGO_ENABLED=0` + explicit `GOOS`/`GOARCH` + `go build -o …` on any agent that has Go.

---

### Example 6 — Checking GoFiles after changing GOOS

```powershell
$env:GOOS = "windows"
go list -f "{{.GoFiles}}" .
$env:GOOS = "linux"
go list -f "{{.GoFiles}}" .
```

### What happens here

The file list changes with the target. That is proof that tags/GOOS are not theory — the toolchain really chooses a different set.

### Predict the result

If you see an empty set / error only for one GOOS, what do you suspect?

**Answer:** that all package files are excluded by constraints for that target (missing `!windows` pair, wrong tag, etc.).

---

### Example 7 — ldflags quoting on PowerShell

```powershell
go build -ldflags="-X main.version=1.0.0" -o app.exe .
```

Also try variants with single quotes around `main.version=…` if the shell “eats” characters.

### What happens here

The same `-ldflags` string is parsed differently by bash and PowerShell. That is why a release script must be tested on the **same** shell as CI (or use `make`/a script with clear quoting).

### Predict the result

If version stays `dev` after a “successful” build, what do you check first?

**Answer:** whether `-X` actually reached the linker (quoting), and whether importpath.name is exact (`main.version`).

---

### Example 8 — Do not set GOOS in a runtime Deployment as a “fix”

Bad flow:

```text
1. Build on CI without GOOS → windows binary by accident
2. In Kubernetes env: GOOS=linux
3. Expectation: “now it is linux”
4. Reality: the process still tries to run the wrong artifact / image
```

### Predict the result

Does `GOOS` in runtime env change an already-linked binary?

**Answer:** no. `GOOS` affects the **build**. Runtime needs the correct image/artifact.

---

### Example 9 — Combined release line

```powershell
$env:CGO_ENABLED = "0"
$env:GOOS = "linux"
$env:GOARCH = "amd64"
go build -trimpath -ldflags="-X 'main.version=1.4.2' -X 'main.commit=abc123'" -o bin/api ./cmd/api
```

`-trimpath` removes local paths from the binary (see `go help build`) — useful for more reproducible / cleaner artifacts. Use only documented flags.

### What happens here

One line = the team contract: no cgo, linux/amd64, stamped version, explicit output.

### Predict the result

Why log this line in CI?

**Answer:** so a debugger later sees the exact mold (OS/arch/CGO/ldflags), not guesses.

---

### Example 10 — `go run` and GOOS

```powershell
$env:GOOS = "linux"
go run .
```

### Predict the result

What is the trap?

**Answer:** `go run` tries to build **and run** for the target. On a Windows host a Linux target will not execute natively. For cross use `go build`, not `go run`.

## Decision analysis

| Situation | Option A | Option B | Guidance |
|-----------|----------|----------|----------|
| Artifact for Linux from a Windows laptop | Build only in Docker | `GOOS/GOARCH` + `CGO_ENABLED=0` | B for pure Go; Docker when you need CGO/sys root |
| Version in the binary | Hard-code in git | `-ldflags -X` from CI | B for release |
| Platform code | `if runtime.GOOS` everywhere | build tags per file | tags for large differences; runtime if for small ones |
| CGO | Always 1 | 0 until you must | prefer 0 |
| Permanent `go env -w GOOS` | Convenient | You forget | avoid for GOOS |

## Trade-offs

- **CGO_ENABLED=0** — easier deploy/cross; you lose packages that require cgo.
- **Build tags** — cleaner than `#ifdef` chaos; more files and harder to review the “whole” package.
- **`-X` metadata** — great UX for `--version`; bad if it becomes the only config channel.
- **One universal binary** — a dream; reality is a GOOS/GOARCH matrix in release.
- **Reproducibility** vs convenience (timestamp in ldflags).

## Common mistakes

1. Building on a laptop and uploading the host binary as the “server artifact.”
2. Leaving `GOOS=linux` in a PowerShell session then wondering why local `go test` fails oddly.
3. Typo in the `-X` variable name.
4. Two files for the same function without tags.
5. Mixing build env with runtime env in a Kubernetes manifest.
6. Cross-compile with CGO=1 without a C cross toolchain.
7. Relying on blog flags that `go help build` does not know.
8. Forgetting `-tags` on CI for integration tests.
9. Stamping secrets via `-X` (they end up visible in the binary via strings).
10. Assuming `CGO_ENABLED=0` “cures” every native dependency problem in the universe.

## Idiomatic Go

- `cmd/app` + `var version = "dev"` + CI `-X`.
- Platform files: `foo_windows.go` / `foo_unix.go` with `//go:build`.
- Release script logs `go env GOOS GOARCH CGO_ENABLED` and the full build line.
- Pure services: `CGO_ENABLED=0` by default in the Dockerfile build stage.
- Read `go help buildconstraint` once seriously — it saves days.

## Practical scenario

A team ships a CLI. Linux users report “cannot execute binary file.” The artifact was built on a Windows agent without `GOOS=linux`.

Fix:

1. CI matrix or at least explicit `GOOS=linux GOARCH=amd64`
2. `CGO_ENABLED=0` because there is no cgo need
3. `-ldflags -X` for git SHA in `app version`
4. Log build env in job artifacts

Next release: Linux users run the binary; `--version` shows the exact commit.

Second incident: alpine image + CGO enabled by default + glibc dependency → crash on start. Switching to `CGO_ENABLED=0` (pure Go) or the correct base image solves it — but the decision requires understanding the build contract, not “restart the pod.”

## Summary

The build environment is a mold: `GOOS`/`GOARCH` choose the platform, `CGO_ENABLED` the bridge to C, `-ldflags -X` stamps string metadata, build tags choose files. For pure Go, `CGO_ENABLED=0` often makes cross-compile and container deploy simpler. That changes the **artifact on disk**, not the runtime breathing of the process — that is the next topic after building and running.
