# 15.08 Inspecting projects: go list, go doc, and go version -m

> **Go Path - Zero to Gopher** / **02 Intermediate → The Go CLI Playbook** / Lesson 15.08

## Lesson goals

After this lesson you should be able to:

- Use `go list` for insight into packages, imports, modules, and build-relevant fields.
- Read documentation from the terminal via `go doc` (package, type, function, method).
- Extract embedded module information from a binary file with `go version -m`.
- Connect these tools to diagnostics: “what is actually being built”, “which version is in the binary”, “what the package exports”.
- Use `go env` with inspection when you suspect `GOOS`/`GOARCH`, `CGO_ENABLED`, `GOWORK`.
- Not invent flags — rely on `go help list`, `go help doc`, `go help version`.

## Prerequisite

- 15.01–15.07: modules, build, env, workspace, tidy/vendor/verify.
- You have at least one local module and one binary you can build with `go build`.
- A basic feel for package import path vs module path.
- Go 1.22+ recommended (the commands exist earlier; examples target the current flow).

## Problem this lesson solves

A debug session often looks like this: “why doesn’t this file compile?”, “which package even enters the build?”, “which library version is in that docker image?”, “what does that exported type do — I don’t want to open a browser”. People open random files, guess, or trust a README that is outdated.

The Go CLI already has eyes for the project:

- **`go list`** — what the tool sees as packages/modules/files under given build conditions.
- **`go doc`** — what is documented next to a symbol.
- **`go version -m`** — what is embedded in an already built binary (BuildInfo / module info).

Without these commands, project inspection becomes archaeology. With them, you get measurable answers before you change code at random.

## Mental model

Three different questions, three tools:

| Question | Tool |
|---------|------|
| What does the toolchain see now (source)? | `go list` |
| What does the package author say about the API? | `go doc` |
| What is finished in the binary artifact? | `go version -m` |

Picture: `go list` is a warehouse inventory under today’s light (tags, GOOS, cgo). `go doc` is the label on the shelf. `go version -m` is the seal on a closed box that has already shipped.

Important nuance: `go list` respects build constraints, `GOOS`/`GOARCH`, tags, cgo. So “list says the file is not there” often means “it was not selected for this build”, not “the file does not exist on disk”.

## Mechanism

### `go list` — package and module inventory

Basic forms:

```powershell
go list .
go list ./...
go list -m
go list -m all
go list -f "{{.ImportPath}} {{.Dir}}" ./...
go list -json .
```

Default output for packages is the import path. Flag `-f` uses a template over the package structure. Flag `-json` gives a machine-readable form. Flag `-m` switches to module mode instead of packages.

Often useful fields (from `go help list` Package struct — do not memorize all, know where to look):

| Field | Why you look |
|-------|----------------|
| `ImportPath` | who the package is in the tool’s eyes |
| `Dir` | where the sources are |
| `GoFiles` | `.go` files in the package (without tests) |
| `CgoFiles` | files that `import "C"` |
| `IgnoredGoFiles` | ignored because of build constraints |
| `Deps` | dependent packages (when requested) |
| `Module` | the module the package belongs to |
| `Stale` / `StaleReason` | whether install/build would do something |
| `TestGoFiles` / `XTestGoFiles` | test files |

Template examples:

```powershell
go list -f "{{.ImportPath}}: cgo={{len .CgoFiles}} ignored={{len .IgnoredGoFiles}}" ./...
go list -f "{{.ImportPath}} module={{if .Module}}{{.Module.Path}}@{{.Module.Version}}{{end}}" .
go list -deps -f "{{.ImportPath}}" .
```

Note: read the exact set of flags and fields from `go help list` on your version. Do not invent `-magic`. Known useful list flags include `-f`, `-json`, `-m`, `-deps`, `-test`, `-export` (for more advanced flows) — check help before a script.

### `go list` and modules

```powershell
go list -m
go list -m all
go list -m -versions example.com/lib
go list -m -f "{{.Path}} {{.Version}} {{.Dir}}" all
```

With an active workspace (15.06), local modules can appear with a local `Dir` instead of a proxy version. Diagnostics:

```powershell
go env GOWORK
go list -m example.com/auth
```

### `go list` under a different GOOS/GOARCH

```powershell
$env:GOOS = "linux"
$env:GOARCH = "amd64"
go list -f "{{.ImportPath}} files={{.GoFiles}}" .
Remove-Item Env:GOOS
Remove-Item Env:GOARCH
```

Same package, different selected files because of build tags / suffix files (`_windows.go`, `_linux.go`).

With cgo:

```powershell
$env:CGO_ENABLED = "0"
go list -f "cgoFiles={{.CgoFiles}} ignored={{.IgnoredGoFiles}}" .
Remove-Item Env:CGO_ENABLED
```

### `go doc` — documentation from the terminal

```powershell
go doc
go doc fmt
go doc fmt.Println
go doc bytes.Buffer
go doc bytes.Buffer.Write
go doc -all encoding/json
go doc -cmd .
```

Behavior (essence):

- With no arguments: documentation of the package in the current directory.
- For `package main`, exported symbols are hidden by default except with `-cmd`.
- Arguments choose package/symbol/method by search rules described in `go help doc`.
- Useful flags (check help): `-all`, `-c`, `-cmd`, `-short`, `-src`, `-u` (exact set depends on version — read help).

`go doc` is not a substitute for `pkg.go.dev` in all cases, but it is the fastest way to check a signature and comment while you are in the terminal.

### `go version -m` — seal on the binary

```powershell
go build -o greeter.exe .
go version -m greeter.exe
go version -m -json greeter.exe
```

What it does:

- `go version` on a file shows the Go version the binary was built with.
- `-m` adds embedded module information (BuildInfo), indented lines below.
- `-json` (with `-m`) gives the JSON form of `runtime/debug.BuildInfo`.
- On a directory: walks and looks for recognized Go binaries; `-v` also reports unrecognized files.

Typical output contains things like:

```text
greeter.exe: go1.22.x
	path	example.com/greeter
	mod	example.com/greeter	(devel)
	dep	rsc.io/quote	v1.5.2	h1:...
	build	-buildmode=exe
	build	CGO_ENABLED=0
	build	GOOS=windows
	build	GOARCH=amd64
```

(Exact shape depends on version and how it was built.)

When BuildInfo exists: modern Go embeds module info into main packages by default in many flows. If `-m` does not show what you expect, check whether you are looking at the right file, whether it is a Go binary at all, and how it was built.

### Trace 1 — “Why doesn’t this file compile in a linux build?”

```text
go list -f "{{.GoFiles}} | ignored={{.IgnoredGoFiles}}" .
GOOS=linux go list -f "{{.GoFiles}} | ignored={{.IgnoredGoFiles}}" .
```

You see which files enter, which are ignored because of constraints.

### Trace 2 — “Which lib version is in that container?”

```text
docker cp .../app /tmp/app
go version -m /tmp/app
```

Faster and often more accurate than guessing from the image tag.

### Trace 3 — “What does this package even export?”

```text
go doc example.com/auth
go doc example.com/auth.Token
```

### Trace 4 — Workspace vs clean module

```text
go env GOWORK
go list -m example.com/auth
GOWORK=off go list -m example.com/auth
```

### Trace 5 — Version embedded via `-ldflags -X` vs module info

```text
go build -ldflags "-X example.com/app/internal/version.Version=1.4.0" -o app .
go version -m app
# -X value is not a substitute for module lines; that is your variable in the package
```

`-ldflags -X` sets a string in the package. `go version -m` shows BuildInfo/module meta. Both are useful; they are not the same.

## Rules and syntax

### Inspection rules

1. First `go list` / `go env`, then only then changing code “in the dark”.
2. When the build “does not see a file”, check IgnoredGoFiles and tags before you say git is to blame.
3. Check API documentation with `go doc` on the exact module version you use.
4. For forensic version in production — `go version -m` on the artifact.
5. In scripts prefer `-f` or `-json`, not parsing human “pretty” output that is not a stable contract.
6. Do not mix `go list -m` (modules) with `go list` (packages) without intent.
7. With cgo suspicion: `go env CGO_ENABLED` + `CgoFiles` in list output.

### Common commands for a cheat sheet

```powershell
go env GOWORK GOOS GOARCH CGO_ENABLED GOMODCACHE
go list ./...
go list -m all
go list -f "{{.ImportPath}} {{.Dir}}" ./...
go doc fmt.Println
go build -o app.exe .
go version -m app.exe
```

### Build tags with list

```powershell
go list -tags=integration -f "{{.GoFiles}}" ./...
```

`-tags` is a build flag that `list` accepts as part of the build context — see `go help list` / build flags.

## Examples

### Example 1 — List packages in a module

**Predict the result:** What does `go list ./...` print in a module with `package main` and an internal package?

```powershell
go mod init example.com/inspect
mkdir internal\greet
@'
package greet

// Hi returns a greeting.
func Hi(name string) string { return "hello " + name }
'@ | Set-Content internal\greet\greet.go
@'
package main

import (
	"fmt"

	"example.com/inspect/internal/greet"
)

func main() { fmt.Println(greet.Hi("Marko")) }
'@ | Set-Content main.go
go list ./...
```

#### What happens here

The script creates module `example.com/inspect`, an `internal/greet` package with `Hi`, and a `main` package that calls it. `go list ./...` prints the import path of each package under the current directory, one per line. Here those paths are the module root and `example.com/inspect/internal/greet`.

**Answer:** Two import paths — the root package and `example.com/inspect/internal/greet` (exact text depends on layout). `./...` expands to packages under the current module/directory per pattern rules.

### Example 2 — Template with IgnoredGoFiles

**Predict the result:** Does `IgnoredGoFiles` grow when a file has the opposite GOOS?

```powershell
@'
//go:build linux

package greet

func HiLinux() {}
'@ | Set-Content internal\greet\greet_linux.go
$env:GOOS = "windows"
go list -f "go={{.GoFiles}} ignored={{.IgnoredGoFiles}}" ./internal/greet
Remove-Item Env:GOOS
```

#### What happens here

The here-string adds `greet_linux.go` constrained to linux with `//go:build linux`. With `GOOS=windows`, the `go list -f` line prints `GoFiles` and `IgnoredGoFiles` for `./internal/greet`, and the linux file appears in the ignored list. `Remove-Item Env:GOOS` clears the override when the command finishes.

**Answer:** On windows GOOS, the linux-only file should appear among the ignored (or not be in `GoFiles`). That is expected build-constraint behavior, not disk corruption.

### Example 3 — `go doc` on your own API

**Predict the result:** Does `go doc` show the comment above `Hi`?

```powershell
go doc example.com/inspect/internal/greet.Hi
```

#### What happens here

`go doc example.com/inspect/internal/greet.Hi` prints the `Hi` declaration and the documentation comment directly above it. The comment is included only when the source has one. The command reads the package docs; it does not call `Hi`.

**Answer:** Yes — it shows the declaration and the documentation comment. If the comment is missing, you see the signature without a useful description — a signal that the API is not documented.

### Example 4 — `go doc` with no arguments in main

**Predict the result:** Without `-cmd`, do you see all exported symbols of the `main` package?

```powershell
cd (Get-Location) # in the root where package main is
go doc
go doc -cmd .
```

#### What happens here

`cd (Get-Location)` stays in the current directory, which the comment says should be the `main` package. Plain `go doc` documents that package and, for `package main`, shows the package comment and synopsis while leaving other exported symbols out. `go doc -cmd .` includes those exported symbols in the listing.

**Answer:** For `package main`, exported symbols are elided by default; `-cmd` includes them in the presentation. That confuses beginners who expect “like a library package”.

### Example 5 — `go version -m` after a build

**Predict the result:** Does the output mention the module path?

```powershell
go build -o inspect.exe .
go version -m inspect.exe
```

#### What happens here

`go build -o inspect.exe .` writes the current package to `inspect.exe`. `go version -m inspect.exe` prints the Go version that built the file and the embedded module info, including lines such as `path`, `mod`, `dep`, and `build`. The module path appears in that block when the binary came from a module.

**Answer:** Yes — expect a line with the Go tool version and indented module/build lines (`path`, `mod`, `dep`, `build` ...). If there is no module info, check whether the file is really the Go binary you are looking at.

### Example 6 — `-ldflags -X` and inspection

**Predict the result:** Does `go version -m` print the value you injected via `-X` as a separate “Version=” BuildInfo field?

```powershell
@'
package version
var Version = "dev"
'@ | Set-Content version.go
# move into package internal/version if you want; illustration:
go build -ldflags "-X main.Version=1.2.3" -o inspect.exe .
go version -m inspect.exe
```

#### What happens here

The here-string writes `package version` into `version.go` beside `package main`, while `-ldflags` sets `main.Version`. Those package clauses do not match, so this directory does not build until `Version` lives in the package named by `-X`, which is what the comment is flagging. Once that string variable exists, `-X` sets it to `1.2.3` in the binary, and `go version -m` still prints module build info rather than the variable's value.

**Answer:** `go version -m` shows BuildInfo/module/build settings. The `-X` value lives in your variable; you read it from the program or debug symbols, not as a substitute for the module list. (For a clean example use `-X example.com/inspect/internal/version.Version=...` when that variable exists.)

### Example 7 — List package dependencies

**Predict the result:** Does `-deps` include the standard library?

```powershell
go list -deps .
```

#### What happens here

`go list -deps .` prints the current package and every package it depends on, as import paths. Standard-library packages are in that list together with packages from other modules. The output is the package graph, not only the `require` lines from `go.mod`.

**Answer:** Yes, you see both standard packages and module dependencies as package import paths. Use `-f` to filter the display as needed. For module level, `go list -m all` is often clearer.

### Example 8 — JSON for scripts

**Predict the result:** Is `-json` better for automation than the default text output?

```powershell
go list -json . | Select-Object -First 40
go version -m -json inspect.exe | Select-Object -First 40
```

#### What happens here

`go list -json .` emits one JSON document for the current package, and `go version -m -json` emits JSON build info for `inspect.exe`. `Select-Object -First 40` only shortens the PowerShell display. The `-json` shape is what a script can parse without reading the human text format.

**Answer:** Yes — a more stable contract for tools. For people in the terminal, `-f` or ordinary output is more readable. Do not parse average human text with regex in CI if `-json` exists.

## Decision analysis

**`go list` or reading files with your eyes?**  
For build diagnostics — list. Eyes lie when tags are in play.

**`go doc` or browser?**  
While coding — `go doc`. For broader discovery and version history — pkg.go.dev still has a place.

**`go version -m` or git tag of the image?**  
A tag lies when someone overwrites the tag. Binary BuildInfo is closer to the truth of the artifact.

**Template `-f` or `-json`?**  
One-off in the shell — `-f`. Pipeline — `-json`.

**When to add `-tags`?**  
When integration files exist and you want to see the same set that test/build with that tag sees.

## Trade-offs

| Approach | Gain | Cost |
|---------|-------|------|
| Manual tree reading | simple for a micro package | miss constraints |
| `go list -f` | fast, targeted | need to know fields |
| `go list -json` | automation | noisier output |
| Only README versions | easy for people | goes stale |
| `go version -m` on the artifact | forensics | requires access to the binary |

## Common mistakes

1. “File disappeared” — actually IgnoredGoFiles because of GOOS/tag.
2. Mixing `go list` and `go list -m`.
3. Parsing unstable human output in CI instead of `-json`/`-f`.
4. `go doc` in the wrong directory — wrong package.
5. Expecting `go version -m` to show your `-X` string as the module version.
6. Ignoring `GOWORK` when list shows local paths CI does not have.
7. Concluding about cgo without looking at `CgoFiles` and `CGO_ENABLED`.
8. Believing `go doc` executes code — it only reads documentation.
9. Scanning the whole disk with `go version` without intent — slow and noisy.
10. Mixing `go list` results between two Go tool versions without a note.

## Idiomatic Go

- In onboarding README: 5 commands for project inspection (`env`, `list`, `doc`, `test`, `version -m` after build).
- In release checklist: save `go version -m` output for the artifact.
- Document the exported API with comments that `go doc` actually shows.
- For “it won’t build” diagnostics: list + env before a large refactor.
- In scripts for dependency inventory: `go list -m -json all` (check help for the exact JSON shape on your version).
- Do not commit guesses; commit measurements.

## Practical scenario

Incident: production gateway “has an old JWT parser”. Git tag on the image says new. The team loses an hour reading Dockerfile cache. Someone finally does:

```powershell
go version -m .\gateway
```

BuildInfo shows the old `dep` version of the parser. Cause: CI job used a cached layer that did not invalidate module download as they thought. After that:

1. Release checklist must save `go version -m` output as an artifact.
2. On-call runbook: first `version -m`, then only then speculation about the git tag.
3. Locally developers use `go list -m` to confirm what the workspace/module chooses before merge.

Second incident: a windows-only file accidentally without a tag; linux CI fails. `go list` with `GOOS=linux` immediately shows the file enters `GoFiles` where it should not. The fix is a constraint, not “fix the linux VM”.

## Summary

- `go list` shows what the toolchain sees under the build context.
- `go doc` reads documentation comments next to the API.
- `go version -m` reads embedded module/build information from the binary.
- Build tags, `GOOS`/`GOARCH`, `CGO_ENABLED`, `GOWORK` change what you see — that is why list goes with `go env`.
- An artifact does not lie the same way a git tag does; use `-m` in release forensics.
- Do not invent flags; `go help list|doc|version` is the source of truth.

## Additional scenario: wrong package path in doc

A developer writes `go doc auth.Token` but the module is `example.com/auth`. Sometimes it works from the current directory by search rules, sometimes it finds the wrong symbol. Better habit: full import path or `cd` into the package then `go doc Token` / `go doc .`.

## More detailed flow: image forensics

```text
1. Extract the binary from the image
2. go version -m app
3. Compare dep versions with go.mod/go.sum in the git tag that “should” match
4. If they diverge — the problem is the build pipeline, not only runtime config
5. Only then look at GOGC/GOMEMLIMIT/GOMAXPROCS if the theme is latency/memory
```

Runtime env does not change what is linked into the binary. Inventory first, then tuning.

## Automation traps

- `go list ./...` in a directory with generated code can be slow — narrow the pattern.
- JSON schema between Go versions needs a smoke test in the CI script.
- Scanning `go version` over node_modules-like noise makes no sense — target `bin/` or explicit paths.
- `go doc` exits to stdout for people; for machines prefer specific list/json flows.

## Final reminder

Inspect before change. Inventory before incident. BuildInfo before accusing the git tag.

Order when something “doesn’t add up”:

1. `go env`
2. `go list` (+ tags/GOOS as needed)
3. `go doc` if the API is unclear
4. `go test` (15.09) for behavior
5. `go version -m` for what has already gone into the world

## Note on `go list -test` and other flags

`go list` can include test packages and a richer graph — read `go help list` before you script. This lesson deliberately keeps focus on everyday forms: packages, modules, template, json, doc, version -m. Advanced list modes are powerful; without help it is easy to invent a field that does not exist.

## Success metrics

- Incidents last shorter because BuildInfo exists.
- Fewer PRs that “guess” platform files.
- People use `go doc` before asking “what does this function do”.
- Scripts use `-json`/`-f`, not brittle regex.
- Workspace confusion is solved with `GOWORK` + `list -m`, not reinstalling Go.

## Additional angle: what inspection is not

- Not a substitute for a security advisory process.
- Not a substitute for `go mod verify` (15.07).
- Not a substitute for race/cover tests (15.09).
- Not magic that makes c-shared “easy” (15.10).

Inspection is light. After light come decisions.

## Mini decision table in one line

| I want... | I do... |
|---------|----------|
| package inventory | `go list ./...` |
| module inventory | `go list -m all` |
| API comment | `go doc ...` |
| binary seal | `go version -m ...` |
| context | `go env ...` |

## A bit more practice with `-f`

```powershell
go list -f "{{.ImportPath}}`t{{.Doc}}" ./...
```

The `Doc` field is a short package description — useful for generating an inventory of internal packages in markdown (then tidy by hand). Do not expect a novel; expect a signal whether the package even has a package comment.

## Extended lab scenario (incident in three commands)

```text
1) go version -m ./gateway | Select-String "jwt|jwx|parser"
2) go list -m example.com/jwtparser
3) go doc example.com/jwtparser.Parse
```

In 10 minutes you know: what is in the binary, what the module chooses locally, and what the API looks like. Only then open Slack speculation. That is a culture of inspection instead of a culture of guessing.

## Symptom matrix and first commands

| Symptom | First command | Common truth |
|---------|--------------|--------------|
| File “doesn’t compile” but exists | `go list -f "{{.IgnoredGoFiles}}"` | build tag / GOOS |
| Wrong version in production | `go version -m` artifact | cache/image lies |
| Don’t know what the package offers | `go doc package` | README outdated |
| Locally sees a different module | `go env GOWORK` + `go list -m` | workspace desk |
| Suspicion of cgo in the graph | `go list -f` + `CgoFiles` | hidden import "C" |

## Anti-pattern catalog with fix

1. **Screenshot of `go list` without `go env`.** → Always attach GOOS/GOWORK.
2. **Regex over human `go version` output.** → `-json` / stable parser.
3. **Doc from the wrong directory.** → Full import path.
4. **Trusting the git tag of the image.** → Artifact BuildInfo.
5. **Ignore IgnoredGoFiles.** → That is often the whole answer.

## How to write a package comment that `go doc` likes

```go
// Package greet offers short greetings for CLI examples.
//
// Not intended for i18n production.
package greet
```

One paragraph > zero. `go list -f "{{.Doc}}"` can pick up a short description for inventory. If a package has no comment, the inventory looks like a list of streets without names.

## Inventory script (illustration)

```powershell
go list -f "{{.ImportPath}}`tdocs={{.Doc}}`tcgo={{len .CgoFiles}}`tignored={{len .IgnoredGoFiles}}" ./...
```

Save the output to `tmp/inventory.tsv` before a larger refactor. After the refactor compare. Inspection becomes a diff, not a feeling.

## BuildInfo and `-trimpath`

```powershell
go build -trimpath -o app.exe .
go version -m app.exe
```

`-trimpath` reduces local paths in build info / debug context — useful for reproducible releases. Orthogonal to module lines, but belongs to the same discipline of “what is written on the box”.

## When `go doc -src` makes sense

If the signature is not enough and you want to see the body from the terminal, `-src` (when it exists in your version — check `go help doc`) saves a context switch. Still not a substitute for good tests (15.09).

## Closing thought before testing

Inspection says what the system **sees** and what is **embedded**. Test (next lesson) says what the system **does**. Without inspection, you misread test failures. Without a test, inspection is only inventory.
