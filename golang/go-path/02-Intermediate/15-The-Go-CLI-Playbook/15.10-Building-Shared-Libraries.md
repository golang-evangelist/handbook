# 15.10 Building shared libraries: c-shared, c-archive, and //export

> **Go Path - Zero to Gopher** / **02 Intermediate → The Go CLI Playbook** / Lesson 15.10

## Lesson goals

After this lesson you should be able to:

- Explain what `-buildmode=c-shared` and `-buildmode=c-archive` do.
- Write a thin FFI layer with `import "C"` and `//export`.
- Know that these modes require **cgo** (`CGO_ENABLED` must not be 0).
- Measure the cost: artifact size, Go runtime in the host process, GC, debugging.
- Decide when an FFI bridge makes sense, and when HTTP/gRPC side-car, pure Go, or pure C are better.
- Connect the topic with `GOOS`/`GOARCH`, build tags, `-ldflags`, and diagnostics `go version -m` / `go list`.
- Not invent buildmode names — use official values from `go help buildmode`.

## Prerequisite

- 15.01–15.09: especially CGO_ENABLED, build, test, inspecting projects.
- A basic feel for C headers/libraries helps, but the lesson remains useful conceptually too.
- Go 1.22+; C toolchain on PATH if you want a real link (on Windows often mingw or another setup). If you lack a C compiler, still learn the model and the stop signs.
- Read at least superficially the cgo pointer passing rules before production FFI.

## Problem this lesson solves

Management asks: “can we plug a Go library into an existing C/C++/C#/Python monolith?” An engineer turns on `c-shared`, gets a `.so` / `.dll` / `.dylib` / `.a`, then discovers:

- a huge binary because the whole Go runtime goes in;
- interesting problems around threads and GC;
- hard debugging across the language boundary;
- that a simpler path was a side-car process or rewriting a small part.

The lesson gives a map: how the mechanism works, what a minimal example with `//export` looks like, what `CGO_ENABLED` means here, and when to quit before FFI becomes architecture.

## Mental model

Ordinary `go build` makes an **executable program** (`main` + runtime in its own process).  
`c-archive` / `c-shared` make a **library** that another language calls via the C ABI.

1. You write Go with exported functions via `//export Name`.
2. `import "C"` brings in the cgo world (required for this bridge).
3. The toolchain embeds the Go runtime into the library.
4. The host (C/C++/…) loads the library and calls C-compatible symbols.
5. You pay the cost: runtime, GC, and scheduler live inside someone else’s process.

Picture: you are not sending the whole cook as a guest into a restaurant (`main` process). You are embedding a **mini kitchen into their restaurant**. Powerful and invasive.

| Buildmode | Typical artifact | How it is used |
|-----------|------------------|-----------------|
| `c-shared` | `.so` / `.dll` / `.dylib` + header | dynamic loading / link |
| `c-archive` | `.a` + header | static link into the host |

Officially: for `c-shared` and `c-archive` the only callable symbols are functions exported via cgo `//export` comments. Exactly one `main` package is required on the list.

## Mechanism

### `//export`

```go
package main

/*
#include <stdint.h>
*/
import "C"

//export Add
func Add(a, b C.int) C.int {
	return a + b
}

func main() {}
```

Essence of the rules:

- The name after `//export` must match the Go function.
- Types on the boundary should be C-compatible (or carefully translated).
- The `//export` comment sits immediately above the function.
- Often you need an empty `main` because the buildmode requires a main package.
- Strings: `C.CString` allocates; agree who does `C.free`.
- Do not send Go pointers into C to keep them outside cgo pointer passing rules — undefined behavior and crashes.

### Build: c-shared

```powershell
go build -buildmode=c-shared -o greeter.dll .
# Linux typically: -o greeter.so
# macOS typically: -o greeter.dylib
```

What it changes:

- Builds the main package + everything it imports into a C shared library.
- Generates a header (often next to the output) with declarations of exported functions.
- Requires cgo and a C linker toolchain.

### Build: c-archive

```powershell
go build -buildmode=c-archive -o greeter.a .
```

What it changes:

- Makes a C archive suitable for static link.
- Also relies on `//export` as the public callable surface layer.
- On some platforms (e.g. AIX note in help) host link requires additional flags — read `go help buildmode` for the platform.

### `CGO_ENABLED`

```powershell
go env CGO_ENABLED
$env:CGO_ENABLED = "0"
go build -buildmode=c-shared -o x.dll .   # expect fail
Remove-Item Env:CGO_ENABLED
```

These buildmodes **require cgo**. `CGO_ENABLED=0` is excellent for pure Go cross-compile of ordinary binaries, but here it is a stop sign. Cross-building a shared library requires an appropriate C cross toolchain — far harder than `CGO_ENABLED=0 GOOS=linux go build`.

### What enters the host process

When the host loads the library:

- The Go runtime initializes.
- GC may run.
- The Go scheduler and goroutines exist.
- Signal/thread interactions with the host runtime can be sensitive.

This is not “just one function”. It is a nested runtime.

### Trace 1 — Minimal Windows flow

```text
go env CGO_ENABLED   # must allow cgo
go build -buildmode=c-shared -o greeter.dll .
# you get greeter.dll + greeter.h (typically)
# C host includes the header and links/loads the dll
```

### Trace 2 — CGO_ENABLED=0 stop

```text
CGO_ENABLED=0 go build -buildmode=c-shared -o x.so .
→ error / rejection (cgo required)
```

### Trace 3 — Oversized artifact

```text
go build -buildmode=c-shared -o plug.so .
ls -l plug.so   # often much larger than a “small C lib”
# question: is a side-car smaller operationally?
```

### Trace 4 — Test is not enough only in Go

```text
go test ./...           # tests the Go side
# you also need a host call (C program / python ctypes / ...)
```

### Trace 5 — Meta diagnostics

```text
go version -m greeter.dll
go list -f "cgo={{.CgoFiles}}" .
```

### Relationship to ordinary cross-compile

| Goal | Typical approach |
|------|-----------------|
| pure Go CLI for linux from a windows laptop | `CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build` |
| c-shared for another OS | need C cross toolchain + cgo; not the same recipe |

### `-ldflags -X` still works for Go variables

```powershell
go build -buildmode=c-shared -ldflags "-X example.com/plug/internal/version.Version=1.2.3" -o plug.dll .
```

Embeds a string into the Go package. Not magic for C macros. Versioning on the C side you still agree via header/SOVERSION policy.

### Build tags

You can keep FFI files behind tags if you want a pure Go build without cgo in the default flow — but the `c-shared` build itself must see `import "C"` and the exports. Often FFI is in a separate main module/package clearly marked as “glue”.

## Rules and syntax

### Minimal form

```go
package main

import "C"

//export Hello
func Hello() *C.char {
	return C.CString("hello")
}

func main() {}
```

### Design rules

1. Thin C ABI layer — do not export a rich Go API.
2. Document memory ownership (`C.free`).
3. Respect cgo pointer passing rules.
4. Test on the real host language.
5. Measure size and startup before promising a “small plugin”.
6. `CGO_ENABLED` must be on for the build.
7. One main package for `c-shared` / `c-archive`.
8. Prefer simple C types on the boundary (`int`, `*C.char`, lengths with buffers).

### When NOT

- When you can use a process boundary (gRPC/HTTP) and the team operates services better than FFI.
- When you need a tiny C lib without GC.
- When the host already has an unstable threading model that mixes poorly with the Go runtime.
- When nobody on the team can debug across the boundary.

## Examples

### Example 1 — Add via c-shared

**Predict the result:** Does the build pass with `CGO_ENABLED=0`?

```powershell
mkdir plug
cd plug
go mod init example.com/plug
@'
package main

import "C"

//export Add
func Add(a, b C.int) C.int { return a + b }

func main() {}
'@ | Set-Content main.go
go env CGO_ENABLED
go build -buildmode=c-shared -o plug.dll .
```

#### What happens here

The here-string writes a `main` package that imports `C`, exports `Add` under a matching `//export Add` comment, and leaves `main` empty. `go env CGO_ENABLED` prints whether cgo is enabled. `go build -buildmode=c-shared -o plug.dll .` produces `plug.dll` and a generated C header when a C toolchain is available. The same buildmode fails when `CGO_ENABLED` is `0`, because a shared library from Go needs cgo.

**Answer:** With cgo enabled and a C toolchain — expect a library + header. With `CGO_ENABLED=0` — do not expect success. If there is no C compiler, the fail is the environment, not “Go does not support buildmode”.

### Example 2 — c-archive

**Predict the result:** Which file type do you get?

```powershell
go build -buildmode=c-archive -o plug.a .
```

#### What happens here

`go build -buildmode=c-archive -o plug.a .` writes a static archive named `plug.a` and, in a normal cgo build, a header beside it. The host links that archive into its own binary. The C functions it can call are the ones marked with `//export`.

**Answer:** A static archive (and typically a header). The host links it statically. Callable symbols still come from `//export`.

### Example 3 — CString and responsibility

**Predict the result:** Who must free the memory?

```go
//export Hello
func Hello() *C.char {
	return C.CString("hello")
}
```

#### What happens here

`C.CString("hello")` allocates a C string and returns it as `*C.char`. `Hello` returns that pointer and does not free it. The caller has to free the pointer once; a second free, or none, breaks the contract.

**Answer:** `C.CString` allocates on the C heap; the host (or an explicitly documented contract) should call `free` / `C.free`. If nobody frees — a leak. If both sides free — corruption.

### Example 4 — Wrong export name

**Predict the result:** What if the name does not match?

```go
//export Add
func Plus(a, b C.int) C.int { return a + b }
```

#### What happens here

The export comment names `Add`, and the function below it is named `Plus`. cgo accepts the comment only when that name is the function's name and the comment sits directly above the function. This pair does not match, so the cgo tool rejects the file.

**Answer:** This violates the name-matching rule — the toolchain/cgo does not accept it as a valid export pattern. Names must agree.

### Example 5 — go test is not enough

**Predict the result:** Does a green `go test` prove that a C# host loads the DLL?

```powershell
go test ./...
```

#### What happens here

`go test ./...` builds and runs the Go tests under this module. A passing line means those tests succeeded. The command does not start a C# process or load the shared library into a host.

**Answer:** No. That tests the Go side. The FFI contract is proven by a host call (even a minimal C `main`).

### Example 6 — version -m on the artifact

**Predict the result:** Can `go version -m` show buildmode?

```powershell
go build -buildmode=c-shared -o plug.dll .
go version -m plug.dll
```

#### What happens here

The first command builds `plug.dll` with `-buildmode=c-shared`. `go version -m plug.dll` reads the build info stored in that file. The settings it prints commonly include the buildmode and `CGO_ENABLED`, along with the module lines.

**Answer:** On a Go-built artifact you often see build lines including buildmode and `CGO_ENABLED`. Use that in release forensics (15.08).

### Example 7 — Pure Go cross-compile contrast

**Predict the result:** Does the same `CGO_ENABLED=0` recipe work for c-shared?

```powershell
$env:CGO_ENABLED = "0"
$env:GOOS = "linux"
$env:GOARCH = "amd64"
go build -o app-linux .
go build -buildmode=c-shared -o app.so .
Remove-Item Env:CGO_ENABLED
Remove-Item Env:GOOS
Remove-Item Env:GOARCH
```

#### What happens here

The session sets `CGO_ENABLED=0`, `GOOS=linux`, and `GOARCH=amd64`. `go build -o app-linux .` is a pure-Go cross-compile and can succeed with cgo off. `go build -buildmode=c-shared -o app.so .` needs cgo, so it does not succeed under the same variables. The three `Remove-Item` lines then clear those variables.

**Answer:** The first (ordinary exe) is classic pure Go cross-compile. The second does not pass by the same recipe because c-shared requires cgo.

### Example 8 — Thin API better than rich

**Predict the result:** Why is it better to export `Process(buf *C.char, n C.int) C.int` than a whole Go `struct` graph?

```text
rich Go API across the boundary → lifecycle hell
thin buffer/status API → clearer contract
```

#### What happens here

The text contrasts a wide Go API handed across the boundary with a single function that takes a C buffer and length and returns a status code. Go structs and slices do not have a C layout the host can free and keep. The thin signature leaves allocation and the object graph inside Go, and the host only sees a pointer, a length, and an integer.

**Answer:** Because the C ABI and memory ownership become hell when you “sell” Go structures and slice semantics across the boundary. Keep the bridge thin.

## Decision analysis

**c-shared or c-archive?**  
Dynamic loading / plugin feel → shared. Embedding into one host binary without a separate .so deploy → archive. Platform and team deploy model decide.

**FFI or side-car?**  
FFI: low latency in the same process, tighter coupling. Side-car: clearer boundaries, easier deploy/restart, more IPC cost.

**Go in a C host or C in Go (ordinary cgo)?**  
This lesson is “Go as a library for C”. The reverse direction (Go calls C) is the more common everyday cgo case — a different story, similar runtime cost.

**When to quit?**  
If a 50MB+ artifact scares the embed team, if there is no C toolchain discipline, if nobody will support pointer rules — quit early.

## Trade-offs

| Approach | Gain | Cost |
|---------|-------|------|
| `c-shared` | one process, C ABI | runtime in the host, size, debug |
| `c-archive` | static link | larger host binary, link complexity |
| Side-car gRPC | clean boundaries | IPC, ops |
| Rewrite in C | no Go runtime | time, bugs |
| Pure Go service | idiomatic flow | not a “plugin into a monolith” |

## Common mistakes

1. `CGO_ENABLED=0` then wondering why c-shared fails.
2. Expecting a “small” library like from C.
3. Leak because of `C.CString` without `free`.
4. Holding Go pointers in C structures outside the rules.
5. Rich export API instead of a thin ABI.
6. Testing only with `go test`.
7. Cross-compile recipe from pure Go copied onto c-shared.
8. Ignoring runtime init cost on load.
9. Mixing `plugin` buildmode (Go plugin) with `c-shared` (C ABI).
10. Commit without documentation of who frees memory.

## Idiomatic Go

- Separate small module/package for glue.
- Thin `//export` surface.
- README: how to build, which C toolchain, how to free.
- CI builds the library on a platform where the toolchain exists; do not lie that it “works everywhere”.
- Measure artifact size in CI as smoke.
- Use `go version -m` in the release record.
- Prefer a side-car until FFI has a clear ROI.
- For ordinary services stay on `CGO_ENABLED=0` policies where you can.

## Practical scenario

A company wants Go ML preprocess in an old C++ pipeline. The team makes `c-shared`. The artifact is tens of MB. Load time bothers batch jobs. One bug: C++ holds a Go string pointer after return — intermittent segfault. After two incidents they move to a gRPC side-car: the same Go code as `main`, C++ calls over the network. Latency rises a little; operational stability more. FFI remains only for one ultra-hot path where measurements prove the need — and there the API is three functions, without string pointer escape.

## Summary

- `c-shared` and `c-archive` package Go (with runtime) as a C library.
- Public symbols come from `//export`; cgo is required.
- `CGO_ENABLED=0` is a stop; cross-build is not like pure Go.
- Cost: size, GC/threads in the host, debug, memory contracts.
- Thin ABI + host tests + clear memory rules.
- Often a side-car is the better production answer.

## Additional scenario: Python ctypes

A team loads `c-shared` from Python. Works in a demo. In production multi-thread Python + Go runtime leads to rare crashes. Without a person who understands both runtimes, MTTD grows. Conclusion: demo ≠ production; FFI requires ownership.

## More detailed flow: from idea to stop/go

```text
1. Define 3 or fewer C functions you really need
2. Prototype //export + c-shared on one platform
3. Measure size and load time
4. Write a host smoke test
5. Pass the pointer/mem checklist
6. If metrics hurt — side-car
7. If they pass — only then multi-platform CI
```

## Extended example: header as contract

After the build open the generated `.h`. That is the surface the host sees. If the header “leaks” Go details — the API is too rich. Aim for C types and clear names.

## Extended example: build tags for two modes

Some teams keep:

- a library `package` as pure Go for ordinary import;
- a separate `cmd/plug` main only for `c-shared`.

That way ordinary consumers of the Go module do not pull cgo. Shared glue is a separate artifact.

## Extended example: ldflags trimpath

```powershell
go build -trimpath -buildmode=c-shared -o plug.dll .
```

`-trimpath` helps reproducibility of paths in meta data — useful with release discipline.

## Final reminder

FFI is a runtime invasion. Do it when measurements say you must. Otherwise: process boundary.

Decision order:

1. Can it be a side-car?
2. Can it be pure C or pure Go?
3. If not — thin `//export`, cgo on, host tests, memory contract.
4. Measure size and stability before scale.

## Note on WASI / wasmexport

Help for `c-shared` mentions a special wasip1 case with `//go:wasmexport`. That is not the focus of this lesson. If you work with WASI, read current Go documentation for that platform — do not mix it with the classic C ABI DLL/SO flow.

## Closing scenario: “just one export”

The team says: “just one function, it’ll be easy”. After six months: 40 exports, strings, callbacks in both directions, custom allocator. Nobody dares to raise the Go version. Lesson: controlling API surface is controlling fate. Start small; keep it small.

## Success metrics

- People know that c-shared ≠ pure Go cross-compile.
- FFI decisions have a checklist, not only enthusiasm.
- A host test exists in CI or the decision “we don’t do FFI” stands in the README.
- Artifact size does not surprise in production.
- Side-car is considered without shame.

## More on the debug experience

When the host crashes:

1. Establish whether the stack crosses the Go/C boundary.
2. Check recent change on `//export` signatures.
3. Check the memory contract.
4. Try reproduction with `GOMAXPROCS=1`.
5. If you cannot debug reliably — that is an architecture signal, not only a “lack of tools”.

## Symptom matrix and first checks

| Symptom | First check | Common truth |
|---------|--------------|--------------|
| Buildmode fail | `go env CGO_ENABLED` | cgo disabled |
| No C compiler | toolchain PATH | environment, not a Go myth |
| Segfault after return | pointer escape / lifetime | Go pointer in C |

## Anti-pattern catalog with fix

1. **40 exports “temporarily”.** → Surface budget; review breaks growth.
2. **Only `go test`.** → Host smoke in CI.
3. **Copy the pure Go cross-compile recipe.** → C cross toolchain or native build.
4. **Callback hell in both directions without rules.** → Simplify the contract or side-car.
5. **Silence about GC pauses.** → Measure in the host process or do not enter that process.

## What to write in the glue module README

```text
# plug (c-shared glue)

Build:
  # requires CGO_ENABLED=1 and a C toolchain
  go build -buildmode=c-shared -o plug.so .

Memory:
  Hello() returns a C string; host calls free.

Do not:
  CGO_ENABLED=0 cross-compile recipe from ordinary services.

Alternative:
  cmd/plugd — gRPC side-car if FFI is not approved.
```

Short, strict, without marketing.

- They hear “DLL/so”. You hear “Go runtime in their process”.

- If they lack tooling for mixed-stack debug — raise the risk in writing.

## Closing thought for the whole CLI playbook

You have been through environment, build, module hygiene, workspace, inspection, test, and the boundary toward the C ABI. The Go CLI is not a collection of tricks — it is the operational language of the project. When you stall, ask:

1. What does `go env` say?
2. What does the module/workspace choose?
3. What do list/doc/version show?
4. What does the test prove?
5. Do you even need to cross a language boundary?

## Additional trace: init and shutdown

Host loads the library → Go runtime init. Host unloads the library → questions about clean shutdown can be platform-sensitive. Do not assume “dlclose then forget” is always safe with GC and background goroutines. If you need dynamic unload, read current Go/cgo documentation for your version and test on the real OS. Many teams choose: load once, live with the process.

## Additional trace: signals and threads

The Go runtime has its own relationship to signals and threads. A host that already installs signal handlers or mixes many native threads can enter a gray zone. That is not a reason to panic in every demo — it is a reason for caution in a production process that already has a complex native runtime (e.g. some app servers). Side-car wins again when you do not want to share signal fate.

## Additional trace: Go tool versions in FFI CI

Pin the Go tool version in CI for the glue module. Raising the Go version is not “just tidy” when you ship a `.so` to a third party — it is a runtime change in their process. Release notes must mention a Go runtime bump the same as an API bump.

## Five questions for an architecture review

1. What is the loss if FFI disappears tomorrow?
2. How many MB may the artifact be?
3. Who debugs a mixed stack at 3 a.m.?
4. May the host allow GC pauses?
5. Do we already have a side-car plan B written?

If the answer to any question is “I don’t know” — it is not go yet.

## Final reminder (once more)

`c-shared` and `c-archive` are not “just another `go build` flag for fun”. It is a decision that the Go runtime lives in someone else’s process. `//export` is a contract. `CGO_ENABLED` is the ticket. Host test is the proof. Side-car is often the smarter exit.

When you finish this lesson, return to the 15.02/15.03 mental model: `CGO_ENABLED=0` remains the hero for clean services. Here the heroic status is consciously revoked — because the bridge to the C ABI requires cgo.
