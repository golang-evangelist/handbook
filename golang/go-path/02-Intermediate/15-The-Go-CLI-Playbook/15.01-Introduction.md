# 15.01 The `go` command as a toolchain, not a single program

> **Go Path - Zero to Gopher** / **02 Intermediate → The Go CLI Playbook** / Lesson 15.01

## Lesson goals

After this lesson you should:

- see `go` as a **family of subcommands** (build, test, mod, list…), not as a single “compiler”
- distinguish the **toolchain** from the **language** and from the **runtime**
- know where the cache lives, where modules live, and how `go env` reveals the real environment
- run `go help` and `go help <topic>` as the first reflex instead of guessing
- connect this lesson to the rest of the playbook: build environment, projects, tests, libraries
- recognize when the problem is not in the code but in the **contract with the toolchain** (version, PATH, module)
- read the subcommand map well enough to know **where to start** when something gets stuck

## Prerequisite

- Go 1.22+ installed; `go version` shows the version
- basic `package main`, `go mod init`, running a simple program
- preferred: an introduction to modules (`go.mod`) and tests (`*_test.go`)
- a terminal (PowerShell, bash, or similar) where you can change directories and read command output
- a basic feel for PATH and what “command not recognized” means

## Problem this lesson solves

Many programmers treat the Go CLI as a set of unrelated scripts: “`go build` makes a binary, `go test` tests, `go get` pulls packages.” When something gets stuck — wrong `GOPATH`, old cache, wrong `GOOS`, missing module — they react at random: delete folders, change PATH, copy commands from forums without understanding the context.

The real problem is not “I don’t know the flag.” The problem is the **mental model**: what `go` actually does, which subcommands share the same assumptions, and where to look for diagnostics. Without that, every following lesson (build tags, workspace, `go list`) feels like magic.

Typical symptoms of this gap:

- “It works on my machine, not on CI” — and nobody compared `go version` or `go env`
- “Dependency vanished” — and `go.sum` is not in the repo, or `replace` points at a colleague’s local path
- “Build is slow” — and the team clears the cache every time “just in case”
- “I don’t know where the binary is” — `go run`, `go build`, and `go install` get mixed without intention
- “`go` is not recognized” — PATH points at an old or empty install

This lesson sets up a **map**: one `go` binary, many subcommands, a shared cache and a shared understanding of modules. Once you have the map, flags become tools, not rituals.

## Mental model

Imagine `go` as a **factory control panel**, not as a single machine.

1. **Input** is source files and `go.mod` (what the module requires). Without a clear input, the factory guesses or gives up.
2. **Workshops** are the subcommands: `build`, `test`, `run`, `install`, `mod`, `list`, `doc`, `env`…
3. **Storage** is the module cache (`GOMODCACHE`) and the build cache (`GOCACHE`). Already-finished work lives there.
4. **Output** is binaries, test reports, documentation, JSON from `go list`.
5. **Satellites** are tools that `go` can run (`go vet`, `go tool`, external linters via `go run`).

Three layers people often mix up:

| Layer | What it is | Example |
|------|--------|--------|
| Language | specification, types, semantics | `goroutine`, `interface`, `slice` |
| Runtime | behavior in the process | GC, scheduler, `GOMAXPROCS` |
| Toolchain + CLI | turning source into artifacts | `go build`, `go test`, `go env` |

The CLI is the entry into the toolchain. That is why one environment mistake can break **multiple** subcommands at once: a wrong `GOOS` affects both `build` and `test` if you run them that way.

Another picture: `go` is an **orchestra conductor**. You do not call `compile` directly for everyday work; the conductor chooses who plays (compiler, linker), in what order, and whether an already-played passage can be skipped (cache).

A third picture: a **city map**. `go help` is the street index. `go env` is the GPS that says where you actually are. `go version` is the year label on the map. Without those three, you wander forums.

## Mechanism

### One binary, multiple entry points

When you type `go build`, the `go` process reads arguments, loads configuration from the environment (`go env`), finds the module, plans what to compile, uses the cache when it can, and calls the compiler and linker. The same package-sharing logic applies to `go test` and `go run` — what differs is the goal and lifecycle, not “another Go installation.”

That is why learning “only build” without `env`/`list` leaves blind spots: you do not see what the conductor **thinks** needs to be played.

Trace of a typical call:

```text
1. Shell finds `go` on PATH
2. `go` parses the subcommand (e.g. build)
3. Reads the effective environment (GOOS, GOARCH, GOCACHE, GOMODCACHE, …)
4. Finds go.mod / go.work in the directory tree
5. Builds the package graph it needs
6. Looks in GOCACHE for already-compiled objects
7. Compiles what is missing, links main (if needed)
8. Writes output (binary, test result, temporary file for run)
```

If step 1 fails — PATH. If step 3 lies — wrong env. If step 4 fails — you are not in a module. Most “magical” bugs live in steps 1–4, not in language syntax.

### Where `go` looks for the truth

- `go env` — effective values (`GOROOT`, `GOPATH`, `GOMODCACHE`, `GOCACHE`, `GOOS`, `GOARCH`…)
- `go version` — which toolchain version is running
- `go help` / `go help build` — built-in documentation; often more accurate than a random blog
- working directory — whether you are inside a module (`go.mod`) or a workspace (`go.work`)

If something “isn’t right,” ask the toolchain for the truth first. Do not ask Stack Overflow before you read `go env GOVERSION` and `go list -m`.

### `go version` — who is actually working

```text
go version
```

Output typically looks like:

```text
go version go1.22.5 windows/amd64
```

What you read:

1. **language/toolchain version** (`go1.22.5`) — matters for features and bug fixes
2. **host platform** (`windows/amd64`) — what that `go` **runs on**, not necessarily what you are building for

`go env GOVERSION` often gives similar information in a script-friendly format. In CI always log the version at the start of the job.

Trace when “it works on my machine”:

```text
Local:  go version go1.22.5 windows/amd64
CI:     go version go1.21.0 linux/amd64
```

A difference in a minor version can change default module behavior, API availability, or fixes. Without a comparison you are guessing.

### `go help` — the built-in manual

```text
go help
go help build
go help environment
go help go.mod
```

`go help` without arguments lists subcommands and short descriptions. `go help <topic>` gives details for that subcommand or topic. This is not marketing copy — it is documentation that ships with **your** installation, so it matches the flags you actually have.

Habit:

1. Before you copy a flag from a blog → `go help <cmd>`
2. Before you “guess” an env variable name → `go help environment` (or `go env`)
3. Before you change `go.mod` manually blind → `go help go.mod` / `go help modules`

### `go env` — the effective environment map

```text
go env
go env GOROOT GOPATH GOMODCACHE GOCACHE GOOS GOARCH GOVERSION
go env -json GOOS GOARCH
```

What you change / what you read:

| Key | Meaning (high level) | Typical touching |
|-------|------------------------|-----------------|
| `GOROOT` | where Go is installed | rarely; do not mix with the project |
| `GOPATH` | older workspace + `bin` | often only for `GOPATH/bin` on PATH |
| `GOMODCACHE` | cache of downloaded modules | delete only with a reason |
| `GOCACHE` | build cache | delete only with a reason |
| `GOOS` / `GOARCH` | build target | deliberately for cross-compile |
| `CGO_ENABLED` | whether cgo is allowed | deliberately for static-ish / cross |

`go env` without arguments prints the full list. With key names — only those. That is handy for scripts and for a clean screenshot in a bug report.

Important: `go env` shows **effective** values — what the toolchain sees after defaults + env + (where present) configuration. That is not the same as “what the docs say for some other machine.”

### The cache is not an optional “optimization”

The build cache speeds up rebuilds. The module cache stores downloaded modules. If something mysteriously behaves differently on two machines, the difference is often in the cache, Go version, or `replace` directives — not in compiler magic.

The cache is a **contract for speed**, not a source of truth. Truth is source, `go.mod`, `go.sum`, and the effective environment.

Trace of a “mysterious” success:

```text
1. go build  → uses an object from GOCACHE
2. You change only a comment → cache hit still possible for some packages
3. You change a go.mod dependency → different graph, different download in GOMODCACHE
4. You clear GOCACHE “just in case” → slower build, same result if the input is the same
```

That is why clearing the cache is not diagnosis — it is a performance reset. Diagnosis is: compare the input (`go env`, `go list`, `go.mod`).

### Subcommands by family

| Family | Typical commands | Job |
|----------|-----------------|--------|
| Building | `build`, `run`, `install`, `clean` | artifacts and running |
| Quality | `test`, `vet`, `fmt` | checking behavior and style |
| Modules | `mod tidy`, `mod download`, `mod vendor` | dependencies |
| Insight | `list`, `doc`, `env`, `version` | diagnostics |
| Tools | `tool`, `generate` | generation and helper tools |

This map tells you **where to start** when something does not work: first `env`/`version`, then `list`, and only then build flags.

### Subcommand map — what to expect

A short guide to what you see in `go help` (not an inventory of every flag — an inventory of **intent**):

**Building and running**

- `go build` — compiles; leaves a binary (for `main`) on disk
- `go run` — compiles to a temporary location and executes immediately
- `go install` — compiles and places into `GOBIN` or `GOPATH/bin`
- `go clean` — removes files the toolchain left in the contexts it supports

**Quality checks**

- `go test` — builds and runs tests
- `go vet` — static checks for suspicious constructs
- `go fmt` / `gofmt` — source formatting

**Modules and dependencies**

- `go mod init` — new `go.mod`
- `go mod tidy` — aligns `go.mod` / `go.sum` with imports
- `go mod download` — downloads modules into the cache
- `go get` — changes dependency requirements (in module mode)

**Insight**

- `go list` — machine-readable view of packages/modules
- `go doc` — documentation for types and packages
- `go env` — effective environment
- `go version` — toolchain version

**Other things you see early**

- `go generate` — runs `//go:generate` directives
- `go work` — workspace (`go.work`) for multiple local modules (later in the playbook)

You do not have to memorize everything today. You must know the **family** and open `go help <name>` when you need detail.

### Flow of a typical day

1. Enter the repo → check that you are in the right directory.
2. `go version` / `go env GOVERSION` — whether it is the expected toolchain.
3. `go test ./...` or a narrower package — signal whether it is a green day.
4. `go run ./cmd/...` for a local try.
5. `go build -o bin/...` when you need an artifact.
6. If something breaks → `go env`, `go list`, `go help <cmd>`.

That is not ceremony. That is hygiene that saves hours.

### Trace: “command not found” on Windows

```text
1. You open PowerShell
2. You type: go version
3. Error: 'go' is not recognized...
4. Check: where.exe go   (or Get-Command go)
5. If empty → Go is not on PATH for this shell
6. Install exists e.g. C:\Program Files\Go\bin\go.exe but PATH was not refreshed
7. New terminal / PATH fix → go version works
```

The problem is not “Go is broken.” The problem is the **shell does not see the binary**. The toolchain starts only once `go` is found.

### Trace: two Go installations

```text
1. go version → go1.21.0
2. C:\Program Files\Go\bin\go.exe version → go1.22.5
3. where.exe go → first path is the older one
4. PATH order chooses which go “wins”
```

That is why in a bug report you always put the full `go version` output and, when needed, `where go` / `which go`.

### The module as an input contract

Without `go.mod` (in modern mode), the toolchain has no clear module path and dependency versions. With `go.mod`:

```text
module example.com/hello

go 1.22
```

`go list -m` confirms the module. `go build` knows where to pull dependencies from. `replace` and `exclude` in `go.mod` change the graph — so “the same code” on two machines is not the same if `go.mod`/`go.sum` are not the same.

### Workspace (`go.work`) — just awareness that it exists

If `go.work` exists in the tree, the toolchain can use multiple local modules together. Details are in a later lesson; here remember: `go env GOWORK` shows whether a workspace is active. If “local replace works for a colleague but not for you,” also check `go.work`.

### What the CLI does **not** do

- It does not replace runtime tuning (`GOGC`, `GOMEMLIMIT`) — that is another lesson.
- It does not replace package design — a bad API stays bad after `go fmt`.
- It does not guarantee the binary is “portable” if you enabled CGO without a plan.
- It does not keep secrets — `go env` can reveal paths; do not log sensitive data.

### Deeper trace: from `go test` to output

When you type `go test ./pkg`:

```text
1. Shell → go
2. Subcommand test
3. go env (effective) loaded
4. Module / workspace found
5. Packages matching ./pkg selected
6. Test binary assembled (with test files)
7. Cache used where possible
8. Test process started
9. Result (PASS/FAIL) on stdout; exit code != 0 on failure
```

Notice the similarity with `build`: steps 1–5 are the shared “entry into the factory.” The difference is what gets linked and what gets run. That is why a wrong module breaks both test and build.

### Deeper trace: `go mod tidy`

```text
1. Reads go.mod and sources
2. Builds the set of needed dependencies from imports
3. Adds / removes requirements in go.mod
4. Updates go.sum (checksums)
5. May download into GOMODCACHE if missing
```

`tidy` does not “fix the internet.” It aligns the module contract with actual imports. If CI has no network and the cache is empty, download can still fail — that is an ops problem, not tidy magic.

### GOROOT vs the project

`GOROOT` is the installation of the standard library and tools. Your project should **not** live in `GOROOT`. If someone copies files into `GOROOT/src`, that is an anti-pattern from ancient times. Modern flow: anywhere on disk + `go.mod`.

Check:

```powershell
go env GOROOT
# your repo is NOT this folder
```

### GOPATH today

`GOPATH` still exists. It is often used for:

- `GOPATH/bin` — where `go install` places tools if `GOBIN` is not set
- compatibility with older material

You do not have to keep source in `GOPATH/src` for module projects. But you must know that `$(go env GOPATH)/bin` is often on a developer’s PATH — that is why `go install` “suddenly works as a command.”

### `go env -w` awareness (without abuse)

The toolchain supports more persistent user defaults via `go env -w` (see `go help env`). That changes **default behavior** for future calls by that user. Use carefully:

- good: local `GOBIN` to a known path
- bad: permanent `GOOS=linux` on a Windows laptop “because production” — you forget and every local build becomes Linux

For a one-off cross-compile prefer a temporary env in the shell (next lesson) rather than permanent `-w`.

### How to read a compiler error with CLI context

Message:

```text
package example.com/hello/internal/db: no Go files in ...
```

CLI context asks:

1. Does `go list` see that package?
2. Are you in the right module (`go list -m`)?
3. Do build tags exclude all files? (15.02)
4. Is the directory empty / wrong checkout?

Without CLI context, people “reinstall Go.” With context, they look at the folder.

### IDE ↔ CLI relationship

The IDE Run button usually does something equivalent to `go run` or a debug build. If the IDE works and the terminal does not:

```text
1. Compare go version in the IDE terminal vs the external shell
2. Compare working directory
3. Compare env (GOOS, GOPATH, GO111MODULE…)
4. Run the same command the IDE logs
```

Team goal: everything that is “green in the IDE” must also be green with a documented CLI command.

| Term | Meaning here |
|--------|----------------|
| Toolchain | `go` + compiler + linker + tracked tools |
| Module | version unit with `go.mod` |
| Package | directory of `.go` files with the same `package` |
| Artifact | binary / library result of a build |

Remember host vs target: on Windows you can build a Linux target (with CGO limits) — that is 15.02.

## Rules and syntax

```text
go <subcommand> [flags] [packages or files]
```

- Packages are often given as paths: `.`, `./...`, `example.com/mod/pkg`.
- Many subcommands accept `-n` (show what it would do) and `-x` (show the commands it executes) — useful for learning; read `go help build` to see which flags that subcommand actually has.
- `go help` without arguments lists subcommands; `go help <name>` gives details.
- Inside a module, relative paths (`./cmd/api`) are common; outside a module the older GOPATH mode is rare on 1.22+.
- Do not mix “install Go” with “install my program”: `go install` for your packages goes to `GOBIN`/`GOPATH/bin`.

Conventions worth remembering immediately:

1. Always check `go version` and `go env GOVERSION` on CI and locally.
2. Work inside `go.mod` (or `go.work`) — that is the default way of working.
3. For diagnostics: `go env` → `go list` → only then flags.
4. Do not clear the cache as the first step; first understand **why** the build is using the wrong input.
5. Write commands in the README exactly as CI executes them.
6. For a bug report: `go version`, relevant `go env`, `go list -m`, and the exact command that fails.

Short note on `./...`:

- Means “this package and everything below in the tree.”
- In a large monorepo it can run more than you think (generated code, experiments).
- That is why CI often uses explicit paths or `go list` filters.

## Examples

### Example 1 — First reflex: version, help, env

```powershell
go version
go help
go help build
go env GOROOT GOPATH GOMODCACHE GOCACHE GOOS GOARCH
```

### What happens here

`go version` confirms which toolchain is actually running (important if you have multiple installs). `go help` gives the subcommand map. `go help build` explains build flags without leaving the terminal. `go env` with a list of keys prints only what you need — less noise than a full `go env`.

On Windows in PowerShell the same patterns work; differences are mostly in paths and the binary name (`.exe`).

### Predict the result

If you run `go env GOOS GOARCH` on a Windows laptop with an amd64 CPU, what do you expect (typically)?

**Answer:** something like `windows` and `amd64` (each key on its own line, or the format `go env` uses for a list). That is the **host default** for the build until you change `GOOS`/`GOARCH`.

---

### Example 2 — Small module and `go run` vs `go build`

```go
// file: hello/main.go
package main

import "fmt"

func main() {
	fmt.Println("toolchain works")
}
```

```powershell
mkdir hello
cd hello
go mod init example.com/hello
# save main.go
go run .
go build -o hello.exe .
.\hello.exe
```

### What happens here

`go mod init` creates the module contract. `go run .` compiles to a temporary output and runs immediately — handy for trying things. `go build -o hello.exe .` leaves a binary on disk. Same foundation (module + `main` package), different output lifecycle. That is the essence of the CLI: **same factory, different output channels**.

If you omit `-o`, the binary name follows the package/directory convention — learn that convention, but in CI always be explicit with `-o`.

### Predict the result

After `go run .`, do you expect a lasting `hello.exe` in the folder?

**Answer:** no. `go run` uses a temporary artifact. A lasting file comes from `go build` (or `go install` into `GOBIN`).

---

### Example 3 — `go list` as an X-ray instead of guessing

```powershell
go list -m
go list -f "{{.ImportPath}} {{.Dir}}" .
go list ./...
```

### What happens here

`go list -m` says what the current module is. The `-f` format prints the fields you need (import path, directory on disk). `./...` lists packages in the tree. When someone says “it can’t find the package,” `go list` often shows you are in the wrong dir or the package is not in the module.

### Predict the result

If you are not in a directory with `go.mod` (and do not have one in parents), what does `go list -m` typically do?

**Answer:** it reports an error that you are not in module-aware mode / there is no `go.mod` (exact message depends on version). Signal: you are not where you think you are.

---

### Example 4 — `go help` before copying from a forum

Someone proposes a nonexistent flag. You do:

```powershell
go help build
```

and search for the flag in the text.

### What happens here

Built-in help is the source of truth for **your** `go`. A blog for Go 1.18 can lie about Go 1.22. If the flag is not in `go help build`, do not “try blindly” — check whether it is another subcommand or another version.

### Predict the result

Does `go help` require a network?

**Answer:** no. It is local toolchain documentation.

---

### Example 5 — Compare local and CI (checklist)

At the start of the CI log and locally capture:

```powershell
go version
go env GOVERSION GOOS GOARCH GOMODCACHE GOCACHE
go list -m
```

### What happens here

Three lines of diagnostics eliminate half of “works on my machine” bugs: version, platform, module. If `go list -m` differs, maybe the CI checkout is not the same repo root.

### Predict the result

CI is `linux/amd64`, laptop `windows/amd64`. Does that by itself mean a binary from the laptop will run on the CI runner?

**Answer:** no. Host platforms differ; for a Linux artifact you build with `GOOS=linux` (next lesson) or you build **on** Linux.

---

### Example 6 — `-n` and `-x` as learning (where they exist)

```powershell
go build -n .
go build -x -o hello.exe .
```

Read `go help build` to confirm meaning: `-n` prints commands without executing; `-x` prints while executing.

### What happens here

You see how the conductor calls the compiler/linker and which paths it uses. That demystifies the “black box” without reading the compiler source.

### Predict the result

Must `go build -n .` leave a new binary?

**Answer:** it should not — `-n` is a dry run (print only). Check the help if you are unsure for the exact version.

---

### Example 7 — PATH error vs code error

```powershell
go version
# if it fails: shell environment problem
# if it works:
cd hello
go build .
# if it fails here: project / code / module problem
```

### What happens here

You separate the layer: whether the toolchain exists at all, or the project does not build. Beginners mix these two and “reinstall Go” because of an error in `main.go`.

### Predict the result

Message `package main: no Go files` — is that “Go is not installed”?

**Answer:** no. The toolchain works; there are no `.go` files in the directory (or you are in the wrong dir).

---

### Example 8 — Filtered `go env` for a bug report

Bad bug report:

```text
build does not work
```

Better:

```powershell
go version
go env GOVERSION GOOS GOARCH CGO_ENABLED GOMODCACHE
go list -m
go build -o bin/app .
# + exact error
```

### What happens here

Five commands give the context a mature engineer expects. Without that, the reviewer guesses platform and version.

### Predict the result

Should you paste the **entire** `go env` into every ticket?

**Answer:** not necessarily. Often a filtered set of keys + version + command is enough. Full `go env` when you suspect a weird `GOROOT`/`GOCACHE`/`GOWORK`.

---

### Example 9 — `go doc` alongside CLI learning

```powershell
go doc fmt.Println
go doc os.Getenv
```

### What happens here

While learning the standard library, `go doc` is faster than the browser and tied to the **installed** version. That is the same toolchain spirit as `go help`: local truth.

### Predict the result

`go doc` for a nonexistent identifier — what do you expect?

**Answer:** an error / message that it was not found. Signal that you got the package or symbol name wrong, not that the network is down.

---

### Example 10 — `go fmt` as hygiene, not as a feature

```powershell
go fmt ./...
```

### What happens here

Formats packages in the tree. It is not a style debate in the Go community — `gofmt` is a contract. The CLI playbook includes these “boring” commands too because they are part of the same `go` binary.

### Predict the result

Does `go fmt` change program behavior at runtime?

**Answer:** it should not — it only changes source whitespace/format. Semantics stay; a git diff is expected.

---

### Example 11 — Interpreting the `go version` line

Sample output:

```text
go version go1.22.5 windows/amd64
```

### Predict the result

What is the host, and what is a potential target?

**Answer:** `windows/amd64` describes the toolchain host. The target for cross-compile is set separately via `GOOS`/`GOARCH` (15.02). Without changing env, the build targets the host.

---

### Example 12 — Module path vs folder

```powershell
go mod init example.com/hello
go list -m
```

`go list -m` prints `example.com/hello`, even if the folder is named `hello` or `cliintro`.

### What happens here

The module path is an import contract, not necessarily the folder name. Beginners mix “directory name” with “module name.”

### Predict the result

Can the folder be named `app` and the module `github.com/org/app`?

**Answer:** yes. That is common. What matters is the `go.mod` module path.

## Decision analysis

| Situation | Option A | Option B | Guidance |
|-----------|----------|----------|----------|
| Don’t know a flag | Copy from a blog | `go help <cmd>` | Always B first |
| “Weird behavior” | Clear cache immediately | Compare `go env` / version | B, then cache if needed |
| Quick try | `go run` | `go build` + manual | `run` for the loop; `build` for an artifact |
| Package diagnostics | Read only the compiler error | `go list` + env | Both; list reveals context |
| Team docs | “just press Run in the IDE” | Commands in README = CI | README must work in the shell |

The decision “what to type first” is often more valuable than knowing a rare flag.

## Trade-offs

- **Cache on** — faster, but can hide confusion if you do not understand the input; still the correct default.
- **Full `go env` in the log** — useful for debug, noisy in everyday CI; filter keys.
- **IDE Run button** — fast locally; bad if the team does not know the equivalent CLI command.
- **Learning all subcommands at once** — overload; better a family map then depth as needed.
- **Pinning an exact Go version in CI** — fewer surprises; requires maintaining bumps.

## Common mistakes

1. Treating `go` as one command instead of a toolchain entry.
2. Ignoring a `go version` difference local vs CI.
3. Clearing `GOCACHE` / `GOMODCACHE` as the first diagnosis step.
4. Working outside a module then blaming “Go.”
5. Mixing `go run` / `go build` / `go install` and not knowing where the artifact is.
6. Copying flags that `go help` does not know.
7. Having two installs and not checking `where go` / `which go`.
8. Committing binaries because “I don’t know how CI builds.”
9. Assuming `GOOS` on the laptop must match production without a cross-compile plan.
10. Asking for help on a forum before `go env` and `go list -m`.

## Idiomatic Go

- README with copy-paste commands: `go test ./...`, `go build -o …`.
- At CI start: log `go version` and key `go env`.
- For package diagnostics: `go list` before manually wandering folders.
- One module per service (or a clear workspace) — no hidden `replace` to laptop paths on the main branch.
- `gofmt` / `go fmt` in pre-commit or CI — style is not a debate.
- Prefer `go help` and `go doc` locally while learning APIs.

## Practical scenario

A team has a CLI tool. On a developer laptop `go test ./...` passes. On CI it fails with an error about an unavailable API from the standard library. Nobody looks at the version.

Investigation:

1. `go version` locally → `go1.22.5`
2. CI image → `go1.20.14`
3. The code uses an API added in a newer version
4. Fix: raise Go on CI **or** lower the requirement in code / the `go` directive deliberately

Without the 15.01 reflex (version + env), the team would “fix” tests blindly.

Second scenario: a new member clones the repo, runs `go build`, gets a module error. They are working from the wrong subfolder without `go.mod`. `go list -m` immediately shows the problem. Half an hour of forums is replaced by one command.

## Summary

`go` is the entry into the toolchain: one binary, many subcommands, a shared cache and module contract. `go version`, `go help`, and `go env` are the three first instruments.
