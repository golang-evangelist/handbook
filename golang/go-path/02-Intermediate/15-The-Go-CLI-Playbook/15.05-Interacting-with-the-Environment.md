# 15.05 Interacting with the environment: Getenv, LookupEnv, and the link to `go env`

> **Go Path - Zero to Gopher** / **02 Intermediate → The Go CLI Playbook** / Lesson 15.05

## Lesson goals

After this lesson you should:

- read environment variables via `os.Getenv` and `os.LookupEnv`
- distinguish an **empty string** from an **unset** variable
- use `os.Expand` / `os.ExpandEnv` for path and URL templates (where it makes sense)
- design a config layer that does not scatter `Getenv` through the whole codebase
- know what does not belong in env (secrets in logs, huge JSONs, a feature-flag avalanche)
- understand the relationship: **`go env`** (toolchain map) vs **`os.Getenv`** (process map that your program reads)
- use `t.Setenv` / careful Setenv in tests without leaking state

## Prerequisite

- 15.01–15.04: CLI map, build/runtime env, build/run/install
- basic Go: functions, errors, `main`, `struct`
- preferred: an introduction to the 12-factor idea “config in env” — even if you do not follow it dogmatically
- you know that runtime levers (`GOGC`…) and app keys (`DATABASE_URL`) live in the same OS map, but under different contracts

## Problem this lesson solves

Code full of `os.Getenv("DB_HOST")` in ten packages. Somewhere a default value, somewhere not. In a test it “works” because the developer has env in the shell profile; on CI it fails. Another problem: `Getenv` returns `""` both for unset and for explicitly empty — so someone thinks the database is on localhost when they actually forgot a secret in Kubernetes.

Third problem: templates like `$HOME/data` are glued by hand with `+`, then bugs arrive on Windows and *nix.

Fourth problem: mixing `go env GOMODCACHE` (tool) with `os.Getenv("GOMODCACHE")` in application code without reason — confusion about what is the application contract and what is the toolchain’s.

The lesson teaches a **clean contract** with the environment: lookup with ok, expand with control, config at the process boundary, a clear boundary toward `go env`.

## Mental model

The environment is a **string→string map** that the OS gives the process at start (and that the process can change for itself).

1. **Getenv(key)** — return the value or `""` if missing. Does not say whether the key exists.
2. **LookupEnv(key)** — return `(value, ok)`. `ok=false` means no key. `ok=true` and `value=""` means explicitly empty.
3. **Expand** — replace `${var}` / `$var` in a string using a function you provide (or env).

The config layer is a **customs house**: at entry into `main` read env, validate, convert into a typed structure, pass further. Inner packages should not know the names of `DATABASE_URL` strings — they receive `Config`.

Picture: mail. Getenv is “give me what is written on the note or empty.” LookupEnv is “is there a note?” Expand is “fill the form where it says $NAME.”

Three maps in the playbook:

| Map | Who reads | Example keys |
|------|---------|-----------------|
| Toolchain (`go env`) | `go` CLI | `GOROOT`, `GOCACHE`, `GOOS` |
| Go runtime | Go runtime at start | `GOGC`, `GOMEMLIMIT`, `GOMAXPROCS` |
| Application | your code (`os.Getenv`) | `DATABASE_URL`, `APP_PORT` |

All three can be in the same OS process environment. Semantics and contract ownership differ.

## Mechanism

### Getenv

```go
host := os.Getenv("DB_HOST")
```

Fast, dangerous if you need the difference “not set” vs “empty.”

Trace:

```text
1. Key does not exist → ""
2. Key exists with value "db" → "db"
3. Key exists with value "" → ""
4. Code with if host == "" { host = "localhost" } treats (1) and (3) the same
```

That is why defaults via `Getenv` can **hide** a forgotten secret.

### LookupEnv

```go
host, ok := os.LookupEnv("DB_HOST")
if !ok {
	// no key — error or a real default deliberately
}
```

Use when absence is an error, and an empty string may be valid (rare for a host) or when you want strict validation.

Trace:

```text
1. No key → ok=false, value=""
2. Key="" → ok=true, value=""
3. Key="db.internal" → ok=true, value="db.internal"
```

Now you can:

```go
host, ok := os.LookupEnv("DB_HOST")
if !ok || host == "" {
	return fmt.Errorf("DB_HOST is required")
}
```

### Expand and ExpandEnv

```go
os.ExpandEnv("$HOME/app/data")
os.Expand("${HOST}:${PORT}", func(k string) string {
	return os.Getenv(k)
})
```

`ExpandEnv` uses the environment. `Expand` takes an arbitrary mapper — handy for tests and for forbidding some keys.

Trace:

```text
input:  "$HOME/app"
HOME= C:\Users\Dev
output: path with HOME replaced (depends on the OS value)
```

After expand, for paths prefer `filepath.Join` over a hand-made slash.

### Setenv / Unsetenv / Clearenv / Environ

```go
os.Setenv("APP_MODE", "test")
os.Unsetenv("APP_MODE")
// Clearenv() — empties the whole process env (dangerous outside controlled tests)
os.Environ() // []string of the form "KEY=value"
```

In production server code you rarely change env at random. In tests: carefully.

Go 1.17+: `t.Setenv` in tests — restores the old state after the test.

```go
func TestPort(t *testing.T) {
	t.Setenv("APP_PORT", "9999")
	// ...
}
```

### Windows vs Unix nuances

- Names on Windows are often case-insensitive at the OS level; do not rely on that in code — be consistent (`DB_HOST`, do not mix `db_host`).
- Paths: prefer `filepath.Join` over a hand-made slash after expand.
- PowerShell setting for a child process:

```powershell
$env:DB_HOST = "localhost"
go run .
```

### Relationship to `go env`

```powershell
go env GOMODCACHE
```

prints the cache path the **toolchain** uses. That is not automatically “config of your API service.”

If in the application you do:

```go
cache := os.Getenv("GOMODCACHE")
```

you get a value **only if that key is actually in the process env**. `go env` can show an effective value from defaults / configuration even when the variable is not explicitly set in the shell.

Trace of confusion:

```text
1. go env GOCACHE → C:\Users\...\go-build   (effective)
2. echo $env:GOCACHE in PowerShell → empty (not exported)
3. os.Getenv("GOCACHE") in your program → ""
4. Conclusion: go env ≠ Getenv for the same key always
```

Therefore:

- for tool diagnostics → `go env`
- for app config → your own keys (`APP_*`, `DATABASE_URL`) + `LookupEnv`
- Go runtime levers (`GOGC`…) set explicitly in the process env if you want them to apply

### Config at the boundary

```go
type Config struct {
	DBHost string
	Port   string
}

func LoadConfig() (Config, error) {
	host, ok := os.LookupEnv("DB_HOST")
	if !ok || host == "" {
		return Config{}, fmt.Errorf("DB_HOST required")
	}
	port := os.Getenv("APP_PORT")
	if port == "" {
		port = "8080" // deliberate default
	}
	return Config{DBHost: host, Port: port}, nil
}
```

An inner package receives `Config`, does not call `Getenv`.

### What does not belong in env

- huge JSON documents (unreadable, length limits)
- secrets you log on an `Environ()` dump
- dozens of feature flags without a scheme (becomes a shadow config DB)
- build-only truths that should be in the binary (`-X`) or in CI

### Fail closed vs default

| Key | Strategy |
|-------|------------|
| `DB_HOST` | fail if missing |
| `APP_PORT` | default `8080` OK |
| `DEBUG` | default false (closed) |
| `GOMEMLIMIT` | ops sets; app maybe only logs |

Security default: dangerous things off until explicitly turned on.

### Trace of service boot

```text
1. Kubernetes injects env into the container
2. api process starts
3. main → LoadConfig()
4. LookupEnv of required keys
5. If fail → log + os.Exit(1) / return error from main
6. Runtime already read GOGC/GOMEMLIMIT (if set)
7. Handlers get Config, do not call Getenv
```

If step 4 passes with a silent default on an empty DB host, the bug is seen only on the first request — late.

### Deeper trace: from shell to Getenv

```text
1. Ops: kubectl set env / chart values
2. Kubelet starts the container with an env block
3. OS process inherits the map
4. Go runtime reads its runtime keys (GOGC…)
5. main calls LoadConfig
6. os.LookupEnv reads app keys
7. Validation → Config struct
8. http.Server start
```

If step 1 has a typo in the key name, step 6 must fail loudly — otherwise you stay silent until a production incident.

### Deeper trace: why `go env` lies to a beginner’s expectation

```text
Developer: “GOCACHE must be in env because go env prints the path”
Reality: go env computes the effective value from defaults + env + config
App Getenv: sees only what is actually in the process
```

That is why the module tool (`go`) and your API are not the same reader. If you build a **tool** that mimics `go`, you might call `go env` externally. If you build a **service**, define your own `APP_*` keys.

### Type validation from a string

Env is always a string. Port, bool, duration need parse:

```go
portStr := optional("APP_PORT", "8080")
port, err := strconv.Atoi(portStr)
if err != nil || port < 1 || port > 65535 {
	return Config{}, fmt.Errorf("APP_PORT invalid: %q", portStr)
}
```

Trace of a bad parse:

```text
APP_PORT=eighty
Atoi fails → better fail at boot than listen in a weird place
```

### Feature flags in env — the boundary

One or two flags (`DEBUG=1`) OK. Fifty flags → think about a dedicated system. The env map becomes unreadable and hard to test.

### `.env` files

Many frameworks load `.env` in dev. That is **not** part of the standard `os` library. If you use a loader:

- do not commit secrets
- in prod prefer the orchestrator’s real env
- tests must not depend on a random `.env` on the laptop without control

### How to document the contract (template)

```markdown
| Key | Required | Default | Example | Who reads |
|-------|----------|---------|--------|---------|
| DB_HOST | yes | — | db.internal | app |
| APP_PORT | no | 8080 | 8080 | app |
| GOMEMLIMIT | no | runtime default | 512MiB | Go runtime |
```

The “Who reads” column prevents mixing layers.

### Security checklist

```text
[ ] No Environ() dump in prod log
[ ] Secrets not in git
[ ] DEBUG default false
[ ] Required secret fail closed
[ ] Examples in README are fake
```

## Rules and syntax

1. **Required:** `LookupEnv` or an explicit check; do not hide absence with a fake default.
2. **Default:** only for safe, documented values.
3. **Customs:** read env in `main`/config package, not in every handler.
4. **Test:** `t.Setenv`, not global Setenv without cleanup.
5. **Do not dump** the whole `Environ()` into the log in production.
6. **Names:** `SCREAMING_SNAKE`, consistent case.
7. **Paths:** `filepath` after expand.
8. **`go env`:** tool; does not replace the app `Getenv` contract.
9. **Secrets:** env OK as transport; still rotation, do not commit into `.env` in git without a policy.
10. **Document** keys in README / chart values.

## Examples

### Example 1 — Getenv trap

```go
host := os.Getenv("DB_HOST")
if host == "" {
	host = "localhost"
}
```

#### What happens here

`os.Getenv("DB_HOST")` returns an empty string when the key is missing and when the key is set to empty. The `if` treats both results as missing and stores `localhost`. Startup continues with that host, so a forgotten variable does not stop the process.

### Predict the result

On CI `DB_HOST` is forgotten. What does the app do?

**Answer:** silently goes to localhost — often the wrong host; bug late. Better fail closed for DB.

---

### Example 2 — LookupEnv fail closed

```go
host, ok := os.LookupEnv("DB_HOST")
if !ok || host == "" {
	log.Fatal("DB_HOST required")
}
```

#### What happens here

`LookupEnv` returns the value and sets `ok` to false only when `DB_HOST` is absent. The `if` also rejects an empty string. `log.Fatal` writes `DB_HOST required` and exits the process immediately.

### Predict the result

No key on CI — what happens at start?

**Answer:** the process fails immediately with a clear message. Better than a 500 on the first request.

---

### Example 3 — Empty vs absent

```powershell
# A: not set
# B:
$env:DB_HOST = ""
```

```go
v, ok := os.LookupEnv("DB_HOST")
```

#### What happens here

The PowerShell fragment distinguishes an unset `DB_HOST` from `DB_HOST` set to `""`. `LookupEnv` then reads whichever state the process actually has. An unset key makes `ok` false; a key set to empty makes `ok` true and `v` empty.

### Predict the result

What is `ok` in A and B?

**Answer:** A → `ok=false`. B → `ok=true` (empty value). Getenv in both returns `""`.

---

### Example 4 — ExpandEnv

```go
p := os.ExpandEnv("$USERPROFILE\\app\\data") // Windows example
```

#### What happens here

`ExpandEnv` replaces `$USERPROFILE` with the value from the process environment. If that variable is unset, the replacement is empty and only the rest of the path text remains. The function returns the resulting string and does not check that it names a real directory.

### Predict the result

If `USERPROFILE` is not set, what often remains in the string?

**Answer:** empty replacement / leftover of the template depending on contents — check the result; do not assume a valid path. Validate after expand.

---

### Example 5 — Config struct

```go
type Config struct {
	Addr string
}

func Load() (Config, error) {
	port := os.Getenv("APP_PORT")
	if port == "" {
		port = "8080"
	}
	return Config{Addr: ":" + port}, nil
}
```

#### What happens here

`Load` reads `APP_PORT` a single time. An empty reading becomes `8080`, and the returned `Config` has `Addr` set to a colon plus that port, with a nil error. The address is fixed in this function before any caller uses it.

### Predict the result

Why does an inner package not call `Getenv("APP_PORT")`?

**Answer:** testability and one source of truth; easier to mock Config.

---

### Example 6 — `go env` vs Getenv

```powershell
go env GOCACHE
go run .\print.go  # code: fmt.Println(os.Getenv("GOCACHE"))
```

#### What happens here

`go env GOCACHE` prints the cache path the toolchain is using, including its default when the variable was never set in the shell. `go run .\print.go` runs the program in the comment, which prints only `os.Getenv("GOCACHE")`. That second value is the raw process environment, so it can be empty while `go env` still prints a path.

### Predict the result

Why can they differ?

**Answer:** `go env` shows the effective toolchain value; `Getenv` sees only explicit process env. Empty Getenv does not mean Go has no cache.

---

### Example 7 — t.Setenv

```go
func TestAddr(t *testing.T) {
	t.Setenv("APP_PORT", "9999")
	cfg, err := Load()
	if err != nil || cfg.Addr != ":9999" {
		t.Fatalf("%v %#v", err, cfg)
	}
}
```

#### What happens here

`t.Setenv("APP_PORT", "9999")` sets the variable for this test and restores the previous value when the test ends. `Load` therefore runs with port `9999` and should return `Addr` `:9999`. `Fatalf` fails the test if `Load` returns an error or a different address.

### Predict the result

Does the next test see `APP_PORT=9999`?

**Answer:** it should not — `t.Setenv` cleans up after the test.

---

### Example 8 — DEBUG default false

```go
debug := os.Getenv("DEBUG") == "1"
```

#### What happens here

The expression is true only when `DEBUG` is the exact string `1`. An unset variable, an empty value, or any other text makes the comparison false. `debug` is then false, which is the closed state.

### Predict the result

What is the state when DEBUG is not set?

**Answer:** false — closed. Good for a production default.

---

### Example 9 — Environ dump trap

```go
log.Println(os.Environ())
```

#### What happens here

`os.Environ` returns every environment entry as a `KEY=value` string. `log.Println` writes that entire slice to the log. Secrets that live in the environment are included in the same line.

### Predict the result

What is the risk?

**Answer:** secrets in the log aggregator. Never in prod without a filter.

---

### Example 10 — PowerShell + go run

```powershell
$env:DB_HOST = "db.internal"
$env:APP_PORT = "8080"
go run ./cmd/api
```

#### What happens here

The two `$env:` assignments put `DB_HOST` and `APP_PORT` into the current PowerShell process. `go run ./cmd/api` is started from that process, so the program inherits both values. They remain in this shell for later commands until something changes them.

### Predict the result

Does the IDE Run button necessarily see the same variables?

**Answer:** no — the IDE can have its own env. Document the CLI way.

---

### Example 11 — Expand with a mapper filter

```go
s := os.Expand("$DB_HOST:$DB_PASSWORD", func(k string) string {
	if k == "DB_PASSWORD" {
		return "" // forbid in this template
	}
	return os.Getenv(k)
})
```

#### What happens here

`os.Expand` calls the function once for `$DB_HOST` and once for `$DB_PASSWORD`. The function returns an empty string for `DB_PASSWORD`, so the password is not copied into `s`. Every other name is filled with `os.Getenv`.

### Predict the result

Why a mapper?

**Answer:** control over which keys a template may see — better than blind ExpandEnv for sensitive strings.

---

### Example 12 — Runtime + app in the same process

```powershell
$env:GOMEMLIMIT = "512MiB"
$env:DB_HOST = "db"
.\api.exe
```

#### What happens here

The shell puts `GOMEMLIMIT` and `DB_HOST` into the environment and then starts `api.exe`. The Go runtime reads `GOMEMLIMIT` at process start and treats `512MiB` as the soft memory limit. `DB_HOST` is left for application code to read; the runtime does not interpret it.

### Predict the result

Who reads what?

**Answer:** Go runtime reads `GOMEMLIMIT`; your `LoadConfig` reads `DB_HOST`. Same map, different consumers.

---

### Example 13 — Required vs optional

```go
func require(key string) (string, error) {
	v, ok := os.LookupEnv(key)
	if !ok || v == "" {
		return "", fmt.Errorf("%s required", key)
	}
	return v, nil
}

func optional(key, def string) string {
	v, ok := os.LookupEnv(key)
	if !ok || v == "" {
		return def
	}
	return v
}
```

#### What happens here

`require` uses `LookupEnv` and returns an error when the key is missing or the value is empty. `optional` uses the same test, returns `def` in that case, and returns the environment value when it is non-empty. The two functions are separate policies around one lookup.

### Predict the result

For `APP_PORT` which helper?

**Answer:** `optional("APP_PORT", "8080")` if the default is documented; for `DB_HOST` → `require`.

---

### Example 14 — CI without a local profile

A developer has in the profile `$env:DB_HOST="localhost"`. CI does not.

### Predict the result

Why does the test “work on my machine”?

**Answer:** Getenv/load sees the local profile. CI has no key — fail or wrong default. Tests should set env explicitly (`t.Setenv`) or use a Config fixture.

---

### Example 15 — Parse duration from env

```go
raw := optional("SHUTDOWN_TIMEOUT", "10s")
d, err := time.ParseDuration(raw)
if err != nil {
	return Config{}, fmt.Errorf("SHUTDOWN_TIMEOUT: %w", err)
}
```

#### What happens here

`optional` returns the `SHUTDOWN_TIMEOUT` string, or `10s` when the key is missing or empty. `time.ParseDuration` accepts a value with a unit, such as `10s`, and returns an error for a bare number such as `10`. On error the function returns an empty `Config` and an error that includes the key name.

### Predict the result

`SHUTDOWN_TIMEOUT=10` without a unit — what happens?

**Answer:** `ParseDuration` typically fails. Fail at boot better than a wrong timeout.

---

### Example 16 — Three-map table (understanding check)

| Key | Map |
|-------|------|
| `GOOS` at `go build` | build / toolchain |
| `GOMEMLIMIT` at `./api` | runtime |
| `DB_HOST` in `LoadConfig` | application |

### Predict the result

Where does `GOCACHE` belong when you look via `go env`?

**Answer:** toolchain map (`go env`), not app config.

---

### Example 17 — Minimal main with customs

```go
func main() {
	cfg, err := config.Load()
	if err != nil {
		fmt.Fprintf(os.Stderr, "config: %v\n", err)
		os.Exit(1)
	}
	if err := run(cfg); err != nil {
		fmt.Fprintf(os.Stderr, "run: %v\n", err)
		os.Exit(1)
	}
}
```

#### What happens here

`main` calls `config.Load` before `run`. A load error is printed to stderr and `os.Exit(1)` ends the process, so `run` does not start. An error from `run` is reported the same way, with exit status 1.

### Predict the result

Why `Exit(1)` on a config error?

**Answer:** the process should not “half” run without a contract. The orchestrator sees a crash loop and alerts.

---

### Example 18 — LookupEnv in a loop? No.

Bad pattern: on every HTTP request `os.Getenv("FEATURE_X")`.

### Predict the result

What is better?

**Answer:** read at start into Config (or controlled reload). The request path stays clean and testable.

---

### Example 19 — Windows case

```powershell
$env:Db_Host = "x"
# code looks for DB_HOST
```

#### What happens here

The shell sets a variable named `Db_Host` to `x`. The comment says the program looks up `DB_HOST`, which is the same spelling with different case. Windows treats those names as one environment key, so the lookup can return `x`; on Linux they are different keys and `DB_HOST` is unset.

### Predict the result

Why consistent SCREAMING_SNAKE?

**Answer:** on Windows case-insensitive OS can hide a bug that blows up on Linux. One canonical name form.

---

### Example 20 — Docs + code aligned

README says `APP_PORT` default 8080. Code has default 3000.

### Predict the result

Who wins in a new member’s head?

**Answer:** chaos. A test that asserts the documented default catches the divergence.

## Decision analysis

| Need | Choose | Avoid |
|---------|-------|-----------|
| Required secret/host | LookupEnv + fail | Getenv + localhost default |
| Safe port default | Getenv/optional | fail for every tiny key |
| Toolchain diagnostics | `go env` | `Getenv("GOCACHE")` in app |
| Test isolation | `t.Setenv` | manual Setenv without cleanup |
| Path template | Expand + filepath | hand-made `+ "\\" +` |

## Trade-offs

- **Everything in env** — 12-factor convenient vs hard to validate complex structures.
- **File config + env override** — flexible vs two sources of truth.
- **Fail closed** — safer vs stricter onboarding (solved with documentation).
- **ExpandEnv** — short vs invisible dependencies on the shell profile.
- **Central LoadConfig** — discipline vs a bit more code at start.

## Common mistakes

1. `Getenv` + silent default for required.
2. Scattered `Getenv` through the service layer.
3. Mixing `go env` and app Getenv expectations.
4. Logging the whole `Environ()`.
5. Tests dependent on the developer profile.
6. Case chaos on Windows.
7. Secrets in README examples committed as real.
8. Huge JSON in one env var.
9. Setenv on the production request path.
10. Assuming IDE and CLI share env.

## Idiomatic Go

- `internal/config.Load() (Config, error)` at the boundary.
- `LookupEnv` for required; documented default for optional.
- `t.Setenv` in tests.
- README key table (name, required, default, example).
- Do not read `GOROOT` from app code unless you are building a toolchain tool.

## Practical scenario

A service in staging “works,” in prod attaches to the wrong DB. Cause: `Getenv("DB_HOST")` with default `localhost`, and in the prod manifest a typo in the key name (`DBHOST`). LookupEnv + fail closed would have failed at start. Additionally: the health check did not verify DB at boot.

Fix:

1. `require("DB_HOST")`
2. Key table in the Helm chart README
3. Boot checks the connection or at least key presence
4. Test with `t.Setenv` without relying on the laptop profile

Second incident: a developer debugs “why GOCACHE empty in app” — mixed `go env` with `Getenv`. Training from 15.01+15.05 solves it in five minutes.

## Summary

`os.Getenv` does not distinguish absent from empty; `os.LookupEnv` does. Load config at the process boundary, fail closed for required, document defaults for optional. `go env` is the toolchain map — not the same as app Getenv. Runtime keys and app keys can share OS env, but have different consumers. Next: managing workspaces.
