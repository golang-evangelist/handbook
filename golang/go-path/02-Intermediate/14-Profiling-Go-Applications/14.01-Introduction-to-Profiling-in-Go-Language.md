# 14.01 Introduction to Profiling in Go: Measure Before You Touch Anything

> **Go Path - Zero to Gopher** / **02 Intermediate → Profiling Go Applications** / Lesson 14.01

## Lesson goals

- Adopt the principle **measure first**, optimize later — without a number there is no claim of speedup.
- Distinguish **CPU profile**, **memory profile** (heap / allocs), **block**, and **mutex** profile.
- Separate **benchmark** from **profile** — what each tool answers and when.
- Establish the diagnostic order before the `pprof` details in 14.02.
- Recognize false “bottlenecks” that come from gut feeling, laptop throttling, or a single slow request.

## Prerequisite

- Go 1.22+; `go test`; a basic HTTP or CLI service you can load locally.
- Preferably 08.06 (mention of **goroutine** profile and race detector).
- A basic feel for latency (P50 / P99) and for RSS / heap growth.

## Problem this lesson solves

A developer “optimizes” without evidence:

- changes `GOMAXPROCS`;
- introduces `sync.Pool` everywhere;
- rewrites strings to `[]byte`;
- “speeds up” JSON with hand-rolled buffers.

…while the bottleneck is slow SQL without an index, an N+1 query, or waiting on the network. **Profiling** and **benchmark** exist so that **evidence** drives the work, not intuition after one slow request on a laptop on battery.

Without measurement discipline:

1. you spend a sprint on the wrong line;
2. you introduce complexity (`Pool`, `unsafe`, special caches) with no gain;
3. you cannot prove a regression in a PR;
4. you mix up “slow Go” with a “slow dependency”.

## Mental model

Two questions, two tools:

1. **How slow is it / how much does it cost?** → benchmark, metrics, load test, tracing.
2. **Where is time / memory spent?** → profile (pprof).

| Profile | What it tells you |
|--------|-----------|
| CPU | Where the processor spends sampled time (stack samples) |
| heap | What lives on the heap now (`inuse_space` / `inuse_objects`) |
| allocs | What is allocated over a period (`alloc_space` / `alloc_objects`) |
| block | Where **goroutines** wait on blocking operations (`channel`, `select`, I/O sink) |
| mutex | Contention on `sync.Mutex` / `RWMutex` |
| goroutine | Which **goroutines** exist and their stacks |

**Benchmark** measures **duration and allocations** of a small piece of code under controlled conditions (`testing.B`). **Profile** shows the **distribution** of cost in a larger system under load.

Remember the chain:

```text
symptom → reproduction + number → profile choice → line of code → hypothesis → change → measure again
```

If you skip the first two steps, pprof becomes a decorative graph.

## Mechanism

This is the heart of the lesson. Here you build the habit: **measure → localize → change → verify**. Everything else (commands, Builder, Pool) comes after.

### Measure first — five steps

1. **Define the goal.** An SLO or at least a clear hypothesis: “P99 `/v1/orders/{id}` < 200 ms on staging at 50 RPS” or “`BenchmarkFormat` < 400 ns/op and < 2 allocs/op”.
2. **Reproduce the load.** `hey`, k6, `go test -bench`, or a manual script. Without reproduction there is no profile worth taking.
3. **Take a baseline.** Record P50/P99, `ns/op`, `B/op`, `allocs/op`, RSS, GC pause roughly — before the change.
4. **Localize.** Only now do you choose CPU / allocs / heap / block / mutex / goroutine profile.
5. **Change one thing, measure again.** Keep or revert. Attributability matters more than a “feeling of speed”.

If you lack (1) and (3), you are not yet tuning — you are guessing.

### Why intuition lies

The human brain likes to “see” a bottleneck in familiar code:

- “JSON is slow” → but 80% of the time is in the DB round-trip;
- “need a Pool” → but allocations are 2% of CPU;
- “goroutine leak” → but the heap grows because of a cache without TTL;
- “need more CPU” → but latency is block on a `channel` or lock.

A profile does not “guess” — it samples or records. That is why measuring is cheaper than a wrong refactor.

### Benchmark vs profile — the boundary

| | Benchmark | Profile |
|--|-----------|---------|
| Focus | micro: function, package | meso/macro: process under load |
| Repeatability | high (same `b.N` loop) | depends on the load scenario |
| Allocations | `-benchmem` / `ReportAllocs` | allocs / heap profile |
| Network / DB | usually disabled or mocked | often included (that is why it is “real”) |
| When | library, hot helper, PR evidence | “I don’t know where” in a service |

A benchmark is **not** a substitute for a profile. A profile is **not** a substitute for a benchmark. You use both in different phases.

Typical flow for a library:

```text
correctness test → Benchmark + -benchmem → (if suspicious) -cpuprofile/-memprofile → list
```

Typical flow for an HTTP service:

```text
metric/SLO → load (hey) → HTTP pprof CPU/allocs → top/list → change → load again
```

### CPU vs memory — two different worlds

**CPU profile** answers: *where does the processor spend time while doing work?*  
Mechanism: periodic **stack samples**. You see flat (time in the function) and cum (time in the function + descendants).

**Memory profile** answers two sub-questions:

- **heap / inuse** — what is *alive now* (leak, cache, retained buffers);
- **allocs** — what is *allocated over time* (GC pressure, churn).

Symptom → choice:

| Symptom | First profile | Why |
|---------|-------------|--------|
| P99 spikes, CPU 80–100% | CPU | you are looking for a hot loop / encode / hash |
| RAM grows for hours / days | heap + goroutine | live objects or forgotten **goroutines** |
| CPU low, latency high | block / goroutine | waiting, not computing |
| Throughput drops with more cores | mutex | contention |
| GC frequent, CPU in `runtime.gc*` | allocs | allocation churn |

Mixing CPU and memory symptoms is a common mistake: you reduce allocations while the bottleneck is bcrypt, or you “speed up” a loop while the heap leaks because of a global map.

### What a benchmark actually measures

```go
func BenchmarkFormat(b *testing.B) {
	m := Money{MinorUnits: 123456, Currency: "RSD"}
	b.ReportAllocs()
	for b.Loop() { // Go 1.24+; older: for i := 0; i < b.N; i++
		_ = Format(m)
	}
}
```

```bash
go test -bench=BenchmarkFormat -benchmem ./quote
```

Typical output:

```text
BenchmarkFormat-8   2500000   401 ns/op   24 B/op   1 allocs/op
```

- `ns/op` — average time per operation on *that* machine;
- `B/op` — bytes allocated per operation;
- `allocs/op` — number of allocations per operation.

What a benchmark does **not** measure reliably:

- network RTT;
- lock contention under 1000 clients;
- GC behavior of a long-lived process;
- “production” P99 with noise.

So: benchmark for micro evidence; profile + load for system evidence.

### Load as a condition for a meaningful CPU profile

A CPU profile on an idle process shows noise: `runtime` parking, your `select` on an empty `channel`, idle loops. Under load (`hey -z 30s -c 20 ...`) samples land on the hot path.

Rule: **the same load before and after the change**. Otherwise you are comparing apples and oranges.

### GC Trace as a cheap signal (not a substitute for pprof)

```bash
GODEBUG=gctrace=1 ./ordersvc
```

You see GC frequency and pause. If GC dominates CPU, the next step is an **allocs** profile — not a blind `sync.Pool`. `gctrace` is a signal, not line localization.

### Metrics and tracing alongside profiles

- **Metrics** (Prometheus): trend — “P99 has been rising since 14:00”.
- **Tracing**: which span (DB vs HTTP vs JSON) eats time.
- **Profile**: which function / line.

Order in an incident often:

```text
metric shows the problem → trace says “DB span” → SQL EXPLAIN
metric shows the problem → trace says “handler” → CPU/allocs pprof
```

If you skip the Trace, you can profile Go for hours while the bottleneck is an index.

### One hypothesis per cycle

Bad:

```text
added Pool + rewrote string to []byte + changed GOMAXPROCS + added cache
→ P99 dropped → I don’t know what helped
```

Good:

```text
baseline → only Builder instead of += → benchmem → keep/revert
```

In the PR state the baseline and after. The reviewer must see attributability.

### False signal: laptop and environment

- throttling on battery;
- Windows Defender / antivirus scanning `go test`;
- Docker Desktop sharing CPU;
- other processes on the same machine;
- “debug” build instead of release-like.

Compare **relatively** on the same machine before/after. Absolute numbers from a laptop are not a production SLO. For SLOs measure on staging/prod hardware.

### When NOT to profile

- one slow request without reproduction;
- an idle process “because you can”;
- a public endpoint without auth (security — details in 14.02);
- before you have a hypothesis of what you are looking for;
- before correctness tests pass.

Profiling broken semantics is a waste of time: correctness first, then speed.

### Linking benchmark ↔ profile in the same PR

Often:

1. bench shows more `allocs/op` after a change → stop;
2. CPU profile shows a hot function → you write a micro-benchmark just for it → you prove the improvement in a PR table;
3. the service is still slow → you return to load + pprof (the bench was not lying; it measured a different layer).

### Diagnostic order (card for the wall)

```text
1. Is the problem real? (SLO / complaint / metric)
2. Can it be reproduced? (load / bench)
3. Where is the time? (trace: DB vs app)
4. If app: CPU or memory symptom?
5. Take the matching profile under load
6. top → list (line)
7. One change
8. Repeat 2–6
```

14.02 will give the commands. Here you must know *why* you choose a step.

### CPU samples — what “70% in encodeJSON” means

That is not always “70% wall-clock for the user”. It is the share of **sampled CPU time** in that profile. If the process waits on the network, CPU % can be low while P99 is high — that is why block/goroutine profile and tracing exist.

### Memory: leak vs churn

- **Churn** — many allocations that GC collects quickly → allocs + GC CPU.
- **Leak / retention** — objects stay alive → heap inuse grows; goroutine profile if there are forgotten **goroutines**.

Same “high RAM” symptom — two different profiles and two different fixes.

### Block and mutex — short introduction

When CPU is idle but latency rises:

- **block profile** — waiting on `channel`, `select`, some I/O paths (with `SetBlockProfileRate`);
- **mutex profile** — lock contention (with `SetMutexProfileFraction`).

Details on enabling in 14.02. Here: do not treat “slow CPU” with a mutex profile, and vice versa.

### Production vs lab profile

| | Lab | Prod/staging |
|--|-----|----------------|
| Load | synthetic | real or recorded |
| Risk | low | pprof must be localhost/admin |
| Signal | clean, maybe unrealistic | noisy, but truthful |
| Goal | prove a change | confirm a hypothesis from an incident |

Never claim “optimized” only from a lab bench if the SLO lives in prod — measure where the contract applies.

### Checklist before “optimization” (Mechanism → practice)

1. Do I have a number (P99, allocs/op, RSS)?
2. Do I have a reproduction?
3. Do I have a profile that shows the place?
4. Do I have a test so I don’t break semantics?
5. Do I have a plan to measure after?

If anything is missing — guessing phase.

## Rules and syntax

- Do not profile an idle process “because you can” — profile under representative load.
- One hypothesis per change; one measured claim per PR.
- Keep baseline numbers in the PR description (before/after table).
- Do not expose pprof publicly (details and `DefaultServeMux` caution in 14.02).
- `go test -bench=... -benchmem` when you suspect allocations.
- `b.ReportAllocs()` in a benchmark that guards an allocation budget.
- Do not compare absolute `ns/op` across different machines as truth.
- Correctness tests exist *alongside* the bench — a faster wrong result is not a win.

Minimal bench pattern:

```go
func BenchmarkName(b *testing.B) {
	// arrange outside the loop
	b.ReportAllocs()
	for b.Loop() {
		_ = HotPath(input)
	}
}
```

Minimal load pattern (local):

```bash
hey -z 30s -c 20 http://127.0.0.1:8080/v1/orders/1
```

While `hey` runs, you take a CPU profile (14.02). Without load a CPU profile is noise.

## Examples

### Example 1 — Benchmark as evidence

#### Predict

What do you expect from `-benchmem` after `ReportAllocs`: which three columns do you look at and why “it feels faster” is not enough?

```go
package quote

import "testing"

func BenchmarkFormat(b *testing.B) {
	m := Money{MinorUnits: 123456, Currency: "RSD"}
	b.ReportAllocs()
	for i := 0; i < b.N; i++ {
		_ = Format(m)
	}
}
```

```bash
go test -bench=BenchmarkFormat -benchmem ./quote
```

#### Answer

You look at `ns/op`, `B/op`, `allocs/op`. After a refactor you compare the **same** numbers on the same machine. Without a table in the PR, “sped up” is a marketing word.

#### What happens here

`testing.B` repeats the call enough times to reduce noise. `ReportAllocs` forces an allocation report. `_ = Format(m)` prevents the compiler from “optimizing” the result away in trivial cases (still write a real sink when needed).

### Example 2 — Same function, wrong conclusion

#### Predict

Does a bench that shows lower `ns/op` automatically mean you may merge?

```go
// "optimization" without checking semantics
func FormatFast(m Money) string {
	return fmt.Sprintf("%d", m.MinorUnits) // different semantics — no currency
}
```

#### Answer

No. A benchmark can show it is “faster” while the result is wrong. Measured optimizations still require table-driven correctness tests.

#### What happens here

A micro-optimization without a test changes the API contract. Profiling does not catch logic errors — tests do.

### Example 3 — Which profile when

#### Predict

For each symptom choose a profile *before* you look at the table.

```text
A) P99 spikes, CPU 90%
B) RAM grows over the day
C) CPU low, latency high, many goroutines on channel
D) throughput drops with more POD CPU
```

#### Answer

```text
A → CPU profile
B → heap + goroutine
C → block / goroutine
D → mutex profile
```

#### What happens here

Profile choice follows the symptom. Wrong profile = hours in the wrong graph.

### Example 4 — GC Trace as a signal

#### Predict

What can `gctrace` *not* tell you that pprof can?

```bash
GODEBUG=gctrace=1 ./ordersvc
```

#### Answer

It does not say *which line* allocates. It says GC frequency/impact. If GC dominates → allocs profile next.

#### What happens here

A cheap signal on the path to pprof. Not a substitute for `go tool pprof`.

### Example 5 — Controlled load

#### Predict

Why is a CPU profile *during* `hey` worth more than a profile at rest?

```bash
hey -z 30s -c 20 http://127.0.0.1:8080/v1/orders/1
```

#### Answer

Samples land on the hot path under representative load. Idle = noise in `runtime` and waiting.

#### What happens here

Load and profile must overlap in time. Capture 15–30 s while `hey` runs (commands in 14.02).

### Example 6 — Bench table in a PR

#### Predict

What must a reviewer see to accept a “performance” PR?

```text
BenchmarkFormat-8   2000000   512 ns/op   64 B/op   2 allocs/op   (before)
BenchmarkFormat-8   2500000   401 ns/op   24 B/op   1 allocs/op   (after)
```

#### Answer

Same bench, same machine/environment, before and after, plus correctness so semantics hold.

#### What happens here

The table turns feeling into evidence. Without it review becomes faith.

### Example 7 — High CPU vs high memory

#### Predict

Endpoint A: CPU 95%, allocs low. Endpoint B: CPU 20%, GC frequent, huge `B/op` in the bench. Which first tool?

#### Answer

A → CPU profile. B → allocs (and benchmem as micro evidence), not mutex “preventively”.

#### What happens here

The symptom chooses the instrument. Same “slow” feeling — two diagnoses.

### Example 8 — When NOT to touch the code

#### Predict

Trace shows 180 ms in SQL, 2 ms in the handler. Where is your next hour?

#### Answer

SQL / index / query — not `strings.Builder` in the handler.

#### What happens here

Profiling Go code is useful only when the app layer actually spends the budget. Otherwise you optimize 1% of the path.

## Decision analysis

| Decision | Why |
|--------|--------|
| Baseline before the change | Proof of regress/improve |
| Benchmark for libraries | Stable micro numbers |
| Profile for services | Sees the whole stack under load |
| Profile type by symptom | Fewer false traces |
| One change per cycle | Attributability |
| Trace before blind pprof | Separates DB from app |
| Relative comparison on the same machine | Less environment noise |
| Correctness alongside bench | Speed without lies |

## Trade-offs

- **Microbenchmark** — precise, easily unrealistic (does not measure network/DB).
- **Production profile** — real, risky if the endpoint is public / expensive.
- **Metrics only** — good trend, weak line-of-code localization.
- **Feeling only** — free and often wrong.
- **Long CPU sample** — better signal, more impact on latency during capture.
- **Lab only** — fast, can lie about prod SLO.

## Common mistakes

1. Optimization before measurement.
2. Benchmark without `-benchmem` when you suspect allocations.
3. CPU profile on an idle process.
4. Mixing “slow SQL” with “slow Go” without tracing.
5. Pool/Cache “preventively” without evidence.
6. Comparing benchmarks on different machines as absolute.
7. Multiple changes at once then “P99 dropped”.
8. Claiming “optimized” only on feeling or one request.
9. Ignoring semantics for lower `ns/op`.
10. Profiling a public internet listener (security fail — see 14.02).

## Idiomatic Go

- `testing.B` with `ReportAllocs` when you guard an allocation budget.
- Table-driven correctness tests *alongside* the bench.
- pprof in the team’s tooling chain (documented access, localhost).
- Prefer a clearer algorithm until a profile says otherwise.
- In the PR: before/after numbers, not adjectives.
- One hypothesis → one change → one measurement.

## Practical scenario

A team spends a sprint on `sync.Pool` for JSON buffers. P99 does not move. The CPU profile shows 70% of time in `bcrypt` on the login path — an expected expensive hash, not a bug. The real problem is the catalog endpoint: the allocs profile shows huge `[]byte` from reading the body without a limit. Limit + stream — P99 drops. The Pool remains as an irrelevant diff. Measure first; localize; only then change.

Second round: a junior “speeds up” money formatting and strips currency from the string. Bench is green. Users see the wrong amount. The correctness test that should have existed — did not. Team conclusion: a performance PR without semantic tests does not get merged.

## Check questions

1. **What first?**  
   Measure (benchmark / metrics / load), then profile, then change.

2. **Benchmark vs profile?**  
   Benchmark: micro, repeatable. Profile: cost distribution in the system under load.

3. **When CPU profile?**  
   When the processor is busy and you need a line / function.

4. **When allocs / heap?**  
   When you suspect memory / GC: churn (allocs) vs live (heap).

5. **When mutex / block?**  
   When latency rises with low CPU and suspicion of waiting / contention.

6. **Why one change per cycle?**  
   So you know what helped or hurt.

7. **Why not trust a laptop absolute?**  
   Throttling and noise; compare relatively; measure the SLO where it applies.

## Tools alongside pprof

- **Metrics** (Prometheus): latency, CPU, GC trend.
- **Tracing**: which span is slow (DB vs HTTP).
- **Logs**: errors and slower queries with request id.
- **Benchmark**: micro evidence for a library.

pprof does not replace these tools — it localizes the line when you already know a problem exists.

### False signal: “the laptop is slow”

Throttling on battery, antivirus, Docker Desktop on Windows — all corrupt absolute numbers. Compare relatively on the same machine before/after. For a prod SLO measure in prod (or staging with similar hardware).

### When NOT to profile — continued

- On one slow request without reproduction.
- On an idle process.
- On a public endpoint without auth.
- Before you have a hypothesis of what you are looking for.
- Before correctness passes.

## Deeper look: what “measure first” means in a team

### Definition of Done for a performance change

- [ ] Correctness tests green.
- [ ] Baseline numbers saved.
- [ ] Same scenario measured after.
- [ ] In the PR a table or link to the profile (internal artifact).
- [ ] No new `sync.Pool` / `unsafe` without evidence.
- [ ] Runbook updated if an operational step changed.

### What to say in standup instead of “I’m optimizing”

Bad: “Working on performance.”  
Good: “I have P99 450 ms on `/catalog`; Trace says app; today CPU profile under hey; hypothesis: `json.Marshal` in a loop.”

A clear hypothesis shortens review and incident.

### Matrix: tool × question

| Question | Tool |
|---------|------|
| How often does the SLO fail? | Metric |
| Which span? | Trace |
| Which function on CPU? | CPU pprof |
| What allocates? | allocs pprof + benchmem |
| What holds memory? | heap pprof |
| Who is waiting? | block / mutex / goroutine |
| Is there a micro-regression in a lib? | benchmark |

If you pick a tool outside the matrix “because I’m used to it”, you are back to intuition.

### Thinking exercise: write the hypothesis in one sentence

Template:

> Under load X, symptom Y; I think the cause is Z; I will check with tool W; success is number B.

Example:

> Under `hey -c 20` for 30 s, P99 `/export` 2 s; I think it is `s += row` in a loop; I will check with allocs pprof + `BenchmarkExport`; success is P99 < 300 ms and < 10 allocs/op in the bench.

Without the template, “looking at pprof” has no stopping criterion.

### What a profile *is not*

- Not a substitute for code review.
- Not proof of correctness.
- Not permission for pprof to listen on `0.0.0.0`.
- Not magic that fixes O(n²) without changing the algorithm.
