# 14.03 Performance Tuning in Practice: Allocations, Builder, Pool, Escape Analysis

> **Go Path - Zero to Gopher** / **02 Intermediate → Profiling Go Applications** / Lesson 14.03

## Lesson goals

- Reduce **unnecessary allocations** *only* where a profile / benchmark shows.
- Use **strings.Builder** for building strings in a loop.
- Know the caution around **sync.Pool** — it is not a silver bullet.
- Put **algorithm and I/O** ahead of micro-optimizations.
- Understand **escape analysis** at a conceptual level (`go build -gcflags=-m`).
- **Never** claim “optimized” without measuring before and after (14.01 discipline).

## Prerequisite

- 14.01–14.02; reading `top` / `list` under load.
- Basic slice / string model in Go.
- Understanding that **interface** and **pointer** stay as English terms (no Serbian substitutes from the ban list).

## Problem this lesson solves

After pprof you see a hot line — what now? This lesson gives **ordinary, idiomatic** moves and warns against premature `sync.Pool`. Also: the biggest win is often not a Go micro-trick, but an index in the database, a smaller payload, or O(n) instead of O(n²).

Without this discipline a team:

- inserts Pool everywhere “preventively”;
- breaks the API so that “nothing escapes”;
- “optimizes” a cold path;
- merges slower code because it did not measure after.

## Mental model

Priority order (remember the order):

1. **Correct algorithm / less work** (complexity, cache of *work results* when it makes sense).
2. **Less I/O** (batch, column projection, body limit, stream).
3. **Fewer allocations on the hot path** (`strings.Builder`, preallocate slice).
4. **Special tricks** (`sync.Pool`, `unsafe`) — rarely, **only with measurement**.

**Escape analysis**: the compiler decides whether an object lives on the stack or the heap. `go build -gcflags=-m` prints decisions — for learning, not for every PR TODO.

The cycle you must never break:

```text
SLO / number → load → pprof list → hypothesis → change → bench/profile → keep or revert
```

If you claim a speedup without a baseline, you are claiming a guess.

## Mechanism

This is the longest section: *what to change when you know the line*, and *why most “tricks” wait for evidence*.

### 0. Before any change — measure first

The repeat from 14.01 is not decoration:

1. Do you have a P99 / `ns/op` / `allocs/op` / RSS baseline?
2. Do you have a `list` that shows *this* line under load?
3. Do you have a correctness test?

If not — **do not optimize**. Go back to 14.01/14.02.

### 1. Allocations — what creates them

Typical sources on a hot path:

- `s += x` in a loop (a new string every time);
- `append` without capacity on a large n (repeated copies);
- `fmt.Sprintf` in a tight loop;
- boxing into `interface{}` / `any` (e.g. a slice of `any`);
- `json.Marshal` → an extra `[]byte` instead of stream encode;
- capturing a large value in a **closure** that lives longer (escape to heap);
- returning the address of a local variable (`*T`) — the object often goes to the heap.

Every allocation is not a mistake. GC exists. The problem is *too many* allocations on a path that must hold an SLO — that is what allocs profile and `-benchmem` prove.

### 2. strings.Builder — mechanism

A `string` in Go is immutable. `s += p` allocates a new string and copies the content. In a loop that is O(n²) characters in the worst growth.

`strings.Builder` holds an internal buffer:

```go
var b strings.Builder
b.Grow(n) // optional: fewer internal expansions
b.WriteString(p)
out := b.String()
```

`Grow` with a rough estimate reduces realloc. A wrong estimate is not fatal — Builder still works.

When Builder is **not** the first move: if `list` shows the DB driver, not Builder.

### 3. Preallocate slice — mechanism

```go
out := make([]string, 0, len(in))
for _, it := range in {
	out = append(out, it.ID)
}
```

`append` without capacity doubles the buffer and copies. On thousands of elements on a hot path, `list` / benchmem see the difference. On ten elements once per request — often noise; measure.

### 4. sync.Pool — mechanism and caution

`sync.Pool` caches temporary objects per P (processor). GC **may** empty the Pool. It is meant for *frequent, short-lived* buffers of the same shape (`bytes.Buffer`, `[]byte` scratch).

It is **not** a generic cache of business entities. It is **not** the first reaction to every allocation.

Obligations:

- `Get` → type assert → `Reset` → use → `Put`;
- **never** keep a reference to the object after `Put` (race + data leak between requests);
- introduce only when allocs profile + bench show a gain.

Without evidence Pool is noise in review and a source of bugs.

### 5. Escape analysis — mechanism

The compiler asks: does the object’s address “escape” outside the stack frame?

Common reasons for heap:

- you return `*T` (**pointer** to a local);
- you write into `interface{}` / `any`;
- you send to another **goroutine** via `channel` or closure;
- you store in a structure that lives on the heap.

```bash
go build -gcflags="-m -m" ./pkg 2>&1 | less
```

Use for *learning*: why a “small” structure still allocates. **Do not** turn `-m` output into a mandatory backlog. An API with `*T` is often correct (mutability, large objects, optional).

### 6. Algorithm before micro — mechanism

CPU profile shows a search loop over a list of 50k? A micro-Builder will not save you. A data structure (`map[string]Item`) or an index will.

```text
O(n²) in app → complexity first
N+1 SQL → query first
10 MB JSON for 3 fields → projection first
```

14.01 matrix: Trace before blind pprof. Same here: do not tune Go while I/O eats the budget.

### 7. JSON and allocations — mechanism

```go
enc := json.NewEncoder(w)
_ = enc.Encode(v) // stream into writer

// vs
b, err := json.Marshal(v)
if err != nil { /* ... */ }
_, _ = w.Write(b) // extra []byte peak
```

On large responses Encoder can reduce peak. **Measure** — it is not always the winner because of internal buffers. The profile decides; marketing does not.

### 8. bytes.Buffer and bufio.Writer

For CSV / text stream into `ResponseWriter`:

- `bufio.NewWriter(w)` + flush;
- or `strings.Builder` then one write (higher peak);
- Pool around Buffer only with evidence.

Same priority order: fewer copies, fewer intermediate sums, measurement.

### 9. When allocation is NOT the problem

Endpoint: 50 ms DB, 0.2 ms serialization. Reducing allocations does not move P99. Allocs profile shows that — that is why 14.01 exists. Tuning with no impact on the SLO is cosmetics.

### 10. One change, one piece of evidence

Bad: Builder + Pool + preallocate + API change in the same PR.  
Good: only Builder; bench table; keep.

Attributability > “everything at once then faster”.

### 11. Escape and API design — decision mechanism

| Choice | Typical consequence | When OK |
|-------|-------------------|--------|
| `func f() T` | less escape | small immutable types |
| `func f() *T` | often heap | large T, mutation, optional |
| `func f() any` | boxing allocation | rarely on hot path |
| closure captures a large slice | memory retention | shorten closure lifetime |

Do not change a public API only because of an `-m` message if that breaks semantics. Readable contract > micro heap.

### 12. What is deliberately not a “first tool”

- `unsafe` and hand-rolled memory tricks;
- assembly;
- code generation for 2% on a cold path;
- `GOMAXPROCS` as a first reaction;
- a global cache without TTL “because of allocations”.

When an SLO demands extremes, take specialist material — most services are fixed by the order in this lesson.

### 13. Final tuning cycle (card)

```text
SLO clear
  → load
  → pprof (top → list)
  → hypothesis (one)
  → change (one)
  → bench / profile / load
  → keep or revert
```

If the cycle runs without numbers, it is not tuning — it is a walk through the code.

### 14. Mapping list → move

| What `list` shows | First idiomatic move | Not first |
|---------------------|------------------------|---------|
| `+=` string in a loop | `strings.Builder` | Pool |
| `append` growth without cap | `make(..., 0, n)` | unsafe |
| `json.Marshal` + Write | `Encoder` / smaller payload | Pool around `[]byte` |
| O(n²) loop | different structure | micro-inline |
| `runtime.gc*` in CPU | allocs profile | “turn off GC” |
| `bytes.Buffer` alloc churn | only then consider Pool | Pool everywhere |
| DB driver / syscall | I/O / query | Builder |

### 15. Bench as a hot-helper contract

When you extract a function from a hot path:

```go
func BenchmarkJoinBuilder(b *testing.B) {
	parts := sampleParts() // fixed input
	b.ReportAllocs()
	for b.Loop() {
		_ = joinBuilder(parts)
	}
}
```

A PR without a before/after table for an allocation claim — incomplete. Never claim an optimization without measuring.

### 16. Pool lifecycle — detailed trap

```go
buf := pool.Get().(*bytes.Buffer)
buf.Reset()
// ...
pool.Put(buf)
// FORBIDDEN: use buf here or keep an alias
```

If another **goroutine** still reads `buf` after `Put`, you have a data race and a leak of someone else’s bytes into the response. The race detector helps; `Reset`+ownership discipline is required.

### 17. Grow heuristic

```go
var b strings.Builder
b.Grow(len(parts) * avgLen)
```

A rough estimate. Too-small Grow → more realloc (still better than `+=`). Too-large → higher peak memory per Builder; measure if RSS worries you.

### 18. Cold vs hot path

Optimizing login bcrypt “because it is in the CPU profile” may be expected. Optimizing an admin CSV export that runs once at night — often not worth the complexity. Ask: does this path hold the SLO under the load we pay for?

### 19. Complexity as a cost

Every Pool, every `unsafe`, every hand-rolled buffer:

- increases cognitive load;
- increases bug surface;
- requires a comment *why* and a *number*.

If the bench shows +3% and the code becomes unreadable — often revert. Idiomatic Go prefers clarity until a profile forces otherwise.

### 20. Link escape ↔ allocs profile

`-m` says “escapes to heap”. Allocs profile says “how much that costs under load”. Trust the profile under load first; `-m` explains *why* it allocates. The reverse (blind hunt through `-m`) wastes hours.

## Rules and syntax

```go
var b strings.Builder
b.Grow(n) // optional
b.WriteString(s)
out := b.String()
```

```go
out := make([]T, 0, len(in))
```

```bash
go build -gcflags="-m -m" ./pkg 2>&1 | less
go test -bench=BenchmarkJoin -benchmem ./pkg
```

Rules:

- Do not introduce Pool without an allocs profile + bench confirmation.
- Do not sacrifice readability for 1% without SLO pressure.
- Always repeat benchmark / profile / load after a change.
- **Never** claim an optimization without measuring before and after.
- Correctness tests stay green — a faster wrong result is not a win.
- Algorithm and I/O before micro buffers.

## Examples

### Example 1 — String in a loop vs Builder

#### Predict

Which variant will have more `allocs/op` on a large `parts` and why?

```go
package join

import "strings"

func joinPlus(parts []string) string {
	s := ""
	for _, p := range parts {
		s += p // many allocations
	}
	return s
}

func joinBuilder(parts []string) string {
	var b strings.Builder
	for _, p := range parts {
		b.WriteString(p)
	}
	return b.String()
}
```

#### Answer

`joinPlus` — every `+=` is a new string. Builder writes into one buffer. Confirm with `-benchmem`; do not trust feeling.

#### What happens here

Classic hot-path fix when `list` shows `+=`. Measure before/after.

### Example 2 — Preallocate slice

#### Predict

What does `make([]string, 0, len(in))` save compared to `var out []string`?

```go
func mapIDs(in []Item) []string {
	out := make([]string, 0, len(in))
	for _, it := range in {
		out = append(out, it.ID)
	}
	return out
}

type Item struct {
	ID string
}
```

#### Answer

It reduces `append` growth (buffer copies). Visible on large `n` on a hot path — benchmem shows it.

#### What happens here

Capacity ahead of time = fewer allocations during the loop. Small, but measurable when the profile says so.

### Example 3 — Pool with caution

#### Predict

Which two steps are mandatory with `Get`/`Put`?

```go
package handler

import (
	"bytes"
	"net/http"
	"sync"
)

var bufPool = sync.Pool{
	New: func() any {
		return new(bytes.Buffer)
	},
}

func handle(w http.ResponseWriter, r *http.Request) {
	buf := bufPool.Get().(*bytes.Buffer)
	buf.Reset()
	defer bufPool.Put(buf)
	// write into buf, then buf.WriteTo(w)
	_, _ = buf.WriteTo(w)
}
```

#### Answer

`Reset` before use; do not keep a reference after `Put`. Pool only if allocs + bench prove the need.

#### What happens here

Buffer reuse. Without Reset — old data. After Put — the object may go to another request. Without a profile — unnecessary complexity.

### Example 4 — Algorithm before micro

#### Predict

CPU `list` shows this loop on 50k elements. Does Pool help?

```go
func findSlow(items []Item, id string) (Item, bool) {
	for _, it := range items {
		if it.ID == id {
			return it, true
		}
	}
	return Item{}, false
}

// better: map[string]Item built once (or an index in the DB)
```

#### Answer

Not as a first move. You need a data structure / less work. Micro tuning will not save an O(n) scan on a hot path if O(1) lookup is possible.

#### What happens here

“Real world” order: algorithm first. The profile shows the loop; the fix is the data model.

### Example 5 — Escape analysis look

#### Predict

Which function typically allocates on the heap and why?

```go
package sample

func answer() *int {
	x := 42
	return &x // x escapes to heap
}

func local() int {
	x := 42
	return x // typically stack
}
```

```bash
go build -gcflags=-m ./sample
```

#### Answer

`answer` — returns a **pointer**; the local escapes to the heap. `local` — value. Do not force “everything on the stack” if the API needs `*T`.

#### What happens here

`-m` teaches why it allocates. Allocs profile measures whether it hurts you. Without measurement there is no claim.

### Example 6 — JSON Encoder vs Marshal

#### Predict

Where do you expect an extra `[]byte` peak?

```go
package api

import (
	"encoding/json"
	"net/http"
)

func writeEncode(w http.ResponseWriter, v any) error {
	enc := json.NewEncoder(w)
	return enc.Encode(v)
}

func writeMarshal(w http.ResponseWriter, v any) error {
	b, err := json.Marshal(v)
	if err != nil {
		return err
	}
	_, err = w.Write(b)
	return err
}
```

#### Answer

`writeMarshal` holds the whole JSON in `[]byte` before writing. Measure on *your* payload — Encoder is not magic.

#### What happens here

Same result for the client; different peak. Profile / bench decide.

### Example 7 — Builder Grow

#### Predict

What happens if `Grow` hits a too-small number?

```go
func joinGrow(parts []string) string {
	var b strings.Builder
	b.Grow(len(parts) * 8) // rough estimate
	for _, p := range parts {
		b.WriteString(p)
	}
	return b.String()
}
```

#### Answer

More internal expansions — still better than `+=`. Not a semantics error.

#### What happens here

Grow is a hint. Measure if that exact path is in `list`.

### Example 8 — Fake optimization without measuring

#### Predict

Why should this PR be rejected even if it “looks faster”?

```go
// PR description: "optimized format" — no bench table, no pprof
func FormatFast(m Money) string {
	return fmt.Sprintf("%d", m.MinorUnits) // changed semantics
}
```

#### Answer

No baseline / after numbers; semantics may be broken. **Never** claim an optimization without measuring; correctness is mandatory.

#### What happens here

Team culture: performance claim = evidence. Otherwise it is guessing.

## Decision analysis

| Decision | Why |
|--------|--------|
| Builder for string loops | Fewer allocations, readable |
| Grow / preallocate | Fewer copies |
| Pool only with evidence | Less complexity and bugs |
| Algorithm first | Biggest win |
| `-m` for learning | Understanding heap pressure |
| Encoder when the profile says | Lower peak on large JSON |
| Revert if bench does not confirm | 14.01 discipline |

## Trade-offs

- **Micro-optimization** — gain, loss of readability.
- **Pool** — less GC, risk of retained memory and reuse bugs.
- **Avoiding pointer API** — less escape, clumsier contract.
- **Hand-rolled `[]byte`** — speed, more code and mistakes.
- **Lab bench only** — fast, can lie about prod P99.
- **Prefetch / result cache** — less work, risk of stale data.

## Common mistakes

1. Pool as the first reaction to every allocation.
2. Keeping a reference to a pooled object after Put.
3. Optimizing a cold path.
4. Ignoring SQL / N+1 because “Go is slow”.
5. Committing code that is slower after an “optimization” without a bench.
6. Treating `-m` output as mandatory TODOs.
7. Claiming “optimized” without a baseline measurement.
8. Several micro-changes in one PR without attributability.
9. Sacrificing semantics for lower `ns/op`.
10. Builder / Pool while Trace shows a DB span.

## Idiomatic Go

- Profile → small change → bench / load.
- Stdlib `strings.Builder`, `bytes.Buffer` — those first, then Pool.
- Prefer clear types; `any` boxing allocates.
- Document a non-obvious performance invariant in a comment **with a measurement**.
- Do not introduce `unsafe` “along the way”.
- Prefer a clearer algorithm until a profile says otherwise.

## Practical scenario

A CSV export endpoint allocates gigabytes via `s += row`. Allocs profile is red; `list` shows `+=`. They switch to `strings.Builder` / `bufio.Writer` into the response — RSS drops, P99 drops. Numbers in the PR. Later a junior adds a Pool around Builder; the bench shows no gain; review deletes the Pool. The team adopts the rule: algorithm and Builder first, Pool only with numbers; **no** speedup claim without measuring.

Second incident: an “optimized” cache without TTL keeps the heap busy. Heap profile shows the map; the “speedup” was a leak. Revert + TTL. Measure heap too, not only `ns/op`.

## Check questions

1. **Why Builder?**  
   Reduces allocations when building a string in a loop.

2. **When Pool?**  
   When an allocs profile shows frequent short-lived objects of the same type and a bench confirms the gain.

3. **What does escape analysis do?**  
   Decides stack vs heap for objects.

4. **What comes before micro tuning?**  
   Algorithm, less work, I/O.

5. **How to verify the effect?**  
   Same benchmark / profile / load as the baseline — without that there is no claim.

6. **When is allocation not the problem?**  
   When the app layer does not hold the latency budget (e.g. DB dominates).

7. **Why not `-m` as a backlog?**  
   It teaches the cause; it does not replace measurement under load.

```text
SLO clear → load → pprof → hypothesis → change → bench/profile → keep/revert
```

### Checklist after tuning

1. Correctness tests still pass.
2. Bench / profile shows improvement on the **same** scenario.
3. No new Pool without numbers.
4. No `unsafe` “along the way”.
5. README / runbook updated if needed.
6. No sentence “optimized” without a table / excerpt.

### When allocation is NOT the problem

If an endpoint spends 50 ms in DB and 0.2 ms in Go, reducing allocations will not move P99. That is why 14.01: measure first.

### Escape and API design

Returning `*T` often escapes. That is OK for large structures and mutability. Do not change the API to value types only because of `-m` if you break semantics.

## Deeper layer: measurement culture in a PR

### Performance PR template

```text
## Baseline
- bench: ...
- load P99: ...
- pprof list: ...

## Change
- one-sentence hypothesis
- one mechanical move (Builder / map / ...)

## After
- same measurements
- keep/revert decision
```

Without this a “perf PR” is noise.

### What to say to the reviewer

“Allocs profile showed `+=` in `exportCSV`; Builder; `BenchmarkExport` 12 allocs/op → 2; P99 2.1s → 280ms under the same hey.”  
That is the language of 14.01–14.03.

### Anti-template

“I refactored for performance.”  
Without a number — reject or ask for measurement.
