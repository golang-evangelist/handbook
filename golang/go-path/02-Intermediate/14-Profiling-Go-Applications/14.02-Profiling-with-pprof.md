# 14.02 Profiling with pprof: HTTP, runtime, and go tool pprof

> **Go Path - Zero to Gopher** / **02 Intermediate → Profiling Go Applications** / Lesson 14.02

## Lesson goals

- Enable **net/http/pprof** safely — **localhost ONLY**, never the public internet.
- Use **runtime/pprof** for a CPU / memory file from a CLI or test.
- Read profiles via **go tool pprof**: `top`, `list`, `web`, local `-http`.
- Distinguish **CPU** (stack samples), **allocs**, **heap**, and **goroutine** profiles.
- Understand caution around **DefaultServeMux** — a blank import must not “leak” onto the public API.

## Prerequisite

- 14.01 (measure first; choose profile by symptom).
- A basic HTTP server with a separate mux.
- Graphviz optional for the `web` command.
- `hey` or a similar load generator locally.

## Problem this lesson solves

Without pprof you guess where the cost is. With **badly exposed** pprof:

- an attacker reads stacks and internal structure;
- expensive handlers (`profile?seconds=30`) become a DoS surface;
- heap/goroutine dumps leak production details.

This lesson teaches **how** to capture a profile and **where** the listener may live: **127.0.0.1** (or an equivalent admin path with port-forward), **never** a public Ingress / LoadBalancer / `0.0.0.0` in the cloud without strict control.

## Mental model

**pprof** samples or records events and writes a **profile**. **go tool pprof** reads it and ranks it.

Three common sources:

1. `net/http/pprof` — HTTP handlers on an **admin** server (`127.0.0.1:6060`).
2. `runtime/pprof` — `StartCPUProfile` / `StopCPUProfile` (and write heap) to a file.
3. `go test -cpuprofile` / `-memprofile` — with a benchmark.

What each type means (repeat from 14.01, now operational):

| Endpoint / type | Meaning |
|----------------|----------|
| `profile?seconds=N` | CPU: **stack samples** over N seconds |
| `heap` | currently live on the heap (inuse) |
| `allocs` | allocations over the lifetime (churn) |
| `goroutine` | stacks of all **goroutines** |
| `block` / `mutex` | waiting / contention (with rate API) |

UI locally:

```bash
go tool pprof -http=127.0.0.1:8081 <source>
```

And that UI is also **localhost** — do not open it on a public host.

## Mechanism

Mechanism here = *how to get a signal safely and how to read it*. Longer than the examples because a bind-address mistake costs an incident.

### path A — net/http/pprof on an admin listener

The `net/http/pprof` package registers handlers. The key danger: a **blank import**

```go
import _ "net/http/pprof"
```

attaches routes to `http.DefaultServeMux`. If your public `ListenAndServe(":8080", nil)` uses DefaultServeMux, **pprof leaks outward**.

Correct pattern:

1. Business mux **without** pprof.
2. Separate admin mux **with** explicit `pprof.Index` / `Handler(...)`.
3. Admin `ListenAndServe("127.0.0.1:6060", adminMux)` — **loopback**.

In Kubernetes: `kubectl port-forward pod/... 6060:6060`, **not** a Service of type LoadBalancer on 6060, **not** an Ingress path `/debug/pprof`.

### path B — runtime/pprof to a file

For a CLI, one-shot job, or reproduction outside HTTP:

```go
f, err := os.Create("cpu.pprof")
if err != nil {
	log.Fatal(err)
}
defer f.Close()
if err := pprof.StartCPUProfile(f); err != nil {
	log.Fatal(err)
}
defer pprof.StopCPUProfile()
// do the work / load
```

A CPU profile writes **stack samples** while capture is active. After: `go tool pprof cpu.pprof`.

Heap to a file (simplified):

```go
f, err := os.Create("heap.pprof")
if err != nil {
	log.Fatal(err)
}
defer f.Close()
runtime.GC() // optional: more stable snapshot before write
if err := pprof.WriteHeapProfile(f); err != nil {
	log.Fatal(err)
}
```

### path C — go test profiles

```bash
go test -bench=. -cpuprofile=cpu.out -memprofile=mem.out ./pkg
go tool pprof cpu.out
go tool pprof -alloc_space mem.out
```

Good for libraries. For a live HTTP service still prefer admin pprof **under** `hey`.

### CPU = stack samples

During `profile?seconds=30` the runtime periodically samples stacks of **goroutines** that consume CPU. `go tool pprof` aggregates:

- **flat** — samples in the function itself;
- **cum** — function + descendants.

Thick **cum**, small **flat** → children do the work; do not optimize an “empty” parent.

### heap vs allocs

- **heap** (`inuse_space` / `inuse_objects`) — what is *now* live; leak, cache, retained buffers.
- **allocs** (`alloc_space` / `alloc_objects`) — what was *allocated* (churn); GC pressure.

For “RAM grows and does not fall” → heap + goroutine.  
For “GC eats CPU / many allocations” → allocs (+ benchmem from 14.01).

### goroutine profile

`/debug/pprof/goroutine` shows stacks. Use when:

- the number of **goroutines** grows monotonically;
- you suspect a forgotten `go func` without cancellation;
- latency is high, CPU is low — you see where they “sit”.

Not a substitute for the race detector; it is complementary.

### go tool pprof navigation

Interactive:

```text
(pprof) top
(pprof) top20
(pprof) list FunctionName
(pprof) web
```

- `top` — ranking; start here.
- `list` — source lines with counts; here you confirm the hypothesis.
- `web` — call graph (Graphviz); look for a thick node.

Local HTTP UI:

```bash
go tool pprof -http=127.0.0.1:8081 http://127.0.0.1:6060/debug/pprof/profile?seconds=15
```

Always `127.0.0.1` for `-http`, not `0.0.0.0`.

### DefaultServeMux — detailed caution

| Situation | Risk | Mitigation |
|-----------|-------|------------|
| `import _ "net/http/pprof"` + `http.ListenAndServe(":80", nil)` | pprof public | separate mux; no blank import on public |
| `ListenAndServe(":6060", admin)` | cloud scanner finds the port | bind `127.0.0.1:6060` + port-forward |
| Ingress `/debug/pprof` | internet DoS + leak | ban the path; NetworkPolicy |
| Same mux business+pprof with “auth middleware” | middleware order mistake | physically separate listener |

Team rule: **pprof is not “temporarily” opened on 0.0.0.0**. Temporary becomes forever.

### block and mutex — enable consciously

By default block/mutex profiles may be empty:

```go
runtime.SetBlockProfileRate(1)        // 1 = every block; in prod pick a higher value (rarer sample)
runtime.SetMutexProfileFraction(10)   // 1/10 of events
```

There is a cost. Enable while debugging contention; document in the runbook; do not leave `Rate(1)` forever without reason.

### Reading order for one CPU profile

```text
1. Capture 15–30 s UNDER LOAD (hey)
2. go tool pprof ... 
3. top20 — who dominates flat/cum?
4. list ThatFunction — which line?
5. Hypothesis in one sentence (template from 14.01)
6. Change (14.03) → measure again
```

If you skip `list`, you often blame the wrong parent from `top`.

### Flat vs cum — mini mechanism

Example: `top` shows `json.Marshal` with large cum, while flat is in `encodeState.reflectValue`. Optimizing “remove Marshal” can be wrong if you actually call Marshal in a loop — `list` shows *your* call. Read both numbers.

### Inlining and “shifted” lines

The compiler inlines tiny functions. `list` sometimes attributes samples to the parent. If a line looks “weird”, look at the caller too. Do not claim a bug in the stdlib until you check your call site.

### GC in a CPU profile

`runtime.gc*` in `top` is often not a “bug in the runtime”. Often it is a *consequence* of your alloc churn → go to an **allocs** profile. 14.01: CPU vs memory are different questions.

### seconds — how long to capture

| Duration | When |
|----------|-----|
| 5 s | rough smoke, often noise |
| 15–30 s | under stable load — default |
| 60 s+ | rare; more impact on latency during capture |

Under variable load a short sample lies. Align `hey -z` with `seconds`.

### Profile files and git

Do not commit huge `.pprof` / `.pb.gz` into the repo. Keep them as a CI artifact or temporary file. In a ticket redact paths if secrets leak into the stack (rare, but possible in user strings on the stack).

### Feature flag pattern

```go
addr := os.Getenv("PPROF_ADDR") // e.g. "127.0.0.1:6060"
if addr != "" {
	go func() {
		mux := http.NewServeMux()
		// register pprof handlers...
		log.Println("pprof listening", addr)
		log.Println(http.ListenAndServe(addr, mux))
	}()
}
```

Empty env = disabled. In prod: only with a runbook and NetworkPolicy.

### K8s runbook excerpt (Mechanism → ops)

```bash
kubectl port-forward pod/orders-x 6060:6060
hey -z 30s -c 20 http://127.0.0.1:8080/v1/orders/1
go tool pprof -http=127.0.0.1:8081 http://127.0.0.1:6060/debug/pprof/profile?seconds=20
```

Keep this internal. Never Ingress `/debug/pprof`.

### What else pprof HTTP offers

- `/debug/pprof/` — index
- `/debug/pprof/cmdline`
- `/debug/pprof/symbol`
- `/debug/pprof/trace` — execution Trace (another story; useful, but harder to start with)
- `heap`, `allocs`, `goroutine`, `threadcreate`, `block`, `mutex`

Start with CPU + allocs + goroutine. The rest by symptom from 14.01.

### Security checklist before capturing on staging

1. Listener on `127.0.0.1` or an admin network?
2. No Service/Ingress on the pprof port?
3. Load is local / internally generated?
4. Do you know how many `seconds`?
5. Do you know that after capture you look at `top` then `list`?

If 1–2 fail — **do not capture**; first fix the bind to `127.0.0.1` / remove the public surface.

## Rules and syntax

Explicit registration (no blank import on the public mux):

```go
mux := http.NewServeMux()
mux.HandleFunc("/debug/pprof/", pprof.Index)
mux.HandleFunc("/debug/pprof/cmdline", pprof.Cmdline)
mux.HandleFunc("/debug/pprof/profile", pprof.Profile)
mux.HandleFunc("/debug/pprof/symbol", pprof.Symbol)
mux.HandleFunc("/debug/pprof/trace", pprof.Trace)
mux.Handle("/debug/pprof/heap", pprof.Handler("heap"))
mux.Handle("/debug/pprof/goroutine", pprof.Handler("goroutine"))
mux.Handle("/debug/pprof/allocs", pprof.Handler("allocs"))
mux.Handle("/debug/pprof/block", pprof.Handler("block"))
mux.Handle("/debug/pprof/mutex", pprof.Handler("mutex"))
go http.ListenAndServe("127.0.0.1:6060", mux)
```

Rules:

- Loopback only or mTLS / VPN admin — **localhost ONLY** as the default policy.
- Do not log raw profiles publicly in a ticket without need.
- Keep CPU `seconds` reasonable (15–30) under load.
- Do not use `ListenAndServe(":6060", ...)` on a cloud VM “temporarily”.
- For block/mutex: `SetBlockProfileRate` / `SetMutexProfileFraction` consciously.
- `go tool pprof -http=127.0.0.1:...` — never a public bind for the UI.

## Examples

### Example 1 — Safe admin listener

#### Predict

Why must the business mux on `:8080` and admin on `127.0.0.1:6060` be separate?

```go
package main

import (
	"log"
	"net/http"
	"net/http/pprof"
)

func main() {
	business := http.NewServeMux()
	business.HandleFunc("GET /v1/hello", hello)
	go func() {
		log.Fatal(http.ListenAndServe(":8080", business))
	}()

	admin := http.NewServeMux()
	admin.HandleFunc("/debug/pprof/", pprof.Index)
	admin.HandleFunc("/debug/pprof/cmdline", pprof.Cmdline)
	admin.HandleFunc("/debug/pprof/profile", pprof.Profile)
	admin.HandleFunc("/debug/pprof/symbol", pprof.Symbol)
	admin.HandleFunc("/debug/pprof/trace", pprof.Trace)
	admin.Handle("/debug/pprof/heap", pprof.Handler("heap"))
	admin.Handle("/debug/pprof/goroutine", pprof.Handler("goroutine"))
	admin.Handle("/debug/pprof/allocs", pprof.Handler("allocs"))
	admin.Handle("/debug/pprof/block", pprof.Handler("block"))
	admin.Handle("/debug/pprof/mutex", pprof.Handler("mutex"))
	log.Println("pprof on 127.0.0.1:6060")
	log.Fatal(http.ListenAndServe("127.0.0.1:6060", admin))
}

func hello(w http.ResponseWriter, r *http.Request) {
	_, _ = w.Write([]byte("ok"))
}
```

#### Answer

The public port must not know `/debug/pprof`. Admin is loopback only; in K8s port-forward, not LoadBalancer.

#### What happens here

Two `ServeMux`, two listeners. Blank import is not needed. `DefaultServeMux` stays untouched.

### Example 2 — CPU profile to a file (runtime/pprof)

#### Predict

When do you choose a file instead of HTTP pprof?

```go
package main

import (
	"log"
	"os"
	"runtime/pprof"
)

func main() {
	f, err := os.Create("cpu.pprof")
	if err != nil {
		log.Fatal(err)
	}
	defer f.Close()
	if err := pprof.StartCPUProfile(f); err != nil {
		log.Fatal(err)
	}
	defer pprof.StopCPUProfile()

	runWorkload() // your load / CLI work
}
```

#### Answer

CLI, batch job, reproduction outside an HTTP server, or when you do not want an HTTP admin surface at all.

#### What happens here

`StartCPUProfile` writes stack samples until `StopCPUProfile`. After: `go tool pprof cpu.pprof` then `top` / `list`.

### Example 3 — go test profiles

#### Predict

What do you get from `-memprofile` that benchmem alone does not show?

```bash
go test -bench=. -cpuprofile=cpu.out -memprofile=mem.out ./pkg
go tool pprof cpu.out
go tool pprof -alloc_space mem.out
```

#### Answer

The distribution of *where* allocation / CPU happens in the stack, not just the aggregate `B/op`.

#### What happens here

The benchmark generates a profile alongside the measurement. Good for a lib. For a service: HTTP pprof under `hey`.

### Example 4 — Interactive top / list / web

#### Predict

What is the order and why does `list` come after `top`?

```text
(pprof) top20
(pprof) list encodeJSON
(pprof) web
```

#### Answer

`top` narrows the candidate; `list` confirms the line; `web` gives call context. Without `list` you often blame the wrong function.

#### What happens here

Navigation from symptom to line. Graphviz needed for `web`.

### Example 5 — Local HTTP UI (still localhost)

#### Predict

Why `-http=127.0.0.1:8081`, and not `-http=:8081`?

```bash
go tool pprof -http=127.0.0.1:8081 http://127.0.0.1:6060/debug/pprof/profile?seconds=15
```

#### Answer

The UI listener also must not be on `0.0.0.0` / all addresses. Same principle: localhost ONLY.

#### What happens here

Downloads a CPU profile for 15 s from the admin port and opens the UI locally. Do not use a public host.

### Example 6 — allocs vs heap

#### Predict

Which command for “too much GC”, which for “RAM does not fall”?

```bash
go tool pprof http://127.0.0.1:6060/debug/pprof/allocs
go tool pprof http://127.0.0.1:6060/debug/pprof/heap
```

#### Answer

GC / churn → allocs. Retention / leak → heap (+ goroutine).

#### What happens here

Two memory questions, two types. Mixing gives the wrong fix (Pool vs turning off a cache).

### Example 7 — Dangerous blank import

#### Predict

What is wrong?

```go
import _ "net/http/pprof"

func main() {
	http.HandleFunc("/v1/hello", hello)
	log.Fatal(http.ListenAndServe(":8080", nil)) // DefaultServeMux
}
```

#### Answer

pprof routes are on the same mux as the public API on `:8080`. Leak + DoS. Use the Example 1 pattern.

#### What happens here

Blank import registers on `DefaultServeMux`. `nil` handler = DefaultServeMux. Classic incident.

### Example 8 — goroutine profile under leak suspicion

#### Predict

The number of **goroutines** grows after every request. Which URL and what do you look for in `top`/`list`?

```bash
go tool pprof http://127.0.0.1:6060/debug/pprof/goroutine
```

#### Answer

You look for a repeating stack of “stuck” **goroutines** (e.g. waiting on a `channel` with no sender, HTTP client without `Close`). Then fix the lifecycle — not a Pool.

#### What happens here

A goroutine profile is a map of *who is alive*, not *who burns CPU*.

## Decision analysis

| Decision | Why |
|--------|--------|
| Separate admin mux | No leak onto the public API |
| Loopback / port-forward | Practical security |
| top → list → web | Fast navigation to the line |
| allocs for GC pressure | Sees churn, not just a snapshot |
| heap for retention | Sees live |
| seconds=15–30 | Enough sample, tolerable cost |
| PPROF_ADDR env | Only when needed |
| No blank import on public | DefaultServeMux caution |

## Trade-offs

- **HTTP pprof** — convenient on a live process, must be protected.
- **File profile (runtime/pprof)** — simple offline, requires local reproduction.
- **Longer CPU seconds** — better signal, more impact on latency during capture.
- **web graph** — readable, needs Graphviz.
- **block rate=1** — rich signal, higher overhead.
- **UI `-http`** — convenient, still localhost ONLY.

## Common mistakes

1. Blank import + DefaultServeMux on public `:80` / `:8080`.
2. `ListenAndServe(":6060")` without a firewall in the cloud.
3. Reading an idle CPU profile as truth.
4. Mixing `alloc_space` and `inuse_space` without awareness.
5. Committing huge `.pprof` files to git.
6. Conclusion from `top` without `list` — wrong function.
7. Ingress path `/debug/pprof` “just for us”.
8. `go tool pprof -http=:8081` open on a shared machine / CI agent.
9. Duration 1 s under unstable load then “nothing there”.
10. Leaving `SetBlockProfileRate(1)` forever without measuring the cost.

## Idiomatic Go

- Feature flag / env `PPROF_ADDR=127.0.0.1:6060` — empty = disabled.
- Document in the runbook: port-forward + exact commands.
- Explicit handler registration on the admin mux.
- For block/mutex: rate API consciously.
- Do not profile in every CI loop without need.
- Same load before/after capture (discipline from 14.01).

## Practical scenario

A startup opens pprof on `0.0.0.0:6060` “temporarily”. An internet scanner finds the endpoint; CPU `profile?seconds=60` DoSes instances. Incident: they shut the port, move to `127.0.0.1` + `kubectl port-forward`, add NetworkPolicy. At the same time they find the real bug via `list` on `json.Marshal` in a loop. Security and performance go together — localhost ONLY is not paranoia, it is the default.

## Check questions

1. **Why not public pprof?**  
   Leak of internals + expensive handlers as a DoS surface.

2. **What does `top` do?**  
   Ranks functions by cost in the profile.

3. **What does `list` do?**  
   Shows source lines with samples.

4. **allocs vs heap?**  
   Allocation churn vs currently live memory.

5. **How safely in K8s?**  
   No Service on pprof; port-forward / admin network; bind localhost in the pod when you can.

6. **What is a CPU profile?**  
   Stack samples over an interval.

7. **Why DefaultServeMux caution?**  
   Blank import attaches pprof to the same mux as `ListenAndServe(..., nil)`.

## Common pprof misconceptions

1. **Flat vs cum** — flat is in the function; cum includes descendants. Thick cum + small flat often means children do the work.
2. **Inlined functions** — `list` can look “shifted”; look at the parent too.
3. **GC in a CPU profile** — `runtime.gc*` is not always a “bug”; go to allocs.
4. **One sample** — a 1 s profile under variable load lies; 15–30 s is better.
5. **Idle truth** — without load a CPU profile is noise.
6. **UI = safe** — only if it is on 127.0.0.1.

### CI note

Do not capture a CPU profile on every PR without need. For libraries: bench + occasional `-cpuprofile` on a release branch. For services: staging profile per incident or a night job with protection.

### Quick check before production

- Is pprof only on localhost / an admin path?
- Does NetworkPolicy / SecurityGroup block 6060 from outside?
- Does a runbook exist and use `127.0.0.1` in examples?
- Is blank import banned on the public server package (lint / review)?

## Deeper operational layer

### What to record in an incident ticket

- the load command;
- the exact profile URL / file name;
- `top20` excerpt;
- `list` excerpt of the hot function;
- hypothesis + whether it was confirmed after the fix.

Without that the next on-call repeats the same hunt.

### When to choose runtime/pprof over HTTP

- one-shot CLI;
- test reproduction;
- any extra port banned by policy;
- you want a deterministic file to attach as a CI artifact.

### When HTTP pprof wins

- long-lived service;
- you need heap/goroutine *on the spot*;
- you do not want a restart for capture;
- you already have admin port-forward discipline.

### Mapping symptom → URL (card)

| Symptom | URL |
|---------|-----|

| RAM live | `/debug/pprof/heap` |
| Goroutine count grows | `/debug/pprof/goroutine` |
| Waiting | `/debug/pprof/block` (with rate) |
