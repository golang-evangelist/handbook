# 03.01 Getting Started with Go and Relational Databases

> **Go Path - Zero to Gopher** / **02 Intermediate → Accessing Relational Databases in Go** / Lesson 03.01

## Lesson goals

After this lesson you should:

- explain the division of responsibility between `database/sql`, a database driver, and PostgreSQL
- open and verify a shared connection pool without treating `sql.Open` as a network check
- configure a bounded pool deliberately and understand what each setting controls
- use a request-scoped `context.Context` for every blocking database operation
- keep the DSN outside source control and close the pool correctly during graceful shutdown
- recognize the five most common pool-related production failures before they reach the database

## Prerequisite

- Go 1.22+; that is the course baseline. A newer API is named only where a lesson actually needs it
- A local PostgreSQL instance — for example from `docker run --rm -e POSTGRES_PASSWORD=dev -p 5432:5432 postgres:16`
- `context` basics: `context.Background()`, `context.WithTimeout`
- Error wrapping with `%w` (lesson 13.01 or 02.10)
- Environment-variable discipline: never hardcode credentials in source code

## Problem this lesson solves

The most common first-database mistake is to call `sql.Open` for every request, concatenate a query string with `fmt.Sprintf`, and assume that a non-nil `*sql.DB` means the database is reachable. None of those assumptions are correct.

`sql.DB` is a **concurrency-safe connection-pool handle**, not a single connection and not proof that authentication or networking works. `sql.Open` validates the driver name and parses the DSN; it does not open a connection. A successful `sql.Open` on port 9999 (where nothing listens) returns a non-nil `*sql.DB` with no error.

This lesson establishes a safe, production-ready bootstrap pattern. CRUD belongs in 03.03; transactions belong in 03.02.

## Mental model

```text
handler / service / repository
       │  context with deadline
       ▼
*sql.DB  ──────────────────────► driver (pgx stdlib adapter)
 pool manager                            │
  ├── idle connections (up to MaxIdle)   │   PostgreSQL wire protocol (TCP)
  ├── open connections (up to MaxOpen)   ▼
  └── waiting requests              PostgreSQL server
```

Key points:

- **`database/sql`** supplies the portable Go API and pool behavior. It is not tied to any specific database.
- **The driver** (here: `github.com/jackc/pgx/v5/stdlib`) implements the PostgreSQL wire protocol. The blank import `_ "github.com/jackc/pgx/v5/stdlib"` registers it by name.
- **`*sql.DB`** should be created once at process startup and shared by all repositories in the service. Creating it per-request creates uncontrolled connection handles and exhausts the database quickly.
- **`PingContext`** is the startup proof that a real network path and valid credentials exist.
- **A query leases a connection** from the pool. `rows.Close()` and `row.Scan()` return the connection; forgetting either creates a leak.

## Mechanism

### Installing the driver

Install one explicit, pinned version. `@latest` is not a reproducible instruction for CI:

```text
go get github.com/jackc/pgx/v5@v5.7.4
go mod tidy
```

Commit the updated `go.mod` and `go.sum`. A `go.sum` entry is a cryptographic guarantee that the module has not changed since it was first downloaded.

`v5.7.4` declares `go 1.21` in its own module file, so the Go 1.22 toolchain builds it. `v5.7.5` and later declare `go 1.23.0`. The command above stays on `v5.7.4` for that reason. Pinning `v5.7.5` or newer on a machine that must stay on Go 1.22 makes the `go` command download a newer toolchain (`GOTOOLCHAIN=auto`).

### The DSN

Use an environment variable — never a literal in a source file:

```text
DATABASE_URL=postgres://app:dev-only-change-me@localhost:5432/shop?sslmode=disable
```

`sslmode=disable` is acceptable only for a local lab. Production must use TLS — `sslmode=require` or the provider-specific TLS configuration. Log the DSN only without the password segment: `postgres://app:***@localhost:5432/shop`.

### Opening, configuring, and verifying the pool

```go
package data

import (
	"context"
	"database/sql"
	"fmt"
	"time"

	_ "github.com/jackc/pgx/v5/stdlib"
)

// Open creates a shared connection pool, configures it, and verifies
// that the database is reachable before returning to the caller.
// The caller is responsible for calling db.Close() once during graceful shutdown.
func Open(ctx context.Context, dsn string) (*sql.DB, error) {
	if dsn == "" {
		return nil, fmt.Errorf("Open: DATABASE_URL is required")
	}

	db, err := sql.Open("pgx", dsn)
	if err != nil {
		// sql.Open failing means the driver name is unknown or the DSN cannot be parsed.
		// The database may not be reachable yet — that is checked by PingContext.
		return nil, fmt.Errorf("open database handle: %w", err)
	}

	// Pool settings — these are policy, not universal magic numbers.
	// See the decision analysis section for how to size each one.
	db.SetMaxOpenConns(20)
	db.SetMaxIdleConns(10)
	db.SetConnMaxLifetime(30 * time.Minute)
	db.SetConnMaxIdleTime(5 * time.Minute)

	// PingContext opens one real connection and runs a lightweight check.
	// It is the only way to confirm credentials and network path at startup.
	pingCtx, cancel := context.WithTimeout(ctx, 5*time.Second)
	defer cancel()
	if err := db.PingContext(pingCtx); err != nil {
		_ = db.Close() // release the handle created above
		return nil, fmt.Errorf("ping database: %w", err)
	}

	return db, nil
}
```

### What happens here — step by step

1. **Blank import** `_ "github.com/jackc/pgx/v5/stdlib"` runs the driver's `init` function, which calls `sql.Register("pgx", ...)`. This is the intentional exception to the "no blank imports" style rule; the driver must register itself, and there is no other API for it.

2. **`sql.Open("pgx", dsn)`** validates the driver name ("pgx" must match what the driver registered) and parses the DSN string. No network activity happens. The returned `*sql.DB` is non-nil even if PostgreSQL is down — this is the most common misconception.

3. **Pool configuration:**
   - `SetMaxOpenConns(20)` — at most 20 connections to this database from this process. More requests wait.
   - `SetMaxIdleConns(10)` — up to 10 connections stay idle in the pool between requests. Idle connections consume database resources; setting this too high wastes a socket on the server side.
   - `SetConnMaxLifetime(30*time.Minute)` — a connection is closed and replaced after 30 minutes regardless of activity. This prevents "stale" connections that survive network middle-box timeouts.
   - `SetConnMaxIdleTime(5*time.Minute)` — a connection idle for 5 minutes is closed. Prevents accumulating idle connections after a traffic spike subsides.

4. **`PingContext`** opens one real TCP connection, authenticates, and runs a trivial server roundtrip. If it fails, the function closes the pool handle and returns a wrapped error. A service that skips this step reports "ready" before it can talk to the database.

5. **Caller responsibility** — the returned `*sql.DB` is shared across the process lifetime. Call `db.Close()` exactly once, in the graceful-shutdown path (e.g. after `http.Server.Shutdown`).

### Pool sizing — concrete calculation

```text
Scenario:
  PostgreSQL max_connections = 100
  Leave 20 for migrations, pgAdmin, and operations
  Available for application = 80
  Application replicas = 4

  MaxOpenConns per replica = 80 / 4 = 20
  MaxIdleConns = 50% of MaxOpenConns = 10 (keeps warm connections without wasting)
```

This is a starting point, not a formula. Under load, use `db.Stats()` to observe `WaitCount`, `WaitDuration`, and `MaxIdleClosed`.

If `SetMaxIdleConns` is higher than `SetMaxOpenConns`, `database/sql` lowers the idle limit to the open limit. An idle cap above the open cap does not create extra connections.

### The bridge: `database/sql`, the driver, PostgreSQL

Three different things sit on the path from a handler to a row. Mixing their names is how the first PostgreSQL service gets two pools and no clear API.

```text
your repository
    database/sql          portable API and the pool (*sql.DB, *sql.Tx, *sql.Rows)
    driver                pgx stdlib adapter, registered under the name "pgx"
    PostgreSQL            server. It does not know that the client is Go
```

`sql.Open("pgx", dsn)` does not return a `pgx.Conn`. The string `"pgx"` is only the name passed to `sql.Register` by the blank import. The value you hold is `*sql.DB`. Lessons 03.02 and 03.03 stay on that type: `BeginTx`, `QueryContext`, `ExecContext`.

The pgx module also has a native pool, `pgxpool.Pool`. That type is not `*sql.DB`. A repository written for one cannot take the other. Use the native pool when the feature does not fit `database/sql`:

- `COPY`
- `LISTEN` / `NOTIFY`
- a codec for a PostgreSQL type you do not want to scan as text

This area does not use `pgxpool` (`github.com/jackc/pgx/v5/pgxpool`). The next two lines are the boundary, not a program to paste:

```go
db, err := sql.Open("pgx", dsn)          // course path; *sql.DB
pool, err := pgxpool.New(ctx, dsn)       // native path; *pgxpool.Pool
```

#### What happens here

1. Both calls end up speaking the PostgreSQL wire protocol. The Go types above that protocol are different.
2. `*sql.DB` is what `BeginTx` and `QueryContext` are defined on. `*pgxpool.Pool` has its own methods and does not satisfy a parameter of type `*sql.DB`.
3. Each pool counts its own connections. Two pools with `MaxOpenConns` 20 on four replicas are 160 connections, not 80.
4. Keep one pool per process per database unless a PostgreSQL feature forces a second, and then split the connection budget on purpose.

### How a cancelled context reaches the server

`QueryContext`, `ExecContext`, and `PingContext` take a `context.Context`. When that context ends, `database/sql` asks the driver to stop waiting. The pgx adapter sends a PostgreSQL cancel request. The goroutine returns. The server may still finish the statement; cancel means the client stopped waiting, not that the statement was rolled back.

```text
handler ctx deadline
    QueryRowContext blocks in the pool if every connection is in use
        either a connection is leased, or ctx ends first
            pgx writes Bind/Execute
            on cancel, pgx sends a cancel request and the Go call returns
    the connection, if leased, goes back to the idle set
```

`WaitCount` in `db.Stats()` counts those waits. A timeout at the pool is `context.DeadlineExceeded`. It is not a SQL syntax error and not `sql.ErrNoRows`.

## Rules and syntax

| Rule | Reason |
|---|---|
| Pass `context.Context` to every blocking operation (`QueryContext`, `ExecContext`, `PingContext`) | Cancellation and deadlines propagate to the driver, which can cancel in-flight queries |
| Use `$1`, `$2`, … placeholders for user-supplied values | The driver sends values separately from the query string; the database cannot interpret them as SQL |
| Check every `Scan`, `Rows.Err`, `Close`, `Commit`, and `Rollback` return | Database failure is operational input, not an exception |
| Set pool limits deliberately with a known formula | An unlimited pool on multiple replicas can exceed the database's `max_connections` |
| Keep migration ownership outside request handlers | Schema changes need sequential ordering, backups, and human review |
| Never log a DSN that contains a password | Logs are often sent to aggregation services with broader access |

## Examples

### Example 1 — Using the pool in a repository

```go
package store

import (
	"context"
	"database/sql"
	"fmt"
	"time"
)

type ProductRepo struct {
	db *sql.DB
}

func NewProductRepo(db *sql.DB) ProductRepo {
	return ProductRepo{db: db}
}

// HealthCheck verifies the database is still reachable. Used by a readiness probe.
// Not called on every request — only by the health-check endpoint.
func (r ProductRepo) HealthCheck(ctx context.Context) error {
	pingCtx, cancel := context.WithTimeout(ctx, 2*time.Second)
	defer cancel()
	if err := r.db.PingContext(pingCtx); err != nil {
		return fmt.Errorf("productRepo health check: %w", err)
	}
	return nil
}
```

#### What happens here

`*sql.DB` is passed to the repository, not created inside it. The repository does not decide pool settings — that is the responsibility of the startup code. `HealthCheck` uses a short context; a normal query uses the request context from the handler.

### Example 2 — Observing pool statistics

```go
package monitor

import (
	"context"
	"database/sql"
	"log/slog"
	"time"
)

// LogPoolStats emits pool metrics at regular intervals.
// Run this as a background goroutine; stop it via context cancellation.
func LogPoolStats(ctx context.Context, db *sql.DB, log *slog.Logger, interval time.Duration) {
	t := time.NewTicker(interval)
	defer t.Stop()
	for {
		select {
		case <-ctx.Done():
			return
		case <-t.C:
			s := db.Stats()
			log.Info("db pool stats",
				"open", s.OpenConnections,
				"idle", s.Idle,
				"in_use", s.InUse,
				"wait_count", s.WaitCount,
				"wait_duration", s.WaitDuration,
			)
		}
	}
}
```

#### What happens here

`db.Stats()` returns a snapshot of the pool's current state. `WaitCount > 0` means requests are waiting for a free connection — the pool is undersized for the current load. `MaxIdleClosed` growing rapidly means `SetConnMaxIdleTime` is too aggressive.

### Example 3 — Graceful shutdown

```go
package main

import (
	"context"
	"log"
	"net/http"
	"os"
	"os/signal"
	"syscall"
	"time"

	"example.com/shop/internal/data"
)

func main() {
	db, err := data.Open(context.Background(), os.Getenv("DATABASE_URL"))
	if err != nil {
		log.Fatal(err)
	}
	// db.Close is deferred to after the HTTP server stops accepting new requests.
	// Closing the pool while handlers are still running causes "use of closed network connection".
	defer db.Close()

	srv := &http.Server{Addr: ":8080"}

	go func() {
		if err := srv.ListenAndServe(); err != nil && err != http.ErrServerClosed {
			log.Fatal(err)
		}
	}()

	quit := make(chan os.Signal, 1)
	signal.Notify(quit, syscall.SIGINT, syscall.SIGTERM)
	<-quit

	shutdownCtx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
	defer cancel()
	if err := srv.Shutdown(shutdownCtx); err != nil {
		log.Printf("server shutdown: %v", err)
	}
	// db.Close() runs here via defer, after all in-flight handlers have returned.
}
```

#### What happens here

`db.Close()` is placed via `defer` in `main` so it runs after `srv.Shutdown`. Shutdown drains in-flight requests first; only after all handlers return does the pool close. Closing the pool prematurely causes panics in handlers still executing queries.

### Example 4 — one statement on the shared pool

CRUD is lesson 03.03. This example only shows the shape every later statement uses: the shared `*sql.DB`, a child context, a PostgreSQL placeholder, and `sql.ErrNoRows` as data rather than a transport failure.

```go
package store

import (
	"context"
	"database/sql"
	"errors"
	"fmt"
	"time"
)

func (r ProductRepo) Price(ctx context.Context, id string) (int, error) {
	ctx, cancel := context.WithTimeout(ctx, 2*time.Second)
	defer cancel()

	var cents int
	err := r.db.QueryRowContext(ctx,
		`SELECT price_cents FROM products WHERE id = $1`,
		id,
	).Scan(&cents)
	if errors.Is(err, sql.ErrNoRows) {
		return 0, fmt.Errorf("product %s: %w", id, err)
	}
	if err != nil {
		return 0, fmt.Errorf("product price: %w", err)
	}
	return cents, nil
}
```

#### What happens here

1. `$1` is not string concatenation. The driver sends `id` separately from the SQL text. A value that contains quotes cannot change the statement.
2. The two-second timeout is a child of the request context. If the caller cancels first, that cancellation still wins.
3. `QueryRowContext` leases one connection. `Scan` returns it to the pool. There is no `*sql.Rows` value to `Close`.
4. `sql.ErrNoRows` means the statement ran and matched nothing. A down database, a cancelled context, or a saturated pool is a different error. Do not map all of them to HTTP 404.
5. The repository does not call `sql.Open`. It uses the pool created in `Open`.

## Decision analysis

| Decision | Choose when | Avoid when |
|---|---|---|
| `sql.Open` once at startup | building any production service | per-request open — it leaks |
| Explicit pool sizing | you have a measured replica count and database connection budget | defaults (unlimited) — they silently overload the database |
| `PingContext` at startup | service must not report "ready" before the database is reachable | inside every handler — it adds an extra roundtrip per request |
| `SetConnMaxLifetime` | database uses a connection load balancer or firewall with idle-connection timeouts | you control the network and DB directly and latency is the concern |
| `errors.Is(err, sql.ErrNoRows)` | mapping a not-found database result to a domain error | treating every database error as HTTP 500 |
| `database/sql` + the pgx stdlib driver | this area: one pool type for startup, transactions, and CRUD | `COPY`, `LISTEN`/`NOTIFY`, or a codec that `database/sql` cannot express |
| `pgxpool.Pool` | that PostgreSQL feature is actually required | alongside a second `*sql.DB` that was also given the full connection budget |

---

## Trade-offs

- **Large `MaxOpenConns`** reduces wait time for application requests but can exhaust the database's `max_connections`, causing other applications or migrations to fail.
- **Small `MaxIdleConns`** reduces the number of idle sockets on the database but increases connection-setup latency on traffic spikes (TCP handshake + TLS + authentication on each new connection).
- **Short `SetConnMaxLifetime`** keeps connections fresh across database failovers but creates continuous churn at high traffic.
- **Skipping `PingContext`** makes the startup faster but allows the service to accept traffic it cannot handle, resulting in 500s until the database becomes reachable.

---

## Common mistakes

1. **`sql.Open` inside a handler** — creates uncontrolled pool handles that are never closed. Each request opens new connections and exhausts the database.
2. **`fmt.Sprintf` to build queries** — user input becomes SQL text; allows SQL injection.
3. **Skipping `PingContext`** — the service reports "healthy" before the database is reachable; the first real request fails.
4. **`SetMaxOpenConns(100)` on every replica without calculation** — ten replicas can send 1000 connection requests to a database with `max_connections = 200`.
5. **Logging the full DSN** — the DSN contains credentials; logs often reach aggregation services with broader access than the application.
6. **Calling `db.Close()` before `srv.Shutdown`** — handlers still executing queries receive connection errors and return 500 for valid requests.
7. **A `*sql.DB` and a `pgxpool.Pool` that each use the full budget** — the server sees the sum. The name `"pgx"` in `sql.Open` is not already a native pool.

---

## Idiomatic Go

- Create one `*sql.DB` per process per database, in `main` or in the composition root, and pass it into repositories.
- The blank driver import sits next to `sql.Open`, not in every repository file.
- Repository methods take `context.Context` first and call `QueryContext`, `ExecContext`, or `QueryRowContext`.
- The DSN comes from the environment. `sslmode=disable` stays in the local lab.
- Stay on `database/sql` through lessons 03.02 and 03.03. Move a single call to `pgxpool` only when that call cannot be written with `database/sql`, and count its connections in the same budget.

## Practical scenario

A SaaS platform migrated from SQLite to PostgreSQL. The engineer copied the SQLite pattern (`sql.Open` in the handler, one connection per request). Under load, the database accepted connections until it hit `max_connections = 100` and started refusing new ones. The service logged "too many connections" errors intermittently — not consistently, because it depended on request timing.

The fix: one `Open` call at startup with `SetMaxOpenConns(20)` (four replicas, 80 connections budgeted for the application). `PingContext` added to the readiness probe. Load test confirmed the `WaitCount` stayed near zero and `max_connections` never exceeded 85 (including migrations and monitoring).

## Check questions

1. **What does `sql.Open` actually do?** Validates the driver name and parses the DSN. It does not open a network connection.

2. **Why is `PingContext` necessary at startup?** Because `sql.Open` succeeds even when the database is down. `PingContext` is the first operation that proves a real TCP connection, authentication, and a server roundtrip work.

3. **What happens if `MaxOpenConns` is not set?** The pool can open unlimited connections. On multiple replicas this easily exceeds the database's `max_connections`.

4. **Why should `db.Close` run after `srv.Shutdown`?** Handlers executing queries must finish before the pool closes. Closing early causes "use of closed network connection" errors.

5. **What does `SetConnMaxLifetime` prevent?** Connections that survive past network middle-box idle timeouts or past a database failover. After the lifetime expires, the pool opens a fresh connection.

6. **When should `PingContext` be called on every request?** Never — it adds an extra server roundtrip. Use it at startup and in a dedicated health-check endpoint.

7. **Why does this area use `*sql.DB` instead of `pgxpool.Pool`?** Transactions and CRUD in the next two lessons are written against `database/sql`. `sql.Open("pgx", dsn)` already uses pgx as the driver. The native pool is a different type, for PostgreSQL features that `database/sql` cannot express.

---

## Summary

`*sql.DB` is a shared, concurrency-safe connection-pool handle. `sql.Open("pgx", dsn)` uses pgx as the driver and still returns that handle, not a `pgx.Conn`. Open it once at startup, size it from the replica count and `max_connections`, prove the network with `PingContext`, pass `context.Context` into every call, and close the pool only after the HTTP server has drained in-flight requests. The next lesson makes several statements atomic with transactions.
