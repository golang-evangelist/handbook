# 03.02 Understanding RDBMS Transactions and Procedures with Go Language

> **Go Path - Zero to Gopher** / **02 Intermediate → Accessing Relational Databases in Go** / Lesson 03.02

## Lesson goals

After this lesson you should:

- decide when several database statements require one atomic transaction and when they do not
- use `BeginTx`, `defer tx.Rollback()`, and `tx.Commit()` without leaking a partial update
- understand each isolation level and know when to request one that is not the default
- call a stored procedure only when its database-side contract is justified
- implement a reusable `withTx` helper that propagates commit errors through a named return
- detect and handle serialization-conflict errors without an unbounded retry loop

## Prerequisite

- Lesson 03.01: `*sql.DB`, pool configuration, `context.Context`, `PingContext`
- Error wrapping with `%w` and `errors.Is` (lesson 13.01–13.04)
- Named return values and `defer` (lesson 02.02 or 13.09)

## Problem this lesson solves

An order workflow typically involves more than one write: reserve stock, create the order record, and append an audit event. If statement two fails after statement one succeeds, the domain is inconsistent — unless all writes share a transaction that either commits or rolls back as a unit.

The opposite mistake is equally expensive: starting a transaction for every read or wrapping a remote HTTP call inside a transaction. Transactions hold database connections, advisory locks, and row-level locks; a long-running transaction blocks vacuuming (in PostgreSQL) and delays other writers. Transactions should be short, local to the database, and justified by a documented invariant.

## Mental model

```text
BeginTx
   │
   ├── statement A  ──► ok
   │
   ├── statement B  ──► error
   │                       │
   │                       ▼
   └── Rollback ◄──────────┘

BeginTx
   │
   ├── statement A  ──► ok
   ├── statement B  ──► ok
   └── Commit       ──► ok (or error → returned to caller)
```

Rules that follow from the model:

1. `defer tx.Rollback()` is safe to call even after `Commit`. After a successful commit, `Rollback` returns `sql.ErrTxDone`, which the deferred call intentionally ignores.
2. Use `tx.ExecContext` / `tx.QueryRowContext`, not `db.ExecContext`. Using the outer `*sql.DB` inside a transaction is a silent correctness bug — that call runs outside the transaction boundary.
3. Commit explicitly and check the error. A commit can fail (network partition, PostgreSQL failover). Ignoring commit errors means the caller believes the operation succeeded when it did not.

## Mechanism

### Basic transaction pattern

```go
package store

import (
	"context"
	"database/sql"
	"fmt"
)

func (r ProductRepo) Transfer(ctx context.Context, fromID, toID int64, amount int64) error {
	tx, err := r.db.BeginTx(ctx, &sql.TxOptions{Isolation: sql.LevelReadCommitted})
	if err != nil {
		return fmt.Errorf("begin transaction: %w", err)
	}
	// defer Rollback before any early return — it is a no-op after Commit.
	defer tx.Rollback() //nolint:errcheck // intentional: ErrTxDone after commit is expected

	if _, err := tx.ExecContext(ctx,
		`UPDATE accounts SET balance = balance - $1 WHERE id = $2`, amount, fromID); err != nil {
		return fmt.Errorf("debit account %d: %w", fromID, err)
	}

	if _, err := tx.ExecContext(ctx,
		`UPDATE accounts SET balance = balance + $1 WHERE id = $2`, amount, toID); err != nil {
		return fmt.Errorf("credit account %d: %w", toID, err)
	}

	if err := tx.Commit(); err != nil {
		return fmt.Errorf("commit transfer: %w", err)
	}
	return nil
}
```

**What happens here — line by line:**

1. `BeginTx(ctx, &sql.TxOptions{Isolation: sql.LevelReadCommitted})` starts a transaction on a leased connection from the pool. The same connection is used for all subsequent `tx.*` calls.
2. `defer tx.Rollback()` — this is registered before any early returns. If the function returns early (from any `if err != nil { return ... }`), Rollback fires and the partial writes are undone.
3. Both `ExecContext` calls use `tx`, not `r.db`. If they used `r.db`, they would run on different connections, outside the transaction.
4. `tx.Commit()` — sends the commit command. If it fails (e.g. the database server crashed during the write), the error propagates to the caller. The deferred Rollback fires after `Commit` returns, but `sql.ErrTxDone` is returned because the transaction already completed (either committed or the server rolled it back).
5. The caller knows the operation either fully succeeded or fully failed — no partial state.

### Reusable `withTx` helper

Repeating BeginTx / defer Rollback / Commit in every repository method is boilerplate. Extract it:

```go
package store

import (
	"context"
	"database/sql"
	"fmt"
)

// withTx runs fn inside a transaction and commits if fn returns nil.
// If fn returns an error, the transaction is rolled back.
// Commit errors propagate through the named return.
func withTx(ctx context.Context, db *sql.DB, opts *sql.TxOptions, fn func(*sql.Tx) error) (err error) {
	tx, err := db.BeginTx(ctx, opts)
	if err != nil {
		return fmt.Errorf("withTx begin: %w", err)
	}

	defer func() {
		if err != nil {
			_ = tx.Rollback() // Rollback: secondary error, original is in err
			return
		}
		// fn succeeded — commit and propagate commit error through named return
		err = tx.Commit()
	}()

	return fn(tx)
}
```

**What happens here:**

1. `err` is a **named return variable**. The deferred closure captures it.
2. `fn(tx)` runs the business logic inside the transaction. Its return value becomes the named `err`.
3. The defer fires after `fn` returns:
   - If `err != nil` (fn failed): `Rollback` is called; `Rollback`'s error is secondary and discarded.
   - If `err == nil` (fn succeeded): `tx.Commit()` runs. If `Commit` fails, the named `err` is set to that error — the caller sees the commit failure.
4. The caller of `withTx` never sees partial state: either fn's error, commit's error, or `nil`.

**Usage:**

```go
func (r OrderRepo) PlaceOrder(ctx context.Context, o Order) error {
	return withTx(ctx, r.db, &sql.TxOptions{Isolation: sql.LevelReadCommitted}, func(tx *sql.Tx) error {
		if err := r.reserveStockInTx(ctx, tx, o.SKU, o.Quantity); err != nil {
			return err
		}
		if err := r.insertOrderInTx(ctx, tx, o); err != nil {
			return err
		}
		return r.auditInTx(ctx, tx, o)
	})
}
```

### Isolation levels and when to request them

`sql.LevelDefault` uses the database's configured default. For PostgreSQL that is `Read Committed`.

| Level | What it prevents | PostgreSQL behaviour |
|---|---|---|
| `LevelReadUncommitted` | (none) | PostgreSQL treats this as Read Committed |
| `LevelReadCommitted` | Dirty reads | **PostgreSQL default** — good starting point |
| `LevelRepeatableRead` | Non-repeatable reads | PostgreSQL uses MVCC; snapshot taken at first statement |
| `LevelSerializable` | Phantom reads, write skew | PostgreSQL may abort a valid transaction with a serialization error |

**Decision rule:** start with `LevelReadCommitted`. Upgrade to `LevelSerializable` only when a documented write-skew or phantom-read anomaly is possible and the invariant cannot be enforced with a conditional `UPDATE` predicate.

### Conditional update as an alternative to locking

Many "lost update" problems are better solved with a predicate in the `WHERE` clause than with a higher isolation level:

```go
// Instead of: read stock, check in Go, write unconditionally
// Use:        conditional update + check RowsAffected

result, err := tx.ExecContext(ctx, `
	UPDATE inventory
	SET available = available - $1
	WHERE sku = $2 AND available >= $1`, quantity, sku)
if err != nil {
	return fmt.Errorf("reserve stock: %w", err)
}
affected, err := result.RowsAffected()
if err != nil {
	return fmt.Errorf("reserve stock result: %w", err)
}
if affected != 1 {
	return ErrInsufficientStock
}
```

The database evaluates the predicate atomically at `LevelReadCommitted`. Two concurrent reservations for the last remaining item: exactly one `UPDATE` matches; the other sees `affected == 0`.

### Serialization conflicts and safe retries

At `LevelSerializable`, PostgreSQL may abort a valid transaction with error code `40001` (serialization failure). The application must retry:

```go
import "github.com/jackc/pgx/v5/pgconn"

func isSerializationFailure(err error) bool {
	var pgErr *pgconn.PgError
	return errors.As(err, &pgErr) && pgErr.Code == "40001"
}

// Retry only operations that are idempotent or use an idempotency key.
for attempt := 1; attempt <= 3; attempt++ {
	err = r.placeOrderSerializable(ctx, o)
	if err == nil || !isSerializationFailure(err) {
		break
	}
	time.Sleep(time.Duration(attempt) * 50 * time.Millisecond)
}
```

**Critical safety rule:** never retry blindly after an unknown network failure. A commit that returned a network error may have already succeeded on the server. Inspect a durable result or use an idempotency key before retrying.

### Stored procedures

Go can call a database function through `QueryRowContext` or `ExecContext`:

```go
var ordersLastWeek int
err = r.db.QueryRowContext(ctx,
	`SELECT * FROM get_orders_report($1, $2)`, startDate, endDate).
	Scan(&ordersLastWeek)
```

**When to use a stored procedure:**

- The logic genuinely belongs near the data (e.g. a reporting aggregation that would transfer megabytes of rows to Go for a simple count).
- The operation requires database-level privileges not granted to the application account.
- The procedure is versioned in the same migration system as the tables and reviewed in the same pull-request process.

**When not to use a stored procedure:**

- Ordinary CRUD that belongs in the application's repository layer.
- Logic that needs to be tested without a running database.
- "Magic" procedures that are updated outside the deployment pipeline.

---

## Rules and syntax

1. Always use `tx.ExecContext` / `tx.QueryRowContext` / `tx.QueryContext` inside a transaction — never `db.*`.
2. `defer tx.Rollback()` before the first early-return statement.
3. Check `tx.Commit()` return value. Assign it to the named return when using `withTx`.
4. Do not hold a transaction open across: HTTP calls, user input, message-broker publish, or sleeps.
5. `RowsAffected()` is not free — it runs a separate server query for some drivers. Call it only when you need it.
6. Log the retry attempt count and error code; a growing retry counter is a production signal.

## Examples

### Example 1 — Predict the result (wrong isolation of error)

```go
func (r Repo) Bad(ctx context.Context) error {
	tx, _ := r.db.BeginTx(ctx, nil)
	defer tx.Rollback()

	if _, err := r.db.ExecContext(ctx, "INSERT INTO log VALUES (1)"); err != nil { // BUG: r.db, not tx
		return err
	}
	return tx.Commit()
}
```

**Predict:** Is the `INSERT` part of the transaction?

**Answer:** No. `r.db.ExecContext` runs on a connection from the pool — a different connection from `tx`. The insert commits immediately, regardless of whether `tx` commits or rolls back. If `tx` rolls back, the log row remains.

---

### Example 2 — Predict the result (`defer Rollback` after `Commit`)

```go
func (r Repo) Safe(ctx context.Context) error {
	tx, err := r.db.BeginTx(ctx, nil)
	if err != nil {
		return err
	}
	defer tx.Rollback()

	if err := tx.Commit(); err != nil {
		return err
	}
	return nil
}
```

**Predict:** Does the defer panic or cause a double commit?

**Answer:** Neither. After a successful `Commit`, the deferred `tx.Rollback()` returns `sql.ErrTxDone` — the transaction is already finished. The error is silently ignored by the defer (no return value captured). This is the correct pattern.

---

### Example 3 — Full order placement with `withTx`

```go
package store_test

import (
	"context"
	"testing"

	"example.com/shop/internal/store"
)

func TestPlaceOrder_InsufficientStock(t *testing.T) {
	// Uses a real PostgreSQL transaction rolled back at the end of the test.
	db := testDB(t) // helper that opens a pool and registers t.Cleanup(db.Close)

	repo := store.NewOrderRepo(db)
	ctx := context.Background()

	// Seed one item in stock
	seedInventory(t, db, "SKU-001", 1)

	// First order: should succeed
	if err := repo.PlaceOrder(ctx, store.Order{SKU: "SKU-001", Quantity: 1}); err != nil {
		t.Fatalf("first order: %v", err)
	}

	// Second order: stock is zero, should return ErrInsufficientStock
	err := repo.PlaceOrder(ctx, store.Order{SKU: "SKU-001", Quantity: 1})
	if !errors.Is(err, store.ErrInsufficientStock) {
		t.Fatalf("expected ErrInsufficientStock, got %v", err)
	}
}
```

#### What happens here

Two concurrent-looking orders are sequential in this test. The first depletes the stock. The second hits `affected == 0` in the conditional update, returns `ErrInsufficientStock`, `withTx` rolls back, and the test asserts the sentinel error.

## Decision analysis

| Situation | Technique | Why |
|---|---|---|
| Multiple writes that share an invariant | `withTx` + conditional `UPDATE` predicate | Atomicity without manual rollback in every code path |
| Read then conditional write | Predicate in `WHERE` clause | Avoids a separate `SELECT` and a race at `ReadCommitted` |
| Risk of write skew (two transactions read same row, both update) | `LevelSerializable` + bounded retry | The only isolation level that prevents write skew in PostgreSQL |
| Procedure that aggregates server-side | Stored procedure via `QueryRowContext` | Avoids transferring large result sets to the application |
| Procedure for ordinary CRUD | Repository method in Go | Testable, versionable, reviewable without a database |
| Unknown network failure on commit | Idempotency key + inspect durable result | Blind retry risks double-write |

---

## Trade-offs

- **Long transactions** hold row locks and delay autovacuum. Keep the critical section to the minimum number of statements.
- **`LevelSerializable`** prevents more anomalies but increases abort rate under contention. Measure before choosing it for high-throughput paths.
- **Stored procedures** reduce round trips but move logic outside the Go test suite and the deployment pipeline unless they are embedded migrations.
- **`withTx` helper** centralizes lifecycle but can obscure transaction boundaries from code review — document the pattern in the package comment.

---

## Common mistakes

1. **Starting the transaction after the first write** — the operation that was supposed to be atomic is already committed.
2. **`db.ExecContext` instead of `tx.ExecContext`** — the statement runs outside the transaction silently.
3. **Forgetting `RowsAffected`** for conditional updates — UPDATE 0 looks like success.
4. **Committing in a `defer`** — the defer runs after every exit path, including error paths where the caller already returned an error; you may commit a partial state.
5. **Holding a transaction across a remote call** — if the HTTP call takes 10 seconds, the database connection and locks are held for 10 seconds.
6. **Unbounded retry on serialization failure** — without a backoff and maximum count, a hot-path retry storm can amplify the contention it is trying to resolve.

## Practical scenario

An e-commerce team introduced a referral credit system: when a user's referral code is used at checkout, the referrer gets a credit and the order is marked as referred. The first version wrote both in sequence without a transaction. Under load, one request could write the credit while another request read the order before the "referred" flag was set, resulting in duplicate credit grants.

The fix: wrap both writes in a `withTx` call at `LevelReadCommitted` with a conditional `UPDATE` predicate on the referral code (marking it as "used" atomically with the order). The predicate `WHERE code = $1 AND used = false` ensures only one concurrent request can match and proceed. `RowsAffected == 0` signals a duplicate attempt and returns a sentinel error mapped to HTTP 409.

## Check questions

1. **Why is `defer tx.Rollback()` safe even after a successful `Commit`?** `Rollback` returns `sql.ErrTxDone` when called on an already-completed transaction. The deferred call ignores that error.

2. **What is the silent bug in using `db.ExecContext` inside a transaction?** The call runs on a different pool connection — outside the transaction boundary. The statement commits immediately and independently, defeating atomicity.

3. **When should you use `LevelSerializable`?** When a documented anomaly (write skew, phantom read) cannot be prevented by a conditional `WHERE` predicate at `LevelReadCommitted`.

4. **Why must you not retry blindly after a commit network error?** The database may have committed the transaction before the connection dropped. A blind retry causes a duplicate write.

5. **What does `RowsAffected() == 0` mean for a conditional `UPDATE`?** No row matched the predicate. For a business invariant like stock reservation, it means the condition was not met (e.g. insufficient stock).

6. **What is the advantage of a `withTx` helper over writing `BeginTx`/`defer Rollback`/`Commit` in every method?** One place to maintain the lifecycle; consistent commit-error propagation through named return; no risk of forgetting `defer Rollback` in a new method.

---

## Summary

Transactions protect a documented invariant across related database operations. Begin early, use `tx.*` consistently, defer rollback, commit explicitly and check the result, keep the critical section short, and do not hold connections across remote calls. The `withTx` helper centralizes lifecycle and propagates commit errors cleanly. The next lesson applies these rules to full CRUD operations.
