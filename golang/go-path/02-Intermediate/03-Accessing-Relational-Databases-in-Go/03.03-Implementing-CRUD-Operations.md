# 03.03 CRUD with database/sql: Query, QueryRow, Exec, Scan, ErrNoRows

> **Go Path - Zero to Gopher** / **02 Intermediate → Accessing Relational Databases in Go** / Lesson 03.03

## Lesson goals

- Use **`Query`** / **`QueryContext`** for queries that return multiple rows, and handle **`Rows`** correctly.
- Use **`QueryRow`** / **`QueryRowContext`** for queries that return at most one row.
- Use **`Exec`** / **`ExecContext`** for `INSERT`, `UPDATE`, and `DELETE`, and read **`Result`** (`RowsAffected`, `LastInsertId`).
- Apply **prepared statements** (`PrepareContext`) inside a transaction when the same query runs repeatedly.
- Scan a row into a `struct` with **`Scan`**, in the correct column order.
- Distinguish **`sql.ErrNoRows`** from every other error, and close `Rows` with `Close` while also checking `rows.Err()`.
- Handle `NULL` columns with `sql.NullString`, `sql.NullInt64`, and similar types.

## Prerequisite

- Lessons 03.01 and 03.02 (`sql.DB`, the pool, `context`, transactions through `BeginTx`).
- Struct types in Go and `errors.Is` for comparing errors.

## Problem this lesson solves

A handler runs `Query`, iterates the result, and forgets `rows.Close()` on one branch (for example, when `Scan` returns an error and the function `return`s immediately). Under load the pool drains slowly because connections are never returned, and `db.Stats().WaitCount` climbs hour after hour while nobody notices the cause. A second team treats "no such row" (`sql.ErrNoRows`) as the same kind of error as a network failure of the database — the API returns `500 Internal Server Error` for a situation that should have been an ordinary `404 Not Found`. A third team swaps the argument order in `Scan` (the query returns `id, name, price`, but `Scan` receives `&p.Name, &p.ID, &p.Price`). The code compiles cleanly, because the types are compatible (string, string, int64), but the data is mapped incorrectly and nobody notices until a user reports that "the product name looks weird". A fourth team opens a new `Prepare` on every loop iteration instead of once before the loop, throwing away the point of a prepared statement, or the reverse — never closes an open `Stmt` that was supposed to live briefly. This lesson settles all four situations with clear rules around `Close`, `ErrNoRows`, the order of `Scan` arguments, and `Prepare` inside a transaction.

## Mental model

| Operation | API | Result |
|-----------|-----|--------|
| Read N rows (0, 1, or more) | `QueryContext` | `*sql.Rows` — iterate with `Next()`, close with `Close()` |
| Read exactly 0 or 1 row | `QueryRowContext` | Call `Scan` directly; `sql.ErrNoRows` when there is no row |
| Change data (write) | `ExecContext` | `sql.Result` — `RowsAffected()`, `LastInsertId()` (driver-dependent) |
| Run the same SQL many times | `PrepareContext` | `*sql.Stmt` bound to a `DB` or `Tx`, used with `ExecContext`/`QueryContext` |

`Scan` maps columns from the SQL result onto the addresses of Go variables **by order** — the order in which they appear in the `SELECT` list. The mapping follows neither the column name nor the field type in the struct. It follows only the positional order of the arguments passed to `Scan`.

## Mechanism

### Step 1 — What actually happens in `QueryContext`, row by row

```go
rows, err := db.QueryContext(ctx, `SELECT id, name FROM products WHERE active = $1`, true)
```

Concretely:

1. `database/sql` takes a connection from the pool (the same waiting mechanism as in 03.01 when the pool is full).
2. The driver sends the SQL text and the value `true` (for `$1`) to the database as two separate pieces of data.
3. The database starts executing the query and returns the **first** result rows — `QueryContext` does **not** return only after the entire result has been read. It returns as soon as the first packet of data has arrived. That means the connection stays **busy** (reserved for this `rows`) until the result is exhausted or `rows.Close()` is called.
4. `rows.Next()` moves the "cursor" to the next row, and returns `false` when there are no more rows (or when an error occurred — a distinction Step 3 explains).

**Predict:** If the query returns 10,000 rows, and the code calls `db.QueryContext` but then, instead of entering the `for rows.Next()` loop, does `return` without `rows.Close()` (say, a conditional branch that was forgotten) — what happens to the connection that `rows` was using?

**Answer:** The connection stays busy and is **not** returned to the pool. From the point of view of `database/sql`, that connection is "in use" because an open `*sql.Rows` exists and was never closed. If this repeats (the same bug on every call to that handler), the pool drains until `MaxOpenConns` is reached, and every later call to the database starts waiting or gets canceled through the context — a classic connection leak whose cause is a missing `Close`, not a network problem.

### Step 2 — `QueryRowContext` and `sql.ErrNoRows`: where the error actually appears

```go
var name string
err := db.QueryRowContext(ctx,
	`SELECT name FROM products WHERE id = $1`, id,
).Scan(&name)
```

This is one expression made of two calls. `QueryRowContext` **immediately** returns a value of type `*sql.Row` — even if `id` matches no row, `QueryRowContext` itself does not return an error (there is no `error` in its result type, only `*sql.Row`). The error materializes only on the `.Scan(&name)` call:

- If exactly one row is found, `Scan` writes the `name` column into the variable and returns `nil`.
- If **no** row matches `WHERE id = $1`, `Scan` returns `sql.ErrNoRows` — a special, predefined error from the `database/sql` package, compared with `errors.Is(err, sql.ErrNoRows)`.
- If a real problem occurred (the network dropped, the column does not exist, the type does not match), `Scan` returns **that** error — different from `sql.ErrNoRows`.

**Predict:** If `WHERE id = $1` matches **two** rows (for example, a schema mistake allows duplicates), what does `QueryRowContext(...).Scan(&name)` return?

**Answer:** `QueryRowContext` internally takes only the **first** row of the result (in the order the database returns, which is not guaranteed to be deterministic without `ORDER BY`) and immediately closes the remaining rows. `Scan` returns a `nil` error and the value from that first row, silently ignoring the second row. This is not a crash, but it is a common source of confusing bugs when the schema allows duplicates the application did not expect.

### Step 3 — `rows.Next()` returning `false`: end of data, or an error?

```go
for rows.Next() {
	var p Product
	if err := rows.Scan(&p.ID, &p.Name); err != nil {
		return nil, fmt.Errorf("scan: %w", err)
	}
	out = append(out, p)
}
if err := rows.Err(); err != nil {
	return nil, fmt.Errorf("rows: %w", err)
}
```

The important, often ignored distinction is this: `rows.Next()` returns a `bool`, **not** `(bool, error)`. When `Next()` returns `false`, that means one of two things:

1. The result was exhausted normally — every row was read, and there is no error.
2. An error occurred **during** iteration (for example, the network dropped on the third of ten rows). In that case `Next()` **also** returns `false` (because it cannot provide the next row), but the real cause is not visible on the `Next()` call itself.

That is why `rows.Err()` is called **after** the loop. It returns `nil` in case 1, and the concrete error in case 2. Code that ignores `rows.Err()` treats a truncated, incomplete iteration as identical to a successfully finished one — the function returns a partial `out` list as if it were complete, with no signal that something went wrong.

**Predict:** If the network breaks exactly on the fifth of ten rows during iteration, how many elements will `out` contain at the end of the loop, and what does `rows.Err()` return?

**Answer:** `out` will contain the first 4 successfully scanned rows (the fifth row, where the error occurred, is not appended if `Scan`/`Next` signals a problem on that attempt). `rows.Err()` returns the concrete network error the driver recorded. Without the `rows.Err()` check, the caller would receive an incomplete list of 4 elements and think the database has only 4 active products, instead of knowing that iteration was cut short by an error.

### Step 4 — `Exec` and `Result`: what `RowsAffected` actually counts

```go
res, err := db.ExecContext(ctx,
	`UPDATE products SET price_minor = $1 WHERE id = $2`, price, id,
)
n, err := res.RowsAffected()
```

`ExecContext` is used when we do not need to read rows back — only to execute a change. `res.RowsAffected()` returns the **number of rows the database actually changed** with that statement — not the number of rows that matched the `WHERE` condition before the change (those two numbers are the same only if every matched row actually changes a value). Concretely, if `WHERE id = $2` finds a row, but `price_minor` is already exactly equal to the `price` we are writing, some databases (depending on the engine and settings) report `RowsAffected() == 0` because "there was no real change", while others report `1` because the row was "matched" whether or not the value changed. This behavior is **database- and driver-dependent**, so `RowsAffected() == 0` should not automatically be read as "the row does not exist" without an extra check when that distinction matters to your logic.

`LastInsertId()` is similarly database-dependent. PostgreSQL generally does not support it (it returns an error if called), because PostgreSQL idiomatically uses `INSERT ... RETURNING id` and reads `id` through `QueryRowContext(...).Scan(&id)` instead of through `Result`. MySQL and SQLite support `LastInsertId()` naturally through `AUTO_INCREMENT`/`ROWID` mechanisms.

**Predict:** If we call `res.LastInsertId()` after an `INSERT` on a PostgreSQL database through the `pgx` driver, what happens?

**Answer:** It returns an error (typically something to the effect that the operation is not supported). PostgreSQL does not return a "last insert id" as part of the protocol the way other engines (MySQL, SQLite) do. The correct pattern for PostgreSQL is `INSERT INTO products (...) VALUES (...) RETURNING id`, read through `QueryRowContext(...).Scan(&id)`.

### Step 5 — Prepared statement: what is shared, and what is not

```go
stmt, err := tx.PrepareContext(ctx,
	`INSERT INTO products (id, name, price_minor) VALUES ($1, $2, $3)`,
)
defer stmt.Close()

for _, p := range items {
	if _, err := stmt.ExecContext(ctx, p.ID, p.Name, p.Price); err != nil {
		return fmt.Errorf("insert many %s: %w", p.ID, err)
	}
}
```

`PrepareContext` sends the SQL text to the database **once**. The database parses it and prepares an execution plan **once**, and returns a handle (`*sql.Stmt`) that Go keeps. Each later `stmt.ExecContext(ctx, p.ID, p.Name, p.Price)` sends **only** the argument values, skipping another parse of the same SQL text. For 1,000 inserts in a loop, that is 1,000 exchanges of values instead of 1,000 full parses of the same query. `stmt.Close()` in a `defer` releases that prepared plan on the database side when it is no longer needed. Leaving an open `Stmt` without `Close` (especially if new ones are constantly created in a loop without closing the old ones) accumulates resources on the database server that are never released until the connection ends.

**Predict:** What would change (in terms of the benefit of `Prepare`) if, instead of preparing once before the loop, we called `tx.PrepareContext` **again on every loop iteration**, then immediately `Exec`, then `Close`?

**Answer:** The purpose of `Prepare` (avoiding a repeated parse of the same SQL text) would be completely undone. The database would parse the same query again on every iteration, the same as calling an ordinary `tx.ExecContext` without a prior `Prepare`. The extra cost of creating and closing a `Stmt` handle on every iteration makes this pattern even slower than a plain `Exec` in a loop, not faster.

### Step 6 — Context canceled in the middle of row iteration

```go
ctx, cancel := context.WithTimeout(ctx, 500*time.Millisecond)
defer cancel()

rows, err := db.QueryContext(ctx, `SELECT id, name, price_minor FROM products`)
if err != nil {
	return nil, err
}
defer rows.Close()

for rows.Next() {
	// per-row work that takes unexpectedly long
}
```

If `ctx` expires **while** the `for rows.Next()` loop is running (for example, per-row work is slower than planned, and the total time exceeds 500ms), `rows.Next()` will at some point return `false` — not because the data is exhausted, but because the driver detected the canceled `context` and stopped pulling further rows from the database. This is **exactly** the situation Step 3 warns about: `rows.Next()` returning `false` says nothing about the cause. Only `rows.Err()` after the loop reveals that the cause is `context.DeadlineExceeded`, not a normal end of the result.

**Predict:** If we ignore `rows.Err()` in this scenario, how many rows will the function return to the caller, and does the caller have any signal that the result is incomplete?

**Answer:** The function returns only the rows that were successfully read and processed before the `context` expired — say 40 of 200 — and **without** the `rows.Err()` check, the caller receives those 40 as if they were the entire result, with no signal that something was interrupted. This is especially dangerous in aggregations (for example, "total number of active products") where an incomplete result looks completely legitimate, and is simply wrong.

### Step 7 — A variable number of arguments: an `IN` list without concatenating values

A common request is to fetch several rows by a list of IDs whose length is not known when the code is written (for example, IDs that arrived in an HTTP request body). The first instinct — to splice the IDs directly into the SQL text with `strings.Join` or `fmt.Sprintf` using the values themselves — is exactly the concatenation pattern this lesson forbids. The correct pattern builds the **count and positions** of the placeholders dynamically, from the length of the slice, while the **values** themselves still travel only through arguments:

```go
func GetByIDs(ctx context.Context, db *sql.DB, ids []string) ([]Product, error) {
	if len(ids) == 0 {
		return nil, nil
	}
	placeholders := make([]string, len(ids))
	args := make([]any, len(ids))
	for i, id := range ids {
		placeholders[i] = fmt.Sprintf("$%d", i+1)
		args[i] = id
	}
	query := fmt.Sprintf(
		`SELECT id, name, price_minor FROM products WHERE id IN (%s)`,
		strings.Join(placeholders, ", "),
	)
	rows, err := db.QueryContext(ctx, query, args...)
	if err != nil {
		return nil, fmt.Errorf("get by ids: %w", err)
	}
	defer rows.Close()

	var out []Product
	for rows.Next() {
		var p Product
		if err := rows.Scan(&p.ID, &p.Name, &p.Price); err != nil {
			return nil, fmt.Errorf("get by ids scan: %w", err)
		}
		out = append(out, p)
	}
	return out, rows.Err()
}
```

Here `fmt.Sprintf` is used to build **only** text of the form `$1, $2, $3` — a string that contains only position numbers, a function of the length of the `ids` slice (controlled by application code, not by user input). The value of each `ids[i]` **never** enters the `query` string. It goes only through `args[i]`, passed as an argument to `QueryContext` via `args...`. The database treats every element of `args` as literal data, regardless of its contents — quotes, spaces, even SQL keywords inside the string itself.

**Predict:** If `ids` contains a value that looks like a piece of SQL syntax (for example, a string that contains a quote or a space), does that affect the structure of the executed query?

**Answer:** No. That value travels through a placeholder as an ordinary parameter, completely separate from the SQL text that was already sent to the database before the arguments were considered. The database always compares the `id` column with the **exact contents** of that value as data. It never interprets the value as part of SQL syntax. That is the essential difference between this pattern (a dynamic number of placeholders, values kept static through arguments) and concatenating user input directly into the SQL text.

This pattern has a practical limit: databases have a maximum number of parameters per query (PostgreSQL allows up to 65535, but the execution plan for an `IN` with several thousand values becomes inefficient well before that limit). For truly large lists (tens of thousands of IDs), the idiomatic pattern is either to split into smaller batches, or (PostgreSQL specifically) to pass an array through `= ANY($1)` with the array as a single parameter (this requires driver support for array types, for example `pq.Array`/`pgtype.Array`), instead of hundreds of individual placeholders.

### Named parameters as an alternative to positional placeholders

`database/sql` also supports **named** parameters through `sql.Named`, as an alternative to positional placeholders (`$1`, `?`) when the SQL query is complex enough that counting positions becomes hard to follow:

```go
_, err := db.ExecContext(ctx,
	`UPDATE products SET name = :name, price_minor = :price WHERE id = :id`,
	sql.Named("name", p.Name),
	sql.Named("price", p.Price),
	sql.Named("id", p.ID),
)
```

Support for named parameters depends on the driver (PostgreSQL through `pgx` supports them; not every driver for every database implements them identically). The safety principle is the same as for positional placeholders: the value travels as an argument, never as text stamped into the SQL string. Use this selectively, when the number of parameters makes positional counting (`$1` ... `$12`) hard to read and maintain.

**Predict:** Does `sql.Named("id", p.ID)` in any way allow `p.ID` to affect the structure of the SQL text (for example, a column name or a table name)?

**Answer:** No. `sql.Named` still carries only the **value** of the argument, with a name that exists solely to bind it to the `:name` form of the placeholder in the SQL text. The column name (`price_minor`) and the table name (`products`) stay fixed literals in the SQL string, independent of any argument. Named parameters change only the **writing style** of the placeholders, not their safety guarantee.

## Rules and syntax

- Always `defer rows.Close()` immediately after checking the error from a successful `QueryContext` — before any other code.
- Always check `rows.Err()` **after** the `for rows.Next()` loop, not only the return value of `Scan` inside the loop.
- `QueryRow().Scan()` is one logical call — the error (including `sql.ErrNoRows`) comes exclusively from `Scan`, not from `QueryRow` itself.
- The number and order of arguments passed to `Scan` must **exactly** match the number and order of columns in the `SELECT` list — by position, not by name.
- For `NULL` columns use `sql.NullString`, `sql.NullInt64`, `sql.NullBool`, `sql.NullTime` (or pointers, for example `*string`) — never a plain `string`/`int64` directly on a column that allows `NULL`.
- Placeholders always — never put user input directly into SQL text, neither in CRUD operations nor anywhere else.
- `Prepare` makes sense when the same SQL runs more than once in the same logical flow (a loop, a batch). For a one-shot query it is usually unnecessary — the driver and the database can cache the plan internally without an explicit `Prepare`.

## Examples

### Example 1 — Create and read one row

```go
package products

import (
	"context"
	"database/sql"
	"errors"
	"fmt"
)

type Product struct {
	ID    string
	Name  string
	Price int64
}

func Insert(ctx context.Context, db *sql.DB, p Product) error {
	_, err := db.ExecContext(ctx,
		`INSERT INTO products (id, name, price_minor) VALUES ($1, $2, $3)`,
		p.ID, p.Name, p.Price,
	)
	if err != nil {
		return fmt.Errorf("products insert: %w", err)
	}
	return nil
}

func Get(ctx context.Context, db *sql.DB, id string) (Product, error) {
	var p Product
	err := db.QueryRowContext(ctx,
		`SELECT id, name, price_minor FROM products WHERE id = $1`, id,
	).Scan(&p.ID, &p.Name, &p.Price)
	if errors.Is(err, sql.ErrNoRows) {
		return Product{}, fmt.Errorf("products get %s: %w", id, err)
	}
	if err != nil {
		return Product{}, fmt.Errorf("products get: %w", err)
	}
	return p, nil
}
```

#### What happens here

`Insert` uses `ExecContext` because we do not need rows back. `Get` uses `QueryRowContext` + `Scan`, with argument order (`&p.ID, &p.Name, &p.Price`) that exactly matches the column order in `SELECT id, name, price_minor`. `errors.Is(err, sql.ErrNoRows)` separates "there is no such product" (a caller in the layer above can map that to `404`) from every other error (which would be mapped to `500`).

**Predict:** What would `Scan` return (with no compile error) if we swapped the order to `.Scan(&p.Name, &p.ID, &p.Price)` while the `SELECT` list stays `id, name, price_minor`?

**Answer:** It compiles without a problem because `p.Name` and `p.ID` are both `string` — they are compatible from the type system's point of view. But `p.Name` would receive the value of the `id` column, and `p.ID` the value of the `name` column. The data would be silently swapped, with no error during the program, until someone notices that the "product names" are actually IDs.

### Example 2 — A list with Query and a mandatory Close

```go
package products

import (
	"context"
	"database/sql"
	"fmt"
)

func ListActive(ctx context.Context, db *sql.DB) ([]Product, error) {
	rows, err := db.QueryContext(ctx,
		`SELECT id, name, price_minor FROM products WHERE active = $1 ORDER BY name`,
		true,
	)
	if err != nil {
		return nil, fmt.Errorf("products list: %w", err)
	}
	defer rows.Close()

	var out []Product
	for rows.Next() {
		var p Product
		if err := rows.Scan(&p.ID, &p.Name, &p.Price); err != nil {
			return nil, fmt.Errorf("products list scan: %w", err)
		}
		out = append(out, p)
	}
	if err := rows.Err(); err != nil {
		return nil, fmt.Errorf("rows: %w", err)
	}
	return out, nil
}
```

#### What happens here

`defer rows.Close()` is registered **immediately** after a successful `QueryContext`, before the loop. The connection therefore returns to the pool whether the loop finishes normally or the function `return`s early because of an error in `Scan`. `rows.Err()` after the loop catches errors that occurred during the iteration itself (Step 3 of Mechanism), not only errors from starting the query.

### Example 3 — Update and Delete, reading RowsAffected

```go
package products

import (
	"context"
	"database/sql"
	"fmt"
)

func UpdatePrice(ctx context.Context, db *sql.DB, id string, price int64) error {
	res, err := db.ExecContext(ctx,
		`UPDATE products SET price_minor = $1 WHERE id = $2`, price, id,
	)
	if err != nil {
		return fmt.Errorf("update: %w", err)
	}
	n, err := res.RowsAffected()
	if err != nil {
		return err
	}
	if n == 0 {
		return fmt.Errorf("update: no row %s: %w", id, sql.ErrNoRows)
	}
	return nil
}

func Delete(ctx context.Context, db *sql.DB, id string) error {
	_, err := db.ExecContext(ctx, `DELETE FROM products WHERE id = $1`, id)
	if err != nil {
		return fmt.Errorf("delete: %w", err)
	}
	return nil
}
```

#### What happens here

`RowsAffected() == 0` after `UPDATE` means `WHERE id = $2` did not find a row. We map that to `sql.ErrNoRows` so a caller higher in the stack (for example an HTTP handler) can use the same `errors.Is` pattern as for `QueryRowContext`. `Delete` in this example **ignores** the number of affected rows — deleting an `id` that does not exist is treated as success (an idempotent operation). This is a conscious decision, not an omission, and it is worth documenting in a comment at the call site.

### Example 4 — A prepared statement in a batch-insert loop, inside a transaction

```go
package products

import (
	"context"
	"database/sql"
	"fmt"
)

func InsertMany(ctx context.Context, db *sql.DB, items []Product) error {
	tx, err := db.BeginTx(ctx, nil)
	if err != nil {
		return err
	}
	defer tx.Rollback()

	stmt, err := tx.PrepareContext(ctx,
		`INSERT INTO products (id, name, price_minor) VALUES ($1, $2, $3)`,
	)
	if err != nil {
		return err
	}
	defer stmt.Close()

	for _, p := range items {
		if _, err := stmt.ExecContext(ctx, p.ID, p.Name, p.Price); err != nil {
			return fmt.Errorf("insert many %s: %w", p.ID, err)
		}
	}
	return tx.Commit()
}
```

#### What happens here

`PrepareContext` is called on `tx` (not on `db`), so the prepared statement is bound to the same connection as the transaction. Every `stmt.ExecContext` call in the loop is part of the same single atomic transaction. If inserting any element of `items` fails (for example, a duplicate key on the third of twenty elements), the function `return`s with an error, and `defer tx.Rollback()` undoes **all** rows previously inserted by this loop. The batch is all-or-nothing, not partially inserted.

**Predict:** If `items` contains 20 elements and the third element violates a `UNIQUE` constraint on the `id` column, how many rows will remain permanently written in the `products` table after this function?

**Answer:** Zero. `defer tx.Rollback()` undoes the first two successfully inserted rows as well, because `tx.Commit()` was never called. The whole operation is atomic: either all 20 succeed and stay written, or none of them do.

### Example 5 — NULL columns through sql.NullString

```go
package products

import (
	"context"
	"database/sql"
)

type ProductNull struct {
	ID          string
	Name        string
	Description sql.NullString
}

func GetDesc(ctx context.Context, db *sql.DB, id string) (string, error) {
	var d sql.NullString
	err := db.QueryRowContext(ctx,
		`SELECT description FROM products WHERE id = $1`, id,
	).Scan(&d)
	if err != nil {
		return "", err
	}
	if !d.Valid {
		return "", nil
	}
	return d.String, nil
}
```

#### What happens here

The `description` column allows `NULL`. `Scan` into a plain `string` would return an error (`converting NULL to string is unsupported`) as soon as it hits a `NULL` value. `sql.NullString` exists exactly for this case: `Scan` writes both the value (`d.String`) and the information about whether that value exists (`d.Valid`). `!d.Valid` means the column was `NULL`. This function consciously turns that into an empty string for the caller, but it could equally return a different signal (for example a `*string` that is `nil`) depending on what the API needs.

**Predict:** What would happen if we tried `Scan(&p.Description)` where `p.Description` has type `string` (not `sql.NullString`), and the actual value in the database is `NULL`?

**Answer:** `Scan` returns an error at execution time (runtime), typically something like "unsupported Scan, storing driver.Value type <nil> into type *string". The program does not crash (there is no panic), but the function that calls `Scan` must handle that error like any other, and the data is not written into `p.Description`.

### Example 6 — The same code, a different placeholder dialect

```go
// The same Go code works identically with a SQLite/MySQL driver, with a placeholder change:
// `SELECT id, name FROM products WHERE id = ?`
// Scan calls stay identical — the difference is only in the SQL string literal.
```

#### What happens here

The `database/sql` API (`QueryContext`, `Scan`, `Rows`, `Result`) is identical regardless of the database. The only change is the placeholder style in the SQL text (`$1` for PostgreSQL, `?` for SQLite/MySQL). Do not mix both styles in the same SQL string — that is a syntax error the database rejects, not something `database/sql` translates automatically.

### Example 7 — A Repository type that groups CRUD methods

```go
package products

import (
	"context"
	"database/sql"
	"errors"
	"fmt"
)

type Repository struct {
	db *sql.DB
}

func NewRepository(db *sql.DB) *Repository {
	return &Repository{db: db}
}

func (r *Repository) Get(ctx context.Context, id string) (Product, error) {
	var p Product
	err := r.db.QueryRowContext(ctx,
		`SELECT id, name, price_minor FROM products WHERE id = $1`, id,
	).Scan(&p.ID, &p.Name, &p.Price)
	if errors.Is(err, sql.ErrNoRows) {
		return Product{}, fmt.Errorf("products get %s: %w", id, err)
	}
	if err != nil {
		return Product{}, fmt.Errorf("products get: %w", err)
	}
	return p, nil
}

func (r *Repository) Create(ctx context.Context, p Product) error {
	_, err := r.db.ExecContext(ctx,
		`INSERT INTO products (id, name, price_minor) VALUES ($1, $2, $3)`,
		p.ID, p.Name, p.Price,
	)
	if err != nil {
		return fmt.Errorf("products create: %w", err)
	}
	return nil
}
```

#### What happens here

`Repository` stores `*sql.DB` (the pool from 03.01) as a field, and every method uses that already existing pool. It does not open its own connection, and it does not call `sql.Open`. This shape groups all CRUD functions for one entity (`products`) under one type, instead of each function floating free in the package. It makes the API cleaner for the caller (`repo.Get(ctx, id)` instead of `products.Get(ctx, db, id)`), and easier to test through an interface in tests where `*sql.DB` is replaced by a test double.

**Predict:** If `Repository.Get` and `Repository.Create` need to take part in the same transaction in some business operation (for example, "create a product and immediately write an audit log in the same TX"), does the current shape of `Repository` (with a field `db *sql.DB`) support that directly?

**Answer:** Not directly. Because the methods use `r.db` fixedly, they have no way to receive a `*sql.Tx` from outside. The solution (building on the `dbtx` pattern from lesson 03.02) is for the methods to take an extra parameter of a small interface type (`ExecContext`/`QueryRowContext`), or for `Repository` to have a constructor variant that takes `*sql.Tx` instead of `*sql.DB`, so the same code works both inside and outside a transaction.

### Example 8 — A safe `IN` list with a variable number of arguments

```go
package products

import (
	"context"
	"database/sql"
	"fmt"
	"strings"
)

func GetByIDs(ctx context.Context, db *sql.DB, ids []string) ([]Product, error) {
	if len(ids) == 0 {
		return nil, nil
	}
	placeholders := make([]string, len(ids))
	args := make([]any, len(ids))
	for i, id := range ids {
		placeholders[i] = fmt.Sprintf("$%d", i+1)
		args[i] = id
	}
	query := fmt.Sprintf(
		`SELECT id, name, price_minor FROM products WHERE id IN (%s)`,
		strings.Join(placeholders, ", "),
	)

	rows, err := db.QueryContext(ctx, query, args...)
	if err != nil {
		return nil, fmt.Errorf("get by ids: %w", err)
	}
	defer rows.Close()

	var out []Product
	for rows.Next() {
		var p Product
		if err := rows.Scan(&p.ID, &p.Name, &p.Price); err != nil {
			return nil, fmt.Errorf("get by ids scan: %w", err)
		}
		out = append(out, p)
	}
	return out, rows.Err()
}
```

#### What happens here

The early `if len(ids) == 0 { return nil, nil }` prevents building invalid SQL of the form `WHERE id IN ()` (an empty list in parentheses is a syntax error in most dialects). For a non-empty `ids`, `placeholders` and `args` grow **together**, position by position — `placeholders[i]` is always `$` plus the position that corresponds to `args[i]`, guaranteed by the same index `i` in the same loop. The resulting `query` string contains only numbers (`$1, $2, $3`), never the actual ID values. Those values reach the database exclusively through `args...`.

**Predict:** If `GetByIDs` is called with a list of 3 IDs, but one of them is duplicated (for example, `["a", "b", "a"]`), how many rows will the function return?

**Answer:** At most 2 (for `"a"` and `"b"`, assuming both exist in the table). An `IN` list with a duplicate does not affect the number of rows the database returns, because `WHERE id IN ($1, $2, $3)` with `$1` and `$3` holding the same value simply checks the same condition twice for the same row. The database returns each row at most once anyway, by the basic definition of `SELECT` without a `JOIN` that would multiply it.

## Decision analysis

| Decision | Reason |
|----------|--------|
| `QueryRow` for exactly one row | Less ceremony (no loop, no `Close`) than `Query` |
| `errors.Is(err, sql.ErrNoRows)` | Clearly separates "no row" (404) from real errors (500) |
| `Prepare` inside `tx` for a batch | One parse of the SQL instead of one per iteration, atomic with the rest of the operation |
| `sql.Null*` types | Correctly models columns that allow `NULL`, without a runtime error on `Scan` |
| `RowsAffected() == 0` → `ErrNoRows` | A consistent error pattern for "no such row" on `UPDATE` as well, not only on `SELECT` |
| A dynamic number of placeholders (not values) for an `IN` list | Supports a variable-length input without concatenating values into the SQL text |

## Trade-offs

- An ORM versus direct `database/sql`: an ORM speeds up writing simple CRUD code, but it hides exactly the details (the order of `Scan`, `Close`, `ErrNoRows`) that this lesson teaches must be understood. `database/sql` gives full control with more ceremony per query.
- `LastInsertId()` is not universally supported (PostgreSQL does not support it). Portable code between databases must plan for `RETURNING id` as the alternative, which means "the same" CRUD code is not always literally identical between engines.
- A large query result (for example, a million rows) is better read in pages (pagination through `LIMIT`/`OFFSET` or keyset pagination) than loaded entirely into one `[]Product` in memory. The `Query`/`Scan` pattern from this lesson works well up to a reasonable result size. It is not a universal solution for every data size.
- Manual mapping (`Scan(&p.ID, &p.Name, &p.Price)`) versus generated code (tools such as `sqlc`): generated code removes the risk of a wrong argument order, but it adds a build-pipeline step. The mental model (Query/QueryRow/Exec/Scan) stays the same in both cases.
- A dynamic `IN` list is simple to write and read up to a few hundred values. For tens of thousands, `= ANY($1)` with an array as a single parameter (or splitting into batches) avoids both the parameter-count limit and the degradation of the execution plan.

## Common mistakes

### Rows never closed

**Wrong:** `db.QueryContext` is called, but `rows.Close()` is not registered with `defer` immediately, or some branch of the code (an early `return` on an error from `Scan`) skips `Close`.
**Effect:** The connection stays busy and is not returned to the pool. Under repeated calls, the pool drains and `WaitCount` from `db.Stats()` grows until every call to the database starts waiting or gets canceled.
**Fix:** Put `defer rows.Close()` on the line immediately after checking the error from `QueryContext`, before any other code, so it runs on every exit path of the function.

### Ignored rows.Err() after the loop

**Wrong:** The code checks the error from `Scan` inside the loop, but never calls `rows.Err()` after `for rows.Next()`.
**Effect:** If iteration is cut short by an error (for example, a network problem on the fifth of ten rows), `Next()` simply returns `false` just as it does at a normal end, and the function silently returns an incomplete list as if it were complete.
**Fix:** Call `rows.Err()` immediately after the loop and return that error if it is not `nil`, before you return the collected list to the caller.

### Treating ErrNoRows as a server error

**Wrong:** The handler or repository function does not distinguish `sql.ErrNoRows` from other errors — every error from `Scan` is mapped to `500`.
**Effect:** A user who asks for a resource that does not exist gets `500 Internal Server Error` instead of the expected `404 Not Found`, and the on-call engineer investigates a "server error" that is actually a normal, expected case.
**Fix:** Check `errors.Is(err, sql.ErrNoRows)` before generic error handling, and map that specific case to `404` (or the matching domain signal) in the layer that knows about HTTP.

### Wrong argument order in Scan

**Wrong:** The order of arguments passed to `Scan` does not match the order of columns in the `SELECT` list, but the types are similar enough (for example, two `string` fields) that the compiler does not report a problem.
**Effect:** Data is silently mapped onto the wrong fields. The program runs without errors and without a panic, but the contents are wrong, and the problem is often discovered only through a user report.
**Fix:** When you write or change a `SELECT` list, immediately check and align the argument order in the matching `Scan` call. Where possible, a comment above the `Scan` line that states the column order helps future edits.

### SQL concatenation in CRUD operations

**Wrong:** Part of a `WHERE` clause, or a value for `INSERT`/`UPDATE`, is assembled with `fmt.Sprintf` or `+` directly into the SQL text, instead of through a placeholder.
**Effect:** Query behavior depends on the contents of the input in a way that was not explicitly planned and checked — the same class of problem described in 03.01, applied here to every CRUD operation, not only to `SELECT`.
**Fix:** Every value that comes from an external source (an HTTP parameter, user input, configuration) goes exclusively through a placeholder as an argument to `Query`/`Exec`/`QueryRow`, never directly into the SQL string.

### Stmt opened in a loop without Close discipline

**Wrong:** `PrepareContext` is called again on every loop iteration instead of once before the loop, or the `Stmt` is never closed with `Close`.
**Effect:** The purpose of `Prepare` (one parse of the SQL, many executions) is undone if it is called per iteration. If the `Stmt` is never closed, resources tied to the prepared plan on the database side accumulate without being released.
**Fix:** Call `PrepareContext` once, before the loop, with `defer stmt.Close()` immediately after checking the error. Use the same `stmt` for every iteration through `stmt.ExecContext`/`stmt.QueryContext`.

### Ignored context during a long row iteration

**Wrong:** The `for rows.Next()` loop does slow per-row work (an external call, a heavy transformation) with no check of `rows.Err()` after the loop, alongside a `context` that has a short timeout.
**Effect:** If the `context` expires in the middle of iteration, `rows.Next()` returns `false` just as it does at a normal end. The function returns an incomplete result that looks complete, exactly as in Step 6 of Mechanism.
**Fix:** Always check `rows.Err()` after the loop, and if the per-row operation is slow, consider whether it needs its own, larger timeout than the query that fetched the rows.

### IN list built by concatenating values instead of placeholders

**Wrong:** The `IN` clause is built with `strings.Join(ids, "','")` or a similar join of the **values themselves** directly into the SQL text, instead of through the dynamic placeholders described in Step 7 of Mechanism.
**Effect:** Query behavior depends on the contents of each list element in a way that was not explicitly planned and checked — the same class of problem as ordinary concatenation in a `WHERE` condition, applied here to a list of values instead of to one value.
**Fix:** Build only the **count and positions** of the placeholders dynamically (`$1, $2, ...`), from the length of the slice. Pass every value exclusively through the `args` slice, never stamped into the SQL text itself.

## Idiomatic Go

- Wrap errors with context: `fmt.Errorf("products get: %w", err)`, so that `errors.Is`/`errors.As` further up the stack still work.
- On a PostgreSQL database use `INSERT ... RETURNING id` and read it through `QueryRowContext(...).Scan(&id)` instead of relying on `LastInsertId()`.
- Group CRUD functions for one entity (for example, a `products` package with `Insert`, `Get`, `ListActive`, `UpdatePrice`, `Delete`) into a shape called a repository. A deeper treatment of this pattern comes in lesson 05.03.
- Write tests against a real (or in-memory) database — testcontainers for PostgreSQL, or SQLite in-memory (`file::memory:?cache=shared`) for fast, isolated tests of CRUD logic.
- For an `IN` list whose element count depends on user input, build the placeholders in code (Step 7) — never with a hand-written `strings.Repeat("?,", n)` that lacks a matching `args` slice of the same length.
- When an SQL query has more than five or six parameters, consider `sql.Named` (named parameters) for readability. The cost is a dependency on driver support for that form.

## Paginating large results: LIMIT/OFFSET versus keyset

The `Query`/`Scan` pattern from this lesson works reliably while the whole result is held in memory as `[]Product`. For results that exceed a few thousand rows, loading everything at once wastes memory and lengthens the time until the first returned row. Two common pagination patterns:

```go
// LIMIT/OFFSET — simple, but OFFSET gets slower with every following page
func ListPageOffset(ctx context.Context, db *sql.DB, page, pageSize int) ([]Product, error) {
	rows, err := db.QueryContext(ctx,
		`SELECT id, name, price_minor FROM products ORDER BY id LIMIT $1 OFFSET $2`,
		pageSize, page*pageSize,
	)
	if err != nil {
		return nil, err
	}
	defer rows.Close()
	// ... the same Scan/Next pattern as in Example 2 ...
	return nil, rows.Err()
}

// Keyset (cursor) pagination — a constant cost per page, regardless of depth
func ListPageKeyset(ctx context.Context, db *sql.DB, lastID string, pageSize int) ([]Product, error) {
	rows, err := db.QueryContext(ctx,
		`SELECT id, name, price_minor FROM products WHERE id > $1 ORDER BY id LIMIT $2`,
		lastID, pageSize,
	)
	if err != nil {
		return nil, err
	}
	defer rows.Close()
	// ... the same Scan/Next pattern as in Example 2 ...
	return nil, rows.Err()
}
```

`ListPageOffset` is simpler to write and simpler for URL parameters (`?page=5`), but `OFFSET 50000` still requires the database to **count and skip** the first 50,000 rows before it returns the next page. The cost grows linearly with page depth. `ListPageKeyset` remembers the last seen `id` (the cursor) and asks only for rows **after** it. The cost per page stays approximately constant no matter how deep the page is, at the cost that the client cannot directly "jump" to an arbitrary page number — only forward through the last cursor.

**Predict:** If, between two calls to `ListPageOffset` (page 1, then page 2), some row is deleted from the first page, does the client risk skipping a row it never saw?

**Answer:** Yes. `OFFSET` counts positions in the current, changing result. If a row disappears before the second page is fetched, every row behind it shifts forward by one place, and the `OFFSET` for the second page now skips a row the client never saw. Keyset pagination (`WHERE id > lastID`) does not have this problem, because the position is determined by the **value** of the last seen row, not by a numeric position in the result.

## Practical scenario

The product-listing handler runs `Query`, iterates the result, and under normal load everything works. A few weeks later, operations reports that the API occasionally starts to "get lost" under load — requests start waiting longer and longer. Diagnostics through `db.Stats()` show that `WaitCount` keeps growing, and that `InUse` connections rarely fall to zero even in quiet periods. A code review finds a branch in the handler that, when `Scan` returns an error on some unusual row (badly written data from an earlier migration), does `return` **before** the line with `rows.Close()` — because `defer` was never set, `Close()` was called only on the happy path at the end of the function. The fix is moving `defer rows.Close()` to immediately after `QueryContext`, instead of calling `Close()` explicitly at the end of the function. A second, independent bug is found in the same review: the endpoint that fetches a single product returns `500` when the product does not exist, because nobody checked `errors.Is(err, sql.ErrNoRows)`. Mapping that to `404` closes that ticket the same day.

A week later, the same team gets a ticket that the "export selected products" endpoint occasionally returns `500` when a user in the UI selects a large number of items at once. The cause is a function similar to `GetByIDs`, but written before this lesson — it built the `IN` list with `strings.Join(ids, ",")` and the IDs directly in the SQL text, without a single placeholder. When a user selects an ID that contains a character the SQL parser does not expect in that position, the query fails with a syntax error instead of returning a result. Replacing it with the pattern from Example 8 (a dynamic number of placeholders, values exclusively through `args`) fixes the syntax error and, along the way, removes a class of risk the old code carried without anyone intending it.

## Check questions

1. **When do you use `QueryRow` instead of `Query`?**
   When the query by definition returns at most one row — the error (including `sql.ErrNoRows`) comes from the `Scan` call, not from `QueryRow` itself.

2. **Why does it matter to call `rows.Err()` after the loop, and not only check the error from `Scan` inside the loop?**
   `rows.Next()` returns `false` both when the result is exhausted normally and when iteration was cut short by an error. `rows.Err()` after the loop is the only way to separate those two cases.

3. **What does `sql.ErrNoRows` specifically represent?**
   A signal that `QueryRow`/`Scan` did not find a matching row in the database — a logically normal, predictable outcome, not a network or system error.

4. **Why use `Prepare` for a batch insert inside a transaction, instead of only `Exec` in a loop?**
   `Prepare` sends the SQL text to the database once and prepares the execution plan once. Each later `ExecContext` on that `Stmt` transmits only the argument values, avoiding another parse of the same query on every iteration.

5. **How is user input (for example, an ID from a URL path) placed into an SQL query in a CRUD operation?**
   Exclusively as a placeholder argument (`$1`, `?`) passed to `Query`/`Exec`/`QueryRow`, never directly into the SQL text through concatenation or `fmt.Sprintf`.

6. **Why does `Scan` into a plain `string` fail (return an error) on a `NULL` column, and what is the correct solution?**
   `NULL` has no direct equivalent in a value of type `string`. `sql.NullString` (or a pointer) carries both the value and the information about whether that value exists (`Valid`), so `Scan` has a place to put both cases.

7. **What happens to `rows.Next()` if the `context` expires in the middle of iterating a large result?**
   `rows.Next()` returns `false`, identically to a normal end of the result. Only `rows.Err()` after the loop reveals that the real cause is the expired `context`, not exhausted data.

8. **Why group CRUD functions in a `Repository` type with `*sql.DB` as a field, instead of free functions that take `db` as a parameter?**
   A cleaner API for the caller (`repo.Get(ctx, id)`) and easier testing and substitution of the dependency, with the same basic `Query`/`QueryRow`/`Exec` mechanics underneath.

9. **Why is the number of placeholders for an `IN` list built dynamically with `fmt.Sprintf("$%d", i+1)`, instead of joining the list of values itself into a string?**
   So that every value still travels through `args` as a parameter, not as text stamped into the SQL. Only the **count and positions** of the placeholders are built dynamically (a function of the slice length), never the contents of the values.

10. **Why does keyset pagination have a constant cost per page, while `OFFSET` gets slower the deeper the page is?**
    `OFFSET` asks the database to count and skip every previous row before the current page. Keyset pagination filters directly with `WHERE id > lastID`, using an index to find the starting point immediately without counting the previous rows.

## Mapping database errors to HTTP responses (preview of lesson 05.x)

| Situation in the database | Typical HTTP response |
|---------------------------|-----------------------|
| `sql.ErrNoRows` | `404 Not Found` |
| Violation of a `UNIQUE` constraint | `409 Conflict` |
| Expired `context` (timeout) | `503`/`504` |
| Everything else, unexpected | `500 Internal Server Error` |

The repository layer (the CRUD functions from this lesson) returns errors in a form that carries enough information (`errors.Is`/`errors.As` friendly) for the handler layer higher in the stack to decide which HTTP status is appropriate. The mapping goes in that direction, from the database toward HTTP, never the other way around.

## Summary

CRUD through `database/sql` rests on four calls: `Query`/`QueryContext` for multiple rows (with a mandatory `defer rows.Close()` and a check of `rows.Err()`), `QueryRow`/`QueryRowContext` for exactly one row (with `errors.Is(err, sql.ErrNoRows)`), and `Exec`/`ExecContext` for writes (with `RowsAffected()`/`RETURNING` as needed). `Scan` maps columns onto Go variables strictly by positional order. `Prepare` inside a transaction speeds up repeated execution of the same query. `sql.Null*` types correctly model `NULL` columns. A variable number of arguments (an `IN` list) is solved with a dynamic number of placeholders, never by concatenating values. Large results are read in pages through `LIMIT`/`OFFSET` or, for deeper pages, through keyset pagination. With this set (03.01 pool and context, 03.02 transactions, 03.03 CRUD), Go code for relational databases is ready for the web layer that comes in the following lessons.
