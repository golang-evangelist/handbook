# 07.04 Working with requests in Gin: binding JSON, query, form, uri

> **Go Path - Zero to Gopher** / **02 Intermediate → Gin: A Web Application Framework for Go** / Lesson 07.04

## Lesson goals

After this lesson you should be able to:

- choose `ShouldBindJSON` (control) over `BindJSON` (less control)
- write input DTO `struct`s with `json`, `form`, `uri`, and `binding` tags
- use `ShouldBindQuery`, `ShouldBindUri`, and `ShouldBind` by source
- separate URI and body structs; separate binding from business rules
- limit body size before bind (`MaxBytesReader` / server limits)
- know the traps: consumed body, `*bool` for query, why not to trust `default=` in a form tag

## Prerequisite

- 07.01–07.03: Engine, Param, groups, Abort
- `encoding/json` basics; `struct` tags
- the notion of **zero value** (type’s zero value — gloss once): e.g. `""`, `0`, `false`, `nil`

## Problem this lesson solves

Manual Decode + manual validation in every handler leads to:

- inconsistent 400 messages
- missed required fields
- mixing “bad JSON” and “email already exists”
- reading an unbounded body (DoS)

Gin binding shortens shape + simple rules (`required`, `gte`). Business rules stay in the service.

## Mental model

```text
HTTP input
  ├─ path/uri  → ShouldBindUri   → struct + uri tag
  ├─ query     → ShouldBindQuery → struct + form tag
  ├─ JSON body → ShouldBindJSON  → struct + json + binding
  └─ form      → ShouldBind      → Content-Type picks strategy

ShouldBind* → error?
  yes → 400 (generic to client; detail in log)
  no  → service (business rules, DB, context.Context)
```

**Binding** (first gloss): connecting input to struct fields + declarative shape checks. Not a substitute for authorization or for a unique email in the DB.

## Mechanism

### ShouldBind vs Bind

| API | On error | Response control |
|-----|----------|------------------|
| `ShouldBindJSON` | returns `error` | you write status/body |
| `BindJSON` | typically 400 + Abort | less control |

Idiom: **always `ShouldBind*`** in new code.

```go
var in CreateItem
if err := c.ShouldBindJSON(&in); err != nil {
	c.AbortWithStatusJSON(http.StatusBadRequest, gin.H{"error": "invalid input"})
	return
}
```

**Predict the result:** after a `BindJSON` error, may you still call `c.JSON(200, …)` once more in the same handler?

**Answer:** not reliably — Abort is already marked / the response may have started. That is why ShouldBind + one explicit error response + return.

### Tags

```go
type CreateUser struct {
	Email string `json:"email" binding:"required,email"`
	Age   int    `json:"age" binding:"required,gte=18,lte=120"`
	Role  string `json:"role" binding:"required,oneof=user admin"`
}
```

Common `binding` operators:

| Operator | Meaning |
|----------|---------|
| `required` | field must be present / non-zero by validator rules |
| `min` / `max` / `len` | string/slice length |
| `gte` / `lte` / `gt` / `lt` | numeric range |
| `email` / `url` | format |
| `oneof=a b` | allowed values |
| `dive` | validate **slice** elements |

`json:"name"` without `binding` — an empty string can pass. `omitempty` in the `json` tag affects **output** serialization more than input binding — do not mix the semantics.

### Query and form tag

For query Gin uses the `form` tag (historically the same binder):

```go
type ListQuery struct {
	Q    string `form:"q"`
	Page int    `form:"page" binding:"omitempty,gte=1"`
}

if err := c.ShouldBindQuery(&q); err != nil { /* 400 */ }
```

**Do not rely** on `form:"page,default=1"` as a documented, portable Gin feature — it is often confusing or does not work as you expect. Idiom:

```go
if q.Page == 0 {
	q.Page = 1
}
```

That is explicit and testable.

### URI bind

```go
type ItemURI struct {
	ID string `uri:"id" binding:"required"`
}

r.GET("/items/:id", func(c *gin.Context) {
	var uri ItemURI
	if err := c.ShouldBindUri(&uri); err != nil {
		c.AbortWithStatusJSON(http.StatusBadRequest, gin.H{"error": "invalid input"})
		return
	}
	_ = uri.ID
})
```

The `uri` tag name must match the Param name (`:id`). Bind uri without `:id` in the route → error.

Alternative for one string: `c.Param("id")` — BindUri shines when there are more fields / shared validation.

### URI + JSON body separately

```go
type UpdateURI struct {
	ID string `uri:"id" binding:"required"`
}
type UpdateBody struct {
	Name string `json:"name" binding:"required,min=1"`
}

func update(c *gin.Context) {
	var uri UpdateURI
	if err := c.ShouldBindUri(&uri); err != nil {
		c.AbortWithStatusJSON(http.StatusBadRequest, gin.H{"error": "invalid uri"})
		return
	}
	var body UpdateBody
	if err := c.ShouldBindJSON(&body); err != nil {
		c.AbortWithStatusJSON(http.StatusBadRequest, gin.H{"error": "invalid body"})
		return
	}
	// service: Update(c.Request.Context(), uri.ID, body)
}
```

Two messages — easier debug. One huge struct with mixed tags confuses.

### ShouldBind and Content-Type

`c.ShouldBind(&v)` picks the binder by Content-Type (JSON, XML, form…). For an API that is always JSON, `ShouldBindJSON` is a clearer contract.

### The body is consumed

`ShouldBindJSON` reads `Request.Body`. A second read sees EOF. If you really need multiple strategies, `ShouldBindBodyWith` / load into a buffer — rare. 99% of handlers: **one** bind at the start.

### Body limit

Binding is not DoS protection:

```go
c.Request.Body = http.MaxBytesReader(c.Writer, c.Request.Body, 1<<20) // 1 MiB
if err := c.ShouldBindJSON(&in); err != nil {
	// may be body too large or bad JSON — map deliberately
}
```

Also set `http.Server` limits where it makes sense. Body too large → 413 or 400 depending on the layer; document it.

### *bool for query three-state

```go
type Filter struct {
	Active *bool `form:"active"`
}
```

| Query | Meaning |
|-------|---------|
| (no `active`) | `nil` — do not filter |
| `active=true` | pointer to true |
| `active=false` | pointer to false |

A plain `bool` cannot distinguish “absent” from **zero value** `false`.

### Binding vs business rule

| Layer | Example |
|-------|---------|
| Binding | email format, age ≥ 18, page ≥ 1 |
| Service | email already exists, no permission, machine state |

Unique email → DB + `error` → 409, not a `binding` tag.

### Response to the client

In production often generic `{"error":"invalid input"}`; validator detail in the debug log. Do not return a raw stack of tags if the contract does not require it. Do not log passwords from a form login.

### dive on a slice

```go
type CreateOrder struct {
	Lines []OrderLine `json:"lines" binding:"required,min=1,dive"`
}
type OrderLine struct {
	SKU string `json:"sku" binding:"required"`
	Qty int    `json:"qty" binding:"required,gte=1"`
}
```

`dive` validates each element. Keep DTOs shallow — deep graphs become unreadable.

### Trace: ShouldBindJSON from entry to service

```text
POST /users  Content-Type: application/json
Body: {"email":"a@b.com","age":20}

1. MaxBytesReader wraps Body (limit)
2. ShouldBindJSON(&in)
     - reads and consumes Body
     - fills CreateUser
     - runs binding tags
3. err == nil
4. svc.Create(c.Request.Context(), in.Email, in.Age)
5. 201 JSON
```

```text
Body: {"email":"not-an-email","age":10}

1. MaxBytesReader
2. ShouldBindJSON → err != nil (email / gte)
3. AbortWithStatusJSON(400, generic)
4. return — service IS NOT CALLED
```

**Predict the result:** after a successful `ShouldBindJSON`, you call `ShouldBindJSON` again in the same handler. What happens?

**Answer:** the second read sees EOF / empty body — bind error. One bind per body (or `ShouldBindBodyWith` / buffer — rare).

### Table: bind error vs service error

| Cause | Typical status | Who returns |
|-------|----------------|-------------|
| Bad JSON / tag failure | 400 | handler after ShouldBind |
| Body too large | 400 or 413 | MaxBytesReader / Server |
| Email already in DB | 409 | service map |
| No row for UPDATE | 404 `item_missing` | service |
| Panic in handler | 500 | Recovery (not a strategy) |

### c.Query vs ShouldBindQuery

| API | When | Drawback |
|-----|------|----------|
| `c.Query("q")` | one string | no type/gte |
| `c.DefaultQuery("page", "1")` | string default | still manual int parse |
| `ShouldBindQuery` | more fields + binding | more code for one key |

For a list endpoint with page/sort/filter — bind a struct. For one debug key — `Query` is OK.

**Predict the result:** `Page int` with `form:"page"` and request `?page=abc`. What do you expect?

**Answer:** bind error (cannot go into int) → 400. Not silently `Page=0` as success.

### ShouldBindUri vs c.Param — when which

| Situation | Choice |
|-----------|--------|
| One `:id` string | `c.Param` often enough |
| More uri fields + `binding` | `ShouldBindUri` |
| UUID format check | `uri` + `binding:"required,uuid"` (if the validator supports it) |
| ID in both path and body | path wins; ignore body ID or reject mismatch |

### Content-Type traps

```go
// Client sends JSON but forgets the header
// ShouldBind may pick the wrong binder
```

For a strict JSON API: `ShouldBindJSON` — do not guess. If the header is missing, better 400 than a silent wrong parse.

| Call | Relies on Content-Type |
|------|------------------------|
| `ShouldBindJSON` | expects JSON |
| `ShouldBindQuery` | query string (not body) |
| `ShouldBind` | yes — picks strategy |
| `ShouldBindUri` | path Param |

### omitempty in binding vs json

| Tag | Role |
|-----|------|
| `json:"x,omitempty"` | on **encode** output — do not send zero |
| `binding:"omitempty"` | on **validation** — skip rules if zero |
| `binding:"required"` | must be present / non-zero by rules |

Do not mix: `omitempty` on the json tag does not mean “optional on input” by name alone — input is controlled by `binding`.

### Helper pattern for 400

```go
func badRequest(c *gin.Context) {
	c.AbortWithStatusJSON(http.StatusBadRequest, gin.H{"error": "invalid input", "code": "bad_request"})
}
```

One shape. Log `err` from bind with request ID (from `c.Get`), without the password body.

## Rules and syntax

1. Prefer `ShouldBind*` over `Bind*`.
2. DTO at the boundary ≠ domain entity necessarily.
3. `json` + `binding` for JSON body; `form` for query/form; `uri` for path.
4. Manual default for page, not a magic `default=` tag.
5. Limit Body before bind.
6. One bind per body; the body is consumed.
7. Business rules in the service with `c.Request.Context()`.
8. Generic 400 to the client; detail in the log.
9. `*bool` when you need absence vs false.
10. Password never back in response/log.

## Examples

### Example 1: ShouldBindJSON + binding

```go
package main

import (
	"net/http"

	"github.com/gin-gonic/gin"
)

type CreateUser struct {
	Email string `json:"email" binding:"required,email"`
	Age   int    `json:"age" binding:"required,gte=18,lte=120"`
}

func main() {
	r := gin.New()
	r.Use(gin.Recovery())
	r.POST("/users", func(c *gin.Context) {
		c.Request.Body = http.MaxBytesReader(c.Writer, c.Request.Body, 1<<20)
		var in CreateUser
		if err := c.ShouldBindJSON(&in); err != nil {
			c.AbortWithStatusJSON(http.StatusBadRequest, gin.H{"error": "invalid input"})
			return
		}
		c.JSON(http.StatusCreated, gin.H{"email": in.Email, "age": in.Age})
	})
	_ = r.Run(":8080")
}
```

#### What happens here

MaxBytesReader limits the body. ShouldBindJSON fills the struct and checks tags. Error → 400 + Abort + return. Success → 201. No panic. Email format is binding; “already exists” would be the service.

### Example 2: Query list

```go
type ListQuery struct {
	Q     string `form:"q"`
	Page  int    `form:"page" binding:"omitempty,gte=1"`
	Active *bool `form:"active"`
}

func list(c *gin.Context) {
	var q ListQuery
	if err := c.ShouldBindQuery(&q); err != nil {
		c.AbortWithStatusJSON(http.StatusBadRequest, gin.H{"error": "invalid input"})
		return
	}
	if q.Page == 0 {
		q.Page = 1
	}
	c.JSON(http.StatusOK, gin.H{"q": q.Q, "page": q.Page, "active": q.Active})
}
```

#### What happens here

Query uses the `form` tag. Page 0 after a successful bind (absent) becomes 1 manually. `Active` stays nil if the query has no key — distinct from false. **Predict:** `?page=0` with `gte=1` — what do you expect? **Answer:** binding error → 400 (0 is not ≥ 1).

### Example 3: Uri + body update

```go
type UpdateURI struct {
	ID string `uri:"id" binding:"required"`
}
type UpdateBody struct {
	Name string `json:"name" binding:"required,min=1,max=100"`
}

func updateItem(c *gin.Context) {
	var uri UpdateURI
	if err := c.ShouldBindUri(&uri); err != nil {
		c.AbortWithStatusJSON(http.StatusBadRequest, gin.H{"error": "invalid uri"})
		return
	}
	c.Request.Body = http.MaxBytesReader(c.Writer, c.Request.Body, 1<<20)
	var body UpdateBody
	if err := c.ShouldBindJSON(&body); err != nil {
		c.AbortWithStatusJSON(http.StatusBadRequest, gin.H{"error": "invalid body"})
		return
	}
	// err := svc.Rename(c.Request.Context(), uri.ID, body.Name)
	c.JSON(http.StatusOK, gin.H{"id": uri.ID, "name": body.Name})
}
```

#### What happens here

Two binds, two clear 400s. ID does not come from the body (prevents path/body mismatch). Context for the service stays ready.

### Example 4: Form login (without leaking the password)

```go
type LoginForm struct {
	User string `form:"user" binding:"required"`
	Pass string `form:"pass" binding:"required,min=8"`
}

func login(c *gin.Context) {
	var in LoginForm
	if err := c.ShouldBind(&in); err != nil {
		c.AbortWithStatusJSON(http.StatusBadRequest, gin.H{"error": "invalid input"})
		return
	}
	// check credential in the service — never return in.Pass
	c.JSON(http.StatusOK, gin.H{"user": in.User})
}
```

#### What happens here

`ShouldBind` reads form encoding. The response echoes only user. Pass stays in memory briefly — do not log the struct with `%+v` in production.

### Example 5: Helper and service boundary

```go
func writeBindError(c *gin.Context, err error) {
	// log.Debug("bind", "err", err) // detail internally
	c.AbortWithStatusJSON(http.StatusBadRequest, gin.H{"error": "invalid input"})
}

func create(svc UserService) gin.HandlerFunc {
	return func(c *gin.Context) {
		var in CreateUser
		if err := c.ShouldBindJSON(&in); err != nil {
			writeBindError(c, err)
			return
		}
		u, err := svc.Create(c.Request.Context(), in.Email, in.Age)
		if err != nil {
			// map conflict → 409, other → 500 without leaking
			c.AbortWithStatusJSON(http.StatusInternalServerError, gin.H{"error": "internal error"})
			return
		}
		c.JSON(http.StatusCreated, u)
	}
}
```

#### What happens here

One helper for 400. The service receives an already-checked shape + Request Context. Bind error and business error do not share the same status without thought.

### Example 6: Patch DTO with pointer fields

```go
type PatchUser struct {
	Email *string `json:"email" binding:"omitempty,email"`
	Age   *int    `json:"age" binding:"omitempty,gte=18,lte=120"`
}

func patchUser(c *gin.Context) {
	c.Request.Body = http.MaxBytesReader(c.Writer, c.Request.Body, 1<<20)
	var in PatchUser
	if err := c.ShouldBindJSON(&in); err != nil {
		c.AbortWithStatusJSON(http.StatusBadRequest, gin.H{"error": "invalid input"})
		return
	}
	if in.Email == nil && in.Age == nil {
		c.AbortWithStatusJSON(http.StatusBadRequest, gin.H{"error": "empty patch"})
		return
	}
	// svc.Patch(c.Request.Context(), c.Param("id"), in)
	c.Status(http.StatusNoContent)
}
```

#### What happens here

Pointer fields distinguish “not sent” from zero value (like `*bool` in query). Empty object `{}` passes bind but fails the business/HTTP check “empty patch”. Email format is still binding; “email taken” remains 409 in the service. MaxBytesReader and Abort + return remain.

**Predict the result:** JSON `{"age":0}` with `gte=18` on `*int`. What do you expect?

**Answer:** bind error — 0 is not ≥ 18. A pointer does not skip numeric rules when the value is present.

### Example 7: List with sort oneof

```go
type ListQuery struct {
	Q    string `form:"q"`
	Page int    `form:"page" binding:"omitempty,gte=1"`
	Sort string `form:"sort" binding:"omitempty,oneof=created_at name"`
}

func listUsers(c *gin.Context) {
	var q ListQuery
	if err := c.ShouldBindQuery(&q); err != nil {
		c.AbortWithStatusJSON(http.StatusBadRequest, gin.H{"error": "invalid input"})
		return
	}
	if q.Page == 0 {
		q.Page = 1
	}
	if q.Sort == "" {
		q.Sort = "created_at"
	}
	c.JSON(http.StatusOK, gin.H{"q": q.Q, "page": q.Page, "sort": q.Sort})
}
```

#### What happens here

`oneof` rejects `sort=password` or an arbitrary SQL-like string at the boundary. Default sort after a successful bind — explicitly. Query never goes raw into SQL without an allowlist; `oneof` is the first allowlist layer.

## Decision analysis

| Decision | Choice | Why |
|----------|--------|-----|
| Should vs Bind | Should | response control |
| default page | manual `if Page==0` | explicit, testable |
| Validation detail to client | generic in prod | less leakage / stable contract |
| Query bool | `*bool` | three states |
| Body limit | MaxBytesReader | DoS hygiene |

## Trade-offs

- **Tag validation** — fast; limited rule language.
- **Generic 400** — stable API; harder self-service debug without logs.
- **dive** — powerful; easy to overdo depth.
- **One DTO for all sources** — fewer types; confusing tags.

## Common mistakes

1. **Wrong:** `BindJSON` then another Write.  
   **Effect:** duplicate/unwanted response.  
   **Fix:** ShouldBind + one Abort/JSON.

2. **Wrong:** `form:"page,default=1"` as a contract.  
   **Effect:** different behavior / false security.  
   **Fix:** manual default.

3. **Wrong:** no body limit.  
   **Effect:** memory pressure.  
   **Fix:** MaxBytesReader + server limits.

4. **Wrong:** business rule only in `binding`.  
   **Effect:** uncaught conflicts in the DB.  
   **Fix:** service + status 409.

5. **Wrong:** `bool` for an optional filter.  
   **Effect:** you cannot say “not sent”.  
   **Fix:** `*bool`.

6. **Wrong:** second `ShouldBindJSON` on the same Request.  
   **Effect:** EOF / empty bind.  
   **Fix:** once, or BodyWith.

7. **Wrong:** logging the whole LoginForm.  
   **Effect:** password leak.  
   **Fix:** log only user/id.

8. **Wrong:** unexported fields in DTO (`email` lowercase).  
   **Effect:** always empty bind, fake required fail.  
   **Fix:** `Email` exported.

9. **Wrong:** `ShouldBind` for a strict JSON API “because shorter”.  
   **Effect:** wrong binder when Content-Type is missing/weird.  
   **Fix:** `ShouldBindJSON`.

10. **Wrong:** ID only in JSON body while the URL has another ID.  
    **Effect:** mismatch, cache confusion, security smell.  
    **Fix:** URI bind / Param as source of truth.

11. **Wrong:** always returning raw validator `err.Error()` to the client.  
    **Effect:** unstable contract, possible internal leak.  
    **Fix:** generic 400; detail in log / debug flag.

## Idiomatic Go

- DTO in `internal/httpapi/dto`.
- Consistent `writeBindError`.
- Service takes plain values or a domain command, not `*gin.Context`.
- Tests: valid JSON, `{}`, wrong type, body too large, uri without id.
- **Exported** fields in DTO (capital letter) so the binder and `encoding/json` see the fields.

## Practical scenario

The API accepts `page=0` and runs huge OFFSET queries. The team adds `binding:"omitempty,gte=1"` + manual default 1. At the same time MaxBytesReader 1 MiB cuts upload abuse. ShouldBind replaces Bind — QA can assert the exact JSON 400. Unique email stays in the service → 409. The incident class “validator said OK, DB blew up on unique” disappears as a confusion class because statuses are no longer the same.

## Check questions

1. Why ShouldBindJSON instead of BindJSON?  
   **Answer:** returns error; you control the response and Abort.

2. Which tag for query parameters?  
   **Answer:** `form:"..."`.

3. Where does “email already exists” live?  
   **Answer:** in the service/DB, not in a binding tag.

4. Why `*bool` in a query filter?  
   **Answer:** distinguishes absent from false (zero value).

5. What to do instead of `default=` in a form tag?  
   **Answer:** after a successful bind set the default manually.

6. Why MaxBytesReader?  
   **Answer:** limits body size before (and during) reading — DoS hygiene.

7. How do you pass cancellation into the service?  
   **Answer:** `c.Request.Context()`.

8. What does `dive` do on a slice field?  
   **Answer:** applies binding rules to each slice element.

9. Why separate Uri and Body structs on update?  
   **Answer:** clear 400 messages; path ID as source of truth; fewer mixed tags.

10. Does `json:"x,omitempty"` make the field optional on input?  
    **Answer:** not reliably as input semantics — input is controlled by `binding` (e.g. omitempty/required).

11. Why should the service not take `*gin.Context`?  
    **Answer:** thinner domain, easier test; pass `context.Context` + plain values.

12. What is the risk of a second `Request.Body` read?  
    **Answer:** the body is consumed — EOF / empty bind.

### Source → API table

| Source | Method | Field tags |
|--------|--------|------------|
| JSON body | `ShouldBindJSON` | `json`, `binding` |
| Query | `ShouldBindQuery` | `form`, `binding` |
| Path | `ShouldBindUri` | `uri`, `binding` |
| Form | `ShouldBind` | `form`, `binding` |

### Predict: zero value and required

Struct field `Name string` with `binding:"required"` — does JSON `{"name":""}` pass?

**Answer:** typically **no** — an empty string is treated as unsatisfied required for a string. Confirm exact behavior with a test for your validator version; do not guess in production without a test.

JSON without the `name` field — also fails required. JSON with `"name":"Ana"` — passes.

### Binding and exported fields

```go
type bad struct {
	name string `json:"name" binding:"required"` // unexported
}
```

`encoding/json` and the binder **do not fill** unexported fields. Use `Name` (**exported**). That is not “Gin magic” — that is Go visibility.

### Predict the result — quick set (07.04)

**1.** `Age int` with `binding:"required,gte=18"`, JSON `{"age":0}` — passes?

**Answer:** no — 0 is zero value and fails required/gte rules (confirm with a test).

**2.** `Active *bool`, query without `active` — value after bind?

**Answer:** `nil`.

**3.** `ShouldBindUri` on a route without `:id` while the struct asks for `uri:"id" required`?

**Answer:** bind error → 400.

**4.** Form login success — may the JSON response contain `pass`?

**Answer:** no.

### Mini trace: MaxBytesReader then bind

```text
Body 5 MiB, limit 1 MiB
  → reading stops at the limit
  → ShouldBindJSON sees an error
  → 400/413 mapping (document what you return)
  → service is not called
```

Without a limit, the decoder may try to load a huge tree into memory. The limit is hygiene, not “paranoia”.

### DTO checklist on a PR

1. Exported fields
2. Correct tag for the source (`json` / `form` / `uri`)
3. `ShouldBind*` not `Bind*`
4. MaxBytesReader on body routes
5. Manual default page/sort
6. Business rules outside tags
7. Generic 400 + log detail
8. Test: happy path, `{}`, wrong type, body limit

## Summary

- `ShouldBind*` + DTO tags cover input shape; you write 400.
- Query uses the `form` tag; page default manually; `*bool` for three states.
- Separate URI and body; limit the body; the body is consumed by one read.
- Business rules and `context` live in the service, not in a tag.
- Do not treat magic `default=` as a contract; do not leak passwords.
