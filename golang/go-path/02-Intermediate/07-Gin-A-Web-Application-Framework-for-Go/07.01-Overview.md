# 07.01 Overview of the Gin framework

> **Go Path - Zero to Gopher** / **02 Intermediate → Gin: A Web Application Framework for Go** / Lesson 07.01

## Lesson goals

After this lesson you should be able to:

- explain **why** a team chooses a web framework after plain `net/http`
- distinguish `gin.Default()` from `gin.New()` and know what each registers
- understand the role of `*gin.Engine` as the router and middleware host
- distinguish `gin.Context` from `context.Context` and know when to use `c.Request.Context()`
- have a mental model of **radix tree** routing (the idea, without implementing the tree)
- add the `github.com/gin-gonic/gin` module and run a minimal server (Go 1.22+)
- know when Gin is **not** needed and how Engine sits behind `http.Server`

## Prerequisite

- module 06: `http.Handler`, middleware as `func(http.Handler) http.Handler`, tests with `httptest`
- `go mod` basics (`go mod init`, `go get`, `go.mod`)
- HTTP methods, status codes, JSON basics
- familiarity with `context.Context` (cancellation, `WithTimeout`) at the level of “I pass it into I/O”

## Problem this lesson solves

Plain `net/http` is enough and powerful. The problem is not that “you can’t” — the problem is that you **repeat the same boilerplate** as soon as the API surface grows:

- reading the body and `encoding/json` into a struct
- field validation (required, range, format)
- route groups with shared middleware (`/v1`, `/admin`)
- convenient helpers for JSON responses and path parameters

Gin does not replace HTTP. It **sits on** `net/http`: Engine implements `http.Handler`, and the handler still works over the HTTP request and response. The framework shortens the path from “I registered a route” to “I read JSON and returned a status”.

This lesson sets the frame: what you get, what you pay (dependency, Context magic, framework upgrades), and how `*gin.Engine` sits at the center. Routing, binding, middleware, and testing details come in 07.02–07.09 — here you must know **where** each piece lives.

## Mental model

Imagine one entry into the application: `http.Server` accepts a TCP connection, parses HTTP, then calls `Handler.ServeHTTP`. In a Gin application that `Handler` is the Engine.

```text
client
  → http.Server (timeouts, Listen)
    → *gin.Engine (http.Handler)
         ├─ global middleware chain (Logger, Recovery, yours)
         ├─ radix tree of routes (method + path → handler chain)
         └─ per request: *gin.Context
              ├─ *http.Request
              ├─ ResponseWriter
              ├─ Param / Query / bind helpers
              └─ Set / Get (request-scoped map)
```

`gin.Context` is a **wrapper** around request/response with helper methods (`ShouldBindJSON`, `JSON`, `Param`, …). It is **not** `context.Context` from the standard library. The first time you see the name: Context here means “Gin’s per-request object”, not cancellation. For database cancellation and other I/O you use `c.Request.Context()`.

**Radix tree (idea):** routes are not scanned as a long list of `if` for every request. Prefixes are shared in a tree (`/api/users`, `/api/users/:id`) so matching is efficient. You do not need to implement the tree. Understand two consequences:

1. Gin is fast at routing because it shares prefixes.
2. Registration order is not “first match wins” like a naive list — the tree picks the path by structure. Conflicts (two routes that cannot be distinguished) are discovered at registration time or in debug mode.

### Glossary table (first time)

| English term | Short gloss | Where it lives |
|--------------|-------------|----------------|
| `Engine` | root router + middleware host | `*gin.Engine` |
| `RouterGroup` | group with a shared prefix | `Group("/v1")` |
| `gin.Context` | Gin’s per-request object | handler parameter |
| `context.Context` | cancellation / deadline | `c.Request.Context()` |
| `HandlerFunc` | `func(*gin.Context)` | routes and middleware |
| `middleware` | layer before/after the handler | `Use`, chain on the route |
| `package` / `module` | package / Go module | `go.mod`, import |
| `map` | key→value map | e.g. `gin.H` |
| `error` | error value | handler boundaries |

## Mechanism

### Why a framework after net/http

Start from one JSON endpoint on plain `net/http`:

```go
mux.HandleFunc("POST /v1/items", func(w http.ResponseWriter, r *http.Request) {
	defer r.Body.Close()
	var in CreateItem
	if err := json.NewDecoder(r.Body).Decode(&in); err != nil {
		http.Error(w, "bad json", http.StatusBadRequest)
		return
	}
	// validate fields manually...
	w.Header().Set("Content-Type", "application/json")
	_ = json.NewEncoder(w).Encode(out)
})
```

That works. When you have 40 such handlers, you repeat Decode, Content-Type, error mapping, path parameters, and auth middleware on a subset of routes. Gin does not remove the need to understand HTTP — it removes **repetition** around the JSON API pattern.

| Need | net/http | Gin |
|------|----------|-----|
| JSON bind + tag validation | manual | `ShouldBindJSON` + `binding` tags |
| Groups `/v1` | manual mux / chi | `RouterGroup` |
| Parameters `/u/:id` | `PathValue` / regex | `c.Param` |
| Middleware | `func(http.Handler) http.Handler` | `gin.HandlerFunc` + `Use` / `c.Next` |
| Logger / Recovery | you write it yourself | built into `Default()` |

A framework makes sense when the API surface grows. For one health endpoint — `net/http` is enough.

### Default vs New

Two Engine constructors:

```go
r := gin.Default() // Engine + Logger + Recovery
r := gin.New()     // empty Engine — you add middleware
```

**What happens in `Default()`:**

1. Internally calls `New()` — creates an empty Engine.
2. Registers `Logger()` — writes requests (method, path, status, latency) to stdout.
3. Registers `Recovery()` — catches `panic` in the chain, logs the stack, returns 500. Panic is **not** a strategy for business errors; Recovery is a safety net.

**What happens in `New()`:**

1. Creates an Engine without global middleware.
2. You explicitly call `r.Use(gin.Logger())`, `r.Use(gin.Recovery())`, or your own layers.

**Predict the result:** if you do `gin.New()`, register `GET /ping`, deliberately `panic("boom")` in the handler, and send a request — what does the client see?

**Answer:** without Recovery, the panic can crash the goroutine handling the request; behavior is bad for production (often an empty/truncated response). With `Default()` or `New()` + `Recovery()`, the client gets 500, the process stays alive. So in production you **always** have Recovery (built-in or custom), and you still return errors via `error` and `AbortWithStatusJSON`, not via `panic`.

`Default()` is convenient for starting and tutorials. In production you often use `New()` + explicit middleware (structured log, your recovery with a JSON body).

### Engine as the center

```go
r := gin.Default()
r.GET("/ping", func(c *gin.Context) {
	c.JSON(http.StatusOK, gin.H{"message": "pong"})
})
```

Execution trace for `GET /ping`:

1. `http.Server` calls `r.ServeHTTP(w, req)`.
2. Engine creates a `*gin.Context` for this request (binds Writer and Request).
3. Global middleware runs (Logger enters, calls `c.Next()`, …).
4. The radix tree finds the route `GET /ping` and its handler chain.
5. The handler calls `c.JSON` — sets Content-Type, status, serializes the map.
6. Logger (after `Next`) sees the status and writes a line.

`gin.H` is an alias for `map[string]any` — a quick JSON object for prototypes. In an API contract later prefer a typed `struct` with `json` tags.

### gin.Context is not context.Context

This is the most common conceptual mistake after switching from `net/http`.

```go
func getItem(c *gin.Context) {
	id := c.Param("id")

	// WRONG as a type: c is not context.Context
	// db.QueryContext(c, ...)  // does not compile (wrong type)

	// CORRECT: cancellation from the HTTP request
	ctx := c.Request.Context()
	row, err := db.QueryContext(ctx, `SELECT name FROM items WHERE id = $1`, id)
	_ = row
	_ = err
}
```

| Need | Use |
|------|-----|
| Path parameter | `c.Param("id")` |
| JSON response | `c.JSON(...)` |
| Request-scoped value (user ID) | `c.Set` / `c.Get` |
| Cancellation for DB / HTTP client | `c.Request.Context()` |
| Deadline / timeout call | `context.WithTimeout(c.Request.Context(), …)` |

**Predict the result:** middleware sets `c.Set("userID", "u-9")`. The handler does `v, ok := c.Get("userID")`. What are `v` and `ok`?

**Answer:** `ok == true`, `v` is `any` with value `"u-9"`. For typed reading often `c.GetString("userID")` (returns `""` if missing or not a string — check the contract).

`Set`/`Get` live **only** for that request. Do not put a DB pool, logger singleton, or whole-process configuration there — those are dependencies on the handler struct or in `main`.

### Run vs http.Server

```go
_ = r.Run(":8080") // internally ListenAndServe; convenient for demos
```

`Run` is a short path. It does not easily give you `ReadHeaderTimeout`, graceful `Shutdown`, or a custom `BaseContext`. For anything closer to production:

```go
srv := &http.Server{
	Addr:              ":8080",
	Handler:           r, // Engine is http.Handler
	ReadHeaderTimeout: 5 * time.Second,
}
log.Fatal(srv.ListenAndServe())
```

The Engine stays the same. Only **how** you listen changes. Timeouts and Shutdown remain your responsibility — Gin does not “turn them on magically”.

### Gin modes

```go
gin.SetMode(gin.DebugMode)   // default in development
gin.SetMode(gin.ReleaseMode) // less debug noise
gin.SetMode(gin.TestMode)    // tests (lesson 07.09)
```

Debug mode warns about route conflicts and prints more. In production set `ReleaseMode` early in `main` (before route registration if you want a consistent mode).

### Installation and modules

```bash
go mod init example.com/api
go get github.com/gin-gonic/gin@latest
```

The import path is `github.com/gin-gonic/gin`. That is a **module** / **package** dependency in `go.mod`. Without `go get`, the build cannot find the types.

### When Gin is not needed

Stay on `net/http` if:

- you have 1–3 routes and no JSON bind complexity
- you are writing a library that must not pull in a web framework
- you are learning HTTP basics (module 06) — first understand `Handler`

Choose Gin when the number of JSON endpoints, groups, and bindings grows. The switch is not “all or nothing”: during migration you can use `gin.WrapH` around an existing `http.Handler`.

### Bridge to module 06

| Concept 06 | Gin |
|------------|-----|
| `http.HandlerFunc` | `gin.HandlerFunc` |
| `func(http.Handler) http.Handler` | middleware with `c.Next()` / `c.Abort()` |
| `ServeMux` patterns | Engine + radix |
| `PathValue` (Go 1.22+) | `c.Param` |
| manual JSON encode | `c.JSON` |
| `r.Context()` | `c.Request.Context()` |

Learn Gin as a **convenience layer**, not as a second HTTP world.

### Engine methods you will see often

| Method | Role |
|--------|------|
| `GET` / `POST` / `PUT` / `PATCH` / `DELETE` | route registration |
| `Group` | prefix + `RouterGroup` |
| `Use` | global (or group) middleware |
| `Static` / `StaticFS` | static files |
| `NoRoute` / `NoMethod` | fallback (07.03) |
| `Run` / `RunTLS` | quick listen |
| `Routes` | introspection of registered routes |

`Static` is convenient, but the same warnings as `FileServer`: root, listing, do not serve secrets.

### Comparison table: three ways to “run” Gin

| Approach | What you get | What you lose | When |
|----------|--------------|---------------|------|
| `r.Run(":8080")` | one line, quick demo | timeouts, Shutdown, custom BaseContext | local tutorial |
| `http.ListenAndServe(":8080", r)` | Engine as Handler | still weak timeout defaults | transitional step |
| `&http.Server{…}.ListenAndServe()` | full control | more boilerplate | production / staging |

**Predict the result:** you put Engine in `http.Server.Handler`, but still call `r.Run` in another goroutine on the same port. What do you expect?

**Answer:** port conflict — the second listen fails with “address already in use”. One listen entry per process for that Addr. Do not mix `Run` and `Server` on the same port.

### Trace: Set / Get through middleware and handler

```text
middleware A: c.Set("requestID", "r-1"); c.Next()
  middleware B: c.Next()
    handler: id := c.GetString("requestID")  → "r-1"
  (return B)
(return A — can log id from Get)
```

The request-scoped map lives for as long as that `*gin.Context`. The next request gets a **new** Context — do not expect `Set` to survive between requests. That is not an application cache.

**Predict the result:** handler A does `c.Set("x", 1)`. Handler B on a **different** route in the same process does `c.Get("x")` on its request. What is `ok`?

**Answer:** `ok == false` (or empty value via GetString) — different map, different Context. `Set` is not a global store.

### DebugMode vs ReleaseMode — what you change in practice

| Mode | Typical effect | Risk if you get it wrong |
|------|----------------|--------------------------|
| `DebugMode` | more route warnings, verbose | noise in production logs |
| `ReleaseMode` | less debug output | you may miss a route conflict if you never tested |
| `TestMode` | more predictable output in tests | do not mix with production `main` |

Set the mode **early** in `main`, before route registration when you want a consistent start. Do not change the mode mid-request handling.

### gin.WrapH — bridge from the net/http world

```go
old := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
	w.WriteHeader(http.StatusOK)
	_, _ = w.Write([]byte("old handler"))
})
r.GET("/legacy", gin.WrapH(old))
```

`WrapH` turns an `http.Handler` into a `gin.HandlerFunc`. Use that while migrating module 06 code into Gin. Still true: one Engine as the entry; do not register the old handler in parallel on `DefaultServeMux` if Server only looks at Engine.

**Predict the result:** the legacy handler calls `http.Error` and writes a body. Can Gin middleware after it in the same chain reliably change the status?

**Answer:** not reliably — the response has already started. Migrating handlers must be aware that Write “locks” the status. New code prefers `c.JSON` / `AbortWithStatusJSON` before the first Write.

## Rules and syntax

1. Handler signature: `func(c *gin.Context)` — that is `gin.HandlerFunc`.
2. `gin.Default()` = `New()` + `Logger` + `Recovery`.
3. `gin.New()` = empty Engine; add Recovery explicitly.
4. `gin.Context` ≠ `context.Context`; for I/O use `c.Request.Context()`.
5. `gin.H` is `map[string]any` — prototype, not a long-term contract.
6. Engine is `http.Handler` — put it in `http.Server.Handler`.
7. Panic is not control flow; Recovery catches panic, you return `error` responses.
8. One routing entry: do not mix `http.DefaultServeMux` and Gin Engine for the same routes.
9. Go 1.22+: same `http.Server` patterns as in module 06; Gin does not change that rule.
10. `go get github.com/gin-gonic/gin` before the first import.

### Minimal main (syntax)

```go
package main

import "github.com/gin-gonic/gin"

func main() {
	r := gin.Default()
	r.GET("/ping", func(c *gin.Context) {
		c.JSON(200, gin.H{"message": "pong"})
	})
	_ = r.Run(":8080")
}
```

In production code prefer the `http.StatusOK` constant and checking the error from `ListenAndServe` / `Run`.

## Examples

### Example 1: Default hello

```go
package main

import (
	"net/http"

	"github.com/gin-gonic/gin"
)

func main() {
	r := gin.Default()
	r.GET("/", func(c *gin.Context) {
		c.String(http.StatusOK, "hello from Gin")
	})
	if err := r.Run(":8080"); err != nil {
		panic(err) // bootstrap only; in a real main use log.Fatal
	}
}
```

#### What happens here

`Default` creates the Engine and attaches Logger and Recovery. `GET "/"` registers the handler in the radix tree. When `GET /` arrives, the middleware chain calls the handler; `c.String` writes plain text with status 200. `Run` blocks on listen. Logger after the handler prints a line with status and duration. If the handler panics, Recovery catches the panic before it crashes the whole process.

### Example 2: New without Logger, with Recovery

```go
package main

import (
	"net/http"

	"github.com/gin-gonic/gin"
)

func main() {
	r := gin.New()
	r.Use(gin.Recovery())

	r.GET("/quiet", func(c *gin.Context) {
		c.JSON(http.StatusOK, gin.H{"ok": true})
	})

	_ = r.Run(":8080")
}
```

#### What happens here

`New` does not register Logger — stdout has no Gin access log. Recovery remains, so a panic still becomes 500. You use this pattern when you have your own structured logger (zap, slog) and do not want a duplicate format. Explicitness: you see in `main` exactly which middleware exists.

**Predict the result:** remove `r.Use(gin.Recovery())` and leave `panic("x")` in the handler. Is that acceptable for production?

**Answer:** no. Without Recovery, a panic in the handler is not safely handled. Put Recovery or CustomRecovery back.

### Example 3: Engine as http.Handler with timeouts

```go
package main

import (
	"log"
	"net/http"
	"time"

	"github.com/gin-gonic/gin"
)

func main() {
	gin.SetMode(gin.ReleaseMode)

	r := gin.New()
	r.Use(gin.Recovery())
	r.GET("/health", func(c *gin.Context) {
		c.Status(http.StatusOK)
	})

	srv := &http.Server{
		Addr:              ":8080",
		Handler:           r,
		ReadHeaderTimeout: 5 * time.Second,
	}
	log.Fatal(srv.ListenAndServe())
}
```

#### What happens here

`ReleaseMode` reduces debug noise. Engine is the Server’s `Handler` field — the same hygiene pattern as in module 06. `c.Status` sends only a status with no body (convenient for health). `ReadHeaderTimeout` protects against a slow client that never finishes headers. Gin does not “add” the timeout here; you set it on the Server.

### Example 4: Multiple routes, gin.H, and Request.Context

```go
package main

import (
	"context"
	"database/sql"
	"net/http"
	"time"

	"github.com/gin-gonic/gin"
)

type Server struct {
	DB *sql.DB
}

func (s *Server) ping(c *gin.Context) {
	c.JSON(http.StatusOK, gin.H{"message": "pong"})
}

func (s *Server) version(c *gin.Context) {
	c.JSON(http.StatusOK, gin.H{"version": "1.0.0"})
}

func (s *Server) dbCheck(c *gin.Context) {
	ctx, cancel := context.WithTimeout(c.Request.Context(), 2*time.Second)
	defer cancel()

	if err := s.DB.PingContext(ctx); err != nil {
		c.JSON(http.StatusServiceUnavailable, gin.H{"ok": false})
		return
	}
	c.JSON(http.StatusOK, gin.H{"ok": true})
}

func main() {
	// db := ... open the pool in a real program
	s := &Server{DB: nil} // placeholder — in the exercise connect a real *sql.DB

	r := gin.New()
	r.Use(gin.Logger(), gin.Recovery())
	r.GET("/ping", s.ping)
	r.GET("/version", s.version)
	if s.DB != nil {
		r.GET("/readyz", s.dbCheck)
	}
	_ = r.Run(":8080")
}
```

#### What happens here

Handlers are **methods** on the `Server` struct — dependencies (`*sql.DB`) live in fields, not in global variables. `ping` and `version` use `gin.H` for quick JSON. `dbCheck` shows the real bridge to `context`: it takes `c.Request.Context()`, adds a timeout, calls `PingContext`. If the client aborts the request, ctx is cancelled and Ping can stop. The `DB == nil` branch is only so the example compiles without a real database; in production readiness always has a pool.

### Example 5: Why not to mix DefaultServeMux

```go
package main

import (
	"net/http"

	"github.com/gin-gonic/gin"
)

func main() {
	// Avoid a parallel “source of truth” for routing:
	// http.Handle("/old", oldHandler)  // DefaultServeMux
	// and separately:
	r := gin.Default()
	r.GET("/new", func(c *gin.Context) {
		c.String(http.StatusOK, "new")
	})

	// One entry:
	srv := &http.Server{Addr: ":8080", Handler: r}
	_ = srv.ListenAndServe()
}
```

#### What happens here

If you register routes on both `http.DefaultServeMux` and Gin Engine, and Server uses only one of them, the other half of the routes “disappears”. Migration: gradually move routes into Gin; temporarily `gin.WrapH(oldHandler)` on a Gin route. One `Handler` on the Server — one source of truth.

### Example 6: CustomRecovery with a JSON body

```go
package main

import (
	"net/http"

	"github.com/gin-gonic/gin"
)

func main() {
	r := gin.New()
	r.Use(gin.CustomRecovery(func(c *gin.Context, recovered any) {
		// log.Error("panic", "recovered", recovered) — in real code
		c.AbortWithStatusJSON(http.StatusInternalServerError, gin.H{
			"error": "internal error",
			"code":  "panic_recovered",
		})
	}))

	r.GET("/boom", func(c *gin.Context) {
		panic("intentional bug for demo")
	})
	r.GET("/ok", func(c *gin.Context) {
		c.JSON(http.StatusOK, gin.H{"ok": true})
	})
	_ = r.Run(":8080")
}
```

#### What happens here

Instead of the default Recovery text, `CustomRecovery` catches the panic and returns the **same JSON shape** as the rest of the API. The client still gets 500; the process stays alive. `/ok` works normally. Panic in `/boom` is **not** a model for “no resource” — only a demonstration of the net. In production log `recovered` and the stack internally; leave a generic message for the client.

**Predict the result:** in CustomRecovery you forget `Abort` / `AbortWithStatusJSON` and only log. What does the client see?

**Answer:** often an incomplete or empty response — the panic was “swallowed” without a clear HTTP finish. Always finish the response in the recovery callback.

## Decision analysis

| Decision | Choice | Why |
|----------|--------|-----|
| Gin vs plain `net/http` | Gin for a growing JSON API | Less boilerplate for bind, groups, JSON |
| Gin vs plain `net/http` | `net/http` for a small surface | Fewer dependencies, clearer HTTP |
| `Default` vs `New` | `New` + explicit in production | You see Logger/Recovery; easier to replace log |
| `Run` vs `http.Server` | `http.Server` | Timeout, Shutdown, control |
| `gin.H` everywhere | Prototype only | Typed `struct` for the contract |
| Panic for 404 | Never | `AbortWithStatusJSON` / `NoRoute` |
| `c` as `context.Context` | Never | `c.Request.Context()` |

## Trade-offs

- **Dependency** — faster features; you pay for framework upgrades and a third-party API surface.
- **Context magic** — less code; harder to track “what was Set” if you overuse the request map.
- **Opinionated** — excellent for JSON APIs; less ideal if you need an extremely custom HTTP pipeline.
- **Radix performance** — excellent for many routes; your handler I/O still dominates latency.
- **Default Logger** — quickly visible; often not the format you want in production (hence `New`).

## Common mistakes

1. **Wrong:** forgotten `go get` / wrong module path.  
   **Effect:** build cannot find `gin`.  
   **Fix:** `go get github.com/gin-gonic/gin` and check `go.mod`.

2. **Wrong:** `Default()` in production without thinking about log format.  
   **Effect:** unstructured stdout, harder to scrape.  
   **Fix:** `New()` + your logger middleware.

3. **Wrong:** only `Run` without `ReadHeaderTimeout`.  
   **Effect:** a slow client holds connections.  
   **Fix:** `http.Server` with timeout fields.

4. **Wrong:** mixing the terms `gin.Context` and `context.Context`.  
   **Effect:** `QueryContext(c, …)` does not compile or cancellation is lost.  
   **Fix:** `c.Request.Context()` for I/O.

5. **Wrong:** panic as control flow (“no user → panic”).  
   **Effect:** Recovery returns a generic 500; you lose a precise status.  
   **Fix:** `c.AbortWithStatusJSON` + `return`; Recovery stays for real bugs.

6. **Wrong:** parallel `DefaultServeMux` + Gin Engine.  
   **Effect:** “route works locally in a mux test, but not on the server”.  
   **Fix:** one Handler — Engine.

7. **Wrong:** DB pool in `c.Set`.  
   **Effect:** confusing lifecycle, harder tests.  
   **Fix:** field on the handler struct.

8. **Wrong:** expecting Gin to solve HTTP/2 / TLS differently from `net/http`.  
   **Effect:** false security.  
   **Fix:** TLS and Server configuration are still yours.

9. **Wrong:** `gin.SetMode` mid-handler per request.  
   **Effect:** nondeterministic noise, races in logs.  
   **Fix:** mode once in `main` / test setup.

10. **Wrong:** treating `c.Set` as a cache between requests.  
    **Effect:** “sometimes has a value” — actually a different Context.  
    **Fix:** Set only request-scoped; cache in a dependency / outside.

## Idiomatic Go

- Module import: `github.com/gin-gonic/gin`.
- Wiring in `main` / `cmd/api`: `New` Engine, `Use` middleware, register routes, `http.Server`.
- Handler as a **method** with a receiver on a dependency struct.
- Typed request/response `struct`s instead of endless `gin.H`.
- `error` at boundaries; panic only for bugs (and then Recovery).
- Tests via `httptest` + Engine (lesson 07.09) — the same router as in `main`.
- Do not export (`exported`) internal state that does not need to be public; keep the HTTP adapter thin.

## Practical scenario

A team has 40 JSON routes on plain `net/http` with copy-paste bind. A new developer spends a day on boilerplate. They introduce Gin: `gin.New()`, explicit Logger + Recovery, groups come in 07.02/07.03. Staging briefly uses `Default` for speed. In production they move to `New` + zap logger middleware. `http.Server` stays with `ReadHeaderTimeout` and graceful `Shutdown`. `readyz` calls `PingContext(c.Request.Context())`. Time to a new endpoint drops, and control over the server lifecycle remains — because Gin did not replace Server, only Handler.

## Check questions

1. What does `gin.Default` add that `gin.New` does not have?  
   **Answer:** the `Logger` and `Recovery` middleware (after the internal `New`).

2. Does Engine implement `http.Handler`?  
   **Answer:** yes — that is why it goes in `http.Server.Handler`.

3. What is (conceptually) a radix tree in Gin routing?  
   **Answer:** a tree of shared path prefixes for efficient method+path matching, instead of a linear list of `if`.

4. Why still use `http.Server` instead of only `Run`?  
   **Answer:** timeouts (`ReadHeaderTimeout`), graceful Shutdown, control of the listen loop.

5. What is `gin.H`?  
   **Answer:** an alias for `map[string]any`, convenient for a quick JSON object.

6. How does Gin relate to `net/http` — replacement or layer?  
   **Answer:** a convenience layer on `net/http`, not a protocol replacement.

7. How do you get a `context.Context` for a database query from a Gin handler?  
   **Answer:** `c.Request.Context()` (wrap with `WithTimeout` if needed).

8. Why does Recovery not replace handling `error` values?  
   **Answer:** it catches panic (bugs); you map business errors to status + JSON and `Abort`, not to panic.

9. Does `c.Set` survive between two HTTP requests?  
   **Answer:** no — each request has its own `*gin.Context` and its own map.

10. What is `gin.WrapH` for?  
    **Answer:** wraps an existing `http.Handler` into a `gin.HandlerFunc` for migration into Engine.

11. Where do you set `gin.ReleaseMode`?  
    **Answer:** early in `main` (before or with route registration), not mid-handler.

12. What is the difference between `ListenAndServe(addr, r)` and `&http.Server{Handler: r}`?  
    **Answer:** the second form enables timeout fields, `Shutdown`, and other Server configuration in one place.

### More detailed trace: from TCP to JSON

Imagine a client sending `GET /ping HTTP/1.1`. Without Gin you would think about `ServeMux`. With Gin the chain looks like this:

1. The OS accepts the connection; `http.Server` reads the request line and headers (`ReadHeaderTimeout` applies here).
2. Server calls `Handler.ServeHTTP` — that is your `*gin.Engine`.
3. Engine allocates / resets a `*gin.Context` for this request: binds `Request`, `Writer`, clears the Param map.
4. Enters the first global middleware. Logger records start time and calls `c.Next()`.
5. `Next` advances the index in the chain. Next is Recovery (if `Default` or explicitly added).
6. Recovery sets a `defer` that catches panic, then calls `c.Next()`.
7. Engine looks up the route in the radix tree for method `GET` and path `/ping`.
8. The found chain (here one handler) runs. The handler calls `c.JSON`.
9. `JSON` sets `Content-Type: application/json`, status, and writes the body.
10. Control returns through `Next`: Recovery’s defer sees no panic; Logger measures duration and status, writes a line.

If in step 8 you do `panic("bug")`, step 10 for Recovery activates the defer: logs the stack, writes 500, marks abort. The handler after the panic does not continue. That is why Recovery exists — not because panic should be your API for “not found”.

### Predict: three configurations

| Setup | Panic in handler | Access log | Typical use |
|-------|------------------|------------|-------------|
| `Default()` | 500 via Recovery | yes (Logger) | tutorial, local start |
| `New()` without Use | bad / process risk | no | almost never in production |
| `New()` + Recovery + your log | 500 | your format | production |

**Predict the result:** `r := gin.New(); r.Use(gin.Logger());` without Recovery, then `panic` in the handler. Does Logger’s line after `Next` reliably finish?

**Answer:** not reliably — panic interrupts normal return through the chain. That is why Recovery sits in the chain (usually early) with `defer recover`.

### Why `gin.H` is not a long-term contract

```go
c.JSON(http.StatusOK, gin.H{"id": id, "name": name})
```

It works. The problem appears when five handlers write slightly different keys (`Id` vs `id`, a missing field). Typed response:

```go
type PingResponse struct {
	Message string `json:"message"`
}

c.JSON(http.StatusOK, PingResponse{Message: "pong"})
```

The compiler and tests catch contract changes. `gin.H` remains for health/prototype.

### Graceful Shutdown sketch (same as module 06)

```go
ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
defer stop()

go func() {
	if err := srv.ListenAndServe(); err != nil && err != http.ErrServerClosed {
		log.Fatal(err)
	}
}()

<-ctx.Done()
shutdownCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
defer cancel()
_ = srv.Shutdown(shutdownCtx)
```

Gin Engine is not shut down separately — `http.Server` is. Active requests get time to finish; new ones are not accepted. `c.Request.Context()` during Shutdown may be cancelled depending on version/settings — that is why DB calls must respect ctx.

### Quick terminology reminder

- **Engine** — root router and middleware host; `http.Handler`.
- **RouterGroup** — group with a prefix and its own `Use` (details in 07.02).
- **gin.Context** — Gin’s per-request object (not `context.Context`, but contains it via Request).
- **HandlerFunc** — `func(*gin.Context)`.
- **Recovery** — middleware that catches panic; not a replacement for `error` handling.

## Summary

- Gin speeds up JSON API development by composing on `net/http`.
- `Default` vs `New` chooses middleware explicitness (Logger + Recovery).
- Engine + radix routes + `gin.Context` are the core model.
- `gin.Context` is not `context.Context`; for cancellation use `c.Request.Context()`.
- Timeout and Shutdown remain your responsibility on `http.Server`.
- Recovery catches panic; business errors go through status and `error` mapping.
