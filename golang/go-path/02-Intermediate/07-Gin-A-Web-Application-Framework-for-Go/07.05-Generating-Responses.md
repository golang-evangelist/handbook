# 07.05 Generating responses in Gin

> **Go Path - Zero to Gopher** / **02 Intermediate → Gin: A Web Application Framework for Go** / Lesson 07.05

## Lesson goals

After this lesson you should be able to:

- send **JSON**, **XML**, and **String** responses via `gin.Context` (Gin request context — gloss once; not `context.Context`)
- set status via `c.JSON`, `c.Status`, `c.AbortWithStatusJSON`
- understand the rule **one meaningful response per request** and why `return` goes immediately after Abort
- keep a consistent **error envelope** and status-code map (200/201/204/400/401/403/404/409/500)
- not mix 200 + an `error` field, not leak DB messages to the client, not use `panic` for control flow
- know when `IndentedJSON` / `PureJSON` make sense, and when `Redirect` is not the right tool for a JSON API

## Prerequisite

- 07.04 (binding, `ShouldBind*`, DTO)
- HTTP status codes and the meaning of “success / client error / server error”
- `encoding/json` intuition (exported fields, `omitempty`)
- difference between `gin.Context` and `context.Context` (for DB/service: `c.Request.Context()`)

## Problem this lesson solves

Without an agreement on responses, a team returns:

- sometimes a string, sometimes JSON, sometimes an HTML error page
- **200** with body `{ "error": "..." }` — clients and monitors think it succeeded
- two serializations in the same request (first 400, then another 200)
- raw `err.Error()` from the database in JSON (schema leak, SQL, paths)
- `IndentedJSON` in production (larger payload, slower)
- `panic("not found")` instead of a status code — Recovery catches the panic and returns a generic 500

Gin helpers (`JSON`, `XML`, `String`, `Status`, `AbortWithStatusJSON`) standardize **serialization and Content-Type**. You still **choose** status codes, envelope shape, and the boundary of what the client may see.

## Mental model

```text
Handler decides:
  success? → c.JSON / c.Status / c.XML / c.String  (+ return)
  error + stop chain? → c.AbortWithStatusJSON(...); return
  domain error? → handleErr(c, err) → status + envelope; return

One request → one meaningful HTTP response.
Headers (if needed) BEFORE the first body write.
DB / service gets context.Context = c.Request.Context(), not *gin.Context.
```

`c.JSON(code, obj)` roughly: set `Content-Type: application/json`, write status, encode the object via `encoding/json` (with Gin nuances like `gin.H`).

`c.AbortWithStatusJSON` = the same as a JSON response **plus** `c.Abort()` — marks that **remaining** handlers / middleware in the chain must not run as “next work”. Code **after** `c.Next()` in outer middleware can still run (you learn that in detail in 07.07). In the handler: after Abort **always** `return`, so you do not “append” a second response.

**One response per request** is not “Gin magic”. It is discipline: after a successful Write do not call another `c.JSON`. After Abort do not continue business logic that writes the body again.

### Status → typical use table

| Code | Constant | Typical meaning in a JSON API |
|------|----------|-------------------------------|
| 200 | `http.StatusOK` | successful read / update that returns a resource |
| 201 | `http.StatusCreated` | resource created; often + `Location` |
| 204 | `http.StatusNoContent` | success with no body (e.g. delete) |
| 400 | `http.StatusBadRequest` | bad input / binding |
| 401 | `http.StatusUnauthorized` | missing / bad authentication |
| 403 | `http.StatusForbidden` | authenticated, no permission |
| 404 | `http.StatusNotFound` | resource does not exist |
| 409 | `http.StatusConflict` | state conflict (e.g. unique) |
| 500 | `http.StatusInternalServerError` | unexpected internal error |

Rule: **do not** send 200 with `{ "error": "..." }`. Status carries semantic weight for clients, CDN, alarms, and the OpenAPI contract.

## Mechanism

### JSON, XML, String

Three basic helpers for the body:

```go
c.JSON(http.StatusOK, gin.H{"ok": true})
c.XML(http.StatusOK, obj)
c.String(http.StatusOK, "hello %s", name)
```

`gin.H` is an alias for `map[string]any` — convenient for quick envelopes. For a stable contract prefer an **exported** `struct` with `json` tags.

**Predict:** what is `Content-Type` after `c.JSON`?

**Answer:** `application/json; charset=utf-8` (Gin’s default for the JSON helper). For XML — XML type. For String — `text/plain`.

XML in a modern JSON-first API is rarely needed; it remains because legacy system clients sometimes ask for it. Use String for health “ok”, a plain probe, or simple text — not for structured errors if the rest of the API speaks JSON.

### Status only (204)

```go
c.Status(http.StatusNoContent) // 204 — no body
```

204 means: success, **no** body. Do not call `c.JSON(...)` after that. Clients that expect JSON on delete often want 200 + a small object — that is a **team contract**, not a Gin rule. If you choose 204, document and test that the body is truly empty.

### AbortWithStatusJSON + return

```go
if token == "" {
	c.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{"error": "missing token"})
	return
}
// further logic only if the token is present
```

Without `return`, the next lines of the handler still run. Abort stops the **rest of the chain** (other handlers registered after this one in the list), but does not “erase” the rest of **your** function. So the idiom is always:

```text
Abort* → return
```

The same applies to `c.AbortWithStatus`, `c.AbortWithError` — in this lesson the focus is `AbortWithStatusJSON` because a JSON API contract wants an envelope.

### IndentedJSON only in development

```go
c.IndentedJSON(http.StatusOK, obj) // prettier print; larger and slower
```

In production: plain `c.JSON`. Indentation costs CPU and bytes. If you debug a response, pretty-print on the client (jq, browser) — not the server.

**Predict:** does `IndentedJSON` change the HTTP status semantically?

**Answer:** no. It only changes the shape of the JSON text. You still pass status as the first argument.

### PureJSON

Gin’s default JSON encoder sometimes escapes HTML characters in strings (`<`, `>` …) to defend against XSS when JSON is embedded in an HTML context. `c.PureJSON` sends JSON **without** that HTML escape — useful when the client expects exact Unicode/characters and it is not HTML embedding.

```go
c.PureJSON(http.StatusOK, gin.H{"msg": "a < b && c > d"})
```

Choose deliberately: browser+HTML embedding vs a pure API client. For a typical mobile/SPA JSON API, PureJSON is a common choice when escape bothers you; for responses that might be embedded in HTML, stay cautious.

### Redirect — rare for a JSON API

```go
c.Redirect(http.StatusFound, "/login")
```

Redirect (302/301/307…) makes sense for browser navigation. For a JSON API client that expects `application/json`, redirect often confuses (follows Location, loses method, gets HTML). Prefer an explicit JSON 401/404 over “go to another URL”.

### Headers before JSON

Headers must be set **before** (or with) the first body write. Example: 201 + Location:

```go
c.Header("Location", "/items/"+id)
c.JSON(http.StatusCreated, gin.H{"id": id})
```

If you call `c.JSON` first, the header may be “too late” — depending on whether the Writer already flushed. Idiom: **Header → JSON/Status**.

More on Cache-Control, cookie, File in 07.06. Here remember the order.

### Error envelope

Agree on one shape:

```json
{ "error": "invalid input" }
```

or richer:

```json
{ "error": { "code": "validation_failed", "message": "invalid input" } }
```

Consistency is worth more than a “clever” message per route. The client parses one type. In production often a **generic** message to the client; detail (validator, SQL) goes to the log, not into JSON.

**Forbidden in this lesson’s contract:**

```go
// BAD: 200 + error field
c.JSON(http.StatusOK, gin.H{"error": "not found"})

// BAD: leaking an internal error
c.JSON(http.StatusInternalServerError, gin.H{"error": err.Error()})
```

### handleErr: domain → HTTP

The service returns `error` values (`errNotFound`, `errConflict`, …). The handler does not know SQL. A helper maps:

```go
var (
	errNotFound = errors.New("not found")
	errConflict = errors.New("conflict")
)

func handleErr(c *gin.Context, err error) {
	switch {
	case errors.Is(err, errNotFound):
		c.AbortWithStatusJSON(http.StatusNotFound, gin.H{"error": "not found"})
	case errors.Is(err, errConflict):
		c.AbortWithStatusJSON(http.StatusConflict, gin.H{"error": "conflict"})
	default:
		// log err internally — client sees generic text
		c.AbortWithStatusJSON(http.StatusInternalServerError, gin.H{"error": "internal error"})
	}
}
```

Call:

```go
item, err := svc.Get(c.Request.Context(), id)
if err != nil {
	handleErr(c, err)
	return
}
c.JSON(http.StatusOK, item)
```

Note: **`c.Request.Context()`** — that is `context.Context` for cancellation/DB. Do not pass `*gin.Context` into the service layer.

### Recovery catches panic — panic is not an error strategy

`gin.Recovery` (built into `Default`, or explicitly in `New`) catches `panic` in the chain and typically returns 500. That is a **safety net**, not an API for “not found”.

```go
// BAD — do not learn this as control flow
if item == nil {
	panic("missing")
}
```

Correct: status + envelope + return. Panic remains for a **bug** (an unexpected nil dereference). In 07.08 you see CustomRecovery → JSON 500.

### Execution trace: success vs Abort

Chain: `[logger, auth, handler]`.

**Successful GET /items/1:**

```text
logger before → auth before (token OK, Next) → handler (JSON 200) → auth after → logger after
```

**Failure without token in auth:**

```text
logger before → auth (AbortWithStatusJSON 401; return; does NOT call Next)
→ handler does NOT run
→ logger after can still log status 401
```

**Handler forgets return after Abort:**

```text
handler: Abort 404, then still c.JSON(200, ...)  → broken / duplicate response
```

That is why `return` discipline is not an optional decoration.

### What happens inside c.JSON (conceptually)

When you call `c.JSON(code, obj)`:

1. Gin prepares the Writer and status line (`code`).
2. Sets JSON Content-Type (if not already “locked” by another write).
3. Serializes `obj` (`struct`, `gin.H`, slice, …) to bytes.
4. Writes the bytes to the response.

If `obj` is a type `encoding/json` cannot encode (e.g. channel, function), encode can fail — in practice that is a **bug in your DTO**, not an “HTTP domain error”. Keep response types simple: string, number, bool, slice, map, struct with exported fields.

**Zero value** in JSON: `""`, `0`, `false`, `null` for pointer/slice/map nil — the client sees them. If you do not want the field, `omitempty` on the tag or a pointer field. That is the response contract, the same mental model as in 07.04 for input.

### XML and String — when yes, when no

```go
type Book struct {
	Title string `xml:"title"`
}

c.XML(http.StatusOK, Book{Title: "Go"})
c.String(http.StatusOK, "ok")
c.String(http.StatusOK, "hello %s", user)
```

- **XML:** legacy integrations, SOAP-ish clients, old ERP. New mobile/SPA clients almost always JSON.
- **String:** probe (`/health` → `ok`), plain text report in the lab. A structured error in a JSON API still goes as a JSON envelope — do not mix a `text/plain` error with a JSON success path.

If the same endpoint sometimes returns JSON and sometimes String “because of a debug flag”, clients suffer. Stable Content-Type per route > flexibility.

### Status 401 vs 403 — the exact semantic boundary

| Code | Meaning | Example |
|------|---------|---------|
| 401 | “I don’t know who you are” / no valid credential | missing header, bad token |
| 403 | “I know who you are, you lack permission” | user role is not admin |

A wrong swap confuses security review and client retry: some clients on 401 clear the session and send to login; on 403 only show “forbidden”. Do not send 401 when the token is valid but the role is insufficient.

### Why not to leak a DB error

Example of bad text that must not go into JSON:

```text
pq: duplicate key value violates unique constraint "users_email_key"
```

An attacker sees the constraint and schema name. An operator sees enough in the **log** with a request ID. The client sees `{ "error": "conflict" }` and status 409. The same principle for timeout, connection refused, migration lock — all go to generic 500 + log, except when you have a **deliberate** domain `error` (`errConflict`) that you defined.

### Composite literal in the response

```go
c.JSON(http.StatusOK, gin.H{
	"id":   id,
	"name": name,
})

type ItemResp struct {
	ID   string `json:"id"`
	Name string `json:"name"`
}
c.JSON(http.StatusOK, ItemResp{ID: id, Name: name})
```

Both are **composite literal** patterns. `gin.H` is speed. `ItemResp` is a contract that tests assert by keys and that OpenAPI can describe. In a public API prefer the struct.

### Predict / Answer — scenario map

| Situation | Status | Body |
|-----------|--------|------|
| List empty but OK | 200 | `[]` or `{ "items": [] }` |
| ID does not exist | 404 | error envelope |
| Create success | 201 | resource (+ Location) |
| Delete success without body | 204 | empty |
| Binding fail | 400 | error envelope |
| No token | 401 | error envelope |
| Token OK, no role | 403 | error envelope |
| Unique email | 409 | error envelope |
| DB down (unexpected) | 500 | generic error; detail in log |

**Predict:** the client sends valid JSON, email already exists. Binding passes. What do you return?

**Answer:** 409 from the service/handleErr branch — not 400 (input shape was correct), not 200 with an error field.

## Rules and syntax

1. Use `http.Status*` constants instead of magic numbers.
2. One meaningful response per request; after Write/Abort → `return`.
3. `AbortWithStatusJSON` when the error must stop the rest of the chain.
4. 204 without body; 201 with resource and preferably `Location`.
5. Same error envelope everywhere; no 200+`error`.
6. Internal error → log + generic 500; no `err.Error()` from DB to the client.
7. `IndentedJSON` only locally/dev.
8. Headers (`Location`, later Cache-Control) **before** JSON.
9. Service takes `context.Context` via `c.Request.Context()`.
10. Do not use `panic` for expected HTTP outcomes; Recovery is a net, not a router.
11. `PureJSON` when you need JSON without HTML escape — deliberately.
12. `Redirect` rarely in a JSON API.

## Examples

### Example 1: Success, create, delete

```go
package main

import (
	"net/http"

	"github.com/gin-gonic/gin"
)

func getItem(c *gin.Context) {
	c.JSON(http.StatusOK, gin.H{"id": c.Param("id"), "name": "mug"})
}

func createItem(c *gin.Context) {
	id := "42"
	c.Header("Location", "/items/"+id)
	c.JSON(http.StatusCreated, gin.H{"id": id})
}

func deleteItem(c *gin.Context) {
	c.Status(http.StatusNoContent)
}

func main() {
	r := gin.New()
	r.Use(gin.Recovery())
	r.GET("/items/:id", getItem)
	r.POST("/items", createItem)
	r.DELETE("/items/:id", deleteItem)
	_ = r.Run(":8080")
}
```

#### What happens here

- GET → 200 + JSON resource.
- POST → 201 + `Location` **before** the body + JSON with `id`.
- DELETE → 204 without body — no second Write.
- Recovery is there for unexpected panic, not as part of “not found” logic.

### Example 2: Abort on auth and binding

```go
type CreateItem struct {
	Name string `json:"name" binding:"required,min=1"`
}

func create(c *gin.Context) {
	if c.GetHeader("X-Token") == "" {
		c.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{"error": "missing token"})
		return
	}
	var in CreateItem
	if err := c.ShouldBindJSON(&in); err != nil {
		c.AbortWithStatusJSON(http.StatusBadRequest, gin.H{"error": "invalid input"})
		return
	}
	c.JSON(http.StatusCreated, gin.H{"name": in.Name})
}
```

#### What happens here

Two early exit points: 401 and 400, each with Abort + return. Success is the only path to 201. **Predict:** if you omit `return` after 401, can binding and 201 still happen? **Answer:** yes — Abort does not erase the rest of **your** function; that is why return is mandatory.

### Example 3: handleErr + Request Context

```go
package main

import (
	"context"
	"errors"
	"log"
	"net/http"

	"github.com/gin-gonic/gin"
)

var (
	errNotFound = errors.New("not found")
	errConflict = errors.New("conflict")
)

type ItemService struct{}

func (ItemService) Get(ctx context.Context, id string) (map[string]string, error) {
	if id == "missing" {
		return nil, errNotFound
	}
	// in real code: DB with ctx
	_ = ctx
	return map[string]string{"id": id, "name": "mug"}, nil
}

func (ItemService) Create(ctx context.Context, name string) (string, error) {
	_ = ctx
	if name == "dup" {
		return "", errConflict
	}
	return "7", nil
}

func handleErr(c *gin.Context, err error) {
	switch {
	case errors.Is(err, errNotFound):
		c.AbortWithStatusJSON(http.StatusNotFound, gin.H{"error": "not found"})
	case errors.Is(err, errConflict):
		c.AbortWithStatusJSON(http.StatusConflict, gin.H{"error": "conflict"})
	default:
		log.Printf("internal: %v", err)
		c.AbortWithStatusJSON(http.StatusInternalServerError, gin.H{"error": "internal error"})
	}
}

func getHandler(svc ItemService) gin.HandlerFunc {
	return func(c *gin.Context) {
		item, err := svc.Get(c.Request.Context(), c.Param("id"))
		if err != nil {
			handleErr(c, err)
			return
		}
		c.JSON(http.StatusOK, item)
	}
}

func createHandler(svc ItemService) gin.HandlerFunc {
	return func(c *gin.Context) {
		var in struct {
			Name string `json:"name" binding:"required"`
		}
		if err := c.ShouldBindJSON(&in); err != nil {
			c.AbortWithStatusJSON(http.StatusBadRequest, gin.H{"error": "invalid input"})
			return
		}
		id, err := svc.Create(c.Request.Context(), in.Name)
		if err != nil {
			handleErr(c, err)
			return
		}
		c.Header("Location", "/items/"+id)
		c.JSON(http.StatusCreated, gin.H{"id": id})
	}
}
```

#### What happens here

The service speaks domain language (`errNotFound`), not HTTP. The handler maps via `errors.Is`. The default branch logs the real `error`, the client sees “internal error”. Context for Get/Create comes from Request — client cancellation can stop DB work. No panic for a missing id.

### Example 4: PureJSON vs IndentedJSON (dev)

```go
func demoEncoders(c *gin.Context) {
	mode := c.Query("mode")
	payload := gin.H{"expr": "x < y", "items": []int{1, 2}}
	switch mode {
	case "indent":
		// local debug only — not in the production contract
		c.IndentedJSON(http.StatusOK, payload)
	case "pure":
		c.PureJSON(http.StatusOK, payload)
	default:
		c.JSON(http.StatusOK, payload)
	}
}
```

#### What happens here

Three ways to the same status 200. `indent` is readable in the terminal, costlier in production. `pure` does not HTML-escape `<`. Default `JSON` is the safer default when you are unsure. In a real API do not pick the encoder by query — pick once in infrastructure.

### Example 5: Forbidden patterns (commented) and the fix

```go
func badPatternsDocumented(c *gin.Context, err error) {
	// BAD: c.JSON(200, gin.H{"error": "..."})
	// BAD: c.JSON(500, gin.H{"error": err.Error()})
	// BAD: panic(err)

	// GOOD:
	if err != nil {
		log.Printf("fail: %v", err)
		c.AbortWithStatusJSON(http.StatusInternalServerError, gin.H{"error": "internal error"})
		return
	}
	c.JSON(http.StatusOK, gin.H{"ok": true})
}
```

#### What happens here

The lesson explicitly names anti-patterns. Fix: status carries the error, envelope is stable, detail stays in the log. Panic is not a `switch` branch.

### Example 6: Same envelope on multiple routes

```go
func writeAPIError(c *gin.Context, code int, msg string) {
	c.AbortWithStatusJSON(code, gin.H{"error": msg})
}

func getUser(c *gin.Context) {
	id := c.Param("id")
	if id == "" {
		writeAPIError(c, http.StatusBadRequest, "invalid input")
		return
	}
	if id == "0" {
		writeAPIError(c, http.StatusNotFound, "not found")
		return
	}
	c.JSON(http.StatusOK, gin.H{"id": id})
}

func getOrder(c *gin.Context) {
	if c.GetHeader("X-Token") == "" {
		writeAPIError(c, http.StatusUnauthorized, "missing token")
		return
	}
	c.JSON(http.StatusOK, gin.H{"order": "1"})
}
```

#### What happens here

One function `writeAPIError` keeps the shape `{ "error": "..." }`. Routes only pick code and message. When tomorrow the envelope becomes `{ "error": { "code", "message" } }`, you change one place. Always Abort inside — the caller still does `return` after calling the helper (or document the helper as “terminal” and return from the helper call in the same branch line).

### Example 7: Empty list is not 404

```go
func listItems(c *gin.Context) {
	items := []gin.H{} // e.g. query result with no rows
	c.JSON(http.StatusOK, gin.H{"items": items})
}
```

#### What happens here

An empty collection is a successful query — **200** and `[]`, not 404. Reserve 404 for “this ID does not exist”, not for “the filter returned no rows”. Clients that treat 404 as “wrong navigation” would otherwise wrongly put the empty-state UI in the error branch.

## Decision analysis

| Decision | Choice | Why |
|----------|--------|-----|
| Error shape | one envelope | client one parser |
| Not found | 404 + Abort | semantic HTTP; stop chain |
| Create | 201 + Location | REST/HTTP contract; cache/clients |
| Delete | 204 or 200+body | team chooses; consistently |
| DB error | generic 500 | no leak |
| Indent JSON | only dev | performance / size |
| Control flow | status+return | not panic |
| Service API | `context.Context` | cancellation, no Gin dependency |

## Trade-offs

- **Generic 500 text** — safer; harder debug without logs/correlation (hence request ID in 07.06/07.07).
- **Rich error code in JSON** — better self-service; more contract to version.
- **204 on delete** — clean HTTP; some clients like a body confirmation.
- **PureJSON** — truer strings; less XSS protection if JSON is embedded in HTML.
- **Abort always** — safer for the chain; sometimes you want a “soft” error and continue (rare in a REST handler).
- **Struct vs gin.H** — struct = contract + tests; gin.H = demo writing speed.

## Common mistakes

1. **Wrong:** `c.JSON(200, gin.H{"error": "not found"})`.  
   **Effect:** monitors and clients see success.  
   **Fix:** 404 + error envelope + Abort/return.

2. **Wrong:** Abort without `return`.  
   **Effect:** another Write / business logic after the error.  
   **Fix:** always `return` immediately.

3. **Wrong:** `c.JSON(500, gin.H{"error": err.Error()})` with a DB error.  
   **Effect:** leaking internal details.  
   **Fix:** log + generic “internal error”.

4. **Wrong:** `IndentedJSON` in production.  
   **Effect:** larger responses, more CPU.  
   **Fix:** `c.JSON`.

5. **Wrong:** `panic("unauthorized")` instead of 401.  
   **Effect:** Recovery → 500; you lose the semantic status; bad signal.  
   **Fix:** `AbortWithStatusJSON(401, ...)`.

6. **Wrong:** `c.JSON` then only then `c.Header("Location", ...)`.  
   **Effect:** Location may not arrive.  
   **Fix:** Header before body.

7. **Wrong:** passing `*gin.Context` into the service / DB layer.  
   **Effect:** tight coupling, harder tests.  
   **Fix:** `c.Request.Context()` + domain types.

8. **Wrong:** two `c.JSON` in the same handler on both branches without return.  
   **Effect:** unpredictable response.  
   **Fix:** early return; one exit point per branch.

## Idiomatic Go

- `handleErr(c, err)` or a small `httpapi` package with `errors.Is` mapping.
- Response DTO as an **exported** struct with `json` tags; `gin.H` for short envelopes.
- Status constants from `net/http`.
- Test the matrix: 200/201/204/400/401/404/409/500 (more depth in 07.09).
- Do not export `*gin.Context` below the HTTP layer.
- A comment in code does not replace the contract — OpenAPI / README lists the envelope.

## Practical scenario

A team has a mobile client that shows a toast on every “error” in JSON, but the HTTP client library caches only based on status. Staging sends 200 + `{ "error": "not found" }` — cache and metrics lie “all OK”, while the UI shows an error. After changing to 404 + the same envelope, error-rate alarms start working, and the cache no longer holds “successful” not-found responses. At the same time they remove `err.Error()` from 500 responses — security review no longer finds SQL fragments in HAR files. `IndentedJSON` remains only behind `gin.IsDebugging()` for local `curl`.

## Check questions

1. What is `Abort` for in `AbortWithStatusJSON`?  
   **Answer:** marks that remaining handlers in the chain must not run; you still need `return` in the current function.

2. Why not 200 + an `error` field?  
   **Answer:** HTTP status lies about success; cache, metrics, and generic clients get it wrong.

3. How do you pass cancellation into the DB layer?  
   **Answer:** `c.Request.Context()` as `context.Context`.

4. When do you use `IndentedJSON`?  
   **Answer:** mostly local development / debug — not the production hot path.

5. What does Recovery do with a panic?  
   **Answer:** catches the panic and typically answers 500; not a substitute for domain status codes.

6. Which status for a unique conflict after successful binding?  
   **Answer:** 409.

7. Where does `Location` go relative to `c.JSON` on create?  
   **Answer:** `c.Header("Location", ...)` before `c.JSON(201, ...)`.

8. `gin.Context` vs `context.Context`?  
   **Answer:** the first is the Gin request API (Param, JSON, Abort); the second is the standard cancellation/value context for service/DB — you take it from Request.

9. 401 or 403 when the token is valid but the role is insufficient?  
   **Answer:** 403.

10. Empty result list — which status?  
    **Answer:** 200 with an empty array/object, not 404.

### Predict: double Write

```go
func h(c *gin.Context) {
	c.AbortWithStatusJSON(http.StatusNotFound, gin.H{"error": "missing"})
	c.JSON(http.StatusOK, gin.H{"ok": true})
}
```

What is the problem?

**Answer:** no `return` after Abort — the second `JSON` tries another response. Fix: `return` immediately after the Abort line.

### Predict: code map

The client sends a wrong type in a JSON field (`age` as a string). Binding fails. The service is not called.

**Answer:** 400 + envelope “invalid input”. Not 500. Not 409.

### Predict: leak

```go
row, err := db.QueryRowContext(c.Request.Context(), q, id).Scan(&name)
if err != nil {
	c.JSON(http.StatusInternalServerError, gin.H{"error": err.Error()})
	return
}
```

What is wrong and how to fix it?

**Answer:** `err.Error()` can leak driver/SQL details. Fix: `errors.Is` on `sql.ErrNoRows` → 404; otherwise log + generic 500. And better AbortWithStatusJSON for chain consistency.

### Mini checklist before merging a route

- [ ] Status code matches semantics (not 200 for an error)
- [ ] One Write path per branch + return
- [ ] Envelope same as on other routes
- [ ] No `err.Error()` from the infra layer in JSON
- [ ] Create: 201 and Location if the contract requires it
- [ ] Delete: 204 **or** agreed 200+body — consistently
- [ ] No panic for expected outcomes
- [ ] Service called with `c.Request.Context()`

## Summary

- `c.JSON` / `XML` / `String` / `Status` build the response; `AbortWithStatusJSON` + `return` stop the chain with a JSON error.
- One meaningful response per request; header before body; 201+Location; 204 without body.
- Consistent error envelope; status map 200/201/204/400/401/403/404/409/500; no 200+error; no DB leak.
- `IndentedJSON` for dev; `PureJSON` deliberately; Redirect rarely in a JSON API.
- `handleErr` + `errors.Is`; service on `c.Request.Context()`; panic is not a control-flow strategy.
