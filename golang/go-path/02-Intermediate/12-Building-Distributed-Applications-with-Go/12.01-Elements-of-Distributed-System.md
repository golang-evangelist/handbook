# 12.01 Elements of a distributed system in Go

> **Go Path - Zero to Gopher** / **02 Intermediate → Building Distributed Applications with Go** / Lesson 12.01

## Lesson goals

After this lesson you should:

- accept **partial failure** (part of the system works, part does not) as the normal state, not an exception;
- design a **timeout** on every network boundary and share the time budget downstream;
- build **idempotent** operations where repeating the same request does no harm;
- understand why there is **no shared memory** between processes — only messages, disk, and an external store;
- set the vocabulary for registration, discovery, and health probes (12.02–12.04);
- distinguish error classes (`context.Canceled`, `context.DeadlineExceeded`, transport) in metrics;
- apply bulkhead and backpressure across the network, not only inside one process.

## Prerequisite

- HTTP client and server in Go (09.xx).
- `context` and timeout (08.xx): `WithTimeout`, `WithDeadline`, cancellation.
- Basic feel for the network: DNS, TCP, latency, packet loss.
- Concurrent tools: `sync.Mutex`, `errgroup`, channel (for aggregation), WaitGroup as needed.
- Errors as values: `errors.Is`, wrap with `%w` (13.xx will go deeper).

## Problem this lesson solves

Code that works in one process (“call a function, get a result”) breaks as soon as you cross a process boundary:

- the other side is alive but slow — your handler holds a goroutine and a connection;
- the response was sent, but the ACK never arrived — the client retries and duplicates the effect;
- half the nodes see a third, half do not (network partition);
- a local `sync.Mutex` “protects” a map, and another pod cannot see it at all.

Without a partial-failure model, teams add “retry forever”, remove timeouts “because otherwise it fails”, and create stampedes. This lesson sets principles **before** registries and health routes: what must hold in an engineer’s head, and only then an HTTP registry.

## Mental model

A distributed system = multiple processes that **do not share RAM**. Communication goes over the network (HTTP, gRPC, message queue). Consequences you must internalize:

1. **Partial failure** — some nodes or jobs fail while others keep working.
2. **Uncertainty** — timeout ≠ reliable proof that the work was not done.
3. **Time is local** — clocks diverge; do not rely on a synchronized wall clock for exact order without agreement (Lamport, store version, DB transaction).
4. **Idempotency** — the same request twice yields the same effect (or a safe no-op).
5. **Boundary = contract** — timeout, status code, schema, retry policy are part of the API, not an “ops detail”.

Go gives you good tools (`context`, `net/http`, `errgroup`), but it does not solve network physics. Tools lower the cost of discipline; the discipline remains yours.

```text
        ┌──────────┐         network        ┌──────────┐
  UI ──►│ checkout │───────────────────────►│  orders  │
        │  :8080   │◄──── timeout/retry ────│  :8081   │
        └────┬─────┘                        └────┬─────┘
             │                                   │
             ▼                                   ▼
        external store (DB/Redis) — the only “shared memory”
```

## Mechanism

This is the heart of the lesson. Read more slowly. Each subsection is a decision you will repeat in 12.02–12.04 and in production.

### Partial failure as the default state

In a monolithic process, “half the function failed” is rare: either panic, or a returned `error`, or everything OK. In a cluster of 20 pods, at any moment something is likely broken: one pod in a crash loop, one AZ slower, one disk full, DNS cache stale.

Three outcomes of every network call:

| Outcome | What you know | What you do not know |
|-------|----------|-------------|
| Success (2xx + body) | Effect (probably) done | Whether this is an idempotent replay |
| Clear error (4xx/5xx/connect refused) | Often “not done” | Sometimes it was done and the response was lost |
| Timeout / cancel | Nothing reliable | Whether the work finished on the server |

Design reads/writes with that three-way logic. Especially writes: assume a timeout can mean “the charge went through”.

### Timeout: a boundary, not decoration

Timeout is not “I’ll add it when I get to it”. It is part of the contract with the user and with the platform.

**Client:**

- `context.WithTimeout` / `WithDeadline` — cancels the request and signals downstream if they honor `Request.Context()`.
- `http.Client{Timeout: ...}` — covers the whole transfer (connect + headers + body). Understand the difference: Client.Timeout is a wall; context is cancellable and inheritable.

**Server:**

- middleware timeout / `http.TimeoutHandler` / `ReadHeaderTimeout`, `WriteTimeout` on `http.Server`;
- the handler takes `r.Context()` and does not start heavy work after cancel without checking.

**Chain:**

The time budget is **shared** downstream. If the user has an 800 ms end-to-end SLO, you must not give every dependency 800 ms.

```text
total 800 ms
├── auth lookup     ≤ 150 ms
├── inventory       ≤ 300 ms
└── pricing         ≤ remainder (but ≤ 300 ms hard cap)
```

A child `context` cannot extend the parent. If the parent expires in 200 ms, a child with `WithTimeout(1*time.Second)` still dies in 200 ms. That is intentional.

### Idempotency: a correctness condition with retry

The network and clients often give *at-least-once* delivery when there is retry. So idempotency is not “nice to have” — it is a correctness condition when you repeat.

- `GET`/`PUT` with a known ID are often naturally idempotent.
- `POST /charge` without a key — dangerous on retry.
- Solution: `Idempotency-Key` header, or a natural operation key + unique constraint in the DB.
- Outbox + dedup table when you cannot make the effect idempotent at the source.

Without idempotency you choose between: (a) no retry → worse availability, (b) retry → risk of duplicate effect. That is not a technical detail — it is a product decision.

### No shared memory between processes

An in-process cache on one pod is not visible to another. A `sync.Mutex` in process A does not protect process B. A session in memory on pod-1 disappears when the LB sends the next request to pod-2.

Consequences:

- shared state → external store (DB, Redis, object storage);
- per-process cache OK with TTL + singleflight + awareness that invalidation is not global;
- sticky session is a compromise, not a substitute for an external store.

### Backpressure and bulkhead across the network

When a downstream service slows, your process must not open infinite goroutines or connections. Limits (`errgroup.SetLimit`, semaphore via buffered channel, `http.Transport.MaxConnsPerHost`) are a **bulkhead** (*partition* — a failure in one section does not sink the whole ship).

The same discipline as in concurrency lessons, now with network SLOs: if inventory hangs, checkout must still respond (503, degradation, or partial response) instead of consuming all goroutines.

### At-least-once, at-most-once, exactly-once (what you actually have)

| Semantics | Reality in HTTP + retry |
|-----------|-------------------------|
| at-most-once | No retry; you can lose the request |
| at-least-once | Retry without protection; you can duplicate |
| exactly-once | Illusion on a single hop; achieved with an idempotent handler + dedup |

In Go HTTP services aim for: **at-least-once delivery + idempotent handler**. That is the industrial default that works.

### Observability as part of the mechanism

Timeout and idempotency without a correlation ID hurt at 3 a.m. Pass `X-Request-ID` or W3C `traceparent` across boundaries. Separate metrics:

- `context.Canceled` — client gave up (often not “your” 5xx business);
- `context.DeadlineExceeded` — your budget expired;
- transport / downstream 5xx — another story.

Without separation, “everything is error” and you do not know whether to raise the timeout or fix a bug.

### Partial success in aggregators

When checkout calls A and B in parallel:

- **all or nothing** (`errgroup.WithContext`) — one fail cancels the other; simpler reasoning;
- **partial success** — show A, hide B or return 207 / JSON with error fields; better UX, more complex client.

The decision is a product one. The mechanism only says: be explicit; do not mix two modes in the same handler without documentation.

### Deadlines, clocks, and order

Do not use `time.Now()` on two nodes to prove “who was first”. For order use:

- a version in the store / optimistic locking;
- a DB transaction or unique insert;
- a monotonic counter in one authoritative store.

Wall clock is for humans and SLOs, not for distributed consensus in your app logic (unless you consciously use NTP-tolerant protocols — out of scope for this lesson).

### Retry with jitter (rules, not a library)

Retry without jitter synchronizes clients and creates a thundering herd. Minimal discipline:

1. Retry only idempotent or explicitly safe operations.
2. Max attempts small (1–2 on the business path; more on background).
3. Exponential backoff + jitter.
4. Honor the overall `context` budget — retry must not exceed it.
5. Do not retry 4xx (except 408/429 with `Retry-After` by policy).

### What registry and health have to do with this

Registry (12.02) and discovery (12.03) exist because instances come and go — that **is** partial failure. Health (12.04) exists so the platform does not send traffic to half-ready pods and does not restart pods because of a slow DB Ping. Without the principles from this lesson, registry becomes magic; with them — just another HTTP contract with TTL and timeout.

### Defensive defaults in Go

- Shared `http.Client` with a configured `Transport` (pool, TLS, `MaxIdleConns`).
- Limit body reads: `io.LimitReader` — do not trust an infinite stream.
- Explicit `StatusCode` check — `Do` does not return `error` for 500.
- `defer res.Body.Close()` always after a successful `Do`.
- Do not log PII in traces; log `request_id`, service, latency, error class.

### Mapping to Kubernetes / cloud (without a vendor lock-in mental model)

| Term here | Typical equivalent |
|------------|-------------------|
| Instance URL | Pod IP + port / Endpoint |
| Registry list | Endpoints / Service |
| Timeout budget | Istio/timeout policy or app context |
| Idempotency-Key | App + DB unique |
| Liveness/readiness | Probe (12.04) |

The course builds a small HTTP registry so you feel the contract. In production you often replace the registry with the platform — the principles remain.

### Mechanism checklist (memorize)

1. Every exit from the process has a timeout.
2. Timeout is not proof of “not done”.
3. Retry only with idempotency or a clear policy.
4. No shared RAM truth between pods.
5. Budget is shared downstream.
6. Bulkhead prevents one dependency from sinking the process.
7. Metrics separate cancel / deadline / other.
8. Correlation ID crosses boundaries.

If you can recite these eight points without looking, you are ready for registries.

### Fail closed vs fail open (product axis)

When a critical dependency is silent, you have two families of responses:

- **Fail closed** — reject the request (503/504). Safer for charging, reservation, auth.
- **Fail open** — pass or degrade (cache, default price). Sometimes OK for personalization; dangerous for money.

The mechanism does not choose for you. It requires the choice to be **explicit** in code and in the runbook. “No response so assume success” is fail open without documentation — that is a bug.

### Hedging (read-only, only consciously)

*Hedged request*: send the same idempotent GET to two instances, take the faster, cancel the other via `context`. Reduces tail latency; **increases** load. Never hedge on `POST /charge`. In this course it is enough to know it exists and that it requires the same budget and cancel discipline as a normal call.

### Circuit mental model (without a library)

When a dependency is 100% down, retry feeds it. A simple app-level circuit:

1. counter of consecutive failures;
2. after a threshold — briefly “open” (immediate 503);
3. after cool-down — one probe request;
4. success → close the circuit.

This is not an attack on the system — it is **protection of your own** process and of the downstream that is recovering. In Go often `atomic` + timer; libraries exist, but you must understand the concept before you add a dependency.

### What “valid Go” means at the boundary

- Check every `error` from the network.
- Do not panic because of a timeout.
- Do not share `Response.Body` between goroutines without control.
- Honor `ctx.Done()` in loops that wait.
- Zero value for `http.Client` “works” but without Timeout — set it explicitly.

### Decision diagram: I got a timeout

```text
timeout on write path?
├── yes → assume uncertainty
│         ├── has Idempotency-Key? → safe retry same key
│         └── no → do not retry automatically; compensation / manual replay
└── no (read) → retry with backoff + another instance (12.03)
```

This diagram is a bridge to registration: without fresh URLs, retry hits the same dead pod.

### SLO, latency, and the “average” trap

Average latency lies. Watch P95/P99. A timeout set to “2× average” often cuts healthy P99 requests under load and creates false errors — which retry then amplifies.

Practically:

1. Measure P99 to the dependency in quiet and peak modes.
2. Set timeout above P99 + margin, but within the user SLO.
3. If it does not fit — reduce work (cache, less fan-out), not just “raise timeout to 30 s”.

### Example — Client with explicit Transport

**Predict the result:** Why does a shared Client with Transport beat `http.Get` in a loop?

```go
func NewHTTPClient() *http.Client {
	return &http.Client{
		Timeout: 5 * time.Second,
		Transport: &http.Transport{
			MaxIdleConns:        100,
			MaxIdleConnsPerHost: 20,
			IdleConnTimeout:     90 * time.Second,
		},
	}
}
```

#### What happens here

`NewHTTPClient` returns one `*http.Client` whose `Timeout` is five seconds for the whole exchange. The `Transport` keeps up to 100 idle connections, at most 20 per host, and drops an idle connection after 90 seconds. Callers that share this client reuse that pool.

**Answer:** Connection pool, one place for Timeout policy, less TIME_WAIT chaos. `http.Get` uses the shared default Client without your Timeout — easy to “hang”.

### Example — wrap errors with context

**Predict the result:** How does an operator distinguish a timeout to `users` from a timeout to `orders`?

```go
body, err := fetchUser(ctx, client, base, id)
if err != nil {
	return fmt.Errorf("checkout: users %s: %w", id, err)
}
```

#### What happens here

When `fetchUser` returns a non-nil error, `fmt.Errorf` prefixes it with `checkout: users` and the id. The `%w` verb wraps the original error, so `errors.Is` and `errors.As` still match it. A nil `err` continues after the `if`.

**Answer:** The wrap message carries the layer and dependency; `errors.Is(err, context.DeadlineExceeded)` still works with `%w`. In the log you see the chain.

### Thought exercise: three nodes, one slow

A calls B and C. B P99 = 50 ms, C occasionally 2 s. SLO A = 500 ms. Without a budget A often fails on C. With a budget: C timeout 200 ms, partial success or 503 with a clear field. Which decision is “correct” depends on the product — the mechanism requires it to be **conscious**.

## Rules and syntax

```go
ctx, cancel := context.WithTimeout(parent, 300*time.Millisecond)
defer cancel()
req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
if err != nil {
	return err
}
res, err := client.Do(req)
if err != nil {
	return err
}
defer res.Body.Close()
```

Rules you keep in PR review:

1. Every exit from the process has a timeout (context and/or Client).
2. Retry only with jitter and only on idempotent / explicitly safe operations.
3. Log `request_id` / `trace_id` across boundaries.
4. Do not treat “no response” as “no effect”.
5. Check `res.StatusCode` — `err == nil` is not enough.
6. Limit reading the response (`LimitReader`).
7. Shared `http.Client`, not `http.Get` in a loop (loses pool discipline).
8. Document method idempotency in OpenAPI / README.

## Examples

### Example 1 — Timeout on the client

**Predict the result:** If the `users` service hangs for 2 s, and this call has a 400 ms timeout, what does the caller see and what happens to resources?

```go
func fetchUser(ctx context.Context, client *http.Client, base, id string) ([]byte, error) {
	ctx, cancel := context.WithTimeout(ctx, 400*time.Millisecond)
	defer cancel()
	req, err := http.NewRequestWithContext(ctx, http.MethodGet, base+"/users/"+id, nil)
	if err != nil {
		return nil, err
	}
	res, err := client.Do(req)
	if err != nil {
		return nil, err
	}
	defer res.Body.Close()
	if res.StatusCode != http.StatusOK {
		return nil, fmt.Errorf("users: status %d", res.StatusCode)
	}
	return io.ReadAll(io.LimitReader(res.Body, 1<<20))
}
```

#### What happens here

`fetchUser` derives a 400-millisecond timeout from the caller context and cancels it on return. The GET is built with `NewRequestWithContext`, so that deadline cancels `client.Do`. A status other than 200 becomes an error. On the success path the body is closed and read through a limit of `1<<20` bytes.

**Answer:** The caller gets an error (usually tied to `context.DeadlineExceeded`) within ≤400 ms. Without a timeout, the goroutine and TCP connection stay busy until the server answers or some other limit breaks — that is how one slow dependency “eats” a worker pool.

### Example 2 — Partial failure in an aggregator (fail-fast)

**Predict the result:** If `a` fails immediately, and `b` would take 300 ms, does `b` get to finish when you use `errgroup.WithContext`?

```go
type partial struct {
	A   []byte
	B   []byte
	Err error
}

func aggregateFailFast(ctx context.Context, a, b func(context.Context) ([]byte, error)) partial {
	g, ctx := errgroup.WithContext(ctx)
	var out partial
	g.Go(func() error {
		var err error
		out.A, err = a(ctx)
		return err
	})
	g.Go(func() error {
		var err error
		out.B, err = b(ctx)
		return err
	})
	out.Err = g.Wait()
	return out
}
```

#### What happens here

`errgroup.WithContext` supplies a context that is cancelled when one of the group functions returns an error. One goroutine stores the bytes from `a` in `out.A`, and the other stores the bytes from `b` in `out.B`. `g.Wait` waits for both and assigns the first error to `out.Err`. The function `b` ends early only if it observes the cancelled context.

**Answer:** Not reliably — cancel of the parent `context` sends a signal and `b` should honor `ctx.Done()`. You get a faster fail and less wasted time, but not partial UX. For “show A, hide B” you do not use this pattern.

### Example 3 — Partial success (without mutual cancellation)

**Predict the result:** How do you collect errors separately so that success of `a` survives failure of `b`?

```go
func aggregatePartial(ctx context.Context, a, b func(context.Context) ([]byte, error)) partial {
	var out partial
	var wg sync.WaitGroup
	var mu sync.Mutex
	wg.Add(2)
	go func() {
		defer wg.Done()
		v, err := a(ctx)
		mu.Lock()
		out.A = v
		if err != nil {
			out.Err = errors.Join(out.Err, fmt.Errorf("a: %w", err))
		}
		mu.Unlock()
	}()
	go func() {
		defer wg.Done()
		v, err := b(ctx)
		mu.Lock()
		out.B = v
		if err != nil {
			out.Err = errors.Join(out.Err, fmt.Errorf("b: %w", err))
		}
		mu.Unlock()
	}()
	wg.Wait()
	return out
}
```

#### What happens here

A `WaitGroup` waits until the `a` goroutine and the `b` goroutine have both finished. Each one calls its function, then under `mu` stores the bytes and joins a labeled error into `out.Err` when the call failed. The parent `ctx` is the one the caller passed in. After `Wait`, `out` holds each side's bytes together with any joined errors.

**Answer:** Each branch keeps its own result; `errors.Join` aggregates errors. The handler can return 200 with a partial body or 207 — a product decision. You must still honor the parent timeout.

### Example 4 — Idempotency-Key with unique constraint

**Predict the result:** Two parallel retries with the same key — can it charge twice if Insert goes through unique?

```go
func (s *Service) Charge(ctx context.Context, key string, amount int) (Payment, error) {
	p, err := s.Store.GetByKey(ctx, key)
	if err == nil {
		return p, nil // already processed
	}
	if !errors.Is(err, ErrNotFound) {
		return Payment{}, err
	}
	p, err = s.psp.Charge(ctx, amount)
	if err != nil {
		return Payment{}, err
	}
	if err := s.Store.InsertKey(ctx, key, p); err != nil {
		// unique conflict → read existing
		return s.Store.GetByKey(ctx, key)
	}
	return p, nil
}
```

#### What happens here

`GetByKey` returns the stored payment when the key is already present. Any lookup error other than `ErrNotFound` is returned at once. On `ErrNotFound` the method calls `s.psp.Charge` and then `InsertKey`. An error from `InsertKey` makes the method return a second `GetByKey` for the same key. A nil insert error returns the payment from the charge.

**Answer:** The unique constraint is the last line of defense. There is still a race PSP vs Insert — in a real system often: reserve the key (pending) before PSP, then update to settled; or the PSP itself accepts an idempotency key. The teaching example shows the *idea*: same key → same Payment.

### Example 5 — Per-process cache is not global

**Predict the result:** On 10 pods, after `Store` on one, how many caches does the cluster see?

```go
var local sync.Map // lives only in this process

func (s *Svc) Get(ctx context.Context, id string) (Item, error) {
	if v, ok := local.Load(id); ok {
		return v.(Item), nil
	}
	it, err := s.remote.Get(ctx, id)
	if err != nil {
		return Item{}, err
	}
	local.Store(id, it)
	return it, nil
}
```

#### What happens here

`local` is a package-level `sync.Map`, so the entries live in this process. `Get` returns the cached `Item` when `Load` finds the id. A miss calls `s.remote.Get`, stores the item, and returns it. A remote error returns the zero `Item` and leaves the map unchanged.

**Answer:** Ten caches. Invalidation must go via events, TTL, or an external cache. `sync.Mutex` does not help other pods. That is “no shared memory”.

### Example 6 — Deadline budget in a handler

**Predict the result:** If A spends 280 ms of an 800 ms budget, what timeout may B get?

```go
func handler(w http.ResponseWriter, r *http.Request) {
	deadline := time.Now().Add(800 * time.Millisecond)
	ctx, cancel := context.WithDeadline(r.Context(), deadline)
	defer cancel()

	aCtx, aCancel := context.WithTimeout(ctx, 300*time.Millisecond)
	defer aCancel()
	// call A with aCtx...

	remain := time.Until(deadline)
	if remain <= 0 {
		http.Error(w, "timeout", http.StatusGatewayTimeout)
		return
	}
	bCtx, bCancel := context.WithTimeout(ctx, remain)
	defer bCancel()
	// call B with bCtx...
	_ = bCtx
}
```

#### What happens here

The handler sets `deadline` to 800 milliseconds after `time.Now()` and binds that instant to the request context with `WithDeadline`. `aCtx` is a child timeout of 300 milliseconds. `remain` is `time.Until(deadline)`. At zero or below, the handler writes status 504. Otherwise `bCtx` is a child of `ctx` whose timeout is `remain`.

**Answer:** B gets the remainder (≈520 ms here, minus overhead), but no more than the parent deadline. This prevents “3 × 1s timeout = 3s” in a handler that has an 800 ms SLO.

### Example 7 — Distinguish error classes

**Predict the result:** Why should `errors.Is(err, context.Canceled)` not increment the same counter as timeout?

```go
func classify(err error) string {
	switch {
	case errors.Is(err, context.Canceled):
		return "canceled"
	case errors.Is(err, context.DeadlineExceeded):
		return "deadline"
	default:
		return "other"
	}
}
```

#### What happens here

`errors.Is` matches a target error through wrapping. `context.Canceled` classifies as `"canceled"`. `context.DeadlineExceeded` classifies as `"deadline"`, and every other value classifies as `"other"`.

**Answer:** Cancel often means the client left; deadline means your budget is short or the dependency is slow. Mixing hides the root cause on the dashboard.

### Example 8 — Bulkhead with a semaphore (channel)

**Predict the result:** What happens when 100 parallel calls arrive and the semaphore has capacity 8?

```go
type Gate struct {
	sem chan struct{}
}

func NewGate(n int) *Gate {
	return &Gate{sem: make(chan struct{}, n)}
}

func (g *Gate) Do(ctx context.Context, fn func(context.Context) error) error {
	select {
	case g.sem <- struct{}{}:
		defer func() { <-g.sem }()
		return fn(ctx)
	case <-ctx.Done():
		return ctx.Err()
	}
}
```

#### What happens here

`NewGate` makes a channel buffer of capacity `n`, one permit per slot. `Do` uses `select` to send an empty struct into that buffer, or to return `ctx.Err()` when the context is done and that send is not taken. The deferred receive returns the permit after `fn` returns. While those permits are held, at most `n` calls of `fn` run together.

**Answer:** At most 8 enter `fn` at once; the rest wait for a slot or the inherited timeout. A slow dependency does not open 100 goroutines to it from this gate (the caller can still make more Gate.Do — that is why the gate lives at the dependency boundary).

## Decision analysis

| Decision | Why |
|--------|--------|
| Timeout everywhere | Prevents infinite waiting and goroutine leaks |
| Idempotent write path | Safe retry with at-least-once |
| Explicit partial success | Better UX than “all or nothing” when the product asks for it |
| External store for shared state | Multiple processes, one truth |
| Trace / request ID | Debug across boundaries under partial failure |
| Bulkhead limit | One dependency does not sink the process |
| Separated error metrics | Correct operational response |
| Short LimitReader | Defense against huge bodies |

## Trade-offs

- **Short timeout** — faster fail, more false errors under load and cold start.
- **Long timeout** — fewer false ones, longer hold on goroutines, connections, and memory.
- **Retry** — better resilience, risk of amplifying load (stampede) and duplicate effects.
- **Strong consistency** — simpler reasoning, higher latency / lower availability.
- **Per-process cache** — speed, complex invalidation, divergence between pods.
- **Fail-fast aggregation** — less wasted work, stricter UX.
- **Partial success** — better UX, harder contract and tests.
- **Exact exactly-once dream** — expensive; idempotency + dedup is more pragmatic.

## Common mistakes

1. Retry on `POST /pay` without a key.
2. No timeout on `http.Client` (default can hang a long time).
3. Believing that timeout means “not done”.
4. In-memory session on multiple pods without sticky/store.
5. Chain of timeouts larger than the user SLO.
6. Flooding logs without a correlation id.
7. `http.Get` / new Client per request — loses connection pool.
8. Ignoring `StatusCode` after `Do`.
9. Retry without jitter → synchronous stampede.
10. Liveness mixed with deep health (will be in 12.04, but the root is here: wrong reaction to partial failure).

## Idiomatic Go

- `context.Context` as the first argument across package boundaries.
- Shared `*http.Client` with a configured `Transport`.
- Error semantics: `errors.Is` for `Canceled` / `DeadlineExceeded`.
- Document API method idempotency (comment + OpenAPI).
- `errgroup` for fail-fast; WaitGroup + Join for partial success.
- Buffered channel as a semaphore for bulkhead when you do not want an external library.
- Test the timeout path with a short `WithTimeout` and a fake slow server (`httptest` + `time.Sleep`).

## Practical scenario

Checkout calls payment. The PSP sometimes answers in 2 s, client timeout 1 s, the mobile app retries. Users get a double charge. The incident looks like “the network is to blame”, and the root is: **no Idempotency-Key**, timeout not aligned with the UI, retry treats timeout as “surely not charged”.

Fix:

1. Client sends a stable Idempotency-Key per payment attempt.
2. Unique in DB / PSP accepts the same key.
3. Timeout budget aligned: UI 3 s, checkout 2.5 s, PSP call 2 s — or UI waits longer with a clear spinner.
4. Retry only on transport errors with the **same** key.
5. Metric `payment_duplicate_key_hit` so you see the protection working.

Partial failure is no longer “unknown magic” — it has a procedure.

## Check questions

1. **What is partial failure?**  
   Part of the system does not work or does not respond while the rest works.

2. **Why is timeout not proof of operation failure?**  
   The work may have finished, and the response was lost or is later than the budget.

3. **What is idempotency for?**  
   Safe repetition of the same request without a duplicate effect.

4. **What does no shared memory mean?**  
   Processes do not share RAM; state goes over the network or an external store.

5. **Why a deadline budget?**  
   So the sum of downstream waits does not exceed the SLO.

6. **What is a bulkhead here?**  
   A limit on parallel work to one dependency so it does not sink the whole process.

7. **At-least-once + what = practical exactly-once effect?**  
   An idempotent handler (and a dedup key).

## Quick check before production

- Are errors explicitly checked at boundaries?
- Do tests cover error and timeout paths?
- Does the client see only public messages?
- Does fail closed apply when a critical dependency is unavailable?
- Does the retry policy mention idempotency?
- Does every outbound call have a timeout and body limit?

Keep these checks in the PR checklist. Reliable error handling and timeout discipline are not decoration — they are part of the service’s contract with the user and with the operator.

## Link to observability

When partial failure hits, you need one story across multiple services. Minimal set:

- `request_id` in the log of every boundary;
- latency per dependency (histogram);
- counters by error class;
- sample of slow requests (not everything at debug level).

Without that, in 12.02–12.04 you will “fix the registry” while the problem is budget or duplicate write.

## Anti-pattern gallery (short)

| Anti-pattern | Why it hurts | Fix |
|--------------|------------|----------|
| `res, _ := client.Do(req)` | Silent fail | Check `err` and status |
| Timeout only on Client, never context | Hard to cancel the chain | Both, consciously |
| Retry on every error | Duplicate write, stampede | Classify + idempotency |
| Global mutable cache without TTL | Stale forever | TTL + invalidation |
| One 30s timeout “for everything” | Bad UX, holding resources | Budget by SLO |
| Panic on timeout | Crashes the process because of the network | Return `error` |

## Summary

Distributed Go is not “more goroutines” — it is network, uncertainty, and timeout and idempotency discipline. There is no shared memory between processes. Bulkhead and clear metrics keep the process alive while parts of the environment fail. With those principles we enter service registration.
