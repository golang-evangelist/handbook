# 12.03 Service discovery: lookup and simple instance choice

> **Go Path - Zero to Gopher** / **02 Intermediate → Building Distributed Applications with Go** / Lesson 12.03

## Lesson goals

After this lesson you should:

- find **healthy (fresh) instances** via registry `GET /services/{name}`;
- apply simple **load choice** (*instance selection* — random or round-robin);
- cache the list briefly while respecting timeouts and TTL from 12.02;
- connect discovery with an HTTP client and cautious retry on a **different** instance;
- know the limits of a tutorial registry versus platform discovery (K8s Service, DNS);
- return 503 when nobody is available — fail closed, not an infinite hang;
- measure `discovery_empty`, retry, and choice distribution.

## Prerequisite

- 12.01–12.02 (timeout, TTL, ListFresh semantics).
- HTTP client with `context`, JSON decode.
- `sync.Mutex` / `atomic.Uint64` for cache and round-robin.
- Optionally `errgroup` — not required here.

## Problem this lesson solves

The client must not hold one hardcoded URL forever. Deploy kills that pod — a wave of 5xx. Discovery returns a set; load choice picks one; on transport error you can try another and invalidate the cache.

Without that, everyone hits a dead instance until TTL expires (or forever if there is no registry). This lesson combines **lookup + choice + short cache + one retry** into a tutorial pattern — not a full service mesh.

## Mental model

```text
client → resolve(service) → [url1, url2, url3]
       → pick(urls) → url2
       → HTTP call (timeout from 12.01)
       → on fail → without(id) / Invalidate → pick next
       → empty → 503
```

“Healthy” here means “registry says fresh (TTL)”. Deeper health (readiness probe) is 12.04. Do not mix them: the list from the registry **does not prove** that `/readyz` is 200 right now — that is why retry and short cache + invalidation exist.

## Mechanism

### Lookup

`GET http://registry:8500/services/orders` → JSON array of instances (`id`, `url`, optionally `meta`).

- Short timeout on lookup (e.g. 200–500 ms) — discovery must not eat the SLO.
- Non-200 → error; empty array → no healthy instances (caller 503).
- Decode into `[]Inst`; prefer empty slice over `nil` for stable JSON on the server side (12.02).

### Load choice

| Strategy | Advantage | Drawback |
|------------|----------|------|
| **Random** | Simple, good long-term distribution | Short-term batches can be less even |
| **Round-robin** | Fairer short-term | Needs atomic index; jump after length change |
| **Power of two choices** | Better with load metrics | Outside tutorial scope |

For the lab and most internal clients random or RR is enough. Do not build consistent hashing until you have proof you need it.

### List cache

Cache for 1–5 s so you do not hit the registry on every request. Rules:

1. Cache **shorter** than instance TTL (otherwise you call dead ones longer than the registry).
2. After transport fail — `Invalidate(service)`.
3. Copy the slice when returning if the caller mutates the list (`without`).
4. Do not hold the cache under lock while doing network Lookup — lock, check, unlock, fetch, lock, store.

### Retry on a second instance

- Max small (1 retry = 2 attempts total on the business path).
- Remove failed `id` from the local attempt (`without`).
- Invalidate cache.
- Respect parent `context` budget — the second attempt must not override it.
- Only for idempotent / safe operations (12.01). Write without a key → no magic retry.

### 503 when empty

Explicit 503 is better than timeout to an old hardcoded host. LB and client can react. Metric `discovery_empty` is a page-worthy signal.

### Client-side discovery vs sidecar/proxy

| Model | Who picks URL |
|-------|-------------|
| Client-side (this lesson) | Your Go code |
| K8s Service ClusterIP | iptables/IPVS / kube-proxy |
| Sidecar (Envoy) | Proxy beside pod |

Same concepts: endpoint set, health, timeout. When you move to DNS `orders.default.svc`, the pick/retry layer simplifies but timeout/idempotency remain.

### Hedging and sticky (optional, deliberate)

- **Hedging**: same GET to two instances, faster wins, cancel the other. Idempotent reads only; increases load.
- **Sticky**: same session → same pod. Useful for local cache; bad when the pod dies — discovery + retry must survive losing the sticky target.

### Thread-safety

- `atomic.Uint64` for RR index.
- `rand.IntN` (Go 1.22+) OK without manual `Rand` + Mutex.
- Cache map under `Mutex`; do not share the same backing array slice between requests if one does `without` in-place — hence a new slice.

### Respect registry TTL

If you cache 30 s and instance TTL is 15 s, you call dead ones longer. Keep cache shorter than TTL, or invalidate aggressively on error. A common mistake for first discovery clients.

### Metrics

- `discovery_empty` — no instances
- `discovery_refresh` — how often lookup runs
- `discovery_error` — registry down / bad status
- `upstream_retry` — how many times you changed URL
- `upstream_selected{id=}` — distribution (to see RR working)

### Defensive

- Timeout on lookup and business call.
- Limit decode size of registry response.
- No infinite retry.
- Log chosen `id`/`url` with `request_id`.
- Fail closed on empty list for critical paths.

### GetOrder algorithm (tutorial)

```text
list = LookupCached(service)
if list empty → error/503
try = 0
while try < maxAttempts and list not empty:
  inst = Pick(list)
  result, err = do(inst.URL)
  if err == nil → return result
  list = without(list, inst.ID)
  Invalidate(service)
  try++
return lastErr
```

This is not a resilience framework — a clear pattern you can swap for a library later without changing the mental model.

### What discovery is not

- Not a replacement for Istio/Linkerd.
- Not a guarantee of readiness (12.04).
- Not a global load balancer with cross-AZ policies.
- Not a security boundary — still mTLS/auth on the business route.

## Rules and syntax

1. Timeout on lookup and on business call.
2. No infinite retry — budget and max attempts.
3. Log chosen instance id/url for debug.
4. Thread-safe round-robin (`atomic.Uint64`).
5. Cache < TTL; invalidate on fail.
6. Copy slice when caller filters.
7. 503 on empty list for user-facing path.
8. Retry only under 12.01 rules (idempotency).

## Examples

### Example 1 — Client lookup

**Predict the result:** Registry returns 500 — does Decode run at all and what does the caller see?

```go
type Inst struct {
	ID  string `json:"id"`
	URL string `json:"url"`
}

func (c *Discover) Lookup(ctx context.Context, service string) ([]Inst, error) {
	ctx, cancel := context.WithTimeout(ctx, c.LookupTimeout)
	defer cancel()
	req, err := http.NewRequestWithContext(ctx, http.MethodGet, c.Base+"/services/"+service, nil)
	if err != nil {
		return nil, err
	}
	res, err := c.HTTP.Do(req)
	if err != nil {
		return nil, err
	}
	defer res.Body.Close()
	if res.StatusCode != http.StatusOK {
		return nil, fmt.Errorf("discovery status %d", res.StatusCode)
	}
	var list []Inst
	if err := json.NewDecoder(io.LimitReader(res.Body, 1<<20)).Decode(&list); err != nil {
		return nil, err
	}
	if list == nil {
		list = []Inst{}
	}
	return list, nil
}
```

#### What happens here

`Lookup` derives a timeout of `c.LookupTimeout` from the caller context and GETs `c.Base + "/services/" + service`. An error from `Do` is returned as-is. A status other than 200 returns an error containing that status code, and the body is left undecoded. A 200 body is decoded up to `1<<20` bytes into `[]Inst`, and a nil slice is replaced with an empty non-nil slice.

**Answer:** Caller gets `error` with status; Decode does not run on the error body. Empty 200 + `[]` is success with zero instances — another branch in the caller.

### Example 2 — Random pick

**Predict the result:** What does PickRandom return on an empty list?

```go
func PickRandom(list []Inst) (Inst, error) {
	if len(list) == 0 {
		return Inst{}, errors.New("no instances")
	}
	return list[rand.IntN(len(list))], nil
}
```

#### What happens here

An empty `list` returns the zero `Inst` and an error whose text is `no instances`. A non-empty list returns the element at `rand.IntN(len(list))` with a nil error.

**Answer:** `error` “no instances”. Never index `list[0]` without checking length.

### Example 3 — Round-robin

**Predict the result:** List shrinks from 3 to 1 mid-run — does RR panic?

```go
type RR struct{ n atomic.Uint64 }

func (r *RR) Next(list []Inst) (Inst, error) {
	if len(list) == 0 {
		return Inst{}, errors.New("no instances")
	}
	i := r.n.Add(1) - 1
	return list[int(i%uint64(len(list)))], nil
}
```

#### What happens here

An empty list returns the zero `Inst` and the error text `no instances`. `n.Add(1) - 1` is the next counter value, so the first call uses index 0. The index actually used is that counter modulo the length of the list passed in. The counter is an `atomic.Uint64`, so concurrent `Next` calls update it with `Add`.

**Answer:** No — modulo with new length still works. Distribution may “jump”; acceptable.

### Example 4 — Call with one retry on a second instance

**Predict the result:** First instance refuses connection — may the second attempt use the same URL from cache?

```go
func (c *Client) GetOrder(ctx context.Context, id string) ([]byte, error) {
	list, err := c.Disc.LookupCached(ctx, "orders")
	if err != nil {
		return nil, err
	}
	var last error
	for try := 0; try < 2 && len(list) > 0; try++ {
		inst, err := PickRandom(list)
		if err != nil {
			return nil, err
		}
		b, err := c.doGet(ctx, inst.URL+"/v1/orders/"+id)
		if err == nil {
			return b, nil
		}
		last = err
		list = without(list, inst.ID)
		c.Disc.Invalidate("orders")
	}
	return nil, last
}
```

#### What happens here

`GetOrder` calls `LookupCached` for `"orders"` and returns immediately when that error is non-nil. The loop runs at most twice, and only while the local `list` still has an element. Each attempt picks a random instance and GETs `inst.URL + "/v1/orders/" + id`, returning the body when `doGet` succeeds. On failure the error is stored in `last`, `without` removes that id from the local slice, and `Invalidate("orders")` drops the cache entry. After the loop the function returns `last`, which is still nil if the lookup returned an empty list and the loop never entered.

**Answer:** It should not — `without` removes id, Invalidate forces fresh lookup next time. In the same loop local `list` already has no failed one. That is the point.

### Example 5 — Short cache

**Predict the result:** Two requests in the same second — how many Lookups to the registry with 2 s cache (no invalidate)?

```go
type cacheEntry struct {
	list  []Inst
	until time.Time
}

func (d *Discover) LookupCached(ctx context.Context, service string) ([]Inst, error) {
	d.mu.Lock()
	ent, ok := d.cache[service]
	if ok && time.Now().Before(ent.until) {
		list := append([]Inst(nil), ent.list...) // copy
		d.mu.Unlock()
		return list, nil
	}
	d.mu.Unlock()

	list, err := d.Lookup(ctx, service)
	if err != nil {
		return nil, err
	}
	d.mu.Lock()
	d.cache[service] = cacheEntry{list: list, until: time.Now().Add(2 * time.Second)}
	d.mu.Unlock()
	return append([]Inst(nil), list...), nil
}

func (d *Discover) Invalidate(service string) {
	d.mu.Lock()
	delete(d.cache, service)
	d.mu.Unlock()
}
```

#### What happens here

While `d.mu` is held, an entry whose `until` is still after `time.Now()` is copied with `append` and returned. A miss unlocks before `Lookup`, so the registry call sits outside the lock. A successful lookup is stored for two seconds, and the caller receives another copy of that slice. `Invalidate` deletes the service key under the same mutex.

**Answer:** Usually one refresh, second cache hit. Copy prevents `without` in one request from breaking cache for another.

### Example 6 — without helper

**Predict the result:** May `without` mutate the input slice in-place?

```go
func without(list []Inst, id string) []Inst {
	out := make([]Inst, 0, len(list))
	for _, it := range list {
		if it.ID != id {
			out = append(out, it)
		}
	}
	return out
}
```

#### What happens here

`without` allocates a new slice and appends every `Inst` whose `ID` differs from `id`. The input slice keeps its original length and elements. An id that occurs more than once is omitted each time, and a list with no match comes back with the same elements in a new slice.

**Answer:** Not in this design — new slice. In-place filtering of shared cache = data race / corruption.

### Example 7 — 503 when nobody is available

**Predict the result:** What is better for a mobile client: hang 30 s or 503 in 5 ms?

```go
list, err := disc.LookupCached(ctx, "orders")
if err != nil || len(list) == 0 {
	http.Error(w, "no available instances", http.StatusServiceUnavailable)
	return
}
```

#### What happens here

The handler asks `LookupCached` for `"orders"`. An error, or a list whose length is 0, writes status 503 with the body `no available instances` and returns. No instance URL is requested on that path.

**Answer:** 503 (with correct client retry/backoff). Hang wastes battery and workers and hides root cause.

### Example 8 — doGet with timeout boundary

**Predict the result:** May business timeout be longer than remaining parent context?

```go
func (c *Client) doGet(ctx context.Context, url string) ([]byte, error) {
	req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
	if err != nil {
		return nil, err
	}
	res, err := c.HTTP.Do(req)
	if err != nil {
		return nil, err
	}
	defer res.Body.Close()
	if res.StatusCode != http.StatusOK {
		return nil, fmt.Errorf("upstream status %d", res.StatusCode)
	}
	return io.ReadAll(io.LimitReader(res.Body, 1<<20))
}
```

#### What happens here

`NewRequestWithContext` binds the caller `ctx` to the GET, so `Do` ends when that context ends. After `Do` returns a response, `defer` closes the body. A status other than 200 becomes an error that includes the code. A 200 body is read with a limit of `1<<20` bytes.

**Answer:** No — child does not extend parent. That is why whole GetOrder shares one budget; retry spends the same deadline (12.01).

## Decision analysis

| Decision | Why |
|--------|--------|
| Random/RR | Enough for lab and many internal clients |
| Short cache | Less pressure on registry |
| Retry second instance | Survives one dead pod |
| Invalidate on fail | Faster learning about death |
| Timeout everywhere | Aligned with 12.01 |
| Copy from cache | No race with `without` |
| 503 on empty | Fail closed, clear signal |

## Trade-offs

- **No cache** — always fresh, expensive for registry.
- **Long cache** — cheaper, slower eviction of dead ones.
- **Many retries** — better chance, higher tail latency and load.
- **Client discovery** vs **sidecar/proxy** — control vs operational simplicity.
- **Random** vs **RR** — simplicity vs short-term fairness.
- **Hedging** — lower P99, higher QPS to upstream.

## Common mistakes

1. Retry same dead URL in a loop.
2. No timeout on discovery.
3. Shared `rand.Rand` without protection in old code (in 1.22+ `rand.IntN` is OK).
4. Assuming registry list means “passed /readyz”.
5. Global mutable slice without copy under concurrency.
6. Cache longer than TTL.
7. Infinite retry while context lives.
8. Retry non-idempotent POST “because discovery”.
9. Swallowing empty list as empty 200 business response.
10. Log without instance id — you do not know whom you picked.

## Idiomatic Go

- Discovery client as dependency (`*Discover`), not global.
- Copy slice when returning from cache.
- Metrics: discovery fail, retry count, empty list.
- Prefer standard K8s DNS/Service in a real cluster when you get there — same concepts.
- `atomic.Uint64` for RR; avoid Mutex only for a counter.

## Practical scenario

Checkout hardcodes one orders pod. During deploy that pod goes down — 5xx wave. They add discovery + random + one retry. Wave disappears for most requests. Then cache 10 s with TTL 15 s — still occasional hits on dead ones. Shorten cache to 2 s + invalidate on error — stable.

Later they replace registry with K8s service DNS; pick/retry code stays similar or thins. The lesson stays valuable because timeout/idempotency/503 policy do not disappear with DNS.

## Deeper Mechanism: cache, TTL, and errors together

Three clocks must agree:

| Clock | Typical value | Role |
|-----|------------------|-------|
| Instance TTL (registry) | 15 s | truth about freshness |
| Discovery cache | 2 s | protects registry |
| Business timeout | part of SLO | protects user |

Invariant: `cache_ttl < instance_ttl` and `lookup_timeout + business_timeout ≤ parent_deadline` (roughly). If you break the order, you “fix” the wrong layer.

### Singleflight with cache (optional)

When cache expires under load, 500 requests may hit registry at once. `singleflight.Group` (or manual inflight map) merges them into one Lookup. That is backpressure to registry — same family as 12.01 bulkhead.

### Example — metric wrapper around pick

**Predict the result:** How to see RR is not stuck on one id?

```go
func (c *Client) pick(list []Inst) (Inst, error) {
	inst, err := c.rr.Next(list)
	if err != nil {
		return Inst{}, err
	}
	// metric: upstream_selected{id=inst.ID}++
	return inst, nil
}
```

#### What happens here

`pick` calls `c.rr.Next` on the list it was given. An error from `Next` is returned with the zero `Inst`. On success the function returns that instance. The `upstream_selected` line is a comment, so this function performs the pick only.

**Answer:** Histogram/counter per id. If one id has 100% — list has one, or bug in Next, or cache always returns one.

### Example — filter by meta.version

**Predict the result:** List has v1 and v2; you want only v2 during canary.

```go
func filterVersion(list []Inst, version string) []Inst {
	out := make([]Inst, 0, len(list))
	for _, it := range list {
		if it.Meta["version"] == version {
			out = append(out, it)
		}
	}
	return out
}
```

#### What happens here

`filterVersion` builds a new slice containing the instances whose `Meta["version"]` equals `version`. The input slice is unchanged. A nil `Meta` yields the empty string for the lookup, and a version that matches no entry yields an empty slice.

**Answer:** New list; empty → 503 or fallback to v1 per policy. Meta comes from 12.02; discovery only filters.

(Note: extend `Inst` with `Meta map[string]string` if you filter — align JSON with registry Instance.)

### What to do when registry is silent

1. Return last cache **shorter** than remaining TTL? Dangerous — stale. Better: fail closed 503 for write; for read maybe stale-if-error with clear header `X-Stale: 1` and metric.
2. Do not open infinite retry to registry in request path — background refresh.
3. Alert on `discovery_error`.

### FAQ

**Why not always DNS?**  
In lab without K8s DNS you learn the contract. In cluster DNS often wins.

**Retry 3 times or 1?**  
On user path often 1 retry (2 attempts). More for background job with budget.

**Should 429 from upstream retry on another instance?**  
Often yes (another instance); sometimes no (global quota). Document.

**What about gRPC balancer?**  
Same concepts: resolver = lookup, picker = load choice. This lesson is HTTP-first but transferable.

### Anti-pattern: “smart” client that is too smart

Client that health-pings every instance before every request:

- doubles QPS;
- merges discovery and ready at wrong layer;
- lags more than it helps.

Leave ready to platform (12.04) and TTL to registry. Client picks and retries cautiously.

### Deeper flow: from service name to bytes

```text
GetOrder(ctx, id)
  → LookupCached("orders")     // cache or GET registry
  → PickRandom / RR
  → doGet(ctx, url+"/v1/orders/"+id)
       fail? → without → Invalidate → Pick again
  → return body | last error | (handler maps to 503)
```

Every arrow inherits timeout from `ctx`. If anywhere you open new `context.Background()` without budget, you violated 12.01.

### Example — mapping errors in HTTP handler

**Predict the result:** `GetOrder` returns “no instances” — which status to user?

```go
b, err := client.GetOrder(r.Context(), orderID)
if err != nil {
	if errors.Is(err, ErrNoInstances) || errors.Is(err, context.DeadlineExceeded) {
		http.Error(w, "temporarily unavailable", http.StatusServiceUnavailable)
		return
	}
	http.Error(w, "error", http.StatusBadGateway)
	return
}
```

#### What happens here

The handler calls `GetOrder` with the request context and `orderID`. `ErrNoInstances` and `context.DeadlineExceeded` both lead to status 503 and the text `temporarily unavailable`. Any other non-nil error leads to status 502 and the text `error`. A nil error leaves `b` available for the rest of the handler.

**Answer:** 503 for empty/deadline (retry-able / unavailable). 502 for other upstream fails per your taxonomy — be consistent and measure separately.

### Example — ErrNoInstances

```go
var ErrNoInstances = errors.New("no instances")

func PickRandom(list []Inst) (Inst, error) {
	if len(list) == 0 {
		return Inst{}, ErrNoInstances
	}
	return list[rand.IntN(len(list))], nil
}
```

#### What happens here

`ErrNoInstances` is one sentinel value from `errors.New`. `PickRandom` returns that same value when `list` is empty. A non-empty list returns one element chosen by `rand.IntN` and a nil error, so a caller can test the empty case with `errors.Is`.

**Predict the result:** Why sentinel and not just string?

**Answer:** `errors.Is` in handler and tests; stable metric taxonomy.

### Background refresh (sketch)

Instead of lookup in every request after expiry:

1. Background goroutine every 1 s runs Lookup for known services.
2. Request path only reads atomic pointer to list.
3. Invalidate still clears pointer on fail.

Trade-off: freshness vs simplicity. In lab request-path cache (Example 5) enough.

### Table “what invalidates cache”

| Event | Invalidate? |
|---------|-------------|
| Successful business call | no |
| Transport error / timeout | yes |
| 500 from upstream | often yes |
| 404 business “not found” | no (that is not dead pod) |
| 503 from upstream | yes (maybe draining) |
| Empty lookup | nothing to invalidate; metric empty |

### Link to registration on deploy

Rolling deploy: old instance DELETE/TTL, new Register. Discovery cache 2 s → at most brief stale. Cache 60 s → longer wave to dying ones. So cache policy is not “optimization” — part of deploy UX.

## Summary

Discovery reads fresh instances, load choice picks, cache and cautious retry increase resilience. Empty list is 503, not hang. Cache must respect TTL. Next: what “healthy” means — liveness vs readiness.
