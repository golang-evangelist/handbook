# 12.04 Status monitoring: /livez and /readyz

> **Go Path - Zero to Gopher** / **02 Intermediate → Building Distributed Applications with Go** / Lesson 12.04

## Lesson goals

After this lesson you should:

- distinguish **liveness** (*is the process alive* — should the process restart) and **readiness** (*ready for traffic* — may traffic be sent);
- implement `/livez` and `/readyz` (and optionally `/healthz` alias) with clear semantics;
- embed **timeout** in dependency checks on the readiness path;
- connect readiness with registration (12.02) — do not accept traffic until ready;
- avoid traps: liveness that touches DB, auth on probes, log flood, circular dependencies;
- drain on shutdown: ready false → wait for LB → Shutdown → DELETE from registry.

## Prerequisite

- 12.01–12.03 (timeout, registry order, discovery ≠ deep health).
- HTTP server in Go; optionally DB `PingContext` (09.xx).
- `atomic.Bool` for gate; signal handling for SIGTERM.
- Basic feel for Kubernetes probe fields (period, timeout, threshold) — map below.

## Problem this lesson solves

One “health” endpoint that pings the database:

- when DB slows, orchestrator **kills** pods (liveness fail) instead of only removing them from load balancer;
- restart loop worsens incident (thundering herd on already sick DB);
- discovery may still see “fresh” instances that are not ready if registration is not tied to ready.

Correct: liveness = “process is alive”; readiness = “may accept traffic”. Timeout in ready check. Registration after ready. Drain before kill signal completes.

## Mental model

| Probe | Question | Typical platform reaction |
|-------|---------|----------------------------|
| Liveness | Should I restart the process? | Kill + restart |
| Readiness | Should I send traffic? | Remove from Service/LB / Endpoints |
| Startup (optional) | Is initial load done? | Wait before liveness |

Go service (recommendation):

- `/livez` → 200 if HTTP server responds (no deep dependencies).
- `/readyz` → 200 if critical dependencies and warm OK; else 503.
- `/healthz` — often alias; **document** what it means for you (readiness better than a mix).

```text
start → listen (/livez OK)
      → warm (DB, cache)          /readyz = 503
      → SetReady(true)          /readyz = 200
      → RegisterLoop            discovery sees
      → ... traffic ...
SIGTERM → SetReady(false)       remove from LB
        → sleep(LB interval)
        → Shutdown + DELETE
```

## Mechanism

### Liveness: cheap and local

Liveness handler does not call external systems (DB, Redis, other HTTP). If process is deadlocked and does not respond on HTTP, probes will not get 200 anyway — platform restarts. If liveness calls DB, **DB incident becomes restart loop**.

Minimal livez: `200 ok`. Nothing more.

### Readiness: critical dependencies + timeout

Readiness may check DB/ping/cache, but:

1. **Short timeout** per check and total budget.
2. Only **critical** dependencies (not optional analytics).
3. 503 on fail (convention; be consistent).
4. Generic public text; detail in log/metric.

Without timeout, slow `Ping` holds goroutine and can saturate health workers — irony: health kills you.

### Startup probe (optional)

Slow cold start (large cache, migrations): startup probe gives time before liveness starts killing. In pure Go lab you often simulate with gate (`ready=false` for N seconds).

### Atomic ready gate

`atomic.Bool` (or equivalent):

- `false` during warm / drain;
- `true` when traffic allowed;
- readiness handler checks gate **before** or **along with** Ping.

Registration (12.02) only after `SetReady(true)`. Discovery (12.03) then sees only those that wanted to be visible — still TTL/heartbeat, but at least not warming.

### Timeout map to platform

| Your handler | Probe field | Rule |
|--------------|-------------|---------|
| ready timeout 500 ms | `timeoutSeconds: 1` | platform ≥ your budget |
| period 2 s | `periodSeconds: 2` | align |
| fail 3 times | `failureThreshold: 3` | less flapping |

If probe `timeoutSeconds` is shorter than your `PingContext`, platform kills probe before your context — false fail.

### Dependency classification

- **Critical** (DB for read API) → ready fail.
- **Optional** (analytics) → do not touch ready; log degradation / feature flag.
- **Circular** (A ready requires B, B ready requires A) → startup deadlock; avoid. Ready checks infrastructure, not “whole mesh”.

### Drain on shutdown

On SIGTERM:

1. `SetReady(false)` — stop passing ready / remove from LB.
2. Wait at least one LB/probe interval so new traffic stops.
3. `Server.Shutdown(ctx)` — finish in-flight requests within budget.
4. Cancel RegisterLoop context → DELETE.
5. Exit.

Without drain, LB still sends to closing server → 502 wave. That is not “attack” — that is bad contract with platform.

### Auth and middleware

Probe routes outside heavy auth/rate-limit middleware, or separate admin/listen port. If JWT middleware blocks `/readyz`, platform thinks you are dead forever.

### Log discipline

Do not log every successful probe at info — noise and cost. Log transitions: ready→not-ready, not-ready→ready, and fail with reason (at debug/metric).

### /healthz as alias

If old chart wants one path: document “healthz = readiness” and call same code as Readyz. Better expose both and keep alias.

### Link to registry and discovery

- Register after ready.
- On drain: ready false **before** DELETE (or nearly simultaneous) so you do not receive new from LB while discovery still sees you briefly — TTL and invalidate on client help (12.03).
- Do not put deep Ping in livez to “speed up” removal — wrong tool; for that use ready + TTL.

### Defensive Go patterns

- `PingContext(ctx)` not `Ping()` without context.
- `atomic.Bool` for gate.
- Small handlers — no template engine.
- Limit: ready must not run heavy migrations “on the side”.

### What to measure

- `ready_status` gauge (0/1)
- `ready_check_fail{dep=db}`
- `livez_fail` (rare — if you have custom logic)
- time from start to first ready
- drain duration

### Fail closed in ready

For critical API: DB down → 503 ready → no traffic → fewer 500 on business route. For static content service maybe shallower ready. Document.

## Rules and syntax

1. Readiness fail → 503, not 500 (convention).
2. Do not require auth on probe routes (or separate port).
3. Do not log every successful probe at info level.
4. Keep handlers outside heavy middleware.
5. Timeout on every deep check.
6. Registration after ready; DELETE with drain.
7. Liveness without external dependencies.
8. Align probe `timeoutSeconds` with handler budget.

## Examples

### Example 1 — Separate livez/readyz

**Predict the result:** DB Ping takes 2 s, ready budget 500 ms — what does probe see and is pod restarted?

```go
type Health struct {
	DB interface{ PingContext(context.Context) error }
}

func (h *Health) Livez(w http.ResponseWriter, _ *http.Request) {
	w.WriteHeader(http.StatusOK)
	_, _ = w.Write([]byte("ok"))
}

func (h *Health) Readyz(w http.ResponseWriter, r *http.Request) {
	ctx, cancel := context.WithTimeout(r.Context(), 500*time.Millisecond)
	defer cancel()
	if h.DB != nil {
		if err := h.DB.PingContext(ctx); err != nil {
			http.Error(w, "db not ready", http.StatusServiceUnavailable)
			return
		}
	}
	w.WriteHeader(http.StatusOK)
	_, _ = w.Write([]byte("ready"))
}
```

#### What happens here

`Livez` writes status 200 and the body `ok`, with no use of the `DB` field. `Readyz` limits the check with a 500-millisecond timeout on the request context. When `DB` is non-nil, an error from `PingContext` writes status 503 and `db not ready`. A nil `DB`, or a ping that returns nil, writes status 200 and `ready`.

**Answer:** Ready returns 503 in ≤500 ms. Livez still 200. Platform removes from LB, **does not** restart only because of DB. That is the whole point of the split.

### Example 2 — Atomic ready flag

**Predict the result:** What does `/readyz` show before `SetReady(true)` even if DB is already alive?

```go
type Gate struct{ ready atomic.Bool }

func (g *Gate) SetReady(v bool) { g.ready.Store(v) }

func (g *Gate) Readyz(w http.ResponseWriter, _ *http.Request) {
	if !g.ready.Load() {
		http.Error(w, "warming", http.StatusServiceUnavailable)
		return
	}
	w.WriteHeader(http.StatusOK)
}
```

#### What happens here

`Gate.ready` is an `atomic.Bool`, and `SetReady` stores the boolean it receives. `Readyz` loads the flag. A false value writes status 503 and `warming`. A true value writes status 200 and no body.

**Answer:** 503 warming. Gate controls warm-up and drain independently of Ping. You often combine gate **and** Ping in same Readyz.

### Example 3 — Wiring and startup order

**Predict the result:** Why does RegisterLoop go only after `SetReady(true)`?

```go
func main() {
	gate := &Gate{}
	db := openDB()
	h := &Health{DB: db}
	ctx, cancel := signalContext()
	defer cancel()

	mux := http.NewServeMux()
	mux.HandleFunc("GET /livez", h.Livez)
	mux.HandleFunc("GET /readyz", func(w http.ResponseWriter, r *http.Request) {
		if !gate.ready.Load() {
			http.Error(w, "warming", http.StatusServiceUnavailable)
			return
		}
		h.Readyz(w, r)
	})

	srv := &http.Server{Addr: ":8080", Handler: mux, ReadHeaderTimeout: 5 * time.Second}
	go func() { _ = srv.ListenAndServe() }()

	warm(ctx)
	gate.SetReady(true)
	go RegisterLoop(ctx, registryURL, "orders", instanceID, selfURL)

	<-ctx.Done()
	gate.SetReady(false)
	time.Sleep(3 * time.Second)
	shutdownCtx, c := context.WithTimeout(context.Background(), 10*time.Second)
	defer c()
	_ = srv.Shutdown(shutdownCtx)
}
```

#### What happens here

`GET /livez` is handled by `h.Livez`. `GET /readyz` writes status 503 and `warming` while `gate.ready` is false, and it calls `h.Readyz` once the flag is true. The HTTP server begins listening on `:8080` before `warm` and `SetReady(true)`. `RegisterLoop` starts with that same `ctx` only after `SetReady(true)`. When `ctx` is done, `main` stores false, sleeps three seconds, and calls `Shutdown` with a fresh ten-second timeout.

**Answer:** So discovery does not publish a half-ready instance. Livez already works so platform does not kill pod during slow start (with startupProbe).

### Example 4 — Aggregate multiple checks

**Predict the result:** First check fails — does second run at all and what does client see?

```go
func (h *Health) Readyz(w http.ResponseWriter, r *http.Request) {
	ctx, cancel := context.WithTimeout(r.Context(), 800*time.Millisecond)
	defer cancel()
	checks := []struct {
		name string
		fn   func(context.Context) error
	}{
		{"db", h.DB.PingContext},
		{"cache", h.Cache.Ping},
	}
	for _, c := range checks {
		cctx, ccancel := context.WithTimeout(ctx, 300*time.Millisecond)
		err := c.fn(cctx)
		ccancel()
		if err != nil {
			http.Error(w, "not ready", http.StatusServiceUnavailable)
			// log.Printf("ready fail %s: %v", c.name, err)
			return
		}
	}
	w.WriteHeader(http.StatusOK)
}
```

#### What happens here

The readiness context lasts at most 800 milliseconds. Each check runs under a 300-millisecond child of that context, and `ccancel` is called as soon as the check returns. The first non-nil error writes status 503 and `not ready`, then returns, so later checks stay uncalled. The `log.Printf` line is a comment. When every check returns nil, the handler writes status 200.

**Answer:** Stops on first error (fail-fast). Public “not ready”; dependency name in log. Sub-budget 300 ms per check within 800 ms.

### Example 5 — What NOT to do in livez

**Predict the result:** Why does this livez worsen DB incident?

```go
// bad
func Livez(w http.ResponseWriter, r *http.Request) {
	_ = db.PingContext(r.Context()) // liveness depends on DB
	w.WriteHeader(http.StatusOK)
}
```

#### What happens here

This `Livez` calls `db.PingContext` with the request context and discards the error through `_`. After `PingContext` returns, the handler writes status 200. The status line waits on the ping, and a non-nil ping error still produces status 200.

**Answer:** DB slow/down → fail or slow liveness → mass restart → even more pressure on DB. Deep checks belong in readiness.

### Example 6 — Drain snippet

**Predict the result:** Why sleep after `SetReady(false)`?

```go
gate.SetReady(false)
time.Sleep(3 * time.Second) // aligned with LB / probe interval
shutdownCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
defer cancel()
_ = srv.Shutdown(shutdownCtx)
```

#### What happens here

`SetReady(false)` runs first. `time.Sleep` then waits three seconds, which the comment ties to the load-balancer or probe interval. `Shutdown` uses `context.Background()` with a ten-second timeout, and the snippet discards the error from `Shutdown`.

**Answer:** So LB has time to stop sending new requests before you close listener. Sleep lasts at least one health interval.

### Example 7 — /healthz alias

**Predict the result:** Old chart calls only `/healthz` — how not to mix live and ready?

```go
mux.HandleFunc("GET /livez", h.Livez)
mux.HandleFunc("GET /readyz", readyHandler)
mux.HandleFunc("GET /healthz", readyHandler) // documented: = readiness
```

#### What happens here

`GET /livez` is registered with `h.Livez`. `GET /readyz` and `GET /healthz` are both registered with `readyHandler`, so a request to either path calls that same function. The comment on the `/healthz` registration states that the alias means readiness.

**Answer:** Alias to readyHandler. In README: “healthz = readiness”. Do not return 200 on healthz until gate is ready.

### Example 8 — Test ready timeout

**Predict the result:** How to prove ready does not wait 2 s when budget is 500 ms?

```go
func TestReadyzTimeout(t *testing.T) {
	h := &Health{DB: slowDB{delay: 2 * time.Second}}
	srv := httptest.NewServer(http.HandlerFunc(h.Readyz))
	defer srv.Close()
	start := time.Now()
	res, err := http.Get(srv.URL)
	if err != nil {
		t.Fatal(err)
	}
	defer res.Body.Close()
	if res.StatusCode != http.StatusServiceUnavailable {
		t.Fatalf("status %d", res.StatusCode)
	}
	if time.Since(start) > 800*time.Millisecond {
		t.Fatal("ready took too long")
	}
}
```

#### What happens here

The test sets `Health.DB` to a `slowDB` whose `delay` is two seconds and serves `h.Readyz` with `httptest`. It times an `http.Get` of that server and requires status 503. If the elapsed time is greater than 800 milliseconds, the test fails with `t.Fatal`.

**Answer:** Status 503 and duration ≪ 2 s prove `WithTimeout` cuts Ping. (In real test use client timeout / context properly with httptest.)

## Decision analysis

| Decision | Why |
|--------|--------|
| Separate live/ready | Correct platform reaction |
| Short timeout | Health must not stall process |
| Ready flag | Control warm-up / drain |
| Registration after ready | Discovery does not see half-ready |
| Generic public text | Less leak of internal topology |
| Alias healthz → ready | Compatibility without mixing semantics |
| Sleep in drain | Align with LB interval |

## Trade-offs

- **Deep ready** — more accurate traffic, more false 503 when dependency flickers.
- **Shallow ready** — more 5xx on business routes.
- **One /healthz** — simpler, easy wrong semantics.
- **Separate admin port for probes** — cleaner, bit more ops complexity.
- **Long drain sleep** — fewer 502, slower rolling deploy.
- **Short drain** — faster deploy, risk mid-request kill.

## Common mistakes

1. Liveness pings DB.
2. No timeout on ready check.
3. Registration before ready.
4. Auth middleware blocks probes.
5. Log flood from successful probes every second.
6. Ready checks unrelated / optional dependency.
7. Probe `timeoutSeconds` shorter than handler timeout.
8. No drain — Shutdown while LB still sends.
9. Circular ready between services.
10. `/healthz` documented as live but behaves as ready (or reverse) without agreement.

## Idiomatic Go

- `atomic.Bool` for gate.
- `PingContext` not `Ping` without context.
- Probe handlers small, without heavy stack.
- Document probe contract in service README.
- `Server.Shutdown` instead of abrupt `Close` when you can.
- Test ready timeout with slow fake DB.

## Practical scenario

During DB failover all pods fail liveness because health mixed Ping. Orchestrator restarts 50 pods at once. After livez/readyz split, pods stay alive, removed from LB until DB clears, then return. MTTR drops.

Same team moves register loop after `SetReady(true)` — discovery no longer sends traffic to warming instances. On deploy they add 3 s drain — 502 at end of pod disappear. Incident post-mortem fits one sentence: **wrong probe semantics amplifies partial failure**.

## Deeper Mechanism: why pod dies “healthy”

Sometimes livez passes, ready passes, business routes still 500. Causes:

1. Ready only checks Ping, routes need schema/migration not done yet — extend warm, not livez.
2. Ready is shallow; optional dependency not in ready but breaks happy path — feature flag or soft-fail in route.
3. Discovery cache (12.03) still holds old address after drain — invalidate + short cache.
4. Register loop has not DELETE yet — TTL window.

Probes are not replacement for good business error metrics. They are **traffic admission and restart policy**.

### Semantics of status codes on probes

| Code | Meaning for platform (typical) |
|-----|----------------------------------|
| 200–399 | Probe success |
| 400+ | Probe fail |

Do not get creative with 204 vs 200 without checking what your orchestrator exactly expects. In K8s any code outside 200–399 is fail for httpGet probe.

### Readiness and partial degradation

When you have two API modes (read from cache vs DB), you may:

- keep ready 200 while cache serves read-only;
- metric `degraded=1`;
- write routes return 503.

That is product decision aligned with 12.01 fail open/closed. Mechanism: do not hide degradation behind fake “all green” if operator must know.

### Example — combined Readyz (gate + DB)

**Predict the result:** Gate true, DB fail — status?

```go
func ReadyCombined(gate *Gate, h *Health) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		if !gate.ready.Load() {
			http.Error(w, "warming", http.StatusServiceUnavailable)
			return
		}
		h.Readyz(w, r)
	}
}
```

#### What happens here

The returned handler loads `gate.ready` before it touches the database. A false flag writes status 503 and `warming`, then returns. A true flag calls `h.Readyz`, and that method writes the status from its own checks.

**Answer:** 503 from Health.Readyz (db not ready). Gate only passes warm/drain layer; Ping remains authority for DB.

### Example — startup delay without K8s startupProbe

**Predict the result:** First 5 s ready must be 503 even with healthy DB.

```go
func (g *Gate) WarmFor(d time.Duration) {
	g.ready.Store(false)
	time.AfterFunc(d, func() { g.ready.Store(true) })
}
```

#### What happens here

`WarmFor` stores false immediately. `time.AfterFunc` schedules `Store(true)` to run after duration `d`. The method returns without waiting, and the flag stays false until that callback runs.

**Answer:** AfterFunc sets gate. In production more often explicit warm() then SetReady; AfterFunc is lab shortcut — beware SetReady(true) before warm is actually done.

### Link to 13.xx

Ready fail is not panic. It is expected `error` path at boundary. When in 13.01 you classify errors, ready timeout goes in same bucket as `DeadlineExceeded` — operationally different from programmer bug.

### Deeper Mechanism: signal order

```text
SIGTERM
  → cancel app ctx          (RegisterLoop sends DELETE)
  → gate.SetReady(false)    (LB/probe remove)
  → sleep(probe interval)
  → Shutdown(http)          (finish in-flight)
  → close DB / rest
  → exit 0
```

Wrong order: Shutdown before ready false → LB still sends to closed port. DELETE before ready false → discovery removes, but LB may still send briefly if it does not watch same signal.

### Example — signalContext

**Predict the result:** Which signals usually cancel ctx in container?

```go
func signalContext() (context.Context, context.CancelFunc) {
	ctx, cancel := context.WithCancel(context.Background())
	ch := make(chan os.Signal, 1)
	signal.Notify(ch, os.Interrupt, syscall.SIGTERM)
	go func() {
		<-ch
		cancel()
	}()
	return ctx, cancel
}
```

#### What happens here

The function returns a cancellable context derived from `context.Background()`. `signal.Notify` delivers `os.Interrupt` and `syscall.SIGTERM` on a channel that can buffer one signal. A goroutine reads one signal and calls `cancel`. The caller also holds `cancel`, so it can end the context itself.

**Answer:** SIGTERM (K8s stop) and Interrupt (Ctrl+C in lab). Without this RegisterLoop does not graceful DELETE.

### Example — ready with multiple states (enum instead of bool)

**Predict the result:** Why three states sometimes beat bool?

```go
type State int32

const (
	StateStarting State = iota
	StateReady
	StateDraining
)

// atomic.Int32 holds State; Readyz passes only StateReady
```

#### What happens here

`State` has underlying type `int32`, and the iota block defines `StateStarting` as 0, `StateReady` as 1, and `StateDraining` as 2. The comment says an `atomic.Int32` would hold one of those values and that `Readyz` would allow only `StateReady`. This snippet stops at the constants.

**Answer:** Starting and Draining both give 503, but metrics/logs distinguish cause. Bool hides nuance; for larger systems state helps operator.

### Flapping: ready flickers

Dependency at timeout edge → ready 200/503/200/503. Effects: Endpoints flap, connection churn.

Mitigation:

- `failureThreshold` / `successThreshold` on probe;
- hysteresis in app (e.g. 2 consecutive fails before not-ready);
- fix dependency instead of “patching” threshold forever.

### What to document in service README

```text
GET /livez  — process up, no deps
GET /readyz — gate + db ping ≤500ms → 200/503
K8s: livenessPath=/livez readinessPath=/readyz
      timeoutSeconds=1 periodSeconds=2 failureThreshold=3
Drain: ready false + 3s + Shutdown 10s
```

Without this platform team guesses. Probe contract is API to cluster.

### FAQ

**Can livez check “deadlock”?**  
If HTTP server does not respond, probe fails — enough. Do not call DB to “detect” deadlock.

**Ready in sidecar?**  
Mesh may do health; still document app ready if sidecar consults app port.

**What about Windows signals in lab?**  
Interrupt works; SIGTERM behavior depends on environment. Gate+Shutdown logic same.

## Summary

Liveness keeps process; readiness keeps user from half-ready instances. Timeout, gate, registration order, and drain complete the distributed foundations module. Do not mix probe semantics — wrong platform reaction amplifies partial failure.
