# 08.02 Goroutine: starting, leaking, and cancelling

> **Go Path - Zero to Gopher** / **02 Intermediate → Concurrent Programming with Go** / Lesson 08.02

## Lesson goals

After this lesson you can:

- use the `go` statement reliably and know that return values are discarded
- recognize and prevent a **goroutine leak**: blocked receive while nobody sends
- cancel work via **context** (`WithCancel`, `WithTimeout`) with `defer cancel()`
- group tasks with **errgroup** (`golang.org/x/sync/errgroup`) and the first error
- tie a goroutine’s lifetime to the lifetime of a request or job
- correctly start `go` inside a loop in Go 1.22+ (per-iteration variable)

## Prerequisite

- Lesson 08.01 (concurrency, parallelism, GOMAXPROCS, CSP)
- Functions, **closure**, `defer`
- Basic work with a **channel** helps, but you can follow the first examples without the depth from 08.04

## Problem this lesson solves

`go f()` looks trivial — and that is why it is abused. Typical problems:

- a goroutine keeps working after the client gave up
- a goroutine waits on a channel that nobody will close or fill
- `main` or a handler finishes, and background work stays a “zombie”
- errors from multiple parallel calls are lost
- in a loop the wrong variable is captured (historically before 1.22; today different, but discipline is still needed)

Without discipline around cancellation and lifetime boundaries, a service becomes slow, memory grows, and debugging is hard. This lesson sets the rules: who starts, who waits, who cancels.

## Mental model

A goroutine is a **unit of work with its own stack** in the Go runtime. It is not an OS thread. It is not a process. You do not “join” it like a thread in some languages — you wait for completion via WaitGroup, channel, or errgroup.

Three questions for every `go`:

1. **What is the completion signal?** (function return, `close` on a channel, `ctx.Done()`)
2. **Who waits for the result or error?** (WaitGroup, channel, `errgroup.Wait`)
3. **What if nobody needs the result anymore?** (cancellation so it does not leak)

**context.Context** is a contract for cancellation and deadline that is passed down through calls. It is not magic and not thread interruption: code must *listen* to `ctx.Done()` or pass `ctx` into an API that respects cancellation (`http.NewRequestWithContext`, DB drivers, etc.).

### Official terminology table (this lesson)

| Official Go term | Short English gloss (first time only) | Do not use as the concept name |
|------------------|---------------------------------------|--------------------------------|
| goroutine | unit of work with its own stack | thread, process |
| channel | typed send/receive medium | — |
| context | cancellation and deadline contract | — |
| closure | function that captures surrounding variables | — |
| WaitGroup | completion counter for a group of goroutine | — |
| select | choice among channel operations | — |
| error | error type/value | — |
| zero value | default value of a type | — |

## Mechanism

### The `go` statement

```go
go f(x, y)
go func(n int) {
	fmt.Println(n)
}(42)
```

What happens:

1. The runtime schedules a new goroutine.
2. The current goroutine does **not** wait for completion.
3. Arguments are evaluated *before* start (like a normal call).
4. Return values are **discarded** — there is no `x := go f()`.

Trace without waiting:

```text
main: go work()     // scheduled
main: return        // process exits
work()              // may never get to execute the body
```

If you need a result, send it on a channel, write it to a field protected by a Mutex, or use errgroup.

### Leak: blocked receive without a sender

Classic leak:

```go
ch := make(chan int) // capacity 0
go func() {
	v := <-ch // BLOCKS forever — nobody sends, nobody closes
	_ = v
}()
```

Trace:

```text
1. make(chan int) — buffer 0
2. new goroutine enters receive
3. receive waits for send or close
4. none of that happens
5. goroutine stays alive forever (while the process lives)
```

Symptoms on a server: `runtime.NumGoroutine()` grows; the goroutine profile in pprof shows a stack on `chan receive`; memory grows.

Other forms of leak:

- a loop with no exit and no check of `ctx.Done()`
- `time.After` in a long loop without `Stop` (timer leak — advanced detail)
- a sender blocked on a full buffer while the receive side gave up

Fixes: send a value; `close(ch)` from the send side; `select` with `ctx.Done()`; do not start a goroutine if you have no receive for the result.

### Context cancellation

```go
ctx, cancel := context.WithCancel(parent)
defer cancel()

ctx, cancel := context.WithTimeout(parent, 3*time.Second)
defer cancel()
```

Mechanism:

1. `WithCancel` / `WithTimeout` create a child context.
2. `cancel()` (or time expiry) closes the `ctx.Done()` channel.
3. Everyone who does `<-ctx.Done()` or passes `ctx` into a respecting API sees the signal.
4. `defer cancel()` frees timer resources even when the work finishes early.

**Context does not forcibly stop a goroutine.** If your loop never looks at `Done`, it will run to the end.

Timeout trace:

```text
t=0      WithTimeout(500ms), defer cancel
t=0      work() enters select: After(2s) vs ctx.Done()
t=500ms  ctx expires → Done closed
t=500ms  select picks Done → return ctx.Err() (DeadlineExceeded)
t=2s     After is NOT chosen (work already exited)
```

### errgroup

`golang.org/x/sync/errgroup` starts a set of goroutine, waits for all, returns the **first** error. With `errgroup.WithContext` the first error cancels `ctx` for the others.

```go
g, ctx := errgroup.WithContext(parent)
g.Go(func() error { return jobA(ctx) })
g.Go(func() error { return jobB(ctx) })
err := g.Wait()
```

Trace:

```text
1. WithContext — linked cancel
2. A and B start
3. A returns error
4. ctx is cancelled
5. B, if it listens to ctx, stops earlier
6. Wait returns the first error
```

Newer versions of `x/sync` have `SetLimit` to bound parallelism inside the group — useful instead of unbounded `go` in a loop.

### Loop + `go` + closure (Go 1.22+)

```go
for i := range 3 {
	go func() {
		fmt.Println(i)
	}()
}
```

In 1.22+ each iteration has a **new** variable `i`. The closure captures that iteration. Prints 0,1,2 (order not guaranteed).

Before 1.22 the same `i` would be shared — often all print 3. The course assumes 1.22+. Explicit `i := i` still helps readability in mixed codebases.

For values you change in the loop (e.g. `u := urls[i]`), still copy into a local variable before `go` when you want a clear review:

```go
for _, u := range urls {
	u := u // local copy per iteration
	g.Go(func() error { return fetch(ctx, u) })
}
```

### Link to WaitGroup (overview)

```go
var wg sync.WaitGroup
wg.Add(1) // BEFORE go
go func() {
	defer wg.Done()
	work()
}()
wg.Wait()
```

`Add` before `go` prevents `Wait` from seeing zero too early. Details in 08.03. For errors from a group prefer errgroup.

### Semaphore via channel (bridge to a pool)

```text
sem := make(chan struct{}, n)  // capacity n
sem <- struct{}{}              // take a slot (blocks if full)
// ... work ...
<-sem                          // release slot
```

At most `n` goroutine at once in the critical part. Why a bound exists: an unbounded number of goroutine consumes memory and can crash the process under peak (08.05).

### Full trace: from `go` to result

```go
out := make(chan int, 1)
go func() { out <- 7 * 7 }()
fmt.Println(<-out)
```

| Step | Who | State |
|-----:|-----|-------|
| 1 | main | `out` buffer 1 empty |
| 2 | main | starts goroutine |
| 3 | g or main | whoever arrives first — send into buffer or receive waits |
| 4 | g | computes 49, sends |
| 5 | main | receives 49, prints |

Without a buffer: send and receive must meet (rendezvous). With buffer 1: send can finish before receive.

### Full trace: leak then fix

**Bad:**

```text
go: v := <-ch   // ch never gets a send
main: return from handler
g lives forever → NumGoroutine +1 per request
```

**Better with context:**

```text
select {
case v := <-ch:
  use(v)
case <-ctx.Done():
  return ctx.Err()
}
cancel / timeout → g exits
```

**Better with close:**

```text
close(ch) or send a value → receive unblocks
```

### What `cancel` is not

- Not `pthread_cancel`.
- Not killing an OS thread (a goroutine is not a thread anyway).
- Not a guarantee that a dense CPU loop will stop in 1 ms without checking `ctx`.
- For CPU loops: periodically `ctx.Err()` or `select` on `Done`.

### HTTP request as a lifetime boundary

```text
client → handler
handler: ctx = r.Context()   // cancelled on disconnect
handler: errgroup.WithContext(ctx)
         go fetch A(ctx)
         go fetch B(ctx)
client closes connection → ctx cancel → A/B stop if they respect ctx
without ctx: A/B keep working → wasted work / leak
```

### Checklist before `go` in a PR

1. Completion signal (`return`, `close`, `ctx.Done`)?
2. Who waits for `error` / result?
3. Limit on goroutine count under peak?
4. Cancellation test?
5. Documentation that the function starts background work?

### Comparing join tools

| Tool | When |
|------|------|
| WaitGroup | just wait for completion; no `error` aggregation |
| errgroup | N steps; first `error`; cancellation |
| result channel | one or more results as values |
| nothing | fire-and-forget — almost always bad without a limit |

### Trace: loop before and after 1.22

```text
items = [a, b, c]

Before 1.22 (classic bug):
  go process(item) in a loop → often all see c

Go 1.22+:
  each iteration has its own item
  process(a), process(b), process(c)

Still idiomatic:
  item := item  or  go func(item T){...}(item)
  for clarity in review
```

## Rules and syntax

```go
ctx, cancel := context.WithTimeout(parent, 3*time.Second)
defer cancel()

g, ctx := errgroup.WithContext(ctx)
g.Go(func() error { return job(ctx) })
if err := g.Wait(); err != nil {
	// first error or cancellation
}
```

Rules:

1. Do not start a goroutine without a plan for completion.
2. Do not ignore `ctx.Err()` in long-running loops.
3. Do not send on a channel after you gave up on the receive side without a strategy (`select` + `ctx.Done()`, buffer, or do not start).
4. A library must not start a goroutine without documentation and a way to stop it.
5. Pass `ctx` as the first argument: `func F(ctx context.Context, ...)`.
6. Do not store a request context in a long-lived service structure.

## Examples

### Example 1 — Basic go and waiting for a result

```go
package main

import "fmt"

func square(n int, out chan<- int) {
	out <- n * n
}

func main() {
	out := make(chan int, 1)
	go square(7, out)
	fmt.Println(<-out) // 49
}
```

#### What happens here

1. `go square(7, out)` does not return 49 to the caller.
2. Buffer 1: `out <- 49` does not block even if `main` is briefly late.
3. `main` does `<-out` and gets 49.

Without a channel (or WaitGroup) `main` could exit before completion.

### Example 2 — Leak: forever on a channel

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

func leak() {
	ch := make(chan int) // buffer 0
	go func() {
		v := <-ch // nobody ever sends
		fmt.Println(v)
	}()
}

func main() {
	before := runtime.NumGoroutine()
	for i := 0; i < 100; i++ {
		leak()
	}
	time.Sleep(20 * time.Millisecond)
	fmt.Println("before", before, "after", runtime.NumGoroutine())
}
```

#### What happens here

Each `leak()` leaves one goroutine on receive. The count grows by ~100. In a short process it vanishes on exit; on a server this is a disaster.

**Predict the result:** If in `leak` you add `close(ch)` right after `go`, what happens to receive?

**Answer:** Receive from a closed channel immediately returns the type’s **zero value** (`0` for `int`) and the goroutine finishes. The leak disappears. (`ok` details in 08.04.)

### Example 3 — Fixing a leak with context

```go
package main

import (
	"context"
	"fmt"
	"time"
)

func work(ctx context.Context, ch <-chan int) error {
	select {
	case v := <-ch:
		fmt.Println("got", v)
		return nil
	case <-ctx.Done():
		return ctx.Err()
	}
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 100*time.Millisecond)
	defer cancel()

	ch := make(chan int) // nobody sends
	if err := work(ctx, ch); err != nil {
		fmt.Println("end:", err)
	}
}
```

#### What happens here

1. `work` waits for either a value or cancellation.
2. After 100 ms `Done` closes.
3. `select` picks `ctx.Done()` — no eternal block.
4. Returns `context.DeadlineExceeded`.

### Example 4 — Context timeout on slow work

```go
package main

import (
	"context"
	"fmt"
	"time"
)

func work(ctx context.Context) error {
	select {
	case <-time.After(2 * time.Second):
		return nil
	case <-ctx.Done():
		return ctx.Err()
	}
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 500*time.Millisecond)
	defer cancel()

	if err := work(ctx); err != nil {
		fmt.Println("cancelled:", err)
	}
}
```

#### What happens here

The work would take 2 s; the context expires at 500 ms. Without a branch on `Done`, the timeout would do nothing.

### Example 5 — errgroup with cancellation

```go
package main

import (
	"context"
	"fmt"
	"time"

	"golang.org/x/sync/errgroup"
)

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
	defer cancel()

	g, ctx := errgroup.WithContext(ctx)

	g.Go(func() error {
		time.Sleep(50 * time.Millisecond)
		return fmt.Errorf("first error")
	})
	g.Go(func() error {
		select {
		case <-time.After(5 * time.Second):
			return nil
		case <-ctx.Done():
			return ctx.Err()
		}
	})

	fmt.Println(g.Wait())
}
```

#### What happens here

1. The first goroutine quickly returns an error.
2. `WithContext` cancels `ctx`.
3. The second picks `Done` instead of sleeping 5 s.
4. `Wait` returns the first error.

### Example 6 — Loop 1.22+ and go

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var wg sync.WaitGroup
	for i := range 3 {
		wg.Add(1)
		go func() {
			defer wg.Done()
			fmt.Println(i)
		}()
	}
	wg.Wait()
}
```

#### What happens here

In Go 1.22+ it prints 0, 1, 2 (in any order). Each iteration has its own `i`. `Add` is before `go`; `Done` in `defer`.

**Predict the result:** What if you move `wg.Add(1)` *inside* the goroutine, and `Wait` right after the loop on a fast machine?

**Answer:** `Wait` can see counter 0 before any `Add` arrives — early return. That is why the rule is: **Add before go**.

### Example 7 — Handler that does not leak

```go
func (h *Handler) ServeHTTP(w http.ResponseWriter, r *http.Request) {
	ctx := r.Context()
	g, ctx := errgroup.WithContext(ctx)

	var a, b []byte
	g.Go(func() error {
		var err error
		a, err = h.clientA.Get(ctx)
		return err
	})
	g.Go(func() error {
		var err error
		b, err = h.clientB.Get(ctx)
		return err
	})
	if err := g.Wait(); err != nil {
		http.Error(w, "dependent service", http.StatusBadGateway)
		return
	}
	_, _ = w.Write(append(a, b...))
}
```

#### What happens here

Work lifetime is tied to the HTTP request. When the client closes the connection, `r.Context()` is cancelled; errgroup spreads the signal; clients that respect `ctx` stop. Without that, work would continue for a response nobody will read.

## Decision analysis

| Decision | Why |
|----------|-----|
| `go` + explicit waiting | Result and error do not disappear |
| Context in the I/O chain | Single cancellation signal |
| errgroup for N steps with error | First error + cancel the rest |
| WaitGroup when there is no error | Simpler “wait for completion” |
| Bound (semaphore / pool) | Unbounded goroutine consume memory |
| Document `go` in the API | Caller knows they must cancel / wait |

## Trade-offs

- **errgroup** — powerful; depends on `x/sync`; for trivial waiting WaitGroup is enough.
- **Large timeout** — fewer false cancellations; slower discovery of stuck dependencies.
- **Small timeout** — faster fail; more errors under load.
- **Fire-and-forget** — simple; high leak risk and lost errors.
- **Propagating context everywhere** — discipline; requires libraries to respect `ctx`.

## Common mistakes

1. **Wrong code:** `go func() { v := <-ch }()` and `ch` is never filled/closed.  
   **What happens:** Leak — goroutine forever on receive.  
   **Why:** Receive on an unbuffered (or empty) channel waits for a sender.  
   **Fix:** `select` + `ctx.Done()`, or `close`/send with a clear owner.

2. **Wrong code:** `ctx, cancel := context.WithTimeout(...);` without `defer cancel()`.  
   **What happens:** Timer/resource leak in the context tree until later GC.  
   **Why:** A timeout context holds a timer until cancelled.  
   **Fix:** Always `defer cancel()`.

3. **Wrong code:** Ignore `r.Context()` in the handler; use `context.Background()`.  
   **What happens:** Work after disconnect.  
   **Why:** Background is not cancelled when the client leaves.  
   **Fix:** `ctx := r.Context()` and pass it down.

4. **Wrong code:** Three `go` without collecting errors.  
   **What happens:** Two errors vanish; only the happy path works.  
   **Why:** Return values from `go` are discarded.  
   **Fix:** errgroup or a channel for `error`.

5. **Wrong code:** `Add` inside the goroutine.  
   **What happens:** `Wait` can return too early.  
   **Why:** Race between `Add` and `Wait`.  
   **Fix:** `Add` before `go`.

6. **Wrong code:** Unbounded `go` per item under peak.  
   **What happens:** Memory grows; scheduler sinks.  
   **Why:** Each goroutine uses stack/memory.  
   **Fix:** Worker pool / semaphore / `SetLimit`.

## Idiomatic Go

- `func F(ctx context.Context, ...)`
- Do not store context in a long-lived service `struct`
- For a group with error: errgroup
- For completion only: WaitGroup
- Distinguish `context.Canceled` from a business error in metrics
- In a 1.22+ loop still write clear local copies when review wants explicitness

## Practical scenario

A checkout service calls inventory, payment, antifraud. Previously sequential (~600 ms). Moved to three `go` without context. Under load test memory grows: clients abort, and goroutine still wait for slow responses.

Fix: `errgroup.WithContext(r.Context())`, 800 ms timeout on the request, all HTTP clients with `NewRequestWithContext`. Goroutine count stabilizes. P99 drops because of overlap; client abandonment actually stops the work.

## Check questions

1. **Why does `go f()` not return a result?**  
   The statement only starts execution; you must explicitly pass the result.

2. **What is a goroutine leak?**  
   A goroutine that never finishes (e.g. blocked receive without a sender) and holds resources even though the job was abandoned.

3. **Does context itself stop the work?**  
   No. Code must listen to `Done` or pass `ctx` to an API that does. A goroutine is not a thread that the OS “kills” via context.

4. **What does errgroup return from `Wait`?**  
   The first error from the group (or `nil`).

5. **Why `defer cancel()`?**  
   Frees context-tree resources as soon as the function exits.

6. **Why Add before go?**  
   So `Wait` does not see zero too early.

7. **What changes for loop + closure in Go 1.22+?**  
   A new loop variable per iteration; the closure captures that iteration.

## Checklist before `go` in a PR — continued

1. Is there a clear completion signal?
2. Does someone wait for the error or result?
3. Is the number of goroutine bounded?
4. Does a test cover cancellation?
5. Does the documentation say the function starts background work?

### Example — semaphore via channel

```go
func mapLimited(ctx context.Context, n int, items []string, fn func(context.Context, string) error) error {
	sem := make(chan struct{}, n)
	g, ctx := errgroup.WithContext(ctx)
	for _, it := range items {
		it := it
		sem <- struct{}{}
		g.Go(func() error {
			defer func() { <-sem }()
			return fn(ctx, it)
		})
	}
	return g.Wait()
}
```

#### What happens here

Buffer `n` = at most `n` concurrent `fn`. With errgroup: first error + cancellation. Bridge to the worker pool from 08.05.

`go` starts work, but does not return a result and does not cancel by itself. A leak is often a blocked receive without a sender. Context is a signal that code must listen to. errgroup combines waiting, the first error, and cancellation. Always: completion plan, bound under peak, `defer cancel()`. Next: `sync` tools.
