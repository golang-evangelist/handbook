# 08.05 Concurrency patterns: pipeline, fan-out/in, worker pool

> **Go Path - Zero to Gopher** / **02 Intermediate → Concurrent Programming with Go** / Lesson 08.05

## Lesson goals

After this lesson you can:

- assemble a **pipeline** of stages connected by channels
- apply **fan-out** (multiple workers) and **fan-in** (merging results)
- build a **worker pool** with a limited number of goroutine
- explain **why a bound exists**: unbounded goroutine consume memory to collapse
- wire **cancellation** through the whole graph (`context` / `close` of the input channel)
- recognize which pattern fits which problem

## Prerequisite

- Lessons 08.01–08.04 (goroutine, sync, channel, select, context)
- Preferred errgroup intro from 08.02
- Go 1.22+ (loop + `go` + closure)

## Problem this lesson solves

Knowing `go` and `chan` is not the same as knowing the *shape* of a program. Without patterns teams:

- start one goroutine per item without a limit → collapse under peak
- build a chain without backpressure → memory balloon
- forget cancellation → work after timeout

This lesson gives three classic shapes: pipeline, fan-out/in, worker pool.

## Mental model

1. **Pipeline** — a sequence of stages: one’s output is the next’s input.
2. **Fan-out** — one input stream is split across multiple workers.
3. **Fan-in** — multiple streams merge into one (merge).
4. **Worker pool** — a fixed number of workers pull from a shared `jobs` channel.
5. **Cancellation** — the same `ctx` or `close` of the input channel so all stages stop.

Choose:

- pipeline when processing is **staged** (parse → transform → save)
- worker pool when processing is the **same** over many independent items
- fan-out/in when you want parallelism inside one stage

### Why a bounded pool exists

```text
Unbounded:
  100_000 items → 100_000 goroutine
  each ~2KB+ stack at start → hundreds of MB just for stacks
  + scheduler + heap objects → OOM / thrashing

Bounded (N=8):
  100_000 items → 8 goroutine
  memory stable; work goes through jobs channel (backpressure)
```

A bound is not “slowness” — it is process protection.

## Mechanism

### Pipeline

```text
source → stageA → stageB → sink
```

Each stage:

1. reads an input `<-chan`
2. writes an output `chan<-`
3. **closes the output** when the input ends or `ctx` cancels
4. has **one** close owner for its output

Trace of one element `n=3` through squaring then `+1`:

```text
gen sends 3 on out1 (may block if unbuffered and stageA is not ready)
stageA receives 3, sends 9 on out2
stageB receives 9, sends 10 on out3
sink receives 10
gen closes out1 → stageA range stops → closes out2 → ...
```

Backpressure: a slow sink slows the whole chain because send blocks when there is no receive (buffer 0) or when the buffer is full.

### Fan-out / fan-in

**Fan-out:** start N copies of the same stage over the same input (or split the work).

**Fan-in:** merge N outputs into one (`merge` with the nil trick from 08.04, or WaitGroup + one output channel).

Trace fan-out N=2:

```text
jobs: 1,2,3,4
W1 takes 1, W2 takes 2, W1 takes 3, W2 takes 4
results arrive in any order
```

If you need order, add indexes or do not parallelize that stage.

### Worker pool

```text
producer → jobs chan (buffer optional) → worker×N → results chan → consumer
```

```go
jobs := make(chan Job)
results := make(chan Result)

// N workers
for w := 0; w < N; w++ {
	go func() {
		for j := range jobs {
			results <- process(j)
		}
	}()
}
```

Trace with N=2, 5 jobs:

```text
1. 2 workers block on <-jobs (empty)
2. producer sends J1 → one worker takes it
3. ...
4. producer close(jobs)
5. range jobs in workers stops; workers exit
6. someone must close(results) after all workers finish (WaitGroup)
```

Choose **N** by CPU, database limit, or external rate limit — not “the more the better”.

### Cancellation through the graph

Three ways (often combined):

1. Close the input → the pipeline drains naturally.
2. `ctx.Done()` in every `select` with receive/send.
3. `errgroup.WithContext` for task trees.

Cancellation trace mid-pool:

```text
ctx cancelled
worker in select: case j := <-jobs / case <-ctx.Done()
picks Done → return
producer also watches ctx and stops sending
```

Without that: workers stay on `<-jobs` or on slow `process` after the client no longer waits.

### Go 1.22+ in a worker loop

```go
for i := range N {
	go func() {
		id := i // in 1.22+ i is per-iteration; id clear for logs
		worker(id)
	}()
}
```

## Rules and syntax

1. One owner closes each channel.
2. Do not close `jobs` while the producer still sends.
3. Limit `N` explicitly — never “goroutine per item” without a bound in a server.
4. Pass `ctx` into every stage.
5. Do not lose errors: err channel, errgroup, or abort the whole pipeline.
6. Close `results` only when all workers finish (WaitGroup).

## Examples

### Example 1 — Small pipeline

```go
package main

import "fmt"

func gen(nums ...int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		for _, n := range nums {
			out <- n
		}
	}()
	return out
}

func sq(in <-chan int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		for n := range in {
			out <- n * n
		}
	}()
	return out
}

func main() {
	for n := range sq(gen(2, 3)) {
		fmt.Println(n) // 4, 9
	}
}
```

#### What happens here

1. `gen` sends 2, then 3, then close.
2. `sq` receives 2 → sends 4; receives 3 → sends 9; close.
3. `main` range prints and exits.

Send can block on unbuffered `out` until the next stage receives — that is desired backpressure.

### Example 2 — Bounded worker pool

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	const workers = 3
	jobs := make(chan int)
	results := make(chan int)

	var wg sync.WaitGroup
	for w := 0; w < workers; w++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for j := range jobs {
				results <- j * 2
			}
		}()
	}

	go func() {
		wg.Wait()
		close(results)
	}()

	go func() {
		for i := 1; i <= 10; i++ {
			jobs <- i
		}
		close(jobs)
	}()

	for r := range results {
		fmt.Println(r)
	}
}
```

#### What happens here

Exactly 3 workers. 10 jobs pass through the same `jobs`. After `close(jobs)`, workers exit `range`; WaitGroup clears the path for `close(results)`; `main` range stops.

**Predict the result:** What if instead of 3 workers you do `go` for each of 10_000 jobs in an HTTP handler under peak?

**Answer:** Goroutine explosion → memory growth, possible OOM. That is why a bounded pool exists.

### Example 3 — Fan-out + fan-in

```go
package main

import (
	"fmt"
	"sync"
)

func fanOut(in <-chan int, n int) []<-chan int {
	outs := make([]<-chan int, n)
	for i := 0; i < n; i++ {
		out := make(chan int)
		outs[i] = out
		go func(out chan<- int) {
			defer close(out)
			for v := range in {
				out <- v * v
			}
		}(out)
	}
	return outs
}

func fanIn(chans ...<-chan int) <-chan int {
	out := make(chan int)
	var wg sync.WaitGroup
	wg.Add(len(chans))
	for _, ch := range chans {
		ch := ch
		go func() {
			defer wg.Done()
			for v := range ch {
				out <- v
			}
		}()
	}
	go func() {
		wg.Wait()
		close(out)
	}()
	return out
}

func main() {
	in := make(chan int)
	go func() {
		for i := 1; i <= 6; i++ {
			in <- i
		}
		close(in)
	}()
	for v := range fanIn(fanOut(in, 3)...) {
		fmt.Println(v)
	}
}
```

#### What happens here

Three workers share the same input (`range in` — each element goes to one worker). Three outputs merge. Result order is not sorted by input.

Note: multiple `range` on the same channel is valid fan-out; each value goes to exactly one receiver.

### Example 4 — Pool with context cancellation

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

func work(ctx context.Context, n int) (int, error) {
	select {
	case <-time.After(30 * time.Millisecond):
		return n * n, nil
	case <-ctx.Done():
		return 0, ctx.Err()
	}
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 80*time.Millisecond)
	defer cancel()

	jobs := make(chan int)
	go func() {
		defer close(jobs)
		for i := 1; i <= 20; i++ {
			select {
			case jobs <- i:
			case <-ctx.Done():
				return
			}
		}
	}()

	const N = 4
	results := make(chan int)
	var wg sync.WaitGroup
	for range N {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for {
				select {
				case <-ctx.Done():
					return
				case j, ok := <-jobs:
					if !ok {
						return
					}
					v, err := work(ctx, j)
					if err != nil {
						return
					}
					select {
					case results <- v:
					case <-ctx.Done():
						return
					}
				}
			}
		}()
	}
	go func() {
		wg.Wait()
		close(results)
	}()

	count := 0
	for range results {
		count++
	}
	fmt.Println("processed before timeout:", count)
}
```

#### What happens here

Timeout 80 ms; each job ~30 ms; 4 workers. Not all 20 finish. Context stops the producer and workers. Without `ctx` branches, the pool would continue after the caller gave up.

### Example 5 — Anti-pattern: goroutine per item

```go
// BAD in a server under peak
for _, item := range items {
	item := item
	go process(item)
}
```

#### What happens here

`len(items)` can be tens of thousands. The bound disappears. Fix: pool or semaphore `make(chan struct{}, N)`.

## Decision analysis

| Decision | Why |
|----------|-----|
| Pipeline | Stages, backpressure through the chain |
| Worker pool | Same work, controlled N |
| Fan-out/in | Parallelism inside a stage |
| Small buffer on jobs | Burst without losing backpressure |
| ctx in every stage | No work after abandonment |

## Trade-offs

- **Larger N** — more parallelism/I/O overlap; more pressure on DB/CPU/memory.
- **Smaller N** — more stable; longer wait queue.
- **Unbuffered jobs** — strong backpressure; more blocking.
- **Buffered jobs** — smoother burst; hides slowness if the buffer is huge.

## Common mistakes

1. **Wrong code:** `go process(x)` for every x without a limit.  
   **What happens:** OOM / thrashing.  
   **Why:** Unbounded goroutine consume memory.  
   **Fix:** Bounded worker pool.

2. **Wrong code:** `close(results)` right after `close(jobs)` without waiting for workers.  
   **What happens:** panic send on closed / lost results.  
   **Why:** Workers still send.  
   **Fix:** WaitGroup then close.

3. **Wrong code:** Pipeline without close on intermediate stages.  
   **What happens:** `range` forever.  
   **Why:** Range waits for close.  
   **Fix:** Each stage closes its out.

4. **Wrong code:** Ignored ctx in `process`.  
   **What happens:** Work after timeout.  
   **Why:** Cancellation is not thread interruption.  
   **Fix:** select on Done / pass ctx.

5. **Wrong code:** Expected order from fan-out without indexes.  
   **What happens:** Wrong result order.  
   **Why:** Workers finish asynchronously.  
   **Fix:** Indexes or a sequential stage.

6. **Wrong code:** Two close on the same channel from two stages.  
   **What happens:** panic.  
   **Why:** Close must have one owner.  
   **Fix:** One closer.

## Idiomatic Go

- Return `<-chan` from a stage function; hide the goroutine inside
- Document who closes
- Do not swallow errors
- Measure N (benchmark / load test) before you “guess”

## Practical scenario

Image resize service: one goroutine per upload. Black Friday: 50k uploads, OOM. Move to pool N=32 (limited by CPU and disk IO). Jobs channel buffer 64. Context from the HTTP request. P99 rises a little, but the service no longer falls. Later a profile (14.xx) shows N=32 is near optimal for their CPU.

## Check questions

1. **Why a bounded pool?**  
   Unbounded goroutine consume memory and can crash the process.

2. **Who closes results in a pool?**  
   A separate goroutine after the workers’ WaitGroup.

3. **What is pipeline backpressure?**  
   A slow sink blocks send along the chain.

4. **Does fan-out preserve order?**  
   No, unless you encode it explicitly.

5. **How to cancel a pool?**  
   context in select with jobs/results; the producer also listens.

6. **Pipeline vs pool?**  
   Stages vs the same work over many items.

## Deeper look: jobs channel capacity

```text
N=4 workers, jobs buffer=0:
  producer often blocks on send — strong backpressure

N=4, jobs buffer=1000, slow sink on results:
  jobs fill; memory grows; problem shifted downstream

Rule: buffer small relative to N * burst; measure heap
```

## Deeper mechanism: who closes what

```text
producer                workers×N              closer                consumer
   |                        |                     |                      |
   |---- jobs <- J -------->|                     |                      |
   |                        |---- results <- R -->|                      |
   |                        |                     |                      |
   | close(jobs)            |                     |                      |
   |                        | range jobs ends     |                      |
   |                        | Done() ×N --------->|                      |
   |                        |                     | Wait → close(results)|
   |                        |                     |                      |
   |                        |                     |   range results ends |
```

If the closer closes `results` before `Wait`, a worker still doing `results <- R` panics (send on closed). So order is part of the contract.

## Example 6 — Semaphore instead of a pool struct

```go
package main

import (
	"context"
	"fmt"
	"sync"

	"golang.org/x/sync/errgroup"
)

func mapLimited(ctx context.Context, n int, items []int, fn func(context.Context, int) error) error {
	sem := make(chan struct{}, n)
	g, ctx := errgroup.WithContext(ctx)
	for _, it := range items {
		it := it
		g.Go(func() error {
			select {
			case sem <- struct{}{}:
			case <-ctx.Done():
				return ctx.Err()
			}
			defer func() { <-sem }()
			return fn(ctx, it)
		})
	}
	return g.Wait()
}

func main() {
	var mu sync.Mutex
	active := 0
	maxActive := 0
	err := mapLimited(context.Background(), 3, make([]int, 20), func(ctx context.Context, n int) error {
		mu.Lock()
		active++
		if active > maxActive {
			maxActive = active
		}
		mu.Unlock()
		mu.Lock()
		active--
		mu.Unlock()
		return nil
	})
	fmt.Println(err, "maxActive", maxActive) // maxActive ≤ 3
}
```

#### What happens here

Buffer `sem` of capacity 3 allows at most three concurrent `fn`. That is the same bound principle as a worker pool, without long-lived workers. A pool is better when worker setup is expensive; a semaphore is shorter for one-shot batches.

**Predict the result:** What if `n=0` for the semaphore capacity?

**Answer:** `make(chan struct{}, 0)` — unbuffered. The first `sem <- struct{}{}` blocks until someone does `<-sem`, but nobody holds a slot → deadlock (or block forever). The bound must be ≥ 1.

## Checklist before production pool

1. N explicit (config or constant), not `len(items)`.
2. `close(jobs)` only from the producer, once.
3. `close(results)` after workers’ WaitGroup.
4. Every stage watches `ctx.Done()`.
5. Errors go to errgroup or err channel — not only `fmt.Println`.
6. Load test: peak items >> N; memory stable.

## One more trace: unbounded fan-out in a handler

```go
func (h *H) ServeHTTP(w http.ResponseWriter, r *http.Request) {
	ids := parseIDs(r) // may be 10_000
	var wg sync.WaitGroup
	for _, id := range ids {
		wg.Add(1)
		go func(id string) {
			defer wg.Done()
			_, _ = h.client.Get(r.Context(), id)
		}(id)
	}
	wg.Wait()
}
```

What happens under peak 100 requests × 10_000 ids = a million goroutine. Fix: `mapLimited` / pool with N=32 inside the handler, or limit `len(ids)` at the input.

**Predict the result:** Does `r.Context()` alone fix OOM?

**Answer:** No. Context cancels work, but by the time cancellation arrives you may already have started a huge number of goroutine. The bound must exist *before* `go`.

## When pipeline, when pool — decision in one table

| Question | Pipeline | Worker pool |
|----------|----------|-------------|
| Does the work have stages? | Yes | Rarely |
| Same function over N items? | Rarely | Yes |
| Where does the bound live? | Per stage (1..K goroutine) | Fixed N workers |
| Backpressure | Channel chain | Full `jobs` buffer / blocked send |

Both patterns can use `context`. Both require one `close` owner per channel.

If unsure: start with a **worker pool** and one stage. Add a pipeline when measurement shows stages have different speeds and benefit from pipeline parallelism.

After a load test record: N, queue length on `jobs`, P99, peak goroutine. Without those four numbers you do not know whether the bound is good.

A pipeline connects stages with channels with close and backpressure. Fan-out/in parallelizes inside a stage. A worker pool with fixed N protects memory — that is why a bound exists. Context is passed through the whole graph. Next: race, errgroup, singleflight, pprof.
