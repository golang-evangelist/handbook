# 08.03 The sync package: WaitGroup, Mutex, Once, and friends

> **Go Path - Zero to Gopher** / **02 Intermediate → Concurrent Programming with Go** / Lesson 08.03

## Lesson goals

After this lesson you can:

- synchronize the end of a group of goroutine with **WaitGroup** (`Add` before `go`, `Done` in `defer`, `Wait`)
- protect shared state with **Mutex** (`Lock` / `Unlock` with `defer`)
- explain what a **data race** is and why without synchronization behavior is **undefined**
- use the race detector: `go test -race` or `go run -race`
- choose **atomic** for a simple counter versus Mutex for a **struct** with multiple fields
- initialize a resource once via **Once**
- know when to mention RWMutex, Cond, and `sync.Map`

## Prerequisite

- Lessons 08.01–08.02
- Basic **struct** types and **pointer**
- Understanding that two goroutine can access the same memory

## Problem this lesson solves

A channel is excellent for flows. For an in-memory cache, a metrics counter, or a session map, a channel often feels artificial. The `sync` package gives primitive tools for that class of problems.

Without them:

- `map` panics / corrupted data under a race
- `main` finishes before workers
- “lazy init” runs twice and opens two connections to the database

The goal is not to lock everything — the goal is to know *what* you protect and *how long* you hold the lock.

## Mental model

Imagine a shared structure as a room with one key (**Mutex**) or a key for readers and a writer (**RWMutex**).

- **WaitGroup** is a counter of unfinished tasks: `Add` before `go`, `Done` at the end, `Wait` blocks until it drops to zero.
- **Once** guarantees a function runs at most once, even if called in parallel.
- **atomic** changes simple counters without a Mutex when you need only a number, not a multi-field invariant.
- **sync.Map** is a specialized map for certain patterns — not the default replacement for `map` + Mutex.
- **Cond** is an advanced signal “wait until the condition changes” — rarely first.

**Data race:** two accesses to the same variable, at least one is a write, without synchronization. Without synchronization behavior is **undefined**. Do not invent rules like “in practice it works on x86”. Detector: `go test -race` / `go run -race`.

## Mechanism

### WaitGroup — order is part of the contract

```text
Add(n) → start n goroutine → each Done() → Wait() continues
```

```go
var wg sync.WaitGroup
wg.Add(1) // REQUIRED before go
go func() {
	defer wg.Done()
	work()
}()
wg.Wait()
```

Trace of the correct order:

```text
1. Add(1) → counter = 1
2. go ... scheduled
3. Wait sees 1 → blocks
4. work finishes → Done → counter = 0
5. Wait unblocks
```

Trace of the wrong order (`Add` inside):

```text
1. go scheduled (has not started yet)
2. Wait sees 0 → returns IMMEDIATELY
3. only then Add(1) — too late
4. main thinks it is done; work is still running
```

Do not copy WaitGroup by value after use — keep it as a field in a struct.

### Mutex — critical section

```go
var mu sync.Mutex
var balance int

mu.Lock()
defer mu.Unlock()
balance++
```

Trace of two goroutine without Mutex (race):

```text
balance = 0
G1 reads 0
G2 reads 0
G1 writes 1
G2 writes 1
result 1 instead of 2 — or worse, undefined
```

With Mutex:

```text
G1 Lock → reads 0 → writes 1 → Unlock
G2 Lock → reads 1 → writes 2 → Unlock
result 2
```

Rules:

1. Always `Unlock` in `defer` after a successful `Lock` (except when you explicitly unlock earlier with great care).
2. Critical section **short**: do not do network I/O while holding the lock if you can extract data and only then send.
3. The same Mutex must protect all fields that form one invariant.

### What a race is — without invented memory-model rules

Definition for this course:

- two accesses to the same variable
- at least one write
- no synchronization (Mutex, channel, atomic, etc.)

**Without synchronization, a race is undefined behavior.** It is detected with:

```bash
go test -race ./...
go run -race .
```

Do not claim “it works on my laptop so it is OK”. The race detector in CI is proof, not a stylistic warning.

### atomic vs Mutex

```go
var n atomic.Int64
n.Add(1) // counter
```

Use atomic when:

- you change **one** number
- you have no invariant “field A and field B must be consistent together”

Use Mutex when:

```go
type Account struct {
	mu      sync.Mutex
	balance int
	version int
}

func (n *Account) Credit(x int) {
	n.mu.Lock()
	defer n.mu.Unlock()
	n.balance += x
	n.version++
}
```

Two fields must be updated together — atomic on one number does not preserve that invariant.

Do not mix atomic and ordinary access to the same data.

### RWMutex

- `RLock` / `RUnlock` for readers (many at once)
- `Lock` / `Unlock` for writers (exclusive)

When contention is low, an ordinary Mutex is often equally good and simpler — measure before you complicate.

### Once

```go
var once sync.Once
var client *Client

func K() *Client {
	once.Do(func() {
		client = connect()
	})
	return client
}
```

`Do` blocks others until the first finishes; later calls are no-ops. If `connect()` can fail, Once does **not** retry automatically — store `error` explicitly in the design.

### sync.Map

Use when:

- a key is written once, read often; or
- goroutine mostly work on disjoint keys

Otherwise: `map[K]V` + Mutex is more readable and often faster.

### Cond (brief)

`sync.Cond` signals “the condition changed” while holding a Mutex. For most early cases a channel or checking a condition in a loop with a Mutex is enough. Do not learn Cond as the first tool.

## Rules and syntax

```go
var mu sync.Mutex
mu.Lock()
defer mu.Unlock()
```

```go
var wg sync.WaitGroup
wg.Add(1)
go func() {
	defer wg.Done()
	work()
}()
wg.Wait()
```

```go
var once sync.Once
once.Do(func() { initResource() })
```

- Do not copy WaitGroup, Mutex, Once by value after first use.
- Pass `*T` (pointer to a struct that contains Mutex), not a struct value.
- Zero value Mutex/WaitGroup/Once is ready for use — no constructor needed.

## Examples

### Example 1 — WaitGroup correctly

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var wg sync.WaitGroup
	for i := range 5 {
		wg.Add(1)
		go func(n int) {
			defer wg.Done()
			fmt.Println(n)
		}(i)
	}
	wg.Wait()
	fmt.Println("done")
}
```

#### What happens here

Five `Add(1)` before the corresponding `go`. `Wait` blocks until all five do `Done`. Numbers print in any order, then `done`.

### Example 2 — Mutex protects a map

```go
package main

import (
	"fmt"
	"sync"
)

type Store struct {
	mu sync.Mutex
	m  map[string]int
}

func (s *Store) Inc(k string) {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.m[k]++
}

func main() {
	s := &Store{m: make(map[string]int)}
	var wg sync.WaitGroup
	for range 1000 {
		wg.Add(1)
		go func() {
			defer wg.Done()
			s.Inc("a")
		}()
	}
	wg.Wait()
	fmt.Println(s.m["a"]) // 1000
}
```

#### What happens here

Without Mutex: race on `map` — often panic “concurrent map writes”. With Mutex: all 1000 increments serialized; result 1000.

### Example 3 — Race detector catches the bug

```go
package counter

import "testing"

func TestRace(t *testing.T) {
	var n int
	done := make(chan struct{}, 2)
	go func() { n++; done <- struct{}{} }()
	go func() { n++; done <- struct{}{} }()
	<-done
	<-done
	t.Log(n)
}
```

Run: `go test -race ./...`

#### What happens here

The detector reports a race on `n`. Without `-race` the test may “pass” with a wrong `n`. Fix: `atomic.Int64` or Mutex.

**Predict the result:** If you replace `n` with `atomic.Int64` and `Add(1)`, does `-race` still complain?

**Answer:** No, if all accesses go through the atomic API. Mixing `n.Load()` with ordinary reading of the same memory another way can still be a race.

### Example 4 — atomic counter vs Mutex struct

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
)

func main() {
	var hits atomic.Int64
	var wg sync.WaitGroup
	for range 1000 {
		wg.Add(1)
		go func() {
			defer wg.Done()
			hits.Add(1)
		}()
	}
	wg.Wait()
	fmt.Println(hits.Load())
}
```

#### What happens here

One counter — atomic is enough. If along with `hits` you also had to update `lastIP string` atomically together, move to Mutex around both fields.

### Example 5 — Once init

```go
package main

import (
	"fmt"
	"sync"
)

var (
	once sync.Once
	cfg  string
)

func load() string {
	once.Do(func() {
		fmt.Println("loading")
		cfg = "prod"
	})
	return cfg
}

func main() {
	var wg sync.WaitGroup
	for range 10 {
		wg.Add(1)
		go func() {
			defer wg.Done()
			fmt.Println(load())
		}()
	}
	wg.Wait()
}
```

#### What happens here

`loading` prints exactly once. All 10 calls get `"prod"`.

### Example 6 — Copying a Mutex (trap)

```go
type Bad struct {
	mu sync.Mutex
	n  int
}

func (b Bad) Inc() { // VALUE receiver — copies Mutex
	b.mu.Lock()
	defer b.mu.Unlock()
	b.n++
}
```

#### What happens here

Each `Inc` call copies the struct, and thus the Mutex. Locking the copy does not protect the original `n`. Fix: `func (b *Bad) Inc()` — pointer receiver.

## Decision analysis

| Decision | Why |
|----------|-----|
| WaitGroup for completion | Simple counter without error frameworks |
| errgroup when there is an error | First error + cancellation (08.02) |
| Mutex for struct invariants | Multiple fields together |
| atomic for a counter | Less contention, simple API |
| map+Mutex instead of sync.Map | Readability; sync.Map only for a special pattern |
| -race in CI | A race is a real bug |

## Trade-offs

- **Short critical section** — better throughput; needs more design (copy then work outside).
- **Long critical section** — simpler; contention and latency grow.
- **RWMutex** — useful when there is really a lot of reading; otherwise complexity without gain.
- **atomic** — fast for a number; does not preserve multi-field invariants.

## Common mistakes

1. **Wrong code:** `go func() { wg.Add(1); ... }()`  
   **What happens:** `Wait` returns too early.  
   **Why:** Race Add/Wait.  
   **Fix:** `Add` before `go`.

2. **Wrong code:** Forgotten `Unlock` (no `defer`).  
   **What happens:** Deadlock — everyone waits for the lock.  
   **Why:** A path with `return`/`panic` skips Unlock.  
   **Fix:** `defer mu.Unlock()` right after Lock.

3. **Wrong code:** Two goroutine write a `map` without Mutex.  
   **What happens:** Panic or corruption; `-race` complains.  
   **Why:** `map` is not safe for parallel writes.  
   **Fix:** Mutex or channel ownership.

4. **Wrong code:** `func (s Store) Inc()` with Mutex inside.  
   **What happens:** The race remains.  
   **Why:** Mutex copy.  
   **Fix:** Pointer receiver.

5. **Wrong code:** atomic on `balance` and a separate write to `version` without locks.  
   **What happens:** A reader sees half-updated state.  
   **Why:** Two fields are not one atomic operation.  
   **Fix:** One Mutex around both.

6. **Wrong code:** “Works on my PC” without `-race`.  
   **What happens:** Intermittent bug in production.  
   **Why:** A race is undefined.  
   **Fix:** `go test -race` in CI.

## Idiomatic Go

- Zero value of sync types is usable
- Mutex as a field; methods with pointer receiver
- `defer Unlock`
- Do not export Mutex without need; export methods that protect invariants
- Document whether a method may be called concurrently

## Practical scenario

A metrics package has `map[string]int` for counters. Under load test: `fatal error: concurrent map writes`. The team adds Mutex around every `++`. Panic disappears, but P99 jumps because Mutex holds I/O logging inside.

Fix: critical section only `m[k]++`; logging after Unlock. For a hot counter they move to `atomic.Int64` per key where that is enough. `-race` stays in CI.

## Deeper trace: critical section too long

```go
mu.Lock()
row := db.QueryRowContext(ctx, "SELECT ...") // BAD: I/O under the lock
_ = row
balance++
mu.Unlock()
```

Trace under load:

```text
1. G1 takes Lock, enters DB round-trip (50 ms)
2. G2..G100 wait on Lock — the queue grows
3. P99 latency jumps even though CPU is low
4. Fix: read data under Lock (map), release Unlock, then I/O
```

Correct form:

```go
mu.Lock()
v := s.m[id]
mu.Unlock()
// I/O or slow processing outside the lock
_ = v
```

## Deeper trace: WaitGroup with error (why errgroup)

```go
var (
	wg  sync.WaitGroup
	mu  sync.Mutex
	err error
)
for _, u := range urls {
	wg.Add(1)
	go func(u string) {
		defer wg.Done()
		if e := fetch(u); e != nil {
			mu.Lock()
			if err == nil {
				err = e
			}
			mu.Unlock()
		}
	}(u)
}
wg.Wait()
```

What is missing: other `fetch` continue after the first error; no cancellation. errgroup.WithContext solves that in one pattern (08.02). WaitGroup remains good when error is not the topic.

## Mini example: RWMutex reading

```go
package main

import (
	"fmt"
	"sync"
)

type Cache struct {
	mu sync.RWMutex
	m  map[string]string
}

func (c *Cache) Get(k string) (string, bool) {
	c.mu.RLock()
	defer c.mu.RUnlock()
	v, ok := c.m[k]
	return v, ok
}

func (c *Cache) Set(k, v string) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.m[k] = v
}

func main() {
	c := &Cache{m: map[string]string{"a": "1"}}
	var wg sync.WaitGroup
	for range 50 {
		wg.Add(1)
		go func() {
			defer wg.Done()
			_, _ = c.Get("a")
		}()
	}
	wg.Add(1)
	go func() {
		defer wg.Done()
		c.Set("a", "2")
	}()
	wg.Wait()
	v, _ := c.Get("a")
	fmt.Println(v)
}
```

#### What happens here

Many readers can hold `RLock` at once. A writer waits for exclusive `Lock`. If writes are frequent, RWMutex does not help — measure.

**Predict the result:** What if `Get` uses `Lock` instead of `RLock`, and there are 1000 pure reads?

**Answer:** Still correct, but reads serialize. You lose potential read parallelism. For a read-heavy cache RWMutex can help; for write-heavy an ordinary Mutex is clearer.

## Checklist before merge

1. Every `go` has `Add` before it when you use WaitGroup.
2. Every `Lock` has `defer Unlock` (or clear pairing).
3. No copying a struct with Mutex by value.
4. `go test -race` passes for the package.
5. The critical section does not do network I/O.
6. atomic is not mixed with ordinary access to the same field.

## One more prediction

**Predict the result:** Two goroutine: one does `n.Add(1)` on `atomic.Int64`, the other does ordinary `fmt.Println(n)` where `n` is the same field cast wrongly / read as an ordinary int via unsafe access. Is that safe?

**Answer:** No. All accesses to the same data must go through the same sync mechanism (atomic API). Mixing atomic and non-atomic access is still a race.

## Mechanism — WaitGroup: full trace with numbers

### Counter state as a table

`WaitGroup` internally holds a counter. `Add(delta)` changes the counter by `delta` (usually positive before `go`, negative via `Done` which is `Add(-1)`). `Wait` blocks until the counter is 0.

Correct flow with three workers:

| Step | Who | Call | Counter after | Wait state |
|------|-----|------|---------------|------------|
| 1 | main | `Add(1)` | 1 | not called yet |
| 2 | main | `go G1` | 1 | — |
| 3 | main | `Add(1)` | 2 | — |
| 4 | main | `go G2` | 2 | — |
| 5 | main | `Add(1)` | 3 | — |
| 6 | main | `go G3` | 3 | — |
| 7 | main | `Wait()` | 3 | **blocked** |
| 8 | G1 | `Done()` | 2 | still blocked |
| 9 | G3 | `Done()` | 1 | still blocked |
| 10 | G2 | `Done()` | 0 | **unblocked** |
| 11 | main | continues | 0 | done |

**Predict:** If in step 1 instead of three `Add(1)` you do once `Add(3)` before a loop that starts three `go`, is the counter the same at the end?

**Answer:** Yes — `Add(3)` at once sets the counter to 3 before any `go`. That is even more readable when you know the exact task count ahead. Important: `Add` must still be **before** `Wait` and before (or at least before `Wait` can see zero while work is not finished) — practice: all `Add` finished before `Wait`, and each `Add` tied to a goroutine finished before the corresponding `go` or at least before that goroutine can do `Done`.

### Wrong trace: `Add` inside the goroutine

```go
var wg sync.WaitGroup
go func() {
	wg.Add(1) // TOO LATE
	defer wg.Done()
	work()
}()
wg.Wait() // often sees 0 immediately
```

| Step | Event | Counter | Consequence |
|------|-------|---------|-------------|
| 1 | `go` scheduled | 0 | worker has not started |
| 2 | `Wait()` | 0 | **returns immediately** |
| 3 | main thinks it is done | 0 | may exit `main` |
| 4 | only now `Add(1)` | 1 | too late |
| 5 | `Done()` | 0 | work may be cut with the program |

Behavior is not “sometimes works” as a contract — it depends on scheduling. On a fast CPU `Add` inside may arrive before `Wait` (test “passes” locally); in CI with `-race` or under load — failure. So the rule is not stylistic: **`Add` before `go`**.

### `Add` with a negative number and panic

```go
wg.Add(1)
wg.Done()
wg.Done() // Add(-1) when counter is 0 → panic
```

**Predict:** What happens?

**Answer:** `sync: negative WaitGroup counter` — panic. Same if you do more `Done` than `Add`, or `Add(-1)` manually before the counter allows it.

### Copying WaitGroup

```go
func start(wg sync.WaitGroup) { // BY VALUE — bad
	wg.Add(1)
	go func() {
		defer wg.Done()
	}()
}
```

The copy has its **own** counter. `Done` on the copy does not wake `Wait` on the original. Fix: `*sync.WaitGroup` or WaitGroup as a field in a struct passed via pointer.

## Mechanism — Mutex: full trace with two goroutine

### Without Mutex — race on `int`

Initial: `balance = 0`. G1 and G2 both do `balance++` (which is read-add-write, not one CPU instruction from the Go contract perspective).

```text
Time →
G1:  load balance → 0
G2:  load balance → 0
G1:  store 1
G2:  store 1
End: balance = 1   ← lost increment
```

Another possible schedule (still a wrong contract, just a different number):

```text
G1: load 0, store 1
G2: load 1, store 2
End: 2  ← “looks OK” but it is still a race
```

The second schedule does **not** prove correctness. The race detector still complains because concurrent accesses exist without synchronization. “Works on my laptop” is one of possible undefined outcomes, not proof.

### With Mutex — serialization

```text
G1: Lock  (success, mu taken)
G1: load 0, store 1
G1: Unlock
G2: Lock  (was waiting, now success)
G2: load 1, store 2
G2: Unlock
End: 2  — and the contract is defined
```

### Mutex around `map`

```go
type Store struct {
	mu sync.Mutex
	m  map[string]int
}

func (s *Store) Inc(k string) {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.m[k]++
}
```

Without Mutex, parallel write to `map` often ends with:

```text
fatal error: concurrent map writes
```

or silent corruption. `-race` also catches read+write without locks.

**Predict:** G1 holds Lock and does `time.Sleep(5 * time.Second)` inside. G2 calls `Inc`. What does G2 do?

**Answer:** Blocks on `Lock` until G1 does `Unlock` — up to 5 seconds. That is why the critical section must be short: do not sleep, do not do HTTP, do not read disk while holding the lock if you can extract data and work outside.

### Defer Unlock and early return

```go
func (s *Store) Set(k string, v int) error {
	s.mu.Lock()
	defer s.mu.Unlock()
	if k == "" {
		return fmt.Errorf("empty key") // Unlock still runs via defer
	}
	s.m[k] = v
	return nil
}
```

Without `defer`, `return` on error leaves the lock taken → deadlock for all following calls.

## Mechanism — what a race is, precisely

### Definition (for this course)

A **data race** exists when:

1. two or more goroutine access the **same** variable (same memory location),
2. at least one access is a **write**,
3. there is no **synchronization** that orders them (Mutex, channel send/receive synchronized with those accesses, `sync/atomic`, a `WaitGroup` signal that establishes happens-before, etc.).

Consequence in Go: program behavior is **undefined**. Not “wrong number”, not “eventually consistent” — undefined. The compiler and CPU may reorder accesses in ways your single-threaded intuition does not predict.

### What is NOT (only) a race

- Two goroutine read the same variable, **nobody writes** → not a data race (can still be a logic bug if you expect a fresh write from a third party).
- Synchronization via channel: `ch <- x` in G1 and `y := <-ch` in G2 order the sequence — after receive, G2 may read data G1 prepared before send.
- `atomic.AddInt64` + only atomic API on that location → not a race on that counter.

### How the detector works (intuition)

```bash
go test -race ./...
go run -race .
```

A build with `-race` instruments memory accesses. At runtime it tracks whether a conflict exists without synchronization. It is slower (often 2–20×) and uses more memory — so in CI on unit/integration tests, not necessarily on every local `go run` of a microservice under load.

**Predict:** A test without `-race` passes 1000 times. With `-race` it fails once. Is that a flaky test or a real bug?

**Answer:** Real bug (race). Flaky is only a symptom — the fix is synchronization, not “rerun the test until it passes”.

### Minimal example that `-race` catches

```go
func TestRace(t *testing.T) {
	var n int
	var wg sync.WaitGroup
	wg.Add(2)
	go func() { defer wg.Done(); n++ }()
	go func() { defer wg.Done(); n++ }()
	wg.Wait()
	t.Log(n) // may be 0, 1, or 2 — undefined
}
```

WaitGroup here synchronizes the **end** of goroutine with `Wait`, but does **not** protect the `n++` accesses against each other. So a race still exists on `n`.

## Example 7 — WaitGroup + Mutex together (correct pattern)

```go
package main

import (
	"fmt"
	"sync"
)

type Counter struct {
	mu sync.Mutex
	n  int
}

func (b *Counter) Inc() {
	b.mu.Lock()
	defer b.mu.Unlock()
	b.n++
}

func (b *Counter) Get() int {
	b.mu.Lock()
	defer b.mu.Unlock()
	return b.n
}

func main() {
	var wg sync.WaitGroup
	b := &Counter{}
	for range 100 {
		wg.Add(1)
		go func() {
			defer wg.Done()
			b.Inc()
		}()
	}
	wg.Wait()
	fmt.Println(b.Get()) // 100
}
```

#### What happens here

WaitGroup guarantees `main` does not print before all 100 finish. Mutex guarantees `Inc` does not run in parallel on `n`. Both tools do **different** jobs — one does not replace the other.

**Predict:** Remove Mutex, leave WaitGroup. Does `Wait` wait for all 100 to finish?

**Answer:** Yes — WaitGroup still works. But `n` at the end is not reliably 100 (race). Synchronizing completion ≠ synchronizing data.

## Example 8 — Deadlock trace with Mutex

```go
var mu sync.Mutex

func f() {
	mu.Lock()
	g() // g also calls mu.Lock
	mu.Unlock()
}

func g() {
	mu.Lock() // waits for itself / same goroutine — deadlock
	mu.Unlock()
}
```

`sync.Mutex` is not reentrant (the same goroutine cannot lock it twice). Fix: do not call methods that take the same lock again while you already hold it; extract a private `lockedFoo()` that assumes the lock is already taken.

## Example 9 — RWMutex trace (read vs write)

```text
G1: RLock  (reader 1)
G2: RLock  (reader 2) — allowed with G1
G3: Lock   (writer) — WAITS until all RUnlock
G1: RUnlock
G2: RUnlock
G3: Lock success — exclusive
```

When almost all accesses are writes, RWMutex does not help — an ordinary Mutex is simpler.

## Common mistakes — extended

7. **Wrong code:** WaitGroup protects `n++` “because Wait waits for the end”.  
   **What happens:** Race on `n` remains.  
   **Why:** WaitGroup only orders “everyone is done”, not mutual access during work.  
   **Fix:** Mutex or atomic for `n`.

8. **Wrong code:** `Add` in a loop after `go` in the same iteration in the wrong order.  
   **What happens:** Intermittent early `Wait`.  
   **Fix:** In the iteration: first `Add(1)`, then `go`.

9. **Wrong code:** Hold Mutex during `http.Get`.  
   **What happens:** All other goroutine stand on Lock while the network runs.  
   **Fix:** Under Mutex only read/write state; do the network outside the lock.

10. **Wrong code:** You ignore `-race` in CI “because it slows things down”.  
    **What happens:** A race reaches production.  
    **Fix:** `-race` on the test job; if needed a nightly full suite if the daily one is too short.

## Check questions — additional

7. **Why does WaitGroup not remove the need for Mutex on a shared `n`?**  
   Because it only orders group completion, not mutual exclusion of access during execution.

8. **What exactly does `Done` do?**  
   Equivalent to `Add(-1)` — decreases the counter; when it reaches 0, wakes `Wait`.

9. **Why is “result 2 without Mutex” still a bug?**  
   Because that is one of possible undefined outcomes; another schedule gives 1; the detector still reports a race.

10. **May zero value `var mu sync.Mutex` be used immediately?**  
    Yes — zero value is unlocked, ready Mutex.

11. **What happens if `Unlock` without `Lock`?**  
    Panic: `sync: unlock of unlocked mutex`.

12. **How can a channel remove a race without Mutex?**  
    One goroutine “owner” of the data receives messages and alone mutates state — no shared write.

## Summary

WaitGroup: Add before go, Done in defer, Wait. Mutex: short section, defer Unlock, pointer receiver. A race without synchronization is undefined — measure with the detector. Atomic for a counter; Mutex for a struct. Once for one-time init. Next: channel rules.
