# 08.04 Channel: buffer, direction, close, select, and the nil trick

> **Go Path - Zero to Gopher** / **02 Intermediate → Concurrent Programming with Go** / Lesson 08.04

## Lesson goals

- Choose an **unbuffered** versus **buffered** channel deliberately, not “by feel”.
- Use type **direction** (`chan<-`, `<-chan`) at API boundaries so the compiler preserves the contract.
- Apply strict **close** rules: who closes, what panics, what returns the zero value.
- Write **select** for multiple communications, timeout, and cancellation via `ctx.Done()`.
- Understand a **nil channel** as a way to disable a select case forever until you replace it.
- Connect channel with **context**, `for range`, and directional types into one production mental model.

## Prerequisite

- Lessons 08.01–08.03: goroutine, Mutex, WaitGroup, Once, basic sync.
- Basic types, `for range`, `defer`, `error`, `struct`.
- Understanding that a goroutine is **not** a thread and **not** a process: it is a lightweight concurrency unit scheduled by the Go runtime.

## Problem this lesson solves

A channel looks like a “queue”, so beginners:

- close from both ends or close more than once → panic;
- treat the buffer as magical performance tuning;
- block forever because nobody receives, and send sits on an unbuffered channel;
- forget that `range` on a channel exits only on `close`;
- send on a closed channel and think that is an “end signal”;
- treat the zero value after close as valid data because they did not check `ok`.

This lesson establishes a channel as **typed synchronization + value transfer**, not as a universal buffer for everything. The goal is not to “know the syntax”, but to predict blocking, panic, and life-cycle before you run the code.

## Mental model

**channel** — a typed medium through which goroutine send and receive values; on this path we always write *channel*, never a translation as a substitute for the type. **select** — a statement that waits on one of several channel cases. **zero value** — the default value of a type (for `int` it is `0`, for a pointer `nil`, for `string` `""`). **context** — the package and value that carries cancellation, deadline, and request-scoped values. **closure** — a function that closes over surrounding variables. **slice** / **map** / **pointer** / **struct** / **interface** / **method** / **receiver** / **package** / **module** — remain English terms; the first mention here serves as a gloss.

- **Unbuffered** (`make(chan T)`): sender and receiver **meet** — rendezvous. Synchronization is built in. Capacity is 0: send blocks until there is a receiver.
- **Buffered** (`make(chan T, n)`): the sender does not block while there is room. That is **pace decoupling**, not an infinite queue.
- **Direction** in a function signature documents the role: send-only (`chan<- T`) or receive-only (`<-chan T`).
- **close** signals “no more values”. Receivers use `v, ok := <-ch` or `for range`.
- **select** picks a ready case; if several are ready — a **random** choice among the ready ones.
- **nil channel**: send/receive on `nil` blocks forever — useful to **disable** a select case when it is no longer relevant.

| Term | What it means in Go | Typical mistake |
|------|---------------------|-----------------|
| Unbuffered channel | Rendezvous; capacity 0 | Send without a receiver → deadlock |
| Buffered channel | Queue up to capacity `n` | Huge `n` as “performance” |
| `close` | Sender signal: end of stream | Close from receiver / double close |
| `v, ok := <-ch` | `ok==false` after close | Treating zero value as data |
| `select` | Waits for ready cases | Assuming fixed order |
| `nil` channel | Operations block forever | Forgotten nil trick → busy on closed |
| Directional type | `chan<-` / `<-chan` | Passing bidirectional type everywhere |
| `ctx.Done()` | `<-chan struct{}` for cancel | Select without Done → work after timeout |

## Mechanism

This section is the core of the lesson. Here predictability is built: what exactly blocks, what panics, what returns the zero value, how select chooses, and how a channel’s life-cycle ties to goroutine and context.

### Type and construction

A channel is a reference type. The zero value for a variable of type `chan T` is `nil`. `make(chan T)` creates an unbuffered channel; `make(chan T, n)` creates a buffered one with capacity `n`. Without `make`, send/receive on `nil` blocks forever; `close(nil)` panics.

```go
var ch chan int          // nil
ch = make(chan int)      // unbuffered, capacity 0
buf := make(chan int, 8) // buffered, capacity 8
```

Capacity is read with `cap(ch)`, current buffer length with `len(ch)`. `len` is not an API for synchronization between goroutine — it changes concurrently and must not be a decision condition like “if there is room, send”.

### Send and receive

- `ch <- v` sends value `v`.
- `v := <-ch` receives.
- `v, ok := <-ch` receives and says whether the channel is still open for future values.

For an **unbuffered** channel: send and receive must meet. If there is no receiver, send blocks. If there is no sender, receive blocks. That is rendezvous: synchronization *and* transfer in one step.

For a **buffered** channel: send does not block while `len < cap`. Receive does not block while there is at least one value. When the buffer is full, send blocks. When empty, receive blocks.

### Close as a sender signal

`close(ch)` marks that there will be **no** new sends. That is the contract: the **sender** (production owner) closes. The receiver does not close if the sender can still send — that leads to panic on send.

Panic and result rules:

| Operation | Channel state | Outcome |
|-----------|---------------|---------|
| `ch <- v` | closed | **panic** |
| `<-ch` | closed, buffer empty | zero value, `ok == false` |
| `<-ch` | closed, buffer still has values | value from buffer, `ok == true` |
| `close(ch)` | already closed | **panic** |
| `close(ch)` | `ch == nil` | **panic** |
| `ch <- v` / `<-ch` | `ch == nil` | block forever |

Close is **not** a way to “wake” a WaitGroup. For one event often `chan struct{}` or context. Close is an end-of-**stream** signal for values.

### Buffer: a queue with an upper bound

A buffered channel behaves like a bounded queue. Capacity `n` means up to `n` values can sit without an active receiver. That **decouples pace** of sender and receiver on short bursts. It is **not**:

- an infinite queue;
- a replacement for a backpressure strategy;
- a performance button without measurement.

When produce is faster than consume, the buffer fills, then send blocks — that *is* backpressure, but only up to `n`. If you set `n` to 100_000 “so it does not block”, memory grows to capacity and a slow consumer is discovered late.

### Directional channel types

Go allows narrowing the type:

```go
func produce(out chan<- int) { /* send only */ }
func consume(in <-chan int)  { /* receive only */ }
```

A bidirectional `chan T` converts implicitly to `chan<- T` or `<-chan T` when passed. The reverse cannot. At an API boundary that prevents a receiver from accidentally sending or closing. A generator often returns `<-chan T` and closes from inside.

### for range over a channel

```go
for v := range ch {
	// ...
}
```

The loop receives until the channel is closed **and** the buffer is drained. Without `close`, `range` lasts forever — a common deadlock/leak situation. That is why the “sender closes” contract is critical: without close, the consumer does not know when to stop.

### select: waiting on multiple communications

```go
select {
case v := <-a:
	// received from a
case b <- x:
	// sent to b
case <-ctx.Done():
	return ctx.Err()
default:
	// no case ready — non-blocking path
}
```

Mechanism:

1. Select evaluates all cases.
2. If **one** is ready — it executes it.
3. If **several** are ready — it picks **randomly** one of the ready ones (not “first in the code”).
4. If **none** is ready and there is no `default` — it blocks until one becomes ready.
5. If there is `default` and none is ready — it goes to `default` immediately.

`default` makes select non-blocking. Use carefully: in a loop without `time.Sleep` / another wait you easily get a busy loop that eats CPU.

### nil channel in select

Send or receive on a `nil` channel is **never** ready — it blocks forever. In select that means: that case is **ignored** as a candidate. Classic use: when one input closes, set the local variable to `nil` so `<-closed` is not forever ready with the zero value.

Without the nil trick, a closed channel in a select loop keeps that case always ready → the loop spins zeros instead of waiting on live inputs.

### Context and channel

`ctx.Done()` returns `<-chan struct{}`. When the context is cancelled (timeout, cancel, parent Done), that channel closes. In select you put it next to business cases:

```go
select {
case job := <-jobs:
	handle(job)
case <-ctx.Done():
	return ctx.Err()
}
```

Important nuance: cancellation does **not** magically kill a goroutine. The goroutine must **check** Done (or I/O must respect ctx). If a sender sends on an unbuffered channel after the consumer cancelled, the sender can stay stuck — hence buffer 1 or select on send with `ctx.Done()`.

### Signal channel and result struct

For a “done” signal without data: `chan struct{}` — the message’s zero value does not waste intent memory. For one result with an error:

```go
type result struct {
	value string
	err   error
}

ch := make(chan result, 1)
go func() {
	v, err := slow(ctx)
	ch <- result{v, err}
}()
select {
case r := <-ch:
	return r.value, r.err
case <-ctx.Done():
	return "", ctx.Err()
}
```

Buffer 1 guarantees the sender does not block forever if you already cancelled and no longer read. That is a small, important pattern with timeout.

### or-done wrapper

When you receive from a channel whose owner you do not control and who may never close:

```go
func orDone(ctx context.Context, in <-chan int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		for {
			select {
			case <-ctx.Done():
				return
			case v, ok := <-in:
				if !ok {
					return
				}
				select {
				case out <- v:
				case <-ctx.Done():
					return
				}
			}
		}
	}()
	return out
}
```

You can `range` the output while respecting cancellation, even if the upstream channel stays open. Useful at system boundaries.

### Channel and Mutex: different jobs

A channel transfers ownership of a value and synchronizes a flow. A Mutex protects shared state (e.g. a map) from concurrent access. Do not use a channel to “simulate a Mutex” without need — you get slower, murkier code. Do not use a Mutex to replace a pipeline flow — you get a shared-state trap. Choose the tool by the question: *am I sending a message / changing flow* or *am I protecting a field*.

### Happens-before intuition (without formalism)

A send on a channel *synchronizes with* the receive of that value: the receiver sees effects the sender finished before the send. Close synchronizes with a receive that sees `ok==false`. That is not permission to share a map without Mutex — it is a guarantee for the *transferred* value and ordering around that communication.

### Blocking, deadlock, and leak

- **Deadlock**: all goroutine in the program blocked; the runtime may panic with a deadlock message (in simple programs).
- **Leak**: a goroutine forever blocked on a channel while the rest of the program runs — harder to see; `NumGoroutine` grows.
- Typical leak: you start a worker, the consumer leaves (timeout), the sender sits on an unbuffered send.

Diagnosis later in 08.06 (pprof goroutine). Here: design send/receive so there is always an exit path (close, ctx, buffer 1).

### Buffer 0 versus buffer N: operational difference

| | Buffer 0 | Buffer N |
|--|----------|----------|
| Send without receiver | Blocks immediately | Blocks only when full |
| Synchronization | Strong (rendezvous) | Weaker (pace decoupling) |
| In-flight memory | Minimal per message | Up to N values |
| Slow consumer | Immediately slows produce | Later, after filling |

By default choose 0 until measurement shows need for a cushion. Small N (1–8) is often enough for jitter. Large N needs policy and a memory budget.

### Multiple senders, one close

If multiple goroutine send on the same channel, **one** owner must close — usually a coordinator after WaitGroup. Senders must not close themselves. Pattern:

1. WaitGroup: each sender `Done` when finished.
2. Separate goroutine: `Wait` then `close(out)`.
3. Receivers `range` until close.

Double close or close while someone still sends = panic.

### Select and fairness

Random choice among ready cases prevents one channel from “starving” another when both are always full. But that is **not** a strict fairness guarantee for all load scenarios. If you need priority, model it explicitly (e.g. first check a high-priority channel in a separate select, or use separate queues).

### time.After and leaking in a loop

```go
// bad in a tight loop: a new timer every time
select {
case <-ch:
case <-time.After(time.Second):
}
```

`time.After` allocates a timer. In a loop prefer `time.NewTimer` + `Reset`, or a context timeout above the loop. Details go into patterns; here remember: a select case that “creates a side effect” on every entry can be expensive.

### Channel as a semaphore

```go
sem := make(chan struct{}, n) // n permits
sem <- struct{}{}             // acquire
<-sem                         // release
```

A buffered channel of capacity `n` limits concurrency. That is a bridge to the worker pool pattern in 08.05. Still true: it does not replace Mutex for a map; it only counts permits.

### Copying channel values

A channel variable holds a reference. Assignment `a := b` shares the same channel. Passing into a function = sharing the same medium. There is no “deep copy” of buffer contents through ordinary assign.

### Interface and channel

You can have `chan interface{}` or `chan any`, but you lose type safety. Prefer a concrete type or a generic helper in newer Go. At package boundaries, a clear `chan Event` is more readable than `chan any`.

### Method receiver and channel fields

A struct can hold a channel as a field (e.g. `jobs chan Job`). A method on a pointer receiver often starts goroutine that read that field. Life-cycle: who closes `jobs`? Document in the package comment. Close in a `Stop()` method with Once prevents double close.

### Module and dependencies

For pure channel lessons the standard library is enough. `context` is in stdlib. Later tools (`errgroup`, `singleflight`) live in `golang.org/x/sync` — that is 08.06. Here we do not introduce an external module without need.

### What the runtime does (intuition)

When a goroutine blocks on a channel, the runtime parks it. When the other side enables communication, it wakes it. That is not an OS thread per goroutine — so you can have thousands of goroutine, but you can still exhaust memory with buffers and leaks. A channel does not make a program “infinitely scalable”; it makes communication explicit.

### Mechanism checklist

1. Was the channel created with `make`?
2. Who is the sole owner of `close`?
3. Do all receivers have an exit (close or ctx)?
4. Can send after cancellation block?
5. Does select assume case order?
6. Does a closed channel remain in select without nil?
7. Do you check `ok` when the zero value can look like valid data?

If you can answer all seven before code review, Mechanism did its job.

### Deep trace: unbuffered send without a receiver

```text
goroutine A: ch <- x     // buffer 0, no receive → PARK
goroutine B: (does not exist)
main: finishes or does something else
→ A leaks or the whole program deadlocks
```

The only fix is the *other side* of communication (receive), or cancellation + buffer 1 if the result is optional.

### Deep trace: closed channel in select without nil

```text
select {
case v, ok := <-a: // a closed → ALWAYS ready, v=0, ok=false
case v, ok := <-b: // b live
}
```

Without `a = nil` after `!ok`, the loop spins zeros from `a` and starves `b` or busy-spins. The nil trick disables the dead input.

## Rules

```go
ch := make(chan int)      // unbuffered
buf := make(chan int, 8)  // buffer 8

func produce(out chan<- int) { /* send only */ }
func consume(in <-chan int)  { /* receive only */ }
```

1. The sender closes; the receiver ranges or reads with `ok`.
2. Never send on a closed channel.
3. Never close twice; never `close(nil)`.
4. Do not close a channel only to “wake” a WaitGroup.
5. Do not rely on buffer size “by gut feel” without measurement and a backpressure policy.
6. Pass directionally narrowed channels into functions.
7. In select with I/O always consider `ctx.Done()`.
8. Use a nil channel deliberately to disable a case — not as a “forgotten make”.
9. `len`/`cap` are not a synchronization signal between goroutine.
10. A sending goroutine must have a path not to leak when the receiver leaves.

## Examples

### Example 1 — Unbuffered rendezvous

```go
package main

import "fmt"

func main() {
	ch := make(chan string)
	go func() {
		ch <- "ping" // waits for a receiver
	}()
	fmt.Println(<-ch)
}
```

#### What happens here

`make(chan string)` creates an unbuffered channel, so the send and the receive have to meet. The new goroutine blocks in `ch <- "ping"` until `main` receives. `fmt.Println(<-ch)` takes that string and prints it.

#### Predict

What is printed? Can the main goroutine finish before the send? What if there is no `go` and in the same goroutine you do `ch <- "ping"` and only then receive?

#### Answer

`ping` is printed. Send and receive meet on the unbuffered channel. Without the other side, one goroutine would block forever. If in the *same* goroutine you do send then receive on an unbuffered channel, send blocks forever — deadlock, because nobody else receives.

### Example 2 — Buffer as pace decoupling

```go
package main

import "fmt"

func main() {
	ch := make(chan int, 2)
	ch <- 1
	ch <- 2
	// ch <- 3 would block without a receiver
	fmt.Println(<-ch, <-ch)
}
```

#### What happens here

`make(chan int, 2)` creates a channel with room for two values. Both sends run in `main` and finish while that room remains. The comment marks that a third send would wait for a receiver. The two receive expressions then print `1` and `2` in send order.

#### Predict

Why do the first two sends pass without another goroutine? How much in-flight memory does buffer 2 hold versus buffer 2000 for the same type?

#### Answer

Capacity 2 allows two values without a receiver. A third send would wait. Buffer 2 is a small cushion; buffer 2000 holds up to 2000 values in memory — that is not free performance, that is a budget.

### Example 3 — close, zero value, and ok

```go
package main

import "fmt"

func main() {
	ch := make(chan int, 1)
	ch <- 7
	close(ch)
	v1, ok1 := <-ch
	v2, ok2 := <-ch
	fmt.Println(v1, ok1)
	fmt.Println(v2, ok2)
}
```

#### What happens here

The buffer holds `7`, and `close` marks the channel so the sender is finished. The first receive returns that buffered `7` with `ok` true. The second receive sees a closed, empty channel, so it returns `0` with `ok` false. The two `Println` calls show those pairs.

#### Predict

What are `v1, ok1` and `v2, ok2`? Would `ch <- 8` after `close` succeed?

#### Answer

First: `7 true` (value still in the buffer). Second: `0 false` (zero value, channel closed). Send after close → panic. Close is a sender signal; it does not erase the buffer immediately — remaining values are drained first.

### Example 4 — for range finishes on close

```go
package main

import "fmt"

func gen(n int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		for i := 1; i <= n; i++ {
			out <- i
		}
	}()
	return out
}

func main() {
	for v := range gen(3) {
		fmt.Println(v)
	}
}
```

#### What happens here

`gen` returns a receive-only channel and starts a goroutine that sends the integers from 1 through `n`. `defer close(out)` closes the channel when that goroutine returns. `for range` in `main` receives until the close, then stops. Calling `gen(3)` prints 1, then 2, then 3.

#### Predict

What is printed? What if you remove `defer close(out)`?

#### Answer

Output: `1`, `2`, `3`. The API returns `<-chan int` — the caller cannot accidentally send or close. Without close, `range` waits forever → the program hangs (leak/deadlock depending on the rest).

### Example 5 — select with context

```go
package main

import (
	"context"
	"fmt"
	"time"
)

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 200*time.Millisecond)
	defer cancel()

	results := make(chan string, 1)
	go func() {
		time.Sleep(500 * time.Millisecond)
		results <- "late"
	}()

	select {
	case r := <-results:
		fmt.Println("ok:", r)
	case <-ctx.Done():
		fmt.Println("cancelled:", ctx.Err())
	}
}
```

#### What happens here

`WithTimeout` cancels the derived context after 200 milliseconds. A second goroutine sleeps 500 milliseconds and then sends `"late"` on a channel of capacity 1. `select` waits for that value or for `ctx.Done()`. The timeout is the earlier of the two, so the Done case prints `ctx.Err()`.

#### Predict

Which case wins? Does the sender goroutine leak if `results` was unbuffered?

#### Answer

Timeout arrives before the result → cancellation is printed. Buffer 1 lets the late sender send without blocking. If the channel were unbuffered and nobody receives anymore, that goroutine would stay stuck on send — a typical leak after cancellation.

### Example 6 — nil channel trick (fan-in skeleton)

```go
package main

import "fmt"

func merge(a, b <-chan int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		for a != nil || b != nil {
			select {
			case v, ok := <-a:
				if !ok {
					a = nil
					continue
				}
				out <- v
			case v, ok := <-b:
				if !ok {
					b = nil
					continue
				}
				out <- v
			}
		}
	}()
	return out
}

func main() {
	a := make(chan int, 2)
	b := make(chan int, 2)
	a <- 1
	b <- 2
	close(a)
	close(b)
	for v := range merge(a, b) {
		fmt.Println(v)
	}
}
```

#### What happens here

`merge` starts a goroutine that reads `a` and `b` while either variable is non-nil, then closes `out`. A receive with `ok` false sets that variable to `nil`, which drops the case from later selects. A receive with `ok` true is forwarded with `out <- v`. `main` places `1` and `2` in the two buffers, closes both inputs, and prints each value `range` receives from `merge`.

#### Predict

Why `a = nil` after `!ok`? What would happen if you left closed `a` in select forever?

#### Answer

A closed channel makes receive always ready with the zero value. Nil disables the case. Without the nil trick, the loop would spin zeros from `a` instead of waiting only on live inputs — a classic fan-in bug.

### Example 7 — select random among ready

```go
package main

import "fmt"

func main() {
	a := make(chan int, 1)
	b := make(chan int, 1)
	a <- 1
	b <- 2
	for i := 0; i < 10; i++ {
		select {
		case v := <-a:
			fmt.Println("a", v)
			a <- v
		case v := <-b:
			fmt.Println("b", v)
			b <- v
		}
	}
}
```

#### What happens here

Each channel starts with one buffered value, so both `select` cases are ready. The case that runs prints its label and value, then sends the value back so the buffer is full again. The loop does this ten times. When both cases are ready, `select` chooses one of them at random on that iteration.

#### Predict

Does case `a` always go first because it is written above? What exactly does the specification guarantee?

#### Answer

No. When both are ready, select chooses randomly. Order in the source code is **not** priority. If you need strict priority, you must model it explicitly.

### Example 8 — directional at the API boundary

```go
package main

import "fmt"

func produce(out chan<- int) {
	for i := 1; i <= 3; i++ {
		out <- i
	}
	close(out)
}

func consume(in <-chan int) {
	for v := range in {
		fmt.Println(v)
	}
}

func main() {
	ch := make(chan int)
	go produce(ch)
	consume(ch)
}
```

#### What happens here

`produce` accepts a send-only channel, sends 1, 2, and 3, then closes it. `consume` accepts a receive-only channel and prints each value until the range ends at close. `main` creates one bidirectional channel, runs `produce` in a new goroutine, and receives in `consume` on the calling goroutine. The parameter types are the directions the compiler enforces at those two calls.

#### Predict

Can `consume` do `close(in)`? Can `produce` do `<-out`?

#### Answer

No — the compiler rejects it. Directional types turn the contract into a compile error instead of runtime panics. That is cheap protection at the package boundary.

### Example 9 — send on closed (intentional panic for learning)

```go
package main

func main() {
	ch := make(chan int)
	close(ch)
	ch <- 1 // panic: send on closed channel
}
```

#### What happens here

The program creates a channel and closes it before any send. The next statement sends `1` on that closed channel. That send panics, as the comment on the line states.

#### Predict

Does `recover` in `main` “fix” the design? What is the correct end signal?

#### Answer

Panic here is a symptom of a wrong contract. `recover` is not architecture. The correct end-of-stream signal is close **from the sender**, and receivers read until `ok==false` / end of range. Do not send after close.

### Example 10 — buffer 1 with timeout (anti-leak)

```go
package main

import (
	"context"
	"fmt"
	"time"
)

func fetch(ctx context.Context) (string, error) {
	ch := make(chan string, 1)
	go func() {
		time.Sleep(50 * time.Millisecond)
		ch <- "data"
	}()
	select {
	case v := <-ch:
		return v, nil
	case <-ctx.Done():
		return "", ctx.Err()
	}
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), time.Millisecond)
	defer cancel()
	fmt.Println(fetch(ctx))
}
```

#### What happens here

`fetch` starts a goroutine that sleeps 50 milliseconds and sends `"data"` on a channel of capacity 1. `select` returns the string from that channel, or returns `ctx.Err()` when the context ends first. `main` calls `fetch` with a timeout of one millisecond. That deadline arrives before the sleep ends, so `Println` receives the error from the Done case.

#### Predict

Why buffer 1? What if buffer is 0 and timeout wins?

#### Answer

With buffer 1, the late send succeeds and the goroutine finishes. With buffer 0, after timeout nobody receives → the sender leaks. A small buffer here is not an “optimization”, but life-cycle hygiene.

## Analysis

| Decision | Why |
|----------|-----|
| Unbuffered by default | Strong synchronization, less hidden state |
| Small buffer as cushion | Decouples short pace bursts |
| Direction in API | Compiler prevents misuse |
| Sender closes | One owner of the close contract |
| select + ctx.Done | Cancellation with communication |
| nil case | Clean fan-in without a busy loop on closed |
| Buffer 1 for one result | Prevents sender leak after cancel |
| `ok` check | Zero value ≠ valid data |

Analysis is not decoration: each decision in the table answers a concrete failure mode from the Problem. If you choose a buffer “because a blog says so”, return to the table and replace the reason with measurement.

## Trade-offs

- **Large buffer** — fewer short-term blocks, more memory and later discovery of a slow consumer.
- **Only channel** — nice flow, awkward for random cache access (there Mutex).
- **default in select** — non-blocking, easy busy-spin.
- **Close as signal** — elegant for a stream; for one event often `chan struct{}` of capacity 1 or context is enough.
- **Strict directional API** — more types in signatures, fewer runtime panics.
- **or-done wrapper** — extra goroutine and channel; cleaner consumer at the boundary.

There is no universally “best” buffer. The trade-off is memory budget versus backpressure sensitivity. In a service under peak, a late-discovered slow consumer costs more than a short block on a small buffer.

## Common mistakes

1. Close from the receiver while the sender still sends.
2. Multiple close or `close(nil)`.
3. `range` without close — forever.
4. Assuming select order when two cases are ready.
5. Unbuffered send in a handler without a guaranteed receiver — deadlock/leak under load.
6. Ignoring `ok` after close and treating the zero value as valid data.
7. Huge buffer “just in case” instead of backpressure.
8. Closed channel left in a select loop without the nil trick.
9. Mixing channel and Mutex without a clear question (flow vs shared state).
10. Cancelling context without a path for the sender to finish (no buffer 1 / Done on send).

## Idiomatic

- Return `<-chan T` from a generator; take `chan<- T` in worker signatures.
- Document who closes in a package/API comment.
- Combine channel with context for production I/O.
- For one result: buffer 1 + one goroutine often prevents sender leak.
- Do not use a channel to simulate a Mutex without need.
- Prefer `chan struct{}` for a pure signal.
- Name channels by role (`jobs`, `results`, `done`), not `ch1`.
- In tests verify cancellation: after cancel, goroutine count should drop.

## Scenario

A pipeline processes uploads: decoder → virus scanner → uploader. First version: buffer 10_000 “so it does not block”. Under peak RAM explodes because produce is faster than S3 upload. Operators see memory growth, not “slow S3”.

Second version: unbuffered or small buffer (e.g. 2) between stages — backpressure naturally slows the input. The decoder does not swallow the whole disk into memory. Stable memory profile. Additionally: each stage in select listens to `ctx.Done()` because the HTTP request can be cancelled.

Third iteration: the generator returns `<-chan Part`, the worker takes `chan<- Result`. Only the producer stage closes. Fan-in in the last stage uses the nil trick. Buffer is not a performance button; it is queue policy and a life-cycle contract.

## Check questions

1. **What does an unbuffered channel guarantee?**  
   Rendezvous: send and receive meet; capacity 0, send blocks without a receiver.

2. **Who closes a channel?**  
   Typically the sole sender / production owner.

3. **What does a nil channel do in select?**  
   Disables that case because operations on nil block forever and are never ready.

4. **Why is a buffer not an infinite queue?**  
   When full, send blocks; memory grows only up to capacity.

5. **How does context enter channel code?**  
   `select` on `ctx.Done()` next to business cases; Done is `<-chan struct{}`.

6. **What does receive from a closed empty channel return?**  
   The type’s zero value and `ok == false`.

7. **Does select respect case order in the code?**  
   No. Among ready ones it chooses randomly.

8. **Why do directional types exist?**  
   So the API boundary forbids the wrong direction (send/close) already at compile time.

## Summary

A channel transfers values and synchronizes goroutine. Unbuffered = rendezvous (send blocks when buffer is 0 and there is no receiver). Buffered = bounded queue. Close is a sender signal; send on closed panics; receive from closed gives zero value and `ok=false`. Select chooses randomly among ready; a nil channel blocks forever and disables a case; `for range` finishes on close. Directional types preserve the contract. `ctx.Done()` in select ties cancellation to communication. Next: patterns — pipeline, fan-out/in, worker pool.
