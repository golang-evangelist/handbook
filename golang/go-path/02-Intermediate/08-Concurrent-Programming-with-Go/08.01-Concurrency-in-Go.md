# 08.01 Concurrency in Go: model, CSP, and GOMAXPROCS

> **Go Path - Zero to Gopher** / **02 Intermediate → Concurrent Programming with Go** / Lesson 08.01

## Lesson goals

After this lesson you can:

- distinguish **concurrency** (program structure) from **parallelism** (simultaneous execution on multiple cores)
- explain the CSP idea in Go: independent parts + communication over a **channel**
- compare the cost of a **goroutine** with an OS thread, without mixing terms (a goroutine is not a thread and not a process)
- read and set **GOMAXPROCS** and know what that value does *not* guarantee
- predict whether concurrency will speed up I/O-bound or CPU-bound work

## Prerequisite

- Go 1.22+; `go version` works in the terminal
- Functions, **closure** (a function that captures surrounding variables), basic `error` contract
- Basic types, `for`, `package main`
- A useful sense of blocking I/O (network, disk) versus pure CPU work

## Problem this lesson solves

Programs often must do several things “at once”: wait for an HTTP response, handle another request, enforce a timeout. If everything is strictly sequential, latency grows because waits add up. If everything runs on OS threads without discipline, the cost of creating threads and synchronizing becomes expensive.

Without a clear model people mix terms and make wrong decisions:

- “I have 8 cores, so I need exactly 8 goroutine” — not necessarily true.
- “Concurrency = always faster” — it is faster only if there is overlapping waits or parallel CPU work.
- “A goroutine is a cheap thread” — it is cheaper *than* an OS thread, but a goroutine *is not* a thread. It is not a process either. It is a distinct unit of work that the Go runtime schedules.
- “Set `GOMAXPROCS=32` and the HTTP service will speed up” — often it will not, because the bottleneck is not CPU.

This lesson establishes a shared language before you go into the `go` statement, `sync`, and channel details.

## Mental model

Three layers you must keep separate:

1. **Concurrency** — a way to *structure* a program so parts can progress independently. Parts can interleave in time. Concurrency is design.
2. **Parallelism** — actually running those parts *at the same time* on multiple processor cores. Parallelism is hardware utilization.
3. **Communication** — how parts exchange data. In Go the idiomatic path goes through a channel; shared memory (with a Mutex) exists when it must.

Classic picture: one cook switching between two pans (concurrency without parallelism — does one, then the other, interleaves). Two cooks for two pans (parallelism). A recipe that says “when the egg is done, announce it” instead of sharing the same pan without agreement — that is communication.

Go stands on CSP inspiration (Communicating Sequential Processes):

- sequential pieces of code (each in its own goroutine) do their work
- a **channel** carries values and synchronizes
- shared memory is not forbidden, but it is not the default tool

The runtime maps many goroutine onto fewer OS threads (**M:N**). You write logic as if you have thousands of lightweight units of work. The scheduler decides what runs on which **P** (processor in the Go sense) and **M** (OS thread). You do not pick an OS thread by hand.

## Mechanism

### Concurrency vs parallelism — line by line

Imagine two functions, each sleeping 200 ms (simulation of network wait):

```text
Sequential:
  time 0ms     200ms    400ms
  |-- A sleeps --|-- B sleeps --|
  total ≈ 400 ms

Concurrent (two goroutine):
  time 0ms     200ms
  |-- A sleeps --|
  |-- B sleeps --|
  total ≈ 200 ms
```

Here there is **no** heavy CPU work. The gain comes because waits overlap. That is concurrency. Parallelism (multiple cores) is not the cause of the speedup — even with `GOMAXPROCS=1` this example still takes ~200 ms, because while a goroutine sleeps, the runtime can run another.

Now imagine two functions that *compute* in a loop with no I/O:

```text
GOMAXPROCS=1, two workers:
  only one Go code runs at a time on the CPU
  total ≈ sum of work (plus small overhead)

GOMAXPROCS=2, two workers on a dual-core CPU:
  both can compute simultaneously
  total ≈ max(work) instead of the sum (ideally)
```

Here concurrency *enables* parallelism, and `GOMAXPROCS` plus the number of cores decide whether parallelism actually happens.

**Diagnosis rule:**

| Symptom | More likely cause | What to touch first |
|---------|-------------------|---------------------|
| CPU low, latency high | waiting on I/O | concurrent calls, timeout, pool toward the outside |
| CPU 100%, latency high | CPU-bound | worker count, algorithm, `GOMAXPROCS` (measure) |
| Memory grows, goroutine count grows | leak / too much work | cancellation, bound on the pool |

### CSP in Go

CSP says: parts are isolated; exchange goes through communication media. In Go:

- goroutine ≈ lightweight “sequential process” in the CSP sense (but *not* an OS process)
- `chan T` ≈ typed channel
- `select` ≈ choice among multiple communications

Idiom: *do not communicate by sharing memory; share memory by communicating*. Meaning: prefer sending a value on a channel over having two goroutine write the same `map` without agreement.

That is **not** dogma. Mutex exists exactly for state that must be shared in memory (cache, metrics counter, session map). CSP is a guide for designing flows; `sync` is a tool for local protection.

Trace of a rendezvous on an unbuffered channel:

```text
1. ch := make(chan int)          // capacity 0
2. goroutine A: ch <- 42         // A BLOCKS — buffer is 0, no receive yet
3. goroutine B: v := <-ch        // B receives 42; A unblocks
4. now A and B can continue
```

Send and receive *meet*. There is no place in the buffer where 42 could “wait” alone. That is synchronization built into communication — the core of CSP in practice.

### Goroutine vs OS thread — what it is and is not

OS thread:

- larger stack (often MB order)
- more expensive creation and context switch
- limited practical count per process

Goroutine:

- small initial stack (kilobytes; grows as needed)
- creation is cheap *relatively*
- thousands can live if they are mostly blocked on I/O or a channel

Important: **a goroutine is not a thread**. The runtime maps many goroutine onto fewer M (OS threads). You do not “join” an OS thread as in some APIs — you wait for completion via WaitGroup, channel, or `errgroup`.

“Cheap” is not “free”. Each goroutine uses memory and enters the scheduler. A leak (started, never finishes, never cancels) consumes RAM. Leak details are in 08.02.

### M:N scheduler — P, M, G

In a rough model:

- **G** — goroutine
- **M** — OS thread (machine)
- **P** — processor in the Go sense; number of P ≈ `GOMAXPROCS`

The scheduler holds queues of G and assigns them to M via P. When a G blocks on a channel or system I/O, M can take another G. That is why I/O concurrency works even with a single P.

You do not need to memorize internal scheduler details to write correct code. You must know:

1. The number of P controls how much Go code can execute *in parallel*.
2. The number of goroutine is not the same as the number of P.
3. Blocking on channel/I/O is not the same as CPU busyness.

### GOMAXPROCS

`GOMAXPROCS` (env variable or `runtime.GOMAXPROCS`) sets the number of **P**.

```go
import "runtime"

n := runtime.GOMAXPROCS(0) // 0 = do not change; returns current value
runtime.GOMAXPROCS(4)      // set to 4
```

Facts:

- Since Go 1.5 the default is the number of logical CPUs (`runtime.NumCPU()`).
- More P → more parallel Go code on CPU-bound work.
- It does not magically increase the speed of an I/O-bound service.
- It does not change how many goroutine you may start — only how many of them can *execute Go code* at the same time.

**Predict the result:** You have an HTTP handler that for each request does three `http.Get` sequentially. CPU is 15%. You change `GOMAXPROCS` from 8 to 32. What do you expect for P99 latency?

**Answer:** Almost nothing. The bottleneck is network waits, not the number of P. You need concurrent calls inside the request (with timeout), not a larger `GOMAXPROCS`.

### The `go` statement — overview (details in 08.02)

```go
go f(x, y)
go func() {
	// work
}()
```

- Starts a function asynchronously; does not wait for completion.
- Return values are **discarded** — there is no `x := go f()`.
- A `main` that finishes kills the whole program, including other goroutine.

Trace without waiting:

```text
1. main: go work()     // schedules goroutine; main does NOT wait
2. main: return        // program exits
3. work() may never get to print
```

So you always need a plan: who waits for completion? (WaitGroup, channel, `errgroup` — later lessons.)

### Loop and closure in Go 1.22+

When you start a goroutine in a loop, Go 1.22+ gives a *new* loop variable per iteration:

```go
for i := range 3 {
	go func() {
		fmt.Println(i) // in 1.22+: 0, 1, 2 (order not guaranteed)
	}()
}
```

Before 1.22 all would capture the same `i`. The course assumes 1.22+. Still: do not rely on print order without synchronization.

### When concurrency does *not* help

1. The work is purely sequential (step B needs A’s result in memory before B starts, with no way to overlap).
2. The bottleneck is an external system with a limit (the database allows 10 connections; you open 1000 goroutine — you only wait in a queue).
3. Synchronization and contention cost eats the gain.
4. You have no measurement — you “optimize” the wrong place.

## Rules and syntax

```go
import "runtime"

// Read current GOMAXPROCS
n := runtime.GOMAXPROCS(0)

// Number of logical CPUs
cpus := runtime.NumCPU()

// Number of live goroutine (diagnostics, not an API contract)
g := runtime.NumGoroutine()
```

Behavioral rules:

1. Do not assume the execution order of two goroutine without synchronization.
2. Shared mutable fields require a channel, Mutex, atomic, or clear ownership by one goroutine.
3. Without synchronization, a data race is **undefined behavior**. Detector: `go test -race` or `go run -race` (details in 08.03 and 08.06).
4. Do not set `GOMAXPROCS` in a library `package` — that is a process decision.
5. Measure before you touch worker count or `GOMAXPROCS`.

## Examples

### Example 1 — Concurrency without a parallelism gain

```go
package main

import (
	"fmt"
	"time"
)

func slow(name string) {
	time.Sleep(200 * time.Millisecond)
	fmt.Println("done:", name)
}

func main() {
	start := time.Now()
	slow("A")
	slow("B")
	fmt.Println("sequential:", time.Since(start))

	start = time.Now()
	done := make(chan struct{}, 2)
	go func() {
		slow("A")
		done <- struct{}{}
	}()
	go func() {
		slow("B")
		done <- struct{}{}
	}()
	<-done
	<-done
	fmt.Println("concurrent:", time.Since(start))
}
```

#### What happens here

Trace of the sequential part:

1. `slow("A")` blocks ~200 ms.
2. `slow("B")` blocks another ~200 ms.
3. Print `sequential:` ≈ 400 ms.

Trace of the concurrent part:

1. `done` is a channel of capacity 2 — the buffer can take two signals without a receiver.
2. Two goroutine start; both immediately enter `Sleep`.
3. The runtime can interleave; both sleeps run on the wall clock.
4. Each sends on `done`; `main` receives two signals.
5. Print `concurrent:` ≈ 200 ms.

Gain = overlapping waits. Not core magic.

**Predict the result:** What if you set `runtime.GOMAXPROCS(1)` before the concurrent part?

**Answer:** Still ≈ 200 ms. Sleeping is not CPU work; one P is enough to schedule goroutine waiting on a timer.

### Example 2 — CPU work and GOMAXPROCS

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"time"
)

func burn(n int) int {
	x := 0
	for i := 0; i < n; i++ {
		x += i % 7
	}
	return x
}

func runWorkers(workers, work int) time.Duration {
	var wg sync.WaitGroup
	start := time.Now()
	for i := 0; i < workers; i++ {
		wg.Add(1) // Add BEFORE go
		go func() {
			defer wg.Done()
			_ = burn(work)
		}()
	}
	wg.Wait()
	return time.Since(start)
}

func main() {
	const work = 20_000_000
	for _, p := range []int{1, 2, runtime.NumCPU()} {
		runtime.GOMAXPROCS(p)
		d := runWorkers(p, work)
		fmt.Printf("GOMAXPROCS=%d workers=%d duration=%v\n", p, p, d)
	}
}
```

#### What happens here

1. `burn` is pure CPU work — no channel, no I/O.
2. `wg.Add(1)` sits *before* `go` so WaitGroup does not see zero too early.
3. With `GOMAXPROCS=1` all workers share one P: parallelism of Go code is 1.
4. With a larger `GOMAXPROCS` (up to CPU count) more `burn` loops can run at once.
5. Numbers depend on the machine. The goal is the mechanism, not a magic constant.

If `workers` >> `GOMAXPROCS` and the work is CPU-bound, excess goroutine only wait to be scheduled — they do not speed up linearly.

### Example 3 — CSP style: ownership via channel

```go
package main

import "fmt"

func main() {
	jobs := make(chan int)    // unbuffered
	results := make(chan int) // unbuffered

	go func() {
		for j := range jobs {
			results <- j * j
		}
		close(results)
	}()

	go func() {
		for i := 1; i <= 5; i++ {
			jobs <- i
		}
		close(jobs)
	}()

	for r := range results {
		fmt.Println(r)
	}
}
```

#### What happens here

Trace for `i = 1`:

1. The sender does `jobs <- 1`. The channel is unbuffered → **blocks** until the worker receives.
2. The worker in `range jobs` receives `1`, computes `1`, sends `results <- 1` → may block until `main` receives.
3. `main` in `range results` receives and prints.
4. After `close(jobs)`, `range jobs` finishes; the worker does `close(results)`.
5. `range results` in `main` finishes.

There is no shared slice that both goroutine mutate. The channel carries the value and synchronizes. That is CSP in miniature.

### Example 4 — False assumption about order

```go
package main

import "fmt"

func main() {
	ch := make(chan string, 2)
	go func() { ch <- "first" }()
	go func() { ch <- "second" }()
	fmt.Println(<-ch)
	fmt.Println(<-ch)
}
```

#### What happens here

1. A buffer of capacity 2 allows both `send` without waiting for a receiver (if they arrive before receive).
2. Which goroutine sends first — **not defined**.
3. Output may be `first`/`second` or the reverse.

The buffer separates pace; it does not define completion order. For strict order: one sender, sequential calls, or explicit sequence numbers.

**Predict the result:** What if it is `make(chan string)` without a buffer, and `main` immediately does `<-ch` before the goroutine arrive?

**Answer:** `main` blocks on receive until some goroutine sends. The program still works, but print order between the two senders is still not guaranteed.

### Example 5 — Goroutine count as a signal

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

func main() {
	fmt.Println("start", runtime.NumGoroutine())
	for i := 0; i < 1000; i++ {
		go func() {
			time.Sleep(time.Second)
		}()
	}
	time.Sleep(50 * time.Millisecond)
	fmt.Println("during sleep", runtime.NumGoroutine())
	time.Sleep(1200 * time.Millisecond)
	fmt.Println("after", runtime.NumGoroutine())
}
```

#### What happens here

1. At start the count is small (often 1 — `main`).
2. After the loop + a short wait, the count jumps toward ~1000+ while goroutine sleep.
3. After ~1.2 s of sleeping, they finish; the count drops back.

On a server you expect a stable floor plus spikes per request. If the floor *only grows*, suspect a leak (08.02).

### Example 6 — Diagnosis: wrong tool

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

func simulateIO() {
	time.Sleep(50 * time.Millisecond)
}

func main() {
	runtime.GOMAXPROCS(1)
	start := time.Now()
	done := make(chan struct{}, 10)
	for i := 0; i < 10; i++ {
		go func() {
			simulateIO()
			done <- struct{}{}
		}()
	}
	for i := 0; i < 10; i++ {
		<-done
	}
	fmt.Println("10 I/O with GOMAXPROCS=1:", time.Since(start))
}
```

#### What happens here

Expected ≈ 50 ms (plus small overhead), not 500 ms. Ten waits overlap even with one P. If someone “fixed” latency by raising `GOMAXPROCS`, they would miss the cause.

## Decision analysis

| Decision | Why |
|----------|-----|
| Concurrency as structure | Enables overlapping I/O and clear responsibility boundaries |
| Parallelism only with measurement | More workers without CPU work waste memory and the scheduler |
| Channel for flows | Less shared state; clearer data ownership |
| Mutex for local shared state | Simpler than a channel for a cache/counter in one process |
| Default GOMAXPROCS | Since 1.5 enough for most; touch manually with measurement |
| Do not call a goroutine a “thread” | Wrong model → wrong expectations about join/priority |

## Trade-offs

- **More goroutine** — better I/O utilization; harder debugging; leak risk.
- **One sequential loop** — simpler reasoning; worse overlapping waits and worse parallelism on CPU.
- **Channel everywhere** — elegant for pipelines; awkward for tiny shared state.
- **Mutex everywhere** — simple model; easy to hit deadlock and contention.
- **High GOMAXPROCS** — more parallel CPU work; more contention on shared structures.

## Common mistakes

1. **Wrong code:** “We have 16 cores, put 16 goroutine per request.”  
   **What happens:** Under peak, thousands of requests × 16 = goroutine explosion; memory and scheduler suffer.  
   **Why:** Core count is not a formula for goroutine per request.  
   **Fix:** Bound (worker pool), measurement, limit toward the outside.

2. **Wrong code:** `go f()` in `main` then immediate `return` without waiting.  
   **What happens:** Program exits; `f` may never run.  
   **Why:** End of `main` = end of process.  
   **Fix:** WaitGroup, channel signal, or blocking receive before exit.

3. **Wrong code:** Two goroutine write the same `map` without Mutex/channel.  
   **What happens:** Data race — undefined behavior; `-race` reports it.  
   **Why:** Without synchronization there is no guaranteed consistency.  
   **Fix:** Mutex, channel ownership, or `sync.Map` only when the pattern fits.

4. **Wrong code:** `GOMAXPROCS(64)` on an I/O-bound API with low CPU.  
   **What happens:** Latency stays; contention may grow.  
   **Why:** The bottleneck is not the number of P.  
   **Fix:** Concurrent I/O, timeout, profiling (14.xx).

5. **Wrong code:** Mixing “goroutine = thread” in a design document.  
   **What happens:** The team expects OS priorities, affinity, manual join.  
   **Why:** Wrong mental model.  
   **Fix:** Use exact terms; wait via WaitGroup/channel/context.

6. **Wrong code:** “Optimizing” worker count without a benchmark.  
   **What happens:** Time is wasted; regressions pass unnoticed.  
   **Why:** Without a measure there is no proof.  
   **Fix:** `testing.B`, pprof, then change.

## Idiomatic Go

- Default: little shared mutable state; clear ownership.
- For data flows: channel and `select`.
- For protecting a structure: `sync.Mutex` / `RWMutex`.
- For cancellation: `context.Context` (08.02+).
- Do not set `GOMAXPROCS` in a library.
- Document whether a function blocks, starts a goroutine, or requires the caller to close a channel.
- In Go 1.22+ loop + closure + `go` captures a per-iteration variable — still synchronize results.

## Practical scenario

A team has an API that for each request calls three external services sequentially. P99 latency is ~900 ms. Proposal: “set `GOMAXPROCS` to 32”. Measurement shows CPU under 20% — the bottleneck is HTTP waits.

Real fix: concurrent calls to the three services inside one request (with timeout and `errgroup`), plus a limit on parallel requests outward. `GOMAXPROCS` stays default. Latency drops because network waits overlap — that is concurrency, not core magic.

Another part of the team runs batch file hashing. There CPU goes to 100%. Raising worker count up to core count and checking `GOMAXPROCS` makes sense. Same tool, different diagnosis.

Third signal: `runtime.NumGoroutine()` in metrics grows for hours. That is not a `GOMAXPROCS` problem — that is a leak or unbounded work start (08.02, 08.05).

## Check questions

1. **What is concurrency, and what is parallelism?**  
   Concurrency is the structure of independent progress and interleaving. Parallelism is simultaneous execution on multiple cores.

2. **What does CSP bring to the Go model?**  
   Focus on communication (channel) instead of sharing memory as the default tool.

3. **Why is a goroutine cheaper than an OS thread — and what is it not?**  
   Smaller initial stack, M:N scheduling, cheaper creation. But a goroutine *is not* a thread and *is not* free: it uses memory and can leak.

4. **What does GOMAXPROCS control?**  
   The number of P: how much Go code can execute in parallel. Not how many goroutine you may start.

5. **When does concurrency not speed up a program?**  
   When there is no overlapping waits and no parallel CPU work, or when the bottleneck is an external system / contention.

6. **Why does an unbuffered channel synchronize send and receive?**  
   Capacity is 0: send blocks until there is a receive (and vice versa). Rendezvous.

7. **What does a data race without synchronization mean?**  
   Undefined behavior. Detect with `go test -race` or `go run -race`.

## Deeper look: scheduler in practice

The Go scheduler uses preemption so long loops do not starve other goroutine. Still, long CPU work without checking cancellation keeps a core busy until you reach a point where the runtime and your code can react to `context`.

Practical rules:

1. Split batches of a million items into chunks and check `ctx.Done()` (08.02).
2. A shared Mutex on a hot path can eat the gain from more P.
3. `runtime.NumGoroutine()` in metrics is a cheap leak signal.
4. Do not mix “more P” with “more throughput toward the database” — the database has its own limit.

### Mini trace: what P is not

```text
Request arrives → handler starts 3 goroutine for HTTP GET
CPU = 10%, GOMAXPROCS = 8

Question: does raising GOMAXPROCS to 16 shorten the request?
Answer: do not expect it. G wait on the network; M are free to do other work.
Bottleneck is RTT of external services + sequential call ordering.
```

### Checklist before you add `go`

1. Does the work wait or compute?
2. Is there a measurable gain (overlap or parallelism)?
3. Who waits for completion and `error`?
4. Does `-race` pass after the change?
5. Does the documentation say a goroutine is started?

### Mini-example: ownership without sharing

```go
package main

import "fmt"

func main() {
	out := make(chan int, 1)
	go func() {
		sum := 0
		for i := 1; i <= 5; i++ {
			sum += i
		}
		out <- sum
	}()
	fmt.Println(<-out)
}
```

#### What happens here

The sum lives only in one goroutine. The channel carries the *finished result*, not a shared counter. That is CSP in one sentence of code.

**Predict the result:** what is printed?

**Answer:** `15`.

### Mini-example: reading GOMAXPROCS without changing it

```go
package main

import (
	"fmt"
	"runtime"
)

func main() {
	fmt.Println("NumCPU", runtime.NumCPU())
	fmt.Println("GOMAXPROCS", runtime.GOMAXPROCS(0))
}
```

#### What happens here

`GOMAXPROCS(0)` only reads. In 1.22+ expect the default to be near `NumCPU` (unless env was intentionally different).

**Predict the result:** are the two values always equal?

**Answer:** often yes on a clean machine; no if `GOMAXPROCS` env or code already changed the value.

## Summary

Concurrency structures a program; parallelism uses cores. Go combines the CSP idea with cheap goroutine and an M:N scheduler. A goroutine is not a thread and not a process. `GOMAXPROCS` tunes parallelism of Go code — measure before you touch it.
