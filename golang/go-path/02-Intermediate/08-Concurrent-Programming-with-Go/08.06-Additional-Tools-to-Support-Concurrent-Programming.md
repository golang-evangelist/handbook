# 08.06 Tools alongside concurrency: race, context, errgroup, singleflight, pprof

> **Go Path - Zero to Gopher** / **02 Intermediate → Concurrent Programming with Go** / Lesson 08.06

## Lesson goals

After this lesson you can:

- use the **race detector** (`go test -race`, `go run -race`) and treat a finding as a real bug
- harden **context** habits in libraries and handlers
- apply **errgroup** as the standard for task groups
- understand **singleflight** conceptually (`Do` / `Forget` in `golang.org/x/sync/singleflight`)
- look at a **goroutine** profile in pprof — HTTP **only on localhost**, never a public address

## Prerequisite

- Lessons 08.01–08.05
- Basic `go test`, HTTP handlers as desired
- A module with `golang.org/x/sync` for errgroup/singleflight

## Problem this lesson solves

Concurrent code can “work” in lucky tests, and in production:

- a data race corrupts a map
- lost errors from a group of calls
- thundering herd toward a cache or database on TTL expiry
- thousands of stuck goroutine without diagnosis

Tools do not replace design — they shorten time to evidence.

## Mental model

| Tool | Question |
|------|----------|
| `-race` | Are two goroutine racing on the same memory without synchronization? |
| `context` | Is this work still allowed to run? |
| `errgroup` | How do I wait for N tasks and take the first error? |
| `singleflight` | How do N identical misses do one real fetch? |
| pprof goroutine | Which goroutine are alive and where do they block? |

Diagnosis order: reproduce → `-race` / test → goroutine profile → only then change the pattern.

Without synchronization, a race is **undefined** behavior. The detector finds it; do not invent memory-model exceptions.

## Mechanism

### Race detector

```bash
go test -race ./...
go run -race .
```

Instruments memory accesses. It is slower and uses more RAM — in CI often on PRs. A finding is a **real bug**, not style.

Trace:

```text
G1: n++
G2: n++
without Mutex/atomic → -race reports counter.go:line
```

### Context (tooling layer)

- Input: `r.Context()`, `WithTimeout`, parent from the caller
- Output: every I/O API that takes `ctx`
- Do not store a request context in a long-lived service structure
- Always `defer cancel()` for WithCancel/WithTimeout/WithDeadline

### errgroup

The default tool for “parallel steps in one scope”. `WithContext` cancels the others on the first error. `SetLimit` (in newer x/sync) limits parallelism.

### singleflight — concept

Package `golang.org/x/sync/singleflight`:

- `Do(key, fn)` — for the same `key`, only one call actually runs `fn`; others wait for the same result/error
- `Forget(key)` — forget the key so the next `Do` runs again

Do not invent other API details. Classic use: cache miss — N requests for the same key must not fire N identical fetches toward the database.

```text
t=0  req A,B,C miss key=user:1
t=0  A enters Do — runs fetch
t=0  B,C wait on the same Do
t=1  fetch done — A,B,C get the same (v, err)
     the third return (shared) signals it was shared
```

Use only for **idempotent** fetches of the same key. Not for “charge a card”.

### pprof goroutine profile

`net/http/pprof` or `runtime/pprof` — type `goroutine` shows stacks of live goroutine.

**Safety:** bind HTTP pprof **only to localhost** (e.g. `127.0.0.1:6060`). **Never** on `0.0.0.0` on the public internet without strict control — the endpoint exposes process internals. Details in 14.02.

```text
Symptom: NumGoroutine grows
pprof goroutine → top stack: runtime.gopark → chan receive
conclusion: leak on <-ch (08.02/08.04)
```

## Rules and syntax

```go
import "golang.org/x/sync/singleflight"

var g singleflight.Group

v, err, shared := g.Do(key, func() (interface{}, error) {
	return fetch(key)
})
_ = shared
```

```go
// ONLY with a localhost listener — see example 1
import _ "net/http/pprof"
```

1. `-race` in CI for a package that touches sync
2. `errgroup.WithContext` when one fail cancels the others
3. `singleflight` only for idempotent fetches
4. pprof on `127.0.0.1`

## Examples

### Example 1 — Finding a race

```go
package counter

import "testing"

func TestRace(t *testing.T) {
	var n int
	done := make(chan struct{}, 2)
	go func() {
		n++
		done <- struct{}{}
	}()
	go func() {
		n++
		done <- struct{}{}
	}()
	<-done
	<-done
}
```

```bash
go test -race ./counter
```

#### What happens here

The detector reports a race on `n`. Fix: `atomic.Int64` or Mutex (08.03).

### Example 2 — errgroup SetLimit idea

```go
package main

import (
	"context"
	"fmt"

	"golang.org/x/sync/errgroup"
)

func main() {
	g, ctx := errgroup.WithContext(context.Background())
	g.SetLimit(4)
	for i := 0; i < 20; i++ {
		i := i
		g.Go(func() error {
			select {
			case <-ctx.Done():
				return ctx.Err()
			default:
				fmt.Println("job", i)
				return nil
			}
		})
	}
	_ = g.Wait()
}
```

#### What happens here

At most 4 `Go` bodies at once (SetLimit). Others wait for a slot — related to the bounded pool from 08.05.

### Example 3 — singleflight Do

```go
package main

import (
	"fmt"
	"sync"
	"time"

	"golang.org/x/sync/singleflight"
)

func main() {
	var g singleflight.Group
	var calls int
	var mu sync.Mutex

	fetch := func(key string) (interface{}, error) {
		mu.Lock()
		calls++
		mu.Unlock()
		time.Sleep(50 * time.Millisecond)
		return "data:" + key, nil
	}

	var wg sync.WaitGroup
	for range 10 {
		wg.Add(1)
		go func() {
			defer wg.Done()
			v, err, shared := g.Do("user:1", func() (interface{}, error) {
				return fetch("user:1")
			})
			fmt.Println(v, err, shared)
		}()
	}
	wg.Wait()
	fmt.Println("real fetches:", calls) // expect 1
}
```

#### What happens here

Ten parallel `Do` with the same key → one real `fetch`. Others share the result; `shared` is true for those that did not start fn (in a typical scenario).

**Predict the result:** After success you call `g.Forget("user:1")` then again 10× `Do`. How many fetches?

**Answer:** Again 1 (new round). `Forget` clears the remembered in-flight/result for the key so the next `Do` can run fn again.

### Example 4 — localhost pprof

```go
package main

import (
	"log"
	"net/http"
	_ "net/http/pprof"
)

func main() {
	mux := http.NewServeMux()
	// register app routes on mux...
	go func() {
		// ONLY localhost — never 0.0.0.0 for pprof in production without protection
		log.Println(http.ListenAndServe("127.0.0.1:6060", nil))
	}()
	log.Println(http.ListenAndServe(":8080", mux))
}
```

#### What happens here

`import _ "net/http/pprof"` registers handlers on **DefaultServeMux**. So the admin listener uses a `nil` handler (= DefaultServeMux) on 127.0.0.1:6060, and public :8080 uses a *separate* `mux` without pprof. More detail in 14.02.

**Never** do `ListenAndServe(":6060", nil)` on a public address.

### Example 5 — Context habit in a library

```go
func FetchUser(ctx context.Context, id string) (User, error) {
	req, err := http.NewRequestWithContext(ctx, http.MethodGet, url+id, nil)
	if err != nil {
		return User{}, err
	}
	res, err := http.DefaultClient.Do(req)
	if err != nil {
		return User{}, err
	}
	defer res.Body.Close()
	// decode...
	return User{}, nil
}
```

#### What happens here

Parent cancellation interrupts `Do`. The library does not start its own goroutine without documentation.

## Decision analysis

| Tool | When |
|------|------|
| -race | Every PR that touches shared state |
| errgroup | N steps, need the first error |
| WaitGroup | Only waiting for completion, no error |
| singleflight | Idempotent fetch of the same key |
| pprof goroutine | Suspected leak / stuck |

## Trade-offs

- **-race** — more expensive tests; catches real bugs
- **singleflight** — less pressure on the backend; also shares errors (everyone sees the same fail)
- **pprof HTTP** — powerful diagnosis; dangerous if publicly exposed

## Common mistakes

1. **Wrong code:** Ignore a `-race` report as “flaky”.  
   **What happens:** Corruption in production.  
   **Why:** A race is undefined.  
   **Fix:** Fix sync; keep -race in CI.

2. **Wrong code:** singleflight around charging.  
   **What happens:** One charge, multiple users share the result / or a shared error.  
   **Why:** The operation is not an idempotent read.  
   **Fix:** Only the fetch/read path.

3. **Wrong code:** `ListenAndServe("0.0.0.0:6060", nil)` with pprof.  
   **What happens:** Public leak of internals.  
   **Why:** pprof on all addresses.  
   **Fix:** `127.0.0.1` or protected admin.

4. **Wrong code:** Context in a service field.  
   **What happens:** Wrong lifetime; one request’s cancellation affects all.  
   **Why:** Context is per-request.  
   **Fix:** Pass as a parameter.

5. **Wrong code:** errgroup without passing ctx into I/O.  
   **What happens:** Other tasks do not stop.  
   **Why:** Cancellation must be listened to.  
   **Fix:** The same ctx in all calls.

6. **Wrong code:** Import pprof on DefaultServeMux that is also the public server.  
   **What happens:** `/debug/pprof` on the production port.  
   **Why:** Side-effect registration.  
   **Fix:** Separate mux / localhost (14.02).

## Idiomatic Go

- `-race` in CI
- `ctx` first argument
- errgroup for groups with error
- singleflight with cache miss
- pprof locally; measure before “optimization”

## Practical scenario

After deploy, goroutine count grows linearly with traffic and does not drop. `-race` clean. Local pprof on 127.0.0.1 shows mass `chan receive` in an old helper that forgot close. Fix from 08.04; the graph stabilizes. Second incident: thundering herd on cache TTL — `singleflight.Do` merges misses; QPS toward the database drops.

## Check questions

1. **What does a -race finding mean?**  
   A real bug — undefined behavior without sync.

2. **Do vs Forget?**  
   Do merges in-flight work for a key; Forget clears the key so fn runs again.

3. **Where may pprof HTTP live?**  
   Localhost (or strictly protected admin) — never the public internet casually.

4. **When singleflight?**  
   Idempotent fetch of the same key (cache miss).

5. **Why a separate mux?**  
   So `import _ "net/http/pprof"` does not open debug on the public port.

6. **Leak diagnosis order?**  
   NumGoroutine → pprof goroutine → find the block → fix ownership/close/ctx.

## Deeper mechanism: what -race sees

```text
Without sync:
  G1: write x
  G2: read x
  → race report (undefined)

With channel:
  G1: x=1; ch <- struct{}{}
  G2: <-ch; read x
  → OK: communication synchronizes

With Mutex:
  G1: Lock; x=1; Unlock
  G2: Lock; read x; Unlock
  → OK
```

Do not claim “it works on x86 so it is not a race”. The detector is the authority for the course.

## Example 6 — Reading a goroutine profile (locally)

```bash
# terminal 1: app with pprof on 127.0.0.1:6060
# terminal 2:
go tool pprof http://127.0.0.1:6060/debug/pprof/goroutine
# then in interactive mode:
#   top
#   list functionName
```

Leak diagnosis trace:

```text
1. NumGoroutine grows
2. pprof goroutine → top shows N × runtime.gopark
3. list shows your package: v := <-ch
4. Nobody sends / closes ch
5. Add ctx or close — count drops
```

CPU profile (stack samples) and heap profile (allocations) are different questions — 14.01/14.02. Here the focus is: **who is alive and where they stand**.

## Example 7 — errgroup vs manual WaitGroup (comparative trace)

```go
// Manual: easy to forget cancellation
var wg sync.WaitGroup
errCh := make(chan error, len(tasks))
for _, t := range tasks {
	wg.Add(1)
	go func(t Task) {
		defer wg.Done()
		errCh <- t.Run(ctx) // ctx may not be cancelled when the first fails
	}(t)
}
wg.Wait()
close(errCh)
```

```go
// errgroup: first error cancels ctx
g, ctx := errgroup.WithContext(parent)
for _, t := range tasks {
	t := t
	g.Go(func() error { return t.Run(ctx) })
}
err := g.Wait()
```

When `t.Run` respects `ctx`, the second variant stops the rest. The first often “burns” CPU/network after a fail.

## Example 8 — singleflight and cache together (concept)

```text
1. Lookup cache
2. Hit → return
3. Miss → g.Do(key, fetch)
4. Write to cache (under Mutex)
5. Return

Without singleflight: 500 misses at once = 500 fetches
With singleflight: 500 misses = 1 fetch, 499 wait
```

`Forget(key)` is used when you know the cache was invalidated and want the next `Do` to actually fetch again, not to stick to an old in-flight result in some edge cases. Do not invent other methods — `Do` and `Forget` are enough for this course.

**Predict the result:** Five goroutine call `Do("k", fn)` while `fn` is still running. How many times does `fn` run?

**Answer:** Once. The others wait for the same result.

## Mini runbook: concurrency incident

1. Metric: `runtime.NumGoroutine()` — does the floor grow?
2. `go test -race` locally on the suspect package.
3. pprof goroutine on **127.0.0.1** — where does it block?
4. If `chan receive`: ownership/close/ctx (08.02/08.04).
5. If thundering herd on cache: singleflight.
6. If OOM with millions of goroutine: bound pool (08.05).
7. Measure after the change — do not trust feeling.

## Deeper example: CPU vs goroutine profile (what you choose)

```text
Symptom A: latency high, CPU 95%
  → CPU profile (stack samples) — where time is spent
  → NOT goroutine profile first

Symptom B: latency high, CPU 10%, NumGoroutine grows
  → goroutine profile — where they block
  → often chan receive / select

Symptom C: memory grows, GC frequent
  → heap / allocs profile (14.01)
```

Without a measure you pick the wrong tool. This lesson closes the concurrency tooling layer; 14.xx teaches reading profiles.

## Example 9 — Forget after invalidation

```go
var g singleflight.Group

func invalidate(key string) {
	cache.Delete(key)
	g.Forget(key)
}

func get(key string) (interface{}, error) {
	v, err, _ := g.Do(key, func() (interface{}, error) {
		return fetch(key)
	})
	return v, err
}
```

#### What happens here

After deleting the cache, `Forget` prevents a new `Do` from wandering into a stale in-flight agreement for the same key in edge cases. For ordinary hit/miss cache often only `Do` is enough; `Forget` is an explicit key reset.

## Example 10 — Context in a test

```go
func TestFetchTimeout(t *testing.T) {
	ctx, cancel := context.WithTimeout(context.Background(), 10*time.Millisecond)
	defer cancel()
	err := slowFetch(ctx)
	if !errors.Is(err, context.DeadlineExceeded) {
		t.Fatalf("got %v", err)
	}
}
```

#### What happens here

The test proves `slowFetch` listens to `ctx`. Without that, timeout in production does not work. This is a cheaper check than a full pprof.

## Example 11 — What pprof must NOT do

// FORBIDDEN in production facing the internet:

// ALLOWED:

```text

Therefore: only localhost or admin network with auth
```

## Example 12 — Combining tools in one handler

```go
func (h *Handler) ServeHTTP(w http.ResponseWriter, r *http.Request) {
	ctx := r.Context()
	key := r.URL.Query().Get("id")

	v, err, shared := h.sf.Do(key, func() (interface{}, error) {
		g, ctx := errgroup.WithContext(ctx)
		var a, b string
		g.Go(func() error {
			var e error
			a, e = h.fetchA(ctx, key)
			return e
		})
		g.Go(func() error {
			var e error
			b, e = h.fetchB(ctx, key)
			return e
		})
		if e := g.Wait(); e != nil {
			return nil, e
		}
		return a + b, nil
	})
	if err != nil {
		http.Error(w, "upstream", http.StatusBadGateway)
		return
	}
	_, _ = shared
	_, _ = fmt.Fprint(w, v)
}
```

#### What happens here

1. Same `key` miss: one real errgroup fetch (singleflight).
2. Inside the fetch: two upstream calls in parallel, first error cancels.
3. `r.Context()` ties lifetime to the client.
4. No unbounded `go` per item.

That is lessons 08.02–08.06 joined in one request path.

### Mini trace: shared from Do

`shared == true` means your call did not start `fn`, but waited on someone else’s in-flight work. What matters is one fetch per key — do not build business logic solely on `shared` without docs for your `x/sync` version.

### Why localhost, once more

`0.0.0.0:6060` + blank import pprof = debug surface on all addresses. The course allows only `127.0.0.1` or an equivalent admin tunnel.

### Link 08 → 14

## Last reminder before 09.xx

Concurrency without measurement is guessing. After every sync pattern change:

1. `go test -race` on the package.
2. Look at `NumGoroutine` under a short load.
3. If you suspect a leak — localhost pprof goroutine.
4. If you suspect CPU — do not touch GOMAXPROCS before a profile (14.xx).


5. Document in the PR which sync contract applies (who closes the channel, who holds the Mutex).
6. Do not merge `ListenAndServe("0.0.0.0:6060", nil)` with pprof.

When these six points become reflex, the tooling layer is no longer theory.

That is the exit card from module 08.
