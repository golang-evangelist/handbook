# 10.05 Authentication and Password Management

> **Go Path - Zero to Gopher** / **02 Intermediate → Secure Coding in Go** / Lesson 10.05

## Lesson goals

After this lesson you should:

- store passwords as **bcrypt** or **argon2id** hashes, never as plain text or fast general-purpose hashes
- generate tokens and nonce values with `crypto/rand`, never with `math/rand`
- compare tokens with `subtle.ConstantTimeCompare` where timing could leak equality
- return a **generic** message on failed login (do not reveal “email exists”)
- connect authentication with password confidentiality and verification integrity
- know why a homemade KDF is not acceptable

## Prerequisite

- Go 1.22+; `[]byte`, `error`
- 10.01–10.04; basic HTTP handler
- `golang.org/x/crypto/bcrypt` or `argon2` from x/crypto

## Problem this lesson solves

A database leak with plain passwords or fast hashes (e.g. a single SHA-256 without salt and without a slow KDF) means mass account compromise. Authentication must assume the hash table will leak one day: the goal is to make offline guessing expensive, and the server must never log the plain password.

Another failure: session tokens or reset links from `math/rand` — predictable. Third: different messages “unknown email” / “wrong password” that make account enumeration easier.

## Mental model

1. **Password is a short-lived secret in memory** — receive, hash, forget plain.
2. **On disk only the KDF output lives** (bcrypt/argon2id) with built-in salt.
3. **Verification** uses the library (`CompareHashAndPassword`), not manual `==` on a hash you “assembled yourself”.
4. **Tokens** (session, CSRF, reset) — `crypto/rand` bytes, sufficient length.
5. **Message to client** — same for “no user” and “wrong password”.
6. **Constant-time compare** — for *tokens* of the same length you compare as secrets; bcrypt compare already has its own API.

```text
registration: plain → bcrypt/argon2id → store hash
login: plain + hash → Compare → OK? issue session (10.06)
token: crypto/rand → store hash or opaque ID
```

## Mechanism

### Why not a general hash for passwords

SHA-256, BLAKE2, and similar are fast — by design. Offline guessing on a GPU runs millions of attempts. Password KDF (bcrypt, argon2id) is **slow** and consumes resources by design; it has **salt** per record so the same password does not yield the same hash.

Impact of wrong choice: table leak → fast compromise of accounts with weak passwords and often strong ones too.

### bcrypt in Go

Package: `golang.org/x/crypto/bcrypt`.

```go
hash, err := bcrypt.GenerateFromPassword([]byte(plain), bcrypt.DefaultCost)
err = bcrypt.CompareHashAndPassword(hash, []byte(plain))
```

- Choose cost (e.g. 10–14) according to login CPU budget; measure on your hardware.
- Salt is inside the bcrypt string — do not store separately.
- On Compare error treat as authentication failure.

### argon2id

`golang.org/x/crypto/argon2` — Argon2id is the modern recommendation (memory-hard). You must serialize parameters (time, memory, threads, salt, key) yourself into the format you store. Do not invent an ad-hoc “argon2 + HMAC” protocol; follow an established format or a library with a clear API.

This lesson shows bcrypt as the shortest std-ecosystem path; argon2id is an equal choice if the team already has parameters and a storage format.

### crypto/rand versus math/rand

| Use | Generator |
|----------|-----------|
| Session ID, reset token, CSRF, key | `crypto/rand` |
| Telemetry jitter in tests, display shuffle | `math/rand/v2` OK |

```go
b := make([]byte, 32)
if _, err := rand.Read(b); err != nil {
	return nil, err
}
```

If `Read` returns an error — fail closed; no token.

### subtle.ConstantTimeCompare for tokens

When comparing two secret `[]byte` of the same length (e.g. expected CSRF and submitted):

```go
import "crypto/subtle"

if subtle.ConstantTimeCompare(expected, got) != 1 {
	return errUnauthorized
}
```

Why: ordinary comparison / `ConstantTimeCompare` reduces information leakage through execution time when comparing. **Does not** replace the bcrypt API for passwords — there use `CompareHashAndPassword`. **Do not** use as a slogan on password strings of different lengths without KDF.

`hmac.Equal` is also constant-time for same-length fields and is often the idiomatic choice.

### Generic login message

```text
client always sees: "invalid credentials" + 401
log internally: user_not_found | bad_password | db_error (with request id)
```

Confidentiality: do not reveal which email exists. Availability: same timing budget where you can (e.g. always run Compare with a dummy hash if user does not exist — advanced practice; minimum is the same message).

### Rehash on login

If policy raises bcrypt cost, on successful Compare:

```go
if bcrypt.Cost(hash) < minCost {
	newHash, err := bcrypt.GenerateFromPassword(plain, minCost)
	// save newHash
}
```

Plain is briefly in memory only during that request.

### What not to log

- plain password
- Authorization header
- reset token in full form (you can hash the token in the store)
- bcrypt hash in info logs without need

### Bounds on password length

Minimum length (e.g. ≥ 12) + maximum (e.g. ≤ 72 for bcrypt truncate behavior — document). Reject too short; do not “sanitize” password by replacing characters.

### Link to CIA and least privilege

| Practice | Principle |
|--------|---------|
| KDF hash | confidentiality at rest for passwords |
| crypto/rand token | integrity/unpredictability of secret |
| generic message | confidentiality of account existence |
| session after login | least privilege of time + 10.06 |

### Dummy hash (optional, in more detail)

So response time is more similar when user does not exist, some systems compare against a pre-generated bcrypt hash. That is an availability/anti-enumeration technique; do not reveal in the response that you used a dummy.

## Rules

1. Only bcrypt or argon2id for passwords.
2. Never `math/rand` for security tokens.
3. `GenerateFromPassword` / `CompareHashAndPassword` — not homemade.
4. Generic 401 message to client.
5. Do not log plain or reset tokens in full form.
6. Bounds on password length before KDF.
7. ConstantTimeCompare / `hmac.Equal` for tokens of the same length.
8. After successful login: session rotation (10.06).

## Examples

### Example 1 — HashPassword / CheckPassword

```go
package authn

import (
	"fmt"

	"golang.org/x/crypto/bcrypt"
)

const minCost = bcrypt.DefaultCost

func HashPassword(plain string) ([]byte, error) {
	if len(plain) < 12 || len(plain) > 72 {
		return nil, fmt.Errorf("password_length")
	}
	return bcrypt.GenerateFromPassword([]byte(plain), minCost)
}

func CheckPassword(hash []byte, plain string) bool {
	err := bcrypt.CompareHashAndPassword(hash, []byte(plain))
	return err == nil
}
```

#### What happens here

Registration stores `HashPassword` output. Login uses `CheckPassword`. Cost is explicit. Length is rejected before KDF.

### Example 2 — random token

```go
package authn

import (
	"crypto/rand"
	"encoding/base64"
	"fmt"
)

func NewToken(nBytes int) (string, error) {
	if nBytes < 16 {
		return "", fmt.Errorf("token too short")
	}
	b := make([]byte, nBytes)
	if _, err := rand.Read(b); err != nil {
		return "", err
	}
	return base64.RawURLEncoding.EncodeToString(b), nil
}
```

#### What happens here

32 bytes of entropy → URL-safe string for cookie or link. Read error propagates.

### Example 3 — constant-time token check

```go
package authn

import (
	"crypto/subtle"
)

func TokenOK(expected, got []byte) bool {
	if len(expected) == 0 || len(expected) != len(got) {
		return false
	}
	return subtle.ConstantTimeCompare(expected, got) == 1
}
```

#### What happens here

Used for CSRF/session opaque bytes of the same length. For passwords still bcrypt Compare. Different lengths → fail without Compare (avoid leaking length through branches where you can align).

### Example 4 — login handler (generic response)

```go
func (h *Handler) Login(w http.ResponseWriter, r *http.Request) {
	var in struct {
		Email    string `json:"email"`
		Password string `json:"password"`
	}
	if err := json.NewDecoder(http.MaxBytesReader(w, r.Body, 1<<20)).Decode(&in); err != nil {
		http.Error(w, "bad request", http.StatusBadRequest)
		return
	}
	u, err := h.users.ByEmail(r.Context(), in.Email)
	ok := err == nil && CheckPassword(u.PasswordHash, in.Password)
	if !ok {
		h.log.Info("login_failed", "email_domain", domainOf(in.Email)) // don't log plain
		http.Error(w, "invalid credentials", http.StatusUnauthorized)
		return
	}
	if err := h.sessions.CreateRotated(r.Context(), w, u.ID); err != nil {
		h.log.Error("session", "err", err)
		http.Error(w, "request failed", http.StatusInternalServerError)
		return
	}
	w.WriteHeader(http.StatusNoContent)
}
```

#### What happens here

One message for all auth failures. Session created in a separate layer. Internal log without password.

func TestCheckPassword(t *testing.T) {
	h, err := HashPassword("correct-password-12")

## Decision analysis

| Decision | Why |
|--------|-------|
| bcrypt/argon2id | slow KDF + salt |
| crypto/rand | cryptographic entropy |
| generic 401 | anti-enumeration |
| ConstantTimeCompare for tokens | less timing leakage |
| Rehash option | raising cost policy |
| Bounds before KDF | availability + bcrypt limits |

## Trade-offs

- **Higher cost** = slower login (availability UX) vs harder offline guessing.
- **Argon2 memory** can be a problem in dense containers — measure.
- **Dummy hash** complicates code; minimum is the same message.
- **Max 72 bytes bcrypt** — document or use argon2id for longer passphrase policies.

## Common mistakes

1. Plain or fast hash in database.
2. `math/rand` for tokens.
3. Different login messages.
4. Logging password.
5. Homemade HMAC-password scheme.
6. `==` on password string in database.
7. ConstantTimeCompare as replacement for bcrypt.
8. No max length → DoS on KDF (availability).
9. Storing reset token in plain in log.
10. Losing salt “because we hashed email+password” homemade.

## Idiomatic Go

- Package `authn` with Hash/Check; session in `authz`/`session`.
- `[]byte` for hash in struct; not string if you can avoid it.
- Tests without golden hash values.
- `x/crypto` modules — add to go.mod deliberately, follow govulncheck (10.02).

## Practical scenario

Startup stores SHA-256 hex passwords. On backup leak forces reset. Migration: on login if legacy hash, verify legacy once, then `HashPassword` bcrypt and save; disable legacy after grace period. Tokens move to `crypto/rand`. Client messages unified. Audit: plain no longer in log aggregator.

### API focus: bcrypt.GenerateFromPassword

Passwords are not stored in plaintext nor as plain SHA-256. `bcrypt.GenerateFromPassword` includes salt and cost — slow on purpose for offline resistance.

```go
package auth

import (
	"fmt"

	"golang.org/x/crypto/bcrypt"
)

const bcryptCost = bcrypt.DefaultCost

func HashPassword(plain string) ([]byte, error) {
	if len(plain) < 12 || len(plain) > 128 {
		return nil, fmt.Errorf("password_policy")
	}
	return bcrypt.GenerateFromPassword([]byte(plain), bcryptCost)
}
```

### API focus: bcrypt.CompareHashAndPassword

Comparison must go through the bcrypt API — do not decode hash manually. Treat error `err == bcrypt.ErrMismatchedHashAndPassword` the same as “no user” externally.

```go
func VerifyPassword(storedHash []byte, plain string) error {
	return bcrypt.CompareHashAndPassword(storedHash, []byte(plain))
}
```

### API focus: crypto/rand.Read

Tokens for password reset, magic link, and session ID must be cryptographically random — `crypto/rand`, not `math/rand`.

```go
func randomToken(n int) (string, error) {
	b := make([]byte, n)
	if _, err := rand.Read(b); err != nil {
		return "", err
	}
	return base64.RawURLEncoding.EncodeToString(b), nil
}
```

### API focus: crypto/subtle.ConstantTimeCompare

When comparing static secrets (API key, HMAC digest, reset token hash), use constant-time compare so length or prefix does not leak through timing.

```go
func safeEqual(a, b []byte) bool {
	return subtle.ConstantTimeCompare(a, b) == 1
}
```

### API focus: argon2.IDKey (alternative)

For new systems the team sometimes chooses Argon2id. Parameters must be documented and tested — same principle: never SHA256(password).

```go
import "golang.org/x/crypto/argon2"

func hashArgon2id(password, salt []byte) []byte {
	return argon2.IDKey(password, salt, 2, 64*1024, 4, 32)
}
```

### API focus: password policy check

Length and complexity checked before hash — without “sanitize” characters.

```go
func ValidatePasswordPolicy(pw string) error {
	if len(pw) < 12 {
		return fmt.Errorf("password_too_short")
	}
	if len(pw) > 128 {
		return fmt.Errorf("password_too_long")
	}
	return nil
}
```

### API focus: timing-safe login response

Always run bcrypt compare (dummy hash if user does not exist) so response time does not reveal account existence — optional, with care not to complicate code unnecessarily; minimum is the same HTTP message.

```go
var dummyHash = []byte("$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy")

func compareOrDummy(stored []byte, pw string) error {
	if stored == nil {
		stored = dummyHash
	}
	return bcrypt.CompareHashAndPassword(stored, []byte(pw))
}
```

### API focus: reset token storage

Store hash of token (SHA-256 or HMAC), not plaintext token in database.

```go
func hashResetToken(token string, pepper []byte) []byte {
	h := sha256.New()
	h.Write(pepper)
	h.Write([]byte(token))
	return h.Sum(nil)
}
```

### API focus: verify email token

One-time token with expiry — delete after use.

```go
func (s *Service) ConsumeVerifyToken(ctx context.Context, token string) error {
	sum := hashResetToken(token, s.pepper)
	row, err := s.repo.FindVerifyByHash(ctx, sum)
	if err != nil || row.ExpiresBefore(time.Now()) {
		return ErrInvalidToken
	}
	return s.repo.MarkVerifiedAndDeleteToken(ctx, row.UserID)
}
```
