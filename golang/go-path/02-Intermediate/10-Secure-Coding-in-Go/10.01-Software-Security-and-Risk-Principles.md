# 10.01 Software Security and Risk Principles

> **Go Path - Zero to Gopher** / **02 Intermediate → Secure Coding in Go** / Lesson 10.01

## Lesson goals

After this lesson you should:

- connect **confidentiality**, **integrity**, and **availability** to concrete Go decisions (what you read, what you write, what you time out)
- apply **least privilege** as a design principle: DB account, process, token, file descriptor
- sketch a simple threat model at design level (assets, trust boundaries, controls) without attack recipes
- distinguish a trust assumption from a technical control
- choose **fail closed** when a check cannot complete, and understand when that hits availability
- know what this area deliberately does not teach (offensive steps, payloads, bypass recipes)

## Prerequisite

- Go 1.22+ installed; you can read `net/http` handlers and `error` values
- Basics path: types, packages, modules, errors as values
- desirable: experience with `go.mod` and running a small HTTP service
- following lessons (10.02–10.14) assume this vocabulary

## Problem this lesson solves

Security is often treated as a final layer: “we’ll add TLS, then login, then something around passwords.” In practice most serious failures happen earlier—in assumptions about who may see what, where the trust boundary is, and what happens when a condition is not met.

Without shared language, teams stack techniques without a frame: validation exists but you do not know *why*; authorization exists on one endpoint but not another; the DB account has permissions “just in case.” This lesson sets the frame: what we protect, from whom in terms of *roles and boundaries*, and by which defensive principles. Later lessons turn principles into Go APIs.

## Mental model

Imagine a Go service as a building with multiple entrances, rooms, and keys:

1. **Asset** — data or capability that matters: PII, session token in the store, admin action, private key, monetary transaction.
2. **Trust boundary** — place where the level of trust changes: public HTTP entry, internal gRPC, database, file system, message queue, env at startup.
3. **Control** — mechanism that reduces risk: authentication, authorization, encryption, validation, audit log, timeout, least-privilege account.
4. **Assumption** — what you believe is true without a control in *your* code (e.g. “only VPN can reach this port”). Assumptions must be explicit.
5. **Blast radius** — how much damage if one control or one secret fails.

Secure design does not mean “no mistakes.” It means: a mistake has limited blast radius, privileges are minimal, and critical decisions are checked at *every* trust boundary—not only on the login form.

```text
[Client] --HTTPS--> [Go API] --TLS--> [Postgres]
                |              |
           trust ↑        trust ↑
        (untrusted input) (internal, but
                           still authz
                           + least privilege)
```

## Mechanism

### Confidentiality, integrity, availability as Go decisions

The three classic goals are not decoration on a security checklist. Each maps to choices in code and operations.

| Goal | Meaning | Typical Go / ops decision |
|------|---------|---------------------------|
| Confidentiality | only authorized parties see the data | TLS, ACL in handler, secrets outside source, AEAD for sensitive fields |
| Integrity | data is not changed without authorization | signature/HMAC where needed, AEAD tag, parameterized SQL, immutable audit |
| Availability | service stays usable | `context` timeout, `ReadHeaderTimeout`, rate limit at boundary, graceful degrade |

**Confidentiality in Go** is not only “there is HTTPS.” It is also: do not log passwords; do not return internal stack to the client; do not put API keys in the repo; do not give the handler access to the whole bucket if one prefix is enough.

**Integrity in Go** is not only a file checksum. It is: the database must not interpret user text as SQL (placeholders); HTML must not interpret user text as markup (`html/template`); tokens are not compared “approximately.”

**Availability in Go** is not only horizontal scale. It is: a goroutine does not leak forever on a channel; a query has a deadline; the HTTP server has timeouts; fail closed on auth must not turn the whole cluster unavailable without a plan (cache, stale-read policy—documented).

Every decision can improve one goal and worsen another. Aggressive rate limiting protects availability from overload, but poor tuning hurts legitimate clients. Strict fail closed protects confidentiality/integrity when the auth service is down, but reduces availability during that outage.

### Least privilege as the first design filter

Process, database user, token, and open file should have the **minimum privileges** needed for the job. In a Go service that looks like:

- DB account without DDL if runtime only reads and writes rows
- HTTP principal without admin role “just in case”
- file descriptor read-only when write is not needed (`os.O_RDONLY`)
- session token bound to one user and short TTL, not an “eternal master key”
- CI token only for deploying one service, not the whole org

If a token “can do everything,” one leak is a disaster. If a token can only what is needed, a leak is still an incident—but blast radius is smaller. Least privilege does not eliminate risk; it **narrows impact**.

Connect the principle to a Go type, not a slogan:

```go
type Principal struct {
	UserID string
	Roles  []string // explicit; empty ≠ admin
}

func (p Principal) Can(action string) bool {
	for _, r := range p.Roles {
		if r == action || r == "admin."+action {
			return true
		}
	}
	return false // deny by default
}
```

Zero value for `Principal{}` must not mean “superuser.” Zero value here means “no roles” → deny.

### Defense in depth (layers, not five of the same tool)

One control is not enough. Layers cover different *kinds* of mistakes:

1. transport (TLS, cert validation)
2. authentication (who is calling)
3. authorization per action (what they may do)
4. input validation (allow-list, lengths)
5. output encoding (HTML/JSON context)
6. least privilege on DB and files
7. logging + monitoring (detection, not a replacement for control)
8. backup / restore (availability after failure)

If one layer fails, another slows or stops damage. Defense in depth is not “five auth libraries.” It is deliberately placing different controls on different trust boundaries.

### Threat modeling at design level (without offense)

Threat modeling in this lesson is **not** an attack recipe. It is a map of risk and decisions:

1. **List assets** — PII, session store, API keys, admin endpoints, monetary actions.
2. **Draw trust boundaries** — where untrusted input enters; where internal space begins.
3. **For each boundary ask** — what goes wrong if input is unchecked, if a token expires, if a dependency fails, if an account has overly broad rights.
4. **Choose controls** — which controls reduce likelihood or impact.
5. **Document assumptions** — e.g. “reverse proxy terminates TLS” must be explicit, otherwise the team thinks the Go process “has HTTPS” while listening plain HTTP internally without network control.

A simple diagram is enough to start:

```text
Internet
   |
   v
[Load balancer / TLS terminate]  <-- assumption: validates cert, forwards identity header?
   |
   v
[Go service :8080]               <-- controls: authn, authz, validation, timeout
   |
   +--> [Postgres]              <-- least privilege account, TLS to database
   +--> [Object storage]        <-- scoped credential
   +--> [Secret store / env]    <-- secrets outside source
```

### Risk = likelihood × impact

You do not treat all threats equally. An admin session is worth more than public `GET /healthz`. You prioritize controls where impact is high. The matrix is not magic—it is team agreement on work order.

| Asset | Likelihood (1–5) | Impact (1–5) | Priority |
|---------|-------------------|--------------|-----------|
| Refund admin action | 3 | 5 | 15 |
| Public product catalog | 4 | 1 | 4 |
| Session cookie store | 3 | 4 | 12 |

### Fail closed versus fail open

When a check cannot complete (auth service timeout, unknown error, missing config):

- **Fail closed** — reject the request (403/503 per policy). Preserves confidentiality and integrity.
- **Fail open** — allow the request “so the system works.” Preserves availability short term, but widens blast radius.

In a Go handler fail closed looks explicit:

```go
func (h *Handler) Refund(w http.ResponseWriter, r *http.Request) {
	p, err := h.auth.Principal(r.Context())
	if err != nil {
		// we do not know who this is — do not perform monetary action
		http.Error(w, "unauthorized", http.StatusUnauthorized)
		return
	}
	if !p.Can("finance.refund") {
		http.Error(w, "forbidden", http.StatusForbidden)
		return
	}
	// ...
}
```

If `Principal` returns an error and you “let it through,” that is fail open on the most expensive action.

### Trace: from HTTP request to control

Follow one request through boundaries. This is a **trace of defensive decisions**, not an attack trace.

```text
1. TCP accepted
2. TLS handshake (or assumption that terminate is on proxy — document)
3. http.Server timeouts limit header/body read duration
4. middleware: request ID, recover, authn
5. handler: path value + type/length validation
6. authz: Can(action) on server, deny by default
7. domain: business rule
8. repository: SQL with placeholder, owner_id = ?
9. response: html/template or encoding/json; generic error to client
10. log: internal detail + request ID, no secrets
```

If step 6 is missing, steps 7–8 do not run. That is least privilege in the control flow, not only in the DB account.

### Predict, then check (1)

Read the following snippet. **Predict** what is wrong relative to CIA / least privilege, *before* you read the answer.

```go
func (h *Handler) GetInvoice(w http.ResponseWriter, r *http.Request) {
	id := r.PathValue("id")
	inv, err := h.db.QueryInvoice(r.Context(), id) // SELECT * FROM invoices WHERE id=$1
	if err != nil {
		http.Error(w, err.Error(), 500)
		return
	}
	_ = json.NewEncoder(w).Encode(inv)
}
```

**Your hypothesis (stop here):** which goals do you break?

<details>
<summary>Answer</summary>

- **Confidentiality:** no authn/authz — anyone who knows the ID can see the invoice (IDOR class problem at design level: missing ownership check).
- **Integrity/confidentiality of response:** `err.Error()` to the client leaks internal detail.
- **Least privilege of data:** query does not bind `owner_id` to the principal.
- Fix at principle level: authenticate → authorize → `WHERE id=$1 AND owner_id=$2` → generic error to client, detail in log.

</details>

### Predict, then check (2)

```go
dsn := "postgres://app:app@db/app?sslmode=disable"
db, _ := sql.Open("postgres", dsn)
```

**Predict:** which principles suffer?

<details>
<summary>Answer</summary>

- Secret in source (or at least in binary string) — confidentiality.
- Ignored error — availability/integrity (you operate with a bad connection).
- `sslmode=disable` — confidentiality in transit to the database.
- Least privilege is not visible here, but one hard-coded account often becomes a “shared superuser” through copy-paste.

</details>

### Assumption versus control

| Statement | Type | What to do |
|-------|-----|-------------|
| “Only internal network sees :9001” | assumption | document + network control; still authz in code |
| `if !p.Can("x") { 403 }` | control | stays in code regardless of network |
| “Proxy adds X-User-Id” | assumption | verify signature/identity; do not trust raw header from the internet |
| TLS min 1.2 in `tls.Config` | control | explicit in process or on proxy (single source of truth) |

An assumption without documentation becomes an invisible SPOF. A control without an assumption about the environment may be misconfigured (e.g. app expects TLS terminate but proxy does not send HTTPS to the client).

### Asset catalog as a code contract

Keep a small catalog close to the domain—not as a PDF nobody reads:

```go
package security

type DataClass string

const (
	DataPublic   DataClass = "public"
	DataInternal DataClass = "internal"
	DataPII      DataClass = "pii"
	DataSecret   DataClass = "secret"
	DataPayment  DataClass = "payment"
)

type Asset struct {
	Name      string
	Class     DataClass
	Controls  []string // e.g. "authz:owner", "tls", "audit"
}
```

This is not runtime enforcement by itself. It is language for review: “does the endpoint for `DataPayment` have audit and strict authz?”

### What this lesson deliberately does not do

- It does not give exploitation steps, payloads, or “how to bypass” a control.
- It does not teach social engineering.

### Trace: process boot as a trust boundary

When the Go process starts you already cross trust boundaries—often invisible in handlers:

```text
1. OS runs the binary (who signed it / where is the image from?)
2. Reading env / secret store (may the secret sit in shell history?)
3. Parsing config (fail closed if required field missing)
4. Opening DB / queue (least privilege account, TLS to peer)
5. Bind address (localhost vs 0.0.0.0 — availability vs exposure)
6. http.Server ListenAndServe (timeouts already set?)
```

If step 3 “assumes” empty admin password when env is missing, that is fail open at the boot boundary. Idiomatic Go: return `error` from `LoadConfig` and do not call `Listen` until config is valid.

```go
func main() {
	cfg, err := LoadConfig()
	if err != nil {
		slog.Error("config", "err", err)
		os.Exit(1)
	}
	// only now build the server
	_ = cfg
}
```

### Predict, then check (3) — role in JWT claim without server check

```go
func (h *Handler) Admin(w http.ResponseWriter, r *http.Request) {
	role := r.Header.Get("X-Role") // "frontend sends admin"
	if role == "admin" {
		h.doAdmin(w, r)
		return
	}
	http.Error(w, "forbidden", http.StatusForbidden)
}
```

**Predict:** which principles fail?

<details>
<summary>Answer</summary>

The client controls the header—that is not authentication or authorization. Integrity of the decision “who may admin” is zero; confidentiality of admin data fails as soon as someone sends the same header. Fix: server derives roles from session store / token *issued and signed* by the server (or IdP), never from a raw client header from the internet.

</details>

### Availability is not an excuse for weak authz

A common compromise teams draw wrongly: “auth must be fast, so we cache Can() forever.” Cache without TTL and without invalidation after role revocation keeps **old allow**—authorization integrity suffers. Correct compromise: short TTL, invalidation on logout/revoke, and fail closed when the store is unavailable for sensitive actions.

### Minimal ADR template with the service

```text
## Assumptions
- TLS terminate on load balancer; app listens plain HTTP only on private network
- Session store is Redis with ACL account only for this service

## Controls in code
- RequireAuth on /v1/*
- RequireCan per route
- ReadHeaderTimeout=5s

## Accepted risks
- /metrics on internal network without auth (until Q3); network ACL documented
```

ADR does not replace code. It prevents an assumption living only in one engineer’s head.

### Table: Go choice ↔ principle (extended overview)

| Go choice | Principle | Why |
|----------|---------|-------|
| `context.WithTimeout` on query | availability + least privilege of time | query does not hold connection forever |
| `os.O_RDONLY` | least privilege | process cannot write if not needed |
| `http.Error(..., 401)` without `err.Error()` | confidentiality | client does not see internal detail |
| DB account without `DROP` | least privilege | DSN leak ≠ schema destruction |
| `Principal.Can` default false | integrity of authz | zero value is not admin |
| TLS min 1.2 (later 10.10) | confidentiality in transit | old protocols are weak |
| session rotation after login (10.06) | session integrity | old ID does not stay valid |
| `html/template` (10.04) | display integrity | data ≠ markup |
| placeholder `$1` (10.12) | SQL integrity | data ≠ command |
| `filepath` confine (10.13) | file confidentiality | path must not escape base |

This table is a bridge to the rest of the area: principles from 10.01 are not slogans—they choose APIs.

### Mini scenario: three wrong assumptions

1. “Frontend hides the admin button” → not a control; server must `Can`.
2. “VPN is enough” → assumption; still validation + authz.
3. “Health check may return config” → leakage; health returns status only.

Every assumption without control in code or network deserves an ADR entry.

## Rules

1. For every new endpoint name the asset and data class before writing SQL.
2. Every trust boundary has at least one explicit control in code or infrastructure—not assumption alone.
3. Privileges: default deny; add permission, do not subtract from “everything allowed.”
4. When authz/authn cannot run, fail closed for sensitive actions.
5. Document assumptions about proxy, network, and secrets in README or ADR next to the service.
6. Risk measures (likelihood × impact) drive work order, not a “this is interesting” feeling.
7. Do not log secrets; do not return internal `error` string to the client.
8. Least privilege applies to DB account, file, token, and IAM—not only “user role” in JWT.

```go
// Pseudo-rule in middleware: no principal → no continuation
func RequireAuth(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		if PrincipalFrom(r.Context()) == nil {
			http.Error(w, "unauthorized", http.StatusUnauthorized)
			return
		}
		next.ServeHTTP(w, r)
	})
}
```

## Examples

### Example 1 — asset catalog and control mapping

```go
package security

var Catalog = []Asset{
	{
		Name:  "user.profile.email",
		Class: DataPII,
		Controls: []string{
			"authn:session",
			"authz:self-or-admin",
			"log:no-value",
			"tls",
		},
	},
	{
		Name:  "order.refund",
		Class: DataPayment,
		Controls: []string{
			"authn:session",
			"authz:finance.refund",
			"audit:who-when-why",
			"idempotency-key",
			"db:runtime-no-ddl",
		},
	},
	{
		Name:     "catalog.product",
		Class:    DataPublic,
		Controls: []string{"rate-limit", "cache"},
	},
}
```

#### What happens here

The catalog encrypts nothing by itself. It forces conversation before code: a refund is not “just another POST,” but `DataPayment` with audit. In code review you ask: does the refund handler actually have all listed controls? If `authz:finance.refund` is missing, the PR does not pass—not because “security says no,” but because the asset requires it.

### Example 2 — fail closed middleware and context principal

```go
package httpapi

import (
	"context"
	"net/http"
)

type ctxKey int

const principalKey ctxKey = 1

type Principal struct {
	UserID string
	Roles  map[string]struct{}
}

func (p Principal) Can(action string) bool {
	if p.Roles == nil {
		return false
	}
	_, ok := p.Roles[action]
	return ok
}

func WithPrincipal(ctx context.Context, p Principal) context.Context {
	return context.WithValue(ctx, principalKey, p)
}

func PrincipalFrom(ctx context.Context) (Principal, bool) {
	p, ok := ctx.Value(principalKey).(Principal)
	return p, ok
}

func RequireCan(action string, next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		p, ok := PrincipalFrom(r.Context())
		if !ok {
			http.Error(w, "unauthorized", http.StatusUnauthorized)
			return
		}
		if !p.Can(action) {
			http.Error(w, "forbidden", http.StatusForbidden)
			return
		}
		next.ServeHTTP(w, r)
	})
}
```

#### What happens here

`Can` on zero value / empty `Roles` returns `false` — deny by default. `RequireCan` does not “guess” role from header here; it assumes earlier authn middleware already set a trusted `Principal` after session check. Confidentiality and integrity of admin actions do not depend on hoping “the frontend will not show the button.”

### Example 3 — least privilege DB DSN from environment

```go
package dbboot

import (
	"context"
	"database/sql"
	"fmt"
	"os"
	"time"
)

func OpenRuntime(ctx context.Context) (*sql.DB, error) {
	dsn := os.Getenv("APP_DATABASE_URL")
	if dsn == "" {
		return nil, fmt.Errorf("APP_DATABASE_URL missing")
	}
	db, err := sql.Open("pgx", dsn)
	if err != nil {
		return nil, err
	}
	db.SetMaxOpenConns(10)
	db.SetConnMaxLifetime(time.Hour)

	pingCtx, cancel := context.WithTimeout(ctx, 3*time.Second)
	defer cancel()
	if err := db.PingContext(pingCtx); err != nil {
		_ = db.Close()
		return nil, fmt.Errorf("ping: %w", err)
	}
	return db, nil
}
```

#### What happens here

Runtime does not know the migration account. If `APP_DATABASE_URL` is missing, the process does not start (fail closed on config) instead of silently running without DB. Ping with timeout protects availability from infinite wait at boot. Secret is not in source—that is confidentiality at delivery process level.

### Example 4 — trace: refund with audit

```go
func (h *Handler) Refund(w http.ResponseWriter, r *http.Request) {
	ctx := r.Context()
	p, ok := PrincipalFrom(ctx)
	if !ok || !p.Can("finance.refund") {
		http.Error(w, "forbidden", http.StatusForbidden)
		return
	}
	orderID := r.PathValue("id")
	if orderID == "" || len(orderID) > 64 {
		http.Error(w, "bad request", http.StatusBadRequest)
		return
	}

	idem := r.Header.Get("Idempotency-Key")
	if idem == "" || len(idem) > 128 {
		http.Error(w, "bad request", http.StatusBadRequest)
		return
	}

	err := h.orders.Refund(ctx, orderID, p.UserID, idem)
	if err != nil {
		h.log.Error("refund failed", "err", err, "order", orderID, "actor", p.UserID)
		http.Error(w, "request failed", http.StatusInternalServerError)
		return
	}
	h.audit.Record(ctx, "order.refund", p.UserID, orderID)
	w.WriteHeader(http.StatusNoContent)
}
```

#### What happens here

Control trace: authz → length validation → idempotency → domain → log internally / generic response → audit. Availability is not sacrificed needlessly: bad request gets 400 quickly. Error confidentiality: client does not see SQL or stack. Business flow integrity: refund is not possible without role and without audit on the success path.

### Example 5 — predict timeout as availability control

```go
srv := &http.Server{
	Addr:              ":8080",
	Handler:           mux,
	ReadHeaderTimeout: 5 * time.Second,
	ReadTimeout:       15 * time.Second,
	WriteTimeout:      30 * time.Second,
	IdleTimeout:       60 * time.Second,
}
```

#### What happens here

Without `ReadHeaderTimeout`, slow header sending keeps the connection open and consumes resources—hit on availability. Timeouts are defensive defaults (see also 10.11). They do not “attack” the client; they limit how long one untrusted peer holds goroutine and memory.

## Decision analysis

| Decision | Why |
|--------|-------|
| CIA as shared language | product and eng talk about the same goal, not “security vibe” |
| Threat model before feature | cheaper than later authz and DB rights refactor |
| Fail closed on sensitive | reduces blast radius in unknown state |
| Asset catalog | prevents forgotten endpoints and “temporary” admin routes |
| Least privilege everywhere | one token leak ≠ root on whole system |
| Deny by default in `Can` | zero value must not mean admin |
| Generic error to client | integrity/confidentiality of operational details |

## Trade-offs

- **More layers** increase operational complexity (certs, secrets, ACL, audit pipeline).
- **Strict fail closed** can reduce availability during auth dependency outage—needs explicit policy (e.g. read-only degrade for some routes, never for refund).
- **Threat model** takes time; for a 200-line service a short checklist is enough, not twenty pages.
- **Asset catalog** goes stale if not updated with PR—better thin and alive than perfect and dead.
- **Least privilege DB** requires migration account separate from runtime—a bit more CI/CD ceremony.

## Common mistakes

1. Mixing authentication (“who you are”) and authorization (“may you do this action”).
2. Believing “internal network” is enough control without authz in code.
3. One DB account with broad rights for all services and migrations.
4. Deferring threat model “until production.”
5. Generic security middleware that does not check a concrete action.
6. Logging secrets and PII “for debug.”
7. Fail open on auth error so users “do not notice outage.”
8. Zero value principal treated as privileged.
9. Returning `err.Error()` in HTTP body.
10. Checklist without mapping to asset (control exists, but not where it matters).

## Idiomatic Go

- Keep security decisions **explicit** (`if !authorized { return ... }`), not magic in a framework.
- Pass `context.Context` with principal; avoid global session maps without lifecycle control.
- Small packages with clear boundaries (`authn`, `authz`, `audit`) instead of monolithic `security` that knows everything.
- Start-time checks (`LoadConfig`, `PingContext`) are idiomatic—fail fast at boot.
- Prefer standard library and explicit types; zero value should be safe (deny, empty, closed).
- Test deny paths like allow: `httptest` with request without role expects 401/403.

## Practical scenario

A team builds a Go API for orders. They have TLS at the edge and a login form, but the refund endpoint only checks that a session cookie exists. Threat model on a whiteboard reveals: asset is money (`DataPayment`); trust boundary is public HTTP; control must be role `finance.refund`, audit who approved, idempotency key, and DB account without DDL.

After the change, the handler uses `RequireCan("finance.refund")`, logs internal failure with request ID, and the client sees a generic message. Runtime DSN comes from env with an account that may only `UPDATE` order status. Leaking an ordinary user session token no longer includes refund in blast radius—money confidentiality and ledger integrity are separate from “someone is logged in.”

Availability stays conscious: if auth store does not respond, refund is 503/401 per policy (fail closed), while `GET /healthz` and public catalog can still run. The team documents that assumption in an ADR.

### Answers

1. Confidentiality — only authorized see (TLS, authz, secrets outside code). Integrity — not changed without authorization (placeholders, AEAD, template escape). Availability — service usable (timeouts, rate limit, degrade policy).
2. Least privilege does not prevent leak by itself; it narrows what a stolen token may do → smaller impact.
3. Place where trust changes: e.g. public HTTP entry; boundary to Postgres.
4. Fail closed rejects when you do not know check outcome—protects data; during long auth outage users cannot do sensitive actions (availability).
5. Assumption: “network blocks port.” Control: `if !p.Can(...)`.
6. Goal is risk and control map for defense; offensive steps do not help the reader design a secure system and violate course security frame.
7. Deny by default: zero value without roles must not open privileged action.
8. Reviewer compares handler to required controls for that data class instead of guessing.
