# 04.03 go:embed and embed.FS — embedding resources in the binary

> **Go Path - Zero to Gopher** / **02 Intermediate → Managing Go Projects** / Lesson 04.03

## Lesson goals

- Use the **`//go:embed`** directive for individual files and for glob patterns.
- Understand all three receiving forms: **`string`**, **`[]byte`**, and **`embed.FS`**.
- Embed HTML templates (`template.ParseFS`), SQL migrations, and static files for `http.FS`.
- Know exactly where the boundaries are: no `.` or `..` in the pattern, no empty directory, the `all:` prefix, files outside the module.
- Recognize when a resource does **not** go into an embed (secrets, user uploads, content that changes without a rebuild).
- Judge the effect on binary size and decide when embed is the right tool, and when it is not.

## Prerequisite

- Lessons 04.01–04.02 (workspace and package organization).
- Basic familiarity with `html/template` is useful; it is covered in more detail in 05.04.
- Familiarity with the `io/fs` interface is a plus, but it is not required — we explain what is needed.

## Problem this lesson solves

A deploy forgets the `templates/` folder. Migrations are missing next to the binary. A Docker image expects files beside `WORKDIR`, and in production they simply are not there because someone copied only the binary. Each of these incidents has the same cause: at runtime the application reads from disk resources it should have carried with itself. The official term for the solution is **embedding** (resources are written into the binary during compilation, instead of being read from disk at runtime). Further in the lesson we use the term embedding and the directive `//go:embed`. The compiler writes the bytes of the files directly into the package, so one binary carries both the code and the resources. There is no longer a question of "did the `templates/` folder arrive on the server" — it is *inside* the server.

## Mental model

1. The `//go:embed` directive is an instruction to the compiler: **put these bytes into the package**, not a runtime call.
2. The variable immediately below the directive — of type `string`, `[]byte`, or `embed.FS` — carries that content.
3. `embed.FS` is a **read-only** virtual file system that implements `io/fs.FS`. There is no `Write`, no `Remove`, no change of contents at runtime.
4. Paths in the pattern are relative to the **directory of the Go file that contains the directive** — not relative to the module, not relative to the package that imported the variable, not relative to the process's current working directory.
5. The pattern cannot contain `.` or `..` as a path segment, it cannot start or end with a slash, and it must match at least one file or a non-empty directory. Otherwise compilation fails.
6. Ideal for static assets, templates, migrations, and seed JSON — never for secrets or content that must change without a rebuild.

## Mechanism

This is the longest part of the lesson because most embed incidents in practice are not "I do not know the syntax" but "I thought the path worked this way, and it works that way". Below is the reference folder structure we use for every path trace that follows:

```text
myapp/
├── go.mod                     (module myapp)
├── cmd/
│   └── server/
│       └── main.go
└── web/
    ├── render.go               <-- directives live here
    ├── version.txt
    ├── templates/
    │   ├── index.html
    │   ├── about.html
    │   └── partials/
    │       └── footer.html
    ├── static/
    │   ├── css/app.css
    │   └── js/app.js
    ├── .well-known/
    │   └── acme-challenge.txt
    └── empty-dir/              (the folder exists, but it is empty)
```

Every trace below assumes the directive is in `web/render.go`, except where noted otherwise.

### Three receiving forms

```go
package web

import "embed"

//go:embed version.txt
var Version string

//go:embed version.txt
var VersionBytes []byte

//go:embed templates
var TemplateFS embed.FS
```

The same file (`version.txt`) can be received at the same time as a `string` and as a `[]byte`. The compiler does not care how many times the same pattern appears in the package. It only has to type the destination variable correctly. `embed.FS` is the only form that carries *more than one* file and a directory structure. `string`/`[]byte` receive the contents of exactly one file (if a pattern matches more than one file for a string/[]byte target, that is a compilation error).

### Path trace 1 — one file into a string

Pattern: `version.txt`. File on disk: `web/version.txt`. The directive is in `web/render.go`, so the root directory of the pattern is `web/`. Result: `Version` contains the exact text from `web/version.txt`, with no transformation (no trim of the newline, no change of encoding).

> **Predict:** If `version.txt` contains `v1.4.2\n` (with a newline at the end), what will `len(Version)` return — the length with that `\n`, or without it?
>
> **Answer:** With `\n`. Embed does not modify the file contents. `Version` is an exact copy of the bytes, including the trailing newline. If you need a trim, you do `strings.TrimSpace(Version)` yourself.

### Path trace 2 — a glob that does not go deep

Pattern: `templates/*.html`. This is a **glob**, not a directory name. The `*` character in Go patterns (the same rule as `path.Match`/`filepath.Match`) **does not cross `/`**. So `*` covers only the direct files in `templates/`, not those in `templates/partials/`.

```text
templates/index.html            ✓ matched
templates/about.html            ✓ matched
templates/partials/footer.html  ✗ NOT matched
```

> **Predict:** The code calls `t.ExecuteTemplate(w, "footer.html", nil)` on a template parsed from `templates/*.html`. What happens?
>
> **Answer:** A runtime error: `template: no template "footer.html" associated with template ...`. The build succeeded (the pattern matched at least one file, `index.html` and `about.html`), but `footer.html` simply is not in the FS that `ParseFS` received. This is one of the most common mistakes in practice — covered further as a separate item.

### Path trace 3 — a pattern with no glob means "the whole directory, recursively"

When the pattern names a **directory** (with no `*`), embed embeds the whole subtree, recursively, including every subfolder:

```go
//go:embed templates
var TemplateFS embed.FS
```

```text
templates/index.html            ✓
templates/about.html            ✓
templates/partials/footer.html  ✓ (recursive!)
```

> **Predict:** Do `//go:embed templates` and `//go:embed templates/*` embed an identical set of files?
>
> **Answer:** No. `templates` (with no glob) goes recursively into `partials/`. `templates/*` is a glob that covers only the direct entries in `templates/`. It will include both files and the subfolder `partials` *as an entry*, but because `partials` is not a file but a directory, `*` still takes it into account as part of the pattern (unlike `*.html`, which filters by extension), so the contents of `partials/` **are still** embedded, because `partials` is a match that is a directory, and the rule "a directory is embedded recursively" holds whether it was matched directly or by a glob. The key difference that *actually* hurts is specifically `*.html` (a filtered glob), not a bare `*`.

### Path trace 4 — the `all:` prefix and hidden files

When a pattern names a directory (with or without a glob), files and subdirectories whose name starts with a dot (`.`) or an underscore (`_`) are **skipped by default** — even when they are inside a matched subtree. The `all:` prefix includes them.

```go
//go:embed .well-known
var WellKnown embed.FS       // EMPTY or an error — .well-known is a hidden name

//go:embed all:.well-known
var WellKnownAll embed.FS    // contains acme-challenge.txt
```

> **Predict:** A team placed an ACME HTTP-01 challenge file in `web/.well-known/acme-challenge.txt` and wrote `//go:embed .well-known`. What happens in production?
>
> **Answer:** The build most likely fails with "no matching files found" (a folder whose *contents* are hidden behaves as if it were empty for the purposes of the embed rules), or if the pattern happens to match something else, the ACME file is certainly missing. TLS certificate issuance fails because the verification file returns 404. The fix is `all:.well-known`.

### Path trace 5 — an empty directory

The directory `empty-dir/` exists on disk but has no file inside it (git does not even see it, because git does not track empty folders).

```go
//go:embed empty-dir
var EmptyFS embed.FS
```

> **Predict:** Does this code compile at all?
>
> **Answer:** No. The rule is explicit: "matches for empty directories are ignored". Emptiness is ignored as a match, which means the pattern effectively matches nothing, and every pattern must match at least one file or a non-empty directory. The compilation error is along the lines of `pattern empty-dir: no matching files found`. If the folder needs to exist for the structure of the repository, put a real file in it (for example, rename the contents of a `.gitkeep` into something meaningful, or a `README.md`). But be careful: `.gitkeep` starts with a dot, so it needs the `all:` prefix for *it itself* to pass as a match.

### Path trace 6 — the directive must sit next to the resources, not next to the importer

This is a gotcha that confuses people who come from languages where paths are relative to the current working directory or to the project "root". In Go, the pattern is relative **exclusively** to the directory of the file that contains the `//go:embed` comment — not to the package that imports that variable, not to `go.mod`, not to the binary that is executing.

```text
cmd/server/main.go     -- HERE there is no templates/ directly beside it
web/render.go          -- HERE web/templates/ exists
web/templates/index.html
```

If someone by mistake put `//go:embed templates` in `cmd/server/main.go`, the compiler looks for `cmd/server/templates`, which does not exist.

> **Predict:** What is the exact error message when the directive looks for a directory that does not exist beside the file that contains the directive?
>
> **Answer:** Something along the lines of `pattern templates: no matching files found`. Go does not say "there is no directory beside this file". It treats non-existence the same as "the pattern matched nothing". The fix: the directive must be in `web/render.go` (beside `templates/`), and `main.go` receives an already filled `embed.FS` as a parameter or through a public variable from the `web` package.

### Path trace 7 — an attempt at `..`

```go
//go:embed ../shared/logo.png
var Logo []byte
```

> **Predict:** Does this ever work, even when `shared/` is part of the same module and logically "nearby"?
>
> **Answer:** Never. The compiler's actual message is of the form `pattern ../shared/logo.png: invalid pattern syntax`. The reason is not arbitrary: `embed.FS` implements `io/fs.FS`, whose contract (`fs.ValidPath`) requires that no path in the file system contain a `..` segment. Allowing `..` in the pattern would mean building an FS that violates its own `interface` contract. The fix: either move `shared/logo.png` so that it is under the same directory as the file with the directive, or under a deeper one, or make a separate package in `shared/` that itself embeds `logo.png` and exports it as `[]byte`, and then other packages import it.

### Path trace 8 — vendor, .git, and symbolic links

A pattern cannot match files outside the module or files that the Go tool does not know how to "pack". Concretely that means `.git/*`, `vendor/*`, and symbolic links, as well as subdirectories that themselves contain their own `go.mod` (a separate module, even if it physically lives inside the tree of the current module).

```go
//go:embed vendor
var VendoredDeps embed.FS
```

> **Predict:** Does the code above have any chance of compiling if `vendor/` exists (for example, the project uses `go mod vendor`)?
>
> **Answer:** No. `vendor/` is explicitly on the exception list regardless of whether it matches real files on disk. The same holds for `.git/*`. The intent of the rule is that embed does not become a way to "pick up" what the tool otherwise treats specially (dependencies, version-control metadata).

### Several lines of the same directive

When the list of patterns is long, the directive can be repeated on several lines above the same variable — semantically identical to one line with spaces:

```go
//go:embed templates/*.html
//go:embed templates/partials/*.html
//go:embed templates/partials/admin/*.html
var TemplateFS embed.FS
```

is equivalent to:

```go
//go:embed templates/*.html templates/partials/*.html templates/partials/admin/*.html
var TemplateFS embed.FS
```

Between the `//go:embed` lines and the `var` declaration, only blank lines and other `//` comments are allowed — no code, no other directive.

### How `ParseFS` reads keys inside `embed.FS`

When `embed.FS` contains files, their "keys" (the paths by which you look them up through `Open`/`ReadFile`/`ParseFS`) are the **same path form** as in the pattern — not an absolute path from disk, and not shortened to only the file name.

```go
//go:embed templates
var TemplateFS embed.FS

// The key is "templates/index.html", NOT "index.html", NOT "web/templates/index.html"
data, err := TemplateFS.ReadFile("templates/index.html")
```

> **Predict:** `template.ParseFS(TemplateFS, "templates/*.html")` — what name does the template `index.html` get inside the `template.Template` tree (the name by which you call it in `ExecuteTemplate`)?
>
> **Answer:** `index.html` — the base name of the file, with no path prefix. `ParseFS` internally uses `path.Base` to derive the template name, even though the *path for finding the file* in the FS is the full one (`templates/index.html`). These are two different namespaces and they are easy to mix up: the path in the FS versus the template name for `ExecuteTemplate`.

### `embed.FS` is read-only

`embed.FS` implements `fs.FS`, `fs.ReadDirFS`, `fs.ReadFileFS`, and `fs.GlobFS`. There is no `fs.StatFS` promise of a real `ModTime()`. Every embedded file gets a `ModTime` equal to zero (`time.Time{}`), because the contents are written into the binary at compilation time and "modification time" loses its meaning. If logic depends on `ModTime` (for example, ETag caching by modification time), an embed FS is the wrong source for that. Use a hash of the contents instead.

## Rules and syntax

- The directive must be **immediately** above the variable declaration (only blank lines and other `//` comments are allowed in between).
- The pattern must not contain `.` or `..` as a segment, and it must not start or end with `/`. For "everything in the current directory" use `*`, not `.`.
- A directory name (with no glob) is embedded recursively. Files and subdirectories that start with `.` or `_` are skipped unless the `all:` prefix is used.
- Empty directories do not count as a match. Every pattern must match at least one file or a non-empty directory, otherwise the build fails.
- Paths in the pattern always use `/`, including on Windows.
- A pattern cannot match files outside the module (`.git/*`, symbolic links, `vendor/`, subdirectories with their own `go.mod`).
- A `*_test.go` file can have its own `//go:embed` directive. That content is not embedded in the production binary, only in the test binary.
- Secrets (API keys, private keys, `.env`) do not go into an embed. Use a secret manager or environment variables at runtime.
- Large video/audio assets: before you embed them, measure the consequence for binary size.

## Examples

### Example 1 — string and []byte from the same file

```go
package main

import (
	_ "embed"
	"fmt"
)

//go:embed hello.txt
var hello string

//go:embed hello.txt
var helloBytes []byte

func main() {
	fmt.Print(hello)
	fmt.Println(len(helloBytes))
}
```

`hello.txt`:

```text
Hello from the embed
```

#### What happens here

The same file goes into a `string` and into a `[]byte`. The compiler does not make a distinction. It only has to know the type of the target. For `string`/`[]byte` a blank import `_ "embed"` is enough, because the type `embed.FS` is not referenced directly. As soon as you need an `embed.FS` variable, the import must be the full `"embed"` (with no underscore), otherwise the build fails with `undefined: embed.FS`.

### Example 2 — embed.FS for HTML templates

```go
package web

import (
	"embed"
	"html/template"
	"io"
)

//go:embed templates
var templateFS embed.FS

func Page(w io.Writer, name string, data any) error {
	t, err := template.ParseFS(templateFS, "templates/*.html", "templates/partials/*.html")
	if err != nil {
		return err
	}
	return t.ExecuteTemplate(w, name, data)
}
```

#### What happens here

The `templateFS` embed directive has no glob (`templates`), so it goes recursively and covers `partials/footer.html` as well. `ParseFS` still asks for explicit patterns (two of them, separated by a comma) in order to parse both the top-level templates and the partials. Directory recursion in `//go:embed` does not mean that `ParseFS` automatically "sees" everything. It still needs a pattern that matches the files you want to parse. The binary carries the templates. There is no dependency on the working directory when the process starts.

### Example 3 — SQL migrations embedded in the binary

```go
package migrate

import (
	"database/sql"
	"embed"
	"fmt"
	"sort"
	"strings"
)

//go:embed migrations/*.sql
var migrationsFS embed.FS

func Up(db *sql.DB) error {
	entries, err := migrationsFS.ReadDir("migrations")
	if err != nil {
		return err
	}
	var names []string
	for _, e := range entries {
		if !e.IsDir() && strings.HasSuffix(e.Name(), ".up.sql") {
			names = append(names, e.Name())
		}
	}
	sort.Strings(names)
	for _, name := range names {
		body, err := migrationsFS.ReadFile("migrations/" + name)
		if err != nil {
			return err
		}
		if _, err := db.Exec(string(body)); err != nil {
			return fmt.Errorf("migrate %s: %w", name, err)
		}
	}
	return nil
}
```

Example `migrations/001_init.up.sql`:

```sql
CREATE TABLE IF NOT EXISTS products (
	id TEXT PRIMARY KEY,
	name TEXT NOT NULL,
	price_minor BIGINT NOT NULL
);
```

The matching `migrations/001_init.down.sql` (rollback), for symmetry with `up`:

```sql
DROP TABLE IF EXISTS products;
```

The `Down` function is the mirror image of `Up`, except that it filters by the `.down.sql` suffix and goes in reverse (descending) name order:

```go
func Down(db *sql.DB) error {
	entries, err := migrationsFS.ReadDir("migrations")
	if err != nil {
		return err
	}
	var names []string
	for _, e := range entries {
		if !e.IsDir() && strings.HasSuffix(e.Name(), ".down.sql") {
			names = append(names, e.Name())
		}
	}
	sort.Sort(sort.Reverse(sort.StringSlice(names)))
	for _, name := range names {
		body, err := migrationsFS.ReadFile("migrations/" + name)
		if err != nil {
			return err
		}
		if _, err := db.Exec(string(body)); err != nil {
			return fmt.Errorf("rollback %s: %w", name, err)
		}
	}
	return nil
}
```

#### What happens here

Migrations become part of the release artifact. No deploy step can "forget" to copy them, because they are inside the binary. Sorting by name gives a deterministic order of application (hence the convention of `001_`, `002_` prefixes). Production tools such as `golang-migrate` and `goose` internally use the same embed principle. This example is a simplified version of that pattern, useful when you do not need the whole tool.

### Example 4 — static files through http.FS

```go
package main

import (
	"embed"
	"io/fs"
	"log"
	"net/http"
)

//go:embed static
var staticRoot embed.FS

func main() {
	sub, err := fs.Sub(staticRoot, "static")
	if err != nil {
		log.Fatal(err)
	}
	http.Handle("GET /static/", http.StripPrefix("/static/", http.FileServer(http.FS(sub))))
	log.Fatal(http.ListenAndServe(":8080", nil))
}
```

#### What happens here

`fs.Sub` strips the `static/` prefix so that the URL `/static/css/app.css` maps to the key `css/app.css` inside the sub-FS, instead of to `static/css/app.css`. `http.FS` adapts any `fs.FS` (including `embed.FS` or its `fs.Sub` result) to the `http.FileSystem` interface that `http.FileServer` understands. Without `fs.Sub`, the URL would have to carry `/static/static/css/app.css`, which nobody wants.

### Example 5 — several patterns in one directive

```go
package assets

import "embed"

//go:embed config/defaults.json migrations/*.sql templates
var All embed.FS
```

#### What happens here

One `embed.FS` variable can cover several patterns separated by a space in the same directive, or — for longer lists — the directive can be repeated several times above the same variable for readability. All matches are joined into the same virtual file system. Repeating the same pattern, or overlap between patterns, is not an error (a file is embedded only once).

### Example 6 — when NOT to embed

```text
- user uploads (they change after deploy, by definition)
- .env / API keys / private keys / TLS certificates with a private key
- feature-flag configuration that must change without a rebuild
- large video/audio assets that would drastically inflate the binary
```

For all of this: object storage, a secret manager, a configuration service, or a CDN — not `go:embed`.

#### What happens here

`go:embed` is for resources that are known at **build time** and unchanging, which you want to carry with the binary. As soon as the contents must change without a new build, or as soon as the contents are sensitive, embed stops being a good tool. The next two sections explain why in more detail.

### Example 7 — an fs.FS abstraction for a dev/prod switch

In development it is convenient to change a template and see the result immediately, with no rebuild. In production it is desirable for the template to travel inside the binary. The solution is for the code to depend on the `fs.FS` interface, not on the concrete `embed.FS`, and for the concrete implementation to be chosen through a build tag:

```go
// assets_prod.go
//go:build !devassets

package web

import "embed"

//go:embed templates
var TemplateFS embed.FS
```

```go
// assets_dev.go
//go:build devassets

package web

import "os"

// os.DirFS reads directly from disk on every call — convenient for development,
// because a change to a file on disk immediately affects the next render, with no rebuild.
var TemplateFS = os.DirFS(".")
```

```go
// render.go — it does not know and does not care which implementation is active
package web

import (
	"html/template"
	"io"
	"io/fs"
)

func Page(fsys fs.FS, w io.Writer, name string, data any) error {
	t, err := template.ParseFS(fsys, "templates/*.html")
	if err != nil {
		return err
	}
	return t.ExecuteTemplate(w, name, data)
}
```

Running in development mode: `go run -tags devassets .`. Running or building for production: an ordinary `go build .` (with no tag), which uses `assets_prod.go` with the embed.

#### What happens here

`fs.FS` is the shared interface implemented by both `embed.FS` and `os.DirFS(...)` (and by `fstest.MapFS` in tests). Code that works with templates does not need to know which implementation stands behind it. It only receives an `fs.FS` as a parameter or a field. The build tag `devassets` chooses the concrete implementation at the file level, with no `if` branching at runtime and with no risk that a developer "live reload" path accidentally stays active in the production binary (because `assets_dev.go` is **not compiled** when the `devassets` tag is not present).

## Security: why secrets do not go into an embed

`go:embed` writes bytes **into the binary**, not into a separately encrypted section. Anything embedded is available to anyone who has the binary, using tools that do not even understand Go:

```powershell
strings.exe .\app.exe | Select-String "API_KEY"
```

If a `.env` or a private key were embedded, that command would simply print it. This is not a theoretical risk. Docker image layers, artifact repositories, and the CI cache store the binary directly, often for longer and with wider access than the team thinks. Concrete consequences:

- Rotating a key requires a **new build and a redeploy everywhere the old binary existed**, not only a change of a value in configuration.
- A binary in a private Docker registry is still readable by anyone who has pull access to that registry. Embed adds no encryption.
- An open-source project that by mistake embeds a test API key in sample code **publishes** that key together with the binary on GitHub Releases.

The fix is always runtime loading: environment variables, `os.ReadFile` from the path of a mounted secret volume (a Kubernetes Secret, a Vault agent), or a call to a secret-manager API when the process starts. If you need a *default, non-critical* value (for example, `defaults.json` with public feature lists), that may freely go into an embed. The difference is whether revealing the contents has a security consequence.

## Binary size

Every embedded byte becomes part of the binary. There is no compression by default, and no deduplication across package boundaries in different binaries. Before you embed something large, measure:

```powershell
go build -o app.exe .
Get-Item .\app.exe | Select-Object Name, Length
```

Compare the size before and after adding the embed directive. A few landmarks from practice:

| Contents | Typical effect |
|---|---|
| HTML templates (tens of KB) | Negligible |
| SQL migrations (KB to low MB) | Acceptable, a common case |
| A CSS/JS bundle (hundreds of KB) | Acceptable, but consider a CDN for cache |
| Images/icons (tens to hundreds of KB) | Mostly OK if there are few of them |
| Video, audio, large datasets (tens to hundreds of MB) | Almost never — use object storage |

Additional levers for a smaller binary (independent of the embed decision, but relevant when you measure the effect):

```powershell
go build -ldflags="-s -w" -o app.exe .
```

`-s` removes the symbol table, `-w` removes DWARF debug information. It shrinks the binary, but it makes later debugging harder (for example, `dlv` loses some capabilities). This is a decision separate from embed, but they are usually mentioned together when a team first notices that the binary is "too big".

> **Predict:** If `cmd/api` and `cmd/worker` both embed the same migrations and both are compiled into separate binaries, are the migration bytes "deduplicated" on disk?
>
> **Answer:** No. Each binary is a self-contained executable. Each copy carries its own copy of the embedded bytes. If both binaries live on the same server, that is duplicated space on disk (mostly acceptable for a size on the order of KB–MB), but if both embed from the same `internal/migrate` package, the code stays DRY even though the bytes are not shared on disk.

## The `all:` prefix and empty directories — practical consequences

These two rules (already shown through Path traces 4 and 5 in Mechanism) most often surprise in production because they manifest **differently**:

- An **empty directory** fails the build, immediately, loudly, on CI. It is easy to discover.
- A **missing `all:` prefix** does not fail the build (if the pattern otherwise matches at least one "visible" file). It only silently omits files that start with `.` or `_`. This is discovered only when someone notices that something is missing at runtime, often in production.

Practical recommendation: when a directory contains both "visible" and "hidden" files, and **all** of them are intentionally needed, always use the `all:` prefix explicitly. Do not assume that the default behavior will cover everything `ls -la` shows.

```go
//go:embed all:static
var StaticAll embed.FS
```

For empty directories that you want to exist in the repository for structure (for example, `migrations/` before the first migration is written), the embed directive simply should not exist until the directory gets at least one file — or put a placeholder file (a `.gitkeep` renamed into a `README.md` with one sentence) and use `all:` if the placeholder starts with a dot.

## Decision analysis

| Decision | Reason |
|---|---|
| Embed templates and migrations | One deploy artifact, no "the folder is missing" incidents |
| `fs.Sub` for HTTP serving | A clean URL space, the prefix does not leak into file paths |
| Never embed secrets | The binary is readable with the `strings` tool; rotation requires a redeploy |
| Disk / object storage for dynamic content | A change with no rebuild and no redeploy |
| `all:` explicitly when there are hidden files | A silent error is worse than a loud error |
| Measuring binary size before embedding larger assets | Prevents "the binary grew 40MB, nobody knows why" |
| An `fs.FS` parameter instead of a concrete `embed.FS` in functions | Testability (`fstest.MapFS`) and a dev/prod switch with no duplicated code |
| Embed in `internal/migrate`, not in each `cmd/` separately | One source of truth for the patterns, even when the binaries stay separate |

## Trade-offs

- A larger binary — every embedded byte stays in every binary that contains it.
- Every change of CSS or of a template requires a new build. There is no "hot reload" of static content without a rebuild (unless a CDN sits in front and the cache expires on its own).
- An embed in a library that other packages import pulls those assets to every consumer of the library. Sometimes it is better to put the embed in the `cmd/` binary, not in a shared library, to avoid imposing the size on everyone.
- Tests can have their own `//go:embed` fixtures that are not shipped to production, but they still consume CI time and disk during the test build.
- Migration tools (golang-migrate, goose) add a layer of abstraction above the manual embed approach. They are worth using as soon as the number of migrations exceeds "I can sort that by name by hand".

## Common mistakes

### 1. `..` in a `//go:embed` pattern

- **Wrong:**

```go
//go:embed ../shared/logo.png
var Logo []byte
```

- **Effect:** A compilation error, along the lines of `pattern ../shared/logo.png: invalid pattern syntax`. This is an absolute rule. There is no legal path with `..` in a `//go:embed` pattern, regardless of where `shared/` is.
- **Fix:** Move the resource so that it is under the same directory as the file with the directive, or under a deeper one, or make a separate package in `shared/` that itself embeds `logo.png` and exports it (`var Logo []byte` declared there), and then the package that needs it imports it.

### 2. A `*.html` glob that does not cover subfolders

- **Wrong:**

```go
//go:embed templates/*.html
var TemplateFS embed.FS
```

when `templates/` also contains `templates/partials/footer.html`.

- **Effect:** The build succeeds (the pattern matches `index.html`, `about.html`), but `footer.html` never enters the FS. The runtime error appears only when the code tries `ExecuteTemplate(w, "footer.html", ...)`: `template: no template "footer.html" associated with template ...`. This error passes through code review unnoticed because the code itself looks correct.
- **Fix:** Use the directory name with no glob (`//go:embed templates`) for recursive coverage, or explicitly list additional patterns: `//go:embed templates/*.html templates/partials/*.html`.

### 3. Embedding an empty directory

- **Wrong:**

```go
//go:embed empty-dir
var EmptyFS embed.FS
```

when `empty-dir/` exists on disk, but has no file.

- **Effect:** A compilation error along the lines of `pattern empty-dir: no matching files found`. Empty directories do not count as a match.
- **Fix:** Add at least one file to the directory (for example, a `README.md` explaining what goes there), or remove the directive until the directory actually gets contents.

### 4. Hidden names without the `all:` prefix

- **Wrong:**

```go
//go:embed .well-known
var WellKnown embed.FS
```

when the goal is for `acme-challenge.txt` inside `.well-known/` to be available.

- **Effect:** The file is silently omitted. The build might not even fail (depending on the rest of the folder's contents), but `.well-known/acme-challenge.txt` is not in the FS. ACME HTTP-01 verification returns 404, TLS certificate issuance fails, and the error is not visible in the code at first glance.
- **Fix:** `//go:embed all:.well-known`. The `all:` prefix includes files and directories whose name starts with a dot or an underscore.

### 5. Embedding secrets (`.env`)

- **Wrong:**

```go
package secrets

import "embed"

//go:embed .env
var EnvFile embed.FS
```

- **Effect:** Even if it compiled (and a `.env` without the `all:` prefix is skipped anyway), the intention is wrong: the secret would end up in the binary, readable with the `strings` tool by anyone who has access to the binary or to a Docker image layer. Rotating the key would require a redeploy everywhere.
- **Fix:** Never embed a `.env` or similar secrets. Load them at runtime from environment variables or a secret manager.

### 6. A missing `import "embed"` for `embed.FS`

- **Wrong:**

```go
package web

//go:embed templates
var TemplateFS embed.FS
```

(with no `import "embed"`, only with `_ "embed"` somewhere else in the package, or with no import at all)

- **Effect:** A compilation error `undefined: embed.FS`, or if the import is omitted entirely, `undefined: embed` together with a note that the import is missing.
- **Fix:** `import "embed"` (with no underscore) when the type `embed.FS` is used directly. The blank import `_ "embed"` works only when the destination type is `string` or `[]byte` and the package otherwise does not reference the `embed` identifier.

### 7. A backslash in the pattern on Windows

- **Wrong:**

```go
//go:embed templates\index.html
var Index string
```

- **Effect:** A compilation error. The pattern uses `\` as a separator, and Go patterns accept only `/`, even when the build runs on Windows. `\` in a pattern is interpreted as an escape character in some contexts, or it simply does not match the file.
- **Fix:** Always `/` in `//go:embed` patterns, regardless of the OS: `//go:embed templates/index.html`.

## A short history: before go:embed

`//go:embed` arrived in Go 1.16 (February 2021). Before that, a team that wanted static resources inside the binary had to reach for third-party tools that generated `.go` files with assets serialized as Go source code (most often as a `[]byte` literal or a `map[string]string`):

| Tool | Approach |
|---|---|
| `go-bindata` | Generates a `.go` file with base64/gzip-encoded contents, plus an API for access |
| `packr` (gobuffalo) | Similar, with a fallback to disk in development mode |
| `statik` | Packs a directory into one `.go` file as a virtual FS |

All of them solved the same problem — "the binary should carry the resources" — but through a `go generate` step that had to be run **before** `go build`, and whose output (the generated `.go` file) had to be kept in the repository or regenerated in CI before every build. `//go:embed` removes that whole step: no generator, no generated file for review. The directive is part of the standard library and part of the `go build` flow. Projects that migrated from `go-bindata`/`packr`/`statik` to `go:embed` usually deleted the entire `go generate` pipeline and tens (or hundreds) of lines of generated code.

## Idiomatic Go

- The documentation of the `embed` package in the standard library is itself an exemplary reference. It is worth reading directly when a doubt appears.
- `template.ParseFS`, `http.FS`, and `fs.Sub` are a common trio in web services. Learn them together.
- Migration tools (golang-migrate, goose) officially support an embed FS as a source of migrations. Do not invent your own loader if the tool already exists in the project.
- When a library exports an `embed.FS`, export it as a `var` with a clear name (`TemplateFS`, not `FS` or `Data`) so consumers know what they are getting without reading the source code.

## Practical scenario

A Kubernetes deploy mounts only the binary (a multi-stage Docker build, the final image is `scratch` or `distroless`). The templates are missing → every HTTP request for an HTML page returns 500 with `open templates/index.html: no such file or directory`. The team moves `//go:embed templates` and `//go:embed migrations/*.sql` into the appropriate packages. The Docker image shrinks to one layer with the binary alone. There is no longer a `COPY templates/ /app/templates/` step that is occasionally forgotten in a new Dockerfile. CSS still goes to a CDN because of the cache strategy (an embed would mean a redeploy for every tiny CSS change). The HTML layout stays embedded because it changes side by side with the code that renders it.

## Windows paths

In `//go:embed` always use `/`, even when you develop on Windows and even when the rest of the project is written with Windows paths in other contexts (scripts, `.gitignore`, and so on). `templates\index.html` is not a valid pattern for the directive. The tool parses the pattern as a URL-like path, not as an OS path, so a backslash does not have the role it has in `cmd.exe` or PowerShell.

## Testing embedded content

A simple test that does `ReadDir` or `ReadFile` on the embed FS catches the situation where someone renames a folder, deletes a file, or changes the pattern and forgets to update the directive:

```go
package migrate

import "testing"

func TestMigrationsEmbedded(t *testing.T) {
	entries, err := migrationsFS.ReadDir("migrations")
	if err != nil {
		t.Fatalf("ReadDir: %v", err)
	}
	if len(entries) == 0 {
		t.Fatal("expected at least one migration in the embed FS")
	}
}
```

This test is a cheap guard in CI. The build would fail anyway if the pattern matched nothing, but this test also catches subtler cases — for example, that the pattern matched the *wrong* subset of files (as in the scenario with `templates/*.html` that does not go into `partials/`).

## Several packages, the same asset

If both `cmd/api` and `cmd/worker` need the same migrations, keep the embed directive in one `internal/migrate` package and export `embed.FS` from there. Do not copy `//go:embed migrations/*.sql` into both binaries. Duplicating the directive means duplicating the source of truth: if someone adds a migration and updates only one copy of the pattern (because the patterns are in two different files, even if they point at the same files on disk through different relative paths), the teams easily drift apart. The binary itself certainly carries its own copy of the bytes. That is acceptable. Duplicating the *code* is not.

## Embed and build tags

Files excluded by build tags at the level of `.go` files do not directly affect `//go:embed` patterns. The directive looks at files **on disk** at compilation time. It does not filter by the build tags of other `.go` files. Be precise with glob patterns so you do not accidentally embed a test fixture (for example, `testdata/large-sample.json`) into the production binary only because the pattern was wider than it needed to be (`*` instead of `*.html`, for example).

## Embed in tests

A `_test.go` file can have its own `//go:embed` directive for fixture data:

```go
package parser_test

import "embed"

//go:embed testdata/*.json
var fixtures embed.FS
```

That content is embedded only in the test binary that `go test` compiles temporarily. It does not enter the production binary that `go build` produces. Useful for golden-file tests that should not depend on the working directory in CI (the fixture is always available regardless of where `go test` was started from).

## Content-Type for static files

When you serve embed content through `http.FileServer`, `http.FS` determines `Content-Type` from the file extension (using the `mime` package of the standard library), not from magic bytes of the contents. If a file has an unusual or missing extension, `Content-Type` can be wrong or generic (`application/octet-stream`). Check the actual `Content-Type` header in browser DevTools after deploy, especially for `.woff2`, `.svg`, and other types that are not always registered by default on every platform.

## What to do after the first embed

Measure the binary size before and after adding the embed directive (`go build` plus a check of the file size, as in the size section). If the jump is not acceptable, move the heavier assets to a CDN or to object storage. Add a test that reads at least one embedded file so CI catches a broken pattern before it reaches production. Document in the project README exactly what is embedded and why. The next engineer who sees an inexplicably large binary should be able to find the answer quickly.

1. Embed `version.txt` as a `string` and print it on a `/version` HTTP route.
2. Make a `templates/` with two pages and one partial in a subfolder. Parse both paths through `ParseFS` and render both pages.
3. Embed SQL migrations and execute them on an in-memory SQLite database in a test.
4. Serve `static/` through `http.FileServer` + embed + `fs.Sub`. Check `Content-Type` in DevTools.
5. Deliberately try `//go:embed ../something` and record the exact compiler error message.
6. Make an empty directory, try to embed it, record the error, then add a file and run the build again.
7. Add a `.hidden` file to a directory you embed without the `all:` prefix. Check that the file is missing from the FS, then add `all:` and check that it appeared.
8. Make a `Down` migration following Example 3 and test the execution order (rollback goes in the reverse order of `Up`).
9. Write an `fs.FS` switch following Example 7 with the build tag `devassets`. Run once with the tag and once without it, and compare the behavior when you change a template on disk with no rebuild.
10. Measure the binary size before and after adding one image of several MB into the embed. Try `-ldflags="-s -w"` and compare the difference.

## Check questions

1. **What does `//go:embed` do?**
   It embeds files into the binary package at compilation time. It is a compiler directive, not a runtime call.

2. **Which types receive embed content?**
   `string`, `[]byte` (for exactly one file), and `embed.FS` (for one or more files/directories).

3. **What are paths in the pattern relative to?**
   To the directory of the Go file that contains the `//go:embed` directive — not to the module, the package that imports the variable, or the process's working directory.

4. **Why can a pattern not contain `..`?**
   `embed.FS` implements `io/fs.FS`, whose contract forbids paths with a `..` segment. Allowing `..` would mean violating that contract.

5. **What happens to files/directories whose name starts with a dot?**
   They are skipped by default when a directory is embedded. The `all:` prefix includes them.

6. **What happens when a pattern matches only an empty directory?**
   The build fails. Empty directories do not count as a match, and every pattern must match at least one file or a non-empty directory.

7. **Why `fs.Sub` together with `http.FS`?**
   So that the root of the HTTP file system is an inner folder, with no prefix in the URL paths of the served files.

8. **May embed content contain secrets?**
   No. The binary is readable with tools such as `strings`. Secrets go through a secret manager or environment variables at runtime.

9. **Does embed content affect binary size?**
   Yes, directly. Every embedded byte stays in every binary that contains it, with no compression by default.

10. **Why use `fs.FS` as a parameter type instead of a concrete `embed.FS`?**
    So the function stays independent of the concrete implementation. In a test you pass `fstest.MapFS`, in development `os.DirFS`, in production `embed.FS`, with no branching inside the function itself.

11. **What existed before `go:embed` (Go < 1.16) for the same problem?**
    Third-party tools (`go-bindata`, `packr`, `statik`) that generated `.go` files with serialized contents through a `go generate` step before `go build`.

## Embed checklist

1. The directive is immediately above the `var` declaration, in a file that is in the same directory as the resource (or its parent).
2. Every path in the pattern uses `/`, never `\`.
3. There is no `.` or `..` segment in the pattern.
4. The `all:` prefix is explicitly added where hidden files are intentionally needed.
5. A test that does `ReadFile`/`ReadDir`/`ParseFS` exists in CI, so a broken pattern does not pass unnoticed.
6. Binary size was measured before and after embedding larger assets.
7. No secret (an API key, a private key, a `.env`) is in an embedded directory.
8. The README documents what is embedded and why.

## Summary

`go:embed` joins static, build-time-known resources with the binary: `string`, `[]byte`, or `embed.FS`, with paths relative to the file that contains the directive and with no possibility of `..`. Ideal for templates (`ParseFS`), migrations, and static files (`http.FS` + `fs.Sub`). Empty directories fail the build. Hidden files require the `all:` prefix. Secrets and content that changes without a rebuild stay outside the embed. Every embedded byte is permanently in the binary — measure the effect on size before you embed something large.
