# 04.02 Go modules and workspaces: go.mod, replace, go.work, tidy in CI

> **Go Path - Zero to Gopher** / **02 Intermediate → Managing Go Projects** / Lesson 04.02

## Lesson goals

- Read and maintain **`go.mod`** and **`go.sum`** and know exactly what is written into which file.
- Use **`go.work`** for local development of several modules without dirtying `go.mod`.
- Use **`replace`** for local paths and understand why it is dangerous on the main branch.
- Explain (at least briefly) how **minimal version selection (MVS)** chooses which dependency version enters the build.
- Know the caution around **multi-module** repositories.
- Run **`go mod tidy`** in CI consciously, as a cleanliness check, not as a blind fix.

## Prerequisite

- `go mod init`, `go get` — basic use.
- The project layout from 04.01 (`cmd`/`internal`).

## Problem this lesson solves

Five `go.mod` files scattered across a monorepo with no workspace — every change in a shared library requires `go get` in five directories in order to test it locally. A `replace` directive toward `C:\Users\marko\dev\redact` stays in the code, passes review because nobody read the `go.mod` diff carefully, and CI on a Linux runner fails with `no such file or directory`. `go.sum` out of sync with `go.mod` after a manual merge conflict — the build works on one laptop and not on another, because the dependency hash differs. CI that does not check whether the module is tidy, so a dependency added locally through the IDE never reaches `go.mod`, and the build fails only on another developer's machine. An accidental major upgrade through a loosely written version in a `go get` command, which pulls an incompatible API change with no warning.

This lesson settles all of the above: the exact semantics of `go.mod`/`go.sum`, when and how to use `replace`, `go.work` as a local solution without committing private paths, and the tidy check as part of CI discipline.

## Mental model

1. A **module** is the unit of versioning — a path (`module example.com/shop`) plus tags of the semver form `vMAJOR.MINOR.PATCH`.
2. **`go.mod`** states **requirements** (which versions of dependencies your code uses directly and indirectly); **`go.sum`** states **cryptographic checksums** of the exact downloaded contents — two different jobs, two different files.
3. **One module per service** is the default advice. More modules means more boundaries, more ceremony, more places where versions can drift apart.
4. **`go.work`** joins several modules **locally**, in the development environment, without writing `replace` into every `go.mod` that would then have to be removed before merge.
5. **`replace`** redirects a requirement for a given module to another path (local disk) or another version. It is powerful for development, and dangerous if it enters the main branch, because other machines do not have the same path on disk.

## Mechanism

### 1. What `go get` writes, step by step

When you call `go get github.com/jackc/pgx/v5@v5.7.4`, this happens:

1. The tool contacts the proxy (by default `proxy.golang.org`, or `GOPROXY` if it is set) and downloads the metadata and the module contents for the requested version.
2. It computes the content hash (`go.sum` format: `h1:...`) and writes it into `go.sum`, together with the hash of that dependency's `go.mod` file.
3. It writes `require github.com/jackc/pgx/v5 v5.7.4` into **your** `go.mod`, in the appropriate `require` block.
4. If `pgx/v5` itself depends on other packages (for example, `github.com/jackc/pgpassfile`), those dependencies are written into `go.mod` with the comment `// indirect`, and they also get their own lines in `go.sum`.

Pin `github.com/jackc/pgx/v5@v5.7.4`. That release's own `go` line is `1.21`, so the Go 1.22 toolchain builds it. A later `pgx` `v5` patch that raises its own `go` line is the wrong pin for this course.

**Predict:** You manually delete the line `github.com/jackc/pgpassfile v1.0.0 // indirect` from `go.mod`, but you do not touch `go.sum`, and you call `go build`. Does the build succeed?

**Answer:** It depends. If `pgpassfile` is still transitively required (because `pgx/v5` imports it), `go build` will add it back into `go.mod` on the next `go mod tidy`, or even on `go build` in newer versions of the tool that automatically update `go.mod` when needed. Until that happens, `go.mod` is in an inconsistent state and `go build`/`go vet` may report that `go.mod` needs an update. Manually editing `go.mod` without `go mod tidy` is therefore risky. It is better to always let the tool write the line.

### 2. `go.sum` — what is checked on every build

`go.sum` contains two lines for every (transitive) dependency: the hash of the module contents and the hash of its `go.mod` file. On **every** `go build`/`go test`, the tool downloads (or finds in the local cache `$GOPATH/pkg/mod`) the dependency contents, computes the hash, and **compares** it with what is written in `go.sum`. If they do not match, the build is rejected with `checksum mismatch` — regardless of whether the difference is benign or malicious. This is the mechanism that prevents someone from silently replacing the contents of a dependency on the proxy or on your disk without your knowledge.

**Predict:** Two developers work on the same repo. Developer A runs `go get pkg@v1.2.0` and commits `go.mod`+`go.sum`. Developer B pulls the changes, but his local module cache (`$GOPATH/pkg/mod`) already has `pkg@v1.2.0` downloaded from **another** project, from another proxy. Does the build on developer B's machine fail with `checksum mismatch`?

**Answer:** No, and that is the point of the mechanism. The contents of `pkg@v1.2.0` are identical regardless of where they were downloaded from (the same tag, the same contents in a properly published library), so the hash is identical, so the check passes. `checksum mismatch` appears only when the contents **differ** for the same declared version — which is a signal that something is wrong (a malicious replacement, a corrupted cache, or a badly configured private proxy), not a normal situation.

### 3. Minimal version selection (MVS) — exactly how a version is chosen

When your module depends on `A@v1.2.0`, and `A` itself depends on `B@v1.0.0`, and you **also** depend directly on `B@v1.3.0`, which version of `B` enters the final build?

Go uses **minimal version selection**: of all the versions that appear as a requirement **anywhere** in the transitive dependency graph, it takes the **greatest** of them — not the newest available in the world, but the greatest **required**. In this example: `A` asks for `B@v1.0.0`, you ask for `B@v1.3.0` — the build uses `v1.3.0`, because that is the greatest requirement that exists in the graph. The word "minimal" here means: Go does not automatically take the newest version published on the internet (the way npm sometimes does with `^` ranges). It takes the smallest version that **satisfies every known requirement**, which is often an older version than what `@latest` would return.

**Predict:** You publish `B@v2.0.0` (a major bump) today. Your `go.mod` still says `require B v1.3.0`. Does the next `go build` (without `go get`) automatically start using `B@v2.0.0`?

**Answer:** No. MVS chooses the greatest **required** version from the existing `require` lines in the graph. `v2.0.0` is not required anywhere until you or some dependency explicitly request it through `go get B@v2.0.0` (or through an import of a `.../v2` path, because Go treats different major versions ≥2 as different module paths). Without an explicit requirement, the build stays on `v1.3.0` forever. Reproducibility is the default behavior, not an accident.

For a look at the versions actually chosen: `go list -m all` prints the **final** graph after MVS, not the raw requirements from each `go.mod` separately.

### 4. `replace` — a redirection mechanism, not a change of identity

`replace example.com/redact => ../redact` does not change the path by which code imports the package (`import "example.com/redact/..."` stays the same). It changes **where the tool fetches the contents** for that path identity. On `go build`, when it meets a requirement for `example.com/redact`, the tool first looks at the `replace` block. If there is a match, it uses the local path (or another version/repo) instead of the proxy, and it **ignores** the `go.sum` hash checks for that module (because local files are not an immutable release the way a published version is).

This explains why it is dangerous on the main branch: `replace ... => ../redact` or `replace ... => C:\Users\marko\redact` works perfectly on the machine where that path exists, and **rejects the build** on every other machine (a CI runner, a colleague, a production build server) with `no such file or directory`, because the tool literally tries to read files from that path.

**Predict:** You add `replace example.com/redact => ../redact` only in your **local** `go.mod`, but you do not commit it (you put it in `.gitignore` mentally, that is, you simply do not stage it). A colleague pulls your commit with the rest of the changes. Does his build work?

**Answer:** If the `replace` line never entered the commit, the colleague does not see it and his build uses the normal `require` (proxy or cache). It works, provided the published version of `example.com/redact` exists and contains what your code expects. The problem arises **only** if the `replace` line **was** committed — hence the rule "replace is short-lived, remove it before merge or replace it with `go.work`".

### 5. `go.work` — a mechanism with no write into `go.mod`

A `go.work` file (created with `go work init ./module-a ./module-b`) lives **beside** the modules, not inside the `go.mod` of any of them. When `go.work` is present in the current or a parent directory, `go build`/`go test`/IDE tooling detect it automatically and use **workspace mode** — which means that for modules listed in the `use` block, the tool uses the local contents from disk instead of the proxy/cache, **with** no change in the `go.mod` of each module.

```go
go 1.22

use (
	.
	../redact
)
```

The effect is identical to `replace` in the sense of "use local disk", but the recording mechanism is completely separate: `go.mod` stays untouched, so it is impossible for a local path to slip by mistake into a commit that affects other developers' `go.mod`. `go.work` itself **may** be committed if it is part of a standard monorepo setup with no personal absolute paths (for example, all relative paths inside the same repo) — or it is kept in `.gitignore` if each developer has their own set of local modules they develop in parallel.

**Predict:** You have a `go.work` with `use (. ../redact)` in your working directory, and AT THE SAME TIME `replace example.com/redact => ../redact-old` in the `go.mod` of the `.` module. Which local contents are used for `example.com/redact`?

**Answer:** `go.work` has priority over `replace` in `go.mod` when the module is listed in the workspace `use` block. Workspace mode overrides the individual modules while it is active. In this case `../redact` (from `go.work`) is used, not `../redact-old` (from the `go.mod` `replace`). This is another reason for `go.work` to be the preferred tool for local multi-module work: one place of decision, outside `go.mod`.

### 6. `go mod tidy` in CI — exactly what is checked

`go mod tidy` does two jobs: (1) it adds to `go.mod`/`go.sum` every dependency that the code actually imports but that is not written down, and (2) it **removes** from `go.mod` requirements for dependencies that the code no longer imports anywhere. The CI step `go mod tidy && git diff --exit-code go.mod go.sum` determines whether the **current state** of `go.mod`/`go.sum` in the repo is identical to what `tidy` would produce. If they differ (a developer locally added an import and forgot `go mod tidy`, or `go.sum` stayed older after a merge), `git diff --exit-code` returns a failing status and the CI step fails, **before** tests run that might even pass with an inconsistent state.

**Predict:** A developer adds `import "golang.org/x/exp/slices"` to the code, but does not run `go mod tidy` locally, and pushes. Does `go build` on CI fail immediately?

**Answer:** It depends on the tool version and the settings. A newer `go build` can automatically update `go.mod` during the build if that is allowed (`-mod=mod`, the default behavior in some configurations), so the build itself can succeed while it updates files on the fly. But the CI step `go mod tidy && git diff --exit-code` still **fails**, because after `tidy` there is a difference between the working state and the committed `go.mod`/`go.sum`. That is exactly the signal we want: "the local state is not equal to what tidy would produce from the current code", regardless of whether the build succeeds or not.

### 7. `GOPROXY`, `GOSUMDB`, `GOPRIVATE` — the exact check order on `go get`

When `go get`/`go build` needs to download a module that is not already in the local cache, the tool goes through several configurable decision points, in order:

1. **`GOPRIVATE`** (and the related `GONOSUMCHECK`/`GOFLAGS`) — a list of module-path patterns (for example, `example.com/internal-libs/*`) for which both the proxy and the sumdb checks are **skipped**. The tool goes directly to the source (for example, a private git server through a configured `GOPROXY=direct` for those patterns, or through VCS).
2. **`GOPROXY`** — a list of proxy servers (by default `https://proxy.golang.org,direct`), tried in order. `direct` as a value means "download directly from VCS (git/hg)" instead of from the proxy.
3. **`GOSUMDB`** — a public, transparent checksum log (`sum.golang.org` by default) that the tool consults to confirm that the hash the proxy returned matches the **globally known** hash for that version. An additional check **above** the `go.sum` check from section 2, useful the first time you download a version that is not yet in your `go.sum`.

**Predict:** A team works with a private module `example.com/internal-libs/auth`, hosted on a private git server with no access from the public internet. `go get` with no configuration tries to download through `proxy.golang.org`. Does it succeed?

**Answer:** No. The public proxy has no access to the private server, and the download fails with an error (404 or a timeout). The fix: `GOPRIVATE=example.com/internal-libs/*` (or a wider `GONOSUMCHECK`/`GOFLAGS` as needed), so that for that path pattern the tool bypasses both the public proxy and the public sumdb, and goes directly to VCS with credentials configured in `.netrc`/git config. Document this in the team README, because it is easy to forget when a new private module is added.

### 8. The build list — the MVS algorithm over the requirement graph, a concrete trace

Last time (section 3) explained **what** MVS chooses. Here is **how** the algorithm actually constructs the final list of versions (the build list), step by step, for a concrete example:

```text
shop (your module) requires: A@v1.2.0, B@v1.3.0
A@v1.2.0 requires: B@v1.0.0, C@v2.0.0
C@v2.0.0 requires: B@v1.1.0
```

1. The tool starts from **your** `go.mod`. The direct requirements are `A@v1.2.0`, `B@v1.3.0`.
2. For each requirement, it recursively loads the `go.mod` of **that** version of that dependency and adds **its** requirements to the set. `A@v1.2.0` brings `B@v1.0.0` and `C@v2.0.0`. `C@v2.0.0` brings `B@v1.1.0`.
3. When the set of all requirements for each module is complete, for **each** module the **maximum** version among all requirements for that module is taken. For `B`, the set of requirements is `{v1.3.0 (yours), v1.0.0 (from A), v1.1.0 (from C)}`, and the maximum is `v1.3.0`.
4. The final build list: `A@v1.2.0`, `B@v1.3.0` (your requirement is already the greatest), `C@v2.0.0`.

**Predict:** You remove your direct requirement for `B` from `go.mod` (only `A` and `C` remain as sources of requirements for `B`, indirectly). Which version of `B` enters the build list now?

**Answer:** `v1.1.0` — the maximum of the remaining requirements `{v1.0.0 (from A), v1.1.0 (from C)}`. This is a concrete demonstration of why removing **your** direct requirement can **lower** the effective version of a dependency that enters the build. MVS always takes the maximum of the **currently existing** requirements, and your direct requirement was the one that had been guaranteeing `v1.3.0`.

### 9. `exclude` and `retract` — directives that MVS takes into account

`go.mod` can contain `exclude module version`. It tells the tool to **never** consider exactly that version as a candidate during MVS, even if some dependency requires it. The algorithm behaves as if that version does not exist and looks for the **next greater** available version that satisfies the remaining requirements. This is a rarely needed tool. It is used when a specific version is known to have a critical bug or a security flaw, and teams cannot wait for every transitive requirement to be updated.

`retract` is a similar but reversed directive. The library publisher (not the consumer) writes `retract v1.2.3` into **their** `go.mod` to warn every consumer that that version should not be used. `go get`/`go list -m -u` show a warning, but they do not block the build automatically unless the consumer explicitly asks for that.

**Predict:** The library `example.com/redact` publishes `v1.5.0` with a critical bug, then immediately publishes `v1.5.1` (the fix) and adds `retract v1.5.0` in the `go.mod` of version `v1.5.1`. Your `go.mod` requires `v1.5.0`. Does `go build` refuse to compile because of `retract`?

**Answer:** Not automatically. `retract` is an informational directive. `go build` still compiles with `v1.5.0` if that is the required version. `go list -m -u all` and `go get` (with no target version) show a warning that the version has been retracted and suggest an upgrade, but the decision to update `go.mod` to `v1.5.1` is made by the consumer explicitly through `go get example.com/redact@v1.5.1`.

### 10. The `-mod` flag and `GOFLAGS` — three modes of working with `go.mod`

The `go build`/`go test`/`go run` tool accepts `-mod=<mode>` (or globally through `GOFLAGS=-mod=<mode>` in the environment), which determines what happens when the code and `go.mod` are not fully aligned:

- **`-mod=readonly`** (the default since Go 1.16): the tool **refuses** to modify `go.mod`/`go.sum` itself if it notices a missing requirement. Instead it reports an error and suggests that you run `go mod tidy` or `go get` manually. This is the safe default choice for CI. The build does **not** silently change files that you should commit consciously.
- **`-mod=mod`**: the tool **itself** updates `go.mod`/`go.sum` during the build when it notices a missing requirement. Useful for local, fast development, but risky in CI because it hides that something is out of sync (the build "works" while it silently modifies files that CI does not commit).
- **`-mod=vendor`**: the tool reads dependencies exclusively from the `vendor/` directory (section 11 of lesson 04.01), ignoring the proxy/cache completely.

**Predict:** CI uses `GOFLAGS=-mod=mod` (set by mistake by copying a local developer configuration). A developer forgets `go mod tidy` before the push and the CI build **succeeds** because `-mod=mod` itself adds the missing `require`. Does the tidy-check step (`go mod tidy && git diff --exit-code`) still catch the problem?

**Answer:** Yes. `-mod=mod` affects only the **build/test** step, not the explicit `go mod tidy && git diff --exit-code` step that runs separately in the same CI pipeline (according to section 6). Even if `go build` with `-mod=mod` "fixes" `go.mod` in memory or on the disk of the CI runner, `git diff` will show that the working copy differs from the committed version, and that step still fails. This is why the tidy-check step should be **independent** of which `-mod` mode is set for the build. It catches the problem regardless of whether the build itself "quietly" fixes things.

## Rules and syntax

- Commit `go.mod` and `go.sum` **together**, in the same commit as the code change that causes them.
- Do not commit a machine-specific `replace` (an absolute path such as `C:\Users\...` or `/home/...`) to a shared branch.
- Prefer `go.work` for local, frequently changing experiments with several modules. Leave `replace` for short-lived, intentional cases.
- Use a multi-module layout only with a clear reason (independent versioning of a library that other teams consume separately).
- In CI: `go mod tidy`, then `git diff --exit-code go.mod go.sum`, to prove that the repo is in a tidy state.
- For a published library's major version ≥2, the module path must contain a `/vN` suffix (`example.com/lib/v2`). Go treats that as another path, not as "a greater version of the same path".

## Development tools

`go get -tool` and the `tool` directive need Go 1.24+. Go 1.22 and Go 1.23 keep the `tools.go` blank-import pattern.

The course baseline is Go 1.22+. A sample that needs Go 1.24+ is not presented as runnable on Go 1.22. On Go 1.24+ you record a development tool the same way you pin a library:

```text
go get -tool golang.org/x/tools/cmd/stringer@v0.38.0
go install tool
```

That writes a `tool` directive into `go.mod`. Review the exact tool version the way you review a library version. On Go 1.22 and Go 1.23 the module keeps a `tools.go` file whose blank import (`import _ "golang.org/x/tools/cmd/stringer"`) is what holds the tool in the module graph. Do not mix the `tool` directive and the `tools.go` blank-import pattern in one module without saying which Go version that module requires.

## Examples

### Example 1 — A readable `go.mod`

```go
module example.com/shop

go 1.22

require (
	github.com/jackc/pgx/v5 v5.7.4
	golang.org/x/sync v0.6.0
)

require (
	// indirect dependencies that tidy adds
	github.com/jackc/pgpassfile v1.0.0 // indirect
)
```

#### What happens here

The `go` line sets the minimum language version that the build tool respects during compilation (an effect on the available language features). The direct `require` block is your conscious choices — packages that your code actually imports. The second `require` block, with the `// indirect` comment, is the dependencies of your dependencies, which `tidy` traces and writes itself. You do not delete them by hand, and you do not touch `go.sum`. `github.com/jackc/pgx/v5 v5.7.4` is the pin: its own `go` line is `1.21`.

### Example 2 — `replace` for local development (temporary)

```go
module example.com/shop

go 1.22

require example.com/redact v1.2.0

replace example.com/redact => ../redact
```

#### What happens here

According to the mechanism in section 4, `go build` recognizes the `replace` block and, for the identity `example.com/redact`, reads the contents from `../redact` on disk, bypassing the proxy and the `go.sum` checks for that module. Excellent for branches in development. Remove it before merge, or replace it with `go.work`, so that `go.mod` on the main branch stays free of local paths.

### Example 3 — `go.work`

```go
go 1.22

use (
	.
	../redact
)
```

```bash
# in the shop directory
go work init . ../redact
```

#### What happens here

The tool sees both modules as a workspace, according to the mechanism in section 5. The `go.mod` of the `shop` module stays clean, with no `replace`. `go.work` is often not committed — each developer generates their own locally, depending on which modules they are currently developing in parallel.

### Example 4 — Multi-module caution

```text
monorepo/
  services/api/go.mod
  services/worker/go.mod
  libs/auth/go.mod
```

The problems: aligning versions of `libs/auth` in both services, a duplicated `tidy` step in CI for all three modules, a harder refactor when a change in `auth` requires a simultaneous change in both services. Use this layout when `auth` really must have an independent semver (for example, it is also published outside the monorepo). Otherwise, one module plus `internal/auth` from 04.01 covers the same need with less ceremony.

#### What happens here

More modules is not "scaling" by itself. According to the MVS mechanism in section 3, each module has its own requirement graph that must be maintained and tidied separately. More modules means more graphs to keep aligned, not automatically a better organization.

### Example 5 — `tidy` in CI

```yaml
# sketch of a GitHub Actions step
- name: Tidy check
  run: |
    go mod tidy
    git diff --exit-code go.mod go.sum
```

#### What happens here

According to the mechanism in section 6, if someone forgets `tidy` locally, this CI step fails before the tests, with a clear message (`git diff` shows exactly which lines are missing or superfluous). It keeps builds reproducible and prevents "works on my machine" situations.

### Example 6 — An upgrade done consciously

```bash
go get golang.org/x/sync@v0.7.0
go mod tidy
go test ./...
```

#### What happens here

An explicit version in `go get`, then `tidy` to align the transitive requirements, then a test of the packages that use that dependency. Avoid `@latest` in scripts without a human check. The MVS mechanism means you will get exactly the version you request, so an unconscious jump to a major version with `@latest` can introduce an incompatible API change with no warning during CI.

## Decision analysis

| Decision | Reason |
|----------|--------|
| One module as the default | Less friction, one requirement graph to maintain |
| `go.work` for local multi-module | `go.mod` stays clean, with no risk of a wrong commit |
| A `tidy` check in CI | `go.sum` discipline, catches a forgotten local `go get` |
| `replace` only short-lived | No laptop paths on the main branch |
| An explicit version in `go get` | Control over which version enters the MVS graph |

## Trade-offs

- A workspace (`go.work`) is not a substitute for published versions of libraries. It is useful only while you develop locally, not as a permanent solution for a production build.
- `go mod vendor` helps offline/air-gap environments and strict reproduction. It increases the repo size significantly.
- Pseudo-versions (`v0.0.0-20240101123456-abcdef`) are valid for MVS, but they are harder to read than tagged releases. Prefer tags for libraries you control.
- MVS means that "the newest in `go.mod`" is not always the newest transitively available. `go list -m all` shows the versions actually chosen, not what `@latest` would return for each dependency individually.

## Common mistakes

### **Wrong:** `replace example.com/redact => C:\Users\marko\dev\redact` (or a similar absolute path) stays in `go.mod` after the merge to the main branch.
**Effect:** CI on a Linux/macOS runner, or any colleague without an identical path on disk, gets `no such file or directory` on `go build`, because the tool literally tries to read files from that path.
**Fix:** Remove `replace` before merge, or replace it with a local `go.work` that is not committed (or is committed only with relative, repo-internal paths).

### **Wrong:** Manually editing `go.sum` (deleting or adding lines) to "resolve" a conflict during a merge.
**Effect:** `go.sum` becomes inconsistent with the actual contents of the dependencies. The next `go build` reports `checksum mismatch` or `missing go.sum entry`, because the hashes do not match what the tool actually downloads.
**Fix:** Accept one side of the conflict for `go.mod`, then run `go mod tidy` so the tool itself regenerates the whole `go.sum` from the exact state of `go.mod`. Never line by line by hand.

### **Wrong:** The repo has five `go.mod` files "for a clean architecture" in a team of three developers, with no need for independent versioning.
**Effect:** Every change that touches a shared library requires `go get`/`tidy` in several modules in order to test it locally. Versions of `libs/auth` drift apart between services because nobody has the discipline to raise everything at the same time.
**Fix:** Go back to one module with an `internal/auth` package (04.01), unless there is a confirmed external consumer that requires an independent semver for `auth`.

### **Wrong:** CI has no `go mod tidy` check. It relies only on `go build`/`go test` to catch dependency problems.
**Effect:** A developer locally adds an import through the IDE (which automatically updates `go.mod` in the editor), but forgets to run `tidy` or to commit the updated `go.sum`. Another developer pulls code that does not build cleanly, or CI uses a stale `go.sum` with no warning.
**Fix:** Add the step `go mod tidy && git diff --exit-code go.mod go.sum` to the CI pipeline, before the tests. It fails quickly and clearly instead of the problem coming to light only on another machine.

### **Wrong:** `go get -u ./...` run with no review, in an attempt to "raise everything to the newest".
**Effect:** Several dependencies jump at once, including potentially major versions with incompatible API changes. When a test fails, it is hard to determine which of the ten changed dependencies is the cause.
**Fix:** Upgrade in a targeted way, one dependency per `go get package@version`, test, then the next. The MVS mechanism guarantees that only that one dependency and its transitive consequences change in a given step.

### **Wrong:** Mixing old `GOPATH` habits (code must be in `$GOPATH/src/...`) with modules in an arbitrary directory.
**Effect:** Confusion about why `go build` does not find local packages, or why behavior differs between machines with different `GOPATH` settings. Unnecessary copying of the repo into a specific folder.
**Fix:** With modules (`go.mod` present), the location on disk is arbitrary. `GOPATH` no longer determines where the code must live or how it is found.

### **Wrong:** A new private module is added as a dependency without setting `GOPRIVATE`, relying on `go get` to "somehow" find a path to it.
**Effect:** `go get` tries through the public proxy and the public sumdb server according to the mechanism in section 7, gets a 404 or an access error, and the developer wastes time thinking the problem is credentials or the network, while the real cause is that the tool does not even attempt direct access to the private server.
**Fix:** Set `GOPRIVATE` (and, if needed, `GONOSUMCHECK`) with the path pattern of the private module, documented in the team README, before the first `go get` of that module on a new machine.

### **Wrong:** Removing your own direct `require` line for a dependency "because tidy will probably keep it anyway" when the dependency is still transitively needed.
**Effect:** According to the MVS mechanism in section 8, removing the direct requirement can **lower** the effective version that enters the build (to the maximum of the remaining, lower transitive requirements), silently returning an older version with possible bugs that the newer version was fixing.
**Fix:** Before deleting a `require` line, run `go list -m all` to determine whether the effective version changes. If it does, and the old version is not desirable, leave an explicit `require` on the desired version even if it is "technically" satisfied transitively by a lower one.

## Idiomatic Go

- `go get package@version` for a targeted, conscious upgrade of one dependency.
- `go list -m -u all` to see which dependencies have a newer version available, before you request them.
- `go list -m all` to see the **versions actually chosen** after MVS, useful when "it works for me, it does not work for you".
- Document in the README how to bring up `go.work` for local multi-module work, and which dependencies the team has intentionally pinned.
- For public libraries: tags of the form `v1.2.3`. For major ≥2, the path must have a `/vN` suffix.
- For development tools, `go get -tool` and the `tool` directive need Go 1.24+. Go 1.22 and Go 1.23 keep the `tools.go` blank-import pattern.

## Practical scenario

A team shares `libs/telemetry` as a separate module because other (independent) services in the company consume it through an internal proxy. Two services in the same monorepo get stuck on different versions of `telemetry` because nobody synchronized the upgrade. A developer, trying to test a new version locally without waiting for a tag and a publish, adds `replace example.com/telemetry => ../../libs/telemetry` to the `go.mod` of their service, and that accidentally enters the pull request.

Review does not notice the line (the diff is large, `replace` is at the bottom of the file). CI on a Linux runner fails with `no such file or directory`, because the runner does not have an identical directory structure to the developer's local monorepo checkout. The fix: a team policy — `go.work` is the only allowed mechanism for local multi-module work, and it is never committed with absolute paths. CI uses only published versions. The tidy check is a mandatory step that would, along the way, have caught the problem here as well (`go mod tidy` would delete the `replace` line because tidy does not generate `replace`, only `require`/`exclude`, so the diff would signal an unexpected difference).

## Check questions

1. **What does `go mod tidy` do, exactly?**
   It adds to `go.mod`/`go.sum` dependencies that the code imports but that are not written down, and it removes from `go.mod` requirements for dependencies that the code no longer imports. It aligns the declared state with the actual imports.

2. **What is `go.work` for, and how does the mechanism differ from `replace`?**
   It locally joins several modules for development without writing anything into the `go.mod` of the individual modules. `replace` writes the redirection directly into `go.mod`, which then has to be removed before a commit to a shared branch.

3. **Why is `replace` dangerous if it enters the main branch?**
   It most often points at a path on disk that exists only on the machine of the developer who added it. CI and other machines get `no such file or directory`.

4. **What does minimal version selection (MVS) choose when there are several requirements for the same dependency?**
   The greatest version of all the **required** versions in the whole transitive graph — not the newest published in the world, but the greatest that appears as a requirement somewhere in the graph.

5. **Why commit `go.sum` together with `go.mod`?**
   `go.sum` contains the hashes that `go build` compares on every build to confirm that the downloaded dependency contents are identical to what was first recorded. Without it, two builds of the same `go.mod` have no guarantee that they use identical dependency contents.

6. **When is it justified to have more than one module in a repo?**
   When there is a confirmed need for independent semver versioning of a part of the code (for example, a library consumed by teams or repositories outside your control of the release cycle). Otherwise one module plus `internal/` from 04.01 covers the same organizational need with less ceremony.

## Diagnosis: "works on my machine" through dependencies

When a build works on one machine and does not work on another, and the reason is not obvious, the check order is:

```bash
go version                          # is the same Go tool on both machines
go list -m all                      # compare the build list from section 8 of Mechanism on both machines
git diff go.mod go.sum              # are the files identical in the repo on both machines (commit hash)
go env GOFLAGS GOPROXY GOPRIVATE    # does the environment configuration differ
```

The most common cause is not a "mysterious" hash inconsistency, but one of three things: (1) a commit that one machine has not pulled, (2) `GOFLAGS=-mod=mod` on one machine that silently updates `go.mod` locally instead of reporting an error, or (3) `replace`/`go.work` active on one machine and not on the other. All three are caught by the commands above before you suspect the Go tool itself or the proxy.

## Checklist before adding a new dependency

1. Does the stdlib already cover the need (`net/http`, `encoding/json`, `context`) with no extra dependency?
2. Is there a team-preferred library for this category of work (HTTP router, logger), instead of a random choice?
3. What is the license, and is it actively maintained (last commit, open security issues)?
4. Does it add **transitive** dependencies that significantly widen the build graph — run `go list -m all` before and after a trial `go get` to see the difference.
5. Is the version tagged (not a pseudo-version) and is the major version stable (≥1)?

## Mini guide: when `go.work`, when `replace`, when a new tag

| Situation | Tool |
|---|---|
| Local, short-lived development of two related libraries at the same time | `go.work` |
| An urgent, temporary local patch while you wait for an upstream PR to be merged | `replace` (short-lived, remove before merge) |
| A permanent change that another team/repo needs to use | A new tag on the library + `go get` of the targeted version |
| Work on a monorepo library used by several services in the same repo, with no separate module | None of the above is needed — `internal/` from 04.01 is usually enough |

## Mechanism — in depth: `go.work` step by step

### Creating a workspace with concrete paths

Imagine that on disk you have:

```text
D:\dev\shop\          ← module example.com/shop
D:\dev\redact\        ← module example.com/redact
```

In the `shop` directory:

```bash
go work init .
go work use ../redact
```

The tool creates `go.work`:

```go
go 1.22

use (
	.
	../redact
)
```

**Predict:** `shop/go.mod` still has `require example.com/redact v1.2.0`. Does that line change after `go work use`?

**Answer:** No. `go.work` does not touch `go.mod`. The requirement stays `v1.2.0` in the declaration, but while the workspace is active, the contents for the identity `example.com/redact` come from `../redact` on disk — even if the local directory has different code from the tagged `v1.2.0`.

### What `go list -m` sees in the workspace

```bash
go list -m example.com/redact
```

Typical output in workspace mode:

```text
example.com/redact => ../redact
```

The arrow `=>` shows that the module has been **remapped** to a local path. Outside the workspace (with no `go.work`, or with `GOWORK=off`) the same call returns only the version from `go.mod`/`go.sum` with no `=>`.

**Predict:** You set `GOWORK=off` in the shell while you are in the `shop` directory that has a `go.work`. Does `go build` still use `../redact`?

**Answer:** No. `GOWORK=off` turns the workspace off. The tool returns to ordinary module mode and reads `example.com/redact` from the proxy/cache according to the `require` in `go.mod`. This is useful as a check: "does my code also work without the local workspace, with only the published version?"

### `go work sync` — aligning requirements

When in a workspace you change a `require` in one of the modules, `go work sync` can align versions of dependencies that appear in several `use` modules. It is not a substitute for `go mod tidy` inside each module. It works at the workspace level to reduce version drift between the local modules you are developing in parallel.

```bash
go work sync
```

**Predict:** `shop` requires `golang.org/x/sync v0.6.0`, `redact` requires `v0.7.0`, and both are in `use`. After `go work sync`, what happens to the versions?

**Answer:** The tool raises the lower requirement to the higher one where that is needed for the workspace to be consistent (MVS inside the workspace). Concretely, `shop` may get an updated `require` on `v0.7.0` if sync decides to align them. That is why you run sync consciously and look at `git diff` before a commit. It can modify the `go.mod` of the local modules.

### When to commit `go.work`, and when not to

| Situation | Commit `go.work`? |
|-----------|-------------------|
| Monorepo: `use (./services/api ./libs/auth)` with relative paths inside the same repo | Often yes — every developer has the same paths |
| A personal experiment: `use (./shop C:\Users\marko\forks\redact)` | No — an absolute / personal path |
| A team convention: everyone generates their own `go.work` locally | No — put it in `.gitignore` |

The rule: if `go.work` on a CI runner or on a colleague's laptop **would have to** find a path that does not exist in the checkout, do not commit it.

## Mechanism — in depth: `replace` in three forms

### Form 1 — a local relative path

```go
replace example.com/redact => ../redact
```

The import in the code stays:

```go
import "example.com/redact"
```

On build the tool reads files from `../redact`. The path identity **does not change**. Only the source of the contents changes.

### Form 2 — another version of the same module

```go
replace example.com/redact v1.2.0 => example.com/redact v1.1.9
```

It forces an older version even if MVS would otherwise choose `v1.2.0`. Rare and intentional — for example, a temporary pin while a bug in `v1.2.0` is fixed.

### Form 3 — another module / a fork

```go
replace example.com/redact => github.com/tim/redact v0.0.0-20240101120000-abcdef123456
```

It redirects to a fork. Useful while you wait for an upstream PR to be merged. Dangerous if it stays forever with no plan to return to the official module.

**Predict:** You commit form 1 (`=> ../redact`) in a PR. CI checks out only the `shop` repo (with no sibling `redact` directory). What does `go build` report?

**Answer:** An error of the type `replacement directory ../redact does not exist` / `no such file or directory` — because the relative path is resolved relative to the location of `go.mod`, and the sibling folder is not in the CI workspace.

### `replace` and `go.sum`

For a local `replace` to a directory, the tool does **not** check the `go.sum` hash for that module. Local files are not an immutable release. That is why `replace` on a shared branch also weakens the reproducibility guarantee: another machine can have different local contents at the same relative path.

## Mechanism — in depth: MVS in plain language

### Analogy: "the highest bar that everyone requires"

Imagine that every `require` in the graph says: "I need at least version X". MVS does not go to the internet to look up "what is newest today". It gathers all those "at least X" requirements and takes the **greatest X** among them.

```text
You say:        B >= v1.3.0   (require B v1.3.0)
A says:         B >= v1.0.0
C says:         B >= v1.1.0
────────────────────────────
MVS chooses:    B v1.3.0
```

If tomorrow `B v1.9.0` comes out on the proxy, and nobody in the graph requires it, the build **stays** on `v1.3.0`. That is reproducibility: the same `go.mod` graph → the same build list, today and a year from now.

### Why it is called "minimal" selection

"Minimal" does not mean "take the smallest possible version in the world". It means: take the **smallest version that satisfies every existing requirement** — and that version is exactly the maximum of the required ones, because anything smaller would not satisfy the strictest requirement.

```text
Requirements for B:  v1.0, v1.1, v1.3
Smallest that satisfies ALL:  v1.3
(because v1.0 does not satisfy the requirement for v1.3)
```

### Major versions ≥ 2 are not "a bigger number of the same path"

```text
example.com/lib      ← v0 and v1
example.com/lib/v2   ← v2 (a different module path!)
example.com/lib/v3   ← v3
```

MVS does **not compare** `v1.9.0` and `v2.0.0` as two versions of the same module. They are two different modules in the graph. That is why `go get example.com/lib@v2.0.0` does not work the way you expect without `/v2` in the path. You need `go get example.com/lib/v2@v2.0.0`.

**Predict:** `go.mod` has `require example.com/lib v1.5.0`. You run `go get example.com/lib@latest` and `latest` is `v2.3.0`. What gets written?

**Answer:** For modules with major ≥ 2, `@latest` on the old path (`example.com/lib` without `/v2`) typically returns the newest **v1** (or v0) tag on that path. It does not automatically jump to the v2 path. To enter v2, explicitly request `example.com/lib/v2@v2.3.0` and change the imports.

### How to see the MVS decision, instead of guessing

```bash
go list -m all                    # the final build list
go list -m -versions example.com/redact   # available tags
go list -m -u all                 # what has something newer than the currently chosen version
go mod why -m github.com/jackc/pgpassfile # why this dependency is in the graph
```

`go mod why -m` is especially useful when you see `// indirect` and ask "who made me pull this?"

## Mechanism — in depth: `go mod tidy` as discipline

### What tidy does, on an example

The starting state — the code imports `pgx`, but `go.mod` is empty of it (the developer added the import in the editor and forgot the tool):

```go
// go.mod before tidy
module example.com/shop
go 1.22
```

```go
// main.go
import _ "github.com/jackc/pgx/v5/stdlib"
```

After `go mod tidy`:

1. The tool scans every `.go` file (including tests).
2. It sees the import `github.com/jackc/pgx/v5/stdlib`.
3. It resolves the module `github.com/jackc/pgx/v5` to the default/selected version. For this course that pin is `v5.7.4`, whose own `go` line is `1.21`.
4. It writes `require` plus the transitive `// indirect` lines.
5. It writes the hashes into `go.sum`.

The reverse — the code no longer imports `golang.org/x/exp`, but the `require` is still there:

```bash
go mod tidy
# removes the dead require and the matching go.sum lines
```

### The CI pattern that catches a forgotten tidy

```yaml
- name: Verify modules are tidy
  run: |
    go mod tidy
    git diff --exit-code go.mod go.sum
```

If the diff is empty → the repo is tidy. If it is not → CI fails and in the log you see exactly which lines are missing or extra.

**Predict:** A developer commits a new import and an updated `go.mod`, but forgets `go.sum`. Does the tidy check fail?

**Answer:** Yes. `go mod tidy` writes the `go.sum` lines, `git diff` sees them, and the exit code is not zero.

### `-mod=readonly` and tidy together

The recommended CI pair:

```bash
go mod tidy
git diff --exit-code go.mod go.sum
go test -mod=readonly ./...
```

The first part proves that the files are aligned with the code. The second part proves that the tests do **not** try to silently append to `go.mod` during the build.

## Example 7 — The whole trace: a local library change through `go.work`

1. You clone `shop` and `redact` as sibling directories.
2. In `redact` you change the signature of `func Redact(s string) string` (a bugfix).
3. In `shop`: `go work init . ../redact`.
4. `go test ./...` in `shop` — it uses the local `redact` with the bugfix.
5. You tag and publish `redact v1.2.1`.
6. In `shop`: `GOWORK=off go get example.com/redact@v1.2.1`.
7. You delete or ignore `go.work`.
8. `go mod tidy` + test + commit only `go.mod`/`go.sum` — with no `replace`, and no personal paths.

#### What happens here

The whole cycle of local development → publish → consumer, without ever writing `replace` into the shared `go.mod`. The workspace was a bridge, not a permanent state.

|----------|------------------|----------------------------------|
| How do you test a local library? | `go.work` | A short-lived `replace` on a feature branch |
| How do you pin a version? | `go get pkg@vX.Y.Z` | `exclude` only for a known bad tag |

| Commit `go.work`? | Only repo-relative paths | Otherwise `.gitignore` |

## Common mistakes — additional

### **Wrong:** `go get pkg@latest` in a script with no human in the loop.
**Effect:** Unexpected minor/major jumps. An API break on a Friday evening.
**Fix:** Pin an explicit version. Leave `@latest` for a manual, reviewed upgrade.

### **Wrong:** You commit `go.work` with `use (C:\\Users\\...\\redact)`.
**Effect:** Colleagues on other operating systems cannot resolve the path.
**Fix:** Relative paths inside the monorepo, or do not commit `go.work`.

### **Wrong:** You trust that `retract` in an upstream `go.mod` automatically blocks your build.
**Effect:** You still build with the retracted version until you explicitly `go get` the correct one.
**Fix:** Follow the `go list -m -u` warnings. Upgrade consciously.

### **Wrong:** `go mod vendor` and then you forget `-mod=vendor` / the `go` line that expects vendor.
**Effect:** The build uses the cache/proxy instead of `vendor/`, or the reverse — confusion about "why my local edit in vendor is not visible".
**Fix:** Document in the README whether the project uses vendor mode. In CI put `-mod=vendor` explicitly if that is the policy.

### **Wrong:** You manually delete `// indirect` lines "for cleanliness".
**Effect:** `go mod tidy` puts them back, or the graph is temporarily inconsistent.
**Fix:** Leave tidy to manage the indirect block.

### **Wrong:** You record a development tool with `go get -tool` on a module that must stay on Go 1.22 or Go 1.23.
**Effect:** The `tool` directive is not understood by those toolchains. The build or the tidy check fails, or the tool is not available where the team expected it.
**Fix:** `go get -tool` and the `tool` directive need Go 1.24+. Go 1.22 and Go 1.23 keep the `tools.go` blank-import pattern.

## Summary

Modules carry version and dependencies through `go.mod` (requirements) and `go.sum` (cryptographic checksums). Minimal version selection chooses the greatest required version, not the newest available. `go.work` solves local multi-module work with no write into `go.mod`. `replace` is the same redirection mechanism but written directly into `go.mod`, so it is dangerous if it escapes onto the main branch. `go mod tidy` in CI is a cheap, fast check that catches inconsistency before it becomes someone else's problem on another machine. `go get -tool` and the `tool` directive need Go 1.24+. Go 1.22 and Go 1.23 keep the `tools.go` blank-import pattern. Start with one module until a concrete reason forces otherwise.
