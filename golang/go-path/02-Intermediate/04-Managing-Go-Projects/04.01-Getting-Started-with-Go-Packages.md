# 04.01 Go project layout: cmd, internal, pkg, and feature packages

> **Go Path - Zero to Gopher** / **02 Intermediate → Managing Go Projects** / Lesson 04.01

## Lesson goals

- Apply the usual layout of **`cmd/`**, **`internal/`**, and optionally **`pkg/`**.
- Choose a **package by feature** instead of an endless layered `models/services/controllers` dump.
- Avoid **`utils` / `common`** as a dumping ground for unrelated functions.
- Understand the exact mechanism by which **`internal`** restricts import (which `import` is allowed, and which the compiler rejects).
- Know the "one package per directory" rule and what happens when you break it.
- Understand the difference between an **exported** and an **unexported** identifier (uppercase/lowercase) and how that boundary overlaps the `internal` directory boundary without being the same thing.
- Know the exact package initialization order (`var`, `init()`) and how wiring in `main` is built on it.
- Connect the layout to the API boundaries of packages and modules covered earlier in the course.

## Prerequisite

- Go package and `import` basics — the packages chapter earlier in the course.
- At least one small service with a `main` function that compiles.
- Basic familiarity with `go build` and `go run`.

## Problem this lesson solves

Picture four real situations, all seen in production repositories:

1. A monolithic `package main` of a thousand and a half lines — all HTTP routing, all database access, all business logic in one file, because it is "easier while the prototype is being written", and then the prototype becomes production.
2. A premature "enterprise" skeleton: folders `handlers/`, `services/`, `repositories/`, `models/`, `dto/`, `mappers/` — created on day one, all empty, all added "just in case", while the real logic still lives in three files because nobody got around to filling in the rest.
3. `utils.ParseEverything`, `common.DoStuff` — a package that started as one helper for parsing dates, and six months later has grown to forty unrelated functions: parsing, sending mail, a database connection, generating a UUID. Everyone imports `utils`, so `utils` imports half the transitive dependencies of the project, and now it is the slowest package to compile in the repo.
4. A constructor for the database connection is called from an `init()` function in the `internal/db` package, which writes a global variable `DB *sql.DB`. A test in a completely different package imports `internal/db` only because it needs one type from it, and suddenly tries to connect to the real production database when the test starts — because `init()` runs automatically, with no explicit call, as soon as the package is imported anywhere in the build graph, and nobody reading the test sees that connection in the test file itself.

The shared symptom: **package boundaries do not reflect change boundaries**, and **hidden behavior on import** (an implicit `init()`, global state) makes the system hard to predict. When you change order logic, you touch five files in three unrelated directories. When another team from another module tries to import your "private" helper because they liked the name, nothing stops them — until you introduce `internal`.

This lesson settles all four: the `cmd` + `internal` layout (plus optional `pkg`), the one-package-per-directory rule, the discipline of "a package by feature" instead of a layered or utils layout, and explicit wiring in `main` instead of hidden `init()` state.

## Mental model

```text
module root/
  go.mod
  cmd/api/main.go          # process entry point (wire-up)
  internal/httpapi/        # HTTP transport layer — only this module imports it
  internal/order/          # feature: domain + store for orders
  internal/catalog/        # feature: catalog
  # pkg/obfuscate/         # optional: code intentionally public to others
```

- **`cmd`** — a thin `main`: load configuration, open the database, mount routes, start the server. No business logic.
- **`internal`** — the module's private library; the compiler (not a linter, not a convention) blocks import from outside. This is a language mechanism, not a recommendation.
- **`pkg`** — controversial in the community; use it only when you really publish an API to other modules from the same repo. Otherwise `internal` covers the need.
- A **feature package** holds things that change together — the order handler, the order store, the order model — in one directory, instead of "all handlers in one folder, all stores in another, forever".
- A package is a **directory**, not a file. Every `.go` file in one directory (except `_test` variants) must declare the same `package` on the first line.
- There are **two independent levels** of privacy in Go: (1) an `internal` directory restricts which **packages** may import a given package; (2) the case of the first character of an identifier restricts which **identifiers** (types, functions, fields) are visible outside the package that declares them, even when the import is allowed. These two mechanisms combine, but they work independently of each other.

## Mechanism

This is the longest part of the lesson because everything else — naming, layout, decisions about `pkg` versus `internal`, wiring in `main` — depends on you understanding *exactly* what the compiler does, not only "a rule to memorize".

### 1. A package as a directory — the discovery mechanism

When you call `go build ./cmd/shop`, the tool does this, step by step:

1. It reads `go.mod` at the root and determines the **module path** (for example, `example.com/shop`).
2. For every `import "example.com/shop/internal/catalog"` in the code, it computes the **filesystem path**: it subtracts the module-path prefix and gets `internal/catalog` relative to the module root.
3. It loads **every** `.go` file in that directory (without descending into subdirectories — a subdirectory is always a separate package).
4. It checks that every file has the **same** `package` clause on the first non-blank, non-comment line. If `store.go` says `package catalog` and `model.go` in the same directory says `package catalogmodel`, the compiler reports an error before it ever reaches types or logic. The error is at the level of "which package is this", not at the level of semantics.
5. Exception: files with the suffix `_test.go` may declare `package catalog_test` (the package with a `_test` suffix). That is an **external test package**, which may import `catalog` like any other consumer, useful for testing only the public API without access to private fields.

When the command is `go build ./...` (every package in the module), the tool additionally **skips** certain directories while walking the tree: every directory whose name starts with a dot (`.git`, `.vscode`) or an underscore (`_internal_scripts`), and the directory named exactly `testdata` (reserved for test fixture files, never treated as a package). This walk rule is not optional and not configurable per project. It is built into the `go` tool itself, so `testdata/` is a safe place for JSON fixtures, golden files, and the like, without fear that the build will try to compile them as Go code.

**Predict:** If in `internal/catalog/` you have `store.go` with `package catalog` and by mistake you create `internal/catalog/legacy/helpers.go` with `package catalog` (the same name, but in a subdirectory), is that the same package as `internal/catalog`?

**Answer:** No. The directory determines the identity of the package, not the name in the `package` clause. `internal/catalog` and `internal/catalog/legacy` are **two different packages** even if both say `package catalog`. The second would be imported as `example.com/shop/internal/catalog/legacy`, and on import Go would give you the alias `catalog` by default, which would collide with the import of the first same-named package in the same file and would require an explicit alias. The package name should match the **last segment of the path** precisely to avoid this.

### 2. Exported versus unexported — the capital-letter mechanism

This is a **second**, completely independent privacy mechanism, at the level of identifiers inside a package, not at the level of the directory path. The rule is mechanical and applies on every reference to an identifier outside the package in which it was declared:

1. The compiler looks at the **first Unicode character** of the identifier name (type, function, method, struct field, constant, variable).
2. If that character is an uppercase letter (Unicode category "uppercase letter"), the identifier is **exported** — visible and usable from any other package that successfully imports the given package.
3. If it is a lowercase letter (or an underscore, or anything other than an uppercase letter), the identifier is **unexported** — visible only inside the same package, in any of its files, but the compiler rejects a reference to it from any other package with an error of the form `undefined: catalog.item` or `item is unexported`.

This rule is independent of the `internal` mechanism: `internal` decides **whether an import of the package is possible at all**, and upper/lower case decides **what of the package contents is visible when the import is possible**. A package can live in `internal/` (unavailable outside the module) and at the same time have exported types (available inside the module) and unexported fields (available only inside the `internal/catalog` package itself, not revealed even to its own module).

```go
package catalog

type Item struct {
	Name  string // exported: available everywhere the catalog import is allowed
	price int64  // unexported: available only inside package catalog
}

func (i Item) Price() int64 { return i.price } // exported method for reading the private field
```

**Predict:** `internal/catalog` has an exported type `Item` with an unexported field `price`. `internal/order` (the same module, import allowed under the `internal` rule) imports `catalog` and tries `item.price = 100`. Does this compile?

**Answer:** No. The import is allowed (both packages are inside the same module, the `internal` rule is satisfied), but `price` is an unexported field — visible exclusively inside `package catalog`. `internal/order` must use an exported method (`item.Price()`) or an exported constructor/setter that `catalog` explicitly provides. This is why these two mechanisms are often combined: `internal` controls **who** may import the package at the module level, and upper/lower case controls **what** that importer may see at the identifier level, even inside the same module.

### 3. The `internal` rule — the exact import-check mechanism

This is NOT a convention that "good programmers" follow. It is a check that `go build`/`go vet` performs on **every** compilation, before code generation.

The algorithm (simplified, but accurate in practice):

1. Take the path of the package being imported, for example `example.com/shop/internal/order`.
2. Find the **last** `internal` segment in that path. Everything **up to and including** the directory that is the parent of `internal` is called the **allowed root prefix** — in this example `example.com/shop`.
3. Take the path of the package that **performs** the import, for example `example.com/shop/cmd/api` or `example.com/other/service`.
4. If the importer's path **does not start with** the allowed root prefix (`example.com/shop`), `go build` rejects compilation with an error of the form: `use of internal package example.com/shop/internal/order not allowed`.

A concrete table with exact paths:

| Who imports | Imports | Allowed? | Why |
|---|---|---|---|
| `example.com/shop/cmd/api` | `example.com/shop/internal/order` | ✅ | The importer starts with `example.com/shop`, the same prefix before `internal` |
| `example.com/shop/internal/httpapi` | `example.com/shop/internal/order` | ✅ | Both are inside `example.com/shop`. `internal` to `internal` is not what matters — the prefix before the last `internal` in the imported path is what matters |
| `example.com/other/service` | `example.com/shop/internal/order` | ❌ | `example.com/other/service` does not start with `example.com/shop` |
| `example.com/shop/v2/cmd/api` (another major, another go.mod) | `example.com/shop/internal/order` | ❌ | A different module, a different prefix — even a "related" project under the same vendor is not exempt |
| `example.com/shop/cmd/api` | `example.com/shop/internal/order/internal/audit` | ❌ | The last `internal` in the path is the one before `audit`. The allowed prefix is `example.com/shop/internal/order`, and `cmd/api` does not start with that longer prefix |

**Predict:** Can `internal/httpapi` import `internal/order` from the same module, even though both have `internal` in the path?

**Answer:** Yes. The rule looks only at the prefix before the **imported** `internal` (`example.com/shop`) and compares it with the full path of the importer. `example.com/shop/internal/httpapi` starts with that prefix, so the import is allowed. The rule does not say "internal cannot import internal". It says "what is *under* `internal` in a given tree is visible only to that tree".

**Predict:** A team decides to move `cmd/api` into a separate repo and a separate module (`example.com/api-binary`), but leaves `internal/order` in the old module and adds a `replace` to point at it locally. Does the import of `internal/order` from the new module work?

**Answer:** It does not work, and `replace` does not bypass it. `replace` changes **where** the code for a given module is fetched from (for example, from local disk instead of the proxy), but it does not change the **path** of the package or the `internal` rule. The new module `example.com/api-binary` still does not start with the prefix `example.com/shop`, so `go build` still rejects the import. This is intentional — `internal` prevents exactly this kind of "move the binary, and try to keep access to private code". (The `replace` mechanism is covered in detail in lesson 04.02.)

### 4. Nested `internal` — granular privacy inside the module

An `internal` segment may appear **more than once** in one path, and each additional level adds an extra, stricter restriction. This is a useful tool when a feature package has a helper subpackage that should not be visible even to the rest of the module, only to the feature itself.

```text
internal/order/
  order.go               # package order — visible to the whole module (the internal rule)
  internal/audit/
    audit.go             # package audit — visible ONLY inside the internal/order tree
```

According to the mechanism in section 3, for `example.com/shop/internal/order/internal/audit`, the last `internal` is the one immediately before `audit`, so the allowed prefix is `example.com/shop/internal/order`. That means `internal/httpapi` (which is outside that prefix) **cannot** import `audit`, even though both belong to the same module and even though `internal/httpapi` freely imports `internal/order` itself.

**Predict:** May `internal/order/model.go` (package `order`, directly in `internal/order/`) import `internal/order/internal/audit`?

**Answer:** Yes. `internal/order` is inside the allowed prefix `example.com/shop/internal/order` (it is literally its root), so the import succeeds. A nested `internal` does not block the feature package from using its own private subpackage. It blocks **every other** part of the module that is not inside that narrower tree. This is a useful pattern when a feature has implementation details (for example, logic for an audit-log format) that you deliberately do not want other feature packages to start importing by accident and building a dependency on them.

### 5. Compilation order — the build graph

`go build` does not compile files in a random order. It builds a **directed acyclic graph (DAG)** of dependencies from `import` clauses, then compiles **leaves first** (packages with no internal dependencies of their own), then packages that depend on them, and so on up to `main`.

For the layout:

```text
cmd/shop/main.go  →  internal/httpapi  →  internal/catalog
```

Compilation order: `internal/catalog` first (no internal dependencies), then `internal/httpapi` (depends on `catalog`), then `cmd/shop` (depends on both). If `internal/catalog` has a type error, `go build` reports the error **there**, before it even tries to compile `main`. The error is not "carried" as a runtime problem. It is caught at the package boundary in the compilation step.

This same graph is also used for the **build cache**: `go build` stores the compilation result of each package (in `$GOCACHE`), keyed by a hash of the file contents and the imported packages. If you change only `internal/catalog`, the next `go build` recompiles `catalog` and everything that (transitively) depends on it (`httpapi`, `main`), but packages that do **not** depend on `catalog` (say, an unrelated `internal/invoice`) are taken from the cache unchanged. The speed of an incremental build depends directly on how shallow and branched the dependency graph is, rather than deep and linear.

**Why this matters for layout:** if `internal/order` imports `internal/httpapi` (so that, for example, it can return an HTTP status code from a domain function), and `internal/httpapi` imports `internal/order` (so that it can call domain logic), the graph is no longer acyclic. That is an **import cycle**, and `go build` rejects compilation with `import cycle not allowed`, with no generated code at all. Hence the rule: the domain (`order`) does not know about the transport (`httpapi`); the transport knows about the domain. The arrow goes in one direction.

Mechanically, cycle detection works as a standard depth-first search (DFS) over the import graph: the tool walks packages, marks each as "in progress" while it resolves its dependencies, and if during that processing it meets a package already marked "in progress" (and not "finished"), that is proof that a path returns to itself — a cycle. This check is why you see the cycle error immediately, before any machine-code generation: the DAG must be confirmed acyclic before anything moves on to type checking and code generation.

### 6. Initialization order — `var`, `init()`, and wiring in `main`

This is the mechanism that directly explains **why** wiring should be written explicitly in `main`, and not left to `init()` functions scattered across packages. Go guarantees an exact, deterministic initialization order, defined by the language specification:

1. For a given package, **package-level `var` declarations** are initialized before any `init()` function in the same package, in an order that respects the dependencies between them (if `var b = f(a)`, `a` must be initialized before `b`, regardless of the order they were written in the file).
2. A package that is **imported** is fully initialized — all of its `var` declarations, then all of its `init()` functions — before the package that imports it begins **its own** initialization. This holds transitively, following the same DAG from section 5.
3. Inside one package, if there are several `.go` files, the `go build` tool passes them to the compiler in lexicographic (alphabetical) order of the file names. `init()` functions are called in that file order, and within the same file, in the order they were written from top to bottom. A package may have several `init()` functions (even in the same file) — all of them are called, in that order, and none is skipped.
4. Only when the **last** package in the chain (usually `main`) has been fully initialized (its `var`s and `init()`s) is the function `main()` called.

This means an `init()` function in `internal/db` that opens a database connection and writes it into a global variable runs **automatically**, as soon as anything in the build graph imports `internal/db` — regardless of whether that import was made for the database connection or only for one type. Explicit wiring in `main` (a call to the constructor `db.New(dsn)` that returns a value, instead of relying on a global variable filled in by `init()`) makes this dependency **visible in the code you read**, instead of hidden in the import order.

```go
// Bad: hidden wiring through init()
package db

var DB *sql.DB

func init() {
	var err error
	DB, err = sql.Open("pgx", os.Getenv("DATABASE_URL"))
	if err != nil {
		panic(err)
	}
}
```

```go
// Good: explicit wiring through a constructor, called from main
package db

func New(dsn string) (*sql.DB, error) {
	return sql.Open("pgx", dsn)
}
```

**Predict:** `cmd/shop/main.go` imports both `internal/catalog` and `internal/httpapi`, where `httpapi` imports `catalog`. All three packages have one `init()` function each that prints its own name. In what order are the messages printed when `go run ./cmd/shop` starts?

**Answer:** `catalog`, then `httpapi`, then `main` — regardless of the order of the `import` lines written in `main.go`. According to the mechanism in step 2, `httpapi` must be fully initialized (including its own `init()`) before `main` begins its initialization, and `httpapi` itself depends on `catalog`, so `catalog` is initialized even earlier. The import order in the source (which package is listed first in the `import` block) **does not affect** the initialization order. Only the dependency graph does.

**Predict:** Is it possible for `internal/catalog` (with no dependencies of its own) to have its `init()` called **after** the `init()` function in `main`?

**Answer:** No, never. The mechanism in steps 2 and 4 guarantees that **all** imported packages are fully initialized before the `main` package begins its initialization, and the `main()` function is called only after that. The order is always: leaves of the graph (packages with no internal dependencies) first, the `main` package last — fully analogous to the compilation order from section 5, because both mechanisms follow the same DAG.

### 7. Feature versus layer — the decision mechanism, step by step

When you add a new piece of functionality, for example "invoices", here is the exact sequence of questions that decides where the code goes:

1. **Which files change together when the invoice rule changes?** If the answer is "the invoice model, the invoice store, and the invoice handler", that is a feature — everything goes in `internal/invoice/`.
2. **Does some of that already exist somewhere else under a generic name?** If you have `handlers/invoice.go`, `services/invoice.go`, `repositories/invoice.go` in three different directories (a layer layout), a change to the invoice rule touches three directories instead of one. That is a sign that the layer layout introduces friction with no benefit.
3. **Does `invoice` need something from `order`?** If you generate an invoice from an order, `internal/invoice` imports `internal/order` — the arrow goes from the newer/dependent functionality toward the older/foundational one. You must check that `order` does **not** import `invoice` back (otherwise a cycle).
4. **Does `invoice` need HTTP types?** Not directly. The HTTP handler for invoices goes in `internal/httpapi` (or in `internal/invoice` itself if the transport is tightly bound to the feature — both are acceptable, but not both **at the same time** for the same resource, so you do not duplicate routes).
5. **With the addition of `invoice`, can the dependency graph of the feature packages still be drawn as an acyclic diagram on one side of a sheet of paper?** If `catalog` depends on `order`, `order` on `invoice`, and someone adds that `invoice` depends back on `catalog` for "just one field", that is a signal that the feature boundary is poorly placed. There is probably a shared concept that deserves its own, smaller package, instead of a circular dependency among three features.

**Predict:** Three feature packages (`order`, `catalog`, `invoice`) each have their own function `formatMoney(cents int64) string` copied three times. Does that violate the "feature over layer" rule?

**Answer:** It does not violate it. Feature packages can still share a **stable, named** helper. Copying it three times is a problem, but the solution is not "back to layers". It is extracting **one** new package with a clear name and one responsibility, for example `internal/money`, which all three feature packages import. A layer approach would put `formatMoney` in `utils` next to fifty other unrelated functions. A feature-first approach puts it in a package whose name *is* its specification.

### 8. `pkg` — a decision mechanism, not a convention

`pkg/` has no special treatment in the compiler. It is a plain directory like any other, importable by anyone who knows the path. The difference between `internal/foo` and `pkg/foo` is only that the compiler blocks import of the first from outside the module, and does not block the second at all.

The decision is a simple check: **Is there a consumer outside this module today?** If there is not, `internal` is the strictly safer default. You can later rename `internal/foo` to `pkg/foo` (a small import-path change, one find-and-replace) when a real external consumer appears. The reverse path — from `pkg` to `internal` when you discover that nobody outside uses it — is the same cost, but almost nobody does it, so `pkg` tends to stay "public" and unused forever, widening the API surface for no reason.

### 9. Anti-`utils` — the mechanism that widens the transitive dependency graph

"`utils` is just a couple of helper functions" sounds harmless until you follow the **transitive** effect on the dependency graph, exactly the way `go build` sees it.

Imagine a `utils` package with four unrelated functions: `ParseJSON` (imports `encoding/json`), `ConnectDB` (imports `database/sql` and a database driver), `SendMail` (imports an SMTP client and a TLS library), `Ptr[T]` (imports nothing extra). The mechanism is as follows:

1. The package `internal/order` imports `utils` exclusively for `utils.Ptr[T]` (a helper that returns a pointer to a value).
2. According to the rule in section 5, `go build` includes the **whole** `utils` package in the dependency graph of the `order` package, because the unit of import is the package, not an individual function. There is no "partial import" of one function without the rest of the package.
3. The compiler therefore has to resolve and compile (or take from the cache) every transitive dependency of the **entire** `utils` package: `database/sql`, the database driver, the SMTP client, the TLS library — even though `order` never calls `ConnectDB` or `SendMail`.
4. Effect on the build cache from section 5: every change in `SendMail` (say, a change of the SMTP port) invalidates the cached compilation result for the **whole** `utils` package, which transitively invalidates every importer of `utils`, including `order`, even though the logic `order` uses (`Ptr[T]`) did not change at all.
5. In tests: if `order_test.go` imports `utils` (transitively, through `order`), and `ConnectDB` in its `init()` tries to connect to a real database (the scenario from the introduction of this lesson), the `order` test package becomes dependent on database availability — even a test that tests only `Ptr[T]` logic, indirectly.

Numerically, with 40 unrelated functions in `utils` and ten feature packages that import it for even one function, the dependency graph has ten edges toward `utils`, and each of those edges transitively pulls **all** the dependencies of all 40 functions. The mistake is not visible in the number of lines of code, but in the number of packages that `go build`/`go test` must consider on every change.

**Predict:** Splitting `utils` (40 functions) into `jsonutil`, `mailer`, `dbconn`, `ptr` (four named packages) — does this change the **total** number of lines of code in the repo?

**Answer:** The number of lines of code and the number of functions do not change. The **dependency graph** changes. A package that before the split imported `utils` for `Ptr[T]` now imports only `ptr`, whose transitive graph is empty (no additional imports). The number of edges in the dependency graph toward "actually used" functionality stays the same or shrinks, but the number of **unnecessary** transitive edges (an importer of `Ptr[T]` that transitively pulls SMTP and the database driver) drops to zero. The build cache from section 5 becomes more precise: a change in `mailer` no longer invalidates the cached compilation of packages that use only `ptr`.

### 10. Blank import — the registration mechanism without direct use

`import _ "github.com/jackc/pgx/v5/stdlib"` (already seen in Example 1) is a special, intentionally supported case in the compiler: an underscore as the alias tells the tool "import this package for its initialization effects (`var` and `init()` from section 6), but do not give me a name through which I would reference its exported identifiers, and do not report an 'imported and not used' error".

The mechanism has three consequences:

1. The package is still **fully** compiled and included in the build graph (section 5). A blank import does not skip compilation. It only skips the requirement that the code reference something from it by name.
2. The package is still **fully initialized** before the importer, according to the mechanism in section 6. That is why database-driver registration works: `pgx/v5/stdlib` in its `init()` calls `sql.Register("pgx", ...)`, and that registration is finished before `main` calls `sql.Open("pgx", ...)`.
3. The compiler's normal rule "every imported package must be used, otherwise it is an error" **does not apply** to a blank import. That is the only legitimate way to import a package exclusively for its initialization effects, without referencing a single exported identifier.

This is also why a blank import is considered an acceptable exception to the rule in section 6 ("wiring belongs in `main`, not in `init()`"): driver registration is infrastructure, not business logic, it carries no environment-specific configuration, and its behavior is identical no matter how many times the package is imported.

**Predict:** You remove the `_ "github.com/jackc/pgx/v5/stdlib"` line from `main.go`, but you leave `sql.Open("pgx", dsn)` in the code. Does `go build` report an error?

**Answer:** `go build` itself succeeds. `database/sql` and `sql.Open` are valid Go code regardless of which drivers are registered. The error appears only at **runtime**, when `sql.Open("pgx", dsn)` looks up the driver registered with `sql.Register` under the name `"pgx"`, which no longer exists (because the `init()` that registers it was never called without the import), with a message of the form `sql: unknown driver "pgx" (forgotten import?)`. This is an example where the compiler cannot catch the error, because the link between the string `"pgx"` and the registered driver is established exclusively through an `init()` effect, outside the type system.

### 11. The `vendor/` directory — the same visibility mechanism, a different source of bytes

`go mod vendor` copies the contents of all dependencies (including transitive ones) into a local `vendor/` directory at the module root, and generates `vendor/modules.txt` which records the exact versions. When `vendor/` is present and the tool is run with `-mod=vendor` (or automatically, if the Go version in `go.mod` is new enough and `vendor/modules.txt` is consistent with `go.mod`), `go build` reads dependencies **from there**, not from the `$GOPATH/pkg/mod` cache and not from the proxy.

What matters for this lesson: the `internal` rule from section 3 and the visibility from section 2 **do not change** when `vendor/` is in play. Those are rules based on the **path** of the package (`example.com/shop/internal/order`), not on the **physical location** on disk from which the bytes are currently being read. The package `example.com/shop/internal/order`, whether it comes from `vendor/example.com/shop/internal/order` or from the module cache, is still unavailable outside the `example.com/shop` prefix.

**Predict:** The repo uses `vendor/` and contains `vendor/example.com/redact` (a dependency). Can another module, from outside, import `example.com/redact` **from your** `vendor/` directory to avoid downloading it from the proxy?

**Answer:** Not in any meaningful way. `vendor/` is specific to **your** build. It is not exposed as a general source of packages to other modules. Another module that wants `example.com/redact` still fetches it independently (from the proxy or from its own `vendor/`), with its own `go.sum` checksum checks. `vendor/` solves reproducibility and an offline build of **your** module. It does not become a shared package source for the whole ecosystem.

### 12. An alias on import — the mechanism for resolving name collisions

The identifier by which code references an imported package is **not** derived from the last segment of the path. It is derived from the name declared in the `package` clause of that package. In practice the two names match because that is the convention (the rule in the Rules and syntax section), but the compiler does not check the match. It uses what is written in the `package` line of the imported package.

1. When a file imports two packages whose `package` names match (for example, `internal/catalog` with `package catalog` and `internal/catalog/legacy` with the same `package catalog`), the compiler does not choose automatically. It reports the error `catalog redeclared in this block` as soon as both are imported without a distinction.
2. The resolution is an explicit alias in front of the path: `legacycatalog "example.com/shop/internal/catalog/legacy"`. From that moment, `legacycatalog.X` references the imported package, and a bare `catalog.X` still references the first one.
3. The special alias `_` is the blank import (section 10). The special alias `.` is a **dot import** — every exported identifier of the imported package becomes available **without** a qualifier in the current file (`Println(...)` instead of `fmt.Println(...)`, if `fmt` were dot-imported). Dot import is rarely used outside generated test-helper packages because it makes it unclear where an identifier comes from when you read the code.

```go
import (
	"example.com/shop/internal/catalog"
	legacycatalog "example.com/shop/internal/catalog/legacy"
)

func Migrate(old legacycatalog.Item) catalog.Item {
	return catalog.Item{Name: old.Name}
}
```

**Predict:** A test file does `import . "example.com/shop/internal/testhelper"`, where `testhelper` exports a function `NewFixture()`. The same test file also imports `"example.com/shop/internal/catalog"`, which **also** exports a function named `NewFixture` (an accidental name match), but qualified through `catalog.NewFixture`. Do these two collide?

**Answer:** They do not collide by themselves. `catalog.NewFixture` is a qualified reference (it comes through the normal, named import of `catalog`), while the dot-imported `testhelper.NewFixture` becomes available as a bare `NewFixture()` with no prefix. A collision would arise only if `catalog` were also dot-imported, or if a function or variable named `NewFixture` were declared locally in the same file. That is exactly why caution with dot import is warranted: it is hard to predict future name collisions in advance, because when you read the code you do not see explicitly which bare identifier comes from where.

### 13. The package documentation comment — the aggregation mechanism for `go doc`

The `go doc`/godoc tool collects documentation by a strict, mechanical rule: a comment that sits **immediately** above the `package` clause, with no blank line between them, is treated as the documentation of the **whole package**. The same rule applies to every exported identifier — a comment immediately above the declaration (with no blank line) becomes its documentation. A blank line breaks the link and the comment is treated as an ordinary note in the code, not as documentation.

If **several** files in the same package have a comment above their own `package` clause, `go doc` **joins** all of those comments (in file order, the same lexicographic sort from section 6), instead of taking only one. That is why the convention is that a package has **exactly one** file (often named `doc.go`, which sometimes contains nothing else besides the `package` clause) with a descriptive comment, and every other file has a `package` line with no comment above it.

```go
// Package catalog manages catalog items: storage, search, and
// price calculation. All operations are safe for concurrent access.
package catalog
```

**Predict:** `store.go` has a short working comment `// TODO: add caching` immediately above `package catalog`, and `item.go` in the same directory has a full descriptive comment above its own `package catalog`. What does `go doc catalog` show as the package description?

**Answer:** It shows **both** comments joined (the aggregation mechanism does not pick the "better" or the "longer" one — it joins everything it finds, in file order), so `// TODO: add caching` would end up mixed into what should be a clean package description for documentation users. This is a concrete, practical reason for the convention "one `doc.go` with the description, other files with no comment above `package`" — it prevents an accidental working comment from becoming part of the package's public documentation.

## Rules and syntax

- One `main` per binary entry, in `cmd/<binary-name>/main.go`.
- Do not put business logic in `main` beyond wiring (parsing configuration, opening resources, calling constructors, starting the server).
- The package name is a short noun in the singular, lowercase, with no underscores (`order`, not `order_service_package`, not `Orders`).
- The directory name and the package name should match (`internal/order` → `package order`), except for rare exceptions with versioned paths (`v2`).
- An `internal` segment blocks import outside the tree whose root is the parent of `internal`. This is a compiler check, not a linter rule. A nested `internal` (`internal/order/internal/audit`) further narrows visibility to a tighter tree.
- An identifier starts with an uppercase letter to be exported (visible outside the package). This is independent of the `internal` rule and applies even inside the same module.
- Wiring (construction of dependencies: database, clients, configuration) belongs in explicit constructors called from `main`, not in implicit `init()` functions that write global state.
- `utils`/`common`/`helpers` are allowed only with **one** clear, named responsibility (`httpmount`, `moneyformat`). If you cannot name the responsibility in two words, do not make the package yet.
- Every `.go` file (except `_test` variants) in one directory must have the same `package` clause.
- Directories named `testdata`, and those that start with a dot or an underscore, are treated as non-packages by `go build ./...` and similar tree walks.
- An import alias is used to resolve name collisions (`legacycatalog "..."`). Reserve dot import (`. "..."`) for rare, conscious cases, never as a default style.
- A descriptive package comment is written in one file (conventionally `doc.go`), immediately above the `package` clause, with no blank line between them.

## Examples

### Example 1 — A minimal layout

```text
shop/
  go.mod
  cmd/shop/main.go
  internal/catalog/item.go
  internal/catalog/store.go
  internal/httpapi/server.go
```

`cmd/shop/main.go`:

```go
package main

import (
	"database/sql"
	"log"
	"net/http"
	"os"

	_ "github.com/jackc/pgx/v5/stdlib"

	"example.com/shop/internal/catalog"
	"example.com/shop/internal/httpapi"
)

func main() {
	db, err := sql.Open("pgx", os.Getenv("DATABASE_URL"))
	if err != nil {
		log.Fatal(err)
	}
	defer db.Close()

	store := catalog.NewPG(db)
	srv := httpapi.New(store)
	log.Fatal(http.ListenAndServe(":8080", srv))
}
```

#### What happens here

`main` only wires things together: open the database, make the store, make the server, start. The domain is in `internal/catalog`, the HTTP transport in `internal/httpapi`. According to the mechanism in the Mechanism section, the build graph goes `catalog → httpapi → main`, and nobody outside this module can import `catalog` or `httpapi` because they are under `internal`. This is also an example of the explicit wiring from section 6: `db`, `store`, and `srv` are local variables passed to constructors. There is no global state and no `init()` magic.

### Example 2 — The order feature package

```go
// internal/order/model.go
package order

type Order struct {
	ID     string
	Total  int64
	Status string
}
```

```go
// internal/order/store.go
package order

import (
	"context"
	"database/sql"
	"fmt"
)

type Store struct{ db *sql.DB }

func NewStore(db *sql.DB) *Store { return &Store{db: db} }

func (s *Store) Get(ctx context.Context, id string) (Order, error) {
	var o Order
	err := s.db.QueryRowContext(ctx,
		`SELECT id, total_minor, status FROM orders WHERE id = $1`, id,
	).Scan(&o.ID, &o.Total, &o.Status)
	if err != nil {
		return Order{}, fmt.Errorf("order get: %w", err)
	}
	return o, nil
}
```

#### What happens here

`db *sql.DB` is a pointer to the shared connection pool. `Store` holds it; it does not copy it. The model and the store live in the same directory because they change together: you add a field to `Order`, and you immediately update `SELECT`/`Scan` in the same file you see on the screen. Every identifier (`Order`, `Store`, `NewStore`, `Get`) starts with an uppercase letter because `internal/httpapi` must be able to import and use them. According to the mechanism in section 2, `internal` allows the import at the package level, but each individual identifier still has to be explicitly exported to be usable. When the feature grows (you add validation, discount calculation), you extract subpackages only when a real need appears, not in advance.

### Example 3 — An anti-example of utils

```go
package utils

func ParseJSON(...) {}
func ConnectDB(...) {}
func SendMail(...) {}
func Ptr[T any](v T) *T { return &v }
```

Better:

```text
internal/jsonutil/
internal/mailer/
internal/ptr/   # if you truly must — or local helper functions
```

#### What happens here

`utils` pulls unrelated dependencies (a JSON parser, a database driver, an SMTP client) into one package. Anyone who imports `utils` for `Ptr[T]` (a helper that returns a pointer to a value — useful for optional parameters) transitively pulls both the database driver and the SMTP client into their build graph, even if they do not use them directly at the type level. According to the mechanism in section 9, this is not only an aesthetic problem. It directly slows the build cache and widens test dependencies (including, in the worst case, a hidden `init()` that tries to connect to a database). Names with a clear responsibility keep the import graph thin.

### Example 4 — When `pkg` makes sense

```text
repo/
  pkg/redact/     # used by two binary cmds and an external module in the monorepo
  internal/api/   # only this service
```

#### What happens here

`pkg/redact` is intentionally public — there is a confirmed consumer outside this module (an external module in the same monorepo). `internal/api` stays private because nobody outside imports it. According to the mechanism in section 8, this is the only real difference: the existence of a real external consumer today, not an assumption about the future.

### Example 5 — Bad layering that creates a cycle

```text
internal/handlers → internal/services → internal/models
internal/models → internal/handlers   # cycle (an "HTTP" DTO in the model)
```

The fix: the DTO goes in `httpapi` or in the feature package; domain models stay without imports of HTTP types.

#### What happens here

According to the compilation-order mechanism (section 5), `go build` builds a DAG from import clauses. When `models` imports `handlers` in order to return an HTTP-specific DTO, and `handlers` already imports `models` for the domain type, the graph is no longer acyclic and the compiler reports `import cycle not allowed` — before any test, before any runtime behavior. The cycle is a symptom of a wrong boundary (the DTO does not belong in the domain), not a signal that you need "one more layer of abstraction".

### Example 6 — Explicit wiring instead of `init()` magic

```go
// internal/mailer/mailer.go
package mailer

type Client struct {
	host string
	from string
}

func New(host, from string) *Client {
	return &Client{host: host, from: from}
}

func (c *Client) Send(to, subject, body string) error {
	// ... SMTP logic using c.host, c.from ...
	return nil
}
```

```go
// cmd/shop/main.go (part)
func main() {
	db, err := sql.Open("pgx", os.Getenv("DATABASE_URL"))
	if err != nil {
		log.Fatal(err)
	}
	defer db.Close()

	mail := mailer.New(os.Getenv("SMTP_HOST"), "noreply@shop.example")
	store := catalog.NewPG(db)
	srv := httpapi.New(store, mail)

	log.Fatal(http.ListenAndServe(":8080", srv))
}
```

#### What happens here

No package has an `init()` function or a global variable that is filled on import. According to the mechanism in section 6, the Go package initialization order still exists (`mailer`, `catalog`, and `httpapi` are still initialized before `main`), but because none of them has its own `init()` with effects, that order is harmless. All real construction (opening the connection, reading `SMTP_HOST`) happens explicitly, in the order a reader of `main.go` sees from top to bottom, testable without starting the process (each constructor can be called directly from a test with fake/test parameters).

### Example 7 — Nested `internal` for an implementation detail

```text
internal/order/
  order.go
  store.go
  internal/audit/
    audit.go        # package audit
```

```go
// internal/order/internal/audit/audit.go
package audit

type Entry struct {
	OrderID string
	Action  string
}

func Log(e Entry) { /* write to the audit log */ }
```

```go
// internal/order/store.go (part)
package order

import "example.com/shop/internal/order/internal/audit"

func (s *Store) MarkShipped(ctx context.Context, id string) error {
	// ... UPDATE query ...
	audit.Log(audit.Entry{OrderID: id, Action: "shipped"})
	return nil
}
```

#### What happens here

`internal/order/internal/audit` is visible **only** inside the `internal/order` tree, according to the mechanism in section 4. `internal/httpapi` or `internal/catalog` cannot import it, even though all of them are inside the same module. This prevents audit logic, meant as an implementation detail of the `order` feature, from becoming an accidental shared dependency of other feature packages that might use it in unplanned ways.

### Example 8 — An external test package (`_test` suffix) according to the discovery mechanism

```go
// internal/catalog/store.go
package catalog

type Store struct{ items map[string]Item }

func NewStore() *Store { return &Store{items: map[string]Item{}} }

func (s *Store) Add(i Item) { s.items[i.Name] = i }

func (s *Store) Get(name string) (Item, bool) {
	i, ok := s.items[name]
	return i, ok
}
```

```go
// internal/catalog/store_test.go — same directory, a DIFFERENT package clause
package catalog_test

import (
	"testing"

	"example.com/shop/internal/catalog"
)

func TestStoreAddGet(t *testing.T) {
	s := catalog.NewStore()
	s.Add(catalog.Item{Name: "widget"})
	if _, ok := s.Get("widget"); !ok {
		t.Fatal("expected widget to be present")
	}
}
```

#### What happens here

According to the exception described in step 5 of section 1, `store_test.go` may declare `package catalog_test` even though it lives in the same directory as `store.go` (which declares `package catalog`). The compiler recognizes the `_test` suffix as a special, allowed case. The test imports `catalog` exactly like any external consumer, using only exported identifiers (`NewStore`, `Item`, `Add`, `Get`). According to the mechanism in section 2, it has no access to unexported fields such as `items`. A test like this proves that the package's public API works without relying on private details, unlike an internal `package catalog` test that would have access to the `items` map directly.

### Example 9 — `doc.go` and the descriptive package comment

```text
internal/catalog/
  doc.go     # only the package clause + a descriptive comment
  item.go
  store.go
```

```go
// internal/catalog/doc.go

// Package catalog manages catalog items: storage, search, and
// price calculation. All operations are safe for concurrent access
// when a shared Store instance is used.
package catalog
```

```go
// internal/catalog/item.go
package catalog // no comment above — the documentation is already in doc.go

type Item struct {
	Name  string
	price int64
}
```

#### What happens here

According to the mechanism in section 13, `go doc example.com/shop/internal/catalog` shows exactly one, clean package description — the one from `doc.go` — because no other file in the directory has a comment immediately above its own `package` clause. If `item.go` accidentally gained a working comment above `package catalog`, `go doc` would join it with the description from `doc.go`, exactly as in the Predict/Answer example. The `doc.go` convention exists specifically to prevent that.

### Example 10 — An alias for resolving a package-name collision

```go
// internal/migrate/run.go
package migrate

import (
	"example.com/shop/internal/catalog"
	oldcatalog "example.com/shop/vendor-legacy/catalog" // same package name, different source
)

func Run(old oldcatalog.Item) catalog.Item {
	return catalog.Item{Name: old.Name}
}
```

#### What happens here

Both packages declare `package catalog` (according to the mechanism in section 12, the name of an imported package comes from the `package` clause, not from the path), so without an alias `go build` reports `catalog redeclared in this block` as soon as both are imported in the same file. The explicit alias `oldcatalog` resolves the collision with no change at all in the imported packages themselves. The alias is local to the file in which it is used. It does not change the identity of the package anywhere else in the module.

## Decision analysis

| Decision | Reason |
|----------|--------|
| Thin `cmd` | Testable libraries; `main` is not tested directly |
| `internal` as the default | The compiler as a mechanical privacy police, not linter advice |
| Feature-first | Local changes, fewer cycles, easier naming |
| No `utils` dump | Clear packages, a thin import graph, a faster build |
| `pkg` only with a confirmed consumer | The API surface does not widen for no reason |
| Wiring in `main`, not in `init()` | Dependencies visible in the code, testable without hidden global state |
| Nested `internal` for implementation details of a feature | Prevents an unplanned shared dependency on code that was not meant as an API even inside the module |
| Blank import only for driver/plugin registration | The initialization effect is infrastructural, not environment-specific business logic |
| An external `_test` package for testing the public API | Proves that the package's exported contract works without access to private fields |
| `doc.go` with a descriptive package comment | Prevents working comments from other files from polluting the aggregated documentation |
| An explicit alias instead of relying on the default name | Prevents a name collision when two packages (especially vendor/legacy) share the same `package` name |

## Trade-offs

- Too many tiny feature packages (one per type) introduces import ceremony. A feature package that is too large brings the monolith back in another form.
- `pkg/` in every tutorial on the internet is not mandatory in your service. The monorepo versus one-repo-per-service context changes the decision.
- Strict layering in a small team (3–5 people) slows work with no measurable benefit. Layering makes sense when a layer becomes a genuinely stable shared platform.
- A monorepo with several `cmd` binaries shares the same `internal`. The mechanism in section 3 allows every `cmd/*` in the same module to access the same `internal` tree, so you have to plan boundaries by naming feature packages, not by physically splitting modules.
- Explicit wiring in `main` becomes verbose with dozens of dependencies. Then it is acceptable to extract one `wire.go`/`container.go` function that still constructs everything explicitly, instead of going back to `init()` magic or introducing a dependency-injection framework that hides the graph behind reflection.
- Nested `internal` adds path depth (`internal/order/internal/audit`) that can look like pretense. Use it only when there is a real risk that another part of the module will accidentally start depending on an implementation detail, not as a default habit for every subpackage.
- A blank import for registration (drivers, plugins) is an accepted exception to the "wiring in `main`" rule, but the boundary is thin. As soon as `init()` starts reading environment variables or changing behavior based on configuration, it is no longer pure registration and should move into an explicit constructor.
- An external `_test` package proves the public contract, but it makes it impossible to check private invariants (for example, whether an internal map is in a consistent state after an operation). For that you still need an internal `package catalog` test in a separate file. Both styles side by side, when needed.

## Common mistakes

### **Wrong:** All business logic (validation, calculations, queries) is written directly in `func main()`.
**Effect:** `main` grows to thousands of lines. It is impossible to test the logic without starting the whole process and a real database. Another binary entry (a worker, a CLI tool) has to copy the entire block of code.
**Fix:** Extract the logic into an `internal/<feature>` package with a constructor that takes dependencies (`db *sql.DB`, `logger`). `main` only calls the constructor and the methods.

### **Wrong:** A new package is named `utils`, `common`, or `helpers` with no further specification.
**Effect:** Within a few months the package has 30–40 unrelated functions. Every importer transitively pulls every dependency of those functions. Build and test time grow with no relation to actual use.
**Fix:** Name the package by **one** responsibility (`jsonutil`, `mailer`, `moneyformat`). If you cannot think of a name in two words, the function does not yet deserve its own package — leave it local next to the call.

### **Wrong:** Expecting that another module can import an `internal` package if you only add a `replace` directive toward it.
**Effect:** `go build` rejects compilation with `use of internal package ... not allowed`, regardless of `replace`. The developer wastes time looking for a "bug" in the tool.
**Fix:** If an external consumer really needs access, move the package to `pkg/` (a conscious decision about a public API) or extract only the needed public `interface` into a new, intentionally public package.

### **Wrong:** Folders `handlers/`, `services/`, `repositories/`, `models/` are created in the first week of the project, all empty, "so we have structure".
**Effect:** The real logic still goes into two or three files while the other folders stay empty for months. When they are finally filled, the boundaries are chosen at random so that "something is put" in each folder.
**Fix:** Create a folder **when** the first feature actually needs its own space, named after the feature (`internal/order`), not after a layer.

### **Wrong:** `internal/models` imports `internal/handlers` in order to return an HTTP-specific DTO type directly from a domain function.
**Effect:** An import cycle — `internal/handlers` already imports `internal/models` for the domain type. `go build` reports `import cycle not allowed` and compiles nothing until they are separated.
**Fix:** The DTO (the shape meant for the HTTP response) lives in `httpapi` or in the feature package. The domain `models`/feature package knows nothing about HTTP. The import arrow goes in one direction.

### **Wrong:** Two files in the same directory declare different `package` clauses (for example, one `package catalog`, the other `package catalogv2` after a careless copy-paste).
**Effect:** `go build` rejects the whole directory with an error about a package-name mismatch, before any type checking. Compilation does not proceed for any other package that depends on this one either.
**Fix:** Check the first line of every `.go` file in the directory. The package name must be identical (except for the `_test` suffix for external test packages).

### **Wrong:** Dependency wiring (a database connection, a mail client, configuration) is done in `init()` functions scattered across several packages, instead of explicitly in `main`.
**Effect:** The order and the cause of initialization become invisible in the code you read. They depend on the import DAG (section 6), not on anything written in `main.go`. A test that imports a package only for one type unknowingly runs an `init()` that tries to connect to a real database or an external service.
**Fix:** Extract a constructor (`func New(...) *T`) that returns a configured value with no effects on the import itself. Call the constructor explicitly from `main`, so the whole dependency chain is readable in one place.

### **Wrong:** An exported function returns an **unexported** type from another package (for example, `func New() unexportedType`), so the caller cannot even name the type of the returned value in its own code.
**Effect:** Code outside the package can call `New()` and hold the result in a variable with `:=`, but it cannot declare a field of that kind in its own struct, and it cannot write the type in the signature of its own function. The API is usable only in a limited, often surprising scope.
**Fix:** Either export the type (uppercase) if it needs to be named outside the package, or return an exported `interface` that describes the behavior instead of the concrete unexported type — a conscious decision about what is actually part of the package's public API.

### **Wrong:** A blank import (`import _ "..."`) is used to "silence" the compiler about a package that is temporarily unused, with the intention of bringing the import back later when it is needed.
**Effect:** The package still enters the build graph and **runs its `init()`** (according to the mechanism in section 10), even though the intention was not to register effects. Side effects (for example, opening a log file, registering metrics) happen unplanned, only because the import stayed in the file.
**Fix:** Remove the unused import completely. Reserve a blank import exclusively for cases where the `init()` effect is intentionally needed (registration of a driver, a format, a codec), not as a way to bypass a compiler error.

### **Wrong:** The team assumes that an `internal` package cannot have its own tests because "nobody outside is allowed to see it".
**Effect:** Feature packages stay untested, or they are tested only indirectly through an HTTP endpoint, which makes it harder to locate the cause when a test fails. The error is seen at the level of the whole HTTP response, not at the level of a concrete function.
**Fix:** The `internal` rule restricts import **outside** the module, not testing **inside** it. Write both a `_test.go` (internal, access to private fields) and, where it makes sense, an external `_test` package (the public contract) in the same `internal/<feature>` directory.

## Idiomatic Go

- The community overwhelmingly uses `cmd/` + `internal/` for services with one or more binary entries. This is not an official stdlib convention, but it is widespread enough to be a *de facto* standard.
- The stdlib itself does not have `internal` in the modern "module" sense because it was written before modules, but the `internal` rule in the language today applies identically to any module, including the stdlib repo.
- Package names are short, with no underscores. The path carries the context (`internal/order`, not `internal/order_management_feature`).
- `go doc ./...` and a README at the module root should be enough for a new team member to find the entry point in a couple of minutes.
- Constructors are named `New`/`NewX` and return a value or pointer ready for use, with no effects on global state. That makes it possible to construct the same type more than once (production, test, another binary entry) with different parameters.
- In idiomatic code `init()` is used sparingly. Registering a database driver (`_ "github.com/jackc/pgx/v5/stdlib"`) is a common, accepted use. Constructing business state in `init()` is not.
- Test files by default use the same `package` as the code they test (access to private fields for detailed unit tests). An external `_test` package is added alongside, not instead, when the public contract needs to be checked.
- `go vet` and `staticcheck` catch some errors related to unused imports and suspicious `init()` patterns before code review. They do not replace the discipline of naming and arranging packages, but they are a cheap first line of defense.

## Practical scenario

A startup starts with a `package main` of 2000 lines — everything in one file, because it is "just an MVP". When a second binary entry is needed (a worker that processes a message queue), the team copies the entire block of code for the database connection and the order logic into a new `main`. Within a month, a bug fix in the order logic lands in only one of the two `main` files — a production incident.

The fix: `cmd/api/main.go` and `cmd/worker/main.go`, both thin; `internal/order` with the domain logic and the store, imported from both. According to the mechanism in section 3, both `cmd/*` binary entries may import `internal/order` because they are in the same module. There is no need for `pkg`. The bug fix happens once, in one package, and is tested once.

When another team (another module, another repo) tries to import `internal/order` so they "do not write their own", `go build` on their side rejects it with `use of internal package ... not allowed`. This is intentional — a signal that there should be a conversation about a stable, public API (a new library or `pkg`), not a silent transitive import of a private implementation that can change without warning.

A `utils` of 40 functions is split in the same sprint into `jsonutil`, `mailer`, `moneyformat` — three named packages, each with a clear responsibility and its own, noticeably smaller set of dependencies.

A few sprints later, a new developer on the team adds an `init()` in `internal/order` that, "to make testing easier", immediately opens a connection to a test database and writes it into a package variable. When `internal/order` is imported in `cmd/worker` (which uses a different database, the production one), the `init()` from `order` tries to connect to the wrong database before `main` even reaches its own code. The team introduces a rule: no feature package has an `init()` with effects. Everything that looks like configuration or a connection goes through an explicit constructor called from `main`, exactly according to the mechanism in section 6.

## Check questions

1. **What is `internal` for, by exactly which mechanism?**
   `go build` compares the importer's path prefix with the path prefix up to (and including) the parent of `internal` in the imported path. If the importer does not start with that prefix, compilation is rejected — regardless of `replace` or other tricks.

2. **What goes in `cmd`, and what does not?**
   Entry points of binaries — a thin `main` that reads configuration, opens resources, mounts dependencies, and starts the process. Business logic, validation, and queries do not belong in `main`.

3. **Why do feature packages reduce cycles compared with a layer layout?**
   A feature package groups everything that changes together in one directory with a clear import direction toward other feature packages. A layer layout splits related code into independent layers that easily start depending on each other in both directions.

4. **What is the concrete problem with `utils`?**
   It becomes a dumping ground of unrelated responsibilities. Every importer transitively pulls every dependency of every function in the package, not only the one it uses, which widens the build graph and slows compilation and testing.

5. **When do you use `pkg` instead of `internal`?**
   When there is a **confirmed, existing** consumer outside your module (another module in the same monorepo, or an external library you consciously publish). Without a confirmed consumer, `internal` is the safer default because it is easy to widen later, while shrinking a public API afterward is something almost nobody does.

6. **What happens if two files in the same directory declare a different `package` clause?**
   `go build` rejects compilation of the whole directory with an error about a package-name mismatch, before any type or logic check. The exception is a `_test.go` file that legally uses the `_test` suffix for an external test package.

7. **How do the `internal` rule and the upper/lower-case rule differ, and why can both be active at the same time?**
   `internal` decides whether an import of the package is allowed at all, based on the directory path and who is importing. Upper/lower case decides which identifiers inside that (already allowed) package are visible. A package can be available for import (not blocked by the `internal` rule) and still hide individual fields and functions through a lowercase letter.

8. **Why does wiring belong in `main`, and not in `init()` functions in feature packages?**
   According to the initialization order, `init()` runs automatically as soon as the package is imported anywhere in the build graph, regardless of the importer's intention. An explicit constructor called from `main` makes the dependencies visible in code that is read from top to bottom, and testable without hidden effects on the import itself.

9. **What exactly does a blank import (`import _ "package"`) do, and when is it justified?**
   It imports a package for its initialization effects (`var` and `init()`) without giving a name through which its exported identifiers would be referenced, and without an "imported and not used" error. It is justified for registration (database drivers, codecs, plugins) — infrastructural effects with no environment-specific business logic.

10. **Does the `internal` rule prevent writing tests for a feature package?**
    No. `internal` restricts import outside the module, not testing inside it. The same directory may contain both an internal `_test.go` (access to private fields) and an external `_test` package (the public contract only), both part of the standard `go test ./...` flow.

11. **Where does the name by which you reference an imported package come from, and what happens when two imported packages match on that name?**
    The name comes from the `package` clause of the imported package, not from the last segment of the path (although by convention they usually match). When two imports match on the name, the compiler reports a redeclaration error until at least one of them gets an explicit alias.

12. **How does `go doc` choose the package description when several files have a comment above the `package` clause?**
    It does not choose. It joins all such comments, in file order, into one aggregated description. That is why the convention keeps the descriptive comment in one file (`doc.go`), and the other files leave the `package` line with no comment above it.

## Summary

Project layout carries boundaries at the level the compiler actually enforces: `cmd` for the entry, `internal` for private code whose import outside the allowed tree `go build` mechanically rejects, feature packages instead of a layer or utils dumping ground. Upper/lower case of an identifier is a second, independent level of privacy inside an already allowed import. Package initialization order is deterministic and follows the same DAG as compilation — the reason wiring should be written explicitly in `main`, and not through `init()` with hidden effects. The "one package per directory" rule and an acyclic build graph are not style recommendations. They are checks that happen on every compilation. Use the compiler as an ally in keeping boundaries, not as an obstacle to work around.
