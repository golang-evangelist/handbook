# 13.07 Handling Error Responses in Goroutines

> **Go Path - Zero to Gopher** / **02 Intermediate → Managing Errors in Go** / Lesson 13.07

## Lesson goals

After this lesson you should:

- use `golang.org/x/sync/errgroup` for parallel tasks with one aggregated error
- cancel `context.Context` on the first error (`errgroup.WithContext`)
- synchronize errors without a shared `var err error` and without manual mutex noise
- limit concurrency with `SetLimit`
- understand what `Wait` returns and how panic in a worker relates to the recover boundary

## Prerequisite

- lesson 13.06 (channel of results, ownership of close)
- `context` package: cancel, timeout, `Done`
- `go get golang.org/x/sync` (module `golang.org/x/sync/errgroup`)
- Go 1.22+

## Problem this lesson solves

Manual `WaitGroup` + a single `error` variable + `Mutex` is easy to get wrong: data race, work continuing after failure, goroutine leaks, forgotten `Done`. The channel of results from 13.06 solves transport, but for “run N, return the first error, cancel the rest” the industry uses **errgroup**. This lesson teaches that contract: error synchronization, cancel on first error, limiting parallelism.

## Mental model

1. **Group** — a set of tasks with a shared lifetime.
2. **First error wins** — `Wait` returns it; later errors are not kept as the winner.
3. **Context cancel** — `WithContext` cancels the child context when some task returns a non-nil `error`.
4. **Limit** — `SetLimit` prevents an explosion of goroutines / connections.
5. The task’s **return value** is the only path for errors to the group (not shared `err`).
6. **Panic** is not `error` — either you catch it at the boundary or the process crashes; errgroup does not turn panic into `error` by itself.

## Mechanism

### Why errgroup instead of WaitGroup

```go
package classic

import "sync"

// anti-pattern: easy to forget Done, race on err, no cancel
func Classic(tasks []func() error) error {
	var (
		wg  sync.WaitGroup
		mu  sync.Mutex
		err error
	)
	for _, t := range tasks {
		t := t
		wg.Add(1)
		go func() {
			defer wg.Done()
			if e := t(); e != nil {
				mu.Lock()
				if err == nil {
					err = e
				}
				mu.Unlock()
			}
		}()
	}
	wg.Wait()
	return err
}
```

Problems: no cancellation of other tasks; mutex policy for “first error” is manual; no limit; easy to copy the wrong closure.

### errgroup.WithContext — basic trace

```go
package egdemo

import (
	"context"

	"golang.org/x/sync/errgroup"
)

func RunAll(parent context.Context, tasks ...func(context.Context) error) error {
	g, ctx := errgroup.WithContext(parent)
	for _, task := range tasks {
		task := task
		g.Go(func() error {
			return task(ctx) // same ctx — canceled on first error
		})
	}
	return g.Wait()
}
```

### What happens here

1. `WithContext` creates a child context and group.
2. Each `g.Go` registers a function that returns `error`.
3. When the first function returns non-nil, the group cancels `ctx`.
4. `Wait` blocks until all finish; it returns the first error (or nil).
5. Other tasks should respect `ctx.Done()` to actually stop.

### Trace — cancel on first error in a loop

```go
package fetch

import (
	"context"
	"fmt"

	"golang.org/x/sync/errgroup"
)

func FetchIDs(parent context.Context, ids []int, get func(context.Context, int) error) error {
	g, ctx := errgroup.WithContext(parent)
	for _, id := range ids {
		id := id
		g.Go(func() error {
			if err := ctx.Err(); err != nil {
				return err // already canceled — fast exit
			}
			if err := get(ctx, id); err != nil {
				return fmt.Errorf("id=%d: %w", id, err)
			}
			return nil
		})
	}
	return g.Wait()
}
```

### Trace — SetLimit

```go
package limited

import (
	"context"

	"golang.org/x/sync/errgroup"
)

func Limited(parent context.Context, n int, work func(context.Context, int) error) error {
	g, ctx := errgroup.WithContext(parent)
	g.SetLimit(8) // at most 8 goroutines at once
	for i := 0; i < n; i++ {
		i := i
		g.Go(func() error {
			return work(ctx, i)
		})
	}
	return g.Wait()
}
```

`SetLimit` must be set before the `Go` calls you want to limit. Without a limit, `n=10_000` opens 10_000 goroutines — often OK for CPU-short work, dangerous for network/DB.

### Trace — error synchronization: what Wait guarantees

```go
package waitnotes

// Wait:
// - waits until all Go tasks finish
// - returns the first non-nil error some task returned
// - if context was canceled because of that error, others should exit
// - nil means: everyone returned nil
```

No magic: if a task ignores context and runs another 30s after an error, `Wait` waits those 30s. Cancel is a signal, not a thread interrupt.

### Trace — task that does not check context

```go
package stubborn

import (
	"context"
	"time"
)

func Stubborn(_ context.Context) error {
	time.Sleep(5 * time.Second) // ignores cancel
	return nil
}

func Good(ctx context.Context) error {
	t := time.NewTimer(5 * time.Second)
	defer t.Stop()
	select {
	case <-ctx.Done():
		return ctx.Err()
	case <-t.C:
		return nil
	}
}
```

### Trace — collecting results with errgroup

errgroup synchronizes errors, not values. You still collect results safely:

```go
package values

import (
	"context"
	"sync"

	"golang.org/x/sync/errgroup"
)

func Map(parent context.Context, in []string, fn func(context.Context, string) (int, error)) ([]int, error) {
	out := make([]int, len(in))
	g, ctx := errgroup.WithContext(parent)
	for i, s := range in {
		i, s := i, s
		g.Go(func() error {
			v, err := fn(ctx, s)
			if err != nil {
				return err
			}
			out[i] = v // each i unique — no race on same index
			return nil
		})
	}
	err := g.Wait()
	return out, err
}

// if you append to the same slice, you need Mutex or channel of results (13.06)
func AppendSafe(parent context.Context, n int, fn func(context.Context, int) (string, error)) ([]string, error) {
	var (
		mu  sync.Mutex
		acc []string
	)
	g, ctx := errgroup.WithContext(parent)
	for i := 0; i < n; i++ {
		i := i
		g.Go(func() error {
			s, err := fn(ctx, i)
			if err != nil {
				return err
			}
			mu.Lock()
			acc = append(acc, s)
			mu.Unlock()
			return nil
		})
	}
	return acc, g.Wait()
}
```

### Trace — parent cancel vs first error cancel

```go
package causes

import (
	"context"
	"errors"
	"fmt"

	"golang.org/x/sync/errgroup"
)

func Distinguish(parent context.Context) error {
	g, ctx := errgroup.WithContext(parent)
	g.Go(func() error {
		<-ctx.Done()
		return ctx.Err()
	})
	g.Go(func() error {
		return fmt.Errorf("boom")
	})
	err := g.Wait()
	if errors.Is(err, context.Canceled) {
		// may be parent cancel OR cancel due to another error —
		// the first error returned from Wait is usually "boom", not Canceled
		return err
	}
	return err
}
```

In practice: `Wait` returns the task error (`boom`). The other task may return `context.Canceled` because it saw Done — the group picks the **first** non-nil it records per its internals. So tasks after cancel should return `ctx.Err()` or `nil` consistently with that policy; cleanest: at the start `if err := ctx.Err(); err != nil { return err }`, and real work returns domain errors.

### Trace — errgroup without WithContext

```go
package plain

import "golang.org/x/sync/errgroup"

func NoCancel(tasks []func() error) error {
	var g errgroup.Group
	for _, t := range tasks {
		t := t
		g.Go(t)
	}
	return g.Wait() // first error is returned, BUT others are not canceled automatically
}
```

Without `WithContext` there is no shared cancel signal. Use only when tasks cannot be canceled or are short-lived.

### Trace — panic in a worker

```go
package protect

import (
	"fmt"

	"golang.org/x/sync/errgroup"
)

func GoSafe(g *errgroup.Group, fn func() error) {
	g.Go(func() error {
		defer func() {
			if rec := recover(); rec != nil {
				// turn into error — team policy
				_ = fmt.Errorf("panic: %v", rec)
			}
		}()
		return fn()
	})
}
```

Note: if `recover` swallows panic and wrongly returns `nil` from defer, the group thinks success. Correct:

```go
g.Go(func() error {
	var err error
	defer func() {
		if rec := recover(); rec != nil {
			err = fmt.Errorf("panic: %v", rec)
		}
	}()
	err = fn()
	return err
})
```

Even better: named result:

```go
g.Go(func() (err error) {
	defer func() {
		if rec := recover(); rec != nil {
			err = fmt.Errorf("panic: %v", rec)
		}
	}()
	return fn()
})
```

### Trace — comparison with channel of results

| Need | errgroup | channel Result |
|---------|----------|----------------|
| First error + cancel | excellent | manual |
| All values + all errors | manual with group | natural |
| Pipeline stage | weaker | better |
| Parallelism limit | `SetLimit` | manual semaphore |
| Simple `error` API | `Wait` | manual aggregation |

Often: errgroup for orchestration, and inside still a small Result if you need partial results.

### Trace — HTTP handler using errgroup

```go
package api

import (
	"context"
	"net/http"

	"golang.org/x/sync/errgroup"
)

func Handler(loadA, loadB func(context.Context) error) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		g, ctx := errgroup.WithContext(r.Context())
		g.Go(func() error { return loadA(ctx) })
		g.Go(func() error { return loadB(ctx) })
		if err := g.Wait(); err != nil {
			http.Error(w, "dependency failed", http.StatusBadGateway)
			return
		}
		w.WriteHeader(http.StatusNoContent)
	}
}
```

Status mapping in more detail in 13.08 — here it matters that `r.Context()` flows into the group.

### Trace — testing cancellation

```go
package eg_test

import (
	"context"
	"errors"
	"testing"
	"time"

	"golang.org/x/sync/errgroup"
)

func TestCancelOnFirstError(t *testing.T) {
	t.Parallel()
	g, ctx := errgroup.WithContext(context.Background())
	started := make(chan struct{})
	g.Go(func() error {
		return errors.New("fail")
	})
	g.Go(func() error {
		close(started)
		select {
		case <-ctx.Done():
			return ctx.Err()
		case <-time.After(3 * time.Second):
			t.Fatal("not canceled")
			return nil
		}
	})
	<-started
	err := g.Wait()
	if err == nil {
		t.Fatal("expected error")
	}
}
```

### Trace — order of Go calls and Limit

```go
g.SetLimit(2)
for i := 0; i < 10; i++ {
    g.Go(...) // 3rd and later wait for a free slot
}
```

A slot is freed when the function **returns**. A long task holds the slot — so limit on “number of allowed DB connections”, not on “number of URLs”.

### Trace — combining parent timeout

```go
ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
defer cancel()
g, ctx := errgroup.WithContext(ctx)
// ...
err := g.Wait()
// err may be context.DeadlineExceeded or a domain error
```

If timeout wins before a task error, `Wait` typically sees tasks returning `ctx.Err()`.

## Rules and syntax

1. Install: `go get golang.org/x/sync@latest` (or pin version in `go.mod`).

2. Basic shape:

```go
g, ctx := errgroup.WithContext(parent)
g.Go(func() error { return work(ctx) })
err := g.Wait()
```

3. Limit:

```go
g.SetLimit(n) // n > 0; before Go calls
```

4. Never write to shared `err` from a task — return `error` from the function passed to `Go`.

5. Every long-running job must have `select` / check `ctx.Err()`.

6. Results: pre-allocated slice by index, or mutex, or channel (13.06).

7. `g.Go` argument is `func() error` — not `func() (T, error)`; close over T in outer scope carefully (closure, lesson 13.09).

8. Do not mix `WaitGroup.Done` with errgroup — pick one coordinator.

## Examples

### Example A — Predict the result

```go
package main

import (
	"context"
	"fmt"

	"golang.org/x/sync/errgroup"
)

func main() {
	g, _ := errgroup.WithContext(context.Background())
	g.Go(func() error { return nil })
	g.Go(func() error { return fmt.Errorf("x") })
	fmt.Println(g.Wait() != nil)
}
```

**Answer:**

```
true
```

### What happens here

`Wait` returns the first non-nil error. Output is `true` because `err != nil`.

### Example B — Predict the result (all nil)

```go
package main

import (

func main() {
```

### What happens here

With no error `Wait` returns `nil`; context is not canceled due to a task error.

### Example C — Predict the result (SetLimit 1)

```go
package main

import (
	"context"
	"fmt"
	"time"

	"golang.org/x/sync/errgroup"
)

func main() {
	g, ctx := errgroup.WithContext(context.Background())
	g.SetLimit(1)
	order := make(chan int, 2)
	g.Go(func() error {
		order <- 1
		time.Sleep(20 * time.Millisecond)
		return nil
	})
	g.Go(func() error {
		order <- 2
		return ctx.Err()
	})
	_ = g.Wait()
	fmt.Println(<-order, <-order)
}
```

**Answer:**

```
1 2
```

### What happens here

Limit 1 serializes start: first task takes the slot, sends `1`, sleeps; only then the second sends `2`. Without limit order would be a race.

### Example D — wrap and errors.Is

```go
package main

import (
	"context"
	"errors"
	"fmt"

	"golang.org/x/sync/errgroup"
)

var ErrGone = errors.New("gone")

func main() {
	g, _ := errgroup.WithContext(context.Background())
	g.Go(func() error {
		return fmt.Errorf("user: %w", ErrGone)
	})
	err := g.Wait()
	fmt.Println(errors.Is(err, ErrGone))
}
```

**Answer:**

```
true
```

### What happens here

errgroup passes through your `error` value; wrap stays compatible with `errors.Is`.

### Example E — parent cancel

```go
package main

import (
	"context"
	"fmt"
	"time"

	"golang.org/x/sync/errgroup"
)

func main() {
	parent, cancel := context.WithCancel(context.Background())
	g, ctx := errgroup.WithContext(parent)
	g.Go(func() error {
		<-ctx.Done()
		return ctx.Err()
	})
	time.AfterFunc(10*time.Millisecond, cancel)
	fmt.Println(g.Wait())
}
```

**Answer:**

```
context canceled
```

### What happens here

Parent cancel cancels the child; task returns `ctx.Err()`; `Wait` returns that error.

## Decision analysis

| Question | A | B | Choice |
|---------|---|---|-------|
| Orchestration | errgroup | manual WG+mu | errgroup almost always |
| Cancel | WithContext | plain Group | WithContext if there is I/O |
| Results | indexed slice | mutex append | indices without lock |
| Limit | SetLimit | semaphore channel | SetLimit |
| Panic | recover→error | crash | per on-call policy |
| Partial | continue without cancel | fail-fast | product decision |

## Trade-offs

- **Fail-fast cancel** saves resources but loses other errors (no automatic `Join`).
- **SetLimit** slows throughput to protect dependencies.
- **Recover** in every task hides bugs if turned into generic log without alerting.
- **errgroup** does not replace channel pipeline; for streams use 13.06 patterns.
- Waiting on `Wait` after cancel lasts until “stubborn” tasks exit — investment in ctx-aware code pays off.

## Common mistakes

1. Shared `error` with errgroup — redundant and dangerous.
2. Ignoring `ctx` in a task — cancel does not work in practice.
3. `SetLimit` after all `Go` — too late / ineffective.
4. Append to slice without mutex from multiple tasks — race.
5. Swallowing panic with `return nil`.
6. Using plain `Group` when cancellation is needed.
7. Mixing `WaitGroup` and errgroup in the same flow.
8. Assuming `Wait` kills goroutines — it only waits for return.
9. Returning `nil` after domain error because it was “already logged”.
10. Forgotten `task := task` / `id := id` in older code before 1.22 (in 1.22 loop is per-iteration, but readability still matters).

## Idiomatic Go

- `g, ctx := errgroup.WithContext(r.Context())` in HTTP handlers.
- Wrap with operation: `fmt.Errorf("load settings: %w", err)`.
- Tie limit to pool size (DB, HTTP client), not magic 100.
- Test cancel path, not only happy path.
- Export functions that take `context.Context` as first argument.
- For aggregating all errors: either manual `errors.Join` without early cancel, or two passes — do not expect that from default errgroup.

## Practical scenario

Checkout service calls in parallel: inventory, pricing, fraud. Without errgroup, fraud timeout leaves inventory reservation “hanging” because pricing still runs 2s. After `WithContext`, inventory sees cancel and does compensating release in `defer` or separate cleanup tied to ctx. On-call metric: p95 checkout latency drops because you do not wait for the slowest successful sibling after the first error — only grace period for ctx-aware exit.

## Summary

`errgroup` synchronizes errors from multiple goroutines: task returns `error`, `Wait` gives the first, `WithContext` cancels the rest. `SetLimit` protects dependencies. Cancel is cooperative — code must read `ctx`. Next lesson maps those errors to HTTP status codes without leaking internal details to the client.

### Additional mechanism — nesting groups

```go
package nest

import (
	"context"

	"golang.org/x/sync/errgroup"
)

func Outer(parent context.Context) error {
	g, ctx := errgroup.WithContext(parent)
	g.Go(func() error {
		ig, ictx := errgroup.WithContext(ctx)
		ig.Go(func() error { return leaf(ictx) })
		return ig.Wait()
	})
	g.Go(func() error { return other(ctx) })
	return g.Wait()
}

func leaf(context.Context) error  { return nil }
func other(context.Context) error { return nil }
```

Inner cancel does not cancel the outer parent automatically beyond errgroup rules — but if inner `Wait` returns an error, the outer task returns that error and cancels siblings. Keep depth shallow.

### Additional mechanism — semaphore vs SetLimit

```go
sem := make(chan struct{}, 8)
sem <- struct{}{} // acquire
<-sem             // release
```

Manual semaphore channel works, but `SetLimit` tracks active `Go` functions in the errgroup API — less boilerplate with `Wait`.

### Example F — Predict the result (two errors)

```go
package main

import (
	"context"
	"fmt"
	"time"

	"golang.org/x/sync/errgroup"
)

func main() {
	g, ctx := errgroup.WithContext(context.Background())
	g.Go(func() error {
		time.Sleep(5 * time.Millisecond)
		return fmt.Errorf("slow")
	})
	g.Go(func() error {
		return fmt.Errorf("fast")
	})
	err := g.Wait()
	fmt.Println(err)
	fmt.Println(ctx.Err() != nil)
}
```

**Answer:**

```
fast
true
```

### What happens here

Faster task returns `"fast"`; group cancels ctx; slower later returns `"slow"` but `Wait` already has first error `"fast"`. `ctx.Err()` is non-nil due to cancel.

### Example G — indexed write

```go
package main

import (
	"context"
	"fmt"

	"golang.org/x/sync/errgroup"
)

func main() {
	out := make([]int, 3)
	g, ctx := errgroup.WithContext(context.Background())
	for i := 0; i < 3; i++ {
		i := i
		g.Go(func() error {
			_ = ctx
			out[i] = i * 10
			return nil
		})
	}
	_ = g.Wait()
	fmt.Println(out)
}
```

**Answer:**

```
[0 10 20]
```

### What happens here

Each index is written by one goroutine — no race. This is the idiomatic counterpart to errgroup for values.

### Extended orchestration status table

| Situation | What Wait returns | ctx | Note |
|-----------|----------------|-----|----------|
| all nil | nil | not canceled due to err | OK |
| one error | that error | canceled | sibling should exit |
| parent timeout | often DeadlineExceeded | canceled | task returns ctx.Err |
| panic without recover | process crashes | — | not error path |
| limit full | Wait still OK | — | Go blocks on slot |

### Scenario — migration from 13.06

Team has `chan Result`. Wants cancel. Options:

1. Keep channel; add `context` + `SafeSend` (13.06) — more control, more code.
2. Move to errgroup + slice — less code, first error focus.
3. Hybrid: errgroup for phases, channel for stream within a phase.

Choose 2 for request/response services; 1 or 3 for pipeline.
