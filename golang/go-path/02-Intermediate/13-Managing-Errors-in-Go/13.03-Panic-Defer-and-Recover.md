# 13.03 Panic, defer, and recover

> **Go Path - Zero to Gopher** / **02 Intermediate → Managing Errors in Go** / Lesson 13.03

## Lesson goals

After this lesson you should:

- use `panic` for programmer impossibilities and broken invariants, not for expected errors
- understand `defer` order (LIFO) and why defer is placed immediately after successful resource acquisition
- put `recover` **only** in a `defer` function and **only** at the boundary (HTTP middleware, goroutine root)
- know that `defer` + `recover` **do not cross** a goroutine boundary — each goroutine has its own panic stack
- not abuse recover as a substitute for `error` return
- connect panic policy with process reliability and diagnostics (log + stack, not the client)

## Prerequisite

- lessons 13.01–13.02 (error as a value; sentinel/types)
- basic concepts: HTTP handler, goroutine (`go f()`), `os.Open` / Close
- Go 1.22+

If you are not sure what a goroutine is: it is a concurrent execution thread started by the Go runtime. Panic in one is **not caught** by recover in another.

## Problem this lesson solves

Two mirrors of the same design mistake:

1. **Panic for “file not found”** — code becomes unreadable; the caller does not see the error in the signature; tests must catch panic instead of comparing `error`.
2. **Panic without recover in an HTTP server** — one nil pointer in a rare handler crashes the whole process (or at least leaves an ugly fall), even though other requests could live.

The right pattern: `error` for expected; panic for invariants; recover at the boundary so one bad request does not crash the whole server — with log and metric, not silent swallowing.

## Mental model

1. **Panic** — “this must not happen if the program is correct” (broken contract, impossible state).
2. **Defer** — scheduled cleanup; runs on exit from the function, LIFO (last defer first).
3. **Recover** — only inside defer; returns the panic value or `nil` if there is no panic; works **only in that** goroutine.
4. **Boundary** — HTTP middleware, gRPC interceptor, worker supervisor, `main` adapter for a plugin.
5. **After recover** — log (stack), metric, return 500 / isolate the worker; **fix the cause**, do not treat recover as a feature.
6. **Must at boot** — `template.Must` / `regexp.MustCompile` may panic at start: the process must not run half-ready.

## Mechanism

### 1. What panic does — step by step

When `panic(x)` executes:

1. Normal function flow stops.
2. Defers of that function run (LIFO), then the caller’s defers, upward along the stack **in the same goroutine**.
3. If some defer does `recover()` and gets non-nil, the panic is “calmed”; the function with the defer continues after the defer block (often via named result).
4. If nobody recovers, the goroutine dies. If it is the main one (or the runtime decides it is fatal), the process usually ends with a stack trace.

**Trace — without recover**

```go
func a() { defer fmt.Println("defer a"); b() }
func b() { defer fmt.Println("defer b"); panic("boom") }
func main() { a() }
```

| Print / event order | What |
|----------------------------|-----|
| enter main → a → b | |
| panic("boom") | stack unwinds |
| defer b | `defer b` |
| defer a | `defer a` |
| process | stack trace, exit |

### 2. When to panic — “yes” list

- Counting an invariant: “this index always exists because we just inserted it” — better assert in a test; in production rather rehabilitate the design. Panic if it is a **library** “Must*” contract documented.
- `template.Must` / `regexp.MustCompile` for **static** artifacts at init/boot.
- Unfixable state at start: the config template must parse or there is no point serving traffic.
- Programmer error in your code found in development — but in libraries prefer `error` if the caller can pass bad input.

### 3. When not to panic — “no” list

- I/O: file, network, disk full
- User input validation
- “Not found”, conflict, timeout
- Control flow instead of `if`
- Errors the caller **expects** and should branch on

### 4. Defer — LIFO and resources

```go
f, err := os.Open(path)
if err != nil {
	return err
}
defer f.Close()
```

Why immediately after successful Open? So every later `return` (including errors) closes the file.

**LIFO trace**

```go
defer fmt.Println("first")
defer fmt.Println("second")
fmt.Println("body")
```

Output:

```
body
second
first
```

The last registered defer exits first. Important when unlock vs close order must be exact: set defer order deliberately.

**Defer captures arguments immediately**

```go
i := 0
defer fmt.Println(i) // prints 0, not 1
i++
```

For “print final i” use a function literal:

```go
defer func() { fmt.Println(i) }()
```

### 5. Recover — only in defer

```go
defer func() {
	if r := recover(); r != nil {
		// log, convert
	}
}()
```

If you call `recover()` outside defer during normal flow, you get `nil` — it does not catch anything useful for calming a panic.

**Named result + recover**

```go
func Guard(fn func() error) (err error) {
	defer func() {
		if rec := recover(); rec != nil {
			err = fmt.Errorf("panic: %v", rec)
		}
	}()
	return fn()
}
```

Named result `err` lets defer **set** the return value after panic. Use for adapter/plugin boundaries — not as the style of the whole codebase.

### 6. HTTP boundary — middleware

```go
func Recover(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		defer func() {
			if rec := recover(); rec != nil {
				slog.Error("panic", "recover", rec, "stack", string(debug.Stack()))
				http.Error(w, "internal error", http.StatusInternalServerError)
			}
		}()
		next.ServeHTTP(w, r)
	})
}
```

**Trace with values — handler panics**

| Step | State |
|-------|--------|
| request enters middleware | defer recover registered |
| `next` panics with `"nil foo"` | unwinding |
| defer recover | `rec == "nil foo"` |
| slog.Error | stack in log |
| http.Error | client sees 500 + “internal error” |
| process | **lives**; next request OK |

The client must **not** see `fmt.Sprint(rec)` or the stack.

### 7. Goroutine boundary — recover does not cross

This is critical.

```go
func parent() {
	defer func() {
		if r := recover(); r != nil {
			fmt.Println("parent caught", r)
		}
	}()
	go child() // panics inside
	time.Sleep(time.Second)
}

func child() {
	panic("from child")
}
```

Parent does **not** catch child panic. The child goroutine dies; in many versions/configurations that ends the whole program.

**Fix — recover at the child root:**

```go
go func() {
	defer func() {
		if r := recover(); r != nil {
			slog.Error("worker panic", "r", r, "stack", string(debug.Stack()))
		}
	}()
	work()
}()
```

Every goroutine that may panic needs its own guard at the root, or a guarantee that `work` does not panic (only returns error).

### 8. Defer Close and Close error

`defer f.Close()` ignores the Close error. For write paths sometimes you need:

```go
defer func() {
	if cerr := out.Close(); err == nil {
		err = cerr
	}
}()
```

(named `err` in the signature). That is a more advanced pattern; remember Close can fail after a successful Write.

### 9. Must at start vs Must in a request

| Place | Must/panic | Why |
|-------|------------|-------|
| `init` / `main` boot | yes | fail fast; no traffic |
| per-request parser | no | return error; one bad request |
| library public API | rarely | document; prefer error |

### 10. Link to 13.01/13.02

Panic is **not** a substitute for `ErrNotFound`. Recover is **not** a substitute for `if err != nil`. After recover you still want metrics and a ticket to fix the root cause — otherwise you mask bugs.

### 11. Does the framework already have recover?

`net/http` Server in newer versions can log panic in a handler; gRPC has an interceptor. Check the docs: do you log the stack? do you return a safe status? Do not blindly duplicate, but confirm the contract.

### 12. Defer in a loop — short preview

```go
for _, p := range paths {
	f, err := os.Open(p)
	if err != nil { return err }
	defer f.Close() // closes only on exit from the function — FD leak in a loop!
}
```

Fix: extract into a function per iteration or Close explicitly. More detail in later lessons on closures; here remember the danger.

## Rules and syntax

1. Do not panic for business / I/O / validation.
2. `recover` only inside a `defer` function literal.
3. At the HTTP boundary: recover → log + stack → 500 without leaking.
4. `defer Close()` immediately after successful open/create.
5. At start, `Must` for static templates is OK.
6. Panic in `go func()` requires its own defer recover at that goroutine’s root.
7. After recover: metric `panics_total`, alert; not “return nil” without a trail.
8. Do not use panic for control flow in a library others import without a documented Must.
9. Defer arguments are evaluated immediately — use a closure for late values.
10. LIFO: plan unlock/close order consciously.

Basic defer:

```go
f, err := os.Open(path)
if err != nil { return err }
defer f.Close()
```

Basic recover:

```go
defer func() {
	if r := recover(); r != nil {
		slog.Error("panic", "r", r)
	}
}()
```

## Examples

### Example 1 — defer closes the file on the error path

```go
package panicsafe

import (
	"fmt"
	"io"
	"os"
)

func CopyFile(dst, src string) error {
	in, err := os.Open(src)
	if err != nil {
		return fmt.Errorf("open src: %w", err)
	}
	defer in.Close()

	out, err := os.Create(dst)
	if err != nil {
		return fmt.Errorf("create dst: %w", err)
	}
	defer out.Close()

	if _, err := io.Copy(out, in); err != nil {
		return fmt.Errorf("copy: %w", err)
	}
	return nil
}
```

### What happens here

If `Create` fails, `in.Close` still runs via defer. If `Copy` fails, both Closes. No panic — I/O errors are values.

### Predict the result

`src` does not exist — which defer runs?

**Answer:** None for files — `Open` failed before `defer in.Close()`. The function returns a wrapped error immediately.

### Example 2 — Must at start

```go
package panicsafe

import "html/template"

func MustProfileTemplate() *template.Template {
	return template.Must(template.New("p").Parse(`<h1>{{.}}</h1>`))
}
```

### What happens here

If the template string cannot parse, `Must` panics. The process does not start. That is intentional fail fast, not a runtime business panic.

### Predict the result

May you call `MustProfileTemplate` inside every HTTP request with a user template?

**Answer:** No — user input needs `template.New(...).Parse` + `error`. Must is for constant artifacts at boot.

### Example 3 — recover middleware

```go
package panicsafe

import (
	"log/slog"
	"net/http"
	"runtime/debug"
)

func Recover(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		defer func() {
			if rec := recover(); rec != nil {
				slog.Error("panic", "recover", rec, "stack", string(debug.Stack()))
				http.Error(w, "internal error", http.StatusInternalServerError)
			}
		}()
		next.ServeHTTP(w, r)
	})
}
```

### What happens here

One handler panic does not crash the whole server process for that request goroutine. Stack goes to the log, not the client.

### Predict the result

Handler does `panic("x")`. What does the client see? What does the log see?

**Answer:** Client: status 500, body “internal error”. Log: `recover=x` + stack. Process continues.

### Example 4 — Guard turns panic into error

```go
package panicsafe

import "fmt"

func Guard(fn func() error) (err error) {
	defer func() {
		if rec := recover(); rec != nil {
			err = fmt.Errorf("panic: %v", rec)
		}
	}()
	return fn()
}
```

### What happens here

Named return lets recover set `err`. Use for legacy/plugin boundaries.

### Predict the result

`Guard(func() error { panic("x"); return nil })` — what is `err.Error()`?

**Answer:** a string containing `panic: x` (exact format depends on `%v`).

### Example 5 — defer LIFO print

```go
package panicsafe

import "fmt"

func Order() {
	defer fmt.Println("first defer")
	defer fmt.Println("second defer")
	fmt.Println("body")
}
```

### What happens here

Last defer exits first.

### Predict the result

Order of lines on stdout?

**Answer:**

```

first defer
```

### Example 6 — do not panic for not found

```go
package panicsafe

import "errors"

var ErrNotFound = errors.New("not found")

func Find(m map[string]int, k string) (int, error) {
	v, ok := m[k]
	if !ok {
		return 0, ErrNotFound
	}
	return v, nil
}
```

### What happens here

The expected outcome is `error`. Panic would be the wrong instrument — the caller would need recover instead of Is.

### Predict the result

`Find(map[string]int{}, "a")` — values?

**Answer:** `0`, `ErrNotFound`. No panic.

### Example 7 — recover does not catch another goroutine

```go
package panicsafe

import (
	"fmt"
	"time"
)

func DemoCrossGoroutine() {
	defer func() {
		if r := recover(); r != nil {
			fmt.Println("caught in parent", r)
		}
	}()
	go func() {
		panic("child boom")
	}()
	time.Sleep(200 * time.Millisecond)
	fmt.Println("parent still running?")
}
```

### What happens here

Parent defer does **not** catch child. In a typical run you see child goroutine / process crash. The message “caught in parent” does **not** appear because of child panic.

### Predict the result

Does “caught in parent” print because of `child boom`?

**Answer:** No. Parent recover does not see child panic.

---

### Example 8 — correct worker root

```go
package panicsafe

import (
	"log/slog"
	"runtime/debug"
)

func StartWorker(work func()) {
	go func() {
		defer func() {
			if r := recover(); r != nil {
				slog.Error("worker panic", "r", r, "stack", string(debug.Stack()))
			}
		}()
		work()
	}()
}
```

### What happens here

Recover is in the **same** goroutine as the potential panic. The parent process can live; the worker needs a restart policy (supervisor).

### Predict the result

`work` panics — does parent `main` die automatically?

**Answer:** Not necessarily — the panic is caught in the worker. (Without recover, child panic would often crash the program.)

---

### Example 9 — defer argument vs closure

```go
package panicsafe

import "fmt"

func DeferArgs() {
	x := 1
	defer fmt.Println("arg", x)
	defer func() { fmt.Println("closure", x) }()
	x = 2
}
```

### What happens here

The first defer bound `x=1` immediately. The closure reads `x` at execution time.

### Predict the result

Output?

**Answer:**

```
closure 2
arg 1
```

(LIFO: first the closure defer, then the arg defer.)

---

### Example 10 — bad recover outside defer

```go
package panicsafe

import "fmt"

func UselessRecover() {
	if r := recover(); r != nil {
		fmt.Println("never for future panic", r)
	}
	// panic("x") here would not be caught by this recover above
}
```

### What happens here

`recover` outside defer during calm flow returns nil. It does not set a “trap” for later.

### Predict the result

Does `UselessRecover` set protection for a later panic in the caller?

**Answer:** No.

## Decision analysis

| Decision | Why |
|--------|-------|
| error for expected | predictable API, testable |
| Must at boot | fail fast, no half service |
| Recover on HTTP | request isolation |
| Defer for Close | fewer FD leaks |
| Stack in log | root-cause diagnostics |
| Recover per goroutine | the runtime model requires it |
| Metric after recover | do not mask silently |

## Trade-offs

- Recover masks bugs if you swallow without log, metrics, and alerts.
- Overly broad recover in a library hides problems from the caller — libraries rarely catch panic.
- Panic-driven libraries are unidiomatic in the Go ecosystem.
- Guard(panic→error) sounds handy, but loses stack context if you do not log immediately.
- Fail fast at boot requires good deploy rollback.

## Common mistakes

1. Panic for validation or not-found.
2. Recover outside defer (does not work as you think).
3. Recover without log and stack.
4. Forgotten defer Close.
5. Assuming parent recover catches a child goroutine.
6. Defer in a loop without care — FD leak.
7. Returning `fmt.Sprint(recover())` to the client.
8. Must on per-request user input.
9. Silent `return nil` after recover without metrics.
10. Relying on “panic always crashes the process” in a server with middleware — the bug stays invisible in uptime.

## Idiomatic Go

- `defer f.Close()` immediately after successful open.
- `template.Must` / `regexp.MustCompile` for static artifacts.
- Middleware recover at the top of the handler chain.
- Metric `panics_total` after recover.
- Worker: own defer recover + restart policy.
- Prefer `error` in public library functions.
- Document every exported `Must*` as “panics on invalid ...”.

## Practical scenario

A nil pointer in a rare handler crashes the worker process without recover — Kubernetes restarts, but all in-flight requests fail, and deploy looks “flaky”. The team adds `Recover` middleware + slog stack + alert on `panics_total`. Uptime stabilizes; the root-cause ticket goes into the sprint. Recover remains a net, not a feature.

Second incident: background `go index()` panics at night; parent HTTP recover does not help. Fix: `StartWorker` pattern with local recover + dead-letter metric.

### Additional trace: what happens with the panic value

`panic(x)` accepts any `any` (`interface{}`). Often it is a string or `error`. In the recover branch:

```go
switch v := rec.(type) {
case error:
	slog.Error("panic", "err", v)
default:
	slog.Error("panic", "val", v)
}
```

Do not send `v` to the client. If you want Guard to turn it into `error`, wrap: `fmt.Errorf("panic: %v", rec)` — and log the stack immediately because that error object **does not** have the panic stack in it.

### Mini exercise — where to put recover

The service has: (a) `main` HTTP server, (b) `go` background reindex every 10 min, (c) library package `calc` that other teams import.

**Answer:** (a) middleware recover; (b) root defer recover in that goroutine + metric; (c) **no** recover in the library — return `error`, document if you have `MustParse`.

### Decision table panic vs error (repeat)

| Signal | Instrument |
|--------|------------|
| User sent bad JSON | `error` |
| Config template invalid at boot | `Must` / panic |
| File not found in a request | `error` / sentinel |
| nil pointer in handler (bug) | panic → recover at boundary + fix bug |
| Worker panic at night | recover at worker root + alert |

### Defer and return values — one more example

```go
func readAll(path string) (data []byte, err error) {
	f, err := os.Open(path)
	if err != nil {
		return nil, err
	}
	defer f.Close()
	return io.ReadAll(f)
}
```

If `ReadAll` fails, `err` is returned, and `Close` still runs. (Advanced: Close error can overwrite — see named return pattern in the exercises.)

## Summary

Panic is for the impossible and boot invariants; expected failure stays `error`. Defer cleans resources (LIFO). Recover lives only in defer and only in the same goroutine — put it at the HTTP/worker boundary with log and metric.
