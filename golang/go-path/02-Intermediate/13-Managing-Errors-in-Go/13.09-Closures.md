# 13.09 Closures in Error Management

> **Go Path - Zero to Gopher** / **02 Intermediate → Managing Errors in Go** / Lesson 13.09

## Lesson goals

After this lesson you should:

- recall the core closure rule: a closure captures the **variable**, not a snapshot — as it applies to error values
- use **named return values + defer** to enrich errors on the way out without a separate `if err != nil` at every exit
- recognize and fix the **shared `err` variable trap** in deferred closures inside loops
- propagate errors from concurrent goroutines through closures using `errgroup`
- implement **retry logic** as a closure without leaking the per-attempt error context
- build an **HTTP error-handler factory** as a closure that unifies error mapping across routes
- distinguish `err :=` (new variable, shadows) from `err =` (same variable, mutates) and understand what each means for a deferred log closure

- **13.01–13.08** in this module: `error` as a value, sentinel errors, `%w` wrapping, `panic`/`defer`/`recover`, `errors.Is`/`errors.As`, channel errors, `errgroup`, HTTP error mapping

## Problem this lesson solves

Error management and closures meet in four recurring patterns that are easy to get wrong:

1. **Named return + defer** — a deferred closure can enrich the return error, but only if it captures the named return variable and not a local shadow.
2. **Shared `err` in a loop** — `var err error` declared outside a loop is not a per-iteration variable; all deferred closures that read it see the last assignment, not the one from their iteration.
3. **Goroutine error collection** — `errgroup` takes tasks as `func() error`; each task is a closure that must capture the right per-iteration binding.
4. **HTTP error-handler factory** — a middleware closure that maps `error` to an HTTP response unifies error handling without duplicating status-code logic in every handler.

Without closure binding rules, error context vanishes silently: the log shows the wrong error, the retry retries forever, or the HTTP handler writes 200 for a failed operation.

## Mental model

### Quick closure reminder

A closure binds a **variable** — not the value the variable holds at creation time. When the variable changes, the closure sees the new value.

```text
outer scope
  err := nil          ← variable lives here
  f := func() {
    log(err)          ← f captures err (not nil — the variable err)
  }
  err = io.EOF
  f()                 → logs io.EOF, not nil
```

Go 1.22+: a `for` loop creates one fresh variable per iteration for loop variables (`i`, `v`). A variable declared **outside** the loop (like `var err error`) is NOT a loop variable and does NOT get a fresh binding per iteration.

| Variable | Declared where | Per-iteration in 1.22? | Defer in loop sees |
|---|---|---|---|
| `i` in `for i := 0` | loop | yes | its own `i` |
| `v` in `range` | loop | yes | its own `v` |
| `err` before the loop | outer scope | **no** | last assignment |
| `errCopy := err` | local copy | per execution | that copy |

### The four error-closure patterns

1. Named return + defer → error enrichment
2. Shared `err` in loop → snapshot to fix
3. errgroup → per-goroutine closure with correct binding
4. HTTP error factory → dependency-injection via closure

## Mechanism

### Pattern 1 — Named return + defer for error enrichment

A named return variable is part of the function's scope. A deferred closure that assigns to it runs **after** the `return` expression is evaluated but **before** the caller receives the value.

```go
package repo

import (
	"context"
	"database/sql"
	"fmt"
)

// ByID wraps every database error with the caller's id for context.
// The named return 'err' is shared between the body and the defer.
func (r ProductRepo) ByID(ctx context.Context, id int64) (_ Product, err error) {
	defer func() {
		if err != nil {
			err = fmt.Errorf("productRepo.ByID id=%d: %w", id, err)
		}
	}()

	var p Product
	err = r.db.QueryRowContext(ctx,
		`SELECT id, sku, name, cents FROM products WHERE id = $1`, id).
		Scan(&p.ID, &p.SKU, &p.Name, &p.Cents)
	if err == sql.ErrNoRows {
		err = ErrNotFound // the defer will wrap it: "productRepo.ByID id=42: product not found"
		return
	}
	return p, err
}
```

**What happens here — line by line:**

1. `(_ Product, err error)` — the error return is named. The blank `_` avoids a named `Product` return that would need explicit handling in all paths.
2. `defer func() { if err != nil { err = fmt.Errorf(...) } }()` — this deferred function **closes over** the named `err`. When the function exits via any path, if `err` is non-nil, it wraps it.
3. At `return` without explicit arguments, Go uses the named return values. The defer fires after that assignment; it sees and can modify `err`.
4. The caller receives the wrapped error. No `if err != nil { return ..., fmt.Errorf("...", err) }` at each exit.

**Predict the result:** if `ByID` is called with `id=42` and the database is down, what does the caller receive?

**Answer:** `productRepo.ByID id=42: <underlying network error>`. The enrichment is automatic for every exit path including panics recovered by the framework.

#### Common trap — shadowing the named return

```go
// bad: `:=` creates a NEW local err, the defer captures the outer named one
func (r ProductRepo) ByID(ctx context.Context, id int64) (_ Product, err error) {
	defer func() {
		if err != nil {
			err = fmt.Errorf("ByID: %w", err)
		}
	}()

	p, err := scanProduct(ctx, r.db, id) // ← correct: = assigns to named err
	// If you wrote:
	// p, newErr := scanProduct(...)     // ← newErr is a new variable; named err stays nil!
	// the defer would never fire because err == nil
	return p, err
}
```

Rule: inside a function with a named return, use `=` (assignment) not `:=` (short declaration) when the result must flow into the named return.

### Pattern 2 — Shared `err` variable trap in a loop

```go
package errloop

import (
	"context"
	"fmt"
	"log/slog"
)

// Bad: var err is outside the loop; all deferred closures capture the same variable.
func ProcessBad(ctx context.Context, ids []int64, log *slog.Logger) {
	var err error
	for _, id := range ids {
		err = process(ctx, id)
		defer func() {
			// ALL defers see the LAST value of err after the loop ends
			if err != nil {
				log.Error("defer saw error", "err", err)
			}
		}()
	}
}
```

**Predict the result:** `ids = [1, 2, 3]`. `process` returns `nil` for `id=1`, `io.EOF` for `id=2`, `nil` for `id=3`. How many times does the log print, and what does it show?

**Answer:** the log prints **zero** times. After the loop `err == nil` (the last assignment). All three deferred closures see `nil`. The error from `id=2` is lost silently.

**Fix — snapshot the per-iteration error:**

```go
package errloop

import (
	"context"
	"log/slog"
)

func ProcessGood(ctx context.Context, ids []int64, log *slog.Logger) {
	for _, id := range ids {
		iterErr := process(ctx, id) // new variable per iteration — a copy, not a reference
		if iterErr != nil {
			defer func(captured error) { // pass by value: frozen at registration time
				log.Error("deferred error log", "err", captured)
			}(iterErr)
		}
	}
}
```

Or, more idiomatically — do not defer a log inside a loop at all. Log immediately:

```go
func ProcessIdiom(ctx context.Context, ids []int64, log *slog.Logger) error {
	for _, id := range ids {
		if err := process(ctx, id); err != nil {
			log.Error("process failed", "id", id, "err", err)
			return fmt.Errorf("process id=%d: %w", id, err)
		}
	}
	return nil
}
```

**Decision:** only `defer` a log/cleanup when you genuinely need it to run at function exit regardless of exit path. For per-iteration errors, log or return immediately.

### Pattern 3 — goroutine error collection with `errgroup` and closure binding

`errgroup.Go` takes `func() error`. Each call is a closure. The binding rules from pattern 2 apply:

```go
package fanout

import (
	"context"
	"fmt"

	"golang.org/x/sync/errgroup"
)

// Correct: each goroutine closure captures a per-iteration binding.
func FetchAll(ctx context.Context, ids []int64, fetch func(context.Context, int64) (string, error)) ([]string, error) {
	g, ctx := errgroup.WithContext(ctx)
	results := make([]string, len(ids))

	for i, id := range ids {
		i, id := i, id // explicit copy; in Go 1.22+ this is redundant but documents intent for reviewers
		g.Go(func() error {
			v, err := fetch(ctx, id)
			if err != nil {
				return fmt.Errorf("fetch id=%d: %w", id, err)
			}
			results[i] = v // safe: each i is unique
			return nil
		})
	}

	if err := g.Wait(); err != nil {
		return nil, err // errgroup returns the first non-nil error
	}
	return results, nil
}
```

**What happens here:**

1. `errgroup.WithContext` creates a group and a derived context. When the first task returns a non-nil error, the context is cancelled — remaining tasks should check `ctx.Done()`.
2. Each `g.Go(func() error {...})` registers a goroutine task. The closure captures `id`, `i`, and `ctx`.
3. `ctx` is the **same** binding for all tasks — intentional: cancellation propagates to all.
4. `id` and `i` are per-iteration (explicit copy in the line above) so each goroutine works on its own item.
5. `g.Wait()` blocks until all goroutines return. The group returns the **first** non-nil error. The rest are discarded (a design decision of errgroup, not a bug).

**Predict the result:** `ids = [10, 20, 30]`. `fetch(ctx, 20)` returns `io.EOF`. `fetch(ctx, 30)` returns `os.ErrDeadlineExceeded`. What does `FetchAll` return?

**Answer:** one of the two errors (non-deterministic — `errgroup` returns whichever goroutine's error is reported first). The caller gets exactly one wrapped error: `fetch id=20: EOF` or `fetch id=30: deadline exceeded`.

#### Collecting all errors (multi-error pattern)

If you need all errors, not just the first:

```go
package multierr

import (
	"context"
	"errors"
	"fmt"
	"sync"
)

func CollectErrors(ctx context.Context, ids []int64, process func(context.Context, int64) error) error {
	var (
		mu   sync.Mutex
		errs []error
	)
	var wg sync.WaitGroup
	for _, id := range ids {
		id := id
		wg.Add(1)
		go func() {
			defer wg.Done()
			if err := process(ctx, id); err != nil {
				mu.Lock()
				errs = append(errs, fmt.Errorf("id=%d: %w", id, err))
				mu.Unlock()
			}
		}()
	}
	wg.Wait()
	return errors.Join(errs...) // Go 1.20+: nil if errs is empty, joined otherwise
}
```

`errors.Join` (Go 1.20+) wraps multiple errors into one. `errors.Is` and `errors.As` unwrap through it.

### Pattern 4 — HTTP error-handler factory as a closure

Repeating status-code logic in every handler is a maintenance problem. A factory closure captures the mapping once:

```go
package mw

import (
	"errors"
	"log/slog"
	"net/http"
)

// ErrorWriter is the contract for turning a domain error into an HTTP response.
type ErrorWriter func(http.ResponseWriter, *http.Request, error)

// WithErrors adapts a handler that returns an error into a standard http.HandlerFunc.
// The error-writing strategy is injected as a closure dependency.
func WithErrors(write ErrorWriter, fn func(http.ResponseWriter, *http.Request) error) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		if err := fn(w, r); err != nil {
			write(w, r, err) // delegate status-code decision to the injected writer
		}
	}
}
```

**Building the `ErrorWriter` closure:**

```go
package mw

import (
	"errors"
	"log/slog"
	"net/http"
)

// NewErrorWriter creates an ErrorWriter that logs internally and sends
// a safe HTTP response. The logger is captured once at construction time.
func NewErrorWriter(log *slog.Logger) ErrorWriter {
	return func(w http.ResponseWriter, r *http.Request, err error) {
		log.Error("handler error",
			"method", r.Method,
			"path", r.URL.Path,
			"err", err,
		)

		switch {
		case errors.Is(err, ErrNotFound):
			http.Error(w, `{"code":"not_found"}`, http.StatusNotFound)
		case errors.Is(err, ErrUnauthorized):
			http.Error(w, `{"code":"unauthorized"}`, http.StatusUnauthorized)
		case errors.Is(err, ErrConflict):
			http.Error(w, `{"code":"conflict"}`, http.StatusConflict)
		default:
			http.Error(w, `{"code":"internal_error"}`, http.StatusInternalServerError)
		}
	}
}
```

**Wiring in `main`:**

```go
func main() {
	log := slog.Default()
	write := mw.NewErrorWriter(log)

	mux := http.NewServeMux()
	mux.Handle("GET /products/{id}", mw.WithErrors(write, productHandler.ByID))
	mux.Handle("POST /products", mw.WithErrors(write, productHandler.Create))
}
```

**What happens here:**

1. `NewErrorWriter(log)` creates a closure that captures `log` at server construction, not at request time.
2. `WithErrors(write, fn)` wraps `fn` (which returns `error`) in a standard `http.HandlerFunc`. The closure captures `write` and `fn`.
3. When `fn` returns a domain error like `ErrNotFound`, `write` maps it to HTTP 404 with a safe body. The stack trace stays in the log, never in the response.
4. Adding a new route reuses the same `write` — no copy-paste of `switch` statements.

**Connection to 13.08 (Handling HTTP Errors):** lesson 13.08 established the principle of mapping domain errors to HTTP statuses. This lesson shows how a closure makes that mapping a first-class injectable dependency rather than a repeated block.

#### Testing the factory

```go
package mw_test

import (
	"errors"
	"net/http"
	"net/http/httptest"
	"testing"
)

func TestWithErrors_NotFound(t *testing.T) {
	t.Parallel()

	write := func(w http.ResponseWriter, r *http.Request, err error) {
		if errors.Is(err, mw.ErrNotFound) {
			http.Error(w, "not found", http.StatusNotFound)
		}
	}

	handler := mw.WithErrors(write, func(w http.ResponseWriter, r *http.Request) error {
		return mw.ErrNotFound
	})

	req := httptest.NewRequest(http.MethodGet, "/products/99", nil)
	rr := httptest.NewRecorder()
	handler.ServeHTTP(rr, req)

	if rr.Code != http.StatusNotFound {
		t.Fatalf("expected 404, got %d", rr.Code)
	}
}
```

The closure makes the test trivial: inject a fake `write` function, verify the status code without starting a real server.

### Pattern 5 — Retry logic as a closure

Retry and the error handling it wraps naturally form a closure:

```go
package retry

import (
	"context"
	"errors"
	"fmt"
	"time"
)

// Retry runs fn up to maxAttempts times, waiting backoff between attempts.
// Only retries when fn returns a retryable error (checked by isRetryable).
func Retry(ctx context.Context, maxAttempts int, backoff time.Duration,
	isRetryable func(error) bool, fn func(context.Context) error) error {

	var lastErr error
	for attempt := 1; attempt <= maxAttempts; attempt++ {
		lastErr = fn(ctx)
		if lastErr == nil {
			return nil
		}
		if !isRetryable(lastErr) {
			return fmt.Errorf("non-retryable after attempt %d: %w", attempt, lastErr)
		}
		if attempt == maxAttempts {
			break
		}
		select {
		case <-ctx.Done():
			return fmt.Errorf("context cancelled during retry (attempt %d): %w", attempt, ctx.Err())
		case <-time.After(backoff):
		}
	}
	return fmt.Errorf("all %d attempts failed, last: %w", maxAttempts, lastErr)
}
```

**Usage — the caller passes a closure:**

```go
err := retry.Retry(ctx, 3, 200*time.Millisecond,
	func(err error) bool { return errors.Is(err, io.ErrUnexpectedEOF) },
	func(ctx context.Context) error {
		return fetchFromAPI(ctx, endpoint) // fn is a closure over endpoint
	},
)
```

**What happens here:**

- `lastErr` is declared in the outer `Retry` scope. It is not a loop variable — it is reassigned on each attempt. The `return` at the end uses the last assignment. No deferred closures needed here.
- `isRetryable` and `fn` are themselves closures (or functions) passed by value. They capture their own dependencies (like `endpoint`) at their creation site.
- `context.Context` flows into every attempt so cancellation terminates the retry loop cleanly.

### Pattern 6 — `defer` + `close` + error check in one closure

A common pattern when opening a resource and wanting to propagate a close error:

```go
package store

import (
	"context"
	"database/sql"
	"fmt"
)

func withTx(ctx context.Context, db *sql.DB, fn func(*sql.Tx) error) (err error) {
	tx, err := db.BeginTx(ctx, nil)
	if err != nil {
		return fmt.Errorf("begin: %w", err)
	}

	defer func() {
		if err != nil {
			_ = tx.Rollback() // Rollback error is secondary; original err is more important
			return
		}
		err = tx.Commit() // commit error replaces a nil err — the named return captures it
	}()

	return fn(tx)
}
```

**What happens here:**

1. `err` is the named return variable.
2. `fn(tx)` is the body. If it returns an error, `err` is non-nil when the defer fires.
3. On error: `Rollback` is called and its error is ignored (the primary error is in `err`).
4. On success (`fn` returned `nil`): the defer fires with `err == nil`, so `Commit` runs. If `Commit` fails, the named return `err` is assigned that failure — the caller sees the commit error.

This pattern appears throughout real Go codebases as `withTx` or `runInTx`.

## Rules and syntax

1. **Named return + defer** — use `=` not `:=` when assigning inside the body; `:=` creates a new variable that does not affect the named return.

2. **`var err error` outside a loop** is not a loop variable. All deferred closures inside the loop capture the same `err`. Snapshot with `captured := err` and pass by value to the defer.

3. **errgroup tasks** — `g.Go(func() error { return work(ctx, id) })`. Copy `id` explicitly (or rely on Go 1.22+ per-iteration semantics). Do not copy `ctx` — cancellation is intentional.

4. **HTTP error factory** — `func(deps) ErrorWriter` or `func(deps) func(http.Handler) http.Handler`. The factory runs once at server construction; the returned closure runs per request.

5. **Do not defer a log in a tight loop** unless you want the log at function exit, not at iteration time. Log immediately and return.

6. **`errors.Is` and `errors.As`** work through `%w`-wrapped chains regardless of which closure layer added the wrapping.

7. **Test closures through their contract** — inject a fake `write ErrorWriter`, a stub `fn`, or a controlled `isRetryable`. Do not test the factory by running a full server.

## Examples

### Example A — Predict the result (named return + defer wrap)

```go
package main

import (
	"errors"
	"fmt"
)

var ErrBase = errors.New("base error")

func risky() (_ string, err error) {
	defer func() {
		if err != nil {
			err = fmt.Errorf("risky: %w", err)
		}
	}()

	return "", ErrBase
}

func main() {
	_, err := risky()
	fmt.Println(err)
	fmt.Println(errors.Is(err, ErrBase))
}
```

**Answer:**

```
risky: base error
true
```

#### What happens here

The defer wraps `ErrBase` with context. `errors.Is` still unwraps the chain and finds `ErrBase`. Wrapping adds context without hiding the type.

### Example B — Predict the result (shadowed `:=` breaks named return)

```go
package main

import (
	"errors"
	"fmt"
)

var ErrBase = errors.New("base error")

func risky() (_ string, err error) {
	defer func() {
		if err != nil {
			err = fmt.Errorf("risky: %w", err)
		}
	}()

	_, err2 := fmt.Println("work") // err2, not err
	_ = err2
	return "", ErrBase // err is set here by the return statement
}

func main() {
	_, err := risky()
	fmt.Println(errors.Is(err, ErrBase))
}
```

**Answer:**

```
work
true
```

#### What happens here

`err2 := ...` does not touch the named `err`. The `return "", ErrBase` assigns to the named `err`. The defer fires and wraps it. The subtle point: if you had written `err := compute()` inside the body, that `:=` would shadow the named `err`, and the defer would see `nil` for the named one.

### Example C — Predict the result (shared `err` in loop)

```go
package main

import (
	"fmt"
	"io"
)

func main() {
	var err error
	errs := []error{nil, io.EOF, nil}

	for _, e := range errs {
		err = e
		defer func() {
			if err != nil {
				fmt.Println("deferred:", err)
			}
		}()
	}
}
```

**Answer:**

```
(no output)
```

#### What happens here

After the loop, `err == nil` (last element is `nil`). All three deferred closures capture the same `err` and all see `nil`. `io.EOF` is silently lost. This is the shared `err` trap.

### Example D — Predict the result (errgroup first error wins)

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"io"
	"os"

	"golang.org/x/sync/errgroup"
)

func main() {
	g, _ := errgroup.WithContext(context.Background())
	g.Go(func() error { return io.EOF })
	g.Go(func() error { return os.ErrPermission })
	g.Go(func() error { return nil })

	err := g.Wait()
	fmt.Println(err != nil)
	fmt.Println(errors.Is(err, io.EOF) || errors.Is(err, os.ErrPermission))
}
```

**Answer:**

```
true
true
```

#### What happens here

`errgroup.Wait` returns the **first** non-nil error seen. The exact error depends on goroutine scheduling. Both `io.EOF` and `os.ErrPermission` are possible results; the third goroutine returns `nil` and does not affect the group error. The output is deterministically `true` for both lines because at least one of the two errors is always returned.

### Example E — Predict the result (`WithErrors` factory)

```go
package main

import (
	"errors"
	"fmt"
	"net/http"
	"net/http/httptest"
)

var ErrNotFound = errors.New("not found")

type ErrWriter func(http.ResponseWriter, *http.Request, error)

func WithErrors(write ErrWriter, fn func(http.ResponseWriter, *http.Request) error) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		if err := fn(w, r); err != nil {
			write(w, r, err)
		}
	}
}

func main() {
	write := func(w http.ResponseWriter, r *http.Request, err error) {
		if errors.Is(err, ErrNotFound) {
			w.WriteHeader(http.StatusNotFound)
			fmt.Fprintln(w, "not found")
		}
	}

	handler := WithErrors(write, func(w http.ResponseWriter, r *http.Request) error {
		return ErrNotFound
	})

	rr := httptest.NewRecorder()
	handler.ServeHTTP(rr, httptest.NewRequest(http.MethodGet, "/", nil))
	fmt.Println(rr.Code)
}
```

**Answer:**

```
404
```

#### What happens here

`WithErrors` returns a closure over `write` and `fn`. The inner closure is the actual HTTP handler. It calls `fn`; `fn` returns `ErrNotFound`; `write` maps it to 404. No switch statement in the handler itself.

### Example F — Predict the result (retry + context cancel)

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"io"
	"time"
)

func retry(ctx context.Context, n int, fn func(context.Context) error) error {
	var last error
	for i := 0; i < n; i++ {
		last = fn(ctx)
		if last == nil {
			return nil
		}
		select {
		case <-ctx.Done():
			return fmt.Errorf("cancelled after %d attempts: %w", i+1, ctx.Err())
		case <-time.After(1 * time.Millisecond):
		}
	}
	return fmt.Errorf("all %d attempts failed: %w", n, last)
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 5*time.Millisecond)
	defer cancel()

	attempts := 0
	err := retry(ctx, 100, func(ctx context.Context) error {
		attempts++
		return io.EOF // always fails
	})

	fmt.Println(err != nil)
	fmt.Println(errors.Is(err, context.DeadlineExceeded))
	fmt.Println(attempts < 100)
}
```

**Answer:**

```
true
true
true
```

#### What happens here

The context times out after 5 ms. The `select` detects `ctx.Done()` before reaching attempt 100. The returned error wraps `context.DeadlineExceeded`. The closure passed to `retry` captures `attempts` from the outer `main` scope — that is a legitimate use of a closure for per-run state.

## Decision analysis

| Situation | Technique | Why |
|---|---|---|
| All exit paths must add error context | Named return + defer wrap | One defer instead of `fmt.Errorf` at every `return` |
| Per-iteration error in a deferred log | Pass by value: `defer func(e error){...}(err)` | `err` is not a loop variable; snapshot prevents seeing last value |
| Fan-out with first-error semantics | `errgroup.WithContext` + closure per id | Structured concurrency; context cancels remaining work |
| Fan-out collecting all errors | `sync.WaitGroup` + `mu + []error` + `errors.Join` | `errgroup` discards secondary errors |
| Uniform HTTP error mapping | `WithErrors(write, fn)` factory | Single mapping closure; handlers stay focused on domain logic |
| Transient failure recovery | `Retry(ctx, n, isRetryable, fn)` closure | Encapsulates backoff; caller passes policy as a function |
| Transaction wrapping | `withTx(ctx, db, func(*sql.Tx) error)` | Commit/rollback logic in one place; named return captures commit error |

---

## Trade-offs

- **Named return + defer**: enriches all paths automatically, but defers add an extra stack frame and can hide shadowing bugs if `:=` is used accidentally inside the body.
- **errgroup first-error**: simplest API, but discards secondary errors. Use a multi-error approach when you need a full failure report.
- **`WithErrors` factory**: centralizes mapping but couples all routes to one error vocabulary. If different route groups need different mapping strategies, use separate factories.
- **Retry closure**: decouples policy (`isRetryable`, `backoff`) from the operation. Risk: an overly broad `isRetryable` retries non-idempotent operations.
- **`withTx` helper**: clear and reusable, but may obscure transaction boundaries from code review if overused. Name it clearly.

---

## Common mistakes

1. **`:=` instead of `=` in a named-return function** — creates a local shadow; the named return stays unaffected; the defer never fires.
2. **`var err error` + defer in a loop** — all defers see the last assignment, not per-iteration values.
3. **Copying `ctx` in errgroup** — `id := id` is good; `ctx := ctx` copies a value that should be shared for cancellation.
4. **`Rollback` return value ignored unconditionally** — in `withTx`, ignore `Rollback` only when `err != nil`. On success, `Commit` is called; `Rollback` after commit returns `sql.ErrTxDone`, not a real error.
5. **Writing error details to the HTTP response** — stack traces, SQL errors, or internal IDs in a client response are a security disclosure. Use the `ErrorWriter` to log internally and send a safe code to the client.
6. **Retrying non-idempotent operations** — a `POST` that inserts a row and fails after the insert must not be blindly retried. Use idempotency keys or inspect a durable result.
7. **Blocking `errgroup` goroutines after cancellation** — if `fn` does not check `ctx.Done()`, the cancelled goroutines keep running; the group waits for all of them before returning.
8. **Ignoring `errors.Join` return value** — `errors.Join(nil, nil)` returns `nil`. Always check the return value.
9. **Global `var errWriter ErrorWriter`** — races in tests that swap the global. Use the factory pattern to inject per-handler writers.
10. **Treating commit failure as safe** — if `Commit` returns an error, the transaction state on the server is undefined. Do not retry commit without checking whether it actually succeeded.

---

## Idiomatic Go

- Name `withTx`, `WithErrors`, `Retry` by role, not by mechanism (`makeWrapper`, `fn2`).
- Inject `ErrorWriter`, `isRetryable`, and logger as function parameters captured in a closure — not as package-level globals.
- Use `errors.Join` (Go 1.20+) for multi-error collection and verify with `errors.Is` in tests.
- Keep `errgroup` goroutine closures short: capture the operation input, call one function, return the wrapped error.
- Document in the package comment who is responsible for calling `Rollback`/`Commit` in a `withTx` helper.
- In code review, when you see `var err error` before a loop with `defer`, ask: "which value of `err` will the defer see?" If the answer is "the last one", that is a bug.

## Practical scenario

A payment service has three steps: validate input, reserve balance, write audit log. All three must be atomic. The team starts with:

```go
// version 1 — broken
func (s *Service) Pay(ctx context.Context, req PayRequest) error {
	var err error
	for _, step := range []func() error{s.validate, s.reserve, s.audit} {
		err = step()
		defer func() {
			if err != nil {
				slog.Error("payment step failed", "err", err)
			}
		}()
	}
	return err
}
```

Problems identified in review:
1. Three defers accumulate until `Pay` returns — log fires after the response is already sent.
2. `err` is shared — if `validate` fails and `reserve` and `audit` succeed, the defers all see `nil`.
3. No transaction: a partial failure leaves the balance reserved without an audit entry.

**Version 2 — correct:**

```go
func (s *Service) Pay(ctx context.Context, req PayRequest) (err error) {
	defer func() {
		if err != nil {
			slog.Error("payment failed", "err", err)
		}
	}()

	return withTx(ctx, s.db, func(tx *sql.Tx) error {
		if err := s.validate(req); err != nil {
			return fmt.Errorf("validate: %w", err)
		}
		if err := s.reserveInTx(ctx, tx, req); err != nil {
			return fmt.Errorf("reserve: %w", err)
		}
		if err := s.auditInTx(ctx, tx, req); err != nil {
			return fmt.Errorf("audit: %w", err)
		}
		return nil
	})
}
```

Changes:
- One named-return defer logs the final error.
- `withTx` handles transaction lifecycle; `Rollback` is called on any step failure.
- Each step returns immediately on error with `%w` wrapping for the caller context.
- The deferred log fires after `withTx` returns, at which point the result is definitive.

### Checklist before merging code with closures and errors

- [ ] Named returns with defer: no `:=` in the body that shadows the named variable
- [ ] `var err error` before a loop: no defer inside the loop that reads that `err`
- [ ] `errgroup.Go` closures: `id` copied per iteration; `ctx` shared
- [ ] `ErrorWriter` factory: injected at construction, not from a global
- [ ] Retry: `isRetryable` checked; context cancellation exits the loop
- [ ] `withTx` commit error: propagated through named return, not discarded

## Check questions

1. **What does `defer func() { if err != nil {...} }()` capture when `err` is a named return?**
   The named return variable — the same binding that the function body writes to before returning.

2. **Why does `var err error` before a loop break the per-iteration error pattern?**
   `err` is not a loop variable; Go 1.22+ per-iteration semantics apply only to variables declared as part of the `for` statement. All defers inside the loop capture the same `err` and see its final value.

3. **What is the idiomatic fix for logging a per-iteration error in a defer?**
   Pass the error by value: `defer func(e error) { log(e) }(err)`. The argument is evaluated at the defer statement, not when the function exits.

4. **What does `errgroup.WithContext` guarantee when one goroutine returns an error?**
   The derived context is cancelled. Other goroutines must check `ctx.Done()` to exit early; the group returns only after all goroutines have returned.

5. **Why does `WithErrors` take an `ErrorWriter` as a parameter instead of using a package-level variable?**
   Dependency injection through a closure makes the handler testable (inject a fake writer), thread-safe (no shared mutation), and composable (different route groups can use different writers).

6. **In `withTx`, when is `Rollback` called and when is `Commit` called?**
   Defer fires on any exit: if `err != nil` (from `fn` or `BeginTx`), `Rollback` is called; if `err == nil`, `Commit` is called and its return replaces `err` through the named return.

7. **What does `errors.Join(nil, io.EOF, nil)` return?**
   A non-nil joined error that wraps `io.EOF`. `errors.Is(result, io.EOF)` returns `true`.

8. **Why should retry logic check `ctx.Done()` between attempts rather than only inside `fn`?**
   If `fn` does not respect the context (e.g. it calls a library that ignores it), the retry loop would sleep through the backoff and start another attempt after the deadline has passed.

---

## Summary

Closures and error management meet at four specific points in Go production code: **named return + defer** for automatic error enrichment, **shared `var err error` in a loop** (a trap fixed by value parameters or immediate returns), **errgroup fan-out** (where per-goroutine closure binding determines which work belongs to which result), and the **`WithErrors` factory** (where a single closure replaces repeated status-code switch statements across all routes). The binding rule is always the same: the closure captures the variable, not the value — knowing which variable is captured is the difference between correct error handling and a silent data loss.
