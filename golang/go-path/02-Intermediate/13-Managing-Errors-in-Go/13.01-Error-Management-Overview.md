# 13.01 Error management overview

> **Go Path - Zero to Gopher** / **02 Intermediate → Managing Errors in Go** / Lesson 13.01

## Lesson goals

After this lesson you should:

- treat `error` as an interface with one method `Error() string`, and an error as a value you return, wrap, and test
- check the error immediately after the call that returns it, before you use the other results
- understand why Go deliberately chooses explicit errors instead of exceptions for expected failure
- recognize the classic trap: a `nil` pointer inside an `error` interface is **not** `== nil`
- avoid the blank identifier `_` for an error without a clearly written reason
- build habits that later lessons deepen (types, `errors.Is` / `errors.As`, panic, tests)

## Prerequisite

- Go 1.22+ installed; you know how to run `go run` and `go test`
- Basics path: functions, multiple return, interfaces, zero value, pointer
- preferred: brief experience with `fmt.Errorf` and `errors.New` (seeing the syntax is enough)
- preferred: 10.14 (difference between a log message and a public message to the client)

If you are not sure what an interface is: in this lesson we start from scratch for `error`, step by step, with concrete values.

## Problem this lesson solves

An ignored error turns partial failure into a silent bug. Typical form:

```go
data, _ := os.ReadFile(path)
// further you “successfully” parse an empty slice
```

Consequences in practice: empty config, zero in the balance, HTTP 200 with an empty body, an audit trail that “exists” but was never written. Go deliberately makes errors explicit — you see `if err != nil` and know failure is part of the API. This lesson sets the mental model: an error is data about the outcome, not a side path and not an exception that “flies” past return.

A second, subtler problem: a function returns an `error` that “looks like nil” in the debugger (the inner pointer is `nil`), but the check `err != nil` still passes. That is the nil-interface trap. Here we unpack it fully.

## Mental model

1. **`error` is an interface** — any type with method `Error() string` satisfies the contract.
2. **An error is a value** — you can return it, store it in a variable, wrap it, pass it, test it.
3. **Check immediately** — close to where it arises, while you still have context (path, ID, step).
4. **Return or handle** — do not swallow without a decision; blank identifier requires a reason in a comment.
5. **`err == nil` is not the same as “no pointer inside”** — an interface has type + value; both must be “empty” for the interface to be nil.
6. **Panic is not a business error** — panic is for programmer impossibility (lesson 13.03).
7. **Client ≠ log** — internal detail stays inside; the client gets a safe, generic message.

## Mechanism

This section is the core of the lesson. Follow it in order: first what `error` is, then how it is returned, then how it is checked, then the nil trap with numbers and types, then blank identifier, then the process boundary.

### 1. Interface `error` in the standard library

In package `builtin` (always available, no import) stands:

```go
type error interface {
	Error() string
}
```

That is the **entire** contract. No magic, no special keyword for “throw”. If a type has method `Error() string` with a value or pointer receiver, a value of that type can sit in a variable of type `error`.

Example type that satisfies the contract:

```go
type SimpleErr struct {
	Msg string
}

func (e SimpleErr) Error() string {
	return e.Msg
}
```

Call:

```go
var err error = SimpleErr{Msg: "disk full"}
fmt.Println(err.Error()) // "disk full"
fmt.Println(err)         // same via fmt, because fmt calls Error()
```

**Trace with values**

| Step | What `err` holds | Type in the interface | Dynamic value |
|-------|----------------|------------------|--------------------|
| after assignment | not nil | `SimpleErr` | `{Msg: "disk full"}` |
| `err.Error()` | — | — | returns `"disk full"` |

### 2. Multi-return: error as the last result

Convention in Go APIs:

```go
func ReadConfig(path string) (Config, error)
```

The last return is `error`. If `err != nil`, the other results are **suspect** — often zero value (`Config{}`, `0`, `nil` slice, `""`). Idiom:

```go
cfg, err := ReadConfig("/etc/app.json")
if err != nil {
	return err // or wrap, or log at the boundary
}
// only now use cfg
```

**Why last?** Because the eye for `if err != nil` “falls” on the end of the list; readers and linters expect that shape. If you put the error in the middle, you break the expectation of the whole ecosystem.

### 3. Why not exceptions for expected failure

In languages with exceptions, `FileNotFound` often “flies” through the stack. In Go:

- expected failure (no file, bad JSON, timeout) = `error` value
- unexpected programmer catastrophe (broken invariant) = `panic` (rare; see 13.03)

Gain of explicitness:

- you see all failure paths in the signature and in the body
- review easily asks “where is the error swallowed”
- tests target concrete return values

Cost: more lines of `if err != nil`. That is intentional — flow readability > brevity.

### 4. Creating a simple error: `errors.New` and `fmt.Errorf`

```go
import (
	"errors"
	"fmt"
)

err1 := errors.New("not found")
err2 := fmt.Errorf("user %s not found", "42")
```

- `errors.New` — fixed message, good for a sentinel (detail in 13.02)
- `fmt.Errorf` — formatted message; with `%w` keeps the cause for the chain (detail in 13.02 and 13.04)

In this lesson it is enough: an error is an object that can say a string about itself.

### 5. Classic trap: nil pointer inside an `error` interface

This is the most important deep part of 13.01. Read slowly.

An interface at runtime is not one address. Conceptually it holds **two** fields:

1. **type** (which concrete type is inside)
2. **value** (data of that type — e.g. a pointer)

An interface is `nil` **only** when **both** fields are empty (no type, no value).

Now imagine:

```go
type MyError struct {
	Code int
}

func (e *MyError) Error() string {
	return fmt.Sprintf("code=%d", e.Code)
}

func returnsNilPointerAsError() error {
	var p *MyError = nil // pointer is nil
	return p            // BUT: type *MyError enters the interface!
}

func main() {
	err := returnsNilPointerAsError()
	if err != nil {
		fmt.Println("err != nil, and that is TRUE for Go")
		// caution: err.Error() here can panic (nil receiver)!
	} else {
		fmt.Println("err == nil")
	}
}
```

**Step-by-step trace**

| Step | Expression | Type component | Value component | `== nil`? |
|-------|-------|----------------|---------------------|-----------|
| 1 | `var p *MyError = nil` | `*MyError` | `nil` | yes, for the pointer |
| 2 | `return p` as `error` | `*MyError` | `nil` | **no** — the interface has a type! |
| 3 | `err := ...` | `*MyError` | `nil` | `err != nil` is **true** |
| 4 | `err.Error()` | — | calls method on nil pointer | often **panic** |

Why do people fall into this? They write:

```go
func Do() error {
	var err *MyError
	if bad {
		err = &MyError{Code: 1}
	}
	return err // when !bad, returns type *MyError + nil value
}
```

**Fix 1 — return typed nil explicitly as “no error”:**

```go
func Do() error {
	if bad {
		return &MyError{Code: 1}
	}
	return nil // here the interface has neither type nor value
}
```

**Fix 2 — hold the error in a variable of type `error`:**

```go
func Do() error {
	var err error // zero value of the interface = real nil
	if bad {
		err = &MyError{Code: 1}
	}
	return err
}
```

**Predict the result (mental exercise)**

What does this print:

```go
var p *MyError
var e1 error = p
var e2 error = nil
fmt.Println(e1 == nil, e2 == nil)
```

**Answer:** `false true` — `e1` carries type `*MyError`, `e2` is a real nil interface.

We repeat this trap in 13.04 when you do type assertion and custom types. Remember the rule: **never return a variable of type `*T` directly as `error` if it can be nil; return `nil` or hold it in an `error` variable.**

### 6. Check immediately — why not “later”

Bad pattern:

```go
a, err1 := step1()
b, err2 := step2()
c, err3 := step3()
if err1 != nil || err2 != nil || err3 != nil {
	// which step? which context? is b valid if step1 failed?
}
```

Good pattern:

```go
a, err := step1()
if err != nil {
	return fmt.Errorf("step1: %w", err)
}
b, err := step2()
if err != nil {
	return fmt.Errorf("step2: %w", err)
}
```

Advantages: context in the message, early exit, you do not use `b` if `a` failed, easy branch testing.

### 7. Blank identifier `_` and error

The blank identifier discards a value. For an error that means: **you consciously ignore failure**.

Allowed only with a reason, e.g.:

```go
// Best-effort metric ping; failure must not interrupt the request.
_, _ = metrics.Inc("handled")
```

Or when the API returns a value you do not need, **but you still check the error**:

```go
n, err := w.Write(buf)
if err != nil {
	return err
}
_ = n // byte count does not matter in this layer
```

Forbidden without a reason:

```go
data, _ := os.ReadFile(path) // silent bug
```

### 8. Wrap context at the layer boundary (preview)

```go
b, err := os.ReadFile(path)
if err != nil {
	return nil, fmt.Errorf("load config %s: %w", path, err)
}
```

`%w` keeps the cause so later `errors.Is` / `errors.As` work through the chain (13.02, 13.04). In this lesson remember: **add where and what**, do not swallow.

### 9. Process boundary: `main`, CLI, HTTP

Inside a library: return `error`.
At the process edge: log, choose exit code or HTTP status, do not “continue with zero value”.

```go
func main() {
	if err := run(); err != nil {
		fmt.Fprintf(os.Stderr, "startup failed: %v\n", err)
		os.Exit(1)
	}
}
```

Fail closed: better that the process does not start than that it runs with half state.

## Rules and syntax

1. **Contract:** a type is `error` if it has `Error() string`.
2. **Convention:** error is the last return; when `err != nil` do not trust the other results.
3. **Check:** immediately after the call; do not accumulate errors “for the end” without reason.
4. **Nil interface:** `return nil` or `var err error` — not `return` of a nil pointer of type `*MyError`.
5. **Blank identifier:** `_` for an error only with a comment stating the reason; a linter (`errcheck`, `staticcheck`) should yell.
6. **Messages:** lowercase, short, no trailing period (`"open config"`), per Go style.
7. **Wrap:** `fmt.Errorf("op: %w", err)` when you raise a layer; `%v` loses the chain for Is/As.
8. **Panic:** do not use for expected I/O or validation.
9. **Boundary:** in `main` / HTTP handler decide: log + status/exit; do not leak SQL/stack to the client.
10. **Zero value with error:** return `T{}` / `nil` / `0` with `err`; the caller must see `err` first.

Minimal idiom:

```go
v, err := Do()
if err != nil {
	return fmt.Errorf("do: %w", err)
}
use(v)
```

## Examples

### Example 1 — check immediately and wrap

```go
package errintro

import (
	"fmt"
	"os"
)

func Load(path string) ([]byte, error) {
	b, err := os.ReadFile(path)
	if err != nil {
		return nil, fmt.Errorf("load %s: %w", path, err)
	}
	return b, nil
}
```

### What happens here

`os.ReadFile` returns `(data, error)`. If the file does not exist, `b` is `nil`, `err` is not nil. We do not parse further — we immediately return a wrapped error with the path. The caller sees context in the log; `errors.Is(err, os.ErrNotExist)` can still work because of `%w`.

### Predict the result

If `path` points to a nonexistent file, what is a typical shape of `err.Error()` (content, not the exact OS text)?

**Answer:** starts with `load <path>: ` and then the OS message (e.g. `no such file or directory`). What matters is that you see **your** prefix + cause.

---

### Example 2 — blank identifier: bad then fix

```go
package errintro

import "os"

// WEAK (don't):
// data, _ := os.ReadFile(path)
// return string(data), nil

func MustReadForDemo(path string) ([]byte, error) {
	return os.ReadFile(path)
}
```

### What happens here

The weak pattern hides failure and lies to the caller that everything is fine. The fix returns the error untouched. The name `MustReadForDemo` here does **not** panic — in Go `Must*` usually panics (see 13.03); this demo only shows that “must” in the name is not an excuse for `_`.

### Predict the result

What happens if the caller does `b, _ := MustReadForDemo(path)` and `path` does not exist, then `len(b)`?

**Answer:** `len(b)` is `0`; the program continues as if it “successfully read an empty file”. Silent bug.

### Example 3 — boundary in `main`

```go
package main

import (
	"fmt"
	"os"

	"example.com/shop/errintro"
)

func main() {
	b, err := errintro.Load("config.json")
	if err != nil {
		fmt.Fprintf(os.Stderr, "startup failed: %v\n", err)
		os.Exit(1)
	}
	fmt.Printf("loaded %d bytes\n", len(b))
}
```

### What happens here

The process fails closed. Exit code `1` lets the orchestrator (systemd, Kubernetes, CI) react. No “continue with empty config”.

### Predict the result

If `config.json` exists and has 12 bytes, what goes to stdout?

**Answer:** `loaded 12 bytes`. Nothing on stderr; exit code 0.

### Example 4 — helper that does not swallow

```go
package errintro

import "io"

func CopyAll(w io.Writer, r io.Reader) error {
	_, err := io.Copy(w, r)
	return err
}
```

### What happens here

We discard the byte count with `_` **on purpose** — not the error. A thin wrapper does not log inside; the caller chooses treatment (retry, 500, CLI message).

### Predict the result

Is `_` here a violation of the lesson rule?

**Answer:** No — the `int64` byte count is ignored, not the error. The error is returned.

### Example 5 — multiple steps, validation as `error`

```go
package errintro

import (
	"encoding/json"
	"fmt"
)

type Cfg struct {
	Port int `json:"port"`
}

func ParseCfg(b []byte) (Cfg, error) {
	var c Cfg
	if err := json.Unmarshal(b, &c); err != nil {
		return Cfg{}, fmt.Errorf("unmarshal: %w", err)
	}
	if c.Port < 1 || c.Port > 65535 {
		return Cfg{}, fmt.Errorf("invalid port %d", c.Port)
	}
	return c, nil
}
```

### What happens here

Each step has its own branch. An invalid port is a normal `error`, not panic. Zero value `Cfg{}` goes with the error — the caller must not use `c.Port` before checking.

### Predict the result

Input `{"port":0}` — what does the function return?

**Answer:** `Cfg{}`, and an `error` whose message contains `invalid port 0`. JSON succeeded; validation failed.

### Example 6 — HTTP boundary without leaking

```go
package errintro

import "net/http"

func Handler(load func() error) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		if err := load(); err != nil {
			// log internally elsewhere (slog with request id)
			http.Error(w, "unavailable", http.StatusServiceUnavailable)
			return
		}
		w.WriteHeader(http.StatusNoContent)
	}
}
```

### What happens here

The internal error does not leak into the body. Status is generic 503. Detail stays for the log (10.14).

### Predict the result

If `load` returns `fmt.Errorf("sql: connection refused")`, what does the HTTP client see in the body?

**Answer:** text `unavailable` (plus the newline that `http.Error` adds), **not** the SQL message. Status 503.

### Example 7 — nil interface trap in a full program

```go
package main

import "fmt"

type Boom struct{ N int }

func (b *Boom) Error() string { return fmt.Sprintf("boom %d", b.N) }

func broken() error {
	var e *Boom
	if false {
		e = &Boom{N: 1}
	}
	return e // type *Boom + nil
}

func fixed() error {
	var e error
	if false {
		e = &Boom{N: 1}
	}
	return e // real nil
}

func main() {
	fmt.Println("broken == nil?", broken() == nil) // false
	fmt.Println("fixed == nil?", fixed() == nil)   // true
}
```

### What happens here

`broken` always returns a “non-nil” interface. The caller thinks there is an error and enters the error branch — or, worse, calls `Error()` and panics on a nil receiver.

### Predict the result

Output of the `main` function?

**Answer:**

```
broken == nil? false
fixed == nil? true
```

### Example 8 — using the result before the check (anti-example)

```go
package errintro

import (
	"encoding/json"
	"fmt"
)

func PortOrBust(b []byte) int {
	var c Cfg
	err := json.Unmarshal(b, &c)
	// WEAK: use c.Port before the check
	fmt.Println("port before check:", c.Port)
	if err != nil {
		return -1
	}
	return c.Port
}
```

### What happens here

On bad JSON, `c` is zero value; printing `0` misleads. Fix: first `if err != nil`, only then read fields.

### Predict the result

Input `not-json` — what is printed before return?

**Answer:** `port before check: 0`, then the function returns `-1`. The message confuses because it looks like “port is zero”, while unmarshal actually failed.

## Decision analysis

| Decision | Options | Why we choose |
|--------|--------|--------------|
| Error as value vs exception | return `error` / throw | explicit flow, easier review |
| When to check | immediately / at end of function | immediately = context + no false use |
| What to return with err | zero value / partial result | zero value + document; partial only if contract is clear |
| Ignore error | `_` / log / return | only `_` with reason; otherwise return or conscious policy |
| Nil typed errors | `return p` / `return nil` | always `nil` or `var err error` |
| Message to client | `err.Error()` / generic text | generic; detail in log |
| Message style | lowercase short / sentence with period | Go convention: lowercase, no trailing period |
| Wrap | `%w` / `%v` / nothing | `%w` when you need Is/As through a layer |

## Trade-offs

- **More `if err != nil`:** noise in the diff, but fewer hidden paths. Helpers and good wrap reduce the pain.
- **Too much context in wrap:** messages become novels; be precise (`op`, `id`), do not dump whole structs.
- **Zero value with error:** forces caller discipline; if they forget the check, they use “empty” — so linters and tests must protect the habit.
- **Strictly forbidden `_`:** sometimes best-effort metrics may truly fail; then a comment + a metric of ignored error count.
- **Fail closed in `main`:** a restart loop must exist in orchestration; otherwise a “black screen” without auto-heal.

## Common mistakes

1. `v, _ := ...` without reason — silent bug.
2. Using `v` before `if err != nil`.
3. Returning a `*MyError` nil pointer as `error` — `err != nil` lies.
4. Panic for validation or “file not found”.
5. `log.Println(err); return nil` — hiding failure from the caller.
6. Comparing `err.Error() == "..."`.
7. Leaking `err.Error()` to the HTTP client.
8. Delaying the check “for later” in a long function.
9. Wrap with `%v` then wondering why `errors.Is` does not work.
10. Mixing “no error” and “error with empty message”.

## Idiomatic Go

- Error last return; name `err` locally.
- Lowercase messages; exported sentinels in 13.02.
- Wrap at package boundaries: `fmt.Errorf("pkg.Op: %w", err)`.
- Check immediately; early return instead of deep nesting.
- At the edge: `slog` + status/exit; inside only `return err`.
- Test error paths as seriously as the happy path (13.05).
- Enable `staticcheck` / `errcheck` in CI so `_` does not pass silently.
- Document in the function comment which sentinel/error type the caller may expect.

## Practical scenario

A sales service ignores the audit write error:

```go
_, _ = audit.Write(event) // “audit is not critical”
```

A month later forensics has no trail for disputed transactions. The team introduces a policy: audit failure either (a) fails the request with 503, or (b) goes into a reliable outbox queue with retry. Explicit error restores reliability. In the same sprint the linter forbids `_` on `error` without `//nolint:errcheck` + an explanation.

Second incident: helper `func lastErr() error { var e *SoftError; return e }` in middleware. Every request enters the “error” branch and returns 500 even though everything succeeded. Fix: `return nil`. The nil-interface lesson from this page becomes a mandatory onboarding point.

### Additional trace: what `fmt` does with `error`

When you write `fmt.Println(err)` or `fmt.Errorf("x: %v", err)`, `fmt` checks whether the value implements `error` (or `Stringer`). If it is `error`, it calls `Error() string`. So your `Error()` method is not only “for humans in the debugger” — it is also the entry into logs, wrap messages, and test output.

**Consequence:** do not put secrets in `Error()` (token, password, full SQL with data). Even if the handler does not leak to the client, the log aggregator often has a wider reader circle.

### Mini exercise with solution — check order

Code:

```go
func loadAndCount(path string) (int, error) {
	b, err := os.ReadFile(path)
	n := len(b)
	if err != nil {
		return 0, err
	}
	return n, nil
}
```

**Question:** Is `n := len(b)` before the check safe?

**Answer:** For `os.ReadFile` on error `b` is usually `nil`, so `len` is 0 and does not panic — but **the style is bad**: you teach the eye that it is OK to use the result before the check. With another API a partial result can be invalid. Idiom: first `err`, then `len(b)`.

### Comparison table — what to do with an error

| Situation | Action |
|-----------|--------|
| Library / service layer | `return fmt.Errorf("op: %w", err)` |
| CLI `main` | stderr + `os.Exit(1)` |
| HTTP handler | log internally + generic status |
| Best-effort metric | `_ = m.Inc()` + comment with reason |
| Unfixable boot invariant | panic / Must (13.03) |

### How to read someone else’s Go code

1. Find all `if err != nil`.
2. Look for `_` next to calls that return `error`.
3. Look for `return err` where `err` is a `*T` variable.
4. Look for `err.Error()` in the HTTP/JSON response.

Those four scans catch most bugs from this lesson.

## Summary

`error` is an interface with `Error() string`. Errors are values: check them immediately, wrap context, do not swallow them without reason. Remember: a nil pointer in an interface is **not** a nil interface — return a real `nil` or hold the error in an `error` variable. Panic is not a substitute for expected failure; the client does not see internal detail. The next lesson builds types: sentinel, struct errors, validation lists.
