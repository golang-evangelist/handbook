# 13.06 Responding to Channel Errors

> **Go Path - Zero to Gopher** / **02 Intermediate → Managing Errors in Go** / Lesson 13.06

## Lesson goals

After this lesson you should:

- send result and `error` together through one channel of type `struct { Value T; Err error }`
- not share one `error` variable between multiple goroutines without synchronization
- choose between result channel and separate error channel consciously, with buffer and ownership
- close the channel exactly once (one owner) and read until all results arrive or a fatal error
- use `select` with `context.Context` to avoid deadlock when producer fails or job is canceled

## Prerequisite

- goroutine and channel basics (send, receive, close, range)
- `error` interface, `errors.Is`, `errors.As` from previous lessons in 13.xx
- `context` package at cancel / Done level
- Go 1.22+ (`go.mod` target 1.22 or newer)

## Problem

In concurrent code `return err` from a worker function is not enough — the error must reach the coordinator. If you only close the channel without a signal, the consumer thinks everything is fine. If multiple goroutines write to the same `var err error` without a mutex, you have a data race. If you send on an unbuffered channel after cancel, you hang. This lesson gives defensive patterns: **channel of results**, ownership of close, and a clear “value or error” contract.

## Mental model

1. **Result** — value **or** error (sometimes both in same structure: partial success + `Err`).
2. **One owner** closes the channel; everyone else only sends or reads.
3. **Coordinator** reads until it gets N results or first fatal error.
4. **No shared `err`** — do not share one variable between goroutines; send `error` through channel or collect under mutex you explicitly control.
5. **Context** — cancellation reduces work after error (more in 13.07 with `errgroup`).
6. **No lost error** — do not log and continue as success; error must reach boundary (handler, CLI, API).

## Mechanism

### Why channel of results

When N goroutines do the same kind of work, the cleanest contract is:

```go
type Result[T any] struct {
	Value T
	Err   error
}

results := make(chan Result[string], n)
```

Each worker sends exactly one `Result`. Coordinator reads `n` times (or `range` until channel closes). No race around shared `err`: each error travels with its result.

### Trace 1 — shared `error` variable (wrong)

```go
package badshare

import (
	"fmt"
	"sync"
)

func SumParallel(xs []int) (int, error) {
	var (
		sum int
		err error // shared — data race if multiple workers write
		mu  sync.Mutex
		wg  sync.WaitGroup
	)
	for _, x := range xs {
		wg.Add(1)
		go func(v int) {
			defer wg.Done()
			if v < 0 {
				// even with mu, you lose which task failed and mix errors
				mu.Lock()
				err = fmt.Errorf("negative: %d", v)
				mu.Unlock()
				return
			}
			mu.Lock()
			sum += v
			mu.Unlock()
		}(x)
	}
	wg.Wait()
	return sum, err
}
```

### What happens here

Mutex stops race detector from screaming, but semantics are still bad: last error wins, successful parts mix with failure, and coordinator has no channel of results — only one final `err`. Better for each worker to send its own `Result`.

### Trace 2 — struct {value, err} on channel (correct)

```go
package fanin

import (
	"context"
	"fmt"
)

type Result[T any] struct {
	Value T
	Err   error
	ID    int
}

func FetchAll(ctx context.Context, ids []int, fetch func(context.Context, int) (string, error)) ([]string, error) {
	n := len(ids)
	ch := make(chan Result[string], n) // buffer = n: worker does not block on send

	for _, id := range ids {
		id := id
		go func() {
			v, err := fetch(ctx, id)
			select {
			case ch <- Result[string]{Value: v, Err: err, ID: id}:
			case <-ctx.Done():
				// canceled: short send attempt not required if buffer holds all
			}
		}()
	}

	out := make([]string, 0, n)
	var firstErr error
	for i := 0; i < n; i++ {
		select {
		case <-ctx.Done():
			return out, ctx.Err()
		case r := <-ch:
			if r.Err != nil && firstErr == nil {
				firstErr = fmt.Errorf("id=%d: %w", r.ID, r.Err)
				// policy: collect all or stop — here we collect remaining results
				continue
			}
			if r.Err == nil {
				out = append(out, r.Value)
			}
		}
	}
	return out, firstErr
}
```

### Trace 3 — who closes the channel

```go
package closer

import "sync"

func Produce(n int, work func(int) (int, error)) <-chan Result[int] {
	ch := make(chan Result[int])
	var wg sync.WaitGroup
	wg.Add(n)
	for i := 0; i < n; i++ {
		i := i
		go func() {
			defer wg.Done()
			v, err := work(i)
			ch <- Result[int]{Value: v, Err: err}
		}()
	}
	go func() {
		wg.Wait()
		close(ch) // one owner — helper goroutine
	}()
	return ch
}

type Result[T any] struct {
	Value T
	Err   error
}
```

Consumer does `for r := range ch`. Workers **never** call `close`. Double close panics; close from reader is anti-pattern.

### Trace 4 — separate error channel

Sometimes you want only an error signal, without value:

```go
package errc

import "context"

func Watch(ctx context.Context, run func(context.Context) error) error {
	errCh := make(chan error, 1) // buffer 1: run can finish before you read
	go func() {
		errCh <- run(ctx)
	}()
	select {
	case <-ctx.Done():
		return ctx.Err()
	case err := <-errCh:
		return err
	}
}
```

Buffer 1 prevents hang if `run` finishes before `select`. Without buffer, if nobody reads, sender blocks forever.

### Trace 5 — unbuffered channel + error = deadlock risk

```go
package deadlockrisk

func Bad(n int) {
	ch := make(chan int) // no buffer
	for i := 0; i < n; i++ {
		go func(i int) {
			if i == 0 {
				return // sends nothing — consumer waits forever
			}
			ch <- i
		}(i)
	}
	for i := 0; i < n; i++ {
		<-ch // deadlock when i==0 worker disappears
	}
}
```

Therefore result struct + always one send (even with `Err != nil`) keeps contract: **N sends for N workers**.

### Trace 6 — select with context on send side

```go
package sendctx

import "context"

type Result struct {
	Err error
}

func SafeSend(ctx context.Context, ch chan<- Result, r Result) bool {
	select {
	case ch <- r:
		return true
	case <-ctx.Done():
		return false
	}
}
```

If channel is full and job canceled, you do not hang on send. Coordinator must understand `false` means “we did not deliver result” — that is why buffer = N is often simpler for fan-out/fan-in.

### Trace 7 — aggregation: first error vs all errors

```go
package agg

import (
	"errors"
	"fmt"
)

func FirstError(rs []Result[int]) error {
	for _, r := range rs {
		if r.Err != nil {
			return r.Err
		}
	}
	return nil
}

func AllErrors(rs []Result[int]) error {
	var errs []error
	for _, r := range rs {
		if r.Err != nil {
			errs = append(errs, r.Err)
		}
	}
	return errors.Join(errs...)
}

type Result[T any] struct {
	Value T
	Err   error
}

func Annotate(id int, err error) error {
	if err == nil {
		return nil
	}
	return fmt.Errorf("worker %d: %w", id, err)
}
```

`errors.Join` (Go 1.20+) keeps multiple errors; `errors.Is` / `errors.As` still work through join chain.

### Trace 8 — pipeline: stage sends Result onward

```go
package pipe

import "context"

func MapStage[A, B any](
	ctx context.Context,
	in <-chan Result[A],
	out chan<- Result[B],
	fn func(context.Context, A) (B, error),
) {
	defer close(out)
	for {
		select {
		case <-ctx.Done():
			return
		case r, ok := <-in:
			if !ok {
				return
			}
			if r.Err != nil {
				out <- Result[B]{Err: r.Err}
				continue
			}
			b, err := fn(ctx, r.Value)
			out <- Result[B]{Value: b, Err: err}
		}
	}
}

type Result[T any] struct {
	Value T
	Err   error
}
```

Error **propagates** through stage instead of disappearing. Downstream decides whether to stop or continue.

### Trace 9 — counting: how many results you expect

```go
package count

import "sync/atomic"

type Gate struct {
	left atomic.Int64
}

func NewGate(n int64) *Gate {
	g := &Gate{}
	g.left.Store(n)
	return g
}

func (g *Gate) Done() bool {
	return g.left.Add(-1) == 0
}
```

When you do not use `WaitGroup` + closer goroutine, explicit counter helps know when you may close channel. Still, `WaitGroup` + one closer remains more readable for most teams.

### Trace 10 — test that catches race on shared err

```go
package race_test

import (
	"sync"
	"testing"
)

func TestSharedErrIsRacy(t *testing.T) {
	t.Parallel()
	// run with: go test -race
	var err error
	var wg sync.WaitGroup
	for i := 0; i < 100; i++ {
		wg.Add(1)
		go func(i int) {
			defer wg.Done()
			if i%2 == 0 {
				err = nil // deliberate race
			}
		}(i)
	}
	wg.Wait()
	_ = err
}
```

This test exists to **document** anti-pattern. In production replace with channel of results.

### Semantics of close and zero value

Read from closed channel returns zero value of type. For `chan Result[T]`, zero value has `Err == nil` and empty `Value` — **do not mix** that with successful result. Therefore `ok` from `v, ok := <-ch` or `range` must be part of protocol; do not interpret “got Result{}” as success after close without `ok`.

### Buffer policy in one sentence

- **buffer = N** (number of workers): workers finish without waiting on coordinator; memory O(N).
- **buffer = 0**: backpressure; you need `select` + context on send.
- **buffer = 1** for one error channel: enough for “fire and forget send” with one reader.

## Rules and syntax

1. Result type:

```go
type Result[T any] struct {
	Value T
	Err   error
}
```

2. Sending error **with** value (or without):

```go
ch <- Result[int]{Err: err}           // failure
ch <- Result[int]{Value: 42, Err: nil} // success
```

3. One closer:

```go
go func() { wg.Wait(); close(ch) }()
```

4. Never share `var err error` between goroutines without `sync.Mutex` **and** clear policy (and even then prefer channel).

5. `select` with `ctx.Done()` on receive and, if needed, on send.

6. `errors.Join` for multiple errors; `fmt.Errorf("...: %w", err)` for context per worker ID.

7. Do not close channel from side that reads; do not close multiple times.

8. For Go 1.22+ in loop `for _, id := range ids { go func() { ... id ... }() }` — `id` is per-iteration; still readable to do `id := id` if team wants explicitness for older readers.

## Examples

### Example A — Predict the result

```go
package main

import "fmt"

type Result struct {
	V   int
	Err error
}

func main() {
	ch := make(chan Result, 2)
	ch <- Result{V: 1}
	ch <- Result{Err: fmt.Errorf("boom")}
	close(ch)
	for r := range ch {
		fmt.Printf("v=%d err=%v\n", r.V, r.Err != nil)
	}
}
```

**Answer:**

```
v=1 err=false
v=0 err=true
```

### What happens here

First Result is success. Second carries error; `V` is zero value `0`, but `Err != nil` is the signal. `range` stops after close.

### Example B — Predict the result (how many sends)

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	ch := make(chan int, 3)
	var wg sync.WaitGroup
	for i := 0; i < 3; i++ {
		wg.Add(1)
		go func(i int) {
			defer wg.Done()
			if i == 1 {
				return // disappears without send
			}
			ch <- i
		}(i)
	}
	wg.Wait()
	close(ch)
	n := 0
	for range ch {
		n++
	}
	fmt.Println(n)
}
```

**Answer:**

```
2
```

### What happens here

Worker `i==1` sent nothing. Contract “3 workers ⇒ 3 messages” is broken. With `Result` struct that worker would send `{Err: ...}` or at least empty success — here work silently disappears.

### Example C — Predict the result (buffer error channel)

```go
package main

import "fmt"

func main() {
	errc := make(chan error, 1)
	errc <- fmt.Errorf("x")
	fmt.Println(<-errc)
}
```

**Answer:**

```
x
```

### What happens here

Buffer 1 allows send without parallel goroutine reading. Same code with `make(chan error)` without buffer would deadlock in `main` on send.

### Example D — coordinator picks first error

```go
package main

import (
	"fmt"
)

type R struct {
	Err error
}

func main() {
	ch := make(chan R, 3)
	ch <- R{}
	ch <- R{Err: fmt.Errorf("a")}
	ch <- R{Err: fmt.Errorf("b")}
	close(ch)
	var first error
	for r := range ch {
		if r.Err != nil && first == nil {
			first = r.Err
		}
	}
	fmt.Println(first)
}
```

**Answer:**

```
a
```

### What happens here

First non-nil error is remembered; `"b"` is ignored in this policy. For all errors use `errors.Join`.

### Example E — ID annotation

```go
package main

import (
	"errors"
	"fmt"
)

func main() {
	base := errors.New("timeout")
	wrapped := fmt.Errorf("id=7: %w", base)
	fmt.Println(errors.Is(wrapped, base))
}
```

**Answer:**

```
true
```

### What happens here

Wrap with worker ID does not break `errors.Is`. That is standard when Result carries `Err` from network or database.

## Decision analysis

| Decision | Option A | Option B | When to choose |
|--------|----------|----------|-------------|
| Error transport | `Result{Value, Err}` | separate `errc` | A for fan-in values; B for “one background task” |
| Buffer | `n` | `0` | `n` for simple wait; `0` for backpressure |
| Policy | first error | `errors.Join` | first for fail-fast; join for batch report |
| Close | WaitGroup + closer | `Gate` counter | WaitGroup is more idiomatic |
| After error | continue collecting | cancel context | continue if partial needed; cancel in 13.07 |

Questions before merge:

- Does every worker **always** send exactly one message?
- Who owns `close`?
- Does anyone share `var err error` without proof there is no race?
- Does consumer distinguish “channel closed” from “success with zero value”?

## Trade-offs

- **Result struct** uses slightly more memory and requires discipline on `Err` field, but removes races and ambiguity.
- **Separate error channel** is thinner, but loses link “which value / which ID”.
- **Large buffer** simplifies send, but holds all results in memory until coordinator reads.
- **Fail-fast without cancel** still burns CPU on remaining workers — next lesson introduces `errgroup`.
- **Collecting all errors** gives better UX for batch API, but complicates partial success responses.

## Common mistakes

1. **Shared `error` variable** between goroutines — data race or silent last error.
2. **Worker that returns without send** — consumer waits forever or counts fewer results.
3. **Multiple `close` calls** — panic.
4. **Reader closes channel** — ownership confusion and race with senders.
5. **Not sending error** (log only) — coordinator sees success.
6. **Unbuffered `errc` without select** — deadlock.
7. **Mixing zero value Result after close with success** — false OK.
8. **Ignoring `ctx.Done()`** — work after cancel, goroutine leak.
9. **String comparison of errors** instead of `errors.Is` — fragile tests.
10. **Fan-out without limit** — thousands of goroutines; limit belongs in 13.07, but plan here.

## Idiomatic Go

- Prefer `type Result[T any] struct { Value T; Err error }` for parallel fetch.
- One helper that spawns, waits, closes channel — do not scatter close across file.
- Wrap: `fmt.Errorf("fetch id=%d: %w", id, err)`.
- Test with `go test -race`.
- Document policy: first error vs join vs partial values.
- Do not export channel if not part of API; return `([]T, error)` from function boundary.
- Use blank identifier only consciously: `_ = <-ch` drops error — avoid.

## Practical scenario

Service pulls profiles for user list from three dependencies (profile, preferences, feature flag). Three teams wrote:

```go
var err error
go func() { p, err = loadProfile(id) }()
```

In CI `-race` occasionally fails; in production sometimes returns profile without error even though flag service failed. Refactor:

1. `type piece struct { name string; data any; err error }`
2. `ch := make(chan piece, 3)`
3. Each goroutine sends its `piece`
4. Handler maps first fatal error to HTTP 502/504, and partial to 207 only if product requires it

After change, on-call sees `name=flags: connection reset` in log with request ID, and client gets generic message (details in 13.08). Channel of results was the bridge between concurrency and HTTP boundary.

### Additional trace — timeout around whole fan-in

```go
package deadline

import (
	"context"
	"time"
)

func WithTimeout(parent context.Context, d time.Duration, run func(context.Context) error) error {
	ctx, cancel := context.WithTimeout(parent, d)
	defer cancel()
	errc := make(chan error, 1)
	go func() { errc <- run(ctx) }()
	select {
	case <-ctx.Done():
		// run may still be running; ctx cancels if it respects Done
		<-errc // optional drain so it does not leak if you want join
		return ctx.Err()
	case err := <-errc:
		return err
	}
}
```

### What happens here

Timeout is coordinator boundary. Workers must read `ctx.Done()` otherwise leak remains. Channel buffer 1 keeps error if timeout wins race.

### Additional trace — partial success as explicit type

```go
package partial

type Outcome[T any] struct {
	OK    []T
	Fails []error
}

func (o Outcome[T]) Err() error {
	if len(o.Fails) == 0 {
		return nil
	}
	return errors.Join(o.Fails...)
}
```

(Add `import "errors"` in real file.) Partial success is not “swallow error” — it is public contract that some `OK` are valid alongside `Fails`.

### Example F — Predict the result (range after close)

```go
package main

import "fmt"

func main() {
	ch := make(chan int, 1)
	ch <- 9
	close(ch)
	v1, ok1 := <-ch
	v2, ok2 := <-ch
	fmt.Println(v1, ok1, v2, ok2)
}
```

**Answer:**

```
9 true 0 false
```

### What happens here

First receive takes 9. Second from closed channel gives zero value and `ok=false`. For `Result`, that second receive **is not** success.

### Example G — Predict the result (Join order)

```go
package main

import (
	"errors"
	"fmt"
)

func main() {
	e := errors.Join(fmt.Errorf("a"), fmt.Errorf("b"))
	fmt.Println(e.Error())
}
```

**Answer:**

```
a
b
```

### What happens here

`errors.Join` merges messages; both errors remain in chain for `errors.Is` if sentinel/wrapped.

### Quick diagnostic table

| Symptom | Likely cause | First check |
|---------|-----------------|--------------|
| Hang in test | fewer sends than expected | worker count vs receive |
| race detector | shared `err` / map | `-race` stack |
| empty result + nil err | close zero value | `ok` flag |
| error “vanished” | log only in worker | look for send Result |
| slow cancel | no select on Done | ctx in loop |

## Summary

Multiple goroutines do not share one `error` variable — they send `struct { Value; Err }` through channel of results. One owner closes channel; coordinator reads N results or reacts to context. Buffer, select, and wrap with ID make error visible without deadlock. Next lesson introduces `errgroup`: cancel on first error and error synchronization without manual WaitGroup noise.
