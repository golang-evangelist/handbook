# 01.03 Using other packages: import paths, alias, and blank import

> **Go Path - Zero to Gopher** / **02 Intermediate → Deep dive into Go Packages** / Lesson 01.03

## Lesson goals

- Reliably read and write **import** paths: distinguish stdlib, a dependency from a **module** (module — unit of versioning and distribution of Go code, described by a `go.mod` file), and a local **package** (package — named code unit imported by one import path) of the same module.
- Use an **alias** for an import only when it is really needed — a name conflict or an awkward default package name.
- Explain, with a concrete example and the exact compiler behavior, why **dot import** is forbidden in this course and in almost all production Go code.
- Apply **blank import** (`_ "path"`) for side-effect registration — most often a SQL driver or image format — and know exactly what breaks if you omit it.
- Recognize an **import cycle** as a compile-time error, not a runtime problem, and know how it is resolved by extracting a shared package.
- Explain how `goimports` groups imports, what the default two classes are, and how a third class for local packages is obtained.
- Track dependencies through `go.mod` / `go.sum` and at every moment know where each line in the import block comes from.

## Prerequisite

- Lessons 01.01 and 01.02 completed (packages, `go mod init`, first exported symbols).
- A working environment with the Go toolchain installed and network access for `go get` (or a known local proxy/vendoring).
- Basic familiarity with the `go.mod` file — at least that you opened it once and read it from top to bottom.

## Problem this lesson solves

The import block looks like the most banal part of a Go file — a few lines at the top that `gofmt` reshuffles anyway. In practice it is the first page of the dependency contract of your code, and that is where chaos is easiest to create that is only felt months later, when the team grows or when a package needs to be split.

Without a clear import model, concrete, measurable problems arise:

- **Name conflicts.** Two packages are called `client`, or both have a symbol `Config`, and the compiler asks you to resolve the conflict — but if you do that randomly (`c1`, `c2`), the next reader loses track of who is who.
- **Hidden dependencies.** Someone adds `_ "somedriver"` so the build works, leaves no comment, and three months later nobody knows why that line exists or what happens if it is deleted.
- **Lost symbol origin.** `import . "package"` erases the prefix — every call looks like a local function, and code review can no longer quickly check whether `Parse` is from your code or from an imported package.
- **Blurred stdlib / dependency boundary.** When `encoding/json` and `golang.org/x/sync/errgroup` are treated as “the same”, the team loses the sense of what must be tracked for security patches and licenses, and what comes free with the toolchain.
- **Circular dependencies between your own packages.** Two packages in the same repository start importing each other because boundaries were not clear from the start — and Go simply refuses to compile that.

This lesson treats import as an **intentional dependency contract**, not as a list of “what I need for the build to work right now”. By the end of the lesson, looking at another person’s import block, you should be able in a few seconds to answer: what is stdlib, what is a dependency that must be in `go.mod`, what is a local package, and whether anything looks suspicious (dot import, blank import without a comment, alias without reason).

## Mental model

Import is a **bridge to someone else’s room**, not copying furniture into yours:

1. **The path** says **where** the room is — `net/http` is a room in your house (stdlib), `example.com/shop/catalog` is a room in another building whose address you have through `go.mod`.
2. **The name you call it by** (default = the package name declared in the `package` line of that code) is the **sign on the door**. Important: the sign does not have to match the folder name where the room lives — they match by convention, not by a language rule.
3. **Alias** is a nickname that **you** stick on the door in your file, when you dislike the sign or when you have two rooms with the same sign.
4. **Dot import** is breaking down the wall between rooms — all foreign furniture (exported symbols) appears in your room without a label of where it came from.
5. **Blank import** is like turning on the power in a room you never enter — the room does something in the background (`init()`), but you take nothing from it directly, so you give it no name.

`go.mod` is an **inventory of bridges** to external buildings your house recognizes; stdlib are streets that already exist in your city and you do not have to register them anywhere to walk them.

A short overview of that analogy in a table, because it is visually easier to remember than only reading:

| Concept | Analogy | Go term |
|---|---|---|
| Import path | Building and room address | import path |
| Package name (`package X` line) | Sign on the door | package |
| Alias | Nickname you give the door | import alias |
| Dot import | Broken wall, furniture mixes | dot import |
| Blank import | Power on, you do not enter the room | blank import |
| `go.mod` | Inventory of recognized bridges | module |

When something in imports confuses you, return to this analogy: ask yourself “which room am I looking at, who put the sign, and am I the one changing it”.

## Mechanism

This is the longest part of the lesson, and intentionally — every later mistake in code reduces to a wrong assumption about something explained here. We go in order, step by step, with concrete traces of what the compiler actually does.

### How the compiler resolves an import path

When the compiler hits `import "example.com/shop/catalog"`, it does not do magic — it does four concrete steps:

1. **Finds the source.** For stdlib it looks in the toolchain installation (`GOROOT/src`). For a module dependency it looks in the local module cache, filled via `go.mod` + `go.sum` (which exactly specify which version and which code hash to use). For a local package of the same module, it joins the `module` prefix from your `go.mod` with the relative folder path.
2. **Reads the `package` line** of every `.go` file in that folder (except `_test.go` files, which may have their own `_test` package suffix). All must declare the same package name — otherwise the build fails immediately.
3. **Binds the exported symbols** of that package to the identifier you use in your file — by default, that identifier is exactly the name from the `package` line, **not** the last segment of the import path.
4. **Checks use.** If you import a package and call nothing from it (without blank import), the build fails with `imported and not used`.

Look at a concrete project structure:

```
shop/
├── go.mod
├── go.sum
├── main.go
├── catalog/
│   └── catalog.go
├── order/
│   └── order.go
└── sku/
    └── sku.go
```

```
// go.mod
module example.com/shop

go 1.22
```

```go
// catalog/catalog.go
package catalog

// Item is a product in the catalog.
type Item struct {
	SKU  string
	Name string
}

// NewItem creates a product with SKU validation.
func NewItem(sku, name string) (Item, error) {
	return Item{SKU: sku, Name: name}, nil
}
```

`main.go` imports `"example.com/shop/catalog"` and calls `catalog.NewItem(...)`. The identifier `catalog` is there because that is the name from the `package catalog` line — the folder happens to have the same name, and that is a convention every Go team follows, not a language requirement.

**Predict:** What if the folder stays `catalog/`, but the first line in `catalog.go` says `package inventory`? How would you reference `NewItem` in `main.go`, and does the import path have to change?

**Answer:** The import path stays `"example.com/shop/catalog"` (that is the folder address, not the package name), but calls go through `inventory.NewItem(...)`, because the identifier the compiler binds is always the one from the `package` line. This is a common source of confusion for beginners — that is why the convention “folder and package name match” is so important that it is practically an unwritten rule, even when it is not a language requirement.

### Import paths: stdlib, modules, local packages of the same module

Three categories, and each has its recognition rule:

- **Stdlib** — short path, no domain (`fmt`, `net/http`, `database/sql`, `context`). Comes with the toolchain; never goes into `go get` nor into the `go.mod` `require` section.
- **Local package of the same module** — path starts exactly with the `module` prefix from your `go.mod` (`example.com/shop/...`). No `go get` needed; it changes by writing `.go` files in the corresponding folder.
- **External dependency** — everything else. Must have a line in the `go.mod` `require` section and corresponding hash values in `go.sum`. Added with `go get module@version` (or automatically on the first `go build`/`go run` when `-mod` mode allows it, and with `go mod tidy` to clean up).

Concrete trace: a file with all three import types at once.

```go
package main

import (
	"context"                      // stdlib
	"fmt"                          // stdlib

	"golang.org/x/sync/errgroup"   // external dependency, must be in go.mod

	"example.com/shop/catalog"     // local package of the same module
)
```

**Predict:** If `"golang.org/x/sync/errgroup"` exists in the import block, but there is no line for it in the `go.mod` `require` section nor in `go.sum`, does `go build` succeed?

**Answer:** It depends on the `-mod` setting. When working locally without special flags, modern `go build` can itself append the dependency to `go.mod`/`go.sum` (as if you ran `go mod tidy`). But on CI or with `-mod=readonly` (common for reproducible builds), the build fails with a message that `go.mod` is out of date and asks you to run `go mod tidy` locally and commit the result. The dependency must be **explicitly recorded**, not “guessed” at build time on someone else’s machine.

### Alias: syntax and what the compiler actually does

The syntax is `alias "path"`, where `alias` becomes the identifier for that import — **exactly the same mechanism** as when the default name would be bound, only you overwrote it.

```go
import (
	crand "crypto/rand"
	"math/rand"
)
```

Here `crand` references `crypto/rand`, and bare `rand` references `math/rand`. The compiler makes no distinction between a “natural” name and an alias — both are just an identifier bound to that import in file scope (visibility scope within one file).

What happens without an alias when names collide? Two packages whose `package` line says `client`:

```go
import (
	"example.com/shop/client"
	"example.com/payments/client"
)
```

```
./main.go:8:2: client redeclared as imported package name
	./main.go:7:2: previous declaration
```

(The message text differs in details by Go version, but the principle is constant: two imports cannot bind the same identifier in the same file without an alias.) Fix:

```go
import (
	shopclient "example.com/shop/client"
	payclient "example.com/payments/client"
)
```

**Predict:** If you import a package with an alias, but never call anything through that alias later in the file, what does `go build` report?

**Answer:** `imported and not used: "example.com/shop/client" as shopclient` — the compiler treats an unused alias identically to an unused default import. An alias does not “protect” an import from the rule that every imported package must be used.

### Dot import: mechanics and why we avoid it

`import . "package"` does one specific thing: every **exported** identifier of that package becomes declared directly in the **file block scope** of your file, with the same name it has in the source package — without a prefix, as if you wrote it.

```go
import . "fmt"

func main() {
	Println("x") // looks like a local function, and it is not
}
```

The problem is not only aesthetic. Imagine you dot-import two packages that both export `Parse`:

```go
import (
	. "example.com/shop/legacyparser"
	. "example.com/shop/newparser"
)

func main() {
	Parse("x") // which Parse? the compiler does not know, and neither do you looking at this line
}
```

This is not reported on the import line — everything compiles until you **call** the ambiguous name; only at the use site does the compiler report that `Parse` is unclear, because it comes from two dot-imported packages at once. That means the problem manifests far from the cause — the worst possible form of error for debugging and for code review.

**Predict:** If you dot-import only one package and never add a local function with the same name, will the code ever break because of that?

**Answer:** Not immediately — it will work as long as names do not collide. But that is exactly the danger: the code works today, and six months later someone adds a local function `Println` or another dot import, and the build fails in a file that “nobody touched”. Forbidding dot import in this course is not a stylistic preference — it is removing a category of errors that manifests late and far from the cause. The language allows dot import for rare cases (generated test DSLs, for example `. "github.com/onsi/ginkgo/v2"` in some test styles), but in application and library code of this course we never use it.

### Blank import: `init()` order and side effects

`_ "path"` does exactly one thing: runs package initialization (global `var` initializations, then all `init()` functions of that package, by dependencies) **without** binding a local identifier. You cannot call anything through `_` — that is not a name, it is a reserved mark “import, but do not reference”.

Classic example, SQL driver:

```go
import (
	"database/sql"

	_ "github.com/jackc/pgx/v5/stdlib" // registers the "pgx" driver with database/sql
)
```

What actually happens: package `pgx/v5/stdlib` in its `init()` calls `sql.Register("pgx", &Driver{})`. That registration fills a **global registry** inside `database/sql` — a map of string keys to driver implementations. The string `"pgx"` in `sql.Open("pgx", dsn)` has **no syntactic link** to the import path; it is a pure string key that matches exclusively by the agreement the driver author documented.

**Predict:** If you remove the line `_ "github.com/jackc/pgx/v5/stdlib"`, will `go build` report an error?

**Answer:** No — it compiles completely cleanly, because `database/sql` knows nothing, in terms of types, about the existence or non-existence of a driver. The error is runtime and appears on the first real call that requires an open connection:

```
$ go run .
panic: sql: unknown driver "pgx" (forgotten import?)
```

`sql.Open("pgx", dsn)` only makes a “lazy” handle and does not fail immediately; `PingContext`/`QueryContext`/`ExecContext` are the places where the registry is actually consulted. That is why a blank import must have a comment explaining why it exists — the compiler protects you from nothing here, and the error that comes out mentions only the string `"pgx"`, not which import you need to bring back.

### Import cycle: compile-time error, not a runtime problem

Go requires that the package dependency graph be **acyclic** (DAG — directed acyclic graph). If package A imports B, and B (directly or through a chain) imports A, `go build` refuses to do anything — no partial build, no warning, only a hard error before anything is run.

Concrete scenario: `catalog` needs to show “last order for this SKU”, so it imports `order.RecentPurchases(sku)`. At the same time, `order` needs to check that the SKU exists before saving an order, so it imports `catalog.Validate(sku)`. Result:

```
$ go build ./...
package example.com/shop/order
	imports example.com/shop/catalog
	imports example.com/shop/order: import cycle not allowed
```

The solution is not “move the function from one to the other” (that only reverses the cycle direction) — the solution is **extract the shared minimal part** into a third package that has no back-dependencies:

```go
// sku/sku.go
package sku

// Valid checks SKU format, with no dependency on catalog or order.
func Valid(code string) bool {
	return len(code) > 0
}
```

Now `catalog` and `order` both import `sku`, and neither imports the other. The cycle is gone because the shared thing (the SKU format rule) moved to where neither of them needs to know the other exists.

**Predict:** Must an import cycle be a direct pair (A imports B, B imports A), or can it go through a longer chain (A→B→C→A)?

**Answer:** It can go through an arbitrarily long chain — every cycle in the dependency graph, no matter how many packages long, fails the build. That is why “extract the shared type into a third package” is sometimes not enough to do only once — sometimes reshuffling boundaries of more packages is needed until the whole graph becomes acyclic. The tool `go list -deps` (or graphically `go mod graph`) helps see the chain before you reach the error.

### `goimports` groups and order

`goimports` (a superset of `gofmt` specifically for the import block) does two things: sorts alphabetically within each group, and **groups** imports into classes separated by a blank line. By default it has **two** groups: stdlib first, then **everything else** (external dependencies **and** local packages together) in one alphabetically sorted group.

Before `goimports -w` (intentionally messy, in one line of random order):

```go
import ("example.com/shop/catalog"; "fmt"; "golang.org/x/sync/errgroup"; "context")
```

After `goimports -w`, default behavior (two groups):

```go
import (
	"context"
	"fmt"

	"example.com/shop/catalog"
	"golang.org/x/sync/errgroup"
)
```

You will notice that `example.com/shop/catalog` (local package) and `golang.org/x/sync/errgroup` (external dependency) are in the **same** group, only alphabetically sorted together. That is the default behavior.

Most examples in this lesson, however, use **three** groups (stdlib / external dependencies / local packages) — that is not the `goimports` default, that is set via the `-local example.com/shop` flag (or the equivalent setting in `gopls`/editor: `"local": "example.com/shop"`). With that flag, `goimports` makes a third group specifically for all imports that start with that prefix:

```
$ goimports -local example.com/shop -w main.go
```

```go
import (
	"context"
	"fmt"

	"golang.org/x/sync/errgroup"

	"example.com/shop/catalog"
)
```

**Predict:** If you manually write stdlib and an external package in the same group, without a blank line between them, and run plain `goimports -w` (without `-local`), will the tool split them into two groups?

**Answer:** Yes — `goimports` does not respect how a human grouped when there is no already existing signal (blank line) that hints intent in a way the tool recognizes; it reconstructs groups by its own rule (stdlib separate from everything else) and rewrites the whole block. For the third group (local packages) to survive saves, the team must consistently configure `-local` in editors and in CI format checks (`goimports -l .` which returns a list of files with incorrect format).

## Rules and syntax

- Group imports: stdlib, blank line, external dependencies, blank line, local packages (with `-local` set in the team) — or at minimum let `goimports`/`gofmt` decide by default.
- Never a relative import (`../foo`) — not supported for modules and tools do not understand it.
- Write aliases short and stable (`pgxstdlib`, not `a`); if you need an alias in multiple places in the repository for the same package, consider renaming the package at the source.
- Dot import is **forbidden** in this course, with no exception for application and library code.
- A blank import must have a comment explaining why it exists and what happens without it.
- Do not import a package only to avoid defining a small shared type — if you notice that would create an import cycle, that is a signal that the package boundary needs rethinking, not that a “shortcut” is needed.
- An import path for stdlib never appears in the `go.mod` `require` section; if you see it there, that is an understanding error, not a tool error.
- Every external module in the import block must have a corresponding line in `go.mod` and a hash in `go.sum` — check before commit: `go mod tidy` and `git diff go.mod go.sum` should not surprise.

## Examples

### Example 1 — Clean import block with three categories

```go
package main

import (
	"context"
	"fmt"
	"net/http"
	"time"

	"golang.org/x/sync/errgroup"

	"example.com/shop/catalog"
)

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
	defer cancel()

	req, err := http.NewRequestWithContext(ctx, http.MethodGet, "https://example.com", nil)
	if err != nil {
		panic(err)
	}
	_ = req

	item, err := catalog.NewItem("a-1", "Milk")
	if err != nil {
		panic(err)
	}

	var g errgroup.Group
	g.Go(func() error {
		fmt.Println(item.SKU, item.Name)
		return nil
	})
	if err := g.Wait(); err != nil {
		fmt.Println(err)
	}
}
```

#### What happens here

Three groups, three categories: `context`/`fmt`/`net/http`/`time` are stdlib and never go into `go.mod`; `errgroup` is an external dependency that must be in `go.mod`/`go.sum`; `catalog` is a local package of the same module. `g.Go(func() error { ... })` starts a **goroutine** (goroutine — an independent, cheap execution thread that the Go runtime multiplexes onto OS threads) — `errgroup.Group` waits for it to finish via `g.Wait()`. It is worth noticing that `var g errgroup.Group` calls no constructor — the type has a useful **zero value** (zero value — the value of a variable right after declaration, before any assignment; for struct fields those are the zero values of their types), so `errgroup.Group{}` is immediately usable.

### Example 2 — Alias because of a name conflict

```go
package main

import (
	"fmt"

	shopclient "example.com/shop/client"
	payclient "example.com/payments/client"
)

func main() {
	s := shopclient.New("https://shop.local")
	p := payclient.New("https://pay.local")
	fmt.Printf("%T %T\n", s, p)
}
```

```go
// both packages have an identical shape, only a different import path
package client

// Client is a pointer to a struct that holds the service base address.
// pointer (pointer — address of a value in memory, instead of a copy of that value)
// allows methods to change state without copying the whole struct.
type Client struct{ Base string }

// New creates a Client and returns a pointer to it.
func New(base string) *Client { return &Client{Base: base} }
```

#### What happens here

Both packages declare `package client`. Without an alias, the second import would try to bind the same identifier `client` and the compiler would refuse to continue (`redeclared as imported package name`). The alias keeps both APIs available in the same file under different names. The long-term solution is better than an alias: rename one of the packages at the source (e.g. `package shopclient`) so the alias becomes unnecessary for all import sites, not only in this file.

### Example 3 — Blank import of a SQL driver, with and without it

```go
package main

import (
	"context"
	"database/sql"
	"fmt"
	"time"

	_ "github.com/jackc/pgx/v5/stdlib" // registers the "pgx" driver via sql.Register in init()
)

func main() {
	dsn := "postgres://app:secret@localhost:5432/shop?sslmode=disable"
	db, err := sql.Open("pgx", dsn)
	if err != nil {
		panic(err)
	}
	defer db.Close()

	ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
	defer cancel()
	if err := db.PingContext(ctx); err != nil {
		fmt.Println("ping:", err)
		return
	}
	fmt.Println("ok")
}
```

#### What happens here

`database/sql` is a facade that knows nothing about Postgres; the concrete driver attaches exclusively through blank import and its `init()`. Remove the line `_ "github.com/jackc/pgx/v5/stdlib"` and the code will still compile — failure moves to `db.PingContext(ctx)` with `sql: unknown driver "pgx" (forgotten import?)`. The DSN in the example is an illustration; in production you read the password from secrets (secret manager, env variable with limited access), you do not hardcode it in code.

### Example 4 — Why not dot import (same task, two styles)

```go
// Style we use:
package main

import (
	"fmt"
	"strings"
)

func main() {
	fmt.Println(strings.Contains("milk and bread", "bread"))
}
```

```go
// Style that is forbidden (shown only so the difference is visible):
package main

import (
	"fmt"
	. "strings"
)

func main() {
	fmt.Println(Contains("milk and bread", "bread")) // where is Contains from?
}
```

#### What happens here

In the first style, `strings.Contains` carries its origin in the call itself — code review recognizes it without thinking. In the second, `Contains(...)` is grammatically identical to a local function call; the reader must know the whole `strings` package API by heart to be sure it is not something defined three files down. The course forbids dot import precisely so origin stays visible at the call site, not only at the top of the file.

### Example 5 — stdlib vs module dependency, with a closure worth noticing

```go
package main

import (
	"encoding/json"
	"fmt"

	"golang.org/x/sync/errgroup"
)

func main() {
	skus := []string{"a-1", "a-2", "a-3"} // slice of string values

	var g errgroup.Group
	for _, sku := range skus {
		sku := sku // the closure below captures the variable; this is an intentional copy per iteration
		g.Go(func() error {
			b, err := json.Marshal(map[string]string{"sku": sku})
			if err != nil {
				return err
			}
			fmt.Println(string(b))
			return nil
		})
	}
	if err := g.Wait(); err != nil {
		fmt.Println(err)
	}
}
```

#### What happens here

`skus` is a **slice** (slice — a variable-length view of an array with a shared internal buffer, length, and capacity) of string values. `encoding/json` is stdlib and does not go into `go.mod`; `errgroup` is an external module and must be there. The anonymous function passed to `g.Go` is a **closure** (closure — a function that “captures” variables from the surrounding scope instead of receiving them as parameters) — it captures `sku`. The line `sku := sku` creates a new local variable on each loop iteration; without it (in older Go versions, before the loop semantics change in Go 1.22) all started **goroutine**s could see the same, last value of the loop variable — a classic and costly mistake when a closure is combined with concurrent code.

### Example 6 — Import cycle: before and after

```go
// BEFORE (does not compile — shown only so the cycle structure is visible)

// catalog/catalog.go
package catalog

import "example.com/shop/order" // catalog needs order for "last order"

func RecentContext(sku string) string {
	return order.RecentPurchases(sku)
}

// order/order.go
package order

import "example.com/shop/catalog" // order needs catalog for SKU validation

func Save(sku string) error {
	if !catalog.Validate(sku) {
		return fmt.Errorf("invalid sku")
	}
	return nil
}
```

```go
// AFTER (compiles — shared part extracted)

// sku/sku.go
package sku

func Valid(code string) bool {
	return len(code) > 0
}

// catalog/catalog.go
package catalog

import "example.com/shop/sku"

func Validate(code string) bool {
	return sku.Valid(code)
}

// order/order.go
package order

import "example.com/shop/sku"

func Save(code string) error {
	if !sku.Valid(code) {
		return fmt.Errorf("invalid sku")
	}
	return nil
}
```

#### What happens here

In the “before” version, `catalog` imports `order` and `order` imports `catalog` — `go build ./...` reports `import cycle not allowed` before anything is run; this is not a runtime problem, the code **does not compile**. In the “after” version, shared SKU format validation is extracted into package `sku`, which has no back-dependencies; `catalog` and `order` both import `sku`, neither imports the other. The dependency graph is acyclic again.

```go
// After, with -local (three groups)
package main

import (
	"context"
	"fmt"

	"golang.org/x/sync/errgroup"

	"example.com/shop/catalog"
)
```

#### What happens here

Without `-local`, `goimports` makes only two groups — stdlib, and everything else alphabetically sorted together (local package `catalog` and external dependency `errgroup` are not separated). With `-local example.com/shop`, the tool extracts a third group specifically for imports that have that prefix. If the team wants three groups consistently across the whole repository, `-local` must be set in the same place for everyone — in the editor (LSP setting), and in CI format checks, otherwise different developers will produce different diffs for the same code.

## Decision analysis

| Decision | Why |
|----------|-----|
| No relative imports | Tools, module cache, and documentation expect a module path, not a filesystem path |
| Alias only when needed | Less cognitive noise; every alias is something the reader must learn by heart |
| Blank import with a comment | Side effect is intent that review can check, not an accident nobody understands |
| Dot import forbidden | Readability and maintainability; otherwise the error manifests far from the cause |
| `goimports` (with agreed `-local`) | Consistent import order and less “noise” diffs in code review |
| Extracting a shared package on a cycle | Fixing the package boundary, not bypassing a language rule |

## Trade-offs

- More aliases in one file is a signal that the file does too many different things — maybe time to split into smaller files or packages.
- Blank import hides a dependency from the view of “which functions do I call in this file” — that is why a comment is mandatory, and the package README should mention it if it is part of the library’s public contract.
- Vendoring versus proxy (`GOPROXY`) does not change import syntax, only how code is physically obtained and cached; the import block stays identical in both cases.
- Importing a large package for one function is sometimes a justified choice — better to consciously accept the dependency and its tracking (security patches, versions) than to copy and maintain your own copy of that logic.
- A third `goimports` group (`-local`) gives a nicer, more readable diff, but requires agreement and consistent configuration across the whole team — undecided `-local` is worse than nobody using it.

## Common mistakes

### Dot import “to save typing”

**Wrong:**
```go
import . "fmt"

func main() {
	Println("done")
}
```

**Effect:** The reader does not see that `Println` comes from `fmt`. If someone later adds a local function `Println`, or another dot import that also exports `Println`, compilation fails at the call site — far from the real cause, which is the import at the top of the file.

**Fix:**
```go
import "fmt"

func main() {
	fmt.Println("done")
}
```

### Forgotten blank import of a driver

**Wrong:**
```go
import (
	"database/sql"
)

func openDB(dsn string) (*sql.DB, error) {
	return sql.Open("pgx", dsn)
}
```

**Effect:** Compiles with no error at all. Runtime fails only on the first real call to the database: `sql: unknown driver "pgx" (forgotten import?)`. The error mentions no import, only the driver string key — it is hard to guess the solution if the blank import mechanism is unknown.

**Fix:**
```go
import (
	"database/sql"

	_ "github.com/jackc/pgx/v5/stdlib" // registers the "pgx" driver via sql.Register
)
```

### Alias without reason (`a`, `b`, `x`)

**Wrong:**
```go
import (
	a "example.com/shop/catalog"
	b "example.com/shop/order"
)
```

**Effect:** There is no name conflict that would justify an alias — this only forces the reader to memorize an arbitrary mapping `a → catalog`, `b → order`. Every new developer wastes time scrolling to the top of the file to understand what `a` is.

**Fix:**
```go
import (
	"example.com/shop/catalog"
	"example.com/shop/order"
)
```

### Import cycle because of shared types

**Wrong:**
```go
// catalog imports order, order imports catalog — see Example 6, "BEFORE" version
```

**Effect:** `go build ./...` refuses the whole build with `import cycle not allowed`, even if 99% of the code is correct. There is no partial build — the whole module is blocked until the cycle is removed.

**Fix:** Extract the shared type/function into a third package without back-dependencies (see Example 6, "AFTER" version), or rethink whether the two packages should even exist separately.

### Relative or physically wrong import path

**Wrong:**
```go
import "../catalog"
```

**Effect:** The Go toolchain does not support relative import paths for modules — this does not compile with a standard invalid-path message, and every tool (IDE, `go doc`, `goimports`) behaves unexpectedly or refuses to work.

**Fix:**
```go
import "example.com/shop/catalog"
```

### Import block manually sorted, bypassing `goimports`

**Wrong:**
```go
import (
	"example.com/shop/catalog"
	"fmt"
	"context"
)
```

**Effect:** Works (compiles), but every `goimports -w` from another developer (or a pre-commit hook) rewrites the order — tiny, irritating merge conflicts in imports that have nothing to do with the real logic of the change.

**Fix:** Run `goimports -w` (or configure the editor to do that automatically on save) and commit an already sorted block — and agree in the team whether `-local` is used.

## Idiomatic Go

- `goimports`/`gofumpt` arrange the import block automatically; do not manually fix an order the tool will change anyway.
- Stdlib packages have short, clear names (`fmt`, `sort`, `strings`) — follow that style when naming your own packages.
- Blank import is idiomatic and common for database drivers (`database/sql` drivers) and image format registration (`_ "image/png"`, `_ "image/jpeg"`) — the decoder registers itself, and is called through shared `image.Decode`.
- Blank import is also idiomatic for side tools like a profiler: `_ "net/http/pprof"` registers HTTP routes for profiling through `init()`, without a single direct call in your code.
- Do not use an alias to “rebrand” an import if the default package name already fits — alias is a tool for resolving conflicts, not decoration.
- Types with a useful **zero value** (like `errgroup.Group`, `sync.Mutex`, `bytes.Buffer`) need no constructor — `var g errgroup.Group` is idiomatic Go, not an omission.
- `go vet` and `staticcheck` catch some import problems (e.g. unused import in some contexts, shadowing) before they reach code review — worth having them in CI.

## Practical scenario

An order service grows. One team imports an internal `metrics` package for its own counters, another adds a Prometheus client — whose package is also `metrics`. The build fails on `redeclared as imported package name`. The first fix is quick: alias `prom` for the Prometheus client and `appmetrics` for the internal package. Review on the PR goes further — it asks that the internal package be renamed to `appmetric` (at the source, in the `package` line) so the alias at every import site becomes unnecessary, not only in this one file.

In parallel, the same service gets a Postgres storage layer. Someone first puts `_ "github.com/jackc/pgx/v5/stdlib"` directly in package `orderstore` (the library that implements the `Store` interface), because that is where it was first needed. Review sends that back: the driver blank import moves to `cmd/api/main.go`, with a comment, because that is the process edge — `orderstore` itself should stay independent of which concrete driver is registered somewhere above it in the call stack.

Later, while adding “show last order on the product page”, `catalog` starts importing `order`, and `order` (which already validates SKU on save) imports `catalog`. The build fails on `import cycle not allowed`. Solution: small SKU format validation moves to a new package `sku`, with no back-dependencies; both existing packages import it, the cycle disappears without loss of functionality.

At the end, the team agrees on `-local example.com/shop` in `.golangci.yml` and in editor settings, so all local packages group separately from external dependencies in every file — diffs in PRs become more readable, and review focuses on logic, not on who put a blank line where.

## Check questions

1. **What does blank import do and what happens without it for a SQL driver?**  
   It runs the package `init()` (which, for drivers, calls `sql.Register`) without binding a local identifier. Without it the code compiles normally, but the first real call to the database fails with `sql: unknown driver`.

2. **Why does the course forbid dot import?**  
   It erases visible symbol origin at the call site; a name conflict is not reported on the import line, but only when the ambiguous identifier is used, far from the cause.

3. **When is an alias justified, and when is it not?**  
   It is justified when package names collide or the default name is awkward to read; it is not justified as decoration when the default name already does the job (avoid `a`, `b`, `x`).

4. **How do you recognize stdlib, an external dependency, and a local package in the import block?**  
   Stdlib is a short path without a domain; a local package starts with the `module` prefix from your `go.mod`; everything else is an external dependency that must have a line in `go.mod`/`go.sum`.

5. **Why is an import cycle a compile-time error, not a runtime problem?**  
   Go requires an acyclic package dependency graph before it runs anything; `go build` stops the whole build with `import cycle not allowed` as soon as it discovers a cycle, regardless of whether the code would otherwise work.

6. **What is the default `goimports` grouping behavior, and how is a third group obtained?**  
   By default there are two groups — stdlib, and everything else (external dependencies and local packages together) alphabetically sorted. A third group, specifically for local packages, is obtained with the `-local <module-prefix>` flag, agreed consistently across editor and CI.

## Summary

An import path shows **where** code comes from; the name or alias determines how you call it locally — and that name always comes from the `package` line of the source code, not from the folder name. Dot import is never used in this course, because it turns name conflicts into an error reported far from the cause. Blank import is an intentional side effect the compiler does not check — that is why it goes with a comment. Stdlib, external dependencies, and local packages have different discipline in `go.mod`, and an import cycle is always a compile-time error that is solved by reshuffling package boundaries, not by bypassing the rule. `goimports` (with agreed `-local`) keeps this whole model visible and consistent in every file, without manual work.
