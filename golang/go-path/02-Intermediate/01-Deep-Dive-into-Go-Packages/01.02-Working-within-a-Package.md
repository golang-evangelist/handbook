# 01.02 Working within one package: namespace, `init`, and tests

> **Go Path - Zero to Gopher** / **02 Intermediate → Deep dive into Go Packages** / Lesson 01.02

## Lesson goals

After this lesson you can:

- explain that **all files of the same package share one namespace** — there is no import between files in the same directory;
- write internal (unexported) helper functions without polluting the package API;
- accurately predict the **order of `init` functions** — within a file, between files of the same package, and between packages that are imported;
- choose between `package foo` (white-box test, sees unexported) and `package foo_test` (black-box test, sees only the API);
- recognize and avoid a **duplicate symbol** in the same package before the compiler does it for you.

## Prerequisite

- Lesson 01.01 (package as compilation unit and API boundary, export, `internal/`).
- Basic `go test ./...`.
- Understanding that a `_test.go` file participates in the test build, but not in ordinary `go build`.

## Problem this lesson solves

Inside a package people often make the same three mistakes:

- they repeat the same helper function in multiple files because they “do not see” that files in the same directory already share **one** namespace;
- they export internal state or helper functions only so the test can “see” them, instead of writing the test in the same package;
- they push logic into `init()` so imports and tests get hidden side effects whose order nobody controls intentionally;
- they mix white-box and black-box tests without intent, so one test breaks when a helper is renamed, and another does not notice when the real contract is broken.

This lesson shows how to live **inside** the room from the previous lesson: what is shared automatically, what stays hidden, how to test the boundary, and exactly when which function runs at program start.

## Mental model

One package = **one symbol table**, regardless of the number of files.

- `a.go` and `b.go` with `package shop` see everything of each other, including unexported functions — as if everything were in one file.
- There is no `shop.a.foo()` — only `foo()`. A file prefix does not exist for the compiler.
- Export (uppercase/lowercase, from 01.01) is a visibility switch toward **other packages**, not toward files in the same package — those two boundaries are easy to mix up, but they are independent.
- `init` runs at package initialization, before `main` and before tests that import the package — that is a hidden “constructor” of the whole compilation unit, with a strict but subtle order.
- A test in `package shop` sees unexported (white-box, literally “test from inside”). A test in `package shop_test` sees only export (black-box, “test as a guest”) and must import the package like any other client.

| Official Go term | Short English gloss (first time only) | Do not use as the concept name |

## Mechanism

### Shared namespace

The compiler does not process `a.go` and `b.go` as two separate programs that are then “linked” — it **parses them together** as one stream of declarations before it does anything else. That means: an identifier defined in `a.go` is available in `b.go` from the moment of parsing, without a single import line, because for the compiler both files belong to the same symbol table.

Take a concrete pair of files:

`catalog/ids.go`:

```go
package catalog

import "strings"

func normalizeSKU(s string) string {
    return strings.ToUpper(strings.TrimSpace(s))
}
```

`catalog/item.go`:

```go
package catalog

import "fmt"

// Item is the public product model.
type Item struct {
    SKU  string
    Name string
}

// NewItem creates an Item with a normalized SKU.
func NewItem(sku, name string) (Item, error) {
    n := normalizeSKU(sku)
    if n == "" {
        return Item{}, fmt.Errorf("catalog: empty SKU")
    }
    if name == "" {
        return Item{}, fmt.Errorf("catalog: empty Name")
    }
    return Item{SKU: n, Name: name}, nil
}
```

`NewItem` calls `normalizeSKU` without anything like `import "./ids.go"` — such syntax does not even exist in Go. The call works because `go build` first collects **all** `.go` files of directory `catalog/`, merges their declarations into one table, and only then checks types and generates code. `normalizeSKU` is not part of the API: a client of package `catalog` sees only `Item` and `NewItem`, because `normalizeSKU` is unexported — but that hiding applies only **toward other packages**. Inside `catalog`, `item.go` and `ids.go` are equal citizens of the same namespace.

### Duplicate symbol — error, not warning

Since all package files are one symbol table, two files cannot define the **same name** at package level, even if that would “work” if they were in different packages.

```go
// report/build.go
package report

func build() string { return "a" }
```

```go
// report/format.go
package report

func build() string { return "b" } // ERROR
```

`go build ./report` stops with a message similar to:

```text
report/format.go:3:6: build redeclared in this block
    report/build.go:3:6: other declaration of build
```

This is not specific to functions — the same applies to `type`, `const`, `var` at package level, and to methods with the same signature on the same type. The solution is not “hide it in another file” (there is no place to hide inside a package) — the solution is a different name, or one function with branching if both `build` actually do related work.

**Predict:** if `build` in `format.go` has a **different signature** (`func build(prefix string) string`), does the error still exist?

**Answer:** Yes — Go does not allow overloading a function name by signature (no function overloading as in C++/Java). A package-level name is a unique key regardless of parameters; the compiler still reports `build redeclared in this block`.

### Internal helper functions

When you need logic that you do **not** want in the API, write it as an unexported function: lowercase, a clear name that says what it does (`normalizeSKU`, `validCurrency`), and call it from public functions of the same package. This is not a special mechanism — it is the same letter rule from 01.01, only applied to organization **inside** the package instead of the boundary toward the outside.

```go
package pricing

import "fmt"

type Quote struct {
    TotalMinor int64
    Currency   string
}

func Calculate(unitMinor int64, qty int, currency string) (Quote, error) {
    if qty < 0 {
        return Quote{}, fmt.Errorf("pricing: qty < 0")
    }
    if err := validCurrency(currency); err != nil {
        return Quote{}, err
    }
    return Quote{
        TotalMinor: unitMinor * int64(qty),
        Currency:   currency,
    }, nil
}

func validCurrency(c string) error {
    switch c {
    case "RSD", "EUR", "USD":
        return nil
    default:
        return fmt.Errorf("pricing: unknown currency %q", c)
    }
}
```

`validCurrency` stays private. If tomorrow you add a check from a config file instead of a `switch`, the public API `Calculate` stands unchanged — only the interior changes, and no client outside the package notices or has to recompile its call.

### Shadowing a package-level identifier with a local variable

The shared namespace also has a subtler consequence: a local variable inside a function may have the same name as a package-level variable or function, from **any** file of the same package — the compiler allows that through **shadowing**, not through an error. This is not a duplicate symbol (which is an error, we saw above) — it is a new, local declaration that temporarily “covers” the outer name within its scope (block).

```go
// catalog/ids.go
package catalog

var count int // package-level call counter

func normalizeSKU(s string) string {
    count++
    return s
}
```

```go
// catalog/report.go
package catalog

import "fmt"

func Summary() string {
    count := 0 // NEW local variable — shadows package-level `count`
    for range []int{1, 2, 3} {
        count++
    }
    return fmt.Sprintf("local count=%d", count) // reads LOCAL count, not package-level
}
```

`count := 0` inside `Summary` does not assign to the package-level variable `count` — it creates a **new**, local one that exists only in the body of `Summary`. The compiler allows this with no warning by default (tool `go vet -shadow`, outside the standard set, can warn). Consequence: package-level `count` from `normalizeSKU` and local `count` from `Summary` are two completely independent variables that happen to have the same name — a shared namespace means they **could** collide if there were no `:=` inside the block, not that they **must**.

**Predict:** if `Summary` writes `count = 0` instead of `count := 0` (without `:=`), which variable does it affect?

**Answer:** The package-level `count`, because `=` without `:=` is assignment to an existing variable, and since there is no local declaration of `count` in that scope before that line, the compiler resolves the name to the nearest existing declaration — package-level `var count int`. This is a difference that often causes a bug: one character (`:=` vs `=`) changes whether the function touches shared package state or its temporary copy.

### `init` — an order that must be predicted, not guessed

`init` is a special function: no parameters, no result, you do not call it yourself — the runtime calls it automatically, exactly once, at package initialization. Before you look at an example, it is worth understanding the **exact** order, because that is where the most guessing without foundation happens.

The order goes in three levels, from widest to narrowest:

1. **Dependencies before the dependent package.** If package `A` imports package `B`, all package-level variables and all `init()` in `B` finish **before** `A` starts anything of its own (its variables or its `init`). This holds transitively through the whole import graph, and cycles are guaranteed not to exist (an import cycle is a compile-time error, topic 01.03) — so this order is always well defined.
2. **Package-level variables before `init()` functions, by dependency, not by writing order.** The compiler analyzes which variable depends on which (e.g. `var b = a + 1` depends on `a`) and initializes them in an order that respects those dependencies — **not** necessarily in the order they are written in the file, and not necessarily by file order. When there is no dependency, the order is by textual appearance (file by file, in lexical order of file names, top-to-bottom within a file).
3. **`init()` functions by files in lexical order of file names, and within a file by appearance order.** The Go toolchain (both `go build` and the `gc` compiler) presents package files to the compiler sorted by file name — so it is recommended that you do **not** rely on the order of `init` functions **between** files as an explicit contract, but if you must know what will happen, it is: `a_init.go` before `b_init.go`, alphabetically. Multiple `init()` functions **in the same file** execute in the order they are written, top-to-bottom — that is guaranteed and stable.

Trace for a concrete small dependency graph, package `shop` that imports `catalog`:

```go
// catalog/catalog.go
package catalog

var Ready = setup()

func setup() bool {
    println("catalog: setup")
    return true
}

func init() {
    println("catalog: init")
}
```

```go
// main.go
package main

import "example.com/shop/catalog"

var _ = catalog.Ready

func init() {
    println("main: init")
}

func main() {
    println("main: main")
}
```

| Step | What runs | Why exactly then |
|------|-----------|------------------|
| 1 | `catalog.Ready = setup()` → prints `catalog: setup` | `catalog` is a dependency of `main`; its package-level variables must be ready before anything in `main` |
| 2 | `catalog.init()` → prints `catalog: init` | `init()` functions of package `catalog` go after its variables, still before the `main` package |
| 3 | `main` package initializes its variables (`var _ = catalog.Ready` — no print, only reading an already set value) | Now that `catalog` is ready, `main` may read its exported values |
| 4 | `main.init()` → prints `main: init` | Last level before calling `main()` |
| 5 | `main()` → prints `main: main` | The runtime calls `main()` only when all initializations, everywhere in the import graph, are finished |

The output is always: `catalog: setup`, `catalog: init`, `main: init`, `main: main` — in that exact order, never differently, regardless of the order files were opened in the editor.

**Predict:** if `main.go` gets a second file, `zzz_init.go`, with `func init() { println("main: zzz") }`, and the existing `init` stays in `main.go`, which prints first?

**Answer:** `main.go` before `zzz_init.go`, because `main.go` is alphabetically before `zzz_init.go` — so the output stays `main: init` then `main: zzz`. If the file were called `a_init.go` instead of `main.go`, the order would reverse. Exactly why order **between files** is not used as a meaningful contract in real code — at most one `init` per package is used, or an explicit `Register`/`New` call when order must be readable from code, not from file names.

Practical consequence of this mechanism: an `init` that does I/O (reads env, opens a connection) runs **before** `main()`, thus before the program manages to parse its CLI flags or print `--help`. If that `init` panics on bad env, the program cannot even show a usage message — it only crashes at start. That is why idiomatic Go style is that I/O and network operations are done in an explicit `New`/`Open`/`FromEnv` call from `main()`, and `init` is reserved for cheap, safe registration (blank import and SQL drivers in detail in 01.03).

### White-box vs black-box test files

A `_test.go` file has two possible `package` clauses, and the choice between them changes what the test sees:

| Form | `package` clause | Sees unexported | Typical purpose |
|------|------------------|-----------------|-----------------|
| White-box | `package foo` (same name as the rest of the package) | yes | testing internal contracts, helpers, invariants |
| Black-box | `package foo_test` | no | documentation test, confirming the public API as a client sees it |

This is the same machinery from 01.01 (one package per directory, with the `_test` suffix exception) applied to tests. A black-box test package is, from the compiler's perspective, a **second**, completely independent package that imports `module/path/foo` like any external client — so it needs an explicit `import`, and so it sees only what `foo` exports.

`catalog/ids_test.go` (white-box):

```go
package catalog

import "testing"

func TestNormalizeSKU(t *testing.T) {
    got := normalizeSKU("  ab-12 ")
    if got != "AB-12" {
        t.Fatalf("got %q", got)
    }
}
```

`catalog/item_export_test.go` (black-box):

```go
package catalog_test

import (
    "testing"

    "example.com/shop/catalog"
)

func TestNewItemAPI(t *testing.T) {
    it, err := catalog.NewItem("x-1", "White bread")
    if err != nil {
        t.Fatal(err)
    }
    if it.SKU != "X-1" {
        t.Fatalf("SKU=%q", it.SKU)
    }
}
```

The white-box test calls `normalizeSKU` directly — that is possible only because `ids_test.go` shares `package catalog` with the rest of the package, thus also shares the symbol table. The black-box test **could not** write `catalog.normalizeSKU(...)` — such a call does not compile, because `catalog_test` is another package for the compiler and sees only `NewItem` and `Item`. Both tests are useful and do not replace each other: white-box quickly catches a regression in internal logic; black-box confirms that the contract real clients see still holds.

Important note on mixing: **both** test forms in the same directory are allowed at the same time (one `_test.go` file with `package catalog`, another with `package catalog_test`) — `go test` merges them into the same test binary. The “one package per directory” exception from 01.01 allows exactly and only this combination: the ordinary package, plus at most one additional “package + `_test`” pair.

### `export_test.go` — a bridge between a black-box test and an internal detail

Sometimes a black-box test **must** check something that is internal, and there is no way to do that without access to an unexported identifier. Instead of permanently exporting that identifier (which makes it part of the public API forever), the stdlib and a large part of the ecosystem use a convention: a special **white-box** file named `export_test.go`, which contains no tests, but only assigns an unexported value to an exported variable **visible only to the test binary**.

```go
// catalog/export_test.go — white-box, package catalog, compiles ONLY with `go test`
package catalog

// NormalizeSKU is a test-only bridge to unexported normalizeSKU.
// It exists only while testing; it does not appear in the production binary
// because _test.go files do not enter `go build`.
var NormalizeSKU = normalizeSKU
```

```go
// catalog/item_export_test.go — black-box, package catalog_test
package catalog_test

import (
    "testing"

    "example.com/shop/catalog"
)

func TestNormalizeSKUViaExport(t *testing.T) {
    if catalog.NormalizeSKU("  ab-12 ") != "AB-12" {
        t.Fatal("normalization does not work as expected")
    }
}
```

Key point: `export_test.go` is still a `_test.go` file, thus **does not enter ordinary `go build`** — only `go test`. So `NormalizeSKU` never becomes part of the public API of the library a client imports into their program; it exists exclusively in the test binary. This trick is used rarely and intentionally — when the value of writing a black-box test (documenting the contract) is greater than the cost of an extra file, and fully exporting the identifier would be excessive.

## Rules and syntax

- Same `package` clause in all non-test (and white-box test) files of the directory; the only additional form is `package name_test` in `_test.go` files.
- Do not export an identifier only because of a test; use a white-box test or intentionally export a factory/constructor, with a reason that outlives that one test.
- `init` has no parameters and returns no value: `func init() { ... }` — the signature is fixed, there is no `init(cfg Config)`.
- Multiple `init()` functions per package are legal (in the same file and across multiple files); order within a file is top-to-bottom and guaranteed, order between files is by lexical file name and **should not** be used as a meaningful contract.
- `init` for driver registration through blank import is idiomatic (`database/sql` + `import _ "..."`, detail in 01.03); `init` for reading env and opening a connection in a library — as a rule no, use an explicit constructor.
- The file name does not affect identifier visibility; visibility is controlled exclusively by uppercase/lowercase (and `internal/` from 01.01). The file name affects **only** the order of `init` functions between files.
- `TestXxx`, `BenchmarkXxx`, `ExampleXxx` functions go in a `_test.go` file, regardless of whether that file is white-box or black-box.
- `export_test.go` convention: a white-box `_test.go` file that only assigns unexported values to exported test-only variables; it does not enter `go build`, only `go test`.

### Example 1 — Multiple files, one namespace

#### What happens here

`NewItem` calls `normalizeSKU` from another file without an import. `normalizeSKU` is not part of the API. A client outside package `catalog` sees only `Item` and `NewItem` — `normalizeSKU` does not exist for them, same as an unexported field from 01.01.

### Example 2 — White-box vs black-box test in the same directory

(The code is identical to the mechanism above — `ids_test.go` + `item_export_test.go`.)

#### What happens here

The white-box test tests a helper that never leaves the package. The black-box test confirms the contract other packages see. `go test ./catalog/...` runs both in the same test binary; failure of one does not mean failure of the other, and both make sense in the same PR.

### Example 3 — `init` caution: implicit env vs explicit constructor

```go
package featureflags

import "os"

var enabled map[string]bool

func init() {
    enabled = map[string]bool{
        "checkout_v2": os.Getenv("FF_CHECKOUT_V2") == "1",
    }
}

func On(name string) bool {
    return enabled[name]
}
```

Better API for testing:

```go
package featureflags

type Flags struct {
    values map[string]bool
}

func FromEnv(getenv func(string) string) Flags {
    return Flags{values: map[string]bool{
        "checkout_v2": getenv("FF_CHECKOUT_V2") == "1",
    }}
}

func (f Flags) On(name string) bool {
    return f.values[name]
}
```

#### What happens here

The first version loads env in `init`, thus **before** `main()` even starts — tests must touch process env (`os.Setenv`) and suffer global state that does not reset automatically between test functions. The second version injects `getenv` as a parameter: no hidden start, `FromEnv(func(string) string { return "1" })` in a test is fully deterministic, without a single `os.Setenv` call.

### Example 4 — Order of `init` across two files of the same package

```go
// featureflags/a_flags.go
package featureflags

func init() {
    println("a_flags: init")
}
```

```go
// featureflags/b_flags.go
package featureflags

func init() {
    println("b_flags: init")
}
```

#### What happens here

The output is `a_flags: init` then `b_flags: init`, because `go build` presents files to the compiler in lexical order of names (`a_flags.go` before `b_flags.go`). If the files change name to `x_flags.go` and `y_flags.go`, the relative order stays the same (`x` before `y`), but the absolute place relative to other package files changes. This is why in production code order between files is not used as a carrier of logic — at most one `init` per package is used when order matters, or an explicit `Register` called from `main`.

### Example 5 — Name conflict in a package

```go
package report

func build() string { return "a" }

// another file must not:
// func build() string { return "b" }
```

#### What happens here

Two `build` in the same package, in any two files, do not compile — `build redeclared in this block`. The solution is a different name (`buildSummary`, `buildDetail`) or one function with a parameter/branching that covers both cases — never “hide it in another file”, because a file does not create a new namespace.

### Example 6 — Multiple `init` functions in the same file

```go
package startup

func init() {
    println("startup: init #1")
}

func init() {
    println("startup: init #2")
}

func init() {
    println("startup: init #3")
}
```

#### What happens here

All three functions are legal in the same file — Go does not require a unique name because `init` is not an ordinary declaration that enters the symbol table by name. The output is always `#1`, `#2`, `#3`, in that order, because order **within** one file is appearance order in the text — that is guaranteed by the language specification, unlike order between files which depends on the file name.

## Decision analysis

| Decision | Motive |
|----------|--------|
| Split files by topic (`parse.go`, `store.go`) | Readability; namespace stays shared regardless of the split |
| Helpers as unexported | API stays thin; internal logic changes without fear of breaking clients |
| White-box for invariants | Faster feedback on internal logic, direct access to helpers |
| Black-box for the contract | Documents how a client must live with the public API |
| Explicit `New`/`FromEnv` instead of `init` with I/O | Testability, predictable moment of side effects |
| At most one `init` per package when order must be clear | Avoids depending on lexical file names as a hidden contract |
| `export_test.go` instead of permanent export | Test gets access to an internal detail without expanding the production API |
| `=` instead of `:=` when the intent is assignment to a package-level variable | Avoids silent shadowing that the compiler does not report as an error |

## Trade-offs

- White-box tests are more brittle on helper refactor (renaming a helper breaks the test), but black-box tests do not see edges and can miss an internal regression.
- More small files help navigation through the IDE; too many files of 15–20 lines each make reviewing the package as a whole in one pass harder.
- `init` for driver registration is short, clear, and common; the same mechanism for configuration hides errors until runtime and complicates tests.
- Exporting an identifier “only for test” expands the public API forever in the eyes of semver users — a cheap decision today, expensive to withdraw later.
- Order of `init` between files is predictable (lexical by name), but relying on it in production code means renaming a file (a purely cosmetic change) changes program behavior — a risk not worth saving one explicit call.

## Common mistakes

### 1. Duplicated helper function instead of one place

- **Wrong:** The same small helper (e.g. string normalization) written again in two files of the same package because the author does not notice it already exists.
- **Effect:** Two implementations diverge over time — a bug fix in one does not transfer to the other; tests pass for one path and not for the other.
- **Fix:** Search the package (`grep`/IDE “find usages”) before writing a new helper; if a similar one already exists, extend it instead of copying.

### 2. `init` that panics on bad env

- **Wrong:** `init()` reads `os.Getenv` and immediately `panic`s if the variable is not set.
- **Effect:** The program crashes at start, before it manages to parse flags or print `--help`; the error message is unclear because it happens before any log initialization.
- **Fix:** Move env reading into an explicit `FromEnv`/`New` called from `main()`, where the error can be returned as `error` and printed with context.

### 3. Tests exclusively white-box

- **Wrong:** The whole test package lives in `package foo`, no test imports `foo` as an external client.
- **Effect:** Refactoring an internal helper breaks “all green” with no check that the public contract (what the client actually calls) stayed intact.
- **Fix:** Add at least one `package foo_test` file that tests only the exported API, as a documentation layer that survives internal refactors.

### 4. `package foo_test` that tries to read unexported

- **Wrong:** A test in `package foo_test` writes `foo.internalField` or `foo.helperFunc(...)`.
- **Effect:** `go build`/`go test` refuses with `undefined: foo.internalField` — a black-box package has no access to anything unexported, no matter how much the test “must” see that detail.
- **Fix:** Move that check into a white-box test (`package foo`) or, if the detail is truly important to the client, consider whether it should become part of the public API.

### 5. Global state mutated from `init` and from tests in parallel

- **Wrong:** `init()` fills a package-level map; tests that run with `-parallel` additionally mutate it without locking.
- **Effect:** Tests are flaky — they pass individually, occasionally fail in a package, depending on order and `go test` parallelism.
- **Fix:** Remove shared state from `init`; each test creates its own instance through a constructor, or uses `t.Cleanup` to restore state if shared state must exist.

### 6. Believing that a file creates a new namespace

- **Wrong:** The assumption that `filea.go` “does not see” `fileb.go` in the same package, so an identifier is deliberately duplicated “to avoid a dependency”.
- **Effect:** The first compile attempt immediately fails with `redeclared in this block`; or, worse, the author renames one of the two to avoid the conflict and now there are two nearly identical functions that diverge.
- **Fix:** Accept that a package is one symbol table; organize files by topic for readability, not by imagined isolation that does not exist.

### 7. Relying on `init` order between files as a contract

- **Wrong:** Logic assumes that `init` in `network.go` surely finishes before `init` in `metrics.go` because “it has always been that way”.
- **Effect:** Renaming a file (with no content change) silently changes the order and breaks program behavior, with errors that are hard to connect to the cause.
- **Fix:** Use at most one `init` per package for anything order-sensitive, or an explicit `Register`/`Wire` called from `main` where the order is visible in the code itself, not in the file name.

### 8. Permanently exporting a test-only helper outside `export_test.go`

- **Wrong:** Instead of an `export_test.go` file that enters only `go test`, the author moves `normalizeSKU` into an ordinary `ids.go` file with uppercase (`NormalizeSKU`) “so tests have access”.
- **Effect:** A test-only need becomes a lasting part of the public API, visible also to clients who will never write a test — the semver contract expands without a real need.
- **Fix:** Keep test-only bridges exclusively in `_test.go` files (ideally `export_test.go`); if something is truly needed by production clients too, export it consciously in an ordinary file, with a doc comment that justifies it.

### 9. Shadowing a package-level variable instead of assignment

- **Wrong:** Inside a function one writes `count := 0` thinking it resets package-level `count`, while actually creating a new local variable.
- **Effect:** Package-level state stays untouched, while the code “looks” like it changes it; the bug is hard to spot because there is no compiler error, only wrong runtime behavior.
- **Fix:** Use `=` (ordinary assignment) when the intent is to change an existing package-level variable; use a different name for a local variable if the intent is not assignment, so shadowing is obvious at a glance.

## Idiomatic Go

- The stdlib splits packages into multiple files (`net/http` has `server.go`, `client.go`, `transport.go`, ...) with one shared namespace — inspiration for organization by topic, not by file size.
- Blank import plus `init` registration is idiomatic exactly for drivers and formats: `import _ "github.com/jackc/pgx/v5/stdlib"` — in detail in 01.03.
- Prefer constructors (`New`, `Open`, `FromEnv`) over global state filled in `init`; keep global state at an absolute minimum.
- `ExampleXxx` tests are almost always in black-box style (`package foo_test`), because they document the API as a client sees it, not how it is assembled inside.
- When you need deterministic initialization order, write it explicitly (`Register` called from `main`) — do not rely on alphabetical file name order.
- `go vet` does not report shadowing by default; if the team often makes this mistake, consider `go vet -vettool` with the `shadow` analyzer as an extra CI step.

A short guide through the three test file forms, for quick decisions when writing a new test:

| Situation | File form | What the test sees |
|-----------|-----------|--------------------|
| You test an internal helper or invariant | `package foo` in `_test.go` | Everything, including unexported |
| You test the public contract as a client | `package foo_test` | Only exported |
| You need an internal detail ONLY for the test, without permanent export | `export_test.go` (`package foo`) + a separate `package foo_test` test | Test-only bridge; production does not see it |

## Practical scenario

In package `billing` the team has `parse.go`, `tax.go`, `invoice.go`. A junior programmer exports `ParseLine` to test it from the `billing_test` package (black-box), instead of writing a white-box test in `package billing`. After a month another service in the same monorepo discovers `ParseLine` in `go doc` and starts using it directly — a dependency on an internal CSV line format becomes a public contract with no intent. Code review introduces a fix: white-box test in `package billing` for `parseLine` (now lowercase again); the public API stays only `InvoiceFromCSV([]byte) (Invoice, error)`. Breaking the line format returns to being an internal matter of package `billing`; semver stays calm because the public signature did not change.

In parallel, the same team had an `init()` in `tax.go` that read tax rates from an env variable at process start. When CI started running tests in parallel for multiple packages, intermittent failures appeared because two tests in the same process (inside the same `go test` binary) shared that global rate map. Replacing with `TaxRates.FromEnv(os.Getenv)` called explicitly from `main()` and from test setup removed the flaky behavior — each test now creates its own instance.

A third bug in the same week was subtler: a senior programmer “fixed” the failed-parse counter in `parse.go` by adding `failedCount := failedCount + 1` inside `ParseLine`, thinking it increments package-level `failedCount` declared in `invoice.go`. The compiler reported nothing — `:=` created a new local variable that shadows the package-level name, uses it once, and throws it away on function exit. The `failedCount` metric the dashboard read stayed frozen at zero for weeks, even though parsing was really failing. The review checklist added an item: “every assignment to a package-level counter goes through an exported method (`(*Stats) IncFailed()`), never by direct assignment by name” — which also solves concurrent access from multiple `goroutine` execution threads.

## Check questions

1. **Must files in the same package import each other?**
   **Answer:** No. They share one namespace from the moment of parsing; `import` exists only for access to **other** packages.

2. **When to use `package foo_test`?**
   **Answer:** When you test the public API as an external client (black-box / documentation test) and do not need access to unexported details.

3. **Why does `init` with I/O make tests and program startup harder?**
   **Answer:** Because it runs before `main()` and before CLI flag parsing, introduces global side effects, and the order of its execution between files depends on the file name, not on explicit intent in code.

4. **What does a white-box test see?**
   **Answer:** All identifiers of the same package, including unexported — because a white-box test file shares the `package` clause with the rest of the package.

5. **Does the file name control identifier export?**
   **Answer:** No. Export is controlled exclusively by uppercase/lowercase initial letter of the identifier (and the `internal/` path from 01.01); the file name affects only the order of `init` functions between files.

6. **In what order do `init` functions of package `A` that imports package `B` run?**
   **Answer:** First package-level variables and `init()` functions of package `B` (and everything `B` further imports) finish completely, and only then variables and `init()` functions of package `A`.

7. **What happens when trying to define two functions of the same name in two files of the same package?**
   **Answer:** `go build` refuses with error `redeclared in this block` — there is no overlapping by signature (function overloading) nor isolation by file inside a package.

8. **What is `export_test.go` for and why does it not expand the public API?**
   **Answer:** It assigns an unexported value to an exported test-only variable from a white-box `_test.go` file; since `_test.go` files do not enter ordinary `go build`, that variable exists only in the test binary, never in production.

9. **Is the order of multiple `init()` functions in one file guaranteed?**
   **Answer:** Yes — appearance order in the text, top-to-bottom, unlike order **between** files which depends on lexical file name and should not be used as a contract.

10. **Why does `count := 0` inside a function not reset package-level `var count int`?**
    **Answer:** `:=` creates a new local declaration that shadows the package-level name within its scope; to touch the existing package-level variable, ordinary assignment `count = 0` is needed, without `:=`.

## Mechanism — deeper: package as one symbol table

### How the compiler actually “sees” a directory

When you run `go build ./catalog`, the tool:

1. Lists all `.go` files in `catalog/` **except** `*_test.go` (for ordinary build).
2. Sorts them by name (lexical).
3. Parses all as **one** package — one name map.
4. Only then checks types, generates code.

That is why there is no “file import”. There is only a `package` clause + (for other packages) an `import` path.

**Predict:** You have `catalog/a.go` and `catalog/b.go`. In `a.go` is `func helper()`. In `b.go` you write `helper()` without an import. Does `go build` work?

**Answer:** Yes, if they are the same `package catalog`. No, if `b.go` is mistakenly `package catalogapi` — then those are two packages in the same directory, which is otherwise forbidden (except the `_test` exception).

### Unexported API inside a package — a thin public belt

```text
┌─────────────────────────────────────┐
│  package catalog (one room)         │
│  NewItem, Item     ← exported       │
│  normalizeSKU      ← unexported     │
│  validName         ← unexported     │
└─────────────────────────────────────┘
         ▲
         │ import "…/catalog"
┌────────┴────────┐
│  package httpapi │  sees only NewItem, Item
└─────────────────┘
```

Internal helpers may be called from any file of the room. A client in another room does not see them — not because they are in a “private file”, but because of the lowercase initial letter.

### `init` and variables: dependencies, not writing order

```go
package boot

var a = f()
var b = a + 1

func f() int {
	println("f")
	return 2
}

func init() {
	println("init", b)
}
```

**Predict the output:**

**Answer:** first `f` (because `a` must be computed), then `init 3` — because `b` depends on `a`, and `init` goes after all package-level variable initializations in that package.

If you write:

```go
var b = a + 1
var a = f()
```

the compiler still respects the dependency: `a` before `b`, regardless of line order — as long as there is no cycle (`var a = b; var b = a` → error).

### White-box test and `-race` on package-level state

```go
// catalog/stats.go
package catalog

var parses int

func noteParse() { parses++ }
```

A white-box test that calls `noteParse` in parallel without protection can introduce a race **in the test**. `go test -race` catches that. Fix: do not share a global counter; or use `t.Parallel()` only when there is no shared state; or protect with a Mutex if it really must.

### `TestMain` and package initialization

```go
func TestMain(m *testing.M) {
	// here the package (and its init) ARE ALREADY initialized
	code := m.Run()
	os.Exit(code)
}
```

**Predict:** Can `TestMain` prevent execution of `init` of the package under test?

**Answer:** No. `init` and package-level variables finish before `TestMain`. If `init` panics, the test binary crashes before `TestMain`.

## Example 9 — `init` registration vs constructor (side by side)

| Approach | When | Test |
|----------|------|------|
| `init` + blank import | driver, codec registration | harder to isolate |
| `New` / `FromEnv` | configuration, I/O, DB | easy fake |

For `featureflags`, the constructor wins. For a `database/sql` driver, `init` registration is the idiom (01.03).

## Common mistakes — additional

### 10. `TestMain` that calls `os.Exit` before `m.Run` without cleanup

- **Effect:** Skipped tests; confusing CI.
- **Fix:** Always `code := m.Run(); ...; os.Exit(code)`.

### 11. Mixing `package foo` and `package Foo` (uppercase)

- **Effect:** The compiler treats it as another package / name error.
- **Fix:** Package name lowercase, stdlib convention.

### 12. Relying on order of `_test.go` files

- **Effect:** Tests that depend on the execution order of other tests.
- **Fix:** Each test independent; `t.Cleanup` for state.

## Check questions — additional

11. **Does `go build` include `_test.go`?**  
    No. Only the `go test` build.

12. **What happens with package-level `var` before the first `init()`?**  
    They are initialized (by dependencies) before any `init` in that package.

13. **Why does Example usually go in `package foo_test`?**  
    Because it documents the public contract as a client sees it.

14. **Can white-box and black-box test be in the same directory?**  
    Yes — that is the allowed exception to “one package per directory”.

15. **Why is shadowing with `:=` not “redeclared in this block” at package level?**  
    Because it is a new declaration in a narrower scope (function/block), not another declaration at the same package level.

## Summary

Inside a package one namespace rules regardless of the number of files: all identifiers are shared, including unexported, while the boundary toward other packages stays the same as in 01.01. A duplicate name at package level is a compilation error, not a style problem. `init` runs by a strict but subtle order — dependencies before the dependent package, variables before `init()` functions, `init()` functions by files in lexical order — and exactly why it is not used for sensitive logic without an explicit `Register`/`New` call. A test file chooses `package foo` (white-box, sees everything) or `package foo_test` (black-box, sees only the API) depending on whether interior or contract is being tested.
