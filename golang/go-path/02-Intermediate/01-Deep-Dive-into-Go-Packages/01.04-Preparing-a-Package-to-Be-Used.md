# 01.04 Preparing a package for use: stable API, documentation, versions

> **Go Path - Zero to Gopher** / **02 Intermediate → Deep dive into Go Packages** / Lesson 01.04

## Lesson goals

After this lesson you can:

- distinguish a compatible public API extension from a **breaking change**, at the level of a concrete signature;
- apply **semantic import versioning** (v2+ with `/v2` in the import path) and explain why Go treats `v1` and `v2` as literally different packages;
- use `go doc` and **Example** tests (`ExampleXxx` functions that compile and run) as living documentation;
- write a short README that points to `go doc`, not duplicates it;
- return an **interface** (an `interface` type contract without a concrete implementation) from the package boundary instead of a concrete infrastructure type (e.g. `*sql.DB`).

## Prerequisite

- 01.01–01.03 (package, export, `internal/`, shared namespace, `init`, import paths, import cycle).
- Basic `go.mod`, version tags (`v1.2.3`).
- Experience with `go test` and at least one `ExampleXxx` preferred, but not required.

## Problem this lesson solves

A package “works for me”, but in practice the team collides with:

- clients that depend on a concrete `*sql.DB` instead of a small **interface**, so every storage change breaks half the services;
- a README that tells marketing, while `go doc` is empty or stale;
- a major break published without `/v2` in the import path, so `go get` quietly pulls the broken version into existing code;
- adding a field to an exported struct that breaks binary clients or JSON contracts without any notice.

This lesson teaches how a package becomes a **product for other programmers**, not just a folder of code that happens to compile.

## Mental model

Publishing a package is issuing a **contract** with four parts:

1. **Signature** — exported functions, types, methods; what is visible in `go doc`.
2. **Documentation** — doc comments plus Example tests that compile and run, so they cannot quietly go stale without a red test.
3. **Version** — semver, and for major ≥ 2, a `/vN` segment in the import path itself (part of the Go module system, not only a git tag).
4. **Implementation boundary** — what the client must not see: concrete drivers, mutexes, internal maps, SQL schema.

If you change the signature, the client must change **their** code to still compile. If you change only the body of an unexported function, the client knows nothing about it — that is the advantage of a thin API from 01.01, now applied to long-term maintainability.

## Mechanism

### What the compiler (and client) sees as a breaking change

Before you look at examples, it is worth having a precise list — because “is this breaking” is not a matter of taste, but whether the client's **existing, unchanged** code still compiles and behaves the same.

Compatible extensions (safe in a minor version):

- a new exported function, type, or constant — existing calls reference nothing new, so they continue to compile;
- a new field in a struct that the client only reads by name (`v.NewField`) — existing access to old fields stays untouched;
- a new method on a **concrete type** (`struct`) — does not affect existing calls.

Breaking (requires a major version or `/vN`):

- removing or renaming an exported symbol — every call that uses it stops compiling;
- changing the type of a parameter or result of an existing function/method — the signature does not match, `go build` refuses the calling code;
- changing meaning without changing the signature (e.g. `Format` now returns a rounded value instead of the exact one) — **quietly** breaks the client, because it compiles identically but produces a different result; this is the most dangerous kind of break because no tool catches it automatically;
- adding a new method to an existing exported **interface** that clients implement — every existing implementation suddenly does not satisfy that interface, so `go build` refuses everywhere that implementation is used as a value of that interface.

**Predict:** package `orderstore` has `type Store interface { Get(...) }`. You add a new method `Delete(...)` on that interface. Which code breaks, and why exactly that?

**Answer:** Every package that has its **own implementation** of `Store` breaks (e.g. a test fake that implements only `Get`) — that type suddenly does not implement `Store` because it is missing `Delete`, so every place that assigns it to a variable of type `Store` stops compiling. Code that only **uses** an existing implementation (`orderstore.NewPG(db)`) does not break, because `NewPG` is the one that must get a `Delete` method — which is the package author's job, not the client's. That is why “adding a method to an existing interface” is more dangerous than adding a method to a `struct`: the number of hit places depends on how many **foreign** implementations exist, which the package author often cannot even see.

### Semantic import versioning — `/v2` is part of the path, not only a git tag

For `v0` and `v1`, the import path has no version suffix: `example.com/shop/quoteformat`. When a package makes a breaking change and publishes `v2.0.0`, the Go module system requires that the **import path** change to include `/v2`:

```text
go.mod:  module example.com/shop/quoteformat/v2
import:  "example.com/shop/quoteformat/v2"
tag:     v2.0.0
```

The mechanism behind this is not cosmetic. For the Go toolchain, `example.com/shop/quoteformat` and `example.com/shop/quoteformat/v2` are **two completely different packages** — different path, different `package` clause space (they can even have a different package name, though convention keeps the same name), and most importantly: **both can exist at the same time in the same binary file**. If module `A` still depends on `quoteformat` v1, and module `B` (which `A` also imports) depends on `quoteformat/v2`, `go build` does not create a version collision — it simply pulls both, as two independent packages, because that is what they are from the dependency graph's perspective.

This solves the problem other ecosystems call “dependency hell”: there is no need for the whole transitive dependency graph to migrate to v2 at once for the build to pass. The cost is that the package author must update **all** internal imports (both in `go.mod`, and in every `.go` file that imports its own v1 path) when making v2 — an easy place for a mistake if even one file is forgotten.

**Predict:** a client has `import "example.com/shop/quoteformat"` (v1) in their code and runs `go get example.com/shop/quoteformat/v2`. Do their old calls automatically switch to the v2 API?

**Answer:** No — `go get .../v2` adds a **new** dependency beside the existing one; the old `import` line still points at v1 and still uses v1 signatures. The client must manually change the `import` path to `.../v2` and adapt calls to the new signature — that is intentional, because automatic signature migration is not something a tool may do without human semantic review.

### `go doc` — how it reads comments

```bash
go doc ./quoteformat
go doc quoteformat.Format
```

`go doc` does not execute code or parse README — it reads **doc comments** directly from source code: the comment block immediately above the `package` clause (mechanism from 01.01) for the package, and the comment block immediately above each exported declaration for that declaration. The convention is that a doc comment starts with the **name** of the symbol (`// Format returns ...`, not `// This function returns ...`) — `go doc` and IDE hover rely on that pattern when generating a short description in the symbol list.

### Example tests — documentation that runs

An `ExampleXxx` function in a `_test.go` file is not an ordinary helper function — `go test` **recognizes it by name** (`Example` prefix) and treats it specially: it runs the body, captures everything that goes to standard output, and compares it with the text in the `// Output:` comment at the end of the function. If they do not match character by character (after trimming whitespace at line ends), the test fails — identical to a `TestXxx` that calls `t.Fatal`.

```go
package quoteformat_test

import (
    "fmt"

    "example.com/shop/quoteformat"
)

func ExampleFormat() {
    s := quoteformat.Format(quoteformat.Money{
        MinorUnits: 25050,
        Currency:   "RSD",
    })
    fmt.Println(s)
    // Output:
    // 250,50 RSD
}
```

Three consequences of this mechanism:

1. `go doc quoteformat.Format` shows this example **below** the function's doc comment, automatically — no double writing of the example in a comment and in a test.
2. `go test ./...` runs it like any other test; if `Format` changes so it returns a different string, this test goes red immediately, before the PR is even merged.
3. The naming convention binds the example to exactly one symbol: `ExampleFormat` for function `Format`, `ExampleMoney_String` for method `String` on type `Money` (`Type_Method` with an underscore), `Example` (without a suffix) for an example that covers the whole package generally.

When print order is not deterministic (e.g. iterating a `map`), use `// Unordered Output:` instead of `// Output:` — `go test` then compares the set of lines regardless of order, not exact text line-by-line.

### README as a pointer to `go doc`, not a duplicate

README has a different role from `go doc`: a quick entry (what the package does in one or two sentences, requirements like Go version, `go get` command), with a link/instruction “see details in `go doc`”. When README starts listing every symbol and its signature, two sources of truth start to diverge — someone changes the signature, the doc comment is updated (because it is next to the code, in the same PR), README stays stale because it is in another file nobody remembered to open.

### `interface` at the package boundary instead of a concrete infrastructure type

Return an `interface` (an `interface` type contract without a concrete implementation), not a concrete infrastructure type, when the client needs only behavior, not implementation detail:

```go
type Store interface {
    Get(ctx context.Context, id string) (Order, error)
    Save(ctx context.Context, o Order) error
}
```

instead of a function returning `*sql.DB` or `*sql.Rows` directly. The mechanism why this matters: `*sql.DB` is a **concrete type** with dozens of methods tied to one technology (SQL via `database/sql`). When you return it from a domain package constructor, every client that wants to test their code must make a **real** (or mock) `*sql.DB`, which means either a real database in the test, or a library to simulate the SQL protocol — much harder than writing a fake type that implements the `Store` interface with two methods. Additionally, changing storage (Postgres → some other database, or even a cache in front of the database) requires that **every** client that captured `*sql.DB` change their code — while a client that depends on `Store` notices nothing, because `Store` is a contract, not an implementation.

### Trace: what actually breaks when `*sql.DB` leaks

It is worth seeing a concrete trace, not only the claim “do not leak infrastructure”. Imagine that `orderstore.New` (bad version) returns `*sql.DB` directly:

```go
func New(dsn string) (*sql.DB, error) {
    return sql.Open("pgx", dsn)
}
```

Three different clients in the same monorepo, during the first year, wrote:

1. HTTP handler: `db, _ := orderstore.New(dsn); rows, _ := db.Query("SELECT ...")` — a direct SQL query written outside package `orderstore`.
2. Test: `db, _ := orderstore.New(testDSN)` — a real Postgres in a Docker container only to test a handler that does not even touch SQL logic directly.
3. Batch script: `db.SetMaxOpenConns(50)` — configures the connection pool directly on the returned `*sql.DB`.

When the team decides to put a cache in front of the database (or migrate to a completely different database), all three break the same day: (1) the handler's SQL query does not exist in the new storage; (2) the test cannot run a Postgres container for a technology that no longer uses it; (3) `SetMaxOpenConns` does not exist on the new connection type. None of these three calls **should have** existed outside the `orderstore` package — they exist only because the concrete type was available, not because it was needed.

With a `Store` interface (Example 1), none of these three places would have anything to capture except `Get`/`Save` methods — the SQL query, connection pool setting, and technology choice stay locked inside the `orderstore` package, where a storage change means editing one file, not archaeology through the whole monorepo.

## Rules and syntax

- Every exported symbol has a doc comment that starts with the symbol name.
- Package doc stays in `doc.go` or the main file (mechanism from 01.01).
- Do not export a type or field only so a test passes (mechanism from 01.02 — use a white-box test or `export_test.go`).
- For major v2: update the `module` line in `go.mod` **and** all internal imports that point at your own package.
- Example name: `ExampleFunction`, `ExampleType_Method`; `// Output:` or `// Unordered Output:` comment at the end of the function.
- Return an `interface` from the package boundary when the client needs swappability/testability; return a concrete type when the package itself is infrastructure and there is nothing to abstract.

## Examples

### Example 1 — Thin API with an interface instead of a concrete type

```go
// Package orderstore stores orders. Clients depend on Store, not on a SQL driver.
package orderstore

import (
    "context"
    "database/sql"
    "fmt"
)

// Order is the public model.
type Order struct {
    ID     string
    Total  int64
    Status string
}

// Store is the contract the HTTP layer needs.
type Store interface {
    Get(ctx context.Context, id string) (Order, error)
    Save(ctx context.Context, o Order) error
}

type pgStore struct {
    db *sql.DB
}

// NewPG creates a Store over database/sql. The concrete type is not exported.
func NewPG(db *sql.DB) Store {
    return &pgStore{db: db}
}

func (s *pgStore) Get(ctx context.Context, id string) (Order, error) {
    var o Order
    err := s.db.QueryRowContext(ctx,
        `SELECT id, total_minor, status FROM orders WHERE id = $1`, id,
    ).Scan(&o.ID, &o.Total, &o.Status)
    if err != nil {
        return Order{}, fmt.Errorf("orderstore get: %w", err)
    }
    return o, nil
}

func (s *pgStore) Save(ctx context.Context, o Order) error {
    _, err := s.db.ExecContext(ctx,
        `INSERT INTO orders (id, total_minor, status) VALUES ($1, $2, $3)
         ON CONFLICT (id) DO UPDATE SET total_minor = EXCLUDED.total_minor, status = EXCLUDED.status`,
        o.ID, o.Total, o.Status,
    )
    if err != nil {
        return fmt.Errorf("orderstore save: %w", err)
    }
    return nil
}
```

#### What happens here

The handler depends on `orderstore.Store`, not on `*pgStore` or `*sql.DB`. A test can replace the Postgres implementation with an in-memory one (`map[string]Order` behind the same interface) without touching calling code. `*sql.DB` does not leak into the API — `pgStore` is unexported, visible only through the `Store` contract. SQL uses `$1` placeholders — never concatenation of user input into the query.

### Example 2 — Fake implementation instead of a real database in a test

```go
package orderstore_test

import (
    "context"
    "sync"
    "testing"

    "example.com/shop/orderstore"
)

type fakeStore struct {
    mu   sync.Mutex
    data map[string]orderstore.Order
}

func newFake() *fakeStore { return &fakeStore{data: make(map[string]orderstore.Order)} }

func (f *fakeStore) Get(_ context.Context, id string) (orderstore.Order, error) {
    f.mu.Lock()
    defer f.mu.Unlock()
    o, ok := f.data[id]
    if !ok {
        return orderstore.Order{}, orderstore.ErrNotFound
    }
    return o, nil
}

func (f *fakeStore) Save(_ context.Context, o orderstore.Order) error {
    f.mu.Lock()
    defer f.mu.Unlock()
    f.data[o.ID] = o
    return nil
}

func TestHandlerWithFakeStore(t *testing.T) {
    var store orderstore.Store = newFake()
    ctx := context.Background()
    if err := store.Save(ctx, orderstore.Order{ID: "o-1", Total: 500, Status: "new"}); err != nil {
        t.Fatal(err)
    }
    got, err := store.Get(ctx, "o-1")
    if err != nil {
        t.Fatal(err)
    }
    if got.Total != 500 {
        t.Fatalf("Total = %d", got.Total)
    }
}
```

#### What happens here

`fakeStore` implements `orderstore.Store` with two methods and a map in memory — no database, no network, the test takes microseconds. `var store orderstore.Store = newFake()` is an explicit check that `*fakeStore` satisfies the interface at the assignment site; if `Store` gets a new method (as in “Predict” from Mechanism), exactly this line would be the first to report a compilation error.

### Example 4 — Leaking a concrete type (anti-example) and the fix

```go
package badmail

import "net/smtp"

// Client exports *smtp.Client details indirectly through a field.
type Client struct {
    SMTP *smtp.Client
}

func (c *Client) Send(to, body string) error {
    _ = to
    _ = body
    return nil
}
```

```go
package mailer

// Client is closed; SMTP details are private.
type Client struct {
    addr string
    send func(addr string, to []string, msg []byte) error
}

func New(addr string) *Client {
    return &Client{addr: addr, send: defaultSend}
}

func defaultSend(addr string, to []string, msg []byte) error {
    _ = addr
    _ = to
    _ = msg
    return nil
}

func (c *Client) Send(to, body string) error {
    msg := []byte("To: " + to + "\r\n\r\n" + body)
    return c.send(c.addr, []string{to}, msg)
}
```

#### What happens here

In the bad version the client touches the `SMTP` field directly and ties itself to the `net/smtp` type — changing transport (e.g. switching to an HTTP-based email API) breaks every client that read that field. In the good version, `send` is a swappable field (function value, topic of the basic functions course) that a test sets to a fake implementation; production uses `defaultSend`. The public API stays only `New` and `Send`, regardless of what changes inside.

### Example 5 — README skeleton alongside a package

```markdown
# quoteformat

Formats monetary amounts for display.

## Requirements

Go 1.22+

## Installation

go get example.com/shop/quoteformat

See `ExampleFormat` in `go doc` for the exact output format.

## Semver

v1: stable `Format`/`Money` API. Breaking changes go into `quoteformat/v2`.
```

#### What happens here

README directs (requirements, installation, short entry to `go doc`); signature and behavior details live in `go doc` and Example tests. When `Format` changes, the doc comment and Example are updated in the same PR as the code — README stays accurate without extra work, because it duplicates nothing that `go doc` already shows.

### Example 6 — `/v2` path in practice

```text
example.com/shop/quoteformat/       (v1, still exists for old clients)
├── go.mod              module example.com/shop/quoteformat
└── quoteformat.go      package quoteformat

example.com/shop/quoteformat/v2/    (new directory OR new git tag + changed go.mod, by layout choice)
├── go.mod              module example.com/shop/quoteformat/v2
└── quoteformat.go      package quoteformat
```

```go
// v2/quoteformat.go
package quoteformat

// Money is an amount in the smallest units; v2 adds a required Scale field
// that v1 did not have — that IS a breaking change, hence v2.
type Money struct {
    MinorUnits int64
    Currency   string
    Scale      int
}
```

A client that wants v2:

```go
import "example.com/shop/quoteformat/v2"
```

#### What happens here

A major break (a new required field that changes the meaning of existing calls that build `Money{...}` without `Scale`) goes with a new import path. Old clients that still import `example.com/shop/quoteformat` (without `/v2`) continue to build with the old signature, untouched. New clients consciously choose the `/v2` path when they are ready for the new contract. Both packages can exist at the same time in the same `go.sum`, and even in the same final binary if different parts of the dependency graph require them.

## Decision analysis

| Decision | Motive |
|----------|--------|
| Return an `interface` from the boundary | Tests and implementation swaps without breaking the client |
| Example tests | Documentation that compiles and runs, not only is read |
| Thin export (01.01 principle, applied to the whole module) | Smaller breaking surface; easier refactor within a major version |
| `/v2` in the path | Clear, coexistent major line for the Go module system |
| Short README, points to `go doc` | One source of truth; less duplicate maintenance |
| Fake implementation in a test instead of a real database | Fast, deterministic tests without a network dependency |

## Trade-offs

- An interface with many methods is hard to implement in a test (every fake implementation must cover everything) — split large interfaces into smaller, focused roles whenever possible.
- An exported struct with public fields is convenient for the client, but every new required field can quietly change the meaning of existing composite literals without named fields — favor named fields in API documentation for exactly this reason.
- Too much API stability slows development (every change requires major thinking); too fast breaks without `/v2` discipline anger clients and spend trust.
- Documenting **all** code is unrealistic; focus on the exported API leaves the interior free to change without doc comment ceremony.
- A `/v2` line means duplicated maintenance (a bug fix must go into both directories if both have active clients) until old clients migrate — a time-limited but real cost.

## Common mistakes

### 1. Quiet meaning change without a signature change

- **Wrong:** `Format` changes the number of decimals or the rounding rule in a new minor version, the function signature stays the same.
- **Effect:** Client code still compiles identically, but produces a different result — the most dangerous kind of break, because `go build` does not catch it, only runtime behavior or, worse, a quietly wrong price display to the user.
- **Fix:** Treat a change of **meaning** as seriously as a signature change; if you change rounding, that goes into a major version or a new function (`FormatV2`) with an Example test that would catch the difference.

### 2. Exporting `*sql.DB` or an ORM type “temporarily”

- **Wrong:** A constructor returns `*sql.DB` directly “until the API is cleaned up”, or a domain type embeds `*gorm.DB` as an exported field.
- **Effect:** Clients capture the concrete type before you manage to hide it; migrating to another storage or a cache in front of the database becomes a breaking change for all of them, even though that should have been an internal detail.
- **Fix:** Return an `interface` (or at minimum, an unexported concrete type behind a constructor that returns an interface) from the first package version, even with one implementation.

### 3. A 200-line README that compiles no snippet

- **Wrong:** README lists every function with a code example that is never run through `go test` or `go vet`.
- **Effect:** The code example in README goes stale as soon as the signature changes; nobody notices until a new user reports that the example does not compile.
- **Fix:** Short README, with direction to `go doc`; real examples go as `ExampleXxx` functions that `go test` checks every time.

### 4. v2 module without `/v2` in the `module` line

- **Wrong:** The team tags `v2.0.0` with breaking changes, but `go.mod` still has `module example.com/shop/quoteformat` (without `/v2`).
- **Effect:** `go get` refuses or behaves unexpectedly — the Go module system requires that a major ≥ 2 module have a `/vN` suffix in the `module` line that matches the tag; without that, the version does not resolve correctly through the proxy and cache.
- **Fix:** On the first major break, update the `module` line to `.../v2` **before** tagging, and update all internal imports in the repository that point at your own package.

### 5. Adding a method to an exported `interface` that others implement

- **Wrong:** The `Store` interface gets a new method `Delete` in a minor version, “because it is just an addition”.
- **Effect:** Every foreign implementation (test fake, alternative backend) stops satisfying `Store` and no longer compiles — a classic minor version that behaves like a major break for implementers.
- **Fix:** Introduce a new, smaller interface (`Deleter`) that the client type-asserts when needed, or announce this as a major/`/v2` change if `Delete` is truly a necessary part of the base contract.

### 6. Package doc disappearing after a file refactor

- **Wrong:** The doc comment lived in `store.go`; a refactor moves content into multiple files and `doc.go` is never created, so the comment simply evaporates.
- **Effect:** `go doc ./orderstore` returns an empty or generic description; a new team member has nowhere to start without reading the implementation.
- **Fix:** On every refactor that touches a file with a package doc comment, move it (or leave a copy) into `doc.go` as a stable place that a refactor is less likely to “move” unconsciously.

### 7. Composite literal without named fields across versions

- **Wrong:** A client writes `quoteformat.Money{100, "RSD"}` (positional, without field names) instead of `Money{MinorUnits: 100, Currency: "RSD"}`.
- **Effect:** Adding a new field **between** existing ones in the struct definition (e.g. `Scale` before `Currency`) shifts which field corresponds to which positional value — it compiles, but with wrong meaning, with no error.
- **Fix:** Document (and lint; `go vet` helps partially) that a public struct from another package is always constructed with named fields; the package author adds new fields at the end of the definition as an extra precaution.

## Idiomatic Go

- The stdlib rarely breaks API; learn from `io`, `context`, `net/http` — multi-year stability comes from small, carefully chosen interfaces (`io.Reader` has one method).
- `Accept interface, return struct` is not absolute dogma — at the package boundary (ports to infrastructure) it is often the reverse: **return interface**, so the client does not depend on the implementation.
- `go generate` and similar tools (stringer and others) keep generated code in unexported space where possible.
- Tags and the proxy (`proxy.golang.org`) expect a correct semver format (`vMAJOR.MINOR.PATCH`) — an incorrect tag is quietly ignored by `go get`, which confuses until you check it directly.
- Example tests without an `// Output:` comment still compile (useful for code examples that cannot be verified deterministically), but are not run as a check — they are only shown in `go doc`.
- Community convention: a `// Deprecated:` comment in a minor version **before** the major break that actually removes the symbol — gives clients time to migrate, with tools (e.g. `staticcheck`) that highlight the struck-through name at the call site.

### Checklist before `v1.0.0`

1. Package doc exists and makes sense without reading the implementation.
2. Every export has a doc comment that starts with its name.
3. At least one Example with `// Output:` exists for the package's central function/type.
4. README is short and points to `go doc` instead of duplicating the reference.
5. There are no exported “temporary” fields or types left for debug or test.
6. An `interface` exists at every boundary where you expect an implementation swap (storage, transport, external service).
7. The decision about what is covered by the semver guarantee is written down — at least one sentence in README or `doc.go`.

## Practical scenario

Library `eventbus` v1 returns a concrete `*RedisBus` from its constructor. Three teams in the organization import Redis directly in their tests so they can instantiate `eventbus.New()`. On migration to NATS as broker, all those tests (and production code that somewhere called `.RedisSpecificMethod()`) break at once, because the concrete type leaked through the whole internal ecosystem.

The team introduces a fix in three steps: (1) `Bus` interface with two methods (`Publish`, `Subscribe`); (2) `NewRedis`/`NewNATS` factories that both return `Bus`, the concrete type stays unexported; (3) Example test (`ExampleNewRedis`) and README that points only to `go doc`. Incompatible changes (e.g. changing the `Publish` signature to take `context.Context`) go into a prepared `eventbus/v2`, with a clearly tagged `v2.0.0` version and an updated `module` line. Onboarding a new team now starts with `go doc ./eventbus` and one Example — without reading the Redis client library to understand how `eventbus` is used.

## Check questions

1. **What is semantic import versioning for v2+?**
   **Answer:** The module/import path includes `/v2` (or `/vN`) with matching git tags; Go treats such a package as a completely different package from v1, which allows both to coexist in the same binary file.

2. **Why do Example tests help the API more than comments with a code example?**
   **Answer:** They compile, they run under `go test`, and their `// Output:` is checked character by character — documentation cannot quietly go stale without a red test.

3. **Why not return `*sql.DB` from a domain package?**
   **Answer:** It leaks concrete infrastructure into the public API; every storage change or adding a cache becomes a breaking change for all clients that captured that concrete type, instead of an internal refactor that should not be felt outside.

4. **What usually breaks implementers of an exported interface?**
   **Answer:** Adding a new method to an existing interface — every foreign implementation that does not also get that method stops satisfying the contract and no longer compiles.

5. **What is a short README for alongside `go doc`?**
   **Answer:** A quick entry (requirements, installation, direction to details), while signatures, behavior, and examples live in doc comments and Example tests next to the code itself, as one source of truth.

6. **Why is a “quiet meaning change without a signature change” the most dangerous kind of breaking change?**
   **Answer:** Client code continues to compile identically, so no tool (compiler, `go vet`) reports it — the problem is discovered only through runtime behavior or, worse, through a quietly wrong result nobody notices in time.

7. **Does `go get module/v2` automatically migrate existing calls from the v1 to the v2 signature?**
   **Answer:** No — it adds v2 as a new, independent dependency beside the existing one; existing `import` lines and calls stay on v1 until the programmer manually changes them to the new path and signature.

8. **What does `go doc package.Function` show besides the function's own doc comment?**
   **Answer:** If a matching `ExampleFunction` (or `ExampleType_Function`) exists in the test file, `go doc` automatically appends it as a usage illustration, including the `// Output:` part.

9. **Why do three unrelated clients break the same day when `orderstore` changes databases, in the example with leaking `*sql.DB`?**
   **Answer:** Because all three, independently of each other, captured the concrete `*sql.DB` type and called methods specific to that technology (SQL query, connection pool setting) — none of those calls exist on the new storage type, while a `Store` interface with two methods would stay untouched.

## Mechanism — deeper: what breaks the client, and what does not

### Table: change → semver level

| Change | Typical semver | Why |
|--------|----------------|-----|
| New function `FormatWithScale` | minor | old calls untouched |
| New field at the end of an exported struct | minor* | caution: positional literals |
| Removed function | major | does not compile |
| Changed result type | major | does not compile |
| New method on an exported **interface** | major | breaks implementers |
| New method on an exported **struct** | minor | implementers are not hit |
| Different rounding with the same signature | major (semantic) | quiet break |
| Bug fix that returns the correct result | patch | caution if someone depended on the bug |

\*Still document named fields in the literal.

### `pkg.go.dev` and `go doc` as the same source

`pkg.go.dev` renders the same doc comments and Example tests you see locally with `go doc`. If README tells a different story from `go doc`, trust goes to the code — that is why README stays a pointer to documentation in code.

```bash
go doc -all ./quoteformat
go test ./quoteformat -run Example
```

### Deprecation before a major break

```go
// Format is deprecated: use FormatMoney.
//
// Deprecated: use FormatMoney from v1.4; Format is removed in v2.
func Format(m Money) string {
	return FormatMoney(m)
}
```

`staticcheck` and the IDE show deprecation. A minor version gives time; major/`/v2` removes.

**Predict:** Can you in a minor version remove `Format` if it was Deprecated earlier?

**Answer:** Semver strictly: removing an exported symbol is major. Deprecation does not give permission for a quiet delete in minor — it only announces a future major.

### Interface at the boundary: small, focused

```go
type Getter interface {
	Get(ctx context.Context, id string) (Order, error)
}

type Saver interface {
	Save(ctx context.Context, o Order) error
}

type Store interface {
	Getter
	Saver
}
```

When you add `Delete`, you can introduce:

```go
type Deleter interface {
	Delete(ctx context.Context, id string) error
}
```

Existing fakes for `Store` do not break until someone requires `Deleter`. That is an alternative to “add a method to Store in a minor”.

### Trace: JSON/semver trap with a new field

```go
type Money struct {
	MinorUnits int64  `json:"minor_units"`
	Currency   string `json:"currency"`
	// new:
	Scale int `json:"scale"`
}
```

An old client sends JSON without `scale` → in Go `Scale` becomes **zero value** `0`. If `0` means “wrong” and not “default 2”, you quietly change behavior. Better: pointer `*int` or `omitempty` + documented default behavior in `Format`.

## Example 8 — `/v2` migration checklist for a library author

1. Branch `v2`.
2. `go.mod`: `module example.com/shop/quoteformat/v2`.
3. Replace all internal imports to `.../v2`.
4. Breaking API (e.g. required `Scale`).
5. Example + doc updated.
6. Tag `v2.0.0`.
7. README: how to migrate from v1 (old → new table).
8. Do not delete v1 immediately — leave tags / major line until consumers migrate.

## Common mistakes — additional

### 8. Breaking change in `v1.x` because “we are not mentally at 1.0 yet, but the tag is 1.0”

- **Effect:** Consumers treat 1.x as stable; a break breaks trust.
- **Fix:** After `v1.0.0`, breaking goes into `/v2` or a new symbol with deprecation.

### 9. Doc comment that does not start with the symbol name

- **Effect:** Worse `go doc` summary; inconsistent style.
- **Fix:** `// Format returns ...` not `// This function ...`.

### 10. Interface with 15 methods “just in case”

- **Effect:** Impossible fake; every new method breaks tests.
- **Fix:** Segregation (Getter/Saver/Deleter).

## Check questions — additional

10. **Why is a new method on a struct not the same as on an interface?**  
    Struct methods do not break foreign types; interface methods require all implementations.

11. **What does `var _ Store = (*T)(nil)` do?**  
    Compile-time check that `*T` implements `Store`.

12. **Why can the zero value of a new field be a semantic break?**  
    Because old JSON/clients send without the field, and `0`/`""` can change meaning.

13. **Does `go get .../v2` change existing imports?**  
    No — it adds a new dependency; the programmer changes imports.

14. **What is package doc in `doc.go` for?**  
    A stable place for the package description that survives file refactor.

1. [ ] No removal of exported symbols.

3. [ ] Example tests green.

## Summary

A package ready for use has a thin, stable API whose breaking and non-breaking changes the author precisely distinguishes; documentation that is tested (doc comments plus Example tests); clear semver, with `/vN` in the import path itself when a major break becomes inevitable; and does not leak concrete infrastructure types through the public signature when the contract is naturally an abstraction — that role is taken by an `interface` returned from the package boundary.
