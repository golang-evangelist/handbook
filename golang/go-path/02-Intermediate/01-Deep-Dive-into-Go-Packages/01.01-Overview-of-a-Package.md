# 01.01 Package overview: compilation unit and API boundary

> **Go Path - Zero to Gopher** / **02 Intermediate → Deep dive into Go Packages** / Lesson 01.01

## Lesson goals

After this lesson you can:

- explain a **package** (package — compilation unit and basic organizational unit of Go code) as a code boundary, not as a folder for anything;
- apply the rule **one package per directory** and recognize the exception for a `_test` package;
- distinguish an exported (**exported**) from an unexported (**unexported**) name by uppercase/lowercase initial letter and know where that boundary applies;
- set up an `internal/` directory to limit who may import a package, with nothing beyond the case-sensitive folder name;
- write a package doc comment that `go doc` and the IDE show as a contract, not as history;
- recognize when a package violates **single responsibility** and what to do about it.

## Prerequisite

- Go 1.22+ installed; `go version` works in the terminal.
- You have run `go mod init` at least once and written `package main` / `func main`.
- Basic types, `if`, `for`; you know `struct` and a basic `func` signature.
- Deep prior knowledge of the **module** (module — a named, versioned collection of packages described by a `go.mod` file) system is not required — it is enough to know that `go.mod` exists.

## Problem this lesson solves

Beginners often treat a package as a folder for files: everything that “goes with the project” ends up in one `package utils` or `package app`. Consequences arrive quickly:

- the compiler and tools see a huge unit with mixed dependencies — a change in one corner of the package recompiles everything that imports it;
- the API boundary disappears — everything is exported or nothing is meaningfully divided;
- documentation becomes a list of types with no story about what the package is for;
- refactoring is painful because the package name and its responsibility do not match;
- there is no mechanism to say “this is shared inside our organization, but not a public API” — until `internal/` is discovered.

This lesson sets up the package as an **intentional contract**: what compiles together, what is exported outward, who may import that export, and how the package name is read in calling code.

## Mental model

Think of a package as a **room with a door**, not as a shelf in a warehouse.

1. **Inside the room** (same `package name`) all files share one namespace. There are no “subpackages” inside the same folder — the directory is the boundary, not the file.
2. **The door** is the exported identifiers. An uppercase initial letter means visible from another package; a lowercase initial letter means private to that room.
3. **The sign on the door** is the package name. In a call you write `name.Identifier`, so the name must be short, a noun, without repetition in types (`http.Server`, not `http.HTTPServer` if that can be avoided).
4. **The building rules** are `internal/`: there is a floor whose doors do not open to guests from outside the building — even if the “doors” (exported identifiers) are technically open, the compiler locks them for other buildings.
5. **The plaque in front of the room** is the doc comment: a short text about what the room is for, not how it is furnished inside.
6. **Single responsibility** means: if you must say “and… and… and…” to describe what the package is for, you probably have two rooms joined into one.

The compiler builds a package as a whole: all `.go` files in the directory (except `_test.go` files that may have a `_test` suffix in the package name) enter the same compilation unit. The API boundary is not the folder on disk — it is the set of exported declarations that folder produces.

## Mechanism

### Package as a compilation unit

Before you look at code, imagine what the compiler actually does when you run `go build ./...` or `go test ./...`. It does not compile file by file as independent units — it first **collects** all `.go` files from one directory, runs them through the parser as one stream of declarations, and only then produces one code object. That means: a function in `a.go` can call a function from `b.go` without anything like an import, because for the compiler those two functions live in the same world from the moment of parsing.

The directory is the boundary of that collection. The rule is strict: **every `.go` file in the directory must have the same `package` clause**, with one single exception — a `_test.go` file may have `package name_test` (suffix `_test`) to create a separate, external test package that imports the main package as a client. Outside that exception, two different package names in the same directory are a **compiler error**, not a warning.

Take a concrete directory `catalog/` with three files:

```text
catalog/
├── item.go      → package catalog
├── ids.go       → package catalog
└── ids_test.go  → package catalog        (white-box, same names)
```

`go build` goes through all three, merges them into one `catalog` unit, and the result is one `.a` object (or part of a binary file if it is `main`). If you add a fourth file `report.go` with `package reports` in the same directory, `go build` stops with a message similar to:

```text
catalog/report.go:1:1: found packages catalog (item.go) and reports (report.go) in ./catalog
```

That is not a style error — that is a refusal to continue compiling. From there comes the rule the rest of the lesson uses: **one package per directory**, with no exception for ordinary compilation (only the `_test` suffix is treated specially, and only for test files).

The import path (`module/path/pkg`) shows **where** that directory is on disk relative to the `module` line in `go.mod`. The package name from the `package` clause is something else — that is the name you write in a call (`pkg.Function`). The convention (not a compiler rule) is that the last path segment matches the package name. When they do not match, `go build` still works, but everyone who reads the import block must open a file to see the real name — so the mismatch confuses and is avoided unless unavoidable (e.g. a `v2` package with a path suffix, topic of lesson 01.04).

**Predict:** if in directory `pricing/` one file starts with `package pricing` and another (ordinary, not `_test.go`) with `package pricingv2`, what does `go build ./pricing` do?

**Answer:** It refuses compilation with the error “found packages pricing (...) and pricingv2 (...)”. There is no silent merge, no warning you can ignore — the build stops before it reaches code generation.

### Exported vs unexported

Visibility in Go is not a special keyword like `public`/`private` in some other languages — it is a **convention written into the identifier itself**: the first letter of the name. When parsing every identifier (type, function, method, field, constant, package-level variable) the compiler checks whether the first letter is from the Unicode uppercase category. If it is, that identifier is **exported** — visible from every package that imports this one. If it is not, the identifier is **unexported** — visible only inside the same package (thus inside the same compilation unit, in all files of that directory).

This rule is not applied at file level. `NewItem` defined in `item.go` may call `normalizeSKU` defined in `ids.go` without any import — both are in the same package, so they see each other regardless of the lowercase letter. The boundary that lowercase creates is the **package** boundary, not the **file** boundary. This is a common point of confusion, and all of lesson 01.02 is devoted to it.

Trace for a concrete example:

```go
package sessioncache

type Store struct {
    data map[string][]byte // unexported field
}

func New() *Store { return &Store{data: make(map[string][]byte)} }

func (s *Store) Get(key string) ([]byte, bool) { // exported method
    v, ok := s.data[key]
    return v, ok
}
```

1. `Store` starts with an uppercase letter → the `type` is exported; another package may write `var s *sessioncache.Store`.
2. `data` starts with a lowercase letter → the field is unexported; code outside package `sessioncache` can neither read nor write `s.data`, even when it holds a `*Store` value.
3. `New` and `Get` are exported methods/functions → that is the public API. `data` stays hidden behind them.

Consequence: changing the type of field `data` (say from `map[string][]byte` to `sync.Map`) does not break any client of package `sessioncache`, because the client never could reference `data` directly. That is the difference between a **breaking change** and an internal refactor — covered in more detail in 01.04, but the root mechanism is this letter rule.

### Unexported field and composite literal from another package

Field visibility is not only a theoretical rule — the compiler applies it also at a place beginners rarely expect: a **composite literal** (an expression that at once builds a struct, slice, or map value, e.g. `Store{...}`) written from **another** package. Take `Store` from the previous example, with unexported field `data`:

```go
package sessioncache

type Store struct {
    data map[string][]byte
}
```

From the **same** package, the following code is legal:

```go
s := Store{data: make(map[string][]byte)} // OK — same package sees `data`
```

From **another** package, the exact same shape does not pass:

```go
package main

import "example.com/shop/sessioncache"

func main() {
    s := sessioncache.Store{data: make(map[string][]byte)}
    _ = s
}
```

```text
unknown field data in struct literal of type sessioncache.Store
```

The compiler does not say “the field is private” — it says the field **does not exist** from the perspective of package `main`, because for that perspective it effectively does not exist as something that may be named. This is the same boundary as accessing `s.data` in a function body — only applied at the moment of constructing the value, not only at later read/write. That is why a package that has at least one unexported field **must** offer a constructor (`New`, `NewFromEnv`, ...) so other packages can create instances — this is not stylistic advice, it is a consequence of the visibility rule.

**Predict:** if `Store` has no unexported field (all fields are `Data`, `Hits` with uppercase), does the same composite literal from the `main` package pass without `New`?

**Answer:** Yes — `sessioncache.Store{Data: ..., Hits: 0}` would compile, because all fields are visible. That is exactly why in Example 2 `badapi` is easy to construct “directly”, without a constructor — and why that is undesirable: there is no place to insert validation or an invariant at creation time.

### `package main` as a special case of single responsibility

`package main` is not an ordinary package name value — it is a signal to the toolchain that the directory produces an **executable binary file**, not a library for import. From that follow two consequences that are often overlooked:

1. **`package main` cannot be imported.** Another package may not write `import "example.com/shop/cmd/api"` — `go build` refuses, because `main` by definition has no API meant for import, only the entry point `func main()`.
2. **More binary targets = more directories**, each with its own `package main`. The convention in the Go ecosystem is to organize that under `cmd/`:

```text
example.com/shop/
├── go.mod
├── cmd/
│   ├── api/
│   │   └── main.go      → package main (HTTP server)
│   └── migrate/
│       └── main.go      → package main (one-shot migration tool)
├── quoteformat/         → package quoteformat (library)
└── internal/orderstore/ → package orderstore (library, internal)
```

Each `main.go` under `cmd/` is **its own** package, its own directory, its own compilation unit — the “one package per directory” rule applies to binary targets the same as to libraries. `cmd/api` and `cmd/migrate` may both import `quoteformat` and `internal/orderstore` (because they are in the same module tree), but they do not import each other, because no `main` package is importable.

This split is a direct application of “single responsibility” at the binary-target level: `cmd/api` runs the server; `cmd/migrate` runs the migration. If they were joined in one `main.go` with a `flag` that chooses behavior, it would still work — but the test and deploy story would be more complicated for two things that are rarely run together.

### `internal/` — a boundary wider than a package, narrower than a module

Export solves “who inside my package sees what”, but not another question: “this package IS exported (uppercase on types), but I do not want anyone outside our organization/repository to import it.” For that the Go toolchain (not the language as grammar, but `go build`/`go vet` path checking) recognizes a special directory name segment: `internal`.

The rule is: a package whose import path contains the segment `internal` (e.g. `example.com/shop/internal/billing`) **may be imported only from code whose path shares the same prefix up to (and including) the directory that is the parent of `internal`**. Everything outside that prefix gets a compiler error, not a warning.

Concrete structure:

```text
example.com/shop/
├── go.mod                     (module example.com/shop)
├── internal/
│   └── billing/
│       └── billing.go         → package billing
├── cmd/
│   └── api/
│       └── main.go            → imports example.com/shop/internal/billing (OK)
└── ../otherteam/reports/
    └── report.go               → imports example.com/shop/internal/billing (ERROR)
```

The root that “protects” `internal/billing` is `example.com/shop` — everything inside that tree (`cmd/api`, any other package under `example.com/shop/...`) may import `internal/billing`. Code outside that tree, including another module on disk or a GitHub repository, gets:

```text
use of internal package example.com/shop/internal/billing not allowed
```

This is a **compile-time** check done by `go build`/`go list`, based solely on the directory path — there is no need for any additional notation in code; `internal` as a directory name is a sufficient signal. That is why this is a cheap and reliable way to keep a publicly exported type (uppercase) **shared inside the organization**, but **closed to external modules**. It is used when you want the benefits of export (testability, sharing between your own `cmd/` tools) without the obligation that it become part of a public semver contract.

**Predict:** if you move `billing.go` from `example.com/shop/internal/billing` to `example.com/shop/pkg/billing` (without changing any identifier inside the file), may external module `example.com/otherteam` import it?

**Answer:** Yes — as soon as the path no longer contains the `internal` segment, the check is not applied. Visibility of `internal/` is purely a matter of directory path, not of file contents.

### Package doc comment

`go doc` and IDE hover do not parse the whole file to extract the “point” of the package — they look at exactly one place: the comment block that stands **immediately above** the `package` clause, with no blank line between the comment and the `package` line. That comment, by convention, starts with `// Package name ...`.

```go
// Package quoteformat formats monetary amounts for display in the UI.
// It does not know exchange rates; it receives an already computed amount and currency code.
package quoteformat
```

When a package has multiple files, the convention is to put this comment in a separate `doc.go` file that contains nothing else except the comment and the `package` clause — so documentation is not “lost” in a file that changes often. If a doc comment appears above the `package` clause in multiple files of the same package, `go doc` merges them all into the display, but that usually means documentation is fragmented without reason — one file (or `doc.go`) is clearer.

The doc comment describes **what** the package offers and **whom** it is for; it does not talk about commit history, does not list every type (that is what `go doc` does automatically from exported declarations), and does not sell the package — it explains the contract.

### Single responsibility

“Single responsibility” is not an abstract nice word — in practice it is a sentence test. Ask: **“If I remove this package, which one problem can I no longer solve?”** If the answer naturally needs the conjunction “and” to connect two independent problems (“and formatting prices and sending emails”), the package does two jobs and is a candidate for a split.

A signal visible in code, not only in the description: imported dependencies. A package that imports both `net/smtp` and `os` (for writing a file) and `strconv` (for formatting) pulls three unrelated worlds into one compilation unit. A change in one (e.g. adding an SMS channel) recompiles and tests everything, including parts that did not move. Splitting by responsibility shrinks that radius.

## Rules and syntax

```go
// Package inventory keeps stock state and computes reservations.
// It does not do HTTP or persistence — callers do that.
package inventory
```

- `package name` — lowercase, one word, no `_` or `-` in the package name (the import path may have `-`, the package name should not).
- **One package per directory.** Exception: a `_test.go` file may use `package name_test` for an external (black-box) test package.
- Package name: short noun (`time`, `sql`, `hasher`), not a verb (`hashing`), preferably singular, consistent across the project.
- Avoid `util`, `common`, `misc`, `helpers` as the only responsibility of a package — those are names that say nothing about the contract.
- Do not put `main` logic in a library; `package main` is the program entry (binary target), not a library for import.
- Export: identifier with uppercase first letter (`Function`, `Type`, `Constant`); unexport: lowercase first letter (`helper`, `state`) — the rule applies at package level, not file level.
- `internal/<anything>` in the path limits import to the tree whose root is the parent of `internal`; the check is at `go build` level, with no special syntax in code.
- Doc for exported symbols: comment immediately above the definition, starts with the symbol name (`// Format returns ...`).
- Package doc: comment immediately above the `package` clause, preferably in `doc.go` when there are multiple files.

## Examples

### Example 1 — Package with a clear responsibility and doc comment

```go
// Package quoteformat formats monetary amounts for display in the UI.
// It does not know exchange rates; it receives an already computed amount and currency code.
package quoteformat

import (
    "fmt"
    "strings"
)

// Money is an amount in the smallest currency units (e.g. cents).
type Money struct {
    MinorUnits int64
    Currency   string
}

// Format returns a string suitable for display, e.g. "1.234,56 RSD".
func Format(m Money) string {
    neg := m.MinorUnits < 0
    v := m.MinorUnits
    if neg {
        v = -v
    }
    whole := v / 100
    frac := v % 100
    body := fmt.Sprintf("%d,%02d %s", whole, frac, strings.ToUpper(m.Currency))
    if neg {
        return "-" + body
    }
    return body
}
```

#### What happens here

Package `quoteformat` has one responsibility: formatting. The doc comment says what it does **not** do (rates), which reduces wrong expectations before the client even reads `Format`. `Money` and `Format` are exported — that is the API. There is no HTTP, SQL, or logging in this package; each of those topics would be a separate package with its own doc comment.

### Example 2 — Bad vs good API boundary

```go
package badapi

// Everything is exported “just in case” — the boundary disappears.
type CacheState struct {
    Raw    map[string][]byte
    Hits   int
    Misses int
}

func (c *CacheState) TouchInternalCounter() { c.Hits++ }

func DumpRaw(c *CacheState) map[string][]byte { return c.Raw }
```

```go
// Package sessioncache holds short-lived sessions in memory.
package sessioncache

import "sync"

// Store is the public API. Internal state is not exported.
type Store struct {
    mu   sync.Mutex
    data map[string][]byte
    hits int
}

// New creates an empty Store.
func New() *Store {
    return &Store{data: make(map[string][]byte)}
}

// Get returns the value and whether it exists.
func (s *Store) Get(key string) ([]byte, bool) {
    s.mu.Lock()
    defer s.mu.Unlock()
    v, ok := s.data[key]
    if ok {
        s.hits++
    }
    return v, ok
}

// Put writes a value; copies the input slice so the client does not mutate internal state by later changing its buffer.
func (s *Store) Put(key string, value []byte) {
    s.mu.Lock()
    defer s.mu.Unlock()
    cp := make([]byte, len(value))
    copy(cp, value)
    s.data[key] = cp
}
```

#### What happens here

In `badapi` everything is public: the client may mutate map `Raw` from outside with no synchronization, and counter `Hits` is part of the contract even though it is a pure implementation detail. In `sessioncache` the public API is exactly `New`, `Get`, `Put`; the map, mutex, and `hits` are unexported. Changing the internal structure (e.g. replacing the map with `sync.Map`) does not break any client because the client never referenced `data` directly.

### Example 3 — Package name is read in the call

```go
package main

import (
    "fmt"

    "example.com/shop/quoteformat"
)

func main() {
    s := quoteformat.Format(quoteformat.Money{
        MinorUnits: 123456,
        Currency:   "rsd",
    })
    fmt.Println(s)
}
```

#### What happens here

You read `quoteformat.Format` — package name plus a verb. If the package were called `utils`, the call `utils.Format` would say nothing about what is being formatted. If the type were called `QuoteFormatMoney`, you would get `quoteformat.QuoteFormatMoney` — pure noise, because the package name is already read before the dot. The package name carries context; types stay shorter thanks to that.

### Example 4 — `internal/` prevents import outside the organization

```text
example.com/shop/
├── go.mod                        module example.com/shop
├── internal/
│   └── pricingcore/
│       └── pricingcore.go        package pricingcore
└── cmd/
    └── api/
        └── main.go
```

```go
// internal/pricingcore/pricingcore.go
// Package pricingcore computes prices by internally agreed rules.
// It is intentionally not a public API — rules change without a semver obligation.
package pricingcore

// Calc returns the price in the smallest units.
func Calc(unitMinor int64, qty int) int64 {
    return unitMinor * int64(qty)
}
```

```go
// cmd/api/main.go — OK, same module tree
package main

import (
    "fmt"

    "example.com/shop/internal/pricingcore"
)

func main() {
    fmt.Println(pricingcore.Calc(199, 3))
}
```

```go
// somewhere in example.com/otherteam/report/report.go — ERROR at build
package report

import "example.com/shop/internal/pricingcore" // use of internal package ... not allowed

func Foo() { _ = pricingcore.Calc(1, 1) }
```

#### What happens here

`Calc` is exported (uppercase), so by the export rule it would be visible everywhere. The `internal` segment in the path adds another, stronger boundary: only code whose import prefix starts with `example.com/shop` (the parent of `internal`) may import `pricingcore`. `cmd/api` is inside that tree — it passes. `example.com/otherteam/report` is outside it — `go build` refuses with a clear message, before generating any code.

### Example 5 — When single responsibility breaks

```go
// Package notify sends notifications (email and SMS) and writes an audit log to a file.
// This is a signal that a split is needed: transport vs audit.
package notify

import (
    "fmt"
    "os"
)

func SendEmail(to, body string) error {
    fmt.Println("email:", to, body)
    return nil
}

func SendSMS(to, body string) error {
    fmt.Println("sms:", to, body)
    return nil
}

func Audit(event string) error {
    f, err := os.OpenFile("audit.log", os.O_APPEND|os.O_CREATE|os.O_WRONLY, 0o644)
    if err != nil {
        return err
    }
    defer f.Close()
    _, err = fmt.Fprintln(f, event)
    return err
}
```

Better direction (sketch of a split; it does not have to be in the same file or the same refactor moment):

```go
package mailer

func Send(to, body string) error { /* ... */ return nil }
```

```go
package sms

func Send(to, body string) error { /* ... */ return nil }
```

```go
package auditlog

func Write(event string) error { /* ... */ return nil }
```

#### What happens here

Mixing notification channels and audit in one package pulls dependencies (file system plus network channels) into the same compilation unit. A test for `SendEmail` now also depends on `audit.log` being openable on disk, even though it only tests sending email. Splitting by responsibility cleans the import graph, cleans tests, and cleans the API — each package has its own `doc.go` that answers exactly one “what is it for”.

### Example 6 — `cmd/` with two binary targets over the same library

```text
example.com/shop/
├── go.mod
├── quoteformat/
│   └── quoteformat.go        package quoteformat
└── cmd/
    ├── api/
    │   └── main.go            package main
    └── priceprobe/
        └── main.go            package main
```

```go
// cmd/api/main.go
package main

import (
    "fmt"

    "example.com/shop/quoteformat"
)

func main() {
    fmt.Println(quoteformat.Format(quoteformat.Money{MinorUnits: 999, Currency: "eur"}))
}
```

```go
// cmd/priceprobe/main.go — small CLI tool, independent binary target
package main

import (
    "fmt"
    "os"
    "strconv"

    "example.com/shop/quoteformat"
)

func main() {
    n, err := strconv.ParseInt(os.Args[1], 10, 64)
    if err != nil {
        fmt.Fprintln(os.Stderr, "usage: priceprobe <minor-units>")
        os.Exit(1)
    }
    fmt.Println(quoteformat.Format(quoteformat.Money{MinorUnits: n, Currency: "eur"}))
}
```

#### What happens here

Both `main.go` files are independent `main` packages, in separate directories, and both import the same library `quoteformat`. Neither imports the other — that would be both senseless (`main` package is not imported) and poorly designed (two programs should not depend on each other). `go build ./cmd/api` and `go build ./cmd/priceprobe` produce two separate binary files; a change in `quoteformat` recompiles both, but a change in `cmd/priceprobe/main.go` does not touch `cmd/api` or `quoteformat`.

## Decision analysis

| Decision | Why | Alternative |
|----------|-----|-------------|
| Short package name | Read in every call; long names multiply noise | Longer, descriptive name — rarely justified |
| Doc above `package` | `go doc` and IDE show purpose before reading code | README only — easily goes stale |
| Few exported types | Smaller breaking surface; easier refactor | Export “just in case” — the cost is flexibility forever |
| `internal/` for shared-but-not-public | Allow import inside the organization without a semver obligation | Fully external publication — more discipline, less freedom |
| Single responsibility | Clear tests, clear import graph, fewer circular dependencies | Large “everything in one” package — faster short term, costlier long term |
| `doc.go` for the package | Documentation is not “lost” in a frequently changed file | Doc comment in an arbitrary file — works, but easily moves |

## Trade-offs

- **Small packages** give a clean API, but more directories and more import lines to track.
- **A larger package** reduces import ceremony, but easily becomes “everything in one” where every change is felt everywhere.
- **`internal/`** solves “shared in the company, not public” with no extra syntax, but adds one directory level that must be respected when organizing code — a forgotten `internal/` segment when you actually need a public package is a common post-refactor bug.
- **Export “for tests”** through uppercase pollutes the API forever in the eyes of semver users; better a white-box test in the same package (01.02).
- **Package name different from the last path segment** works (the compiler does not insist they match), but costs cognitive effort when reading `go list` output and documentation.
- **A constructor for every type with an unexported field** is an extra function to write and maintain, but the cost is small compared to how much validation and invariants that constructor lets you guarantee in one place.
- **Multiple `cmd/` binary targets** over the same library means duplicated `main.go` skeleton code (flag parsing, logging), but each binary stays small and is easy to run/test independently of the others.

**Predict:** package `billing` has one exported field `Amount` and one unexported `raw`. Another package writes `billing.Invoice{Amount: 100}` (without mentioning `raw`). Does this compile, and what happens to `raw` in the resulting value?

**Answer:** It compiles — a composite literal may omit fields, and the named form (`Field: value`) does not require all fields to be listed, only that no unexported name from another package is mentioned. `raw` gets its **zero value** (default value of the type) because no other package can set it directly — the only way for `raw` to get another value at creation is through a constructor inside package `billing`.

## Common mistakes

### 1. `package util` without a boundary

- **Wrong:** New code “that has nowhere else to go” ends up in `package util` or `package common`.
- **Effect:** Over time the package imports half the project; every change in it recompiles unrelated parts; the name says nothing about the contract.
- **Fix:** Name the package by responsibility (`slug`, `hasher`, `quoteformat`) even for one function; when you truly need a shared helper without context, limit it to one small, clearly described package.

### 2. Repeating the package name in the type

- **Wrong:** `package user` with type `user.UserService` or function `user.NewUserService()`.
- **Effect:** The call in code duplicates the word (`user.UserService`), which is pure noise because the package name is already read before the dot.
- **Fix:** Shorten to `user.Service` and `user.New()`; the package name carries context, the type stays short.

### 3. Doc comment that tells history, not the contract

- **Wrong:** `// Package foo — written in March, refactored in April, TODO add cache`.
- **Effect:** `go doc foo` prints commit history instead of answering “what is this for and how is it used”.
- **Fix:** Write the doc comment as a contract: what the package does, what it does not do, what the key assumptions are; keep history in the git log or CHANGELOG.

### 4. Mixing `main` logic and a library in the same package

- **Wrong:** `package app` contains both `func main()` and exported types that other parts of the project import.
- **Effect:** Package `main` cannot be imported from another package (Go forbids that), so the library and program get forced together, usually through duplicated code or odd workarounds.
- **Fix:** Extract the library into its own package (`package inventory`) and keep `package main` thin — only wiring that calls the library.

### 5. Exporting internal state “temporarily”

- **Wrong:** A field or type is exported “only so tests pass” or “only until I finish the refactor”.
- **Effect:** Some client (or a test in another package) starts using it before you manage to hide it; now it is part of the public contract forever, by semver rules.
- **Fix:** Use a white-box test (01.02) for internal details or intentionally export through a constructor/factory — not through leaving uppercase on a field.

### 6. Forgotten or wrongly positioned `internal/`

- **Wrong:** A package that should be visible only inside the organization is placed directly in `pkg/` or at the module root, without an `internal` segment in the path.
- **Effect:** External modules freely import a package intended as an implementation detail; a later contract change becomes a breaking change for other people's code you did not even know about.
- **Fix:** Move the package under `internal/` as soon as you notice there is no reason for it to be public; the visibility check is automatic — it is enough that the directory name is `internal`.

### 7. Multiple unrelated domains in one folder “because it is easier”

- **Wrong:** `package notify` contains sending email, and SMS, and writing an audit log file (see Example 5).
- **Effect:** Email tests depend on the file system because of the audit part; changing the SMS provider recompiles and tests audit code that did not even move.
- **Fix:** Split by responsibility (`mailer`, `sms`, `auditlog`); a shared `Notifier` `interface`, if needed, lives in a fourth, thin package.

### 8. Using the file name as a substitute for the package name

- **Wrong:** The assumption that `billing_internal.go` means “private”, and `billing_api.go` means “public”.
- **Effect:** Visibility still depends only on uppercase/lowercase of the identifier and on the `internal/` directory path — the file name affects none of that, so the assumption misleads both author and reviewer.
- **Fix:** Organize files by topic for readability (that is legitimate), but check visibility exclusively through the identifier letter and, if needed, through a real `internal/` directory.

## Idiomatic Go

- The stdlib is the model: `net/http`, `encoding/json`, `database/sql` — short names, clear responsibility, a doc comment that immediately says “what and why”.
- Prefer a noun for the package name; the verb is carried by the function/method (`Format`, `Parse`, `New`).
- A domain library should not depend on a concrete UI or HTTP framework — that depends the other way around.
- `internal/` is the standard tool for shared code inside a monorepo that must not become an external contract; use it instead of a naming convention or a comment “do not import this”.
- One package = one focus in `go doc`; if `go doc ./pkg` needs two sentences with “and” to describe the package, that is a signal to split.

## Practical scenario

A team builds a shop API. The first PR has `package app` with HTTP handlers, SQL queries, price formatting, and sending email. The build is slower in CI because every change to an email template pulls a recompile of the SQL layer that shares the same package. Code review asks for a split:

- `quoteformat` — price display, public package, also used by the mobile team through a separate service;
- `internal/orderstore` — SQL, placed under `internal/` because it is tied to a concrete database schema that changes often and nobody outside this service should depend on it;
- `mailer` — sending, public `interface` (contract without a concrete implementation) with a swappable implementation;
- `cmd/shop` — wiring: `main` that joins everything above.

After the split, a PR that changes a SQL query in `orderstore` does not touch `quoteformat` or anyone outside its own module, because `internal/` prevented anyone else from importing it. A new team member opens `go doc ./quoteformat` and immediately sees the contract without needing to read SQL. The API boundary and the `internal/` segment have become a tool for team speed, not just code aesthetics.

## Trace: what `go list` sees

A package is not a folder in the tool's head. `go list` prints the compilation unit as `go` sees it.

```bash
go list -f '{{.ImportPath}} {{.Name}} {{.GoFiles}}' ./...
```

#### What happens here

1. `ImportPath` is the path by which another package writes `import`. It follows the `module` line plus the relative directory.
2. `Name` is the identifier from the `package` clause. That is the name in the selector (`slug.Make`), not the last path segment.
3. `GoFiles` is the set of files that enter that unit. File `slug_test.go` with clause `package slug_test` is not in that set. That is another package, an external test.

### Predict the result

The module is `example.com/paketlab`. Directory `slug/` has `package slug`. What is `ImportPath`, and what is `Name`?

**Answer.** `example.com/paketlab/slug` and `slug`. If the clause says `package webslug`, `Name` is `webslug`, and the path stays `example.com/paketlab/slug`. The call then writes `webslug.Make`, even though you still call the directory `slug`.

### Why this breaks one `utils`

`go list ./...` over a `package utils` that mixes SQL and HTTP shows one `ImportPath` and one long `GoFiles`. Every importer of that package is tied to that whole unit. Splitting into `store` and `httpapi` makes two `ImportPath`s. Changing a SQL query changes the `store` unit. A package that does not import `store` does not pull those files into its graph.

## Check questions

1. **What is the API boundary of a package in Go?**
   **Answer:** The set of exported identifiers (uppercase initial letter) that other packages may use; everything unexported is an implementation detail visible only inside the same package.

2. **Why is the package name part of the code UX?**
   **Answer:** Because it appears in every selector (`pkg.Func`); a bad name (e.g. `utils`) makes calls unreadable, a good name (`quoteformat`) carries context.

3. **What does “one package per directory” mean and what is the exception?**
   **Answer:** All ordinary `.go` files in the directory must share the same `package` clause; the only exception is a `_test.go` file that may use the `_test` suffix for an external test package.

4. **How does `internal/` change the visibility of exported identifiers?**
   **Answer:** A package whose path contains the `internal` segment may be imported only from code inside the tree whose root is the parent of `internal`; outside that tree, `go build` refuses the import even if all identifiers are technically exported.

5. **What is a package doc comment for and where exactly must it stand?**
   **Answer:** It explains the package's responsibility for `go doc`/IDE; it must stand immediately above the `package` clause, with no blank line between, by convention starting with `// Package name ...`.

6. **When does a package violate single responsibility?**
   **Answer:** When the package description naturally needs the conjunction “and” to connect independent jobs (e.g. “and email and SQL and format”), or when it imports unrelated external dependencies (network, disk, format) without a shared theme.

7. **Does a directory automatically define the package API?**
   **Answer:** Not directly. The directory defines the compilation unit (which files enter together); the API is the exported declarations that unit produces, plus any visibility restriction through `internal/`.

8. **Why does composite literal `pkg.Type{field: v}` from another package fail when `field` is unexported?**
   **Answer:** The compiler treats the unexported field as unnamed from the perspective of the other package — the error is “unknown field”, not “access denied”; the solution is a constructor that returns an already filled value.

9. **Why can `package main` not be imported from another package?**
   **Answer:** `package main` marks an executable binary target, not a library; there is no sense in an API for import, so the toolchain does not allow it — each binary target lives in its own `cmd/<name>` directory.

## Summary

A package is a compilation unit and a contract: name, doc comment, exported/unexported boundary. The rule is one package per directory, with the only exception the `_test` suffix for external tests. `internal/` adds a second boundary beyond export — it allows sharing inside the organization without a semver obligation toward the outside world. Single responsibility keeps the boundary clear over time; short names and hidden internal state make the API readable and stable to change.
