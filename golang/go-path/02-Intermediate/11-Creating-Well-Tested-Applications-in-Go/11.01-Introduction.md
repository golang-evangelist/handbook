# 11.01 Why test: pyramid, boundaries, and what you should not measure

> **Go Path - Zero to Gopher** / **02 Intermediate → Creating Well-Tested Applications in Go** / Lesson 11.01

## Lesson goals

After this lesson you can:

- explain **why** tests exist in a Go project: fast feedback, safe refactoring, behavior documentation;
- sketch the **test pyramid** (unit → integration → E2E) and know where Go teams usually invest time;
- distinguish **what is worth testing** from what only creates noise and brittle suites;
- set expectations for the rest of the module: `testing`, `go test`, HTTP, coverage, bench, and fuzz;
- recognize when “more tests” **reduces** quality because they measure the wrong things.

## Prerequisite

- Go 1.22+ installed; `go version` works.
- Basic modules (`go mod init`), packages, functions, `error` as a value.
- A preferred intro to `interface` and simple HTTP handlers (not required for this lesson).
- If you completed Basics `02.12 Testing`, this area goes deeper: same tool, production trade-offs.

## Problem this lesson solves

Without agreement on what a test is for, a team quickly falls into one of two traps:

1. **Zero tests** — every change is a manual check; regressions are caught in production.
2. **Too many wrong tests** — snapshot every HTML page, mock every method, assert on private details; the suite breaks on every refactor and nobody runs it.

A third, quieter trap: **tests that always pass**. They cover lines, CI is green, and the contract was never checked. Coverage looks good; production still carries a rounding bug.

The lesson sets a frame: a test is a **cheap contract check**. If the contract is unclear, the test will not help. If the contract is clear, the test should protect it without tying you to an implementation that is allowed to change.

## Mental model

Think of the test suite as a **fuse in an electrical panel**, not as wall decoration.

1. A **unit test** looks at a small wire: one function, one `package`, deterministic input → output.
2. An **integration test** looks at how two or three wires join: a database in Docker, a real HTTP client, the file system.
3. **E2E** powers the whole house: browser, deploy, external services. Expensive, slow, rare — but it catches gaps the lower levels miss.

The pyramid is not a dogma of “always 70/20/10”. It is **cost vs signal**:

| Level | Speed | Stability | What it catches |
|------|--------|------------|-----------|
| Unit | milliseconds | high | logic, edge cases |
| Integration | seconds | medium | wires, SQL, HTTP contracts |
| E2E | minutes | lower | user flow, configuration |

The Go ecosystem favors **many fast unit** and **a few careful integration** tests because the toolchain is fast (`go test`) and because `interface` makes fakes easy without heavy frameworks.

A second mental frame — **contract versus implementation**:

```text
Contract:  "Quote(weight, zone) returns a price or error"
         ↑ the test protects this

Implementation: zone map, if-else, roundCents helper
         ↑ this may change without failing the test
```

When an assert looks at a private `roundCents` field, the test protects the implementation. When an assert looks at `got == 502`, the test protects the contract.

## Mechanism

### Why test at all

Four reasons that show up in healthy Go teams:

1. **Regression** — yesterday `ApplyDiscount` worked; today someone changes rounding. Without a test, the bug lives until a manual check or production.
2. **Design feedback** — if a function is hard to test, it is often hard to use: too many hidden dependencies, a global clock, a hard-coded HTTP client.
3. **Documentation that does not lie** — a failing test is a document that lies. CI keeps the suite truthful; a README comment has no such pressure.
4. **Courage to refactor** — without a suite, an “improvement” becomes a gamble. With a suite, you change `struct` fields and know whether you broke the contract.

### Trace: what happens when there are no tests

```text
1. Developer changes Discount(price, pct) — rounding from int to float and back
2. Manually checks one happy path in main: Discount(100, 10) → 90  ✓
3. Merge
4. Production: Discount(99, 10) → 90 instead of 89 (business rule: floor)
5. Support ticket, hotfix, postmortem

With a table-driven unit test that has {99, 10, 89}:
1–2. same
3. go test fails locally / in CI
4. production never sees the bug
```

A test is not magic — it is a **repeatable check** that a machine runs faster and more often than you do.

### The pyramid in a Go project

Typical layout:

```text
pkg/pricing/          ← pure domain, table-driven unit tests
internal/store/       ← SQL integration (testcontainers or short docker)
cmd/api/              ← a few smoke HTTP tests via httptest
e2e/ (optional)       ← rare, nightly job
```

Not everything has to live in the same repo. What matters is that **most asserts** live close to pure logic.

### Predict, then check: where does a new test go?

Imaginary PR: you change the VAT formula in `pkg/tax` and add a field to the JSON response of an HTTP handler.

**Predict:** how many tests and at which level?

**Answer (healthy budget):**

- 5–15 table-driven rows in the `tax` unit test (edge rates, zero, negative input → `error`);
- 1–2 `httptest` tests that the JSON field exists and status stays 200/400 as required;
- **zero** new E2E unless you change a whole checkout flow that E2E already covers.

If instead you only add an E2E “purchase end to end”, you catch the VAT bug more slowly and debug it more expensively.

### What you should not (or rarely) test

1. **Stdlib behavior** — do not test that `json.Marshal` works; test *your* type mapping.
2. **Framework magic** — if the router works, test handlers and domain, not whether the framework registers a route (unless you are writing a framework).
3. **Private helpers as the only focus** — better through the public API; otherwise you break refactors.
4. **Exact log message text** — logs change; assert on the side effect the user sees (status, body, DB row).
5. **Wall clock without control** — inject `time.Now()` in production; otherwise flaky tests.
6. **External SaaS in a unit test** — the network is not deterministic; use a fake or a recorded response at the integration level.
7. **Coverage as a 100% goal** — line coverage ≠ correctness; more on that in 11.11.
8. **Generated code** — `stringer`, protobuf stubs: test *your* use, not the generator.
9. **Getters with no logic** — `func (u User) ID() string { return u.id }` carries no signal.

### Signal vs noise

A good test:

- fails **only** when the contract breaks;
- has a name that says *what* is protected (`TestInvoice_RejectsNegativeQuantity`);
- has short setup; a clear assert;
- can run alone (`go test -run TestInvoice_RejectsNegativeQuantity`).

A bad test:

- fails when you rename a private field;
- needs 40 lines of mocks for 3 lines of logic;
- depends on the order of other tests or global state;
- is named `Test1` or `TestStuff`.

### Trace: flaky test from the wall clock

```go
// BAD — flaky around midnight / DST / slow CI
func TestTrialActive(t *testing.T) {
	start := time.Now()
	end := start.Add(24 * time.Hour)
	if !TrialActive(start, end, time.Now()) {
		t.Fatal("expected active")
	}
}
```

Why does it fail occasionally? If `TrialActive` uses `time.Now()` inside *and* the test passes another `now`, or if the “same moment” boundary depends on milliseconds between calls — nondeterminism.

Fix (idea; details in 11.04):

```go
func TrialActive(start, end, now time.Time) bool {
	return !now.Before(start) && now.Before(end)
}

func TestTrialActive(t *testing.T) {
	now := time.Date(2026, 3, 1, 12, 0, 0, 0, time.UTC)
	start := now.Add(-time.Hour)
	end := now.Add(time.Hour)
	if !TrialActive(start, end, now) {
		t.Fatal("expected active")
	}
}
```

An injected `now` makes the test **deterministic**. That is a mechanism, not a style tip.

### How the Go toolchain fits the pyramid

| Tool | Role in the pyramid |
|------|------------------|
| `go test` | runs unit and most integration in the same format |
| `testing` package | `Test`, `Benchmark`, `Fuzz`, `Example` |
| `httptest` | cheap HTTP without a real port (11.09–11.10) |
| `-short` | locally skip slow integrations |
| `-race` | catches data races in concurrent code |
| CI matrix | fast job on PR; slow ones at night |

You do not need a special “test framework” for the pyramid to work. You need agreement on what goes in PR CI and what goes in the nightly job.

### Predict, then check: is this a unit test?

Code:

```go
func TestCreateUser(t *testing.T) {
	db, err := sql.Open("pgx", os.Getenv("DATABASE_URL"))
	if err != nil {
		t.Fatal(err)
	}
	defer db.Close()
	// ... Insert ...
}
```

**Predict:** unit or integration?

**Answer:** Integration (or worse — depends on an external database). It uses a real driver and env. That is not a mistake — it is simply **not** the unit level. Put it behind a `-short` skip or in an `internal/store` suite with an explicit prerequisite.

## Rules and syntax

In Go, tests live in `*_test.go` next to the code:

```go
package pricing

import "testing"

func TestApplyDiscount(t *testing.T) {
	got := ApplyDiscount(1000, 10) // cents
	want := 900
	if got != want {
		t.Fatalf("ApplyDiscount(1000, 10) = %d, want %d", got, want)
	}
}
```

Rules that hold through the whole module:

1. The file must be named `*_test.go` or `go test` will not see it as a test source.
2. The function must start with `Test` and have signature `func TestXxx(t *testing.T)` (details in 11.02).
3. The package can be the same (`pricing`) or external (`pricing_test`) — 11.06.
4. Tests **do not** enter the production binary (`go build` without test files).
5. The test name should describe the contract, not the implementation.
6. One test = one story; a table inside the test for variants of the same story (11.05).

Go 1.22+ does not change these basics. Later lessons will mention `b.Loop` (Go 1.24+) only as a note; the primary bench API remains `b.N`.

## Examples

### Example 1 — First contract in a pure function

`clamp.go`:

```go
package mathx

// Clamp returns v limited to [lo, hi]. Assumes lo <= hi.
func Clamp(v, lo, hi int) int {
	if v < lo {
		return lo
	}
	if v > hi {
		return hi
	}
	return v
}
```

`clamp_test.go`:

```go
package mathx

import "testing"

func TestClamp(t *testing.T) {
	tests := []struct {
		name       string
		v, lo, hi  int
		want       int
	}{
		{name: "u_opsegu", v: 5, lo: 0, hi: 10, want: 5},
		{name: "ispod", v: -1, lo: 0, hi: 10, want: 0},
		{name: "iznad", v: 99, lo: 0, hi: 10, want: 10},
	}
	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			got := Clamp(tt.v, tt.lo, tt.hi)
			if got != tt.want {
				t.Fatalf("Clamp(%d,%d,%d)=%d, want %d",
					tt.v, tt.lo, tt.hi, got, tt.want)
			}
		})
	}
}
```

#### What happens here

Three contracts in one table. A failure on `ispod` does not hide whether `iznad` works — `t.Run` separates them in the report. No HTTP, no database: a pure unit. This is the bottom of the pyramid.

### Example 2 — What *not* to test

```go
func TestJSONMarshalWorks(t *testing.T) {
	b, err := json.Marshal(map[string]int{"a": 1})
	if err != nil {
		t.Fatal(err)
	}
	if string(b) != `{"a":1}` {
		t.Fatalf("unexpected %s", b)
	}
}
```

#### What happens here

You are testing the stdlib and key order in a `map` (which is **not** guaranteed across versions/implementations the way you might think for a “stable string”). You spend CI time without protecting *your* contract. Better: test that your DTO with tags serializes the fields the API promises.

### Example 3 — Integration in place, not in the unit folder

```go
func TestStoreInsert(t *testing.T) {
	if testing.Short() {
		t.Skip("skipping DB in -short")
	}
	dsn := os.Getenv("TEST_DATABASE_URL")
	if dsn == "" {
		t.Skip("TEST_DATABASE_URL is not set")
	}
	// ... real sql.DB ...
}
```

#### What happens here

Same `go test` runner, different pyramid level. `-short` protects the laptop workflow. Skip with a reason is better than a flaky fail when there is no database.

### Example 4 — Checklist before a PR

```text
[ ] Are there new rules in the domain? → table-driven unit
[ ] Is a SQL/HTTP wire changing? → at least one integration / httptest
[ ] Am I only touching UI copy? → do not add a brittle golden without agreement
[ ] Does the test depend on the clock/network? → inject clock / fake
[ ] Does the test name state the contract? → rename
```

#### What happens here

This checklist is not bureaucracy; it is 30 seconds that prevent an hour of flaky debugging later.

### Example 5 — Trace of bad vs good names

```text
BAD:   TestHandler1
       TestStuff
       TestFinalFinal2

GOOD:  TestQuote_LocalZone
       TestInvoice_RejectsNegativeQuantity
       TestAuth_ExpiredTokenReturns401
```

When CI fails at 02:00, the name is the first diagnosis. `TestStuff` sends you back to archaeology.

## Decision analysis

| Decision | Why |
|--------|--------|
| More unit than E2E | Cheap signal, fast feedback, less flaky |
| Test the contract, not private fields | Refactor without a red CI |
| Skip stdlib asserts | You are not paying for the Go team's regression |
| `-short` for DB | Laptop stays fast; CI can run full suites |
| Names that read as contracts | Cheap onboarding and overnight debug |
| Coverage as a map, not a KPI | Prevents false confidence (11.11) |

## Trade-offs

- **Speed vs trust** — unit alone catches logic; it does not catch a wrong DSN in a compose file. That is why a thin integration layer exists.
- **Encapsulation vs white-box** — a test in the same package sees unexported details and easily breaks on refactor; black-box forces the public API (11.06).
- **Number of tests vs maintenance** — 200 brittle mock tests cost more than 40 good table-driven ones.
- **E2E coverage** — catches gaps, but every flaky E2E trains the team to ignore a red CI.
- **Time to write a test** — the first test for a function is expensive; the fifth row in a table is cheap. Design for the table.

## Common mistakes

1. Measuring success by test count or % coverage instead of regression signal.
2. Snapshotting a whole HTML response and failing on every CSS class.
3. A unit test that spins up real Postgres and external Stripe — slow and unstable.
4. Asserting on `err.Error()` string instead of `errors.Is` / type (later also in 13.05).
5. Sharing global state between tests (`var cache = map[...]`) without cleanup.
6. Tests that call a production URL “because it is convenient”.
7. A `TestXxx` name that does not say what is protected.
8. Fear of deleting bad tests — a dead suite is worse than a thin one.
9. Mixing benchmark and correctness: “it was fast so it is correct” — it is not.
10. Adding E2E because unit “looks too simple” — the wrong reflex.

## Idiomatic Go

- Stdlib `testing` is enough for most cases; add libraries only when the pain hurts.
- Table-driven tests for edge cases (following lessons).
- Prefer pure functions at the domain boundary.
- `t.Helper()`, clear messages, `t.Parallel()` when safe — later in the module.
- CI: `go test ./...` on every PR; slower levels on a schedule.
- Keep `*_test.go` next to the code it protects; do not hide everything in `/tests` without a reason.

## Practical scenario

A team builds a billing service. First month: only manual curl. Second month: E2E that spins the whole stack for every PR — CI takes 25 minutes, flaky login. Third month: they extract `package money` and `package tax` with table-driven tests; the HTTP layer has about ten `httptest` tests; E2E stays one smoke at night. PR feedback drops to 2 minutes. A “VAT rounding” bug is caught in a unit test, not in production. The lesson they paid for in time: **the pyramid is not theory — it is a budget of CI minutes**.

Another time: a new engineer adds 30 mock tests around the ORM. Every schema refactor breaks 12 tests with no API behavior change. The lead deletes half, moves rules into `package billing` without the ORM, and leaves 3 integration SQL tests. The suite earns trust again.

## Check questions

1. **What is the test pyramid for?**  
   To align cost and signal: mostly fast unit, less integration, little E2E.

2. **What is a good subject for a unit test?**  
   A deterministic contract of pure logic or an isolated unit with fakes.

3. **Why not test `json.Marshal` by itself?**  
   That is stdlib; test *your* model and tags through the behavior you guarantee.

4. **When does E2E make sense?**  
   When you verify joining of multiple layers that unit cannot see (auth+routing+store), rarely and stably.

5. **Why is 100% coverage not a goal?**  
   Because a covered line can pass without an assert on the real rule; false confidence.

6. **Predict:** a test that calls the real Stripe API in `go test` on every PR — what is the problem?  
   Instability, secrets, slowness, cost; that is not the unit level.

7. **What does “the test protects the contract” mean?**  
   It fails when promised behavior changes, not when a private detail is refactored.

## How to judge whether the suite helps

After a month of maintenance, ask three questions:

1. **Does a test failure mean a product bug or a brittle test?** If it is often the latter, reduce coupling to details.
2. **How many CI minutes do tests cost per PR?** If that grows without new signal, move slow tests to a nightly job.
3. **Can a new teammate read the test name and guess the contract?** If not, rename before you add more asserts.

These questions are a cheaper compass than “let's add more coverage”.

## Deeper trace: from idea to test level

Imagine a requirement: “a user must not order more than 10 items per SKU in one order”.

```text
Step 1 — Where does the rule live?
  A) in the HTTP handler as an if
  B) in a SQL CHECK
  C) in a pure function ValidateLine(qty int) error
  → C is cheapest for a unit test; A and B can additionally protect the boundary

Step 2 — Which test do you write first?
  table-driven:
    qty=1  → nil
    qty=10 → nil
    qty=11 → error
    qty=0  → error
    qty=-1 → error

Step 3 — What do you NOT write as the first test?
  E2E purchase in a browser just to check qty=11
  (slow, expensive, same signal as unit for this rule)

Step 4 — What do you add later?
  one httptest: POST with qty=11 → 400
  optional DB check if CHECK is part of defense in depth
```

This trace is a template for the rest of the module: **first the cheap level that protects the rule**, then a thin wire layer.

### Predict, then check: three PRs

| PR | Change | Predict level |
|----|--------|---------------|
| A | discount formula | |
| B | new HTTP header `X-Request-Id` logging | |
| C | move Postgres → another schema with the same semantics | |

**Answers:**

- A → unit table-driven in the domain (required).
- B → maybe no unit at all (log noise); if needed, assert that middleware sets context, not the exact log line text.
- C → integration store tests; domain unit stays green if the boundary is clean.

### Anti-pattern catalog (extended)

1. **Test as a copy of the implementation** — the same if in test and code; both change together, the bug remains.
2. **Test that learns the private mock call order** — brittle; prefer the outcome.
3. **One giant TestAll** — not usefully filterable with `-run`; split it.
4. **Sleep(2s) instead of a condition** — flaky on slow CI.
5. **A 2000-line HTML golden file** — fails on whitespace; assert structure or key nodes.
6. **Production feature flag in a unit test without control** — nondeterminism.
7. **Shared `package`-level `var db`** — test order becomes a contract.
8. **“We'll cover it in QA”** — QA is not a regression cache for pure arithmetic.

### What a healthy signal looks like in practice

```text
Day 1:  rounding bug → add a table row → CI red on main? fix
Day 2:  refactor zone map → unit green, handler test green
Day 3:  flaky E2E login → move to nightly job, do not block PR
Day 4:  coverage drop on tax package → look at HTML map → missing error branch
Day 5:  new teammate reads TestQuote_EU_Overweight → understands the rule without Slack
```

If your suite does not produce days like these, the pyramid is probably theorized rather than applied.

### Additional mechanism — trace from bug to test level

When a ticket arrives “wrong amount on the invoice”, ask in order:

1. Does the domain formula exist as a pure function?
2. Is there a table-driven case for that input?
3. Does the handler only forward, or does it compute again?
4. Does E2E even check the number, or only HTTP 200?

**Predict-then-answer:** E2E passes, and the user sees wrong VAT. Where is the hole?

Answer: E2E probably does not assert the amount, or staging data does not cover the edge. Fix domain + table; do not add another slow E2E as the first reaction.

```go
func TestCheckoutPage(t *testing.T) {

```

#### What happens here

```go

	}

```

#### What happens here

### Mini-protocol after an incident

1. Reproduce the bug with one unit case (if it is domain).
2. If it is not reproducible without I/O — an integration test with a stub.
3. Only if the flow crosses multiple systems — E2E / synthetic.
4. Delete or mark a test that would only “touch” a line without an assertion.

### Example — cheap fuse

```go
func TestDiscount_VIP(t *testing.T) {
	got := Discount(1000, true)
	if got != 900 {
		t.Fatalf("Discount(1000,true)=%d, want 900", got)
	}
}
```

#### What happens here

One assertion, milliseconds. The bottom of the pyramid must turn red before the browser suite.

### CI budget table

| Level | Typical duration | Role |
|------|------------------|-------|
| Unit | < 1s per package | contracts |
| Integration | seconds | I/O boundaries |
| E2E | minutes | rare end-to-end flows |

### Predict-then-answer — 90% coverage, bug in production

How?

Answer: line visits without asserts, or assert at the wrong level (11.11).

### Predict-then-answer — when E2E is the first tool

Answer: when the hole comes from joining multiple systems that unit/httptest do not see (e.g. cookie + redirect + third-party service).

### Decision analysis — continued

| Question | Unit | Integration | E2E |
|---------|------|-------------|-----|
| Formula / rounding | yes | rarely | no |
| DB constraint | no | yes | no |
| JSON shape of handlers | httptest | sometimes | no |
| “User can pay” | partly | partly | yes |

### Trade-offs — continued

| | More unit | More E2E |
|--|-----------|----------|
| Feedback | fast | slow |
| Fidelity to the whole system | lower | higher |
| Flaky | lower | higher |
| Maintenance cost | medium | high |

### Practical scenario — continued

A team spins up 30 E2E after an incident. CI +25 min. VAT is still wrong — no E2E asserts the amount. Fix: table-driven unit + 3 E2E smoke.

### Common mistakes (this lesson)

1. E2E instead of unit for a formula.
2. Testing the stdlib.
3. Snapshotting whole HTML “for safety”.
4. A suite that hurts on every private refactor.
5. “More tests” without a clear contract.
6. Coverage % as a substitute for the pyramid.
7. Skipping E2E for months without a ticket.

### Idiomatic Go in this frame

- Pure functions for rules (11.05).
- `httptest` for handlers (11.09), not a real port in unit.
- Fakes before heavy mock frameworks (11.04).
- Example for docs, not for 20 edges (11.07).

### Additional exercises — continued

1. Last production bug: sketch where it should have turned red.
2. Delete or rewrite one test that measures a private detail.
3. Write one unit for a formula instead of an E2E idea.
4. Calculate CI minutes: unit vs E2E last month.
5. Add to CONTRIBUTING: “new business if = new t.Run”.
6. List 5 asserts and mark the pyramid level.
7. Find a test without an assertion; add an assert or delete it.
8. Propose a max number of E2E in CI for your team.

### Check questions (supplement)

1. **What does the pyramid optimize?** Feedback budget against risk.
2. **What not to test in unit?** stdlib, UI noise, private without reason.
3. **First step after a financial bug?** Unit on the formula.
4. **Why is E2E not a quality seal?** Slow, expensive, easy without a real assert.
5. **When integration?** When the contract depends on real I/O behavior.
6. **What to ask instead of “we need more tests”?** “Which contract is unprotected?”

### Mini protocol after an incident

1. Reproduce the bug at the cheapest level.
2. Add a failing test before the fix.
3. Fix + green.
4. Ask whether E2E even asserts the same claim — if not, do not replace unit with E2E.

## Summary

Tests protect contracts, not coverage vanity. The pyramid steers the budget: cheap unit tests carry most of the signal; integration and E2E cover the wires. Do not test stdlib, UI noise, and private details without reason — the suite must remain trustworthy.
