# 11.04 Unit tests: isolation, interface, and fakes

> **Go Path - Zero to Gopher** / **02 Intermediate → Creating Well-Tested Applications in Go** / Lesson 11.04

## Lesson goals

After this lesson you can:

- define a **unit** in a Go project: a function, a type, or a small set of types with a clear contract;
- isolate the unit from the network, database, and clock using **interface** and **fake** implementations;
- write fast, deterministic `TestXxx` functions without external services;
- distinguish a fake from a mock framework and know when `if got != want` is enough;
- recognize when a “unit test” actually pulls half the system and the level should move;
- inject a clock and `context` boundaries without flaky behavior.

## Prerequisite

- Lessons 11.01–11.03 (`testing`, `go test`, cache, `-run`).
- Small, focused `interface` types; satisfied implicitly.
- Basic work with `error` as a value and `context.Context`.

## Problem this lesson solves

A common scenario: `OrderService.Place` writes to Postgres, sends email, and reads `time.Now()`. A “unit” test then:

1. requires a database or 80 lines of mock setup;
2. fails when SMTP is unavailable;
3. is flaky because of the clock;
4. does not clearly say *which* domain rules it protects.

A unit test should answer: **for this input, this unit respects the contract**. Everything else is wire — that goes to the integration level. This lesson shows how to draw a boundary so the unit suite stays fast and readable.

## Mental model

Think of a unit as a **box with sockets**.

- The sockets are **dependencies** (store, mailer, clock).
- Production plugs in real plugs (SQL, SMTP, `time.Now`).
- The test plugs in **fake** plugs: in memory, predictable, no network.

```text
        ┌─────────────────┐
 input →│  PlaceOrder     │→ output / error
        │  (unit)         │
        └────┬────┬───┬───┘
             │    │   │
          Store Mail Clock   ← interface
             │    │   │
        [fake][fake][fixed]  ← in the test
```

If the box must know *how* the SQL driver works, it is not isolated. If it takes an `OrderStore` interface, you can replace the implementation without changing the logic.

Key word: **contract at the boundary**, not “mock every line”.

Fake ≠ mock framework:

| Term | What it is | Typically in Go |
|-------|--------|--------------|
| Fake | working replacement (map instead of DB) | hand-written `struct` |
| Stub | returns a fixed response | field/function |
| Mock | verifies *calls* | library; less often needed |
| Spy | records calls with real behavior | call slice in a fake |

Idiomatic Go prefers **small interfaces + hand-written fakes** in `_test.go`.

## Mechanism

### What a unit is

In Go a unit is often not a class, but:

| Shape | Example | Typical test |
|-------|--------|--------------|
| Pure function | `ApplyTax(cents, rate)` | table-driven, no fake |
| Service with DI | `Checkout{Store, Mailer}` | fake store/mailer |
| Adapter | wrapper around `http.Client` | fake `RoundTripper` |
| Small type | `Cart` methods | in-memory state |

If a function has no I/O, you do not need an interface — just input/output.

### Why interface, not a concrete type

```go
type OrderStore interface {
	Save(ctx context.Context, o Order) error
	Find(ctx context.Context, id string) (Order, error)
}
```

- Production: `PostgresOrderStore`.
- Test: `memOrderStore` — a `map` in a `struct`.
- You do not pull `database/sql` into a unit test.
- You can simulate an error (`return errUnavailable`) without taking down Postgres.

Rule: the **consumer defines the interface** (the service), not the production store package — you avoid cyclic dependencies. Often the interface lives in the same package as the service, and the store satisfies it implicitly.

### Trace: constructing the service

```go
type Clock interface {
	Now() time.Time
}

type Checkout struct {
	Store  OrderStore
	Mailer Mailer
	Clock  Clock
}

func (c Checkout) Place(ctx context.Context, o Order) error {
	o.CreatedAt = c.Clock.Now()
	if err := c.Store.Save(ctx, o); err != nil {
		return err
	}
	return c.Mailer.Send(ctx, o.Email, "order-placed")
}
```

```text
1. Test creates memStore, memMailer, fixedClock{t0}
2. Checkout{...}.Place(...)
3. Assert: store has the order, mailer has 1 message, CreatedAt == t0
4. No TCP, no SMTP, no flaky Now()
```

### Predict, then check: do you need an interface?

```go
func HashPassword(pw string) (string, error) {
	b, err := bcrypt.GenerateFromPassword([]byte(pw), 10)
	return string(b), err
}
```

**Predict:** does a unit test need a fake bcrypt?

**Answer:** Usually **no**. Call real bcrypt with a low cost in the test *or* test only that error/success branches work. Do not mock crypto without reason. If the cost is expensive for the suite, extract a `Hasher` interface — but that is a suite performance trade-off, not dogma.

### In-memory fake

```go
type memStore struct {
	m map[string]Order
}

func (m *memStore) Save(ctx context.Context, o Order) error {
	if m.m == nil {
		m.m = make(map[string]Order)
	}
	m.m[o.ID] = o
	return nil
}

func (m *memStore) Find(ctx context.Context, id string) (Order, error) {
	o, ok := m.m[id]
	if !ok {
		return Order{}, ErrNotFound
	}
	return o, nil
}
```

A fake may be simple. It does not have to simulate SQL transactions — that is integration.

### Simulating an error

```go
type failStore struct{}

func (failStore) Save(context.Context, Order) error { return errors.New("disk full") }
func (failStore) Find(context.Context, string) (Order, error) {
	return Order{}, errors.New("disk full")
}
```

Test: `Place` must return an error and **must not** send mail if save fails (contract order).

### Predict, then check: dependency order

```go
func (c Checkout) Place(ctx context.Context, o Order) error {
	if err := c.Mailer.Send(ctx, o.Email, "order-placed"); err != nil {
		return err
	}
	return c.Store.Save(ctx, o)
}
```

**Predict:** what is problematic for the contract “order exists before mail”?

**Answer:** Mail can succeed, Save can fail — the user gets mail without an order. A unit test with a spy mailer + fail store catches that if it asserts “mail was not sent when save fails”. Design and test go together.

### Clock as a dependency

```go
type fixedClock struct{ t time.Time }

func (f fixedClock) Now() time.Time { return f.t }
```

Never:

```go
if time.Since(start) < time.Second { t.Fatal("too fast") } // flaky
```

### context in a unit test

```go
ctx := context.Background()
// or
ctx, cancel := context.WithCancel(context.Background())
defer cancel()
```

For unit: `Background` is often enough. If the unit reacts to cancel, test:

```go
ctx, cancel := context.WithCancel(context.Background())
cancel()
err := svc.Place(ctx, o)
if !errors.Is(err, context.Canceled) { ... }
```

### When unit becomes integration

Signs:

- `sql.Open` in the test;
- `net.Listen`;
- reading `os.Getenv` without which the test does not work (except skip);
- `time.Sleep` to “wait for a goroutine” without synchronization;
- HTTP to a real host.

That is not a mistake — just **rename the level** and budget (11.01 pyramid).

### RoundTripper fake (HTTP client as a unit)

```go
type roundTripFunc func(*http.Request) (*http.Response, error)

func (f roundTripFunc) RoundTrip(r *http.Request) (*http.Response, error) {
	return f(r)
}

client := &http.Client{Transport: roundTripFunc(func(r *http.Request) (*http.Response, error) {
	return &http.Response{
		StatusCode: 200,
		Body:       io.NopCloser(strings.NewReader(`{"ok":true}`)),
		Header:     make(http.Header),
	}, nil
})}
```

You test code that *uses* the client, without the network. For handlers on the server side — `httptest` (11.09).

## Rules and syntax

1. Dependencies as `struct` fields or constructor parameters — not global variables.
2. Narrow interface: 1–3 methods. Not a `UserRepository` with 40 methods “just in case”.
3. Fake in `*_test.go` (or `fake_test.go`) — does not have to be in production.
4. Assert the **outcome** (state, return value), not every internal call, except when order is part of the contract.
5. `t.Helper` in assert helpers (11.02).
6. One test — one story; a table for variants (11.05).
7. Go 1.22+: same DI patterns; no new “unit test framework” in stdlib.

```go
func TestCheckout_PlaceSavesAndMails(t *testing.T) {
	store := &memStore{}
	mail := &memMailer{}
	clk := fixedClock{t: time.Date(2026, 1, 2, 3, 4, 5, 0, time.UTC)}
	c := Checkout{Store: store, Mailer: mail, Clock: clk}

	err := c.Place(context.Background(), Order{ID: "1", Email: "a@b.c"})
	if err != nil {
		t.Fatalf("Place: %v", err)
	}
	if _, ok := store.m["1"]; !ok {
		t.Fatal("order not saved")
	}
	if len(mail.sent) != 1 {
		t.Fatalf("sent %d, want 1", len(mail.sent))
	}
}
```

## Examples

### Example 1 — Pure function without a fake

```go
func ApplyDiscount(cents, pct int) (int, error) {
	if cents < 0 || pct < 0 || pct > 100 {
		return 0, errors.New("invalid")
	}
	return cents * (100 - pct) / 100, nil
}
```

```go
func TestApplyDiscount(t *testing.T) {
	got, err := ApplyDiscount(1000, 10)
	if err != nil {
		t.Fatal(err)
	}
	if got != 900 {
		t.Fatalf("got %d want 900", got)
	}
}
```

#### What happens here

No interface. The unit is pure. Do not introduce DI where there are no dependencies.

### Example 2 — Fake store + error

```go
func TestCheckout_PlaceStoreErrorNoMail(t *testing.T) {
	mail := &memMailer{}
	c := Checkout{
		Store:  failStore{},
		Mailer: mail,
		Clock:  fixedClock{t: time.Now().UTC()},
	}
	err := c.Place(context.Background(), Order{ID: "1", Email: "a@b.c"})
	if err == nil {
		t.Fatal("expected err")
	}
	if len(mail.sent) != 0 {
		t.Fatalf("mail sent on store failure: %v", mail.sent)
	}
}
```

#### What happens here

The contract “do not send mail if it was not saved” becomes an executable specification.

### Example 3 — Predict flaky

```go
func TestExpiry(t *testing.T) {
	exp := time.Now().Add(50 * time.Millisecond)
	time.Sleep(60 * time.Millisecond)
	if !Expired(exp, time.Now()) {
		t.Fatal("expected expired")
	}
}
```

**Predict:** why is it bad?

**Answer:** Sleep + slow CI = flaky or a slow suite. Pass `now` into `Expired(exp, now)`.

### Example 4 — Overly wide interface

```go
type Everything interface {
	SaveOrder(Context, Order) error
	SaveUser(...)
	SendEmail(...)
	ChargeCard(...)
	// 20 methods
}
```

#### What happens here

The fake becomes a project of its own. Split: `OrderStore`, `Mailer`, `Payments`.

### Example 5 — Spy call list

```go
type memMailer struct {
	sent []string
}

func (m *memMailer) Send(ctx context.Context, to, template string) error {
	m.sent = append(m.sent, to+":"+template)
	return nil
}
```

#### What happens here

A spy is still a fake — it works in memory. Asserting on `sent` checks a side-effect without a mock framework.

### Example 6 — When you do not mock

Code only wraps `json.Marshal`. Test through the public API that produces the JSON you guarantee; do not replace `encoding/json` with a fake.

## Decision analysis

| Decision | Motive |
|--------|--------|
| Narrow interface on the consumer | Easy fake, no cycles |
| Fake instead of mock lib | Less magic, clear outcome |
| Clock DI | Determinism |
| Pure function without DI | Cheapest unit |
| Integration separated | Honest CI budget |

## Trade-offs

- **DI everywhere** — testable, but more boilerplate for trivial functions.
- **Mock framework** — faster setup for complex interactions; more brittle and harder for juniors.
- **Fake that becomes a mini-database** — expensive to maintain; push to integration.
- **Testing private methods** — see 11.06; prefer the public contract.
- **context on every call** — correct for I/O; often superfluous in pure arithmetic.

## Common mistakes

1. Unit test with real Postgres without an integration label.
2. `time.Now()` and `Sleep` in an assert.
3. An interface with 30 methods.
4. Asserting mock call order instead of business outcome (when order is not a contract).
5. Global client `var httpClient = http.DefaultClient`.
6. A fake that panics on an unexpected call — OK for strict spies, but often excessive.
7. Mixing table-driven domain with HTTP in the same test without need.
8. Forgotten `context` cancel scenario where it is part of the contract.
9. Production SMTP in a test “temporarily”.
10. Name `TestUnit1` without a contract in the name.

## Idiomatic Go

- Accept an interface, return a `struct`.
- Fake next to the test.
- Errors: `errors.Is` / sentinel in the assert.
- Do not export an interface only for the test if the consumer can keep it inside.
- `httptest` for handlers; `RoundTripper` for clients — choose the right end of the wire.

## Practical scenario

A team mocks the ORM with 15 expectations per test. Renaming a column breaks 40 tests; API behavior is the same. The lead deletes the mocks, introduces an `OrderStore` interface, `memStore`, and 5 integration SQL tests. PR review time drops. A new “mail before save” bug is caught by Example 2 style test in one day.

## Check questions

1. **What is a unit test in Go?**  
   A fast, deterministic check of a small unit's contract without external I/O.

2. **Why an interface?**  
   So you can replace a dependency with a fake at the boundary.

3. **Fake vs mock?**  
   A fake is a working replacement; a mock often verifies calls — Go prefers fake + outcome.

4. **How to fix a flaky clock?**  
   Pass `now` or a `Clock` interface.

5. **Predict:** `sql.Open` in `TestPlace` — unit?  
   No — integration (or a bad unit).

6. **Where to define the interface?**  
   Typically at the consumer.

7. **When is DI not needed?**  
   A pure function without dependencies.

### Additional mechanism — unit boundary and dependency sockets

A unit test answers: **for this input, this unit respects the contract** — without network, database, and wall clock.

#### Design trace

```text
OrderService.Place
  |- Store interface   -> in-memory fake
  |- Mailer interface  -> fake that remembers calls
  |- Clock interface   -> fixedClock{t}
```

**Predict-then-answer:** Place calls `time.Now()` directly. What happens in the test around midnight?

Answer: flaky branches. Inject `Clock`.

### Example — narrow interface

```go
type Store interface {
	Save(ctx context.Context, o Order) error
}

type memStore struct{ items []Order }

func (m *memStore) Save(ctx context.Context, o Order) error {
	m.items = append(m.items, o)
	return nil
}
```

#### What happens here

The test does not spin up Postgres. The fake is small because the interface is narrow — not “all of SQL”.

### Example — fixed clock

```go
type Clock interface{ Now() time.Time }
type fixedClock struct{ at time.Time }
func (f fixedClock) Now() time.Time { return f.at }
```

#### What happens here

Determinism. No “sometimes fails in CI in UTC”.

### Table: fake vs mock framework

| | Fake | Mock framework |
|--|------|----------------|
| Code | hand-written type | generated / library |
| Readability | high for small interfaces | varies |
| When | narrow DI | complex protocols (rarely at the start) |

### Predict-then-answer — a 200-line fake

Answer: the interface is loose; narrow the methods or raise the test to integration with a real database in a container.

### Predict-then-answer — a “unit” that opens :5432

Answer: not a unit. Either a fake Store, or mark it as integration.

### Example — pure function without a fake

```go
func TestNetPrice(t *testing.T) {
	if NetPrice(100, 20) != 120 {
		t.Fatal("unexpected")
	}
}
```

#### What happens here

No DI. Do not force an interface where there are no dependencies.

### Additional trace — fake contract

A fake must respect the same interface, not “approximately work”. If production returns a wrapped error, the fake needs the same shape so an errors.Is test makes sense.

```go
if !errors.Is(err, ErrNotFound) {
	t.Fatalf("got %v", err)
}
```

**Predict-then-answer:** the fake always returns fmt.Errorf("missing") without wrap. What breaks?

Answer: errors.Is tests — align the fake with the production error contract.


### More on isolation

Rule: if a test fails when you turn off Wi-Fi or when the database is down, it is not a unit.

Checklist before merging a unit test:

1. No network.
2. No real clock (Clock or pure function).
3. No global mutable state without protection.
4. An assert exists.

**Predict-then-answer:** fake Store keeps data in a package-level map, tests with t.Parallel(). Risk?

Answer: data race / crossed data. Use an instance per test.


### Extension — fake quality

A fake that lies about the contract is worse than having no fake.

| Production | Fake |
|------------|------|
| errors.Is(ErrX) | same ErrX |
| ctx cancel | respects ctx |
| idempotent Save | same semantics |

**Predict-then-answer:** Parallel + shared package-level fake store?

Answer: race — instance per test.

#### What happens here

The DI boundary must be narrow and faithful.

## Summary

Unit tests protect the contract of a small, isolated unit. Interfaces and fakes remove network, database, and clock from the equation. Pure logic goes without a fake; services with DI go with narrow interfaces. If a test pulls half the infrastructure, it is not unit — move the boundary.
