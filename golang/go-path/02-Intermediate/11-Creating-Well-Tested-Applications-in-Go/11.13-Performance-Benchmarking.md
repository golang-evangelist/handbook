# 11.13 Performance benchmarking: when to measure (and when not)

> **Go Path - Zero to Gopher** / **02 Intermediate → Creating Well-Tested Applications in Go** / Lesson 11.13

## Lesson goals

- Know **when** a benchmark makes sense (symptom, hypothesis, budget).
- Distinguish a benchmark from a unit test, load test, and profiling.
- Avoid ritual measurement of everything “because Go has `Benchmark`.”
- Connect ns/op and allocs/op to product / SRE questions.
- Choose the right layer: microbench of a function vs measuring a hot path.
- Prepare the decision for writing `BenchmarkXxx` in 11.14.
- Understand that a bench **does not prove correctness**.

## Prerequisite

- Lessons 11.04–11.12 (tests, coverage).
- Basic feel for CPU, memory, GC (conceptually).
- Preferred: one real “slow” ticket from experience.

## Problem this lesson solves

Two mirrors of the same mistake:

1. **Too little:** production is on fire, the team guesses without numbers, “optimizes” blindly.
2. **Too much:** every function has a `Benchmark`, CI takes hours, nobody reads ns/op, and correctness bugs pass.

A benchmark is an expensive tool: it costs writing time, CI, and review attention. This lesson sets **entry conditions** before 11.14 teaches the `b.N` syntax.

## Mental model

```text
Symptom (slow, costly, GC)
        │
        ▼
   Hypothesis (“X allocates too much”)
        │
        ▼
   Budget / SLA (p99, $CPU, allocs)
        │
        ▼
   Right measurement layer
   (profile → bench → load)
        │
        ▼
   Decision (merge / rollback / continue)
```

| Tool | Question |
|------|---------|
| Unit `Test` | Is it correct? |
| Coverage | Was it executed? |
| Fuzz | Which input breaks? |
| **Benchmark** | How much does an operation cost here? |
| pprof (11.16–17) | Where do time / bytes go? |
| Load test | How does the system hold under traffic? |

## Mechanism

### Entry conditions — checklist before a bench

Run a `Benchmark` only when you have at least 3 of 4:

1. **Symptom** — measurable (latency, CPU $, OOM, GC pause).
2. **Hypothesis** — one sentence (“JSON marshal in a loop allocates”).
3. **Budget** — what is “good enough” (e.g. < 2µs, < 3 allocs/op).
4. **Layer** — you know it is not network / DB lock outside the process.

If the hypothesis is missing, first **profile** (11.16–11.17), do not bench everything.

### Predictive decision flow

```text
Users complain about a slow checkout
    │
    ├─ Is it a DB query? → EXPLAIN / APM, not a Go JSON bench
    ├─ Is it the frontend? → another tool
    └─ Is it CPU in the Go process? → pprof → bench on the hot function
```

**Predict-then-answer:** APM shows 90% of time in SQL. Do you write `BenchmarkCheckoutHandler`?

Answer: **not as a first step**. A handler bench measures Go CPU, not the network to the database. First the query / index.

### Microbench vs hot path

| Microbench `BenchmarkHash` | Hot path bench |
|----------------------------|----------------|
| Pure function | More realistic input (size, shape) |
| Good for a library | Good for an app ticket |
| Easy to overfit | Harder setup |
| Useful for algorithm choice | Useful for regression |

A library that **sells** performance (compression, codec) — bench is part of the product. An internal CRUD app — bench with a ticket, not with every getter.

### What a bench is not

- A replacement for `Test` (correctness).
- A replacement for a load test (concurrency, queue, network).
- A guarantee of the same ns/op on every laptop (noise, CPU frequency, governor).
- Proof that p99 is better in the cluster (local ns/op ≠ distributed p99).

### How you talk with product / SRE

Engineer: “We have a bench, ns/op −12%.”  
SRE: “Is that on the hot path we pay for in p99?”

Translations:

| Number | Link |
|------|------|
| ns/op | local cost of the operation |
| p99 | user experience / SLA |
| CPU $ | cloud bill |
| allocs/op | pressure on GC, often a hidden p99 |

A good perf PR maps at least **two** columns, not only ns/op.

### When to postpone a bench

- The API still changes shape every day.
- No symptom — only “maybe we will need it.”
- The bench input is not representative (3 bytes instead of 3 MB of JSON).
- CI is already red from flaky tests — stability first.

### When to do a bench immediately

- Choosing between two algorithms (sort, cache, codec).
- A regression budget for a library release.
- After a profile: confirmation that the change is really cheaper.
- A documented SLA on the package (`// Budget: ≤2 allocs/op` in a comment next to the bench).

### Trace of a bad ritual

```text
every PR → 40 Benchmark → CI +8 min
    → nobody reads
    → once ns/op jumps 3% because of noise
    → false fail or ignore fail (even worse)
```

Better: a **small set** of benches on the hot path + a manual/overnight broader set.

## Rules and syntax

This lesson is a **decision**, not syntax. Minimal stamp for later:

```bash
go test -bench=BenchmarkQuote -benchmem ./ship/
```

Decision rules:

1. Symptom → hypothesis → budget → measurement.
2. Do not bench correctness.
3. Representative input.
4. Document why the bench exists (1–2 line comment).
5. Prefer a profile when you do not know where.
6. Map ns/op to a business metric when you talk “success.”

## Examples

### Example 1 — Good reason

```text
Ticket: p99 Encode of a message 12ms → 40ms after a library upgrade.
Hypothesis: the new version allocates a buffer per call.
Budget: return ≤ 2 allocs/op on a 4KiB input.
Layer: BenchmarkEncode_4k + -benchmem; then pprof if needed.
```

#### What happens here

Clear input, clear budget, clear success. The bench is not a ritual — an instrument for the ticket.

### Example 2 — Bad reason

```text
“Let’s add a Benchmark for every handler because it is best practice.”
```

#### What happens here

No symptom or budget. CI noise. Postpone.

### Example 3 — Wrong layer

```go
// Bench that does http.Get against staging
func BenchmarkProd(b *testing.B) {
	for i := 0; i < b.N; i++ {
		http.Get("https://staging/api")
	}
}
```

#### What happens here

It measures network/staging, not your algorithm. Flaky, slow, dangerous for CI. Use a load tool or a stub (11.10) with clear intent.

### Example 4 — Dialog before writing

Dev: “JSON slow?”  
Lead: “The profile shows 60% in `json.Marshal` on the hot path. Input?”  
Dev: “Average payload 2KB.”  
Lead: “Budget?”  
Dev: “allocs/op ≤ 5 as before the change.”  
Lead: “OK — `BenchmarkMarshal_2k` in 11.14 style.”

#### What happens here

Entry conditions met. The next lesson is mechanics.

### Example 5 — Library vs app

| Repo | Bench policy |
|------|----------------|
| `compressx` library | Bench in every PR for public APIs |
| internal `billing` | Bench only with a perf ticket + overnight |

#### What happens here

Same language, different attention economy.

### Example 6 — Mapping metrics

```text
ns/op: 850 → 720 (−15%)
allocs/op: 4 → 1
p99 checkout: 80ms → 78ms (−2.5%)
```

#### What happens here

The local bench celebrates; the user barely feels it. Maybe the bottleneck is not that function. Profile / APM checks the layer hypothesis.

## Decision analysis

| Situation | Bench now? | Alternative |
|-----------|------------|-------------|
| Choosing a hash algorithm | yes | — |
| Do not know where CPU is | no | pprof |
| Slow SQL | no | DB tool |
| Library release guarantee | yes | — |
| Unstable API spike | no | wait |
| Flaky CI already | postpone | stabilize |

## Trade-offs

| | More benches | Fewer, targeted |
|--|----------------|-----------------|
| Regression signal | broader | narrower but clearer |
| CI cost | higher | lower |
| Noise / false alarm | higher | lower |
| Onboarding | “everything looks measured” | you must know the hot path |

Course trade-off: **few benches that someone actually reads**.

## Common mistakes

1. **Bench instead of a correctness test.**
2. **Bench without representative input.**
3. **Optimization without a symptom.**
4. **Concluding about p99 from ns/op alone.**
5. **Ignoring allocs when GC is the problem.**
6. **Staging HTTP in a unit bench.**
7. **40 benches nobody maintains.**
8. **One laptop run as “truth.”**
9. **Mixing** with a coverage KPI.
10. **Too little context** in a PR: only “faster” without a budget.

## Idiomatic Go

- A comment above `Benchmark` with budget / ticket.
- `-benchmem` when memory is part of the story.
- `go test -bench` locally before a perf story.
- Stdlib and quality modules: read their benches as a **policy** model, not as an obligation to copy quantity.

## Practical scenario

A team “optimizes” string concatenation for a week. The bench shows −30% ns/op. Production is unchanged. The profile then shows 85% of time waiting on Redis. The bench was accurate and **irrelevant**.

New policy: no perf PR without a profile screenshot or APM span alongside the bench number.

### Additional mechanism — attention economy

Every `Benchmark` in CI costs:

- machine time;
- review time (“is this jump noise?”);
- the team’s cognitive budget (yet another signal besides tests, lint, cover).

So the **decision to add a bench** is the same family of decisions as “whether I add a new metrics dashboard” — only if someone watches.

### Symptom → first tool matrix

| Symptom | First tool | Bench? |
|---------|-----------|--------|
| Wrong result | `Test` | no |
| Unknown bad input | fuzz | not first |
| CPU in process, do not know where | pprof | after |
| Choosing algorithm A/B | bench | yes |
| p99 spike, APM says DB | DB/APM | no |
| Library release guarantee | bench + budget | yes |
| “Maybe it will be slow” | nothing / wait | no |

### Example 7 — A budget that can be rejected

```text
Budget (codec.Encode, 4KiB input):
  ns/op: no worse than +10% vs main on the same runner
  allocs/op: ≤ 2
```

#### What happens here

A reviewer can say “no” objectively. Without a number, a perf PR is taste.

### Example 8 — Too little vs too much (two teams)

Team A: zero benches, guessing.  
Team B: 200 benches, all flaky and ignored.

#### What happens here

Both miss. Goal: **few, read, tied to a budget**.

### Example 9 — One-sentence hypothesis

Bad: “Needs to be faster.”  
Good: “`BuildTree` allocates per node; I expect ≤1 alloc/op after arena/reuse.”

#### What happens here

Bench design follows from the hypothesis (what you measure, which input). Without a sentence, you measure “something.”

### Example 10 — When product asks “optimize”

Product: “Make it faster.”  
Eng: “Which metric and which percentile? Which user journey?”  
Product: “Checkout p95.”  
Eng: “APM first; bench only if the span shows our Go CPU.”

#### What happens here

You translate the request into a layer. 11.13 is a lesson in **translation**, not only the Go API.

### Predict-then-answer: bench passes locally −20%, CI +5%

Answer: noise, different CPUs, thermal, parallelization. Do not merge only because of a local number; use the same runner, `-count`, and a story with a profile if needed.

### Anti-pattern: “Benchmark Driven Development” for CRUD

A new `UserService.Get` immediately gets `BenchmarkGet`. No SLA, no symptom. After a year CI +15 min, nobody knows what the number means.

Policy: bench with a **ticket** or **library contract**, not with every export.

## Summary

A benchmark works when you have a symptom, hypothesis, budget, and the right layer — often after a profile. It does not replace correctness tests or a load test. Avoid ritual measurement of everything; protect the team’s time for places where a number changes a decision. Next lesson: how `BenchmarkXxx` and `b.N` are written in practice.
