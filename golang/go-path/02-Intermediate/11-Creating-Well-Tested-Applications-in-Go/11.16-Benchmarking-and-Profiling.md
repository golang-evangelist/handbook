# 11.16 Benchmarking and profiling: `-cpuprofile` and `-memprofile` from tests

> **Go Path - Zero to Gopher** / **02 Intermediate → Creating Well-Tested Applications in Go** / Lesson 11.16

## Lesson goals

- Record a **CPU** and **memory** pprof profile during a `go test` / bench run.
- Use the `-cpuprofile` and `-memprofile` flags with a focused `-bench`.
- Keep artifacts as **local files** (or a CI artifact), not in a git branch.
- Distinguish a cover profile from a pprof profile.
- Know when a recording is “too thin” (few samples).
- Prepare files for reading in 11.17 (`go tool pprof`).

## Prerequisite

- Lessons 11.13–11.14 (when and how to bench).
- Local disk for `*.prof` files.
- Preferred: `.gitignore` for profiles.

## Problem this lesson solves

You see that `BenchmarkEncode` is slower after a PR, but you do not know **which functions** eat CPU or where allocations are. ns/op is a thermometer; **pprof** is an organ map.

Go test can record profiles **while** tests/benches run — without a separate HTTP `pprof` endpoint in this step. This lesson teaches **how to record**; 11.17 **how to read**.

## Mental model

```text
go test -bench=BenchmarkX -cpuprofile=cpu.prof -memprofile=mem.prof
        │
        ▼
   bench loop runs + runtime samples
        │
        ▼
   cpu.prof / mem.prof   (local files)
        │
        ▼
   go tool pprof   (lesson 11.17)
```

| File | Question |
|------|---------|
| `cover.out` | Which lines ran? (11.12) |
| `cpu.prof` | Where is CPU time spent? |
| `mem.prof` | Where are allocations? |
| bench stdout | How large is ns/op / allocs/op? |

## Mechanism

### Basic flags

```bash
go test ./codec/ -bench=BenchmarkEncode -benchmem \
  -cpuprofile=cpu.prof \
  -memprofile=mem.prof
```

Generates local files in the current directory (or the path you specify).

### Why with a Benchmark, not with an empty Test

A profile needs **enough samples**. A short 1ms `Test` gives a thin CPU profile. A bench with `b.N` keeps the CPU busy — denser recording.

```bash
# thin
go test ./codec/ -cpuprofile=cpu_thin.prof -run TestNone -count=0
# denser
go test ./codec/ -bench=BenchmarkEncode -cpuprofile=cpu_dense.prof
```

**Predict-then-answer:** is `-run TestFoo -cpuprofile` always useless?

Answer: not always — if `TestFoo` does heavy work long enough. In practice a bench is a more reliable sample generator.

### Only one package / one bench

Focus:

```bash
go test ./codec/ -bench=BenchmarkEncode_4k -cpuprofile=cpu.prof
```

A broad `-bench=.` mixes many scenarios — harder to interpret in 11.17.

### Memory profile

```bash
go test ./codec/ -bench=BenchmarkEncode -memprofile=mem.prof -benchmem
```

`-benchmem` prints a summary; `mem.prof` gives **where** in the code.

### Block / mutex (note)

There are also `-blockprofile`, `-mutexprofile` for advanced cases. The course focuses on CPU and mem — enough for most perf tickets.

### Local files and git

```gitignore
*.prof
cpu.prof
mem.prof
tmp/pprof/
```

If CI keeps an artifact, the job uploads a zip — **not** a commit to the branch.

### Review dialog

Author: “Here is cpu.prof.”  
Reviewer: “Which exact command? Which bench? Which input?”  
Author: (pastes the cheatsheet line)  
Reviewer: “OK — in 11.17 we look at top.”

Without the command, the profile is decoration.

### Trace: cheatsheet line

Always document:

```text
go version
go test ./codec/ -bench=BenchmarkEncode -benchmem -count=5 \
  -cpuprofile=tmp/cpu_before.prof -memprofile=tmp/mem_before.prof
```

After the fix: `cpu_after.prof` with the same command.

### What not to mix

```bash
# BAD name
go test -coverprofile=cpu.prof   # this is COVER, not CPU
```

Use clear names: `cover.out`, `cpu.prof`, `mem.prof`.

### Predict-then-answer: does a profile change ns/op?

Answer: **it can a little** (sampling overhead). For strict ns/op comparisons run the bench **without** a profile; record profiles in a separate run when you need the map.

### Enough samples

If `pprof` in 11.17 shows an almost empty top, lengthen:

```bash
go test -bench=BenchmarkEncode -benchtime=3s -cpuprofile=cpu.prof
```

## Rules and syntax

1. Record with a focused `-bench` whenever you can.
2. Clear file names + command in the PR.
3. Do not commit `*.prof` without agreement.
4. Do not mix with `-coverprofile`.
5. Before/after same input, same command, same `go version`.
6. Leave reading for 11.17 — here it is recording.

```bash
mkdir -p tmp/pprof
go test ./pkg/ -bench=BenchmarkHot -benchmem \
  -cpuprofile=tmp/pprof/cpu.prof \
  -memprofile=tmp/pprof/mem.prof
```

## Decision analysis

| Goal | Action |
|------|--------|
| ns/op regression | bench without profile |
| Where CPU? | `-cpuprofile` + bench |
| Where alloc? | `-memprofile` + `-benchmem` |
| Coverage gap | `-coverprofile` (11.12) |

## Trade-offs

| | Profile with bench | Bench number only |
|--|-----------------|-----------------|
| Diagnosis | strong | weak |
| Overhead | small | none |
| Artifacts | yes | no |

## Common mistakes

1. **Committing `*.prof` to git.**
2. **Cover file named `cpu.prof`.**
3. **Thin recording** then concluding “there is nothing.”
4. **Broad `-bench=.`** without focus.
5. **Before/after** different commands.
6. **Expecting** a profile to replace APM for a distributed system.
7. **Mixing** mem and cpu interpretation without reading (11.17).
8. **One laptop** as the only truth.
9. **Forgotten** `go version` in the note.
10. **Profiling** a flaky test instead of a stable bench.

## Idiomatic Go

- `tmp/pprof/` locally.
- Cheatsheet command in the PR.
- Stdlib `testing` flags — no extra agent for this step.
- Next: `go tool pprof`.

## Practical scenario

A team sees +25% ns/op. Without a profile they guess “GC.” `mem.prof` shows a new `make([]byte)` in a loop. Fix: buffer pool. After: same bench, fewer allocs, ns/op back. The profile shortened the debate from a day to an hour.

### Additional mechanism — what the runtime does while recording

When you add `-cpuprofile=cpu.prof`, the Go runtime periodically samples stacks of goroutines that spend CPU. Each sample is a “vote” for a symbol on the stack. That is why a short test gives few votes, and a `b.N` loop many — the map becomes readable.

A mem profile records allocations (depending on recording mode): you see **where** in the source code heap pressure arises, not only how much the `-benchmem` summary says.

**Predict-then-answer:** you run `-cpuprofile` with `go test -c` (only compiling the test binary) without a run. What do you get?

Answer: an empty or useless profile — no execution. You need a `go test` that actually runs the bench/test.

### Command matrix (cheatsheet for PR)

| Goal | Command (template) |
|------|------------------|
| Number only | `go test -bench=BenchmarkX -benchmem -count=5 ./pkg/` |
| CPU map | `... -cpuprofile=tmp/cpu.prof` |
| Mem map | `... -memprofile=tmp/mem.prof` |
| Denser | add `-benchtime=3s` |
| Cover (different!) | `-coverprofile=tmp/cover.out` |

Copy the table into the team wiki — reduces “wrong file” mistakes.

### Example 7 — File names that do not lie

```text
tmp/pprof/
  cpu_BenchmarkEncode_4k_before.prof
  cpu_BenchmarkEncode_4k_after.prof
  mem_BenchmarkEncode_4k_before.prof
```

#### What happens here

The name carries bench, input, and phase. A month later you know what you are opening. `cpu.prof` alone forgets context.

### Example 8 — One package, not monorepo in one recording

```bash
# BAD for interpretation
go test ./... -bench=. -cpuprofile=cpu.prof

# BETTER
go test ./internal/codec/ -bench=BenchmarkEncode -cpuprofile=tmp/cpu.prof
```

#### What happens here

`./...` mixes dozens of benches into one file. `top` becomes noise. Narrow the package and bench name.

### Example 9 — Separate run for ns/op and for profile

```bash
# 1) clean number for the PR table
go test ./codec/ -bench=BenchmarkEncode -benchmem -count=5

# 2) map for diagnosis
go test ./codec/ -bench=BenchmarkEncode -benchtime=2s -cpuprofile=tmp/cpu.prof
```

#### What happens here

Sampling overhead does not “spoil” the ns/op quote in the PR description. Diagnosis still has a dense recording.

### Example 10 — What to do with the file after 11.17

1. Read `top` / `list`.
2. Write a hypothesis in the ticket.
3. Delete or archive the local `*.prof` (not git).
4. Leave the bench as a budget guardian.

A profile is incident evidence, not a permanent part of the repo.

### Error trace: wrong working directory

```bash
cd /tmp
go test /path/to/module/codec -bench=BenchmarkEncode -cpuprofile=cpu.prof
```

`cpu.prof` appears in `/tmp`, not in the module. In the PR you say “here is the profile” and the reviewer cannot find the file. Use a relative path from the module root: `tmp/pprof/cpu.prof`.

### Predict-then-answer: `-memprofile` without a bench, only a fast Test

Answer: it can record *something* if the Test allocates, but the map is often thin or dominated by the test framework. For hot-path allocations — a bench.

### Link to fuzz and cover (once more)

| Tool | Artifact | Do not mix with |
|------|----------|-------------|
| cover | `cover.out` | `cpu.prof` |
| fuzz | `testdata/fuzz/...` | pprof |
| bench | stdout ns/op | — |
| pprof recording | `*.prof` | cover |

### Additional mechanism — recording a profile from go test

`-cpuprofile` and `-memprofile` record pprof artifacts **during** a test/bench run. They are not cover profiles.

#### Trace

```bash

go test ./codec/ -bench=BenchmarkEncode -benchmem \
  -cpuprofile=tmp/pprof/cpu.prof \
  -memprofile=tmp/pprof/mem.prof
```

**Predict-then-answer:** why with a Benchmark, not with an empty Test?

Answer: you need enough samples. A short Test gives a thin CPU profile; a b.N loop keeps the CPU busy.

### Example — focused bench

```bash

```

#### What happens here


### Do not mix with coverage

| Flag | File | Question |
|-----------|------|---------|

| -memprofile | mem.prof | allocations |

Answer: wrong tool under the wrong name — confusion in the team.
