# 11.07 Example tests: `Example` functions, Output, and godoc

> **Go Path - Zero to Gopher** / **02 Intermediate → Creating Well-Tested Applications in Go** / Lesson 11.07

## Lesson goals

- Write `Example`, `ExampleF`, `ExampleT_M`, and `ExampleF_suffix` functions that `go test` executes.
- Use the `// Output:` comment to verify the printed result.
- Use `// Unordered output:` when line order is not guaranteed.
- Understand the Example ↔ **godoc** / `pkg.go.dev` display link.
- Know the difference between Example and an ordinary `Test` (purpose, style, assertions).
- Keep examples deterministic (no network, random, wall clock).
- Choose `package foo_test` for examples that teach clients.

## Prerequisite

- Lessons 11.03–11.06 (`go test`, packages, black-box).
- Basic `fmt.Println` / printing to stdout.
- A preferred look at [pkg.go.dev](https://pkg.go.dev) documentation for some stdlib package (e.g. `fmt`, `strings`).

## Problem this lesson solves

Documentation lies faster than code:

- a README example stays on the old API;
- a comment above a function forgets a new parameter;
- a blog post copies an outdated snippet.

A reader pastes a dead example and loses an hour. Example tests solve that by being **examples that compile and run** in `go test` — if behavior changes, CI turns red before docs drift away.

Another problem: a team writes 30 Example functions instead of table-driven tests. Example is not a substitute for edges and errors — that is what `Test` functions do.

## Mental model

An Example is a **triple citizen**:

1. **Documentation** — rendered in godoc under the symbol.
2. **Test** — `go test` runs it and compares stdout with `Output`.
3. **Usage model** — shows an idiomatic call, not all 12 edge cases.

```text
godoc / pkg.go.dev          go test
        ▲                      ▲
        │   ExampleXxx         │
        └──────────┬───────────┘
                   │
            source *_test.go
```

| You need… | Choose |
|-----------|--------|
| How `Quote` is used in 5 lines | `ExampleQuote` |
| 12 edge cases + errors | `TestQuote` + table |
| Demo with `main`, files, CLI | `examples/` (11.08) |

## Mechanism

### Naming — what godoc binds

| Form | Binds to | Example |
|-------|------------|--------|
| `Example` | package | introductory package example |
| `ExampleF` | function `F` | `ExampleQuote` |
| `ExampleT_M` | method `M` of type `T` | `ExampleLimiter_Allow` |
| `ExampleF_suffix` | same function, more examples | `ExampleQuote_eu` |
| `ExampleT_M_suffix` | same method, variants | `ExampleT_M_err` |

**Suffix rule:** after the underscore comes a **lowercase** letter (`_eu`, `_empty`). If you write `_EU` or `_Empty`, godoc often **does not** bind the example as you expect.

### Output comment

At the end of the Example function:

```go
// Output:
// 502
```

`go test` captures stdout and compares it with the expected text (with the usual trailing newline normalization). Comparison is strict: space, case, Unicode — everything must match.

### What if there is no Output?

Without `// Output:` and without `// Unordered output:`:

- the Example still compiles;
- it often is **not** executed as an output check;
- it can still appear in documentation in some flows.

Course practice: **put Output** when you want CI protection. An example without Output is a weaker contract.

### Unordered output

```go
// Unordered output:
// a
// b
```

Use when `map` iteration or similar nondeterminism mixes **line** order. The tool compares as a set of lines, not as ordered text.

Do not abuse it: keep most examples ordered (sort keys before printing).

### Where to live: `foo` vs `foo_test`

| Choice | When |
|-------|-----|
| `package foo_test` | public library, you teach the external call (recommended with 11.06) |
| `package foo` | rare; internal context, shared white-box fixture |

### No `t *testing.T`

```go
func ExampleQuote() { // no parameters, no return
	fmt.Println(42)
	// Output:
	// 42
}
```

The check is **stdout**, not `t.Fatalf`. Therefore:

- no `log` noise;
- no goroutine printing without synchronization;
- no wall clock and random;
- no network.

### Execution trace

1. `go test` finds `Example*`.
2. If Output / Unordered output exists, it runs the function.
3. Captures stdout.
4. Compares with the comment.
5. On fail shows a diff (got vs want).

```bash
go test -run Example -v
go test -run ExampleHello_unicode -v
```

### Predict-then-answer: may an Example return `error`?

```go
func ExampleX() error { return nil }
```

Answer: **not** as an Example contract — the signature must have no parameters and no results. Print errors and `return` from the function:

```go
func ExampleQuote() {
	_, err := quote.Quote(-1, "local")
	if err != nil {
		fmt.Println("err:", err)
		return
	}
	// Output:
	// err: weightGrams must be > 0
}
```

### Predict-then-answer: does `fmt.Printf` enter Output?

Yes — everything that goes to stdout. `t.Log` does not exist here; the `log` package writes to stderr by default and does **not** enter Output comparison (trap: you think you are testing log, but Output only looks at stdout).

### Godoc and pkg.go.dev

```bash
go test -run Example
# local documentation preview (if you use the godoc tool):
# godoc -http=:6060
```

On `pkg.go.dev` Example sections appear next to the symbol after the module is available to the tool. Locally: read `*_test.go` and run `go test` — that is the source of truth.

### Link to black-box (11.06)

An Example in `package greeter_test` looks like copy-paste for the user:

```go
fmt.Println(greeter.Hello("Marko"))
```

Same mental model as an API test: storefront, not warehouse.

## Rules and syntax

```go
package ship_test

import (
	"fmt"

	"example.com/shop/ship"
)

func ExampleQuote() {
	price, err := ship.Quote(200, "local")
	if err != nil {
		fmt.Println("err:", err)
		return
	}
	fmt.Println(price)
	// Output:
	// 502
}
```

Rules:

1. The name starts with `Example`.
2. No parameters; no return values.
3. The `Output` block exactly matches stdout.
4. Avoid extra logs that “pollute” the output.
5. One clear scenario per Example; suffix for variants.
6. Do not replace table-driven `Test` with Examples.
7. Suffix after `_` in lowercase.
8. Determinism: same output on every machine.

Go 1.22+ does not change Example mechanics — same contract with the `testing` package.

## Examples

### Example 1 — Basic Example next to a function

```go
// greeter/greeter.go
package greeter

import "fmt"

// Hello returns a greeting for the name.
func Hello(name string) string {
	if name == "" {
		name = "world"
	}
	return fmt.Sprintf("Hello, %s!", name)
}
```

```go
// greeter/greeter_test.go
package greeter_test

import (
	"fmt"

	"example.com/learn/greeter"
)

func ExampleHello() {
	fmt.Println(greeter.Hello("Marko"))
	// Output:
	// Hello, Marko!
}
```

#### What happens here

A reader on pkg.go.dev immediately sees the call. `go test` checks that the string was not silently changed to “Ciao”. No `t.Fatalf` — the check is textual Output.

### Example 2 — Multiple examples with a suffix (including Unicode)

```go
func ExampleHello_empty() {
	fmt.Println(greeter.Hello(""))
	// Output:
	// Hello, world!
}

func ExampleHello_unicode() {
	fmt.Println(greeter.Hello("привет"))
	// Output:
	// Hello, привет!
}
```

#### What happens here

Same symbol, two scenarios. Godoc shows both. Suffix `_empty` / `_unicode` must be lowercase. **привет** stays in Cyrillic form in the example — Output compares bytes/runes exactly; Latinization would break the test and wrongly “fix” documentation.

This is not a substitute for exhaustive `Test` tables — only documentation variants.

**Predict-then-answer:** if in code you change the greeting to `Hello, %s.` (period instead of `!`), what fails?

Answer: `ExampleHello`, `ExampleHello_empty`, `ExampleHello_unicode` — all whose Output contains the old form.

### Example 3 — Method Example

```go
package counter

type Counter struct{ n int }

func (c *Counter) Add(v int) { c.n += v }

func (c *Counter) Value() int { return c.n }
```

```go
package counter_test

import (
	"fmt"

	"example.com/learn/counter"
)

func ExampleCounter_Add() {
	var c counter.Counter
	c.Add(2)
	c.Add(3)
	fmt.Println(c.Value())
	// Output:
	// 5
}
```

#### What happens here

The name `ExampleCounter_Add` binds to method `Add` of type `Counter`. Note: field `n` is unexported — the example uses only public methods (same pressure as 11.06).

### Example 4 — Package Example

```go
// In package hash_test
func Example() {
	fmt.Println("package hash: use Sum32(data)")
	// Output:
	// package hash: use Sum32(data)
}
```

#### What happens here

`Example` without a suffix goes with the **package**, not one symbol. Use for one short orientation (“where to start”), not an essay.

### Example 5 — Unordered output and map

```go
func ExampleKeys_unordered() {
	m := map[string]int{"b": 2, "a": 1}
	for k := range m {
		fmt.Println(k)
	}
	// Unordered output:
	// a
	// b
}
```

Better idiomatic example — sorting:

```go
func ExampleKeys_sorted() {
	m := map[string]int{"b": 2, "a": 1}
	keys := make([]string, 0, len(m))
	for k := range m {
		keys = append(keys, k)
	}
	sort.Strings(keys)
	for _, k := range keys {
		fmt.Println(k)
	}
	// Output:
	// a
	// b
}
```

#### What happens here

The first form teaches `Unordered output`. The second teaches the client to sort — better docs. Choose sorted + `Output` whenever you can.

### Example 6 — Deliberate Output fail (learning the diff)

```go
func ExampleHello_broken() {
	fmt.Println(greeter.Hello("Marko"))
	// Output:
	// Hello, Markoo!
}
```

Run:

```bash
go test -run ExampleHello_broken -v
```

#### What happens here

You see a got/want diff. This is an exercise — do not commit a deliberately broken Example. Goal: recognize how `go test` reports an Example fail (different from a `t.Fatalf` message).

### Example 7 — Error as a documented flow

```go
func ExampleQuote_invalid() {
	_, err := ship.Quote(0, "local")
	fmt.Println(err)
	// Output:
	// weightGrams must be > 0
}
```

#### What happens here

Sometimes you want docs to show **what an error looks like**. OK for one clear case. Do not cover all 15 error strings with Examples — that is the job of a `Test` table.

### Example 8 — What not to put in an Example

```go
// BAD — nondeterministic
func ExampleNow() {
	fmt.Println(time.Now())
	// Output: ???
}

// BAD — network
func ExampleFetch() {
	resp, _ := http.Get("https://example.com")
	fmt.Println(resp.StatusCode)
}
```

#### What happens here

CI will be flaky or slow. For time: inject a clock into the API and in the Example use a fixed moment. For network: 11.09–11.10 (`httptest`).

## Decision analysis

| Situation | Example | Test | examples/ main |
|-----------|---------|------|----------------|
| Idiomatic happy path | yes | optional | — |
| 10 edge cases | no | yes | — |
| Error with a stable message | 1× OK | table | — |
| CLI with flags | no | yes | yes |
| 40-line tutorial | no | Sample test (11.08) | yes |
| Map range | sorted Output or Unordered | — | — |

**PR question:** “Does this Example teach the call, or only duplicate a Test?” If it duplicates — delete the Example or shorten Test coverage with docs.

## Trade-offs

| | Example | `Test` |
|--|---------|--------|
| Readability for people outside the code | high (godoc) | medium |
| Edges and errors | weak | strong |
| Check | stdout text | arbitrary assert |
| Flaky risk | high if nondeterminism | you control it |
| Number of scenarios per symbol | 1–3 | dozens |

Trade-off: Example is a **narrow, expensive** channel (docs + CI). Do not spend it on noise.

## Common mistakes

1. **Example instead of a whole test suite** — you lose assert structure and case names.
2. **Wrong suffix** (`_Empty`) — the example does not bind in godoc.
3. **Space / trailing space** in Output that you do not see in the editor.
4. **Printing in a map loop** without Unordered or sort.
5. **`log.Println` instead of `fmt`** — stderr ≠ Output.
6. **Time, random, network** in an Example.
7. **Huge Example** of 80 lines — docs become unreadable.
8. **Forgotten Output** — false feeling that CI protects the example.
9. **Latinizing a Unicode example** (e.g. “privet” instead of “привет”) when the API returns / accepts the original — Output and cultural context break.
10. **Example in a white-box package** that calls private — docs teach the warehouse, not the storefront.

## Idiomatic Go

- Short, copy-paste examples next to the symbol.
- `package foo_test` for public libraries.
- One happy path + possibly one error or variant.
- Prefer deterministic `Output` over `Unordered output`.
- Stdlib is the model: read `Example` in `strings`, `fmt`, `path/filepath`.
- Keep stdout clean — only what the reader needs to see.

## Practical scenario

Package `geo.Format` was documented with a README snippet. After a refactor `Format` adds a space after the comma. README lies for a month; five tickets “example does not work”.

The team moves the snippet into:

```go
func ExampleFormat() {
	fmt.Println(geo.Format(44.8, 20.5))
	// Output:
	// 44.8, 20.5
}
```

CI catches the next format change the same day. README now says: “See ExampleFormat on pkg.go.dev” instead of duplicating code.

## Check questions

1. **What is Example for?**  
   Executable documentation: godoc display + stdout check in `go test`.

2. **How is accuracy checked?**  
   With a `// Output:` comment that must match the print.

3. **Example or Test for 10 edge cases?**  
   `Test` + table; Example for 1–2 idiomatic calls.

4. **What is `ExampleFoo_bar`?**  
   An additional example for `Foo` with suffix `bar` (lowercase).

5. **When `Unordered output`?**  
   When stdout line order is not stable (e.g. map range).

6. **Why `fmt` and not `log` for Output?**  
   Output captures stdout; `log` typically writes to stderr.

7. **May an Example have `t *testing.T`?**  
   No — the signature has no parameters.

8. **Why keep привет in the example?**  
   Output and docs must match real Unicode behavior; Latinization lies.

## Summary

Example functions are documentation that must not lie: `go test` compares stdout with `Output`, and godoc shows them next to the API. Use them for short idiomatic paths; leave edges to `Test` functions. Name by convention, keep determinism, choose a black-box package when you teach clients how to call your code.
