# 11.12 Generating code coverage reports

> **Go Path - Zero to Gopher** / **02 Intermediate → Creating Well-Tested Applications in Go** / Lesson 11.12

## Lesson goals

- Generate a **cover profile** with `go test -coverprofile`.
- Read a function summary with `go tool cover -func`.
- Open an **HTML map** with `go tool cover -html`.
- Use `-coverpkg` to control what enters measurement.
- Align local and CI commands.
- Know what not to commit (artifacts) and how not to mix cover with a CPU profile.
- Apply a checklist after generation (11.11 interpretation + this tool).

## Prerequisite

- Lesson 11.11 (coverage ≠ correctness).
- `go test` on a module.
- Basic terminal: file redirection, deleting local artifacts.

## Problem this lesson solves

`go test -cover` alone gives **one number** per package. For review you need:

- which **functions** are weak;
- which **lines** in the touched file are red;
- whether you measure only the package under test or also dependencies (`-coverpkg`).

Without a profile and HTML map, the team argues about % in the abstract. This lesson shows **how the report is made** and how to read it — not how to idolize it.

## Mental model

```text
go test -coverprofile=cover.out
           │
           ▼
      cover.out  (profile)
           │
     ┌─────┴──────┐
     ▼            ▼
 -func         -html
 text          map in the browser
```

| Output | Question it answers |
|-------|----------------------|
| `-cover` number | What is the package average? |
| `-func` | Which functions pull it down? |
| `-html` | Which lines in the file? |
| `-coverpkg` | What is even in the denominator? |

## Mechanism

### Step 1 — profile

```bash
go test ./ship/ -coverprofile=cover.out
```

The file `cover.out` is a textual profile (mode + lines). It is not meant for manual editing.

```bash
go test ./... -coverprofile=coverage.out
```

Note: one `-coverprofile` for `./...` aggregates; interpret carefully when you mix many packages.

### Step 2 — function summary

```bash
go tool cover -func=cover.out
```

Example (illustration):

```text
example.com/app/ship/quote.go:10:	Quote		90.0%
example.com/app/ship/normalize.go:5:	normalizeZone	100.0%
total:					(statements)		92.0%
```

**Predict-then-answer:** `Quote` at 90% — what do you do first?

Answer: open HTML or look at which lines are missing; do not “add an empty test” to push to 100.

### Step 3 — HTML map

```bash
go tool cover -html=cover.out -o cover.html
# or interactively:
go tool cover -html=cover.out
```

Colors (conceptually): green = covered, red = not, gray = not code for measurement. Read **touched** files first.

### `-covermode`

```bash
go test -covermode=set -coverprofile=cover.out ./...
go test -covermode=count -coverprofile=cover.out ./...
go test -covermode=atomic -coverprofile=cover.out ./...
```

| Mode | Idea |
|------|--------|
| `set` | yes/no visit (often the default) |
| `count` | visit count |
| `atomic` | count-safe with `-race` |

For ordinary PR review, `set` or the default is enough. With `-race` use `atomic` when you measure cover at the same time.

### `-coverpkg` — what enters the denominator

Default: the package you test is measured. Sometimes you want a test in the `api` package to also measure `internal/billing`:

```bash
go test ./api/ -coverpkg=./api/,./internal/billing/ -coverprofile=cover.out
```

Or broader:

```bash
go test ./... -coverpkg=./... -coverprofile=cover.out
```

**Caution:** an overly broad `-coverpkg` drops % because it pulls untested packages into the denominator — or conversely, confuses CI thresholds. **Align** local and CI with the same policy.

**Predict-then-answer:** you test only `./ship` without `-coverpkg`, and `ship` calls `internal/tax` — does `tax` enter %?

Answer: **usually not** (default scope is the package under test). If you want `tax` in the report, list it in `-coverpkg` or run tests in `tax`.

### CI artifacts

- Generate `coverage.out` / `cover.html` as a **job artifact**.
- Do not commit to git without agreement (noise, conflicts).
- If you need a badge, use a CI service — not a manual % in README that goes stale.

### What you do not combine in the same step

- Coverage profile ≠ CPU profile (`-cpuprofile`) — that is 11.16.
- Coverage threshold ≠ benchmark budget — that is 11.13–11.14.
- HTML colors ≠ fuzz corpus — that is 11.15.

### Mini checklist after generation

1. Is the profile fresh (delete the old one before the run)?
2. Does `-coverpkg` match the team agreement?
3. Are you looking at touched files or getting lost in the whole tree?
4. Does a red branch make sense to leave (e.g. `main`) or need a test?

### Packages without tests

```text
?    example.com/app/cmd/tools    [no test files]
```

or 0% — a signal, not a tool error. Add a test or exclude from the threshold deliberately.

### Trace of the local workflow

```bash
rm -f cover.out cover.html
go test ./internal/billing/ -coverprofile=cover.out -covermode=atomic
go tool cover -func=cover.out | sort -k3 -n
go tool cover -html=cover.out -o cover.html
```

Open `cover.html`, jump to the file from the PR diff, look for red next to new `if`s.

## Rules and syntax

1. `-coverprofile=FILE` writes the profile.
2. `go tool cover -func=FILE` / `-html=FILE`.
3. `-coverpkg` lists packages for instrumentation — document it.
4. Same command shape in CI and README.
5. Do not mix with `-cpuprofile` in the same “story” without need.
6. Delete / ignore artifacts locally (`.gitignore`).
7. Interpret with 11.11: map + assert.

Example `.gitignore` fragment:

```gitignore
cover.out
coverage.out
cover.html
*.coverprofile
```

## Examples

### Example 1 — One package, full loop

```bash
cd ship
go test -coverprofile=cover.out .
go tool cover -func=cover.out
go tool cover -html=cover.out -o cover.html
```

#### What happens here

From number → function → line. That is the minimal professional flow before commenting on a PR.

### Example 2 — Filtering weak functions

```bash
go tool cover -func=cover.out | findstr /V "100.0%"
# on Unix: go tool cover -func=cover.out | grep -v '100.0%'
```

#### What happens here

You quickly see what is not fully green. Then HTML for detail.

### Example 3 — coverpkg policy

```bash
# Policy A: package only
go test ./api/ -coverprofile=c.out

# Policy B: api tests also measure the service
go test ./api/ -coverpkg=./api/,./service/ -coverprofile=c.out
```

#### What happens here

Same tests, different denominator. The CI threshold must know which policy you use — otherwise “locally 85%, CI 60%” becomes paranormal ops.

### Example 4 — Race + cover

```bash
go test -race -covermode=atomic -coverprofile=cover.out ./store/
```

#### What happens here

`atomic` mode avoids races in coverage counters while `-race` runs. Slower — OK for overnight / important package.

### Example 5 — PR script (conceptual)

```bash
go test ./... -coverprofile=coverage.out
go tool cover -func=coverage.out > coverage.txt
# upload coverage.out + coverage.txt as an artifact
```

#### What happens here

A reviewer downloads the artifact, locally `go tool cover -html` — without “trust me on %.”

### Example 6 — Trap of an old profile

```bash
# BAD: you look at yesterday's cover.out after changing code
go tool cover -html=cover.out
```

#### What happens here

The map lies. Always regenerate the profile after changing tests/code.

**Predict-then-answer:** you change only production code, do not regenerate the profile, HTML is still green on an old line that no longer exists — a confusing display is possible. Regenerate.

### Example 7 — Focus on one file in your head

There is no magic “only this file” flag in the basic flow — you filter with your eyes in HTML or look at `-func` lines for that file. Some CI tools cut a diff; locally: discipline.

## Decision analysis

| Question | Action |
|---------|--------|
| Quick healthcheck? | `go test -cover` |
| Which function is stuck? | `-func` |
| Which line? | `-html` |
| Test in A, logic in B? | `-coverpkg` agreement |
| CI badge? | artifact + service, not a git binary |

## Trade-offs

| | Broad `./... -coverpkg=./...` | Narrow package |
|--|------------------------------|------------|
| Monorepo overview | yes | no |
| % meaningful for a threshold | often harder | easier |
| Time | longer | shorter |

HTML for a whole monorepo can be slow / large — generate for the touched package.

## Common mistakes

1. **Committing `cover.out` / HTML** to the repo without agreement.
2. **Reading an old profile.**
3. **Different `-coverpkg` locally and in CI.**
4. **Mixing** with `-cpuprofile` files by name (`cpu.out` vs `cover.out` — keep clear names).
5. **A threshold on an aggregate** that punishes new packages without tests without context.
6. **Only % in the PR description** without a map.
7. **`-covermode=count` ritual** without need.
8. **Ignoring `?` no test files.**
9. **Opening HTML as proof of correctness** (11.11!).
10. **Forgotten `.gitignore`.**

## Idiomatic Go

- Clear names: `cover.out`, not `out.txt`.
- `go tool cover` from the toolchain — no extra CLI to start.
- Document the command in CONTRIBUTING.
- One “source of truth” script `scripts/cover.ps1` / `.sh`.

## Practical scenario

CI reports 71%, laptop 88%. After debugging: laptop uses `-coverpkg=./pkg/`, CI `./...`. The team introduced `make cover` with the same flags. The quality discussion returned to red branches instead of “CI is lying.”

## Check questions

1. **Which flag writes the profile?**  
   `-coverprofile=FILE`.

2. **How the function summary?**  
   `go tool cover -func=FILE`.

3. **How the HTML map?**  
   `go tool cover -html=FILE`.

4. **What is `-coverpkg` for?**  
   Chooses which packages to instrument / enter measurement.

5. **Why align CI and local?**  
   So % and map are comparable; otherwise false alarms.

6. **Should you commit cover.out?**  
   By default no — CI artifact / local ignore.

7. **`set` vs `atomic`?**  
   `atomic` with `-race` for safe counting.

8. **Does HTML prove correctness?**  
   No — only visit (11.11).

### Additional mechanism — what a profile looks like inside (conceptually)

`cover.out` starts with a mode line (`mode: set` / `count` / `atomic`), then rows of the form:

```text
path/file.go:StartLine.StartCol,EndLine.EndCol statements count
```

Do not edit by hand. If you “fix” a number, HTML lies. Always regenerate from `go test`.

### Example 8 — Only the touched package in a PR

```bash
# assume the PR touches only ./internal/billing
go test ./internal/billing/ -coverprofile=cover.out
go tool cover -html=cover.out -o billing-cover.html
```

#### What happens here

You do not get lost in 0% `cmd/` tools. Review takes 10 minutes instead of an hour.

### Example 9 — Merging multiple profiles? (caution)

Third-party tools can merge profiles. In the course: **one fresh** `go test -coverprofile` per question you ask. Less magic, fewer lies.

### Example 10 — `-cover` vs `-coverprofile`

```bash
go test -cover ./ship/                 # only prints %
go test -coverprofile=c.out ./ship/  # profile (+ usually also %)
```

#### What happens here

Without a profile there is no `-func` / `-html`. For PR review always a profile.

### Predict-then-answer: delete `cover.out` between runs?

Answer: yes — or overwrite with the same explicit name after a successful test. Do not read yesterday’s file thinking it is today’s.

### CI pseudocode (GitHub Actions style, conceptual)

```yaml
- run: go test ./... -coverprofile=coverage.out -covermode=atomic
- run: go tool cover -func=coverage.out
- uses: actions/upload-artifact@v4
  with:
    name: coverage
    path: coverage.out
```

No commit to the branch. The artifact lives with the run.

### Threshold policy (proposed CONTRIBUTING text)

```text
1. Same coverpkg locally and in CI.
2. New business package: at least a smoke test + map reviewed.
3. Do not require 100% on cmd/main.
4. A test without an assert is rejected regardless of %.
```

## Summary

`go test -coverprofile` makes a profile; `go tool cover` gives a function summary and HTML map; `-coverpkg` chooses what is measured. Align local and CI commands, do not commit artifacts without agreement, and always read the map with the number — coverage remains a tool for gaps, not a quality seal.
