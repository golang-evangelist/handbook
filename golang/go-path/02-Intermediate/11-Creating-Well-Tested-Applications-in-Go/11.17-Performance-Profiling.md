# 11.17 Performance profiling: reading pprof recordings

> **Go Path - Zero to Gopher** / **02 Intermediate → Creating Well-Tested Applications in Go** / Lesson 11.17

## Lesson goals

- Read profiles recorded in 11.16 using **`go tool pprof`**.
- Use `top`, `list`, and the web UI for orientation.
- Distinguish **flat** vs **cum** time.
- Interpret memory profiles (allocations) carefully.
- Follow the flow: top → list → hypothesis → change → bench.
- Know the limits of local pprof versus a distributed system.
- Connect a bench budget (11.14) with profile findings.

## Prerequisite

- Lesson 11.16 (`-cpuprofile`, `-memprofile` local files).
- Existence of at least one `cpu.prof` / `mem.prof` for practice.
- Go toolchain with `go tool pprof`.

## Problem this lesson solves

You have `cpu.prof` on disk. Without reading, the file is a souvenir. Teams often:

- open the wrong profile;
- optimize `runtime.*` blindly;
- mix flat and cum;
- expect local pprof to explain network p99 in a cluster.

This lesson teaches **reading literacy** for local recordings from `go test`.

## Mental model

```text
cpu.prof
   │
   ▼
go tool pprof cpu.prof
   │
   ├─ top     → which symbols dominate
   ├─ list F  → lines in function F
   └─ web/UI  → call graph (if available)
   │
   ▼
hypothesis → change → go test -bench → (optional new profile)
```

| View | Question |
|--------|---------|
| `top` | Who is expensive? |
| `list` | Which line? |
| graph | Who calls whom? |
| bench | Did the change help? |

## Mechanism

### Starting

```bash
go tool pprof cpu.prof
```

Interactive prompt:

```text
(pprof) top10
(pprof) list Encode
(pprof) quit
```

Textual one-shot:

```bash
go tool pprof -top cpu.prof
go tool pprof -list Encode cpu.prof
```

Web UI (if graphics / browser OK):

```bash
go tool pprof -http=:8080 cpu.prof
```

### flat vs cum

| | flat | cum |
|--|------|-----|
| Idea | time in the symbol itself | symbol + callees below |
| Use | where “work is done” | who is responsible in the call tree |

**Predict-then-answer:** a `JSON` library has small flat, large cum in your `EncodeAll`. What does that often mean?

Answer: your code **often calls** an expensive library — maybe reduce call count / size, do not “rewrite encoding/json” immediately.

### runtime in top

Seeing `runtime.mallocgc`, `runtime.scanobject` is not always a “runtime bug.” It often means **too many allocations in your code**. Go to `mem.prof` / `-benchmem`.

### Memory profile

```bash
go tool pprof -top mem.prof
```

Depending on recording, pprof mem may show alloc_space / inuse_space etc. For test recordings focus on **who allocates** in your package. Compare with `allocs/op` from the bench.

### Diagnosis flow (step by step)

1. `top20` — ignore noise below the threshold.
2. Pick a symbol from **your** module.
3. `list Symbol` — lines with numbers.
4. Form a hypothesis (“line 80 makes a new buffer every time”).
5. Change.
6. `go test -bench=... -benchmem -count=5`.
7. Optionally a new profile `cpu_after.prof` and compare `top`.

### Before/after comparison

```bash
go tool pprof -top cpu_before.prof
go tool pprof -top cpu_after.prof
```

Look for a drop in your symbol, not a random shift of `runtime`. One sentence in the PR: “Encode flat 40% → 15%.”

### Predict-then-answer: optimize the first flat `runtime.memclrNoHeapPointers`?

Answer: **rarely directly**. Ask who allocates / who calls. Mem profile + your `list`.

### Limits of local pprof

Local pprof answers: “What does **this** Go change do in **this** process?”  
A distributed symptom often asks: “Which hop, which replica, which timeout?”

That is why the next module (12.x) enters elements of a distributed system — so you do not try to solve network partial failure with yet another `list` view of a local profile.

### Profile vs CI policeman

```text
Profile = detective on an incident / ticket
Bench  = policeman on a PR (budget)
```

Do not ask CI to run heavy profiles on every push without need. Document the expectation in a bench comment: e.g. “do not return above 2 allocs/op on this input.”

### Trace: from top to line

```text
(pprof) top
  flat  ...  ship.Quote
(pprof) list Quote
  120ms  quote.go:42  tmp := make([]byte, n)
```

Hypothesis: allocation in a loop. Fix: reuse buffer. Bench confirms allocs/op.

## Rules and syntax

```bash
go tool pprof -top cpu.prof
go tool pprof -list FuncName cpu.prof
go tool pprof -http=:8080 cpu.prof
go tool pprof -top mem.prof
```

Rules:

1. First `top`, then `list`.
2. Focus on symbols in your code.
3. Interpret flat vs cum consciously.
4. Dominant runtime ⇒ often allocations / GC pressure.
5. Confirm with a bench, not a feeling.
6. Do not expect a local profile to replace cluster APM.
7. Keep the recording command with the interpretation.

## Examples

### Example 1 — top

```bash
go tool pprof -top cpu.prof
```

Illustration:

```text
Showing nodes accounting for 1.20s, 80% of 1.50s total
flat  flat%  ...  cum   cum%
0.40s 26.67% ...  0.40s 26.67%  example.com/app/codec.Encode
0.20s 13.33% ...  0.60s 40.00%  encoding/json.Marshal
```

#### What happens here

`Encode` has significant flat — worth `list Encode`. `json.Marshal` cum larger — Encode calls it.

### Example 2 — list

```bash
go tool pprof -list Encode cpu.prof
```

#### What happens here

You see lines. Look for `make`, `append`, `Marshal` in a loop.

### Example 3 — mem top

```bash
go tool pprof -top mem.prof
```

#### What happens here

Which symbols allocate. Align with the `ReportAllocs` story.

### Example 4 — HTTP UI

```bash
go tool pprof -http=127.0.0.1:8080 cpu.prof
```

#### What happens here

Graph and tables in the browser. Useful for the call graph; flat/cum discipline still applies.

### Example 5 — Before/after note

```text
cpu_before: Encode flat 26%
cpu_after:  Encode flat 9%
bench: ns/op 2400→1800; allocs/op 4→1
```

#### What happens here

The PR story has a complete arc: map + number.

### Example 6 — Wrong target

```text
top shows runtime.gcBgMarkWorker
Dev “optimizes” GC GOGC blindly
```

#### What happens here

Without a mem finding in app code, GOGC tuning is often a mask. Find allocations.

### Example 7 — Link to the distributed world

```text
Local pprof: Encode slow
APM: 90% time in HTTP wait on payment
```

#### What happens here

Two different problems. A local profile does not deny APM — you choose the layer.

## Decision analysis

| Finding | Next step |
|-------|----------------|
| Your `make` in a loop | reuse / pool; bench allocs |
| High cum in lib, small flat | reduce calls / payload |
| Empty top | lengthen benchtime, re-record |
| Network dominates outside the process | APM / 12.x, not a pprof line |

## Trade-offs

| | Deep pprof ritual | Bench only |
|--|---------------------|------------|
| Diagnosis | precise | rough |
| Time | larger | smaller |
| CI | rarely | more often bench |

## Common mistakes

1. **Optimizing runtime** blindly.
2. **Only cum** or **only flat** without context.
3. **Conclusion from a thin profile.**
4. **No bench confirmation** after a change.
5. **Mixing** cover HTML with pprof.
6. **Expecting** cluster diagnosis from a local file.
7. **UI graph** without reading numbers.
8. **Ignoring** mem when GC is the symptom.
9. **Comparing** before/after with different inputs.
10. **Profile on every PR** as an obligation — excessive.

## Idiomatic Go

- `go tool pprof` from the toolchain.
- top → list → fix → bench.
- Document the finding in the PR.
- Read [pprof](https://github.com/google/pprof) / Go blog posts when you need deeper.
- The same mental model carries to `net/http/pprof` in a service — but that is a different setup.

## Practical scenario

Incident: CPU 90% on one service. Locally they reproduce with a bench + `cpu.prof`. `list` shows regex compilation on the hot path per request. Fix: `regexp.MustCompile` once in `init`/constructor. Bench −70% ns/op; production calms. Without `list`, the team would have “scaled pods.”

## Exercises

1. Open `cpu.prof` with `-top`; write down your top 3 symbols.
2. `list` on one; write a hypothesis in one sentence.
3. Compare `cpu_thin` vs `cpu_dense` top.
4. Open `mem.prof` `-top`; tie it to allocs/op.
5. Record before/after (or two revisions) and compare top5.
6. Run the `-http` UI and find the same symbol as in `list`.
7. Deliberately “optimize” the wrong thing; see that the bench does not confirm — rollback.
8. Explain flat vs cum to a colleague in 4 sentences.
9. Write 5 bullets: unit assert, coverage map, fuzz corpus, bench ns/op, pprof top.
10. Note one case where pprof is **not** the right tool (network/DB).

## Check questions

1. **Which command reads a profile?**  
   `go tool pprof [options] file.prof`.

2. **What does `top` do?**  
   Lists symbols by consumption.

3. **flat vs cum?**  
   Symbol alone vs symbol + descendants.

4. **What does dominant runtime.mallocgc often mean?**  
   Allocation pressure from app code — look at mem / bench allocs.

5. **How to confirm a fix?**  
   Same `Benchmark` + optionally a new profile.

6. **Does pprof replace APM?**  
   Not for distributed hops.

7. **First step after recording?**  
   `top`, then `list` on your symbol.

8. **Profile vs bench in CI?**  
   Bench as a budget guardian; profile as a detective when needed.

### Additional mechanism — call graph visualization

The `-http` UI shows a graph: node = symbol, edge = call. Thick nodes spend more. Use the graph to **navigate**, and `list` to **judge the line**. The graph alone does not replace bench confirmation.

### Example 9 — raw (advanced, brief)

```bash
go tool pprof -raw cpu.prof | more
```

#### What happens here

You see raw samples. Rarely needed on the course — `top`/`list` is enough. Know it exists when the UI truncates the view.

### Example 10 — Same symbol, different tool

```text
-benchmem: 4 allocs/op
mem.prof top: Encode dominant
```

#### What happens here

Number and map agree → strong hypothesis. If they disagree, check whether you recorded the same bench/input.

### Predict-then-answer: `list` shows a different file than expected

Answer: inline / generated code / same name in another package. Qualify with the full symbol path.

### “5 minute” on-call flow

1. Reproduce the bench locally.
2. Record `cpu.prof` (11.16).
3. `top10` — take the first **app** symbol.
4. `list` — one hypothesis.
5. If it is not app CPU — go to APM (module 12).

### Anti-pattern: UI screenshot without a command

A PR with a graph image, without a `go test ...` line. Nobody reproduces. A cheatsheet command is mandatory.
