# 11.02 Philosophy of the testing package: no mandatory assertion library

> **Go Path - Zero to Gopher** / **02 Intermediate → Creating Well-Tested Applications in Go** / Lesson 11.02

## Lesson goals

After this lesson you can:

- understand the **philosophy** of the stdlib `testing` package: simplicity, explicit checks, clear messages;
- know why Go teams often **do not** introduce an assert library at the start;
- use `t.Helper()`, `t.Errorf`, and `t.Fatalf` in the right places;
- distinguish **continuing** a test after an error from **stopping** the current test;
- read a `go test` report and understand where the failing line is in a helper;
- set habits that carry table-driven and HTTP tests in later lessons.

## Prerequisite

- Lesson 11.01 (why test, pyramid).
- Go 1.22+; basic `*_test.go` and `func TestXxx(t *testing.T)`.
- Understanding of `if`, functions, and `error` values.

## Problem this lesson solves

Programmers coming from the xUnit/JUnit/Chai world look for `assert.Equal(a, b)` and wonder why Go “has no assert”. Then they either:

- pull in a heavy library before learning `t.Fatal`, or
- write tests without messages (`if got != want { t.Fail() }`) so debugging takes longer than writing the code.

Another problem: a helper function without `t.Helper()` — CI says the error is in `assertEq` on line 12, while the real culprit is the call on line 87. You lose minutes on every failure.

The lesson shows that `testing` is **intentionally thin**: you control the branch, the message, and whether the test stops. That is a feature, not a gap.

## Mental model

`*testing.T` is a **report + flow control** for one test.

1. You do the **check** yourself (`if`, `==`, `errors.Is`).
2. **Reporting** goes through `t.Error` / `t.Errorf` (continue) or `t.Fatal` / `t.Fatalf` (stop this test).
3. A **helper** function that reports an error must call `t.Helper()` so the stack trace shows the *caller*, not the helper line.
4. An assertion library is **sugar** over the same model — useful when duplication hurts, not required for “real testing”.

Philosophy: explicitness > magic. You read the test and see exactly what counts as failure.

```text
go test runner
    │
    ▼
creates *testing.T for TestFoo
    │
    ▼
calls TestFoo(t)
    │
    ├─ t.Errorf  → records fail, continues
    ├─ t.Fatalf  → records fail, return from TestFoo
    └─ end without fail → PASS
```

## Mechanism

### The testing package

- The runner (`go test`) finds `TestXxx`, `BenchmarkXxx`, `FuzzXxx`, `ExampleXxx`.
- For each `TestXxx` it creates a `*testing.T` and calls the function.
- If any `Error`/`Fatal` remains recorded, the test is a fail.
- A panic in a test also fails the test (unless you catch it yourself — usually you should not).
- Other tests in the package can still run after one fails (unless the runner stops because of `-failfast`).

### Naming TestXxx

Rule from the documentation: the name must start with `Test`, and the next character must be an uppercase letter or `_` (not a lowercase letter right after `Test`).

| Name | Does the runner see it? |
|-----|-----------------|
| `TestAdd` | yes |
| `Test_add` | yes |
| `Testadd` | **no** (treated as an ordinary function) |
| `testAdd` | no |

### Trace: life of one TestXxx

```go
func TestSum(t *testing.T) {
	got := Sum(2, 2)
	if got != 4 {
		t.Fatalf("Sum(2,2)=%d, want 4", got)
	}
	t.Log("sum ok")
}
```

```text
1. go test compiles package + *_test.go
2. Finds TestSum
3. Allocates T, status=ok
4. Calls TestSum
5a. got==4 → Log (visible with -v) → return → PASS
5b. got!=4 → Fatalf records, stops TestSum → FAIL
6. Prints ok/FAIL for the package
```

### Why there is no mandatory assert package

- Stdlib wants a small surface API.
- `if got != want { t.Fatalf(...) }` is readable for juniors and in code review.
- Libraries (`testify`, etc.) add matchers, suites, mocks — useful in large codebases, but they hide flow if used without measure.
- Go Path - Zero to Gopher here teaches the **foundation**; you choose a library deliberately later.
- Even with a library, the same `*testing.T` still sits underneath.

### t.Errorf vs t.Fatalf

| Method | Effect | When |
|-------|--------|-----|
| `t.Error` / `t.Errorf` | fail + **continue** the function | you want more asserts in the same test (e.g. more `struct` fields) |
| `t.Fatal` / `t.Fatalf` | fail + **`return` from the test** | further steps make no sense (nil `pointer`, setup fail) |
| `t.Fail` / `t.FailNow` | same without a message | rarely; always prefer a message |

`Fatal` does not stop *another* test — only the current `Test` function (and exits it immediately).

### Predict, then check: Errorf or Fatalf?

```go
func TestUser(t *testing.T) {
	u, err := ParseUser(input)
	if err != nil {
		// A or B?
	}
	if u.Age != 30 {
		t.Errorf("age")
	}
	if u.Name != "Ana" {
		t.Errorf("name")
	}
}
```

**Predict:** what goes in place of the error after `ParseUser`?

**Answer:** `t.Fatalf` (or `t.Fatal`). If `err != nil`, `u` is often zero/`nil` — further field access is meaningless or panicky. For `Age` and `Name` use `Errorf` so you see *both* fields in one run.

### Trace: Errorf gathers, Fatalf cuts

```go
func TestPerson(t *testing.T) {
	got := Person{Name: "X", Age: 1}
	want := Person{Name: "Ana", Age: 30}
	if got.Name != want.Name {
		t.Errorf("Name: got %q want %q", got.Name, want.Name)
	}
	if got.Age != want.Age {
		t.Errorf("Age: got %d want %d", got.Age, want.Age)
	}
}
```

Output (condensed):

```text
--- FAIL: TestPerson
    person_test.go:12: Name: got "X" want "Ana"
    person_test.go:15: Age: got 1 want 30
```

One run, two diagnoses. With `Fatalf` on the first if you only see Name.

### t.Helper

When you extract a check into a function:

```go
func assertEq[T comparable](t *testing.T, got, want T) {
	t.Helper()
	if got != want {
		t.Fatalf("got %v, want %v", got, want)
	}
}
```

Without `t.Helper()`, `go test` shows the line inside `assertEq`. With it — the call line in the test. That saves minutes in a large suite.

### Trace: with and without Helper

```go
func assertEq(t *testing.T, got, want int) {
	// intentionally without t.Helper()
	if got != want {
		t.Fatalf("got %d want %d", got, want)
	}
}

func TestClip(t *testing.T) {
	assertEq(t, Clip(9), 8) // real fail here
}
```

```text
WITHOUT Helper:
  clip_test.go:5: got 9 want 8     ← line in assertEq

WITH t.Helper() at the top of assertEq:
  clip_test.go:12: got 9 want 8    ← call line in TestClip
```

### Predict, then check: does Helper “swallow” the error?

**Predict:** does `t.Helper()` change whether the test is PASS or FAIL?

**Answer:** No. It only changes **where** the report shows the location. The fail still counts.

### t.Log and -v

`t.Log` / `t.Logf` write messages that are shown by default when a test **fails**, or always with `-v`. Use them for context (input, intermediate value), not as a substitute for an assert.

### t.Cleanup

```go
func TestFile(t *testing.T) {
	f, err := os.CreateTemp("", "t")
	if err != nil {
		t.Fatal(err)
	}
	t.Cleanup(func() { os.Remove(f.Name()); f.Close() })
	// ... test ...
}
```

Cleanup runs even after `Fatal` in that test (LIFO order). Better than scattered `defer` when setup goes into a loop of subtests.

### t.Run (preview)

```go
t.Run("local", func(t *testing.T) { ... })
```

Creates a subtest with its own name in the report and for `-run`. Details in 11.03 and 11.05. Important already: `Fatal` in a subtest stops **that** subtest, not necessarily the parent in a way that stops other `t.Run` calls (the parent continues to the next `t.Run` unless you check yourself).

### Parallel (preview)

`t.Parallel()` strongly speeds things up, but requires isolation. Do not touch a shared `map` without synchronization. The module will later insist on this in HTTP and fuzz contexts where it matters.

## Rules and syntax

```go
package pricing

import "testing"

func TestApplyDiscount(t *testing.T) {
	got, err := ApplyDiscount(1000, 10)
	if err != nil {
		t.Fatalf("unexpected err: %v", err)
	}
	if got != 900 {
		t.Errorf("got %d, want 900", got)
	}
}
```

Required rules:

1. Signature: `func TestXxx(t *testing.T)` — the first parameter is `*testing.T`.
2. After a setup error → `Fatalf`.
3. After independent fields → `Errorf` to gather signal.
4. Every helper that calls `Error`/`Fatal` → `t.Helper()` at the top.
5. Message: `got ... want ...` (or equivalent) — diagonally readable in CI.
6. Do not swallow `error` with `_` in a test if it is part of the contract.
7. Do not use `panic` for an expected fail — use `t.Fatal`.

Go 1.22+: generic helpers (`assertEq[T comparable]`) are valid and common.

## Examples

### Example 1 — Minimal test with Fatalf

```go
package mathx

import "testing"

func Add(a, b int) int { return a + b }

func TestAdd(t *testing.T) {
	got := Add(2, 3)
	if got != 5 {
		t.Fatalf("Add(2,3)=%d, want 5", got)
	}
}
```

#### What happens here

One check, one message. If it fails, there is nothing further to run — `Fatalf` is enough.

### Example 2 — Errorf for multiple fields

```go
func TestParsePoint(t *testing.T) {
	got, err := ParsePoint("3,4")
	if err != nil {
		t.Fatalf("ParsePoint: %v", err)
	}
	if got.X != 3 {
		t.Errorf("X: got %d want 3", got.X)
	}
	if got.Y != 4 {
		t.Errorf("Y: got %d want 4", got.Y)
	}
}
```

#### What happens here

Setup must succeed (`Fatalf`). Coordinates are independent checks (`Errorf`). One fail run can show both errors if both are wrong.

### Example 3 — Helper with t.Helper

```go
func assertNoErr(t *testing.T, err error) {
	t.Helper()
	if err != nil {
		t.Fatalf("unexpected err: %v", err)
	}
}

func assertEq[T comparable](t *testing.T, got, want T) {
	t.Helper()
	if got != want {
		t.Fatalf("got %v, want %v", got, want)
	}
}

func TestQuote(t *testing.T) {
	got, err := Quote(10, "local")
	assertNoErr(t, err)
	assertEq(t, got, 502)
}
```

#### What happens here

A failure shows the line in `TestQuote`, not in the helper. Generic `assertEq` works for `int`, `string`, and other `comparable` types.

### Example 4 — Bad Fail without a message

```go
func TestBad(t *testing.T) {
	if Sum(1, 1) != 2 {
		t.Fail()
	}
}
```

#### What happens here

CI says FAIL without `got/want`. You have to open the code. Always write a message.

### Example 5 — Cleanup after Fatal

```go
func TestTemp(t *testing.T) {
	dir, err := os.MkdirTemp("", "demo")
	if err != nil {
		t.Fatal(err)
	}
	t.Cleanup(func() { os.RemoveAll(dir) })

	if err := os.WriteFile(dir+"/a.txt", []byte("x"), 0o600); err != nil {
		t.Fatal(err) // Cleanup still runs
	}
}
```

#### What happens here

Even when `Fatal` cuts the test, the temp directory is removed. Without Cleanup/defer, junk remains on disk on CI agents.

### Example 6 — Predict the report

Code:

```go
func TestTwo(t *testing.T) {
	t.Error("first")
	t.Fatal("second")
	t.Error("third")
}
```

**Predict:** which messages do you see?

**Answer:** `first` and `second`. `third` is not executed because `Fatal` acts like `FailNow` + return.

## Decision analysis

| Decision | Motive |
|--------|--------|
| Explicit `if` instead of assert lib from day one | You learn the model; review sees the branch |
| `Fatalf` after `err != nil` | Prevents nil deref and false follow-up fails |
| `Errorf` for independent fields | More signal per run |
| `t.Helper` in every assert helper | Exact line in CI |
| `got/want` format | Scannable log |
| Soften libraries later | Less magic until the foundation is solid |

## Trade-offs

- **Assert lib** — less typing, more abstraction; juniors do not see the flow.
- **Only Fatalf everywhere** — simple, but you lose multiple diagnoses.
- **Only Errorf everywhere** — continues after nil and creates panics or junk in the log.
- **Deep helpers** — DRY, but too many layers hide what is asserted; keep them thin.
- **t.Log in passing tests** — with `-v` it greens the CI log; use sparingly.

## Common mistakes

1. `Testfoo` with a lowercase letter — the runner ignores the function.
2. Forgotten `t.Helper()` — false line in the report.
3. `t.Fatal(err)` without context of what was called.
4. Comparing errors via `err.Error() == "..."`.
5. Assertion on a private detail instead of the contract.
6. `panic("fail")` instead of `t.Fatal`.
7. Swallowed `error`: `got, _ := Foo()`.
8. Shared mutable state without isolation.
9. Copy-paste `if` without a table when there are 8 of the same (solve in 11.05).
10. Introducing testify on day 1 instead of learning `T`.

## Idiomatic Go

- Messages: `got %v, want %v` or `Func(x)=%v, want %v`.
- Helpers in the same `*_test.go` or `assert_test.go` in the package.
- For complex `struct` later `go-cmp`; for now explicit fields are OK.
- Do not test panic unless it is the *contract* to panic (rare in idiomatic Go — prefer `error`).
- Keep the test readable top to bottom: arrange → act → assert.

## Practical scenario

A team introduced `testify/assert` everywhere. Review became an `assert.Equal(t, a, b)` wall. A new teammate does not know that `assert.Equal` **does not** stop the test (unlike `require`). After two nil panics in tests, they introduce a rule: `require` for prerequisites, `assert` for fields — or they return to stdlib `Fatalf`/`Errorf` in smaller packages. Lesson: a library does not replace understanding `*testing.T`.

## Exercises

1. Write `TestClamp` with `Fatalf` on a wrong result.
2. Extend it to check three fields of a result-struct with `Errorf`.
3. Extract `assertEq` with `t.Helper` and deliberately break want — confirm the line in the report.
4. Remove `t.Helper` and compare the line; put it back.
5. Write a test with `t.Error` then `t.Fatal` then `t.Error` — predict which messages appear, then check.
6. Add `t.Cleanup` that deletes a temp file and call `t.Fatal` before the end — confirm the file is gone.
7. Run `go test -v` and read the `t.Log` output.

## Check questions

1. **What does `t.Errorf` do that `t.Fatalf` does not?**  
   It records a fail and **continues** executing the test.

2. **What is `t.Helper` for?**  
   It moves the reported error location to the helper's caller.

3. **Why does Go not have a mandatory assert package?**  
   Intentionally thin API; explicit checks are part of the culture.

4. **Does `Fatal` stop the whole `go test` process?**  
   No — it stops the current test (function); other tests can continue.

5. **Predict:** `func Testadd(t *testing.T)` — does it run?  
   No. After `Test` there must be an uppercase letter or `_`.

6. **When do you choose Fatalf right after a call?**  
   When `error != nil` or the value is unusable for further asserts.

7. **What does `t.Fail()` not give?**  
   A message — that is why you avoid it.

## Deeper mechanism: *testing.T state

Internally (simplified for learning):

```text
T {
  failed  bool
  skipped bool
  finished bool  // after FailNow/Fatal
  helpers map[pc]bool
  ...
}
```

- `Error` / `Errorf` → `failed = true`, continue.
- `Fatal` / `Fatalf` / `FailNow` → `failed = true`, `runtime.Goexit` in the test goroutine (so it looks like return, but it is not an ordinary return from defer the same way — **defers still run**).
- `Skip` / `SkipNow` → skipped, not a fail.

### Predict, then check: defer after Fatal

```go
func TestDefer(t *testing.T) {
	x := 0
	defer func() { x = 1 }()
	t.Fatal("stop")
	// does defer set x?
}
```

**Answer:** Yes — `Fatal` stops the test goroutine via `Goexit`, and `defer` in that function still runs. That is why `t.Cleanup` and `defer` remain reliable for cleanup.

### Trace: FailNow vs return

```go
func TestManual(t *testing.T) {
	if bad {
		t.Error("bad")
		return // manual return after Error — OK
	}
}
```

`Error` + `return` ≈ often enough. `Fatal` = `Error` + `FailNow` (forced exit). Use `Fatal` when you do not want to forget `return`.

### Helper in a closure

```go
func TestClosure(t *testing.T) {
	check := func(got, want int) {
		t.Helper()
		if got != want {
			t.Fatalf("got %d want %d", got, want)
		}
	}
	check(1, 2)
}
```

`t.Helper()` inside a function literal works — the location jumps to the `check(1, 2)` line. Forgotten Helper → line inside the literal.

### What an assertion library actually does

Pseudo:

```go
func Equal(t *testing.T, got, want any) {
	t.Helper()
	if !objectsAreEqual(got, want) {
		t.Errorf(...)
	}
}
```

That is the same model. `require.Equal` calls something closer to `Fatalf`. When you understand this, you choose a library for ergonomics, not for “real” testing.

### Message protocol (team standard)

A proposal that scales:

```text
FuncName(args): got %v, want %v
unexpected err: %v
expected err, got nil
field X: got %v, want %v
```

When everyone uses the same shape, the CI log is read diagonally. Do not mix Serbian and English messages randomly in the same package — pick the team's language and stick to it.

### Mini exercise in your head before 11.03

Imaginary output:

```text
--- FAIL: TestInvoice (0.00s)
    assert_test.go:14: got 0 want 10
```

`assert_test.go:14` is in a helper. **Predict** the first fix in review: add `t.Helper()`. After that the output shows `invoice_test.go:88` — the real call.

### Additional mechanism — testing.T as report and flow control

`*testing.T` is not an assertion library. You write `if`, choose the message, choose whether the test **continues** or **stops**.

#### Trace of one check

```text
got != want
  |- t.Errorf  -> Fail, continue (more checks in the same test)
  |- t.Fatalf -> FailNow, stop immediately
```

**Predict-then-answer:** after `Fatalf`, does the next `if` in the same test run?

Answer: no.

### Example — Errorf vs Fatalf on the error path

```go
got, err := Parse(in)
if err != nil {
	t.Fatalf("Parse(%q): %v", in, err) // got is not reliable
}
if got != want {
	t.Errorf("Parse(%q)=%v, want %v", in, got, want)
}
```

#### What happens here

On an unexpected error you stop. On a wrong value you can Errorf if you want more asserts — often one Fatalf with a full message is clearer.

### Example — t.Helper()

```go
func assertEq(t *testing.T, got, want int) {
	t.Helper()
	if got != want {
		t.Fatalf("got %d want %d", got, want)
	}
}

func TestSum(t *testing.T) {
	assertEq(t, Sum(2, 2), 4) // fail shows this line
}
```

#### What happens here

Without `Helper()`, CI shows the line in `assertEq`. With `Helper()` — the caller's line. That saves minutes on every failure.

### Method table

| Method | Effect |
|-------|--------|
| `t.Fail` | mark fail, continue |
| `t.FailNow` | mark fail, stop |
| `t.Error` / `Errorf` | Fail + message |
| `t.Fatal` / `Fatalf` | FailNow + message |
| `t.Helper` | hide helper from the location |
| `t.Cleanup` | reliable resource release |
| `t.Run` | named subtest |

### Predict-then-answer — Fatal from a goroutine

Answer: do not call `Fatal`/`FailNow` from another goroutine. Report on the main one (channel / `Error` + sync).

### Predict-then-answer — `t.Fail()` without a message

Answer: CI says it failed, but not why. Always `Errorf`/`Fatalf` with got/want.

### When to introduce an assert library

| Signal | Stay on stdlib | Library / cmp |
|--------|------------------|----------------|
| Small package | yes | not yet |
| Deep equal of large structs | `cmp.Diff` | yes |
| Team does not know Fatal/Helper | learn first | later |

### Example — Cleanup

```go
func TestFile(t *testing.T) {
	f := createTemp(t)
	t.Cleanup(func() { _ = f.Close() })
	// ...
}
```

#### What happens here

Cleanup is called even when the test fails — clearer ownership than “a stack of defer in a helper”.

### Scenario

Helper `mustEq` without `Helper()` — every fail “on line 12”. After one `t.Helper()` review time drops; people see the real call.

### Common mistakes (this lesson)

1. `t.Fail()` without a message.
2. Helper without `Helper()`.
3. Fatal from a goroutine.
4. Fatalf when it still makes sense to gather more Errorf (rare, but).
5. Assertion library before mastering the model.
6. Message “fail” instead of got/want/input.

### Additional exercises

1. Deliberately remove Helper; compare the fail output.
2. Make two Errorf; read the report.
3. Refactor three copy-paste if into a helper with Helper.
4. Try Fatal from a goroutine — record why not.
5. Rewrite one message to include the input.
6. Add Cleanup on a test that opens a resource.
7. Write a team rule: Fatal when it cannot continue.
8. Read the `testing` docs for Cleanup and Run.

### Questions

1. **Difference between Errorf and Fatalf?** Continue vs stop.
2. **What does Helper do?** Fixes the fail location.
3. **Why got/want?** Fast debug.
4. **May Fatal be in a goroutine?** No.
5. **What is Cleanup for?** Reliable Close with T.
6. **Is an assert library mandatory?** No.

## Summary

The `testing` package expects you to write checks and messages. `Errorf` gathers, `Fatalf` stops, `Helper` cleans traces. An assertion library is an option, not a prerequisite — master this model first. Next lesson: how `go test` finds, caches, and filters those functions.
