# 11.08 Testing code samples: living documentation

> **Go Path - Zero to Gopher** / **02 Intermediate → Creating Well-Tested Applications in Go** / Lesson 11.08

## Lesson goals

- Treat a code sample as **part of the product**, not as decoration in a README.
- Distinguish `Example` (11.07), `examples/` programs, and `TestSample_` / tutorial tests.
- Include samples in CI (`go test`, `go build ./examples/...`).
- Avoid secrets, paid API calls, and nondeterminism in living examples.
- Reduce drift between README, wiki, and the real API.
- Know what **does not** belong in a unit sample (manual UI, production keys).

## Prerequisite

- Lessons 11.06–11.07 (black-box, Example).
- Basic module: `go.mod`, `go build`, `go test ./...`.
- Preferred: local CI or a script that runs tests.

## Problem this lesson solves

Three common symptoms:

1. **README lies** — a snippet uses a removed parameter.
2. **Wiki example** only works on the author's laptop (absolute paths, personal token).
3. **`examples/demo`** has not built for months; a new engineer “fixes” docs instead of code.

A sample that is not under `go test` / `go build` in CI **rots**. This lesson sets a system: what to keep alive, where it lives, how to verify.

## Mental model

Think of three shelves of documentation:

```text
┌─────────────────┐  ┌──────────────────┐  ┌────────────────────┐
│ ExampleXxx      │  │ TestSample_...   │  │ examples/*/main.go │
│ next to symbol  │  │ flow in *_test.go│  │ mini applications  │
│ Output + godoc  │  │ assert / fake    │  │ go build in CI     │
└─────────────────┘  └──────────────────┘  └────────────────────┘
         │                     │                      │
         └──────────┬──────────┴──────────────────────┘
                    ▼
              “Do not lie to the user”
```

| Form | Length | Check | Audience |
|-------|--------|---------|---------|
| Example | short | stdout | API readers |
| Sample test | medium | `t.Fatal` | tutorial flow |
| `examples/` | longer | `go build` (+test) | “how do I run it” |

## Mechanism

### Why a sample “dies”

1. The API changes in a PR that does not touch the README.
2. A reviewer does not see markdown as code.
3. There is no job that compiles the snippet.

Therefore a snippet must either:

- be an **Example** (compiles as Go), or
- be in a **`.go` file** under build/test, or
- be generated from code (advanced; out of course scope).

A markdown fenced block **by itself** is not a test.

### Layer 1 — Example as the source of truth for short calls

Already covered in 11.07. README says:

```markdown
See `ExampleClient_Get` in the package documentation.
```

instead of duplicating 15 lines that will go stale.

### Layer 2 — `TestSample_` for multi-step flows

When a tutorial has steps “create client → write → read”, Example becomes awkward (too much stdout). Instead:

```go
func TestSample_WriteThenRead(t *testing.T) {
	// steps 1–3 with a fake store
}
```

The name `TestSample_` (or `TestTutorial_`) signals: this is a **documentation flow**, not only a unit edge case.

### Layer 3 — `examples/` modules or packages

```text
examples/
  hello/
    main.go
  checkout/
    main.go
```

CI:

```bash
go build ./examples/...
# or:
go test ./examples/...
```

If an example is a separate mini-module (`examples/hello/go.mod`), CI must explicitly enter that dir — document it in the README.

### Trace: drift detection

```text
PR changes Client.Get signature
    │
    ├─ ExampleClient_Get  → fail (stdout / compile)
    ├─ TestSample_Get     → fail (compile / assert)
    ├─ examples/hello     → build fail
    └─ README.md          → CI stays silent  ← hole
```

Therefore README points to living code, not the other way around.

### Predict-then-answer: does `go test ./...` build `examples/hello` with only `main`?

If `examples/hello` is part of the same module and has no `*_test.go`, `go test ./examples/hello` still compiles the package (including `main`) in a test context — but team practice often explicitly does `go build ./examples/...` for clarity. Check your CI; do not assume.

### What to forbid in a living sample

| Forbidden | Why | Alternative |
|------------|-------|-------------|
| API keys in code | leakage | env + skip if missing |
| Paid SaaS calls | cost, flaky | `httptest` stub |
| `time.Now` in Output | flaky | fixed clock |
| Absolute Windows paths of the author | does not work for others | `t.TempDir()` |
| “Click in the browser” steps | not automated | separate manual doc |

### Sample with network — allowed shape

```go
func TestSample_HTTPGet(t *testing.T) {
	ts := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprint(w, `{"ok":true}`)
	}))
	t.Cleanup(ts.Close)

	client := NewClient(ts.URL) // injected base URL
	// ...
}
```

Details of `httptest` — lessons 11.09–11.10. Here the message is: a **sample may teach an HTTP flow**, but not the real internet.

### Predict-then-answer: may a sample read `os.Getenv("PROD_SECRET")`?

It can with:

```go
if os.Getenv("PROD_SECRET") == "" {
	t.Skip("PROD_SECRET not set")
}
```

But for **unit** CI on a PR it is better that a sample does not require a secret at all. Keep a “live integration” sample in a nightly job with a vault, separately.

### PR checklist for docs

1. Is the snippet captured in `.go` / Example?
2. Does CI build/test cover that path?
3. Does README only link?
4. Are there secrets / network / nondeterminism?

## Rules and syntax

1. Short API call → `Example` (11.07).
2. Multi-step tutorial → `TestSample_` with fakes.
3. Runnable demo → `examples/...` + `go build` in CI.
4. README does not duplicate — it points.
5. No secrets in git.
6. No external network in default `go test ./...`.
7. Name clearly so review recognizes a docs test.
8. Delete or mark outdated wiki snippets that cannot be under test.

Minimal CI fragment (conceptual):

```bash
go test ./...
go build ./examples/...
```

## Examples

### Example 1 — README points to Example

````markdown
## Quick start

```go
// Do not paste long code here — see ExampleClient_Ping in the client package.
```
````

Better:

```markdown
## Quick start

Run and read `ExampleClient_Ping` (godoc / source `client/example_test.go`).
```

#### What happens here

One source of truth. README cannot “lag” behind another form of the same code.

### Example 2 — TestSample with a fake store

```go
package notebook_test

import (
	"testing"

	"example.com/app/notebook"
)

type memStore struct {
	m map[string]string
}

func (m *memStore) Put(k, v string) error {
	if m.m == nil {
		m.m = map[string]string{}
	}
	m.m[k] = v
	return nil
}

func (m *memStore) Get(k string) (string, bool) {
	v, ok := m.m[k]
	return v, ok
}

func TestSample_WriteThenRead(t *testing.T) {
	store := &memStore{}
	nb := notebook.New(store)

	if err := nb.Write("hello", "world"); err != nil {
		t.Fatalf("Write: %v", err)
	}
	got, ok := nb.Read("hello")
	if !ok || got != "world" {
		t.Fatalf("Read got %q ok=%v", got, ok)
	}
}
```

#### What happens here

The tutorial “write then read” is executable. No disk, no Docker. `memStore` implements the same interface production expects — the sample teaches **dependency injection** along the way.

### Example 3 — examples/hello

```go
// examples/hello/main.go
package main

import (
	"fmt"

	"example.com/learn/greeter"
)

func main() {
	fmt.Println(greeter.Hello("Marko"))
}
```

```bash
go build -o bin/hello ./examples/hello
./bin/hello
```

#### What happens here

The user sees a real `main`. CI guarantees it compiles. Output is not compared automatically here — optionally add a `Test` in `examples/hello` or leave an Example in the library.

### Example 4 — Outdated wiki → archive

```markdown
> **Outdated (2024):** this snippet uses Client v1.
> Use `TestSample_WriteThenRead` and `examples/checkout`.
```

#### What happens here

Better explicitly outdated than silently wrong. Even better: delete and replace with a link.

### Example 5 — Sample that deliberately Skips an external system

```go
func TestSample_LiveAPI(t *testing.T) {
	if os.Getenv("LIVE_API") != "1" {
		t.Skip("set LIVE_API=1 to run live sample")
	}
	// ...
}
```

#### What happens here

Default CI stays fast and without network. A nightly job can set `LIVE_API=1`. The name and Skip message must be clear.

### Example 6 — Duplication that hurts

```go
// README
client.Get(ctx, "/v1/x")

// Example
client.Get(ctx, id) // new signature

// examples/hello
client.Get("/v1/x") // old
```

#### What happens here

Three truths. After this lesson: README link, one Example, one example main — or main calls the same helper as the test.

**Predict-then-answer:** which layer does CI catch first on a signature change?

Answer: whichever **compiles** — Example and `examples/` and `TestSample_`. Markdown README last (never, without an extra tool).

### Example 7 — Small golden for a stdout CLI sample

```go
func TestSample_CLIHelp(t *testing.T) {
	cmd := exec.Command("go", "run", "./examples/hello", "-help")
	out, err := cmd.CombinedOutput()
	if err != nil {
		t.Fatalf("%v: %s", err, out)
	}
	if !bytes.Contains(out, []byte("Usage")) {
		t.Fatalf("help missing Usage: %s", out)
	}
}
```

#### What happens here

A soft assert (`Contains`) instead of a whole golden file — less brittleness. (More on golden traps in 11.10.)

## Decision analysis

| Question | Answer leads to |
|---------|-----------------|
| 5 lines next to a symbol? | Example |
| 3 steps with a fake DB? | TestSample |
| User needs a binary? | examples/ |
| Only a marketing screenshot? | do not automate as unit |
| Need real cloud? | separate integration job |

**Decision:** if you call something a “sample” and it is not under CI, either connect it or mark it “unmaintained”.

## Trade-offs

| | More living samples | Fewer / only Example |
|--|----------------------|----------------------|
| Onboarding | faster | slower |
| CI time | longer | shorter |
| Maintenance | higher cost | lower |
| README drift risk | lower if they link | higher if they duplicate |

Team trade-off: **few, but alive** > **many dead**.

## Common mistakes

1. **Markdown snippet as the only documentation “test”.**
2. **Secrets in examples/** committed “temporarily”.
3. **Real HTTP** in `go test ./...` on every PR.
4. **Absolute paths** and personal home dir.
5. **Duplication** README + Example + main with three API versions.
6. **Huge example** that nobody runs locally.
7. **Forgotten `go build ./examples/...`** in CI.
8. **Sample without `t.Cleanup` / Close** on servers and files.
9. **Mixing a load test** into a “hello world” sample.
10. **Silence on `Skip`** — all samples skip and nobody notices.

## Idiomatic Go

- `examples/` at the module root — common in public projects.
- Example for a symbol; `examples` for a story.
- Interface + fake in a sample test.
- `t.TempDir()` for files.
- Document in CONTRIBUTING: “new sample = CI covered”.

## Practical scenario

An SDK team has 12 README snippets. After a v2 breaking change, support gets 30 tickets a day. An engineer spends a sprint only on docs.

New policy:

1. All short snippets → Example.
2. Two tutorials → `TestSample_*`.
3. Three demos → `examples/...` + CI build.
4. README clean links.

Tickets drop; the next breaking change breaks CI the same day, not users after release.

## Check questions

1. **Why test samples?**  
   So documentation does not lie and CI catches API drift.

2. **Example vs examples/main?**  
   Example for a short API next to a symbol; `examples/` for demos with `main`.

3. **What should CI at least do for examples?**  
   `go build` (and test if it exists).

4. **What does not belong in a living sample?**  
   Secrets, paid calls without control, nondeterminism, manual UI.

5. **How to reduce README/Example duplication?**  
   README points to Example; Example is the source of truth.

6. **What is the `TestSample_` name for?**  
   A signal that the test is a documentation flow, not only an edge case.

7. **When `t.Skip` for a live API?**  
   When it is explicitly opt-in; default CI without secrets and network.

8. **Does a markdown fence get checked by CI?**  
   No — it must be `.go` / Example / a special tool.

### Additional mechanism — sample as a contract with the user

When you publish an SDK, a sample is part of the **public contract** just like the exported API. A breaking change in the API without updating the sample = a breaking change in onboarding practice.

Therefore a sample enters the same review channel as code: diff, test, CI.

### Example 8 — Generator? (out of scope, but awareness)

Some teams generate README from Example output. Not required on the course — the principle matters: **one source of truth**. If you ever introduce a generator, CI must still verify it.

### Example 9 — Versioning samples

```text
examples/
  v1/
    hello/main.go
  v2/
    hello/main.go
```

#### What happens here

Major SDK versions keep separate demos. CI builds both while v1 lasts. Document EOL.

### Example 10 — Sample that teaches errors

```go
func TestSample_InvalidConfig(t *testing.T) {
	_, err := notebook.New(nil)
	if err == nil {
		t.Fatal("expected error for nil store")
	}
}
```

#### What happens here

Onboarding does not show only the happy path — it shows what an expected error looks like. Still without network and secrets.

### Predict-then-answer: may `examples` have its own `go.mod`?

Answer: yes, often for isolating dependency versions. CI must explicitly `cd examples/hello && go test` / `go build`. Document it.

### Checklist “before deleting an old sample”

1. Is there a replacement (Example / new example)?  
2. Are README links updated?  
3. Does the CI job no longer build a dead path?  
4. Does CHANGELOG mention the removal?

## Summary

A code sample is part of the product. Keep it alive through Example, Sample tests, and building `examples/`. Remove secrets and network from unit examples. Fewer dead snippets — fewer support tickets and faster onboarding. Documentation that passes `go test` earns trust.
