# 11.14 Benchmark testing: `BenchmarkXxx`, `b.N`, and allocations

> **Go Path - Zero to Gopher** / **02 Intermediate → Creating Well-Tested Applications in Go** / Lesson 11.14

## Lesson goals

- Write `BenchmarkXxx(b *testing.B)` functions by convention.
- Understand the loop driven by **`b.N`** as the **primary** model on Go **1.22+**.
- Use `ResetTimer`, `StopTimer` / `StartTimer` for clean setup.
- Measure memory with `ReportAllocs` and `-benchmem`.
- Know **`b.Loop`** only as an API from **Go 1.24+** — do not force it on an older toolchain.
- Read ns/op, B/op, allocs/op and variance (multiple runs).
- Avoid traps: measuring setup, dead-code elimination, unstable input.

## Prerequisite

- Lesson 11.13 (when a bench makes sense).
- `go test`, packages, basic Go.
- Toolchain **Go 1.22+** for the course; note for 1.24 where needed.

## Problem this lesson solves

In 11.13 you decided *to* measure. Now you need *how* to write a measurement that:

- does not count data preparation into ns/op;
- does not lie because the compiler optimized away a “dead” result;
- reports allocations when that is part of the budget;
- works on Go 1.22+ with `b.N` without depending on the 1.24 API.

## Mental model

```text
go test -bench=BenchmarkX -benchmem
        │
        ▼
  chooses N (automatically) to run “long enough”
        │
        ▼
  your code: for i := 0; i < b.N; i++ { ... }
        │
        ▼
  ns/op ≈ total_time / N
  B/op, allocs/op if -benchmem / ReportAllocs
```

`b.N` is **not** your fixed “1000.” The runner increases N until it gets a stable sample.

## Mechanism

### Signature and name

```go
func BenchmarkQuote(b *testing.B) {
	for i := 0; i < b.N; i++ {
		_, _ = Quote(200, "local")
	}
}
```

- Name starts with `Benchmark`.
- Parameter `*testing.B` (not `*testing.T`).
- Lives in `*_test.go`.

### Primary pattern: `b.N` (Go 1.22+)

```go
for i := 0; i < b.N; i++ {
	// measured work
}
```

That is the **main** style on the course and in industry for 1.22/1.23.

### Note: `b.Loop` (Go 1.24+)

From Go **1.24** there is:

```go
for b.Loop() {
	// measured work
}
```

Use **only** if the team toolchain is ≥ 1.24 and the team agrees. On the course Go 1.22+ the primary is **`b.N`**. Do not mix it into the material as a requirement.

### ResetTimer — setup outside measurement

```go
func BenchmarkParse(b *testing.B) {
	data := bytes.Repeat([]byte("x"), 1<<20) // expensive setup
	b.ResetTimer()
	for i := 0; i < b.N; i++ {
		_, _ = Parse(data)
	}
}
```

Without `ResetTimer`, allocating a 1MiB buffer enters the time — false ns/op.

### StopTimer / StartTimer

```go
func BenchmarkWithPerIterSetup(b *testing.B) {
	for i := 0; i < b.N; i++ {
		b.StopTimer()
		in := makeInput() // do not measure
		b.StartTimer()
		_ = process(in)
	}
}
```

Use rarely — per-iteration Stop/Start has its own cost. Prefer setup before the loop + `ResetTimer`.

### ReportAllocs and -benchmem

```go
func BenchmarkEncode(b *testing.B) {
	b.ReportAllocs()
	for i := 0; i < b.N; i++ {
		_, _ = Encode(payload)
	}
}
```

```bash
go test -bench=BenchmarkEncode -benchmem ./...
```

Output (illustration):

```text
BenchmarkEncode-8   500000   2400 ns/op   512 B/op   4 allocs/op
```

| Column | Meaning |
|--------|----------|
| ns/op | average time per operation |
| B/op | bytes allocated per op |
| allocs/op | number of allocations per op |
| `-8` | `GOMAXPROCS` |

### Dead-code / compiler trap

```go
// BAD: result is unused — the compiler may “eat” the work
for i := 0; i < b.N; i++ {
	Quote(200, "local")
}
```

Better:

```go
var sink int
for i := 0; i < b.N; i++ {
	sink, _ = Quote(200, "local")
}
_ = sink
```

or `b.SetBytes` when you measure throughput:

```go
b.SetBytes(int64(len(data)))
```

### Predict-then-answer: is one run enough?

```bash
go test -bench=BenchmarkQuote -count=1
```

Answer: for a rough feel yes. For a regression decision: `-count=5` (or more) and watch the range, not one lucky number.

### Parallel bench

```go
func BenchmarkQuoteParallel(b *testing.B) {
	b.RunParallel(func(pb *testing.PB) {
		for pb.Next() {
			_, _ = Quote(200, "local")
		}
	})
}
```

Harder to interpret (lock, false sharing). First master sequential `b.N`.

### Sub-benchmarks

```go
func BenchmarkQuote(b *testing.B) {
	for _, zone := range []string{"local", "eu"} {
		b.Run(zone, func(b *testing.B) {
			for i := 0; i < b.N; i++ {
				_, _ = Quote(200, zone)
			}
		})
	}
}
```

### Execution trace

1. `go test` finds `Benchmark*`.
2. Calibrates N.
3. Runs the loop.
4. Prints ns/op (+ mem if you ask).
5. With `-cpuprofile` (11.16) it can record a profile during the bench.

### Note on inlining and odd jumps

A tiny change sometimes “kills” inlining and ns/op jumps. Check the same input, same build tags, without `-race` in a perf measurement (race slows things down). Do not conclude immediately that the algorithm is at fault.

## Rules and syntax

```bash
go test -bench=BenchmarkQuote -benchmem -count=5 ./ship/
go test -bench=. -benchtime=2s ./ship/
```

Rules:

1. `Benchmark` prefix; `*testing.B`.
2. Loop `i < b.N` on Go 1.22+ (primary).
3. `b.Loop` only with a Go 1.24+ agreement.
4. Setup → `ResetTimer` → loop.
5. Keep the result (sink) against DCE.
6. `-benchmem` / `ReportAllocs` for memory.
7. Multiple `-count` for variance.
8. Correctness unit tests stay separate.

## Examples

### Example 1 — Minimal bench

```go
func BenchmarkQuoteLocal(b *testing.B) {
	for i := 0; i < b.N; i++ {
		_, _ = ship.Quote(200, "local")
	}
}
```

#### What happens here

Clean hot path. The runner chooses N. You get ns/op.

### Example 2 — ResetTimer

```go
func BenchmarkHashBig(b *testing.B) {
	data := make([]byte, 1<<20)
	for i := range data {
		data[i] = byte(i)
	}
	b.ResetTimer()
	for i := 0; i < b.N; i++ {
		_ = Hash(data)
	}
}
```

#### What happens here

Preparing 1MiB is not in ns/op. Hash is.

### Example 3 — ReportAllocs

```go
func BenchmarkEncode(b *testing.B) {
	payload := map[string]string{"a": "b"}
	b.ReportAllocs()
	b.ResetTimer()
	for i := 0; i < b.N; i++ {
		_, _ = json.Marshal(payload)
	}
}
```

#### What happens here

You see allocs/op. A “≤ 1 alloc” budget becomes checkable.

### Example 4 — Sink against elimination

```go
var blackhole int

func BenchmarkAbs(b *testing.B) {
	for i := 0; i < b.N; i++ {
		blackhole = Abs(-i)
	}
}
```

#### What happens here

A global/package sink prevents the compiler from throwing away the loop. (Sometimes a local `sink` + `_ = sink` after the loop is enough.)

### Example 5 — Sub-benchmark input size

```go
func BenchmarkParse(b *testing.B) {
	for _, n := range []int{16, 1024, 1 << 20} {
		b.Run(fmt.Sprintf("n=%d", n), func(b *testing.B) {
			data := make([]byte, n)
			b.SetBytes(int64(n))
			b.ResetTimer()
			for i := 0; i < b.N; i++ {
				_, _ = Parse(data)
			}
		})
	}
}
```

#### What happens here

`SetBytes` gives MB/s in the output. Sizes reveal scaling.

### Example 6 — Go 1.24 Loop (note only)

```go
// +build go1.24

func BenchmarkQuoteLoop(b *testing.B) {
	for b.Loop() {
		_, _ = ship.Quote(200, "local")
	}
}
```

#### What happens here

Same goal as `b.N`, newer API. On the course it remains **optional**; primary material uses `b.N`.

### Example 7 — Parallel

```go
func BenchmarkQuoteParallel(b *testing.B) {
	b.RunParallel(func(pb *testing.PB) {
		for pb.Next() {
			_, _ = ship.Quote(200, "local")
		}
	})
}
```

#### What happens here

Measures behavior under concurrent calls. Interpret carefully.

### Example 8 — Checklist before merging a perf PR

- [ ] Unit tests still pass
- [ ] `go test -bench=... -benchmem` before/after in the description
- [ ] `go version` listed
- [ ] Bench input documented
- [ ] No requirement for `b.Loop` if `go` < 1.24
- [ ] Allocations commented if they are part of the budget

## Decision analysis

| Need | Tool |
|---------|------|
| Operation time | `b.N` loop + ns/op |
| Memory | `-benchmem` / `ReportAllocs` |
| Setup outside measure | `ResetTimer` |
| Throughput | `SetBytes` |
| Concurrency | `RunParallel` (later) |
| Toolchain 1.22 | only `b.N` |

## Trade-offs

| | Longer `-benchtime` / larger `-count` | Short single run |
|--|-----------------------------------|------------------|
| Stability | better | noise |
| CI time | longer | shorter |
| Signal | clearer | rough |

## Common mistakes

1. **Measuring setup** without `ResetTimer`.
2. **One run** as truth.
3. **No sink** — falsely “fast.”
4. **`-race` enabled** in a perf comparison.
5. **Forcing `b.Loop`** on Go 1.22.
6. **Bench instead of Test** for correctness.
7. **Overly large parallel** without a hypothesis.
8. **Comparing** laptop vs CI without context.
9. **Ignoring** allocs when the budget is memory.
10. **Undocumented input** (which size?).

## Idiomatic Go

- `b.N` loop; clear name `BenchmarkXxx`.
- `ReportAllocs` when you talk about GC.
- Sub-benchmarks by size / case.
- Budget comment from 11.13.
- Read stdlib bench style (`strings`, `bytes`).

## Practical scenario

A “faster cache” PR shows −40% ns/op. The reviewer asks for `-benchmem`: allocs/op **×3**. GC on production worsens. PR returned — the budget was allocs, not only ns. `ReportAllocs` saved a bad merge.

## Check questions

1. **What is `b.N`?**  
   The iteration count the runner chooses; the loop measures work N times.

2. **Primary API on Go 1.22+?**  
   `for i := 0; i < b.N; i++`.

3. **When `b.Loop`?**  
   Go 1.24+ and team agreement — otherwise not.

4. **What is `ResetTimer` for?**  
   So setup does not enter measured time.

5. **How allocations?**  
   `-benchmem` and/or `b.ReportAllocs()`.

6. **Why a sink?**  
   Prevents elimination of “unused” work.

7. **Why `-count=5`?**  
   See variance, not one lucky run.

8. **Does a bench prove correctness?**  
   No — that is what `Test` functions do.

### Additional mechanism — loop driven by b.N

On Go **1.22+** the primary pattern is:

```go
func BenchmarkQuote(b *testing.B) {
	for i := 0; i < b.N; i++ {
		_, _ = Quote(200, "local")
	}
}
```

`b.N` is **not** your fixed 1000. The runner increases N until it gets a stable sample. `ns/op ≈ total_time / N`.

**Predict-then-answer:** why not write `for i := 0; i < 1000; i++`?

Answer: too short or too long; the runner calibrates N automatically.

### Note: b.Loop (Go 1.24+ only)

```go
for b.Loop() {
	_, _ = Quote(200, "local")
}
```

Use **only** if the team toolchain is >= 1.24. On the course and in CI on 1.22/1.23 **`b.N`** remains. Do not require `b.Loop` in a PR on older `go`.

### Example — ResetTimer

```go
func BenchmarkHashBig(b *testing.B) {
	data := make([]byte, 1<<20)
	b.ResetTimer() // setup outside measure
	for i := 0; i < b.N; i++ {
		_ = Hash(data)
	}
}
```

#### What happens here

Without ResetTimer, allocating 1MiB enters ns/op — a false number.

### Example — ReportAllocs and -benchmem

```go
func BenchmarkEncode(b *testing.B) {
	b.ReportAllocs()
	b.ResetTimer()
	for i := 0; i < b.N; i++ {
		_, _ = json.Marshal(payload)
	}
}
```

```bash
go test -bench=BenchmarkEncode -benchmem -count=5 ./codec/
```

#### What happens here

You see `B/op` and `allocs/op`. A “<= 2 allocs” budget becomes checkable.

### Example — sink against dead-code elimination

```go
var sink int
for i := 0; i < b.N; i++ {
	sink, _ = Quote(200, "local")
}
_ = sink
```

#### What happens here

The compiler must not “eat” the loop because the result is used.

### Predict-then-answer — is one run enough to merge?

Answer: no. Use `-count=5` (or more) and watch the range, not one lucky number.

### Predict-then-answer — -race enabled in a perf comparison

Answer: the race detector slows things down — do not compare ns/op with and without -race as the same measure.

### StopTimer / StartTimer — continued

For rare per-iter setup. Prefer setup before the loop + ResetTimer (Stop/Start have overhead).

### More on b.N discipline

Measurement checklist:

1. Loop `i < b.N` (not a manual 1000).
2. Setup outside measure (`ResetTimer`).
3. Result sink.
4. `-benchmem` if memory is the topic.
5. `-count>=5` for variance.
6. `b.Loop` only with Go 1.24+.

**Predict-then-answer:** bench passes locally −30%, CI +5%. Merge based on the laptop?

Answer: no — same runner, count, go version; document conditions.

## Summary

`BenchmarkXxx` measures work in a loop driven by `b.N` — that is the primary model on Go 1.22+. `ResetTimer` / `StopTimer` clean setup; `ReportAllocs` and `-benchmem` reveal memory cost. `b.Loop` exists from Go 1.24 as a newer API — mention it, do not force it until the toolchain catches up. Read variance, not one lucky run.
