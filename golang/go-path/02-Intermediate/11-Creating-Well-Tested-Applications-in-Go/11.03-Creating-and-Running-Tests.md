# 11.03 Creating and running tests: go test, cache, and filters

> **Go Path - Zero to Gopher** / **02 Intermediate → Creating Well-Tested Applications in Go** / Lesson 11.03

## Lesson goals

After this lesson you can:

- create `*_test.go` files and run them with the `go test` command;
- use `-run`, `-count`, `-v` and understand the **test cache**;
- know when the cache helps, and when it hides flaky behavior;
- run tests by package, by path, and recursively (`./...`);
- predict what a `-run` regexp matches (including subtests);
- fit the local workflow with what CI should do.

## Prerequisite

- Lessons 11.01–11.02.
- A module with `go.mod`; you can `go build` / `go run`.
- Understanding of packages and paths in a module.

## Problem this lesson solves

People write `TestFoo`, then:

- run the wrong directory and think “there are no tests”;
- do not know why a second run “passes immediately” (cache);
- cannot isolate one failing test in a large suite;
- get surprised in CI because locally they did not use the same flags;
- write `-run Test` and wonder why it takes “everything” — because the regexp `Test` matches almost all names.

This lesson is the **operational layer**: how the toolchain sees and executes your tests.

## Mental model

`go test` is a **compiler + runner + cache**.

1. It finds packages (the paths you give it).
2. It compiles the package **together** with `*_test.go` (or as an external test package — 11.06).
3. It runs the test binary or results from the **cache** if inputs are unchanged.
4. It prints a summary; with `-v` also individual tests.

The cache is not magic “skip your code forever” — it caches a **successful** result for the same set of inputs (sources, env relevant to the test, flags…). Changing code or `-count=1` changes the equation.

```text
go test ./pkg/pricing
        │
        ├─ resolve packages
        ├─ compile pricing + *_test.go → test binary
        ├─ cache hit? → print (cached) ok
        └─ cache miss → run tests → store success
```

## Mechanism

### Files

- Name: `foo_test.go` next to `foo.go`.
- `package` same name → white-box (sees unexported).
- `package foo_test` → black-box (11.06).
- Build tags can exclude slower suites.
- A file without the `_test.go` suffix is **not** a test source even if it contains `TestFoo`.

### Basic commands

```bash
go test                  # package in the current dir
go test ./...            # all packages below
go test ./pkg/pricing    # one package
go test -v ./pkg/pricing
go test -c               # compile the test binary, do not run
```

### -run

Regexp over the test name (and subtest):

```bash
go test -run TestQuote ./...
go test -run 'TestQuote/(local|eu)' -v
go test -run 'TestQuote$'  # exactly TestQuote, not TestQuoteExtra
```

For table-driven subtests (`t.Run`) the name is `TestFoo/case_name`.

### Predict, then check: what does -run match?

Suite:

```text
TestAdd
TestAdditional
TestAdd/positive
TestSum
```

Command: `go test -run TestAdd`

**Predict:** what all goes in?

**Answer:** `TestAdd`, `TestAdditional`, and subtest `TestAdd/positive` — because `-run` is a **regexp**, and `TestAdd` is a prefix/substring pattern that also matches `TestAdditional` (`TestAdd` matches the start of `TestAdditional`).

For only `TestAdd` and its subtests you often need:

```bash
go test -run '^TestAdd$'          # only TestAdd (without subtests? actually parent)
go test -run '^TestAdd$' -v
go test -run '^TestAdd(/|$)' -v   # TestAdd and TestAdd/...
```

Exact behavior: `-run` filters the list of tests; subtests are filtered further. Practice with `-v` until you get a feel — do not memorize “magic” strings blindly.

### Trace: one failure, narrowing

```text
1. go test ./...
   --- FAIL: TestQuote/eu (0.00s)
2. go test -run 'TestQuote/eu' -v ./pkg/ship
3. fix the code
4. go test -count=1 -run 'TestQuote' -v ./pkg/ship
5. go test ./...
```

Step 2 saves time. Step 4 with `-count=1` avoids a false feeling from the cache while you debug.

### -count

```bash
go test -count=1 ./...     # bypass cache; always execute
go test -count=10 -run Flaky
```

`-count=1` is common in CI and local flaky-test debugging: it forces re-execution.

`-count=N` runs each test N times (useful for flaky hunting).

### -v

Verbose: prints `=== RUN`, logs from `t.Log`, pass lines. Without `-v`, passing tests are quiet (except when a package fails — then you see fail details).

### Cache

- Successful tests can be cached.
- A fail is not “cached” as green.
- `go clean -testcache` clears the test cache.
- A change in a dependent package invalidates.
- Some flags and environment variables affect the cache key.

### Predict, then check: why does the second run take 0.00s?

```text
$ go test ./pkg/pricing
ok   example.com/app/pkg/pricing  0.15s

$ go test ./pkg/pricing
ok   example.com/app/pkg/pricing  (cached)
```

**Predict:** was the code really executed again?

**Answer:** No. Cache hit. If you suspect flaky behavior or a test that reads an external file outside cache inputs, use `-count=1` or `go clean -testcache`.

### Trace: cache and flaky

```text
1. Test sometimes fails because it shares a tmp file
2. First run PASS → written to cache
3. next 9 local runs: (cached) — flaky is NOT seen
4. CI with -count=1 or a clean agent: FAIL
5. “Works on my machine”
```

That is why CI often forces `-count=1` or a clean environment. Locally, when hunting flaky: `-count=20 -run TestName`.

### Other useful flags (operational minimum)

| Flag | Role |
|-----------|--------|
| `-timeout 30s` | kills a stuck test |
| `-failfast` | stop on the first fail |
| `-list .` | list tests without running (with `-run`) |
| `-short` | signal to tests to skip slow parts |
| `-parallel N` | max parallel tests |

Details of `-race`, `-cover`, `-shuffle` come in 11.11+ and in the CLI playbook (15.09). Already now: local `go test ./...` should be a **subset** of the CI command.

### testing.Short

```go
if testing.Short() {
	t.Skip("db integration")
}
```

Running: `go test -short ./...` — Skip activates. Without `-short`, the test continues.

### Skip vs Fatal

- `t.Skip` — the test is not a fail; deliberately skipped (no env, `-short`).
- `t.Fatal` — fail.
- Do not abuse Skip to hide a broken test.

## Rules and syntax

```go
// file: mathx/clamp_test.go
package mathx

import "testing"

func TestClamp(t *testing.T) {
	if Clamp(5, 0, 3) != 3 {
		t.Fatalf("Clamp(5,0,3)=%d, want 3", Clamp(5, 0, 3))
	}
}
```

```bash
# from the module root
go test ./mathx
go test -v -run TestClamp ./mathx
go test -count=1 ./mathx
```

Rules:

1. Run from the module or give the package path — not a “random” folder outside `go.mod`.
2. `./...` does not enter `vendor` in a confusing way — know what your module contains.
3. For debug always think: do I need `-count=1`?
4. Narrow `-run` until you isolate the fail.
5. In CI document the exact command in README/CI yaml.

Go 1.22+: same cache and `-run` model; these habits are not broken.

## Examples

### Example 1 — From zero to green

```bash
mkdir -p mathx
cd mathx
# assume go.mod in the parent
```

`mathx/add.go`:

```go
package mathx

func Add(a, b int) int { return a + b }
```

`mathx/add_test.go`:

```go
package mathx

import "testing"

func TestAdd(t *testing.T) {
	if Add(1, 2) != 3 {
		t.Fatal("1+2 should be 3")
	}
}
```

```bash
go test ./mathx
# ok      example.com/.../mathx  0.XXXs
```

#### What happens here

The toolchain found `TestAdd`, compiled, ran, cached success.

### Example 2 — Filtering subtests

```go
func TestAdd(t *testing.T) {
	cases := []struct{ name string; a, b, want int }{
		{"pos", 1, 2, 3},
		{"neg", -1, -2, -3},
	}
	for _, tc := range cases {
		t.Run(tc.name, func(t *testing.T) {
			if Add(tc.a, tc.b) != tc.want {
				t.Fatalf("got %d want %d", Add(tc.a, tc.b), tc.want)
			}
		})
	}
}
```

```bash
go test -v -run 'TestAdd/neg' ./mathx
```

#### What happens here

Only the `neg` subtest. The report shows `TestAdd/neg`. This is the bread-and-butter debug ritual.

### Example 3 — List without executing

```bash
go test -list '.*' ./mathx
```

#### What happens here

You see the names the runner knows. Useful when you suspect `Testadd` is not registered.

### Example 4 -count and flaky

```bash
go test -count=50 -run TestConcurrentCache ./...
```

#### What happens here

If it fails on the 17th repetition, you have a reproduction. With cache without `-count`, you might never see the fail locally.

### Example 5 — Predict cached

```text
$ go test -run TestAdd ./mathx
ok  (cached)
$ # change only a comment in add.go
$ go test -run TestAdd ./mathx
```

**Predict:** cached or a real run?

**Answer:** Real run — the package source changed, the cache key no longer applies. (Changing *only* an unused file outside the package may stay cached — that is why you understand package boundaries.)

### Example 6 — Skip in short mode

```go
func TestIntegration(t *testing.T) {
	if testing.Short() {
		t.Skip("skip integration in -short")
	}
	// slow check
}
```

```bash
go test -short ./...   # Skip
go test ./...          # executes
```

#### What happens here

Same suite, two budgets. The laptop uses `-short`; the nightly job does not.

## Decision analysis

| Decision | Motive |
|--------|--------|
| `-run` for debug | Fast loop |
| `-count=1` in CI / flaky hunt | Bypass false cache feeling |
| `./...` on PR | Do not forget a package |
| `-v` only when needed | Less noise |
| `-short` locally | Speed without deleting integrations |
| Documented CI command | No “works on my machine” |

## Trade-offs

- **Cache** — fast feedback; hides flaky and some external dependencies.
- **Wide `-run Test`** — convenient, but runs too much; learn more precise regexp.
- **`-failfast`** — faster signal, less total diagnosis per run.
- **One monolithic test package** — slower feedback when `./...` pulls everything.
- **Test binaries on disk (`-c`)** — useful for special runners; do not commit without agreement.

## Common mistakes

1. Running `go test` from the wrong directory — “no tests”.
2. Trusting a cached green while hunting flaky.
3. `-run Test` that unintentionally runs half the suite.
4. Committing a local `*.test` binary.
5. Skip instead of a fix.
6. Different command locally and in CI.
7. Forgotten `./...` so CI does not see a new package.
8. Timeout too short for a slow integration suite.
9. Mixing `go run` and `go test` in your head — different inputs.
10. Expecting the cache to respect manually changed files *outside* the package/module graph.

## Idiomatic Go

- Locally: `go test ./...` often; `-count=1` when you suspect.
- Debug: `-v -run 'Name'`.
- CI: explicit flags in yaml, not “whatever the developer types”.
- Subtest names without spaces (or quote the regexp carefully).
- Keep tests fast so cache and the loop stay pleasant.

## Practical scenario

Developer: “tests are green”. CI red. Cause: locally cached PASS after a flaky race; CI agent clean + `-count=1`. The team introduces in the Makefile:

```make
test:
	go test -count=1 ./...
```

and the same command in the PR check. “Works on my machine” disappears in a week. Another win: `-run` culture — review asks that a bugfix PR show a reproduction with one `-run` string in the description.

## Exercises

1. Make a package with two `Test` and run only one via `-run`.
2. Deliberately break a test, fix it, watch cached on the next run.
3. Do `go clean -testcache` and compare time.
4. Add `t.Run` subtests and isolate one with `-run 'TestX/y'`.
5. Run `go test -list .` and find a function that is not listed because of the name.
6. Write an integration test with `testing.Short` skip; compare `-short` vs without.
7. Predict what `-run 'Add'` does over `TestAdd` and `TestAdditional`, then check with `-v`.
8. Run `-count=10` on a fast test and read the output.

## Check questions

1. **What does `go test ./...` do?**  
   Runs tests in all packages under the current path in the module.

2. **What is `-count=1` for?**  
   Forces execution and avoids a test cache hit.

3. **What is `-run`?**  
   A regexp filter over test/subtest names.

4. **Does a fail go into the cache as green?**  
   No. Success is cached.

5. **Predict:** `-run TestAdd` and `TestAdditional` exists — does the second run?  
   Yes, typically — the regexp matches a prefix/substring; narrow the pattern if needed.

6. **When `t.Skip`?**  
   When a prerequisite is missing (`-short`, no DSN) — not when the test is broken.

7. **Why should CI and laptop use a similar command?**  
   So you do not debug environment differences instead of code.

## Deeper mechanism: what enters the cache key

Simplified: the cache remembers success for a combination of:

```text
- package and test source files
- relevant build/test flags
- certain env variables the toolchain tracks
- compiler version / GOOS/GOARCH where they matter
```

What often is **not** in the key the way you expect:

- a manual change to a file the package does not import;
- an external service on the network (hence flaky + cache = false calm);
- database contents on localhost.

Therefore: a test that reads a “live” external world must be careful with the cache — either `-count=1`, or do not cache such a suite in CI.

### Trace: package boundaries and cached

```text
pkg/a  changes
pkg/b  is tested, imports a
→ go test ./pkg/b  will not be stale cached relative to a

pkg/c  does not depend on a
→ go test ./pkg/c  may stay cached
```

Understand the import graph. `./...` invalidates per package, not “the whole repo always”.

### Predict, then check: more -run puzzles

Suite names:

```text
TestParse
TestParseJSON
TestParse/empty
TestPrepare
ExampleParse
```

| Command | Predict set |
|---------|----------------|
| `-run Parse` | |
| `-run '^TestParse$'` | |
| `-run Example` | |
| `-run 'TestParse/'` | |

**Answers (typical regexp filter behavior):**

- `Parse` — matches `TestParse`, `TestParseJSON`, `TestParse/empty`, `TestPrepare`? `TestPrepare` contains `Pre`+`pare` not `Parse` — **no**. `ExampleParse` — yes if Examples are filtered by the same `-run` (yes, `-run` applies to Example when they run).
- `^TestParse$` — only exact `TestParse` (parent); subtests depend on whether the parent enters and how further filtering works — practically use `-v` to confirm.
- `Example` — Example functions.
- `TestParse/` — subtests whose full path has that pattern.

If it is unclear — **that is the point of the exercise**: run `-v` and watch `=== RUN` lines. Do not memorize false certainty.

### Operational checklist for a PR

```text
[ ] go test ./...  (or make test)
[ ] if fail: -run narrow, -v read
[ ] if “cached confuses”: -count=1
[ ] if flaky: -count=20 -run Name
[ ] if slow locally: -short
[ ] same command as documented CI
```

### What CI usually adds (preview)

Lesson 15.09 goes deeper: `-race`, `-cover`, `-shuffle`, `-timeout`. Already remember: local `go test ./...` should be a **subset** of the CI command, not a completely different world. If you never run the race detector locally, do not be surprised when CI fails on it after the merge window.

### Additional mechanism — go test as compiler, runner, and cache

`go test` is not just “run functions”. It selects packages, compiles with `*_test.go`, runs, and can **return a cached success**.

#### Trace of local debug

```bash
go test ./internal/billing/ -run '^TestQuote$' -v -count=1
```

**Predict-then-answer:** why `-count=1`?

Answer: so the result does not come from the test cache when you debug flaky / a suspicious cache.

### Example — -run regexp

```bash
go test -run TestParse           # almost everything that contains TestParse
go test -run '^TestParse$'       # exactly that name
go test -run 'TestParse/(empty|bom)'  # subtests
```

#### What happens here

`-run` is a regexp over the full name path, including `t.Run` segments. `Test` alone runs almost the whole suite.

### Example — cache lies

You change a file the test reads from disk **outside** the package. The cache may stay green.

Mitigations:

- `-count=1` in CI;
- input in the package `testdata`;
- document dependencies.

### Flag table

| Flag | Purpose |
|-----------|--------|
| `-v` | verbose, Run log |
| `-run` | filter (regexp) |
| `-count=1` | no cache / forced run |
| `-count=N` | hunt flaky |
| `-timeout` | kill stuck ones |
| `-race` | data race (slower) |
| `-list` | names without executing |
| `./...` | all packages below |

### Predict-then-answer — wrong cwd

You run `go test` in an empty dir. What do you see?

Answer: no packages / no test files — it is not that “there are no tests in the project”.

### Predict-then-answer — CI != laptop

Locally green, CI red. Most common causes?

Answer: different Go version, `-race` only in CI, `-count=1` in CI, OS paths, skip env.

### Example — list

```bash
go test -list . ./parse/
```

#### What happens here

You see `Test` / `Benchmark` / `Fuzz` / `Example` names before you spend time on a run.

### CI checklist (lesson topic)

1. Same major Go version.
2. `-count=1` (or equivalent) so the cache does not hide.
3. Documented `./...` scope.
4. `-race` at least on critical packages.
5. Same filters locally when reproducing a CI fail.

### Scenario

A developer “fixes” flaky by running it once locally (cache hit). In CI with `-count=1` it still fails. Lesson: flaky is hunted with `-count=20`, not with a cached success.

1. `-run Test` and wonder why everything runs.
2. Debug with an active cache.
3. Wrong directory.
4. Locally without `-race`, CI with `-race`.
5. Unconscious `./...` vs one package.
6. Ignoring `-timeout` on a stuck test.

2. **How exactly one name?** `^TestFoo$`.

### Additional trace — regexp edges for -run

```bash
go test -run 'Test' ./pkg/          # too wide
go test -run '^TestFoo$' ./pkg/     # exact
go test -run 'Foo$' ./pkg/          # suffix
go test -run 'TestFoo/bar$' ./pkg/  # subtest bar
```

**Predict-then-answer:** does `-run Foo` run `TestFoo` and `TestFood`?

Answer: yes, if the regexp matches — that is why you use anchors `^`/`$` when you want precision.

### Cache invalidation — checklist

1. Change to a .go in the package -> invalidates.
2. Change to test flags -> invalidates.
3. External file outside the package -> success may stay cached.
4. Flaky -> -count=N, not one cached run.

### Example — reproducing a CI fail

```bash
go test ./internal/billing/ -race -count=1 -run '^TestQuote_EU$'
```

#### What happens here

Same flags as CI, one test, no cache.


### More on -run and the cache

When debugging a CI fail, copy the **same** flags: -race, -count=1, -run with anchors.

```bash
go test ./pkg/ -count=1 -run '^TestFoo$' -v
```

If locally you want to see whether it is flaky:

```bash
go test ./pkg/ -count=50 -run '^TestFoo$'
```

**Predict-then-answer:** does one green run prove it is not flaky?

Answer: no. Flaky is measured by repetition.

| Goal | Command |
|------|---------|
| One test | -run '^Name$' |
| Subtest | -run 'Parent/child' |
| No cache | -count=1 |
| List | -list . |
| Verbose | -v |


### One more thing about the cache

If you suspect the cache: -count=1. If you suspect flaky: -count=20. If you suspect the filter: -list then an exact -run with anchors.

## Summary

`go test` compiles, runs, and can cache successes. `-run` narrows, `-count` repeats or forces, `-v` reveals details. Align local habits with CI so cache and filters work for you, not against you. Next: how to design unit tests with isolation and fakes.
