# 11.11 Code coverage analysis: coverage is not correctness

> **Go Path - Zero to Gopher** / **02 Intermediate → Creating Well-Tested Applications in Go** / Lesson 11.11

## Lesson goals

- Understand what `go test -cover` **measures** (executed statements), and what it **does not prove** (correctness).
- Read the percentage and coverage map without false confidence.
- Distinguish “touched” from “asserted.”
- Use coverage to find **gaps** and coverage regressions, not as the only quality KPI.
- Know typical traps: empty tests, generated code, `main`, error branches.
- Connect coverage to a review protocol (what to ask for in a PR).
- Prepare the ground for generating reports in 11.12.

## Prerequisite

- Lessons 11.04–11.10 (unit, table, HTTP tests).
- Running `go test ./...`.
- Basic idea of branches (`if`, `switch`, early return).

## Problem this lesson solves

A team sees **92% coverage** on a dashboard and concludes “we are almost done with quality.” Meanwhile:

- a test calls a function and **has no assert**;
- an error branch exists but returns the wrong type — and is still “covered”;
- a critical `else` is never hit, but the average % looks fine because of trivial getters.

Coverage answers: **“Which lines / statements did the test binary execute?”**  
It does not answer: **“Is the behavior correct?”**

This lesson builds a mental model that prevents % from replacing thinking.

## Mental model

```text
        Coverage map              Good test
   ┌─────────────────────┐    ┌──────────────────────┐
   │ green = visited     │    │ arrange → act →      │
   │ red = not           │    │ assert CLAIM         │
   └─────────────────────┘    └──────────────────────┘
            │                            │
            └──────────┬─────────────────┘
                       ▼
              Confidence only when BOTH
              exist for that branch
```

Analogy: coverage is a **walking map of a building**. It says which rooms you walked through. It does not say you checked whether the safe is locked.

| Signal | What it means | What it does not mean |
|--------|-----------|--------------|
| High % | Much code ran in the test | The code is correct |
| Low % | Much code was not touched | Necessarily a bad product |
| Green line | Visit | An assert exists |
| Red line | Not executed | Must test immediately (sometimes not — e.g. `main`) |

## Mechanism

### How Go measures (conceptually)

On `go test -cover` the tool instruments the package: it counts executions of blocks / statements. At the end it prints a percentage for the package.

```bash
go test -cover ./...
```

Example output (illustration):

```text
ok   example.com/app/ship   0.012s  coverage: 78.3% of statements
```

Detailed flags and the HTML map — **11.12**. Here **interpretation** matters.

### Statement coverage vs your claim

```go
func Abs(n int) int {
	if n < 0 {
		return -n
	}
	return n
}
```

```go
func TestAbs_Touched(t *testing.T) {
	_ = Abs(-3) // no assert
}
```

**Predict-then-answer:** does this test raise coverage for `return -n`?

Answer: **yes**, the branch ran. Does it prove the result is `3`? **No.** Coverage is green; a bug `return n` instead of `-n` in the negative branch can still pass if there is no assert — or if the assert wrongly expects the wrong value.

Better:

```go
func TestAbs(t *testing.T) {
	if Abs(-3) != 3 {
		t.Fatalf("Abs(-3)=%d", Abs(-3))
	}
	if Abs(2) != 2 {
		t.Fatalf("Abs(2)=%d", Abs(2))
	}
}
```

Now both coverage and the claim cover both branches.

### False confidence: “a test that only calls”

```go
func TestAll(t *testing.T) {
	Handle(httptest.NewRecorder(), httptest.NewRequest("GET", "/", nil))
	Parse("")
	Parse("x")
	Parse("999999999999999999999")
}
```

High % is possible; zero proof. A reviewer looks at **`t.Run` names and asserts**, not only %.

### Error branches — often red

```go
v, err := strconv.Atoi(s)
if err != nil {
	return 0, fmt.Errorf("id: %w", err)
}
```

Happy-path tests leave `err != nil` red. Those branches often hide a wrong status code or message. The coverage map **helps** here: look for red `if err`.

### What to leave low on purpose

| Region | Why % may be low | Action |
|--------|-------------------------|--------|
| `main` / wiring | hard without integration | thin smoke or exclude from threshold |
| generated code | noise | `-coverpkg` / ignore agreement |
| `panic("TODO")` branches | dead | delete or test |
| platform files | CI OS | build tags |

### Coverage regression

Useful KPI use: **do not allow new code in a PR without a test** (delta coverage), instead of a religion of “globally 95%.”

Ask: *Which `t.Run` owns this new `if` branch?*

### Predict-then-answer: 100% ⇒ no bugs?

Answer: **no**. Coverage does not prove:

- correct business formulas;
- concurrency;
- performance (11.13+);
- security properties;
- API compatibility with clients.

Fuzz (11.15) and bench/profile (11.16–11.17) measure **other axes**.

### Link to table-driven tests

A table with named cases makes the map meaningful: red branch ↔ “which case is missing.” Without names, % is a number without a story.

### Mini-protocol for a PR (10 minutes)

1. Open the map only for touched files (how — 11.12).
2. For every new `if` / `switch` / early `return`: find a test.
3. Reject a “touch” without an assert.
4. Record deliberate gaps (e.g. `main`) in the PR description.

This protocol is worth more than raising the global threshold by 2%.

### Trace of a false green

```text
new bug in else branch
    → tests still call only if branches
    → coverage 91% → 91% (unchanged)
    → CI green
    → production red
```

Coverage is **not** an alarm for a wrong result on an already visited line. The alarm is an **assert**.

### When to take % seriously anyway

- A sudden % drop on a touched package in a PR.
- A new file at 0% while it holds business logic.
- Error paths permanently red on a critical package.

## Rules and syntax

```bash
go test -cover ./ship/
go test -cover ./...
```

Interpretation rules:

1. % is the start of an investigation, not a seal.
2. Green ≠ assert.
3. Look for red error branches.
4. Do not force 100% religiously.
5. Delta on new code > absolute number for the whole monorepo.
6. Separate coverage from CPU profiles and fuzz corpora.
7. Document deliberate exceptions.

Go 1.22+ keeps the same basic `-cover` contract; report details in 11.12.

## Examples

### Example 1 — High cover, wrong result

```go
func Discount(cents int, vip bool) int {
	if vip {
		return cents / 2 // bug: should be /10 for 10%? business — example
	}
	return cents
}

func TestDiscount_TouchesVIP(t *testing.T) {
	_ = Discount(1000, true)
	_ = Discount(1000, false)
}
```

#### What happens here

Coverage can be 100%. The business bug lives. Add an assert:

```go
if Discount(1000, true) != 900 { /* desired contract */ }
```

### Example 2 — Red error branch

```go
func ParsePort(s string) (int, error) {
	n, err := strconv.Atoi(s)
	if err != nil {
		return 0, err
	}
	if n < 1 || n > 65535 {
		return 0, fmt.Errorf("range")
	}
	return n, nil
}
```

```go
func TestParsePort_OK(t *testing.T) {
	n, err := ParsePort("8080")
	if err != nil || n != 8080 {
		t.Fatalf("%d %v", n, err)
	}
}
```

#### What happens here

The map shows red on `err != nil` and the range `if`. Add cases `"x"` and `"99999"`. Coverage rises **and** claims exist.

### Example 3 — Getter noise

```go
func (u User) ID() string { return u.id }
```

#### What happens here

Testing every getter raises % without value. Better cover through a scenario that uses `ID()` meaningfully. Do not agonize over 2 red getter lines.

### Example 4 — Review dialog

Author: “Cover 94%.”  
Reviewer: “Which test proves the new `if err` in `Checkout`?”  
Author: “…none, but the line is green because I called the function in a helper.”  
Reviewer: “Add `t.Run(\"stock_error\")` with an assert on the error type.”

#### What happens here

Culture: % is an introduction, not a conclusion.

### Example 5 — main wiring

```go
func main() {
	cfg := Load()
	http.ListenAndServe(cfg.Addr, routes())
}
```

#### What happens here

Often 0% on `main`. Options: extract `run(cfg) error` and test; or smoke; or exclude from the threshold. Do not fake 100% by force.

### Example 6 — Table as a map legend

```go
func TestAbs_Table(t *testing.T) {
	tests := []struct {
		name string
		in   int
		want int
	}{
		{name: "neg", in: -2, want: 2},
		{name: "pos", in: 2, want: 2},
		{name: "zero", in: 0, want: 0},
	}
	for _, tc := range tests {
		t.Run(tc.name, func(t *testing.T) {
			if Abs(tc.in) != tc.want {
				t.Fatalf("got %d", Abs(tc.in))
			}
		})
	}
}
```

#### What happens here

Every branch has a name. When the map shows a gap, you know which `t.Run` is missing.

## Decision analysis

| Goal | Use coverage? | Additionally |
|------|-------------------|---------|
| Find untested branches | yes | read the map |
| Prove correctness | not alone | assert / oracle |
| Gate on PR | carefully (delta) | branch checklist |
| Marketing badge | weak | easy to abuse |
| Perf / race | no | bench, race detector |

## Trade-offs

| | High % threshold | Low / no threshold |
|--|--------------|---------------------|
| Pressure to write tests | yes | lower |
| Risk of empty tests | rises | — |
| Focus on critical packages | can be lost | can be kept deliberately |
| Maintenance cost | higher | lower |

Healthy trade-off: **moderate threshold + mandatory map reading for touched code + zero tolerance for tests without asserts**.

## Common mistakes

1. **% as the definition of quality.**
2. **Tests without asserts** for cover.
3. **Ignoring error branches** because the happy path raises the average.
4. **Forcing 100%** including `main` and generated.
5. **Mixing** cover profiles with CPU profiles.
6. **Only a global number** without a map of touched files.
7. **Not asking “which t.Run?”** in review.
8. **Forgetting** that a refactor can drop % without losing quality (longer dead code deleted).
9. **Covering** panics and unreachable branches senselessly.
10. **Concluding** from one package at 0% that the tool is broken — maybe there are no tests (`?` in the output).

## Idiomatic Go

- `go test -cover` locally before a PR.
- Table-driven names ↔ branches.
- Critical packages (`billing`, `auth`) stricter than `cmd/`.
- Document exceptions in CONTRIBUTING.
- Next tool step: 11.12 (`-coverprofile`, HTML).

## Practical scenario

A fintech service requires “90% coverage” to merge. The team adds `TestAllHelpers` that calls everything without asserts. Badge green. A bug in interest rounding ships to production — the line was green.

After the incident the policy:

1. Ban on tests without asserts (lint / review).
2. Coverage map mandatory for the `interest` package.
3. Threshold stays 90%, but with a branch checklist.

`go test -cover` answers: **which statements did the test binary execute?** It does not answer: **is the result correct?**

### Additional trace — coverage and review questions

For every new branch in a PR:

1. Which t.Run owns it?
2. Which assert proves the outcome (not only a call)?
3. Is the error path covered?

If the answer to 2 is missing, % is irrelevant.

### Table: signal vs action

| Signal | Action |
|--------|--------|
| High % without asserts | reject |
| Red if err | add a case |
| New file 0% | test or exclude |
| % drop after deleting dead code | OK |

### Predict-then-answer — refactor lowers %

Answer: maybe you deleted dead code; % is not a moral score.


### More on interpreting %

Ask for every PR:

| Question | Good answer |
|---------|---------------|
| Which new branch? | if/return X |
| Which test? | TestFoo/bar |
| Which assert? | got==want / errors.Is |
| Deliberate gap? | main / generated |

If the assert is missing, coverage is decoration.

**Predict-then-answer:** coverage jumps 5% after adding TestTouch. Progress?

Answer: not necessarily — without a claim that is only a visit.


### Extension — coverage as a map, not a seal

Three lies:

1. High % = quality
2. Green line = assert
3. 100% = no bugs

Three truths:

1. % shows visit
2. Assert proves a claim
3. The map leads to gaps (especially err)

## Summary

Coverage shows what ran, not what was proven. A high percentage without asserts and without reading the map gives false confidence. Use it to find gaps and coverage regressions, and build quality with tests that force a branch and check the outcome — especially errors and business edges.
