# 11.15 Fuzz testing: `FuzzXxx`, seed, and corpus

> **Go Path - Zero to Gopher** / **02 Intermediate → Creating Well-Tested Applications in Go** / Lesson 11.15

## Lesson goals

- Write `FuzzXxx(f *testing.F)` functions in Go’s native fuzzing.
- Add seed inputs with `f.Add`.
- Write an `f.Fuzz` callback with an **oracle** (what is correct / not allowed).
- Run a short campaign with `-fuzz` and `-fuzztime`.
- Understand a **failing corpus** in `testdata/fuzz/...` as a regression.
- Know what fuzz **is not** (not a replacement for table-driven; not an exploit toolkit).
- Fit fuzz into CI: seed on PR, longer campaign overnight.

## Prerequisite

- Lessons 11.04–11.05 (unit, tables).
- Go **1.22+** with built-in fuzz support (`go test -fuzz`).
- Understanding that a test must have a **claim** (oracle), not only “no panic.”

## Problem this lesson solves

Table-driven tests cover inputs you **imagine**. Production sends inputs you did not imagine: empty bytes, huge strings, odd Unicode, invalid JSON shape.

Fuzz automatically **mutates** inputs and looks for a crash / oracle fail. When it finds a problematic input, Go saves it in the corpus so it **never disappears** from `go test` again.

This lesson teaches defensive quality engineering — **without** framing for system abuse.

## Mental model

```text
f.Add(seed…)          initial examples
        │
        ▼
f.Fuzz(func(...))     oracle over every input
        │
        ├─ pass → mutate further (−fuzz campaign)
        └─ fail → write to testdata/fuzz/FuzzXxx/
                 and fail in ordinary go test
```

| Part | Role |
|-----|--------|
| Seed (`f.Add`) | Smart start; documented cases |
| Oracle | What may / may not happen |
| Corpus | Regression inputs (binary files) |
| `-fuzz` | Active mutation campaign |
| Ordinary `go test` | Seed + saved corpus, without a long campaign |

## Mechanism

### Signature

```go
func FuzzParse(f *testing.F) {
	f.Add("42")
	f.Add("-1")
	f.Fuzz(func(t *testing.T, s string) {
		_, err := Parse(s)
		if err != nil {
			return // expected for many strings
		}
		// oracle for a successful parse...
	})
}
```

- Name: `Fuzz` + suffix.
- `f *testing.F` outside; inside `t *testing.T` in the callback.
- Argument types in the `Fuzz` callback must be supported (e.g. `[]byte`, `string`, `int`, …).

### f.Add — seed

```go
f.Add([]byte{0x00, 0xff})
f.Add("привет") // Unicode seed OK
```

Seeds also run in ordinary `go test` (without `-fuzz`). Those are your “always check this” inputs.

### Oracle — the core of value

Bad oracle:

```go
f.Fuzz(func(t *testing.T, data []byte) {
	Decode(data) // only “no panic” — weak, but sometimes a start
})
```

Better oracle (round-trip):

```go
f.Fuzz(func(t *testing.T, data []byte) {
	v, err := Decode(data)
	if err != nil {
		return
	}
	out, err := Encode(v)
	if err != nil {
		t.Fatalf("encode: %v", err)
	}
	v2, err := Decode(out)
	if err != nil || !equal(v, v2) {
		t.Fatalf("roundtrip mismatch")
	}
})
```

**Predict-then-answer:** fuzz finds an input where `Decode` does not panic but breaks a range invariant. What catches it — panic or oracle?

Answer: **oracle** (`t.Fatalf`). Without an oracle, the bug lives.

### Running

```bash
# seed + corpus (CI PR)
go test ./parse/ -run FuzzParse

# campaign
go test ./parse/ -fuzz=FuzzParse -fuzztime=30s
```

`-fuzz` takes a regex. `-fuzztime` limits duration.

### Failing corpus

When fuzz fails, Go writes the input under e.g.:

```text
testdata/fuzz/FuzzParse/<hash>
```

Ordinary `go test` then **re-runs** that input. Commit it with the fix — that is a regression test.

Do not delete the corpus “because it bothers” without a fix — you lose the signal.

### Commit policy

| Job | What it does |
|-----|----------|
| PR | `go test ./...` (seed + corpus, without a long campaign) |
| Overnight | `go test -fuzz=Fuzz... -fuzztime=20m` on critical packages |
| After a find | PR with fix + `testdata` file |

### What fuzz is not

- Not a replacement for clear table-driven cases with names.
- Not a load test.
- Not guidance for attacking other systems — the goal is for **your** parser/codec to be more robust.
- Not a guarantee of absence of bugs — it only searches the mutation space.

### Predict-then-answer: may Fuzz call the network?

Technically it can, but **not** in default CI. Fuzz needs a fast, local, deterministic code path. Stub dependencies.

### Link to coverage

Fuzz can increase branch visit, but % is not the goal. The goal is an oracle fail / crash. The coverage map (11.11–11.12) and fuzz are different axes.

## Rules and syntax

1. `func FuzzName(f *testing.F)`.
2. `f.Add` for seeds of supported types.
3. `f.Fuzz(func(t *testing.T, ...) { ... })` with an oracle.
4. Avoid nondeterminism and the network.
5. Commit a failing corpus with the fix.
6. PR: without a `-fuzz` campaign; overnight: with `-fuzztime`.
7. Keep `testdata/fuzz` in git.

```bash
go test -fuzz=FuzzParse -fuzztime=10s ./...
go test ./...   # corpus + seed
```

## Examples

### Example 1 — Basic string parse

```go
func ParseU32(s string) (uint32, error) {
	n, err := strconv.ParseUint(s, 10, 32)
	if err != nil {
		return 0, err
	}
	return uint32(n), nil
}

func FuzzParseU32(f *testing.F) {
	f.Add("0")
	f.Add("4294967295")
	f.Add("abc")
	f.Fuzz(func(t *testing.T, s string) {
		n, err := ParseU32(s)
		if err != nil {
			return
		}
		// oracle: successful parse ⇒ decimal form round-trip
		out := strconv.FormatUint(uint64(n), 10)
		n2, err2 := ParseU32(out)
		if err2 != nil || n2 != n {
			t.Fatalf("s=%q n=%d out=%q", s, n, out)
		}
	})
}
```

#### What happens here

Invalid strings are OK (err). Valid ones must round-trip. Fuzz looks for odd strings that pass parse but break the oracle.

### Example 2 — []byte decode

```go
func FuzzDecode(f *testing.F) {
	f.Add([]byte{})
	f.Add([]byte{0x00})
	f.Fuzz(func(t *testing.T, data []byte) {
		defer func() {
			if recover() != nil {
				t.Fatalf("panic on %q", data)
			}
		}()
		_, _ = Decode(data)
	})
}
```

#### What happens here

Minimal oracle: **no panic**. Useful for Cgo / parser start; improve to stricter invariants.

### Example 3 — Corpus as a named test

After a find, besides the binary corpus:

```go
func TestParseU32_RegressionOverflowText(t *testing.T) {
	_, err := ParseU32("999999999999999999999")
	if err == nil {
		t.Fatal("expected error")
	}
}
```

#### What happens here

The corpus keeps the raw input; the named test keeps the **story** for people. Both can live together.

### Example 4 — Two arguments

```go
func FuzzClip(f *testing.F) {
	f.Add(10, 0, 100)
	f.Fuzz(func(t *testing.T, v, lo, hi int) {
		if lo > hi {
			lo, hi = hi, lo
		}
		got := Clip(v, lo, hi)
		if got < lo || got > hi {
			t.Fatalf("got %d not in [%d,%d]", got, lo, hi)
		}
	})
}
```

#### What happens here

The oracle is a mathematical invariant — ideal for fuzz.

### Example 5 — CI separation

```bash
# pr.yml
go test ./...

# nightly.yml
go test ./codec/ -fuzz=Fuzz -fuzztime=20m
```

#### What happens here

PR stays fast. Overnight looks for bugs. A find → new PR with the corpus.

### Example 6 — Bad fuzz (network)

```go
// NOT in unit fuzz
f.Fuzz(func(t *testing.T, path string) {
	http.Get("https://example.com/" + path)
})
```

#### What happens here

Slow, flaky, side effects. Fuzz the path parser locally; HTTP stub separately (11.10).

## Decision analysis

| Goal | Fuzz | Table | Example |
|------|------|--------|---------|
| Known edge | seed / table | yes | — |
| Unknown input | yes | no | — |
| Docs | no | no | yes |
| Round-trip codec | excellent | partial | — |

## Trade-offs

| | More fuzz campaigns | Seed only |
|--|---------------------|-----------|
| Bug finds | higher | lower |
| CI CPU | higher | lower |
| Corpus maintenance | grows | little |

## Common mistakes

1. **Fuzz without an oracle** (only a call).
2. **Deleting testdata** instead of a fix.
3. **Long campaign on every PR.**
4. **Network / clock / random** in the callback.
5. **Replacing** all table tests with fuzz.
6. **Not understanding** that ordinary `go test` does not mutate aggressively.
7. **Overly broad** fuzz of the whole application instead of a parser.
8. **Ignoring** Unicode / encoding seeds.
9. **Mixing** with an exploit narrative — focus on your own code.
10. **Uncommitted** corpus only on one machine locally.

## Idiomatic Go

- Fuzz next to codec, parse, canonicalize.
- Seeds as documentation + start.
- `testdata/fuzz` in VCS.
- Overnight `-fuzztime` on critical packages.
- Read `testing` docs for supported types.

## Practical scenario

A billing parser fails in production on an empty string with a BOM. The table did not have that case. Overnight fuzz + oracle “err or valid number” finds the input in 2 minutes. Corpus + fix — the bug does not return.

## Check questions

1. **What does `f.Add` do?**  
   Adds a seed input that always runs.

2. **What is an oracle?**  
   A claim about what a correct outcome / invariant is.

3. **Where does a failing input go?**  
   Into the `testdata/fuzz/FuzzName/...` corpus.

4. **PR vs overnight?**  
   PR without a long campaign; overnight with `-fuzz` and `-fuzztime`.

5. **Does fuzz replace tables?**  
   No — it complements them.

6. **What does `go test` without `-fuzz` do?**  
   Seed + saved corpus, without aggressive mutation.

7. **Why round-trip?**  
   A strong, automatic oracle for a codec/parser.

8. **Lesson goal?**  
   Robustness of your own code, not attacking other systems.

### Additional mechanism — input types and limits

The fuzz callback takes a limited set of types (e.g. `string`, `[]byte`, `int`, `byte`, `rune`, `float64`, `bool`, and some combinations). If you need a struct, serialize to `[]byte` and decode inside — or fuzz fields separately.

**Predict-then-answer:** can you `f.Add(myStruct{})`?

Answer: not directly for an arbitrary struct — use supported types / `[]byte`.

### Example 7 — Minimization (conceptually)

When fuzz finds a fail, the runtime often tries to **shorten** the input (minimization) to keep the fail with a smaller example. That is why a corpus file sometimes looks “small” — that is an advantage for review.

### Example 8 — Seed that documents BOM

```go
f.Add("\ufeff123")
f.Add("123")
```

#### What happens here

If the parser must not accept BOM, the oracle / err branch proves it. Without a seed, it may never hit quickly.

### Example 9 — Separate Fuzz per invariant

```go
func FuzzDecodeNoPanic(...) { /* recover / no panic */ }
func FuzzDecodeRoundTrip(...) { /* encode/decode */ }
func FuzzDecodeRange(...) { /* fields in range */ }
```

#### What happens here

One huge oracle is hard to debug. More Fuzz functions = clearer fail.

### Example 10 — What to commit after an overnight find

1. Production fix.  
2. `testdata/fuzz/...` input.  
3. Optional named `Test..._Regression`.  
4. Short note in the PR: how the oracle catches it.

Without (1)+(2), the overnight run will fail again — or lose the signal.

### Anti-pattern: fuzz as “security theater”

A team enables `-fuzztime=5s` on every PR, zero oracles, zero corpus in git. Looks modern, does not catch bugs. Better: a strong oracle + overnight 20m on one package.

### Additional mechanism — FuzzXxx, seed, and corpus

Native fuzz: `FuzzXxx(f *testing.F)`, `f.Add` seeds, `f.Fuzz` callback with an **oracle**. A `-fuzz` campaign mutates; a failing input goes into `testdata/fuzz/...`.

#### Trace

```text
f.Add(seed) -> f.Fuzz(oracle)
                 |- pass -> mutate further (-fuzz)
                 |- fail -> testdata/fuzz/FuzzName/<hash>
                            + fail in ordinary go test
```

**Predict-then-answer:** go test without -fuzz — does it mutate aggressively?

Answer: no. It runs seed + saved corpus.

### Example — seed + round-trip oracle

```go
func FuzzParseU32(f *testing.F) {
	f.Add("0")
	f.Add("4294967295")
	f.Fuzz(func(t *testing.T, s string) {
		n, err := ParseU32(s)
		if err != nil {
			return
		}
		out := strconv.FormatUint(uint64(n), 10)
		n2, err2 := ParseU32(out)
		if err2 != nil || n2 != n {
			t.Fatalf("s=%q n=%d out=%q", s, n, out)
		}
	})
}
```

#### What happens here

Invalid strings OK (err). Valid ones must round-trip. The oracle gives value; “only no panic” is a weak start.

### Example — failing corpus

When fuzz fails, Go writes the input under `testdata/fuzz/FuzzParseU32/...`. **Commit** with the fix — that is a regression.

**Predict-then-answer:** delete the corpus so CI goes green?

Answer: no. Fix + keep the input.

## Summary

Native fuzz in Go ties `FuzzXxx`, `f.Add` seeds, and a `testdata` corpus to `go test`. A campaign with `-fuzz` searches for inputs; a strong oracle determines value. Commit a failing input as a regression. Fuzz complements table-driven tests — it does not replace budget, profile, or a clear specification.
