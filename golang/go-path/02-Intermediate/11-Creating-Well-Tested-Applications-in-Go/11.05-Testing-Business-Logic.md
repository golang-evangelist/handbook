# 11.05 Testing business logic: pure functions and table-driven rules

> **Go Path - Zero to Gopher** / **02 Intermediate → Creating Well-Tested Applications in Go** / Lesson 11.05

## Lesson goals

After this lesson you can:

- extract **business rules** into pure functions that are easy to test;
- write **table-driven** tests for edge cases, rounding, and validations;
- name cases so a test failure immediately says *which* rule broke;
- separate domain from HTTP/SQL so the suite stays fast;
- use `t.Run` with a table and filter one case via `-run`;
- recognize when a table becomes overcrowded and should be split.

## Prerequisite

- Lesson 11.04 (isolation, fakes).
- `struct`, `slice`, `error`, basic `switch`.
- `t.Run` and `-run` from 11.02/11.03.

## Problem this lesson solves

Business logic often lives “scattered”:

- discount in a handler;
- VAT in a SQL view;
- rounding in front-end JavaScript;
- a special if in a cron job.

When a financial bug arrives, nobody knows *where* the source of truth is. Handler tests check status 200, and the formula stays without a net. This lesson pushes rules into a **pure layer** and shows how table-driven tests become a living domain specification.

## Mental model

Think of the domain as a **calculator with a printed manual**.

- Manual = case table (input → output / error).
- Calculator = pure function without I/O.
- The handler only enters numbers and reads the result.

```text
HTTP / SQL / UI
       │
       ▼
  [ DTO → domain types ]
       │
       ▼
  pure functions / value objects   ← table-driven tests
       │
       ▼
  decisions (price, status, permission)
```

A table is not a “style trick” — it is a **specification that CI executes**. A new row = a new rule or edge case.

## Mechanism

### Pure function

1. Same input → same output.
2. No hidden `time.Now()`, global state, network.
3. Errors are return values, not panics.
4. Types speak units (`Money` in cents, not `float64` euros).

### Table-driven pattern

```go
tests := []struct {
	name string
	in   Input
	want Output
	err  bool
}{
	{name: "zero_qty", in: Input{Qty: 0}, err: true},
	{name: "happy", in: Input{Qty: 2, Price: 100}, want: Output{Total: 200}},
}

for _, tt := range tests {
	t.Run(tt.name, func(t *testing.T) {
		got, err := Fn(tt.in)
		if tt.err {
			if err == nil {
				t.Fatal("expected err")
			}
			return
		}
		if err != nil {
			t.Fatalf("unexpected err: %v", err)
		}
		if got != tt.want {
			t.Fatalf("got %+v want %+v", got, tt.want)
		}
	})
}
```

### Trace: adding a rule

```text
1. Product owner: "EU zone + overweight (>5kg) → +200"
2. You add a row to the table BEFORE implementation (or right with it)
3. Test red
4. Implementation
5. Test green
6. Handler stays thin — only calls Quote
```

This is a TDD-ish flow without religion: the table drives edge cases.

### Predict, then check: float money

```go
func PriceEUR(cents int) float64 { return float64(cents) / 100 }
```

**Predict:** why does table-driven with `float64` hurt?

**Answer:** Rounding and binary representation. Keep **cents as `int`** in the domain; format only at the edge (JSON string, display).

### Naming rows

| Bad | Better |
|------|--------|
| `case1` | `qty_zero_rejected` |
| `test` | `eu_overweight_surcharge` |
| `a` | `discount_100_percent` |

The name goes into `t.Run` → `-run` and the CI report.

### Splitting tables

When a table has 40 rows of mixed topics:

```text
TestQuote_Zones
TestQuote_Weight
TestQuote_Validation
```

Or separate files `quote_zones_test.go`. The signal stays clear.

### wantErr vs errors.Is

```go
wantErr error // sentinel
// ...
if !errors.Is(err, tt.wantErr) {
	t.Fatalf("err=%v want %v", err, tt.wantErr)
}
```

Better than an `err != nil` bool when you have multiple error kinds.

### Parallel subtests

```go
t.Run(tt.name, func(t *testing.T) {
	t.Parallel()
	// only if there is no shared mutable state
})
```

Pure function + local input = often OK. Shared `map` fake = no.

### Trace: -run of one row

```bash
go test -v -run 'TestQuote/eu_overweight' ./pkg/ship
```

```text
=== RUN   TestQuote
=== RUN   TestQuote/eu_overweight
--- PASS: TestQuote/eu_overweight
```

The loop still exists, but the runner filters the subtest.

## Rules and syntax

1. A `slice` of anonymous `struct`s as the table.
2. Required `name` field + `t.Run`.
3. Copying `tt := tt` is not needed from Go 1.22+ in `range` (the loop variable is per iteration) — use Go 1.22+.
4. Do not log the whole table in one `Fatal` without the case name.
5. Money in whole units.
6. The handler does not contain the formula — it calls the domain.

Note on Go 1.22: `for _, tt := range tests { t.Run(..., func(...) { use tt }) }` is safe — each iteration has its own `tt`. On older versions you needed `tt := tt`.

## Examples

### Example 1 — Quote with zones

```go
package ship

import "errors"

var ErrUnknownZone = errors.New("unknown zone")

func Quote(weightGrams int, zone string) (int, error) {
	if weightGrams <= 0 {
		return 0, errors.New("weight")
	}
	base := map[string]int{"local": 500, "eu": 900, "world": 1500}
	b, ok := base[zone]
	if !ok {
		return 0, ErrUnknownZone
	}
	if zone == "eu" && weightGrams > 5000 {
		b += 200
	}
	return b, nil
}
```

```go
func TestQuote(t *testing.T) {
	tests := []struct {
		name   string
		w      int
		zone   string
		want   int
		wantEr error
	}{
		{name: "local", w: 1000, zone: "local", want: 500},
		{name: "eu", w: 1000, zone: "eu", want: 900},
		{name: "eu_overweight", w: 6000, zone: "eu", want: 1100},
		{name: "bad_zone", w: 1000, zone: "mars", wantEr: ErrUnknownZone},
		{name: "bad_weight", w: 0, zone: "local", wantEr: errors.New("weight")},
	}
	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			got, err := Quote(tt.w, tt.zone)
			if tt.wantEr != nil {
				if err == nil || err.Error() != tt.wantEr.Error() && !errors.Is(err, tt.wantEr) {
					// for sentinel use Is; for "weight" compare carefully here
					if !errors.Is(err, tt.wantEr) && (err == nil || err.Error() != tt.wantEr.Error()) {
						t.Fatalf("err=%v want %v", err, tt.wantEr)
					}
				}
				return
			}
			if err != nil {
				t.Fatal(err)
			}
			if got != tt.want {
				t.Fatalf("got %d want %d", got, tt.want)
			}
		})
	}
}
```

Better shape for `bad_weight`: sentinel `ErrInvalidWeight` and only `errors.Is`.

#### What happens here

One table protects zones, surcharge, and errors. `-run 'TestQuote/eu_overweight'` isolates the surcharge.

### Example 2 — ACL state transition

```go
func CanTransition(from, to Status) bool {
	allowed := map[Status][]Status{
		Draft:     {Submitted},
		Submitted: {Paid, Cancelled},
		Paid:      {Shipped},
	}
	for _, s := range allowed[from] {
		if s == to {
			return true
		}
	}
	return false
}
```

Table: every allowed transition + a few forbidden ones (`Paid→Draft`).

#### What happens here

State machine specification without UI.

### Example 3 — Rounding in cents

```go
func NetFromGross(gross, rateBP int) int {
	// rateBP: 2000 = 20.00%
	return gross * 10000 / (10000 + rateBP)
}
```

Table: known fiscal examples from the specification, not random float.

### Example 4 — Predict the name in CI

Failure:

```text
--- FAIL: TestQuote/eu_overweight (0.00s)
    quote_test.go:41: got 900 want 1100
```

**Predict:** what is missing in the code?

**Answer:** The surcharge branch was not applied or the condition `weightGrams > 5000` is wrong (e.g. `>=` vs `>`).

### Example 5 — Anti-table

```go
func TestQuote(t *testing.T) {
	if Quote(1, "local"); false { }
	// 200 lines of copy-paste ifs
}
```

#### What happens here

It does not filter, does not read, does not grow. Move to a table.

### Example 6 — Thin handler

```go
func (h Handler) quote(w http.ResponseWriter, r *http.Request) {
	// parse input...
	price, err := ship.Quote(weight, zone)
	// write JSON...
}
```

The unit table lives in `ship`; the handler test (11.09) checks status/JSON, not the formula.

## Decision analysis

| Decision | Motive |
|--------|--------|
| Pure domain | Fast tests, one source of truth |
| Table + t.Run | Scales edges, `-run` works |
| Cents / BP | No float surprises |
| Sentinel errors | `errors.Is` in the table |
| Thin handlers | Formula is not trapped in HTTP |

## Trade-offs

- **Large table** — clear specification; can become “junk” without splitting.
- **Strict TDD** — good for rules; slower feel for exploratory UI.
- **want as a whole struct** — readable; sometimes field-by-field `Errorf` is better.
- **Generating tables** — rare; prefer readable literals.
- **Parallel** — faster; requires purity.

## Common mistakes

1. Formula in a handler without a table test.
2. `float64` for money.
3. `case1`, `case2` names.
4. One `Fatal` without `t.Run` — you do not know which row.
5. Comparing `err.Error()` instead of sentinel/`Is`.
6. Table mixes HTTP and domain.
7. Forgotten edge case (`0`, `max`, empty string).
8. Copy-paste wrong `want` with a green test (false confidence).
9. Testing implementation (private helper) instead of the rule.
10. 80 rows in one table without splitting by topic.

## Idiomatic Go

- Table-driven is the default style for multiple inputs.
- `errors.Is` / `As` in the assert.
- Document odd rules with a comment *above the table row*, not a novel.
- Keep Example 1 as a package template.

## Practical scenario

Billing bug: VAT rounding. Three teams, three formulas. After extracting `package tax` with 25 table rows from the accounting specification, hotfixes stop. Handler tests no longer “guess” tax — only status. When the law changes the rate, the PR is: change the function + 2 new rows.

## Check questions

1. **What is a table-driven test?**  
   A loop over a case table with `t.Run`, instead of copying the body.

2. **Why a pure function?**  
   Determinism, speed, one source of rules.

3. **How to isolate one row?**  
   `go test -run 'TestName/row_name'`.

4. **Why not float for money?**  
   Rounding and binary artifacts; use whole units.

5. **Predict:** 40 ACL+pricing rows in one table — what to do?  
   Split by topic.

6. **Where does the formula live?**  
   In the domain package, not in the handler.

7. **What is `name` in the struct for?**  
   Report, `-run`, rule documentation.

## Deeper trace: from specification to row

```text
Spec: "If zone is eu and weight > 5kg, add 2 EUR"
       │
       ▼
Units: 5kg = 5000g; 2 EUR = 200 cents (with base)
       │
       ▼
Row: {name: "eu_overweight", w: 6000, zone: "eu", want: 1100}
       │
       ▼
Edges: w=5000 without surcharge; w=5001 with surcharge — two rows
```

The `>` vs `>=` edge is a common production bug. **Two table rows** cost less than one hotfix.

### Predict, then check: parallel subtest and error

```go
for _, tt := range tests {
	t.Run(tt.name, func(t *testing.T) {
		t.Parallel()
		got, err := Quote(tt.w, tt.zone)
		_ = got
		_ = err
	})
}
```

If `Quote` uses a global mutable `var cache map...` without a lock — **Predict:** race. Solution: pure function without globals, or `-race` in CI (15.09) + remove the global.

### Additional mechanism — table as a living domain specification

A business rule belongs to a **pure function**. The table (`name`, input, want, wantErr) is documentation that executes.

#### Trace

```text
handler -> Discount(cents, vip) -> int
                ^
         table-driven TestDiscount
```

**Predict-then-answer:** discount is computed in the handler and in a cron in two places. What follows?

Answer: extract one function; one table; the handler only calls.

### Example — edges and rounding

```go
tests := []struct {
	name string
	in   int
	vip  bool
	want int
}{
	{name: "vip_10pct", in: 1000, vip: true, want: 900},
	{name: "no_vip", in: 1000, vip: false, want: 1000},
	{name: "zero", in: 0, vip: true, want: 0},
}
for _, tc := range tests {
	t.Run(tc.name, func(t *testing.T) {
		got := Discount(tc.in, tc.vip)
		if got != tc.want {
			t.Fatalf("got %d want %d", got, tc.want)
		}
	})
}
```

#### What happens here

The name `vip_10pct` in the fail output immediately says which rule breaks. `-run TestDiscount/vip` isolates.

### Example — wantErr

```go
{name: "negative", in: -1, wantErr: true},
```

#### What happens here

Validation is part of the contract. Do not test only the happy path.

### Money in integers

| Bad approach | Better |
|-------------|-------|
| `float64` euros | minor units (`int64` cents) |
| “Ad hoc” rounding | documented rule + case |

**Predict-then-answer:** float compared with `==`. Risk?

Answer: instability. For money use int + explicit rounding.

### Predict-then-answer — an 80-row table

Answer: split `TestDiscount_*` / `TestVAT_*`; keep human names; not one megafile.

| Change | Where |

### Additional trace — naming cases

Good: vat_round_half_up_odd, acl_deny_guest_delete.
Bad: case1, test2, .

Fail output and -run depend on the name. Treat the name as part of the specification.


### More on tables

Every production bug in the domain should leave a **row** in the table with a name that describes the rule.

Anti-pattern:

```go
t.Run("1", ...)
t.Run("2", ...)
```

Better:

```go
t.Run("discount_vip_boundary_1000", ...)
```

**Predict-then-answer:** two teams change the same formula in the handler and in a worker. What does the table do?

Answer: it forces one source of truth — a pure function both call.


### Extension — table-driven edges

Matrix for money and validation:

| name | input | wantErr | note |
|------|------|---------|----------|
| ok_base | 1000 | no | happy |
| zero | 0 | no | edge |
| neg | -1 | yes | validation |
| max | MaxInt | no/yes | overflow policy |

Each row = a contract. When product changes a rule, the row + implementation change.

**Predict-then-answer:** two rows with the same name?

Answer: -run and the fail report become ambiguous — names unique.

### Example — t.Run filter

```bash
go test -run TestDiscount/vip -v
```

#### What happens here

Only VIP cases. Fast feedback while you tune the formula.

### Anti-pattern — logic in a test helper

Do not compute expected in the test with the same formula as production (copy-paste bug). Expected should be a literal from the specification.

## Summary

Business logic deserves a pure layer and table-driven tests. The table is a living specification: edges, rounding, forbidden transitions. Keep money in integers, case names clear, handlers thin. When a rule lives in one place, a tax or ACL change becomes a controlled PR, not archaeology.
