# 11.06 Black-box tests: package `foo_test` and the public contract

> **Go Path - Zero to Gopher** / **02 Intermediate → Creating Well-Tested Applications in Go** / Lesson 11.06

## Lesson goals

- Distinguish **white-box** (`package foo`) and **black-box** (`package foo_test`) tests in the same directory.
- Write tests that see **only the exported API** of the package under test.
- Correctly import the module path in an external test package.
- Know when black-box protects design, and when white-box makes sense.
- Mix both styles deliberately (`*_internal_test.go` + `*_test.go`) without import cycles.
- Force constructors (`New`, `Open`) instead of directly composing private fields.
- Avoid common traps: wrong package name, relative import, “a test that sees the warehouse”.

## Prerequisite

- Lessons 11.04–11.05 (unit and table-driven tests).
- A valid `go.mod` and understanding of the module path.
- Go's export rule: an identifier with an uppercase first letter is visible outside the package.
- Basics: `go test`, `t.Run`, `t.Fatalf`.

## Problem this lesson solves

White-box tests easily “break” encapsulation:

- they assert a private field `cache.entries`;
- they call unexported `normalize()` directly;
- they pass while the public API already does not work for other packages.

A typical team symptom:

1. Refactoring a private helper breaks 40 tests — even though package users feel no change.
2. Or the opposite: public `Quote` changes its contract, and the suite stays green because tests look at an internal `calc` that “accidentally” stayed the same.

A black-box test forces you to check **what other packages actually use**. That is not dogma of “only black-box” — it is a clear signal of what is contract and what is an implementation detail.

## Mental model

Think of a package as a **shop with a storefront**.

| Part | In code | Who sees it |
|-----|--------|---------|
| Storefront | exported types, functions, methods | all clients |
| Warehouse | unexported | only the same `package` |
| White-box tester | `package foo` in `*_test.go` | storefront + warehouse |
| Black-box tester | `package foo_test` | only storefront, like another package |

```text
package quote                 package quote_test
┌──────────────────┐          ┌────────────────────┐
│ Quote()          │◄─────────│ TestQuote_...      │
│ NewStore()       │  import  │ import "mod/quote" │
│ parse()  (priv)  │          │ (does not see parse)    │
│ store.map (priv) │          │                    │
└──────────────────┘          └────────────────────┘
```

**Decision rule:** if you must test `parse` directly, choose one of:

1. export it (it becomes part of the contract — rare);
2. test it through `Quote` (black-box);
3. keep a white-box test next to the internal helper — **deliberately**, with a file name that says so.

## Mechanism

### How Go sees test packages

For a package in directory `quote/`:

| File | `package` clause | Sees unexported? | Typical role |
|------|--------------------|----------------------|---------------|
| `quote.go` | `quote` | yes (production) | API + internal |
| `quote_test.go` | `quote` | yes | white-box |
| `quote_test.go` | `quote_test` | no | black-box |
| `parse_internal_test.go` | `quote` | yes | narrow internal test |

Both styles can live in the **same** directory. `go test` compiles the production package plus test files into a separate test binary context. You do not mix production with `foo_test` in the application runtime — `*_test.go` never enters a normal `go build` of the package for deploy.

### Compiler trace: what happens when you call private

Assume:

```go
// quote.go
package quote

func parse(s string) (int, error) { /* ... */ }

func Quote(s string) (int, error) {
	return parse(s)
}
```

```go
// quote_test.go
package quote_test

import (
	"testing"

	"example.com/shop/quote"
)

func TestParseDirect(t *testing.T) {
	_, err := quote.parse("x") // ← what happens?
	_ = err
}
```

**Predict-then-answer:** does this compile?

Answer: **no**. An error like `cannot refer to unexported name quote.parse`. The compiler treats `quote_test` as an **external** package. That is not a “runtime ban” — it is the same boundary as between `shop/cart` and `shop/quote`.

### Import path

```go
package quote_test

import (
	"testing"

	"example.com/shop/quote"
)

func TestQuote_Local(t *testing.T) {
	got, err := quote.Quote(1000, "local")
	if err != nil {
		t.Fatalf("Quote: %v", err)
	}
	if got != 510 {
		t.Fatalf("got %d, want 510", got)
	}
}
```

The module path must match the `module` line in `go.mod`. Relative imports like `../quote` are **not** idiomatic and often break tooling.

If the package is at the root of module `example.com/shop` and files are in `./quote`, the import is `"example.com/shop/quote"`.

### Why the `quote.` prefix?

In a black-box package you do not have “bare” identifiers from production. You write `quote.Quote`, `quote.New`, not `Quote`. That is the same style as in any client code — a usage example for the test reader.

### Avoiding import cycles

The dependency flow may only go:

```text
quote_test ──import──► quote
```

Never:

```text
quote ──import──► quote_test   // forbidden / senseless
```

If production code “needs” something from a test, the design is wrong. Move the helper into production (if it is part of the contract) or into an `internal/...` package that is not test-only.

### Shared helpers between white and black

Three patterns (from most common to rarer):

1. **Duplicate a small assert** in both files — OK for 3–5 lines.
2. **White-box file** for an internal helper; black-box for API — without sharing.
3. **`export_test.go`** in `package quote` that exports hooks only for tests (advanced; see Example 5).

```go
// export_test.go — package quote (not quote_test)
package quote

// ParseForTest exports parse only for tests in quote_test.
// Production outside the package still does not see parse.
var ParseForTest = parse
```

```go
// quote_ext_test.go
package quote_test

import (
	"testing"

	"example.com/shop/quote"
)

func TestParseViaHook(t *testing.T) {
	_, err := quote.ParseForTest(" 42 ")
	if err != nil {
		t.Fatal(err)
	}
}
```

This is a **deliberate** encapsulation breach through an exported hook. Use rarely; document why it exists.

### Mixing white and black in the same dir

Allowed and common:

```text
ship/
  quote.go
  normalize.go
  quote_test.go              // package ship_test  — API
  normalize_internal_test.go // package ship       — internal
```

Clear file names speed up review: `_internal_test` signals “sees the warehouse”.

### What black-box forces in design

- Public constructors (`New`, `Open`, `MustParse`) instead of `S{priv: ...}` from a test.
- Documented errors and returns — because the test cannot “peek” into state.
- Fewer tests that exist only to bind private helpers.

### What white-box still does better

- A complex internal algorithm before the API stabilizes.
- Cache / index invariants the API does not expose.
- Fast tests during a spike while you still change the public shape.

### Trace: `go test` and both packages

```bash
cd ship
go test -v .
```

Runs **all** `Test*` in `package ship` and `package ship_test` for that directory. Filtering:

```bash
go test -run TestQuote -v .
go test -run TestNormalize -v .
```

Function names are global in the sense of the `-run` regex for that package test run — choose clear names so you do not collide white and black `TestQuote` without need (usually one style per scenario).

### Predict-then-answer: two `package` in one `*_test.go`?

```go
package ship_test
// ...
package ship  // second package in the same file?
```

Answer: **no**. One file = one `package` clause. Split into two files.

### Predict-then-answer: may `package ship_test` be named `ship_tests`?

Technically the compiler accepts another name, but the **convention** is `foo_test`. Tools, documentation, and team expectations count on the `_test` suffix. Stay with the convention.

## Rules and syntax

1. External package name: `foo_test`, where `foo` is the production package name.
2. Import the production package with the **full** module path.
3. Reference symbols with the package prefix: `ship.Quote`.
4. Do not put production code in `*_test.go` (it does not enter a normal client build, but it confuses).
5. `Example` functions can also be in `foo_test` — see 11.07.
6. `go test .` in the package directory runs both styles.
7. Production never imports the test package.
8. Prefer `New` / factory in the test if the structure has unexported fields.

Minimal layout:

```text
module example.com/shop   (go.mod above)

ship/
  quote.go
  quote_test.go                 // package ship_test
  normalize_internal_test.go    // package ship (optional)
```

## Examples

### Example 1 — Same API, black-box package

```go
// file: ship/quote.go
package ship

import "fmt"

// Quote returns a shipping price in minor units (e.g. cents).
func Quote(weightGrams int, zone string) (int, error) {
	if weightGrams <= 0 {
		return 0, fmt.Errorf("weightGrams must be > 0")
	}
	switch zone {
	case "local":
		return 500 + weightGrams/100, nil
	case "eu":
		return 1000 + weightGrams/50, nil
	default:
		return 0, fmt.Errorf("unknown zone %q", zone)
	}
}
```

```go
// file: ship/quote_test.go
package ship_test

import (
	"testing"

	"example.com/shop/ship"
)

func TestQuote_Local(t *testing.T) {
	got, err := ship.Quote(200, "local")
	if err != nil {
		t.Fatalf("err: %v", err)
	}
	if got != 502 {
		t.Fatalf("got %d, want 502", got)
	}
}

func TestQuote_UnknownZone(t *testing.T) {
	_, err := ship.Quote(100, "mars")
	if err == nil {
		t.Fatal("expected error")
	}
}
```

#### What happens here

The test behaves like another package in a monorepo. Refactoring an internal name does not break the suite. Changing the `Quote` formula breaks — the desired signal. The import path documents **how the package is used from outside**.

### Example 2 — White-box for an internal detail, black-box for API

```go
// file: ship/normalize.go
package ship

import "strings"

func normalizeZone(z string) string {
	return strings.ToLower(strings.TrimSpace(z))
}
```

```go
// file: ship/normalize_internal_test.go
package ship

import "testing"

func TestNormalizeZone(t *testing.T) {
	got := normalizeZone("  EU ")
	if got != "eu" {
		t.Fatalf("got %q, want %q", got, "eu")
	}
}
```

```go
// file: ship/quote_api_test.go
package ship_test

import (
	"testing"

	"example.com/shop/ship"
)

func TestQuote_AcceptsMixedCaseIfPublicAPIDoes(t *testing.T) {
	// If Quote internally calls normalizeZone, black-box checks that
	// through public behavior — not through normalizeZone.
	got, err := ship.Quote(100, "Local")
	if err != nil {
		// If the API does not normalize yet, this test documents the current contract.
		t.Skip("API currently requires exact zone string; see internal test")
	}
	_ = got
}
```

#### What happens here

Internal `normalizeZone` has a fast white-box test. The public contract is checked separately. If `Quote` does not yet call `normalizeZone`, black-box **does not lie** that the API accepts `"Local"` — `Skip` or an explicit fail by team agreement.

### Example 3 — Constructor forced by private fields

```go
// file: store/store.go
package store

import "fmt"

type Store struct {
	path   string
	opened bool
}

func New(path string) (*Store, error) {
	if path == "" {
		return nil, fmt.Errorf("path required")
	}
	return &Store{path: path, opened: true}, nil
}

func (s *Store) Path() string { return s.path }

func (s *Store) Close() error {
	s.opened = false
	return nil
}

func (s *Store) IsOpen() bool { return s.opened }
```

```go
// file: store/store_test.go
package store_test

import (
	"testing"

	"example.com/shop/store"
)

func TestNew_EmptyPath(t *testing.T) {
	_, err := store.New("")
	if err == nil {
		t.Fatal("expected error")
	}
}

func TestNew_RoundTrip(t *testing.T) {
	s, err := store.New("/tmp/data")
	if err != nil {
		t.Fatal(err)
	}
	if s.Path() != "/tmp/data" {
		t.Fatalf("path: %q", s.Path())
	}
	if !s.IsOpen() {
		t.Fatal("expected open")
	}
	_ = s.Close()
	if s.IsOpen() {
		t.Fatal("expected closed")
	}
}
```

#### What happens here

From `store_test` you **cannot** write `store.Store{path: "x"}` — fields are unexported. The test must go through `New`, like a production client. That is the design pressure black-box gives for free.

**Predict-then-answer:** what if you do `s := &store.Store{}`?

Answer: it compiles (the type is exported), but fields stay zero value and you cannot set them from outside. `IsOpen()` returns `false`. Such a test often lies about real usage — prefer `New`.

### Example 4 — Table-driven black-box

```go
func TestQuote_Table(t *testing.T) {
	tests := []struct {
		name    string
		weight  int
		zone    string
		want    int
		wantErr bool
	}{
		{name: "local", weight: 200, zone: "local", want: 502},
		{name: "eu", weight: 100, zone: "eu", want: 1002},
		{name: "bad weight", weight: 0, zone: "local", wantErr: true},
		{name: "bad zone", weight: 10, zone: "x", wantErr: true},
	}

	for _, tc := range tests {
		t.Run(tc.name, func(t *testing.T) {
			got, err := ship.Quote(tc.weight, tc.zone)
			if tc.wantErr {
				if err == nil {
					t.Fatal("expected error")
				}
				return
			}
			if err != nil {
				t.Fatalf("unexpected err: %v", err)
			}
			if got != tc.want {
				t.Fatalf("got %d, want %d", got, tc.want)
			}
		})
	}
}
```

#### What happens here

Same pattern as in 11.05, but from `ship_test`. The table describes the **contract**, not internal `switch` branches by helper name.

### Example 5 — `export_test.go` hook (advanced)

```go
// file: ship/export_test.go
package ship

// NormalizeZoneExport exposes normalizeZone to tests in ship_test.
var NormalizeZoneExport = normalizeZone
```

```go
func TestNormalize_ExportedHook(t *testing.T) {
	if ship.NormalizeZoneExport(" Eu ") != "eu" {
		t.Fatal("normalize hook failed")
	}
}
```

#### What happens here

Production clients outside `ship` do not import `export_test.go` content in their build in a way that changes the API in docs — the file is `*_test.go` and tied to the test build. Still, the symbol `NormalizeZoneExport` exists for black-box tests. Use when you really need to test internal **and** want the test file to stay `ship_test` (e.g. to share setup with API tests). Most of the time a simpler `package ship` internal test is better.

### Example 6 — Common mistake: wrong import

```go
package ship_test

import (
	"testing"

	ship "example.com/shop/ship" // OK alias
	// "ship"                     // NO — not a standard path
)

func TestOK(t *testing.T) {
	_, _ = ship.Quote(1, "local")
}
```

#### What happens here

Alias `ship` is redundant if it matches the default name, but it is valid. The mistake is trying a local name without a module path.

### Example 7 — Refactor trace: what each style catches

| Change | White-box `TestNormalize` | Black-box `TestQuote` |
|---------|---------------------------|------------------------|
| Rename `normalizeZone` → `normZone` | breaks (direct call) | stays quiet |
| Change price formula in `Quote` | stays quiet (does not call Quote) | breaks |
| Add trim in `normalizeZone`, `Quote` calls it | may pass | catches through public input `" Local"` if you assert |

#### What happens here

Neither style is “complete” alone. Choose by the question you are asking.

## Decision analysis

| Question | Prefer black-box | Prefer white-box |
|---------|----------------------|----------------------|
| Does the public API work for clients? | yes | — |
| Does an internal parser cover 20 edges? | through API if cheap | directly if expensive / deep |
| Library for other teams | default black-box | narrowly internal |
| Internal package `internal/...` | both OK; black still useful | often white for speed |
| Unstable spike API | — | yes, until the shape freezes |
| Regression after a storefront bug | yes | supplement |

**Decision in a PR:** if a new test touches a private field, the reviewer asks: “Can the same claim go through an exported method?” If yes — move to black-box.

## Trade-offs

| | Black-box (`foo_test`) | White-box (`foo`) |
|--|------------------------|-------------------|
| Encapsulation | strong | weak |
| Break on internal refactor | rare | frequent |
| Access to helpers | none (except a hook) | full |
| Signal for API design | strong | weaker |
| Writing speed at the start | sometimes slower | faster |
| Fidelity to client code | high | lower |

The trade-off is not “pick one forever”. The trade-off is **where you draw the contract boundary**.

## Common mistakes

1. **A test in `package foo` that asserts private fields “because it is easier”** — the suite becomes glue for the implementation.
2. **Relative import** (`../foo`) instead of the module path.
3. **Cyclic idea** that production imports a test helper package.
4. **Package name `foo_tests` / `footest`** instead of `foo_test`.
5. **Direct composition** of an exported struct with zero value instead of `New`, so tests pass for an impossible state.
6. **Everything white-box “temporarily”** that stays for years.
7. **Duplicate test of the same claim** in both styles without need — noise in CI.
8. **Mixing production code into `*_test.go`** “only for a build tag” without a clear reason.
9. **Expecting black-box to see `export_test.go` symbols in a normal `go build`** — confusion about the test build.
10. **Skipping an API test** instead of a clear assert when the contract is not yet agreed — better `t.Fatal` with a message or an explicit issue.

## Idiomatic Go

- For library packages: **default black-box** for the public API.
- Name files: `foo_test.go` (API), `foo_internal_test.go` (warehouse).
- Constructors `NewX` + unexported fields = tests as clients.
- Table-driven + black-box = readable contract.
- `Example` in `foo_test` (next lesson) continues the same story: documentation from the client angle.
- The standard library and popular modules often combine both — read their `*_test.go` as a model, not as dogma.

## Practical scenario

A team keeps a `billing/tax` package. White-box tests for years called `roundVAT` directly. A new English refactor renames the helper to `roundHalfUp` and fixes one branch. **38 tests red**, even though public `Calculate` for existing inputs is the same — except one edge case that no API test covered.

After the incident:

1. API table-driven tests move to `package tax_test`.
2. One `round_internal_test.go` remains for numeric rounding edges.
3. PR checklist: “New test — does it have to go into the warehouse?”

Result: an internal rename no longer sounds the siren; a real regression fail comes when `Calculate` output changes.

## Check questions

1. **What is a black-box test in Go?**  
   A test in `package foo_test` that sees only the exported API of package `foo`.

2. **Why use black-box?**  
   To protect encapsulation and test the contract as other packages see it.

3. **When white-box?**  
   Internal algorithms, invariants the API does not expose, early development of an unstable API.

4. **How do you import the package under test?**  
   Full module path, e.g. `"example.com/shop/ship"`.

5. **What does a private field in a struct force?**  
   Using constructors and public methods instead of directly composing fields from the test.

6. **Can white and black live in the same directory?**  
   Yes — different files, different `package` clauses.

7. **What is the `export_test.go` pattern?**  
   A file in `package foo` (test build) that exports hooks for `foo_test`, rarely and deliberately.

8. **Does `go test` run both styles?**  
   Yes, for that package directory.

### Additional mechanism — foo_test sees only the storefront

`package foo_test` imports `foo` as an **external** client. Unexported is invisible — that is the point of a black-box test.

## Summary

Black-box (`foo_test`) tests the package storefront; white-box sees the warehouse. Use black-box to protect the API and encapsulation, white-box sparingly for internal parts. Correct module import and `New` constructors make tests faithful to clients. The goal is not dogma of one style — but a clear signal of what is contract and what is detail.
