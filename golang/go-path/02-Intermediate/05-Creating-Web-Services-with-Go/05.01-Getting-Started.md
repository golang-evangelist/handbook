# 05.01 Web services in Go: Server, Handler, ServeMux patterns (Go 1.22+)

> **Go Path - Zero to Gopher** / **02 Intermediate → Creating Web Services with Go** / Lesson 05.01

## Lesson goals

After this lesson you can:

- start an **`http.Server`**, understand what **`ListenAndServe`** does, and why in production you do not use bare `http.ListenAndServe` without a struct;
- register routes on **`ServeMux`** with Go **1.22+** patterns `METHOD /path`, wildcards `{id}` and `{$}`, and read values via `r.PathValue`;
- distinguish **`http.Handler`** from **`http.HandlerFunc`** and choose the right form;
- write **middleware** as a higher-order function `func(http.Handler) http.Handler`, understand the onion model and that calling `next` is optional;
- set **ReadHeaderTimeout**, **ReadTimeout**, **WriteTimeout**, **IdleTimeout** and know when each fires;
- sketch **graceful Shutdown(ctx)** with a signal;
- separate a thin `main` from `Routes() http.Handler` for `httptest` tests;
- understand **404 vs 405**, **MaxHeaderBytes**, briefly **healthz vs readyz**, and why libraries must not touch **DefaultServeMux**.

## Prerequisite

- Functions, `interface`, methods with a receiver (02.x).
- Package layout `cmd` / `internal` (04.01).
- Basic HTTP concepts: request, response, status code, header — you do not need to have written a server before.
- Go **1.22 or newer** (HTTP method + path patterns on the stdlib `ServeMux`).

## Problem this lesson solves

Without this foundation you typically get:

1. `http.HandleFunc("/", …)` without an HTTP method in the pattern — POST and GET go to the same handler, so you manually check `r.Method` everywhere.
2. Global `DefaultServeMux` — two packages register the same path, collide at runtime, hard to test.
3. A server without timeouts — the connection stays open while the client slowly sends headers (slowloris-style load).
4. All routes and logic in `main` — you cannot call the handler from a unit test without a TCP port.
5. The old routing feel (longest prefix) instead of Go 1.22 rules — bugs on trailing slash and wildcards.
6. No path to graceful shutdown because you never held `*http.Server`.

This lesson builds the skeleton: Server + mux + Handler + timeout + Routes + middleware. JSON and the database come in later lessons.

## Mental model

Imagine five layers, bottom to top:

1. **TCP accept** — `ListenAndServe` opens a socket on `Addr` (e.g. `:8080`).
2. **HTTP parsing** — the server reads the request line and headers; this is where Read* timeouts fire.
3. **Routing** — `ServeMux` chooses which `Handler` matches `(method, path)`.
4. **Handler** — your code: `ServeHTTP(w, r)` writes the response.
5. **Middleware onion** — wrappers around the handler (log, auth, request ID) before and after `next`.

One sentence: **The Server does not “know” your domain — it only delivers `*http.Request` to the right `Handler`, and you control time, routes, and composition.**

```text
client ──TCP──► http.Server ──► ServeMux ──► [middleware…] ──► Handler
                      ▲                              │
                      │         response ◄────────────┘
                      └── timeout / Shutdown control the lifecycle
```

## Mechanism

### What is http.Handler

`http.Handler` is an `interface` with one method:

```go
type Handler interface {
	ServeHTTP(ResponseWriter, *Request)
}
```

Everything that handles HTTP in the Go stdlib is a Handler: your struct, the mux, a middleware wrapper, and even `http.HandlerFunc`.

**Predict, then answer.** Type `API` has a method `ServeHTTP(w, r)`. Is `API{}` a valid argument for `mux.Handle("GET /x", …)`?

> **Answer:** Yes — it satisfies `Handler`. `Handle` wants a `Handler`, not a function.

### HandlerFunc — adapter

```go
type HandlerFunc func(ResponseWriter, *Request)

func (f HandlerFunc) ServeHTTP(w ResponseWriter, r *Request) {
	f(w, r)
}
```

An ordinary function becomes a Handler by wrapping it in `HandlerFunc`, or by using `mux.HandleFunc` which does that for you.

**Predict, then answer.** You have `func ping(w http.ResponseWriter, r *http.Request)`. What is the type of `http.HandlerFunc(ping)`?

> **Answer:** A value of type `http.HandlerFunc`, which implements `Handler`. You can pass it wherever `http.Handler` is required.

### http.Server and ListenAndServe

Minimal production shape:

```go
srv := &http.Server{
	Addr:              ":8080",
	Handler:           mux, // nil = DefaultServeMux — avoid in lib/app
	ReadHeaderTimeout: 5 * time.Second,
}
err := srv.ListenAndServe()
```

`ListenAndServe`:

1. listens on `Addr`;
2. for each accepted connection starts processing (an internal goroutine per connection — the server runtime does that; you do not write `go` by hand for it);
3. parses the HTTP request;
4. calls `Handler.ServeHTTP`;
5. returns an `error` when it stops (e.g. after `Shutdown`, or if bind fails).

`http.ListenAndServe(addr, handler)` is a shortcut that builds a temporary `Server` — **you have no reference** for `Shutdown`. So from day one hold `*http.Server`.

**Predict, then answer.** You call `http.ListenAndServe(":8080", mux)`. The port is taken. What happens?

> **Answer:** The function immediately returns an `error` (bind failure). If you used `log.Fatal(err)`, the process exits. There is no “silent” success.

### ServeMux — choosing a handler

```go
mux := http.NewServeMux()
mux.HandleFunc("GET /healthz", health)
mux.Handle("GET /greet", API{Greeting: "hello"})
```

From Go **1.22**, the pattern is a string that can contain:

- an HTTP method (GET, POST, …) — space — path;
- wildcards `{name}` for one segment;
- `{$}` for “the rest of the path to the end”.

Without an HTTP method in the pattern, the mux accepts **all** methods for that path — you then must check in the handler. In new code **put the HTTP method in the pattern**.

### Wildcard {id} and PathValue

Pattern `"GET /products/{id}"` matches `/products/42` with `id=42`.

```go
id := r.PathValue("id") // "42"
```

`PathValue` is an empty string if the name does not exist in the pattern that matched the request. Detailed validation (UUID format, ranges) is in 05.02 — here remember the value comes from the mux, not from a hand-rolled `strings.Split`.

**Predict, then answer.** Registered: `"GET /products/{id}"`. A `GET /products/42/extra` arrives. Does it match?

> **Answer:** No — `{id}` is **one** segment. More segments need a different pattern (e.g. with `{$}` or a deeper path).

### Wildcard {$}

`{$}` captures the rest of the path. Use it carefully (e.g. static files, catch-all). Example pattern: `"GET /files/{$}"`. Read the value with `r.PathValue("$")` — the wildcard name is the literal `$`.

Do not confuse `{$}` with “all application routes”. Prefer explicit routes; catch-all only when you truly need it.

### HTTP method + path in one string

| Pattern | GET /hello | POST /hello | GET /hello/ | GET /other |
|---------|------------|-------------|-------------|------------|
| `"GET /hello"` | match | no (405 if another HTTP method exists on the same path, otherwise 404/405 per mux rules) | depends on trailing slash rules | no |
| `" /hello"` (no HTTP method) | match | match | … | no |
| `"GET /hello/"` | no | no | match | no |

The exact 404 vs 405 matrix depends on which patterns you registered for the same path. Rule to remember:

- **no path** → **404**;
- **path exists, HTTP method does not** → **405** (often with an `Allow` header).

**Predict, then answer.** You only have `"GET /items"`. The client sends `DELETE /items`. Expected status?

> **Answer:** **405 Method Not Allowed** — the path is known to the mux via the GET pattern; the HTTP method is not allowed. (If there is no pattern at all for `/items`, it would be 404.)

### Middleware as a higher-order function

Signature:

```go
func withLog(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		start := time.Now()
		next.ServeHTTP(w, r) // calling next is OPTIONAL
		log.Printf("%s %s %s", r.Method, r.URL.Path, time.Since(start))
	})
}
```

That is a higher-order function: takes a Handler, returns a Handler. You compose a chain:

```go
h := withLog(withAuth(Routes()))
srv.Handler = h
```

### Onion model

The request goes **outside to inside**, the response **inside to outside**:

```text
withLog
  └─ withAuth
       └─ mux / handler
```

Registration order matters:

- `withLog(withAuth(mux))` — log also sees auth failures;
- `withAuth(withLog(mux))` — auth rejects before the inner handler is logged (the log middleware can still log if it logs before/after next).

### Calling next is OPTIONAL

Auth middleware **does not have to** call `next`:

```go
func withAuth(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		if r.Header.Get("Authorization") == "" {
			http.Error(w, "unauthorized", http.StatusUnauthorized)
			return // next is NOT called — the onion stops
		}
		next.ServeHTTP(w, r)
	})
}
```

**Predict, then answer.** `withAuth` returns 401 and does not call `next`. Does the inner handler write a body?

> **Answer:** No. The chain is broken. That is intentional — middleware can short-circuit the response.

### Timeouts — when each fires

Set them on `http.Server`. Each measures a **different** time:

| Field | What it measures | When it “fires” / what it is for |
|-------|------------------|----------------------------------|
| **ReadHeaderTimeout** | time to read request headers | Client sends headers very slowly or never finishes — connection is cut. First line of defense against slowloris-style load. |
| **ReadTimeout** | time for the whole request read (headers + body) from accept | Slow body upload; includes header time. Must be ≥ expected max upload. |
| **WriteTimeout** | time to write the response | Slow client that does not read the response; a handler that holds the connection too long while writing. |
| **IdleTimeout** | idle keep-alive connection time between requests | Keep-alive stays open without a new request for too long — server closes. |

Order in the life of one request (simplified):

1. connection accepted;
2. reading headers → **ReadHeaderTimeout**;
3. reading the rest (body) within **ReadTimeout**;
4. `ServeHTTP` + writing → **WriteTimeout**;
5. keep-alive waits for the next request → **IdleTimeout**.

**Predict, then answer.** `ReadHeaderTimeout = 5s`, `ReadTimeout = 30s`. Header arrives in 1s, a 100 MiB body takes 40s. What cuts it off?

> **Answer:** **ReadTimeout** — the full request read exceeds 30s. ReadHeaderTimeout already passed successfully.

**Predict, then answer.** Only `IdleTimeout = 60s`, no ReadHeaderTimeout. Are you protected from slow sending of the first headers on a new connection?

> **Answer:** Not reliably. IdleTimeout measures the pause **between** keep-alive requests, not a “stuck” first request. So **always** set at least `ReadHeaderTimeout`.

### Graceful Shutdown(ctx)

Production sketch (signal + Shutdown):

```go
srv := &http.Server{Addr: ":8080", Handler: mux, ReadHeaderTimeout: 5 * time.Second}

go func() {
	if err := srv.ListenAndServe(); err != nil && err != http.ErrServerClosed {
		log.Fatal(err)
	}
}()

stop := make(chan os.Signal, 1)
signal.Notify(stop, os.Interrupt, syscall.SIGTERM)
<-stop

ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
defer cancel()
if err := srv.Shutdown(ctx); err != nil {
	log.Printf("shutdown: %v", err)
}
```

What `Shutdown(ctx)` does:

- stops accepting **new** connections;
- waits for active requests to finish, or until `ctx` expires;
- `ListenAndServe` then returns `http.ErrServerClosed` (that is not a “fatal” process error — so you check `err != http.ErrServerClosed`).

Without an `*http.Server` reference, there is no `Shutdown`. So do not start with bare `http.ListenAndServe` in services you plan for production.

### Why not DefaultServeMux in libraries

`http.Handle` / `http.HandleFunc` without a mux write to the **global** `DefaultServeMux`.

Problems:

- two packages, same path → panic on registration or unexpected behavior;
- tests share global state;
- a library “pollutes” the application mux without consent.

Rule: **a library exports `Routes() http.Handler` or takes `*ServeMux` / registers on a passed-in mux. The application in `main` composes.**

`ListenAndServe(addr, nil)` uses DefaultServeMux — avoid that in serious code too.

### Thin main vs Routes()

```go
// internal/httpapi/routes.go
func Routes() http.Handler {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /healthz", healthz)
	mux.HandleFunc("GET /readyz", readyz)
	return mux
}

// cmd/shop/main.go
func main() {
	srv := &http.Server{
		Addr:              ":8080",
		Handler:           httpapi.Routes(),
		ReadHeaderTimeout: 5 * time.Second,
	}
	log.Fatal(srv.ListenAndServe())
}
```

`main` = wiring (address, timeout, signal). Domain HTTP logic = `httpapi`.

### httptest as motivation for Routes()

```go
func TestHealthz(t *testing.T) {
	req := httptest.NewRequest(http.MethodGet, "/healthz", nil)
	rec := httptest.NewRecorder()
	httpapi.Routes().ServeHTTP(rec, req)
	if rec.Code != http.StatusOK {
		t.Fatalf("code=%d", rec.Code)
	}
}
```

No port, no `ListenAndServe`. That is why `Routes() http.Handler` exists from day 1 — not for “pretty design”, but for a **test without the network**.

### 404 vs 405 in practice

| Situation | Status | Who responds |
|-----------|--------|--------------|
| Unknown path | 404 | ServeMux |
| Known path, wrong HTTP method | 405 | ServeMux |
| Resource does not exist in the DB (`/products/999`) | 404 | your Handler (after PathValue) |

Do not override mux 405 with a manual `if r.Method` on every route if you already put the HTTP method in the pattern.

### MaxHeaderBytes

`Server.MaxHeaderBytes` limits the size of the request header block. Together with `ReadHeaderTimeout` it is basic hardening. A default exists in the stdlib; raise it only if you truly have legitimately large headers (rare). A large cookie jar is better solved by architecture than by unbounded headers.

### healthz vs readyz (brief)

| Endpoint | Meaning | Typical check |
|----------|---------|---------------|
| `/healthz` (liveness) | Process is alive | Always 200 if the HTTP server runs |
| `/readyz` (readiness) | Ready for traffic | Ping DB, cache, dependencies |

Kubernetes: a bad `/readyz` removes the pod from the Service; a bad `/healthz` restarts the pod. If you merge both into one endpoint that pings the DB, a DB restart kills pods instead of only temporarily removing them from the load balancer.

### Pattern order and specificity

In 1.22+ the mux chooses by matching rules (not the old “longest prefix feel”). So:

- write explicit patterns;
- cover conflict cases with an `httptest` table;
- read the official `ServeMux` docs when you add a catch-all.

### Trailing slash

`/foo` and `/foo/` are not automatically the same. Test both or normalize in middleware (redirect). Do not assume old behavior.

### Host in the pattern (note)

A pattern can include a host (`"GET example.com/path"`). For most CRUD APIs at the start it is not needed. Leave it for multi-tenant later.

### TLS note

`ListenAndServeTLS` for HTTPS in-process. In production TLS often terminates at a reverse proxy — still keep timeouts on the Go `Server` behind the proxy.

### BaseContext / ConnContext (direction)

`Server.BaseContext` and `ConnContext` attach values at connection level. Useful for a per-connection logger. Not required on day one; know they exist.

## Rules and syntax

1. **Go 1.22+:** put the HTTP method in the pattern (`"GET /x"`), unless you consciously want all methods.
2. **Wildcard:** `{name}` = one segment; `{$}` = the rest to the end; read with `r.PathValue("name")` / `r.PathValue("$")`.
3. **Handler vs HandlerFunc:** struct with dependencies → `Handler`; plain function → `HandleFunc` / `HandlerFunc`.
4. **Middleware:** `func(http.Handler) http.Handler`; call `next` only if you continue the chain.
5. **Server fields:** always at least `ReadHeaderTimeout`; add Read/Write/Idle per load.
6. **No DefaultServeMux** in libraries and in applications shared across packages — pass/return `http.Handler`.
7. **`ListenAndServe` error:** check it; after Shutdown expect `http.ErrServerClosed`.
8. **Thin main:** `Routes()` + server configuration; business logic outside `main`.
9. **404/405:** let the mux handle HTTP method/path; map domain “no entity” in the handler.
10. **MaxHeaderBytes** + timeouts = basic hardening before JSON/body limits (05.02).

## Examples

### Example 1 — Minimal server with 1.22 mux and timeouts

```go
package main

import (
	"fmt"
	"log"
	"net/http"
	"time"
)

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /healthz", func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte("ok"))
	})
	mux.HandleFunc("GET /hello", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, "hello")
	})

	srv := &http.Server{
		Addr:              ":8080",
		Handler:           mux,
		ReadHeaderTimeout: 5 * time.Second,
		ReadTimeout:       10 * time.Second,
		WriteTimeout:      15 * time.Second,
		IdleTimeout:       60 * time.Second,
	}
	log.Println("listening :8080")
	log.Fatal(srv.ListenAndServe())
}
```

#### What happens here

- `NewServeMux` — local mux, not DefaultServeMux.
- `"GET /healthz"` and `"GET /hello"` — HTTP method in the pattern; `POST /hello` does not enter the hello handler.
- Four timeout fields set explicitly.
- `log.Fatal` shows bind/listen errors; for production Shutdown use the pattern from Mechanism (goroutine + signal).

**Predict, then answer.** `curl -X POST localhost:8080/hello` — which status do you expect?

> **Answer:** 405 (path `/hello` exists as a GET pattern; POST is not allowed).

### Example 2 — Handler type instead of a bare function

```go
package httpapi

import (
	"fmt"
	"net/http"
)

type API struct {
	Greeting string
}

func (a API) ServeHTTP(w http.ResponseWriter, r *http.Request) {
	fmt.Fprintln(w, a.Greeting)
}

func Routes() http.Handler {
	mux := http.NewServeMux()
	mux.Handle("GET /greet", API{Greeting: "hello from Handler"})
	mux.HandleFunc("GET /ping", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, "pong")
	})
	return mux
}
```

#### What happens here

- `API` carries a dependency (here a string; tomorrow a store, logger, clock).
- `mux.Handle` takes a `Handler`; `HandleFunc` adapts a function.
- `Routes()` returns an `http.Handler` ready for Server and for `httptest`.

**Predict, then answer.** Why `Handle("GET /greet", API{…})` and not `HandleFunc`?

> **Answer:** `API` is not `func(ResponseWriter,*Request)` — it is a struct that already implements `Handler` via the method `ServeHTTP`.

### Example 3 — Wildcard route and PathValue

```go
package main

import (
	"fmt"
	"log"
	"net/http"
	"time"
)

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /products/{id}", func(w http.ResponseWriter, r *http.Request) {
		id := r.PathValue("id")
		fmt.Fprintf(w, "product=%s\n", id)
	})
	mux.HandleFunc("GET /files/{$}", func(w http.ResponseWriter, r *http.Request) {
		rest := r.PathValue("$")
		fmt.Fprintf(w, "file=%s\n", rest)
	})

	srv := &http.Server{
		Addr:              ":8080",
		Handler:           mux,
		ReadHeaderTimeout: 5 * time.Second,
	}
	log.Fatal(srv.ListenAndServe())
}
```

#### What happens here

- `{id}` captures exactly one segment (`/products/abc` → `abc`).
- `{$}` captures the rest (`/files/a/b/c` → `a/b/c`).
- Format validation of the id is not here — that is 05.02.

**Predict, then answer.** Request `GET /products/10/details`. Which handler?

> **Answer:** Neither of these two for products — `{id}` does not consume `10/details`. The response is 404 (unless you add another pattern).

### Example 4 — Middleware chain (log + auth), next optional

```go
package httpapi

import (
	"log"
	"net/http"
	"time"
)

func withLog(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		start := time.Now()
		next.ServeHTTP(w, r)
		log.Printf("%s %s %s", r.Method, r.URL.Path, time.Since(start))
	})
}

func withAuth(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		if r.Header.Get("X-Token") != "secret" {
			http.Error(w, "unauthorized", http.StatusUnauthorized)
			return // next is NOT called
		}
		next.ServeHTTP(w, r)
	})
}

func Routes() http.Handler {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /private", func(w http.ResponseWriter, r *http.Request) {
		_, _ = w.Write([]byte("ok"))
	})
	return withLog(withAuth(mux))
}
```

#### What happens here

- Onion: log outside, auth inside (or reverse — choose consciously).
- Without `X-Token: secret` → 401, the inner handler does not run.
- `withLog` still measures time because it calls `next` (which is the auth wrapper).

**Predict, then answer.** Order `withAuth(withLog(mux))`, wrong token. Does the log line after `next` still print?

> **Answer:** No — with `withAuth(withLog(mux))` auth is outside; without a token it does not call `next`, so the log middleware never runs at all. With `withLog(withAuth(mux))` log always enters, calls auth as `next`, then logs even after 401. Order changes what you observe.

### Example 5 — Thin main, Routes, httptest motivation

```go
// internal/httpapi/routes.go
package httpapi

import "net/http"

func healthz(w http.ResponseWriter, r *http.Request) {
	w.WriteHeader(http.StatusOK)
	_, _ = w.Write([]byte("ok"))
}

func Routes() http.Handler {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /healthz", healthz)
	mux.HandleFunc("GET /readyz", func(w http.ResponseWriter, r *http.Request) {
		// dependency ping would go here; for now always ready
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte("ready"))
	})
	return mux
}
```

```go
// cmd/shop/main.go
package main

import (
	"log"
	"net/http"
	"time"

	"example.com/shop/internal/httpapi"
)

func main() {
	srv := &http.Server{
		Addr:              ":8080",
		Handler:           httpapi.Routes(),

		ReadTimeout:       10 * time.Second,
		WriteTimeout:      15 * time.Second,
		IdleTimeout:       60 * time.Second,
		MaxHeaderBytes:    1 << 20, // 1 MiB
	}
	log.Fatal(srv.ListenAndServe())
}
```

```go
// internal/httpapi/routes_test.go
package httpapi_test

import (
	"net/http"
	"net/http/httptest"
	"testing"

	"example.com/shop/internal/httpapi"
)

func TestHealthz(t *testing.T) {
	req := httptest.NewRequest(http.MethodGet, "/healthz", nil)
	rec := httptest.NewRecorder()
	httpapi.Routes().ServeHTTP(rec, req)
	if rec.Code != 200 {
		t.Fatalf("got %d", rec.Code)
	}
}

func TestHelloMethodNotAllowed(t *testing.T) {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /hello", func(w http.ResponseWriter, r *http.Request) {
		_, _ = w.Write([]byte("hi"))
	})
	req := httptest.NewRequest(http.MethodPost, "/hello", nil)
	rec := httptest.NewRecorder()
	mux.ServeHTTP(rec, req)
	if rec.Code != http.StatusMethodNotAllowed {
		t.Fatalf("got %d want 405", rec.Code)
	}
}
```

#### What happens here

- `main` has no routes — only Server fields.
- `httptest` calls `ServeHTTP` directly — motivation for `Routes()`.
- The second test proves 405 without starting a port.
- `MaxHeaderBytes` set explicitly along with timeouts.

### Example 6 — Graceful Shutdown sketch

```go
package main

import (
	"context"
	"log"
	"net/http"
	"os"
	"os/signal"
	"syscall"
	"time"

	"example.com/shop/internal/httpapi"
)

func main() {
	srv := &http.Server{
		Addr:              ":8080",
		Handler:           httpapi.Routes(),
		ReadHeaderTimeout: 5 * time.Second,
	}

	go func() {
		log.Println("listening", srv.Addr)
		err := srv.ListenAndServe()
		if err != nil && err != http.ErrServerClosed {
			log.Fatal(err)
		}
	}()

	stop := make(chan os.Signal, 1)
	signal.Notify(stop, os.Interrupt, syscall.SIGTERM)
	<-stop
	log.Println("shutting down")

	ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()
	if err := srv.Shutdown(ctx); err != nil {
		log.Printf("shutdown error: %v", err)
	}
}
```

#### What happens here

- Listen in a goroutine so main can wait for a signal.
- `Shutdown` closes the entrance; waits for active requests up to 10s.
- `ErrServerClosed` is not fatal — expected outcome.

**Predict, then answer.** Why `make(chan os.Signal, 1)` (buffer 1)?

> **Answer:** So the signal is not lost if it arrives before the receiver reads (documented idiom for `signal.Notify`).

## Decision analysis

| Decision | Alternative | Why this way |
|----------|-------------|--------------|
| `http.Server` struct | `http.ListenAndServe` | Shutdown, timeout fields, MaxHeaderBytes |
| ServeMux 1.22 patterns | Manual `if r.Method` | Fewer branches, 405 from the mux |
| Local `NewServeMux` | DefaultServeMux | No global state |
| `Routes() http.Handler` | Routes in main | httptest, thin main |
| Handler struct | Functions only | Dependency injection |
| Middleware HOF | Global hooks | Testable, composable |
| Separate healthz/readyz | One “status” | Correct orchestrator behavior |

## Trade-offs

- **Stdlib ServeMux vs chi/gin/echo:** stdlib 1.22 covers method+path+wildcard for most CRUD APIs. A third-party router when you need a richer middleware ecosystem or more advanced routing — not in advance.
- **ReadTimeout vs large upload:** too short a ReadTimeout cuts legitimate slower uploads; too long holds connections. Tune per endpoint or use a reverse proxy limit + sufficient ReadTimeout.
- **WriteTimeout vs streaming/SSE:** WriteTimeout can cut long streams. For SSE you often need a different model or a larger/zero WriteTimeout with another idle mechanism.
- **Too much micro-middleware:** each layer adds indirection. Group (e.g. one `withObservability`) until it hurts.
- **Graceful timeout 10s:** too short kills long requests on deploy; too long slows rolling update. Align with orchestrator `terminationGracePeriod`.

## Common mistakes

1. **Route without an HTTP method** — POST falls into the same handler; later you forget the check.
2. **`ListenAndServe(":8080", nil)`** — DefaultServeMux, confusing tests and collisions.
3. **No ReadHeaderTimeout** — open to slow header attack/load.
4. **Business logic in `main`** — no unit test of routes.
5. **Ignoring the error from ListenAndServe** — silent fail on bind in some setups.
6. **Collision / overly broad pattern** — catch-all swallows specific routes; discovered late.
7. **Middleware always calls next** — auth “lets through” and then writes 401 after the handler (too late, often after a side effect).
8. **Mixing healthz and readyz** — DB restart kills pods instead of temporarily removing them from the LB.
9. **Bare ListenAndServe then “add Shutdown later”** — the refactor hurts; start with `*http.Server`.
10. **Manually killing mux 405** in every handler — duplication and inconsistency.

## Idiomatic Go

- `http.Handler` / `http.HandlerFunc` duo — official adapter pattern.
- Middleware: `func(http.Handler) http.Handler`.
- Go 1.22+ release notes / `ServeMux` docs for patterns — source of truth.
- `httptest.NewRequest` + `httptest.ResponseRecorder` + `ServeHTTP`.
- Constants `http.MethodGet`, `http.StatusOK` instead of magic strings/numbers where readability helps.
- Package `internal/httpapi` (or `internal/server`) for the HTTP layer; `cmd/...` only starts.

## Practical scenario

The team has an old service: every handler starts with `if r.Method != http.MethodPost { … }`. Two production bugs: (1) one handler forgot the check — GET deleted a resource; (2) a load test held thousands of half-open connections because there was no ReadHeaderTimeout.

Migration:

1. Move to `"POST /orders"`, `"GET /orders/{id}"` — mux returns 405, copy-paste HTTP method checks disappear.
2. Introduce `*http.Server` with timeouts — scans no longer hold workers forever.
3. `Routes()` + `httptest` route table — CI catches 405/404 regressions.
4. Separate `/healthz` (always ok) and `/readyz` (Ping DB) — a DB deploy no longer restarts every pod.
5. Middleware `withLog(withAuth(mux))` — auth does not call next on fail; the audit log still sees rejections because log is outside.

Result: fewer branches, measurable hardening, tests without a port.

## Check questions

1. **What is `http.Handler`?**  
   An `interface` with method `ServeHTTP(ResponseWriter, *Request)`.

2. **What is `HandlerFunc` for?**  
   Adapts an ordinary function into a `Handler` (has a method `ServeHTTP` that calls that function).

3. **What does Go 1.22 `ServeMux` bring that is new?**  
   Patterns with an HTTP method, wildcards `{name}` and `{$}`, plus `Request.PathValue`.

4. **Why `ReadHeaderTimeout`?**  
   Cuts connections that slowly or never finish sending headers (basic protection against slowloris style).

5. **When does `IdleTimeout` fire?**  
   A keep-alive connection is idle between requests longer than the set time.

6. **Why not `DefaultServeMux` in a library?**  
   Global state, route collisions, hard tests — a library should return or fill a passed-in mux/Handler.

7. **Why `Routes() http.Handler`?**  
   Thin main + unit test via `httptest` without a TCP port.

8. **Must middleware call `next`?**  
   No — e.g. auth can return 401 and break the chain.

9. **404 vs 405 — who returns what?**  
   Unknown path → 404; known path wrong HTTP method → 405 (mux). Non-existent domain entity → 404 from the handler.

10. **What does `Shutdown(ctx)` do?**  
    Stops accepting new connections and waits for active requests to finish until the context expires.

## Summary

Foundation of web services in Go: **`http.Server`** (timeouts, MaxHeaderBytes, Shutdown) + **`ServeMux` 1.22** (method+path, `{id}`, `{$}`, PathValue) + **`Handler`/`HandlerFunc`** + **middleware** as a higher-order function (onion, next optional) + **thin main / `Routes()`** for **`httptest`**. No DefaultServeMux in lib. Separate healthz from readyz. You now have a skeleton that 05.02 hangs JSON, status codes, and input validation on.
