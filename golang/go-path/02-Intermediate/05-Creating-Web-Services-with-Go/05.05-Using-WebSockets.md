# 05.05 WebSocket in Go: upgrade, Hub pattern, deadlines, one read/write goroutine

> **Go Path - Zero to Gopher** / **02 Intermediate → Creating Web Services with Go** / Lesson 05.05

## Lesson goals

After this lesson you can:

- explain WebSocket as an **HTTP upgrade** to a long-lived bidirectional connection (status 101);
- use **`github.com/gorilla/websocket`**: `Upgrader`, `Upgrade`, `ReadMessage`, `WriteMessage`, `SetReadLimit`, `SetReadDeadline`, `SetWriteDeadline`, `SetPongHandler`, `PingMessage`, `CloseMessage`;
- follow the rule **one writer per connection** — do not share `Conn` write across goroutines without a mutex **or** (better) one write goroutine + channel;
- implement the **Hub** pattern (register / unregister / broadcast);
- separate **readPump** and **writePump**;
- set **`CheckOrigin`** consciously (risk awareness, without attack procedures);
- set **`SetReadLimit`** to limit message size.

## Prerequisite

- 05.01–05.02: HTTP handlers, `ResponseWriter`, `Request`.
- Basic **goroutine** and **channel** (select, buffered channel).
- Understanding that a TCP connection is long-lived — not request/response like REST.

This lesson uses **gorilla/websocket** as the teaching API. Other libraries exist; the principles (one writer, deadlines, origin, limit) remain.

## Problem this lesson solves

Realtime “over REST” often ends as:

- endless long-poll / short polling every 1–2s → DB and CPU burn;
- parallel `WriteMessage` on the same `*websocket.Conn` from multiple goroutines → **corrupted frames**;
- without read/write deadlines → **zombie** connections hold memory and file descriptors;
- broadcast without a Hub → each handler holds its own client list with a data race;
- `CheckOrigin: return true` in production with cookie sessions → unwanted cross-site connections (awareness, not a recipe).

The lesson gives a correct introductory pattern: upgrade → Client → readPump/writePump → Hub.

## Mental model

1. The client sends an HTTP request with WebSocket headers (`Upgrade: websocket`, …).
2. The server via `Upgrader.Upgrade` responds **101 Switching Protocols** and keeps the TCP connection.
3. Further goes a **frame** protocol (text/binary/ping/pong/close), not a new HTTP request per message.
4. The **Hub** holds the set of clients and fans out messages through channels.
5. Per connection: **readPump** (one goroutine reads) + **writePump** (one goroutine writes from a `send` channel).
6. Deadlines + ping/pong discover dead peers.
7. `SetReadLimit` protects memory from huge frames.

```text
Browser ──HTTP Upgrade──► Upgrader.Upgrade
                              │
                              ▼
                           Client
                          /      \
                   readPump      writePump
                      │              ▲
                      ▼              │
                   Hub.broadcast   send channel
                      │
                      └──► other Client.send
```

## Mechanism

### HTTP upgrade

An ordinary handler looks “like HTTP”, but after a successful `Upgrade` you no longer write JSON over the same stream as in a REST handler — you use the WebSocket API on `*websocket.Conn`.

```go
var upgrader = websocket.Upgrader{
	ReadBufferSize:  1024,
	WriteBufferSize: 1024,
	CheckOrigin: func(r *http.Request) bool {
		// production: compare Origin against a host allowlist
		return true // local demo only
	},
}

conn, err := upgrader.Upgrade(w, r, nil)
```

`Upgrade` internally writes the 101 response. If it returns an error, do **not** call `http.Error` again on the same `w` — the response may already have started.

### Trace 1 — echo in one goroutine

```text
GET /echo (+ WS headers)
  → Upgrade OK
  → loop: ReadMessage → WriteMessage
  → read/write error → Close
```

For echo, sequential read+write in **one** goroutine is correct — no parallel write. As soon as you add broadcast / timer ping from another goroutine, you need writePump or a mutex.

### Predict, then answer — two WriteMessage

**Question.** `go writeA(conn)` and `go writeB(conn)` both call `WriteMessage` without a mutex. What do you expect under load?

**Answer.** Interleaved frames, corrupted protocol, errors on the peer. gorilla docs: concurrent write is not safe without synchronization. Solution: **one writer** (writePump + `send` channel) or `sync.Mutex` around every write (weaker ergonomics with ping).

### One writer per connection

Two idiomatic patterns:

1. **Single writer goroutine** (course recommendation): all messages and ping go through `send` / ticker in `writePump`.
2. **Mutex** around every `WriteMessage` / `WriteControl`: works, but easier to forget ping/close paths.

Read side: usually **one** read goroutine (`ReadMessage` loop). Do not start two read loops on the same conn.

### Hub pattern

The Hub serializes mutations of the client set:

- `register` channel ← new Client
- `unregister` channel ← deregistration
- `broadcast` channel ← message for everyone

One Hub goroutine in `Run()` `select`s those channels. That avoids a race on `map[*Client]struct{}` without lightning locking everywhere (examples often still have a mutex — what matters is **one owner** of membership logic).

### Trace 2 — chat message

```text
Client A readPump reads frame
  → hub.broadcast <- msg
  → Hub.Run sends to each c.send
  → Client B/C writePump WriteMessage
```

Slow client: `send` buffer full → Hub takes the `default` branch (drop + unregister) instead of blocking the whole fan-out.

### readPump

Responsibilities:

1. `SetReadLimit(n)` — max message size.
2. `SetReadDeadline` — if no read/pong by the deadline, read fails.
3. `SetPongHandler` — on pong renew the read deadline.
4. Loop `ReadMessage`; success → forward to Hub; error → unregister + `Close`.

### writePump

Responsibilities:

1. Wait on the `send` channel or ping `ticker`.
2. Before write: `SetWriteDeadline`.
3. If `send` is closed (`!ok`) → `WriteMessage(CloseMessage, ...)` and exit.
4. Otherwise `WriteMessage(TextMessage, msg)` or binary by agreement.
5. On ticker: `WriteMessage(PingMessage, nil)`.

### Trace 3 — dead peer

```text
writePump sends PingMessage
  → peer does not send pong
  → read deadline expires
  → readPump ReadMessage err
  → unregister + Close
  → writePump sees closed send / write err → exit
```

Without a ping/deadline loop, a dead mobile network holds the Client in the Hub map for hours.

### Predict, then answer — forgotten Hub.Run

**Question.** `hub := NewHub()`; handlers send to `hub.register`, but nobody calls `go hub.Run()`. What happens?

**Answer.** Register/broadcast block on an unbuffered channel (or fill the buffer then block). Connections “hang”. Always `go hub.Run()` at startup.

### Predict, then answer — WriteTimeout of the HTTP server

**Question.** `http.Server{WriteTimeout: 15 * time.Second}` and a WebSocket that lives for minutes. What can go wrong?

**Answer.** Some servers apply WriteTimeout to hijacked connections depending on version/settings — a long-lived WS may be cut. In practice: put WS on a mux/server without an aggressive WriteTimeout, or check your stack’s docs. Still leave ReadHeaderTimeout for Slowloris defense on the HTTP entrance.

### CheckOrigin — awareness

`CheckOrigin` decides whether Upgrade may continue based on the `Origin` header.

- Local demo: often `return true` with a comment that this is **not** production.
- Production with cookie auth on the same site: allowlist known front origins (exact scheme+host+port).
- Public API with a token in the first frame / header: still think about the team’s origin policy.

This lesson does **not** give attack steps; only: do not blindly `return true` in production without a reason.

### SetReadLimit

```go
c.conn.SetReadLimit(4096) // bytes
```

A message over the limit → read error → Close the connection. Without a limit, a huge frame consumes memory.

### Predict, then answer — limit

**Question.** Limit 4096, the client sends 10_000 bytes of text. What does readPump do?

**Answer.** `ReadMessage` returns an error; defer unregister/Close. That is desired fail-closed behavior.

### Gorilla API — concept map

| API | Role |
|-----|------|
| `Upgrader` | settings + `Upgrade` |
| `Upgrade` | HTTP → `*Conn` |
| `ReadMessage` | read the next data frame |
| `WriteMessage` | write data/control (with writer discipline) |
| `SetReadLimit` | max size |
| `SetReadDeadline` / `SetWriteDeadline` | anti-zombie |
| `SetPongHandler` | renew read deadline on pong |
| `PingMessage` / `CloseMessage` | frame type constants |

### Auth note (defense)

A token in the query string leaks into logs. Prefer a same-origin cookie policy, or a first frame with a token after Upgrade, with TLS. Auth scheme details are outside the introductory Hub focus — do not put secrets in the URL without awareness of logs.

## Rules and syntax

1. After an `Upgrade` error — do not naively write another HTTP response on the same `w`.
2. **One writer** per `Conn`: writePump or mutex.
3. **One reader** per `Conn`: readPump.
4. Always unregister + `Close` on exit.
5. `CheckOrigin` in production is not “always true” without a reason.
6. `SetReadLimit` mandatory for public endpoints.
7. Read/write deadlines + ping period < pong wait.
8. `go hub.Run()` once at startup.
9. Do not share the same `Conn` across Hubs / handlers ad hoc.
10. Buffer of the `send` channel: too small → drop; too large → memory — measure.

```go
const (

	pongWait   = 60 * time.Second
	pingPeriod = (pongWait * 9) / 10
)
```

## Examples

### Example 1 — Upgrade + echo

```go
package main

import (
	"log"
	"net/http"

	"github.com/gorilla/websocket"
)

var upgrader = websocket.Upgrader{
	ReadBufferSize:  1024,
	WriteBufferSize: 1024,
	CheckOrigin: func(r *http.Request) bool {
		// illustration: in production check an Origin allowlist
		return true
	},
}

func echo(w http.ResponseWriter, r *http.Request) {
	c, err := upgrader.Upgrade(w, r, nil)
	if err != nil {
		log.Println("upgrade:", err)
		return
	}
	defer c.Close()

	c.SetReadLimit(4096)
	for {
		mt, msg, err := c.ReadMessage()
		if err != nil {
			break
		}
		if err := c.WriteMessage(mt, msg); err != nil {
			break
		}
	}
}

func main() {
	http.HandleFunc("GET /echo", echo)
	log.Fatal(http.ListenAndServe(":8080", nil))
}
```

#### What happens here

HTTP GET `/echo` becomes a WebSocket. The loop reads and writes **sequentially** in one goroutine — OK for echo. `SetReadLimit` protects memory. For broadcast you need a Hub and separate pumps.

### Example 2 — Hub

```go
package ws

type Hub struct {
	clients    map[*Client]struct{}
	broadcast  chan []byte
	register   chan *Client
	unregister chan *Client
}

func NewHub() *Hub {
	return &Hub{
		clients:    make(map[*Client]struct{}),
		broadcast:  make(chan []byte, 64),
		register:   make(chan *Client),
		unregister: make(chan *Client),
	}
}

func (h *Hub) Run() {
	for {
		select {
		case c := <-h.register:
			h.clients[c] = struct{}{}
		case c := <-h.unregister:
			if _, ok := h.clients[c]; ok {
				delete(h.clients, c)
				close(c.send)
			}
		case msg := <-h.broadcast:
			for c := range h.clients {
				select {
				case c.send <- msg:
				default:
					close(c.send)
					delete(h.clients, c)
				}
			}
		}
	}
}
```

#### What happens here

One Hub goroutine serializes register/unregister/broadcast. Slow clients (full `send`) drop out instead of blocking everyone. `close(c.send)` signals writePump to end.

### Example 3 — Client: readPump / writePump

```go
package ws

import (
	"net/http"
	"time"

	"github.com/gorilla/websocket"
)

const (
	writeWait  = 10 * time.Second
	pongWait   = 60 * time.Second
	pingPeriod = (pongWait * 9) / 10
)

type Client struct {
	hub  *Hub
	conn *websocket.Conn
	send chan []byte
}

var upgrader = websocket.Upgrader{
	ReadBufferSize:  1024,
	WriteBufferSize: 1024,
	CheckOrigin: func(r *http.Request) bool {
		return true // demo; production: allowlist
	},
}

func ServeWS(hub *Hub, w http.ResponseWriter, r *http.Request) {
	conn, err := upgrader.Upgrade(w, r, nil)
	if err != nil {
		return
	}
	c := &Client{hub: hub, conn: conn, send: make(chan []byte, 16)}
	hub.register <- c
	go c.writePump()
	go c.readPump()
}

func (c *Client) readPump() {
	defer func() {
		c.hub.unregister <- c
		c.conn.Close()
	}()
	c.conn.SetReadLimit(4096)
	_ = c.conn.SetReadDeadline(time.Now().Add(pongWait))
	c.conn.SetPongHandler(func(string) error {
		return c.conn.SetReadDeadline(time.Now().Add(pongWait))
	})
	for {
		_, msg, err := c.conn.ReadMessage()
		if err != nil {
			break
		}
		c.hub.broadcast <- msg
	}
}

func (c *Client) writePump() {
	ticker := time.NewTicker(pingPeriod)
	defer func() {
		ticker.Stop()
		c.conn.Close()
	}()
	for {
		select {
		case msg, ok := <-c.send:
			_ = c.conn.SetWriteDeadline(time.Now().Add(writeWait))
			if !ok {
				_ = c.conn.WriteMessage(websocket.CloseMessage, []byte{})
				return
			}
			if err := c.conn.WriteMessage(websocket.TextMessage, msg); err != nil {
				return
			}
		case <-ticker.C:
			_ = c.conn.SetWriteDeadline(time.Now().Add(writeWait))
			if err := c.conn.WriteMessage(websocket.PingMessage, nil); err != nil {
				return
			}
		}
	}
}
```

#### What happens here

**One** readPump reads; **one** writePump writes (messages + ping). Deadlines renew on pong/write. Unregister on reader exit closes `send` (in the Hub) and stops the writer.

### Example 4 — main wiring

```go
package main

import (
	"log"
	"net/http"

	"example.com/shop/internal/ws"
)

func main() {
	hub := ws.NewHub()
	go hub.Run()
	http.HandleFunc("GET /ws", func(w http.ResponseWriter, r *http.Request) {
		ws.ServeWS(hub, w, r)
	})
	log.Fatal(http.ListenAndServe(":8080", nil))
}
```

#### What happens here

The Hub lives for the whole process lifetime. Each upgrade creates a Client and two goroutines. Broadcast goes through the hub channel.

### Example 5 — WRONG: parallel Write

```go
// WRONG
go func() { _ = conn.WriteMessage(websocket.TextMessage, a) }()
go func() { _ = conn.WriteMessage(websocket.TextMessage, b) }()

// CORRECT — both send to c.send; writePump alone writes
c.send <- a
c.send <- b
```

#### What happens here

Without synchronization, frames interleave. Channel + one write goroutine is the simplest correct discipline.

### Example 6 — CheckOrigin with allowlist (defensive)

```go
var allowed = map[string]bool{
	"http://localhost:3000": true,
	"https://shop.example":  true,
}

var upgrader = websocket.Upgrader{
	CheckOrigin: func(r *http.Request) bool {
		origin := r.Header.Get("Origin")
		return allowed[origin]
	},
}
```

#### What happens here

Upgrade passes only for known Origin values. Empty Origin: team decision (some clients do not send it) — document. This is not a bypass guide; it is **narrowing** the entrance.

### Example 7 — SetReadLimit behavior in a test (conceptual)

```go
// In integration / manually:
// 1) SetReadLimit(64)
// 2) send a text frame longer than 64 bytes
// 3) expect connection break / error on the read side
```

#### What happens here

The limit is fail-closed. In team docs record that the max application protocol size ≤ the limit.

### Example 8 — application protocol (JSON text)

```go
type Envelope struct {
	Type string `json:"type"`
	Body string `json:"body"`
}
```

Agreement:

1. Text frame = JSON `Envelope`
2. Max body per `SetReadLimit`
3. Unknown `Type` → ignore or close (agreement)
4. Auth before or right after upgrade (no secrets in the access log URL)

#### What happens here

The Hub still fans out bytes; message meaning lives in the app layer. Without an agreement you only have echo/chat of bytes.

### Example 9 — mutex alternative (shorter)

```go
var mu sync.Mutex

func write(conn *websocket.Conn, mt int, data []byte) error {
	mu.Lock()
	defer mu.Unlock()
	_ = conn.SetWriteDeadline(time.Now().Add(writeWait))
	return conn.WriteMessage(mt, data)
}
```

#### What happens here

The mutex serializes write. Both ping and close must go through the same `write`. WritePump + channel remains more readable for a chat Hub.

## Decision analysis

| Decision | Motive | Alternative |
|----------|--------|-------------|
| gorilla/websocket | Mature API, Hub examples | coder/websocket, x/net |
| Hub + channel | Fan-out without a race | List in every handler |
| read/write pump | Respect concurrency rules | Everything in one loop (echo only) |
| Deadlines + ping | Clean dead connections | Only TCP keepalive hopes |
| SetReadLimit | Memory defense | Unlimited frame |
| CheckOrigin consciously | Narrow cross-site WS | Always true |

## Trade-offs

- Stdlib has no full WebSocket server API — a third-party dependency is expected.
- `send` buffer: too small → drop clients; too large → RAM.
- One-process Hub does not scale to multiple instances — later Redis/NATS pubsub; pump principles remain.
- Text vs binary frame — protocol agreement.
- Mutex vs writePump — mutex shorter for a micro service; pump clearer for chat.

## Common mistakes

1. **Write from multiple goroutines** without mutex/pump.
2. **`CheckOrigin` always true** in production with a cookie session without a reason.
3. **No unregister** — leaking the client map.
4. **No `SetReadLimit`** — huge frame.
5. **Forgotten `go hub.Run()`**.
6. **Ping without PongHandler / read deadline** — zombie or false timeout.
7. **Another HTTP write after a failed Upgrade**.
8. **Token in query** with detailed access logs.
9. **Same Conn in two Hubs**.
10. **Mixing REST JSON middleware** with a WS handler that already Upgrades.

## Idiomatic Go

- Copy (with understanding) the gorilla chat pattern, then adapt.
- Channel for fan-in/fan-out; one Hub goroutine as map owner.
- `defer` Close in the pumps; unregister exactly once (avoid double-close of `send` — the Hub closes).
- Graceful shutdown (more advanced): close register; unregister all clients.

## Practical scenario

A live auction board polls every 2s — DB QPS burns. Moving to WS + Hub reduces HTTP request count. The first deploy without writePump discipline corrupts messages under load (two goroutines write prices). After pump + ping, mobile clients stay in sync, dead connections leave the map. Origin allowlist admits only the known front.

## Multi-instance note

One Hub in one process does not see clients on another machine. For horizontal scaling: external pubsub; each instance still holds local Conn + writePump. Do not “fix” that by sharing `*Conn` over the network.

## Predict, then answer — close send twice

**Question.** Both readPump and Hub call `close(c.send)`. What happens?

**Answer.** Panic on the second `close`. Discipline: the **Hub** closes `send` on unregister; writePump only reads `!ok`. readPump sends unregister, does not close `send` itself.

## Example 10 — local CheckOrigin helper

```go
func allowOrigins(list ...string) func(*http.Request) bool {
	set := make(map[string]bool, len(list))
	for _, o := range list {
		set[o] = true
	}
	return func(r *http.Request) bool {
		return set[r.Header.Get("Origin")]
	}
}

// upgrader.CheckOrigin = allowOrigins("http://localhost:3000", "https://shop.example")
```

#### What happens here

The allowlist is explicit. Lazy `return true` is no longer the default. Empty Origin → false (strict); if you need an exception for non-browser clients, document it separately.

## Backpressure and send buffer size

```go
send: make(chan []byte, 16)
```

- Small (1–4): quickly drop slow clients — good for “only the latest”.
- Medium (16–64): tolerates short stalls.
- Large (thousands): holds old messages in RAM — dangerous under slow clients.

The Hub `default` branch when the buffer is full is an intentional trade-off: sacrifice the slow client, save the others.

## TextMessage vs BinaryMessage

```go
_ = conn.WriteMessage(websocket.TextMessage, []byte(`{"type":"tick"}`))
_ = conn.WriteMessage(websocket.BinaryMessage, rawProtobuf)
```

Mix only if the protocol allows it. A readPump that always does `broadcast <- msg` does not interpret type — if needed, forward `messageType` too.

## Shutdown sketch (intro)

On SIGTERM:

1. Stop accepting new Upgrades (health fail / close listener).
2. Send CloseMessage through writePump to every Client.
3. Wait briefly; then `Close` remaining Conn.
4. Exit `Hub.Run` (more advanced: `done` channel in select).

Detailed orchestration depends on the process model — what matters is not leaving goroutines forever blocked on `ReadMessage`.

## Comparison with a REST handler

| REST | WebSocket |
|------|-----------|
| Short request | Long connection |
| One response | Many frames |
| `r.Context()` cancel common | Conn lifecycle + ping |
| Easy httptest | Need dial or echo loop |
| JSON encoder | ReadMessage/WriteMessage |

Do not push WS where REST + SSE/polling suffice — WS when you need low-latency bidirectional.

## Proxy and idle timeout

A load balancer or reverse proxy often cuts idle TCP. If the idle limit is 60s, and `pingPeriod` is 54s (with `pongWait` 60s), you stay under the threshold. If ping is rare, “random disconnect” in production. Align ping with infrastructure.

## Predict, then answer — broadcast blocks

**Question.** The Hub does `c.send <- msg` without `select/default`, and one client does not read. What happens?

**Answer.** The Hub goroutine blocks on that client; nobody else gets register/broadcast. That is why the example uses `select` + `default` (drop the slow one).

## Upgrader buffer sizes

`ReadBufferSize` / `WriteBufferSize` on `Upgrader` set the Conn’s internal buffers. Too small → more syscalls; too large → RAM per connection. For chat text 1024 is a common start; measure under real payload.

## What to log

Log: successful/failed Upgrade (without the whole Origin as a secret if not needed), unregister reason (read err), active client count (metric). Do not log the full content of every message in production (PII, volume).

## Connection teardown diagram

```text
read err / limit / deadline
  → readPump defer: unregister + Conn.Close
  → Hub: delete client, close(send)
  → writePump: !ok on send → CloseMessage → return
  → defer: ticker.Stop + Conn.Close
```

Double `Close` on Conn is practically tolerable (more idempotent than double-close of a channel); double-close on `send` is a panic — so only the Hub closes `send`.

## Messages larger than the limit — app layer

If the protocol needs large payloads, do not blindly raise `SetReadLimit` to megabytes. Chunk, or move large transfer to HTTP upload + WS only for the signal. WS is not a substitute for object storage.

## API surface recap (gorilla)

Remember this set for the next exercise without looking at the docs:

`Upgrader` → `Upgrade` → `SetReadLimit` → `SetReadDeadline` / `SetPongHandler` → `ReadMessage` in readPump; `SetWriteDeadline` → `WriteMessage` (`TextMessage` / `PingMessage` / `CloseMessage`) in writePump.

If you remember only one rule: **one writer per Conn** — the rest follows.

## Summary

WebSocket = HTTP **upgrade** + long-lived connection. With **gorilla/websocket**: Upgrade, pumps, Hub, deadlines, ping/pong, `SetReadLimit`. **One writer** per connection. `CheckOrigin` consciously. The realtime layer starts with connection discipline, not just “open a socket”.
