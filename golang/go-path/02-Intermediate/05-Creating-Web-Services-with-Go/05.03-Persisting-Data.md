# 05.03 Persistence behind HTTP: repository, database/sql, context cancel

> **Go Path - Zero to Gopher** / **02 Intermediate → Creating Web Services with Go** / Lesson 05.03

## Lesson goals

After this lesson you can:

- connect HTTP handlers to a **repository interface** (a data store behind a contract);
- keep `database/sql` **behind** the store implementation, never in the handler;
- always pass `r.Context()` through to `QueryContext` / `ExecContext` / `QueryRowContext`;
- map `sql.ErrNoRows` to domain `ErrNotFound`, then to HTTP 404;
- test handlers with a **fake store** + `httptest` without a real database;
- do **wiring** in `main`: the pool (`*sql.DB`) lives there; the handler receives only an interface;
- write SQL with placeholders — **never** concatenate `PathValue` into a query.

## Prerequisite

- Lessons 03.x on `database/sql` (opening a pool, `Query`/`Exec`, scanning rows).
- Lessons 05.01–05.02: `ServeMux`, handlers, JSON, mapping errors to status.
- Understanding `interface` types and injecting dependencies into a `struct` field.
- Basic `context.Context`: cancel, deadline, `errors.Is`.

If you have not yet seen `r.PathValue` (Go 1.22+), briefly: a named path segment from the route pattern, e.g. `"GET /products/{id}"` → `r.PathValue("id")`.

## Problem this lesson solves

A typical “fast” handler opens SQL directly:

```go
func GetProduct(w http.ResponseWriter, r *http.Request) {
	db, _ := sql.Open("pgx", os.Getenv("DATABASE_URL")) // bad: new pool per request
	row := db.QueryRow(`SELECT ... WHERE id = '` + r.PathValue("id") + `'`) // bad: SQL inject
	// ...
}
```

Consequences:

1. **No unit test** without a live database — CI slow, unstable, expensive.
2. `context.Background()` on the request path **ignores** client cancellation; the pool drains because the query still holds a connection.
3. SQL and HTTP mix — you change the schema, you break handlers; you change status codes, you touch SQL.
4. Concatenating input into SQL = a hole (here we learn **defense**: placeholders).

The lesson introduces a boundary: the handler knows HTTP; the store knows SQL; `main` joins them.

## Mental model

```text
  client HTTP
       │
       ▼
  Handler (JSON, status, PathValue)
       │  r.Context() + domain call
       ▼
  Store interface  ──────►  fake store (map in memory) in the test
       │
       ▼
  PG / SQLite implementation
       │  QueryContext / ExecContext
       ▼
  *sql.DB (pool in main)
       │
       ▼
  database
```

Four rules of the mental model:

1. **Handler** knows HTTP and DTOs (JSON in/out), does not know about `*sql.DB`.
2. **Store** knows SQL and the domain model; returns domain errors, not raw `sql.ErrNoRows` to the handler.
3. **Context** flows from `*http.Request` to `QueryContext` — cancel closes waiting on the database.
4. **Wiring** is the only place where `*sql.DB` and HTTP meet (`main` or composition root).

## Mechanism

### From request to a row in the database

Step by step, for `GET /products/abc`:

1. `ServeMux` calls `ProductHandlers.Get`.
2. The handler takes `id := r.PathValue("id")` and calls `h.Store.Get(r.Context(), id)`.
3. `PG.Get` calls `db.QueryRowContext(ctx, sql, id)`.
4. If the driver/database sees that `ctx` is canceled, the query stops (or an error arrives quickly).
5. `Scan` fills `Product`; or `err == sql.ErrNoRows`.
6. Store: `errors.Is(err, sql.ErrNoRows)` → return `ErrNotFound`.
7. Handler: `errors.Is(err, ErrNotFound)` → `404`; otherwise `500` (without leaking the SQL message to the client).

### Trace 1 — successful Get

```text
Request GET /products/p1
  → Handler.Get
  → Store.Get(ctx, "p1")
  → QueryRowContext → Scan OK
  → Product{ID:"p1", ...}
  → 200 + JSON
```

### Trace 2 — no row

```text
Request GET /products/x
  → Store.Get
  → sql.ErrNoRows
  → ErrNotFound
  → Handler → 404
```

### Trace 3 — client abandons mid-query

```text
Request GET /products/p1
  → ctx = r.Context()
  → client closes TCP / timeout middleware cancels ctx
  → QueryRowContext returns ctx.Err() (often wrapped)
  → Handler → 503 or 504 (team agreement), pool connection is released
```

### Predict, then answer — what does the handler “see”?

**Question.** The store does this:

```go
if errors.Is(err, sql.ErrNoRows) {
	return Product{}, fmt.Errorf("get: %w", err) // wrap sql.ErrNoRows, without ErrNotFound
}
```

The handler checks only `catalog.ErrNotFound`. Which status does the client get?

**Answer.** Probably **500**, because `errors.Is(err, ErrNotFound)` is false, and `sql.ErrNoRows` was not mapped to the domain. So the store **must** explicitly translate `sql.ErrNoRows` into `ErrNotFound` (or another agreed sentinel).

### Predict, then answer — Background instead of r.Context()

**Question.** The handler calls `h.Store.Get(context.Background(), id)` while the server has `ReadTimeout` / the client has left. What happens to the pool?

**Answer.** The query can **continue** even after the abandoned HTTP request. A connection from the pool stays busy. Under load: `SetMaxOpenConns` “fills up”, new requests wait. Always `r.Context()` (or a derived timeout **from** that parent).

### Repository interface — contract, not database

```go
type Store interface {
	Get(ctx context.Context, id string) (Product, error)
	Create(ctx context.Context, p Product) error
}
```

Why a small, concrete interface, not `Repository[T any]`?

- The handler depends on the **methods it actually uses** (interface segregation).
- The fake in the test implements two methods, not twenty.
- A generic “CRUD repository” often signs more than needed and pushes SQL details back to the caller.

One gloss: **repository** here means “a store of domain objects behind an interface” — learning from DDD; in Go we practice it as a small interface in the domain/catalog package.

### database/sql behind the store

`*sql.DB` is a **pool**, not one connection. It lives in `main`:

```go
db, err := sql.Open("pgx", dsn)
db.SetMaxOpenConns(20)
db.SetMaxIdleConns(5)
db.SetConnMaxLifetime(time.Hour)
```

The store holds `DB *sql.DB` and uses the `*Context` variants:

| Method | When |
|--------|------|
| `QueryRowContext` | one row (Get) |
| `QueryContext` | multiple rows (List) |
| `ExecContext` | INSERT/UPDATE/DELETE |

Without the `Context` suffix: the query does **not** honor request cancel. On the request path — always with Context.

`sql.Open` alone does not check the network — so `PingContext` at startup. If ping fails, the process should not accept traffic.

### Predict, then answer — Query vs QueryContext

**Question.** The store calls `db.QueryRow(sql, id)` (without Context), and the handler passed `r.Context()`. Does client cancel interrupt the query?

**Answer.** **No.** Without `QueryRowContext` the database does not see cancel. The context argument must reach a `*Context` method.

### Errors: layer by layer

```text
sql.ErrNoRows     →  catalog.ErrNotFound  →  HTTP 404
unique_violation  →  catalog.ErrConflict  →  HTTP 409
ctx.Err()         →  wrap                →  HTTP 503/504 (agreement)
other             →  wrap + log          →  HTTP 500 (generic message)
```

The handler does **not** import `database/sql` only to read `ErrNoRows`. That is an abstraction leak.

### Trace 4 — Create then Get in a test

```text
POST /products  {id:p2, name:Bread}
  → Store.Create(ctx, ...)
  → ExecContext INSERT
  → 201
GET /products/p2
  → Store.Get → row exists → 200
```

Same fake `map` or same database — the store contract stays the same.

### Fake store + httptest

In the test:

1. `mem` implements `Store` with `map[string]Product`.
2. The handler gets `mem` instead of `PG`.
3. `httptest.NewRequest` + `httptest.NewRecorder` + `mux.ServeHTTP`.
4. Assert on `Code`, `Body`, header — **without** Postgres.

Integration tests with a real database remain a separate job; the HTTP unit layer stays fast.

Why not a tool-generated mock? A hand-written `mem` is readable, has no reflection, and forces the same `error` contract (`ErrNotFound`). When the interface grows, `mem` hurts — a signal to split the interface.

### Wiring in main

```text
sql.Open → configure pool → catalog.PG{DB: db} → httpapi.Handlers{Store: pg} → mux → Server
```

The HTTP package sees only `Store`. The catalog package sees `database/sql`. `main` sees both.

### Predict, then answer — where to put SetMaxOpenConns?

**Question.** A programmer puts `db.SetMaxOpenConns(20)` inside `PG.Get` “to be close to the query”. What is the problem?

**Answer.** Every Get resets a global pool parameter; a race between goroutines; no single place for ops configuration. The pool is configured **once** in `main` (or in an `OpenDB` helper that only `main` calls).

### Safe SQL

Placeholder (`$1` for pgx/Postgres, `?` for database/sql sqlite drivers — depends on the driver):

```go
`SELECT id, name FROM products WHERE id = $1`  // id as an argument
```

Never:

```go
`... WHERE id = '` + id + `'`  // forbidden
```

Defensively: validating the `id` format (e.g. UUID) still makes sense, but a **placeholder is mandatory**.

Dynamic ORDER BY? Do not glue a user string — allowlist columns (`id`, `name`) then insert an **identifier from a map**; values still go through a placeholder.

### Child timeout from r.Context()

When you want a shorter budget than the whole request:

```go
ctx, cancel := context.WithTimeout(r.Context(), 2*time.Second)
defer cancel()
p, err := h.Store.Get(ctx, id)
```

The child is canceled both when the parent (`r.Context()`) dies and when 2s expires. Not the reverse: a timeout from `Background` loses the link to HTTP cancel.

## Rules and syntax

1. **Do not import `database/sql` in the HTTP package** if you can — only the store package and `main`.
2. **Always `r.Context()`** on the request path; `context.Background()` only for startup/shutdown tasks outside a request.
3. Timeout: server (`ReadHeaderTimeout`, `WriteTimeout`) **and/or** `context.WithTimeout(r.Context(), d)` consciously — the child must come from `r.Context()`.
4. Transactions (`BeginTx`) live in the store/service layer, not in the handler with external HTTP calls inside a TX.
5. SQL only with placeholders; never concatenate `PathValue` / body fields into a query string.
6. Open the pool (`*sql.DB`) **once** in `main`; no `sql.Open` per request.
7. Domain sentinel errors (`var ErrNotFound = errors.New(...)`) + `errors.Is` in the handler.
8. Wrap in the store: `fmt.Errorf("catalog get: %w", err)` — keep the chain; log detail server-side.
9. To the client: generic messages (`not found`, `internal error`), not raw SQL.
10. Go 1.22+: route patterns `"GET /products/{id}"` + `PathValue`.

## Examples

### Example 1 — Interface, domain model, PG implementation

```go
package catalog

import (
	"context"
	"database/sql"
	"errors"
	"fmt"
)

type Product struct {
	ID    string
	Name  string
	Price int64 // prices in minor units (e.g. cents)
}

type Store interface {
	Get(ctx context.Context, id string) (Product, error)
	Create(ctx context.Context, p Product) error
}

var ErrNotFound = errors.New("catalog: not found")

type PG struct{ DB *sql.DB }

func (p PG) Get(ctx context.Context, id string) (Product, error) {
	var out Product
	err := p.DB.QueryRowContext(ctx,
		`SELECT id, name, price_minor FROM products WHERE id = $1`,
		id,
	).Scan(&out.ID, &out.Name, &out.Price)
	if errors.Is(err, sql.ErrNoRows) {
		return Product{}, ErrNotFound
	}
	if err != nil {
		return Product{}, fmt.Errorf("catalog get: %w", err)
	}
	return out, nil
}

func (p PG) Create(ctx context.Context, prod Product) error {
	_, err := p.DB.ExecContext(ctx,
		`INSERT INTO products (id, name, price_minor) VALUES ($1, $2, $3)`,
		prod.ID, prod.Name, prod.Price,
	)
	if err != nil {
		return fmt.Errorf("catalog create: %w", err)
	}
	return nil
}
```

#### What happens here

`Store` is the contract. `PG` uses `QueryRowContext` / `ExecContext` with `ctx`. `sql.ErrNoRows` disappears behind `ErrNotFound`. The handler never sees `database/sql`.

### Example 2 — Handler that depends on Store

```go
package httpapi

import (
	"encoding/json"
	"errors"
	"net/http"

	"example.com/shop/internal/catalog"
)

type ProductHandlers struct {
	Store catalog.Store
}

func (h ProductHandlers) Get(w http.ResponseWriter, r *http.Request) {
	id := r.PathValue("id")
	if id == "" {
		http.Error(w, "missing id", http.StatusBadRequest)
		return
	}
	p, err := h.Store.Get(r.Context(), id)
	if errors.Is(err, catalog.ErrNotFound) {
		http.Error(w, "not found", http.StatusNotFound)
		return
	}
	if err != nil {
		// log err server-side here
		http.Error(w, "internal error", http.StatusInternalServerError)
		return
	}
	w.Header().Set("Content-Type", "application/json")
	_ = json.NewEncoder(w).Encode(p)
}

func (h ProductHandlers) Create(w http.ResponseWriter, r *http.Request) {
	var body struct {
		ID    string `json:"id"`
		Name  string `json:"name"`
		Price int64  `json:"price_minor"`
	}
	dec := json.NewDecoder(r.Body)
	dec.DisallowUnknownFields()
	if err := dec.Decode(&body); err != nil {
		http.Error(w, "json", http.StatusBadRequest)
		return
	}
	if body.ID == "" || body.Name == "" {
		http.Error(w, "validation", http.StatusBadRequest)
		return
	}
	err := h.Store.Create(r.Context(), catalog.Product{
		ID: body.ID, Name: body.Name, Price: body.Price,
	})
	if err != nil {
		http.Error(w, "internal error", http.StatusInternalServerError)
		return
	}
	w.WriteHeader(http.StatusCreated)
}
```

#### What happens here

The handler does not know about SQL. The only entry into persistence is a `Store` method. Context is not lost. The test injects a fake.

### Example 3 — Fake store + httptest (404 and 200)

```go
package httpapi_test

import (
	"context"
	"encoding/json"
	"net/http"
	"net/http/httptest"
	"testing"

	"example.com/shop/internal/catalog"
	"example.com/shop/internal/httpapi"
)

type mem struct {
	data map[string]catalog.Product
}

func (m mem) Get(ctx context.Context, id string) (catalog.Product, error) {
	p, ok := m.data[id]
	if !ok {
		return catalog.Product{}, catalog.ErrNotFound
	}
	return p, nil
}

func (m mem) Create(ctx context.Context, p catalog.Product) error {
	m.data[p.ID] = p
	return nil
}

func TestGetNotFound(t *testing.T) {
	h := httpapi.ProductHandlers{Store: mem{data: map[string]catalog.Product{}}}
	mux := http.NewServeMux()
	mux.HandleFunc("GET /products/{id}", h.Get)

	req := httptest.NewRequest(http.MethodGet, "/products/x", nil)
	rec := httptest.NewRecorder()
	mux.ServeHTTP(rec, req)

	if rec.Code != http.StatusNotFound {
		t.Fatalf("code=%d", rec.Code)
	}
}

func TestGetOK(t *testing.T) {
	h := httpapi.ProductHandlers{Store: mem{data: map[string]catalog.Product{
		"p1": {ID: "p1", Name: "Milk", Price: 199},
	}}}
	mux := http.NewServeMux()
	mux.HandleFunc("GET /products/{id}", h.Get)

	req := httptest.NewRequest(http.MethodGet, "/products/p1", nil)
	rec := httptest.NewRecorder()
	mux.ServeHTTP(rec, req)

	if rec.Code != http.StatusOK {
		t.Fatalf("code=%d", rec.Code)
	}
	var got catalog.Product
	if err := json.NewDecoder(rec.Body).Decode(&got); err != nil {
		t.Fatal(err)
	}
	if got.Name != "Milk" {
		t.Fatalf("name=%q", got.Name)
	}
}
```

#### What happens here

Without Postgres you prove the 404 and 200 branches. `mem` honors the same `ErrNotFound` contract. CI stays fast.

### Example 4 — List with QueryContext and limit

```go
func (p PG) List(ctx context.Context, limit int) ([]Product, error) {
	if limit <= 0 || limit > 100 {
		limit = 20
	}
	rows, err := p.DB.QueryContext(ctx,
		`SELECT id, name, price_minor FROM products ORDER BY id LIMIT $1`,
		limit,
	)
	if err != nil {
		return nil, fmt.Errorf("catalog list: %w", err)
	}
	defer rows.Close()

	out := make([]Product, 0, limit)
	for rows.Next() {
		var item Product
		if err := rows.Scan(&item.ID, &item.Name, &item.Price); err != nil {
			return nil, fmt.Errorf("catalog list scan: %w", err)
		}
		out = append(out, item)
	}
	if err := rows.Err(); err != nil {
		return nil, fmt.Errorf("catalog list rows: %w", err)
	}
	return out, nil
}
```

#### What happens here

`QueryContext` honors cancel. `defer rows.Close()` releases the connection. An empty result is `[]Product{}`, not `ErrNotFound` — List with no rows is not 404.

### Example 5 — Context cancel and store

```go
package catalog_test

import (
	"context"
	"errors"
	"testing"
	"time"
)

func TestGetHonorsCancel(t *testing.T) {
	// Assume you have a pg store connected to a slow query / pg_sleep in integration.
	// Here we show the contract: after cancel, the error carries ctx.Err().
	ctx, cancel := context.WithTimeout(context.Background(), time.Nanosecond)
	defer cancel()
	time.Sleep(time.Millisecond)

	if !errors.Is(ctx.Err(), context.DeadlineExceeded) {
		t.Fatalf("expected deadline, got %v", ctx.Err())
	}
	// In an integration test:
	// _, err := store.Get(ctx, "p1")
	// if !errors.Is(err, context.DeadlineExceeded) { ... }
}
```

#### What happens here

Context timeout is the contract. The unit here checks ctx itself; real proof is integration with a slow query and a short timeout.

### Example 6 — Wiring in main (pool + handlers)

```go
package main

import (
	"context"
	"database/sql"
	"log"
	"net/http"
	"os"
	"time"

	_ "github.com/jackc/pgx/v5/stdlib"

	"example.com/shop/internal/catalog"
	"example.com/shop/internal/httpapi"
)

func main() {
	dsn := os.Getenv("DATABASE_URL")
	if dsn == "" {
		log.Fatal("DATABASE_URL is not set")
	}
	db, err := sql.Open("pgx", dsn)
	if err != nil {
		log.Fatal(err)
	}
	defer db.Close()

	db.SetMaxOpenConns(20)
	db.SetMaxIdleConns(5)
	db.SetConnMaxLifetime(time.Hour)

	ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()
	if err := db.PingContext(ctx); err != nil {
		log.Fatal("ping:", err)
	}

	h := httpapi.ProductHandlers{Store: catalog.PG{DB: db}}
	mux := http.NewServeMux()
	mux.HandleFunc("GET /products/{id}", h.Get)
	mux.HandleFunc("POST /products", h.Create)

	srv := &http.Server{
		Addr:              ":8080",
		Handler:           mux,
		ReadHeaderTimeout: 5 * time.Second,
	}
	log.Fatal(srv.ListenAndServe())
}
```

#### What happens here

The only place where `*sql.DB` and HTTP join. Ping at startup is fail-closed. Pool parameters protect the database. Other packages stay clean.

### Example 7 — WRONG vs CORRECT: SQL and context

```go
// WRONG — concatenation + Background
id := r.PathValue("id")
_, _ = db.ExecContext(context.Background(),
	`DELETE FROM products WHERE id = '`+id+`'`)

// CORRECT — placeholder + r.Context()
_, err := db.ExecContext(r.Context(),
	`DELETE FROM products WHERE id = $1`, id)
```

#### What happens here

The first form is both a security hole and a resource leak. The second is the minimum for production.

### Example 8 — Service layer when business logic grows

```go
type Service struct {
	Store Store
	// e.g. publisher, validator...
}

func (s Service) Create(ctx context.Context, p Product) error {
	if p.Price < 0 {
		return ErrInvalid
	}
	return s.Store.Create(ctx, p)
}
```

The handler calls `Service`, the service calls `Store`. TX and rules like “do not create a duplicate name” live here, not in HTTP.

#### What happens here

When the handler becomes fat, extract a service. At the start of the course: handler → store is enough.

## Decision analysis

| Decision | Motive | Alternative we reject |
|----------|--------|------------------------|
| Small `Store` interface | Test + replaceable implementation | SQL directly in the handler |
| `r.Context()` always | Request cancel and deadline | `context.Background()` in the request |
| `ErrNotFound` in the domain | Handler does not parse `sql.ErrNoRows` | `database/sql` import in httpapi |
| Pool in `main` | One lifecycle, clear limits | `sql.Open` per request |
| Placeholder SQL | Defense against injection | String concatenation |
| Fake + httptest | Fast CI for the HTTP layer | Only E2E with a database |
| Concrete Store, not generic Repo[T] | Smaller contract surface | “Universal” CRUD |

## Trade-offs

- **Interface per feature** vs one large `Store`: start concrete; merge later if it hurts.
- **Service layer** between handler and store: add when business rules / TX / multiple stores grow.
- **Unit fake** does not replace integration: indexes, constraints, column types still need a real database.
- **Mapping ctx.Err() to status**: 503 vs 504 vs 499 — team agreement; what matters is not treating it as 500 without logging the reason.
- **SQLite in the test** vs mem fake: SQLite catches SQL errors; mem is faster for a pure HTTP contract.

## Common mistakes

1. **SQL in the handler** — clean unit test impossible; mixed responsibilities.
2. **`context.Background()` on the request path** — zombie queries, drained pool.
3. **Leaking `*sql.DB` through the HTTP package** — the handler “knows” about the driver and schema.
4. **Swallowing `ErrNoRows` as 500** — the client cannot tell “missing” from “broken”.
5. **Concatenating `PathValue` into SQL** — injection and brittle queries.
6. **Long TX in the handler** with external calls — you hold rows locked while waiting on the network.
7. **`sql.Open` without `PingContext` / without MaxOpen** — late production failure; uncontrolled pool.
8. **Returning a raw SQL message to the client** — schema and internal state leak.
9. **Forgotten `rows.Close()` / `rows.Err()`** — leaking connections from the pool.
10. **Testing only the happy path** — 404 and cancel branches stay unchecked.

## Idiomatic Go

- **Accept interface, return concrete** (in the community spirit): the handler field is `Store`; in `main` you construct `catalog.PG{...}`.
- Wrap with `%w`; check with `errors.Is` / `errors.As`.
- Sentinel `var ErrNotFound = errors.New(...)` in the domain package — exported (`Err` prefix).
- Zero value: empty `Product{}` with an error; do not mix “no data” and “success with empty”.
- Package boundary: `internal/catalog`, `internal/httpapi`, `cmd/shop/main.go`.
- Same idiom as in standard Go server examples: composition in `main`, thin handlers.

## Practical scenario

The team has 40 handlers with copy-paste SQL and `QueryRow` without context. Refactor:

1. Introduce `catalog.Store` and move SQL into `PG`.
2. Handlers get a `Store` field; tests with `mem` pass in CI without a Postgres service.
3. A separate job runs migrations + integration.
4. After deploy, client timeout no longer leaves queries forever — `QueryContext` honors cancel.
5. The “pool exhausted” incident drops; `db.wait` metrics calm down.

Lesson: the repository interface boundary + context is not aesthetics — it is operational hygiene.

## Check questions

1. **Why a repository interface?**  
   Separates HTTP from SQL and enables a fake in the test without a live database.

2. **Which context goes into the store call?**  
   `r.Context()` or a child made from it (`WithTimeout`).

3. **Where does `*sql.DB` live?**  
   In `main` wiring and the store implementation — not in the handler package.

4. **How does `sql.ErrNoRows` reach the client?**  
   Store → `ErrNotFound` → handler → HTTP 404.

5. **Why does cancel matter?**  
   Releases DB resources when the client abandons; protects the pool.

6. **Why not concatenate id into SQL?**  
   Opens room for injection and brittle queries; use placeholders.

7. **What is `httptest` with a fake store for?**  
   Fast check of HTTP status and body without infrastructure.

8. **Where is the pool configured?**  
   Once in `main` (MaxOpen, MaxIdle, ConnMaxLifetime), not in a store method.

## Mini checklist before merge

1. The handler package does not import `database/sql`.
2. Every store query uses a `*Context` variant.
3. `sql.ErrNoRows` → `ErrNotFound` → 404 covered by a test.
4. No string concatenation in SQL.
5. `*sql.DB` is opened once; Ping at startup.
6. Fake store covers at least Get 200 and Get 404.

## What is not a goal of this lesson

- ORM (GORM, ent…) — the same boundary principles apply; the API changes.
- Schema migrations — a separate tool (goose, golang-migrate); wiring still in `main`.
- Replica / read-write split — later; first one pool and a clean interface.

## Transaction in the store (reminder)

```go
func (p PG) Transfer(ctx context.Context, from, to string, amount int64) error {
	tx, err := p.DB.BeginTx(ctx, nil)
	if err != nil {
		return fmt.Errorf("begin: %w", err)
	}
	defer tx.Rollback() // no-op after Commit

	// ExecContext on tx, not on p.DB
	if _, err := tx.ExecContext(ctx, `UPDATE ...`, amount, from); err != nil {
		return err
	}
	if _, err := tx.ExecContext(ctx, `UPDATE ...`, amount, to); err != nil {
		return err
	}
	return tx.Commit()
}
```

TX lives in store/service. The handler does not hold an open transaction while decoding JSON or calling external HTTP.

## Observability (brief)

Log `err` with the request id from context (if middleware injects it). Metrics: count of `ErrNotFound` vs 500, query duration, pool wait. Without that, “pool exhausted” debugging takes days.

## Checklist for the PR reviewer

- [ ] No `database/sql` in the HTTP package
- [ ] Every query has `*Context` and `r.Context()` (or a child)
- [ ] `ErrNotFound` → 404 test exists
- [ ] No SQL concatenation
- [ ] Pool MaxOpen set in `main`

## Summary

HTTP handler + **repository interface** + `database/sql` behind the store + **`r.Context()`** through the whole path. `sql.ErrNoRows` becomes domain `ErrNotFound` then 404. The pool lives in `main`. You test handlers with a fake store and `httptest`; you integrate the database consciously. No SQL concatenation.
