# 02.12 Testing

> **Go Path - Zero to Gopher** / **01 Basics → Go Fundamentals** / Lesson 02.12

## Lesson goals

After this lesson you will be able to:

- write tests in the `testing` package with `TestXxx(t *testing.T)`
- distinguish `t.Error` / `t.Errorf` from `t.Fatal` / `t.Fatalf`
- use table-driven tests and `t.Run`
- run `go test` and read the output
- interpret an intro to coverage (`go test -cover`)

## Prerequisite

- Package, functions, `error`
- Go 1.22+
- An intro to concurrency is not required; `-race` fits well

## Problem this lesson solves

Without automated tests every change is a manual ritual. Go standardizes: the same tool (`go test`), the same naming convention. Beginners write one huge test instead of a table; or chase “100% cover” and do not test behavior. This lesson sets the idiomatic minimum.

## Mental model

A `*_test.go` file enters only the test build. `TestName(t *testing.T)` is one test. `t` reports failure, logs, runs subtests.

**Table-driven:** a slice of structs (input, expected, name). Loop + `t.Run`. A new case = a new row.

```text
go test
  → find Test*
  → run each
  → Errorf: record, continue
  → Fatalf: record, stop that test immediately
  → report PASS/FAIL
```

## Mechanism

### Basic signature

```go
func TestAdd(t *testing.T) {
	got := Add(1, 2)
	if got != 3 {
		t.Fatalf("Add(1,2)=%d, want 3", got)
	}
}
```

The name must start with `Test` then a capital letter (`TestAdd`, not `Testadd` for reliable `-run`).

### `Errorf` vs `Fatalf`

| Method | Records failure | Continues that test |
|--------|-----------------|---------------------|
| `t.Error` / `t.Errorf` | yes | yes |
| `t.Fatal` / `t.Fatalf` | yes | **no** — immediate return |

Use `Fatal` when further checks make no sense (e.g. `err != nil` so you must not read the result). Use `Error` when you want more failures in the same test.

**Predict the result:**

```go
func TestDemo(t *testing.T) {
	t.Errorf("first")
	t.Fatalf("second")
	t.Errorf("third") // does it run?
}
```

**Answer:** `first` and `second` are recorded; `third` does **not** run because `Fatalf` stops.

### Table-driven + `t.Run`

```go
tests := []struct {
	name string
	a, b int
	want int
}{
	{name: "positive", a: 1, b: 2, want: 3},
	{name: "zeros", a: 0, b: 0, want: 0},
}
for _, tt := range tests {
	t.Run(tt.name, func(t *testing.T) {
		got := Add(tt.a, tt.b)
		if got != tt.want {
			t.Fatalf("got %d want %d", got, tt.want)
		}
	})
}
```

Failure shows `--- FAIL: TestAdd/zeros`. Filter: `go test -run TestAdd/zeros`.

On Go 1.22+ `tt` in the loop is per-iteration — the closure in `t.Run` captures the correct row. (Before 1.22: `tt := tt` copy.)

### What `go test` does

```text
go test ./...
go test -v ./package
go test -run TestAdd -v
go test -count=1 ./...
go test -cover ./...
go test -race ./...
```

1. Finds `*_test.go` in packages.
2. Compiles test binaries.
3. Runs tests (caches successful ones — that is why `-count=1` when you doubt).
4. `-v` shows `t.Log` and names.
5. `-cover` measures executed statements — a signal, not a KPI.

### White-box vs black-box

- `package foo` in the test — sees **unexported**.
- `package foo_test` + import — only **exported** API.

### `t.Helper`

```go
func assertEq(t *testing.T, got, want int) {
	t.Helper()
	if got != want {
		t.Fatalf("got %d want %d", got, want)
	}
}
```

Failure shows the line in `TestXxx`, not inside the helper.

### Testing `error` with `errors.Is`

Do not compare `err.Error()` strings. Use `errors.Is(err, ErrSentinel)` or a type.

## Rules and syntax

1. `func TestXxx(t *testing.T)` in `*_test.go`.
2. `Fatal` stops the test; `Error` continues.
3. `t.Helper()` in assert helpers.
4. Do not rely on test order or global state.
5. `-count=1` disables the cache.
6. Coverage guides; it does not prove correctness.
7. Isolate external I/O; `-short` for slower tests.

## Examples

### Example 1 — First test

`mathx/add.go`:

```go
package mathx

func Add(a, b int) int { return a + b }
```

`mathx/add_test.go`:

```go
package mathx

import "testing"

func TestAdd(t *testing.T) {
	got := Add(2, 3)
	if got != 5 {
		t.Fatalf("Add(2,3)=%d, want 5", got)
	}
}
```

```text
go test ./mathx
```

#### What happens here

`go test` finds `TestAdd`, runs it, PASS if there is no Error/Fatal.

### Example 2 — Table-driven

```go
package mathx

import "testing"

func TestAddTable(t *testing.T) {
	tests := []struct {
		name string
		a, b int
		want int
	}{
		{name: "positive", a: 2, b: 3, want: 5},
		{name: "negative", a: -1, b: -1, want: -2},
		{name: "zero", a: 0, b: 7, want: 7},
	}
	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			got := Add(tt.a, tt.b)
			if got != tt.want {
				t.Fatalf("Add(%d,%d)=%d, want %d", tt.a, tt.b, got, tt.want)
			}
		})
	}
}
```

#### What happens here

Three subtests, clear names in `-v`. A new edge = a new row.

### Example 3 — Errorf vs Fatalf

```go
package mathx

import "testing"

func TestDiv(t *testing.T) {
	got, err := Div(1, 0)
	if err == nil {
		t.Fatalf("expected error, got=%d", got) // do not continue
	}
	got, err = Div(9, 3)
	if err != nil {
		t.Errorf("unexpected err: %v", err)
	}
	if got != 3 {
		t.Errorf("got %d want 3", got)
	}
}
```

#### What happens here

The first `Fatalf` stops if division by zero “succeeds.” Later `Errorf` can report more problems in the same test when it makes sense to continue.

### Example 4 — errors.Is table

```go
package parse

import (
	"errors"
	"testing"
)

var ErrEmpty = errors.New("empty")

func Normalize(s string) (string, error) {
	if s == "" {
		return "", ErrEmpty
	}
	return s, nil
}

func TestNormalize(t *testing.T) {
	tests := []struct {
		name    string
		in      string
		want    string
		wantErr error
	}{
		{name: "ok", in: "Go", want: "Go"},
		{name: "empty", in: "", wantErr: ErrEmpty},
	}
	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			got, err := Normalize(tt.in)
			if tt.wantErr != nil {
				if !errors.Is(err, tt.wantErr) {
					t.Fatalf("err=%v, want %v", err, tt.wantErr)
				}
				return
			}
			if err != nil {
				t.Fatalf("unexpected: %v", err)
			}
			if got != tt.want {
				t.Fatalf("got %q want %q", got, tt.want)
			}
		})
	}
}
```

#### What happens here

The table covers success and a sentinel. `errors.Is` is more stable than comparing the message. An early `return` after an expected `error` avoids false `got` checks.

### Example 5 — Helper + black-box

```go
package greet_test

import (
	"testing"

	"example.com/demo/greet"
)

func assertEq(t *testing.T, got, want string) {
	t.Helper()
	if got != want {
		t.Fatalf("got %q want %q", got, want)
	}
}

func TestHello(t *testing.T) {
	assertEq(t, greet.Hello(""), "hello")
	assertEq(t, greet.Hello("Marko"), "hello, Marko")
}
```

#### What happens here

`package greet_test` forces the public API. `t.Helper` fixes the line in the report.

### Example 6 — Coverage as a signal

```go
func Clamp(v, lo, hi int) int {
	if v < lo {
		return lo
	}
	if v > hi {
		return hi
	}
	return v
}
```

A test only with `Clamp(5,0,10)` does not hit the branches. `go test -cover` shows the gap. Add table rows for `v<lo` and `v>hi`.

#### What happens here

Coverage guides attention. 100% with a wrong `want` is still false confidence.

## Decision analysis

| Decision | Motive |
|----------|--------|
| Table-driven | Scales edge cases |
| `t.Run` | Filtering and a readable report |
| `Fatal` vs `Error` | Stop when further makes no sense |
| Black-box | Forces the contract |
| Cover as a signal | Not as a KPI |

## Trade-offs

- White-box is faster, more brittle on refactor.
- Too many mocks — tests are green, production fails.
- `t.Parallel` speeds up with an isolation requirement.
- 100% cover encourages meaningless tests.

## Common mistakes

1. **Test dependent on global state / order**
   ```go
   var n int
   func TestA(t *testing.T) { n++ }
   func TestB(t *testing.T) { if n != 1 { t.Fatal() } }
   ```
   Fix: local state in every test.

2. **Comparing `err.Error()` strings** — use `errors.Is`.

3. **Huge test without a table** — you do not see which case fails.

4. **Forgotten `t.Helper`** — wrong line in the report.

5. **`t.Error` where `Fatal` is needed** — continued on invalid state / panic.

6. **Cache: “green locally”** — `go test -count=1`.

7. **Test that always passes** (`if false`).

## Idiomatic Go

- One table per behavior.
- `-short` for slower tests.
- Test file next to the code.
- CI: `go test ./...` (+ `-race` where it makes sense).
- Subtest name describes the case.

## Practical scenario

A flags library: one `TestParse` of 200 lines. Review asks for a table. QA reports “empty list” — one row, reproduction in 10s. Coverage shows an unexecuted branch — they add a case. CI keeps the cover profile as a trend, not as a 100% gate.

## Exercises

1. `Reverse(s string) string` + table-driven (empty, Unicode).
2. Move white-box to `package x_test`.
3. Helper `assertNoErr(t, err)` with `t.Helper`.
4. `go test -cover` for `Clamp` + add branches.
5. `go test -run` only one subtest.
6. Deliberately break the implementation; compare `Errorf` vs `Fatalf` output.
7. Table for `(string, error)` with `errors.Is`.

## Check questions

1. **How do you sign a basic test?**  
   `func TestName(t *testing.T)` in `*_test.go`.

2. **What is table-driven?**  
   A loop over a table of cases instead of copying the body.

3. **What is `t.Run` for?**  
   Named subtests and a `-run` filter.

4. **Difference between `Error` and `Fatal`?**  
   Both record; `Fatal` immediately stops that test.

5. **What does `-cover` say?**  
   How much of the code the tests executed — not a proof of correctness.

6. **Why `-count=1`?**  
   Disables the cache of successful tests.

7. **White-box vs black-box?**  
   The same package sees unexported; `foo_test` only exported.

### Deeper mechanism: what `go test` compiles

For package `mathx` with `add.go` and `add_test.go`:

1. The toolchain makes a temporary test binary that includes the package + test files.
2. It does not include `*_test.go` in an ordinary `go build` of a production CLI.
3. It runs `Test*` functions (and optionally `Example*`, `Benchmark*` — out of focus).
4. If any test calls `Fail`/`Error`/`Fatal`, the package FAIL.

That is why “works in main, fails in test” often means: different input, different order, or cache.

### Fatalf after Errorf — order in the report

```go
func TestOrder(t *testing.T) {
	t.Errorf("A")
	t.Errorf("B")
	t.Fatalf("C")
	t.Errorf("D") // will not
}
```

The report shows A, B, C. D does not run. Use more `Errorf` when you want all failures at once (e.g. more struct fields); `Fatalf` when the state is already invalid.

### Example 7 — Subtest filter in practice

```text
go test -v -run 'TestAddTable/zero' ./mathx
```

Runs only the subtest whose name matches the regex. Faster while debugging one table row.

### Example 8 — Parallel intro (caution)

```go
func TestIndep(t *testing.T) {
	t.Parallel()
	// this test must not share global state
}
```

`t.Parallel` speeds up the suite. If tests share a map/file — race or flaky. For this course: know it exists; use when tests are truly independent.

### Example 9 — `-short` for slower tests

```go
func TestIntegration(t *testing.T) {
	if testing.Short() {
		t.Skip("skipping under -short")
	}
	// slow I/O
}
```

```text
go test -short ./...
```

A fast CI job uses `-short`; a night job runs full integration.

### Checklist before a PR

- [ ] `go test ./...` (and `-count=1` if you doubt)
- [ ] table-driven for edge cases
- [ ] `errors.Is` instead of message comparison
- [ ] no shared global state among tests
- [ ] `-race` if you touch concurrency
- [ ] cover as a signal, not as the only gate

### What FAIL output means (how to read)

```text
--- FAIL: TestAddTable (0.00s)
    --- FAIL: TestAddTable/zero (0.00s)
        add_test.go:42: got 1 want 0
FAIL
```

Read top-down:

1. Which test / subtest.
2. Which file and line.
3. The message you wrote yourself in `Fatalf` — that is why write `got` and `want`.

Without a good message you debug blind.

### Example 10 — Bad vs good assert message

```go
// Bad:
if got != want { t.Fatal("fail") }

// Good:
if got != want {
	t.Fatalf("Add(%d,%d)=%d, want %d", a, b, got, want)
}
```

### Example 11 — Test package layout

```text
mathx/
  add.go
  add_test.go      // package mathx  (white-box) or
  add_export_test.go // package mathx_test (black-box)
```

Do not mix both styles in the same file. The team picks a convention; black-box forces the public contract.

### Why table-driven saves time

One bug in a parser often needs 8 edge inputs. Without a table: 8 almost identical functions. With a table: 8 rows. Review sees the behavior matrix immediately. When QA reports a new case — one row, one commit.

### Example 12 — Cache demonstration

```text
go test ./mathx
go test ./mathx
go test -count=1 ./mathx
```

The cache of successful tests speeds things up; `-count=1` forces a repeat when you suspect flaky.

### Example 13 — Log in a test

```go
t.Logf("input=%q", in)
```

Visible with `go test -v`. Use for diagnostics, not as an assert.

### Example 14 — Skip

```go
if runtime.GOOS == "windows" {
	t.Skip("not relevant on windows")
}
```

`Skip` is not FAIL — it marks that the test did not run. Use for platform / `-short`.

### Example 15 — Complete small module test flow

1. Write `Clamp` in `mathx/clamp.go`.
2. Write a table with three branches in `clamp_test.go`.
3. `go test -v ./mathx` — see subtest names.
4. Break one `want` — read the FAIL message.
5. `go test -cover ./mathx` — check that branches are covered.
6. Restore the correct `want`, commit test + code together.

This ritual matters more than memorizing flags.

### Table: Error vs Fatal

| You need… | Use |
|-----------|-----|
| More checks in the same test | `Errorf` |
| State further invalid | `Fatalf` |
| Setup fail (e.g. cannot open fixture) | `Fatalf` |
| Compare 5 struct fields | more `Errorf` or a helper |

### FAQ

**Q: Do tests have to be in the same folder?**  
A: Yes, next to the package code (convention). Name `*_test.go`.

**Q: Do `Example` functions enter the docs?**  
A: Yes (`ExampleXxx`) — out of focus for this lesson, but `go test` also runs them.

**Q: Does 100% cover mean no bugs?**  
A: No. Cover does not check that `want` is correct.

### Example 16 — Testing a named result / multiple values

```go
got, err := Parse("42")
if err != nil {
	t.Fatalf("err=%v", err)
}
if got != 42 {
	t.Fatalf("got=%d", got)
}
```

Always `err` first, then the value — the same order as in production code.

### Example 17 — Table with wantErr bool

```go
{name: "ok", in: "1", want: 1, wantErr: false},
{name: "bad", in: "x", wantErr: true},
```

In the loop: if `wantErr`, check `err != nil` and `return`; otherwise check `err == nil` and `got`.

### Takeaway sentence

**`go test` is a contract with your future self: table + clear message + Fatal when further makes no sense.**

### Example 18 — Naming subtests

Bad: `t.Run("1", ...)`.  
Good: `t.Run("empty-input", ...)` or `t.Run("overflow", ...)`.

The name must make sense in FAIL output without opening the file.

### Example 19 — Do not share `t` wrongly

```go
// In a t.Run callback always use the *new* t parameter:
t.Run(name, func(t *testing.T) {
	// this t, not the outer one
})
```

The outer `t` and the inner `t` are different; mixing confuses parallel tests.

### Example 20 — Minimal CI snippet

```text
go test ./...
go vet ./...
go test -race ./...   # when there is concurrency
```

That is a sufficient minimum for the Basics end. Coverage HTML stays a local tool for gaps.

### Last checklist

1. Does the table have edge cases?
2. Does the message have got/want?
3. Is Fatal in the right place?
4. Does the test pass in isolation (`-count=1`)?
5. Does CI run `go test ./...`?

When all five items pass, this lesson is done — the debugging course (04.xx) builds on the same ritual.

### Closing predict

What does `go test -run TestAdd -v` do if `TestAdd` and `TestAddTable` both exist?

**Answer:** the regex matches **both** names (prefix). For only `TestAdd` use `^TestAdd$` or a more precise pattern.

### Last ritual

Write a failing test → see FAIL → fix the code → `go test -count=1` green → only then refactor. The reverse order is guessing.

That is the whole Basics test mindset.

### Quick recap

- `TestXxx(t *testing.T)` in `*_test.go`
- table + `t.Run` for edges
- `err` first, then value
- `go test ./...` (+ `-count=1`, `-race`, `-cover` as needed)
- failing test before the fix

That closes the Basics Fundamentals test layer.

Next time you write a feature without a test — stop: first a failing `TestXxx`, then the implementation. That is not a ritual, but a way to know it works.

Now you have the tool; use it.

## Summary

Go tests are functions with `testing.T`, most often table-driven with `t.Run`. `Errorf` records and continues; `Fatalf` stops. `go test` is the entry; coverage guides. Test behavior and `error` idiomatically (`errors.Is`), keep tests isolated.
