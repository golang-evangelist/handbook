# 02.02 Variables and Simple Data Types

> **Go Path - Zero to Gopher** / **01 Basics → Go Fundamentals** / Lesson 02.02

## Lesson goals

After this lesson you should be able to:

- use the zero value table without guessing and design APIs around it
- apply the rules of short declaration (`:=`) and redeclaration
- recognize and avoid harmful shadowing (especially `err`, `ctx`, `client`)
- distinguish package, function, and block scope
- use the blank identifier deliberately, not to hide errors
- do explicit conversions and avoid string / rune / byte traps
- predict the result of short programs with shadows and UTF-8 slicing

## Prerequisite

- 01.03 (introduction to primitives)
- 02.01 (environment ready: `go run`, modules, editor)

## Problem this lesson solves

Getting Started gave an overview of types. In practice bugs come from: shadowing the variable `err`, wrong scope, a `:=` redeclaration that is not what you think, and slicing a UTF-8 string by bytes. An “uninitialized variable” from the C mental model does not exist here — there is a zero value that can be wrongly *interpreted*. This lesson goes deeper than 01.03: same area, stricter discipline.

## Mental model

A name in Go lives in a **block**. An inner block can declare the same name — that is **shadowing**: the outer name is hidden, not deleted.

`:=` left operands: at least one name must be **new in the current block**. Already existing names are **assigned**, new ones are **declared**. That is not the same as “always a new variable”.

Zero value means: you can read before an explicit assignment. That is a feature, not a bug — but you must know what you are reading and what zero *means* for your type.

```text
package scope
   └── function scope
         └── block (if / for / switch / { })
               └── deeper block ...
```

String index = byte. A Unicode “character” in the sense of a code point = rune. Mixing without conversion produces invalid text or silent bugs in UI/JSON.

## Mechanism

### Zero value table (extended)

| Type | Zero value | Note |
|------|------------|------|
| `bool` | `false` | |
| numerics (`int`, `float64`, …) | `0` | including `complex` |
| `string` | `""` | |
| pointer | `nil` | dereference → panic |
| slice | `nil` | `len=0`, `append` works |
| map | `nil` | reading OK, writing → panic |
| channel | `nil` | send/receive blocks forever |
| function | `nil` | call → panic |
| interface | `nil` | |
| struct | fields zero | recursively by fields |

Design principle: `var t T` should be a safe default object wherever you can. For a map field in a struct — either document that it must be `make`d, or initialize in the constructor.

### Declarations: var, const, :=

```go
var x int          // zero value 0
var y int = 7      // explicit
var z = 7          // type inferred (int)
w := 7             // short declaration — only inside a function
const Pi = 3.14159 // compile-time constant
```

Line by line:

1. `var x int` — use when you want zero or a later assignment.
2. `:=` — use when you have a value immediately and the type is obvious.
3. `const` — does not change; can be typed or untyped.
4. Package-level `:=` **does not exist** — only `var` / `const` / `func`.

### Short declaration and redeclaration

```go
a := 1
a, b := 2, 3 // a is assigned, b is declared
// a := 4    // error in the same block: no new name
```

In a new block:

```go
a := 1
{
	a := 2 // new a — shadows the outer one
	fmt.Println(a) // 2
}
fmt.Println(a) // 1
```

Key: “same block” is not “same function”. Every `if`, `for`, `switch`, and explicit `{ }` opens a new block.

### Scope — three levels

- **Package:** `var` / `const` / `func` outside a function — visible in the whole package; capital initial letter = exported.
- **Function:** parameters and locals from the start of the function to the end.
- **Block:** body of `if` / `for` / `switch` / `select` and explicit `{ }`.

Init in `if`:

```go
if n, err := strconv.Atoi(s); err != nil {
	return err
} else {
	use(n) // n and err live in else too
}
// here n and err are not visible
```

### Blank identifier

```go
n, _ := strconv.Atoi(s) // ignore error — caution
for range tickets {
	count++
}
_ = mustInit() // explicitly discard if the API forces use
```

`_` discards the value; it does not occupy an “unused variable”. The compiler does not allow unused local variables — `_` is a valve, not an excuse to swallow `error`.

### Conversions (not a “cast” in the C sense)

```go
var x int = 3
var y int64 = int64(x) // explicit
s := string([]rune{'č', 'a'})
b := []byte("go")
```

Rules:

1. Between different types — always an explicit conversion.
2. `string(65)` is `"A"` (code point), **not** `"65"`.
3. `string([]byte{...})` interprets bytes as UTF-8 text.
4. For decimal printing of a number: `strconv.Itoa` / `fmt.Sprint`.

### String, rune, byte — memory model

```go
s := "Ž"
fmt.Println(len(s))       // number of bytes, often 2 for Ž
fmt.Printf("%x\n", s[0])  // first byte, not the whole character
```

`range` over a string gives `index` (byte offset) and `rune`. `utf8.RuneCountInString` counts runes. Slicing `s[:n]` cuts **bytes** — it can cut through a UTF-8 sequence and give an invalid string.

### Named types and distinct types

```go
type UserID int
type OrderID int

var u UserID = 1
// var o OrderID = u // does not compile without conversion
var o OrderID = OrderID(u)
```

The same underlying type does not mean they are interchangeable — that is intentional.

### Predict the result — redeclaration

```go
package main

import "fmt"

func main() {
	x := 1
	x, y := 2, 3
	fmt.Println(x, y)
}
```

**Question:** What is printed? Does the second `:=` make a new `x`?

**Answer:** `2 3`. `x` is assigned (it exists in the block), `y` is declared. Not a new `x`.

### Predict the result — shadow

```go
package main

import "fmt"

func main() {
	err := "outer"
	{
		err := "inner"
		fmt.Println(err)
	}
	fmt.Println(err)
}
```

**Answer:** `inner` then `outer`. The inner `err` is a new variable; the outer one is untouched.

### int width, rune and byte as types

`int` is 32 or 64 bits depending on architecture (`GOARCH`). `int32` / `int64` are fixed. `rune` is an alias for `int32` (Unicode code point). `byte` is an alias for `uint8`.

```go
var r rune = 'Č'
var b byte = 'A'
fmt.Printf("rune=%d byte=%d\n", r, b)
```

When working with files and the network — `[]byte`. When working with text as characters — `[]rune` or `range` over `string`. When working with numbers for JSON/protocols — choose an explicit width (`int64`) instead of a bare `int` if you cross machines.

### Multiple assignment and swap

```go
a, b := 1, 2
a, b = b, a // swap without a temporary variable
x, y := f() // function with two results
```

The right-hand side is evaluated before assignment — that is why swap works. That is not magic of `:=`; it works with `=` too.

### iota for groups of constants

```go
const (
	StatusDraft = iota // 0
	StatusOpen         // 1
	StatusClosed       // 2
)
```

`iota` grows by line in a `const` block. Used for enum-like sets. The type can be named (`type Status int`) for type safety.

### Predict the result — string(int)

```go
fmt.Println(string(50))
fmt.Println(strconv.Itoa(50))
```

**Answer:** `string(50)` gives `"2"` (Unicode code point U+0032, character `'2'`). `strconv.Itoa(50)` gives `"50"`. For `string(65)` you get `"A"`. Remember: **code point, not decimal representation of the number**.

### When zero value lies business-wise

```go
type Account struct {
	Balance int // 0 can mean “zero dinars” OR “not loaded”
}
```

If you need to distinguish “not set” from zero, use a pointer (`*int`), `sql.NullInt64`, or an explicit `bool` flag. Zero value is not a universal “optional”.

### Export and documenting zero value

For an exported type in a package comment / doc comment on the type:

```go
// Buffer holds bytes for sending.
// The zero value is a ready Buffer with a nil inner slice — Write allocates as needed.
type Buffer struct {
	buf []byte
}
```

To an API reader the zero value must be clear without reading all the code. If zero **is not** safe (e.g. nil map), a `New` constructor is part of the contract, not an option.

### Predict the result — multiple assignment

```go
a, b := 1, 2
a, b = b, a
fmt.Println(a, b)
```

**Answer:** `2 1` — the right-hand side is evaluated before assignment.

### Predict the result — iota

```go
const (
	StatusDraft = iota // 0
	StatusOpen         // 1
	StatusClosed       // 2
)
```

**Answer:** `StatusOpen == 1`, `StatusClosed == 2`. Keep a clean `iota` chain; do not mix hand-written numbers in the middle of the block without need.

Named type for type safety:

```go
type Status int

const (
	StatusDraft Status = iota
	StatusOpen
	StatusClosed
)
```

### Example 6 — Width conversion and loss

```go
package main

import "fmt"

func main() {
	var big int64 = 3_000_000_000
	small := int32(big) // may “cut off” at 32-bit
	fmt.Println(big, small)

	var x int = 42
	var y int64 = int64(x) // safe widening
	fmt.Println(y)
}
```

#### What happens here

An explicit conversion to a narrower type can change the value — the compiler does not protect against overflow in conversion. That is why conversions are verbose: so you see them in review. Widening `int` → `int64` is usually safe on a 64-bit OS, but `int` on a 32-bit machine is already 32 bits — that is why protocols prefer fixed widths.

**Predict the result:** On a typical 64-bit system, is `int(3_000_000_000)` OK?

**Answer:** Yes, `int` is 64-bit. On 32-bit, conversion from `int64` to `int` would truncate. Do not assume portability without a fixed width.

### Example 7 — Shadowing ctx (anti-pattern)

```go
package main

import (
	"context"
	"fmt"
	"time"
)

func work(ctx context.Context) {
	fmt.Println("deadline outer?", ctx.Err())
	ctx, cancel := context.WithTimeout(ctx, time.Millisecond) // intentional shadow
	defer cancel()
	time.Sleep(2 * time.Millisecond)
	fmt.Println("deadline inner?", ctx.Err())
}

func main() {
	work(context.Background())
}
```

#### What happens here

Shadowing `ctx` here is an **idiomatic** pattern: a new child context in a narrower scope. The difference from harmful shadowing of `token`: here you want the rest of the function to see the child. The rule is not “never shadow” — but “shadow only when the lifetime is intentionally narrower and obvious”. For `err` and `ctx` a short scope is often OK; for `client` / `conn` rarely.

## Rules and syntax

1. No unused local variables or imports.
2. Type conversion always explicit between different types.
3. `:=` only inside a function.
4. Redeclaration with `:=` requires at least one new name **in the same block**.
5. Shadowing `err` in a short `if` is a common idiomatic pattern; shadowing `ctx` / `client` / `token` is often a bug.
6. `string(sliceOfBytes)` interprets bytes as UTF-8 (not a hex dump).
7. Package-level `var` initialization may call functions — watch order and side effects.
8. Exported identifiers start with a capital letter.
9. Zero value map: do not do `m[k] = v` before `make` or literal initialization.
10. Prefer `strconv` for number ↔ text, not `string(int)`.

## Examples

### Example 1 — Zero values and a safe API

```go
package main

import "fmt"

type Config struct {
	Verbose bool
	Retries int
	Name    string
}

func main() {
	var c Config
	fmt.Printf("%#v\n", c)

	var list []int
	fmt.Println(list == nil, len(list), cap(list))
	list = append(list, 1)
	fmt.Println(list == nil, list)

	var f func()
	if f != nil {
		f()
	} else {
		fmt.Println("nil function — do not call")
	}

	var m map[string]int
	fmt.Println("read nil map:", m["x"])
	// m["x"] = 1 // panic
	m = make(map[string]int)
	m["x"] = 1
	fmt.Println(m)
}
```

#### What happens here

`Config` fields are zero — `Verbose` false means “quiet” without constructor ceremony. That is conscious API design: choose zero to mean “default off” or “empty”. A nil slice behaves as empty for `append` and `len` — idiomatic. A nil function must not be called. A nil map allows reading (zero value of the value type) but panics on write — that is why constructors `make` map fields. The example ties zero value to a safe API: document the meaning of zero for every exported field.

**Predict the result:** What does `fmt.Println(list == nil)` print after `append`?

**Answer:** `false` — `append` must return (and you must keep) a new header; after assignment the slice is no longer nil.

### Example 2 — Short declaration, redeclaration, shadowing

```go
package main

import (
	"fmt"
	"strconv"
)

func parsePair(a, b string) (int, int, error) {
	x, err := strconv.Atoi(a)
	if err != nil {
		return 0, 0, err
	}
	y, err := strconv.Atoi(b) // err: assign to existing; y: new
	if err != nil {
		return 0, 0, err
	}
	return x, y, nil
}

func shady() {
	err := fmt.Errorf("outer")
	if true {
		n, err := strconv.Atoi("x") // new err in if scope
		fmt.Println("inner", n, err)
	}
	fmt.Println("outer err still", err)
}

func main() {
	fmt.Println(parsePair("2", "3"))
	shady()
}
```

#### What happens here

In `parsePair`, the second `:=` uses the existing `err` and a new `y` — allowed redeclaration/assignment in the **same** function block. In `shady`, `err` inside `if` is a **new** variable because it is a new block; the outer `err` stays `outer`. That confuses when you expect the inner error to “overwrite” the outer one. `go vet` / linters (`shadow`) sometimes warn — listen to them for `token`, `client`, `ctx`. For a short `if v, err := f(); err != nil` the shadow is often intentional and local.

**Predict the result:** What does the last `fmt.Println` in `shady` print?

**Answer:** `outer err still outer` (more precisely: Error string “outer”) — the inner `err` did not change the outer one.

### Example 3 — Block scope and package var

```go
package main

import "fmt"

var packageCounter int

func main() {
	packageCounter++
	x := "func"
	fmt.Println(x)

	if true {
		x := "block"
		fmt.Println(x)
		for i := 0; i < 2; i++ {
			x := i
			fmt.Println("for", x)
		}
		fmt.Println("after for", x)
	}
	fmt.Println("after if", x)
	fmt.Println("package", packageCounter)
}
```

#### What happens here

Every block can introduce a new `x`. A package variable lives longer than `main` and is shared among package functions — convenient for a counter in a demo, bad for tests and concurrency without synchronization. Excessive shadowing makes debugging harder: prefer new names (`blockX`) when the shadow is not intentional. Output (order): `func`, `block`, `for 0`, `for 1`, `after for block`, `after if func`, `package 1`.

### Example 4 — String, rune, byte traps

```go
package main

import (
	"fmt"
	"strconv"
	"unicode/utf8"
)

func unsafePrefix(s string, nBytes int) string {
	if nBytes > len(s) {
		nBytes = len(s)
	}
	return s[:nBytes]
}

func runePrefix(s string, nRunes int) string {
	if nRunes <= 0 {
		return ""
	}
	i := 0
	for idx := range s {
		if i == nRunes {
			return s[:idx]
		}
		i++
	}
	return s
}

func main() {
	s := "Čaša"
	fmt.Println("bytes", len(s), "runes", utf8.RuneCountInString(s))
	fmt.Printf("unsafe: %q\n", unsafePrefix(s, 1))
	fmt.Printf("rune:    %q\n", runePrefix(s, 1))

	b := []byte(s)
	r := []rune(s)
	fmt.Println("byte0", b[0], "rune0", string(r[0]))

	num := 65
	fmt.Println("string(rune):", string(rune(num)))
	fmt.Println("Itoa:", strconv.Itoa(num))
}
```

#### What happens here

`Č` takes multiple bytes; `s[:1]` is not the first character — `unsafePrefix` can give an invalid UTF-8 prefix. `runePrefix` walks by `range` (rune boundaries) and cuts on a clean boundary. `string(65)` / `string(rune(65))` gives `"A"`, not `"65"` — a classic trap; `strconv.Itoa` gives decimal text. For user text always ask: “byte or character?” before slicing, truncating for UI, or limits in a database.

**Predict the result:** For `s := "Ž"`, what is `len(s)` and what is `utf8.RuneCountInString(s)`?

**Answer:** `len` is 2 (typical for UTF-8 `Ž`); rune count is 1.

### Example 5 — Blank identifier and named result preview

```go
package main

import (
	"fmt"
	"os"
	"strconv"
)

func parsePort(s string) (port int, err error) {
	if s == "" {
		err = fmt.Errorf("empty port")
		return // named result: returns port=0, err
	}
	port, err = strconv.Atoi(s)
	return
}

func main() {
	fmt.Println(parsePort("8080"))
	fmt.Println(parsePort(""))

	n, err := strconv.Atoi(os.Args[0]) // Args[0] is the path — intentionally bad input
	_ = n
	if err != nil {
		fmt.Println("expected error:", err)
	}
}
```

#### What happens here

Named results (`port`, `err`) are declared in the signature — bare `return` returns their current values (zero if not set). Useful in short functions; in long ones it can confuse (hidden return). `_ = n` shows the blank identifier when you deliberately ignore a value. Do **not** do `n, _ := strconv.Atoi(...)` in production without reason — you swallow `error`. Here `err` stays in focus.

## Decision analysis

| Decision | Option A | Option B | When you choose |
|----------|----------|----------|-----------------|
| Declaration | `var x T` | `x := v` | A for zero / later assignment; B when you have a value immediately |
| Error in if | shadow `err` in `if` | unique `parseErr` | A for a short guard; B when `err` lives on in the function |
| Number as text | `strconv` | `fmt.Sprintf` | A for simple conversions; B for formatted output |
| String prefix | byte slice | rune-aware | A for protocols/bytes; B for UI text |
| Map field | zero nil + documentation | `make` in constructor | B when writes must work immediately |
| Package var | global counter | parameter / struct field | B for testability; A only for narrow cases |
| Named result | bare `return` | explicit `return a, b` | A in short functions; B when readability suffers |

Zero value API: design structures so that `var t T` is usable. Short declaration reduces type noise, but requires attention to scope. Explicit conversions are verbose — intentionally, so loss of precision is visible (`int64` → `int` on 32-bit).

## Trade-offs

- **Zero values** — fewer constructors, more hidden default meanings.
- **`:=`** — writing speed vs shadows and type inference you do not see in review.
- **Package-level mutable var** — convenient, bad for tests and concurrency.
- **Working with `[]byte` instead of string** — fewer allocations, more mutation risks.
- **Linter shadow** — sometimes noise, often saves production.
- **Named result** — shorter return, less obvious data flow.
- **`string` immutability** — safety from accidental mutation vs allocations on change.

## Common mistakes

1. `s[:n]` for “n characters” on Unicode text.
2. `string(i)` to print a number.
3. Shadowing that swallows an outer error (`token`, `err` in a long scope).
4. Assuming `int` is always 64-bit.
5. Reading “uninitialized” as in C — in Go it is zero, but maybe not what you want.
6. `:=` instead of `=` when you only change existing names with no new name — does not compile.
7. Exporting a struct with a nil map field that later panics on write.
8. Ignoring `error` via `_` “temporarily” that stays forever.
9. Mixing `byte` and `rune` in loops over a string.
10. Relying on the order of package `var` init across files without need.

## Idiomatic Go

- New names instead of deep shadowing, except a short `err`.
- `var p T` when you want zero; `:=` when you have a value immediately.
- `strconv` / `fmt` for textual form of numbers.
- Document the meaning of zero value for exported types.
- Use `utf8` / `[]rune` when counting characters.
- Blank `_` only when you truly do not need the value — not to hide errors.
- Capital letter = exported; lowercase = package-private.
- Prefer small scopes: init in `if` keeps `err` local.

## Practical scenario

A service shortens notification titles to 80 “characters” with `title[:80]`. In production, a title with an emoji at position 78 produces invalid UTF-8 and the client JSON parser breaks. Fix: `runePrefix` (or a safe truncate library). Second incident: `token, err := auth(); if cond { token, err := refresh(); ... }; use(token)` — the inner `token` shadows, outside remains an expired token. Review introduces a ban on shadowing `token`/`client` in the linter config. Third: zero value `var cache map[string]User` in a struct panics on the first write — the constructor does `make`. The team adds to the coding standard: “every map/channel/pointer field must have documented zero behavior or a constructor”.

## Check questions

1. **What does `:=` require in a block?**  
   At least one new name on the left.

2. **Is a nil slice the same as an empty slice from `make`?**  
   No — both have `len` 0, but `== nil` distinguishes them; `append`/`len` behavior is similar.

3. **What is shadowing?**  
   An inner declaration of the same name hides the outer one.

4. **Why can `s[:1]` be wrong?**  
   It can cut through a UTF-8 code point.

5. **How do you convert int to textual decimal form?**  
   `strconv.Itoa` / `fmt.Sprint`, not `string(int)`.

6. **What is the zero value for `bool` and for a pointer?**  
   `false` and `nil`.

7. **Does `:=` work at package level?**  
   No — only inside a function.

8. **Why does writing to a nil map panic while reading does not?**  
   Reading returns the zero value of the value type; writing requires an allocated hash table.

If a linter reports shadowing, do not turn it off immediately — read whether the shadow hides an error or is an intentional short err/ctx scope.

## Summary

Variables in Go are deterministically zero-initialized, strictly typed, and scoped by blocks. Short declaration and shadowing require discipline; string indices are bytes. These traps separate “works on a laptop” from a reliable service. Next: creating and debugging programs.
