# 02.11 Concurrent Programming

## Lesson goals

After this lesson you will be able to:

- start a **goroutine** with `go`
- distinguish **concurrency** from **parallelism**
- use an unbuffered **channel** for signal and data, with a concrete trace of who blocks
- close a channel (`close`) and read with `range`
- write a basic `select`
- synchronize completion with `sync.WaitGroup`
- explain a data race and why you run `go test -race`

This is an **introduction**, not a catalog of all patterns (worker pool, pipeline, `context` cancel — later).

## Prerequisite

- Functions, **closure**, `error` (02.08–02.10)
- Basic `for`, **slice**
- Go 1.22+

## Problem this lesson solves

Network and I/O programs spend time waiting. Sequential code does one thing at a time. Go offers light goroutines and channels — but a wrong shared variable gives a data race. Without WaitGroup the program exits before work finishes.

**A goroutine is not an OS thread.** The runtime schedules many goroutines onto fewer OS threads (M:N). **Concurrency** is not the same as **parallelism**.

## Mental model

**Goroutine** — a concurrent flow scheduled by the Go runtime. Cheaper to start than an OS thread, but shares process memory. Do not call it a thread.

**Concurrency** = structure: more tasks *progress* (often by overlapping waits).  
**Parallelism** = truly simultaneous on multiple cores.

**Channel** — a typed pipeline. Unbuffered: send and receive **meet** (rendezvous) — one side **blocks** until the other is ready.

**WaitGroup** — a counter of “how many are still working.” `Add` / `Done` / `Wait`.

**Data race** — two goroutines, same memory, at least one write, without synchronization. Detector: `-race`.

## Mechanism

### The `go` statement

```go
go doWork(x)
```

Starts `doWork` concurrently. The caller **does not wait**. When `main` (the process) finishes, all remaining goroutines vanish with the process.

### Unbuffered channel — who blocks

```go
ch := make(chan string)

go func() {
	ch <- "message" // blocks until someone receives
}()

msg := <-ch // blocks until someone sends
```

Concrete trace:

| Moment | Goroutine A (`main`) | Goroutine B |
|--------|----------------------|-------------|
| 1 | creates `ch` | — |
| 2 | starts B with `go` | begins |
| 3 | reaches `msg := <-ch` → **blocks** (no data) | works |
| 4 | still blocks | `ch <- "message"` → **rendezvous**, sends |
| 5 | receives, unblocks | finishes |
| 6 | prints `msg` | — |

If B tries to send and A **never** receives — B stays blocked forever (leak / deadlock pattern). If A reads and B **never** sends — A blocks forever.

**Predict the result:** reverse the order — first `ch <- "x"` in `main` (without another goroutine), then only then `go` the receiver. What happens?

**Answer:** `main` blocks on send immediately; the receiver never starts → deadlock. That is why an unbuffered channel requires that the “other side” already exists or is in another goroutine.

### Buffered channel (mention only)

`make(chan int, n)` allows up to `n` sends without a current receiver. It changes the semantics. In this lesson we stay on unbuffered for clear synchronization.

### `close` and comma-ok

```go
close(ch)
v, ok := <-ch // ok=false when closed and empty
```

- The **sender** closes (one owner).
- Sending on a closed channel → `panic`.
- Reading a closed one: **zero value** of the type; `ok` distinguishes.

### `range` over a channel

```go
for v := range ch {
	// ...
}
```

The loop runs until the channel is closed (and the buffer drained). If nobody closes — `range` waits forever.

### WaitGroup — trace

```go
var wg sync.WaitGroup
wg.Add(1)          // before go!
go func() {
	defer wg.Done()
	// work
}()
wg.Wait()          // blocks until counter != 0
```

Trace with 2 tasks:

| Step | Counter | Who waits |
|------|---------|-----------|
| `Add(1)` ×2 | 2 | — |
| `go` ×2 | 2 | — |
| `Wait` | 2 | `main` **blocks** |
| first `Done` | 1 | `main` still waits |
| second `Done` | 0 | `main` unblocked |

`Add` **after** `go` → race: `Wait` can see 0 too early. Pass `*sync.WaitGroup` (**pointer**), not a copy.

### `select`

```go
select {
case v := <-ch:
	fmt.Println(v)
case <-time.After(time.Second):
	fmt.Println("timeout")
}
```

Picks the first ready case. If two are ready — **randomly** one. That is concurrency: you wait for *one of* the events without a spin-loop.

### Data race

```go
n++ // from multiple goroutines without sync → race
```

Fixes: channel (ownership by message), `sync.Mutex`, `sync/atomic`. Detection: `go run -race` / `go test -race`.

### Concurrency vs parallelism

One goroutine on one core still gives concurrency (overlapping I/O). Parallelism needs more cores and work that can run in parallel. A channel “works” even with one core.

## Rules and syntax

1. Do not close a channel from the receiver side.
2. Sending on a closed channel → `panic`.
3. Reading a closed one → zero value; use `ok`.
4. `WaitGroup`: `Add` before `go`; `Done` in `defer`; do not go below zero.
5. Shared maps/variables: mutex, channel, or atomic — not “I hope.”
6. End of `main` kills the process and other goroutines.
7. Do not call a goroutine a “thread.”
8. In a loop + `go` on 1.22+: per-iteration variables; you may still pass an argument for clarity.

## Examples

### Example 1 — Goroutine + unbuffered channel

```go
package main

import "fmt"

func main() {
	ch := make(chan string)
	go func() {
		ch <- "message from goroutine"
	}()
	msg := <-ch
	fmt.Println(msg)
}
```

#### What happens here

`main` blocks on receive; the sender blocks on send until they meet. Synchronization + data. We did not create an OS thread API — we started a goroutine.

### Example 2 — close + range

```go
package main

import "fmt"

func main() {
	ch := make(chan int)
	go func() {
		for i := 1; i <= 3; i++ {
			ch <- i
		}
		close(ch)
	}()
	for n := range ch {
		fmt.Println("received", n)
	}
	fmt.Println("range done")
}
```

#### What happens here

The sender closes after the last value. `range` finishes only then. Without `close`, `main` waits forever.

### Example 3 — WaitGroup

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

func main() {
	var wg sync.WaitGroup
	tasks := []string{"A", "B", "C"}
	for _, t := range tasks {
		wg.Add(1)
		go func(name string) {
			defer wg.Done()
			time.Sleep(50 * time.Millisecond)
			fmt.Println("done", name)
		}(t)
	}
	wg.Wait()
	fmt.Println("all finished")
}
```

#### What happens here

The `name` argument makes ownership clear (closure in a loop). `Wait` blocks until the counter falls to 0. Without `Wait`, `main` often exits before the print. On Go 1.22+ even without the argument the loop would be OK because of per-iteration variables.

### Example 4 — select + timeout

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	ch := make(chan string)
	go func() {
		time.Sleep(200 * time.Millisecond)
		ch <- "late response"
	}()
	select {
	case msg := <-ch:
		fmt.Println("got:", msg)
	case <-time.After(100 * time.Millisecond):
		fmt.Println("timeout")
	}
}
```

#### What happens here

The timeout case is ready first → print `timeout`. Concurrency: you wait for one of the events.

### Example 5 — Intentional data race

```go
package main

import (
	"fmt"
	"sync"
)

// go run -race .
func main() {
	var wg sync.WaitGroup
	var n int
	for i := 0; i < 1000; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			n++ // INTENTIONAL race
		}()
	}
	wg.Wait()
	fmt.Println("n=", n)
}
```

#### What happens here

Many goroutines write `n`. The print may look “almost correct”; `-race` reports the conflict. Parallelism often worsens visibility — a race is a bug even when it “passes.”

### Example 6 — Channel instead of a shared counter

```go
package main

import "fmt"

func main() {
	ch := make(chan int)
	const workers = 100
	for i := 0; i < workers; i++ {
		go func() { ch <- 1 }()
	}
	sum := 0
	for i := 0; i < workers; i++ {
		sum += <-ch
	}
	fmt.Println("sum=", sum) // 100
}
```

#### What happens here

No shared `n++`. Ownership of `sum` stays in `main`. Share memory by communicating.

## Decision analysis

| Decision | Motive |
|----------|--------|
| Unbuffered for intro | Clearer synchronization / blocking |
| WaitGroup for join | Simpler than channel-only-for-join |
| `select` + timeout | Prevents eternal blocking |
| `-race` in CI | Catches races that “pass” |
| goroutine ≠ thread | Accurate runtime model |

## Trade-offs

- Goroutines are cheap, not free.
- A channel can hide a deadlock.
- A buffered channel is easy to abuse as an uncontrolled queue.
- Mutex vs channel — both legitimate; learning starts from channel.
- `-race` slows tests.

## Common mistakes

1. **Exiting main before the end**
   ```go
   go work()
   // no Wait — process vanishes
   ```
   Fix: WaitGroup or receive from a channel.

2. **close from multiple senders** → panic. One close owner.

3. **Shared map without a lock** → race / panic.

4. **`Add` inside a goroutine**
   ```go
   go func() { wg.Add(1); ... }()
   wg.Wait() // race
   ```
   Fix: `Add` before `go`.

5. **`range` without close** → eternal blocking.

6. **Copying WaitGroup by value** — pass a pointer.

7. **Calling a goroutine a “thread”** — wrong model.

8. **Sending in main before starting the receiver** on unbuffered → deadlock.

## Idiomatic Go

- Prefer message communication when learning.
- Document who closes the channel.
- In tests: `-race`.
- Later: `context` for cancellation — here know that it exists.
- Small goroutines with one job.
- Write “goroutine” and “channel” as the official terms.

## Practical scenario

A service sends email in the background. First PR: `go sendEmail()` without WaitGroup in a migration — SMTP is cut off. Second: WaitGroup. Third: `stats.sent++` without a mutex — `-race` catches it. Team: every PR with `go` must pass `-race`. Review rejects “spawn thread” — asks for “start goroutine.”

## Check questions

1. **What does `go f()` do?**  
   Starts `f` in a new goroutine — it is not 1:1 creation of an OS thread.

2. **What characterizes an unbuffered channel?**  
   Send and receive meet; one side blocks until the other is ready.

3. **Who closes a channel?**  
   Typically the sender (one owner).

4. **What is WaitGroup for?**  
   Wait for a group to finish (`Add`/`Done`/`Wait`).

5. **What is a data race?**  
   Concurrent access with a write without sync; `-race` detects it.

6. **Concurrency vs parallelism?**  
   Structure vs simultaneous on cores.

7. **Why is a goroutine not a thread?**  
   A thread is an OS thread; a goroutine is a lighter flow (M:N).

### One more blocking trace: 2-step pipeline

```go
in := make(chan int)
out := make(chan int)

go func() {
	for v := range in {
		out <- v * 2
	}
	close(out)
}()

go func() {
	in <- 1
	in <- 2
	close(in)
}()

for v := range out {
	fmt.Println(v)
}
```

Who blocks when:

1. The first goroutine waits on `in` (range).
2. The second sends `1` → rendezvous → the first receives.
3. The first sends `2` on `out` → `main` must receive from `out` or else the first blocks.
4. After `close(in)`, range on `in` finishes; `close(out)`; `main` range finishes.

If `main` does not read `out` fast enough, the sender on `out` blocks — backpressure “for free” with an unbuffered channel.

### Mutex intro (one more sentence)

```go
var mu sync.Mutex
var n int
mu.Lock()
n++
mu.Unlock()
```

A mutex protects a critical section. For the intro prefer a channel when learning ownership; a mutex is a legitimate alternative when you share a structure in place. Never copy `sync.Mutex` by value (embed a pointer or do not export a struct that contains a mutex without documentation).

### What `-race` reports (how to read)

The report shows:

- two goroutines
- write/read locations
- stacks

First ask: “which variable?” then “which synchronization is missing?” Do not ignore “WARNING: DATA RACE” because the test “passes.”

### Example 7 — Wrong Add inside go (trap)

```go
// BAD
var wg sync.WaitGroup
for i := 0; i < 3; i++ {
	go func() {
		wg.Add(1) // LATE
		defer wg.Done()
	}()
}
wg.Wait() // can see 0 too early
```

Fix: `wg.Add(1)` **before** `go`.

### Example 8 — One sender, multiple values, then close

```go
package main

import "fmt"

func gen(n int) <-chan int {
	ch := make(chan int)
	go func() {
		for i := range n {
			ch <- i
		}
		close(ch)
	}()
	return ch
}

func main() {
	for v := range gen(3) {
		fmt.Println(v)
	}
}
```

#### What happens here

The factory returns a receive-only channel (`<-chan int`). The sender is hidden in a goroutine; it closes. The caller only reads. This is a small idiomatic pattern before a worker pool.

### Table: who blocks on an unbuffered channel

| Situation | Sender | Receiver |
|-----------|--------|----------|
| Nobody receives | blocked on `ch <-` | — |
| Nobody sends | — | blocked on `<-ch` |
| Both ready | rendezvous, both continue | rendezvous |
| Channel closed, read | — | zero value, `ok=false` |
| Send on closed | **panic** | — |

Print this table next to example 1 while you practice — that is the whole unbuffered channel model.

### Why not “just sleep instead of WaitGroup”

```go
go work()
time.Sleep(time.Second) // BAD
```

Sleep “works on my laptop” while the job is faster than a second. Under load or slower CI — flaky. WaitGroup / channel is a completion signal, not a time guess.

### Mini FAQ

**Q: How many goroutines may I create?**  
A: Thousands are common for I/O. Millions without backpressure — a problem. Measure and limit (later patterns).

**Q: Does a channel copy the value?**  
A: The value is sent (a copy). For large structs send a pointer deliberately.

**Q: Do I need parallelism for a channel to work?**  
A: No. Concurrency works on one core too.

### Example 9 — Two receivers, one sender (caution)

If two goroutines read from the same channel, values are **distributed** (each value goes to one receiver). That is fan-out. Do not expect both to get the same message. For broadcast you need another pattern (later).

### Example 10 — Done channel instead of WaitGroup (alternative)

```go
done := make(chan struct{})
go func() {
	// work
	close(done)
}()
<-done // wait for signal
```

`struct{}` carries no data — only a signal. WaitGroup is better for N tasks; a done channel is simple for one.

### Example 11 — Select default (non-blocking poll)

```go
select {
case v := <-ch:
	fmt.Println("got", v)
default:
	fmt.Println("nothing ready")
}
```

`default` makes `select` non-blocking. Use rarely and deliberately — you easily turn it into a busy spin if you put it in a `for` without sleep/blocking.

### What the runtime does with `go`

Simplified:

1. Creates a new goroutine (small stack at the start).
2. Puts it in the scheduling queue.
3. The M:N scheduler assigns it to an OS thread when there is work.
4. On blocking on channel/I/O, the thread can do other work.

That is why thousands of goroutines are not thousands of OS threads. That is why you do not call them threads.

### Concurrency checklist (intro)

- [ ] `Add` before `go`
- [ ] `Done` in `defer`
- [ ] one `close` owner
- [ ] `main` waits for the end (WaitGroup/channel)
- [ ] no shared write without sync
- [ ] `-race` run at least once
- [ ] you do not use sleep as join

### Example 12 — Concrete deadlock (intentional)

```go
ch := make(chan int)
ch <- 1 // main blocks forever — nobody receives
```

Run and interrupt the process. The runtime message about deadlock (when all goroutines sleep) is a signal that the communication model is wrong — not that “Go does not work.”

### Example 13 — Correct rendezvous in two lines of mental model

1. Every `ch <- x` must have a matching `<-ch` (sometime, somewhere).
2. Every `range ch` must have `close(ch)` (from the owner) or another exit.

If you break (1) or (2) — you block.

### Takeaway sentence

**A goroutine is a cheap unit of work; a channel is a rendezvous; WaitGroup is an end counter; a race is a bug even when the test passes.**

### Example 14 — Multiple Done calls by mistake

```go
wg.Add(1)
go func() {
	wg.Done()
	wg.Done() // panic: negative WaitGroup counter
}()
```

`Done` exactly once per `Add(1)`. That is why `defer wg.Done()` — once, even on early return.

### Example 15 — Channel closed, values still in the buffer

For unbuffered there is no “remainder.” For buffered (mention): `close` + `range` delivers remaining values then stops. That is why the intro stays on unbuffered — fewer hidden states.

### Example 16 — The main goroutine is also a goroutine

`main` runs in goroutine #1. That is why the same rules apply: if `main` finishes, the process vanishes. There is no special “main thread” semantics as in some UI frameworks.

### Decision map (short)

| You need… | Tool |
|-----------|------|
| Start work | `go` |
| Transfer value + sync | channel |
| Wait for N jobs | WaitGroup |
| Wait for A or B | `select` |
| Find a race | `-race` |

If you remember only the table above and the rule “Add before go,” most intro bugs disappear.

### One more predict

```go
ch := make(chan int, 1)
ch <- 1
close(ch)
fmt.Println(<-ch)
fmt.Println(<-ch)
```

**Answer:** first `1`, then `0` (zero value after close on an empty buffer). Buffered is a mention — but it shows why `ok` exists: `v, ok := <-ch` distinguishes zero value from “closed.”

1. Does `main` wait?
2. Is `close` unique?
3. Is there a race on a shared variable?
4. Did you run `-race`?

If yes/yes/no/yes — the intro is done.

### Quick recap

- `go f()` starts, does not wait
- `ch <-` / `<-ch` meet
- `close` + `range` close the flow
- WaitGroup: Add → go → Done → Wait
- `-race` does not lie

## Summary

Goroutines start concurrent work; a channel transfers data and blocks until rendezvous; `close`+`range` close the flow; `select` chooses ready communication; WaitGroup waits for the end. Concurrency ≠ parallelism; goroutine ≠ thread. A data race is measured with `-race`. Next: testing.
