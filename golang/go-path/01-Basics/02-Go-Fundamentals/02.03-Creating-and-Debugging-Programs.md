# 02.03 Creating and Debugging Programs

> **Go Path - Zero to Gopher** / **01 Basics → Go Fundamentals** / Lesson 02.03

## Lesson goals

After this lesson you should be able to:

- distinguish compiler errors, `go vet` findings, and test failures
- read compiler messages and go to the right line (first error first)
- use `fmt` / `log` debugging pragmatically and know what Delve is
- interpret a stack trace on panic
- recognize a typical nil pointer problem and turn it into an `error`
- know build tags at a mention level
- have a repeatable debugging flow: reproduce → isolate → fix → cover with a test

## Prerequisite

- 02.01 and 02.02
- a small module with `cmd/` and at least one package
- Go 1.22+ on PATH

## Problem this lesson solves

Beginners treat every red text the same. Compiler, vet, test, and runtime panic need different reactions. Without a method, people sprinkle prints everywhere or get lost in the debugger. This lesson builds a **practical order**: understand the signal → reproduce → isolate → fix → cover with a test. The goal is not Delve mastery — but not to panic when you see a stack.

## Mental model

Three times of error:

1. **Compile time** — the program does not build (`undefined`, `cannot use`, unused import).
2. **Static analysis time** — `go vet` / linters: the code builds, but is suspicious.
3. **Run time** — panic, wrong result, deadlock, wrong logical output.

```text
reproduce → shrink the example → read the message/stack →
hypothesis → check (print / test / breakpoint) → fix → regression test
```

Delve (`dlv`) is a debugger: breakpoint, step, print variables. You do not have to master it immediately; you must know it exists and when print is not enough (large state, timing, a loop with thousands of iterations).

A signal is not blame. A signal is data. First classify, then act.

## Mechanism

### Compiler — reading the message

```text
go build ./...
```

Typical form: `file.go:line:column: text`.

Reading rules:

1. Open the **first** error first — later ones are often a cascade.
2. The column shows where the parser/type checker “breaks”, not always where your intent is.
3. `undefined: X` — no declaration / wrong package / missing import.
4. `cannot use A as B` — types do not match; you need a conversion or another value.
5. `X declared and not used` — a local variable must be used or removed.

### vet — what build lets through

```text
go vet ./...
```

Example findings:

- wrong `Printf` verb (`%d` for a string)
- suspicious `copy` / `append` patterns
- some nil dereference patterns
- wrong struct tags (depending on version/analyzer)

Build can pass; vet may not. That is why CI needs both.

### Tests as a reproducer

```text
go test ./...
go test -v -run TestName ./package
go test -count=1 ./...
```

- A failing test ≠ compile error — logic or assertion.
- Cache of successful tests: `-count=1` forces a rerun.
- `-v` shows `t.Log` output.
- `-run` filters by test name regex.

### fmt / log debugging

```go
log.Printf("user=%s id=%d", u, id)
fmt.Printf("%#v\n", value)
fmt.Printf("%T %+v\n", value, value)
```

| Verb | Meaning |
|------|---------|
| `%v` | default value |
| `%+v` | struct with field names |
| `%#v` | Go-syntax representation |
| `%T` | type |
| `%q` | string with quotes |

`log` packages a timestamp (by default) — better for server flows. `fmt` is enough for a local demystifier.

### Panic stack — line by line

```text
panic: runtime error: invalid memory address or nil pointer dereference
goroutine 1 [running]:
main.(*Server).Start(0x0)
        /path/server.go:12 +0x20
main.main()
        /path/main.go:20 +0x30
```

How to read:

1. First line — **why** (nil pointer, index out of range, …).
2. Frames from the top — where it broke (`Start` on line 12).
3. Go down until you find **your** package (not only runtime internals).
4. Ask: which value is nil / out of range? where did it come from?

### Nil pointer mechanism

```go
var p *User
fmt.Println(p.Name) // panic: dereference nil
```

Method with a pointer receiver on nil:

```go
func (s *Server) Start() {
	fmt.Println(s.Addr) // panic if s == nil
}
```

Defense: constructor `New...`, check `if s == nil`, or return `error` instead of panic in libraries.

### recover — only for boundaries

```go
defer func() {
	if r := recover(); r != nil {
		log.Printf("panic caught: %v", r)
	}
}()
```

`recover` makes sense at goroutine / HTTP handler middleware boundaries, not as a replacement for `error` in ordinary logic. In this lesson use it only to see a stack in a demo — in the production mental model prefer `error`.

### Build tags (mention)

```go
//go:build integration

package store
```

The file enters the build only with `-tags=integration`. Must be at the top of the file, blank line before `package`. Used for optional integration tests / platform code. Do not abuse it for “commenting out” a whole file.

### Predict the result — type of error

Code:

```go
var x int = "seven"
```

**Question:** Does `go vet` or the compiler catch this?

**Answer:** The compiler — `cannot use "seven" (untyped string constant) as int`. Vet is never reached.

### Predict the result — Printf

```go
name := "Marko"
fmt.Printf("hello %d\n", name)
```

**Question:** Does `go build` pass? What does vet say? What does runtime print?

**Answer:** Build often passes. Vet reports a mismatched verb. Runtime prints something like `hello %!d(string=Marko)`.

## Rules and syntax

1. Fix the first compile error before the rest.
2. Do not commit `fmt.Print` debug forever — replace with a log level or remove.
3. Panic stack: your code first, not runtime internals.
4. `go test` caches successful tests — use `-count=1` when you suspect the cache.
5. Race conditions: `go test -race` when you touch concurrency (later courses).
6. The build tag line must be as close as possible to the top of the file, with a blank line before `package`.
7. Libraries: prefer `error` over panic for expected failures.
8. `t.Fatal` / `t.Fatalf` stops that test; `t.Error` records and continues.
9. A minimal reproducer before a large “refactor in the dark”.
10. One hypothesis = one experiment (do not change five things at once).

## Examples

### Example 1 — Reading a compile error

Deliberately wrong code (`cmd/broken/main.go`):

```go
package main

import "fmt"

func main() {
	var x int = "seven"
	fmt.Println(x)
}
```

```text
go build ./cmd/broken
```

The message says you cannot use `string` as `int` — the exact line.

Fix:

```go
package main

import (
	"fmt"
	"strconv"
)

func main() {
	x, err := strconv.Atoi("7")
	if err != nil {
		fmt.Println(err)
		return
	}
	fmt.Println(x)
}
```

#### What happens here

The compiler does not “guess” a conversion. The message is direct. After the fix, types match. Habit: do not change five things at once — one error, one fix, build again. If you add an unused import while fixing, you get a **new** first error — that is why format on save / organize imports helps keep the signal clean.

### Example 2 — Vet catches what build lets through

```go
package main

import "fmt"

func main() {
	name := "Marko"
	fmt.Printf("hello %d\n", name)
}
```

```text
go build .
go vet .
```

#### What happens here

A `Printf` format string is not in all cases a compiler “hard error” — vet fills the gap. That is why CI needs `go vet ./...` alongside build. Fix: `%s` instead of `%d`. In production a wrong verb can ruin metrics or log aggregation for months before someone notices `%!d`.

**Predict the result:** After replacing `%d` → `%s`, does vet still report?

**Answer:** Not for this case — verb and argument match.

### Example 3 — Panic, stack, nil, then error

```go
package main

import "fmt"

type Server struct {
	Addr string
}

func (s *Server) Start() {
	fmt.Println("listening on", s.Addr)
}

func main() {
	var s *Server
	defer func() {
		if r := recover(); r != nil {
			fmt.Println("caught for demo:", r)
		}
	}()
	s.Start()
}
```

Without recover (production mental model): remove the defer and run to see the real stack.

Better program:

```go
package main

import (
	"errors"
	"fmt"
)

type Server struct {
	Addr string
}

func NewServer(addr string) (*Server, error) {
	if addr == "" {
		return nil, errors.New("empty address")
	}
	return &Server{Addr: addr}, nil
}

func (s *Server) Start() error {
	if s == nil {
		return errors.New("nil server")
	}
	fmt.Println("listening on", s.Addr)
	return nil
}

func main() {
	s, err := NewServer("127.0.0.1:8080")
	if err != nil {
		fmt.Println(err)
		return
	}
	if err := s.Start(); err != nil {
		fmt.Println(err)
	}
}
```

#### What happens here

A nil receiver accessing a field panics. The `NewServer` constructor and checks turn a runtime panic into an `error`. The stack trace from the first example shows the exact `Start` line — learn to read the frame, not to guess. Debugging questions in order: “who is nil?” → “why was it not initialized?” → “how can the API prevent that next time?”.

### Example 4 — Test + log + Delve mention

`internal/mathx/div.go`:

```go
package mathx

import "fmt"

func Div(a, b int) (int, error) {
	if b == 0 {
		return 0, fmt.Errorf("division by zero")
	}
	return a / b, nil
}
```

`internal/mathx/div_test.go`:

```go
package mathx

import "testing"

func TestDiv(t *testing.T) {
	_, err := Div(1, 0)
	if err == nil {
		t.Fatal("expected error")
	}
	got, err := Div(9, 3)
	if err != nil || got != 3 {
		t.Fatalf("got=%d err=%v", got, err)
	}
}
```

```text
go test ./internal/mathx -v -count=1
```

When a test fails in a larger system:

1. Narrow with `-run TestDiv`
2. Add a temporary `t.Logf` or `log.Printf`
3. If you need state mid-loop: `dlv test ./internal/mathx` (intro: `break`, `continue`, `print`, `quit`)

#### What happens here

The test locks down behavior. `-count=1` disables the cache. Delve is not required for this bug — the test message is enough. Use the debugger when state is large, timing matters, or print pollutes. Do not learn all Delve commands at once: enough is reaching a breakpoint and printing a variable.

**Predict the result:** You change `Div` so that for `b==0` it returns `(0, nil)`. What does `TestDiv` do?

**Answer:** Fails on the first `t.Fatal("expected error")`.

### Example 5 — Table-driven test as diagnostics

```go
package mathx_test

import (
	"testing"

	"example.com/demo/internal/mathx"
)

func TestDivTable(t *testing.T) {
	tests := []struct {
		name    string
		a, b    int
		want    int
		wantErr bool
	}{
		{name: "ok", a: 9, b: 3, want: 3},
		{name: "zero", a: 1, b: 0, wantErr: true},
		{name: "neg", a: -8, b: 2, want: -4},
	}
	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			got, err := mathx.Div(tt.a, tt.b)
			if tt.wantErr {
				if err == nil {
					t.Fatalf("expected error")
				}
				return
			}
			if err != nil || got != tt.want {
				t.Fatalf("got=%d err=%v want=%d", got, err, tt.want)
			}
		})
	}
}
```

#### What happens here

A table-driven test gives named cases — failure shows `--- FAIL: TestDivTable/zero`. That is faster diagnostics than one monolithic test. `t.Run` creates a subtest. When debugging, run only the subtest: `go test -run TestDivTable/zero -count=1`. This is the bridge between “I have a bug” and “I have a regression test”.

### Example 6 — Index out of range stack

```go
package main

import "fmt"

func first(xs []int) int {
	return xs[0]
}

func main() {
	fmt.Println(first(nil))
}
```

#### What happens here

The panic message will be `index out of range` (or similar) — different from nil pointer. The stack shows `first` then `main`. The fix is not “catch with recover” — but a check `len(xs) == 0` and return `error`, or a contract that the caller does not send an empty slice. Learn to distinguish the **kind** of panic: nil, bounds, type assert — each has a different typical fix.

### Example 7 — Error with context (%w)

```go
package main

import (
	"errors"
	"fmt"
)

func openConfig(path string) error {
	if path == "" {
		return fmt.Errorf("open config: %w", errors.New("empty path"))
	}
	return nil
}

func main() {
	err := openConfig("")
	fmt.Println(err)
	fmt.Println(errors.Unwrap(err))
}
```

#### What happens here

`%w` wraps the error so that `errors.Is` / `errors.As` / `Unwrap` work. Production debugging often starts from a message with context (`open config: ...`) instead of a bare `empty path`. Habit: every boundary (`open`, `decode`, `dial`) adds a layer of context. That is not “log instead of error” — but an error that carries a trail.

**Predict the result:** What does `fmt.Println(err)` print?

**Answer:** Something like `open config: empty path`.

### Example 8 — Minimal reproducer checklist

When a bug “exists only in the large system”:

1. Copy the input that triggers it (JSON, flag, ID).
2. Make a `TestRepro` or `cmd/repro/main.go` with that input.
3. Strip dependencies while the bug remains.
4. When fewer than 30 lines remain — you have a reproducer.
5. Fix + leave the test.

#### What happens here

Without a reproducer, “fix” is guessing. With a reproducer, review and CI protect against regression. This discipline is worth more than any debugger trick. If you cannot reproduce, you do not yet understand the bug — keep shrinking, do not refactor at random.

### Example 9 — go test cache demonstration

```text
go test ./internal/mathx
go test ./internal/mathx
go test -count=1 ./internal/mathx
```

#### What happens here

The second call is often faster / “(cached)”. The third with `-count=1` forces execution. When a flaky test “passes locally after re-run”, suspect the cache or order. In CI scripts many teams put `-count=1` on critical packages.

## Decision analysis

| Decision | Option A | Option B | When you choose |
|----------|----------|----------|-----------------|
| Signal | print/`t.Log` | Delve | A for small state; B for deep state/timing |
| Nil in API | panic | `error` | B in libraries; A only for programmer invariants |
| CI check | build only | build + vet + test | Always B |
| Reproduction | manually in main | `go test` | B when you want regression in the repo |
| Build tag | integration files | always included | A when network/DB is needed |
| Test cache | default | `-count=1` | B when suspecting flaky/cache |
| Errors | `errors.New` | `fmt.Errorf` + `%w` | B when you keep the chain with context |

Why not panic in a library on nil? Because the caller can return 500 and a metric instead of crashing the process. Why test before the debugger? Because reproduction in a test stays in the repo.

## Trade-offs

- **Print debugging** — fast, dirties logs, changes timing (Heisenbug).
- **Delve** — precise, slower setup, learning curve.
- **Strict nil check** — verbose, fewer panics.
- **Vet** — rare false positives; still worth it.
- **Test cache** — speed vs “why does it not fail locally”.
- **recover at the boundary** — protects the process, can hide a bug if there is no log/metric.
- **Lots of `t.Log`** — useful with `-v`, noise without a filter.

## Common mistakes

1. **Fixing the last compile error first**  
   What happens: you change the cascade instead of the cause.  
   Why: later errors often disappear when you fix the first.  
   Fix: always the first compiler message first.

2. **Ignoring vet because build passes**
   ```go
   fmt.Printf("hello %d\n", name) // name is a string
   ```
   What happens: runtime prints `%!d(string=...)`.  
   Why: `Printf` is not always a hard error.  
   Fix: `go vet ./...`; verb `%s`.

3. **Empty recover without a log**
   ```go
   defer func() { recover() }()
   ```
   What happens: panic disappears silently.  
   Fix: log `r` and a metric.

4. **Debug print with PII in production** — remove before merge.

5. **“Cached test = fix”** — `go test -count=1`.

6. **Reading the stack from the bottom** — first the panic message and the top frame of your package.

7. **Changing five things at once** — one hypothesis, one experiment.

8. **`t.Error` where `t.Fatal` is needed** — continued on invalid state.

9. **Wrong build tag** — `//go:build` at the top + blank line before `package`.

10. **Fixing in “runtime” without a reproducer** — make a failing test first.

## Idiomatic Go

- `go test` / `go vet` / `gofmt` before every PR.
- Errors with context: `fmt.Errorf("open config: %w", err)`.
- Constructors `New...` return a ready object or an error.
- Log at boundaries; inside return `error`.
- Minimal reproducer before a large refactor.
- Document build tags in the README if they exist.
- Table-driven tests for edge cases.
- In CI: `go test ./...` + `go vet ./...` (+ linter per team agreement).

## Practical scenario

CI fails: locally green. Cause — cached test (`-count=1` reveals flaky). Second failure: panic in production, stack shows `cfg.DB.Ping` where `cfg` was loaded but the `DB` field is nil because YAML had no section — zero value. Fix: config validation at start returns `error`, the process does not start. Vet in CI catches a `Printf` bug before metrics go to Grafana with `%!s`. The team adds a short “Debugging checklist” to the handbook: reproduce, vet, test, stack, then Delve. Mentoring advice to a new member: “If you cannot write a failing test for the bug, you do not yet understand the bug.”

## Exercises

1. Deliberately make three compile errors (type, unused import, undefined); fix them in order from the first.
2. Insert a bad `Printf` and compare `go build` vs `go vet`.
3. Trigger a nil pointer panic; save the stack; then refactor to `error`.
4. Write `TestDiv` as above; deliberately break the implementation and read the `t.Fatal` output.
5. Run `go test -count=1 ./...` on your module.
6. Read `dlv --help` and once run `dlv test` on a package — only `help` / `quit` if you do not want to go deeper.
7. **Predict-then-run:** `first([]int{})` vs `first(nil)` — is the panic message the same?
8. Write a table-driven test with three cases; deliberately break one and run only that subtest via `-run`.

## Check questions

1. **Which error has priority — the first or the last compile?**  
   The first; the others are often consequences.

2. **Is vet a replacement for tests?**  
   No — static heuristics, does not check business logic.

3. **What do you read first in a panic dump?**  
   The panic message and the top frames of your package.

4. **Why `-count=1`?**  
   Disables caching of successful test results.

5. **What is a build tag for?**  
   Conditional inclusion of files in the build (e.g. integration).

6. **Why a constructor instead of panic on nil?**  
   Turns a runtime crash into a manageable `error` at the API boundary.

7. **What does `%#v` give?**  
   A Go-syntax representation of the value — useful for struct debug.

8. **Does `recover` replace `error`?**  
   No — reserved for boundaries; expected failures go as `error`.

### Workshop exercise — from panic to test

1. Write a function that panics on a nil pointer (deliberately).
2. Save the stack output in a note; mark the frame that is yours.
3. Refactor to `New` + `error`.
4. Write `TestNew_Empty` and `TestStart_NilReceiver` (the second can check error, not panic).
5. Insert a bad `Printf` and watch the difference `go build` vs `go vet`.
6. Run `go test -count=1 -v` and read the output as if you were in a CI log.

### Workshop exercise — reading someone else's stack

Take (or generate) a panic with three call levels (`main` → `run` → `load`). On paper answer:

1. What kind of panic is it?
2. What is your first frame?
3. Which variable is likely nil / out of range?
4. Which test would lock down the fix?

### Mechanism (continued) — log.SetFlags and noise

```go
log.SetFlags(log.LstdFlags | log.Lshortfile)
log.Printf("state=%v", state)
```

`Lshortfile` adds file:line — useful while you look for where a print lives. In production a structured logger (later) replaces ad-hoc `log.Printf`, but for local debug this is enough. Do not log secrets (tokens, passwords, PII).

### Mechanism (continued) — difference t.Error and t.Fatal

```go
if got != want {
	t.Errorf("got %v want %v", got, want) // continues the test
}
if err != nil {
	t.Fatalf("setup: %v", err) // stops immediately
}
```

After a failed setup `Fatal` prevents false follow-up errors. After an assertion in a table-driven subtest, `Fatal` in `t.Run` closes only that subtest — convenient.

### Example 10 — Intentional compile chain

```go
package main

import (
	"fmt"
	"strings" // deliberately unused in step 1
)

func main() {
	fmt.Println(hello()) // undefined in step 2
	var x int = "7"      // type in step 3
}
```

Fix **only the first** error the compiler reports, build again, repeat. The goal of the exercise is not a finished program — but the habit of order.

#### What happens here

The cascade disappears as the first errors disappear. If you “fix” the third while the first lives, you waste time. This mini-exercise should become muscle memory before larger projects.

### Debugging checklist (copy into the handbook)

```text
[ ] Do I reproduce the bug locally?
[ ] Is the signal compile / vet / test / panic?
[ ] Read the first error / top stack frame?
[ ] Do I have a failing test or a minimal main?
[ ] Am I changing one thing per attempt?
[ ] After the fix: go test -count=1 and go vet?
[ ] Temporary debug print removed?
```

If you cannot check the first three — you are not yet in the “write a fix” phase, but in the “understand the signal” phase.

Remember the order as a mantra: **signal → reproduction → hypothesis → one experiment → fix → test**. Everything else (Delve, print, intuition) is tools inside that order, not a replacement for it.

When stuck, return to the checklist — not “one more refactor”.

Debugging is a craft: slower at the start, faster after hundreds of signals.

## Summary

Debugging in Go starts by distinguishing compile / vet / test / runtime signals. Read messages and stacks, reproduce in a test, use print sparingly, reach for Delve when you need state. Nil and format bugs are common — constructors and vet reduce them. Next: deeper aggregate types.
