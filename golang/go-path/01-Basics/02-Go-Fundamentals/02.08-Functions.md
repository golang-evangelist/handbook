# 02.08 Functions

> **Go Path - Zero to Gopher** / **01 Basics → Go Fundamentals** / Lesson 02.08

## Lesson goals

After this lesson you can:

- treat functions as first-class values
- write a **closure** (a function that captures surrounding variables) and understand loop variable capture in Go 1.22+
- use a **higher-order function** (a function that takes or returns a function) to map behavior
- explain `defer` and LIFO order line by line
- apply the multiple-result idiom with `error` as the last result, including named result

## Prerequisite

- The packages lesson (02.07) or equivalent: you know `package`, exported and unexported names
- Basic types, `if`, `for`, slice
- Go 1.22+ (important for the loop semantics change)

## Problem this lesson solves

Without a clear model of functions, code becomes copy-paste blocks, and failures are “lost” in `panic` or ignored. Closures in a loop historically captured the wrong variable — in Go 1.22 the behavior changed, so you must know *what* holds today. `defer` without LIFO intuition closes files in the wrong order. A higher-order function without a clear type becomes magic nobody can read. This lesson connects functions-as-values, closure, higher-order function, `defer`, and the `error` idiom into one toolkit.

## Mental model

A function in Go is a **value with a type**, just as `int` is a value with a type. The type `func(int, int) int` describes a contract: two integers in, one integer out. A value of that type can live in a variable, an argument, a result, or a `map`. A function name (`Add`) and a **function literal** (`func(a, b int) int { ... }`) are two ways to obtain such a value.

A call and a reference are not the same thing. `Add(2, 3)` executes the body and yields `int`. `Add` without parentheses executes nothing: it is the function itself, and you may pass it to other code.

A **closure** is a function value that **uses variables from the function that created it**. Those variables are not its parameters. A closure does not photograph the number that was in the variable at that moment. It holds the variable itself, so it also sees later changes. That is why two calls to the same factory give two independent states, and two closures created in the same call share one state.

Since Go 1.22, the loop variable of `for i := range n` (and classic `for i := 0; i < n; i++`) gets a **new variable on each iteration**. A closure that captures `i` no longer shares one `i` across all iterations. Older code (pre 1.22) shared one `i` — that is why tutorials are still full of `i := i`.

`defer` says: “run this call when the **current function** exits”. Multiple `defer` = a stack (last registered, first executed). Arguments are evaluated immediately; only the call is deferred.

Multiple results: Go has no exceptions for expected failures. Typical contract: `(T, error)` — success when `err == nil`.

## Mechanism

### Function as a value

Start from a named function you already know:

```go
func Add(a, b int) int {
	return a + b
}
```

`Add` has type `func(int, int) int`. You do not write that type next to `func Add`; the compiler derives it from the parameter and result lists. You can write the same type by hand when you need a variable, parameter, or result:

```go
var op func(int, int) int
```

This line **does not create a function**. It creates a variable whose **zero value** is `nil`: there is not yet any function in it. Calling `op(2, 3)` in that state crashes the program (`panic`), because there is no body to execute.

Assignment without parentheses puts an existing function into the variable. The body does not run:

```go
op = Add          // reference: "this is Add"
sum := op(2, 3)   // call: execute whatever currently sits in op
```

`sum` is `5`. Variable `op` still holds `Add`. The next assignment **replaces** the function. The variable's type stays the same; only behavior changes:

```go
op = func(a, b int) int { return a * b }
fmt.Println(op(2, 3)) // 6
```

`func(a, b int) int { return a * b }` is a **function literal**: a function without a package name, created at that place in the code. The literal must have the same type as `op`. The compiler rejects an assignment whose signature does not match, for example `op = strings.ToUpper`.

Three things beginners mix up:

| Expression | What the result is | What you may do with it |
|------------|--------------------|-------------------------|
| `Add` | value of type `func(int, int) int` | assignment, passing, returning |
| `Add(2, 3)` | value of type `int` | computation, printing, further calls that need `int` |
| `op` while `nil` | empty function value | check `op == nil`; call is `panic` |

Parentheses are the boundary. `op = Add()` does not compile: `Add()` yields `int`, and `op` wants a function. `op = Add` compiles: both sides are `func(int, int) int`.

A function that takes a function does not know the name or body. It knows only the contract:

```go
func Apply(a, b int, fn func(int, int) int) int {
	return fn(a, b)
}

fmt.Println(Apply(2, 3, Add)) // 5
```

`Apply` is a **higher-order function**: one of its parameters is a function. The caller chooses the behavior (`Add` or a function literal), and `Apply` only applies the contract. That is why function type exists as a separate type, not only as declaration syntax.

The same function may be called by name or via a variable. `Add(2, 3)` and `op(2, 3)` after `op = Add` execute the same body. The variable is not a copy of the code. It points at that code. Later changes to local variables in `main` do not change `Add`, because `Add` does not use those variables. As soon as a function literal starts using surrounding variables, it stops being “just code” and becomes a **closure**. That is the next section.

### Closures

Look at a counter factory, line by line:

```go
func counter() func() int {
	n := 0
	return func() int {
		n++
		return n
	}
}
```

1. `counter` is not a counter. It creates a counter and returns it. Its result has type `func() int`: a function with no parameters that returns `int`.
2. `n := 0` is a local variable of **this** call to `counter`. The next call to `counter()` gets another variable `n`.
3. The returned function has no parameter `n`. The name `n` in its body is that outer variable. That capture is the **closure**.
4. When `counter` returns, its stack frame would otherwise disappear, and with it `n`. The returned function still uses `n`, so the compiler leaves that variable on the heap as long as the returned function lives. You do not write that by hand. You see the consequence: `n` survives the return from `counter`.
5. Every later call to the returned function does `n++` on the **same** variable. That is why a sequence of calls yields 1, then 2, then 3.

Distinguish two calls. A factory call creates state. A call to the returned function changes that state:

```go
a := counter()
b := counter()
fmt.Println(a()) // 1
fmt.Println(a()) // 2
fmt.Println(b()) // 1
fmt.Println(a()) // 3
```

`a` and `b` are two results of two calls to `counter()`, hence two separate `n`s. That is why `b()` starts from 1 even though `a` has already reached 2. The next `a()` continues from 2 to 3, because `b` did not touch `a`'s `n`.

**Predict the result:** if you do `a(); a(); b(); a()`, what is the sequence of numbers?

**Answer:** `1`, `2`, `1`, `3` — because `a` and `b` do not share `n`.

If from the same call you return two functions, they share that one variable:

```go
func pair() (inc, dec func() int) {
	n := 0
	inc = func() int { n++; return n }
	dec = func() int { n--; return n }
	return inc, dec
}
```

`up, down := pair()` then `up(); up(); down()` yields 1, 2, 1. `up` and `down` are not two counters. They are two operations on the same `n`, because both were created while one call to `pair` existed.

A second rule the counter example easily hides: a closure captures the **variable**, not the value as it was when the function literal was written.

```go
n := 10
inc := func() int {
	n++
	return n
}
n = 100
fmt.Println(inc()) // 101
```

The function literal was written while `n` was 10, but the call happens after `n = 100`. The body reads the variable as it is at call time, so the result is not 11. If you need a snapshot, make a new variable and capture that:

```go
snapshot := n
inc = func() int {
	snapshot++
	return snapshot
}
```

Now a later change to `n` does not touch `snapshot`. A parameter has the same effect: the value enters a new call variable, and the function literal does not share it with the outer `n`.

A string follows the same rule. A closure does not copy the text “once forever” unless you no longer change the outer variable. A string is immutable, but the variable that holds it may receive another string:

```go
prefix := "ord"
next := func() string { return prefix }
prefix = "usr"
fmt.Println(next()) // usr
```

In the `makeID` example later in the lesson, `prefix` is not changed after creation, so it looks as if it were copied. The model still holds: the variable is shared.

A closure is a good tool when state is small, local, and short-lived: an ID counter, a predicate that remembers a threshold, deferred cleanup. When the same state has several operations you want to pass as one unit, or expose as a package API, a **struct** with **method**s is clearer. A closure that captures ten surrounding variables is harder to read than explicit parameters.

### Loop and closure (Go 1.22+)

```go
funcs := make([]func() int, 0, 3)
for i := range 3 {
	funcs = append(funcs, func() int { return i })
}
```

In 1.22+ `funcs[0]()`, `funcs[1]()`, `funcs[2]()` return 0, 1, 2. Each iteration has its own variable `i`, and the function literal captures exactly that one.

**Historical trap (pre 1.22):** all three functions captured one shared `i`, which at the end of the loop remains 2 (after the last increment / last assignment), so all three calls would return 2. For code that must run on older versions still write `i := i` inside the loop: a new local variable per iteration, and you capture that. That is the manual version of what 1.22 does itself. The course assumes Go 1.22+.

The compiler does not “remember” loop history as a list. For each iteration (from 1.22) it creates a new variable and links the closure to *that* variable. The runtime then keeps those variables on the heap while slice `funcs` holds references to the closures.

### Higher-order functions

A **higher-order function** is a function whose at least one parameter or at least one result is again a function. That is not special language syntax — it is a way of using type `func(...)`.

Three common forms:

1. **Takes a function** — “do something with this behavior” (`Apply`, `filter`, `sort.Slice` with `less`).
2. **Returns a function** — a factory (`counter`, `makeID`, middleware factory).
3. **Takes and returns** — behavior transformation (`func(http.Handler) http.Handler`).

Walk through `filter` line by line with concrete values:

```go
func filter[T any](in []T, keep func(T) bool) []T {
	out := make([]T, 0, len(in))
	for _, v := range in {
		if keep(v) {
			out = append(out, v)
		}
	}
	return out
}
```

Call:

```go
nums := []int{1, 2, 3, 4}
even := filter(nums, func(n int) bool { return n%2 == 0 })
```

Execution trace:

| Step | `v` | `keep(v)` | `out` after step |
|------|-----|-----------|------------------|
| start | — | — | `[]` (len 0, cap 4) |
| 1 | `1` | `false` | `[]` |
| 2 | `2` | `true` | `[2]` |
| 3 | `3` | `false` | `[2]` |
| 4 | `4` | `true` | `[2 4]` |

`filter` does not know what “even” is. It only knows: for each element call `keep`; if `true`, append to `out`. The predicate is a function literal (here also a closure if it captures an outer variable). Generics (Go 1.18+) make the type safe without `any` as a runtime box for this pattern: `T` is `int` in this call.

Another example — a factory that returns a function:

```go
func greaterThan(threshold int) func(int) bool {
	return func(n int) bool {
		return n > threshold
	}
}

keep := greaterThan(3)
fmt.Println(filter([]int{1, 2, 3, 4, 5}, keep)) // [4 5]
```

`greaterThan(3)` creates a closure over `threshold == 3`. `keep` is a value of type `func(int) bool`. `filter` is still the same. The higher-order layer lets you compose behavior without changing the loop.

When **not** to use a higher-order function: when you have one loop called in one place and the predicate is one line. Then a plain `for` + `if` reads clearer. Use higher-order when the same algorithm (filter, retry, middleware) is needed multiple times with different behavior.

### `defer`

`defer` registers a call that will run **when the current function finishes** — whether by a normal `return` or by `panic` (before the panic propagates further, that function's defers still run).

Minimal trace:

```go
func demo() {
	fmt.Println("A")
	defer fmt.Println("B")
	fmt.Println("C")
}
// output: A, C, B
```

Why? The line `defer fmt.Println("B")` **does not print B immediately**. It tells the runtime: “push the call `Println("B")` onto the defer stack”. Then `C` is printed. Only on exit from `demo` does the runtime pop the defer stack (LIFO) and execute `B`.

Multiple `defer` — LIFO:

```go
func order() {
	defer fmt.Println(1)
	defer fmt.Println(2)
	defer fmt.Println(3)
}
// output: 3, 2, 1
```

**Predict the result:**

```go
func mystery() {
	n := 1
	defer fmt.Println(n)
	n = 2
	fmt.Println(n)
}
```

What is printed?

**Answer:** first `2` (ordinary `Println`), then `1`. Why not `2` then `2`? Because the **arguments** of the `defer` expression are evaluated **immediately** at registration. At the moment of `defer fmt.Println(n)`, `n` is `1`, so a call with argument `1` is pushed onto the stack. The later assignment `n = 2` does not change the already evaluated argument.

If you want defer to see a *later* value, use a function literal that reads the variable at execution time:

```go
func mystery2() {
	n := 1
	defer func() { fmt.Println(n) }()
	n = 2
	fmt.Println(n)
}
// output: 2, then 2
```

Here `defer` registers a call to a closure with no arguments. The closure captures variable `n`. On exit it reads the current `n`, which is `2`.

Classic resource pattern:

```go
f, err := os.Open(path)
if err != nil {
	return err
}
defer f.Close()
```

1. `Open` succeeds → `f` is not `nil`.
2. `defer f.Close()` registers Close of **that** `f` (receiver/argument is already bound).
3. Any later `return` from the function first runs `Close`, then returns the result to the caller.

If you put `defer f.Close()` **before** checking `err`, and `Open` fails, `f` may be `nil` and `Close` on a `nil` file is safe in the standard library for `*os.File`, but the pattern “defer right after successful acquisition” remains the rule for all resources (mutex, DB row, HTTP body).

**`defer` in a loop** — trap:

```go
for _, path := range paths {
	f, err := os.Open(path)
	if err != nil {
		return err
	}
	defer f.Close() // closes only at the end of the WHOLE function
	// read f ...
}
```

All files stay open until the end of the function. With thousands of paths that exhausts file descriptors. Solution: extract the iteration body into a helper — each call has its own defer stack:

```go
for _, path := range paths {
	if err := readOne(path); err != nil {
		return err
	}
}

func readOne(path string) error {
	f, err := os.Open(path)
	if err != nil {
		return err
	}
	defer f.Close()
	// ...
	return nil
}
```

### Multiple results and `error`

Go allows a list of results. Typical contract:

```go
func Parse(s string) (int, error) {
	n, err := strconv.Atoi(s)
	if err != nil {
		return 0, fmt.Errorf("Parse: %w", err)
	}
	return n, nil
}
```

Caller:

```go
n, err := Parse(s)
if err != nil {
	return err
}
// here it is safe to use n
```

What the runtime/compiler *does*:

1. The compiler checks that every `return` returns exactly as many values as the signature requires, of the right types.
2. There is no “implicit” `error` — if you ignore the second result with the blank identifier (`n, _ := Parse(s)`), the compiler stays quiet, but you lose the failure signal. That is a discipline error, not a syntax error.
3. The zero value for `int` on failure (`0`) is not a “magic sentinel” by itself — the sentinel is `err != nil`. Never conclude success from `n` alone.

**Named result** — names in the signature:

```go
func writeReport(dir, name, body string) (err error) {
	// ...
	defer func() {
		cerr := f.Close()
		if err == nil {
			err = cerr
		}
	}()
	// ...
	return nil
}
```

`err` is already declared as a result. A naked `return` or `return nil` writes into that variable. A closure in `defer` **sees the same** `err` variable (a closure captures the variable!). That is why defer can *append* a Close error if until then `err == nil`.

Without a named result you must use a local variable and return it explicitly — also valid, just longer. Use named result sparingly: when defer truly must modify the result.

Multiple results are not only `(T, error)`. They can be `(int, int, error)`, `(value, ok bool)` for the map lookup idiom, etc. Ecosystem convention: **`error` last**.

## Rules and syntax

1. Function type: `func(T1, T2) (R1, R2)`.
2. Named result: `func() (n int, err error)` — use sparingly; good for `defer` + modifying `err`.
3. Variadic parameters: `func Sum(xs ...int) int` — inside, `xs` has type `[]int`.
4. `defer` works only within a function; there is no package-level `defer`.
5. `go f()` starts a **goroutine** — a topic for later lessons; here only: `f` is still a function value.
6. A method is a function with a **receiver**; it can be taken as a value: `t.Method` or `Type.Method`.
7. No default arguments and no function-name overloading.
8. `panic` / `recover` are not a replacement for `error` — for expected failures use `error`.
9. Unused parameter: name it `_` or remove it; an unused result must be given the blank identifier explicitly if you do not bind it.
10. A closure captures the variable, not a snapshot of the value — unless you deliberately make a new local variable.

## Examples

### Example 1: First-class and a map of operations

```go
package main

import "fmt"

func main() {
	ops := map[string]func(int, int) int{
		"+": func(a, b int) int { return a + b },
		"*": func(a, b int) int { return a * b },
		"-": func(a, b int) int { return a - b },
	}

	a, b := 10, 4
	for name, fn := range ops {
		fmt.Printf("%d %s %d = %d\n", a, name, b, fn(a, b))
	}
}
```

#### What happens here

`map` `ops` has key `string` and value type `func(int, int) int`. Each function literal in the map is a separate function with that contract. The loop knows nothing about addition or multiplication: `name` is the key, `fn` is the function currently under that key, and `fn(a, b)` is the call. Adding an operation is a new map entry. The print loop does not change, because it depends only on the contract, not the body.

If a key does not exist, reading from the map gives the **zero value** of the function, i.e. `nil`. Calling that value is `panic`. That is why production code first checks `fn, ok := ops[name]` and rejects an unknown operator before calling. That is exercise 5.

`range` order over a map is not guaranteed — so in tests do not assert print-line order without sorting keys.

### Example 2: Closure counter and state isolation

```go
package main

import "fmt"

func makeID(prefix string) func() string {
	var n int
	return func() string {
		n++
		return fmt.Sprintf("%s-%04d", prefix, n)
	}
}

func main() {
	orderID := makeID("ord")
	userID := makeID("usr")
	fmt.Println(orderID()) // ord-0001
	fmt.Println(orderID()) // ord-0002
	fmt.Println(userID())  // usr-0001
	fmt.Println(orderID()) // ord-0003
}
```

#### What happens here

`makeID("ord")` is a factory call. In that call local variables `prefix` (value `"ord"`) and `n` (zero value `0` for `int`) are created. The returned function uses both, so both outlive the return from `makeID`. The result is stored in `orderID`.

`makeID("usr")` is a second call. It gets its own `prefix` and its own `n`. `userID` does not see `orderID`'s state.

The first `orderID()` does `n++` on its `n` and returns `ord-0001`. The second continues the same `n` and returns `ord-0002`. `userID()` starts from its zero and returns `usr-0001`. The next `orderID()` goes to `ord-0003`.

Nobody changes `prefix` here after return, so the output looks as if the text were copied into the closure. The model is still a shared variable: if after creating the function literal `makeID` did `prefix = "x"` before `return`, the returned function would print `x`, not the argument the caller passed.

### Example 3: Loop + closure in Go 1.22

```go
package main

import "fmt"

func main() {
	var handlers []func() string
	labels := []string{"alpha", "beta", "gamma"}

	for i, label := range labels {
		handlers = append(handlers, func() string {
			return fmt.Sprintf("%d:%s", i, label)
		})
	}

	for _, h := range handlers {
		fmt.Println(h())
	}
}
```

Expected output:

```text
0:alpha
1:beta
2:gamma
```

#### What happens here

Each iteration has its own `i` and `label` (Go 1.22+ per-iteration variables). Closures do not “see” the last loop value. Pre 1.22 all three calls would typically see the last `i`/`label` — a historical trap; for the course we assume 1.22+.

**Predict:** if inside the loop you add `label = "X"` *after* appending the closure, does an already created handler change its output? Not for *previous* iterations — they capture *their* `label` variables. For the *current* iteration, if you change `label` before the closure is ever called, that handler sees the changed value because it captures the variable.

### Example 4: `defer` LIFO, named result, and multiple results

```go
package main

import (
	"errors"
	"fmt"
	"os"
	"path/filepath"
)

func writeReport(dir, name, body string) (err error) {
	if err = os.MkdirAll(dir, 0o755); err != nil {
		return err
	}

	path := filepath.Join(dir, name)
	f, err := os.Create(path)
	if err != nil {
		return err
	}
	defer func() {
		cerr := f.Close()
		if err == nil {
			err = cerr
		}
	}()

	defer fmt.Println("defer A")

	n, err := f.WriteString(body)
	if err != nil {
		return err
	}
	if n == 0 {
		return errors.New("writeReport: empty write")
	}

	defer fmt.Println("defer B")
	fmt.Println("bytes written:", n)
	return nil
}

func main() {
	dir := filepath.Join(os.TempDir(), "gopath-defer")
	if err := writeReport(dir, "report.txt", "content\n"); err != nil {
		fmt.Println("failure:", err)
		return
	}
	fmt.Println("ok")
}
```

#### What happens here

1. `MkdirAll` — if it fails, you return `error` immediately; no open file, no defer for close.
2. `Create` — on success you register a defer that closes `f` and, if `err` is still `nil`, writes the Close error into named result `err`.
3. `defer fmt.Println("defer A")` goes onto the stack.
4. `WriteString` — on error `return err` still runs all defers (including Close).
5. `defer fmt.Println("defer B")` is registered **later**, so on exit it runs **before** A (LIFO): first B, then A, then the Close closure (exact order depends on registration order in your file — follow the stack).
6. Named result lets the Close error not disappear silently when the write succeeded.

`errors.New` here makes a plain `error`; deeper wrapping and `errors.Is` in 02.10.

### Example 5: Higher-order filter (generics)

```go
package main

import "fmt"

func filter[T any](in []T, keep func(T) bool) []T {
	out := make([]T, 0, len(in))
	for _, v := range in {
		if keep(v) {
			out = append(out, v)
		}
	}
	return out
}

func main() {
	nums := []int{1, 2, 3, 4, 5, 6}
	even := filter(nums, func(n int) bool { return n%2 == 0 })
	fmt.Println(even)

	words := []string{"go", "path", "function", "defer"}
	long := filter(words, func(s string) bool { return len(s) > 4 })
	fmt.Println(long)
}
```

#### What happens here

`filter` knows neither `int` nor `string` — it knows a predicate. Generics make a higher-order function type-safe. The predicate is a function literal (here without capturing outer state, so a closure in the narrower sense “captures the environment” is not necessary, but it is still a function value). The same algorithm works for two types without a copy-paste loop.

If the predicate captures an outer threshold (`minLen := 4`), it becomes a real closure over `minLen`.

## Decision analysis

| Decision | Motive | Alternative |
|----------|--------|-------------|
| `(T, error)` instead of panic | Expected failure is part of the contract | `panic` only for programmer bugs |
| Closure for local state | Without global variables | `struct` + method when the API grows |
| `defer Close` right after successful Open | Cleanup on every `return` | Manual Close on every branch — easy to forget |
| Named `err` + defer close | You do not lose the Close error | Local variable + explicit return |
| Map of function values / strategy | Extension without a huge `switch` | `switch` when the set of operations is small and closed |
| Local copy in a loop only if targeting &lt;1.22 | Document why `i := i` exists | On 1.22+ not needed for per-iteration semantics |
| Higher-order `filter` | One algorithm, many predicates | Inline `for` for one-off use |

## Trade-offs

- **Closures** are powerful, but harder to read if they capture too much outer state — prefer explicit parameters.
- **`defer` in a loop** holds resources until the end of the function, not the end of the iteration — extract the body into a helper.
- **Named result** can hide `return` (naked return) — use them idiomatically when they truly help (`defer` + `err`).
- **Variadic API** is convenient but hides slice allocation; for a hot path sometimes `[]T` is better.
- **Higher-order everywhere** can look like JavaScript; in Go a plain loop is often more readable.
- **Function value on a hot path** can be harder to inline than a direct call — measure before optimizing.

## Common mistakes

1. Capturing a loop from an old tutorial without checking the Go version (pre-1.22 mental model).
2. `defer f.Close()` when Open failed — defer only after checking `err`.
3. Ignoring `error`: `n, _ := strconv.Atoi(s)`.
4. Expecting `defer` to “return” a value to the caller — it does not; only side-effect (except via a named result you share with a closure).
5. Mixing `error` with `panic` for user-input validation.
6. A huge closure as “services” instead of types with methods.
7. `defer` in `for` without an extracted function → holding file descriptors until the end of the handler.
8. Calling a `nil` function value from a `map` without an `ok` check → `panic`.
9. Believing a closure copies `int`/`string` at the moment the literal is written.
10. Mixing `Add` and `Add()` when assigning to a function-typed variable.

## Idiomatic Go

- `error` last in the result list.
- Check `err` immediately, before using `T`.
- `defer` for unlock, close, rollback — near resource acquisition.
- Small functions; name is a verb (`Parse`, `Load`, `Close`).
- Do not export a closure as an API without need — better a named function or an **interface**.
- For constructor options: `type Option func(*Server)` is a common pattern (higher-order / function options).
- Document Go 1.22+ if the code depends on per-iteration loop semantics.

## Practical scenario

An API gateway logs every request. Middleware is `func(http.Handler) http.Handler` — a higher-order function. Inside, `defer` measures time: `start := time.Now()` then `defer func() { log.Print(time.Since(start)) }()` — a function literal so `Since` sees the real end, not an argument evaluated too early. In a worker pool, closures send work on a **channel**; after upgrading to Go 1.22, bugs disappear where all workers processed the same ID (old loop + closure trap). The team introduces a linter that forbids `_ = err` outside tests. The `writeReport` idiom with named `err` reduces lost errors on an NFS mount.

## Check questions

1. **What does it mean that functions are first-class in Go?**  
   **Answer:** They can be assigned to variables, passed as arguments, and returned from functions, because they have a type (`func(...)`).

2. **How does Go 1.22 change capturing a loop variable in a closure?**  
   **Answer:** Each iteration has its own loop variable, so closures see that iteration's value, not a shared last one. Pre 1.22 the shared variable was a trap.

3. **What is the execution order of multiple `defer` calls?**  
   **Answer:** LIFO — the last registered defer runs first on exit from the function.

4. **Why is `error` usually the last result?**  
   **Answer:** Ecosystem convention: the caller always knows where to look for the failure signal; tools and people expect that layout.

5. **When does `defer` evaluate arguments?**  
   **Answer:** Immediately at registration of the defer expression; only the call is delayed until the end of the function.

6. **What is a higher-order function?**  
   **Answer:** A function that takes and/or returns a function value — e.g. `filter` or middleware `func(Handler) Handler`.

7. **Why does `inc()` after `n=100` return 101, not 11?**  
   **Answer:** The closure captures variable `n`, not a snapshot of value 10.

## Summary

Functions are values: you compose them, return them, build closures over state. Go 1.22 fixes the classic loop trap (per-iteration variables); mention pre-1.22 only as a historical trap. A higher-order function composes algorithm and behavior through type `func`. `defer` is a cleanup stack with immediate argument evaluation. Multiple results with `error` (and named result when defer must append an error) is the basic contract of reliable Go code.
