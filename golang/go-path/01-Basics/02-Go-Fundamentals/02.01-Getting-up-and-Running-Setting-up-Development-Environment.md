# 02.01 Getting up and Running — Setting up Development Environment

> **Go Path - Zero to Gopher** / **01 Basics → Go Fundamentals** / Lesson 02.01

## Lesson goals

After this lesson you should be able to:

- install Go 1.22+ and verify that `go version` matches the expected line
- distinguish `GOROOT`, `GOPATH`, `GOMODCACHE`, `GOBIN`, and module-aware mode
- set up an editor (VS Code + `gopls`) with format on save and organize imports
- interpret `GOPROXY`, `GOPRIVATE`, `GOSUMDB`, and `go env` output
- create a local module with a `cmd/` layout and run `go run` / `go build` / `go vet`
- have a repeatable checklist for a new machine or a new team member

## Prerequisite

- administrative or user access to install software
- completed Getting Started module (concepts of `go run`, `go build`, `go.mod`)
- VS Code or another editor that supports the Language Server Protocol
- basic familiarity with a terminal (PowerShell, bash, or zsh)

## Problem this lesson solves

Without a correct environment you lose hours to a wrong PATH, an old toolchain, an editor that does not format, a proxy that blocks module downloads, and mixing the old GOPATH mental model with modules. A “weird import” is often not a bug in the code — the workspace root has no `go.mod`, or the `go` on PATH is not the one you think. This lesson sets up a reproducible workstation before deeper work with types, loops, and debugging.

## Mental model

The toolchain has several “roots” you need to distinguish:

1. **GOROOT** — where Go itself is installed (standard library, tools). You rarely change it by hand.
2. **GOPATH** — the historical workspace root; today it mostly holds the cache and `bin` for `go install` results. Your project **does not have to** live here.
3. **GOMODCACHE** — cache of downloaded module versions (often under `GOPATH/pkg/mod`).
4. **GOBIN** — optional: where `go install` puts binaries; if empty, `GOPATH/bin` is used.

The project lives wherever you want, with a `go.mod`. Module-aware mode is the default: commands look for `go.mod` upward from the current directory.

```text
                    ┌─────────────────┐
   go.dev/dl ──►    │  GOROOT (SDK)   │
                    └────────┬────────┘
                             │
   your code ──► go.mod ──►  │  go tool ──► GOMODCACHE (dependencies)
                             │
   go install ──► GOBIN or GOPATH/bin ──► PATH
```

`gopls` is the language server: autocomplete, jump-to-definition, diagnostics, formatting via `gofmt` / `goimports`.

`GOPROXY` says where `go` downloads modules from (e.g. `https://proxy.golang.org,direct`). `GOPRIVATE` excludes proxy/checksum rules for private paths.

## Mechanism

### Installation by platform

**Windows.** Prefer the official MSI from [go.dev/dl](https://go.dev/dl/). Alternative: `winget install GoLang.Go` if your team uses it. After the MSI **open a new** PowerShell — an old window often does not see the updated PATH.

**macOS.** Package from go.dev or Homebrew (`brew install go`). Check that the Homebrew version is not older than 1.22 if the course requires new loops.

**Linux.** The official tarball under `/usr/local/go` (and `export PATH=/usr/local/go/bin:$PATH`) gives a predictable version. Distro packages sometimes lag — always run `go version` before continuing.

After installation run:

```text
go version
go env GOROOT GOPATH GOMODCACHE GOMOD GOPROXY GO111MODULE GOTOOLCHAIN
```

You expect `go1.22.x` or newer. `GO111MODULE` today is usually `on` or empty (same effect for new projects). `GOTOOLCHAIN` controls whether `go` may pull a newer compiler according to `go.mod` — important for CI.

### PATH, line by line

`go` and tools (`gopls`, your `go install` binaries) must be on PATH.

1. `GOROOT/bin` — the `go` command itself.
2. `GOPATH/bin` or `GOBIN` — installed CLI tools.
3. On Windows often: `%USERPROFILE%\go\bin` alongside `C:\Program Files\Go\bin`.
4. On Unix: `$HOME/go/bin` alongside `/usr/local/go/bin`.

Check which `go` wins:

```text
# Windows PowerShell
Get-Command go | Format-List *
go version

# bash/zsh
which -a go
type go
```

If you see two installations, the first on PATH wins. That is the cause of “locally I have 1.22, but `go version` says 1.19”.

### Editor: VS Code + Go extension + gopls

Step by step:

1. Install the **Go** extension (Go team in the VS Code Marketplace).
2. Open any `.go` file — the extension suggests installing `gopls` and helper tools.
3. Accept the install, or do it manually:

```text
go install golang.org/x/tools/gopls@latest
```

4. Enable format on save and organize imports.

Illustrative `settings.json` fragment:

```json
{
  "go.useLanguageServer": true,
  "editor.formatOnSave": true,
  "[go]": {
    "editor.defaultFormatter": "golang.go",
    "editor.codeActionsOnSave": {
      "source.organizeImports": "explicit"
    }
  },
  "gopls": {
    "ui.semanticTokens": true
  }
}
```

What each setting does:

- `go.useLanguageServer` — VS Code talks to `gopls`, not the old legacy tool.
- `formatOnSave` — `gofmt` style with no debate in a PR.
- `organizeImports` — adds/removes imports; reduces “unused import” noise.
- `semanticTokens` — better identifier coloring (optional, UX).

**Workspace root.** Open the folder that **contains** `go.mod`. If you open a parent monorepo without `go.work`, `gopls` often cannot find the module. Solutions: open the module subfolder, or add a `go.work` that lists the modules.

### go env — reading and writing

Without `-w` it only reads. With `-w` it writes to the user env file (path: `go env GOENV`).

```text
go env GOPROXY
go env -w GOPROXY=https://proxy.golang.org,direct
go env -w GOPRIVATE=github.com/your-org/*
go env -u GOPRIVATE
```

`go env -u KEY` clears a persistent value. Do not mix shell `export` / `$env:` (temporary for the session) with `go env -w` (persistent for the `go` tool) without intention.

### GOPROXY, GOPRIVATE, GOSUMDB

Module dependency download flow:

1. `go` looks at the `go.mod` / `go get` request.
2. It looks up the module via the `GOPROXY` list (comma-separated; `direct` = VCS directly).
3. It verifies the checksum via `GOSUMDB` (default `sum.golang.org`), except for paths in `GOPRIVATE` / `GONOSUMDB`.

For private repos:

```text
go env -w GOPRIVATE=github.com/company/*
```

Without that, the public proxy often returns 404 for private code — it looks like “repo does not exist”, but actually the proxy has no access.

### First module on a clean machine

Windows (PowerShell):

```text
mkdir $env:USERPROFILE\dev\hello-env
cd $env:USERPROFILE\dev\hello-env
go mod init example.com/hello-env
mkdir -Force cmd\hello
```

Unix:

```text
mkdir -p ~/dev/hello-env/cmd/hello
cd ~/dev/hello-env
go mod init example.com/hello-env
```

`go.mod` after init looks roughly like:

```go
module example.com/hello-env

go 1.22
```

The `go 1.22` line documents the package **language level** (e.g. integer `range`, per-iteration loop variables). That is not just a “min version for docs” — it affects language semantics.

Minimal `cmd/hello/main.go`:

```go
package main

import "fmt"

func main() {
	fmt.Println("hello, environment")
}
```

Commands:

```text
go run ./cmd/hello
go vet ./...
go build -o bin/hello.exe ./cmd/hello
```

On Unix omit `.exe`. `go run` compiles to a temporary binary and runs it. `go build -o` writes the artifact where you say. `go vet` does static checks.

### go install versus go build

```text
go install ./cmd/hello
```

The binary goes to `$(go env GOBIN)` or `$(go env GOPATH)/bin`. It must be on PATH for `hello` to work from any directory.

| Command | Where the binary ends up | Typical use |
|---------|--------------------------|-------------|
| `go build -o dist/app` | where you say | CI artifact, deploy |
| `go install ./cmd/x` | GOBIN / GOPATH/bin | local CLI tools |
| `go run ./cmd/x` | temporary | quick development |

### go.work (briefly, for monorepos)

When you have several local modules in one workspace:

```text
go work init ./service-a ./service-b
```

`go.work` tells tooling how to wire local replacements. Do not commit `go.work` to every repo if the team does not want that — it is often a local file. Important: without `go.work` or an opened module folder, `gopls` at the monorepo root suffers.

### Predict the result — which go?

Imaginary PATH (Windows style, order matters):

```text
C:\OldGo\bin;C:\Program Files\Go\bin;%USERPROFILE%\go\bin
```

`C:\OldGo\bin\go.exe` is 1.19. `C:\Program Files\Go\bin\go.exe` is 1.22.4.

**Question:** What does `go version` print?

**Answer:** The line for 1.19 — the first `go` on PATH. Fix: remove `OldGo` or put the new Go first.

### Predict the result — GOMOD

You are in `C:\Users\Ana\dev\hello-env\cmd\hello` and there is a `go.mod` in `hello-env`.

**Question:** What is `go env GOMOD`?

**Answer:** The full path to `hello-env\go.mod`. If you are in `C:\Users\Ana\dev` (parent without `go.mod` and without `go.work`), `GOMOD` is empty — a signal that you are not in a module tree.

## Rules and syntax

1. Do not mix two Go installations on PATH without intention — the first `go` wins.
2. Projects with `go.mod` — module mode; do not set `GO111MODULE=off` out of nostalgia.
3. Do not edit `GOROOT` except for diagnostics.
4. Install tools (`gopls`) with an explicit version or `@latest` deliberately: `go install golang.org/x/tools/gopls@latest`.
5. CI should use the same major/minor as local, or a documented `GOTOOLCHAIN` policy.
6. `go env` without `-w` only reads; with `-w` it writes user configuration.
7. Import paths always use `/`, never `\` — even on Windows.
8. Workspace in the editor = folder with `go.mod` (or a valid `go.work`).
9. Do not commit `bin/` artifacts or local `go.work` if team agreement says otherwise.
10. After an MSI/Homebrew install always open a new terminal before diagnosing PATH.

## Examples

### Example 1 — Environment diagnostics

Module `example.com/envcheck`, file `cmd/envcheck/main.go`:

```go
package main

import (
	"fmt"
	"runtime"
)

func main() {
	fmt.Println("compiler:", runtime.Compiler)
	fmt.Println("version:", runtime.Version())
	fmt.Println("os/arch:", runtime.GOOS+"/"+runtime.GOARCH)
	fmt.Println("numCPU:", runtime.NumCPU())
}
```

Run:

```text
go version
go env GOVERSION GOROOT GOPATH GOMODCACHE GOPROXY GOMOD
go run ./cmd/envcheck
```

#### What happens here

`go version` and `runtime.Version()` should agree on the major/minor line. `runtime.Version()` comes from the compiled binary — if PATH points to one `go` and the program prints another, you are mixing toolchains. `GOMOD` shows the path to `go.mod` when you are inside a module; it is empty outside it. If `GOMOD` stays empty while you think you are in the project, you are not in a tree with `go.mod` or you are in the wrong cwd. This is the first step when “import does not work”. `GOOS`/`GOARCH` confirm the target platform — important when you later start cross-compiling (`GOOS=linux go build`).

### Example 2 — Module path and local import

`go.mod`:

```go
module example.com/hello-env

go 1.22
```

`internal/msg/msg.go`:

```go
package msg

func Greeting(name string) string {
	if name == "" {
		return "hello"
	}
	return "hello, " + name
}
```

`cmd/hello/main.go`:

```go
package main

import (
	"fmt"
	"os"

	"example.com/hello-env/internal/msg"
)

func main() {
	name := ""
	if len(os.Args) > 1 {
		name = os.Args[1]
	}
	fmt.Println(msg.Greeting(name))
}
```

```text
go run ./cmd/hello Marko
gofmt -w .
go vet ./...
```

#### What happens here

The module path in `go.mod` (`example.com/hello-env`) is the prefix of all import paths inside the project. `internal/` is special: code outside this module tree must not import `internal` packages — the compiler enforces that. An editor with `gopls` should jump to the `Greeting` definition (F12 / Go to Definition). If `gopls` reports “cannot find module”, restart the language server (`Go: Restart Language Server`) or check the workspace root. `go vet ./...` confirms that tooling sees the same packages as the compiler. `os.Args[1]` is the first argument after the program name — classic CLI input without the flag package.

**Predict the result:** `go run ./cmd/hello` without arguments.

**Answer:** `hello` — `name` stays `""`, the branch in `Greeting` returns the default string.

### Example 3 — go install and PATH

Same `cmd/hello` as above.

```text
go env GOBIN GOPATH
go install ./cmd/hello
```

On Windows look for `hello.exe` in `%USERPROFILE%\go\bin` (if `GOBIN` is not set). Open a **new** terminal:

```text
hello Marko
```

If it is “not recognized as a command”, PATH does not include that `bin`. Temporary check:

```text
# PowerShell
& "$(go env GOPATH)\bin\hello.exe" Marko
```

Experiment with `GOBIN`:

```text
mkdir $env:TEMP\mygobin
go env -w GOBIN=$env:TEMP\mygobin
go install ./cmd/hello
Get-ChildItem $env:TEMP\mygobin
go env -u GOBIN
```

#### What happens here

`go install` compiles and installs into the bin directory, unlike `go build -o` which writes where you say. For CLI tools you use globally (`gopls`, `staticcheck`, your helper), `go install` is convenient. For application artifacts in CI, more often `go build -o dist/...` because you control the name and path. `GOBIN` redirects the destination — useful for isolation, but easy to forget to reset (`go env -u GOBIN`). Understanding the difference prevents “where did my exe go”.

### Example 4 — Proxy, tidy, and checksum

In the same module:

```text
go env GOPROXY GOSUMDB GOPRIVATE
go get rsc.io/quote@v1.5.2
```

Then temporarily in `cmd/hello/main.go`:

```go
package main

import (
	"fmt"

	"rsc.io/quote"
)

func main() {
	fmt.Println(quote.Hello())
}
```

```text
go mod tidy
go run ./cmd/hello
```

`go.mod` gets a `require`, `go.sum` gets checksum lines. Remove the `quote` import, restore Hello World, then:

```text
go mod tidy
```

#### What happens here

The proxy speeds up and stabilizes downloads. `go.sum` protects integrity — if someone replaces the content of the same version, the checksum will not match. `go mod tidy` synchronizes `require` with the real import graph: adds what is needed, removes what is no longer imported. If you are behind a corporate firewall and `go get` fails, look first at `GOPROXY`, `GOPRIVATE`, TLS intercept, and Git credentials — do not “reinstall Go” immediately. For offline exercises the standard library is enough; this example deliberately touches the network so you see the real flow.

**Predict the result:** After `tidy` without the `quote` import, does `require rsc.io/quote` remain in `go.mod`?

**Answer:** It should not — `tidy` removes unused direct dependencies (indirect ones may remain in `go.sum` history in some cases, but the module is cleaned according to the graph). Main point: `tidy` is the source of truth for “what the project actually uses”.

### Example 5 — Mini-checklist script of the mental model

Not a required file in the repo — a personal note `SETUP.md`:

```text
[ ] go version >= 1.22
[ ] Get-Command go / which go shows the expected path
[ ] go env GOROOT shows the expected installation
[ ] GOPATH/bin or GOBIN on PATH
[ ] gopls responds (hover on fmt.Println)
[ ] Workspace root contains go.mod
[ ] go run ./cmd/... works
[ ] go vet ./... exits 0
[ ] GOPROXY reachable or corporate mirror configured
[ ] For private modules: GOPRIVATE set
```

#### What happens here

A checklist turns “feels configured” into measurable signals. Half of the “weird” errors while learning Go are the wrong binary on PATH or a workspace without `go.mod`. If any item fails, do not move on to types — fix the signal first. On a team the same list goes into a README “Developer Setup” and shortens onboarding from days to an hour.

### Windows and WSL notes

PowerShell and CMD can have a different PATH until you open a new window after an MSI install. WSL has a **separate** Linux Go — do not mix `C:\Program Files\Go` with `/usr/local/go` in the same session without intention. For paths in Go code prefer `path/filepath` and slash-agnostic APIs; in imports always `/`. Antivirus sometimes locks the `go-build` cache — symptom: slow or failed build; diagnosis: temporarily exclude scanning of `%LocalAppData%\go-build` (with IT approval).

### GOTOOLCHAIN and the go.mod line — in more detail

From Go 1.21+, the toolchain can honor the requirement from `go.mod`. Example:

```go
module example.com/hello-env

go 1.22
```

If locally you have Go 1.21, and the module requires 1.22 language features, behavior depends on `GOTOOLCHAIN` (e.g. `auto` may download a newer toolchain). In CI pin explicitly:

```text
# example CI idea, not a required script
go version
go env GOTOOLCHAIN
```

For the course: keep **Go 1.22+** locally and in notes. When you see an error like “integer range requires go1.22”, the problem is not the syntax you memorized — it is the language version tooling applies.

### Caches worth knowing

| Cache | Env / location | When you touch it |
|-------|----------------|-------------------|
| module download | `GOMODCACHE` | corrupted download, full disk |
| build cache | `go env GOCACHE` | weird incremental build |
| gopls | internal | restart language server |

Cleaning (carefully, slow afterward):

```text
go clean -modcache
go clean -cache
```

Do not do this routinely — only when diagnostics point to a broken cache. After `clean -modcache` the next build downloads dependencies again.

### Predict the result — import path

`go.mod` says `module example.com/hello-env`. The file is `internal/msg/msg.go`, package name `msg`.

**Question:** Which import string does `cmd/hello/main.go` use?

**Answer:** `example.com/hello-env/internal/msg` — module path + directory path. The package name (`msg`) is the identifier after the import, not necessarily the same as part of the path, but idiomatically they match.

### Diagnostic flow when “nothing works”

When the editor shows red or `go` cannot find a package, go in order — do not jump:

1. `go version` — is it the expected line?
2. `which go` / `Get-Command go` — is it the expected path?
3. `go env GOMOD` — are you in a module?
4. `go list ./...` — does tooling see the packages?
5. `gopls` restart — is the editor aligned with the CLI?
6. Only then change the code.

This order saves hours of false refactoring.

### Example 6 — go list as an X-ray

In the module root:

```text
go list ./...
go list -m all
go list -f "{{.Dir}} {{.ImportPath}}" ./...
```

#### What happens here

`go list ./...` lists the packages the module sees — if your new folder is not there, often a `package` clause is missing or the file is not saved. `go list -m all` shows the module graph (after dependencies). The `-f` format is for scripts and path diagnostics. Learn this command before you start “fixing” imports at random: first ask tooling what it sees.

**Predict the result:** You run `go list ./...` from a parent folder that has no `go.mod`.

**Answer:** An error in the style that it is not a module / cannot find — confirmation that cwd is not in a module tree. `cd` into the folder with `go.mod` and repeat.

### Example 7 — Reproducible go.mod and toolchain note

Add to personal notes (does not have to be in git):

```text
go version          → _______________
go env GOVERSION    → _______________
go env GOTOOLCHAIN  → _______________
go env GOROOT       → _______________

```

Run the same set on the CI agent (log) and compare. A major/minor difference = risk for integer `range` and other 1.22 behaviors.

#### What happens here

Reproducing “works on my machine” requires the same signals. A 30-second note prevents an hour of diagnosis. On a team this becomes part of the bug report template: paste a `go env` excerpt with the OS.

### Example 8 — Private module and 404 error

Thought-exercise simulation (no required private repo):

1. `GOPRIVATE` empty, `go get` toward `github.com/company/secret` → often 404 from the proxy.
2. Set `go env -w GOPRIVATE=github.com/company/*`.
3. Check Git credentials (`ssh -T git@github.com` or credential helper).
4. Retry `go get`.

#### What happens here

404 is not always “repo does not exist” — it often means “proxy has no access”. Separating symptoms (network vs auth vs wrong path) is an environment skill, not a language skill. Write in the team checklist: “404 on private → first GOPRIVATE”.

## Decision analysis

| Decision | Option A | Option B | When you choose |
|----------|----------|----------|-----------------|
| Editor | VS Code + gopls | GoLand | A: common denominator, free; B: richer IDE, paid |
| Project location | anywhere + `go.mod` | inside GOPATH/src | Always A for new code |
| Persistent env changes | `go env -w` | system env vars | A for personal Go settings; B for machine IT policies |
| Artifact | `go build -o` | `go install` | A for deploy/CI; B for local CLIs |
| Proxy | public `proxy.golang.org` | corporate mirror | A for open source; B behind a firewall |
| Monorepo | open module folder | `go.work` | A for one service; B when working on several local modules at once |
| Version in CI | pin exact patch | major.minor + GOTOOLCHAIN | Pin for reproducibility; toolchain auto for team flexibility |

Why not keep projects in GOPATH? Because modules solve versions, location, and reproduction better. Why `go env -w` instead of only a shell profile? Because it is per-user, inspectable (`go env`), and less likely to break every shell you open.

## Trade-offs

- **Proxy** — speed and availability vs privacy / control over private code (`GOPRIVATE`).
- **gopls** — rich UX, uses CPU/RAM on large workspaces; sometimes needs a restart.
- **Global go install** — convenient, but tool versions can drift from the project; pin the version in the README.
- **One Go installation** vs multiple toolchains — simplicity vs need to test older versions.
- **Format on save** — consistency, but conflicts with the habit of manual formatting from other languages.
- **go.work in git** — easier monorepo onboarding vs local paths that differ by machine.
- **Distro package Go** — easier install vs outdated version below the course 1.22+.

## Common mistakes

1. Two Gos on PATH; `go version` shows the old one.
2. Wrong folder opened in VS Code (parent without `go.mod` / without `go.work`).
3. `GOPATH` mental model: copying code into `src/...` “so it works”.
4. Blocked proxy without `GOPRIVATE` for internal modules.
5. `gopls` not installed or outdated; editor “dumb”.
6. Mixing up `GOBIN` and expectations of where the binary is.
7. CI uses Go 1.20 while locally you use 1.22 `for range n` loops.
8. Old terminal after MSI — PATH not refreshed.
9. Mixing Windows Go and WSL Go in the same debug session.
10. Import with a backslash or wrong module prefix.

## Idiomatic Go

- Check `go version` and `go env` before debugging a “weird” import.
- Workspace = directory with `go.mod` (or `go.work`).
- Format on save + `go vet` in pre-commit or CI.
- Pin major/minor version in team documentation.
- Do not commit `bin/` artifacts.
- For tools: `go install package@version` with an explicit version in the README.
- Use `internal/` for packages you do not want external modules to import.
- Keep `cmd/<name>/main.go` for binary entry points.

## Practical scenario

A new team member on Windows installs Go, but `go` does not exist in PowerShell — the MSI did not refresh the PATH session. After restarting the terminal it works. VS Code shows red lines on valid code because the monorepo root was opened without `go.work`, and the module is in a subfolder — they open that subfolder or add `go.work`. `go get` to a private GitHub fails with 404 via the public proxy — they set `GOPRIVATE=github.com/company/*` and SSH/HTTPS credentials. Another symptom: `go version` says 1.22, but `runtime.Version()` in a test says older — there is still another `go` from an old zip on PATH that the CI agent uses in a non-interactive shell. Within an hour the environment is aligned with the README “Developer Setup” checklist: version, env, gopls, test `go test ./...`. Mentoring takeaway: prove the toolchain first, only then debug business logic.

### Scenario continuation — go.sum conflict

A PR fails on `go mod verify` because one developer used a different `GOPROXY` that served a different artifact (rare, but the lesson: checksum protects). The team introduces a documented mirror and forbids `GOSUMDB=off` except for temporary diagnostics. A third developer commits `vendor/` without agreement — review asks for either a full vendor workflow or clean module mode, not half-and-half.

## Check questions

1. **What is GOROOT?**  
   The location of the Go toolchain installation and the standard library.

2. **Does a project have to be in GOPATH?**  
   No — modules work from any directory with a `go.mod`.

3. **What is gopls for?**  
   Language server for autocomplete, diagnostics, navigation, and formatting.

4. **What does GOPROXY do?**  
   Defines the sources from which modules are downloaded (list of URLs and `direct`).

5. **How do you permanently change a go env value?**  
   `go env -w KEY=value`.

6. **Why can `go env GOMOD` be empty?**  
   The current directory is not inside a tree with `go.mod` (nor an active `go.work` context).

7. **Difference `go build -o` vs `go install`?**  
   The first writes the binary where you specify; the second into `GOBIN` or `GOPATH/bin`.

8. **What is GOPRIVATE for?**  
   Excludes public proxy/checksum policy for private module paths.

### Workshop exercise — clean machine checklist

Do this on your laptop and record the outputs (do not commit that file if it contains private paths):

1. `go version` and `go env GOROOT GOPATH GOMODCACHE GOPROXY GOBIN GOENV GOTOOLCHAIN`
2. Create a module in `~/dev/env-lab` (or `%USERPROFILE%\dev\env-lab`)
3. Add `cmd/hello` and `internal/msg` as in Example 2
4. Confirm `go run`, `go vet`, `go install`, PATH
5. Deliberately open the **parent** folder in VS Code and observe `gopls` diagnostics
6. Return the workspace to the module root and restart the language server
7. Compare time: with and without understanding `GOMOD` — which check discovered the problem fastest?

### Workshop exercise — two go on PATH (simulation)

### Quick command glossary (print beside the monitor)

| Command | Question it answers |
|---------|---------------------|
| `go version` | Which toolchain? |
| `go env GOMOD` | Am I in a module? |
| `go env GOPROXY` | Where to download modules from? |
| `go list ./...` | Which packages does tooling see? |
| `go vet ./...` | Is there suspicious code that build lets through? |
| `gopls version` | Is the language server there? |

Keep this table until it becomes a reflex. Most “language” mysteries on day 1 are actually tooling mysteries.

## Summary

A correct environment: Go 1.22+ on PATH, a clear `go env`, modules outside GOPATH mystique, an editor with `gopls`, a proxy configured for your network, and a checklist you can repeat on a new machine. With that you are ready for deeper work with variables and types — without false bugs from tooling.
