# 02.07 Organizing Programs

> **Go Path - Zero to Gopher** / **01 Basics → Go Fundamentals** / Lesson 02.07

## Lesson goals

After this lesson you can:

- split a program into **package**s and understand the package name ↔ directory relationship
- distinguish **exported** and **unexported** identifiers (uppercase / lowercase initial letter)
- explain when and why `init` exists, and why you avoid it in most application code
- use the `internal/` convention to limit visibility within a **module**
- recognize circular imports and break them with a third package or a smaller contract
- practically split a monolithic `main` into a readable structure (`cmd/`, `internal/`, optionally `pkg/`)

## Prerequisite

- Go 1.22+ installed; `go version` works
- You know **module** (`go.mod`), `package main`, `func main`
- You have covered basic types and functions at the “program works in one file” level
- A rough idea of what `error` is (details come in 02.10)

## Problem this lesson solves

A beginner Go project often lives in one thousand-line file: HTTP handlers, SQL, validation, and `main` mixed together. The compiler allows it. A team cannot read, test, or share responsibilities. Without packages there is no clear API boundary, no control over what is public, and circular imports appear as soon as you try to “wire everything to everything”.

The other extreme is a folder per technology layer (`models`, `utils`, `helpers`, `controllers`) with no domain boundary. The dependency graph quickly becomes a loop. This lesson gives a mental model: a **package** is a unit of compilation and API, not just a folder on disk.

## Mental model

Think of a package as a **box with a label**.

1. **Package name** (`package auth`) is the label other code uses in calls (`auth.Parse`). Usually it matches the directory name, lowercase, short.
2. **Directory** is the physical box: all `.go` files in the same directory **must** have the same `package` name (except `*_test.go` with `package foo_test`, covered later in testing).
3. **Uppercase initial letter** = **exported** outside the package. `User` is visible to another package; `user` is not. There are no `public` / `private` keywords.
4. **`internal/`** is a locked room in the **module** building: only code within the parent tree may import that package. That is a tool rule (`go`), not a README comment.
5. **Circular import** is a loop of boxes that open each other — the compiler forbids it because it cannot determine initialization order.

The order Go uses when starting a package (simplified):

1. resolves dependencies (the import graph must be a directed acyclic graph — DAG)
2. initializes package variables
3. calls `init` functions in that package
4. only then enters `main` (if it is `package main`)

### Official terminology table (this lesson)

| Official Go term | Short English gloss (first time only) | Do not use as the concept name |
|------------------|---------------------------------------|--------------------------------|
| package | package / compilation unit | — |
| module | module (`go.mod`) | — |
| exported / unexported | visible / not visible outside the package | “public/private” as Java keywords |
| import path | path in `import "..."` | — |
| blank identifier | `_` (e.g. blank import) | empty identifier as a substitute |
| zero value | default value of the type | null value |
| interface | method contract | — |
| init | special package-start function | — |

In prose we use English. Names of Go concepts stay English (official).

## Mechanism

### Package and directory

A **module** has a root with `go.mod`. An **import path** is the module path plus the relative path to the package:

```text
module example.com/shop

shop/
  go.mod
  cmd/api/main.go          → package main
  internal/auth/token.go   → package auth
  pkg/money/money.go       → package money
```

In `cmd/api/main.go`:

```go
import "example.com/shop/internal/auth"
```

The name you use in code (`auth.Parse`) comes from the **package name** (`package auth`), not from the last path segment — even though convention requires them to match. If you name the directory `helpers` but write `package utils` in the file, the caller sees `utils.X` while the path says `helpers`. That works, but confuses people and tools.

One directory = one compilation unit for non-test files. Files `user.go` and `user_store.go` in the same directory are **not** subpackages. They share the same namespace: an unexported identifier from `user.go` is visible in `user_store.go`. The visibility boundary is the package, not the file.

```go
// user.go
package user

type record struct { // unexported type — visible to the whole package
	id string
}
```

```go
// store.go — same directory, same package
package user

func load(id string) record {
	return record{id: id} // OK: same package sees record
}
```

### Exported vs unexported

The rule is syntactic: an identifier starts with an uppercase Unicode “letter” category → **exported**. This applies to types, functions, **method**s, constants, **struct** fields, and **interface** methods.

```go
package inventory

type Item struct {
	SKU   string // exported field
	stock int    // unexported — invisible outside the package
}

func NewItem(sku string, n int) Item {
	return Item{SKU: sku, stock: n}
}

func (i Item) Stock() int { return i.stock }
```

Another package can call `inventory.NewItem` and read `item.SKU`, but not `item.stock`. Encapsulation in Go is not a `private` keyword — it is uppercase/lowercase. Typical pattern: unexported fields + exported constructor (`New…`) + exported methods that read or change state under package control.

What is *not* a boundary:

- a `// private` comment — the compiler ignores it
- a `_` prefix in a name — not Java privacy; `_` is the **blank identifier** or a “do not use” convention, not a visibility rule
- a file in another directory with the same `package` name — that is a *different* package if the path is different

### Import: path, alias, blank import

```go
import (
	"fmt"
	m "example.com/shop/pkg/money"
	_ "image/png" // blank import: only for side-effect (init)
)
```

- Without an alias, the local name is the last path segment *only if it matches the `package` name* — actually the local name comes from the `package` clause in that package.
- An alias (`m`) shortens or resolves a name clash.
- **Blank import** (`import _ "pkg"`) loads a package only for `init` / registration. Rare in application code; document why it exists.

Relative imports (`import "./foo"`) are not idiomatic in module mode — use a full import path.

### `init`

`init` is called automatically, with no arguments and no return value. You can have multiple `init`s in the same package. Order depends on file order and order within a file — relying on that is fragile.

```go
package config

var Defaults map[string]string

func init() {
	Defaults = map[string]string{"env": "dev"}
}
```

Typical abuses: driver registration, global state, silently reading env, network call on import. Consequence: importing the package starts work; tests and `main` lose control over order.

Better: an explicit `New` / `Setup` / `Load` function that `main` (or a test) calls.

When `init` is acceptable: white registrations without I/O, as in the stdlib (`image` decoders via blank import). Even then, in *your* application code prefer an explicit start.

### `internal/`

If an import path contains an `internal` element, the import is allowed only from a tree whose parent is the directory immediately above that `internal`.

Example: `example.com/shop/internal/auth` can be imported by code under `example.com/shop/...`, but not from `example.com/other/...`.

```text
example.com/shop/internal/auth     ← allowed from example.com/shop/cmd/...
example.com/shop/internal/auth     ← forbidden from example.com/partner/...
```

Important: `Gross` can be **exported** relative to package `tax`, and still hidden from foreign modules because of `internal` in the path. Two levels of protection:

1. lowercase — hides from *other packages* (even in the same module)
2. `internal/` — hides the package from *other modules*

### Circular imports

If `a` imports `b` and `b` imports `a`, `go build` fails. The compiler must know initialization order; a loop makes that impossible.

Solutions (from most common):

1. **Extract a shared type** into a third package (`domain`, `model` only if it really is a shared contract — not “every struct in the world”)
2. **Move the dependency onto a small interface** at the consumer (accept a contract, not a concrete type) — details in 02.09
3. **Merge packages** if they are actually one responsibility (premature split)
4. **Invert the dependency**: higher layer imports lower, never the reverse

Do not “fix” circularity with `any` / `interface{}` everywhere — you lose types.

### How to split a program

A practical pattern for a service:

| Path | Role |
|------|------|
| `cmd/<name>/` | only `main`, wiring, flags, reading env |
| `internal/<domain>/` | business logic, hidden from other modules |
| optionally `pkg/` | things you *intentionally* export as a library |

Many teams today prefer only `internal` + `cmd`, without `pkg`, until they actually publish a library.

Anti-pattern: package “by layer” without domain (`models`, `utils`, `helpers`, `controllers`). You quickly get:

- everyone imports `models`
- `utils` imports half the project
- circularity or empty folders

Ask about the package name: “What will the call look like?” `http.Get` is good; `httphelper.DoHTTPGetRequest` is not (stutter + noise).

### Initialization order — mini trace

Assume:

```text
main → imports auth
auth → imports domain
domain → (no dependency toward auth/main)
```

Order: first `domain` (variables, then `init`), then `auth`, then `main` enters `func main`. That is why `init` in `domain` must not expect `auth` to already be “ready” — `auth` is not initialized yet.

### Module path as a contract

The `go.mod` line `module example.com/shop` is not decoration. Every `import "example.com/shop/..."` depends on it. If you rename the module path, you change every import path in the project (and consumer code if you are a library).

For the course and local exercises you often use `example.com/...` or `github.com/<user>/<repo>`. What matters is that it stays stable until you plan a migration.

`go get` / `go mod tidy` operate on the module path. Packages inside a module are not separate modules until you give them their own `go.mod` (multi-module repo is an advanced topic — here it stays one module).

### What the compiler sees vs what a human sees

| Level | Rule |
|-------|------|
| Compiler | same `package` name in the directory; exported by uppercase letter; acyclic import graph; `internal` path rule |
| Convention | package name = directory name; short name; small exported surface |
| Team | where `cmd` lives, what may go in `pkg`, whether `internal/domain` exists |

The lesson teaches both mechanism and convention. You can break convention and still compile — but review will stop.

### Checklist before PR: organization

1. Does `main` do business logic or only wiring?
2. Is something exported that only one package uses?
3. Is there a `utils` / `helpers` package growing without a boundary?
4. Does the import graph have a loop (try a build)?
5. Does `init` do I/O?
6. Could another module “glue onto” something that should be `internal`?

If for 2–5 you answer “yes, problematic”, refactor before the API “escapes” into production.

### Mini example: alias and name clash

Two packages can have the same local name if paths end differently, but the local `package` name must be unique in the file — hence an alias:

```go
import (
	shopauth "example.com/shop/internal/auth"
	legauth "example.com/legacy/auth"
)

token, err := shopauth.Parse(raw)
_ = legauth.Parse // imagine an old API during migration
```

Without an alias, two `package auth` in the same file cannot coexist peacefully under the same name.

## Rules and syntax

1. One directory = one package name (for non-test files).
2. `package main` + `func main` = executable program; other packages are libraries (you cannot import `package main` as a lib).
3. Import path uses the module path; alias: `import m "example.com/shop/pkg/money"`.
4. Blank import `import _ "pkg"` only for side-effect (`init`) — rare and document why.
5. Do not export everything: start lowercase, export when another package truly needs it.
6. Package name: short, no `_`, no `CamelCase`, no `util` if you can do better.
7. Files in a package can be split by topic (`user.go`, `user_store.go`) — that is not a subpackage.
8. Test files `*_test.go` in the same package see unexported; `package foo_test` is black-box (details in 02.12).
9. Do not introduce relative imports in a module project.
10. Document exported identifiers with a comment that starts with the name (`// Message represents...`).

## Examples

### Example 1: Two packages, exported API

Structure:

```text
example.com/greeter/
  go.mod
  cmd/hello/main.go
  greet/greet.go
```

`greet/greet.go`:

```go
package greet

import "fmt"

// Message is an exported type — other packages may use it.
type Message struct {
	Text string
	loud bool // unexported: only this package controls loudness
}

// New creates a Message. loud stays inside the package.
func New(text string, loud bool) Message {
	return Message{Text: text, loud: loud}
}

// Format returns a string ready for printing.
func (m Message) Format() string {
	if m.loud {
		return fmt.Sprintf(">>> %s <<<", m.Text)
	}
	return m.Text
}

// shout is intentionally unexported — an internal detail.
func shout(s string) string {
	return fmt.Sprintf(">>> %s <<<", s)
}
```

`cmd/hello/main.go`:

```go
package main

import (
	"fmt"

	"example.com/greeter/greet"
)

func main() {
	m := greet.New("hello", true)
	fmt.Println(m.Format())
	// m.loud — compilation error outside package greet
	// greet.shout("x") — error: unexported
}
```

#### What happens here

`main` does not know about `loud` or `shout`. The public contract is `New` + `Format` + field `Text`. That is encapsulation without classes: lowercase = package boundary. `Format` may read `loud` because it is a **method** in the same package.

### Example 2: `internal/` and an external import attempt

```text
example.com/shop/
  go.mod
  cmd/api/main.go
  internal/tax/tax.go
```

`internal/tax/tax.go`:

```go
package tax

// Rate is the VAT percentage for the demo.
func Rate() float64 {
	return 0.20
}

// apply is unexported — even within the shop tree outside package tax, apply is invisible.
func apply(amount float64) float64 {
	return amount * (1 + Rate())
}

// Gross is the exported API of this internal package (public within the shop module).
func Gross(net float64) float64 {
	return apply(net)
}
```

`cmd/api/main.go`:

```go
package main

import (
	"fmt"

	"example.com/shop/internal/tax"
)

func main() {
	fmt.Println(tax.Gross(100))
}
```

If another module does `import "example.com/shop/internal/tax"`, `go build` rejects it. Within `example.com/shop` the import succeeds.

#### What happens here

`internal` is a tool rule, not a comment. `Gross` is exported *relative to the package*, but the `internal` path keeps it closed to external modules. `apply` is additionally hidden even from sibling packages in the same module. Two layers: letter and path.

### Example 3: Circular import and fix with a third package

Bad (does not compile):

```text
order/order.go  → import ".../payment"
payment/pay.go  → import ".../order"
```

Fix — shared types in `domain`:

`domain/money.go`:

```go
package domain

// Cents stores money as whole cents — no float for money.
type Cents int64
```

`order/order.go`:

```go
package order

import "example.com/shop/domain"

type Order struct {
	ID    string
	Total domain.Cents
}

func New(id string, total domain.Cents) Order {
	return Order{ID: id, Total: total}
}
```

`payment/pay.go`:

```go
package payment

import (
	"fmt"

	"example.com/shop/domain"
)

func Charge(id string, amount domain.Cents) error {
	if amount <= 0 {
		return fmt.Errorf("payment: amount must be positive, got %d", amount)
	}
	// here would go a call to the processor
	return nil
}
```

`cmd/checkout/main.go`:

```go
package main

import (
	"fmt"
	"log"

	"example.com/shop/domain"
	"example.com/shop/order"
	"example.com/shop/payment"
)

func main() {
	o := order.New("o-1", domain.Cents(2500))
	if err := payment.Charge(o.ID, o.Total); err != nil {
		log.Fatal(err)
	}
	fmt.Println("charged", o.Total, "cents for", o.ID)
}
```

#### What happens here

`order` and `payment` no longer import each other. Both depend on `domain`, which depends on no one. The graph is acyclic. `main` wires the parts — that is the role of `cmd`. `Cents` is a cheap shared contract; it is not “the whole world model in one package”.

### Example 4: Multiple files in the same package (not subpackages)

`calc/add.go`:

```go
package calc

func Add(a, b int) int { return a + b }
```

`calc/mul.go`:

```go
package calc

func Mul(a, b int) int { return a * b }
```

`calc/doc.go`:

```go
// Package calc provides simple arithmetic operations for the course.
package calc
```

The caller sees one package `calc` with `Add` and `Mul`.

#### What happens here

The compiler merges all package files into one unit. Unexported identifiers from `add.go` are visible in `mul.go`. If you need a boundary, make a **new directory** (new package), not a new file. `doc.go` is a convention for package docs without logic.

### Example 5: Thin `main` and explicit start (no `init`)

`internal/app/app.go`:

```go
package app

import "fmt"

type Config struct {
	Name string
}

type App struct {
	cfg Config
}

func New(cfg Config) (*App, error) {
	if cfg.Name == "" {
		return nil, fmt.Errorf("app: Name is required")
	}
	return &App{cfg: cfg}, nil
}

func (a *App) Run() error {
	fmt.Println("started:", a.cfg.Name)
	return nil
}
```

`cmd/shop/main.go`:

```go
package main

import (
	"log"
	"os"

	"example.com/shop/internal/app"
)

func main() {
	cfg := app.Config{Name: os.Getenv("APP_NAME")}
	a, err := app.New(cfg)
	if err != nil {
		log.Fatal(err)
	}
	if err := a.Run(); err != nil {
		log.Fatal(err)
	}
}
```

#### What happens here

No `init` that reads env on import. `main` controls configuration and order. A test can call `app.New` with a fixed `Config` without changing the process environment. Wiring stays in `cmd`; logic in `internal`.

### Example 6: Bad layout (what not to do) vs better

Bad graph (conceptual):

```text
cmd/api → controllers → models ← services → models
services → utils ← controllers
```

Better:

```text
cmd/api → internal/httpapi → internal/billing
                          ↘ internal/catalog
domain types in internal/billing or a thin internal/domain
```

#### What happens here

Instead of a central `models` that everyone pulls, dependencies go downward toward smaller packages. `cmd` remains the only place that knows all concrete parts. When `billing` does not need to know about HTTP, there is no loop.

### Example 7: Documenting an exported API

```go
package money

// Cents represents an amount in cents. Negative values are allowed
// only when the API explicitly works with debts.
type Cents int64

// Add adds two amounts. Does not check overflow; the caller chooses the range.
func Add(a, b Cents) Cents { return a + b }
```

#### What happens here

The comment starts with the identifier name (`// Cents ...`). `go doc` and IDEs expect that. A package's exported API is a contract — document it. Unexported helpers can be shorter.

## Decision analysis

| Decision | Why |
|----------|-----|
| Package by domain (`order`, `payment`) | Responsibility boundary follows the business, not technology |
| `internal/` for private packages | Prevents other modules from “gluing onto” your internal API |
| Small exported surface | Easier to change implementation without breaking callers |
| `cmd` only for wiring | You test libraries without `main` |
| Avoid `init` for work | Explicit start is debuggable and testable |
| Third package instead of circularity | Clearer dependency graph |
| Multiple files, one package | Reading organization without fake boundaries |

When choosing a package name, write a sample call on paper. If it sounds like `util.DoStuff`, rename.

## Trade-offs

- **More packages** = better boundaries, but more import boilerplate and risk of an overcrowded graph.
- **One fat package** = faster project start, worse encapsulation; OK for small CLI tools.
- **`pkg/` public** = convenient for a multi-module ecosystem, but everything you export becomes a contract.
- **`init` for registries** (e.g. image decoders) is idiomatic in the stdlib, but in application code often hides dependencies.
- **Black-box tests** (`foo_test`) force the public API; white-box tests cover unexported more easily, but are more tightly tied to implementation.
- **Early `internal`** = less later pain; exporting later is easier than pulling back a public API.

## Common mistakes

1. **Package name ≠ directory** (`package utils` in folder `helpers`) — confuses readers.
2. **Exporting everything uppercase** “just in case” — brittle API.
3. **A `models` package everyone imports** — circularity soon.
4. **Logic in `init`** that reads network/files — crash on import, hard to test.
5. **Mixing `package main` into libraries** — you cannot import that code.
6. **Attempting to import `internal` from another module** — “works locally in the monorepo” until you split the module.
7. **Circularity “fixed” with `any` everywhere** — you lose types; better make a domain package.
8. **Stutter** (`greet.GreetMessage`) — the package name already carries context.
9. **Relative imports** in a module project — brittle and unidiomatic.

## Idiomatic Go

- Short package names: `json`, `http`, `tar` — not `jsonparserlibrary`.
- Avoid stutter: `greet.GreetMessage` → `greet.Message`.
- Document exported identifiers with a comment that starts with the name.
- Keep `main` thin: parse flags, create dependencies, call `Run`.
- Use `internal` early; it is easier to export later than to pull back a public API.
- One concept per package; if you cannot describe the package in one sentence, it is probably two packages.
- Prefer `New` / `Load` over a hidden `init` for configuration.
- Keep the module path in `go.mod` stable — it is part of the public contract if you publish a library.

## Practical scenario

A team builds an online store. First PR: everything in `main.go` — cart, price, email. After two months, QA cannot test price without an SMTP server. Refactor:

1. `internal/cart` — items and total
2. `internal/pricing` — discounts, VAT
3. `internal/notify` — a small **interface** `Sender`, SMTP implementation in `internal/notify/smtp`
4. `cmd/shop/main.go` — wires concrete SMTP

When marketing asks for Slack instead of email, only the wiring in `main` and a new adapter change. Circularity is avoided because `pricing` does not know about `notify`. `internal` prevents a partner module from accidentally importing `smtp` details.

Second incident: someone exports `internal/pricing` as `pkg/pricing` “so the partner can see prices”. After a month the partner depends on internal types. The team learns: exported from `pkg` is a contract — not a shortcut.

4. Split one package into three files (`doc.go`, `parse.go`, `format.go`) without changing the package name. Write a short test in the same `package` (white-box) that calls an unexported helper.
5. Refactor an imagined monolith: name three packages and one `cmd` for a CLI that computes BMI (input, calculation, output). Do not write HTTP.
6. Rewrite an example with `init` that reads env into `New(Config)` + wiring in `main`. Compare how you test both approaches.

## Check questions

1. **What determines whether an identifier is visible outside the package?**  
   **Answer:** Whether the name starts with an uppercase letter (**exported**). There are no `public`/`private` keywords.

2. **Must the package name equal the directory name?**  
   **Answer:** The compiler does not force equality, but convention and readability require them to match; the toolchain and people expect that.

3. **Why does `go build` reject circular imports?**  
   **Answer:** The import graph must be a directed acyclic graph so that package initialization order is determined.

4. **What is the `internal` directory for?**  
   **Answer:** To limit package import only to code within the parent module tree — a private API at the path level.

5. **When is `init` acceptable, and when harmful?**  
   **Answer:** Acceptable for white registrations without I/O (as in the stdlib). Harmful when it does network, files, or hides required configuration that `main` should start explicitly.

6. **Why is splitting into multiple files in the same directory not a new visibility boundary?**  
   **Answer:** All non-test files in the directory form one **package**; unexported names are visible to the whole package.

7. **What is the role of `cmd/<name>`?**  
   **Answer:** A thin entry point: flags, env, dependency wiring; business logic lives in library packages.

## Summary

You organize a Go program with **package**s: the directory is the unit, uppercase is the API boundary (**exported**/**unexported**), `internal` protects the **module**, and circularity is solved by extracting a shared domain or a smaller contract. `main` wires; packages compute. Use `init` rarely and consciously. A good package name and a small exported surface are worth more than a “perfect” `utils` folder.
