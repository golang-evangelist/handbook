# 02.05 Control Flow Branches

> **Go Path - Zero to Gopher** / **01 Basics → Go Fundamentals** / Lesson 02.05

## Lesson goals

After this lesson you should be able to:

- write readable `if`/`else` branches and guard clauses
- use `switch` idiomatically (value-based and expression-less)
- recognize **type switch** and **type assertion** (comma-ok)
- understand why `fallthrough` is rare
- combine comma-ok with `if` for **map** and type assertion

## Prerequisite

- 01.06 (introduction to control flow)
- 02.02–02.04 (types, map, slice)
- Go 1.22+

## Problem this lesson solves

Getting Started showed the syntax. In larger code, branches become unreadable: deep `else`, fallthrough from C habits, type assertion without `ok`, a `switch` that should be a map of handlers. This lesson deepens **branching decisions**.

## Mental model

Branching answers “which path next?”. In Go prefer:

1. early exits for `error` and invalid input (guard clauses)
2. `switch` for discrete values or ranges
3. **type switch** when an **interface** (`any`) carries multiple dynamic types
4. comma-ok when an operation can fail without an `error` value (map, type assertion)

`fallthrough` deliberately looks ugly — because you rarely need it.

```text
input
  ├─ invalid? → return error (guard)
  ├─ discrete value? → switch
  ├─ dynamic type in interface? → type switch / assertion
  └─ happy path (shallow)
```

## Mechanism

### Guard clauses vs pyramid

A bad shape pushes the happy path to the right. A good shape:

```go
func normalizeUser(name string, age int) (string, error) {
	name = strings.TrimSpace(name)
	if name == "" {
		return "", fmt.Errorf("name required")
	}
	if age < 0 {
		return "", fmt.Errorf("age cannot be negative")
	}
	if age > 150 {
		return "", fmt.Errorf("unrealistic age: %d", age)
	}
	return strings.ToLower(name), nil
}
```

Every failure exits immediately. The runtime does not favor either style — readability and review favor guards.

### `switch` with a value — design

```go
switch kind {
case KindNone:
	return fmt.Errorf("not selected")
case KindEmail, KindSMS:
	// same branch — list, not fallthrough
	return sendText(kind, body)
case KindPush:
	return sendPush(body)
default:
	return fmt.Errorf("unknown %d", kind)
}
```

`default` catches future iota values. Grouping `case A, B:` avoids fallthrough.

### Expression-less `switch`

```go
switch {
case score < 0 || score > 100:
	return "invalid"
case score >= 90:
	return "excellent"
default:
	return "other"
}
```

The first matching case wins. Order matters (`>= 90` before `>= 75`).

### `fallthrough` — what it actually does

```go
switch x {
case 1:
	fmt.Println("one")
	fallthrough
case 2:
	fmt.Println("two-ish")
}
```

For `x==1` it prints **both** lines. Case 2 is **not checked** — the body runs unconditionally. That is why it is dangerous.

**Predict the result:** `x==2` in the switch above — what is printed?

**Answer:** only `two-ish` (case 1 does not match; there is no entry into the fallthrough chain from above).

### Type assertion

```go
var i any = "hello"
s := i.(string)        // panics if not string
s, ok := i.(string)    // comma-ok: ok=false, s=""
```

What the runtime does:

1. Looks at the dynamic type of the value in the interface.
2. If it matches `string`, returns the value.
3. Without `ok`: on mismatch → `panic`.
4. With `ok`: on mismatch → zero value + `false`.

### Type switch

```go
switch v := x.(type) {
case nil:
	return "nil"
case int:
	return fmt.Sprintf("int=%d", v)
case string:
	return fmt.Sprintf("string=%q", v)
default:
	return fmt.Sprintf("type %T", v)
}
```

`x.(type)` works **only** in a type switch. `v` has the type of the matching case.

Trap: a typed `nil` pointer in `any` is **not** the same as a nil interface:

```go
var p *int
var x any = p
// x == nil is false — x holds type *int and value nil
```

### comma-ok with map

```go
if score, ok := scores[name]; ok {
	// key exists; score may be 0
} else {
	// key does not exist
}
```

Without `ok`, `scores[name]` for a missing key gives the **zero value** — you cannot tell “no entry” from “entry is 0”.

### `switch` with init

```go
switch p := path; p {
case "/", "/home":
	return "home"
default:
	return "other"
}
```

`p` lives only in the `switch` scope.

## Rules and syntax

1. Braces are required even for a single statement.
2. `else` binds to the nearest `if`.
3. Type switch case types must be possible dynamic types.
4. `fallthrough` may only be the last statement in a case.
5. Type assertion without `ok` panics on the wrong type.
6. Prefer case lists (`case 1, 2, 3:`) over a fallthrough chain.
7. Initialization in `if`/`switch` lives only in that statement.
8. `default` in an enum switch — return `error` instead of a silent no-op.

## Examples

### Example 1 — Guard clauses

```go
package main

import (
	"fmt"
	"strings"
)

func normalizeUser(name string, age int) (string, error) {
	name = strings.TrimSpace(name)
	if name == "" {
		return "", fmt.Errorf("name required")
	}
	if age < 0 {
		return "", fmt.Errorf("age cannot be negative")
	}
	if age > 150 {
		return "", fmt.Errorf("unrealistic age: %d", age)
	}
	return strings.ToLower(name), nil
}

func main() {
	fmt.Println(normalizeUser("  Ana  ", 30))
	fmt.Println(normalizeUser("", 30))
}
```

#### What happens here

The happy path is at the bottom, with no `else`. For `"  Ana  ", 30`: trim → `"Ana"` → checks OK → `"ana"`. For an empty string: immediate `error`.

### Example 2 — Switch design with iota

```go
package main

import "fmt"

type Kind int

const (
	KindNone Kind = iota
	KindEmail
	KindSMS
	KindPush
)

func send(kind Kind, body string) error {
	switch kind {
	case KindNone:
		return fmt.Errorf("channel not selected")
	case KindEmail, KindSMS:
		fmt.Println("text:", kind, body)
		return nil
	case KindPush:
		if len(body) > 120 {
			return fmt.Errorf("push too long")
		}
		fmt.Println("push:", body)
		return nil
	default:
		return fmt.Errorf("unknown channel %d", kind)
	}
}

func main() {
	_ = send(KindEmail, "hello")
	_ = send(KindPush, "short")
}
```

#### What happens here

`default` catches unexpected values. Grouping Email/SMS avoids fallthrough. When the switch grows, consider `map[Kind]Handler` — but for a small enum set, switch is clear.

### Example 3 — Type switch and typed nil

```go
package main

import "fmt"

func describe(x any) string {
	switch v := x.(type) {
	case nil:
		return "nil"
	case int:
		return fmt.Sprintf("int=%d", v)
	case string:
		return fmt.Sprintf("string=%q", v)
	case []byte:
		return fmt.Sprintf("bytes len=%d", len(v))
	default:
		return fmt.Sprintf("type %T value %v", v, v)
	}
}

func main() {
	var p *int
	fmt.Println(describe(42))
	fmt.Println(describe("go"))
	fmt.Println(describe([]byte{1, 2}))
	fmt.Println(describe(p))   // type *int, not case nil
	fmt.Println(describe(nil)) // case nil
}
```

#### What happens here

`describe(nil)` goes to `case nil` (nil interface). `describe(p)` where `p` is a nil `*int` in `any` — **not** a nil interface — typically falls into `default` with type `*int`. Remember this trap before deeper lessons on interface.

### Example 4 — comma-ok and why not fallthrough

```go
package main

import "fmt"

func lookupScore(scores map[string]int, name string) string {
	if score, ok := scores[name]; ok {
		switch {
		case score >= 50:
			return "pass"
		default:
			return "fail"
		}
	}
	return "no entry"
}

func main() {
	m := map[string]int{"Ana": 80, "Voja": 0}
	fmt.Println(lookupScore(m, "Ana"))  // pass
	fmt.Println(lookupScore(m, "Voja")) // fail (key exists, score 0)
	fmt.Println(lookupScore(m, "Lara")) // no entry
}
```

#### What happens here

Without comma-ok, `Voja` and `Lara` would look the same (`0`). With `ok`, you distinguish absence from zero.

**Predict the result:** `lookupScore(m, "Voja")` without the `ok` branch — what would you wrongly conclude?

**Answer:** that there is no entry or that it is a fail — you do not know; `0` is ambiguous.

### Example 5 — Switch vs map lookup

```go
package main

import "fmt"

func route(path string) string {
	switch p := path; p {
	case "/", "/home":
		return "home"
	case "/health":
		return "ok"
	default:
		if len(p) > 0 && p[0] == '/' {
			return "page:" + p
		}
		return "bad"
	}
}

func routeByMap(path string) string {
	handlers := map[string]string{
		"/":       "home",
		"/home":   "home",
		"/health": "ok",
	}
	if h, ok := handlers[path]; ok {
		return h
	}
	return "missing"
}

func main() {
	fmt.Println(route("/health"), routeByMap("/health"))
	fmt.Println(route("/x"), routeByMap("/x"))
}
```

#### What happens here

A map scales when branches are data (lookup). Switch stays better when each branch has a different procedure. The choice is not aesthetics — it depends on whether the branch is data or logic.

### Example 6 — Type assertion panic vs ok

```go
package main

import "fmt"

func main() {
	var i any = 42
	if s, ok := i.(string); !ok {
		fmt.Println("not a string, ok=", ok, "s=", s)
	}
	// s2 := i.(string) // panic: interface conversion
}
```

#### What happens here

The comma-ok version quietly rejects. A bare assertion panics. In production always use `ok` when the type is not guaranteed.

## Decision analysis

| Decision | When |
|----------|------|
| `if` / guard | booleans, `error`, validation |
| `switch` | ≥3 discrete branches or ranges |
| type switch | you parse `any` / plugin messages |
| comma-ok | zero value is not enough as a discriminator |
| map of handlers | branches are data, not procedures |
| fallthrough | almost never — join case lists |

## Trade-offs

- **Guard clauses** — more returns, less depth.
- **Large switch** — central, can grow; a strategy map is more flexible.
- **Type switch** — convenient, but a signal that you may need an interface with a method.
- **fallthrough** — saves a line, costs clarity.
- **Init in if** — narrower scope vs reuse.

## Common mistakes

1. **Map without ok when 0 is valid**
   ```go
   v := m[k]
   if v == 0 { /* maybe no key */ }
   ```
   Fix: `v, ok := m[k]`.

2. **Fallthrough from C habit**
   ```go
   case 1:
   	doA()
   	fallthrough // often a mistake
   case 2:
   	doB()
   ```
   Fix: `case 1, 2:` or separate branches.

3. **Type assertion without ok**
   ```go
   s := i.(string) // panic
   ```
   Fix: `s, ok := i.(string)`.

4. **Deep else for errors** — turn into a guard.

5. **Forgotten default in an enum switch** — silent no-op for new constants.

6. **Mixing nil interface and typed nil** — see example 3.

7. **Overly broad default that swallows bugs** — log or return `error`.

## Idiomatic Go

- Validation and `error` up top; logic below.
- Case lists instead of fallthrough.
- `default` for unknown — return `error`.
- Type switch as a bridge; long-term a method on an interface.
- Keep branches short — extract functions.
- Name constants for switch instead of magic numbers.

## Practical scenario

Billing has `switch invoice.Status`. A PR adds `fallthrough` from `issued` to `paid` “temporarily” — draft invoices get a paid side effect. Revert. Another PR: map status→handler. Flag lookup: `if enabled, ok := flags[key]; ok && enabled`. Type switch in an anti-corruption layer translates `any` from legacy JSON. The review checklist forbids fallthrough without a “why” comment.

## Check questions

1. **What is a guard clause?**  
   An early exit for `error`/invalid input before the main logic.

2. **Does fallthrough check the next case?**  
   No — the next body runs unconditionally.

3. **What is comma-ok on a map for?**  
   Distinguishes an existing key from absence.

4. **What does a type switch require?**  
   An expression of interface type and `.(type)` in the switch.

5. **Why default in an enum switch?**  
   Catches unexpected values.

6. **What does type assertion without ok do on the wrong type?**  
   `panic`.

7. **Is a typed nil in any equal to a nil interface?**  
   No.

### Deeper trace: validating HTTP methods

```go
func mutates(method string) (bool, error) {
	switch method {
	case "GET", "HEAD", "OPTIONS":
		return false, nil
	case "POST", "PUT", "PATCH", "DELETE":
		return true, nil
	case "":
		return false, fmt.Errorf("empty method")
	default:
		return false, fmt.Errorf("unknown method %q", method)
	}
}
```

Trace:

| Input | Result |
|-------|--------|
| GET | false, nil |
| POST | true, nil |
| "" | false, error |
| FOO | false, error |

**Predict:** does `case "GET": fallthrough; case "POST": return true` do what you want for GET?

**Answer:** No — GET would fall into the POST branch and return true. That is why lists `case "GET", "HEAD":`.

### Type assertion chain vs type switch

```go
// Less readable:
if n, ok := x.(int); ok { ... } else if s, ok := x.(string); ok { ... }

// More readable:
switch v := x.(type) {
case int: ...
case string: ...
}
```

Type switch is for multiple types. One type → assertion with `ok`.

### Example 7 — Bool map: false vs absence

```go
package main

import "fmt"

func main() {
	flags := map[string]bool{"dark": false}
	if v, ok := flags["dark"]; ok {
		fmt.Println("exists, value=", v) // false
	}
	if v, ok := flags["light"]; !ok {
		fmt.Println("does not exist, v=", v) // false zero, but !ok
	}
}
```

#### What happens here

Without `ok`, both look like `false`. With `ok` you distinguish “off” from “no key”.

### Example 8 — Guard + switch together

```go
func price(cents int, vip bool) (int, error) {
	if cents < 0 {
		return 0, fmt.Errorf("negative")
	}
	switch {
	case vip && cents > 10_000:
		return cents * 90 / 100, nil
	case vip:
		return cents * 95 / 100, nil
	default:
		return cents, nil
	}
}
```

#### What happens here

Guard first. Then an expression-less `switch` for business rules. The happy path stays shallow.

### More traces: type assertion panic message

When you do `i.(string)` and `i` holds `int`, the panic message looks like:

```text
interface conversion: interface {} is int, not string
```

That tells you the dynamic type exactly. In production still use comma-ok instead of catching this panic.

### When a map of handlers beats switch

- The number of branches grows often (plugins, feature flags).
- A branch is mostly “call this function”, not 20 lines of local logic.
- You want to register handlers in `init` or configuration.

When each branch is a different procedure with local rules — stay on `switch`.

### Mini exercise in your head

Input: `scores["Ana"]=0`, you look up Ana.  
Without `ok`: you see 0 — did she fail or is she missing? You do not know.  
With `ok`: `ok==true`, `score==0` → she exists and failed.

This one sentence is why comma-ok exists.

### Example 9 — Init in if with map lookup

```go
if v, ok := m[key]; ok && v > 0 {
	fmt.Println("positive", v)
}
```

#### What happens here

One line: key exists **and** value > 0. Without `ok`, `v>0` does not distinguish absence.

### Example 10 — Why default is not optional

```go
switch status {
case "open", "closed":
	// ok
}
// forgotten default — new status "paused" silently does nothing
```

Fix: `default: return fmt.Errorf("unknown status %q", status)`.

### Decision summary in one sentence

Guard for `error`, `switch` for discrete branches, comma-ok when zero value lies, type switch for `any` — and almost never `fallthrough`.

### Example 11 — Complete small router

```go
package main

import "fmt"

func handle(method, path string) string {
	if method == "" || path == "" {
		return "bad request"
	}
	switch method {
	case "GET", "HEAD":
		switch path {
		case "/", "/home":
			return "home"
		case "/health":
			return "ok"
		default:
			return "not found"
		}
	case "POST":
		return "write"
	default:
		return "method not allowed"
	}
}

func main() {
	fmt.Println(handle("GET", "/health"))
	fmt.Println(handle("POST", "/"))
	fmt.Println(handle("GET", ""))
}
```

#### What happens here

Outer guard, then nested switch. For larger systems this grows into a multiplexer — but the branching pattern stays the same.

### Example 12 — Fallthrough rewrite to lists

```go
// Avoid:
case 1:
	fallthrough
case 2:
	do()

// Prefer:
case 1, 2:
	do()
```

Branching in idiomatic Go: guard clauses, clear switch, rare fallthrough, comma-ok, type assertion / type switch as tools for interface values. The next lesson deepens loops.
