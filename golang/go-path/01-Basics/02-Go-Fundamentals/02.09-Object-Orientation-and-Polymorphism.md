# 02.09 Object orientation and polymorphism

> **Go Path - Zero to Gopher** / **01 Basics → Go Fundamentals** / Lesson 02.09

## Lesson goals

After this lesson you will be able to:

- explain why Go **has no classes** and no **type inheritance** (no `extends` / `class`)
- model data with a **struct** and behavior with **method**s that have a **receiver**
- define an **interface** and understand *implicit* satisfaction (no `implements`)
- explain the **method set** of type `T` versus `*T` and why that affects an interface
- use **embedding** (an embedded field) as composition, not as inheritance
- perform a **type assertion** and a **type switch** on an interface value
- keep interfaces small and close to the consumer; use `io.Reader` as a polymorphism pattern

## Prerequisite

- Functions, a **method** with a **receiver**, packages, exported / unexported names (02.07–02.08)
- Basic work with a **struct** and a **pointer** (`*T` vs `T` receiver)
- Go 1.22+

## Problem this lesson solves

Programmers from the Java/C# world look for `class Animal` / `class Dog extends Animal` and conclude that Go “has no OOP.” In fact Go has object decomposition, but through a different mechanism:

- data in a **struct**
- behavior in a **method**
- polymorphism via an **interface** that you **satisfy without `implements`**
- reuse via **embedding** / fields (**composition**), not a type hierarchy

A mistaken transfer of inheritance leads to huge interfaces, “god object” structs, and a false sense that `Embedded` is the same as `extends`. This lesson sets the correct model: **Go has no inheritance — it has embedding and composition**.

## Mental model

Three layers:

1. **Struct** — the shape of data in memory (fields).
2. **Method** — a function bound to the **receiver** type (`func (c Circle) Area() float64`).
3. **Interface** — a set of methods. A type satisfies an interface if it has all of those methods — **implicitly**.

The **method set** of a type answers: “which methods may you call on a value of that type?” For `T` and `*T` the sets are not always the same. That determines whether `T` or only `*T` satisfies some interface.

Polymorphism: a function takes `io.Reader` and works the same for a file, a network stream, or an in-memory buffer. It does not care about the concrete type, only about the contract `Read([]byte) (int, error)`.

**Embedding**: embed a type in a struct (`type Server struct { Logger; Config }`). You get name promotion — it is *not* “is-a” inheritance. `Server` is not a subtype of `Logger`.

When you have an interface value and need the concrete type: **type assertion** (`v.(T)`) or **type switch**.

## Mechanism

### Method and receiver

```go
type Counter struct{ n int }

func (c *Counter) Inc() { c.n++ }
func (c Counter) Value() int { return c.n }
```

- **Pointer receiver** (`*Counter`) when the method mutates state or when the struct is large (you avoid a copy).
- **Value receiver** (`Counter`) when it is logically a copy / an immutable view.

Go allows you to call a method with a pointer receiver on a variable of type `Counter` (it takes the address) — and the reverse in many cases — but the **method set** for interface satisfaction follows stricter rules (next section).

A method must be declared in the **same package** as the type. You cannot add a method on `string` or on someone else’s type from another package — you make a wrapper struct.

### Interface and implicit satisfaction

```go
type Stringer interface {
	String() string
}
```

Any type with a method `String() string` satisfies `Stringer` — even from another package, with no announcement. There is no `implements` list. The compiler checks at assignment / call. If a method is missing, the error is at the use site.

That encourages small interfaces defined **at the consumer** (accept interfaces, return structs).

### Method set (key for interface)

Simplified:

| Type | Method set includes |
|------|---------------------|
| `T` | methods with receiver `T` |
| `*T` | methods with receiver `T` **and** `*T` |

Therefore: if `Inc` has a pointer receiver, a variable of type `Counter` (value) *can* call `Inc` in ordinary code (the compiler takes `&c`), but `Counter` **does not satisfy** an interface that requires `Inc` — only `*Counter` satisfies it.

```go
type Incrementer interface {
	Inc()
}

var c Counter
// var i Incrementer = c  // does not compile: Counter's method set has no Inc
var i Incrementer = &c    // OK
```

Remember: “works when I call it” ≠ “satisfies the interface.” The method set is the bridge.

### Empty interface and `any`

`any` is an alias for `interface{}` — every value. That is not an “OOP base,” but the absence of a contract. Use sparingly; prefer a concrete small interface or generics.

An interface value internally holds a pair: **dynamic type** + **dynamic value**. A `nil` interface means both parts are missing. Trap: a pointer that is `nil`, wrapped in an interface, is **not** `== nil` at the interface level.

```go
var p *Counter = nil
var i Incrementer = p
fmt.Println(i == nil) // false — type is *Counter, value is nil
```

### Embedding (composition, not inheritance)

```go
type Engine struct{ HP int }
type Car struct {
	Engine // embedded
	Brand  string
}
```

`Car` gets promoted access to `HP` and to `Engine` methods — as if they were declared on `Car`, but:

- `Car` **is not** a subtype of `Engine`
- there is no polymorphism “wherever Engine, there also Car”
- if `Engine` and `Car` have the same method, `Car`’s shadows it; you can still call `c.Engine.Method()`

Embedding a pointer field (`*Logger`) is possible: then a **zero value** `Car` can have a `nil` embedded pointer — calling a promoted method → `panic`. An explicit field is often more readable.

Go **has no inheritance**. Embedding is syntax sugar for composition + name promotion.

### Type assertion

When you have an `interface` value and you know (or check) the concrete type:

```go
var s Stringer = MyType{}
mt, ok := s.(MyType)
if !ok {
	// not MyType
}
```

The form `s.(MyType)` without `ok` panics if the type does not match. Prefer “comma ok.”

Type assertion works on an interface value. It does not “cast” arbitrary types as in C.

### Type switch

```go
switch v := x.(type) {
case int:
	fmt.Println("int", v)
case string:
	fmt.Println("string", v)
case nil:
	fmt.Println("nil interface")
default:
	fmt.Printf("other: %T\n", v)
}
```

`v` in each `case` has the type of that branch. Use when you branch behavior by several known types. For one type — assertion; for a family — often a small interface is better than a huge type switch.

### `io.Reader` as a pattern

```go
type Reader interface {
	Read(p []byte) (n int, err error)
}
```

The whole ecosystem (JSON decoder, HTTP body, compression) is built around this contract. Your type becomes part of the ecosystem as soon as it has a correct `Read`. That is polymorphism without a shared base class.

### Why Go rejects class hierarchy

In languages with classes you often get:

```text
Animal
  └─ Mammal
       └─ Dog
```

and “protected” fields, virtual methods, brittle changes in the base. Go chooses another path:

1. **Struct** holds data — no hidden base class.
2. **Interface** holds behavior — small contracts, implicit satisfaction.
3. **Embedding** / fields hold reuse — composition, not is-a trees.

Consequence: it is easier to add a new type that satisfies a small interface than to insert a leaf into a deep hierarchy. Cost: there is no “free” sharing of implementation through descendants — you share via functions, embedding, or an explicit field.

### Method set — extended table

| Declaration | Enters method set of `T`? | Enters method set of `*T`? |
|-------------|---------------------------|----------------------------|
| `func (t T) A()` | yes | yes |
| `func (t *T) B()` | no | yes |

Therefore an interface that requires `B()` accepts `*T`, not `T`. Mixing value and pointer **receiver**s on the same type is allowed, but be aware of the consequences for an interface.

### Embedding + interface together

A common pattern:

```go
type Store interface {
	Get(id string) (string, error)
}

type Cached struct {
	Store // embedded interface — composition over a contract
	mem   map[string]string
}
```

`Cached` can promote `Get` or redefine it (shadow) and call `c.Store.Get`. Still **not** class inheritance: `Cached` is not a subtype of a concrete Postgres store; it depends on the interface.

### Type assertion — error trace

```go
var s Speaker = Dog{Name: "Ava"}
r := s.(Robot) // panic: not Robot
```

Without `ok` the panic is hard. With `ok`:

```go
r, ok := s.(Robot)
if !ok {
	// branch for "not Robot"
}
```

A type switch is more readable when you have 3+ types. When you have 1 type and want the data — assertion. When you can stay on an interface method — **do not** assert; stay on the contract.

### Checklist: did I do “Java in Go”?

- [ ] Do I have a `Base*` struct that everyone “inherits” via embedding only to share fields?
- [ ] An interface with 10+ methods in a library package?
- [ ] An `I` prefix on every interface (`IReader`) without need?
- [ ] Do I expect an embedded type to pass as a subtype where the “parent” stands?
- [ ] Do I use `any` instead of a single method?

If more answers are “yes,” go back to small interfaces and explicit fields.

## Rules and syntax

1. An interface is declared as a list of methods; no data fields (a constraint interface in generics is another story).
2. Nil interface vs nil pointer in an interface — a classic trap.
3. A method must be in the same package as the type.
4. An interface value = (dynamic type, dynamic value).
5. Small interface: 1–3 methods. Large interfaces rarely belong in libraries.
6. Define the interface where it is **used**, not where it is implemented (except when you export a stable contract like `io.Reader`).
7. Do not build deep trees of “base” structs for an OOP feeling — Go has no inheritance.
8. Embedding ≠ subtype. Do not expect `Car` to pass where an `Engine` parameter stands.
9. For interface satisfaction look at the **method set**, not only “can I call the method.”
10. Type assertion with `ok`; type switch when there are more types.

## Examples

### Example 1: Struct + method without classes

```go
package main

import (
	"fmt"
	"math"
)

type Circle struct {
	Radius float64
}

func (c Circle) Area() float64 {
	return math.Pi * c.Radius * c.Radius
}

func (c Circle) Scale(k float64) Circle {
	return Circle{Radius: c.Radius * k}
}

type Rect struct {
	W, H float64
}

func (r Rect) Area() float64 { return r.W * r.H }

func main() {
	c := Circle{Radius: 2}
	fmt.Println("circle:", c.Area())
	fmt.Println("scaled:", c.Scale(2).Area())
	fmt.Println("rectangle:", Rect{W: 3, H: 4}.Area())
}
```

#### What happens here

`Circle` and `Rect` have no shared base class. Each type carries its own data and methods. For shared behavior, an interface follows — not `extends Shape`. The composite literal `Circle{Radius: 2}` creates a value.

### Example 2: Small interface and implicit satisfaction

```go
package main

import (
	"fmt"
	"math"
)

type Shaper interface {
	Area() float64
}

type Circle struct{ Radius float64 }

func (c Circle) Area() float64 { return math.Pi * c.Radius * c.Radius }

type Rect struct{ W, H float64 }

func (r Rect) Area() float64 { return r.W * r.H }

func totalArea(shapes ...Shaper) float64 {
	var sum float64
	for _, s := range shapes {
		sum += s.Area()
	}
	return sum
}

func main() {
	fmt.Println(totalArea(
		Circle{Radius: 1},
		Rect{W: 2, H: 3},
		Circle{Radius: 2},
	))
}
```

#### What happens here

`Circle` nowhere writes `implements Shaper`. The compiler sees the method `Area` and allows passing it. `totalArea` is polymorphic. The interface has one method — easy to mock in a test.

### Example 3: Method set — why `&c` and not `c`

```go
package main

import "fmt"

type Counter struct{ n int }

func (c *Counter) Inc() { c.n++ }
func (c *Counter) Value() int { return c.n }

type Incrementer interface {
	Inc()
	Value() int
}

func bump(i Incrementer) {
	i.Inc()
	fmt.Println("value:", i.Value())
}

func main() {
	c := Counter{}
	// bump(c) // does not compile: Counter method set has no Inc
	bump(&c) // OK: *Counter satisfies Incrementer
}
```

#### What happens here

An ordinary call `c.Inc()` might pass (the address is taken), but assignment to an interface looks at the **method set**. Pointer receiver methods enter the method set of `*Counter`, not of `Counter`. This is a common trap when writing tests and mocks.

### Example 4: `io.Reader` polymorphism

```go
package main

import (
	"fmt"
	"io"
	"strings"
)

func countBytes(r io.Reader) (int, error) {
	buf := make([]byte, 64)
	total := 0
	for {
		n, err := r.Read(buf)
		total += n
		if err == io.EOF {
			return total, nil
		}
		if err != nil {
			return total, err
		}
	}
}

func main() {
	s := strings.NewReader("Go Path - Zero to Gopher lesson about Reader")
	n, err := countBytes(s)
	if err != nil {
		fmt.Println("error:", err)
		return
	}
	fmt.Println("bytes:", n)
}
```

#### What happens here

`countBytes` does not import a concrete source. `strings.NewReader` satisfies `io.Reader`. Tomorrow you replace the input with a file — the function signature stays. The core of Go polymorphism in practice.

### Example 5: Embedding instead of inheritance

```go
package main

import "fmt"

type Logger struct {
	Prefix string
}

func (l Logger) Log(msg string) {
	fmt.Printf("%s%s\n", l.Prefix, msg)
}

type Audit struct {
	Logger // embedded — composition, not extends
	User   string
}

func (a Audit) Action(name string) {
	a.Log(fmt.Sprintf("user=%s action=%s", a.User, name))
}

type Service struct {
	audit Audit // has-a field, not a hierarchy
}

func (s Service) Delete(id string) {
	s.audit.Action("delete:" + id)
}

func main() {
	svc := Service{audit: Audit{
		Logger: Logger{Prefix: "[audit] "},
		User:   "marko",
	}}
	svc.Delete("42")
}
```

#### What happens here

`Audit` uses **embedding** for `Logger` and gets `Log` by promotion. That **is not** type inheritance: you cannot pass `Audit` where a `Logger` parameter stands unless there is an interface. `Service` holds `audit` as a field (has-a). No brittle `BaseService` hierarchy.

### Example 6: Type assertion and type switch

```go
package main

import "fmt"

type Speaker interface {
	Speak() string
}

type Dog struct{ Name string }

func (d Dog) Speak() string { return d.Name + ": woof" }

type Robot struct{ ID int }

func (r Robot) Speak() string { return fmt.Sprintf("robot-%d: beep", r.ID) }

func describe(s Speaker) {
	// type assertion with ok
	if d, ok := s.(Dog); ok {
		fmt.Println("dog:", d.Name)
	}

	// type switch
	switch v := s.(type) {
	case Dog:
		fmt.Println("switch dog:", v.Speak())
	case Robot:
		fmt.Println("switch robot:", v.Speak())
	default:
		fmt.Printf("unknown: %T\n", v)
	}
}

func main() {
	describe(Dog{Name: "Ava"})
	describe(Robot{ID: 7})
}
```

#### What happens here

`Speaker` hides the concrete type. Assertion extracts `Dog` when it is a `Dog`. Type switch branches on more types without a chain of ifs. Both mechanisms work on an **interface** value; they do not replace a small interface when you can stay on the `Speak()` contract.

### Example 7: Interface at the consumer

```go
package main

import "fmt"

// The consumer defines only what it needs.
type Store interface {
	Find(id string) (string, error)
}

type Memory struct {
	data map[string]string
}

func (m Memory) Find(id string) (string, error) {
	v, ok := m.data[id]
	if !ok {
		return "", fmt.Errorf("no id %q", id)
	}
	return v, nil
}

func printName(s Store, id string) {
	name, err := s.Find(id)
	if err != nil {
		fmt.Println("error:", err)
		return
	}
	fmt.Println(name)
}

func main() {
	m := Memory{data: map[string]string{"1": "Ana"}}
	printName(m, "1")
	printName(m, "9")
}
```

#### What happens here

`Store` is not in the database package — it lives next to `printName`. `Memory` does not know about `Store`. In production you add `Postgres` with the same method; the test injects a fake store. A large `UserRepository` with 20 methods would be the opposite of this approach.

### Example 8: Type assertion on `error` (bridge to 02.10)

```go
package main

import (
	"fmt"
)

type temporary interface {
	Temporary() bool
}

type timeoutErr struct{}

func (timeoutErr) Error() string   { return "timeout" }
func (timeoutErr) Temporary() bool { return true }

func maybeRetry(err error) bool {
	t, ok := err.(temporary)
	return ok && t.Temporary()
}

func main() {
	fmt.Println(maybeRetry(timeoutErr{}))
	fmt.Println(maybeRetry(fmt.Errorf("permanent")))
}
```

#### What happens here

A small local interface `temporary` + type assertion give polymorphism over `error` values without a shared base class. In modern code you more often see `errors.As`, but the mechanism is the same: interface + assertion. Go has no inheritance of `error` types.

### Example 9: Method set trap in one line

```go
type Counter struct{ n int }

func (c *Counter) Inc() { c.n++ }

type IncOnly interface{ Inc() }

func main() {
	var i IncOnly
	c := Counter{}
	// i = c  // no: method set of Counter
	i = &c    // yes: method set of *Counter
	i.Inc()
}
```

#### What happens here

One line of difference (`c` vs `&c`) decides whether the type satisfies the interface. Remember the **method set** before you blame the compiler.

## Decision analysis

| Decision | Why |
|----------|-----|
| Interface with 1 method | Easy to satisfy, easy to mock |
| Return concrete types | The caller chooses the abstraction |
| Composition by field / embedding | Explicit dependencies; not inheritance |
| Look at method set for interface | Avoids surprises with pointer receiver |
| `io.Reader` style contracts | Fit into the stdlib |
| Type assertion / type switch | When you really need the concrete type |
| Pointer receiver for mutation | Clear semantics of shared state |

## Trade-offs

- **Implicit interface** = less typing, but “who all implements?” needs tools / IDE.
- **Embedding** looks like inheritance — abuse creates a hidden API and a false is-a.
- **Small interfaces** sometimes require more types instead of one “god interface.”
- **Methods on foreign types** you cannot — a wrapper struct is the cost.
- **Nil in an interface** requires discipline; better return `error` than a nil implementation.
- **Type switch** can grow into a “manual visitor” — a signal that a better interface is needed.

## Common mistakes

1. Building an `IAnimal` / `AbstractBase` hierarchy “like in Java” — Go has no inheritance.
2. An interface with dozens of methods in a library package.
3. Mixing embedding with subtypes (`Car` where `Engine` is needed).
4. Forgetting the method set: a value does not satisfy an interface with pointer receiver methods.
5. Forgetting that `(*T)(nil)` assigned to an interface ≠ nil interface.
6. Using `any` instead of a real contract.
7. An embedded pointer field nil and panic on a promoted call.
8. Type assertion without `ok` in production code.
9. Exporting a huge interface “just in case” from the same package as the struct.

## Idiomatic Go

- “Accept interfaces, return structs.”
- Interface names: `Reader`, `Writer`, `Stringer` — often an `-er` suffix for one method.
- The stdlib is the textbook: `io`, `http.Handler`, `fmt.Stringer`.
- Composition / embedding > inheritance as the default strategy — because there is no inheritance.
- Generics when you share an algorithm over types; interface when you share behavior with runtime polymorphism.
- Keep the method set consistent: mutating methods on a pointer receiver.
- Use type assertion / type switch when the contract is no longer enough (e.g. a richer `error` type — see 02.10).

## Practical scenario

A team ports a Java service with `abstract class PaymentProcessor`. In Go they make:

```text
type Capturer interface { Capture(id string, cents int64) error }
```

`Stripe`, `Fake`, `Offline` — three structs. The HTTP layer handler takes `Capturer`. No shared base class with protected fields. Later they add a `LoggingCapturer` decorator that holds a `Capturer` (composition) and logs. Tests do not spin up Docker for Stripe.

When someone proposes a `BaseProcessor` with 15 methods and “inheritance via embedding,” review rejects it: embedding is not `extends`; split the interface or extract a package. Another PR: value `Stripe{}` does not pass into `Capturer` because `Capture` is on a pointer receiver — fix: pass `&Stripe{}` or align the method set.

3. Make structs `Dog` and `Robot` with `Speak() string`. A function takes an interface; inside a type switch prints the type.

## Check questions

1. **Does Go have class inheritance?**  
   **Answer:** No. It uses struct + method + interface and composition (**embedding** / fields). No `class` / `extends`.

2. **What does implicit interface satisfaction mean?**  
   **Answer:** The type does not have to declare `implements`; it is enough that its **method set** contains all interface methods.

3. **What is the method set in the context of a pointer receiver?**  
   **Answer:** Methods with a pointer receiver enter the method set of `*T`, not of `T`; therefore only `*T` can satisfy an interface that requires those methods.

4. **Why is embedding not inheritance?**  
   **Answer:** It gives name promotion and composition; it does not create a subtype. The embedded type is not a “parent” in the OOP sense.

5. **What are type assertion and type switch for?**  
   **Answer:** To extract a concrete type from an interface value; assertion for one type (with `ok`), type switch for more branches.

6. **Why are small interfaces desirable?**  
   **Answer:** They are easier to satisfy and mock; they reduce coupling; they match the style of consumer contracts.

7. **What is `io.Reader` for as an example?**  
   **Answer:** It shows polymorphism over byte sources without a shared base class — the ecosystem builds on the contract.

## Summary

Go OOP is not a class hierarchy — it is data (**struct**), a **method** with a **receiver**, a small **interface** with implicit satisfaction via the **method set**, and **embedding**/composition instead of inheritance. Polymorphism lives in contracts like `io.Reader`. When you need the concrete type, use a **type assertion** or a **type switch**. Return a struct, accept an interface; avoid huge abstractions transferred from other languages.
