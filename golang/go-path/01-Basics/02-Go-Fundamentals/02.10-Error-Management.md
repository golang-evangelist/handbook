# 02.10 Error management

> **Go Path - Zero to Gopher** / **01 Basics → Go Fundamentals** / Lesson 02.10

## Lesson goals

After this lesson you will be able to:

- use the built-in **`error` interface**
- create `error` values with `errors.New` and `fmt.Errorf`
- wrap causes with `%w` and inspect the chain via `errors.Is` / `errors.As`
- define a sentinel `error` and your own types that satisfy `error`
- distinguish expected failure (you return `error`) from a programmer panic
- use `errors.Join` (Go 1.20+) when there are several independent failures

## Prerequisite

- Functions with multiple return values and the `(T, error)` idiom (02.08)
- **Interface** at the level of “a type with methods”; type assertion / `errors.As` (02.09)
- Go 1.22+ (`errors` package from the stdlib)

## Problem this lesson solves

In languages with exceptions you often “throw” everything and catch it far away. In Go, expected failures are **values** of type `error`. Beginners either ignore `err`, or panic on every bad input, or compare `err.Error()` strings. Without `%w` and `errors.Is` the cause is lost through HTTP → service → database layers.

This lesson teaches: `error` is part of the API. The message is for humans; the identity (sentinel / type) is for the program.

## Mental model

`error` is an **interface**:

```go
type error interface {
	Error() string
}
```

Every value with a method `Error() string` is an `error`. A `nil` `error` = success.

Cause chain: a higher layer adds context (`fmt.Errorf("load user %s: %w", id, err)`), and the lower one keeps the identity. `errors.Is` walks the chain and compares. `errors.As` walks the chain and looks for a concrete type (like a type assertion through the chain).

**Sentinel**: `var ErrNotFound = errors.New("not found")` — compare via `errors.Is`, not via the string.

**Panic**: for “this must not happen” (bug, invariants). Not for “file does not exist” or “user sent bad JSON.”

### Official terminology table (this lesson)

| Official Go term | Short English gloss (first time only) | Do not use as the concept name |
|------------------|---------------------------------------|--------------------------------|
| error | failure contract / type in Go | error *as the type name alone* |
| wrapping (`%w`) | wrapping a cause into a chain | — |
| sentinel error | stable package `error` value | — |
| unwrap | peeling a layer of the chain | — |
| interface | method contract | interfejs |
| type assertion | extracting a type (As works similarly) | — |
| zero value | default value | null value |
| pointer | `*T` | pokazivač |
| panic / recover | breaking flow / catching in defer | — |

In prose you may say “failure,” “message,” “what went wrong.” Call the type and contract **`error`**.

## Mechanism

### Creation

```go
err := errors.New("no data")
err2 := fmt.Errorf("user %d: %s", id, "no data")
```

`errors.New` creates a simple value. `fmt.Errorf` formats a message. Both return `error`.

### Wrapping (`%w`)

```go
return fmt.Errorf("GetUser(%s): %w", id, err)
```

Only **`%w`** enables proper `Unwrap` for the chain. `%v` or `%s` inserts text, but does **not** link the cause for `errors.Is` / `errors.As`.

Trace:

1. the lower layer returns `ErrNotFound`
2. the middle does `fmt.Errorf("service: %w", err)`
3. the upper sees a long message, but `errors.Is(err, ErrNotFound)` can still be `true`

### `errors.Is` and `errors.As`

```go
if errors.Is(err, ErrNotFound) {
	// treat as "not found"
}

var ne *NotExist
if errors.As(err, &ne) {
	// use ne.Path — As looks for the type in the chain
}
```

- **`Is`**: compares with a target *value* (often a sentinel), walks through `Unwrap` / `Is` methods.
- **`As`**: looks for a *type*, fills a **pointer** to a variable of that type (similar to a type assertion through the chain).

Without a chain (`%v` instead of `%w`), `Is`/`As` see only the outer layer.

### Your own type that satisfies `error`

```go
type ValidationError struct {
	Field, Msg string
}

func (e *ValidationError) Error() string {
	return e.Field + ": " + e.Msg
}
```

Often a **pointer** receiver for consistent `errors.As` (method set + the type you look for). If the type should participate in the chain as a cause, implement `Unwrap() error`.

```go
type QueryError struct {
	Query string
	Err   error
}

func (e *QueryError) Error() string {
	return "query " + e.Query + ": " + e.Err.Error()
}

func (e *QueryError) Unwrap() error { return e.Err }
```

### `errors.Join` (1.20+)

When several independent failures need to be preserved (e.g. Close of multiple resources):

```go
return errors.Join(err1, err2)
```

`errors.Is` can hit any member. Do not mix Join with one cause + context — for context through layers still use `%w`.

### Panic and recover

`panic` breaks normal flow. `recover` works **only** inside a `defer` function of that goroutine (concurrency details in 02.11). HTTP servers catch panic so they do not bring down the process — that does not mean you should panic for validation.

Boundary:

| Situation | Typical tool |
|-----------|--------------|
| User sent bad input | return `error` |
| File does not exist | return `error` (often `os.ErrNotExist` in the chain) |
| Bug: index out of range that “must not” | `panic` (or better prevent it) |
| Initialization of a hardcoded template in `mustParse` | sometimes `panic` |

### Check immediately

```go
f, err := os.Open(path)
if err != nil {
	return fmt.Errorf("open config: %w", err)
}
// use f only here
```

Do not use a partially filled result with a non-nil `err` except when the API *documents* that (rare).

### Anatomy of a chain — step by step

Imagine three layers:

```text
handler → service → repository
```

1. Repository returns `ErrNotFound` (sentinel).
2. Service does `return fmt.Errorf("service.GetUser(%s): %w", id, err)`.
3. Handler sees the message with context, but does:

```go
if errors.Is(err, ErrNotFound) {
	// HTTP 404
}
```

Without `%w` at step 2, the handler must parse the string or lose semantics. With `%w`, the message grows, the identity remains.

If the service adds its own type:

```go
type UserError struct {
	ID  string
	Err error
}

func (e *UserError) Error() string {
	return "user " + e.ID + ": " + e.Err.Error()
}
func (e *UserError) Unwrap() error { return e.Err }
```

then the handler can also `errors.As(err, &ue)` for `ID`, and `errors.Is(err, ErrNotFound)` via `Unwrap`.

### Sentinel vs type — when which

| Need | Tool |
|------|------|
| Stable “not found” without extra fields | sentinel `var ErrNotFound = errors.New(...)` |
| Code, field, retry hint, HTTP status | custom type + `Error()` (+ `Unwrap` as needed) |
| Diagnostic message only in a CLI | `fmt.Errorf("...")` without `Is` |
| Several independent failures | `errors.Join` |

Do not make a sentinel for every validation branch — a `ValidationError` type with `Field` often scales better.

### What `Error() string` is not

The method `Error()` is for humans and logs. It is not an API for branching. Whenever you write `strings.Contains(err.Error(), "not found")`, ask: why don’t I have a sentinel or a type?

Exception: temporary debug. It does not stay in a production handler.

### Panic, defer, recover — framework only

```go
func safe(fn func()) (err error) {
	defer func() {
		if r := recover(); r != nil {
			err = fmt.Errorf("panic: %v", r)
		}
	}()
	fn()
	return nil
}
```

This turns a panic into an `error` — useful at the boundary (HTTP middleware), not as a substitute for `return err` in business logic. Details of `recover` in concurrent code: it works only in the same goroutine where the panic happened.

### Checklist before return `error`

1. Did I add context for what I was doing?
2. Did I preserve the chain with `%w` (if there is a cause)?
3. Can the caller `Is`/`As` without parsing the string?
4. Am I returning a non-nil `error` with a “useful” result without documentation?
5. Is this expected (validation/I/O) or a bug (panic)?

## Rules and syntax

1. Check `err != nil` immediately after the call.
2. Do not compare `err.Error() == "..."`.
3. Add context on return through layers; do not swallow the lower `error` without `%w` or conscious logging.
4. Export a sentinel if it is part of the package’s public contract (`Err…`).
5. `fmt.Errorf("%v", err)` does **not** wrap for `Is`/`As` — use `%w`.
6. After success work with the value; ignore the result with a non-nil `err` except a documented exception.
7. `panic` in libraries almost never for user input.
8. In tests: `errors.Is` / `As`, not `Equal` on the whole message.
9. Message: lowercase start, often without a period (`"open config: ..."` style).

## Examples

### Example 1: Basic idiom and `errors.New`

```go
package main

import (
	"errors"
	"fmt"
)

var ErrEmpty = errors.New("empty input")

func parseName(s string) (string, error) {
	if s == "" {
		return "", ErrEmpty
	}
	return s, nil
}

func main() {
	name, err := parseName("")
	if err != nil {
		if errors.Is(err, ErrEmpty) {
			fmt.Println("treat as validation failure")
			return
		}
		fmt.Println("unknown:", err)
		return
	}
	fmt.Println(name)
}
```

#### What happens here

`ErrEmpty` is a sentinel. The caller uses `errors.Is`, not the string. An empty string result with a non-nil `error` is ignored — the contract is clear: check `err` first.

### Example 2: `%w`, context, and `Is`

```go
package main

import (
	"errors"
	"fmt"
)

var ErrNotFound = errors.New("not found")

func repoFind(id string) error {
	if id == "0" {
		return ErrNotFound
	}
	return nil
}

func serviceFind(id string) error {
	if err := repoFind(id); err != nil {
		return fmt.Errorf("serviceFind(%s): %w", id, err)
	}
	return nil
}

func main() {
	err := serviceFind("0")
	fmt.Println("message:", err)
	fmt.Println("Is NotFound?", errors.Is(err, ErrNotFound))
}
```

#### What happens here

The message output contains context `serviceFind(0): not found`, and `errors.Is` still recognizes `ErrNotFound` because `%w` preserved the chain. If it had been `%v`, `Is` would be `false` — a common mistake.

### Example 3: `errors.As` and a custom type

```go
package main

import (
	"errors"
	"fmt"
)

type HTTPError struct {
	Code int
	Msg  string
}

func (e *HTTPError) Error() string {
	return fmt.Sprintf("http %d: %s", e.Code, e.Msg)
}

func fetch() error {
	return fmt.Errorf("gateway: %w", &HTTPError{Code: 503, Msg: "unavailable"})
}

func main() {
	err := fetch()
	var he *HTTPError
	if errors.As(err, &he) {
		fmt.Println("code:", he.Code, "msg:", he.Msg)
		return
	}
	fmt.Println("not HTTPError:", err)
}
```

#### What happens here

`As` unwraps the chain and fills `he` with a **pointer** to the found type. You can branch behavior by `Code` (retry on 503, no retry on 400) without parsing the string. The type must satisfy `error` (`Error() string`).

### Example 4: Validation without panic

```go
package main

import (
	"fmt"
	"strconv"
)

type ValidationError struct {
	Field string
	Msg   string
}

func (e *ValidationError) Error() string {
	return fmt.Sprintf("%s: %s", e.Field, e.Msg)
}

func parsePort(s string) (int, error) {
	if s == "" {
		return 0, &ValidationError{Field: "port", Msg: "required"}
	}
	n, err := strconv.Atoi(s)
	if err != nil {
		return 0, &ValidationError{Field: "port", Msg: "must be a number"}
	}
	if n < 1 || n > 65535 {
		return 0, &ValidationError{Field: "port", Msg: "out of range"}
	}
	return n, nil
}

func main() {
	for _, in := range []string{"", "xyz", "80", "99999"} {
		p, err := parsePort(in)
		if err != nil {
			fmt.Printf("input %q -> error: %v\n", in, err)
			continue
		}
		fmt.Printf("input %q -> port %d\n", in, p)
	}
}
```

#### What happens here

Bad user input is not a panic. The API returns a typed `error` that the UI can map to a form field via `errors.As`. The program stays in control of flow. The **zero value** `0` for `int` with an `error` is not interpreted as a successful port.

### Example 5: When panic is right (invariant)

```go
package main

import "fmt"

func mustPositive(n int) int {
	if n <= 0 {
		panic(fmt.Sprintf("mustPositive: n=%d", n))
	}
	return n
}

func main() {
	fmt.Println(mustPositive(3))
	// mustPositive(0) would crash the program — that is a caller bug, not expected API input.
}
```

#### What happens here

`must*` helpers in initialization (e.g. parsing a hardcoded template) may panic. A public parser of user input must not. Boundary: expected vs bug.

### Example 6: `Unwrap` and `errors.Join`

```go
package main

import (
	"errors"
	"fmt"
)

var (
	ErrA = errors.New("A")
	ErrB = errors.New("B")
)

func closeBoth() error {
	var err1 error = ErrA
	var err2 error = ErrB
	return errors.Join(err1, err2)
}

func main() {
	err := closeBoth()
	fmt.Println(err)
	fmt.Println("Is A?", errors.Is(err, ErrA))
	fmt.Println("Is B?", errors.Is(err, ErrB))
}
```

#### What happens here

`Join` keeps both failures. `Is` passes for `ErrA` and for `ErrB`. Use when failures are independent; for one cause through layers still prefer `%w` with context.

### Example 7: Bad vs good context

```go
// BAD: loses the chain
func bad(err error) error {
	return fmt.Errorf("load: %v", err)
}

// GOOD: preserves the chain
func good(err error) error {
	return fmt.Errorf("load: %w", err)
}
```

#### What happens here

Both produce a readable message. Only `good` allows `errors.Is` / `As` on the original cause. In code review look for `%w` when an `error` is returned upward.

### Example 8: Three layers — `Is` trace through the chain

```go
package main

import (
	"errors"
	"fmt"
)

var ErrNotFound = errors.New("not found")

func repo(id string) error {
	if id == "" {
		return ErrNotFound
	}
	return nil
}

func service(id string) error {
	if err := repo(id); err != nil {
		return fmt.Errorf("service(%q): %w", id, err)
	}
	return nil
}

func handler(id string) string {
	err := service(id)
	if err == nil {
		return "ok"
	}
	if errors.Is(err, ErrNotFound) {
		return "404"
	}
	return "500"
}

func main() {
	fmt.Println(handler(""))  // 404
	fmt.Println(handler("1")) // ok
	err := service("")
	fmt.Println(err) // service(""): not found
}
```

#### What happens here

The handler does not parse the string. The identity `ErrNotFound` survives two `%w` layers. The message grows for the log; semantics remain for branching. That is the whole reason wrapping exists.

### Example 9: `As` after `Join`

```go
package main

import (
	"errors"
	"fmt"
)

type FieldError struct {
	Field string
}

func (e *FieldError) Error() string { return e.Field + " invalid" }

func validate() error {
	return errors.Join(
		&FieldError{Field: "email"},
		&FieldError{Field: "age"},
	)
}

func main() {
	err := validate()
	var fe *FieldError
	if errors.As(err, &fe) {
		fmt.Println("first FieldError in chain/Join:", fe.Field)
	}
}
```

#### What happens here

`Join` keeps multiple failures. `As` finds the first matching type. For *all* `FieldError` values you need a different pass (e.g. an `errors.Unwrap` loop or your own collection type) — this intro teaches that `Join` + `As` exist, not that they solve every UI form.

### Example 10: What not to do — string comparison

```go
// BAD
if err != nil && err.Error() == "not found" {
	// brittle
}

// GOOD
if errors.Is(err, ErrNotFound) {
	// stable
}
```

#### What happens here

As soon as someone adds context (`fmt.Errorf("repo: %w", ErrNotFound)`), the string is no longer equal. `Is` still works. That is why the lesson pushes `Is`/`As`.

### Example 11: Named result + `defer` and `error` (bridge to 02.08)

```go
package main

import (
	"fmt"
	"os"
)

func readPrefix(path string) (data []byte, err error) {
	f, err := os.Open(path)
	if err != nil {
		return nil, fmt.Errorf("open %s: %w", path, err)
	}
	defer func() {
		cerr := f.Close()
		if err == nil && cerr != nil {
			err = fmt.Errorf("close %s: %w", path, cerr)
		}
	}()
	buf := make([]byte, 8)
	n, err := f.Read(buf)
	if err != nil {
		return nil, fmt.Errorf("read %s: %w", path, err)
	}
	return buf[:n], nil
}
```

#### What happens here

A **named result** `err` lets `defer` append a failure on `Close` if the read succeeded. `%w` preserves the cause. This connects functions (02.08) and `error` discipline — without panic on I/O.

## Decision analysis

| Decision | Motive |
|----------|--------|
| `error` values | Explicit flow, easy to follow |
| `%w` through layers | Diagnostics + `Is`/`As` |
| Sentinel for stable cases | Stable package contract |
| Custom type for data | Code, field, retry hint |
| No panic for I/O and validation | Process stays alive |
| `Join` for several independent | Do not lose the second `error` |

## Trade-offs

- **Lots** of `if err != nil` — the cost of explicitness; patterns, not magic.
- **Too many sentinels** — API bloat; sometimes a custom type is enough.
- **Too much wrapping** — long messages; keep context useful (`what you did` + `%w`).
- **String-only error** — fast, but without `Is`; OK for small CLIs internally.
- **Panic in `main` for fatal** — acceptable; in libraries not.
- **Log at every layer and return** — duplicate logs; agree where logging happens.

## Common mistakes

1. `_ = err` or complete ignoring.
2. Comparing message strings (`err.Error() == ...`).
3. `fmt.Errorf("%v", err)` then wondering why `Is` does not work.
4. Panic on `os.Open` failure.
5. A sentinel with extra state in a global — race; better a type.
6. Logging and returning the same `error` without agreement → duplicate logs.
7. Mixing `err` from a loop with `defer` without a named result (see 02.08).
8. Returning a non-nil `error` with a “useful” result without documentation.
9. `errors.As(err, he)` instead of `errors.As(err, &he)` — you need a pointer to the variable.

## Idiomatic Go

- Message: lowercase start, often without a period at the end.
- Context: what you did + `%w`.
- `errors.Join` when there are several independent `error` values.
- Document which sentinels / types the package exports.
- In tests: `errors.Is` / `As`, not a brittle message.
- Names: `ErrNotFound`, `ValidationError` — consistent in the package.
- Do not translate the message in lower layers if the upper does i18n — translate at the edge (handler).

## Practical scenario

Checkout service: `ErrInsufficientFunds` sentinel + `PaymentError` with `ProviderCode`. The gateway wraps `fmt.Errorf("checkout: %w", err)`. The handler does `errors.As` for HTTP 402 vs 502. Earlier they compared `err.Error()`, then translating the message in i18n broke production. After `%w` and types, translation is only in the handler; the `error` identity remains.

Panic recovery middleware catches only real bugs (nil **pointer**), not “card declined.” The team introduces a lint rule: forbidden `panic` in `internal/` except `must*` on init paths.

## Check questions

1. **What is `error` in Go?**  
   **Answer:** An **interface** with method `Error() string`; `nil` means no failure.

2. **What is `%w` for in `fmt.Errorf`?**  
   **Answer:** It wraps the cause so that `errors.Is` / `As` / `Unwrap` can follow the chain.

3. **Difference between `errors.Is` and `errors.As`?**  
   **Answer:** `Is` compares with a target value (often a sentinel); `As` looks for a type and fills a **pointer**.

4. **Why not panic on expected failure?**  
   **Answer:** Panic breaks flow and is meant for bugs; expected failure is part of the API contract via `error`.

5. **Why not compare the `err.Error()` string?**  
   **Answer:** The message is not a stable contract; it is brittle under refactor, localization, and wrapping.

6. **What does `errors.Join` do?**  
   **Answer:** Joins several independent `error` values; `Is` can hit any of them.

7. **Why is `fmt.Errorf("%v", err)` not enough through layers?**  
   **Answer:** It inserts text, but does not make an `Unwrap` chain — `Is`/`As` lose the lower identity.

## Summary

`error`s are values: you create them, wrap them with context (`%w`), inspect with `Is`/`As`, type them when you need data. Panic stays for invariants. Discipline around `err` makes Go services predictable through layers. The message is for a human; sentinel and type are for the program.
