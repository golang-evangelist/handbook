# 01.05 Creating Functions and Methods

> **Go Path - Zero to Gopher** / **01 Basics → Go: Getting Started** / Lesson 01.05

## Lesson goals

After this lesson you should be able to:

- write functions with multiple return values and understand the `(T, error)` pattern
- use **named result** sparingly and **variadic** parameters correctly
- introduce `defer` for resource cleanup (LIFO order)
- define a **method** with a value and a pointer **receiver**
- explain why methods are not classes and how **composition** (including **embedding**) is used instead of inheritance
- choose a receiver deliberately: mutation, copy, type consistency

## Prerequisite

- 01.03 and 01.04 (types, zero value, pointer, `struct`, slice, map)
- basic `package` and exported / unexported rules (capital initial letter)
- reading `fmt`, briefly running `go run`

## Problem this lesson solves

Without functions, code is duplicated. Without a clear contract for `error` values you get `panic`s and silent bugs. Without understanding receivers, programmers:

- copy large `struct` values unnecessarily, or
- mutate data thinking they work on a copy (value receiver + field change), or
- build artificial “classes” because they come from Java/C# habits

Go has no class inheritance. Go uses functions + methods on types + composition (+ later interface). This lesson sets that model before control flow and before deeper Fundamentals topics.

## Mental model

A function is a named block with parameters and results. A method is a function with a **receiver** argument in front of the name:

```text
func Name(parameters) results { body }

func (r T)  Name(...)  — value receiver  (copy of r)
func (r *T) Name(...)  — pointer receiver (address)
```

Multiple results enable `(value, error)` without exceptions. `nil` for `error` means “no error”.

`defer` registers a call that runs when leaving the function — **LIFO** (last registered, first executed).

Methods do not create a type hierarchy. Polymorphism comes through interface (later modules), not through `extends`. Composition: “has” instead of “is” — including embedding as sugar for a promoted method.

```text
call Charge(...)
   │
   ├─ success → (Receipt, nil)
   └─ failure → (zero Receipt, error)
         │
         └─ caller ALWAYS checks err before using Receipt
```

## Mechanism

### Basic function

```go
func add(a, b int) int {
	return a + b
}
```

Parameters of the same type can be shortened: `a, b int` instead of `a int, b int`.

An exported name (capital letter) is visible to another `package`. Unexported (lowercase letter) stays inside the package.

### Multiple return values and error

```go
func div(a, b int) (int, error) {
	if b == 0 {
		return 0, fmt.Errorf("division by zero")
	}
	return a / b, nil
}
```

Line by line for `div(10, 0)`:

1. `b == 0` → condition true
2. Returns `0` (zero value for `int`) and a new `error` value
3. The caller must: `v, err := div(10, 0); if err != nil { ... }`
4. **Do not use** `v` until you have checked `err`

The `(T, error)` pattern is the basic contract in Go. There are no checked exceptions. The error path is visible in the types.

`fmt.Errorf("...: %w", err)` wraps an error for later `errors.Is` / `errors.As` (Fundamentals / idioms).

### Named result

```go
func split(sum int) (x, y int) {
	x = sum * 4 / 9
	y = sum - x
	return // “naked” return — returns current x, y
}
```

A named result documents the results in the signature. A naked return in **longer** functions reduces readability — use it rarely.

A good case: `defer` must set the result:

```go
func timed() (elapsed time.Duration) {
	start := time.Now()
	defer func() {
		elapsed = time.Since(start)
	}()
	// ... work ...
	return
}
```

### Variadic parameters

```go
func sum(vals ...int) int {
	total := 0
	for _, v := range vals {
		total += v
	}
	return total
}

sum(1, 2, 3)     // OK
sum(s...)        // unpack slice s []int
```

Rules:

1. A variadic parameter (`...T`) may only be **at the end** of the parameter list
2. Inside the function `vals` has type `[]T`
3. At the call site, `slice...` unpacks an existing slice
4. Each call with an argument list may allocate a temporary slice — measure if it is in a hot loop

**Predict the result:**

```go
func f(nums ...int) { fmt.Println(len(nums)) }
f()
f(1, 2)
```

Answer: prints `0` then `2`. An empty variadic call gives `len == 0`, not a `nil` panic in `range`.

### defer — deferred cleanup

```go
f, err := os.Open(path)
if err != nil {
	return err
}
defer f.Close()
```

Key facts:

1. `defer` arguments are **evaluated immediately**; the call is deferred
2. Execution order: LIFO
3. `defer` in a `for` loop holds resources until the end of the **function**, not the end of the iteration — be careful

```go
func demoDeferArgs() {
	x := 1
	defer fmt.Println("defer sees", x) // evaluates x=1 immediately
	x = 2
	fmt.Println("now", x)
}
// prints: now 2
// then: defer sees 1
```

If you want defer to see a **later** value, use a function literal with a pointer or a named result:

```go
defer func() { fmt.Println(x) }() // reads x when the defer runs
```

### Method and receiver

```go
type Counter struct{ n int }

func (c Counter) Value() int { return c.n }

func (c *Counter) Inc() { c.n++ }
```

Value receiver (`c Counter`): the method works on a **copy**. Changing a field does not change the caller.

Pointer receiver (`c *Counter`): the method works on the address. Changing a field changes the original.

Go automatically takes the address on a call if the value is addressable:

```go
var c Counter
c.Inc()     // like (&c).Inc()
p := &c
p.Value()   // like (*p).Value()
```

Convention: if a type has mutating methods, often **all** methods go on `*T` for method set consistency (important later for interface).

Receiver name: short (`c`, `u`, `s`), not `this` / `self`.

### Composition instead of inheritance

Go **has no** class inheritance. Instead:

1. Fields of type `struct` inside another `struct` (composition)
2. **Embedding** — a nested field without an explicit name; methods are **promoted**

```go
type Engine struct {
	PowerKW int
}

func (e Engine) Describe() string {
	return fmt.Sprintf("%d kW", e.PowerKW)
}

type Car struct {
	Engine // embedding
	Model  string
}

func (c Car) Label() string {
	return c.Model + " (" + c.Describe() + ")"
}
```

`Car` is **not** a subtype of `Engine` for assignment. Embedding is sugar: `c.PowerKW` and `c.Describe()` work because they are promoted. That is composition, not subtype inheritance.

## Rules and syntax

1. A function / method name with a capital letter — exported.
2. `error` is an interface; `nil` means “no error”.
3. Ignore a result explicitly with the blank identifier `_` if you must; do not silently swallow `error` in production.
4. A variadic parameter only at the end of the list.
5. `defer` in a loop can hold resources until the end of the function — close in a nested function or another pattern.
6. Do not mix value and pointer semantics randomly for the same type without a reason.
7. Receiver name short (`c`, `u`, `s`), not `this`/`self`.
8. Use naked return rarely; prefer explicit `return` values.
9. When calling a variadic function with a slice, put `...`.
10. Go has no inheritance — embedding / composition are not `extends`.

## Examples

### Example 1 — Multiple returns and error

```go
package main

import (
	"errors"
	"fmt"
)

func parsePort(s string) (int, error) {
	if s == "" {
		return 0, errors.New("empty port")
	}
	var port int
	_, err := fmt.Sscanf(s, "%d", &port)
	if err != nil {
		return 0, fmt.Errorf("port is not a number: %w", err)
	}
	if port < 1 || port > 65535 {
		return 0, fmt.Errorf("port out of range: %d", port)
	}
	return port, nil
}

func main() {
	for _, in := range []string{"8080", "", "x", "70000"} {
		p, err := parsePort(in)
		if err != nil {
			fmt.Println("input", in, "→", err)
			continue
		}
		fmt.Println("input", in, "→", p)
	}

	// Predict: what is p when err != nil for ""?
	// Answer: 0 — zero value; do not use it
}
```

#### What happens here

The function returns either a valid port or an `error` — never “half-and-half” without a signal. `%w` wraps the error for later `errors.Is` / `errors.As`. The caller always checks `err` before using `p`. For an empty string you get `0` and the message “empty port”; for `"x"` a wrapped parse error; for `"70000"` a range error; for `"8080"` the value `8080` and `nil`. This is the basic idiomatic contract in Go instead of throwing exceptions.

### Example 2 — Variadic, named result, defer

```go
package main

import (
	"fmt"
	"os"
	"strings"
	"time"
)

func joinComma(parts ...string) string {
	return strings.Join(parts, ",")
}

func timed() (elapsed time.Duration) {
	start := time.Now()
	defer func() {
		elapsed = time.Since(start)
	}()
	time.Sleep(20 * time.Millisecond)
	return
}

func writeTemp() error {
	f, err := os.CreateTemp("", "gopatl-*.txt")
	if err != nil {
		return err
	}
	defer os.Remove(f.Name())
	defer f.Close()

	_, err = f.WriteString("Go Path - Zero to Gopher exercise\n")
	return err
}

func main() {
	fmt.Println(joinComma("a", "b", "c"))
	words := []string{"x", "y"}
	fmt.Println(joinComma(words...))
	fmt.Println("duration:", timed())
	if err := writeTemp(); err != nil {
		fmt.Println("error:", err)
	}

	// Predict the defer order in writeTemp:
	// first Close, then Remove (LIFO)
}
```

#### What happens here

`parts ...string` takes an arbitrary number of arguments; `words...` unpacks a slice. The named result `elapsed` makes sense here because `defer` sets the result after the body — one of the rare good cases for naked/named return. In `writeTemp`, `defer` guarantees `Close` and file removal even on an early `return` after a write error. The order is LIFO: `Remove` registered first, then `Close` — on exit `Close` runs first, then `Remove`. (In stricter patterns you also check the `Close` error — a more advanced topic.)

### Example 3 — Value vs pointer receiver

```go
package main

import "fmt"

type Account struct {
	Name    string
	Balance int // cents
}

func (a Account) Display() string {
	return fmt.Sprintf("%s=%d", a.Name, a.Balance)
}

func (a Account) CreditCopy(cents int) {
	a.Balance += cents // changes the copy
}

func (a *Account) Credit(cents int) {
	a.Balance += cents
}

func main() {
	acc := Account{Name: "checking", Balance: 1000}
	acc.CreditCopy(500)
	fmt.Println("after CreditCopy:", acc.Display()) // checking=1000

	acc.Credit(500)
	fmt.Println("after Credit:", acc.Display()) // checking=1500

	p := &Account{Name: "savings", Balance: 0}
	p.Credit(100)
	fmt.Println(p.Display()) // savings=100

	// Predict: what does CreditCopy do on a pointer?
	p.CreditCopy(50)
	fmt.Println("after CreditCopy on p:", p.Display()) // savings=100
}
```

#### What happens here

`CreditCopy` has a value receiver — it works on a copy, state stays `1000`. `Credit` uses `*Account` and changes the original to `1500`. Go automatically takes the address on the call `acc.Credit`. Even when you call `p.CreditCopy(50)`, Go dereferences and copies the **value** for the value receiver — `p.Balance` stays `100`. `Display` can stay a value receiver because it only reads; many styles still keep all methods on `*T` for consistency when the type has mutating methods.

### Example 4 — Composition and embedding

```go
package main

import "fmt"

type Engine struct {
	PowerKW int
}

func (e Engine) Describe() string {
	return fmt.Sprintf("%d kW", e.PowerKW)
}

type Car struct {
	Engine // embedding
	Model  string
}

func (c Car) Label() string {
	return c.Model + " (" + c.Describe() + ")"
}

func main() {
	c := Car{Engine: Engine{PowerKW: 110}, Model: "Urban"}
	fmt.Println(c.Label())
	fmt.Println("direct access:", c.PowerKW)
	fmt.Println("explicit:", c.Engine.Describe())

	// Predict: does this compile?
	// var e Engine = c
	// Answer: no — Car is not Engine in the type system
}
```

#### What happens here

There is no `class Car extends Engine`. `Car` uses **embedding** of the `Engine` field; `Engine` methods are promoted onto `Car` as long as there is no name conflict. That is composition with sugar, not subtype inheritance: `Car` is not a “kind of” `Engine` in the type system for assignment. `c.PowerKW` is shorthand for `c.Engine.PowerKW`. Embedding in more detail comes in Fundamentals; here it shows why you do not need classes to share behavior.

### Example 5 — defer in a loop (trap) and the fix

```go
package main

import (
	"fmt"
	"os"
)

func bad(paths []string) error {
	for _, path := range paths {
		f, err := os.Open(path)
		if err != nil {
			return err
		}
		defer f.Close() // closes only at the end of bad(), not the end of the iteration
		// ... read f ...
		_ = f
	}
	return nil
}

func better(paths []string) error {
	for _, path := range paths {
		if err := readOne(path); err != nil {
			return err
		}
	}
	return nil
}

func readOne(path string) error {
	f, err := os.Open(path)
	if err != nil {
		return err
	}
	defer f.Close()
	// ... read f ...
	_ = f
	return nil
}

func main() {
	fmt.Println("better pattern: defer in a narrow function per resource")
}
```

#### What happens here

In `bad`, each `defer f.Close()` stays registered until the end of `bad` — with thousands of files you hold thousands of open handles. Fix: extract `readOne` so that `defer` is tied to the lifetime of one resource. This is one of the most common production traps with `defer`; remember it before you write batch file processing.

### Example 6 — blank identifier and an error you must not swallow

```go
package main

import (
	"fmt"
	"strconv"
)

func mustPort(s string) int {
	p, err := strconv.Atoi(s)
	if err != nil {
		panic(err) // OK only in main/test helpers, not in a library
	}
	return p
}

func main() {
	// Bad in a production handler:
	// n, _ := strconv.Atoi(userInput)

	n, err := strconv.Atoi("42")
	if err != nil {
		fmt.Println("error:", err)
		return
	}
	fmt.Println("port", n)
	fmt.Println("must", mustPort("8080"))
}
```

#### What happens here

The blank identifier `_` explicitly discards a value — the compiler will not complain — but in production silence on `error` hides bugs. `must*` helpers that call `panic` make sense in `main`, tests, or initialization where failure means “the program must not start”. In library code return `error` to the caller.

## Decision analysis

| Decision | Option A | Option B | Recommendation |
|----------|----------|----------|----------------|
| Failure signal | `(T, error)` | `panic` | A for expected failures; B for a bug / impossible state |
| Named result | named + naked | explicit return | B by default; A for short defer cases |
| Receiver | value `T` | pointer `*T` | `*T` for mutation / large struct / consistency; `T` for small immutable |
| Sharing behavior | embedding | explicit field + delegation | embedding when the relationship is clear; otherwise explicit field |
| Variadic | `...T` | `[]T` | `...T` for a convenient API; `[]T` when you always have a slice |
| Cleanup | `defer` | manual Close on every branch | `defer` immediately after a successful Open |

Why `(T, error)` instead of exceptions? Explicitness: the error path is visible in the code and types. The cost is verbosity. Use named return for short functions where the names document the results, or where `defer` must set the result — otherwise return explicit values.

Choose a pointer receiver when: you mutate, you spare a large structure from copying, or you need consistency with other pointer methods. Choose a value receiver for a small immutable type (`time.Time` style) or when you want the method to guarantee it does not change the original.

## Trade-offs

- **Multiple returns** — clear, but the habit of “ignore err” is dangerous.
- **`defer`** — reliable cleanup, but in long loops it holds resources longer.
- **Pointer receiver** — shared state; a `nil` receiver is possible (`func (a *Account) ...` with `a == nil`).
- **Variadic** — convenient API, but hides a slice allocation at the call site.
- **Embedding** — less boilerplate, more hidden promoted methods; overuse reduces readability.
- **Naked return** — shorter code, harder review and debug.
- **must* + panic** — faster in tools, dangerous in HTTP handlers.

## Common mistakes

1. **Swallowing `error` with the blank identifier**
   ```go
   n, _ := strconv.Atoi(s)
   fmt.Println(n)
   ```
   What happens: you use the **zero value** when parsing fails — a silent bug.  
   Why: the compiler does not complain about `_`.  
   Fix: `n, err := ...; if err != nil { return ..., err }`.

2. **Value receiver + mutation**
   ```go
   func (a Account) Credit(cents int) { a.Balance += cents }
   acc.Credit(500) // Balance does not change
   ```
   What happens: the copy is changed.  
   Why: a value **receiver** copies `Account`.  
   Fix: `func (a *Account) Credit(...)`.

3. **`defer` in a `for` that opens files**
   ```go
   for _, p := range paths {
   	f, err := os.Open(p)
   	defer f.Close() // until the end of the WHOLE function
   }
   ```
   What happens: thousands of open handles.  
   Why: `defer` lasts until the end of the function, not the iteration.  
   Fix: extract `readOne(path)` with its own `defer`.

4. **Variadic without `...` on a slice call**
   ```go
   sum(nums) // type error if the signature is sum(...int)
   ```
   Fix: `sum(nums...)`.

5. **Naked return in a long function** — hard to track results. Prefer explicit `return x, err`.

6. **Embedding as inheritance**
   ```go
   var e Engine = car // does not compile
   ```
   Why: Go has no inheritance; embedding is composition.  
   Fix: use `car.Engine` or redesign the API.

7. **`defer fmt.Println(n)` expecting a later `n`**
   Arguments are evaluated immediately.  
   Fix: `defer func() { fmt.Println(n) }()`.

8. **Unexported method from another package** — lowercase initial letter; rename to exported if needed.

9. **Logging `error` and swallowing it in a library** — return `error` to the caller; log at the boundary.

10. **Mixing value/pointer methods without a reason** — affects the **method set** for interface; be consistent.

## Idiomatic Go

- Often a small, focused function API.
- Return the error; log at the boundary (`main`, HTTP handler).
- Receiver: one or two letters from the type name.
- `defer Close` immediately after a successful Open.
- Do not export methods that are only helpers — lowercase initial letter.
- Prefer composition of structures over “base classes”.
- Be consistent: if one method of a type requires a pointer, mutating ones go on a pointer.
- Use `%w` when wrapping errors.
- Avoid naked return in functions longer than ~20 lines (team style).

## Practical scenario

A billing library has `func Charge(card string, cents int) (Receipt, error)`. The handler in the HTTP layer checks `err` and maps to 402/500. Inside, `type Ledger struct` holds a balance map; methods `func (l *Ledger) Apply(tx Tx) error` use a pointer because they change the map.

An engineer first put a value receiver — unit tests “pass” because they assert on the returned copy, and production “loses” transactions because the map is changed on a copy of the header / value that is discarded. Code review catches: “mutation + value receiver = false success”.

`defer mu.Unlock()` after `mu.Lock()` (when they introduce a mutex) prevents deadlock on early return. The team forbids naked return in files with functions longer than ~20 lines — a style linter in CI.

Third incident: batch file import with `defer f.Close()` inside a loop — after 10k files the process hits the open file descriptor limit. Fix: `processFile(path)` with its own `defer`. After that the PR template checklist has an item: “Is there defer in a loop?”

## Check questions

1. **What is a receiver?**  
   A special method parameter that binds a function to a type (`T` or `*T`).

2. **When to choose a pointer receiver?**  
   When the method changes state, when you need to avoid copying a large value, or when you need method set consistency.

3. **What does `defer` do?**  
   Defers a call until exit from the enclosing function; order is LIFO; arguments are evaluated immediately.

4. **Why use named return rarely?**  
   Naked return in longer functions reduces readability and hides what is returned.

5. **Do methods make Go an OOP language with classes?**  
   No — there is no class inheritance; methods + composition + interface.

6. **What is the type of parameter `vals` in `func f(vals ...int)`?**  
   Inside the function: `[]int`.

7. **Why does `p.CreditCopy(50)` not change `p` if it is a value receiver?**  
   Because for a value receiver the value is copied; the change stays on the copy.

8. **Does embedding mean `Car` is a subtype of `Engine`?**  
   No. It is composition with promoted method/fields, not subtype inheritance.

When reviewing someone else’s code, look for a value receiver with a field change — that is the fastest signal that the author still mixes the Java/C# model with the Go model.

### Additional mechanism: method set (introduction)

The **method set** of a type determines which methods “belong” to the type — later critical for interface.

- For type `T`, the method set includes methods with receiver `T`
- For type `*T`, the method set includes methods with receiver `T` **and** `*T`

That is why receiver consistency is not just style: it affects whether a value satisfies an interface. Details come in Fundamentals; here remember the rule: if a type has at least one pointer method because of mutation, often put all methods on `*T`.

**Predict:**

```go
type Box struct{ n int }
func (b Box) Get() int    { return b.n }
func (b *Box) Set(v int)  { b.n = v }

var b Box
b.Set(3)           // OK — Go takes &b
fmt.Println(b.Get()) // 3
```

The call `b.Set(3)` works because `b` is addressable. The literal `(Box{}).Set(3)` does **not** compile — a temporary value is not addressable.

### Additional mechanism: function as value (preview)

Functions are values. You can assign them to a variable and pass them (higher-order function preview):

```go
func apply(n int, fn func(int) int) int {
	return fn(n)
}

func main() {
	double := func(x int) int { return x * 2 } // function literal
	fmt.Println(apply(5, double)) // 10
}
```

A function literal here is not yet a full **closure** capturing outer variables in the sense of later exercises — Fundamentals goes deeper. In the notes use the official term **closure**.

### Checklist before merging a function

1. Does every `error` path return zero value + `error`, and success value + `nil`?
2. Is the receiver `*T` where there is mutation?
3. Does `defer Close` sit immediately after a successful Open?
4. Is there `defer` in a loop without a nested function?
5. Is the name exported only if other packages need it?
6. Does the variadic parameter sit at the end of the list?
7. Does embedding really simplify the API, or only hide dependencies?

If the checklist passes in code review, this lesson is done. The next lesson joins these contracts with `if` / `for` / `switch` into a readable flow.

One sentence to take away: **mutation needs a pointer receiver; an error needs `error`; a resource needs `defer`.** If you keep those three consistent, the rest of the function API in Go becomes predictable.

Before you move on to control flow, write one small `Ledger` structure with `Apply` (pointer) and `Balance` (value or pointer) method, plus `(Receipt, error)` on a public function — that is the exercise that joins the whole lesson.

If `Apply` with a value receiver “passes” a test on the copy, deliberately break the test so it asserts state **after** the call on the same object — the bug surfaces immediately.

One more signal in review: `defer` in a `for` without a nested function. If you see it in a batch file import, ask for a refactor to `processOne(path)` before merge — that is the same lesson as `Close`, just with thousands of handles.

Leave the blank identifier `_` for `error` only in tools where discarding is deliberate and documented. In an HTTP handler and library code that is a red flag: the error must either be returned, or logged at the boundary with a reason.

Finally: Go has no inheritance. If you need to share behavior, choose composition / embedding or later interface — not a class tree.

## Summary

Functions with multiple results and `error` make the contract explicit. Variadic and `defer` cover practical API and resource patterns. A method binds behavior to a type through a value or pointer receiver; composition (and embedding) replaces class inheritance. Go has no inheritance — you build from functions, methods, and composition. The next lesson manages program flow.
