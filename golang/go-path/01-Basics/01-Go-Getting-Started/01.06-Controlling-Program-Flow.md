# 01.06 Controlling Program Flow

> **Go Path - Zero to Gopher** / **01 Basics → Go: Getting Started** / Lesson 01.06

## Lesson goals

After this lesson you should be able to:

- use `if` with an init statement and guard clauses
- write `switch` with an expression and without an expression (without the C-fallthrough habit)
- master the three forms of the `for` loop and `range` (including Go 1.22 `for i := range n`)
- use `break` / `continue` deliberately
- understand `panic` / `recover` at an introductory level and why `panic` is not a substitute for `error`

## Prerequisite

- functions, types, collections from 01.03–01.05
- reading `error` values and the `(T, error)` pattern
- Go 1.22+

## Problem this lesson solves

Control flow determines readability and correctness. In Go there is no `while` or `do-while` as separate keywords — everything is `for`. `switch` is stronger than in C (no automatic fallthrough). Beginners often misuse `panic` as a Java exception, or forget `if err != nil` right after a call.

Without a clear branching model, code becomes an `if/else` pyramid, and loops become busy-spin or “break from switch thinking I left the for”. This lesson sets the rules before a deeper Fundamentals pass (02.05–02.06).

## Mental model

A program is a sequence of blocks. `if` chooses a branch. `switch` chooses among a list of conditions or values. `for` repeats while the condition holds — including “while” and an infinite loop. `range` produces indexes/values from a collection.

The error path in idiomatic Go goes **up early**:

```text
do the work
  → if error: return immediately (guard)
  → otherwise continue on the happy path (sidewalk, not a pyramid)
```

`panic` unwinds the normal stack; `recover` can catch `panic` only in a `defer` function. That is for catastrophic situations and infrastructure (e.g. isolating one bad handler), not for “file not found”.

## Mechanism

### `if` with init — narrower scope

```go
if n, err := strconv.Atoi(s); err != nil {
	return 0, err
} else if n < 0 {
	return 0, fmt.Errorf("negative: %d", n)
} else {
	return n, nil
}
```

What happens:

1. `strconv.Atoi(s)` runs **once** in the init part.
2. `n` and `err` live only inside the `if` / `else if` / `else` block — they do not “leak” into the rest of the function.
3. The compiler checks types; `err` has type `error`.

**Predict the result:** after this `if`, may you write `fmt.Println(n)` in the continuation of the function?

**Answer:** No — `n` is not in scope outside the `if`. If you need `n` afterward, use the classic form:

```go
n, err := strconv.Atoi(s)
if err != nil {
	return 0, err
}
// here n lives
```

### Guard clauses — shallow happy path

Instead of:

```go
if ok {
	if valid {
		// real work deep to the right
	} else {
		return errInvalid
	}
} else {
	return errNotOk
}
```

write:

```go
if !ok {
	return errNotOk
}
if !valid {
	return errInvalid
}
// real work here, without an else pyramid
```

The runtime does nothing special — this is style. But style changes how many bugs review catches: an early `return` makes all branches visible.

### `switch` with a value

```go
switch day {
case 1, 2, 3, 4, 5:
	fmt.Println("weekday")
case 6, 7:
	fmt.Println("weekend")
default:
	fmt.Println("invalid")
}
```

Line by line for `day == 6`:

1. Go compares `day` with the list in the first `case` — no match.
2. The second `case` contains `6` — match.
3. The body runs; there is **no** fall into `default` or the next case.
4. After the body, the `switch` is done.

Unlike C: a case does **not** “leak” downward. If you really want leaking, you write an explicit `fallthrough` (rare; Fundamentals 02.05).

### `switch` without an expression — a substitute for an `else if` chain

```go
switch {
case score >= 90:
	grade = "A"
case score >= 80:
	grade = "B"
default:
	grade = "C"
}
```

Each `case` is a boolean expression. The first true one wins. For `score == 85`: first case false, second true → `"B"`.

### Three forms of `for`

```go
for i := 0; i < 3; i++ { } // classic counter
for i < 3 { }               // while-style (condition only)
for { }                     // forever; exit with break/return
```

The compiler treats them all as the same loop. There is no separate `while` instruction in the language.

Go 1.22+ adds:

```go
for i := range 3 {
	// i = 0, 1, 2
}
```

That is a shorter form of “repeat 3 times”. It requires `go 1.22` (or newer) in `go.mod`.

### `range`

```go
for i, v := range slice { }
for k, v := range m { }
for i, r := range s { } // string → byte index + rune
```

For slice `[]int{10, 20}`:

| Iteration | `i` | `v` |
|-----------|-----|-----|
| 1 | 0 | 10 |
| 2 | 1 | 20 |

`v` is a **copy** of the element. Changing `v` does not change the slice. Changing `slice[i]` does.

`range` over a `nil` slice or `nil` **map** — zero iterations, no `panic`.

### `break` / `continue`

- `continue` — go to the next iteration of the same loop.
- `break` — leave the **nearest** loop or `switch`.

Trap: `break` inside a `switch` that is inside a `for` leaves the `switch`, **not** the loop. You learn labels deeper in 02.06; here remember the trap.

### `panic` / `recover` (introduction)

```go
defer func() {
	if r := recover(); r != nil {
		fmt.Println("caught:", r)
	}
}()
panic("something fatal")
```

What the runtime does:

1. `panic` starts unwinding the stack of that goroutine.
2. All `defer`s of that function run (LIFO).
3. If some `defer` calls `recover`, the panic stops in that goroutine; `recover` returns the `panic` argument.
4. If there is no `recover`, the process prints the stack and exits.

**Do not use** for input validation. For “port is not a number” return `error`.

### Concrete trace: from raw string to discount

Imagine input `"4599"` and code `"SAVE25"`. Steps that the programmer and the runtime walk together:

1. `strconv.Atoi("4599")` → `n=4599`, `err=nil`.
2. Guard: price is not negative.
3. Code is not empty.
4. Code is known (`SAVE25`) → `percent=25`.
5. Calculation: `4599 * 75 / 100`.
   - `4599 * 75 = 344925`
   - `344925 / 100 = 3449` (integer; remainder discarded)
6. Function result: `(3449, nil)`.
7. The caller sees `err == nil` and may use `3449`.

If the input is `"x"`:

1. `Atoi` → `n=0`, `err != nil`.
2. The guard in the `if` init branch prints failure and does **not** call `discount`.
3. You never “hit” business logic with garbage in `n`.

This trace is the template for almost every Go handler: parse → check `error` → work → result.

### What the compiler rejects in control flow

The compiler does **not** check whether you covered all `case` values. That is why `default` in a `switch` over an enum is not decoration — it catches future constants.

The compiler **rejects**:

- `if x` where `x` is not `bool` (no truthy numbers as in C)
- using a variable from `if` init outside the block
- `fallthrough` that is not the last statement in a `case`

The compiler does **not** catch:

- an infinite loop without an exit
- a forgotten `if err != nil`
- a `break` that leaves the wrong level

That is why style (guard clauses) and tests exist.

### Mapping from other languages

| Habit | In Go |
|-------|-------|
| `while (cond)` | `for cond { }` |
| `do/while` | `for { ...; if !cond { break } }` |
| C fallthrough | case does not expand; join lists |
| `try/catch` | `(T, error)` + guard |
| `foreach` | `for _, v := range ...` |

### Mini checklist before merge

- Every call with `error` has `if err != nil` immediately below
- No `panic` for user input
- `switch` has `default` where it makes sense
- An infinite `for` has a clear exit
- `break` in a `switch` inside a `for` does what you think
- Integer `range` only with Go 1.22+ in `go.mod`

## Rules and syntax

1. Parentheses around `if`/`for`/`switch` conditions are not needed; braces are mandatory.
2. `switch` cases automatically break — `fallthrough` is explicit and rarely needed.
3. `range` on a nil slice/map — zero iterations, no `panic`.
4. One value from `range` on a slice gives the index; use the blank identifier `_` when you do not need it.
5. `panic` with `nil` still panics.
6. `recover` outside `defer` does nothing useful.
7. Prefer `if err != nil { return ..., err }` early — guard clauses.
8. Go 1.22+: `for i := range n` requires `n` of an integer type.

## Examples

### Example 1 — if init and guard clauses

```go
package main

import (
	"fmt"
	"strconv"
)

func discount(priceCents int, code string) (int, error) {
	if priceCents < 0 {
		return 0, fmt.Errorf("price cannot be negative")
	}
	if code == "" {
		return priceCents, nil
	}
	if code != "SAVE10" && code != "SAVE25" {
		return 0, fmt.Errorf("unknown code %q", code)
	}
	percent := 10
	if code == "SAVE25" {
		percent = 25
	}
	return priceCents * (100 - percent) / 100, nil
}

func main() {
	raw := "4599"
	if price, err := strconv.Atoi(raw); err != nil {
		fmt.Println("failure:", err)
	} else {
		out, err := discount(price, "SAVE10")
		if err != nil {
			fmt.Println(err)
			return
		}
		fmt.Println(out)
	}
}
```

#### What happens here

Early returns reduce nesting. `if` with `strconv.Atoi` keeps `price` and `err` in a narrower scope.

Trace for `discount(4599, "SAVE10")`:

1. `priceCents >= 0` — OK.
2. `code != ""` — OK.
3. code is `SAVE10` — OK.
4. `percent = 10`.
5. `4599 * 90 / 100` → `413910 / 100` → `4139` (integer division).

### Example 2 — switch with and without an expression

```go
package main

import "fmt"

func classifyMethod(m string) string {
	switch m {
	case "GET", "HEAD":
		return "safe-read"
	case "POST", "PUT", "PATCH":
		return "write"
	case "DELETE":
		return "delete"
	default:
		return "unknown"
	}
}

func band(score int) string {
	switch {
	case score < 0 || score > 100:
		return "invalid"
	case score >= 90:
		return "excellent"
	case score >= 75:
		return "very good"
	case score >= 50:
		return "pass"
	default:
		return "fail"
	}
}

func main() {
	fmt.Println(classifyMethod("PUT")) // write
	fmt.Println(band(82))              // very good
}
```

#### What happens here

The first `switch` compares a value; multiple patterns in one `case` share the same branch. The second `switch` without an expression replaces an `else if` chain. No fallthrough: after a matched case, execution does not “leak”.

**Predict the result:** `band(90)` — which string?

**Answer:** `"excellent"` — the first case that is true (after the range check) is `score >= 90`.

### Example 3 — for forms, range, Go 1.22 integer range

```go
package main

import "fmt"

func main() {
	for i := 0; i < 3; i++ {
		fmt.Println("classic", i)
	}

	n := 3
	for n > 0 {
		fmt.Println("while-style", n)
		n--
	}

	sum := 0
	for _, v := range []int{2, 4, 6} {
		sum += v
	}
	fmt.Println("sum", sum) // 12

	for i := range 3 {
		fmt.Println("int-range", i) // 0 1 2
	}

	count := 0
	for {
		count++
		if count >= 3 {
			break
		}
		if count == 2 {
			continue
		}
		fmt.Println("infinite loop step", count)
	}
}
```

#### What happens here

Three classic forms + integer `range` (1.22+). `range` gives index/value; `_` discards the index. An infinite loop uses `break`/`continue`.

Trace of the infinite loop:

| count after ++ | condition | action |
|----------------|-----------|--------|
| 1 | `< 3`, not 2 | print step 1 |
| 2 | `< 3`, `== 2` | `continue` (skip print) |
| 3 | `>= 3` | `break` |

### Example 4 — panic/recover only as isolation

```go
package main

import "fmt"

func safeRun(label string, fn func()) {
	defer func() {
		if r := recover(); r != nil {
			fmt.Printf("%s: recovered from panic: %v\n", label, r)
		}
	}()
	fn()
	fmt.Printf("%s: finished normally\n", label)
}

func main() {
	safeRun("task-1", func() {
		fmt.Println("working")
	})
	safeRun("task-2", func() {
		panic("simulated bug in an add-on")
	})
	fmt.Println("main program continues")
}
```

#### What happens here

`safeRun` shows the pattern frameworks use so one bad handler does not crash the whole process. `recover` catches the `panic` value. After recovery, `safeRun` finishes, and `main` continues.

For an expected failure (e.g. bad JSON) you use `error` — `panic` would be the wrong signal.

### Example 5 — break in switch inside for (trap)

```go
package main

import "fmt"

func main() {
	cmds := []string{"a", "stop", "b"}
	for _, c := range cmds {
		switch c {
		case "stop":
			break // leaves switch, NOT for
		}
		fmt.Println("after switch:", c)
	}
	fmt.Println("loop done")
}
```

#### What happens here

The output will include `after switch: stop` — because `break` did not stop the loop. Fix in this lesson: use `return` from the function, or `continue` with a condition; in 02.06 you learn labels (`break Outer`).

## Decision analysis

| Decision | Option A | Option B | Recommendation |
|----------|----------|----------|----------------|
| Error | guard + `return err` | deep `else` | A |
| Multiple branches | `switch` | `else if` chain | `switch` when ≥3 discrete / ranges |
| Loop | only `for` | look for `while` | only `for` |
| Failure | `error` | `panic` | `error` for expected; `panic` for a bug |
| Scope | `if` init | outer variable | init when the value is needed only in the branch |

## Trade-offs

- **Early return** — more `return` points, but shallower blocks.
- **Init in if** — narrower scope, less convenient for reuse.
- **Infinite for** — flexible, easy to forget the exit condition.
- **recover** — can hide bugs if panics are swallowed too much.
- **Fallthrough** — exists, but almost always better to join case lists.

## Common mistakes

1. **Forgotten `if err != nil`**
   ```go
   n, err := strconv.Atoi(s)
   fmt.Println(n) // uses n even when err != nil
   ```
   What happens: you often get the **zero value** (`0`) and a “success” that is not a success.  
   Why: Go does not throw an exception; you must read `error`.  
   Fix: immediately `if err != nil { return ..., err }`.

2. **Expecting C fallthrough**
   ```go
   switch x {
   case 1:
   	fmt.Println("one")
   case 2:
   	fmt.Println("two")
   }
   ```
   What happens for `x==1`: only “one”.  
   Why: a Go case does not leak.  
   Fix: `case 1, 2:` or explicit `fallthrough` (rare).

3. **`panic` instead of `error`**
   ```go
   if user == "" {
   	panic("empty user")
   }
   ```
   What happens: crashes the goroutine/process.  
   Why: empty input is an expected failure.  
   Fix: `return "", fmt.Errorf("empty user")`.

4. **`break` in switch thinking it breaks for** — see example 5.

5. **`recover` outside defer**
   ```go
   recover() // catches nothing useful here
   panic("x")
   ```
   What happens: the process still crashes.  
   Why: `recover` works only in a `defer` of that goroutine.  
   Fix: `defer func() { recover() }()`.

6. **Busy loop without an exit**
   ```go
   for { /* forgotten break */ }
   ```
   What happens: 100% CPU.  
   Fix: a condition, `break`, or blocking I/O / `select` (later).

## Idiomatic Go

- Guard clauses for errors and validation.
- `switch` for discrete values and ranges.
- Only `for` for loops; do not look for `while`.
- `continue` when it reduces nesting.
- `panic` not in a public API for expected failures.
- Keep `case` bodies short — extract functions.
- Check `err` before using `T`.

## Practical scenario

A worker reads jobs from a queue. The loop is `for { job, ok := dequeue(); if !ok { break }; ... }`. For each job, `switch job.Type` chooses a handler. Payload validation returns `error`; the handler logs and goes to `continue`, it does not panic. Around the plugin call sits `defer recover` because plugins are third-party — the worker records a metric and moves on. In code review the team rejects a PR that uses `panic` for “invalid JSON”.

## Check questions

1. **Which keyword replaces while?**  
   `for` with only a condition.

2. **Does a case automatically fall into the next?**  
   No — you need explicit `fallthrough`.

3. **Where does `recover` have an effect?**  
   In a function called directly from `defer`.

4. **Why if init?**  
   Narrower scope for temporary variables.

5. **When to use panic?**  
   For unforeseen states — not for ordinary `error` situations.

6. **What does `for i := range 3` do in Go 1.22?**  
   `i` goes 0, 1, 2.

7. **Does `break` in switch break the surrounding for?**  
   No — only the switch (without a label).

### Additional example: parsing a list with continue

```go
package main

import (
	"fmt"
	"strconv"
)

func parseAll(raw []string) (vals []int, bad int) {
	for _, s := range raw {
		n, err := strconv.Atoi(s)
		if err != nil {
			bad++
			continue
		}
		vals = append(vals, n)
	}
	return vals, bad
}

func main() {
	v, b := parseAll([]string{"1", "x", "3", ""})
	fmt.Println(v, b) // [1 3] 2
}
```

#### What happens here

`continue` skips invalids without nesting. A named result here documents two counters; you could also use an explicit return. Trace: `"x"` and `""` increment `bad`; `1` and `3` go into the slice.

### Additional example: switch + for for a small state machine

```go
state := "start"
for i := 0; i < 5; i++ {
	switch state {
	case "start":
		state = "work"
	case "work":
		if i == 3 {
			state = "done"
		}
	case "done":
		fmt.Println("done at", i)
		state = "end"
	case "end":
		// no-op
	}
}
```

#### What happens here

The loop drives time; `switch` holds state. When a state machine grows, you often move to a map of handlers — but for an introduction this form is readable.

### Control flow checklist

- [ ] every `error` checked immediately
- [ ] no `panic` for user input
- [ ] `default` where an enum can grow
- [ ] `break` level correct
- [ ] integer range only with Go 1.22+
- [ ] infinite `for` has an exit

### Final mental model of the lesson

Control flow is not a list of keywords — it is a way to make **failure visible** and the **happy path shallow**. When you review someone else’s PR, look for:

1. Is `error` being lost?
2. Is `switch` clearer than an `else if` chain?
3. Does the loop have an obvious exit?
4. Does `panic` sit where `error` belongs?

If those four questions pass, the syntax is already done.

One takeaway exercise: take a 40-line function with an `if` pyramid and rewrite it into guard clauses + one `switch`. Compare the diff — usually half the indentation disappears.

Another: run the example with `break` in switch inside for and convince yourself with your eyes that the loop continues — that is a lesson theory rarely “lands” until you see the output.

## Summary

Control flow in Go relies on `if` (with init), a strong `switch`, a single `for` loop, and `range`. `break`/`continue` steer loops. `panic`/`recover` exist, but are not a substitute for `error`. That wraps up Getting Started; Fundamentals deepens the environment and the same topics.
