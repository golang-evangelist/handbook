# 01.04 Working with Collections

> **Go Path - Zero to Gopher** / **01 Basics → Go: Getting Started** / Lesson 01.04

## Lesson goals

After this lesson you should be able to:

- tell apart an **array** `[N]T` from a **slice** `[]T`: value, fixed length, header
- use `len`, `cap`, `append` and understand sharing of the **backing array**
- work with a **map**: `nil` map, comma-ok idiom, `delete`, random order
- define a **struct**, named fields, and a **composite literal**
- choose the right collection for the problem (order, lookup, fixed schema)
- predict when `append` reallocates and when a subslice “overwrites” someone else’s data

## Prerequisite

- lesson 01.03 (types, zero value, pointer, pass by value, `string` / UTF-8)
- ability to run `go run` in a module
- basic understanding that arguments are copied

## Problem this lesson solves

Almost every program gathers data: a list of users, an index by ID, a record with multiple fields. Without an accurate memory model you get bugs that look “intermittent”:

- you mix array and slice → unexpected copies or mutations of “someone else’s” data through a shared backing array
- you write into a `nil` map → `panic` in production under the first load
- you treat a `struct` like a map without a schema → you lose type checking and autocomplete
- you call `append(s, x)` without assigning the result back → “missing” elements
- you rely on `range` order over a map → flaky tests

This lesson builds an accurate model: what is a value, what is a header, what is copied, what is shared.

## Mental model

Four aggregates, four contracts:

**Array** `[N]T` — a value with exactly N elements of type T. Assignment copies the **entire** array. Length is part of the type: `[3]int` and `[4]int` are not the same type.

**Slice** `[]T` — a small **header**: pointer to the backing array, `len`, `cap`. Assignment copies the header, not the elements. `append` may allocate a new backing array when there is no capacity left.

**Map** `map[K]V` — a reference descriptor to a hash table. The zero value is `nil`; reading from a `nil` map returns the zero value of the value type; writing to a `nil` map panics. You need `make` or a composite literal.

**Struct** — an aggregate of named fields. A value type: assignment copies the fields. A composite literal can use field names (recommended).

```text
slice header:
  ┌──────────┐
  │ ptr  ──────────► [ backing array ........ ]
  │ len = 3  │
  │ cap = 8  │
  └──────────┘
```

Remember: **two slice headers can share the same backing array**. A change through one is visible to the other — until `append` eventually reallocates.

## Mechanism

### Array — fixed length in the type

```go
var a [3]int              // [0 0 0] — zero value of the elements
b := [3]int{1, 2, 3}
c := [...]int{1, 2}       // compiler counts: [2]int
```

Line by line for `var a [3]int`:

1. The type is `[3]int` — exactly 3 elements of type `int`
2. No initializer → each element gets the zero value `0`
3. `len(a)` is `3`; `cap(a)` is also `3` (for an array always `len == cap`)

Assignment copies:

```go
fixed := [3]int{1, 2, 3}
copied := fixed
copied[0] = 99
// fixed is still [1 2 3]; copied is [99 2 3]
```

**Predict the result:** can `[3]int` and `[4]int` be assigned to each other?

Answer: **no** — different types. You need an explicit element conversion or you go through a slice.

### Slice — header over an array

```go
s := []int{1, 2, 3}           // literal: len=3, cap=3
t := make([]int, 0, 8)        // len=0, cap=8
u := b[:]                     // slice view over array b
```

`make([]T, len)` sets the length (elements = zero value).  
`make([]T, len, cap)` also sets the capacity.  
`make([]T, 0, n)` is a common pattern: an empty slice ready for `append` with no current elements.

### append — always keep the result

```go
s = append(s, x)
s = append(s, 1, 2, 3)
s = append(s, other...)
```

`append` returns a **new** slice header. The old header in the variable is not updated on its own:

```go
nums := make([]int, 0, 4)
fmt.Printf("start len=%d cap=%d\n", len(nums), cap(nums)) // 0 4

nums = append(nums, 10) // len=1 cap=4
nums = append(nums, 20) // len=2 cap=4
nums = append(nums, 30) // len=3 cap=4
nums = append(nums, 40) // len=4 cap=4
nums = append(nums, 50) // len=5 cap≥8 — reallocation
```

Line by line for the fifth `append`:

1. Current header: `len=4`, `cap=4` — no room for one more element
2. The runtime allocates a new, larger backing array (implementations often double; do not rely on the exact factor in the spec)
3. Copies the old elements, adds `50`
4. Returns a new header; that is why you must write `nums = append(...)`

**Predict the result:**

```go
s := []int{1, 2}
append(s, 3)
fmt.Println(s)
```

Answer: `[1 2]` — forgotten assignment; `3` is “lost” (maybe allocated and then the header discarded).

### Sharing the backing array

```go
a := []int{1, 2, 3, 4}
b := a[:2]   // len=2, but cap may be 4
b[0] = 9     // also changes a[0]
```

A more dangerous scenario — `append` on a subslice that still has remaining `cap`:

```go
base := []int{10, 20, 30, 40, 50}
head := base[:3]          // [10 20 30], cap often 5
tail := base[3:]          // [40 50]
head = append(head, 111)  // writes into base[3]!
// base may become [10 20 30 111 50]
```

Line by line:

1. `base` has a backing array of 5 elements
2. `head := base[:3]` — same ptr, `len=3`, `cap=5` (typically)
3. `tail := base[3:]` — points at index 3
4. `append(head, 111)` sees there is room (`cap > len`) → writes at index 3 of the same array
5. `tail[0]` now sees `111` instead of `40`

Safe copy:

```go
safe := append([]int(nil), base[:3]...)
// or: safe := make([]int, 3); copy(safe, base[:3])
```

### Map — hash table with a nil trap

```go
m := map[string]int{"a": 1}
v, ok := m["b"] // v=0, ok=false
delete(m, "a")
```

Zero value:

```go
var ages map[string]int
fmt.Println(ages["Ana"]) // 0 — reading is OK
// ages["Ana"] = 30      // panic: assignment to entry in nil map

ages = make(map[string]int)
ages["Ana"] = 30         // OK
```

Comma-ok separates “key exists with zero value” from “key does not exist”:

```go
scores := map[string]int{"Ana": 0}
v, ok := scores["Ana"]   // 0, true  — exists, value is 0
v2, ok2 := scores["Bob"] // 0, false — does not exist
```

A map key must be **comparable** (no slice, no map, no function as a key). Iteration with `range` has **no guaranteed order**.

### Struct — field schema

```go
type User struct {
	ID   int
	Name string
}
u := User{ID: 1, Name: "Ana"} // named composite literal
```

Assignment copies the fields. If a field is a slice or map, what is copied is the **header/descriptor**, not a deep copy of the contents:

```go
type Product struct {
	SKU   string
	Price int
	Tags  []string
}
p := Product{SKU: "KB-01", Tags: []string{"usb"}}
alias := p
alias.Price = 1           // does not touch p.Price
alias.Tags[0] = "changed" // DOES touch p.Tags[0] — same backing array
```

### Composite literal — quick overview

```go
arr := [2]int{1, 2}
sl := []string{"a", "b"}
mp := map[string]int{"x": 1}
st := User{ID: 2, Name: "Marko"}
```

Prefer named fields for a `struct`: they survive adding / reordering fields.

## Rules and syntax

1. Array length is part of the type; you cannot change it at runtime.
2. `append` must capture the return value: `s = append(s, x)`.
3. `cap` is the capacity up to which `append` can grow without a new allocation (for that header).
4. A map key must be comparable.
5. Map iteration has no guaranteed order — sort the keys explicitly when you need stability.
6. Exported `struct` fields start with a capital letter; unexported with a lowercase letter.
7. `make(map[K]V)` and `map[K]V{}` give an empty usable map; `var m map[K]V` is `nil`.
8. A positional `struct` literal requires all fields in order — brittle; prefer names.
9. `range` over a `nil` slice / `nil` map → zero iterations, no `panic`.
10. Comparing two slices with `==` does not compile (except comparison with `nil`); use `slices.Equal` (Go 1.21+).

## Examples

### Example 1 — Array vs slice, len/cap, append

```go
package main

import "fmt"

func main() {
	var days [7]string
	days[0] = "monday"
	fmt.Println("array len:", len(days), "type fixed at 7")
	fmt.Println("days[1] zero:", days[1] == "")

	nums := make([]int, 0, 4)
	fmt.Printf("start len=%d cap=%d\n", len(nums), cap(nums))
	for i := 1; i <= 5; i++ {
		nums = append(nums, i*10)
		fmt.Printf("after %d: len=%d cap=%d %v\n", i, len(nums), cap(nums), nums)
	}

	fixed := [3]int{1, 2, 3}
	copied := fixed
	copied[0] = 99
	fmt.Println("original array:", fixed, "copy:", copied)

	// Predict: does this compile?
	// var other [4]int = fixed
}
```

#### What happens here

The array `days` has zero-value strings (`""`) at every position until you fill them. The slice starts with `cap=4`; the fifth `append` forces capacity growth (expect a `cap` jump, e.g. to 8). Assignment `copied := fixed` copies the elements; changing the copy does not touch the original. The line `var other [4]int = fixed` would not compile — `[3]int` and `[4]int` are different types. That is the key difference versus a slice header, where the type `[]int` does not carry the length.

### Example 2 — Shared memory and the append trap

```go
package main

import "fmt"

func main() {
	base := []int{10, 20, 30, 40, 50}
	head := base[:3]
	tail := base[3:]
	fmt.Println("head", head, "tail", tail)
	fmt.Printf("head cap=%d\n", cap(head))

	head[2] = 999
	fmt.Println("base after changing head:", base)

	head = append(head, 111)
	fmt.Println("base after append on head:", base)
	fmt.Println("head", head, "tail", tail)

	safe := append([]int(nil), base[:3]...)
	safe[0] = -1
	fmt.Println("base unchanged:", base, "safe:", safe)

	// Predict before running: what is base[3] after append(head, 111)?
}
```

#### What happens here

`head` and `tail` share the same backing array with `base`. Changing `head[2]` changes `base[2]` to `999`. `append` on `head` when there is capacity writes into the same array — it **overwrites** the element that `tail` sees (`40` becomes `111`). That is why “subslice then append” is a dangerous pattern in APIs that return a view. `append([]int(nil), base[:3]...)` copies the elements into a new backing array; `safe` is independent. In production use `copy` or an explicit copy when you need independence — document the function’s contract if it retains a slice.

### Example 3 — Map: nil, make, comma-ok, delete

```go
package main

import "fmt"

func main() {
	var ages map[string]int
	fmt.Println("nil map read:", ages["Ana"]) // 0, no panic
	// ages["Ana"] = 30 // panic: assignment to entry in nil map

	ages = make(map[string]int)
	ages["Ana"] = 30
	ages["Marko"] = 28
	ages["Zero"] = 0

	if years, ok := ages["Lara"]; !ok {
		fmt.Println("Lara is not in the map")
	} else {
		fmt.Println("Lara:", years)
	}

	if years, ok := ages["Zero"]; ok {
		fmt.Println("Zero exists, value:", years)
	}

	delete(ages, "Ana")
	delete(ages, "missing") // no-op
	fmt.Println(ages)

	inventory := map[string]int{
		"cpu": 12,
		"ram": 40,
	}
	for sku, qty := range inventory {
		fmt.Println(sku, qty)
	}

	// Predict: how many times does the same order repeat across 10 runs?
	// Answer: it is not guaranteed — do not rely on order.
}
```

#### What happens here

The zero value of a map is `nil`: reading is safe (returns the zero value), writing is not. `make` allocates the map structure. Comma-ok separates “key exists with zero value” (`Zero` → `0, true`) from “key does not exist” (`Lara` → `0, false`) — critical for `map[string]int` where `0` is a valid value. `delete` is a no-op if the key is absent. `range` does not guarantee order — in tests you sort the keys explicitly.

### Example 4 — Struct and a slice of structs

```go
package main

import "fmt"

type Product struct {
	SKU   string
	Price int // cents
	Tags  []string
}

func main() {
	p := Product{
		SKU:   "KB-01",
		Price: 4599,
		Tags:  []string{"peripherals", "usb"},
	}
	fmt.Printf("%+v\n", p)

	catalog := []Product{
		{SKU: "KB-01", Price: 4599},
		{SKU: "MS-02", Price: 2499, Tags: []string{"wireless"}},
	}
	catalog[0].Price = 4399
	fmt.Println("price after change:", catalog[0].Price)

	alias := p
	alias.Price = 1
	fmt.Println("p.Price still", p.Price)

	alias.Tags = append(alias.Tags, "sale")
	fmt.Println("p.Tags", p.Tags, "alias.Tags", alias.Tags)

	// Predict: does p.Tags contain "sale" if append did NOT reallocate?
	alias.Tags[0] = "mutated"
	fmt.Println("after mutating the element:", p.Tags[0], alias.Tags[0])
}
```

#### What happens here

A `struct` groups fields of different types. `%+v` prints field names. A slice of structs is a common “table in memory” model. Assignment `alias := p` copies the fields: `Price` is independent. But `Tags` is a slice header — the copied header still points at the same backing array until `append` eventually reallocates. Mutating `alias.Tags[0]` therefore also touches `p.Tags[0]`. That is a common source of bugs when “copying” aggregates: a shallow copy of a `struct` is not a deep copy.

### Example 5 — Array as a contract, set pattern, combination

```go
package main

import "fmt"

// Digest is a fixed array — length is part of the type.
type Digest [32]byte

type Session struct {
	ID      string
	UserIDs []string
	Meta    map[string]string
}

func main() {
	var d Digest
	d[0] = 0xab
	fmt.Println("digest length", len(d))

	s := Session{
		ID:      "s-1",
		UserIDs: []string{"u1", "u2"},
		Meta:    map[string]string{"role": "admin"},
	}
	fmt.Printf("%+v\n", s)

	// Set pattern: map[T]struct{}
	seen := make(map[string]struct{})
	for _, id := range s.UserIDs {
		seen[id] = struct{}{}
	}
	if _, ok := seen["u1"]; ok {
		fmt.Println("u1 exists in the set")
	}

	// Predict: len(seen) after writing the same id twice in the loop?
	seen["u1"] = struct{}{}
	fmt.Println("len(seen) =", len(seen)) // still 2
}
```

#### What happens here

`[32]byte` models a fixed-width value better than a slice — it cannot “accidentally” grow; the type carries the contract. `Session` combines a slice (ordered list) and a map (key-value metadata). `map[string]struct{}` is the idiomatic set: the value uses no memory; writing the same key again does not increase `len`. This example ties all four aggregates into one small domain.

### Example 6 — make len versus cap (predict)

```go
package main

import "fmt"

func main() {
	a := make([]int, 3)    // len=3 cap=3, elements 0
	b := make([]int, 0, 3) // len=0 cap=3
	fmt.Println("a", a, "len", len(a), "cap", cap(a))
	fmt.Println("b", b, "len", len(b), "cap", cap(b))

	a = append(a, 9)
	b = append(b, 9)
	fmt.Println("a after append", a) // [0 0 0 9]
	fmt.Println("b after append", b) // [9]
}
```

#### What happens here

`make([]T, n)` immediately has `n` zero-value elements — `append` adds **after** them. `make([]T, 0, n)` is an empty buffer ready for `append` — often a better choice when you are building a list. Predict before running: `a` after append has 4 elements; `b` has 1. Mixing these two forms is a common source of “weird zeros” at the start of a slice.

## Decision analysis

| Need | Choose | Do not choose (usually) | Why |
|------|--------|-------------------------|-----|
| Fixed width (SHA-256, IPv4) | array `[N]T` | slice | length in the type |
| Dynamic list | slice | array | `append`, view |
| Lookup by key | map | linear slice search | average O(1) |
| Ordered sequence + duplicates | slice | map | map scrambles order |
| Unique set | `map[T]struct{}` | slice + linear check | speed + clarity |
| Fixed field schema | struct | `map[string]any` | types, refactor |
| Index + list | slice + map | map only | map has no stable order |

When to use an array? When length is part of the contract (e.g. SHA256 digest `[32]byte`) or for small fixed buffers. For everything else — a slice. A map is for lookup; a slice is for ordered sequence. A struct is for a fixed schema; a string→any map loses types.

`make([]T, n)` sets `len=n`; `make([]T, 0, n)` is empty and ready for append — often a better choice.

Before you introduce a third collection into an API, ask: do I need order, uniqueness, or lookup? One answer — one structure. Two answers — often a slice + map index.

## Trade-offs

- **Slice sharing** — cheap (only the header is copied), but requires discipline around mutation and `append`.
- **Append amortization** — cheap on average, occasionally expensive allocations and copies of the whole backing array.
- **Map** — average O(1) access, higher memory overhead, random order.
- **Large struct values** — clean semantics on assignment, more expensive copying; a pointer shares changes and introduces `nil`.
- **`[N]T` in a public API** — often awkward because of the type; prefer a slice except when N must be exact.
- **Named vs positional literals** — named are longer to write, more resilient to refactor.
- **Deep copy** — more expensive and more tedious, but the only correct option when a “copy” must be independent.

## Common mistakes

1. `append(s, x)` without assigning back into `s`.
2. Writing into a `nil` map.
3. Relying on `range` order over a map.
4. Subslice + `append` that corrupts other views.
5. Comparing slices with `==` (except with `nil`) — does not compile; use `slices.Equal`.
6. Positional `struct` literals that break after adding a field.
7. Mixing `make([]T, n)` and `make([]T, 0, n)` — “weird zeros” at the start.
8. Shallow copy of a `struct` with nested slice/map fields — a false sense of independence.
9. Using an array where you need a dynamic list (and vice versa).
10. Assuming `cap` after `append` always grows by exactly 2× — an implementation detail.

## Idiomatic Go

- Prefer a slice until you need a fixed array.
- Use named `struct` literals.
- Check a map with comma-ok when the zero value is not enough of a signal.
- Document if a function retains a slice and may mutate the backing array.
- For a set: `map[T]struct{}` saves value memory.
- Initialize maps immediately (`make` or a literal); do not leave `nil` if you will write.
- When returning a subslice from a function, consider `slices.Clone` / a copy so the caller does not corrupt your buffer.
- For comparing slices use `slices.Equal` (standard library).
- Export fields only when other packages need to read/write them.

## Practical scenario

An API gateway caches routes in `map[string]Route` for O(1) lookup by path, and for metric output keeps a `[]string` of sorted keys because a map does not preserve order. `Route` is a `struct` with fields for handler name, timeout, and a slice of middleware names.

Production bug #1: function `cloneRoute(r Route)` copies the struct, then changes `Tags` with `append` — the cached tags change too because the header shares the backing array. Fix: copy the tag slice explicitly before changing (`append([]string(nil), r.Tags...)`).

Bug #2: `var hits map[string]int` global without `make` — the first `hits[path]++` panics under load. Initialization in `init` or at construction time fixes it.

Bug #3: a test “the first route in the metric output is always `/health`” — flaky because `range` over a map scrambles order. Fix: collect the keys, `sort.Strings`, then print.

After these three fixes the team adds a short rule to the package README: “if a function returns a slice from an internal buffer, it must document that it is read-only or clone it”. That is cheaper protection against the next shared-backing-array incident.

## Check questions

1. **What is copied when you assign a slice?**  
   The header (`ptr`, `len`, `cap`), not necessarily the backing array elements.

2. **Why does writing to a `nil` map panic?**  
   There is no allocated hash table; you need `make` or a composite literal.

3. **Are `[3]int` and `[4]int` the same type?**  
   No — length is part of the array type.

4. **What is comma-ok on a map for?**  
   It distinguishes an existing key (even with a zero value) from a missing key.

5. **Why named `struct` literals?**  
   They survive adding/reordering fields; they are more readable.

6. **What can go wrong with `head := base[:n]; head = append(head, x)`?**  
   If `head` has remaining `cap`, `append` writes into the same backing array and may overwrite data that other views see.

7. **How do you idiomatically model a set?**  
   `map[T]struct{}` — the key is the element, the value uses no memory.

8. **When to choose an array instead of a slice?**  
   When length is part of the contract (fixed width) or for a small fixed buffer whose size must not “accidentally” grow.


Before the next lesson, practice at least once an intentional bug with a shared backing array — better here than in a production cache.

Whenever you see `append` in a code review, ask two questions: (1) is the result saved? (2) does the header share a backing array with something that must not change?

Those two checks eliminate most bugs from this lesson before they reach main.

### Additional mechanism: copy, clone, full slice expression

When you need an independent copy of the elements:

```go
src := []int{1, 2, 3, 4}
dst := make([]int, len(src))
n := copy(dst, src) // n == 4
dst[0] = 99
// src is still [1 2 3 4]
```

`copy` copies `min(len(dst), len(src))` elements. It does not change the destination’s `len` or `cap` — that is why `dst` must already have sufficient length.

A full slice expression also controls `cap`:

```go
base := []int{10, 20, 30, 40, 50}
head := base[:3:3] // len=3, cap=3 — append MUST reallocate
head = append(head, 111)
// base stays [10 20 30 40 50] — 111 was not written into base
```

Line by line for `base[:3:3]`:

1. The new header points at the same start as `base`
2. `len` is 3
3. `cap` is forced to 3 (the third index)
4. `append` sees `cap == len` → no room → new backing array
5. `base` remains untouched

**Predict the result:**

```go
a := []int{1, 2, 3, 4}
b := a[:2:2]
b = append(b, 9)
fmt.Println(a, b)
```

Answer: `a` stays `[1 2 3 4]`; `b` is `[1 2 9]`. Without the trailing `:2`, `append` could overwrite `a[2]`.

### Additional mechanism: nil slice vs empty slice

```go
var s1 []int           // nil: s1 == nil is true, len=0, cap=0
s2 := []int{}          // empty, non-nil
s3 := make([]int, 0)   // empty, non-nil
fmt.Println(s1 == nil, s2 == nil, s3 == nil) // true false false
```

For most `append` / `range` / `len` behavior, `nil` and an empty slice are the same. The difference shows up in JSON (`null` vs `[]`) and in API contracts where `nil` means “not set” and empty means “set to empty”. Document what your API means.

### Mini exercise in your head: map + struct together

```go
type Item struct {
	SKU string
	Qty int
}

index := map[string]Item{
	"A": {SKU: "A", Qty: 2},
}
it := index["A"]
it.Qty = 5
fmt.Println(index["A"].Qty) // still 2!
```

Why? `index["A"]` returns a **copy** of the `Item` value. Changing `it` does not write back into the map. Fix: `it.Qty = 5; index["A"] = it` or keep `map[string]*Item`.

This is one of the most common traps after “nil map” — remember it before the next lesson on methods.

### Additional mechanism: len, cap, and “empty but capacious”

```go
s := make([]int, 0, 10)
fmt.Println(len(s), cap(s), s == nil) // 0 10 false
s = append(s, 1, 2, 3)
fmt.Println(len(s), cap(s)) // 3 10
s = s[:0]
fmt.Println(len(s), cap(s)) // 0 10 — elements “hidden”, cap remains
```

`s = s[:0]` does not free the backing array; it only sets `len` to 0. Useful for buffer reuse in loops (fewer allocations), dangerous if someone else still holds an old header to the same elements.

**Predict:** after `s = s[:0]`, does the old element `1` still exist in the backing array’s memory?

Answer: **yes**, until GC frees the array when there are no more references. `len` simply does not expose it. That is why buffer reuse in security-sensitive code sometimes needs an explicit wipe (`clear` in newer Go, or a zeroing loop).

### Quick choices before the next lesson

1. Growing list → slice + `append`
2. Lookup by key → map (+ `make`)
3. Fixed width → array
4. Field schema → struct + named composite literal
5. Set → `map[T]struct{}`

If you know these five choices by heart, collections are ready for functions and methods.

Remember one more thing: **a header is not a deep copy**. Every time you assign a slice, a map descriptor, or a `struct` with a slice/map field, ask “what is shared?”. Answering that question prevents the cache bugs from the practical scenario.

Whenever in a code review you see `var m map[...]` without `make`, or `append` without assignment, leave a comment before merge — those are the two cheapest checks from this lesson.

A third cheap check: does `range` over a map in a test assume order? If yes — sort the keys before the assert.

## Summary

An array is a fixed-length value; a slice is a header over an array with `append` and shared memory; a map is a hash table with `nil` traps; a `struct` aggregates typed fields. Choice and discipline around sharing the backing array determine correctness. Composite literals and named fields make code resilient to refactor. The next lesson covers functions and methods.
