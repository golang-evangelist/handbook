# 01.03 Working with Primitive Data Types

> **Go Path - Zero to Gopher** / **01 Basics → Go: Getting Started** / Lesson 01.03

## Lesson goals

After this lesson you should:

- choose an appropriate numeric type and understand `bool` as a separate type, not a “small int”
- distinguish `byte` and `rune`, and understand `string` as an immutable sequence of UTF-8 bytes
- use the **zero value** deliberately: know what you get when you do not write an initializer
- choose between `var` and `:=` according to scope and intent
- define constants and `iota` enumerations, including typed and untyped constants
- work with **pointer** values (`&`, `*`, `new`) without arithmetic
- understand that Go always passes arguments **by value** (a copy of the argument, including a copy of an address)

## Prerequisite

- lessons 01.01 and 01.02 (installation, `go run`, modules, basic `package main`)
- a module where you can run `go run .` or `go run ./cmd/...`
- basic reading of `fmt.Println` / `fmt.Printf`

## Problem this lesson solves

Without a clear type model programmers make bad decisions that later look like “mysterious bugs”:

- they mix `string` indices with “characters” and cut UTF-8 in the middle of a multi-byte character
- they expect `int` to always be 32-bit (or always 64-bit) and send it on the wire without a fixed width
- they forget the zero value and treat `false` / `0` / `""` / `nil` as “I did not set it”, so logic fails
- they try pointer arithmetic as in C (`p+1`) and wonder why the compiler rejects it
- they expect implicit conversions between `int32` and `int64` as in other languages

This lesson sets the rules of memory and type behavior **before** collections, functions, and control flow. If you get the mental model wrong here, every later lesson will only multiply the confusion.

## Mental model

Every variable in Go has a **type** and a **value**. The type determines how many bytes the value occupies, which operations are allowed, and what the zero value is. If you do not add an explicit initialization, the value is the type’s **zero value** — it is not “uninitialized garbage” as in C. That is a conscious language decision: the program is deterministic from the first second.

```text
variable  =  ( type , value )
                  │       │
                  │       └─ either explicit, or the type’s zero value
                  └─ fixed at compile time (static types)
```

A **string** is not an array of `rune` values in memory for indexing. It is a **read-only** sequence of bytes (UTF-8) plus metadata (`len`). Indexing `s[i]` gives a byte of type `byte`. A `range` loop over a `string` walks Unicode code points and yields `rune`.

A **pointer** holds the address of a value of type `T` (the pointer type is written `*T`). Passing a pointer is still **pass by value**: the address is copied, not the whole object. There is no arithmetic (`p+1` does not exist in safe Go). For arrays and slices later you use indices, not pointer movement.

Remember three questions before every declaration:

1. Do I need a **value** (`T`), an **address** (`*T`), or **immutable text** (`string` / `[]byte`)?
2. Does the zero value make sense as a default state, or must I set a value explicitly?
3. Must the type have a **fixed width** (protocol, database, file), or is a local `int` enough?

## Mechanism

This section is the heart of the lesson. Read it slowly: every subsection has concrete values you can predict before running.

### bool

`bool` has exactly two values: `true` and `false`. The zero value is `false`.

```go
var ready bool        // false
hot := true
if hot {              // idiomatic — do not write if hot == true
	fmt.Println("system is ready")
}
```

There is no implicit conversion from a number. This **does not compile**:

```go
var n int = 1
if n { // compiler error: non-boolean condition in if statement
}
```

**Predict the result:** what does this fragment print?

```go
var a bool
var b bool = true
fmt.Println(a, b, a == false, b && !a)
```

Answer: `false true true true`. Zero value `a` is `false`; `!a` is `true`; `b && !a` is `true`.

### Numeric types

Integer types with fixed width:

| Type | Range (approximate) |
|------|---------------------|
| `int8` | −128 … 127 |
| `uint8` (`byte`) | 0 … 255 |
| `int16` | −32768 … 32767 |
| `uint16` | 0 … 65535 |
| `int32` (`rune` is an alias) | ≈ ±2.1×10⁹ |
| `uint32` | 0 … ≈4.2×10⁹ |
| `int64` | ≈ ±9.2×10¹⁸ |
| `uint64` | 0 … ≈1.8×10¹⁹ |

Plus:

- `int` and `uint` — size depends on architecture (usually 32 or 64 bits on today’s machines)
- `uintptr` — an integer type large enough to hold a pointer; low-level / `unsafe`, not for everyday code
- `float32`, `float64` — IEEE 754
- `complex64`, `complex128` — real + imaginary part

`byte` is an **alias** for `uint8`. `rune` is an **alias** for `int32` (Unicode code point). Alias means: the same type in everyday sense, another name for readability.

```go
var b byte = 65        // same as uint8
var r rune = 'A'       // code point 65
fmt.Printf("%T %T\n", b, r) // uint8 int32
```

### Strict conversions — line by line

Go has **no** implicit cast between different numeric types.

```go
var a int32 = 100
// var bad int64 = a + 20   // DOES NOT COMPILE
var b int64 = int64(a) + 20 // OK: b == 120
var c int = int(b)          // OK on a 64-bit machine; watch narrowing
```

Step by step for `b`:

1. `a` has value `100` of type `int32`
2. `int64(a)` makes a new value `100` of type `int64`
3. literal `20` is an untyped constant; in an `int64` context it becomes `int64(20)`
4. the sum is `120` of type `int64`, assigned to `b`

**Predict the result:**

```go
var x int = 5
var y int64 = 10
// fmt.Println(x + y) // ?
```

Answer: **does not compile**. You must `int64(x) + y` or `x + int(y)`.

### float64 and “weird” addition

```go
sum := 0.1 + 0.2
fmt.Printf("%.17f\n", sum)
```

Typical output is not exactly `0.30000000000000000`, but something like `0.30000000000000004`. That is not a Go bug — that is binary floating point. For money use **integers** (cents) of type `int64`, not `float64`.

### String — bytes, not “characters”

Literal:

```go
s := "Gošća"           // UTF-8 in the source file
escaped := "a\tb\n"    // escape sequences
raw := `path\nje`      // raw string — \n is literally two characters
```

Key facts:

1. `string` is immutable: `s[0] = 'x'` **does not compile**
2. `len(s)` counts **bytes**, not visual characters
3. `s[i]` is a `byte` at position `i`
4. `range s` yields `(byteIndex, rune)`
5. The zero value is `""` (empty string, not `nil`)

Line by line for `"Gošća"` (UTF-8):

| Code | Character | Bytes (approx.) |
|------|-----------|-----------------|
| G | ASCII | 1 |
| o | ASCII | 1 |
| š | U+0161 | 2 |
| ć | U+0107 | 2 |
| a | ASCII | 1 |

`len("Gošća")` is **7** (bytes), while `len([]rune("Gošća"))` is **5** (code points).

```go
s := "Gošća"
fmt.Println(len(s))           // 7
fmt.Println(s[0])             // 71 ('G' as a byte)
for i, r := range s {
	fmt.Printf("i=%d r=%c\n", i, r)
}
// i=0 G, i=1 o, i=2 š, i=4 ć, i=6 a
// indices jump because š and ć take 2 bytes
```

**Predict the result:** what is `len("Ž")`?

Answer: **2** (UTF-8 for U+017D is two bytes). `len([]rune("Ž"))` is **1**.

### Zero value — table and meaning

| Type | Zero value | Meaning in practice |
|------|------------|---------------------|
| `bool` | `false` | “off” / “no” |
| numeric | `0` | zero, not “empty” |
| `string` | `""` | empty text |
| pointer `*T` | `nil` | no address |
| later: slice, map, channel, function, interface | `nil` | special rules per type |

```go
var active bool
var count int
var label string
var p *int
fmt.Printf("%v %d %q %v\n", active, count, label, p)
// false 0 "" <nil>
```

Zero value is not an excuse for unclear APIs. When you export a type from a package, document what `var x T` means for your domain.

### var versus :=

```go
var x int = 3      // explicit type
var y = 3          // type inferred: int
z := 3             // short declaration — only inside a function
var p *int         // deliberate zero value: nil
var buf []byte     // nil slice (collections in 01.04)
```

Rules:

1. `:=` requires **at least one new** variable on the left
2. `:=` is not allowed at `package` level — there `var` / `const`
3. Choose `var` when you want the zero value or wider scope
4. Choose `:=` for local variables with a clear type on the right side

```go
n := 10
n, err := strconv.Atoi("20") // OK: err is new; n is only assigned
// n := 30                   // error: no new variables on left side of :=
```

### Constants and iota

Constants are evaluated at compile time.

```go
const Pi = 3.14159
const AppName = "inventory"

const (
	StatusOK = iota // 0
	StatusFail      // 1
	StatusRetry     // 2
)
```

`iota` resets to `0` in **every** `const (` block and grows by 1 per line (including lines with `_`).

```go
type Day int

const (
	Monday Day = iota // 0
	Tuesday           // 1
	Wednesday         // 2
	Thursday          // 3
	Friday            // 4
	Saturday          // 5
	Sunday            // 6
)
```

Bit-shift pattern (common for sizes):

```go
const (
	_  = iota             // discard 0
	KB = 1 << (10 * iota) // iota=1 → 1<<10 = 1024
	MB                    // 1<<20
	GB                    // 1<<30
)
```

Line by line for `MB`:

1. New `const (` block → `iota` starts from 0
2. First line: `_ = iota` → `iota` is 0, value discarded
3. Second line: `KB = 1 << (10 * iota)` — here `iota` is 1 → `1 << 10` = 1024
4. Third line: `MB` repeats the expression with `iota` = 2 → `1 << 20` = 1048576
5. Fourth: `GB`, `iota` = 3 → `1 << 30`

### Typed vs untyped constants

```go
const typed int32 = 42
var x int = int(typed) // needs explicit conversion

const untyped = 42
var y int64 = untyped  // OK
var z float64 = untyped // OK
```

An untyped constant can “live” in a larger range until it is used. That is why `1 << 100` can be a valid constant, and does not fit in `int` on a 64-bit machine as a variable without context.

**Predict the result:**

```go
const u = 42
var a int32 = u
var b float64 = u
fmt.Println(a, b)
```

Answer: `42 42` — prints without error because `u` is untyped.

### Pointer — address without arithmetic

```go
x := 10
p := &x          // p has type *int, value = address of x
fmt.Println(*p)  // 10 — dereference
*p = 11          // changes x
fmt.Println(x)   // 11

q := new(int)    // *int, points to zero value (0)
fmt.Println(*q)  // 0
*q = 5

var r *int       // nil
// *r = 1        // panic: nil pointer dereference
```

What `new(int)` does step by step:

1. Allocates memory for one value of type `int`
2. Sets that memory to the zero value (`0`)
3. Returns a pointer `*int` to that memory

There is no `p++` on a pointer. There is no `p + 1`. For arrays / slices use indices. Package `unsafe` exists for rare low-level cases — out of scope of this lesson.

### Pass by value — copy of the argument

```go
func addOne(v int) {
	v++ // changes only the local copy
}

func addOnePtr(p *int) {
	*p++ // changes the value at the address
}

func main() {
	n := 10
	addOne(n)
	fmt.Println(n) // 10

	addOnePtr(&n)
	fmt.Println(n) // 11
}
```

Line by line for `addOne(n)`:

1. `n` is `10` in `main`
2. On the call, Go copies value `10` into parameter `v`
3. `v++` makes `v` equal to `11`
4. The function ends; `n` in `main` is still `10`

Line by line for `addOnePtr(&n)`:

1. `&n` is the address of variable `n`
2. That address is **copied** into parameter `p` (still pass by value!)
3. `*p++` reads the memory at that address and increments it
4. `n` in `main` becomes `11`

For small types (`int`, `bool`, small `struct`) a copy is cheap and often clearer. Choose a pointer when you share mutations or when you measure that a copy is expensive — not “just in case”.

## Rules and syntax

1. Explicit conversion: `float64(x)`, never an implicit cast as in C / JavaScript.
2. `int` and `int64` are **different types** — conversion is required.
3. `:=` is not allowed at package level; there it is `var` / `const`.
4. An unused local variable — compile error (not a warning).
5. `nil` is not valid for an ordinary `int` or `string`; it is for pointer, slice, map, channel, function, interface.
6. `string` indices are bytes; a UTF-8 character can take 1–4 bytes.
7. A typed constant must fit the type; untyped adapts to context within the rules.
8. `byte` ≡ `uint8`, `rune` ≡ `int32` — but choose the name by intent (`byte` for a buffer, `rune` for text).
9. Dereferencing a `nil` pointer → `panic` at runtime.
10. Concatenating `string`s makes a new `string` (immutability).

## Examples

### Example 1 — Types, zero value, conversions

```go
package main

import "fmt"

func main() {
	var active bool
	var count int
	var label string
	fmt.Printf("zero: %v %d %q\n", active, count, label)

	var a int32 = 100
	var b int64 = int64(a) + 20
	fmt.Println("b =", b)

	sum := 0.1 + 0.2
	fmt.Printf("float64 sum=%.17f\n", sum)

	var hot bool = true
	if hot {
		fmt.Println("system heated")
	}

	// Predict: does this compile?
	// var c int64 = a
	// Answer: no — need int64(a)
}
```

#### What happens here

Uninitialized variables get the zero value — the program is deterministic from the start. `int32` does not add directly with `int64` without conversion; that is why `int64(a) + 20` yields `120`. Adding `0.1+0.2` shows binary floating point: the result is not always “0.3” in decimal print with many digits. `bool` enters `if` without comparison to `true` — idiomatic Go. The commented line `var c int64 = a` would not pass the compiler: types must match explicitly.

### Example 2 — byte, rune, string

```go
package main

import "fmt"

func main() {
	s := "Gošća"
	fmt.Println("bytes:", len(s))
	fmt.Println("first byte:", s[0])

	fmt.Println("--- range by rune ---")
	for i, r := range s {
		fmt.Printf("i=%d r=%c U+%04X\n", i, r, r)
	}

	b := []byte(s)
	rs := []rune(s)
	fmt.Println("bytes len:", len(b), "runes len:", len(rs))

	letter := 'Ž'
	fmt.Printf("rune literal: %T %c %d\n", letter, letter, letter)

	escaped := "line\t\"quotes\"\n"
	raw := `path\nje literally`
	fmt.Print(escaped)
	fmt.Println(raw)

	// Predict: len("č") ?
	fmt.Println("len(č) =", len("č"))
}
```

#### What happens here

`len(s)` counts UTF-8 bytes, not “visual characters”. For `"Gošća"` expect `7`, not `5`. `range` gives the byte index where the code point starts and the `rune` value — that is why indices jump (0, 1, 2, 4, 6). Conversion to `[]rune` gives one element per code point. Single-quote literals are `rune`. A raw string does not interpret escape sequences — useful for Windows paths and regex. `len("č")` is `2` because “č” is a multi-byte UTF-8 character.

### Example 3 — Constants, iota, typed constants

```go
package main

import "fmt"

type Day int

const (
	Monday Day = iota
	Tuesday
	Wednesday
	Thursday
	Friday
	Saturday
	Sunday
)

const (
	_  = iota
	KB = 1 << (10 * iota)
	MB
	GB
)

func main() {
	var d Day = Friday
	fmt.Println("d =", d, "Friday == 4?", Friday == 4)

	const typed int32 = 42
	var x int = int(typed)
	fmt.Println("x =", x)

	const untyped = 42
	var y int64 = untyped
	var z float64 = untyped
	fmt.Println("y,z =", y, z)

	fmt.Println("KB,MB,GB =", KB, MB, GB)

	// Predict: does this compile without conversion?
	// var ordinary int = Friday
	// Answer: no — Day and int are different types
}
```

#### What happens here

`iota` resets in every `const (` block and grows per line. Defining `Day` as a new type prevents mixing with ordinary `int` without conversion — useful for domain enumerations. Untyped constant `42` can be assigned to both `int64` and `float64`. A typed `int32` constant requires explicit conversion to `int`. The bit shift pattern with `iota` is common for unit sizes: `KB=1024`, `MB=1048576`, `GB=1073741824`. The line `var ordinary int = Friday` does not compile because `Friday` is type `Day`, not `int`.

### Example 4 — Pointer and pass by value

```go
package main

import "fmt"

func addOne(v int) {
	v++
}

func addOnePtr(p *int) {
	*p++
}

func main() {
	n := 10
	addOne(n)
	fmt.Println("after value:", n) // 10

	addOnePtr(&n)
	fmt.Println("after pointer:", n) // 11

	p := new(int)
	fmt.Println("new zero:", *p) // 0
	*p = 5
	fmt.Println("*p =", *p)

	var q *int
	fmt.Println("nil pointer:", q)
	// *q would panic — do not dereference nil

	// Predict: what does this print?
	x := 7
	px := &x
	py := px
	*py = 9
	fmt.Println("x =", x) // ?
}
```

#### What happens here

`addOne` gets a copy of `n`; incrementing does not change the caller — output stays `10`. `addOnePtr` gets a copy of the address; through `*p` it changes the same memory — output becomes `11`. `new(T)` allocates a zero value and returns `*T`. A `nil` pointer exists as the zero value — reading through it causes `panic`. At the end: `px` and `py` hold the same address; `*py = 9` changes `x`, so the output is `x = 9`. There is no moving the pointer to the “next int”; for arrays use slice (next lesson).

Before you wire pointers everywhere, measure: for small types a copy is cheaper and clearer than `nil` risk.

### Example 5 — Mini reference in code: when which type

```go
package main

import "fmt"

type Cents int64
type Status int

const (
	StatusPending Status = iota
	StatusPaid
	StatusFailed
)

func main() {
	var flag bool
	var counter int
	var amount Cents = 1999
	var unixMs int64 = 1_700_000_000_000
	var title string = "Invoice #42"
	var buf []byte = []byte(title)
	var st Status = StatusPending
	var inv *struct{ ID int }

	fmt.Printf("flag=%v counter=%d amount=%d\n", flag, counter, amount)
	fmt.Printf("unixMs=%d title=%q bytes=%d\n", unixMs, title, len(buf))
	fmt.Printf("status=%v inv=%v\n", st, inv)
}
```

#### What happens here

This example joins type-choice heuristics into one small program. `bool` for a flag, `int` for a local counter, `Cents` (`int64`) for money, `int64` for Unix time in milliseconds (fixed width), `string` for UI text, `[]byte` when you need a buffer, typed `Status` + `iota` instead of magic strings, pointer only when you share an optional aggregate. Zero value `inv` is `nil` — “no invoice”, which is a meaningful signal.

### Mini-table: quick choice

| Need | Type | Note |
|------|------|------|
| Yes/no flag | `bool` | zero = `false` |
| Counter, index | `int` | platform-sized |
| Money, DB ID | `int64` / own type | fixed width |
| UI text | `string` | UTF-8 |
| Binary buffer | `[]byte` | details in 01.04 |
| State enum | typed const + `iota` | not string “magic” |
| Sharing mutation | `*T` | with `nil` discipline |

This table is not dogma — it is a starting heuristic until you gain a feel for API boundaries.

Remember also: **type readability in a function signature** often matters more than micro-optimizing width. `func Add(a, b int) int` is clear; moving to `int64` makes sense only when a contract (database, protocol, Unix time in milliseconds) requires it.

## Decision analysis

| Question | Option A | Option B | When to choose |
|----------|----------|----------|----------------|
| Initialization | zero value (`var x T`) | explicit value | A when 0/`false`/`""`/`nil` makes sense; B when “empty” is not a valid state |
| Integer width | `int` | `int64` / `int32` | `int` locally; fixed width at system boundaries |
| Text | `string` | `[]byte` / `[]rune` | `string` for text; `[]byte` for I/O; `[]rune` when cutting by code point |
| Constant | untyped | typed (`const x int32 = 1`) | untyped more flexible; typed when you want a stricter contract |
| Sharing | value `T` | pointer `*T` | `T` while the copy is cheap and clean; `*T` for mutation / large structures |
| Enum | `iota` + type | string constants | `iota` for internal states; string when it goes on the wire/JSON without a map |

Why zero value instead of mandatory initialization everywhere? Because it enables useful default structures (`var sb strings.Builder` later, empty buffer, `false` as “off”). Why no pointer arithmetic? Because it eliminates a whole class of memory bugs; `unsafe` exists for rare cases. Why is `string` not `[]rune` under the hood? UTF-8 is compact and compatible with byte I/O; conversion to `[]rune` is explicit when you count characters.

Choosing `int` vs `int64`: for local counters often `int`; for wire/format where you need a fixed layout (protocols, databases) choose explicit width.

## Trade-offs

- **`int` depends on the platform** — convenient locally, careful in binary protocols and JSON schemas that expect a fixed range.
- **`string` immutability** — safer sharing, but more allocations on frequent concatenations (`strings.Builder` in later lessons).
- **Pointer** — less copying of large values, more lifetime and `nil` risk; easier to share mutations, easier also for mutation to “leak”.
- **`iota`** — short and clear, but not a real enum from other languages (no automatic exhaustiveness check in `switch` without tools).
- **Untyped constants** — powerful, but confuse beginners when they “magically” fit a type.
- **`float64`** — convenient for science and graphics; dangerous for money and comparison with `==`.
- **Typed domain (`type Cents int64`)** — more conversions, but less mixing of units.

## Common mistakes

1. `len(s)` as character count for Unicode text — it counts bytes.
2. Comparing `float64` with `==` for money — use integer cents.
3. `var p *T` then `*p` without a check — `panic` on `nil`.
4. Mixing a `byte` loop (`for i := 0; i < len(s); i++`) with a `rune` loop (`range`).
5. `:=` with a redeclaration error when all variables are already in scope.
6. Implicitly expecting `int32 + int` to work without conversion.
7. Mutating a `string` via an index — does not compile.
8. Cutting `s[:n]` by “characters” without `[]rune` — can cut UTF-8 in the middle of a character.
9. Using `float64` for money in invoices and VAT calculation.
10. Pointer to `int` “just in case” — adds `nil` risk without benefit.

## Idiomatic Go

- Prefer `:=` for local variables with a clear type from the right side.
- Use `var` when you want the zero value or wider scope (e. and a variable filled in a loop / `if`).
- For money and precise quantities — integers (cents), not `float64`.
- Name types (`type Status int`) when values have meaning in the domain.
- Do not use a pointer to `int` without need — only when you share mutations or measure that a copy hurts.
- Comment **why** the type is `int64` if it is not obvious (e.g. Unix timestamp in ms).
- Write `if hot {` instead of `if hot == true {`.
- For textual truncation by characters: `[]rune(s)` then cut, then `string(...)`.
- Export (capital first letter) only for API that other packages need to see.

## Practical scenario

An invoice service stores amounts in `int64` cents. A beginner engineer puts `float64` and after a week “1.00 + 0.10” gives weird results in the PDF — the client sees `1.099999999` instead of `1.10`. The team introduces `type Cents int64` and add/subtract functions that return `Cents`, not raw `int64` everywhere in the code.

For item descriptions they use `string` in UTF-8. When truncating a title to 40 “characters” they first convert to `[]rune` before cutting, not `s[:40]` over bytes — because that would cut in the middle of a multi-byte character and get invalid UTF-8 that blows up in the JSON encoder.

They model invoice status as:

```go
type InvoiceStatus int

const (
	InvoiceDraft InvoiceStatus = iota
	InvoiceSent
	InvoicePaid
	InvoiceVoid
)
```

They pass a pointer to `Invoice` to methods that change status (mutation); amounts they still return by value as `Cents`. Zero value `InvoiceStatus` is `InvoiceDraft` (0) — deliberate: a new invoice starts as draft. The team documents that in a type comment so nobody thinks 0 is “uninitialized”.

Another incident: an endpoint for “character count in a note” used `len(note)`. A user with diacritics (“Žučna čokolada — special”) gets a larger number than expected and the UI truncates wrong. Fix: count `len([]rune(note))` for display, and leave `len(note)` only for buffer / byte limit on the network.

4. Write two functions — by value and by pointer — that “try” to set `score`; prove the difference by printing before and after the call.
5. Try `s[0] = 'A'` on a `string` and explain the compiler message in your own words.
6. Convert `int32` to `int` and back; then try addition without conversion and record the exact error.
7. **Predict-then-run:** what does `fmt.Println(len("šđ"), len([]rune("šđ")))` print? Explain.
8. Make a `const` block with `_ = iota` then `KiB`, `MiB`, `GiB` as in the lesson; print the values and verify they are 1024, 1048576, 1073741824.

## Check questions

1. **What is the zero value for `string`?**  
   Empty string `""` (not `nil`).

2. **Is `byte` the same as `rune`?**  
   No. `byte` is an alias for `uint8`; `rune` is an alias for `int32` (Unicode code point).

3. **Why does `addOne(n)` not change `n`?**  
   The argument is copied (pass by value); the parameter copy is incremented, not the original.

4. **What does `new(int)` return?**  
   A pointer `*int` to an allocated zero value of type `int` (value `0`).

5. **What does `iota` do in a `const` block?**  
   Generates successive integer constants from zero, per line; resets in every new `const (` block.

6. **Why is `len("Ž")` not 1?**  
   Because `len` on a `string` counts UTF-8 bytes; “Ž” takes 2 bytes.

7. **Does Go have pointer arithmetic in safe code?**  
   No. There is no `p+1` / `p++` on a pointer; for sequences use indices / slice.

8. **When to choose `int64` instead of `int`?**  
   When you need fixed width at a system boundary (database, protocol, timestamp), not only a local counter.


When you get stuck on a type, return to the question: do I need a value, an address, or immutable text? The answer almost always chooses among `T`, `*T`, and `string`/`[]byte`.

Zero value is not an excuse for unclear APIs — document what `var x T` means for your type as soon as you export it from a package.

One more check before you go further: open an empty `main`, declare one variable of each basic type without an initializer, and print them. If the result surprises you, return to the zero value table — that is the foundation for slice, map, and `struct` in the next lesson.

## Summary

Primitives in Go have deterministic zero values, strict conversions, and a clear model of `string` as UTF-8 bytes. Constants and `iota` cover enumerations; pointers exist without arithmetic. Everything goes by value — a pointer is the value of an address. `bool` is not a number; `byte` and `rune` are aliases with different intents; `float64` is not for money. The next lesson introduces array, slice, map, and `struct`.
