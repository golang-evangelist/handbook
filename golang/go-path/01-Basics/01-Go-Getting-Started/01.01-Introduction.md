After this lesson you should:

- understand why Go was created and which software engineering problems it solves

- Go 1.22 or newer installed (`go version` must work)

If you do not have Go on the machine yet, a later part of the course (Fundamentals) covers installation in more detail. For this lesson it is enough that the `go` command exists in PATH. Check:

## Problem this lesson solves

Teams that build cloud services, CLI tools, and network daemons often choose between languages that are fast but hard to maintain (C/C++), languages with a large runtime and complexity (Java), and dynamic languages that speed up prototypes but pay a cost in production (Python). Go was created as a response to that trade-off: fast enough, simple enough, concurrent enough, with a predictable build.

Without a clear mental model people struggle to decide *why* they are learning Go, not only *how* to write the syntax. This lesson sets that context before you enter modules, types, and collections.

The second problem is practical: many “Hello World” tutorials stop at `fmt.Println` and do not explain what happens underneath. You then do not understand why `go run` “works” while `go build` leaves a file; why `package main` must exist; why a goroutine is not an OS thread; why the program exits as soon as `main` finishes. Without those mechanisms later lessons feel like a list of syntax instead of a tool for engineering work.

## Mental model

Think of Go as a tool that deliberately narrows the decision space:

1. **One way to format code** (`gofmt`) — less debate about style.
2. **One way to distribute a program** — a statically linked binary file (with the usual exceptions around CGO).
3. **One concurrency model** — goroutine + channel (you learn channel later; here what matters is that there is a cheap way to run thousands of concurrent units of work).
4. **Little language, more library** — the language is small; the power is in the standard library and ecosystem.
5. **Explicitness over magic** — errors are often returned as a value of type `error`; there is no silent exception catching as the default style.

Go is not a “better C” or a “faster Python”. It is a language designed around the *engineering workflow*: fast compilation, readable code, explicit errors, and a runtime that removes the burden of manual memory management while keeping the sense of control typical of compiled languages.

Imagine three layers while you read any Go program:

```text
your source code (.go)
        ↓  compiler + linker (toolchain)
binary file (machine code + Go runtime)
        ↓  OS starts the process
runtime schedules goroutines, GC, I/O
```

When you write `fmt.Println("hello")`, you are not writing a script that an interpreter reads line by line in production. You write source code that becomes a process with the Go runtime inside. That difference explains both the fast start of CLI tools and the feeling of “one file you copy to the server”.

## Mechanism

### History and compatibility

Robert Griesemer, Rob Pike, and Ken Thompson started work on Go at Google around 2007. The public release followed in 2009. The goal was not an academic experiment but practice: large C++/Java codebases, slow compilation, hard concurrency, and dependencies that make deployment painful.

A key decision after that is the **Go 1 compatibility promise**: code written for Go 1 should keep working with future Go 1.x versions, with rare, documented exceptions. That is why the ecosystem does not break on every minor version. Go 1.22+ brings new idioms (e.g. `for i := range n`), but old Go 1 code still compiles.

What does that mean for you as a beginner? You can learn from examples written a few years ago and expect them to compile. New versions add features and fix the runtime, but they do not deliberately break your yesterday’s `package main`. When you see `go 1.22` in `go.mod` (next lesson), that is a declaration of the language level the module expects — not “you must forget old Go”.

A concrete trace through time: a program from 2015 with `package main`, `import "fmt"`, and `fmt.Println("ok")` still passes `go build` on Go 1.22 today. You did not have to change syntax because of a “breaking” minor version. That is a different feeling from ecosystems where every new major framework version breaks the API.

### Static typing

Types are checked at compile time. There is no “silent” addition of a string and a number. That reduces a class of bugs that in dynamic languages only show up at runtime. The cost: you must explicitly convert types when needed.

Predict the result — does this compile?

```go
package main

import "fmt"

func main() {
	var n int = 3
	var s string = "path"
	fmt.Println(n + s)
}
```

**Answer:** no. The compiler rejects `n + s` because `int` and `string` have no shared `+` operation in Go. You get a compile error, not a runtime surprise. That is deliberate: the error is cheaper at build time than in production.

Line by line with concrete values (what the compiler “sees”):

1. `var n int = 3` — variable `n` has type `int`, value `3`.
2. `var s string = "path"` — variable `s` has type `string`, value `"path"`.
3. Expression `n + s` — left side type `int`, right side type `string`. In Go the `+` operator for addition applies to numbers of the same type, and for strings only string + string. Mixing is not allowed.
4. The build stops before any process runs. There is no console output; there is no `"3path"` at runtime.

The fix requires explicit intent, e.g. formatting:

```go
fmt.Println(fmt.Sprintf("%d%s", n, s))
```

Trace with the same values: `Sprintf("%d%s", 3, "path")` produces the string `"3path"`, then `Println` prints that string. Types are aligned because the argument to `Println` is a single `string`.

Or a conversion if it makes sense in the domain (e.g. `strconv.Itoa(n)` then string concatenation). The point of the mechanism: the compiler is the guardian of the type contract, not an “optional warning”.

One more short trace — this *is* valid:

```go
var a int = 2
var b int = 5
fmt.Println(a + b) // 7
```

Here `a` and `b` share type `int`, so `+` has clear semantics: `2 + 5 → 7`. The difference is not “string magic”, but a strict type rule.

### Compiling to a single binary file

`go build` produces an executable for the target platform. Deployment often looks like: copy the binary, run it. No JVM on the server, no “virtualenv + wheel + system library” ritual for a simple CLI. (CGO and dynamic libraries change the story — for starters assume pure Go.)

What exactly happens in the toolchain, simplified:

1. **Parse** — source text becomes an AST (abstract syntax tree).
2. **Type check** — check types, missing imports, undefined names.
3. **Compile** — the package is translated to object code.
4. **Link** — your code + the standard library + the Go runtime are joined into one executable.
5. **Emit** — a file on disk ready for the OS (`hello.exe` on Windows, `hello` on Unix).

Concrete trace for `hello.go` with a single `Println`:

1. The parser sees `package main`, `import "fmt"`, `func main`, the call `fmt.Println`.
2. Type check confirms that `Println` exists as an exported function in package `fmt`, and that a `string` argument matches.
3. Compile translates your `main` and pulls in the needed parts of `fmt` (and dependencies).
4. Link inserts the Go runtime (scheduler, GC, stack management) into the same file.
5. Emit writes e.g. `hello.exe` of several megabytes — most of that is not your one line of code, but the runtime + standard library.

That is why the first success in Go often feels “faster” than in C++ monoliths: less header drama, a clear package graph, caching of build artifacts in the local cache. You do not need to understand every linker step to be productive, but you should know that **there is no line-by-line interpreting** in production — the user runs machine code.

Cross-compile (later in practice): you can build the same source for another OS/arch by setting `GOOS` and `GOARCH`. The mechanism stays the same; the linker’s target platform changes. Mental model example: on Windows you set `GOOS=linux` `GOARCH=amd64` and get a linux binary — without a linux machine for that step (with pure Go, without CGO).

### Garbage collector (GC)

Go has a GC. You do not call `free`. The GC is concurrent and tuned for low latency in typical server scenarios. That does not mean memory “does not matter” — allocations still cost — but you do not manually manage object lifecycles as in C.

What the runtime does in broad strokes:

- allocates objects on the heap when they live longer than the stack or “escape” from a function
- tracks reachability from roots (stack, globals, registers)
- frees unreachable objects in phases that overlap with program execution
- aims for short pauses instead of long “stop the world” periods typical of older GC designs

Concrete trace (simplified):

1. In `main` you write `s := "hello"` — string literal; data lives in the binary / rodata, the reference is local.
2. You create a `slice` or `map` that grows in a loop — allocations go to the heap.
3. When there are no more references to that object (e.g. the variable leaves scope and nobody else holds a pointer), the object becomes a GC candidate.
4. The GC frees it later; you did not call `free(s)`.

For a beginner: you write code, the runtime cleans up. For an engineer: you profile allocations when latency or memory becomes a problem. This lesson gives you the first layer — so you do not expect a manual `malloc`/`free` mental model.

### Goroutine

`go f()` starts function `f` concurrently. A goroutine is **not** an OS thread 1:1; the runtime multiplexes them over a pool of OS threads. That is why you can have thousands of goroutines without thousands of OS threads. That is the language’s concurrency *model* — details (channel, `select`, data race) you learn later.

Important distinction:

| Term | What it is |
|------|------------|
| OS thread | a thread scheduled by the kernel; expensive to create in large numbers |
| goroutine | a lightweight concurrent unit scheduled by the Go scheduler |
| parallelism | truly simultaneous execution on multiple cores |
| concurrency | structuring a program so multiple tasks *interleave* |

Go gives you cheap concurrency. Parallelism depends on `GOMAXPROCS` and hardware. Do not mix those two terms: you can have thousands of goroutines on one core (concurrency without parallelism).

Predict the result — what is printed (approximately)?

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	go fmt.Println("A")
	fmt.Println("B")
	time.Sleep(50 * time.Millisecond)
}
```

**Answer:** you usually see both `A` and `B`, but the order is not guaranteed. `B` often comes out first because the main goroutine continues immediately; `A` arrives from the background one. Without `Sleep`, the process can exit before `A` arrives — when `main` finishes, the program exits. The runtime does not wait for “remaining” goroutines just because they exist.

Line by line with concrete values:

1. The process starts; the runtime creates the main goroutine that executes `main`.
2. `go fmt.Println("A")` — the scheduler gets a new goroutine; its job is a `Println` call with argument `"A"`. It has *not necessarily* printed yet.
3. The main goroutine immediately executes `fmt.Println("B")` — `"B\n"` goes to stdout (often first).
4. `time.Sleep(50 * time.Millisecond)` — the main goroutine sleeps ~50 ms; in that window the scheduler usually gets to run the background goroutine.
5. The background goroutine prints `"A\n"`.
6. `Sleep` finishes, `main` returns, the process exits with status 0.

If you remove step 4, steps 5–6 often collapse into “main already returned” — so `"A"` disappears from the output. That is not a console bug; that is the process life-cycle.

### gofmt

`gofmt` (and `go fmt`) automatically formats code. Teams do not argue about tabs, brace position, and blank lines. The tool is part of the standard tooling, not an optional style linter.

Mechanism: `gofmt` parses valid Go code into an AST, then prints the canonical form. If the code is not syntactically valid, `gofmt` does not “guess” style — it must pass the parser. So formatting is not a substitute for compilation; it is normalization of *correct* code.

Concrete trace: you write

```go
func main(){fmt.Println("x")}
```

After `gofmt -w` you get (approximately):

```go
func main() {
	fmt.Println("x")
}
```

Space after `func main()`, new line after `{`, tab indentation, closing `}` on its own line — that is not your taste, it is the canon. Convention: tabs for indentation. Do not fight that in the editor — configure it to respect `gofmt`.

### Simplicity instead of class inheritance

Go has no inheritance. No classes, no type inheritance like in Java. You have `struct`, method (functions bound to a type via a receiver), and `interface` (later). The mechanism for sharing behavior and fields is embedding and composition — not an “extends” hierarchy.

Why does that matter already in the introduction? Because many people arrive with the mental model “first draw UML class trees”. In Go you first ask: which small `interface` do I need? Which `struct` holds the data? Which function or method does the work? Deep type hierarchies that are hard to refactor are not the default style.

Preview (without deep code yet): instead of `class Dog extends Animal`, in Go you often have `struct Dog` with the fields you need, and functions/methods that work with `Dog`. If multiple types share behavior, you define a small `interface` with those methods — types satisfy it *implicitly*, without an `implements` list. Details later; here remember the design direction.

### Where Go is used — and where it is not the first choice

**Often a good choice:**

- cloud and infrastructure (Kubernetes ecosystem, daemons, control planes)
- network HTTP/gRPC services
- CLI tools (`gh`, parts of the `docker` CLI ecosystem, internal ops tools)
- pipelines, agents, proxies
- tools where you want one binary on a CI/CD agent without “install runtime + dependencies”

**Often not the first choice:**

- mobile UI with a rich native toolkit (the iOS/Android ecosystem is elsewhere)
- desktop GUI with rich widgets (possible, but not a strong point)
- numerical scientific stack as in the Python/NumPy world
- extremely low-level work where you need precise memory layout control and no GC (there C/Rust are more common)

### Short comparison of design decisions

| Decision | Go | C | Java | Python | Rust |
|----------|----|---|------|--------|------|
| Memory | GC | manual | GC | GC | ownership |
| Types | static | static | static | dynamic | static |
| Concurrency | goroutine | thread/API | thread | GIL + async/thread | async/thread + ownership |
| Inheritance | none (embedding + composition) | no classes | classes | classes | trait/impl |
| Build artifact | binary | binary | bytecode+JVM | interpreter/venv | binary |
| Focus | simplicity + tooling | control | platform + OOP | writing speed | memory safety |

No column is the “winner”. Go chooses the middle: less control than Rust/C, more predictability than Python, less ceremony than Java.

### Anatomy of Hello World — line by line

Minimal program:

```go
package main

import "fmt"

func main() {
	fmt.Println("Hello, World")
}
```

We go in order with concrete values:

1. **`package main`** — every `.go` file belongs to exactly one package. The name `main` is not decoration: for an executable program the toolchain looks for package `main` as the entry. A library package is named differently (`fmt`, `os`, your `pricing`).
2. **Blank line** — style; `gofmt` keeps it between `package` and `import`.
3. **`import "fmt"`** — you explicitly import a package from the standard library. The string `"fmt"` is the import path. Without this `fmt.Println` does not exist in this file.
4. **`func main()`** — the process entry function. No parameters, no return values. The OS/runtime starts the process, the Go runtime initializes, then calls `main`.
5. **`fmt.Println("Hello, World")`** — call to the exported function `Println` from package `fmt`. The argument is a string literal with value `"Hello, World"` (12 characters + the internal string representation in the runtime). The function writes those bytes plus a newline (`\n`) to standard output. The `Println` signature returns `(n int, err error)` — number of bytes written and a possible `error`; here we ignore the return values (allowed in an introduction; in production you often check I/O errors).
6. **End of `main`** — the function returns; the process ends with status 0 (success), unless you called `os.Exit` or an uncaught `panic` occurred.

What the compiler does with this file on `go run hello.go` — step-by-step trace:

1. Reads `hello.go` from disk.
2. Checks that it is `package main` and that `func main` exists with the correct signature.
3. Checks that `fmt` is used (unused import = error: e.g. `import "os"` without `os.` fails the build).
4. Compiles to a temporary binary (the path is in the tooling temp directory — you usually do not see it).
5. Runs that file as a child process; the child prints `Hello, World` then exits with code 0.
6. The parent (`go run`) deletes the temporary artifact after completion.

If instead of `"Hello, World"` you put `"Hello"`, the only change in the trace is the literal content and the bytes on stdout; the rest of the mechanism (`package`, `import`, `main`, temporary build) stays the same.

### Life cycle: `go run` versus `go build`

- `go run .` (or `go run file.go`) — compiles to a temporary binary, runs it, then discards it. Great for learning and quick checks.
- `go build` — leaves a binary in the current directory (or via `-o` on the path you specify). That is what you deploy or package.

Both use the same compiler. The difference is whether you want a lasting artifact.

Predict the result — after these commands, which file remains on disk?

```text
go run hello.go
go build -o hello.exe hello.go
```

**Answer:** after `go run` there is no lasting `hello.exe` (the temporary one was deleted). After `go build -o hello.exe` the file `hello.exe` remains and you can run it again without compiling: `.\hello.exe`.

Trace with concrete file names:

1. `go run hello.go` — the toolchain creates e.g. a temporary `exe` in a temp folder, runs it, deletes it. In your folder only `hello.go` still exists.
2. `go build -o hello.exe hello.go` — the same source, but emit goes to `hello.exe` next to `hello.go`.
3. `.\hello.exe` — the OS loads `hello.exe`; the Go toolchain is no longer needed for that run.
4. Delete `hello.exe` and try `.\hello.exe` again — it fails; source `hello.go` by itself is not an executable.

Predict the result — what does this program print, and does it compile?

```go
package main

import "fmt"

func main() {
	var x int
	var s string
	var ok bool
	fmt.Println(x, s, ok)
}
```

**Answer:** it compiles. The output is `0` then an empty string (looks like two spaces between zero and `false` visually depending on the console) then `false` — more precisely: `Println` separates arguments with a space, so you see `0  false` because `s` is the zero value `""` (nothing between the spaces). Concretely: `x == 0`, `s == ""`, `ok == false`. There is no “garbage” from memory; zero value is part of the language.

### The standard library as part of the design

Go sells itself as a “small language”, but the standard library covers HTTP client/server, JSON, crypto primitives, archives, templates, testing, benchmarking. Many CLIs and internal services live for months on just `net/http`, `encoding/json`, and a `database/sql` driver. Third parties come when the standard library does not cover the domain (e.g. specialized protocols), not as the default first step.

Security note (defensive): the standard library gives you good primitives (`crypto/*`, TLS in `net/http`), but *you* choose what you do with input. Never build a shell command by concatenating an untrusted string; validate paths; do not log secrets. The language does not replace discipline around confidential data.

### Culture of explicit errors (preview)

In idiomatic Go, functions often return `(T, error)`. You will not master that pattern in this lesson, but you should know it is *deliberate*: there are no silent exceptions that cut the stack except `panic` (which is not for ordinary errors). That affects how you read code — more `if err != nil`, less hidden control flow. Later lessons practice it.

Concrete trace (preview, without a deep API):

```go
n, err := fmt.Println("hello")
if err != nil {
	// here you would handle an I/O problem
	_ = n
}
```

`Println` returns the number of bytes (`n`) and an `error` (`err`). If everything is fine, `err == nil`. If stdout cannot accept the data, `err != nil`. You *see* the failure branch in the code — it is not hidden in a catch block far from the call.

`panic` and `recover` exist, but they are not a substitute for `error`. `defer` (more detail later) ties cleanup to leaving a function. For now remember: ordinary failure = a value of type `error`; `panic` = “the program is in an inconsistent state”.

### Zero value (preview)

Every type in Go has a zero value — the default value of a variable that is declared but not explicitly initialized (`0`, `""`, `nil`, `false`, empty `struct`). That is part of the language, not “undefined behavior”. Details in the types lesson; here what matters is that you do not expect C “garbage” in uninitialized local variables.

Trace with concrete types:

| Declaration | Zero value | Example print |
|-------------|------------|---------------|
| `var n int` | `0` | `0` |
| `var s string` | `""` | (empty) |
| `var ok bool` | `false` | `false` |
| `var p *int` | `nil` | `<nil>` |
| `var t struct{}` | empty `struct` | `{}` |

That is why the earlier “predict the result” with `var x int` / `var s string` / `var ok bool` matters: the compiler does not require you to “set” them before reading — the zero value is already there.

### Exported and unexported (preview)

Identifiers that start with a capital letter are exported from the package (`Println`); lowercase are unexported — visible only inside the same package. The compiler enforces that at the package boundary. That is why `fmt.println` from your code does not work: lowercase `println` is not the exported API.

Trace:

1. In package `fmt` there is the exported name `Println` — your `main` may call it as `fmt.Println`.
2. If inside there were something like `printSomething` (lowercase first letter), your other package could not call it.
3. The error is not “file not found” — the error is visibility at the package boundary.

The same rules apply to types, constants, and fields in a `struct`: `Name` is exported, `name` is not. Later lessons practice this when you share code across packages.

## Rules and syntax

1. Every `.go` file belongs to exactly one package (`package name`).
2. An executable program must have `package main` and `func main()` with no parameters and no return values.
3. Imports are listed explicitly; an unused import is a compile error.
4. Statements do not require a trailing `;` — the compiler inserts them by rules (that is why a new line after `{` is not decoration, but part of the grammar).
5. Identifiers that start with a capital letter are exported from the package (`Println`); lowercase are unexported (`println` from another package you do not see).
6. `gofmt` expects tabs for indentation; do not fight that.
7. The file name is not the same as the package name — a package is a logical unit, files are a physical split.
8. `go f()` starts `f` in a new goroutine; when `main` finishes, the process exits without waiting for other goroutines (unless you explicitly synchronize them).
9. The type `error` is an ordinary `interface` contract of the language for failure; do not mix it with `panic`.
10. Valid Go 1.22+ code in this course assumes a module-aware toolchain; a single file can work with `go run`, but real projects use modules (next lesson).

## Examples

### Example 1 — Hello World with `go run`

Save as `hello.go`:

```go
package main

import "fmt"

func main() {
	fmt.Println("Hello, Go Path - Zero to Gopher")
}
```

Run:

```text
go run hello.go
```

Expected output:

```text
Hello, Go Path - Zero to Gopher
```

#### What happens here

The compiler reads `package main`, finds `func main`, links `fmt.Println`, builds a temporary executable and runs it. The process writes one line to standard output and finishes with status 0.

Concrete value flow, step by step:

1. Source file `hello.go` contains the literal `"Hello, Go Path - Zero to Gopher"` (characters H-e-l-l-o-,- -G-o- -P-a-t-h).
2. The toolchain compiles package `main`; the literal enters the binary as data.
3. The runtime calls `main`; the main goroutine’s stack enters the function body.
4. `Println` receives that string; internally it sends it to the stdout writer, then adds `\n`.
5. The OS (console / terminal) shows the line `Hello, Go Path - Zero to Gopher`.
6. `Println` returns `(n, err)` — e.g. `n` equal to the number of bytes written, `err == nil` in the normal case; we ignore them.
7. `main` returns → exit code 0. The temporary binary from `go run` is deleted.

There is no `go.mod` in this minimal example — for one file `go run` works, but real projects use modules (next lesson). If you later add `go.mod` in the same directory, you can still `go run hello.go`, but organization moves to package paths.

If you change the literal to `"Hi"`, the same mechanism applies: only the content of steps 1 and 5 changes. If you delete `import "fmt"` but leave `fmt.Println`, the build fails at type check / undeclared name — the process never starts.

### Example 2 — Multiple imports and short formatting

```go
package main

import (
	"fmt"
	"os"
	"runtime"
)

func main() {
	fmt.Printf("Go runtime version: %s\n", runtime.Version())
	fmt.Printf("OS/Arch: %s/%s\n", runtime.GOOS, runtime.GOARCH)
	fmt.Printf("PID: %d\n", os.Getpid())
}
```

Run:

```text
go run info.go
```

Example output (values depend on the machine):

```text
Go runtime version: go1.22.5
OS/Arch: windows/amd64
PID: 18432
```

#### What happens here

The `import (...)` block groups dependencies. Three packages:

- `fmt` — formatted I/O
- `runtime` — data about the Go runtime itself and the target platform (`Version`, `GOOS`, `GOARCH` are exported identifiers)
- `os` — bridge to the operating system; `Getpid` asks for the process identifier

`Printf` uses verbs (`%s`, `%d`) similar to C `printf`, but for basic types the compiler/vet often catch mismatches. Line by line in `main` with example Windows values:

1. `runtime.Version()` returns the version string built into the toolchain/runtime — e.g. `"go1.22.5"`. `Printf` replaces `%s` with that string → line `Go runtime version: go1.22.5`.
2. `runtime.GOOS` is `"windows"`, `runtime.GOARCH` is `"amd64"` (constants known at build time for that platform). Format `"%s/%s"` yields `windows/amd64`.
3. `os.Getpid()` asks the OS for the current process PID — e.g. `18432` (typically `int`). Verb `%d` formats an integer.
4. Each `Printf` sends one formatted line to stdout and ends it with `\n` because `\n` is in the format string.

Why three packages instead of one? Because Go forces explicit boundaries: I/O formatting (`fmt`), runtime introspection (`runtime`), and OS calls (`os`) are not symbols available without `import`. That makes the dependency graph readable — you open a file and immediately see what it pulls.

This program shows that “Hello World” is not magic — it is an ordinary process that calls the standard library and reads its own runtime. The same three lines on a Linux machine may give `linux/amd64` and another PID; the mechanism is identical, only the values the runtime/OS return change.

Predict: if you delete `import "os"` but leave `os.Getpid()`, what happens?

**Answer:** compile error — undefined name `os`. Go does not import packages implicitly.

### Example 3 — `go build` and a lasting binary

```go
package main

import (
	"fmt"
	"os"
)

func main() {
	name := "Go Path - Zero to Gopher"
	if len(os.Args) > 1 {
		name = os.Args[1]
	}
	fmt.Printf("Hello, %s\n", name)
}
```

Build and run (Windows example):

```text
go build -o hello.exe .
.\hello.exe Marko
```

On Unix:

```text
go build -o hello .
./hello Marko
```

Expected output for `.\hello.exe Marko`:

```text
Hello, Marko
```

Without arguments:

```text
Hello, Go Path - Zero to Gopher
```

#### What happens here

`go build` produces an executable you can copy to another machine of the same OS/arch combination (without the Go tooling).

Line by line with concrete values when you run `.\hello.exe Marko`:

1. The OS starts the process; the Go runtime fills `os.Args` from the arguments the kernel passed.
2. Assume `os.Args == []string{"hello.exe", "Marko"}` (on some systems `[0]` is the full path — e.g. `D:\...\hello.exe`).
3. `os.Args[0]` is the program name/path — we do not use it as the greeting.
4. `len(os.Args)` is `2` → condition `len(os.Args) > 1` is `true`.
5. `os.Args[1]` is `"Marko"`; assignment `name = os.Args[1]` changes `name` from the initial `"Go Path - Zero to Gopher"` to `"Marko"`.
6. `Printf("Hello, %s\n", name)` replaces `%s` with `"Marko"` → stdout gets `Hello, Marko\n`.

Trace without arguments (`.\hello.exe`):

1. `os.Args == []string{"hello.exe"}` (or with a full path in `[0]`).
2. `len(os.Args) == 1` → `> 1` is `false`.
3. The `if` branch does not run; `name` stays `"Go Path - Zero to Gopher"` (value from the short declaration `:=`, not the zero value — you set it explicitly).
4. Output: `Hello, Go Path - Zero to Gopher`.

Note on zero value vs initial value: `name := "Go Path - Zero to Gopher"` is *not* the zero value; the zero value for `string` would be `""`. Here you choose a sensible default before looking at CLI input.

This is the skeleton of a CLI tool: argument parsing later you replace with the `flag` package, but the entry point remains `main`. Defensively: do not blindly trust the length and content of `os.Args` in production — check, validate, do not inject raw arguments into a shell.

### Example 4 — Concurrency in one sentence (goroutine)

```go
package main

import (
	"fmt"
	"time"
)

func say(msg string) {
	for i := 1; i <= 3; i++ {
		fmt.Println(msg, i)
		time.Sleep(50 * time.Millisecond)
	}
}

func main() {
	go say("background")
	say("main")
	time.Sleep(200 * time.Millisecond)
}
```

One possible output (order is not guaranteed):

```text
main 1
background 1
main 2
background 2
main 3
background 3
```

#### What happens here

`go say("background")` starts a concurrent call: the scheduler gets a new goroutine with argument `msg == "background"`. The main goroutine continues with `say("main")` — that is an ordinary synchronous call on the current goroutine.

Inside `say`, a trace with concrete values (one possible chronology):

1. t≈0 — background goroutine created; main enters `say("main")` with `msg == "main"`.
2. Main prints `main 1` (`i == 1`), sleeps 50 ms.
3. During that sleep the scheduler often lets the background run: `background 1` (`msg == "background"`, `i == 1`), then it also sleeps 50 ms.
4. Main wakes, prints `main 2`, sleeps; background prints `background 2`; same for `i == 3`.
5. `say("main")` returns after the third sleep (~150 ms of total sleep in the loop, plus work).
6. `time.Sleep(200 * time.Millisecond)` at the end of `main` gives a spare window for the background goroutine to finish its third round if it is behind.
7. `main` returns; the process exits.

Why is order not a contract? Because `Println` + scheduler + OS scheduling are not deterministic relative to your source line order. You may see two “main” in a row then “background” — the program is still correct.

Without the short `Sleep` at the end of `main`, the process could exit before the background goroutine finishes — when `main` finishes, the program exits. This is not a production pattern (later you use `sync.WaitGroup` or a channel); the goal is to see that concurrency is syntactically cheap. Messages interleave — order is not guaranteed.

Predict: remove the last `time.Sleep(200 * time.Millisecond)`. Does `background 3` always print?

**Answer:** no. You often see only part of the background messages or none, because `main` finishes soon after `say("main")` and the runtime kills the process. That is why production code synchronizes completion explicitly.

## Decision analysis

| Question | Typical alternative | Go choice | Why |
|----------|---------------------|-----------|-----|
| How to check types? | runtime (dynamic languages) | compiler (static) | earlier bug catching in services |
| How to share memory? | manual / ownership | GC | faster infrastructure development, acceptable latency |
| How to distribute work? | OS thread / async framework | goroutine + channel | cheap concurrency, one model |
| How to share type behavior? | class inheritance | embedding + composition + small `interface` | less brittle hierarchies |
| How to format code? | linter rules / debates | `gofmt` | less noise in PRs |
| How to distribute? | VM + classpath / venv | one binary file | simple CLI/service deploy |

Why does Go choose static typing and GC at the same time? Because the target audience is infrastructure and service engineers: they want checking at build time, but do not want every request to handle `malloc`/`free`. Why no class inheritance? Because deep hierarchies in large codebases become brittle; composition and small `interface`s scale better in Google’s (and similar) environments. Why `gofmt`? Because style PRs spend time without adding value.

When you choose Go for a new service, you ask: do we need simple binary deployment, a good standard networking library, and a team that can quickly read other people’s code? If yes — Go enters the shortlist. If you need soft real-time without GC pauses or a rich GUI toolkit — you look further.

## Trade-offs

- **Language simplicity** means fewer expressive abstractions (no generics until Go 1.18; they exist now, but are restrained). Less “magic”, more explicit code.
- **GC** removes a whole class of bugs, but introduces pause characteristics and a less predictable footprint than manual memory.
- **One binary file** simplifies deploy, but binaries are not as tiny as a script; cross-compile is excellent, but you must target the right `GOOS`/`GOARCH`.
- **Goroutines** are cheap, but data races still exist — the tool `go test -race` exists because the model does not automatically eliminate shared mutable state.
- **Compatibility promise** slows API breakage, which is good for the ecosystem, but means some design mistakes stay for a long time (zero value behavior, `nil` and `interface` traps — topics of later lessons).
- **Explicit `error`** makes code longer to read for beginners, but makes control flow visible in review.

## Common mistakes

1. **Mixing `go run` and a “project”** — `go run` is not a substitute for modules and tests; use it for quick attempts.
2. **Expecting `main` to return `error`** — it does not; CLI errors often go to `os.Exit` or log + return from `main` after handling.
3. **Unused import / variable** — in Go that is a compile error, not a warning.
4. **Running without `package main`** — a library compiles, but there is no entry point for a binary.
5. **Assuming Go is “like Python with types”** — the mental model of the runtime, packages, and zero values is different.
6. **Forgetting that the program exits with the end of `main`** — background goroutines do not keep the process alive by themselves.
7. **Mixing goroutine and OS thread** — a goroutine is a lightweight unit of the Go scheduler, not a 1:1 mapping to a kernel thread.
8. **Looking for class inheritance** — Go has no inheritance; learn embedding and composition instead of `extends`.
9. **Ignoring `gofmt`** — manual style creates noise; let the tool format before commit.
10. **Relying on print order from multiple goroutines** — without synchronization order is not a contract.

## Idiomatic Go

- Write code that `gofmt` does not have to aggressively “fix” — let the tool format.
- Keep `main` thin: setup, library call, error handling.
- Prefer the standard library until you prove you need a third party.
- Do not introduce class hierarchies “out of habit” from Java/C# — use `struct`, functions, and methods.
- Package names short, lowercase, without underscores (`fmt`, `http`, not `utils_helpers`).
- Comments explain *why*, not *what* an obvious line does.
- For failure use `error`; leave `panic` for situations with no sensible continuation.
- Learn concurrency slowly: first understand the `main` life-cycle, then channel, then `select`.

## Practical scenario

A platform team needs a small internal CLI that checks whether config files are valid before deploy. A Python script works, but dependencies on CI agents break, and the “one file for ops” requirement keeps failing. An engineer writes a Go program: `package main`, reads files, validates, exits with code 0/1. `go build` on CI produces a binary for linux/amd64. The agent only downloads the artifact and runs it — no pip, no virtualenv.

Later the same team adds parallel checking of multiple files via goroutines because the check is I/O-bound. First they must learn the intro lesson: without `WaitGroup` or a channel, `main` would “eat” the results. The language was chosen for the deploy model and concurrency, not for “trendiness”.

Security layer in the same tool: config paths are not passed through a shell; files are opened via `os.Open` with error checking; secrets from config are not printed in logs. Go gives you the tool — discipline remains yours.

## Check questions

1. **What is the Go 1 compatibility promise?**  
   A commitment that Go 1.x programs remain compatible with future Go 1 releases, with rare documented exceptions.

2. **Why does `package main` exist separately from `func main`?**  
   `package main` marks an executable package; `func main` is the entry function. Library packages are not `main` and do not have that entry point.

3. **What is the difference between `go run` and `go build`?**  
   `go run` compiles and immediately runs (temporary artifact); `go build` leaves a lasting binary.

4. **Why does Go not have class inheritance like Java?**  
   The design favors embedding, composition, and small `interface`s for simpler maintenance of large codebases. Go has no type inheritance in the OOP sense.

5. **Is a goroutine the same as an OS thread?**  
   No. A goroutine is a lightweight concurrent unit that the Go runtime multiplexes over OS threads.

6. **What happens when `main` finishes while other goroutines are still running?**  
   The process exits; remaining goroutines are not waited for automatically.

7. **What does it mean that an identifier is exported?**  
   It starts with a capital letter and is visible from other packages (e.g. `Println`).

8. **Why does an unused import fail compilation?**  
   Because Go forces a clean dependency graph; a dead import is an error, not a warning.

## Summary

Go is a compiled, statically typed language with a GC, cheap goroutines, mandatory formatting, and the Go 1 compatibility promise. It was created to speed up builds and simplify engineering work on network services and tools. Go has no inheritance — instead it uses embedding and composition. Hello World shows package, import, and `main`. `go run` serves the fast learning loop; `go build` serves the artifact. The compiler checks types before runtime; the runtime schedules goroutines and runs GC. The next step is a real project with modules.
