# 01.02 Starting a Project

> **Go Path - Zero to Gopher** / **01 Basics → Go: Getting Started** / Lesson 01.02

## Lesson goals

After this lesson you should:

- initialize a Go module with `go mod init` and understand the module path
- read and interpret `go.mod` (and know what `go.sum` is for)
- distinguish the old GOPATH mode from module-aware mode
- organize a small project with `cmd/` and `internal/`
- use `go run`, `go build`, `gofmt`, and `go vet` in the everyday workflow
- correctly import a package via module path + relative directory path
- understand the visibility rule for `internal/` and the exported / unexported identifier difference inside a package

## Prerequisite

- Go 1.22+ installed
- completed lesson 01.01 (you know `package main`, `go run`, `go build`, a goroutine is not an OS thread)
- a terminal in an empty working directory where you may create files

Check that you are in an empty folder before the exercises — `go mod init` writes `go.mod` in the current directory.

## Problem this lesson solves

A single `hello.go` is not a project. As soon as you add a second package, a dependency from GitHub, or want a reproducible build on CI, you need a **module**: a name, a language version, a list of requirements. Without that Go does not know where to pull packages from or how to cache them.

Historically there was GOPATH: all projects in one directory tree, imports by path under `src`. That broke local experiments and forced unnatural paths. Modules (from Go 1.11, default from 1.16) solve it: the project lives where you want, `go.mod` defines the root, dependency versions are explicit.

The second problem this lesson solves is organization. Beginners often put everything in one `main.go` at the root, then after a month do not know what is CLI, what is library, what another repo may import. The `cmd/` and `internal/` conventions are not compiler magic — they are disciplines that prevent chaos before it starts.

## Mental model

A module is a **unit of versioning and a dependency boundary**. A package is a **unit of compilation and visibility** (exported identifiers). A file is only a physical piece of a package.

```text
module (go.mod)
  └── package a (directory)
        └── file1.go, file2.go
  └── package b
        └── ...
```

Three questions you always separate:

1. **Where is the module root?** — the directory with `go.mod`.
2. **Where is the package?** — one directory; all `.go` files in it share the same `package` name.
3. **How is the package imported?** — string = module path + path from the root to that directory.

The `module path` (e.g. `github.com/devlore/inventory`) does not have to exist on the network while you develop locally — it is a **namespace name** by which other code imports your packages (`import "github.com/devlore/inventory/internal/store"`). For exercises you may use `example.com/school/todo` or `my.local/demo`.

`internal/` is a special directory: code under it can be imported only by the parent tree of the module. That is a path-level encapsulation mechanism, not a language one.

`cmd/` is a convention (not a compiler rule): each subdirectory is one CLI (`cmd/server`, `cmd/migrate`).

Imagine the relationship like this:

```text
         go.mod  ←  “my name is example.com/shop”
            |
   +--------+---------+
   |                  |
 cmd/shop          internal/pricing
 package main       package pricing
 (CLI entry)        (library, hidden outside)
```

`main` imports `example.com/shop/internal/pricing`. An external module **cannot** import that same path — the compiler rejects it. Inside package `pricing`, the name `Discount` (capital letter) is exported; `helper` (lowercase) would be unexported.

## Mechanism

### `go mod init` — what it exactly does

```text
mkdir demo && cd demo
go mod init example.com/demo
```

Creates `go.mod`:

```go
module example.com/demo

go 1.22
```

Line by line:

- `module example.com/demo` — records the module path. From now on that is the prefix of all import paths inside this tree.
- `go 1.22` — the language version the module expects. It affects available language features (e.g. idioms from Go 1.22) and default toolchain behavior. It is not “install exactly 1.22” if you have newer — a newer toolchain can build an older language level, under compatibility rules.

What does *not* happen on `go mod init`:

- it does not create `main.go`
- it does not download dependencies
- it does not make `cmd/` or `internal/`
- it does not write `go.sum` (that file appears when requirements / checksums appear)

That is a deliberately narrow step: mark the root, then add code.

### Module path as a contract, not as a URL obligation

Predict: does `go mod init example.com/demo` succeed only if `example.com/demo` exists on the internet?

**Answer:** no. The module path is an identifier. Local development works without a network. The network becomes important when `go get` / build pulls *external* modules, or when you publish your code for others to import. So for exercises choose a stable path (`example.com/...`) and later align it with the real remote URL if you publish.

A bad path choice (e.g. `temp` or `test`) later breaks import strings when the project grows. Choose a name as if it will live for years.

### Adding code — package pattern, not a “script”

```text
mkdir -p cmd/demo
```

`cmd/demo/main.go` with `package main`. Run from the module root:

```text
go run ./cmd/demo
```

The dot-slash path is a **package pattern** relative to the module, not a “script”. The toolchain:

1. finds `go.mod` upward from the current directory
2. resolves `./cmd/demo` as a package in that directory
3. checks that it is `package main` and that `func main` exists
4. compiles that package + dependencies
5. runs a temporary binary

Difference from `go run main.go` in lesson 01.01: here you target a *package* (directory), which scales when you have multiple files in the same `main` package.

### Anatomy of an import path — with concrete values

Let:

```text
module example.com/shop
```

and file:

```text
internal/pricing/price.go   →  package pricing
```

The import in `cmd/shop/main.go` must be:

```go
import "example.com/shop/internal/pricing"
```

Break the string apart:

| Part | Value | Meaning |
|------|-------|---------|
| module path | `example.com/shop` | from `go.mod` |
| relative path | `internal/pricing` | from root to the package directory |
| name in code | `pricing` | default identifier = package name |

The call `pricing.Discount(...)` uses the package name, not the directory name as a separate language — they usually match by convention.

Predict: does `import "./internal/pricing"` work?

**Answer:** no in module-aware mode. Relative imports are not allowed. The compiler wants a full path tied to the module path. That prevents “import the neighbor from disk” dependencies that fall apart as soon as you move the folder.

### `go build` — which `main`, which artifact

```text
go build -o bin/demo ./cmd/demo
```

Compiles the package and its dependencies into one binary. The path `./cmd/demo` chooses which `main` package enters. If in the module you have two CLIs (`cmd/shop` and `cmd/shopctl`), you build each explicitly — do not expect one `go build` to “guess” both entries into one file.

What the linker includes:

- your `main` package
- all imported packages from the same module
- the standard library as needed
- the Go runtime

The result is one executable for the current `GOOS`/`GOARCH` (unless you cross-compile).

### `gofmt` / `go fmt`

```text
gofmt -w .
go fmt ./...
```

`gofmt -w` writes formatted files. `go fmt ./...` walks all packages under the current one.

Mechanism: parser → AST → canonical printer. `gofmt` does not change semantics. It does not fix a wrong `Printf` verb, does not add `error` checks, does not write tests. That is why `go vet` and `go test` exist.

Usual import layout after `gofmt`:

1. standard library
2. blank line
3. other packages (your module, third party)

That is not a language law, but it is the de facto ecosystem style — `gofmt` + `goimports` (external tool) often maintain it.

### `go vet`

```text
go vet ./...
```

Static checks that the compiler does not always treat as errors, but that often are bugs: suspicious `Printf` verbs, unreachable code, mistakes in `copy`/`append` patterns, etc. Vet is not a substitute for tests.

Predict the result — what does `go build` do, and what does `go vet`?

```go
fmt.Printf("price=%d discount=%s\n", 100)
```

**Answer:** `go build` often *passes* (the number of `Printf` arguments is not always a hard compiler error in the same sense as types). `go vet` reports a mismatch of verbs and arguments. That is why the loop `gofmt` → `go vet` → `go test` → `go build` is not ceremony — it catches different classes of problems.

### `go.sum` and `go mod tidy` (what you should know from day one)

When you add an external dependency (`go get example.com/something@v1.2.3`), the toolchain writes `require` into `go.mod` and checksum lines into `go.sum`. `go.sum` protects against unexpected content changes of the same version tag (supply-chain discipline).

`go mod tidy`:

- adds missing requirements for code you actually import
- removes requirements the code no longer uses
- maintains `go.sum`

For this lesson you may not yet have external dependencies — you still need to know that `go.mod` + `go.sum` go into version control together, and local binaries (`bin/`) do not.

### GOPATH versus modules

| | GOPATH era | Module |
|---|------------|--------|
| Where code lives | `$GOPATH/src/...` | anywhere with `go.mod` |
| Dependency versions | often “what is on disk” | `require` + `go.sum` |
| `go get` | changes the global workspace | changes the module |
| Default today | legacy | module-aware |

`GOPATH` still exists (e.g. for cache), but **you do not put projects in GOPATH to make them work**. `GOMODCACHE` holds downloaded modules. If you see a tutorial that starts with “put code in `~/go/src/...`”, that is history — do not do new projects that way.

### The `internal/` rule — step by step

The compiler looks at the import path. If the path contains an `/internal/` element (or starts with `internal/` right after the module root in the tree sense), import is allowed only from the parent tree of that `internal` directory within the same module (simplified: from your module, not from outside).

Example:

```text
example.com/shop/internal/pricing   ← OK from example.com/shop/...
example.com/other/internal/x        ← another module CANNOT import pricing from shop
```

That is not the same as an unexported identifier:

| Mechanism | What it protects | Boundary |
|-----------|------------------|----------|
| lowercase (`helper`) | a name inside the package | package |
| `internal/` directory | the whole package from external modules | module tree |

You can have an exported `Discount` inside `internal/pricing` — exported for *your* module, still invisible to *another* module.

### Minimal workspace example — compilation flow

```text
example.com/demo/
  go.mod
  cmd/demo/main.go
  internal/greeter/greeter.go
```

`main` imports `example.com/demo/internal/greeter`. When you run `go run ./cmd/demo`:

1. `go.mod` is loaded → module path `example.com/demo`
2. `cmd/demo` is parsed → `package main`
3. import `.../internal/greeter` is seen → that package is loaded
4. type-check links calls (e.g. `greeter.Hello("Marko")`)
5. compilation + link + temporary run

If greeter exports `Hello` and you call `greeter.hello`, the compiler reports that `hello` is unexported — the error is at the package boundary, before runtime.

### Multiple `main` packages in one module

One module may have multiple entries:

```text
cmd/shop/main.go      → binary shop
cmd/shopctl/main.go   → binary shopctl
```

Both can import the same `internal/pricing`. You do not copy business logic. You do not make two modules just because you have two commands — until versions truly live separately, one module is simpler.

Predict: what does `go build ./...` do in a module with two `main` packages?

**Answer:** it tries to build all matching packages. For multiple `main` that can produce multiple binaries in the current directory (named after the directory) or be awkward in scripts — that is why CI often explicitly does `go build -o dist/shop ./cmd/shop` and the same for the other entry. Explicit paths make intent clear.

### Package name versus directory name

Discipline rule:

- directory `internal/pricing` → `package pricing`
- directory `cmd/shop` → `package main` (exception: all CLI entries are `main`)

The package name in the file does not have to be bit-for-bit the folder name, but a mismatch confuses readers. The compiler requires that *all files in the same directory* have the same `package` name (except `package x_test` for external tests — later).

### What the compiler does with `go.mod` during an error

If you write a wrong import `example.com/shop/internal/pricng` (typo):

1. the toolchain looks for that package in the module and in the dependency cache
2. does not find it
3. reports an error like “cannot find package” / “no required module provides package”

Read the message from the module path downward — often it is a typo or a forgotten `go get`. Do not “fix” it with a relative import.

### Security angle at project start

Defensive habits from the first `cmd/`:

- do not commit secrets to the repo (tokens, `.env` with production credentials)
- do not log `os.Args` if they may contain secrets
- validate CLI inputs before you use them as file paths
- commit `go.sum` — that is part of the integrity story, not noise to “clean”

The Go toolchain helps with reproducibility; you still choose what enters the source code.

### Daily cycle (habit mechanism)

```text
code change
   → gofmt -w .
   → go vet ./...
   → go test ./...
   → go run ./cmd/...   (or go build)
```

Each step catches a different class of problems: style, suspicious constructs, regressions, behavior. Skipping `vet` because “build passes” is a common cause of embarrassing `Printf` bugs in a PR.

## Rules and syntax

1. At the module root there is exactly one `go.mod` (a workspace with multiple `go.mod` is an advanced `go.work` topic).
2. The package name in the file (`package greeter`) usually matches the directory name; `main` is the exception.
3. The import path is `modulePath` + the relative path of the package directory.
4. All files in the same directory must have the same `package` name (except `_test` packages).
5. Unused imports and local variables — compile error.
6. An `internal` segment in the path activates the visibility rule between modules.
7. Do not edit `go.mod` by hand without need — `go get`, `go mod tidy` maintain requirements.
8. Relative imports (`./foo`) are not allowed in module mode.
9. Exported identifiers start with a capital letter; unexported with lowercase — the boundary is the package, not the file.
10. `go run ./path` and `go build ./path` target a package, not “any file outside the package model” when you work on a real project.

## Examples

### Example 1 — Init, main, run

`go.mod`:

```go
module example.com/shop

go 1.22
```

`cmd/shop/main.go`:

```go
package main

import "fmt"

func main() {
	fmt.Println("shop CLI ready")
}
```

Commands:

```text
go mod init example.com/shop
mkdir -p cmd/shop
# write main.go
go run ./cmd/shop
go build -o bin/shop ./cmd/shop
```

Expected `go run` output:

```text
shop CLI ready
```

#### What happens here

`go mod init` records the module name in `go.mod`. Until `cmd/shop/main.go` exists, there is nothing to run — init only sets the root.

`go run ./cmd/shop` then:

1. finds `go.mod` at the root (`example.com/shop`)
2. loads the package in `cmd/shop`
3. sees `package main` and `func main`
4. compiles (here only standard `fmt`)
5. runs the temporary artifact
6. `Println` writes one line; `main` returns; exit 0

`go build -o bin/shop` does the same steps 1–4, but leaves a lasting file `bin/shop` (or `bin/shop.exe` on Windows if you name it that way). The `bin/` directory is not magic — just organization; it is often in `.gitignore`.

Predict: if you run `go run ./cmd/shop` from the *wrong* directory where there is no `go.mod` upward, what happens?

**Answer:** error — the toolchain cannot establish the module context / package path. Return to the module root or specify the path correctly.

### Example 2 — Internal package and import

`internal/pricing/price.go`:

```go
package pricing

// Discount returns the price after a percentage discount.
func Discount(cents int, percent int) int {
	if percent < 0 {
		percent = 0
	}
	if percent > 100 {
		percent = 100
	}
	return cents * (100 - percent) / 100
}
```

`cmd/shop/main.go`:

```go
package main

import (
	"fmt"

	"example.com/shop/internal/pricing"
)

func main() {
	fmt.Println(pricing.Discount(2000, 15))
}
```

Run:

```text
go run ./cmd/shop
```

Output:

```text
1700
```

#### What happens here

Line by line with concrete values:

1. `Discount(2000, 15)` — `cents == 2000`, `percent == 15`.
2. First `if`: `15 < 0`? no.
3. Second `if`: `15 > 100`? no.
4. Expression: `2000 * (100 - 15) / 100` → `2000 * 85 / 100`.
5. Integer division: `170000 / 100` → `1700`.
6. `fmt.Println` prints `1700`.

The function `Discount` starts with a capital letter — it is exported from package `pricing`. `main` imports it via the full module path. If someone outside this module tried `import "example.com/shop/internal/pricing"`, the compiler would report a ban because of `internal`. That protects implementation details without “friend” keywords.

If the function were `discount` (lowercase), even *your* `main` in another package could not call it — unexported at the package boundary.

Integer arithmetic here is deliberate: you work in cents to avoid float for money. For production currencies later you use more careful types/strategies — here the mechanism is package + export + `internal`.

### Example 3 — gofmt and go vet in a loop

Deliberately “ugly” and suspicious code in `cmd/shop/main.go` before formatting:

```go
package main

import (
	"fmt"

	"example.com/shop/internal/pricing"
)

func main() {
	price := 2500
	fmt.Printf("price=%d discount=%s\n", pricing.Discount(price, 10))
}
```

Problems:

- `Printf` has two verbs (`%d`, `%s`), and one argument after the format
- if you manually break indentation with spaces, the style is not `gofmt`

Fixed code:

```go
package main

import (
	"fmt"

	"example.com/shop/internal/pricing"
)

func main() {
	price := 2500
	fmt.Printf("price=%d\n", pricing.Discount(price, 10))
}
```

Commands:

```text
gofmt -w ./cmd/shop/main.go
go vet ./...
go run ./cmd/shop
```

Expected output after the fix:

```text
price=2250
```

#### What happens here

`Discount(2500, 10)` → `2500 * 90 / 100` → `2250`.

`gofmt` aligns indentation and import layout (standard library, then blank line, then the rest — the usual group style). It does not change `2250` or the logic.

`go vet` catches `Printf` argument mismatches that at runtime would give wrong or warning output. The compiler itself does not treat all `Printf` errors equally strictly in all cases; vet supplements with discipline.

The flow you want as muscle memory: format → vet → run/test → build.

Predict: after `gofmt -w`, does the bug with `%s` disappear?

**Answer:** no. Formatting is not a semantic fix. Only fixing the number of verbs / arguments (or `go vet` as a signal) solves the bug.

### Example 4 — Small real layout with two commands

```text
example.com/shop/
  go.mod
  cmd/shop/main.go
  cmd/shopctl/main.go
  internal/pricing/price.go
  internal/pricing/price_test.go
```

`cmd/shopctl/main.go`:

```go
package main

import (
	"fmt"
	"os"
	"strconv"

	"example.com/shop/internal/pricing"
)

func main() {
	if len(os.Args) != 3 {
		fmt.Fprintln(os.Stderr, "usage: shopctl <cents> <percent>")
		os.Exit(2)
	}
	cents, err1 := strconv.Atoi(os.Args[1])
	percent, err2 := strconv.Atoi(os.Args[2])
	if err1 != nil || err2 != nil {
		fmt.Fprintln(os.Stderr, "arguments must be integers")
		os.Exit(2)
	}
	fmt.Println(pricing.Discount(cents, percent))
}
```

```text
go run ./cmd/shopctl 5000 20
go build -o bin/shop ./cmd/shop
go build -o bin/shopctl ./cmd/shopctl
```

Expected output:

```text
4000
```

#### What happens here

Two `main` packages share the same `internal/pricing`. You do not duplicate business logic in both CLIs.

Concrete flow for `go run ./cmd/shopctl 5000 20`:

1. `os.Args` looks roughly: `[0]=...shopctl`, `[1]="5000"`, `[2]="20"` → `len == 3`.
2. `strconv.Atoi("5000")` → `cents=5000`, `err1=nil`.
3. `strconv.Atoi("20")` → `percent=20`, `err2=nil`.
4. Both `error`s are `nil` → you do not enter the branch with `os.Exit(2)`.
5. `Discount(5000, 20)` → `5000 * 80 / 100` → `4000`.
6. `Println` prints `4000`.

If you run without arguments, `len(os.Args) != 3`, the message goes to stderr, exit code 2 — convention for usage error.

`strconv.Atoi` returns a value and an `error` — the idiomatic multiple-return pattern (more detail in the functions lesson). This is the skeleton of monorepo style inside one module: multiple entries, one library.

Defensively: this CLI does not execute a shell, does not open arbitrary paths — it only parses numbers. When you add file operations, validate the path and reject `..` surprises.

### Example 5 — Deliberate import failure and reading the message

In `main` temporarily write:

```go
import "example.com/shop/internal/does-not-exist"
```

Run:

```text
go run ./cmd/shop
```

#### What happens here

The compiler/toolchain does not find the package. The message will name the import path. There is no runtime magic — the build stops. Fix the path or delete the import. The exercise is to read the diagnostics instead of guessing: almost always it says *which* string was not resolved.

## Decision analysis

| Decision | Alternative | Choice in this lesson | Why |
|----------|-------------|----------------------|-----|
| Where should code live? | `$GOPATH/src/...` | anywhere + `go.mod` | less friction, clear root |
| How to name an import? | relative path | module path + path | platform-independent, unambiguous |
| Where to put the CLI? | `main.go` at the root | `cmd/<name>` | multiple entries, clean root |
| How to hide details? | everything exported | `internal/` + unexported names | smaller API surface |
| How to catch `Printf` bugs? | only `go build` | `go vet` in the loop | build does not catch everything |
| Dependencies | “what is on disk” | `require` + `go.sum` | reproducibility on CI |

Why `example.com/...` instead of `C:\projects\shop`? Because an import path must be **platform-independent** and unambiguous in the ecosystem. Why `internal/` instead of everything public? Because the exported API grows faster than you think; `internal` reduces the surface other modules can hook onto. Why `cmd/`? Because explicit paths `./cmd/name` make intent clear in Makefile/CI.

You add `go mod tidy` as soon as you introduce external dependencies: it removes unused `require` lines and fills `go.sum` with checksums. Without `go.sum`, CI and local builds can diverge relative to proxy content.

## Trade-offs

- **Modules** give reproducibility, but introduce `go.sum` noise in PRs and learning semantic import versioning (`/v2` in the path).
- **`internal/`** protects, but makes sharing code between two of your modules harder — then you extract a shared public module.
- **One module vs many modules** — one module is simpler to start; micro-modules make sense only when versions truly live separately.
- **`go run` vs installed binary** — `go run` is slower because of constant compilation; for frequent calls you build once.
- **Vet** is not perfect — false positives rare, false negatives more often; it does not replace review.
- **`cmd/` convention** is not enforced by the compiler — team discipline; without it the project still “works”, but grows into chaos.

## Common mistakes

1. **`go mod init` without a sensible path** then later broken imports when you publish the repo.
2. **Putting `main.go` at the root** and mixing library with CLI — works, but grows into chaos; prefer `cmd/`.
3. **Wrong import** (`import "./internal/pricing"`) — relative imports are not allowed in module mode.
4. **Multiple `package` names in the same folder** — the compiler rejects it.
5. **Forgotten `go mod tidy`** after removing dependencies — dirty `go.mod`.
6. **Expecting `gofmt` to fix bugs** — it formats style, not logic; that is why vet and tests exist.
7. **Building from the wrong directory** — `go` looks for `go.mod` upward; run from the module or specify the path.
8. **Mixing module and package** — a module is a dependency boundary (`go.mod`); a package is a directory with a `package` clause.
9. **Expecting `internal/` to hide names inside the same module** — it does not; for that use unexported (lowercase). `internal` protects from *external* modules.
10. **Committing local binaries** instead of `go.mod`/`go.sum` — the opposite is needed.

## Idiomatic Go

- One module per repo until you prove the need for more.
- `cmd/<name>` for each binary; directory name = command name.
- Business logic in packages outside `main`; `main` only wires things.
- After every larger change: `gofmt -w .` → `go vet ./...` → `go test ./...` → `go build`.
- Align the module path with the future remote URL if you plan to publish.
- Do not commit local binaries; commit `go.mod` and `go.sum`.
- Package names short, without underscores, singular or a clear noun (`pricing`, not `pricing_utils`).
- Keep `main` thin: parse input, call the library, map `error` → exit code.

## Practical scenario

A startup has a Python script `deploy_helper.py` and a Node tool for migrations. A new engineer introduces Go module `github.com/acme/ops` with `cmd/deploy` and `cmd/migrate`, shared `internal/config` for reading YAML. CI runs:

```text
go vet ./...
go test ./...
go build -o dist/deploy ./cmd/deploy
go build -o dist/migrate ./cmd/migrate
```

Artifacts go to an internal bucket. The ops team does not install Python dependencies on jump hosts. When someone tries to import `internal/config` from another repo, the build fails — deliberately. The team then extracts the stable `github.com/acme/ops-config` as a public API, and the rest stays internal. Directory organization prevented accidental merging of API surfaces.

Security detail from the same scenario: `internal/config` does not print secrets from YAML in debug mode by default; the CLI accepts a path to the config as an argument, but refuses to pass it to a shell. The module boundary and input discipline work together.

## Check questions

1. **What does `go mod init` do?**  
   Creates `go.mod` with the module path and language version; marks the directory as the module root.

2. **What is `internal/` for?**  
   Restricts package import to the parent module tree; external modules cannot import that code.

3. **Why are relative imports not OK in modules?**  
   The import path must be unambiguous and tied to the module path, not to the file’s position on disk.

4. **What is the difference between `gofmt` and `go vet`?**  
   `gofmt` formats style; `go vet` looks for suspicious constructs and likely bugs.

5. **Must you keep the project in GOPATH?**  
   No. In module-aware mode the project lives where it has `go.mod`.

6. **What is the difference between module and package?**  
   A module is a unit of dependency and versioning (`go.mod`). A package is a unit of compilation and exported/unexported visibility (a directory with a `package` name).

7. **Why does `Discount` with capital D work from `main`, and `discount` does not?**  
   Capital letter = exported across the package boundary; lowercase = unexported, visible only inside the same package.

8. **What should you commit: `bin/shop` or `go.sum`?**  
   `go.sum` (with `go.mod`); local binaries usually not.


The project is no longer a lonely file: you have a name, boundaries, and a tooling loop.

## Summary

A Go project starts with `go mod init`, a clear module path, and the `cmd/` + `internal/` convention. A package is imported with the full path; relative imports are out. The tools `go run`, `go build`, `gofmt`, and `go vet` form the basic local cycle. The GOPATH era is history for new projects; modules are the default way of working. Exported/unexported and `internal/` together control what leaks as API. The next lesson enters primitive data types.
