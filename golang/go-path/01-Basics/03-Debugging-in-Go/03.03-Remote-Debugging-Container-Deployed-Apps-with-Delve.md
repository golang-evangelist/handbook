# 03.03 Remote Debugging Container Deployed Apps with Delve

> **Go Path - Zero to Gopher** / **01 Basics → Debugging in Go** / Lesson 03.03

## Lesson goals

After this lesson you can:

- run Delve in headless mode with `--listen`, `--headless`, `--api-version=2`, `--accept-multiclient`;
- prepare a debug binary (not stripped; often with `-gcflags="all=-N -l"`);
- write a Dockerfile debug stage and publish the port **only** on loopback;
- connect VS Code remote attach;
- explain the security risk: **never** expose the Delve port publicly;
- use an SSH tunnel or port-forward instead of opening a port to the world;
- distinguish a debug image from a production image.

## Prerequisite

- Local Delve CLI (03.01–03.02): break, continue, print, locals.
- Basic Docker: image, port mapping, multi-stage build (conceptual level is enough).
- VS Code Go extension (for attach example).
- You understand DWARF/symbols must exist in the binary.

## Problem this lesson solves

“It works on my machine” disappears in a container: different env vars, networking, read-only filesystem, different DNS. Prints in the image require rebuild per iteration. Remote Delve allows attach from the editor to a process in the container.

Without discipline that opens a critical hole: whoever reaches the Delve API can read memory and control the process. So security is not a footnote — it is part of the design. This lesson teaches the **correct** pattern: headless on localhost or through an SSH tunnel, never a public network address. It does not give instructions for attach to someone else’s processes.

## Mental model

**Headless Delve** = debugger server without an interactive prompt. Listens on TCP. Client (`dlv connect` or VS Code) sends API commands (`api-version=2`).

```text
[VS Code / dlv connect] --TCP--> [headless dlv] --control--> [your app]
                                      ↑
                         only 127.0.0.1 or SSH tunnel
```

**Target** still needs DWARF. Stripped image (`-ldflags="-s -w"`) = bad remote debug.

**Debug stage** in Dockerfile: separate stage with Delve + non-stripped binary + debug port open. Production stage stays thin and **without** Delve.

**Port publish:** `-p 127.0.0.1:2345:2345` binds host loopback → container. `-p 2345:2345` on a cloud VM without firewall = disaster.

Analogy: local `dlv debug` is a locked room in your house. Headless on `0.0.0.0` is an open window on the street with a sign “type commands.”

## Mechanism

### Headless startup (concept)

In a container or on a remote machine (your lab):

```text
dlv exec ./app --headless --listen=127.0.0.1:2345 --api-version=2 --accept-multiclient
```

or:

```text
dlv debug --headless --listen=127.0.0.1:2345 --api-version=2 --accept-multiclient
```

Flags:

| Flag | Role |
|------|--------|
| `--headless` | no interactive UI; API server |
| `--listen=` | address:port where it listens |
| `--api-version=2` | protocol modern clients expect |
| `--accept-multiclient` | multiple clients / reconnect |

**Key:** `listen=127.0.0.1:2345` (loopback), not `0.0.0.0:2345`, unless a strict tunnel/ACL is in front and you know what you are doing. For this course: **always loopback + tunnel**.

### Client

```text
dlv connect 127.0.0.1:2345
```

Then the same commands as locally: `break`, `continue`, `print`, `locals`, `goroutines`, `trace`...

### VS Code attach

```json
{
  "name": "Attach remote",
  "type": "go",
  "request": "attach",
  "mode": "remote",
  "remotePath": "",
  "port": 2345,
  "host": "127.0.0.1",
  "showLog": true
}
```

You set `substitutePath` when paths in the container differ from local sources:

```json
"substitutePath": [
  { "from": "D:\\proj\\mysvc", "to": "/src" }
]
```

Without mapping the breakpoint in the editor stays “gray” / does not hit.

### Why `-gcflags="all=-N -l"` in the debug stage

Optimizations remove locals and inline functions (04.01). In a container that looks like “remote does not work” although attach succeeds. Debug stage:

```text
go build -gcflags="all=-N -l" -o /app/server ./cmd/server
```

Without `-s -w`. Production stage may strip — but that is not the image you debug.

### Dockerfile debug stage (sketch)

```dockerfile
FROM golang:1.22 AS debug
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN go install github.com/go-delve/delve/cmd/dlv@latest
RUN go build -gcflags="all=-N -l" -o /app/server ./cmd/server
EXPOSE 2345 8080
CMD ["dlv", "exec", "/app/server", "--headless", "--listen=127.0.0.1:2345", "--api-version=2", "--accept-multiclient", "--continue"]
```

Note: `--continue` (check `dlv help` for your version) immediately runs execution until a breakpoint. If the flag is not supported, run without it and do `continue` from the client.

### Multi-stage: prod vs debug

```dockerfile
FROM golang:1.22 AS build
WORKDIR /src
COPY . .
RUN go build -o /out/server ./cmd/server

FROM gcr.io/distroless/static AS prod
COPY --from=build /out/server /server
ENTRYPOINT ["/server"]

FROM golang:1.22 AS debug
WORKDIR /src
COPY . .
RUN go install github.com/go-delve/delve/cmd/dlv@latest
RUN go build -gcflags="all=-N -l" -o /out/server ./cmd/server
EXPOSE 2345
CMD ["dlv","exec","/out/server","--headless","--listen=127.0.0.1:2345","--api-version=2","--accept-multiclient","--continue"]
```

You pick the target at build time. **Never** tag `debug` as `latest` in a production registry without control.

### SSH tunnel — default safe bridge

On the remote machine Delve listens only on `127.0.0.1:2345`. From the laptop:

```text
ssh -L 2345:127.0.0.1:2345 user@staging-host
```

Then local VS Code attach to `127.0.0.1:2345`. Traffic goes through SSH; security group **does not** open 2345 to the internet.

Same for Docker on a remote host: publish on host loopback + SSH `-L`, or only SSH to the host where the container is on the local network.

### Docker run — correct publish

```text
docker run --rm -p 8080:8080 -p 127.0.0.1:2345:2345 mysvc:debug
```

Note `127.0.0.1:2345:2345`. Application port 8080 for traffic; 2345 only for local attach.

### Checklist before attach

1. Binary is not stripped.
2. Source on laptop matches commit in the image.
3. `substitutePath` / `remotePath` configured.
4. Port mapped to loopback or reachable only via tunnel.
5. You know how to shut down debug container/pod after the session.
6. No production secrets you must not view on shared staging (team agreement).
7. You work on **your** lab/staging resource — no attach to someone else’s PID.

### What risk means (conceptual, no attack instructions)

A Delve API client can:

- read variables and memory;
- set breakpoints;
- in some conditions change state (`set`).

That is equivalent to a remote window into the process. Hence policy: localhost/tunnel only, time-limited debug deployment, audit who brought up the debug image, destroy after session.

### Kubernetes sketch (concepts only)

- debug Pod with Delve, **no** public Service/LoadBalancer on 2345;
- `kubectl port-forward pod/name 2345:2345` (tunnel from laptop);
- attach locally;
- delete Pod after.

Port-forward = tunnel, like SSH. Do not learn all of Kubernetes here — remember the principle.

### Predict, then check: which `docker run` is acceptable on a laptop?

A) `docker run -p 2345:2345 mysvc:debug`  
B) `docker run -p 127.0.0.1:2345:2345 mysvc:debug`  
C) `docker run -p 0.0.0.0:2345:2345 mysvc:debug` on cloud VM with SG `0.0.0.0/0`

**Answer:** B for local lab. A on a laptop often still binds all host network addresses — avoid the habit. C is unacceptable.

### FAQ

**Does Delve in a container require privileged?**  
Usually not for `dlv exec` of a process you start yourself. Attach to someone else’s PID is not course material.

**Can the same image be prod and debug?**  
Technically yes, bad practice: larger attack surface and slower binary.

**What about read-only root filesystem?**  
Debug stage often needs writes (tmpdir); do not copy prod hardenings blindly to debug image.

**Why `--api-version=2`?**  
Modern clients (VS Code Go) expect that protocol.

### Security memorandum (put in team wiki)

1. Delve port is not the application port.
2. Localhost or encrypted tunnel only.
3. Debug image ≠ `latest` in prod registry.
4. Time limit on debug deployment.
5. Audit who started it.
6. After session — destroy.
7. Prefer local reproduction; remote only when environment changes the bug.

### Diagnostic flow when attach “does not work”

1. Is headless listening at all? Log “API server listening...”.
2. `dlv connect 127.0.0.1:2345` from terminal — before VS Code.
3. If CLI fails: publish/firewall/listen address.
4. If CLI works and VS Code does not: host/port in launch, path mapping.
5. If it stops but `locals` empty: strip/opt binary.

### Relation to 03.01–03.02

Remote does not teach new “magic” observation commands. It teaches **transport and security**. If you do not know local CLI, remote will be chaos with more layers.

### Lab rhythm (complete)

1. `docker build -f Dockerfile.debug -t shop-api:debug .`
2. `docker run --rm -p 8080:8080 -p 127.0.0.1:2345:2345 shop-api:debug`
3. Wait until Delve listens.
4. VS Code → Attach remote → breakpoint in handler.
5. `curl http://127.0.0.1:8080/health`
6. Hit → `locals` → conclusion → Stop → shut down container.


### Additional lab: diagnosis order (print)

1. Does local dlv debug reproduce the bug? If not — do not go remote.
2. Does local headless + connect on 127.0.0.1 work?
3. Does Docker image build pass and dlv exist in image PATH?
4. Publish only 127.0.0.1:2345?
5. Does dlv connect from host work before VS Code?
6. Path mapping aligned?
7. Container shut down after session?

If you get stuck on step N, do not jump to N+2. Each layer adds a new class of errors.

### Additional: why commit sync matters

You debug an image with commit A while local editor shows commit B. Breakpoint “hits” wrong logic or a line that does not exist in the binary. Always align: same SHA in image label / build arg and local checkout.

### Additional: env in container

Bug often lives in APP_ENV, feature flag, or connection string. Before deep dive into code, in attach session check whether target sees expected env values (via print if in variables, or via config struct after load).


### Detailed walk: from symptom to attach

Symptom: “in Docker API returns 500, locally it does not.”

Step 1 — isolate environment  
Run the same binary locally with the same env file as compose. If 500 reproduces locally, remote is not needed.

Step 2 — confirm debug image  
`docker image inspect` / label with git SHA. Enter a temporary shell only if policy allows and confirm `dlv version` exists.

Step 3 — headless listen on loopback inside container  
Not `0.0.0.0` “because it is easier.” Publish from host as `127.0.0.1:2345:2345`.

Step 4 — CLI connect before IDE  
If CLI does not work, IDE will not magically.

Step 5 — break in handler that returns 500  
`args` request path; `locals` error value. Often you see the real `error` instead of guessing.

Step 6 — write finding, shut down debug, write test  
Remote session is not a place for a long stay.

### Decision table: local vs remote

| Question | If yes | If no |
|---------|--------|--------|
| Reproduces locally? | Stay on `dlv debug` | Consider remote |
| Depends on Docker DNS/network? | Remote/lab compose | Local mock |
| Need production secret in memory? | Stop — team agreement | Continue carefully |
| Can you tunnel? | SSH / port-forward | Do not open public port — seek alternative |

### Another predict-then-check

Does `--accept-multiclient` make public listen safe?

**Answer:** No. Multiclient eases reconnect; it does not add authentication. Security is network isolation (localhost/tunnel), not that flag.

### Extended remote debugging FAQ

**Why does break sometimes hit only after container restart?**  
Old process / old binary. You rebuilt image but container still holds old layer in memory. `docker rm` + new `run`.

**Can I debug tests in a container?**  
Technically yes (`dlv test` headless), but rarely worth it at the start. Local `dlv test` is faster. Save remote for “only fails in this environment.”

**What if several developers share staging?**  
Agree who holds the debug Pod. Multiclient is not a substitute for communication. One developer’s `set` ruins the other’s session.

**Does TLS on Delve port fix public listen?**  
The course does not teach “secure public Delve.” Default practice: do not listen publicly. Tunnel is the model.

**How do I know listen is really loopback in the container?**  
In CMD explicitly `127.0.0.1:2345`. Then publish `127.0.0.1:2345:2345` on host. Two layers of same intent.

### Anatomy of a bad day (anti-scenario)

1. Dev publishes `2345` on all network addresses “temporarily.”
2. Forgets.
3. Laptop on café Wi-Fi / cloud SG open.
4. Scanner finds port.
5. Incident.

Prevention is not “I will be careful.” Prevention is: compose/Helm by default *does not* expose 2345; debug profile explicit; TTL; checklist.

### Connection to concurrency

Remote pause changes timing even more (network + debugger). A race that “disappears” under Delve is not proof it is gone. Use `-race` in CI and locally; remote Delve for state after reproduction.

## Rules and syntax

1. Debug binary: without `-s -w`; often `-gcflags="all=-N -l"`.
2. Delve listen on `127.0.0.1` or only via SSH/port-forward.
3. Do not leave debug stage as default production deploy.
4. Delve is not a login server — network isolation is access control.
5. Map sources (`substitutePath`) when breakpoint does not hit.
6. Document in team: which compose profile is `debug`.
7. Do not practice attach on processes you did not start in the lab.
8. After session: stop/rm debug container or pod.

## Examples

### Example 1: Local simulation headless + connect

Terminal A:

```text
dlv exec ./server --headless --listen=127.0.0.1:2345 --api-version=2 --accept-multiclient
```

Terminal B:

```text
dlv connect 127.0.0.1:2345
break main.main
continue
```

#### What happens here

**Trace:**

1. Terminal A: Delve loads `./server`, listens only on loopback:2345, waits for client.
2. Terminal B: client connects to same host/port.
3. `break main.main` is sent via API to headless process.
4. `continue` runs target; stops on `main`.
5. Further: `print`/`locals` as locally.

If this does not work on one machine, Docker will not either — fix local headless first.

### Example 2: `docker run` with loopback publish

```text
docker build -f Dockerfile.debug -t mysvc:debug .
docker run --rm -p 8080:8080 -p 127.0.0.1:2345:2345 mysvc:debug
```

#### What happens here

1. Image contains `dlv` + debug binary.
2. Container starts headless Delve.
3. Host maps 2345 only to 127.0.0.1 — other devices on network do not see the port.
4. You attach from the same laptop.

This is minimal hygiene for laptop lab.

### Example 3: Compose debug profile

```yaml
services:
  api:
    build:
      context: .
      dockerfile: Dockerfile.debug
    ports:
      - "8080:8080"
      - "127.0.0.1:2345:2345"
    environment:
      - APP_ENV=dev
```

#### What happens here

Team runs `docker compose up api` for debug. Production compose **does not** have 2345. Separate profiles so someone does not accidentally deploy debug CMD.

### Example 4: VS Code remote attach with path mapping

```json
{
  "name": "Attach Docker Delve",
  "type": "go",
  "request": "attach",
  "mode": "remote",
  "port": 2345,
  "host": "127.0.0.1",
  "substitutePath": [
    {
      "from": "D:\\proj\\mysvc",
      "to": "/src"
    }
  ]
}
```

#### What happens here

1. Breakpoint in local `handler.go` maps to `/src/...` in container.
2. Delve ties lines via DWARF + substitutePath.
3. Without mapping: UI thinks break is set, target does not stop on “your” line.

**Predict the result:** if code in image is at `/src` and locally `D:\proj\mysvc`, which `from`/`to`?  
**Answer:** `from` = local path, `to` = path in container (`/src`).

### Example 5: What NOT to do (security)

```text
# BAD: publish Delve on public network address on cloud VM
docker run -p 2345:2345 mysvc:debug
# + security group 0.0.0.0/0 on 2345
```

#### What happens here

Debug port becomes process control from the network. Treat as critical incident if it happens. Correct: loopback + SSH `-L 2345:127.0.0.1:2345`, or private network with strict ACL — **never** public ingress on Delve.

### Example 6: SSH tunnel rhythm (conceptual)

On staging host (your lab):

```text
dlv exec ./server --headless --listen=127.0.0.1:2345 --api-version=2 --accept-multiclient
```

On laptop:

```text
ssh -L 2345:127.0.0.1:2345 user@staging-host
dlv connect 127.0.0.1:2345
```

#### What happens here

1. Delve on server does not listen publicly.
2. SSH creates local port 2345 that goes to remote loopback.
3. Your client thinks it is “local” connect — and it is, up to the tunnel.
4. Firewall does not need to open 2345 to the world.

## Decision analysis

| Decision | Motive |
|--------|--------|
| Separate debug image/stage | Do not poison prod image with Delve |
| `-N -l` in debug | Truer variables |
| Bind 127.0.0.1 | Reduces exposure |
| `api-version=2` | Expected client protocol |
| `substitutePath` | Breakpoints across OS paths |
| SSH / port-forward | Tunnel instead of public port |
| Prefer local reproduction | Smaller attack surface |

## Trade-offs

- **Debug image** larger, slower, unsafe if it leaks.
- **Headless + continue** changes startup (race with early events).
- **Optimized prod** does not debug well — reproduce in debug stage.
- **Multiclient** convenient, widens surface if port is badly exposed.
- Port-forward/SSH slower, but safer than public port.
- Path mapping requires commit sync discipline.

## Common mistakes

### 1. Stripped binary in “debug” image

**What happens here:** attach works, locals/source do not.  
**Correct:** build without `-s -w`, with `-N -l`.

### 2. Publish `2345` on `0.0.0.0` in cloud

**What happens here:** critical exposure.  
**Correct:** `127.0.0.1` + SSH tunnel / port-forward.

### 3. Wrong `substitutePath`

**What happens here:** breakpoint gray / does not hit.  
**Correct:** align local root with WORKDIR in image; confirm with `dlv connect`.

### 4. Host firewall blocks connect

**What happens here:** timeout.  
**Correct:** local headless without Docker first; then check publish.

### 5. Mixing app port and Delve port in launch.json

**Wrong:** attach on 8080.  
**Correct:** app 8080, Delve 2345 (or other agreed).

### 6. Delve not in image

**What happens here:** CMD does not find `dlv`.  
**Correct:** `go install` in Dockerfile debug stage.

### 7. Left debug CMD in production manifest

**What happens here:** production with debugger server.  
**Correct:** separate target/tag; checklist before deploy.

## Idiomatic Go / DevOps

- Two artifacts: `Dockerfile` (prod) and `Dockerfile.debug` or build target.
- Document: “Remote debug only via SSH -L 2345:127.0.0.1:2345”.
- CI never publishes debug image to public registry without control.
- Prefer local reproduction; remote when environment matters.
- After session destroy; do not “leave running until tomorrow.”

## Practical scenario

Kubernetes pod in staging. Dev opens NodePort on 2345 “for five minutes.” Network scan finds open Delve; memory with secrets becomes readable. Post-mortem: port-forward only via bastion host, NetworkPolicy deny on 2345, debug image only in private registry, TTL on debug deployment. Team now has checklist before every remote attach. Local reproduction is first choice again.

## Check questions

1. **What is headless Delve?**  
   **Answer:** Mode where Delve listens on network API without local interactive UI, for remote client.

2. **Which flags are commonly used?**  
   **Answer:** `--headless --listen=127.0.0.1:2345 --api-version=2 --accept-multiclient` (plus `exec`/`debug`).

3. **Why not strip debug binary?**  
   **Answer:** Without symbols/DWARF debugger does not map source and locals reliably.

4. **How does VS Code typically connect?**  
   **Answer:** `request: attach`, `mode: remote`, `host`/`port` to Delve listener (usually 127.0.0.1 via tunnel).

5. **Why never expose Delve port publicly?**  
   **Answer:** Gives remote control over process and memory read — critical security risk.

6. **What is SSH `-L` in this context?**  
   **Answer:** Forwards local port to remote loopback Delve listener without publicly opening port.

7. **Why separate debug and prod image?**  
   **Answer:** So production does not carry Delve and slower debug binary; reduces attack surface.

## Summary

Remote debug: headless Delve, debug binary, mapped port on localhost or SSH tunnel, editor attach, path mapping. Separate debug stage. Security is part of design: never public Delve, never attach to someone else’s processes, destroy after session. Observation commands stay the same as in 03.02 — only transport changes.
