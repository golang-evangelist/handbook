# 03.02 Exploring Delve with Command Line and Editor Integration

> **Go Path - Zero to Gopher** / **01 Basics → Debugging in Go** / Lesson 03.02

## Lesson goals

After this lesson you can:

- run `dlv debug` and the basic cycle `break` / `continue` / `next` / `step` / `stepout`;
- read state with `print`, `locals`, `args`, `stack`;
- list `goroutines` and understand why that is not a list of OS threads;
- use `trace` for observation without a long permanent stop;
- connect the same knowledge to VS Code `launch.json` (`type: go`, `mode: debug`);
- diagnose “F5 does not work” by first reproducing the same step in the CLI.

## Prerequisite

- Delve installed (`dlv version` works) — lesson 03.01.
- A small Go module with `package main` (Go 1.22+).
- Preferably: VS Code + official Go extension (concepts apply to GoLand too).
- You understand print vs breakpoint and why you do not strip the debug binary.

## Problem this lesson solves

GUI buttons hide meaning. When F5 “does not work,” you are left without a model. Delve CLI teaches the vocabulary: what `next` is versus `step`, where arguments are, how to see other goroutines. The editor only sends the same commands. This lesson connects both worlds so you can learn in the CLI, work fast in the UI — and fix the UI when it lies.

## Mental model

Session = conversation with the debugger.

1. **break** — “stop here” (location).
2. **continue** (`c`) — “run to the next hit / end.”
3. **next** (`n`) — next line in the **same** function (treats a call as one step).
4. **step** (`s`) — enter the call.
5. **stepout** — leave the current function back to the caller.
6. **print / locals / args** — what matters in this frame.
7. **stack** — chain of frames.
8. **goroutines** — who exists; switch focus.
9. **trace** — pass through a location and record, without (required) a long stop.

VS Code `launch.json` with `"type": "go", "mode": "debug"` tells the extension: run Delve over the package like `dlv debug`.

Analogy: CLI is grammar; GUI is a keyboard with shortcuts. Without grammar, shortcuts sound like magic.

## Mechanism

This is the longest section. Here you learn *what happens* between keystrokes and the target process.

### CLI entry: how Delve starts the target

```text
dlv debug ./cmd/api
dlv debug . -- -flag value
dlv test ./pkg/foo
dlv exec ./already-built.bin
```

What each means:

| Form | Role |
|-------|--------|
| `dlv debug <package>` | Delve compiles (with debug info) and runs under control |
| `dlv test <package>` | Same, but for package tests |
| `dlv exec <binary>` | Controls an already built file — you are responsible for build flags |

Arguments after `--` go to **your program**, not Delve:

```text
dlv debug . -- -port 8080 -env dev
```

If you forget `--`, Delve may try to parse `-port` as its own flag and the session looks “broken.”

### Breakpoints: location and lifecycle

```text
break main.go:42
break main.sum
break pkg.(*Type).Method
breakpoints
clear 1
```

Lifecycle:

1. **create** — `break` picks PC (program counter) via DWARF.
2. **hit** — target stops; you observe.
3. **clear/disable** — session hygiene.

Function break (`break main.sum`) is more resilient to line shifts when you add comments. Line break is precise when you know the exact statement.

If you break on a blank line or pure comment, Delve often jumps to the next executable statement — or does not stop as you expect. Break on *code*, not decoration.

### Stepping: next vs step vs stepout

```text
continue   # c
next       # n
step       # s
stepout
```

**Predict, then check:** on the line `v := helper(21)` what does `step` do, and what does `next`?

```go
func helper(n int) int { return n * 2 }

func main() {
	v := helper(21)
	_ = v
}
```

**Answer:**  
- `step` enters `helper` (next stop inside, `n` is 21).  
- `next` stays in `main` and moves to the line after return (`v` becomes 42).

Hypothesis rule:

- you suspect the callee body → `step`;
- you trust the helper → `next`;
- you wandered into `fmt` / stdlib → `stepout` or `continue` to your breakpoint.

### State: args, locals, print, stack

```text
args
locals
print expr
whatis x
stack
```

Order on a hit (habit):

```text
stack          # where am I?
args           # what came in?
locals         # what am I computing?
print ...      # hypothesis
```

`print` accepts a limited subset of Go expressions (fields, indexes, `len`/`cap`, simple arithmetic). It is not a full interpreter. If the expression fails, simplify it.

### Goroutine: Go level, not OS thread

```text
goroutines
goroutine 1
```

`goroutines` lists concurrent flows in the runtime. **Do not** call them threads in your head: many goroutines share a smaller number of OS threads. For an application bug you almost always look at `goroutines`, not `threads` (`threads` exists but is a lower level — 04.04).

When you stop, ask: “Is the active goroutine the one my hypothesis is about?” If not — switch context before `locals`.

### Trace: temporary log without changing code

```text
trace main.go:27
trace main.handler
```

`trace` records passes through a location. Use it when you want event frequency (“how many times it enters the handler”) without a manual stop each time. It is not production logging — it lives in the session.

### GUI → CLI mapping

| VS Code / button | Delve CLI |
|-----------------|-----------|
| F5 Start | `dlv debug` + continue |
| F9 Breakpoint | `break` |
| F10 Step Over | `next` |
| F11 Step Into | `step` |
| Shift+F11 Step Out | `stepout` |
| Variables | `locals` / `args` |
| Debug Console izraz | `print` |
| Call Stack | `stack` |
| Logpoint (approximate) | `trace` |

When the GUI is silent, do the same action in the CLI — you see the real message.

### VS Code launch.json — what it really means

```json
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "Launch package",
      "type": "go",
      "request": "launch",
      "mode": "debug",
      "program": "${workspaceFolder}"
    }
  ]
}
```

- `type: go` — Go extension / DAP adapter.
- `request: launch` — start a new target (not attach).
- `mode: debug` — build and debug the package.
- `program` — **which** package; most common cause of “does not stop.”

For program arguments:

```json
"args": ["-port", "8080"]
```

That is equivalent to `-- -port 8080` in the CLI.

### Typical five-minute session (rhythm)

1. Reproduce the bug without the debugger (so you know steps and input).
2. `dlv debug ./cmd/...`
3. `break` on the suspicious function (function break).
4. `continue`, reproduce input.
5. `args` + `locals` + one `print`.
6. `step` only into **your** package, not stdlib.
7. Write down the finding, `exit`, write a test.

This rhythm matters more than knowing every subcommand.

### Quick cheat sheet

```text
dlv debug .              # start
break file.go:N          # stop
break pkg.Func           # stop on function
continue / c             # go
next / n                 # line
step / s                 # enter
stepout                  # leave
args / locals / print x  # state
stack                    # stack
goroutines               # list
trace file.go:N          # trace without long stop
exit                     # end
```

### Deeper: what happens when you say `break main.sum`

1. Delve looks up symbol `main.sum` in debug info.
2. Finds entry address(es) for the function.
3. Writes a breakpoint (software trap) at that address.
4. When the CPU arrives, the OS notifies the debugger.
5. Delve maps PC back to source and frame.
6. Prompt wakes; target is stopped.

If the symbol does not exist (inline in opt build, wrong package), break does not work as you expect. That is why 04.01 covers `-N -l`.

### Deeper: frame and why `stack` comes before `print`

```text
main → a → b → c   (you are in c)
```

If in `c` you `print x` and conclude “x is wrong,” the bad input might come from `b`. `stack` shows the chain; switching frames (more in 04.02) shows where the value first “went wrong.”

### Deeper: Debug Console is not a Delve REPL

In VS Code Debug Console you evaluate expressions in frame context. That is not guaranteed 1:1 with every `dlv` command. `goroutines` as a CLI list may be in a separate panel. For advanced use (`funcs`, complex `trace`) the CLI is often clearer.

### Diagnosis: CLI works, F5 does not

1. Same package: `dlv debug ./cmd/api` vs `program` in JSON.
2. Same break: function name.
3. If CLI hits and UI does not — path / launch / extension.
4. If CLI does not hit — build, strip, wrong code, build tag.

Do not reinstall VS Code as step 1.

### Security note (brief)

This lesson is local debug. Do not open a headless listen port here. Remote patterns (localhost / SSH tunnel) are 03.03. Do not practice attach on someone else’s processes.

### Mechanism FAQ

**Why does `step` into `fmt.Println` hurt?**  
You enter the standard library: hundreds of steps. Use `next`.

**What if `print` says optimized out?**  
The build is probably optimized — see 04.01 (`-gcflags="all=-N -l"`).

**Can I change variables?**  
`set` exists (04.04) — for experiment only, not a fix.

**Do breakpoints survive `restart`?**  
Usually yes; program state starts over.

Sketch on paper:

```text
main

```

Mark where `break main.sum` stops, what `args` shows, what `stepout` does. Then do Example 1 and compare your sketch to reality.


### Mechanism extension: how to practice without burnout

Repeat the same five-minute rhythm three days in a row on *different* small programs:

1. arithmetic (sum/discount);
2. pointer + nil;
3. two goroutines + channel.

Each day only: break → continue → args/locals → next/step deliberately → exit. Muscle memory for commands comes from repetition, not reading a table.

### Extension: what “hit” means

When you say a breakpoint “hit,” you mean:

1. PC reached the break address;
2. (optional) condition is true — conditions in 04.03;
3. Delve took control and waits for a command.

If a break “exists” in the list but never hits, the problem is the execution path, not `break` command syntax.

### Extension: list and orientation

```text
list
```

Shows source around the current PC. Use when you are lost after a series of `next`. Better than guessing “which line am I on.”

### Extension: restart in the hypothesis loop

```text
restart
```

Restarts the target. Breakpoints usually remain. Use when you got input wrong or want a clean start without `exit` + new `dlv debug`.

### Another predict-then-check exercise

```go
func main() {
    x := 1
    x = x + 1
    fmt.Println(x)
}
```

If you break on `main.main`, `continue`, then exactly two `next` (skipping declarations depending on where Delve stops on entry), what do you expect from `print x` before `Println`?

**Answer:** `2`. If you see `1`, you did one `next` too few — repeat and count lines with `list`.



Remember: CLI is source of truth when the UI lies; UI is speed when you already understand CLI.
## Rules and syntax

1. Break location: `file:line` or qualified function name.
2. `step` into `fmt` / reflect / runtime — almost always a beginner mistake; prefer `next`.
3. After a hit, check **which** goroutine is active.
4. `print` is not full Go — simplify the expression.
5. Editor and CLI share the same Delve; learn CLI to understand GUI.
6. Program arguments go after `--` or in `args` in launch.json.
7. `program` in launch.json must point to the right package.
8. `trace` for frequency; `break` for deep investigation.
9. After a session, clear stale breakpoints in the editor so tomorrow’s F5 does not stop randomly.

## Examples

### Example 1: Mini program and complete CLI session

```go
package main

import "fmt"

func sum(a, b int) int {
	return a + b
}

func main() {
	x := 10
	y := 32
	fmt.Println(sum(x, y))
}
```

Session:

```text
dlv debug .
break main.sum
continue
args
print a+b
stepout
locals
continue
```

#### What happens here

**Trace with values:**

1. `dlv debug` builds and stops before execution (waits for commands).
2. `break main.sum` — trap at entry to `sum`.
3. `continue` — `main` sets `x=10`, `y=32`, calls `sum`.
4. Stop in `sum`: `args` → `a=10`, `b=32`.
5. `print a+b` → `42`.
6. `stepout` — return to `main`; `locals` may show `x`, `y` and (after assignment) result in the `sum` call depending on line.
7. `continue` — `Println` prints `42`, program ends.

You see the link between frames without a single `fmt.Printf` in `sum`.

### Example 2: `next` vs `step` with prediction

```go
package main

func helper(n int) int { return n * 2 }

func main() {
	v := helper(21)
	_ = v
}
```

**Predict the result:** If on the line `v := helper(21)` you do `next`, do you ever see `n` inside `helper`?  

**Answer:** No — `next` does not enter. For `n` you need `step` (or break in `helper`).

#### What happens here

1. Break on `main.main`, `continue`, `next` to the call.
2. Path A: `step` → into `helper`, `print n` → `21`, `print n*2` → `42`.
3. Path B: `next` → stay in `main`, `v` becomes `42` without entering.

Choice depends on hypothesis, not the habit “always F11.”

### Example 3: Stack and nested calls

```go
package main

func a(n int) int { return b(n + 1) }
func b(n int) int { return c(n + 1) }
func c(n int) int { return n * 10 }

func main() {
	_ = a(1)
}
```

```text
break main.c
continue
stack
print n
```

#### What happens here

**Trace of value `n`:**

1. `main` calls `a(1)` → in `a`, `n=1`.
2. `a` calls `b(2)` → in `b`, `n=2`.
3. `b` calls `c(3)` → in `c`, `n=3`.
4. `stack` shows `c` ← `b` ← `a` ← `main`.
5. `print n` in `c` → `3`; return would be `30`.

Hypothesis “where is n broken” becomes checking frames, not guessing.

### Example 4: Goroutine list

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	go func() {
		for {
			time.Sleep(time.Second)
		}
	}()
	fmt.Println("breakpoint here")
	time.Sleep(2 * time.Second)
}
```

```text
break main.main
continue
next
goroutines
```

#### What happens here

1. Main starts; after `go func()` a background goroutine exists.
2. After several `next`, `goroutines` shows main + worker (often in sleep/wait).
3. Conclusion: the state of the “world” is not only main’s frame.

If you assume one stack in concurrent code, you miss the bug in another flow.

### Example 5: VS Code launch.json for package and arguments

```json
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "Debug main package",
      "type": "go",
      "request": "launch",
      "mode": "debug",
      "program": "${workspaceFolder}",
      "args": ["-port", "8080"],
      "env": {
        "APP_ENV": "dev"
      }
    },
    {
      "name": "Debug current file",
      "type": "go",
      "request": "launch",
      "mode": "debug",
      "program": "${file}"
    }
  ]
}
```

Set a breakpoint in `main`, F5, pick the configuration. VARIABLES ≈ `locals`/`args`. CALL STACK ≈ `stack`.

#### What happens here

1. Extension starts Delve as `dlv debug` over `program`.
2. `args` go to the process (like after `--`).
3. Gutter breakpoint = `break`.
4. If it does not hit: check that `program` is not the wrong subfolder.

`Debug current file` works only if that file has `package main` and can build alone — for modules with `cmd/api` use an explicit path.

### Example 6: Trace instead of temporary Println

```go
package main

import "fmt"

func tick(i int) {
	_ = i
}

func main() {
	for i := 0; i < 5; i++ {
		tick(i)
	}
	fmt.Println("end")
}
```

```text
trace main.tick
continue
```

#### What happens here

1. Each call to `tick` generates a trace in the session.
2. You see 5 passes (`i` 0..4) without manual stops.
3. For depth at `i==3`: ordinary break + `condition` (04.03) or break then manual filtering.

## Decision analysis

| Decision | Motive |
|--------|--------|
| Learn CLI first | Portable, debuggable knowledge |
| `break` on function | Resilient to line shifts |
| `next` by default | Less wandering in stdlib |
| `goroutines` early | Concurrency bugs |
| `mode: debug` | Standard local launch |
| CLI as fallback when F5 is silent | Isolate extension layer |
| `trace` before Println noise | Cleaner diff |

## Trade-offs

- **CLI** slower UX, clearer model.
- **GUI** faster to click, hides config errors.
- **Break on every line** slows you down — be precise.
- **Conditional breakpoints** (04.03) reduce noise but cost evaluation.
- Debugging tests (`dlv test`) vs app — choose by reproduction.
- `trace` on an extremely hot path still slows the session.

## Common mistakes

### 1. `step` into `fmt` / stdlib

**Wrong:** F11 / `step` on `fmt.Println`.  
**What happens here:** you wander the standard library.  
**Why:** `step` enters the call.  
**Correct:** `next` / F10; `step` only into your function.

### 2. Breakpoint in code that never runs

**What happens here:** never stops.  
**Why:** wrong build tag, wrong file, dead code.  
**Correct:** confirm `go run` path; function break; `stack` when you stop elsewhere.

### 3. Wrong `program` in launch.json

**Wrong:** `"program": "${workspaceFolder}"` while `main` is in `cmd/api`.  
**What happens here:** you debug the wrong package or fail.  
**Correct:** `"program": "${workspaceFolder}/cmd/api"` or CLI `dlv debug ./cmd/api`.

### 4. Expecting `print` to change state

**What happens here:** you read a value, nothing changes.  
**Why:** `print` is observation; mutation is `set` (04.04).  
**Correct:** separate observation and experiment.

### 5. Mixing `attach` and `debug` mode

**What happens here:** you wait for a remote port that does not exist, or the opposite.  
**Correct:** local learning = `launch` + `mode: debug`. Attach is 03.03 / 04.05.

### 6. Forgotten arguments after `--`

**Wrong:** `dlv debug . -port 8080`  
**Correct:** `dlv debug . -- -port 8080`

### 7. Working on stripped / opt binary then blaming CLI

**Correct:** build/debug info first (03.01, 04.01), then commands.

## Idiomatic Go

- Keep `launch.json` in the repo (no secrets) for shared DX.
- For libraries: `dlv test` + breakpoint in `_test.go` or code.
- Reproduce with the smallest program before debugging a monorepo.
- Learn core commands by heart: break, continue, next, step, stepout, print, locals, args, stack, goroutines, trace.
- After a finding — test. Debugger explains; test preserves.

## Practical scenario

A new team member “cannot debug” in VS Code. Outcome: `program` pointed at `cmd/old` instead of `cmd/api`. In CLI `dlv debug ./cmd/api` works immediately. After aligning launch.json, GUI works. Team puts both in onboarding README: CLI cheat sheet + sample launch.json. On code review for suspicious concurrency, they ask for `goroutines` output from Delve, not just a log line.

## Check questions

1. **Difference between `next` and `step`?**  
   **Answer:** `next` stays in the current function (skips the call as one step); `step` enters the called function.

2. **What are `args` vs `locals` for?**  
   **Answer:** `args` are function parameters; `locals` are frame local variables.

3. **How do you pass CLI arguments to the program under Delve?**  
   **Answer:** After `--` in `dlv debug . -- -flag value` (or `args` in launch.json).

4. **What does `"mode": "debug"` mean in launch.json?**  
   **Answer:** Launch package/program under Delve with a debug build.

5. **Why look at `goroutines`?**  
   **Answer:** To see all concurrent flows and switch to the one holding relevant state. Those are not OS threads.

6. **What is `trace` for?**  
   **Answer:** Records passes through a location without required long stops — temporary log in the session.

7. **First step when F5 does not hit a breakpoint?**  
   **Answer:** Same package and break in CLI (`dlv debug`); that isolates launch/extension from Delve/build issues.

## Summary

Delve CLI core: `break`, `continue`, `next`, `step`, `stepout`, `print`, `locals`, `args`, `stack`, `goroutines`, `trace`. VS Code Go launch with `type: go` and `mode: debug` is the same engine. Learn the vocabulary once — use it everywhere. `next` is the default step; `step` is deliberate entry. Program arguments go after `--`. When the UI lies, the CLI tells the truth.
