# 03.01 Getting Started With Go and Debugging

> **Go Path - Zero to Gopher** / **01 Basics → Debugging in Go** / Lesson 03.01

## Lesson goals

After this lesson you can:

- explain why a debugger exists alongside `fmt.Println` and structured logging;
- understand that Go by default embeds debug information into the binary;
- compare print-debugging with breakpoints;
- visualize the call stack and goroutines (concurrent streams that the Go scheduler schedules) as part of debugging;
- install Delve (`dlv`) the official way via `go install` and verify that it works;
- distinguish situations where print remains useful from those where the debugger saves hours.

## Prerequisite

- Go 1.22+ and the `go` command on PATH.
- You can run a small program (`go run .`) and simple tests.
- Basic concepts: function, package (Go package), call stack at the idea level.
- No prior debugger experience required; the lesson starts from zero.

## Problem this lesson solves

When a program “behaves wrongly,” the first reflex is often: add `fmt.Println` everywhere. That works for small scripts. In a service with concurrency (more than one stream of work in one process) prints mix order, change timing, and create a Heisenbug (a bug that changes behavior when you observe it). Print also does not show the stack or local variables at the exact moment without extra code.

A debugger stops the target process, shows state, and allows step-by-step. Without a tool like Delve you stay on deduction from logs. This lesson builds the mental model before concrete CLI commands (those come in 03.02).

## Mental model

A **debugger** is a controlling process that controls the **target** (your program): sets breakpoints, reads memory, follows execution streams.

**Debug info** (often DWARF inside ELF/PE/Mach-O formats) maps machine addresses back to source file and line, and describes local variables. The Go compiler by default includes enough information for debugging. Aggressive optimizations can “lie” (variable gone, order mixed) — more detail in 04.01. For now remember: for a hard bug you sometimes build with less optimization.

**Print vs breakpoint:**

| Print / log | Breakpoint |
|-------------|------------|
| Always active in that build | Conditional, lives in the debugger session |
| Changes I/O and often timing | Stops at the exact place |
| Useful in a production signal | Intended for development and investigation |
| Easy to leave forgotten in code | Lives in debugger configuration |

**Stack:** who called whom up to the current line.  
**Goroutine mindset:** the bug may not be in the stream you currently look at. Delve lists goroutines; learn to ask “who else is running?”. A goroutine is **not** an OS thread (operating system thread) — many goroutines can share a smaller number of OS threads; Delve shows you the Go level.

Analogy: print is like every passer-by yelling where they were. A debugger is like freezing the street, reading license plates, and asking who called whom.

## Mechanism

This section is the core of the lesson: here you learn *why* the debugger works, not only *which* command to type. Read it more slowly than the examples. If you stall somewhere, do a small experiment in the terminal then come back.

### What Go embeds into the binary

`go build` and `go run` produce a binary with symbols and DWARF, unless you deliberately strip them:

```text
go build -ldflags="-s -w" -o app .
```

`-s -w` strips symbols and DWARF sections (strip). For learning debugging **do not strip**. A production stripped image makes attach and reading source lines harder.

What debug info carries, conceptually:

1. line table: “this machine address = `file.go:42`”;
2. type descriptions and locations of local variables;
3. function names for a readable stack.

Without that the debugger sees bytes, not your source.

### Session flow (conceptually, before CLI details)

1. You start the debugger over a package or an already built binary.
2. You set a breakpoint on `file.go:line` or on a function name.
3. You continue execution to a hit (`continue`).
4. You look at locals / print an expression (`locals` / `print`).
5. You go step-by-step: `next` (over a call), `step` (into a call), later `stepout` (exit).

This rhythm is the same in CLI and in the editor. The editor only sends the same ideas with buttons.

### Installing Delve

Official path:

```text
go install github.com/go-delve/delve/cmd/dlv@latest
```

Check:

```text
dlv version
```

`dlv` must be on PATH. On Windows that often means `%USERPROFILE%\go\bin` (or `GOBIN` if you change it).

Steps if PowerShell says the command was not found:

1. `go env GOPATH` and `go env GOBIN`.
2. Add the appropriate `bin` to the user PATH.
3. Open a **new** terminal (the old one does not see the PATH change).
4. Again `dlv version`.

Without this the VS Code Go extension also will not find Delve and F5 fails with a missing `dlv` message.

### Why Delve specifically, not “any” debugger

Go has its own runtime: scheduler, goroutines, panics with a rich stack. Delve is built around that model. A generic debugger sees OS threads; Delve lists goroutines and wait status. For the course and everyday application Go, Delve is the default tool.

### Print remains — but in the right place

Print-debugging is not forbidden. It is excellent when:

- you measure latency in production with a structured log;
- you need a lasting event trail after deploy;
- you work in an environment where a debugger is not available.

The debugger is stronger when:

- you do not know *where* the state is wrong, only *that* it is;
- you need stack and locals at the same moment;
- concurrent streams require a goroutine list;
- you do not want to commit temporary `fmt.Println`.

Healthy workflow:

```text
reproduce → (if possible) test → Delve → fix → test stays green
         → structured log only if you need production observation
```

### Predict-then-answer: what will this program print?

Before you run it, predict the output:

```go
package main

import "fmt"

func discount(price, pct int) int {
	return price - price*pct/100
}

func main() {
	fmt.Println(discount(1999, 15))
}
```

**Your prediction:** _____  

**Answer:** `1699`.  
Calculation: `1999 * 15 = 29985`, `29985 / 100 = 299` (integer division), `1999 - 299 = 1700`? Pause — check the order.

Exact trace:

1. `price*pct` → `1999 * 15` → `29985`
2. `29985 / 100` → `299` (int)
3. `price - 299` → `1999 - 299` → `1700`

Corrected prediction: the output is **1700**, not 1699. Many expect “15% of 1999 = 299.85 ≈ 300” and get 1699. Integer arithmetic gives 299. A debugger on the `return` line shows intermediate values without guessing: `print price*pct/100` → `299`.

### Windows, antivirus, and attach

Local `dlv debug` (start a new process under control) usually works more easily than attach to an already existing PID. Antivirus sometimes interferes. For learning stay on `dlv debug` / `dlv test`. **Do not** practice attach on other people’s processes — only on programs you start in your own session.

### Deeper: what “stop the program” means

When the debugger stops on a breakpoint, the target process no longer executes your Go code at that moment. From an observation standpoint:

1. CPU registers and memory are readable;
2. you can read local variables via the DWARF map;
3. you can continue (`continue`) or go step by step.

That is **not** the same as `time.Sleep` in code. Sleep is part of the program. A breakpoint is external control. That is why in production you do not “leave a breakpoint” — you leave a log.

### Deeper: zero value and a false “it works”

A zero value of a type often hides a bug: `0` for `int`, `""` for `string`, `nil` for pointer, `nil` for slice, `nil` for map, `nil` for channel, `nil` for interface. The program “does not panic,” but computes wrongly — as in the JSON example where `Pct` stayed `0`.

The debugger is especially strong exactly there: you see that a field is the zero value, while you thought it was loaded. A print that does not print that field leaves you in fog.

### Deeper: error values are not “a debugger error”

In Go the type `error` (interface) carries a description of failure. In the debugger you often see:

```text
print err
```

and get either `nil` or a concrete value. Do not mix:

- **error** — a value a function returns by convention;
- **panic** — a controlled crash of the flow that the runtime prints;
- **logic bug** — the program “runs” but computes wrongly.

The debugger helps with all three, but differently: for `error` you look at the `if err != nil` branch; for `panic` you look at the stack; for logic you look at locals.

### Deeper: `defer` and the order you see on the stack

```go
func f() {
	defer fmt.Println("later")
	fmt.Println("now")
}
```

When you stop inside `f` before return, `defer` has not run yet. When you leave the function, `defer` runs. If you debug a resource closed in `defer`, know *where* in the lifecycle you stand — otherwise you think the file is closed while it is not yet.

### Deeper: mapping “symptom → tool”

| Symptom | First tool |
|---------|------------|
| Wrong number / string in output | Breakpoint + `print` / test |
| Intermittent failure in concurrency | `-race`, then Delve on the reproduction |
| Panic nil pointer | Panic stack, then break before dereference |
| “Works on my machine” | Same commit + same input locally; only then remote |
| Slow endpoint | Profiler (`pprof`), not only the debugger |
| Wrong JSON / config | Break after decode; check zero value |

The debugger is not a hammer for every nail. Profiling and tests have their places.

### Deeper: why `go run` is not the same as a production binary

`go run` builds a temporary binary and runs it. `go build -o app .` makes a lasting artifact. `dlv debug` builds and controls. `dlv exec ./app` controls an already existing file.

For learning:

- `dlv debug .` — fewest worries about flags;
- `dlv exec` — when you want to confirm the *exact* artifact (e.g. a Docker stage).

If you strip then `exec`, do not blame Delve.

### Step-by-step: first local session from zero

Assume a module:

```text
demo/
  go.mod   # module example.com/skola/demo
  main.go  # discount example
```

1. `cd demo`
2. `go run .` — confirm the program works at all (e.g. prints `1700`).
3. `dlv version` — confirm the tool.
4. `dlv debug .`
5. At the `(dlv)` prompt: `break main.discount`
6. `continue`
7. The program stops in `discount`.
8. `args` — you see `price=1999`, `pct=15` (or `print price`).
9. `print price*pct/100` — you see `299`.
10. `continue` or `exit`.

If step 5 says it cannot find the function, check the package name (`main.discount` for `package main`). If step 2 does not work, do not go to the debugger — first fix the build.

### Anatomy of one “wrong” output without a panic

Beginners often think: “no panic, so no bug.” Wrong. Many bugs are silent:

```go
func average(nums []int) int {
	if len(nums) == 0 {
		return 0 // zero value — is that “no data” or “average 0”?
	}
	s := 0
	for _, n := range nums {
		s += n
	}
	return s / len(nums)
}
```

The call `average(nil)` returns `0`. Is that OK? Depends on the domain. A debugger on the return shows `len(nums)==0`. A table-driven test separates “no data” from “average zero.” Here you see why the lesson insists on test + Delve, not only on “runs without panic.”

### What the debugger does *not* do

- Does not prove absence of a race (for that: `-race` and careful design).
- Does not replace code review.
- Does not fix production by itself — `set` in a session (later) is not a deploy.
- Does not read minds: if you look at the wrong goroutine, you draw the wrong conclusion.
- Does not magically work on a stripped binary.

### Mini FAQ

**Do I need CLI if I use VS Code?**  
Not every day, but you must understand the model. When F5 “does not work,” CLI isolates whether the problem is Delve or the editor.

**Does `fmt.Printf("%#v", x)` replace the debugger?**  
Helps for a one-off insight. Does not give stack navigation, conditional stops, or a goroutine list.

**Why not debug in Docker immediately?**  
Because you add network, path mapping, and image. First local `dlv debug`. Remote is 03.03.

**What if `dlv version` works but `dlv debug` fails?**  
Read the message: often wrong directory, no `main`, or Delve/Go version. Do not reinstall VS Code as the first step.

**Can I debug a test instead of `main`?**  
Yes: `dlv test` — more detail in later lessons. For libraries without `main` that is the natural path.

### Exercise in your head: three hypotheses

Symptom: API returns a price without discount.

Hypothesis A: arithmetic in `discount` is wrong.  
Hypothesis B: `pct` arrives as 0 (decode/tag).  
Hypothesis C: wrong handler / cache returns an old response.

How do you choose the first breakpoint?

- A → break in `discount`, check `price`/`pct` and the expression.
- B → break after `Unmarshal` / bind, `print` the input struct.
- C → break in the handler that chooses cache vs fresh calculation.

Without a hypothesis, `continue` in a circle is wandering. A debugger without a question is an expensive `println`.

### Relationship of concurrency and parallelism

**Concurrency**: program structure — multiple tasks in flight, channel, `go` statement.  
**Parallelism**: real simultaneous execution on multiple cores.

The debugger pauses the world for observation. That breaks parallelism and changes concurrency timing. Therefore:

1. reproduce the bug (deterministically if possible);
2. only then stop;
3. for races use `-race` alongside visual insight.

### When *not* to open the debugger

- A typo in a constant that a test catches immediately — write a test, not a session.
- Wrong URL in a curl example — read the request.
- Build fails because of syntax — read the compiler, not Delve.
- CVE in a dependency — modules and upgrade (05.x), not a breakpoint.

Choose the tool by error layer: compiler → test → debugger → profiler → modules/infra.

## Rules and syntax

1. Do not learn the debugger on a stripped binary.
2. Print remains valid for telemetry; the debugger for interaction and local investigation.
3. In concurrent code assume multiple streams until you prove otherwise.
4. Install Delve via the official `go install` module, not a random fork.
5. The Delve version should support your Go version — on a strange error first update `dlv`.
6. Privileges / antivirus on Windows sometimes block attach — local `dlv debug` is a more reliable path to start.
7. Do not strip (`-s -w`) in a dev build “because it is smaller” — that turns off the map for the debugger.

## Examples

### Example 1: Program with suspicious arithmetic

```go
package main

import "fmt"

func discount(price, pct int) int {
	return price - price*pct/100
}

func main() {
	fmt.Println(discount(1999, 15))
}
```

With print you would add `fmt.Println(price, pct)` inside. With the debugger: breakpoint on `return`, check intermediate values without changing code.

#### What happens here

**Execution trace (concrete values):**

1. `main` calls `discount(1999, 15)`.
2. In `discount`: `price = 1999`, `pct = 15`.
3. Expression `price*pct/100` = `29985/100` = `299`.
4. Result = `1999 - 299` = `1700`.
5. `fmt.Println` prints `1700`.

If you expected 1699, the debugger shows you *why* (integer division), not only *what* is on the screen. In real code the formula is buried deeper — the same procedure applies.

### Example 2: Why print changes timing

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	done := make(chan struct{})
	go func() {
		time.Sleep(10 * time.Millisecond)
		fmt.Println("worker")
		close(done)
	}()
	// fmt.Println("main-pre") // uncomment: changes scheduling
	<-done
	fmt.Println("main-end")
}
```

#### What happens here

**Trace (typical order without an extra print in main):**

1. `main` creates channel `done`.
2. A new goroutine starts (anonymous function literal).
3. Main blocks on `<-done`.
4. Worker sleeps 10 ms, prints `"worker"`, closes the channel.
5. Main wakes, prints `"main-end"`.

Every extra I/O in main can change scheduling. The debugger also changes timing (it stops), but deliberately — you control when it goes on. That is why you still hunt races with `-race`, and use the debugger for state *after* reproduction.

### Example 3: Stack in your head before Delve

```go
package main

func a() { b() }
func b() { c() }
func c() {
	panic("look at the stack")
}

func main() {
	a()
}
```

Run `go run .` — the `panic` print already shows the stack. A debugger on `c` *before* the panic shows the same chain plus locals.

#### What happens here

**Trace to the panic:**

1. `main` → `a`
2. `a` → `b`
3. `b` → `c`
4. `c` calls `panic("look at the stack")`
5. Runtime prints the chain: `c` ← `b` ← `a` ← `main`

You learn to read “who calls whom.” In Delve the `stack` command gives the same, with the ability to move frames. A panic is already a mini-debugger on stderr — but it stops *after* the failure; Delve can stop *before*.

### Example 4: Installation and first CLI session

```text
go install github.com/go-delve/delve/cmd/dlv@latest
cd path/to/module
dlv debug .
```

Inside Delve (overview — details in 03.02):

```text
break main.main
continue
next
print i
exit
```

#### What happens here

1. `dlv debug` compiles with debug info and starts the target under control.
2. `break main.main` sets a breakpoint on entry into `main`.
3. `continue` runs to the hit.
4. `next` goes line by line in the same function.
5. `print` evaluates an expression in the current frame.
6. `exit` closes the session.

That is the “hello world” of debugging. If this does not work, do not go to remote/Docker until it passes locally.

### Example 5: Goroutine mindset

```go
package main

import (
	"fmt"
	"time"
)

func worker(id int) {
	time.Sleep(time.Hour)
	fmt.Println(id)
}

func main() {
	for i := 0; i < 3; i++ {
		go worker(i)
	}
	fmt.Println("main keeps going — where are the workers?")
	time.Sleep(50 * time.Millisecond)
}
```

#### What happens here

**Trace:**

1. Loop `i = 0, 1, 2` starts three goroutines with `worker(0)`, `worker(1)`, `worker(2)`.
2. Main prints the message.
3. Main sleeps 50 ms and finishes — the process can kill workers before `time.Hour`.
4. In the debugger, after a breakpoint in `main`, `goroutines` shows main + three workers (often in sleep).

Print does not show that structurally. A concurrent program needs a view of **multiple** streams. From the first lesson build the habit: do not assume one stack.

**Note:** `go worker(i)` in a loop in Go 1.22+ uses a per-iteration variable `i` — each goroutine gets its own value. In older versions this was a classic trap; the course assumes 1.22+.

### Example 6: Same bug — three approaches

```go
package main

import (
	"encoding/json"
	"fmt"
)

type Offer struct {
	Price int `json:"price"`
	Pct   int `json:"pct"`
}

func apply(o Offer) int {
	return o.Price - o.Price*o.Pct/100
}

func main() {
	raw := []byte(`{"price":1999,"percent":15}`)
	var o Offer
	if err := json.Unmarshal(raw, &o); err != nil {
		panic(err)
	}
	fmt.Println(apply(o))
}
```

#### What happens here

**Trace:**

1. JSON has key `"percent"`, struct tag expects `"pct"`.
2. `Unmarshal` succeeds (`err == nil`), but `o.Pct` stays zero value `0`.
3. `o.Price` = `1999`.
4. `apply` computes `1999 - 1999*0/100` = `1999`.
5. Output: `1999` instead of the expected discount.

Approach A — print: `fmt.Printf("%+v\n", o)` → `Pct:0`.  
Approach B — Delve: break in `apply`, `print o` — same, without changing code.  
Approach C — test: table-driven with JSON input; the failure stays in CI.

Order: C when possible, B for investigation, A for a production signal. The real cause is the wrong JSON tag — the debugger only speeds up the insight.

## Decision analysis

| Decision | Motive |
|----------|--------|
| Delve instead of GDB for everyday Go | Better understands goroutines and the Go runtime |
| Debug info included (no strip) | Mapping to source and locals |
| Breakpoint before print for logic | Less noise in code |
| `-race` alongside the debugger | Races are not visible from the stack alone |
| Install `dlv` early | Later lessons assume the tool |
| Test + Delve instead of only log in staging | Faster feedback loop |

## Trade-offs

- **Debugger** slows and changes timing — bad as the only tool for some race reproductions.
- **Print/log** scales to production; debugger rarely there (except controlled remote — 03.03, with strict security).
- **More debug info** = larger binary.
- **Optimized build** faster, harder for step-by-step (04.01).
- Learning CLI Delve before GUI gives transferable knowledge between editors.
- Heisenbug: both print and debugger change the observer — therefore reproduce with a test when you can.

## Common mistakes

### 1. Stripped binary then “Delve does not see source”

**Wrong:**

```text
go build -ldflags="-s -w" -o app .
dlv exec ./app
```

**What happens:** no (or almost no) DWARF/symbols; lines and locals disappear or are poor.  
**Why:** you deliberately removed the map.  
**Correct:** `go build -o app .` or `dlv debug .` without strip flags.

### 2. Old `dlv` with new Go

**What happens:** strange errors at start or incomprehensible crashes.  
**Why:** Delve follows Go versions.  
**Correct:** `go install github.com/go-delve/delve/cmd/dlv@latest`, then `dlv version`.

### 3. `dlv` not on PATH

**What happens:** “dlv is not recognized” / extension cannot find the tool.  
**Why:** `go install` puts the binary in `GOPATH/bin`, and PATH is not updated.  
**Correct:** add `bin` to PATH, new terminal, `dlv version`.

### 4. Only print in concurrent code

**Wrong (mentally):** “I will add five more Println and I will see the order.”  
**What happens:** order changes; Heisenbug.  
**Why:** I/O affects scheduling.  
**Correct:** reproduce; use `-race` for races; Delve for state; structured log with request ID for production.

### 5. Debugging the wrong package

**Wrong:** `dlv debug` from the wrong directory.  
**What happens:** breakpoint “does not hit” or wrong `main`.  
**Correct:** `cd` into the module/package you actually run; e.g. `dlv debug ./cmd/api`.

### 6. Mixing production flags into a dev build

**Wrong:** same script for release and debug with `-s -w`.  
**Correct:** separate scripts `build-debug` and `build-release`.

### 7. Ignoring the panic stack

**What happens:** people immediately open Delve even though stderr already shows the exact chain.  
**Correct:** read the panic print first; Delve when you need locals *before* the crash or deeper interaction.

## Idiomatic Go

- Structured logs for production; debugger for local investigation.
- Reproduce the bug with a test when you can, then debug the test (`dlv test`).
- Keep `go.mod` and tool versions aligned.
- Document in README how the team starts debug (one command).
- Do not commit temporary `fmt.Println` from investigation — or turn them into a meaningful log with a level.

## Practical scenario

A service in staging returns the wrong discount. Dev adds 12 prints, push, waits for deploy — 40 minutes per iteration. Locally: reproduces the JSON input, `dlv debug`, breakpoint in `apply`, sees `Pct: 0` because the JSON tag does not match the field. Fix in five minutes. The team introduces a rule: first local reproduction + Delve, only then “log in staging.” Later remote debug (03.03) they use only on an isolated network, never publicly.

## Check questions

1. **Why a debugger alongside `fmt.Println`?**  
   **Answer:** Stops execution, shows locals/stack/goroutine without lasting code pollution and with controlled stepping.

2. **Does Go by default include debug info?**  
   **Answer:** Yes, unless you explicitly remove it with linker flags such as `-ldflags="-s -w"`.

3. **What is DWARF in this context?**  
   **Answer:** A debug metadata format that maps binary code to source and describes variables.

4. **Why “goroutine mindset”?**  
   **Answer:** The bug may be in another concurrent stream; looking at one stack is not enough. A goroutine is not the same as an OS thread.

5. **How do you install Delve?**  
   **Answer:** `go install github.com/go-delve/delve/cmd/dlv@latest`, then check that `dlv` is on PATH (`dlv version`).

6. **When does print still make sense?**  
   **Answer:** For a lasting production signal, latency, and environments without a debugger — not as the only tool for local logic.

7. **What is a Heisenbug in the context of print-debugging?**  
   **Answer:** A bug that changes behavior because observation (I/O, timing) changes scheduling; common in concurrency code.

## Extra analytical notes (for reinforcement)

### Comparative trace: print vs Delve on the same bug

Same program, same error (`Pct` stays 0 because of JSON tag).

**Path A — print only:**

1. You add `fmt.Printf("offer=%+v\n", o)` after `Unmarshal`.
2. `go run .` → you see `Pct:0`.
3. You delete the print or forget it in a PR.
4. Tomorrow the same pattern on another field.

**Path B — Delve without changing code:**

1. `dlv debug .`
2. `break main.apply`
3. `continue`
4. `print o` → `{Price:1999 Pct:0}`
5. `exit`
6. You fix the tag; write a test with JSON input.

Both paths lead to the same insight. Path B does not pollute the diff. Path A is faster only if you already have log infrastructure and seek a production signal.

### Table “what I look at on screen”

| Source | What it shows | What it does not show |
|--------|---------------|------------------------|
| `fmt.Println` | Text you asked for | Stack, other goroutines, conditional stop |
| Panic stderr | Stack at crash moment | Locals *before* panic without extra work |
| `-race` | Race warnings | Business logic semantics |
| Delve `locals` | Frame state | Whether that is “correct” in the domain — you judge that |
| Test failure | Expected vs got | Always the cause (sometimes you need Delve) |

### One more predict-then-answer

```go
package main

import "fmt"

func main() {
	var p *int
	fmt.Println(p == nil)
}
```

**Output prediction:** _____  

**Answer:** `true`.  
A pointer without allocation is zero value `nil`. No panic because there is no dereference (`*p`). Panic happens only when you do `*p`. A debugger on `print p` shows `nil` before someone downstream dereferences.

### Security note (bridge to 03.03)

Local `dlv debug` on your laptop is low risk. Headless Delve listening on the network is **high** risk if it is not bound to localhost or an SSH tunnel. In this lesson we do not open a port. Remember the principle ahead of time: debugger API ≈ remote process control. Details and correct patterns are in 03.03. Never practice attach on a process that is not yours.

### Brief history for context (without nostalgia)

Before Delve, people often used GDB or pure print. The Go runtime made the GDB experience awkward for goroutines. Delve was created so the debugger speaks Go’s language. That is why the course does not teach GDB for everyday work. If you ever work with cgo / native, you can expand the toolkit — but the basic path remains Delve.

## Summary

Debugging in Go starts with a mental model: debug info, stack, goroutine, breakpoint vs print. Delve is the standard debugger for Go. Install it now; the next lesson introduces concrete CLI commands and editor integration. Do not strip the binary while learning. Tell yourself: first reproduce, then observe with state, and only then expand logs. A goroutine is not an OS thread. Error values, panics, and logic bugs need different first steps — the debugger is a shared microscope, not the only tool.
