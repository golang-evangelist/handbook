# 04.02 Exploring Application State

> **Go Path - Zero to Gopher** / **01 Basics → Debugging Go Application with Delve** / Lesson 04.02

## Lesson goals

After this lesson you can:

- read `locals`, `args`, `print`, and `whatis` in a real Delve session;
- understand what `vars` adds relative to `locals` and when you need the wider list;
- conceptually understand `examinemem` (raw view of bytes) without misusing it;
- interpret **goroutine** state (the concurrent unit of the Go runtime) and stack frames;
- follow an observation checklist on every breakpoint hit;
- distinguish a nil interface, a typed nil pointer, and an ordinary zero value in the debugger.

## Prerequisite

- Delve navigation from previous lessons (03.02) and debugger architecture (04.01).
- Go 1.22+ installed; a small program with `struct`, slice, and map types.
- You know how to run `dlv debug` and stop with `break` + `continue`.

## Problem this lesson solves

A breakpoint stops you — and then what? Without a disciplined state review, you mash `continue` forever. The bug stays “somewhere in the loop,” and you waste an hour on the wrong frame or the wrong goroutine.

Investigation is not magic. Investigation is a sequence:

1. confirm which goroutine you are in;
2. confirm how you got here (`stack`);
3. read the input (`args`);
4. read temporary state (`locals`);
5. check a hypothesis (`print`);
6. change frame or goroutine if needed.

This lesson is an observation checklist. The goal is not to memorize ten commands by heart, but that after every stop you know *what* you are looking at and *why*.

## Mental model

A stack frame = the context of one function call: arguments + locals + return address.

Imagine the call `greet(u)` as a box on the table. Inside the box are:

- **args** — input (what the caller wanted: `u`);
- **locals** — temporary state (what the function computes: `msg`);
- **print expr** — an ad-hoc question (`len(s)`, `req.URL.Path`, `u.Name`);
- **whatis** — which type Delve sees for an expression;
- **vars** — a wider list (including package variables in some contexts);
- **stack / frame** — navigation through the chain of boxes;
- **goroutine** — which execution stream; same commands, different world.

`examinemem` (conceptually): when the Go view is not enough, you look at bytes at an address. Rare in everyday work. Useful when you suspect memory corruption, cgo layout, or encoding. This lesson mentions it so you know it exists — not so you use it as the first tool.

Key sentence: **the debugger shows the current snapshot**, not history. If you want “how it got here,” you use frames and hypotheses, not a magical replay.

## Mechanism

### Typical order on a hit

```text
goroutines   # where am I? which is active?
stack        # how did I get here?
args         # input into this function
locals       # state in this frame
print ...    # hypothesis (one at a time)
frame 1      # or up/down — another frame
```

Expression evaluation in Delve is **not** a full Go interpreter. Simple fields, indexes, `len`/`cap` — yes. Complex method calls, side-effect calls, generic packages — sometimes no. When `print` rejects an expression, shrink it: first `print p`, then `print p.X`, not immediately `print p.Foo().Bar()`.

### Checklist on every hit (print it)

1. Which goroutine is active?
2. What is the top of the stack (function + file:line)?
3. What do `args` say?
4. What do `locals` say?
5. Which hypothesis? Which `print` checks it?
6. Do you need an upstream `frame` (the caller)?
7. Do you need another goroutine?

If you skip 1–2, you often “fix” the wrong layer. Typical example: you look at the handler, but the error is in a SQL helper two frames down — or in a worker goroutine while you are in `main`.

### What `args` vs `locals` means exactly

`args` are the frame’s parameters. For:

```go
func greet(u User) string
```

`args` shows `u` (and possibly a named result if one exists).

`locals` are local variables *in that frame* that are live at the current line. If you stopped *before* the line `msg := ...`, `msg` may not yet exist in `locals`. That is not a Delve bug — that is an accurate snapshot of the variable’s lifetime.

### `print` as a scientific instrument

A good `print` answers **one** hypothesis:

- “Is `err` nil?” → `print err`
- “How many elements does the slice have?” → `print len(items)`
- “What is the path?” → `print r.URL.Path`

A bad `print` is a fishing expedition: `print everythingISee` until “something pops out.” Keep a WATCH list (in the editor) or a small list of expressions you repeat.

### `whatis` — the type the debugger sees

Go has static types, but an interface value carries a dynamic type. `whatis` separates:

- what you think you are looking at;
- what Delve actually sees.

Example: a variable of type `error` can hold `*os.PathError` at runtime. Without `whatis` / a detailed `print` you easily guess the wrong `fmt` or the wrong type assertion.

### Interface values under the microscope

```go
var r io.Reader = strings.NewReader("abc")
```

In the debugger you want to see three cases:

1. **both nil** — the interface is nil (`r == nil` is true);
2. **type `*strings.Reader`, value points at an object** — a normal non-nil interface;
3. **concrete type, nil pointer value** — the classic trap: `err != nil` is true even though there is “no error” in the data sense.

`whatis` + a detailed `print` separate those cases better than guessing. Remember: an interface is a pair (type, value), not a single field.

### Map and slice — what to look at

For `map[string]int`:

- does the key exist (`print m["x"]`);
- `len(m)`;
- **do not** assume iteration order — `range` is not a stable contract for order.

For a slice:

- `len` / `cap`;
- element contents (`print s[0]`);
- a shared backing array with another slice (aliasing) — bugs like “changed A, B moved.”

Delve shows you the current state. You still have to understand aliasing from the code: the debugger does not draw a “family tree” of slices for you.

### When `vars` / package variables help

A global `var clients = map[string]*Client{}` in a package: a bug “leaks” a client. `vars` or `print` of a qualified name shows the map.

Watch out: concurrent map access can still be a race. A debugger snapshot is **not** proof of safety — only a snapshot at one moment. For races use `go test -race`, not only `print`.

### JSON and the wrong field under Delve

A common “invisible” bug: the JSON key does not match the tag, so the zero value remains, and you “fix” arithmetic downstream.

```go
type In struct {
	Amount int `json:"amount"`
}
// input: {"Amount":50}  → Amount stays 0
```

Break after `json.Unmarshal`: `print v` shows `Amount:0`. State at the I/O → domain boundary reveals the contract (tags), not the formula.

### Shadowing trap

```go
func f() error {
	err := doA()
	if err == nil {
		err := doB() // new err in the inner block
		if err != nil {
			return err
		}
	}
	return err // outer err — can be nil even though doB failed in some variants
}
```

In the debugger `print err` depends on the frame **and** the scope. `list` + attention to `:=` saves hours. If you see two `err` in `locals` (depending on version / line), ask which block you are looking at.

### Watch expressions (GUI) ≈ repeated print

In VS Code WATCH you add `len(items)` and `items[0].ID`. On every stop they refresh. In the CLI you repeat `print`. Same goal: the hypothesis stays in front of your eyes.

### `examinemem` — when to even think about it

Use the Go level (`print`, `locals`) for as long as you can. Think about raw memory only when:

- you suspect corruption that types do not explain;
- you work near cgo / unsafe;
- you investigate encoding (endianness, padding) with a clear reason.

Misreading bytes is easy. Without layout knowledge, `examinemem` can mislead you more than help.

### Named results and blank identifier in the debugger

```go
func div(a, b int) (q int, err error) {
	if b == 0 {
		err = errors.New("zero")
		return
	}
	q = a / b
	return
}
```

Named results (`q`, `err`) often appear in both `args` and `locals` depending on the Delve version and stop point. The blank identifier (`_`) deliberately throws the value away — you will not find it in `locals`. If an `Unmarshal` result “disappears,” check that you did not do `_, err :=` instead of `v, err :=`.

### Channel state (brief)

For `ch := make(chan int, 2)` the debugger may show buffer length and elements (depending on version / `print`). More important than a rich display: understand whether the goroutine is **sending**, **receiving**, or **blocking**. `goroutines` + `stack` often worth more than forcing a display of the entire channel contents.

### Closure and captured variables

```go
func makeAdd(n int) func(int) int {
	return func(x int) int { return x + n }
}
```

A function literal (closure) captures `n`. When you stop inside the closure body, `print n` and `print x` should be visible. If you debug a loop that creates a goroutine per iteration, check whether you capture the **loop index** or a copy — a classic trap before Go 1.22 loops, and still relevant when you explicitly capture an address.

### How to record a finding (for a ticket)

Template after a successful state read:

```text
Location: file:line / function
Goroutine: id / role
args: ...
locals: ...
print hypotheses: ...
Conclusion: ...
Next step: test / conditional break / change
```

Without a note, tomorrow you repeat the same session. With a note, a colleague reproduces in five minutes.

### Predict-then-answer (mandatory thinking exercise)

Look at this code **before** you “debug it in your head”:

```go
func scale(xs []int, factor int) {
	for i := range xs {
		xs[i] *= factor
	}
}

func main() {
	a := []int{1, 2, 3}
	b := a[:2]
	scale(b, 10)
	// predict: a[0], a[1], a[2], len(a), len(b)
}
```

**Your prediction (write before scrolling):** `a = ???`

**Answer:** `a` becomes `{10, 20, 3}` because `b` shares the backing array with `a` for indexes 0 and 1. `len(a)=3`, `len(b)=2`. In Delve: break after `scale`, `print a`, `print b`, `print len(a)`, `print cap(a)`.

If you were wrong — that is exactly where the debugger teaches better than reading a tutorial: you see aliasing as numbers, not as theory.

### One more predict-then-answer (state)

```go
var r io.Reader
fmt.Println(r == nil) // ?
```

**Prediction:** _____  
**Answer:** `true` — both the type and the value in the interface are nil. In Delve `print r` / `whatis r` confirm it. That is not the same as a typed nil pointer in an interface that gives `r == nil` → false.

## Rules and syntax

1. First `args`/`locals`, then complex `print`.
2. Nil pointer: `print p.X` can fail — check `p != nil` first.
3. Interface value: look at the dynamic type (`whatis` / detailed print), not only “is it nil.”
4. Slice: `print s`, `print len(s)`, `print cap(s)`, `print s[0]` (when `len > 0`).
5. Do not mix goroutines: a local from A does not apply in B.
6. After `set` (lesson 04.04) state is no longer “clean” — document the experiment.
7. After `continue` always refresh the view — the frame may be different.
8. An optimized / stripped build breaks reading locals — use a debug build (see 04.01).

## Examples

### Example 1: Struct and args/locals

```go
package main

import "fmt"

type User struct {
	ID   int
	Name string
}

func greet(u User) string {
	msg := "hello, " + u.Name
	return msg
}

func main() {
	fmt.Println(greet(User{ID: 7, Name: "Marko"}))
}
```

Session:

```text
break main.greet
continue
args
locals
print u.Name
whatis u
next
locals
```

#### What happens here

- On entry into `greet`, `args` shows `u = main.User {ID: 7, Name: "Marko"}`.
- Before the line `msg := ...`, `msg` may not yet be in `locals`.
- After `next` over that line, `locals` shows `msg = "hello, Marko"`.
- `whatis u` confirms `main.User`.
- `print u.Name` → `"Marko"`.

**Execution trace (concrete values):**

| Step | Command | Expected |
|------|---------|----------|
| 1 | `break main.greet` | BP set |
| 2 | `continue` | stop in `greet` |
| 3 | `args` | `u.ID=7`, `u.Name="Marko"` |
| 4 | `print u.Name` | `"Marko"` |
| 5 | `next` (over `msg`) | PC moves on |
| 6 | `locals` | `msg="hello, Marko"` |

### Example 2: Pointer and nil check

```go
package main

func load(id int) *string {
	if id < 0 {
		return nil
	}
	s := "ok"
	return &s
}

func main() {
	p := load(-1)
	_ = p
}
```

```text
break main.main
continue
next
print p
print p == nil
```

#### What happens here

- `load(-1)` returns a nil pointer.
- `print p` shows `nil` (or an equivalent display).
- You see that `p` is nil **before** a panic happens on a dereference elsewhere.
- State > guessing: you do not have to read only a stack dump after a crash.

**Execution trace:**

| Moment | Expression | Value |
|--------|------------|-------|
| after `p := load(-1)` | `p` | `nil` |
| | `p == nil` | `true` |
| (if you did `print *p`) | evaluation error / panic as expected | — |

### Example 3: Slice in a loop

```go
package main

func sum(nums []int) int {
	total := 0
	for i, v := range nums {
		total += v
		_ = i
	}
	return total
}

func main() {
	_ = sum([]int{1, 2, 3, 4})
}
```

Breakpoint in the loop body (line `total += v`):

```text
break main.go:<line total += v>
continue
print i
print v
print total
print nums
continue
print i
print v
print total
```

#### What happens here

You confirm loop invariants. If `total` jumps strangely, you see the exact `v` of that iteration.

**Execution trace (nums = {1,2,3,4}):**

| Hit | `i` | `v` | `total` before `+=` | `total` after `+=` |
|-----|-----|-----|---------------------|---------------------|
| 1 | 0 | 1 | 0 | 1 |
| 2 | 1 | 2 | 1 | 3 |
| 3 | 2 | 3 | 3 | 6 |
| 4 | 3 | 4 | 6 | 10 |

If on the 3rd hit you see `v=99`, the bug is in the input (`nums`), not in the addition.

### Example 4: Stack frames

```go
package main

func a(x int) { b(x + 1) }
func b(x int) { c(x + 1) }
func c(x int) {
	_ = x // break here
}

func main() { a(10) }
```

```text
break main.c
continue
print x
stack
frame 1
print x
frame 2
print x
frame 0
```

#### What happens here

In `c`, `x` is 12; in the `b` frame 11; in `a` 10. Tracing the transformation through frames shows *where* the value first “went wrong” — here deliberately, step by +1.

**Execution trace:**

| Frame | Function | `x` |
|-------|----------|-----|
| 0 | `c` | 12 |
| 1 | `b` | 11 |
| 2 | `a` | 10 |
| 3 | `main` | (no `x`, call `a(10)`) |

### Example 5: Goroutine state

```go
package main

import (
	"sync"
	"time"
)

func main() {
	var wg sync.WaitGroup
	wg.Add(1)
	go func() {
		defer wg.Done()
		n := 42
		time.Sleep(time.Hour)
		_ = n
	}()
	wg.Wait()
}
```

```text
break main.main
continue
# stop during Wait (or break in the closure body)
goroutines
goroutine <id-worker>
locals
print n
goroutine 1
locals
```

#### What happens here

You learn that state lives **per goroutine**. Main has no `n`; the worker has `n=42` while sleeping. If you read `locals` in main and look for `n`, it “disappeared” — you are actually looking at the wrong stream.

**Execution trace:**

| Context | `n` in locals | Note |
|---------|---------------|------|
| main during `Wait` | does not exist | waiting for Done |
| worker during `Sleep` | `42` | lives on the worker’s stack |

### Example 6: JSON tag vs field (repeated as a state exercise)

```go
package main

import "encoding/json"

type In struct {
	Amount int `json:"amount"`
}

func parse(b []byte) (In, error) {
	var in In
	err := json.Unmarshal(b, &in)
	return in, err
}

func main() {
	v, err := parse([]byte(`{"Amount":50}`))
	_, _ = v, err
}
```

```text
break main.main
continue
# next until after parse
print v
print v.Amount
print err
```

#### What happens here

`v.Amount` is `0` (zero value), `err` is `nil`. Unmarshal “succeeded,” but the key `Amount` does not map to the tag `amount`. Without looking at state people “fix” arithmetic downstream.

**Execution trace:**

| Expression | Value | Conclusion |
|------------|-------|------------|
| `err` | `nil` | no I/O error |
| `v.Amount` | `0` | tag does not match key |
| input JSON | `{"Amount":50}` | wrong case/key |

## Decision analysis

| Decision | Motive | Alternative | Why not first |
|----------|--------|-------------|---------------|
| Checklist args→locals→print | Repeatable investigation | Immediate `continue` | You lose the signal |
| Frames before “rewrite everything” | Cause often upstream | Change only the top | Symptom ≠ cause |
| `whatis` on interface | Dynamic type | Guess the cast | Fake nil / wrong type |
| Rare `examinemem` | Only when Go view is not enough | Raw bytes always | Misinterpretation |
| `goroutines` before locals | The right stream | Read “whatever” | Wrong stack |
| Small `print` expressions | Delve is not a full interpreter | Huge expression | Evaluation fails |

## Trade-offs

- **Too many print expressions** in the GUI slow the session on every stop.
- **Trusting a stale frame** after `continue` — always refresh the view.
- **Optimized build** breaks this lesson — locals disappear or lie (see 04.01).
- **Raw memory** requires layout knowledge — easy to misread.
- **`vars` on a large package** can be noisy — filter your thinking, not only the output.
- **Snapshot ≠ race-free proof** — the debugger does not replace `-race`.

## Common mistakes

### 1. Reading a local after `stepout`

**Wrong expectation:** after `stepout` from `greet` still `print msg`.

**What happens:** `msg` no longer lives in the current frame; print fails or shows garbage/another name.

**Why:** locals are bound to the frame. When you leave, the frame is the caller’s.

**Correct:** `print` the local **before** `stepout`, or return with a break into the function.

### 2. Ignoring the active goroutine

**Wrong:** `locals` in main while the bug lives in a worker.

**What happens:** “variable does not exist” / wrong values.

**Why:** each goroutine has its own stack.

**Correct:** `goroutines` → `goroutine N` → then `locals`.

### 3. Overly complex `print`

**Wrong:** `print obj.Get().Nested().X` in one step.

**What happens:** Delve rejects it or gives a confusing error.

**Why:** evaluation is not a full Go runtime for every expression.

**Correct:** split: `print obj`, then field by field.

### 4. Mixing exported / unexported names

**Wrong:** `print u.name` for field `Name`.

**What happens:** not found / error.

**Why:** Go is case-sensitive; outside the package you only see exported names in the API (in the same package you also see unexported, but the name must be exact).

**Correct:** `print u.Name` (exactly as in the source).

### 5. Concluding from one frame without `stack`

**Wrong:** you see a bad `total` and change only the loop.

**What happens:** the real cause is bad input two frames above.

**Why:** the symptom is at the bottom; the cause is often upstream.

**Correct:** `stack` + `frame N` + caller `args`.

### 6. Looking only at `len` without contents

**Wrong:** `print len(items)` is 3 — “then it is OK.”

**What happens:** length is correct, but `items[1].ID` is wrong.

**Why:** bug in the element, not in the length.

**Correct:** `print items` or `print items[i]` for the suspicious index.

### 7. Forgetting that an interface is a pair (type, value)

**Wrong:** `print err` is “not nil” so you conclude there is a meaningful error.

**What happens:** typed nil pointer in an interface → `err != nil` while the message/behavior confuses.

**Why:** interface nil rules.

**Correct:** `whatis err` + detailed print of the dynamic type/value.

## Idiomatic Go

- Reproduce the bug with a **test**; debug the test — less state, faster restart.
- Name variables meaningfully — the debugger becomes more readable (`customerID` > `x`).
- Log a request ID; in the debugger filter with a condition (04.03) by ID.
- Prefer small functions: shorter frames, easier `args`/`locals`.
- Do not use the debugger as a substitute for clear `error` returns — the debugger explains, types keep the contract.

## Practical scenario

An API returns an empty list. Break in the handler: `args` OK (request arrived). `locals` shows `rows` as a nil slice / empty. `stack` + `frame` deeper: a SQL `Scan` error was swallowed (`_ = err` or logged and ignored). Without the checklist you would “fix” the JSON encoder. With the checklist: MTTD (mean time to detect) drops from hours to minutes.

Second layer: another goroutine fills a cache while the handler reads. `goroutines` shows the worker mid-write. The conclusion is not “JSON is slow” — but concurrency without synchronization. The debugger snapshot leads to a hypothesis; `go test -race` confirms it.

## Check questions

1. **What does `args` show?**  
   **Answer:** The arguments (parameters) of the current stack frame — the input into that function.

2. **What is `whatis` for?**  
   **Answer:** Shows the type of an expression/variable as the debugger sees it (useful for interface / dynamic type).

3. **Why change frame?**  
   **Answer:** To see the caller’s locals and arguments and determine where the value first “went wrong.”

4. **Why does goroutine context matter?**  
   **Answer:** Each has its own stack and locals; looking at the wrong stream = wrong conclusion.

5. **When do you think about `examinemem`?**  
   **Answer:** When you need a raw view of bytes because the language abstraction does not explain corruption or layout — rarely in everyday app debugging.

6. **Why can `print p.X` fail even when you “know” the struct exists?**  
   **Answer:** Because `p` is a nil pointer; first check `p`, then fields.

7. **What does `vars` add relative to `locals`?**  
   **Answer:** A wider view (including package variables in some contexts), not only the current frame’s locals.

## Summary

You read state systematically: goroutine, stack, `args`, `locals`, `print`, type (`whatis`), frame. That is the core of debugger work after a hit. Slice, map, and interface require deliberate looking (`len`/`cap`, keys, dynamic type), not only “open the Variables panel.”

Remember three disciplines: (1) checklist on every stop, (2) one hypothesis per `print`, (3) frame/goroutine before “rewrite everything.” A zero value in the output is often not “the calculation” — but input, tag, or a swallowed `error`.
