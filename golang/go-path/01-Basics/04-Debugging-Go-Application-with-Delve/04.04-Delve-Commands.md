# 04.04 Delve Commands — Systematic Overview

> **Go Path - Zero to Gopher** / **01 Basics → Debugging Go Application with Delve** / Lesson 04.04

## Lesson goals

After this lesson you can:

- use basic movement and control commands: `break`, `continue`, `next`, `step`, `stepout`;
- approach `step-instruction` carefully and know why you rarely touch it;
- restart a session (`restart`) and recompile the target (`rebuild`) when you change the source;
- work with **goroutine** (`goroutines`, `goroutine N`) as the primary concurrency model in Go;
- know that `threads` exists, but you use it rarely (cgo, OS threads);
- navigate code before you hit a line: `sources`, `funcs`, `list`;
- change state with `set` **only** as an experiment, not as a production fix;
- use `help` as the source of truth for your Delve version.

## Prerequisite

- Lessons 04.01–04.03 (architecture, state, breakpoints).
- `dlv debug` or `dlv test` works for you locally.
- You can set at least one breakpoint and read `args` / `locals` (04.02).

## Problem this lesson solves

Fragmented command knowledge leads to random clicking: `step` into the standard library forever, `si` instead of `s`, wrong goroutine, `set` then forgetting that memory is artificial. This lesson is a **systematic reference** walkthrough with examples — not an encyclopedia of every subcommand from every version, but a working set that covers most real sessions. All commands here exist in real Delve; check the form with `help` if your version differs slightly.

## Mental model

The Delve REPL is a **control panel** over one target process. Commands fall into groups:

1. **Flow control** — where to stop (`break`), how to go on (`continue`, `next`, `step`, `stepout`, rarely `step-instruction`).
2. **Observing state** — what is worth it (linked to 04.02: `print`, `args`, `locals`, `stack`).
3. **Program navigation** — which files and functions exist in the binary (`sources`, `funcs`, `list` as a source view).
4. **Concurrency** — **goroutine** (Go scheduler); `threads` are OS threads — another level, rare.
5. **Session life** — `restart`, `rebuild`, `exit` / `quit`.
6. **Mutation** — `set` changes memory in the target; it is not a substitute for changing code.
7. **Help** — `help`, `help <command>`.

```text
You (REPL)  →  Delve  →  target process (goroutine, stack, memory)
                ↑
         breakpoints from 04.03
```

A **goroutine** is not an operating system thread. The runtime maps many goroutines onto fewer OS threads. That is why for pure Go code you almost always look at `goroutines`, not `threads`.

**`step-instruction`** drops to machine instructions (one step at CPU level). Useful rarely; easy to lose mapping to the source line. For an application bug use `next` / `step`.

## Mechanism

### Flow control — working set table

| Command | Abbreviation | Role |
|---------|--------------|------|
| `break` | (sometimes `bp` in help) | Set a breakpoint (details 04.03) |
| `continue` | `c` | Continue to the next breakpoint or the end |
| `next` | `n` | Execute the current line; **does not enter** a function call |
| `step` | `s` | **Enters** a function call (including stdlib if you are on a call line) |
| `stepout` | `so` | Runs until return from the current function |
| `step-instruction` | `si` | One machine instruction |

**Rule of thumb:** until you know you need the inside of a call, use `next`. When you want to see the body of **your** function, `step`. When you entered wrongly (e.g. into `fmt.Println`), `stepout`.

### continue vs next vs step — one line of code

On the line `y := f(x)`:

- **`next` (`n`)** — execute the whole expression (the call to `f` happens “in the background” from your abstraction level); next line in the **same** function.
- **`step` (`s`)** — you stop on the **first line** inside `f` (if the symbol is available to the debugger).
- **`stepout` (`so`)** — if you are already inside `f`, you exit back to the caller on the line after the call.

This is Go level, not assembler. For assembler use `si` — and you usually regret it.

### step-instruction — caution (must read)

`step-instruction` / `si` moves the program counter by **one** CPU instruction. One line of Go code can be tens or hundreds of instructions (inlining, optimization, garbage collector helper code).

**When it makes sense (rarely):**

- suspicion of wrong codegen or optimization;
- work at the cgo / assembly boundary;
- comparison with a native debugger report.

**When it does not make sense (99% of application work):**

- business logic, HTTP handler, nil **pointer**, wrong condition;
- learning Delve — confuses more than it helps.

Mini experiment (once in a career): on a simple assignment do 20× `si` and note how many times `list` still shows the “same” line. Then do one `next`. The difference in time and mental load is the lesson.

### Session: restart, rebuild, exit

| Command | Role |
|---------|------|
| `restart` | Restarts the target of the **same** binary; breakpoints in the session usually stay |
| `rebuild` | Recompiles the program (when Delve/mode supports it in your setup) then restarts |
| `exit` / `quit` | Ends the Delve session |

**`restart`** resets the program’s **runtime state**: variables, open connections, in-memory cache. It does not redeploy a Docker image and does not change a remote server — that is a local (or attach) target.

**`rebuild`** use when you changed a `.go` file and want the debugger to see new code without a manual `exit` + new `dlv debug`. On large modules rebuild can be slow; it is still faster than losing breakpoint context.

Flow after changing a hypothesis:

```text
# wrong input in args
restart
# or
rebuild   # if you changed the source
continue
```

### Concurrency: goroutines (primary), threads (rare)

| Command | Role |
|---------|------|
| `goroutines` | List of goroutines (ID, state, location) |
| `goroutine N` | Switch the debugger **context** to goroutine N |
| `threads` | OS threads — lower level |

**Why goroutine first:** Go code runs in goroutines. `main` is a goroutine. Every `go func()` adds a goroutine. Deadlock, leak, or “who holds the mutex” you almost always solve by switching to the right goroutine and looking at `stack` / `locals` **in that context**.

**When `threads`:**

- cgo calls a C library that blocks an OS thread;
- suspicion of a problem outside the Go scheduler;
- comparison with a tool report that talks about threads.

Otherwise the thread list confuses: the runtime holds more M/P/G relationships; thread count ≠ goroutine count.

**Context mistake:** you read `locals` while in goroutine A, thinking you are in B — the conclusion is false. Always `goroutine N` then `stack`, then `locals`.

### Navigation: sources, funcs, list

| Command | Role |
|---------|------|
| `sources` | List of source file paths in debug information |
| `funcs` | List of functions; often with a regex filter |
| `list` | Show a **view** of source around the current location (PC) |

Typical flow when you do not know the line:

```text
funcs Apply
funcs \.ApplyCredit
break github.com/org/app/internal/billing.(*Service).ApplyCredit
list
continue
```

**`list`** gives a view — it does not open an editor. Confirms you are on the function body, not on a declaration or wrong symbol. A **pointer receiver** in the method name (`(*Service)`) must exactly match the symbol from `funcs`.

**`sources`** helps when a breakpoint says “unbound” — whether the file is even in the build (build tags, another package).

### Mutation: set (experiment only)

```text
set n = 2
set u.Name = "test"
set *p = 42
```

`set` writes into the target process memory. Use it to **confirm a hypothesis** (“if n were 2, branch B would pass”). Do not mentally commit “the fix is set in the debugger.”

After `set`:

- invariants can be broken (e.g. cache and field disagree);
- a remote session on a shared environment can damage someone else’s tests;
- race timing changes — a heisenbug can “disappear.”

Real fix: change the source + test. `set` is a lab.

### help — first ally

```text
help
help next
help goroutines
help set
```

Delve documents itself locally. A web blog can be outdated; **`help` in your installation** is the source of truth for aliases, `rebuild` support, and the exact form of `condition`.

Habit: before you type an exotic command, `help <name>`.

### Abbreviations worth remembering

```text
c   continue
n   next
s   step
so  stepout
si  step-instruction
```

Check `help` — alias lists depend on version, but `c` / `n` / `s` / `so` are stable habits in CLI sessions.

### Command learning order (suggested five days)

| Day | Focus |
|-----|-------|
| 1 | `break`, `continue`, `next`, `print`, `exit` |
| 2 | `step`, `stepout`, `args`, `locals`, `stack` |
| 3 | `goroutines`, `goroutine`, conditional BP from 04.03 |
| 4 | `sources`, `funcs`, `list`, `restart` |
| 5 | `set` (experiment), deliberate avoidance of `si` |

Do not learn everything at once. This order follows real sessions from “stop in main” to “I found the hanging goroutine.”

### threads vs goroutines — decision table

| Question | Answer |
|----------|--------|
| Debugging a pure Go HTTP server | `goroutines` |
| Suspect deadlock between two goroutines | `goroutines` + `goroutine N` + `stack` |
| cgo / SQLite driver “blocks” | maybe `threads` + `goroutines` |
| Blog says “look at thread 3” | check whether it is the Go or C part |

### Predict-then-answer #1 — next or step?

Code:

```go
package main

import "fmt"

func inner(v int) int { return v * 2 }

func main() {
	x := inner(3)
	fmt.Println(x)
}
```

You stand on the line `x := inner(3)` in `main`. You type **`step`**. **Where are you after one step?**

**Prediction:** ???

**Answer:** In the body of function `inner` (first executable line in `inner`), with `v=3` in `args`. **`next`** would stay in `main` and assign `x=6` without stopping in `inner`.

### Predict-then-answer #2 — stepout

Continuation: you are inside `inner`, on `return v * 2`. One **`stepout`**. **Where are you?**

**Prediction:** ???

**Answer:** Back in `main`, on the line after the call `inner(3)` (usually `fmt.Println` or the assignment finished — depending on optimization; `list` confirms). `print x` may already be `6`.

### Predict-then-answer #3 — goroutine

```go
go worker()
go worker()
// main waits
```

In `main` you stopped with a breakpoint. **`goroutines`** shows at least three active (main + two workers). You switch to **`goroutine 2`**. **`locals` in the main goroutine** — are they still visible?

**Prediction:** ???

**Answer:** Not in the sense of the “current frame” — the context is goroutine 2. For main you must **`goroutine 1`** (check the ID in the list; numbers are not always 1/2/3). This is the classic context mistake.

### Predict-then-answer #4 — restart and set

You did `set n = 99`, then **`restart`**. **Is n still 99?**

**Prediction:** ???

**Answer:** No — restart runs the program again; memory is fresh. Breakpoints often stay; **`set` mutation does not**.

### funcs → break → list (working ritual)

```text
(dlv) funcs Handler
(dlv) break main.(*Server).Handler
(dlv) list
(dlv) continue
```

The ritual prevents a break on the wrong symbol (value vs pointer **receiver**, wrong package).

### What `list` does not do

- Does not change the execution line.
- Does not replace the IDE (04.05) — but in an SSH session without UI, `list` is gold.

### exit without notes

`quit` before you write `stack` / `print` = you repeat the reproduction tomorrow. Minimum: one line of conclusion in the ticket before `exit`.

### Terminology (Go and English)

- **Goroutine** — lightweight concurrent unit in the Go runtime; do not confuse with OS threads.
- **receiver** — `(*T)` in the method name in `funcs` / `break`.
- **pointer** — Delve shows addresses; dereference in `print` / `set` carefully.
- **zero value** — `nil` interface / pointer / map; common panic cause (04.03 unrecovered).
- **interface** — a dynamic value has a type and a data part; `print` helps when you are not sure what it holds.
- **closure** — a goroutine captures variables from outside; `locals` shows copies/heap.
- **`list`** — shows source around the current line (not a Go slice type).
- **inlining** — the compiler can embed a function body into the caller; `step` behavior can surprise — hence `list` + `funcs`.

### Wrap-up bridge before Rules

When you master flow control + goroutine + navigation, editor integration (04.05) becomes only another client of the same ideas. CLI remains the diagnosis when F5 lies.

## Rules and syntax

1. Prefer `next` over `step` until you deliberately enter **your** function or test.
2. Use `step-instruction` (`si`) only when you need machine level — otherwise you lose source-line context.
3. After `set`, mark the session as experimental; the real fix goes into source + `go test`.
4. Before reading `locals` of another goroutine always `goroutine N` — do not mix contexts.
5. `restart` resets program state; breakpoints in the session usually stay; `set` does not survive restart.
6. Use `funcs` / `sources` / `list` when you do not know the exact line — instead of guessing a line number.
7. For concurrency in Go: **`goroutines`**, not `threads`, except rare cgo cases.
8. Always check `help <cmd>` for nuances of your Delve version — do not trust an outdated blog.
9. `rebuild` after changing a `.go` file; `restart` when you change only input/state, not code.
10. `exit` only after a note — at least stack + conclusion.

## Examples

### Example 1: Basic cycle break → args → next → stepout

```go
package main

func add(a, b int) int {
	return a + b
}

func main() {
	x := add(2, 3)
	_ = x
}
```

```text
(dlv) break main.add
(dlv) continue
(dlv) args
(dlv) next
(dlv) stepout
(dlv) continue
```

#### What happens here

Classic loop: stop in the called function, look at input, execute the body one line (`next` inside), return to the caller (`stepout`), finish the program. This is the backbone of a CLI session.

**Execution trace:**

| Step | Command | Location (approx.) | Values / note |
|------|---------|--------------------|---------------|
| 1 | `break main.add` | BP on symbol | — |
| 2 | `continue` | inside `add` | `args`: `a=2`, `b=3` |
| 3 | `next` | on `return` or after | expression `a+b` → `5` |
| 4 | `stepout` | in `main` after the call | `print x` → `5` (after assignment) |
| 5 | `continue` | end | process finished |

### Example 2: step vs next on the same line

```go
package main

func scale(n int) int {
	return n * 10
}

func main() {
	v := scale(4)
	_ = v
}
```

Stop in `main` on the line `v := scale(4)`.

```text
(dlv) break main.main
(dlv) continue
(dlv) list
# A) next
# B) step — repeat session restart then B)
```

#### What happens here

- **`next`:** you stay in `main`; `v` becomes `40` without entering `scale` with a stop.
- **`step`:** you enter `scale`; you see `n=4` in `args`.

**Execution trace (step path):**

| Step | Action | `v` in main | `n` in scale |
|------|--------|-------------|--------------|
| stop in main | `list` | undefined / 0 | — |
| `step` | entry | — | `4` |
| `stepout` | return | `40` | — |

### Example 3: step-instruction caution (deliberately short)

On any assignment do **`si`** five times in a row, then **`list`**.

#### What happens here

The program counter moves by instructions; `list` may still show the same Go source line. That explains why `si` is not a tool for an everyday bug in a handler or **interface** branching.

**Execution trace:**

| `si` # | Typical behavior |
|--------|------------------|
| 1–5 | same source view; mental loss of context |
| after `n` | one Go line — you return to productivity |

### Example 4: restart and rebuild

```text
(dlv) break main.main
(dlv) continue
(dlv) set v = 100    # experiment — if v exists in scope
(dlv) restart
(dlv) continue
(dlv) print v
```

After changing a file on disk:

```text
(dlv) rebuild
(dlv) continue
```

#### What happens here

`restart` clears the effect of `set`. `rebuild` imports new code — a breakpoint on a symbol usually stays; line numbers may have moved.

**Execution trace:**

| Event | `v` after | Breakpoints |
|-------|-----------|-------------|
| after `set v=100` | `100` (artificial) | active |
| after `restart` | initial value from code | usually active |
| after `rebuild` | depends on new code | check `breakpoints` |

### Example 5: funcs, sources, list

```text
(dlv) sources
(dlv) funcs main\.
(dlv) funcs scale
(dlv) break main.scale
(dlv) list
(dlv) continue
```

#### What happens here

You do not guess line 42 in a file you have not opened. `sources` confirms that `main.go` is in the binary. `list` gives a body view before you spend time on the wrong symbol.

**Execution trace:**

| Command | Expected outcome |
|---------|------------------|
| `funcs scale` | `main.scale` |
| `break main.scale` | bound BP |
| `list` | body with `return n * 10` |
| `continue` | stop in `scale` |

### Example 6: Goroutine (not threads)

```go
package main

import (
	"sync"
	"time"
)

func worker(id int, wg *sync.WaitGroup) {
	defer wg.Done()
	time.Sleep(50 * time.Millisecond)
	_ = id
}

func main() {
	var wg sync.WaitGroup
	for i := 1; i <= 2; i++ {
		wg.Add(1)
		go worker(i, &wg)
	}
	wg.Wait()
}
```

```text
(dlv) break main.main
(dlv) continue
(dlv) goroutines
(dlv) goroutine 3
(dlv) stack
(dlv) locals
(dlv) threads
```

#### What happens here

`goroutines` shows main and worker goroutines. **`goroutine N`** switches context — then `stack` belongs to that goroutine. `threads` is optional: you see OS threads the runtime runs on; for this pure Go example you do not solve the bug via `threads`.

**Execution trace:**

| Context | `stack` (top) | Note |
|---------|---------------|------|
| main | `main.main` | waiting on `Wait` |
| worker goroutine | `main.worker` | `id` in `args` |
| wrong: locals in main while looking at worker | false conclusion | always switch `goroutine` |

### Example 7: set as experiment (not fix)

```go
package main

func mustEqual(n int) {
	if n != 2 {
		panic("n is not 2")
	}
}

func main() {
	n := 1
	mustEqual(n)
}
```

```text
(dlv) break main.main
(dlv) continue
(dlv) next
(dlv) print n
(dlv) set n = 2
(dlv) continue
```

#### What happens here

You confirm: “if n were 2, the panic would not happen.” That validates the hypothesis before changing code. Then fix the source — assignment `n := 2` or the logic — **`set` is not a fix**.

**Execution trace:**

| Moment | `n` | Outcome |
|--------|-----|---------|
| after `next` | `1` | — |
| after `set n=2` | `2` (mutated) | — |
| `continue` | `2` | no panic |
| after `restart` without code fix | `1` | panic again |

## Decision analysis

| Decision | Motive | When not |
|----------|--------|----------|
| Abbreviations `c` / `n` / `s` | Speed in CLI | When learning the first time — write full names |
| Avoid `si` by default | Less noise, source line | Machine / cgo investigation |
| `funcs` before guessing a line | Exact symbol, pointer receiver | When you already stand on a line in the editor |
| `set` only as experiment | Control the science of the bug | Never as a “deploy fix” |
| `goroutine` > `thread` for Go | Real concurrency model | cgo blocking an OS thread |
| `restart` instead of new `dlv` | Breakpoints stay | When you need a completely different binary |
| `list` after break on symbol | Location confirmation | — |

## Trade-offs

- **`restart`** loses runtime state (TCP connections, in-memory cache) — sometimes you must manually reproduce to the point.
- **`rebuild`** slower on a large module; still cheaper than losing the BP set.
- **`set`** can leave inconsistent invariants (two fields that must stay aligned).
- **`step`** into stdlib — you quickly enter foreign code; **`stepout`** is the rescue.
- Too much reliance on command memory — keep a cheat sheet in module 04 notes.
- **`threads`** list can confuse — use it with purpose, not from curiosity.

## Common mistakes

### 1. step into the standard library forever

**Wrong:** on `fmt.Println` you do `step` and keep `step` through fmt.

**What happens:** you get lost in foreign code; the ticket stays empty.

**Why:** `step` enters the call.

**Correct:** `next` over the call; or `stepout` back to your package.

### 2. step-instruction by mistake instead of step

**Wrong:** you type `si` thinking it is the abbreviation for `step`.

**What happens:** hundreds of steps without Go semantics.

**Why:** `si` = instruction, not function.

**Correct:** `s` for step; `si` only deliberately.

### 3. set then forgetting state is artificial

**Wrong:** “works in the debugger” then merge without changing code.

**What happens:** production still crashes; a colleague cannot reproduce the “fix.”

**Why:** `set` does not change the binary on disk.

**Correct:** confirm hypothesis → change source → test → commit.

### 4. Wrong goroutine ID

**Wrong:** `goroutine 2` because “second worker” without the list.

**What happens:** you look at the wrong `stack` / `locals`.

**Why:** IDs are assigned by the runtime; they are not always 1,2,3.

**Correct:** `goroutines` → find the location → exact ID.

### 5. locals without switching goroutine

**Wrong:** worker hangs, but you read `locals` in main context.

**What happens:** “nothing suspicious” — false.

**Why:** locals are per goroutine / frame.

**Correct:** `goroutine N` then `stack` then `locals`.

### 6. break on a regex that hits too many funcs

**Wrong:** `funcs HTTP` then break on the first hit without `list`.

**What happens:** you stop in the wrong handler.

**Why:** the same word in multiple symbols.

**Correct:** narrow the regex; `list`; function break with full name.

### 7. Expecting that restart redeploys remote

**Wrong:** attach to staging; `restart` expects a new Docker image.

**What happens:** the same old binary in the container.

**Why:** `restart` = restart of the **current** target.

**Correct:** new image/deploy; locally `rebuild` after changing code.

### 8. quit without notes

**Wrong:** `exit` as soon as you see the bug.

**What happens:** the exact `stack` and values are lost.

**Why:** the session is ephemeral.

**Correct:** ticket note template then `quit`.

## Idiomatic Go

- Pair commands with the checklist from 04.02 (`args`, `locals`, `stack` after every stop).
- For libraries without `main`: `dlv test` + the same `next` / `step` / `goroutines`.
- Nil **pointer** / **zero value** map: break + `print` before access; goroutine that writes to a map — check both sides via `goroutine`.
- **closure** in a goroutine: check captured variables in `locals` — a common source of race logic.
- Do not commit a “fix” that exists only as `set` in a session.

## Practical scenario

During an incident an engineer uses `funcs Invoice` to find `(*Service).ApplyCredit`, `break`, `continue`, `args`. Enters stdlib by mistake with `step`; **`stepout`** returns focus. Two goroutines: **`goroutines`**, **`goroutine 12`**, sees a stuck mutex in `stack`. Temporarily **`set`** a flag to confirm a branch; **`rebuild`** with the real patch after the test. Nobody touched `si` — correctly. The ticket contains the goroutine ID and a `list` view, not only “concurrency bug.”

## Check questions

1. **What does `stepout` do?**  
   **Answer:** Continues execution until the current function returns to the caller; you stop on the line after the call in the caller.

2. **Difference between `next` and `step` on a line with a function call?**  
   **Answer:** `next` executes the whole line without entering the callee with a stop; `step` enters the callee and stops on the first line inside (if the symbol is available).

3. **When do you use `step-instruction`?**  
   **Answer:** Rarely — for machine instruction level; not for ordinary application bugs in Go code.

4. **Difference between `restart` and `rebuild`?**  
   **Answer:** `restart` runs the existing binary again; `rebuild` recompiles the changed source (when supported) then usually restarts.

5. **Why `goroutine N`?**  
   **Answer:** Switches the debugger context to the chosen goroutine so `stack` and `locals` are meaningful for that concurrent unit.

6. **Why not start with `threads` in a pure Go service?**  
   **Answer:** The Go model is goroutine; OS threads are a lower level and are rarely the first answer for business logic.

7. **What is `funcs` for?**  
   **Answer:** Finds the exact symbol name (including pointer receiver) before `break`.

8. **What is `list` for?**  
   **Answer:** Shows source around the current location — confirmation that you are in the right place.

9. **What is `set` for?**  
   **Answer:** Changes a value in target memory for an experiment / hypothesis confirmation — not as a lasting fix.

10. **Does `set` survive `restart`?**  
    **Answer:** No; restart runs the program again with initial state from the code.

11. **What is the source of truth for command syntax?**  
    **Answer:** `help` / `help <command>` in your Delve installation.

12. **What does `continue` do?**  
    **Answer:** Continues execution to the next breakpoint, signal event, or end of the process.

## Summary

Working Delve vocabulary for everyday Go development: flow control (`break`, `continue`, `next`, `step`, `stepout`), careful `step-instruction`, session life (`restart`, `rebuild`), **goroutine** as the primary concurrency view, navigation (`sources`, `funcs`, `list`), experimental `set`, and `help` for the version.
