# 04.05 Editor Integration with Delve

> **Go Path - Zero to Gopher** / **01 Basics → Debugging Go Application with Delve** / Lesson 04.05

## Lesson goals

After this lesson you can:

- configure the **VS Code Go extension** for debugging and test debug;
- write `launch.json` configurations: **launch** of a package (`mode: debug`), **test** (`mode: test`), **attach** (`mode: remote` / local);
- use the UI for breakpoints (gutter), conditions, and logpoints;
- distinguish **Debug Console** (DAP evaluation) from a full Delve REPL in the CLI;
- know that **GoLand** offers a similar model (briefly) — the same Delve underneath;
- attach remotely **defensively**: localhost / known dev port, not random production hosts.

## Prerequisite

- CLI Delve knowledge (04.04) — the editor is a **client**, not another debugger.
- VS Code (or a compatible fork) + the official **Go** extension (Go team at Google).
- `dlv` on PATH (`go install github.com/go-delve/delve/cmd/dlv@latest` or Install Tools).
- Go 1.22+ on PATH.

## Problem this lesson solves

Teams live in the editor. If `launch.json` lies (`program` points at the wrong folder), “the debugger does not work” even though Delve is healthy. Mixing **Debug Console** with expectations of a full REPL (`goroutines` as text) confuses. Attach to the wrong port or to an internet-facing server without control is both a security and an operational risk. This lesson connects the UI to the model you already know from the CLI — same target, same breakpoints, different UX.

## Mental model

```text
UI (gutter breakpoint, F5, Variables / Call Stack panels)
        ↓
Go extension (DAP adapter — Debug Adapter Protocol)
        ↓
Delve API
        ↓
Target process (goroutine, stack, memory)
```

**launch** = start a **new** target under Delve (`request: launch`, `mode: debug` or `test`).

**attach** = connect to an **existing** process (`request: attach`, `mode: local` or `remote`).

**Debug Console** — expression evaluation in the context of the current frame (e.g. `myVar`, `len(s)`). Not 1:1 with all `dlv` commands; flow control goes through toolbar buttons (Continue, Step Over = `next`, Step Into = `step`).

**GoLand** — JetBrains Run/Debug configurations instead of JSON; same concepts: breakpoint, step, Variables, Goroutines panel. Delve is still the engine for Go.

**Defensive attach practice:** remote attach only on **`127.0.0.1`** / a known dev port (e.g. headless `dlv` from 03.x), with awareness that you open a debug port only locally or through an SSH tunnel — not to production without an explicit process and permissions.

## Mechanism

### Installation and tools

1. Install the **Go** extension (official).
2. Command Palette: **Go: Install/Update Tools** — include `dlv`.
3. Terminal: `dlv version` — must work outside VS Code.
4. After upgrading Go, repeat Install/Update Tools.

Without `dlv` on PATH, F5 often fails with “cannot find dlv” — that is not a bug in your code.

### launch.json — basic structure

File: `.vscode/launch.json` (the team can commit it **without secrets**).

```json
{
  "version": "0.2.0",
  "configurations": []
}
```

Each item in `configurations` has `"type": "go"` and `"request": "launch"` or `"attach"`.

### Pattern: debug a package (main)

```json
{
  "name": "Debug package",
  "type": "go",
  "request": "launch",
  "mode": "debug",
  "program": "${workspaceFolder}/cmd/api"
}
```

`program` must point at the package directory with `func main()` (or at `.` if main is at the module root).

CLI equivalent:

```text
dlv debug ./cmd/api
```

### Pattern: debug a test

```json
{
  "name": "Debug test",
  "type": "go",
  "request": "launch",
  "mode": "test",
  "program": "${workspaceFolder}/internal/billing",
  "args": ["-test.run", "TestApplyCredit"]
}
```

Equivalent:

```text
dlv test ./internal/billing -- -test.run TestApplyCredit
```

Break in the test function or in the code under test — the same `next` / `step` as in 04.04.

### Pattern: attach remote (localhost)

```json
{
  "name": "Attach remote (local only)",
  "type": "go",
  "request": "attach",
  "mode": "remote",
  "host": "127.0.0.1",
  "port": 2345
}
```

The target must already be listening (headless Delve). **Keep the host on loopback** unless you explicitly build an SSH tunnel and understand the risk.

**Defense:** do not commit a `host` that points at a public production IP; do not share a debug port with the internet without a firewall and agreement.

### Pattern: args and env (no secrets in git)

```json
{
  "name": "api local",
  "type": "go",
  "request": "launch",
  "mode": "debug",
  "program": "${workspaceFolder}/cmd/api",
  "args": ["-addr", ":8080"],
  "env": {
    "APP_ENV": "dev",
    "LOG_LEVEL": "debug"
  }
}
```

Put API keys in a local override (User settings, `.env` in `.gitignore`) — not in committed JSON.

### Multiple configurations in one repo

```json
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "api",
      "type": "go",
      "request": "launch",
      "mode": "debug",
      "program": "${workspaceFolder}/cmd/api"
    },
    {
      "name": "worker",
      "type": "go",
      "request": "launch",
      "mode": "debug",
      "program": "${workspaceFolder}/cmd/worker"
    },
    {
      "name": "test billing",
      "type": "go",
      "request": "launch",
      "mode": "test",
      "program": "${workspaceFolder}/internal/billing"
    },
    {
      "name": "attach docker (localhost)",
      "type": "go",
      "request": "attach",
      "mode": "remote",
      "host": "127.0.0.1",
      "port": 2345
    }
  ]
}
```

The dropdown next to **F5** selects the configuration — the name should be clear to a new team member.

### UI breakpoints

- Click on the **gutter** (left of the line number) = ordinary breakpoint.
- Right click: **Conditional Breakpoint**, **Logpoint** (trace-like message).
- **Breakpoints** panel = list like `breakpoints` in the CLI (enable/disable, condition).

A function breakpoint from the UI depends on the extension version; you can always break in code + CLI `break main.Handler` if you need a symbol.

### Panels during a session

| Panel | CLI approximate |
|-------|-----------------|
| VARIABLES | `locals`, `args` (current frame) |
| WATCH | repeated `print` expressions |
| CALL STACK | `stack`, frame switching |
| Goroutines (where present) | `goroutines`, `goroutine N` |
| DEBUG CONSOLE | expression evaluation, not a full REPL |

Clicking a frame in Call Stack changes context — analogous to changing frame in Delve.

### Debug Console vs Delve CLI

| Action | Debug Console | `dlv` REPL |
|--------|---------------|------------|
| `myVar`, `p.x` | yes | `print` |
| `len(slice)` | often yes | `print len(slice)` |
| `continue` as text | not reliably | `continue` / `c` |
| `goroutines` | usually no | `goroutines` |
| `funcs` regex | no | `funcs` |
| `set` | limited / depends | `set` |

**Rule:** do flow control with the toolbar / F10 F11; advanced navigation and goroutine — CLI in a parallel terminal attached to the same session **or** a dedicated Goroutines UI.

### go.delveConfig and PATH

In Settings:

- path to `dlv` if it is not global;
- `go.delveConfig` — extra flags (e.g. `--check-go-version=false` only if you understand the risk);
- after a Go upgrade: Install/Update Tools.

### When the GUI lies, the CLI tells the truth

Symptoms:

- breakpoint gray / **unbound**;
- F5 starts the wrong package;
- Variables empty while the line is clearly executable.

Action:

1. `dlv version`
2. `dlv debug` on the **same** `program` path as in launch.json
3. same break — if CLI works, the problem is launch path / multi-root / extension
4. if CLI does not work, the problem is build / DWARF / code / tags

### GoLand (briefly)

Run → Edit Configurations → **Go Build** / **Go Test**. Breakpoint in the gutter. Debug icon. Variables, Goroutines, Evaluate Expression panels ≈ Debug Console. Same Delve background; learned quickly if you know the VS Code concepts from this lesson. Team IDE choice does not change the mental model from 04.01–04.04.

### Compound launch (note)

VS Code `compounds` can start api + worker. Two processes = two debug sessions — like two `dlv` terminals. Do not mix breakpoints between processes.

### Test Explorer vs launch test

“Debug Test” above `func TestX` builds a similar configuration to `mode: test`. Use whichever is faster; understand the JSON when the UI hits the wrong package in a multi-module repo.

### Quick F5 diagnosis

| Symptom | Check |
|---------|-------|
| cannot find dlv | PATH / Install Tools |
| unbound breakpoint | `program`, build tags |
| wrong main | `program` in launch.json |
| attach timeout | port, headless, firewall |
| empty variables | strip binary, optimization |
| trust workspace | VS Code Workspace Trust |

### Predict-then-answer #1 — which mode?

You want to debug **one** test function in package `internal/tax`. **`mode`** in launch.json?

**Prediction:** ???

**Answer:** `"mode": "test"` with `"program"` on the package folder and `args` with `-test.run` and the test name.

### Predict-then-answer #2 — attach host

A colleague proposes `"host": "production.example.com", "port": 2345` in shared `launch.json`. **What do you do?**

**Prediction:** ???

**Answer:** Do not commit; attach only on **127.0.0.1** or a tunnel; production requires a separate process, permissions, and usually is not Delve headless on a public port. Defense: local / staging under control.

### Predict-then-answer #3 — Debug Console

In Console you type `goroutines` and nothing meaningful. **Why?**

**Prediction:** ???

**Answer:** Console is not a full CLI; use the Goroutines panel or a terminal with `dlv connect`.

### Predict-then-answer #4 — Variables empty

The breakpoint hits, but VARIABLES is empty. One common build cause?

**Prediction:** ???

**Answer:** Binary without debug information (strip, wrong build flag) — check that the debug build goes through the extension / `go build -gcflags` as the extension expects; compare with `dlv debug` CLI.

### Terminology

- **Goroutine** — display in Call Stack / Goroutines panel; do not confuse with OS threads.
- **interface** — in Debug Console `print` of a dynamic type value.
- **pointer** — Watch on `*p` carefully; zero value in Console can look like `nil`.
- **receiver** — breakpoint on a method must match pointer/value receiver in the symbol.
- **`list` / editor view** — source view around the line; CLI equivalent is `list`.
- **inlining** — step in optimized code can skip expected lines; in both UI and CLI.
- **closure** — goroutine in the Goroutines panel + locals in the frame.

### Workspace Trust and folders

VS Code **Workspace Trust** can block starting the debugger until you confirm the folder. On Windows antivirus sometimes slows the first attach — that is not the same as “wrong `program`,” but the symptom can look similar (timeout). Order: trust → `dlv version` → F5 → only then AV exceptions per team policy.

### Multi-root workspace and ${workspaceFolder}

In a repo with `frontend/` and `backend/go-mod/` a breakpoint in a Go file must be in a folder opened as root **and** `program` must point at that module. If you open the parent monorepo, `${workspaceFolder}` can be the parent — and `main` in `services/billing/cmd`. Solution: a named configuration with a full relative path or open the Go module as a separate workspace root.

### buildTags in launch.json

When you use build tags (`//go:build integration`), the debug build must include the same tags as the failing test. The Go extension supports `buildFlags` / env in the launch config (check your version’s docs). Otherwise a breakpoint in a tagged file stays outside the binary — same as in the CLI when `sources` does not list the file.

### substitutePath (remote / container)

When source in the container differs from the path on the laptop, some setups use path mapping (DAP `substitutePath` or equivalent in settings). Attach to localhost Docker still requires that the editor sees the **same** lines as DWARF. If the stack shows `/app/main.go` and you only have `cmd/api/main.go` locally, you need mapping — otherwise a gutter break does not hit.

### Step-by-step: first successful F5 (checklist)

1. Open the module with `go.mod`.
2. Install/Update Tools → `dlv`.
3. Create `.vscode/launch.json` with the correct `program`.
4. Set a break on an executable line in that package.
5. F5 → choose the configuration.
6. Check VARIABLES; Continue.
7. If fail: terminal `dlv debug <same path>`.

### Step-by-step: first attach (checklist)

1. Start headless only on **127.0.0.1** (or Docker `-p 127.0.0.1:2345:2345`).
2. Check `curl` / telnet on the port (optional).
3. VS Code attach config with the same host/port.
4. Break in a handler that will definitely be called.
5. Generate traffic.
6. If timeout: firewall, wrong port, process is not headless.

### What to commit in .vscode

| File | Commit? |
|------|---------|
| `launch.json` without secrets | often yes |
| `settings.json` with delve path | team agreement |
| personal breakpoint state | no |
| `.env` with API key | no (gitignore) |

### Linking to 04.04 commands in the UI

| Delve CLI | VS Code (typical) |
|-----------|-------------------|
| `continue` / `c` | Continue (F5) |
| `next` / `n` | Step Over (F10) |
| `step` / `s` | Step Into (F11) |
| `stepout` / `so` | Step Out (Shift+F11) |
| `restart` | Restart (Ctrl+Shift+F5) |
| `break` | gutter / Breakpoints panel |

Debug Console is not a column in this table — that is evaluation, not flow control.

## Rules and syntax

1. `"type": "go"` required for the Go extension — do not mix with other debugger types.
2. `program` must point at the package you build (dir with `main` or a test package).
3. Do not keep secrets in committed `env` in `launch.json` — local override or `.gitignore`.
4. Logpoint / trace in the UI ≠ production structured log.
5. When the UI sticks, reproduce in the CLI (`dlv debug` / `dlv test`) — you isolate the layer (extension vs code).
6. **Attach remote:** prefer `127.0.0.1`; public host only with tunnel, permission, and audit.
7. GoLand: same discipline — debug build, not a release strip binary.
8. Breakpoint on a line must be in a file that is in the build (build tags).
9. Multi-root workspace: check which folder is `${workspaceFolder}` for `program`.
10. Debug Console: evaluation, not a substitute for `funcs` / `goroutines` in the CLI.

## Examples

### Example 1: Minimal launch + gutter breakpoint

`main.go` at the module root:

```go
package main

import "fmt"

func main() {
	msg := "hello debug"
	fmt.Println(msg)
}
```

`.vscode/launch.json`:

```json
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "Debug root main",
      "type": "go",
      "request": "launch",
      "mode": "debug",
      "program": "${workspaceFolder}"
    }
  ]
}
```

Gutter break on the assignment `msg := ...`, **F5**, VARIABLES panel.

#### What happens here

Equivalent to `dlv debug .` + `break main.main` + `continue`. The UI sends DAP requests; Delve stops the target.

**Execution trace:**

| Step | UI / action | State |
|------|-------------|-------|
| F5 | launch | process start |
| hit BP | editor focuses line | pause |
| VARIABLES | automatic | `msg` = `"hello debug"` |
| Continue (F5) | DAP continue | print in terminal |

### Example 2: Debug a single test

```go
package tax

import "testing"

func VAT(cents int) int {
	return cents * 20 / 100
}

func TestVAT(t *testing.T) {
	if VAT(1000) != 200 {
		t.Fatalf("bad vat")
	}
}
```

Launch:

```json
{
  "name": "Debug TestVAT",
  "type": "go",
  "request": "launch",
  "mode": "test",
  "program": "${workspaceFolder}/internal/tax",
  "args": ["-test.run", "^TestVAT$"]
}
```

Break inside `VAT`, F5.

#### What happens here

Equivalent to `dlv test ./internal/tax -- -test.run TestVAT`. Fastest path for a package without `main`.

**Execution trace:**

| Frame | WATCH / VARIABLES | Note |
|-------|-------------------|------|
| `TestVAT` | `t` | test context |
| `VAT` | `cents=1000` | business logic |
| after return | result `200` | assert passes |

### Example 3: Conditional breakpoint in the UI

On a line in a handler: right click → **Add Conditional Breakpoint** → `path == "/admin"`.

Generate traffic on `/ok` and `/admin`.

#### What happens here

Same concept as `condition` in the CLI (04.03). The UI stores the condition in workspace breakpoint state — be careful not to commit personal conditions if the team does not want that.

**Execution trace:**

| Request | Condition | Stop in editor? |
|---------|-----------|-----------------|
| GET `/ok` | false | no |
| GET `/admin` | true | yes |

### Example 4: Attach headless on localhost

Terminal 1:

```text
dlv exec ./bin/api --headless --listen=127.0.0.1:2345 --api-version=2 --accept-multiclient
```

**Important:** bind only to loopback (`127.0.0.1`). Writing `--listen=:2345` listens on all interfaces (`0.0.0.0`) and publicly exposes the Delve API — that is wrong for everyday development. Prefer `--listen=127.0.0.1:2345`, or Docker `-p 127.0.0.1:2345:2345`, or an SSH tunnel. Never treat a public listen as OK.

`launch.json` attach with `127.0.0.1:2345`. Break in the editor in a handler.

#### What happens here

The editor **does not build** the binary in attach mode — client only. Path mapping must match the source on disk. **Defense:** port only on loopback, not `--listen=:2345` on `0.0.0.0` in dev without reason.

**Execution trace:**

| Component | Role |
|-----------|------|
| headless dlv | holds target + API |
| VS Code attach | DAP client |
| break in .go | BP on the same source as the binary |

### Example 5: Debug Console vs CLI — same moment

Paused in `main`; in Console: `msg`. In terminal: `dlv connect 127.0.0.1:2345` (if attach) or a parallel session — `print msg`.

#### What happens here

Two UX surfaces, one engine. Console is fast for an expression; `goroutines` and `funcs` — CLI.

**Execution trace:**

| Channel | Input | Expected |
|---------|-------|----------|
| Debug Console | `msg` | `"hello debug"` |
| CLI | `print msg` | same |
| Debug Console | `goroutines` | often does not work like CLI |
| CLI | `goroutines` | list of goroutines |

### Example 6: GoLand equivalent (briefly)

Go Build configuration: Package path `cmd/api`. Breakpoint in `main`. Debug. Evaluate Expression on `msg`.

#### What happens here

You do not have to change tools to understand debugging — the mental model transfers: launch = new process, breakpoint = `break`, step buttons = `next`/`step`.

**Execution trace:**

| VS Code | GoLand |
|---------|--------|
| launch.json | Run Configuration |
| F10 | Step Over |
| Variables | Variables pane |

### Example 7: Wrong program path (anti-example)

```json
"program": "${workspaceFolder}"
```

But `main` is in `cmd/api` — breakpoint in `cmd/api/main.go` stays **unbound**.

#### What happens here

F5 starts the wrong package. CLI diagnosis: `dlv debug ./cmd/api` + break works → fix `program`.

**Execution trace:**

| `program` | Break in `cmd/api` | Outcome |
|-----------|--------------------|---------|
| workspace root | yes | unbound / miss |
| `./cmd/api` | yes | hit |

### Example 8: Logpoint instead of temporary fmt

Logpoint message: `id={id}` on a line in a loop. Continue — messages in Debug Console / Output without changing code.

#### What happens here

Like `trace` in Delve (04.03). Do not leave dozens of logpoints in the repo as a production solution.

**Execution trace:**

| Iteration | Logpoint | Process stops? |
|-----------|----------|----------------|
| i=0..n | messages | usually no (log only) |
| ordinary BP | — | yes |

## Decision analysis

| Decision | Motive | When not |
|----------|--------|----------|
| Commit basic `launch.json` | Equal DX in the team | When it contains secrets |
| Separate config per binary | Fast reproduction | One main at root — one config |
| CLI as fallback | Extension diagnosis | Always — keep the habit |
| localhost attach | Reduces attack surface | Controlled remote dev with tunnel |
| Debug test before `main` | Less state | Integration test of the whole server |
| UI conditional BP | Fast filtering | Complex condition — CLI `condition` |

## Trade-offs

- **GUI** faster for everyday work, harder for automation and regex `funcs`.
- **CLI** better for SSH server without IDE, scripts, and advanced goroutine.
- The extension hides build flags — check `go.delveConfig`.
- GoLand license vs VS Code free — team choice, not the debugger.
- Logpoint can slow a hot loop — like trace.
- Multi-client headless attach — watch who else changes state (`set` in CLI).

## Common mistakes

### 1. Wrong `program` path

**Wrong:** `"program": "${workspaceFolder}"` in a repo where main is in `cmd/api`.

**What happens:** F5 runs the wrong `main`; breakpoints unbound.

**Why:** the debug build does not include that file as entry.

**Correct:** `"program": "${workspaceFolder}/cmd/api"`.

### 2. Break in a file that is not in the build

**Wrong:** break in `debug_only.go` with a tag that is not active.

**What happens:** gray / unbound breakpoint.

**Why:** the file is not in the binary.

**Correct:** check build tags; `sources` in CLI.

### 3. Attach to wrong port / host

**Wrong:** port 2345 taken by another process or wrong container.

**What happens:** attach timeout.

**Why:** no listener or firewall.

**Correct:** `127.0.0.1`, check the headless command, Docker port mapping `-p 127.0.0.1:2345:2345`.

### 4. Expecting a full Delve REPL in Debug Console

**Wrong:** you type `continue`, `next`, `goroutines` as in 04.04.

**What happens:** nothing or a strange message.

**Why:** DAP evaluation ≠ CLI.

**Correct:** toolbar for step; CLI for advanced commands.

### 5. `dlv` missing

**Wrong:** only VS Code without Install Tools.

**What happens:** F5 fails immediately.

**Why:** the extension does not always bundle dlv onto PATH.

**Correct:** Go: Install/Update Tools; `dlv version`.

### 6. Workspace trust / antivirus (Windows)

**Wrong:** trust not given; AV blocks inject.

**What happens:** attach launch fails without a clear reason.

**Why:** OS security.

**Correct:** trust the folder; exception for the dev tool (team policy).

### 7. Strip / release binary with attach

**Wrong:** attach to a production strip binary without debug symbols.

**What happens:** empty Variables, strange stack.

**Why:** no DWARF.

**Correct:** debug build locally; attach only to a debug artifact.

### 8. Remote attach to the public internet

**Wrong:** `"host": "prod.company.com", "port": 2345` in shared config.

**What happens:** exposure of the debug API; compliance risk.

**Why:** Delve is not for an unauthenticated public network.

**Correct:** localhost, SSH tunnel, explicit SRE procedure — not a “shortcut” in JSON.

## Idiomatic Go

- One `launch.json` with 3–5 named configurations: api, worker, test-package, attach-local.
- Team README: “F5 → choose `api`.”
- Libraries: prefer **Debug Test** / `mode: test`.
- Do not replace tests with the debugger — the debugger explains, the test preserves behavior.
- **interface** values in WATCH — check the dynamic type in Console before a cast.

Attach to Docker: host must be `127.0.0.1` with `-p` mapping, not `0.0.0.0` in a café. After the fix the GUI works; CLI knowledge remains.

## Check questions

1. **What does the Go extension do relative to Delve?**  
   **Answer:** Mediates IDE requests via DAP to Delve, which controls the target process.

2. **Which `mode` for running a package with `main`?**  
   **Answer:** `"mode": "debug"` with `"request": "launch"`.

3. **How do you debug one test?**  
   **Answer:** `"mode": "test"`, `program` on the package, `args` with `-test.run TestName`.

4. **Difference between Debug Console and Delve REPL?**  
   **Answer:** Console evaluates expressions in the current frame; the REPL supports the full command set (`goroutines`, `funcs`, `set`, …).

5. **Does GoLand use a different debugger for Go?**  
   **Answer:** Typically also Delve; the difference is UI and configuration, not the basic model.

6. **Why attach host `127.0.0.1`?**  
   **Answer:** Limits the debug API to loopback; reduces the risk of accidental exposure.

7. **What does an unbound breakpoint in the UI mean?**  
   **Answer:** The line/file is not mapped in the loaded debug binary — check `program` and build tags.

8. **Where is the equivalent of `locals`?**  
   **Answer:** The VARIABLES panel for the current Call Stack frame.

9. **Does F10 in VS Code correspond to `next`?**  
   **Answer:** Yes — Step Over ≈ `next` in Delve.

10. **Attach vs launch?**  
    **Answer:** Launch starts a new process under the debugger; attach hooks onto one already running (e.g. headless).

11. **Where to keep API keys for debug?**  
    **Answer:** Outside committed JSON — local settings / `.env` in `.gitignore`.

12. **First step when F5 does not work but the code compiles?**  
    **Answer:** `dlv version` and reproduction of the same package in the CLI.

## Summary

Editors are **clients** over Delve: `launch.json` (debug package, test, attach), gutter breakpoints, state panels, Debug Console for expressions. GoLand briefly shares the same mental model. Attach works **defensively** — localhost and controlled tunnels. With the wrap-up of module 04 you have a local, remote, and IDE path for investigating Go programs before you enter Go modules.
