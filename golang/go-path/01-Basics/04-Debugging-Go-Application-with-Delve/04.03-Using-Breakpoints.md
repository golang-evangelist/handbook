# 04.03 Using Breakpoints

> **Go Path - Zero to Gopher** / **01 Basics → Debugging Go Application with Delve** / Lesson 04.03

## Lesson goals

After this lesson you can:

- set a breakpoint on `file:line` and on a function name;
- use conditional breakpoints via `condition`;
- distinguish `trace` from an ordinary breakpoint;
- react to a panic via Delve’s built-in unrecovered-panic breakpoint (not invented commands);
- review, temporarily disable, and clear breakpoints (`breakpoints`, `toggle`, `clear`, `clearall`);
- choose a location strategy for the situation (loop, HTTP, rare branch).

## Prerequisite

- Navigation in Delve and reading state (04.02).
- A small program with a loop, an HTTP handler, or a possible panic.
- Go 1.22+; `dlv debug` works locally.

## Problem this lesson solves

A break on a line in a loop of 100000 iterations = manual hell. A break on the wrong function = it never stops. Without conditions and trace you waste hours on hits that do not interest you.

A panic happens “somewhere” — you want an automatic stop with stack and locals, not only a stderr dump. This lesson teaches **precise targeting**: where to stop, when to stop, when only to record a pass, and how to clean the session after an experiment.

## Mental model

**Breakpoint** = “stop execution here (if the condition holds).”

**Tracepoint** (in Delve: a breakpoint with the `trace` property, command `trace`) = “when you pass here, print / record, but do not necessarily stop forever.” Check `help break` and `help trace` in your version.

**Function break** = a symbolic name (`main.interest`, `main.(*Server).ServeHTTP`). More resistant to line shifts when editing.

**Unrecovered panic breakpoint** = Delve’s built-in mechanism that stops when a panic is not caught (`recover`). That is gold for nil pointer and similar crashes in local reproduction. **Do not** rely on an invented `onpanic` command as a “primary” tool — learn what `help` / your Delve version’s documentation actually offers around panic breakpoints.

Lifecycle: create → (hit) → inspect (04.02) → disable/clear.

## Mechanism

### Locations

```text
break main.go:27
break main.(*Server).ServeHTTP
break package.funcName
```

A line break must land on an **executable** statement. An empty line, a standalone type declaration, or a comment often give unbound / shift to the next instruction.

A function break follows the symbol. When you add ten comment lines above the body, the line number moves — the function name stays.

### Condition

Two common patterns:

```text
break main.go:27
condition 1 i == 50
```

or (depending on version) in one step:

```text
break main.go:27 if i == 50
```

The condition uses names **visible at that location**. If the variable is not yet live on that line, the condition “does not work” — not magic, but scope.

### Review and cleanup

```text
breakpoints
clear 1
clearall
toggle 1
```

- **toggle / disable**: keeps the definition, does not activate — handy for later comparison.
- **clear**: removes from the session.
- **clearall**: hygiene at the end of the experiment.

### Trace

```text
trace main.go:27
trace main.handler
```

Hits and continues with a message — like a temporary log **without** changing code. Does not replace structured logging in production. Replaces `fmt.Println` while you investigate.

### Panic — built-in unrecovered-panic breakpoint

Delve by default can stop on an **unrecovered panic** (a panic not caught with `recover`). In practice:

1. run the program under Delve;
2. allow the panic to happen (or deliberately cause it);
3. the session stops with the stack at the crash moment — you can `stack`, `args`, `locals`, `print`.

Check `help` / the breakpoint list in your version (`breakpoints`) to see how the panic breakpoint is shown and whether it is enabled. Names and UI details differ slightly between versions; the concept stays: **stop when a panic starts and is not recovered**.

If someone in an old blog writes `onpanic` as if it were a standard everyday command — treat that carefully. The source of truth is local `help`, not a headline from the internet.

### Location choice strategies

| Situation | Strategy |
|-----------|----------|
| Do not know which branch | `trace` on entry + later `condition` |
| Know the function, lines jump | Break on function name |
| Loop 1e6 | `condition` on index / ID |
| Rare panic | Unrecovered-panic breakpoint |
| Shipping hotfix | Minimal break, quick find, `clearall` |
| HTTP handler | Condition on `path` / `userID` |

### Logpoint / trace ethics

Trace in the editor sounds like a log. Differences:

- lives only in the debug session;
- does not go to a log aggregator;
- can slow a hot path during the session.

Does not replace structured logging in code for production.

### Conditions that often break

- String comparison with wrong case (`"/Admin"` vs `"/admin"`).
- Condition uses a variable out of scope on that line.
- Condition on a field before it is assigned in the function.
- Float comparison for exact equality.
- Condition on `err` before `err` is assigned.

When a condition “does not work”: temporarily remove the condition, stop once, `print` the names, then restore the condition with the exact expression.

### Breakpoint hygiene in a team

Saved breakpoints in `.vscode` can be shared if you want — but personal conditions with your user ID should not enter git. Use a local override. After the session: disable or clear so tomorrow’s F5 does not stop on a stale place.

### Disable vs clear (more detail)

In the editor a checkbox next to a breakpoint ≈ disable. Use disable when comparing two places alternately: A on / B off, then reverse. Use `clear` when you know that location is no longer relevant.

### Hit count (where it exists)

Some clients support “stop only after N hits.” Useful when the first 100 iterations are not interesting. If the UI lacks it, condition `i >= 100` does the same idea in the CLI.

### Function break and method / pointer receiver

For a method with a pointer receiver:

```text
break main.(*Server).ServeHTTP
```

For a value receiver the form differs. `funcs ServeHTTP` (04.04) helps when you are not sure of the exact symbol. Wrong form = the break never binds.

### Break in a test vs break in `main`

For libraries without `main`, the fastest path is `dlv test` (or editor “Debug Test”) + break in the test function or in the code under test. Advantages:

- less state (no whole server);
- fast `restart`;
- condition can be on the test input (`in == 42`).

For HTTP integration you still need `main` / `ListenAndServe`, but first isolate the logic into a function you test.

### Condition and map / slice indexes

```text
condition 1 key == "refund"
condition 1 len(items) > 0 && items[0].ID == 7
```

The second form is fragile: if `len(items)==0`, evaluating `items[0]` can fail in the condition. Safer pattern: first stop on `len(items) > 0`, then in the session `print`; or split into two checks when Delve allows it.

### Combined strategy: trace → condition → break

1. `trace` on handler entry — how many times is it called?
2. `condition` on a rare message type — stop only then.
3. Ordinary break + 04.02 checklist — deep investigation.
4. `clearall` — hygiene.

This sequence prevents you from immediately nailing an unconditional break into a hot path.

### What the `breakpoints` list should tell you

For each BP check:

- ID (for `clear` / `condition`);
- location (file:line or symbol);
- whether it is enabled;
- whether it has a condition / trace flag;
- whether it is hit count / built-in panic BP.

If you see a BP you do not recognize — disable it before you spend an hour on “why does it stop.”

### Predict-then-answer

Code:

```go
func find(nums []int, target int) int {
	for i, v := range nums {
		if v == target {
			return i
		}
	}
	return -1
}

func main() {
	_ = find([]int{1, 2, 3, 4, 5, 9, 12}, 9)
}
```

You set `break` on the `for` line **without** a condition. **How many times will you stop before the return?**

**Prediction:** ???

**Answer:** You stop on every entry into the loop body / on that line per iteration — typically 6 times until you find `9` (indexes 0..5), depending on the exact break line. With `condition v == 9` you stop **once**, with the `i` that matches the hit (usually `i=5` for this slice).

### Extension: hitcount condition (real Delve)

```text
condition -hitcount 1 >= 100
```

Stops only after enough hits. Useful when the first N iterations are not interesting. If the UI has no hit count, the same effect comes from `condition` with `i >= 100` when `i` is in scope.

### Extension: when not to use a condition

- The condition depends on a variable out of scope on that line.
- Float exact equality.
- String case mismatch.

When a condition “does not work”: remove the condition, stop once, `print` the names, then restore the condition.

### Extension: unrecovered-panic reminder

Delve automatically sets unrecovered-panic. `breakpoints` shows it. Do not invent `onpanic` as a primary command — rely on built-in behavior and `help breakpoints`.


### Strategy: from symptom to break type

| Symptom | First choice |
|---------|--------------|
| Loop 1e5 | `condition` on index / ID |
| Rare HTTP path | function break + `condition` on path |
| “Does it even enter?” | `trace` |
| Crash / panic | unrecovered-panic + `stack` |
| Stable function, lines jump | function break |
| Experiment done | `clear` / `clearall` |

Remember: a condition filters the stop, it does not change the program’s business logic.

### Mini lab: five hits without five stops

1. Make a loop 0..4 that calls `tick(i)`.
2. `trace main.tick`
3. `continue`
4. Count the traces — should be 5.
5. Replace trace with an ordinary break + `condition` `i == 3` and confirm one stop.


### Lesson 04.03 wrap-up reminder

Break chooses *where*. Condition chooses *when*. Trace chooses *observation without stopping*. Panic break chooses *the crash moment*. Clear chooses *hygiene*.

When you master these five, the next lesson (systematic CLI) only names the same craft with commands.

Practice them on the same small program until they become reflex. One hour of repetition is worth more than reading a table.

Prerequisite for 04.04: you can set a function break, one condition, and one `trace` without looking at notes.

If any of that sticks, return to Examples 1–3 of this lesson and walk them again with a paper checklist.

That is a sufficient bridge to a systematic command overview.

Now you are ready for 04.04.

## Rules and syntax

1. A line break must be on an executable statement, not on an empty line / declaration without code.
2. A condition uses names visible at that location.
3. Too many unconditional breaks on a hot path slow things down.
4. For a function break choose the fully qualified form (package + type + method).
5. After a refactor check that the break still exists (`breakpoints`).
6. Trace for event frequency; break for deep investigation.
7. Panic: rely on the built-in unrecovered-panic mechanism + `help`, not blog aliases.
8. After the experiment `clear` / `clearall` — hygiene is part of the craft.

## Examples

### Example 1: Line vs function

```go
package main

import "fmt"

func interest(principal, rate int) int {
	return principal * rate / 100
}

func main() {
	fmt.Println(interest(10000, 7))
}
```

```text
break main.interest
# equivalent targeting of the body (adjust line number):
break main.go:6
continue
args
print principal
print rate
```

#### What happens here

A function break follows the symbol. If you add comments above, the line moves — the function break stays valid.

**Execution trace:**

| Step | Action | Result |
|------|--------|--------|
| 1 | `break main.interest` | BP on symbol |
| 2 | `continue` | stop in `interest` |
| 3 | `args` | `principal=10000`, `rate=7` |
| 4 | (after return) | result `700` in the caller |

Add 10 comment lines above `return` and repeat: the function break still hits; the old line number may not.

### Example 2: Condition in a loop

```go
package main

func find(nums []int, target int) int {
	for i, v := range nums {
		if v == target {
			return i
		}
	}
	return -1
}

func main() {
	_ = find([]int{1, 2, 3, 4, 5, 9, 12}, 9)
}
```

```text
break main.go:5
condition 1 v == 9
continue
print i
print v
print target
```

#### What happens here

You do not stop on every `i`. Only when `v == 9` do you enter the session. That is the difference between a tool and torture.

**Execution trace (with condition):**

| Loop pass | `v` | Condition `v==9` | Stop? |
|-----------|-----|------------------|-------|
| i=0 | 1 | false | no |
| i=1 | 2 | false | no |
| … | … | … | no |
| i=5 | 9 | true | **yes** → `print i` → `5` |

### Example 3: Tracepoint instead of logging

```go
package main

import "net/http"

func handler(w http.ResponseWriter, r *http.Request) {
	_, _ = w.Write([]byte("ok"))
}

func main() {
	http.HandleFunc("/", handler)
	_ = http.ListenAndServe(":8080", nil)
}
```

```text
trace main.handler
continue
```

Send requests (`curl` or browser); watch hits without a manual stop every time.

#### What happens here

You get a “passed here” signal as a temporary log. For depth: turn the trace into an ordinary break or add condition `r.URL.Path == "/admin"`.

**Execution trace:**

| Request | Trace message | Process stops? |
|---------|---------------|----------------|
| GET / | hit handler | no (continues) |
| GET / | hit handler | no |
| (convert to break) | — | yes, you wait for `continue` |

### Example 4: Stop on unrecovered panic

```go
package main

func boom(ok bool) {
	if !ok {
		panic("not ok")
	}
}

func main() {
	boom(false)
}
```

```text
break main.main
continue
# allow the panic; Delve stops on unrecovered panic
stack
goroutines
locals
print ok
```

#### What happens here

You see locals and stack at the critical moment. More useful than reading only a stderr dump when you need one more `print`. If there is a `recover` in `defer`, the panic may be “caught” and the unrecovered breakpoint does not activate — that is expected.

**Execution trace:**

| Moment | State |
|--------|-------|
| entry `boom(false)` | `ok=false` |
| `panic("not ok")` | unrecovered panic |
| Delve stop | `stack` shows `boom` ← `main` |
| `print ok` | `false` |

### Example 5: Clear and hygiene

```text
break main.main
break main.boom
breakpoints
clear 2
breakpoints
clearall
breakpoints
```

#### What happens here

Stale breakpoints confuse the session (“why does it stop here?”). `clear` hygiene is part of the craft.

**Execution trace:**

| Command | BP count (illustrative) |
|---------|-------------------------|
| after 2× `break` | 2 (+ possible built-in) |
| `clear 2` | 1 remaining |
| `clearall` | 0 user ones (built-in panic BP may remain — check the list) |

### Example 6: Condition on a string path

```go
package main

import "net/http"

func route(path string) string {
	switch path {
	case "/ok":
		return "ok"
	case "/admin":
		return "admin"
	default:
		return "missing"
	}
}

func main() {
	http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
		_, _ = w.Write([]byte(route(r.URL.Path)))
	})
	_ = http.ListenAndServe(":8080", nil)
}
```

```text
break main.route
condition 1 path == "/admin"
continue
```

Ordinary traffic on `/ok` does not stop. A request on `/admin` stops.

#### What happens here

You filter by function input, not by “every HTTP request.”

**Execution trace:**

| Request path | Condition | Stop? | `print path` |
|--------------|-----------|-------|--------------|
| `/ok` | false | no | — |
| `/missing` | false | no | — |
| `/admin` | true | yes | `"/admin"` |

## Decision analysis

| Decision | Motive | When not |
|----------|--------|----------|
| Function break | Stability when editing | When you need exactly one line in a huge function |
| Condition | Scales loops / high traffic | When the condition lies because of scope |
| Trace | Observation without stopping | When you need deep `locals` |
| Unrecovered panic BP | Fast crash diagnosis | When `recover` deliberately swallows the panic |
| `clearall` at the end | Clean session | When you deliberately keep a BP set for regression |
| Disable instead of clear | Fast A/B of locations | When you will never need the BP again |

## Trade-offs

- **Conditions** cost evaluation on every pass — on an extremely hot loop they still slow things down.
- **Trace** on an extremely hot path still slows (less than a stop, more than nothing).
- **Too many breaks** = spontaneous stop everywhere; you lose focus.
- GUI checkbox “logpoint” ≈ trace; CLI knowledge transfers better between editors.
- **Panic + recover**: if middleware catches the panic, you may not see the “crash breakpoint” — you must break in the `recover` branch or temporarily remove recover in local reproduction.

## Common mistakes

### 1. Break on a line without an instruction

**Wrong:** break on an empty line between functions.

**What happens:** unbound breakpoint or stop “somewhere nearby.”

**Why:** no executable instruction.

**Correct:** break on a statement (`return`, call, assignment) or on a function name.

### 2. Condition with a name out of scope

**Wrong:** `condition 1 total == 10` on a line before `total` exists.

**What happens:** break is ignored / condition error / never stops as you expect.

**Why:** variable scope and lifetime.

**Correct:** stop without a condition, `locals`, then write the condition with the right name and line.

### 3. Forgotten break from a previous session

**Wrong:** F5 stops at a place you “did not touch today.”

**What happens:** confusion, false conclusions.

**Why:** editor saved BP in workspace state.

**Correct:** Breakpoints panel → disable/clear; in CLI `breakpoints` + `clear`.

### 4. Break in code that a build tag excludes

**Wrong:** break in `foo_windows.go` while building on another OS / without the tag.

**What happens:** never hits.

**Why:** that file is not in the binary.

**Correct:** check build tags / `sources` (04.04).

### 5. Expecting that a condition changes business logic

**Wrong:** “I will put a condition and the program will behave differently.”

**What happens:** the program behaves the same; only the stop is filtered.

**Why:** a breakpoint does not change semantics (except slowing / race timing).

**Correct:** condition = stop filter; the fix goes into the source + test.

### 6. Trace treated as a permanent production log

**Wrong:** leave dozens of logpoints as an “ops solution.”

**What happens:** no central logging; disappears outside the session.

**Why:** trace lives in the debugger.

**Correct:** structured log in code for production; trace for investigation.

### 7. Panic break disabled / wrong expectations around `onpanic`

**Wrong:** you type a nonexistent command or expect a stop even though `recover` catches the panic.

**What happens:** the process “survives” or Delve does not stop as you imagined.

**Why:** unrecovered vs recovered; the source of truth is `help` / `breakpoints`.

**Correct:** learn the built-in unrecovered-panic breakpoint; check whether the code does `recover`.

## Idiomatic Go

- Reproduce with the smallest test + break in the test (`dlv test` / editor test debug).
- Condition on `reqID` / `userID` in handlers — not on every request.
- Do not commit personal `.vscode` breaks if the team does not want that — share `launch.json`, not personal UI state.
- For rare branches: `trace` first (frequency), then conditional break (depth).

## Practical scenario

A handler processes 10k messages/s in a load test. Unconditional break — impossible. Condition `msg.Type == "Refund"` catches the rare type. Trace on entry counts how many Refunds arrive. Unrecovered-panic breakpoint catches a nil map access in a rare branch. After the fix, `clearall`. The ticket gets: exact condition, `print msg`, stack — not “sometimes it crashes.”

## Exercises

1. Set a function break and a line break on the same code; compare behavior after adding 10 comment lines.
2. In a loop stop only when `i > 100` (deliberately large slice).
3. Make a `trace` on a function and generate 5 hits.
4. Cause a panic without `recover` and catch it with the unrecovered-panic mechanism; then add `recover` and observe the difference.
5. Practice the `breakpoints` / `toggle` / `clear` / `clearall` cycle.
6. HTTP: condition on `path == "/admin"` from Example 6.
7. Predict-then-answer: calculate how many unconditional stops `find` has before `9`, then verify with Delve.

## Check questions

1. **Advantage of a break on a function name?**  
   **Answer:** More resistant to line shifts when editing the source.

2. **What does a conditional breakpoint do?**  
   **Answer:** Stops only when the condition is true; otherwise continues without a stop.

3. **What is a tracepoint / `trace` for?**  
   **Answer:** Records/passes through a location without (mandatory) lasting stop — like a temporary log in the session.

4. **Why `clear`?**  
   **Answer:** Removes stale breakpoints that confuse the session.

5. **Benefit of stopping on unrecovered panic?**  
   **Answer:** Enables reviewing state and stack at the crash moment under debugger control, before you lose context.

6. **Why can a condition “not work”?**  
   **Answer:** Often a name out of scope, wrong string case, or a condition on a variable before assignment — first `print`, then the condition.

7. **Does a breakpoint change the program’s business logic?**  
   **Answer:** No (except slowing / timing effects); it only filters when the debugger stops.

## Extra mini-example: toggle between two locations

```go
func prepare(n int) int { return n * 2 }
func finish(n int) int  { return n + 1 }

func main() {
	x := prepare(21)
	y := finish(x)
	_ = y
}
```

```text
break main.prepare
break main.finish
continue
# investigation in prepare...
toggle 1
continue
# now only finish stops
print n
```

#### What happens here

You do not delete BPs while comparing two layers. `toggle` disables `prepare`; you stay focused on `finish` where `n` is already `42` (21*2). Afterward: `clearall`.

**Execution trace:**

| Stop | Function | `n` / local | Note |
|------|----------|-------------|------|
| 1 | `prepare` | `n=21` | BP1+BP2 active |
| after toggle 1 | — | — | BP1 disabled |
| 2 | `finish` | `n=42` | only BP2 |

## Summary

Breakpoints are precise tools: location, condition, trace, unrecovered panic, cleanup. Choose the narrowest filter that confirms the hypothesis. Function break for stability, condition for loops and traffic, trace for frequency, panic mechanism for crash.

Order in practice: the narrowest condition that still confirms the hypothesis → inspect (04.02) → fix in source + test → `clearall`. Next: a systematic overview of Delve commands.
