# 04.01 Introduction to Delve Architecture

> **Go Path - Zero to Gopher** / **01 Basics → Debugging Go Application with Delve** / Lesson 04.01

## Lesson goals

After this lesson you will be able to:

- describe Delve at a conceptual level: debugger process vs target process;
- explain the role of DWARF debug information;
- understand why optimized binaries “lie” during step-by-step execution;
- know when to use `-gcflags='all=-N -l'`;
- distinguish `dlv debug` and `dlv exec` in the context of binary quality;
- not interpret `<optimized out>` as “the variable is nil”.

## Prerequisite

- Local work with the Delve CLI (03.02) and concepts from 03.01–03.03.
- Basics: compiling with `go build`, what a stack is.
- Go 1.22+.

## Problem this lesson solves

When `print x` in Delve says `<optimized out>` or `next` jumps to “impossible” lines, it looks like a Delve bug. Often it is a consequence of compiler optimizations: variables live only in registers, code is rearranged, inlining erases frames. Without an architectural model you waste time on wrong hypotheses — and “fix” code that is not broken.

## Mental model

Two processes (simplified):

1. **Debugger (`dlv`)** — controls, reads memory, sets breakpoints, interprets DWARF.
2. **Target** — your Go program (or test). The runtime still manages goroutines; Delve integrates knowledge of the Go scheduler better than a generic GDB for Go.

**DWARF** describes: which PC corresponds to `file:line`, where locals live, types, frames. Without DWARF you see machine instructions; with DWARF you see Go source.

**Optimizations:**

- `-N` — disable (reduce) optimizations;
- `-l` — reduce inlining.

```text
go build -gcflags="all=-N -l" -o app .
```

`all=` applies the flags to every package in the build, not only main.

Analogy: a binary without DWARF = a city without street signs. An optimized binary with DWARF = maps exist, but some buildings are merged (inlining) and some apartments are “repainted” (`optimized out`). A debug build = maps + buildings separated as in the blueprint.

## Mechanism

### From source to session

```text
.go source → compiler/linker → binary + DWARF
                              ↓
                         dlv loads binary
                              ↓
                    maps break → address
                              ↓
                 target stops → reading registers/memory
                              ↓
                    DWARF → variable name / line
```

Delve does **not** interpret Go source live like a script. It reads the binary + DWARF and controls the process. It uses the source for display.

### Why it “lies”

| Compiler effect | Symptom in Delve |
|-------------------|-----------------|
| Inlining | odd `step`; no helper frame |
| Dead store elimination | `print` has nowhere to look; optimized out |
| Register allocation | value is not on the stack |
| Code motion | line order ≠ instruction order |

### From machine address to line

When you set `break main.go:20`, Delve:

1. finds the compilation unit for `main.go`;
2. looks up the PC for that line in the DWARF line table;
3. writes a breakpoint at that address;
4. when the CPU reaches it, the OS notifies the debugger;
5. Delve maps the PC back to the line and frame.

A break on a comment often jumps to the next real statement.

### Inlining by example

Helper `clamp` called from 20 places. The optimizer inlines it into callers. In the debugger:

- `break main.clamp` may not exist as a standalone symbol;
- `step` from the call site does not enter “into the helper’s file”;
- the stack is shorter.

With `-l` the helper remains. A debug build is not a whim — it is the condition that the mental model of the source matches the stack.

### `dlv debug` vs `dlv exec`

```text
dlv debug ./cmd/api     # Delve compiles and runs
dlv exec ./api.bin      # uses an already built binary
```

For `exec`, you are responsible for the flags. Remote/Docker often uses `exec`. The local happy path — `debug`.

### Recommended local scripts

`scripts/build-debug.ps1`:

```powershell
go build -gcflags="all=-N -l" -o bin/app-debug.exe ./cmd/app
```

`scripts/build-release.ps1`:

```powershell
go build -ldflags="-s -w" -o bin/app.exe ./cmd/app
```

You debug only `app-debug`. Do not open the release artifact in Delve except to confirm that strip hurts.

### Predict-then-answer

Same function, two builds. In the opt build, is it guaranteed that `print x` in `calc` works?

```go
func calc(a, b int) int {
	x := a + b
	y := x * 2
	return y
}
```

**Answer:** No. The compiler may eliminate `x`/`y`. With `-N -l` you more often see both. `<optimized out>` ≠ `nil`.

### Symptoms that look like Delve, but are not

| Symptom | Common real cause |
|---------|------------------|
| optimized out | opt build |
| no source lines | strip or wrong path |
| break does not hit | wrong package / tag |
| odd step | inlining |
| attach refused | port / firewall / not headless |

### Mini check before a hard session

1. Binary is not stripped.
2. When needed `-gcflags="all=-N -l"`.
3. `dlv version` compatible with `go version`.
4. You work against the same commit as the source in the editor.

### Why Delve and not raw GDB

GDB sees OS threads. Delve lists goroutines and wait status, and understands Go frames better. For everyday application Go — Delve. Native/cgo specialization is outside this introduction.

### Connection to remote (03.03)

If the debug stage forgets `-N -l` and also strips, remote attach “works” (the process stops) but `locals` are empty. Delve’s architecture is not broken — the map is poor.

### Architecture FAQ

**Why `all=` in gcflags?**  
Without `all=` the flags often apply only to the package from the CLI; dependencies stay optimized.

**Can I mix opt libraries and a debug main?**  
Yes. In your own code you see locals; in opt dependencies you do not. For a deep investigation through a lib — rebuild with `all=-N -l`.

**Is DWARF the same on Windows/Linux/macOS?**  
Conceptually yes; the container format (PE/ELF/Mach-O) carries sections differently; Delve abstracts most of it.

### Lab of feeling (not a scientific benchmark)

1. Build `calc-opt` and `calc-dbg`.
2. Compare `locals` in the same function.
3. Compare loop time for 1e7 calls (Measure-Command).
4. Conclusion: you pay CPU to see the truth in the debugger — fair during investigation, not forever in production.

### What Delve knows about the runtime (conceptually)

- list of G (goroutine) and status (running, waiting, syscall...);
- linking a panic to the stack;
- that the “thread” a programmer imagines often is not an OS thread.

So do not call a goroutine a thread in your notes.

### Deeper: strip and panic

Even without Delve, the runtime prints a stack thanks to symbols. A stripped binary gives a poorer traceback. The same metadata serves panic and the debugger.

### Deeper: commit mismatch

The debugger shows the truth of *that* binary. If the editor has a newer commit, an “odd step” may simply be different code. Align the SHA.

### Relationship of parallelism and pause

When Delve stops, you observe a frozen world. That breaks parallelism and changes concurrency timing. Do not conclude about a race from one paused session alone — use `-race`.

### Extended flow: from suspicion to rebuild

1. Symptom: `print total` → optimized out.
2. Hypothesis A: total is truly uninitialized.
3. Hypothesis B: opt build.
4. Test: rebuild `-N -l`, same break.
5. If `total` appears — B was correct; continue investigating logic.
6. If still 0 — A; look for the branch that does not update.

Without step 4 people “fix” the compiler instead of the code.

### Connection to tests

`dlv test` also depends on DWARF. If CI builds with aggressive flags and you debug differently locally, symptoms diverge. Document the debug build.

### Extra layer: how to talk about the problem to a colleague


This template shortens triage from 30 minutes to 3.

### Extra layer: what the compiler is allowed to do (intuition)

The compiler may:

- compute constants ahead of time;
- remove a variable that is no longer read;
- insert a small function body into the caller;
- rearrange independent statements.

It must not change the *observable* behavior of the program per the Go memory model (with nuances). The debugger sees the implementation, not only abstract semantics — that is why it “lies” relative to the source.

### Extra layer: connection to embedding and method set (conceptually)

When you debug a type with embedding and a method on the embedded type, the stack and `whatis` help you see *which* concrete type lives in the variable. Optimizations can blur the display further. That is why a debug build also helps with interface and method set investigation (more detail in later course modules).

### Extra layer: zero value reminder

A zero value is not a bug by itself. The bug is when a zero value means “not loaded” and you interpret it as “the user sent zero”. The debugger shows the value; you interpret the domain.

### Workshop: drawing on paper


Draw an arrow: source → compiler → binary+DWARF → dlv → break address → stop → read → variable name. Next to each arrow write one thing that can go wrong (e.g. strip on the third link).


### Case study: “step jumps lines”


Symptom: `next` skips a line that “must” execute. Possible causes: code motion, a line with no instructions (declaration), wrong file under a build tag, or you are looking at an optimized function. Check order: `list` → whether the line is executable → rebuild `-N -l` → only then suspect logic.


### Case study: “break on function does not exist”


Function break does not find the symbol. Causes: inlining, wrong package qualifier, a method with pointer receiver in the type name (`.*Type`), or a build that did not include that file. Check: `funcs` filter (04.04) + `-l` rebuild.


### Connection to error values


When investigation centers on `if err != nil`, an optimized build sometimes “eats” temporaries. A debug build makes the branch more readable. Still: `error` is a type; do not replace it in your head with a word that mixes human mistake and a program value.


### Connection to pointer and nil


A pointer’s zero value is `nil`. Optimized out is neither a pointer nor nil — it is a hole in the map. If you swap those two concepts, you will add unnecessary nil checks instead of a rebuild.


### What to take as a habit


Before every hard session: (1) debug binary, (2) same commit, (3) hypothesis written down, (4) only then break. These four steps reduce false conclusions more than any advanced command.


### Catalog of questions you ask yourself on hit

1. Is this a debug binary?
2. Is this the goroutine I expect?
3. Does `stack` confirm the call path?
4. Is the value a zero value or truly loaded?
5. Is `error` nil or does it carry a message?
6. Would a test catch this without a debugger?

If the answer to (1) is not “yes”, the rest of the questions are unstable.

### Comparative example: two interpretations of the same symptom

Symptom: `print discountPct` → optimized out.

Beginner interpretation: “pct is missing, add default 15.”  
Interpretation after this lesson: “first `-N -l`; if 0 appears, then JSON/tag; if 15 appears, the formula downstream.”

The difference is discipline, not IQ.

Two paragraphs prevent months of mixed flags in the team.

### Decision table: which build for which session

| Session goal | Build |
|-------------|--------|
| Learning Delve / first break | `dlv debug` or `-N -l` |
| Confirm that strip hurts | intentional `-s -w` (once) |

Choose the build consciously. Default “just `go build`” is not always wrong, but you must know what you lose in `locals`.

### Short protocol after every “odd” print

1. Read the exact text: `optimized out`, evaluation error, or a real value.
2. If optimized out → rebuild debug → repeat the same `print`.
3. If a real value → build a hypothesis about logic / input.
4. If evaluation fails → simplify the expression (`print p` before `print p.X`).

This protocol prevents mixing three different problem classes into one frustration.

## Rules and syntax

1. `all=` in `-gcflags` applies to all packages.
2. Avoid strip (`-s -w`) in a debug build.
3. Do not conclude a logic bug only because of `<optimized out>` — rebuild first.
4. `dlv exec` requires that you guarantee good flags.
5. Architecture: Delve is not magic; it depends on debug info quality.
6. Align the Delve version with the Go version.
7. Goroutine ≠ OS thread when interpreting the list.

## Examples

### Example 1: Same function, two builds

```go
package main

import "fmt"

func calc(a, b int) int {
	x := a + b
	y := x * 2
	return y
}

func main() {
	fmt.Println(calc(3, 4))
}
```

```text
go build -o calc-opt.exe .
go build -gcflags="all=-N -l" -o calc-dbg.exe .
dlv exec ./calc-dbg.exe
```

#### What happens here

**Trace (dbg):** `a=3`, `b=4` → `x=7` → `y=14` → return 14 → print `14`.  
In the opt build `x` or `y` may disappear from `locals`. That is not a “Go error” — it is a trade-off of speed and observation.

### Example 2: Inlining confuses `step`

```go
package main

func tiny(v int) int { return v + 1 }

func main() {
	n := tiny(41)
	_ = n
}
```

#### What happens here

Under strong optimizations `tiny` may be inlined into `main`. A break on `tiny` sometimes does not exist as a frame. With `-l` the call remains. The hypothesis “the function does not execute” often means “it no longer exists as a separate frame”.

### Example 3: Conceptual session diagram

```text
[dlv process] --control--> [target: your server]
     |                           |
  DWARF from binary          goroutines, memory
     |                           |
  UI/CLI <---- state ------------+
```

#### What happens here

When the target stops, the world “freezes” for observation. Other goroutines also pause in the stop-the-world sense of debugging — timing is not production.

### Example 4: `dlv debug` vs `dlv exec`

```text
dlv debug ./cmd/api
dlv exec ./api.bin
```

#### What happens here

`debug` builds something suitable for the session. `exec` trusts your artifact — in Docker that must be a debug stage.

### Example 5: Panic and DWARF

```go
package main

func main() {
	var p *int
	_ = *p
}
```

#### What happens here

A runtime panic (`nil` pointer dereference) prints a stack. A stripped binary is poorer. The same metadata serves panic and Delve. **Predict:** is `p == nil` before `*p`? **Yes** — a pointer’s zero value is `nil`.

## Decision analysis

| Decision | Motive |
|--------|--------|
| Separate dlv/target | Correct interpretation of attach errors |
| DWARF as a map | Why strip hurts |
| `-N -l` when needed | Fidelity > speed in investigation |
| `exec` in a container | Predictable artifact |
| Two build scripts | Do not mix release and debug |

## Trade-offs

- **Without optimization** slower program — OK for debug.
- **With optimization** more realistic perf, worse observability.
- **Inlining** speeds up, erases function boundaries.
- Larger binary with debug info.
- Keep `make debug` / `make release` separate.

## Common mistakes

### 1. Interpreting `<optimized out>` as nil

**Wrong:** “total is nil/0 because Delve does not see it.”  
**What happens:** you change the wrong thing.  
**Why:** the value may exist in a register; the map is poor.  
**Correct:** rebuild `-N -l`, then judge the logic.

### 2. Strip + wondering why there are no lines

**Correct:** no `-s -w` in a debug build.

### 3. Debugging an old binary on disk

**What happens:** break “does not follow” the new code.  
**Correct:** rebuild; check file time / SHA.

### 4. Expecting Delve to “fix” missing DWARF

**Correct:** fix the build flags.

### 5. Mixing Go and Delve versions

**Correct:** `go install ...@latest`, align.

### 6. Concluding about a race from one paused session

**Correct:** `-race` + reproduction; debugger for state.

### 7. `-N -l` in a prod deploy script without intent

**Correct:** only the debug artifact.

## Idiomatic Go

- Document the debug build in Makefile/task.
- For a CI failure: same commit + debug flags.
- Use Delve’s knowledge of goroutines — that is why we choose Delve.
- Do not replace tests with the debugger.

## Practical scenario

Incident: “total” in a report is wrong. Dev debugs an opt binary, `print total` says optimized out, changes code at random. Mentor asks for rebuild `-N -l`, sees that `total` stays old because the `if err != nil` branch returns earlier — logic, not the compiler. The team adds `scripts/debug-build` and a wiki paragraph on DWARF/optimization.

## Check questions

1. **Which two processes take part?**  
   **Answer:** Debugger (Delve) and target (application/test).

2. **What is DWARF for?**  
   **Answer:** It maps machine code to source, describes types and variable locations.

3. **Why does an optimized binary “lie”?**  
   **Answer:** It rearranges code, inlines, removes temporary variables.

4. **What does `-gcflags='all=-N -l'` do?**  
   **Answer:** It reduces optimizations and inlining for more faithful debugging on all packages in the build.

5. **Difference between `dlv debug` and `dlv exec`?**  
   **Answer:** `debug` builds and runs; `exec` controls an already existing binary.

6. **Is optimized out the same as nil?**  
   **Answer:** No. Optimized out means the debugger has no reliable location for the value.

7. **Why not call a goroutine a thread?**  
   **Answer:** It is a Go runtime flow; many of them share a smaller number of OS threads. Delve lists goroutines, not “your” threads 1:1.

## Summary

Delve controls the target with the help of a DWARF map. Optimizations speed up runtime but hurt observability. When locals disappear or steps jump, first suspect build flags, and only then a “broken debugger”. `all=-N -l` is an investigation tool. Strip is the enemy of learning.
