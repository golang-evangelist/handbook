# 05.03 Understanding Go module versions

> **Go Path - Zero to Gopher** / **01 Basics → Exploring Go Modules** / Lesson 05.03

Semver, v0/v1/v2+ lines, major suffix `/v2`, incompatible versions as different modules, and pseudo-versions — a map between version number, import path, and compatibility.

## Lesson goals

After this lesson you should be able to:

- read versions by semver rules in the Go ecosystem;
- distinguish expectations for v0, v1, and v2+;
- explain why major v2+ goes in the module path as `/v2`, `/v3`, …;
- recognize incompatible import paths as **different modules** in the graph;
- interpret pseudo-versions when there is no clean tag;
- connect semver with MVS version selection (lower bound, not “always latest”);
- plan major version migration without a “big bang” build break.

## Prerequisite

- Lessons **05.01** and **05.02** (module path, `require`, MVS, `go get` basics).
- Basic git: **tag**, **commit**, **branch**; difference between tag and branch.
- Go **1.22+** on `PATH`.
- Terminal (PowerShell or bash) and ability to run `go list -m -versions`.

## Problem this lesson solves

Without a clear version model, developers do this:

- import a v2 library without `/v2` in the path and get odd errors or the “old” API;
- expect `v1.9` to automatically move to `v2.0` as the “same module”;
- not understand why `v0.x` may break API without a new major number;
- fear pseudo-versions because they “look ugly”, though they are legitimate and reproducible;
- tag `v2.0.0` without changing the `module` line in the author’s `go.mod`;
- move a git tag after release and break checksum trust in the team.

This lesson gives a map: **version number ↔ module path ↔ compatibility ↔ dependency graph**.

## Mental model

Semver in Go modules is not just a sticker on a GitHub release. It is part of **import identity** and enters the tool that builds the graph.

```text
v0.x.y   →  experiment; API breaks allowed (semver rule for 0.y)
v1.x.y   →  stable API for that module path (without /vN suffix)
v2.x.y   →  NEW module path (.../v2) because major break
v3.x.y   →  .../v3 — again a new module in path terms
```

Think of a major version as a **new product name** in the import world. `shop` and `shop/v2` are different shelves in the same store, not two jars on the same shelf with the same label.

Pseudo-version is a bridge when you use a specific **commit** instead of a tag:

```text
v0.0.0-20240101123456-abcdefabcdef
   │       │              │
   │       │              └─ short commit hash (12 hex digits in practice)
   │       └─ UTC timestamp (YYYYMMDDHHMMSS)
   └─ base (often v0.0.0 or context of previous tag)
```

Three questions to always ask when you see a version in `go.mod`:

1. **What is the module path** (with or without `/vN`)?
2. **Does semver major match the suffix** in the author’s `module` line?
3. **Is this a tag or pseudo-version** (commit snapshot)?

```text
         tag v1.4.0                    pseudo-version
              │                              │
              ▼                              ▼
    github.com/org/lib@v1.4.0     lib@v0.0.0-20240601-abc...
              │                              │
              └──────────► MVS picks ◄─────────┘
                    smallest sufficient
                    version per graph
```

## Mechanism

This section is the longest — read in order. Each subsection builds on the next.

### Semver basics in Go modules

Module version form: **`vMAJOR.MINOR.PATCH`**, with optional **pre-release** and **build metadata** parts (per semver 2.0.0, adapted to Go rules).

| Segment | Meaning in the ecosystem |
|---------|------------------------|
| **MAJOR** | breaking API changes (after v1); for v2+ must change module path |
| **MINOR** | new capabilities, backward compatible |
| **PATCH** | bug fixes, backward compatible |

Go **requires prefix `v`** in module tags: `v1.2.3`, not `1.2.3`. A tag without `v` will not be recognized as a module semver version in the standard way.

Examples of valid forms:

```text
v1.0.0
v1.2.3
v2.0.0
v1.3.0-beta.1
v1.3.0-beta.1+build.42
```

The Go tool compares versions lexicographically by semver rules adapted for modules (including treatment of pre-release segments).

### Pre-release and stable versions

Pre-release version looks like `v1.4.0-rc.1` or `v2.0.0-beta.2`.

Rules in practice:

- pre-release is **not** the default MVS upgrade target to “newest stable”;
- `go get module@latest` picks the newest **stable** version (without pre-release), unless you explicitly ask for pre-release;
- in production do not take beta/rc without conscious decision and test plan.

```bash
go list -m -versions github.com/org/lib
```

Trace (illustrative output):

```text
github.com/org/lib v1.0.0 v1.1.0 v1.2.0 v1.3.0-beta.1 v1.3.0
```

You see both beta and stable — choice depends on your command and MVS graph.

### v0 — unstable line

Semver says: **major version 0** means API may change without the compatibility promise as on v1+.

For Go modules:

- module path is usually **without** `/v0` suffix (v0 is not a “special path” like v2);
- `v0.1.0`, `v0.9.0`, `v0.15.2` are all the same logical line on the same path;
- author may break function signatures between minor versions on v0;
- v0 consumer must follow changelog aggressively and pin versions.

Moving from v0 to v1 is a **stability signal**, not a path suffix change:

```text
module github.com/org/alat    // v0.x and v1.x on the SAME path
```

Tag `v1.0.0` on the same module path says: “API is ready for wider use with semver promise”.

### v1 — stable line on base path

On v1:

- **MINOR** adds functionality without breaking existing API;
- **PATCH** fixes bugs without breaking;
- **MAJOR** break on the v1 line **must not** happen as a “silent” minor — that violates semver and loses trust.

Consumer import:

```go
import "github.com/org/alat"
```

`go.mod`:

```go
require github.com/org/alat v1.8.3
```

MVS treats `v1.8.3` as lower bound; if someone else in the graph requires `v1.9.0`, the higher sufficient version within the **same** major line and **same** module path is chosen.

### v2+ and mandatory major suffix in module path

Starting from **Go module semver v2** rules (v2 module major version):

- if you publish **v2.0.0** or higher, the author’s `go.mod` **must** have:

```go
module github.com/org/alat/v2
```

- consumer imports **must** include `/v2`:

```go
import "github.com/org/alat/v2/paket"
```

Same for v3, v4, …:

```text
github.com/org/alat      →  v0 or v1 (no /v1 suffix!)
github.com/org/alat/v2   →  v2.x.y
github.com/org/alat/v3   →  v3.x.y
```

**Why?** So that:

1. in the same program you can temporarily hold v1 and v2 (migration);
2. MVS and compiler never mix incompatible APIs as “the same module”;
3. import path unambiguously determines major line.

This is **incompatible major version as a different module** — central concept of the lesson.

### Two majors in one program

A valid `go.mod` may have:

```go
require (
    github.com/org/alat   v1.10.0
    github.com/org/alat/v2 v2.3.1
)
```

That is **not** a conflict — those are **two modules** in the graph. The compiler builds both package trees.

Mental picture:

```text
  app
   ├── import github.com/org/alat     → module @ v1.10.0
   └── import github.com/org/alat/v2  → module @ v2.3.1
```

### Incompatible versions = different modules (formally)

For the Go tool:

| Import path | Typical semver line | Same module? |
|-------------|------------------------|-------------|
| `example.com/lib` | v0.x, v1.x | one module |
| `example.com/lib/v2` | v2.x | **second** module |
| `example.com/lib/v3` | v3.x | **third** module |

`example.com/lib` @ v1 and `example.com/lib/v2` @ v2 are **not** “two versions of the same name” — they are different nodes in `go mod graph`.

Consequence: author documentation must clearly state **which path** to import for which major.

### Tagging and author `go.mod` — contract

Author checklist before `v2.0.0`:

1. Copy or refactor code into a module whose line is `module .../v2`.
2. In package code, imports within the same major use `/v2` prefix where needed.
3. Tag `v2.0.0` on commit that matches that `go.mod`.
4. Publish README: old path stays on v1 maintenance or EOL plan.

Mistake: tag `v2.0.0` while `go.mod` still says `module github.com/org/alat` without `/v2`. Consumers cannot use the module consistently by the rules.

### Pseudo-versions — when and why

Pseudo-version appears when Go must pin an **exact commit** that has no matching semver tag (or when you explicitly request a commit).

Typical form:

```text
v0.0.0-YYYYMMDDHHMMSS-abcdefabcdef01
```

Rules (simplified):

- timestamp is UTC time of commit;
- hash is shortened commit hash;
- prefix `v0.0.0-` is base when there is no closer tag context;
- if a tag **below** the requested commit exists, base may be `v1.2.3-...` (version of previous tag + commit metadata).

When used:

- library has no release tag yet;
- you need a fix commit between tags;
- temporary fork until tag is published;
- local development before tagging (rare in production).

Command:

```bash
go get example.com/lib@deadbeef1234
```

Go writes pseudo-version in `go.mod`. That is **normal** and **reproducible** — not a “dirty version”.

When author publishes `v1.4.0`, move to tag:

```bash
go get example.com/lib@v1.4.0
go mod tidy
```

### `+incompatible` (legacy) — recognition only

Older modules sometimes have tag `v2.0.0+incompatible` on path **without** `/v2`. That is legacy mode before strict v2 path rules. New public modules **should not** use it. If you see it in old code, plan migration to `.../v2` module.

### MVS and semver together

MVS picks the **smallest version that satisfies all lower bounds** in the graph — within the **same module path**.

Example:

```text
A require lib v1.2.0
B require lib v1.5.0
→ MVS picks lib v1.5.0
```

It does **not** merge `lib` v1 and `lib/v2` — those are different modules with separate MVS resolutions.

Upgrade to new **major** always requires **import path change** (v2+), not just `go get @v2` on old path.

### `go get` and semver selectors

Useful selectors (real commands):

```bash
go get example.com/lib@v1.4.2
go get example.com/lib/v2@v2.1.0
go get example.com/lib@latest
go get example.com/lib@none
```

`@none` removes module from graph (useful after migration).

Trace — requesting v2 on wrong path (simulated error):

```text
go: module github.com/org/alat@v2.0.0 found, but does not contain package ...
```

Message varies, but essence is: **path and major do not match**.

### Semver communication and CHANGELOG

Library author team writes:

- **PATCH**: what was fixed, no API break;
- **MINOR**: new functions, examples, migration tips if needed;
- **MAJOR (v2+)**: what breaks, new import path, v1 EOL timeline.

Without that consumers guess. Go modules enforce path discipline for major; documentation must follow.

### Tag security and checksum

When a tag is published:

- **do not move** git tag to another commit;
- `go.sum` and sumdb remember content hash for that version;
- moving tag looks like same version string, different code — “works on my machine” and security incident.

Pseudo-version pins commit **explicitly** — that is why it is useful while tag is not trusted.

### Connection to 05.04

Versions determine **what** proxy downloads; tools `go list -m`, `go mod graph`, and `go get -u` show **how** the graph looks in practice. Next lesson adds replace, vendor, and env policies — but semver/path rules from this lesson remain the foundation.

## Rules and syntax

### For library authors

1. API break after v1 → new major + new path suffix for v2+.
2. Semver tag must match `module` line content (`/v2` for v2 tag).
3. Do not move git tag after release.
4. Use v0 while API is not ready for v1 promise.
5. README: clearly state import path per major.

### For consumers

```go
import (
    alat "github.com/org/alat"       // v1 line
    alat2 "github.com/org/alat/v2"   // v2 line
)
```

### Pre-release policy

`v1.3.0-beta.1` is valid semver. Do not expect it to appear in build as “ordinary” upgrade without explicit `@v1.3.0-beta.1` or similar.

## Examples

### Example 1 — two majors in `require`

**Context:** gradual service migration from v1 to v2.

`go.mod`:

```go
module example.com/moj-servis

go 1.22

require (
    github.com/org/tracer v1.4.2
    github.com/org/tracer/v2 v2.1.0
)
```

`main.go`:

```go
package main

import (
	"fmt"

	tracer "github.com/org/tracer"
	tracer2 "github.com/org/tracer/v2"
)

func main() {
	fmt.Printf("v1 type: %T\n", tracer.Client{})
	fmt.Printf("v2 type: %T\n", tracer2.Client{})
}
```

**Trace:**

```bash
go mod tidy
go build -o bin/app .
```

```text
# build successful — both modules in graph
```

#### What happens here

Two majors live side by side because import paths differ. Migration can go package by package.

### Example 2 — error: v2 API without `/v2` suffix

**Wrong import:**

```go
import "github.com/org/lib" // you expect v2 types
```

**Trace:**

```bash
go build .
```

```text
# undefined: NewClientV2
# or: package does not have symbol from v2 documentation
```

#### What happens here

Old path stays on v1 line. Module identity is path + version line. Without `/v2` you are not at the v2 counter.

**Correct:**

```go
import "github.com/org/lib/v2"
```

```bash
go get github.com/org/lib/v2@v2.0.0
```

### Example 3 — pseudo-version in `go.mod`

**Context:** need commit before tag.

```go
require example.com/eksperiment v0.0.0-20240506120000-0123456789ab
```

`main.go`:

```go
package main

import (
	"fmt"

	"example.com/eksperiment/ping"
)

func main() {
	fmt.Println(ping.OK())
}
```

**Trace:**

```bash
go get example.com/eksperiment@0123456789ab
go mod tidy
go build .
```

```text
go: added example.com/eksperiment v0.0.0-20240506120000-0123456789ab
```

#### What happens here

Go records exact code snapshot. Build is reproducible without a pretty tag.

### Example 4 — v0 signature break (author perspective)

```go
// v0.3.0
package greeter

func Hello(name string) string { return "hello " + name }
```

```go
// v0.4.0 — author changes signature
package greeter

func Hello(name string, loud bool) string {
	if loud {
		return "HELLO " + name
	}
	return "hello " + name
}
```

**Consumer trace:**

```bash
go get example.com/greeter@v0.4.0
go build ./...
```

```text
./main.go:10: not enough arguments in call to greeter.Hello
```

#### What happens here

on v0 semver allows break without new major path. Consumer must read release notes.

### Example 5 — `go list -m -versions` and tag choice

**Trace:**

```bash
go list -m -versions github.com/google/uuid
```

```text
github.com/google/uuid v1.0.0 v1.1.0 ... v1.6.0
```

```bash
go get github.com/google/uuid@v1.6.0
go list -m github.com/google/uuid
```

```text
github.com/google/uuid v1.6.0
```

#### What happens here

You explicitly pin stable version on known path (v1 line without `/v2`).

## Decision analysis

| Question | Decision |
|---------|--------|
| Library still changes API every week | stay on v0 or do not publish widely |
| API stable for external consumers | tag v1 on base path |
| Breaking change after v1 | plan v2 + `module .../v2` |
| Need urgent commit fix before tag | pseudo-version, then tag later |
| Large migration in monolith | hold v1 and v2 in parallel temporarily |
| Legacy `+incompatible` in dependency | plan migration, do not copy pattern |

## Trade-offs

| Choice | You gain | You pay |
|-------|---------|--------|
| Strict semver + `/v2` | clear compatibility | more work migrating imports |
| Eternal v0 | iteration speed | less consumer trust |
| Long pseudo-versions in production | flexibility | worse readability, harder audit |
| Skipping major path rules | short-term laziness | ecosystem and cache breakage |
| Parallel v1 and v2 | safe migration | larger binary graph, double maintenance |

## Common mistakes

### 1. Tag `v2.0.0` without `module .../v2`

- **Wrong:** `module github.com/org/lib` + git tag `v2.0.0`.
- **What you see:** `go get` / proxy errors, consumers cannot import `/v2` consistently.
- **Why it fails:** semver major and module path must align.
- **Correct:** `module github.com/org/lib/v2` before publishing v2 tags.

### 2. Import v2 without `/v2` suffix

- **Wrong:** `import "github.com/org/lib"` expecting v2 API.
- **What you see:** missing types/functions from v2 docs.
- **Why it fails:** v1 and v2 are different modules.
- **Correct:** `import "github.com/org/lib/v2"`.

### 3. Moving git tag after release

- **Wrong:** `git tag -f v1.2.0` to new commit.
- **What you see:** checksum mismatch, CI passes/fails randomly.
- **Why it fails:** same version string, different archive content.
- **Correct:** new tag (e.g. `v1.2.1`) or new major line.

### 4. Treating v0 as production SLA

- **Wrong:** “we are on v0.18, surely stable”.
- **What you see:** frequent build breaks on minor upgrade.
- **Why it fails:** semver allows API break on v0.y.
- **Correct:** pin version, read changelog, push author toward v1.

### 5. Fear of pseudo-versions

- **Wrong:** manually delete pseudo-version from `go.mod` without tag.
- **What you see:** unstable build or return to old commit.
- **Why it fails:** precise pin is lost.
- **Correct:** accept pseudo-version until tag exists; then `go get @vX.Y.Z`.

### 6. Expecting MINOR to break API on v1

- **Wrong:** author changes signature in `v1.3.0` without major bump.
- **What you see:** lost trust, broken consumers.
- **Why it fails:** violates semver promise on v1 line.
- **Correct:** v2 module + `/v2` path.

### 7. `go get @v2` on old module path

- **Wrong:** `go get github.com/org/lib@v2.0.0` without `/v2` in author module imports.
- **What you see:** confusing messages about packages and versions.
- **Why it fails:** v2 tag belongs to module with `/v2` path.
- **Correct:** `go get github.com/org/lib/v2@v2.0.0`.

## Idiomatic Go

- Respect major path suffix without exceptions for public v2+ modules.
- Prefer semver tags over long-term pseudo-versions in production.
- In README write which major path to import.
- Breaking change = new major module, not “silent” minor on v1.
- In applications upgrade major in controlled PR with tests.
- Use `go list -m -versions` before `@latest` decision.

## Practical scenario

Team uses `internal-auth v1.8`. Author publishes `v2.0` with new context-first API.

1. First try: `go get github.com/firma/internal-auth@v2.0.0` on old import path — failure or wrong graph.
2. Fix: import `github.com/firma/internal-auth/v2`, `go get` new module.
3. Adapter layer maps old calls to v2 over two weeks.
4. Hotfix commit before tag `v2.0.1` — short pseudo-version in one service’s `go.mod`.
5. After tag, everyone moves to `v2.0.1`; v1 removed with `go get ...@none` when no references remain.

## Deeper cut: interpreting tags in the repo

Imagine tags in Git repo of library `example.com/alat`:

```text
v0.9.1
v1.0.0
v1.2.0
v2.0.0
v2.0.1
v3.1.0-rc.1
```

| Tag | Module path for import | Note |
|-----|------------------------|----------|
| v0.9.1 | `example.com/alat` | v0 line |
| v1.0.0 | `example.com/alat` | first stable signal |
| v1.2.0 | `example.com/alat` | minor within v1 |
| v2.0.0 | `example.com/alat/v2` | mandatory suffix |
| v2.0.1 | `example.com/alat/v2` | patch on v2 module |
| v3.1.0-rc.1 | `example.com/alat/v3` | pre-release — conscious decision |

Self-check questions:

1. May consumer import v1 and v2 in same program? **Yes** — different modules.
2. Is `v3.1.0-rc.1` default `@latest`? **No** — pre-release is not mixed with stable `@latest` the same way.

### Pseudo-version in CI log

When CI prints:

```text
example.com/lib v0.0.0-20240601101010-deadbeefcafe
```

in ticket write:

- which commit (hash);
- why no tag (fork, urgent fix, waiting release process);
- date when you move to semver tag.

Pseudo-version is a **bridge**, not long-term production destination.

### Another practical example: v1 → v2 migration

```go
import (
    oldlib "example.com/analizator"
    newlib "example.com/analizator/v2"
)
```

Step strategy:

1. Add v2 beside v1 in `go.mod`.
2. Move one package per PR to `newlib`.
3. Remove references to `oldlib`.
4. `go get example.com/analizator@none` if v1 no longer needed.
5. `go mod tidy` and full `go test ./...`.

This is controlled migration instead of one “big bang” commit.

### Semver and team communication

In CHANGELOG write clearly:

- **MINOR**: new functions, old calls still work;
- **PATCH**: fixes without signature change;
- **MAJOR**: what exactly breaks, new import path, recommended migration steps.

Without that consumers guess. Go modules enforce path discipline for major; human documentation must follow the tool.

### Answers

1. **MAJOR** — breaking changes (after v1 goes with new path); **MINOR** — compatible new capabilities; **PATCH** — compatible fixes.
2. So incompatible API is separate module; enables parallel v1/v2 use and clear import identity.
3. **No** — different module paths, separate MVS nodes.
4. When you pin exact commit without (matching) tag or before tag is published.
5. **v0** — API may break; **v1** — semver compatibility promise within major on same path.
6. Same version string, different content hash — breaks `go.sum`/sumdb trust.
7. `module .../v3`, `import ".../v3/..."`, `require .../v3 v3.x.y`.
8. Newest **stable** version, not pre-release, unless explicit selector says otherwise.
9. Go module convention: first stable line is default path without suffix; `/vN` starts at v2.
10. `go get module/path@none` then `go mod tidy`.

## Summary

Versions in Go modules carry semver meaning and affect **import identity**. v0 is unstable on base path; v1 is stable line on same path; v2+ requires `/vN` suffix because major break is a **new module** in the graph. Pseudo-versions legitimately pin commits. MVS resolves versions within each module path separately. Next lesson introduces advanced tools: `replace`, vendor, proxy env, and graph diagnostics.
