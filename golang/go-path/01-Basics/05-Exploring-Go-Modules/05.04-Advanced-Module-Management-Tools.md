# 05.04 Advanced Go module management tools

> **Go Path - Zero to Gopher** / **01 Basics → Exploring Go Modules** / Lesson 05.04

`replace`, `exclude`, vendor, `GOPROXY`, `GOSUMDB`, `GOPRIVATE`, graph diagnostics, and controlled upgrade — tooling above basic `go mod tidy` / `go get`.

## Lesson goals

After this lesson you should be able to:

- use **`replace`** and explain how it changes module mapping at build time;
- apply **`exclude`** when a specific version must leave the graph;
- vendor dependencies with **`go mod vendor`** and know the effect of **`-mod=vendor`** on build;
- configure **`GOPROXY`**, **`GOSUMDB`**, **`GOPRIVATE`** (and if needed **`GONOPROXY`**, **`GONOSUMDB`**);
- explore the graph with **`go list -m`** and **`go mod graph`**;
- run controlled upgrades with **`go get -u`** and **`go get -u=patch`**;
- use **`go mod download`**, **`go mod verify`**, and **`go mod edit`** for operational tasks;
- distinguish local development, CI policy, and production trust.

## Prerequisite

- Lessons **05.01–05.03** (modules, dependencies, semver and path rules).
- Terminal access and ability to temporarily change env vars in session.
- Go **1.22+**.
- Basic understanding of network (HTTP proxy) and private Git hosting.

## Problem this lesson solves

Basic tidy/get workflow is not enough when:

- you debug a bug in a dependency on disk next to the app;
- corporate modules must not go to public proxy or public sum database;
- CI requires offline or vendored build;
- you do not know who pulled a transitive library with CVE label;
- you need to bump patch/minor versions without blind “latest on everything”;
- you need to temporarily replace module with fork or local copy;
- suspicious module version must be excluded until fix arrives.

This lesson gives **diagnostics and control**, not just “add import”.

## Mental model

Three layers of working with modules:

```text
1. Declaration     →  go.mod / go.sum (what you want, hashes)
2. Transport       →  GOPROXY, GOSUMDB, GOPRIVATE (where from and with what trust)
3. Materialization →  module cache ($GOPATH/pkg/mod) or vendor/
```

Key directives in `go.mod`:

| Directive | Effect on build |
|-----------|-----------------|
| **`replace`** | changes mapping “module path + version → source” **only in your module** |
| **`exclude`** | forbids a specific version in MVS resolution |

Env variables:

| Env | Role |
|-----|--------|
| **`GOPROXY`** | list of proxies and `direct` fallback |
| **`GOSUMDB`** | checksum database for public modules |
| **`GOPRIVATE`** | module patterns that skip public proxy/sumdb flow |

Diagnostics:

```text
go list -m   →  what was selected (MVS result)
go mod graph →  who requires whom (graph edges)
```

`replace` does **not** change remote repository — it changes locally how **your** build resolves modules.

## Mechanism

Read this section carefully — details here save hours of debugging.

### `replace` — what exactly happens at build

`replace` directive in `go.mod` tells the tool: when this project asks for module `M` (and optionally version `v`), use **another source**.

Syntax (real forms):

```go
replace example.com/lib => ../lib
replace example.com/lib v1.2.3 => ../lib
replace example.com/lib v1.2.3 => example.com/lib v1.2.4
replace example.com/lib => github.com/fork/lib v1.2.5
replace example.com/lib => ./third_party/lib
```

Effect during **`go build`** / **`go test`**:

1. Compiler and module loader still see **original** import path in Go code (`import "example.com/lib/..."`).
2. Loader maps that module to **replacement** from `replace` (local folder, other version, fork).
3. **`go.sum`** still records hashes of **downloaded** content (replacement must be consistent).
4. Replacement applies **only** to module containing `replace` — other projects in monorepo without that line do not see same replacement.

Local development (most common case):

```text
workspaces/
  app/          ← go.mod with replace => ../lib
  lib/          ← go.mod module example.com/skola/lib
```

Without publishing tag in `lib`, you change API and immediately build `app`.

**Important:** `replace` with relative path `../lib` on developer disk **does not** carry same build to CI machine of another colleague if that path does not exist. Therefore commit `replace => ../` on shared branch is risky.

### `exclude` — ban one version

```go
exclude example.com/lib v1.2.7
```

MVS will **never** pick exactly `v1.2.7` for that module. If that was the only solution, tool seeks next compatible one.

Used rarely:

- known broken release;
- temporary guard until `v1.2.8` arrives;
- coordination with `go get` to fix version.

`exclude` is **not** long-term strategy — upgrade or fork + `replace` fix root cause.

### `go mod vendor` and `-mod=vendor`

```bash
go mod vendor
```

Copies source code (and module `go.mod`/`go.sum` per rules) into **`vendor/`** at root of your module.

Build with vendor copy:

```bash
go build -mod=vendor -o bin/app .
```

What happens:

- loader prefers **`vendor/`** over network download (when `-mod=vendor` active);
- reproducibility does not depend on current proxy state;
- diff in `vendor/` can be large — team decides whether to commit vendor.

Go also supports **`-mod=readonly`** (does not change modules during build) and default behavior depends on version and presence of `vendor/` — in CI be **explicit** in script.

When vendor makes sense:

- Docker build without network in compile stage;
- strict audit “exactly these files enter artifact”;
- environments where proxy is unstable.

When it is excess:

- small services with normal proxy access and committed `go.sum`;
- frequent dependency upgrade (vendor diff chokes review).

### `GOPROXY` — where module is downloaded

Default (typical):

```bash
go env GOPROXY
```

```text
https://proxy.golang.org,direct
```

Meaning:

- first try **module proxy** (cache, speed, stability);
- if proxy cannot, go **`direct`** to VCS (git) source.

Example temporary change in session (PowerShell):

```powershell
$env:GOPROXY = "https://proxy.golang.org,direct"
```

Example fully direct download (slower, sometimes needed in diagnostics):

```powershell
$env:GOPROXY = "direct"
```

**`GONOPROXY`** — pattern list of modules that **always** go direct (often subset of `GOPRIVATE`).

### `GOSUMDB` — integrity verification

Default:

```bash
go env GOSUMDB
```

```text
sum.golang.org
```

When downloading public module, tool compares content hash with local `go.sum` and public database. Mismatch **stops** build.

Exclusion for private paths goes via **`GOPRIVATE`** (and if needed **`GONOSUMDB`**).

### `GOPRIVATE` — private modules

```bash
go env -w GOPRIVATE=git.firma.local/*,github.com/firma/*
```

Effect (high level):

- modules matching pattern **do not go** through public proxy the same way;
- sumdb check skipped for those paths (so internal modules need not be in public database).

**Authentication** (SSH key, token) must still work — `GOPRIVATE` only steers **module policy**, does not log you into Git.

Trace typical error without `GOPRIVATE`:

```text
410 Gone
invalid checksum
authentication required
```

After configuration and correct Git access, `go get git.firma.local/tim/sdk@v1.2.0` works.

### `go list -m` — selected versions

Useful commands (real):

```bash
go list -m all
go list -m github.com/google/uuid
go list -m -versions github.com/google/uuid
go list -m -json all
```

| Flag / form | What you get |
|--------------|-------------|
| `go list -m all` | all modules in build graph with selected version |
| `go list -m MOD` | one module |
| `-versions` | known versions from proxy/VCS |
| `-json` | machine-readable output for scripts |

Difference vs “manually reading `require`”: you see **transitive** modules and exact MVS versions, including `// indirect`.

### `go mod graph` — who requires whom

```bash
go mod graph
```

Output (format):

```text
example.com/app github.com/google/uuid@v1.6.0
github.com/some/parent github.com/google/uuid@v1.5.0
```

Each line: **parent** → **child@version** (requirement in graph).

Filtering (Windows):

```powershell
go mod graph | findstr uuid
```

Used for CVE: find **parent** module pulling vulnerable version, then upgrade parent or child directly.

### `go get -u` and `-u=patch`

```bash
go get -u ./...
go get -u=patch ./...
go get -u github.com/org/lib
```

| Pattern | Behavior (simplified) |
|---------|------------------------------|
| `-u` | bump to newer minor/patch in semver sense for modules in argument |
| `-u=patch` | patch only within same minor line |
| `./...` | all packages in module |

After upgrade always:

```bash
go test ./...
go mod tidy
```

`-u` is **not** substitute for semver awareness on major migration (v2 path — lesson 05.03).

### `go mod download`

```bash
go mod download
go mod download github.com/google/uuid@v1.6.0
go mod download -json
```

Downloads modules to **module cache** without build. Useful for:

- warm-up CI cache;
- check whether proxy/VCS returns module;
- scripts preparing environment.

### `go mod verify`

```bash
go mod verify
```

Verifies module content in local cache matches `go.sum`. If someone manually touches `$GOPATH/pkg/mod`, verify will notice.

### `go mod edit` — programmatic `go.mod` changes

Real flags:

```bash
go mod edit -require=example.com/lib@v1.2.0
go mod edit -droprequire=example.com/lib
go mod edit -replace=example.com/lib=../lib
go mod edit -dropreplace=example.com/lib
go mod edit -exclude=example.com/lib@v1.2.7
go mod edit -dropexclude=example.com/lib@v1.2.7
go mod edit -go=1.22
```

Used in scripts and automation instead of manual editing.

### How layers join in one build

```text
go build
   │
   ├─► load go.mod (+ replace/exclude)
   ├─► resolve graph (MVS)
   ├─► for each module: GOPRIVATE? → direct / custom proxy
   │                    else GOPROXY chain
   ├─► verify go.sum / GOSUMDB (where applicable)
   ├─► if -mod=vendor → read vendor/
   └─► compile packages
```

### `replace` vs `go.work` (short note)

Go **workspace** (`go.work`) solves multi-module local development without committed `replace` in each `go.mod`. This lesson focuses **`replace` in go.mod** because that is what you most often see in existing repos and CI logs. Workspace is alternative for local monorepo — both change **where** code comes from, not import path in source.

## Rules and syntax

### `replace` in team

- local `replace` in uncommitted `go.mod` — OK for daily work;
- commit `replace => ../relative` — often bad for CI on other machines;
- fork `replace` — document reason, removal deadline, link to upstream issue.

### `exclude` in team

- temporary measure + ticket for upgrade;
- do not pile exclude lists for years;
- after fix release: `go mod edit -dropexclude=...`.

### Vendor policy

- if you commit `vendor/`, CI must use `-mod=vendor`;
- otherwise vendor in repo gives false sense of control;
- periodically `go mod vendor` after tidy so vendor does not go stale.

### Env priority

| Method | Duration |
|-------|----------|
| `go env -w GOPRIVATE=...` | per-user on machine |
| `$env:GOPRIVATE=...` in session | temporary |
| CI environment variables | per pipeline |

## Examples

### Example 1 — local `replace` and build effect

Structure:

```text
workspaces/
  app/
  lib/
```

`app/go.mod`:

```go
module example.com/skola/app

go 1.22

require example.com/skola/lib v0.0.0

replace example.com/skola/lib => ../lib
```

`app/main.go`:

```go
package main

import (
	"fmt"

	"example.com/skola/lib/greet"
)

func main() {
	fmt.Println(greet.Hi("Marko"))
}
```

`lib/go.mod`:

```go
module example.com/skola/lib

go 1.22
```

**Trace:**

```bash
cd app
go build -o bin/app .
./bin/app
```

```text
Hello, Marko
```

Change `greet.Hi` in `lib`, run `go build` again — **without** `go get` tag.

#### What happens here

build uses files from disk in `../lib`, not proxy archive `v0.0.0`.

### Example 2 — `go mod vendor` rhythm

```bash
go mod tidy
go mod vendor
go build -mod=vendor -o bin/app .
```

**Trace (abbreviated):**

```text
# vendor/ filled with module copies from graph
# build does not open network when -mod=vendor
```

#### What happens here

dependencies materialized in repo; offline reproducibility.

### Example 3 — graph diagnostics and transitive dependencies

Small program:

```go
package main

import (
	"fmt"

	"github.com/google/uuid"
)

func main() {
	fmt.Println(uuid.New())
}
```

**Trace:**

```bash
go mod tidy
go list -m all | findstr uuid
go mod graph | findstr uuid
```

```text
github.com/google/uuid v1.6.0
example.com/demo github.com/google/uuid@v1.6.0
```

#### What happens here

you see selected version and direct link app → uuid (plus eventual indirect parents in larger project).

### Example 4 — private module pattern

```bash
go env -w GOPRIVATE=git.firma.local/*
go env -w GOPROXY=https://proxy.golang.org,direct
go get git.firma.local/tim/sdk@v1.2.0
```

**Trace (before auth fix):**

```text
fatal: could not read Username for 'https://git.firma.local'
```

**After SSH and GOPRIVATE:**

```bash
git ls-remote git@git.firma.local:tim/sdk.git
go get git.firma.local/tim/sdk@v1.2.0
go list -m git.firma.local/tim/sdk
```

#### What happens here

public modules still may use proxy; internal path bypasses public sum/proxy flow.

### Example 5 — careful upgrade

```bash
go get -u=patch ./...
go test ./...
go list -m -u all
```

**Trace:**

```text
go: upgraded github.com/foo/bar v1.2.0 => v1.2.3
ok      example.com/app   0.412s
```

#### What happens here

patch-first policy reduces risk before wider `-u`.

### Example 6 — `exclude` + upgrade

`go.mod` temporarily:

```go
exclude github.com/broken/lib v1.2.7
```

**Trace:**

```bash
go get github.com/broken/lib@v1.2.8
go mod edit -dropexclude=github.com/broken/lib@v1.2.7
go mod tidy
```

#### What happens here

bad version excluded from MVS until you move to fix.

### Example 7 — `go mod download` and `go mod verify`

```bash
go mod download -json github.com/google/uuid@v1.6.0
go mod verify
```

**Trace:**

```text
all modules verified
```

#### What happens here

confirmation of cache integrity vs `go.sum`.

## Decision analysis

| Need | Tool / command |
|---------|----------------|
| Develop library beside app | `replace => ../lib` (local) |
| Bad release in ecosystem | `exclude` + `go get` to fix |
| Offline / audit build | `go mod vendor` + `-mod=vendor` |
| Internal Git modules | `GOPRIVATE` (+ auth) |
| “Who brought this lib?” | `go mod graph`, `go list -m all` |
| Regular hygiene upgrade | `go get -u=patch`, then test, then `-u` |
| Automatic go.mod edit | `go mod edit -require=...` |
| Cache check | `go mod verify` |

## Trade-offs

| Technique | Plus | Minus |
|---------|------|-------|
| `replace` | fast feedback loop | easily “leaks” into git |
| `vendor/` | offline reproducibility | large diff, merge noise |
| public proxy | speed, cache | not for secret modules |
| sumdb | integrity of public modules | private path must be excluded |
| aggressive `-u` | fresh patches | higher semver break risk |
| `exclude` | quick guard | masks debt without upgrade |

## Common mistakes

### 1. Commit local `replace` that works only on one machine

- **Wrong:** `replace => ../lib` in shared `main` branch without monorepo layout on CI.
- **What you see:** CI “module not found” or empty path.
- **Why it fails:** relative path does not exist on build agent.
- **Correct:** local replace without commit, `go.work`, or published module / fork with documented replace.

### 2. `GOPRIVATE` not configured

- **Wrong:** internal module goes to `proxy.golang.org`.
- **What you see:** 410, auth, checksum errors.
- **Why it fails:** proxy must not serve private code.
- **Correct:** `go env -w GOPRIVATE=git.firma.local/*` and correct Git access.

### 3. Vendor in repo without CI `-mod=vendor`

- **Wrong:** `vendor/` committed, CI builds by default and still pulls network.
- **What you see:** vendor stale, build does not use what you think.
- **Why it fails:** flag not aligned with policy.
- **Correct:** explicit `go build -mod=vendor` in CI/Dockerfile.

### 4. `exclude` as permanent solution

- **Wrong:** exclude list grows for years.
- **What you see:** hard upgrades, MVS surprises.
- **Why it fails:** exclude does not fix cause.
- **Correct:** upgrade, `go get` fix version, remove exclude.

### 5. Upgrade without tests

- **Wrong:** `go get -u ./...` and immediate merge.
- **What you see:** production incident after deploy.
- **Why it fails:** transitive changes not visible in application diff.
- **Correct:** `go test ./...` and review `go mod` diff.

### 6. Only `go.mod` without `go list -m all`

- **Wrong:** debug only direct `require` lines.
- **What you see:** “uuid is old” though you bumped direct dependency.
- **Why it fails:** MVS and transitive parents hold old version.
- **Correct:** `go mod graph` + upgrade parent or targeted `go get`.

### 7. Wrong `GOPROXY=direct` in production without reason

- **Wrong:** proxy disabled globally.
- **What you see:** slower, less stable builds.
- **Why it fails:** lose cache and proxy benefits.
- **Correct:** default proxy for public modules; `direct` only for diagnostics.

## Idiomatic Go

- `replace` locally; remove before final PR (except agreed fork with deadline).
- Private paths explicitly in `GOPRIVATE` and onboarding docs.
- Explore graph with tools, not guessing.
- Patch-first upgrade policy for production services.
- Document: vendor yes/no, CI `-mod` flag, env patterns.
- After every dependency change: `go mod tidy` + test.

## Practical scenario

**Case A — CI and internal module:** build fails with auth error on `git.firma.local`. Developer had no `GOPRIVATE`. After `go env -w GOPRIVATE=git.firma.local/*` and SSH in onboarding checklist, pipeline passes.

**Case B — overnight build without network:** team introduces `go mod vendor` and `-mod=vendor` in Dockerfile. Build stage does not depend on proxy at that moment.

**Case C — CVE in transitive library:** `go mod graph | findstr vulnerable` shows parent; `go get parent@newer` raises whole subgraph; temporary `exclude` only until vendor publishes fix.

**Case D — debug in fork:** `replace orig => github.com/mojfork/orig v1.2.4-fix` until patch merges; PR describes replace removal deadline.

## Diagnostic scenario step by step

Symptom: build pulls old transitive library with CVE label.

1. `go list -m all | findstr affected-module`
2. `go mod graph | findstr affected-module` — who is parent?
3. `go get parent@newer` or `go get affected-module@fixed-version`
4. `go test ./...`
5. `go mod tidy`
6. commit `go.mod` + `go.sum`

If fixed version does not exist: temporary `exclude` + ticket to vendor + consider fork with `replace`.

### Private modules — short list

```bash
go env -w GOPRIVATE=git.firma.local/*
# if needed:
# go env -w GONOPROXY=git.firma.local/*
# go env -w GONOSUMDB=git.firma.local/*
```

Verify SSH access:

```bash
git ls-remote git@git.firma.local:tim/sdk.git
```

Without auth, modules will not work — env only steers policy.

### Vendor checklist for Dockerfile

```dockerfile
COPY go.mod go.sum ./
COPY vendor ./vendor
RUN go build -mod=vendor -o /app ./cmd/app
```

No network in build stage. Cost: larger copy context and obligation to refresh vendor.

### `go list -m -u` — what is stale

```bash
go list -m -u all
```

Output marks modules where newer version exists (format depends on Go version). Use after `-u=patch` to see what else can rise.

### Replace in build graph — mental check

Before commit `replace` ask:

1. Does CI have same folder layout?
2. Does fork replace have removal deadline?
3. Does `go.sum` reflect actual replacement content?

If answer to first is “no” — do not commit relative replace.

## Check questions

1. What is `replace` for, and what is `exclude` for?
2. How does `replace` affect import paths in `.go` files?
3. When does vendor make sense, and when is it excess?
4. What does `GOPRIVATE` do vs proxy and sumdb?

### Answers

1. **`replace`** changes module source for your build; **`exclude`** forbids one version in MVS.
2. **Does not change** — imports stay same; where module loads from changes.
3. Vendor makes sense for offline/audit/strict CI; excess when proxy + `go.sum` enough and vendor goes stale.
4. **`GOPRIVATE`** marks modules that must not go through public proxy/sumdb flow like public modules.
5. Finds **parent** node pulling vulnerable version; you know where to upgrade.
6. Raises only patch — smaller semver jump, lower API break risk.
7. CI and other developers do not have same relative path on disk.
8. **Transitive** modules and exact MVS versions, including indirect.
9. **`download`** only fills cache; **`build`** compiles and pulls modules as needed.
10. E.g. **`go mod edit -require=example.com/lib@v1.2.0`**.

## Summary

Advanced module management combines local replacements (`replace`), version exclusions (`exclude`), vendor materialization, and network trust policies (`GOPROXY`, `GOSUMDB`, `GOPRIVATE`). `go list -m` and `go mod graph` reveal actual graph and transitive links. `go get -u` and `-u=patch` do version hygiene with tests. `go mod download`, `verify`, and `edit` supplement operational work.
