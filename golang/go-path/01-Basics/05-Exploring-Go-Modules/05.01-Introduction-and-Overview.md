# 05.01 Introduction to Go modules: why they exist and how they work

> **Go Path - Zero to Gopher** / **01 Basics → Exploring Go Modules** / Lesson 05.01

## Lesson goals

After this lesson you should be able to:

- explain why GOPATH mode is over and what modules replace;
- read `go.mod` and understand the role of the **module path**;
- distinguish the role of `go.sum` from `go.mod`;
- describe *minimal version selection* (MVS) in plain language;
- connect modules to reproducible builds in the team and CI;
- read basic env values (`GOPROXY`, `GOSUMDB`, `GOMOD`) and know what they mean.

## Prerequisite

- Go **1.22** or newer installed and available on `PATH`.
- Basic knowledge of **package**s, `import` paths, and the `go run` / `go build` commands.
- Working in a terminal (PowerShell, bash, or similar).
- You do not need prior experience with the old GOPATH workflow, but it helps if you have it.
- Useful: basic git (clone, commit) — modules live in the repo.

## Problem this lesson solves

Before modules, Go projects often depended on the global `GOPATH` tree. That meant:

- dependencies lived **outside** the project itself, in a shared folder;
- versions were not clearly “locked” in the repo;
- two projects on the same machine easily stepped on each other with the same library checkout;
- CI and the local machine did not always have the same set of libraries;
- “works on my laptop” was a common incident, not an exception.

Imagine: a team has three services. They all import `github.com/firma/platni-sdk`. In the GOPATH era that often meant **one** folder on disk. When one developer runs `git pull` in that folder because of a breaking change, the other two services mysteriously fail — even though nobody touched their code.

A module fixes reproducibility: the project carries its dependency declaration (`go.mod`) and proof of the content of those dependencies (`go.sum`). The team does not guess what is “currently on disk”; it builds from the declared graph.

Without that contract:

1. onboarding takes longer (you have to guess versions);
2. security review has nothing to compare (no hashes);
3. upgrading a library is a random event, not a PR with a diff.

## Mental model

Think of a module as a **boundary contract for the project**:

1. **Name (module path)** — public address under which others import your code.
2. **Language version** — which Go version is the minimum for that module (`go` directive).
3. **Requirement list** — which modules and which versions your code expects (`require`).
4. **Checksum** — confirmation that downloaded content is exactly what was seen before (`go.sum` + checksum database).

Simple formula:

```text
go.mod  = “what I want” (identity + requirements)
go.sum  = “what I actually got and verified” (hashes)
```

The compiler and the `go` tool together build a **dependency graph**, not a random folder under `$GOPATH/src`.

In the mental model, keep these distinctions:

| Term | What it is | What it is not |
|-------|-----------|----------|
| **module** | version and dependency boundary | one file or one package |
| **package** | compilation unit (`package name`) | the same as module |
| **module path** | logical name in the ecosystem | necessarily the folder name on disk |
| **version (MVS)** | smallest sufficient that satisfies all requirements | always “the newest that exists” |

Visually:

```text
                    ┌─────────────────────────────┐
                    │         your module         │
                    │  module example.com/app     │
                    │  go 1.22                    │
                    │  require ( ... )            │
                    └─────────────┬───────────────┘
                                  │
              ┌───────────────────┼───────────────────┐
              ▼                   ▼                   ▼
         module A@v1.2        module B@v3.1        module C@v0.4
              │                   │
              └─────────┬─────────┘
                        ▼
                   (indirect dependencies)
```

MVS decides **which** version of each module enters the build. `go.sum` confirms that the content of that version is the same as before.

## Mechanism

This section is the heart of the lesson. Read slowly — each subsection builds on the next.

### Why GOPATH mode is over

In the GOPATH era, `import "github.com/foo/bar"` looked for files on a physical path like:

```text
$GOPATH/src/github.com/foo/bar
```

The version was often:

- “whatever is currently in that folder”, or
- what `vendor` copied into the project (manually or semi-automatically).

Problems piled up:

1. **One checkout, many consumers** — upgrading one project breaks another.
2. **No clear pin in git** — the repo does not carry a version contract.
3. **Hard to share with CI** — “works locally” because your `GOPATH` happens to be good.
4. **Poor isolation** — experiments and production share the same space.

Modules introduce a different contract:

- `go.mod` at the project root (or module root);
- semantic versions (semver) as part of the ecosystem;
- proxy and checksum database as the default path to source code;
- isolation: multiple projects can depend on different versions of the same module **without** stepping on each other.

Since Go 1.16+ module mode is the default. In Go 1.22+ you work module-first: you expect `go.mod`, not `GOPATH` as the source of truth.

### Module path — identity, not folder

The **module path** is an identifier, e.g.:

- `github.com/tvojorg/inventar`
- `example.com/skola/vaje`
- `git.firma.local/tim/sdk`

Rules in practice:

- it should be unique in the ecosystem (as much as possible);
- for public modules it usually follows hosting (GitHub, GitLab…);
- for private modules it can be an internal domain;
- major version **v2+** changes the path (`…/v2`) — in detail in lesson 05.03.

Important: you can clone the repo to `D:\temp\xyz` or `/home/marko/projekti/abc`. Imports still use the module path from `go.mod`, **not** the folder name on disk.

### `go.mod` — declaration: `module`, `go`, `require`

Minimal file:

```go
module example.com/demo/inventar

go 1.22
```

What each line means:

| Directive | Role |
|-----------|--------|
| `module` | name / path of this module (module path) |
| `go` | minimum Go version the module expects |
| `require` | direct (and recorded indirect) dependencies |

When you add dependencies, `require` lines appear. Indirect dependencies may be marked `// indirect` — that is **not** an error; it means your code does not import that module directly, but the graph needs it.

Example with requirements:

```go
module example.com/demo/inventar

go 1.22

require (
	github.com/google/uuid v1.6.0
	golang.org/x/text v0.14.0
)

require (
	some.example/transitive v1.0.0 // indirect
)
```

`require` says: “for a build of this module, I need at least this version (lower bound)”. MVS may later choose a **higher** version if another requirement in the graph raises the lower bound.

### `go.sum` — why it exists

`go.sum` stores hash values for modules (and often for `.mod` files). The idea is:

1. `go` downloads the module (usually via proxy);
2. it computes a checksum of the content;
3. it compares with a known value (locally in `go.sum` and/or via the checksum database);
4. if they do not match — **the build stops**.

Why is that critical?

- A git tag can be moved (bad practice, but it happens).
- An archive on the proxy or mirror can be replaced.
- Without a hash, the “same version” does not guarantee the same bytes.

Conceptually, the **checksum database** (`sum.golang.org`, env `GOSUMDB`) is a public log:

```text
for module X at version Y, the expected hash is Z
```

That protects against silent tag changes or malicious archive replacement.

Remember:

- `go.mod` without `go.sum` is an incomplete contract for applications;
- `go.sum` is not “noise” — commit it together with `go.mod`;
- you do not commit cache from `$GOPATH/pkg/mod` — that is the machine’s local cache.

### Minimal version selection (MVS) — in plain language

When multiple packages require the same module at different versions, Go **does not always pick the newest**. Instead:

1. collect all lower bounds (minimum versions someone requires);
2. choose the **largest among those minimums**;
3. that version must satisfy all requirements in the graph.

Example (conceptual):

```text
A requires  lib @ v1.2.0
B requires  lib @ v1.5.0
C requires  lib @ v1.3.0
```

MVS picks `v1.5.0` — that is the smallest version that is ≥ all required minimums in this set.

Why does this matter?

- dependency resolution is **deterministic**;
- there is no “floating latest” behavior that breaks the build overnight;
- upgrade happens when some requirement **raises the lower bound**, not when the author publishes a new tag.

Comparison with other ecosystems (rough):

| Style | Typical behavior |
|------|-------------------|
| npm/yarn with caret | often toward the newest compatible range |
| Go MVS | smallest version that satisfies all minimums |

Subjectively you might think “why don’t I have the newest?” — the answer: because nobody in the graph required more. That is intentional.

### Proxy and checksum database (high level)

Default environment often looks like this:

```bash
go env GOPROXY
go env GOSUMDB
go env GOMOD
```

Interpretation:

- **`GOPROXY`** — where modules are downloaded from (e.g. `https://proxy.golang.org,direct`);
- **`GOSUMDB`** — which checksum database verifies hashes (e.g. `sum.golang.org`);
- **`GOMOD`** — which `go.mod` is active in the current directory.

`direct` in the `GOPROXY` chain means: if the proxy fails / does not apply, go to the VCS source. Private modules (later `GOPRIVATE`) should not go through the public proxy/sumdb flow — that is topic 05.04.

### How `go` enters module mode

If `go.mod` exists in the tree, tools work in the context of that module. Without `go.mod`, behavior depends on the environment — in modern Go expect a module-first approach.

Check:

```bash
go env GOMOD
```

If you see a path to `go.mod`, you are in module context. If you see `/dev/null` or empty (depending on OS), you are not in a module.

### Import paths and module path

An import in code must start with the module path (or a standard library path):

```go
import "example.com/demo/inventar/internal/lager"
```

You do not import relative paths like `../lager` in production style — the module path gives a stable address that does not depend on where the folder is on disk.

### Pseudo-versions (short introduction)

When there is no clean tag, Go may write a **pseudo-version**, e.g.:

```text
v0.0.0-20240506120000-0123456789ab
```

That is not “dirty” — it is a precise pin on a commit. In detail in 05.03. Here it is enough to know: `go.sum` and MVS work with pseudo-versions too.

### `replace` — what it does to the build (short introduction)

The `replace` directive changes the mapping “module path → source code” for **your** build. E.g. a local folder instead of a downloaded version:

```go
replace example.com/lib => ../lib
```

The build then compiles local code. That is a powerful tool for development, but it easily “leaks” into git and breaks CI — in detail in 05.04. In this lesson remember only: `replace` changes **where** code comes from, not the import name in source code.

## Rules and syntax

### Key directives in `go.mod` (overview)

| Directive | Role (brief) | Focus of this lesson |
|-----------|----------------|-------------------|
| `module` | module name / path | yes |
| `go` | minimum Go version | yes |
| `require` | dependencies and lower bounds | yes |
| `exclude` | forbid a specific version | intro (detail 05.04) |
| `replace` | local / temporary source swap | intro (detail 05.04) |
| `retract` | author withdraws a bad version | later |

### What goes in git, and what does not

You usually commit:

- `go.mod`
- `go.sum`

You do not commit:

- arbitrary local cache from the module cache (`$GOPATH/pkg/mod` / `GOMODCACHE`);
- local experiments with `replace` to `../` without team agreement.

### Reading someone else’s `go.mod` — order

1. `module` — who is this?
2. `go` — what is the language minimum?
3. direct `require` lines — what does the author consciously pull?
4. indirect — consequence of the graph, not necessarily the application author’s intent.

### Commands you may already use

| Command | Purpose |
|---------|--------|
| `go mod init` | creates `go.mod` (detail 05.02) |
| `go get` | adds / moves a dependency |
| `go mod tidy` | aligns `go.mod`/`go.sum` with actual imports |
| `go list -m all` | list of selected module versions |
| `go env GOPROXY` / `GOSUMDB` / `GOMOD` | environment diagnostics |

Do not invent flags. If unsure — `go help mod` and `go help get`.

## Examples

### Example 1 — reading a minimal `go.mod`

Create folder and files:

```text
inventar/
  go.mod
  main.go
```

`go.mod`:

```go
module example.com/skola/inventar

go 1.22
```

`main.go`:

```go
package main

import "fmt"

func main() {
	fmt.Println("module works without external dependencies")
}
```

Run:

```bash
cd inventar
go run .
```

Expected output:

```text
module works without external dependencies
```

#### What happens here

1. `go run .` looks for `go.mod` in the tree.
2. It reads `module example.com/skola/inventar` — that is the identity.
3. There are no external `require` entries, so no need for third-party `go.sum` entries either.
4. The build is locally self-contained: only the standard library (`fmt`).

Execution trace (conceptual):

```text
terminal: go run .
    → load go.mod
    → module path = example.com/skola/inventar
    → compile package main
    → run main()
    → print message
```

### Example 2 — dependency and appearance of `go.sum`

Extend `main.go`:

```go
package main

import (
	"fmt"

	"golang.org/x/text/cases"
	"golang.org/x/text/language"
)

func main() {
	c := cases.Title(language.English)
	fmt.Println(c.String("go modules are a boundary contract"))
}
```

Then:

```bash
go get golang.org/x/text@latest
go mod tidy
go run .
```

After that:

- `go.mod` gets a `require` line for `golang.org/x/text`;
- `go.sum` gets hash lines;
- the program prints the title-cased string.

#### What happens here

1. `go get` adds or updates a requirement in `go.mod` (version lower bound).
2. Content is downloaded via proxy (by default, if the network allows).
3. Checksum is computed and written to `go.sum`.
4. `go mod tidy` removes unused requirements and fills in those missing for current code and tests.
5. `go run .` uses the version chosen from the graph, not “whatever you have globally”.

Execution trace:

```text
go get golang.org/x/text@latest
    → version resolution (latest tag / proxy)
    → write require in go.mod
    → download to module cache
    → write hashes to go.sum

go mod tidy
    → scan imports in code and tests
    → align require + go.sum

go run .
    → MVS picks versions
    → verify hashes (go.sum / GOSUMDB)
    → build + run
```

### Example 3 — MVS “in your head” with execution trace

Imagine a conceptual graph (you do not have to reproduce a monorepo):

```text
service-a  →  requires  github.com/primer/lib v1.4.0
service-b  →  requires  github.com/primer/lib v1.7.2
```

If you connect them in one build graph, the chosen version is not an “average” nor “the newest in the world”, but the smallest that satisfies both minimums — here `v1.7.2`.

Small mental simulator:

```text
input requirements: {1.4.0, 1.7.2}
step 1: find max(lower bounds) = 1.7.2
step 2: verify 1.7.2 ≥ each requirement → yes
MVS output: v1.7.2
```

#### What happens here

MVS reduces surprises: upgrade happens only when some requirement in the graph **raises the lower bound**. If tomorrow `service-a` still asks for `v1.4.0` and `service-b` asks for `v1.7.2`, the build still uses `v1.7.2` — not “whatever is latest today”.

### Example 4 — module path vs folder on disk

```text
D:\projekti\inventar-2026\          ← physical folder (can be anything)
go.mod: module example.com/skola/inventar
```

Import in another package within the same module:

```go
import "example.com/skola/inventar/internal/lager"
```

Rename the folder to `inventar-vezba` and run again:

```bash
go test ./...
```

#### What happens here

The module separates **identity** from **location**. Therefore:

- `replace` can redirect source without changing all imports;
- fork and local development do not require renaming all strings in code;
- CI checkout in `/tmp/...` still works.

Execution trace:

```text
disk: D:\projekti\inventar-vezba\
go.mod module path: example.com/skola/inventar
import in code: example.com/skola/inventar/internal/lager
    → Go maps import to package within this module
    → folder name on disk is not part of the import
```

### Example 5 — env diagnostics on an empty module

```bash
mkdir mvs-demo && cd mvs-demo
go mod init example.com/skola/mvs-demo
go env GOMOD
go env GOSUMDB
go env GOPROXY
```

#### What happens here

- `GOMOD` shows which `go.mod` is active (path to the file).
- `GOSUMDB` reveals whether the checksum database is enabled.
- `GOPROXY` shows where modules are downloaded from.

If the checksum database is disabled in a corporate environment, ask the team why — that is a conscious security decision, not default laziness.

## Decision analysis

| Situation | Decision | Why |
|-----------|--------|-------|
| Public open source | real hosting module path | consumers import the same address |
| Internal tool | corporate domain | clear privacy + `GOPRIVATE` later |
| Course / exercise | `example.com/...` | no fake GitHub paths |
| Commit `go.sum` | always for app/lib you share | integrity + reproducibility |
| Reading someone else’s `go.mod` | first `module`/`go`, then direct `require` | indirect are a consequence |
| “I want newest always” | no — use explicit `go get` | MVS and pin prevent overnight breaks |

## Trade-offs

| Approach | Advantage | Cost |
|---------|----------|------|
| Modules + `go.sum` | reproducibility, integrity | initial learning, more files in review |
| Old GOPATH style | sometimes simpler for micro-scripts | poor project isolation |
| Always “latest” dependencies | fast features | unstable builds |
| MVS | predictable graph | sometimes an “older” version than you subjectively expect |
| Public proxy + sumdb | speed and trust | need policy for private modules |

Modules are not magic: you still must understand breaking changes and test upgrades. But the boundary of responsibility is clearer — the contract is in the repo.

## Common mistakes

### 1. Module path = folder name

- **Wrong:** you rename the folder to `moj-inventar` and expect imports to follow that name.
- **What you see:** imports still ask for `example.com/...`; or you manually change everything to the folder name.
- **Why it fails:** module path is the logical identity in `go.mod`, not the directory name.
- **Correct:** keep the module path; the folder on disk may be named anything.

### 2. Deleting `go.sum` “because it is large”

- **Wrong:** you delete `go.sum` before commit.
- **What you see:** CI pulls different content or regenerates a different state.
- **Why it fails:** you lose proof of integrity.
- **Correct:** commit `go.mod` and `go.sum` together.

### 3. Manual `require` without `tidy`

- **Wrong:** you type versions by hand and do not run `go mod tidy`.
- **What you see:** inconsistent graph, odd builds.
- **Why it fails:** the tool and code must agree on actual imports.
- **Correct:** after changing imports — `go get` and/or `go mod tidy`, then review the diff.

### 4. Expecting “always newest”

- **Wrong:** you think Go automatically takes the latest tag.
- **What you see:** “old” version in `go list -m all`.
- **Why it fails:** MVS picks the smallest sufficient version.
- **Correct:** explicitly `go get module@vX.Y.Z` when you want an upgrade.

### 5. Copying someone else’s `go.mod` without changing `module`

- **Wrong:** copy-paste `go.mod` from another project.
- **What you see:** wrong imports, conflicts, confused review.
- **Why it fails:** module path must be yours.
- **Correct:** `go mod init` with the right path, then add dependencies.

### 6. `// indirect` as error

- **Wrong:** you panic-delete all `// indirect` lines.
- **What you see:** `tidy` brings them back or the build breaks.
- **Why it fails:** indirect dependencies are part of the graph.
- **Correct:** read them as a consequence; do not delete by force.

## Idiomatic Go

- One `go.mod` per module (usually per repo for applications).
- Choose module path once and change it rarely.
- `go.mod` and `go.sum` live in version control together.
- Do not rely on global `GOPATH` as the source of truth for dependencies.
- For documentation and course use `example.com/...`.
- Read `go.mod`/`go.sum` diff in code review as part of behavior change.
- Upgrade consciously (`go get`), not by accidental `git pull` in a shared folder.

## Practical scenario

A team runs three microservices. Before modules, they all pulled the same `GOPATH` checkout of library `platni-sdk`. One service urgently moved to a breaking API; the other two failed in CI.

After introducing modules:

1. each service has its own `go.mod`;
2. `platni-sdk` is pinned by version in `require`;
3. `go.sum` in CI verifies the hash;
4. upgrade is done explicitly (`go get`), in a separate PR;
5. `go list -m all` in review shows what was actually selected.

Result: incidents like “it worked on my laptop yesterday” become rarer, because the dependency contract is part of the repo.

Second scenario: the security team asks “which exact version of `uuid` enters the artifact?”. The answer is not “whatever the developer has in cache”, but the line from `go list -m all` + hash from `go.sum`.

## Check questions

1. How do **module** and **package** differ?
2. What is module path and why is it not the same as the path on disk?
3. What role does `go.sum` have that `go.mod` does not?
4. What does the checksum database (`GOSUMDB`) do conceptually?
5. How does MVS pick a version when there are multiple minimums?
6. Why was the GOPATH model problematic for multiple projects on the same machine?
7. Does `// indirect` mean the dependency is not needed for the build? Explain.
8. What does the `go` directive in `go.mod` mean?
9. Why do we commit `go.sum` together with `go.mod`?
10. What does `GOPROXY` control at a high level?

### Answers

1. **Module** is the version and dependency boundary (the whole contract in `go.mod`). **Package** is the compilation unit within a module (`package name`). One module contains one or more packages.
2. Module path is the logical name in the ecosystem (e.g. `example.com/app`). The folder on disk can be anywhere; imports use the path from `go.mod`, not the folder name.
3. `go.sum` stores checksums (hashes) of downloaded content. `go.mod` declaratively says what you want; `go.sum` proves what you got.
4. Public log of expected hashes for (module, version). Prevents silent tag/archive changes.
5. It takes the largest among lower bounds (the smallest version that is ≥ all requirements).
6. Because projects shared the same dependency checkout; upgrading one easily breaks another.
7. No. It often means your code does not import that module directly, but the graph still needs it because of other dependencies.
8. Minimum Go version the module expects (e.g. `go 1.22`).
9. Because it is part of the integrity and reproducibility contract; without it CI may get different content.
10. Where modules are downloaded from (proxy chain, often with `direct` as fallback).

## Summary

Go modules replace GOPATH as the source of truth for project boundaries and dependencies. **Module path** is identity; `go.mod` declaratively describes path, Go version, and `require` requirements; `go.sum` stores checksums for integrity. The checksum database (`GOSUMDB`) supplements local proof with a public record. **MVS** picks the smallest version that satisfies all lower bounds in the graph, which makes builds more predictable. The next step is to actively manage these mechanisms with commands: `go mod init`, `go get`, `go mod tidy`.
