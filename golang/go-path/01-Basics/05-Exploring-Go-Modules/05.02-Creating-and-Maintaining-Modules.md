# 05.02 Creating and maintaining Go modules

> **Go Path - Zero to Gopher** / **01 Basics → Exploring Go Modules** / Lesson 05.02

## Lesson goals

After this lesson you should be able to:

- initialize a module with `go mod init`;
- add and update dependencies via `go get`;
- clean the graph with `go mod tidy`;
- read and understand `require` blocks (direct and `// indirect`);
- tie **tool** dependencies to the project via `tools.go` + build tag pattern (Go 1.22);
- know what we intentionally leave for later (`retract`);
- use `go list -m` to see what was actually selected after tidy.

## Prerequisite

- Lesson 05.01 (module path, `go.mod`, `go.sum`, MVS at high level).
- Go **1.22+**.
- Write access to the project working folder.
- Basic git: you can view `git diff go.mod go.sum`.

## Problem this lesson solves

Many developers “have a module” because someone once ran `go mod init`, but they do not know:

- when `go.mod` changes by itself vs when you must act consciously;
- why `go.sum` grows after `tidy`;
- how to safely bump a library version;
- how to keep generators and linters tied to the project without mixing them with runtime dependencies;
- what to commit after successfully adding a library.

Without a maintenance routine this happens:

1. “zombie” `require` lines stay in `go.mod` after code is deleted;
2. CI fails because one team member has a different generator globally;
3. a PR changes only `go.mod`, not `go.sum` — the contract breaks;
4. someone manually enters a nonexistent tag and loses an hour debugging.

This lesson builds the routine: **init → develop → get → tidy → test → commit**.

## Mental model

Think of `go.mod` as **inventory + policy**, and commands as **warehouse operators**:

| Command | Role in the warehouse |
|---------|-------------------|
| `go mod init` | opens a new warehouse and gives it a name (module path) |
| `go get` | orders or changes version of goods (explicitly) |
| `go mod tidy` | inventory: keep only what code actually uses |
| `go build` / `go test` | consumer that requires inventory to be accurate |
| `go list -m` | read labels on shelves (what was selected) |

You do not “store libraries in the project” as copies (except when you later use vendor). You store the **contract**. Cache on the machine (`GOMODCACHE`) is an ephemeral copy.

Two mental drawers:

```text
RUNTIME dependencies
  → packages your program / library imports
  → enter the final build artifact (indirectly or directly)

TOOL dependencies
  → generators, linter wrappers, stringer, mockgen...
  → needed by CI and developers, not the end user runtime
```

Mixing these two drawers causes confusion: the app “pulls” a tool it does not need in production, or CI lacks a tool because nobody tied it to the module.

## Mechanism

### `go mod init` — opening the contract

```bash
mkdir demo && cd demo
go mod init example.com/skola/demo
```

Result: `go.mod` with `module` and `go` lines. The name you pass **becomes** the module path — choose carefully, because later migration means changing imports.

Check:

```bash
go env GOMOD
type go.mod
```

(On Unix: `cat go.mod`.)

What `init` does **not** do:

- does not download libraries;
- does not create `main.go`;
- does not create `go.sum` until there is something to hash.

### `go get` — explicitly moving requirements

Typical forms (real flags only):

```bash
go get example.com/neki/mod@v1.2.3
go get example.com/neki/mod@latest
go get example.com/neki/mod@none
```

What each does:

| Form | Effect |
|-------|--------|
| `@v1.2.3` | pin to that version (lower bound / requirement) |
| `@latest` | newest known version per tool policy |
| `@none` | remove requirement for that module |

`go get` updates `go.mod` (and often `go.sum`) for the requested version. In Go 1.22+ it remains the main way to explicitly move a dependency.

Note: for upgrading multiple dependencies there is also `go get -u` / `go get -u=patch` — more detail in 05.04. Here remember: `-u` is not magic; always follow with `go test ./...`.

### `go mod tidy` — inventory

```bash
go mod tidy
```

What it does in practice:

1. looks at which **package**s your code (and tests) actually import;
2. adds missing `require` lines;
3. removes requirements that are no longer needed;
4. aligns `go.sum`.

Golden rule: after a larger import refactor — run `tidy` **before** commit.

`tidy` is not a substitute for thinking: if you intentionally wanted an old version and someone else raises the lower bound through another requirement, MVS can still choose higher — but `tidy` at least removes dead entries.

### `require` block — reading the contract

Example:

```go
module example.com/skola/demo

go 1.22

require (
	github.com/google/uuid v1.6.0
	golang.org/x/text v0.14.0
)

require (
	some.example/indirect v1.0.0 // indirect
)
```

Direct dependencies are those your code imports. Indirect ones appear because your direct dependencies (or tool pattern) require them.

`// indirect` is **not** an error. It means: “this module is not a direct import of your code, but the graph needs it”.

### Tool dependencies — `tools.go` pattern (Go 1.22)

Historically developers kept tools via:

- global `go install` (not reproducible per project);
- “dummy” import in a file like `tools.go` with `//go:build tools`.

For **Go 1.22** prefer the classic pattern that works everywhere:

```go
//go:build tools

package tools

import (
	_ "golang.org/x/tools/cmd/stringer"
)
```

Then:

```bash
go mod tidy
go install golang.org/x/tools/cmd/stringer@v0.21.0
```

(Align version with what `go.mod` holds after tidy.)

Why build tag `tools`?

- ordinary `go build` does **not** compile this file;
- blank identifier import (`_`) pulls the module into the dependency graph;
- CI and the team share the same generator version via `go.mod`.

**Optional (newer):** in newer Go versions there is a clearer `tool` flow / `tool` directive in the ecosystem (`go get -tool` and related, depending on exact version). If your team already uses Go that supports it, check official documentation — the goal is the same: reproducible toolchain. For this course and Go 1.22, `tools.go` + build tag is a reliable default.

Practice to take with you:

1. tools should be **tied to the repo**, not only your laptop;
2. CI should be able to install the same generator version;
3. a tool is not a runtime import — do not mix it with application libraries without reason.

### `go list -m` — what was actually selected

```bash
go list -m all
go list -m github.com/google/uuid
```

Useful after `tidy` / `get`: you see the exact version, including indirect. That is the bridge to 05.04 (`go mod graph`).

### What we do not do yet: `retract`

`retract` lets the **author** of a module mark a bad version as withdrawn. That is a topic for library maintainers. In this lesson it is enough to know it exists and is **not** part of everyday consumer `tidy` workflow.

### When `go` changes `go.mod` by itself

Some commands (`go test`, `go build`) may add missing requirements if environment policy allows. Still, the idiomatic workflow is explicit:

1. write code / add import;
2. `go get` or `go mod tidy`;
3. review diff;
4. `go test ./...`;
5. commit `go.mod` + `go.sum`.

### Cache vs contract

```text
go.mod / go.sum     →  source of truth in git
GOMODCACHE          →  local machine cache (do not commit)
vendor/             →  materialization (topic 05.04)
```

`go get` does **not** create a `node_modules`-style folder in the project. Cache is elsewhere; contract is in `go.mod`.

### Extension: `go mod download` and `go mod verify`

```text
go mod download
go mod verify
```

`download` materializes modules in cache. `verify` checks that cached content matches `go.sum`. Use in CI when you suspect cache corruption.

### Extension: `go mod edit`

```text
go mod edit -go=1.22
go mod edit -require=example.com/lib@v1.2.3
```

Programmatically changes `go.mod`. For daily work more often `go get` + `tidy`; `edit` is useful in scripts.

## Rules and syntax

### Module name at `init`

```bash
go mod init <module-path>
```

- use reverse-DNS or hosting path style;
- do not use spaces;
- for course/demo: `example.com/...` is fine;
- choose once — migration hurts.

### Forbidden habits

- Manually deleting half of `go.sum` “to make it shorter”.
- Commit only `go.mod` without `go.sum` in an application repo.
- Changing `require` version by hand without checking the tag exists.
- Global `go install` as the only source of generator for the team.
- Committing local `replace` to `../` without agreement (detail 05.04).

### Team working rhythm

1. Feature branch: add code and import.
2. `go get` or `go mod tidy`.
3. Review `git diff go.mod go.sum`.
4. Run `go test ./...`.
5. Only then commit.

### Anti-pattern checklist

- manually deleting indirect lines “because I do not know what they are” — no;
- commit only half of `go.sum` — no;
- `go get` in production container without pin — no;
- tool installed only on one laptop — no.

## Examples

### Example 1 — init from empty folder

```bash
mkdir cene && cd cene
go mod init example.com/skola/cene
```

`main.go`:

```go
package main

import "fmt"

func main() {
	fmt.Println("module example.com/skola/cene ready")
}
```

```bash
go run .
```

Expected output:

```text
module example.com/skola/cene ready
```

#### What happens here

1. `go mod init` writes identity (`module` + `go`).
2. Without external imports, `go.sum` may stay absent — nothing third-party to hash.
3. `go run .` builds `package main` in that module context.

Execution trace:

```text
go mod init example.com/skola/cene
    → creates go.mod
go run .
    → GOMOD = .../cene/go.mod
    → no external require
    → build + print
```

### Example 2 — adding a library via `go get`

`main.go`:

```go
package main

import (
	"fmt"

	"github.com/google/uuid"
)

func main() {
	id := uuid.New()
	fmt.Println("new id:", id)
}
```

```bash
go get github.com/google/uuid@v1.6.0
go run .
go list -m github.com/google/uuid
```

#### What happens here

1. `go get` pins version in `require`.
2. Module is downloaded to cache; `go.sum` gets checksums (and related `.mod` entries).
3. `go run` uses the selected version.
4. `go list -m` confirms what is in the graph.

Execution trace:

```text
go get github.com/google/uuid@v1.6.0
    → require in go.mod
    → download
    → go.sum hashes
go run .
    → import github.com/google/uuid
    → MVS + verify
    → print UUID
```

### Example 3 — removing dead dependency with `tidy`

1. Delete `uuid` import from code and return to a simple `fmt` example.
2. Leave the old `require` line in `go.mod` on purpose.
3. Run:

```bash
go mod tidy
git diff go.mod go.sum
```

#### What happens here

`tidy` sees code no longer imports `uuid` and removes the unnecessary requirement. Inventory returns to actual usage. That prevents “zombies” in the graph and reduces attack surface.

Execution trace:

```text
code without uuid import
go.mod still has require uuid
go mod tidy
    → scan imports
    → uuid not needed
    → remove require
    → align go.sum
```

### Example 4 — `tools.go` pattern for a generator

`tools.go`:

```go
//go:build tools

package tools

import (
	_ "golang.org/x/tools/cmd/stringer"
)
```

```bash
go mod tidy
go list -m golang.org/x/tools
go install golang.org/x/tools/cmd/stringer@v0.21.0
```

#### What happens here

1. Blank import under `tools` build tag does **not** enter ordinary application build.
2. It still participates in the module graph — so `tidy` pulls the dependency.
3. The team shares the same generator version via `go.mod`, instead of “whatever stringer you have globally”.

Execution trace:

```text
go build .          → ignores tools.go (tag)
go mod tidy         → sees tools.go in module context
                    → adds require for x/tools
go install ...      → installs binary aligned with version
```

### Example 5 — conscious version bump

```bash
go get golang.org/x/text@v0.14.0
go test ./...
go mod tidy
git diff go.mod go.sum
```

#### What happens here

1. `go get` moves lower bound / requirement.
2. Tests confirm no regression.
3. `tidy` cleans eventual noise.
4. Diff shows exactly what enters the PR.

If tests fail, do not mix “tidy noise” with bugfix: either revert version (`go get ...@old`), or fix code in a separate commit.

### Example 6 — `go get ...@none`

```bash
go get github.com/google/uuid@none
go mod tidy
```

#### What happens here

`@none` removes the requirement. If code still imports the package, the next `tidy`/`build` will ask for the dependency again — so remove import first, then `@none` / `tidy`.

## Decision analysis

| Situation | Recommendation | Why |
|-----------|-----------|-------|
| New repo | `go mod init` immediately | choose path before first import |
| New library in code | import, then `go get` or `tidy` | explicit contract |
| Large cleanup | `go mod tidy` + review diff | removes zombies |
| CI | cache module cache, source of truth = `go.mod`/`go.sum` | speed without losing contract |
| Generator in project | `tools.go` + build tag | reproducible toolchain on 1.22 |
| Library upgrade | separate PR + tests | easier review and rollback |
| Library author, bad release | `retract` (later) | not everyday consumer step |

Ask yourself: “Can a new team member run `go test ./...` and get the same graph?” If not — workflow is not done.

## Trade-offs

| Practice | Plus | Minus |
|--------|------|-------|
| Explicit `go get @vX.Y.Z` | control | more typing |
| Always `@latest` | speed | surprises |
| `tools.go` blank import | works on Go 1.22 and wider | feels “weird” to beginners |
| Newer `tool` flow (optional) | clearer semantics | needs newer Go / team agreement |
| Global `go install` only | fast locally | CI drift |
| Manual editing `require` | sense of control | easy inconsistent state |

`retract` is intentionally not in everyday routine — consumers rarely write `retract`; library authors do.

## Common mistakes

### 1. Wrong path at `init`

- **Wrong:** `go mod init demo` then later you want `github.com/org/demo`.
- **What you see:** imports and docs do not match hosting.
- **Why it fails:** module path is identity; migration hurts.
- **Correct:** `go mod init` with the right path immediately (or `example.com/...` for exercise).

### 2. Forgotten `tidy` after deleting packages

- **Wrong:** you delete code, leave `require`.
- **What you see:** false inventory, larger graph, confused review.
- **Why it fails:** contract no longer matches code.
- **Correct:** `go mod tidy` before commit.

### 3. Commit only `go.mod`

- **Wrong:** PR has only `go.mod`, no `go.sum`.
- **What you see:** CI regenerates differently or loses hashes.
- **Why it fails:** incomplete integrity contract.
- **Correct:** always both files together.

### 4. Tool = runtime in the same mindset

- **Wrong:** you treat `stringer` as an application library.
- **What you see:** confusion about what goes to production, odd imports.
- **Why it fails:** tool and runtime have different goals.
- **Correct:** `tools.go` + build tag; runtime imports separate.

### 5. Nonexistent version by hand

- **Wrong:** you enter `v9.9.9` that does not exist.
- **What you see:** error on `go build` / `go get`.
- **Why it fails:** tag/proxy does not know that version.
- **Correct:** `go list -m -versions module` or documented tag, then `go get`.

### 6. Expecting `node_modules` folder

- **Wrong:** you look for library copies in the project after `go get`.
- **What you see:** empty project folder, cache elsewhere.
- **Why it fails:** Go stores contract, not necessarily vendor copy.
- **Correct:** read `go.mod`/`go.sum`; vendor is a conscious decision (05.04).

### 7. `@none` before deleting import

- **Wrong:** you remove requirement while code still imports the package.
- **What you see:** build/`tidy` brings dependency back or breaks.
- **Why it fails:** code still needs the package.
- **Correct:** remove import first, then `@none` / `tidy`.

## Idiomatic Go

- One module, clear path, clean tidy before merge.
- Pin consciously; upgrade in a separate PR.
- Keep toolchain dependencies reproducible (`tools.go` on 1.22).
- Do not commit local `replace` experiments without agreement.
- Read `go.mod` diff as part of code review, not as noise.
- After dependency change: `go test ./...` is not optional.

## Practical scenario

A new colleague clones the service. `go test` fails because locally they lack `mockgen` that README says “install globally”. After introducing tool dependency in the module (`tools.go`) and CI step `go install` from version in `go.mod`, everyone generates the same mock. Code review no longer accepts PRs with “I have a different generator version”.

Second example: someone removed package `legacy/xml` but left `require`. `go mod tidy` in pre-commit hook removes dependency and reduces attack surface. Diff in PR clearly shows the library is gone.

Third: upgrade `uuid` in the same PR as a large feature. Review cannot tell whether test failure comes from feature or version. Process fix: dependency upgrade in a separate PR.

## Check questions

1. What exactly does `go mod init` create?
2. What is the difference between `go get` and `go mod tidy`?
3. What does `// indirect` mean?
4. Why should a tool dependency not be treated as an ordinary runtime import?
5. Why is `retract` not part of beginner maintenance of a consumer module?
6. What should be committed after successfully adding a library?
7. How does `go get ...@none` help when removing a dependency?
8. Why does `tools.go` use `//go:build tools`?
9. What does `go list -m all` show after tidy?
10. Why should library upgrade go in a separate PR?

### Answers

1. Creates `go.mod` with `module` (path you gave) and `go` directive. Does not necessarily create `go.sum` or source code.
2. `go get` explicitly adds/moves/removes requirement for a module. `go mod tidy` aligns whole inventory with actual imports in code and tests (adds missing, removes unneeded, aligns `go.sum`).
3. Marker that the module is not a direct import of your code, but is needed by the graph (transitively or via tool pattern).
4. Because the tool serves development/CI, not end-user program runtime; mixing confuses inventory and review.
5. Because `retract` is written by the **author** of the library to mark a bad version; consumer daily work is `get`/`tidy`, not `retract`.
6. `go.mod` and `go.sum` together (after tests).
7. Removes requirement for that module from `go.mod`; used with import removal, often followed by `tidy`.
8. So the file is not compiled in ordinary application build, yet still participates in module graph via blank import.
9. List of selected module versions in the graph (direct and indirect) — actual MVS result.
10. So review and rollback are clear: feature and dependency change are not mixed in the same diff.

## Extension: reading diff as review checklist

When you open a PR that touches module files, ask:

1. **Why** did the version move — feature, CVE, or accidental `@latest`?
2. Is `go.sum` fully updated (no “half file”)?
3. Do CI tests cover the package that uses the new library?
4. Did a tool dependency accidentally enter runtime import?
5. Is there a `replace` that does not belong in this PR?

If you cannot answer (1), ask the author for one sentence in the PR description.

### Mini lab: two packages, one module

```text
example.com/vezba/odrzi/
  go.mod
  cmd/app/main.go
  internal/poruka/poruka.go
```

`internal/poruka/poruka.go`:

```go
package poruka

func Hello(name string) string {
	return "hello, " + name
}
```

`cmd/app/main.go`:

```go
package main

import (
	"fmt"

	"example.com/vezba/odrzi/internal/poruka"
)

func main() {
	fmt.Println(poruka.Hello("Marko"))
}
```

```bash
go mod init example.com/vezba/odrzi
go run ./cmd/app
```

#### What happens here

Both packages live in the **same** module. Import uses module path + package path. There is no second `go.mod` in `internal/`. That is a common application layout.

Execution trace:

```text
go run ./cmd/app
    → load go.mod (one module)
    → compile package main + package poruka
    → import mapped to internal/poruka
    → print
```

### Mini lab: what `tidy` will not do for you

`tidy` **does not**:

- pick the “nicest” major version;
- migrate your code from v1 to v2 imports;
- write `retract` instead of the library author;
- fix breaking API — only import inventory.

So major upgrade (lesson 05.03) requires code changes, not just `tidy`.

### Command table — what to touch by hand

| Action | Use tool | Do not do by hand |
|--------|--------------|---------------|
| New module path | `go mod init` | copy-paste someone else’s `go.mod` |
| New lib version | `go get @vX.Y.Z` | random number in editor |
| Cleanup | `go mod tidy` | delete half of `go.sum` |
| Check selection | `go list -m all` | guess from README |
| Tool pin | `tools.go` + tidy | global install only |

### Another scenario: onboarding checklist

When a new team member arrives, give them this order:

```text
1. git clone ...
2. cd project
3. go version          # confirm 1.22+
4. go env GOMOD
5. go mod download     # optional: warm cache
6. go test ./...
7. (if generator needed) go install from version in go.mod
```

If step 6 fails because of a tool, the problem is tool dependencies — not “bad Go”. Return to `tools.go` pattern.

## Summary

`go mod init` gives identity (module path). `go get` explicitly moves requirements. `go mod tidy` aligns inventory with actual imports. The `require` block is a readable record of that contract; `// indirect` is not an error. On Go 1.22 tie tool dependencies via `tools.go` + build tag pattern (newer `tool` flow is optional alternative on newer versions). Leave `retract` to library authors.
