# 06.06 Implementing Reflection

> **Go Path - Zero to Gopher** / **01 Basics → The Go Standard Library** / Lesson 06.06

## Lesson goals

After this lesson you should be able to:

- explain why `reflect` is **not** the normal way to write Go code: it is slower and loses static types;
- list when reflection is justified (serde, tools, rare framework layers);
- list the three laws of reflection and connect them to `Type` / `Value`;
- walk a concrete `Type`/`Value` path through a struct (fields, kind, tags);
- connect `fmt` and `encoding/json` as centralized users of reflection;
- choose interface, generics, or `go generate` instead of ad-hoc reflect in business logic.

## Prerequisite

- Structs, interfaces, `any`.
- Go 1.22+.
- Lessons 06.02 (`fmt`) preferred; 07.01 will deepen interfaces.

## Problem this lesson solves

Beginners discover `reflect` and start writing “generic” helpers for everything. Consequences:

- panics at runtime instead of compiler errors;
- slower hot path (millions of calls);
- unreadable errors;
- breaks on field refactor because the compiler does not see the field name in a string.

This lesson positions reflection as a **special tool at the system edge**, not as the default style of a Go program.

## Mental model

Go is statically typed: the compiler knows types and rejects wrong calls. Reflection moves part of those decisions to **runtime**: you ask “what type is this value?” and “what fields does it have?” while the program is already running.

Three laws (Rob Pike / `reflect` documentation):

1. **Reflection goes from interface value to reflection object**  
   value in `any` / interface → `reflect.ValueOf` / `TypeOf`
2. **Reflection goes from reflection object to interface value**  
   `Value.Interface()` back to `any`
3. **To modify a reflection object, the value must be settable**  
   you must have a settable target (`Elem` on a pointer, exported field, etc.)

```text
concrete value → (any) → reflect.Value / Type → (Interface) → any
```

### Why it is slow

Each step does more than direct field access:

- boxing into an interface;
- looking up kind, field count, names;
- indirections and settability checks;
- no inlining that the compiler does for ordinary `x.Field`.

In a microbenchmark, reading a field via reflection is often **several times slower** than direct access. On a hot path (per byte, per request in a tight loop) that is felt.

### Why it loses static types

The compiler does not check `FieldByName("Name")` — a typo `"name"` you discover in production or a test. `v.Int()` on a string is not a compile error: it is a **panic** at runtime. The type system did not save you; you turned it off.

Therefore: reflection is not “smarter Go”. It is an **exit into dynamic mode** at a cost.

## Mechanism

### Type and Value — first walk step

```go
t := reflect.TypeOf(x)
v := reflect.ValueOf(x)
fmt.Println(t.Kind(), v.Kind())
```

- `Type` describes **what** the type is (name, kind, fields, methods).
- `Value` holds the **data** (for reading/writing under rules).
- `Kind` is the category: `Struct`, `Slice`, `Int`, `Pointer`, `String`, …

`TypeOf(nil)` is a special case (nil without a type) — avoid confusing demos without a typed nil.

### Concrete Type/Value walk through a struct

Goal: take a value, peel a pointer if needed, walk exported fields, read the `json` tag and the value.

```go
func dump(x any) {
	v := reflect.ValueOf(x)
	t := v.Type()

	if v.Kind() == reflect.Pointer {
		if v.IsNil() {
			fmt.Println("nil pointer")
			return
		}
		v = v.Elem()
		t = v.Type()
	}

	if v.Kind() != reflect.Struct {
		fmt.Println("not a struct:", t)
		return
	}

	for i := 0; i < t.NumField(); i++ {
		sf := t.Field(i)      // StructField: name, type, tag
		fv := v.Field(i)      // field Value
		tag := sf.Tag.Get("json")
		fmt.Printf("%s json=%q value=%v typ=%s\n",
			sf.Name, tag, fv.Interface(), sf.Type)
	}
}
```

Line by line:

1. `ValueOf(x)` — input as an interface box → reflection object (law 1).
2. If kind is `Pointer`, `Elem()` drops to the pointed-to value. Treat a nil pointer separately — otherwise panic.
3. Check `Struct` — otherwise `NumField` makes no sense and panics.
4. `t.Field(i)` gives metadata; `v.Field(i)` gives the value.
5. `Tag.Get("json")` reads the struct tag — the same mechanism `encoding/json` uses.
6. `fv.Interface()` returns the field back to `any` (law 2) for printing.

This is a **school walk**. In production for JSON use `json.Marshal`, not your dump, except in tools.

### Settability (law 3)

```go
p := reflect.ValueOf(&x).Elem()
if p.CanSet() {
	p.SetInt(10)
}
```

`ValueOf(x)` for a non-pointer copy is often **not** settable: you would be changing a temporary copy. That is why mutation goes through an address (`&x`) then `Elem`.

From another package unexported fields are not settable / visible in the expected way — reflection respects export.

### When it is justified

| Situation | Reflect? |
|-----------|----------|
| `encoding/json`, `fmt`, ORMs, DI containers | yes — centralized, cached |
| debug dump / generic tool | often yes |
| business logic “for every struct” | no |
| hot path millions of times/s | no |
| 2–3 known types | type switch / interface |
| a family of types with the same behavior | interface or generics |

`fmt` and `json` use reflect so you do not write an encoder for every struct by hand. That justifies a **library**, not every service rewriting the same layer.

## Rules and syntax

- Check `Kind` before `Int`/`Len`/`Field`.
- Cache `reflect.Type` if you must in a loop.
- Prefer `json.Marshal` over hand-rolled reflect for JSON.
- For type-safe “generic” functions (Go 1.18+) **generics** are often better than reflect.
- Document panic assumptions or replace them with `error` returns.

## Examples

### Example 1 — TypeOf / ValueOf over a slice

```go
package main

import (
	"fmt"
	"reflect"
)

func main() {
	var x any = []int{1, 2, 3}
	t := reflect.TypeOf(x)
	v := reflect.ValueOf(x)
	fmt.Println("type:", t, "kind:", t.Kind())
	fmt.Println("len:", v.Len(), "index0:", v.Index(0).Int())
}
```

#### What happens here

1. `x` is an interface box whose dynamic type is `[]int`.
2. `TypeOf` / `ValueOf` reveal kind `Slice`.
3. `Len()` and `Index(0).Int()` read data dynamically.
4. The compiler no longer protects “is this really a slice of ints” at the call site — you are responsible. Wrong kind → panic.

### Example 2 — settable field

```go
package main

import (
	"fmt"
	"reflect"
)

type Tacka struct {
	X int
	Y int
}

func main() {
	t := Tacka{1, 2}
	rv := reflect.ValueOf(&t).Elem()
	fx := rv.FieldByName("X")
	if fx.CanSet() {
		fx.SetInt(99)
	}
	fmt.Printf("%+v\n", t)
}
```

#### What happens here

1. `&t` enters `ValueOf`; `Elem` gives a settable struct value.
2. `FieldByName("X")` finds the field; `CanSet` is true for an exported field of an addressable struct.
3. `SetInt(99)` changes `t.X` in place.
4. Direct `ValueOf(t)` (without a pointer) would not allow a reliable `Set` — violation of law 3.

### Example 3 — why json uses reflect (justified use-case)

```go
package main

import (
	"encoding/json"
	"fmt"
)

type Artikal struct {
	SKU  string  `json:"sku"`
	Cena float64 `json:"cena"`
}

func main() {
	b, err := json.Marshal(Artikal{SKU: "A-1", Cena: 12.5})
	if err != nil {
		panic(err)
	}
	fmt.Println(string(b))
}
```

#### What happens here

1. You do not write a manual encoder for `Artikal`.
2. `encoding/json` uses reflection to read fields and tags (the same walk as our `dump`, but production-maintained).
3. That is a **justified**, centralized use-case: once in stdlib, used everywhere.

Your service should call `Marshal`, not rewrite a reflect layer “for flexibility”.

### Example 4 — downside: panic on wrong kind

```go
package main

import (
	"fmt"
	"reflect"
)

func asInt(x any) int {
	v := reflect.ValueOf(x)
	return int(v.Int()) // panic if not int-like
}

func main() {
	defer func() {
		if r := recover(); r != nil {
			fmt.Println("caught:", r)
		}
	}()
	fmt.Println(asInt("no"))
}
```

#### What happens here

1. `"no"` enters as `any`.
2. `v.Int()` requires an int kind — string is not → **panic**.
3. `recover` in `defer` catches the panic for the demo; in a library you should check `Kind` and return `error`.
4. The static type system did not participate here. Cost of reflection: errors later and louder.

### Example 5 — alternative without reflect

```go
package main

import "fmt"

type Stringer interface {
	String() string
}

func printAll(items []Stringer) {
	for _, it := range items {
		fmt.Println(it.String())
	}
}

type Novcic int

func (n Novcic) String() string { return fmt.Sprintf("%d RSD", int(n)) }

func main() {
	printAll([]Stringer{Novcic(50)})
}
```

#### What happens here

1. The interface requires behavior; the compiler checks that `Novcic` has `String`.
2. No `Kind` check, no panic because of a wrong field.
3. New types are added by implementing methods — not by extending a reflect switch.

When you feel the need for reflect to “walk any struct”, first ask: does a small interface (07.01) solve the problem?

### Example 6 — caching type and generics instead of reflect

```go
package main

import (
	"fmt"
	"reflect"
)

type Artikal struct {
	SKU string
}

var tipArtikla = reflect.TypeOf(Artikal{})

func fields() int { return tipArtikla.NumField() }

func First[T any](s []T) (T, bool) {
	var zero T
	if len(s) == 0 {
		return zero, false
	}
	return s[0], true
}

func main() {
	fmt.Println("fields:", fields())
	v, ok := First([]int{7, 8})
	fmt.Println(v, ok)
}
```

#### What happens here

1. `tipArtikla` is computed once — no `TypeOf` in a tight loop.
2. `First` is a generic: the compiler keeps type `T`. No `any` casts.
3. For “first slice element” reflect would be pure loss.

## Decision analysis

| Situation | Decision |
|-----------|--------|
| JSON/XML/config mapping | stdlib / generated code |
| debug dump | reflect OK in tools |
| hot path | avoid reflect |
| library for any struct | reflect or go generate |
| 2–3 known types | type switch / interface |
| algorithm family over types | generics |

## Trade-offs

| Approach | Plus | Minus |
|---------|------|-------|
| reflect | flexible for unknown types | slow, panics, loss of static types |
| generics | more type-safe | not for unknown struct tags at runtime |
| go generate | fast at runtime | build step |
| interfaces | idiomatic Go | need an API agreement |

## Common mistakes

1. **Wrong:** `Set` on a non-settable `Value`.  
   **Effect:** panic.  
   **Why:** law 3 — no addressable target.  
   **Fix:** work through a pointer + `Elem`; check `CanSet`.

2. **Wrong:** reflect in a tight loop without caching `Type`.  
   **Effect:** unnecessary CPU cost.  
   **Why:** metadata lookup repeats.  
   **Fix:** cache `Type`; or remove reflect.

3. **Wrong:** `v.Int()` without checking `Kind`.  
   **Effect:** panic on the wrong type.  
   **Why:** no compiler check.  
   **Fix:** `if v.Kind() != reflect.Int { return err }`.

4. **Wrong:** rewriting a JSON marshaller “for learning” in production.  
   **Effect:** bugs, slower code, maintenance.  
   **Why:** stdlib already solves the problem.  
   **Fix:** `encoding/json`; learn reflect on a demo, not in a service.

5. **Wrong:** a “generic validator” via reflection over string tags without cache/tests.  
   **Effect:** slow checks, panics on typo.  
   **Why:** errors moved to runtime.  
   **Fix:** explicit `Validate() error` methods or code generation.

6. **Wrong:** walking unexported fields from another package as if they were public.  
   **Effect:** `CanInterface`/`CanSet` false; unexpected behavior.  
   **Why:** export applies to reflect too.  
   **Fix:** exported fields or code in the same package.

## Idiomatic Go

- Reflection at the system edge (serde, tools).
- Business logic without reflect.
- Cache `reflect.Type` if you must.
- Prefer `encoding/json`, `fmt`, generics, interfaces.
- One sentence to remember: **reflection moves errors from the compiler to runtime — you pay with check and test discipline.**

## Practical scenario

A team wrote a “generic validator” via reflection over tags. It was slow and panic-prone on a typo in a tag. Switch: `go generate` + explicit `Validate() error` methods on types. Reflect remained only in a thin layer that reads tags at `init` and caches rules. `fmt` and `json` still use reflect — but the Go team maintains that, not every service again.

## Check questions

1. List the three laws of reflection.  
   **Answer:** interface→reflect; reflect→interface; modify only if settable.

2. When is a `Value` settable?  
   **Answer:** when it represents an addressable / exported target (e.g. `Elem` on a pointer).

3. Why is reflect slower?  
   **Answer:** dynamic lookup, boxing, fewer compiler optimizations than direct code.

4. How does `encoding/json` use reflect?  
   **Answer:** it reads struct fields and tags at runtime to serialize/deserialize.

5. When do you choose an interface instead of reflect?  
   **Answer:** when you can describe behavior with methods; the compiler then checks.

6. What is `Kind`?  
   **Answer:** the type category (`Struct`, `Int`, `Slice`…).

7. Why is a panic from `v.Int()` on a string not a compiler error?  
   **Answer:** the type is lost in `any`; the check is at runtime.

## Deeper pass: why reflect is not the default style

Write two versions of the same field read:

```go
// A: static
cena := a.Cena

// B: reflect
v := reflect.ValueOf(a).FieldByName("Cena").Float()
```

Version A:

- the compiler checks that `Cena` exists;
- inlining and optimizations possible;
- rename in the IDE works;
- the error shows at `go build`.

Version B:

- typo `"cena"` you discover later;
- slower;
- IDE helps less;
- panic possible.

That is why B is reserved for tools that **must** work with unknown types at runtime (JSON, ORM, copy framework). Your service that knows about `Artikal` needs A.

### Walk — extended trace with nil and pointer

Input: `dump(&Artikal{SKU:"A", Cena:1.5})`

1. `ValueOf` sees Pointer.
2. `IsNil`? no.
3. `Elem` → struct value.
4. `NumField` → 2.
5. Field 0: `SKU`, tag `json:"sku"`, value `"A"`.
6. Field 1: `Cena`, tag `json:"cena"`, value `1.5`.

Input: `dump((*Artikal)(nil))` → “nil pointer” branch, without panic — that is why we check.

### Mini API map

| API | Role |
|-----|-------|
| `TypeOf` | type description |
| `ValueOf` | value |
| `Kind` | category |
| `NumField` / `Field` | struct |
| `CanSet` / `Set*` | mutation |
| `Interface` | back to `any` |
| `Tag.Get` | struct tag |

### Generics vs reflect — once more

```go
func First[T any](s []T) (T, bool) {
	var zero T
	if len(s) == 0 {
		return zero, false
	}
	return s[0], true
}
```

The compiler keeps `T`. Reflect would work with `any` and casts. For this problem the generic wins.

### Checklist before reflect

1. Does an interface solve the problem?
2. Does a generic solve the problem?
3. Does `encoding/json` already do the job?
4. If you really need reflect — cache Type, check Kind, return error instead of panic.
5. Is this the system edge or a hot path?

If 1–3 say “yes”, do not use reflect.

## Workshop

Goal: three laws of reflection, a safe struct walk, settable rules, and a deliberate “no reflect” decision. Reflection here means the `reflect` package — runtime insight into types.

### Exercise R1 — TypeOf / ValueOf / Kind

```go
package main

import (
	"fmt"
	"reflect"
)

type Artikal struct {
	SKU  string  `json:"sku"`
	Cena float64 `json:"cena"`
}

func main() {
	a := Artikal{SKU: "A1", Cena: 9.5}
	t := reflect.TypeOf(a)
	v := reflect.ValueOf(a)
	fmt.Println(t, t.Kind(), v.Kind())
	fmt.Println(t.NumField(), t.Field(0).Name, t.Field(0).Tag.Get("json"))
}
```

#### What happens here

1. `TypeOf` gives the type description; `ValueOf` gives the value in a reflect wrapper.
2. `Kind` is the category (`Struct`, `Int`, `Slice`…) — you branch on kind, not on the type name.
3. `NumField` / `Field` work only when kind is `Struct` — otherwise panic.
4. You read a struct tag via `Tag.Get("json")` — the same mechanism `encoding/json` uses.

### Exercise R2 — walk with pointer and nil

```go
func dump(x any) {
	v := reflect.ValueOf(x)
	if v.Kind() == reflect.Pointer {
		if v.IsNil() {
			fmt.Println("nil pointer")
			return
		}
		v = v.Elem()
	}
	if v.Kind() != reflect.Struct {
		fmt.Println("not a struct", v.Kind())
		return
	}
	t := v.Type()
	for i := 0; i < v.NumField(); i++ {
		f := t.Field(i)
		fmt.Printf("%s json=%q val=%v\n", f.Name, f.Tag.Get("json"), v.Field(i).Interface())
	}
}
```

Call: `dump(Artikal{...})`, `dump(&Artikal{...})`, `dump((*Artikal)(nil))`.

#### What happens here

1. Pointer kind → `Elem` to reach the struct value.
2. `IsNil` before `Elem` prevents panic on a nil pointer.
3. `Interface()` returns the field back to `any` (interface box).
4. Unexported fields exist in Type, but `Interface()` on them can fail — stick to exported fields.

### Exercise R3 — CanSet and mutation

```go
func setSKU(ptr any, sku string) error {
	v := reflect.ValueOf(ptr)
	if v.Kind() != reflect.Pointer || v.IsNil() {
		return fmt.Errorf("need non-nil pointer")
	}
	v = v.Elem()
	f := v.FieldByName("SKU")
	if !f.IsValid() {
		return fmt.Errorf("no SKU")
	}
	if !f.CanSet() {
		return fmt.Errorf("SKU is not settable")
	}
	if f.Kind() != reflect.String {
		return fmt.Errorf("SKU is not string")
	}
	f.SetString(sku)
	return nil
}
```

#### What happens here

1. Third law: modify only if the value is settable.
2. `ValueOf(struct)` by value → fields are not settable; you need a pointer.
3. `CanSet` before `Set*` — better `error` than panic.
4. `FieldByName` with a typo returns an invalid Value — check `IsValid`.

### Decision table — reflect or not?

| Question | If yes | Action |
|---------|--------|--------|
| Can an interface? | yes | methods, not reflect |
| Can a generic? | yes | type parameter |
| Does `encoding/json` work? | yes | use stdlib |
| Tool / serde edge? | yes | reflect + cache Type |
| Business-logic hot path? | yes | **do not** reflect |

### Exercise R4 — panic vs error

```go
// BAD
func mustInt(x any) int {
	return reflect.ValueOf(x).Int() // panic if not int-like
}

// BETTER
func asInt(x any) (int64, error) {
	v := reflect.ValueOf(x)
	switch v.Kind() {
	case reflect.Int, reflect.Int64, reflect.Int32:
		return v.Int(), nil
	default:
		return 0, fmt.Errorf("kind %s", v.Kind())
	}
}
```

#### What happens here

1. The Reflect API often panics on a wrong kind — that is not a compiler error.
2. A wrapper that returns `error` makes the system edge predictable.
3. In libraries prefer error; leave `Must*` for tests/init where fail-fast is OK.

### Exercise R5 — caching Type

```go
var artikalType = reflect.TypeOf(Artikal{})

func jsonTags() []string {
	var out []string
	for i := 0; i < artikalType.NumField(); i++ {
		out = append(out, artikalType.Field(i).Tag.Get("json"))
	}
	return out
}
```

#### What happens here

1. `TypeOf` in a loop thousands of times is more expensive than a package cache.
2. Tag walk at `init` + rule cache = the pattern serious validators use.
3. Business logic still calls `Validate() error` — reflect stays a thin layer.

### Workshop FAQ

**Q: Why is reflect slower?**  
A: Dynamic lookup, boxing into `any`, less inlining. A direct field the compiler optimizes better.

**Q: Do generics kill the need for reflect?**  
A: For many helpers yes. Reflect remains when the type is not known at compile-time (JSON, ORM).

**Q: What is a method set in the reflect world?**  
A: It still applies: which methods a type has determines interface satisfaction; reflect only reads existing reality.

**Q: Can reflect call an unexported method from another package?**  
A: Not in a safe/idiomatic way — respect exported/unexported boundaries.

**Q: Why does `v.Int()` on a string panic only at runtime?**  
A: The type is lost in `any`; the check is dynamic.

**Q: Where is reflect OK in stdlib?**  
A: `fmt`, `encoding/json`, `database/sql` scan — centralized, tested, cached.

**Q: How do I debug Kind?**  
A: Log `v.Kind().String()` and `%T` before an assert / Set call.

### Edge cases

1. Interface inside interface — you may need an Elem loop.
2. Slice/map kind — `Len`, `Index`, `MapKeys` instead of Field.
3. Unaddressable value from a map — CanSet false.
4. Struct with an embedding field — Field can be Anonymous.

## Summary

Reflection turns interface values into `Type`/`Value`, returns them back, and modifies only settable targets. It is slower and loses static types — that is why it is **not** the normal style of writing Go. It is justified in serde and tools; dangerous in business logic. `fmt` and `json` are examples of good, centralized users. Next module: structs and interfaces as the real idiomatic tool.
