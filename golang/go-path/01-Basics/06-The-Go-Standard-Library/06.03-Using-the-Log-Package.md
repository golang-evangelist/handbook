# 06.03 Using the Log Package

> **Go Path - Zero to Gopher** / **01 Basics → The Go Standard Library** / Lesson 06.03

## Lesson goals

After this lesson you should be able to:

- use the standard `log` package with flags, a prefix, and output to stderr;
- explain the limits of the classic logger (no levels, weak structure);
- write structured logs with `log/slog` (Go 1.21+, here we target 1.22+);
- choose levels (`Debug`, `Info`, `Warn`, `Error`) and understand filtering on the handler;
- choose Text vs JSON handler and use `With` for shared fields;
- avoid `log.Fatal` in libraries and leaking secrets into the log.

## Prerequisite

- 06.01–06.02 (`fmt`, stderr/stdout, basic format).
- Go 1.22+ (`slog` exists since 1.21).
- Basic feel for JSON lines in log aggregators (Loki, Cloud Logging, ELK).

## Problem this lesson solves

`fmt.Println` in a service quickly becomes chaos:

- no levels (you cannot silence Debug in production);
- no consistent fields — searching “all requests user_id=X” does not work;
- hard to filter in an aggregator;
- timestamp format varies by developer;
- `log.Fatal` in a helper kills the process and kills tests.

Classic `log` helps partially (prefix, flags, one Writer). `log/slog` brings structure, levels, and handlers **without** an external dependency.

## Mental model

```text
event → logger → handler → Writer (stderr/file)
              ↓
        attributes (key=value) + level + time
```

With package `log`: one global logger, textual lines, flags for date/file/prefix. No first-class levels.

With `slog`: a **record** with a level + message + attributes; a **handler** decides the format (text or JSON) and whether the record passes the level threshold.

Key difference for operations: a structured log is **data**. A textual `Printf` is a story for a human. Aggregators love data.

## Mechanism

### Standard `log`

```go
log.SetOutput(os.Stderr)
log.SetFlags(log.LstdFlags | log.Lshortfile)
log.SetPrefix("inventory: ")
log.Println("server start")
```

What each call does:

1. `SetOutput` — all `Print*` go to that `Writer` (here stderr, so CLI stdout stays clean).
2. `SetFlags` — what is glued in front of the message (date, time, file…).
3. `SetPrefix` — a static string before the message (service name).
4. `Println` — formats the line and writes.

Common functions: `Print`, `Printf`, `Println`, `Fatal`, `Fatalf`, `Panic`, `Panicf`.

`Fatal` = log + `os.Exit(1)`. `Panic` = log + `panic`. Both are dangerous in libraries: the test and the caller lose control.

### Classic log flags

| Flag | Effect |
|------|--------|
| `Ldate` | date |
| `Ltime` | time |
| `Lmicroseconds` | microseconds with the time |
| `Llongfile` / `Lshortfile` | path:line or file:line |
| `Lmsgprefix` | affects message prefix order |
| `LUTC` | time in UTC |
| `LstdFlags` | `Ldate \| Ltime` (default) |

You combine with bits: `log.LstdFlags | log.Lshortfile`.

### `log/slog` — record and handler

```go
slog.Info("query ok", "duration_ms", 12, "route", "/health")
```

The call builds a record: level Info, message `"query ok"`, attributes `duration_ms=12`, `route=/health`. The default logger sends to the handler; the handler filters by level and serializes.

Levels (rising severity): `Debug`, `Info`, `Warn`, `Error`. Numeric threshold on the handler: everything below the threshold is discarded cheaply.

Handlers in stdlib:

- `slog.NewTextHandler` — key=value text, pleasant for local development;
- `slog.NewJSONHandler` — one JSON object per line, pleasant for production aggregators.

```go
logger := slog.New(slog.NewJSONHandler(os.Stderr, &slog.HandlerOptions{
	Level: slog.LevelInfo,
}))
slog.SetDefault(logger)
```

`SetDefault` changes the global `slog.Info` etc. In larger applications you often pass `*slog.Logger` explicitly instead of a global.

### Attributes

Two styles:

```go
slog.Info("ok", "user", id, "attempt", n)
slog.Info("ok", slog.String("user", id), slog.Int("attempt", n))
```

The first is shorter (variadic pairs). The second is stricter on types. Both end up as attributes on the record.

`logger.With("request_id", rid)` returns a **child** logger: every following record inherits those fields. Less repetition, more consistent correlation.

`InfoContext(ctx, ...)` leaves room for the handler to read values from `context` (e.g. trace id) — useful when you connect observability.

### What not to log

Secrets, tokens, passwords, full personal data without a policy. An attribute struct must not encourage `slog.Info("auth", "header", req.Header.Get("Authorization"))`. A log is often more durable and more widely read than a database.

## Rules and syntax

### Levels in production

| Level | When |
|------|------|
| `Debug` | local development / temporary diagnostics |
| `Info` | life events (start, request finished) |
| `Warn` | unexpected but tolerable (retry succeeded) |
| `Error` | operation failed (DB ping failed) |

### Key discipline

Agree on a vocabulary: `request_id`, `user_id`, `duration_ms`. Do not mix `requestId` and `req_id` in the same service — filters in Loki become hell.

### Libraries

A library does not call `log.Fatal`. It takes `*slog.Logger` or returns `error`. Killing the process is a `main` decision.

## Examples

### Example 1 — classic `log` with a prefix

```go
package main

import (
	"log"
	"os"
)

func main() {
	log.SetOutput(os.Stderr)
	log.SetPrefix("billing: ")
	log.SetFlags(log.LstdFlags | log.Lshortfile)
	log.Println("service started")
	log.Printf("port=%d", 8080)
}
```

#### What happens here

1. Output goes to stderr — if this binary ever enters a pipe with data on stdout, the log does not mix streams.
2. Prefix `billing: ` sits on every line — in a multi-service log you immediately see the source.
3. `Lshortfile` adds `file:line` — faster jump into code during an incident.
4. `Println` / `Printf` write textual lines. No levels: everything is “equally important”.

### Example 2 — slog text handler

```go
package main

import (
	"log/slog"
	"os"
)

func main() {
	h := slog.NewTextHandler(os.Stderr, &slog.HandlerOptions{Level: slog.LevelDebug})
	log := slog.New(h)
	log.Debug("loading cache")
	log.Info("ready", "worker", 4)
	log.Warn("slow database", "ms", 850)
}
```

#### What happens here

1. The handler threshold is `Debug` — all levels from Debug upward pass.
2. The `Debug` line is visible. If the threshold were `Info`, this line would disappear.
3. `Info` and `Warn` carry attributes as pairs; the text handler prints them readably for a human.
4. The local variable `log` shadows the package name — OK in a short `main`; in a larger file better `logger`.

### Example 3 — JSON handler for production

```go
package main

import (
	"context"
	"log/slog"
	"os"
)

func main() {
	h := slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{Level: slog.LevelInfo})
	logger := slog.New(h)

	ctx := context.Background()
	logger.InfoContext(ctx, "http_request",
		"method", "GET",
		"path", "/api/prices",
		"status", 200,
		"duration_ms", 18,
	)
	logger.Error("db_ping_failed", "err", "connection refused")
}
```

#### What happens here

1. The JSON handler writes one object per event. An aggregator parses fields without regex hell.
2. Threshold `Info` — `Debug` would be discarded.
3. `InfoContext` sends `context`; here it is empty, but the API is ready for a trace.
4. `Error` marks a failed operation. Attribute `err` is a string in this demo; in real code you often pass an `error` value.

Note: in a CLI a JSON log often goes to stderr; here stdout illustrates a “stream to the aggregator”. Do not mix a JSON log and a JSON API response on the same stream without need.

### Example 4 — child logger with `With`

```go
package main

import (
	"log/slog"
	"os"
)

func main() {
	base := slog.New(slog.NewJSONHandler(os.Stderr, nil))
	reqLog := base.With("request_id", "req-123", "service", "prices")
	reqLog.Info("start")
	reqLog.Info("done", "items", 3)
}
```

#### What happens here

1. `base` is the root logger.
2. `With` sticks `request_id` and `service` onto **all** following child records.
3. `start` and `done` both carry the same correlation fields; `done` adds `items` as well.
4. In HTTP middleware you create `reqLog` once per request and pass it down — the whole handling shares the ID.

### Example 5 — level from an env variable

```go
package main

import (
	"log/slog"
	"os"
	"strings"
)

func parseLevel(s string) slog.Level {
	switch strings.ToLower(s) {
	case "debug":
		return slog.LevelDebug
	case "warn":
		return slog.LevelWarn
	case "error":
		return slog.LevelError
	default:
		return slog.LevelInfo
	}
}

func main() {
	lvl := parseLevel(os.Getenv("LOG_LEVEL"))
	h := slog.NewJSONHandler(os.Stderr, &slog.HandlerOptions{Level: lvl})
	slog.SetDefault(slog.New(h))
	slog.Debug("visible only if debug")
	slog.Info("always info+")
}
```

#### What happens here

1. Ops changes `LOG_LEVEL` without a rebuild (with a process restart).
2. Unknown / empty value → Info (safe default).
3. With `LOG_LEVEL=debug`, the Debug line passes; otherwise it is not in the output.
4. `SetDefault` makes `slog.Info` in other packages use the same handler — convenient at the `main` edge.

## Decision analysis

| Context | Choice | Why |
|----------|-------|-------|
| Small CLI debug | `log` or `slog` text | simple for a human |
| HTTP service | `slog` JSON | filters, metrics with the log |
| Library | takes `*slog.Logger`; no `Fatal` | caller controls life |
| Temporary printf debug | OK locally | remove before merge |
| Request correlation | `With("request_id", …)` | less repetition |

## Trade-offs

| Tool | Plus | Minus |
|------|------|-------|
| `fmt` | simplest | no levels/structs |
| `log` | in stdlib for ages | weak structure |
| `slog` | standard, levels, JSON | needs attribute discipline |
| external loggers | rich features | dependency, learning the API |

## Common mistakes

1. **Wrong:** `log.Fatal` / `slog` + `os.Exit` in a library package.  
   **Effect:** tests and embedded calls kill the whole process.  
   **Why:** a library does not own the application lifecycle.  
   **Fix:** return `error`; `Fatal` only in `main` if at all.

2. **Wrong:** mixing stdout data and logs on the same stream in a CLI.  
   **Effect:** pipes and scripts break on log lines.  
   **Why:** stdout is the result contract.  
   **Fix:** log on stderr; data on stdout.

3. **Wrong:** unstable keys (`UserName` vs `user_name`).  
   **Effect:** dashboards and queries miss half the events.  
   **Why:** aggregators match exact field names.  
   **Fix:** an agreed attribute vocabulary in the team.

4. **Wrong:** logging the whole request body / Authorization.  
   **Effect:** leaking secrets into durable logs.  
   **Why:** a log often goes to systems with wider access.  
   **Fix:** redact; log IDs and status, not secrets.

5. **Wrong:** Debug level left in production without need.  
   **Effect:** noise, storage cost, slower hot path.  
   **Why:** every record costs CPU and I/O.  
   **Fix:** Info+ in production; Debug temporarily when needed.

6. **Wrong:** error logged in every layer then again at the boundary.  
   **Effect:** three identical Error lines for one incident.  
   **Why:** no agreement on who “owns” the log.  
   **Fix:** log once at the boundary (handler); inside return `error`.

## Idiomatic Go

- One default logger at the application edge (`main`).
- Pass the logger or use `With` for request scope.
- Consistent snake_case / agreed keys.
- Prefer `slog` for new code on Go 1.22+.
- `AddSource: true` in `HandlerOptions` useful in development; in enormous traffic noisy.
- Classic `log` remains OK for small tools — do not force slog where there is no need.

## Practical scenario

A team had `log.Printf` with hand-assembled strings. Searching “which request_id” in Grafana Loki did not work because the ID was not a field. Moving to `slog` JSON + `With("request_id", …)` in middleware enabled a filter for one request across all services. On-call time dropped because Error carried `err` and `path` as fields, not as free text. Notably: one microservice logged a JWT — a security review forced redaction before production.

## Check questions

1. What do `SetFlags` and `SetPrefix` do?  
   **Answer:** they control what is glued to the message (time/file) and a static name prefix.

2. Why is `Fatal` not suitable in libraries?  
   **Answer:** it calls `os.Exit` and kills the process; the caller and tests lose control.

3. What is the role of a handler in `slog`?  
   **Answer:** it filters by level and serializes the record (text/JSON) to a Writer.

4. Difference Text vs JSON handler?  
   **Answer:** Text for a human locally; JSON for machine parsing in production.

5. What is `logger.With(...)` for?  
   **Answer:** a child logger with permanent attributes on all following records.

6. When do you choose `Error` and when `Warn`?  
   **Answer:** Error when the operation failed; Warn when it is unusual but the system continues (e.g. retry succeeded).

7. Why are consistent attribute keys important?  
   **Answer:** aggregators and dashboards filter by exact field names.

## Deeper pass: from event to JSON line

### Trace of one `slog.Info` call

```go
logger.Info("http_request", "method", "GET", "status", 200)
```

1. The logger builds a record: level Info, message `http_request`, attributes method/status.
2. The handler compares the level with the threshold (`LevelInfo`) — Info passes; Debug would stop here.
3. The JSON handler serializes an object (time, level, msg, fields) to the Writer.
4. The aggregator indexes fields — filter `status=500` becomes a query, not a grep on a string.

### Comparing the same event

Classic:

```go
log.Printf("request method=%s path=%s status=%d", m, p, s)
```

Structured:

```go
slog.Info("request", "method", m, "path", p, "status", s)
```

The first is faster to type in a script. The second survives production.

### `HandlerOptions` in practice

```go
opts := &slog.HandlerOptions{
	Level:     slog.LevelInfo,
	AddSource: true,
}
```

`AddSource` adds file:line — useful in development, noisy and expensive in enormous traffic. In production often off; turn on temporarily during an incident.

### Migrating from `log` to `slog` (steps)

1. Replace global `log.Printf` at the `main` edge with a JSON/text handler.
2. Pass `*slog.Logger` into services (or `With` per request).
3. Unify attribute keys (`request_id`, do not mix styles).
4. Enable JSON in staging before production.
5. Remove `Fatal` from libraries in the same pass.

### Why not to log in a loop at Debug in production

Every record = allocations + I/O. Debug on a hot path under load can itself become a bottleneck. Keep the threshold Info+; turn Debug on locally or on one instance.

### Logger checklist

1. stderr for log in a CLI; do not mix with stdout data.
2. One agreed key vocabulary.
3. No secrets in attributes.
4. Libraries without `Fatal`.
5. Error logged once at the boundary.
6. Child logger (`With`) for request scope.

## Workshop

Goal: from ad-hoc `log.Printf` to a structured `slog` record that can be filtered. Do the steps in order; each has an execution trace.

### Exercise R1 — classic log with flags

```go
package main

import (
	"log"
	"os"
)

func main() {
	log.SetOutput(os.Stderr)
	log.SetPrefix("app ")
	log.SetFlags(log.Ldate | log.Ltime | log.Lshortfile)

	log.Println("start")
	log.Printf("user=%s id=%d", "Ana", 7)
}
```

#### What happens here

1. `SetOutput(os.Stderr)` keeps the log apart from stdout data (piping stays clean).
2. `SetPrefix` sticks a static prefix on every line.
3. `SetFlags` chooses date, time, and short file name — diagnostics without slog.
4. `Println` / `Printf` use the same logger; the difference is only the format engine.
5. A global logger is convenient in `main`; in a library prefer a passed logger.

### Exercise R2 — why Fatal is not for libraries

```go
func ucitaj(path string) error {
	// BAD in a library:
	// log.Fatal("failure")
	return fmt.Errorf("ucitaj %s: %w", path, errNema)
}

func main() {
	if err := ucitaj("x.conf"); err != nil {
		log.Printf("error: %v", err)
		os.Exit(1) // exit only at the edge
	}
}
```

#### What happens here

1. `log.Fatal` calls `os.Exit` — tests, defer, and the caller lose control.
2. The library returns `error`; `main` decides the exit code.
3. Logging the error once at the boundary prevents double noise in the aggregator.

| Place | Allowed | Forbidden |
|-------|------------|------------|
| `main` / CLI edge | `Fatal` / `os.Exit` (consciously) | — |
| library package | `return error` | `log.Fatal` |
| HTTP handler | log + status code | `Fatal` |

### Exercise R3 — slog Text vs JSON

```go
package main

import (
	"log/slog"
	"os"
)

func main() {
	text := slog.New(slog.NewTextHandler(os.Stderr, &slog.HandlerOptions{
		Level: slog.LevelDebug,
	}))
	text.Debug("boot", "phase", "init")
	text.Info("ready", "port", 8080)

	jsonL := slog.New(slog.NewJSONHandler(os.Stderr, &slog.HandlerOptions{
		Level: slog.LevelInfo,
	}))
	jsonL.Debug("will_not_be_seen") // below threshold
	jsonL.Info("request", "method", "GET", "status", 200)
	jsonL.Error("db_fail", "err", "timeout", "retry", 1)
}
```

#### What happens here

1. The handler filters by level before serialization — Debug disappears when the threshold is Info.
2. The Text handler is readable to a human locally.
3. The JSON handler makes one object per line — aggregators index fields.
4. Attributes go as key/value pairs after the message.
5. The same event (`request`) becomes searchable by `status`, not grep on free text.

### Exercise R4 — child logger with `With`

```go
base := slog.New(slog.NewJSONHandler(os.Stderr, nil))
req := base.With("request_id", "r-42", "tenant", "acme")

req.Info("auth_ok", "user", "mila")
req.Info("auth_ok", "user", "petar") // same request_id and tenant
```

#### What happens here

1. `With` makes a child logger — permanent attributes stick to every following record.
2. Middleware / handler scope keeps `request_id` without repeating it in every call.
3. A filter in Loki/ELK by `request_id` shows the whole request trace.
4. Do not mix key styles (`requestId` vs `request_id`) — dashboards break.

### Decision table — levels

| Situation | Level | Example |
|-----------|------|--------|
| Successful request | Info | `status=200` |
| Retry succeeded | Warn | temporary timeout |
| Operation failed | Error | DB down |
| Development detail | Debug | SQL query text (no secrets) |

### Exercise R5 — redacting secrets

```go
token := "eyJhbGciOi..." // JWT — NOT in the log
slog.Info("login", "user", "ana", "token_len", len(token))
// never: slog.Info("login", "token", token)
```

#### What happens here

1. Log aggregators keep data a long time — a secret in the log is a leak.
2. Log metadata (`token_len`, `user`) instead of the raw secret.
3. A code review checklist must have the item “no secrets in attributes”.

### Mini project — mini HTTP middleware logger (sketch)

```go
func withRequestLogger(base *slog.Logger, requestID string) *slog.Logger {
	return base.With("request_id", requestID)
}

func handle(log *slog.Logger, path string, err error) {
	if err != nil {
		log.Error("handler_fail", "path", path, "err", err.Error())
		return
	}
	log.Info("handler_ok", "path", path)
}
```

#### What happens here

1. One base logger in `main`.
2. Per request a child with `request_id`.
3. The error is logged once with `path` and `err` as fields.
4. The handler does not call `Fatal` — returns status / error upward.

### Workshop checklist

- [ ] stderr for log; stdout for CLI data.
- [ ] Consistent attribute keys (vocabulary of 5+ names).
- [ ] Level threshold: Info+ in “production”, Debug locally.
- [ ] No `Fatal` in a library.
- [ ] No JWT/passwords in attributes.
- [ ] `With` for request/tenant scope.
- [ ] JSON handler tried at least once and “parsed” by eye.

### Workshop FAQ

**Q: Must I go to slog immediately?**  
A: For new code on Go 1.22+ — yes, prefer it. A small tool can stay on `log`.

**Q: Text or JSON in staging?**  
A: JSON in staging/production; Text locally. Staging should resemble production.

**Q: Where do I put `AddSource: true`?**  
A: In development and temporarily during an incident. In enormous traffic noisy and more expensive.

**Q: How do I test a logger?**  
A: Handler into a `bytes.Buffer`, then check that the buffer contains the expected key/message.

**Q: What about `log.Panic`?**  
A: Even more aggressive than Fatal (panic). In a library — no. At the edge — rarely and consciously.

**Q: Does slog replace `fmt`?**  
A: No. `fmt` is formatting; slog is an event log with levels and attributes.

**Q: How many attributes per record?**  
A: Enough for a filter (id, path, status, err). Do not dump the whole request body.

### Edge cases

1. Debug below threshold — confirm the line does not exist.
2. Duplicate Error in a retry loop — merge into one Warn + a final Error.
3. Child `With` then another `With` — attributes stack (layer by layer).
4. Mixing `log` and `slog` on the same stderr — agree one style per process.

1. Why does Fatal kill tests?
2. What does the handler do before printing?
3. What is `With` for?
4. When Warn and when Error?
5. Why consistent keys?

When you answer without looking — move on to package `time`.

### Extra pass — from Print to aggregator (step by step)

Imagine one HTTP request through three logging layers.

**Step A — classic log (script)**

```go
log.Printf("GET /api status=%d rid=%s", 200, rid)
```

Trace: one string line; filtering by `rid` requires regex.

**Step B — slog Text (local development)**

```go
slog.Info("request", "method", "GET", "path", "/api", "status", 200, "request_id", rid)
```

Trace: readable to a human; attributes already separated.

**Step C — slog JSON (production)**

```go
logger := slog.New(slog.NewJSONHandler(os.Stderr, &slog.HandlerOptions{Level: slog.LevelInfo}))
reqLog := logger.With("request_id", rid)
reqLog.Info("request", "method", "GET", "path", "/api", "status", 200)
```

#### What happens here

1. The handler chooses format; the logger chooses level and attributes.
2. `With` fixes `request_id` for the whole request.
3. The aggregator indexes JSON fields — query `status=500` does not depend on text order.
4. The same event must not be logged as Error in middleware and again as Error in the handler without agreement (noise).

### Attribute glossary (mini standard)

| Key | Value type | Example |
|-------|---------------|--------|
| `request_id` | string | `r-42` |
| `tenant` | string | `acme` |
| `method` | string | `GET` |
| `path` | string | `/v1/orders` |
| `status` | int | `200` |
| `err` | string | short message / `err.Error()` |
| `duration_ms` | int/int64 | `37` |

Stick to agreed names. Mixing `requestId` and `request_id` breaks the dashboard.

### Exercise R6 — measuring duration in the log

```go
start := time.Now()
// ... handler work ...
slog.Info("request_done",
	"path", path,
	"duration_ms", time.Since(start).Milliseconds(),
)
```

#### What happens here

1. `Since` gives a `Duration`; you convert to ms for a simple filter.
2. Do not log raw `Duration.String()` if the aggregator expects a number.
3. Debug details (SQL) stay below the threshold in production.

### Exercise R7 — one Error at the boundary

```go
func run() error {
	if err := korak1(); err != nil {
		return fmt.Errorf("korak1: %w", err) // no log here
	}
	return nil
}

func main() {
	if err := run(); err != nil {
		slog.Error("app_failed", "err", err.Error())
		os.Exit(1)
	}
}
```

#### What happens here

1. Inner layers return an error with context (`%w`).
2. Log once at the edge — on-call sees one event, not a cascade.
3. The library still has no `Fatal`.

- [ ] Attribute vocabulary written down (5–10 keys).
- [ ] JSON at least once “read” as an object (by eye or `jq`).
- [ ] Duration as a number, not only free text.
- [ ] Error logged once per failure at the boundary.
- [ ] Child logger per request/tenant.

## Summary

Classic `log` gives fast textual lines with flags and a prefix. `log/slog` introduces levels, attributes, and handlers — text for development, JSON for production. Idiom: structure at the system edge, no `Fatal` in libraries, no secrets in records. Next lesson: time with package `time`.
