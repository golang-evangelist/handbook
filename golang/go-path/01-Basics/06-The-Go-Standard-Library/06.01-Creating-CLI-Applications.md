# 06.01 Creating CLI Applications

> **Go Path - Zero to Gopher** / **01 Basics → The Go Standard Library** / Lesson 06.01

## Lesson goals

After this lesson you should be able to:

- explain the CLI process contract with the shell: `argv`, stdin, stdout, stderr, and exit code;
- read arguments via `os.Args` and understand what `os.Args[0]` is;
- define and parse options with the `flag` package, including `flag.Args()` for positional arguments;
- organize a manual subcommand router with `flag.NewFlagSet` per command;
- return correct exit codes and keep `os.Exit` out of the library (`run() error` pattern);
- separate the roles of stdin (input), stdout (data), and stderr (diagnostics).

## Prerequisite

- Basic Go: `package main`, functions, `error`, `if`, `for`, slice.
- Go 1.22 or newer.
- A terminal where you can run `go run .` with arguments (PowerShell, bash, or similar).
- Preferred: completed lessons on packages and modules (05.x), so you know where `main` lives.

## Problem this lesson solves

Many “CLI” programs in Go start as `fmt.Println` scripts, then later become unreadable and unreliable in CI and pipes:

- flags (options) and positional arguments get mixed without a clear contract;
- there is no agreed exit code, so CI cannot tell whether the tool succeeded;
- errors go to stdout, so the next program in the pipe (`jq`, `grep`) “eats” the error text and fails;
- subcommands are a chain of `if`s with no structure, so Usage and parsing scatter;
- `os.Exit` is called deep in helpers, so functions cannot be tested without killing the process.

This lesson builds a small, idiomatic command-line skeleton **without** a heavier framework (Cobra and similar come later in a career). The goal is not “the prettiest UX”, but a clear mental model that keeps pipes, CI, and tests under control.

## Mental model

A CLI is not “a program that prints text”. A CLI is a **contract with the shell** (and with other processes):

```text
process
  ├── argv[]     → os.Args          (what the user / script passed)
  ├── stdin      → os.Stdin         (pipe, file, keyboard)
  ├── stdout     → os.Stdout        (successful result for the next pipe)
  ├── stderr     → os.Stderr        (diagnostics for a human / CI log)
  └── exit code  → os.Exit(n)      (0 = success, != 0 = failure)
```

Three decisions you always keep separate:

1. **What is an option?** — tokens like `-n 3` or `--name Ana`. The `flag` package (or you manually) parses them.
2. **What is a positional argument?** — what remains after flag parsing, e.g. a file name or a message.
3. **What is a subcommand?** — often the first positional token before that command’s flags: `app greet --name Ana`.

The `flag` package parses **options**. Positional arguments remain after `Parse()`. Subcommands are not language magic: it is an agreement that `os.Args[1]` (or the first element of your argument list) chooses which function you call, and the rest goes into that command’s `FlagSet`.

For testing and a clean `main`, imagine one more layer:

```text
main → run(args) error → os.Exit only here
```

The library and business logic return `error`. The process exits at the edge.

## Mechanism

### From the shell to `os.Args`

When you type in the terminal:

```bash
go run . first "second part" --x
```

(or equivalently with a built binary), the shell **first** splits the command line into tokens. Quotes keep a space as one argument. The Go runtime then fills `os.Args` as a `[]string`:

| Index | Typical value | Meaning |
|--------|------------------|----------|
| `0` | path to the program / temporary binary | **not** a user argument |
| `1` | `"first"` | first user argument |
| `2` | `"second part"` | second (with a space) |
| `3` | `"--x"` | third — here only a string, not automatically a flag |

That is why beginners err when they use `os.Args[0]` thinking it is the first parameter. The first user token is `os.Args[1]`, and you often write `os.Args[1:]` to get the whole “tail”.

Without the `flag` package, you split tokens yourself. That is fine for micro-tools with one or two arguments. As soon as you introduce `-h`, default values, and a mix of options and positions, `flag` saves mistakes.

### Package `flag` — the global set

The simplest way:

```go
var name = flag.String("name", "guest", "user name")
flag.Parse()
fmt.Println(*name)
```

What happens, line by line:

1. `flag.String` **registers** the `-name` option in the package’s default `FlagSet`. It returns a `*string` — a pointer to the place where the value will land after parsing.
2. The default value `"guest"` holds until the user passes `-name ...`.
3. `flag.Parse()` reads `os.Args[1:]` (does not touch `Args[0]`), recognizes known flags, fills registered variables, and leaves the rest as positionals.
4. After `Parse()`, you read `*name`. Without the star you get a pointer, not a string — a common beginner mistake.

The same families exist for other types: `flag.Int`, `flag.Bool`, `flag.Duration`, etc. You can also use `flag.StringVar(&s, "name", "guest", "...")` if you already have a variable.

After a successful `Parse()`:

- `flag.Args()` — all remaining positional arguments (`[]string`);
- `flag.Arg(i)` — the i-th positional (0-based);
- `flag.NArg()` — how many there are;
- `flag.NFlag()` — how many flags were explicitly set.

Order on the command line: it is usual to put flags before positionals, but the Go `flag` package typically stops parsing flags when it hits the first non-flag argument (depending on version and call style — in practice: keep flags before positions and document Usage).

### `FlagSet` — when one command is not enough

Global `flag.Parse()` works for a tool with **one** command. As soon as you have `greet` and `sum`, each command needs its own options. That is why `flag.NewFlagSet` exists:

```go
fs := flag.NewFlagSet("greet", flag.ContinueOnError)
name := fs.String("name", "guest", "name")
err := fs.Parse(args)
```

Three error modes when creating the set:

| Constant | Behavior |
|-----------|-----------|
| `flag.ContinueOnError` | `Parse` returns an `error`; you decide the message and exit code |
| `flag.ExitOnError` | on error prints and calls `os.Exit(2)` |
| `flag.PanicOnError` | panic — rarely for a CLI |

For a testable CLI choose `ContinueOnError`. That way `Parse` does not kill the process behind the test’s back.

`fs.SetOutput(os.Stderr)` directs the flag package’s Usage and error messages to stderr — important so stdout stays clean for data.

### Manual subcommands pattern

There is no built-in “subcommand” in the `flag` package. The pattern is explicit:

1. Look at the first token (`args[0]`) as the command name.
2. Pass the remaining arguments (`args[1:]`) to that command’s `FlagSet`.
3. Each command has a function of type `func(args []string) error`.
4. `main` calls `run(os.Args[1:])`; on error it writes to stderr and does `os.Exit`.

Conceptual flow for `app greet --name Ana`:

```text
os.Args = [app, greet, --name, Ana]
run(Args[1:]) → args = [greet, --name, Ana]
switch "greet" → cmdGreet([--name, Ana])
FlagSet.Parse → name="Ana", positionals=[]
prints "hello, Ana"
return nil → exit 0
```

### Exit codes

The shell and CI read the number the process returns:

| Code | Typical meaning |
|-----|------------------|
| `0` | success |
| `1` | generic error (did not finish as intended) |
| `2` | often: wrong usage / bad arguments (Usage) |

The `2` for bad usage convention is not a Go language law, but it is common in Unix tools. Be consistent in your tool and document it.

```go
if err := run(os.Args[1:]); err != nil {
	fmt.Fprintln(os.Stderr, err)
	os.Exit(1)
}
```

For Usage errors you can return a special error type or use `errors.Is` to choose between `1` and `2`. The point: **one place** in `main` maps an error to a code.

Avoid `os.Exit` in packages below `main`. A test that calls such a helper cannot “catch” the error — the process disappears.

### stdin, stdout, stderr

- **stdin** (`os.Stdin`): read input (`bufio.Scanner`, `io.ReadAll`, etc.) when the tool runs in a pipe (`Get-Content f.txt | go run .`).
- **stdout** (`os.Stdout`): only the successful result that may go further (`\| jq`).
- **stderr** (`os.Stderr`): errors, Usage, progress, diagnostics.

If you mix an error onto stdout, the next program in the chain sees the error text as “data” and blows up. That is one of the most common CLI bugs in CI.

### Testing without killing the process

Extract the logic:

```go
func run(args []string, stdout, stderr io.Writer) error {
	// ...
	return nil
}
```

In a test pass `args` and a `bytes.Buffer`. You can return the exit code as an `int` from a thin wrapper, but **without** `os.Exit` inside `run`. That way the CLI becomes an ordinary function.

## Rules and syntax

### Flag definitions

```go
fs := flag.NewFlagSet("greet", flag.ContinueOnError)
name := fs.String("name", "guest", "name")
loud := fs.Bool("loud", false, "uppercase")
count := fs.Int("n", 1, "how many times")
```

- The flag name is without a leading dash in registration: `"name"` → the user types `-name`.
- A bool flag without a value: `-loud` sets `true`.
- Help: `-h` / `-help` usually prints Usage (`flag` package behavior).

### Conventions

- short tools: the global `flag` package;
- multiple commands: `FlagSet` per command + `switch` on the name;
- Usage short, accurate, on stderr (or consistently on one stream);
- positional arguments documented in order: `app sum 1 2 3`;
- `main` thin; logic in `run` / `cmdX`.

### What not to mix

| Token | Role |
|-------|--------|
| `greet` | subcommand (positional choice of behavior) |
| `-name Ana` | command flag |
| `file.txt` | positional data |
| `-greet` | **not** a subcommand — that is a flag named `greet` |

## Examples

### Example 1 — raw `os.Args`

```go
package main

import (
	"fmt"
	"os"
)

func main() {
	fmt.Println("program:", os.Args[0])
	for i, a := range os.Args[1:] {
		fmt.Printf("arg[%d]=%q\n", i, a)
	}
}
```

Running:

```bash
go run . first "second part" --x
```

#### What happens here

1. The runtime fills `os.Args`. Index `0` is the program path (with `go run` often a temporary binary) — printed as `program: ...`.
2. `range os.Args[1:]` walks only user tokens. The loop sees three elements.
3. First: `arg[0]="first"` — an ordinary token.
4. Second: `arg[1]="second part"` — because of quotes the shell kept the space as **one** argument. Without quotes it would be two tokens.
5. Third: `arg[2]="--x"` — looks like a flag, but here it is **not** parsed. It is only a string in the slice. The program has no `flag.Parse()`, so the dash has no special meaning.

Trace conclusion: the shell splits, Go receives a finished `[]string`. You (or the `flag` package) add flag semantics.

### Example 2 — `flag` with a positional remainder

```go
package main

import (
	"flag"
	"fmt"
	"os"
)

func main() {
	n := flag.Int("n", 1, "how many times to print")
	flag.Parse()

	if flag.NArg() < 1 {
		fmt.Fprintln(os.Stderr, "usage: prog -n N message")
		os.Exit(2)
	}
	msg := flag.Arg(0)
	for i := 0; i < *n; i++ {
		fmt.Println(msg)
	}
}
```

Sample call: `go run . -n 3 hello`

#### What happens here

1. `flag.Int("n", 1, ...)` registers `-n` with default `1`. `n` is `*int`.
2. `flag.Parse()` sees `-n` and `3`, writes `3` into `*n`. The next token `hello` is not a flag → goes to positionals.
3. `flag.NArg()` is `1`. The check passes. If there were no message, the program writes Usage to **stderr** and exits with code `2` (bad usage).
4. `flag.Arg(0)` is `"hello"`.
5. The loop `i := 0; i < *n; i++` prints the message three times on stdout. Each `Println` is one line suitable for a pipe.

If you call without `-n`, `*n` stays `1` — the default works with no extra code.

### Example 3 — manual subcommands

```go
package main

import (
	"errors"
	"flag"
	"fmt"
	"os"
	"strings"
)

func main() {
	if err := run(os.Args[1:]); err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
}

func run(args []string) error {
	if len(args) < 1 {
		return errors.New("usage: app <greet|sum> ...")
	}
	switch args[0] {
	case "greet":
		return cmdGreet(args[1:])
	case "sum":
		return cmdSum(args[1:])
	default:
		return fmt.Errorf("unknown command %q", args[0])
	}
}

func cmdGreet(args []string) error {
	fs := flag.NewFlagSet("greet", flag.ContinueOnError)
	fs.SetOutput(os.Stderr)
	name := fs.String("name", "guest", "name")
	if err := fs.Parse(args); err != nil {
		return err
	}
	fmt.Printf("hello, %s\n", *name)
	return nil
}

func cmdSum(args []string) error {
	fs := flag.NewFlagSet("sum", flag.ContinueOnError)
	fs.SetOutput(os.Stderr)
	if err := fs.Parse(args); err != nil {
		return err
	}
	total := 0
	for _, a := range fs.Args() {
		var x int
		if _, err := fmt.Sscanf(a, "%d", &x); err != nil {
			return fmt.Errorf("not a number: %q", a)
		}
		total += x
	}
	fmt.Println(total)
	return nil
}

func norm(s string) string { return strings.TrimSpace(s) }
```

Calls: `go run . greet --name Mira` and `go run . sum 1 2 10`

#### What happens here

1. `main` parses nothing itself. It passes `os.Args[1:]` into `run`. If `run` returns an error, it goes to stderr and `os.Exit(1)`. Success = quiet exit with code `0`.
2. `run` looks at `args[0]`. For `"greet"` it calls `cmdGreet` with the **remainder** — without the command name. The command’s flags do not mix with the router.
3. In `cmdGreet`, `NewFlagSet("greet", ContinueOnError)` makes an isolated set. `SetOutput(os.Stderr)` keeps help off stdout.
4. `Parse` on `[--name, Mira]` sets `*name = "Mira"`. `Printf` writes the greeting. `return nil` → the process finishes successfully.
5. In `cmdSum`, after `Parse` the positional numbers are in `fs.Args()`. The loop scans each string into an `int`. Failure of one token returns an `error` with `%q` (visible quotes help in the log). Success prints one number — clean stdout for a pipe.
6. `norm` is a helper for exercises; it shows that helper functions do not call `os.Exit`.

Trace for unknown command `app foo`: the `default` branch returns an error; `main` prints it and exits with `1`.

### Example 4 — reading stdin in a pipe

```go
package main

import (
	"bufio"
	"fmt"
	"os"
)

func main() {
	sc := bufio.NewScanner(os.Stdin)
	lines := 0
	for sc.Scan() {
		lines++
	}
	if err := sc.Err(); err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	fmt.Println(lines)
}
```

```bash
Get-Content file.txt | go run .
```

#### What happens here

1. `NewScanner(os.Stdin)` reads what the shell passes on standard input — here file content through a pipe.
2. Each successful `Scan()` advances to the next line; the loop body only increments the counter. We do not use the line content here (`Text()` would give it).
3. After the loop you **must** check `sc.Err()`. End of input is not an error; an I/O error is. The error goes to stderr, exit `1`.
4. The line count goes to stdout as one number — the next tool can read it.

If you run without a pipe, the program waits for the keyboard until you close input (Ctrl+Z Enter on Windows in some environments, Ctrl+D on Unix).

### Example 5 — testable `run` with writers

```go
package main

import (
	"bytes"
	"fmt"
	"io"
)

func run(args []string, stdout, stderr io.Writer) int {
	if len(args) < 1 {
		fmt.Fprintln(stderr, "usage: echo <text>")
		return 2
	}
	fmt.Fprintln(stdout, args[0])
	return 0
}

func main() {
	// in a real main: code = run(os.Args[1:], os.Stdout, os.Stderr); os.Exit(code)
	var out, errBuf bytes.Buffer
	code := run([]string{"hello"}, &out, &errBuf)
	fmt.Println("code", code, "out", out.String(), "err", errBuf.String())
}
```

#### What happens here

1. `run` does not touch `os.Exit`. It returns an `int` as the exit code — a test can assert `2` for bad usage.
2. A successful call with `["hello"]` writes into the `stdout` buffer; `errBuf` stays empty; the return is `0`.
3. In production `main` you only map the real `os.Stdout` / `os.Stderr` and finally call `os.Exit(code)`. One shutdown point.

## Decision analysis

| Choice | When | Why |
|-------|------|-------|
| only `os.Args` | 1–2 arguments, no options | less abstraction, clear enough |
| global `flag` | one command | fast, stdlib, enough for most scripts |
| `FlagSet` + `switch` | small multi-command CLI | isolated options per command, zero dependency |
| Cobra / similar framework | large production CLI | rich UX, help generation — but steeper learning curve |
| errors on stderr | always in pipes | keeps stdout for data |
| `run() error` or `run() int` | as soon as you want tests | `os.Exit` stays in `main` |

Keep the library free of `os.Exit`. `main` is the only place that closes the process.

## Trade-offs

| Approach | Plus | Minus |
|---------|------|-------|
| manual router | zero dependency, clear control | more boilerplate |
| framework | rich UX, completion | dependency, learning curve |
| everything on stdout | “simple” while alone | breaks pipes and CI |
| `os.Exit` deep down | quick “kill” | impossible orderly testing |
| `ContinueOnError` | you control exit | you must print Usage yourself |
| `ExitOnError` | less code | hidden `os.Exit(2)` |

## Common mistakes

1. **Wrong:** treating `os.Args[0]` as the first user argument.  
   **Effect:** you “read” the program path instead of the parameter; logic and Usage lie.  
   **Why:** index `0` is reserved for the process name/path.  
   **Fix:** use `os.Args[1:]` or `flag.Args()` after parsing.

2. **Wrong:** errors and Usage on stdout.  
   **Effect:** `tool \| jq` fails because `jq` parses the error text.  
   **Why:** stdout is the data contract between processes.  
   **Fix:** `fmt.Fprintln(os.Stderr, err)`; leave data on stdout.

3. **Wrong:** `os.Exit` in a helper / package function.  
   **Effect:** tests kill the process; you cannot return the error back.  
   **Why:** exit is a process decision, not a library one.  
   **Fix:** `return error` (or a code); `os.Exit` only in `main`.

4. **Wrong:** subcommand as a flag (`-greet` instead of `greet`).  
   **Effect:** the router does not see the command; user and documentation disagree.  
   **Why:** the flag package treats `-greet` as an option, not as an action name.  
   **Fix:** first positional token = command; flags only in its `FlagSet`.

5. **Wrong:** ignoring `flag.NArg()` / positional length.  
   **Effect:** panic on `flag.Arg(0)` or a quietly wrong result.  
   **Why:** flag parsing does not guarantee that a required file/message exists.  
   **Fix:** check `NArg()` before reading; on failure exit `2` + Usage.

6. **Wrong:** reading `*name` before `Parse()`, or forgetting the dereference.  
   **Effect:** always the default value, or a type error / wrong pointer print.  
   **Why:** registration only reserves a place; the value arrives only after `Parse`.  
   **Fix:** first `Parse`, then `*name` (or `StringVar` into an ordinary variable).

## Idiomatic Go

- `run() error` (or `run(...) int`) pattern in `main`.
- stderr for diagnostics, stdout for data.
- `FlagSet` per subcommand; `ContinueOnError` when you want control.
- Exit codes agreed with CI (document `0` / `1` / `2`).
- Usage short and accurate; sample call in one line.
- Do not introduce a framework until the manual pattern hurts.
- For numbers from strings prefer `strconv` in more serious code; `Sscanf` is OK in a small demo.

## Practical scenario

A DevOps pipe runs `inventory-export | jq .items`. A developer wrote errors and Usage with `fmt.Println` on stdout. When the database fell over, `jq` got `connection refused` instead of JSON and CI reported a “JSON parse error” instead of the real error. After moving errors to stderr, exit `1` for a DB failure and exit `2` for bad arguments, the pipe became reliable: `jq` is not run over error text, and the CI log clearly shows the cause. A `version` subcommand was added that prints semver on stdout — support can ask for the exact tool version without mixing with the export flow.

## Check questions

1. What is `os.Args[0]`?  
   **Answer:** The path (or name) of the running program; it is not the first user argument.

2. How do you get positional arguments after `flag.Parse()`?  
   **Answer:** `flag.Args()` (the whole slice), or `flag.Arg(i)` / `flag.NArg()`.

3. Why does `FlagSet` help with subcommands?  
   **Answer:** Each command has isolated options and Usage; a global `flag` would mix definitions and parsing.

4. Where should error messages go?  
   **Answer:** To stderr (`os.Stderr`), so stdout stays for data and pipes.

5. Why does `run() error` make testing easier?  
   **Answer:** A test calls `run` and checks the error without `os.Exit`; the process stays alive.

6. What is the difference between exit `1` and `2` in many CLI conventions?  
   **Answer:** `1` is a generic execution error; `2` often means wrong usage / bad arguments.

7. What does `fs.SetOutput(os.Stderr)` do?  
   **Answer:** Directs that `FlagSet`’s messages and Usage to stderr instead of the default output.

8. Why is `-greet` not the same thing as the `greet` subcommand?  
   **Answer:** `-greet` is a flag (option); `greet` is a positional token that your router interprets as a command name.

## Deeper pass: from token to exit code

Imagine the call:

```bash
app sum -verbose 10 20 30
```

(Assume you added `-verbose` on `cmdSum`.) Flow:

1. The shell produces `os.Args` ≈ `[app, sum, -verbose, 10, 20, 30]`.
2. `main` calls `run(Args[1:])` → `[sum, -verbose, 10, 20, 30]`.
3. `switch` sees `"sum"` → `cmdSum([-verbose, 10, 20, 30])`.
4. `FlagSet.Parse` strips `-verbose`; `fs.Args()` remains `[10, 20, 30]`.
5. The loop sums 60; `fmt.Println(60)` on stdout.
6. `return nil` → `main` does not call `os.Exit` → the process finishes with 0.

If the token is `xyz` instead of `sum`:

1. `default` returns `fmt.Errorf("unknown command %q", "xyz")`.
2. `main` writes that message to stderr.
3. `os.Exit(1)` — CI sees failure, stdout stays empty (the pipe does not get garbage).

### Why `ContinueOnError` changes testability

With `ExitOnError`, a bad flag calls `os.Exit(2)` inside `Parse`. A test that calls `cmdGreet([]string{"-nope"})` cannot catch the error — the process disappears. With `ContinueOnError`, `Parse` returns an `error`, you return it upward, the test asserts the message and code.

### Usage as a contract

A good Usage line answers three questions in one line:

```text
usage: app greet [-name NAME]
usage: app sum NUMBER [NUMBER...]
```

The user (and future you in six months) sees the order: command, flags, positionals. Do not write a novel — link to a `help` subcommand if more is needed.

### Table: where what lives in the code

| Responsibility | Where |
|-------------|-----|
| `os.Exit` | only `main` |
| flag parsing | the command’s `FlagSet` |
| command choice | `run` / `switch` |
| business logic | functions below, without `os` if possible |
| error print | `main` or a thin CLI layer → stderr |
| data print | command → stdout |

### Extended example: exit 2 for Usage, 1 for runtime

```go
package main

import (
	"errors"
	"fmt"
	"os"
)

var errUsage = errors.New("usage: demo <name>")

func main() {
	code := 0
	if err := run(os.Args[1:]); err != nil {
		fmt.Fprintln(os.Stderr, err)
		if errors.Is(err, errUsage) {
			code = 2
		} else {
			code = 1
		}
	}
	os.Exit(code)
}

func run(args []string) error {
	if len(args) != 1 {
		return errUsage
	}
	if args[0] == "boom" {
		return errors.New("simulated runtime error")
	}
	fmt.Println("hello,", args[0])
	return nil
}
```

#### What happens here

1. No arguments → `errUsage` → stderr + code 2.
2. Argument `boom` → ordinary error → code 1.
3. Argument `Mila` → stdout greeting → code 0.
4. `errors.Is` separates error classes without comparing message strings.

### Checklist before merging a CLI

1. Do errors go to stderr?
2. Does `os.Exit` exist only in `main`?
3. Is Usage accurate and short?
4. Does bad usage return the agreed code (often 2)?
5. Can `run` be called from a test with a `[]string`?
6. Do subcommands have an isolated `FlagSet`?

If you say “yes” six times, the tool is ready for pipes and CI.

## Workshop: from idea to a finished CLI (step-by-step)

This workshop joins the whole lesson into one protocol. Do it on an empty module.

### Step 1 — skeleton

```go
package main

import (
	"fmt"
	"os"
)

func main() {
	if err := run(os.Args[1:]); err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
}

func run(args []string) error {
	fmt.Println("TODO", args)
	return nil
}
```

Run `go run .`. See the empty TODO. Confirm that stderr errors work by `return errors.New("x")`.

### Step 2 — router

Add a `switch` on `args[0]` with `greet` and `help`. Unknown → error. Empty → Usage error.

### Step 3 — FlagSet

In `greet` add `-name` with default `"guest"`. `ContinueOnError` + `SetOutput(os.Stderr)`.

### Step 4 — pipe

Add a `lines` command that counts lines from stdin (`bufio.Scanner`). Test: `echo a\`n`b | go run . lines`.

### Step 5 — exit codes

Separate `errUsage` (code 2) from others (code 1) as in the extended example.

### Step 6 — test without a process

Extract `run(args, stdout, stderr io.Writer) int` and in `_test.go` check code 2 for empty args.

When you finish all six steps, you have an idiomatic small CLI: router, flags, pipe, exit codes, test.

### Common questions during the workshop

**Q:** Why does `flag.String` return a pointer?  
**A:** Registration happens before `Parse`; the value is filled later — the pointer shares a place in memory.

**Q:** Can a flag come after a positional?  
**A:** Keep flags first; document the order; do not rely on exotic layouts.

**Q:** Cobra right away?  
**A:** No. Learn this skeleton. A framework later saves boilerplate, but does not teach the model.

## Summary

A CLI in Go rests on `os.Args`, the `flag` package, clear stdin/stdout/stderr streams, and exit codes. A manual subcommand pattern with `FlagSet` is enough for small and medium tools. Keep `os.Exit` in `main`, errors on stderr, data on stdout. The next lesson goes deeper into `fmt` — formatting that a CLI constantly uses.
