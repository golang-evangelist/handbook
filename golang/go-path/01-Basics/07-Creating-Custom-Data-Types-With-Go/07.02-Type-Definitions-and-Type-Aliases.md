# 07.02 Type Definitions and Type Aliases

> **Go Path - Zero to Gopher** / **01 Basics → Creating Custom Data Types With Go** / Lesson 07.02

## Lesson goals

After this lesson you should be able to:

- distinguish a **type definition** (`type T U`) from a **type alias** (`type T = U`);
- predict differences in the method set and compiler boundaries;
- do explicit conversions between defined types with the same underlying type;
- choose definition when you need a new identity (UserID, Meter), alias when you need only a name or a migration.

## Prerequisite

- 07.01 (struct, methods, interfaces).
- Go 1.22+.

## Problem this lesson solves

Two syntaxes look similar:

```go
type Meter int
type Meter = int
```

But they mean different things. Mixing them leads to:

- unexpected “cannot use … as …” errors;
- methods that “disappear” because an alias is not a new type;
- a wrong feeling that an alias is domain protection (it is not).

## Mental model

**Type definition** (`type T U`) — a new type with the same **representation** (underlying), but a new **identity**.  
**Type alias** (`type T = U`) — a new name for the **same** type; no new identity.

```text
definition:  Meter ≠ int     (needs conversion)
alias:       MeterAlias ≡ int  (no conversion)
```

Methods attach to the **defined** type. An alias only redirects the name; the method set still belongs to the real type behind the name.

Underlying type: for `type Meter float64`, the underlying is `float64`. Conversions between types with the same underlying (under language rules) require the explicit form `T(x)`.

## Mechanism

### Definition — new identity

```go
type Kelvin float64

func (k Kelvin) Celsius() float64 { return float64(k) - 273.15 }
```

1. `Kelvin` is not `float64` in the type system — a different type.
2. You can add methods on `Kelvin`.
3. Assignment `var f float64 = k` does not pass without `float64(k)`.
4. The zero value of `Kelvin` is `0` (same bits as float64 zero), but the type remains `Kelvin`.

### Alias — only a name

```go
type Celzijus = float64 // same as float64
```

1. `Celzijus` and `float64` are interchangeable.
2. You do not get a new type boundary.
3. Methods “on an alias” are not a way to make a new type — language rules require a defined type in the package.

### Conversions

```go
var k Kelvin = 300
var f float64 = float64(k) // OK
// var f float64 = k       // not OK

type A int
type B int
var a A = 1
var b B = B(a) // explicit between two definition types
```

`[]A` is not `[]B` automatically — element by element or a smart helper. Slice types are different even when the element has the same underlying.

### When what

| Goal | Choice |
|------|-------|
| do not mix UserID/OrderID | `type X int64` (definition) |
| units Meter/Second | definition + methods |
| shorten a horrible type | better a named struct; alias only if you must |
| temporary rename / API migration | alias |
| generated code while a package moves | alias |

## Rules and syntax

| Syntax | Identity | Methods | Conversion to base |
|----------|-----------|--------|----------------------|
| `type T U` | new | yes, on `T` | explicit |
| `type T = U` | same as U | not as a “new type” | not needed |

Use alias sparingly. Definition when mixing raw `int`/`string` causes bugs.

## Examples

### Example 1 — definition prevents mixing

```go
package main

import "fmt"

type UserID int64
type OrderID int64

func FindUser(id UserID) { fmt.Println("user", id) }

func main() {
	var u UserID = 7
	var o OrderID = 7
	FindUser(u)
	// FindUser(o) // does not compile
	FindUser(UserID(o)) // deliberate conversion
}
```

#### What happens here

1. `u` and `o` have the same numeric value 7, but different types.
2. `FindUser(o)` the compiler rejects — that is the desired protection.
3. `UserID(o)` is an explicit decision: “I know what I am doing”. The boundary stays visible in review.

### Example 2 — alias does not protect

```go
package main

import "fmt"

type UserID = int64
type OrderID = int64

func FindUser(id UserID) { fmt.Println(id) }

func main() {
	var o OrderID = 9
	FindUser(o) // works — both are int64
}
```

#### What happens here

1. An alias is not a new boundary. `OrderID` is `int64`, `UserID` is `int64`.
2. Swapping IDs passes the compiler — a domain bug remains possible.
3. For domain safety choose definition, not alias.

### Example 3 — methods on a definition

```go
package main

import "fmt"

type Meter float64

func (m Meter) Km() float64 { return float64(m) / 1000 }

func main() {
	d := Meter(2500)
	fmt.Println(d.Km()) // 2.5
}
```

#### What happens here

1. `Meter(2500)` is a conversion from an untyped/float context into a definition type.
2. `Km` lives on `Meter`, not on `float64`.
3. Point of the type: meaning + behavior, not just a number.

### Example 4 — conversion and interface

```go
package main

import "fmt"

type Nadimak string

func (n Nadimak) String() string { return "[" + string(n) + "]" }

func main() {
	var s fmt.Stringer = Nadimak("laza")
	fmt.Println(s) // [laza]
	raw := string(s.(Nadimak))
	fmt.Println(raw)
}
```

#### What happens here

1. `Nadimak` has its own method set — satisfies `Stringer`.
2. Printing uses `String()`, not the raw string.
3. Back to `string` goes an explicit conversion after a type assert.

### Example 5 — alias in a migration

```go
package lib

// old name in the public API, new internal
type ClientConfig = Config

type Config struct {
	Host string
	Port int
}
```

#### What happens here

1. Old imports that use `ClientConfig` still see the same type as `Config`.
2. No duplicate struct — only a name.
3. After documentation migration the alias is deleted.

### Example 6 — units and JSON underlying

```go
package main

import (
	"encoding/json"
	"fmt"
)

type TicketID string

type Ticket struct {
	ID     TicketID `json:"id"`
	Naslov string   `json:"naslov"`
}

type Meter float64
type Second float64

func Brzina(put Meter, t Second) float64 {
	return float64(put) / float64(t)
}

func main() {
	b := []byte(`{"id":"T-9","naslov":"bug"}`)
	var t Ticket
	_ = json.Unmarshal(b, &t)
	fmt.Printf("%T %s\n", t.ID, t.ID)
	fmt.Println(Brzina(Meter(100), Second(10)))
}
```

#### What happens here

1. JSON still works because the underlying of `TicketID` is type `string`.
2. In Go code functions can require exactly `TicketID`.
3. `Brzina(Meter(100), Second(10))` makes units visible at the call; swapping argument types is harder to smuggle.

## Decision analysis

| Goal | Choice |
|------|-------|
| domain ID | definition |
| units + methods | definition |
| temporary rename | alias |
| only a shorter name for `map[...]` | consider a struct; alias last option |

## Trade-offs

| | Definition | Alias |
|--|------------|-------|
| safety | high | low |
| friction | more conversions | less |
| methods | yes | not as a new type |
| API migration | harder | easier |

## Common mistakes

1. **Wrong:** expecting an alias to make a new type.  
   **Effect:** mixing IDs passes.  
   **Why:** alias ≡ old type.  
   **Fix:** `type T U` without `=`.

2. **Wrong:** assuming `[]Meter` is `[]float64`.  
   **Effect:** compiler error.  
   **Why:** slice types are different.  
   **Fix:** convert elements or a generic helper.

3. **Wrong:** excessive `type MyString string` without benefit.  
   **Effect:** noise and pointless conversions.  
   **Why:** definition has a cost.  
   **Fix:** definition only when it protects meaning.

4. **Wrong:** implicit mixing of definition types.  
   **Effect:** does not compile (good!) — the developer forces a `=` alias to “pass”.  
   **Why:** wants to avoid explicitness.  
   **Fix:** leave the conversion; explicitness is a feature.

5. **Wrong:** trying a method on an alias to a type from another package as if it were a local defined type.  
   **Effect:** compiler error.  
   **Why:** methods go on defined types that you define.  
   **Fix:** make a local `type T other.U` (definition) if you need a method set.

## Idiomatic Go

- Domain ID → definition.
- Units → definition + methods.
- Alias sparingly (migration, generated code).
- Conversions make boundaries visible in code review.

## Practical scenario

An ecommerce API mixed `productID` and `warehouseID` as `int64`. A bug sent an inventory query to the wrong entity. After `type ProductID int64` / `type WarehouseID int64`, the compiler caught the swap on a PR. The alias option was rejected exactly because it would not have caught the error.

## Check questions

1. Syntax difference definition vs alias?  
   **Answer:** `type T U` vs `type T = U`.

2. Are `type A int` and `int` the same type?  
   **Answer:** No — definition makes a new type.

3. When does an alias make sense?  
   **Answer:** Name migration, generated code, rarely shortening.

4. How do you convert between two definition types with the same underlying type?  
   **Answer:** Explicitly `B(a)`.

5. Why is `[]A` not `[]B` automatically?  
   **Answer:** Slice types are different in the type system.

6. Can methods live on an alias as on a new type?  
   **Answer:** Not in that sense — you need a defined type.

7. How does definition help domain safety?  
   **Answer:** The compiler prevents mixing differently meaning values of the same underlying form.

## Deeper pass: underlying, conversions, and checklist

### Underlying type

Every type has an underlying type. For `type Meter float64`, the underlying is `float64`. Conversions allowed between types with the same underlying (under rules):

```go
type A struct{ X int }
type B A // B is a new type; underlying is struct{ X int }
var a A = A{X: 1}
var b B = B(a) // explicit
```

For structs, a definition based on another struct type still requires an explicit conversion.

### Why `[]Meter` is not `[]float64`

The type system treats the slice type as a whole. Even when the element is convertible, slice types are not. You must:

```go
out := make([]float64, len(meters))
for i, m := range meters {
	out[i] = float64(m)
}
```

Or a generic helper. That is not a bug — it prevents silent mixing of units in collections.

### Alias in generated code

A generator often does `type Foo = other.Foo` while moving packages. After migration the alias is deleted. That is a legitimate, temporary use — not a domain model.

### Checklist choosing definition vs alias

1. Does mixing with raw `int`/`string` cause bugs? → definition  
2. Are you only shortening a name? → consider a struct or (rarely) alias  
3. Do you need methods? → definition  
4. Are you doing an API migration? → alias temporarily  
5. Is `[]T` a problem if T becomes a definition? → plan conversions ahead  

### One more trace: Money

```go
type Cents int64

func (c Cents) String() string {
	return fmt.Sprintf("%d.%02d RSD", c/100, c%100)
}

func Add(a, b Cents) Cents { return a + b }
```

1. You cannot accidentally add `Cents` with an ordinary `int64` without conversion.
2. `Stringer` gives a display.
3. Zero value is `Cents(0)` — “0.00 RSD” if you call String.

## Workshop

Goal: clearly separate type definition (`type T U`) from type alias (`type T = U`), method set, and domain safety of units.

### Exercise R1 — definition prevents mixing

```go
package main

import "fmt"

type Meter float64
type Second float64

func brzina(put Meter, vreme Second) float64 {
	return float64(put) / float64(vreme)
}

func main() {
	d := Meter(100)
	t := Second(9.58)
	fmt.Println(brzina(d, t))
	// fmt.Println(brzina(t, d)) // does not compile — wrong type
}
```

#### What happens here

1. `Meter` and `Second` have the same underlying type (`float64`), but are **different** types.
2. The compiler rejects swapping arguments — that is the point of domain types.
3. Explicit conversion `float64(put)` is a deliberate unit boundary.
4. Zero value for both is `0` — still typed as `Meter(0)` / `Second(0)`.

### Exercise R2 — alias does not make a new type

```go
type UserID = string

func hello(id UserID) { fmt.Println(id) }

func main() {
	var s string = "u-1"
	hello(s) // OK — alias is only a name
}
```

Compare with:

```go
type OrderID string

func track(id OrderID) {}

func main() {
	var s string = "o-1"
	// track(s) // ERROR
	track(OrderID(s))
}
```

#### What happens here

1. Alias `UserID = string` **is** `string` — no boundary.
2. Definition `OrderID string` requires an explicit conversion.
3. You can attach methods only to a definition type, not to an alias of the same name as a predefined one.
4. Use alias for migration/naming; definition for meaning.

### Decision table — definition vs alias

| Need | Choice | Why |
|---------|-------|-------|
| Prevent mixing `int` meanings | definition | compiler guards |
| Methods on the type | definition | method set follows the new type |
| Temporary package migration | alias | same as the old type |
| Only a shorter name for `map[string]struct{}` | think / struct | alias rarely worth it |
| Slice of elements | plan conversions | `[]Meter` ≠ `[]float64` |

### Exercise R3 — methods and Stringer on a definition type

```go
type Cents int64

func (c Cents) String() string {
	neg := ""
	v := c
	if v < 0 {
		neg = "-"
		v = -v
	}
	return fmt.Sprintf("%s%d.%02d RSD", neg, v/100, v%100)
}

func Add(a, b Cents) Cents { return a + b }

func main() {
	fmt.Println(Add(Cents(199), Cents(1)))
}
```

#### What happens here

1. The method set belongs to `Cents`, not `int64`.
2. `%v` / `%s` via `fmt` use `String()` (Stringer).
3. `Add` takes only `Cents` — you cannot accidentally add with a “number of orders”.
4. Arithmetic works because the underlying is an integer type — but the result type stays `Cents`.

### Exercise R4 — slice conversion

```go
meters := []Meter{1, 2, 3}
out := make([]float64, len(meters))
for i, m := range meters {
	out[i] = float64(m)
}
```

#### What happens here

1. The type system treats the slice type as a whole.
2. Element-by-element conversion is deliberate and visible.
3. That is not a bug — it prevents silent mixing of units in collections.

### Exercise R5 — alias in a migration (sketch)

```go
// old package
// type Config struct{ ... }

// new package during the move:
type Config = stari.Config // temporary
```

#### What happens here

1. Callers do not have to change types immediately.
2. After migration the alias is deleted or replaced with a real definition.
3. Do not leave an alias forever “because it works” — document a deadline.

2. Type `Rate` (e.g. basis points) as a definition — do not mix with `Cents`.
3. Function `ApplyDiscount(cena Cents, rate Rate) Cents` with a clear formula.

#### What happens here

1. Money values without `float64` reduce rounding errors.
2. Definition types make the function signature documentation.
3. Tests work over domain types, not over “magic int”.

### Workshop FAQ

**Q: Does a definition copy methods of the underlying type?**  
A: No. `Meter` does not get methods from `float64` (there are none). You attach your own.

**Q: Can an alias have methods?**  
A: Methods belong to the real type. An alias to `string` does not get new methods under another name as if it were a new type.

**Q: What about `type A B` where B is a struct?**  
A: A new type; same fields of the underlying form; conversion `A(b)` explicit.

**Q: Generics and definition?**  
A: Works. A constraint can require underlying or comparable under language rules.

**Q: When is `int` enough?**  
A: When there is no risk of mixing meanings. As soon as “user id” and “order id” share `int` — definition.

**Q: Does JSON see the difference?**  
A: It often serializes the underlying. Tags and custom marshal are still yours.

**Q: Renaming a type in an API?**  
A: Alias temporarily; then definition or a struct with a field.

### Edge cases

1. `type M = Meter` then `type Meter float64` — the alias points at the definition.
2. Conversion between two definition types with the same underlying — explicit, deliberate.
3. Exported type with unexported underlying struct — package boundaries still apply to fields.
4. Named result + definition — readable signatures (`func f() (cena Cents, err error)`).

### Extra pass — wallet from scratch to test

**Step 1 — types**

```go
type Cents int64
type BasisPoints int // 100 bp = 1%
```

**Step 2 — arithmetic**

```go
func (c Cents) Add(o Cents) Cents { return c + o }

func (c Cents) Sub(o Cents) (Cents, error) {
	if o > c {
		return 0, fmt.Errorf("insufficient: have %s need %s", c, o)
	}
	return c - o, nil
}
```

**Step 3 — discount**

```go
func ApplyDiscount(cena Cents, bp BasisPoints) Cents {
	// bp/10000 of the price
	return cena - Cents(int64(cena)*int64(bp)/10000)
}
```

**Step 4 — table test (sketch)**

```go
tests := []struct {
	cena Cents
	bp   BasisPoints
	want Cents
}{
	{10000, 1000, 9000}, // 10.00 RSD - 10% = 9.00
	{100, 0, 100},
}
```

#### What happens here

1. `Cents` and `BasisPoints` do not mix without conversion.
2. Integer arithmetic avoids float “0.1 + 0.2” surprises.
3. `String()` on an error uses Stringer — more readable messages.
4. Raw `ApplyDiscount(100, 5)` does not compile — that is domain-model success.

### Exercise R6 — alias trap in the domain

```go
type UserID = string
type OrderID string

func f(u UserID, o OrderID) {}

func demo() {
	var s string = "x"
	f(s, OrderID(s)) // UserID accepts string; OrderID needs conversion
}
```

#### What happens here

1. An alias does not protect from mixing with `string`.
2. A definition protects — that is why IDs should be definitions.
3. Code review: `type X = string` in the domain = a red flag.

### Exercise R7 — underlying and struct definition conversion

```go
type A struct{ X int }
type B A

func main() {
	a := A{X: 1}
	b := B(a)
	fmt.Println(b.X)
}
```

#### What happens here

1. `B` is a new type; fields come from the underlying form.
2. Conversion `B(a)` is explicit and local.
3. Methods on `A` do not automatically move to `B`.

### FAQ — five more questions

**Q: Does `iota` work with a definition type?**  
A: Yes — `type Flag int` then `const ( A Flag = iota ... )`.

**Q: What about JSON tags on a definition type?**  
A: Tags live on struct fields; `Cents` itself often goes as a number.

**Q: Can a definition be a slice?**  
A: `type IDs []string` — yes; method set on `IDs`.

**Q: Why not an alias for `map[string]struct{}`?**  
A: Often a clearer named struct or a definition set type.

**Q: When is underlying not enough signal?**  
A: When you need an invariant (non-negative) — add a constructor `NewCents` + an unexported field in a struct.

## Summary

`type T U` makes a new type; `type T = U` only a new name. Method set and compiler boundaries follow definition. Choose definition for meaning, alias for naming/migration. Next lesson: embedding types and composition — not inheritance.
