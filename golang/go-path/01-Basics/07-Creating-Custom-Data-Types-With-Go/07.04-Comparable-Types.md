# 07.04 Comparable Types

> **Go Path - Zero to Gopher** / **01 Basics → Creating Custom Data Types With Go** / Lesson 07.04

## Lesson goals

After this lesson you should be able to:

- know which types may go in `==` / `!=` and as a Go map key;
- use the `comparable` constraint in generic functions;
- explain why slice, map, and func are **not** comparable;
- compare slice/map contents via `slices.Equal` and `maps.Equal`;
- predict a panic when comparing interface values whose dynamic type is not comparable;
- write an `Equal` method on a struct that contains a slice.

## Prerequisite

- Basic types, maps, generics at a beginner level.
- Go 1.22+ (`slices` / `maps` in stdlib).
- 07.01–07.03.

## Problem this lesson solves

Errors like:

```text
invalid operation: s1 == s2 (slice can only be compared to nil)
```

or a panic / failure to compile when a struct contains a slice and you want `==` as a map key. Also: generic code that requires `comparable` for map keys, and naive `any == any` that panics at runtime.

## Mental model

**Comparable** ≈ may go in `==` / `!=` and (with nuances) as a map key.

Comparable (simplified):

- bool, numbers, string, pointer, channel, interface, array (if the element is comparable), struct (if **all** fields are comparable)

Not comparable:

- slice, map, func

For **content** equality of slice/map use helper functions (`slices.Equal`, `maps.Equal`), not `==`.

```text
==  →  same type + language comparable rules
Equal helper  →  collection content
map key  →  must be comparable
```

## Mechanism

### Rules of `==`

```go
a == b   // for comparable types
s == nil // a slice may only be compared to nil
```

Two slices with each other: **does not compile**. That is not “not implemented yet” — deliberate: slice equality would be ambiguous (same backing array? same content? depth?).

A struct is comparable **only** if every field is. One `[]string` field makes the whole struct non-comparable — it cannot go in `==` nor as a map key.

### `comparable` constraint

```go
func Keys[K comparable, V any](m map[K]V) []K {
	out := make([]K, 0, len(m))
	for k := range m {
		out = append(out, k)
	}
	return out
}
```

A generic parameter with `comparable` may go in `==` and as a map key type. Without that, `map[K]V` does not compile.

### `slices.Equal` / `maps.Equal`

```go
import (
	"maps"
	"slices"
)

slices.Equal([]int{1, 2}, []int{1, 2}) // true
maps.Equal(map[string]int{"a": 1}, map[string]int{"a": 1}) // true
```

`maps.Equal` does not depend on iteration order — it compares key/value pairs.

### Interface comparison — hidden panic

Interfaces are comparable at the language level, but runtime **panics** if the dynamic values are not comparable (e.g. both `any` hold a slice). That is why you do not compare `any` naively.

### Set pattern

```go
type Set[T comparable] map[T]struct{}
```

An empty struct as the value costs zero bytes of useful payload — an idiomatic set.

## Rules and syntax

- A struct with a slice/map/func field is not comparable.
- A slice may `== nil` / `!= nil`, not `== otherSlice`.
- For tests prefer `slices.Equal` / `maps.Equal`.
- From Go 1.21+ there is also `slices.Contains` — prefer stdlib over a hand-rolled loop. `slices`, `maps`, and `cmp` are walked through together in Others, lesson 01.05. On Go 1.22, `maps.Keys` returns a slice. From Go 1.23 it returns an iterator.

## Examples

### Example 1 — what works, what does not

```go
package main

import "fmt"

func main() {
	fmt.Println(1 == 1)
	fmt.Println("a" == "a")
	var s []int
	fmt.Println(s == nil)
	// fmt.Println([]int{1} == []int{1}) // does not compile
}
```

#### What happens here

1. Scalars pass `==`.
2. `s == nil` is an allowed check for “no slice”.
3. Comparing two slice literals by content via `==` is forbidden in the language — use `slices.Equal`.

### Example 2 — struct comparable or not

```go
package main

type A struct {
	ID   int
	Name string
}

type B struct {
	ID   int
	Tags []string // makes B non-comparable
}

func main() {
	_ = A{1, "x"} == A{1, "x"}
	// _ = B{} == B{} // no
}
```

#### What happens here

1. `A` has only comparable fields → `==` works.
2. `B.Tags` is a slice → the whole `B` loses comparable.
3. Consequence: `map[B]int` does not compile; you need another key design or an `Equal` method.

### Example 3 — generic Set

```go
package main

import "fmt"

type Set[T comparable] map[T]struct{}

func (s Set[T]) Add(v T) { s[v] = struct{}{} }
func (s Set[T]) Has(v T) bool { _, ok := s[v]; return ok }

func main() {
	s := Set[string]{}
	s.Add("Go")
	fmt.Println(s.Has("Go"))
}
```

#### What happens here

1. `T comparable` allows `T` as a map key.
2. `Add` writes an empty struct; `Has` is comma-ok on the map.
3. Without the `comparable` constraint this map definition would not compile.

### Example 4 — slices.Equal and maps.Equal

```go
package main

import (
	"fmt"
	"maps"
	"slices"
)

func main() {
	a := []int{1, 2, 3}
	b := []int{1, 2, 3}
	fmt.Println(slices.Equal(a, b))

	m1 := map[string]int{"x": 1}
	m2 := map[string]int{"x": 1}
	fmt.Println(maps.Equal(m1, m2))
}
```

#### What happens here

1. `slices.Equal` compares length and elements by index.
2. `maps.Equal` compares the set of pairs — insertion order does not matter.
3. In a test: `if !slices.Equal(got, want) { t.Fatalf(...) }` reads clearer than hand-rolled loops.

### Example 5 — interface comparison caution

```go
package main

import "fmt"

func main() {
	var i any = []int{1}
	var j any = []int{1}
	defer func() {
		if r := recover(); r != nil {
			fmt.Println("panic:", r)
		}
	}()
	fmt.Println(i == j) // may panic
}
```

#### What happens here

1. `i` and `j` are interface boxes; the `==` syntax is allowed.
2. The dynamic values are slices — runtime panics.
3. Conclusion: in code that takes `any` do not do `==` unless you control the types.

### Example 6 — Equal method on a struct with a slice

```go
package main

import (
	"fmt"
	"slices"
)

type Tim struct {
	Ime     string
	Clanovi []string
}

func (t Tim) Equal(o Tim) bool {
	return t.Ime == o.Ime && slices.Equal(t.Clanovi, o.Clanovi)
}

func main() {
	a := Tim{"A", []string{"x", "y"}}
	b := Tim{"A", []string{"x", "y"}}
	fmt.Println(a.Equal(b))
}
```

#### What happens here

1. `Tim` is not comparable because of the slice field.
2. We ourselves define content equality — the idiomatic path for domain types.
3. Map key strategies if needed: a canonical string, a hash, or only simple fields in the key.

## Decision analysis

| Need | Tool |
|---------|------|
| map key | comparable type |
| slice equality | `slices.Equal` |
| map equality | `maps.Equal` |
| struct with slice | `Equal` method |
| generic set | `map[T]struct{}` + `comparable` |

## Trade-offs

| Approach | Plus | Minus |
|---------|------|-------|
| `==` | built-in, fast | limited |
| Equal helpers | clear, stdlib | need to know the API |
| hash + DeepEqual | flexible | slower / reflection |

## Common mistakes

1. **Wrong:** `==` on two slices.  
   **Effect:** does not compile.  
   **Why:** a slice is not comparable.  
   **Fix:** `slices.Equal`.

2. **Wrong:** a struct with a slice as a map key.  
   **Effect:** compiler error.  
   **Why:** the struct inherits a non-comparable field.  
   **Fix:** another key shape or do not use a map over that struct.

3. **Wrong:** `any == any` with a slice inside.  
   **Effect:** panic at runtime.  
   **Why:** the dynamic type is not comparable.  
   **Fix:** type switch / explicit comparison.

4. **Wrong:** assuming `maps.Equal` depends on insertion order.  
   **Effect:** wrong mental model (even if the result often “looks OK”).  
   **Why:** maps have no order.  
   **Fix:** think in sets of pairs.

5. **Wrong:** a hand-rolled nested for instead of `slices.Equal` in tests.  
   **Effect:** off-by-one, worse message.  
   **Why:** repeating stdlib logic.  
   **Fix:** stdlib helper + `t.Fatalf` with `%v`.

## Idiomatic Go

- `comparable` in generics for keys.
- `slices` / `maps` packages instead of copy-paste loops.
- Keep map keys simple (string/int/definition types).
- For domain types with a slice: an explicit `Equal` method.

## Practical scenario

Configuration `type Cfg struct { Hosts []string }` could not go in `==` for a cache key. The team switched to a canonical string (sort + join) as the key, and in tests to `slices.Equal`. A generic cache `map[K]V` got `K comparable`. One panic incident: comparing two `any` from JSON decode — fix a type switch before comparison.

## Check questions

1. Which types are not comparable?  
   **Answer:** slice, map, func (and struct/array that contain them).

2. What is `comparable` for?  
   **Answer:** a constraint that allows `==` and a map key in generics.

3. Why is a struct with a slice not a map key?  
   **Answer:** it is not comparable because it contains a non-comparable field.

4. Difference `s == nil` vs `s1 == s2` for a slice?  
   **Answer:** with nil it is allowed; with each other it does not compile.

5. What does `maps.Equal` do?  
   **Answer:** content equality of maps by key/value pairs.

6. Why can `any == any` panic?  
   **Answer:** if the dynamic types are not comparable.

7. How do you make a set of unique values?  
   **Answer:** `map[T]struct{}` where `T` is comparable.

## Deeper pass: key strategies and testing Equal

### Map key strategies when a struct is not comparable

1. A simple `string` / `int` / definition type as the key.  
2. A canonical string (e.g. join of a sorted slice) as the key.  
3. A hash if it is hard — document collisions.  

Do not force `==` where the language does not allow it.

### Test pattern

```go
if !slices.Equal(got, want) {
	t.Fatalf("got %v want %v", got, want)
}
```

Reads clearer than hand-rolled loops and reduces off-by-one.

### Generic helper then stdlib

```go
func Contains[T comparable](list []T, want T) bool {
	for _, v := range list {
		if v == want {
			return true
		}
	}
	return false
}
```

From Go 1.21+ prefer `slices.Contains` instead of your own.

### Equality checklist

1. Does the type go as a map key? → must be comparable.  
2. Does the struct have a slice/map/func field? → not comparable.  
3. Are you comparing slice/map content? → Equal helpers.  
4. Are you comparing any? → think twice (panic).  

## Workshop

Goal: comparable types, map keys, why slice/map/func do not go in `==`, and content equality via `slices`/`maps`.

### Exercise R1 — what may go in `==`

```go
package main

import "fmt"

func main() {
	fmt.Println(1 == 1)
	fmt.Println("a" == "a")
	type Tacka struct{ X, Y int }
	fmt.Println(Tacka{1, 2} == Tacka{1, 2})

	var s []int
	fmt.Println(s == nil) // OK
	// fmt.Println([]int{1} == []int{1}) // does not compile
}
```

#### What happens here

1. Basic types and a struct without non-comparable fields may go in `==`.
2. A slice may only be compared to `nil`, not to each other.
3. Map and func are also not comparable (except `== nil` where it applies).
4. The compiler blocks invalid comparisons — that is a feature.

### Exercise R2 — struct with a slice field

```go
type Red struct {
	ID   int
	Tagovi []string
}

// var _ = Red{} == Red{} // error: Red is not comparable
```

#### What happens here

1. One non-comparable field “infects” the whole struct.
2. Such a type cannot be a map key.
3. Strategies: extract a comparable key (`ID`), or a canonical string, or an `Equal` method.

### Exercise R3 — map as a set

```go
set := map[string]struct{}{}
for _, w := range []string{"a", "b", "a"} {
	set[w] = struct{}{}
}
_, ok := set["a"]
fmt.Println(len(set), ok) // 2 true
```

#### What happens here

1. A map key must be comparable — `string` is.
2. `struct{}{}` as the value saves memory (empty struct).
3. `ok` from the lookup is the idiomatic membership check.
4. The zero value of a map is `nil` — reading works, writing panics until you `make`.

### Exercise R4 — content equality

```go
import (
	"fmt"
	"maps"
	"slices"
)

func main() {
	a := []int{1, 2, 3}
	b := []int{1, 2, 3}
	fmt.Println(slices.Equal(a, b))

	m1 := map[string]int{"x": 1}
	m2 := map[string]int{"x": 1}
	fmt.Println(maps.Equal(m1, m2))
}
```

#### What happens here

1. `slices.Equal` compares elements in order.
2. `maps.Equal` compares key/value pairs (order does not matter).
3. For float caution: NaN != NaN by IEEE — read EqualFunc docs when needed.
4. Tests become shorter and less off-by-one.

### Exercise R5 — comparable constraint

```go
func Contains[T comparable](list []T, want T) bool {
	for _, v := range list {
		if v == want {
			return true
		}
	}
	return false
}
```

From Go 1.21+ prefer `slices.Contains`.

#### What happens here

1. Constraint `comparable` allows `==` in the generic body.
2. Types that are not comparable fail the call’s type check.
3. That is the same requirement as a map key — generics make it explicit.

### Exercise R6 — the `any == any` trap

```go
var a any = []int{1}
var b any = []int{1}
// fmt.Println(a == b) // panic at runtime: slice is not comparable
```

#### What happens here

1. The compiler allows `==` on `any` because an interface is comparable **if** the dynamic types are comparable.
2. If inside they are not — panic at runtime.
3. That is why you do not compare `any` naively; use a type assert or a specialized Equal.

### Decision table — how do I compare?

| Type | `==` | Better tool |
|-----|------|------------|
| int/string/struct (clean) | yes | `==` |
| slice | only vs nil | `slices.Equal` |
| map | only vs nil | `maps.Equal` |
| func | only vs nil | do not compare the “body” |
| any | caution | assert / Equal |
| type with a slice field | no | `Equal` method / ID |

### Workshop FAQ

**Q: Are arrays comparable?**  
A: Yes, if the element is comparable. Fixed length is part of the type.

**Q: Is an interface comparable?**  
A: Yes, provided the dynamic values are — otherwise panic on `==`.

**Q: Why does Go not compare slices with `==`?**  
A: The semantics (header vs content vs identity) would be confusing; that is why explicit helpers.

**Q: `maps.Clone` vs Equal?**  
A: Clone copies; Equal compares. Different jobs.

**Q: Pointers?**  
A: `==` compares addresses, not deep content.

**Q: Float key?**  
A: Technically comparable, but NaN and rounding make a bad key — avoid.

**Q: How Equal for your own type?**  
A: Method `Equal(other T) bool` or a package function — document the rules.

### Edge cases

1. Nil map vs empty map — check `maps.Equal` treatment.
2. Struct with a func field — not comparable.
3. Channel — comparable by identity (same channel), not by buffer content.
4. Generic `map[K]V` requires `K comparable`.

### Code review trace

When you see:

```go

```

stop the PR. That is not type equality — it is a brittle string dump. Use Equal / `==` / ID.

### Extra pass — order index (full mini project)

```go
package main

import (
	"fmt"
	"slices"
)

type OrderID string

type Order struct {
	ID    OrderID
	Items []string
}

func indexByID(orders []Order) map[OrderID]Order {
	m := make(map[OrderID]Order, len(orders))
	for _, o := range orders {
		m[o.ID] = o
	}
	return m
}

func sameItems(a, b []string) bool {
	aa := slices.Clone(a)
	bb := slices.Clone(b)
	slices.Sort(aa)
	slices.Sort(bb)
	return slices.Equal(aa, bb)
}

func main() {
	orders := []Order{
		{ID: "o1", Items: []string{"bread", "milk"}},
		{ID: "o2", Items: []string{"milk", "bread"}},
	}
	idx := indexByID(orders)
	fmt.Println(idx["o1"].ID)
	fmt.Println(sameItems(orders[0].Items, orders[1].Items))
}
```

#### What happens here

1. `OrderID` is a comparable definition type — a valid map key.
2. `Order` with a slice field is **not** comparable — that is why it is not a key.
3. `sameItems` compares content regardless of order (sort of a copy).
4. `Clone` before `Sort` preserves the original input order.
5. Trying `map[Order]int` does not compile — a deliberate exercise.

### Exercise R7 — set and frequency

```go
func unique(words []string) []string {
	seen := map[string]struct{}{}
	var out []string
	for _, w := range words {
		if _, ok := seen[w]; ok {
			continue
		}
		seen[w] = struct{}{}
		out = append(out, w)
	}
	return out
}
```

#### What happens here

1. `map[string]struct{}` = a set.
2. Comma-ok avoids duplicates.
3. Order of `out` follows first appearance — more deterministic than ranging over a map.

### Exercise R8 — Array vs slice equality

```go
a := [2]int{1, 2}
b := [2]int{1, 2}
fmt.Println(a == b) // true — array comparable

s1 := []int{1, 2}
s2 := []int{1, 2}
fmt.Println(slices.Equal(s1, s2))
```

#### What happens here

1. A fixed-length array with comparable elements may use `==`.
2. A slice needs a helper.
3. The array type includes length: `[2]int` ≠ `[3]int`.

### Exercise R9 — channel identity

```go
ch1 := make(chan int)
ch2 := ch1
ch3 := make(chan int)
fmt.Println(ch1 == ch2) // true
fmt.Println(ch1 == ch3) // false
```

#### What happens here

1. A channel is comparable by identity (same object), not by buffer content.
2. Rarely useful; do not use as “deep equal”.

### FAQ — more questions

**Q: Nil vs empty slice in Equal?**  
A: `slices.Equal` treats nil and empty as equal — confirm in a test if you need different semantics.

**Q: How Equal for a struct with a slice?**  
A: Manually compare fields; for slice fields call `slices.Equal`.

**Q: Does `maps.Equal` look at the value type?**  
A: Values must be comparable with each other under Equal rules — see the docs for func/slice values.

**Q: Hash as a key?**  
A: Document collisions; prefer a canonical string when you can.

**Q: Why not `fmt.Sprint` for equality?**  
A: Brittle, slow, depends on format — false positive/negative.
