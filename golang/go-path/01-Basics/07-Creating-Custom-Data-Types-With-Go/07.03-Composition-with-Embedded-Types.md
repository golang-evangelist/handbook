# 07.03 Composition with Embedded Types

> **Go Path - Zero to Gopher** / **01 Basics → Creating Custom Data Types With Go** / Lesson 07.03

## Lesson goals

After this lesson you should be able to:

- use embedding of a Go struct into another struct and understand promotion of fields and methods;
- predict shadowing: when an outer name hides an inner one, the **outer method wins**;
- resolve ambiguity when two embedded types offer the same name;
- use embedding of interfaces into an interface (`io.ReadWriter` style) and into a struct (decorator);
- use the pattern with `sync.Mutex` — and know why you often do **not** embed a mutex but name the field;
- explain why embedding is **not** class inheritance (no is-a, no virtual dispatch through a “base”).

## Prerequisite

- 07.01–07.02 (struct, methods, interfaces, types).
- Go 1.22+.
- A basic feel for `io.Reader` / `io.Writer` helps.

## Problem this lesson solves

From OOP habits people write “extends” and expect virtual methods. In Go you expect **composition**. Embedding eases delegation with syntactic sugar, but:

- it looks like inheritance even though it is has-a;
- shadowing confuses which `ID` or `Tag` is called;
- promotion can hide real dependencies and widen the API more than it should (`Lock` on a cache);
- a nil embedded interface panics on call.

This lesson teaches embedding of structs **and** interfaces as a composition tool — without the word “inherit”.

## Mental model

Embedding is a **field without an explicit name**:

```go
type Motor struct{ KW int }

type Auto struct {
	Motor // embedded — the field name is Motor
	Marka string
}
```

`Auto` **has** a `Motor` (has-a). It is not “Auto is a Motor”. Syntactic sugar allows `a.KW` instead of `a.Motor.KW` as long as there is no conflict — that is **promotion**.

For interfaces:

```go
type ReadWriter interface {
	io.Reader
	io.Writer
}
```

A larger interface is a **union of methods** of smaller ones. That is not a class hierarchy; it is joining contracts of behavior.

```text
embedding  →  anonymous field
promotion   →  selectors “bubble” outward
shadowing   →  the outer name at that level wins
ambiguity   →  the compiler does not guess — explicit path
polymorphism →  still via interface, not via a “base”
```

## Mechanism

### Promotion of fields and methods

When you embed `Motor` in `Auto`:

1. There is a real field `Motor` (you can use `a.Motor`).
2. Exported fields of `Motor` become available as `a.KW` if there is no conflict.
3. Methods of `Motor` enter the outer type’s method set (under usual pointer/value receiver rules) — again with conflicts.

A call `a.Opis()` where `Opis` is on `Motor` is equivalent to `a.Motor.Opis()` when there is no override on `Auto`.

### Shadowing — the outer wins

If `Auto` (or `Specijal`) declares a field or method of the same name:

- selector `s.ID` chooses the **outer** field;
- `s.Tag()` calls the **outer** method;
- the inner still lives: `s.Baza.ID`, `s.Baza.Tag()`.

There is no virtual table: if you have a variable of the embedded type, you call **its** methods, not an outer “override”. If you want polymorphism, put values in an interface.

### Ambiguity

```go
type A struct{ X int }
type B struct{ X int }
type C struct {
	A
	B
}
// c.X — error: ambiguous
// c.A.X or c.B.X — OK
```

The compiler does not choose “the first embedded”. You must be explicit.

### Embedding interfaces into an interface

```go
type ReadWriter interface {
	Reader
	Writer
}
```

`ReadWriter` requires all methods of both. A type that satisfies both also satisfies the join. Stdlib idiom (`io.ReadWriter`).

### Embedding an interface into a struct

```go
type Greeter struct {
	io.Reader
}
```

`Greeter` gets `Read` by promotion **if** the field is non-nil. If `Reader` is nil, a call to `g.Read` panics. Useful for decorators; dangerous without nil control.

### Pattern `sync.Mutex` — embed or name?

A common (and often wrongly copied) idiom:

```go
type Keš struct {
	sync.Mutex // EMBEDDED — promotes Lock/Unlock
	m map[string]string
}
```

Problem: outside code can `k.Lock()` — you widen the cache API with sync details. Better:

```go
type Keš struct {
	mu sync.Mutex // NAMED — no promotion
	m  map[string]string
}

func (k *Keš) Get(key string) (string, bool) {
	k.mu.Lock()
	defer k.mu.Unlock()
	v, ok := k.m[key]
	return v, ok
}
```

**Rule:** use embedding when you **want** promotion into the API. Do not use embedding when promotion widens the surface more than it should. For a mutex almost always name `mu`.

### Why this is not inheritance

| Expectation from classes | What Go does |
|---------------------|-------------|
| is-a hierarchy | has-a field |
| virtual call through a base type | none; you need an interface |
| a slice of “bases” holds overrides | does not work |
| `super.Tag()` magic | explicit `s.Baza.Tag()` |

Composition + interfaces replace class inheritance. Embedding is sugar around composition, not a substitute for virtual dispatch.

## Rules and syntax

- Embedded name = type name (without a package qualifier in the field selector).
- Multiple embeddings with the same selector → ambiguity.
- Do not build deep embedding trees as class hierarchies.
- Prefer a clearly named field if promotion hurts readability.
- JSON: embedded fields often “flatten” on marshal; a named field often stays nested — check the output.

## Examples

### Example 1 — field and method promotion

```go
package main

import "fmt"

type Motor struct{ KW int }

func (m Motor) Opis() string { return fmt.Sprintf("%d kW", m.KW) }

type Auto struct {
	Motor
	Marka string
}

func main() {
	a := Auto{Motor: Motor{KW: 110}, Marka: "Zastava"}
	fmt.Println(a.KW)          // 110 — promotion
	fmt.Println(a.Opis())      // 110 kW — method promotion
	fmt.Println(a.Motor.Opis()) // same call via the explicit path
}
```

#### What happens here

1. The composite literal fills the embedded field with the type name `Motor: Motor{...}`.
2. `a.KW` reads the promoted field — equivalent to `a.Motor.KW`.
3. `a.Opis()` finds the method on the embedded type because `Auto` has no own `Opis`.
4. The explicit path still exists — embedding does not erase the has-a relationship.

### Example 2 — shadowing, the outer method wins

```go
package main

import "fmt"

type Baza struct{ ID string }

func (b Baza) Tag() string { return "base:" + b.ID }

type Specijal struct {
	Baza
	ID string
}

func (s Specijal) Tag() string { return "spec:" + s.ID }

func main() {
	s := Specijal{Baza: Baza{ID: "B1"}, ID: "S9"}
	fmt.Println(s.ID)        // S9 — outer
	fmt.Println(s.Baza.ID)   // B1 — inner
	fmt.Println(s.Tag())     // spec:S9 — outer method
	fmt.Println(s.Baza.Tag()) // base:B1
}
```

#### What happens here

1. Both types have `ID` and `Tag`. On selector `s` the outer level wins.
2. The inner is not deleted — only hidden.
3. There is no “virtual” `Tag` if you held a `Baza` value separately: you would call `Baza.Tag`.
4. Value trace: `s.ID` is `"S9"`; `s.Baza.ID` is `"B1"` — two fields, two strings.

### Example 3 — no inheritance polymorphism

```go
package main

import "fmt"

type Zivotinja struct{ Ime string }

func (z Zivotinja) Glas() { fmt.Println("?") }

type Pas struct{ Zivotinja }

func (p Pas) Glas() { fmt.Println("av") }

func main() {
	p := Pas{Zivotinja: Zivotinja{Ime: "Džeki"}}
	p.Glas()            // av
	p.Zivotinja.Glas()  // ?
	// there is no: var z Zivotinja = p  with virtual Glas
}
```

#### What happens here

1. `Pas` has an embedded `Zivotinja` — has-a.
2. `p.Glas()` calls the outer method (shadowing).
3. There is no assignment of `Pas` into `Zivotinja` as a “subtype”. For a list of different sounds use interface `Glasac { Glas() }`.

### Example 4 — embedding an interface into a struct

```go
package main

import (
	"fmt"
	"io"
	"strings"
)

type Greeter struct {
	io.Reader
}

func main() {
	g := Greeter{Reader: strings.NewReader("hello")}
	buf := make([]byte, 6)
	n, _ := g.Read(buf)
	fmt.Println(string(buf[:n]))
}
```

#### What happens here

1. A field of type `io.Reader` is embedded — `Read` is promoted.
2. `NewReader` gives a non-nil implementation; `Read` reads “hello”.
3. Had `Reader` stayed the nil zero value, `g.Read` would panic — embedding does not protect from nil.

### Example 5 — embedding interfaces into an interface + ambiguity

```go
package main

import (
	"fmt"
	"io"
)

type ReadWriter interface {
	io.Reader
	io.Writer
}

type A struct{ X int }
type B struct{ X int }
type C struct {
	A
	B
}

func main() {
	var _ ReadWriter // only a type-name demonstration
	c := C{A: A{X: 1}, B: B{X: 2}}
	fmt.Println(c.A.X, c.B.X)
	// fmt.Println(c.X) // does not compile: ambiguous selector X
}
```

#### What happens here

1. `ReadWriter` joins two contracts — the type must have both `Read` and `Write`.
2. `C` uses embedding of `A` and `B` with the same field `X`.
3. `c.X` is ambiguity; `c.A.X` / `c.B.X` are unambiguous. The compiler does not guess.

### Example 6 — Mutex named; decorator with override Write

```go
package main

import (
	"fmt"
	"io"
	"os"
	"sync"
)

type Keš struct {
	mu sync.Mutex
	m  map[string]string
}

func (k *Keš) Get(key string) (string, bool) {
	k.mu.Lock()
	defer k.mu.Unlock()
	v, ok := k.m[key]
	return v, ok
}

type Brojac struct {
	io.Writer
	N int
}

func (b *Brojac) Write(p []byte) (int, error) {
	n, err := b.Writer.Write(p)
	b.N += n
	return n, err
}

func main() {
	k := &Keš{m: map[string]string{"a": "1"}}
	fmt.Println(k.Get("a"))

	b := &Brojac{Writer: os.Stdout}
	fmt.Fprintln(b, "hello")
	fmt.Fprintln(os.Stderr, "bytes:", b.N)
}
```

#### What happens here

1. `Keš` does not use embedding of `Mutex` — `Lock` is not part of the type’s public API. Only the cache methods lock.
2. `Brojac` uses embedding of `Writer`, but **defines its own** `Write` — the outer method wins (shadowing). Inside it explicitly calls `b.Writer.Write`.
3. `Fprintln(b, ...)` uses `Brojac` as an `io.Writer` because of method `Write`; counter `N` grows.

## Decision analysis

| Situation | Embedding? |
|-----------|------------|
| has-a with frequent delegation | yes |
| you want an is-a hierarchy | no — interface |
| decorator around Reader/Writer | often yes |
| sync.Mutex in a struct | usually **do not** embed — name `mu` |
| deep tree of 5 levels | no |

## Trade-offs

| | Embedding | Named field |
|--|-----------|-----------------|
| brevity | better | longer |
| clarity | sometimes worse | better |
| shadowing risk | higher | lower |
| API surface | easier to “leak” | more controlled |

## Common mistakes

1. **Wrong:** treating embedding as inheritance / is-a.  
   **Effect:** expecting virtual dispatch and `[]Baza` with overrides — does not work.  
   **Why:** embedding is has-a sugar.  
   **Fix:** interface for polymorphism; embedding for composition.

2. **Wrong:** nil embedded interface then calling methods.  
   **Effect:** panic.  
   **Why:** promotion calls a method on a nil value.  
   **Fix:** always set an implementation; check nil.

3. **Wrong:** embedded `sync.Mutex` then public `Lock` on the type.  
   **Effect:** broken encapsulation; outside mistakes in locking.  
   **Why:** promotion widens the API.  
   **Fix:** named field `mu`.

4. **Wrong:** shadowing an ID field then wrong JSON / log.  
   **Effect:** you read the outer ID thinking it is the base.  
   **Why:** the outer selector wins.  
   **Fix:** explicit path or different names.

5. **Wrong:** ignoring ambiguity “the compiler will choose”.  
   **Effect:** does not compile.  
   **Why:** Go does not guess.  
   **Fix:** `c.A.X` / rename.

6. **Wrong:** deep embedding trees as a Java hierarchy.  
   **Effect:** unreadable code, hard to follow methods.  
   **Why:** wrong mental model.  
   **Fix:** shallow composition + interfaces.

## Idiomatic Go

- Composition instead of class inheritance.
- Small embedded types when promotion truly helps.
- Mutex as `mu sync.Mutex`, not embedded, except a deliberate decision.
- Interfaces for polymorphism.
- Explicit fields when readability suffers.
- Check JSON output before embedding enters a public API.

## Practical scenario

A team embedded `User` into `Admin` and expected a slice of “users” to hold admins with override methods. It did not work. Solution: interface `Account` with `Permissions()`, and `Admin` and `User` separately. Embedding remained only for a shared `AuditMeta` data struct. Another PR: embedded `sync.Mutex` on `Cache` — clients called `Lock` in the wrong order; switching to `mu` removed promotion.

## Check questions

1. What is promotion?  
   **Answer:** Selectors of fields/methods of the embedded type “bubble” to the outer type when there is no conflict.

2. Why is embedding not inheritance?  
   **Answer:** It remains has-a; there is no is-a nor virtual dispatch through a base type.

3. What happens on shadowing?  
   **Answer:** The outer field/method wins on that selector; the inner remains via the explicit path.

4. How does embedding interfaces help?  
   **Answer:** It joins smaller contracts into a larger one or adds methods to a struct by promotion.

5. What if two embedded types have the same field?  
   **Answer:** Ambiguity — you need an explicit selector.

6. What risk does a nil embedded interface carry?  
   **Answer:** Panic when calling a promoted method.

7. When prefer a named field (e.g. mutex)?  
   **Answer:** When you do not want promotion to widen the API or hide ownership.

## Deeper pass: JSON, Mutex, and an embedding checklist

### JSON and embedding

```go
type Meta struct {
	Created string `json:"created"`
}
type Dokument struct {
	Meta
	Naslov string `json:"naslov"`
}
```

Fields often “flatten” into one JSON object (`created` next to `naslov`). If you want a nested object `{"meta":{...}}`, use a named field `Meta Meta`. **Always** check marshal output before embedding enters a public API.

### When NOT to use embedding

- When you want to hide methods of the inner type → named field.  
- When the relationship is “has”, but promotion confuses the reader → name it.  
- When it is `sync.Mutex` → almost always `mu`.  
- When you are building an OOP hierarchy in your head → stop; use an interface.

### Decorator reminder (already in example 6)

The outer `Write` wins (shadowing). Inside you explicitly call the embedded `Writer`. That is composition, not override in the class sense.

### Checklist before merge

1. Is the has-a relationship clear from the type names?  
2. Does promotion hide too much?  
3. Is there shadowing of ID/method?  
4. Would an interface better model polymorphism?  
5. Is the mutex named, not embedded?  
6. Can a nil embedded interface panic?

If you answer “problematic” three times, refactor before merge.

### Exercise R1 — field promotion

```go
package main

import "fmt"

type Adresa struct {
	Grad string
	PTT  string
}

type Kupac struct {
	Adresa
	Ime string
}

func main() {
	k := Kupac{
		Adresa: Adresa{Grad: "Beograd", PTT: "11000"},
		Ime:    "Mila",
	}
	fmt.Println(k.Grad, k.PTT, k.Ime)
	fmt.Println(k.Adresa.Grad)
}
```

#### What happens here

1. `Adresa` is an anonymous embedded field — type and field name match.
2. `k.Grad` is a promoted selector; equivalent to `k.Adresa.Grad` when there is no conflict.
3. The relationship is has-a: a customer **has** an address, is not a “subtype” of address.
4. The composite literal still fills the embedded field explicitly via `Adresa: ...`.

### Exercise R2 — shadowing methods

```go
type Baza struct{}

func (Baza) Tag() string { return "base" }

type Specijal struct {
	Baza
}

func (Specijal) Tag() string { return "special" }

func main() {
	s := Specijal{}
	fmt.Println(s.Tag())      // special
	fmt.Println(s.Baza.Tag()) // base
}
```

#### What happens here

1. The outer method wins on selector `Tag`.
2. The inner remains available via the explicit path `s.Baza.Tag()`.
3. That is not a virtual override from classical OOP — there is no polymorphism through a “base” type.
4. Polymorphism in Go goes through an interface, not through an embedding tree.

### Exercise R3 — ambiguity

```go
type A struct{ X int }
type B struct{ X int }
type C struct {
	A
	B
}

func main() {
	c := C{A: A{X: 1}, B: B{X: 2}}
	// fmt.Println(c.X) // error: ambiguous
	fmt.Println(c.A.X, c.B.X)
}
```

#### What happens here

1. Two embedded types with the same selector → ambiguity.
2. The compiler requires an explicit path.
3. Refactor: named fields or a different data model.

### Exercise R4 — embedding an interface, not a mutex

```go
package main

import (
	"io"
	"sync"
)

type Brojac struct {
	io.Writer
	N int
}

func (b *Brojac) Write(p []byte) (int, error) {
	n, err := b.Writer.Write(p)
	b.N += n
	return n, err
}

type Bezbedno struct {
	mu sync.Mutex // named — NOT embedded
	n  int
}

func (b *Bezbedno) Inc() {
	b.mu.Lock()
	b.n++
	b.mu.Unlock()
}
```

#### What happens here

1. Decorator `Brojac` shadows `Write`, and inside calls the embedded `Writer`.
2. Embedded `io.Writer` (nil) → panic on call — check before use.
3. `sync.Mutex` as a named field does not promote `Lock` onto the type’s API.
4. An embedded mutex would “leak” `Lock`/`Unlock` into the public method set — usually you do not want that.

### Decision table — embed or name?

| Situation | Embed | Name |
|-----------|--------|--------|
| You want selector promotion | yes | — |
| You want to hide the inner API | — | yes |
| `sync.Mutex` / `RWMutex` | almost never | almost always |
| JSON flattened object | often embedding | nested field |
| OOP hierarchy in your head | stop | interface |

### Workshop FAQ

**Q: Why is embedding not inheritance?**  
A: No is-a, no virtual dispatch through a base type. It remains composition.

**Q: Do methods of the embedded type automatically enter an interface?**  
A: Promoted methods enter the outer type’s method set — yes, that is a common idiom for “wrapper + extra methods”.

**Q: What if I embed a pointer type `*T`?**  
A: Possible; nil pointer embedded → panic on call. Initialize.

**Q: Multiple embedding?**  
A: Allowed, but ambiguity grows. Keep it shallow.

**Q: Embedding interfaces into an interface?**  
A: Joins contracts (`io.ReadWriter`). That is idiomatic.

**Q: Can fields shadow?**  
A: Yes — an outer field of the same name hides promotion.

**Q: When a decorator instead of a middleware function?**  
A: When you need to keep an `io.Writer` type and add state (`N` bytes).

### Edge cases

1. Promoted method with a pointer receiver — the outer type must be addressable where needed.
2. Two levels of embedding — the selector can be deep; readability drops.
3. JSON `omitempty` on embedded — check encoding/json documentation.
4. A test that calls `Lock` on the type — a signal that the mutex leaked by promotion.

### Extra pass — byte decorator (full trace)

```go
package main

import (
	"bytes"
	"fmt"
	"io"
)

type Brojac struct {
	io.Writer
	N int64
}

func (b *Brojac) Write(p []byte) (int, error) {
	n, err := b.Writer.Write(p)
	b.N += int64(n)
	return n, err
}

func main() {
	var buf bytes.Buffer
	br := &Brojac{Writer: &buf}
	fmt.Fprint(br, "hello")
	fmt.Println(br.N, buf.String())
}
```

#### What happens here

1. `Brojac` uses embedding of `io.Writer` — the type satisfies Writer through promotion, but `Write` is shadowed.
2. The outer `Write` counts bytes then delegates.
3. `fmt.Fprint` accepts `io.Writer` — `*Brojac` enters the box.
4. If `Writer` stays nil → panic on the first `Write` — that is why initialization in the composite literal.

### Exercise R6 — name instead of embedding when the API leaks

```go
type Store struct {
	mu sync.Mutex

func (s *Store) Get(k string) (int, bool) {
	s.mu.Lock()
	defer s.mu.Unlock()

```

#### What happens here

1. `Lock` is not on `Store`’s method set for outside packages as a promoted API.
2. Synchronization remains an implementation detail.
3. Embedded `sync.Mutex` would allow `store.Lock()` outside — usually bad.

## Summary

Embedding places a type as an anonymous field and promotes selectors, but remains has-a composition — not inheritance. Shadowing: the outer method wins. Ambiguity requires explicitness. Use embedding interfaces to join contracts; almost always name a mutex. Polymorphism works through an interface. Next lesson: type comparability.
