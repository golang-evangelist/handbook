# 07.01 Interfaces and Structs

> **Go Path - Zero to Gopher** / **01 Basics → Creating Custom Data Types With Go** / Lesson 07.01

## Lesson goals

After this lesson you should be able to:

- define a Go struct and a Go method on it;
- declare an interface and satisfy it **implicitly** (without `implements`);
- distinguish a small interface from an oversized “god” interface;
- explain the trap: a `nil` pointer inside a non-`nil` interface;
- choose a value or pointer receiver and connect that to the method set;
- define an interface on the consumer side for testability.

## Prerequisite

- Basic types, functions, pointers.
- Go 1.22+.
- Module 06 finished if possible (especially `fmt.Stringer` and a feel for `error`).

## Problem this lesson solves

Developers from class-based languages look for `implements` and inheritance. In Go:

- an interface is satisfied **automatically** if the required methods exist;
- `nil` behavior confuses and causes production bugs (`err != nil` always true);
- oversized interfaces couple code and make mocks hard in tests;
- a wrong receiver changes whether a value may enter an interface.

This lesson builds a practical mental model without imitating classical OOP.

## Mental model

**Struct** = data + (optionally) methods.  
**Interface** = a set of methods (behavior), without fields.

```text
value type  --methods-->  satisfies interface
```

An interface value is a “box” with two parts:

1. **dynamic type** — which concrete type is inside;
2. **dynamic value** — the value / pointer itself.

| Box state | `i == nil` |
|---------------|------------|
| both parts `nil` | `true` — a true nil interface |
| type `*T`, value `nil` | `false` — the box is not empty, only the pointer inside is |

That is the classic trap when returning `error` and in dependency injection.

The method set determines what may enter an interface:

- for type `T`: methods with receiver `T`;
- for type `*T`: methods with receiver `T` **and** `*T`.

That is why the error “`T` does not implement …” often means: you need a pointer or a different receiver.

## Mechanism

### Struct and methods

```go
type Account struct {
	ID      string
	Balance int
}

func (r *Account) Deposit(n int) { r.Balance += n }

func (r Account) String() string {
	return fmt.Sprintf("%s=%d", r.ID, r.Balance)
}
```

Line by line:

1. `Account` is a definition type whose underlying form is a struct with two fields.
2. `Deposit` has a pointer receiver: it changes `Balance` on the **same** object. Had it been `(r Account)`, the increment would go to a copy and disappear after return.
3. `String` has a value receiver: it only reads. A pointer would also work; here a value is enough.
4. Composite literal `Account{ID: "A", Balance: 0}` makes a value; the zero value of the struct has `""` and `0`.

### Interface and implicit satisfaction

```go
type Stringer interface {
	String() string
}
```

There is no `implements` keyword. If `Account` has `String() string`, the value (under method-set rules) may be passed where `Stringer` stands. The compiler checks at assignment / call.

### Nil trap — value trace

```go
func maybeErr(fail bool) error {
	var e *MyError
	if fail {
		e = &MyError{Msg: "x"}
	}
	return e // DANGEROUS when fail==false
}
```

When `fail == false`:

1. `e` is `*MyError` with value `nil`.
2. `return e` packs into interface `error`: dynamic type = `*MyError`, dynamic value = `nil`.
3. `err == nil` is **false**, because the box is not empty.
4. The caller enters `if err != nil` and calls `err.Error()` — often a panic on a nil receiver.

Correct:

```go
if fail {
	return &MyError{Msg: "x"}
}
return nil // a true nil interface
```

### Receiver and method set in practice

| Receiver | When |
|----------|------|
| `(t T)` | does not change state, small type, pure function over a copy |
| `(t *T)` | changes state or a large struct (avoids a copy) |

If any method needs a pointer, often the whole method set keeps pointer receivers for a consistent method set — easier satisfaction of an interface with `*T`.

Go on call `b.Inc()` on an addressable variable `b` automatically takes `&b` if the method is on `*T`. But a **value** `T` in an interface does not magically get pointer methods.

### Small interfaces and the consumer side

Idiom: interfaces with 1–3 methods (`io.Reader`, `io.Writer`). Define the interface where it is **used**, not next to every concrete type “just in case”.

```text
consumer defines Loader{ Load(...) }
production: Mem satisfies Loader
test: Fake also satisfies Loader
```

Common guidance: *accept interfaces, return structs* — functions take narrow behavior, return a concrete type.

### `any`

`any` is an alias for `interface{}` — the empty interface, accepts everything, loses type checking. Use sparingly (containers, serde boundaries), not as the default parameter of business logic.

## Rules and syntax

- Fields and methods that start with a capital letter are exported (visible from another package); lowercase — unexported. Do not say “public/private” in the OOP sense — say exported/unexported.
- An interface value compares to `nil` only when you want “no dynamic type”.
- Do not build a class hierarchy; compose (see 07.03).
- `error` is an interface — return a clean `nil`.

## Examples

### Example 1 — struct + methods + interface

```go
package main

import "fmt"

type Speaker interface {
	Say() string
}

type Person struct{ Name string }

func (c Person) Say() string { return "hello, I am " + c.Name }

type Robot struct{ Model string }

func (r Robot) Say() string { return "bip-" + r.Model }

func greet(g Speaker) {
	fmt.Println(g.Say())
}

func main() {
	greet(Person{Name: "Mila"})
	greet(Robot{Model: "X42"})
}
```

#### What happens here

1. `Speaker` requires one method — a small interface.
2. `Person` and `Robot` have no shared “base class”. Both have `Say` → both may go into `greet`.
3. `greet` depends on behavior, not on the concrete type. New type: add a method, do not change `greet`.
4. Trace: `greet(Person{...})` — the compiler checks the method set; the runtime box holds `Person` and calls `Say`.

### Example 2 — pointer receiver

```go
package main

import "fmt"

type Brojac struct{ N int }

func (b *Brojac) Inc() { b.N++ }

func main() {
	var b Brojac // zero value N=0
	b.Inc()
	fmt.Println(b.N) // 1
}
```

#### What happens here

1. `b` is an addressable variable. Call `b.Inc()` becomes `(&b).Inc()`.
2. Inside `Inc`, `b.N++` changes the original — after the call `N` is 1.
3. Had the receiver been a value, `main` would still see `0`.

### Example 3 — nil interface vs nil pointer

```go
package main

import "fmt"

type E struct{ M string }

func (e *E) Error() string { return e.M }

func bad() error {
	var p *E = nil
	return p
}

func good() error {
	return nil
}

func main() {
	var err error
	err = bad()
	fmt.Println("bad == nil?", err == nil) // false
	err = good()
	fmt.Println("good == nil?", err == nil) // true
}
```

#### What happens here

1. `bad` returns an interface whose type is `*E`, value nil → `err == nil` is false.
2. `good` returns a typeless nil interface → true.
3. This is the same mechanism as in `maybeErr`. Remember: **typed nil ≠ nil interface**.

### Example 4 — the consumer defines the interface

```go
package main

import "fmt"

type Ucitavac interface {
	Ucitaj(id string) (string, error)
}

func stampaj(u Ucitavac, id string) {
	s, err := u.Ucitaj(id)
	if err != nil {
		fmt.Println("error:", err)
		return
	}
	fmt.Println(s)
}

type Mem map[string]string

func (m Mem) Ucitaj(id string) (string, error) {
	v, ok := m[id]
	if !ok {
		return "", fmt.Errorf("no %s", id)
	}
	return v, nil
}

func main() {
	stampaj(Mem{"a": "apple"}, "a")
}
```

#### What happens here

1. The interface lives next to the consumer `stampaj`.
2. `Mem` is a Go map with a method — it satisfies `Ucitavac` without registration.
3. A test can substitute a fake type with the same method without changing production.
4. Early return on error keeps the happy path flat (see 08.02).

### Example 5 — method set and interface

```go
package main

import "fmt"

type Counter interface {
	Inc()
	Value() int
}

type C struct{ n int }

func (c *C) Inc()      { c.n++ }
func (c *C) Value() int { return c.n }

func main() {
	var c Counter = &C{}
	c.Inc()
	fmt.Println(c.Value())
	// var c2 Counter = C{} // does not compile: C has no method set with Inc
}
```

#### What happens here

1. Both methods are on `*C` → only `*C` satisfies `Counter`.
2. `&C{}` works. `C{}` as a value does not — the compiler rejects it.
3. Table: value `T` sees only `(T)` methods; `*T` sees `(T)` and `(*T)`.

### Example 6 — interface in a map (plugin registry)

```go
package main

import "fmt"

type Plugin interface {
	Name() string
	Start() error
}

type Ping struct{}

func (Ping) Name() string  { return "ping" }
func (Ping) Start() error { return nil }

func main() {
	registry := map[string]Plugin{
		"ping": Ping{},
	}
	p := registry["ping"]
	fmt.Println(p.Name(), p.Start())
}
```

#### What happens here

1. The map stores behavior, not a concrete type in the loop API.
2. Adding a plugin = a new entry + a type with methods; the loop over the registry does not change.

## Decision analysis

| Question | Guidance |
|---------|----------|
| Value or pointer receiver? | changes state → pointer |
| Where to define the interface? | at the consumer |
| How many methods? | as few as possible (1–3) |
| How to return “no error”? | `return nil`, not a typed nil |
| Polymorphism? | interface, not a “base class” |

## Trade-offs

| Style | Plus | Minus |
|------|------|-------|
| small interfaces | testability, flexibility | more small types |
| concrete types everywhere | simple | hard coupling |
| rich “service” interfaces | one place | hard mocking |
| `any` parameters | fast | loss of checking |

## Common mistakes

1. **Wrong:** `var p *T = nil; return p` as `error`.  
   **Effect:** `err != nil` always, often panic in `Error()`.  
   **Why:** typed nil in the box.  
   **Fix:** `return nil` or return a non-nil pointer only when there is an error.

2. **Wrong:** a value receiver that “looks like” it changes fields.  
   **Effect:** changes disappear; a hard-to-spot bug.  
   **Why:** the method works on a copy.  
   **Fix:** pointer receiver.

3. **Wrong:** an interface with 15 methods.  
   **Effect:** every fake in a test implements everything; the API is rigid.  
   **Why:** oversized contract.  
   **Fix:** split into small interfaces.

4. **Wrong:** defining an interface next to every struct “just in case”.  
   **Effect:** noise, wrong dependency.  
   **Why:** the interface belongs to the consumer.  
   **Fix:** define when another package/function truly abstracts.

5. **Wrong:** passing `T` where the interface requires pointer methods.  
   **Effect:** compiler error about the method set.  
   **Why:** `T` does not have those methods in the set.  
   **Fix:** pass `*T` or align the receiver.

6. **Wrong:** an exported huge interface from a library that the consumer does not control.  
   **Effect:** break when adding methods (broken compatibility).  
   **Why:** adding methods to an interface breaks implementers.  
   **Fix:** small, stable interfaces; or new versions carefully.

## Idiomatic Go

- Accept interfaces, return structs.
- `error` is an interface — return a clean nil.
- `String()` for display (cheap).
- Do not build a class hierarchy; compose.
- In tests fake types satisfy a small interface — without `reflect`.

## Practical scenario

A handler checked `if err != nil` after a repo call that returned `var e *NotFound; return e`. It always entered the error branch. Fix: `return nil`. Additionally, the repo interface was reduced to `Find(id) (Item, error)` instead of 20 methods — the mock in the test became readable. A method-set error on a PR (“User does not implement Store”) was fixed by passing `*User` instead of a value.

## Check questions

1. How does a type “implement” an interface in Go?  
   **Answer:** Implicitly — if all methods with matching signatures exist (method set).

2. What makes up an interface value?  
   **Answer:** Dynamic type + dynamic value.

3. Why is `var p *T = nil; return p` as `error` not nil?  
   **Answer:** The box has type `*T`; it is not an empty interface.

4. When a pointer receiver?  
   **Answer:** When the method changes state or when you want to avoid copying a large struct.

5. Why small interfaces?  
   **Answer:** Easier satisfaction, testing, and API evolution.

6. Where should an interface be defined by idiom?  
   **Answer:** On the consumer side.

7. What is `any`?  
   **Answer:** An alias for `interface{}` — accepts everything, no method.

## Deeper pass: the interface box step by step

```go
var g Speaker
g = Person{Name: "Mila"}
```

1. `g` starts as a nil interface (`g == nil` → true).
2. Assignment packs type `Person` and value `{Name:"Mila"}`.
3. `g == nil` → false.
4. `g.Say()` → lookup methods in the dynamic type’s method set → call.

```go
var p *Person = nil
g = p
```

1. The dynamic type is `*Person`, value nil.
2. `g == nil` → **false**.
3. If `Say` has a pointer receiver and dereferences without a check — panic.

That is why when returning `error`: either a true `nil`, or a non-nil pointer to a real error.

### Method set table (memorize)

| Value you pass | Methods available |
|---------------------------|-----------------|
| `T` | only `(T)` |
| `*T` | `(T)` and `(*T)` |

The compiler error “does not implement” often means: you need `&x` or to align the receiver.

### Interface checklist

1. Interface ≤ 3 methods without a strong need?
2. Definition at the consumer?
3. No typed nil as `error`?
4. Receivers consistent?
5. Test can fake without reflect?

## Workshop

Goal: implicit interface satisfaction, method set, pointer vs value receiver, and the typed nil trap. Work in small steps.

### Exercise R1 — small interface, two implementations

```go
package main

import "fmt"

type Speaker interface {
	Say() string
}

type Person struct{ Name string }

func (c Person) Say() string { return "hello, " + c.Name }

type Robot struct{ Model string }

func (r Robot) Say() string { return "bip-" + r.Model }

func greet(g Speaker) {
	fmt.Println(g.Say())
}

func main() {
	greet(Person{Name: "Mila"})
	greet(Robot{Model: "R2"})
}
```

#### What happens here

1. `Speaker` asks for only one method — a small interface.
2. No `implements`: `Person` and `Robot` satisfy the contract because they have `Say()`.
3. `greet` depends on behavior, not on a concrete struct — a test can pass a fake.
4. Composite literal `{Name: "Mila"}` makes a value of type `Person`.

### Exercise R2 — method set and receiver

```go
type Account struct{ Balance int }

func (r *Account) Deposit(n int) { r.Balance += n }

func (r Account) String() string {
	return fmt.Sprintf("balance=%d", r.Balance)
}

var s fmt.Stringer = Account{Balance: 10} // OK — String has a value receiver
// var u interface{ Deposit(int) } = Account{} // ERROR — need *Account
var u interface{ Deposit(int) } = &Account{}
u.Deposit(5)
```

#### What happens here

1. The method set for `T` contains methods with receiver `T`.
2. The method set for `*T` contains both `T` and `*T` receivers.
3. `Deposit` changes state → pointer receiver; that is why value `Account{}` does not enter an interface with `Deposit`.
4. The compiler error “does not implement” often means: add `&` or align the receiver.

| You pass | Available methods |
|-------------|-----------------|
| `T` | only `(T)` |
| `*T` | `(T)` and `(*T)` |

### Exercise R3 — typed nil trap

```go
type MojErr struct{ Msg string }

func (e *MojErr) Error() string { return e.Msg }

func loose() error {
	var e *MojErr = nil
	return e // BAD: non-nil interface, nil pointer inside
}

func tight() error {
	return nil // GOOD: true nil interface
}

func main() {
	err := loose()
	fmt.Println(err == nil) // false!
	if err != nil {
		fmt.Println("entering the branch even though there is no real error")
	}
	fmt.Println(tight() == nil) // true
}
```

#### What happens here

1. An interface box has a dynamic type and a dynamic value.
2. `return e` packs type `*MojErr` + nil value → the box is not nil.
3. `err == nil` is false — a classic production bug.
4. Return a bare `nil` or a non-nil pointer to a real error — never a typed nil “for empty”.

### Exercise R4 — interface on the consumer side

```go
// in the service package (consumer)
type SacuvajStor interface {
	Sacuvaj(id string, data []byte) error
}

type Servis struct{ store SacuvajStor }

func (s Servis) Registruj(id string, data []byte) error {
	return s.store.Sacuvaj(id, data)
}
```

In a test:

```go
type fake struct{ calls int }

func (f *fake) Sacuvaj(id string, data []byte) error {
	f.calls++
	return nil
}
```

#### What happens here

1. The consumer defines the interface — only methods it actually calls.
2. The fake does not need to pull a database; the test is fast.
3. The producer (e.g. `PostgresStore`) satisfies the contract without knowing the service.
4. An oversized interface would force a fake with dozens of empty methods.

### Decision table — value vs pointer receiver

| Question | Pointer | Value |
|---------|---------|-------|
| Changes state? | yes | — |
| Large struct? | often yes | small OK |
| Need in a map as a key? | caution | value comparable more often |
| Package consistency? | align style | align style |

### Workshop FAQ

**Q: Why is there no `implements`?**  
A: Implicit satisfaction reduces coupling; a new type “naturally” enters if it has the methods.

**Q: May an interface have fields?**  
A: No — only methods. Data lives in the struct.

**Q: What is `any`?**  
A: An alias for `interface{}` — empty method set, accepts everything.

**Q: When an empty interface in an API?**  
A: Rarely. Prefer a concrete small contract; `any` on a decode edge is OK.

**Q: Pointer or value in a slice of interfaces?**  
A: Depends on the method set. If you need pointer methods, store `*T`.

**Q: Can a struct “inherit” an interface?**  
A: It does not inherit; it can use interface embedding as a field — see the following lessons.

**Q: How do I debug the dynamic type?**  
A: `fmt.Printf("%T\n", i)` or a type assert / type switch.

### Edge cases

1. Nil interface vs a type with a nil pointer — compare `== nil`.
2. Value-receiver method called on a pointer — Go automatically dereferences on a method call, but the method set for assignment into an interface still applies.
3. Two packages, same method names, different types — no conflict; the box carries its type.
4. An exported method is needed for another package to satisfy the interface.

### Extra pass — from box to test

**Step 1 — consumer signature**

```go
type Sender interface {
	Send(to, body string) error
}
```

**Step 2 — production implementation**

```go
type SMTP struct{ Addr string }

func (s SMTP) Send(to, body string) error {
	if to == "" {
		return fmt.Errorf("empty receiver")
	}
	// ... network ...
	return nil
}
```

**Step 3 — fake**

```go
type spy struct {
	lastTo string
	n      int
}

func (s *spy) Send(to, body string) error {
	s.lastTo = to
	s.n++
	return nil
}
```

**Step 4 — service**

```go
type Mailer struct{ s Sender }

func (m Mailer) Welcome(email string) error {
	return m.s.Send(email, "welcome")
}
```

#### What happens here

1. `Mailer` does not know about SMTP — only `Sender`.
2. The test injects `spy` and checks `n` / `lastTo`.
3. Pointer receiver on `spy` because it changes state; `SMTP` can be value if immutable.
4. Typed nil: `func bad() Sender { var s *SMTP; return s }` — the box is not nil.

### Exercise R5 — `%T` diagnostics

```go
var g Speaker = Person{Name: "Ana"}
fmt.Printf("%T\n", g) // main.Person
```

#### What happens here

1. `%T` reveals the dynamic type in the box.
2. Useful before a type assert when debugging DI / factory.

### Table — nil checklist

| Expression | `== nil`? | Why |
|-------|-----------|-------|
| `var e error` | true | true nil interface |
| `var p *T; var e error = p` | false | type in the box |
| `return nil` | true | OK |
| `return (*T)(nil)` as error | false | typed nil |

## Summary

A struct carries data and methods; an interface describes behavior and is satisfied implicitly. The most dangerous trap is a nil pointer in a non-nil interface. The method set and receiver choice determine what may enter the box. Small interfaces on the consumer side lead to testable design. Next lesson: type definitions and aliases.
