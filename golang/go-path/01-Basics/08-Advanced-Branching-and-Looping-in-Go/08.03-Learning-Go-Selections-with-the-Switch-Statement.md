# 08.03 Learning Go Selections with the Switch Statement

> **Go Path - Zero to Gopher** / **01 Basics → Advanced Branching and Looping in Go** / Lesson 08.03

## Lesson goals

After this lesson you should be able to:

- write an expression `switch` and a switch **without** an expression;
- group branches with multi-case syntax;
- explain that Go does **not** fall through by default (unlike C/Java) and why `fallthrough` is rarely wanted;
- use init in a switch;
- distinguish an expression switch from a type switch (07.05);
- build a CLI command router as a mini project.

## Prerequisite

- 08.01–08.02, 06.01 (CLI feel).
- Go 1.22+.
- 07.05 for type switch (related topic; here expression switch).

## Problem this lesson solves

Long `if else if` chains for commands and status codes become noisy. `switch` organizes them. But:

- people expect C `fallthrough` by default — in Go they do **not**;
- they forget `default`;
- they mix expression switch and type switch;
- they use `fallthrough` instead of a shared function or multi-case.

## Mental model

```text
switch expression {
case a, b:  // multi — same body, without fallthrough
case c:
default:
}
```

Without an expression:

```text
switch {
case x > 0:
case x == 0:
default:
}
```

**Key difference from C:** after a case branch body, execution does **not** fall into the next case. You do not need `break` to stop falling. `break` exists for early exit from the switch, but is rarely needed.

`fallthrough` explicitly continues into the **next** case (without re-checking its condition). It is rarely desirable: easy to misread, hard to test, often better solved with multi-case or a shared function.

Why you rarely want fallthrough:

1. The reader assumes the case stops — the surprise is a bug.
2. The next case is not evaluated — the “condition” of the next branch is ignored.
3. Sharing logic is clearer via a helper function or `case a, b:`.

## Mechanism

### Expression switch

```go
switch dan {
case "pon", "uto", "sre", "cet", "pet":
	fmt.Println("weekday")
case "sub", "ned":
	fmt.Println("weekend")
default:
	fmt.Println("unknown")
}
```

The expression is evaluated once. Case values must be comparable with the expression’s type. Multi-case = a list of equalities for the **same** body.

### Switch without an expression

```go
switch {
case ocena >= 90:
	...
case ocena >= 80:
	...
}
```

Each case is a bool. Order matters (the first that is true wins) — like an if/else chain, more readable when there are several thresholds.

### Init

```go
switch x := f(); x {
case 1:
	...
}
```

`x` lives in the switch scope.

### Fallthrough (rarely)

```go
switch n {
case 1:
	fmt.Println("one")
	fallthrough
case 2:
	fmt.Println("and two?")
}
```

For `n == 1` it prints both lines. For `n == 2` only the second. Do not use as a substitute for multi-case.

### Type switch — not this lesson

`switch v := x.(type)` is 07.05. Here: expression switch over values.

## Rules and syntax

- Case values comparable with the expression.
- No default fallthrough — a case stops by itself.
- `default` optional but recommended when input can be unexpected.
- Do not mix with `switch v := x.(type)`.
- Normalize a string (`ToLower`) before the switch to reduce the number of cases.

## Examples

### Example 1 — expression switch, no falling

```go
package main

import "fmt"

func main() {
	kod := 404
	switch kod {
	case 200:
		fmt.Println("ok")
	case 400, 401, 403:
		fmt.Println("client error")
	case 404:
		fmt.Println("not found")
	case 500, 502, 503:
		fmt.Println("server error")
	default:
		fmt.Println("other status")
	}
}
```

#### What happens here

1. `kod` is 404 — hits case 404, prints the message.
2. It does **not** fall into the 500 branch — no C fallthrough.
3. Multi-case 400/401/403 shares a body without the `fallthrough` keyword.

### Example 2 — switch without an expression

```go
package main

import "fmt"

func zona(temp int) string {
	switch {
	case temp < 0:
		return "freezing"
	case temp < 15:
		return "cold"
	case temp < 25:
		return "pleasant"
	default:
		return "hot"
	}
}

func main() {
	fmt.Println(zona(12)) // cold
}
```

#### What happens here

1. For 12: first case false, second (`< 15`) true → `"cold"`.
2. Threshold order matters — if `< 25` were before `< 15`, wrong result.
3. More readable than a long if-else when there are several ranges.

### Example 3 — init and why to avoid fallthrough

```go
package main

import "fmt"

func main() {
	switch x := 1; x {
	case 1:
		fmt.Println("case 1")
		// fallthrough // uncomment: would also run case 2
	case 2:
		fmt.Println("case 2")
	}
	stampajMali(1)
}

func stampajMali(x int) {
	if x == 1 || x == 2 {
		fmt.Println("small", x)
	}
}
```

#### What happens here

1. Init declares `x` for the switch.
2. Without fallthrough only “case 1”.
3. With fallthrough case 2 would also run **without** checking `x == 2` — that is why it is dangerous.
4. `stampajMali` shows clearer sharing of logic than fallthrough.

### Example 4 — string commands

```go
package main

import (
	"fmt"
	"strings"
)

func main() {
	cmd := strings.ToLower("HeLp")
	switch cmd {
	case "help", "h", "?":
		fmt.Println("help")
	case "version", "v":
		fmt.Println("1.0.0")
	default:
		fmt.Println("unknown")
	}
}
```

#### What happens here

1. Normalization before the switch reduces cases.
2. Command aliases go into multi-case.
3. Default catches noise — important for a CLI.

## Mini project — CLI command router

Goal: a tool with commands `greet`, `add`, `version`, `help`. The router is a `switch` on the first word.

```go
package main

import (
	"errors"
	"fmt"
	"os"
	"strconv"
	"strings"
)

func main() {
	if err := route(os.Args[1:]); err != nil {
		fmt.Fprintln(os.Stderr, err)
		if errors.Is(err, errUsage) {
			os.Exit(2)
		}
		os.Exit(1)
	}
}

var errUsage = errors.New("usage: router <greet|add|version|help> ...")

func route(args []string) error {
	if len(args) < 1 {
		return errUsage
	}
	switch strings.ToLower(args[0]) {
	case "greet", "g":
		return cmdGreet(args[1:])
	case "add":
		return cmdAdd(args[1:])
	case "version", "v":
		fmt.Println("router 1.0.0")
		return nil
	case "help", "h", "?":
		printHelp()
		return nil
	default:
		return fmt.Errorf("unknown command %q: %w", args[0], errUsage)
	}
}

func printHelp() {
	fmt.Print(`commands:
  greet <name>   greet
  add <a> <b>    add two integers
  version        print version
  help           this message
`)
}

func cmdGreet(args []string) error {
	if len(args) < 1 {
		return fmt.Errorf("greet requires a name: %w", errUsage)
	}
	ime := strings.Join(args, " ")
	fmt.Printf("hello, %s\n", ime)
	return nil
}

func cmdAdd(args []string) error {
	if len(args) != 2 {
		return fmt.Errorf("add requires two numbers: %w", errUsage)
	}
	a, err := strconv.Atoi(args[0])
	if err != nil {
		return fmt.Errorf("first is not int: %w", err)
	}
	b, err := strconv.Atoi(args[1])
	if err != nil {
		return fmt.Errorf("second is not int: %w", err)
	}
	fmt.Println(a + b)
	return nil
}
```

```bash
go run . greet Ana
go run . add 2 3
go run . help
go run . foo
```

#### What happens here (mini project)

1. `main` maps the error to exit: Usage → 2, other → 1 (06.01).
2. `route` switches on the normalized command name; multi-case for aliases.
3. Each command is a function — the switch stays a thin router, without fallthrough.
4. `default` wraps `errUsage` via `%w` — `errors.Is` works in `main`.
5. No C-style falling from `greet` into `add` — each branch stops after `return`.

## Decision analysis

| Situation | Tool |
|-----------|------|
| discrete values / commands | expression switch |
| ranges / bool conditions | switch without expression or if |
| dynamic Go types | type switch (07.05) |
| sharing a body for a and b | multi-case, not fallthrough |
| CLI router | switch + functions per command |

## Trade-offs

| | switch | if/else |
|--|--------|---------|
| many equalities | cleaner | noisy |
| ranges | switch{} OK | if often equal |
| fallthrough | exists but a late smell | N/A |

## Common mistakes

1. **Wrong:** expecting C fallthrough (forgotten break “lets” the next case run).  
   **Effect:** in Go a case does **not** fall — the “bug” you expect does not happen; or conversely you add fallthrough by mistake.  
   **Why:** Go ends a case by default.  
   **Fix:** learn the model without falling; multi-case for the same body.

2. **Wrong:** `fallthrough` to share logic.  
   **Effect:** the next case runs without checking the condition — confusing flow.  
   **Why:** fallthrough does not re-evaluate the case.  
   **Fix:** multi-case or a shared function.

3. **Wrong:** mixing with type switch syntax.  
   **Effect:** wrong tool for the problem.  
   **Why:** `.(type)` is a different construct.  
   **Fix:** expression switch for values; type switch for types.

4. **Wrong:** no `default` on CLI input.  
   **Effect:** silence on an unknown command.  
   **Why:** forgotten edge.  
   **Fix:** default → Usage error.

5. **Wrong:** huge bodies in case branches.  
   **Effect:** unreadable router.  
   **Why:** a switch should direct.  
   **Fix:** `cmdX` functions (mini project).

6. **Wrong:** wrong order in a switch without an expression.  
   **Effect:** a wider condition “eats” a narrower one.  
   **Why:** the first true wins.  
   **Fix:** order thresholds from narrower to wider (as in `zona`).

## Idiomatic Go

- No default fallthrough — rely on that.
- Multi-case for aliases.
- Thin case branches + functions.
- `default` for unknown input.
- Normalize a string before the switch.

## Practical scenario

A team ported a C switch with deliberate fallthrough for “code groups”. In Go they forgot that a case stops — logic “broke” until they moved to multi-case. A CLI router with fallthrough from `help` into `version` accidentally printed both — fallthrough removed, separate functions introduced. Exit codes 1/2 wired through `errors.Is(errUsage)`.

## Check questions

1. Does a Go case fall into the next without `break`?  
   **Answer:** No — there is no default fallthrough.

2. What is `fallthrough` for and why is it rare?  
   **Answer:** It forces entry into the next case without a check; confusing — better multi-case/function.

3. Difference expression switch vs switch without an expression?  
   **Answer:** The first compares a value; the second a sequence of bool conditions.

4. Difference from a type switch?  
   **Answer:** A type switch chooses by the dynamic type of an interface (`.(type)`).

5. How do you group multiple values into the same body?  
   **Answer:** `case a, b, c:` — multi-case.

6. Why a thin router + `cmdX`?  
   **Answer:** Readability, testing, fewer conflicts in the switch file.

7. How does the mini project choose exit 2?  
   **Answer:** `errors.Is(err, errUsage)` in `main`.

## Deeper pass: fallthrough versus multi-case (table)

| Goal | Bad path | Good path |
|------|---------|-----------|
| Same body for 400 and 401 | fallthrough chain | `case 400, 401:` |
| Sharing part of the logic | fallthrough into case 2 | `helper()` from both branches |
| C habit “forget break” | expect falling | in Go there is none — relax |

### Why you “rarely want” fallthrough — one more trace

```go
switch n {
case 1:
	fmt.Println("A")
	fallthrough
case 2:
	fmt.Println("B") // runs even when n==1!
}
```

The reader thinks: “case 2 only when n==2”. Fallthrough lies to that intuition. That is why code review often rejects it.

### Switch checklist

1. Do you expect C fallthrough? → drop the habit.  
2. Do you need the same body? → multi-case.  
3. Do you need shared logic? → function.  
4. Is there default for CLI?  
5. Are you mixing with type switch?  
6. Are case bodies thin?

### Exercise R1 — basic switch

```go
package main

import "fmt"

func statusTekst(kod int) string {
	switch kod {
	case 200:
		return "ok"
	case 400, 401, 403:
		return "client"
	case 500, 502, 503:
		return "server"
	default:
		return "unknown"
	}
}

func main() {
	fmt.Println(statusTekst(401))
}
```

#### What happens here

1. Each `case` stops at the end — no default fallthrough as in C.
2. Multi-case `400, 401, 403` shares the same body without `fallthrough`.
3. `default` catches everything else — required for CLI/API input.
4. `return` in a case makes the branch thin and clear.

### Exercise R2 — deliberate fallthrough (to see why it is rare)

```go
n := 1
switch n {
case 1:
	fmt.Println("A")
	fallthrough
case 2:
	fmt.Println("B")
}
```

#### What happens here

1. `fallthrough` forces entry into the next case **without** checking the condition.
2. For `n==1` it prints both A and B — often a surprise.
3. Code review usually asks for multi-case or a helper instead of fallthrough.
4. Use only when you really want “continue into the next body”.

### Exercise R3 — switch without an expression

```go
func zona(temp int) string {
	switch {
	case temp < 0:
		return "icy"
	case temp < 15:
		return "cold"
	case temp < 25:
		return "pleasant"
	default:
		return "hot"
	}
}
```

#### What happens here

1. Switch without an expression = a chain of bool conditions, more readable than deep if/else.
2. Case order matters — the first hit wins.
3. Good for ranges; for discrete constants prefer an expression switch.

### Exercise R4 — thin router

```go
func route(cmd string, args []string) error {
	switch cmd {
	case "add":
		return cmdAdd(args)
	case "list", "ls":
		return cmdList(args)
	case "help", "-h", "--help":
		return cmdHelp(args)
	default:
		return fmt.Errorf("%w: %s", errUsage, cmd)
	}
}
```

#### What happens here

1. The switch only chooses; logic lives in `cmdX` functions.
2. Multi-case covers aliases (`list`/`ls`).
3. `main` maps `errUsage` to exit 2 via `errors.Is`.
4. You test `route` with buffers without `os.Exit`.

### Decision table

| Goal | Bad path | Good path |
|------|---------|-----------|
| Same body for multiple values | fallthrough chain | multi-case |
| Shared logic | fallthrough | shared function |
| Ranges | long if/else | switch without expression |
| C “forget break” | expect falling | in Go there is none |
| Type by dynamic type | this switch | type switch (`.(type)`) |

### Workshop FAQ

**Q: Do you need `break` at the end of a case?**  
A: Not to stop — the case already stops. `break` can exit the case body early.

**Q: Is switch on strings slow?**  
A: For a CLI negligible. The compiler may optimize; readability first.

**Q: Can a case have an expression?**  
A: A case compares equality (or bool in a switch without an expression), not arbitrary ranges in an expression switch — for ranges use a switch without an expression.

**Q: Fallthrough and multi-case together?**  
A: Rarely makes sense; avoid the combination.

**Q: Switch in a loop + break?**  
A: `break` without a label exits the switch, not the for — use a label or return.

**Q: When a map of functions instead of switch?**  
A: When you register plugins/commands dynamically; for a closed set switch is clear.

**Q: Init in switch?**  
A: `switch x := f(); x { ... }` — scope like if init.

### Edge cases

1. Empty switch case body — allowed, but document why.
2. Duplicate case value — compiler error.
3. `fallthrough` into the last case — often pointless.
4. Large case with I/O — extract a function for testing.

### Comparison with type switch (branch)

| Value switch | Type switch |
|--------------|-------------|
| `switch x` | `switch x.(type)` |
| compares values | compares dynamic type |
| CLI codes, enum-like | decode `any` |

Do not mix them in the same head until you separate the purpose.

### Extra pass — CLI router with exit codes

```go
package main

import (
	"errors"
	"fmt"
	"os"
	"strings"
)

var errUsage = errors.New("usage")

func cmdAdd(args []string) error {
	if len(args) < 2 {
		return fmt.Errorf("%w: add a b", errUsage)
	}
	// ... add ...
	return nil
}

func cmdHelp(args []string) error {
	fmt.Println("commands: add, list, help")
	return nil
}

func route(cmd string, args []string) error {
	switch cmd {
	case "add":
		return cmdAdd(args)
	case "list", "ls":
		return cmdHelp(args) // placeholder
	case "help", "-h", "--help":
		return cmdHelp(args)
	default:
		return fmt.Errorf("%w: unknown %q", errUsage, cmd)
	}
}

func main() {
	if len(os.Args) < 2 {
		fmt.Fprintln(os.Stderr, "usage: tool <cmd>")
		os.Exit(2)
	}
	cmd := strings.ToLower(os.Args[1])
	if err := route(cmd, os.Args[2:]); err != nil {
		fmt.Fprintln(os.Stderr, err)
		if errors.Is(err, errUsage) {
			os.Exit(2)
		}
		os.Exit(1)
	}
}
```

#### What happens here

1. The switch chooses the command; bodies are thin functions.
2. `errUsage` + `errors.Is` chooses exit 2 (bad usage) versus 1 (other).
3. `os.Exit` only in `main` — `route` stays testable.
4. Multi-case covers aliases without fallthrough.

### Exercise R7 — break from case in a loop

```go
for _, kod := range []int{200, 500, 200} {

	case 500:
```

#### What happens here

1. The same trap as with for+switch in loops.
