# 08.02 Learning Go Selections with if/Else Statements

> **Go Path - Zero to Gopher** / **01 Basics → Advanced Branching and Looping in Go** / Lesson 08.02

## Lesson goals

After this lesson you should be able to:

- use `if init; condition` and understand the scope of variables from the init;
- prefer early return (guard clauses) over deep nesting;
- combine if with comma-ok patterns (map, type assert);
- write readable branches without “else hell”;
- build a grade and status classifier as a mini project.

## Prerequisite

- Basic bool operations and errors.
- Go 1.22+.
- 08.01 preferred; 06.01 for a CLI feel in the mini project.

## Problem this lesson solves

Code with five levels of `if/else` is hard to read and test. Also, people forget:

- the scope of a variable from `if init` (it does not “leak” outward — that is a feature);
- comma-ok on map / type assert;
- that `else` is often unnecessary after `return`;
- that braces `{}` in Go **are** required even for a single statement.

## Mental model

`if` in Go can have a **short statement** before the condition:

```go
if err := rad(); err != nil {
	return err
}
```

`err` lives only in the if/else block — less name leakage into the outer scope.

**Early return**: handle the error/invalid case immediately and exit. The happy path stays left-aligned, like a list of guards (guard clauses), not like a pyramid.

```text
check edge → return
check edge → return
main logic
return success
```

## Mechanism

### Basic if/else

```go
if x > 0 {
} else if x == 0 {
} else {
}
```

- Condition **without** required parentheses around the expression: `if x > 0 {` (not C-style `if (x)` as a style).
- The `{}` block is **always** required.

### If with init

```go
if v, ok := m[k]; ok {
	fmt.Println(v)
}
```

1. Init runs once.
2. The condition uses the init result.
3. Variables from init apply in if **and** else, not outside that.

### Early return

```go
func f(x int) error {
	if x < 0 {
		return fmt.Errorf("negative")
	}
	// main logic
	return nil
}
```

After `return` in the if branch, `else` is redundant. Less indentation = fewer bugs.

### Comma-ok

The same form for a map and a type assert:

```go
v, ok := m[k]
s, ok := x.(string)
```

Often you join it into the condition: `if v, ok := m[k]; ok { ... }`.

## Rules and syntax

- Block braces `{}` required.
- The init statement may be simple; do not treat it as a place for heavy logic with side-effects that are hard to test.
- Prefer positive, short guards at the top.
- Do not fear several consecutive `if`s with `return` — that is not “bad style” in Go.

## Examples

### Example 1 — if init with an error

```go
package main

import (
	"fmt"
	"os"
)

func main() {
	if data, err := os.ReadFile("config.txt"); err != nil {
		fmt.Fprintln(os.Stderr, "no config:", err)
	} else {
		fmt.Println("bytes:", len(data))
	}
	// data does not exist here
}
```

#### What happens here

1. `ReadFile` is called in the init; `data` and `err` enter the if/else scope.
2. On error the stderr branch; on success it prints the length.
3. Outside the block `data` does not exist — reduces shadowing and accidental use of an uninitialized name.

### Example 2 — early return vs nested

```go
package main

import "fmt"

func opisNested(x int) string {
	if x >= 0 {
		if x <= 100 {
			return "ok"
		} else {
			return "too large"
		}
	} else {
		return "negative"
	}
}

func opisEarly(x int) string {
	if x < 0 {
		return "negative"
	}
	if x > 100 {
		return "too large"
	}
	return "ok"
}

func main() {
	fmt.Println(opisEarly(50))
	fmt.Println(opisNested(50))
}
```

#### What happens here

1. Both functions for `50` return `"ok"`.
2. The nested version indents the happy path and multiplies `else`.
3. The early version reads top-down: edges first, then success — idiomatic Go.

### Example 3 — comma-ok patterns

```go
package main

import "fmt"

func main() {
	m := map[string]int{"ana": 5}
	if v, ok := m["ana"]; ok {
		fmt.Println("ana", v)
	}
	if _, ok := m["marko"]; !ok {
		fmt.Println("marko is not in the map")
	}

	var x any = "hey"
	if s, ok := x.(string); ok {
		fmt.Println("string length", len(s))
	}
}
```

#### What happens here

1. Map lookup: `ok` distinguishes “key exists with value 0” from “no key”.
2. Type assert: the same form prevents panic (07.05).
3. The check is part of the condition, not a later `if ok` after assignment.

### Example 4 — bool functions in the condition

```go
package main

import (
	"fmt"
	"strings"
)

func main() {
	email := " tim@firma.rs "
	if e := strings.TrimSpace(email); strings.Contains(e, "@") && len(e) > 5 {
		fmt.Println("looks like email:", e)
	}
}
```

#### What happens here

1. Init prepares `e` once — trim is not repeated in the body.
2. The condition combines two checks with `&&` (short-circuit: if there is no `@`, `len` need not be looked at in the same priority sense — here both use `e`).
3. Scope of `e` stays in the if block.

## Mini project — grade/status classifier

Goal: CLI takes a numeric grade (0–100) and an optional attendance flag; prints a letter grade and status.

```go
package main

import (
	"flag"
	"fmt"
	"os"
	"strconv"
)

func main() {
	prisutan := flag.Bool("prisutan", true, "whether the student attended")
	flag.Parse()
	if flag.NArg() != 1 {
		fmt.Fprintln(os.Stderr, "usage: classifier [-prisutan=true|false] grade")
		os.Exit(2)
	}
	ocena, err := strconv.Atoi(flag.Arg(0))
	if err != nil {
		fmt.Fprintln(os.Stderr, "grade must be an integer")
		os.Exit(2)
	}

	slovo, st, err := klasifikuj(ocena, *prisutan)
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	fmt.Printf("grade=%s status=%s\n", slovo, st)
}

func klasifikuj(ocena int, prisutan bool) (slovo string, status string, err error) {
	if ocena < 0 || ocena > 100 {
		return "", "", fmt.Errorf("grade out of range: %d", ocena)
	}
	if !prisutan {
		return "F", "absent", nil
	}
	if ocena >= 90 {
		return "A", "excellent", nil
	}
	if ocena >= 80 {
		return "B", "very_good", nil
	}
	if ocena >= 70 {
		return "C", "good", nil
	}
	if ocena >= 60 {
		return "D", "satisfactory", nil
	}
	return "F", "failed", nil
}
```

```bash
go run . 85
go run . -prisutan=false 95
go run . 120
```

#### What happens here (mini project)

1. Range guard first — do not classify invalid input.
2. Attendance short-circuits to F / absent before the ladder.
3. Early-return ladder instead of an `else if` pyramid — easy to insert a new threshold.
4. CLI: flag + positional; exit 2 for usage (06.01).
5. `klasifikuj` is a pure function — easy to test without I/O.
6. Errors on stderr; result on stdout.

## Decision analysis

| Style | When |
|------|------|
| early return | errors, validation, guard |
| else if chain | mutually exclusive nearby branches without return |
| if init | temporary values with the condition |
| switch | many equal discrete values (08.03) |

## Trade-offs

| Style | Plus | Minus |
|------|------|-------|
| early return | flat happy path | more `return` points |
| deep nest | one exit point | pyramid, hard to read |
| if init | narrow scope | a crowded init confuses |

## Common mistakes

1. **Wrong:** expecting `err` from if init to live after the block.  
   **Effect:** does not compile / shadowing with an outer `err`.  
   **Why:** scope is if/else.  
   **Fix:** declare outside if needed after, or handle everything in the block.

2. **Wrong:** `else` after `return` in if.  
   **Effect:** unnecessary indentation.  
   **Why:** return already ends the branch.  
   **Fix:** delete else; continue at the same level.

3. **Wrong:** `v := m[k]` without `ok` when 0/"" can be a valid value.  
   **Effect:** you cannot tell “no key” from zero value.  
   **Why:** a map index always “returns” a value.  
   **Fix:** comma-ok.

4. **Wrong:** if without `{}` (habit from another language).  
   **Effect:** compiler error.  
   **Why:** Go requires blocks.  
   **Fix:** always `{}`.

5. **Wrong:** heavy logic in the if init.  
   **Effect:** hard testing and reading.  
   **Why:** init should be short.  
   **Fix:** extract a function; in if only the result.

6. **Wrong:** a pyramid of 4+ levels instead of guards.  
   **Effect:** bugs in “else” branches.  
   **Why:** cognitive load.  
   **Fix:** early return.

## Idiomatic Go

- Guard clauses at the top of the function.
- `if err != nil { return ... }` right after the call.
- Comma-ok in the condition.
- Pure functions for classification (mini project) separated from CLI I/O.

## Practical scenario

A handler had five levels of if/else for request validation. The reviewer could not see the happy path. Moving to early return reduced diff conflicts and enabled a unit test only over a `klasifikuj`-like function. Another bug: `score := m[user]` treated 0 as “no grade” — comma-ok separated the cases.

## Check questions

1. Where do variables from `if init` live?  
   **Answer:** In the if and else block, not outside them.

2. What is early return?  
   **Answer:** Handling the edge and `return` immediately, so the happy path stays flat.

3. Why comma-ok on a map?  
   **Answer:** Distinguishes missing key from zero value.

4. Does Go allow if without `{}`?  
   **Answer:** No — the block is required.

5. When is `else` after return not needed?  
   **Answer:** Always when the if branch already returns — continuation can be at the same level.

6. Why is `klasifikuj` separate from `main`?  
   **Answer:** Testability without I/O and exit codes.

7. How does if init help with `ReadFile`?  
   **Answer:** Local scope for `data`/`err`; clear error vs success branch.

## Deeper pass: guard clauses in an HTTP handler (analogy)

The same pattern as in `klasifikuj` you see in handlers:

```go
func handle(w http.ResponseWriter, r *http.Request) {
	id := r.PathValue("id")
	if id == "" {
		http.Error(w, "no id", http.StatusBadRequest)
		return
	}
	item, err := repo.Find(id)
	if err != nil {
		http.Error(w, "not found", http.StatusNotFound)
		return
	}
	// happy path — without an else pyramid
	_ = json.NewEncoder(w).Encode(item)
}
```

Every edge ends with `return`. The happy path stays at the bottom, left-aligned.

### Table test sketch for klasifikuj

```go
func TestKlasifikuj(t *testing.T) {
	tests := []struct {
		ocena    int
		prisutan bool
		slovo    string
		wantErr  bool
	}{
		{85, true, "B", false},
		{95, false, "F", false},
		{120, true, "", true},
	}
	for _, tt := range tests {
		slovo, _, err := klasifikuj(tt.ocena, tt.prisutan)
		if tt.wantErr {
			if err == nil {
				t.Fatalf("expected error")
			}
			continue
		}
		if err != nil || slovo != tt.slovo {
			t.Fatalf("got %q err=%v", slovo, err)
		}
	}
}
```

## Workshop

Goal: `if` with init, early return (guard clauses), comma-ok, and avoiding else pyramids.

### Exercise R1 — if with init scope

```go
package main

import (
	"fmt"
	"os"
)

func main() {
	if data, err := os.ReadFile("config.txt"); err != nil {
		fmt.Println("error:", err)
		return
	} else {
		fmt.Println("bytes", len(data))
	}
	// data is not visible here
}
```

Better style — early return without else:

```go
data, err := os.ReadFile("config.txt")
if err != nil {
	fmt.Println("error:", err)
	return
}
fmt.Println("bytes", len(data))
```

#### What happens here

1. `if init; condition` narrows variable scope to the if/else branches.
2. Early return keeps the happy path left, without a pyramid.
3. `data` after the error check is reliably available.
4. In tests prefer functions that return value+error instead of printing.

### Exercise R2 — guard clauses

```go
func klasifikuj(ocena int, prisutan bool) (string, string, error) {
	if ocena < 0 || ocena > 100 {
		return "", "", fmt.Errorf("grade out of range: %d", ocena)
	}
	if !prisutan {
		return "F", "absent", nil
	}
	if ocena >= 90 {
		return "A", "excellent", nil
	}
	if ocena >= 80 {
		return "B", "very_good", nil
	}
	if ocena >= 70 {
		return "C", "good", nil
	}
	return "D", "sufficient", nil
}
```

#### What happens here

1. Edge conditions end the function immediately (`return`).
2. No `else` after return — more readable.
3. Happy / main logic stays at the bottom.
4. Named result is not required; here we return letter, status, and `error`.
5. An error is a value (`error`), not a panic or exit.

### Exercise R3 — comma-ok for map and assert

```go
m := map[string]int{"a": 1}
if v, ok := m["a"]; ok {
	fmt.Println("has", v)
} else {
	fmt.Println("no key")
}

var x any = "hi"
if s, ok := x.(string); ok {
	fmt.Println(s)
}
```

#### What happens here

1. A map lookup without `ok` returns the zero value — you do not know whether the key existed.
2. An assert without `ok` panics; with `ok` you branch calmly.
3. The idiom `if v, ok := ...; ok {` joins init and condition.

### Exercise R4 — pyramid vs flattened

```go
// BAD
if a {
	if b {
		if c {
			doWork()
		}
	}
}

// BETTER
if !a {
	return
}
if !b {
	return
}
if !c {
	return
}
doWork()
```

#### What happens here

1. Deep nesting reduces readability and makes error handling harder.
2. Negated guard + return flattens control flow.
3. Go fmt does not force this — team discipline does.

### Decision table — if patterns

| Situation | Pattern |
|-----------|---------|
| Error then continue | early return |
| Temporary vars only in the branch | if init |
| Map / assert | comma-ok |
| Two symmetric branches | if/else OK |
| Many discrete values | consider `switch` |

### Exercise R5 — always `{}`

```go
if ok {
	doWork()
}
// if ok doWork() // not allowed — braces required
```

#### What happens here

1. Go requires a `{}` block — prevents classic C “dangling else” bugs.
2. `gofmt` aligns `else` with the closing brace.

### Workshop FAQ

**Q: May if init call a function with an error?**  
A: Yes — a common idiom exactly for `Create`/`Read`/`Parse`.

**Q: Else after return — forbidden?**  
A: Not forbidden; often redundant and noisy. Prefer without else.

**Q: How do I test branches?**  
A: Table-driven: input → expected output/err.

**Q: Ternary operator?**  
A: Go does not have one. Use if or a small function.

**Q: `if err != nil` fatigue?**  
A: Deliberately explicit. Guard clauses keep the noise under control.

**Q: Scope leaking from if init?**  
A: Variables from init are not visible after the whole if/else.

**Q: When leave else?**  
A: When two branches are peer and both return/do something — readability beats dogma.

### Edge cases

1. `if err != nil` after several calls — check you have not overwritten `err`.
2. Shadowing: `if data, err := ...` vs an existing `err` in the function.
3. Bool from a function + error — do not ignore the error because of the bool.
4. Negation of a complex condition — parentheses for clarity.

### Extra pass — table test + guard in practice

```go
func TestKlasifikuj(t *testing.T) {
	tests := []struct {
		name     string
		ocena    int
		prisutan bool
		slovo    string
		wantErr  bool
	}{
		{"B present", 85, true, "B", false},
		{"absent", 95, false, "F", false},
		{"out of range", 120, true, "", true},
		{"boundary A", 90, true, "A", false},
		{"boundary D", 0, true, "D", false},
	}
	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			got, _, err := klasifikuj(tt.ocena, tt.prisutan)
			if tt.wantErr {
				if err == nil {
					t.Fatalf("expected error")
				}
				return
			}
			if err != nil || got != tt.slovo {
				t.Fatalf("got %q err=%v want %q", got, err, tt.slovo)
			}
		})
	}
}
```

#### What happens here

1. The table covers edges better than one happy example.
2. `t.Run` names the subtest — a failure shows immediately.
3. `klasifikuj` has no `fmt`/`os` — the test is fast and deterministic.
4. Guard in production code = the same edges as in the table.

### Exercise R6 — shadowing err

```go
func ucitajIObradi(path string) error {
	data, err := os.ReadFile(path)
	if err != nil {
		return err
	}
	if err := obradi(data); err != nil { // new err in if init scope
		return fmt.Errorf("obradi: %w", err)
	}
	return nil
}
```

#### What happens here

1. The second `err` in `if init` shadows the outer — deliberate local scope.
2. After the if the outer `err` is still nil from ReadFile — do not mix them.
3. Prefer clear names or early return so shadowing does not confuse.

### Exercise R7 — bool + error

```go
func nadji(m map[string]int, k string) (int, bool, error) {
	if m == nil {
		return 0, false, fmt.Errorf("nil map")
	}
	v, ok := m[k]
	return v, ok, nil
}
```

#### What happens here

1. `ok` is not a substitute for `error` — different axes (key exists vs system error).
2. Do not ignore `err` because of `ok`.
3. In a simpler API you often stop at `(v, error)` or `(v, bool)` — do not force all three without need.
